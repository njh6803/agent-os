# 기본 에이전트 `assistant`의 코드는 일에 묶이지 않고, 문서 검색은 스킬·연결 플러그인·규칙 파일에 둔다. 커스텀 에이전트는 그 폴더를 복사해 만든다

기준선(ADR 0046)은 "참조 에이전트 doc-qa"를 두기로 했고, 기능 계획 doc-qa-agent는 그것을 문서 검색 서버를 불러 근거를 찾고 출처를 달아 답하는 에이전트로 적었다. 설계 인터뷰(일지 2026-11-10-1345)는 다섯 라운드에 걸쳐 그 모양(누가 검색하는지, 어디에 두는지, 출처의 모양, 실행의 끝)을 정했고, 합의 요약 첫 판에서 사용자가 방향을 바꿨다. "문서 질의응답 에이전트 (doc-qa-agent) 이름이 마음에 안들어. 지금 만드는 걸 기본 기본 에이전트로 만들껀데. 문서에 대한 질의 응답만 하는게 아니라 승인 같은 기능도 있잖아." 뜻을 묻자 "함께 내는 대표 에이전트라기보다는 이 에이전트를 기반으로 고객사에 요구사항에 맞춰 커스텀 에이전트를 만들 수 있게. 특별한 요구사항이 없으면 이 에이전트를 사용."이라고 답했다. 그래서 이 에이전트는 사용처 하나의 본보기가 아니라 커스텀 에이전트의 바탕이 됐고, 바탕이 되려면 코드가 문서 검색에 묶이면 안 된다. **기본 에이전트는 플러그인 `assistant`다. 코드는 매니페스트가 고른 스킬을 지시로, 앞 대화를 데이터로 엮어 `ctx.llm()`을 한 번 부를 뿐이고 어떤 일의 이름도 들지 않는다. 문서 검색은 세 자리에 있다. 일하는 방법을 적은 스킬 `cite-sources`, 문서 검색 서버를 주소로 가리키는 연결 플러그인 `doc-search`, 규칙 파일의 에이전트 표다. 모델이 검색 도구를 스스로 부르고, 문서 전문 읽기는 질문한 사람의 승인 뒤에 부르며, 지식베이스 목록은 막는다. 커스텀 에이전트는 이 폴더를 복사해 이름을 바꾸고 매니페스트와 스킬을 고쳐 만든다. 런타임은 calc를 모르듯 이 에이전트도 모른다.**

## 결정

- **뜻과 이름.** 용어집의 "참조 에이전트"를 "기본 에이전트"로 바꾸고 "커스텀 에이전트"를 더한다(`CONTEXT.md`). 기본 에이전트는 이 저장소가 함께 내는 에이전트 플러그인이고, 쓰는 조직에 특별한 요구가 없으면 그대로 쓰며, 요구가 있으면 복사해 고쳐 커스텀 에이전트의 바탕으로 삼는다. 플러그인의 이름은 `assistant`다. 기능의 이름은 `doc-qa-agent`에서 `base-agent`로 바꾼다. "참조 배포"라는 말은 그대로 둔다.
- **런타임은 모른다.** "에이전트를 지정하지 않으면 이 에이전트가 답한다"는 런타임의 기본값은 두지 않는다. 위젯의 `agent` 속성은 지금처럼 필수이고(`web/apps/widget/EMBED.md` 94줄을 Grep으로 봤다), 서버의 설정도 계약도 이 뜻 때문에 바뀌지 않는다. "요구가 없으면 그대로 쓴다"는 배포하는 사람이 고르는 기본 선택이라는 뜻이다. 그래서 참조 배포와 질문 페이지의 예시 설정이 `assistant`를 가리킨다(deploy-package 기능 계획에 넘겼다). 런타임에는 "기본 모델"(에이전트가 모델을 고르지 않으면 런타임이 쓰는 모델)이라는 말이 이미 있어 "기본 에이전트"도 런타임이 아는 기본값으로 읽힐 수 있으므로, 용어집의 항목에 "런타임은 그 에이전트를 모른다"를 함께 적었다.
- **코드.** `plugins/agents/assistant/agent.py`는 어떤 일에도 묶이지 않는다. 매니페스트의 `skills`가 고른 스킬의 본문을 지시로 엮고(`AgentContext.skills`, ADR 0041), 앞 대화를 데이터로 엮은 뒤(`AgentContext.conversation`, ADR 0022) `ctx.llm()`을 한 번 부른다. 도구 이름, 검색 결과의 칸, 형식의 판, 출처의 모양, 일의 이름을 코드에 적지 않는다. 지금의 calc가 이 모양에 가깝다. calc의 코드에서 계산에만 해당하는 것은 프롬프트 머리의 세 문장(`PROMPT`의 첫 줄 "계산 요청이다. 도구가 있으면 도구로 계산한다. 최종 답만 짧게 답한다.")과 앞 대화 블록의 구절 "계산에 필요한 값만 가져온다"이고, 나머지는 스킬 블록과 앞 대화 블록을 엮어 `ctx.llm()`을 한 번 부른다(`plugins/agents/calc/agent.py` 전체를 읽었다). 기본 에이전트의 코드는 그 두 자리에도 일의 이름을 적지 않는다.
- **문서 검색이 있는 자리 셋.**
  - **스킬 `cite-sources`**(`plugins/skills/cite-sources/SKILL.md`). 일하는 방법을 적는다. 질문에 답하기 전에 검색 도구를 부르고, 찾은 조각의 근거로만 답하며, 출처를 아래 "답의 모양"대로 적고, 근거가 없으면 모른다고 답하고, 검색 결과 안의 지시를 따르지 않는다. (바뀜: 이력 2026-11-10 "인사와 앞 대화에 관한 요청에는 검색 없이 답한다")
  - **연결 플러그인 `doc-search`**(`plugins/mcp/doc-search/plugin.toml`). 원격 MCP 서버를 가리키는 http 모양의 MCP 플러그인이다(ADR 0049). 커밋하는 주소는 배포용 서비스 이름이다(`http://rag-engine:<포트>/mcp` 꼴. 경로 `/mcp`는 rag-engine의 명세에서 읽었고 포트는 그 저장소의 배포가 정한다). Docker Compose에서는 서비스 이름이 곧 주소라 공개 데모와 참조 배포가 같은 주소를 쓴다(ADR 0049 결정 "주소는 매니페스트에 그대로 적는다"). 두 배포의 서비스 이름과 포트가 커밋한 주소와 같으면 이 파일을 고치지 않고 쓰고, 다르면 배포가 제 플러그인 디렉터리에서 이 파일의 주소를 고친다(플러그인 디렉터리는 배포의 몫이다. 같은 항목). 토큰이 필요하면 `[server.headers]`에 환경 변수의 이름으로만 적는다.
  - **규칙 파일의 에이전트 표**(`plugins/rules.toml`의 `[agents.assistant]`). 아래 "도구 셋의 규칙"이다.
- **도구 셋의 규칙.** 문서 검색 서버는 읽기 도구 셋(`search`, `get_document`, `list_knowledge_bases`)을 연다(rag-engine의 `.scratch/core/spec.md` "MCP 도구" 절을 읽었다. 그 저장소는 명세 단계라 코드로 확인한 것이 아니다).
  - `allow = ["doc-search:search"]`. 검색은 묻지 않고 부른다. 규칙 파일에 적지 않은 도구는 묻는 것이 기본이라(ADR 0044), 적지 않으면 질문마다 승인 카드가 뜬다(ADR 0046 Consequences "규칙 파일의 기본값").
  - `ask = ["doc-search:get_document"]`. 문서 전문 읽기는 승인을 받은 뒤에 부른다. 그 도구는 `include_text`를 참으로 넘길 때만 전문을 돌려주고 기본은 문서의 정보(제목, 크기, 갱신일 같은 것)만 돌려주므로(rag-engine 명세 187줄을 읽었다) 스킬이 전문이 필요할 때 그 인자를 넘기라고 적는다. 규칙 파일의 줄은 도구 이름으로만 맞고 인자 패턴이 없어(ADR 0044의 "인자 패턴은 없다") `include_text` 없이 부르는 호출도 묻는다. 조각만으로 부족해 모델이 전문을 읽으려 하면 실행이 멈추고 위젯에 승인 카드가 떠서(`web/apps/widget/components/organisms/ApprovalCard.tsx`가 있다) 질문한 사람이 승인하거나 거부한다. 거부는 실패가 아니라 `tool_called(ok=false)`로 모델에 돌아가므로(`core/run.py`의 `_refuse`) 모델은 조각만으로 답한다. PRD가 기준선을 승인 통제를 실제 사용처에서 시험하는 자리로 적은 것과 맞고, 사용자가 말한 "승인 같은 기능"이 기본 에이전트에서 실제로 일어나는 자리다.
  - `deny = ["doc-search:list_knowledge_bases"]`. 지식베이스 목록은 막는다. deny인 도구는 모델의 도구 목록에 오르지 않는다(`.claude/rules/core.md`의 승인 게이트 항목).
  - **자리가 매니페스트가 아니라 규칙 파일인 이유.** 전문 읽기를 묻게 하는 길은 둘이다. 저자의 승인 요구(에이전트 매니페스트의 `requires_approval`)와 운영자의 `ask`(규칙 파일)다. 운영자의 allow는 저자의 승인 요구를 풀지 못한다(ADR 0044 결정의 차례). 매니페스트에 적으면 전문 읽기를 묻지 않고 열고 싶은 배포가 에이전트를 복사해 고쳐야 하고, 규칙 파일에 적으면 그 한 줄을 allow나 deny로 옮기면 된다. 검색을 허락하는 줄이 어차피 규칙 파일에 있어야 하므로 도구 셋의 결정이 한 표에 모인다. 맞는 줄이 없어도 묻는 것이 기본이지만 `ask`를 글자로 적는다. 적용 규칙이 `default`가 아니라 `ask`로 기록되고, 에이전트 표에 적힌 줄은 연결 직후 실재를 대 보므로(ADR 0044 이력 2026-11-05 "그 에이전트의 표는 연결 뒤 대 본다") 문서 검색 서버가 도구 이름을 바꾸면 조용히 지나가지 않고 그 실행이 원인 `tool_connection`으로 끝난다.
  - **공개 데모.** 공개 데모는 배포의 규칙 파일로 전문 읽기도 deny로 막는다(public-demo 기능 계획에 넘겼다). 익명 최종 사용자가 스스로 승인할 수 있기 때문이다(ADR 0046 이력 2026-11-06). 규칙 파일은 플러그인 루트마다 하나라(일지 2026-11-10-1345 "인터뷰 전에 대 본 사실") 공개 데모는 제 플러그인 루트의 규칙 파일을 바꿔 쓴다. 이미지에 든 파일을 덮는지 루트를 따로 두는지는 공개 데모의 설계가 정한다.
- **검색은 모델이 한다.** 모델이 `search`를 스스로 부른다. 검색어를 모델이 짓고, 모자라면 다시 검색하며, 이어지는 질문에서도 모델이 앞 대화를 보고 검색어를 고쳐 쓴다. 에이전트 코드는 검색 결과를 만지지 않는다. 어댑터가 도구 결과의 글만 남기므로(`adapters/mcp.py`의 `_text_of`. 서브에이전트가 코드를 읽었다) 모델은 문서 검색 서버가 낸 JSON 글을 그대로 받는다. 코드가 조각에 번호를 붙이거나 자료 묶음으로 감싸지 않고, 형식의 판(`format_version`)도 확인하지 않는다. 출처는 답의 글 안에 적으므로 `run_finished`의 계약은 바뀌지 않는다.
- **검색 대상과 조각 수.** 스킬은 `knowledge_base`를 넘기지 말라고 적어 서버의 기본 지식베이스를 쓰게 한다. 스킬의 지시일 뿐 코드 장치는 없다. 모델이 그 인자를 넣으면 런타임은 막지 않는다. 지식베이스 목록을 막아 두었으므로 모델이 이름을 알 길은 질문 글과 검색 결과뿐이다. 한 번의 검색이 돌려주는 조각 수는 모델이 넘기는 `top_k`가 정하고(서버의 기본은 10, 최대는 50이다. 같은 명세를 읽었다) 에이전트 쪽에 그것을 묶는 코드는 없다. 단단한 끝은 문서 검색 서버 쪽의 일이다. 그 서버의 명세는 `top_k`의 최댓값을 설정 `RAG_SEARCH_MAX_TOP_K`(기본 50)로 두므로(같은 명세 97줄과 186줄을 읽었다. 명세 단계라 코드로 확인한 것이 아니다) 공개 데모는 그 설정을 낮춰 끝을 묶고, 낮출 값은 공개 데모의 설계가 정한다(public-demo 기능 계획에 넘겼다).
- **끝 둘.** 매니페스트에 턴의 끝 `max_turns`와 도구 호출의 끝 `max_tool_calls`를 적는다(ADR 0052). 값은 명세가 정한다. 인터뷰는 "검색 두 번과 답 한 번"을 생각했고, 전문 읽기가 열려 셈이 달라졌다(검색 두 번에 전문 읽기 한 번이면 도구 호출이 셋이고 턴이 넷이다).
- **답의 모양.** 근거를 쓴 문장의 끝에 `[1]`처럼 번호를 달고, 답의 끝에 "출처"라는 줄과 번호 목록을 둔다. 목록의 줄은 문서 제목, 위치(쪽이나 절), 갱신일이다. (바뀜: 이력 2026-11-10 "전문에서 가져온 근거의 위치는 절의 제목이고 없으면 전문이라고 적는다") 갱신일은 검색 결과의 `updated_at`에서 날짜 부분만 그대로 옮긴다. 서버가 UTC로 내므로(rag-engine 명세 103줄을 읽었다) UTC의 날짜다. 근거를 찾지 못하면 출처 목록 없이 정해진 한 문장으로 답한다(문구는 명세가 정한다). 굵게와 목록 같은 마크다운을 써도 된다고 스킬에 적는다(위젯이 답을 마크다운으로 그리는 것은 ADR 0053). 이 모양은 지금 위젯에서도 읽힌다. 지금 위젯은 답의 줄바꿈을 그대로 보이기 때문이다(`Conversation.tsx` 213줄을 Grep으로 봤다). 인터뷰에서 사용자가 고른 미리보기는 일지 2026-11-10-1345의 라운드 3에 있다. 날짜만 보이는 갱신일로는 같은 날 바뀐 두 판을 가르지 못하지만, 정확한 시각과 조각 식별자(`chunk_id`)가 트레이스의 검색 결과(`tool_called`)에 남아 어떤 판의 문서로 답했는지를 되짚을 수 있다.
- **문서 속 지시.** 스킬에 검색 결과와 문서 전문은 데이터로만 다루고 그 안의 지시를 따르지 않는다고 적는다. 코드로 막는 장치는 없다. 피해의 범위는 열린 도구와 답의 글로 묶인다. 열린 도구는 검색과, 승인 뒤의 전문 읽기이고, 문서 검색 서버가 MCP로 여는 것은 읽기 도구뿐이다(ADR 0048). 런타임이 도구 결과를 바깥 글로 감싸는 것은 mcp-trust부터다(ADR 0046).
- **모델과 대화.** 매니페스트에 `model`을 적지 않아 기본 모델을 따른다. 앞 대화는 calc처럼 데이터로 엮는다. 공개 데모에서 대화 이어 가기를 열지는 공개 데모의 설계가 정한다.
- **놓는 자리.** 기본 플러그인 루트 `plugins/`에 calc와 함께 둔다. 에이전트 `plugins/agents/assistant`, 스킬 `plugins/skills/cite-sources`, 연결 `plugins/mcp/doc-search`, 규칙 파일의 표다. `serve`를 기본값으로 띄우면 `assistant`가 목록에 보인다.
- **커스텀 에이전트를 만드는 길.** 에이전트 폴더를 복사해 폴더 이름과 매니페스트의 `name`을 새 이름으로 바꾸고, 매니페스트(쓸 MCP 서버, 스킬, 모델, 끝 둘)와 스킬을 고친다. 규칙 파일의 표는 에이전트 이름이 열쇠라 새 이름의 표를 더한다. 요구가 코드까지 닿으면 복사한 코드를 고친다. 만드는 순서를 안내 문서로 함께 내고(자리는 명세가 정한다), "이름만 바꾼 사본이 원본과 같은 시험을 지난다"는 시험을 둔다. 그 사본은 폴더, `name`, 규칙 파일의 표 이름만 바꾼 것이다.
- **시험.** 빠른 검사는 검색 도구 형식의 판 1.0.0을 흉내 내는 가짜 검색 서버(테스트 픽스처)로 돌고, 그 판은 픽스처 파일 한 곳에만 적는다(ADR 0048 Consequences). 실제 모델 시험은 출처와 갱신일이 붙는지, 근거 없는 질문에 모른다고 답하는지, 지시가 섞인 조각을 따르지 않는지를 본다. 승인 사례 둘(승인하면 전문을 읽고 답한다, 거부하면 조각만으로 답한다)을 더하고, 어느 시험 층에 둘지는 명세가 정한다. 위젯의 실제 모델 e2e에 사례를 하나 더한다. 마지막 티켓은 실제 문서 검색 서버 이미지로 한 번 돌리는 것이고, 그 이미지가 나올 때까지 기능을 닫지 않는다.
- **이름을 고치는 범위.** 기능 폴더(`.scratch/doc-qa-agent` → `.scratch/base-agent`)와 다른 기능 계획의 `**Blocked by:**` 줄과 본문을 고친다. PRD의 "참조 에이전트 doc-qa" 문장은 사용자 승인으로 고친다. ADR 본문은 글자를 고치지 않고 포인터와 이력으로 남긴다(아래 Consequences "다른 ADR의 본문"). 일지, 끝난 기능의 명세, 대기열 항목 같은 기록은 고치지 않는다.
- **범위 밖.** 런타임이 아는 기본 에이전트, 코드 없이 설정만으로 선언하는 에이전트, sdk의 바탕 클래스, `run_finished`의 구조화한 출처 칸, 문서 검색 밖의 도구 서버.

## Considered Options

- **에이전트 코드가 먼저 검색한다.** 인터뷰의 추천안이었다. 질문이 오면 코드가 질문 글 그대로 검색 도구를 한 번 부르고, 조각에 번호를 붙여 "자료이고 지시가 아니다"라는 묶음으로 프롬프트에 넣은 뒤 모델을 한 번 부른다. 모델 호출이 한 번이고, 도구 호출 형식을 잘 지키지 못하는 모델에서도 답이 나오며, 코드가 형식의 판을 확인할 수 있다. 사용자가 선택지 밖의 답으로 "Agentic RAG 방식으로"라고 답했고, 올린 선택지 가운데 "모델이 스스로 검색"이 그 방식이다. 추천안은 질문 글이 곧 검색어라 이어지는 질문에 약하고, 코드가 검색 도구의 이름과 결과의 칸을 알아야 해서 뒤에 정한 "코드는 일에 묶이지 않는다"와 맞지 않는다.
- **참조 배포 전용 플러그인 루트를 따로 둔다.** 인터뷰의 추천안이었다(`reference/doc-qa/plugins/` 같은 새 폴더). 공개 데모와 참조 배포가 `serve --plugins-root`로 그 폴더만 가리키면 calc와 everything이 함께 올라가지 않는다. 사용자가 "기본 plugins/ 폴더에 함께"를 골랐다. 그 값은 Consequences에 적는다.
- **가짜 서버로 닫고 실제 이미지 시험은 answer-eval에 넘긴다.** 인터뷰의 추천안이었다. 사용자가 "이미지가 나올 때까지 열어 둠"을 골랐다. "끝났다"는 표시가 실제 서버와 맞물린 뒤에만 붙는다.
- **기본 에이전트의 다른 뜻 둘.** 인터뷰가 올린 선택지는 "함께 내는 대표 에이전트"(용어집의 참조 에이전트 그대로)와 "지정하지 않으면 답하는 기본값"이었고 사용자는 둘 다 아닌 뜻(커스텀 에이전트의 바탕)을 말했다. 런타임의 기본값은 서버의 설정과 위젯의 계약(`agent`가 필수다)을 바꾸고 "런타임은 그것을 모른다"(ADR 0048, PRD)를 다시 열어야 해서 두지 않는다.
- **코드 없이 설정만으로 에이전트를 선언한다.** 매니페스트에 "바탕 동작을 쓴다"는 칸을 두면 바탕이 고쳐질 때 커스텀 에이전트가 저절로 따라간다. 거부했다. 매니페스트의 계약과 로더가 바뀐다. 지금은 `entrypoint`가 필수이고(`sdk/manifest.py` 243~245줄을 읽었다) 에이전트는 개발자가 코드로 쓰는 플러그인이다(`.claude/rules/sdk.md`).
- **sdk에 바탕 클래스를 둔다.** 스킬과 앞 대화를 엮어 모델을 한 번 부르는 클래스를 `agent_os.sdk`에 두고 물려받게 한다. 거부했다. sdk의 공개 표면이 늘어 계약 변경이 하나 더 생기고, 프롬프트를 엮는 방식이 sdk에 고정된다. 플러그인은 고유 모듈명으로 로드되어 다른 플러그인의 코드를 물려받는 길이 없으므로(`adapters/filesystem.py` 5~6줄을 Grep으로 봤다) 남는 길이 복사다.
- **나머지 도구 둘을 모두 막는다.** 합의 요약 첫 판의 안이었고 ADR 0046의 2026-11-06 이력이 공개 데모에 대해 적은 것("도구는 읽기 전용 검색 하나만 열며")과 같은 모양이다. 사용자가 "문서 전문 읽기를 승인 뒤에 부르게 엶"을 골랐다. 공개 데모는 배포의 규칙 파일로 그 모양을 지킨다.
- **이름만 넓히고 승인은 타지 않는다. 또는 다른 도구 서버도 붙여 범용 도우미로 넓힌다.** 앞의 것은 기본 에이전트가 승인 흐름을 한 번도 보이지 않는다. 뒤의 것은 PRD가 만들지 않겠다고 적은 범용 챗 제품에 닿고 어떤 도구를 붙일지부터 다시 설계해야 한다. 둘 다 고르지 않았다.
- **전문 읽기의 승인을 매니페스트의 `requires_approval`로 건다. 또는 도구 셋의 규칙을 공통 표 `[common]`에 적는다.** 사용자에게 묻지 않고 정한 기본값이다. 앞의 것을 고르지 않은 이유는 결정의 "자리가 매니페스트가 아니라 규칙 파일인 이유"다. 뒤의 것은 이름만 바꾼 사본이 표를 더하지 않아도 같은 규칙을 받지만, 공통 표는 모양만 보고 실재를 대 보지 않아(ADR 0044) 도구 이름이 바뀐 것을 잡지 못한다.
- **이름 `guide`, `desk`, `default`.** `guide`는 승인을 받아 무언가를 해 주는 일까지 맡기기에 좁고, `desk`는 낱말만으로 뜻이 바로 떠오르지 않으며, `default`는 런타임이 아는 기본값으로 읽힌다. 사용자가 `assistant`를 골랐다.
- **용어 "참조 에이전트"를 유지하고 뜻만 넓힌다.** 고칠 문서가 적고 "참조 배포"와 말의 짝이 맞는다. 거부했다. 사용자가 쓰는 말과 문서의 말이 달라진다.
- **출처를 문장마다 괄호로 적는다.** 문장이 길어지고 같은 문서를 여러 번 인용하면 같은 괄호가 되풀이되며, 답변 평가가 괄호 안의 글을 해석해야 한다(어림). 사용자가 "문장 끝 번호와 출처 목록"을 골랐다.
- **갱신일을 한국 시간으로 바꿔 적는다. 또는 서버에 표시용 날짜 칸을 요청한다.** 앞의 것은 모델의 날짜 계산이 틀릴 수 있고 다른 시간대의 배포가 스킬을 고쳐야 한다. 뒤의 것은 두 저장소 사이의 계약(검색 도구 형식의 판)이 바뀌어야 한다. 사용자가 "서버가 준 날짜 그대로"를 골랐다.
- **연결 플러그인에 내 PC 주소(`127.0.0.1`)를 적는다.** 개발자가 파일을 고치지 않고 돌릴 수 있다. 거부했다. 배포가 주소를 바꾼 파일을 따로 두어야 하고 ADR 0049의 전제(공개 데모와 참조 배포가 같은 주소를 쓴다)와 어긋난다.
- **`run_finished`에 구조화한 출처 칸을 더한다.** 옛 기능 계획이 인터뷰에 넘긴 갈래다. 모델이 검색하면 출처를 별도 칸으로 내려면 답의 글을 다시 해석해야 해서 고르지 않았다. 계약이 바뀌지 않는다.

## Consequences

- **모델이 도구 호출 형식을 지켜야 답이 나온다.** 검색을 모델이 시작하므로, 도구 호출 형식을 지키지 못하는 모델에서는 검색 없이 답하거나 실행이 실패한다(어림). local-model의 기능 계획은 도구 호출을 해석하는 방식이 서빙 엔진과 모델 계열마다 다르다는 것을 설계 인터뷰가 먼저 볼 것으로 이미 적었고, 수락은 calc 예시로 본다. 기본 에이전트의 실제 모델 시험도 그 모델로 돌릴지는 그 설계 인터뷰가 정한다(local-model 기능 계획에 넘겼다).
- **코드가 형식의 판을 확인하지 않는다.** 문서 검색 서버가 결과의 칸을 바꾸면 모델이 낯선 JSON을 받고, 빠른 검사는 가짜 서버로 초록이다. 잡는 자리는 가짜 서버가 따르는 판을 적은 한 곳, 마지막 티켓의 실제 이미지 시험, answer-eval이다. 도구 이름이 바뀐 것은 규칙 파일의 에이전트 표가 연결 직후 잡는다.
- **사본은 원본을 따라가지 않는다.** 커스텀 에이전트는 복사한 뒤 기본 에이전트와 따로 바뀐다. 기본 에이전트가 고쳐져도 사본은 저절로 고쳐지지 않아, 판을 올릴 때 손으로 맞춘다. 안내 문서에 적는다.
- **한 폴더에 섞인다.** 규칙 파일이 플러그인 루트마다 하나라 calc의 표와 `assistant`의 표가 한 파일에 있다. 공개 데모가 이 폴더를 쓰면 calc와 everything도 함께 올라가므로, 사이트 파일의 열 에이전트 목록에서 calc를 뺀다(public-demo 기능 계획에 넘겼다).
- **개발자 PC.** 커밋한 주소는 서비스 이름이라 그 이름의 서버가 없는 자리에서는 `assistant`의 실행이 원인 `tool_connection`으로 끝난다. 로컬에서 돌리려면 매니페스트의 주소를 고치고(ADR 0049 Consequences "로컬 개발"), 테스트는 주소를 바꿔 쓴 사본으로 돈다(mcp-http의 실제 모델 테스트가 그렇게 한다고 서브에이전트가 `tests/test_main.py`에서 읽었다).
- **위젯 e2e의 픽스처.** 위젯의 실제 모델 e2e는 저장소의 `plugins/`를 통째로 임시 폴더에 옮긴 뒤 픽스처를 그 위에 쓰고, 규칙 파일은 픽스처가 덮어쓰며 calc의 줄만 다시 적는다(`web/packages/e2e-stack/src/plugins.ts`의 `copyRepoPlugins`와 `writeFixturePlugins`를 읽었다). 그래서 새 플러그인 셋이 그 시험 환경에 섞이고, `assistant`의 표는 그 규칙 파일에 없다. 위젯 e2e에 `assistant` 사례를 더하는 티켓이 이 픽스처를 함께 고친다.
- **전문 읽기의 크기.** `get_document`가 돌려주는 글의 크기에 끝이 있는지는 확인하지 못했다. 전문은 조각보다 훨씬 많은 글을 모델에 보내므로 실행 하나의 토큰이 커질 수 있고, 토큰 합 상한(token-limit)은 슬라이스 11이다. 명세 단계가 rag-engine의 명세를 확인하고, 끝이 없으면 그 저장소의 계획에 넘긴다.
- **기능이 열려 있는 기간.** rag-engine은 명세를 마친 단계이고 저장소에는 뼈대 파일 셋뿐이라(일지 2026-11-10-1345), 그 이미지가 나올 때까지 base-agent가 몇 주(어림) 동안 진행 중으로 남는다. 이 기능을 기다리는 answer-eval, public-demo, deploy-package의 Blocked by도 그만큼 풀리지 않는다.
- **공개 데모의 비용 셈.** 실행 하나의 모델 호출 수의 끝이 10이 아니라 매니페스트의 `max_turns`가 되고 검색 횟수는 `max_tool_calls`가 묶는다(ADR 0052). 공개 데모는 전문 읽기를 막으므로 그 셈에 전문의 크기가 들지 않는다.
- **갱신일의 날짜.** UTC의 날짜라 한국 시간 0시부터 9시 사이에 고친 문서는 답에 전날로 보인다. 날짜만 아는 문서를 넣을 때는 그 날짜의 UTC 0시로 넣어야 답에 같은 날짜가 보인다(수집 때 갱신일을 넘길 수 있다. rag-engine 명세 120줄을 읽었다). 공개 데모의 문서 넣는 절차에 넘겼다.
- **답변 평가의 입력.** 출처 목록의 줄(문서 제목, 위치, 갱신일)이 answer-eval이 읽을 모양이다. 그 기능 계획에 넘겼다.
- **용어와 PRD.** `CONTEXT.md`에서 참조 에이전트를 기본 에이전트로 바꾸고 커스텀 에이전트를 더했다. PRD의 "무엇을 만드나"에서 "참조 에이전트 doc-qa"를 "기본 에이전트 assistant"로 고친다(사용자 승인).
- **다른 ADR의 본문.** 포인터를 단 것과 달지 않은 것을 ADR마다 가른다(`.claude/rules/adr.md`).
  - **ADR 0046.** 기준선 표의 `doc-qa-agent` 줄, Consequences의 "그래서 doc-qa와 참조 배포는 검색 도구를 허락하는 규칙 파일을 함께 낸다."와 "그때까지는 doc-qa의 프롬프트가 검색 결과를 데이터로 엮는 것에 기댄다."에 그 ADR의 2026-11-10 이력을 가리키는 포인터를 달고, 그 이력에 무엇이 바뀌었는지를 적는다. Consequences의 "같은 PR에 드는 것"은 그때 PR의 기록이고, 이력 항목들의 `doc-qa`는 지난 이력이라 달지 않는다. 파일 이름의 `doc-qa-baseline`도 그대로 둔다.
  - **ADR 0048.** 저장소 표의 agent-os 줄, "런타임(`src/`)은 calc를 모르듯 doc-qa도 모른다.", "agent-os의 가짜 검색 서버와 doc-qa가 따라 고친다.", "런타임이 doc-qa와 문서 검색 서버의 이름을 모르는지는 리뷰가 본다."에 `(바뀜: ADR 0051)`을 단다. 결정의 방향(런타임은 모른다, 의존은 플러그인에서 서버로만 간다)은 그대로이고 바뀐 것은 이름과, 검색 도구의 형식을 아는 자리다. 그 자리는 에이전트 코드가 아니라 스킬 `cite-sources`(결과의 칸 이름), 연결 플러그인 `doc-search`(주소), 규칙 파일(도구 이름), 가짜 검색 서버(판)다. 배경 문단과 거부한 안 둘의 `doc-qa`는 그때의 근거라 달지 않는다.
  - **ADR 0049.** 시험 항목의 "실제 플러그인은 doc-qa-agent가 가져온다."와 Consequences의 "doc-qa-agent는 이 모양으로 문서 검색 서버를 가리키는 플러그인을 가져오고"에 `(바뀜: ADR 0051)`을 단다. 기능의 이름이 base-agent가 됐고 그 플러그인이 `doc-search`다.
  - **ADR 0045.** 18줄의 `docs/doc-qa-direction`은 그때 열려 있던 PR의 브랜치 이름이라 달지 않는다.
  - **ADR 0044.** 바뀌지 않는다. 이 ADR은 그 규칙 파일을 쓰는 첫 플러그인 묶음이다.

## 이력

### 2026-11-10 인사와 앞 대화에 관한 요청에는 검색 없이 답한다

결정 "문서 검색이 있는 자리 셋"의 스킬 항목은 스킬이 "질문에 답하기 전에 검색 도구를 부르고"라고 적는다고 했다. 사용자가 그 범위를 두 번 좁혔다. 첫째는 이 ADR을 병합하기 직전에 기능 계획에 더한 요구다(2026-11-10, `.scratch/base-agent/plan.md`의 "사용자가 앞의 글에 더한 요구"). 인사, 감사, 이 도우미가 무엇을 하는지 묻는 말에는 검색 없이 짧게 답하고, 그 밖의 질문은 문서에 없으면 모델이 아는 내용이라도 답하지 않는다. 둘째는 명세를 쓰기 전의 물음(앞의 답을 다듬어 달라는 요청을 어떻게 할지)에 한 답이다(일지 2026-11-10-1906). "검색 없이 다듬는다. 이미 기억에 있는데 다시 검색할 이유가 있나? 그리고 인사나 기억 관련돼서 질문하는건 검색 결과랑 상관 없이 답을 해야지. 검색 도구를 호출 했을 때 검색 결과가 없을 때 답변하지 못한다라고 해야하는거 아니야??" 그래서 스킬이 적는 것은 다음으로 바뀐다. 나머지(출처의 모양, 검색 결과 안의 지시를 따르지 않는 것)는 그대로다.

- **요청을 셋으로 가른다.** 인사, 감사, 이 도우미가 무엇을 하는지 묻는 말(어떤 문서가 있는지 묻는 말도 여기에 든다)에는 검색 없이 답한다. 앞 대화에 관한 요청(앞의 답을 줄이거나 다시 정리해 달라는 요청, 앞에서 무엇을 묻고 답했는지 묻는 말)에는 검색 없이 앞 대화에 있는 내용만으로 답한다. 그 밖의 모든 요청은 답하기 전에 검색하고 검색 결과에 있는 내용으로만 답한다. 모델이 이미 아는 내용, 상식, 추천, 의견을 묻는 말도 셋째에 든다.
- **모른다고 답하는 때.** 정해진 한 문장은 검색했는데 질문에 답하는 조각이 없을 때 쓴다. 문구는 사용자가 골랐다. "등록된 문서에서 관련 내용을 찾지 못했으니, 다른 표현이나 다른 질문으로 다시 물어봐 주세요."
- **찾은 조각의 근거로만 답한다는 것에 예외가 하나 생긴다.** 앞 대화에 관한 요청에는 그 실행이 찾은 조각이 아니라 앞 대화에 있는 내용으로 답한다. 사용자가 고른 선택지가 이 값을 적었다("검색 결과에 없는 것은 답하지 않는다"에 예외가 생깁니다). 예외를 좁히는 것은 둘이다. 앞의 답을 다듬을 때 재료는 앞의 답뿐이고 앞의 답이 쓰던 번호와 출처 줄을 그대로 남긴다. 다듬을 답이 앞 대화에 그대로 남아 있지 않고 요약으로만 남았으면 검색하는 갈래로 간다(요약에는 번호와 출처 줄이 남지 않는다). 앞에서 무엇을 묻고 답했는지 묻는 말에는 앞 대화가 요약으로만 남았어도 검색 없이 답하고, 앞 대화가 없으면 없다고 답한다.

가르기는 스킬의 지시이고 코드 장치가 아니다. 결정 "문서 속 지시"와 같은 한계다. 모델이 문서에 관한 질문을 인사나 앞 대화에 관한 요청으로 잘못 가르면 검색 없이 답할 수 있고, 앞 대화는 질문한 사람이 넣은 글과 같은 수준으로만 믿을 수 있어(`.claude/rules/sdk.md`의 신뢰 경계) 앞 질문에 심어 둔 주장이 다듬은 답에 실릴 수 있다. 사용자가 그 값을 적은 선택지를 골랐다. 보장이 필요한 조직은 사본의 코드에 고정 단계를 넣는다(결정 "커스텀 에이전트를 만드는 길"). 이 가르기를 적은 스킬을 실은 실제 모델이 갈래마다 무엇을 했는지는 `.scratch/base-agent/probes/skill_follow.py`로 쟀고, 결과와 근거의 종류는 그 폴더의 `README.md`에 있다. 잰 것은 그 글자가 실린 실행에서 모델이 한 일까지다. 스킬의 어느 문장이 그 행동을 만들었는지, 곧 스킬 없이도 그랬을지는 그 문장을 뺀 판을 돌리지 않아 가르지 못했다. 결정 "시험"의 실제 모델 시험에는 사례가 는다(인사, 범위 밖의 두 예, 지침을 무시하라는 요구, 다듬기). 스킬의 본문과 시험의 자리는 명세(`.scratch/base-agent/spec.md`)가 정한다.

### 2026-11-10 전문에서 가져온 근거의 위치는 절의 제목이고 없으면 전문이라고 적는다

결정 "답의 모양"은 출처 목록의 위치를 "쪽이나 절"로 적었다. 검색 결과의 조각은 `location`에 쪽과 절을 싣지만 문서 전문(`get_document`의 `text`)에는 위치의 칸이 없다. 전문은 파싱한 블록의 글을 빈 줄로 이은 글 하나다(rag-engine의 `.scratch/core/spec.md` 195줄을 읽었다. 그 저장소는 명세 단계라 코드로 확인한 것이 아니다). 그래서 명세(`.scratch/base-agent/spec.md`의 "스킬 `cite-sources`")가 스킬에 한 줄을 더했다. 문서 전문에서 가져온 내용은 위치에 그 내용이 든 절의 제목을 적고, 전문에 절의 제목이 없으면 `전문`이라고 적는다. 조각에서 가져온 내용의 위치는 그대로 쪽이나 절이다.

절의 제목이 든 전문과 제목 없이 글만 이은 전문 두 모양에서 실제 모델이 그렇게 적는지는 `.scratch/base-agent/probes/skill_follow.py`의 사례 "전문 읽기 승인"과 "제목 없는 전문"으로 쟀고, 결과와 근거의 종류는 그 폴더의 `README.md`에 있다. 실제 문서 검색 서버의 전문에 절의 제목이 드는지는 확인하지 못했다. 마지막 티켓(실제 이미지로 한 번 돌리기)이 본다. Consequences "답변 평가의 입력"이 적은 출처 목록의 줄에 이 갈래가 는다(answer-eval 기능 계획에 넘겼다).
