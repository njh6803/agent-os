# 모델 제공사에 `openai-compatible`을 더해 모델 파일에 적은 주소의 모델 서버에 붙고, 키는 환경 변수의 이름으로만 적으며 엔진마다 다른 설정은 서버를 띄우는 쪽이 맞춘다

모델은 플러그인이고 제공사 `provider`는 값이 `anthropic` 하나인 닫힌 목록이다(ADR 0040. `sdk/manifest.py`의 `ModelProvider`를 읽었다). 그래서 바깥 API에 닿지 못하는 폐쇄망 배포 환경에서는 실행이 돌지 않는다. ADR 0046이 기준선에 local-model을 넣어 그 환경의 모델 서버로 실행이 돌게 하기로 했고, 기능 계획(`.scratch/local-model/plan.md`)의 수락은 계열이 다른 모델 둘을 모델 파일만 바꿔 같은 시험으로 통과시키는 것이다. ADR 0040은 둘째 제공사를 `provider` 목록에 값을 더하는 가산 변경으로 미뤘고, 그 기능 계획은 주소를 어디에 둘지, 서빙 엔진의 확장에 얼마나 기댈지, 모델이 도구 호출 형식을 지키지 않았을 때 무엇이 보일지를 설계 인터뷰에 넘겼다. local-model 설계 인터뷰(일지 2026-11-11-1534)가 그것을 정했다. 결정의 원문은 그 일지의 `> 사용자:` 인용과 라운드 7에서 확인받은 합의 요약이고, 아래가 그것과 다르게 읽히면 일지가 원천이다. 그 시험을 실제 모델로 돌리는 절차(로컬 모델 시험, 병합 조건, GPU 서버)는 결정의 단위가 달라 ADR 0058이 정한다.

인터뷰 전과 도중에 본 것은 다음과 같다. 근거의 종류는 문장마다 밝히고, 조사 서브에이전트의 스크립트는 세션 스크래치패드에 있어 커밋하지 않았으므로 아래의 "손으로 봤다"는 일지의 조사 보고(combo-probe) 절이 적은 결과다. 명세나 구현 티켓이 근거로 들 것은 `.scratch/local-model/probes/`에 다시 지어 커밋한다.

- **지금 코드(읽었다).** `adapters/anthropic.py`의 `AnthropicModels.build`는 `provider`로 갈라 `ChatAnthropic`을 만들고 키 값을 만지지 않는다. `core/loop.py`는 도구를 `{"name", "description", "input_schema"}` 꼴로 `bind_tools`에 넘기고, `core/model.py`의 `reply_from`은 응답의 `tool_calls`만 읽고 `invalid_tool_calls`는 보지 않는다. `core/run.py`의 `_ask`는 모델을 부르는 것과 응답을 읽어 기록하는 것을 `blamed("model_call")` 안에 두고, ADR 0031은 그 원인을 "`ctx.llm()` 안에서 모델 포트에 닿는 몫"이 낸 예외로 적는다. 도구 호출 기록 `ToolCall`은 `id`, `name`, 풀린 인자 `args`만 들어 인자가 깨진 호출을 담을 자리가 없다(`sdk/events.py`).
- **라이브러리(손으로 봤다. Python 3.12.10, langchain-core 1.6.3, langchain-openai 1.6.2, openai 3.49.0, pyright 1.1.414. 루프백의 가짜 서버).** 저장소 락의 판을 제약으로 걸면 새로 드는 패키지는 넷이다(langchain-openai, openai, tiktoken, regex). `ChatOpenAI`에 키를 문자열로 주면 만드는 동안 요청이 없고, 키를 주지 않으면 환경에 `OPENAI_API_KEY`가 없을 때 만드는 자리에서 예외가 난다. 키를 주지 않았는데 환경에 `OPENAI_API_KEY`가 있으면 그 값이 `base_url`의 서버로 실려 간다. 키 자리에 동기 함수를 주면 만들 때는 불리지 않고 요청마다 한 번 불린다. 루프와 같은 꼴로 도구를 붙여 부르면 요청은 `POST /v1/chat/completions`이고 본문의 키는 `model`, `stream`, `messages`, `tools` 넷이며 `tool_choice`와 `strict`는 없다. 출력 길이 상한은 `max_completion_tokens`라는 이름으로만 나가고 주지 않으면 그 키가 없다. 모델 이름에 따라 Responses API(`/v1/responses`)로 갈 수 있고 `use_responses_api=False`를 주면 가지 않는다. 응답의 인자가 깨진 JSON이면 예외 없이 `tool_calls`가 비고 `invalid_tool_calls`에만 들어가며 글은 빈 문자열이다. `<tool_call>` 같은 글만 온 응답은 그 글이 답이 된다. 사고 칸(`reasoning`, `reasoning_content`)은 버려진다. 400·401·404는 요청 한 번으로 예외이고, 500·429·503·타임아웃·접속 실패는 SDK가 두 번 더 보낸다. langchain-openai를 거치면 HTTP 타임아웃의 기본이 없어 서버가 630초 붙잡은 요청이 그대로 기다렸다. import부터 둘째 턴까지 루프백이 아닌 주소로의 접속 시도는 없었다(LangSmith 환경 변수가 없는 환경에서 봤다). 다만 `get_num_tokens`를 부르면 tiktoken이 인코딩 파일을 받으러 바깥으로 나가려 한다(루프는 그것을 부르지 않는다). pyright strict는 `Any`·`cast`·무시 주석 없이 지났다. 실제 모델 서버로는 보지 않았다.
- **vLLM 0.33.0(문서와 소스의 원문을 읽었다. 일지의 조사 보고(web-research) 절).** 도구 호출은 서버를 띄울 때 `--enable-auto-tool-choice`와 `--tool-call-parser <이름>`을 줘야 켜지고 파서는 모델 계열마다 다르다. 요청에 도구가 있고 `tool_choice`가 없으면 서버가 그것을 `auto`로 채우고, 두 옵션 없이 띄운 서버는 그 요청을 오류 응답으로 거절한다(소스를 읽었다. 조사 보고는 그 응답을 HTTP 400으로 적는다). 형식 강제는 서버 옵션 `--tool-strict-level`이고, 사고를 내는 모델의 사고 글은 응답의 `reasoning` 칸에 따로 실린다. `hermes` 파서는 표지가 없거나 안의 JSON이 깨지면 도구 호출 없이 글에 원문을 싣는다. 요청에 상한이 없으면 서버의 기본값을, 그것도 없으면 문맥에서 입력을 뺀 나머지를 쓴다. 상한과 입력의 합이 문맥을 넘는 요청은 0.33.0에서는 상한을 남은 자리로 줄여 받고 입력만으로 문맥을 넘을 때만 거절하며(`get_max_tokens`), 0.30.0에서는 거절한다(그 판의 소스를 읽었다. 조사 보고는 바뀐 판을 0.32.0으로 적는다).

**`ModelProvider`에 값 `openai-compatible`을 더한다. 이 값의 모델 파일은 모델 서버의 주소 `base_url`을 글자 그대로 반드시 적고, 키가 필요하면 선택 칸 `api_key_env`에 환경 변수의 이름을 적는다. 런타임은 그 주소에 표준 Chat Completions 요청만 보내고, 도구 호출 파서나 형식 강제처럼 서빙 엔진마다 다른 설정은 모델 서버를 띄우는 쪽이 맞춘다. 키 값은 어댑터가 호출 때 환경에서 읽고 모델 파일, 이벤트, 실패 문구에 싣지 않으며, 그 변수가 없으면 첫 모델 호출에서 실패한다. 인자가 깨진 도구 호출은 그 실행을 원인 `model_call`의 실패로 끝내고, 글로 샌 도구 호출은 답으로 보인다. 붙는 코드는 `langchain-openai`를 런타임 의존으로 들여 쓴다.**

## 결정

- **제공사.** 새 값은 `openai-compatible` 하나이고 뜻은 "OpenAI 호환 API를 내는 모델 서버에 주소로 붙는다"다. vLLM이나 NPU용 서빙 엔진으로 띄운 모델 서버와 클라우드의 OpenAI 호환 서비스가 모두 이 값을 쓴다. 서빙 엔진마다 다른 점을 런타임이 맞춰 주지 않으므로 표준에서 벗어난 엔진은 붙지 않을 수 있고, 이 기능이 시험으로 확인하는 엔진은 vLLM 하나다. 닫힌 목록에 값을 더하고 선택 칸을 더하는 것이라 옛 매니페스트의 뜻은 바뀌지 않고 `schema_version`은 `"1"` 그대로다(ADR 0008의 기준. 같은 판단의 선례는 ADR 0049의 매니페스트 항목).
- **모델 파일.** `openai-compatible`의 모델 파일은 `provider`, `model_id`(모델 서버에 보내는 모델 이름)에 더해 `base_url`이 필수다. `base_url`은 글자 그대로 적고 `http`·`https`만 받으며 `사용자:비밀번호@`가 든 주소는 읽는 단계에서 거부한다. `api_key_env`는 선택이고 환경 변수의 이름만 적는다. 이름의 꼴은 명세가 정하고 출발점은 ADR 0049의 헤더 변수 이름 규칙이다. `openai-compatible` 파일에 `base_url`이 없거나, `anthropic` 파일이나 모델이 아닌 종류의 매니페스트에 `base_url`·`api_key_env`가 있으면 읽는 단계에서 거부한다(다른 종류의 매니페스트에 적힌 모델 칸을 거부하는 것은 지금의 `max_tokens`·`temperature`와 같다, ADR 0040 Consequences "모델 매니페스트의 모양"). `max_tokens`와 `temperature`는 지금 칸 그대로이고, 이 제공사에서는 없으면 요청에 싣지 않는다. 그래서 `max_tokens`가 없을 때의 뜻이 제공사마다 다르다. `anthropic`은 어댑터의 16000이고 `openai-compatible`은 모델 서버의 기본값이다.
- **주소는 비밀이 아닌 것으로 본다.** 관리 API의 매니페스트 응답과 실패 문구에 그대로 실린다. 사용자 정보가 든 주소를 거부하는 까닭이 이것이다. 원격 MCP 서버의 주소와 같은 방식이다(ADR 0049 결정 "주소는 매니페스트에 그대로 적는다"). 주소의 쿼리 문자열에 비밀을 적는 것은 막지 않고, 적으면 그 값이 주소와 함께 같은 자리에 실린다. 원격 MCP 서버의 주소에서 받아들인 것과 같은 알려진 한계이고(ADR 0049 Consequences "문구에 실리는 것과 실리지 않는 것"), 키를 두는 자리는 `api_key_env`다(바뀜: 이력 2026-11-12 "모델 파일의 주소에 쿼리 문자열이 있으면 읽는 단계에서 거부한다"). 배포마다 주소가 다르면 그 배포의 모델 파일을 고친다.
- **키.** 키 값은 `serve`의 환경에만 둔다. 어댑터가 모델 호출 때 `api_key_env`가 가리키는 변수를 읽어 넘기고, 런타임은 값을 모델 파일, 이벤트, 실패 문구에 싣지 않으며 로그에 찍지 않는다(헌법 원칙 V). 이 약속이 닿지 않는 자리는 셋이고 아래에 따로 적는다. 모델 서버가 값을 바꿔 되울리면 가리지 못하고("되울린 키"), 라이브러리의 로거가 값을 찍는지는 보지 않았으며(Consequences "로그"), http 주소에서는 값이 평문으로 간다(Consequences "배포가 알아야 할 것"). 변수가 환경에 없으면 실행은 시작되고 첫 모델 호출에서 원인 `model_call`로 실패하며, 실패 내용은 변수의 이름을 들고 값은 들지 않는다. Anthropic 키가 없을 때와 같은 시점이고(ADR 0040), 모델을 만드는 것이 키도 네트워크도 요구하지 않는다는 포트의 전제가 그대로 지켜진다. 어댑터는 키를 언제나 직접 넘겨, 라이브러리가 환경의 `OPENAI_API_KEY`를 스스로 읽어 모델 서버로 보내는 일이 없게 한다. `api_key_env`가 없으면 키 없이 붙는 서버로 보고 비밀이 아닌 자리 채움 글자를 넘기며, 그 글자는 인증 헤더로 서버에 간다(라이브러리가 키 없이는 만들어지지 않는다. 헤더를 아예 빼는 길은 보지 않았다). 키를 호출 때 읽는 함수로 넘기는 방식은 라이브러리가 받아 주는 것까지 손으로 봤고, 그 함수가 실패할 때의 예외 모양은 보지 않아 구현 티켓이 확인한다.
- **되울린 키.** 모델 서버가 오류 글에 받은 키를 되돌려 보내면 그 값을 실패 문구에서 가린다. 원격 MCP 서버의 헤더 값에서 같은 문제를 다룬 방식(환경에서 읽은 값을 글자 그대로 찾아 가린다, ADR 0049 이력 2026-11-09 "서버가 되울린 헤더 값을 실패 문구에서 가린다")이 출발점이고 남는 한계도 같다(서버가 값을 바꿔 되울리면 놓친다). core는 키 값을 모르므로 가리는 자리는 어댑터 쪽이어야 하는데, 모델 호출의 예외는 어댑터가 만든 모델 객체에서 core로 바로 올라온다(`core/run.py`의 `_ask`를 읽었다). 어댑터가 그 사이에 설 수 있는지(모델 객체를 감싸는 것 등)는 명세의 프로브가 먼저 보고 자리를 정한다.
- **요청.** Chat Completions 하나만 쓰고 Responses API로 가지 않게 고정한다. 싣는 것은 모델 이름, 대화, 도구 목록, 그리고 모델 파일에 있을 때의 출력 길이 상한과 온도다(바뀜: 이력 2026-11-12 "모델 이름의 머리에 따라 라이브러리가 요청을 바꾸는 것을 알려진 한계로 둔다"). `tool_choice`를 싣지 않으므로 도구를 부를지는 모델이 정한다. 서빙 엔진의 확장 칸은 싣지 않고, 응답에 사고 글이 별도 칸으로 와도 읽지 않는다. 타임아웃과 재시도의 칸은 두지 않고 라이브러리의 기본 동작 그대로 둔다(ADR 0040이 모델의 파라미터를 둘로 묶은 것과 같은 까닭이다).
- **서빙 엔진마다 다른 설정은 서버를 띄우는 쪽이 맞춘다.** 모델에 맞는 도구 호출 파서, 사고 끄기, 형식 강제는 모델 서버를 띄울 때의 옵션이다. 배포 안내가 vLLM의 옵션 예시를 싣고, 로컬 모델 시험을 돌릴 때마다 서버의 판과 옵션을 기록한다(ADR 0058). 치르는 값은 둘이다. 서버 옵션을 바꿀 수 없는 남의 모델 서버에서는 맞출 방법이 없고, 모델 파일만 봐서는 그 모델이 어떤 서버 옵션을 요구하는지 알 수 없다.
- **인자가 깨진 도구 호출.** 모델 서버가 도구 호출을 돌려줬는데 그 인자가 올바른 JSON이 아니면 그 실행을 실패로 끝내고 원인은 이미 있는 `model_call`이다. 지금 코드는 그 응답을 빈 답으로 내보내므로(위 "라이브러리") 응답을 읽는 자리가 깨진 호출을 확인해야 한다. 그 자리는 명세가 정하고 출발점은 `blamed("model_call")` 안에서 응답을 읽는 `core/model.py`의 `reply_from`이다. 실패 내용은 어느 도구의 인자가 깨졌는지를 들고 깨진 인자의 글은 싣지 않는다. 그 글에 트레이스에서 가려야 하는 인자(ADR 0009의 `secret_args`)가 들어 있을 수 있기 때문이다. 계약과 웹 화면은 바뀌지 않고, 위젯에는 지금의 `model_call` 문구와 다시 보내기 단추가 뜬다(`web/apps/widget/components/organisms/FailureAlert.tsx`를 읽었다).
- **글로 샌 도구 호출.** 모델이 도구를 부르려 했는데 서버가 알아채지 못해 그 글이 답으로 돌아오면, 런타임은 보통의 답과 가를 수 없어 답으로 내보낸다. 막는 것은 둘이다. 배포 안내가 맞는 파서와 형식 강제 옵션을 쓰게 하고, 로컬 모델 시험이 트레이스에 도구 호출이 실제로 남아야 통과하게 해서 모델과 서버의 조합이 맞는지를 가린다(ADR 0058).
- **포트와 어댑터.** core의 포트는 `ModelSource` 그대로이고 포트의 수는 늘지 않는다(ADR 0012, ADR 0040). 환경을 읽는 코드는 어댑터에만 있다. 제공사로 가르는 자리(지금은 `AnthropicModels.build`의 `match`)와 모듈의 이름은 명세가 정한다.
- **의존.** `langchain-openai`를 런타임 의존으로 선언한다(어댑터 층). openai SDK, tiktoken, regex가 그 뒤에서 온다. 판의 묶음은 구현 티켓이 `uv lock`으로 풀어 본 뒤 정하고, 어댑터가 openai SDK를 직접 import하게 되면 그것도 직접 의존으로 선언한다(직접 import하는 의존은 선언하는 관행, ADR 0049의 의존 항목). core와 sdk가 import하지 못하게 import-linter의 금지 목록 둘에 `langchain_openai`와 `openai`를 더한다.
- **평소의 시험.** 기본 pytest와 CI는 시험이 루프백에 띄운 가짜 호환 서버로 돈다. 보는 것은 요청의 모양(경로, 본문의 키, 키 헤더, 상한과 온도가 없을 때 빠지는 것), 응답의 해석(글, 도구 호출, 토큰 수, 모델 이름), 실패(인자가 깨진 도구 호출, 키 변수 없음, 인증 거부, 꺼진 서버, 되울린 키를 가리는 것), 환경의 `OPENAI_API_KEY`가 실려 가지 않는 것, 그리고 calc 예시가 그 서버를 모델로 삼아 MCP 도구를 써서 답하고 트레이스가 남는 것이다. 실제 모델로 보는 시험은 ADR 0058이다.
- **범위 밖.** 토큰 단위 스트리밍(ADR 0014 그대로), 서버로 그대로 넘기는 칸과 엔진의 확장, 깨진 도구 호출을 모델에 되돌려 다시 시키는 것, 새 실패 원인, 타임아웃과 재시도의 칸, 인증 헤더를 빼는 길, 자체 서명 인증서의 설정, 임베딩처럼 대화가 아닌 API.

## Considered Options

- **서빙 엔진마다 값 하나(`vllm`, `ollama` 같은 값).** 엔진의 차이를 런타임이 알게 되어 값마다 규칙과 시험이 늘고, 새 엔진이 올 때마다 계약이 바뀐다. 기능 계획이 이 기능을 "서빙 엔진과 모델을 같은 자리에서 바꿔 끼우는 경계"로 정한 것과도 어긋난다. 거부했다.
- **값을 `openai`로 하고 주소를 선택 칸으로 둔다.** 주소를 빠뜨린 모델 파일이 라이브러리의 기본 주소(OpenAI)로 나간다. 폐쇄망을 위한 기능에서 설정 실수가 바깥 접속이 된다. 거부했다.
- **주소를 환경 변수의 이름으로 적거나 `serve` 전체에 환경 변수 하나로 둔다.** 앞의 것은 ADR 0049가 원격 MCP 서버에서 거부한 까닭(실패 문구와 관리 API에 주소 대신 변수 이름만 보인다)이 그대로다. 뒤의 것은 모델마다 다른 서버를 가리키지 못해, 수락의 모델 둘이 서버 둘일 때 성립하지 않는다. 거부했다.
- **키를 정해진 환경 변수 하나에서 읽는다.** 모델 서버마다 다른 키를 쓰지 못한다. 거부했다.
- **모델 파일에 서버로 그대로 넘길 칸을 둔다.** 형식 강제나 사고 끄기를 모델 파일에서 켤 수 있다. 그러나 그 칸이 계약에 들고 엔진마다 뜻이 달라 검증할 수 없다. ADR 0040이 제공사에 그대로 넘기는 칸을 미룬 것과 같은 까닭으로 거부했다.
- **런타임이 vLLM의 확장을 직접 쓴다.** 시험하는 엔진에서는 깨진 도구 호출이 줄지만, 다른 엔진에서 그 칸이 어떻게 다뤄지는지 알 수 없고(보지 않았다) 엔진을 바꿔 끼우는 경계가 깨진다. 거부했다.
- **깨진 인자를 모델에게 오류로 돌려주고 다시 시킨다.** 도구가 실패했을 때 루프가 하는 일과 같은 모양이라 모델의 실수 한 번으로 실행이 끝나지 않는다. 그러나 `ToolCall`에 깨진 인자를 담을 자리가 없어 이벤트의 모양이 바뀌고, 재생과 재개가 그 기록을 다뤄야 한다. 거부했다. 치르는 값은 모델이 한 번 실수하면 그 실행 전체가 실패한다는 것이다.
- **새 실패 원인을 더한다.** 관리 화면에서 서버에 닿지 못한 것과 모델의 형식 실수가 원인만으로 갈린다. 그러나 실패 원인은 계약이고 최종 사용자 실패 항목이 같은 값 집합을 가리켜(`.claude/rules/sdk.md`) 웹 화면의 문구까지 바뀐다. 거부했다. 치르는 값은 실패 내용까지 읽어야 둘이 갈린다는 것이다.
- **알려진 표지가 답에 있으면 실패로 돌린다.** 표지는 파서마다 다르고(vLLM 문서의 파서 목록), 도구 호출 형식을 설명하는 답처럼 그 글자를 정당하게 담은 답이 실패가 된다. 거부했다. 치르는 값은 설정이 틀린 배포나 형식 강제가 없는 엔진에서 이상한 답이 실패 표시 없이 최종 사용자에게 보인다는 것이다.
- **런타임이 요청마다 형식 강제를 요구한다.** 표준 요청의 `tool_choice`로 도구 호출을 강제하면 모델이 답으로 끝낼 수 없고, vLLM에서 형식만 묶는 것은 서버 옵션이다(원문). OpenAI 규격의 도구 `strict` 칸을 호환 서버들이 어떻게 다루는지는 보지 않았다. 거부했다.
- **어댑터를 직접 짜거나 openai SDK만 들이고 변환은 직접 한다.** 의존이 줄지만, 루프가 기대는 메시지와 도구 호출의 해석(`core/loop.py`, `core/model.py`)을 이 저장소가 직접 짓고 지켜야 한다. 거부했다. 치르는 값은 이 라이브러리가 공식 OpenAI만 겨냥한다고 스스로 적어(문서 원문) 호환 서버와의 어긋남을 이 저장소의 시험이 지켜야 한다는 것이다.
- **키 변수가 없으면 실행 전에 거부하거나 서버를 띄울 때 확인한다.** 앞의 것은 모델을 만드는 것이 키를 요구하게 되어 포트의 전제와 Anthropic 키의 동작에서 갈리고, ADR 0049도 헤더 변수에서 같은 안을 거부했다. 뒤의 것은 기본 모델의 이름을 시작 때 확인하는 선례(ADR 0040)가 있으나, 모델 파일은 실행마다 다시 읽어 시작 뒤에 바뀔 수 있고 기본 모델이 아닌 모델의 키를 시작 때 볼 자리가 없다. 거부했다. 치르는 값은 설정 실수가 첫 요청이 실패할 때까지 드러나지 않는다는 것이다.
- **`max_tokens`가 없으면 16000을 보내거나 호환 서버에서는 꼭 적게 한다.** 문맥이 16,384인 모델(A.X 4.0 Light, 모델 카드 원문)에 16000을 보내면 입력이 384토큰을 넘는 요청은 상한과의 합이 문맥을 넘는다. 그 요청을 vLLM 0.30.0은 거절하고 0.33.0은 상한을 조용히 줄여 받으므로(위 "vLLM"), 서빙 엔진과 판에 따라 결과가 갈리는 값을 기본으로 보내게 된다. 꼭 적게 하면 모델마다 문맥 길이를 알아야 모델 파일을 쓸 수 있다. 거부했다.

## Consequences

- **계약 변경이 첫 티켓이다.** sdk의 `ModelProvider`와 새 칸 둘, `openapi.json`, 생성한 TS 타입이 함께 바뀐다. 생성 타입은 기본값이 있는 칸도 필수로 내므로(ADR 0049 Consequences의 같은 대목) 매니페스트 값을 생성 타입으로 적은 테스트 픽스처와 스토리에 새 칸이 늘고, 관리 화면이 매니페스트를 JSON 그대로 그리므로 줄이 늘어 사진 정답이 바뀔 수 있다(ADR 0049 이력 2026-11-10 "관리 화면의 매니페스트 JSON에 transport 줄이 늘어 사진 정답이 바뀐다"의 선례. 어느 파일인지는 세지 않았다). 그 티켓이 다른 티켓을 막는다.
- **구현 티켓이 함께 고칠 자리.** 제공사가 `anthropic` 하나이고 키가 `ANTHROPIC_API_KEY`라는 것을 전제로 적은 살아 있는 문서와 설정 전부이고, 구현 티켓이 그 말들로 저장소를 grep해 다시 찾는다. 지금 보이는 것은 `pyproject.toml`의 의존성 선언과 import-linter의 금지 목록 둘("core knows no provider", "sdk knows no engine"), `.claude/rules/sdk.md`의 모델 항목("값은 `anthropic` 하나", "`model`만 `provider`·`model_id`·`max_tokens`·`temperature`를 가진다"), `.claude/rules/adapters.md`의 모델 소스 항목(`ChatAnthropic`과 키를 스스로 읽는다는 문장), `.claude/rules/core.md`의 모델 포트 행, `README.md`와 `.env.example`의 모델 설명이다. `docs/constitution/tech.md`의 런타임 의존성 행은 이 ADR과 같은 PR이 고친다(헌법 판 3.0.85).
- **ADR 0040의 본문.** 세 자리에 `(바뀜: ADR 0057)` 포인터를 단다. 둘째 제공사를 거부하며 "`provider`는 닫힌 목록이고 지금은 `anthropic` 하나다"라고 적은 문장, 모델 매니페스트의 모양을 적은 문장(`provider`의 값, `max_tokens`가 없을 때의 16000), 키가 제공사의 환경변수 `ANTHROPIC_API_KEY`라는 문장이다. "이번 범위 밖"의 둘째 제공사는 그 ADR의 범위를 적은 기록이라 달지 않는다. 기능 계획은 주소의 자리를 ADR 0040의 이력에 적으리라 했으나, 새 의존성과 실패 처리까지 정하게 되어 새 ADR로 낸다.
- **최종 사용자에게 보이는 것.** 깨진 도구 호출과 키 변수 없음과 꺼진 서버는 모두 지금의 `model_call` 문구다. 글로 샌 도구 호출은 답으로 보일 수 있다.
- **배포가 알아야 할 것.** deploy-package의 배포 안내에 넘긴다(`.scratch/deploy-package/plan.md`에 적었다).
  - **서버 옵션.** 도구 호출을 켜는 두 옵션(`--enable-auto-tool-choice`, `--tool-call-parser`) 없이 띄운 서버는 도구가 든 요청을 거절해 실행이 원인 `model_call`로 실패한다. 옵션은 줬는데 파서가 모델과 맞지 않거나 형식 강제 옵션(`--tool-strict-level`)이 없으면 도구 호출이 답의 글로 샐 수 있다(`hermes` 파서는 표지를 찾지 못하면 글을 그대로 답에 싣는다, 소스). Qwen3처럼 사고가 기본으로 켜진 모델은 서버 옵션으로 끈다(vLLM 0.33.0 문서 원문).
  - **평문.** http 주소에서는 키가 평문으로 가므로 http 주소는 신뢰하는 내부 네트워크에서만 쓴다.
  - **프록시.** 프록시 환경 변수가 있으면 루프백 주소로 가는 요청도 프록시로 간다. 내부 주소를 `NO_PROXY`에 적어야 하고, `NO_PROXY=localhost`는 주소가 `127.0.0.1`일 때 덮지 못한다(손으로 봤다). 빠뜨린 요청은 키를 그 프록시에 넘긴다.
  - **상한.** 출력 길이 상한이 `max_completion_tokens`라는 이름으로만 나가므로, 옛 이름 `max_tokens`만 읽는 엔진에서는 모델 파일의 상한이 듣지 않을 수 있다(Ollama의 호환 층 소스를 읽었다). 상한을 적지 않았을 때 엔진의 기본값이 짧으면 답이 중간에 잘릴 수 있다(다른 엔진의 기본값은 보지 않았다).
  - **기다림.** HTTP 타임아웃의 기본이 없어 답하지 않는 모델 서버는 실행 전체의 기한(기본 600초)이 끊는다. 일시적 오류에는 SDK가 두 번 더 보낸다.
  - **주소의 쿼리.** 주소는 관리 API의 매니페스트 응답과 실패 문구에 그대로 실리므로 주소의 쿼리 문자열에 비밀을 적지 않는다. 런타임은 모델 파일을 읽는 단계에서 그것을 막지 않는다(결정 "주소는 비밀이 아닌 것으로 본다")(바뀜: 이력 2026-11-12 "모델 파일의 주소에 쿼리 문자열이 있으면 읽는 단계에서 거부한다").
- **로그.** openai SDK와 그 아래 HTTP 클라이언트의 로거가 DEBUG에서 인증 헤더나 요청 본문을 찍는지는 보지 않았다. 구현 티켓의 수락에 "키가 있는 모델로 부르며 루트 로거를 DEBUG로 켠 시험에서 키 값이 로그에 나타나지 않는다"를 넣는다(헌법 원칙 V. 같은 수락의 선례는 ADR 0049 Consequences "로그").
- **모델 파일을 쓰는 사람.** 모델 파일은 `base_url`과 `api_key_env`를 함께 들어, 파일을 쓴 사람이 운영자의 환경 변수를 제 주소로 보내게 적을 수 있다. 이 ADR은 그것을 막는 승인을 두지 않는다. 플러그인 디렉터리에 파일을 두는 운영자가 지금의 신뢰 경계다(ADR 0049 Consequences "매니페스트 저자와 운영자"와 같은 판단이다).
- **뒤 기능이 기대는 것.** deploy-package는 배포 환경의 모델 서버를 이 값의 모델 파일로 가리키고, answer-eval은 로컬 모델의 지연과 정답률을 이 길로 다시 잰다(그 기능 계획).
- **용어.** `CONTEXT.md`에 모델 서버와 서빙 엔진을 더하고, 모델의 정의에 모델 서버의 주소와 키 변수의 이름을 더했다. 모델 항목이 피하는 말 "엔드포인트"는 그대로이고, 기능 계획이 쓴 "OpenAI 호환 엔드포인트"는 모델 서버로 읽는다.

## 이력

### 2026-11-12 모델 파일의 주소에 쿼리 문자열이 있으면 읽는 단계에서 거부한다

local-model 명세(`.scratch/local-model/spec.md`의 "매니페스트")를 쓰며 정했고 사용자가 승인했다(일지 2026-11-12-0248 "ADR 0057 이력 둘의 승인"). 설계가 묻지 않은 자리를 명세가 재어 찾은 것이다. 측정은 `.scratch/local-model/probes/`(결과는 그 `README.md`)이고 Windows 10에서만 쟀다.

**찾은 것.** langchain-openai 1.6.2와 openai 3.49.0은 쿼리가 든 `base_url`의 쿼리 뒤에 경로를 붙여, 가짜 모델 서버가 받은 요청 줄이 `POST /v1/?probe_token=query-secret-4b9dchat/completions`였다(쟀다, `.scratch/local-model/probes/openai_compat.py`의 `path_with_query`). 경로는 `/v1/`이고 `chat/completions`는 쿼리 값의 꼬리가 되어 Chat Completions의 경로를 가리키지 않는다. 실제 모델 서버가 그 요청에 무엇을 답하는지는 보지 않았다. 같은 주소는 401의 원인 예외(`httpx2.HTTPStatusError`)의 글과 `httpx2` 로거의 INFO 요청 줄에 쿼리째 실린다(쟀다, 같은 프로브의 `query_url_401`, `logs_401_query_url`). 결정 "주소는 비밀이 아닌 것으로 본다"가 쿼리를 막지 않은 것은 원격 MCP 서버의 주소와 같은 판단이었는데, 이 제공사에서는 쿼리가 든 주소로 Chat Completions에 붙는 모델 서버가 없을 것으로 보아(어림) 받아 둘 까닭이 없고, 받아 두면 쿼리에 적은 비밀이 관리 API와 실패 문구와 원인 예외와 로그로 나가기만 한다.

**바뀐 것.** `openai-compatible`의 `base_url`은 조각(`#` 뒤)을 뗀 글자에 `?`가 있으면 읽는 단계에서 거부한다(빈 쿼리도 든다). 문구는 `base_url 에 쿼리 문자열을 적을 수 없다`이고 값을 되울리지 않는다. 결정 "주소는 비밀이 아닌 것으로 본다"의 쿼리 문장들과 Consequences "주소의 쿼리"의 "런타임은 … 막지 않는다"가 거짓이 되어 포인터를 달았다. 주소의 나머지가 관리 API와 실패 문구에 실리는 것은 그대로다. 원격 MCP 서버의 `url`의 규칙은 바꾸지 않는다(그 칸에서 쿼리가 요청을 깨는지는 재지 않았다). 조각은 라이브러리가 떼고 보내 막지 않는다(쟀다, `.scratch/local-model/probes/openai_compat.py`의 `path_with_fragment`). 배포 안내에 넘긴 "주소의 쿼리"는 비밀을 적지 말라는 안내가 아니라 이 거부 문구를 설명하는 것이 된다(`.scratch/deploy-package/plan.md`에 적었다).

**거부한 안.** 쿼리를 막지 않고 그대로 둔다(이 결정의 원래 모양이다. 첫 호출이 깨진 요청 줄로 가고 쿼리는 관리 API와 실패 문구와 로그에 그대로 실린다). 어댑터가 쿼리를 떼어 경로를 고친다(파일에 적은 주소와 실제로 가는 주소가 달라지고, 쿼리로 인증하는 서버라면 조용히 인증이 빠진다).

### 2026-11-12 모델 이름의 머리에 따라 라이브러리가 요청을 바꾸는 것을 알려진 한계로 둔다

local-model 명세(`.scratch/local-model/spec.md`의 "요청")를 쓰며 정했고 사용자가 승인했다(일지 2026-11-12-0248 "ADR 0057 이력 둘의 승인"). 설계가 묻지 않은 자리를 명세가 재어 찾은 것이다.

**찾은 것.** `use_responses_api=False`로 Responses API를 막아도 langchain-openai 1.6.2는 모델 이름을 보고 Chat Completions 요청을 바꾼다. 이름이 `o1-local`·`o3-local`이면 시스템 메시지가 `role: developer`로 가고, `gpt-5-local`·`gpt-5-pro-local`이면 매니페스트의 `temperature`가 빠진다. `local-model`과 `my-codex-model`은 그대로다(쟀다, `.scratch/local-model/probes/openai_compat.py`의 `model_name_quirks`. 이 여섯 이름만 넣었다). 조건은 읽었다(`chat_models/base.py`). 역할은 이름이 정규식 `^o\d`에 맞을 때 바뀌고, 온도는 소문자로 바꾼 이름이 `gpt-5`로 시작하고 `chat`이 없으며 값이 1이 아닐 때 빠진다(`reasoning_effort`나 `reasoning.effort`가 `none`이면 빼지 않는데, 어댑터는 그 칸을 주지 않는다). 로컬 모델 시험의 두 모델 이름(`skt/A.X-4.0-Light`, `openai/gpt-oss-20b`)은 두 조건에 걸리지 않는다(읽은 조건에 대 봤다).

**바뀐 것.** 그런 이름의 모델을 내는 모델 서버에서는 결정 "요청"의 "모델 파일에 있을 때의 … 온도"가 실리지 않고 대화의 시스템 메시지가 다른 역할로 간다. 그 문장에 포인터를 달았다. 런타임은 이것을 막지 않는다. 다른 실린 것(모델 이름, 도구 목록, 상한)과 `tool_choice`를 싣지 않는 것은 그대로다.

**거부한 안.** 하위 클래스가 라이브러리의 요청 본문을 만드는 메서드(`_get_request_payload`)를 재정의해 되돌린다(라이브러리의 안쪽 메서드에 기대어 판을 올릴 때마다 깨질 수 있고, 그 이름의 실제 OpenAI 모델에는 라이브러리의 처리가 맞다). 그런 `model_id`를 읽는 단계에서 거부한다(sdk가 라이브러리의 이름 규칙을 알게 되고, 게이트웨이 뒤의 OpenAI 모델을 쓰지 못한다).
