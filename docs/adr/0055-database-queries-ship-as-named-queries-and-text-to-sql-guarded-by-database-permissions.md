# 데이터베이스 조회는 정해 둔 조회와 조회문 직접 작성을 둘 다 커스텀 에이전트용 부품으로 내고, 실행 전에 묻지 않으며 안전은 데이터베이스 권한으로 지킨다

기본 에이전트가 찾는 수단은 문서 검색 하나다(ADR 0051). "지난달 재고가 몇 개야?"처럼 숫자가 바뀌고 합계를 내야 하는 질문은 문서 검색으로 답하지 못한다. 문서 검색 서버는 그런 데이터를 색인하지 않고, 그 저장소의 PRD는 그런 질의를 "클라이언트 쪽 도구의 몫"으로 적었다(그 저장소의 `docs/PRD.md` 13줄을 읽었다). agent-os의 PRD는 그것을 "구조화 데이터 질의(Text-to-SQL)"라는 이름으로 "미룬 것"에 올려 "돌아오면 그 기능의 설계 인터뷰가 처음부터 묻는다"고 적어 두었다. 사용자가 "메모리 계층이나 검색 수단의 확장을 원해"라고 했고, 설계 인터뷰(일지 2026-11-10-1845)에서 문서 검색 밖의 수단으로 "문서 묶음 여럿 중에서 고르기", "데이터베이스에 묻기", "사내 시스템 조회"를 골랐다. 이 문서는 뒤의 둘을 정한다(앞의 것은 ADR 0051의 이력이다). **데이터베이스 조회는 두 방식을 모두 정식으로 낸다. 운영자가 조회문을 미리 적어 두는 정해 둔 조회와, 모델이 조회문을 스스로 쓰는 조회문 직접 작성(Text-to-SQL)이다. 둘 다 런타임 밖의 MCP 서버(조회 서버)가 맡고, 커스텀 에이전트가 골라 붙이며 기본 에이전트에는 붙이지 않는다. 조회문을 실행하기 전에 사람에게 묻지 않고, 안전은 조회문 검사가 아니라 데이터베이스 권한으로 지킨다. 두 방식 모두 사람마다 볼 수 있는 데이터로만 답한다. 사내 시스템 조회는 본보기 하나와 만드는 방법의 안내를 내고 조회만 한다. 웹 검색은 하지 않는다.**

## 결정

- **두 방식을 모두 정식으로 낸다.** 정해 둔 조회는 운영자가 조회문을 미리 적어 두고 모델은 값만 넘겨 부른다. 조회문 직접 작성은 모델이 질문을 읽고 조회문(SQL)을 스스로 쓴다. 둘 다 이 저장소가 시험하고 평가하는 기능으로 낸다. PRD의 "미룬 것"에서 그 항목을 꺼낸다(사용자 승인).
- **자리.** 조회는 MCP 서버의 도구다. 이 저장소가 내는 것은 조회 서버를 가리키는 연결 플러그인, 스킬, 규칙 파일의 본보기 표, 안내 문서다. 기본 에이전트 `assistant`에는 붙이지 않고(ADR 0051의 범위 밖 그대로다), 필요한 조직이 커스텀 에이전트에 붙인다. core, sdk, 채널 계약은 이 결정으로 바뀌지 않는다.
- **실행 전에 묻지 않는다.** 본보기 규칙 파일은 조회 도구를 `allow`로 적는다. 일반 직원은 조회문을 읽지 못하므로 승인 카드를 띄워도 내용을 판단하기 어렵다. 조사한 운영용 제품 다섯(Snowflake Cortex Analyst, Databricks Genie, Microsoft Fabric data agent, Google 대화형 분석, Amazon Bedrock Knowledge Bases)에서 실행 전에 사람에게 확인받는 곳은 찾지 못했다(서브에이전트가 공식 문서에서 핵심어에 걸린 문장을 읽은 결과이고 페이지 전체를 읽은 것이 아니다. 일지의 "조사 (셋째)" 절). 운영자는 규칙 한 줄로 `ask`로 바꿀 수 있다.
- **안전은 데이터베이스 권한으로 지킨다.** 안내 문서가 셋을 요구한다. 조회 권한만 가진 전용 데이터베이스 계정을 쓴다. 그 계정에는 보여도 되는 표만 연다. 결과의 줄 수와 실행 시간에 상한을 둔다.
- **두 방식 모두 사람마다 다르게 보인다.** 사람마다 볼 수 있는 데이터가 다른 조직에서 두 방식 모두 그 사람이 볼 수 있는 데이터로만 답한다.
  - 정해 둔 조회는 조회 서버가 지금 묻는 주체를 조회의 값으로 채운다. 모델은 그 값을 넘기지 않고 넘겨도 쓰이지 않는다. "내 휴가가 며칠 남았어?"의 "내"를 모델이 아니라 서버가 정한다.
  - 조회문 직접 작성은 데이터베이스의 행 수준 보안을 쓴다. 조회 서버가 요청마다 데이터베이스에 지금 누구인지를 알리고, 데이터베이스가 그 사람에게 보이는 줄만 돌려준다. 모델이 쓴 조회문이 그 설정을 바꾸거나 되돌리지 못해야 한다. PostgreSQL 문서로 보면 `SET LOCAL`은 트랜잭션 끝까지만 남고, 두 부분으로 된 이름의 설정은 누구나 넣을 수 있으며, `RESET ROLE`은 누구나 실행할 수 있다(서브에이전트가 공식 문서 원문을 읽었다고 보고했다). 그래서 모델이 쓴 조회문이 같은 세션에서 돌면 설정이나 역할을 되돌릴 수 있다는 것은 그 문장들에서 낸 추론이다(어림). 막는 방식은 명세가 실제 데이터베이스로 재서 정한다. 조직의 데이터베이스 관리자가 표마다 정책을 써야 한다.
  - 조사한 Snowflake, Databricks, Microsoft의 제품이 질문한 사람의 신원이나 권한으로 실행한다(같은 보고).
- **조회 서버의 조건 여섯.** 서버를 만들지 가져다 쓸지는 구현 직전에 정하고, 지금은 지켜야 할 조건만 정한다(기본값). 만들기로 하면 서버를 둘 저장소도 그때 정한다. 이 저장소, 문서 검색 서버의 저장소(rag-engine), 새 저장소가 후보다(사용자가 "구현 직전에 정함"을 골랐다. 아래 Considered Options). 다른 저장소에 두면 서버 안쪽(데이터베이스에 붙는 방식, 주체를 데이터베이스에 알리는 방식, 상한을 거는 방식)은 그 저장소의 ADR이 정하고, 이 문서에는 이 저장소가 내는 것과 서버에 요구하는 조건이 남는다.
  - 쓰기를 조회문 검사가 아니라 데이터베이스 권한으로 막는다.
  - 한 번에 조회문 하나만 실행한다.
  - 결과의 줄 수와 실행 시간에 상한을 둔다.
  - 묻는 사람은 모델이 채우는 인자가 아니라 런타임이 주체 전파로 넘긴 주체로만 받는다.
  - 익명 주체의 요청과, 주체가 실리지 않았거나 읽지 못한 요청에는 사람별 조회를 거부한다. 주체 전파는 기본이 꺼져 있어(ADR 0042 "서버 파일") 켜지 않고 연결하면 주체 없는 요청이 온다(PR 직전 리뷰가 짚었고 사용자가 "거부한다고 적음"을 골랐다. 일지 2026-11-10-1845의 "PR 직전 리뷰").
  - 바깥 API 없이 폐쇄망에서 돈다.
- **조건의 근거.** 조사에서 본 것들이다. MCP Toolbox의 문서는 SQL 문자열 검사와 세션 플래그가 우회된다고 적고 엔진 수준의 잠금을 권한다. DBHub는 읽기 전용 설정이 적용되지 않던 문제와 주석 해석 차이로 DROP이 지나간 문제가 보안 권고로 공개됐다. Postgres MCP Pro는 제한 모드에서 서버 파일을 읽는 우회가 보고됐다. Datadog Security Labs의 글은 읽기 전용 트랜잭션을 입력의 `COMMIT;`으로 끝낼 수 있었다고 적고, 권한을 줄인 데이터베이스 계정, 여러 문장을 싣지 못하는 prepared statement, 호출마다 연결을 새로 쓰기를 권고했다(여기까지는 서브에이전트가 원문을 읽었다고 보고했다. 일지의 "조사 (셋째)" 절). 그 글이 다룬 것이 공식 참조 PostgreSQL 서버이고 그 서버가 보관 처리됐다는 것은 웹 요약으로 읽었다(일지의 "조사" 절). MCP Toolbox는 인증된 사용자의 값으로 매개변수를 채우는 기능이 MCP로는 지원되지 않는다고 적어(웹 요약), 지금 그대로는 위 여섯 가운데 넷째(묻는 사람을 주체로만 받는다)에 맞지 않는다. 구현 직전에 다시 조사한다.
- **틀린 숫자를 줄인다.** 표와 열의 설명, 그리고 검증된 질문과 조회문의 예시를 스킬에 담게 한다. 답에는 어떻게 계산했는지(기간, 조건)를 문장으로 밝히게 한다. 최종 사용자의 화면에는 조회문이 보이지 않기 때문이다(진행 항목은 도구 이름과 성패만 싣는다. ADR 0023). 평가는 정답 조회문의 결과와 견준다. 조사한 제품들이 표·열 설명과 검증된 질의 예시로 정확도를 올리고, Snowflake와 Databricks가 정답 조회문의 결과와 견주는 평가를 낸다(같은 보고). 모두 기본값이다.
- **사내 시스템 조회.** "내 휴가가 며칠 남았어?"처럼 사내 시스템(인사, 결재 같은 것)의 API를 불러 답하는 것이다. 시스템마다 연결을 따로 만들어야 하므로 이 저장소는 본보기 하나와 만드는 방법의 안내를 낸다. 조회만 하고, 신청이나 결재 같은 쓰기는 범위 밖이다(기본값). 묻는 사람은 정해 둔 조회와 같이 서버가 주체 전파로 받은 주체로 정한다(합의 요약 뒤에 문서를 쓰며 정했다. 일지 2026-11-10-1845의 "문서를 쓰며 정한 것").
- **웹 검색은 하지 않는다.** 인터뷰가 올린 선택지였고 사용자가 고르지 않았다. 기준선의 전제가 바깥 API 없는 폐쇄망이다(PRD 성공의 정의).
- **차례.** 구현은 기준선 뒤다. 시작하는 때와 새 부품의 차례는 ADR 0046 이력 2026-11-10 "제품 1.0에 지식베이스 고르기가 들고 커스텀 에이전트의 부품 다섯이 새 묶음으로 선다"가 원천이고, 조회는 기억 다음이다. 조회 안에서는 정해 둔 조회로 조회 서버의 뼈대(주체를 받는 길, 권한, 상한)를 먼저 세우고, 가장 크고 위험한 조회문 직접 작성을 그 위에 얹는다. 기능 계획은 `.scratch/named-query/plan.md`, `.scratch/system-lookup/plan.md`, `.scratch/text-to-sql/plan.md`다.
- **명세가 정할 것.** 조회 서버(만들지 가져다 쓸지, 만들면 어느 저장소에 둘지), 먼저 지원할 데이터베이스, 정해 둔 조회를 적는 파일의 모양, 조회문 직접 작성에서 주체를 데이터베이스에 알리고 되돌리지 못하게 막는 방식, 상한의 값, 스킬에 표 구조를 담는 모양, 평가 세트와 재는 방법, 사내 시스템 조회의 본보기로 삼을 시스템, 조회 서버의 신뢰 수준이다. 조회 결과에 사람이 쓴 글(문의 내용 같은 열)이 섞이면 그 글 속의 지시가 문서 속 지시와 같은 위험이 된다. 고객 문의 글에 심은 지시가 도우미를 움직여 비공개 표를 읽게 한 사례가 공개돼 있다(Supabase MCP, 서브에이전트가 원문을 읽었다고 보고했다).
- **범위 밖.** 데이터베이스에 쓰는 조회문, 사내 시스템의 쓰기(신청, 결재), 웹 검색, 기본 에이전트에 조회를 붙이는 것, 문서 검색 서버가 구조화 데이터를 색인하는 것.

## Considered Options

- **정해 둔 조회만 낸다.** 인터뷰의 첫 추천안이었다. 모델이 조회문을 쓰지 않으므로 운영자가 적어 둔 것 밖의 데이터가 나갈 길이 없다. 사용자가 방식을 되물은 뒤("보통 TTS랑 정해 둔 조회 둘 다 지원해?") 고르지 않았다. 적어 두지 않은 질문에는 답하지 못한다.
- **정해 둔 조회가 기본이고, 조회문 직접 작성은 막아 두고 운영자가 열 수 있게 한다.** 설명 뒤 다시 물을 때의 추천안이었다. MCP Toolbox의 문서가 모델이 쓴 SQL을 그대로 실행하는 도구를 개발 보조용으로 적고 운영 에이전트에는 쓰지 말라고 적은 것(웹 요약)과 같은 방향이다. 사용자가 "두 방식을 모두 정식으로 지원"을 골랐다. 그 값은 Consequences에 적는다.
- **조회문 직접 작성은 승인 뒤에만 실행한다. 또는 실행할 때마다 묻는 것을 기본으로 한다.** 인터뷰가 올린 선택지 둘이다. 사용자가 "묻지 않고 실행하고, 안전은 데이터베이스 권한으로 지킴"을 골랐다. 조회문을 읽지 못하는 사람의 승인은 통제가 되지 못한다.
- **정해 둔 조회에서만 사람마다 다르게 하고, 조회문 직접 작성은 모두 같은 범위를 본다.** 인터뷰의 추천안이었다. 행 수준 보안과 되돌리지 못하게 막는 장치가 필요 없어 일이 작다(어림). 사용자가 "두 방식 모두 사람별로 다르게"를 골랐다. 고르지 않은 나머지는 "첫 판은 두 방식 모두 같은 범위"다.
- **읽기 전용을 조회문 검사(첫 낱말 분류, 구문 분석)나 읽기 전용 트랜잭션으로 지킨다.** 거부했다. 위 "조건의 근거"에 적은 DBHub와 Postgres MCP Pro가 이 방식에 기댔고 우회가 보고됐으며(원문을 읽었다는 보고), 공식 참조 PostgreSQL 서버도 읽기 전용 트랜잭션에 기댔다가 우회됐다(웹 요약). MCP Toolbox의 문서도 이 방식이 우회된다고 적는다.
- **기본 에이전트에 붙인다.** 거부했다. ADR 0051을 다시 열어야 하고, 사용자가 "기본은 그대로, 골라 붙이는 부품으로"를 골랐다.
- **조회 서버를 지금 문서 검색 서버의 저장소(rag-engine)에 두기로 정한다.** 그 저장소의 PRD는 "구조화 데이터의 Text-to-SQL. 클라이언트 쪽 도구의 몫이다."라고 적는다(그 저장소의 `docs/PRD.md` 13줄을 읽었다). 초안은 묻지 않고 그 줄을 따라 이 길을 닫았다. 사용자가 승인 뒤에 "근데 데이터베이스 조회와 사내 시스템 조회는 reg-engine 저장소 ADR이여야 하는거 아니야?"라고 물었고, 올린 선택지 "구현 직전에 정함"과 "지금 rag-engine으로" 가운데 앞의 것을 골랐다. 그래서 이 길은 닫지 않고 후보로 남긴다. 그 저장소에 두려면 그 PRD의 그 줄을 먼저 고쳐야 한다. 지금 정하면 설치할 서버가 하나로 줄고 주체를 확인하는 처리와 데이터베이스 연결 코드를 문서 검색과 함께 쓸 수 있지만(어림), 문서 검색 서버가 업무 데이터베이스의 접속 정보까지 갖게 되어 범위가 커진다. 사내 시스템 조회의 본보기를 두는 자리는 `system-lookup`의 명세가 정한다. 문서를 색인하고 검색하는 일이 아니라 그 저장소와는 맞지 않는다고 이 세션이 답했고, 사용자가 달리 말하지 않았다.

## Consequences

- **일이 크다.** 조회문 직접 작성을 정식으로 내려면 표 구조를 설명하는 스킬의 모양, 숫자가 맞는지 재는 평가, 행 수준 보안을 지키는 서버가 모두 필요하다(어림). 제품 1.0의 나머지와 시간을 나눠 쓴다.
- **조직의 데이터베이스 관리자가 할 일이 생긴다.** 전용 계정, 보여도 되는 표의 권한, 행 수준 보안의 정책은 이 제품 밖에서 조직이 만든다. 안내 문서가 무엇을 해야 하는지를 적지만 그것을 했는지는 이 제품이 확인하지 못한다. PostgreSQL에서는 슈퍼유저, `BYPASSRLS` 역할, `FORCE ROW LEVEL SECURITY`를 켜지 않은 표의 소유자가 행 수준 보안을 건너뛴다(서브에이전트가 공식 문서 원문을 읽었다고 보고했다).
- **트레이스에 남는 것.** 묻지 않고 실행하므로 통제의 자리는 실행 뒤의 기록이다. 조회문은 `tool_called`의 인자(`args`)로, 결과는 같은 이벤트의 `content`로 트레이스에 남아 운영자가 되짚는다(`src/agent_os/sdk/events.py`의 `ToolCalled`를 읽었다). 결과에 든 값도 트레이스에 그대로 남으므로 수명은 보존 기간이 정한다. 사람별 조회의 결과도 같다. 행 수준 보안은 질문한 사람과 데이터베이스 사이의 경계이고, 트레이스는 그 경계 밖에서 모든 사람의 결과를 모은 기록이다. 그래서 데이터베이스에서는 그 사람에게만 보이는 줄도 관리 API로 트레이스를 읽는 운영자에게는 보인다(`src/agent_os/admin/http.py` 231줄의 `read_trace`. ADR 0054가 같은 줄을 든다). 안내 문서는 이 사실을 고지에 적도록 안내한다. 결과의 어느 칸이 트레이스에 남는지와 가릴 길이 있는지는 명세가 본다. 값 가림(value-masking)은 런타임이 아는 비밀 값만 가리므로 조회 결과에는 닿지 않는다(`.scratch/value-masking/plan.md`를 읽었다. PR 직전 리뷰가 짚었다. 일지 2026-11-10-1845의 "PR 직전 리뷰").
- **익명 주체.** 익명 주체의 요청에는 사람별 조회를 거부하므로, 익명 모드의 사이트에서는 누구에게나 같은 답이 나가는 조회만 쓸 수 있다. 주체 전파를 켜지 않고 연결한 조회 서버도 같다.
- **주체 전파에 기댄다.** principal-propagation 전에는 조회 서버가 묻는 사람을 알 길이 모델이 채우는 인자뿐이라 만들지 않는다. 주체가 조직의 사용자 식별자와 대응될 수 있어야 데이터베이스와 사내 시스템이 그 사람을 알아본다. 그 설계에 넘겼다.
- **끝 둘을 나눠 쓴다.** 조회 호출이 그 에이전트의 도구 호출의 끝과 턴의 끝을 나눠 쓴다(ADR 0052). 조회문이 틀려 다시 쓰는 호출도 그 끝에 든다.
- **용어와 PRD.** `CONTEXT.md`에 "정해 둔 조회"와 "조회문 직접 작성"을 더한다. PRD의 "미룬 것"에서 그 항목을 꺼내고 "무엇을 만드나"와 성공의 정의에 데이터베이스 조회를 더한다(사용자 승인).
- **근거의 한계.** 다른 제품과 오픈소스 서버의 방식은 서브에이전트의 보고이고, 이 세션은 어느 주소도 직접 받아 보지 않았다. "찾지 못했다"는 서브에이전트가 읽은 문장에 없었다는 뜻이다. 주소와 근거의 종류는 일지 2026-11-10-1845의 조사 절이 적는다.
