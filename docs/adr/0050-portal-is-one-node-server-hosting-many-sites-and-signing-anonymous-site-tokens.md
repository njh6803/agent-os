# 질문 페이지는 `node:http` 서버 하나로 사이트 여럿을 담고, 고지를 확인한 브라우저의 익명 식별자로 사이트 토큰을 낸다

최종 사용자 경로는 사이트가 RS256으로 서명한 토큰만 받는다(ADR 0023). 공개 데모에도 배포 환경에도 위젯을 붙일 포털이나 토큰을 서명할 서버가 없을 수 있어, 기능 계획 pilot-portal은 토큰을 서명해 내주는 작은 질문 페이지를 이 저장소가 함께 내기로 했다(ADR 0046 이력 2026-11-06). 그 페이지는 사이트 쪽이고 Agent OS의 일부가 아니다(ADR 0047 Consequences). 설계 인터뷰 도중 사용자가 앞선 요구를 다시 꺼냈다. 사이트마다 위젯을 설정할 수 있어야 하고(에이전트, 모양), 그 설정으로 그린 위젯을 사이트를 고르는 셀렉트 박스로 골라 보고 질문해 볼 수 있어야 하며, 사이트마다 로그인이 필요한지 익명인지 둘 다인지가 설정이어야 한다. 그 요구는 저장소 어디에도 적혀 있지 않았고(일지 2026-11-09-1410), 사용자가 "설정은 사이트 여럿, 미리보기까지 지금"을 골라 이 기능의 범위가 됐다. **질문 페이지는 `web/apps/` 아래의 앱 하나이고, 표준 라이브러리 `node:http`로 선 무상태 서버 하나가 페이지와 끝점을 함께 낸다. 시작 인자는 질문 페이지 설정 TOML과 `serve`의 사이트 파일 둘이고, 설정은 사이트 여럿의 목록이며, 시작 때 두 파일을 대 보아 어긋나면 뜨지 않는다. 페이지는 하나이고 셀렉트 박스로 고른 사이트의 설정으로 위젯을 그린다. 처음 온 브라우저는 고지 전문을 확인한 뒤에야 그 사이트의 익명 식별자 쿠키를 받고, 토큰 끝점은 그 식별자로 `sub`가 `anon-<UUID>`인 120초짜리 토큰을 그 사이트의 발급자로 서명해 낸다. 보증 모드는 익명·로그인·둘 다를 받되 이번에 실제로 도는 것은 익명뿐이다.** Next를 쓰지 않는 이유는 web 워크스페이스의 ESLint가 Next 서버 파일(route, middleware, proxy, instrumentation)과 Server Actions를 모든 앱에서 막아(`web/eslint.config.mjs`, ADR 0019) 개인 키로 서명하는 코드를 Next 앱 안에 둘 자리가 없기 때문이다. 사이트 파일을 함께 읽는 이유는 발급자·열 에이전트·허용 출처·공개 키가 이미 거기 있어 다시 적으면 두 파일이 어긋날 수 있기 때문이다.

## 결정

- **앱과 서버.** `web/apps/` 아래 질문 페이지 앱 하나(폴더 이름은 명세가 짓는다)이고, 표준 라이브러리 `node:http` 서버 하나가 페이지, 끝점, 정적 파일을 낸다. 서버는 무상태다. 식별자를 저장하지 않고 쿠키 값의 꼴만 검사한다. `127.0.0.1`과 `::1`에서만 듣고, 설정의 호스트가 그 밖이면 시작에서 구성 오류로 끝난다(fail-closed, 위젯의 시작 래퍼 `tools/start.ts`와 같은 문구). TLS를 끝내는 프록시 뒤에만 선다. 루프백 목록은 `serve`(`main.py`의 `LOOPBACK_HOSTS`), 관리 화면(`tools/loopback.ts`), 위젯(`tools/start.ts`)에 이어 네 파일이 따로 들고, 바꾸면 넷을 함께 고친다. 서버는 `serve`를 부르지 않는다. 사이트 파일을 디스크에서 읽을 뿐이다. Next와 새 프레임워크 의존성이 없고 프로세스가 하나라 컨테이너 이미지도 하나다(release-image 몫). 선례는 위젯 e2e의 중계(`web/apps/widget/e2e/relay.ts`)다.
- **띄우기.** 두 Next 앱의 시작 래퍼(`node tools/start.ts`)처럼 node가 타입만 벗겨 `.ts` 파일을 빌드 없이 바로 돌린다. 앱의 `start` 스크립트는 `node <입구>.ts --config … --site-file …` 꼴이고 빌드 단계와 `dist` 폴더가 없다. import는 확장자를 붙이고 문법은 기준 tsconfig의 `erasableSyntaxOnly`가 묶어 둔다(`web/tsconfig.base.json`). 타입 검사는 `pnpm -C web verify`의 `tsc --noEmit`이 워크스페이스 전체에 돈다. 컨테이너 이미지는 소스와 `node_modules`를 그대로 담는다. 조건이 하나 있다. 질문 페이지가 import하는 워크스페이스 패키지(사이트 파일 읽기, `@agent-os/ui`의 `THEMES`·`MODES`, 디자인 시스템 CSS)도 node가 바로 읽을 수 있는 꼴이어야 한다. 이 조합이 서는지는 명세 전에 `.scratch/pilot-portal/probes/`의 프로브로 재고, 그 결과를 이 ADR의 이력에 적는다. 재기 전에는 어림이다. 지금 코드를 읽어 아는 걸림돌은 셋이다. `@agent-os/ui`의 진입점 `src/index.ts`는 React 컴포넌트(`.tsx`)까지 다시 내보내므로 타입 벗기기만으로는 읽지 못해 `THEMES`·`MODES`만 드는 진입점(서브패스 export)이 필요할 수 있다. 디자인 토큰 CSS `src/styles/theme.css`는 Tailwind 지시문(`@theme`)을 품은 원본이라 브라우저가 그대로 읽지 못하고, 패키지의 `build`가 내는 `dist/theme.css` 같은 산출이 필요할 수 있다. node는 `node_modules` 아래 파일의 타입을 벗기지 않는데 pnpm 워크스페이스 링크를 실제 경로로 풀면 그 밖이 된다는 것은 Node 문서로 아는 것이고 이 워크스페이스에서 대 보지 않았다. 위젯 빌드의 `next.config.ts`가 옮겨 간 패키지의 `.ts` 진입점을 읽는지도 같은 프로브가 본다.
- **시작 인자와 시작 검사.** 시작 인자는 질문 페이지 설정 TOML 파일과 `serve`의 사이트 파일(`--site-file`과 같은 파일) 둘이다. 읽는 데는 위젯이 이미 쓰는 smol-toml을 쓴다. 설정은 사이트 여럿의 목록이다. 사이트마다 발급자(사이트 파일의 항목을 고르는 열쇠), 경로에 쓸 이름(slug), 에이전트 하나, 위젯의 모양 값(제목, 소개, 테마, 밝음), 보증 모드(익명·로그인·둘 다), 고지 글, 보고서 링크를 적고, 공통으로 개인 키 경로와 `kid`, 공개 출처, 듣는 호스트와 포트를 적는다. 정확한 칸 이름은 명세가 짓는다. 고지 글은 비울 수 있는 칸이다. 비우면 질문 페이지의 기본 글을 쓰고, 사이트가 적은 글이 있으면 그 글이 이긴다(ADR 0047대로 문구는 사이트가 가진다). 기본 글은 질문이 기록되고 모델 API에 보내진다는 것, 익명 식별자 쿠키를 둔다는 것, 개인정보를 넣지 말라는 것을 적는다. 익명 식별자 쿠키를 둔다는 문장은 사이트가 글을 적어도 질문 페이지가 고지 전문에 늘 넣는다. 그 쿠키는 사이트의 글이 아니라 질문 페이지의 동작이기 때문이다. 사이트 파일에서는 발급자, 열 에이전트, 허용 출처, 공개 키, 대상(`audience`)을 읽는다. 시작 때 대 보는 것은 다음이고 하나라도 어긋나면 뜨지 않는다(fail-closed). 발급자가 사이트 파일에 있다. 고른 에이전트가 그 사이트의 열 에이전트에 든다. 질문 페이지의 공개 출처가 그 사이트의 허용 출처에 든다. 설정의 `kid`로 그 사이트에 든 공개 키가 개인 키에서 난 공개 키와 같다. 설정의 모양이 맞다(모르는 키, 빠진 필수 키, 테마 키는 `THEMES`에, 밝음은 `MODES`에, 보증 모드는 셋 가운데, 이름은 경로에 쓸 수 있는 글자). 개인 키 파일이 없거나 RSA 개인 키가 아니면 구성 오류다. 사이트 파일 형식(`schema_version` "1")은 바꾸지 않고, 질문 페이지가 그 형식에 묶인다. 두 파일은 시작 때 한 번 읽는다. `serve`는 바뀐 사이트 파일을 요청마다 변경 시각으로 보고 다시 읽지만(ADR 0023 이력 2026-11-04), 질문 페이지는 그러지 않아 운영 중에 사이트 파일이나 질문 페이지 설정이나 키를 바꾸면 다시 띄워야 하고, 그 전까지는 옛 판으로 검사하고 서명한다.
- **경로.** `/`는 `/portal/`로 302다. `/portal/`이 페이지 하나다. 사이트마다 `/portal/sites/<이름>/` 아래에 확인 여부를 답하는 상태 끝점, 쿠키를 내는 확인 끝점(POST), 토큰 끝점이 있다. 토큰 끝점은 쿠키가 없거나 꼴이 아니면 401이고, 보증 모드가 로그인인 사이트에서는 늘 거절한다. `/portal/health`가 있다. 페이지 스크립트와 디자인 토큰 CSS·글꼴 CSS 같은 정적 파일을 낸다. 그 밖은 404다. 끝점 이름은 명세가 짓는다. 프록시가 질문 페이지로 넘기는 규칙은 `= /`와 `/portal/` 둘이고 위젯 e2e의 중계처럼 그 밖은 404다. 그래서 공개 주소의 페이지 주소는 `https://<공개 호스트>/portal/`이고 루트로 들어오면 넘어간다. 페이지는 고른 사이트를 질의 `?site=<이름>`에 남겨 새로 고침과 링크가 같은 사이트를 열고, 사이트가 하나면 셀렉트 박스를 숨긴다.
- **익명 식별자 쿠키.** 확인 끝점이 UUID v4를 만들어 `HttpOnly`, `SameSite=Strict`, `Path=/portal/sites/<이름>`, 30일로 둔다. 확인 끝점은 요청의 `Origin` 헤더가 설정의 공개 출처와 같을 때만 쿠키를 내고, 헤더가 없거나 다르면 거절한다(상태 코드는 명세가 짓는다). 다른 사이트의 페이지가 사용자의 브라우저로 보낸 폼 POST가 고지를 보이지 않은 채 확인을 만들지 못하게 하기 위해서다. `SameSite=Strict`는 쿠키를 보내는 요청을 막을 뿐 쿠키를 받는 요청은 막지 않는다(RFC 6265bis의 저장 규칙을 읽었다. 브라우저로 재지 않았다). 이미 꼴이 맞는 쿠키가 실려 있으면 새로 만들지 않고 그 값의 만료만 다시 적는다. 그래야 요청 하나로 식별자가 바뀌어 위젯이 대화를 지우는 일이 없다. 토큰을 낼 때마다 만료를 30일 뒤로 다시 적어, 마지막 질문 뒤 30일이 지나야 새 식별자가 된다. 대화 도중 식별자가 바뀌어 위젯이 대화를 지우는 일(위젯은 발급자나 `sub`가 바뀌면 저장을 지운다, ADR 0024)이 없게 하기 위해서다. 값이 UUID 꼴이 아니면 없는 것으로 보아 확인부터 다시 받는다. `Secure`는 설정의 공개 출처가 https일 때만 붙인다. 운영(TLS를 끝내는 프록시 뒤, https 출처)에서는 늘 붙고, e2e의 `http://*.localhost`에서는 붙지 않아 브라우저가 평문 출처의 `Secure` 쿠키를 받는지에 기대지 않는다. 쿠키 경로가 사이트마다 다르므로 같은 브라우저도 사이트에 따라 다른 익명 주체가 되고, 고지 글이 사이트마다 다를 때 그 글을 확인한 뒤에만 그 사이트의 쿠키를 받는다. 대가로 사이트를 옮길 때마다 확인을 한 번씩 더 한다. 확인 전에는 쿠키도 토큰도 내지 않는다.
- **토큰.** RS256이고 헤더에 `kid`를 싣는다. `iss`는 그 사이트의 발급자, `sub`는 `anon-<UUID>`, `aud`는 사이트 파일의 그 사이트 `audience`, `exp`는 `iat`+120초다. 주체는 `<발급자>|anon-<UUID>`가 되어 트레이스와 관리 화면에서 사람이 익명 주체를 바로 알아본다(관리 화면은 지금 `|`만으로 최종 사용자의 실행을 가른다, `RunDecision.tsx`). 뒤의 portal-login이 같은 발급자로 계정 id를 `sub`로 낼 때 `anon-` 접두를 금지하면 두 보증 모드의 주체가 글자로 겹치지 않는다. 위젯이 요청마다 새 토큰을 받으므로(EMBED.md) 토큰은 요청 직후에만 쓰이고, 120초면 느린 망에서도 넉넉하다고 어림하며(`serve`가 30초 여유를 더 본다, `http/sites.py`) 샌 토큰이나 보증 모드를 바꾼 뒤 남는 옛 토큰이 살아 있는 시간이 짧다. 질문 페이지 키 하나로 모든 사이트에 서명하고, 운영자는 그 공개 키와 `kid`를 사이트마다 `[[sites.public_keys]]`에 붙인다.
- **키 만들기 명령.** 질문 페이지 앱에 명령 하나(이름은 명세가 짓는다)를 두어 `node:crypto`로 RSA 2048 키 쌍을 만들고, 개인 키를 준 경로에 PEM으로 쓰며, 사이트 파일에 붙일 `[[sites.public_keys]]` 조각(`kid`와 `pem`)을 출력한다. 키 파일은 커밋하지 않는다. 선례는 위젯 e2e의 `token.ts`(같은 호출로 키를 만든다)다.
- **페이지.** 서버가 HTML 하나를 그리며 사이트 목록과 사이트마다의 공개 설정(이름, 제목, 소개, 테마, 밝음, 보증 모드, 고지 글, 보고서 링크)을 JSON 데이터 블록으로 싣는다. 페이지 스크립트는 인라인이 아니라 같은 출처의 파일이다. 스크립트는 고른 사이트의 상태 끝점에 물어, 확인 전이면 고지 전문과 "확인하고 질문하기" 단추가 위젯을 덮은 모양을 그리고, 단추를 누르면 확인 끝점을 불러 쿠키를 받고 덮개를 걷는다. 위젯은 페이지 안 방식이다. `<agent-os-widget>` 요소와 같은 출처의 `/widget/element.js`를 두고, 요소의 속성 다섯(`agent`, `heading`, `intro`, `theme`, `mode`)을 사이트 설정으로 채우며, `tokenProvider`는 그 사이트의 토큰 끝점을 부른다. 같은 출처라 쿠키가 저절로 실리고 postMessage 규약이 필요 없다. 짧은 고지는 위젯 곁에 늘 보인다. 사이트를 바꾸면 이동 없이 스크립트가 요소의 속성과 토큰 끝점을 바꿔 끼운다. 위젯 요소는 속성 다섯을 `observedAttributes`로 두고 바뀌면 다시 그리며 `agent`가 바뀌면 위젯 한 벌을 새로 띄운다(`web/apps/widget/element/WidgetElement.tsx`의 코드를 읽었다). 보증 모드가 로그인인 사이트의 페이지는 위젯 없이 "이 사이트는 로그인이 필요하고 로그인은 아직 제공하지 않는다"는 알림을 그리고, 둘 다인 사이트의 페이지는 익명 흐름 옆에 같은 알림이 붙은 비활성 로그인 단추를 둔다. 페이지의 CSP는 `default-src 'none'`에 `script-src`·`connect-src`·`style-src`·`font-src`·`img-src`를 `'self'`로 열고(위젯 e2e가 `style-src 'self'`로도 위젯이 칠해지는 것을 본다, EMBED.md CSP 절), `frame-ancestors 'none'`과 `base-uri 'none'`을 더한다. 둘은 `default-src`로 되돌아가지 않는 지시문이라 따로 적어야 하고(CSP3 명세를 읽었다. 브라우저로 재지 않았다), 질문 페이지는 프레임에 들어갈 까닭이 없다. 프록시에 기대지 않고 페이지가 제 응답에 싣는다. 사이트 파일에서 그 사이트의 허용 출처에 질문 페이지의 공개 출처를 적는다.
- **모양과 화면.** 질문 페이지의 모양은 디자인 시스템의 토큰 CSS와 글꼴 CSS를 질문 페이지가 같은 출처에서 내어 쓴다. 화면(셀렉트 박스, 짧은 고지, 덮개, 아직 없음 둘)은 명세 전에 `/ui-design pilot-portal`로 그려 `.scratch/pilot-portal/design/`에 둔다(web-widget 선례).
- **기록.** 질문 페이지의 로그에 쿠키 값과 토큰을 싣지 않는다(원칙 V의 연장).
- **함께 쓰는 코드.** 사이트 파일 읽기(위젯 빌드의 `tools/site-file.ts`)와 e2e 준비(위젯 e2e의 중계, 픽스처 플러그인, `serve` 띄우기)를 워크스페이스 패키지로 옮기고, 위젯 빌드와 위젯 e2e가 그것을 쓰게 고친다. 패키지의 이름과 수는 명세가 짓고, e2e 준비는 테스트 전용 devDependency다. 중계는 상류를 셋(`serve`, 위젯 Next, 질문 페이지)으로 받게 넓힌다. 앱 사이 import는 ESLint 경계가 막지만 워크스페이스 패키지는 허용된다(`web/eslint.config.mjs`). 관리 화면 e2e의 사본은 그대로 둔다(이 기능의 범위 밖).
- **빈도 제한.** 질문 페이지는 토큰 끝점에 빈도 제한을 두지 않는다. 토큰은 서명 한 번이고 그 CPU 비용은 작다고 어림하며(재지 않았다), 실행의 비용은 `serve`의 주체별·사이트별 상한(`channel/http/limits.py`)이, 요청 폭주는 프록시의 접속 주소별 빈도 제한(public-demo 계획)이 막는다.
- **테스트.** Vitest가 설정 읽기와 사이트 파일 대조, 토큰 서명과 클레임, 쿠키 판정(확인 끝점의 `Origin` 세 갈래인 없음·다른 출처·같은 출처와 기존 쿠키 보존을 포함), 페이지 데이터, 페이지 응답의 CSP 헤더를 본다. Playwright e2e가 `serve`, 위젯 Next, 질문 페이지, 중계를 띄우고 익명·로그인·둘 다 사이트를 두어, 확인 뒤 질문해 답을 받는 것, 확인 전의 401과 위젯의 "로그인 정보를 받지 못했습니다." 알림, 다른 출처 페이지의 폼 POST 뒤에도 상태 끝점이 미확인으로 답하는 것, 사이트 바꾸기, 로그인 사이트의 알림과 둘 다 사이트의 비활성 로그인 단추(아직 없음 화면 둘), 사이트별 시간당 실행 수 상한을 1로 둔 둘째 질문의 거부를 본다. 실제 모델 e2e 하나가 calc에 질문한다. 마커는 명세가 정하고 새 마커면 `pyproject.toml`과 `tests.md`를 고친다. 기능 계획의 수락 셋을 덮는다.

## Considered Options

- **Next 앱으로 둔다(관리 화면·위젯과 같은 스택).** 거부했다. ESLint가 Next 서버 파일과 Server Actions를 막아(ADR 0019) 개인 키로 서명하는 코드를 둘 자리가 없고, 토큰 끝점만 다른 프로세스로 빼면 프로세스가 둘이 된다. ADR 0024는 위젯에서 "Next 없음"을 고르지 않았지만 거부하지도 않았다.
- **빌드해서 `dist`를 돌린다.** 디자인 시스템 패키지의 내보내는 빌드(`tsconfig.build.json`)가 선례다. 거부했다. 두 Next 앱의 시작 래퍼가 이미 node로 `.ts`를 바로 돌리고, 빌드 단계와 산출물 폴더가 하나 늘며 무시 규칙과 린트 범위를 다시 정해야 한다.
- **사이트 파일을 읽지 않고 설정에 발급자·대상·에이전트를 다시 적는다.** 거부했다. 같은 값이 두 파일에 있어 어긋나도 시작 때 알 수 없고, 어긋남은 첫 토큰이 열 에이전트 밖의 404(`channel/http/end_user.py`의 고정 문구)나 서명 검증 실패로 거절될 때 드러난다.
- **사이트마다 제 페이지를 두고 셀렉트 박스는 이동이다.** 설계 인터뷰의 추천이었다. 서버가 쿠키 유무로 덮개를 그려 클라이언트 스크립트가 얇다. 사용자가 "페이지 하나에서 클라이언트가 위젯을 바꿔 끼운다"를 골랐다. 대가로 덮개와 확인 여부를 서버가 아니라 스크립트가 사이트마다 상태 끝점에 물어 그린다. 라운드 1의 "서버가 쿠키 유무로 페이지를 두 모양으로 그린다"는 이것으로 바뀌었다.
- **발급자는 질문 페이지의 공개 출처 하나이고 사이트 파일의 허용 출처도 그 하나다.** 설계 인터뷰 라운드 1의 답이었다. 사이트가 여럿이 되면서(라운드 3) 발급자는 사이트 파일의 그 사이트 발급자가 되고, 허용 출처는 "질문 페이지의 공개 출처가 그 사이트의 허용 출처에 든다"는 시작 검사가 됐다. 같은 라운드가 바꾼 라운드 1의 답은 이 둘과 설정 파일 하나의 안(파일은 하나이되 사이트 여럿의 목록이 됐다), 에이전트 하나(사이트마다 하나가 됐다)다.
- **식별자 쿠키와 고지 확인을 질문 페이지 전체에 하나로 둔다.** 거부했다. 고지 글이 사이트마다 다를 때 다른 글을 확인한 브라우저가 그 사이트에 들어가고, 같은 브라우저가 모든 사이트에서 같은 익명 주체가 된다.
- **식별자를 저장하지 않고 토큰마다 새로 낸다.** 거부했다. 위젯이 발급자나 `sub`가 바뀌면 저장을 지워 질문마다 대화가 끊긴다.
- **`sub`를 UUID만으로 낸다.** 거부했다. 트레이스와 관리 화면에서 익명 주체를 알아볼 표지가 없고, portal-login의 계정 id와 글자로 겹칠 수 있다.
- **토큰 수명을 서버가 받는 최대(600초)로 둔다.** 거부했다. 위젯이 요청마다 받으므로 긴 수명은 이득이 없고 샌 토큰이 사는 시간만 는다.
- **`Secure`를 늘 붙인다.** 거부했다. 평문 출처(e2e의 `http://*.localhost`)에서 브라우저가 `Secure` 쿠키를 받는지 재지 않았다. 공개 출처가 https일 때만 붙이면 운영에서는 늘 붙고 e2e는 그 물음에 기대지 않는다.
- **로그인·둘 다 모드를 이번에는 구성 오류로 거절한다.** 거부했다. 미리보기에서 사이트의 보증 모드가 보이지 않고, portal-login이 설정의 모양을 다시 바꾸게 된다. 받되 "아직 없음"을 보이고 로그인 사이트의 토큰 끝점은 늘 거절한다.
- **질문 페이지에 자체 빈도 제한을 둔다.** 거부했다. 무상태가 깨지고, 프록시가 접속 주소별로 이미 막는다. 질문 페이지만 프록시 없이 두는 배치는 이 기능의 범위 밖이다.
- **e2e 준비 코드를 질문 페이지에도 사본으로 둔다.** 거부했다. 관리 화면 `e2e/stack.ts` 354줄과 위젯 `e2e/stack.ts` 329줄(중계 85줄, 픽스처 플러그인 138줄, 토큰 45줄이 더 있다. `wc -l`로 손으로 봤다)에 셋째 사본이 더해진다. 워크스페이스 패키지로 빼 위젯 e2e와 함께 쓴다.
- **위젯 관리 화면과 레이아웃·아이콘 같은 새 모양 칸을 이번에 넣는다.** 넣지 않는다. 설정을 화면에서 고치는 관리 화면은 사이트 쪽에 둔다는 ADR 0047의 자리에 맞게 새 기능 행으로 세우고, 새 모양 칸은 위젯의 임베드 속성과 함께 넓혀야 해서 다른 행이다. 둘의 이름과 자리는 아래 Consequences에 있다.

## Consequences

- **다른 ADR.** ADR 0047의 "떼어 낼 때 끊을 연결" 두 문장에 포인터를 단다. 사이트 파일 읽기의 자리가 위젯 빌드의 `tools/site-file.ts`에서 워크스페이스 패키지로 옮겨 가고, 루프백 목록이 셋에서 넷이 된다. ADR 0024의 nginx가 넘기는 경로 문장(위젯 경로와 최종 사용자 접두사만 넘기고 나머지는 404)에 포인터를 단다. 질문 페이지를 함께 띄운 배치에서는 `= /`와 `/portal/`도 넘긴다.
- **위젯은 바뀌지 않는다.** 위젯은 여전히 쿠키를 쓰지 않는다(ADR 0024). 쿠키를 쓰는 것은 사이트 쪽인 질문 페이지다. 식별자 쿠키의 값은 비밀이 아니라 익명 주체의 이름 재료다. 새어도 그 익명 주체로 질문할 수 있을 뿐이고, 그것은 새 브라우저가 새 식별자를 받는 것과 다르지 않다. `SameSite=Strict`라 다른 사이트의 페이지에서 일으킨 요청에는 쿠키가 실리지 않는다. 쿠키를 받는 확인 끝점은 이것으로 보호되지 않아 결정 "익명 식별자 쿠키"의 `Origin` 검사가 맡는다. 고지 확인은 화면의 관문이지 접근 통제가 아니다. 쿠키를 직접 만들어 보내는 클라이언트는 고지 화면을 건너뛸 수 있고, 그렇게 받는 것은 새 브라우저가 받는 것과 같은 익명 주체다. 쿠키에 서명을 두지 않는 것은 결정 "앱과 서버"의 무상태와 키 하나를 지키기 위해서이고, 꼴 검사는 `sub`에 들어갈 값이 트레이스와 로그로 흘러드는 길을 막는 몫이다(PR 직전 리뷰가 서명을 물었다).
- **사이트를 바꾸면 새 대화다.** 셀렉트 박스로 사이트를 바꾸면 토큰의 발급자와 `sub`가 바뀌어 위젯이 저장한 대화를 지운다(ADR 0024). 미리보기의 쓰임이라 받아들인다.
- **전역 `fetch` 금지가 질문 페이지의 스크립트에도 걸린다.** `web/eslint.config.mjs`의 `no-restricted-globals`는 `files`를 두지 않은 블록이라 워크스페이스의 모든 파일에서 전역 `fetch`·`EventSource`·`XMLHttpRequest`를 막는다(코드를 읽었다). 질문 페이지의 스크립트가 부르는 것은 Agent OS의 API가 아니라 질문 페이지 자신의 끝점이라 생성 클라이언트의 대상이 아니다. 어떻게 풀지(그 파일 경로에 이유를 적은 예외, 또는 다른 길)는 명세가 정한다. 예외를 두면 `.claude/rules/web-workspace.md`대로 설정 파일에 경로와 이유를 함께 적는다. 같은 설정의 Next 서버 파일 금지도 파일 이름 글롭(`**/{route,middleware,proxy,instrumentation}.{ts,tsx,mts,cts,js,jsx,mjs,cjs}`)으로 모든 앱에 걸리므로, 질문 페이지의 파일 이름은 그 넷을 피한다.
- **상한.** 익명 주체는 쿠키를 지워 식별자를 새로 받으면 주체별 상한을 피할 수 있으므로 비용을 묶는 것은 사이트별 시간당 실행 수 상한이다(ADR 0046 이력 2026-11-06 "사이트의 의무"). 사이트가 여럿이면 그 상한이 사이트 수만큼 서므로, 배포 전체를 묶는 것은 사이트가 하나인 배치에서뿐이다(기능 계획이 이미 적었다). public-demo는 사이트 하나라 셀렉트 박스가 숨는다. `serve`의 CORS 허용 출처는 모든 사이트의 합집합 하나다(`http/sites.py`). 그래서 시작 검사의 "공개 출처가 그 사이트의 허용 출처에 든다"는 운영자의 설정 어긋남을 잡는 것이지 `serve`의 방어가 아니다. 사이트를 가르는 것은 토큰의 발급자다. 사이트 여럿은 `serve`의 사이트 파일이 처음부터 받던 것이고(ADR 0023), 사이트는 테넌트가 아니라(`CONTEXT.md`의 사이트 _Avoid_) PRD가 미룬 멀티테넌시는 이 설계가 건드리지 않는다.
- **CI.** 질문 페이지 e2e가 `serve`, 위젯 Next, 질문 페이지를 띄우므로 CI에 e2e 잡이 하나 늘고 Next 빌드를 한 번 더 한다(어림). 실제 모델 e2e의 마커가 새것이면 `pyproject.toml`의 `markers`(`--strict-markers`)와 `tests.md`를 고친다.
- **용어.** `CONTEXT.md`에 질문 페이지, 질문 페이지 설정, 보증 모드, 로그인 모드, 익명 주체, 익명 식별자, 고지, 고지 확인을 더하고, 사이트와 사이트 파일과 모드 항목을 손질한다. 디자인 시스템의 모드(라이트·다크)와 사이트의 보증 모드가 다른 말이 된다.
- **`tech.md`.** 웹 행에 질문 페이지의 스택(node:http, node가 `.ts`를 바로, 사이트 파일 읽기의 워크스페이스 패키지, 토큰 CSS와 글꼴 CSS)을 적고, 원격·CI 행의 프록시가 넘기는 것에 질문 페이지를 더한다.
- **다른 행.** portal-login 계획에서 익명 모드와 로그인 모드를 페이지의 설정으로 고르고 한 배포에서는 하나만 쓴다던 문장을, 보증 모드는 질문 페이지 설정이 사이트마다 고르고 한 배포에 익명 사이트와 로그인 사이트가 함께 설 수 있다는 문장으로 고친다. pilot-portal 계획에서 이 페이지를 사이트 하나로 등록한다던 문장을 담는 사이트마다 하나로 등록하는 것으로 고친다. 새 행 둘을 세운다. portal-admin(질문 페이지 설정을 화면에서 고치는 관리 화면. ADR 0047대로 사이트 쪽인 질문 페이지의 것이고 Agent OS 관리 화면이 아니다)과 widget-appearance(레이아웃·아이콘 같은 새 모양 칸을 위젯의 임베드 속성과 질문 페이지 설정에 더한다)다. 둘의 슬라이스는 10(제품 1.0 묶음. 0.1 판에는 들지 않는다)이고 Blocked by는 pilot-portal이다. 이 ADR의 승인 화면에서 사용자가 골랐고(일지 2026-11-09-1410), 두 행의 기능 계획이 원천이다. release-image는 질문 페이지 이미지에 소스와 `node_modules`를 그대로 담고, compose에서 TLS를 끝내는 프록시가 다른 컨테이너에 있을 때 루프백만 듣는 네 프로세스(`serve`, 관리 화면, 위젯, 질문 페이지)와 프록시를 잇는 방법은 그 행의 설계 인터뷰가 한꺼번에 정한다(release-image 계획에 적었다).
- **명세가 짓는 것.** 폴더 이름, 끝점 이름, 패키지의 이름과 수, 설정의 칸 이름, 키 만들기 명령의 이름, 마커 이름, 로그인 사이트의 토큰 끝점이 거절할 때의 상태 코드와 문구, 확인 끝점이 `Origin` 검사로 거절할 때의 상태 코드, 상태 끝점의 응답 모양, 전역 `fetch` 금지를 푸는 길. 설계 인터뷰의 답과 확인받은 요약은 일지 2026-11-09-1410에 글자 그대로 있다.
