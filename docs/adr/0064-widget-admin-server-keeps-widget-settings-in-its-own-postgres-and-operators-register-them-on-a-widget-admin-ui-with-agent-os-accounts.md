# 위젯 관리 서버가 위젯 설정을 자기 PostgreSQL에 들고, 운영자는 다른 포트의 위젯 관리 화면에 Agent OS의 운영자 계정으로 들어와 등록하며, 위젯은 허용 출처와 요청 글자 수 상한을 컨테이너가 뜰 때 받는다

ADR 0061은 사이트마다의 위젯 설정을 위젯 쪽의 서버가 데이터베이스에 들고 운영자가 화면에서 등록한다는 방향만 정하고, 그 서버를 어느 프로그램으로 세울지, 데이터베이스의 종류, 화면의 로그인, 맞춤 항목의 목록, 위젯이 위젯 설정을 받아 오는 주소, 백업과 배포를 '위젯 설정 관리' 행의 설계 인터뷰에 넘겼다(그 ADR의 결정 "이 ADR이 정하지 않는 것"). 그 행은 앞서 넷을 더 넘겨받았다. 위젯 미리보기 페이지 설정을 화면에서 고치는 일, 사이트 파일의 허용 출처와 요청 글자 수 상한을 화면에서 바꾸는 일, 로그인 방식을 화면에서 고르는 일, 위젯 컨테이너가 뜰 때 하는 빌드를 없애는 일이다(`.scratch/portal-admin/plan.md`). 설계 인터뷰(일지 2026-11-15-1312)가 그것을 일곱 라운드로 정했고, 사용자는 여러 자리에서 추천과 다른 답을 골랐다. 서버는 FastAPI로, 데이터베이스는 위젯 쪽의 PostgreSQL 컨테이너로, 화면의 주소는 포트를 하나 더 열어, 값을 옮기는 길은 짓지 않고, 고지의 고정 문장은 화면이 처음 값으로만 채운다는 것이다. **위젯 쪽에 위젯 관리 서버와 위젯 관리 화면을 새로 짓는다. 위젯 관리 서버는 FastAPI로 지은 이 저장소의 둘째 파이썬 패키지이고, Agent OS의 코드를 가져다 쓰지 않으며, 위젯 설정과 위젯 미리보기 페이지 설정을 자기 PostgreSQL 컨테이너에 든다. 위젯 관리 화면은 새 Next 앱이고 관리 화면과 포트만 다른 주소에 서며, 운영자는 Agent OS의 운영자 계정으로 로그인한 그대로 들어온다. 위젯 미리보기 페이지의 서버는 그대로 두고 그 페이지가 담는 사이트의 목록과 보증 모드와 보고서 링크만 위젯 관리 서버에서 받아 온다. 위젯은 사이트 파일의 허용 출처와 요청 글자 수 상한을 빌드에 굳히지 않고 컨테이너가 뜰 때 받는다.** Agent OS의 계약(`sdk`, `openapi.json`, 사이트 파일의 형식, 사이트 토큰의 주장)은 바뀌지 않는다. 일은 행 다섯으로 나뉘고 넷이 0.1 판의 조건이다.

이 ADR의 "위젯 관리 화면"은 ADR 0061과 그 뒤의 계획이 "위젯 설정 관리 화면"이라고 적은 것이고, "위젯 관리 서버"는 "위젯 쪽 서버"라고 적은 것이다. 인터뷰에서는 "관리자 페이지", "프론트", "백엔드"라고 불렀다. 용어집의 이름은 이 인터뷰에서 정했다(결정 "이름"). 인터뷰의 답과 확인받은 합의 요약은 일지 2026-11-15-1312에 글자 그대로 있다.

## 결정

- **위젯 관리 서버.** 위젯 설정을 저장하고 내주는 서버를 FastAPI로 짓는다. 이 저장소의 `agent_os` 옆에 서는 둘째 파이썬 패키지이고, 자기 명령으로 따로 뜨는 프로그램이다. `agent_os`를 import하지 않고 `agent_os`도 이 패키지를 import하지 않으며, Agent OS와는 HTTP로만 말한다(로그인 확인도 HTTP다). 그 경계는 import-linter의 계약으로 판정한다. 계약 파일(openapi)과 거기서 만드는 화면용 클라이언트가 Agent OS의 것과 따로 하나 더 생긴다. 인터뷰는 처음에 Node 서버를 올렸고 사용자는 "미리보기 페이지 서버를 키워 하나로"를 골랐다가 "근데 프론트랑 백엔드가 따로 있어야 하는거 아닌가?"라고 되물었으며, 화면을 짓는 방식을 묻는 질문에 "추천대로 하는데 백엔드는 FastAPI로 하고 싶은데"라고 답했다. 자리를 묻는 질문에는 "이 저장소의 새 파이썬 패키지로 따로"를 골랐다. FastAPI, 입력값 검사(pydantic), 타입 검사(pyright), 테스트(pytest)는 이 저장소가 이미 쓰는 것이라(`docs/constitution/tech.md`를 읽었다) 새로 드는 의존성은 PostgreSQL 쪽뿐이고, 계약 파일에서 화면용 클라이언트를 만드는 방식도 이미 있다(`web/packages/api-client`). 대가는 띄우는 프로그램이 하나 늘고, 계약 파일과 생성 클라이언트가 한 벌 더 생기며, 위젯 쪽 코드가 Agent OS와 같은 판 리듬과 잠금 파일에 묶인다는 것이다. 반대 방향의 선례가 있다. ADR 0048은 문서 검색 서버를 이 저장소의 `src/` 아래에 두는 안을 거부했다. 그때는 무거운 의존성이 까닭이었고 이번에는 이미 쓰는 의존성이라는 점이 다르며, 위젯이 참조 클라이언트로 이 저장소에 남아 있는 것(ADR 0047)과 같은 배치다. 패키지와 명령의 이름, 계약 파일의 자리, 배포 묶음(휠)을 나눌지는 widget-admin-server의 명세가 정한다.
- **데이터베이스.** 위젯 관리 서버의 데이터베이스는 PostgreSQL이고 위젯 쪽의 컨테이너를 따로 띄운다. Agent OS의 PostgreSQL(ADR 0062)과 컨테이너도, 데이터베이스도, 접속 계정도 함께 쓰지 않는다. "데이터베이스는 서비스마다 따로 띄운다"(ADR 0048)를 그대로 따르고, 위젯을 나중에 떼어 낼 때 데이터베이스를 함께 옮기기 쉽다. 추천은 Node에 내장된 SQLite였고 사용자가 "PostgreSQL, 위젯 쪽 컨테이너를 따로"를 골랐다. 대가는 띄우는 프로그램과 백업할 대상이 하나씩 더 는다는 것이다. 드라이버, 표를 만들고 올리는 도구, 테스트와 CI가 데이터베이스를 띄우는 방법은 postgres-foundation의 ADR이 고르는 것을 그대로 쓴다. 사용자가 "Agent OS 쪽이 고르는 것을 그대로"를 골랐다. 제품 안의 도구가 한 벌이 되고 이 행이 따로 고를 것이 없으며, 대가는 위젯 관리 서버의 구현이 그 행의 설계가 끝날 때까지 기다린다는 것이다. `.scratch/postgres-foundation/plan.md`가 두 인터뷰 가운데 먼저 도는 쪽에 맡긴 셋은 이렇게 정해졌다. 종류와 도구는 맞춘다. 컨테이너는 따로 띄운다. 백업은 묶지 않고 데이터베이스마다 하되 방법은 Agent OS 쪽이 정한 것을 따른다(Consequences "운영"). 그 도구는 `agent_os` 밖의 패키지에서도 쓰이게 되므로, postgres-foundation의 설계가 그것을 함께 본다(Consequences "다른 행").
- **위젯 관리 화면.** 운영자가 쓰는 화면은 `web/` 워크스페이스의 새 Next 앱이다. 관리 화면과 위젯처럼 React로 짓고, 디자인 시스템 패키지의 부품과 관리 화면이 쓰는 방식(화면 부품의 층, 스토리 테스트, 사진 비교, 린트 규칙)을 그대로 쓴다. 화면은 요청을 위젯 관리 서버로 넘긴다. 사용자가 추천("화면은 새 Next 앱으로 따로")대로 하되 백엔드만 FastAPI로 바꿨다. 대가는 띄우는 프로그램이 하나 늘고, 앱끼리는 코드를 가져다 쓸 수 없어(`web/eslint.config.mjs`가 막는다. 읽었다) 관리 화면 앱의 부품은 다시 짓거나 공유 패키지로 옮겨야 하며, 검사(e2e, 사진 비교)의 대상 앱이 하나 늘어 CI가 길어진다는 것이다.
- **주소.** 위젯 관리 화면은 관리 화면과 같은 이름(호스트)의 다른 포트에 선다. 추천은 "관리 화면과 같은 포트의 다른 경로"였고 사용자가 "다른 포트를 하나 더"를 골랐다. 브라우저에서 출처가 갈려, 위젯 관리 화면의 스크립트는 Agent OS의 관리 기능을 부르지 못한다(Agent OS 서버는 `Sec-Fetch-Site`가 있으면 `same-origin`만 받는다, ADR 0062). 대가는 인터넷에 여는 포트와 방화벽 규칙과 배포 안내의 항목이 하나씩 늘고, 운영자가 주소 둘을 기억해야 한다는 것이다. 그 포트의 TLS는 관리 화면의 포트처럼 앞단의 프록시가 끝낸다. 운영자의 로그인 쿠키가 `https`와 자기 PC의 `localhost`에서만 저장되기 때문이다(ADR 0062 결정 "로그인 상태"). 포트의 번호와 운영자가 그 포트를 닫는 방법은 portal-admin의 명세가 관리 화면의 포트(ADR 0062 결정 "포트와 TLS")에 맞춰 정한다. Agent OS의 관리 화면에는 위젯 관리 화면으로 가는 링크를 두지 않는다. 관리 화면에 위젯 전용 기능을 두지 않는다는 ADR 0047의 결정 그대로이고, 주소는 배포 안내에 적는다.
- **로그인.** 운영자는 관리 화면에 로그인한 운영자 계정 그대로 위젯 관리 화면에 들어온다. 로그인은 한 번이고 로그인 화면도 관리 화면의 것 하나다. 사용자가 "Agent OS 관리 화면의 계정으로 함께"를 골랐다. 운영자 로그인 상태를 든 쿠키 둘은 포트를 가리지 않아 브라우저가 위젯 관리 화면의 포트에도 보낸다. ADR 0062가 쿠키 프로브(`.scratch/admin-login/probes/cookie_relay/README.md`, Chromium 153)로 든 것이다. 그 프로브에서 호스트가 같고 포트가 다른 서버로 가는 요청에 쿠키가 실렸고, 그 서버가 응답의 `Set-Cookie`로 같은 이름의 쿠키를 덮을 수 있었다(ADR 0062 결정 "요청 출처 검사"와 Consequences "한계". 이 세션은 그 프로브를 다시 돌리지 않았다). 위젯 관리 서버는 받은 쿠키를 Agent OS 서버의 "지금 누구인지" 경로에 그대로 전해 로그인이 유효한지와 계정 이름을 확인하고, 짧은 JWT의 수명(기본 5분, ADR 0062 결정 "유지 시간")이 끝나면 "갱신" 경로에 같은 방식으로 전해 이어 주며, 그때 Agent OS가 내는 새 쿠키를 응답에 그대로 실어 브라우저에 되돌린다. 위젯 관리 서버가 Agent OS에 부르는 경로는 그 둘뿐이다. 계정과 비밀번호를 저장하지 않고, 쿠키를 저장하거나 기록하지 않는다. Agent OS는 갱신용 번호를 쓸 때마다 바꾸고 이미 바꾼 옛 번호가 다시 오면 그 로그인을 끊으므로(ADR 0062 결정 "로그인 상태"), 관리 화면의 탭과 위젯 관리 화면의 탭이 동시에 갱신하는 경우는 그 ADR이 명세에 넘긴 "탭 둘이 동시에 갱신할 때의 짧은 유예"와 같은 경우로 다룬다. 위젯 쪽이 Agent OS에 기대는 방향이라 ADR 0047과 맞고, Agent OS의 계약에 더하는 것이 없다(두 경로는 admin-login이 들이는 것이다). 대가는 넷이다. 이 화면의 로그인이 admin-login 뒤에야 완성되어 0.1 판까지의 순서가 묶인다. Agent OS 서버가 내려가 있으면 이 화면에 들어올 수 없다. 두 화면이 같은 이름에 있어야 쿠키가 함께 쓰인다. 그리고 위젯 관리 서버가 운영자의 로그인 쿠키를 받는 프로그램이 된다(Consequences "신뢰와 노출"). 쿠키가 다른 포트에 실리고 그 포트의 서버가 쿠키를 덮을 수 있다는 것은 위 프로브가 본 것이지만, 위젯 관리 서버가 그 쿠키를 Agent OS의 두 경로에 전해 로그인을 이어 주는 흐름 전체는 돌려 보지 않았다(어림). portal-admin의 명세가 먼저 확인한다.
- **고칠 수 있는 계정.** 로그인한 운영자 계정은 모두 위젯 설정과 위젯 미리보기 페이지 설정을 고친다. 0.1 판의 계정은 시스템 관리자와 관리자 두 단계뿐이고 관리자는 Agent OS에서도 계정 관리만 빼고 모든 일을 한다(ADR 0062 결정 "두 단계와 권한 표"). 위젯 관리 서버는 로그인이 유효한지와 계정 이름만 확인하면 되어 Agent OS의 단계 이름을 몰라도 된다. 사용자가 "로그인한 운영자 계정 모두"를 골랐다. 대가는 0.1 판 뒤에 역할 기능(admin-roles)이 생겨 보기만 하는 계정이 만들어지면, 그 계정이 위젯 설정을 고치지 못하게 그때 권한을 더해야 한다는 것이다. 그 일을 admin-roles의 기능 계획에 적는다.
- **주소의 검사.** 위젯 설정의 로그인 주소와 로그아웃 주소는 형식만 검사한다. `https://`로 시작하는 완전한 주소만 받고, 자기 PC에서 시험할 때 쓰는 `http://localhost` 주소는 받는다. `javascript:`처럼 주소가 아닌 값을 넣어 위젯이 든 페이지에서 스크립트를 돌리는 길을 막는다(그런 값이 스크립트로 도는 것은 브라우저의 일반 동작으로 아는 것이고 재 보지 않았다). 저장할 때 위젯 관리 서버가 검사하고, 위젯도 그 주소를 열거나 부르기 전에 한 번 더 본다. 어느 도메인의 주소인지는 가리지 않아 로그인 서버를 다른 도메인에 둔 사이트도 그대로 등록한다. 사용자가 "주소의 형식만 검사"를 골랐다. 대가는 위젯 관리 화면에 들어온 사람이 엉뚱한 도메인의 주소를 등록하는 것까지는 막지 못한다는 것이고, 그것을 막는 것은 그 화면의 로그인뿐이다.
- **0.1 판에서 등록하는 것.** ADR 0061 결정 "0.1 판에서 등록하는 것"의 목록에 다섯을 더한다. 글은 로그인 단추의 문구와 URL 방식 창의 탭 제목과 문의 링크이고, 새 화면 요소는 첫 화면의 예시 질문(누르면 그 질문이 보내지는 단추들)이며, 고르는 값은 밝기 스위치 숨기기다. 추천은 "더 넣지 않기"였고 사용자가 "예시 질문과 문의 링크까지"를 골랐다. 대가는 지금 위젯에 없는 화면 요소 둘(예시 질문, 문의 링크)을 새로 지어야 하고, 나란히 그리고 있는 위젯 화면(widget-login-state의 화면 그리기)에도 더해야 한다는 것이다. 그림 올리기와 자유 색은 ADR 0061이 정한 대로 widget-appearance가 0.1 판 뒤에 맡는다.
- **밝기 스위치 숨기기.** 위젯 설정에 밝기 스위치(다크 모드 스위치)를 숨기는 값을 둔다. 운영자가 켜면 그 사이트의 위젯에는 스위치가 나오지 않고, 위젯은 운영자가 정한 처음 밝기(정하지 않았으면 기기의 설정)로 고정된다. 사람이 전에 고른 값이 브라우저에 남아 있어도 그 사이트의 위젯은 그 값을 쓰지 않는다. 추천은 "두지 않기"였고 사용자가 "숨기는 설정 두기"를 골랐다. ADR 0061 결정 "다크 모드 스위치"의 "늘 사람이 고르기"가 "사이트가 숨기지 않는 한 사람이 고르기"로 바뀐다. 대가는 위젯이 지어서 시험할 화면이 한 갈래 는다는 것이다.
- **위젯 미리보기 페이지 설정.** 위젯 미리보기 페이지가 담는 사이트의 목록, 사이트마다의 발급자와 보증 모드와 보고서 링크는 위젯 관리 서버가 데이터베이스에 들고 운영자가 위젯 관리 화면에서 고친다. 추천은 "0.1 판 뒤로"였고 사용자가 "모두 0.1 판에"를 골랐다. 위젯 미리보기 페이지의 서버(Node로 지은 것)는 방문자에게 페이지를 내고 사이트 토큰을 내주는 지금의 일을 그대로 하고, 그 값들만 위젯 관리 서버에서 받아 온다(지금은 시작할 때 설정 파일을 한 번 읽는다. `web/apps/portal/server/load.ts`를 읽었다). 사용자가 "그대로 두고 설정을 백엔드에서 받게"를 골랐다. 이미 지어 통과한 코드와 검사를 버리지 않는다. 대가는 위젯 쪽의 서버가 두 언어(파이썬의 위젯 관리 서버, Node의 위젯 미리보기 페이지 서버)로 남고, 위젯 미리보기 페이지가 위젯 관리 서버에 기대어 그 서버가 내려가 있으면 설정을 받지 못한다는 것이다. 화면에서 저장한 값은 아무것도 다시 띄우지 않아도 반영된다. 위젯 설정은 다음에 위젯을 열 때, 위젯 미리보기 페이지 설정은 다음에 그 페이지를 열 때다. 위젯 미리보기 페이지의 서버가 받아 온 값을 짧게 기억하기로 하면 그 시간만큼 늦는다(Consequences "재지 않은 것"). 그 페이지의 설정 파일에는 시작에 필요한 값(공개 주소, 서명 키의 경로와 키 식별자, 듣는 주소와 포트, 위젯 관리 서버의 주소)이 남고, portal-login이 지은 뒤에는 로그인 서버 항목도 portal-login-admin이 화면으로 옮길 때까지 그 파일에 남는다. 서명 키의 경로 같은 값은 화면에서 받지 않는다. 그 파일이 지금 사이트마다 드는 에이전트와 위젯의 모양과 고지 칸(`agent`, `heading`, `intro`, `theme`, `mode`, `notice`. `web/apps/portal/server/config.ts`를 읽었다)은 ADR 0061이 위젯 설정에 등록하게 한 값이고, 그 파일에서 빼는 일은 widget-login-state가 맡는다. 파일에 남겨 두면 그 페이지가 임베드 속성으로 넘기는 값이 위젯 설정보다 앞서(ADR 0061 결정 "위젯 설정") 화면에서 고쳐도 그 페이지의 위젯이 바뀌지 않기 때문이다. 그 페이지는 사이트의 이름 하나만 임베드 속성으로 넘기게 된다.
- **시작 검사가 가는 자리.** 위젯 미리보기 페이지의 서버는 지금 뜰 때 설정 파일과 사이트 파일을 대 보고 하나라도 어긋나면 뜨지 않는다(ADR 0050 결정 "시작 인자와 시작 검사"). 사이트의 목록이 실행 중에 바뀌는 값이 되면 그 검사는 뜰 때 한 번으로 설 수 없어 세 자리로 갈린다. 첫째, 저장할 때 위젯 관리 서버가 값의 모양과, 사이트의 이름과 발급자가 다른 사이트와 겹치지 않는지를 보고 어긋나면 저장을 거절한다. 발급자가 겹치면 익명 사이트의 토큰으로 로그인 사이트의 에이전트를 열 수 있다는 까닭은 ADR 0050이 적은 그대로다. 둘째, 위젯 미리보기 페이지의 서버가 사이트의 목록을 받아 올 때, 사이트 파일과 자기 키가 있어야 볼 수 있는 것을 사이트마다 본다. 발급자가 사이트 파일에 있는지, 그 페이지의 공개 출처가 그 사이트의 허용 출처에 드는지, 설정의 키 식별자로 사이트 파일에 든 공개 키가 자기 개인 키와 짝인지, 로그인이 필요한 사이트가 쓰는 로그인 서버 항목이 있는지(ADR 0059 결정 "로그인 서버 항목")다. 어긋난 사이트는 그 사이트만 닫는다. 목록에 내지 않고 토큰을 내주지 않으며 까닭을 로그에 남긴다. 다른 사이트는 그대로 선다. 운영자가 화면의 값을 고치면 그 사이트는 다시 열리고, 사이트 파일 쪽을 고쳤으면 지금처럼 다시 띄운 뒤에 열린다(ADR 0056 결정 "사이트 파일을 고치면"). 셋째, 뜰 때는 설정 파일에 남은 시작 값(개인 키 파일 등)을 보고, 그것이 어긋나면 지금처럼 뜨지 않는다. 에이전트는 위젯 설정의 값이 되므로 그것이 그 사이트의 열 에이전트에 드는지는 위젯 미리보기 페이지가 더는 보지 않고, `serve`가 요청을 받을 때 거절한다(ADR 0023). 위젯 관리 서버는 사이트 파일을 읽지 않는다. `agent_os`를 가져다 쓰지 않아 그 파일을 푸는 코드가 없고, 그 파일을 푸는 자리를 하나 더 늘리지 않으려는 것이다. 그래서 운영자가 사이트 파일에 없는 발급자를 등록하면 저장은 되고 그 사이트는 닫힌 채로 남으며, 위젯 관리 화면이 그것을 운영자에게 알리는 방법은 portal-admin의 명세가 정한다. 대가는 틀린 설정이 "뜨지 않는다"로 바로 드러나던 것이 "그 사이트만 닫힌다"로 바뀌어, 운영자가 화면의 알림이나 로그를 보아야 안다는 것이다. 이 항목은 설계 인터뷰에서 묻지 않았고 초안을 쓰며 정했다. 승인 화면에서 사이트 파일과 맞지 않는 사이트의 처리를 따로 물었고 사용자가 "그 사이트만 닫기"를 골랐다(아래 "승인 때 함께 확인받는 세부", 다른 선택지는 Considered Options).
- **"테스트" 메뉴와 공개 주소.** 위젯 관리 화면의 메뉴에 위젯 미리보기 페이지로 가는 항목을 두고, 메뉴에 보이는 글자는 "테스트"다. 용어집의 이름(위젯 미리보기 페이지)은 그대로다. 사용자가 "관리자 페이지의 메뉴에 미리보기 페이지가 메뉴로 들어가 있으면 좋겠어. … 실제 관리자가 테스트해볼 수 있는 페이지야."라고 했고, 그 화면이 "새로 짓는 위젯 쪽 화면"이라고 골랐으며, 메뉴 글자는 추천("미리보기")과 달리 "테스트"를 골랐다. 대가는 메뉴 글자와 문서의 이름이 다르고, 이 저장소의 문서에서 "테스트"가 자동 시험을 가리키는 말이기도 해서 섞일 수 있다는 것이다. 위젯 미리보기 페이지는 주소를 아는 사람이 여는 페이지로 그대로 남고, 메뉴는 운영자가 그 페이지를 여는 또 하나의 입구다. 사용자가 "공개 주소도 남기기"를 골랐다. 공개 데모와 사내 로그인 두 계획이 그 페이지에 기대고 있어 그 둘이 바뀌지 않는다. 대가는 운영자가 시험하는 자리와 사람들이 실제로 쓰는 자리가 같은 페이지라, 저장하기 전의 설정을 운영자만 미리 볼 수는 없다는 것이다. 저장하면 곧바로 모두에게 보인다.
- **값을 옮기는 길은 짓지 않는다.** 지금 위젯 미리보기 페이지 설정 파일에 적힌 값을 데이터베이스로 옮기는 명령도, 서버가 처음 뜰 때 저절로 읽어 넣는 길도 짓지 않는다. 운영자가 위젯 관리 화면에서 새로 입력한다. 추천은 "파일을 읽어 넣는 명령 하나"였고 사용자가 "옮기지 않고 화면에서 새로 입력"을 골랐다. 0.1 판이 처음 내는 판이라 옮길 운영 데이터가 거의 없다. 대가는 시험과 예시 배포가 처음 값을 넣는 다른 길이 따로 필요하고, 지금 예시로 적어 둔 값을 손으로 다시 넣어야 한다는 것이다. 그래서 처음 배포한 직후의 데이터베이스는 비어 있다. 그때 위젯 미리보기 페이지는 등록된 사이트가 없다는 안내를 보이고, 운영자가 위젯 관리 화면에서 첫 사이트를 등록해야 위젯이 뜬다. 시험은 화면이 쓰는 저장 경로를 직접 불러 값을 넣고, 저장 경로가 아직 없는 widget-admin-server의 시험은 데이터베이스에 직접 넣는다.
- **고지의 고정 문장.** 위젯 미리보기 페이지가 사이트의 고지 글과 무관하게 고지 전문에 늘 넣던 문장 둘(익명 식별자를 둔다는 문장, 질문이 로그인한 계정과 함께 기록된다는 문장)은 늘 넣지 않는다. 위젯 관리 화면이 위젯 미리보기 페이지가 담는 사이트의 고지 전문에 그 문장을 처음 값으로 넣어 두고, 운영자가 자기 말로 다듬을 수 있다. 추천은 "미리보기 페이지가 위젯에 넘겨 붙이기"였고 사용자가 "화면이 처음 값으로 채워 주기"를 골랐다. 대가는 운영자가 지우면 쿠키를 두면서도 고지에서 그 사실이 빠진다는 것이다. 지금 코드는 익명 식별자 문장만 넣고(`web/apps/portal/server/notice.ts`의 `noticeText`를 읽었다), 계정 문장은 ADR 0059가 넣기로 정했을 뿐 아직 지어지지 않았다.
- **바꾼 기록.** 저장할 때마다 계정 이름, 시각, 사이트, 바뀐 항목의 이전 값과 새 값을 데이터베이스의 표에 한 줄씩 남긴다. 로그인 주소처럼 최종 사용자의 브라우저가 여는 값이 바뀌었을 때 누가 언제 바꿨는지 되짚을 수 있다. 0.1 판에는 그 기록을 보는 화면을 만들지 않는다(Agent OS의 로그인 기록과 같은 방식이다, ADR 0062). 위젯 설정에는 비밀을 두지 않으므로(ADR 0061) 값을 기록에 남겨도 된다. 사용자가 "바꿀 때마다 한 줄씩 남기기"를 골랐다. 대가는 표 하나와 저장할 때의 쓰기 하나가 늘고 기록이 계속 쌓인다는 것이다.
- **위젯 설정을 받아 가는 주소.** 위젯은 위젯을 내주는 공개 주소 아래의 정해진 경로에서 그 사이트의 위젯 설정을 받아 온다. 그 경로의 요청은 앞단의 프록시가 위젯 관리 서버로 넘긴다. 토큰도 로그인도 없이 누구나 읽고(ADR 0061 결정 "위젯 설정"), 페이지 안 방식의 위젯은 사이트의 출처에서 부르므로 다른 출처의 페이지가 읽을 수 있게 연다. 쿠키를 싣지 않는 읽기다. 저장하는 경로는 위젯 관리 화면의 포트에만 있고 공개 주소로는 닿지 않으며, 다른 사이트에서 온 요청을 Agent OS와 같은 규칙으로 거절한다(`Sec-Fetch-Site`가 있으면 `same-origin`만 받는다). 경로의 이름, 답의 모양과 판 표시, 등록되지 않은 사이트의 이름을 물었을 때의 답은 widget-admin-server의 명세가 정하고, widget-login-state가 그것을 따른다.
- **허용 출처와 요청 글자 수 상한.** 위젯은 사이트 파일의 두 값을 빌드에 굳히지 않는다. 위젯 이미지는 미리 지어 두고, 컨테이너가 뜰 때 사이트 파일을 읽어 두 가지만 한다. 위젯의 스크립트가 받아 갈 값 파일을 쓰고, 지어 둔 산출물에서 위젯 페이지를 품어도 되는 사이트를 알리는 응답 머리(`frame-ancestors`)의 값을 바꿔 넣는다. 사용자가 0.1 판의 범위로 "위젯이 실행 중에 받게만"을, 방법으로 "뜰 때 값만 바꿔 넣기"를 골랐다. 뜰 때의 빌드가 없어져 뜨는 시간과 메모리가 줄고(release-image의 명세는 위젯 컨테이너가 시작해 첫 응답을 내기까지 13.6~40.7초, 뜰 때의 빌드의 메모리 최고치로 1,452~1,567MiB를 적는다. `.scratch/release-image/spec.md`의 "이미지의 구성"을 읽었다), Next의 서버 파일을 금지하는 규칙(ADR 0019, ADR 0024)도 Agent OS의 계약도 고치지 않으며, 사이트 파일을 푸는 코드도 늘지 않는다(위젯 이미지에 이미 들어 있다). 대가는 둘이다. 사이트 파일을 고친 뒤에는 지금처럼 위젯을 다시 띄워야 한다. 그리고 Next가 지어 내는 파일의 모양에 기대므로 Next의 판을 올릴 때 깨질 수 있어 시험으로 지켜야 한다. 앞선 실험(`.scratch/release-image/probes/widget_runtime/README.md`를 읽었다)이 응답 머리를 바꿔 넣는 것과 값을 다시 쓰는 것을 따로따로는 보았지만, 이 조합을 리눅스 컨테이너에서 처음부터 끝까지 돌려 본 적은 없다(어림). 그래서 widget-runtime-values의 첫 일이 이것을 확인하는 것이고, 서지 않으면 이 결정으로 돌아와 사용자에게 다시 묻는다. 이 방법은 ADR 0056이 고르지 않은 안(Considered Options "지어 둔 파일의 자리표를 뜰 때 바꿔 넣는다")을 다시 연 것이다. 그 ADR은 페이지와 응답 머리까지 이 길로 내는 판을 돌려 보지 않았다고 적고 고르지 않았으며, 그 사정은 지금도 같다. 달라진 것은 사용자가 뜰 때의 빌드를 없애기로 고른 것이고, 그래서 돌려 보는 일을 구현의 첫 자리에 두었다. 두 값을 화면에서 고치는 일은 0.1 판에 넣지 않고 0.1 판 뒤의 새 행(site-limits-admin)이 설계부터 한다. 두 값은 Agent OS가 요청을 받아들일지를 가르는 채널의 신뢰 설정이라, 위젯 쪽의 화면이 고치면 ADR 0047의 경계와 어긋나기 때문이다. 대가는 0.1 판에서 두 값을 화면으로 바꾸지 못한다는 것이다.
- **배포에 느는 것.** 단독 compose에 컨테이너 셋이 는다. 위젯 관리 서버, 위젯 관리 화면, 위젯 쪽의 PostgreSQL이다. 앞의 둘은 이 저장소가 판마다 짓는 이미지이고 판 번호는 Agent OS와 같다. 그래서 판마다 짓고 올리는 이미지는 넷에서 여섯이 된다(ADR 0056 결정 "판마다 나오는 것"). 위젯 쪽의 PostgreSQL은 받아 쓰는 바깥 이미지다. 새 프로세스 둘도 다른 네 프로세스와 같은 규칙을 따른다. 루프백에만 묶이고, 이미지 안에서만 켜지는 명시적인 설정이 있을 때에만 컨테이너 네트워크의 주소에 묶인다(ADR 0056 결정 "루프백 규칙의 예외"). 프록시가 넘기는 경로에 위젯 설정을 받아 가는 경로 하나가 늘고, 프록시가 듣는 포트에 위젯 관리 화면용 하나가 는다. 이미지를 짓는 파일과 compose와 프록시 설정은 widget-admin-server와 portal-admin의 티켓이 release-image의 것 위에 더한다. 이 항목은 고른 것들에서 따라 나오는 것을 모아 적은 것이고 설계 인터뷰에서 따로 묻지 않았다(아래 "승인 때 함께 확인받는 세부").
- **회사 로그인 서버 항목.** 로그인 서버 항목(ADR 0059)을 화면에서 고치는 일은 0.1 판에 넣되, portal-login이 그 항목을 지은 뒤의 새 행(portal-login-admin)이 맡는다. 그 행은 설계 인터뷰를 따로 하고, 클라이언트 비밀 같은 비밀 값을 화면이 받을지는 그 인터뷰가 정한다. 추천은 "화면은 비밀 값을 받지 않기"였고 사용자가 "그 화면을 짓는 행의 설계에서 정하기"를 골랐다. 이 ADR은 그때까지 위젯 관리 서버의 데이터베이스에 비밀 값을 두지 않는다는 것까지만 정한다.
- **이름.** 용어집에 위젯 관리 화면과 위젯 관리 서버를 올린다. 사용자가 "위젯 관리 화면과 위젯 관리 서버"를 골랐다. 사용자가 쓴 말 "위젯 관리자 페이지"에 가깝고, 이 화면이 위젯 설정 말고도 위젯 미리보기 페이지 설정과 "테스트" 메뉴, 나중에는 로그인 서버 항목까지 담으므로 넓은 이름이 맞다. 대가는 `CONTEXT.md`의 관리 화면(Agent OS의 웹 앱)과 낱말 하나 차이라 줄여 쓰면 섞인다는 것이다. 그래서 "관리 화면"으로 줄여 쓰지 않는다고 용어집에 적었다.
- **기능 행.** 일을 행 다섯으로 나눈다. 사용자가 "저장과 읽기를 먼저 떼어 넷으로"를 골랐고, 0.1 판 뒤의 행 하나가 더 있다. widget-admin-server는 위젯 관리 서버의 뼈대와 데이터베이스와 위젯이 위젯 설정을 받아 가는 주소를 짓고 postgres-foundation을 기다린다. portal-admin은 위젯 관리 화면, 로그인 확인, 저장 경로, 바꾼 기록, 위젯 미리보기 페이지 설정을 데이터베이스로 옮기는 일을 맡고 widget-admin-server와 admin-login과 widget-login-state를 기다린다. widget-runtime-values는 위젯이 두 값을 뜰 때 받게 하고 release-image를 기다린다. portal-login-admin은 로그인 서버 항목을 화면에서 고치는 일을 설계부터 하고 portal-login과 portal-admin을 기다린다. site-limits-admin은 허용 출처와 요청 글자 수 상한을 화면에서 고치는 일을 설계부터 하고 0.1 판 뒤다. widget-login-state는 portal-admin이 아니라 widget-admin-server를 기다리게 바뀐다. 그 행과 그 뒤의 portal-login이 운영자 로그인(admin-login)과 나란히 갈 수 있다. 앞의 넷은 0.1 판의 조건이다. 대가는 행이 늘어 명세와 리뷰가 그만큼 늘고, widget-admin-server가 끝난 때에는 값을 넣을 화면이 아직 없어 시험이 데이터베이스에 값을 직접 넣어야 한다는 것이다.
- **승인 때 함께 확인받는 세부.** 합의 요약을 확인받은 화면에 없었고 이 초안을 쓰며 정한 것이 있다. 승인 화면에서 그 목록을 보이고 확인받았다. 사용자가 "이대로 확정"을 골랐고, 따로 물은 셋에는 PRD의 포트 문장에 "고치기"를, 사이트 파일과 맞지 않는 사이트의 처리에 "그 사이트만 닫기"를, deploy-package의 순서에 "묶기"를 골랐다(일지 2026-11-15-1312 "ADR 0064의 승인"). 설계의 빈 자리를 채운 것은 넷이다. 위젯 미리보기 페이지가 뜰 때 하던 검사를 세 자리로 가른 것(위 "시작 검사가 가는 자리"), 그 페이지의 설정 파일에서 빼는 칸에 에이전트를 더한 것(합의 요약은 이름, 소개, 색, 밝기, 고지 다섯을 적었다. 위 "위젯 미리보기 페이지 설정"), 위젯 관리 화면의 포트도 TLS를 앞단의 프록시가 끝내는 것(위 "주소"), 관리 화면과 위젯 관리 화면이 동시에 갱신하는 경우를 탭 둘의 경우로 다루는 것(위 "로그인")이다. 고른 것에서 따라 나오는 것을 적은 것은 다섯이다. 짓는 이미지가 여섯이 되고 새 프로세스 둘이 루프백 규칙을 따르는 것(위 "배포에 느는 것"), 위젯 관리 서버가 Agent OS에 부르는 경로를 둘로 고정하는 것(위 "로그인"), 위젯 설정을 받아 가는 경로를 다른 출처에 열고 저장 경로를 위젯 관리 화면의 포트에만 두는 것(위 "위젯 설정을 받아 가는 주소"), 백업을 묶지 않고 데이터베이스마다 하는 것(위 "데이터베이스"), 로그인한 운영자 계정이면 사이트의 보증 모드와 발급자도 바꿀 수 있다는 것(Consequences "신뢰와 노출")이다. 문서에 관한 것은 여섯이다. PRD의 성공 조건에서 밖으로 여는 포트를 적은 괄호 문장을 고치는 것(Consequences "PRD"), `docs/constitution/tech.md`에 문단을 더하고 헌법의 판을 올리는 것(Consequences "스택"), 새 행 넷의 이름과 슬라이스와 Blocked by(Consequences "다른 행"), release-image와 ops-backup-upgrade의 Blocked by에는 새 행을 더하지 않고 deploy-package의 Blocked by에 portal-admin을 더한 것(같은 항목), 용어집에서 위젯 미리보기 페이지 설정과 로그인 서버 항목의 뜻을 고친 것(Consequences "용어"), 앞선 ADR에는 이력을 쌓지 않고 포인터만 달며 이력은 ADR 0046 하나에 쌓은 것(Consequences "다른 ADR")이다. 합의 요약은 앞선 ADR들에 이력과 표시를 단다고 적었다. 뒤에 끝나는 행의 명세에 넘긴 것은 둘이고 둘 다 요약에 없었다. portal-login과 portal-admin 가운데 뒤에 끝나는 행의 명세가, 사이트가 쓰는 로그인 서버 항목의 이름을 두는 자리와, 위젯 미리보기 페이지가 담는 사이트의 로그인 주소와 로그아웃 주소를 운영자가 손으로 등록하는지를 정한다(Consequences "명세가 짓는 것").

## Considered Options

- **위젯 미리보기 페이지의 서버를 키워 하나로 한다.** 그 서버 하나가 데이터베이스와 화면과 위젯 설정을 내주는 주소까지 맡는 안이다. 사용자가 한 번 골랐다가 화면과 서버를 가르자고 되물은 뒤 FastAPI를 골라 바뀌었다. 그 서버의 뼈대(저장하는 것이 없고 요청의 본문을 읽지 않으며 읽기 전용으로 뜬다)를 고쳐야 했고, 위젯 미리보기 페이지를 쓰지 않는 배치도 위젯 설정을 쓰려면 그 서버를 띄워야 했다.
- **새 Node 서버를 따로 세운다, 또는 위젯 앱 안에 서버 코드를 허용한다.** 첫 라운드의 후보였다. 앞의 것은 Node에서 PostgreSQL을 쓰는 드라이버와 그 테스트를 `web/`에 새로 들여야 했고, 뒤의 것은 Next의 서버 파일을 금지하는 규칙을 고쳐야 했다(ADR 0024가 그 예외를 거부했다). Node의 드라이버 후보(`pg`, `postgres`)를 타입 검사와 린트에 대 본 서브에이전트의 보고가 일지에 있지만, 서버가 파이썬으로 정해져 쓰지 않았고 그 프로브는 커밋하지 않았다.
- **위젯 관리 서버를 Agent OS 서버 안의 경로로 둔다, 또는 다른 저장소에 둔다.** 앞의 것은 Agent OS가 위젯 설정을 모른다는 ADR 0047과 ADR 0061의 결정을 고쳐야 한다. 뒤의 것은 계약과 CI와 릴리스 절차가 저장소마다 한 벌씩 더 든다(ADR 0048이 문서 검색 서버에 치른 값이다).
- **Node에 내장된 SQLite를 쓴다, 또는 Agent OS의 PostgreSQL 컨테이너 안에 데이터베이스를 따로 만든다.** 앞의 것은 추천이었고 서버가 Node일 때의 안이다. 뒤의 것은 "데이터베이스는 서비스마다 따로 띄운다"(ADR 0048)에 예외를 적어야 한다.
- **위젯 쪽에 계정을 따로 둔다, 또는 배포할 때 정한 비밀번호 하나로 들어온다.** 로그인이 둘이 되거나, 누가 바꿨는지를 계정 이름으로 남길 수 없다.
- **위젯 관리 화면을 관리 화면과 같은 포트의 다른 경로에 둔다.** 추천이었다. 여는 포트가 늘지 않지만 두 화면이 같은 출처가 되어, 위젯 관리 화면의 스크립트가 Agent OS의 관리 기능을 부를 수 있다.
- **화면을 파일로 지어 위젯 관리 서버가 함께 낸다, 또는 서버가 HTML을 직접 그린다.** 띄우는 프로그램이 늘지 않지만 관리 화면과 위젯이 쓰는 방식(스토리 테스트, 사진 비교, 층 경계)을 그대로 쓰지 못한다.
- **시스템 관리자만 고친다, 또는 로그인 주소와 로그아웃 주소만 시스템 관리자가 고친다.** 위젯 관리 서버가 Agent OS의 계정 단계를 알아야 하고, 앞의 것은 그 한 사람이 없으면 위젯의 문구 하나도 고치지 못한다.
- **로그인 주소와 로그아웃 주소를 미리 적어 둔 도메인이나 사이트의 페이지와 같은 주소로만 받는다.** 엉뚱한 도메인을 막지만 배포 설정에 목록이 하나 더 들거나, 로그인 서버를 다른 도메인에 둔 사이트가 등록하지 못한다.
- **위젯 미리보기 페이지를 운영자만 보게 닫는다, 또는 운영자만 보는 시험 자리를 하나 더 짓는다.** 앞의 것은 공개 데모와 사내 로그인 두 계획을 바꾸고, 뒤의 것은 지을 화면이 하나 는다.
- **사이트 파일과 맞지 않는 사이트가 하나라도 있으면 위젯 미리보기 페이지가 어느 사이트도 열지 않는다, 또는 저장할 때 위젯 관리 서버가 사이트 파일을 읽어 거절한다.** 승인 화면의 다른 선택지였다. 앞의 것은 지금의 동작에 가까워 틀린 것이 바로 드러나지만, 화면에서 사이트 하나를 잘못 저장하면 다른 사이트의 위젯도 함께 멈춘다. 뒤의 것은 틀린 값이 들어가지 않지만 위젯 관리 서버에 사이트 파일을 푸는 코드를 하나 더 지어야 하고, 저장한 뒤에 운영자가 사이트 파일을 고쳐 어긋나는 경우는 막지 못해 그때의 처리가 따로 든다.
- **파일의 값을 읽어 넣는 명령을 짓는다, 또는 서버가 처음 뜰 때 저절로 읽어 넣는다.** 앞의 것은 추천이었다. 시험과 예시 배포가 같은 명령으로 처음 값을 넣을 수 있었다. 뒤의 것은 파일과 데이터베이스 가운데 무엇이 원천인지 헷갈리기 쉽다.
- **고지의 고정 문장을 위젯 미리보기 페이지가 위젯에 넘겨 늘 붙인다.** 추천이었다. 운영자가 지워도 문장이 빠지지 않지만, 위젯의 공개 표면에 사이트가 넘기는 고지 문장이 하나 더 든다.
- **바꾼 기록을 마지막으로 바꾼 사람과 시각만 남긴다, 또는 남기지 않는다.** 이전 값을 되짚을 수 없다.
- **위젯 앱에 서버 쪽 파일을 허용해 요청 때마다 사이트 파일을 읽는다.** 앞선 실험 판의 방식이고 사이트 파일을 고치면 다시 띄우지 않아도 페이지와 응답 머리가 따른다. 페이지 안 방식의 스크립트(`element.js`)는 띄울 때 한 번 지어 따라가지 않았다(`.scratch/release-image/probes/widget_runtime/README.md`의 4절을 읽었다. Windows PC 한 대에서 한 번 돌린 결과다). Next의 서버 파일을 금지하는 규칙을 고쳐야 하고 응답이 조금 느려진다.
- **Agent OS 서버가 두 값을 공개 경로로 내주고 응답 머리는 프록시가 붙인다.** ADR 0047이 위젯을 떼어 낼 때의 방법으로 적어 둔 길이다. Agent OS의 계약이 바뀌고, 프록시 없이 띄운 위젯은 머리가 없어 아무 사이트나 품을 수 있게 된다(지금은 값이 없으면 아무도 품지 못한다). 재 본 적이 없다(어림).
- **서버와 화면을 한 행에 둔다, 또는 한 행에 모두 둔다.** 명세가 줄지만 widget-login-state와 그 뒤의 portal-login이 운영자 로그인이 끝날 때까지 명세와 구현을 시작하지 못한다.
- **이름을 위젯 설정 관리 화면과 위젯 설정 서버로 올린다.** 고칠 문서가 적고 관리 화면과 덜 섞이지만, 이 화면이 위젯 설정만 다루는 것처럼 읽힌다.

## Consequences

- **신뢰와 노출.** 위젯 관리 서버는 운영자의 로그인 쿠키를 받는 둘째 프로그램이다. 쿠키가 포트를 가리지 않으므로, 같은 이름의 다른 포트에 선 프로그램은 운영자가 그 화면을 여는 것만으로 쿠키를 받는다. ADR 0062 Consequences "한계"가 방문자용 포트에 적은 것(그 포트의 서버가 운영자의 쿠키를 받고 같은 이름의 쿠키를 덮을 수 있다)이 이 포트에도 그대로이고, 이 ADR은 그 성질을 로그인을 함께 쓰는 길로 쓴다. 그 서버가 뚫리면 운영자의 로그인 상태가 드러나고, 서버와 서버 사이의 요청은 `Sec-Fetch-Site`가 없어 Agent OS가 받으므로(ADR 0062) 그 쿠키로 Agent OS의 관리 기능을 부를 수 있다. 그래서 위젯 관리 서버가 Agent OS에 부르는 경로를 둘로 고정하고 시험으로 지키며, 쿠키를 저장하거나 기록하지 않는다. 같은 운영자가 같은 서버에 띄우는 프로그램이라는 것이 이 노출을 받아들이는 근거다. 위젯 설정의 로그인 주소와 로그아웃 주소를 바꿀 수 있는 사람은 로그인한 운영자 계정 모두이고, 형식 검사는 엉뚱한 도메인을 막지 못한다(ADR 0061 Consequences "신뢰와 노출"이 넘긴 물음의 답이다). 로그인한 운영자 계정은 사이트의 보증 모드와 발급자도 바꿀 수 있다. 로그인이 필요하던 사이트를 익명으로 돌리면 로그인하지 않은 사람이 그 사이트의 에이전트에 질문할 수 있게 된다. 지금은 서버의 파일을 고칠 수 있는 사람만 하던 일이다. 그것을 막는 것은 위젯 관리 화면의 로그인이고, 되짚는 길은 바꾼 기록이다. 위젯 설정과 위젯 미리보기 페이지 설정에는 비밀을 두지 않는다. 위젯 설정은 누구나 읽는 주소로 나가기 때문이다.
- **운영.** 단독 배포에 컨테이너 셋(위젯 관리 서버, 위젯 관리 화면, 위젯 쪽의 PostgreSQL), 인터넷에 여는 포트 하나, 백업할 데이터베이스 하나가 는다. ADR 0056이 정한 다섯에 Agent OS 쪽의 PostgreSQL(postgres-foundation)과 이 셋을 더하면 아홉이다. 이 셈은 지금 계획대로일 때의 것이고 Agent OS 쪽의 배치는 postgres-foundation의 설계가 정한다(어림). 판마다 짓고 올리는 이미지는 넷에서 여섯이 된다(결정 "배포에 느는 것"). 그 컨테이너들을 단독 compose와 배포 파일 묶음에 더하는 일은 release-image의 명세를 고치지 않고 그 위에 더하며(postgres-foundation과 같은 방식이다), widget-admin-server와 portal-admin의 명세가 맡는다. 위젯 쪽 데이터베이스의 백업과 복원은 Agent OS 쪽 데이터베이스에 정해지는 방법을 따르고, 어느 행이 더하는지는 postgres-foundation의 설계가 Agent OS 쪽에 정한 것과 같게 한다. 위젯 관리 서버가 내려가 있으면 위젯은 위젯 설정을 받지 못하고(그때의 화면은 widget-login-state의 명세가 짓는다, ADR 0061) 위젯 미리보기 페이지는 사이트의 목록을 받지 못한다. 처음 배포한 직후에는 등록된 사이트가 없어, 운영자가 계정을 만들고 위젯 관리 화면에서 첫 사이트를 등록하기 전에는 위젯 미리보기 페이지에 위젯이 뜨지 않는다. 지금은 설정 파일의 예시만으로 뜬다.
- **순서.** 0.1 판까지의 길이 이렇게 묶인다. release-image 뒤에 postgres-foundation이 서고, 그 뒤에 admin-login과 widget-admin-server가 나란히 선다. widget-admin-server 뒤에 widget-login-state, portal-login, step-up-login이 차례로 서고, portal-admin은 admin-login과 widget-login-state가 모두 끝난 뒤에 선다. portal-login-admin은 portal-login과 portal-admin 뒤다. widget-runtime-values는 release-image만 기다린다. deploy-package는 portal-login에 더해 portal-admin을 직접 기다린다. 처음 배포한 직후에는 등록된 사이트가 없어, 그 행의 수락이 위젯 관리 화면에서 첫 사이트를 등록하는 단계를 지나기 때문이다.
- **재지 않은 것.** 아래는 어림이고 적힌 행이 확인한다. 운영자의 로그인 쿠키가 다른 포트에 실리는 것은 ADR 0062의 쿠키 프로브가 Chromium 153에서 본 것이고 다른 브라우저는 재지 않았다. 위젯 관리 서버가 그 쿠키를 "지금 누구인지"와 "갱신" 경로에 전해 로그인을 이어 주는 흐름(갱신 때 Agent OS가 내는 새 쿠키를 브라우저에 되돌려 주는 것, 탭 둘이 동시에 갱신하는 것까지)은 돌려 보지 않았고 portal-admin의 명세가 확인한다. 위젯 이미지를 미리 짓고 뜰 때 값만 바꿔 넣는 조합이 리눅스 컨테이너에서 서는지, 읽기 전용 디스크에서도 서는지는 widget-runtime-values의 첫 일이 확인한다. 위젯 미리보기 페이지의 서버가 요청 때 위젯 관리 서버에 물어도 응답이 느려지지 않는지, 그 값을 짧게 기억할지는 portal-admin의 명세가 본다. 확인해서 어긋나면 이 결정의 그 대목을 이력으로 다시 본다.
- **스택.** `docs/constitution/tech.md`에 위젯 관리 서버(둘째 파이썬 패키지, 데이터베이스는 PostgreSQL)와 위젯 관리 화면(새 Next 앱)을 적는다. 둘 다 구현 티켓이 들이기 전까지 저장소에 없다. 그 문서의 "파이썬 한 패키지를 유지하고 배포가 갈릴 때만 나눈다"는 그대로다. 위젯 관리 서버는 배포가 갈리는 경우다. 새 의존성은 이 ADR이 더하지 않는다. PostgreSQL의 드라이버와 표 관리 도구는 postgres-foundation의 ADR이 더한다.
- **PRD.** 기준선 성공 조건의 "(밖으로 여는 포트는 방문자용 하나와, 로그인으로 지키는 관리 화면용 하나다)"를 "(밖으로 여는 포트는 방문자용 하나와, 로그인으로 지키는 관리 화면용 하나와 위젯 관리 화면용 하나다)"로 고친다(ADR 0046 이력 2026-11-15 "위젯 설정 관리가 행 넷으로 나뉘고 셋이 기준선의 행으로 더해진다"). 전제의 "`serve` 한 프로세스와 PostgreSQL"은 Agent OS의 프로세스를 센 문장이라 그대로다.
- **다른 행.** 기능 계획을 고쳤다. 새 행 넷(widget-admin-server, widget-runtime-values, portal-login-admin은 슬라이스 9, site-limits-admin은 슬라이스 10)을 세우고 portal-admin을 다시 썼다. Blocked by는 결정 "기능 행"대로이고 site-limits-admin은 widget-runtime-values와 pilot-release를 기다린다. widget-login-state는 widget-admin-server를 기다리게 바꾸고 이 ADR이 그 행에 더한 일 넷을 적었다. pilot-release는 새 행 셋을 더 기다린다. postgres-foundation에는 두 인터뷰 가운데 먼저 도는 쪽에 맡겼던 셋의 답을, admin-login에는 "지금 누구인지"와 "갱신" 경로에 위젯 관리 서버가 기댄다는 것을, admin-roles에는 위젯 설정을 고치는 권한을, deploy-package와 ops-backup-upgrade에는 느는 컨테이너와 포트와 데이터베이스를, portal-login에는 로그인 서버 항목이 파일에 남는다는 것을, release-image에는 widget-runtime-values가 그 행 뒤에 온다는 것을 적었다. release-image의 명세 Out of Scope 한 항목과 티켓 08의 한 줄도 같은 까닭으로 고쳤다. 둘 다 portal-admin이 그 행보다 먼저 돌 수 있다는 전제를 적은 자리였다. ADR 0046 이력 2026-11-14가 이 인터뷰에 맡긴 물음(release-image와 ops-backup-upgrade가 portal-admin을 기다리는지, deploy-package가 직접 기다리는지)은 이렇게 정했다. release-image와 ops-backup-upgrade의 Blocked by에는 새 행을 더하지 않았다. 위젯 쪽의 컨테이너를 그 행들이 낸 것 위에 더하는 일은 widget-admin-server와 portal-admin의 명세가 맡는다. deploy-package의 Blocked by에는 portal-admin을 더했다. 그 행은 portal-login과 widget-login-state를 거쳐 portal-admin을 기다리고 있었는데 widget-login-state가 portal-admin을 기다리지 않게 되어 그 길이 끊겼고, 그 행의 수락은 위젯 관리 화면에서 첫 사이트를 등록하는 단계를 지난다. widget-runtime-values와 portal-login-admin은 deploy-package의 Blocked by에 없어 그 행이 먼저 돌 수 있다. 그러면 참조 배포의 메모리 문장과 로그인 서버 항목의 예시를 고치는 일은 그 두 행의 명세가 맡는다.
- **용어.** `CONTEXT.md`에 위젯 관리 화면과 위젯 관리 서버를 더했다. 위젯 미리보기 페이지 설정의 뜻을 고쳤다. 사이트마다 에이전트, 위젯의 모양, 보증 모드, 고지를 적은 파일이었고, 이 ADR로 그 페이지가 담는 사이트의 목록과 사이트마다의 발급자, 보증 모드, 보고서 링크를 정한 값이 된다(ADR 0061 Consequences "구현 티켓이 코드와 같은 티켓에서 고치는 문서"가 이 인터뷰 뒤로 미뤄 둔 일이다). 로그인 서버 항목의 뜻에서는 "위젯 미리보기 페이지 설정에 … 적은 것"이라는 자리를 뺐다. 그 항목을 두는 자리가 portal-login이 지을 때는 설정 파일이고 portal-login-admin이 화면으로 옮긴 뒤에는 달라지므로, 용어집이 자리를 적지 않게 했다. 코드는 구현 티켓이 따라온다.
- **다른 ADR.** 이 ADR이 본문의 문장을 바꾸는 ADR에 포인터를 단다. 달린 자리는 그 ADR마다 `(바뀜: ADR 0064)`로 찾는다. ADR 0061(다크 모드 스위치가 모든 위젯에 보이고 늘 사람이 고른다는 문장들, 0.1 판에서 등록하는 것의 목록, widget-login-state가 portal-admin을 기다린다는 문장들), ADR 0050(설정이 사이트 여럿의 목록이고 시작 때 두 파일을 대 보아 어긋나면 뜨지 않는다는 문장들, 설정 파일의 칸과 그 검사, 익명 식별자 문장을 고지 전문에 늘 넣는다는 문장, 바꾸면 다시 띄워야 한다는 문장, 페이지가 싣는 공개 설정과 임베드 속성, portal-admin 행의 자리), ADR 0059(없는 로그인 서버 항목을 가리키면 시작에서 구성 오류라는 문장, 계정 문장을 고지 전문에 늘 넣는다는 문장, 로그인 방식을 화면에서 고르는 일을 portal-admin이 맡는다는 문장), ADR 0056(이미지 넷과 컨테이너 다섯, 받을 바깥 이미지가 nginx 하나라는 문장, 루프백 규칙의 예외를 두는 네 곳, 호스트에 발행하는 포트, 프록시가 넘기는 경로, 위젯이 컨테이너가 뜰 때 빌드하고 빌드에 굳는다는 문장들, portal-admin 계획에 넘긴 요구), ADR 0047과 ADR 0024와 ADR 0023(허용 출처가 위젯 빌드의 입력이라는 문장들, 프록시가 넘기는 경로), ADR 0062(쿠키가 다른 포트에 실리는 한계가 방문자용 서버나 그 페이지가 뚫렸을 때의 일이라는 문장)다. 그 ADR들에는 이력을 쌓지 않는다. 다른 ADR의 본문 결정이 바꾼 문장에는 포인터만 단다는 규칙(`.claude/rules/adr.md`)과 ADR 0061 Consequences의 같은 이름 항목이 한 방식을 따랐다. 거부한 안의 근거 문장, 그때의 수를 적은 문장, 지난 이력 항목에는 달지 않는다. ADR 0056이 고르지 않은 안(지어 둔 파일의 자리표를 뜰 때 바꿔 넣는다)을 다시 연 것과 ADR 0048이 거부한 배치(다른 서버를 이 저장소의 `src/` 아래에 둔다)와 닮은 배치를 고른 것은 이 ADR의 결정에 적었다. ADR 0046에는 일이 행 넷으로 나뉘고 셋이 기준선의 행으로 더해진다는 이력을 쌓는다.
- **화면.** portal-admin은 명세 전에 `/ui-design portal-admin`으로 위젯 관리 화면을 그린다(사이트의 목록, 사이트 하나의 위젯 설정과 위젯 미리보기 페이지 설정, "테스트" 메뉴, 로그인하지 않았을 때의 화면). widget-login-state의 화면 그리기에는 첫 화면의 예시 질문, 문의 링크, 밝기 스위치를 숨긴 위젯이 더해진다.
- **명세가 짓는 것.** widget-admin-server의 명세는 패키지와 명령의 이름, import-linter 계약의 모양, 계약 파일의 자리와 생성 클라이언트, 표의 모양, 위젯 설정을 받아 가는 경로와 답의 모양과 판 표시, 등록되지 않은 사이트의 답, 다른 출처에 여는 응답 머리, 사이트의 이름의 꼴, 단독 compose에 더하는 컨테이너 둘을 짓는다. 그 명세는 셋을 더 적는다. 위젯 설정을 받아 가는 경로의 답이 위젯 설정의 항목만 싣는다는 것(같은 데이터베이스에 드는 위젯 미리보기 페이지 설정과 바꾼 기록, 나중에 들 수 있는 로그인 서버 항목이 그 경로로 나가지 않게 한다), 다른 출처에 여는 응답 머리를 그 읽는 경로에만 단다는 것, 누구나 읽는 그 경로의 요청 수를 제한할지다. portal-admin의 명세는 화면의 포트, 로그인하지 않았거나 로그인 시간이 끝났을 때의 화면, 쿠키를 전하는 흐름, 저장 경로와 입력값 검사, 바꾼 기록의 표, 위젯 미리보기 페이지의 서버가 설정을 받아 오는 경로와 때, 발급자가 사이트 파일에 없는 사이트를 등록했을 때의 알림, 고지 전문에 처음 값으로 넣는 문장을 어디서 얻는지, 사이트를 지우는 일, 단독 compose에 더하는 위젯 관리 화면의 컨테이너를 짓는다. 그 명세는 넷을 더 정한다. 첫째, 입력값 검사에서 로그인 주소와 로그아웃 주소의 사용자 정보 자리(`user:pw@`)와 쿼리에 든 값을 받을지다. 위젯 설정은 누구나 읽는 주소로 나가고 바꾼 기록에 이전 값과 새 값이 그대로 남으므로, 주소에 비밀이 실리면 위젯 설정에 비밀을 두지 않는다는 전제(결정 "바꾼 기록", 위 "신뢰와 노출")가 깨진다. 둘째, `http://localhost` 예외를 호스트 이름 전체로 견주는 시험이다. 앞 글자만 견주면 `http://localhost.example.test` 같은 주소가 지나간다. 셋째, 쿠키를 전하는 흐름에서 Agent OS가 낸 `Set-Cookie`를 속성을 바꾸지 않고 되돌리는지의 확인이다. 넷째, 운영자가 고지의 글을 고친 뒤 이미 고지를 확인한 브라우저에 다시 확인을 받을지다. 지금 확인은 사이트 단위로 남는다(ADR 0059 결정 "고지 확인"). widget-admin-server의 명세에 더한 셋과 이 넷, 그리고 아래에서 portal-login의 명세에 넘기는 계정 문장의 길은 PR 직전 리뷰가 낸 빈 자리이고 승인 뒤에 더했으며, 결정은 바꾸지 않는다(일지 2026-11-15-1312 "PR 직전 리뷰"). portal-login이 portal-admin보다 먼저 끝났으면 사이트가 자기가 쓰는 로그인 서버 항목의 이름을 가리키고 있으므로, 사이트의 목록을 데이터베이스로 옮길 때 그 이름을 두는 자리도 portal-admin의 명세가 정한다(portal-admin이 먼저 끝났으면 portal-login의 명세가 정한다). 같은 두 행 가운데 뒤에 끝나는 행의 명세가 하나를 더 정한다. 위젯 미리보기 페이지가 담는 사이트의 로그인 주소와 로그아웃 주소는 그 페이지의 끝점이라(ADR 0059), 운영자가 위젯 설정에 그 주소를 손으로 등록하는지 위젯 관리 화면이 처음 값으로 채워 주는지다. 옛 portal-admin 계획이 이 인터뷰에 넘긴 물음이고 인터뷰에서 다루지 않았다. portal-login이 portal-admin보다 먼저 끝나면 계정 문장을 고지 전문의 처음 값으로 넣어 줄 위젯 관리 화면이 아직 없으므로(결정 "고지의 고정 문장"), 그 동안 로그인 사이트의 고지 전문에 그 문장을 넣는 길은 portal-login의 명세가 정한다. widget-login-state의 명세는 위젯 미리보기 페이지 설정 파일에서 칸을 뺄 때의 `schema_version`을 정한다. widget-runtime-values의 명세는 값 파일의 자리와 모양, 응답 머리를 바꿔 넣는 방법, 지금처럼 합친 허용 출처와 가장 작은 상한을 쓸지, 위젯 이미지에서 덜어 낼 것(뜰 때의 빌드, 워크스페이스 전체 의존성, 읽기 전용이 아닌 루트), 위젯 상태 확인의 시작 유예, 배포 안내의 메모리 문장을 짓는다(`.scratch/release-image/spec.md`의 Out of Scope가 넘긴 것이다).
