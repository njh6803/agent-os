# 실패한 실행은 런타임이 정한 실패 원인을 들고 최종 사용자 항목에도 싣는다

실패한 실행의 기록은 지금 `run_failed`의 `error` 문자열 하나이고, 최종 사용자의 실패 항목은 고정 문구 하나와 실행 식별자다(ADR 0023). 그래서 위젯은 실패가 왜 났는지 모른다. 대화 요약이 거듭 실패하면 클라이언트는 새 대화를 시작해야 하는데(ADR 0022), 위젯은 요약 실패를 다른 실패와 가를 길이 없다. conversation과 end-user-channel 명세가 이 물음을 web-widget에 넘겼고, 그 물음을 가져간 end-user-continuation의 설계 인터뷰(일지 2026-10-15-07)에서 사용자가 골랐다. **`run_failed`에 실패 원인을 담는 선택 필드 하나가 는다. 값은 런타임이 실패가 생긴 자리로 정하는 닫힌 목록이고 실패의 모든 종류를 가른다(대화 요약, 시간 초과, 도구 서버 연결, 모델 호출, 루프 상한, 에이전트 코드 등이고, 자리를 모르는 실패는 그 밖이다. 정확한 목록은 명세가 정한다). 최종 사용자 실패 항목도 같은 값을 싣는다. 원인이 든 `run_failed`는 런타임만 낸다. 트레이스 형식은 3 그대로다. 최종 사용자에게 보일 문구는 위젯이 원인마다 정하고, 항목의 고정 문구는 그대로다.** 타입으로 가르는 이유는 위젯이 원인에 따라 안내(새 대화를 권할지 따위)를 고르고 운영자도 트레이스에서 실패를 가르게 하기 위해서다. 문구를 위젯에 두는 이유는 화면의 말을 바꿔도 계약이 바뀌지 않고, 원인 값을 모르는 위젯도 고정 문구로 내려갈 수 있기 때문이다.

## Considered Options

- **가르지 않는다.** 실패 항목과 이벤트는 그대로이고, 위젯은 어떤 실패에서든 "다시 시도"(마지막으로 끝난 실행을 다시 이어 감)와 "새 대화"를 함께 보인다. 계약과 sdk가 바뀌지 않는다. 사용자가 고르지 않았다.
- **투영이 `error` 문구의 머리를 보고 가른다.** core는 요약 실패의 메시지를 "대화 요약이 실패했다"로 시작한다(`core/run.py`의 `_summary_outcome`, 코드를 읽었다). sdk와 형식은 그대로다. 그러나 core의 문구와 채널이 문자열로 묶이고, 요약 도중의 시간 초과는 시간 초과 문구라 요약으로 갈리지 않는다. 거부했다.
- **요약 하나만, 또는 요약과 시간 초과 둘만 가른다.** 둘은 core에 따로 선 실패 자리가 있어 매기기 쉽고, 최종 사용자에게 드러나는 내부 사정이 적다. 사용자가 모든 종류를 골랐다. 대가는 `_drive`가 `except Exception` 하나로 받던 실패(도구 연결, 모델 호출, 루프 상한, 재생 대조, 에이전트 예외 등)를 자리로 다시 가르는 코드와, 최종 사용자 항목에 실리는 내부 구성의 단서(도구 서버가 있다는 것 따위)다.
- **트레이스 형식을 4로 올린다.** 옛 코드가 헤더에서 파일 전체를 거부한다. 그러나 형식 목록, 재개할 수 있는 형식(`RESUMABLE`), 지침이 함께 바뀌고, 새 이벤트 종류 없이 필드만으로 형식을 올리는 첫 선례가 된다. 옛 코드는 형식을 올리지 않아도 이 필드가 든 줄을 손상으로 거부한다(아래 Consequences). 거부했다.
- **에이전트가 낸 `run_failed`를 원인까지 그대로 통과시킨다.** 코드가 늘지 않는다. 그러나 플러그인이 요약 실패를 지어내면 위젯이 근거 없이 새 대화를 권한다. 거부했다.
- **서버가 원인마다 문구를 보낸다.** 위젯이 받은 문장을 그대로 보이면 되고 다른 클라이언트도 같은 말을 쓴다. 그러나 화면의 말을 서버가 들게 되어 문구를 바꿀 때마다 서버와 계약 설명이 바뀐다. 거부했다.

## Consequences

- **sdk의 이벤트가 바뀐다. 가산 변경이다.** `RunFailed`에 선택 필드 하나(기본 없음)가 는다. 이벤트는 관리 API의 응답 타입이라 `openapi.json`도 바뀐다(`.claude/rules/sdk.md`). 형식 1·2·3의 옛 줄은 원인 없음으로 그대로 읽힌다. 필드 이름과 값의 이름은 계약 티켓이 짓는다.
- **형식은 3 그대로다.** 아는 종류의 이벤트에 모르는 필드가 있으면 옛 코드는 검증 오류로 그 트레이스를 손상(`PluginError`)으로 거부한다. 모르는 종류의 줄만 `UnknownEvent`로 보존한다(`adapters/jsonl.py`의 `_read_event`, 코드를 읽었다). 그래서 반쯤 읽고 잘못 재개할 길이 없고, 실패한 실행은 애초에 재개와 이어 가기의 대상도 아니다. ADR 0022가 형식을 3으로 올린 이유(새 종류가 보존되어 반쯤 읽힌다)는 여기 걸리지 않고, ADR 0009의 2026-09-22 이력이 `LlmCalled`에 `prompt`를 더하며 형식을 그대로 둔 것과 같은 판단이다.
- **런타임이 쓰는 `run_failed`는 모두 원인을 든다.** 원인은 실패가 생긴 자리로 정한다. 요약 실패(`_summary_outcome`)와 시간 초과(`deadline_failure`)는 자리가 따로 있다. `_drive`가 한데 받던 예외는 core가 소유한 자리나 타입으로 가르고, 자리를 모르는 예외는 "그 밖"이다. 정확한 목록, 가르는 방법, 에이전트가 직접 부른 `ctx.llm()`·`ctx.tool()`의 실패를 어느 원인으로 볼지는 명세가 정한다. 요약 도중에 기한이 온 실패도 명세가 정한다. 지금 그 결말은 `deadline_failure`가 단계를 보지 않고 쓰는 시간 초과이지만, 같은 접기는 같은 기한에 거듭 걸리므로 위젯에는 다시 시도보다 새 대화가 맞을 수 있다. 몸통은 요약 단계인지 알므로 원인으로는 그것을 가를 수 있다 — 위에서 거부한 문구 머리의 안은 그러지 못했다.
- **원인이 든 `run_failed`는 런타임만 낸다.** 에이전트는 신뢰 경계 밖이다(`core/run.py`의 `_Body` 주석). 에이전트가 원인이 든 `run_failed`를 내면 그 실행은 런타임의 `run_failed`(원인은 에이전트 코드)로 끝난다. 에이전트가 `conversation_summarized`를 낼 수 없는 것과 같은 규칙이고(ADR 0022), `.claude/rules/core.md`의 런타임만 내는 이벤트 항목에 한 줄 는다. 원인 없는 `run_failed`를 에이전트가 내는 지금의 동작은 명세가 본다. 지금은 그것이 통과한 뒤 에이전트가 run_finished 없이 돌아오면 런타임이 `run_failed`를 하나 더 써서, 실패 항목이 둘이 된다(`core/run.py`의 `_drive`, 코드를 읽었다).
- **최종 사용자 실패 항목에 같은 값이 는다.** 고정 문구(`"실행이 실패로 끝났다"`)와 실행 식별자는 그대로다. 원인 값을 늘리는 것은 계약의 가산 변경이고 생성 타입(api-client)에 새 값이 실린다. 생성 타입과 대조하는 `satisfies` 검사는 이벤트 종류 목록만 보므로(`web/packages/api-client/src/stream.ts`, 코드를 읽었다) 원인 값을 가르는 소비자가 새 값을 다루는지는 그 소비자의 테스트가 본다. 위젯은 원인마다 문구를 정하고, 모르는 값이면 고정 문구를 보인다(web-widget).
- **운영자 채널 `/runs`와 관리 API는 원문 이벤트라 원인을 그대로 싣는다.** 관리 화면이 원인을 어떻게 그릴지는 명세가 정한다.
- **계약 티켓.** 이 필드와 항목은 end-user-continuation의 첫 계약 티켓이 함께 싣는다(`.scratch/plan.md`).
- **용어집.** 실패 원인이 늘었다.
