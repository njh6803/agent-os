# 질문 페이지의 로그인 모드는 설정에 이름 붙여 적은 로그인 서버의 OIDC로 사람을 확인하고, 로그인 상태를 서명된 쿠키에 두며 Agent OS의 계약은 바꾸지 않는다

ADR 0050은 질문 페이지 설정이 보증 모드 셋을 받게 하되 로그인 갈래는 "아직 없음"으로 두었다. 로그인 사이트의 끝점은 늘 거절하고 둘 다 사이트에는 눌리지 않는 로그인 단추가 있다. 기능 계획 portal-login이 그 갈래를 채운다. 배포 환경에서는 사내 사람만 질문해야 하기 때문이다(ADR 0046 이력 2026-11-06). 설계 인터뷰(일지 2026-11-12-1937)에서 사용자는 로그인 방식을 하나로 좁히는 질문에 두 방식을 모두 두는 길을 되물은 뒤 "0.1은 하나, 구조는 열어 두기"를 골랐고, 로그인의 범위에는 추천과 달리 "사이트마다 로그인 서버를 다르게 설정 가능"을 골랐으며, 유지 시간의 기준과 로그아웃 방식은 설정으로 고르게 하기를 골랐다. 같은 인터뷰가 질문 도중의 로그인 요구도 0.1 판에 넣기로 했고, 그 결정은 계약을 바꾸는 일이 모여 있어 ADR 0060이 따로 맡는다. **질문 페이지의 로그인 방식은 OIDC 하나다. 로그인 서버는 질문 페이지 설정에 이름 붙인 항목으로 적고 사이트가 그 이름을 가리키며, 같은 항목을 가리키는 사이트끼리는 로그인과 로그아웃을 함께 한다. 클라이언트는 `openid-client`이고 ID 토큰의 서명 검사를 켜며 로그인 서버의 주소는 `https`만 받는다. 로그인 서버를 통과한 모든 계정이 질문할 수 있고, 운영자가 고른 주장(기본 `sub`)의 값이 그 사람의 식별자로서 사이트 토큰의 `sub`가 된다. 로그인 상태는 서버에 두지 않고 브라우저의 서명된 쿠키에 두며, 유지 시간의 기준(기본은 로그인한 때부터 8시간)과 로그아웃 방식(기본은 질문 페이지에서만)은 운영자가 고른다. 이름과 소속 같은 계정 정보는 어디에도 보관하지 않는다. Agent OS가 받는 것은 지금처럼 질문 페이지가 서명한 사이트 토큰뿐이고, 이 결정으로는 `sdk`·`openapi.json`·사이트 파일의 형식·위젯의 공개 표면이 바뀌지 않는다.** OIDC를 고른 이유는 비밀번호를 로그인 서버만 다루고 질문 페이지는 보지 않기 때문이다. 로그인 상태를 쿠키에 두는 이유는 질문 페이지가 저장소 없이 도는 지금 구조(ADR 0050 결정 "앱과 서버")를 지키기 위해서이고, 그 대가는 한 사람만 골라 바로 로그아웃시킬 수 없다는 것이다. Agent OS의 계약을 그대로 두는 이유는 ADR 0023이 사이트가 서명한 토큰 하나로 신원을 받기로 하고 로그인 서버의 토큰을 직접 받는 안을 거부했기 때문이다. 로그인 서버가 낸 ID 토큰은 질문 페이지까지만 온다.

## 결정

- **로그인 방식.** OIDC의 인가 코드 흐름 하나이고 PKCE, `state`, `nonce`를 쓴다. 로그인 서버 항목에 방식의 이름을 적는 칸을 두어, 뒤에 다른 방식(LDAP)을 더할 때 설정의 모양을 바꾸지 않게 한다. 0.1 판이 받는 값은 OIDC 하나이고 다른 값은 시작에서 구성 오류다. 클라이언트는 `openid-client`다. 기본 호출은 ID 토큰의 서명을 보지 않으므로 서명 검사를 켜는 설정(`enableNonRepudiationChecks`)을 반드시 넣는다. `.scratch/portal-login/probes/oidc_client/probe/flow.mjs`로 쟀다(6.8.9를 프로브가 직접 지은 가짜 로그인 서버에 댔다. 서명이 틀린 ID 토큰을 기본 호출은 받아들였고 검사를 켠 호출은 거부했다. 그 밖의 고장 일곱인 발급자·대상·만료·`nonce` 다름과 없음·`alg` `none`과 `HS256`은 두 호출 모두 거부했다). 로그인 서버의 주소는 `https`만 받는다. 라이브러리가 `http` 발급자를 요청을 보내기 전에 거부하고(같은 `flow.mjs`의 `insecure` 묶음), 그것을 푸는 선택지 `allowInsecureRequests`는 `@deprecated`라 `@typescript-eslint/no-deprecated`에 걸린다(같은 폴더의 `probe/lint.mjs`가 `web/eslint.config.mjs`를 글자 그대로 옮긴 무대에서 본다). 판정자는 인라인 끄기 주석을 받지 않는다(`web/eslint.config.mjs`의 `noInlineConfig`를 읽었다). 결과의 원천은 `.scratch/portal-login/probes/README.md`다.
- **로그인 서버 항목.** 질문 페이지 설정에 로그인 서버를 이름 붙인 항목의 목록으로 적는다. 항목마다 방식, 로그인 서버의 주소(발급자), 클라이언트 식별자와 비밀, 식별자로 쓸 주장, 유지 시간의 기준과 길이, 로그아웃 방식을 든다. 보증 모드가 로그인이거나 둘 다인 사이트는 항목 하나의 이름을 가리키고, 가리키지 않거나 없는 이름을 가리키면 시작에서 구성 오류다(fail-closed, ADR 0050 결정 "시작 인자와 시작 검사"와 같은 방향). 익명 사이트는 가리키지 않는다. 같은 항목을 가리키는 사이트끼리는 한 번의 로그인으로 모두 로그인 상태가 되고 로그아웃도 함께 된다. 사이트를 고르는 셀렉트 박스로 사이트를 바꿔도 다시 로그인하지 않는다. 따로 로그인하게 하려면 주소가 같은 항목을 이름만 달리해 두 번 적는다. 함께 쓸지를 정하는 스위치는 따로 두지 않는다. 로그인 뒤 돌아오는 주소는 항목마다 하나이고, 운영자가 그 주소를 로그인 서버에 등록한다. 클라이언트 비밀 같은 비밀 값은 설정에 직접 적지 않고 파일 경로로 가리킨다(서명 개인 키와 같은 방식).
- **로그인할 수 있는 사람.** 로그인 서버가 인증한 계정이면 누구나 질문할 수 있고 질문 페이지는 더 가르지 않는다. 일부만 허용하려면 로그인 서버에서 이 클라이언트에 로그인할 수 있는 사람을 좁힌다(널리 쓰이는 로그인 서버 제품이 그 기능을 준다는 것은 어림이고 고객사의 제품에 대 보지 않았다).
- **식별자와 사이트 토큰.** 식별자는 운영자가 항목에 적은 주장의 값이고, 적지 않으면 `sub`다. 조직이 사번 같은 통용 식별자를 다른 주장으로 준다면 운영자가 그 이름을 적는다. 뒤의 기능이 주체가 조직의 사용자 식별자와 대응되기를 요구하기 때문이다(principal-propagation 기능 계획). 그 주장이 ID 토큰에 없으면 그 사람의 로그인을 거절한다. 식별자가 `anon-`으로 시작하면 로그인을 거절한다(ADR 0050 결정 "토큰"이 넘긴 요건. 익명 주체와 글자로 겹치지 않게 한다). 토큰 끝점은 로그인 상태인 브라우저에 `sub`가 그 식별자인 사이트 토큰을 그 사이트의 발급자로 서명해 낸다. 이 결정으로는 주장 다섯과 수명 120초가 그대로다(선택 주장 둘은 ADR 0060이 더한다). 주체는 `<발급자>|<식별자>`이고, 질문 페이지 설정이 사이트마다 발급자가 다르기를 강제하므로(`web/apps/portal/server/config.ts`의 `overlaps`를 읽었다) 같은 사람도 사이트가 다르면 다른 로그인 주체다. 운영 도중 식별자로 쓸 주장을 바꾸면 모든 사람이 새 주체가 되어 앞선 기록과 이어지지 않는다. 이름, 소속, 그룹은 사이트 토큰에 싣지 않는다. 계정 정보의 원본은 로그인 서버에 두고 질문 페이지와 Agent OS는 계정의 표를 만들지 않는다. 사람별 데이터는 뒤의 기능이 주체를 열쇠로 삼아 더한다(ADR 0054).
- **로그인 상태.** 로그인에 성공하면 질문 페이지가 식별자, 화면에 보일 이름, 끝나는 시각, 항목의 이름을 적은 값에 서명해 쿠키로 낸다. 서버는 아무것도 저장하지 않아 다시 띄워도 로그인이 풀리지 않는다. 쿠키는 `HttpOnly`이고 서명만 붙이며 암호화하지 않는다. 유지 시간의 기준은 항목마다 둘 가운데 하나다. 기본은 질문 페이지가 정한 길이(로그인한 때부터 8시간이고 값을 바꿀 수 있다)이고, 다른 하나는 ID 토큰의 만료 시각이다. 로그인 상태가 끝난 뒤에는 그 쿠키로 토큰을 내지 않는다. 로그인 도중의 값(`state`, `nonce`, PKCE 검증 값)도 서버에 두지 않고 로그인이 끝날 때까지만 사는 쿠키에 둔다.
- **로그인 흐름.** 로그인은 같은 탭이 로그인 서버로 갔다가 돌아오는 이동이다. 팝업을 쓰지 않는다. 로그인을 시작하는 끝점, 돌아오는 끝점, 로그아웃 끝점은 모두 `/portal/` 아래에 두어 프록시가 질문 페이지로 넘기는 규칙 둘(ADR 0050 결정 "경로")을 바꾸지 않는다. 여기서 정하는 것은 프록시 규칙을 늘리지 않는다는 것 하나이고, 끝점마다의 경로는 명세가 짓는다. 돌아온 요청의 검증이 실패하거나(남의 `state`, 로그인 서버의 오류 응답) 식별자를 얻지 못하면 로그인 상태를 만들지 않고 까닭을 화면에 알린다.
- **화면.** 로그인 사이트는 로그인 전에 위젯 대신 "로그인하고 질문하기" 단추를 보인다. 둘 다 사이트는 지금처럼 익명으로 바로 질문할 수 있고 같은 단추가 눌린다. 로그인한 뒤에는 로그인 서버가 준 이름(없으면 계정 이름, 그것도 없으면 "로그인됨")과 로그아웃 단추를 보인다. 어느 계정으로 기록되는지를 질문하는 사람이 눈으로 확인하게 하기 위해서다. 이름은 쿠키에만 있고 질문 페이지 서버와 Agent OS에 저장하지 않는다. 유지 시간이 끝나면 다음 질문을 보내려는 때 "로그인 시간이 끝났습니다"와 "다시 로그인" 단추를 보인다. 위젯이 질문마다 토큰을 새로 받으므로(`web/apps/widget/components/pages/drivers.ts`의 `authorize`를 읽었다) 그때 드러난다. 같은 사람으로 다시 로그인하면 위젯이 저장한 대화가 남는다(위젯은 토큰의 발급자와 `sub`가 같으면 저장을 지우지 않는다, ADR 0024). 둘 다 사이트에는 "로그인 없이 계속"을 함께 두고, 고르면 익명 주체의 새 대화다. 둘 다 사이트의 브라우저는 익명 식별자 쿠키를 함께 들 수 있지만, 로그인 상태가 끝났다고 질문 페이지가 익명 토큰을 말없이 내지 않는다. 사람이 "로그인 없이 계속"을 고른 뒤에만 익명 주체로 바뀐다. 사용자가 고른 설명의 조건이고, 말없이 바뀌면 위젯이 주체가 바뀐 것을 보고 대화를 지운다. 그러려면 질문 페이지가 끝난 로그인 상태와 없는 로그인 상태를 갈라야 하고, 그 방법은 명세가 짓는다. 만료를 알게 된 그 질문은 실행이 서기 전에 막힌 것이라 위젯이 저장하지 않으므로(`web/apps/widget/lib/storage.ts`의 머리 주석을 읽었다) 다시 로그인하고 돌아온 화면에 없고, 질문한 사람이 다시 적는다. 이 알림과 단추는 위젯이 아니라 질문 페이지가 그린다. 토큰을 내주는 함수가 페이지의 것이라 페이지가 만료를 먼저 알고, 문구는 사이트가 가진다(ADR 0047). 화면은 명세 전에 `/ui-design portal-login`으로 그린다.
- **로그아웃.** 방식은 항목마다 둘 가운데 하나다. 기본은 질문 페이지의 로그인 쿠키만 지우는 것이고 조직의 다른 프로그램은 영향을 받지 않는다. 다른 하나는 로그인 서버에서도 함께 로그아웃하는 것이고, 여럿이 쓰는 PC에서 다음 사람이 앞사람의 계정으로 로그인되는 일을 막는다. `openid-client`의 타입 선언에 로그인 서버의 로그아웃 주소를 짓는 `buildEndSessionUrl`이 있다(6.8.9의 `build/index.d.ts`를 읽었고 실행해 보지 않았다). 로그아웃하면 화면에서 대화가 사라진다. 둘 다 사이트는 익명으로 돌아가고, 그때 위젯이 주체가 바뀐 것을 보고 저장한 대화를 지운다(지금 위젯의 동작, ADR 0024). 익명 주체는 로그인 주체의 대화를 이어 갈 수 없다(지금 서버의 판정 그대로다).
- **고지 확인.** 로그인한 사람도 고지를 사이트마다 한 번 확인한다. 로그인하면 질문이 그 사람의 식별자와 함께 기록되기 때문이다. "질문이 로그인한 계정과 함께 기록된다"는 문장은 사이트가 고지 글을 적어도 질문 페이지가 고지 전문에 늘 넣는다(익명 식별자 쿠키의 문장과 같은 규칙, ADR 0050 결정 "시작 인자와 시작 검사"). 고지 확인의 기록은 지금처럼 그 브라우저가 든 그 사이트의 쿠키다(지금은 익명 식별자 쿠키가 있는지가 그 기록이다, `web/apps/portal/server/handler.ts`를 읽었다). 그래서 익명으로 확인한 브라우저는 로그인한 뒤 다시 확인하지 않고, 같은 사람도 다른 브라우저에서는 다시 확인한다. 로그인 상태는 고지 확인 전에도 생길 수 있지만(로그인은 항목 단위이고 확인은 사이트 단위다), 사이트 토큰은 로그인한 사람에게도 그 사이트의 고지를 확인한 뒤에만 낸다.
- **보증 모드를 바꿀 때.** 익명 사이트를 로그인 사이트로 바꾸면, 바꾸기 직전에 낸 익명 토큰으로 최대 약 2분 30초(토큰 수명 120초에 `serve`의 시계 여유 30초, `src/agent_os/http/sites.py`를 읽었다) 동안 더 질문할 수 있고 이미 열린 답 스트림은 끝까지 나온다. 이 공백을 받아들이고 코드는 바꾸지 않는다. 바로 막아야 하는 경우를 위해 배포 안내에 서명 키를 바꾸고 `serve`를 다시 띄우는 절차를 적는다.
- **그룹.** 제품 1.0의 문서 권한이 쓸 최종 사용자의 그룹은 로그인 서버에서 온다. 0.1 판은 이 방향만 잡고 그룹을 읽거나 싣지 않는다. 질문 페이지에서 Agent OS를 거쳐 도구 서버까지 넘기는 길은 principal-propagation과 문서 검색 서버 저장소의 문서 권한 설계가 정한다. 로그인한 뒤 바뀐 소속은 다시 로그인할 때까지 반영되지 않는다.
- **기록.** 질문 페이지의 로그에 ID 토큰, 인가 코드, 클라이언트 비밀, 쿠키 값을 싣지 않는다(원칙 V의 연장, ADR 0050 결정 "기록").
- **시험.** 시험용 가짜 로그인 서버는 프로브의 것(`.scratch/portal-login/probes/oidc_client/apps/portal/testing/fake-idp.ts`)을 바탕으로 직접 짓고, 로그아웃 끝점을 더하며, `https`로 띄운다. 시험의 인증서는 사설 인증 기관으로 만들고 `NODE_EXTRA_CA_CERTS`로 알린다. `.scratch/portal-login/probes/oidc_client/probe/flow.mjs`의 `tls` 묶음으로 쟀다(그 변수를 준 회차는 통과했고 주지 않은 회차는 TLS 검증 오류로 거부됐다. Windows 10에서만 돌렸다). 그 측정은 질문 페이지 서버가 로그인 서버를 부르는 쪽만 본 것이고, e2e의 브라우저가 그 인증서의 로그인 화면을 여는 길은 재지 않았다. Vitest가 설정 읽기와 시작 검사, 로그인 쿠키의 서명과 만료, 식별자 판정(주장 없음, `anon-` 접두)을 보고, 질문 페이지 e2e가 가짜 로그인 서버를 거쳐 로그인, 이름 표시, 로그아웃 방식 둘, 유지 시간의 기준 둘, 만료 뒤 다시 로그인, 같은 항목을 가리키는 두 사이트와 이름을 달리한 두 사이트를 본다. 위젯이 탭 저장소(sessionStorage)에 둔 대화가 로그인 서버에 다녀온 뒤에도 남는지는 어림이고 그 e2e로 잰다. 수락은 기능 계획 그대로다. 사내 로그인 하나를 흉내 낸 시험 환경에서 로그인한 사람만 calc 예시에 질문할 수 있고 트레이스의 주체가 그 사람이다.

## Considered Options

- **아이디와 비밀번호를 직접 받는 방식(LDAP)을 0.1 판에 함께 넣는다.** 사용자가 처음에 둘 다를 되물었다. 고르지 않았다. 질문 페이지가 비밀번호를 직접 다루게 되어 비밀번호가 기록에 새지 않게 하는 일과 반복 시도 차단을 떠맡고, 디렉터리와 통신하는 라이브러리와 시험용 가짜 디렉터리가 더 든다(어림, 재지 않았다). 방식의 이름 칸으로 구조만 열어 두고 새 기능 행 portal-ldap-login이 맡는다.
- **운영자가 질문 페이지 설정에 계정 목록을 적는다.** 설계 인터뷰의 셋째 선택지였고 고르지 않았다.
- **계정 정보를 Agent OS나 질문 페이지의 저장소에 보관한다.** 설계 인터뷰에서는 "회원 정보"라고 불렀다. 사용자가 뒤의 개인화 화면을 염두에 두고 물었다. 거부했다. 실행 기록에 이미 주체가 남고 사람별 기억(ADR 0054)도 주체를 열쇠로 쓰게 설계되어 있어, 계정의 표 없이 식별자만 넘겨도 사람별 데이터를 뒤에 더할 수 있다. 계정의 표를 두면 질문 페이지의 무상태가 깨지고 원본이 둘이 된다.
- **로그인 상태를 서버의 저장소에 두고 쿠키에는 번호만 둔다.** 어떤 로그인 상태든 서버가 바로 지울 수 있다. 거부했다. 질문 페이지에 저장소가 생긴다. 조사한 제품 가운데 oauth2-proxy, Auth.js, Rails, ASP.NET Core는 내용을 담은 쿠키가 기본이고 GitLab, Grafana, Django는 서버 저장이 기본이었다(서브에이전트가 원문을 받아 읽었고 이 세션은 다시 대 보지 않았다, 일지 2026-11-12-1937 "조사: 로그인 상태를 유지하는 방식").
- **refresh token으로 로그인 상태를 주기적으로 다시 확인한다.** 계정 정지가 유지 시간보다 빨리 반영된다. 0.1 판에는 넣지 않는다. 쿠키의 암호화, 약 4KB의 쿠키 크기 한도, 동시 갱신의 충돌, 가짜 로그인 서버의 갱신 기능이 따라온다(어림). 새 기능 행 portal-login-recheck가 맡고, 그때까지는 유지 시간을 짧게 잡거나 ID 토큰의 만료를 따르는 기준으로 보완한다.
- **유지 시간의 기준을 하나로 고정한다(질문 페이지의 8시간, 또는 ID 토큰의 만료).** 사용자가 설정으로 고르기를 물었고 둘을 설정으로 두었다. 두 기준은 끝나는 시각을 어느 값으로 정하는지만 달라 구현이 작다(어림). ID 토큰의 만료는 본래 로그인 상태의 수명을 뜻하지 않지만 그것에 맞추는 관행도 있다(같은 조사).
- **`oauth4webapi`와 `jose`의 조합, 또는 라이브러리 없이 직접 구현한다.** 셋 모두 질문 페이지 tsconfig의 복사로 타입 검사를 지나고, node가 `.ts`를 바로 돌려 가짜 로그인 서버와 흐름 한 바퀴를 돌았다. `.scratch/portal-login/probes/oidc_client/`로 쟀다(흐름 코드의 줄 수는 `openid-client` 56, 조합 99, 직접 구현 273이고 패키지 수는 3, 2, 0이다. 값의 원천은 `.scratch/portal-login/probes/README.md`). 직접 구현은 암호화된 ID 토큰, RS256 밖의 알고리즘, 공개 키 캐시 같은 것을 뺐고 그것을 우리가 채워야 한다. 사용자가 사용량을 물어 조사했다. 2026-11-05부터 11-11까지의 주간 내려받기 수는 `@azure/msal-node` 29,685,459, `oauth4webapi` 25,389,873, `openid-client` 23,842,164였다(`curl -s https://api.npmjs.org/downloads/point/last-week/<이름>`으로 손으로 봤다. `openid-client`의 수는 이 세션이 다시 봤고 나머지는 서브에이전트가 봤다). 앞의 둘이 더 크다. `oauth4webapi`는 `openid-client` 6.x가 의존하는 아래층이라 그 수에 `openid-client`의 몫이 들어 있고(레지스트리의 `dependencies`를 서브에이전트가 손으로 봤다), `@azure/msal-node`의 수에 Azure SDK의 몫이 크다는 것은 어림이다. 그래서 범용 서버 쪽 OIDC 클라이언트 가운데 `openid-client`보다 많이 쓰이는 별개의 대안은 찾지 못했다고 보았다(일지 2026-11-12-1937 "조사: Node의 OIDC 클라이언트 사용량"). 사용자가 `openid-client`를 골랐다.
- **가짜 로그인 서버를 `oidc-provider`로 세운다.** 거부했다. `.scratch/portal-login/probes/oidc_client/probe/deps.mjs`로 쟀다(패키지 40개에 타입 선언 19개가 따로 들고, 직접 지은 것은 의존성이 0이다). 고장 심기와 TLS는 직접 지은 쪽에만 붙여 쟀다.
- **질문 페이지 전체에 로그인 서버 하나를 둔다.** 설계 인터뷰의 추천이었다. 사용자가 "사이트마다 로그인 서버를 다르게 설정 가능"을 골랐다. 한 질문 페이지에서 조직이 다른 사이트를 함께 운영할 수 있고, 대가로 설정과 시험이 는다.
- **로그인 서버를 사이트마다 통째로 적거나, 함께 쓸지를 스위치로 고른다.** 사용자가 설정으로 되는지 물었다. 이름 붙인 항목을 사이트가 가리키게 해, 같은 항목이면 함께이고 이름을 달리 적으면 따로가 되게 했다. 스위치가 없어 코드의 갈래가 늘지 않는다. 대가는 따로 쓰려면 항목을 한 번 더 적고 돌아오는 주소를 로그인 서버에 하나 더 등록하는 것이다.
- **팝업 창으로 로그인한다.** 거부했다. 팝업 차단의 영향을 받고 휴대폰에서 동작이 다르다.
- **질문 페이지가 그룹이나 계정 목록으로 로그인할 사람을 거른다.** 거부했다. 로그인 서버가 이미 맡는 일이고, 사이트마다 대상을 가르는 일은 뒤의 그룹과 문서 권한 설계가 다룬다.
- **식별자를 `sub`나 이메일로 고정한다.** 거부했다. 조직마다 로그인 서버가 주는 주장이 다르고, 뒤의 기능이 조직의 사용자 식별자와의 대응을 요구한다.
- **로그아웃 단추를 두지 않거나 방식을 하나로 고정한다.** 사용자가 설정으로 되는지 물었고 항목마다 고르게 했다. 대가는 두 방식을 모두 짓고 시험하는 것이다.
- **보증 모드를 바꿀 때 남는 익명 토큰을 막는 장치를 둔다.** 거부했다. 공백이 짧고, 바로 막을 길(서명 키 교체)이 이미 있다.
- **로그인한 사람에게는 고지 확인을 받지 않는다.** 거부했다. 로그인하면 질문이 사람을 가리키는 식별자와 함께 남아, 익명일 때보다 알릴 까닭이 크다.
- **만료를 알게 된 질문을 다시 로그인한 뒤 자동으로 다시 보내거나 입력 칸에 남긴다.** 셀프 리뷰가 짚은 열린 가지를 승인 화면에서 물었고 사용자가 "다시 적게 두기"를 골랐다. 자동으로 다시 보내려면 위젯이 아직 보내지 못한 글을 저장해야 하고, 입력 칸에 남기려면 기본 로그인 단계에서 위젯을 고쳐야 한다.
- **`http` 주소의 로그인 서버를 받는다.** 거부했다. 결정 "로그인 방식"의 린트 판정 때문에 시험에서만 여는 길도 없다.

## Consequences

- **다른 ADR.** ADR 0050의 문장 일곱 곳에 이 ADR의 포인터를 단다. 첫 단락의 "이번에 실제로 도는 것은 익명뿐이다", 결정 "앱과 서버"의 "쿠키 값의 꼴만 검사한다"(로그인 쿠키는 서명을 검사한다), 결정 "경로"의 로그인 사이트 토큰 끝점이 늘 거절한다는 문장과 "그 밖은 404다"(끝점이 는다), 결정 "익명 식별자 쿠키"의 "확인 전에는 쿠키도 토큰도 내지 않는다"(로그인 쿠키는 확인 전에도 낸다), 결정 "페이지"의 로그인 사이트 알림과 비활성 로그인 단추, 결정 "테스트"의 아직 없음 화면 둘이다. ADR 0050의 무상태, 키 만들기, 익명 토큰의 결정은 그대로이고, 익명 식별자 쿠키의 결정은 위에 든 한 문장 밖이 그대로다.
- **Agent OS는 바뀌지 않는다.** `serve`는 지금처럼 사이트 토큰의 필수 주장 다섯과 `nbf`만 읽고(`src/agent_os/http/sites.py`를 읽었다) 로그인 사이트의 토큰과 익명 사이트의 토큰을 가르지 않는다. `sdk`, `openapi.json`, 사이트 파일의 형식, 위젯의 공개 표면이 그대로다. 계약을 바꾸는 일은 ADR 0060에 모인다.
- **질문 페이지가 처음으로 밖을 부른다.** 지금 질문 페이지 서버에는 밖으로 나가는 HTTP 호출이 없고 처리기가 동기 함수다(`web/apps/portal/server/handler.ts`를 읽었다). 로그인 서버의 설정 문서, 토큰 끝점, 공개 키를 부르게 되므로 비동기 경로가 생기고, 질문 페이지의 컨테이너가 로그인 서버에 닿는 네트워크가 필요하다. 조직의 로그인 서버가 사설 인증 기관의 인증서를 쓰면 `NODE_EXTRA_CA_CERTS`로 그 인증 기관을 알린다. 이 준비물(로그인 서버에 클라이언트 등록, 돌아오는 주소, 인증 기관, 비밀 값 파일)은 deploy-package 기능 계획에 넘긴다.
- **의존성.** `openid-client`와 그것이 끌어오는 `jose`, `oauth4webapi`로 패키지가 셋 는다(모두 MIT, 설치 스크립트 없음. `.scratch/portal-login/probes/oidc_client/probe/deps.mjs`로 쟀다). 설치하는 티켓이 같은 커밋에서 `docs/constitution/tech.md`의 웹 행에 적는다. 라이브러리 안의 전역 `fetch`는 web 워크스페이스의 ESLint가 보는 범위 밖이다(같은 폴더의 `probe/lint.mjs`가 `node_modules` 안 파일을 판정자가 보지 않는 것을 본다).
- **질문 페이지 설정의 형식.** 로그인 서버 항목의 목록과 사이트가 항목을 가리키는 칸이 는다. 지금 형식은 모르는 칸을 거부하므로 옛 판의 질문 페이지는 새 설정으로 뜨지 않는다(안전한 쪽이다). 형식 번호를 올릴지는 명세가 정한다.
- **한계.** 서버에 로그인 상태의 목록이 없어 한 사람만 골라 바로 로그아웃시킬 수 없고, 로그인 서버에서 계정을 정지해도 유지 시간이 끝날 때까지는 질문할 수 있다. 유지 시간을 짧게 잡거나 ID 토큰의 만료를 따르는 기준으로 줄인다. 쿠키의 이름은 서명만 되고 암호화되지 않아 그 브라우저를 쓰는 사람이 읽을 수 있다. 로그인 쿠키를 훔친 사람은 유지 시간 동안 그 사람으로 질문할 수 있고, `HttpOnly`와 https 출처의 `Secure`가 그 길을 좁힌다. 로그인 도중의 값을 든 쿠키는 로그인 서버에서 돌아오는 요청에 실려야 하므로 `SameSite=Strict`를 쓸 수 없다는 것은 쿠키 규격으로 아는 것이고 브라우저로 재지 않았다(어림). 로그인만 받는 사이트에서 로그아웃한 뒤 위젯이 탭 저장소에 둔 대화가 그 탭에 남는지와 그것을 어떻게 지울지는 명세가 본다(둘 다 사이트는 위젯이 스스로 지운다).
- **기본 로그인만 든 동안의 대화.** 둘 다 사이트에서 익명으로 질문하다가 스스로 로그인하면 주체가 바뀌어 위젯이 대화를 지운다(지금 위젯의 동작). ADR 0060이 들어가면 대화 넘겨받기로 바뀐다. 사용자가 "어느 경우든 로그인하면 대화를 넘겨받기"를 골랐고, 그 장치가 뒤 기능의 몫이라 그 사이에만 이렇다.
- **상한.** 같은 사람도 사이트마다 다른 로그인 주체라 `serve`의 주체별 상한이 사이트마다 따로 선다. 로그인 주체는 익명 주체와 달리 쿠키를 지워 주체별 상한을 피하지 못한다.
- **용어.** `CONTEXT.md`에 로그인 서버, 로그인 서버 항목, 로그인 상태, 로그인 주체를 더하고 로그인 모드를 손질했다.
- **다른 행.** 질문 도중의 로그인은 새 행 step-up-login이 맡는다(ADR 0060). 새 행 둘을 세운다. portal-ldap-login(아이디와 비밀번호를 직접 받는 로그인 방식)과 portal-login-recheck(refresh token으로 로그인 상태를 다시 확인하기)이고, 둘 다 슬라이스 10(제품 1.0 묶음)이며 portal-login과 pilot-release를 기다린다. 화면에서 로그인 방식을 고르는 일은 portal-admin이 맡는다(그 기능 계획에 넘긴다). admin-login의 설계 인터뷰는 이 인터뷰의 조사(로그인 상태를 유지하는 방식, 쿠키 지침)를 일지에서 다시 쓸 수 있다. 방식은 그 행이 따로 정한다. principal-propagation에는 그룹이 로그인 서버에서 온다는 방향과 식별자를 운영자가 고른다는 것을 넘긴다.
- **명세가 짓는 것.** 설정 칸과 방식 값의 이름, 끝점의 경로, 로그인 쿠키와 로그인 도중 쿠키의 이름·경로·속성, 쿠키 서명 키의 자리(토큰 서명 키를 함께 쓸지 따로 둘지), 함께 로그아웃을 켰는데 로그인 서버가 로그아웃 끝점을 알리지 않을 때의 동작, `|`가 든 식별자의 처리(주체가 `<발급자>|<식별자>`라 가르는 글자와 겹친다), 식별자의 길이와 글자의 한도, 로그인 서버에 요청할 범위(`openid`에 이름을 얻을 범위), 거절과 만료의 문구, 로그인 서버가 응답하지 않을 때의 화면, 질문 페이지 설정의 형식 번호, 끝난 로그인 상태와 없는 로그인 상태를 가르는 방법(끝난 쿠키를 얼마나 남길지), 로그인한 채 고지를 확인한 기록을 어느 쿠키로 남길지(지금 그 기록인 익명 식별자 쿠키를 로그인만 받는 사이트에서도 낼지 따로 둘지). 설계 인터뷰의 답과 확인받은 요약은 일지 2026-11-12-1937에 글자 그대로 있다.
