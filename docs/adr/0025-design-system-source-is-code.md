# 디자인 시스템은 코드가 원천이고 Claude Design은 탐색과 화면을 맡는다

위젯 설계 인터뷰 끝에 사용자가 화면 작업 전에 디자인 시스템과 화면 디자인을 먼저 만들자고 했다. 위젯과 관리 화면은 **디자인 시스템 하나를 나눈다.** 그 원천을 어디에 두는지가 물음이었다. **토큰과 핵심 컴포넌트는 코드에서 만들고 테스트한다. 그것이 원천이다. Claude Design에는 사용자가 시작하는 `/design-sync`로 올린다. Claude Design은 방향 탐색(색과 글꼴 짝, 대략의 화면)과, 올린 디자인 시스템으로 그리는 Wireframe과 UI mockups를 맡는다.** (바뀜: 이력 2026-10-16 "디자인 시스템과 화면은 Claude 아티팩트에 두고, Claude Code가 편집자로 저장소에서 올린다") (바뀜: 이력 2026-10-20 "화면은 Claude Code가 화면 디자인 스킬로 그리고, 웹에서 고친 것은 거꾸로 동기화로 코드에 들인다") (바뀜: 이력 2026-10-21 "디자인 시스템 아티팩트의 편집을 tokens.json으로 열고, 사람이 알리거나 화면 작업과 올리기가 찾은 웹 편집을 디자인 토큰 CSS로 들인다") **확정한 화면은 기능의 `.scratch/<slug>/design/`에 내보내 커밋하고, 화면마다 근거 문서의 전체 경로와 기준 커밋을 적는다.** 그다음 구현이 그 화면을 근거로 짓는다. 근거 문서는 화면을 그릴 때 있는 것이다. 명세 전에 그리는 화면은 ADR과 `plan.md`의 그 기능 행이고, 명세가 생긴 뒤에는 명세가 화면을 가리킨다.

연동의 방향이 이것을 정했다. `DesignSync` 도구는 로컬 컴포넌트 라이브러리를 Claude Design의 디자인 시스템 프로젝트에 컴포넌트 하나씩 맞추는 도구이고, `/design-sync` 안에서만 쓴다(도구 설명을 읽었다). 토큰의 제약도 코드에서만 보인다. Tailwind의 `@property` 등록이 shadow root 안에서 되지 않아 손대지 않은 CSS는 비교한 58곳 중 31곳이 다르게 그려졌다. 사이트의 `html { font-size }`가 바뀌면 rem 기반 위젯이 따라 줄었다(`.scratch/web-widget/probes/widget_tailwind/`). 단위 같은 토큰 결정은 이것을 잴 수 있는 자리에서 내린다. 명세와 화면의 연결을 저장소에 두는 이유는, 디자인 도구 안에 두면 저장소를 보는 세션이 그것을 보지 못하기 때문이다. 명세를 고치는 세션이 같은 자리에서 어느 화면을 고칠지 본다.

## Considered Options

- **Claude Design에서 디자인 시스템을 먼저 만들고 코드가 따라 옮긴다.** 디자인 작업이 가장 자유롭다. 그러나 원천이 둘이 되어 어긋나고, shadow root와 rem 같은 코드의 제약을 나중에 맞춰야 한다. 거부했다.
- **Claude Code가 Artifact(Design, Design System 형식)로 만든다.** 링크로 바로 읽힌다. 그러나 사람이 직접 보며 고치는 작업은 Claude Design이 낫다. 거부했다. (바뀜: 이력 2026-10-20 "화면은 Claude Code가 화면 디자인 스킬로 그리고, 웹에서 고친 것은 거꾸로 동기화로 코드에 들인다")
- **명세와 화면의 연결을 디자인 도구 안의 파일에 둔다.** 동기화를 요청하면 그 파일을 따라 화면을 고칠 수 있다. 그러나 저장소를 보는 세션이 그 기록을 보지 못한다. 거부했다.
- **위젯만의 디자인 시스템.** 최종 사용자용 모양에만 맞춘다. 그러나 관리 화면에도 아직 스타일이 없어서(ADR 0021 이력 2026-10-03) 같은 일을 두 번 한다. 거부했다.

## Consequences

- **design-system 기능이 `plan.md`에 는다.** web-widget과 admin-style이 그것을 기다리고, 파이썬 기능(conversation, end-user-channel)과는 나란히 간다.
- **Tailwind는 design-system이 토큰과 함께 처음 들인다.** 토큰은 Tailwind의 테마로 코드에 선다. 위젯과 관리 화면이 그것을 쓴다(ADR 0021 이력 2026-10-03, ADR 0024). shadow root와 rem의 측정은 위젯의 모양으로 했고, 그 결과를 토큰의 단위와 shadow root용 CSS에 반영하는 것이 이 기능의 일이다.
- **세부는 design-system 기능의 인터뷰가 정한다.** 두 앱이 토큰과 컴포넌트를 나누는 패키지의 모양(`packages/ui`를 둘지), rem과 px, 다크 모드, 접근성, 한글 글꼴과 남의 페이지에 싣는 법, Storybook을 둘지(Claude Design의 디자인 시스템이 미리보기를 대신할 수 있다), 디자인 문서의 이름과 자리와 실리는 방식(공유 하나와 앱별, `.claude/rules`의 `paths`)이다. (바뀜: ADR 0026)
- **`.scratch/<slug>/design/`은 새 자리다.** 그 규약을 `docs/agents/issue-tracker.md`에 더하는 일은 design-system 기능이 맡는다.
- **화면은 기능마다 그린다.** 위젯의 화면은 web-widget의 명세 직전에, 관리 화면의 화면은 admin-style에서 그린다.
- **코드가 바뀌면 `/design-sync`로 다시 맞춘다.** (바뀜: ADR 0026) (바뀜: 이력 2026-10-16 "디자인 시스템과 화면은 Claude 아티팩트에 두고, Claude Code가 편집자로 저장소에서 올린다") (바뀜: 이력 2026-10-21 "디자인 시스템 아티팩트의 편집을 tokens.json으로 열고, 사람이 알리거나 화면 작업과 올리기가 찾은 웹 편집을 디자인 토큰 CSS로 들인다") 자동으로 맞춰지지 않는다.

## 이력

### 2026-10-16 디자인 시스템과 화면은 Claude 아티팩트에 두고, Claude Code가 편집자로 저장소에서 올린다

admin-style의 화면을 그리려다 계정이 엇갈렸다. 저장소의 디자인 시스템 프로젝트(`.design-sync/config.json`의
`projectId`)와 재탐색 프로젝트는 njh4803 계정의 단독 Claude Design(claude.ai/design)에 있고, Claude Code는 njh6803
계정으로 로그인되어 있다(`claude auth status`로 봤다). 사용자가 두 계정이 같은 디자인을 나누고, 저장소에 판을 적어 같은
판인지 맞대 볼 수 있기를 바랐다. 공식 안내의 원문을 내려받아 대 봤다(`.scratch/design-artifacts/probes/`의
`find_sentences.mjs`, `pricing_rows.mjs`). 단독 Claude Design은 2026-12-14에 닫힌다. 프로젝트는 단독 쪽에 남아 닫힐
때까지 돌고(내려받기는 하나씩이다), 디자인 시스템은 "팀 디자인 시스템 마이그레이션"으로 Claude 아티팩트에 옮긴다.
개인 요금제는 프로젝트 공유와 협업이 없고(요금제 비교표의 "Project sharing and collaboration"이 Free·Pro·Max 모두 no),
njh4803의 설정에도 조직이나 멤버를 다루는 탭이 없었다(손으로 봤다). Team은 업무용 이메일로만 만든다. 아티팩트는 Pro·Max에서도 이메일로 특정 사람을 초대해 편집 권한을
줄 수 있다(베타). 개인 계정 사이에 데이터를 옮기는 것은 지원하지 않는다고 적혀 있고, 아티팩트 하나의 주인을 옮기는
방법은 공유 안내에서 찾지 못했다(손으로 읽었다). 위 결정이 거부한 "Claude Code가 Artifact(Design, Design System 형식)로
만든다"의 근거(사람이 직접 보며 고치는 작업은 Claude Design이 낫다)는 Claude Design이 아티팩트로 옮겨 가며 사라졌다.

**디자인 시스템과 화면은 Claude 아티팩트에 둔다. 주인은 njh4803 계정이고, Claude Code가 로그인한 njh6803 계정을 편집자로
초대한다. 원천은 그대로 코드다. 디자인 시스템은 지금의 `/design-sync` 빌드로 파일을 만들고, Claude Code가 편집자로서
Design System 아티팩트의 `project/` 아래 같은 경로에 바뀐 파일만 올리며 빌드에서 빠진 경로는 지운다. 올린 커밋은
아티팩트 색인의 `lastChange`에 적고, 같은 판인지는 파일의 sha256으로 맞댄다. 화면은 njh4803이 Design 아티팩트를 만들기만 하고 njh6803을 편집자로
초대하며, 그리기는 njh6803이 한다. 확정한 화면은 지금처럼 `.scratch/<slug>/design/`에 커밋한다.**

- 디자인 시스템 아티팩트는 https://claude.ai/artifact/8ttLDZQqchfD2ao1XG56GH 다. njh4803의 단독 디자인 시스템을
  "팀 디자인 시스템 마이그레이션"으로 옮겼다. 빌드가 `ds-bundle/`로 그대로 옮기는 저장소 원본 다섯(`df705c17`의
  `.claude/rules/web-design.md`와 `.design-sync/foundations/`의 네 파일)이 아티팩트의 `project/guidelines/web-design.md`,
  `project/foundations/<이름>/index.html`과 바이트까지 같다(쟀다, `hash_match.mjs`). 그래서 빌드의 `ds-bundle/<경로>`가
  아티팩트에서는 `project/<같은 경로>`다. 빌드 산출 전체가 같은지는 커밋된 원본이 없어 맞대지 못했고, 다음 동기화가 본다.
- njh6803의 Claude Code는 초대를 수락한 뒤 그 아티팩트를 편집 권한으로 읽고, 색인에 `lastChange`를 더해 썼다(손으로
  봤다. 판 `1792115455-aa71`이고 다시 받은 파일의 sha256이 올린 것과 같다, `hash_match.mjs`). 수락하기 전에는 도구가
  "artifact not found"를 낸다.
- 올리기는 그 입력을 바꾼 PR이 main에 병합된 뒤 main에서 빌드해 하고, `lastChange`의 `via`에 빌드한 main의 커밋을
  적는다. 병합 전에 올리면 squash로 사라질 브랜치 커밋이 남고, 미리 지은 빌드를 올리면 그사이 병합된 변경이 빠진 채
  `via`만 앞선다. 파일 몇 개만 올리면 `via`를 부분이라 적어 다음 동기화가 전체를 맞대게 한다(모양은
  `docs/agents/issue-tracker.md` 화면 디자인 절).
- 옮긴 배치(색인의 `editing: "off"`와 `source`)를 지키고, 화면의 "Finish the migration" 정리는 하지 않는다. 정리는
  파일을 아티팩트 형식의 배치로 다시 짜서 빌드와 경로가 맞지 않게 되고, 화면 편집을 켜 원천을 둘로 만든다.
- 공식 안내대로라면 첫 쓰기로 단독 쪽과 갈라졌다. 다시 옮기기는 옮긴 뒤 Claude에서 바뀐 디자인 시스템을 그대로 두고
  건너뛴다(원문을 대 봤다. 실제로 건너뛰는지는 재지 않았다). 그래서 `/design-sync`의 업로드 도구(`DesignSync`)로 단독
  프로젝트에 올리는 일은 그만둔다. 빌드는 그대로 쓴다. 단독 쪽의 원본(디자인 시스템 프로젝트와 재탐색 프로젝트)은 따로
  지우지 않고 2026-12-14에 사이트와 함께 닫히게 둔다. 재탐색 프로젝트의 디자인 파일은 이미 `.scratch/design-system/design/`에
  있다.
- Claude Code의 디자인 시스템 목록에는 다른 계정이 공유한 이 디자인 시스템이 나오지 않는다(손으로 봤다). Claude Code가
  화면을 그릴 때는 그 주소를 이름으로 댄다.
- 재지 못한 것: njh4803이 Design 아티팩트를 비워서 만들 수 있는지, 그것에 이 디자인 시스템을 붙일 수 있는지, njh6803이
  편집자로 그리는 흐름(admin-style이 처음 그릴 때 잰다). 빌드 산출 전체가 지금 아티팩트와 같은지와 빌드에서 빠진 경로의
  지우기(다음 동기화가 잰다). 다시 옮기기가 실제로 건너뛰는지(재지 않고 둔다. 단독 쪽에 올리지 않으므로 다시 옮길 일이 없다).

거부한 안은 다섯이다.

- **2026-12-14까지는 `/design-sync`로 단독 프로젝트에 올리고 njh4803이 다시 옮긴다.** 지금 흐름을 지키지만, 바뀔
  때마다 브라우저 조작이 들고 닫힌 뒤에는 결국 직접 올려야 한다.
- **Claude Code가 화면 아티팩트를 직접 만든다.** 브라우저 조작이 없지만 주인이 njh6803이 되고, 주인을 옮기는 방법이 안내에 없다.
- **njh4803의 워크스페이스에 njh6803을 멤버로 둔다.** 개인 요금제에는 프로젝트 공유와 협업이 없고, Team은 업무용
  이메일로만 만들며 두 명 이상이다.
- **단독 Claude Design에서 njh4803 하나로 계속 그린다.** 계정을 나누지 않아 단순하지만 2026-12-14에 닫힌다.
- **정리를 하고 아티팩트 형식(`tokens.json`, `components/bundle.js`)으로 올리는 빌드를 새로 짓는다.** 아티팩트의 화면
  기능을 다 쓰지만 빌드를 새로 지어야 하고 화면 편집이 켜져 원천이 둘이 된다.

함께 고치는 것: `docs/agents/issue-tracker.md`의 화면 디자인 절, `.design-sync/NOTES.md`, `kickoff/prompting.md`,
`.scratch/admin-style/design/screens-prompt.md`의 하는 법과 고른 뒤, `.scratch/plan.md`(design-artifacts 행, admin-style·
web-widget 행), `.claude/rules/web-design.md`의 머리 문장, `README.md`의 `.design-sync/` 줄, 헌법 `tech.md`의 웹 행,
ADR 0026 본문의 포인터.

### 2026-10-20 화면은 Claude Code가 화면 디자인 스킬로 그리고, 웹에서 고친 것은 거꾸로 동기화로 코드에 들인다

skill-call-sites의 설계 인터뷰가 화면 디자인 절차를 프로젝트 스킬 `/ui-design`으로 만들기로 하면서(ADR 0033의 2026-10-20 이력 "하네스가 스킬을 부르는 자리를 감사하고, 설명에만 기대던 계기를 하네스로 옮긴다"), 위 이력이 admin-style의 첫 그리기로 넘긴 칸 가운데 Design 아티팩트를 누가 만들고 누가 그리는지를 정했다. 위 이력의 전제는 이미 바뀌어 있었다. 세션 시작 훅이 남기는 계정 기록(주 체크아웃의 `.scratch/token-report/ledger/accounts.jsonl`, 커밋하지 않는 파일, `tools/hook_session_usage.py`)을 보면 Claude Code의 세션은 2026-10-18 21:05 UTC부터 모두 njh4803으로 시작했고, 그 전에는 njh6803과 번갈아 쓰였다(계정이 바뀐 줄을 찍어 손으로 봤다). 일지에는 계정을 바꾸려고 세션을 멈춘 인계가 둘 있지만(2026-10-18-02, 2026-10-19-25), 둘 다 멈춘 자리와 이을 일만 적었고 왜 바꾸는지와 위 이력의 계정 구성을 어떻게 할지는 적지 않았다. 지금 계정으로 디자인 시스템 아티팩트를 Artifact 도구로 읽자 머리에 "owned by you"가 나왔다(손으로 봤다). 편집자로 초대받은 계정이면 "writer"가 나온다는 것은 도구 설명에서 읽었고 보지는 않았다(어림). 고른 것은 사용자다(일지 2026-10-20-35).

**화면은 Claude Code가 그린다. 화면 디자인 스킬 `/ui-design`이 Design 형식으로 아티팩트를 만들고 디자인 시스템 아티팩트를 붙여 그린 뒤, 사람이 고른 화면을 읽어 `.scratch/<slug>/design/`에 옮긴다. 계정은 런북, 스킬, 저장소 어디에도 적지 않는다. 쓸 때 디자인 시스템 아티팩트를 읽어 지금 계정이 주인("owned by you")이거나 편집자("writer")인지 보고, 둘 다 아니면 멈춘다. 원천은 그대로 코드다. 사람은 목업과 디자인 시스템을 웹에서 고칠 수 있고, 고친 것은 거꾸로 동기화(`CONTEXT.md`)로 코드에 들인다. 목업 쪽은 `/ui-design`이, 디자인 시스템 쪽은 새 기능 design-reverse-sync가 맡는다. 그 기능이 닫히기 전까지 디자인 시스템 아티팩트의 편집은 꺼 둔다.**

- 계정을 적지 않는 까닭은 런북이다. 런북으로 시작하는 새 프로젝트에는 디자인 시스템 아티팩트가 아직 없어, 그때 로그인한 계정이 그것을 만들고 주인이 된다. 그래서 런북에는 오래 쓸 계정으로 로그인한 채 디자인을 시작한다는 원칙만 둔다. 위 이력의 계정 구성(njh4803 주인, njh6803 편집자)은 이 저장소의 그때 사정이었고, 주인이 아닌 계정의 Claude Code로 그릴 때는 편집자 초대가 여전히 길이다.
- Design 형식(Artifact 도구가 보여 준 형식 설명을 읽었다)은 형식 주소와 제목으로 만들고, 색인은 `project/canvas.json`, 화면 파일은 `.dc.html`이다. 디자인 시스템은 `project/ds/<폴더>/tokens.json`과 색인의 `designSystems` 기록으로 들인다. 우리 디자인 시스템 아티팩트에는 `tokens.json`이 없다(파일 목록을 봤다, 판 `1792491791-94a2`, 파일 875개). 그래서 붙이는 법은 `/ui-design`을 들이는 PR이 형식 설명대로 짓고 첫 그리기에서 확인한다. 지금 계정이 Design 형식으로 새 아티팩트를 만들 수 있고 "Agent OS 디자인 시스템"이 "(mine)"으로 붙일 후보에 나온 것은 읽기 전용 조회로 봤고, 실제로 만들지는 않았다. 만들면 아티팩트가 하나 생기기 때문이다.
- 아티팩트는 claude.ai에 올라가므로 Claude Code가 만든 Design 아티팩트도 사람이 같은 링크로 웹에서 보고 고칠 수 있다. 사람이 고친 뒤 Claude Code가 그 위에 덮어쓰려 하면 거절되고 새 판을 받는다(형식 설명과 Artifact 도구 설명을 읽었다).
- 목업의 거꾸로 동기화. `/ui-design`이 확정한 화면을 옮길 때 그 폴더의 README 표에 아티팩트 주소와 판 id를 적고(`docs/agents/issue-tracker.md` 화면 디자인 절이 이미 그렇게 적는다), 그 기능으로 다시 부르거나 구현이 그 화면을 근거로 읽을 때 지금 판과 대 본다. 다르면 웹에서 고친 것이므로 다시 옮긴다. 고친 값이 디자인 시스템에 없는 색·글꼴·간격이면 토큰 코드로 옮길지 사람에게 묻고, 옮기면 `web/packages/ui`의 판정(명암비, axe)을 지난다. Design 아티팩트의 읽기 결과에도 판 id가 나오는지는 디자인 시스템 아티팩트에서만 봤다(어림).
- 디자인 시스템의 거꾸로 동기화. Design System 형식의 웹 편집기는 `tokens.json`의 토큰을 고치는데(형식 설명을 읽었다) 우리 빌드는 그 파일을 내지 않고, 색인의 `editing: "off"`가 편집을 끈다. 편집을 켜는 법, `tokens.json`을 내는 빌드, 고친 토큰을 디자인 토큰 CSS(`theme.css`)로 옮기는 규칙과 판정, 다음 올리기가 웹에서 고친 것을 덮어쓰기 전에 거르는 자리를 design-reverse-sync(`plan.md`)가 설계 인터뷰부터 정한다. 그때까지는 위 이력대로 `editing: "off"`를 지킨다.
- 원천을 코드에 두는 까닭은 그대로다. 관리 화면과 위젯이 쓸 디자인 토큰과 컴포넌트는 코드 패키지 `web/packages/ui`에 있고(앱이 들이는 것은 admin-style과 web-widget의 일이다), 판정(명암비, axe, 토큰 밖 클래스, 사진 비교)은 코드의 Storybook에서만 돈다. 웹에서 고친 값도 코드로 옮긴 뒤에야 화면에 나오고 검사를 받는다.
- 재지 못한 것: Design 아티팩트를 실제로 만들고 디자인 시스템을 붙이는 것, Design 아티팩트 읽기 결과의 판 id, 편집자 계정의 "writer" 머리, 디자인 시스템 아티팩트의 편집을 켜는 법.

거부한 안은 여섯이다.

- **원래 흐름으로 되돌린다.** Claude Code를 njh6803으로 다시 로그인하고, njh4803이 브라우저에서 Design 아티팩트를 만들어 초대한 뒤 그린다. 위 이력 그대로지만 브라우저 조작이 남고 계정이 절차에 고정된다.
- **런북 준비에서 디자인 주인 계정을 정해 그 프로젝트의 파일에 적는다.** 런북 원본에는 남지 않지만, 계정을 바꾸면 그 파일도 고쳐야 한다.
- **계정을 확인하지 않는다.** 다른 계정이면 도구가 "artifact not found"나 쓰기 거절을 낼 때에야 안다(위 이력이 수락 전에 그 오류를 봤다).
- **원천을 아티팩트로 옮긴다.** 웹에서 고친 것이 곧바로 원천이 되지만, 앱이 쓰는 것은 코드 패키지이고 판정도 코드에서만 돌아 결국 코드로 옮겨야 한다. 원천이 둘이 되어 어긋나는 것은 이 ADR이 처음에 거부한 안의 이유와 같다.
- **목업만 거꾸로 동기화하거나, 판만 대 보고 옮기지 않거나, 웹에서는 보기와 댓글만 한다.** 사용자는 디자인 시스템까지 웹에서 고칠 수 있기를 골랐다. 대 보기만 하는 안과 보기만 하는 안은 웹에서 고친 것이 저장소에 들어오지 않거나 약속에만 기댄다.
- **디자인 시스템의 거꾸로 동기화를 `/ui-design`의 PR에 함께 짓는다.** PR이 커지고, 아직 모르는 것(편집을 켜는 법, `tokens.json`과 `theme.css`의 대응)을 그 PR 안에서 재야 한다.

함께 고치는 것: 이 이력의 PR은 `.scratch/plan.md`(admin-style·web-widget 행, design-reverse-sync 행), `CONTEXT.md`(거꾸로 동기화), 이 ADR 본문의 포인터를 고친다. 다음 PR이 `/ui-design`과 함께 `docs/agents/issue-tracker.md` 화면 디자인 절(계정 문단, 시작 프롬프트와 그리는 법), `KICKOFF.md` 9단계, `kickoff/prompting.md`(브라우저 요령과 계정 문단), `.scratch/admin-style/design/screens-prompt.md`의 하는 법, `.design-sync/NOTES.md`의 계정 문장을 고친다.

### 2026-10-21 디자인 시스템 아티팩트의 편집을 tokens.json으로 열고, 사람이 알리거나 화면 작업과 올리기가 찾은 웹 편집을 디자인 토큰 CSS로 들인다

design-reverse-sync의 설계 인터뷰(일지 2026-10-21-12)가 위 이력이 넘긴 넷, 곧 편집을 켜는 법, `tokens.json`을 내는 빌드, 고친 토큰을 디자인 토큰 CSS로 옮기는 규칙과 판정, 다음 올리기가 웹 편집을 덮어쓰기 전에 거르는 자리를 정했다. 찾은 사실은 아래다.

- Design System 형식의 페이지 스크립트(아티팩트에 실린 `app.js`)를 Artifact 도구로 받아 읽었다. `tokens.json`은 계열마다 토큰 목록(이름, 값, 쓰임 설명)이고 색 계열에만 테마가 붙으며, 다른 토큰을 가리키는 값은 `{다른 토큰}` 꼴이다. 페이지 테마는 8개까지, 색 토큰은 600개까지 받는다. 색 토큰은 테마마다 값을 가진 한 목록으로 센다(형식 설명 `artifact-type/reference/format.md`를 읽었다, 판 `1792564314-af13`). 페이지는 토큰의 값·설명 고치기, 더하기, 지우기, 이름 바꾸기(그 토큰을 가리키는 값과 README의 이름도 함께 고친다)와 README·마크다운 문서·컴포넌트 설명·에셋·글꼴의 편집 화면을 두고, 테마를 더하는 화면은 두지 않는다. 저장은 약 800ms 디바운스의 자동 저장으로 `tokens.json`을 통째로 다시 쓰고, 충돌하면 토큰 단위로 합친다. 저장할 때 페이지가 `tokens.css`, `api/*.md`, `manifest.json`을 다시 짓는다. 우리 아티팩트처럼 파일로 둔 형식(색인 `project/design-system.json`의 `layout: "files"`)에서는 사람이 저장해도 색인의 `lastChange`가 바뀌지 않는다.
- 같은 스크립트에서, 색인의 `editing: "off"`는 페이지 전체를 읽기 전용으로 하고 README 밖의 절을 숨긴다. 그 키를 지우면 편집이 켜지고, `source` 키는 남아도 배너를 띄울 뿐이다. 배너의 정리 버튼은 파일을 옮기지 않고 에이전트에게 요청을 보낸다. 컴포넌트 미리보기는 페이지가 지은 토큰 CSS와 번들 CSS를 함께 싣는데, 우리 번들(`_ds_bundle.css`)이 토큰을 다시 선언하므로 웹에서 고친 값은 컴포넌트 카드에 보이지 않을 것으로 본다(어림).
- 아티팩트의 판 id는 사람이 고치지 않아도 오른다. 형식 쪽 파일이 바뀌며 `1792491791-94a2`에서 `1792564314-af13`으로 올랐고 `project/` 아래 파일은 크기가 그대로였다(2026-10-21 서브에이전트가 Artifact 도구의 파일 목록을 두 번 받아 손으로 봤다). 파일 목록에는 경로, 종류, 바이트만 있고, 읽기 결과의 머리에 파일마다 sha256이 나온다(손으로 봤다).
- 웹 저장은 아티팩트를 지켜보는 세션에 턴도 알림도 일으키지 않는다(ArtifactComments 도구 설명을 읽었다). 아티팩트를 읽는 것은 Claude 도구 안에서만 되므로, 주기적으로 확인하려면 회차마다 세션이 하나 든다. 예약 세션은 시작하는 데만 opus로 약 $0.32가 들고, 그 주의 사용 한도는 이미 81%를 썼다(어림: 2026-10-21 서브에이전트가 아침 보고 다섯 회차의 세션 기록과 사용량을 세션 스크래치패드의 스크립트로 센 값이고, 스크립트와 명령은 남기지 않았다).
- `theme.css`에는 토큰마다의 주석이 없다. `tokens.json`에 낼 토큰은 112개다. 테마·모드 한 벌마다 색 98개(원색 68, 반투명 7, 쓰임새 23)이고, 모든 벌이 같은 글자 크기 3, 간격 7, 모서리 4다. 원색은 테마마다 한 블록이라 같은 테마의 라이트·다크가 한 값을 나누고, 반투명은 값이 모든 테마에 같아 뿌리에 한 번 둔다(`theme.css`를 읽어 셌다).

**디자인 시스템 올리기가 Design System 형식의 `tokens.json`을 함께 내고, 색인의 `editing` 키를 지워 아티팩트의 편집을 켠다. 사람이 웹 편집을 마치고 알리면 그 세션이 거꾸로 동기화를 하고, 알리지 않은 웹 편집은 화면 작업과 올리기가 먼저 찾아 멈춘다. 디자인 토큰 CSS로 자동으로 옮기는 것은 값 바꾸기뿐이고, 나머지와 판정에 걸린 값은 사람이 고른다. 올리기와 거꾸로 동기화는 프로젝트 스킬 `/sync-design-system` 하나가 맡는다. 원천은 그대로 코드다.**

- **`tokens.json`.** `web/tools`의 TypeScript 스크립트가 `theme.css`를 읽어 짓고, 같은 스크립트가 거꾸로 방향의 비교와 옮기기를 한다. 명암비는 패키지의 계산(`web/packages/ui/src/testing/index.ts`의 `contrastRatio`)을 그대로 불러 같은 공식으로 "통과하는 가장 가까운 값"을 낸다. 테스트는 typescript-eslint와 vitest를 지나 `pnpm -C web verify`에 든다. `web/tools`에 도구와 테스트를 나란히 두는 선례는 `visual.ts`와 `visual.test.ts`다. 다만 `web/tools`는 아직 `@agent-os/ui`에 의존하지 않고, 판정 스토리의 짝 표(`CONTRAST_PAIRS`, `web/packages/ui/src/styles/contrast.ts`)는 패키지 밖으로 내보내지 않는다(`web/package.json`과 패키지의 `exports`를 읽었다). 컴포넌트 카드와 나머지 파일은 지금처럼 Claude Design용 번들 스킬의 빌드를 빌려 짓는다. 그 빌드를 걷어 낼지는 `plan.md`에 따로 연 행(design-card-build)이 정한다. 2026-12-14 뒤에도 번들 스킬이 남는지는 모른다(어림).
- **테마와 범위.** 페이지 테마는 테마 넷 × 모드 둘의 여덟이고(`nokcheong-light`, `nokcheong-dark`처럼), 기본인 녹청 라이트가 첫째다. 사람은 어느 벌의 색이든 고칠 수 있다. 페이지 한도(8)를 채우므로 테마를 더하면 그때 다시 정한다. 내는 토큰은 원색과 반투명(값), 쓰임새 토큰(그 벌의 대응대로 원색을 `{원색}` 꼴로 가리킨다), 글자 크기, 간격, 모서리다. 밀도와 이름 있는 치수(버튼 높이 등)는 페이지에 그 축이 없어 내지 않는다.
- **토큰 설명.** 토큰마다의 쓰임 설명은 `theme.css`의 그 줄 주석이 원천이다. 원색은 기본 테마(녹청) 블록에만, 쓰임새 토큰은 라이트 대응 블록에 둔다. 스크립트가 주석을 설명으로 내고, 웹에서 설명을 고치면 거꾸로 동기화가 그 주석을 고친다. 값과 설명이 한 파일에 있어 함께 리뷰된다. 처음 쓸 주석은 112개다.
- **편집 켜기.** 색인의 `editing` 키만 지운다. 토큰·글·그림 편집이 모두 켜진다(토큰만 켜는 스위치는 없다). 페이지의 색·글자·간격 보기는 `tokens.json`으로 그려 바로 바뀌지만, 컴포넌트 카드는 거꾸로 동기화를 병합하고 다시 올린 뒤에 바뀔 것으로 본다(어림). `source` 키는 남기고, 옮기기 마무리 배너가 떠도 누르지 않는다. 정리를 하지 않는 까닭 가운데 빌드와 경로가 어긋난다는 것은 위 2026-10-16 이력 그대로다. 그 이력의 다른 까닭(화면 편집을 켜 원천을 둘로 만든다)은 이 이력이 편집을 켜면서 거꾸로 동기화로 원천을 코드 하나에 두어 맡는다. 키를 지우는 것은 `tokens.json` 올리기, 웹 편집 확인, 계기 훅, 스킬이 모두 들어온 뒤의 마지막 단계다.
- **웹 편집을 아는 법.** 올리기의 마지막 호출이, 올린 뒤 `project/` 아래 있는 파일마다의 sha256을 `project/` 아래 기록 파일 하나에 적는다. 올리기는 바뀐 파일만 보내므로(`docs/agents/issue-tracker.md` 화면 디자인 절) 기록은 앞 기록에 이번에 보내고 지운 것을 합친 것이다. 이번에 보낸 것만 적으면 보내지 않은 파일이 다음 확인에서 모두 기록에 없는 새 파일로 걸린다. 확인은 웹에서 고칠 수 있는 파일(`tokens.json`, 마크다운, 색인의 그림 목록)을 읽어 머리의 sha256을 그 기록과 맞대고, 기록에 없는 새 파일도 웹 편집으로 본다. 페이지가 저장할 때 `tokens.json`에서 다시 짓는 파일(`tokens.css`, `api/*.md`, `manifest.json`)은 확인에서 빼고 `tokens.json`으로 본다. 이 기능의 첫 올리기 전에는 기록이 없고 맞댈 웹 편집도 없다. 기록은 그 첫 올리기가 처음 쓰고, 편집 켜기는 그 뒤의 마지막 단계라 그 전에는 편집이 꺼져 있다. 판 id는 사람이 고치지 않아도 올라 쓰지 않는다. 이 사실은 위 2026-10-20 이력의 목업 쪽 거꾸로 동기화(판을 대 보아 다르면 웹에서 고친 것으로 본다)에도 닿는다. 판이 달라도 웹 편집이 아닐 수 있으므로 `/ui-design`을 들이는 PR이 목업에서 무엇을 대 볼지 정한다. 페이지에는 그 기록 파일을 고치는 화면이 없다(형식 설명의 파일 표가 표에 없는 경로를 "kept, no UI"로 적는다). 저장소에 더 커밋할 것이 없다.
- **계기.** 기본은 사람이 알리는 것이다. 사용자는 처음에 웹 편집을 근접실시간으로 알기를 원했고, 확인 방식과 주기를 묻자 사람이 알리는 안을 직접 냈다(일지 2026-10-21-12). 웹 편집은 사람이 마감하고 결과를 확인하므로 사람이 알리는 때가 편집이 끝난 때이고, 반쯤 고친 상태를 들일 일이 없다. 사람이 Claude Code에 디자인 시스템을 고쳤다고 말하거나 `/sync-design-system`을 치면 그 세션이 거꾸로 동기화를 한다. 말로 알리는 것은 스킬 설명에 기대고, 그 설명은 스킬 목록 예산이 줄면 빠질 수 있다(ADR 0033의 2026-10-20 이력 "하네스가 스킬을 부르는 자리를 감사하고, 설명에만 기대던 계기를 하네스로 옮긴다"). 그래서 알리지 않은 웹 편집은 셋이 찾는다. 세션이 `web/packages/ui`나 `web/apps/*` 아래 파일을 처음 고치려 할 때 계기 훅이 그 세션에 한 번 확인하라고 알리고(막지 않는다, 선례 `tools/hook_scratch_probe_rule.py`), `/ui-design`은 그리기 전에, 올리기는 보내기 전에 확인한다. 디자인 시스템 패키지를 고치는 일뿐 아니라 앱 화면을 고치는 일도 확인한다. 예약 작업이나 감시 세션은 두지 않는다. 이 계기 훅은 회고가 대기열에서 더하는 훅이 아니라 사용자가 설계 인터뷰에서 정한 것이라, ADR 0036의 더하는 문턱(같은 실수의 세 번째나 손상 한 번)을 거치지 않는다.
- **찾았을 때.** 화면 작업이나 `/ui-design`이 웹 편집을 찾으면 고친 파일과 토큰을 보여 주고 멈춰, 사람이 "먼저 들인다"와 "지금 코드 값으로 계속한다" 가운데 고른다. 먼저 들이면 그 거꾸로 동기화는 자기 티켓과 PR로 따로 병합하고(ADR 0037: PR 하나에 티켓 하나), 화면 작업은 그 병합 뒤 main을 합쳐 잇는다. 계속하면 같은 세션의 화면 작업에서는 다시 묻지 않는다. 올리기가 찾아도 멈춰, 사람이 "먼저 들인다"(거꾸로 동기화를 병합한 뒤 올린다)와 "웹 편집을 버리고 코드로 덮어쓴다" 가운데 고르고, 고를 때까지 올리지 않는다. 올리기의 확인은 화면 작업에서 "계속한다"를 골랐어도 돈다. 그래서 사람이 고르지 않은 디자인 값이 main에 들어가지 않고, 웹 편집이 말없이 덮어써지지도 않는다. 올리기 자리는 인터뷰의 넷째 라운드 설명("고침이 있으면 거꾸로 동기화 PR을 내고 병합한 뒤 올립니다")과 뒤 라운드의 답이 부딪쳐, 셀프 리뷰 뒤 사용자가 멈추고 묻는 쪽을 골랐다(일지 2026-10-21-12).
- **티켓.** 거꾸로 동기화 한 번이 `.scratch/design-reverse-sync/issues/`의 다음 번호 티켓 하나다. 그 세션이 코드를 고치기 전에 티켓을 써서 같은 PR에 싣고(ADR 0037), 브랜치는 `feature/NN-<slug>`다. ADR 0037은 기능 밖에서 제품 코드를 고치는 일을 "그 동작을 만든 기능 폴더"에 두는데, `theme.css`는 design-system이 처음 만들었고(#156) 지금의 테마·색·밀도는 design-refresh의 티켓 03·04가 바꿨다(#216, #221). 글자 그대로 읽으면 폴더가 하나로 정해지지 않으므로, 그 동작을 "웹 편집을 들이는 동작"으로 읽어 그것을 만든 이 기능의 폴더에 둔다. 들인 기록이 한 폴더에 모이고, 이 기능의 구현 티켓과 같은 폴더에 섞인다.
- **옮기는 규칙.** 값 바꾸기(원색, 반투명, 글자 크기, 간격, 모서리)는 스크립트가 `theme.css`의 그 줄로 옮긴다. 이 토큰들은 `theme.css`에 한 번씩만 있어(원색은 테마 블록, 반투명은 뿌리, 크기는 `@theme static`) 사본 블록이 없다. 시스템 다크 같은 사본 블록은 대응과 밀도에만 있어, 사람이 고른 대응 바꾸기를 옮길 때 그 사본까지 함께 고친다(`theme.css`의 블록을 읽었다). 코드에서 한 값을 여러 페이지 테마가 나누는 색(원색은 같은 테마의 라이트·다크, 반투명은 여덟 모두)은 그 벌들이 모두 같은 값으로 바뀌었을 때만 옮기고, 일부만 바뀌었으면 멈추고 묻는다. 코드에는 그 값을 벌마다 나눠 둘 자리가 없다. hex가 아닌 값(oklch 등)은 hex로 바꿔 옮기고 바꾼 값을 보고에 적는다. 쓰임새 토큰이 가리키는 원색을 바꾸는 것(대응 바꾸기), 토큰 더하기·지우기·이름 바꾸기는 멈추고 보여 준 뒤 묻는다. 크기를 바꾸면 그 크기를 박아 둔 스토리 단언도 같은 PR에서 고친다. 크기를 박아 둔 단언이 있다는 것은 단언 모양을 보고 짐작한 어림이다. 기본 테마(녹청)가 쓰는 값(녹청의 원색, 반투명, 크기)을 바꾸면 사진 비교의 정답 사진도 바뀔 수 있으므로, 같은 PR에서 `pnpm -C web visual:update`로 다시 만들고 바뀐 사진을 사람이 보고 PR 본문에 적는다(`.claude/rules/web-design.md`). 마지막 올리기 뒤에 코드와 웹이 같은 토큰을 함께 바꿨으면 멈추고 묻는다.
- **판정.** 옮긴 값은 코드의 판정(여덟 벌의 명암비, axe, 토큰 밖 클래스, 사진 비교)을 지난다. 명암비에 걸리면 걸린 토큰 짝, 실제 명암비, 통과하는 가장 가까운 값을 보여 주고 멈춰, 사람이 "제안 값으로 들인다", "그 토큰만 코드 값으로 되돌린다", "웹에서 다시 고친다" 가운데 고른다. 고를 때까지 걸린 값은 코드에 커밋되지 않고, 그동안 디자인 시스템 올리기도 막힌다.
- **토큰 밖 편집.** README, 지침 문서, 컴포넌트 설명, 그림과 글꼴의 웹 편집도 찾아 무엇이 바뀌었는지 보여 주고, 사람이 "저장소 파일에 옮긴다"와 "버린다" 가운데 고른다. 옮기는 것은 Claude가 평소처럼 원본을 고치는 PR이다. 지침 문서 `web-design.md`의 원본은 Claude Code의 규칙 파일(`.claude/rules/web-design.md`)이라 자동으로 옮기지 않는다.
- **절차의 자리.** 문서 두 곳(`docs/agents/issue-tracker.md` 화면 디자인 절, `.design-sync/NOTES.md`의 돌리는 법)에 흩어진 올리기 절차를 프로젝트 스킬 `/sync-design-system`으로 옮긴다. 스킬이 하는 일은 셋이다. 확인은 웹 편집을 찾아 보여 주고 위 "찾았을 때"대로 멈추며, 계기 훅의 알림을 받은 세션과 그리기 전의 `/ui-design`이 이것만 부른다. 거꾸로 동기화는 사람이 웹 편집을 마치고 알리거나 부를 때와, 확인에서 "먼저 들인다"를 골랐을 때 한다. 올리기는 확인을 먼저 하고, 웹 편집이 없거나 사람이 고른 뒤에 보낸다. 이름은 두 방향(들이기, 올리기)을 모두 말하고, Claude Design용 번들 스킬 `/design-sync`와 앞글자가 다르다.
- **명세가 정할 것.** 셀프 리뷰가 절차의 중간으로 들어오는 갈래를 밟아 찾은 것이다. 방향은 위대로이고, 세부는 명세(`/to-spec`)가 정한다. (1) 확인의 비교: 여러 호출로 나뉜 올리기가 중간에 실패해 기록과 파일이 어긋난 때를 웹 편집과 가르는 법, 첫 올리기 뒤에 기록이 없거나 읽히지 않을 때 멈추는지, 코드와 웹이 같은 토큰을 함께 바꿨는지 가를 기준본(기록에 올린 커밋을 함께 적고 그 커밋의 `theme.css`에서 `tokens.json`만 다시 짓는 길이 있다. 빌린 빌드를 다시 돌리는 아래 거부한 안과는 다르다). (2) 같은 웹 편집을 두 세션이 함께 들이지 않게 하는 법: 거꾸로 동기화 PR이 열렸거나 병합됐지만 다시 올리기 전인 동안에는 기록이 그대로라 다른 세션의 확인도 같은 편집을 찾는다. (3) 계기 훅의 갈래: 거꾸로 동기화를 하는 세션 자신의 쓰기와 사람에게 묻지 못하는 서브에이전트에 알릴지, 컨텍스트 압축이나 인계 뒤에 "고를 때까지 기다림"과 "먼저 들이는 중"을 어디에 남길지. (4) 아티팩트를 읽지 못할 때(지금 계정이 주인도 편집자도 아닐 때 등) 확인이 멈추는지 지나가는지. (5) 반투명과 글자 크기·간격·모서리의 설명 주석 자리. (6) 명암비 계산과 짝 표를 `web/tools`에서 부르는 길(의존을 더하거나 내보내기를 넓힌다).
- 재지 못한 것: 편집을 켠 페이지에서 실제로 저장한 `tokens.json`의 모양(편집이 꺼져 있어 저장해 보지 않았다), 웹에서 고친 값이 컴포넌트 카드에 보이지 않는지, 계기 훅이 `web/` 아래 첫 쓰기에 실제로 실리는지(선례는 스크래치 스크립트의 훅이다), 슬래시 메뉴가 `/sync-design-system`과 `/design-sync`를 나란히 띄우지 않는지(메뉴가 앞글자로 거른다고 본 어림).

거부한 안은 아래다.

- **주기적으로 확인한다.** 아침 보고가 매일, 예약 작업이 낮 시간에 30분마다나 하루 종일 15분마다, 열어 둔 감시 세션이 15분마다 지문을 맞대는 안이다. 사람이 알리지 않아도 찾지만 회차마다 세션 비용이 들고(가벼운 회차도 sonnet으로 하루 $4~19, 어림), 감시 세션은 닫으면 멈추고, 세션 안의 반복 예약은 7일 뒤 만료되어 다시 걸어야 한다(CronCreate 도구 설명을 읽었다). 사람이 마감한 때를 모르므로 반쯤 고친 상태를 가르는 대기도 따로 지어야 한다.
- **고친 사람이 아티팩트 댓글로 Claude를 부를 때만.** 기다리는 비용이 없지만 지켜보는 세션을 늘 열어 둬야 하고, 그 세션의 댓글 자동 응답이 켜져 있어야 한다(켜져 있는지는 보지 않았다). Claude Code에 직접 알리는 것보다 한 단계가 많다.
- **찾으면 기다리는 티켓을 써서 병합해 둔다, 또는 찾은 작업이 거꾸로 동기화까지 한다.** 앞의 것은 ADR 0037의 "작업 전에 티켓만 담아 따로 병합하는 PR은 두지 않는다"에 예외를 만들고, 뒤의 것은 디자인 값이 사람의 확인 없이 main에 들어간다.
- **올리기가 찾으면 묻지 않고 들인 뒤 올린다.** 인터뷰 넷째 라운드의 설명이다. 값만 바꾼 웹 편집이 사람이 고르지 않은 채 main에 들어가고, 기본 테마의 값이 바뀌면 바뀐 사진을 사람이 봐야 해서 결국 사람을 부른다. 셀프 리뷰 뒤 사용자가 멈추고 묻는 쪽을 골랐다.
- **화면 작업의 확인을 디자인 시스템 패키지(`web/packages/ui`)로 좁히거나, 티켓을 시작하는 절차(`implement` 스킬)에 넣는다.** 앞의 것은 앱 화면을 고치는 동안 웹 편집이 들어오지 않은 채 남는다. 뒤의 것은 그 스킬을 사람만 부르게 되어 있어(`disable-model-invocation`) 그 길로 시작하지 않은 작업을 확인하지 않는다.
- **화면 작업이 웹 편집을 찾으면 알리기만 하고 계속하거나, 그 세션이 먼저 들이고 돌아온다.** 앞의 것은 사람이 그 줄을 놓치면 다음 올리기에서야 다시 걸린다. 뒤의 것은 한 세션이 브랜치 둘을 오가 컨텍스트가 커지고 인계가 날 수 있다(어림).
- **정리까지 해 카드에도 바로 보이게 하거나, 올릴 파일 전부를 저장소에서 새로 짓는다.** 웹에서 고친 값이 카드에도 곧바로 보이지만, 정리는 빌린 빌드의 배치와 경로를 어긋나게 하고, 새로 짓는 것은 Storybook에서 카드를 만드는 변환기를 다시 짓는 큰 일이다.
- **Claude가 형식의 안내(`from-code.md`)대로 매번 `tokens.json`을 쓰거나, 웹 편집을 모두 Claude가 손으로 옮긴다.** 짓는 코드가 없거나 어떤 고침이든 받지만, 같은 입력에 같은 결과가 나온다는 보장이 없어 테스트로 판정할 수 없다. 스크립트를 파이썬(`tools/`)에 두는 안은 명암비 공식이 두 언어에 생긴다.
- **대응 바꾸기까지 자동으로 옮긴다.** 네 테마에서 같게 바뀐 대응은 공통 대응으로, 한 테마만 바뀐 대응은 그 테마의 덮기 블록으로 옮기는 안이다. 웹 편집에 따라 `theme.css`의 덮기 블록이 늘고, 덮기를 더할 때마다 그 갈래를 맞대는 판정 사례가 필요하다(`.claude/rules/web-design.md`의 대응과 덮기 문단).
- **판정에 걸린 토큰만 버리고 들이거나, 걸린 값을 예외로 적고 들인다.** 앞의 것은 웹에서 고친 것이 사람의 선택 없이 사라지고, 뒤의 것은 판정을 비켜 가는 길이 생긴다.
- **기본 테마의 라이트·다크 둘만, 색만, `theme.css`의 전부를 낸다.** 둘만이면 군청·자초·쪽빛을 웹에서 보지도 고치지도 못한다. 색만이면 글자·간격·모서리를 웹에서 볼 수 없다. 전부면 밀도 축이 없어 보통 값만 낼 수 있고, 웹에서 고친 보통 값이 촘촘 값과 어긋날 수 있다.
- **토큰 설명을 따로 된 표에 두거나 내지 않는다.** 표는 토큰을 더하거나 이름을 바꿀 때 두 파일을 함께 고쳐야 하고, 내지 않으면 화면을 그리는 에이전트가 토큰의 쓰임을 README에서만 안다.
- **토큰 밖 편집을 원본으로 자동으로 옮기거나 묻지 않고 덮어쓴다.** 앞의 것은 빌드가 짓는 파일마다 원본을 찾는 규칙을 지어야 하고, 뒤의 것은 사람이 웹에서 고친 글과 그림이 말없이 사라진다.
- **지난 올리기 커밋에서 다시 지어 맞대거나, 판 id를 저장소에 커밋한다.** 앞의 것은 빌린 빌드가 짓는 README 같은 파일을 맞대려면 그 커밋에서 빌드를 다시 돌려야 한다. 뒤의 것은 올릴 때마다 판 id를 적는 PR이 하나 더 생기고 무엇이 바뀌었는지 알려 주지 않으며, 판 id는 사람이 고치지 않아도 오른다.
- **거꾸로 동기화만 새 스킬로 하거나, 스킬 없이 문서 절차에 더한다.** 올리기 절차가 문서에 남아 거르는 단계를 건너뛰어도 막는 것이 없고, 스킬이 없으면 사람이 웹에서 고친 뒤 부를 이름이 없다.
- **티켓을 `theme.css`를 처음 만든 design-system 폴더에 둔다.** ADR 0037을 글자 그대로 따르는 한 읽기지만, 지금 값을 정한 design-refresh와는 따로 놓인다. 고른 폴더도 구현 티켓이 끝나면 done인 폴더에 티켓을 더하는 것은 같아, 그것으로는 둘을 가르지 않는다(done 폴더를 어떻게 볼지는 ADR 0037이 명세로 넘겼다).
