# HTTP 채널의 응답은 실행의 이벤트 스트림이고 실행은 연결에 묶이지 않는다

HTTP 채널은 CLI 다음의 두 번째 채널이다. **`POST /runs`는 `{agent, request}`를 받아 `text/event-stream`으로 답하고, SSE 프레임 하나의 `data`는 트레이스 한 줄과 같은 이벤트 JSON 하나다. 스트림은 결말 이벤트(`run_finished`, `run_failed`, `run_paused`)를 보낸 뒤 닫힌다. 실행은 연결에 묶이지 않는다.** 클라이언트가 떠나도 실행은 끝까지 가고 트레이스에 남는다. 승인은 `POST /runs/{run_id}/approval`이 결정을 받아 같은 모양의 스트림으로 재개된 실행을 내보낸다. 연결에 묶지 않는 이유는 연결이 끊기는 것이 전송의 사건이지 사람의 결정이 아니기 때문이다. 취소는 이 기능의 목표가 아니고, 결정 없이 취소를 들이면 실행이 도구를 반쯤 부른 채 기록 없이 사라진다. SSE를 고른 이유는 이 스트림의 소비자가 원격과 프록시 뒤에 설 위젯(슬라이스 4)이기 때문이다. FastAPI 0.141의 `EventSourceResponse`가 keepalive 주석과 버퍼링을 막는 헤더를 붙여 모델 호출이 수십 초 조용해도 연결이 산다. 나중에 미디어 타입을 바꾸는 것은 파괴적 변경이다.

## Considered Options

- **끊기면 실행도 취소한다.** 가장 단순한 구현이 저절로 이것이 된다. 라우트가 `run()`을 그대로 yield하면 FastAPI가 끊김에서 제너레이터를 취소한다(2026-09-24 프로브: 제너레이터가 `CancelledError`를 받았다). `CancelledError`는 `BaseException`이라 `_drive`의 `except Exception`을 지나치므로 `run_failed`가 남지 않고 트레이스는 결말 없음이 된다. 부르던 도구는 실행됐어도 `tool_called`가 없다. 거부했다.
- **시작과 구독을 가른다.** `POST /runs`가 실행 식별자를 돌려주고 `GET /runs/{run_id}/events`로 구독하면 끊긴 스트림에 다시 붙을 수 있다. 그러나 구독 경로는 아무 실행이나 관찰하는 면이 되어 관리와 겹치고(용어집: 관찰은 관리의 일), 떨어진 실행의 관리와 트레이스 꼬리 읽기가 는다. 나중에 경로를 더하는 가산 변경이라 지금 계약을 깨지 않는다. 재접속과 함께 위젯으로 미뤘다.
- **JSONL(`application/jsonl`).** 트레이스 파일과 CLI `--verbose`와 바이트가 같고 openapi의 항목 스키마가 곧 `Event`다. 그러나 keepalive가 없고 중간 장치가 버퍼링할 수 있는 형식이다. 거부했다.
- **WebSocket.** 일시정지는 실행을 끝내는 것이라(ADR 0009) 같은 연결로 결정을 기다릴 일이 없고, 양방향이 쓸 자리가 없다. 거부했다.
- **SSE 프레임에 `event:`와 `id:`를 싣는다.** `event`는 브라우저 `EventSource`가 종류별로 받게 하지만 기본 `onmessage`가 못 받고 종류가 두 곳에 적힌다. `id`는 재접속이 없으면 쓰는 곳이 없고, 재접속을 만드는 날 더하는 것은 가산이다. 거부했다.
- **채널에 승인 요청을 읽는 경로(`GET /runs/{run_id}/approval`).** 다른 사람이 승인할 때 무엇을 승인하는지 채널 토큰만으로 볼 수 있다. 그러나 관찰이 채널로 샌다. 시작한 쪽은 스트림 마지막의 `run_paused`에서, 운영자는 관리 API에서 본다. 거부했다.
- **요청마다 모델을 고른다.** 채널 토큰을 가진 쪽이 비용을 정하게 되고, 모델 플러그인이 예약만 된 지금 이름을 검증할 기준이 없다. 거부했다.

## Consequences

- **스트림에 나간 이벤트는 이미 트레이스에 있다.** `_drive`가 쓰고 나서 내보낸다. 떠난 클라이언트는 나머지를 관리 API의 트레이스 상세로 본다. 스트림과 트레이스는 같은 사실의 두 모습이지 두 사실이 아니다(원칙 V).
- **실행 전 실패는 상태 코드와 에러 봉투로, 실행 안의 실패는 200 스트림 속 `run_failed`로 답한다.** 경계는 첫 이벤트다. CLI가 `PluginError`를 진단으로, `run_failed`를 스트림으로 가르는 것과 같은 경계다. 그러려면 첫 이벤트를 받은 뒤에 응답을 시작해야 한다. yield 라우트는 첫 항목 전에 200을 보내므로, 그대로 쓰면 실행 전 실패가 200으로 시작된 뒤 끊긴 스트림이 된다(2026-09-24 프로브).
- **core의 실행 전 실패가 하위 타입으로 갈린다.** `PluginError` 아래에 부재(없는 에이전트, 없는 실행)와 재개 불가(일시정지 아님, 형식 1)를 둔다. 나머지(깨진 매니페스트, 없는 mcp, 마스킹과 승인의 충돌, 진입점 import 실패, 손상, 결정 이벤트를 쓰지 못함)는 `PluginError` 그대로다. 표가 MRO로 옮긴다 — 부재 404, 재개 불가 409, 그 밖 500. CLI는 기반 타입을 잡으므로 바뀌지 않는다. 일지 2026-09-19의 슬라이스 2 씨앗이 적은 "예외에 HTTP 상태 코드를 두지 않고 채널의 표 하나가 번역(MRO로 조상 상속)"이 이것이다. 채널이 포트와 `run_status()`로 먼저 확인하는 안은 형식 1 판정(`RESUMABLE`)이 core 밖으로 새어 거부했다. core는 여전히 상태 코드를 모른다. 어휘가 는 것은 ADR 0010의 2026-09-24 이력.
- **결정의 본문은 `decision`을 판별자로 한 유니온이다.** `{"decision": "approve"}` 또는 `{"decision": "deny", "reason": "…"}`. 승인에 `reason`이 오면 422, 거부의 사유가 없거나 공백뿐이면 422다. CLI의 `_decision`과 같은 규칙이고 core의 `Deny`가 한 번 더 막는다. 경로 이름이 `resume`이 아니라 `approval`인 이유는 경로가 사람이 주는 입력을 가리키고, 용어집의 승인이 허가와 거부를 함께 담기 때문이다.
- **재개 스트림의 첫 이벤트는 결정 이벤트다.** 재생된 사실은 다시 나가지 않으므로(ADR 0009) 재개 스트림은 결정, `run_resumed`, 새 사실이다.
- **서버가 멈출 때 클라이언트가 떠난 실행은 기다리지 않고 취소한다.** 그 실행은 결말 없음이고, 결말 없음의 정의가 곧 "끝내지 못하고 사라진 실행"이다. 트레이스 쓰기는 동기라 취소가 반쪽 줄을 남기지 않는다. 부르던 도구가 기록 없이 끝날 수 있는 것은 프로세스가 죽은 것과 같다.
- **같은 실행에 결정이 동시에 둘 오면 둘째는 409다. 이것은 불변식이고 테스트가 고정한다.** `resume()`의 첫 걸음(트레이스 읽기, 일시정지 확인, 결정 이벤트 쓰기)에 `await`가 없어 한 이벤트 루프 안에서는 둘째가 마지막 이벤트를 결정으로 읽고 재개 불가가 된다. 그 사이에 `await` 하나가 들어오면 승인된 도구가 두 번 실행되고 트레이스가 섞인다. 워커가 하나라는 것은 `uvicorn.run`에 앱 객체를 넘기는 것이 보장한다(워커가 여럿이면 uvicorn이 import 문자열을 요구하며 시작 실패로 끝난다). **프로세스 사이의 경합은 알려진 한계다.** CLI `resume`과 HTTP 승인이 같은 순간 같은 실행에 오면 둘 다 통과한다. 막으려면 어댑터의 조건부 이어쓰기와 파일 잠금이 필요하고 포트가 바뀐다.
- **모델은 `serve` 수준에서 시작 때 한 번 푼다.** `--model` > `AGENT_OS_MODEL` > 기본값, CLI와 같은 규칙이다. API 키는 시작 때 보지 않고 CLI와 같이 실행 안의 `run_failed`로 드러난다. 모델 플러그인이 생기면 다시 본다.
- **FastAPI의 하한이 오른다.** 락파일은 0.141.1이지만 `pyproject.toml`의 선언은 `fastapi>=0.115`다. `fastapi.sse`에 기대는 순간 그 하한이 거짓이 되므로, 계약 티켓이 하한을 `fastapi.sse`가 들어온 버전으로 올리고 `tech.md`의 HTTP 행과 맞춘다. 의존성을 더하는 것이 아니라 이미 쓰는 것의 선언을 바로잡는 것이다.
- **이번 범위 밖.** 토큰 단위 스트리밍, 취소와 타임아웃, 재접속, 여러 요청을 한 대화로 잇기, 최종 사용자 인증과 CORS와 위젯 설정, 원격 바인딩(ADR 0011 그대로 루프백만), 동시 실행 상한, 실행 목록(관리 API의 `/traces`가 이미 한다). 그중 재접속, 최종 사용자 인증과 CORS와 위젯 설정, 원격 바인딩은 소비자가 있는 위젯이 물려받는다.

## 이력

### 2026-09-24 재개에서 트레이스가 가리키는 에이전트가 없으면 부재가 아니라 `PluginError`다

티켓을 쪼개기 전의 명세 검토가 열었다. 위 Consequences는 부재에 "없는 에이전트"를 넣었고, core에서
매니페스트 부재를 던지는 자리는 `run()`과 `resume()`이 함께 쓰는 한 곳이라 문자 그대로 옮기면 재개에서도
404가 된다. 그런데 재개의 경로가 가리키는 자원은 실행이고 그 실행은 있다. 404는 식별자를 잘못 적었다는
뜻이어야 하고, 깨진 것은 요청이 아니라 서버의 플러그인 루트다.

**`run()`에서 요청이 댄 에이전트가 없으면 부재(404)이고, `resume()`에서 트레이스의 시작 이벤트가 가리키는
에이전트가 없으면 `PluginError`(500)다.** 에이전트가 가리키는 mcp 플러그인이 없을 때와 같은 모양이다 —
이름을 댄 것이 요청이 아니라 서버가 가진 기록이다. 재개 불가(409)를 거부한 이유는 클라이언트가 고칠 수
없는 서버 구성 문제를 4xx로 말하게 되기 때문이다. 재개 불가는 실행 자체의 상태(일시정지 아님, 형식 1)로
남는다. CLI는 기반 타입을 잡으므로 진단도 종료 코드도 그대로다.

### 2026-09-24 서버를 멈출 때 연결이 남은 실행도 유예 뒤에 취소한다

명세가 앱의 수명을 다루는 티켓에게 구현 전에 재라고 넘긴 것을 명세 검토가 쟀다. uvicorn(0.53.0)은 멈출
때 연결마다 닫기를 요청하지만 응답 중인 연결은 닫지 않고, 연결이 전부 끝나거나
`timeout_graceful_shutdown`이 지나야 앱의 수명을 닫는다. 기본값은 제한 없음이다. 실측으로 연결된 SSE
스트림 하나가 끝날 때까지(6.4초) 수명 종료가 오지 않았고, 그동안 클라이언트가 떠난 실행도 계속 돌았다.
위 Consequences의 "클라이언트가 떠난 실행은 기다리지 않고 취소한다"는 연결된 클라이언트가 하나라도 있으면
거짓이었다.

**`serve`는 uvicorn에 유예(`timeout_graceful_shutdown`)를 넘긴다. 유예가 지나면 남은 연결이 끊기고 앱의
수명이 닫히며, 앱이 소유한 실행은 연결이 남았든 떠났든 기다리지 않고 취소된다.** 전부 결말 없음이다.
실측으로 유예 1초에서 1.6초에 연결이 끊기고 수명 종료가 왔다. 유예의 길이는 구현 티켓이 정한다. 기본값
(연결이 끝날 때까지 기다리고 강제는 두 번째 Ctrl+C)은 멈추라는 명령이 실행 하나가 끝나기를 제한 없이
기다리는 모양이라 거부했다. 연결된 클라이언트는 결말 이벤트 없이 닫힌 스트림을 받고, 그것이 "서버가 그
실행을 끝내지 못했다"는 뜻이다. 대가로 uvicorn이 유예를 넘긴 요청 태스크를 취소하며 표준 에러에 ERROR를
찍는다. 이 순서는 앱의 수명을 직접 닫는 테스트로는 잴 수 없어서, `serve`가 uvicorn에 유예를 넘기는 것을
조립 테스트가 판정한다.

### 2026-09-24 계약의 스트림 항목 스키마는 FastAPI의 정형 그대로 둔다

명세 검토가 열었다. FastAPI(0.141.1)는 SSE 라우트마다 정형 스키마를 붙여 `itemSchema`에 `data`(필수)와
`event`·`id`·`retry`(선택)를 싣고, 끄는 인자가 없다. 위 Considered Options가 `event:`와 `id:`를 싣지 않기로
했으므로 계약이 서버가 보내지 않는 필드를 선택으로 광고하게 된다.

**광고를 그대로 둔다. 서버는 `data`만 보내고 테스트가 그 전송을 고정한다.** 지우려면 `server`가 생성된
스키마를 후처리해야 하고, 그 코드는 FastAPI를 올릴 때마다 어긋날 자리가 된다. 선택 필드라 생성
클라이언트가 오지 않는 값을 요구하지는 않는다. 이 불일치는 HTTP 층의 rules 파일에 적어, 계약만 읽은
사람이 `event:`를 보내도록 서버를 "고치지" 않게 한다. 재접속을 만드는 날 `id`가 실제로 실리면 광고와
전송이 맞아진다.
