# 접속 확인은 관리 화면의 플러그인 화면에 두어 켜 둔 원격 MCP 서버와 모델은 화면이 스스로 되풀이해 확인하고 stdio MCP 서버는 운영자가 누를 때만 확인하며, 진단 묶음 명령은 만들지 않는다

ADR 0046은 기준선에 diag-bundle 행(비밀과 최종 사용자 글을 기본으로 싣지 않는 진단 묶음)을 두었고, 그 기능 계획은 판, 구성, 원격 MCP 서버마다의 접속 확인 결과, 최근 실패한 실행의 원인을 파일 하나로 묶는 명령을 적었다. ADR 0049는 원격 MCP 서버에 붙는 길을 정하면서 "접속을 미리 확인하는 길"을 이 행에 넘겼고(결정 "범위 밖"), 어댑터의 서버 하나를 여는 함수(`_opened`)를 접속 확인에 다시 쓸 수 있게 그 경계를 지킨다고 적었다(Consequences "뒤 기능이 기대는 것"). release-image와 postgres-foundation의 명세는 묶음이 적을 판과, `serve`와 `migrate`가 멈출 때 찍는 글을 이 행에 넘겼다. 설계 인터뷰(일지 2026-11-20-1928)는 묶음에 담을 것을 정하려고 시작했다. 그런데 사용자가 첫 라운드에서 파일이라는 모양 자체를 되물었고("이걸 왜 파일로 관리해?? 로그로 남기거나 DB에 저장해야하는거 아니야?"), 다섯 라운드를 지나며 설계의 뿌리가 두 번 바뀌었다. 사용자는 네 자리에서 추천과 다른 답을 골랐다(진단 정보를 내주는 모양, 서버 로그, 꺼 둔 플러그인, 기능의 이름). 선택지 밖의 답도 냈다("근데 DB에 저장할 필요도 없을 것 같은데 로그에 남고 진단 페이지도 필요 없을 것  같아.", "근데 이건 플러그인 메뉴에서 MCP 목록에서 같이 있는게 좋을 것 같은데", "버튼 없이 폴링방식으로 하는건?").

인터뷰 동안 대 본 사실은 다음과 같다. 근거의 종류를 함께 적는다.

- 관리 라우터는 `PluginSource`와 `TraceStore`만 받는다(`src/agent_os/admin/http.py` 112줄의 시그니처와 `src/agent_os/server.py` 65~66줄의 독스트링을 읽었다). ADR 0010의 2026-09-24 이력이 "관리 라우터는 도구 포트를 받지 않는다"고 정했고, 조회 하나가 MCP 서버 여럿을 띄우는 길을 그 시그니처가 닫는다.
- 어댑터의 `_opened(name, server)`는 두 전송을 같은 함수로 연다(`src/agent_os/adapters/mcp.py` 216줄을 읽었다). 그래서 전송이 stdio인 MCP 서버를 확인하면 그 프로세스가 실제로 뜬다. 원격 MCP 서버의 기한은 접속 30초, 읽기 300초다(같은 파일 344줄을 읽었다). stdio에는 여는 동안의 기한이 어댑터 안에 없다(서브에이전트가 코드를 읽은 보고다. 나는 그 파일을 `fail_after|move_on_after|Timeout\(`로 Grep해, 닫을 때의 유예와 원격의 기한 둘만 나오는 것을 봤다).
- `ModelSource`는 모델을 만드는 메서드 하나뿐이고, 만들 때 키도 네트워크도 요구하지 않는다(`src/agent_os/core/ports.py` 478~491줄의 독스트링을 읽었다). 모델 제공사나 모델 서버에 닿는지만 확인하는 함수는 없다(서브에이전트가 `src/agent_os`를 Grep한 보고다). 두 제공사의 파이썬 SDK에 모델 목록을 묻는 기능의 파일이 있다(`.venv` 아래 `anthropic/resources/models.py`와 `openai/resources/models.py`가 있는 것을 Glob으로 봤다). 그 요청에 요금이 붙는지와 로컬 모델 서버가 그 요청에 답하는지는 대 보지 않았다(어림).
- 꺼진 플러그인을 거부하는 판정은 core의 실행 준비에 있고(`src/agent_os/core/run.py`의 `_reject_disabled`가 있는 것을 Grep으로 봤다), 어댑터는 넘겨받은 서버를 모두 연다(서브에이전트가 코드를 읽은 보고다).
- 관리 화면의 플러그인 목록은 첫 페이지(`/`) 한 화면에만 있고, 종류별 구역 넷(에이전트, MCP, 스킬, 모델)이 세로로 놓이며, 행마다 켜고 끄는 스위치와 "매니페스트" 링크가 있다(`web/apps/admin/components/organisms/PluginList.tsx` 전체를 읽었다). 모델만 모아 다루는 화면은 없다(서브에이전트가 코드를 읽은 보고다). 관리 화면의 읽기는 정해진 간격으로 되풀이하지 않고 창으로 돌아올 때 다시 읽는다(`web/apps/admin/hooks/queries/admin/index.ts`의 `revalidateOnFocus: true`와 `refreshInterval: 0`을 Grep으로 봤다). 간격을 두고 다시 읽는 화면은 결정으로만 있다. ADR 0063이 대화 화면에서 아직 도는 실행의 트레이스를 3초마다 다시 읽기로 했고, 그 코드는 아직 없다(`web/apps/admin`의 ts·tsx를 `refreshInterval|setInterval`로 Grep해 위의 한 줄만 나왔다).
- `serve`에서 정해진 간격으로 되풀이하는 작업은 찾지 못했다. 앱의 수명이 소유하는 태스크 그룹은 하나 있고 채널의 실행들을 맡는다(`src/agent_os/channel/http/runs.py`의 `Runs.lifespan`을 읽었다. `channel/http/router.py` 91줄이 그것을 라우터의 수명으로 건다). `src/agent_os`의 `.py`를 `anyio\.sleep|asyncio\.sleep|time\.sleep`으로 Grep해 나온 것은 둘이고, 둘 다 다시 시도의 간격이다(`adapters/postgres/database.py`의 데이터베이스 연결, `adapters/filesystem.py`의 파일 교체).
- 배포 안내(`deploy/standalone/README.md`)는 열두 절이고 "문제 해결"이라는 절은 없다(그 문서의 제목 줄을 Grep으로 읽었다).
- 실행 상세 페이지는 실패 원인을 이미 보이고(`web/apps/admin/components/organisms/EventItem.tsx` 50줄을 Grep으로 읽었다), 플러그인 상세 페이지는 매니페스트 전체를 보인다(서브에이전트가 코드를 읽은 보고다).

**파일로 묶는 진단 명령도, 따로 두는 진단 페이지도, 확인 결과를 담는 데이터베이스 표도 만들지 않는다. 접속 확인(켜 둔 mcp 종류와 model 종류의 플러그인이 가리키는 바깥 서버에 관리가 실제로 붙어 보는 일)을 관리 화면의 플러그인 화면에 둔다. 켜 둔 원격 MCP 서버와 켜 둔 모델은 플러그인 화면이 열려 있는 동안 화면이 정해진 간격으로 스스로 되풀이해 확인하고, 전송이 stdio인 MCP 서버는 그 행의 '접속 확인' 버튼을 운영자가 누를 때만 프로세스를 한 번 띄워 확인한다. 꺼 둔 플러그인은 확인하지 않는다. 확인은 브라우저가 아니라 `serve`가 하고, 화면은 새로 두는 관리 경로를 부른다. 결과는 화면에만 있고 서버 로그에도 트레이스에도 따로 남기지 않는다. `serve`가 뜨지 않아 화면을 볼 수 없을 때는 배포 안내에 새로 두는 '문제 해결' 절이 맡는다. 기능의 이름은 diag-bundle에서 connection-check로 바꾼다.** 계약에서 바뀌는 것은 `openapi.json`이다(관리 경로가 는다). sdk의 매니페스트와 이벤트는 바뀌지 않는다.

인터뷰의 답(고른 라벨과 그 선택지의 설명)과 확인받은 합의 요약 열아홉은 일지 2026-11-20-1928에 글자 그대로 있다. 아래가 그것과 다르게 읽히면 일지가 원천이다. 인터뷰에서는 쉬운 말로 '원격 방식', '프로그램 방식', '폴링'이라고 불렀고, 이 ADR은 그것을 용어집의 말로 옮겼다. 원격 방식의 서버는 원격 MCP 서버이고, 프로그램 방식의 서버는 전송이 stdio인 MCP 서버(플러그인이 프로세스를 실행해 쓰는 서버. 아래에서는 'stdio MCP 서버'라고 적는다)다. 폴링은 "화면이 정해진 간격으로 스스로 되풀이해 확인한다"로 적는다. '플러그인 화면'은 용어집의 말이 아니라, 관리 화면의 첫 페이지(`/`)에 있는 플러그인 목록을 가리키는 말이다. 합의 요약에 없던 것을 이 ADR이 더한 자리는 Consequences의 "합의 요약에 더한 것"에 모았다.

## 결정

- **만들지 않는 것.** 파일로 묶는 진단 명령, 관리 화면의 진단 페이지, 확인 결과를 담는 데이터베이스 표, `serve`가 화면과 무관하게 뒤에서 되풀이하는 확인을 만들지 않는다. 원래 계획이 묶음에 담으려던 것 가운데 구성 보기, 최근 실패 원인, 트레이스의 글 싣기는 이 기능에서 빼고 지금의 화면 그대로 둔다. 구성은 플러그인 상세 페이지가 매니페스트 전체로 보이고, 실패 원인은 실행 상세 페이지가 이미 보인다. 묶음이 없으므로 최종 사용자의 글을 묶음에서 가리는 규칙도 짓지 않는다. 관리 화면은 인증을 지난 운영자만 보고, 운영자는 실행 상세 페이지에서 이미 트레이스 전체를 본다.
- **자리.** 접속 확인은 플러그인 화면의 MCP 구역과 모델 구역의 행에 둔다. 에이전트와 스킬의 행, 플러그인 상세 페이지에는 두지 않는다. 사용자가 진단 페이지 대신 고른 자리다("플러그인 메뉴에서 MCP 목록에서 같이", "모델을 관리할 수 있는 화면에서 같이"). 모델만 모아 다루는 화면은 없으므로 모델 구역의 행이 그 자리다.
- **화면이 스스로 하는 확인.** 켜 둔 원격 MCP 서버와 켜 둔 모델은 플러그인 화면이 열려 있는 동안 화면이 정해진 간격으로 스스로 되풀이해 확인하고, 행마다 상태를 보인다. 운영자가 누를 것은 없다. 간격의 값은 명세가 정한다. 화면을 닫으면 확인도 멈춘다. `serve`가 스스로 시작하는 확인은 없다.
- **운영자가 누르는 확인.** stdio MCP 서버는 행에 '접속 확인' 버튼을 두고, 운영자가 누를 때만 그 프로세스를 한 번 띄워 확인한 뒤 끈다. 화면을 보는 것만으로는 프로세스가 뜨지 않는다. 버튼 뒤에 둔 까닭은 뜨는 것만으로 무언가를 바꾸는 서버가 있을 수 있기 때문이다. 그런 서버라면 그 일이 확인 때도 일어난다.
- **꺼 둔 플러그인.** 확인하지 않는다. 꺼 둔 행은 상태를 보이지 않고, 버튼은 누를 수 없는 모양으로 보인다. 그래서 꺼 둔 MCP 서버는 실행에서도(실행 준비가 꺼진 것을 부른 실행을 거부한다) 접속 확인에서도 뜨지 않는다. 사용자가 고른 선택지의 설명이 이것을 '꺼 둔 것은 어떤 경우에도 뜨지 않는다'고 적었다. 대가는 확인하려면 먼저 켜야 한다는 것이다. 붙지 않는 서버를 켜 둔 사이에 들어온 실행은 실패할 수 있다. 이 판정은 화면이 아니라 `serve`가 한다. 화면이 꺼 둔 행의 요청을 보내지 않는 것만으로는 지켜지지 않는다. 관리 경로를 직접 부르는 요청이 있을 수 있고, 꺼진 것을 거부하는 지금의 판정은 실행 준비에만 있기 때문이다. 접속 확인의 길에 같은 판정을 새로 둔다.
- **확인은 `serve`가 한다.** 브라우저는 MCP 서버나 모델 서버에 직접 붙지 않는다. 화면은 새로 두는 관리 경로를 부르고, `serve`가 붙어 본 결과를 돌려준다. 헤더 값과 키는 `serve`의 환경에만 있고 브라우저로 가지 않는다. 경로의 이름, 요청 하나가 플러그인 몇을 확인하는지, 응답의 모양, 화면이 스스로 하는 확인의 메서드는 명세가 정한다. 명세가 지킬 조건은 넷이다.
  - 느린 서버 하나가 다른 행의 결과를 막지 않는다.
  - 화면이 스스로 하는 확인과 프로세스를 띄우는 확인은 서로 다른 오퍼레이션이다.
  - 프로세스를 띄우는 확인은 조회(GET)가 아니고, 요청 하나가 서버 하나만 연다.
  - 인증은 다른 관리 경로와 같다. 새 경로는 미들웨어의 기본값 뒤에 선다(ADR 0011. 운영자 로그인이 들어오면 ADR 0062의 것이다).
- **MCP 서버를 확인하는 법.** 실행이 서버 하나를 열 때와 같은 단계(접속, 세션 열기, `initialize()`, 도구 목록 읽기)를 지난 뒤 닫는다. 어댑터의 같은 함수를 다시 쓴다(ADR 0049 Consequences "뒤 기능이 기대는 것"). 그래서 확인이 붙었으면 실행도 그 서버를 열 수 있다. 붙지 못한 까닭의 글은 실행이 접속에 실패했을 때 트레이스에 남는 글과 같다(`MCP 서버 <이름>(<명령이나 주소>)에 붙지 못했다: <원인>`. 괄호는 stdio면 매니페스트의 명령이고 원격이면 주소다, `src/agent_os/adapters/mcp.py`의 `_where`. 원격의 모양은 ADR 0049 결정 "실패"). 꺼진 서버와 토큰 불일치는 그 글에서 갈린다. 서버가 돌려준 오류 응답의 상태가 원인 끝에 `(HTTP 401 Unauthorized)`처럼 붙기 때문이다(ADR 0049의 이력과 mcp-http 명세의 "실패 문구"). 닫기는 원격이면 ADR 0049의 닫기를, stdio면 ADR 0034의 프로세스 정리를 그대로 지난다.
- **모델을 확인하는 법.** 모델마다 그 모델 제공사나 모델 서버에 '쓸 수 있는 모델 목록'을 묻는 요청을 한 번 보낸다. 서버가 꺼졌는지, 키가 틀렸는지, 모델에 적어 둔 model id가 그 목록에 있는지를 가른다. 답변을 만들지 않는 요청이다. 붙지 못한 까닭의 글은 명세가 정한다. 그 요청에 요금이 붙는지와 로컬 모델 서버가 그 요청에 답하는지는 대 보지 않았다(어림). 명세의 프로브가 실제로 돌려 확인한다. 요금이 붙거나 그 요청에 답하지 않는 서버가 있으면, 명세를 쓰는 같은 작업에서 그 결과와 함께 이 항목을 이력으로 다시 정한다.
- **기한.** 확인마다 기다리는 시간의 한도를 둔다. 값은 명세가 정한다. 원격 MCP 서버의 접속 기한은 실행과 같은 30초이고(mcp가 자기 클라이언트에 쓰는 값을 어댑터가 적어 넘긴다, `src/agent_os/adapters/mcp.py` 344줄과 그 위의 독스트링), stdio에는 여는 동안의 기한이 어댑터 안에 없어 지금은 실행 기한(기본 600초)만 걸린다. 한도가 없으면 답하지 않는 서버의 행이 그만큼 확인하는 중으로 남는다. 한도에 닿은 stdio 확인은 띄운 프로세스를 ADR 0034의 정리 길로 거둔다.
- **결과가 있는 자리.** 붙었는지와 붙지 못한 까닭(예: 서버가 꺼짐, 토큰이 맞지 않음)을 그 행에 글로 보인다. 결과는 화면에만 있다. 화면을 떠나면 사라지고, 데이터베이스에도 서버 로그에도 트레이스에도 남기지 않는다. 접속 확인은 실행이 아니어서 실행 식별자가 없고 이벤트를 쓰지 않는다. 요청마다 uvicorn이 찍는 접근 기록 한 줄(주소와 응답 코드)은 그대로 남는다(uvicorn의 기본값이 켜짐인 것을 `uvicorn/config.py` 216줄에서 읽었다. 실제 배포의 로그를 본 것은 아니다). 그 줄에는 붙었는지가 들어 있지 않다.
- **붙지 못한 확인은 오류 응답이 아니다.** 붙지 못한 확인과 꺼 둔 플러그인의 확인 요청에는 오류 응답(4xx, 5xx)이 아니라 성공 응답으로 답하고, 결과를 본문에 싣는다. 까닭은 둘이다. 오류 응답은 서버 표준 에러에 실패 한 줄을 남긴다(`src/agent_os/http/errors.py`의 `AssignRequestId`. 서브에이전트가 코드를 읽은 보고이고, 그 줄이 경로와 주체를 적지 않는다는 대목은 내가 다시 읽었다). 화면이 되풀이하는 확인이 꺼진 서버를 만날 때마다 그 줄이 쌓이면 "따로 남기지 않는다"는 답과 어긋난다. 그리고 에러 코드 어휘 여섯(ADR 0010의 2026-10-03 이력)과 "관리 라우트는 409도 429도 내지 않는다"(`.claude/rules/admin.md`)가 그대로 선다. 없는 플러그인(404)과 형식 오류(422)는 다른 관리 경로와 같다.
- **비밀.** 결과의 글에 헤더 값과 키 값을 싣지 않는다(원칙 V). MCP 서버의 글은 실행의 실패 문구가 지나는 가리기(ADR 0049 이력 2026-11-09 "서버가 되울린 헤더 값을 실패 문구에서 가린다")를 그대로 지나고, 모델 쪽 글의 가리기는 명세가 정한다. 주소는 지금처럼 비밀이 아닌 것으로 보아 글에 실린다(ADR 0049 결정 "주소는 매니페스트에 그대로 적는다").
- **포트와 층.** 포트는 다섯 그대로다. `ToolSource`와 `ModelSource`에 접속 확인의 메서드가 는다. 닿는 바깥 지점이 MCP 서버와 모델 제공사·모델 서버 그대로라 새 포트가 아니다(ADR 0012의 기준. 켜짐을 `PluginSource`의 메서드 둘로 둔 것이 선례다, ADR 0017). 관리는 어댑터를 import하지 못하므로(원칙 IV) 관리 라우터가 그 접속 확인을 받아 부르고, `server`가 넘긴다. 관리 라우터는 도구 연결을 여는 길(`ToolSource.connect`)을 여전히 받지 않는다. 받는 것은 접속 확인뿐이다. 화면이 스스로 하는 확인이 부르는 길은 원격 MCP 서버와 모델만 인자로 받게 해, stdio MCP 서버를 넘기는 코드가 타입 검사에서 걸리게 한다. 이 모양(관리 라우터에 포트의 일부만 넘기는 법, 원격 모양만 받는 시그니처)은 pyright로 재 보지 않은 구상이다. 명세의 프로브가 재고, 서지 않으면 같은 성질(화면이 스스로 하는 확인의 길은 프로세스를 띄우지 못한다)을 아키텍처 테스트로 지킨다. 조회(GET) 하나가 프로세스를 띄우지 못한다는 ADR 0010의 성질은 이 시그니처가 아니라 위 결정 "확인은 `serve`가 한다"의 조건(프로세스를 띄우는 확인은 조회가 아니다)이 지킨다. 화면이 스스로 하는 확인의 메서드는 명세가 정하므로 그 길이 조회가 아닐 수 있고, 그래서 두 성질을 따로 지킨다. 이름과 시그니처는 명세가 정한다.
- **`serve`가 뜨지 않을 때.** 관리 화면은 `serve`에서 받아 보이는 앱이라, `serve`가 죽으면 접속 확인도 보이지 않는다. 그때는 배포 안내(`deploy/standalone/README.md`)에 새로 두는 '문제 해결' 절이 맡는다. 그 절은 셋을 적는다. 첫째는 서버에서 칠 명령이다(`docker compose ps`로 어느 컨테이너가 죽었는지 보고, `docker compose logs` 뒤에 서비스 이름을 붙여 그 컨테이너가 남긴 글을 본다). 둘째는 `serve`와 `migrate`가 멈출 때 찍는 글의 뜻이다(글의 목록은 postgres-foundation 명세 "멈출 때의 글"의 표다). 셋째는 지금 떠 있는 판을 읽는 법이다(`.env`의 `AGENT_OS_VERSION`이 띄운 이미지의 태그다. 배포 안내 141줄을 읽었다). 판 번호는 관리 화면에 보이지 않는다. 배포 안내의 4절에는 `migrate`가 멈췄을 때 까닭을 읽는 법과 "띄우기가 끊겼을 때" 소절이 이미 있다(`deploy/standalone/README.md` 133~203줄을 읽었다). 새 절이 그 글을 옮겨 올지 가리키기만 할지는 명세가 정한다. 대가는 둘이다. 멈출 때의 글이 바뀌면 이 절도 함께 고쳐야 하고, 관리 화면만 보는 사람은 판을 알 수 없다.
- **이름.** 기능의 이름을 diag-bundle에서 connection-check로 바꾼다. 묶음이 없어져 옛 이름이 내용과 맞지 않는다. mcp-http의 계획과 ADR 0049가 이 기능의 일을 이미 "접속 확인", "접속을 미리 확인하는 길"이라고 불렀다. 대가는 넷이다. 그 이름을 적은 다른 계획과 명세를 함께 고쳐야 한다. ADR의 본문에는 옛 이름이 남는다. 문서 검색 서버 저장소의 같은 이름 계획(`rag-engine:diag-bundle`)과 이름이 갈린다. 배포 안내에 문제 해결 절을 두는 일은 새 이름에 드러나지 않는다.
- **수락.** 기능의 수락 조건은 "일부러 깨뜨린 배포(모델 서버 꺼짐, MCP 서버 꺼짐, 토큰 불일치)에서 플러그인 화면만 보고 원인을 가를 수 있다"다. 옛 조건의 "묶음만 보고"를 바꾼 것이다.
- **다른 계획에 넘기는 것.** 문서 검색 서버 쪽의 진단과 통합 배포의 관리 명령은 각 계획의 설계에 넘긴다. 통합 배포 계획(`.scratch/deploy-package/plan.md`)에는 agent-os 쪽에 진단 묶음이 없고 접속 상태는 관리 화면에 보인다는 것, 그리고 관리 명령에 진단 항목을 둘지와 문서 검색 서버 쪽 진단을 어떻게 내줄지는 통합 배포의 설계가 그 저장소의 설계를 보고 정한다는 것을 적었다. 문서 검색 서버 저장소의 계획은 건드리지 않고, 그 저장소에서 그 기능의 설계를 시작할 때 정한다(사용자가 고른 선택지의 설명이다. 그 행은 그 저장소의 계획에만 있다, ADR 0048의 2026-11-06 이력). 대가는 그 설계가 서기 전까지 두 저장소의 계획이 서로 다른 방향(한쪽은 화면, 한쪽은 파일 묶음)을 적은 채로 남는다는 것이다.

## Considered Options

- **필요할 때 뽑는 파일(진단 묶음 명령).** 원래 계획이고 인터뷰의 첫 추천이었다. `serve`가 죽은 때에도 쓸 수 있고, 조직 밖의 지원 담당에게 그대로 보낼 수 있다. 사용자가 파일이라는 모양을 되물었고("이걸 왜 파일로 관리해?? 로그로 남기거나 DB에 저장해야하는거 아니야?"), 진단 정보를 내주는 모양으로 "관리 화면의 진단 페이지"를 골라 거부했다. 정보 자체는 어느 쪽이든 로그와 트레이스에 그대로 남는다는 것은 그 질문에 세션이 붙인 설명이다. `serve`가 죽은 때는 문제 해결 절이 맡는다.
- **관리 화면의 진단 페이지와 확인 결과를 담는 데이터베이스 표.** 사용자가 라운드 1에서 골랐다가 라운드 2에서 접었다("근데 DB에 저장할 필요도 없을 것 같은데 로그에 남고 진단 페이지도 필요 없을 것  같아."). 접속 확인을 그 대상을 다루는 화면에 붙이는 쪽을 골랐다.
- **전부 화면이 스스로 확인한다(stdio MCP 서버까지).** 누를 것이 없다. 그러나 화면을 열어 둔 것만으로 stdio 프로세스가 간격마다 뜨고, 조회 하나가 MCP 서버를 띄우지 못한다는 ADR 0010의 성질이 사라진다. 거부했다.
- **화면을 열 때와 창으로 돌아올 때만 스스로 확인한다.** 바깥 서버로 가는 요청이 가장 적다. 그러나 화면을 열어 둔 사이에 꺼진 서버는 다시 읽기 전까지 알 수 없다. 사용자가 간격마다 확인하는 쪽을 골랐다.
- **전부 버튼.** 라운드 2의 추천이었다("버튼을 누를 때만"). "관리 라우터는 도구 포트를 받지 않는다"(ADR 0010의 2026-09-24 이력)에서 가장 적게 벗어난다. 그러나 운영자가 행마다 눌러야 상태를 안다. 사용자가 누르지 않는 방식을 물었고("버튼 없이 폴링방식으로 하는건?"), 원격 MCP 서버와 모델은 화면이 스스로 확인하는 쪽을 골랐다.
- **`serve`가 화면과 무관하게 뒤에서 되풀이해 확인한다.** 화면을 열지 않아도 상태가 쌓인다. 그러나 `serve`에는 정해진 간격으로 되풀이하는 작업이 지금 없고(주기 작업을 맡는 프로세스는 retention-worker부터 든다, `docs/PRD.md`), 결과를 보관해야 하는데 보관은 두지 않기로 했다. 선택지에 올리지 않았다(일지 라운드 3).
- **`/health`가 서버들을 함께 본다, 또는 CLI 명령 `agent-os mcp check`를 둔다.** ADR 0049가 이미 거부했다. 상태 확인마다 모든 서버에 요청이 가고 `/health`의 뜻이 바뀌며, CLI 표면과 테스트가 는다.
- **`serve`가 다른 컨테이너(프록시, 위젯)에도 접속해 보고 화면에 보인다.** 라운드 2의 선택지였다. `serve`에는 Docker 소켓을 얹지 않고(`deploy/standalone/compose.yaml`을 읽었다), `serve`가 죽으면 그 결과도 보이지 않는다. 문제 해결 절의 `docker compose ps`가 맡는다.
- **꺼 둔 플러그인도 확인할 수 있다.** 추천이었다. 켜기 전에 붙는지 볼 수 있어, 붙지 않는 서버를 켜 둔 사이의 실패가 없다. 사용자가 "켜 둔 것만"을 골랐다. 그 선택지의 설명대로 '꺼 둔 것은 어떤 경우에도 뜨지 않는다'가 지켜진다.
- **확인할 때마다 결과 한 줄을 서버 로그에 남긴다.** 추천이었다. 화면을 본 사람이 아니어도 언제 붙지 않았는지 뒤에 알 수 있다. 사용자가 "따로 남기지 않는다"를 골랐다. 대가는 결과를 그때 화면을 본 사람만 안다는 것이다.
- **판 번호를 관리 화면에 보인다.** 관리 화면만 보는 사람이 판을 알 수 있다. 그러나 판을 돌려주는 관리 경로와 화면이 는다. 사용자가 문제 해결 절에 적는 쪽(추천)을 골랐다.
- **브라우저가 직접 붙어 본다.** `serve`에 새 경로가 필요 없다. 그러나 헤더 값과 키가 브라우저로 가야 하고, compose 네트워크 안의 주소(서비스 이름)는 운영자의 브라우저에서 닿지 않는다. 거부했다.
- **붙지 못한 확인을 오류 응답으로 낸다(새 코드나 409).** 응답의 상태 코드만 보고 가를 수 있다. 그러나 에러 코드 어휘를 늘리거나 관리 라우트가 409를 내게 하는 계약 변경이고, 오류 응답마다 서버 표준 에러에 한 줄이 남는다. 거부했다.
- **접속 확인의 새 포트를 하나 만든다, 또는 관리가 자기 Protocol을 선언한다.** 관리가 실행에 쓰는 메서드를 볼 일이 없다. 그러나 닿는 바깥 지점이 그대로라 ADR 0012의 기준으로 새 포트가 아니고, 같은 서버를 가리키는 포트가 둘이 된다. 관리가 자기 Protocol을 선언하는 안은 ADR 0012가 이미 거부했다(도메인별 포트는 두지 않는다). 거부했다.
- **이름을 그대로 두고 설명만 바꾼다.** 추천이었다. 고칠 문서가 가장 적고, 문서 검색 서버 저장소의 같은 이름 계획과 맞는다. 사용자가 "이름도 바꾼다"를 골랐다.

## Consequences

- **계약 변경이 첫 티켓이다.** `openapi.json`에 관리 경로가 늘고, 생성한 TS 타입(`web/packages/api-client`)이 함께 바뀐다. 그 티켓이 다른 티켓을 막는다(`docs/agents/issue-tracker.md`).
- **ADR 0010의 성질이 좁아진다.** "관리 라우터는 도구 포트를 받지 않는다"(2026-09-24 이력)는 "관리 라우터는 도구 연결을 여는 길(`ToolSource.connect`)을 받지 않고 접속 확인만 받는다"가 된다. 조회 하나가 MCP 서버의 프로세스를 띄우는 길이 닫혀 있다는 성질은 그대로다. `GET /plugins`도 여전히 매니페스트만 돌려주고 MCP 서버에 붙지 않는다(ADR 0012). 새로 생기는 것은 둘이다. 관리 쪽 요청이 원격 MCP 서버와 모델 제공사·모델 서버에 네트워크 요청을 보낸다. 그리고 운영자가 누른 요청 하나가 stdio 프로세스 하나를 띄운다.
- **바깥 서버가 받는 것.** 플러그인 화면이 열려 있는 동안 간격마다, 켜 둔 원격 MCP 서버에는 세션 하나가 생겼다 닫히고(실행마다 세션을 여는 것과 같다, ADR 0049 Consequences "서버의 몫") 모델 제공사·모델 서버에는 모델 목록 요청이 간다. 탭과 운영자의 수만큼 곱해진다. 명세가 간격을 정할 때 이것을 함께 본다. 보이지 않는 탭에서 확인을 멈출지도 명세가 정한다.
- **버튼을 연달아 누를 때.** 누른 만큼 프로세스가 뜬다. 같은 플러그인의 확인이 겹칠 때 어떻게 할지(화면이 응답이 올 때까지 버튼을 막는 것으로 둘지, `serve`도 겹침을 줄일지)는 명세가 정한다. 관리 라우트는 409도 429도 내지 않으므로 거절로 풀지 않는다. 운영자는 채널로 실행을 일으켜 같은 프로세스를 이미 띄울 수 있으므로, 접속 확인이 운영자에게 새 권한을 주는 것은 아니다.
- **접속 확인이 보지 못하는 것.** 접속 확인은 "붙는다"를 말하고 "실행이 성공한다"를 말하지 않는다. 서버를 하나씩 확인하므로 두 서버가 같은 이름의 도구를 내는 충돌은 잡지 못한다. 그 충돌은 실행의 `tool_connection` 실패로 드러난다(`src/agent_os/adapters/mcp.py` 165줄의 문구를 Grep으로 읽었다). 모델 목록 요청이 지나도 실제 모델 호출은 실패할 수 있다(사용 한도 같은 것은 어림이다). 승인 규칙 파일이 깨진 것 같은 구성 오류도 접속 확인의 일이 아니다. 접속 확인은 `serve` 프로세스의 환경으로 붙어 본다. `.env`를 고치고 `serve`를 다시 띄우지 않았으면 옛 값으로 확인하고, 실행도 같은 환경을 쓴다.
- **공개 데모.** 공개 계정은 관리자 단계라(ADR 0065) 플러그인 화면을 열고 버튼을 누를 수 있다. 공개 계정은 이미 실행을 일으켜 모델을 부르고 같은 프로세스를 띄울 수 있으므로, 접속 확인이 공개 데모에 새 위험을 더하지는 않는다고 본다(내 판단이다). 화면이 되풀이하는 확인이 모델 제공사에 보내는 요청의 수는 간격과 함께 명세가 본다.
- **구현 티켓이 함께 고칠 자리.** 이 PR은 문서만 고치고 코드와 규칙 파일은 고치지 않는다. 규칙 파일은 지금의 코드를 적은 것이라 코드와 같은 티켓에서 바뀌어야 한다(ADR 0012 Consequences의 첫 항목이 남긴 규약이다). 고칠 자리는 다음과 같다.
  - `.claude/rules/admin.md`의 첫 항목("관리 라우터는 도구 포트를 받지 않는다").
  - `.claude/rules/core.md`의 포트 표에서 `ToolSource`와 `ModelSource`의 행.
  - `src/agent_os/core/ports.py`의 두 포트 독스트링. `ModelSource`의 "메서드는 하나이고 동기다"는 모델을 만드는 메서드의 불변식(준비 단계의 첫 걸음에 `await`가 없다, ADR 0014)이라, 접속 확인의 메서드가 비동기여도 깨지지 않는다. 그 문장을 모델을 만드는 메서드의 것으로 좁혀 적는다.
  - `src/agent_os/server.py` 65~66줄의 독스트링과 `src/agent_os/admin/http.py` 129~134줄의 주석("이 라우터는 도구 포트를 받지 않는다").
  - 배포 안내의 새 절과, 그 문서를 보는 시험(`tests/tools/test_deploy_guide.py`. 무엇을 검사하는지는 읽지 않았다).
  - 플러그인 화면의 행(`web/apps/admin/components/organisms/PluginList.tsx`)과 그 화면의 사진 정답.
- **옛 이름이 남는 자리.** 이 PR이 고친 살아 있는 문서는 기능 계획(폴더째 `.scratch/connection-check/`로 옮겼다), `.scratch/deploy-package/plan.md`, `.scratch/mcp-http/plan.md`, `.scratch/postgres-foundation/spec.md`(사용자 이야기 37, 시험을 다루는 절의 한 문장, Out of Scope의 한 항목), 도구가 만드는 `.scratch/plan.md`다. 끝난 기능의 명세 셋(mcp-http, release-image, local-model)과 일지는 기록이라 고치지 않았다(`docs/constitution/operations.md` 문서 위치). 그 문서들의 diag-bundle은 connection-check로 읽는다.
- **다른 ADR의 본문.** 포인터를 단 것과 달지 않은 것을 ADR마다 가른다(`.claude/rules/adr.md`).
  - **ADR 0010.** 바뀌는 문장("관리 라우터는 도구 포트를 받지 않는다")은 본문이 아니라 2026-09-24 이력에 있다. 지난 이력 항목은 기록이라 포인터를 달지 않고, 그 ADR에 새 이력 항목을 더했다. ADR 0049가 ADR 0009에 한 것과 같다.
  - **ADR 0046.** 기준선 표의 diag-bundle 행은 이름과 한 줄이 모두 바뀐다. 그 ADR의 관례대로 이력에 쌓고 행에 포인터를 달았다.
  - **ADR 0048.** 결정 "배포와 운영은 데이터를 가진 저장소가 맡는다"는 저장소마다 진단을 내고 통합 배포의 관리 명령이 두 저장소의 명령을 차례로 부른다고 적는다. agent-os 쪽에는 진단을 내는 명령이 없어져 그 범위가 바뀌므로 포인터를 달았다.
  - **ADR 0049.** 세 자리에 포인터를 달았다. 굵은 요약의 "재시도와 미리 확인은 없다"는, 실행이 접속하기 전에 미리 확인하지 않는다는 뜻으로는 그대로이지만 운영자가 실행 밖에서 미리 아는 길이 생겨 범위가 바뀐다. 결정 "범위 밖"의 "접속을 미리 확인하는 길(diag-bundle)"과 Consequences "뒤 기능이 기대는 것"의 diag-bundle 문장은 그 길이 이 ADR로 정해졌다. 거부한 안 "꺼진 서버를 미리 아는 길을 지금 둔다"는 그때의 근거라 달지 않았다.
  - **ADR 0012.** "`/plugins`는 매니페스트만 돌려주고 MCP 서버에 붙지 않는다"는 글자 그대로 참이고, 포트가 다섯이라는 것도 그대로라 달지 않았다.
  - **ADR 0063.** 도입 문단은 관리 라우터가 도구 포트를 받지 않는다는 규칙이 그대로라고 적는다. 그 ADR이 그 규칙을 바꾸지 않았다는 그때의 사실이라 달지 않았다.
  - **ADR 0056, ADR 0066.** diag-bundle을 이름으로 든 문장은 거부한 안의 근거(0056)와 그때 한 일의 기록(0066 Consequences "다른 행")이라 달지 않았다.
- **합의 요약에 더한 것.** 사용자가 확인한 요약 열아홉에 없던 것을 이 ADR이 더했다. 승인받을 때 따로 보인다.
  - 붙지 못한 확인과 꺼 둔 플러그인의 확인 요청에 오류 응답이 아니라 성공 응답의 결과로 답한다(결정 "붙지 못한 확인은 오류 응답이 아니다").
  - 포트는 다섯 그대로이고 `ToolSource`와 `ModelSource`에 메서드를 더한다. 새 포트를 만들지 않는다(결정 "포트와 층").
  - 프로세스를 띄우는 확인은 조회가 아닌 요청이고 요청 하나가 서버 하나만 연다. 느린 서버 하나가 다른 행의 결과를 막지 않는다. 화면이 스스로 하는 확인과 프로세스를 띄우는 확인은 서로 다른 오퍼레이션이고, 인증은 다른 관리 경로와 같다(결정 "확인은 `serve`가 한다"의 조건 넷).
  - 요약 ⑲는 ADR 0010의 결정에 "바뀌었다는 표시를 단다"고 적었다. 그 문장이 지난 이력에 있어, 표시는 포인터가 아니라 ADR 0010의 새 이력 항목이다.
  - ADR 0048의 본문 한 문장과 ADR 0049의 굵은 요약 한 문장에 포인터를 달았다(요약은 ADR 0010만 들었다).
  - 주소는 비밀이 아닌 것으로 보아 결과의 글에 실리고, 모델 쪽 글의 가리기는 명세가 정한다(결정 "비밀").
  - 요약 ⑫의 "코드 구조로 막고"는 타입으로 가르는 모양으로 적었다. 그 모양이 pyright에서 서지 않으면 아키텍처 테스트로 지킨다. 타입보다 약한 장치로 물러나는 길이다(결정 "포트와 층").
  - 공개 계정도 접속 확인을 쓸 수 있고, 그것이 공개 데모에 새 위험을 더하지 않는다고 본 것은 내 판단이다(Consequences "공개 데모").
- **용어.** `CONTEXT.md`에 접속 확인을 더하고, 관리의 정의에 접속 확인을 한다는 것을 더했다.
