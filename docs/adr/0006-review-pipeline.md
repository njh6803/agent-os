# 리뷰는 두 단계 세 축이다

리뷰 파이프라인은 세 축이다. 표준·명세(커밋 전 `/code-review`), 보안·버그·성능(PR 직전 CodeRabbit CLI `coderabbit-review` 서브에이전트, 그리고 PR의 CodeRabbit) (바뀜: 이력 2026-10-07 "CLI가 돌지 못하면 보안은 `/security-review`, 버그·성능은 `bug-perf-review`가 PR 직전에 본다"), 유지보수성·경계(PR에서 Claude Code Review). 판단 기준과 심각도의 원천은 `CODING_STANDARDS.md`, 누가 언제 보는지는 `docs/constitution/operations.md`의 "리뷰 파이프라인"이다. 선행 저장소 `ai-agent-platform`의 2단계 파이프라인을 옮기되 이 계정과 플랜에서 실측한 대로 고쳤다.

## 개정 이력

- 2.2.0 (2026-09-20 오전): 선행 저장소대로 PR 봇 둘. CodeRabbit이 보안·성능, Claude가 유지보수성·경계.
- 2.2.1 (같은 날 오후): CodeRabbit PR 리뷰를 끄고 CLI만 남겼다. 사용자 결정. 근거는 PR #2 실측. 비공개 저장소의 Free 플랜은 시트가 없어 Walkthrough 요약만 남기고 체크는 `pass`였고, 둘째 푸시는 "Review rate limited"로도 `pass`였다. 초록만 늘고 리뷰는 없는 봇은 "코멘트 0개인 초록은 리뷰 없음" 규약을 흐린다. 무료 CLI는 주기당 3회라 커밋마다가 아니라 PR마다 한 번이다.
- 같은 날 저녁: Claude Code Review를 공식 플러그인 대신 직접 프롬프트로 바꾸고 "코멘트 0개면 실패" 스텝을 두는 PR #10을 열었다(회고 후보 1. 병합은 Actions 결제 문제가 풀린 뒤). 플러그인은 서브에이전트를 백그라운드로 띄우고 턴을 끝내 짧은 실행 다섯에서 코멘트 없이 초록이 됐다. 단일 에이전트가 요약 코멘트 하나를 `gh pr comment`로 남기는 것이 완료 조건이다.
- 2026-10-07부터의 개정은 아래 `## 이력` 절에 `###`로 쌓는다. `tools/check_adr_pointers.py`가 제목이 `## 이력`인 절만 이력으로 읽는다.

## 버린 대안

CodeRabbit 유료나 공개 전환(PR 봇 둘을 되살린다. 플랜 결정은 사용자 몫으로 남겨 두었다). Claude 플러그인 유지 + 검사 스텝만(문서 PR마다 빨강 소음). 검사 없이 플러그인만(초록 착시 그대로).

## Consequences

- 봇의 초록은 리뷰가 아니다. 병합 전에 코멘트 수를 보고, 코멘트 없는 초록은 `tools/gh_run_summary.py`로 실행 내용을 본다. 워크플로 파일을 바꾼 PR은 액션이 건너뛰므로 별도 PR로 먼저 병합한다. (바뀜: ADR 0021 이력 2026-09-28 "CI의 web 단계는 뼈대와 같은 PR에 들고, e2e도 `verify` 잡이 돈다")
- 셀프 리뷰는 문서만 바뀐 diff에서도 돈다. 첫날 여덟 번에 Major 다섯을 잡았다. 비용은 소스 파일이 없는 diff의 Standards 축을 sonnet으로 돌려 줄인다(code-review 스킬 사본 4단계). (바뀜: ADR 0033)
- 스킬 사본 둘(retro, code-review)이 원본과 다르다. `npx skills update -p`가 덮어쓰면 사본 머리 주석으로 알아챈다.
- 2026-09-21 공개 전환으로 전체 리뷰가 무료가 되자 사용자 결정으로 CodeRabbit PR 리뷰를 다시 켰다(PR #12). PR 봇은 둘이고 역할 분담은 operations.md. 별 10개 미만은 자동 리뷰가 없어 PR마다 `@coderabbitai review`로 부른다. CodeRabbit 체크는 요청이 없거나 한도를 넘어도 `pass`라 필수 검사에 넣지 않는다. 다음에 끌 조건: 비공개로 돌아가거나 봇이 초록만 늘릴 때.
- 2026-09-21 실측(첫 슬라이스 PR #16~#19, #21~#23. #20은 워크플로 PR): CodeRabbit PR 리뷰가 일곱 중 다섯에서 "Review rate limited"로 `pass`가 됐다. 한도가 예외가 아니라 기본 상태다. CLI 슬라이스 리뷰(findings 0)를 각 PR 코멘트로 링크해 대체했고 operations.md에 규약으로 적었다.
- 2026-09-21 정정: 위 2.2.1 항목의 "무료 CLI는 주기당 3회"는 틀렸다. 공식 요금제 문서의 rate limits 표는 CLI를 개발자당 시간당 3회로 적고 롤링 윈도라고 명시한다. OSS PR 리뷰는 별 수에 따라 시간당 1~10회다. 출처를 보지 않고 선행 저장소 기록을 옮긴 것이 원인이다. 결정 자체(커밋마다가 아니라 PR마다 한 번)는 유지하되, 이제 그것은 한도가 아니라 선택이므로 바꾸려면 ADR을 남긴다.

## 이력

### 2026-10-07 CLI가 돌지 못하면 보안은 `/security-review`, 버그·성능은 `bug-perf-review`가 PR 직전에 본다

2026-09-23부터 CLI 좌석이 없어(`Seat: not assigned`, 좌석 배정에는 유료 구독이 필요하다) PR 직전 CLI 축이 비었고,
보안·버그·성능 축은 PR 리뷰의 CodeRabbit 하나였다. 그 CodeRabbit도 시간당 한도에 걸리는 일이 되풀이됐다(대기열 136의
회차 넷, PR #156·#158·#163·#165). 한도는 PR마다, 회차마다 달랐다. #157은 세 회차 가운데 둘째만 리뷰를 받았고, #162는 한도가
풀린 뒤 다시 부른 요청이 리뷰를 받았고, #163은 두 회차 모두 막혔다(일지 2026-10-07-02, 2026-10-07-11, 2026-10-07-15).
PR #163에서는 내장 `/security-review`를 PR 직전에 대신 돌려 관찰 하나를 반영했다(일지 2026-10-07-15). 그 명령은 보안만
본다.

**CLI가 돌지 못하면(미설치, 로그인·좌석 없음, 한도 초과) PR 직전에 대체 둘을 나란히 돌린다.** 보안은 내장
`/security-review`, 버그·성능은 프로젝트 서브에이전트 `bug-perf-review`(`.claude/agents/`)다. 서브에이전트는
`coderabbit-review`와 같은 트리아지(유효·오탐·보류)로 가르고, 지적은 실패 시나리오 하나로 말할 수 있을 때만 낸다. 무엇이
돌았는지와 결과는 PR 체크리스트에 적고, 그것이 PR 리뷰의 CodeRabbit이 한도에 걸린 PR의 보안·버그 축 대체다
(`operations.md` 리뷰 파이프라인). CLI가 돌면 대체는 돌지 않는다. 축 셋과 그 소유는 그대로다.

거부한 안. 한도가 풀린 뒤 `@coderabbitai review`를 다시 부르는 것은 새 파일이 없고 리뷰를 받은 때도 있었지만(#162),
다시 불러도 막힌 때가 있었다(#163). 막히는 까닭은 재지 않았다. 다시 부르기는 지금처럼 해도 되고, 축의 대체를 그것에 걸지
않는다. 사용자 설치 플러그인 `code-review:code-review`는 버그와 `CLAUDE.md` 준수를 신뢰도로 걸러 PR 코멘트로 남기지만,
저장소 밖이라 클라우드 세션에는 없고 성능을 보지 않는다. 대체하지 않고 PR에 "리뷰 없음"을 적는 것은 지금까지의
상태다. 사용자가 서브에이전트를 골랐다(2026-10-07).

### 2026-10-12 리뷰가 한도에 걸린 회차는 병합이 기다리지 않고, 덮인 것과 빈 것을 가려 적는다

PR을 연 뒤의 리뷰가 한도에 걸리는 모양 둘이 되풀이됐고, 그때마다 덮였는지와 기다릴지를 규약이 정하지 않았다.

첫째는 CodeRabbit의 수정 커밋 재리뷰다. 지적을 반영해 푸시하면 전체 재리뷰가 OSS 시간당 한도로 비었지만, 반영한 지적의
스레드에서는 CodeRabbit의 답글이 수정 커밋을 읽고 확인했다고 일지가 적었다. 대기열 41이 센 것은 PR #80·#89·#93·#95·#123의
다섯 번이고, #89에서는 스크립트까지 돌렸다(일지 2026-09-26-05·2026-09-28-03·2026-09-28-07·2026-10-02-04). 같은 모양은 그
밖의 PR에도 있었다(일지 2026-10-01-04). 그때마다 그대로 병합했지만, 한도의 `pass`를 리뷰 없음으로 읽는 규약(`operations.md`
리뷰 파이프라인)은 그것이 리뷰를 받은 것인지 말하지 않았다. 다만 #95의 두 스레드 가운데 하나는 커밋을 읽지 않고 작성자의
답글을 되풀이했다(일지 2026-09-28-07). 분석 체인이 커밋을 읽었는지로 답글을 가른 것은 그 #95뿐이고, 나머지 넷은 그 기준으로
대 보지 않았다.

둘째는 계정의 주간 사용량 한도다. claude-review와 카나리아는 같은 계정의 `claude -p`로 돈다. 그 한도(HTTP 429,
`rate_limit_event`의 `rateLimitType`이 `seven_day`)에 걸리자 claude-review는 리뷰를 시작하지 못하고 빨갛게 끝났고(PR
#166·#172), #172에서는 카나리아의 자식 `claude -p`도 첫 요청에서 막혀 작업 규약 3의 하네스 확인을 병합 전에 하지 못했다.
haiku로도 같았다. 두 번 모두 풀리기를 기다릴지 사람에게 물었고, 사용자는 두 번 다 기다리지 않고 병합을 골랐다. #172에서는
처음에 기다리기로 했다가 CI 결과를 본 뒤 바꿨다(일지 2026-10-07-12·2026-10-11-01). #172가 미룬 카나리아 넷은 한도가 풀린
것을 확인한 뒤(2026-10-12 06:35 KST) 후속 PR #175에서 모두 통과 4였다(일지 2026-10-12-02).

**한도에 걸린 리뷰를 병합이 기다리지 않는다. 대신 그 회차에 무엇이 덮였고 무엇이 비었는지를 가려 적는다.**

- **CodeRabbit의 수정 커밋 재리뷰가 한도로 비면 반영한 지적마다 스레드 답글을 본다.** 답글이 수정 커밋을 직접 읽었으면(분석
  체인이 그 커밋의 파일을 열었거나 그 위에서 스크립트를 돌렸다) 그 지적은 덮였다. 작성자의 답글을 되풀이하기만 했으면
  덮이지 않았다. 수정 커밋에서 지적을 고친 것 밖의 변경은 claude-review가 돌았으면 유지보수성·경계 축으로 보지만, 보안·버그
  축은 그 회차에 비어 있다. 덮인 지적과 덮이지 않은 지적, 비어 있는 축을 PR 코멘트 하나에 적는다.
- **claude-review가 계정 한도로 빨가면 그 빨강은 지적이 아니라 리뷰 없음이다.** 필수 검사 `verify`가 초록이고 다른 리뷰의
  지적을 반영했으면 풀리기를 기다리지 않고 병합한다. 마지막으로 리뷰를 받은 커밋(없으면 없다고)과 풀리는 시각을 PR 코멘트에
  남긴다. 주 체크아웃의 `/git-pr-merge`(사용자 수준 스킬)는 실패한 체크가 있으면 멈추므로, 이때는 주 체크아웃에서도 워크트리의
  병합 길(`next-session`의 "워크트리에서 병합할 때" 1~3)로 병합하고 `tidy-checkouts`가 루트를 main으로 옮긴다. ADR 0005의
  2026-09-29 이력("`/git-pr-merge`로만")과 2026-10-06 이력(워크트리에서 보는 "검사 실패 없음")에 대한 예외다. `--admin`과
  직접 푸시를 쓰지 않는다는 것은 그대로다.
- **카나리아가 계정 한도로 막히면 그 회차는 측정이 아니다.** 통과도 실패도 아니다. `claude`를 띄우지 않는 사전 확인만 돌리고
  병합하며, 그 하네스는 카나리아가 통과할 때까지 확인되지 않은 것이다. 돌릴 명세와 풀리는 시각은 일지의 "다음"에, 병합 전에
  돌지 못했다는 것은 그 하네스를 닫는 대기열 행의 닫힘 표지에 적고, 풀린 뒤의 첫 세션이 그 명세를 돌린다.

축 셋과 그 소유, 한도가 풀린 뒤 `@coderabbitai review`를 다시 불러도 되고 축의 대체를 그것에 걸지 않는다는 것(위 2026-10-07
이력)은 그대로다.

거부한 안. 풀릴 때까지 기다리면 그동안 PR과 그 뒤의 작업이 멈춘다. 두 번 모두 풀리는 시각은 몇 시간 뒤(21:00 UTC)였지만,
주간 한도가 그보다 오래 갈 수 있는지는 재지 않았다.
claude-review와 CodeRabbit은 필수 검사가 아니고, 미룬 카나리아는 후속에서 돌았다(#175). 스레드 답글을 모두 확인으로 보는
것은 #95의 되풀이 답글을 덮인 것으로 센다. claude-review를 본 세션의 서브에이전트로 대신 돌리는 것은 고르지 않았다. 리뷰
관점 넷은 커밋 전 셀프 리뷰의 표준 축(`CODING_STANDARDS.md`)이 이미 보고, 그 위에 리뷰 하나를 더하는 값은 재지 않았다.
사용자가 두 대기열 행을 승인했고(41은 2026-09-28, 165는 2026-10-11), 이 이력은 2026-10-12에 승인했다.
