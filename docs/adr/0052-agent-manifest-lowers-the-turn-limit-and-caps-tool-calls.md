# 에이전트 매니페스트의 선택 칸 둘로 턴의 끝을 낮추고 도구 호출 횟수에 끝을 둔다

`ctx.llm()` 한 번은 모델을 많아야 10번 부른다(`src/agent_os/core/loop.py` 27줄 `MAX_TURNS = 10`, 47~54줄을 읽었다). 에이전트나 매니페스트가 이 끝을 낮추는 길은 없다. 루프는 모델이 한 턴에 낸 도구 호출을 모두 실행하고(같은 파일 52~53줄), 마지막 턴에 낸 호출도 실행한 뒤에 `LoopLimitExceeded`를 던진다. 도구 호출의 횟수에는 끝이 없다. 공개 데모는 토큰 합 상한(token-limit, 슬라이스 11) 없이 실행 하나의 토큰 최댓값을 에이전트의 구조로 묶기로 했고(ADR 0046 이력 2026-11-06 "기준선 열 안에서 공개 데모를 먼저 연다"의 "공개 데모의 비용"), 그 구조의 첫 줄이 "실행 하나의 모델 호출 수의 끝"이다. 기본 에이전트(ADR 0051)는 모델이 스스로 검색하므로 그 끝이 지금은 10이고, 질문에 지시를 섞어 검색을 여러 번 부르게 만드는 것을 막는 장치가 없다. 설계 인터뷰(일지 2026-11-10-1345 라운드 2와 5)에서 사용자가 "에이전트마다 끝을 낮추는 칸 추가"와 "도구 호출 횟수의 끝을 칸으로 더함"을 골랐다. **에이전트 매니페스트에 선택 칸 `max_turns`와 `max_tool_calls`를 더한다. 둘 다 1 이상의 엄격한 정수이고 기본은 없음이다. `max_turns`는 지금의 10이 서는 자리의 끝을 낮추기만 하고, 넘긴 실행은 지금처럼 원인 `loop_limit`으로 끝난다. `max_tool_calls`는 실행 하나에서 도구를 부르는 횟수의 끝이고, 끝을 넘은 호출은 부르지 않고 실패 결과로 모델에 돌려주어 실행은 이어진다. 칸이 없는 에이전트는 지금과 같다.**

## 결정

- **칸 둘.** 에이전트 매니페스트(`PluginManifest`)에 `max_turns`와 `max_tool_calls`를 더한다. 선례는 같은 모양의 선택 칸 `conversation_limit`이다(`sdk/manifest.py` 208~216줄을 읽었다. ADR 0022). 1 이상의 엄격한 정수만 받고(0, 음수, 불린, 숫자 문자열, 실수는 매니페스트를 읽는 단계에서 거부한다), 에이전트가 아닌 종류가 적으면 `requires_approval`처럼 거부한다. 기본은 없음이고 숫자 기본값을 매니페스트에 두지 않는다. 두면 그 숫자가 직렬화 스키마와 관리 API의 매니페스트 응답에 박혀 기본값을 바꾸는 것이 계약 변경이 된다(`.claude/rules/sdk.md`). 없음을 읽는 것은 core의 몫이다. 선택 칸이라 `schema_version`은 `"1"` 그대로다.
- **`max_turns`.** 지금의 10이 서는 자리와 같은 자리의 끝이다. `ctx.llm()` 한 번의 루프가 도는 턴의 수이고, 재개하면 처음부터 다시 세어 재생된 턴도 센다(ADR 0009). 없으면 core의 10이다. 낮추기만 한다. 10을 넘는 값은 그 에이전트의 실행이 시작되기 전에 거부한다. 10보다 올리는 것은 ADR 0009가 "상한을 올리는 별도 결정"으로 남겨 둔 것이고 이 ADR은 그 결정을 하지 않는다. 끝을 넘긴 실행은 지금의 10턴 초과와 똑같이 `LoopLimitExceeded`가 나고 원인 `loop_limit`의 `run_failed`로 끝나며 답이 나오지 않는다. 대화 요약의 모델 호출은 지금처럼 턴에 들지 않는다(`.claude/rules/core.md`의 대화 요약 항목).
- **`max_tool_calls`.** 실행 하나에서 도구를 부르는 횟수의 끝이다. 없으면 끝이 없다(지금과 같다). 세는 자리는 도구를 부르는 한 자리 `_call`이다(`core/run.py`). 루프가 부르는 호출과 에이전트가 `ctx.tool()`로 직접 부르는 호출이 같은 길을 지나므로(`.claude/rules/core.md`의 승인 게이트 항목) 같은 셈에 들고, `ctx.llm()`을 여러 번 부르는 에이전트에서도 실행 전체로 센다. 재개하면 재생된 호출도 센다. 턴의 끝과 같은 이유다. 멈추고 재개하기를 되풀이해 셈을 비울 수 있으면 끝이 아니다(ADR 0009).
- **끝을 넘은 도구 호출.** 부르지 않고 `tool_called(ok=false)`로 "횟수를 넘었다"는 결과를 모델에 돌려준다. 운영자가 막은 도구를 다루는 지금의 길과 같은 모양이다(`core/run.py` 615~618줄, `_refuse`). 실행은 실패하지 않고, 모델은 이미 받은 결과로 답한다. 직접 부른 에이전트는 지금의 거부와 같이 `ToolError`를 받는다. 모델이 그 뒤에도 도구만 내면 턴이 소모되어 `loop_limit`으로 끝난다.
- **턴의 끝만으로는 모자란 이유.** 루프가 한 턴의 도구 호출을 모두 실행하므로, 턴의 끝이 3이어도 모델이 한 턴에 검색을 여러 개 내면 그 수만큼 불린다. 턴의 끝은 모델 호출의 수를, 도구 호출의 끝은 도구 결과가 입력에 쌓이는 횟수를 묶는다.
- **기본을 읽는 자리.** 없음을 10과 끝 없음으로 읽는 것은 core다(`MAX_TURNS`, 기본 대화 한도 `DEFAULT_CONVERSATION_LIMIT`, 기본 실행 기한과 같은 자리).
- **계약.** sdk의 매니페스트 모델이 바뀌고, 매니페스트는 관리 API의 응답 타입 그대로라 `openapi.json`과 api-client의 생성물이 함께 바뀐다(`openapi.json`에 `conversation_limit`이 이미 실려 있다. Grep으로 봤다). base-agent의 첫 티켓이고 그 기능의 다른 티켓을 막는다(`CLAUDE.md` 작업 규약 2).
- **명세가 정할 것.** 다음은 이 ADR이 정하지 않는다.
  - 무엇을 한 번으로 세는가. 운영자가 거부한 호출, 연결에 없는 이름, 승인자가 거부한 호출, 도구가 실패한 호출을 세는지다.
  - 셈과 승인의 차례. 끝을 넘은 호출이 승인 대상이면 묻기 전에 거부해야 질문한 사람이 쓸모없는 승인을 하지 않는다(어림. 코드로 대 보지 않았다).
  - 끝을 넘은 호출의 `tool_called.rule` 값과 문구. `rule`은 닫힌 목록 다섯의 `AppliedRule`이라 값을 더하면 계약의 가산 변경이고, 연결에 없는 이름처럼 비우는 선례가 있다(`core/run.py` 613줄).
  - 10을 넘는 `max_turns`를 어느 층이 보는가. sdk가 읽는 단계에서 보면 10이 sdk에도 적혀 core의 `MAX_TURNS`와 두 곳이 되고, core가 실행을 준비할 때 보면 매니페스트는 읽히지만 그 에이전트의 실행이 시작 전에 거부된다. 어느 쪽이든 실행 식별자가 생기기 전이다.
  - 기본 에이전트가 적을 값(ADR 0051).

## Considered Options

- **지금의 10번 그대로 두고 스킬에만 적는다.** 계약을 바꾸지 않는다. 거부했다. 스킬의 "검색은 두 번까지"는 강제력이 없고, 공개 데모는 최대 비용을 10번 기준으로 셈해야 해서 같은 예산이면 시간당 허용 실행 수를 더 낮게 잡아야 한다.
- **끝에 닿으면 도구를 떼고 한 번 더 불러 답하게 한다.** 최종 사용자가 실패 안내를 덜 본다. 거부했다. 런타임 루프의 동작이 바뀌어 범위가 커지고, 멈춘 실행을 재개할 때의 재생 대조에 영향이 있을 수 있다(어림. 코드로 확인하지 않았다).
- **한 턴에 도구 하나로 제한한다.** 모델에 "도구는 한 번에 하나만"이라는 설정을 넘긴다. langchain-anthropic의 `bind_tools`는 `parallel_tool_calls` 인자를 받는다(주 체크아웃의 설치본 `langchain_anthropic/chat_models.py` 2326줄과 2512~2521줄을 Grep으로 봤다. 설치본의 판은 보지 않았다). 거부했다. 그 보장은 모델 제공사의 설정에 기대어 다른 제공사의 모델(local-model)이 오면 다시 확인해야 하고, 실제 모델이 그 설정을 지키는지도 확인하지 않았다. 런타임이 직접 세면 제공사가 바뀌어도 같은 보장이 남는다.
- **도구 호출의 끝을 스킬의 지시로만 묶는다.** 거부했다. 질문에 지시를 섞어 모델이 검색을 여러 번 부르게 만들면 실행 하나의 토큰이 셈한 최댓값을 넘고, 그 초과분은 모델 API 계정의 사용 한도만 받는다. token-limit은 슬라이스 11이라 그 전에는 다른 방어가 없다.
- **끝을 넘은 도구 호출에서 실행을 실패로 끝낸다.** 턴의 끝과 같은 모양이라 단순하다. 고르지 않았다. 이미 찾은 근거로 답할 수 있는 실행을 버리게 되고, 운영자의 deny가 이미 "부르지 않고 모델에 돌려준다"는 길을 쓴다.
- **`max_turns`로 10보다 올리는 것도 받는다.** 고르지 않았다. 상한의 목적은 비용이 무한정 늘지 않게 하는 것이고(ADR 0009), 올리는 것은 에이전트 저자가 아니라 런타임의 결정이다.

## Consequences

- **칸이 없는 에이전트.** calc를 비롯해 칸을 적지 않은 에이전트는 지금과 같다. 턴은 10이고 도구 호출에는 끝이 없다.
- **실패 문구.** `LoopLimitExceeded`의 문구(`루프가 {MAX_TURNS}턴 안에 멈추지 않았다`)는 그 실행에 걸린 끝을 싣게 된다. ADR 0031의 2026-10-16 이력이 `loop_limit`의 뜻을 "10턴 안에 멈추지 않아"로 적은 것은 지난 이력의 기록이라 고치지 않는다. 뜻(루프가 끝 안에 멈추지 않았다)은 같다.
- **승인이 끼는 실행.** 승인으로 멈췄다 재개한 실행은 재생된 턴과 호출을 다시 세므로, 승인 한 번이 끝을 더 주지 않는다. 승인이 여러 번 끼는 에이전트는 그 수를 넣어 값을 정한다.
- **공개 데모의 비용 셈.** "실행 하나의 모델 호출 수의 끝"이 10이 아니라 그 에이전트의 `max_turns`가 되고, 검색 횟수가 `max_tool_calls`로 묶인다. 입력 토큰은 여전히 조각 하나의 크기와 조각 수까지 알아야 묶인다(public-demo 기능 계획).
- **커스텀 에이전트.** 기본 에이전트를 복사한 커스텀 에이전트는 매니페스트에서 두 값을 고쳐 쓴다(ADR 0051). 올릴 수 있는 것은 `max_tool_calls`이고 `max_turns`는 10까지다.
- **구현 티켓이 함께 고칠 문서.** `.claude/rules/core.md`의 "루프 상한은 10턴이고 실행 전체 기준이라 재생된 턴도 센다"와 승인 게이트 항목(도구 호출의 셈이 서는 자리), `.claude/rules/sdk.md`의 에이전트 매니페스트 선택 칸, `core/loop.py`의 모듈 독스트링이다. 하네스는 다음 실행에 바로 영향을 주므로 같은 티켓에서 고친다(`CLAUDE.md` 작업 규약 4).
- **다른 ADR의 본문.**
  - **ADR 0009.** Consequences의 "**`MAX_TURNS = 10`은 실행 전체 기준이고 재생된 턴도 센다.**"로 시작하는 항목에 `(바뀜: ADR 0052)`를 단다. 세는 방식(실행 전체, 재생된 턴 포함)과 "상한을 올리는 별도 결정"은 그대로이고, 바뀐 것은 범위다. 10은 끝의 천장이고 에이전트가 그보다 낮출 수 있다.
  - **ADR 0022.** `conversation_limit`은 선례로 들 뿐 바뀌지 않는다.
  - **ADR 0031.** 위 "실패 문구"대로 달지 않는다.
  - **ADR 0044.** 적용 규칙의 다섯 값은 이 ADR로 바뀌지 않는다. 끝을 넘은 호출의 `rule`을 명세가 새 값으로 정하면, 그 명세를 쓰는 작업이 ADR 0044의 이력과 포인터를 단다(`.claude/rules/adr.md`).
