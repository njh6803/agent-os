# 모델은 플러그인이고, 런타임이 실행마다 그 매니페스트를 읽어 모델을 만든다

지금 모델은 프로세스 하나에 하나다. `main.py`가 `--model` > `AGENT_OS_MODEL` > 코드의 기본값(`adapters/anthropic.py`의 `DEFAULT_MODEL`, `claude-opus-5`) 순으로 이름을 풀어 `ChatAnthropic` 하나를 만들고, `run()`·`resume()`과 `serve`가 그 인스턴스를 쓴다(ADR 0014, ADR 0010 이력. 코드를 읽었다). 플러그인 종류 `model`은 디렉터리와 값만 예약되어, `plugins/models/`에 파일을 두면 관리 목록에 뜨고 켜고 끌 수 있지만 런타임이 읽지 않아 효과가 없다(ADR 0017). PRD의 운영자는 "어떤 에이전트, 도구, 모델이 등록돼 돌아가는지 한 곳에서 보고 켜고 끄고" 싶어 하고, `.scratch/plan.md`의 프론티어가 비어 PRD 범위에서 다음 기능을 고르는 설계 인터뷰가 이 결정을 내렸다(일지 2026-10-31-04). **모델은 `plugins/models/<이름>/plugin.toml`의 플러그인이다. 에이전트는 매니페스트의 선택 칸 `model = "<플러그인 이름>"`으로 모델을 고르고, 없으면 기본 모델을 쓴다. 기본 모델은 `--model` > `AGENT_OS_MODEL` 순으로 받는 모델 플러그인의 이름이고, 코드의 기본값은 없어진다. 런타임은 실행을 준비할 때마다 그 이름의 모델 매니페스트를 읽어 그 설정으로 모델 객체를 만든다.** 그래서 모델 파일을 고치거나 켜고 끈 것이 서버를 다시 띄우지 않아도 다음 실행부터 듣고, 에이전트마다 다른 모델을 쓴다. `ctx.llm()`은 그대로 프롬프트 하나를 받는다.

## Considered Options

- **서버를 다시 띄울 때 읽는다.** `serve`가 시작할 때 모델 플러그인을 모두 읽어 모델 객체를 만들어 두고 실행은 그 지도에서 고른다. 모델 객체를 실행마다 만들지 않고 포트가 그대로다. 그러나 파일을 바꾸면 다시 띄워야 하고, 켜고 끄기를 다음 실행부터 듣게 하려면 시작 때 만든 지도에서 꺼진 것을 거르는 판정이 따로 서서, 실행마다 파일에서 읽는 에이전트·MCP 매니페스트(파일시스템이 원천인 ADR 0003. 실행마다 읽는 것은 `core/run.py`의 `_requested_manifest`·`_resolve_servers`다. 코드를 읽었다)와 반영 시점이 갈린다. 거부했다.
- **요청마다 모델을 고른다.** ADR 0014가 거부한 안이다. 이름을 검증할 기준(모델 플러그인)은 이제 생기지만, 채널 토큰을 가진 쪽이 비용을 정하게 되는 것은 그대로라 거부를 유지한다.
- **모델 파일에 제공사와 id만 둔다.** 파라미터는 코드의 고정값 그대로다. 이 세션이 추천했고 사용자가 고르지 않았다. 같은 id에 파라미터만 다른 설정을 두 플러그인으로 등록할 길이 없다.
- **`ChatAnthropic`이 받는 필드를 모두 둔다.** 설치된 langchain-anthropic 1.7.2의 `ChatAnthropic.model_fields`는 36개다(`uv run python -c`로 셌다). 생성 파라미터(`top_p`, `top_k`, `stop_sequences`, `thinking`, `reasoning_effort`), 호출 설정(`timeout`은 `default_request_timeout`의 별칭이다, `max_retries`, `streaming`), 제공사에 그대로 넘기는 칸(`model_kwargs`, `betas`, `default_headers`) 같은 것이다. 칸마다 검증과 시험이 늘고, 제공사가 늘면 제공사마다 받는 칸이 달라 종류별 규칙이 지금 필요해진다. 거부했다. `max_tokens`와 `temperature` 둘만 두고 나머지는 가산 변경으로 미룬다.
- **둘째 제공사를 지금 들인다.** 새 langchain 통합 패키지(`tech.md` 개정)와 제공사별 API 키 환경변수·파라미터 규칙이 지금 생기고 실제 모델을 부르는 시험이 제공사마다 늘어난다. 거부했다. `provider`는 닫힌 목록이고 지금은 `anthropic` 하나다.
- **시작 이벤트에 모델 플러그인 이름을 남긴다.** 선택 칸이라 트레이스 형식은 3 그대로지만(선택 칸을 더하며 형식을 그대로 둔 선례는 ADR 0031과 ADR 0009의 2026-09-22 이력이다. ADR 0022는 재개의 입력이 되는 이벤트가 늘어 3으로 올린 쪽이다), 이벤트가 관리 API 계약이라 `openapi.json`·생성 타입·관리 화면의 필드 이름 표가 바뀌고, 재개는 지금 디스크의 매니페스트를 읽으므로 기록된 이름과 재개가 부른 모델이 다를 수 있다. 거부했다. 트레이스는 지금처럼 응답이 돌려준 실제 모델 이름(`llm_called.model`, `conversation_summarized.model`)을 남긴다.
- **기본 모델을 시작 때 보지 않는다.** API 키처럼 그 이름을 쓰는 첫 실행에서 드러나게 둔다. 오타를 첫 요청이 실패할 때까지 모른다. 거부했다.
- **기본 플러그인의 이름을 `opus`나 `default`로 한다.** `opus`는 3라운드의 추천 선택지였으나 버전이 다른 opus를 나란히 등록하지 못해 사용자가 선택지 밖의 답으로 물렸고, `default`는 같은 질문의 셋째 선택지였고 그 설명이 견줬다(세 선택지는 일지 2026-10-31-04의 "PR 직전 리뷰" 절). 운영자가 `--model`로 고른 기본 모델과 말이 겹쳐 이름이 `default`인 플러그인이 기본이 아닌 상태가 생기고, 둘째 모델 플러그인을 들이면 이름이 내용을 말하지 않는다. 거부했다. 이름은 제공사의 id 그대로 `claude-opus-5`이고 다음 버전은 `claude-opus-5-5`다. 플러그인 이름 패턴(`sdk/ids.py`, 소문자·숫자·하이픈)이 점을 받지 않아 `opus5.5` 같은 이름은 애초에 쓸 수 없다.
- **모델 파일의 id 칸을 `model`이나 `id`로 한다.** `model`과 `id`는 3라운드 같은 질문의 선택지(`provider, model`·`provider, id`)였고 그 설명이 견줬다(같은 일지의 "PR 직전 리뷰" 절). `model`은 에이전트 매니페스트의 `model`(플러그인 이름)과 같은 키가 파일 종류에 따라 다른 뜻이 되고, `id`는 `name` 곁에서 어느 것이 관리 목록의 이름이고 어느 것이 제공사에 보내는 값인지 헷갈린다. 거부했다. 용어집의 말대로 `provider`와 `model_id`다.

## Consequences

- **모델 매니페스트의 모양.** 공통 넷(`schema_version = "1"`, `kind = "model"`, `name`, `version`)에 `provider`(닫힌 목록, 지금은 `"anthropic"`), `model_id`(제공사에 보내는 모델 이름), 선택 `max_tokens`(1 이상의 엄격한 정수. 없으면 어댑터의 16000, 지금의 고정값), 선택 `temperature`(0 이상 1 이하의 엄격한 실수. 없으면 제공사 기본값)다. 둘 다 `conversation_limit`처럼 엄격 검증(`strict=True`)이라 범위 밖의 값, 불린, 숫자 문자열, 다른 종류의 매니페스트에 적힌 이 칸들은 매니페스트를 읽는 단계에서 거부한다. `max_tokens`는 실수(`2.0`)도 거부하고, `temperature`는 pydantic 2.13.5의 엄격한 실수가 정수를 받으므로 TOML의 `0`·`1`을 `0.0`·`1.0`으로 받는다(`uv run python`으로 `True`·`"0.5"`의 거부와 `0`·`1`의 수용을 봤다). 에이전트 매니페스트의 `model`은 플러그인 이름 패턴의 선택 칸이고 다른 종류에서는 거부한다. 공통 넷만 적은 모델 매니페스트(`tests/test_server.py`의 `SONNET`, 관리 화면 e2e 스택의 `models/sonnet` 픽스처가 그 꼴이다)는 필수 칸이 없어 같은 단계에서 거부되고, 그 픽스처는 구현 티켓이 고친다. 기존 칸의 뜻과 필수 여부가 바뀌지 않으므로 `schema_version`은 "1" 그대로다(ADR 0008 이력). API 키는 모델 파일에 담지 않고(용어집의 모델) 지금처럼 제공사의 환경변수(`ANTHROPIC_API_KEY`)이며 시작 때 보지 않는다.
- **준비 단계에 모델 판정이 는다.** 실행마다 에이전트의 `model`(없으면 기본 모델의 이름)로 `PluginSource.read_manifest(MODEL, 이름)`을 부른다. 포트에 메서드가 늘지 않는다. 없거나 읽히지 않으면 없는 mcp와 같은 `PluginError`(운영자 면 500, 최종 사용자 면 고정 문구 500)이고, 꺼졌으면 `Disabled`(409)다. 지금의 순서 부재 → 깨짐 → 꺼짐(에이전트 → mcp) → import에서 꺼짐이 에이전트 → mcp → 모델이 된다. 재개도 같은 준비를 지나 지금 디스크의 매니페스트가 가리키는 모델을 쓴다(mcp와 같다. `resume()`이 `_recorded_manifest`로 읽는다). 대화 요약은 그 실행의 모델 그대로다(ADR 0022). 기본 모델의 이름이 core에 드는 입구(`run()`·`resume()`의 새 인자인지, 모델을 만드는 것이 이름을 드는지)와 모델의 없음·깨짐이 깨짐 안에서 mcp의 앞인지 뒤인지는 명세가 정하고 시험이 고정한다. `.claude/rules/core.md`의 준비 순서 문장과 `Disabled`를 적는 문장(에이전트와 그 mcp까지만 든다)은 구현 티켓이 고친다.
- **core의 모델 포트가 "모델 하나"에서 "모델 설정으로 모델을 만드는 것"으로 바뀐다.** 지금 `type ChatModel = BaseChatModel`(`core/ports.py`)을 `run()`·`resume()`이 인스턴스로 받는다. 이제 모델 매니페스트를 받아 `BaseChatModel`을 돌려주는 것을 받고, `adapters/anthropic.py`의 factory가 `provider = "anthropic"`의 구현이며 `main.py`가 조립한다. core가 닿는 지점은 그대로라 포트는 다섯 그대로다(ADR 0012). 모델 객체를 실행마다 만든다. 만드는 것이 네트워크를 타지 않는다는 것은 어림이고 구현 티켓이 본다. `.claude/rules/core.md`의 포트 표와 `.claude/rules/adapters.md`의 "`main.py`가 만든다"는 구현 티켓이 고친다.
- **기본 모델.** `--model`과 `AGENT_OS_MODEL`의 이름과 우선순위는 그대로이고 값이 모델 플러그인의 이름이다. 둘 다 없거나 비었거나 그 이름의 모델 매니페스트가 없거나 읽히지 않으면 구성 오류다. `serve`는 토큰·호스트·사이트 파일 문제와 한 목록(`main.py`의 `_configuration_problems`)으로 시작 때 내고(사이트 파일을 시작 때 한 번 읽는 ADR 0023과 같은 자리), CLI `run`·`resume`은 지금 빈 이름을 거부하는 자리에서 끝난다. 꺼짐은 시작 때 보지 않는다. 운영자가 언제든 바꾸는 상태라 그것을 쓰는 실행이 409다. 시작 때 읽은 것은 확인에만 쓰고 실행은 실행마다 다시 읽는다. 대가로 시작이 플러그인 폴더를 한 번 읽는다. 지금 `serve` 시작은 `FilesystemPlugins`를 만들기만 하고 읽지 않는다(코드를 읽었다). ADR 0014와 ADR 0010 이력의 "시작 때 한 번 푼다"가 바뀐다.
- **저장소가 기본 모델 플러그인 하나를 둔다.** `plugins/models/claude-opus-5/plugin.toml`이고 `model_id = "claude-opus-5"`, `max_tokens = 16000`으로 지금 동작 그대로다. `plugins/agents/calc`는 `model` 칸 없이 기본 모델을 쓴다. 격리된 플러그인 루트로 `serve`를 띄우는 시험과 CI, 두 e2e 스택은 그 루트에 기본 모델이 가리키는 모델 매니페스트를 두고 그 이름을 `AGENT_OS_MODEL`이나 `--model`로 넘긴다. 두 스택(`web/apps/admin/e2e/stack.ts`, `web/apps/widget/e2e/stack.ts`)은 지금 `--plugins-root`로 임시 루트에 픽스처 플러그인을 쓰고 `--model` 없이 띄워 기본값에 기대며, 관리 스택의 모델 픽스처 `models/sonnet`은 공통 넷뿐이라 새 규칙에서 읽히지 않는다(코드를 읽었다). 이름만 넘기면 `serve`가 시작 때 구성 오류로 끝난다. 어느 이름을 둘지는 명세가 정한다. `-m llm` 시험은 그 플러그인으로 실제 모델을 부른다.
- **계약이 바뀐다.** 매니페스트는 관리 API의 응답 타입이라 `openapi.json`의 `PluginManifest`에 새 칸이 들고, 생성 타입과 스토리·테스트의 매니페스트 리터럴이 바뀐다. 관리 API의 경로는 늘지 않는다. 목록·상세·켜고 끄기가 네 종류를 이미 다룬다. 관리 화면은 `PluginList.tsx`의 "로더 없는 종류" 집합에서 model을 빼 안내 줄을 걷고, 상세는 지금처럼 매니페스트 JSON 그대로다. 화면 디자인 단계(`ui-design`)는 없다. 첫 티켓이 계약 티켓이다.
- **트레이스는 바뀌지 않는다.** 이벤트 형식 3 그대로이고 `llm_called.model`과 `conversation_summarized.model`은 응답이 돌려준 실제 모델 이름이다. 같은 id에 파라미터만 다른 두 플러그인은 트레이스로 가르지 못한다.
- **이번 범위 밖.** 토큰 단위 스트리밍(ADR 0014 그대로), 요청마다 모델 고르기(거부 유지), 둘째 제공사(`provider` 목록에 값을 더하는 가산 변경), 나머지 파라미터와 `thinking`·`model_kwargs`, 대화 한도의 모델별 기본값(ADR 0022가 모델 플러그인 때 다시 보기로 한 것. 다시 봤고 넣지 않는다, 그 이력), 스킬 로더. `.claude/rules/sdk.md`의 "첫 슬라이스는 `kind`와 디렉터리만 예약한다"와 종류별 칸을 적는 불릿(`agent`만 `entrypoint`·`mcp`, `mcp`만 `[server]`), `README.md`의 `disabled.toml` 줄 "skill과 model은 로더가 생길 때 그 로더가 켜짐을 본다"와 `serve` 줄(`README.md:96`. 모델 이름 없이 띄우면 구성 오류가 된다), `.env.example`(`AGENT_OS_MODEL`이 없다. 기본 모델의 이름을 넘기는 줄이 든다)은 구현 티켓이 고친다.
