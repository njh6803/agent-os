# 여러 브랜치가 함께 쓰는 조율 상태는 항목마다 파일 하나로 나누고 새 것은 번호 대신 제목으로 부르며, 전체 계획은 기능 계획에서 만든 생성 파일이고 헌법 README는 판 줄만 남긴다

나란히 도는 브랜치가 병합 때마다 같은 파일에서 부딪혔다. 사용자가 "병렬로 돌리면 병합되기전까지 브랜치가 다른 브랜치의 영향을 주는 변경을 모르잖아... 그리고 retro-queue.md 처럼 같이 읽고 쓰는 것들은 충돌이 많이 나길래"라고 했고, 앞 세션의 안 가운데 "git 안에 두되 항목마다 파일 하나로 나눈다"를 골라 "이거 진행하자. 그리고 이왕 수정하는 김에 회차를 3회에서 5회로 기준을 바꾸자"고 했다. 번호에는 "근데 꼭 번호로 해야해? 그냥 제목으로 하면 안되나?"라고 물었다(설계 인터뷰는 일지 2026-11-06-04). 이 결정은 브랜치 여럿이 함께 읽고 쓰는 조율 상태 넷(회고 반영 대기열, 일지·하네스 티켓·ADR의 번호, 전체 계획, 헌법 판)을 하나씩 보고, 공유 파일을 없애거나 생성 파일로 바꾼다. 더하는 문턱을 다섯으로 올리는 것은 ADR 0036의 이력이고, 하네스 티켓의 이름은 ADR 0037의 이력이다.

**까닭.** 2026-11-05~06에 이 워크트리에서 봤고, 수는 origin/main 83a66cdc(설계 때 이 브랜치가 합쳐 둔 판. PR 직전에 15f11711을 더 합쳤고 수는 다시 세지 않았다)에서 다시 셌다. 이 ADR의 수는 달리 적지 않으면 모두 이 기준이다. 변경을 세는 기점은 날짜가 아니라 커밋 19bbfa06(2026-10-22, 대기열 번호 437까지 든 커밋)이다.

- **대기열은 가장 자주 부딪히는 파일이다.** `.scratch/retro-queue.md`는 머리말 18줄과 표 행 551개(열린 133, 닫힌 418)이고 번호는 1~573, 빈 번호 22개다(스크래치 스크립트로 손으로 셌다). 19bbfa06 뒤 83a66cdc까지의 main 커밋 120개 가운데 96개가 이 파일을 고쳤고 번호는 437에서 573으로 136개 늘었다(`git rev-list --count 19bbfa06..origin/main`과 같은 명령에 `-- .scratch/retro-queue.md`를 준 것, `git show 19bbfa06:.scratch/retro-queue.md`로 손으로 봤다). 행 하나를 더하거나 승인 칸에 회차를 더하는 두 브랜치는 같은 자리(표의 끝, 같은 행)를 고쳐 병합할 때마다 손으로 푼다. 일지 418개 가운데 "충돌"과 파일 이름을 80자 안에 함께 든 것이 대기열 62, `plan.md` 28, 헌법 README 8이다(grep 근접으로 센 어림).
- **번호는 받고 옮기는 일을 만든다.** 일지 418개 가운데 123개가 번호를 옮겼다고 적었고, 까닭이 이름순(main의 최신 일지보다 앞서서)인 것이 84, 형제와 겹친 것이 43이다(조사 서브에이전트의 `git grep`, 한 줄에 함께 나온 것만 센 어림. 둘의 합 127이 123을 넘는 것은 두 까닭을 함께 적은 일지가 있어서로 보이나 다시 세지 않았다). 옮김 84건은 겹침이 아니라 "최신 일지는 이름순"이라는 규칙(`docs/constitution/operations.md` 20행) 탓이다. 하네스 티켓 번호를 옮긴 기록은 0줄이다. 번호를 받으려고 `tools/sibling_overlap.py`를 지시문을 낼 때와 커밋 직전에 두 번 치고, 겹치면 브랜치·세션 제목·워크트리 이름·인용까지 옮긴다(ADR 0037 "번호"). ADR은 44개로 적고(7주에 하루 한 개 꼴) "ADR 0036" 인용과 색인·규칙이 번호에 기대어 번호를 둔다.
- **`plan.md`를 고친 커밋은 Status가 아니라 내용 칸을 고친다.** 19bbfa06 뒤 origin/main 83a66cdc까지의 `plan.md` 커밋 39개 가운데 내용 칸만 고친 것이 22, Status와 내용이 8, Status만 3, 행 추가 3, 표 밖 3이다(`.scratch/retro-queue-per-item/probes/plan_changes.py`로 쟀다). Status를 티켓에서 만들어 내는 것만으로는 두 브랜치가 부딪히는 자리의 대부분이 남는다(커밋이 고친 칸으로 본 어림이다. 충돌 자체를 세지는 않았다). 그래서 행 자체를 기능 폴더로 나눈다. `tests/test_plan_status.py`(하네스 티켓 044)가 Status와 티켓의 어긋남을 이미 잡고 있어, Status를 만들어 내면 그 시험은 생성 파일 대조로 바뀐다.
- **헌법 README의 이력은 한 줄이라 판을 올리는 두 브랜치가 반드시 부딪힌다.** `docs/constitution/README.md`는 판 줄 하나와 이력 한 줄 19,133자(36,255바이트, `N.N.N은/는` 꼴의 판 84개)다(파이썬 한 줄로 손으로 셌다). 19bbfa06 뒤 83a66cdc까지 커밋 15개(`git rev-list --count`). 판 올리기는 pre-commit의 `tools/check_constitution_version.py`가 막고, 형제가 먼저 매겨 비워 둔 판(`reserved_version`)은 이력 문단으로 알아본다(`tools/sibling_overlap.py` 362행 `RESERVED`, 699행. 코드를 읽었다).
- **대기열을 읽고 쓰는 자리.** 파싱하는 도구는 `tools/queue_open_rows.py`, `tools/sibling_overlap.py`, `tools/morning_collect.py`(`morning_sources.py`의 `main_text`가 `origin/main:<경로>`를 읽는다)이고, 경로를 이름으로 맞대는 자리는 `tools/hook_measure_word.py`, `tools/check_ticket.py`의 면제 모양, `.github/workflows/claude-code-review.yml` 97행의 경로 거르기다. 시험 여섯 파일, 카나리아 명세 아홉, 프로브 다섯이 그 모양에 걸린다(조사 서브에이전트가 코드를 읽었다). 일지 밖에서 `retro-queue`를 드는 자리는 42개 파일 120곳이다(83a66cdc에서 `docs/journal`을 뺀 `git grep`).
- **노션은 원천이 아니다.** 이 세션에는 노션 연결이 켜져 있었지만(연결 상태 도구, 도구 77개) 사용자가 "일단 노션 작업은 하지 말자"고 했다. 읽기 전용 보기와 병합 직후 갱신 둘 다 하지 않는다.
- **열린 PR은 하나다.** 2026-11-06 PR 직전의 `gh pr list --state open`에 #473(`docs/doc-qa-direction`) 하나이고, `.scratch/plan.md`·`CONTEXT.md`·ADR 0042·ADR README 등을 고치며 대기열 파일과 헌법 README는 고치지 않는다. 설계 인터뷰 때 열려 있던 #472(`docs/approval-rules-tickets`)는 이 PR이 origin/main을 합치기 전에 병합됐고(15f11711), 병합된 내용은 `.scratch/plan.md`와 함께 대기열 파일도 고쳤다(행 아홉을 닫고 573을 고치고 574를 더함. `git diff --stat 83a66cdc 15f11711`).

**결정은 열이다.** 1·2·5~7의 상세(파일 모양, 수, 이름)는 사용자가 선택 화면에서 고른 것이고 원문은 일지의 인용이다. 3의 `끝` 줄과 4는 합의 요약에 없던 것으로, 산출물을 쓰며 드러난 틈이라 이 ADR을 승인할 때 따로 확인받았다.

1. **대기열은 폴더다.** `.scratch/retro-queue.md` 대신 `.scratch/retro-queue/` 폴더에 항목마다 파일 하나를 둔다. 옛 항목(83a66cdc 기준 번호 1~573, 빈 번호 22개. 이행 티켓이 그때의 수를 다시 센다)은 번호를 네 자리로 채운 `0573.md`이고, 새 항목은 retro가 지은 짧은 영어 제목(슬러그)이 파일 이름이자 식별자다(`coderabbit-inline-size.md`). 파일은 하네스 티켓과 같은 굵은 라벨 줄이다. `# <ID>: 머리 한 문장` 아래 `**상태:**`(열림, 닫힘 (…), 만료 <날짜>), `**어디로:**`, `**승인:**`(승인 날짜, 회차, 잇기), 본문(지금 괄호 안의 상세). 닫힌 항목도 같은 폴더에 두고 상태 줄로 가른다. 닫기는 git 이동이 아니라 상태 줄 고침이다. 머리말의 규칙(승인 칸 꼴, 닫힘 꼴, 식별자 영구, 넷으로 짧게, 기본 반영 자리)은 폴더의 `README.md`로 옮기고 색인 파일은 두지 않는다. 열린 목록은 `queue_open_rows.py`가 그때그때 낸다. 옛 인용 "대기열 573"은 글자 그대로 두고 도구가 네 자리로 채워 `0573.md`로 풀며, 새 인용은 "대기열 coderabbit-inline-size"다. 잇기 `<번호>의 k회차`는 `<식별자>의 k회차`다. 두 브랜치가 같은 항목을 고치면 그 파일 하나에서만 부딪히고, 서로 다른 항목을 더하면 부딪히지 않는다.
2. **더하는 문턱과 만료 보호선은 다섯이다.** ADR 0036 이력 2026-11-06. 끝이 열린 결함 종류의 "세 번째 사례부터"는 셋 그대로다. 열린 항목 43개(83a66cdc 기준)의 "세 번째" 문구는 회차 다섯 티켓이 그때의 열린 항목에서 손으로 보며 고치고 고친 목록을 그 PR 본문에 적는다.
3. **전체 계획은 기능 계획에서 만든 생성 파일이다.** 기능마다 `.scratch/<slug>/plan.md`(기능 계획)를 둔다. `# <slug>: 한 줄` 아래 `**슬라이스:**`, `**Blocked by:**` 줄과 본문(지금 내용 칸)이고, 다른 기능이 넘긴 것은 받는 기능의 이 파일에 적는다. 기능을 끝낸 세션이 `**끝:** <날짜>` 줄을 더한다(지금은 마지막 티켓을 병합한 세션이고, 개발 브랜치가 선 뒤에는 출시 PR을 여는 세션이다, ADR 0043). (바뀜: 이력 2026-11-06 "명세가 끝 줄, 설계 줄, 비워 둔 판, 최신 일지, 일지 이름의 겹침, 시험의 고정값과 실패 문장, 판 올리기, 조각의 차례를 정한다") Status는 도구가 만든다. `끝` 줄이 있으면 done, 아니면 그 폴더 `issues/`에 done 티켓이 있으면 in-progress, 아니면 todo. 그래서 done인 기능에 기능 밖 고침 티켓이 열려도 done이 선다(ADR 0037 "자리"). 티켓이 모두 닫혔고 done이 있는데 `끝` 줄이 없으면 시험이 빨개져 그 줄을 적게 한다. 루트 `.scratch/plan.md`는 도구가 슬라이스 번호와 slug 순으로 만들어 커밋하는 생성 파일이고, 시험이 원천과 대조해 어긋나면 빨개지며, 병합 충돌은 다시 만들어 푼다. 표 밖의 글(머리말, 목표 배치, 첫 슬라이스의 범위)은 손으로 쓰는 파일 하나에 두고 도구가 그 뒤에 표와 프론티어 문단(기능 계획의 `끝` 줄에서 만든다)을 붙인다. 폴더가 없는 기능 16개(2026-11-06 origin/main 83a66cdc 기준. 행 36개 가운데 폴더가 있는 기능은 20개)는 폴더와 기능 계획만 생기고, harness 성격의 기능(`harness`, `ticket-for-every-pr` 같은 것)은 지금처럼 행이 없다. 이행 때 done인 기능(같은 기준 19개)의 `끝` 줄은 전체 계획 생성 티켓이 그 기능의 마지막 티켓을 병합한 커밋의 날짜를 git 기록에서 찾아 적는다. 프론티어의 정의(Blocked by가 비었거나 전부 done)는 그대로다.
4. **설계 인터뷰의 계기는 폴더가 아니라 명세의 부재다.** 3으로 기능 폴더가 미리 생기므로, 기능 폴더 `.scratch/<slug>/`가 없으면 설계 인터뷰부터 한다는 계기(`CLAUDE.md` 작업 규약 1, `grill-with-docs`의 설명, `tools/hook_grill_design_check.py`, `next-session` 결정표. 넷의 문구는 서로 다르다)는 명세 `.scratch/<slug>/spec.md`가 없으면으로 바뀐다. ADR 0042의 "각 기능은 `.scratch/<slug>/`가 없으니 차례가 오면 설계 인터뷰부터 하고"는 명세가 없으니 설계 인터뷰부터 한다는 뜻으로 읽는다. (바뀜: 이력 2026-11-06 "명세가 끝 줄, 설계 줄, 비워 둔 판, 최신 일지, 일지 이름의 겹침, 시험의 고정값과 실패 문장, 판 올리기, 조각의 차례를 정한다")
5. **헌법 README는 판 줄만 남긴다.** `**Version**` 줄과 비워 둔 판 장치만 두고, 옛 이력 줄(선택지 설명의 "87개". `N.N.N은/는` 꼴로 세면 84개, 까닭의 셈)은 `docs/constitution/history.md`로 옮긴다. 그 파일은 기록이라 그 뒤로 더하지 않고, 판을 올린 까닭은 그 변경의 ADR 이력이나 일지에 적는다. 비워 둔 판은 README의 판 줄 곁에 "N은 함께 돌던 형제 브랜치(`…`)가 먼저 매겨 비워 두었다" 꼴로 남고, 훅이 "이 브랜치가 그 판의 이력 문단을 더했다"로 보던 신호는 "이 브랜치의 판 줄이 main이 이 브랜치 몫으로 비워 둔 판과 같다"로 바뀐다. (바뀜: 이력 2026-11-06 "명세가 끝 줄, 설계 줄, 비워 둔 판, 최신 일지, 일지 이름의 겹침, 시험의 고정값과 실패 문장, 판 올리기, 조각의 차례를 정한다") 두 브랜치가 함께 판을 올리면 판 줄 하나에서만 부딪힌다.
6. **하네스 티켓은 제목으로 부른다.** ADR 0037 이력 2026-11-06. 새 티켓은 `.scratch/harness/issues/<slug>.md`, 브랜치는 `chore/<slug>`, 옛 44장은 번호를 지킨다.
7. **일지는 날짜와 시각과 제목으로 부른다.** `docs/journal/<YYYY-MM-DD>-<HHMM>-<슬러그>.md`이고 시각은 그 세션이 일지를 만든 로컬 시분이다. "최신 일지"는 이름순이 아니라 그 브랜치에 마지막으로 더해진 일지(git 기록)다. 먼저 만들고 늦게 병합해도 옮기지 않는다. (바뀜: 이력 2026-11-06 "명세가 끝 줄, 설계 줄, 비워 둔 판, 최신 일지, 일지 이름의 겹침, 시험의 고정값과 실패 문장, 판 올리기, 조각의 차례를 정한다") 옛 일지는 이름을 지키고 "일지 2026-10-19-21" 인용도 그대로 풀린다. 새 인용은 "일지 2026-11-06-1432"다. `operations.md` 20행의 규칙 문장이 바뀌므로 그 티켓이 헌법 판을 올린다.
8. **ADR은 번호를 유지한다.** 색인과 인용과 `.claude/rules/adr.md`의 번호 규칙이 번호에 기댄다. `tools/sibling_overlap.py`는 ADR 번호와 헌법 판의 겹침만 보고, 일지·대기열·티켓의 "다음 빈 번호"와 "옮길 번호"는 사라진다. 그래서 `CLAUDE.md` 환경 함정의 커밋 전 대조 문장도 그만큼 줄어든다.

(바뀜: 이력 2026-11-06 "명세가 끝 줄, 설계 줄, 비워 둔 판, 최신 일지, 일지 이름의 겹침, 시험의 고정값과 실패 문장, 판 올리기, 조각의 차례를 정한다") 커밋 검사의 면제 모양(`tools/check_ticket.py`)에 `.scratch/retro-queue/`, `docs/constitution/history.md`, `.scratch/<slug>/plan.md`를 더하고, 리뷰 봇 워크플로의 경로 거르기도 폴더로 바꾸며, 아침 보고의 `main_text`는 origin/main의 폴더를 읽는다. 옮기는 동안 옛 파일을 고친 열린 브랜치는 main을 합칠 때 "한쪽은 고치고 한쪽은 지운" 충돌을 만나고 자기 변경을 새 폴더에 다시 적는다.

**단계.** 이 ADR의 PR은 설계 산출물(일지, 이 ADR과 ADR 0036·0037의 이력, `CONTEXT.md`, 프로브)까지다. 구현은 사용자가 `/to-spec`과 `/to-tickets`로 명세와 티켓을 내고, 조각은 합의대로 여섯이다. 대기열 분할(결정 1과 10의 시험·면제·폴더 README), 회차 다섯(결정 2와 ADR 0036 이력), 전체 계획 생성(결정 3과 설계 계기 4), 일지 이름(결정 7), 티켓 이름(결정 6과 ADR 0037 이력), 헌법 README(결정 5). 조각마다 티켓 하나 이상이고 티켓마다 PR 하나다. 조각 사이의 순서는 셋이다. 설계 계기(4)는 전체 계획 생성(3)과 같은 티켓이거나 그보다 먼저 병합된다. 폴더가 먼저 생기면 폴더 없음을 보는 계기가 기능 16개의 설계 인터뷰를 건너뛴다. `sibling_overlap.py`의 번호 알림은 조각마다 제 것(일지 순번, 대기열 번호, 티켓 번호)만 뗀다. 대기열 분할·일지 이름·티켓 이름 셋은 `tools/sibling_overlap.py`와 그 시험, `tools/check_ticket.py`를 함께 고치므로 나란히 열지 않고 차례로 연다(ADR 0037 "파일이 겹치지 않는 티켓만 나란히"). 각 조각은 그 티켓이 병합될 때 서고 그날이 그 조각의 전환일이다. 그때까지 도구·스킬·지침·시험은 옛 규칙을 지키고, `CONTEXT.md`의 용어는 정한 모양과 전환일 전의 모양을 함께 적어 지금도 참이다. 대기열 분할 티켓은 옛 파일을 고친 열린 PR이 적은 때에 병합한다. 명세가 정할 것은 아래 목록이다.

- 전환일과 전환 시점의 최대 티켓 번호를 어디에 고정하는지
- 전체 계획을 만드는 도구의 이름과 도는 때
- "대기열 573"과 "일지 2026-10-19-21" 인용을 파일로 푸는 도구
- 최신 일지를 git 기록에서 찾는 법과 커밋 전 일지·main을 합친 뒤 들어온 일지의 처리
- 커밋 검사가 브랜치 두 꼴(`chore/NNN-<slug>`, `chore/<slug>`)을 맞대는 법
- 저장소 상태 시험 셋의 실패 문장
- 비워 둔 판의 새 신호
- 아침 보고의 폴더 읽기
- 리뷰 봇 워크플로의 경로 거르기
- `끝` 줄을 적을 세션이 없는 경우(나란히 돈 마지막 티켓 둘이 각각 병합된 때)
- `끝` 줄을 마지막 티켓의 PR에 싣는 법과 그 날짜(병합 뒤에 적으면 그 사이 main의 상태 시험이 빨갛다)
- 프론티어 문단의 지금 서술(닫힌 슬라이스의 PR 번호 같은 것)을 기능 계획에 옮길지 버릴지
- 바뀌는 자리의 전수

## Considered Options

- **노션을 원천으로 쓴다(대기열, 번호, 전체 계획).** 사용자가 처음 물었다. 세션마다 MCP 호출이 들고, 원천이 git 밖으로 나가 PR 리뷰와 시험이 보지 못하며, 아침 보고 예약 작업 세션에 노션이 켜졌는지 보지 못했다(어림). 사용자가 뺐다. 읽기 전용 보기와 병합 직후 갱신도 함께 뺐다.
- **번호를 두고 겹침 도구만 강화한다.** 옮김 123건 가운데 84건은 겹침이 아니라 이름순 규칙 탓이라 도구로 줄지 않는다. 거부했다.
- **대기열 항목을 YAML 머리(frontmatter)로 쓴다.** 도구가 값을 키로 읽기 쉽지만 `tools/`에 YAML을 읽는 선례가 없고 `pyproject.toml`의 경계 주석이 YAML 읽기를 sdk의 스킬 문서 모듈 하나로 묶는다(ADR 0041). 거부했다. 기능 계획도 같다.
- **표 행 한 줄을 그대로 파일 하나에 둔다.** 이행이 가장 단순하지만 한 줄 900자 넘는 파일이라 사람이 읽기 어렵고 뒤에 모양을 바꾸면 550여 파일을 두 번 옮긴다. 거부했다.
- **닫은 항목을 `closed/`로 옮기거나 지운다.** 옮기면 닫기가 git 이동이 되어 같은 항목을 고친 브랜치와 이름 바꿈 충돌이 나고 인용을 푸는 도구가 폴더 둘을 본다. 지우면 잇기와 닫힌 항목 인용이 git 기록으로만 풀려, 대기열의 닫힌 행을 기록으로 가르는 `operations.md` 문서 위치 절과 어긋난다. 거부했다.
- **폴더 README에 도구가 만든 색인을 둔다.** 항목을 더하거나 닫는 브랜치마다 색인이 바뀌어 지금 대기열 파일과 같은 충돌 자리가 하나 남는다. 거부했다.
- **대기열 규칙을 `docs/agents/issue-tracker.md`로 옮긴다.** 대기열 규칙은 ADR 0036과 retro 스킬도 들고 있어 자리가 셋이 되고, 폴더만 연 사람이 규칙을 못 본다. 거부했다.
- **대기열 폴더를 `.scratch/harness/` 아래 둔다.** 커밋 검사가 `.scratch/harness/`를 티켓 폴더로 따로 판정해 그 판정을 손봐야 한다. 거부했다.
- **옛 항목 번호를 채우지 않는다(`573.md`).** 인용 글자와 같지만 폴더 목록이 1, 10, 100 순으로 선다. 거부했다.
- **만료 보호선은 셋에 두고 chore 계기만 다섯.** 3·4회차 항목이 목록에 남아 눈에 띄지만 수가 둘이 되고, 열린 항목이 줄지 않는 방향이라 ADR 0036이 거부한 "문턱만 올리고 만료는 두지 않는다"에 가깝다. 거부했다.
- **끝이 열린 결함 종류의 수도 다섯.** 수가 하나라 기억하기 쉽지만 사례 둘을 더 고친 뒤에야 근본 고침으로 넘어간다. 거부했다.
- **열린 항목의 "세 번째" 문구를 두거나 스크립트로 일괄 치환한다.** 두면 열린 항목(살아 있는 문서)에 옛 표현이 남고, 일괄 치환은 306의 "세 번째 사례"처럼 다른 뜻까지 바꾼다. 거부했다.
- **기능 계획을 `spec.md` 머리에 둔다.** 파일이 늘지 않지만 명세가 없는 기능 17개(83a66cdc 기준)에 머리만 있는 `spec.md`가 생기고, `to-spec`이 쓰는 파일을 도구도 읽는다. 거부했다.
- **Status만 티켓에서 만들고 행은 한 파일에 둔다.** 커밋 39개 가운데 Status만 고친 것은 3개라 대부분이 남는다(`plan_changes.py`). 거부했다.
- **헌법 README 이력을 판마다 파일로 나누거나 ADR처럼 끝에 더한다.** 나누면 판마다 파일이 생기고(결정 5의 셈으로 84개), 끝에 더하면 두 브랜치가 같은 끝을 고쳐 지금과 같다. 판 줄만 남기면 충돌이 한 줄로 준다. 거부했다.
- **일지 번호를 ADR처럼 유지한다.** 옮김 123건의 자리가 그대로 남는다. 거부했다. 반대로 ADR을 slug로 부르는 것은 인용 46곳과 색인·규칙을 모두 바꾸고 얻는 것이 적다(ADR은 7주에 44개). 거부했다.
- **이행 스크립트를 `tools/`에 남긴다.** 한 번 쓰는 코드가 pyright strict·타입 우회 검사·변이 표의 대상으로 남고 옛 파일이 없는 저장소에서는 할 일이 없다. 거부했다.
- **전환기를 두어 옛 파일과 새 폴더를 함께 읽는다.** 열린 브랜치가 옛 파일을 고쳐도 병합되지만 읽는 도구 셋이 둘을 읽고 전환기가 끝나는 조건과 정리 작업을 또 정한다. 옛 대기열 파일을 고친 열린 PR이 없어(2026-11-06 PR 직전의 열린 PR은 #473 하나이고 대기열을 고치지 않는다. 그 전에 열려 있던 #472는 대기열을 고쳤지만 이 PR이 열리기 전에 병합됐다) 거부했다.
- **이 PR에서 모두 구현한다.** 도구 다섯(`sibling_overlap.py`, `queue_open_rows.py`, `check_ticket.py`, `morning_collect.py`, `hook_journal_retro.py`)과 그 시험 셋(`test_sibling_overlap.py`, `test_queue_open_rows.py`, `test_check_ticket.py`) 10,749줄(`wc -l`)과 스킬·규칙·워크플로·운영 문서·헌법 README가 한 PR에 들어 셀프 리뷰와 CI 한 바퀴가 길고, 그 사이 main이 움직이면 대기열 파일 충돌을 거듭 푼다. 거부했다. 회차 다섯과 대기열 분할만 이 PR에서 하는 안도 설계 산출물과 구현이 섞여 거부했다.

## Consequences

- **공유 파일이 둘 남는다.** 대기열의 같은 항목 파일과 헌법 README의 판 줄이다. 둘 다 부딪히는 범위가 한 파일·한 줄로 줄고, 전체 계획은 다시 만들면 풀린다. 서로 다른 항목을 더하는 브랜치는 부딪히지 않는다.
- **폴더에 파일이 550여 개 놓인다.** 열린 항목은 도구가 골라 내므로 사람은 폴더를 훑지 않는다. 같은 제목(slug)을 두 브랜치가 더하면 git이 양쪽에서 더함(add/add) 충돌로 알린다.
- **옛 인용을 푸는 규칙이 도구에 든다.** "대기열 573"을 `0573.md`로, "일지 2026-10-19-21"을 옛 파일로 푸는 것이다. 인용 글자는 바꾸지 않는다(83a66cdc에서 `git grep -ohE '대기열 [0-9]+'`를 폴더별로 센 수. `docs/journal` 3,107, `tools`·`tests` 739, `.scratch` 898, `.claude` 198, `docs/adr` 46, 전체 5,140).
- **전환기에 이름 꼴이 섞인다.** 옛 일지와 새 일지, 번호로 부르는 티켓과 슬러그로 부르는 티켓, 번호 항목과 슬러그 항목이 함께 산다. 전환일 뒤의 옛 꼴만 시험이 막는다. (바뀜: 이력 2026-11-06 "명세가 끝 줄, 설계 줄, 비워 둔 판, 최신 일지, 일지 이름의 겹침, 시험의 고정값과 실패 문장, 판 올리기, 조각의 차례를 정한다") 전환 전에 낸 지시문이 번호(`티켓 045`)를 들고 전환 뒤에 돌면 그 세션이 옛 꼴로 만들다 시험에 막혀 제목으로 바꾼다. 병합 전에 시작해 main을 합친 뒤 옛 스킬 사본을 실은 세션은 옛 대기열 파일을 다시 만들 수 있고, 상태 시험이 pre-commit에서 막으며 실패 문장이 README를 가리킨다.
- **`plan.md`를 손으로 고치면 시험이 빨개진다.** 전체 계획을 손으로 고치던 자리(`to-tickets`가 행을 더하고, 기능 상태를 바꾸는 세션이 Status를 고치고, `code-review` 6단계가 받는 쪽 행에 적는 것. `next-session`은 읽기만 한다)는 기능 계획을 고치고 도구를 돌리는 자리가 된다. 끝난 기능의 `끝` 줄은 사람이 아니라 기능을 끝낸 세션이 적고, 빠뜨리면 시험이 빨개진다.

- **`끝` 줄은 마지막 티켓의 PR이 적고, 빠지면 저장소 상태 시험이 막는다.** 막는 자리는 결정 3 그대로다. `**슬라이스:**` 줄이 있는 기능 계획의 티켓이 모두 닫혔고(done 또는 wontfix) done이 하나 이상인데 `끝` 줄이 없으면 시험이 빨개진다. 결정 3은 그 줄을 마지막 티켓을 병합한 세션이 적는다고 적었는데, 병합 뒤에 적으면 그 사이 main의 시험이 빨갛다. 그래서 마지막 티켓의 PR이 그 티켓을 닫는(done이나 wontfix로 바꾸는) 커밋에서 `끝` 줄을 적고, 날짜는 그 커밋의 로컬 날짜다. 마지막 티켓 둘이 나란히 돌면, main 보호가 strict(필수 검사 `verify`)라 늦게 병합되는 PR이 main을 합친 뒤의 CI에서 막혀 그 PR이 적는다. 다른 세션까지 막히는 것은 관리자 우회 병합이나 main 직접 푸시 뒤뿐이다. 개발 브랜치(ADR 0043)가 선 뒤 `끝` 줄을 누가 적는지(결정 3의 괄호는 출시 PR을 여는 세션이라 적었다)는 그 전환을 맡는 harness 티켓이 다시 정한다. 명세 세션에서 사용자는 처음에 그 기능의 티켓을 고친 브랜치만 커밋 검사가 막는 안을 골랐다. 그 설명이 strict 규칙을 빠뜨린 것을 명세 검토가 짚어 고친 설명으로 다시 물었고, 사용자가 이 안을 골랐다. 두 번의 설명은 일지 2026-11-06-12에 글자 그대로 있다.
