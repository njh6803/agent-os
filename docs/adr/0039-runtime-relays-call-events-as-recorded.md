# 런타임은 모델·도구 호출의 이벤트를 기록하는 자리에서 흘리고, 에이전트는 몸통과 맞물린 제 태스크에서 돈다

런타임이 모델 호출과 도구 호출에서 만든 이벤트(`llm_called`, `tool_called`)는 지금 컨텍스트에 쌓였다가 에이전트가 다음 이벤트를 낼 때 나온다(`core/run.py`의 `_relay`). 루프 전체가 `ctx.llm()` 한 번인 에이전트(저장소의 계산 에이전트)는 그 이벤트가 모두 결말 바로 앞에 한꺼번에 나와, 운영자 `/runs`도 위젯도 실행 도중에 무엇을 부르는지 보지 못한다. 용어집의 이벤트 스트림("생기는 대로 채널이 내보내는 열")과도 어긋난다. web-widget 명세를 쓰며 사용자가 이 기능에서 core까지 바꾸기로 골랐다(일지 2026-10-23-40). **런타임은 모델·도구 호출의 이벤트를 기록하는 자리에서 곧바로 흘린다. 몸통(`_Body`)은 에이전트를 anyio 태스크 그룹의 자식 태스크에서 돌리고, 컨텍스트는 이벤트를 기록하면 몸통을 깨운 뒤 몸통이 그 이벤트를 내보내고 다음을 청할 때까지 기다린다(맞물림). 에이전트가 낸 이벤트도 같은 길을 지난다. 이벤트는 컨텍스트의 줄에 남고, 태스크 사이로는 깨우는 신호만 건넌다.** 맞물림이라 에이전트는 몸통이 앞의 이벤트를 트레이스에 쓰고 내보내기 전에 다음 일을 하지 않는다. 그래서 지금의 역압이 그대로이고, ADR 0014의 "스트림에 나간 이벤트는 이미 트레이스에 있다"도 그대로이며, 도구를 요청한 모델 호출의 이벤트는 그 도구를 부르기 전에 쓰인다. 지금은 루프가 끝난 뒤에 쓰여, 그 쓰기가 실패해도 도구는 이미 불린 뒤다. 시제품(`.scratch/web-widget/probes/live_relay.patch`)을 커밋 934f8dfa의 사본에 대 재 보니, 계산 에이전트 모양의 실행에서 모델 호출과 도구 줄이 실행 도중에 나왔고, 함께 부른 도구는 그대로 겹쳐 돌았으며, 기존 core·채널·MCP 시험 553개와 실제 MCP의 트레이스 쓰기 실패 네 사례가 그대로 지났다(`.scratch/web-widget/probes/live_relay.py`, 그 README의 2026-10-23 결과).

## Considered Options

- **지금처럼 모은다.** core가 바뀌지 않는다. 위젯은 실행 도중에 고정 문구만 보이고 도구 줄은 결말 앞에 한꺼번에 받는다. 명세를 쓰던 세션이 추천한 안이었고 사용자가 고르지 않았다.
- **같은 태스크에서 되돌아 나온다.** 에이전트를 자식 태스크로 옮기지 않고, 컨텍스트의 await 안에서 바깥 제너레이터로 제어를 넘긴다. 파이썬의 비동기 제너레이터는 안쪽 코루틴이 await하는 도중에 yield할 수 없으므로, 에이전트 코루틴을 `send`로 직접 구동하는 구동기가 필요하다. 에이전트가 `asyncio.gather`나 태스크 그룹으로 띄운 하위 태스크의 호출은 그 구동기 밖이라 흘리지 못한다. 거부했다.
- **맞물리지 않는 자식 태스크.** 에이전트가 이벤트를 넣고 기다리지 않는다. 몸통이 늦으면 줄이 끝없이 자라고(역압이 없다), 도구가 앞의 모델 호출 이벤트가 트레이스에 쓰이기 전에 불려 그 쓰기가 실패해도 도구가 불린다. 거부했다.
- **이벤트 자체를 메모리 흐름으로 보낸다.** 줄과 신호를 따로 두지 않는다. 그러나 anyio 4.15.1의 메모리 흐름에서는, 보내는 쪽이 기다리던 받는 쪽에 항목을 넘긴 뒤 받는 쪽이 깨어나기 전에 asyncio의 날 취소(`Task.cancel()`)로 끝나면 그 항목이 받는 쪽에도 흐름에도 남지 않았다. anyio 취소 범위로 끊으면 받는 쪽이 그 항목을 받았다(`.scratch/web-widget/probes/anyio_facts.py`, 그 README의 2026-10-23 결과). 이 저장소의 취소는 지금 모두 anyio 범위라(실행 타임아웃, 연결이 끊긴 HTTP 응답, CLI의 Ctrl+C. 채널의 취소 자리를 grep했다) 잃지 않지만, 그러면 이벤트가 남는지가 몸통을 끊는 쪽이 어떤 취소를 쓰는지에 달린다. 잃은 이벤트는 트레이스에서도 빠진다. 고른 안은 이벤트를 컨텍스트의 줄에 두어, 신호를 잃어도 몸통이 끝날 때의 정리가 남은 이벤트를 받는다. 거부했다.

## Consequences

- **에이전트의 정리 코드가 도는 태스크가 바뀐다.** 에이전트의 제너레이터는 그것을 순회한 에이전트 태스크가 `run()`이 끝나기 전에 닫는다. `run()`을 부른 태스크가 아니다. `_closing`이 막는 것(가비지 수집이 다른 태스크에서 닫아 에이전트가 쥔 취소 범위가 깨지는 것)은 그대로 막힌다. 컨텍스트 변수는 자식 태스크를 띄울 때 복사되므로 에이전트가 바꾼 값은 부른 쪽에 보이지 않는다. `.claude/rules/core.md`의 "같은 태스크에서 돈다"와 `tests/core/test_run.py`의 단언은 구현 티켓이 고친다.
- **버려진 실행에서 에이전트는 yield 자리가 아니라 기다리던 자리에서 끊긴다.** 소비자가 스트림을 닫거나 트레이스 쓰기가 실패하면, 지금은 에이전트의 yield 자리에 `GeneratorExit`가 들어간다. 이제는 몸통이 태스크 그룹을 취소해, 에이전트가 기다리던 자리(모델·도구 호출, 맞물림의 기다림)에 취소가 들어간다. 그래서 에이전트의 `finally` 안의 await도 취소된다. 실행 타임아웃은 지금도 취소로 끊으므로 모양이 하나가 된다. 플러그인 작성자가 알아야 하므로 구현 티켓이 sdk `BaseAgent.run`의 독스트링에 적는다.
- **이벤트 하나에 수십 µs가 더 든다.** 잠들지 않는 도구를 2,000번 부른 실행에서 이벤트 하나가 지나는 시간이 11µs에서 76µs로, 다른 회차에서 18µs에서 101µs로 늘었다. 실제 모델 호출 하나는 그보다 몇 자릿수 길어 실행 시간에는 드러나지 않을 것이다(어림이고, 실제 모델로는 재지 않았다).
- **채널의 구동 규칙은 그대로다.** 몸통은 태스크 그룹 안에서 yield한다. 실행 타임아웃의 취소 범위가 yield를 건너는 것과 같아, 부르는 쪽은 지금처럼 한 태스크에서 순회하고 이벤트 사이에 await하지 않는다(`.claude/rules/channel.md`).
- **모든 면이 함께 바뀐다.** 두 진입점(`run()`, `resume()`)이 몸통을 공유하므로 운영자 `/runs`, 최종 사용자 경로, CLI가 모두 실행 도중에 이벤트를 받는다. 면마다 다르게 두지 않는다. 최종 사용자 스트림이 이것으로 얻는 항목은 ADR 0023의 이력이다.
- **재생 구간은 바뀌지 않는다.** 재생에서는 이미 트레이스에 있는 이벤트를 다시 쓰지 않으므로 흘릴 것이 없다(ADR 0009).
