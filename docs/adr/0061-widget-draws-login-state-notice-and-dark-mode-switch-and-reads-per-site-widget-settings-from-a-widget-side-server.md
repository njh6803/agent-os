# 위젯이 로그인 상태와 고지와 다크 모드 스위치를 직접 그리고, 사이트마다의 위젯 설정을 위젯 쪽 서버에서 받아 오며, 주소 하나를 창으로 여는 URL 방식을 더한다

ADR 0050과 ADR 0059는 고지, 로그인 단추, 로그인한 이름, 만료 알림을 위젯 미리보기 페이지가 위젯 바깥에 그린다고 정했고, pilot-portal의 명세는 그 페이지 위쪽 띠에 다크 모드 스위치를 두었다(`.scratch/pilot-portal/spec.md`를 Grep으로 봤다). 그 화면을 그리던 탐색(일지 2026-11-13-0426)에서 사용자가 방향을 바꿨다. 위젯을 제 페이지에 넣는 사이트에도 그 화면이 따라 들어가야 하고 사이트가 화면을 만들어서는 안 된다는 것, 그리고 위젯을 주소 하나로도 내자는 것이다(같은 일지의 사용자 말 "위젯 상자 안에 다크 모드 스위치, 위젯 아래 고지 줄, '로그인하고 질문하기' 상자, 이름 줄, 만료 덮개 등 다 나와야하는거 아니야? 고객사가 화면을 만들어야하는거야? EMBED.md에 url로 제공하는 것도 추가하자"). 그 방향을 설계 인터뷰(일지 2026-11-13-1813)로 정했고, 인터뷰에서 사용자는 추천과 다른 답으로 범위를 넓혔다. 사이트마다의 값을 운영자가 화면에서 등록하게 하고, 그 저장소와 화면을 0.1 판에 넣는다는 것이다. **위젯은 로그인 상태(로그인 단추, 로그인한 이름과 로그아웃 단추, 만료 알림, 로그인 거절 알림), 고지(짧은 줄, 전문 펼침, 확인 전의 덮개), 다크 모드 스위치를 자기 안에 그린다. 사이트는 화면을 만들지 않고, 토큰을 내주는 통로의 답에 그때그때 달라지는 것(보일 이름, 로그인하지 않음, 로그인 시간이 끝남, 로그인이 거절됨, 고지를 아직 확인하지 않음)을 싣는다. 달라지지 않는 값(위젯의 이름과 소개, 색과 처음 밝기, 고지의 글, 로그인 주소와 로그아웃 주소)은 위젯 설정이다. 위젯 설정은 사이트마다 위젯 쪽 서버가 데이터베이스에 들고 운영자가 위젯 설정 관리 화면에서 등록하며, 위젯은 태그에 적힌 사이트의 이름으로 뜰 때 받아 온다. 위젯은 받은 사이트 토큰을 만료 시각까지 다시 쓴다. 로그인은 로그인 주소를 새 창으로 열어 맡기고, 로그아웃은 등록된 주소를 직접 부르는 것이 기본이다. 임베드 방식에 URL 방식이 더해져 셋이 된다.** 계약이 바뀌는 자리는 위젯의 공개 표면(`web/apps/widget/EMBED.md`) 하나다. Agent OS의 계약(`sdk`, `openapi.json`, 사이트 파일의 형식, 사이트 토큰의 주장)은 바뀌지 않는다. 새로 생기는 것은 위젯 쪽의 서버와 데이터베이스와 위젯 설정 관리 화면이고, 그 자리와 종류는 이 ADR이 정하지 않고 '위젯 설정 관리' 행의 설계 인터뷰에 넘긴다.

이 ADR의 "사이트"는 설계 인터뷰의 말 "고객사"이고 "위젯"은 "챗봇"이다(`CONTEXT.md`의 피할 말). "위젯 설정 관리 화면"은 운영자가 위젯 설정을 등록하는 위젯 쪽의 화면이고, 인터뷰에서는 "관리 화면"이라고 불렀다. `CONTEXT.md`의 관리 화면(Agent OS의 웹 앱)과 다른 것이라 이 ADR은 그 말로 적지 않고, 용어집에 올릴 이름은 '위젯 설정 관리' 행의 설계 인터뷰가 정한다. 인터뷰의 답과 확인받은 요약은 일지 2026-11-13-1813에 글자 그대로 있다.

## 결정

- **위젯이 그리는 것.** 위젯은 아래 셋을 자기 상자 안에 그리고, 페이지 안 방식, iframe 방식, URL 방식에서 모양이 같다. 사이트는 이 화면을 만들지 않는다. 첫째는 로그인 상태다. 로그인 전에는 "로그인하고 질문하기" 단추를, 로그인한 뒤에는 이름 줄과 "로그아웃" 단추를, 로그인 시간이 끝난 뒤에는 "로그인 시간이 끝났습니다"와 "다시 로그인" 단추를, 로그인이 거절됐을 때는 사이트가 준 한 문장의 알림을 그린다. 둘째는 고지다. 입력창 아래의 짧은 줄과 "고지 전문" 펼침, 그리고 고지 확인 전에 상자를 덮는 덮개와 "확인하고 질문하기" 단추다. 셋째는 다크 모드 스위치다. 위젯은 스스로 사람을 로그인시키지 않는다. 최종 사용자가 누구인지는 지금처럼 사이트가 서명한 사이트 토큰으로만 받는다(ADR 0023, ADR 0060 결정 "위젯의 안내와 로그인 통로"의 그 문장은 그대로다).
- **토큰 답.** 사이트가 토큰을 내주는 통로(페이지 안 방식의 `tokenProvider`, iframe 방식과 URL 방식의 메시지)의 답이 는다. 사이트는 지금처럼 토큰 글자 하나만 답할 수 있고, 그런 사이트는 고치지 않아도 지금과 똑같이 동작한다. 그 밖에 사이트는 토큰과 보일 이름을 함께 답하거나, 토큰 대신 상태 넷 가운데 하나를 답한다. 로그인하지 않음, 로그인 시간이 끝남, 로그인이 거절됨(무엇이 막혔는지 한 문장과 함께), 고지를 아직 확인하지 않음이다. 위젯은 그 답대로 그린다. 이름은 화면에만 쓰이고 사이트 토큰에 싣지 않아 Agent OS로 가지 않는다(이름을 사이트 토큰에 싣지 않는다는 것은 ADR 0059 결정 "식별자와 사이트 토큰"이, Agent OS에 저장하지 않는다는 것은 같은 ADR의 결정 "화면"이 정했고 둘 다 그대로다). 사이트가 로그인으로 확인한 사람의 토큰이라고 답하면서 이름을 주지 않으면 위젯은 "로그인됨"을 보인다. 토큰 글자만 답하는 사이트의 위젯은 이름 줄을 그리지 않는다. 토큰을 받지 못한 그 밖의 까닭(함수가 없다, 던졌다, 시간이 넘었다)은 지금처럼 "로그인 정보를 받지 못했습니다." 알림이다. 로그인 거절은 추천("사이트가 자기 화면에")과 달리 사용자가 "위젯이 그리기"를 골랐다. 대가는 위젯의 약속에 상태가 하나 더 들어가고, 거절 뒤 그 상태를 언제 지울지(새로 고치면 사라지는지)를 사이트가 따로 기억해야 한다는 것이다.
- **위젯이 사이트에 알리는 것.** 위젯은 둘을 사이트에 알린다. 사람이 "확인하고 질문하기"를 눌렀다는 것과 "로그인 없이 계속"을 골랐다는 것이다. 토큰을 묻는 같은 통로에 실어 보내고, 통로를 더 내지 않는다. 고지 확인을 기록하는 쪽은 지금처럼 사이트다(위젯 미리보기 페이지는 그 브라우저의 쿠키로 기록한다, ADR 0050).
- **보증 모드는 위젯의 칸이 아니다.** 위젯에는 익명 모드, 로그인 모드, 둘 다를 고르는 값을 두지 않는다. 화면은 위젯 설정에 로그인 주소가 있는지와 사이트의 토큰 답으로 정해진다. 로그인 주소가 없으면 로그인 단추를 그리지 않는다. 로그인 주소가 있고 사이트가 로그인하지 않음이라고 답하면 로그인 단추만 보인다(로그인 모드의 사이트가 그렇게 답한다). 로그인 주소가 있고 사이트가 익명 주체의 토큰을 주면 질문할 수 있고 로그인 단추도 보인다(둘 다인 사이트가 그렇게 답한다). 로그인 시간이 끝남이라는 답에는 익명으로 계속할 수 있는 사이트인지가 함께 오고, 그럴 때만 위젯이 "로그인 없이 계속"을 함께 그린다. 사람이 그것을 고른 뒤에만 익명 주체로 바뀌고, 사이트는 로그인 상태가 끝났다고 익명 토큰을 말없이 내지 않는다(ADR 0059 결정 "화면"의 조건 그대로다).
- **고지.** 위젯 설정에 고지의 짧은 줄과 전문이 있으면 위젯이 입력창 아래에 한 줄과 "고지 전문" 펼침을 그린다. 사이트가 고지를 아직 확인하지 않음이라고 답하면 위젯이 상자를 덮는 덮개에 전문과 "확인하고 질문하기"를 그리고, 누르면 사이트에 알린 뒤 토큰을 다시 묻는다. 고지를 등록하지 않은 사이트의 위젯은 지금처럼 고지 없이 뜬다. 지금 위젯에는 상자를 덮는 덮개 부품이 없어 새로 짓는다(위젯 소스를 읽은 서브에이전트의 보고다, 일지 2026-11-13-1813 "조사: 위젯과 위젯 미리보기 페이지의 지금 코드").
- **다크 모드 스위치.** 스위치는 모든 위젯에 보인다. (바뀜: ADR 0064) 고른 값은 위젯이 브라우저 저장소에 두어 탭을 닫았다 열어도, URL 방식의 창을 새로 열어도 남는다. 한 번도 고르지 않은 사람에게는 사이트가 정한 처음 밝기(임베드 속성 `mode`나 위젯 설정의 값)를 쓰고, 그것도 없으면 지금처럼 시스템 설정을 따른다. 그래서 `mode`의 뜻이 고정하는 값에서 처음 값으로 바뀐다. 추천("정한 사이트는 고정". 밝기를 정해 준 사이트의 위젯은 그 값으로 고정하고 스위치를 그리지 않는 안이다)과 달리 사용자가 "늘 사람이 고르기"를 골랐다. (바뀜: ADR 0064) 대가는 자기 페이지의 밝기에 위젯을 맞춰 둔 사이트의 위젯이 사람의 선택으로 페이지와 다른 밝기가 될 수 있다는 것이다. ADR 0026의 2026-10-06 이력("테마는 색과 글꼴의 한 벌이고 다섯이며, 라이트·다크는 모드다")은 위젯의 모드를 사이트가 넘긴다고 정했고, "최종 사용자도 위젯에서 고른다"를 사이트의 분위기와 어긋날 수 있고 위젯에 부품이 는다는 까닭으로 거부했다. 이 결정은 그 안을 모드에 한해 다시 열어 받아들인다. 사이트가 넘기는 모드는 처음 값이 되고, 테마는 지금처럼 사이트가 고른다(그 이력의 제목이 적은 테마의 수 다섯은 같은 ADR의 2026-10-12 이력 "테마는 넷이고 색만 바꾸며, 글꼴은 모든 테마가 Noto Sans KR과 Noto Sans Mono를 쓴다"가 넷으로 바꿨다). 저장하는 값은 밝게와 어둡게 가운데 하나뿐이고 사람을 가리키지 않는다. 지금 위젯이 쓰는 브라우저 저장소는 탭 저장소 하나라(`web/apps/widget/lib/storage.ts`를 Grep으로 봤다) 탭을 닫아도 남는 값은 이것이 처음이다. 페이지 안 방식에서는 그 값이 사이트 출처의 저장소에 위젯의 이름표를 달고 놓인다. iframe 방식에서는 브라우저가 다른 사이트 안에 든 문서의 저장소를 막으면 기억되지 않을 수 있다(어림, 재 보지 않았다). 위젯 미리보기 페이지 위쪽 띠의 스위치는 없앤다. 그 페이지의 바탕은 사이트가 정한 밝기(없으면 시스템 설정)를 따르므로, 위젯을 어둡게 골라도 바탕은 그대로라 둘의 밝기가 다를 수 있다. (바뀜: 이력 2026-11-16 "만료 알림의 기본 모양은 대화 안의 카드이고, 창 없이 부르는 로그아웃이 통하는 조건을 재서 고치며, 위젯 미리보기 페이지의 바탕은 기기의 설정을 따른다") 지금은 띠의 스위치 하나가 바탕과 위젯을 함께 바꾼다(`web/apps/portal/browser/portal.ts`를 읽었다).
- **토큰을 만료 시각까지 다시 쓴다.** 위젯은 받은 사이트 토큰의 만료 시각을 읽어, 끝나기 전까지 같은 토큰으로 요청을 보낸다. 토큰은 위젯의 메모리에만 두고 브라우저 저장소에 쓰지 않는다. 새로 묻는 때는 넷이다. 뜰 때, 토큰이 끝난 뒤 요청을 보내려 할 때, 사람이 다른 창에 다녀왔을 때, 위젯의 단추(로그인, 로그아웃, "확인하고 질문하기", "로그인 없이 계속")를 누른 뒤다. 지금 위젯은 요청마다 토큰 함수를 부른다(`web/apps/widget/components/pages/drivers.ts`를 읽었다). 사용자가 "토큰의 만료시간을 알 수 있지 않아? … 굳이 매 질문마다 새 토큰을 받아야 해?"라고 물었고, 다시 올린 화면에서 "만료 전까지 다시 쓰기"를 골랐다. 얻는 것은 사이트의 서버에 묻는 횟수가 주는 것과, URL 방식에서 창을 연 페이지가 닫혀도 토큰이 끝날 때까지 질문할 수 있다는 것이다. 대가는 사이트의 페이지에서 로그아웃하거나 계정을 바꿔도 위젯이 든 페이지가 새로 뜨지 않으면 토큰이 끝날 때까지 위젯이 앞 사람으로 질문한다는 것이다. 사이트 토큰의 수명 상한은 600초다(`src/agent_os/http/sites.py`의 `MAX_LIFETIME_SECONDS`를 읽었다). 요청마다 새로 받던 까닭 둘(비밀이 브라우저에 남지 않게 한다, 사람이 바뀐 것을 요청마다 알아챈다. `.scratch/web-widget/spec.md`를 읽은 서브에이전트의 보고다)이 토큰의 수명 안에서는 느슨해진다. `serve`가 요청마다 토큰을 검증하는 것은 그대로다.
- **로그인은 새 창이다.** "로그인하고 질문하기"와 "다시 로그인"을 누르면 위젯이 위젯 설정의 로그인 주소를 새 창으로 연다(휴대폰에서는 새 탭). 세 방식에서 같다. 위젯이 든 창은 그대로라 위젯이 닫히거나 다시 열리지 않는다. 사람이 로그인하고 위젯이 든 창으로 돌아오면 위젯이 토큰을 다시 물어 로그인된 것을 알아챈다. 대가는 로그인한 뒤 새 창을 닫고 위젯이 든 창으로 돌아오는 일을 사람이 한다는 것이다. 위젯 미리보기 페이지의 로그인은 끝나면 창이 스스로 닫히게 지을 수 있고, 다른 사이트의 로그인 페이지가 창을 닫아 줄지는 그 사이트의 몫이다. 인터뷰 첫 라운드에서는 위젯이 든 창을 로그인 주소로 보내는 안을 골랐다가, 사용자가 "로그인은 새 창으로 띄어주면 안되나? 그러면 위젯이 닫히거나 다시 열일 없고 위젯 안에서 로그인 할 필요도 없잖아"라고 해 바꿨다. ADR 0059는 "팝업 창으로 로그인한다"를 팝업 차단과 휴대폰에서의 동작을 까닭으로 거부했는데, 이 결정이 그 안을 다시 열어 받아들인다. 사람이 단추를 누른 그 순간에 여는 창은 보통 차단되지 않는다고 알지만 재 보지 않았다(어림). 위젯이 창으로 돌아온 것을 알아채는 코드는 지금 없어 새로 짓는다(`web/apps/widget`에서 `visibilitychange`, `focus`, `pageshow`, `window.open`을 Grep으로 찾아 0건이었다).
- **로그아웃.** 위젯 설정에 로그아웃 주소와 부르는 방법을 둔다. 부르는 방법은 둘 가운데 하나이고 기본은 창 없이 부르기다. 위젯이 그 주소를 브라우저가 쿠키를 실어 보내는 요청으로 직접 부른 뒤 토큰을 다시 묻고, 사이트가 여전히 로그인한 사람의 토큰을 주면 "로그아웃하지 못했습니다" 알림을 보인다. 다른 하나는 새 창으로 열기이고 로그인과 같은 규칙이다(새 창이 열리고, 돌아오면 토큰을 다시 묻는다). 로그아웃 주소를 등록하지 않은 사이트의 위젯에는 로그아웃 단추를 그리지 않는다. 직접 부르기는 페이지 안 방식에서 로그아웃 주소가 위젯이 든 페이지와 같은 출처이면 통한다. 위젯이 사이트의 페이지 안에서 돌아 그 요청이 페이지가 자기 서버에 보내는 것이기 때문이다. 로그아웃 주소가 그 페이지와 다른 출처이면(로그인 서버나 API를 다른 주소에 둔 사이트) 페이지 안 방식에서도 두 출처가 같은 등록 도메인 아래에 있고 그 로그아웃 끝점이 페이지의 출처를 허용할 때만 통한다. iframe 방식과 URL 방식에서는 위젯이 다른 출처에서 돌아, 위젯의 출처와 사이트의 출처가 같은 등록 도메인 아래에 있고 사이트의 로그아웃 끝점이 위젯의 출처를 허용할 때만 통한다. (바뀜: 이력 2026-11-16 "만료 알림의 기본 모양은 대화 안의 카드이고, 창 없이 부르는 로그아웃이 통하는 조건을 재서 고치며, 위젯 미리보기 페이지의 바탕은 기기의 설정을 따른다") 로그인 서버에서도 함께 로그아웃하는 방식(ADR 0059 결정 "로그아웃")은 창이 로그인 서버의 주소로 이동해야 끝나 직접 부르기로는 마치지 못한다. 그런 사이트와 위 조건이 맞지 않는 사이트는 운영자가 새 창으로 열기를 고른다. 이 문단의 통하는 조건은 쿠키와 OIDC의 규격으로 아는 것이고 재 보지 않았다(어림). 위젯 미리보기 페이지는 페이지 안 방식이고(`web/apps/portal/browser/portal.ts`를 읽었다) 로그아웃 끝점도 그 페이지의 것이라(결정 "위젯 미리보기 페이지") 쿠키만 지우는 로그아웃은 기본값으로 통한다. 인터뷰에서는 새 창만 쓰는 안과 사이트의 페이지에 로그아웃을 부탁하는 안을 차례로 올렸고, 사용자가 "로그아웃 API 주소를 위젯 설정에서 받는데 … 그냥 API 호출하면 되는거 아니야?"라고 되물은 뒤 이 안을 골랐다. 대가는 위젯 설정에 칸이 하나 늘고, 지어서 시험할 길이 둘이라는 것이다. ADR 0024는 위젯이 쿠키를 쓰지 않는다고 정했고, 그래서 저절로 실리는 쿠키가 여는 물음(ADR 0019)이 위젯에는 생기지 않는다고 적었다. 그 결정은 범위가 좁아진다. 위젯이 쿠키를 두지 않는 것과 최종 사용자 경로의 인증이 헤더에 실은 사이트 토큰뿐이라는 것은 그대로다. 창 없이 부르는 로그아웃은 브라우저가 사이트의 쿠키를 저절로 싣는 요청이고, 위젯이 그런 요청을 보내는 것은 이것이 처음이다. 그 쿠키가 닿는 곳은 사이트의 로그아웃 끝점이지 Agent OS가 아니고, 다른 출처의 요청이 그 끝점을 부를 수 있게 열지는 사이트가 판단한다(Consequences "신뢰와 노출"). 로그아웃하면 위젯이 주체가 바뀐 것을 보고 저장한 대화를 지우는 것도 지금 그대로다(ADR 0059 결정 "로그아웃").
- **URL 방식.** 임베드 방식이 하나 는다. 위젯 쪽 서버가 내는 위젯 페이지의 주소에 사이트의 이름을 붙인 주소를 사이트의 페이지가 창으로 열면, 그 창 전체가 위젯이다. 창은 자기를 연 페이지에 토큰을 묻는다. 묻고 답하는 메시지는 iframe 방식의 것과 같고, 허용 출처에서 온 답만 받는 것도 같다(지금 iframe 방식은 `web/apps/widget/lib/token.ts`가 부모 창에 묻고 허용 출처의 답만 받는다. 읽었다). 그래서 사이트의 회원 로그인이 그대로 이어진다. 사이트는 자기 서버에서 토큰을 서명하고, 창을 여는 페이지에 답하는 스크립트를 넣어야 한다. 창을 연 페이지가 닫히거나 다른 곳으로 가면 위젯은 토큰을 더 받지 못하고, 받아 둔 토큰이 끝날 때까지만 질문할 수 있다. 끝난 뒤에는 "이 창을 연 페이지에서 다시 열어 주세요" 한 문장을 보이고 입력을 막는다. 주소를 직접 열어 연 페이지가 처음부터 없을 때도 같은 문장이다. 지금 위젯 페이지를 최상위 창으로 열면 토큰 요청이 자기 창에 가고 10초 뒤 "로그인 정보를 받지 못했습니다."가 된다(코드의 흐름을 따라 읽은 서브에이전트의 보고다). 자기를 연 창에 묻는 코드는 지금 없어 새로 짓는다. 창을 여는 쪽이 연 창과의 연결을 끊는 옵션으로 열면 위젯은 물을 곳이 없다. 위젯 앱의 코드에는 그 연결을 끊는 응답 헤더가 없지만(`web/apps/widget`을 `Opener`와 `Cross-Origin`으로 Grep해 0건이었다) 프록시가 내는 헤더는 보지 않았다(어림).
- **위젯 설정.** 사이트마다 달라지지 않는 값은 위젯 설정(`CONTEXT.md`)에 둔다. 사용자가 "위젯 관리자 페이지에서 위젯 설정으로 등록하면 되는거 아니야? … 굳이 토큰에 담을 필요가... 보일 이름정도만 토큰에서 받고 바뀌는 값들"이라고 했다. 위젯 설정은 위젯 쪽 서버가 데이터베이스에 들고, 운영자가 위젯 설정 관리 화면에서 등록한다. 추천은 위젯을 내주는 서버의 설정 파일이었고 사용자가 "위젯 서버의 데이터베이스"라고 답했다. 위젯은 임베드 속성(URL 방식은 주소)에 적힌 사이트의 이름 하나로, 뜰 때 자기 쪽 서버에서 그 사이트의 위젯 설정을 받아 온다. 지금 위젯이 임베드 속성으로 받는 다섯 값(`agent`, `heading`, `intro`, `theme`, `mode`)도 위젯 설정에 등록할 수 있다. 임베드 속성에 값을 따로 적으면 그 값이 위젯 설정보다 앞서므로, 지금처럼 다섯 값을 적는 사이트는 그대로 동작한다. 사이트의 이름을 적지 않은 위젯은 위젯 설정을 받아 오지 않고 임베드 속성의 값을 지금처럼 쓴다. 로그인 주소와 고지의 글이 위젯 설정에만 있으므로 그 위젯에는 로그인 단추와 고지가 나오지 않는다. 다크 모드 스위치와 토큰 다시 쓰기는 사이트의 이름과 무관하게 모든 위젯에 든다. (바뀜: ADR 0064) 위젯은 토큰을 받기 전에도 고지와 로그인 단추를 그려야 하므로 위젯 설정을 사이트 토큰 없이 받아 온다. 그래서 위젯 설정에는 비밀을 두지 않는다.
- **0.1 판에 넣는다.** 위젯 설정의 데이터베이스와 위젯 설정 관리 화면은 0.1 판을 내는 조건이다. 추천("0.1 판 뒤, 그때까지 파일")과 달리 사용자가 "0.1 판에 넣기"를 골랐다. 대가는 0.1 판 전에 정하고 지을 것이 는다는 것이다. 이 저장소에는 지금 데이터베이스가 없고(`docs/constitution/tech.md`를 SQLite, Postgres, 데이터베이스, DB로 Grep해 0건이었다), 종류를 고르는 결정, 위젯 설정 관리 화면에 누가 들어오는지, 백업과 복원, 배포 꾸러미에 넣는 일이 함께 붙는다.
- **0.1 판에서 등록하는 것.** 글과 고르는 값이다. 글은 위젯의 이름, 소개 한 줄, 입력창 안내 문구, 고지의 짧은 줄과 전문, 로그인 주소, 로그아웃 주소다. 고르는 값은 에이전트, 색 테마 넷 가운데 하나, 처음 밝기, 로그인 시간이 끝났을 때 알림의 모양, 로그아웃을 부르는 방법이다. (바뀜: ADR 0064) 사용자는 맞춤을 더 넓혀 달라고 했다("챗봇 이름, 챗봇 아이콘 업로드, url은 파비콘 업로드, 배경 이미지 업로드 또는 배경색 변경할 수 있는 컬러팔레트, 인풋창 플레이스홀더 문구, 고지 문구 등 … 만료 알림의 모양 같은 것도 선택할 수 있도록"). 그 가운데 그림 올리기(위젯 아이콘, URL 방식 창의 파비콘, 배경 이미지)와 자유 색은 widget-appearance 행이 0.1 판 뒤에 맡는다. 사용자가 "글과 고르는 값 먼저"를 골랐다. 까닭은 둘이다. 그림 올리기는 파일을 저장하고 검사하는 일(형식, 크기, 그림 파일에 숨은 스크립트)이 따로 든다(어림, 재지 않았다). 자유 색과 배경 이미지는 디자인 시스템이 스토리 테스트로 판정하는 명암비(테마 넷과 모드 둘의 여덟 벌, `.claude/rules/web-design.md`를 읽었다)를 벗어나 따로 설계가 필요하다. 입력창 안내 문구는 지금 위젯 코드의 상수다(`web/apps/widget/components/organisms/Composer.tsx`를 읽었다).
- **Agent OS는 바뀌지 않는다.** `serve`, Agent OS의 관리 화면과 관리 API, 사이트 파일, `openapi.json`은 위젯 설정을 모른다. 의존은 위젯에서 Agent OS로 한쪽이라는 ADR 0047의 방향과, 관리 화면과 관리 API에 위젯 전용 기능을 두지 않는다는 결정은 그대로다. 바뀌는 것은 ADR 0047의 다른 두 자리다. 임베드 옵션이 값을 정하고 기본값을 위젯 배포의 설정 파일에 둔다는 결정이 위젯 설정으로 바뀌고, 그 ADR이 거부한 "위젯 전용 서버(저장소, 인증, 관리 화면)"를 다시 열어 받아들인다. 그때의 근거는 저장할 것이 사이트별 값 몇 개라는 것이었다. 지금은 운영자가 화면에서 등록하는 값이 늘었고 사용자가 그 저장소와 화면을 0.1 판에 넣기로 했다.
- **이 ADR이 정하지 않는 것.** 위젯 쪽 서버를 어느 프로그램으로 세울지, 데이터베이스의 종류, 위젯 설정 관리 화면의 로그인, 맞춤 항목의 목록, 백업과 복원, 배포 꾸러미에 넣는 일, 위젯이 위젯 설정을 받아 오는 주소와 답의 모양은 '위젯 설정 관리' 행의 설계 인터뷰가 사실을 재며 정한다. 사용자가 "새 행의 설계 인터뷰에서"를 골랐다. 재 볼 것이 많기 때문이다. 위젯 앱에는 서버 코드를 둘 수 없어(워크스페이스가 Next의 서버 파일을 금지하고 ADR 0024가 그 예외를 거부했다) 서버의 자리부터 골라야 하고, 데이터베이스는 이 저장소에 처음이다. 그 인터뷰에 셋을 더 넘긴다. 위젯 미리보기 페이지 설정이 지금 드는 값(이름, 소개, 색, 밝기, 고지)을 위젯 설정으로 옮기는 방법과 처음 띄웠을 때의 값, 위젯 미리보기 페이지가 사이트의 고지 글과 무관하게 고지 전문에 넣는 문장 둘(익명 식별자를 둔다는 문장은 지금 넣고 있고, 질문이 로그인한 계정과 함께 기록된다는 문장은 ADR 0059 결정 "고지 확인"이 넣기로 했다)을 누가 보장하는지, 다크 모드 스위치를 숨기는 값을 둘지다. 마지막 것은 이 ADR의 "늘 사람이 고르기"와 부딪히므로 그 인터뷰가 사용자에게 다시 묻는다.
- **위젯 미리보기 페이지.** 위젯 미리보기 페이지도 사이트이므로 같은 약속을 따른다. 그 페이지에 남는 것은 사이트 고르기, 보고서 링크, 사이트 토큰을 내는 일, 고지 확인의 기록, 로그인과 로그아웃의 끝점(ADR 0059)이다. 띠의 다크 모드 스위치, 고지 확인 덮개와 짧은 고지 줄, 로그인 단추 줄은 그리지 않고 위젯이 그린다. 그 페이지의 토큰 끝점은 새 토큰 답(보일 이름과 상태)을 내고, 위젯이 알린 고지 확인을 받아 기록한다.
- **기능 행.** 새 행 widget-login-state가 위젯 쪽 일 전부를 맡는다. 로그인 상태의 화면, 고지의 줄과 덮개, 다크 모드 스위치, 새 창 로그인, 로그아웃, URL 방식, 토큰 다시 쓰기, 위젯 설정 받아 오기, 그리고 위젯 미리보기 페이지를 이 약속으로 옮기는 일이다. 익명 모드의 사이트만으로 끝까지 시험할 수 있다. portal-admin 행은 '위젯 설정 관리'(위젯 쪽 서버의 데이터베이스와 위젯 설정 관리 화면)로 고쳐 세우고 0.1 판의 조건에 넣는다. 순서는 portal-admin, widget-login-state, portal-login, step-up-login, pilot-release다. widget-login-state가 portal-admin을 기다리는 까닭은 위젯이 위젯 설정을 받아 오는 주소와 답의 모양이 그 행에서 정해지기 때문이다. (바뀜: ADR 0064) portal-login은 widget-login-state 뒤에서 사내 로그인(OIDC, ADR 0059)만 맡는다. 사용자가 "위젯 행을 새로 세우기"를 골랐다. 행마다 명세와 리뷰가 작아지고, 대가는 0.1 판까지의 길에 행이 늘고 portal-login이 그 행을 기다린다는 것이다.

## Considered Options

- **URL 방식의 창을 위젯 미리보기 페이지의 서버가 통째로 낸다.** 설계 인터뷰의 추천이었다. 운영자가 설정에 사이트를 적으면 주소가 생기고, 사이트는 그 주소를 열기만 하면 되어 서버도 코드도 필요 없다. 사용자가 "고객사 페이지가 토큰 제공"을 골랐다. 추천안은 사이트의 회원 로그인과 이어지지 않고, 미리보기용이던 서버가 실제 최종 사용자의 질문을 받게 된다. 두 가지를 모두 내는 안도 고르지 않았다.
- **위젯이 든 창을 로그인 주소로 보낸다.** 첫 라운드에서 골랐던 안이다. 사이트는 코드 없이 주소만 적으면 된다는 것은 새 창과 같다. 위젯이 든 창이 떠났다 돌아와 위젯이 다시 열리고, URL 방식에서는 위젯 창이 통째로 로그인 페이지가 된다. 사용자가 새 창으로 바꿨다. URL 방식에서 위젯 창이 이동하는 안(추천이었다)과 창을 연 페이지가 이동하는 안도 같은 답으로 접었다.
- **로그인 주소와 고지의 글을 토큰 답에 모두 싣는다.** 설계 인터뷰의 추천이었다. 통로가 하나이고 서버가 늘지 않는다. 사용자가 달라지지 않는 값을 토큰 답에 실을 까닭이 없다고 해 위젯 설정으로 갔다. 달라지지 않는 글을 임베드 속성에 적는 안도 고르지 않았다.
- **위젯 설정을 위젯을 내주는 서버의 설정 파일에 둔다.** 추천이었다. ADR 0047이 기본값의 자리로 적어 둔 곳이고 데이터베이스가 필요 없다. 운영자가 화면에서 고치는 일은 portal-admin 행이 나올 때까지 없다. 사용자가 데이터베이스를 골랐다.
- **위젯 설정을 위젯 미리보기 페이지 설정에 더한다.** 고르지 않았다. 위젯 미리보기 페이지를 쓰지 않는 사이트의 위젯이 그 페이지의 서버에 기대게 된다.
- **위젯 설정을 Agent OS 서버가 든다.** 고르지 않았다. ADR 0047이 거부한 안(위젯 맞춤 설정을 관리 화면의 사이트 메뉴에 두고 `serve`가 공개 경로로 내준다)이고, 관리 화면과 `serve`가 위젯을 알게 된다.
- **데이터베이스와 위젯 설정 관리 화면을 0.1 판 뒤에 짓고 그때까지는 파일에서 읽는다.** 추천이었다. 위젯이 설정을 받아 오는 약속은 저장하는 곳과 무관하게 같아 나중에 옮겨도 사이트의 페이지와 위젯은 바뀌지 않는다. 사용자가 "0.1 판에 넣기"를 골랐다.
- **지금처럼 요청마다 토큰을 새로 받는다.** 사람이 바뀐 것을 요청마다 알아챈다. 사용자가 만료 시각까지 다시 쓰기를 골랐다. URL 방식에서 창을 연 페이지가 닫혔을 때 곧바로 안내하고 입력을 막는 안(추천이었다)은 이 답으로 접었다.
- **로그인 거절을 사이트가 자기 화면에 알린다.** 추천이었다. 위젯의 약속에 상태가 하나 덜 들어간다. 사용자가 "위젯이 그리기"를 골랐다. 추천안은 거절 문장의 생김새가 위젯의 다른 알림과 따로이고 사이트마다 알리는 방식이 다를 수 있다.
- **밝기를 정한 사이트의 위젯은 고정하고 스위치를 그리지 않는다.** 추천이었다. 자기 페이지의 밝기에 위젯을 맞춰 둔 사이트의 화면이 바뀌지 않는다. 사용자가 "늘 사람이 고르기"를 골랐다.
- **다크 모드의 값을 탭 저장소에만 둔다, 또는 기억하지 않는다.** 고르지 않았다. 사용자가 "브라우저에 계속 기억"을 골랐다.
- **위젯 미리보기 페이지 띠의 스위치를 남긴다.** 고르지 않았다. 남기면 그 페이지의 위젯이 다른 사이트에 넣은 위젯과 다르게 동작한다.
- **로그아웃을 새 창으로만 한다.** 첫 화면에서 추천이었고 사용자가 고르며 되물었다. 세 방식에서 같은 동작이지만 쿠키만 지우는 로그아웃에도 창이 하나 열린다. 부르는 방법의 한 값으로 남겼다.
- **위젯이 사이트의 페이지에 로그아웃을 부탁한다.** 둘째 화면의 추천이었다. 사이트의 페이지가 자기 출처에서 자기 서버를 부르므로 세 방식 모두에서 쿠키가 실리고 로그아웃 주소를 등록하지 않아도 된다. 사용자가 받지 않았다. 사이트의 스크립트에 갈래가 하나 늘고, URL 방식에서 창을 연 페이지가 닫혀 있으면 부탁할 곳이 없다.
- **로그아웃을 직접 부르기로만 한다.** 고르지 않았다. 다른 등록 도메인의 iframe 방식과 URL 방식, 로그인 서버에서도 함께 로그아웃하는 사이트에서 위젯의 단추를 쓸 수 없게 된다(어림).
- **그림 올리기와 자유 색까지 0.1 판에 넣는다.** 고르지 않았다. 까닭은 결정 "0.1 판에서 등록하는 것"에 적었다.
- **위젯 쪽 일을 portal-login 행에 함께 둔다.** 고르지 않았다. 행 하나가 위젯의 공개 표면, 위젯 미리보기 페이지의 이전, 사내 로그인을 함께 들어 명세와 리뷰가 커진다.

## Consequences

- **위젯의 공개 표면이 바뀐다.** `web/apps/widget/EMBED.md`가 사이트에 약속한 것 가운데 이 ADR의 결정이 닿는 문장은 모두 바뀐다. 지금 아는 것은 다섯이다. 임베드 속성에 사이트의 이름 하나가 늘고, `mode`의 뜻이 고정에서 처음 값으로 바뀌며, 토큰을 내주는 통로의 답과 위젯이 그 통로에 싣는 것이 늘고, 위젯이 토큰을 묻는 때가 요청마다에서 결정 "토큰을 만료 시각까지 다시 쓴다"의 넷으로 바뀌며(`EMBED.md`는 지금 "위젯은 요청을 보낼 때마다 이 함수를 부른다."라고 적는다. Grep으로 봤다), URL 방식이 더해진다. 다섯은 예시이고, 공개 표면을 고치는 티켓이 `EMBED.md`를 처음부터 끝까지 이 ADR에 대 본다. 토큰 글자만 답하는 사이트와 임베드 속성 다섯만 적는 사이트는 페이지를 고치지 않아도 된다. 다만 그런 사이트의 위젯도 둘이 달라진다. 모든 위젯에 다크 모드 스위치가 새로 나타나 `mode`를 적어 둔 사이트에서도 사람이 다른 밝기를 고를 수 있고, 위젯이 토큰 함수를 요청마다 부르지 않게 된다. (바뀜: ADR 0064) 공개 표면을 바꿀 때 옛 이름을 한동안 함께 받는다는 규칙(`web/apps/widget/EMBED.md` "지킬 것")은 그대로 따른다. 이 표면을 고치는 티켓이 widget-login-state의 첫 티켓이고 다른 티켓을 막는다.
- **ADR 0059의 공개 표면과 ADR 0060의 로그인 통로.** ADR 0059는 portal-login이 위젯의 공개 표면을 바꾸지 않는다고 적었다. 그것은 portal-login 행에 대해서는 여전히 참이다. 공개 표면은 그 앞의 widget-login-state가 바꾼다. ADR 0060이 공개 표면에 더하기로 한 통로(그 ADR의 말로 페이지가 "로그인을 맡겠다"고 위젯에 알리는 길)는 두지 않는다. 위젯 설정에 로그인 주소가 있는 사이트에서만 위젯이 로그인 요구의 안내에 단추를 그리고, 누르면 새 창 로그인을 한다. 로그인 주소가 없는 사이트에서는 단추 없이 "이 사이트에서는 답할 수 없는 질문입니다"만 그린다(그 문장은 ADR 0060 그대로다).
- **ADR 0060의 다시 보내기와 넘겨받기.** ADR 0060은 로그인이 같은 탭의 이동이라 페이지가 다시 열리고 위젯이 저장한 대화를 되살린 뒤 표시된 질문을 다시 보낸다고 적었다. 새 창 로그인에서는 위젯이 든 창이 이동하지 않는다. 위젯은 사람이 돌아와 새로 받은 토큰에 로그인 확인 표시가 있으면 표시된 질문을 한 번 다시 보낸다. 위젯이 탭 저장소에 둔 대화가 로그인 서버에 다녀온 뒤에도 남는지를 재기로 한 것(ADR 0060 결정 "시험과 수락", ADR 0059 결정 "시험")은 위젯이 든 창이 이동하지 않아 이 흐름에서는 걸리지 않는다. 돌거나 멈춘 익명 실행을 넘겨받지 않고 그 교환을 끝내지 못한 교환으로 닫는다는 결정은 그대로이고, 페이지가 다시 열리지 않는 채 주체가 바뀔 때 열린 스트림을 어떻게 닫는지는 step-up-login의 명세가 짓는다.
- **신뢰와 노출.** 토큰을 다시 쓰는 동안에는 사이트에서 일어난 로그아웃과 계정 바꿈이 최대 토큰의 수명만큼 늦게 위젯에 닿는다. 여럿이 쓰는 PC에서 앞사람이 사이트의 페이지에서 로그아웃하고 위젯이 든 창을 그대로 두면, 그 창의 위젯은 토큰이 끝날 때까지 앞사람의 것이다. 위젯 미리보기 페이지가 내는 토큰의 수명 120초(ADR 0050 결정 "토큰")는 위젯이 요청마다 새 토큰을 받는다는 것을 전제로 고른 값이다. 다시 쓰기에서는 그 수명이 위젯이 그 페이지에 다시 묻는 간격이자 로그아웃이 늦게 닿는 시간의 상한이 되므로, 그 값을 그대로 둘지는 widget-login-state의 명세가 다시 본다. 위젯의 로그아웃 단추와 다른 창에 다녀오는 일은 토큰을 다시 묻게 하므로 이 틈은 사람이 위젯이 든 창을 떠나지 않은 채 다른 길로 로그아웃한 경우에만 남는다. 위젯 설정의 로그인 주소와 로그아웃 주소는 위젯이 사람의 브라우저에서 열거나 부르는 주소라, 위젯 설정 관리 화면에 들어온 사람이 그것을 바꾸면 최종 사용자를 다른 곳으로 보낼 수 있다. 그래서 그 화면의 로그인과 주소의 검사는 '위젯 설정 관리' 행의 설계가 먼저 정할 것이다. 창 없이 부르는 로그아웃이 다른 출처에서 통하려면 사이트가 자기 로그아웃 끝점을 위젯의 출처에 열어야 하고, 그 판단은 사이트의 몫이다. (바뀜: 이력 2026-11-16 "만료 알림의 기본 모양은 대화 안의 카드이고, 창 없이 부르는 로그아웃이 통하는 조건을 재서 고치며, 위젯 미리보기 페이지의 바탕은 기기의 설정을 따른다")
- **운영.** 위젯 쪽에 서버와 데이터베이스와 위젯 설정 관리 화면이 생겨 띄우고 백업할 것이 는다. 스택이 바뀌는 결정(데이터베이스의 종류)은 '위젯 설정 관리' 행의 ADR이 `docs/constitution/tech.md`와 함께 다룬다. 이 ADR은 스택을 바꾸지 않는다.
- **재지 않은 것.** 아래는 어림이고 적힌 행이 잰다. 단추를 누른 순간에 여는 새 창이 차단되지 않는지와 휴대폰에서의 동작, 위젯이 창으로 돌아온 것을 알아채는 신호가 세 방식에서 모두 오는지, URL 방식의 창이 자기를 연 페이지와 메시지를 주고받는지(프록시의 헤더 포함), iframe 방식에서 브라우저 저장소의 값이 남는지는 widget-login-state의 e2e가 잰다. 창 없이 부르는 로그아웃이 통하는 조건은 widget-login-state의 명세가 재고, 로그인 서버에서도 함께 로그아웃하는 사이트에서 새 창으로 여는 로그아웃은 portal-login의 e2e가 잰다. (바뀜: 이력 2026-11-16 "만료 알림의 기본 모양은 대화 안의 카드이고, 창 없이 부르는 로그아웃이 통하는 조건을 재서 고치며, 위젯 미리보기 페이지의 바탕은 기기의 설정을 따른다") (바뀜: 이력 2026-11-16 "URL 방식의 창이 자기를 연 페이지와 메시지를 주고받는 조건을 쟀다") 재서 어긋나면 이 결정의 그 대목을 이력으로 다시 본다.
- **다른 ADR.** 이 ADR이 본문의 문장을 바꾸는 ADR에 포인터를 단다. 달린 자리는 그 ADR마다 `(바뀜: ADR 0061)`로 찾는다. ADR 0024(임베드 방식이 둘이라는 문장, 요청마다 토큰을 새로 받는다는 결정, 쿠키를 쓰지 않아 ADR 0019의 물음이 생기지 않는다는 문장), ADR 0047(임베드 옵션이 값을 정하고 기본값을 설정 파일에 두며 맞춤 설정 화면을 사이트 쪽이나 떼어 낸 뒤의 위젯 프로젝트에 만든다는 결정, 운영자가 위젯 외형을 사이트 쪽에서 바꾼다는 문장), ADR 0050(위젯이 요청마다 새 토큰을 받는다는 문장, 위젯 미리보기 페이지가 그리는 고지 확인 덮개와 짧은 고지와 로그인 단추, 위젯은 바뀌지 않는다는 문장, portal-admin과 widget-appearance 행의 자리), ADR 0059(같은 탭의 로그인과 팝업을 쓰지 않는다는 결정, 로그인 전의 단추와 만료 알림을 페이지가 그린다는 결정, 질문마다 토큰을 새로 받아 만료가 그때 드러난다는 문장, 탭 저장소를 e2e로 잰다는 문장), ADR 0060(로그인 통로, 계약이 바뀌는 자리의 셈, 같은 탭의 이동을 전제로 한 다시 보내기, 탭 저장소를 e2e로 잰다는 문장, 명세가 짓는 통로의 모양)이다. 거부한 안의 근거 문장과 이력 항목에는 달지 않는다(`.claude/rules/adr.md`). ADR 0047이 거부한 위젯 전용 서버, ADR 0059가 거부한 팝업 로그인, ADR 0026의 2026-10-06 이력이 거부한 "최종 사용자도 위젯에서 고른다"를 다시 연 것은 이 ADR의 결정에 적었다. ADR 0046에는 widget-login-state와 portal-admin이 기준선의 행이 된다는 이력을 쌓는다.
- **구현 티켓이 코드와 같은 티켓에서 고치는 문서.** `web/apps/widget/EMBED.md`(속성 표, 토큰 답, 토큰을 묻는 때, URL 방식, "지킬 것"의 공개 표면 목록), `.scratch/pilot-portal/spec.md`가 적은 위젯 미리보기 페이지의 화면이다. 그 글들은 지금의 코드를 적은 것이라 이 ADR이 아니라 코드를 바꾸는 티켓이 고친다. 위젯의 알림 문구 "위젯 설정이 올바르지 않습니다."(`EMBED.md`와 위젯 코드를 Grep으로 봤다)는 위젯을 넣은 자리가 틀렸을 때의 글이라(`EMBED.md`는 `agent` 속성이 틀렸을 때와 번들이 자기 `<script>`를 찾지 못했을 때를 든다) 새 용어 위젯 설정과 뜻이 다르고, 그 문구를 바꿀지는 공개 표면을 고치는 티켓이 본다. `CONTEXT.md`의 위젯 미리보기 페이지와 위젯 미리보기 페이지 설정은 그 페이지의 설정 파일이 드는 값을 위젯 설정으로 옮기는 방법이 정해진 뒤에 고친다('위젯 설정 관리' 행의 설계 인터뷰에 넘긴 것이다).
- **용어.** `CONTEXT.md`에 위젯 설정을 더했다. 그 말은 사이트 파일과 위젯 미리보기 페이지 설정의 피할 말이었고, 두 항목의 피할 말을 따로 있는 용어를 가리키게 고쳤다. 고지의 뜻도 고쳤다. 고지는 위젯 미리보기 페이지가 알리는 글이었고, 이 ADR로 위젯이 알리는 글이 되어 사이트마다의 글은 위젯 설정에 든다. 고지 확인의 뜻은 바뀌지 않는다.
- **다른 행.** 새 행 widget-login-state를 세운다. 슬라이스 9이고 portal-admin을 기다린다. (바뀜: ADR 0064) portal-admin은 '위젯 설정 관리'로 고쳐 슬라이스 9로 옮긴다. 그 행이 앞서 넘겨받은 것(위젯 미리보기 페이지 설정을 화면에서 고치기, 사이트 파일의 허용 출처와 요청 글자 수 상한, 로그인 서버 항목 고르기, release-image 명세가 넘긴 위젯 이미지의 뒷일)을 0.1 판에 넣을지는 그 행의 설계 인터뷰가 사용자에게 다시 묻는다. 이 ADR은 그 넷을 0.1 판에 넣는다고도 뺀다고도 정하지 않는다. 그 가운데 위젯이 사이트 파일의 값을 실행 중에 읽게 고치는 일은 사용자가 portal-admin을 만들 때 함께 하기로 골랐던 것이라(ADR 0056), 그 행이 0.1 판으로 당겨진 지금도 함께 하는지를 사용자가 정한다. 로그인 서버 항목은 portal-login이 짓는데 새 순서에서는 portal-admin이 그보다 앞이라, 그 항목을 화면에서 고르는 일을 어느 행의 어느 자리에 둘지도 그 인터뷰가 정한다. portal-login은 widget-login-state를 기다리고, 그 기능 계획의 "위젯의 공개 표면을 바꾸지 않는다"는 그대로 참이며 화면을 그리는 일(`/ui-design`)은 widget-login-state로 옮긴다. widget-appearance는 그림 올리기와 자유 색을 맡고, 새 모양 값을 임베드 속성과 위젯 미리보기 페이지 설정이 아니라 위젯 설정에 더하며, 0.1 판 뒤의 행이라 portal-admin과 widget-login-state와 pilot-release를 기다린다. step-up-login의 기능 계획에는 로그인 통로가 위젯 설정의 로그인 주소로 바뀐 것과 탭 저장소를 재는 일이 걸리지 않게 된 것을 적는다. pilot-release는 0.1 판의 조건이 된 portal-admin을 직접 기다리고, widget-login-state는 portal-login과 step-up-login을 거쳐 기다린다.
- **화면.** 명세 전에 `/ui-design widget-login-state`로 위젯 안의 화면을 새 시작 프롬프트 파일로 다시 그린다. `.scratch/portal-login/design/screens-prompt.md`는 위젯 바깥에 그리는 화면의 시작 프롬프트라 쓰지 않는다. 탐색 화면은 일지 2026-11-13-0426이 가리키는 아티팩트에 남아 있다. 그 탐색에서 사용자가 고른 것 셋은 입력으로 넘긴다. 이름 줄은 빛나는 형광 초록 점과 이름과 보조 단추 "로그아웃"이고, 만료 알림의 기본 모양은 위젯 상자를 덮는 상자이며, 거절 알림은 무엇이 막혔는지 한 문장만 보인다(일지 2026-11-13-0426 "다음"의 넘길 입력). (바뀜: 이력 2026-11-16 "만료 알림의 기본 모양은 대화 안의 카드이고, 창 없이 부르는 로그아웃이 통하는 조건을 재서 고치며, 위젯 미리보기 페이지의 바탕은 기기의 설정을 따른다") 만료 알림의 다른 모양은 그 화면 작업이 후보를 그린다.
- **명세가 짓는 것.** widget-login-state의 명세가 짓는 것은 다음이다. 임베드 속성의 이름, 토큰 답의 꼴(이름과 상태를 싣는 모양, 로그인으로 확인한 사람의 토큰인지를 싣는 방법), 위젯이 통로에 싣는 알림의 꼴, 페이지 안 방식과 메시지 방식에서 그것이 어떻게 다른지, URL 방식의 주소 모양, URL 방식에서 위젯이 답을 보낸 창을 가리는 방법과 창을 연 페이지가 토큰을 보낼 창을 가리는 방법(iframe 방식은 위젯이 답을 보낸 창이 부모 창인지를 보고 사이트는 그 위젯 iframe의 창에만 보낸다, ADR 0024 Consequences "임베드의 모양"), 브라우저 저장소의 키와 그 값을 사이트마다 따로 기억할지, 만료 시각보다 얼마나 앞서 새로 물을지, 창으로 돌아온 것을 알아채는 신호, 로그아웃 요청의 메서드, 위젯 설정에 로그인 주소가 없는데 사이트가 로그인하지 않음이라고 답했을 때의 화면, 위젯 설정을 받아 오지 못했을 때의 화면, 임베드 속성 `agent`를 적지 않은 위젯이 위젯 설정의 에이전트로 뜨는 차례와 어느 쪽에도 에이전트가 없을 때의 화면(지금은 `agent`가 필수이고 없으면 위젯이 알림 "위젯 설정이 올바르지 않습니다."를 보이고 입력창을 막는다고 `web/apps/widget/EMBED.md`의 속성 표가 적으며, `web/apps/widget/lib/embed.ts`의 `readEmbed`가 그 속성이 없으면 문제로 올린다. 둘 다 읽었다), 토큰을 새로 묻는 때가 겹칠 때(앞선 물음의 답이 오기 전에 다른 때가 올 때)와 토큰이 끝나기 직전에 보낸 요청이 끝난 토큰으로 `serve`에 닿았을 때 위젯이 하는 일, 새 창을 열지 못했을 때(브라우저가 막았을 때)의 화면, 알림과 단추의 문구다.

## 이력

### 2026-11-16 만료 알림의 기본 모양은 대화 안의 카드이고, 창 없이 부르는 로그아웃이 통하는 조건을 재서 고치며, 위젯 미리보기 페이지의 바탕은 기기의 설정을 따른다

widget-login-state의 화면 작업과 명세(`.scratch/widget-login-state/spec.md`)가 본문의 세 대목을 바꿨다. 다른 결정은 그대로다.

첫째는 만료 알림의 기본 모양이다. Consequences "화면"은 기본 모양을 위젯 상자를 덮는 상자라고 적었다. 화면 작업이 세 모양(대화 안의 카드, 위젯을 덮는 상자, 입력창 위 띠)을 그린 뒤 사용자가 세 모양을 모두 고르는 값으로 두고 기본을 대화 안의 카드로 골랐다(일지 2026-11-15-1319의 "고를 갈래, 첫 라운드"와 "둘째 라운드", `.scratch/widget-login-state/design/README.md`). 덮는 상자는 운영자가 위젯 설정에서 고르는 값으로 남는다. 만료 알림의 모양이 고르는 값이고 셋이라는 결정 "0.1 판에서 등록하는 것"은 그대로다.

둘째는 창 없이 부르는 로그아웃이 통하는 조건이다. 결정 "로그아웃"은 그 조건을 어림으로 적었고 Consequences "재지 않은 것"이 명세에 재라고 넘겼다. 프로브 `.scratch/widget-login-state/probes/logout_fetch/`가 Playwright의 Chromium 153(기본 프로필)에서 쟀다. 잰 것은 요청을 보내는 문서와 로그아웃 주소의 짝 일곱(페이지 안 방식 셋, iframe 방식 둘, URL 방식 둘), 쿠키의 `SameSite` 셋, 부르는 법 다섯이고, 명세가 고른 부르는 법(`mode: "cors"`, `redirect: "manual"`)이 그 다섯에 든다. 본문과 다른 대목이 둘이다. 하나는 "끝점이 출처를 허용할 때만 통한다"다. 끝점이 204로 답한 갈래에서는 같은 자리와 같은 `SameSite`에서 끝점이 CORS 응답 머리를 내든 내지 않든 결과가 같았고, 끝점이 303으로 답한 갈래에서도 명세가 고른 부르는 법으로 부른 칸은 그랬다. 위젯은 응답을 읽지 않고 토큰을 다시 물어 판정하므로(결정 "로그아웃"이 정한 방법이다) 응답을 읽을 허락이 필요 없고, 통하는지를 가른 것은 쿠키가 요청에 실리느냐였다. 끝점이 요청의 `Origin`을 보고 거절하면 통하지 않을 것이다(어림, 그런 끝점은 재지 않았다). 끝점이 받는 `Origin`은 페이지 안 방식에서 페이지의 출처이고 iframe 방식과 URL 방식에서 위젯의 출처였다(쟀다). 다른 하나는 "같은 등록 도메인 아래에 있을 때만 통한다"다. `SameSite`가 `Lax`나 `Strict`인 쿠키에는 맞았다. 요청을 보내는 문서와 로그아웃 주소의 등록 도메인이 다른 세 자리(페이지 안 방식에서 로그아웃 주소가 다른 등록 도메인에 있는 자리, iframe 방식과 URL 방식에서 위젯의 출처가 사이트와 다른 등록 도메인인 자리)에서 그 쿠키는 실리지 않았다. `SameSite=None` 쿠키는 그 세 자리에서도 요청에 실렸고 지워졌다. 그 결과는 서드파티 쿠키를 막는 브라우저나 설정에서 다를 수 있다(어림). 재지 못한 것은 Firefox와 WebKit, 제품 브라우저, iframe 방식과 URL 방식에서 로그아웃 주소가 사이트의 페이지와 다른 출처인 자리, `Origin`을 보고 거절하는 끝점, GET으로 받는 로그아웃, 로그인 서버에서도 함께 로그아웃하는 방식이다(그 프로브의 `README.md` "재지 못한 것"). 위젯이 보내는 요청의 모양과 운영자에게 권하는 것은 명세의 "로그아웃"이 정한다. 부르는 방법이 둘이고 기본이 창 없이 부르기라는 결정은 그대로다. 이 대목에 포인터를 단 자리는 셋이다. 결정 "로그아웃"의 통하는 조건, Consequences "신뢰와 노출"의 끝 문장, Consequences "재지 않은 것"이다. "신뢰와 노출"은 사이트가 자기 로그아웃 끝점을 위젯의 출처에 열어야 한다고 적었는데, 잰 범위에서는 끝점이 CORS 응답 머리로 출처를 허용할 필요가 없었다. 사이트가 판단할 것은 그 끝점이 다른 출처에서 온 POST를 `Origin`을 보고 거절할지와, 등록 도메인이 다른 자리에서 쓰려면 로그인 쿠키를 `SameSite=None`으로 낼지다. "재지 않은 것"이 어림이라고 적은 것 가운데 이 조건은 이제 Chromium에서 잰 것이다.

셋째는 위젯 미리보기 페이지의 바탕이다. 결정 "다크 모드 스위치"는 그 페이지의 바탕이 사이트가 정한 밝기(없으면 시스템 설정)를 따른다고 적었다. 그 뒤 ADR 0064가 그 페이지의 설정 파일에서 `mode` 칸을 빼(결정 "위젯 미리보기 페이지 설정") 그 페이지는 사이트가 정한 밝기를 알지 못한다. 명세는 그 페이지가 바탕 하나를 위해 위젯 설정을 따로 받아 오게 하지 않고, 바탕이 기기의 설정을 따르게 했다(명세의 "위젯 미리보기 페이지"). 이력을 승인받는 화면에서 사용자가 "보는 사람 기기의 설정 따르기"를 골랐고, 고르지 않은 안은 그 페이지가 위젯 설정을 한 번 더 받아 와 바탕을 처음 밝기에 맞추는 것이다(일지 2026-11-16-1242 "ADR 이력 승인"). 위젯과 바탕의 밝기가 다를 수 있다는 본문의 대가는 그대로이고, 처음 밝기를 등록한 사이트에서는 사람이 스위치를 누르기 전에도 다를 수 있다.

### 2026-11-16 URL 방식의 창이 자기를 연 페이지와 메시지를 주고받는 조건을 쟀다

Consequences "재지 않은 것"은 URL 방식의 창이 자기를 연 페이지와 메시지를 주고받는지를 widget-login-state의 e2e에 넘겼다. 그 결과가 결정 "URL 방식"을 다시 보게 할 수 있어, 명세(`.scratch/widget-login-state/spec.md`)를 쓰는 자리에서 프로브 `.scratch/widget-login-state/probes/opener_message/`로 먼저 쟀다. Playwright의 Chromium 153(기본 프로필) 하나이고, 위젯 코드가 아직 없어 위젯의 창이 보낼 물음과 사이트의 페이지가 낼 답을 흉내 낸 측정이다. 결정은 그대로다.

`window.open`으로 연 창은 위젯의 창의 출처가 사이트의 페이지와 같은 출처이든, 등록 도메인이 같은 다른 출처이든, 등록 도메인이 다른 출처이든 물음과 답을 주고받았다. 창의 크기를 주어 열어도, 연 뒤 위젯의 창을 새로 고쳐도 같았다. 여는 법과 응답 머리 가운데 주고받지 못한 것은 넷이다. 연결을 끊는 옵션(`noopener`)으로 열었을 때, `rel`을 적지 않은 `target="_blank"` 링크로 열었을 때, 위젯의 창의 응답이 `Cross-Origin-Opener-Policy: same-origin`을 실었을 때, 사이트의 페이지의 응답이 같은 머리를 실었을 때다. 결정 "URL 방식"은 이 가운데 연결을 끊는 옵션과 위젯 쪽의 응답 머리만 적었다. 본문에 없던 것이 둘이다. 링크로 여는 사이트는 `rel="opener"`를 적어야 하고(그렇게 적은 칸은 주고받았다), `Cross-Origin-Opener-Policy: same-origin`을 내는 사이트는 그 값을 `same-origin-allow-popups`로 두어야 URL 방식을 쓸 수 있다(그 값을 실은 칸은 주고받았다). 연 뒤 사이트의 페이지를 닫으면 위젯의 창의 `window.opener`가 `null`이 됐고, 사이트의 페이지가 같은 출처의 다른 문서로 가면 `window.opener`는 남고 답이 오지 않았다.

재지 못한 것은 Firefox와 WebKit, 제품 브라우저, 브라우저의 팝업 차단, 위젯의 실제 코드, 프록시가 내는 머리다(그 프로브의 `README.md` "재지 못한 것"). 그래서 e2e가 위젯의 실제 코드와 프록시를 거친 주소에서 다시 본다는 것은 그대로다. 사이트가 지킬 것 셋과 물을 곳이 없을 때의 화면은 명세의 "URL 방식"이 적는다. 포인터는 Consequences "재지 않은 것"에 단다. 그 항목이 어림이라고 적은 것 가운데 이 주고받기는 이제 Chromium에서 흉내 낸 물음과 답으로 잰 것이다.

### 2026-11-18 용어집의 이름 보증 모드를 신원 확인 방식으로 바꿨다

사용자가 용어집(`CONTEXT.md`)의 이름 "보증 모드"를 사람이 흔히 쓰는 말인 "신원 확인 방식"으로 바꾸기로 했다(harness 티켓 `.scratch/harness/issues/rename-assurance-mode.md`, 일지 2026-11-18-1036). 이 ADR의 본문은 글자를 고치지 않으므로 옛 이름이 그대로 있다. 본문의 "보증 모드"는 "신원 확인 방식"으로 읽는다. 결정은 바뀌지 않고 코드의 이름(`assurance`)도 그대로다. 결정의 제목 "보증 모드는 위젯의 칸이 아니다"도 옛 이름 그대로 두고, 다른 문서는 그 제목을 글자 그대로 따온다.
