# 문서 검색 서버는 agent-os 밖의 저장소이고, agent-os의 런타임은 그 서버를 모른다

설치형 문서 질의응답의 기준선(ADR 0046)에는 문서 검색 서버가 필요하다. 이 서버는 파서, 임베딩 모델, 벡터 저장소 같은 무거운 의존성과 자기 관리자 페이지를 가진다. 이 서버를 쓰는 doc-qa 에이전트, 답변 평가, 둘을 함께 띄우는 참조 배포도 어딘가에 두어야 한다. 2026-11-05의 계획 제안서(일지 2026-11-06-02)는 처음에 저장소 셋(agent-os, 문서 검색 서버, 배포 묶음)을 두었다가 둘로 줄였다. 배포와 운영은 데이터를 가진 저장소가 맡아야 하고, doc-qa는 agent-os 위의 에이전트이므로 문서 검색 서버의 클라이언트라는 판단이었다.

## 결정

- **저장소는 둘이다.**

  | 저장소 | 맡는 것 | 아는 것 |
  |---|---|---|
  | agent-os | 런타임, 채널, 관리 화면, 위젯과 질문 페이지, 참조 에이전트 doc-qa, 답변 평가, 이미지와 참조 배포 | 런타임은 MCP 표준만 안다. doc-qa 플러그인과 참조 배포만 문서 검색 서버의 검색 도구 형식과 이미지 판을 안다 (바뀜: ADR 0046 이력 2026-11-06 "기준선 열 안에서 공개 데모를 먼저 연다") (바뀜: ADR 0051) |
  | 문서 검색 서버 | 문서 수집, 색인, 검색, 관리 API(REST)와 관리자 페이지, 자기 배포와 운영 | MCP 표준과, MCP `_meta`에 실린 주체의 범용 형식만 안다. agent-os를 모른다 |

  그 저장소는 아직 없다. 이름이 정해지기 전에는 `.scratch/plan.md`가 그 저장소의 행을 `rag-server:<slug>`로 가리킨다. (바뀜: 이력 2026-11-06 "문서 검색 서버의 저장소 이름을 rag-engine으로 정한다")
- **의존은 agent-os의 플러그인과 참조 배포에서 문서 검색 서버로만 간다.** (바뀜: ADR 0046 이력 2026-11-06 "기준선 열 안에서 공개 데모를 먼저 연다") 클라이언트가 서버의 도구 형식을 알고, 서버는 어떤 클라이언트가 쓰는지 모른다. 런타임(`src/`)은 calc를 모르듯 doc-qa도 모른다. (바뀜: ADR 0051) agent-os의 `plan.md`는 문서 검색 서버의 행을 가리킬 수 있고, 문서 검색 서버의 계획은 agent-os의 행을 가리키지 않는다.
- **검색 도구의 형식이 두 저장소 사이의 계약이다.** 입력은 질문, 개수, 필터이고, 출력은 조각, 문서 경로, 쪽, 위치, 갱신일, 점수다. 이 형식에 판을 붙이고, 문서 검색 서버 저장소에 MCP 클라이언트로 그 형식을 확인하는 계약 시험을 둔다. agent-os는 ADR 0043의 CI 분담대로, 빠른 검사에서는 그 판을 흉내 내는 가짜 검색 서버(테스트 픽스처)로 시험하고 실제 이미지의 compose e2e에서는 판을 고정한 실제 이미지로 시험한다.
- **문서 검색 서버는 MCP로 읽기 도구만 연다.** 수집, 삭제, 재색인 같은 쓰기는 관리 API로만 연다. 문서 속 지시에 속은 에이전트가 문서를 지우는 일을 구조로 막기 위해서다.
- **배포와 운영은 데이터를 가진 저장소가 맡는다.** 저장소마다 자기 이미지, 단독 compose, 배포 안내, 데이터의 백업과 복원, 판 올림 호환, 진단을 낸다. 둘을 함께 띄우는 참조 배포는 agent-os에 두고, 그 관리 명령은 두 저장소의 명령을 차례로 부른다.
- **데이터베이스는 서비스마다 따로 띄운다.** 각 서비스는 연결 문자열 하나만 받고, 다른 서비스의 데이터베이스를 읽지 않으며, 자기 마이그레이션만 한다. 배포 환경에 이미 PostgreSQL이 있으면 연결 문자열만 바꿔 그쪽에 붙일 수 있다. agent-os의 데이터베이스는 trace-postgres부터 생기고, 그 전의 판은 파일 트레이스다(ADR 0046).
- **참조 배포가 밖으로 여는 포트는 TLS를 끝내는 리버스 프록시 하나다.** 나머지 컨테이너는 내부 네트워크에서만 통신한다.
- **제품의 판은 agent-os의 릴리스다.** 그 릴리스의 참조 배포가 문서 검색 서버 이미지의 판을 고정한다. 문서 검색 서버는 자기 판을 따로 낸다.

## Considered Options

- **문서 검색 서버를 agent-os 안(`src/` 아래 패키지나 `plugins/` 아래 MCP 서버)에 둔다.** 거부했다. 무거운 의존성이 런타임의 잠금 파일과 CI에 들어오고, 런타임의 보장과 무관한 코드가 같은 판 리듬에 묶인다.
- **배포 묶음 저장소를 따로 둔다.** 거부했다. 내용이 설정, 문서, 절차, 시험이 대부분이라 얇고, 기준선 동안 doc-qa와 검색 도구가 함께 바뀌어 변경마다 저장소 둘을 고쳐야 한다. 위젯을 떼어 내는 것을 미룬 ADR 0047과 같은 이유다.
- **doc-qa와 참조 배포를 문서 검색 서버 저장소에 둔다.** 거부했다. 서버가 자기 클라이언트를 품게 되어 의존 방향이 거꾸로 선다.
- **데이터베이스 인스턴스 하나를 함께 쓰고 데이터베이스나 스키마만 나눈다.** 기본값으로는 거부했다. 운영 대상이 하나 줄지만, 저장소마다 배포가 스스로 완결되지 않고 주 판 올림과 장애가 함께 묶인다. 연결 문자열만 받게 했으므로, 배포 환경이 원하면 이렇게 배치할 수 있다.

## Consequences

- **형식을 바꿀 때.** 검색 도구의 형식을 바꾸면 문서 검색 서버가 판을 올리고, agent-os의 가짜 검색 서버와 doc-qa가 따라 고친다. (바뀜: ADR 0051) 가짜 서버가 실제 서버와 어긋나는 일은 실제 이미지의 compose e2e가 잡는다. 그래서 가짜 서버가 따르는 형식의 판을 한 곳에 적는다.
- **저장소마다 따로 두는 것.** CI, 규칙 파일, 릴리스 절차를 저장소마다 둔다. 혼자 운영하는 비용이 는다.
- **다른 저장소의 행.** agent-os의 `plan.md`에 다른 저장소의 행이 Blocked by로 들어간다. 그 행이 닫혔는지는 문서 검색 서버 저장소를 보고 확인한다. 그 저장소가 생기기 전에는 그런 행(answer-eval, deploy-package, stale-warning)을 열 수 없다.
- **데이터베이스의 값.** 데이터베이스를 서비스마다 띄우므로 컨테이너 하나와 메모리 수백 MB(어림)가 더 든다.
- **e2e의 기댐.** agent-os의 실제 이미지 compose e2e가 판을 고정한 문서 검색 서버 이미지에 기댄다.
- **런타임의 경계.** 플러그인 경계 시험(`tests/test_plugins_boundary.py`)과 import-linter는 코드의 import만 본다. 런타임이 doc-qa와 문서 검색 서버의 이름을 모르는지는 리뷰가 본다. (바뀜: ADR 0051)

## 이력

### 2026-11-06 문서 검색 서버의 저장소 이름을 rag-engine으로 정한다

같은 날 받은 계획 제안서의 둘째 판(일지 2026-11-06-11)이 문서 검색 서버 저장소의 이름을 `rag-engine`으로 정했다. 그래서 `.scratch/plan.md`는 그 저장소의 행을 `rag-engine:<slug>`로 가리킨다. 그 판은 그 저장소의 행도 다시 나눴다. ADR 0046 본문이 든 첫 판의 행 다섯(bootstrap, rag-mcp, rag-admin, search-eval, rag-ops)은 기준선의 행 일곱(core, source-sync, admin, search-eval, release-image, backup-upgrade, diag-bundle)이 됐다. rag-mcp는 core로, rag-admin은 source-sync와 admin으로, rag-ops는 release-image와 backup-upgrade와 diag-bundle로 나뉘었고, bootstrap은 빠졌다. 새 저장소는 agent-os의 킥오프 런북(`KICKOFF.md`)으로 시작하므로 뼈대를 만드는 행을 따로 두지 않는다. 1.0 열에는 db-source와 change-log가 더해졌다. 그에 따라 agent-os의 두 행이 기다리는 행이 바뀌었다. answer-eval은 `rag-engine:core`를, deploy-package는 `rag-engine:release-image`, `rag-engine:backup-upgrade`, `rag-engine:diag-bundle`을 기다린다. stale-warning이 기다리는 `rag-engine:doc-freshness`는 접두사만 바뀌었다. 이 행들은 그 저장소의 계획에만 있고, 이 저장소에는 만들지 않는다. 그 저장소는 아직 없다(2026-11-06에 이 PC의 `C:\project`를 `ls`로, GitHub의 njh6803 계정을 `gh repo view njh6803/rag-engine`과 `gh repo list njh6803`으로 봤다. 둘 다 없었다). 저장소 둘, 한 방향의 의존, 검색 도구 형식의 계약이라는 결정은 바뀌지 않았다.

### 2026-11-13 용어 "질문 페이지"를 "위젯 미리보기 페이지"로 바꿨다

사용자가 용어집(`CONTEXT.md`)의 "질문 페이지(Portal)"를 "위젯 미리보기 페이지"로 바꾸기로 했다(이름 바꾸기 chore `.scratch/harness/issues/rename-portal-to-widget-preview.md`). 이 ADR의 본문은 기록이라 옛 이름을 그대로 두므로, 본문의 "질문 페이지"는 "위젯 미리보기 페이지"로 읽는다. 결정은 바뀌지 않는다. 코드 이름 `portal`과 경로 `/portal/`도 그대로다.
