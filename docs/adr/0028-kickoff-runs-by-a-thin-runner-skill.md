# 킥오프는 런북을 읽는 얇은 진행 스킬이 순서대로 진행하고 사람 몫에서 멈춘다

킥오프 런북(`KICKOFF.md`, `kickoff/`)은 사람이 세션에 단계를 하나씩 시키는 문서였다. 사용자가 런북의 모든 과정이 순서대로
자동으로 진행되고, 사람의 결정은 추천과 함께 선택 화면으로 고르며, 절차는 스킬로 처리되기를 바랐다(일지 2026-10-12-13
"기본 테마와 테마 이름"). 그런데 런북의 마지막 절은 런북을 세 번 돌린 뒤에야 손본 부분을 스킬로 만들고 "그 전에는 도구를
만들지 않는다"고 적었고, 런북을 끝까지 돈 것은 agent-os 한 번뿐이다. 단계의 내용은 아직 자주 바뀐다. 반면 순서대로 넘어가기,
멈출 자리, 묻는 방식, 진행의 기록은 어느 프로젝트에서나 같다. 그래서 내용은 런북에 두고 진행만 스킬로 굳힌다. 설계 인터뷰의
질문과 고른 선택지의 설명은 일지 2026-10-12-25에 글자 그대로 있다.

**킥오프는 사용자 레벨의 짧은 스킬(`/kickoff`)이 런북 저장소의 진행 규율(가칭 `kickoff/runner.md`)을 읽어 순서대로
진행한다. 단계의 내용은 런북이 원천이고, 진행 규율은 순서, 멈출 자리, 선택 화면, 진행 기록만 가진다. 런북 마지막 절의 도구
규칙은 이 스킬을 예외로 둔다.**

## 사람 몫

사람에게 넘기는 자리는 셋이다. 런북의 단계마다 정해진 모양의 "사람 몫" 줄에 적고, 진행 규율은 그 줄에서 멈춘다. 줄의 모양을
보는 검사는 명세가 정한다. 지금 런북은 사람 몫을 단계 곳곳의 산문에 적었다. 8단계는 봇 리뷰의 전제 둘(시크릿, CodeRabbit
로그인)을 사람이 한다고 적었지만, 바로 아래의 CodeRabbit App 설치는 주어 없이 적었고 사람이 OAuth 승인을 했다는 것은 첫
킥오프의 일지에만 있다. 산문에서 판단하게 두면 이런 자리를 놓친다.

- **결정**: 사람이 고를 것이다. 추천을 맨 앞에 둔 선택 화면(Claude Code는 `AskUserQuestion`)으로 묻는다. 단계 안에서 부르는
  스킬이 글로 물으라고 해도 선택 화면으로 올린다.
- **허락**: 세션이 할 일을 사람이 승낙하는 것이다. 원격에 드러나는 일(저장소 만들기, 푸시, 브랜치 보호, PR, 병합, 봇을 부르는
  코멘트)과 저장소 밖을 바꾸는 일(전역 플러그인과 전역 스킬, 사용자 레벨 스킬 만들기)에만 무엇을 어디에 하는지 보인 선택
  화면을 띄운다. 새 프로젝트 안의 패키지 설치와 템플릿 내려받기는 Claude Code의 권한 프롬프트에 맡긴다.
- **사람만**: 로그인, 토큰과 시크릿, 앱 설치와 OAuth, 유료 좌석처럼 사람만 할 수 있는 일이다. 할 일과 그 자리를 보이고
  "했다 / 건너뛴다"를 고르게 한다. "했다"를 고르면 세션이 확인 명령(예: `gh secret list`의 이름과 시각,
  `coderabbit auth status`의 `Seat:`)으로 대 보고, 맞지 않으면 다시 묻는다. 건너뛴 일은 진행 파일에 남고 끝에 다시 보인다.

이 셋은 하네스의 말이다. 제품의 결정(Decision)과 승인(Approval)은 실행이 멈춘 자리의 일이고(`CONTEXT.md` 인터럽트 절) 이
셋과 다르다. 그래서 `CONTEXT.md`에 넣지 않는다. 검사가 실패하거나 세션이 끊긴 자리처럼 사람 몫이 아닌 멈춤은 진행 규율이 따로
정한다.

원격에 기대지 않는 사람 몫은 0단계 앞의 **준비**에 모은다. 무엇을 만들지, `gh` 로그인, 공개와 비공개, 비공개면 Actions 분량,
CodeRabbit CLI 로그인과 좌석이다. 공개 여부는 7단계의 `.coderabbit.yaml`과 8단계의 보호 브랜치가 기대므로 가장 먼저 정한다.
원격이나 첫 PR에 기대는 것(시크릿 등록, CodeRabbit App, 보호 브랜치, 첫 PR의 Claude 코멘트)은 그 단계에서 멈추고,
하네스가 다 깔린 뒤의 `/context` 실측은 8단계 끝, 9단계로 넘기기 전에 멈춘다. 공개 여부를 정하는 플랜 확인
(`gh api user --jq .plan.name`)도 준비로 온다. Actions 분량은 런북 1단계에서 사람이 Billing 화면을 보던 것을 준비에서
세션이 `gh api users/<login>/settings/billing/usage`로 읽는다. `<login>`은 `gh api user --jq .login`이다(git의 사용자 이름과
다를 수 있다). 이 명령은 달마다, 저장소마다 쓴 분과 저장 용량 행을 내고 옛 `settings/billing/actions`는 410이다. 응답 헤더가
요구하는 범위는 `user`다(2026-10-12 손으로 봤다). 기본 범위로 막 로그인한 토큰으로는 재지 않았고, 막히면
`gh auth refresh -s user`가 사람 몫으로 더해진다. (바뀜: 이력 2026-10-12 "킥오프 세션은 새 프로젝트의 스킬을 읽어 따르고 준비의 로그인이 user 범위를 받는다") 응답에는 저장소의 공개 여부와 한도가 없어, 이번 달·분 단위·비공개 저장소로
거르는 법은 명세가 정한다. Billing 화면의 Included usage와 같은 값인지는 재지 않았다. 이 명령은 사용자 계정의 사용량이다.
저장소 주인이 조직이면 `organizations/<org>/settings/billing/usage`이고 그 조직의 관리자만 부를 수 있다(GitHub REST 문서
https://docs.github.com/en/rest/billing/usage, 2026-10-12 읽었다). 주인이 개인인지 조직인지에 따른 갈래와, 관리자가 아닐 때
사람에게 Billing 확인을 넘기는 것은 명세가 정한다.

## 배치와 진행

- **스킬의 자리.** `~/.claude/skills/kickoff/SKILL.md`이고 사람만 부른다(`disable-model-invocation`). 본문은 런북 저장소 clone의
  진행 규율 경로와 그것을 읽어 따르라는 문장뿐이다. 0단계가 그 기계의 clone 경로로 이 파일을 만든다. (바뀜: 이력 2026-10-12 "첫 시작은 진행 규율이 스킬을 먼저 만들고 같은 세션에서 잇는다") 사용자 레벨 스킬은 어느
  폴더에서 연 세션에나 실리고 같은 이름이면 프로젝트 레벨을 이긴다(https://code.claude.com/docs/en/skills.md, 서브에이전트가
  읽었다). 다른 저장소의 스킬을 싣는 것은 CLI의 `--add-dir`·`/add-dir`이고 설정의 `additionalDirectories`는 싣지 않는다
  (https://code.claude.com/docs/en/large-codebases.md, 2026-10-12 읽었다). 데스크톱 앱에서 더한 폴더가 어느 쪽인지는 그
  문서에 없다.
- **첫 시작.** 스킬이 없는 새 기계에서는 런북 저장소를 clone하고, 새 프로젝트 폴더에서 연 세션에 진행 규율을 읽고 따르라는 한
  줄을 붙여 넣는다. 그 한 줄은 `KICKOFF.md` 머리에 둔다. 붙여 넣은 한 줄은 스킬을 부른 것이 아니라 압축 뒤에 다시 실릴 것이
  없다. 그래서 첫 시작의 세션은 0단계가 스킬을 만든 뒤 진행 파일에 적고 끝나고, 사람이 새 세션에서 `/kickoff`로 잇는다. 세션
  도중에 만든 사용자 레벨 스킬을 그 세션에서 바로 부를 수 있는지는 확인하지 못했다. (바뀜: 이력 2026-10-12 "첫 시작은 진행 규율이 스킬을 먼저 만들고 같은 세션에서 잇는다")
- **진행 파일.** 준비의 첫 일로 새 프로젝트 폴더에 진행 파일(가칭 `.scratch/kickoff.md`)을 만들고 단계마다 끝남, 건너뜀과
  이유, 사람 몫 대기를 적는다. 8단계의 첫 커밋부터 커밋된다. `/kickoff`를 다시 부르면 첫 미완 단계부터 잇는다. 일지는 지금처럼
  사람의 프롬프트와 갈린 곳을 적는다.
- **세션.** 준비부터 8단계까지 한 세션이다(첫 시작은 위의 경계 하나가 더 있다). (바뀜: 이력 2026-10-12 "첫 시작은 진행 규율이 스킬을 먼저 만들고 같은 세션에서 잇는다") 압축 뒤에는 부른 스킬의 본문만 스킬마다
  5,000토큰까지 다시 실린다(https://code.claude.com/docs/en/context-window.md, 서브에이전트가 읽었다). 짧은 스킬이 다시 실려
  세션이 진행 규율과 진행 파일을 다시 읽는다. 첫 킥오프는 세 세션이었고 그 첫 세션이 0~8단계와 첫 설계 인터뷰를 했다. 그
  세션이 맥락을 다 써 이어진 표지가 한 번 이상 있다는 것은 서브에이전트가 이 기계의 세션 기록을 검색해 손으로 본 것이다.
  일지에는 없어 저장소에서 다시 낼 수 없다.
- **범위.** 준비와 0~8단계다. 끝에서 첫 기능의 설계 인터뷰(9단계 1)로 넘긴다. 7단계가 복사한 next-session이 지시문을 내고
  open-session이 새 세션을 연다. 지시문 첫 줄의 `/grill-with-docs`는 지금처럼 open-session이 그 스킬 파일을 읽으라는 한 줄로
  옮긴다. open-session은 Windows 데스크톱 앱 전용이라 다른 OS에서는 사람이 지시문을 붙여 넣는다. 9단계 안에서 사람이 직접
  부르는 스킬(`grill-with-docs`, `to-spec`, `to-tickets`, `implement`)의 관문과 PR #186이 넣은 디자인 도구의 차례는 바꾸지
  않는다.
- **4·5단계.** 사람이 직접 부르는 setup과 grill-me는 세션이 그 스킬 파일을 읽어 따른다(첫 킥오프와 open-session의 선례). (바뀜: 이력 2026-10-12 "킥오프 세션은 새 프로젝트의 스킬을 읽어 따르고 준비의 로그인이 user 범위를 받는다") 선택
  화면으로 고친 `grilling` 사본은 7단계에 복사되므로 5단계에서는 원본이 돈다. 묻는 방식은 진행 규율이 정한다. 복사 순서는
  그대로다.
- **결정과 조사의 가름.** 서브에이전트는 `AskUserQuestion`을 쓰지 못한다(https://code.claude.com/docs/en/sub-agents.md,
  서브에이전트가 읽었다). 사실 조사는 서브에이전트에 맡기고 선택 화면은 본 세션이 띄운다.

## 함께 바뀌는 것

- **첫 커밋과 main 커밋 훅.** 런북은 7단계에 `hook_git_main_commit`을 등록하고 8단계에서 첫 커밋을 main 위에 한다. 훅은
  `git branch --show-current`가 `main`이면 막는다(코드를 읽었다). 이 기계는 Git for Windows의 시스템 설정이
  `init.defaultBranch=main`이라, 임시 폴더에서 `git init`만 한 저장소에서도 그 명령이 `main`을 냈다(2026-10-12 손으로 봤다).
  설정이 없으면 `master`가 되어 훅은 막지 않지만 8단계의 보호와 런북 전체가 main을 가정한다. 그래서 1단계의 `git init`에
  `-b main`을 붙이고, 훅은 커밋이 하나도 없는 저장소(`git rev-parse --verify HEAD`가 실패)에서 막지 않는다. 훅이 막는 사고(다른
  세션이 체크아웃을 main으로 옮긴 뒤의 커밋)는 커밋이 없는 저장소에서 일어나지 않는다. 첫 킥오프는 이 훅이 생기기 전이었다.
  훅의 테스트와 `tools/hook_payloads.toml`의 사례, 독스트링의 "언제나 실수다", 런북 7단계의 훅 설명을 함께 고친다. 훅 러너
  `tools/run_hooks.py`의 `main` 픽스처는 `git init -b main`만 한 빈 저장소라, 표의 main 위 커밋 deny 사례가 침묵이 되지 않게
  그 픽스처에 커밋 하나를 두고 빈 저장소 사례는 따로 둔다. agent-os의
  다른 문서가 쓰는 "main 위 커밋은 훅이 막는다"는 커밋이 있는 이 저장소에서 그대로 참이다.
- **ADR 0005.** Consequences의 "원격 생성과 시크릿 등록은 사람이 한다"에서 원격 생성은 세션이 허락을 받아 한다. 시크릿 등록은
  그대로 사람이다. 같은 절의 "런북 1단계의 플랜 확인에 남은 분량도 포함한다"는 준비의 명령 확인으로 옮긴다.
- **런북.** 머리의 첫 시작 한 줄, 준비 절, 단계마다의 사람 몫 줄, 1단계의 플랜 확인과 Billing 화면 확인을 준비로, 1단계의
  `git init -b main`, 1단계의 폴더 만들기와 "이 디렉터리에서 Claude Code를 연다"(세션은 이미 새 프로젝트 폴더에서 열려 있다),
  8단계 `gh repo create`의 `--private`을 준비에서 정한 공개 여부로,
  에이전트 규칙 3의 "결정만 번호 붙여 묻는다"를 선택 화면으로, "어디에 무엇이 사는가"의 전역 스킬 행이다. 마지막 절의 예외는 이 ADR과 함께 한 줄로 먼저 넣었다.
  CodeRabbit CLI를 설치하는 단계는 런북에 없어 준비 절이 그 확인을 든다. 1단계의 일지 이름 규칙(`<날짜>-01-kickoff.md`)은 첫
  킥오프의 실제 이름(`2026-09-19-kickoff.md`)과 다르다. `kickoff/facts.md`에 billing API의 확인일을 적는다.
- **새 파일.** 진행 규율, 사용자 레벨 스킬의 원문(0단계가 만드는 것), 진행 파일의 모양이다. (바뀜: 이력 2026-10-12 "첫 시작은 진행 규율이 스킬을 먼저 만들고 같은 세션에서 잇는다")
- 이 변경들은 구현과 함께 들어간다. 검증은 임시 폴더에서 준비부터 2단계까지 진행 스킬로 돌리고, 새 세션에서 `/kickoff`를 다시
  불러 진행 파일에서 잇는지 본다. (바뀜: 이력 2026-10-12 "킥오프 세션은 새 프로젝트의 스킬을 읽어 따르고 준비의 로그인이 user 범위를 받는다") 단계의 내용은 런북 그대로라 진행 규율만 시험한다. 런북 전체의 검증은 여전히 두 번째
  프로젝트다.

## 거부한 안

- **단계마다 스킬.** 한 번만 돌린 단계를 스킬로 굳히고 런북을 목차로 만든다. 단계가 바뀔 때마다 스킬과 런북 두 곳을 고친다.
- **런북 문서만 고친다.** 단계 끝마다 "이어서", 결정마다 "선택 화면"을 문장으로 넣는다. 문서는 강제력이 없다(`CLAUDE.md`
  교정 루프의 배치 표). 멈출 자리를 셀 장치도 생기지 않는다.
- **스킬 전체를 사용자 레벨에 복사.** 압축 뒤에도 본문이 다시 실리지만, 런북 저장소에서 고칠 때마다 다시 복사해야 하고
  저장소 밖의 사본이 낡아도 검사가 보지 못한다.
- **런북 저장소에 두고 `--add-dir`로 연다.** 전역에 아무것도 두지 않지만 세션마다 다시 더해야 하고, 데스크톱 앱에서 되는지
  확인하지 못했다.
- **플러그인.** 판과 갱신 명령이 생기지만 매니페스트가 늘고, 스킬이 읽을 런북 본문을 캐시와 clone 가운데 어디서 읽을지
  확인하지 못했다.
- **사람 몫을 닿을 때마다 멈춘다.** 런북 순서는 그대로지만 원격과 무관한 로그인도 8단계까지 기다리고 멈춤이 흩어진다.
- **덧댄 사본을 2단계로 당긴다.** 4·5단계도 선택 화면 라운드로 돌지만, 사본을 지키는 지침 검사는 7단계에 와 그 사이 사본만
  먼저 있다.
- **첫 커밋을 위해 훅 등록을 늦추거나 사람이 첫 커밋을 한다.** 앞은 복사 목록에 순서 예외를 만들고, 뒤는 사람 몫을 하나
  늘린다.

## 이력

### 2026-10-12 첫 시작은 진행 규율이 스킬을 먼저 만들고 같은 세션에서 잇는다

위 "첫 시작"은 세션 도중에 만든 사용자 레벨 스킬을 그 세션에서 부를 수 있는지 확인하지 못해, 첫 시작의 세션을 0단계 뒤에
끝내고 사람이 새 세션에서 `/kickoff`로 잇게 했다. 명세(`.scratch/kickoff-auto-flow/spec.md`)가 그것을 쟀다. 세션 시작 때
이미 있던 스킬 폴더에 도중에 만든 `disable-model-invocation` 스킬은 사용자 메시지로 보낸 `/이름`으로 바로 불렸다. 세션
시작 때 없던 폴더에 만든 스킬은 두 번 보내도 인식되지 않다가 `/reload-skills` 뒤에 불렸다
(`.scratch/kickoff-auto-flow/probes/skill_live/run.py`, claude 2.1.296). 잰 자리는 `claude -p`의 stream-json 사용자 메시지와
프로젝트 레벨 폴더다. 사용자 레벨 `~/.claude/skills`도 같은 규칙이라는 것은 공식 skills 문서의 문장이다
(https://code.claude.com/docs/en/skills.md, 원문을 받아 2026-10-12 손으로 봤다). 대화형 입력창에서 사람이 친 것은 재지
않았고 명세의 검증 절차가 본다. 새 기계에는 그 폴더가 아직 없을 수 있다.

그래서 첫 시작에도 세션을 끊지 않는다. 진행 규율은 시작할 때 사용자 레벨 스킬이 있고 이 clone을 가리키는지 본다. 없으면
허락을 받아 바로 만들고, 사람에게 같은 세션에서 `/kickoff`를 치게 한다. 스킬 폴더를 새로 만들었으면 `/reload-skills`를
먼저 치게 한다. 스킬을 0단계까지 미루지 않는 것은 붙여 넣은 한 줄이 압축 뒤에 다시 실리지 않기 때문이다. 미루면 스킬 없이
도는 구간이 준비 전부를 덮는다. 0단계의 같은 항목은 시작 확인의 결과를 진행 파일에 옮기는 일이 된다. `/kickoff`가 그래도 불리지 않으면
같은 폴더의 새 세션에서 `/kickoff`로 잇는 옛 길이 대체다. 그래서 "준비부터 8단계까지 한 세션"은 첫 시작에도 선다. 검증은
첫 시작의 한 줄로 시작해 같은 세션의 `/kickoff`로 잇는 것까지 본다(명세 Testing Decisions).

### 2026-10-12 킥오프 세션은 새 프로젝트의 스킬을 읽어 따르고 준비의 로그인이 user 범위를 받는다

명세 검토(`spec-reviewer`, 일지 2026-10-13-01)가 위 본문이 놓친 둘을 짚었고, 사용자가 둘 다 골랐다.

첫째, 2단계가 세션 도중에 처음 만드는 새 프로젝트의 `.claude/skills/`는 그 킥오프 세션에서 불리지 않는다. 세션 시작 때 없던
프로젝트 레벨 스킬 폴더에 만든 스킬은 사용자 메시지의 `/이름`으로 두 번 불러도 실리지 않고 `/reload-skills` 뒤에만 실렸다
(`.scratch/kickoff-auto-flow/probes/skill_live/run.py`의 C, claude 2.1.296). 위 "4·5단계"는 사람만 부르는 setup과 grill-me만
읽어 따르게 했는데, 5단계의 grill-me가 부르는 grilling과 8단계 끝의 retro·next-session·open-session도 같은 폴더의 스킬이다.
그래서 킥오프 동안 새 프로젝트의 스킬은 모두 세션이 그 스킬 파일을 Read로 읽어 따른다. 읽은 본문은 압축 뒤에 다시 실리지
않으므로 진행 규율이 단계를 다시 읽을 때 그 파일도 다시 읽는다. 거부한 안은 둘이다. `/reload-skills`를 사람 몫으로 두는 안은
멈춤이 늘고, reload 뒤에 같은 폴더에 새로 만든 스킬도 불리지 않는 것을 명세 검토의 임시 스크립트가 봐(어림) 7단계 뒤에 한 번
더 들 수 있다. 2단계 뒤 세션을 끊는 안은 "준비부터 8단계까지 한 세션"을 깨고 7단계가 복사하는 스킬에 같은 문제가 남는다.

둘째, `gh auth login`의 브라우저 흐름은 `repo`, `read:org`, `gist`에 `-s`로 더한 범위만 청한다(gh 소스 trunk의
`internal/authflow/flow.go`, 명세 검토가 받아 읽었다). 그래서 위 "사람 몫"이 막힐 때만 사람 몫으로 더한 `gh auth refresh -s user`는
새 기계에서 언제나 든다. 준비의 `gh` 로그인 줄이 `user` 범위를 함께 받는다. 로그인이 안 돼 있으면 `gh auth login -s user`,
로그인했는데 범위가 없으면 `gh auth refresh -h github.com -s user`다. 브라우저 승인이 한 번으로 끝나고, 공개 여부를 고르기 전에
사용량을 보는 명세의 차례가 선다. `user`는 프로필 쓰기까지 주는 넓은 범위라 줄의 설명에 그 값과 빼는 명령을 적는다. 조직의
플랜을 읽는 `admin:org`는 받지 않는다. 조직 전체를 관리하는 범위라 플랜 하나를 읽는 값으로는 크다.

검증의 범위도 바뀐다. 위 "함께 바뀌는 것"의 "준비부터 2단계까지"를 명세가 4단계까지로 늘렸다. 2단계가 만든 스킬을 같은
세션에서 읽어 따르는지 보는 첫 자리가 4단계의 setup이기 때문이다.
