# 판은 main이 움직일 때 CI가 스스로 내어 이미지 넷을 Docker Hub에 올리고, 단독 compose는 프록시와 네 컨테이너를 보통의 Docker 네트워크로 묶는다

기능 계획 release-image는 판마다 `serve`, 관리 화면, 위젯, 질문 페이지의 컨테이너 이미지를 짓고 올리며 agent-os만 띄우는 단독 compose와 배포 안내를 내는 행이고, 고를 것을 설계 인터뷰에 넘겼다. 이미지를 올릴 레지스트리, 태그 규칙, 폐쇄망을 위해 이미지를 파일로 옮기는 방법, 취약점 점검 결과, 루프백에만 서는 네 프로세스에 다른 컨테이너의 프록시를 잇는 방법(ADR 0050 Consequences "다른 행"이 넘겼다), 질문 페이지 토큰 끝점의 프록시 빈도 제한(ADR 0050 결정 "빈도 제한"이 넘겼다)이다. 설계 인터뷰는 두 세션에 걸친 여섯 라운드였고, 사용자는 도중에 방향을 넷 바꿨다. 판 내기를 전부 자동으로 하자고 했고, dev 전환(ADR 0043)을 release-image보다 먼저 끝내기로 했으며, 라운드 3에서 고른 네트워크 이름공간 공유 배치를 보통의 Docker 네트워크로 바꿨고, 관리 화면을 로그인 기능 뒤에 인터넷에 열기로 했다. **판은 사람이 누르는 단추 없이 CI가 낸다. dev 전환이 끝난 뒤, main이 움직일 때(출시 PR이나 핫픽스의 병합) 지난 판 뒤로 제품 변경이 있으면 CI가 커밋 접두로 번호를 계산하고, 이미지 넷을 짓고, 실제로 띄워 시험하고, 취약점을 점검하고, 이 제품 전용 Docker Hub 계정에 올리고, GitHub 릴리스에 배포 파일 묶음과 소프트웨어 목록과 점검 결과를 첨부한 뒤, 마지막에 git 태그를 단다. 0.1.0 전의 판은 모두 출시 후보이고, 저장소의 판 설정 파일에서 한 줄을 지우는 PR이 정식 판의 신호다. 저장소에 적힌 번호는 0.0.0으로 한 번 바꾸고 실제 번호는 이미지를 지을 때만 넣는다. 단독 compose는 컨테이너 다섯(nginx와 이미지 넷)을 보통의 Docker 네트워크로 묶고 프록시가 컨테이너 이름으로 접속한다. 그래서 네 프로세스의 루프백 규칙에 이미지 안에서만 켜지는 명시적 예외를 둔다. 밖으로 여는 포트는 프록시의 443과, 443으로 넘기기만 하는 80이며, 관리 화면은 인터넷에 열지 않고 compose가 그 포트를 서버 자신의 `127.0.0.1`에만 열어 운영자가 SSH 포트 포워딩으로 닿는다. 위젯 이미지는 컨테이너가 뜰 때 운영자의 사이트 파일로 빌드한 뒤 서비스를 시작한다.** 정하는 것은 판을 만들어 올려 두는 데까지다. 서버에 올리는 일은 운영자의 수작업이고 그 절차는 deploy-package, ops-backup-upgrade, public-demo가 정한다.

## 결정

- **판마다 나오는 것.** 이미지 넷(`serve`, 관리 화면, 위젯, 질문 페이지)을 이 제품 전용 Docker Hub 계정 아래에 올린다. git 태그는 `v0.1.0` 꼴이고, 이미지에는 그 판의 번호 태그와 커밋 해시 태그 둘을 단다. 늘 최신을 가리키는 `latest` 태그는 두지 않는다. 판 올림이 이미지 태그를 바꾸는 일이라(ops-backup-upgrade 기능 계획) 움직이는 태그가 있으면 어느 판이 도는지 알 수 없다. GitHub 릴리스에는 배포 파일 묶음(compose 파일, 프록시 설정, 환경 변수 틀, 배포 안내를 묶은 압축 파일 하나), 이미지에 든 소프트웨어 목록(SBOM), 취약점 점검 결과를 첨부한다. 릴리스 노트는 제품 변경을 한 PR의 제목을 "새 기능", "고친 것", "올릴 때 할 일"로 묶은 것이고 사람이 쓰는 글이 없다. 모든 판에 노트가 붙고 고친 것도 빠짐없이 실린다. 첫 정식 판 0.1.0은 그동안 병합된 PR이 500개가 넘어(인터뷰 때 가장 최근 PR이 522번이었다) 목록만으로 읽을 수 없으므로, 저장소에 그 판의 소개 글 파일이 있으면 노트 맨 위에 싣는 자리를 두고 다른 판에서는 비운다. 실제로 처음 나가는 판은 0.1.0의 출시 후보이므로(아래 "출시 후보와 정식 판") 그 출시 후보들의 노트에도 같은 자리를 둔다. 출시 후보의 노트는 지난 판(출시 후보 포함) 뒤의 변경을 싣고, 정식 판의 노트는 지난 정식 판 뒤의 변경 전부를 싣는다. 정식 판의 노트가 마지막 출시 후보 뒤의 변경만 실으면 거의 비기 때문이다. 출시 후보의 노트에 관한 이 세 문장은 인터뷰에서 묻지 않았고, 셀프 리뷰를 반영하며 이 ADR이 기본값으로 정했다.
- **보증하는 환경.** 이미지와 단독 compose는 리눅스 x86-64의 Docker Engine과 Docker Compose에서만 띄워 보고, 배포 안내에 그 환경만 보증한다고 적는다. Podman, RHEL 계열 전용 바탕 이미지, ARM 서버는 0.1 판의 범위 밖이라고 적는다. 배포 환경이 Docker를 허용하지 않는 곳으로 정해지면 이 결정을 다시 연다. 저장소의 문서에는 배포 환경의 운영체제와 컨테이너 런타임이 사실로 적혀 있지 않다(마크다운 전체를 `[Pp]odman|RHEL|UBI`로 grep하면 release-image 기능 계획 한 곳만 맞았다. 일지 2026-11-11-1110 "인터뷰 전에 대 본 사실").
- **레지스트리와 계정.** Docker Hub에 이 제품의 이름으로 무료 개인 계정을 새로 만들고 그 아래에 네 이미지를 공개로 올린다. 무료 개인 계정의 접근 토큰은 저장소 하나로 좁힐 수 없고 계정이 닿는 모든 저장소에 걸리므로(Docker 문서 `security/access-tokens/reference`의 원문을 받아 대 봤다. 일지 2026-11-11-1110 "Docker Hub"), 계정에 이 제품의 이미지만 두어 토큰이 새도 닿는 범위가 이 제품에서 끝나게 한다. 계정 만들기, 2단계 인증, 접근 토큰 발급, GitHub 저장소에 비밀 값을 넣는 일은 사람 몫이고, 이것이 없으면 첫 판 내기가 실패한다. 한 사람이 계정을 둘 가져도 되는지는 약관에서 그런 문장을 찾지 못했고(검색어 몇 개로 본 것이다), 약관에는 6개월 넘게 쓰지 않은 계정을 닫을 수 있다는 조항이 있다(조사 보고에서 옮겼다). 원하는 이름이 비어 있는지는 확인하지 않았다. 받는 횟수 제한은 공식 출처끼리 수가 달라(같은 일지) 배포 안내에 무엇을 적을지는 명세가 정한다.
- **인터넷이 막힌 곳.** 배포 안내에 인터넷이 되는 PC에서 이미지를 받아 파일로 저장하고(`docker save`), 옮겨서 불러온 뒤, 해시를 대조하는 명령을 적고, 그 명령을 실제로 돌려 본 기록을 남긴다. 모델 파일까지 포함한 반입 절차는 deploy-package가 이 명령 위에 짓는다(그 기능 계획이 제 몫으로 적는다).
- **서버 이미지의 Node와 예시 MCP 서버.** `serve` 이미지에 파이썬과 Node를 함께 넣고, calc 예시가 쓰는 MCP 서버 패키지(`@modelcontextprotocol/server-everything`)를 판을 고정해 이미지에 미리 설치한다. 인터넷이 없는 서버에서도 예시가 돌고, 운영자가 Node로 띄우는 MCP 서버를 플러그인으로 더할 수 있다. 예시 플러그인의 실행 명령은 지금 `npx -y`이고 패키지의 판을 적지 않으므로(`plugins/mcp/everything/plugin.toml`을 읽었다) 미리 설치한 것을 실행하도록 고친다. 미리 설치돼 있어도 `npx -y`가 레지스트리에 묻는지는 재지 않았고(npm의 소스와 문서를 읽은 어림), 명세가 잰다. 이미지가 커지고 점검 대상이 는다(크기는 재지 않았다).
- **판이 나는 때.** dev 전환(ADR 0043 Consequences "전환")을 먼저 끝낸다. 그 뒤에는 main이 움직일 때마다, 곧 출시 PR이 병합되거나 핫픽스가 병합될 때, 지난 판 뒤로 제품 변경이 있으면 CI가 판을 낸다. 판을 낼지를 그때 판단하는 사람도 에이전트도 없고, 전체 계획의 기능 목록이 곧 판을 내는 계획이다. 제품 변경이 없으면 내지 않는다(하네스 기능, ADR·명세·일지 같은 저장소의 문서만 고친 기능). 이 규칙이 서기 전에 끝난 기능은 첫 판에 함께 실린다. 판 내기는 한 번에 하나만 돈다. 두 병합이 잇달아 오면 둘째가 첫째의 태그 뒤에서 번호를 계산한다.
- **제품 변경.** 제품 변경으로 세는 범위는 `src`, `web`, `plugins`와 의존성 잠금 파일, Dockerfile, compose 파일, 프록시 설정, 배포 안내, 판 설정 파일이다. 배포 안내는 문서이지만 배포 파일 묶음에 들어 판과 함께 나가므로 제품 변경으로 센다. 커밋 접두만으로는 제품의 변경을 가르지 못한다. 인터뷰 때 `origin/main`의 지난 14일 feat 커밋 47개 가운데 9개가 `src`·`web`·`plugins`를 고치지 않았고, 제목으로 보면 하네스의 것이었다(`git rev-list --count`에 `--since=14.days`와 `--grep`과 경로를 붙여 손으로 봤다. 일지 2026-11-11-1110 라운드 2. 하네스의 것이라는 가름은 제목을 읽은 것이다. 셀프 리뷰가 커밋 f64dfe41c에서 같은 명령으로 47과 38을 다시 봤다). 정확한 경로 목록은 명세가 짓는다.
- **번호.** 지난 판 뒤의 제품 변경에 `fix`만 있으면 끝자리를 올리고(0.1.0 → 0.1.1), `feat`이 하나라도 있으면 가운데 자리를 올린다(0.1.x → 0.2.0). `feat`도 `fix`도 아닌 접두(커밋 검사가 받는 나머지 여섯인 `docs`, `style`, `refactor`, `test`, `chore`, `perf`)의 제품 변경만 있을 때도 끝자리를 올린다. 의존성 잠금 파일이나 배포 안내만 고친 판이 그렇다. 사용자가 고른 규칙은 `fix`와 `feat`만 말했고, 그 밖의 접두는 셀프 리뷰가 낸 빈 칸이라 이 ADR이 기본값으로 정했다. 그런 변경을 노트의 어느 묶음에 싣는지는 명세가 정한다. 올릴 때 운영자가 손댈 것(설정, 환경 변수, 데이터, 플러그인 코드)이 있는 변경은 제목의 접두 뒤에 느낌표를 붙이고(`feat!:` 꼴. 커밋 검사 `tools/check_commit_msg.py`가 이미 받는다. 범위를 붙일 때는 `feat(범위)!:` 꼴만 받고 `feat!(범위):`는 거부한다. 셀프 리뷰가 그 검사에 경계 입력을 넣어 손으로 봤다), 그런 변경이 있으면 가운데 자리를 올리며 노트의 "올릴 때 할 일"에 싣는다. 그래서 끝자리만 오른 판은 이미지 태그만 바꾸면 된다는 약속이 된다. 맨 앞자리(1.0.0)는 자동으로 올리지 않는다. 유의적 버전 2.0.0의 4항이 0.y.z에 허용하는 읽기다(원문을 받아 대 봤다. 같은 일지 "판 번호와 릴리스 관행"). 번호의 원천은 git 태그다.
- **출시 후보와 정식 판.** 저장소에 지금이 어느 정식 판의 출시 후보 단계인지를 적은 판 설정 파일을 둔다. 그 줄이 있는 동안 CI는 `v0.1.0-rc.1`, `rc.2`처럼 출시 후보만 낸다. pilot-release의 마지막 티켓이 그 줄을 지우는 PR을 내고, 그 변경이 main에 오르면 CI가 정식 판 `v0.1.0`을 낸다. 판 설정 파일의 변경도 제품 변경이라, 그때 다른 제품 코드가 바뀌지 않았어도 판이 난다. 맨 앞자리를 올릴 때(1.0.0)도 같은 파일에 다음 정식 판의 번호를 적어 알린다. 파일의 이름과 모양은 명세가 짓는다. 설계상의 계획이고 돌려 본 것이 아니다.
- **저장소의 번호.** `pyproject.toml`의 `version`은 지금의 0.1.0에서 0.0.0으로 한 번 바꾸고 판마다 고치지 않는다. 소스에서 바로 돌린 것이 판 이미지가 아님을 드러내고, CI가 저장소에 커밋할 일이 없다. 이 편집은 계약 파일 `openapi.json`의 판 칸 한 줄과 잠금 파일 `uv.lock`의 자기 패키지 항목을 함께 바꾼다(커밋된 `openapi.json`과 앱이 내보낸 문서의 글자 일치를 `tests/tools/test_export_openapi.py`가 단언한다). 계약 파일에 닿으므로 그 티켓이 다른 티켓을 막는다. CI가 이미지를 지을 때 그 판의 번호를 넣어, 이미지 안에서는 `agent-os --version`과 서버가 만드는 API 문서의 판 칸이 태그와 같은 번호를 보인다(둘 다 설치된 패키지의 번호를 읽는다. `src/agent_os/server.py`와 `src/agent_os/channel/cli/main.py`를 읽었다). 출시 후보에서는 글자까지 같지는 않다. 파이썬의 판 표기는 `0.1.0-rc.1`을 `0.1.0rc1`로 읽으므로(`packaging` 26.3에 넣어 손으로 봤다. 일지 2026-11-11-1110 "판 번호와 릴리스 관행"의 서브에이전트와 셀프 리뷰가 저마다 스크래치 스크립트로 봤고 저장소의 프로브는 아니다) 이미지 안에서는 `0.1.0rc1` 꼴로 보일 것이다. 빌드 백엔드 hatchling이 그 꼴로 적는지는 돌려 보지 않았다(어림). 번호를 넣는 방법은 명세가 재서 정한다. 잠금 파일에도 번호가 있어 `pyproject.toml`만 고쳐 쓰는 방법이 잠금 검사를 지나는지는 돌려 보지 않았다.
- **판 내기의 차례와 실패.** 차례는 짓기, 실제로 띄워 시험, 취약점 점검, Docker Hub에 올리기, GitHub 릴리스, git 태그다. 태그는 모든 단계가 성공한 뒤 마지막에 단다. GitHub의 릴리스는 태그를 가리키므로, 릴리스를 먼저 만들고 태그를 뒤에 다는 차례가 글자 그대로 되는지(릴리스를 초안으로 만들어 두었다가 태그와 함께 공개하는 식인지)는 명세가 정한다. GitHub가 릴리스를 공개할 때 없는 태그를 함께 만든다는 것은 기억이고 대 보지 않았다(어림). 지킬 것은 실패한 판 내기가 그 판의 git 태그와 공개된 릴리스를 남기지 않는다는 것이다. 실패하면 태그가 달리지 않고, 다음에 main이 움직일 때 CI가 지난 판 뒤의 제품 변경을 다시 알아보고 다시 시도한다. 번호 하나는 커밋 하나에만 붙는다. Docker Hub에 올린 뒤의 단계에서 실패하면 다음 시도가 다른 커밋에서 같은 번호를 계산하므로, 한 번 올라간 번호 태그를 다른 커밋의 이미지로 덮지 않게 한다. 그 방법은 명세가 정한다. 이미지를 먼저 커밋 해시 태그로만 올리고 번호 태그는 마지막 단계에서 붙이는 길과, 번호를 계산할 때 Docker Hub에 이미 있는 번호 태그도 보는 길이 후보이고 둘 다 돌려 보지 않았다. main에 올린 세션(출시 PR이나 핫픽스를 병합한 세션)은 판 내기가 끝날 때까지 기다렸다가 결과를 보고와 일지에 적고, 실패했으면 원인을 고치는 일을 다음 작업으로 넘긴다. dev 전환 뒤에는 main이 출시 PR과 핫픽스에서만 움직이므로, 다시 시도가 저절로 오기를 기다리지 않는다. 원인이 저장소에 있으면(워크플로, Dockerfile, compose의 버그) 그 수정을 핫픽스로 main에 올려 main을 움직인다(ADR 0043의 hotfix 길). 원인이 저장소 밖에 있으면(비밀 값이 없다, Docker Hub의 장애) 원인이 풀린 뒤 세션이 실패한 실행을 다시 돌린다(`gh run rerun`은 실행 전체나 실패한 잡만 다시 돌린다. `gh run rerun --help`의 출력을 손으로 봤고 돌려 보지는 않았다). 사람 몫이 없어 실패하는 첫 판 내기가 뒤의 경우다. 번호 태그를 덮지 않는다는 요건과 이 두 길은 사용자가 고른 선택지의 설명에 없던 것이고, 셀프 리뷰가 낸 빈 칸이라 이 ADR이 기본값으로 정했다. 병합 절차(`next-session`의 `merge.md`)에 판 내기를 기다리는 단계가 하나 는다. 판 내기에 걸리는 시간은 재지 않았다.
- **취약점 점검.** 취약점이 발견돼도 판은 내고 점검 결과 파일을 릴리스에 첨부한다. 고칠 수 있는(고친 판이 이미 나와 있는) 심각한 취약점이 있으면 릴리스 노트 맨 위에 경고를 싣는다. 판 내기가 바깥 사정(바탕 이미지에 든 취약점)으로 멈추지 않는다. 대신 심각한 취약점이 든 이미지가 그대로 나갈 수 있고, 고치는 일은 경고를 본 뒤의 보통 작업이다. 점검 도구와 "심각한"의 문턱은 명세가 정한다.
- **컨테이너 배치.** 단독 compose의 컨테이너는 다섯이다(프록시 nginx와 이미지 넷). compose의 보통 Docker 네트워크에 다섯을 두고 프록시가 컨테이너 이름으로 접속한다. 받을 바깥 이미지는 nginx 하나다. 컨테이너는 root가 아닌 사용자로 돌고, 첫 프로세스에는 init을 둔다(기능 계획이 이미 적었다). 플러그인 폴더와 트레이스 폴더는 이미지 밖에 두어 판을 바꿔도 남게 한다. `serve`가 쓰는 자리는 트레이스 폴더와 플러그인 루트의 `disabled.toml` 둘이고, 뒤의 것은 같은 폴더에 임시 파일을 만든 뒤 바꿔 끼우므로 플러그인 루트 폴더가 쓰기 가능해야 켜고 끄기가 된다(`src/agent_os/adapters/jsonl.py`와 `filesystem.py`를 읽었다. 일지 2026-11-11-1110 "실행 경로와 환경 변수"). 보통의 네트워크에서 `0.0.0.0`에 묶은 서버에 다른 컨테이너가 서비스 이름으로 닿는 것은 `.scratch/release-image/probes/netns/README.md` 항목 2의 양성 대조로 봤다(Windows의 Docker Desktop). 프록시와 네 이미지를 그렇게 묶은 배치 전체는 이 저장소에서 재지 않았다. 컨테이너를 다시 만든 뒤 프록시가 새 주소를 다시 찾는지(프록시가 옛 주소를 기억하는 일이 있다는 것은 어림이다), 서버를 껐다 켠 뒤 스스로 돌아오는지는 명세가 리눅스에서 잰다.
- **루프백 규칙의 예외.** 네 프로세스(`serve`, 관리 화면의 Next, 위젯의 Next, 질문 페이지)는 `127.0.0.1`과 `::1`에만 묶이고 그 밖의 호스트면 시작에서 구성 오류로 끝난다(ADR 0011, ADR 0019, ADR 0024, ADR 0050. 목록은 `src/agent_os/main.py`, `web/apps/admin/tools/loopback.ts`, `web/apps/widget/tools/start.ts`, `web/apps/portal/server/config.ts` 네 곳이 따로 든다). 보통의 Docker 네트워크에서 프록시가 닿으려면 네 프로세스가 컨테이너 안에서 루프백 밖의 주소에 묶여야 한다. 그래서 네 곳의 시작 검사에 예외를 둔다. 이미지 안에서만 켜지는 명시적인 설정이 있을 때에만 루프백 밖의 주소를 받고, 그 설정이 없으면 지금처럼 거부한다(fail-closed는 그대로다). 관리 화면이 `serve`로 요청을 넘기는 상류 주소도 `127.0.0.1` 하나만 받고 빌드 때 산출물에 박히므로(`loopback.ts`와 `web/apps/admin/next.config.ts`를 읽었다) 같은 예외로 함께 다룬다. 설정의 이름과 모양, 상류 주소를 이미지에서 어떻게 넣는지는 명세가 정하고, 코드는 release-image의 티켓이 고친다. 예외가 켜졌을 때 묶는 주소는 컨테이너 안의 것이고 호스트에 발행하는 포트는 compose가 정한다.
- **밖으로 여는 포트.** 밖으로 여는 포트, 곧 호스트의 모든 주소에 발행하는 포트는 프록시의 443과 80이다. 그 밖에 호스트에 발행하는 것은 서버 자신의 `127.0.0.1`에만 여는 관리 화면의 포트 하나다(아래 "관리 화면"). 443은 TLS로만 듣고 HSTS를 내며(기능 계획이 이미 적었다), 80은 443으로 넘기기만 한다. ADR 0024의 nginx 항목이 평문 80에 함께 둔 인증서 발급의 확인 경로(ACME HTTP-01)는 단독 compose에 두지 않는다. 인증서를 운영자가 파일로 넣기 때문이다(아래 "TLS 인증서"). 프록시가 넘기는 경로는 위젯 경로, 최종 사용자 접두사, 질문 페이지의 `= /`와 `/portal/`이고(ADR 0024, ADR 0050) 그 밖은 404다. 셋은 한 공개 출처 아래에 선다. 관리 API와 관리 화면은 프록시가 넘기지 않는다. 그 공개 출처를 둘 도메인은 운영자가 고르고, 배포 안내가 ADR 0050의 요건(등록 도메인 아래 모든 호스트를 같은 운영자가 믿을 수 있게 쥔다. release-image 기능 계획이 풀어 적었다)을 적는다. 이 제품이 도메인을 검사하는 길은 두지 않는다. 기능 계획이 설계 인터뷰에 넘긴 물음이었으나 인터뷰에서 묻지 않았고, 이 ADR이 기본값으로 정해 승인 화면에서 확인받았다.
- **관리 화면.** 단독 compose는 관리 화면을 인터넷에 열지 않는다. compose가 관리 화면의 포트를 서버 자신의 `127.0.0.1`에만 발행하고, 운영자는 SSH 포트 포워딩으로 닿는다(ADR 0011의 원격 접근과 같은 길이다). 사용자는 관리 화면을 인터넷에 열기로 했고, 계정과 비밀번호 로그인을 먼저 만든 뒤에 같은 서버의 다른 포트로 열기로 골랐다. 그 일은 새 기능 admin-login의 것이고(아래 Consequences "다른 행") 이 결정은 그때까지의 기본 상태를 정한다.
- **위젯 이미지.** 위젯의 빌드는 사이트 파일을 입력으로 받아 허용 출처(`frame-ancestors`와 번들의 값)와 요청 글자 수 상한을 산출물에 굳힌다(ADR 0024, `web/apps/widget/next.config.ts`). 미리 지어 둔 이미지는 운영자의 사이트 파일을 알 수 없으므로, 위젯 컨테이너는 뜰 때 운영자의 사이트 파일로 빌드한 뒤 서비스를 시작한다. 위젯 코드와 ADR 0019·ADR 0021·ADR 0024의 규칙은 고치지 않는다. 치르는 값은 뜨는 시간과 이미지 크기다. Windows 10의 PC 한 대에서 지금 코드의 위젯을 앞 빌드의 산출물 없이 짓는 빌드는 14.6~76.0초였다(`.scratch/release-image/probes/widget_runtime/README.md` 결과 1번의 14.6초와 `.scratch/release-image/probes/widget_build/README.md` 결과 1번의 76.0초. 76.0초는 네트워크 훅을 실은 빌드이고 CPU가 가득 찬 때의 값이다. 다른 세션이 함께 돌던 때라 범위로만 읽는다. 앞 빌드의 산출물을 둔 빌드는 13.3초까지 내려갔고 이 범위에 넣지 않았다. 컨테이너는 뜰 때마다 산출물 없이 짓는다고 보았기 때문이다). 빌드가 import하는 개발 의존성까지 든 의존성 묶음은 의존 그래프로 닿는 패키지 전체로 470.7MB였고, 빌드의 타입 검사가 시험 쪽 패키지의 타입까지 요구하면 636.8MB에 가깝다(`widget_build` 결과 4번. Windows용 네이티브 패키지가 든 값이고, 시험 쪽 패키지 없이 빌드를 돌려 보지 않아 뒤의 것은 어림이다). 텔레메트리를 끈 빌드에서 node 쪽의 루프백 밖 연결 시도는 세 번 모두 0건이었고 양성 대조는 마지막 실행에서만 섰으며, Turbopack이 직접 여는 소켓은 그 훅이 보지 못한다(같은 프로브 결과 3번). 리눅스 컨테이너에서의 빌드 시간과 메모리, 인터넷이 실제로 없는 빌드는 재지 않았고 명세가 잰다.
- **사이트 파일을 고치면.** 지금은 `serve`, 질문 페이지, 위젯 세 컨테이너를 모두 다시 띄워야 바뀐 사이트 파일을 따른다. `serve`는 사이트 파일을 시작할 때 한 번 읽고(`src/agent_os/main.py`의 `_read_sites`를 읽었다. 변경 시각으로 다시 읽기는 ADR 0023의 2026-11-04 이력이 정했을 뿐 구현되지 않았다), 질문 페이지도 시작 때 한 번 읽으며(ADR 0050 결정 "시작 인자와 시작 검사"), 위젯은 빌드에 굳는다. 위젯 컨테이너가 다시 뜨는 동안 위젯은 응답하지 않는다. 배포 안내가 이 절차를 적는다.
- **TLS 인증서.** 운영자가 가진 인증서와 키 파일을 정해진 폴더에 두면 프록시가 읽는다. 사내 인증 기관이 발급한 인증서도 쓸 수 있고 인터넷이 막힌 곳에서도 된다. 시험 삼아 띄울 때 쓰도록 스스로 서명한 인증서를 만드는 명령을 배포 안내에 적는다. 인증서를 갱신하는 일은 운영자 몫이다.
- **토큰 경로의 빈도 제한.** 질문 페이지의 토큰 끝점 앞에서 프록시가 접속 주소별 요청 빈도를 제한한다(ADR 0050 결정 "빈도 제한"이 넘긴 요건). nginx의 `limit_req`는 기본으로 503으로 거부하고 `limit_req_status 429`를 주면 429다(`.scratch/release-image/probes/netns/README.md` 항목 5. Windows의 Docker Desktop에서, 네트워크 이름공간을 함께 쓰는 배치로 쟀다). 그 PC의 호스트에서 `127.0.0.1`로 건 요청은 상대 주소가 compose 네트워크의 게이트웨이로 보였고, 다른 기기에서 온 요청과 리눅스 서버에서 실제 접속 주소가 보이는지는 재지 못했다. 한도의 수치와 리눅스에서의 접속 주소는 명세가 재서 정한다.
- **실제 이미지로 띄우는 시험.** ADR 0043이 main으로 가는 PR과 main 푸시에 더하기로 한 실제 이미지의 compose e2e 잡은 release-image의 첫 티켓이 Dockerfile·compose와 함께 더한다. dev 전환이 먼저 끝나면 그때는 Dockerfile이 없어 전환 티켓이 그 잡을 만들 수 없다. 판 내기의 "실제로 띄워 시험"도 같은 compose를 쓴다. 판 내기 워크플로는 release-image의 티켓들이 dev에 쌓으므로 release-image의 출시 PR이 병합될 때 처음으로 끝까지 돈다.

## Considered Options

- **네트워크 이름공간을 함께 쓰는 배치(전용 자리 지킴 컨테이너가 주인).** 라운드 3에서 추천했고 사용자가 골랐다. 네 프로세스가 지금처럼 `127.0.0.1`에서만 들어 코드를 고치지 않고, 운영자가 compose에 서버의 포트를 잘못 더해도 바깥에 직접 열리지 않는다(프록시가 주인인 배치에서 쟀다. 이름공간을 빌린 서비스에 준 `ports`는 Docker가 거부했고, 주인이 대신 발행한 포트는 닿지 않았다. `.scratch/release-image/probes/netns/README.md` 항목 4). 프록시를 다시 띄우는 여섯 조작 뒤에 모두 다시 닿았다(항목 7.2). 약한 곳은 자리 지킴 컨테이너였다. 그것을 다시 띄우는 다섯 조작 가운데 `docker compose restart holder` 하나만 닿았고, 나머지 넷은 닿지 않았으며 회복 명령이 경우마다 갈렸다(항목 7.3). 측정은 Windows의 Docker Desktop에서만 했고 조작마다 두 번씩이었으며, Docker 데몬이나 호스트를 다시 켠 뒤는 재지 못했다. 라운드 5 뒤에 사용자가 "네트워크는 도커 네트워크로 묶으면 되는거 아니야?"라고 물었고, 라운드 6에서 보통의 Docker 네트워크를 골라 이 배치는 버려졌다. 얻은 것은 운영자에게 익숙한 꼴, 약한 곳과 회복 절차가 없어지는 것, deploy-package에서 문서 검색 서버와 같은 방식으로 이어지는 것이다. 잃은 것은 아래 Consequences "잃는 것"에 있다.
- **프록시가 이름공간의 주인인 배치.** 선택지에 올리지 않았다. `depends_on`을 적지 않은 판에서 프록시를 다시 띄우는 여섯 조작 가운데 셋이 502였다(같은 프로브 항목 3).
- **한 컨테이너에 프록시와 네 프로세스를 모두 넣는다.** 선택지에 올리지 않았다. 이미지가 넷이라는 기존 결정(기능 계획, ADR 0050)과 어긋난다.
- **GitHub 컨테이너 레지스트리에 올린다.** 라운드 1의 추천이었다. 워크플로의 기본 토큰으로 올릴 수 있어 사람이 만들 계정과 비밀 값이 없다(GitHub 문서의 웹 요약이고 원문을 대 보지 않았다). 사용자가 Docker Hub를 골랐다.
- **사람이나 에이전트가 판을 내는 때를 정한다(태그를 손으로 달거나, 에이전트가 준비하고 사용자가 GitHub의 배포 환경에서 승인한다).** 괄호의 뒤쪽이 라운드 2의 추천이었다(라운드 1은 태그를 누가 언제 다는지를 물었고 그 화면의 추천은 일지에 남지 않았다). 사용자가 "전부 자동으로 안될까?"와 "판을 내는 것도 에이전트가 알아서 판단해서 미리 플랜으로 할 수 없나?"로 답해 버려졌다. 판을 내는 계획은 전체 계획의 기능 목록이 된다.
- **판마다 릴리스 노트 파일을 쓴다.** 라운드 2의 추천이었다(일지는 추천을 "판마다 노트 파일을 씀"으로만 적었고 누가 쓰는지는 남지 않았다). 같은 답으로 버려졌다. 노트는 PR 제목을 묶은 것이고, 제목이 개발자의 말이라 운영자에게 필요 없는 항목이 섞일 수 있다.
- **release-image를 먼저 하고 dev 전환은 따로 한다.** 라운드 4의 추천이었다. 사용자가 dev 전환을 먼저 끝내기를 골랐다. 전환이 큰 작업이라(ADR 0043이 인터뷰 때 센 것으로 tools 12개와 스킬 8개) 그동안 release-image와, 인터뷰 때 그것을 기다리던 기능 넷(diag-bundle, deploy-package, ops-backup-upgrade, public-demo)과, 이 ADR이 세우는 admin-login이 늦어진다. 대신 판을 내는 계기가 "main이 움직였고 지난 판 뒤로 제품 변경이 있다" 하나로 단순해진다.
- **판마다 저장소의 번호를 올린다(CI가 커밋하거나 release-please 같은 도구의 릴리스 PR).** 거부했다. 판마다 계약 파일 `openapi.json`이 함께 바뀌고, 워크플로가 번호를 고친 커밋을 보호된 main에 바로 올리지 못할 것으로 읽었다(어림. 올려 보지 않았다). semantic-release는 0으로 시작하는 판을 지원하지 않는다고 FAQ가 적는다(원문을 받아 대 봤다).
- **태그의 번호가 `pyproject.toml`의 번호와 다르면 CI가 실패한다.** 라운드 1의 답에 든 조건이었다. 번호의 원천이 태그가 되고 저장소의 번호를 0.0.0으로 두면서 라운드 5에서 버려졌다.
- **취약점이 있으면 판 내기를 멈춘다.** 거부했다. 우리 코드가 아니라 바탕 이미지에 든 취약점으로 판 내기가 멈춰 전부 자동이 깨진다.
- **위젯이 요청 때마다 사이트 파일을 읽도록 지금 고친다.** 실험 판(`.scratch/release-image/probes/widget_runtime/runtime.patch`)에서 빌드 하나가 띄울 때의 사이트 파일을 따랐다. 그러나 그 판은 ESLint 오류 4건(Next 서버 파일 금지와 `app/` 경계. ADR 0019, ADR 0021)에 걸리고 위젯 쪽 시험 269개 가운데 5개가 실패했으며(같은 README 결과 8번. 프로브가 다시 내는 값이 아니라 서브에이전트가 그 명령들을 손으로 돌려 본 것이다. e2e와 사진 비교는 돌리지 않았다), ADR 0024가 앞서 거부한 안(헤더만 내는 Next proxy를 ADR 0019의 서버 파일 금지에서 예외로 두는 안)을 다시 열어야 한다. 페이지 응답 시간의 중앙값이 1.4~1.5ms에서 5.0~6.3ms가 됐다(같은 PC에서 차례로 100번씩. 결과 7번. 늘어난 몫이 proxy의 것인지 요청 때 그리기의 것인지는 가르지 않았고, 미리 그린 페이지에 proxy만 건 갈래의 중앙값은 3.1ms였다). 떠 있는 서버가 바뀐 사이트 파일을 다음 요청부터 따라가도 페이지 안 방식의 `element.js`는 띄울 때 지은 값으로 남았다(결과 4번. 한 번 돌렸다). 모두 Windows에서 잰 값이다. 사용자는 이 일을 portal-admin을 만들 때 함께 하기로 골랐다.
- **지어 둔 파일의 자리표를 뜰 때 바꿔 넣는다.** `element.js`에서는 자리표가 한 곳뿐이고 그 숫자를 583927로 바꾼 파일이 바로 지은 파일과 바이트까지 같았다(`widget_runtime` 결과 5번의 (나). 4000은 압축기가 `4e3`으로 써 그 꼴로 바꿔야 같았고, 바꾼 파일을 서버가 내는 것은 재지 않았다). 페이지와 헤더까지 이 길로 내는 판은 돌리지 않았다(어림). 고르지 않았다.
- **관리 화면을 지금 관리 토큰과 프록시 방어만으로 인터넷에 연다.** 라운드 6의 추천이었다(운영자가 허용 주소를 적어야 열린다). 사용자가 로그인을 먼저 만든 뒤에 열기를 골랐다. 관리 API의 인증은 고정 토큰 하나를 견주는 것이고, 그 파일에서 시도 횟수나 잠금을 가리키는 글자는 찾지 못했다(`src/agent_os/http/auth.py`를 Grep했다. 다른 파일은 보지 않았다).
- **관리 화면 로그인을 0.1 판 뒤(제품 1.0 묶음)에 만든다.** 합의 확인 화면의 추천이었다. 사용자가 0.1 판에 넣기를 골랐다.
- **인증서를 프록시가 스스로 발급받는다(ACME).** 기본으로 두지 않았다. 인터넷이 막힌 곳과 사내 인증 기관에서는 되지 않는다. 이 안이 라운드 3의 화면에 선택지로 올랐는지는 일지에 남지 않았다.

## Consequences

- **다른 ADR.** 루프백 규칙을 적은 문장에 이 ADR의 포인터를 단다. ADR 0011의 "루프백이 아닌 주소에는 바인딩하지 않는다", ADR 0010의 "루프백이 아닌 주소는 받지 않는다", ADR 0015의 "루프백만 받는 규칙(ADR 0011)은 채널에도 그대로 걸린다", ADR 0019의 "Next도 루프백에만 선다"(여는 문단과 결정 항목의 두 곳), ADR 0024의 "Next는 루프백에만 선다", ADR 0050 결정 "앱과 서버"의 듣는 주소 문장이다. 규칙은 그대로이고 이미지 안의 명시적 설정이라는 예외가 하나 는다. ADR 0011의 이력 2026-09-28 "루프백 규칙이 관리 화면에도 걸린다"와 2026-09-30 "관리 화면의 상류는 `127.0.0.1` 하나다"가 정한 것에도, 이력 2026-10-03 "최종 사용자 경로만 nginx를 거쳐 원격에 열린다"가 적은 "파이썬은 루프백에만 선다"에도 같은 예외가 걸린다. 지난 이력 항목은 기록이라 포인터를 달지 않고 여기에 적는다. 루프백 목록을 네 파일이 따로 들고 바꾸면 넷을 함께 고친다는 결합(ADR 0047의 "떼어 낼 때 끊을 연결", ADR 0050 결정 "앱과 서버")은 그대로이고, 예외의 판정도 네 곳이 따로 들어 함께 고친다. ADR 0043 Consequences "CI 분담"의 "잡 이름과 모양은 harness 티켓이 정한다"에도 포인터를 단다. compose e2e 잡은 release-image의 첫 티켓이 더한다. ADR 0024의 nginx 항목 "평문 80은 인증서 발급의 확인 경로(ACME HTTP-01, `/.well-known/acme-challenge/`)와 HTTPS로 넘기는 것만 하고, 안으로는 아무것도 넘기지 않는다"에도 포인터를 단다. 단독 compose의 80은 확인 경로를 두지 않고 넘기기만 한다. ADR 0015가 채널 토큰을 루프백 안의 같은 기기에 두는 근거로 든 전제는 단독 compose에서 "같은 compose 네트워크의 컨테이너"로 넓어진다. 운영자 채널을 부르는 것이 그 네트워크의 다른 컨테이너일 수 있고, 평문 HTTP가 그 네트워크 안을 지난다.
- **잃는 것.** 운영자가 compose 파일에 `serve`나 관리 화면의 포트를 호스트의 모든 주소로 잘못 발행하면 암호화 없이 열린다(토큰은 여전히 필요하다). 네트워크 이름공간을 함께 쓰는 배치에서는 이름공간을 빌린 서비스의 `ports`를 Docker가 거부했다(프록시가 주인인 배치에서 쟀다. `.scratch/release-image/probes/netns/README.md` 항목 4). "루프백 밖에는 절대 묶지 않는다"는 규칙의 단순함도 잃는다. 배포 안내가 발행하는 포트를 고치지 말라고 적고, 예외가 이미지 밖에서 켜지지 않게 하는 방법은 명세가 정한다.
- **PRD와 기준선.** 관리 화면 로그인이 0.1 판에 들어가면 PRD의 기준선 성공 조건 "(밖으로 여는 포트는 하나다)"와 ADR 0046의 같은 문장, deploy-package 기능 계획의 "443 하나"가 0.1의 목표로는 맞지 않게 된다. 사용자는 이 ADR의 승인 화면에서 앞의 둘을 이 PR에서 고치기를 골랐다. PRD의 문장은 "(밖으로 여는 포트는 방문자용 하나와, 로그인으로 지키는 관리 화면용 하나다)"가 됐고, ADR 0046은 본문의 그 문장에 포인터를 달고 이력 2026-11-11 "관리 화면 로그인이 기준선의 행이 된다"에 같은 문장을 적었다. 그 문장은 0.1 판의 목표를 적은 것이다. release-image의 단독 compose가 밖으로 여는 것은 프록시 하나(443과, 443으로 넘기기만 하는 80)이고, 관리 화면을 위한 포트는 admin-login이 관리 화면을 열 때 생긴다. 80은 PRD의 문장에 적지 않고 이 ADR에만 둔다. admin-login의 설계가 세부(여는 포트 번호, 운영자가 열지 않고 둘 수 있는지)를 정하면 그 문장을 다시 본다. 참조 배포 쪽에는 글자가 어긋나는 문장이 셋 더 있다. ADR 0048의 "참조 배포가 밖으로 여는 포트는 TLS를 끝내는 리버스 프록시 하나다", deploy-package 기능 계획의 "호스트에 포트를 내놓지 않는다", 그 수락 문장의 "443과 VM을 관리하는 SSH뿐"이다. 단독 compose는 80도 열고 관리 화면의 포트를 호스트의 `127.0.0.1`에 내놓는다. 이 ADR이 정하는 것은 단독 compose이고, 참조 배포가 그 둘을 따를지는 deploy-package의 설계 인터뷰가 정한다(그 기능 계획에 적었다).
- **다른 행.** 새 행 admin-login을 세운다(관리 화면의 계정과 비밀번호 로그인, 그 뒤 관리 화면을 같은 서버의 다른 포트로 인터넷에 연다). 슬라이스는 9이고 `**Blocked by:**`는 release-image이며, pilot-release가 그 행을 기다린다(ADR 0046 이력 2026-11-11). pilot-release가 기다리는 것은 사용자가 고른 선택지의 설명에 있었고, admin-login이 release-image를 기다리는 것은 묻지 않고 정한 기본값이다(관리 화면을 여는 일이 단독 compose와 프록시 설정을 고친다). pilot-release 기능 계획의 수락이 프로브를 다시 돌리는 판은 판 설정 파일의 줄을 지우기 전의 마지막 출시 후보다. 정식 판은 줄을 지운 변경이 main에 오른 뒤에야 나기 때문이다. 그 수락은 "그 판으로"라고만 적어 정식 판으로 읽혔으므로 "마지막 출시 후보로"로 고쳤다(묻지 않고 정한 기본값이다). ADR 0011 결정이 넘긴 물음(원격이 필요해지면 TLS를 어디서 끝내는지와 토큰 대신 무엇을 쓰는지)은 그 행의 설계 인터뷰가 답한다. portal-admin 기능 계획에 요구 하나(허용 출처와 요청 글자 수 상한도 그 화면에서 바꾼다)와, 그 값을 읽는 세 곳(`serve`, 질문 페이지, 위젯)을 함께 고쳐야 한다는 사실과, `widget_runtime` 프로브의 자리를 적는다. 위젯이 그 값을 `serve`에 물어 받아 오는 길은 재지 않았다. release-image 기능 계획의 수락 문장 "main에 판 태그를 달면"은 태그를 CI가 다는 규칙에 맞게 고치고, 프록시를 잇는 방법을 고르라던 문장을 이 결정으로 바꾼다. deploy-package는 이 배치 위에 문서 검색 서버를 같은 네트워크로 잇는다.
- **dev 전환이 먼저다.** 전환은 harness 티켓의 일이라 전체 계획의 `**Blocked by:**`에 적을 수 없다(`tools/plan_table.py`는 전체 계획의 기능이 아닌 항목에 오류를 낸다. 셀프 리뷰가 임시 트리에서 돌려 종료 코드 2를 손으로 봤다). 그래서 전체 계획의 프론티어는 release-image를 조건 없이 들고, 프론티어만 보고 다음 기능을 고르는 세션은 조건을 보지 못한다. 조건은 세 곳이 든다. 전체 계획의 머리(`.scratch/plan-head.md`), release-image 기능 계획 본문의 첫 문장, 그리고 일지의 "다음"과 다음 작업 지시문이다. 전환이 끝나기 전에는 release-image의 명세도 티켓도 시작하지 않는다. 사용자가 고른 설명이 "먼저 끝낸 뒤 release-image를 시작"이기 때문이다. 전환 티켓은 닫힐 때 전체 계획 머리의 그 문장을 걷는다.
- **병합 절차.** `next-session`의 `merge.md`에 "main에 올린 뒤 판 내기를 기다려 결과를 보고와 일지에 적는다"는 단계를 더하는 일은 판 내기 워크플로를 짓는 release-image의 티켓이 한다. 하네스를 고치는 일이라 그 티켓은 워크트리에서 하고 새 세션에서 불러 본다.
- **CI와 비밀 값.** 워크플로가 하나 는다. Docker Hub의 접근 토큰이 GitHub의 비밀 값으로 들고, 그 값은 판 내기 잡만 읽는다. 워크플로의 기본 토큰으로 만든 태그와 릴리스는 다른 워크플로를 일으키지 않으므로(release-please-action의 README가 GitHub 문서를 인용한 것을 읽었다) 태그가 CI를 다시 돌리지 않는다. docker 액션은 커밋 해시로 고정한다(ADR 0027이 `actions/*` 밖의 액션에 요구한다). `aquasecurity/trivy-action`은 2026년 3월에 판 태그 거의 전부가 악성 커밋으로 옮겨진 권고(GHSA-69fq-xp46-6x23)가 있고 커밋으로 고정한 사용자는 영향이 없었다고 그 권고가 적는다(조사 보고에서 옮겼다). 워크플로는 zizmor 감사(ADR 0027)를 지난다.
- **명세가 리눅스에서 재거나 정하는 것.** 컨테이너를 다시 만든 뒤 프록시가 새 주소를 다시 찾는지, 서버를 껐다 켠 뒤 스스로 돌아오는지. 위젯을 뜰 때 빌드하는 시간과 메모리, 인터넷 없이 빌드되는지. 이미지에 번호를 넣는 방법, 판 내기에 걸리는 시간, 이미지 크기. 취약점 점검 도구와 문턱, 바탕 이미지, 상태 확인 방법(지금 상태 확인 끝점은 `serve`의 `/health`와 질문 페이지의 `/portal/health`뿐이고 관리 화면과 위젯에는 없다), 빈도 제한의 수치와 리눅스에서 보이는 접속 주소. root가 아닌 사용자에게 passwd 항목이 없을 때 운영자 채널의 주체 이름을 읽는 `getpass.getuser()`가 실패하는지(어림이다). 판 설정 파일과 예외 설정의 이름, 제품 변경의 경로 목록, 관리 화면과 위젯의 포트(기본이 둘 다 3000이다. `web/apps/admin/tools/start.ts`와 `web/apps/widget/tools/start.ts`가 환경 변수 `PORT`가 없으면 "3000"을 쓴다. 두 파일을 읽었다). 릴리스와 태그의 구체적인 차례, 한 번 올라간 번호 태그를 덮지 않는 방법, 실패한 실행을 다시 돌리는 절차, `feat`도 `fix`도 아닌 접두의 변경을 노트의 어느 묶음에 싣는지.
- **규약 문서.** `docs/constitution/tech.md`의 스택 행(레지스트리, 프록시, 점검 도구)과 `docs/constitution/operations.md`의 병합 절차는 이 PR에서 고치지 않는다. 아직 Dockerfile도 워크플로도 없고 도구가 정해지지 않았기 때문이다. 그것을 짓는 release-image의 티켓이 같은 변경에서 고친다.
- **용어.** `CONTEXT.md`에 제품 판(이 ADR은 판이라고만 쓴다), 출시 후보, 제품 변경, 배포 파일 묶음, 단독 배포를 더한다. 설계 인터뷰의 답과 확인받은 요약은 일지 2026-11-11-1110과 2026-11-11-1532에 글자 그대로 있다.
- **묻지 않고 정한 것의 확인.** 이 문서가 기본값으로 정했다고 적은 곳은 승인 화면에서 일곱 가지로 묶어 보였고, 사용자가 "모두 그대로 둠"을 골랐다. 그 밖의 접두는 끝자리를 올린다, 실패한 판 내기를 다시 돌리는 두 길, 한 번 올라간 번호 태그를 덮지 않는다, 출시 후보와 정식 판의 노트가 싣는 범위, 질문 페이지의 도메인은 운영자가 고르고 제품이 검사하지 않는다, admin-login은 release-image 뒤에 시작하고 dev 전환 전에는 release-image의 명세도 시작하지 않는다, pilot-release의 수락은 마지막 출시 후보로 프로브를 다시 돌린다는 일곱이다. 화면의 글과 답은 일지 2026-11-11-1532의 "ADR 승인"에 글자 그대로 있다.
