# 운영자의 규칙 파일은 실행을 준비할 때 읽혀 도구 호출마다 집행되고, 적용 규칙이 기록에 남으며, 재개에서는 운영자의 deny가 결정을 이긴다

ADR 0042의 묶음 ① 후보 6(운영자의 승인 규칙 파일)이 적어 둔 조건(공통 표와 에이전트별 표, 규칙은 "도구 이름"이나 "서버:\*", 차례는 deny → `requires_approval` → ask → allow → 묻는다, deny는 모델의 도구 목록에서 빼고 직접 호출은 거부로 기록, 운영자는 저자의 승인 요구를 풀지 못한다, 파일 이름은 명세가 짓는다) 위에서 approval-rules의 설계 인터뷰(일지 2026-11-05-08)가 세부를 정했다. 라운드 1의 두 호출 다섯 질문은 모두 추천안으로 합의됐고 라운드 2가 합의 요약 열 가지를 확인받았다. 결정의 원문은 그 일지의 `> 사용자:` 인용이고, 이 ADR은 그 요약을 용어집(`CONTEXT.md`)의 말로 옮긴 것이며 조건은 하나도 빼지 않았다. 인터뷰가 "판정의 근거"라고 부른 것은 용어집의 **적용 규칙**이고, 런타임이 호출마다 규칙을 대 보는 일은 "판정"(용어집에서 재생 평가의 사람 판정)이 아니라 **집행**이라 쓴다. **규칙 파일은 플러그인 루트의 운영자 파일이고 실행을 준비할 때마다 한 번 읽혀 그 실행의 도구 호출마다 집행된다. 집행의 차례는 운영자의 deny → 저자의 승인 요구 → 운영자의 ask → 운영자의 allow → 적힌 규칙이 없으면 묻는다이고, 어느 호출을 어느 규칙이 정했는지(적용 규칙)가 `tool_called`와 `run_paused`의 선택 칸 하나에 남는다. 재개도 지금 디스크의 규칙을 집행하므로 멈춘 사이 deny가 된 도구는 결정이 승인이어도 부르지 않는다. 한 에이전트의 연결에 같은 이름의 도구가 둘 이상이면 연결 직후 실패다.** 이름·문구·검사 자리는 명세(`.scratch/approval-rules/spec.md`, `/to-spec`)가 짓는다.

## 자리와 읽는 때

- 규칙 파일은 플러그인 루트의 운영자 파일이고 꺼진 플러그인의 운영자 파일(`disabled.toml`) 옆에 둔다(ADR 0017의 2026-11-04 이력). 파일 이름은 명세가 짓는다.
- 실행을 준비할 때마다(시작과 재개 모두) 한 번 읽고 캐시하지 않는다. 그 실행의 호출마다 그때 읽은 판을 집행한다. 도는 실행 중에 고친 파일은 다음 실행과 다음 재개부터 듣는다. `disabled.toml`을 `_prepare`가 그렇게 읽는다(`core/run.py`. 코드를 읽었다).
- 파일이 없으면 규칙 없음이라 모든 도구 호출이 묻는다. 깨지면(문법, 형식 버전, 모르는 키, 이름 패턴, 값의 타입, UTF-8, 열기 실패) `disabled.toml`이 깨졌을 때와 같이 그 실행을 시작하지 않는다. 실행 식별자를 만들기 전에 `PluginError`로 끝나 트레이스가 없고, 재개는 결정 이벤트를 쓰기 전에 끝나 일시정지 그대로다(`core/run.py`의 모듈 독스트링. 코드를 읽었다). 운영자 면은 500이고 최종 사용자 면은 고정 문구의 500이다(ADR 0023). 준비 순서(`.claude/rules/core.md`)에서는 깨짐의 "운영자 파일의 손상" 자리에 든다.

## 모양

- `schema_version = "1"`이 필수이고 모르는 키는 손상이다(`disabled.toml`과 같은 규칙).
- 공통 표 하나와 에이전트별 표가 있다. 에이전트별 표의 키는 에이전트 이름(플러그인 이름 패턴)이다. 표마다 `deny`·`ask`·`allow`의 문자열 배열이고 비어도 된다.
- 규칙 문자열은 두 꼴뿐이다. 도구 이름 그대로, 그리고 `<서버 플러그인 이름>:*`(그 서버의 모든 도구). (바뀜: 이력 2026-11-05 "규칙 줄에 서버에 묶인 도구 하나의 꼴이 늘고 allow는 서버를 붙인다") 전역 `*`는 없고 인자 패턴도 없다. (바뀜: 이력 2026-11-06 "도구 이름의 별표는 패턴이다") 인자 패턴은 내장 도구가 생길 때 더한다(일지 2026-11-04-01의 사용자 원문 "일단 "도구 이름과 서버 와일드카드만"으로 하고 … 내장도구가 생긴다면 추가하자").
- 모양만 본다. 에이전트·도구·서버의 이름이 실재하는지는 보지 않는다. (바뀜: 이력 2026-11-05 "그 에이전트의 표는 연결 뒤 대 본다") `disabled.toml`도 문법과 이름 패턴까지만 본다(`adapters/filesystem.py`의 `read_disabled`. 코드를 읽었다). 공통 표는 모든 에이전트에 걸려 어느 한 실행의 준비에서 다 대 볼 수 없다. 오타는 조용히 아무것도 하지 않는다. 기본이 묻는다라 allow나 ask의 오타는 "뜻밖에 묻는다"로 그친다. deny의 오타는 그 deny를 무효로 하므로, 같은 도구에 맞는 allow(`<서버>:*` 등)가 있고 저자의 승인 요구가 없으면 그 도구는 묻지 않고 돈다(PR 봇이 짚었다). 맨 도구 이름 규칙은 그 표가 덮는 모든 에이전트의 모든 서버에서 그 이름의 도구에 맞고(서버 칸은 `<서버>:*`에만 대 본다), 같은 이름 검사(아래 절)는 한 에이전트의 연결 안에서만 서므로, 공통 표의 맨 이름 allow는 다른 에이전트가 고른 다른 서버의 같은 이름 도구도 묻지 않고 돌린다. allow는 `<서버>:*`나 에이전트별 표로 쓰기를 권한다(PR 직전 보안 리뷰가 짚었다). (바뀜: 이력 2026-11-05 "규칙 줄에 서버에 묶인 도구 하나의 꼴이 늘고 allow는 서버를 붙인다") (바뀜: 이력 2026-11-06 "도구 이름의 별표는 패턴이다")
- 표와 키의 정확한 이름은 명세가 짓는다.

## 집행의 차례

- 공통 표와 그 에이전트의 표를 `deny`·`ask`·`allow`마다 합친다(두 표의 deny를 모두 모으고 ask와 allow도 그렇게). 그래서 에이전트별 allow가 공통 deny·ask를 풀지 못하고, 공통 allow도 에이전트별 ask를 풀지 못한다. 운영자 파일은 더하는 쪽으로만 작용한다.
- 차례는 deny(운영자) → 승인 요구(저자, 매니페스트의 `requires_approval`) → ask(운영자) → allow(운영자) → 어느 것에도 맞지 않으면 묻는다(기본. 일지 2026-11-04-01의 사용자 원문 "Claude Code의 평가 순서처럼 하자. 기본을 '물어본다'로 …"). 운영자의 allow는 저자의 승인 요구를 풀지 못하고(일지 2026-11-03-04의 "> 사용자: 못 풀게 하자."), 운영자의 deny는 승인 요구가 있는 도구도 막는다.
- deny인 도구는 모델에 붙이는 도구 목록에서 뺀다. 에이전트가 직접 부르거나 모델이 이름으로 부른 호출은 도구를 부르지 않고 거부로 기록하며(`tool_called(ok=false)`, 문구는 명세) 루프는 계속되고 직접 부른 에이전트는 `ToolError`를 받는다. 지금의 거부 경로 그대로다(`core/run.py`의 `_deny`. 코드를 읽었다).
- ask와 "묻는다"는 지금처럼 `run_paused`로 멈추고 그 실행의 채널(CLI의 운영자, 운영자 채널, 최종 사용자 위젯)이 결정한다. 둘은 행동이 같고 기록된 적용 규칙만 다르다.
- allow는 묻지 않고 부른다.
- 저자의 승인 요구가 가리키는 도구가 실재하는지 보는 지금의 검사(`_reject_unknown_declarations`, 연결 직후)는 deny로 빼기 전의 전체 목록에 대 본다.

## 기록

- `tool_called`와 `run_paused`에 선택 칸 하나(적용 규칙)가 는다. (바뀜: 이력 2026-11-05 "승인 결정은 서버에도 묶인다") 값은 다섯이다. 운영자 deny, 저자 승인 요구, 운영자 ask, 운영자 allow, 적힌 규칙 없음.
- `run_paused`에는 멈추게 한 적용 규칙이, `tool_called`에는 그 호출을 정한 적용 규칙이 든다. 멈춘 뒤 결정을 받아 돈 호출이면 멈추게 한 것 그대로다(멈춘 사이 deny가 되어 거부된 호출은 운영자 deny다. 재개 절). 재생 구간의 호출은 기록을 다시 쓰지 않는다(ADR 0009).
- 트레이스 형식은 3 그대로다. 선택 칸을 더하며 형식을 그대로 둔 선례는 ADR 0031(`run_failed`의 원인)과 ADR 0009의 2026-09-22 이력(`llm_called.prompt`)이고, ADR 0042 묶음 ②가 밀리초 칸에 정한 "기본값 없음의 선택 필드, 형식 번호 그대로"와 같은 모양이다. 반대 방향의 선례는 ADR 0022로, 재개의 입력이 되는 이벤트 종류가 늘어 3으로 올렸다. ADR 0008의 기준은 "기존 필드의 뜻이나 필수 여부가 바뀔 때" 올리는 것이다. 옛 트레이스에는 칸이 없다.
- 이벤트는 관리 API의 응답 타입이라 `openapi.json`, 생성 TS 타입, 관리 화면의 필드 이름 표(`web/apps/admin/components/organisms/EventItem.tsx`)가 바뀐다. 첫 티켓이 계약 티켓이다. 칸의 이름은 다른 이벤트의 필드 이름과 겹치지 않아야 한다(`.claude/rules/sdk.md`의 필드 이름 표 규칙). 칸과 값의 이름은 명세가 짓는다.

## 재개

- 재개도 준비 단계에서 규칙 파일을 다시 읽어 지금 디스크의 규칙을 집행한다.
- 멈춘 사이 그 도구가 deny가 됐으면 결정이 승인이어도 도구를 부르지 않고 거부로 기록하며 실행은 계속된다. 적용 규칙은 운영자 deny다. 결정이 거부여도 같다. 집행의 차례에서 운영자 deny가 먼저라 적용 규칙과 거부 문구는 결정의 것이 아니라 운영자 deny의 것이다. 승인자는 그 실행의 주체이고 최종 사용자일 수 있어(ADR 0009의 2026-10-03 이력), 운영자의 deny는 누구의 결정으로도 넘지 못한다. ADR 0042의 "저자는 운영자의 deny를 넘지 못한다"와 같은 방향이다.
- 그 밖의 변화(ask가 allow로, 승인 요구에서 빠짐 등)는 지금 규칙대로 결정을 그 호출에 적용한다(승인이면 부르고 거부면 거부로 기록한다). ADR 0009의 2026-09-22 이력 "같은 호출이면 정책이 바뀌었어도 결정을 적용한다"가 조건 없이 서는 것은 저자의 승인 요구뿐이고, 운영자의 규칙에서는 deny 하나가 결정을 이긴다(ADR 0009의 2026-11-05 이력).

## 같은 이름의 도구

- 한 에이전트가 고른 서버들이 준 도구 목록에 같은 이름이 둘 이상이면 연결 직후 `run_failed`(원인 `tool_connection`)다. 저자의 승인 요구의 오타가 실패하는 때(연결 직후)와 원인이 같다.
- 지금은 어댑터가 도구 이름으로 길을 모아 같은 이름이면 뒤 서버가 앞 서버를 조용히 덮는다(`adapters/mcp.py`의 `routes[route.tool.name]`. 코드를 읽었다). 그 상태로는 "도구 이름" 규칙이 어느 서버의 도구를 막는지 가를 수 없고 "서버:\*" 규칙은 덮인 서버에 맞지 않는다.
- 이를 위해 어댑터가 도구마다 그 도구를 낸 서버 플러그인의 이름을 `ToolSpec`(core 타입, `core/ports.py`)에 실어 넘긴다. "서버:\*" 규칙을 대 보는 근거이기도 하다. 검사가 어댑터에 서는지 core에 서는지는 명세가 정한다. 다만 지금의 `McpConnection.tools()`는 이름으로 모은 딕셔너리의 값을 돌려줘 같은 이름이 하나로만 보이므로(`adapters/mcp.py`. 코드를 읽었다), core에 두려면 연결이 덮지 않은 목록을 돌려줘야 하고, 어댑터에 두려면 `connect`가 딕셔너리에 쓰기 전에 던진다.

## 층과 포트

- 집행은 core의 승인 게이트 한 자리(`core/run.py`의 `_Context._call`)에 선다. 루프의 호출과 에이전트의 직접 호출이 같은 자리를 지난다(ADR 0009).
- 규칙 파일은 `PluginSource`에 동기 읽기 메서드 하나가 늘어 읽고 포트는 다섯 그대로다(ADR 0012의 2026-11-05 이력). 형식은 어댑터가 소유하고 돌려주는 값은 core 타입이다. `disabled.toml`과 같은 자리다.
- sdk는 두 이벤트의 선택 칸 말고는 바뀌지 않는다. 매니페스트는 그대로다.

## 범위 밖

- 관리 API와 관리 화면은 바꾸지 않는다. 트레이스 상세가 새 칸을 그리는 데까지(필드 이름 표의 항목 하나)만이다. (바뀜: 이력 2026-11-05 "승인 결정은 서버에도 묶인다") 규칙 파일은 `disabled.toml`처럼 git으로 고치고, 운영자 파일의 화면 편집은 묶음 ⑤의 관리 화면 CRUD(ADR 0042 후보 21)가 맡는다.
- 사이트 축은 없다. 인자 패턴은 없다.
- 맡기기의 deny·ask는 묶음 ④(ADR 0042 후보 2)에서 정한다. 서버의 신뢰 수준과 도구 정의 해시는 다음 기능 mcp-trust(후보 7)다. (바뀜: ADR 0046)
- 최종 사용자가 주체인 실행에서 운영자의 ask와 적힌 규칙 없음은 그 최종 사용자 자신의 확인이고 운영자의 검토가 아니다. 결정은 그 실행의 주체만 내리고(ADR 0009의 2026-10-03 이력, ADR 0023), 지금의 저자 승인 요구도 같은 길이다. 요청자에 맞서 서는 운영자의 제어는 deny뿐이다. 운영자가 묻는 ask(승인자 축)는 ADR 0023이 거부한 "운영자도 채널 토큰으로 최종 사용자의 실행에 결정한다"를 다시 여는 것이라 범위 밖이다(PR 직전 보안 리뷰가 짚었다).
- 승인 결정을 서버에 묶는 일은 이 ADR이 정하지 않는다. (바뀜: 이력 2026-11-05 "승인 결정은 서버에도 묶인다") 멈춘 사이 매니페스트의 `mcp`가 바뀌어 같은 이름의 도구가 다른 서버에서 오면 승인이 그 서버의 도구를 부른다. 이 기능 전부터 있는 길이고, 재개의 일치 검사(`_require_paused_call`)는 도구 이름과 인자만 비교한다(코드를 읽었다). `ToolSpec`에 서버 칸이 생기면 `run_paused`에 서버를 싣고 재개가 대 볼 수 있지만, 이벤트 칸을 하나 더하는 계약 결정이라 사용자가 정할 물음이다(PR 봇이 짚었다).
- deny된 호출이 최종 사용자에게 보이는 모양은 지금의 거부와 같은 길이다. 최종 사용자 투영(`channel/http/items.py`의 `project`)은 `tool_called`에서 도구 이름과 `ok`만 옮기고 내용(거부 문구)은 싣지 않으므로, 위젯에는 실패한 진행 항목으로만 보인다(코드를 읽었다. PR 직전 보안 리뷰가 짚었다). 적용 규칙 칸도 명세가 최종 사용자 항목에 더하지 않는 한 위젯에 가지 않는다.

## Considered Options

라운드의 고르지 않은 선택지는 라벨만 일지에 있다. 이 ADR이 견준 이유는 아래다.

- **적용 규칙을 기록하지 않는다.** 운영자가 "왜 멈췄나, 왜 그냥 돌았나"를 트레이스에서 읽을 수 없어 ADR 0042의 기록 보장이 이 기능에서 비게 된다. 거부했다.
- **새 이벤트 종류로 낸다.** 이벤트 종류가 늘면 형식 번호를 올린 선례(ADR 0022)를 따르게 되고, 재생 기록 열 밖의 종류 목록(`core/run.py`의 `_NOT_REPLAYED`)과 api-client의 종류 목록도 바뀐다. 선택 칸 하나로 같은 사실을 남길 수 있다. 거부했다.
- **재개에서 결정이 이긴다.** ADR 0009의 2026-09-22 이력 그대로 두는 안이다. 승인자가 최종 사용자일 수 있어 운영자의 deny를 결정 하나가 넘게 된다. 거부했다.
- **그 에이전트의 표만 연결 뒤 대 본다, 에이전트 이름의 실재도 본다.** (바뀜: 이력 2026-11-05 "그 에이전트의 표는 연결 뒤 대 본다") 공통 표는 한 실행의 준비에서 다 대 볼 수 없고, `disabled.toml`도 실재를 보지 않는다. 기본이 묻는다라 allow의 오타는 뜻밖에 묻는 데서 그친다(deny의 오타가 허락으로 번지는 길은 모양 절에 적었다). 거부했다.
- **같은 이름의 도구를 지금처럼 조용히 덮는다, mcp-trust에 넘긴다.** 덮으면 규칙이 어느 서버의 도구를 가리키는지 가를 수 없고, 넘기면 그 사이 이 기능의 "서버:\*" 규칙이 덮인 서버에 맞지 않는다. 거부했다.
- **결정 칸에 deny 미리 알림을 더한다, 규칙 파일 원문 GET만 더한다.** 관리 API와 관리 화면의 변경을 이 기능에서 열지 않는다. 운영자 파일의 화면 편집은 묶음 ⑤의 몫이다. 거부했다.
- **전역 `*`와 인자 패턴.** 사용자가 2026-11-04에 "일단 도구 이름과 서버 와일드카드만"으로 미뤘다. 내장 도구가 생길 때 더한다. (바뀜: 이력 2026-11-06 "도구 이름의 별표는 패턴이다")
- **운영자가 저자의 승인 요구를 푼다.** 2026-11-03에 라운드 밖에서 사용자가 "못 풀게 하자"로 거부했다(일지 2026-11-03-04, ADR 0042).
- **allow를 두지 않는다(deny·ask 둘뿐). 또는 allow를 두되 좁은 allow가 넓은 ask를 이긴다.** 2026-11-04의 묶음 ① 라운드가 올린 두 선택지이고 둘 다 고르지 않았다. 사용자는 선택지 밖에서 "Claude Code의 평가 순서처럼 하자. 기본을 '물어본다'로 …"를 답해, allow가 들어오되 기본은 묻는다가 됐다(일지 2026-11-04-01, ADR 0042).

## Consequences

- **계약.** `tool_called`·`run_paused`의 선택 칸 하나가 `openapi.json`, `packages/api-client`의 생성 타입, 관리 화면의 필드 이름 표를 바꾼다. (바뀜: 이력 2026-11-05 "승인 결정은 서버에도 묶인다") 트레이스 형식은 3 그대로다. 첫 티켓이 계약 티켓이고 그 기능의 다른 티켓을 막는다(작업 규약 2).
- **포트.** `PluginSource`에 동기 읽기 메서드 하나, `ToolSpec`에 서버 플러그인 이름 칸이 는다. 포트는 다섯 그대로다(ADR 0012의 2026-11-05 이력). 시그니처와 값의 모양은 명세가 정한다.
- **이력과 포인터.** ADR 0009에 이력 2026-11-05(운영자의 deny가 재개의 결정을 이긴다)를 쌓고, 본문 "승인이 필요한 도구는 에이전트 매니페스트의 `requires_approval`이 정하고"에 `(바뀜: ADR 0044)`를 단다. 승인이 필요한 도구를 이제 운영자의 규칙 파일(ask, 적힌 규칙 없음)도 정하기 때문이다. ADR 0012에 이력 2026-11-05를 쌓는다. ADR 0017의 본문은 글자 그대로 참이라(운영자 파일 둘이 느는 것은 그 2026-11-04 이력에 있다) 포인터가 없다.
- **구현 티켓이 코드와 같은 티켓에서 고치는 하네스 문서.** `.claude/rules/core.md`의 재개 항목("같은 호출이면 정책이 바뀌었어도 적용한다"는 저자의 승인 요구로 좁힌다), 승인 게이트 항목(집행의 차례와 적용 규칙), 준비 순서의 "운영자 파일의 손상"(규칙 파일이 든다), 포트 표의 `PluginSource`·`ToolSource` 행. `.claude/rules/adapters.md`의 운영자 파일 항목(규칙 파일 읽기)과 MCP 어댑터(같은 이름의 도구, `ToolSpec`의 서버 칸). `.claude/rules/sdk.md`의 이벤트 칸 항목(선택 필드, 형식 3 그대로, 필드 이름 표).
- **치르는 값.** 기본이 묻는다라 규칙 파일이 없는 배치에서는 모든 도구 호출이 멈춘다. 저장소의 calc와 e2e·테스트(위젯 e2e의 `tools` 에이전트, calc의 `-m llm` 시험, 채널 테스트의 도구 에이전트, `tests/core/test_run.py`의 도구를 부르는 사례 다수)가 allow 규칙 파일을 함께 둔다(구현 티켓. 멈추는 자리의 셈은 서브에이전트가 코드를 읽은 것이고 다수는 어림이다). 같은 이름의 도구를 내는 서버 둘은 한 에이전트가 함께 쓸 수 없다. allow·ask의 오타는 소리 없이 묻는다가 되고, deny의 오타는 소리 없이 그 deny가 없어진 것이 된다(같은 도구에 맞는 allow가 있으면 묻지 않고 돈다). (바뀜: 이력 2026-11-05 "그 에이전트의 표는 연결 뒤 대 본다") 공통 표의 맨 도구 이름 allow는 그 이름을 내는 모든 서버의 도구를 연다(모양 절). (바뀜: 이력 2026-11-05 "규칙 줄에 서버에 묶인 도구 하나의 꼴이 늘고 allow는 서버를 붙인다") 인터뷰가 모양의 보기로 든 Claude Code의 MCP 도구 규칙은 단일 도구 규칙도 서버에 묶이는데(`mcp__서버__도구`) 이 ADR의 "도구 이름" 꼴에는 서버 접두가 없다. 서버에 묶인 단일 도구 꼴(`<서버>:<도구>`)은 이 ADR이 정하지 않았고, 더하려면 이 ADR의 이력에 쌓는다(물음은 일지 2026-11-05-08의 "다음"). (바뀜: 이력 2026-11-05 "규칙 줄에 서버에 묶인 도구 하나의 꼴이 늘고 allow는 서버를 붙인다") 에이전트의 도구가 모두 deny이면 모델에 붙일 도구가 없다. 멈춘 사이 전부 deny가 된 실행의 재개는 이미 도구 호출 블록이 든 대화를 도구 정의 없이 모델에 보내게 되는데, API가 그런 요청을 거부하면 원인 `model_call`의 `run_failed`다(어림. 재지 않았다. `core/loop.py`의 `_bind`가 빈 목록이면 도구를 붙이지 않는 것은 코드를 읽었다). 명세가 실제 호출로 대 보고 처리를 정한다. (바뀜: 이력 2026-11-05 "명세가 정한 것과 잰 것") 이 기능 전의 코드가 새 칸이 든 `tool_called`·`run_paused` 줄을 읽으면 아는 종류의 모르는 필드라 그 트레이스를 손상(`PluginError`)으로 거부한다(`adapters/jsonl.py`의 `_read_event`, ADR 0031). `run_failed`의 원인 칸과 달리 두 이벤트는 재개의 입력이라, 옛 판은 새 판이 쓴 멈춘 실행을 재개하지 못한다. 같은 저장소를 옛 판과 새 판이 함께 읽지 않는 배치라 받아들인다(`.claude/rules/adapters.md`가 원인 칸에서 받아들인 것과 같은 판단).
- **`CONTEXT.md`.** 저자, 승인 요구, 적용 규칙이 용어로 섰다. 운영자·최종 사용자 정의의 "플러그인을 쓰는 개발자"는 저자로, 하위 실행 정의의 "승인 정책"은 승인 요구로 바꿨다.
- **`.scratch/plan.md`.** approval-rules 행에 이 ADR과 일지를 적는다. skill-plugin 행은 티켓 다섯이 모두 병합되어 done이다.
- **명세로 넘긴 것.** 파일 이름, 표와 키의 이름, 선택 칸과 다섯 값의 이름, 거부 문구, 깨짐의 문구, 같은 이름 검사의 자리(어댑터인지 core인지), `PluginSource` 메서드의 시그니처와 돌려주는 값의 모양, 테스트 자리, 예시 allow 규칙 파일의 내용(allow는 맨 이름이 아니라 `<서버>:*`나 에이전트별 표로 쓴다), 도구가 모두 deny인 재개(이미 도구 호출 블록이 든 대화에 빈 도구 목록으로 모델을 부르는 길)의 처리와 시험, 모델이 연결 목록에 없는 이름을 불렀을 때 승인 게이트 앞에서 거부할지, 에이전트가 낸 `tool_called`·`run_paused`의 적용 규칙 칸을 런타임만 쓰게 막을지(지금 `_reject_runtime_only`는 대화 요약과 실패 이벤트만 막는다. 코드를 읽었다. PR 봇이 짚었다). 명세가 ADR 본문의 사실을 거짓으로 만들면 이 ADR의 이력에 쌓고 포인터를 단다(`.claude/rules/adr.md`).
- **근거의 종류.** "코드를 읽었다"로 적은 것은 인터뷰가 올리기 전에 이 세션이 대 본 것이고 자리는 일지 2026-11-05-08의 "찾은 사실"에 있다(`core/run.py`의 게이트·거부·연결 직후 검사, `adapters/mcp.py`의 길 모으기, `adapters/filesystem.py`의 `read_disabled`, `adapters/jsonl.py`의 형식 번호, `sdk/events.py`의 두 이벤트 칸, 관리 API의 플러그인 경로 셋). "어림"은 대 보지 못한 것이다. 프로브는 없다. 이 결정에 수치 근거가 없기 때문이다. (바뀜: 이력 2026-11-05 "명세가 정한 것과 잰 것")

## 이력

### 2026-11-05 규칙 줄에 서버에 묶인 도구 하나의 꼴이 늘고 allow는 서버를 붙인다

명세(`.scratch/approval-rules/spec.md`의 "표와 키와 규칙 줄의 모양")를 쓰며 사용자가 골랐다(일지 2026-11-05-10). 본문 "모양"의 "규칙 문자열은 두 꼴뿐이다"에 셋째 꼴 `<서버 플러그인 이름>:<도구 이름>`(그 서버의 그 도구 하나)이 더해져 꼴은 셋이다. 서버 칸은 이제 `<서버>:*`와 `<서버>:<도구>`에 대 본다. 그리고 `allow`에는 서버를 붙인 두 꼴만 쓰고 맨 도구 이름은 깨진 파일로 거부한다. 열어 주는 규칙은 넓게 맞으면 뜻밖의 도구가 열리므로 정확해야 하고, 막는 deny와 묻는 ask는 넓게 맞아도 안전한 쪽이라 맨 이름을 그대로 받는다. 치르는 값의 "공통 표의 맨 도구 이름 allow는 그 이름을 내는 모든 서버의 도구를 연다"는 길이 이것으로 닫힌다. 물음은 PR 469의 PR 직전 보안 리뷰가 짚어 일지 2026-11-05-08의 "다음"에 사용자가 정할 것으로 남겼던 것이다.

### 2026-11-05 승인 결정은 서버에도 묶인다

명세의 "서버 칸과 재개의 대조"를 쓰며 사용자가 골랐다(일지 2026-11-05-10). `run_paused`에 멈춘 도구를 낸 서버 플러그인의 이름을 드는 선택 칸이 하나 더 늘어, 두 이벤트에 느는 선택 칸은 셋(`tool_called`의 적용 규칙, `run_paused`의 적용 규칙과 서버)이다. 기본값이 없음이라 트레이스 형식은 3 그대로이고 관리 화면의 필드 이름 표에는 두 줄이 든다. 재개의 일치 검사는 도구 이름과 마스킹된 인자에 더해 멈춤 기록에 서버가 있고 지금 연결에 그 이름의 도구가 있으면 그 도구를 낸 서버와 같은지 보고, 다르면 재개 불일치다. 지금 연결에 그 이름의 도구가 없으면 서버를 대 보지 않고, 재개가 아닐 때와 같이 게이트 앞에서 `도구가 없다`로 거부하며 결정은 소비된다(명세 "집행의 차례" 3이 정했다. 사용자의 답은 서버가 다를 때만 불일치라 했다). 서버가 없는 옛 멈춤 기록은 지금처럼 이름과 인자만 본다. 본문 "범위 밖"의 "승인 결정을 서버에 묶는 일은 이 ADR이 정하지 않는다"는 이것으로 정해졌다. ADR 0009의 2026-11-05 둘째 이력이 같은 결정을 든다. 계기는 PR 469의 CodeRabbit이 Major로 짚은 것이다.

### 2026-11-05 그 에이전트의 표는 연결 뒤 대 본다

명세의 "에이전트 표의 검사"를 쓰며 사용자가 골랐다(일지 2026-11-05-10). Considered Options가 거부했던 "그 에이전트의 표만 연결 뒤 대 본다, 에이전트 이름의 실재도 본다"의 앞절반이 들어왔다. 거부의 근거였던 "뜻밖에 허락되는 일은 없다"를 PR 469의 CodeRabbit 첫 회차가 짚어 바로잡은 뒤(deny의 오타는 같은 도구에 맞는 allow가 있으면 묻지 않고 돈다. 일지 2026-11-05-08 봇 회차) 사용자에게 다시 물었다. 에이전트 이름의 실재는 그대로 보지 않는다. 그 에이전트의 표에 적힌 줄은 연결 직후, 저자의 승인 요구가 가리키는 도구의 실재를 보는 검사 바로 뒤에 대 본다. 맨 도구 이름은 연결의 도구에 그 이름이 있어야 하고, `<서버>:*`는 그 서버가 매니페스트의 `mcp`에 있어야 하며, `<서버>:<도구>`는 그 서버가 낸 그 도구가 있어야 한다. 어긋나면 `run_failed`(원인 `tool_connection`)다. 공통 표는 여러 에이전트에 걸치므로 본문대로 모양만 본다. 그래서 "모양"의 "모양만 본다. 에이전트·도구·서버의 이름이 실재하는지는 보지 않는다"는 공통 표와 에이전트 이름에만 남고, deny의 오타가 allow 뒤에 숨는 길은 에이전트 표에서 닫히고 공통 표에서 남는다.

### 2026-11-05 명세가 정한 것과 잰 것

명세(`.scratch/approval-rules/spec.md`)가 "명세로 넘긴 것"을 채웠다. 파일 이름은 `rules.toml`, 표는 `[common]`과 `[agents.<에이전트 이름>]`, 적용 규칙 칸은 `rule`이고 값은 `deny`·`requires_approval`·`ask`·`allow`·`default`(sdk의 닫힌 목록 `AppliedRule`), 서버 칸은 `server`, 거부 문구는 `운영자가 거부했다: <서버>:<도구>`, 깨짐과 읽기 실패의 문구는 `disabled.toml`의 둘 그대로다. 같은 이름 검사는 MCP 어댑터가 연결을 열며 이름으로 모을 때 한다(`같은 이름의 도구가 둘이다: <도구> (<서버>, <서버>)`). `PluginSource.read_rules()`는 인자 없는 동기 메서드이고 core의 불변 값 `Rules`를 돌려주며 파일이 없으면 빈 값이다. 연결 목록에 없는 이름의 호출은 게이트 앞에서 `도구가 없다: <이름>`으로 거부하고 적용 규칙은 없음이다. 두 칸은 런타임만 쓰고 에이전트가 채워 내면 `run_failed`(원인 `agent_code`)다. 결정이 적용된 호출의 적용 규칙은 멈추게 한 것 그대로이고 deny만 예외다(본문 "기록"과 같다). 명세가 더 찾은 것 하나는 마스킹과 묻기의 충돌이다. 마스킹할 인자가 있는 도구를 운영자의 ask나 적힌 규칙 없음이 멈추게 하면 승인 뒤 마스킹된 값이 도구에 가므로, 저자의 승인 요구와 겹치는 도구를 거부하는 지금의 자리처럼 준비 단계에서 `PluginError`로 거부한다. 잰 것은 "치르는 값"의 어림 하나다. 도구 호출 블록이 든 대화를 도구 정의 없이 보내도 API가 받았다(`.scratch/approval-rules/probes/all_deny_resume_call.py`, 모델 `claude-opus-5`, 세 갈래 여섯 회차 모두 수락. 결과는 그 폴더의 README). 그래서 모두 deny인 재개에 처리를 따로 두지 않고, 구현 티켓의 `-m llm` 시험 하나가 실제 재개로 다시 잰다.

### 2026-11-06 도구 이름의 별표는 패턴이다

티켓 02(규칙 파일 읽기)를 구현하다 사용자가 골랐다. 구현 세션은 맨 `*`나 `send_*`가 와일드카드가 아니라 글자 그대로의 이름으로 읽혀 `deny = ["send_*"]`가 조용히 아무 도구도 막지 않는 모양을 짚고 어떻게 할지 물었다. 사용자는 처음에 읽을 때 깨진 파일로 거부하는 안을 골랐다가, Claude Code는 어떻게 하는지 물은 뒤 "같게 해줘"라고 했다. Claude Code의 권한 규칙 문서(`https://code.claude.com/docs/en/permissions`, 2026-11-06에 읽었다)는 deny와 ask가 도구 이름 전체에 맞는 글롭(`"*"`는 모든 도구, `"mcp__*"`는 모든 MCP 도구)을 받고, allow는 글자 그대로의 `mcp__<서버>__` 접두 뒤에서만 글롭(`mcp__github__get_*`)을 받으며 앞이 열린 allow 글롭은 건너뛰어 아무것도 승인하지 않는다고 적는다.

본문 "모양"의 "전역 `*`는 없고"가 이것으로 뒤집힌다. 도구 이름의 `*`는 아무 글자열(빈 것 포함)에 맞는 패턴이고 패턴은 도구 이름 전체에 맞아야 한다. 맨 `*`는 모든 서버의 모든 도구, `send_*`는 그 접두로 시작하는 도구, `<서버>:get_*`는 그 서버의 그 접두 도구다. 다른 글자는 글자 그대로이고 `?`나 `[…]` 같은 다른 글롭 문법은 없다. 서버 칸은 플러그인 이름이라 패턴이 아니고 `*:add`는 깨진 파일이다. `<서버>:*`는 도구 칸이 `*`인 꼴의 하나로 읽힌다. `allow`는 이력 2026-11-05 "규칙 줄에 서버에 묶인 도구 하나의 꼴이 늘고 allow는 서버를 붙인다"대로 서버를 붙인 꼴만 받고, 그 도구 칸에서만 패턴을 받는다. 맨 `*`와 `send_*`는 맨 이름이라 allow에서 깨진 파일이다. Claude Code는 같은 줄을 건너뛰어 승인하지 않지만 이 파일은 조용히 효력이 없는 줄이 남지 않게 읽을 때 거부한다. 인자 패턴은 여전히 없다. 본문 Considered Options의 "전역 `*`와 인자 패턴" 가운데 전역 `*`가 들어왔고 인자 패턴은 그대로 미룬다.

이력 2026-11-05 "그 에이전트의 표는 연결 뒤 대 본다"의 검사는 도구 이름에 `*`가 든 줄을 도구의 실재 검사에서 뺀다. 패턴은 맞는 도구가 지금 없어도 뜻이 있고(맨 `*`는 어느 도구든 막는다), 그 검사는 글자 그대로의 이름이 오타인지를 잡으려는 것이기 때문이다. `<서버>:패턴`의 서버는 에이전트 매니페스트의 `mcp`에 있는지 계속 본다. 그래서 패턴 줄의 오타(`snd_*`)는 그 검사로 드러나지 않는다. 받아들인 잔여다. Claude Code도 같은 문서에서 도구 이름에 `*`가 든 deny·ask 규칙을 "맞는 도구 없음" 시작 경고에서 뺀다. 이 검사는 티켓 05가 구현하며 명세와 티켓 05가 같은 결정으로 고쳐졌다.

맞춤의 의미는 core의 `Rule.matches`가 소유하고 파일의 글자 모양은 어댑터가 본다. 명세(`.scratch/approval-rules/spec.md`의 "표와 키와 규칙 줄의 모양"과 "핵심의 규칙 값과 포트 메서드")와 티켓 02가 같은 결정으로 고쳐졌다.
