# Agent OS는 위젯을 모른다: 관리 화면과 serve는 위젯 전용 기능을 갖지 않고, 위젯의 외형과 문구는 위젯과 사이트가 가진다

위젯(`web/apps/widget`)은 용어집에서 "사이트의 페이지에 들어가 최종 사용자가 채널을 쓰는 앱"이고 채널이 아니다. Agent OS가 보장하는 중재, 강제, 기록과도 무관하다. 앞으로 위젯에 맞춤 설정(색, 로고, 인사말, 추천 질문)이 생기면 그 설정 화면을 어디에 둘지가 문제가 된다. 2026-11-05의 계획 제안서(일지 2026-11-06-02)는 위젯을 나중에 별도 저장소로 떼어 낼 수 있도록 Agent OS 관리 화면에 위젯 앱의 관리 기능을 두지 않는다고 적었고, 사용자가 2026-11-06 PRD 개정으로 "Agent OS는 위젯을 모른다"를 승인했다.

main 83a66cd에서 지금 상태를 읽었다. 관리 화면(`web/apps/admin`)에 위젯 관리 기능이 없다. 관리 화면과 `src/`가 위젯을 이르는 곳은 모두 주석과 독스트링이다. 예를 들어 위젯을 경로를 쓰는 쪽의 예로 들거나(위젯이 fetch로 스트림을 읽는다), 같은 규칙을 따른다고 적거나(루프백 목록, 사이트 파일의 허용 출처), 문구와 표시는 위젯의 몫이라고 적는다(`git grep -i -E 'widget|위젯' -- web/apps/admin src`로 손으로 봤다). 그 가운데 루프백 목록과 사이트 파일의 규칙은 주석만이 아니라 함께 고쳐야 하는 결합이고, 아래 "떼어 낼 때 끊을 연결"에 적었다. `openapi.json`의 경로 열셋은 범용(`/end-user/...`, `/runs`, `/plugins`, `/traces`, `/health`)이고 스키마 이름에 widget이 없다. `web/eslint.config.mjs`의 경계 규칙이 앱 사이의 import를 막는다. 이 ADR은 그 상태를 규칙으로 고정한다.

## 결정

- **의존 방향은 위젯에서 Agent OS로 가는 한쪽뿐이다.** 위젯은 `openapi.json` 계약(생성된 api-client)과 디자인 시스템 패키지를 통해 Agent OS를 알지만, `serve`, 관리 API, 관리 화면은 위젯을 모른다. 모른다는 것은 위젯의 코드를 import하지 않고 위젯 전용 경로와 기능을 두지 않는다는 뜻이다. 주석이 위젯을 채널을 쓰는 앱의 예로 드는 것은 그대로 둔다.
- **관리 화면과 관리 API에 위젯 전용 기능을 두지 않는다.** 위젯의 외형, 문구, 배치를 보거나 고치는 기능이 그것이다.
- **위젯의 외형과 문구는 위젯과 사이트가 가진다.** 사이트가 위젯을 넣을 때 넘기는 임베드 옵션(커스텀 요소의 속성, iframe의 초기화 메시지)이 값을 정하고, 기본값은 위젯 배포의 설정 파일에 둔다. 맞춤 설정 화면이 필요하면 사이트 쪽이나, 떼어 낸 뒤의 위젯 프로젝트에 만든다.
- **사이트 파일은 채널의 신뢰 설정만 든다.** 발급자, 공개 키, 대상, 허용 출처, 열 에이전트, 상한이다. 위젯의 외형 칸을 더하지 않는다(`CONTEXT.md`의 사이트 파일 항목이 이미 "위젯 설정"을 피할 말로 적었다). 관리 화면이 사이트 파일을 고치게 되더라도(admin-crud), 그것은 채널 설정을 고치는 것이다.
- **위젯은 최종 사용자 채널의 참조 클라이언트로 이 저장소에 남는다.** 떼어 내는 것은 아래 신호 가운데 둘 이상이 보일 때 새 ADR로 정한다.

## 떼어 낼 신호

| 신호 | 확인 방법 |
|---|---|
| 채널 계약이 안정되었다 | `openapi.json`의 최종 사용자 경로가 몇 달 동안 호환을 깨는 변경 없이 유지된다 |
| 위젯을 따로 내보낼 이유가 생겼다 | 위젯을 SDK로 배포하거나, 사용처가 위젯만 받아 자기 사이트에 맞춰 고치려 한다 |
| 맡는 사람이 달라졌다 | 위젯을 전담하는 사람이 생겨 런타임과 다른 리듬으로 일한다 |
| 바뀌는 속도가 크게 달라졌다 | 위젯은 자주 바뀌는데 런타임은 드물게 바뀌고, 위젯의 사진 비교와 e2e가 런타임 변경을 느리게 만든다 |

## 강제

- **화면.** `web/eslint.config.mjs`의 앱 사이 import 금지가 관리 화면과 위젯의 코드 결합을 막는다(이미 있다).
- **API.** `openapi.json`의 경로와 스키마 이름에 위젯 전용 이름(예: `widget`)이 없는지 보는 저장소 상태 테스트를 harness 티켓 하나로 더한다. 이 ADR의 PR에는 들지 않는다. 이름을 피해 들어오는 기능까지 잡지는 못하므로 이 테스트는 경보이고, 규칙의 원천은 이 ADR이다. 나머지는 리뷰가 본다.

## 떼어 낼 때 끊을 연결

- 위젯 빌드(`web/apps/widget/tools/site-file.ts`)가 `serve`의 사이트 파일을 직접 읽어, 허용 출처(frame-ancestors)와 가장 작은 `request_chars`를 `serve`와 같은 규칙으로 판정한다(`main.py`의 주석, ADR 0024). 그 규칙의 이름과 차례와 사례는 두 언어가 함께 읽는 픽스처(`tests/fixtures/site_file/`)가 원천이다. 떼어 내면 위젯이 다른 저장소의 운영자 파일 형식에 기대게 되므로, 위젯 배포 설정에 값을 따로 적거나 `serve`가 범용 공개 경로로 사이트 정보를 내주는 방식 가운데 하나로 바꾼다. 어느 쪽인지는 떼어 내는 ADR이 정한다.
- 루프백만 받는 호스트 목록을 `serve`(`main.py`의 `LOOPBACK_HOSTS`), 관리 화면(`tools/loopback.ts`), 위젯의 시작 래퍼(`tools/start.ts`)가 따로 들고, 바꾸면 셋을 함께 고친다(세 파일의 주석). 떼어 내면 위젯의 목록은 그 저장소가 혼자 가진다.
- 위젯이 쓰는 api-client와 디자인 시스템(`packages/api-client`, `packages/ui`)을 패키지로 배포한다. 떼어 내기로 정하기 전에는 하지 않는다.
- 위젯 e2e와 `-m llm_widget`은 지금 실제 `serve`를 띄워 돈다(`web/apps/widget/playwright.config.ts`의 머리 주석을 읽었다). 떼어 낸 뒤에는 판을 고정한 `serve` 이미지(release-image)에 대고 돈다.

## Considered Options

- **위젯 맞춤 설정을 관리 화면의 사이트 메뉴에 두고 `serve`가 공개 경로로 내준다.** 거부했다. 관리 화면과 `serve`가 위젯을 알게 되어, 떼어 낼 때 끊을 연결이 늘어난다.
- **위젯 전용 서버(저장소, 인증, 관리 화면)를 둔다.** 거부했다. 저장할 것이 사이트별 값 몇 개라서 서버를 하나 더 운영할 이유가 없다. 셀프 서비스 멀티테넌시가 필요해지면 다시 본다(PRD의 미룬 것).
- **위젯을 지금 별도 저장소로 뗀다.** 거부했다. 최종 사용자 채널의 계약이 넓고(시작, 결정, 구독, 이어 가기, 항목, 상한, 에러) 계획의 여러 행(run-handoff, delegation, approval-rules)이 그 계약을 바꿀 수 있다. 지금 떼면 채널을 고칠 때마다 저장소 두 곳을 함께 고친다.

## Consequences

- **두 자리의 설정.** 위젯 맞춤 설정 화면이 운영자의 관리 화면과 따로 있게 된다. 운영자는 채널 설정을 관리 화면에서, 위젯 외형을 사이트 쪽에서 바꾼다.
- **실행 중의 외형 변경.** 외형을 실행 중에 바꾸려면 위젯이 설정을 실행 중에 읽어야 한다. 허용 출처는 지금처럼 빌드 입력이므로, 바꾸면 위젯을 다시 빌드한다(ADR 0024).
- **PRD.** "최종 사용자" 줄과 "무엇을 만드나"의 채널 줄을 고쳤다(2026-11-06 사용자 승인).
- **pilot-portal.** 용어집에서 사이트는 Agent OS의 일부가 아니다. pilot-portal은 사이트이므로 위젯과 같은 규칙(의존은 페이지에서 Agent OS로)을 따르고, 이 저장소에 두는 동안에도 `serve`와 관리 화면은 그 페이지를 모른다.
- **ADR 0024.** 이력에 "떼어 낼 때 끊을 연결"을 가리키는 항목 하나를 적는다.
