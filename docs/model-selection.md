# 모델과 추론 레벨 선택 지표

세션과 서브에이전트의 모델과 추론 레벨(노력, effort)을 고를 때 쓰는 근거를 모은다. 공식 자료가 모델과 레벨마다 말하는 용도,
이 저장소에서 잰 것, 모델이 바뀔 때 다시 재는 절차의 셋이다. 어느 작업에 어느 모델을 쓰는지(작업과 모델의 짝)는 여기 두지
않는다. 짝의 원천은 `next-session` 결정표의 "모델" 칸이고, 그 결정과 칸을 바꾸는 규칙은 ADR 0029다. 이 문서는 그 칸을
바꾸려 할 때와 새 모델이 나왔을 때 읽는다.

근거는 문장마다 무엇으로 섰는지 적는다(`docs/agents/issue-tracker.md`의 프로브와 근거). "원문 대조"는 공식 문서의 마크다운
본문을 `curl`로 받아 수와 문장을 대 본 것이고 날짜를 붙인다. "쟀다"는 커밋한 프로브가 다시 내는 값이다. 웹 요약(WebFetch의
답 따위)은 근거로 쓰지 않는다.

## 1. 이 저장소에서 모델을 고르는 자리

| 자리 | 고르는 것 | 원천 |
|---|---|---|
| 지시문으로 여는 새 세션 | 모델과 레벨 | `next-session` 결정표의 "모델" 칸. 지시문의 "모델" 줄로 옮기고 `tools/open_session.ps1`이 보내기 전에 입력창에서 고른다(ADR 0029). 레벨 스윕 동안 칸이 `Opus 5.5 / xhigh`인 구현·하네스 브랜치는 `tools/model_sweep.py`가 내는 갈래다(ADR 0029 이력 2026-10-13) |
| 사람이 직접 여는 세션 | 모델과 레벨 | 새 세션 화면의 기본값. `open_session.ps1`은 지시문 세션을 연 뒤 그 기본값을 고르기 전의 값으로 되돌린다(ADR 0029) |
| 프로젝트 서브에이전트 | 모델 | `.claude/agents/*.md`의 `model` 머리. 없으면 세션의 모델을 물려받는다(Claude Code 문서 model-config) |
| `code-review`의 표준 축 서브에이전트 | 모델과 노력 | `.claude/skills/code-review/SKILL.md`. 변경 종류와 상관없이 언제나 `sonnet`·`high`다(ADR 0033). 명세 축은 둘 다 받지 않아 세션의 모델을 물려받는다(노력도 물려받는다는 것은 ADR 0033의 어림) |
| 카나리아 | 모델 | 카나리아 명세의 `model`(기본값은 `tools/canary.py`). 까닭은 `docs/constitution/operations.md` 환경 규약 상세 |
| PR 봇 claude-review | 모델 | `.github/workflows/claude-code-review.yml`의 `claude_args`. 지금은 `--model`이 없다(워크플로를 읽었다). 어느 모델로 도는지는 실행 로그로 보지 않았다 |
| 모델 판정 실험 | 판정자의 모델과 레벨 | `.scratch/harness/probes/session_cost/README.md`의 사전 등록. 이미 돌린 실험의 기록이라 모델이 바뀌어도 고치지 않는다 |

`sonnet`·`opus`·`haiku` 같은 별칭은 Anthropic API에서 그 계열의 최신 판으로 풀린다(Claude Code 문서 model-config). 그래서
서브에이전트처럼 별칭을 쓰는 자리는 새 판이 나오면 정의를 고치지 않아도 따라간다. 결정표의 칸은 모델 메뉴의 이름
(`Opus 5.5`)이라 따라가지 않는다. 메뉴에서 그 이름이 사라지면 스크립트가 보내기 전에 멈춘다(ADR 0029의 결과 절).

## 2. 공식 자료가 말하는 것

이 절은 원문 대조다(2026-10-13). 받은 주소는 절 끝에 있다. 영어 원문을 옮기지 않고 뜻을 줄여 적었다.

### 모델

| 모델 | 공식 문서가 적은 용도 | API 기본 레벨 | 단가: 입력 / 출력 / 캐시 읽기($/MTok) | 상대 지연 |
|---|---|---|---|---|
| Fable 5.1 | 어려운 추론과 긴 에이전트 작업. Opus 5.5를 높은 레벨로 돌려도 평가가 모자랄 때 | `high` | 10 / 50 / 0.25 | 느리다 |
| Opus 5.5 | 오래 도는 에이전트 코딩과 지식 작업. 대부분의 작업은 여기서 시작하라고 한다 | `medium` | 4 / 20 / 0.20 | 중간 |
| Sonnet 5.5 | 속도와 지능의 균형. 일상의 코딩, 에이전트, 데이터 분석 | `high` | 2 / 10 / 0.10 | 빠르다 |
| Haiku 5.5 | 양이 많고 지연에 민감한 분류, 추출, 라우팅, 서브에이전트 작업 | `medium` | 0.10 / 0.50 / 0.01(프롬프트 10만 토큰 이하), 0.50 / 2.50 / 0.05(초과) | 가장 빠르다 |

- 넷 모두 컨텍스트 1M 토큰, 출력 128K 토큰, 적응형 생각이다. Fable 5.1과 Opus 5.5는 생각을 끌 수 없다(models overview).
- Haiku 5.5는 프롬프트 길이로 단가가 갈린다. 캐시 읽기와 쓰기를 포함한 프롬프트가 10만 토큰을 넘는 요청은 모든 토큰을 높은
  단가로 낸다(pricing, optimizing-for-cost-and-intelligence). Claude Code는 Haiku 5.5를 1M 창으로 돌린다(model-config).
  그래서 긴 세션은 대부분의 요청이 높은 단가다(어림).
- Claude Code의 기본 레벨은 API와 다르다. Opus 5.5, Sonnet 5.5, Haiku 5.5가 `medium`이다(model-config). 그래서 Sonnet
  5.5는 API에서는 `high`로, Claude Code에서는 `medium`으로 시작한다.
- 은퇴는 넷 모두 2027년 9월 이후로 약속돼 있다. Fable 5.1은 2027-09-01, Opus 5.5는 2027-09-22, Sonnet 5.5는 2027-09-28,
  Haiku 5.5는 2027-10-07보다 이르지 않다(models overview).
- Fable은 요금제와 좌석 등급에 따라, 요금제에 포함된 한도 대신 사용 크레딧으로 청구될 수 있다. 그때 Claude Code가 동의를
  묻는다. Remote Control이 붙은 세션처럼 사람이 없을 수 있는 세션에서는 그 물음이 기한(기본 5분)까지 답을 받지 못하면 요청을 보내지
  않고 턴을 끝낸다(model-config). 지시문 세션을 Fable로 열면 첫 턴이 그렇게 멈출 수 있다(어림). 2026-10-31에
  `Fable 5.1 / xhigh`로 연 시험 세션 하나는 멈추지 않고 첫 턴에 답했다(ADR 0029 이력 2026-10-31, 손으로 봤다). 다만 사람이
  PC 앞에 있던 때(`idle=0s`)라, 사람이 없는 세션에서도 그렇다는 근거는 아니다.

### 레벨

| 레벨 | API 문서가 적은 용도(effort) | Claude Code 문서가 적은 용도(model-config) |
|---|---|---|
| `low` | 가장 효율적이고 능력을 조금 내준다. 서브에이전트처럼 단순한 작업 | 사람이 결과마다 보는 짧은 교환. 브레인스토밍, 첫 초안, 이름 바꾸기 |
| `medium` | 균형. 속도, 비용, 성능을 함께 맞춰야 하는 에이전트 작업 | Opus 5.5와 Sonnet 5.5에서 범위가 분명한 일상 엔지니어링. 새 기능 구현 |
| `high` | 과제가 필요로 하는 만큼 토큰을 쓴다. 복잡한 추론, 어려운 코딩 | 검증이 중요하거나 경계 사례가 많은 일. 기존 코드의 버그 고치기 |
| `xhigh` | 30분 넘게 도는 에이전트·코딩 작업, 수백만 토큰의 예산 | 더 많은 토큰으로 더 깊이 추론한다 |
| `max` | 토큰 제약 없는 가장 깊은 추론 | 사람 없이 끝까지 풀 어려운 문제. 보안 취약점 찾기. 수확이 줄고 지나치게 생각하기 쉬워 넓게 쓰기 전에 시험하라고 한다 |

- 레벨은 토큰 상한이 아니라 행동의 신호다. 낮은 레벨도 어려운 문제에서는 생각하지만 덜 생각한다(effort).
- 레벨은 도구를 쓰는 모양도 바꾼다. 낮으면 도구 호출을 합치거나 줄이고 설명 없이 바로 움직인다. 높으면 도구를 더 부르고,
  계획을 먼저 말하고, 바꾼 것을 길게 요약한다(effort).
- 레벨의 눈금은 모델마다 다르다. 같은 이름의 레벨이 모델마다 같은 값이 아니다(model-config). Sonnet 5.5는 Sonnet 5에서 눈금을
  다시 잡았다(effort).
- Opus 5.5와 Fable 5.1의 시험에서 높은 레벨은 경계 사례를 더 시험하고 답하기 전에 더 검증했으며 스스로 정하는 것도 많았다.
  낮은 레벨은 출발점을 빨리 돌려줘서, 사람이 결과마다 보고 다음 걸음을 이끄는 일에 맞는다(model-config).
- Sonnet 5.5는 `low`와 `medium`의 긴 에이전트 작업에서 끝내기 전에 멈추고 사용자에게 확인을 구하기 쉽고, `low`에서는 변경을
  검증하지 않고 끝났다고 할 수 있다. `xhigh`와 `max`에서는 끝난 뒤 스스로 검토를 더 돌리고 서브에이전트를 띄우기도
  한다(prompting-claude-sonnet-5-5). ADR 0029가 결정 때(2026-10-12) Sonnet 5.5 칸을 `high`로 둔 까닭이 앞의 것이다.
- 앱의 노력 메뉴는 낮음~최대 다섯 칸이 `low`~`max`이고 여섯째 칸은 레벨이 아닌 Ultracode다(ADR 0029). Ultracode는 큰 작업마다 동적
  워크플로를 짜는 Claude Code 설정이다. `/effort`나 설정으로 켜고 끄면 레벨은 그대로이고, `--effort ultracode` 플래그로 켜면
  레벨도 `xhigh`가 된다(model-config).
- 프롬프트에 `ultrathink`를 넣으면 그 턴에 더 깊이 생각하라는 지시가 더해질 뿐, API로 가는 레벨은 바뀌지 않는다(model-config).

### 모델마다 출발 레벨

API 문서의 레벨 표는 일반론이고, 모델마다의 권고가 그 표보다 앞선다(effort). 모델마다 권하는 출발점은 아래와 같다.

| 모델 | 출발 레벨 | 올리고 내리는 기준 |
|---|---|---|
| Fable 5.1 | `high`(기본) | 능력이 가장 중요한 에이전트·코딩 작업은 `xhigh`나 `max`로, 평가에서 품질이 버티는 일상 작업은 `medium`이나 `low`로(effort) |
| Opus 5.5 | `medium`(기본) | Opus 5에서 쓰던 값을 옮기지 말고 자기 평가로 레벨 몇 개를 잰다(effort). `xhigh`와 `max`는 품질 이득을 잰 작업에만 남긴다. 같은 레벨에서 Opus 5보다 턴마다 더 생각하고 특히 `xhigh`와 `max`에서 그렇다. 여러 코딩 평가에서는 `low`도 Opus 5의 `high`에 가까웠다(prompting-claude-opus-5-5) |
| Sonnet 5.5 | 명세가 분명한 에이전트 코딩과 여러 단계의 도구 사용은 `medium`. 어렵거나 긴 일은 `high` | 그 밖은 `high`(API 기본)에서 시작하고, 대화처럼 지연에 민감한 일은 `medium`이나 `low`로. `xhigh`와 `max`는 평가에서 품질 이득이 보일 때만(effort, prompting-claude-sonnet-5-5) |
| Haiku 5.5 | `medium`(기본). 에이전트 코딩도 | 대화, 짧은 도구 작업, 단순하고 많은 요청은 `low`. 다만 긴 에이전트 프롬프트에서는 `low`가 검색이나 확인을 건너뛰거나 일찍 멈추기 쉽다. 지식 작업, 긴 에이전트 작업, 엄격한 지시 따르기는 `high`. `xhigh`와 `max`는 품질 이득이 보일 때만 쓰고 Sonnet 5.5와 견준다(effort) |

### 작업 성격마다 공식 문서가 든 것

이 저장소의 짝이 아니라 공식 문서가 작업의 성격을 들어 적은 문장이다. 받은 원문에서 작업 성격을 든 곳만 모았다.

| 작업 성격 | 공식 문서가 든 모델·레벨 |
|---|---|
| 설계, 모호한 문제 | Fable은 근본 원인 조사, 장애 디버깅, 아키텍처 결정처럼 모호한 문제에서 더 조사하고 검증하는 값을 한다(model-config). Opus 5.5는 대규모 리팩터링과 복잡한 시스템 공학에서 시작하라고 한다(choosing-a-model) |
| 구현 | Opus 5.5는 실제 저장소에서 테스트가 통과할 때까지 변경을 끌고 가는 다단계 작업에 가장 강하고, `medium`에서 Opus 5의 `high`와 같거나 나았다(prompting-claude-opus-5-5). Claude Code는 범위가 분명한 새 기능 구현에 `medium`, 기존 코드의 버그 고치기처럼 검증이 중요한 일에 `high`를 든다(model-config) |
| 리뷰, 검증 | Opus 5.5는 Opus 5보다 버그를 더 잡고 잘못된 경보가 적었다는 초기 사용자의 보고가 있다(prompting-claude-opus-5-5). Claude Code는 보안 취약점 찾기처럼 사람 없이 끝까지 풀 문제에 `max`를 든다(model-config) |
| 화면, 그림 | Opus 5.5는 가장 낮은 레벨에서도 Opus 5의 가장 높은 레벨보다 빽빽한 차트의 값을 정확히 읽었다(prompting-claude-opus-5-5). Sonnet 5.5는 빽빽한 차트와 기술 도면에 자르기·확대 도구를 주면 정확해지고, 도면에서는 `high`부터 도움이 된다(prompting-claude-sonnet-5-5). 화면 디자인 작업 자체에 모델이나 레벨을 권한 문장은 받은 원문에 없다. 디자인 방향 없이 맡긴 프론트엔드 출력은 몇 가지 기본 모양으로 흐르고, 피할 모양을 이름으로 든 지시가 잘 듣는다고 한다(prompting-claude-opus-5-5) |
| 짧은 조작, 분류 | Haiku 5.5와 `low`(models overview, effort). Claude Code는 이름 바꾸기 같은 작은 변경과 사람이 결과마다 보는 교환에 `low`를 든다(model-config) |

### 공식 측정

공식 문서(optimizing-for-cost-and-intelligence)가 적은 Anthropic 내부 벤치마크다. 이 저장소에 그대로 옮기지 못하는 까닭은
아래 "옮길 때의 한계"다.

- SWE-bench Pro 부분집합(478문제, 2026-09-19~20에 돌렸고, 턴마다 출력 16,384 토큰 상한, `xhigh`는 한 번만 돌렸다)에서
  Opus 5.5를 `high`와 견주면 `medium`은 약 2.5점 낮고 비용은 약 70%, `low`는 약 8점 낮고 비용은 약 3분의 1, `xhigh`는 약
  1.4점 높고 비용은 2.5배였다.
- 같은 부분집합에서 Opus 5.5의 `medium`과 Fable 5.1의 기본(`high`)이 92.8%와 92.3%로 실행 사이의 잡음 안이었고, 푼 과제 하나의
  비용은 $0.22와 $1.19였다. Opus 5.5의 `low`는 87.4%에 $0.12였다.
- Opus 5.5로 모든 과제를 `low`로 먼저 돌리고 실패한 과제만 `high`로 다시 돌리면 약 97%를 과제당 약 $0.17에 풀었다. 전부
  `high`로 돌리면 95.3%에 $0.29였다. 실패를 알려 주는 검사가 있어야 하고, 실패한 과제는 두 번 도는 시간이 든다.
- 조사와 지식 작업의 벤치마크 넷(Fable 5)에서는 정확도와 비용의 곡선이 거의 평평했다. `low`가 1~3점을 내주고 과제당 비용을
  3분의 1에서 절반까지 덜었다.
- Haiku 5.5는 GPQA Diamond에서 Opus 5.5 비용의 약 20분의 1로 85%를 맞혔다. 같은 방식으로 돌린 Opus 5.5는 91%였다.
- 같은 문서의 권고 가운데 이 저장소의 스윕에 닿는 것을 옮긴다. 과제 설명만으로는 레벨을 올려 얻는 것이 있는 작업인지 알 수
  없으니 자기 작업의 표본으로 레벨 두세 개를 재 본다. 레벨마다 다른 세션에서 잰다(세션 도중에 레벨을 바꾸면 캐시가 깨져 비교가
  흐려진다). 지난번에 잰 모델이 아니라 실제로 쓸 모델로 잰다. 토큰 단가가 아니라 끝낸 과제 하나의 비용으로 견준다. 중앙값이
  아니라 가장 어려운 꼬리로 견준다. 두 번째 모델을 더하는 구성은 한 모델의 레벨별 곡선 전체를 이겨야 한다. 모델을 고르는 문서
  (choosing-a-model)는 모델을 바꾸기보다 레벨을 맞추는 것이 흔히 더 나은 손잡이라고 적었다.

### 옮길 때의 한계

이 절은 해석이다.

- 공식 측정의 과제는 이슈 하나이고 과제당 비용이 $0.1~1 남짓이다. 이 저장소의 브랜치는 TDD, 게이트, 셀프 리뷰, PR 반영까지
  가는 세션이고 문서 종류를 뺀 종류의 비용 중앙값이 $30~46이다(3절). 크기가 수십 배 달라 레벨마다의 점수 차와 비용 비를 그대로 옮기지 않는다.
- 공식 측정의 품질은 테스트 통과율이다. 이 저장소에서 그에 가까운 것은 재작업 점수와 사람 개입이고(3절) 둘 다 거칠다.
- 그래서 공식 측정에서는 "레벨이 첫 손잡이다"와 "레벨마다 따로 재라"는 방향만 빌린다. ADR 0029가 결정 때(2026-10-12) 둔
  칸은 대부분 `Opus 5.5 / xhigh`로, 공식 문서가 Opus 5.5의 출발점으로 권하는 `medium`보다 두 칸 높다. 그 칸을 둔 까닭은 그
  ADR의 "결정 때 둔 칸의 값"이고, 내릴지는 이 저장소의 스윕이 정한다. 구현 칸은 지난 티켓을 갈래마다 다시 푸는 측정(다시 풀기)으로도
  정한다(4절).

## 3. 이 저장소에서 잰 것

원천은 소급 측정 프로브의 README 결과 절(`.scratch/harness/probes/session_cost/README.md`, 2026-10-13 첫 실행)이다. 아래 수는
거기서 옮겼고, 커밋한 `branches.json`을 `analyze.py`가, 커밋한 `judge_results.jsonl`을 `judge.py score`가 다시 낸다(쟀다). 자료는 2026-09-19~10-12의 트랜스크립트이고, main에
병합된 브랜치 192개다. 비용은 응답의 토큰에 API 단가를 곱한 환산 값이다. 구독 요금제의 사용량 한도가 같은 비율로 움직이는지는
재지 않았다.

### 모델과 레벨이 대부분 하나였다

본 세션 비용이 가장 큰 모델·레벨은 192개 가운데 `claude-opus-5-5`·`xhigh` 135, `claude-fable-5-1`(`xhigh` 19, `high` 12),
`claude-opus-5`·`xhigh` 19, `claude-opus-4-7`·`xhigh` 7이다. 모델이 시기와 겹쳐 바뀌었으므로 기록만으로는 모델이나 레벨의
효과를 가를 수 없다. 이 저장소에서 모델이나 레벨만 바꿔 잰 결과는 아직 없다.

### 작업 종류별 기준선

본 세션 비용의 90% 이상이 `claude-opus-5-5`·`xhigh`인 브랜치 97개다. 종류는 브랜치 이름으로 가른다. `feature/`는 구현,
`chore/`와 `claude/`는 하네스, `fix/`는 수정이고, `docs/`는 이름에 따라 명세·티켓·디자인·문서로 나뉜다(정의는 프로브 README의
사전 등록). 수정은 하나뿐이라 σ를 셀 수 없어 표에서 뺐다.
n_k는 사전 등록의 식으로 이 표의 무리에서 셈한 스윕 한 갈래의 브랜치 수이고, 기하평균 비용 30% 감소를 가르는 수다. 첫
스윕은 지시문으로 열린 브랜치만 다루므로 그 무리로 셈한 구현 27, 하네스 25를 쓴다(ADR 0029 이력 2026-10-13).

| 종류 | n | 비용 중앙값 | 사분위 | σ(로그) | n_k | 턴 시간 중앙값 | PR 뒤 비용의 몫 |
|---|---|---|---|---|---|---|---|
| 하네스 | 42 | $36.1 | $23.4~45.8 | 0.75 | 55 | 90분 | 0.34 |
| 구현 | 22 | $45.5 | $28.0~55.2 | 0.52 | 27 | 105분 | 0.27 |
| 문서 | 14 | $2.4 | $1.4~3.9 | 0.92 | 83 | 3분 | 1.00 |
| 명세 | 7 | $42.3 | $31.6~51.7 | 0.45 | 20 | 120분 | 0.24 |
| 디자인 | 6 | $38.0 | $21.9~49.2 | 0.78 | 59 | 74분 | 0.20 |
| 티켓 | 5 | $30.2 | $22.2~43.3 | 0.44 | 20 | 50분 | 0.19 |

PR 뒤 비용은 그 브랜치에 귀속된 응답 가운데 PR이 열린 시각 뒤의 것이다(`collect.py`를 읽었다). 봇 리뷰 반영, 병합, 다음
지시문, 회고가 여기 든다. 문서 종류의 1.00은 까닭을 보지 않았다.

해석:

- 종류 안의 흩어짐이 커서(σ 0.44~0.92) 레벨을 바꿨을 때의 30% 차이를 가르려면 한 갈래에 20~83개가 든다. 지난 3주 반 동안
  병합된 구현 브랜치가 44개였으니 종류마다 몇 주가 걸린다(어림, 프로브 README).
- 문서 종류는 중앙값이 $2.4라 레벨을 내려도 덜 수 있는 금액이 작다.
- PR을 연 뒤의 비용이 구현의 약 3할, 하네스의 약 3~4할이다. ADR 0029가 결정 때(2026-10-12) Sonnet 5.5를 둔 칸은 PR
  반영·병합만 남은 끊긴 작업이고, PR을 연 세션은 반영과 병합까지 한다(`next-session` `merge.md`). 그래서 이 몫의 대부분은 PR을 연
  세션의 모델과 레벨로 돈다(어림). 다만 세션 컨텍스트가 20만 토큰을 넘어 PR을 연 뒤 인계하면 PR 뒤의 몫은 인계로 연 세션의
  모델로 돈다(스윕 브랜치는 그 갈래, 스윕 밖은 `Sonnet 5.5 / high`. `next-session` `handoff.md`의 인계 줄, ADR 0033). 이 몫만 낮은 모델로 돌리는 것은 레벨 스윕이 끝난 뒤의 후보다(ADR 0029 이력 2026-10-13).

### 열기 전에 알 수 있는 지표

feature 티켓 44개(merge-base 판본)에서 비용과의 Spearman ρ다.

| 지표 | ρ(비용) | 성격 |
|---|---|---|
| 글자 수 | 0.67 | 탐색 |
| 백틱으로 든 파일 경로 수 | 0.65 | 탐색 |
| 수용 기준 수 | 0.61 | 탐색 |
| 참조한 ADR 수 | 0.55 | 탐색 |
| 이름으로 든 층 수 | 0.49 | 탐색 |
| 열린 결정 수(정의는 사전 등록) | 0.48, 90% 구간 [0.25, 0.68] | 사전 등록한 가설 1. 섰다 |
| 계약 접촉 | 0.30 | 탐색. 사전 등록한 가설 2(접촉 쪽 비용 비 1.26, 90% 구간 [0.89, 1.78])는 서지 않았다 |

feature 밖의 브랜치 134개에서는 첫 사람 메시지의 글자 수 0.48, 읽을 것의 파일 수 0.40, 이어받을 상태의 글자 수 0.40, 이름으로 든
층 수 0.39였다.

모델 판정 실험에서는 Opus 5.5(`high`)에게 저장소를 읽히지 않고 `CLAUDE.md`, 실제 결과를 붙인 기준 티켓 열 개, 대상 티켓
하나만 보여 주고 턴 시간의 범위를 맞히게 했다. 실제 턴 시간과의 ρ가
0.416(90% 구간 [0.10, 0.66])이라, 가장 강한 단순 지표(백틱 경로 수 0.518)를 0.1 넘게 앞서야 한다는 사전 등록의 기준에 못 미쳐
쓸모 있다고 볼 수 없었다. 맥락을 가진 실제 세션이 못 맞힌다는 뜻은 아니다.

해석:

- 이 지표들은 티켓이 얼마나 비쌀지를 맞힌다. 비싼 티켓에 높은 레벨이 필요한지, 싼 티켓을 낮은 레벨로 돌려도 품질이 같은지는
  답하지 않는다. 그것은 레벨을 바꿔 연 결과로만 안다(스윕).
- 그래서 결정표는 티켓의 지표가 아니라 작업 종류로 칸을 나눈다. 세션을 열기 전에 모델이 티켓을 분류하게 하는 단계는 판정
  실험 결과로 보아 근거가 약하다.
- 스윕에서 두 갈래의 티켓 크기가 고르지 않으면 글자 수나 백틱 경로 수로 맞춰 볼 수 있다(어림).

### 측정의 한계

- 서브에이전트 응답의 약 7할이 최종 usage 없이 남아 출력 토큰이 빠진다. 그 비용은 낮게 잡히고 이 저장소 비용의 15%다.
- 웹 검색 요금은 비용에 들지 않는다.
- 턴 시간은 권한 확인을 기다린 시간과 턴 끝의 `system` 기록 꼬리를 담고, 나란히 돈 세션을 겹쳐 더한다.
- 사람 개입은 턴 도중에 사람이 친 메시지(`queued_human`)를 세지 않는다.
- 단가표(`costs.py`)는 Claude Code의 셈에 맞춰 두었다. `claude-sonnet-5-5`의 캐시 읽기만 공식 가격표와 다르다. Claude Code는
  입력의 0.1배로, 가격표는 0.05배로 셈한다(`cache_read_fit.py`로 쟀다. 그 프로브는 그때의 트랜스크립트를 읽어 기록이 쌓이면 쌍의
  수가 바뀌고, 다시 내는 것은 어느 배수가 맞는지의 판정이다). 지난 측정에는 거의 닿지 않는다. 그러나 본
  세션 전체를 Sonnet 5.5로 돌리는 스윕에서는 어느 단가를 쓰느냐로 그 갈래의 비용이 약 3할 갈릴 수 있다(어림, 프로브 README의
  "2026-10-13 캐시 읽기 단가 대조"). 스윕은 이 표로 판정하고, Sonnet 5.5가 갈래에 들면 공식 가격표로 셈한 판정을 함께
  적는다(ADR 0029 이력 2026-10-13).

## 4. 다시 재는 절차

### 계기

다음 가운데 하나가 생기면 이 절을 돈다. 자동으로 알리는 훅은 없고, 알아챈 세션이나 사람이 시작한다.

- 공식 모델 목록(models overview)에 새 모델이 오르거나, 결정표 칸의 모델에 은퇴가 다가온다.
- 앱의 모델 메뉴나 노력 메뉴가 바뀐다. `open_session.ps1`이 보내기 전에 멈추는 것으로 드러난다(ADR 0029의 결과 절).
- Claude Code가 레벨의 기본값이나 눈금을 바꾼다(model-config).
- 결정표의 칸을 바꾸자는 제안이 나온다(사용자, 회고, 스윕의 결과).
- 레벨 스윕의 기간이 끝났다. `tools/model_sweep.py`가 그날부터 stderr로 알린다.
- 다시 풀기의 판정이 나왔다(아래 "준비 중인 다시 풀기").
- 결정표 칸의 모델을 바꾼 지 14일이 지났다. 아래 순서의 8만 돈다.

### 순서

1. **원문을 받는다.** 2절 끝의 주소를 `curl -sSL`로 스크래치 폴더에 받고, 고칠 수와 문장을 `grep`으로 대 본다. 모델 목록은 이
   원문에서만 가져온다. 세션의 환경 정보와 claude-api 스킬의 모델 표는 쓰지 않는다. 2026-10-12에는 둘 다 Haiku 4.5를 최신으로
   적어 첫 보고가 틀렸다(일지 2026-10-12-37). WebFetch의 답은 웹 요약이라 근거가 아니다.
2. **2절을 고친다.** 바뀐 용도와 수를 고치고 원문 대조 날짜를 바꾼다.
3. **단가표를 맞춘다.** 새 모델의 단가를 `.scratch/harness/probes/session_cost/costs.py`와 사용량 보고서의 단가표
   (`tools/token_report.py`의 `PRICES`)에 함께 더한다. 두 표가 같은지 대 보는 시험은 없다. 그 모델로 돈 세션이 쌓이면
   `cache_read_fit.py`로 캐시 읽기 배수가 Claude Code의 셈과 맞는지 본다. 공식 가격표와 Claude Code의 셈이 다르면 둘 다 적는다
   (지금의 `claude-sonnet-5-5`처럼). 단가표에 없는 모델의 응답은 비용에서 빠지고, `analyze.py`의 "단가표에 없는 모델의 응답"
   표지로 드러난다. 프롬프트 길이로 단가가 갈리는 모델(지금은 Haiku 5.5)은 표가 10만 토큰 이하의 단가만 들어, 그 모델로 긴
   세션을 돌리면 비용이 낮게 잡힌다. 그 모델을 칸에 두려면 길이의 갈래를 먼저 두 표에 더한다.
4. **메뉴를 본다.** 새 모델의 메뉴 이름과 노력 칸을 `composer_menu_tree.ps1 -Effort`와 `composer_effort_labels.ps1`로 손으로
   보고(`.scratch/harness/probes/README.md`), 그 모델의 "모델" 줄로 시험 세션 하나를 열어 `get_session`이 모델과 레벨을 그대로
   보이는지 본다. ADR 0029가 같은 방법으로 시험 세션 여덟 개를 열었다. 그 모델이 Fable이면 이 시험 세션에서 사용 크레딧
   동의가 첫 턴을 멈추는지도 본다. 멈추면 결정표 칸에도 스윕의 갈래에도 두지 않는다(ADR 0029 이력 2026-10-13).
5. **소급 측정을 다시 돈다.** 새 모델로 돈 브랜치가 쌓였으면 `collect.py`와 `analyze.py`를 다시 돌리고(돌리는 법은 프로브 README),
   결과를 날짜와 함께 프로브 README 결과 절에 더한 뒤 3절을 고친다. 사전 등록 절은 고치지 않는다(고치는 법은 그 절의 머리).
6. **레벨은 스윕이 정한다. 구현 칸은 다시 풀기로도 정한다.** 같은 종류의 작업을 레벨만 바꿔 열고, 소급 측정 프로브 README
   사전 등록의 "스윕의 판정 기준"과 스윕 프로브 README(`.scratch/harness/probes/model_sweep/`)의 사전 등록으로 판정한다. 한
   갈래라도 n_k에 못 미치면 판정하지 않는다. 모델은 같은 계열의 새 판이면 공식 자료로 옮기고, 계열이 바뀌거나 단가가 오르면
   모델도 스윕으로 정한다. 그 조건과 옮긴 뒤 레벨을 재는 순서는 ADR 0029 이력 2026-10-13이다. 스윕에 들지 않는 설계
   인터뷰·명세 칸은 사용자의 결정으로 계열을 바꿨다(ADR 0029 이력 2026-10-31). 구현 칸은 모델과 레벨 모두 다시
   풀기의 판정으로도 바꾸고, 그때는 스윕 도중이어도 바꾼다(ADR 0029 이력 2026-10-20).
7. **칸을 바꾸면** ADR 0029의 이력에 근거와 함께 쌓고(`.claude/rules/adr.md`), `next-session` 결정표의 칸을 고친다.
   `tests/tools/test_open_session.py`의 결정표 테스트가 새 칸을 스크립트가 읽는지 본다. 1절의 자리 가운데 모델 이름을 별칭이 아니라
   판으로 적은 곳도 함께 고친다. 모델 판정 실험의 사전 등록은 기록이라 고치지 않는다(`analyze.py`의 해시 가드가 그 절을 고정한다).
8. **하네스를 다시 본다.** 칸의 모델을 바꾸고 14일이 지나면 저장소 루트에서
   `uv run python tools/hook_report.py --days <오늘에서 바꾼 날을 뺀 날 수>`를 돌린다. 창은 바꾼 다음 날부터 오늘까지(UTC 날짜)라,
   10-01에 바꾸고 10-15에 돌리면 `--days 14`이고 창은 10-02~10-15다. 바꾼 날을 넣으면 그날 앞 모델의 알림이 섞인다. 1분 남짓
   걸려 Bash의 `timeout`을 300000으로 준다(그 독스트링). 모델의 행동을 고치려고 더한 계기 훅
   가운데 그 창에서 알림이 0인 것은 새 모델이 그 실수를 하지 않는다는 표지라, 빼자고 사용자에게 넘긴다(retro 4단계의 넘김).
   막는 훅과 손상을 막는 훅은 0건이어도 남긴다. 알림이 남은 계기 훅은 새 모델도 같은 실수를 한다는 뜻이다. 모델이 바뀌어도
   하네스는 더해지기만 하고 빠지지 않았다(ADR 0036).

### 지금 도는 스윕

첫 스윕은 구현과 하네스에서 지시문으로 연 브랜치를 이름으로 갈라 `Opus 5.5 / xhigh`와 `Opus 5.5 / medium`을 견준다. 이
절에 있던 미정 항목(새 모델의 근거, σ_k의 무리, 사람 개입의 턴 도중 메시지, Sonnet 5.5의 단가)과 함께 ADR 0029 이력
2026-10-13이 정했고, 판정에 쓰는 정의는 스윕 프로브 README의 사전 등록이다. 판정 명령은 그 프로브의
`sweep.py judge`이고, 기간이 끝난 7일 뒤에 한 번 친다.

### 준비 중인 다시 풀기

병합된 구현 티켓을 그 병합 직전의 코드에서 갈래(Opus 5.5의 xhigh·high·medium, Sonnet 5.5의 high·medium)마다 headless 세션에
다시 풀게 하고, 숨은 시험·게이트·비용으로 견준다. 설계는 `.scratch/model-rerun/design.md`이고, 결과로 칸과 서브에이전트의
`model`을 바꾸는 절차는 ADR 0029 이력 2026-10-20이다. 아직 돌리지 않았다. 판정이 구현 칸을 바꾸면 그날 `tools/model_sweep.py`의
`SWEPT`에서 구현을 빼고, 스윕은 하네스만 판정한다.
