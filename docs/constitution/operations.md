# Agent OS 헌법 · 검증과 운영

커밋, 병합, 트래커, LLM 테스트, 가드레일을 만질 때 읽는다. 검증 명령은 `CLAUDE.md`에 있고 실제로 돌려 통과한 명령만 적는다.

## LLM 테스트
LLM을 실제로 호출하는 테스트는 `llm` 마커를 붙인다. 기본 `pytest -q`는 이 마커를 제외한다. `uv run --env-file .env pytest -m llm`이 돌리며, `.env`의 `ANTHROPIC_API_KEY`가 없으면 skip이 아니라 실패한다. `.env`는 커밋하지 않는다. 그래서 워크트리에는 없고 `--env-file`은 작업 폴더 기준으로 풀려 uv가 테스트 전에 종료 코드 2로 멈춘다(2026-10-05 워크트리 감사 서브에이전트가 손으로 봤다). `.claude/worktrees/<이름>/`에서는 `--env-file ../../../.env`로 주 체크아웃의 것을 읽고 사본을 만들지 않는다(버리는 변이 워크트리는 `tools/mutate.py`의 절차). 원칙 I의 판정은 이 명령이다. CI가 생겨도 매 푸시에서는 돌리지 않는다. 손으로 돌리는 계기는 LLM 테스트 파일을 건드렸을 때가 아니라 그 테스트가 지나는 코드(`core/run.py`·`core/loop.py`, 어댑터, `channel/`, `main.py`)를 건드렸을 때다 — PR #46이 테스트를 한 줄도 안 고치고 그 아래 배관을 전부 바꿨다(대기열 1). 돌렸으면 일지 검사 절에 통과 수와 트레이스의 토큰 합계를 적는다.

## 가드레일
자동 검사는 둘이고 내용은 같다 — 인용 대조는 경고만이라 pre-commit에만 있고, 커밋 메시지 검사는 커밋에 걸리는 것이라 pre-commit의 commit-msg 훅에만 있고, 변이 표의 원문 확인(`tools/mutate.py --check`, 대기열 92)은 커밋에 든 표만 보는 것이라 pre-commit에만 있고, e2e는 CI에만 있다. 로컬 pre-commit 훅이 커밋마다, GitHub Actions CI(`.github/workflows/ci.yml`)가 푸시와 PR마다 ruff, ruff-format, pyright, import-linter, pytest(기본 마커), 지침 검사, 타입 우회 검사, 그리고 web의 `pnpm -C web verify`를 돈다. web의 것은 생성물 최신성(`web/tools/generate-api-client.ts --check` — 루트 `openapi.json`에서 다시 생성한 결과가 커밋된 생성 클라이언트 타입과 같은가), ESLint(typescript-eslint와 eslint-plugin-boundaries — 원칙 III의 TS 판정자와 층 경계, 경고 0), Prettier, tsc(루트와 워크스페이스 패키지마다), Vitest, tsconfig 검사(`web/tools/check-tsconfig.ts`)다(ADR 0020·0021). Vitest는 프로젝트 셋이다. node 환경, 관리 화면 페이지의 jsdom, 그리고 디자인 시스템의 스토리 테스트를 실제 chromium에서 도는 `storybook`이다(ADR 0026). CI에서는 파이썬 쪽 검사를 `python` 잡이, `pnpm -C web verify`를 `web` 잡이 돌고(그 전에 chromium을 깐다), 같은 때 `e2e` 잡이 e2e(`pnpm -C web/apps/admin exec playwright test` — 실제 `serve`와 시작 래퍼로 띄운 관리 화면을 지나는 Playwright)를 돈다. 브라우저는 그 잡에서 설치하고, 없으면 e2e는 건너뛰지 않고 실패한다. pre-commit에는 없다. 필수 검사 `verify`는 세 잡을 기다려 결과를 모으는 잡이고 셋이 모두 성공일 때만 초록이다. 건너뛴 잡은 필수 검사여도 성공으로 보고되므로 건너뜀과 취소도 빨강으로 본다. 잡을 더하면 `verify`의 `needs`에 넣는다. 빠뜨리면 `verify`가 같은 실행의 잡 목록을 API로 읽어 빨강으로 본다(잡 구조는 ADR 0021의 첫째, 이 판정은 둘째 2026-10-01 이력). 마크다운 표 검사(`tools/check_md_tables.py`, 대기열 44)와 줄 구분 문자 검사(`tools/check_line_separators.py`, 대기열 22)는 pre-commit이 스테이지된 파일에 돌리고, CI에서는 pytest의 저장소 상태 테스트(`test_이_저장소의_…`)가 저장소 전체에 돌린다. 훅 페이로드 실행(`tools/run_hooks.py`, 대기열 24)은 pre-commit에 먼저 들어갔고 CI는 web-admin 티켓 05의 워크플로 PR에서 뒤따랐다. 원칙 III의 판정자는 언어마다 하나다. 파이썬은 타입 우회 검사다 — pyright strict가 `Any`·`cast`·억제 주석을 하나도 잡지 않아서 `tools/check_type_escapes.py`가 대신 판정한다. TypeScript는 typescript-eslint다(`web/eslint.config.mjs`, 변이 테스트는 `web/eslint.config.test.ts`). 훅은 각자 설치해야 하므로 CI가 최종 판정이다. main은 보호 브랜치다. 필수 검사 `verify`, 최신 main 기준(strict), 선형 이력, 강제 푸시와 삭제 금지, 관리자 우회 허용(혼자일 때). 관리자 토큰으로 도는 에이전트도 같은 우회를 갖고(`gh pr merge --admin`, main 직접 푸시), 로컬 훅은 커밋만 막는다(ADR 0005의 2026-09-29 이력). 경위는 ADR 0005. 병합은 여전히 `/git-pr-merge`로 한다. 스킬이 체크를 먼저 보기 때문이다. 워크트리에서는 그 스킬이 main을 가로채거나 실패해, 같은 체크를 본 뒤 `next-session`의 "워크트리에서 병합할 때"로 한다(ADR 0005의 2026-10-06 이력). 클론 뒤 주 체크아웃에서 `uv run pre-commit install`을 한 번 하면 pre-commit과 commit-msg 두 훅이 깔린다. git 훅은 워크트리와 공유되고, 워크트리에서 치면 공유 훅이 박아 둔 파이썬 경로가 그 워크트리의 것으로 덮인다(2026-10-05 워크트리 감사 서브에이전트가 pre-commit 4.6.2의 `install_uninstall.py`를 읽었다). `uv sync`와 `pnpm -C web install --frozen-lockfile`은 체크아웃마다, 워크트리를 팔 때마다 한다. 없으면 web verify 훅이 첫 커밋부터 빨갛고, `uv run --no-sync`는 빈 `.venv`를 만들어 조용히 돈다. 스토리 테스트의 chromium은 체크아웃마다가 아니라 기계마다 Playwright 판마다 Playwright의 브라우저 캐시(Windows는 `%LOCALAPPDATA%\ms-playwright`)에 깔린다. 그래서 처음과 Playwright 판이 바뀔 때 `pnpm -C web exec playwright install --only-shell chromium`을 친다. 없으면 스토리 테스트는 건너뛰지 않고 실패한다(일지 2026-10-07-01). 훅이 안 걸린 저장소는 그 자체가 결함이다. 훅 시스템은 pre-commit 하나만 둔다. 둘이면 `.git/hooks/pre-commit` 한 자리를 다퉈 한쪽이 조용히 안 걸린다. 파이썬 파일이 안 바뀐 커밋에서도 pyright·import-linter·pytest는 돌고, web 파일이 안 바뀐 커밋에서도 web verify는 돈다(`always_run`). 이유는 둘이다. 파이썬 파일만 바꿔도 돌아야 하는 것은 pyright·pytest와 같고, 파이썬 티켓이 `openapi.json`을 바꾸면 생성물 최신성이 빨개져 다시 생성한 타입이 같은 커밋에 담긴다. CI에 경로 필터를 걸게 되면 미매칭은 skip이 아니라 실패로 만든다. 원칙 IV 중 "플러그인은 sdk만 import한다"는 import-linter가 아니라 `tests/test_plugins_boundary.py`가 판정한다 — 플러그인은 `root_packages` 밖이다(ADR 0018). 원칙 II의 "skip된 테스트는 초록이 아니다"는 `tests/conftest.py`가 판정한다. 바뀐 마크다운의 20자 이상 따옴표 인용을 저장소와 대조하는 `tools/check_quotes.py`(대기열 42)는 경고만 내므로 pre-commit에만 있고 CI에는 없다.

에이전트 자신의 도구 출력에 비밀이 실리는 것은 게이트가 보지 않는다. `.claude/settings.json`의 `permissions.deny`가 모든 위치의 `.env`에 Read·Edit와 PowerShell 읽기 모양을 막고(`.scratch/harness/probes/env_deny_probe.md`), `tools/hook_env_read.py`가 Bash로 읽는 길(`cat .env`, `< .env`, `.env`를 빼지 않은 저장소 전체 grep)과 `.env`를 경로로 준 Grep을 막는다(대기열 43 — 2026-09-28 감사에서 서브에이전트의 grep 한 번에 키 값이 도구 출력에 실렸다). 못 보는 것은 그 훅의 독스트링. 두 장치 모두 호출의 모양을 보는 에이전트 층이다(공식 permissions 문서: 권한 규칙은 보안 경계가 아니다). 에이전트 밖의 층은 키 자체다 — `.env`에는 사용 한도를 건 개발용 키만 두고, 2026-09-28에 도구 출력에 실린 키는 회전했다(사용자 확인 2026-09-29). Claude Code 훅의 원천은 그 설정 파일이고 훅마다 이유는 `tools/hook_*.py` 독스트링에 있다.

## 브랜치와 병합
- 원격은 GitHub(`njh6803/agent-os`, 공개). main은 보호 브랜치다(가드레일 절). 티켓마다 `feature/<NN>-<slug>` 브랜치를 따고 혼자여도 PR을 연다. 티켓 밖의 하네스·설정 변경은 `chore/<slug>`, 티켓 밖의 제품 코드 수정은 `fix/<slug>`(대기열 23), 문서만 바꾸면 `docs/<slug>`. main 위의 커밋은 `tools/hook_git_main_commit.py`가 막는다. 브랜치 이름은 그 작업을 하는 세션의 제목이기도 하다(`open-session`). `/git-pr`이 `.github/PULL_REQUEST_TEMPLATE.md`를 채운다.
- 병렬 브랜치는 PR 전에 main에 rebase한다. 병합은 squash이고 main 이력은 PR 단위다. 주 체크아웃에서는 `/git-pr-merge`로, 워크트리에서는 `next-session`의 "워크트리에서 병합할 때"로 한다. PR 제목이 곧 main의 커밋 제목이므로 컨벤셔널 커밋 형식이다. 리뷰는 아래 리뷰 파이프라인.
- 병렬 작업은 프론티어(막힌 것이 없는 티켓)에서만 하고, 티켓마다 워크트리 하나다. 일지는 `docs/journal/<날짜>-<NN>-<슬러그>.md`이고 `NN`은 그날의 순번이다. 같은 날 세션 둘이 쓰면 순번이 갈라 주고, "최신 파일"은 이름 정렬로 정한다.
- 커밋 메시지는 컨벤셔널 커밋, 한국어. 형식(`<타입>: <제목>`, 72자, 마침표 없음)은 commit-msg 훅이 판정하고, 본문의 "왜 그렇게 했는지와 남긴 위험"은 리뷰가 본다.
- PR을 연 세션이 반영과 병합까지 한다(`/git-pr-feedback`, 병합은 주 체크아웃이면 `/git-pr-merge`, 워크트리면 `next-session`의 "워크트리에서 병합할 때"). PR 생성이나 병합은 세션을 끝내는 사건이 아니라 `next-session` 스킬의 계기이고, 계기는 훅(`tools/hook_pr_next_session.py`)이 넣는다. 지시문은 병합 뒤에 실행된다. 세션을 끝내는 것은 지시문의 "어디서"가 새 세션일 때뿐이며, 그때 `open-session` 스킬이 같은 체크아웃에 연다(딥링크. 폴더를 싣지 못한다). 막힌 것이 없는 티켓이 둘 이상이면 `next-session`이 티켓마다 지시문을 내고 `open-session`이 그 세션을 차례로 전부 열며, 그 세션들은 지시문대로 각자 워크트리를 파서 일한다(위 "티켓마다 워크트리 하나"). "이 세션"이면 이어간다. 어느 쪽인지는 결정표(스킬)가 정하고, 사용자가 이어서 지시하면 따른다.

## 리뷰 파이프라인
세 축이다. 표준·명세, 보안·버그·성능, 유지보수성·경계. 축 이름은 이 줄이 원천이다. 판단 기준과 심각도의 원천은 `CODING_STANDARDS.md`이고 여기는 누가 언제 무엇을 보는지만 적는다.

1. **커밋 전 셀프 리뷰.** `/code-review`가 표준 축(`CODING_STANDARDS.md`)과 명세 축(`.scratch/<slug>/spec.md`)을 본다. 범위는 merge-base 이후 커밋과 미커밋 작업 전부이고, 문서만 바뀐 변경도 면제하지 않는다. Critical·Major는 커밋 전에 고친다. 건너뛰지 않는다. Minor·Nit은 별도 티켓으로 뺄 수 있다. 보고를 받은 뒤 그대로 구현하지 않고 근거를 먼저 확인하는 것은 이 축도 2단계와 같다. 아래 초록 착시의 반대편이다. 범위를 잡는 법과 반영 절차는 스킬 1·6단계.
2. **PR 직전 CodeRabbit CLI.** `coderabbit-review` 서브에이전트(`.claude/agents/`)가 보안·버그·성능 축을 PR 전에 한 번 본다. 트리아지(유효·오탐·보류)만 하고 수정은 본 세션이 한다. CLI 상한은 개발자당 시간당 3회이고 롤링 윈도다(공식 요금제 문서의 rate limits 표, 2026-09-21 확인). 공개 저장소라 OSS 플랜이지만 CLI 상한은 무료 플랜과 같다. "PR마다 한 번, `sdk`·`core`·`adapters`가 우선"은 한도가 아니라 우리 선택이다. 시간당 3회면 커밋마다도 돌 수 있으므로 바꾸려면 ADR을 남긴다. `coderabbit --usage`는 청구 주기 누적과 초기화 날짜만 보여주고 시간당 잔량은 보여주지 않는다.
   - **CLI가 연결 단계에서 즉시 끝나는 것은 한도가 아니라 좌석 미배정이다.** 증상은 `You are not a member of the requested organization`이고 확인은 `coderabbit auth status`의 `Seat: not assigned`다(2026-09-23 실측). **좌석 배정에는 유료 구독이 필요하다** — 공식 문서 `management/seat-assignment`가 요청의 전제를 "active paid subscription"으로 적고 체험 종료 후에는 불가하다고 명시한다. 배정 화면은 조직 설정의 Team Management이고 구독 상태는 Subscription and Billing이지만, `Plan: Free`에서는 거기 배정할 좌석이 없다. 2026-09-22까지는 CLI가 실제로 돌았으므로(일지 `2026-09-22-10`, finding 3건) 체험 종료로 끊긴 것으로 본다. **유료 전환 전까지 PR 직전 CLI 축은 구조적으로 비어 있고** 보안·버그 축은 PR 봇 하나다 — 그것도 OSS 시간당 한도에 걸리므로, 축이 비는 것을 PR 체크리스트에 그대로 적는다.
3. **PR 리뷰.** 봇 둘이 역할을 나눈다. CodeRabbit(`.coderabbit.yaml`)이 보안·버그·성능, Claude Code Review(`.github/workflows/claude-code-review.yml`)가 유지보수성(리뷰 관점 넷)과 경계(import-linter가 못 보는 원칙 IV 위반, `sdk` 계약 변경의 동반 수정). CI가 자동 검사. 별이 10개 미만인 공개 저장소는 CodeRabbit이 자동으로 돌지 않으므로(PR #12 실측), PR을 연 직후 에이전트가 `gh pr comment <번호> --body "@coderabbitai review"`로 요청한다. OSS 플랜의 PR 리뷰 상한은 저장소 별 수에 따라 시간당 1~10회이고 우리는 별이 적어 하한 쪽이다. CodeRabbit 체크는 한도를 넘거나 요청이 없어도 `pass`가 되므로 필수 검사(가드레일 절)에 넣지 않고 코멘트가 있는지로 판정한다. 셋이 초록이고 코멘트를 반영한 뒤 `/git-pr-merge`. 이력은 ADR 0006.
4. **반영.** `/git-pr-feedback`이 CI 결과와 코멘트를 읽어 반영한다. 보류한 지적은 별도 티켓.

봇의 초록은 리뷰했다는 뜻이 아니다(선행 저장소 실측).
- CodeRabbit(PR)은 비공개+무료에서 작성자에게 시트가 없으면 변경 요약(Walkthrough)만 남기고 `pass`가 되고, 시간당 한도를 넘으면 "Review rate limited"로도 `pass`다(PR #2 실측 둘). 공개 저장소에서는 전체 리뷰가 무료라 켰다. 한도 초과의 `pass`는 남으므로 코멘트가 있는지 본다.
- Claude Code Review는 **자기 워크플로 파일**(`claude-code-review.yml`)을 바꾼 PR에서 건너뛰면서 `pass`가 된다. 액션이 그 파일을 기본 브랜치의 것과 비교해 다르면 실행하지 않는다(PR #3·#6 실측, 로그 경고 "Skipping action due to workflow validation"). 그 파일의 변경은 별도 PR로 먼저 병합한다. 다른 워크플로 파일(`ci.yml`)만 바꾼 PR은 건너뛰지 않는다.
- Claude Code Review는 플러그인을 쓰던 동안 코멘트 없이 `pass`가 되곤 했다(PR #2·#4·#5). 플러그인이 서브에이전트를 백그라운드로 띄우고 턴을 끝내는데 헤드리스 실행이 그 전에 종료됐다. 그래서 워크플로를 직접 프롬프트(단일 에이전트, 요약 코멘트 하나가 완료 조건)로 바꾸고, 실행 시작 뒤 생긴 `claude[bot]` 코멘트가 0개면 잡을 실패시키는 스텝을 둔다(2026-09-20 회고 후보 1, PR #10). 그 워크플로부터는 코멘트가 없는 초록이 나오지 않아야 하고, 나오면 `uv run python tools/gh_run_summary.py <run-id>`로 결과 블록·경고·Claude의 말을 본다.
- Claude Code Review는 PR 헤드의 `.claude/`, `CLAUDE.md`, `.mcp.json`을 쓰지 않고 main의 것으로 되돌린다. 하네스를 바꾼 PR은 병합된 뒤에야 리뷰에 반영된다.
- 병합 전에 코멘트가 실제로 있는지 본다. 코멘트 0개인 초록은 "리뷰 없음"으로 읽고 이유를 확인한다.
- **`gh pr checks`의 초록이 현재 HEAD의 것이 아닐 수 있다.** 푸시 직후 GitHub가 PR head를 갱신하기 전에 조회하면 이전 커밋의 결과가 그대로 보인다(PR #44 실측. 새 커밋에 대한 워크플로 실행이 하나도 없는데 세 축이 전부 `pass`였다). 위아래의 다른 항목들이 "리뷰가 돌지 않았는데 pass"인 것과 달리 이것은 **다른 커밋의 pass를 현재 것으로 읽는 것**이라, 코멘트가 있는지로는 잡히지 않는다 — 그 코멘트도 이전 커밋의 것이다. 판정은 `gh run list --branch <브랜치> --json headSha`로 **어느 커밋이 검사됐는지** 보는 것이고, 병합 직전에 `gh pr view --json headRefOid`와 `git rev-parse HEAD`가 같은지 먼저 본다. 동기화는 몇십 초 걸릴 수 있다. **같은 지연이 리뷰를 부르는 쪽에도 있다.** 푸시 직후 `gh pr ready`를 치면 claude-review가 그 순간의 옛 head를 리뷰하고, `@coderabbitai review`는 "Head commit changed"로 버려진다(PR #117 — claude-review가 이미 되돌린 실험 커밋의 `exit 1`을 Critical로 냈다, 대기열 86). 둘 다 `tools/hook_pr_head_sync.py`가 PR head가 로컬 HEAD에 못 미치면 막는다(PR 쪽이 앞섰거나, 다른 브랜치의 PR이거나, PR head가 로컬에 없으면 지나간다). 막히면 `gh pr view --json headRefOid`가 로컬 HEAD와 같아진 뒤 다시 친다.
- CodeRabbit이 초록으로 지나가는 사유가 하나 더 있다. **별이 10개 미만인 저장소는 자동 리뷰를 받지 않는다**(PR #43 실측, "This repository does not receive automatic reviews because it has fewer than 10 stars"). 공개라서 무료인 것과 자동으로 도는 것은 다르다. 수동으로 `@coderabbitai review`를 남겨야 하고, **그 코멘트 뒤에 푸시하면 "Pull request base or head changed"로 아무것도 하지 않는다**(같은 PR 실측). 요청은 마지막 푸시 뒤에 남긴다.
- PR #43이 "반례"로 적혀 있던 것은 조건을 잘못 읽은 것이었다. #43은 `ci.yml`만 바꿨고 건너뛴 #3·#6은 둘 다 `claude-code-review.yml` 자체를 바꿨다(2026-09-28 `git show --stat`으로 확인). 조건은 위 항목대로 "자기 워크플로 파일이 다른가"이고 반례가 아니다. 판정은 언제나 "코멘트가 실제로 있는가"다.
- CodeRabbit PR 리뷰는 OSS 시간당 한도에 자주 걸린다(첫 슬라이스 PR 일곱 중 다섯이 "Review rate limited"로 `pass`). 그 PR의 보안·버그 축은 PR 직전 CLI 슬라이스 리뷰 결과를 그 PR 코멘트로 링크한 것이 대체이고, 링크가 없으면 리뷰 없음이다.

전제 둘은 사람이 한 번 한다. `claude setup-token`으로 만든 토큰을 저장소 시크릿 `CLAUDE_CODE_OAUTH_TOKEN`에 등록, 로컬 `coderabbit auth login`. 에이전트는 토큰과 시크릿을 다루지 않는다. 등록 여부만 `gh secret list`로 본다. 이름과 시각만 나온다.

## 문서 위치
문서는 범위가 있는 곳에 둔다. 저장소 전체에 해당하면 루트 `docs/`, 한 앱에만 해당하면 그 앱 안(README). 한 앱에만 걸리는 지침은 중첩 `CLAUDE.md`가 아니라 그 경로를 `paths`로 든 `.claude/rules/*.md`에 둔다. 규약을 한곳에 모으는 쪽이고(ADR 0004), 중첩 `CLAUDE.md`는 그 안의 `@` 임포트까지 따라와 루트 지침에 거는 검사(줄 수, 임포트 허용 목록) 밖에 놓인다(ADR 0021). `tools/check_instructions.py`가 빨강으로 본다. 같은 사실을 두 곳에 두지 않고, 지역 문서는 루트를 요약하지 않고 가리키며, 루트가 지역 문서를 색인한다. 헌법, 용어집, ADR 번호열은 하나다. 지역 결정도 루트 ADR 열에 넣고 제목에 범위를 적는다.

잔존 grep(`CLAUDE.md` 작업 규약 4)은 살아 있는 문서만 본다. 기록은 당시의 사실이라 옛 말이 남아도 잔존이 아니다. 기록은 일지(`docs/journal/`), `plan.md`의 상태가 done인 기능의 `.scratch/<slug>/` 명세·티켓·프로브, ADR의 지난 이력 항목, 대기열의 닫힌 행, 그리고 살아 있는 문서 안의 이력(헌법 README의 버전 이력, 프로브 README의 지난 결과)이다. 살아 있는 문서는 `plan.md`, 진행 중인 기능의 명세·티켓, 대기열의 열린 행, ADR의 본문, 헌법, `CLAUDE.md`, rules, 스킬, 독스트링과 주석이다. PR #117에서 셀프 리뷰는 `plan.md`를 잔존으로 짚어 맞았고, claude-review는 done인 web-admin의 명세·티켓을 잔존으로 짚었다. 이 가름이 없어 둘의 기준이 갈렸다(대기열 87).

## 환경 규약 상세
명령을 치기 전에 알아야 하는 것은 `CLAUDE.md` 환경 함정에 있다. 그 밖에 선행 저장소가 겪은 것과 가끔 쓰는 것.
- ruff E501은 표시 폭 기준이라 한글 한 글자가 2로 세어진다.
- `PYTHONUTF8=1`은 `.claude/settings.json`의 `env`가 넣는다(대기열 40). 설정 `env`의 값이 Bash 도구의 명령에 보이는 것을 사용자 설정의 다른 값으로 실측했다(2026-09-28). 훅 프로세스 쪽은 재지 못했고 훅은 어차피 stdin을 바이트로 읽는다. 사용자 터미널에서 도는 pre-commit은 이 밖이라 conftest가 stdout을 UTF-8로 고정한다.
- 환경이 없어 skip된 테스트는 초록이 아니다. `tests/conftest.py`가 skip이 하나라도 있으면 세션을 실패로 끝낸다(2026-09-28). `-m`의 deselect는 skip이 아니다.
- `alembic.ini` 같은 ini 계열은 환경변수로 인코딩을 못 바꾼다. ASCII만.
- pyright 프로브는 `tests/` 아래에 둔다. 점 디렉터리와 `include` 밖은 검사 없이 "0 errors"다. 분석 여부는 `--outputjson`의 `summary.filesAnalyzed`로 본다. `--pythonpath`는 `[tool.pyright]`의 `venvPath`·`venv`에 덮여 무시되니 임시 환경은 `--venvpath`로 넘긴다.
- **바꾼 rules와 스킬은 새 `claude -p` 세션에서 불러 본다(작업 규약 3의 하네스 확인, 대기열 63).** 바꾼 세션은 증거가 되지 못한다. 그 세션은 바꾼 본문을 이미 알고, 새로 만든 규칙은 그것을 만든 세션에서 `paths`에 맞는 파일을 Read로 열어도 실리지 않았고, `EnterWorktree`로 옮겨 온 세션은 주 체크아웃의 스킬을 실었다(둘 다 손으로 봤다, 일지 2026-09-30-01·2026-10-01-03). **`tools/canary.py`가 명령을 짓고 회차를 돌려 판정한다(대기열 129).** 명세 TOML 하나(질문, 카나리아, 실험군·대조군 갈래)를 받아 `uv run python tools/canary.py <명세> <출력 디렉터리>` 한 번으로 모든 회차를 돌고, 회차마다 stream-json 원본을 남긴다. 명세의 모양과 판정의 원천은 그 도구의 독스트링이다. 근거로 드는 명세는 프로브 자리에 커밋한다(예: `.scratch/harness/probes/canary/`). 워크트리 세션의 가드(`CLAUDE.md` 환경 함정)가 회차를 묶은 반복문을 거부해(대기열 120), 셸에는 이 단순 명령 하나만 친다. 러너가 짓는 명령은 `claude -p --setting-sources project,local --strict-mcp-config --model sonnet --output-format stream-json --verbose`에 도구를 좁힌 것이고, 질문은 stdin으로 간다. 스킬은 `--tools Skill`, 규칙은 `--tools Read`다. 규칙 명령에 `.claude/` 읽기 거부(`--disallowed-tools 'Read(./.claude/**)'`)를 더하면 claude 2.1.291에서 `paths` 규칙의 로드까지 막혀, 실험군과 대조군이 모두 "없음"이었다(손으로 봤다, 일지 2026-10-06-15·2026-10-07-01, 대기열 127). 2.1.286에서는 같은 명령으로 규칙이 실렸으니(일지 2026-10-06-06) 판이 바뀌며 생긴 회귀로 보인다. 판의 변경 기록은 읽지 않았다. 그래서 거부를 두지 않고, 트랜스크립트의 Read 호출이 대상 파일 하나뿐인지를 본다. `--tools`는 가변 인자라 뒤에 둔 질문까지 도구 이름으로 삼킨다(아래 프로브의 첫 판에서 질문이 사라져 `Input must be provided` 오류가 났다). `--allowed-tools Skill`로 띄운 세션에서도 Read가 승인 없이 돌아 바뀐 스킬 파일을 직접 읽었고, 그러면 답이 스킬이 실려서 나온 것인지 가를 수 없다. `--tools Skill`로 좁힌 세션에는 Read가 없었다(손으로 봤다, 일지 2026-10-01-05). init 이벤트에서 `tools`가 그 하나뿐이고 `mcp_servers`가 비었는지도 러너가 본다. `--tools`는 내장 도구만 좁히고, 로그인한 계정의 claude.ai 커넥터는 `--strict-mcp-config`가 뺀다. claude 2.1.286에서 `--tools Skill` 세션의 init에 커넥터 셋(Atlassian, Docs, Slack)과 그 도구 76개가 실렸고, 이 플래그를 더하자 `tools`가 `Skill` 하나, `mcp_servers`가 0이었으며 스킬 목록(36개, `code-review` 포함)은 그대로였다. 환경 변수 `ENABLE_CLAUDEAI_MCP_SERVERS=false`로도 빠졌다(`.scratch/harness/probes/canary_init/`, 대기열 85). `--setting-sources project,local`은 실을 설정 원천(`user`, `project`, `local`)에서 사용자 설정을 뺀다(claude 2.1.286의 `--help`를 읽었다). 이 플래그 없이 돈 탐침에는 사용자 전역 Stop 훅이 돌아 Slack 알림을 보냈다(일지 2026-09-29-03).
  - **질문은 카나리아다.** 바뀐 본문을 드러내지 않고, 그 본문에만 있는 것(낱말, 경로, 항목 수)을 그대로 옮기게 하며, 없으면 "없음"이라 답하게 한다. 질문은 낱말만이 아니라 그 낱말이 놓일 자리(칸, 절)까지 묻는다. next-session 카나리아는 칸을 짚은 질문 덕에 문장의 자리를 잘못 읽은 것을 잡았다(일지 2026-10-06-15, 대기열 127).
  - **대조군을 하나 둔다.** 규칙은 `paths` 밖의 파일을 Read하게 한다. 스킬은 바뀌기 전 사본(주 체크아웃, 또는 main을 꺼낸 임시 워크트리)에서 시작한 세션에 같은 질문을 던진다. 대조군이 "없음"이나 옛 줄을 답해야 질문이 답을 흘리지 않은 것이다.
  - **실험군이 "없음"이면 카나리아는 실패다(대기열 127).** 대조군과 같은 답이면 확인이 빈 것이지 통과가 아니다.
  - **스킬은 세션을 시작한 체크아웃의 사본이 실린다(손으로 봤다, 일지 2026-10-01-03·05).** 바뀐 사본이 있는 체크아웃에서 시작한다. 모델이 부르지 못하는 스킬(`disable-model-invocation: true`)은 프롬프트 머리에 슬래시 명령으로 넣는다(일지 2026-10-01-03). 그 길을 러너에 적는 법은 러너의 독스트링에 있다.
  - **Sonnet으로 세 번 묻는다.** 실린 규칙의 카나리아 하나(SWR 훅)에 Haiku는 세 번 중 두 번 "없음"이라 답했고, Sonnet은 세 번 다 답했다(손으로 봤다, 일지 2026-09-30-02).
- **워크트리 세션에 실리는 것은 세션이 어떻게 그 폴더에 왔느냐에 따라 다르다.** 세션은 어느 모드인지 알 길이 없어, 워크트리에서 고친 하네스는 위 항목의 `claude -p`로 확인한다. 아래 표는 2026-10-05 워크트리 감사 서브에이전트가 손으로 본 것과 일지 2026-10-02-01·2026-10-02-02, `tools/launch_hook.py` 독스트링을 모은 것이다.

  - 주 체크아웃의 사본은 그 순간 주 체크아웃에 체크아웃된 브랜치의 것이다. main이 아닐 수 있다.
  - 훅의 `.venv`가 비어 있으면(`uv run --no-sync`가 빈 환경을 만든다, 감사 서브에이전트가 손으로 봤다) ruff를 띄우는 `hook_ruff_line_width` 하나만 침묵한다. 판정은 pre-commit과 게이트에 남는다.
  - `settings.local.json`은 추적하지 않아 손으로 판 워크트리에는 없다. 가드는 `settings.json`에만 두고 local에는 allow만 둔다(`tools/check_instructions.py`가 local의 가드를 빨갛게 한다). 워크트리 세션에서 권한 프롬프트가 늘면 local이 없어서다.
- **세션 파일은 폴더 키로 갈린다.** `~/.claude/projects/` 아래 트랜스크립트는 세션을 시작한 폴더의 키에 쌓이고, `EnterWorktree`가 워크트리 키로 옮긴다. 같은 세션 id의 사본이 두 키에 함께 있고 낡은 쪽이 워크트리 키인 것을 감사 서브에이전트가 일곱 쌍 손으로 봤다. 어느 때 갈리는지는 재지 않았다. 워크플로는 스크립트가 작업 폴더 키에, 상태와 결과가 주 키에 놓였다(2026-10-05 이 세션에서 손으로 봤다). 자동 메모리는 주 키 한 곳이다. 세션 파일을 읽는 탐침과 훅은 키 둘을 다 보거나 메시지 id로 겹침을 거른다.
