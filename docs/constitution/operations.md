# Agent OS 헌법 · 검증과 운영

커밋, 병합, 트래커, LLM 테스트, 가드레일을 만질 때 읽는다. 검증 명령은 `CLAUDE.md`에 있고 실제로 돌려 통과한 명령만 적는다.

## LLM 테스트
LLM을 실제로 호출하는 테스트는 `llm` 마커를 붙인다. 기본 `pytest -q`는 이 마커를 제외한다. `uv run --env-file .env pytest -m llm`이 돌리며, `.env`의 `ANTHROPIC_API_KEY`가 없으면 skip이 아니라 실패한다. `.env`는 커밋하지 않는다. 그래서 워크트리에는 없고 `--env-file`은 작업 폴더 기준으로 풀려 uv가 테스트 전에 종료 코드 2로 멈춘다(2026-10-05 워크트리 감사 서브에이전트가 손으로 봤다). `.claude/worktrees/<이름>/`에서는 `--env-file ../../../.env`로 주 체크아웃의 것을 읽고 사본을 만들지 않는다(버리는 변이 워크트리는 `tools/mutate.py`의 절차). 원칙 I의 판정은 이 명령이다. CI가 생겨도 매 푸시에서는 돌리지 않는다. 손으로 돌리는 계기는 LLM 테스트 파일을 건드렸을 때가 아니라 그 테스트가 지나는 코드(`core/run.py`·`core/loop.py`, 어댑터, `channel/`, `main.py`)를 건드렸을 때다 — PR #46이 테스트를 한 줄도 안 고치고 그 아래 배관을 전부 바꿨다(대기열 1). 돌렸으면 일지 검사 절에 통과 수와 트레이스의 토큰 합계를 적는다. 합계는 그 실행 끝의 결과 요약 바로 위에 찍히는 `LLM 토큰 합계 …` 줄을 옮긴다. 무엇을 세고 무엇을 세지 못하는지는 `tools/llm_tokens.py`의 독스트링이 원천이다(대기열 113).

## 가드레일
자동 검사는 둘이고 내용은 같다 — 인용 대조는 경고만이라 pre-commit에만 있고, 커밋 메시지 검사는 커밋에 걸리는 것이라 pre-commit의 commit-msg 훅에만 있고, 변이 표의 원문 확인(`tools/mutate.py --staged`, 대기열 92·312)과 헌법 판 검사(`tools/check_constitution_version.py`, 대기열 31)는 커밋에 들 판(색인)을 부모 판이나 `origin/main`과 견주는 것이라 pre-commit에만 있고, e2e와 사진 비교는 CI에만 있다. 로컬 pre-commit 훅이 커밋마다, GitHub Actions CI(`.github/workflows/ci.yml`)가 푸시와 PR마다 ruff, ruff-format, pyright, import-linter, pytest(기본 마커), 지침 검사, 타입 우회 검사, 워크플로 감사(zizmor), 그리고 web의 `pnpm -C web verify`를 돈다. pre-commit에서는 파일을 고치는 ruff 둘 뒤에 검사 러너 `tools/run_checks.py`가 파일을 고치지 않는 `always_run` 검사(목록은 그 파일의 `CHECKS`)를 함께 띄워 결과를 모은다. pre-commit은 훅을 하나씩 돌기 때문이고, 건너뛰기는 그 id로 `SKIP=pytest`처럼 한다. 러너의 pytest는 `pytest-xdist`로 논리 CPU 수의 절반만큼 프로세스를 나눠 돌고, CI와 손으로 치는 pytest는 한 프로세스라 테스트끼리 부딪혀 나는 실패는 러너에서만 난다(ADR 0035). 설정 최상위의 `default_stages: [pre-commit]`이 커밋 메시지 훅 밖의 훅을 commit-msg 단계에서 다시 돌지 않게 한다(ADR 0005의 2026-10-07 이력). web의 것은 생성물 최신성(`web/tools/generate-api-client.ts --check` — 루트 `openapi.json`에서 다시 생성한 결과가 커밋된 생성 클라이언트 타입과 같은가), ESLint(typescript-eslint와 eslint-plugin-boundaries — 원칙 III의 TS 판정자와 층 경계, 경고 0), Prettier, tsc(루트와 워크스페이스 패키지마다, 그리고 사진 비교의 `packages/ui/visual`), Vitest, tsconfig 검사(`web/tools/check-tsconfig.ts`)다(ADR 0020·0021). Vitest는 프로젝트 셋이다. node 환경, 관리 화면 페이지의 jsdom, 그리고 디자인 시스템의 스토리 테스트를 실제 chromium에서 도는 `storybook`이다(ADR 0026). CI에서는 파이썬 쪽 검사를 `python` 잡이, `pnpm -C web verify`를 `web` 잡이 돌고(그 전에 chromium을 깐다), 같은 때 `e2e` 잡이 e2e(`pnpm -C web/apps/admin exec playwright test` — 실제 `serve`와 시작 래퍼로 띄운 관리 화면을 지나는 Playwright)를 돈다. 브라우저는 그 잡에서 설치하고, 없으면 e2e는 건너뛰지 않고 실패한다. pre-commit에는 없다. 같은 때 `visual` 잡이 사진 비교를 돈다. 판을 고정한 Playwright 이미지(`web/tools/visual.ts`의 `IMAGE`, 태그에 digest를 붙였다)를 잡의 컨테이너로 쓰고, 그 안에서 설치하고 Storybook 정적 빌드를 지은 뒤 `web/packages/ui`의 스토리를 커밋한 정답 사진과 `maxDiffPixels: 0`으로 비교한다. 정답 사진도 그 이미지 안에서만 만든다. 로컬에서는 `packages/ui`를 건드렸을 때 `pnpm -C web visual`을 친다. 정적 빌드는 호스트에서 짓고 비교만 네트워크 없는 컨테이너에서 하므로 Docker가 있어야 하고, 없으면 건너뛰지 않고 실패한다. pre-commit에는 없다(ADR 0026). 필수 검사 `verify`는 네 잡을 기다려 결과를 모으는 잡이고 넷이 모두 성공일 때만 초록이다. 건너뛴 잡은 필수 검사여도 성공으로 보고되므로 건너뜀과 취소도 빨강으로 본다. 잡을 더하면 `verify`의 `needs`에 넣는다. 빠뜨리면 `verify`가 같은 실행의 잡 목록을 API로 읽어 빨강으로 본다(잡 구조는 ADR 0021의 첫째, 이 판정은 둘째 2026-10-01 이력). 필수 검사의 판정을 바꾸는 PR은 draft 동안 두 경우를 실제 실행으로 본다. 빨강이어야 하는 경우는 그 경우를 만든 실험 커밋을 푸시해 보고 되돌리고, 다시 돌린 시도는 그 실험 실행을 `gh run rerun --failed`로 다시 돌려 본다. 그 판정을 들인 PR #119가 재기 전에 적은 동작 둘이 틀렸다. `verify` 뒤에 도는 잡은 잡 목록에 나오지 않았고, 지금 시도의 잡만 읽는 판정은 실패한 잡만 다시 돌린 시도에서 앞 시도의 잡이 옮겨지는 도중이라 샐 수 있었다(둘 다 실제 실행으로 손으로 봤다, 일지 2026-10-01-10, 대기열 90). 마크다운 표 검사(`tools/check_md_tables.py`, 대기열 44), 줄 구분 문자 검사(`tools/check_line_separators.py`, 대기열 22), 카나리아 명세 모양 검사(`tools/canary.py --shape`, 대기열 287)는 pre-commit이 스테이지된 파일에 돌리고, CI에서는 pytest의 저장소 상태 테스트(`test_이_저장소의_…`)가 저장소 전체에 돌린다. 훅 페이로드 실행(`tools/run_hooks.py`, 대기열 24)은 pre-commit에 먼저 들어갔고 CI는 web-admin 티켓 05의 워크플로 PR에서 뒤따랐다. 워크플로 감사는 체크아웃의 `persist-credentials: false`(artipacked)와 서드파티 액션의 커밋 해시 고정(unpinned-uses)을 판정하고, CI에서는 `python` 잡이 돈다. 도구의 판과 옵션은 `tech.md`의 워크플로 감사 행이다(ADR 0027). 원칙 III의 판정자는 언어마다 하나다. 파이썬은 타입 우회 검사다 — pyright strict가 `Any`·`cast`·억제 주석을 하나도 잡지 않아서 `tools/check_type_escapes.py`가 대신 판정한다. TypeScript는 typescript-eslint다(`web/eslint.config.mjs`, 변이 테스트는 `web/eslint.config.test.ts`). 훅은 각자 설치해야 하므로 CI가 최종 판정이다. main은 보호 브랜치다. 필수 검사 `verify`, 최신 main 기준(strict), 선형 이력, 강제 푸시와 삭제 금지, 관리자 우회 허용(혼자일 때). 관리자 토큰으로 도는 에이전트도 같은 우회를 갖고(`gh pr merge --admin`, main 직접 푸시), 로컬 훅은 커밋만 막는다(ADR 0005의 2026-09-29 이력). 경위는 ADR 0005. 병합은 여전히 `/git-pr-merge`로 한다. 스킬이 체크를 먼저 보기 때문이다. 워크트리에서는 그 스킬이 main을 가로채거나 실패해, 같은 체크를 본 뒤 `next-session`의 "워크트리에서 병합할 때"로 한다(ADR 0005의 2026-10-06 이력). 실패한 체크가 claude-review의 계정 한도뿐이면 주 체크아웃에서도 그 길로 한다(리뷰 파이프라인 3, ADR 0006의 2026-10-12 이력). 클론 뒤 주 체크아웃에서 `uv run pre-commit install`을 한 번 하면 pre-commit과 commit-msg 두 훅이 깔린다. git 훅은 워크트리와 공유되고, 워크트리에서 치면 공유 훅이 박아 둔 파이썬 경로가 그 워크트리의 것으로 덮인다(2026-10-05 워크트리 감사 서브에이전트가 pre-commit 4.6.2의 `install_uninstall.py`를 읽었다). `uv sync`와 `pnpm -C web install --frozen-lockfile`은 체크아웃마다, 워크트리를 팔 때마다 한다. 없으면 러너의 web verify가 첫 커밋부터 빨갛고, `uv run --no-sync`는 빈 `.venv`를 만들어 조용히 돈다. 스토리 테스트의 chromium은 체크아웃마다가 아니라 기계마다 Playwright 판마다 Playwright의 브라우저 캐시(Windows는 `%LOCALAPPDATA%\ms-playwright`)에 깔린다. 그래서 처음과 Playwright 판이 바뀔 때 `pnpm -C web exec playwright install --only-shell chromium`을 친다. 없으면 스토리 테스트는 건너뛰지 않고 실패한다(일지 2026-10-07-01). PowerShell 7(`pwsh`)도 기계마다 PATH에 둔다. pytest의 `tests/tools/test_open_session.py`가 그것으로 `tools/open_session.ps1`의 함수를 부르고, 없으면 건너뛰지 않고 실패한다(ADR 0030). 훅이 안 걸린 저장소는 그 자체가 결함이다. 훅 시스템은 pre-commit 하나만 둔다. 둘이면 `.git/hooks/pre-commit` 한 자리를 다퉈 한쪽이 조용히 안 걸린다. 파이썬 파일이 안 바뀐 커밋에서도 pyright·import-linter·pytest는 돌고, web 파일이 안 바뀐 커밋에서도 web verify는 돈다(`always_run`). 이유는 둘이다. 파이썬 파일만 바꿔도 돌아야 하는 것은 pyright·pytest와 같고, 파이썬 티켓이 `openapi.json`을 바꾸면 생성물 최신성이 빨개져 다시 생성한 타입이 같은 커밋에 담긴다. CI에 경로 필터를 걸게 되면 미매칭은 skip이 아니라 실패로 만든다. 원칙 IV 중 "플러그인은 sdk만 import한다"는 import-linter가 아니라 `tests/test_plugins_boundary.py`가 판정한다 — 플러그인은 `root_packages` 밖이다(ADR 0018). 원칙 II의 "skip된 테스트는 초록이 아니다"는 `tests/conftest.py`가 판정한다. 바뀐 마크다운의 20자 이상 따옴표 인용을 저장소와 대조하는 `tools/check_quotes.py`(대기열 42)는 경고만 내므로 pre-commit에만 있고 CI에는 없다.

에이전트 자신의 도구 출력에 비밀이 실리는 것은 게이트가 보지 않는다. `.claude/settings.json`의 `permissions.deny`가 모든 위치의 `.env`에 Read·Edit와 PowerShell 읽기 모양을 막고(`.scratch/harness/probes/env_deny_probe.md`), `tools/hook_env_read.py`가 Bash로 읽는 길(`cat .env`, `< .env`, `.env`를 빼지 않은 저장소 전체 grep)과 `.env`를 경로로 준 Grep을 막는다(대기열 43 — 2026-09-28 감사에서 서브에이전트의 grep 한 번에 키 값이 도구 출력에 실렸다). 사용자 설정 파일 둘(`~/.claude/settings.json`, `~/.claude.json`)을 Read·Grep·Bash·PowerShell로 출력하는 길은 `tools/hook_user_settings_read.py`가 막고, 값 없이 키 이름만 내는 명령을 안내한다(대기열 272 — 설정의 한 갈래를 통째로 출력해 비밀이 세션 기록에 남았다). 그 설정의 `env`가 세션의 환경에 들어가 `env`·`printenv`로 나오는 길은 그 훅도 보지 않는다. 못 보는 것은 두 훅의 독스트링. 이 장치들은 모두 호출의 모양을 보는 에이전트 층이다(공식 permissions 문서: 권한 규칙은 보안 경계가 아니다). 에이전트 밖의 층은 키 자체다 — `.env`에는 사용 한도를 건 개발용 키만 두고, 2026-09-28에 도구 출력에 실린 키는 회전했다(사용자 확인 2026-09-29). Claude Code 훅의 원천은 그 설정 파일이고 훅마다 이유는 `tools/hook_*.py` 독스트링에 있다.

## 브랜치와 병합
- 원격은 GitHub(`njh6803/agent-os`, 공개). main은 보호 브랜치다(가드레일 절). PR마다 티켓 하나이고(ADR 0037) 혼자여도 PR을 연다. 브랜치 이름은 그 티켓 파일 이름의 stem 그대로다. 기능 디렉터리의 티켓은 `feature/<NN>-<slug>`(하네스 기능도, 기능 밖의 제품 고침도 그 기능 디렉터리의 티켓이다), harness 티켓은 `chore/<NNN>-<slug>`, 면제 PR(기능의 설계·명세·티켓을 쓰는 PR, 기록만 바꾸는 PR)은 `docs/<slug>`다. 티켓의 자리·번호·상태는 `docs/agents/issue-tracker.md`. main 위의 커밋은 `tools/hook_git_main_commit.py`가 막는다. 브랜치 이름은 그 작업을 하는 세션의 제목이기도 하다(`open-session`). `/git-pr`이 `.github/PULL_REQUEST_TEMPLATE.md`를 채운다.
- 병렬 브랜치는 PR 전에 main에 rebase한다. 병합은 squash이고 main 이력은 PR 단위다. 주 체크아웃에서는 `/git-pr-merge`로, 워크트리에서는 `next-session`의 "워크트리에서 병합할 때"로 한다(claude-review가 계정 한도로만 빨간 예외는 리뷰 파이프라인 3). PR 제목이 곧 main의 커밋 제목이므로 컨벤셔널 커밋 형식이다. 리뷰는 아래 리뷰 파이프라인.
- 워크트리는 `.claude/worktrees/<이름>`에 두고 `.worktrees/`로 옮기지 않는다(`EnterWorktree`가 새 워크트리를 만드는 위치다, ADR 0032). `EnterWorktree`를 치기 직전에(`name`으로 만들 때도 `path`로 들어갈 때도) `git worktree list --porcelain`을 쳐서 본다. 같은 브랜치가 체크아웃된 워크트리가 있으면 새로 만들지 않고 `EnterWorktree(path)`로 그 자리에 들어가고, 그 자리가 주 체크아웃이면 거기서 잇는다(`next-session` 3단계의 이미 있는 브랜치 문장과 같은 두 갈래다). 경로 이름만 같고 브랜치가 다르면 들어가지 않고 이름을 바꾼다. 들어가기 전에 이 세션을 뺀 `isRunning` 세션(`list_sessions`) 가운데 제목이 그 브랜치인 것이 있으면 사람에게 넘긴다(제목으로 거르는 법은 `tidy-checkouts` 3의 판정 3과 같다). 판정 3과 달리 `list_sessions`의 `branch`는 보지 않는다. 인계하는 세션은 제목만 `<브랜치> (인계함)`으로 바꾸므로, `branch`까지 보면 인계받은 새 세션이 넘긴 세션에 막힐 수 있다(ADR 0032 이력 2026-10-20). 제목이 브랜치가 아닌 세션과 `list_sessions`를 쓰지 못하는 서브에이전트는 이 세션 확인을 거치지 못하고 목록만 본다. `locked` 줄은 막는 이유로 쓰지 않는다. `EnterWorktree`가 만든 워크트리는 그 세션의 pid로 잠기므로 자기 워크트리로 다시 들어오는 세션이 스스로 막히고, 죽은 pid의 잠금은 `tidy-checkouts`가 풀고 지운다. 다른 세션이 잠근 워크트리는 `EnterWorktree(path)`가 그 pid가 살아 있으면 `belongs to another running Claude Code session`으로 거부한다. 인계로 넘긴 세션은 턴을 끝내도 프로세스가 남아 pid가 산다. 그래서 넘기는 세션이 열기 전에 자기 잠금을 푼다(`next-session` "인계할 때" 4, 대기열 326). 이미 워크트리 안에 있는 세션은 `name`으로 새로 만들지 못하고 `path`로만 옮긴다(도구 설명). 그 세션이 새 브랜치가 필요하면 그 워크트리를 쓰는 세션이 없는지 본 뒤 거기서 `git switch -c <브랜치> origin/main`으로 딴다(`next-session` "워크트리에서 병합할 때" 5). 중복 생성은 git이 이미 막으므로(`.scratch/harness/probes/worktree_duplicate_checkout.sh`) 이 확인의 몫은 그 자리를 쓰는 세션을 거르는 것이다.
- 워크트리의 정리는 `tidy-checkouts`가 한다. 앱이 표지(`claude-desktop-worktree`)를 단 워크트리(앱이 만든 것)는 `tidy-checkouts`가 남기고 앱의 정리에 맡긴다. 병합된 워크트리를 턴을 마친 지 한 시간 넘은 세션의 프로세스만 쥐고 있으면 `tidy-checkouts`가 그 프로세스를 끝내고 지운다. 세션은 사이드바에 남는다(ADR 0032 이력 2026-10-20). 앱의 `clean_up_worktrees`는 30·60·90일 기준이라 병합 직후의 정리에 맞지 않아 쓰지 않는다(ADR 0032).
- 병렬 작업은 프론티어(막힌 것이 없는 티켓)에서만 하고, 티켓마다 워크트리 하나다. 일지는 `docs/journal/<날짜>-<NN>-<슬러그>.md`이고 `NN`은 그날의 순번이다. 같은 날 세션 둘이 쓰면 순번이 갈라 주고, "최신 파일"은 이름 정렬로 정한다.
- 커밋 메시지는 컨벤셔널 커밋, 한국어. 형식(`<타입>: <제목>`, 72자, 마침표 없음)은 commit-msg 훅이 판정하고, 본문의 "왜 그렇게 했는지와 남긴 위험"은 리뷰가 본다.
- PR을 연 세션이 반영과 병합까지 한다(`/git-pr-feedback`, 병합은 주 체크아웃이면 `/git-pr-merge`, 워크트리면 `next-session`의 "워크트리에서 병합할 때". 예외는 리뷰 파이프라인 3). 다만 세션 컨텍스트가 20만 토큰을 넘은 채 단계 경계(셀프 리뷰 직전, 커밋 뒤, PR 연 뒤)에 와서 인계 계기(`tools/hook_handoff.py`)가 오면 그 세션은 같은 브랜치·워크트리의 새 세션에 넘기고, 남은 반영과 병합은 그 새 세션이 한다(`next-session` 결정표의 인계 줄, ADR 0033). PR 생성이나 병합은 세션을 끝내는 사건이 아니라 `next-session` 스킬의 계기이고, 계기는 훅(`tools/hook_pr_next_session.py`)이 넣는다. 지시문은 병합 뒤에 실행된다. 세션을 끝내는 것은 지시문의 "어디서"가 새 세션일 때뿐이며, 그때 `open-session` 스킬이 같은 체크아웃에 연다(딥링크. 폴더를 싣지 못한다). 막힌 것이 없는 티켓이 둘 이상이면 `next-session`이 티켓마다 지시문을 내고 `open-session`이 그 세션을 차례로 전부 열며, 그 세션들은 지시문대로 각자 워크트리를 파서 일한다(위 "티켓마다 워크트리 하나"). "이 세션"이면 이어간다. 어느 쪽인지는 결정표(스킬)가 정하고, 사용자가 이어서 지시하면 따른다.

## 리뷰 파이프라인
세 축이다. 표준·명세, 보안·버그·성능, 유지보수성·경계. 축 이름은 이 줄이 원천이다. 판단 기준과 심각도의 원천은 `CODING_STANDARDS.md`이고 여기는 누가 언제 무엇을 보는지만 적는다.

1. **커밋 전 셀프 리뷰.** `/code-review`가 표준 축(`CODING_STANDARDS.md`)과 명세 축(브랜치가 가리키는 티켓 파일. 기능 디렉터리의 티켓이면 그 디렉터리의 `spec.md`도)을 본다. 범위는 merge-base 이후 커밋과 미커밋 작업 전부이고, 문서만 바뀐 변경도 면제하지 않는다. Critical·Major는 커밋 전에 고친다. 건너뛰지 않는다. Minor·Nit은 별도 티켓으로 뺄 수 있다. 보고를 받은 뒤 그대로 구현하지 않고 근거를 먼저 확인하는 것은 이 축도 2단계와 같다. 아래 초록 착시의 반대편이다. 범위를 잡는 법과 반영 절차는 스킬 1·6단계.
2. **PR 직전 CodeRabbit CLI.** `coderabbit-review` 서브에이전트(`.claude/agents/`)가 보안·버그·성능 축을 PR 전에 한 번 본다. 트리아지(유효·오탐·보류)만 하고 수정은 본 세션이 한다. 유효 지적은 고치는 값이 작으면 PR을 열기 전에 고친다. `보류` 판정도 고치는 값이 작으면 확인을 기다리지 않고 고친다. 고치지 않고 두는 지적은 판정과 고치는 데 드는 값을 PR 체크리스트의 그 줄에 적는다. 둔 지적을 PR 봇이 같은 자리에서 다시 짚어 결국 고친 일이 두 번이었고, PR을 연 뒤에 고치면 푸시와 CI가 한 바퀴 더 돈다(대기열 190). CLI 상한은 개발자당 시간당 3회이고 롤링 윈도다(공식 요금제 문서의 rate limits 표, 2026-09-21 확인). 공개 저장소라 OSS 플랜이지만 CLI 상한은 무료 플랜과 같다. "PR마다 한 번, `sdk`·`core`·`adapters`가 우선"은 한도가 아니라 우리 선택이다. 시간당 3회면 커밋마다도 돌 수 있으므로 바꾸려면 ADR을 남긴다. `coderabbit --usage`는 청구 주기 누적과 초기화 날짜만 보여주고 시간당 잔량은 보여주지 않는다.
   - **CLI가 연결 단계에서 즉시 끝나는 것은 한도가 아니라 좌석 미배정이다.** 증상은 `You are not a member of the requested organization`이고 확인은 `coderabbit auth status`의 `Seat: not assigned`다(2026-09-23 실측). **좌석 배정에는 유료 구독이 필요하다** — 공식 문서 `management/seat-assignment`가 요청의 전제를 "active paid subscription"으로 적고 체험 종료 후에는 불가하다고 명시한다. 배정 화면은 조직 설정의 Team Management이고 구독 상태는 Subscription and Billing이지만, `Plan: Free`에서는 거기 배정할 좌석이 없다. 2026-09-22까지는 CLI가 실제로 돌았으므로(일지 `2026-09-22-10`, finding 3건) 체험 종료로 끊긴 것으로 본다. **유료 전환 전까지 PR 직전 CLI 축은 구조적으로 비어 있고** 아래 대체 둘이 그 자리를 맡는다.
   - **CLI가 돌지 못하면(미설치, 로그인·좌석 없음, 한도 초과) 대체 둘을 PR 직전에 나란히 돌린다(대기열 136).** 보안은 내장 `/security-review`, 버그·성능은 `bug-perf-review` 서브에이전트(`.claude/agents/`)다. `/security-review`는 보안만 보므로 나머지 둘을 서브에이전트가 보고, 지적은 `coderabbit-review`와 같은 트리아지(유효·오탐·보류)로 가르고, 고치는 값이 작으면 PR을 열기 전에 고치고 두는 지적은 판정과 그 값을 PR 체크리스트에 적는 처리(위 2의 본문)도 같다. `/security-review`는 작업을 커밋하고 origin/main을 합친 뒤에 돌린다. 미커밋 변경만 있는 브랜치에서 그 명령이 모은 diff는 비었다(손으로 봤다, 일지 2026-10-07-16). 그 명령의 프롬프트는 커밋 목록을 `git log --no-decorate origin/HEAD...`(대칭차)로, diff를 `git diff origin/HEAD...`(merge-base부터)로 채운다(claude 2.1.296 실행 파일에 든 그 프롬프트의 `COMMITS:`·`DIFF CONTENT:` 칸을 읽었다). 그래서 합치기 전에는 이 브랜치를 딴 뒤 main에 병합된 PR이 커밋 목록에 섞여, 리뷰를 맡은 서브태스크에 넘길 범위를 손으로 좁혔다(일지 2026-10-12-27·2026-10-12-32, 대기열 206). 임시 저장소에서 git 2.32로 합치기 전과 뒤에 `git log --no-decorate --format=%s origin/HEAD...`를 쳐 보니, 합친 뒤에는 main의 커밋이 빠지고 병합 커밋이 더해졌다(손으로 봤다). 무엇이 돌았는지와 결과는 PR 체크리스트의 그 줄에 적는다. 경위는 ADR 0006의 2026-10-07 이력.
3. **PR 리뷰.** 봇 둘이 역할을 나눈다. CodeRabbit(`.coderabbit.yaml`)이 보안·버그·성능, Claude Code Review(`.github/workflows/claude-code-review.yml`)가 유지보수성(리뷰 관점 넷)과 경계(import-linter가 못 보는 원칙 IV 위반, `sdk` 계약 변경의 동반 수정). CI가 자동 검사. 별이 10개 미만인 공개 저장소는 CodeRabbit이 자동으로 돌지 않으므로(PR #12 실측), PR을 연 직후 에이전트가 `gh pr comment <번호> --body "@coderabbitai review"`로 요청한다. OSS 플랜의 PR 리뷰 상한은 저장소 별 수에 따라 시간당 1~10회이고 우리는 별이 적어 하한 쪽이다. CodeRabbit 체크는 한도를 넘거나 요청이 없어도 `pass`가 되므로 필수 검사(가드레일 절)에 넣지 않고 코멘트가 있는지로 판정한다. 셋이 초록이고 코멘트를 반영한 뒤 `/git-pr-merge`(한도에 걸린 회차는 아래 항목과 초록 착시 목록). 이력은 ADR 0006.
   - **claude-review가 계정의 주간 사용량 한도로 빨가면 풀리기를 기다리지 않는다(대기열 165).** 그 실행은 리뷰를 시작하지 못하고 끝난다. `uv run python tools/gh_run_summary.py <run-id>`의 결과 블록이 `"is_error": true`와 `"terminal_reason": "api_error"`이고, Claude의 말이 "You've hit your weekly limit"으로 시작한다(PR #172의 실행 38120400317을 손으로 봤다). 그 빨강은 지적이 아니라 리뷰 없음이다. 이때 PR의 `mergeStateStatus`는 `UNSTABLE`일 수 있고, GitHub GraphQL 스키마는 그 값을 "Mergeable with non-passing commit status."로 정의한다(스키마의 `MergeStateStatus`를 읽었다. 이 저장소에서 그 값을 본 적은 없다). 필수 검사 `verify`가 초록이고 다른 리뷰의 지적을 반영했으면 병합하고, 마지막으로 리뷰를 받은 커밋(없으면 없다고)과 풀리는 시각을 PR 코멘트에 남긴다. 주 체크아웃의 `/git-pr-merge`는 실패한 체크가 있으면 멈추므로(사용자 수준 스킬의 2단계를 읽었다) 이때는 `next-session`의 "워크트리에서 병합할 때" 1~3으로 병합하고 `tidy-checkouts`를 돈다. 카나리아가 같은 한도에 막히는 것은 환경 규약 상세의 카나리아 항목이다. 경위는 ADR 0006의 2026-10-12 이력.
4. **반영.** `/git-pr-feedback`이 CI 결과와 코멘트를 읽어 반영한다. 보류한 지적은 별도 티켓. 다만 봇 리뷰의 둘째 회차부터는 Critical·Major가 아닌 지적을 티켓으로 빼지 않고 PR 코멘트에 보류 이유를 남기는 것으로 닫는다. 그 기준과 회차를 세는 법은 `next-session` 1단계가 원천이다(대기열 137).

봇의 초록은 리뷰했다는 뜻이 아니다(선행 저장소 실측).
- CodeRabbit(PR)은 비공개+무료에서 작성자에게 시트가 없으면 변경 요약(Walkthrough)만 남기고 `pass`가 되고, 시간당 한도를 넘으면 "Review rate limited"로도 `pass`다(PR #2 실측 둘). 공개 저장소에서는 전체 리뷰가 무료라 켰다. 한도 초과의 `pass`는 남으므로 코멘트가 있는지 본다.
- Claude Code Review는 **자기 워크플로 파일**(`claude-code-review.yml`)을 바꾼 PR에서 건너뛰면서 `pass`가 된다. 액션이 그 파일을 기본 브랜치의 것과 비교해 다르면 실행하지 않는다(PR #3·#6 실측, 로그 경고 "Skipping action due to workflow validation"). 그 파일의 변경은 별도 PR로 먼저 병합한다. 다른 워크플로 파일(`ci.yml`)만 바꾼 PR은 건너뛰지 않는다.
- Claude Code Review는 플러그인을 쓰던 동안 코멘트 없이 `pass`가 되곤 했다(PR #2·#4·#5). 플러그인이 서브에이전트를 백그라운드로 띄우고 턴을 끝내는데 헤드리스 실행이 그 전에 종료됐다. 그래서 워크플로를 직접 프롬프트(단일 에이전트, 요약 코멘트 하나가 완료 조건)로 바꾸고, 실행 시작 뒤 생긴 `claude[bot]` 코멘트가 0개면 잡을 실패시키는 스텝을 둔다(2026-09-20 회고 후보 1, PR #10). 그 워크플로부터는 코멘트가 없는 초록이 나오지 않아야 하고, 나오면 `uv run python tools/gh_run_summary.py <run-id>`로 결과 블록(거부 수 포함)·훅 오류와 알림·경고·Claude의 말을 본다.
- Claude Code Review는 PR 헤드의 `.claude/`, `CLAUDE.md`, `.mcp.json`을 쓰지 않고 main의 것으로 되돌린다. 하네스를 바꾼 PR은 병합된 뒤에야 리뷰에 반영된다.
- Claude Code Review의 러너에는 uv가 없어, 저장소 훅(등록이 모두 `uv run`이다)이 돌지 못한다. 설정 파일은 실린다(init의 `settingSources`에 `project`가 있다). 그래서 설정의 권한 규칙은 걸리지만 로컬의 막는 훅(`hook_env_read` 등)은 CI 리뷰에서 돌지 않는다. 로그에 응답이 남은 것은 SessionStart이고 `/bin/sh: 1: uv: not found`(종료 127)였다. 127은 막는 코드(2)가 아니라 리뷰는 돈다(PR #172·#174·#176의 실행). 다른 이벤트의 훅은 응답이 로그에 없다. #174·#176 끝의 "Stop hook error" 알림도 같은 까닭으로 보나 어림이다(대기열 178).
- 병합 전에 코멘트가 실제로 있는지 본다. 코멘트 0개인 초록은 "리뷰 없음"으로 읽고 이유를 확인한다.
- **`gh pr checks`의 초록이 현재 HEAD의 것이 아닐 수 있다.** 푸시 직후 GitHub가 PR head를 갱신하기 전에 조회하면 이전 커밋의 결과가 그대로 보인다(PR #44 실측. 새 커밋에 대한 워크플로 실행이 하나도 없는데 세 축이 전부 `pass`였다). 위아래의 다른 항목들이 "리뷰가 돌지 않았는데 pass"인 것과 달리 이것은 **다른 커밋의 pass를 현재 것으로 읽는 것**이라, 코멘트가 있는지로는 잡히지 않는다 — 그 코멘트도 이전 커밋의 것이다. 판정은 `gh run list --branch <브랜치> --json headSha`로 **어느 커밋이 검사됐는지** 보는 것이고, 병합 직전에 `gh pr view --json headRefOid`와 `git rev-parse HEAD`가 같은지 먼저 본다. 동기화는 몇십 초 걸릴 수 있다. **같은 지연이 리뷰를 부르는 쪽에도 있다.** 푸시 직후 `gh pr ready`를 치면 claude-review가 그 순간의 옛 head를 리뷰하고, `@coderabbitai review`는 "Head commit changed"로 버려진다(PR #117 — claude-review가 이미 되돌린 실험 커밋의 `exit 1`을 Critical로 냈다, 대기열 86). 둘 다 `tools/hook_pr_head_sync.py`가 PR head가 로컬 HEAD에 못 미치면 막는다(PR 쪽이 앞섰거나, 다른 브랜치의 PR이거나, PR head가 로컬에 없으면 지나간다). 막히면 `gh pr view --json headRefOid`가 로컬 HEAD와 같아진 뒤 다시 친다.
- CodeRabbit이 초록으로 지나가는 사유가 하나 더 있다. **별이 10개 미만인 저장소는 자동 리뷰를 받지 않는다**(PR #43 실측, "This repository does not receive automatic reviews because it has fewer than 10 stars"). 공개라서 무료인 것과 자동으로 도는 것은 다르다. 수동으로 `@coderabbitai review`를 남겨야 하고, **그 코멘트 뒤에 푸시하면 "Pull request base or head changed"로 아무것도 하지 않는다**(같은 PR 실측). 요청은 마지막 푸시 뒤에 남긴다.
- PR #43이 "반례"로 적혀 있던 것은 조건을 잘못 읽은 것이었다. #43은 `ci.yml`만 바꿨고 건너뛴 #3·#6은 둘 다 `claude-code-review.yml` 자체를 바꿨다(2026-09-28 `git show --stat`으로 확인). 조건은 위 항목대로 "자기 워크플로 파일이 다른가"이고 반례가 아니다. 판정은 언제나 "코멘트가 실제로 있는가"다.
- CodeRabbit PR 리뷰는 OSS 시간당 한도에 자주 걸린다(첫 슬라이스 PR 일곱 중 다섯이 "Review rate limited"로 `pass`). 그 PR의 보안·버그 축은 PR 직전에 돈 리뷰(CLI, 또는 2단계의 대체 둘)의 결과를 PR 체크리스트나 코멘트에 적은 것이 대체이고, 적은 것이 없으면 리뷰 없음이다.
- **PR을 연 뒤 수정 커밋의 전체 재리뷰가 한도로 비면 반영한 지적마다 그 스레드의 CodeRabbit 답글을 본다(대기열 41).** 답글이 수정 커밋을 직접 읽었으면(분석 체인이 그 커밋의 파일을 열었거나 그 위에서 스크립트를 돌렸다) 그 지적은 덮였다. 작성자의 답글을 되풀이하기만 한 답글은 확인이 아니다(#95의 두 스레드 가운데 하나, 일지 2026-09-28-07). 수정 커밋에서 지적을 고친 것 밖의 변경은 claude-review가 돌았으면 유지보수성·경계 축으로 보지만, 보안·버그 축은 그 회차에 비어 있다. 덮인 지적과 덮이지 않은 지적, 비어 있는 축을 PR 코멘트 하나에 적는다. 병합은 재리뷰를 기다리지 않는다(ADR 0006의 2026-10-12 이력).

전제 둘은 사람이 한 번 한다. `claude setup-token`으로 만든 토큰을 저장소 시크릿 `CLAUDE_CODE_OAUTH_TOKEN`에 등록, 로컬 `coderabbit auth login`. 에이전트는 토큰과 시크릿을 다루지 않는다. 등록 여부만 `gh secret list`로 본다. 이름과 시각만 나온다.

## 문서 위치
문서는 범위가 있는 곳에 둔다. 저장소 전체에 해당하면 루트 `docs/`, 한 앱에만 해당하면 그 앱 안(README). 한 앱에만 걸리는 지침은 중첩 `CLAUDE.md`가 아니라 그 경로를 `paths`로 든 `.claude/rules/*.md`에 둔다. 규약을 한곳에 모으는 쪽이고(ADR 0004), 중첩 `CLAUDE.md`는 그 안의 `@` 임포트까지 따라와 루트 지침에 거는 검사(줄 수, 임포트 허용 목록) 밖에 놓인다(ADR 0021). `tools/check_instructions.py`가 빨강으로 본다. 같은 사실을 두 곳에 두지 않고, 지역 문서는 루트를 요약하지 않고 가리키며, 루트가 지역 문서를 색인한다. 헌법, 용어집, ADR 번호열은 하나다. 지역 결정도 루트 ADR 열에 넣고 제목에 범위를 적는다.

잔존 grep(`CLAUDE.md` 작업 규약 4)은 살아 있는 문서만 본다. 기록은 당시의 사실이라 옛 말이 남아도 잔존이 아니다. 기록은 일지(`docs/journal/`), 끝난 기능의 `.scratch/<slug>/` 명세·티켓·프로브(제품 기능은 `plan.md`의 상태가 done일 때, 하네스 기능은 그 디렉터리에 티켓이 있고 모두 done일 때. done인 제품 기능에 고침 티켓이 열려도 나머지는 기록이고 그 티켓만 살아 있다), `.scratch/harness/issues/`에서 `Status:`가 done인 티켓 하나하나(`.scratch/harness/`는 기능 디렉터리가 아니어서 폴더째 기록이 되지 않고 티켓을 하나씩 본다), ADR의 지난 이력 항목, 대기열의 닫힌 행, 그리고 살아 있는 문서 안의 이력(헌법 README의 버전 이력, 프로브 README의 지난 결과, 카나리아 명세 머리 주석의 `# 최신 결과:` 줄과 그 뒤에 이어 적은 줄)이다. 살아 있는 문서는 `plan.md`, 진행 중인 기능의 명세·티켓, done이 아닌 harness 티켓과 열린 고침 티켓, `.scratch/harness/probes/`, 대기열의 열린 행, ADR의 본문, 헌법, `CLAUDE.md`, rules, 스킬, 독스트링과 주석이다. PR #117에서 셀프 리뷰는 `plan.md`를 잔존으로 짚어 맞았고, claude-review는 done인 web-admin의 명세·티켓을 잔존으로 짚었다. 이 가름이 없어 둘의 기준이 갈렸다(대기열 87).

## 환경 규약 상세
명령을 치기 전에 알아야 하는 것은 `CLAUDE.md` 환경 함정에 있다. 그 밖에 선행 저장소가 겪은 것과 가끔 쓰는 것.
- ruff E501은 표시 폭 기준이라 한글 한 글자가 2로 세어진다.
- `PYTHONUTF8=1`은 `.claude/settings.json`의 `env`가 넣는다(대기열 40). 설정 `env`의 값이 Bash 도구의 명령에 보이는 것을 사용자 설정의 다른 값으로 실측했다(2026-09-28). 훅 프로세스 쪽은 재지 못했고 훅은 어차피 stdin을 바이트로 읽는다. 사용자 터미널에서 도는 pre-commit은 이 밖이라 conftest가 stdout을 UTF-8로 고정한다.
- **`UV_LINK_MODE=copy`도 `.claude/settings.json`의 `env`가 넣는다(대기열 217).** 이 설정을 읽은 Claude 세션이 치는 uv는 `.venv`에 패키지를 uv 캐시에서 하드링크가 아니라 복사로 깐다. 워크트리 세션은 주 체크아웃의 설정을 읽으므로(아래 모드 표), 주 체크아웃이 이 값을 들인 커밋보다 뒤면 그 세션에는 닿지 않는다. 클라우드 세션은 재지 않았다. 하드링크 `.venv`는 다른 `.venv`의 파이썬이 올린 확장 모듈(링크 수 74~78)을 쥔 것으로 `tidy-checkouts`의 판정 3에 걸리고 그 파일의 지우기가 `WinError 5`로 막혔다. 복사 `.venv`는 세 번 모두 걸리지 않고 지워졌으며, 자기 `.venv`에서 띄운 파이썬은 여전히 잡혔다(`.scratch/harness/probes/venv_link_mode.py`, 2026-10-13). 2026-10-14에 셋을 손으로 봤다. 첫째, 워크트리에서 띄운 `claude -p`의 Bash와 그 아래 `uv run python`이 `copy`를 받았고, 이 값이 없던 주 체크아웃에서 띄운 것은 빈 값이었다(stream-json의 도구 결과로 봤다). 둘째, git은 커밋 훅에 이 값을 넘겼고 값을 뺀 대조 커밋은 빈 값이었다(임시 저장소의 훅이 찍었다). pre-commit은 Bash가 띄운 git의 훅이라 첫째와 둘째를 이은 것이고, 그 자리를 한 번에 재지는 않았다. 셋째, 플래그 없이 이 환경 변수만 둔 `uv sync`는 `pydantic_core`의 `.pyd`를 링크 수 1로, 같은 자리의 `hardlink`는 77로 채웠다. 사용자 터미널의 uv는 이 밖이다. 링크 방식은 패키지를 깔 때 정해지므로 이미 있는 `.venv`의 패키지는 그 패키지를 다시 깔 때까지 하드링크로 남고, 같은 `.venv`에 사용자 터미널의 uv가 까는 패키지는 하드링크다. 이 PC의 `uvx`가 이 값을 둔 채 앞선 실패가 캐시에 남긴 임시 디렉터리를 휠의 잘못된 항목으로 읽은 일이 한 번 있었다(ADR 0027). 고르는 과정에서 `pyproject.toml`에 두어 모든 uv에 거는 안과 기록만 하는 안은 기각됐다(일지 2026-10-14-02). 2026-10-15부터 `tidy-checkouts`의 판정 3은 올린 모듈을 보지 않는다. 하드링크로 올린 모듈은 그 파일이 든 폴더의 이름 바꾸기를 막지 않으므로, 도구가 다시 만들 수 있는 무시된 항목을 휴지통(`.claude/worktrees/.tidy-trash/`)으로 옮긴 뒤 git이 워크트리를 지우고, 막힌 파일만 휴지통에 남긴다(`tools/tidy_checkouts.py` 독스트링의 판정 4, 일지 2026-10-15-06). 그래서 pnpm의 하드링크 `node_modules`(대기열 258)는 바꾸지 않았다. 이 설정은 복사 `.venv`가 다른 체크아웃의 파이썬에 잡히지 않아 휴지통에 남는 것을 줄이는 몫으로 남는다.
  - **새 워크트리의 첫 `uv sync`나 `uv run`은 2분을 넘길 수 있다.** 같은 프로브에서 복사는 105~148초, 하드링크는 11~22초였다(세 번. 차이가 백신 검사 때문이라는 것은 어림). Bash 도구의 기본 제한(120000ms)에 걸리므로 `timeout` 600000으로 치거나 백그라운드로 돌린다. 걸려 끊겨도 다시 치면 이어 깐다. 걸린 명령이 끊기지 않고 백그라운드로 넘어갔으면 그 작업이 끝난 것을 작업 도구로 본 뒤에 다시 친다(같은 `.venv`에 두 uv가 함께 까는 경우는 재지 않았다). 30초에 프로세스 트리째 죽인 복사 `uv sync`를 다시 치자 53.6초에 종료 0이었고, `uv sync --check`가 바꿀 것이 없다고 했으며 주요 모듈이 import됐다(2026-10-14, 손으로 봤다). pre-commit의 `uv run`이 첫 uv 실행이면 커밋 명령이 이 제한에 걸린다. 워크트리마다 파일 10780개, 146.8MiB가 더 든다(2026-10-13에 워크트리 `.venv` 65개, C: 여유 360GB).
  - pnpm의 `node_modules`도 하드링크이고 이 값으로 풀리지 않는다. 2026-10-13의 판정 한 번에서 `node.exe`·`esbuild.exe`가 쥔 워크트리가 남았다.
- 환경이 없어 skip된 테스트는 초록이 아니다. `tests/conftest.py`가 skip이 하나라도 있으면 세션을 실패로 끝낸다(2026-09-28). `-m`의 deselect는 skip이 아니다.
- `alembic.ini` 같은 ini 계열은 환경변수로 인코딩을 못 바꾼다. ASCII만.
- pyright 프로브는 `tests/` 아래에 둔다. 점 디렉터리와 `include` 밖은 검사 없이 "0 errors"다. 분석 여부는 `--outputjson`의 `summary.filesAnalyzed`로 본다. `--pythonpath`는 `[tool.pyright]`의 `venvPath`·`venv`에 덮여 무시되니 임시 환경은 `--venvpath`로 넘긴다.
- **Windows에서 맨 `bash`는 WSL의 것으로 찾아진다(대기열 147).** Python `subprocess`에 `["bash", …]`를 넘기면 System32의 `bash.exe`(WSL)가 돌아 Windows 경로와 환경 변수가 넘어가지 않았고(`uname`이 WSL 커널, `TEMP` 없음, 작업 폴더가 `/mnt/c/…`), PowerShell의 `Get-Command bash`도 `C:\Windows\system32\bash.exe`를 먼저 찾았다. `shutil.which("bash")`와 Git Bash의 `type -a bash`는 Git Bash를 먼저 찾았다(2026-10-13 손으로 봤다, 처음 겪은 것은 일지 2026-10-07-14). 그래서 bash 스크립트를 띄우는 탐침과 도구는 `shutil.which`로 찾은 경로를 넘기거나 Git Bash에서 돈다.
- **주 체크아웃 안의 워크트리(`.claude/worktrees/`)에서 `.git` 디렉터리를 찾아 올라가는 도구는 주 체크아웃을 루트로 잡는다(대기열 159).** 워크트리의 `.git`은 디렉터리가 아니라 파일이라, 올라가다 처음 만나는 `.git` 디렉터리가 주 체크아웃의 것이다. 그런 도구에는 설정을 경로로 넘긴다. 겪은 것은 zizmor이고 경위와 처방은 ADR 0027과 `tech.md`의 워크플로 감사 행이다. `CLAUDE.md` 환경 함정의 "검사 도구가 내가 생각하는 것을 실제로 봤는지"와 같은 계열이다.
- **워크트리 가드가 거부한 모양(대기열 122).** 규칙은 `CLAUDE.md` 환경 함정에 있고 여기는 근거다. 거부 메시지는 명령이 git이 아니라고 보일 수 없다는 것과, 워크트리 세션의 git은 그 워크트리만 겨눠야 한다는 것이었다(일지 2026-10-06-08·2026-10-07-02). 거부된 것은 `git` 복합 명령(파이프·서브셸·`$(…)`), 주 체크아웃을 당기는 `git -C <루트> pull`(일지 2026-10-02-06·2026-10-03-02), heredoc·반복문·`$@`가 든 복합 명령, 따옴표 인자나 `$TEMP` 변수가 든 단일 명령이다(일지 2026-10-06-12·15). 같은 세션에서 따옴표 인자를 넘긴 `uv run python -c`와 `sed -i`는 지나갔다(일지 2026-10-07-02).
- **바꾼 rules와 스킬, 서브에이전트는 새 `claude -p` 세션에서 불러 본다(작업 규약 3의 하네스 확인, 대기열 63).** 바꾼 세션은 증거가 되지 못한다. 그 세션은 바꾼 본문을 이미 알고, 새로 만든 규칙은 그것을 만든 세션에서 `paths`에 맞는 파일을 Read로 열어도 실리지 않았고, `EnterWorktree`로 옮겨 온 세션은 주 체크아웃의 스킬을 실었다(둘 다 손으로 봤다, 일지 2026-09-30-01·2026-10-01-03. 그 뒤 워크트리 사본이 끼어드는 계기는 아래 모드 표 항목).
  - **`tools/canary.py`로 돌린다(대기열 129).** 명세 TOML 하나(질문, 카나리아, 실험군·대조군 갈래)를 받아 `uv run python tools/canary.py <명세> <출력 디렉터리>` 한 번으로 모든 회차를 돌고, 회차마다 stream-json 원본을 남긴다. 규칙, 스킬, 서브에이전트(`.claude/agents/*.md`, 대기열 153)를 본다. 명세의 모양과 판정의 원천은 그 도구의 독스트링이다. 근거로 드는 명세는 프로브 자리에 커밋하고(예: `.scratch/harness/probes/canary/`), 최신 결과는 그 명세의 머리 주석에 `# 최신 결과:` 줄로 적는다(결과, 날짜, 자리, claude 판, 옛 판 대조군이면 러너가 그 갈래에 찍은 커밋, 일지). 러너가 커밋을 찍지 않던 동안에는 실행 사이에 주 체크아웃이 당겨진 것을 모른 채 대조군 커밋을 틀리게 적었다(대기열 219). 그 갈래의 커밋이 `모름`이거나, 도는 동안 움직였거나 움직였는지 모른다고 찍혔으면, 회차가 어느 판을 읽었는지 모르므로 결과로 적지 않고 다시 돌린다(`모름`이면 그 체크아웃의 git을 먼저 고친다). 프로브 README의 한 행에 명세마다의 결과를 이어 적던 동안에는, 명세를 더한 PR과 그 행을 함께 고친 다른 PR이 나란히 돌아 그 행에서 병합 충돌이 세 번 났다(대기열 196). 워크트리 세션의 가드(위 항목)가 회차를 묶은 반복문을 거부해(대기열 120), 셸에는 이 단순 명령 하나만 친다.
  - **명령은 도구를 좁힌다.** 러너가 짓는 명령은 `claude -p --setting-sources project,local --strict-mcp-config --model sonnet --output-format stream-json --verbose`에 도구를 좁힌 것이고, 질문은 stdin으로 간다. 스킬은 `--tools Skill`, 규칙은 `--tools Read`다. 서브에이전트는 `--tools Agent`에 그 정의의 도구를 더한다. `--tools Agent` 하나로 좁힌 본 세션에서는 서브에이전트가 도구 0개로 거부됐고, 정의의 도구 넷을 더하자 돌았다(claude 2.1.292에서 손으로 본 두 구성, 일지 2026-10-12-02). 그래서 본 세션도 그 도구를 갖고, 러너는 본 세션이 그 서브에이전트를 부르는 Agent 밖의 도구를 쓰지 않았는지 본다. `--tools`는 가변 인자라 뒤에 둔 질문까지 도구 이름으로 삼킨다(아래 프로브의 첫 판에서 질문이 사라져 `Input must be provided` 오류가 났다). `--allowed-tools Skill`로 띄운 세션에서도 Read가 승인 없이 돌아 바뀐 스킬 파일을 직접 읽었고, 그러면 답이 스킬이 실려서 나온 것인지 가를 수 없다. `--tools Skill`로 좁힌 세션에는 Read가 없었다(손으로 봤다, 일지 2026-10-01-05).
  - **규칙 명령에 읽기 거부를 두지 않는다(대기열 127).** 규칙 명령에 `.claude/` 읽기 거부(`--disallowed-tools 'Read(./.claude/**)'`)를 더하면 claude 2.1.291에서 `paths` 규칙의 로드까지 막혀, 실험군과 대조군이 모두 "없음"이었다(손으로 봤다, 일지 2026-10-06-15·2026-10-07-01). 2.1.286에서는 같은 명령으로 규칙이 실렸으니(일지 2026-10-06-06) 판이 바뀌며 생긴 회귀로 보인다. 판의 변경 기록은 읽지 않았다. 그래서 거부를 두지 않고, 트랜스크립트의 Read 호출이 대상 파일 하나뿐인지를 본다.
  - **커넥터와 사용자 설정을 뺀다.** init 이벤트에서 `tools`가 좁힌 도구뿐이고 `mcp_servers`가 비었는지도 러너가 본다. `--tools`는 내장 도구만 좁히고, 로그인한 계정의 claude.ai 커넥터는 `--strict-mcp-config`가 뺀다. claude 2.1.286에서 `--tools Skill` 세션의 init에 커넥터 셋(Atlassian, Docs, Slack)과 그 도구 76개가 실렸고, 이 플래그를 더하자 `tools`가 `Skill` 하나, `mcp_servers`가 0이었으며 스킬 목록(36개, `code-review` 포함)은 그대로였다. 환경 변수 `ENABLE_CLAUDEAI_MCP_SERVERS=false`로도 빠졌다(`.scratch/harness/probes/canary_init/`, 대기열 85). `--setting-sources project,local`은 실을 설정 원천(`user`, `project`, `local`)에서 사용자 설정을 뺀다(claude 2.1.286의 `--help`를 읽었다). 이 플래그 없이 돈 탐침에는 사용자 전역 Stop 훅이 돌아 Slack 알림을 보냈다(일지 2026-09-29-03).
  - **질문은 카나리아다.** 바뀐 본문을 드러내지 않고, 그 본문에만 있는 것(낱말, 경로, 항목 수)을 그대로 옮기게 하며, 없으면 "없음"이라 답하게 한다. 질문은 낱말만이 아니라 그 낱말이 놓일 자리(칸, 절)까지 묻는다. next-session 카나리아는 칸을 짚은 질문 덕에 문장의 자리를 잘못 읽은 것을 잡았다(일지 2026-10-06-15, 대기열 127). 다만 자리는 답이 놓일 곳을 확인하려고 묻는 것이고, 옮길 문단은 자리가 아니라 내용으로 고른다. `bug_perf_review_budget.toml`의 첫 판은 옮길 문단을 자리("보고 형식 절 제목 바로 아래 첫 문단")로 고르고 그 자리가 다른 문장으로 시작하면 "없음"이라 하게 했다. 문단을 고친 뒤 다시 돌리자 정의가 실린 실험군 한 회차가 "없음"이라 답했다. 문단을 내용(턴 한도를 말하는 문단)으로 고르자 통과 4였다(일지 2026-10-12-14, 대기열 191). 표본은 그 한 회차이고, 그 조건이 답을 흔들었다는 것은 어림이다.
  - **대조군을 하나 둔다.** 규칙은 `paths` 밖의 파일을 Read하게 한다. 스킬과 서브에이전트는 바뀌기 전 사본(주 체크아웃, 또는 바뀌기 전 커밋)에서 시작한 세션에 같은 질문을 던진다. 커밋은 러너에 `--control-commit <커밋>`으로 주면 러너가 시스템 임시 디렉터리 아래 임시 워크트리로 꺼내 대조군으로 돌리고 걷는다. 대조군이 주 체크아웃인 명세는 그 PR이 병합되면 대조군이 새 사본이라, 다시 돌릴 때 옛 판의 커밋을 이 인자로 준다. 이 인자가 없던 동안에는 옛 판을 손으로 꺼내고 대조군만 바꾼 명세 사본을 스크래치에 지었다(대기열 233). 대조군이 "없음"이나 옛 줄을 답해야 질문이 답을 흘리지 않은 것이다. 세션에는 체크아웃의 `CLAUDE.md`와 함께 상위 폴더의 `CLAUDE.md`도 실린다. 다만 주 체크아웃 안의 연결된 워크트리에서 띄운 세션에는 주 체크아웃의 것이 실리지 않았고 그 위 폴더의 것은 실렸다(`.scratch/harness/probes/claude_md_parent.py`로 쟀다, claude 2.1.292). 그래서 `.claude/worktrees/` 안의 갈래에는 주 체크아웃의 `CLAUDE.md`가 섞이지 않는다. 러너가 `--control-commit`으로 꺼내는 옛 판은 시스템 임시 디렉터리 아래라 주 체크아웃이 상위 폴더가 아니다. 러너는 갈래마다 함께 실리는 상위 폴더의 `CLAUDE.md`에 카나리아가 있으면 돌리지 않는다(대기열 171).
  - **실험군이 "없음"이면 카나리아는 실패다(대기열 127).** 대조군과 같은 답이면 확인이 빈 것이지 통과가 아니다. 통과했어도 러너가 `"없음" 섞임`으로 표시한 회차는 찍힌 답을 읽는다. 한 물음에 "없음"이라 답했으면 질문이 묻는 자리나 본문 문장의 자리를 고쳐 다시 돌린다(일지 2026-10-12-35·2026-10-13-06, 대기열 212).
  - **계정 한도로 막힌 회차는 측정이 아니다(대기열 165).** 자식 `claude -p`가 계정의 주간 사용량 한도에 걸리면 원본의 `rate_limit_event`가 `rateLimitType: seven_day`, `status: rejected`이고 결과가 `usage_limit_reached`다. 러너는 한도의 종류를 가리지 않고 거절(`rejected`)이나 `usage_limit_reached`가 찍혔는데 답을 내지 못한 회차를 판정하지 않고 `[측정 아님]`으로 따로 세어 풀리는 시각을 찍고, 측정된 실패가 없으면 종료 코드 4로 끝난다(대기열 338, 판정과 종료 코드는 `tools/canary.py` 독스트링이 원천). 통과도 실패도 아니고, 풀리기를 기다리지 않는다. 사전 확인(아래 `--preflight`)만 돌리고 병합하며, 그 하네스는 카나리아가 통과할 때까지 확인되지 않은 것이다. 돌릴 명세와 풀리는 시각은 일지의 "다음"에, 병합 전에 돌지 못했다는 것은 그 하네스를 닫는 대기열 행의 닫힘 표지에 적는다. 풀린 뒤의 첫 세션이 짧은 질문 하나로 풀렸는지 보고 그 명세를 돌린다. 그 질문도 사용자 설정을 빼고(`claude -p --setting-sources project,local --strict-mcp-config`) 질문은 파일에 써서 `<`로 넘긴다. 맨 `claude -p`에는 사용자 전역 Stop 훅이 실리고(위 커넥터 항목), 따옴표 인자는 워크트리 가드가 거부할 수 있다. 병합 뒤라 대조군은 바뀌기 전 커밋이다(위 대조군 항목의 `--control-commit`). PR #172가 미룬 넷이 이 길로 다음 날 모두 통과 4였다(PR #175, 일지 2026-10-12-02). 경위는 ADR 0006의 2026-10-12 이력.
  - **스킬은 세션을 시작한 체크아웃의 사본이 실린다(손으로 봤다, 일지 2026-10-01-03·05).** 바뀐 사본이 있는 체크아웃에서 시작한다. 모델이 부르지 못하는 스킬(`disable-model-invocation: true`)은 프롬프트 머리에 슬래시 명령으로 넣는다(일지 2026-10-01-03). 그 길을 러너에 적는 법은 러너의 독스트링에 있다.
  - **Sonnet으로 세 번 묻는다.** 실린 규칙의 카나리아 하나(SWR 훅)에 Haiku는 세 번 중 두 번 "없음"이라 답했고, Sonnet은 세 번 다 답했다(손으로 봤다, 일지 2026-09-30-02).
  - **한 번 통과한 뒤 문구만 고쳤으면 사전 확인으로 갈음한다(대기열 184).** `uv run python tools/canary.py --preflight <명세> [<명세> ...]`는 `claude`를 띄우지 않고 돌리기 전의 확인(러너 독스트링의 판정 목록 아래 문단)만 돈다. 커밋 대조군으로 통과한 명세는 `--preflight --control-commit <커밋> <명세>`로 같은 커밋을 꺼내 본다. 빼면 그 명세의 대조군 체크아웃이 없거나 새 사본이라 막힌다. 갈음하려면 넷이 모두 맞아야 한다. 같은 PR 안에서 같은 claude 판으로 그 명세가 통과했다. 그 뒤 고친 곳이 원천 파일의 본문이고 머리말은 하나도 고치지 않았다. 명세에서 고친 칸은 `expect`뿐이다(머리 주석의 `# 최신 결과:` 줄은 칸이 아니다). 카나리아가 질문이 묻는 자리(절, 칸)에 남았다. `expect`를 열어 둔 것은 문구를 고치면 그 문구에서 고른 카나리아도 함께 바뀌기 때문이다. 일지 2026-10-12-09의 재확인에도 셀프 리뷰가 카나리아 조각을 바꾼 회차가 들었다(그 일지의 셀프 리뷰 절). 하나라도 어긋나면 다시 돌린다. 판이 바뀌며 규칙의 로드가 조용히 막힌 일이 있었고(위 읽기 거부 항목), 실리는지는 앞선 통과가 근거일 뿐 이 모드는 재지 않는다(러너 독스트링의 못 보는 것). 일지에는 사전 확인으로 갈음했다고 적고, 그 명세의 `# 최신 결과:` 줄은 마지막으로 실제 돌린 결과를 지우지 않은 채 갈음한 날짜와 일지를 뒤에 덧붙인다. 덮어쓰면 그 줄만 읽는 사람이 갈음을 실제로 돌린 결과로 읽는다. 이 모드가 없을 때는 문구를 고칠 때마다 다시 돌려, `claude -p` 40번 가운데 28번이 재확인이었다(일지 2026-10-12-09).
- **워크트리 세션에 실리는 것은 세션이 어떻게 그 폴더에 왔느냐에 따라 다르다.** 세션은 어느 모드인지 알 길이 없어, 워크트리에서 고친 하네스는 위 항목의 `claude -p`로 확인한다. 아래 표는 2026-10-05 워크트리 감사 서브에이전트가 손으로 본 것과 일지 2026-10-02-01·2026-10-02-02, `tools/launch_hook.py` 독스트링, `.scratch/harness/probes/claude_md_parent.py`·`enter_worktree_loading.py`, 워크트리를 실험군으로 돌린 서브에이전트 카나리아(`canary/bug_perf_review_budget.toml`의 `# 최신 결과:` 줄)를 모은 것이다.

  - **`EnterWorktree`로 들어온 세션에 워크트리 사본이 끼어드는 계기는 주 체크아웃의 변경이다(대기열 189).** 처음에는 스킬도 서브에이전트 정의도 주 체크아웃 사본이다. 주 체크아웃의 `.claude/skills/`·`.claude/agents/` 아래 파일이 바뀌자 스킬 목록에 워크트리 사본이 경로를 단 이름(`.claude/worktrees/<이름>:<스킬>`)으로 더해지고 서브에이전트 정의가 워크트리 사본으로 바뀌었다. 다음 메시지, 세션의 Edit, 바깥 편집으로는 바뀌지 않았다. 갈래와 결과, 재지 않은 것은 `.scratch/harness/probes/enter_worktree_loading.py`의 README 행과 독스트링이 원천이고(claude CLI 2.1.296), 실행 파일을 읽은 것과 앱 세션의 어림은 일지 2026-10-13-59다. 데스크톱 앱의 세션은 앱이 묶은 판으로 돌아 이 측정 밖이다. 그래서 세션은 어느 사본을 실었는지 미리 알 수 없고, 워크트리에서 고친 스킬은 Read로 디스크의 `SKILL.md`를 열어 따른다. 경로를 단 이름은 끼어든 때의 사본이라 그 뒤의 편집이 실린다고 기대지 않는다. 서브에이전트가 어느 사본으로 돌았는지는 그 보고에 판을 가를 표지가 있을 때만 안다. claude CLI 2.1.303에서 다시 재니 끼어들 때 바뀌지 않은 것까지 그 워크트리의 스킬이 모두 더해졌다. 워크트리가 `.gitignore`에 든 이 저장소의 모양에서는 워크트리 파일을 읽기만 하거나 워크트리에서 시작한 세션에서는 끼지 않았다(`.gitignore`에 없으면 주 체크아웃 세션이 읽기만 해도 끼었다. `.scratch/harness/probes/worktree_skill_listing.py`, 대기열 274). 더해진 목록이 세션이 끝날 때까지 실린다고 보고(어림), `tools/hook_worktree_skill_overrides.py`가 `EnterWorktree` 뒤에 그 워크트리의 경로를 단 이름을 주 체크아웃의 `.claude/settings.local.json` `skillOverrides`에 `"off"`로 적는다. 그 훅을 등록한 세션에서는 바깥 변경 뒤에도 훅이 적은 이름이 목록에 붙지 않았고, 훅이 적은 뒤에 새로 생긴 스킬은 붙었다(같은 프로브. 붙는 예외는 그 훅의 못 보는 것). 이것은 CLI에서 `git worktree add`로 만든 워크트리에 `EnterWorktree(path)`로 들어간 측정이다. 이 PC의 데스크톱 앱(Claude Code 2.1.299)에서 `EnterWorktree(name)`으로 워크트리를 만들며 들어간 세션은 훅이 키를 적었는데도 주 체크아웃의 스킬 파일이 바뀐 뒤 목록에 실리는 그 이름이 모두 붙었고, 같은 날 다른 앱 세션이 그 워크트리에 `EnterWorktree(path)`로 다시 들어간 둘째 회차도 같았다(`.scratch/harness/probes/worktree_overrides_app.py`). 그래서 갈린 것은 들어가는 꼴(`name`과 `path`)이 아니다. 갈린 것이 앱과 CLI(CLI의 측정은 클라우드 컨테이너의 2.1.303이라 OS와 판도 다르다)인지, 워크트리를 만든 길(첫 회차의 `EnterWorktree(name)`은 워크트리에 local 사본을 남겼고, git이 추적하지 않는 파일이라 `git worktree add`는 남기지 않는다)인지, 다른 까닭인지는 가르지 않았다(후보는 그 훅의 못 보는 것). 그래서 앱 세션에서는 경로를 단 이름이 여전히 끼어든다고 본다. 이름이 꺼진 세션에서는 끈 이름을 Skill 도구로 부를 수 없어, 목록이 그 이름과 함께 싣던 안내(일하는 파일이 든 폴더의 사본을 부른다, 공식 문서 skills)도 사라지고 Skill 호출은 주 체크아웃에 실린 사본으로 돈다. 워크트리에서 고친 스킬은 위 문장대로 Read로 연다. 서브에이전트 정의가 바뀌는 것은 그대로다.
  - 훅의 `.venv`가 비어 있으면(`uv run --no-sync`가 빈 환경을 만든다, 감사 서브에이전트가 손으로 봤다) ruff를 띄우는 `hook_ruff_line_width` 하나만 침묵한다. 판정은 pre-commit과 게이트에 남는다.
  - `settings.local.json`은 추적하지 않아 손으로 판 워크트리에는 없다. 가드는 `settings.json`에만 두고 local에는 allow만 둔다(`tools/check_instructions.py`가 local의 가드를 빨갛게 한다). 워크트리 세션에서 권한 프롬프트가 늘면 local이 없어서다.
- **세션 파일은 폴더 키로 갈린다.** `~/.claude/projects/` 아래 트랜스크립트는 세션을 시작한 폴더의 키에 쌓이고, `EnterWorktree`가 워크트리 키로 옮긴다. 같은 세션 id의 사본이 두 키에 함께 있고 낡은 쪽이 워크트리 키인 것을 감사 서브에이전트가 일곱 쌍 손으로 봤다. 어느 때 갈리는지는 재지 않았다. 워크플로는 스크립트가 작업 폴더 키에, 상태와 결과가 주 키에 놓였다(2026-10-05 이 세션에서 손으로 봤다). 자동 메모리는 주 키 한 곳이다. 세션 파일을 읽는 탐침과 훅은 키 둘을 다 보거나 메시지 id로 겹침을 거른다.
