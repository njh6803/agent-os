# 2026-11-16 (17:05) 위젯 관리 화면의 명세 (portal-admin)

이 세션은 사람이 지시문을 손으로 붙여 넣어 열었다. 지시문의 "이어받을 상태"에 따르면 앞 세션(`docs/portal-admin-screens`)의 인계 열기(`open_session.ps1 -Action send`)가 자동 모드 분류기에 다시 거부되었고(사유 "Undermining Oversight") 그래서 open-session이 이 세션을 열지 못했다. 그 일은 앞 세션의 일지(2026-11-16-0025)가 병합된 뒤에 나서 거기 적히지 않았다(대기열 72). 대기열 `open-session-send-denied-despite-allow-rule`에 이 회차(12회차)를 더할 몫이 이 세션에 남아 있다.

세션 제목 `docs/portal-admin-spec`. 브랜치 `docs/portal-admin-spec`, 워크트리 `.claude/worktrees/portal-admin-spec`. 모델 Fable 5.2.

## tidy-checkouts

첫 턴에 제목을 브랜치 이름으로 바꾸고(앱이 지은 제목 "Portal-admin 명세"였고 묻지 않고 바뀌었다) `tidy-checkouts`를 돌았다. 아래는 명령의 출력을 읽은 것이다.

- 주 체크아웃은 dev였고 깨끗했으며(`git status --porcelain`이 빈 출력) 원격에 없는 커밋이 없어(`git rev-list --count origin/dev..HEAD`가 0) `git merge --ff-only --no-overwrite-ignore origin/dev`로 `716e51d25`에서 `02dcfe97d`(PR 590의 병합)로 당겼다. 당긴 커밋의 파일 목록에 `.claude/skills/tidy-checkouts/`는 없었다(merge의 출력).
- `judge`는 워크트리 스물여덟을 모두 `남긴다`로 냈다. 까닭은 바뀐 파일, 쥔 프로세스, 병합된 PR 없음, 앱의 표지, 다시 만들 수 없는 무시된 항목이었다. `지운다`와 `끝낸다`는 없었다.
- `empty-trash`는 휴지통의 `node_modules` 아홉을 비우지 못하고 종료 1로 끝났다. 모두 `esbuild.exe`에서 `WinError 5`였고 도구가 든 쥔 프로세스는 `node.exe`(pid 36848)와 `esbuild.exe` 둘(pid 15344, 2116)이다.

그 뒤 `EnterWorktree`(name `portal-admin-spec`)로 들어와 `git switch -c docs/portal-admin-spec`로 이 브랜치를 땄다. HEAD는 `02dcfe97d`이고 `origin/dev`와 같다(`git rev-parse HEAD origin/dev`).

## 읽은 것과 찾은 것

- 선행 기능 셋(widget-admin-server, admin-login, widget-login-state)은 `.scratch/plan.md`에서 모두 `todo`이고 `spec.md`가 dev에 없다(`ls`로 봤다). widget-login-state의 명세만 위 워크트리에 초안으로 있다.
- 그 초안(병합 전, 기준 커밋 `59536371f`)이 이 기능에 넘기는 것을 Out of Scope에서 읽었다. 모양 값 셋(로그인 전의 모양, 고지 전문을 보이는 법, 예시 질문의 모양)을 등록하기로 하면 "표의 칸, 답의 칸, 위젯이 답에서 그 값을 읽는 줄, 위젯 전체의 시험과 e2e의 사례를 portal-admin이 더한다"가 하나이고, 저장 경로에 넘기는 다섯이 있다. 문의 링크의 주소에도 로그인 주소와 같은 형식 검사를 건다, 사용자 정보 자리와 쿼리를 받지 않기로 하면 위젯의 검사에도 같은 규칙을 더한다, 예시 질문은 넷까지이고 질문마다 100자까지 받는다, 위젯 테스트 페이지가 담는 사이트의 빈 고지를 어떻게 다룰지 정한다, 사이트 고르기의 글이 사이트의 이름으로 바뀐 것을 다시 본다. 그 초안은 위젯이 네 모양 값의 열두 모양을 모두 그리게 정했고(사용자가 "열두 모양을 모두 이번에"를 골랐다고 적는다), ADR 0064에 이력 "시험할 때 받는 http 주소를 호스트 이름이 .localhost로 끝나는 것까지 넓힌다"를 더한다. 병합 전이라 바뀔 수 있다.
- 화면 문서(`screens-prompt.md`, widget-login-state의 디자인 `README.md`)와 기능 계획 넷은 서브에이전트가 읽어 칸과 동작과 제안 표시를 정리했다(이 세션은 그 보고를 받았고 원문과 하나씩 대 보지는 않았다). 보고가 든 어긋난 자리는 넷이다. 화면 모양 칸의 수(시작 프롬프트는 셋, 그 뒤 예시 질문의 모양이 넷째 후보가 됐다), 문의 링크(시작 프롬프트는 글과 주소 두 칸, 위젯 그림은 글을 "문의하기"로 고정), 예시 질문의 상한(시작 프롬프트의 가정은 넷), 로그인 전 미리보기의 예시 질문(시작 프롬프트는 보이고 위젯 화면 작업의 제안은 보이지 않는다).
- 코드의 지금 상태는 서브에이전트가 읽어 보고했다(읽기만 했다). `web/apps/`는 `admin`, `portal`, `widget` 셋이고 위젯 관리 서버와 위젯 관리 화면의 코드, 운영자 계정과 로그인 쿠키의 코드, 위젯이 위젯 설정을 받아 오는 코드는 아직 없다. `openapi.json`에 로그인과 "지금 누구인지"와 "갱신" 경로가 없다. 쿠키 프로브 `.scratch/admin-login/probes/cookie_relay/`는 Chromium에서 같은 호스트의 다른 포트로 Strict 쿠키가 실리는 것과 Next 중계가 `Set-Cookie`를 바꾸지 않는 것까지 쟀고, 서버가 쿠키를 다른 서버에 전하는 흐름은 재지 않았다(그 프로브의 README를 서브에이전트가 읽었다).
- 웹 편집 확인(`ui-design` 스킬의 "웹 편집 확인")은 서브에이전트가 돌았다. 화면 아티팩트의 화면 파일 스물하나가 HEAD(`02dcfe97d`)의 커밋된 판과 모두 같았다(바이트까지 같은 것 여섯, 줄바꿈만 다른 것 열다섯, 내용이 다른 것 0). 아티팩트의 판은 `1794816599-9891`이었다.
- 이 세션이 원문에 직접 대 본 것: 화면 `README.md` 17~31행(새 아이콘 셋, 작은 더함과 뺌, PR 583과 다른 자리, 탐색용 가정), `screens-prompt.md` "고른 뒤"(135~147행), 기능 계획 전체, widget-login-state 초안 173~181행과 376~392행, `web/packages/ui/src/components/atoms/Icon.stories.tsx` 71행(`ICON_NAMES`의 길이 17), `web/apps/portal/server/handler.ts`의 고지 확인 끝점(확인한 기록은 익명 식별자 쿠키가 있는지이고 `cookie-policy.ts`의 `COOKIE_LIFETIME_DAYS`가 30이다), ADR 0061 16행("고지 확인을 기록하는 쪽은 지금처럼 사이트다").
- `git fetch origin` 뒤에도 `origin/dev`는 `02dcfe97d`이고 열린 PR은 591 하나다. widget-login-state의 명세는 아직 병합되지 않았다.

## 사용자에게 물은 것과 답

설계 문서(ADR 0064·0065, 기능 계획, 화면 `README.md`)가 명세 전에 사람에게 묻게 한 것 셋과 to-spec 2단계의 시험 이음매 확인을 선택 화면 하나로 올렸다. 선택 화면은 훅(`hook_choice_facts`)이 두 번 막았고(둘째는 질문 문장을 고쳐서다) 그사이 위 "원문에 직접 대 본 것"을 대 보았다. 고지 확인 덮개의 단추 이름을 "확인"에서 "확인하고 질문하기"로 고쳤다(ADR 0061 16행).

1. 예시 질문의 모양. 물은 것: 위젯 첫 화면의 예시 질문을 어떤 모양으로 보일지(세로 목록, 줄을 바꿔 감기는 알약, 입력창 위 띠)를 0.1 판의 위젯 관리 화면에서 운영자가 사이트마다 고르게 할지. 기능 계획 26행이 명세 전에 묻게 했다.

   > 사용자: "0.1 판에 고르는 칸을 넣기 (Recommended)" — 설명: '글' 탭의 예시 질문 칸 아래에 작은 그림 셋 가운데 하나를 고르는 칸이 하나 늘고, 고르면 저장 전의 미리보기와 저장 뒤의 실제 위젯에서 예시 질문이 그 모양으로 바뀝니다. 앞서 로그인 전 모양과 고지 전문을 보이는 법을 넣으신 것과 같은 방식입니다. 치르는 값은 ADR 0064에 이력 한 건(초안을 보여 드리고 승인을 받습니다)과, 이 기능이 저장하고 전달하고 시험할 값이 하나 느는 것입니다.

   고르지 않은 안은 "0.1 판 뒤로 미루기"였다. ADR 0064에 이력을 쓰고 셀프 리뷰를 반영한 뒤에 승인을 받는다.

2. 고지 재확인. 물은 것: 운영자가 위젯 테스트 페이지에 담긴 사이트의 고지 글을 고쳐 저장했을 때, 그 고지를 이미 확인한 브라우저에 고지 확인 덮개를 다시 띄울지. 기능 계획 22행의 "PR 직전 리뷰가 낸 빈 자리 넷"의 넷째다.

   > 사용자: "다시 띄우지 않기 (Recommended)" — 설명: 지금과 같습니다. 한 번 확인한 브라우저는 쿠키가 남아 있는 30일 동안 덮개를 다시 보지 않고, 고친 글은 위젯의 고지 줄을 눌러 전문을 열면 보입니다. 위젯 테스트 페이지는 로그인한 사람만 여는 시험용 페이지가 되므로(ADR 0065) 이 정도로 충분하다고 봅니다. 치르는 값은 중요한 문장을 더해도 이미 확인한 사람은 스스로 열어 보기 전까지 모른다는 것입니다.

   고르지 않은 안은 "글이 바뀌면 다시 띄우기"와 "저장할 때 운영자가 고르기"였다.

3. 새 아이콘. 물은 것: 확정한 화면이 디자인 시스템의 아이콘 열일곱 밖의 셋(external-link, chevrons-up-down, chevron-down)을 그려 썼는데 디자인 시스템에 더할지. `screens-prompt.md` "고른 뒤" 2가 새 아이콘을 명세 전에 묻게 했다.

   > 사용자: "셋 다 더하기 (Recommended)" — 설명: 디자인 시스템의 아이콘이 열일곱에서 스물로 늘고, 화면은 그린 그대로 섭니다. 다른 화면도 같은 아이콘을 쓸 수 있게 됩니다. 치르는 값은 디자인 시스템 패키지의 아이콘 목록과 그 수를 세는 시험, 아이콘 전체를 찍은 사진 비교의 기준 그림, 디자인 시스템 아티팩트를 이 기능의 티켓 하나가 함께 고치는 것입니다.

   고르지 않은 안은 "더하지 않고 글자로만 두기"였다.

4. 시험 이음매(to-spec 2단계). 물은 것: 이 기능이 맞게 지어졌는지를 어느 자리에서 시험할지.

   > 사용자: "브라우저로 한 번 끝까지, 규칙은 서버 시험 (Recommended)" — 설명: 시험이 진짜 서버들과 데이터베이스를 모두 띄우고 브라우저로 '관리 화면에 로그인, 위젯 관리 화면에서 사이트 등록과 고침, 미리보기가 바뀜, 저장, 위젯 테스트 페이지의 위젯이 바뀜'을 한 번 밟습니다. 잘못된 주소, 겹치는 이름, 로그인하지 않은 요청을 거절하는 규칙들은 위젯 관리 서버의 주소를 직접 부르는 빠른 시험이 봅니다. 위젯 테스트 페이지 서버와 화면 부품은 지금 쓰는 시험 자리(요청을 받아 응답을 내는 함수, 스토리와 사진 비교)를 그대로 씁니다. 치르는 값은 CI에 브라우저 시험 잡이 하나 늘고 그 잡이 Docker로 데이터베이스를 띄우는 것입니다(잡을 새로 둘지 있는 잡에 얹을지는 명세에서 정합니다).

   고르지 않은 안은 "서버와 화면을 따로만 시험"과 "거절 규칙까지 모두 브라우저로"였다.

묻지 않고 명세가 정하기로 한 것도 있다. 주소의 사용자 정보 자리(`user:pw@`)와 쿼리를 받을지는 기능 계획 22행이 "명세가 먼저 확인하는 것"에 넣었고 ADR 0064 Consequences "명세가 짓는 것"이 명세에 맡겼으므로, 명세가 정하고 "명세가 정했다"로 표시한다. 화면의 탐색용 가정과 제안(`README.md` 26~31행)도 `screens-prompt.md` "고른 뒤" 2대로 명세가 결정으로 바꾼다.

## 용어

- 사이트마다 저장할 때 하나씩 오르는 수를 처음에 "판"이라 썼다가 "저장 번호"로 바꿨다. `CONTEXT.md`에 제품 판, 마지막 좋은 판, 헌법 판, 비워 둔 판이 있어 "판"이 이미 다른 뜻으로 쓰인다(`domain-modeling` 스킬을 부르고 용어집을 읽었다). 명세 여덟 곳과 portal-login-admin, widget-admin-server의 기능 계획에 쓴 말을 함께 고쳤다. "판정", "판 표시", "0.1 판", "옛 판의 파일"은 다른 뜻이라 그대로다.
- 용어집에는 아직 아무것도 더하지 않았다. 후보는 "바꾼 기록"이고, 코드가 드는 구현 티켓이 올린다.

## 나란히 열린 PR 593과 겹치는 자리

`git fetch origin` 뒤 `gh pr list --state open`이 PR 593(`docs/widget-login-state-spec-2`, widget-login-state의 명세)과 PR 592(release-image 티켓 09)를 냈다. `origin/dev`는 `aae33d2d1`(PR 591)까지 나갔다. 아래는 `gh pr diff 593 --name-only`와 `git diff --word-diff=porcelain origin/dev origin/docs/widget-login-state-spec-2`의 출력을 읽은 것이다.

- PR 593이 이 브랜치와 함께 고친 파일은 셋이다. `.scratch/portal-login/plan.md`, `.scratch/widget-admin-server/plan.md`, ADR 0064다. 그 PR이 먼저 병합되면 `origin/dev`를 합칠 때 셋 모두 충돌이 난다. 기능 계획 둘은 양쪽이 더한 문단을 모두 남기고, ADR 0064는 결정 "주소의 검사"의 포인터를 이어 달고 이력은 그 PR의 것을 앞에 둔다.
- 그 PR은 ADR 0064에 이력 "시험할 때 받는 http 주소를 호스트 이름이 .localhost로 끝나는 것까지 넓힌다"를 더하고, 호스트 이름을 이름 전체로 견주는 것도 그 이력에 적는다. 그래서 이 브랜치의 주소 이력은 "셋을 더한다"에서 호스트 이름 견주기를 빼 "둘을 더한다"로 고쳤다.
- 그 PR은 widget-admin-server의 기능 계획에 "예시 질문의 모양을 뺀 열아홉 항목이 답에 실린다"를 적는다. 이 브랜치가 같은 기능 계획에 적은 빈 자리(로그인 전 모양과 고지 전문을 보이는 법을 표와 답에 누가 넣는지)의 답이 되므로, 합칠 때 그 항목을 지운다.
- 그 PR의 명세가 이 기능에 넘긴 다섯(문의 링크의 검사, 사용자 정보 자리의 규칙을 위젯의 검사에 더하기, 예시 질문 넷과 100자, 빈 고지, 사이트 고르기의 글)은 초안에서 읽은 것과 같고, 이 명세가 인용한 절 이름 셋("위젯 설정의 항목과 앞서는 차례", "주소의 검사", "위젯 테스트 페이지")도 그 PR의 명세에 그대로 있다.

## 명세가 먼저 확인한 것 셋

ADR 0064와 ADR 0065의 Consequences "재지 않은 것"이 이 명세에 넘긴 물음 셋을 서브에이전트 셋에 나눠 맡겼다. 결과 문서는 본 세션이 직접 읽어 보고와 대조한 뒤에 명세로 옮겼다. 근거의 종류는 프로브마다 다르다.

- **로그인 쿠키를 전하는 흐름**(`.scratch/portal-admin/probes/login_relay/`, 프로브가 다시 낸다). Agent OS와 위젯 관리 서버와 위젯 테스트 페이지의 서버가 대역이고, 관리 화면 앱의 Next 중계와 Chromium은 실제 것이다. 결과에서 명세의 결정이 된 것은 넷이다. 서버는 `Cookie` 머리만 전한다(브라우저의 머리를 그대로 전하면 주소창 이동과 다른 포트의 링크 이동이 403이었다). `Set-Cookie`는 줄마다 옮긴다(한 값으로 합치면 갱신용 번호 쿠키가 옛 값으로 남았다). 갱신은 화면이 부른다(서버가 스스로 갱신하는 꼴은 유예가 없을 때 탭 하나의 요청 넷이 같은 번호로 갱신을 불러 로그인이 끊겼다). 포트가 다른 탭 둘의 동시 갱신은 유예 없이는 끊기므로 admin-login의 유예에 기대고, 그 유예에 바라는 것 하나를 admin-login의 기능 계획에 적었다.
- **설정을 받아 오는 때**(`.scratch/portal-admin/probes/settings_fetch/`, 프로브가 다시 낸다). PC 한 대의 루프백에서 PostgreSQL만 컨테이너로 띄워 쟀다. 요청마다 한 번 묻는 것이 부하가 낮을 때 중앙값 3.3~4.8ms를 더했고, 2초 기억은 50ms마다 요청을 보낼 때만 300 가운데 290이 맞았다. 명세는 "기억하지 않는다", "로그인을 먼저 확인하고 들어온 요청에서만 받아 온다", "호출마다 제한 시간 2초(어림)"를 정했다. 제한 시간이 없는 `fetch`는 답하지 않는 상대에 304초와 307초를 기다렸다. 서버가 다른 서버를 부르는 호출의 제한 시간은 세 자리 모두 2초로 맞췄다("로그인 확인"의 3초를 고쳤다).
- **화면 부품을 공유 패키지로 옮기기**(`.scratch/portal-admin/probes/shared_widget_parts/`, 손으로 봤다). 결과를 스스로 다시 내는 프로브가 없고 패치 둘과 보조 스크립트 둘이 남았다(이 문단을 쓴 때의 수다. 아래 넷째 추가 측정 뒤에는 패치 셋과 스크립트 셋이다). 20파일을 `@agent-os/widget-ui`로 옮긴 뒤 `pnpm -C web verify`와 위젯의 사진 비교와 위젯 e2e가 통과했고 정답 사진은 한 장도 바뀌지 않았다. 명세는 "옮기기만 한다", "스토리는 패키지에, 사진은 위젯 앱의 것을 그대로", "패키지는 생성 클라이언트와 swr을 값으로 들이지 않는다", "패키지가 `apps/` 아래를 들이지 않는다"를 정했다. 실험의 산출물은 격리 워크트리에서 이 워크트리로 복사했다.

보고를 받은 뒤 추가로 요청한 측정이 넷이다. 결과는 아래 "추가 측정"에 적는다.

- 위젯 테스트 페이지의 서버(포트 C, Node)에서 화면이 갱신을 부르는 꼴의 동시 갱신. 첫 측정은 이 꼴을 위젯 관리 화면의 길에서만 쟀다.
- `httpx2`. 첫 측정은 dev 전용 `httpx` 0.28.1로 쟀는데, 위젯 관리 서버가 새 의존성 없이 쓸 수 있는 것은 런타임 의존성 `httpx2`다(`pyproject.toml`을 읽었다). 명세가 받아 쓰는 측정은 설치할 판으로 잰다(to-spec 3단계).
- `openapi-fetch`. `web/` 아래의 코드는 전역 `fetch`를 직접 쓰지 못하고 생성 클라이언트로 부른다(`web/eslint.config.mjs`를 읽었다). 첫 측정은 전역 `fetch`와 `node:http`를 직접 불렀다.
- 미리보기를 보기만 하는 그림으로 가렸을 때의 접근성 검사. 공유 패키지 실험에서 관리 화면의 틀 안에 둔 위젯 화면이 `<main>`이 겹쳐 axe 위반 셋을 냈다. 명세의 "미리보기" 절은 미리보기를 화면 읽기 프로그램에 한 줄로 읽히는 그림으로 정해 두었으므로, 그 모양에서도 위반이 나는지를 같은 서브에이전트에 물었다.

### 추가 측정

로그인 쪽 셋은 `.scratch/portal-admin/probes/login_relay/README.md`의 결과 1·2·4·6과 "덤"에서 직접 읽어 명세로 옮겼다.

- **포트 C의 동시 갱신.** 위젯 테스트 페이지의 서버 대역이 전역 `fetch`로 부른 길과 `node:http`로 부른 길 모두, 화면이 갱신을 부르는 꼴에서 유예 없이 같은 번호를 든 갱신이 없었고 로그인이 살아 있었다. 두 길 모두 유예가 없는 회차 하나씩만 쟀다. 유예가 있는 회차와 탭 둘의 회차는 위젯 관리 서버 대역의 길에서만 쟀다는 범위를 명세에 함께 적었다.
- **`httpx2` 2.13.0.** `Cookie`만 실은 요청이 요청 출처 검사를 지났고, `Set-Cookie` 두 줄이 글자 그대로 닿았으며, 화면이 갱신을 부르는 꼴이 유예 없이 살아 있었다. 줄을 꺼내는 호출도 `httpx`와 같다. 새로 드러난 것이 하나 있다. `AsyncClient`가 받은 쿠키를 클라이언트의 통에 기본으로 넣고, `Secure`가 없는 쿠키는 쿠키 없이 온 다음 요청에 실었다. 로그인 쿠키가 실리지 않은 까닭이 `Secure`와 `http://` 주소의 조합이라는 것은 어림이라, 배포의 `https://` 주소에서는 한 운영자의 쿠키가 다른 요청에 실릴 수 있다고 보고 명세가 "클라이언트가 쿠키를 기억하지 않게 짓는다"를 정했다. 받는 도메인이 없는 정책의 통을 준 클라이언트는 통이 비어 있었고 요청이 든 `Cookie`는 그대로 닿았다.
- **`openapi-fetch` 0.17.0.** 대역이 받은 머리가 전역 `fetch`를 직접 부른 길과 같았고, 호출이 돌려준 원래의 응답에서 `Set-Cookie`를 줄마다 꺼낼 수 있었으며, 받은 쿠키를 다음 요청에 싣지 않았고, 제한 시간의 신호를 넘긴 호출이 제한 시간에 `TimeoutError`를 던졌다. 그래서 판정자 규칙(전역 `fetch` 금지)에 예외를 두지 않고 생성 클라이언트로 부른다고 정했다. 판정자가 앱의 `openapi-fetch` 직접 import도 막으므로(`web/eslint.config.mjs`의 `OPENAPI_FETCH_IMPORT`, 코드를 읽었다) 그 클라이언트는 생성 클라이언트 패키지에 더한다. 잰 것은 타입 없는 클라이언트이고 이 길로는 흐름 전체를 재지 않았다는 범위를 명세에 적었고, 그 클라이언트로 지은 서버의 시험이 같은 사례를 다시 보게 했다.
- 같은 측정이 낸 어림 하나를 명세에 더했다. "갱신"에 제한 시간이 걸려 끊기면 Agent OS는 번호를 이미 바꿨는데 새 번호가 브라우저에 닿지 않아, 다음 갱신이 옛 번호를 들고 간다. 유예 안이면 받아 주고 밖이면 로그인이 끊긴다고 보고, 관리 화면이 답을 받지 못했을 때와 같은 일로 다룬다.

선행 기능 계획 둘에 한 줄씩 더했다. admin-login에는 두 경로가 `openapi.json`에 서고 이 기능이 생성 클라이언트 패키지에 서버용 클라이언트를 더한다는 것을, widget-admin-server에는 그 서버의 생성 클라이언트 패키지에 이 기능이 클라이언트 둘을 더한다는 것을 적었다.

넷째인 미리보기를 가리는 법은 `.scratch/portal-admin/probes/shared_widget_parts/README.md`의 "미리보기를 그림으로 가렸을 때"에서 직접 읽어 명세로 옮겼다. 근거의 종류는 손으로 봤다이다. 그 폴더의 `preview_shield.mjs`는 기대와 견줘 종료 코드를 내지만, 패치를 붙인 체크아웃에서 스토리북을 띄워 한 번 돌린 것이라 같은 종류로 적는다.

- **가리지 않은 대조.** 관리 화면의 틀 안에 위젯 화면을 그대로 두면 axe 위반이 셋이었고(`landmark-main-is-top-level`, `landmark-no-duplicate-main`, `landmark-unique`), 실제 Tab이 위젯 안의 조작에 열 번 섰다.
- **갈래 셋.** 감싼 요소에 `inert`와 `aria-hidden="true"`를 함께 준 갈래와 `inert`만 준 갈래는 두 폭(1280×900, 320×640)에서 위반이 없었고, 실제 Tab이 위젯 안에 한 번도 서지 않은 채 미리보기 뒤의 "저장"에 닿았다. `aria-hidden`만 준 갈래는 새 위반 둘(`aria-hidden-focus`, `nested-interactive`)을 냈고 Tab이 위젯 안에 열 번 섰다.
- **명세가 정한 것.** 부품을 고치지 않고 감싼 요소로 가린다. 바깥 요소에 `role="img"`와 이름을, 안쪽 요소에 `inert`와 `aria-hidden="true"`를 함께 준다. `inert`만으로도 브라우저의 접근성 트리는 같았는데 둘을 함께 주는 까닭은, 시험 도구(testing-library)의 역할 찾기가 `inert`를 보지 않아 `inert`만 준 갈래에서 위젯의 단추와 `<main>`을 잡았기 때문이다. 그래서 "역할로 잡히지 않는다"는 스토리 시험이, Tab은 브라우저 시험이 본다(`userEvent.tab()`은 `inert` 앞에서 멈춰 실제 Tab과 다르게 돌았다).
- ADR 0065 결정 "미리보기"가 적은 대가(미리보기와 실제 위젯이 다른 것은 입력뿐이다)는 그대로 선다. 부품의 `<main>`을 입력으로 바꾸는 안은 고르지 않았다.
- **휠과 클릭.** 그 절이 "보지 않은 것"에 적은 둘을 같은 서브에이전트에 더 물었다(같은 README의 "휠과 클릭", 손으로 봤다). 둘을 함께 준 갈래에서 위젯의 단추 자리를 실제 마우스로 눌러도 처리기가 불리지 않았고, 넘친 자리 위에서 휠을 굴려도 그 자리는 그대로인 채 페이지가 200px 굴렀다. 가리지 않은 대조에서는 처리기가 한 번 불리고 휠이 위젯 안을 굴렸다. 긴 안내는 처음에, 긴 대화는 끝에 머물러 반대쪽이 보이지 않았다. 폭 둘에서 한 번씩이고 누른 것은 "새 대화" 하나, 본 스크롤은 휠뿐이다. 고지를 그리는 부품은 아직 없어 긴 안내로 대신했다.
- **그래서 명세가 더 정한 것.** 미리보기 안은 굴려 볼 수 없고, 높이를 넘는 글은 한쪽 끝만 보이며, 나머지는 저장한 뒤 위젯 테스트 페이지에서 본다. 미리보기 아래에 그것을 알리는 도움말 한 줄을 둔다(확정한 화면에 없는 줄이다). 고르지 않은 안은 미리보기의 높이를 글에 맞춰 늘리는 것과 가린 요소 밖에 스크롤하는 조작을 따로 두는 것이고, 둘 다 해 보지 않았다. 이 대가는 ADR 0065의 이력 초안에 적었고 승인을 받을 때 따로 짚는다.
- **위젯 쪽에 넘긴 것 하나.** 가리지 않은 위젯에 긴 안내를 주자 axe가 `scrollable-region-focusable`을 냈다(위젯의 `<main>`이 스크롤되는데 키보드로 닿을 길이 없다). 관리 화면 앱의 Storybook에서 본 것이고 위젯 앱의 Storybook에서는 보지 않았다. 가린 미리보기에서는 나지 않아 이 기능의 일이 아니므로, 명세의 Out of Scope와 widget-login-state의 기능 계획에 적었다. 그 폴더에서 일하던 세션(`docs/widget-login-state-spec-2`)은 PR 593이 병합되어 돌지 않고(`list_sessions`의 출력), 그 PR은 그 기능 계획을 고치지 않았다(`git diff --stat 02dcfe97d origin/dev`의 출력이 비었다).
- 격리 워크트리의 `README.md`, `move-with-consumer-inert.patch`, `preview_shield.mjs`를 이 워크트리로 복사했다. `preview_shield.mjs`는 가짜 출처로 정적 빌드를 여는 스크립트이고 프로세스를 끄거나 파일을 지우거나 밖으로 요청을 보내는 줄이 없다(앞 120줄을 읽고 나머지는 `grep`으로 봤다).

서브에이전트의 보고는 모델의 출력이고 승인이 아니다. 공유 패키지 실험의 보고 머리에 "`web/` 아래를 고쳤다. 부모 세션이 이 세션에서 `/sync-design-system` 확인을 했는지 본다"가 있었다. 그 고침은 격리 워크트리 안의 실험이고 이 브랜치에는 패치 파일로만 남는다. 웹 편집 확인은 이 세션이 명세를 쓰기 전에 이미 돌았다.

## ADR 이력 초안 둘 (프로브가 본 것)

앞의 둘과 같이 초안이고 셀프 리뷰를 반영한 뒤에 승인을 받는다. 이력은 모두 넷이 됐다(ADR 0064에 셋, ADR 0065에 하나).

- ADR 0064 "로그인 시간이 끝났을 때의 갱신은 화면이 부르고, 위젯 테스트 페이지의 서버는 설정을 요청마다 받아 와 기억하지 않는다". 본문이 명세에 확인을 맡긴 넷의 뜻을 프로브 둘의 결과로 정했다. 갱신을 일으키는 쪽은 화면이다, "그대로"는 `Cookie` 머리 하나와 줄마다 옮긴 `Set-Cookie`이고 클라이언트는 쿠키를 기억하지 않는다, 흐름 전체는 대역에서 섰고 탭 둘의 동시 갱신은 admin-login의 유예에 기댄다, 받아 온 설정은 기억하지 않는다. 포인터는 다섯 자리다. 결정 "로그인"에 둘, 결정 "위젯 미리보기 페이지 설정"에 하나, Consequences "재지 않은 것"에 둘이다.
- ADR 0065 "위젯 테스트 페이지의 서버도 화면이 부른 갱신만 전하고, 미리보기는 옮긴 부품을 고치지 않고 감싼 요소로 가린다". 운영자 문의 로그인 흐름, 공유 패키지로 옮겨 본 결과, 미리보기를 가리는 법과 그 대가 둘(화면 읽기 프로그램에 그림 한 줄로만 읽힌다, 미리보기 안을 굴려 볼 수 없다)이다. 포인터는 두 자리다. 결정 "미리보기"와 Consequences "재지 않은 것"이다.
- ADR 본문에 단 포인터는 모두 열이다(ADR 0064에 여덟, ADR 0065에 둘. `grep -n -o`로 셌다). `uv run python tools/check_adr_pointers.py`는 출력 없이 끝났다(명령의 출력을 읽었다). (이 절을 쓴 때의 수다. 아래 셀프 리뷰의 표준 Major 2를 반영한 뒤에는 ADR 0065에 셋, 모두 열하나다)

`open-session`의 1단계(같은 제목의 실행 중 세션이 없고 실행 중인 세션도 없다)와 2단계(프롬프트 파일)까지 밟았고, 3단계의 `pwsh -NoProfile -File C:\project\agent\tools\open_session.ps1 -Action send …` 호출이 자동 모드 분류기에 거부됐다(사유 "Destructive or Unwanted Actions". 이 세션을 연 지시문이 적은 앞 회차의 사유 "Undermining Oversight"와 문구가 다르다). 스크립트가 돌지 않아 `fired=`가 없고 새 세션은 생기지 않았다. 다른 길로 돌아가지 않았다. 제목을 `docs/portal-admin-spec`으로 되돌렸고, 잠금은 다시 잠그지 않는다. 이 세션에서 셀프 리뷰부터 잇는다. 대기열 `open-session-send-denied-despite-allow-rule`에는 이 세션을 연 지시문이 넘긴 회차와 함께 이 거부도 한 회차로 더한다.

## 셀프 리뷰 (커밋 전)

본 범위: 기준 `02dcfe97d`(`git merge-base origin/dev HEAD`의 출력), 바뀐 추적 파일 여덟(기능 계획 여섯, ADR 둘), 커밋 0, 미추적 파일 스물둘(명세, 프로브 스무 파일, 이 일지). 표준 축은 `model: sonnet`·`effort: high`로, 명세 축은 모델을 주지 않고 띄웠다. 두 브리프에 주장 검증 목록 열 항목을 그대로 붙였고, 사용자의 답 넷은 라벨과 설명을 글자 그대로 명세 축의 요구에 옮겼다. 변경이 바깥 문서의 주소를 근거로 든 자리는 없어(명세와 ADR 변경의 `http` 주소는 모두 예시 주소다. grep으로 봤다) 발췌는 싣지 않았다. 변경이 에이전트가 따르는 절차를 바꾸지 않아 갈래 밟기 문단은 붙이지 않았다.

### 판정

두 축을 합쳐 Critical 0, Major 4, Minor 10, Nit 5다. 지적마다 원문(명세, ADR, 프로브, 기준 커밋의 코드)에 대 본 뒤 고쳤다. Major 넷 가운데 셋은 고쳤고, 하나(명세 M2)는 사용자가 고를 일이라 물음으로 올린다.

**고친 것 (표준 축).**

- Major 1. `login_relay/probe.mjs`의 `stop()`이 끄기 직전에 그 pid의 명령줄을 읽어, 그 회차의 인자(포트가 든 명령줄 꼬리)가 있을 때만 끈다. 윈도는 PowerShell의 `Get-CimInstance Win32_Process`로, 그 밖은 `ps -o args= -p`로 읽는다. 표지가 없으면 끄지 않고 pid를 찍는다. 표지 없는 폴백 `child.kill()`은 없앴다. 독스트링에 새로 쓴 문장: "POSIX 갈래(`ps` 로 읽고 프로세스 그룹을 끈다)는 돌려 보지 않았다. 이 프로브를 돌린 곳은 윈도뿐이다." `login_relay/README.md`의 두 자리(다시 돌 때 드는 것, 끄는 법)도 맞췄다.
- Major 2. ADR 0065 결정 "위젯 테스트 페이지"의 운영자 계정 항목에서 쿠키를 전해 확인하는 방식을 적은 두 문장 뒤에 포인터 하나를 달았다. 이어진 두 문장이라 하나다(`.claude/rules/adr.md`). 포인터는 열하나가 됐고(ADR 0064에 여덟, ADR 0065에 셋. `grep -n -o`로 셌다) 명세 서두의 "열"과 "이력" 문단의 "두 자리"를 "열하나"와 "세 자리"로 고쳤다.
- Minor 3. 프로브 색인의 "잰 판" 열에 판을 직접 적었다(`docs/agents/issue-tracker.md`의 "라이브러리나 도구를 쟀으면 그 판도 그 줄에 적는다"). 값은 세 프로브 README의 "잰 판", "환경", "본 판"에서 글자 그대로 옮겼고, 없는 "환경 표"를 가리키던 자리를 그 절 이름으로 고쳤다.
- Minor 4. ADR 0064 넷째 이력의 측정 문장에 범위와 전역 `fetch`의 값을 적었다. 새로 쓴 문장: "요청마다 한 번 묻는 것이 페이지 응답에 더한 시간은, `node:http`로 연결을 이어 쓸 때 호스트의 CPU 부하가 낮던 되풀이 넷에서 중앙값 3.3~4.8ms였고, 부하가 100%이던 되풀이 둘에서 21~39ms였다", "같은 호출을 전역 `fetch`로 하면 잰 PC(윈도, Node 24.19.0)에서는 부하가 낮던 되풀이 넷에서 중앙값이 8.7~16.3ms 더해졌다(쟀다). 그 판의 `fetch`가 쉬던 연결에 요청을 쓰기 전에 0ms 타이머 하나를 기다리고 윈도에서 그 타이머가 15.6ms 뒤에 불렸기 때문이고, 그 자리가 다른 리눅스 컨테이너의 Node 24.22.3에서는 `fetch`와 `node:http`의 중앙값 차가 0.2~0.3ms였다(쟀다. 판과 플랫폼을 따로 바꿔 보지는 않았다)." 이 값들을 다시 내는 것은 커밋한 프로브 `.scratch/portal-admin/probes/settings_fetch/`의 `run.py`와 `fetch_idle_timer.mjs`이고, 옮긴 자리는 그 `README.md` 요약의 1과 3, 결과 절의 타이머 표, 해석 절의 갈래다. 명세의 "0.5~0.8ms 느릴 뿐"에는 "(`node:http`, 부하가 낮던 되풀이 넷)"을 더했다.
- Minor 5. 명세가 `cases.json`의 표를 든 문서로 적은 자리를 고쳤다. 새로 쓴 문장: "그 표를 든 문서는 루트 `README.md`의 두 자리이고(구조의 `fixtures/container_network/` 줄과, "네 프로세스의 판정은 … 사례 표 하나가 잠근다"는 문장) 둘 다 프로세스를 넷으로 세므로 함께 고친다. ADR 0056 결정 "루프백 규칙의 예외"가 "네 프로세스"로 센 자리에는 포인터 "(바뀜: ADR 0064)"가 이미 있고, `.claude/rules/` 아래에는 그 표를 든 규칙이 없다(기준 커밋에서 `container_network`를 grep으로 봤다)."
- Nit 6. 이 일지의 "패치 둘과 보조 스크립트 둘"에 그 문단을 쓴 때의 수라는 말을 붙였다.

**고친 것 (명세 축).**

- Major M1. 지적이 맞았다. 관리 화면 앱의 중계는 `source: "/api/:path*"`를 상류에 통째로 넘기고(기준 커밋의 `web/apps/admin/next.config.ts`, 코드를 읽었다) 명세는 위젯 관리 화면이 그 방식을 "그대로 따른다"고 적어, 위젯 관리 화면용 포트로 온 브라우저 아닌 요청이 로그인을 보지 않는 안쪽 길에 닿았다. "저장 경로"에 새 항목을 더했다. 새로 쓴 문장: "위젯 관리 화면의 중계는 운영자용 경로 일곱만 위젯 관리 서버로 넘긴다. 안쪽 길과 위젯 설정을 받아 가는 경로는 넘기지 않고, 그 밖의 경로로 온 요청은 위젯 관리 서버에 닿지 않은 채 없다는 답을 받는다. 관리 화면 앱의 중계는 상류의 경로를 가리지 않고 넘기므로(기준 커밋의 `web/apps/admin/next.config.ts`, 코드를 읽었다) 이 자리만은 그 방식을 그대로 따르지 않는다." "프로그램 사이의 길", "위젯 관리 화면의 틀과 주소", 안쪽 길 항목, "포트와 compose"의 네 자리에 같은 뜻의 문장을 보탰고 절 제목의 괄호와 서두의 "명세가 정했다" 목록에 "중계가 넘기는 경로"를 넣었다. 계약(`openapi.json`)과 ADR의 결정은 바꾸지 않는다. ADR 0064가 안쪽 길을 "밖에서 넘기지 않는 경로"로 정한 것을 지키는 쪽으로 좁힌 것이라 사용자에게 따로 묻지 않았다.
- Minor(까닭의 수, 위젯의 2,000자). "저장할 때의 검사" 표에서 "주소가 아니다"를 꼴에 어긋나는 것으로 좁히고 "주소에 사용자 정보 자리가 있다"를 새 행으로 더했으며, 주소 칸의 2,000자는 "너무 길다"에 든다고 적었다. 주소의 사례 표에 "까닭" 칸을 더했다. 위젯의 검사에는 이 기능이 사용자 정보 자리의 규칙과 2,000자 상한을 더한다고 적었다. 새로 쓴 문장: "사용자 정보 자리는 그 명세가 이 명세에 넘긴 일이고, 길이는 세 자리의 규칙을 글자까지 같게 두어 사례 표 하나로 잠그려고 이 명세가 더했다. 위젯 관리 서버와 위젯 관리 화면은 받지 않는 까닭까지 가르고("저장할 때의 검사"), 위젯은 받는지만 가른다."
- Minor(아이콘의 대가). 사용자가 고를 때 들은 값 전부를 받았다. 새로 쓴 문장: "더하는 티켓 하나가 함께 고치는 것은 넷이다. 디자인 시스템 패키지의 아이콘 목록, 그 수를 세는 스토리 시험(지금 열일곱을 세고 스물이 된다. 기준 커밋의 `web/packages/ui/src/components/atoms/Icon.stories.tsx`, 코드를 읽었다), 아이콘 전체를 찍은 사진 비교의 기준 그림, 디자인 시스템 아티팩트다."
- Minor(지우기가 거절됐을 때). "사이트 지우기"에 항목을 더했다. 확인 창을 닫지 않고 단추 위에 까닭 한 줄을 보이며, 까닭은 셋(저장 번호가 다르다, 요청이 실패했다, 로그인이 끝났다)이고 저장 번호가 다를 때는 "지우기" 단추를 끄고 "취소"만 남긴다. "문구" 표에 세 행, 화면 부품 시험에 사례 하나, "화면과 다르게 짓는 것"에 한 줄을 더했다. 확정한 그림에 없는 줄이라 그렇게 적었다.
- Minor(고지 처음 값). ADR 0064 결정 "고지의 고정 문장"에 맞췄다. 새로 쓴 문장: "켤 때는 그 칸이 비어 있을 때에만 처음 값을 넣는다. 등록 화면에서든 이미 등록한 사이트의 화면에서든 같다." 치르는 값(담았다가 끈 사이트에 쿠키 문장이 남을 수 있다)도 적었다.
- Minor(중계의 시험 자리). Testing Decisions에 중계 사례를 더했다. 새로 쓴 문장: "로그인 쿠키도 브라우저의 머리도 없는 요청으로 위젯 관리 화면의 주소에서 안쪽 길을 부르면 없다는 답이 오고 위젯 테스트 페이지 설정이 실리지 않는다. 그리고 로그인한 브라우저의 페이지가 "갱신"을 중계로 부르면 그 답의 `Set-Cookie` 두 줄이 브라우저의 쿠키로 서서, 쿠키 둘의 값이 부르기 전과 달라진다." 처음에는 "짧은 JWT의 수명이 끝난 뒤"로 적었다가, admin-login이 시험에서 수명을 줄이는 길을 두는지 알 수 없어 "갱신"을 바로 부르는 사례로 고쳤다. 경로의 가름은 관리 화면 앱의 `next.config.test.ts`를 선례로 빠른 시험으로도 잠근다고 적었다.
- Minor(CI에 치르는 값). 지적의 전제를 원문에 대 보니, 기존 두 시험의 준비에 위젯 관리 서버와 데이터베이스가 드는 것은 widget-login-state가 먼저 더한다(병합된 그 명세의 Testing Decisions "수락 문장의 자리"). 새로 쓴 문장: "그 시험들의 준비에 위젯 관리 서버와 데이터베이스가 드는 것은 widget-login-state가 먼저 더하고(그 명세의 Testing Decisions "수락 문장의 자리"), 이 기능이 더하는 것은 Agent OS의 운영자 계정과 로그인 단계다. 그래서 이 기능이 CI에 새로 치르는 값은 위젯 관리 화면 앱의 e2e 잡 하나와 기존 두 시험의 준비가 길어지는 것이다." "브라우저로 끝까지 가는 시험은 하나다"는 "이 기능이 새로 두는" 것으로 좁혔다.
- Nit 셋. admin-login 기능 계획의 "그래서 위 문단이 말한 계약 변경은 없다"를 "위 문단의 끝이 말한 "그 명세가 계약 변경으로 따로 올린다"에 해당하는 것은 없다. 이 행이 스스로 바꾸는 계약 두 자리와는 다른 이야기다"로 고쳤다. 도움말은 주소인 칸에서 그 칸의 도움말 뒤에 주소의 도움말이 이어 붙는다고 적었다. deploy-package 기능 계획이 받은 "배포 안내에 더 적을 것"을 다섯에서 여섯으로 늘려 "사이트 파일을 고친 뒤 무엇을 다시 띄우는지의 전체 절차"를 넣고, 명세의 두 자리(배포 안내 항목, Out of Scope)에도 맞췄다. 그 기능 계획의 `Blocked by`에 portal-admin이 있다는 것은 표준 축이 확인한 그대로다.

**남긴 것과 이유.**

## 셀프 리뷰 뒤에 물은 것과 답

셀프 리뷰 반영을 마친 뒤 선택 화면 하나로 둘을 올렸다. 명세 축 M2(미리보기의 높이를 넘는 글)와 ADR 이력 초안 넷의 승인이다(`CLAUDE.md` 작업 규약 5의 차례). 선택 화면은 훅(`hook_choice_facts`)이 두 번 막았다. 첫 번째에 설명의 사실을 ADR 0064 이력 78~102행, ADR 0065 이력 77~85행, 명세의 "미리보기"와 "문구", `settings_fetch/README.md` 요약에 대 보았고, 미리보기를 가리는 법을 "투명한 덮개"로 적은 것이 틀려(실제는 위젯을 감싼 요소에 `inert`와 `aria-hidden`을 주는 것이다) 질문 문장과 넷째 라벨을 고쳤다. 해 보지 않은 안의 값에는 어림이라고 적었다. 두 번째 막음은 질문 문장이 바뀌어서였다.

1. 미리보기의 높이를 넘는 글. 물은 것: "위젯 관리 화면의 미리보기(설정 양식 옆에 저장 전 값으로 그려 보이는 위젯 그림)에서, 고지 전문처럼 긴 글이 미리보기 칸의 높이를 넘으면 어떻게 보이게 할까요? 미리보기는 그 안의 단추가 눌리지 않게 '조작할 수 없는 그림'으로 감싸 두어서, 그 안을 마우스 휠로 스크롤할 수 없습니다."

   > 사용자: "넘친 글은 테스트 페이지에서 보기 (Recommended)" — 설명: 지금 명세에 적힌 안입니다. 미리보기 안은 스크롤되지 않고 긴 글은 한쪽 끝만 보입니다(실험에서 첫 화면의 긴 글은 앞부분이, 긴 대화는 끝부분이 보였습니다. 고지 전문은 그리는 부품이 아직 없어 어느 쪽이 보일지 보지 못했습니다). 미리보기 아래에 '미리보기 안은 스크롤할 수 없다. 긴 글의 나머지는 저장한 뒤 "테스트"에서 본다.'는 흐린 한 줄이 섭니다. 치르는 값: 긴 글의 나머지를 보려면 저장한 뒤 위젯 테스트 페이지를 열어야 합니다. 감싸는 방식은 Chromium에서 손으로 확인했고(다른 브라우저와 터치·키보드 스크롤은 보지 않았습니다) 추가 실험 없이 바로 진행합니다.

   고르지 않은 안은 "미리보기를 글 길이만큼 늘리기"와 "미리보기 밖에 스크롤 단추 두기"였다. 둘 다 해 보지 않은 안이라 값을 어림으로 적어 올렸다. 답이 지금 명세의 안이라 결정은 바뀌지 않는다. 명세의 "미리보기" 절 제목과 서두(사용자가 고른 것 다섯 → 여섯, 명세가 정한 것의 목록에서 이 항목을 뺐다)와 그 절의 끝 문장, ADR 0065 이력의 머리 문단과 셋째 문단에 사용자가 골랐다는 것을 적었다. 절 제목의 괄호는 넘겨받은 것 열여덟, 사용자가 고른 것 여섯, 명세가 정한 것 스물셋이 된다.

2. ADR 이력 초안 넷의 승인. 물은 것: "명세가 ADR 0064와 ADR 0065에 덧붙인 변경 기록(이력) 초안 넷 가운데 승인하는 것을 모두 골라 주세요. 고르지 않은 것은 고칠 점을 적어 주시면 고쳐서 다시 보여 드립니다." 여럿을 고르는 화면이고 사용자가 넷을 모두 골랐다.

   > 사용자: "예시 질문 모양 고르는 칸" — 설명: ADR 0064의 이력입니다. 위젯 첫 화면의 예시 질문을 세 모양(세로 목록이 기본, 감기는 알약, 입력창 위 띠) 가운데 운영자가 고르는 칸이 위젯 설정에 하나 늡니다. 앞서 '0.1 판에 고르는 칸을 넣기 (Recommended)'로 고르신 것을 기록으로 옮긴 것입니다. 치르는 값: 위젯 관리 화면에 작은 그림 고르기 하나와 도식 그림 셋이 늘고, 서버가 저장하고 내주고 시험할 값이 하나 늡니다. 이 칸은 확정한 화면 그림에 없어 구현 때 다른 그림 고르기와 같은 부품으로 짓습니다.

   > 사용자: "주소 검사와 설정 파일 값 둘" — 설명: ADR 0064의 이력입니다. 운영자가 등록하는 주소 넷(로그인 주소, 로그아웃 주소, 문의 링크, 보고서 링크)에 같은 검사 하나를 겁니다. 'https://이름:비밀번호@…'처럼 계정 정보 자리가 든 주소와 2,000자를 넘는 주소는 받지 않습니다(2,000자는 어림으로 정한 상한입니다). 치르는 값: 보고서 링크에 평문 http 주소를 걸던 배포는 그 주소를 화면에서 등록하지 못하고, 주소의 쿼리에 비밀 값을 넣는 것은 여전히 막지 못해 도움말로만 알립니다. 또 위젯 테스트 페이지의 설정 파일에 시작 값 둘(Agent OS 서버의 주소, 관리 화면의 주소)이 늘고 그 파일의 형식 번호가 하나 오릅니다.

   > 사용자: "로그인 연장은 화면이 요청" — 설명: ADR 0064의 이력입니다. 로그인 시간이 끝나면 서버가 스스로 연장하지 않고 화면이 연장을 요청한 뒤 같은 요청을 한 번 다시 보냅니다. 서버가 스스로 연장하는 방식에서는 탭 하나가 동시에 보낸 요청 넷이 같은 번호로 연장을 요청해 로그인이 끊겼습니다(대역 서버로 잰 실험, 유예가 없을 때). 또 위젯 테스트 페이지는 사이트 설정을 요청마다 새로 받아 와, 운영자가 저장한 값이 다음 요청부터 보입니다. 치르는 값: 요청마다 잰 PC에서 부하가 낮을 때 3.3~16.3밀리초(부르는 방법에 따라 다릅니다), CPU 부하가 100%일 때 21~39밀리초가 더 들었고 배포 환경에서는 재지 못했습니다. 위젯 관리 서버가 내려가 있거나 느린 동안에는 테스트 페이지도 사이트 목록을 내지 못합니다.

   > 사용자: "테스트 페이지 로그인과 미리보기 가리기" — 설명: ADR 0065의 이력입니다. 위젯 테스트 페이지도 위와 같은 로그인 규칙을 씁니다. 미리보기는 위젯 부품을 고치지 않고, 조작할 수 없게 표시한 요소로 감싸 가립니다. 부품을 공유 패키지로 옮겨 본 실험에서 옮긴 20파일 가운데 17파일이 한 글자도 바뀌지 않았습니다(손으로 본 실험입니다). 치르는 값: 화면 읽기 프로그램에는 미리보기가 그림 한 줄로만 읽혀, 화면을 보지 못하는 운영자는 미리보기로 글을 확인하지 못합니다. 긴 글을 다루는 문단은 첫 질문의 답대로 고칩니다.

   이력 넷은 승인됐다(ADR 0064의 "위젯 설정에 예시 질문의 모양을 고르는 값으로 더한다", "등록하는 주소 넷에 같은 검사를 걸어 사용자 정보 자리를 받지 않고, 위젯 테스트 페이지의 설정 파일에 시작 값 둘을 더한다", "로그인 시간이 끝났을 때의 갱신은 화면이 부르고, 위젯 테스트 페이지의 서버는 설정을 요청마다 받아 와 기억하지 않는다", ADR 0065의 "위젯 테스트 페이지의 서버도 화면이 부른 갱신만 전하고, 미리보기는 옮긴 부품을 고치지 않고 감싼 요소로 가린다"). 승인 뒤에 이력의 글을 고친 것은 ADR 0065 이력에 사용자가 골랐다는 문장 둘을 더한 것뿐이고, 승인 화면의 넷째 설명이 미리 알린 고침이다.
