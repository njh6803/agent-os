## 171의 전제

지시문이 먼저 재라고 한 전제(주 체크아웃 안의 워크트리 세션에 상위 폴더의 `CLAUDE.md`가 함께 실리는지)를
`.scratch/harness/probes/claude_md_parent.py`로 쟀다(claude 2.1.292, sonnet). 임시 디렉터리에 git 저장소와 그 연결된
워크트리를 만들고 폴더마다 표지 낱말이 다른 `CLAUDE.md`를 둔 뒤, 갈래마다 도구 없이 실린 지시를 옮기게 했다.

- 첫 판(`안쪽` 둘, `옆` 하나)에서 `안쪽`은 자기 것만 옮겼다. 상위 파일이 실리면 모델이 옮긴다는 양성 대조가 없어
  갈래를 늘렸다.
- 둘째 판(일곱 회차, 모두 도구 0회)에서 연결된 워크트리(`안쪽`, `둥지`)는 자기 것과 뿌리의 것을 옮겼고 주 저장소
  `바깥`의 것은 없었다. 보통 하위 폴더 `하위`는 뿌리, `바깥`, 자기 것 셋을 옮겼다. 상위 폴더의 `CLAUDE.md`는 git
  루트를 넘어 실리지만, 연결된 워크트리에서는 주 워크트리 루트의 것만 빠진다. 경로가 `.claude/` 아래인지와는 상관이
  없었다(`둥지`).
- 셋째 판(여덟 회차, 커밋한 판)은 셀프 리뷰가 짚어 자기 `CLAUDE.md`를 지운 워크트리 `빈칸`을 더했다. `빈칸`도 뿌리의
  것만 옮겨, 빠지는 까닭이 같은 자리의 자기 파일이 아니라 주 워크트리 루트를 건너뛰는 것이다.

그래서 171의 걱정(주 체크아웃 안에 꺼낸 대조군에 병합된 새 `CLAUDE.md`가 섞인다)은 일어나지 않는다. 다만 주 체크아웃
위 폴더의 `CLAUDE.md`는 어느 갈래에나 실리므로, 확인은 "갈래마다 함께 실리는 상위 폴더의 `CLAUDE.md`(연결된 워크트리면
주 워크트리 루트만 뺀다)"로 지었다. 대조군이면 답을 흘리고, 실험군이면 통과가 그 파일에서 왔을 수 있어 두 갈래 모두에
건다. 대기열 행은 대조군만 말했으므로 이 넓힘은 PR 본문에 적는다. 같은 측정으로 앞 일지가 남긴 한계(실험군에 실린 것이
워크트리 사본인지 상위 폴더의 사본인지)도 풀렸다. 워크트리 사본이다.

## 에이전트 갈래

설계 입력은 지운 탐침의 독스트링과 앞 일지 회고 절의 시험 사례였다. `tools/canary.py`에 `kind = "agent"`를 더했다.

- **명세.** 칸 `agent`(정의의 `name`)와 `agent_tools`(정의의 `tools` 줄)가 반드시 있다. `agent_tools`에 `Agent`나
  `Task`를 넣으면 명세 오류다. 갈래에는 `target`을 쓰지 않는다. 두 칸은 다른 kind에서 쓰지 않는다.
- **명령.** `--tools`는 `Agent`에 `agent_tools`를 더한 것이다(`tools_for`). 앞 세션이 손으로 본 두 구성(Agent 하나면
  도구 0개로 거부, 넷을 더하면 돈다)이 근거다.
- **사실 뽑기.** `parent_tool_use_id`가 붙은 assistant 이벤트는 서브에이전트의 것으로 따로 센다(턴 수와 도구 호출).
  본 세션의 호출은 `Agent(<subagent_type>)` 꼴로 모은다. 본 세션이 부른 Agent의 호출 id로 도구 결과를 짝지어
  `tool_use_result`의 `status`와 `totalToolUseCount`를 남긴다. 결과가 글이면 `오류: <글>`이다. 다른 도구의 결과는
  판정에 쓰지 않아, 재지 않은 모양을 검증해 규칙·스킬 회차를 떨어뜨리지 않도록 보지 않는다. init의 `Task`는 `Agent`로
  읽는다.
- **판정.** 본 세션은 그 에이전트를 부르는 Agent 밖의 도구를 쓰지 않는다. 서브에이전트는 도구를 부르지 않는다(백그라운드는
  assistant 이벤트의 도구 호출, 앞쪽은 결과의 도구 횟수). 실험군이거나 init의 `agents`에 그 에이전트가 있는 대조군이면
  그 에이전트를 한 번 부르고 서브에이전트가 돈 근거가 있어야 한다. 근거는 그 에이전트의 `completed` 결과이거나
  서브에이전트의 assistant 이벤트다. 새 에이전트라 옛 사본에 없는 대조군(153의 첫 사건)은 부르지 않아도 된다.
- **사전 확인.** 실험군 사본의 정의가 머리말의 `name`과 `tools`로 명세와 맞는지 본다(`agent_problems`). 대조군 정의는
  없거나 달라도 된다. 실렸는지는 init의 `agents`가 가른다.

테스트를 먼저 써 빨강(수집 단계의 가져오기 실패)을 본 뒤 구현했고, 처음 돌린 테스트 133개가 초록이었다. 기존 테스트
하나(`read_facts`의 전체 비교)는 `Facts`에 본 세션 호출 칸이 생겨 기대값에 `calls`를 더했다. 테스트가 잡은 결함을 덮은
것이 아니라 사실의 모양이 늘어난 것이다. 변이는 에이전트 갈래 스물둘과 상위 폴더 넷을 더해 예순다섯이 모두 기대대로
빨갰다. 변이를 쓰다가 "근거를 다른 에이전트의 결과에서도 찾는다"를 잡을 사례가 없는 것을 보고, 돌리기 전에 다른
에이전트(Explore)의 완료 결과 사례를 더했다. 셀프 리뷰를 반영한 뒤 변이는 예순여덟이다(아래 절).

`read_facts`는 원래 `{`로 시작하지 않는 줄과 풀리지 않는 줄을 건너뛰고, 읽는 이벤트의 모양이 어긋나면 실패로 본다.
지운 탐침은 객체가 아닌 JSON 줄도 실패로 봤다. 이 차이는 그대로 두었다. 명세 축이 배열 줄이나 두 객체를 붙인 줄에 Read를
숨기면 지나가는 것을 손으로 보였지만, claude가 내지 않는 모양이고 잘린 꼬리는 종료 코드가 잡는다.

`spec_reviewer_agent.toml`(질문은 지운 스크립트와 글자가 같다)을 실제로 돌려 통과 4였다. 실험군 1·3은 서브에이전트를
앞쪽으로 띄워 결과 `completed`(도구 0회), 실험군 2와 대조군은 백그라운드로 띄워 `async_launched`와 서브에이전트의
assistant 이벤트 하나였다. 두 근거가 모두 실제로 쓰였다. 대조군은 옛 문장을 옮겼다. 원본에서 init의 `Task`, 호출
이름 `Agent`, 결과의 `status`가 테스트의 가정과 같은 것을 봤다. 대조군 옛 판은 앞 세션이 걷은 자리
`C:/project/agent-canary-58969f7`에 다시 꺼냈다.
