## 사실 확인

서브에이전트 둘(Explore, 읽기만)이 코드와 배포 파일을 살폈다. 아래는 그 보고를 줄인 것이고, 근거의 종류는 보고가 적은 대로다.

### 코드 쪽

- 명령줄 도구는 argparse이고 하위 명령은 `run`, `resume`, `migrate`, `serve` 넷이다. 인자는 `src/agent_os/channel/cli/main.py`의 `build_parser`가, 조립은 `src/agent_os/main.py`의 `main()`이 한다(코드를 읽었다). `uv run agent-os --help`와 `--version`을 손으로 봤다. 서버를 띄우지 않고 구성만 읽어 출력하는 하위 명령은 없다(코드를 읽었다).
- 종료 코드는 0(끝남), 1(실패), 3(일시정지)이고 2는 argparse의 인자 오류다(코드를 읽었다, `channel/cli/main.py` 76~78줄).
- `adapters/filesystem.py`의 `_describe`는 검증 오류에서 받은 값을 되울리지 않고 "종류 (칸 위치): 문구"만 남긴다. `disabled.toml`의 깨짐 문구는 이 보호에서 빠져 검증 오류 전문을 싣는다(코드를 읽었다. `.claude/rules/adapters.md`도 "닫지 않은 잔여"라고 적는다).
- 비밀 값은 환경 변수 이름으로 간접 참조한다. 모델의 `api_key_env`, 원격 MCP 서버의 `[server.headers]`, 토큰 둘과 `AGENT_OS_DATABASE_URL`이 그렇다(코드를 읽었다). 값이 직접 적힐 수 있는 자리는 원격 MCP 서버 `url`의 쿼리 문자열(ADR 0049의 알려진 한계)이고, stdio MCP 서버의 `command`와 `args`에 토큰을 적을 수 있다는 것은 어림이다.
- 트레이스는 파일이다. `JsonlTrace`가 `<traces>/<run_id>.jsonl`에 실행 하나당 파일 하나를 쓴다. PostgreSQL에 실행이나 이벤트를 저장하는 코드는 없다(코드를 읽었다, `adapters/jsonl.py`, `adapters/postgres/migrations/versions/0001_first.py`).
- 실패한 실행만 거르는 목록은 이미 있다. `TraceStore.list(status="failed", limit, after)`이고 limit은 기본 50, 상한 200이다. 행(`RunSummary`)은 `run_id`, `status`, `started_at`, `last_at`, `agent`, `principal`을 들고 `cause`와 `error`는 들지 않는다. 원인을 얻으려면 실행마다 `read()`로 마지막 `run_failed`를 꺼내야 한다(코드를 읽었다, `core/ports.py`, `adapters/jsonl.py`).
- 최종 사용자의 글과 문서 조각이 실리는 칸: `run_started.request`, `conversation_summarized.summary`, `llm_called.prompt`·`text`·`tool_calls[].args`, `run_finished.output`, `tool_called.args`·`content`, `run_paused.args`, `approval_denied.reason`. 사람을 가리키는 식별자가 실리는 칸: `run_started.principal`, `approval_granted.approver`, `approval_denied.approver`(코드를 읽었다, `sdk/events.py`).
- 실패의 내용 `run_failed.error`는 core가 `"<예외 종류>: <글>"` 꼴로 짓는다. 원격 MCP 서버 `url`의 쿼리나 모델 서버의 응답 글이 들 수 있다(코드를 읽었다, `core/run.py`).
- 서버 하나를 여는 함수는 `adapters/mcp.py`의 `_opened(name, server)`이고 stdio와 http가 같은 함수로 열린다. 그래서 stdio 서버를 확인하면 서버 프로세스가 실제로 뜬다. 실패는 `ConnectionError("MCP 서버 <이름>(<명령|url>)에 붙지 못했다: <원인><상태>")`가 된다(코드를 읽었다).
- 모델 서버에 닿는지 확인하는 함수는 없다. `serve`의 `_model_problem`은 모델 매니페스트가 있고 읽히는지만 본다. `openai-compatible` 모델의 실패 글은 넷으로 갈린다(요청을 거절했다 `(HTTP <코드>)`, 닿지 못했다, 응답을 읽지 못했다, 호출이 실패했다). `anthropic` 쪽은 라이브러리 예외의 종류와 글이 그대로 실린다는 것은 코드를 읽은 어림이다.
- `serve`의 데이터베이스 확인은 이 기준 커밋에 아직 없다(다른 세션의 티켓 `03-serve-requires-database`가 맡았다). `migrate`의 글과 종료 코드는 있다(코드를 읽었다, `main.py`, `adapters/postgres/database.py`).
- `GET /health`는 `{status: "ok"}`만 준다. 읽히지 않는 매니페스트는 `GET /plugins`의 표지 행으로 보인다. `rules.toml` 깨짐, 사이트 파일, 모델 이름, 토큰 같은 구성 오류를 보여 주는 관리 경로는 없고 `serve`가 시작할 때 stderr에만 찍힌다(코드를 읽었다, `admin/http.py`, `main.py`).

### 배포 쪽

- 단독 compose의 서비스는 일곱이다. `proxy`, `postgres`, `migrate`(한 번 돌고 끝난다), `serve`, `admin`, `widget`, `portal`. 상태 확인이 없는 것은 `proxy`와 `migrate`다(코드를 읽었다, `deploy/standalone/compose.yaml`).
- 트레이스와 플러그인 루트는 이름 있는 볼륨(`agent-os_traces` → `/data/traces`, `agent-os_plugins` → `/app/plugins`)이고 `serve`만 붙인다. 사이트 파일은 호스트 폴더 `./site`를 읽기 전용으로 얹는다. `.env`는 `serve`가 `env_file`로 통째로 받는다(코드를 읽었다).
- `.env.example`의 키는 일곱이고 비밀 값은 넷이다(`AGENT_OS_ADMIN_TOKEN`, `AGENT_OS_CHANNEL_TOKEN`, `AGENT_OS_DATABASE_PASSWORD`, `ANTHROPIC_API_KEY`). `serve`의 환경에는 비밀번호가 든 `AGENT_OS_DATABASE_URL`도 들어가므로 `docker inspect`와 `docker compose config`의 출력은 그대로 실으면 비밀 값이 샌다(코드를 읽은 어림).
- 이미지 넷 어디에도 `docker` 명령줄 도구를 깔지 않는다. apt로 까는 것은 `tini`뿐이다(코드를 읽었다, `deploy/images/*.Dockerfile`. 실제 이미지 안을 들여다보지는 않았다). 네 이미지는 uid 10001로 돌고 `widget`을 뺀 컨테이너의 루트는 읽기 전용이다.
- 배포 안내가 보증하는 호스트는 리눅스 x86-64의 Docker Engine 28.3.3 이상과 Compose 2.20.2 이상이다. 안내의 명령은 모두 bash 문법이다. `deploy/`에 호스트에서 도는 `.sh`나 `.ps1`은 없다(코드를 읽었다, `deploy/standalone/README.md`. `find`를 손으로 봤다).
- 배포 파일 묶음은 `deploy/standalone/` 아래 파일 전부를 담고 권한은 파일 0644로 고정한다. `tools/release.py`의 독스트링이 "실행 권한이 필요한 파일은 지원하지 않는다"고 적는다(코드를 읽었다).
- 단독 배포 e2e(`web/packages/e2e-standalone`)에 일부러 깨뜨린 배포(모델 서버 꺼짐, MCP 서버 꺼짐, 토큰 불일치, 데이터베이스 꺼짐)를 만드는 시험이나 도우미는 없다. 가까운 것은 API 키 없이 돌려 `"cause":"model_call"`을 보는 사례다. e2e의 정리 단계가 `docker compose logs --no-color --timestamps`를 파일로 남기는 선례가 있다(코드를 읽었다).
- compose에 기록 드라이버나 기록 크기 제한 설정은 없다(`grep`을 손으로 봤다).

## 라운드 1

질문: 진단 묶음은 누가 받아 보는 파일로 설계할까요? 선택지는 "조직 밖 지원 담당까지 (Recommended)", "같은 조직 안에서만", "기본은 밖, 옵션으로 안"이었다.

> 사용자: 자세하게 이해하기 쉽게 설명해줘.

선택지를 고르지 않은 답이다. 같은 결정을 쉬운 말과 구체적인 예시로 다시 설명하고 다시 묻는다.

다시 올린 질문: 문제가 생겼을 때 만드는 진단 파일을, 운영자가 회사 밖(제품을 만든 쪽)으로 보내도 되는 파일로 만들까요? 선택지는 "밖으로 보내도 되게 (Recommended)", "회사 안에서만 보게", "둘 다 만들 수 있게"였다. 설명에 넣은 사실 가운데 관리 화면의 실행 상세 페이지가 요청한 사람의 값을 "주체" 칸에 보여 준다는 것은 코드를 읽었다(`web/apps/admin/components/organisms/RunDetail.tsx` 76줄, `EventItem.tsx`의 `FIELD_NAMES`).

> 사용자: 이걸 왜 파일로 관리해?? 로그로 남기거나 DB에 저장해야하는거 아니야?

선택지를 고르지 않고 설계의 전제를 물은 답이다. "받는 사람"보다 앞선 결정(진단 정보를 어떤 모양으로 내주는가)이 아직 열려 있다는 뜻으로 읽었다. 파일은 정보를 보관하는 자리가 아니라 이미 있는 기록(컨테이너 기록, 트레이스, 설정)을 필요한 순간에 모아 내보내는 사본이라는 것을 설명하고, 그 결정을 먼저 묻는다.

설명에 넣은 사실을 올리기 전에 대 봤다. 0.1 판(`pilot-release`)이 `deploy-package`를 기다리고 `deploy-package`가 `diag-bundle`을 기다린다(두 기능 계획의 `**Blocked by:**` 줄을 읽었다). 관리 화면이 `serve`에서 정보를 받아 보여 주는 앱이라는 것은 `.claude/rules/web-admin.md`의 중계(`rewrites`) 항목을 읽은 것이다.

> 사용자: 진단 정보를 운영자에게 어떤 모양으로 내줄까요? (정보 자체는 어느 쪽이든 지금처럼 로그와 실행 기록에 그대로 남습니다) → "관리 화면의 진단 페이지"

— 설명: 파일을 뽑는 명령 대신 관리 화면에 진단 페이지를 두고, 서버가 확인한 결과(판, 설정 상태, 접속 확인, 최근 실패)를 데이터베이스에 저장해 브라우저에서 보여 줍니다. 운영자가 서버에 접속하지 않아도 됩니다. 대가: 관리 화면은 serve에서 정보를 받아 보여 주는 앱이므로, serve나 데이터베이스가 죽은 때(진단이 가장 필요한 때)에는 페이지가 내용을 보여 주지 못합니다. 회사 밖의 사람에게 보여 주려면 화면을 캡처해야 합니다. 지금 계획의 '진단 묶음'과 다른 기능이 되므로 ADR 0046의 이력으로 범위를 바꾸고 통합 배포 계획도 고쳐야 하며, 다른 저장소에 있는 문서 검색 서버 쪽 계획과도 어긋나게 됩니다. 서버가 원격 MCP 서버를 주기적으로 확인하는 방식은, 상태 확인 경로가 MCP 서버들까지 함께 보는 안을 ADR 0049가 거부한 것과 가까운 방향입니다(가깝다는 것은 제 해석입니다).

추천(필요할 때 뽑는 파일)과 다른 답이다. 이 답으로 설계의 뿌리가 바뀐다. 파일을 받는 사람을 묻던 질문과 "트레이스의 글을 운영자가 골라 싣는 방법"은 묻지 않게 됐다. 관리 화면은 로그인한 운영자만 보고, 운영자는 실행 상세 페이지에서 이미 트레이스 전체를 본다. 새로 열린 가지는 확인을 언제 하는가, 무엇에 접속해 보는가, 무엇을 저장하는가, 서버가 죽었을 때의 안내, 다른 계획(ADR 0046, 통합 배포, 문서 검색 서버 쪽)에 넘길 것이다.

## 라운드 2

올리기 전에 선택지 설명에 넣을 사실을 대 봤다. 근거의 종류는 다음과 같다.

- 두 제공사의 파이썬 SDK에 모델 목록을 묻는 기능이 있다. 손으로 봤다(Glob으로 `.venv/Lib/site-packages/anthropic/resources/models.py`와 `.venv/Lib/site-packages/openai/resources/models.py`가 있는 것을 확인했다). 그 요청에 사용료가 드는지와 로컬 모델 서버가 그 요청에 답하는지는 어림이다.
- 지금 `serve`에는 정해진 간격으로 작업을 돌리는 자리가 없다. 손으로 봤다(`src/agent_os/server.py`에서 `create_task|start_soon|lifespan|add_event_handler`를 Grep으로 찾았고 일치가 없었다). 주기 작업을 맡는 별도 프로세스(worker)는 retention-worker부터 들어온다(`docs/PRD.md` 34줄을 읽었다).
- ADR 0049가 거부한 것은 상태 확인 주소(`/health`)가 MCP 서버들을 함께 보는 안과 CLI 명령 `agent-os mcp check`다(그 ADR 33줄을 읽었다). 이유는 상태 확인마다 모든 서버에 요청이 간다는 것과 `/health`의 뜻이 바뀐다는 것이다.
- 원격 MCP 서버의 접속 기한은 30초다(`.scratch/mcp-http/spec.md` 96줄을 읽었다. mcp가 자기 클라이언트에 쓰는 값이다).
- 단독 배포의 compose에서 상태 확인이 있는 서비스는 postgres, serve, admin, widget, portal이고 proxy에는 없다. serve에는 Docker 소켓을 얹지 않는다. 관리 화면은 프록시를 거치지 않고 서버의 `127.0.0.1:3000`에 발행된다(`deploy/standalone/compose.yaml` 22~167줄을 읽었다). serve 이미지에 docker 도구를 까는 줄은 없다(`deploy/images/serve.Dockerfile`을 `docker`로 Grep했고 주석 넷만 나왔다).
- 로컬 모델 서버 쪽 실패 글은 `요청을 거절했다 (HTTP <코드>)`와 `닿지 못했다`로 갈린다(`src/agent_os/adapters/openai_compatible.py` 212·215줄을 읽었다).

질문 넷을 한 화면에 올렸다. 답은 다음과 같다.

> 사용자: 진단 페이지의 접속 확인(서버가 MCP 서버와 모델 서버에 실제로 접속해 보는 일)은 언제 실행할까요? → 선택지를 고르지 않고 "근데 DB에 저장할 필요도 없을 것 같은데 로그에 남고 진단 페이지도 필요 없을 것  같아."

선택지는 "버튼을 누를 때만 (Recommended)", "정해진 간격으로 자동", "페이지를 열 때마다"였다.

> 사용자: 접속 확인에 프로그램 방식(stdio, 실행할 때마다 프로그램을 띄워 쓰는 방식)의 MCP 서버도 넣을까요? → "두 방식 모두 확인 (Recommended)". 덧붙인 말: "근데 이건 플러그인 메뉴에서 MCP 목록에서 같이 있는게 좋을 것 같은데"

— 설명: 원격 방식의 서버에는 접속해 보고, 프로그램 방식의 서버는 프로그램을 한 번 띄워 도구 목록을 받은 뒤 끕니다. 실제 실행이 서버를 여는 것과 같은 함수(어댑터의 서버 하나를 여는 함수. src/agent_os/adapters/mcp.py를 읽었습니다)를 쓰므로, 명령이 없어서 뜨지 않는 경우(예: 인터넷이 막힌 곳에서 내려받아 띄우는 서버)도 실행 전에 잡습니다. 대가: 확인할 때 그 프로그램이 실제로 한 번 뜹니다. 뜨는 것만으로 무언가를 바꾸는 서버가 있다면 그 일이 확인 때도 일어납니다.

> 사용자: 모델 서버(답변을 만드는 AI 모델을 제공하는 서버)가 정상인지는 어떻게 확인할까요? → "모델 목록을 물어 확인 (Recommended)". 덧붙인 말: "근데 이건 모델을 관리할 수 있는 화면에서 같이 있는게 좋을 것 같은데"

— 설명: 모델 플러그인마다 모델 서버에 '쓸 수 있는 모델 목록'을 묻는 요청을 한 번 보냅니다. 서버가 꺼졌는지, 키가 틀렸는지, 적어 둔 모델 이름이 그 서버에 있는지를 가를 수 있습니다. 답변을 만들지 않는 요청이라 사용료가 들지 않을 것으로 봅니다(어림입니다. 두 제공사의 파이썬 SDK에 모델 목록 기능이 있는 것은 설치된 파일로 확인했고, 과금 여부와 로컬 모델 서버가 이 요청에 답하는지는 명세 단계에서 실제로 돌려 확인합니다). 대가: 모델에 접속하는 코드에 '확인' 기능을 새로 더해야 합니다(지금은 모델 서버에 닿는지만 보는 함수가 없습니다).

> 사용자: 서버(serve)가 죽어서 진단 페이지가 열리지 않거나, 프록시·위젯 같은 다른 컨테이너가 죽었을 때는 어떻게 알려 줄까요? → 다른 답("Something else")을 골랐고 적은 글은 없었다.

선택지는 "배포 안내에 문제 해결 절 (Recommended)", "다른 컨테이너에도 접속해 봄", "페이지만, 안내는 그대로"였다.

이 답들로 설계의 뿌리가 한 번 더 바뀐다. 내가 읽은 방향은 이렇다. 따로 두는 진단 페이지도, 확인 결과를 담는 데이터베이스 표도 두지 않는다. 접속 확인은 그 대상을 다루는 화면에 붙인다. MCP 서버의 확인은 플러그인 화면의 MCP 목록에, 모델 서버의 확인은 모델을 다루는 화면에 둔다. 확인 결과는 그 자리에 바로 보여 주고 기록은 서버의 로그에 남긴다. 이 읽기는 다음 라운드의 첫 질문으로 확인받는다. 넷째 질문은 전제(진단 페이지)가 사라졌으므로 "서버가 뜨지 않을 때의 안내"로 고쳐 다시 묻는다.

### 넷째 질문을 고쳐 다시 물었다

올리기 전에 대 본 사실이다. 배포 안내 문서 `deploy/standalone/README.md`는 열두 절이고 "문제 해결"이라는 절은 없다. 실패했을 때의 안내는 4절("띄우기와 확인", "띄우기가 끊겼을 때")과 12절("데이터베이스 비밀번호 바꾸기")에 있다(그 문서의 제목 줄과 `docker compose` 명령이 나오는 줄을 Grep으로 읽었다. 다른 절에 더 있는지는 읽지 않았다). 이 문서가 배포 파일 묶음과 어긋나지 않는지 보는 시험이 있다(`tests/tools/test_deploy_guide.py`의 첫 줄을 읽었다. 무엇을 검사하는지는 읽지 않았다).

> 사용자: 서버(serve)가 아예 뜨지 않아 관리 화면에서 아무것도 확인할 수 없을 때를 위해, 배포 안내 문서에 '문제 해결' 절을 새로 둘까요? → "문제 해결 절을 새로 둔다 (Recommended)"

— 설명: 배포 안내 문서(deploy/standalone/README.md)에 '문제 해결' 절을 새로 만듭니다. 관리 화면이 열리지 않을 때 서버에서 칠 명령(docker compose ps로 어느 컨테이너가 죽었는지 보기, docker compose logs 뒤에 컨테이너 이름을 붙여 그 컨테이너가 남긴 글 보기)과, 서버와 데이터베이스 준비 명령(migrate)이 멈출 때 찍는 글의 뜻을 한곳에 모읍니다. 제품 코드는 바뀌지 않고 문서가 늘어납니다. 대가: 멈출 때 찍는 글이 바뀌면 이 절도 함께 고쳐야 하므로, 문서를 맞춰 유지하는 일이 늘어납니다. 이 문서가 배포 파일 묶음과 어긋나지 않는지 보는 시험이 있어(tests/tools/test_deploy_guide.py의 첫 줄을 읽었습니다. 무엇을 검사하는지는 아직 읽지 않았습니다) 절을 더할 때 그 시험도 함께 봐야 합니다.

추천과 같은 답이다.

### 서브에이전트의 조사(관리 화면, 관리 API, 로그, 접속 코드)

라운드 2의 답으로 필요해진 사실을 Explore 서브에이전트가 찾았다. 아래는 그 보고에서 설계에 쓰는 것만 옮긴 것이고, 따로 적지 않은 것은 모두 코드를 읽은 것이다(파일과 줄은 보고가 적은 것이다. 내가 다시 연 줄은 다음 절에 따로 적는다).

- 관리 화면의 페이지는 다섯(`/`, `/plugins/[kind]/[name]`, `/runs`, `/runs/[runId]`, `/settings`)이고, 왼쪽 탐색 항목은 플러그인·실행·설정 셋이다(`web/apps/admin/components/organisms/AdminNav.tsx` 423~427줄).
- 플러그인 목록은 `/` 한 화면에만 있고, 탭 없이 종류별 구역 넷(에이전트, MCP, 스킬, 모델)이 세로로 놓인다. 행마다 켜고 끄는 스위치 하나와 "매니페스트" 링크 하나가 있고, 읽히지 않는 매니페스트의 행에는 "읽을 수 없는 매니페스트: <이유>" 한 줄이 붙는다(`web/apps/admin/components/organisms/PluginList.tsx`의 `KIND_NAMES` 15~20줄과 `Row` 177~225줄. 보고가 적은 줄 번호 136~141, 298~346은 226줄인 이 파일과 맞지 않아 내가 파일을 다시 읽었다. 보고의 다른 화면 파일 줄 번호는 대 보지 않았다).
- 모델만 모아 다루는 화면은 없다. 모델은 플러그인 목록의 "모델" 구역으로만 나온다.
- 플러그인 상세 페이지는 이름, 켜짐 표시, 매니페스트 전체(JSON)를 보여 주고, 누를 수 있는 것은 목록으로 돌아가는 링크 하나다(`PluginDetail.tsx` 369~395줄).
- 관리 화면 어디에도 agent-os의 판 번호가 나오지 않는다. 손으로 봤다(Grep `version|버전|0\.0\.0`, 범위 `web/apps/admin`의 ts·tsx). 판을 돌려주는 관리 경로도 없다.
- 플러그인 관련 관리 경로는 셋이다. `GET /plugins`, `GET /plugins/{kind}/{name}`, `PUT /plugins/{kind}/{name}/enabled`(본문 `{"enabled": 불린}`, 응답 204)(`openapi.json` 2334~2562줄, `src/agent_os/admin/http.py` 120~196줄).
- 관리 라우터는 `PluginSource`와 `TraceStore`만 받고 도구 포트를 받지 않는다. 관리 조회가 MCP 서버를 띄울 수 없게 일부러 막아 둔 것이다(ADR 0010)(`src/agent_os/server.py` 65~67·112줄, `admin/http.py` 132줄).
- `serve`에는 자기 로거도 로그 설정도 없다. `logging`을 쓰는 곳은 `adapters/mcp.py`의 필터 하나다. 응답이 400 이상이면 stderr에 `요청 실패: request_id=… status=… <내용>` 한 줄을 쓰고, 경로와 주체는 일부러 적지 않는다(`src/agent_os/http/errors.py` 389~412줄). 성공한 관리 동작을 남기는 코드는 찾지 못했다. uvicorn의 접근 로그가 켜져 있는지는 어림이다(끄는 인자가 `main.py` 233~253줄에 없다는 것만 읽었다).
- `serve`가 시작할 때 사이트 파일, 두 토큰, 기본 모델의 문제는 진단을 stderr에 쓰고 종료 1로 끝난다. `rules.toml`이 깨진 것과 다른 플러그인의 매니페스트가 깨진 것은 뜬 채로 실행만 실패한다(`main.py` 223~232, 380~432, 547~571줄).
- MCP 어댑터가 구현하는 포트는 `ToolSource.connect(servers)`이고, 서버 하나를 여는 `_opened(name, server)`는 포트에 드러나지 않은 어댑터 안의 함수다. 원격 방식의 기한은 `httpx2.Timeout(30, read=300)`이다. 프로그램 방식(stdio)에는 프로세스가 뜨지 않거나 답하지 않을 때의 기한이 어댑터 안에 없고, 지금은 실행 기한(600초)만 걸린다(`adapters/mcp.py` 215~344줄, `core/run.py` 204줄).
- 꺼 둔 MCP 플러그인을 열지 않게 막는 곳은 어댑터가 아니라 core의 실행 준비다(`core/run.py` 1734~1759줄). 어댑터는 넘겨받은 서버를 모두 연다.
- 모델을 만드는 포트는 `ModelSource.build(manifest)`이고, 만들 때는 키도 네트워크도 요구하지 않는다. 모델 서버에 닿는지만 확인하는 함수는 없다. 손으로 봤다(Grep `def ping|def probe|def check|health|/models|models.list`, 범위 `src/agent_os`). Anthropic 쪽 키를 라이브러리가 환경에서 스스로 읽는다는 것은 어댑터의 독스트링을 읽은 것이고, 라이브러리의 동작은 어림이다.

### 내가 다시 연 것

보고의 사실 가운데 다음 라운드의 선택지에 넣는 것은 원문을 다시 읽었다.

- "관리 라우터는 플러그인과 트레이스 포트만 받는다. 도구 포트를 받지 않으므로 조회 하나가 MCP 서버 여럿을 띄우는 것이 구조적으로 불가능하다"(`src/agent_os/server.py` 65~66줄의 독스트링). 같은 결정이 ADR 0010 155~157줄(2026-09-24 이력)과 `.claude/rules/admin.md`의 첫 항목에 있다. 접속 확인은 관리 쪽의 동작이 MCP 서버를 여는 일이라 이 결정을 고쳐야 한다.
- 관리 라우터의 시그니처는 `admin_router(*, health, plugins, trace)`이고, 켜고 끄는 경로는 `PUT /plugins/{kind}/{name:verbatim}/enabled`다(`src/agent_os/admin/http.py` 112, 180~196줄).
- 실패한 요청의 기록 한 줄은 `AssignRequestId`가 쓰고, 경로도 주체도 적지 않는다. 감사 로그는 비목표다(`src/agent_os/http/errors.py` 390~392, 408~411줄).

## 라운드 3

질문 넷을 한 화면에 올렸다. 화면 곁의 글에서 내가 읽은 방향(진단 페이지와 데이터베이스 표를 두지 않고, 접속 확인을 그 대상을 다루는 화면에 붙이며, 서버가 뜨지 않을 때는 배포 안내의 문제 해결 절이 맡는다)을 먼저 적었고, 틀렸으면 바로잡아 달라고 했다. 방향을 고친 답은 없었다.

추천(확인할 때마다 결과 한 줄)과 다른 답이다. 라운드 2의 "로그에 남고"는 새 기록을 남기라는 뜻이 아니라 지금 남는 것으로 충분하다는 뜻이었다고 읽는다.

### 폴링을 묻기 전에 대 본 것

- 관리 화면의 읽기는 주기적으로 되풀이하지 않고, 창으로 돌아올 때 다시 읽는다(`web/apps/admin/hooks/queries/admin/index.ts` 15·17줄의 `revalidateOnFocus: true`, `refreshInterval: 0`을 Grep으로 확인했다).

> 사용자: 플러그인 화면에서 접속 확인을 어떤 방식으로 일으킬까요? → "원격·모델은 자동, 프로그램 방식은 버튼 (Recommended)"

— 설명: 플러그인 화면이 열려 있는 동안, 켜 둔 원격 방식의 MCP 서버와 모델은 화면이 정해진 간격으로 스스로 확인해 행마다 상태를 보여 줍니다(간격의 값은 명세가 정합니다). 누를 것이 없습니다. 프로그램 방식의 MCP 서버만 행에 '접속 확인' 버튼을 두고, 누를 때만 그 프로그램을 한 번 띄워 봅니다. 그래서 화면을 보는 것만으로는 프로그램이 뜨지 않습니다. 대가: 화면이 열려 있는 동안 간격마다 원격 서버와 모델 서버에 요청이 가고, 탭을 여러 개 열면 그만큼 늘어납니다. 확인 방식이 두 가지라서 만들 것과 설명할 것이 가장 많습니다. 관리 화면 쪽이 MCP 서버에 붙지 않는다는 지금의 결정(ADR 0010. src/agent_os/server.py의 설명과 그 ADR을 읽었습니다)은 '자동 확인은 네트워크 요청만 하고, 프로그램은 운영자가 누른 때만 뜬다'로 고쳐야 합니다.

추천과 같은 답이다. 다른 선택지는 "전부 자동(폴링)", "열 때와 돌아올 때만 자동", "전부 버튼"이었다. 라운드 3의 첫 질문(버튼의 자리)은 이 답으로 닫혔다. 프로그램 방식의 버튼은 목록의 행에 두고, 원격 방식과 모델의 상태도 같은 행에 보인다.

[제가 채운 것] ⑪ 확인은 브라우저가 아니라 서버(serve)가 하고, 화면은 새로 두는 관리 API를 부릅니다. 이 API는 계약(openapi.json)의 변경이라 기능의 첫 티켓이 되고, 모양은 명세가 정합니다. ⑫ 자동 확인의 길은 프로그램을 띄울 수 없게 코드 구조로 막고, 꺼 둔 것을 확인하지 않는 것도 화면이 아니라 서버가 지킵니다. ⑬ 확인마다 기다리는 시간의 한도를 둡니다(값은 명세가 정합니다). ⑭ 붙지 못한 까닭(예: 서버가 꺼짐, 토큰이 맞지 않음)을 그 행에 글로 보입니다. MCP 서버의 글은 실행이 접속에 실패했을 때 남는 글과 같은 것을 쓰고(이 기능이 서버 하나를 여는 같은 접속 코드를 다시 쓴다고 ADR 0049의 55줄이 적어 두었습니다), 모델의 글은 명세가 정합니다. 결과는 화면에만 있고 화면을 떠나면 사라집니다. ⑮ 에이전트와 스킬의 행, 플러그인 상세 페이지에는 두지 않습니다. ⑯ 원래 계획에 있던 구성 보기, 최근 실패 원인, 트레이스의 글 싣기는 이 기능에서 빼고 지금의 화면 그대로 둡니다(구성은 플러그인 상세 페이지가, 실패 원인은 실행 상세 페이지가 이미 보여 줍니다. 두 화면의 코드를 읽었습니다). ⑰ 수락 조건은 '일부러 깨뜨린 배포(모델 서버 꺼짐, MCP 서버 꺼짐, 토큰 불일치)에서 플러그인 화면만 보고 원인을 가를 수 있다'로 바꿉니다. ⑱ 모델 목록 요청에 요금이 붙는지와 로컬 모델 서버가 그 요청에 답하는지는 명세 단계에서 실제로 돌려 확인합니다. ⑲ 새 ADR 하나를 쓰고, '관리 라우터는 도구 포트를 받지 않는다(조회가 MCP 서버를 띄우지 못한다)'는 ADR 0010의 결정(그 ADR 155~156줄의 이력을 읽었습니다)에 바뀌었다는 표시를 답니다. ADR 초안은 셀프 리뷰 뒤에 따로 보여 드리고 승인받습니다.

추천과 같은 답이다. frontier가 비었고 사용자가 공유된 이해를 확인했으므로 설계 인터뷰를 닫는다. 기능의 새 이름은 `connection-check`다. 이 일지의 파일 이름과 브랜치 이름(`docs/diag-bundle-design`)은 인터뷰를 시작할 때의 이름 그대로 둔다.

## 용어와 ADR 초안

`domain-modeling` 스킬을 불러 용어집과 ADR을 썼다. 이 구간은 대화가 한 번 요약된 뒤에 이어 한 것이라, ADR이 근거로 드는 자리는 요약에 기대지 않고 다시 열었다.

### 쓰기 전에 다시 연 것

- `src/agent_os/core/ports.py` 478~491줄(`ModelSource`의 독스트링. 메서드는 하나이고 동기이며 만들 때 키도 네트워크도 요구하지 않는다)과 536~546줄(`ToolSource.connect`)을 Grep으로 읽었다.
- `src/agent_os/admin/http.py` 112줄(`admin_router(*, health, plugins, trace)`)과 118~147줄(주석 "이 라우터는 도구 포트를 받지 않는다")을 읽었다. `.claude/rules/admin.md` 전체를 읽었다(첫 항목이 "관리 라우트는 409도 429도 내지 않는다"를 적는다).
- ADR 0012의 1~30줄을 읽었다. 새 포트를 만들지 않는 기준은 "닿는 바깥 지점이 그대로"이고, 관리가 자기 Protocol을 선언하는 안은 그 ADR이 거부했다.
- ADR 0049의 1~62줄, ADR 0010의 140줄부터 끝, ADR 0046의 28~49줄과 200줄부터 끝, ADR 0048의 14~53줄을 읽었다.
- `src/agent_os/adapters/mcp.py`를 `같은 이름|TimeoutError|fail_after|move_on_after|Timeout\(`로 Grep했다. 나온 줄은 72·165줄(두 서버가 같은 이름의 도구를 낼 때의 문구), 344줄(원격의 기한 `httpx2.Timeout(30, read=300)`), 384줄(닫을 때의 유예)뿐이다. stdio를 여는 동안의 기한이 그 파일에 없다는 서브에이전트의 보고와 맞는다.
- `docs/adr`를 `도구 포트|MCP 서버에 붙지 않|서버를 띄우지|진단 묶음|진단을 낸다|진단\(`로 Grep했다. 나온 자리는 ADR 0010(155·156줄), 0012(24줄), 0046(43줄), 0048(23줄), 0063(8줄)이다. 이름으로 들지 않은 ADR 가운데 이 결정에 걸리는 문장을 찾으려는 것이었고, 0063의 8줄이 새로 나왔다.
- 용어집에서 MCP 서버, 전송, 원격 MCP 서버, 모델, 모델 서버, 관리, 관리 화면, 공개 계정의 항목을 Grep과 Read로 읽었다.

### 용어

`CONTEXT.md`에 **접속 확인(Connection Check)**을 모델 서버 항목 뒤에 더했다. 켜 둔 mcp 종류와 model 종류의 플러그인이 가리키는 바깥 서버에 관리가 실제로 붙어 보고, 붙었는지와 붙지 못한 까닭을 운영자에게 알려 주는 일이다. 피할 말에는 진단(없앤 기능의 말), 헬스 체크와 상태 확인(컨테이너와 `/health`가 프로세스가 살아 있는지 보는 것), 핑, 연결 테스트, 도구 연결(실행 하나의 상태)을 적었다. 관리의 정의에는 접속 확인을 한다는 구절을 더했다. 인터뷰에서 쓴 '폴링'은 용어집의 다른 항목이 피할 말로 들고 있어, ADR에서는 "화면이 정해진 간격으로 스스로 되풀이해 확인한다"로 적었다.

### ADR 0067 초안

`docs/adr/0067-connection-check-lives-on-the-plugin-screen-and-there-is-no-diagnostic-bundle.md`를 썼다. 번호는 `docs/adr`의 가장 높은 번호 0066 다음이다. 쓰기 전에 `uv run python tools/sibling_overlap.py`가 "번호 겹침 없음", "함께 고친 파일 없음"으로 끝났다(손으로 봤다). 결정의 원문은 위 라운드들의 `> 사용자:` 인용과 라운드 5의 확인받은 요약이다.

확인받은 요약에 없던 것을 ADR이 더했다. ADR 승인을 받을 때 따로 보인다.

- 붙지 못한 확인과 꺼 둔 플러그인의 확인 요청에 오류 응답이 아니라 성공 응답의 결과로 답한다. 오류 응답은 서버 표준 에러에 실패 한 줄을 남기므로, 화면이 되풀이하는 확인이 꺼진 서버를 만날 때마다 그 줄이 쌓이면 "따로 남기지 않는다"는 답과 어긋난다. 에러 코드 어휘 여섯과 "관리 라우트는 409도 429도 내지 않는다"도 그대로 선다.
- 포트는 다섯 그대로이고 `ToolSource`와 `ModelSource`에 접속 확인의 메서드를 더한다. 닿는 바깥 지점이 그대로라 ADR 0012의 기준으로 새 포트가 아니다. 관리 라우터는 `ToolSource.connect`를 여전히 받지 않는다. 화면이 스스로 하는 확인의 길이 stdio MCP 서버를 받지 못하게 타입으로 가르는 모양은 pyright로 재 보지 않은 구상이고(어림), 명세의 프로브에 넘겼다.
- 프로세스를 띄우는 확인은 조회가 아닌 요청이고 요청 하나가 서버 하나만 연다. 느린 서버 하나가 다른 행의 결과를 막지 않는다.
- 요약 ⑲는 ADR 0010의 결정에 "바뀌었다는 표시를 단다"고 적었다. 그 문장은 ADR 0010의 지난 이력(2026-09-24)에 있고 지난 이력에는 포인터를 달지 않으므로(`.claude/rules/adr.md`), 표시는 ADR 0010의 새 이력 항목으로 했다.
- ADR 0048의 본문 한 문장과 ADR 0049의 굵은 요약 한 문장에도 포인터를 달았다(요약은 ADR 0010만 들었다).

### 다른 ADR에 단 것

- ADR 0010: 이력 `2026-11-20 관리 라우터가 접속 확인을 받고 도구 연결을 여는 길은 여전히 받지 않는다`를 더했다.
- ADR 0046: 이력 `2026-11-20 diag-bundle이 connection-check로 바뀌고 진단 묶음 대신 관리 화면의 접속 확인이 선다`를 더하고, 기준선 표의 diag-bundle 행에 그 이력의 포인터를 달았다.
- ADR 0048: 결정 "배포와 운영은 데이터를 가진 저장소가 맡는다"의 끝에 `(바뀜: ADR 0067)`을 달았다.
- ADR 0049: 굵은 요약의 "재시도와 미리 확인은 없다" 뒤, 결정 "범위 밖"의 끝, Consequences "뒤 기능이 기대는 것"의 diag-bundle 문장 뒤에 `(바뀜: ADR 0067)`을 달았다.
- 달지 않은 것은 ADR 0012(24줄은 글자 그대로 참이다), 0056(거부한 안의 근거), 0063(그 ADR이 그 규칙을 바꾸지 않았다는 그때의 사실), 0066(그때 한 일의 기록)이고, 까닭은 ADR 0067 Consequences "다른 ADR의 본문"에 적었다.
- `docs/adr/README.md`의 색인에 0067 행을 더했다.
- `uv run python tools/check_adr_pointers.py`는 출력 없이 끝났다(손으로 봤다).

### 기능 계획과 다른 문서

- `git mv`로 `.scratch/diag-bundle`을 `.scratch/connection-check`로 옮기고 계획을 새 설계로 다시 썼다. `**Blocked by:**` 뒤에 `**설계:** ADR 0067`을 더했다. 앞 기능들이 넘긴 사실 가운데 문제 해결 절이 쓸 것(판을 읽는 다른 길, 위젯과 관리 화면이 뜨지 않을 때의 글, `serve`와 `migrate`가 멈출 때의 글과 종료 코드)은 남겼다. "단독 배포의 컨테이너는 다섯"은 지금 일곱이라(위 "배포 쪽"의 보고) 그 수로 고쳤다.

- `.scratch/postgres-foundation/spec.md`: 사용자 이야기 37, 시험을 다루는 절의 한 문장("운영자와 진단 묶음이 그 글을 읽기 때문이다"), Out of Scope의 한 항목을 고쳤다. 셋째 자리는 라운드 4 뒤에 찾은 둘(102·434줄)에 없던 것이고, `진단 묶음|묶음이`로 그 명세를 Grep해 403줄에서 찾았다. 그 기능의 티켓을 다른 세션들이 진행하고 있어 문장 셋만 고쳤다.

1. Major(CLI). ADR 0067 결정 "비밀"이 MCP 서버의 글은 실행의 가리기를 "그대로 지난다"고만 적었는데, 그 가리기는 짧은 값을 가리지 않는다. **유효, 고쳤다.** ADR 0049의 89줄을 읽었다. 그 이력의 "남는 한계"가 서버가 값을 바꿔 되울린 것과 8자보다 짧은 값을 놓친다고 적는다. 실행에서는 놓친 글이 트레이스에 남지만, 접속 확인에서는 플러그인 화면의 행에 바로 보인다. 그래서 한계를 결정에 적고, 서버가 쓴 글을 화면에 그대로 보일지를 명세에 넘겼다.
2. Major(CLI). ADR 0067 결정 "모델을 확인하는 법"이 모델 목록이 여러 쪽으로 나뉘어 오는 경우를 다루지 않는다. **유효, 고쳤다.** 리뷰어가 든 SDK의 기본 쪽 크기는 리뷰어의 기억이고 이 세션이 확인하지 않았다. 그래서 수는 옮기지 않고 "대 보지 않았다"로 적어 명세의 프로브에 넘겼다.
3. Minor(CLI). ADR 0067 결정 "`serve`가 뜨지 않을 때"와 기능 계획이 `.env`의 `AGENT_OS_VERSION`을 지금 떠 있는 판으로 적었는데, `.env`만 고치고 다시 띄우지 않으면 둘이 어긋난다. **유효, 고쳤다.** compose가 `.env`를 띄울 때 읽는다는 데서 끌어낸 어림이고 재 보지 않았다. 그렇게 적고 명세에 넘겼다.
4. CLI는 Critical, 서브에이전트는 Minor로 본 것. MCP 서버 주소의 쿼리 문자열이 로그에 남는다. **유효로 보고 고쳤다. 심각도는 Minor로 본다.** 주소가 글과 로그에 실리는 것은 ADR 0049가 알려진 한계로 받은 것이다(그 ADR 결정 "주소는 매니페스트에 그대로 적는다"). 새로 생기는 것은 되풀이다. `.scratch/mcp-http/spec.md`의 127줄과 `.scratch/mcp-http/probes/README.md`의 62줄을 읽었다. httpx2의 로거가 INFO로 주소 전체와 응답 상태가 든 줄을 찍고, 기본 WARNING에서는 나오지 않는다. 화면이 되풀이하는 확인은 로그 수준을 낮춘 배포에서 그 줄을 간격마다 더하고, 그 줄의 응답 상태로 붙었는지가 드러나 "서버 로그에 남기지 않는다"는 결정과 맞닿는다. 그래서 결정 "결과가 있는 자리"에 적고 명세에 넘겼다.
5. Minor(서브에이전트의 관찰). stdio 확인에 기한이 있는지와 같은 플러그인의 확인이 겹칠 때. **ADR은 그대로 두고 명세에 넘겼다.** ADR 0067이 이미 확인마다 기다리는 시간의 한도를 두고 그 값을 명세에 넘겼으며, 겹침도 Consequences "버튼을 연달아 누를 때"가 명세에 넘겼다. 더한 것은 `serve` 쪽에서도 줄일지를 묻는 한 줄이다(아래 기능 계획의 넷째).
6. Minor(서브에이전트의 관찰). 확인 간격의 하한과 서버 쪽 상한이 없다. **ADR은 그대로 두고 5와 같은 줄로 명세에 넘겼다.** 화면이 간격을 두는 것만으로는 관리 경로를 직접 되풀이해 부르는 요청을 막지 못한다.

고친 것은 다음과 같다. ADR 0067은 사용자가 승인한 글이라, 결정을 바꾸지 않고 한계를 밝히는 문장만 뒤에 더했다. 더한 문장은 원문으로 옮긴다.

- ADR 0067 결정 "모델을 확인하는 법": "목록이 여러 쪽으로 나뉘어 올 때 요청 한 번으로 model id가 있는지를 가를 수 있는지도 대 보지 않았다." 그 뒤의 문장은 "요금이 붙거나, 그 요청에 답하지 않는 서버가 있거나, 요청 한 번으로 가를 수 없으면, 명세를 쓰는 같은 작업에서 그 결과와 함께 이 항목을 이력으로 다시 정한다."로 넓혔다.
- ADR 0067 결정 "결과가 있는 자리": "로그 수준을 INFO나 DEBUG로 낮춘 배포에서는 서버 로그에 남는 것이 더 있다. 실행이 원격 MCP 서버에 붙을 때 httpx2의 로거가 요청마다 한 줄을 INFO로 찍고, 그 줄에는 서버의 주소 전체(쿼리 문자열까지)와 응답 상태가 든다" 뒤에 근거의 괄호를 달았고, 이어서 "접속 확인은 같은 길로 붙으므로 같은 줄이 찍힐 것으로 본다(접속 확인으로 잰 것은 아니다). 그 줄에는 응답 상태가 들어 붙었는지를 알 수 있고, 화면이 되풀이하는 확인은 그 줄을 간격마다 더한다. 모델 쪽 요청이 같은 줄을 남기는지는 대 보지 않았다. 접속 확인의 길에서 그 로거를 어떻게 둘지는 명세가 정한다."를 적었다. 근거의 괄호를 처음에는 프로브 경로 없이 "쟀다"로 적어 훅이 알렸고, 프로브 파일(`.scratch/mcp-http/probes/http_close.py`의 `unauthorized` 사례)과 결과가 있는 자리를 가리키게 고쳤다.
- ADR 0067 결정 "비밀": "그 가리기가 놓치는 것은 접속 확인에서도 놓친다. 서버가 값을 바꿔 되울린 것과 8자보다 짧은 값이다(같은 이력의 "남는 한계"). 그래서 첫 문장은 그 범위 안에서만 참이다. 실행에서는 놓친 글이 트레이스에 남고, 접속 확인에서는 플러그인 화면의 행에 보인다. 서버가 쓴 글을 화면에 그대로 보일지, `serve`가 지은 글(응답 상태 같은 것)만 보일지는 명세가 정한다."

- CodeRabbit은 한도에 걸려 리뷰를 내지 않았다. 요약 코멘트의 머리가 `Review limit reached`이고, `@coderabbitai review`에는 `Review rate limited`로 답했다(같은 출력). 리뷰가 없던 푸시라 CodeRabbit의 회차로 세지 않는다(`merge.md` "병합 전" 2의 회차 세기).
- 인라인 코멘트와 리뷰는 없다. `gh api repos/{owner}/{repo}/pulls/614/comments --paginate`의 출력이 `[]`이고 `gh pr view 614 --json reviews`의 목록이 비었다(둘 다 파일로 받아 읽었다).

고칠 지적이 없어 이 회차에 고친 것은 없다. 그래서 일지와 대기열 항목만 실은 커밋을 푸시한다(`merge.md` "병합 전" 4). 그 푸시로 도는 리뷰는 claude-review의 둘째 회차로 세고, CodeRabbit이 리뷰를 내면 그 봇의 첫 회차로 센다. 그 리뷰에서 보류하는 일이 나오면 일지에 다시 적어 푸시하지 않고 PR 코멘트와 다음 지시문의 "이어받을 상태"에 적는다(같은 문서 2의 "뒤로 넘긴 일").

## 회고

이 일지의 두 세션(설계 인터뷰를 한 앞 세션, 셀프 리뷰부터 이어받은 이 세션)을 함께 봤다. 사건은 이 일지와, 일지에서 사건을 뽑게 한 서브에이전트의 보고에서 모았다. 낸 후보는 열일곱이다. 승인이 열(있던 항목에 회차를 더한 것 여섯, 새 항목 넷), 기각이 일곱이고 넘긴 것은 없다. 대기열에서 만료한 항목이 다섯이다.

있던 항목에 회차를 더한 것(열린 항목이 이미 처방한 사건이다).

- `handoff-trigger-before-background-commit-ends` 10회차. 인계 계기가 커밋 명령이 백그라운드로 넘어간 직후에 두 번 왔고(277,152·348,898 토큰) 두 커밋 모두 뒤에 실패했다. 경계가 아니어서 넘기지 않았고, 매번 `handoff.md`의 판정을 다시 따졌다.
- `0563` 6회차. 커밋의 인용 검사 경고 열둘이 선택 화면의 라벨 다섯, 고치기 전의 글 넷, 커밋된 적 없는 글 셋이었고 줄마다 열어 가렸다(위 둘째 커밋 시도 절).

- `cli-review-claims-path` 8회차. PR 직전 리뷰에서 CLI가 돌아, 셀프 리뷰 반영으로 새로 쓴 문장들을 겨냥할 주장으로 넘길 길이 없었다(위 "PR 직전 리뷰" 절). 따로 띄운 리뷰는 없었고 그 문장들은 CLI의 전체 리뷰만 거쳤다.

### 이어받은 세션(푸시부터)이 더한 것 (2026-11-21)

푸시부터 이어받은 세션의 새 사건만 봤다. 후보는 셋이고 승인이 하나(있던 항목에 회차를 더했다), 기각이 둘이다.

- 승인. `directive-length-bound-at-writing` 2회차. 앞 세션의 첫 `open-session`이 URL 8339자로 쏘기 전에 멈췄고, 지시문의 네 줄을 줄여 다시 열었다(위 "인계 (커밋 뒤)" 절의 끝). 앞 세션이 회차 대조를 이 세션에 넘겼다. 그 항목의 승인 줄은 1회차였고 이 "회고" 절은 그 항목에 회차를 적은 적이 없어 하나를 더했다(항목 파일을 읽었다).
- 기각. CodeRabbit이 한도에 걸려 PR의 첫 푸시에 리뷰를 내지 않았다. 규약이 이미 다룬다(리뷰가 없던 푸시는 회차로 세지 않는다). 보안·버그·성능 축은 PR 직전에 CLI가 끝까지 돌아 봤다(위 "PR 직전 리뷰" 절). `uv run python tools/queue_open_rows.py --search rate.limit --search Review.rate --search 리뷰.한도`에 맞은 항목 아홉은 모두 닫힌 항목이었다(그 출력을 읽었다).
- 기각. 승인 화면을 훅(`hook_choice_facts`)이 한 번 막았다. 훅이 그 자리에서 막았고, 막힌 뒤 어댑터의 독스트링에 한 번 더 대고 같은 화면을 올렸다. 앞 세션의 같은 기각과 같은 꼴이다.

`handoff-trigger-before-background-commit-ends`의 10회차 글에 앞 세션이 더한 사건(리뷰 반영 커밋을 띄운 직후의 계기 하나)은 회차 수를 바꾸지 않는다. 앞 세션이 커밋하지 못한 그 편집을 이 세션의 커밋에 실었다.

## 다음

푸시, PR 열기(#614), ADR 0067에 뒤에 더한 한계 넷의 사용자 승인, 봇의 첫 회차는 끝났다(위 "이어받은 세션: 푸시부터"). 이 세션에 남은 일은 이 일지를 실은 커밋의 푸시, 그 푸시로 도는 봇 회차, 병합이다. 그 경과는 일지에 다시 적어 푸시하지 않고 PR 코멘트에 적는다.

병합 뒤의 다음 단계는 connection-check의 명세다(`.scratch/connection-check/plan.md`, `**설계:** ADR 0067`).
