## 조사

세션 스크래치패드의 스크립트로 기록을 읽었다. ADR이 드는 수 대부분은 뒤에 `.scratch/harness/probes/token_usage/measure.py`로
옮겨 단가표(`session_cost/costs.py`)로 다시 셌다(그 README의 결과). 아래에서 그 프로브에 없는 수(general-purpose 44개와
그 68%, sonnet 서브에이전트 19개, 316호출 세션의 구간, 상위 세션 열 가운데 아홉)는 스크래치 스크립트로만 셌다. 인터뷰
도중에 말한 수는 근사 가중치(입력 1, 캐시 읽기 0.1, 캐시 쓰기 1.25, 출력 5)였고 두 폴더에 겹친 세션 기록을 두 번
셌다. 아래 "고친 것"에 그 차이를 적는다.

- **원인의 갈래.** 메인 세션이 비용의 대부분이었다(프로브 최종 판 기준 24시간 87.0%). 비용 상위 메인 세션 열 가운데 아홉은 브랜치
  하나, PR 하나였고 컨텍스트가 50만~96만 토큰까지 압축 없이 커졌다. 한 세션(`canary-commit-control-and-precheck`, 316호출)을
  구간으로 나누니 구현 46분 동안 8.6만에서 45.9만으로 늘었고, Bash 결과와 Read 결과가 그 구간 글자의 절반을 넘었다.
- **서브에이전트.** 지난 24시간 general-purpose 44개는 모두 6.5만 토큰 안팎에서 시작했고, 비용의 약 68%가 셀프 리뷰 두
  축이었다. 48시간 동안 sonnet 서브에이전트 가운데 19개가 `xhigh`였다(같은 집계에 `medium` 42개도 있었다). 노력을
  지정받지 않은 서브에이전트가 메인 세션의 노력으로 도는 것으로 본다(어림, 부모 세션과 짝지어 보지 않았다).
- **CI 대기.** `tools/wait_ci.py` 대기 뒤 깨어난 호출은 비용의 0.08%였고 캐시를 다시 쓰지 않았다. 60분 넘게 쉰 뒤에는 거의
  모두 다시 썼다. 메인 세션 캐시는 대부분 1시간 TTL이었다.
- **레벨 스윕.** 메인 세션 비용에서 Opus 5.5 `xhigh`가 가장 컸다. 진행 중인 레벨 스윕(ADR 0029 이력 2026-10-13, 2026-12-15
  판정)의 갈래다.
- **Claude Code 설정(claude-code-guide 서브에이전트가 공식 문서를 WebFetch로 받았다. 모두 웹 요약이고 바이트 대조는
  하지 않았다).** 자동 압축 창은 `autoCompactWindow`와 `/autocompact`로 바꿀 수 있고 1M 모델은 약 96.7만 토큰에서 압축한다
  (https://code.claude.com/docs/en/model-config.md). 프로젝트 설정의 `enabledPlugins` `false`는 그 프로젝트에서 사용자
  설정을 이긴다(https://code.claude.com/docs/en/plugins/loading.md). 사용자 범위 MCP는 `/mcp`로 프로젝트별로 끌 수 있다
  (https://code.claude.com/docs/en/mcp.md). 서브에이전트의 노력은 프런트매터 `effort`와 Agent 호출의 `effort`로 정한다
  (https://code.claude.com/docs/en/sub-agents.md). 훅이 `/compact`를 실행하는 방법은 찾지 못했다
  (https://code.claude.com/docs/en/hooks.md, 앞 200K자만 읽었다). opusplan은 계획 모드에서 opus, 그 밖에서 sonnet이다
  (https://code.claude.com/docs/en/model-config.md).
- **실제 압축.** 기록의 압축 17건(포크 사본과 시험 세션을 뺐다) 가운데 12건 뒤에 세션은 117~341번 더 호출했고, 압축
  직후 사람이 맥락을 다시 설명한 글은 없었다(입력 글을 읽은 판단이다).

## 인터뷰

`grilling` 라운드로 물었다. 사용자가 고른 것은 라벨을, 직접 쓴 답은 그 글을 옮긴다. 직접 쓴 답이 선택지 번호를 가리키면
그 선택지의 라벨과 설명을 함께 옮긴다.

> 사용자: (Playwright — Playwright MCP 두 벌을 어떻게 할까요?) "플러그인판만 남김 (Recommended)" — 설명: 사용자 범위의 중복 playwright MCP 서버를 ~/.claude.json에서 지우고, 플러그인판은 모든 프로젝트에 남깁니다. 도구 이름 50개가 줄고 나중에 쓸 수도 있습니다.

> 사용자: (도구 위치 — 경고 훅과 일간 보고서 도구를 어디에 둘까요?) "이 저장소 tools/ + 프로젝트 설정이 호출은 문제가 있어?"

> 사용자: (보고서 지표 — 일간 보고서에 무엇을 넣을까요?) "1번으로 하는데 도움이 될 만한 측정 지표들이 더 있을지 검토해줘." — 1번은 "기본 묶음 + 경보 (Recommended)" — 설명: 계정별·전체 비용(저장소 단가표로 달러 환산), 메인·서브 비중, 모델·노력별, 상위 세션 5개, 40만 넘은 세션 수, 휴지 뒤 재작성, 시작 컨텍스트 중앙값, 서브에이전트 유형별. 하루 비용이 지난 7일 중앙값의 1.5배를 넘는 등 이상치는 경보 줄로 맨 위에 올립니다.

에이전트는 묶음 티켓(이름에 `and`·`batch`가 든 것, 어림)이 상위에 많지만 티켓마다 고정 절차 비용이 있어(PR 뒤 비용 몫
하네스 34%, 구현 27%, `docs/model-selection.md`) 잘게 쪼개는 것만으로는 풀리지 않는다고 답했다. 최근 7일 비용의 93.4%가
이 저장소라 프로젝트 설정 호출에 큰 문제는 없다고 답했다(인터뷰 중 스크래치로 셌다).

### 6라운드

> 사용자: (인계 지점 — 언제 새 세션으로 인계할까요?) "20만 넘은 뒤 첫 단계 경계 (Recommended)" — 설명: 컨텍스트가 20만을 넘은 뒤 '구현 커밋 뒤' 또는 'PR을 연 뒤'가 오면 훅이 모델에게 인계를 지시합니다. 작은 티켓은 나뉘지 않아 인계 비용을 치르지 않습니다.

> 사용자: (추가 지표 — 일간 보고서에 더할 지표를 골라 주세요.) "티켓별 비용과 PR 전후 몫 (Recommended)" — 설명: 브랜치마다 비용, PR 전후 비중, 인계 횟수를 냅니다. 소급 측정의 중앙값(하네스 $36.1, 구현 $45.5)과 견주어 티켓이 너무 커지는지 봅니다. "캐시 효율" — 설명: 요청당 평균 컨텍스트, 캐시 읽기 비율, 60분 휴지 뒤 재작성 토큰을 냅니다. 캐시가 깨져 비싸게 다시 쓰는 낭비를 잡습니다. "큰 도구 결과와 반복 Read" — 설명: 2만 자가 넘는 Bash·Read 결과와 여러 세션에서 반복해 읽힌 파일 상위를 냅니다. git worktree list, tidy_checkouts.py 같은 후보를 찾습니다. "시작 기본 컨텍스트 구성" — 설명: 스킬 목록·지연 도구 목록·CLAUDE.md·rules 크기의 추이를 냅니다. 플러그인이나 지침이 늘어 모든 요청이 비싸지는 것을 잡습니다.

> 사용자: (훅 등록 — 경고·인계 훅과 계정 기록 훅을 어느 설정에 등록할까요?) "프로젝트 설정 (Recommended)" — 설명: .claude/settings.json에 저장소 훅 규약(래퍼, 테스트, hook_payloads.toml)대로 등록합니다. 비용의 93.4%를 덮고, 다른 프로젝트 세션은 보고서에 '계정 모름'으로 들어갑니다.

> 사용자: (티켓 크기 — 묶음 티켓을 줄이는 규칙을 지금 둘까요?) "보고서로 지켜본 뒤 결정하는데 인터뷰 후 상세 플랜을 설계하고 플랜 파일이 생성 되잖아? 그거랑 티켓이랑 달라? 하나의 플랜이 하나의 티켓이 아닌거야?" — 고른 갈래는 "보고서로 지켜본 뒤 결정 (Recommended)" — 설명: 티켓별 비용 지표로 큰 티켓이 반복되는지 본 뒤, 세 번 반복되면 retro가 규칙 후보로 올립니다(CLAUDE.md 교정 루프).

에이전트는 명세 하나가 `/to-tickets`로 티켓 여럿이 되고, 비용 상위 세션 대부분은 명세 없이 대기열 항목을 묶는 하네스 chore
배치(`next-session` 결정표)였다고 답했다.

### 용어와 문서

> 사용자: 우리 방금 grill with docs로 인터뷰한거야?

> 사용자: domain-modeling, grill-with-docs 스킬들은 disable-model-invocation: false로 못바꿔?

에이전트는 `domain-modeling`은 이미 모델이 부를 수 있고 `grill-with-docs`만 사람 전용이라고 답했고, 바꾸는 일은 별도 세션
제안 카드로 올렸다. 사용자가 그 카드를 시작했다(브랜치 `chore/grill-with-docs-model-invoked`).

> 사용자: 이 세션에서 domain-modeling을 불러 합의한 토큰 최적화 방침의 용어와 ADR 초안을 만들어줘.

> 사용자: (용어 자리 — 하네스 용어를 어디에 정의할까요?) "CONTEXT.md에 하네스 절 신설하는데 컨텍스트 엔지니어링을 위해서 모든 파일을 참고할 때 필요한 부분만 잘라서 가져오도록 하는건 반영되는거지?" — 고른 갈래는 "CONTEXT.md에 하네스 절 신설 (Recommended)" — 설명: '용어집은 하나'(operations.md 55행)를 따라 CONTEXT.md에 '## 하네스' 절을 만들고 위 일곱 용어를 넣습니다. 첫 문장을 '런타임과 그것을 만드는 하네스의 용어집'으로 넓힙니다. 기존 하네스 말(지시문, 대기열 등)은 이번에 소급해 넣지 않습니다. (설명 안의 '용어집은 하나'는 operations.md 55행의 "헌법, 용어집, ADR 번호열은 하나다."를 줄여 쓴 것이다. 셀프 리뷰가 짚었다.)

> 사용자: (부분 읽기 — 큰 파일을 범위 없이 읽는 일을 어떻게 다룰까요?) "알리는 훅 + 보고서 감시 (Recommended)" — 설명: Read와 Bash 출력에서 파일이나 결과가 문턱(예: 2만 자, 값은 명세에서)을 넘으면 모델에게 범위를 주라고 알립니다. 보고서로 지켜보다가 알림 뒤에도 반복되면 막는 훅 후보로 올립니다(tools.md 기준).

> 사용자: 보고서에 시작 기본 컨텍스트 구성에 읽은 파일도 들어가나? 세션을 진행하는 동안 읽은 파일들을 기록하고 그 세션에서 필요없는 파일을 읽었는지 확인하고 싶은데... 보고서에 필요없는데 읽은 파일들을 알려주도록 / 별로 필요없나?

에이전트는 같은 세션에서 바뀌지 않은 파일을 다시 읽은 것을 프로브(`rereads`)로 쟀다. Read 글자의 3.5%였다.

> 사용자: (읽은 파일 — 세션에서 읽은 파일의 낭비를 보고서에 어떻게 담을까요?) "반복 Read 지표에 다시 읽기 한 줄 내용을 참고하기 위해 읽은 파일일 수 있지않아?" — 고른 갈래는 "반복 Read 지표에 다시 읽기 한 줄 (Recommended)" — 설명: 같은 세션에서 바뀌지 않은 파일을 다시 읽은 횟수·글자와 상위 파일을 기존 지표에 더합니다. 지금은 Read의 3.5%이고, 그 절반이 tidy_checkouts.py입니다.

에이전트는 다시 읽기가 정당할 수 있다고 받아 이름을 "다시 읽기 후보"로 바꾸고, 작업 트리를 바꾸는 git 명령 뒤의 읽기를
뺐다. 그래도 3.3%였고 `tools/tidy_checkouts.py`가 그 40%였다.

> 사용자: 근데 이게 도움이 될까? / 도움이 돼?

> 사용자: 아니 위 작업은 다 진행해. 내가 물어본건 (위 "보고서에 시작 기본 컨텍스트 구성에…" 인용) 이게 필요한가? 도움이 되냐였어

에이전트는 질문을 ADR 초안에 대한 것으로 잘못 읽고 "ADR이 도움이 안 된다"고 답했다. 사용자가 바로잡았다. 읽은 파일을 모두
기록해 필요 없던 것을 판정하는 기능은 필요 없고(판정이 의도에 달렸고, 셀 수 있는 다시 읽기는 전체의 약 0.5%), 다시 읽기
후보 한 줄로 충분하다고 답한 뒤 멈췄던 ADR을 이어 썼다.

- [Nit] 다른 문서를 행 번호로 가리킨다, [Nit] 독스트링의 가운뎃점 뒤 공백.

셋째 회차(리뷰 반영 헤드 `9995895`)는 새 지적으로 Minor 하나(`cmd_compactions` 한 함수에 파일 순회, 경계 찾기, 집계,
판별, 출력이 섞였다. `CODING_STANDARDS.md`의 추상화 수준)와, 앞 회차와 같은 Minor 둘·Nit 둘이었다. 프로브라 두고 PR
코멘트에 이유를 남겼다. 보고서 도구로 옮길 때 함수를 나누고 시험을 붙인다(대기열 273). CodeRabbit은 세 헤드 모두
`Review rate limited`라 리뷰하지 않았다.

일지 번호를 옮긴 헤드(`ca08f39`)에서 CodeRabbit이 이 PR의 첫 리뷰를 냈다. 인라인 Minor 둘이 지금 코드에서 재현되어
고쳤다.

- `simulate`가 첫 호출의 시각을 못 읽으면 측정 전체가 `ValueError`로 끝난다. `calls()`는 `cutoff`가 있을 때만 그 오류를
  잡는데 `cmd_simulate`는 `cutoff=None`으로 부른다.
- `idle`의 호출이 모두 단가표 밖이면 비용 합이 0이라 0으로 나눈다.

첫 판(분모에 `or 1.0`, 세션을 건너뛰고 수를 셈)을 두 축으로 셀프 리뷰했다(표준 축 sonnet, 명세 축은 두 지적을 요구로).

- 표준 축 [하드] 첫 판의 `or 1.0`이 측정 아닌 실행(단가표 안의 호출 0)을 `$0.00`과 종료 0으로 바꾼다
  (`.claude/rules/probes.md` 첫 항목). 고쳤다. `idle`과 `split` 모두 단가표 안의 호출 수를 표지로 보고 2로 끝나며,
  `idle`도 단가표 밖 호출 수를 찍는다. 그래서 독스트링의 "그 호출 수를 따로 찍는다"가 단가를 쓰는 하위 명령 둘 모두에서
  선다(명세 축도 참고로 냈다).
- 두 축 [Minor] 새 주석 "`cmd_split`과 같이 분모만 1로 둔다"는 사실과 다르다(`cmd_split`은 합을 찍기 전에 1로 바꾼다).
  위 수정으로 그 주석이 없어졌다.
- 두 축 [참고] 시간대 없는 시각은 `ValueError`가 아니라 `TypeError`로 끝난다(`calls`와 `simulate`). 표준 축의 중복 smell
  (시각 해석이 세 자리)과 함께 `time_of()` 하나로 모아, 읽지 못하거나 시간대가 없으면 `None`을 낸다.
- 표준 축 [판단] `no_time`의 이름은 `unreadable_start`로 바꿨다.
- 두었다: 세션이 하나만 남을 때 `statistics.quantiles`가 끝나는 것과, "첫 호출"이 세션 컨텍스트 0인 호출을 거른 뒤의 첫
  호출이라는 것. 둘 다 diff 밖의 기존 동작이고, 72시간 창의 세션은 481개다. 보고서 도구로 옮길 때 시험과 함께 대기열
  273이 든다.

다시 돈 것: 실제 기록으로 `split 24`·`idle 72`·`simulate 72`는 끝까지 출력했다(시각을 못 읽은 세션 0, 단가표 밖 0). 이
실행은 고친 갈래를 지나지 않으므로, 명세 축이 만든 합성 기록 하네스(스크래치)로 다섯 경우를 손으로 돌렸다. 시각 없음·
형식 틀림·시간대 없음은 `simulate`가 "1개 뺌"으로 세고 셋 모두 끝까지 돌았고, 단가표 밖 모델만 있으면 `idle`·`split`이
표지 없음으로 2로 끝났다. README의 실행 기록 수는 바뀌지 않는다(옛 판은 그런 세션에서 멈췄을 것이라 그 실행이 끝까지 돈
것이 0개였다는 뜻이다).

같은 헤드의 claude-review 넷째 회차는 Critical·Major가 없어 두고 PR 코멘트에 이유를 남겼다.

- [Minor] `CONTEXT.md` 하네스 절의 **세션**이 제품 항목들의 `_Avoid_: 세션`과 겹친다. '세션'은 제품이 정의한 용어가 아니라
  제품 항목이 쓰지 말라고 올린 낱말이라 하네스 절 머리말의 "제품 용어와 이름이 겹치면"에 들지 않고, 하네스의 **세션**
  항목이 `_Avoid_: 실행·대화(제품 용어)`로 이미 가른다.
- [Minor] `REPO_PREFIX`를 README "못 보는 것"에 적기. 다른 PC에서는 `plugins`가 이 저장소의 세션 기록을 하나도 고르지
  못해 표지 없음으로 2로 끝나므로 틀린 수를 조용히 내지 않는다. 대기열 273.
- [Nit] 행 번호로 가리키기는 앞 회차와 같다. [Nit] PR 본문의 일지 경로는 푸시 뒤 리뷰가 돈 다음에 고쳤다.

다섯째 회차(`55edd1e`)도 Critical·Major가 없었다. 새 Minor 둘(`reads`·`rereads`·`plugins`가 파일 고르기와 겹침 거르기
루프를 각자 쓴다, `_simulate`와 `GIT_MUTATION`을 고정하는 시험이 없다)과 앞 회차와 같은 Minor 셋·Nit 하나다. 둘 다
보고서 도구로 옮길 때의 일이라 두었다. 그런데 앞 회차들의 PR 코멘트와 이 일지의 "다음"은 함수 나누기와 시험을 대기열
273이 든다고 적었는데, 273의 행은 경로 상수와 타입만 들고 있었다. 받는 쪽에 적지 않고 넘긴 것이라(`code-review` 6단계
4), 273의 "어디로"에 함수 나누기, 공용 반복자, 시험(남은 세션이 하나일 때의 `statistics.quantiles`를 더해. Python
3.12.10에서 데이터 하나로 `StatisticsError`가 나는 것을 손으로 봤다)을 적었다.

## 회고

후보 아홉, 승인 다섯(대기열에 넷, 다른 세션이 반영한 것 하나), 넘김 하나, 기각 셋이다.

- **1-가. 세션 기록에 남은 비밀의 처리.** 넘김(사람만 할 수 있는 외부 계정의 일). 사용자가 답했다. 이 저장소가 공개라
  보안 리뷰(PR 직전) 뒤 사용자 결정으로 그 답과 비밀의 종류·자리는 적지 않는다. 일지 규약의 인용에서 벗어나는 한 번의
  예외다.

  > 사용자: (공개 문장 — 공개 저장소에 올릴 일지와 대기열의 토큰 관련 문장을 어떻게 할까요?) "표적 정보를 빼고 올린다 (Recommended)" — 설명은 표적 정보를 담아 옮기지 않는다.

- **1-나. 사용자 설정 파일을 통째로 출력하는 명령이 비밀을 기록에 남긴다.** 승인. 사건은 이 세션의 설정 출력이고, 실패가
  조용하고 모양이 고정돼 훅 층이며(`hook_env_read` 선례, 대기열 43), PR 하나로 되돌릴 수 있다. 대기열 272.
- **2. 세션 비용을 근사 가중치로, 겹친 기록을 두 번 세어 계산했다.** 승인. 검사로 잡을 수 없는 선택이라 단가표와 측정
  도구를 기본 길로 가리키는 길잡이 층이다. ADR 0033의 보고서 도구가 받는다. 대기열 273.

  후보의 40%(24.5만 자)이고, 그 단계의 스킬 문장 층이다. 대기열 271.
- **4. 워크트리 안의 스킬 사본이 스킬 목록에 섞인다.** 승인. 사건은 72시간 70개 세션(스크래치로 셌다)이고, 기전을 모르니
  프로브부터 둔다. 대기열 274.
- **5. 사람만 부르는 `grill-with-docs`를 미리 알리지 않아 인터뷰가 `grilling`만으로 돌았다.** 승인. 사용자가 시작한 별도
