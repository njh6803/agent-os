# 2026-10-06 (12) 탐색이 디자인 시스템 문서의 재료를 받는다, 색 토큰의 두 층

일지 2026-10-06-09의 세션이 PR #150을 병합한 뒤 이어서 했다. 워크트리 `.claude/worktrees/design-system-design`이고,
origin/main(`88badb1`)에서 `chore/design-system-doc-checklist`를 땄다. 순번은 11을 형제 워크트리
`02-limits-and-backlog`의 일지가 이미 써서 12다.

## 목업은 언제 그리고, 탐색은 무엇인가

PR #150을 여는 사이에 사용자가 두 가지를 물었다.

> 사용자: "UI 목업이랑 와이어프레임 작업은 언제해?"

탐색 2단계의 화면은 방향을 보는 와이어프레임 수준이고, 기능의 UI 목업은 디자인 시스템을 코드로 만들어 `/design-sync`로
올린 뒤 화면이 있는 기능마다 그 명세 직전에 그린다고 답했다(ADR 0025, `docs/agents/issue-tracker.md` 화면 디자인 절).

> 사용자: "보통 디자인 시스템을 이렇게 그려?"

링크가 함께 왔다. 내장 브라우저는 로그인 화면에서 멈췄고, 로그인은 대신하지 않았다. 사용자가 Chrome으로 열기를 골랐으나
Claude in Chrome 확장이 두 번 모두 응답하지 않아 페이지를 보지 못했다.

> 사용자: "실제 디자인 시스템이 아니라 참고용이라는거지?"

그렇다고 답했다. 탐색 결과는 방향을 고르는 재료이고, 실제 디자인 시스템은 코드(`web/packages/ui`)이며, Claude Design의
디자인 시스템 프로젝트는 그 코드를 `/design-sync`로 올린 사본이다.

## 디자인 시스템 문서의 재료

사용자가 Claude Design에 디자인 시스템 문서에 보통 무엇이 드는지 물어 받은 답을 붙였다. 항목은 여섯이다. 색 토큰의 두
층(원색 → 쓰임새), 컴포넌트의 상태(기본, 올림, 누름, 포커스, 쓸 수 없음, 오류, 불러오는 중), 해부도와 치수, 쓰는 법(언제
쓰는지, 해도 되는 것과 안 되는 것), 정리 순서(기초 → 컴포넌트 → 패턴 → 화면), 구현 연결(디자인 토큰 목록과 props 표)이다.

> 사용자: "클로드 디자인에서 채팅한건데 탐색에서 적용할 수 있게 킥오프에 추가해줘"

목록은 런북의 부록 B(`kickoff/prompting.md`)에 "디자인 탐색 프롬프트가 담을 것" 절로 두고 9단계의 1에서 가리키게 했다.
이 저장소의 탐색 프롬프트에는 그 항목을 받는 3단계 글을 더했다.

여섯 가운데 두 층만은 ADR 0026의 결정(색 토큰은 쓰임새 이름뿐, 팔레트를 비운다)과 부딪혀 사용자에게 물었다.

> 사용자(질문에 답): "두 층, 원색은 컴포넌트에 안 보임 (Recommended)"

테마마다 원색 토큰을 두고 쓰임새 토큰이 모드마다 그 하나를 가리키며, 컴포넌트는 쓰임새 토큰만 쓴다. 원색 토큰은
Tailwind 유틸리티를 만들지 않는 CSS 변수로만 둔다. 다른 선택지는 둘이었다. 하나는 쓰임새 토큰만 두는 지금의 결정이고,
다른 하나는 탐색에서만 두 층을 보고 코드에 둘지는 명세가 그 결과를 보고 정하는 것이었다. ADR 0026의 셋째 2026-10-06
이력이다. 테마 다섯 × 모드 둘이면 쓰임새 토큰의 값을 열 벌
고르므로, 원색 토큰이 없으면 한 테마 안의 밝기 단계가 벌마다 따로 논다는 것이 추천의 근거였다.

## 내려받는 형식과 표를 채우는 길

> 사용자: "exploration-prompt.md 에서 "하는 법" 4번에서 내보내는 형식을 뭘로해?
> Cluade Code?"

HTML로 내려받기(있으면 파일을 통째로 받는 ZIP)를 추천했다. 다음에 읽는 것은 명세 세션의 에이전트이고, HTML과 CSS는 hex
값, 글꼴 이름, px 값을 글자로 남겨 읽고 커밋할 수 있다. Claude Code로 넘기는 길은 구현을 맡기는 것이라 탐색 → 명세 →
티켓 → 코드의 순서를 건너뛰고, 링크가 저장소 밖에 남는다. 메뉴는 직접 보지 못했으므로 이것은 지식에 기댄 추천이다.
내보낸 결과를 보면 하는 법의 "어떤 형식이 되는지는 확인하지 않았다"를 고친다.

> 사용자: ""하는 법" 5번에서는 직접 적거나 다음 명세 세션에 맡길 수 있도록 해줘."

하는 법의 표 채우기를 두 길로 나눴다(3단계 글을 넣는 단계가 끼어 6번이 됐다). 직접 적는 길은 커밋할 세션이 이미 있을
때이고, 파일과 줄을 그 세션의 작업 폴더에 넣는다. 맡기는 길은 내보낸 파일을 저장소 밖에 둔 채 명세 세션에 경로와 붙여
넣은 날을 알리고, 그 세션이 파일을 옮겨 줄을 채운다. 맡긴 세션은 붙여 넣은 순간의 기준 커밋을 모르므로 날짜로 구하고
"(어림)"을 붙인다. 주 체크아웃에 넣지 않게 한 것은, 다른 세션이 같은 경로로 커밋해 병합하면 주 체크아웃의 추적되지 않은
파일이 pull을 막는다고 보았기 때문이다(git의 동작에 기댄 어림이다. 워크트리 가드가 임시 저장소로 재는 복합 명령을
거부했다). 이 사정은 모든 기능의 화면에 해당해 `docs/agents/issue-tracker.md` 화면 디자인 절에도 적었다. 받는 쪽은
`design/README.md`의 포인터, `plan.md`의 design-system 행, 이 일지의 "다음"이다.

## 한 번에 넣기와 사람의 일 줄이기

PR #152를 연 뒤 사용자가 둘을 더 말했다.

> 사용자: "exploration-prompt.md 에서 고른 뒤를 좀 더 쉽고 자세하게 알려줘.
> 사용자가 직접하게 하지말고 자동으로 될 수 있으면 자동으로 할 수 있게.
>
> 그리고 2번이랑 3번이랑 합쳐서 한번에 해도 되는거 아니야?
> 맞으면 킥오프에서는 그렇게 할 수 있도록 수정해줘."

합쳐도 된다고 답했다. 2단계(그리기)와 3단계(문서로 정리하기) 사이에는 사람이 고를 것이 없다. 3단계는 사용자가 붙인 목록을
받으려고 2단계 뒤에 덧붙인 글이었을 뿐이다(사용자에게는 나눈 까닭이 글의 길이뿐이었다고 답했는데, 이 세션에서 길이를
따져 나눈 적은 없다. 일지 09의 길이 판단은 1단계와 2단계를 나눈 것이다). 1단계는 사람이 방향을 고르므로 그대로 따로 둔다. 2단계 글 하나에 둘을 넣고, 사이에 `---` 줄을 두고 지킬 것을 앞쪽에
두어 도구가 자르면 둘로 나눠 넣게 했다. 런북 부록 B에는 프롬프트를 사람이 고르는 자리에서만 나눈다고 적었다.

사람의 일은 도구 안의 조작(붙여 넣기, 고르기, 내보내기)과 결정으로 줄였다. 2단계 글의 `<기본 테마 이름>` 자리표시를
없애고 Claude Design이 하나를 추천하게 했다. 확정은 명세 세션이 묻는다. "고른 뒤"는 사람이 하는 일 둘(내보내기, 명세
세션의 질문에 답하기)과 명세 세션이 차례로 하는 일 다섯(파일 옮기기, 표 채우기, 기본 테마 적기, 글꼴 확인, 명세)으로
갈랐다. 파일을 직접 넣는 길은 커밋할 세션이 이미 있을 때의 선택으로만 남겼다. Claude Design의 내용을 세션이 직접
읽어 오는 길은 찾지 못했다. DesignSync 도구는 디자인 시스템 프로젝트를 `/design-sync`로 맞출 때만 쓰고, 공유 링크는
내장 브라우저에서 로그인 화면에 멈췄으며 Chrome 확장은 연결되지 않았다. 내보내기의 Claude Code 선택지로 파일을 받아
오는 길은 확인하지 않은 채 대안으로 적었다. 런북 9단계의 1과 부록 B에 사람과 세션의 일을 가르는 법을 더했다.

## 탐색 결과 보기와 버튼 글자

사용자가 Claude Design 프로젝트의 공유 링크를 주며 확인해 보라고 했다. 내장 브라우저가 로그인 화면에 멈추자 사용자가 그
창에서 직접 로그인했다(로그인은 대신하지 않았고, 쿠키 배너는 모두 거부를 눌렀다). 디자인 본문은 다른 출처의 iframe이라
글로 읽히지 않았고, 화면으로 찍어도 글자가 작았다. 왼쪽 대화와 위쪽 선택지에서 읽은 것은 넷이다.

- 테마 다섯은 먹, 청록, 공문, 황토, 자두이고 모드는 라이트와 다크다. 파일은 "Agent OS 디자인 시스템 v2"(5쪽)다.
- 이 브랜치의 앞 판 2단계 글이 `<기본 테마 이름>`을 바꾸지 않은 채 들어갔고, Claude Design이 기본 테마를 먹으로 잡았다.
  자리표시를 없애고 추천을 받게 한 것이 맞다는 근거로 보았다.
- 대화에 Save as standalone HTML 동작이 보여, 하는 법 4의 형식을 그것으로 적었다.
- 승인 묻기의 버튼 글자를 사용자가 Claude Design에 "승인"으로 바꾸라고 했다.

버튼 글자는 용어집과 부딪힌다. 용어집에서 승인은 허가와 거부를 모두 담는 행위이고, 결정은 허가이거나 사유를 붙인
거부다. 지금 관리 화면의 버튼과 테스트도 "허가"다. "허가"로 되돌리기를 추천했으나 사용자가 정했다.

> 사용자: "승인 버튼의 글자는 승인으로해줘"

용어집은 용어만 담는 자리라 고치지 않았다. 버튼 글자는 `plan.md`의 design-system 행에 결정으로, admin-style 행에 지금
관리 화면의 "허가" 버튼과 테스트를 바꿀 일로 적었다. 탐색 프롬프트의 승인 묻기도 "승인"과 "거부"로 고쳤다.

> 사용자: "그리고 저장소 밖이 어딜 의미하는거야? 바탕화면에 둬?"

저장소 폴더 아래만 아니면 어디든 되고, 브라우저가 내려받은 폴더에 그대로 두면 된다고 답했다. 하는 법 4에 그대로 적었다.

> 사용자: ""/to-spec을 칩니다. 이 스킬은 사람만 부를 수 있습니다."
> 새 세션 스킬로 하면 안되나?"

된다. `open-session`은 지시문의 첫 줄이 이 저장소의 스킬 명령이면 그 스킬 파일을 읽어 따르라는 한 줄로 옮겨 보낸다
(`.claude/skills/open-session/SKILL.md`를 읽었다. 이 세션도 그렇게 `/grill-with-docs`로 시작했다). 그래서 사람의 일에서
`/to-spec` 치기를 빼, "고른 뒤"의 사람의 일은 경로 알리기와 결정에 답하기 둘이 됐다. 명세 세션은 to-spec을 따르며 명세를
쓰기 전에 1~4를 한다. 부록 B의 사람에게 남기는 일도 셋으로 고쳤다. 앞 셀프 리뷰가 "`/to-spec`은 사람만 부른다"를
입구의 빈틈으로 짚었던 것은 이 길을 몰랐던 데서 왔다.

> 사용자: "그리고 직접 다운로드 받아서 항상 현재 프로젝트 바로 상위 디렉토리에 다운받도록 할 수 없나?"

둘로 나눠 답했다. 세션이 내장 브라우저로 내려받는 것은 할 수 있으나, 내려받기마다 사람의 허락이 들고 브라우저가 어디에
저장하는지는 세션이 정하지 못한다(확인하지 않았다). 자리를 저장소의 바로 위 폴더로 정하는 것은 되고, 그러면 세션이 그
자리에서 파일 이름으로 찾으므로 사람이 경로를 알릴 일도 없다. 두 갈래를 물었다.

> 사용자(질문에 답): "상위 폴더 바로 (Recommended)", "2번으로 하고 사용자가 원치 않으면 1번으로"

정해진 자리는 저장소의 바로 위 폴더(이 PC에서는 `C:\project`)이고, 내려받기는 명세 세션이 내장 브라우저로 한다. 사람이
원치 않으면 사람이 그 자리에 저장한다. 그래서 "고른 뒤"의 사람의 일은 로그인과 내려받기 허락, 결정에 답하기 둘이 됐고,
세션의 일은 내려받기와 파일 찾기가 앞에 붙어 여섯이 됐다. 하는 법의 사람 조작은 1~3이다. 파일을 세션의 작업 폴더에
직접 넣는 길과 Claude Code 선택지의 글을 넘기는 대안은 정해진 자리가 대신해 뺐다. 화면 디자인 절, 런북 9단계의 1,
부록 B도 같은 모양으로 고쳤다.

## 셀프 리뷰

`/code-review`(base `88badb1`, 파일 9개, 커밋 0, 미추적 1)를 두 축 모두 sonnet으로 돌렸다. 하드 위반은 없었다.

  두 층을 보고 코드에 둘지는 명세가 정하는 안이었다(세션 기록과 대조). 맡기는 길의 `--until`을 `--` 뒤에 붙이면 경로로
  읽혀 날짜가 빠졌다(리뷰가 찾았고 다시 손으로 돌려 확인했다). 전체 명령을 적었다. 직접 적는 길에 작업 폴더의 자리와
  세션이 없을 때를 적고, "붙여 넣은 직후"를 병합 전 브랜치와 맞게 고쳤다. 3단계 글이 붙여 넣는 쪽에서 풀 수 없는
  "2단계"를 가리켜 내용으로 바꿨다. 패턴의 "다시 하기"는 도메인에 없는 개념이라 뺐고, 패턴 목록을 이 프롬프트의 제안으로
  분류했다. 하는 법 4에 3단계도 확인하지 않았다고 적었다. 받는 쪽을 `plan.md` 행과 "다음"에도 두었다.
- **고쳤다, 표준 축.** `kickoff/prompting.md`가 1(두 층)을 첫 프롬프트에 넣는 것으로 읽혀, 1~6을 고른 뒤의 글에 넣는다고
  고쳤다. 상태 표가 열두 쓰임새 토큰 밖의 토큰을 막거나 어기게 만들어, 새 토큰을 따로 적게 했다. `plan.md`의 "첫 티켓이
  잴 것"에 셋째 이력을 더했고, 두 층이 `data-theme`·`data-mode`를 따르는지도 첫 티켓이 잴 것으로 이력에 적었다(기존
  측정은 한 층). git 동작의 근거를 "어림"으로 적었다. 두 길의 설명이 네 곳에 흩어져 `design/README.md`는 포인터로,
  `KICKOFF.md`의 항목 괄호는 지웠다. 용어집 정의에서 규칙 문장을 뺐다. "내려받은"과 "내보낸"을 "내보낸 파일"로 맞췄다.
- **남겼다.** ADR 0026 Considered Options의 "팔레트를 남긴다"에는 포인터를 달지 않았다. 셋째 이력이 그 팔레트를
  Tailwind의 기본 팔레트로 밝혔고, 그 판정은 지금도 참이다. "원색"이 회색과 밝기 단계까지 담는 이름으로 좁다는 Nit은

  구현 연결이 CSS 변수와 JSON 가운데 JSON만 받는 것은 요구가 둘 중 하나라 두었다. 맡기는 길의 기준 커밋이 날짜에서
  오는 것은 사람이 해시를 모를 때의 길이라 두었고 "(어림)"으로 밝혔다.

- **고쳤다.** (명세, Major) 명세 세션의 입구가 비어 있었다. 세션이 열리는 때, 사람이 무엇을 치는지(`/to-spec`은 사람만

  어림하고 미심쩍을 때만 묻는다. "조작과 결정뿐", "할 일은 둘" 같은 닫힌 말에 반례(경로 알리기, `/to-spec` 치기, 글꼴

- **남겼다.** claude-review의 Minor 둘. 용어집의 쓰임새 토큰 정의는 ADR 0026 셋째 이력이 정한 구조이고, 첫 티켓이 재는
