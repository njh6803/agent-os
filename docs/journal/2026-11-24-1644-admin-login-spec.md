## 사용자에게 물은 화면 (16:40쯤)

시험 경계의 확인(to-spec 2단계)과 화면 폴더가 명세 전에 다시 묻기로 한 둘(새 아이콘, 계정 상태의 표시), 설계에 없던 하나(갈라진 대화를 목록에 보이는 모양)를 한 화면에 물었다. 첫 호출은 선택 화면의 사실을 대 보라는 훅이 막았다. 아이콘 수(열일곱), 배지가 실행 상태 넷에만 쓰이는 것, 실패한 실행은 이어 가지 못하는 것(`gather_continued`), 실제 `serve`를 HTTP로 부르는 `-m llm` 시험이 이미 있는 것(`tests/test_main.py`)을 코드에 대 보았다. 시험 경계 선택지의 복제 시간에 "작업자 여덟이 함께 돌 때 중앙값, postgres-foundation이 잰 값"을 덧붙이고, 배지 선택지의 "확정한 계정 화면 둘"을 "확정한 계정 목록 화면(데스크톱과 모바일)"으로 고쳤다. 질문 문장과 라벨은 그대로다.

1. 시험 경계
   > 질문: admin-login 명세의 시험 경계를 이렇게 잡으려 합니다. 서버 쪽은 지금처럼 앱을 메모리에서 띄워 HTTP로 부르되, 계정과 로그인 상태는 시험마다 복제한 진짜 PostgreSQL에 두고, 시험 도우미가 로그인 경로를 실제로 불러 쿠키를 받습니다. 명령줄(첫 계정 만들기, 서명 키 바꾸기)·sdk 이벤트·화면의 페이지 시험·e2e(토큰 대신 로그인)·사진 비교는 지금 있는 경계를 그대로 씁니다. 실제 모델로 '대화 화면에서 예시 에이전트에 요청해 답을 받는다'를 보는 시험은 새 표지를 만들지 않고 기존 `-m llm` 시험이 서버를 HTTP로 불러 확인합니다. 이 경계로 갈까요?
   >
   > 사용자: 이대로 (Recommended) — "진짜 데이터베이스라 동시 갱신, 잠금, 링크의 한 번 쓰기를 실제와 같게 봅니다. 실제 `serve`를 HTTP로 부르는 `-m llm` 시험이 이미 있어 그 옆에 더합니다. 대가는 시험 하나마다 데이터베이스 준비와 지우기(작업자 여덟이 함께 돌 때 중앙값 약 0.23~0.27초, postgres-foundation이 잰 값)와 비밀번호 비교 시간이 붙어 전체 시험이 길어지는 것입니다."

   다른 선택지는 "HTTP 시험은 가짜 저장소"(메모리 가짜로 빠르게, 동시 갱신은 따로 진짜 데이터베이스 시험)였다.

2. 새 아이콘
   > 질문: 관리 화면 목업이 디자인 시스템에 없는 아이콘 일곱을 그렸습니다: 대화(message-square), 계정(users), 계정 메뉴 열기(chevrons-up-down), 로그아웃(log-out), 링크 복사(copy), 잠김(lock), 상태 점(circle). 이 아이콘을 어디에 둘까요?
   >
   > 사용자: 디자인 시스템에 더함 (Recommended) — "`web/packages/ui`의 아이콘 이름 목록(지금 열일곱)에 더하고 디자인 시스템 아티팩트에도 올립니다. 위젯 같은 다른 앱도 같은 이름으로 씁니다. 대가는 디자인 시스템의 사진 비교와 올리기 단계가 함께 느는 것입니다."

   다른 선택지는 "관리 화면 앱에서만 씀"이었다.

3. 계정 상태
   > 질문: 계정 목록에서 계정의 상태(쓰는 중, 쓰지 않음, 비밀번호를 정하기 전)와 잠김을 어떻게 보일까요? 설계 때 처음에는 '상태 배지, 잠김 배지'라고 설명하셨고, 그린 화면은 배지 대신 글자와 아이콘으로 그렸으며 그 화면을 확정하셨습니다.
   >
   > 사용자: 배지로 하고 활성, 비활성, 비밀번호 미설정 상태로 하는건 어때?

   선택지는 "그린 대로 글자와 아이콘 (Recommended)"과 "배지로 보임"이었고, 사용자는 둘 가운데 고르지 않고 글로 답했다. 배지로 보이고, 세 상태의 화면 이름을 활성(쓰는 중), 비활성(쓰지 않음), 비밀번호 미설정(비밀번호를 정하기 전)으로 바꾸자는 제안이다. 명세는 이 제안을 따른다(아래 "제안을 받아들이며 정한 것").

4. 갈라진 대화
   > 질문: 실패한 실행 뒤에 '다시 보내기'를 하면, 실패한 실행에서는 이어 갈 수 없어서 그 앞의 끝난 실행에서 이어 갑니다. 그래서 대화가 두 갈래(실패한 시도, 다시 보낸 시도)로 갈라집니다. 실행 목록 화면이 없어지고 대화 목록이 그 자리에 서는데, 갈라진 대화를 목록에 어떻게 보일까요?
   >
   > 사용자: 갈라진 끝마다 한 줄 (Recommended) — "실패한 시도도 목록에 한 줄로 남아 '실패'로 거를 수 있고, 모든 실행이 목록에서 닿습니다. 대가는 첫 요청이 같은 줄이 둘 보이는 것입니다."

   다른 선택지는 "첫 요청마다 한 줄"이었다.

## 제안을 받아들이며 정한 것

3의 제안을 따르며 정한 것은 넷이다.

- 배지의 값은 넷(활성, 비활성, 비밀번호 미설정, 잠김)이다. 잠김은 상태가 아니라 따로 붙는 사실이지만 같은 배지 부품이 보인다. 실행의 상태 배지는 그 쓰는 법 문서가 실행 상태 넷에만 쓴다고 적어, 디자인 시스템에 새 배지 부품 하나를 더한다(명세 "디자인 시스템에 더하는 것").
- "비활성"은 꺼진 플러그인을 부르는 말과 겹쳐 읽힐 수 있어, 용어집(`CONTEXT.md`)의 운영자 계정 항목에 화면의 "비활성"은 쓰지 못하게 막은 계정이라는 풀이를 한 줄 더했다.
- ADR 0062 결정 "계정"의 상태 이름(비밀번호를 정하기 전, 쓰는 중, 쓰지 않음)은 글자를 그대로 두고, 이력에 화면의 이름으로 읽는 법을 적었다. 결정은 바뀌지 않으므로 포인터를 달지 않았다.
- 명세 서두의 "사용자가 고른 것" 3은 추천안이 아니라 사용자가 글로 낸 안이라고 적었다.

## 코드를 읽으며 바로잡은 것

- FastAPI가 이벤트 스트림 응답에 `X-Accel-Buffering: no`를 싣는다(`fastapi/routing.py` 645행, 0.141.1). 처음에는 싣지 않는다고 적었다. Grep 도구가 `.venv`를 `.gitignore`대로 넘어 찾지 못한 것이었고, Bash의 `grep -rli`로 찾았다(CLAUDE.md 환경 함정의 Glob·Grep 항목과 같은 일이다). 명세의 관리 화면용 포트 절은 이 머리를 근거로 쓴다.
- 관리 화면 앱의 중계(Next 16.3.6의 `next/dist/server/lib/router-utils/proxy-request.js`, httpxy)를 읽었다. 제한 시간은 `proxyTimeout`이 없으면 30초이고 소켓이 쉬는 시간에 걸린다. 위 머리를 포함해 윗단의 응답 머리를 모두 옮긴다. 연결 묶음은 `keepAlive: true`, `maxSockets: 256`, `maxFreeSockets: 64`이고 쉬는 연결을 닫는 시간은 없다. 그래서 스트림의 연결 유지 주석 15초가 중계의 30초와 nginx의 60초보다 짧다(명세 "관리 화면용 포트").

## ADR 이력과 받는 기능 계획

- ADR 0011, 0062, 0063에 2026-11-24 이력을 하나씩 쌓고, 바뀐 본문 문장 뒤에 포인터를 달았다. `uv run python tools/check_adr_pointers.py`는 아무것도 내지 않고 끝났다.
- 명세가 새로 넘기는 것을 받는 기능의 계획(admin-roles, audit-export, trace-postgres, deploy-package, portal-admin)에 단락으로 적었다. 다섯의 `**Blocked by:**`를 봤다. admin-roles와 portal-admin은 admin-login을 바로 들고, deploy-package는 portal-admin을 거쳐, audit-export와 trace-postgres는 pilot-release를 거쳐 admin-login 뒤에 돈다(셀프 리뷰가 "먼저 돌 수 있다"는 첫 판단을 바로잡았다. 사슬은 스크래치 스크립트로 따라갔다).
- 기능 계획 admin-login의 수락 문장 "실행 목록을 보고"를 "대화 목록을 보고"로 고쳤다. `.claude/rules/web-design.md`의 예 "실행 목록의 배지"는 지금은 참이라, 화면을 바꾸는 티켓이 고친다고 명세에 적었다.

## 셀프 리뷰 직전의 인계 (18:20쯤)

세션 컨텍스트가 20만 토큰을 넘은 채 셀프 리뷰 직전에 와서 인계 계기가 들어왔다. 넘기지 않는 다섯 경우에 들지 않아 새 세션에 넘긴다. 이 세션의 지금 제목은 `docs/admin-login`이고, 넘기며 `docs/admin-login (인계함)`으로 바꾼다. 아무것도 커밋하지 않았다.

- **명세의 남은 자리.** `.scratch/admin-login/spec.md` "계정 이름과 비밀번호" 절에 〔프로브 대기〕 셋이 남았다. "스레드와 동시에 도는 해시"(한꺼번에 도는 해시의 상한과 메모리), "견줌 시간"의 끝(HTTP 길의 견줌 시간), "스레드로 넘기는 길"(uvicorn의 실제 요청 길). 같은 절의 "비밀번호 규칙"(유니코드 넷)과 "견줌 시간"의 함수 길은 `hash_load` README의 항목 3·4로 채웠다.

### hash_load 덧붙인 갈래 (19:27 끝)

서브에이전트가 `hash_load`에 갈래 셋을 더해 돌렸다(토큰 `075196`, 약 10분, 측정 50, 측정 아님 2, 종료 1, 남은 컨테이너 0). 측정 아님 둘은 전용 스레드 서버 K=100의 #2·#3이고 앞선 실행과 같은 `httpx.ReadError`다. 결과는 `hash_load/README.md`의 "덧붙인 갈래(실행 `075196`)"가 원천이다.

- 해시만 도는 스레드 넷(`ThreadPoolExecutor(max_workers=4)`를 `run_in_executor`로 기다린다)은 다른 스레드 일과 함께 K=40을 세 번 잇달아 넘긴 뒤에도 견줌 스레드가 4가지였고 남는 상주가 76.7~76.9 MiB였다(회차 16 모두 측정). 같은 실행의 기본 묶음 + 한도 4는 742~799 MiB였다.
- 아레나 하나는 한 스레드의 견줌에서 +0.8ms로 가르지 못했고(5ms 대조는 섰다), 스레드 넷이 함께 견주는 판에서 +17.0ms였다(mmap 문턱 +19.4ms). 넷 판의 5ms 대조가 +10.1ms로 부풀어 그 판의 크기는 확실하지 않다.
- uvicorn 서버 CPU 4개 K=100에서 전용 넷은 최고 상주 134.9 MiB, 견줌 스레드 4, `/health` 90분위 20.3ms였다(창 하나).
- 서브에이전트가 코드를 읽어 적은 것: `run_in_executor`는 기다리던 쪽이 취소되면 `Future.cancel()`만 부르고 이미 도는 견줌은 끝까지 돈다. AnyIO의 기본도 스레드 일이 끝날 때까지 기다린다. `contextvars`는 넘기지 않는다.

이 결과로 남는 메모리를 다루는 안 넷(전용 스레드 넷, 아레나 하나, mmap 문턱, 그대로 두고 적기)을 모두 잰 수로 견줄 수 있게 됐다. 사용자에게 고르게 한다.

### 해시 메모리를 물었다 (19:40쯤)

> 질문: 로그인이 몰렸다 끝난 뒤 서버에 남는 비밀번호 해시 메모리(지금 설계로는 685~818 MiB, 쟀다)를 어떻게 다룰까요? 어느 안이든 동시에 도는 해시는 넷으로 묶습니다.

> 사용자: 해시 전용 스레드 넷 (Recommended)

고른 선택지의 설명(글자 그대로): "서버가 뜰 때 해시만 도는 스레드 넷을 만들고 해시를 늘 거기서 돌립니다. 남는 메모리가 76~77 MiB로 묶였습니다(쟀다, 다른 스레드 일과 섞여도). 걸린 시간은 회차가 둘뿐이라 가르지 못했습니다(CPU 2개에서 길고 4개에서 짧았다). 환경 변수 없이 코드로 묶으므로 어디서 띄워도 걸립니다(메모리는 리눅스 컨테이너에서만 쟀다). 값: 서버를 켜고 끌 때 그 스레드를 만들고 닫는 코드가 듭니다. ADR 0062의 결정 문장(이벤트 루프 밖의 스레드로 넘긴다)은 그대로 참입니다."

다른 선택지는 할당기 영역 하나(`arena_max=1`), 큰 메모리는 바로 돌려주기(`mmap_threshold`), 그대로 두고 한계로 적기였다. 묻기 전에 대화에 적은 것: 한도를 넘은 로그인은 거절하지 않고 차례를 기다린다(429를 내려면 계약에 에러 코드가 는다). 그 설명에서 "가장 늦은 요청도 1.6초 안"이라고 한 것은 CPU 4개의 값이고 CPU 2개에서는 2.3초였다고 다음 말에서 바로잡았다. 훅이 선택 화면을 두 번 막아(질문 문장을 고쳐 다시 막혔다) 설명의 수를 `hash_load` README와 서브에이전트 보고에 대 보고 넷을 고쳤다(700~800 → 685~818, 전용 스레드의 시간은 가르지 못함, 영역 하나의 19.8 MiB, 1.6초의 CPU 수).

ADR 0062는 이력을 쌓지 않는다. 결정 문장 "해시와 견줌은 이벤트 루프 밖의 스레드로 넘긴다"가 그대로 참이고, `anyio.to_thread.run_sync`는 그 결정 시점의 프로브를 적은 근거 문장이라 `.claude/rules/adr.md`의 "달지 않는 것"에 든다. 앞 세션의 인계는 이 길이 결정과 어긋난다고 봤다.

### port_shape_async 트랜잭션 갈래 (19:35쯤 끝)

서브에이전트가 트랜잭션을 여는 메서드와 작업 객체의 모양을 갈래로 더해 세 번 돌렸다(83회차 모두 측정, 종료 0. 새 갈래 35, 앞선 48은 결과가 같았다). `@asynccontextmanager`와 클래스 두 어댑터가 strict 오류 0, 타입 우회 0, import-linter 통과였고, 어긋난 어댑터 다섯이 잡혔다. 반환은 `AsyncGenerator`로 적고(`AsyncIterator`는 `reportDeprecated`), 포트의 둘째 타입 인자는 기본값으로 둬야 했다.
