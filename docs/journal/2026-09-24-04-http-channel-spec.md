## 선행 조건

드리프트 칩은 **병합되지 않았다.** `git fetch` 뒤 원격에 그 브랜치가 없고 main에 커밋도 없으며,
`docs/constitution/README.md`는 2.3.3(Last Amended 2026-09-21) 그대로다. 명세의 계약 티켓에 지시문의 문장을
그대로 적고, 드리프트 정리는 칩의 일이지 계약 티켓이 대신하지 않는다는 것을 덧붙였다(리뷰가 잡은 뒤).

## 명세를 쓰기 전에 잰 것

셋은 스크래치 프로브로 쟀다(`scratchpad/probe_mw_sse.py`, `probe_openapi_sse.py`, `probe_named_event.py`, 저장소 밖).
03이 "명세가 확인한다"고 넘긴 것들이다.

- **`BaseHTTPMiddleware` 둘 뒤에서도 SSE는 모이지 않는다.** 첫 프레임이 제너레이터가 다음으로 가기 전에 `send`에
  도착했고 두 미들웨어의 헤더가 스트림 응답에 붙었다. 끊기면 라우트 제너레이터는 `CancelledError`를 받지만
  요청 밖에서 만든 태스크는 끝까지 갔다. "실행은 앱의 수명이 소유한다"가 여기서 나왔다.
- **FastAPI 0.141.1은 의존성을 다 푼 뒤에 SSE 제너레이터를 부르고 응답을 시작한다**(라우팅 소스). 첫 이벤트를
  기다릴 자리가 있다는 뜻이라 "첫 이벤트 전 실패는 상태 코드"가 구현 가능하다. 방법은 티켓에 남겼다.
- **스트림 항목은 그대로 두면 `Streamitem Start Run`이라는 익명 `oneOf`로 인라인된다.** 채널 쪽에 `sdk`의
  `Event`를 가리키는 이름 있는 별칭 하나로 `#/components/schemas/Event`가 생기고, `TraceEvent`는 평평한 열 그대로
  같은 멤버를 가리켰다. `sdk`를 건드리지 않는다. ADR 0010 이력이 명세에 넘긴 이름을 이것으로 정했다.
- httpx `ASGITransport`가 lifespan을 보내지 않는다는 것도 소스로 봤다. 03은 "끊김을 보내지 않는다"까지 적었다.
  채널의 실행을 lifespan이 소유하면 테스트가 수명을 직접 열어야 한다.
- 계약 파일은 `openapi: 3.1.0`인데 SSE 응답은 3.2의 `itemSchema`로 나온다. 위젯의 생성기 몫으로 적었다.

## 이음매 확인 — 둘 다 추천대로

to-spec 2단계("이음매가 기대와 맞는지 확인한다")를 `AskUserQuestion` 두 개로 올렸다.

> 사용자: (스트림 이음매) "같은 앱에 ASGI 직접 호출 (Recommended)"
> 사용자: (LLM 테스트) "serve 프로세스로 하나 (Recommended)"

새 이음매는 없다. 주 이음매(`create_app()` + `ASGITransport`)는 그대로이고, 같은 앱에 구동자가 하나 는다 —
`app(scope, receive, send)`를 직접 부르며 스트림의 수명 셋(조각별 전달, 끊겨도 끝까지, 서버가 멈추면 떠난 실행은
결말 없음)에만 쓴다. ADR 0010 이력이 "클라이언트를 손으로 짜는 안은 거부했다"고 적은 것과의 긴장은 명세에 적었다.
HTTP를 짜지 않고 ASGI를 그대로 말하므로 그 이력이 걱정한 "테스트되지 않는 두 번째 HTTP 클라이언트"가 아니고,
그래서 범위를 그 셋으로 묶는다. `-m llm`은 실제 `serve` 서브프로세스로 `gatedcalc`를 멈추고 HTTP로 승인해
끝까지 가는 것 하나다.

## 결정의 값이 가장 컸던 자리

**동시 재개의 불변식을 "트레이스 쓰기가 동기"라는 사실에 묶어 적었다.** 03은 "`await`가 없다"까지 적었다. 명세는
그것이 깨지는 구체적인 변경 — 트레이스 쓰기를 비동기로 바꾸거나 스레드로 보내는 것 — 을 이름으로 적어, 성능
개선처럼 보이는 PR이 승인된 도구를 두 번 실행하게 만드는 길을 테스트 이름과 함께 막았다.

**본문의 `agent`도 원격 입력이다.** 관리 명세가 `{name}`과 `{run_id}`에 건 경로 순회 방어가 채널에서는 본문 필드로
온다. ADR에 없는 문장이지만 새 결정이 아니라 관리 규칙("파일 경로로 조립되는 것은 패턴을 지난다")을 적용한 것이다.

## 셀프 리뷰

`/code-review main`을 두 축 병렬로 돌렸다. 범위는 미추적 파일 하나. 표준 축은 소스가 없어 sonnet.

- **표준 축: 사실 주장 전부 통과.** 인용 8곳, 설치본의 동작 다섯, 현재 코드의 서술, ADR·일지 참조를 grep과
  소스로 대조했다. 대기열 20의 가족(사실 주장·인용)이 이번에는 사실 쪽에서 0건이었다. Minor 둘 — 파일 경로가
  많다(선례 명세 둘과 같은 관행이라 남겼다), 서두의 "셋뿐"과 본문의 "(이 명세가 정했다)" 다섯이 어긋난다.
- **명세 축: Major 1, Minor 11, Nit 4.** Major는 `start_run`·`StartRun`·`submit_approval`·`Decision(Approve|Deny)`
  를 원천 없이 정한 것이었다. 계약 이름이고 core의 `Approve`·`Deny`·`Decision`과 겹친다. **이름을 빼고 조건 셋만
  남겨 라우트 티켓으로 넘겼다** — 관리 API의 `operation_id`도 티켓에서 지어졌다. 그러자 "(이 명세가 정했다)"가
  셋으로 맞았다(표준 축 Minor도 함께 닫힘).
- **인용 둘이 원문과 달랐다(설계 세션 3회차, 명세 세션 1회차).** ADR 0011 이력 제목을 앞 절만 따옴표에 넣었고,
  ADR 0010 이력의 "클라이언트를 손으로 짜는 안"을 "손으로 짠 클라이언트"로 바꿔 따옴표에 넣었다. 둘 다 원문으로.
- **ADR 문장을 넓혀 귀속했다.** ADR 0014의 "클라이언트가 떠난 실행은 기다리지 않고 취소한다"를 "수명이 남은 실행을
  취소한다"로 옮기고 ADR에 붙였다. 연결이 남은 실행은 ADR이 정하지 않았고 uvicorn의 종료 순서에 달린 것이라
  Further Notes로 뺐다. 주체를 `create_app`이 받는 것도 ADR 0010 이력에 잘못 붙였다 — 구현 세부로 다시 적었다.
- 그 밖에 고친 것: 추가 필드 422의 근거(CLI의 "조용히 버리는 대신 거부한다"), 두 구동자가 "첫 이벤트 전 실패"를
  나눠 재는 이유, 미들웨어 프로브 사실, 테스트 목록의 진입점 import 실패, 관리 쪽 부재는 `None`→404 그대로,
  `--traces` 한정, rules `paths`를 ADR 0016 문장대로, 원칙 IV 첫 문장의 금지 열거, ADR 0009 이력의 이름.

## 갈린 곳

- 이음매 둘 다 추천대로 갔다.
- `itemSchema`가 서버가 보내지 않는 `event`·`id`·`retry`를 광고하는 것은 정하지 않고 명세 검토로 넘겼다. 지우려면
  계약을 만드는 쪽에 손을 대야 하고, 그것이 결정이다.
- 재개하려는 실행의 에이전트가 그새 사라지면 404가 된다. ADR 0014의 "부재에 없는 에이전트"를 문자 그대로 적용한
  결과라 새 결정이 아니라고 봤고, 괜찮은 모양인지는 명세 검토에 올렸다.
- `plan.md`는 고치지 않았다. 기능 상태가 바뀌지 않았다(명세 선례 #39도 고치지 않았다).

## 번복하거나 고친 것

- 계약 이름 넷(`start_run`, `StartRun`, `submit_approval`, `Decision`) → 명세에서 빼고 조건만.
- "루프 상한(10턴)이 이벤트 수를 묶는다" → 에이전트가 내는 이벤트는 상한 밖이라 거짓. "떠나면 버린다, 이미
  트레이스에 있다"로(리뷰 전).
- 관리 토큰 진단을 옛 표현 목록에 넣은 것 → 여전히 참이라 뺐다(리뷰 전).
- 인용 둘, ADR 0014 문장의 범위, 주체의 귀속 → 위 셀프 리뷰.
