# dev-base-tools: 나머지 도구를 기준 브랜치 규칙으로 바꾼다 (인계 중간 기록)

세션 제목: `chore/dev-base-tools`. 이 일지는 컨텍스트가 인계 문턱을 넘어 셀프 리뷰 직전에 새 세션으로 넘기며 만들었다. 새 세션이 같은 파일을 이어 쓰고 커밋한다.

## 사용자 프롬프트

> 사용자: `/implement .scratch/harness/issues/dev-base-tools.md` (다음 작업: tools/의 나머지 도구를 기준 브랜치 규칙(hotfix/*는 main, 그 밖은 origin/dev가 있으면 dev)으로 바꾼다. 이번 요청 범위: PR과 병합까지)

## 결정

- 규칙의 한 곳은 `tools/base_rule.py`다. 훅(`hook_push_behind_main.base_branch`)과 CI가 표준 라이브러리만으로 돌리는 `check_ticket.base_ref`는 import하지 않고 따로 구현하되, `tests/tools/test_base_rule.py`가 세 구현이 같은 입력에 같은 기준을 내는지와 `"hotfix/"` 문자열이 세 파일 밖에 없는지를 고정한다.
- `tidy_checkouts`는 기준을 규칙으로 바꾸지 않고 `origin/main`과 `origin/dev` 둘 다 본다. 둘 다 보호된 오래 사는 브랜치라 닿은 커밋은 잃는 것이 이름뿐이고, 없는 ref는 무시된다. `PROTECTED_BRANCHES`에 `dev`를 더했고 비교는 `casefold`다(반박이 찾은 빈칸).
- `sibling_overlap`은 기준 ref(규칙)와 다른 오래 사는 브랜치를 모두 형제로 견준다. 기준이 dev일 때 dev에 없고 main에만 있는 번호(hotfix)를 놓치지 않기 위해서다.
- `check_ticket`은 `hotfix/<slug>`를 harness 티켓(`.scratch/harness/issues/<slug>.md`)의 브랜치 모양으로 알아본다. 기능 코드를 고치는 핫픽스도 같은 자리다. 안내문은 hotfix 브랜치에는 `hotfix/<slug>`를, chore 브랜치에는 hotfix를 권하지 않는다.
- 보고(`morning_*`)는 작업 브랜치가 없어 `integration_ref`(= `base_ref(root, None)`)를 읽는다.

## 한 것 (모두 커밋하지 않은 작업 트리에 있다)

- 새 파일: `tools/base_rule.py`, `tests/tools/test_base_rule.py`, `tests/tools/test_morning_sources_base.py`.
- 고친 도구: `sibling_overlap`, `tidy_checkouts`, `check_ticket`, `check_constitution_version`, `morning_sources`, `morning_collect`, `mutate`, `wait_ci`, `hook_prompt_directive`, `queue_open_rows`, `rerun_select`(뒤의 넷은 글만).
- 시험: `test_sibling_overlap`(dev·hotfix 다섯과 반박 셋), `test_tidy_checkouts`(dev 넷과 반박 넷에 보호 브랜치 대소문자), `test_check_ticket`(hotfix 갈래), `test_check_constitution_version`(dev 둘).
- 티켓 `.scratch/harness/issues/dev-base-tools.md`: 결정표와 반박 결과를 끝에 적었고 `Status: done`, 수용 기준 체크. `uv run python tools/plan_table.py`를 돌려 `.scratch/plan.md`를 갱신했다.
- `uv run ruff check .`와 `uv run ruff format --check .`는 초록이다. `uv run python tools/run_checks.py`는 백그라운드로 돌렸으나 인계로 멈췄다. 새 세션이 다시 친다.

## 남은 것

1. 셀프 리뷰(`/code-review`)를 Standards·Spec 두 축으로 돌려 Critical·Major를 고친다. 범위는 `origin/main` 이후의 작업 트리와 미추적 파일 셋이다. 명세는 티켓 파일과 ADR 0043이다.
2. `uv run python tools/run_checks.py`(Bash `timeout` 600000 또는 백그라운드)와 린트를 다시 친다. 이 PC에서 다른 세션이 함께 돌면 600초에 닿으니 백그라운드로 넘어가면 다시 치지 않고 끝 알림을 기다린다.
3. 커밋 전에 `git branch --show-current`와 `uv run python tools/sibling_overlap.py`를 친다. 커밋은 `git commit -F`로, 트레일러는 `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`다.
4. PR을 열고(PR 본문 끝에 `🤖 Generated with [Claude Code](https://claude.com/claude-code)`), ccd_pr의 `get_status`와 필요하면 `bind_pr`로 묶는다. 봇 회차와 병합은 `merge.md`대로 묻지 않고 진행한다. 워크트리에서 병합하므로 "워크트리에서 병합할 때"를 따른다.
5. 단계를 닫는 세션이면 회고(`retro`)와 이 일지의 "다음" 절을 쓴다.

## 셋째 세션의 기록 (PR과 병합)

이 세션의 제목은 `chore/dev-base-tools`다. 사용자 프롬프트는 앞 세션이 낸 지시문 한 건이고 위 "사용자 프롬프트"와 같다(이번 요청 범위: PR과 병합까지).

- `tidy-checkouts`를 먼저 돌았다. 루트는 이미 `origin/main`(dc616c58c)과 같아 당길 것이 없었고, 병합된 워크트리는 모두 쥔 프로세스나 바뀐 파일이 있어 지울 것이 없었다.
- `origin/main`이 한 칸 나아가 있어(`dev-review-bot-off`, #536) 병합 커밋으로 합쳤다. 충돌은 없었다. 합친 뒤 `sibling_overlap`은 번호 겹침과 함께 고친 파일 없음을 냈다.
- 합친 상태로 `uv run python tools/run_checks.py`를 다시 쳤다. 출력 끝에서 열 검사(check-ticket, zizmor, lint-imports, check-instructions, check-type-escapes, pyright, pyright-linux, run-hooks, pytest, web-verify)가 모두 `Passed`였고 종료 코드는 0이었다(손으로 읽었다). `uv run ruff check .`는 `All checks passed!`, `uv run ruff format --check .`는 `2106 files already formatted`였다. 앞 일지의 "확인할 점"에 있던 `uv run pyright`는 이 러너의 pyright 두 줄이 통과해 갈음된다.
- 위 "알림"이 짚은 합치기는 이 세션에서 끝냈다. 앱의 세션 목록은 이 브랜치의 PR을 아직 보이지 않았다(PR 없음, `gh pr list --head chore/dev-base-tools --state all`이 빈 배열).

- 표준 Major: `tidy_checkouts` 독스트링이 두 브랜치를 같은 원격의 보호 브랜치로 보고 커밋이 사라지지 않는다고 쓴 것은 ADR 0043이 원격의 dev 보호를 사람의 몫으로 남겨 근거가 없었다. 근거를 추적 ref가 커밋을 쥐고 있고 그 ref가 사라지면 `remove-branch`가 다시 판정한다는 것으로 바꾸고 원격 보호를 근거로 삼지 않는다고 적었다. 같은 글의 지울 것이 늘어나는 길은 없다는 문장은 잘못 지우는 길은 늘지 않는다는 뜻으로 고쳤다(두 축이 같이 짚었다).

남긴 것과 이유:

- Duplicated Code `sibling_overlap._has_trunk`와 `base_rule.has_ref`: 모듈 독스트링이 "ref는 이 모듈의 git 호출로 본다"고 정했고(시험이 이 모듈의 `_git_result`를 대신하는 자리가 있다) 합치면 시험 고침이 넓다. Minor로 남긴다.

## 확인할 점

- 이 세션의 마지막 `tidy_checkouts` 변경(`casefold`)은 윈도 `for-each-ref`의 대소문자 변경에 대한 방어라 리눅스 CI에서도 단언이 맞는지 본다(시험은 순수 함수 `judge_branch`로 고정했다).
- 편집기가 낸 pyright 진단(`"owner" is not accessed` 등, `tests/tools/test_sibling_overlap.py` 1157·1253·2022행 근처)은 이번에 더하지 않은 줄을 가리키는 것으로 읽었다(진단 목록의 줄 번호를 보았을 뿐 `uv run pyright`는 아직 돌리지 않았다). 새 세션이 `uv run pyright`를 `run_checks.py`와 함께 확인한다.
- 위 "한 것"의 시험 결과(`-k "dev or hotfix"` 5 통과, 반박 `-k "반박"` 3 통과, tidy `-k "반박 or 보호_브랜치"` 9 통과, `test_check_constitution_version.py` 27 통과, `test_morning_sources_base.py` 4 통과)는 이 세션이 `uv run pytest`로 돌려 본 것이다. 전체 pytest는 아직 돌리지 않았다.
