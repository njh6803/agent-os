## 안내의 명령을 돌려 본 결과

환경: 이 PC는 Windows 10 + Docker Desktop(Engine 29.9.2)이고, 리눅스 소유와 권한이 필요한 시험은 WSL Ubuntu(root, ext4)에서 쳤다. 안내가 지원하는 최소 판(Engine 28.3.3)은 오프라인 반입(아래 넷째)만 그 판의 `docker:28.3.3-dind`에서 쳤고 나머지는 29.9.2에서 쳤다. 이미지는 09의 e2e가 지은 `agent-os-e2e/*:0.1.0-rc.1`이고, 묶음은 `tools/release.py bundle --number 0.1.0-rc.1 --namespace agent-os-e2e`로 만들었다.

- 스스로 서명한 인증서(안내의 `openssl req -x509` 한 줄)와 `root:101 0640` 키로 프록시가 떴고 TLSv1.3으로 응답했다. 손으로 봤다. 키가 `root:root 0600`이면 프록시가 종료 1로 끝난다는 안내의 문장은 시제품의 기록(`bridge_edge` README)을 옮긴 것이고 이번에 다시 재지 않았다.
- 위젯 미리보기 페이지 개인 키를 `root:10001 0640`으로 두면 그 컨테이너가 섰고, `0600`이면 종료 1로 끝났다. 손으로 봤다.
- 바인드 마운트(안내 8절의 명령 그대로): 이미지의 플러그인을 호스트 폴더로 옮기고 두 폴더를 `10001:10001`로 넘기면 플러그인을 끄고 켜는 요청이 204와 204였고 실행이 트레이스 파일을 만들었다. 손으로 봤다.
- 인터넷이 막힌 곳의 반입(안내 9절): 첫 판은 이미지를 `docker save`한 파일을 `docker load`한 뒤 compose가 프록시 이미지를 못 찾았다. compose가 `nginx@sha256:…`로 고정한 프록시 이미지는 Engine 28.3.3에서 파일로 저장했다가 불러오면 그 digest 이름이 남지 않기 때문이다(서버 쪽에서 그 이름의 이미지를 찾지 못해 받으려다 실패했다). 그래서 안내가 프록시 이미지에 태그(`agent-os-proxy:local`)를 붙여 옮기고 서버의 `compose.override.yaml`로 그 태그를 쓰게 고쳤다. 고친 명령을 네트워크 없는(`--network none`) Engine 28.3.3 dind에서 쳤고, 파일의 `sha256sum -c`가 통과하고 이미지 ID 대조(`docker image inspect --format '{{.Id}}'`)가 같았고 프록시가 떴다. 안내가 대조할 해시를 둘로 나누어 적는다(파일의 해시는 옮기는 도중의 손상을, 이미지의 ID는 불러온 이미지가 받은 이미지와 같은지를 본다. 레지스트리 digest는 불러온 이미지에 남지 않으므로 쓰지 않는다). 돌려 보지 못한 것: `docker compose pull`은 실제 이름공간 이미지가 아직 레지스트리에 없어 프록시 이미지만 받아 봤다. 나머지 이미지는 로컬에 지어 둔 것으로 `save`와 `load`를 쳤다.
- 안내를 처음부터 따라 한 순서(WSL, 새로 푼 묶음, `/etc/hosts`에 `agent.example.com`을 임시로 더했다가 지웠다): 환경 변수 파일(권한 600, 토큰 둘을 `openssl rand -hex 32`로, API 키는 자리표시 값), 인증서와 키, 개인 키와 공개 키 추출, `site/sites.toml`에 공개 키 붙여 넣기, `docker compose up -d --wait --wait-timeout 600`이 종료 0이었고 `docker compose ps`가 넷은 `healthy`, 프록시는 `Up`이었다. `up`이 끝났을 때 컨테이너는 29초 된 상태였다. `https://agent.example.com/`를 `-L`로 따라가면 200(`/`는 `/portal/`로 넘어간다), `http://`는 308, 서버의 `127.0.0.1:3000`은 200, 프록시의 `/api/`는 404, 발행 포트는 프록시의 80·443과 관리 화면의 `127.0.0.1:3000`뿐이었다.
- 이 따라 하기에서 안내의 틀린 자리를 넷 고쳤다. 첫 curl이 200이라던 것은 `/`가 302라 `-L`을 붙였다. `docker compose ps`에서 프록시가 `running`으로 보인다던 것은 `Up`만 보여 고쳤다. 판 번호를 한 줄만 바꾸라는 줄이 가리킨 절 번호가 10절이 아니라 11절이었다. 위젯이 다시 빌드하는 시간을 "수십 초"라 적은 것은 잰 값(아래)에 맞춰 고쳤다.
- 사이트 파일을 고친 뒤 재기동(안내 5절): `portal/portal.toml`의 제목을 고친 직후에는 새 제목이 페이지에 없었고(`-L`로 받아 센 줄 수 0), `docker compose restart serve widget portal` 뒤 위젯 경로(`/widget`)가 502를 세 번(0, 3, 6초) 낸 뒤 9초에 200이 되었고, 그 뒤 페이지에 새 제목이 들었다(3줄). 위젯이 다시 뜨는 동안 응답하지 않는 것을 봤다. 이 PC에서 이번 한 번은 9초였고, 처음 이미지로 빌드하는 `up`은 29초였다. 명세는 위젯이 뜨기까지 21.5~31.4초를 쟀다고 적어, 안내에는 10초에서 30초 사이이고 서버의 사양에 따라 더 걸릴 수 있다고 적었다. 이 재기동은 `portal.toml`의 제목만 고쳐 본 것이고, 사이트 파일(`sites.toml`)을 고친 재기동은 따로 돌려 보지 않았다. 안내가 고치라는 허용 출처가 실제로 듣는지는 e2e의 CORS 시험이 대신 본다.
- 프록시 설정(안내 6절): `nginx -c /etc/agent-os/proxy/nginx.conf -t`는 종료 0이었고 `-s reload`도 0이었다. 설정에 없는 지시문을 붙이면 `-t`가 종료 1이었다. 같은 이름으로 인증서를 새로 만들어 두고 `-t`와 reload를 치니 서버가 내는 인증서의 serial이 바뀌었다.
- 위젯 미리보기 페이지에서 질문하고 답을 받는 것: 따라 하기에서는 API 키 자리에 자리표시 값을 넣었으므로 모델 호출은 하지 않았다. 대신 단독 e2e로 봤다(아래). 처음에는 따라 하기 스크립트가 루트의 `.env`에서 API 키를 읽어 묶음의 `.env`에 옮기게 짰는데 자동 모드 분류기가 거부했다(이유 없음). 키는 문서화된 길인 playwright 프로세스의 `--env-file`로만 쓰기로 하고 스크립트의 그 줄을 지웠다.

## `bridge_recover` 프로브 재측정

README에 "다시 돌린 날짜(2026-11-16, 배포 안내 티켓)" 절을 더했다. 같은 명령(`--reuse` 없음)으로 전체를 돌렸다. 측정 87회차, 측정 아님 0회차, 종료 0. 기록 파일(`raw.log`)의 시각이 20:06부터 20:34까지라 약 28분이 걸렸다(손으로 봤다). 결론 1~10의 방향은 바뀌지 않았다.

- 안내의 "약 10초": (다) upstream resolve에서 뒷단을 다시 만든 뒤 프록시로 닿은 때가 다시 만들기·다시 시작·`rm -f` 뒤 `up -d`·판 올림·넷을 한꺼번에 다시 만들기 다섯 조작에서 8.8~9.3초였다. 안내의 문장과 09 시험의 문턱 15초를 그대로 둔다.
- 8번(설정 파일 reload): 폴더째 얹으면 세 가지 고치는 길 모두 reload로 먹었고, 파일 하나로 얹으면 바꿔 끼우기와 `sed -i`가 reload와 `up -d`로는 안 먹고 `restart proxy` 뒤에 먹었으며, 깨진 설정은 `nginx -t`와 reload가 종료 1이고 옛 설정이 계속 답했다. 명세의 "폴더째 얹는다" 결정을 바꾸지 않았다.
- `supervise.sh`의 환경 변수 표지가 dockerd에 실리는지: 손으로 봤다(README에 근거를 적었다). 표지를 환경에서 직접 읽지는 않았고 정상 종료 갈래의 종료 코드 143에서 그렇다고 읽었으므로 어림이 섞여 있다.

## 판단과 번복

- 안내에 `docker compose pull`이 든 반입 명령을 실제 이름공간의 이미지로 시험하지 못했다. 이름공간의 이미지는 아직 출시 전이라 레지스트리에 없다. 출시 PR의 첫 실제 배포 때 그 한 줄을 다시 칠 일을 아래 "다음"에 둔다.

- 안내의 어조는 운영자에게 하는 존댓말(`~하십시오`, `~입니다`)로 맞췄다. 저장소의 다른 사용자 문서가 없어 기준이 될 선례가 없었고, 이 문서가 처음이다.

범위: base `origin/dev`, 수정 2개와 미추적 4개, 커밋 0. 명세 축은 이 세션이, 표준 축은 서브에이전트(sonnet, high)가 맡았다. 표준 축은 pytest와 변이 표를 시간 안에 돌리지 못해 "11 passed, 6/6"을 확인하지 못했다고 적었고, 이 세션이 반영 뒤에 다시 돌려 12 passed와 6/6을 봤다.

## 회고

후보 여섯, 판정은 승인 1, 기각 5, 넘김 0이다. 승인은 새 항목이 아니라 열린 항목에 회차를 더하는 것이다.

- 승인: 셀프 리뷰 직전 인계 열기(`open_session.ps1 -Action send`)를 자동 모드 분류기가 사유 없이 거부했다. 조건은 사건(이 세션이 제목을 되돌리고 `인계 못함`을 적었다), 층(열린 항목이 이미 처방한 사건이라 회차로 센다), 되돌림(회차 한 줄)이다. `open-session-send-denied-despite-allow-rule`에 13회차로 더했다.
- 기각: 따라 하기 스크립트가 루트 `.env`의 API 키를 묶음의 `.env`로 옮기려 하자 분류기가 거부했다. 비밀을 옮기는 길을 앱 가드가 그 자리에서 막은 것이다.
- 기각: `cd`로 하위 폴더에 들어가려다 훅이 막았다. 이미 있는 훅이 그 자리에서 막았다.
- 기각: 변이 표의 `'''` 다중행 원문이 0번으로 나왔다. `tools/mutate.py --check`가 그 자리에서 알렸다.
- 기각: 한 번 잰 9초를 "10초 안팎"으로, 일지의 `REQUIRED` 수와 소요 시간을 옛 값으로 적은 것을 셀프 리뷰 두 축이 잡았다. 리뷰가 잡도록 둔 기준(`code-review`의 주장 검증 7·1)이라 리뷰가 제 몫을 한 것이다.
