## 조사: 위젯과 위젯 미리보기 페이지의 지금 코드

인터뷰 전에 Explore 서브에이전트 둘을 띄워 지금 코드를 읽게 했다. 아래는 그 둘의 보고를 옮긴 것이고, 모두 코드를 읽은 것이며 브라우저로 돌려 본 것은 없다. 줄 번호는 보고가 적은 것이고 이 세션은 `opener|dispatchEvent|CustomEvent|localStorage`가 위젯 소스에 없는 것(Grep, 일치는 스토리 하나와 `testing/site.ts`뿐)과 미리보기 페이지 서버의 끝점 정규식·401 문구(Grep)만 다시 대 보았다.

위젯(`web/apps/widget`):

- 페이지와의 통로는 토큰 묻기 하나다. 페이지 안 방식은 요소의 `tokenProvider`(`element/WidgetElement.tsx`의 접근자, 타입 선언은 `unknown`)이고 iframe 방식은 postMessage의 `agent-os/token-request`와 `agent-os/token`이다(`lib/token.ts`의 `requestToken`). 페이지에 알리는 이벤트나 콜백 속성은 없다.
- 토큰을 받지 못한 까닭(함수 없음, 던짐, 문자열 아님, 거부, 10초 초과, iframe의 `token: null`, 풀 수 없는 JWT)은 가르지 않고 모두 "로그인 정보를 받지 못했습니다." 알림이 된다(`element/token.ts`의 `providerToken`, `components/pages/drivers.ts`의 `authorize`, `FailureAlert.tsx`).
- 토큰의 페이로드를 직접 풀어 `iss`와 `sub` 둘만 읽고 서명은 보지 않는다(`lib/storage.ts`의 `bundleOf`).
- 브라우저 저장소는 `sessionStorage` 하나이고 키는 `agent-os-widget:<에이전트 이름>`이다. `localStorage`, 쿠키, IndexedDB는 쓰지 않는다.
- `mode` 속성이 없을 때 시스템 설정을 따르는 것은 CSS의 `prefers-color-scheme`이다(`web/packages/ui/src/styles/theme.css`). 위젯 안에 모드를 바꾸는 스위치는 없고, 위쪽 띠에는 이름과 "새 대화" 버튼만 있다(`TopBar.tsx`). 디자인 시스템에는 `Switch` 부품이 있다.
- 위젯 상자를 덮는 덮개 부품은 없다. `.claude/rules/web-design.md` 51행의 "위젯은 남의 화면을 덮지 않고 대화 안에 묻는다"는 사이트의 화면을 덮는 일을 말한다.
- 위젯 페이지(`/widget`)는 Next 앱이 낸다(`next.config.ts`의 `basePath`). 그 주소를 최상위 창이나 팝업으로 열면 `window.parent`가 자기 자신이라 토큰 요청이 자기 창에 가고, 답이 없어 10초 뒤 "로그인 정보를 받지 못했습니다."가 된다(코드의 흐름을 따라 읽은 것이다). `window.opener`를 쓰는 코드는 없다.

위젯 미리보기 페이지(`web/apps/portal`):

- 위젯을 페이지 안 방식으로 넣고, `tokenProvider`는 같은 출처의 `POST /portal/sites/<이름>/token`을 부른다(`browser/portal.ts`).
- 페이지가 그리는 것은 위쪽 띠(사이트 셀렉트, 다크 모드 스위치), 둘 다 사이트의 비활성 로그인 단추 줄, 사이트를 바꾼 뒤의 정보 글, 위젯 자리(뼈대, 고지 확인 덮개, 로그인 안내, 위젯), 짧은 고지 줄과 "고지 전문" 펼침, 보고서 링크다(`server/page.ts`).
- 다크 모드 스위치의 값은 스크립트의 변수 `modeOverride` 하나에만 있고 어느 저장소에도 두지 않는다. 사이트를 고를 때마다 비운다.
- 고지는 사이트 설정의 `notice` 칸 하나(전문)이고 짧은 줄은 사이트가 바꾸지 못하는 페이지 상수다(`server/config.ts`, `server/page.ts`, `server/notice.ts`). 확인을 누르면 `POST /portal/sites/<이름>/acknowledgement`가 쿠키 `portal_anon`을 내고, 쿠키가 없으면 토큰 끝점은 401 "고지 확인이 필요합니다."다(`server/handler.ts`).
- 페이지 응답의 CSP에 `frame-ancestors 'none'`이 있어 다른 사이트의 iframe에 들어갈 수 없다. `/portal/?site=<이름>`으로 열면 그 사이트가 골라진다.

> 질문: 주소 하나를 팝업 창으로 열면 창 전체가 위젯인 'URL 방식'에서, 그 창의 페이지는 누가 내고 로그인과 토큰 서명은 누가 맡을까요?

> 질문: 고지(질문이 기록되고 모델로 보내진다는 안내)에서, 입력창 아래의 짧은 고지 줄과 질문 전에 전문을 보여 주는 확인 덮개를 누가 그릴까요?
>
> 사용자: "둘 다 위젯이 (Recommended)" — 설명: 사이트가 짧은 고지 글과 전문을 위젯에 넘기면, 위젯이 입력창 아래에 한 줄과 '고지 전문' 펼침을 그립니다. 사이트가 '아직 확인하지 않은 브라우저'라고 알리면 위젯이 상자를 덮는 덮개에 전문과 '확인하고 질문하기' 버튼을 그리고, 누르면 사이트에 알려 사이트가 기록합니다. 고지를 넘기지 않은 사이트의 위젯은 지금처럼 고지 없이 뜹니다. 세 방식에서 모양이 같고 고객사는 화면을 만들지 않습니다. 대가는 위젯과 사이트 사이의 약속이 늘고(고지 글 넘기기, 확인 알리기) 위젯에 덮개 부품을 새로 짓는 것입니다(지금 위젯에는 덮개 부품이 없습니다).

같은 라운드의 둘째 화면(다크 모드)도 훅이 한 번 막았다. `web/apps/widget/element/WidgetElement.tsx` 99~105행(`mode`가 있으면 `data-mode`를 달고 없으면 지운다)을 읽고, `prefers-color-scheme`(`theme.css` 567행)과 `modeOverride`(`portal.ts` 442·489행), 위젯의 `sessionStorage`(`storage.ts` 185행)를 Grep으로 본 뒤 같은 글로 다시 올렸다.

> 질문: 위젯 안의 다크 모드 스위치로 고른 값(밝게 또는 어둡게)을 얼마나 오래 기억할까요?
>
> 사용자: "브라우저에 계속 기억 (Recommended)" — 설명: 위젯이 고른 값을 브라우저 저장소에 두어, 탭을 닫았다 열어도 팝업을 새로 열어도 유지됩니다. 한 번도 고르지 않은 사람은 시스템 설정을 따릅니다. 값은 '밝게/어둡게' 하나뿐이고 사람을 가리키지 않습니다. 대가는 위젯이 처음으로 탭을 닫아도 남는 값을 브라우저에 둔다는 것입니다(지금 위젯은 탭 저장소만 쓰고 쿠키는 쓰지 않습니다). 페이지 안 방식에서는 그 값이 고객사 사이트의 저장소에 위젯 이름표를 달고 놓입니다. iframe 방식에서는 브라우저가 다른 사이트 안의 저장소를 막으면 기억되지 않을 수 있습니다(어림, 재 보지 않았습니다).

> 질문: 사이트가 위젯의 밝기를 미리 정해 준 경우(위젯에 mode 값을 적어 준 사이트)에는 다크 모드 스위치를 어떻게 할까요?
>
> 사용자: "늘 사람이 고르기" — 설명: 스위치는 모든 위젯에 보입니다. 사이트가 정한 값은 처음 한 번의 값일 뿐이고 사람이 고르면 그 선택이 이깁니다. 대가는 자기 페이지 밝기에 위젯을 고정해 둔 고객사의 위젯이 사람의 선택으로 페이지와 다른 밝기가 될 수 있다는 것입니다.

둘째 답은 추천("정한 사이트는 고정")과 다른 안이다. 고르지 않은 추천안의 설명: "밝기를 정해 준 사이트의 위젯은 지금처럼 그 값으로 고정하고 스위치를 그리지 않습니다. 정하지 않은 사이트의 위젯에만 스위치가 보이고, 처음에는 시스템 설정을 따릅니다. 자기 페이지의 밝기에 위젯을 맞춰 둔 고객사의 화면이 바뀌지 않습니다. 대가는 그런 사이트에서는 최종 사용자가 밝기를 고르지 못한다는 것, 밝기를 정하지 않고 이미 위젯을 넣어 둔 사이트에는 스위치가 새로 나타난다는 것입니다."

## 인터뷰 라운드 2

라운드 1의 답으로 열린 가지를 올렸다. 올리기 전에 대 본 것: iframe 방식의 위젯은 허용 목록의 출처에서 온 답만 받는다(`web/apps/widget/lib/token.ts` 32행을 읽었다). 미리보기 페이지의 스위치는 페이지의 뿌리와 위젯의 `mode`를 함께 바꾼다(`web/apps/portal/browser/portal.ts` 489~491행을 읽었다). 사이트 토큰의 수명 상한은 600초다(`src/agent_os/http/sites.py` 49행 `MAX_LIFETIME_SECONDS = 600`, `EMBED.md` 124행). 위젯은 요청마다 토큰 함수를 부른다(`web/apps/widget/components/pages/drivers.ts` 65행). 기능 계획 표에서 step-up-login과 deploy-package가 portal-login을 기다린다(`.scratch/plan.md`). 첫 화면은 훅이 한 번 막았고(수가 든 문장 "최대 10분"), `sites.py`를 본 뒤 같은 글로 다시 올렸다.

첫 화면의 질문 넷 가운데 셋에 사용자가 선택지를 고르지 않고 글로 답했다. 셋 모두 설계의 방향을 바꾸는 말이라 글자 그대로 옮긴다.

> 질문: 고객사가 로그인 주소와 고지 글 같은 것을 위젯에 알려 주는 자리를 어디로 할까요?
>
> 사용자: "위젯 관리자 페이지에서 위젯 설정으로 등록하면 되는거 아니야? 로그인, 로그아웃 주소, 고지글과 전문을 입력하게 굳이 토큰에 담을 필요가... 보일 이름정도만 토큰에서 받고 바뀌는 값들"

올린 선택지는 둘이었고 둘 다 고르지 않았다. "토큰 답에 모두 (Recommended)"(위젯이 토큰을 물을 때 고객사가 토큰, 보일 이름, 로그인 주소와 로그아웃 주소, 짧은 고지 글과 전문, 상태를 한 번에 답하고, 위젯이 알릴 것도 토큰을 물을 때 함께 보낸다)와 "바뀌지 않는 글은 태그에"(로그인 주소, 로그아웃 주소, 고지 글은 위젯 태그나 주소 뒤의 값에 적고 달라지는 것만 토큰 답에 싣는다)다. 사용자의 답은 셋째 길이다. 바뀌지 않는 값은 운영자가 관리 화면에서 위젯 설정으로 등록하고, 토큰 답에는 보일 이름과 그때그때 바뀌는 값만 싣는다.

> 질문: URL 방식으로 연 위젯 창에서, 그 창을 연 고객사 페이지가 닫히거나 다른 곳으로 이동해 토큰을 더 받지 못하게 되면 어떻게 할까요?
>
> 사용자: "위젯이 질문마다 새 토큰을 받을 필요가 있을까?
> 토큰의 만료시간을 알 수 있지 않아? 토큰 만료 시간으로 처리하면 될 것 같은데 굳이 매 질문마다 새 토큰을 받아야 해?"

올린 선택지는 "안내하고 입력 막기 (Recommended)"와 "받아 둔 토큰으로 계속"이었다. 사용자의 답은 URL 방식만이 아니라 위젯이 질문마다 토큰을 새로 받는 지금의 규칙 자체를 묻는다.

> 질문: URL 방식으로 연 위젯 창에서 '로그인하고 질문하기'를 누르면 어느 창이 로그인 페이지로 갈까요?
>
> 사용자: "로그인은 새 창으로 띄어주면 안되나? 그러면 위젯이 닫히거나 다시 열일 없고 위젯 안에서 로그인 할 필요도 없잖아."

올린 선택지는 "위젯 창이 이동 (Recommended)"과 "원래 페이지가 이동"이었다. 사용자의 답은 셋째 길(로그인 페이지를 새 창으로 연다)이고, 라운드 1의 "로그인 주소로 이동"(위젯이 든 창을 그 주소로 보낸다)과 ADR 0059가 거부한 안 "팝업 창으로 로그인한다"에 닿는다.

> 질문: 로그인 서버가 로그인을 거절했을 때(예: 허락되지 않은 계정) '무엇이 막혔는지 한 문장'은 누가 그릴까요?
>
> 사용자: "위젯이 그리기" — 설명: 사이트가 토큰 답에 '로그인이 거절됨'과 문장을 싣고, 위젯이 자기 안에 알림으로 보입니다. 모든 사이트에서 같은 생김새입니다. 대가는 위젯의 약속에 상태가 하나 더 들어가고, 거절 뒤 그 상태를 언제 지울지(새로 고치면 사라지는지)를 사이트가 따로 기억해야 한다는 것입니다.

넷째 답은 추천("사이트가 자기 화면에")과 다른 안이다. 고르지 않은 추천안의 설명: "위젯은 거절을 모릅니다. 미리보기 페이지는 로그인 서버에서 돌아온 자리에서 자기 화면(위젯 바깥)에 한 문장을 보이고, 위젯은 '로그인하지 않음' 상태 그대로 로그인 단추를 보입니다. 고객사 사이트는 자기 로그인 페이지가 알아서 알립니다. 위젯의 약속에 상태가 하나 덜 들어갑니다. 대가는 거절 문장의 생김새가 위젯의 다른 알림과 따로라는 것, 고객사마다 거절을 알리는 방식이 다를 수 있다는 것입니다."

셋째 답(로그인은 새 창)은 조사 없이 범위를 물을 수 있어 바로 둘째 화면에 올렸다. 올리기 전에 대 본 것: 위젯 코드에 `visibilitychange`, `focus` 리스너, `pageshow`, `window.open`이 없다(`web/apps/widget`의 `*.{ts,tsx}`를 Grep으로 봤고 0건이다). ADR 0059 17행 "로그인은 같은 탭이 로그인 서버로 갔다가 돌아오는 이동이다. 팝업을 쓰지 않는다."와 38행의 거부한 안 "팝업 창으로 로그인한다. 거부했다. 팝업 차단의 영향을 받고 휴대폰에서 동작이 다르다."를 읽었다. 이 화면도 훅이 한 번 막았고 같은 글로 다시 올렸다.

> 질문: '로그인하고 질문하기'를 누르면 로그인 페이지를 새 창으로 여는 방식을 어디까지 쓸까요?
>
> 사용자: "모든 방식에서 새 창 (Recommended)" — 설명: 페이지 안 방식, iframe 방식, URL 방식 모두 '로그인하고 질문하기'(로그인 시간이 끝난 뒤의 '다시 로그인'도)를 누르면 로그인 주소가 새 창으로 열립니다(휴대폰에서는 새 탭). 위젯이 든 창은 그대로라 위젯이 닫히거나 다시 열리지 않습니다. 사람이 로그인하고 위젯이 든 창으로 돌아오면 위젯이 토큰을 다시 물어 로그인된 것을 알아챕니다. 라운드 1에서 고르신 '위젯이 든 창을 로그인 주소로 보낸다'를 이것이 대신합니다. 대가는 셋입니다. 로그인한 뒤 새 창을 닫고 돌아오는 일은 사람이 합니다(미리보기 페이지의 로그인은 끝나면 창이 스스로 닫히게 지을 수 있지만 고객사 로그인 페이지는 고객사 몫입니다). 위젯이 '창으로 돌아왔다'를 알아채는 코드를 새로 짓습니다(지금 위젯에는 없습니다). 지난 인터뷰는 미리보기 페이지의 로그인에 '팝업 창'을 쓰지 않기로 했고 까닭은 팝업 차단과 휴대폰에서의 동작이었습니다(ADR 0059). 단추를 누른 그 순간에 여는 창은 보통 차단되지 않지만 재 보지 않았습니다(어림).

이 답은 라운드 1의 "로그인 주소로 이동"(위젯이 든 창을 그 주소로 보낸다)을 대신한다. 사이트가 로그인 주소와 로그아웃 주소를 글자로 알려 준다는 것과 로그아웃 주소가 없으면 로그아웃 버튼을 그리지 않는다는 것은 그대로다.

> 질문: 위젯이 다크 모드 스위치를 갖게 되면, 미리보기 페이지 위쪽 띠에 있는 다크 모드 스위치는 어떻게 할까요?
>
> 사용자: "없애기 (Recommended)" — 설명: 미리보기 페이지 띠의 스위치를 없애고 위젯 안의 스위치만 둡니다. 위젯의 스위치는 위젯만 바꾸고, 페이지 바탕은 사이트가 정한 밝기(없으면 시스템 설정)를 따릅니다. 미리보기 페이지의 위젯이 고객사 페이지에 넣었을 때와 똑같이 동작합니다. 대가는 위젯을 어둡게 골라도 페이지 바탕은 그대로라 둘의 밝기가 다를 수 있다는 것입니다. 지금은 띠의 스위치 하나가 페이지 바탕과 위젯을 함께 바꿉니다.

## 조사: 위젯 설정을 둘 자리와 요청마다 토큰을 받는 까닭

사용자의 첫째·둘째 답에 쓸 사실을 Explore 서브에이전트가 찾았다. 모두 코드나 문서를 읽은 것이고 실행해 본 것은 없다.

- **사이트 파일.** 형식은 `src/agent_os/main.py` 305~382행(`_SiteFile`, `_SiteEntry`, `_LimitsEntry`)이 정한다. 사이트 하나의 칸은 `issuer`, `audience`, `public_keys`, `allowed_origins`, `agents`, `limits`이고 모르는 키는 거부한다. `serve`가 시작할 때 한 번 읽는다(175행). 고치는 길은 파일 편집뿐이고 `openapi.json`에 사이트 경로가 없다. 형식을 정한 것은 ADR 0023이다.
- **관리 화면.** `web/apps/admin`에 사이트나 위젯 설정 화면이 없다. `openapi.json`의 경로 열셋에 사이트나 위젯 경로가 없다.
- **위젯이 받는 설정.** 빌드 때 사이트 파일에서 허용 출처와 요청 글자 수 상한을 번들에 담는다(`web/apps/widget/lib/build.ts`). 실행 중에 받아 오는 설정은 없고, 위젯이 부르는 서버 경로는 `/end-user/runs` 아래 넷뿐이다. 토큰 없이 부를 수 있는 서버 경로는 `/health` 하나다(`src/agent_os/http/auth.py` 40행).
- **위젯 미리보기 페이지 설정.** `web/apps/portal/server/load.ts`가 시작 때 한 번 읽는다. 사이트 칸은 `name`, `issuer`, `agent`, `heading`, `intro`, `theme`, `mode`, `assurance`, `notice`, `report_url`이다(`server/config.ts` 65~76행). 위젯에는 속성으로 넘긴다(`browser/portal.ts` 366~370행).
- **ADR 0047.** 15행 "관리 화면과 관리 API에 위젯 전용 기능을 두지 않는다.", 16행 "위젯의 외형과 문구는 위젯과 사이트가 가진다. 사이트가 위젯을 넣을 때 넘기는 임베드 옵션(커스텀 요소의 속성, iframe의 초기화 메시지)이 값을 정하고, 기본값은 위젯 배포의 설정 파일에 둔다. 맞춤 설정 화면이 필요하면 사이트 쪽이나, 떼어 낸 뒤의 위젯 프로젝트에 만든다.", 17행 "사이트 파일은 채널의 신뢰 설정만 든다. … 위젯의 외형 칸을 더하지 않는다", 43행의 거부한 안 "위젯 맞춤 설정을 관리 화면의 사이트 메뉴에 두고 `serve`가 공개 경로로 내준다. 거부했다."
- **기능 계획 둘.** portal-admin(슬라이스 10)은 설정을 고치는 화면을 위젯 미리보기 페이지 쪽에 두고 원천을 위젯 미리보기 페이지 설정 파일로 둔다. 사이트 파일의 허용 출처와 요청 글자 수 상한도 그 화면에서 바꾸고 위젯이 그 값을 실행 중에 읽게 고치는 일을 함께 하기로 했다. widget-appearance(슬라이스 10)는 새 모양 칸을 위젯의 속성과 위젯 미리보기 페이지 설정에 함께 더한다.
- **요청마다 토큰을 받는 까닭.** ADR 0024 29행 "서명 토큰은 사이트가 준 손잡이로 요청할 때마다 새로 받는다. … 토큰은 요청을 시작할 때만 검증되므로 열린 스트림은 만료와 무관하게 이어진다." ADR 안에 까닭을 따로 적은 문장은 없다. `.scratch/web-widget/spec.md` 101행 "내 백엔드가 서명한 짧은 토큰을 함수(페이지 안 방식)나 postMessage(iframe 방식)로 요청마다 넘기고 싶다. 그래야 비밀이 브라우저에 남지 않는다.", 176행 "서명 토큰은 클라이언트가 들지 않고 부르는 쪽이 요청마다 `Authorization` 헤더로 넘긴다. 위젯은 토큰 손잡이가 실패한 것을 요청을 보내기 전에 가려 401과 같은 화면으로 보여야 하기 때문이다.", 250행은 요청마다 새로 받은 토큰의 `iss`와 `sub`를 저장한 것과 견준다.

이 세션이 보고에서 다시 대 본 것: ADR 0047 14~17행과 43~44행을 Read로 열었다. 44행은 거부한 안 "위젯 전용 서버(저장소, 인증, 관리 화면)를 둔다. 거부했다. 저장할 것이 사이트별 값 몇 개라서 서버를 하나 더 운영할 이유가 없다. 셀프 서비스 멀티테넌시가 필요해지면 다시 본다(PRD의 미룬 것)."이다. 위젯 코드에서 서버를 부르는 곳은 `element/fonts.ts`, `components/pages/drivers.ts`, `api/runs/index.ts`뿐이다(Grep). 관리 화면의 페이지는 `/`, `plugins/[kind]/[name]`, `runs`, `runs/[runId]`, `settings`다(Glob). 위젯 앱의 `next.config.ts`는 `headers()`로 헤더를 내고 `basePath`가 `/widget`이다(Grep).

## 인터뷰 라운드 2 (이어서): 설정을 드는 자리와 토큰 다시 쓰기

조사 뒤 사용자의 첫째·둘째 답을 선택지로 다시 올렸다. 이 화면도 훅이 한 번 막았고 위의 다시 대 본 것을 확인한 뒤 같은 글로 올렸다.

> 질문: 사이트마다의 위젯 설정(로그인 주소, 로그아웃 주소, 고지 글과 전문)을 어느 프로그램이 들고 있게 할까요?
>
> 사용자: "위젯 서버의 데이터베이스"

사용자가 선택지를 고르지 않고 글로 답했다. 올린 선택지는 셋이었다. "위젯 서버의 설정 파일 (Recommended)", "미리보기 페이지 설정에 더하기", "Agent OS 서버가 든다"다. 사용자의 답은 첫째 안에서 드는 프로그램(위젯 서버)은 같고 저장하는 곳이 파일이 아니라 데이터베이스다. 첫째 안의 설명: "위젯을 내주는 서버가 사이트마다의 위젯 설정을 파일로 들고, 위젯이 뜰 때 자기 서버에서 받아 옵니다. 고객사는 위젯 태그(URL 방식은 주소)에 사이트 이름 하나를 적습니다. 토큰 답에는 토큰과 그때그때 달라지는 것(보일 이름, 로그인하지 않음, 로그인 시간이 끝남, 로그인 거절, 고지를 아직 확인하지 않음)만 싣습니다. Agent OS 서버와 사이트 파일은 바뀌지 않아 'Agent OS는 위젯을 모른다'는 결정(ADR 0047)을 지킵니다. 그 결정은 위젯의 기본값을 위젯 배포의 설정 파일에 둔다고 이미 적어 두었습니다. 운영자가 화면에서 고치는 일은 계획표의 portal-admin 행(위젯 쪽 설정 화면)이 맡고, 그 화면이 생기기 전까지는 운영자가 파일을 고칩니다. 대가는 위젯 서버에 설정을 내주는 길을 새로 짓는다는 것(지금 위젯은 실행 중에 받아 오는 설정이 없습니다), 위젯 태그에 '사이트 이름' 값이 하나 는다는 것, portal-admin 행이 0.1 판을 내는 조건에 들어 있지 않아 그때까지는 화면이 없다는 것입니다." 데이터베이스는 ADR 0047 44행이 거부한 안 "위젯 전용 서버(저장소, 인증, 관리 화면)"에 닿으므로 다음 화면에서 범위와 때를 묻는다.

> 질문: 위젯이 받은 토큰을 만료 시각까지 다시 쓰게 할까요, 지금처럼 질문마다 새로 받게 할까요?
>
> 사용자: "만료 전까지 다시 쓰기 (Recommended)" — 설명: 위젯이 토큰 안의 만료 시각을 읽어, 끝나기 전까지는 같은 토큰으로 질문을 보내고 끝나면 새로 묻습니다. 토큰은 위젯의 메모리에만 두고 브라우저 저장소에는 쓰지 않습니다. 사람이 다른 창에 다녀왔을 때와 위젯의 로그인 단추나 로그아웃 단추를 누른 뒤에는 만료 전이라도 새로 묻습니다. 고객사 서버에 묻는 횟수가 줄고, URL 방식에서는 창을 연 페이지가 닫혀도 토큰이 끝날 때까지(최대 10분) 질문할 수 있습니다. 끝난 뒤에는 '이 창을 연 페이지에서 다시 열어 주세요' 한 문장을 보이고 입력을 막습니다. 대가는 고객사 페이지에서 로그아웃하거나 계정을 바꿔도 페이지가 새로 뜨지 않으면 토큰이 끝날 때까지는 위젯이 앞 사람으로 질문한다는 것입니다. 지금 규칙의 까닭 둘(토큰이 브라우저에 남지 않게 한다, 사람이 바뀐 것을 질문마다 알아챈다. 위젯 명세)이 토큰 수명 안에서는 느슨해집니다.

이 답은 라운드 2 첫 화면의 둘째 질문(창을 연 페이지가 닫혔을 때)도 함께 정한다. 그리고 ADR 0024 29행 "서명 토큰은 사이트가 준 손잡이로 요청할 때마다 새로 받는다"와 ADR 0059 결정 "화면"의 "위젯이 질문마다 토큰을 새로 받으므로"를 바꾼다.

## 인터뷰 라운드 3: 데이터베이스의 때, 설정의 범위, 기능 행

"위젯 서버의 데이터베이스"에 붙는 사실을 대 봤다. `docs/constitution/tech.md`에 데이터베이스를 가리키는 말(SQLite, Postgres, 데이터베이스, DB)이 0건이다(Grep). `docs/PRD.md` 25행은 멀티테넌시를 미룬 것으로 적었다. `.scratch/plan.md` 69행에서 pilot-release가 기다리는 행은 answer-eval, deploy-package, answer-markdown, admin-login, step-up-login이고 portal-admin은 없다. 66행과 71행에서 deploy-package와 step-up-login이 portal-login을 기다린다. 화면은 훅이 한 번 막았고 같은 글로 다시 올렸다.

> 질문: 위젯 설정을 담을 데이터베이스와 등록 화면은 언제 지을까요?
>
> 사용자: "0.1 판에 넣기" — 설명: 데이터베이스와 관리 화면을 0.1 판을 내는 조건에 넣습니다. 0.1 판부터 운영자가 화면에서 등록합니다. 대가는 0.1 판 전에 정하고 지을 것이 는다는 것입니다. 이 저장소에는 지금 데이터베이스가 없어(기술 스택 문서에 없고 Agent OS 서버는 파일에 저장합니다) 종류를 고르는 결정이 필요하고, 관리 화면을 누가 쓸 수 있는지(로그인), 백업과 복원, 한 번에 띄우는 배포 꾸러미에 넣는 일이 함께 붙습니다. 이 일들이 0.1 판을 내는 길에 더해집니다.

추천("0.1 판 뒤, 그때까지 파일")과 다른 안이다. 고르지 않은 추천안의 설명: "이번 설계는 방향을 정합니다. 사이트마다의 위젯 설정은 위젯 서버가 데이터베이스에 들고, 운영자가 위젯 쪽 관리 화면에서 등록하며, 위젯은 뜰 때 사이트 이름으로 받아 옵니다. 데이터베이스와 관리 화면은 한 묶음으로 계획표의 portal-admin 행(지금도 0.1 판을 내는 조건이 아닙니다)이 짓고, 데이터베이스의 종류와 관리 화면의 로그인과 백업은 그 행의 설계 인터뷰가 정합니다. 0.1 판에서는 위젯 서버가 같은 내용을 설정 파일에서 읽고 운영자가 파일을 고칩니다. 위젯이 설정을 받아 오는 약속은 저장하는 곳과 무관하게 같아, 나중에 데이터베이스로 옮겨도 고객사 페이지와 위젯은 바뀌지 않습니다. 대가는 0.1 판에 등록 화면이 없다는 것, 파일에서 데이터베이스로 옮기는 일이 나중에 한 번 든다는 것입니다."

> 질문: 위젯 태그에 지금 적는 다섯 값(에이전트 이름, 위쪽 이름, 소개, 색, 밝기)도 위젯 설정에 등록하게 할까요?
>
> 사용자: "모두 설정으로 하는데 더 많이 커스텀할 수 있었으면 좋겠어.
> 챗봇 이름, 챗봇 아이콘 업로드, url은 파비콘 업로드, 배경 이미지 업로드 또는 배경색 변경할 수 있는 컬러팔레트, 인풋창 플레이스홀더 문구, 고지 문구 등 더 있으면 추천해주고 만료 알림의 모양 같은 것도 선택할 수 있도록"

사용자가 추천안 "모두 설정으로 (Recommended)"의 방향을 받고 맞춤 칸을 넓혀 달라고 글로 답했다. 추천안의 설명: "위쪽 이름, 소개 한 줄, 색, 밝기, 에이전트 이름도 위젯 설정에 등록합니다. 고객사는 위젯 태그(URL 방식은 주소)에 사이트 이름 하나만 적으면 됩니다. 태그에 값을 따로 적으면 그 값이 등록한 설정보다 앞서므로, 지금처럼 태그에 다섯 값을 적는 사이트는 그대로 동작합니다. 미리보기 페이지 설정이 사이트마다 이미 들고 있는 그 다섯 값도 위젯 설정 한 곳으로 모입니다. 대가는 사이트 이름 없이 태그만 적은 위젯에는 로그인 단추와 고지가 나오지 않는다는 것(로그인 주소와 고지 글은 설정에만 있습니다), 같은 값을 두 곳에 적을 수 있어 어느 쪽이 앞서는지를 문서에 적어야 한다는 것입니다." 사용자의 말 "챗봇"은 용어집의 피할 말이라 ADR과 명세에서는 위젯으로 적는다.

> 질문: 이번 설계로 일이 커졌습니다. 기능 계획표의 행을 어떻게 나눌까요?
>
> 사용자: "위젯 행을 새로 세우기 (Recommended)" — 설명: 새 행 하나가 위젯 쪽 일 전부를 맡습니다. 로그인 상태 줄, 로그인 시간이 끝났을 때의 상자, 로그인 거절 알림, 고지 줄과 덮개, 다크 모드 스위치, 새 창 로그인, URL 방식, 토큰 다시 쓰기, 위젯 서버에서 설정 받아 오기, 그리고 미리보기 페이지가 그 약속을 따르게 옮기는 일입니다. 익명 사이트만으로 끝까지 시험할 수 있습니다. portal-login은 그 뒤에 서서 사내 로그인(OIDC)만 맡습니다. 행마다 명세와 리뷰가 작아집니다. 대가는 0.1 판까지의 길에 행이 하나 늘고 portal-login이 그 행을 기다린다는 것입니다(step-up-login과 deploy-package는 지금도 portal-login을 기다립니다).

## 인터뷰 라운드 4: 남은 결정을 정할 자리와 0.1 판의 맞춤 범위

라운드 3의 답 둘("0.1 판에 넣기", 맞춤 확대)에 닿는 앞선 결정을 원문으로 봤다.

- **위젯 앱의 서버 코드 금지.** ADR 0024 21행 "헤더만 내는 Next proxy를 ADR 0019의 서버 파일 금지에서 예외로 두는 안은, 금지한 서버 파일이 생겨 거부했다.", 38행 "워크스페이스는 Next의 서버 파일을 금지하므로 헤더는 `next.config`가 낸다.", 39행 "API를 부르는 서버 코드를 두지 않는다는 ADR 0019의 규칙은 ESLint 판정 그대로 위젯에도 걸린다."를 읽었다. 그래서 데이터베이스를 읽고 관리 화면을 내는 서버를 위젯의 Next 앱 안에 두려면 그 금지를 다시 열어야 한다. 위젯이 실행 중에 값을 읽는 실험 판(`.scratch/release-image/probes/widget_runtime/README.md`)은 `proxy.ts`와 `app/config/route.ts`를 새로 더한 것이다.
- **두 행의 자리.** `.scratch/portal-admin/plan.md`와 `.scratch/widget-appearance/plan.md`는 둘 다 "슬라이스 10은 ADR 0050 승인 화면에서 사용자가 골랐다(제품 1.0 묶음. 0.1 판에는 들지 않는다)"고 적었다. portal-admin은 화면을 위젯 미리보기 페이지 쪽에 두고 위젯 미리보기 페이지 설정 파일을 원천으로 삼기로 했고, 누가 그 화면에 들어오는지(운영자를 가르는 인증)를 설계 인터뷰로 넘겼다.
- **디자인 시스템.** `.claude/rules/web-design.md` 13행은 디자인 토큰에 없는 클래스와 여덟 벌(테마 넷 × 모드 둘)의 명암비를 스토리 테스트가 판정한다고 적었고, 23행은 테마마다의 색을 두지 않는다고 적었다. 자유 배경색과 배경 이미지는 이 판정 밖이다.
- **지금 고정된 글.** 입력창 안내 문구는 `web/apps/widget/components/organisms/Composer.tsx` 174행의 "무엇을 도와드릴까요?"다.

사용자가 "더 있으면 추천해주고"라고 해서 맞춤 항목 후보를 본문에 냈다. 글(위젯 이름, 소개 한 줄, 입력창 안내 문구, 고지 짧은 줄과 전문, 로그인 단추 문구, 첫 화면의 예시 질문, URL 방식 창의 탭 제목, 문의나 신고 링크), 그림(위젯 아이콘, URL 방식 창의 파비콘, 배경 이미지), 색과 모양(색 테마, 처음 밝기, 배경색, 로그인 시간이 끝났을 때 알림의 모양), 동작(로그인 주소와 로그아웃 주소, 다크 모드 스위치를 보일지)이다. 제안일 뿐이고 목록은 아래 첫 답대로 새 행의 설계 인터뷰가 정한다. 다크 모드 스위치를 보일지는 라운드 1의 "늘 사람이 고르기"와 부딪히므로 그 인터뷰가 다시 묻는다.

화면은 훅이 한 번 막았고 같은 글로 다시 올렸다.

> 질문: 설정을 저장하고 관리 화면을 내는 서버에 관한 남은 결정(서버를 어디에 세울지, 데이터베이스의 종류, 관리 화면의 로그인, 맞춤 항목의 목록)은 어디서 정할까요?
>
> 사용자: "새 행의 설계 인터뷰에서 (Recommended)" — 설명: 이번 인터뷰는 위젯이 그리는 것과 위젯의 약속(사이트 이름으로 설정을 받아 온다, 토큰 답에 싣는 것, 새 창 로그인, URL 방식, 토큰 다시 쓰기)까지 정하고 ADR 하나로 닫습니다. 그 ADR에는 방향도 적습니다. 사이트마다의 위젯 설정은 위젯 쪽 서버가 데이터베이스에 들고, 운영자가 관리 화면에서 등록하며, 0.1 판에 넣는다는 것입니다. 서버를 어디에 세울지, 데이터베이스의 종류, 관리 화면의 로그인, 맞춤 항목의 목록은 '위젯 설정 관리' 행(portal-admin 행을 고쳐 세웁니다)의 설계 인터뷰가 다음 세션에서 사실을 재며 정합니다. 까닭은 재 볼 것이 많기 때문입니다. 위젯 앱에는 지금 서버 코드를 둘 수 없어 서버의 자리부터 골라야 하고, 데이터베이스는 이 저장소에 처음입니다. 대가는 설정 서버의 모양이 다음 세션까지 정해지지 않는다는 것, 위젯이 설정을 받아 오는 주소와 답의 모양은 그 행의 설계가 선 뒤에야 굳는다는 것입니다.

> 질문: 0.1 판의 관리 화면에서 맞출 수 있는 항목은 어디까지로 할까요?
>
> 사용자: "글과 고르는 값 먼저 (Recommended)" — 설명: 0.1 판에서는 글(위젯 이름, 소개 한 줄, 입력창 안내 문구, 고지 짧은 줄과 전문, 로그인 주소와 로그아웃 주소)과 고르는 값(색 테마 넷 가운데 하나, 처음 밝기, 로그인 시간이 끝났을 때 알림의 모양)을 등록합니다. 그림 올리기(위젯 아이콘, URL 방식 창의 파비콘, 배경 이미지)와 자유 색(컬러 팔레트)은 계획표의 widget-appearance 행이 맡아 0.1 판 뒤에 더합니다. 까닭은 둘입니다. 그림 올리기는 파일을 저장하고 검사하는 일(형식, 크기, 그림 파일에 숨은 스크립트)이 따로 듭니다(어림, 재지 않았습니다). 자유 색과 배경 이미지는 지금 디자인 시스템이 테스트로 보장하는 글자 대비(색 테마 넷과 밝기 둘의 여덟 벌)를 벗어나 따로 설계가 필요합니다. 대가는 0.1 판에서는 아이콘과 배경을 바꾸지 못한다는 것입니다.

## 인터뷰 라운드 5: 로그아웃 단추

라운드 2의 "모든 방식에서 새 창"은 '로그인하고 질문하기'와 '다시 로그인'만 다뤘고, 라운드 1의 "위젯이 든 창을 로그인 주소나 로그아웃 주소로 보낸다" 가운데 로그아웃 쪽이 남아 있어 따로 물었다. 화면은 훅이 한 번 막았고 같은 글로 다시 올렸다. 로그아웃 뒤 위젯이 저장한 대화를 지운다는 것은 ADR 0059 19행에서 읽었다.

> 질문: 위젯의 '로그아웃' 단추를 누르면 어떻게 동작하게 할까요?
>
> 사용자: "로그아웃도 새 창 (Recommended).
> 근데 로그아웃은 그냥 API 호출하고 끝나는거 아니야?"

사용자가 추천안을 고르면서 글로 되물었다. 고른 선택지의 설명: "로그인과 같은 규칙을 씁니다. 로그아웃 주소가 새 창으로 열리고(휴대폰에서는 새 탭), 사람이 위젯이 든 창으로 돌아오면 위젯이 토큰을 다시 물어 로그아웃된 것을 알아챕니다. 페이지 안 방식, iframe 방식, URL 방식이 모두 같은 동작입니다. 로그아웃 주소를 등록하지 않은 사이트의 위젯에는 로그아웃 단추를 그리지 않는다는 라운드 1의 결정은 그대로입니다. 대가는 로그아웃 한 번에 창이 하나 열린다는 것입니다(미리보기 페이지의 로그아웃은 끝나면 창이 스스로 닫히게 지을 수 있지만 고객사의 로그아웃 페이지는 고객사 몫입니다). 로그아웃하면 위젯이 사람이 바뀐 것을 보고 저장한 대화를 지우는 것은 지금 위젯의 동작 그대로입니다." 되물음이 창 없이 끝내는 길을 가리키므로 그 길을 선택지로 다시 올린다.

다시 올리기 전에 대 본 것: 위젯 미리보기 페이지의 쿠키는 `SameSite=Strict`이고(`web/apps/portal/server/anonymous-cookie.ts` 35행), `web/apps/portal/server/handler.ts` 243행의 주석이 "쿠키가 `SameSite=Strict` 라 다른 사이트에서 일으킨 요청에는 쿠키가 실리지 않는다"고 적었다(Grep). 이 화면도 훅이 한 번 막았다.

> 질문: 로그아웃을 창 없이 끝내는 방식으로 바꿀까요?
>
> 사용자: "로그아웃 API 주소를 위젯 설정에서 받는데 로그아웃 해달라고 알려? 그냥 API 호출하면 되는거 아니야?"

사용자가 두 선택지를 고르지 않고 다시 되물었다. 올린 선택지는 "사이트에 부탁하고 끝 (Recommended)"(위젯이 토큰을 묻는 통로로 사이트에 로그아웃을 부탁하고 사이트가 자기 서버를 부른다)과 "새 창 그대로"였다. 사용자의 뜻은 위젯 설정에 등록한 로그아웃 API 주소를 위젯이 직접 부르는 것이다. 직접 부르기가 통하는 범위(브라우저가 로그인 쿠키를 싣는 경우)를 구체적인 장면으로 풀어 다시 묻는다.

셋째 화면을 올리기 전에 대 본 것: 로그아웃 방식이 항목마다 둘(로그인 쿠키만 지우기, 로그인 서버에서도 함께 로그아웃하기)이라는 것은 ADR 0059 19행에서 읽었다. 위젯 미리보기 페이지가 페이지 안 방식이라는 것은 `web/apps/portal/browser/portal.ts` 364행(`document.createElement("agent-os-widget")`)에서, 그 페이지가 자기 끝점을 `credentials: "same-origin"`으로 부른다는 것은 153·170·188행에서 읽었다. 다른 주소에서 연 문서의 요청에 로그인 쿠키가 실리는 조건(같은 도메인 아래이고 API가 위젯 주소를 허용한다, 다른 도메인이면 쿠키를 열어야 한다)과, 로그인 서버에서도 함께 로그아웃하려면 창이 로그인 서버 주소로 이동해야 한다는 것은 쿠키와 OIDC 규격으로 아는 것이고 재 보지 않았다(어림). 본문에는 방식마다 직접 부르기가 통하는지를 표로 풀었다. 이 화면도 훅이 한 번 막았고 같은 글로 다시 올렸다.

> 질문: 위젯의 '로그아웃' 단추는 등록된 로그아웃 주소를 어떻게 부르게 할까요?
>
> 사용자: "직접 부르기, 새 창도 선택 (Recommended)" — 설명: 위젯 설정에 로그아웃 주소와 함께 '부르는 방법'을 고르는 칸을 둡니다. 기본은 '창 없이 부르기'입니다. 위젯이 그 주소를 쿠키와 함께 직접 부른 뒤 토큰을 다시 물어 로그아웃된 화면으로 바뀌고, 다시 물었는데 여전히 로그인 상태이면 '로그아웃하지 못했습니다' 알림을 보입니다. 직접 부르기가 통하지 않는 사이트(위젯과 다른 도메인에 있는 iframe·URL 방식, 로그인 서버에서도 함께 로그아웃하는 사이트)는 운영자가 '새 창으로 열기'를 고르고, 그때는 로그인과 같은 규칙(새 창이 열리고, 돌아오면 토큰을 다시 묻기)입니다. 위젯 미리보기 페이지는 페이지 안 방식이라 기본값으로 통합니다. 로그아웃 주소를 등록하지 않으면 단추를 그리지 않는 것은 그대로입니다. 대가는 설정 칸 하나와, 지어서 시험할 길이 둘이라는 것입니다. 통하는 조건은 쿠키 규격으로 아는 것이고 재 보지 않았습니다(어림).

고르지 않은 선택지는 "직접 부르기만"(창 없이 부르는 길 하나. 다른 도메인의 iframe·URL 방식 사이트는 쿠키와 API를 위젯 주소에 열거나 단추를 숨기고, 로그인 서버에서도 함께 로그아웃하는 방식은 위젯의 단추로 쓸 수 없게 된다)과 "사이트에 부탁하고 끝"(앞 화면의 안)이다. 이 답으로 라운드 5 첫 화면의 "로그아웃도 새 창"은 '부르는 방법'의 한 값으로 남고, 기본값은 창 없이 부르기가 된다. 로그아웃이 정해져 frontier가 비었다. 결정이 에이전트의 절차(스킬, 훅, 브랜치와 병합의 규약)를 바꾸지 않아 중간으로 들어오는 갈래를 밟는 단계는 해당하지 않는다. 다음은 합의 요약을 올려 확인받는 것이다.

## 합의 요약

요약을 쓰기 전에 일지의 라운드 1~5와 ADR 0060 전문, `CONTEXT.md` 111~189행을 다시 읽었다. 요약은 본문에 올렸고 아래에 글자 그대로 옮긴다. "(새로 확인)"은 사용자가 고른 설명에 없던 것을 세션이 답들을 이으며 채운 항목이다. 화면은 훅이 한 번 막았고(수가 든 문장 "일곱 묶음", "ADR 0061"), 묶음이 일곱인 것과 `docs/adr`의 가장 큰 번호가 0060인 것(Glob), `uv run python tools/sibling_overlap.py`의 "번호 겹침 없음"을 본 뒤 같은 글로 다시 올렸다. 그 도구의 출력에서 `origin/dev`가 `30dd409`로 움직인 것을 봤다.

> **1. 위젯이 직접 그리는 것** (지금은 위젯 미리보기 페이지가 그리고 있습니다)
>
> - **로그인 상태.** 로그인 전에는 '로그인하고 질문하기' 단추, 로그인 뒤에는 이름 줄과 '로그아웃' 단추를 그립니다. 로그인 시간이 끝나면 "로그인 시간이 끝났습니다"와 '다시 로그인'을 보이고, 로그인이 거절되면 사이트가 준 한 문장을 알림으로 보입니다.
> - **고지.** 입력창 아래의 짧은 줄과 '고지 전문' 펼침을 그리고, 아직 확인하지 않은 브라우저에는 위젯 상자를 덮는 덮개와 '확인하고 질문하기' 단추를 그립니다.
> - **다크 모드 스위치.** 모든 위젯에 보이고, 고른 값은 브라우저에 계속 기억합니다. 사이트가 정한 밝기는 처음 값일 뿐입니다. 미리보기 페이지 위쪽 띠의 스위치는 없앱니다.
>
> **2. 위젯과 사이트 사이의 약속**
>
> - **토큰 답.** 사이트는 지금처럼 토큰 글자만 답해도 되고, 토큰과 보일 이름을 함께 답하거나, 토큰 대신 상태(로그인하지 않음, 로그인 시간이 끝남, 로그인이 거절됨과 그 문장, 고지를 아직 확인하지 않음)를 답합니다. 이름은 화면에만 쓰이고 토큰에는 싣지 않습니다.
> - **(새로 확인)** 이름 없이 로그인된 토큰만 온 경우에는 "로그인됨"이라고 보입니다.
> - **(새로 확인)** 위젯이 사이트에 알릴 것('고지를 확인했다', '로그인 없이 계속')은 토큰을 묻는 같은 통로에 실어 보냅니다. 정확한 모양은 명세가 짓습니다.
> - **(새로 확인)** '로그인 시간이 끝남' 답에는 익명으로 계속할 수 있는 사이트인지가 함께 오고, 사람이 '로그인 없이 계속'을 누른 뒤에만 익명으로 바뀝니다. 지난 인터뷰(ADR 0059)의 조건을 그대로 지킵니다.
> - **(새로 확인)** 위젯에는 "익명만, 로그인만, 둘 다"를 고르는 칸을 따로 두지 않습니다. 설정에 로그인 주소가 없으면 로그인 단추가 없고, 로그인 주소가 있는데 사이트가 '로그인하지 않음'이라고 답하면 로그인 단추만 보이며, 로그인 주소가 있고 사이트가 익명 토큰을 주면 질문도 할 수 있고 로그인 단추도 보입니다.
> - **토큰 다시 쓰기.** 받은 토큰은 위젯의 메모리에만 두고 만료 시각까지 다시 씁니다. 만료된 뒤, 사람이 다른 창에 다녀왔을 때, 로그인이나 로그아웃 단추를 누른 뒤에는 새로 묻습니다.
> - **로그인.** 세 방식 모두 로그인 주소를 새 창(휴대폰은 새 탭)으로 열고, 사람이 돌아오면 위젯이 토큰을 다시 묻습니다.
> - **로그아웃.** 기본은 위젯이 등록된 로그아웃 주소를 창 없이 직접 부르는 것이고, 통하지 않는 사이트는 운영자가 설정에서 '새 창으로 열기'를 고릅니다. 로그아웃 주소가 없으면 단추를 그리지 않습니다.
>
> **3. URL 방식** (주소 하나를 팝업으로 열면 창 전체가 위젯)
>
> - 위젯 서버의 위젯 주소에 사이트 이름을 붙인 주소를 사이트의 페이지가 팝업으로 엽니다. 팝업은 자기를 연 페이지에 토큰을 묻습니다.
> - **(새로 확인)** 묻고 답하는 메시지는 iframe 방식과 같은 것을 쓰고, 허용 목록에 있는 주소에서 온 답만 받습니다.
> - 연 페이지가 닫혀도 토큰이 끝날 때까지(최대 10분) 질문할 수 있고, 끝나면 '이 창을 연 페이지에서 다시 열어 주세요'를 보이고 입력을 막습니다. **(새로 확인)** 주소를 직접 열어서 연 페이지가 처음부터 없을 때도 같은 문장을 보입니다.
>
> **4. 위젯 설정**
>
> - 사이트마다의 값을 위젯 쪽 서버가 데이터베이스에 들고, 운영자가 관리 화면에서 등록하며, 0.1 판에 넣습니다.
> - 위젯은 태그(URL 방식은 주소)에 적힌 사이트 이름으로, 뜰 때 설정을 받아 옵니다. 태그에 따로 적은 값은 설정보다 앞섭니다. 사이트 이름을 적지 않은 위젯은 지금과 똑같이 동작합니다(로그인 단추와 고지가 없습니다).
> - 0.1 판에서 등록하는 것은 글(위젯 이름, 소개, 입력창 안내 문구, 고지 짧은 줄과 전문, 로그인 주소, 로그아웃 주소)과 고르는 값(에이전트, 색 테마 넷, 처음 밝기, 만료 알림의 모양, 로그아웃을 부르는 방법)입니다. 그림 올리기와 자유 색은 0.1 판 뒤입니다.
> - Agent OS 서버와 사이트 파일은 바뀌지 않습니다. 다만 예전 결정(ADR 0047)이 "저장할 값이 몇 개뿐이라 서버를 하나 더 둘 이유가 없다"며 거부했던 '위젯 전용 서버(저장소, 관리 화면)'를 이번에 다시 열어 받아들이게 됩니다.
> - 다음 설계 인터뷰로 넘기는 것: 서버를 세울 자리, 데이터베이스 종류, 관리 화면의 로그인, 맞춤 항목 목록, 백업, 배포 꾸러미에 넣는 일. **(새로 확인)** 여기에 셋을 더 넘깁니다. 미리보기 페이지 설정 파일이 지금 들고 있는 값(이름, 소개, 색, 밝기, 고지)을 위젯 설정으로 옮기는 방법과 처음 띄웠을 때의 값, 미리보기 페이지가 고지 전문에 늘 넣던 두 문장(익명 식별자를 둔다, 로그인한 계정과 함께 기록된다)을 누가 보장하는지, 다크 모드 스위치를 숨기는 설정을 둘지입니다.
>
> **5. 위젯 미리보기 페이지에 남는 것**
>
> - 사이트 고르기, 보고서 링크, 토큰 발급, 고지 확인의 기록, 사내 로그인 끝점이 남습니다. 띠의 스위치, 고지 덮개와 짧은 줄, 로그인 단추 줄은 위젯으로 옮겨 갑니다.
>
> **6. 기능 행**
>
> - 새 행 `widget-login-state`: 위 1~3과 설정 받아 오기, 미리보기 페이지를 새 약속으로 옮기는 일을 맡습니다.
> - `portal-admin` 행: '위젯 설정 관리'(데이터베이스와 관리 화면)로 고쳐 세우고 0.1 판 조건에 넣습니다. 폴더 이름은 다른 문서들이 가리키고 있어 그대로 둡니다.
> - **(새로 확인)** 순서는 위젯 설정 관리 → `widget-login-state` → `portal-login`(사내 로그인만) → `step-up-login` → 0.1 판입니다. 위젯이 설정을 받아 오는 주소와 답의 모양이 설정 관리 행에서 정해지기 때문입니다.
> - `widget-appearance` 행: 그림 올리기와 자유 색을 맡고 0.1 판 뒤입니다.
> - 다음 세션: 위젯 설정 관리 행의 설계 인터뷰입니다. `widget-login-state`의 화면 그리기는 그것과 나란히 할 수 있습니다.
>
> **7. 문서**
>
> - 새 ADR 0061 하나에 적고, 이번 결정으로 문장이 바뀌는 앞선 ADR 다섯(0024, 0047, 0050, 0059, 0060)에는 "바뀜" 표시를 답니다.
> - 용어집에 "위젯 설정"을 새 용어로 올립니다(지금은 피할 말로 적혀 있습니다). 문서에서는 용어집대로 "고객사"를 사이트로, "챗봇"을 위젯으로 적습니다.

> 질문: 위 합의 요약대로 ADR과 기능 계획을 써도 될까요?
>
> 사용자: "요약대로 쓰기 (Recommended)" — 설명: 요약의 일곱 묶음을 ADR 0061 초안과 기능 계획에 옮깁니다. '새로 확인'이라고 표시한 항목도 요약에 적힌 대로 정해집니다. ADR 초안은 셀프 리뷰를 거친 뒤 다시 보여 드리고 승인을 받습니다.

이것으로 설계 인터뷰를 닫는다. 다음은 용어집과 ADR 0061 초안, 앞선 ADR의 포인터, 기능 계획이다.

## 문서 작성

기준 브랜치가 움직여 `origin/dev`를 합쳤다(1117a170f에서 30dd4096f로, fast-forward). 이 브랜치에 커밋이 없어 병합 커밋은 생기지 않았다.

- **용어집.** `CONTEXT.md`에 위젯 설정(Widget Settings)을 더했다. 그 말은 사이트 파일과 위젯 미리보기 페이지 설정의 피할 말이었으므로, 두 항목의 피할 말을 "따로 있는 용어다"로 고쳤다.
- **ADR 0061 초안.** `docs/adr/0061-widget-draws-login-state-notice-and-dark-mode-switch-and-reads-per-site-widget-settings-from-a-widget-side-server.md`. 결정 열일곱 갈래, 고르지 않은 안 열일곱, Consequences 열둘이다. 인터뷰의 "고객사"와 "챗봇"은 용어집의 "사이트"와 "위젯"으로 옮겨 적었다.
- **조사: 앞선 ADR에서 이 결정이 바꾸는 문장.** 서브에이전트가 ADR 0023·0024·0026·0046·0047·0050·0056·0059·0060의 본문을 읽고 보고했다(근거의 종류: 문서를 읽었다. 줄 번호와 문장을 함께 받았다). 보고가 짚은 문장은 포인터를 달기 전에 본 세션이 그 줄을 Read로 다시 읽어 확인했다. 보고가 초안에서 어긋난다고 짚은 것은 다섯이고 모두 고쳤다.
  1. 초안의 "다른 ADR" 목록에 빠진 자리(ADR 0047의 둘째 문장과 Consequences, ADR 0050의 토큰 문장, ADR 0060 Consequences의 넷째 자리)를 목록에 넣었다.
  2. 같은 목록의 "ADR 0024의 위젯이 받는 값과 저장소에 관한 문장"을 지웠다. ADR 0024 본문에는 받는 값을 적은 문장이 없고, 탭 저장소 문장은 여전히 참이다.
  3. 초안 머리 문단이 다크 모드 스위치를 ADR 0050과 ADR 0059가 정했다고 적은 것을 고쳤다. 띠의 스위치는 pilot-portal 명세가 둔 것이다(`.scratch/pilot-portal/spec.md`의 7·11·37행을 Grep으로 봤다).
  4. 탭 저장소를 재기로 한 자리의 인용을 "ADR 0059 Consequences"에서 "ADR 0059 결정 "시험""으로 고쳤다.
  5. ADR 0026의 2026-10-06 이력이 위젯의 모드를 사이트가 넘긴다고 정하고 "최종 사용자도 위젯에서 고른다"를 거부했는데 초안이 그 ADR을 이르지 않았다. 그 이력의 115·139행을 읽어 확인하고, 초안의 결정 "다크 모드 스위치"에 그 안을 모드에 한해 다시 열었다고 적었다. 이력 항목은 기록이라 포인터는 달지 않았다.
- **보고에 없던 것 하나를 더했다.** 위젯 미리보기 페이지의 토큰 수명 120초(ADR 0050 결정 "토큰")는 위젯이 요청마다 토큰을 받는다는 전제로 고른 값이다. 다시 쓰기에서는 그 수명이 위젯이 다시 묻는 간격이 되므로 widget-login-state의 명세가 다시 본다고 초안의 Consequences "신뢰와 노출"에 적었다.
- **포인터 `(바뀜: ADR 0061)` 스물셋.** ADR 0024에 둘(임베드 방식이 둘이라는 문장, 요청마다 토큰을 새로 받는다는 문장), ADR 0047에 둘(결정의 임베드 옵션과 맞춤 설정 화면 묶음, Consequences "두 자리의 설정"), ADR 0050에 여섯(토큰 문장, 고지 확인 덮개, 짧은 고지, 로그인 사이트의 알림과 비활성 단추, "위젯은 바뀌지 않는다", 새 행 둘의 자리), ADR 0059에 다섯(같은 탭의 로그인, 로그인 전의 단추, 만료가 드러나는 때, 화면을 페이지가 그린다는 묶음, 탭 저장소를 재는 e2e), ADR 0060에 여덟(머리 문단의 통로 문장과 계약 자리의 셈, 결정 "위젯의 안내와 로그인 통로"의 두 묶음, 같은 탭의 이동을 전제로 한 다시 보내기, 결정 "시험과 수락"의 탭 저장소 묶음, Consequences의 넷째 자리, 명세가 짓는 것)이다. 본문의 다른 글자는 고치지 않았다. `uv run python tools/check_adr_pointers.py`가 출력 없이 끝났다.
- **ADR 0046 이력.** `### 2026-11-14 위젯 설정 관리와 위젯이 그리는 로그인 상태가 기준선의 행이 된다`를 쌓았다. 기준선 표에 두 줄(portal-admin, widget-login-state)이 늘고, Blocked by와 계약의 바뀜을 적었다. 본문에는 이 이력이 거짓으로 만드는 문장이 없어 포인터를 달지 않았다(표에 줄이 더해질 뿐이다).
- **색인.** `docs/adr/README.md`에 0061 행을 더했다.
- **기능 계획.** widget-login-state를 새로 썼다(슬라이스 9, portal-admin을 기다린다, `**설계:** ADR 0061`). portal-admin을 '위젯 설정 관리'로 고쳐 썼다(슬라이스 10에서 9로, 설계 줄은 없다. 다음 세션의 설계 인터뷰가 맡는다). portal-login은 widget-login-state를 기다리게 하고 설계 줄에 ADR 0061을 더했다. widget-appearance는 그림 올리기와 자유 색을 맡는 0.1 판 뒤의 행으로 고쳐 썼다(portal-admin, widget-login-state, pilot-release를 기다린다). step-up-login은 설계 줄에 ADR 0061을 더하고 로그인 통로와 탭 저장소 측정이 빠진 것을 적었다. pilot-release는 portal-admin을 직접 기다리게 했다. `uv run python tools/plan_table.py`로 `.scratch/plan.md`를 다시 만들었다.
- **건드리지 않은 것.** release-image, deploy-package, ops-backup-upgrade의 기능 계획은 다른 세션이 고치고 있을 수 있어 건드리지 않았다(`release-image-tickets` 워크트리의 PR #569가 열려 있다). 위젯 쪽 서버와 데이터베이스가 그 세 행에 미치는 것은 portal-admin 계획의 설계 인터뷰 항목으로 적었다.
- **겹침 확인.** `uv run python tools/sibling_overlap.py`가 "번호 겹침 없음"을 냈다. 함께 고친 파일은 `.scratch/plan.md` 하나이고(워크트리 `mcp-shutdown-spec`) 도구가 만드는 파일이라 병합 때 다시 만든다.

## 인계

경계는 `셀프 리뷰 직전`이다. 셀프 리뷰를 하려고 `code-review` 스킬을 부른 직후 인계 계기(`hook_handoff`. 세션 컨텍스트 238,093 토큰)가 왔고, 그 스킬의 단계는 하나도 밟지 않았다. 넘기지 않는 때 다섯을 봤다. 계기를 낸 호출은 실패하지 않았고, 요청 범위는 PR과 병합까지이며, 이 세션의 지시문은 인계로 시작하지 않고, 일지에 `인계 못함` 줄이 없으며(Grep 0건), `get_session`의 `self`에 `parentSessionId`가 없다. 그래서 넘긴다. 이 세션의 바꾸기 전 제목은 `docs/widget-login-state-design`이다. 이 브랜치에 열린 PR은 없다(`gh pr list --head`가 빈 목록을 냈다). 변경은 모두 커밋하지 않은 채 워크트리에 있다.

이 세션이 번복하거나 고친 것은 아래다.

- 로그인: 첫 라운드에서 고른 "위젯이 든 창을 로그인 주소로 보낸다"를 사용자의 말로 새 창으로 바꿨다(라운드 2).
- 로그아웃: 세션의 추천 둘(새 창만, 사이트의 페이지에 부탁)을 사용자가 받지 않아 "직접 부르기, 새 창도 선택"으로 바꿔 올렸고 그것을 골랐다(라운드 5).
- ADR 0061 초안의 사실 오류 다섯을 서브에이전트의 보고로 고쳤다("문서 작성"의 조사 항목).
- ADR 0061 초안의 "다른 행"이 pilot-release는 step-up-login을 거쳐 새 행들을 기다린다고 적었던 것을, portal-admin은 pilot-release가 직접 기다리는 것으로 고쳤다. 기준선의 행이 될 때마다 pilot-release에 직접 더한 앞선 이력들(2026-11-10, 2026-11-11, 2026-11-12)과 같은 꼴이다. widget-login-state는 portal-login과 step-up-login을 거쳐 막으므로 더하지 않았다.

9. **Nit.** widget-login-state 계획이 다섯을 "명세가 재는 것"이라 적었는데 ADR 0061은 넷을 e2e 몫으로 둔다. 이 일지 "문서 작성"의 "PR #569가 열려 있다"는 지금 병합됐다.

"승인 화면에서 함께 알릴 것" 일곱의 판정: (가) 귀결이고 알림 필수(승인된 계약 문장을 뒤집고, 일지 2026-11-13-0426은 그 통로를 이미 정한 것으로 넘겼다), (나) 귀결, (다) 귀결(사실 기록. ADR 0026 쪽은 사용자가 본 적이 없다), (라) 귀결(넘김), (마) 귀결, (바) 새 판단(ADR 0056의 "사용자는 이 일을 portal-admin을 만들 때 함께 하기로 골랐다"를 묻지 않고 다시 연다), (사) 귀결(이력 안의 기한 문장은 위 2).

확인했고 어긋나지 않았다고 보고한 것: 요약 1~7의 글머리와 조건절 넷, 추천과 다른 답 다섯이 모두 고른 안으로 적힌 것, 사용자 말 인용 일곱과 머리 문단 인용, Considered Options 가운데 일지가 적은 안(11·12·16·17번은 일지가 고르지 않은 선택지를 적지 않아 대 보지 못했다), 다음 인터뷰로 넘기는 아홉 가지가 portal-admin 계획에 있는 것, 기능 계획의 세 줄과 `uv run python tools/plan_table.py --check`, ADR 0047·0059·0060·0026에서 옮긴 문장.

## ADR 0061 승인 (2026-11-15)

셀프 리뷰를 반영한 뒤 승인 화면을 올렸다. 화면 앞의 글로 보인 것은 아래다.

- **이 문서가 정하는 것 일곱.** 위젯이 직접 그리는 화면(로그인 단추, 이름 줄과 로그아웃 단추, 만료 알림, 거절 알림, 고지의 줄과 펼침과 덮개, 다크 모드 스위치), 사이트가 위젯에 알려 주는 것(토큰과 보일 이름, 또는 상태 넷. 토큰 글자만 답하는 사이트는 고치지 않아도 된다), 위젯 설정(위젯 쪽 서버의 데이터베이스, 운영자가 화면에서 등록, 0.1 판. 그림 올리기와 자유 색은 0.1 판 뒤), 토큰을 만료 시각까지 다시 쓰기, 로그인은 새 창이고 로그아웃은 창 없이 직접 부르기가 기본, URL 방식, 작업 순서(portal-admin, widget-login-state, portal-login, step-up-login, pilot-release).
- **합의 요약에 글자로 없었는데 문서를 쓰며 더한 것 일곱.** "인계"의 (가)~(사)를 쉬운 말로 옮겼다. (가) ADR 0060의 로그인 통로를 두지 않는다(이미 승인한 계약 문장을 뒤집는 것이라 가장 먼저 알렸다), (나) 로그인하고 돌아오면 표시된 질문을 한 번 다시 보낸다, (다) 예전에 거부한 안 셋(ADR 0047의 위젯 전용 서버, ADR 0059의 팝업 로그인, ADR 0026 이력의 "최종 사용자도 위젯에서 고른다")을 다시 열었다, (라) 미리보기 페이지의 토큰 수명 120초를 widget-login-state 명세가 다시 본다, (마) pilot-release가 portal-admin을 직접 기다리고 widget-appearance가 pilot-release를 기다린다, (바) portal-admin이 넘겨받은 일 넷은 이 문서가 정하지 않고 다음 설계 인터뷰가 다시 묻는다(ADR 0056에서 함께 하기로 고른 일도 그때 다시 묻는다), (사) 포인터 스물넷(ADR 0024에 셋, 0047에 둘, 0050에 여섯, 0059에 다섯, 0060에 여덟)과 ADR 0046의 이력.
- **셀프 리뷰가 찾아 알린 것 셋.** 위젯 설정은 토큰 없이 받아 오는 공개 값이라 비밀을 두지 않는다, 토큰 글자만 답하는 사이트의 위젯에는 이름 줄이 없다(이름 없이 로그인한 사람의 토큰이라고 답하면 "로그인됨"), 0.1 판 기한은 그대로 2027-03-05라고 적었다(둘째 질문으로 따로 물었다).
- **셀프 리뷰로 고친 것 다섯.** 페이지를 고치지 않는 사이트에도 달라지는 것 둘(모든 위젯에 스위치, 토큰 함수를 요청마다 부르지 않음), 대가 문장 둘(새 창을 사람이 닫고 돌아온다, 설정 칸 하나와 시험할 길 둘), ADR 0024 쿠키 문장의 범위, "위젯 설정 관리 화면"이라는 이름, 용어집 "고지"의 뜻.

**첫 시도는 pre-commit에 막혔다.** `git commit -F <메시지 파일>`을 백그라운드로 돌렸고 종료 코드 1로 끝났다. pytest만 실패했다(`2 failed, 7312 passed, 7 warnings in 1076.31s`). 실패한 둘은 앞 세션의 둘째 시도(위 "커밋")에서 실패한 것과 같은 시험이고 같은 단언이다.

인계 계기(`커밋 뒤`, 323,954 토큰)가 그 호출에 왔다. 이 세션의 지시문의 "이어받을 상태"가 `인계: 커밋 뒤`로 시작해 같은 경계이고(`handoff.md` 1의 셋째) 커밋도 실패해(첫째) 넘기지 않았다.

그 파일만 따로 돌리니 `uv run pytest tests/tools/test_rerun_runner.py -q`가 `63 passed in 184.67s`였다. 앞 세션의 두 번과 같은 꼴이다. 따로 돌리면 지나는 시험이 전체 검사 안에서만 실패했다. 실패한 때 이 PC의 부하는 보지 않았다(`ListAgents`에는 세션 시작 때 다른 세션 넷이 busy였다. 부하가 원인이라는 것은 어림이다). 이 브랜치에서 pytest를 건너뛰지 않은 커밋 시도는 셋이고 셋 다 pytest에서 막혔다(앞 세션의 둘과 이 시도).

지시문대로 사용자에게 다시 물었다. 선택 화면 앞의 글로는 실패한 검사가 pytest 하나이고 시험 둘이라는 것, 그 파일만 따로 돌리면 63개가 지난다는 것, 이 커밋이 문서 둘만 바꾼다는 것, 건너뛰지 않은 시도 셋이 모두 막혔다는 것, 푸시하면 CI가 전체 pytest를 다시 돌리고 그 초록을 본 뒤에만 병합한다는 것을 보였다. 훅이 화면을 한 번 막아 설명의 수를 원문에 댔다. 한 번에 걸린 시간을 "25~30분"으로 적었던 것을 세 시도의 값(1435.94초, 1713.44초, 이번 web-verify 1395.0초)에 맞춰 "23~29분"으로 고쳤고, CI가 PR에서 도는 것은 `.github/workflows/ci.yml`의 `on:`(`pull_request:`)과 72행 `uv run pytest -q`로, `SKIP=pytest`가 그 검사 하나만 빼는 것은 `tools/run_checks.py`의 독스트링 24행으로 봤다(Grep).

> 사용자: 남은 문서 커밋은 pytest 제외 (Recommended)

고른 선택지의 설명: "이 PR에서 파이썬 코드를 바꾸지 않는 커밋(이번 커밋과, 뒤에 올 리뷰 봇 반영·회고 일지 커밋)은 커밋 검사에서 pytest 하나만 건너뛰고 나머지 검사는 그대로 돌립니다. 전체 pytest는 PR을 연 뒤 푸시할 때마다 GitHub의 CI가 돌리고, 그 초록을 확인한 뒤에만 병합합니다. 같은 일로 다시 묻지 않습니다. 치르는 값은 이 PC에서 전체 pytest가 통과한 기록이 이 PR의 커밋에 남지 않는다는 것입니다." 고르지 않은 선택지는 "이번 커밋만 pytest 제외"(다음 커밋은 건너뛰지 않고 먼저 시도하고 막히면 다시 묻는다)와 "건너뛰지 않고 다시 시도"였다.

그래서 이 PR에서 `.py`를 바꾸지 않는 커밋은 `SKIP=pytest`로 치고, 전체 pytest의 초록은 PR의 CI(`verify`)로 확인한 뒤에만 병합한다. 이 결정은 이 PR의 문서 커밋에만 걸린다. 파이썬 코드를 바꾸는 커밋이 생기면 건너뛰지 않는다.

**둘째 시도는 지났다.** `SKIP=pytest git commit -F <메시지 파일>`을 백그라운드로 돌렸고 종료 코드 0으로 끝났다. 커밋은 `5606d61aa`(`docs: PR 직전 리뷰를 ADR 0061에 반영하고 일지를 잇는다 (widget-login-state)`)이고 파일 둘(ADR 0061과 이 일지)이다. 검사 묶음은 503.38초 걸렸다. pytest는 Skipped였고, check-ticket, lint-imports, zizmor, check-instructions, check-type-escapes, pyright(32.3초), pyright-linux(32.8초), run-hooks(46.2초), web-verify(502.8초), markdown tables, line separators, mutation tables, quotes, commit message는 Passed였다. ruff 둘과 canary specs, constitution version은 볼 파일이 없어 Skipped였다. 첫 시도에서 1395.0초 걸린 web-verify가 이번에는 502.8초였다. 무엇이 달랐는지는 보지 않았다.

## 푸시와 PR

푸시 전에 `git fetch origin`을 쳤고 기준 브랜치가 PR 둘(#571, #572)만큼 움직여 있었다(`origin/dev`가 `5b9a4f491`). `uv run python tools/sibling_overlap.py`는 "번호 겹침 없음"을 냈다. `git diff --name-only HEAD...origin/dev`가 낸 파일 열여덟과 `git diff --name-only origin/dev...HEAD`가 낸 이 브랜치의 파일 열일곱에는 같은 경로가 없다. 기준 브랜치에서 바뀐 `docs/constitution/operations.md`의 문단은 LLM 테스트가 띄우는 예시 MCP 서버의 설치이고, 이 PR이 따를 규약이 새로 서지 않았다. 그래서 다시 합치지 않고 푸시하려 했다. `sibling_overlap`의 "함께 고친 파일"에는 워크트리 `admin-login-design`이 `.scratch/plan.md`, `CONTEXT.md`, ADR 0046, `docs/adr/README.md`를 함께 고친 것으로 나왔다. 나중에 병합하는 쪽에서 글자 충돌이 날 수 있는 후보다.

**그 푸시는 훅이 막았다.** `git push -u origin docs/widget-login-state-design`을 `tools/hook_push_behind_main.py`가 거부했다. 이 브랜치가 `origin/dev`보다 2커밋 뒤처졌고, dev는 PR 전에 기준 브랜치에 맞추는 규약이라는 까닭이다. 겹치는 파일이 없으니 합치지 않아도 된다고 본 위의 판단이 그 규약과 어긋났다. 이 세션의 앞에서 같은 까닭으로 한 번 합쳤는데(위 "인계받은 세션") 둘째 때는 파일이 겹치는지만 보고 규약을 다시 대 보지 않았다.

`git merge --no-edit origin/dev`로 합쳤다. 충돌은 없었고 병합 커밋은 `6fcadc184`다(파일 열여덟, commit-msg 검사만 돌았다). 합친 뒤 `uv run python tools/plan_table.py`는 `.scratch/plan.md`를 바꾸지 않았고(`git status --short`에 이 일지만 남았다), `uv run python tools/sibling_overlap.py`는 "번호 겹침 없음"을 냈으며, `uv run python tools/check_adr_pointers.py`는 출력 없이 끝났다. `sibling_overlap`의 "함께 고친 파일"에 열린 PR #573이 `.scratch/plan.md`로 새로 나왔다.

훅이 안내한 대로 합친 결과에 검증 명령을 돌린 뒤 푸시한다. pytest는 사용자의 선택대로 PR의 CI에 맡기고 나머지를 돌린다. `SKIP=pytest uv run python tools/run_checks.py`를 백그라운드로 띄웠고, 손으로 친 `uv run ruff check .`는 `All checks passed!`를, `uv run ruff format --check .`는 `2254 files already formatted`를 냈다.

그 러너는 종료 코드 0으로 끝났다. pytest는 Skipped였고 lint-imports, check-ticket, zizmor, check-instructions, check-type-escapes, pyright-linux(34.6초), pyright(34.6초), run-hooks(46.0초), web-verify(433.5초)가 Passed였다. 끝난 뒤 `git fetch origin`을 다시 쳤고 `git log --oneline HEAD..origin/dev`가 비어 있어(기준 브랜치가 더 움직이지 않았다) 푸시했다. 이번에는 훅이 막지 않았다.

PR은 `gh pr create --base dev --head docs/widget-login-state-design …`으로 열었다.
