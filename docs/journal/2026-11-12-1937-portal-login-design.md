## 조사(첫 라운드 전)

기능 계획 `.scratch/portal-login/plan.md`와 ADR 0050의 결정·Consequences를 직접 읽었고, 서브에이전트 셋에게 사실을 맡겼다. 원본 보고는 이 세션과 함께 사라지므로 선택지에 쓴 사실만 근거의 종류와 함께 옮긴다.

질문 페이지의 지금 코드(코드를 읽었다. 괄호는 파일)

- 프레임워크 없는 `node:http` 서버 하나이고 처리기 `handle`은 동기 함수다. 요청에서 읽는 것은 메서드, 경로, 질의, 헤더, 쿠키뿐이고 본문을 읽는 코드와 밖으로 나가는 HTTP 호출이 없다(`web/apps/portal/server/handler.ts`, `serve.ts`. `fetch(`·`node:https`·`node:net`·`request.on(`으로 `server/`를 grep해 시험 파일 한 줄만 나왔다).
- 로그인 사이트는 메서드와 쿠키와 상관없이 403 "이 사이트는 로그인이 필요합니다. 로그인은 아직 제공하지 않습니다."이고(`handler.ts` 211~213행), 서버는 `both` 사이트를 익명 사이트와 똑같이 다룬다. 사이트 끝점은 `acknowledgement`와 `token` 둘뿐이다.

## 라운드 1

질문 화면은 훅이 한 번 막아, 설명에 든 수와 동작(120초와 30초, 시작 때만 읽기, 모르는 발급자 거부, 열린 스트림, 사용자 표 없음)을 코드에 다시 대 본 뒤 올렸다. OIDC 선택지의 "Keycloak, AD FS가 이 방식을 지원한다"는 일반 지식이라고 설명에 적었다.

### 로그인 방식

질문: "질문 페이지의 사내 로그인을 어떤 방식 하나로 만들까요? (0.1 판은 인터넷이 차단된 폐쇄망 서버 한 대가 목표입니다.)"

> 사용자: 회사 로그인 서버로 보내기 (Recommended), 아이디·비밀번호를 직접 받기 둘 다 지원하고 위젯 관리자페이지에서 설정하는 건 어때? 그리고 우리 agent-os에 로그인을 연동하는 건 필요없나? 회원정보를 DB에 가지고 있어야 나중에 개인화 화면을 만들 수 있을까해서

고른 라벨이 아니라 되물음이다. 든 두 선택지의 설명은 아래였다.

- "회사 로그인 서버로 보내기 (Recommended)" — 설명: 질문 페이지가 회사 로그인 서버의 화면으로 사람을 보냈다가, 로그인이 끝나면 결과를 돌려받는 표준 방식입니다(OIDC). 비밀번호는 회사 로그인 서버만 다루고 질문 페이지는 보지 못합니다. 고객사 내부망에 이 방식을 지원하는 로그인 서버(예: Keycloak, AD FS. 두 제품이 이 방식을 지원한다는 것은 일반 지식이며 이 저장소에서 확인한 사실은 아닙니다)가 있어야 하고, 없으면 그 서버를 먼저 설치해야 합니다. 질문 페이지에는 로그인 서버를 호출하는 기능과 로그인 후 돌아오는 주소가 새로 생깁니다(지금 코드에는 외부를 호출하는 부분이 없습니다).
- "아이디·비밀번호를 직접 받기" — 설명: 질문 페이지가 로그인 화면을 직접 보여 주고, 입력받은 아이디와 비밀번호를 회사의 계정 디렉터리(예: Active Directory)에 물어 확인하는 방식입니다(LDAP). 별도의 로그인 서버가 없어도 됩니다. 대신 질문 페이지가 비밀번호를 직접 다루므로 비밀번호가 기록에 새지 않게 하는 일과 반복 시도 차단을 우리가 책임져야 합니다. 디렉터리와 통신하는 새 라이브러리와 시험용 가짜 디렉터리도 필요합니다(어림: 표준 기능만으로 구현하기 어렵다고 보며, 측정하지는 않았습니다).

고르지 않은 셋째 선택지는 "운영자가 계정 목록 작성"이었다. 이 답으로 열린 가지는 셋이다. 두 방식을 0.1 판에서 어디까지 만드는지, 회원 정보를 어디에 두는지(Agent OS에 로그인을 연동하는지), 화면에서 고르는 일을 어느 기능이 맡는지다. 라운드 2에서 묻는다.

### 그룹의 출처

질문: "제품 1.0의 문서 권한에서 사용할 '이 사람이 속한 그룹' 정보는 어디에서 가져오는 방향으로 잡아 둘까요? (0.1 판에서는 방향만 정하고, 그룹을 사용하는 기능은 만들지 않습니다.)"

> 사용자: "회사 로그인 시스템에서 (Recommended)"

— 설명: 로그인할 때 회사 로그인 시스템이 알려 주는 소속 그룹을 그대로 사용하는 방향입니다. 회사가 이미 관리하는 그룹을 다른 곳에 다시 입력할 필요가 없습니다. 대신 그룹 정보가 질문 페이지에서 Agent OS를 거쳐 문서 검색 서버까지 전달되어야 하므로, 그 전달 방법은 1.0의 다른 설계(주체 전달, 문서 검색 서버의 문서 권한)에서 확정해야 합니다. 로그인한 뒤에 바뀐 소속은 다시 로그인할 때까지 반영되지 않습니다.

### 익명에서 로그인으로 바꿀 때 남는 익명 토큰

질문: "익명으로 열려 있던 사이트를 로그인 전용으로 바꿀 때, 바꾸기 직전에 발급된 익명 토큰을 어떻게 다룰까요?"

> 사용자: 짧은 공백 받아들이기 (Recommended).
> 근데 익명으로 이용하는데 로그인이 필요한 요청 같은게 있을 수 있는거 아니야? 그건 어떻게 해? (익명+로그인) 유형으로 둬야하나? 어떤식으로 해?

고른 라벨은 "짧은 공백 받아들이기 (Recommended)" — 설명: 별도의 조치를 하지 않습니다. 전환 직전에 익명으로 들어와 있던 사람은 최대 약 2분 30초(토큰 수명 120초에 서버의 시간 여유 30초) 동안 더 질문할 수 있고, 이미 나오고 있던 답은 끝까지 나옵니다. 즉시 차단해야 하는 경우를 위해, 배포 안내에 '서명 키를 교체하고 Agent OS 서버를 다시 띄우는' 선택 절차를 적어 둡니다. 코드는 바뀌지 않습니다.

뒤의 되물음(익명으로 쓰다가 로그인이 필요한 요청)은 `both` 사이트의 동작을 묻는 것이라 라운드 2의 질문으로 올린다.

### 로그인한 사람의 고지 확인

질문: "로그인한 사람에게도 '질문이 기록된다'는 고지를 확인받을까요? (로그인하면 질문 내용이 그 사람을 가리키는 식별자와 함께 기록에 남습니다.)"

> 사용자: "사이트마다 한 번 확인 (Recommended)"

— 설명: 로그인한 뒤 그 사이트에서 처음 질문하기 전에, 익명으로 질문하는 사람과 같은 고지 화면을 보여 주고 '확인하고 질문하기'를 누르게 합니다. 질문이 로그인한 계정과 함께 기록된다는 문장은, 사이트가 고지 글을 직접 작성했더라도 질문 페이지가 항상 고지에 포함합니다. 확인했다는 사실을 어디에 기억할지는 다음 라운드에서 정합니다.

## 라운드 2

라운드 1의 되물음 셋을 본문에서 먼저 풀고 질문 셋으로 올렸다. 올리기 전에 다시 대 본 것: portal-admin이 "제품 1.0 묶음. 0.1 판에는 들지 않는다"(`.scratch/portal-admin/plan.md` 5행), trace-postgres가 슬라이스 11(`.scratch/plan.md` 기능 표), ADR 0023 14행의 세션 교환 거부, `src/agent_os`에 익명 여부를 읽는 코드가 없음(`anon|익명`으로 grep해 주체와 무관한 주석만 나왔다), 위젯 저장이 발급자와 `sub`의 묶음이 다르면 지움(`web/apps/widget/lib/storage.ts` 머리 주석과 29행), ADR 0054 24행("누구의 기억인지는 … 런타임이 주체 전파로 넘긴 주체로 받는다").

### 두 방식의 범위

질문: "두 로그인 방식(회사 로그인 서버로 보내기, 아이디·비밀번호 직접 받기)을 모두 지원하자는 제안을 0.1 판에서 어디까지 만들까요?"

> 사용자: "0.1은 하나, 구조는 열어 두기 (Recommended)"

— 설명: 0.1 판에서는 '회사 로그인 서버로 보내기'(OIDC) 하나만 구현합니다. 다만 설정 파일에 로그인 방식의 이름을 적는 칸을 두고 코드도 방식을 추가할 수 있는 구조로 만들어, 나중에 '아이디·비밀번호 직접 받기'(LDAP)를 설정의 모양을 바꾸지 않고 추가할 수 있게 합니다. LDAP 방식은 제품 1.0 묶음의 새 기능으로 계획표에 올리고, 화면에서 방식을 고르는 일은 질문 페이지 관리 화면(1.0 묶음이며 0.1 판에는 포함되지 않음)이 맡습니다. 0.1 판에서는 지금처럼 설정 파일로 정합니다.

### 회원 정보

질문: "로그인한 사람의 정보(회원 정보)를 어디에 보관할까요? (나중에 개인화 화면을 만들 가능성을 고려한 질문입니다.)"

> 사용자: "보관하지 않고 식별자만 전달 (Recommended)"

— 설명: 질문 페이지는 로그인 서버가 알려 준 '이 사람의 고정 식별자'만 토큰에 실어 Agent OS에 전달하고, 회원 표는 어디에도 만들지 않습니다. 이름이나 소속 같은 정보의 원본은 회사 로그인 시스템에 그대로 둡니다. 개인화에 필요한 사람별 데이터는 이 식별자를 열쇠로 삼아 나중에 추가할 수 있습니다. 실행 기록에는 이미 식별자가 남고, 사람별 기억 기능(계획표의 user-memory)도 이 식별자를 열쇠로 쓰도록 설계되어 있습니다. Agent OS와 질문 페이지의 현재 구조가 바뀌지 않습니다.

### 둘 다 사이트의 동작

질문: "'익명과 로그인 둘 다' 유형의 사이트는 어떻게 동작하게 할까요? (익명으로 쓰다가 로그인이 필요한 경우를 어떻게 다룰지에 대한 질문입니다.)"

> 사용자: 질문 도중 로그인 요구사항은 별로 없어? 조사해봐

고르지 않았다. 올린 선택지는 "익명으로 시작, 원할 때 로그인 (Recommended)", "질문 도중 로그인 요구도 추가", "'둘 다' 유형 없애기"였다. 조사 둘을 서브에이전트에 맡겼다. 하나는 다른 제품의 사례와 표준(웹), 하나는 이 저장소의 계획에서 익명 주체를 가르는 기능과 지금 구조로 그 흐름을 만들 때 바꿀 자리다. 조사가 닿으면 이 질문을 다시 올린다.

## 조사: 질문 도중 로그인 요구

서브에이전트 둘의 보고가 닿았다. 원문은 세션과 함께 사라지므로 설계가 기대는 사실만 근거의 종류와 함께 적는다.

### 다른 제품과 표준(웹)

근거의 종류는 서브에이전트가 가른 대로다. "원문"은 서브에이전트가 페이지를 `curl`이나 내장 브라우저로 받아 읽은 것이고, 이 세션이 다시 대 보지는 않았다.

- 고객 상담용 채팅 제품은 익명으로 시작한 대화 도중의 로그인을 문서로 다룬다. Microsoft Copilot Studio(Authenticate 노드, 도구 연결 카드), Amazon Connect 채팅(Authenticate Customer 블록, 2024-12), Zendesk 메시징(사이트 로그인이 위젯에 반영되고 자동 병합), Intercom(같은 기기 쿠키일 때 자동 병합), Genesys Cloud(step-up authentication), LivePerson이다(원문. LivePerson 웹은 검색 요약).
- 계기는 개인 데이터 조회, 결제 같은 거래, 상담원 연결, 사용자 권한이 필요한 도구 호출이다. AWS 블로그는 일반 질문과 공개 정보에는 인증을 요구하지 말라고 적는다(원문). 문서에 대한 질문이 계기인 사례는 Copilot Studio의 권한이 걸린 지식 소스 하나였다(원문).
- 사내 지식 검색 도구는 처음부터 로그인을 전제하거나 익명을 따로 가른다. Glean은 익명 검색을 지원하지 않고, Microsoft 365 Copilot은 Entra ID 계정이 필수이며, Amazon Q Business는 익명 앱과 인증 앱을 한 앱 환경에 함께 두지 못하고, Vertex AI Search 위젯은 위젯 단위로 둘 가운데 하나를 고른다(원문).
- 로그인 뒤에 대화가 이어지는지는 제품마다 다르다. Copilot Studio, Amazon Connect, Genesys는 같은 대화가 이어지고, Zendesk와 Intercom은 병합하되 부작용(중복 티켓, 쿠키 의존과 지연)을 문서에 적었으며, ChatGPT는 마지막 대화 하나만 이어진다(원문).
- 표준: RFC 9470의 step-up은 이미 로그인한 사용자를 더 강한 인증으로 올리는 규약이고 익명에서 로그인으로 넘어가는 일을 정하지 않는다. MCP는 도구 호출 도중 권한이 필요함을 401, 403 `insufficient_scope`(2025-11-25 판), URL elicitation(`URLElicitationRequiredError`, 2025-11-25 판의 새 기능)으로 알린다(원문).
- 확인하지 못한 것: Salesforce의 대화 도중 전환, ChatGPT의 한도나 첨부가 로그인을 일으키는지, 문서 질의응답 위젯(Inkeep 등)의 방식.

### 이 저장소의 계획과 지금 구조

- 익명 주체를 거부하기로 적은 기능은 둘이다. user-memory(슬라이스 15, "익명 주체에게는 쓰지 않고 기억 서버도 익명 주체의 요청을 거부한다", ADR 0054 13행)와 named-query(슬라이스 15, 익명 주체의 사람별 조회를 거부, ADR 0055 25행)다. 거부하는 쪽은 런타임이 아니라 MCP 서버다(문서를 읽었다).
- 익명을 어떻게 다룰지 열어 둔 것: system-lookup("익명 주체의 요청을 다루는 법"), kb-selection(익명 주체의 실행에서 목록을 보게 할지), principal-propagation(거부할 때의 오류 코드)(문서를 읽었다).
- 그 거부를 최종 사용자의 화면에 어떻게 알리는지, 로그인으로 어떻게 이끄는지를 정한 서술은 찾지 못했다. 지금 구조 그대로면 도구의 실패는 `tool_called(ok=false)`로 모델에 돌아가고 화면에는 진행 항목과 모델의 답 글로만 닿는다(코드를 읽었다. 화면에 닿는 모양은 어림).
- 승인 규칙의 조건에 주체나 익명 여부를 쓸 수 없다(`core/rules.py`의 `applied_rule`에 주체 인자가 없다, 코드를 읽었다).
- 위젯이 페이지에 "로그인이 필요하다"를 알릴 수단이 없다. 공개 표면은 속성 다섯, `tokenProvider`, postMessage의 토큰 요청뿐이다(`web/apps/widget/EMBED.md` 176행, 코드를 읽었다). 토큰을 받지 못했거나 401이면 "로그인 정보를 받지 못했습니다. 페이지를 새로 고쳐 주세요." 알림이고 단추가 없다.
- 사람을 기다리는 멈춤은 `run_paused` 하나이고 승인 게이트에서만 난다. 멈춤의 이유나 최종 사용자 항목의 종류를 더하면 `sdk`의 이벤트와 `openapi.json`이 바뀐다(코드를 읽었다).
- 익명으로 시작한 대화는 로그인한 주체가 이어 갈 수 없다. 서버는 `DifferentPrincipal`을 최종 사용자 면에서 404로 답하고, 위젯은 토큰의 발급자와 `sub`가 바뀌면 그 전에 저장한 대화를 비운다. 옮기거나 합치는 장치는 없다(코드를 읽었다).

## 라운드 3

조사 셋(위의 둘과 OIDC 클라이언트 후보의 측정)이 도는 동안, 그 결과와 무관한 질문 넷을 올렸다. 올리기 전에 대 본 것: principal-propagation 계획 5행("주체가 조직의 사용자 식별자와 대응될 수 있어야 한다"), ADR 0023 42행("`sub`는 사이트가 인증한, 오래 가는 사용자 식별자여야 한다"), ADR 0050 17행(`anon-` 접두 금지 요건)과 "무상태"(8·12·39·46행), `anonymous-cookie.ts`(서명 없음, 사이트별 경로)와 `cookie-policy.ts`(30일), `config.ts`(모르는 칸 거부, `schema_version` "1"), user-memory·named-query·system-lookup이 슬라이스 15라는 것(`.scratch/plan.md` 96~100행). OpenID Connect Core의 `sub` 정의(2절)와 `preferred_username`·5.7절은 WebFetch의 웹 요약이다(https://openid.net/specs/openid-connect-core-1_0.html. 원문을 받아 대 보지 않았다).

### 로그인한 사람의 식별자

질문: "로그인한 사람을 실행 기록에 무엇으로 남길까요? (회사 로그인 서버가 알려 주는 여러 항목 중 어느 것을 그 사람의 식별자로 쓸지에 대한 질문입니다.)"

> 사용자: "운영자가 고르기, 기본은 고정 식별자 (Recommended)"

— 설명: 설정 파일에 '어느 항목을 식별자로 쓸지' 적는 칸을 둡니다. 적지 않으면 로그인 서버의 고정 식별자를 씁니다. 회사 로그인 서버가 사번처럼 조직에서 통용되는 번호를 따로 알려 준다면 운영자가 그 항목의 이름을 적습니다. 뒤 판에 계획된 기능(사람별 기억 삭제, 사내 시스템 조회)이 '식별자가 조직의 사용자 식별자와 대응될 수 있어야 한다'고 요구하는데, 회사마다 로그인 서버가 알려 주는 항목이 달라서 운영자가 고르게 합니다. 치르는 값은 설정 칸이 하나 늘어나는 것, 그리고 운영 도중 이 칸을 바꾸면 모든 사람이 새 사람으로 기록되어 이전 기록과 연결이 끊어지는 것입니다. 지정한 항목이 로그인 서버의 응답에 없으면 그 사람의 로그인을 거절합니다.

### 로그인 상태를 기억하는 곳

질문: "한 번 로그인한 사람을 질문 페이지가 어디에 기억할까요?"

> 사용자: "브라우저의 서명된 쿠키에 (Recommended)"

— 설명: 질문 페이지가 '이 사람은 누구이고 언제까지 로그인 상태인지'를 적은 값에 서버만 만들 수 있는 서명을 붙여 브라우저 쿠키로 보관합니다. 서버는 아무것도 저장하지 않으므로, 질문 페이지가 저장소 없이 동작하는 현재 구조가 유지되고 서버를 다시 띄워도 로그인이 풀리지 않습니다. 한계는 특정한 한 사람만 골라서 즉시 로그아웃시키는 기능이 없다는 점입니다. 회사에서 계정을 정지해도 쿠키의 유효 시간이 끝날 때까지는 질문할 수 있으므로, 유효 시간을 짧게 잡아 보완합니다(다음 질문).

### 로그인 상태의 유지 시간

질문: "로그인 상태를 얼마 동안 유지할까요? (이 시간이 지나면 질문 페이지가 회사 로그인 서버에 다시 확인합니다.)"

> 사용자: "8시간, 설정으로 변경 가능 (Recommended)."
> 사용자: 근데 보통 토큰 만료 시간이 있지 않아?
> 사용자: 일반적으로 JWT로 하지않나해서 그리고 refresh token이 있을 수 도 있는거 아니야?
> 사용자: JWT 방식 말고 또 있어? 조사해봐 보통 어떻게 하는지

— 설명: 로그인한 시각부터 8시간 동안 유지하고, 운영자가 설정 파일에서 시간을 바꿀 수 있게 합니다(8시간은 하루 업무 시간을 기준으로 제안하는 값입니다). 하루 업무 시간 동안 다시 확인하는 일이 없습니다. 회사에서 계정을 정지한 뒤에도 최대 약 8시간은 질문할 수 있습니다. 시간이 지나면 질문 페이지가 회사 로그인 서버로 보내고, 그 서버에 로그인이 살아 있으면 비밀번호를 다시 입력하지 않고 돌아옵니다(어림: 로그인 서버의 설정에 따라 다릅니다). 위젯은 대화를 탭 단위로 저장하지만, 로그인 서버에 다녀온 뒤에 대화가 복원되는지는 재지 않았습니다(어림).

8시간은 고른 것으로 적되 되물음이 붙었으므로 잠정이다. 로그인 상태를 유지하는 방식(JWT, refresh 토큰, 그 밖의 방식)과 흔한 수명을 서브에이전트에 웹 조사로 맡겼고, 보고가 닿으면 refresh 토큰을 쓸지를 질문으로 올리며 이 답을 다시 확인받는다.

### 로그인할 수 있는 사람

질문: "로그인 사이트에서 누가 질문할 수 있게 할까요?"

> 사용자: "회사 로그인을 통과한 모든 계정 (Recommended)"

— 설명: 회사 로그인 서버가 인증한 사람이면 누구나 질문할 수 있고, 질문 페이지는 추가로 가르지 않습니다. 일부 부서만 허용하려면 회사 로그인 서버에서 '이 프로그램에 로그인할 수 있는 사람'을 제한합니다(어림: 널리 쓰이는 로그인 서버 제품은 이 기능을 제공하지만, 고객사의 제품은 확인하지 못했습니다). 사이트마다 대상을 다르게 하는 일은 뒤 판의 그룹과 문서 권한 설계에서 다룹니다.

### 둘 다 사이트의 동작(다시 올림)

조사 둘의 결과를 설명에 넣어 같은 질문과 라벨로 다시 올렸다. 올리기 전에 다시 대 본 것: `RunPaused`의 독스트링("승인을 기다리며 멈췄다", `src/agent_os/sdk/events.py` 125행), 위젯의 공개 표면 목록에 이벤트나 콜백이 없음(`web/apps/widget/EMBED.md` 176행), 이어 가기의 `DifferentPrincipal`(`src/agent_os/core/continuation.py` 252행).

질문: "'익명과 로그인 둘 다' 유형의 사이트는 어떻게 동작하게 할까요? (익명으로 쓰다가 로그인이 필요한 경우를 어떻게 다룰지에 대한 질문입니다.)"

> 사용자: "질문 도중 로그인 요구도 추가"

— 설명: 위 동작에 더해, 답변 도중 '이 요청은 로그인이 필요합니다'라고 알리고 로그인 단추를 보여 주는 흐름을 0.1 판에 만듭니다. 조사 결과 이 흐름은 고객 상담용 채팅 제품(Zendesk, Intercom, Amazon Connect 등)에서 흔하고, 계기는 개인 데이터 조회나 결제, 상담원 연결입니다. 지금 구조에서 만들려면 세 가지를 고쳐야 합니다. 첫째, 실행이 멈추는 이유가 '승인 대기' 하나뿐이어서 '로그인 대기'를 더하려면 서버와 위젯 사이의 계약을 바꿔야 합니다. 둘째, 위젯이 페이지에 '로그인이 필요하다'고 알리는 통로가 없습니다. 셋째, 익명일 때의 대화를 로그인한 뒤에 이어 가지 못하므로 대화를 넘겨주는 장치가 필요합니다. 0.1 판에는 이 흐름을 일으킬 기능이 없어서, 만들어도 시험할 실제 사례가 없습니다. 작업량은 재지 않았습니다(어림: 0.1 판의 범위가 크게 늘어납니다).

"위 동작"은 추천으로 올린 첫 선택지("익명으로 시작, 원할 때 로그인")의 동작이다. 그 설명: '둘 다' 사이트에서는 로그인 없이 바로 질문할 수 있고, 화면의 '로그인하고 질문하기' 단추를 누르면 로그인한 사람으로 바뀝니다. 로그인하면 익명일 때의 대화는 화면에서 지워지고 새 대화로 시작합니다(위젯은 질문하는 사람이 바뀌면 저장한 대화를 지우고, 서버도 익명일 때의 대화를 로그인한 사람이 이어 가는 요청을 거절합니다). (뒤의 문장들은 답변 도중의 로그인 요구를 0.1 판에 만들지 않는다는 내용이라 고른 답에 들지 않는다.)

추천과 다른 답이다. 이 답으로 열리는 가지: 무엇이 로그인 요구를 일으키는지, 서버가 익명 주체를 무엇으로 알아보는지, 로그인한 뒤 답을 어떻게 잇는지, 위젯이 페이지에 알리는 통로, 계약(`sdk`의 이벤트, `openapi.json`, 위젯의 공개 표면)의 변경, 기능 행을 나눌지다.

## 조사: 로그인 상태를 유지하는 방식

라운드 3의 되물음("보통 토큰 만료 시간이 있지 않아? … JWT 방식 말고 또 있어?")에 답하려고 서브에이전트에 맡긴 웹 조사다. "원문"은 서브에이전트가 `curl`로 받아 그 문장을 본 것이고, 이 세션이 다시 대 보지는 않았다.

- 방식은 셋이다. 서버 저장소의 세션과 무작위 번호 쿠키, 서명하거나 암호화한 쿠키에 내용을 담는 무상태 방식, 브라우저 저장소의 토큰. RFC 10017(OAuth 2.0 for Browser-Based Applications, 2026-08) 6.1.2.3절이 앞의 둘을 나란히 견준다. 서버 쪽은 어떤 세션이든 폐기할 수 있고, 클라이언트 쪽은 서버가 기억할 것이 없지만 폐기가 어렵다. 같은 문서가 로그인만 맡기고 스스로 로그인 상태를 관리하는 애플리케이션은 쿠키 기반 세션이면 된다고 적는다(1절, 7.1절). 브라우저 저장소의 토큰은 OWASP와 IETF가 말린다(원문).
- 무상태 쿠키가 기본인 것: oauth2-proxy, Auth.js(암호화한 JWT), Rails, ASP.NET Core. 서버 저장이 기본인 것: GitLab, Grafana, Django(원문).
- ID 토큰의 만료는 세션 수명이 아니다(OpenID Connect Core 2절 `exp`의 주석, NIST SP 800-63C-4 4.7절). 반대 방향의 관행도 있다. Microsoft 문서는 웹 애플리케이션이 보통 세션 수명을 ID 토큰 수명(기본 1시간)에 맞춘다고 적는다(원문).
- refresh 토큰은 신원만 필요한 경우 기본이 아니다. 쓰는 제품(Grafana, oauth2-proxy의 `cookie-refresh`. 기본은 꺼짐)은 로그인 서버에서 접근 권한이 회수됐는지를 다시 확인하려는 선택 기능으로 둔다. 무상태 쿠키에 두면 동시 요청의 경합(oauth2-proxy는 쿠키 저장이 세션을 잠글 수 없어 충돌하면 다시 로그인하게 된다고 적는다), 4KB 쿠키 한도, 암호화가 따른다. `offline_access`는 사용자가 자리에 없어도 쓰는 토큰을 청하는 범위라 계정 정지의 재확인에는 맞지 않는다(앞은 원문, 끝 문장은 서브에이전트의 어림).
- 수명의 권장값: OWASP Session Management Cheat Sheet는 사무직이 하루 종일 쓰는 애플리케이션의 절대 만료를 4~8시간으로 든다. NIST SP 800-63B-4는 AAL1 30일 이하, AAL2 24시간 이하(유휴 1시간 이하)를 권장한다. 제품의 기본값은 7~30일이다(oauth2-proxy 7일, Auth.js 30일, Grafana 유휴 7일·최대 30일)(원문).
- 계정 정지를 반영하는 길: 짧은 수명과 재로그인(무상태에서 가능), `prompt=none`의 조용한 재확인(전체 페이지 이동이면 가능), refresh 토큰(가능하나 위의 문제), Back-Channel Logout(세션을 찾아 지울 상태가 필요해 무상태 그대로는 불가)(원문).
- 쿠키 지침(RFC 10017 6.1.3.2절): Secure와 HttpOnly는 필수, SameSite=Strict와 `__Host-` 접두는 권장(원문).

## 측정: OIDC 클라이언트 후보와 가짜 로그인 서버

서브에이전트가 `.scratch/portal-login/probes/oidc_client/`에 프로브를 만들어 쟀다(node 24.19.0, Windows 10, 2026-11-12. 스크립트 여섯이 종료 코드 0, 실행 79회차). 이 세션이 `flow.mjs`의 `good`·`insecure` 묶음(9회차)과 `fault` 묶음(48회차)을 손으로 다시 돌렸고(`node .scratch/portal-login/probes/oidc_client/probe/flow.mjs --group good --group insecure`, 같은 명령의 `--group fault`. 측정이 아닌 회차 0), 결과가 그 폴더 `README.md`의 표와 같았다. 나머지 묶음과 나머지 스크립트(`typecheck.mjs`, `lint.mjs`, `deps.mjs`, `registry.mjs`, `loc.mjs`)는 이 세션이 다시 돌리지 않았다. 결과의 원천은 그 폴더의 `README.md`다.

- 후보 셋(`openid-client` 6.8.9, `oauth4webapi` 3.8.8 + `jose` 6.2.17, `node:crypto`와 `node:http`·`node:https`로 직접 구현) 모두 질문 페이지의 tsconfig로 타입 검사를 지났고 우회 구문이 필요 없었으며, node가 `.ts`를 바로 돌려 인가 코드 흐름 한 바퀴(PKCE, state, nonce)를 마쳤다.
- 두 라이브러리의 기본은 ID 토큰의 서명을 보지 않는다(서명이 틀린 토큰을 받아들였다). `openid-client`는 `enableNonRepudiationChecks`, `oauth4webapi`는 `validateApplicationLevelSignature`나 jose의 `jwtVerify`를 불러야 거부했다. 그 밖의 고장 일곱(iss, aud, exp, nonce 다름·없음, alg none·HS256)은 세 후보가 모두 거부했다.
- 두 라이브러리는 `http` 발급자를 요청 전에 거부하고, 푸는 선택지 `allowInsecureRequests`가 `@deprecated`라 저장소 린트의 `@typescript-eslint/no-deprecated`에 걸린다. 판정자는 인라인 끄기 주석을 받지 않는다. `https` 발급자에 사설 인증 기관을 쓰면 `NODE_EXTRA_CA_CERTS`로 세 후보가 모두 통과했다.
- 라이브러리 안의 전역 `fetch`는 판정 범위 밖이고, 부르는 코드는 `fetch`를 넘기지 않아도 된다. `customFetch`에 `node:http`의 `request`로 만든 함수를 끼우면 전역 `fetch` 호출이 0이 된다.
- 의존성: `openid-client`는 패키지 3개(자신, jose, oauth4webapi) 770,234바이트, `oauth4webapi` + `jose`는 2개 548,439바이트, 모두 MIT이고 설치 스크립트가 없다. 직접 구현은 0이다.
- 코드 줄 수(빈 줄과 주석 제외): `openid-client` 56, `oauth4webapi` 99, 직접 구현 273. 직접 구현이 뺀 것: 암호화된 ID 토큰, RS256 밖의 알고리즘(PS256, ES256, EdDSA), 공개 키 캐시와 키가 바뀌었을 때 다시 받기, 응답 크기 상한, `at_hash`, `acr`·`auth_time` 등이다.
- 세 후보 모두 Promise를 돌려주는데 질문 페이지의 처리기는 동기 함수다(`handler.ts` 89행).
- 가짜 로그인 서버: 직접 만든 것(`node:http` + `node:crypto`, 274줄, 고장 여덟 가지와 TLS 포함, 의존성 0)과 `oidc-provider` 9.13.3(98줄에 로그인·동의 폼을 제출하는 코드 121줄, 패키지 40개 1,755,723바이트, 타입 선언은 `@types/oidc-provider`를 따로 설치)을 쟀고 둘 다 한 바퀴를 돌았다.

### 유지 시간의 기준과 refresh token(다시 올림)

되물음에 답한 것: 둘 다 설정으로 둘 수 있고 만드는 값이 다르다. 유지 시간의 기준을 고르는 설정은 끝나는 시각을 어느 값으로 정하는지만 달라 작고(어림), refresh token은 켰을 때 도는 부분을 다 지어야 해 크다(어림). 올리기 전에 대 본 것: 일지의 "조사: 로그인 상태를 유지하는 방식"(Grafana와 oauth2-proxy의 선택 기능, 기본은 꺼짐, oauth2-proxy의 동시 갱신 한계), `openid-client` 6.8.9의 타입 선언에 `refreshTokenGrant`가 있음(프로브 폴더의 `node_modules/openid-client/build/index.d.ts` 1953행. 실행해 보지 않았다), 프로브의 가짜 로그인 서버 `fake-idp.ts`에 `refresh`라는 글자가 없음.

질문: "로그인 유지 시간의 기준과 refresh token을 어디까지 설정으로 고를 수 있게 할까요?"

> 사용자: "유지 시간 기준은 설정으로 선택, refresh token은 뒤 판 (Recommended)"

— 설명: 운영자가 설정 파일에서 유지 시간의 기준을 둘 가운데 하나로 고릅니다. 하나는 질문 페이지가 정한 시간(기본값이고, 로그인한 시각부터 8시간이며 값을 바꿀 수 있습니다)이고, 다른 하나는 회사 로그인 서버가 준 토큰(ID 토큰)의 만료 시간입니다. 두 방식은 로그인 상태가 끝나는 시각을 어느 값으로 정하는지만 달라서 구현이 작습니다(어림: 재지 않았습니다). refresh token은 0.1 판에 만들지 않고, LDAP 로그인과 같이 뒤 판의 새 기능으로 계획표에 올립니다. 암호화한 쿠키, 쿠키 크기 한도(약 4KB), 동시 갱신 충돌 처리, 시험용 가짜 로그인 서버의 갱신 기능(측정에 쓴 가짜 서버에는 없습니다)까지 필요해서 로그인 유지 부분의 작업이 크게 늘어나기 때문입니다(어림). 그때까지 계정 정지의 반영은 유지 시간을 짧게 잡거나 로그인 서버의 토큰 만료를 따르는 방법으로 보완합니다.

이 답으로 라운드 3의 유지 시간(8시간, 설정으로 변경 가능)은 잠정에서 확정이 됐다. 기본 기준은 질문 페이지가 정한 시간이다. 새 기능 행이 하나 더 는다(refresh token으로 로그인 상태를 다시 확인하기. LDAP 로그인과 함께 뒤 판).

## 조사: 로그인 요구의 계기를 누가 어디에 정하는가

라운드 4의 되물음("보통 어떤식으로 해?")에 답하려고 서브에이전트에 맡긴 웹 조사다. "원문"은 서브에이전트가 `curl`로 받아 그 문장을 본 것이다. 이 세션은 받아 둔 사본에서 Intercom Fin 문서에 "verified email"이 든 줄이 있는 것만 봤고 나머지는 다시 대 보지 않았다.

- 에이전트나 봇을 만든 사람이 정의에 적는 사례가 일곱으로 가장 많다. Copilot Studio(토픽의 Authenticate 노드와 도구별 "User authentication". 관리자는 데이터 정책으로 인증 없는 에이전트의 게시를 막는다), Amazon Connect(흐름의 Authenticate Customer 블록), Salesforce Agentforce(토픽과 액션에 건 필터), GPT Actions(액션의 인증 유형), Auth0 for AI Agents, LangGraph Agent Auth, Amazon Bedrock AgentCore Identity(코드의 `@requires_access_token`)다(원문).
- 도구 서버의 응답이 계기인 사례는 셋이다. ChatGPT 앱(도구 정의의 `securitySchemes`와 오류 응답의 `_meta["mcp/www_authenticate"]`), Claude 커넥터("Sign in when needed"), LibreChat(서버의 거부를 자동 감지)이다(원문).
- 운영자나 관리자의 설정이 계기인 사례는 넓게 보아 넷이다. Intercom Fin(데이터 커넥터별 Audience 규칙 "logged-in users with a verified email"), AgentCore Policy(Gateway에 붙인 Cedar 정책, 도구별, 사용자 클레임 조건), Claude 커넥터(조직 Owner가 커넥터의 인증 방식을 고른다), LibreChat(`librechat.yaml`의 서버별 `requiresOAuth`)이다(원문).
- 사례의 대부분은 이미 로그인한 사람이 외부 서비스에 연결 권한을 주는 일이다. 익명인 사람을 로그인시키는 사례는 Copilot Studio, Amazon Connect, Agentforce, Intercom Fin(이메일 확인), Zendesk, Genesys다.
- 찾지 못한 것: 따로 둔 정책 파일의 거부를 익명 사용자의 로그인 요구로 바꾸는 사례. AgentCore Policy가 거부한 호출을 로그인 요구로 바꾸는지와 Intercom에서 규칙에 맞지 않는 익명 사용자에게 로그인 안내가 뜨는지는 문서에서 찾지 못했다.
- 주소: https://learn.microsoft.com/en-us/microsoft-copilot-studio/configure-enduser-authentication , https://docs.aws.amazon.com/connect/latest/adminguide/authenticate-customer.html , https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy.html , https://fin.ai/help/en/articles/13975792-create-data-connectors-for-fin , https://developers.openai.com/apps-sdk/build/auth , https://claude.com/docs/connectors/custom , https://www.librechat.ai/docs/configuration/librechat_yaml/object_structure/mcp_servers

## 조사: Claude와 Gemini가 로그인 전후의 대화를 잇는 방식

라운드 4의 되물음("클로드랑 제미나이는 어떻게 해?")에 답하려고 서브에이전트에 맡긴 웹 조사다. 이 세션은 받아 둔 사본에서 Claude 문서의 한 문장(아래 인용)만 다시 봤다.

- Claude는 로그인하지 않고 대화하는 길이 문서에 없다(로그인 도움말은 앱을 열면 로그인 선택지가 보인다고 적는다. 원문 https://support.claude.com/en/articles/13189465-log-in-to-your-claude-account . "비로그인 대화가 없다"는 문장은 찾지 못했고 첫 화면은 직접 보지 못했다).
- Claude에서 이미 로그인한 사람이 대화 도중 커넥터의 로그인을 요구받으면, 대화 안에 연결 카드가 뜨고 로그인을 마치면 같은 턴이 이어진다. 문서의 문장은 "Claude retries the same tool call automatically with the new token, and the turn continues with no context lost"다(원문 https://claude.com/docs/connectors/building/lazy-authentication.md . 이 세션이 사본 22행에서 봤다). 다시 실행되는 것은 질문 전체가 아니라 막힌 도구 호출 하나다.
- Gemini는 웹에서 로그인 없이 글 대화를 할 수 있고(원문 https://support.google.com/gemini/answer/13275745 ), 로그인이 필요한 기능을 쓸 때 로그인을 요구한다. 로그인한 뒤 로그인 전의 대화가 어떻게 되는지는 공식 문서에 없다. 비로그인 데이터는 계정과 연결되지 않는다고만 적혀 있어 옮겨지지 않는다고 본 것은 서브에이전트의 어림이다. 앱 연결을 마친 뒤 같은 질문이 자동으로 다시 실행되는지도 찾지 못했다.
- ChatGPT는 로그인 없이 한 번에 대화 하나를 하고, 계정을 만들면 가장 최근 대화가 사이드바에 나타나며 그 앞의 대화는 저장되지 않는다(원문 https://help.openai.com/en/articles/9125172-the-chatgpt-home-page . 서브에이전트가 브라우저로 본문을 읽었다).
- Copilot과 Perplexity는 로그인 없이 대화할 수 있으나 로그인 뒤의 처리가 공식 문서에 없다.
- 찾지 못한 것: 로그인한 사람의 새 대화로 방금 그 질문을 자동으로 다시 보내는 방식을 문서로 밝힌 제품.

## 조사: Node의 OIDC 클라이언트 사용량

라운드 4의 되물음("openid-client를 가장 많이 사용해?")에 답하려고 서브에이전트에 맡긴 조사다. 내려받기 수는 서브에이전트가 `curl -s https://api.npmjs.org/downloads/point/last-week/<이름>`으로 손으로 본 것이고 기간은 2026-11-05부터 2026-11-11이다. 이 세션은 `openid-client`의 수만 같은 명령으로 다시 봤고 같았다(23,842,164).

- 주간 내려받기 수: `jose` 225,966,397(JWT 일반 도구라 OIDC 사용량으로 읽을 수 없다), `@azure/msal-node` 29,685,459(Azure SDK의 몫이 크다는 것은 어림), `oauth4webapi` 25,389,873, `openid-client` 23,842,164, `better-auth` 18,855,487, `next-auth` 9,359,440, `@auth/core` 7,114,611, `passport-openidconnect` 153,860, `express-openid-connect` 179,714.
- `oauth4webapi`는 `openid-client` 6.x와 `@auth/core`가 의존하는 아래층이라 그 수에 두 패키지의 몫이 들어 있다(레지스트리의 `dependencies`를 손으로 봤다).
- 오픈 소스 프로젝트 14개의 `package.json`을 읽은 결과 8개가 `openid-client`에 직접 의존한다. express-openid-connect, Backstage, n8n, Directus, LibreChat, Immich, Actual Budget, @kubernetes/client-node다. Auth.js는 `oauth4webapi`, NocoDB와 Outline은 Passport 계열이다(브랜치 끝의 파일을 읽었고 커밋은 고정하지 않았다).
- OpenID Foundation의 인증 목록에 `openid-client`와 `oauth4webapi`가 올라 있다(웹 요약 https://openid.net/developers/certified-openid-connect-implementations/ . 요약 둘의 답이 서로 달랐다고 서브에이전트가 적었다).
- 결론: 범용 서버 쪽 OIDC 클라이언트 가운데 `openid-client`보다 많이 쓰이는 별개의 대안은 찾지 못했다.

### 로그인 뒤 대화를 잇는 방식(다시 올림)

> 사용자: "로그인 전 대화를 넘겨받아 이어 가기"

— 설명: 로그인을 마치면 로그인 전의 대화가 화면에 그대로 남고, 막혔던 질문을 로그인한 사람의 이름으로 같은 대화에 이어서 다시 보냅니다. 에이전트가 앞의 대화 맥락을 기억한 채 답합니다. 조사 결과 ChatGPT가 이와 가깝습니다(계정을 만들면 로그인 전의 가장 최근 대화 하나가 계정으로 옮겨집니다). 치르는 값은 첫째 선택지의 것에 더해 세 가지입니다. 질문 페이지가 '이 익명 식별자와 이 로그인한 사람은 같은 브라우저'임을 서명해 알리는 표시를 토큰에 추가해야 합니다(토큰 형식의 변경). 서버가 그 표시가 있을 때에만 익명일 때의 대화를 로그인한 사람이 잇도록 보안 규칙에 예외를 하나 둡니다. 그리고 한 대화 안에 두 사람의 기록이 이어진 것을 관리 화면이 어떻게 보여 줄지 정해야 합니다. 작업량은 재지 않았습니다(어림: 첫째 선택지보다 크고 셋째보다 작습니다).

추천("같은 질문을 자동으로 다시 보내기")과 다른 답이다. 설명이 가리킨 "첫째 선택지의 것"은 그 선택지의 설명에 적은 둘이다. 서버와 화면 사이 계약에 '로그인 필요' 표시를 추가하는 것과, 위젯이 페이지에 로그인을 요청하는 통로를 추가하는 것이다(지금 위젯에는 그런 통로가 없다). 이 답으로 열리는 가지: 스스로 로그인할 때도 대화를 넘겨받는지(라운드 3에서 정한 "로그인하면 익명일 때의 대화는 화면에서 지워지고 새 대화로 시작"과 맞추기), 막힌 답변이 어떤 결말로 끝나고 다시 보낸 질문이 어느 실행에 이어 붙는지, 넘겨받은 사실을 실행 기록의 어디에 적는지, 관리 화면의 표시다.

### OIDC 클라이언트(다시 올림)

질문: "회사 로그인 서버와 통신하는 부분을 무엇으로 만들까요?"

> 사용자: "검증된 라이브러리 openid-client 사용 (Recommended)"

— 설명: 조사 결과 범용 서버 쪽 로그인 라이브러리 가운데 openid-client보다 많이 쓰이는 별개의 대안은 찾지 못했습니다. 주간 내려받기 수는 약 2,384만 회이고(2026-11-05부터 11-11까지. 제가 같은 명령으로 다시 확인했습니다), package.json을 확인한 오픈 소스 프로젝트 14개 가운데 8개(n8n, Directus, LibreChat, Immich, Backstage 등)가 직접 씁니다. 프로브 측정에서는 로그인 흐름 코드가 56줄로 가장 짧았습니다. 치르는 값은 세 가지입니다. 패키지 3개(약 770KB, 모두 MIT 라이선스)가 늘어납니다. 기본 설정이 로그인 서버가 준 토큰의 서명을 검사하지 않으므로 검사를 켜는 설정을 반드시 넣어야 합니다(프로브에서 서명이 틀린 토큰을 기본 설정이 받아들이고, 검사를 켠 설정이 거부하는 것을 확인했습니다). 그리고 로그인 서버 주소는 https만 받습니다(https가 아닌 주소를 허용하는 설정이 '곧 없어질 기능'으로 표시되어 이 저장소의 검사에 걸립니다). 시험용 가짜 서버도 https로 띄웁니다(사내 인증 기관의 인증서는 환경 변수로 등록하면 동작하는 것을 프로브에서 확인했습니다).

이 답으로 정해진 것: OIDC 클라이언트는 `openid-client`이고, ID 토큰의 서명 검사를 켜는 설정(`enableNonRepudiationChecks`)을 넣으며, 로그인 서버 주소는 `https`만 받고, 시험용 가짜 로그인 서버도 `https`로 띄운다.

### 로그아웃 방식의 설정

질문: "로그아웃 방식을 설정으로 고를 수 있게 할까요?"

> 사용자: "설정으로 고르기, 기본은 질문 페이지에서만 (Recommended)"

— 설명: 화면에 로그아웃 단추를 두고, 운영자가 로그인 서버 설정마다 둘 가운데 하나를 고릅니다. 기본은 질문 페이지의 로그인 쿠키만 지우는 방식이고(회사의 다른 프로그램은 영향을 받지 않습니다), 다른 하나는 회사 로그인 서버에서도 함께 로그아웃하는 방식입니다(함께 쓰는 PC에서 다음 사람이 앞사람의 계정으로 로그인되는 일을 막습니다). '둘 다' 사이트에서는 로그아웃하면 익명으로 돌아갑니다. 측정한 라이브러리 openid-client에 로그인 서버의 로그아웃 주소를 만드는 기능이 있습니다(타입 선언에서 확인했고 실행해 보지는 않았습니다). 치르는 값은 두 방식을 모두 만들고 시험하는 것, 시험용 가짜 로그인 서버에 로그아웃 기능을 더하는 것(측정에 쓴 가짜 서버에는 없습니다), 그리고 이 기능을 지원하지 않는 로그인 서버에 함께 로그아웃을 켰을 때의 동작을 명세에서 정해야 한다는 것입니다. 작업량은 재지 않았습니다(어림: refresh token보다 훨씬 작습니다).

## 조사: 계기 셋을 모두 넣을 수 있는가

되물음("3개 다 지원하는건?")에 답하려고 이 세션이 코드와 계획을 읽었다.

- 운영자 지정과 저자 지정은 런타임이 도구를 부르기 직전에 스스로 판정하는 길이라 함께 둘 수 있다. 지금의 승인 게이트가 같은 자리에서 두 층을 차례로 본다. `src/agent_os/core/rules.py`의 `applied_rule`은 운영자의 deny → 저자의 `requires_approval` → 운영자의 ask → 운영자의 allow → `default` 차례이고, 운영자의 allow가 저자의 `requires_approval`을 풀지 못한다(코드를 읽었다).
- 도구 서버의 응답은 도구 서버가 질문한 사람이 익명인지 알아야 성립한다. 그것을 알리는 principal-propagation은 슬라이스 10의 todo이고 mcp-trust(슬라이스 10, todo)를 기다린다(`.scratch/plan.md` 75·77행). 그 기능 계획은 주체의 형식을 문서 검색 서버 저장소의 doc-permission 설계 인터뷰와 함께 맞추기로 했고 그 인터뷰는 아직 열리지 않았다고 적는다. 같은 글에 "익명 주체인지가 형식에 실려야 한다"가 있다.
- MCP 2025-11-25 규격에는 서버가 "주소에서 무언가를 마쳐야 요청을 처리할 수 있다"고 알리는 오류 `URLElicitationRequiredError`(코드 -32042)가 있다(앞선 조사가 받아 둔 사본 `dl2\mcp_elicit_1125.md` 422행에서 이 세션이 봤다). 이 저장소의 MCP 클라이언트가 그것을 다루는지는 보지 않았다.

대화를 넘겨받는 답이 닿는 자리도 함께 봤다(코드를 읽었다).

- 대화는 시작 이벤트의 `previous_run`으로 이어진 실행의 고리이고 실행마다 주체가 적힌다. `src/agent_os/core/continuation.py` 251~254행은 앞 실행의 시작 이벤트 주체가 요청한 주체와 다르면 `DifferentPrincipal`을 던진다. 고리를 거슬러 읽다 주체가 다른 실행을 만나면 `PluginError`다(`.claude/rules/core.md`의 이어 가기 판정).
- `src/agent_os/http/sites.py`는 필수 주장 다섯(47행)과 `nbf`만 읽고, 주체를 `발급자|sub`로 짓는다(158~171행). 그 밖의 주장은 읽지 않는다.
- 위젯은 대화를 sessionStorage에 두고(`web/apps/widget/lib/storage.ts` 1~17행. 결말이 있는 교환은 요청 글까지 저장하고, 실행이 서기 전에 거절된 교환과 입력창의 글은 저장하지 않는다), 토큰의 발급자나 `sub`가 저장한 것과 다르면 맞지 않는 것으로 본다(`components/pages/useConversation.ts` 140행의 `sameBundle`).
- 관리 화면은 실행마다 주체를 보인다(`web/apps/admin/components/organisms/RunList.tsx` 275·333행, `RunDetail.tsx` 76행).
- 실패 원인의 닫힌 목록은 `src/agent_os/sdk/events.py` 166행의 `FailureCause`다.

### 계기의 범위

질문: "세 가지 계기 가운데 0.1 판에 어디까지 만들까요?"

> 사용자: "운영자 지정만 0.1 판, 나머지 둘은 뒤 판 (Recommended)"

— 설명: 0.1 판에는 운영자가 규칙 파일에 '로그인한 사람만 쓰는 도구'를 적는 방식 하나를 만들고, '에이전트를 만든 사람이 지정'과 '도구 서버의 응답'은 각각 뒤 판의 새 기능으로 계획표에 올립니다. 어느 계기든 '로그인이 필요해 답변이 끝났다'는 같은 신호로 화면에 전달되게 만들 계획이어서, 뒤에 계기를 더해도 화면과 로그인 흐름은 고치지 않습니다(어림: 설계의 의도이고 만들어 보지는 않았습니다). 추천하는 까닭은 질문 도중 로그인이 이 기능에서 이미 가장 큰 부분이기 때문입니다(규칙 파일, 실행 기록, 위젯, 대화 넘겨받기를 모두 고칩니다).

이 답으로 새 기능 행이 둘 더 는다(저자가 매니페스트에 적는 로그인 요구, 도구 서버의 응답이 일으키는 로그인 요구. 뒤의 것은 principal-propagation을 기다린다).

### 스스로 로그인할 때의 대화

질문: "'로그인하고 질문하기' 단추로 스스로 로그인할 때도 로그인 전의 대화를 넘겨받게 할까요?"

> 사용자: "어느 경우든 로그인하면 대화를 넘겨받기 (Recommended)"

— 설명: 로그인 요구를 받아 로그인하든 단추를 눌러 스스로 로그인하든, 로그인 전의 대화가 화면에 남고 이어서 질문할 수 있습니다. 규칙이 하나라 화면의 동작을 예상하기 쉽고, 넘겨받는 장치를 한 번 만들어 두 곳에 씁니다. 앞에서 정한 '스스로 로그인하면 익명일 때의 대화는 화면에서 지워지고 새 대화로 시작한다'를 이 답으로 바꿉니다. 서버의 지나간 기록은 고치지 않습니다. 익명일 때의 답변은 익명으로, 로그인 뒤의 답변은 로그인한 사람으로 남습니다.

라운드 3의 "로그인하면 익명일 때의 대화는 화면에서 지워지고 새 대화로 시작"이 이 답으로 바뀐다. 다만 넘겨받는 장치는 아래 답으로 갈린 새 기능 행의 몫이라, 기본 로그인만 들어간 동안에는 스스로 로그인하면 대화가 지워진다(지금 위젯의 동작 그대로다).

> 사용자: "항목 이름으로 가르기: 같은 항목이면 함께, 따로 적으면 따로 (Recommended)"

— 설명: 설정 파일에 회사 로그인 서버를 이름을 붙인 항목으로 적고, 사이트가 그 이름을 가리킵니다. 같은 항목을 가리키는 사이트끼리는 한 번 로그인하면 모두 로그인된 상태가 되고, 화면의 사이트 선택 상자로 사이트를 바꿔도(지금 페이지 이동 없이 바뀝니다) 다시 로그인하지 않습니다. 로그아웃하면 그 사이트들에서 함께 로그아웃됩니다. 따로 로그인하게 하고 싶으면 주소가 같은 항목을 이름만 달리해 두 개 적습니다. 스위치를 따로 두지 않아 코드의 갈래가 늘지 않습니다. 치르는 값은 따로 쓰려면 항목을 한 번 더 적고 회사 로그인 서버에 '로그인 뒤 돌아오는 주소'를 하나 더 등록해야 한다는 것입니다(돌아오는 주소를 항목 이름마다 하나로 만들기 때문입니다). Agent OS의 기록에는 어느 쪽이든 지금처럼 사이트마다 다른 사람으로 적힙니다(설정이 사이트마다 발급자가 다르도록 강제하기 때문입니다).

질문: "로그인 유지 시간이 끝났을 때 화면이 어떻게 동작하게 할까요?"

> 사용자: "만료를 알리고 다시 로그인하게 하기 (Recommended)"

— 설명: 유지 시간이 끝난 뒤 다음 질문을 보내려는 순간, 화면에 '로그인 시간이 끝났습니다'와 '다시 로그인' 단추가 뜹니다(위젯은 질문을 보낼 때마다 질문 페이지에서 짧은 토큰을 새로 받는데, 그때 로그인이 끝난 것을 알게 됩니다). 같은 사람으로 다시 로그인하면 대화가 그대로 남아 이어집니다(위젯은 질문하는 사람이 같으면 저장한 대화를 지우지 않습니다). '둘 다' 사이트에는 '로그인 없이 계속' 단추도 함께 두고, 그것을 누르면 익명의 새 대화로 시작합니다. 익명으로 바뀌는 것을 사람이 알고 고릅니다.

질문: "로그인할 때 화면을 어떤 방식으로 회사 로그인 서버에 보낼까요?"

> 사용자: "같은 탭에서 회사 로그인 화면으로 이동 (Recommended)"

— 설명: 로그인 단추를 누르면 지금 탭이 회사 로그인 화면으로 갔다가 질문 페이지로 돌아옵니다. 팝업 차단의 영향을 받지 않고 휴대폰에서도 같은 방식으로 동작합니다. 대화는 위젯이 브라우저의 탭 저장소에 넣어 두기 때문에 돌아온 뒤에도 남습니다(지금도 새로 고침에 대화가 남는 방식입니다. 다른 사이트에 다녀온 뒤에도 남는지는 브라우저의 표준 동작으로 알고 있으나 재지 않았습니다, 어림). 치르는 값은 로그인 요구로 막힌 질문을 돌아온 뒤 자동으로 다시 보내도록 위젯의 저장 내용에 '다시 보낼 질문' 표시를 더해야 한다는 것입니다(지금 위젯은 끝난 질문의 글은 저장하지만 다시 보내라는 표시는 없습니다).

sessionStorage가 다른 출처에 다녀온 뒤에도 남는지는 어림이다. 명세 단계에서 가짜 로그인 서버를 거치는 e2e로 잰다.

질문: "Agent OS가 '이 사람은 로그인하지 않은 사람'임을 무엇으로 알아보게 할까요?"

> 사용자: "토큰에 '로그인으로 확인한 사람' 표시를 넣기 (Recommended)"

— 설명: 질문 페이지가 Agent OS에 보내는 서명된 토큰에 '이 사람은 로그인으로 확인했다'는 항목을 하나 더합니다. Agent OS는 그 항목이 있는 토큰만 로그인한 사람으로 보고, 항목이 없으면 로그인하지 않은 사람으로 봅니다. 그래서 이 기능을 모르는 옛 토큰이나 다른 사이트의 토큰은 '로그인한 사람만 쓰는 도구'에서 막히는 쪽으로 동작합니다(안전한 쪽입니다). 치르는 값은 토큰 형식에 선택 항목이 하나 늘어난다는 것이고(계약의 변경입니다. 지금 Agent OS는 필수 항목 다섯과 시간 항목 하나만 읽고 나머지는 읽지 않습니다), 위젯을 자기 사이트에 넣어 쓰는 다른 사이트도 로그인한 사람용 도구를 쓰려면 이 항목을 넣어야 합니다. 뒤 판의 '질문한 사람을 도구 서버에 전달하는 기능'도 익명인지를 알아야 한다고 그 계획에 적혀 있어서 같은 항목을 쓸 수 있습니다(어림: 그 기능의 설계는 아직 하지 않았습니다).

이 답과 함께 사용자가 되물었다.

> 사용자: 근데 로그인 토큰이 있으면 식별자가 있으니 자동으로 알수 있는거 아니야?
> 아니 로그인 토큰 자체가 로그인을 판단할 수 있는거아닌가?

답하려고 본 것: `web/apps/portal/server/token.ts` 21~25행(익명 주체도 `anon-`에 해시를 붙인 식별자를 갖는다)과 35~36행(익명이든 아니든 같은 함수가 `iss`와 `sub`를 넣어 토큰을 짓는다). 회사 로그인 서버가 준 ID 토큰은 질문 페이지 서버까지만 오고 Agent OS에는 가지 않는다(`/end-user` 아래는 사이트가 서명한 토큰만 연다, `.claude/rules/http.md`). 그래서 Agent OS가 받는 토큰은 두 경우에 모양이 같고, 식별자가 있다는 것만으로는 가르지 못한다. 이 설명을 넣어 같은 결정을 한 번 더 확인받는다.

### 셋째 화면

위 되물음에 답한 뒤 질문 둘을 올렸다. 올리기 전에 대 본 것은 위 `token.ts`의 두 자리와, `.claude/rules/core.md`의 "거부는 실행을 끝내지 않는다"(거부된 호출의 결과가 모델에 돌아가 계속한다)와 "실패한 실행은 고리에 들지 않으므로 같은 앞 실행으로 다시 이어 가는 것이 곧 다시 시도다"이다.

질문: "Agent OS는 질문 페이지가 만든 토큰만 받고, 그 토큰에는 익명인 사람에게도 식별자가 들어갑니다. 로그인 여부를 무엇으로 가르게 할까요?"

> 사용자: "질문 페이지가 토큰에 '로그인으로 확인함'을 적기 (Recommended)"

— 설명: 질문 페이지는 회사 로그인 서버의 토큰을 직접 받으므로 로그인 여부를 압니다. 그 사실을 Agent OS에 보내는 토큰에 한 항목으로 적습니다. 항목이 없는 토큰은 로그인하지 않은 사람으로 봅니다. 그래서 틀리더라도 '로그인한 사람만 쓰는 도구'가 막히는 쪽으로 틀립니다(안전한 쪽입니다). 식별자의 모양에 기대지 않으므로, 위젯을 자기 사이트에 넣어 쓰는 다른 사이트의 계정 이름이 어떤 모양이든 같은 규칙으로 동작합니다. 치르는 값은 토큰 형식에 선택 항목이 하나 늘어난다는 것입니다(계약의 변경입니다. 지금 Agent OS는 필수 항목 다섯과 시간 항목 하나만 읽습니다). 뒤 판의 '질문한 사람을 도구 서버에 전달하는 기능'도 익명인지를 알아야 한다고 그 계획에 적혀 있어서 같은 항목을 쓸 수 있습니다(어림: 그 기능의 설계는 아직 하지 않았습니다).

둘째 화면의 답과 같은 결정이다. 되물음에 답한 뒤 다시 확인받았다.

질문: "익명인 사람의 질문이 '로그인한 사람만 쓰는 도구'에 닿았을 때, 그 답변을 어떻게 끝낼까요?"

> 사용자: "그 자리에서 답변을 끝내고 로그인 안내를 보이기 (Recommended)"

— 설명: 도구를 실행하지 않고 그 답변을 거기서 끝냅니다. 화면에는 '이 질문에 답하려면 로그인이 필요합니다'와 로그인 단추가 뜹니다. 로그인하고 돌아오면 같은 질문이 자동으로 다시 보내지고, 앞의 대화에 이어서 답이 나옵니다. 끝난 답변은 기록에 '로그인이 필요해 끝남'이라는 새 사유로 남고, 대화의 흐름에는 들지 않습니다(지금도 실패로 끝난 답변은 대화의 흐름에 들지 않고, 같은 앞 답변에 이어 다시 보내는 것이 다시 시도입니다). 로그인을 제공하지 않는 익명 전용 사이트에서는 단추 없이 '이 사이트에서는 답할 수 없는 질문입니다'라는 안내만 보입니다. 치르는 값은 실행 기록의 끝난 사유에 값이 하나 늘어난다는 것(계약의 변경)과, 모델이 그 도구 없이 답할 수 있었던 부분까지 함께 끊긴다는 것입니다.

## 합의 요약(확인받음)

아래 요약을 본문으로 올리고 "이 합의 요약대로 설계 문서(ADR) 초안을 쓸까요?"를 물었다.

> 사용자: 이대로 진행

고친 곳 없이 확인받았다. "다"의 열 가지는 질문으로 올리지 않고 이 요약으로 확인받은 것이다.

frontier가 비어 요약을 올렸다. 올리기 전에 더 본 것: `web/apps/portal/server/handler.ts` 223~240행(고지 확인의 상태는 익명 쿠키가 있는지로 답하고, 확인하면 그 쿠키를 낸다. 곧 익명 쿠키가 고지 확인의 기록이다), `config.ts` 63·117행(`schema_version`은 글자 "1"이어야 한다), `docs/adr/`의 마지막 번호가 0058이라는 것.

### 가. 기본 로그인(기능 행 portal-login, 0.1 판)

1. 로그인 방식은 OIDC 하나다. 질문 페이지 설정에 방식 이름 칸을 두어 구조는 열어 둔다. 클라이언트는 `openid-client`이고 ID 토큰의 서명 검사를 켜며, 로그인 서버 주소는 `https`만 받는다.
2. 로그인 서버는 설정에 이름을 붙인 항목으로 적고 사이트가 그 이름을 가리킨다. 같은 항목을 가리키는 사이트끼리는 로그인과 로그아웃을 함께 한다. 따로 쓰려면 주소가 같은 항목을 이름만 달리해 적는다. 로그인 뒤 돌아오는 주소는 항목마다 하나다.
3. 회사 로그인을 통과한 모든 계정이 질문할 수 있다. 질문 페이지는 더 가르지 않는다.
4. 식별자는 운영자가 설정에서 고른 주장이고 기본은 `sub`다. 그 주장이 없으면 로그인을 거절한다. 회원 정보는 보관하지 않고 식별자만 Agent OS에 전한다. 기록의 주체는 지금처럼 사이트마다 다르다.
5. 로그인 상태는 브라우저의 서명된 쿠키에 둔다(서버는 무상태 그대로다). 유지 시간의 기준은 운영자가 고른다. 기본은 로그인한 시각부터 8시간(값을 바꿀 수 있다)이고 다른 하나는 ID 토큰의 만료다.
6. 로그인은 같은 탭이 로그인 서버로 갔다가 돌아오는 이동이다.
7. 화면은 로그인 서버가 준 이름(없으면 계정 이름, 그것도 없으면 "로그인됨")과 로그아웃 단추를 보인다. 로그아웃 방식은 로그인 서버 항목마다 고른다. 기본은 질문 페이지의 로그인 쿠키만 지우고, 다른 하나는 로그인 서버에서도 함께 로그아웃한다.
8. 유지 시간이 끝나면 다음 질문을 보내려는 때 만료를 알리고 다시 로그인하게 한다. 둘 다 사이트에는 "로그인 없이 계속"을 함께 두고, 고르면 익명의 새 대화다.
9. 로그인한 사람도 고지를 사이트마다 한 번 확인한다. "질문이 로그인한 계정과 함께 기록된다"는 문장은 질문 페이지가 늘 고지에 넣는다.
10. 익명 사이트를 로그인 사이트로 바꿀 때 남는 익명 토큰은 짧은 공백(최대 약 2분 30초)을 받아들이고, 배포 안내에 서명 키를 바꾸는 절차를 적는다.
11. 사용자의 그룹은 회사 로그인 시스템에서 온다(0.1 판에서는 방향만 잡는다).

### 나. 질문 도중 로그인(새 기능 행, 0.1 판, 기본 로그인 뒤)

1. 계기는 운영자가 규칙 파일에 적는 "로그인한 사람만 쓰는 도구"다.
2. 런타임은 토큰의 "로그인으로 확인함" 표시로 로그인 여부를 가른다. 표시가 없으면 로그인하지 않은 사람이다.
3. 익명인 사람의 실행이 그 도구에 닿으면 도구를 부르지 않고 실행을 그 자리에서 끝낸다. 화면에는 로그인 안내와 단추가 뜬다. 로그인을 제공하지 않는 익명 사이트에서는 안내만 뜬다.
4. 로그인하고 돌아오면 같은 질문을 자동으로 다시 보내고, 로그인 전의 대화에 이어 답한다(대화 넘겨받기). 스스로 로그인할 때도 대화를 넘겨받는다.
5. 지나간 기록은 고치지 않는다. 익명일 때의 실행은 익명 주체로, 로그인 뒤의 실행은 로그인한 주체로 남는다.

### 다. 이 세션이 제안한 세부(질문으로 올리지 않은 것)

1. 넘겨받기는 익명에서 로그인으로 가는 한 방향뿐이다. 질문 페이지가 로그인한 사람의 토큰에 "이 브라우저의 익명 식별자"를 적고, 런타임은 그 식별자의 대화만 잇게 한다. 넘겨받은 첫 실행의 시작 이벤트에 넘겨받은 익명 주체를 적고, 관리 화면은 그 실행에 한 줄로 보인다.
2. 로그아웃하면 화면의 대화를 지운다. 익명인 사람은 로그인한 사람의 대화를 이어 갈 수 없다.
3. 한 도구에 로그인 요구와 승인 요구가 함께 걸리면 로그인 요구를 먼저 본다.
4. 고지 확인은 지금처럼 브라우저의 사이트별 쿠키로 기억한다. 익명일 때 확인했으면 로그인한 뒤 다시 묻지 않고, 다른 PC에서는 다시 확인한다.
5. 기본 로그인만 들어간 동안에는 둘 다 사이트에서 스스로 로그인하면 대화가 지워진다(지금 위젯의 동작). 질문 도중 로그인이 들어가면 넘겨받기로 바뀐다.
6. `anon-`으로 시작하는 계정 식별자는 로그인을 거절한다(ADR 0050이 넘긴 요건).
7. 시험용 가짜 로그인 서버는 프로브의 것을 바탕으로 직접 짓고 `https`로 띄우며, 로그아웃 기능을 더한다.
8. 비밀 값(클라이언트 비밀 등)은 설정 파일에 직접 적지 않고 파일 경로로 가리킨다(지금의 서명 키와 같은 방식).
9. 새 기능 행의 이름은 `step-up-login`이다.
10. 수락 기준. 기본 로그인: 사내 로그인 하나를 흉내 낸 시험 환경에서 로그인한 사람만 calc 예시에 질문할 수 있고 트레이스의 주체가 그 사람이다(기능 계획 그대로). 질문 도중 로그인: 둘 다 사이트에서 익명으로 calc 예시에 질문하다가 로그인한 사람만 쓰는 도구에 닿으면 로그인 안내가 뜨고, 로그인한 뒤 같은 대화에 이어 답이 나오며, 트레이스에 넘겨받은 사실이 남는다.

### 라. 계약이 바뀌는 자리

기본 로그인은 Agent OS의 계약을 바꾸지 않는다. 질문 페이지 설정에 칸이 늘고 의존성 `openid-client`(패키지 셋)가 는다. 질문 도중 로그인은 다섯 자리를 바꾼다. 규칙 파일의 줄 종류 하나, 이벤트의 값과 칸(적용 규칙의 값 하나, 실패 원인의 값 하나, 시작 이벤트의 넘겨받은 주체 칸 하나), 사이트 토큰의 선택 주장 둘(로그인으로 확인함, 넘겨받을 익명 식별자), 위젯의 공개 표면(페이지가 로그인을 맡는 통로 하나)과 저장 형식(다시 보낼 질문의 표시), 그리고 그것들이 드러나는 `openapi.json`이다.

### 마. 뒤 판에 새 기능 행으로 올리는 것

LDAP 로그인, refresh token으로 로그인 상태를 다시 확인하기, 저자가 매니페스트에 적는 로그인 요구, 도구 서버의 응답이 일으키는 로그인 요구(principal-propagation 뒤).

### 바. 명세로 미루는 것

설정 칸의 이름, 끝점 경로와 프록시 규칙, 쿠키 서명 키의 자리, 함께 로그아웃을 지원하지 않는 로그인 서버에서의 동작, sessionStorage가 로그인 서버에 다녀온 뒤 남는지의 측정, `|`가 든 식별자의 처리, 주장과 칸의 이름.

합의 요약을 원천으로 아래를 썼다. 쉬운 말은 용어집의 말로 옮겼고 조건은 빼지 않았다.

- `CONTEXT.md`: 새 용어 일곱(로그인 서버, 로그인 서버 항목, 로그인 상태, 로그인 주체, 로그인 확인 표시, 로그인 요구, 대화 넘겨받기)을 더하고 로그인 모드를 손질했다. 규칙 파일·적용 규칙·실패 원인·대화·이어 가기 항목은 지금의 코드를 적은 글이라 고치지 않았고, step-up-login의 구현 티켓이 코드와 함께 고친다(ADR 0060 Consequences).
- ADR 초안 둘: ADR 0059(기본 로그인. `portal-login`의 설계 줄)와 ADR 0060(질문 도중 로그인과 대화 넘겨받기. `step-up-login`의 설계 줄). 둘로 나눈 까닭은 기능 행이 둘이고 계약을 바꾸는 일이 뒤의 것에 모여 있기 때문이다.
- ADR 0050에 포인터 여덟(ADR 0059 일곱, ADR 0060 하나)을 달았다. 다른 ADR의 포인터 대상은 서브에이전트에 맡겨 찾았다(0001~0058 가운데 열쇠말 grep에 걸린 것과 이름으로 든 것의 본문을 읽었다고 보고했고, 열어 보지 않은 ADR의 번호도 보고에 있었다). 보고가 든 열네 자리에 ADR 0060의 포인터 열다섯을 달았다. ADR 0044에 일곱, ADR 0022에 셋, ADR 0023에 셋, ADR 0024에 하나, ADR 0042에 하나다(ADR 0022의 둘은 한 항목 안의 떨어진 두 문장이다). 셀프 리뷰 뒤에 둘을 더 달았다(ADR 0022의 "노출면이 새로 생기지 않는다", ADR 0009의 "거부는 실행을 끝내지 않는다". 아래 "셀프 리뷰"). 문장은 Edit의 글자 그대로 일치로 확인했다. 보고가 짚은 초안의 어긋남 둘(ADR 0031과 ADR 0023의 본문에는 값이나 주장을 세어 적은 문장이 없다는 것, 두 초안이 `serve`가 읽는 주장을 다르게 적은 것)을 고쳤다. `uv run python tools/check_adr_pointers.py`는 포인터를 달기 전에 0으로 끝났고, 단 뒤의 것은 아래 검증에 적는다.
- ADR 0046에 이력 "질문 도중 로그인이 기준선의 행이 된다"를 쌓았다. admin-login을 기준선에 더한 2026-11-11 이력과 같은 꼴이다.
- 기능 계획: `portal-login`에 설계 줄을 적고 본문을 고쳤다. 새 기능 계획 다섯(`step-up-login`, `portal-ldap-login`, `portal-login-recheck`, `author-login-requirement`, `server-login-requirement`)을 만들었다. 넘겨 적은 곳은 `pilot-release`(step-up-login을 기다린다), `deploy-package`(로그인 서버 준비물), `principal-propagation`(로그인 확인 표시, 식별자, 그룹의 방향), `admin-login`(다시 쓸 수 있는 조사), `portal-admin`(화면에서 로그인 방식 고르기)이다. `uv run python tools/plan_table.py`가 0으로 끝났고 새 행 다섯이 표에 생긴 것을 `.scratch/plan.md`에서 봤다.
- 프로브 README의 "근거로 드는 자리" 칸을 채웠다.

### 합의 요약에 없어 이 세션이 채운 것

ADR을 쓰며 합의 요약이 정하지 않은 자리가 나왔다. 아래는 이 세션이 채운 것이고 ADR 승인 화면에서 따로 확인받는다.

ADR 0059

1. 만료 알림과 "다시 로그인"·"로그인 없이 계속" 단추는 위젯이 아니라 질문 페이지가 그린다. 그래서 기본 로그인은 위젯의 공개 표면을 바꾸지 않는다.
2. 새 끝점(로그인 시작, 돌아오는 곳, 로그아웃)은 모두 `/portal/` 아래에 두어 프록시 규칙을 바꾸지 않는다.
3. 로그인 도중의 값(`state`, `nonce`, PKCE 검증 값)도 서버에 두지 않고 짧게 사는 쿠키에 둔다.
4. 로그인 상태는 고지 확인 전에도 생길 수 있지만(로그인은 항목 단위, 확인은 사이트 단위) 사이트 토큰은 확인 뒤에만 낸다.
5. `docs/constitution/tech.md`의 웹 행은 `openid-client`를 설치하는 티켓이 고친다.
6. 새 행의 이름 `portal-ldap-login`과 `portal-login-recheck`, 슬라이스 10, pilot-release를 기다림.
7. 식별자로 쓸 주장과 유지 시간의 기준·길이를 로그인 서버 항목마다 둔다(합의는 로그아웃 방식만 "항목마다"라고 적었다. 셀프 리뷰가 목록에서 빠졌다고 짚었다).
8. 둘 다 사이트에서 로그인 상태가 끝났을 때 익명 토큰을 말없이 내지 않는다는 것을 결정에 적었다(사용자가 고른 설명의 조건 "익명으로 바뀌는 것을 사람이 알고 고릅니다"를 옮긴 것이다). 끝난 로그인 상태를 가르는 방법은 명세로 미뤘다.
9. 만료를 알게 된 그 질문은 다시 로그인한 뒤 화면에 없고 다시 적는다(셀프 리뷰의 열린 가지. 승인 화면에서 따로 묻는다).

ADR 0060

1. 로그인 요구는 최종 사용자의 실행에만 건다. 운영자 채널과 CLI의 실행에는 따지지 않는다.
2. 집행의 차례에서 운영자의 deny가 로그인 요구보다 먼저다(합의는 로그인 요구가 승인 요구보다 먼저라는 것만 정했다).
3. 로그인 확인 표시는 요청마다 토큰에서 읽고 트레이스에 따로 적지 않는다.
4. 승인을 기다리며 멈춘 사이 로그인 요구가 걸리면 재개 때 실행을 끝낸다.
5. 같은 질문을 다시 보내는 것은 한 번이다.
6. 넘겨받기의 판정(같은 발급자 안에서만, 요청 토큰에 로그인 확인 표시가 있을 때만)과, 고리를 거슬러 읽을 때 넘겨받은 주체가 적힌 경계는 손상이 아니라는 것.
7. 위젯은 새 토큰의 넘겨받을 익명 주체가 저장한 대화의 `sub`와 같으면 대화를 지우지 않는다.
8. 새 행의 이름 `author-login-requirement`와 `server-login-requirement`, 그리고 step-up-login이 기준선의 행이 되어 pilot-release가 기다린다는 것(ADR 0046 이력).
9. 로그인 요구의 배열을 규칙 파일의 공통 표와 에이전트별 표 둘 다에 둔다(셀프 리뷰가 목록에서 빠졌다고 짚었다).
10. 다시 보낼 질문의 표시는 그 교환이 대화의 마지막 교환인 동안만 산다. 로그인하지 않고 돌아오면 안내가 남고, 안내가 마지막 교환으로 남아 있는 동안 뒤에 로그인하면 그때 다시 보내며, 그 사이에 다른 질문을 보냈으면 표시를 지운다(셀프 리뷰의 열린 가지).
11. 돌거나 멈춘 익명 실행은 넘겨받지 않는다. 위젯은 그 교환을 끝내지 못한 교환으로 닫고 앞서 끝난 교환들만 남긴다(셀프 리뷰의 Major. 승인 화면에서 따로 묻는다).
12. 다시 보낸 실행이 끝난 실행에서 이미 부른 도구를 다시 부를 수 있다는 것을 대가로 적었다(결정이 아니라 고른 설계의 귀결이다).

6. Minor, ADR 0060 20행 "새 신뢰가 생기지 않는다"의 반례. ADR 0054 13행 "익명 주체에게는 기억을 쓰지 않는다"가 막던 공용 PC 앞사람의 교환이 로그인 주체의 대화에 들어 기억의 재료가 된다. ADR 0022 38행 "노출면이 새로 생기지 않는다"에는 포인터가 없다.
7. Minor, ADR 0060 16행. 로그인 요구는 실행을 끝내는데 ADR 0009 29행 "거부는 실행을 끝내지 않는다"에 포인터가 없고 ADR 0060의 "다른 ADR" 목록에도 없다.
8. Minor, `CONTEXT.md` 532행과 ADR 0060 8행 "…최종 사용자의 실행만 부를 수 있는". ADR 0060 14행(운영자 채널과 CLI의 실행에는 따지지 않는다)이 반례다.
9. Nit. ADR 0059 34행의 "그 폴더의 `README.md`"는 `.scratch/portal-login/probes/README.md`다. 이 일지 산출물 절의 "열넷"은 내역의 합이 열다섯이다.

열린 가지(합의도 ADR도 정하지 않은 것) 넷. 만료를 알게 된 그 질문을 다시 로그인한 뒤 다시 보내는지(위젯은 거절된 교환을 저장하지 않는다). 자동으로 다시 보낸 실행이 끝난 실행에서 이미 부른 도구를 다시 부르는 것. 로그인을 취소한 뒤 남은 "다시 보낼 질문"이 나중의 로그인에 뒤늦게 나가는지. 로그인한 채 한 고지 확인이 익명 식별자 쿠키를 내는지.

### 표준 축의 보고

행 번호는 보고를 받은 때의 것이다.

1. Major, ADR 0022 38행 "노출면이 새로 생기지 않는다"에 `(바뀜: ADR 0060)`이 없다. ADR 0060의 Consequences가 스스로 그 문장의 범위가 바뀐다고 적었는데 "다른 ADR" 목록의 "ADR 0022의 세 곳"에는 없다(`.claude/rules/adr.md` 첫 항목).
2. Minor, ADR 0060 18행 "로그인은 사이트의 일이고(ADR 0047)". ADR 0047에는 로그인이 없고 위젯의 외형과 문구를 위젯과 사이트가 가진다고만 적는다. 근거 인용이 범위를 넓혔다.
3. Minor, ADR 0059 15행 "주장 다섯과 수명 120초는 그대로다"와 8행 "계약은 바꾸지 않는다"는 ADR 0060이 선택 주장 둘을 더하고 위젯의 표면을 바꾸면 범위가 달라진다. 앞을 가리키는 말은 54행에만 있다.
4. Minor, `CONTEXT.md` "로그인 요구"의 정의가 "운영자가 규칙 파일에 적어 둔 도구들"인데 `author-login-requirement`와 `server-login-requirement`의 기능 계획은 같은 용어로 저자와 도구 서버가 일으키는 요구를 가리킨다. 정의가 계기 셋을 포괄하지 않는다.
5. Minor, 피할 말. ADR 0060 49행 "로그인으로 확인한 사용자의 토큰"과 ADR 0059 22행 "사용자의 그룹"은 최종 사용자여야 한다. ADR 0059 8·15·30행의 "회원 정보"와 "회원 표"는 로그인 주체 항목의 피할 말 "회원"과 글자가 같지만 다른 개념이라 판단 사항이다.
6. Nit, ADR 0059 34행. 일지의 `oauth4webapi`와 `@azure/msal-node`의 내려받기 수(둘 다 `openid-client`보다 크다)와 그 사정이 본문에 없어 "별개의 대안은 찾지 못했다"가 최다 사용으로 읽힌다.
7. Nit, ADR 0060 35행 "ChatGPT … 계정으로 옮겨진다"가 일지 조사의 표현보다 강하다.
8. Nit, ADR 0059 48행 "익명 식별자 쿠키 … 결정은 그대로다"와 같은 항목이 든 ADR 0050 결정 "익명 식별자 쿠키"의 포인터가 어긋난다.
9. Nit, `principal-propagation` 기능 계획과 ADR 0050 17행이 "portal-login 기능 계획"을 가리키는데, 그 문장이 portal-login 본문에서 빠지고 ADR 0059로 옮겨 가 가리키는 자리가 약해졌다.

문제없다고 본 것: 포인터의 수와 자리 묘사가 ADR 0059와 0060의 서술과 맞다(0059→0050 일곱, 0060→0044 일곱·0042 하나·0022 셋·0023 셋·0024 하나·0050 하나). `tools/check_adr_pointers.py`가 0으로 끝났고 `tools/check_md_tables.py`, `tools/check_line_separators.py`, `tools/check_instructions.py`가 출력 없이 끝났으며 `tests/test_plan_status.py` 13개가 통과했다. ADR 0031과 ADR 0023의 본문에 값이나 주장을 세어 적은 문장이 없다는 것(0023의 "필수 클레임" 문장은 이력 아래다), ADR 0009의 2026-11-05 이력 인용이 글자 그대로라는 것, 코드의 서술(`sites.py`, `applied_rule`, `continuation.py`, `drivers.ts`, `handler.ts`, `config.ts`, `buildEndSessionUrl`)이 지금 코드와 맞다는 것, 프로브의 수가 README와 같고 잰 범위 밖으로 넓힌 문장을 찾지 못했다는 것, ADR 0046의 이력과 기능 계획의 모양과 색인의 새 행이 맞다는 것, 프로브 TypeScript에 타입 우회가 없다는 것이다.

한 줄 요약: 표준 축은 Major 1·Minor 4·Nit 4이고 가장 무거운 것은 ADR 0022의 빠진 포인터다. 명세 축은 Major 1·Minor 6·Nit 2에 열린 가지 넷이고 가장 무거운 것은 돌거나 멈춘 실행 중에 로그인하면 넘겨받은 대화가 지워지는 것이다.

### 반영

지적마다 근거를 먼저 열었다. 명세 축 1은 `web/apps/widget/components/pages/drivers.ts`의 `restore`(묶음이 같으면 대화를 되돌리고 `saved.reattach`가 있으면 다시 붙는다)와 `web/apps/widget/lib/rejection.ts`의 `subscriptionStep`(둘째 404가 `vanished`)을 읽어 사실로 봤다. 명세 축 7은 ADR 0009 29행을, 6은 ADR 0022 38행과 ADR 0054 13행을, 표준 축 2는 ADR 0047에 로그인이 없다는 보고를 받아들이고 ADR 0023 본문에서 근거를 다시 찾았다.

고친 것. 새로 쓴 사실 문장은 PR 직전 리뷰에 밀 주장으로 넘긴다.

- ADR 0060에 결정 "돌거나 멈춘 실행은 넘겨받지 않는다"를 더했다(명세 축 1). 새 문장: "지금 위젯은 페이지가 다시 열리면 저장해 둔 다시 붙을 실행에 새 토큰으로 구독하고, 남의 실행이라 404가 두 번 오면 저장과 화면을 비운다", "위젯은 대화를 넘겨받은 뒤 그 실행에 다시 붙지 않고 그 교환을 끝내지 못한 교환으로 닫는다(지금 위젯의 `unfinished` 결말, `web/apps/widget/lib/conversation.ts`를 읽었다)". 고르지 않은 안(로그인 주체가 구독하고 결정한다)을 Considered Options에 적었다. 설계 결정이라 승인 화면에서 따로 묻는다.
- ADR 0060 "대화 넘겨받기"의 방향 문장을 누가 지키는지로 고쳐 썼다(명세 축 5). 새 문장: "런타임은 앞 실행의 주체가 익명이었는지 보지 않는다(로그인 확인 표시를 트레이스에 적지 않아 볼 수 없다)".
- ADR 0060 Consequences에 사람별 기억과의 관계를 적고 `.scratch/user-memory/plan.md`에 넘겼다(명세 축 6). 새 문장: "저장은 기본이 승인 카드로 묻는 것이라(ADR 0054) 그 사람이 카드에서 거를 수 있고". ADR 0022 38행에 포인터를 달았다(표준 축 1과 같은 지적).
- ADR 0009 29행 "거부는 실행을 끝내지 않는다"에 포인터를 달고 ADR 0060의 "다른 ADR" 목록을 고쳤다(명세 축 7). 처음 포인터 대상을 찾은 서브에이전트는 이 문장을 달지 않는 쪽으로 봤는데, 로그인 요구에 닿은 호출이 거부로 기록되고 그 실행이 끝나므로 본문만 읽으면 지금의 결정을 잘못 알게 된다고 판단했다.
- `CONTEXT.md`의 로그인 요구 정의를 도구에 걸린 제한으로 고쳐 계기가 늘어도 맞게 하고, 운영자가 시작한 실행에는 걸리지 않는다고 적었다(명세 축 8, 표준 축 4). ADR 0060 첫 단락의 굵은 문장도 같이 고쳤다.
- ADR 0060 "같은 질문을 다시 보낸다"에 표시가 사는 동안을 적었다(열린 가지 셋째). Consequences에 "다시 보낸 실행은 처음부터 돈다"를 더했다(열린 가지 둘째). 새 문장: "기본 에이전트가 쓰는 문서 검색 서버의 도구 셋은 읽기 도구라고 ADR 0051이 적었다(결정 "도구 셋의 규칙". 그 ADR도 명세를 읽고 적은 것이다)".
- ADR 0060 18행의 근거를 ADR 0047에서 ADR 0023으로 고쳤다(표준 축 2). 새 문장: "최종 사용자가 누구인지는 사이트가 서명한 토큰으로만 받고(ADR 0023)".
- ADR 0059 "화면"에 로그인 상태가 끝나도 익명 토큰을 말없이 내지 않는다는 조건을 적었다(명세 축 2). 새 문장: "만료를 알게 된 그 질문은 실행이 서기 전에 막힌 것이라 위젯이 저장하지 않으므로(`web/apps/widget/lib/storage.ts`의 머리 주석을 읽었다) 다시 로그인하고 돌아온 화면에 없고, 질문한 사람이 다시 적는다"(열린 가지 첫째. 승인 화면에서 따로 묻는다).
- ADR 0059의 "주장 다섯과 수명 120초는 그대로다"와 첫 단락의 굵은 문장을 "이 결정으로는"으로 한정하고 ADR 0060을 가리키게 했다(표준 축 3). 두 ADR이 한 변경에서 함께 서므로 포인터 대신 문장을 고쳤다.
- ADR 0059와 0060의 "사용자의 그룹", "사용자의 토큰"을 최종 사용자로, "회원 정보"와 "회원 표"를 계정 정보와 계정의 표로 고쳤다(표준 축 5). 고르지 않은 안에는 인터뷰에서 "회원 정보"라 불렀다고 한 번 남겼다.
- ADR 0059의 내려받기 수 문장에 더 큰 두 패키지의 수와 사정을 적었다(표준 축 6). 새 문장: "2026-11-05부터 11-11까지의 주간 내려받기 수는 `@azure/msal-node` 29,685,459, `oauth4webapi` 25,389,873, `openid-client` 23,842,164였다", "`oauth4webapi`는 `openid-client` 6.x가 의존하는 아래층이라 그 수에 `openid-client`의 몫이 들어 있고", "`@azure/msal-node`의 수에 Azure SDK의 몫이 크다는 것은 어림이다". 수는 이 일지의 "조사: Node의 OIDC 클라이언트 사용량"에서 옮겼다.
- ADR 0060의 ChatGPT 문장을 일지 조사의 표현으로 낮췄다(표준 축 7). ADR 0059의 README 경로(명세 축 9), ADR 0050과 어긋난 "그대로다" 문장(표준 축 8), 일지의 포인터 수(명세 축 9)를 고쳤다.
- `.scratch/portal-login/plan.md`에 앞선 문서가 넘긴 요건 둘(`anon-` 접두 금지, 그룹의 방향)을 ADR 0059의 어느 결정이 받았는지 적었다(표준 축 9).
- "합의 요약에 없어 이 세션이 채운 것" 목록에 빠진 결정을 더했다(명세 축 4). ADR 0059에 셋, ADR 0060에 넷이다.

남긴 것과 이유.

- 명세 축 3(끝점을 `/portal/` 아래로 정한 것). 합의 바가 명세로 미룬 항목이지만 프록시 규칙을 늘리지 않는다는 것 하나만 여기서 정한다고 좁혀 적었고, 끝점마다의 경로는 명세에 남겼다. 승인 화면의 목록에서 확인받는다.
- 열린 가지 넷째(로그인한 채 한 고지 확인의 기록). ADR 0059 "명세가 짓는 것"에 넘겼다. 받는 쪽은 portal-login의 명세이고 그 기능 계획이 그 절을 가리킨다.

다시 돌린 명령. 반영하기 전에 `uv run python tools/run_checks.py`가 0으로 끝났고 `uv run ruff check .`와 `uv run ruff format --check .`가 통과했다. 반영한 뒤에는 `uv run python tools/check_adr_pointers.py`, `uv run python tools/plan_table.py`, `uv run python tools/check_md_tables.py`가 출력 없이 끝났다. 손으로 치는 다섯은 커밋의 pre-commit으로 갈음하고 결과는 커밋 뒤에 적는다.

## 승인

셀프 리뷰를 반영한 뒤 승인 화면을 올렸다(답은 2026-11-13 자정을 넘겨 받았다). 본문에 리뷰 결과, 이 세션이 채운 세부의 목록, 대가 둘을 쉬운 말로 적고 질문 넷을 물었다. 올리기 전에 설명의 사실을 댔다. 위젯이 실행이 서기 전에 거절된 교환과 입력창의 글을 저장하지 않는다는 것은 `web/apps/widget/lib/storage.ts`의 머리 주석에서, 위젯이 제 상태를 페이지에 알리는 길이 없다는 것은 `web/apps/widget/EMBED.md` "지킬 것"의 공개 표면 목록에서 읽었다.

질문: "답을 받고 있거나 승인을 기다리는 도중에 '로그인하고 질문하기'를 누르면, 그때 받던 답은 어떻게 할까요?"

> 사용자: "앞 대화는 남기고 받던 답만 포기 (Recommended)"

— 설명: 로그인하고 돌아오면 이미 끝난 질문과 답은 화면에 그대로 남고 이어서 질문할 수 있습니다. 로그인하는 순간에 받고 있던 답(또는 기다리던 승인 카드)만 끝내지 못한 것으로 닫히고, 필요하면 같은 질문을 다시 보냅니다. 서버 쪽 약속(계약)은 더 바뀌지 않고 채팅 창의 동작만 정합니다. 지금 초안이 이 안입니다.

고르지 않은 선택지는 "받던 답도 로그인 뒤 이어 받기"(로그인한 사람이 익명일 때 시작한 실행을 지켜보고 승인하는 예외를 서버에 더한다)와 "답을 받는 동안 로그인 단추 막기"(채팅 창이 제 상태를 페이지에 알리는 길을 하나 더 만든다)였다.

질문: "로그인 시간이 끝난 것을 알게 된 그 질문(보내려던 글)은 다시 로그인한 뒤 어떻게 할까요?"

> 사용자: "다시 적게 두기 (Recommended)"

— 설명: 다시 로그인하고 돌아오면 앞의 대화는 남아 있지만 보내려던 그 글은 화면에 없어 다시 적습니다. 채팅 창은 서버에 닿기 전에 막힌 글과 입력 칸의 글을 저장하지 않기 때문입니다(위젯 저장 코드의 주석을 읽었습니다). 유지 시간(합의하신 기본값은 로그인한 때부터 8시간)이 끝날 때 한 번 겪는 일이고 더 만들 것이 없습니다. 지금 초안이 이 안입니다.

고르지 않은 선택지는 "로그인 뒤 자동으로 다시 보내기"(질문 도중 로그인의 다시 보낼 질문 장치를 같이 쓴다)와 "입력 칸에 글만 남기기"(기본 로그인 단계에서 위젯을 고치게 된다)였다.

질문: "본문에 적은 '제가 채운 세부'(기본 로그인 여덟, 질문 도중 로그인 열) 가운데 바꾸고 싶은 것이 있나요?"

> 사용자: "없음, 그대로 두기 (Recommended)"

— 설명: 목록의 내용이 두 설계 문서에 지금 적힌 대로 남습니다.

질문: "위 답을 반영한 설계 문서 둘(ADR 0059 기본 로그인, ADR 0060 질문 도중 로그인)과, 0.1 판 목록에 둘째 기능을 더한다는 기록(ADR 0046 이력)을 승인할까요?"

— 설명: 위 세 질문에서 고르신 대로 문서를 맞춘 뒤 상태를 '승인됨'으로 바꾸고 커밋, PR, 병합까지 진행합니다. 계약이 바뀌는 다섯 자리(합의 요약의 '라')도 이 승인에 들어갑니다. 추천과 다르게 고르신 것이 있으면 그 부분을 고친 뒤 고친 문장을 다시 확인받고 진행합니다.

### 이 화면으로 확인받은 목록

본문에 올린 글 그대로다. 위 "합의 요약에 없어 이 세션이 채운 것"의 ADR 0059 1~8과 ADR 0060 1~10을 쉬운 말로 옮긴 것이고, 그 목록의 ADR 0059 9와 ADR 0060 11은 위 질문 둘로 따로 물었으며 ADR 0060 12는 대가의 첫째다.

기본 로그인(ADR 0059)

1. 로그인 시간이 끝났다는 알림과 "다시 로그인"·"로그인 없이 계속" 단추는 채팅 창이 아니라 질문 페이지가 그립니다. 그래서 기본 로그인은 채팅 창(위젯)을 고치지 않습니다.
2. 로그인에 쓰는 새 주소들은 지금의 `/portal/` 아래에 두어 프록시 설정을 바꾸지 않습니다. 합의에서는 주소를 명세로 미뤘는데, "프록시 규칙을 늘리지 않는다"는 것 하나만 지금 정했습니다.
3. 로그인하러 다녀오는 동안 필요한 임시 값도 서버에 저장하지 않고 잠깐 사는 쿠키에 둡니다.
4. 로그인은 고지를 확인하기 전에도 할 수 있지만, 질문은 고지를 확인한 뒤에만 할 수 있습니다.
5. 기술 스택 문서는 `openid-client`를 실제로 설치하는 티켓이 고칩니다.
6. 뒤 판 기능 둘의 이름은 `portal-ldap-login`(아이디·비밀번호 로그인)과 `portal-login-recheck`(로그인 상태 재확인)입니다.
7. "어느 값을 식별자로 쓸지"와 "유지 시간"은 로그인 서버 항목마다 따로 정합니다.
8. '둘 다' 사이트에서 로그인 시간이 끝나도 말없이 익명으로 바뀌지 않고, "로그인 없이 계속"을 눌러야 익명이 됩니다(고르신 설명의 조건을 문서에 옮긴 것입니다).

질문 도중 로그인(ADR 0060)

1. "로그인한 사람만 쓰는 도구" 규칙은 채팅으로 질문하는 사람에게만 적용하고, 운영자가 관리 화면이나 명령줄에서 돌리는 실행에는 적용하지 않습니다.
2. 운영자가 아예 막은 도구가 로그인 규칙보다 먼저입니다. 로그인해도 못 쓰는 도구에 로그인 안내를 띄우지 않기 위해서입니다.
3. "로그인으로 확인함" 표시는 요청마다 토큰에서 읽고 기록에 따로 남기지 않습니다.
4. 승인을 기다리며 멈춘 사이에 그 도구에 로그인 규칙이 새로 걸리면, 익명인 사람이 승인해도 도구를 부르지 않고 실행을 끝냅니다.
5. 로그인 뒤 같은 질문을 자동으로 다시 보내는 것은 한 번뿐입니다.
6. 대화 넘겨받기는 같은 사이트 안에서, 로그인한 사람의 요청일 때만 됩니다.
7. 채팅 창은 새 토큰에 적힌 익명 식별자가 화면의 대화 주인과 같을 때만 대화를 지우지 않습니다.
8. 뒤 판 기능 둘의 이름은 `author-login-requirement`와 `server-login-requirement`이고, `step-up-login`이 0.1 판 목록에 들어가 0.1 판 출시가 이것을 기다립니다.
9. 로그인 규칙은 규칙 파일의 "모든 에이전트 공통" 칸과 "에이전트별" 칸 둘 다에 적을 수 있습니다.
10. 다시 보낼 질문은 그것이 대화의 마지막 질문일 때만 다시 보냅니다. 로그인하지 않고 돌아온 뒤 다른 질문을 했으면 지난 질문이 뒤늦게 나가지 않습니다.

결정은 아니지만 알아 두실 대가 둘

- 로그인 뒤 다시 보낸 질문은 처음부터 다시 돌기 때문에, 로그인 규칙에 걸리기 전에 이미 부른 도구가 한 번 더 불릴 수 있습니다. 기본 에이전트의 도구는 읽기뿐이라고 ADR 0051이 적었지만, 무언가를 쓰는 도구를 가진 커스텀 에이전트에서는 그 도구가 두 번 실행될 수 있습니다.
- 공용 PC에서 앞사람이 익명으로 나눈 대화가 화면에 남아 있으면, 뒤에 로그인한 사람이 그 대화를 이어받습니다. 뒤 판의 "사람별 기억" 기능이 이 내용을 걸러야 하는지는 그 기능의 계획에 넘겨 적었습니다.

승인을 받아 ADR 0059와 0060의 `status`를 `accepted`로, 색인의 상태를 같게 바꿨다. `date`는 합의를 확인받고 초안을 쓴 2026-11-12로 둔다(ADR 0046의 이력 제목과 같은 날이다).
