## 측정이 정한 것

행은 "PostToolUse `WebFetch`의 계기 훅"이었다. 무조건 알리기 전에 WebFetch가 늘 요약을 돌려주는지부터 봤다.

- **결과 객체.** 프로브 `webfetch_payload/run.sh`의 A가 저장소 밖 `claude -p`(2.1.296)에서 탐침 훅으로 받은 입력은
  `tool_response`의 키가 `bytes`·`code`·`codeText`·`durationMs`·`result`·`url`이었다. 트랜스크립트의 `toolUseResult`와
  같은 모양이다.
- **본문 통과.** WebFetch는 어떤 문서는 줄이지 않고 그대로 돌려준다. 그 결과는 결과의 UTF-8 바이트 수가 `bytes`와
  정확히 같았다. 셀프 리뷰가 바이트 수만으로는 내용을 대 본 것이 아니라고 짚어, A의 통과 결과를 같은 주소에서 `curl`로
  받은 본문과 스크래치 스크립트로 바이트 단위로 대 봤고 34296바이트 모두 같았다(손으로 봤다). 트랜스크립트(`transcripts.py`)에서 그렇게 가른 두 무리는 결과 길이와 `bytes`의 비가 0.998~1.0과 0.341
  이하로 떨어져 사이에 걸친 것이 없었다(수는 프로브 README 행). 통과한 것은 모두 `code.claude.com` 문서였고, 같은 곳의
  10만 바이트 넘는 문서는 요약이었다. 원인은 Claude Code 코드를 읽지 않아 모른다. 그래서 통과에는 침묵한다. 웹
  요약의 정의(`docs/agents/issue-tracker.md`)가 "작은 모델이 질문에 답하는 도구의 출력"이라 통과는 웹 요약이 아니고,
  침묵하지 않으면 훅이 틀린 말을 한다. 통과는 Claude Code 문서에 몰려 있는데, 이 하네스가 가장 많이 받는 문서다.
- **글자 수가 아니라 바이트.** 대시가 든 문서는 36269자·36277바이트였다. 글자 수로 대면 통과를 요약으로 읽는다.
- **3xx와 404.** 리다이렉트는 `bytes`가 안내문 자체의 크기라 결과와 같아, 통과 판정만으로도 침묵한다. 404는 `bytes`가
  0이라 code를 보지 않으면 요약으로 읽힌다. 그래서 2xx가 아니면 먼저 침묵한다.
- **요약의 새 안내.** 요약 결과 끝에 WebFetch 자신의 영문 안내가 붙었다. 페이지의 앞 100000자만 읽었으니 이어 읽으려면
  같은 주소를 `offset`과 함께 다시 부르라는 내용이다. 훅과는 상관이 없고, 요약이 페이지의 앞부분만 본다는 것을 이
  세션에서 처음 봤다.

## 바꾼 것

- **훅 `tools/hook_webfetch_summary.py`.** 도구 이름이 `WebFetch`가 아니면, code가 2xx가 아니면, 결과의 UTF-8 바이트
  수가 `bytes`와 같으면 침묵한다. 나머지는 "이 WebFetch 결과는 웹 요약이다"로 시작해 받은 바이트와 줄인 글자 수를 들고,
  수와 인용을 근거로 쓰거나 원문 확인이라 말하려면 본문을 내려받아 대 보라고 한다. 결과 객체가 없거나 code·bytes·result의
  타입이 다르면 수 없이 알린다. 막지 않는다.
- **넷.** `.claude/settings.json`의 PostToolUse `WebFetch` 등록, `tests/tools/test_hook_webfetch_summary.py` 열셋,
  `tools/hook_payloads.toml`의 발동 하나(프로브 A의 실제 요약)와 침묵 셋(같은 프로브의 실제 301, 트랜스크립트의 실제 404,
  수만 맞춘 본문 통과). 실제 통과 결과는 3만 바이트가 넘는 남의 문서 본문이라 표에 옮기지 않았고, 실제 입력은 프로브 C가
  본다. `tools/run_hooks.py`는 82건 모두 기대대로였다.
- **실제 세션 확인.** 같은 프로브의 B가 등록 모양(래퍼를 거친 훅)을 붙인 `claude -p`에서 요약 뒤 훅 알림의 첫 문장을
  물었고, 모델이 그 문장을 옮겼다. 대조군 C(본문 통과)는 스트림에 그 문장이 없이 "알림 없음"이었다. 셀프 리뷰를 반영한
  판으로 다시 돌려도 같았다.
- **변이 표** `webfetch_summary_hook_mutations.toml`. 첫 판은 대조군이 빨강이었다. 리다이렉트 테스트가 실제와 다른
  짧은 안내문을 써 `bytes`가 결과와 달랐고, 그래서 code 판정을 그 테스트도 잡는 것처럼 보였다. 프로브 A의 실제
  안내문으로 바꾸고 바이트 일치를 단언하자 열하나 모두 기대대로였다.
- **`.claude/rules/tools.md` 시간 문단.** WebFetch에 붙는 훅과 그 시간(202~342ms, `webfetch_payload/time_hook.sh`)을
  더했다. 처음에는 앞의 두 훅 PR(#185, #195)처럼 두었는데, 셀프 리뷰가 그 둘은 Bash 훅이라 문단의 일반 문장이 덮었고
  WebFetch는 도구마다 열거하는 그 문단에 없는 새 자리라고 짚었다. 카나리아 `tools_rule_webfetch_hook.toml`은 통과 4였다
  (실험군 셋이 제목·훅 이름·시간을 옮겼고 대조군은 "없음").
- **프로브 README 두 행, `KICKOFF.md`**(매처 목록, 훅 목록, 계기 훅 목록, 바꿀 곳), **`kickoff/pitfalls.md`** 새 행,
  **대기열 209 닫힘.**
- 두지 않은 것: `docs/agents/issue-tracker.md`와 스킬 셋(`grilling`, `code-review`, `to-spec`)은 고치지 않았다.
  `grilling`은 "WebFetch가 준 수와 인용은 원문을 받아 대 보기 전에는 이것이다"라고 보수적으로 적었다. 훅의 침묵은
  통과라는 긍정 신호가 아니어서(훅이 돌지 않은 것과 구별되지 않는다) 그 규칙이 그대로 맞다. 웹 요약의 정의는
  issue-tracker의 것("작은 모델이 질문에 답하는 도구의 출력")이고, 훅은 그 정의대로 가른다.
