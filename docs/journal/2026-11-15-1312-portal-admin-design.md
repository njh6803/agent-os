## 조사: 형제 워크트리 admin-login-design의 초안

Explore 서브에이전트가 형제 워크트리의 파일을 Read·Glob·Grep으로 읽고(줄 단위 비교만 Bash의 `diff`) 보고했다. 아래는 그 보고를 옮긴 것이고 모두 파일을 읽은 것이다. 이 세션은 보고를 다시 대 보지 않았다. 그 브랜치의 커밋과 병합 상태는 보고가 git 명령을 쓰지 않아 확인하지 못했다.

- **상태.** ADR 0062와 ADR 0063은 둘 다 `status: proposed`, `date: 2026-11-15`다. 그 워크트리의 일지 `2026-11-14-2152-admin-login-design.md`의 마지막 절은 설계 인터뷰가 닫혔고 합의 요약 26항목을 사용자가 확정했으며, ADR 초안과 용어집·PRD·기능 계획의 변경이 커밋되지 않은 채 워크트리에 있고, 셀프 리뷰 직전에 다른 세션으로 넘겼다고 적는다. 남은 차례는 셀프 리뷰, 사용자 승인, `accepted`로 바꾸기, 커밋·PR·병합이다.
- **ADR 0062가 정하는 것.** 관리 화면과 운영자용 HTTP 경로(관리 API와 `/runs`)는 사람마다 하나인 운영자 계정(이름과 비밀번호)으로 로그인해야 열린다. 계정, 갱신용 번호, 틀린 횟수, 서명 키, 비밀번호 링크, 로그인 기록은 0.1 판부터 PostgreSQL에 둔다. 그것을 쓰는 프로세스는 파이썬 `serve`이고(포트 선언은 `agent_os.http`, 구현은 `agent_os.adapters`), PostgreSQL을 들이는 일(드라이버, 표 관리 도구, 테스트와 CI가 데이터베이스를 띄우는 길, compose의 컨테이너, 백업과의 관계)은 새 행 postgres-foundation(슬라이스 9, `release-image`를 기다린다)이 맡고 admin-login이 그 뒤에 선다. 로그인 상태는 짧은 JWT와 갱신용 번호이고 둘 다 `__Host-` 접두사의 `HttpOnly; Secure; SameSite=Strict; Path=/` 쿠키다. 서버는 `Sec-Fetch-Site`가 있으면 `same-origin`만 받는다. 비밀번호는 Argon2id다. 단계는 시스템 관리자 하나와 관리자 여럿이다. 관리 화면은 같은 이름의 다른 포트(기본 8443)에 선다. 관리 토큰과 채널 토큰은 없앤다. OIDC와 API 키는 두지 않는다.
- **ADR 0063이 정하는 것.** 관리 화면에 대화 화면을 더하고, 트레이스에 요청한 계정과 결정한 계정을 남긴다.
- **위젯 쪽을 언급하는가.** 두 ADR 어디에도 "위젯 설정 관리 화면", "portal-admin", "위젯 쪽 서버"가 없다(보고의 Grep). "위젯 미리보기 페이지"는 그 페이지의 로그인 상태(ADR 0059)가 이 결정으로 바뀌지 않는다는 문장에 나온다. Node 쪽이 데이터베이스를 쓴다는 문장은 없다.
- **용어집.** 형제 쪽이 더한 항목은 운영자 계정, 시스템 관리자, 관리자, 운영자 로그인 상태, 요청한 계정, 결정한 계정이다. 운영자와 관리 화면의 정의도 고쳤다(관리 화면: "운영자가 관리를 쓰고, 채널로 실행을 일으키고 결정을 내리는 웹 앱"). "계정"(단독)과 "로그인 상태"(단독)는 피할 말이다.
- **함께 고치는 파일.** 형제 브랜치는 ADR 0061이 dev에 들어오기 전에 갈라진 것으로 보인다(그 워크트리에 ADR 0061 파일, 용어 위젯 설정, widget-login-state 행이 없다. 파일 내용을 견준 것이고 git 기록으로는 보지 않았다). `.scratch/plan.md`(admin-login 행, 새 행 postgres-foundation·admin-2fa·admin-approval·admin-roles), `docs/adr/README.md`(0062·0063 행), ADR 0046(이력 2026-11-15 "PostgreSQL이 기준선의 postgres-foundation부터 든다"), `CONTEXT.md`를 고친다. 이 브랜치가 같은 파일을 고치면 병합 때 글자 충돌이 날 자리다.
- **이 인터뷰와 맞물리는 지점.** 데이터베이스가 둘이 될 수 있다(0062의 PostgreSQL은 `serve`의 것이고 위젯 쪽 서버를 말하지 않는다). 위젯 설정 관리 화면에 들어오는 사람도 dev의 문구로는 운영자라, 운영자 계정과 같은 계정인지 다른 계정인지를 갈라야 한다. 0062는 "쿠키는 포트를 가르지 않는다"는 프로브 결과를 근거로 `__Host-` 쿠키와 `Sec-Fetch-Site` 검사를 쓰므로, 위젯 쪽 화면이 같은 호스트의 다른 포트에 쿠키 로그인을 두면 같은 조건에 놓인다.

## 조사: 웹 워크스페이스의 서버 구조

Explore 서브에이전트의 보고를 옮긴다. 근거의 종류는 보고가 적은 대로다. "코드"는 파일을 읽은 것, "손"은 명령의 출력을 본 것이다. 이 세션이 다시 대 본 것은 절 끝에 따로 적는다.

- **워크스페이스.** 앱은 `admin`, `portal`, `widget` 셋이고 패키지는 `api-client`, `e2e-stack`, `react-18`, `site-file`, `ui` 다섯이다(손, `ls web/apps web/packages`). 관리 화면과 위젯은 Next 서버(`next start`, `output` 없음)이고, 위젯 미리보기 페이지는 Next 의존성이 없는 순수 Node 서버다(코드, 각 `package.json`과 `tools/start.ts`).
- **위젯 미리보기 페이지의 서버.** 표준 라이브러리 `node:http`의 `createServer`로 서고 프레임워크가 없다(코드, `web/apps/portal/server/serve.ts`). 처리기는 동기 함수 `(request) => response`이고 요청 값에 본문 칸이 없다(코드, `serve.ts` 16행, `handler.ts` 31~40행). 빌드 없이 node가 타입만 벗겨 `.ts`를 돌린다. 설정은 smol-toml 1.9.1로 읽고 칸 검사는 손으로 쓴 함수다. 쿠키는 `portal_anon` 하나다. 페이지의 CSP는 `connect-src 'self'; frame-ancestors 'none'`이다.
- **관리 화면.** 브라우저가 같은 출처의 `/api`를 부르고 Next의 `rewrites`가 파이썬으로 넘긴다. 라우트 핸들러나 서버 코드가 없다. 토큰 둘은 sessionStorage에 둔다(코드, `web/apps/admin/next.config.ts` 36행, `stores/tokens.ts`).
- **Next 서버 파일 금지.** `web/eslint.config.mjs` 327~333행이 `**/{route,middleware,proxy,instrumentation}.{ts,tsx,…}` 이름의 파일을 앱을 가리지 않고 막고 예외 목록이 없다. 전역 `fetch`도 막고 예외는 `apps/portal/browser/portal.ts` 한 파일이다. `openapi-fetch`의 직접 import는 `packages/api-client`에서만 풀려 있다. `app/` 파일은 노드 내장 모듈과 next·react 밖의 외부 모듈을 import하지 못한다(코드, 같은 파일 99~120행, 273~314행).
- **판.** `engines.node`는 `>=24 <25`, `packageManager`는 `pnpm@11.24.0`, TypeScript `~5.9.3`, Next `16.3.6`, React `19.3.0`이다(코드, `web/package.json`과 앱의 `package.json`). 저장소에 Dockerfile과 compose 파일이 아직 없고(손, `git ls-files`) release-image의 이미지 티켓 07·08·09는 `ready-for-agent`다.
- **위젯의 배포 모양.** `basePath`는 `/widget`이고, 허용 출처와 요청 글자 수 상한을 빌드 때 `env`에 박으며, `frame-ancestors` 헤더는 빌드 산출물에 굳는다(코드, `web/apps/widget/next.config.ts`). 위젯이 API를 부르는 주소는 위젯의 출처와 같고(iframe 방식은 `window.location.origin`, 페이지 안 방식은 번들 `<script>`의 출처) 생성 클라이언트가 아는 경로는 `/end-user/*` 넷뿐이다. 위젯이 새 서버를 부르려면 전역 `fetch` 금지에 예외를 두거나 생성 클라이언트가 아닌 클라이언트 자리를 새로 만들어야 한다(보고의 판단).
- **배포 배치.** 정해진 컨테이너는 다섯(nginx와 이미지 넷: serve, 관리 화면, 위젯, 위젯 미리보기 페이지)이다(코드, ADR 0056). nginx가 넘기는 경로는 `/end-user/`, `/widget`, `/`와 `/portal/`이고 나머지는 404다(코드, `.scratch/release-image/spec.md` 270~298행). 쓰는 볼륨은 serve의 플러그인 루트와 트레이스 폴더 둘뿐이고 관리 화면과 위젯 미리보기 페이지는 읽기 전용 루트다. 위젯 컨테이너는 뜰 때 사이트 파일로 빌드한다.
- **widget_runtime 프로브.** 실험 판(`proxy.ts`, `app/config/route.ts`)은 헤더와 값을 시작 때의 사이트 파일에서 읽었고 응답이 1.0~3.4ms에서 3.9~24.2ms로 늘었으며 ESLint 오류 넷(Next 서버 파일 금지, `app/` import 규칙)이 났다(코드, `.scratch/release-image/probes/widget_runtime/README.md`. 그 측정은 2026-11-11 Windows의 것이다).
- **데이터베이스.** `web/pnpm-lock.yaml`에 데이터베이스 드라이버와 ORM이 하나도 없고(손, `sqlite|postgres`와 그 밖의 이름을 grep해 0건) 코드에 `node:sqlite` 사용도 없다. 스키마 검증 라이브러리와 HTTP 서버 프레임워크도 직접 의존에 없다. 파이썬 의존성에도 데이터베이스 패키지가 없고 import-linter 계약은 core에 `sqlite3`를 금지한다(코드, `pyproject.toml`). Node 24의 `node:sqlite`가 어떤 안정도인지는 보고가 확인하지 못했다(어림).

이 세션이 다시 대 본 것: 위젯 페이지의 제목이 고정 글자 "위젯"이고(`web/apps/widget/app/layout.tsx` 5행) 입력창 안내 문구가 "무엇을 도와드릴까요?"이며(`components/organisms/Composer.tsx` 174행) 위젯의 `.tsx`에 예시 질문을 그리는 코드가 없다(Grep `title|무엇을 도와드릴까요|예시|suggest`).

## 조사: 문서의 앞선 결정

## 인터뷰 라운드 1

이 일지는 선택 화면의 답을 `> 사용자: "<고른 라벨>" — 설명: <그 선택지의 설명>`으로 적는다. 따옴표 안의 라벨만 사람이 고른 것이고, 설명은 세션이 쓴 선택지의 글을 글자 그대로 옮긴 것이다. 사람이 "Other"에 적은 글은 그렇다고 따로 밝힌다.

조사 셋(웹 워크스페이스의 서버 구조, 형제 워크트리의 초안, 문서의 앞선 결정)을 Explore 서브에이전트에 맡기고, 그 조사에 기대지 않는 결정 하나를 먼저 올렸다. ADR 0061 결정 "다크 모드 스위치"와 "이 ADR이 정하지 않는 것"을 읽은 것이 근거다. 화면은 훅(`hook_choice_facts`)이 한 번 막았고, ADR 0061의 그 두 대목을 이 세션이 Read로 읽은 것과 대 본 뒤 같은 글로 다시 올렸다.

> 질문: 사이트가 위젯의 밝기 스위치(다크 모드 스위치)를 숨길 수 있게 하는 설정을 둘까요?
>
> 사용자: "숨기는 설정 두기" — 설명: 위젯 설정에 '밝기 스위치 숨기기' 칸을 둡니다. 운영자가 켜면 그 사이트의 위젯에는 스위치가 나오지 않고, 위젯은 운영자가 정한 처음 밝기(정하지 않았으면 기기의 설정)로 고정됩니다. 사람이 전에 고른 값이 브라우저에 남아 있어도 그 사이트의 위젯은 그 값을 쓰지 않습니다. 대가는 지난 인터뷰의 '늘 사람이 고르기'가 '사이트가 숨기지 않는 한 사람이 고르기'로 바뀌어 ADR 0061에 바뀐 내용을 이력으로 더해야 한다는 것, 그리고 위젯이 지어서 시험할 화면이 한 갈래 는다는 것입니다.

추천("두지 않기")과 다른 안이다. 고르지 않은 추천안의 설명: "모든 위젯에 스위치가 보이고, 사람이 밝게와 어둡게를 고릅니다. 지난 인터뷰에서 고르신 '늘 사람이 고르기'(ADR 0061) 그대로입니다. 운영자가 위젯 설정에 등록하는 처음 밝기는 한 번도 고르지 않은 사람에게만 쓰입니다. 대가는 페이지가 늘 밝은(또는 늘 어두운) 사이트에서도 사람이 위젯만 다른 밝기로 바꿀 수 있다는 것입니다. 나중에 숨기는 설정이 필요해지면 설정 칸 하나를 더하는 일이라, 이미 등록한 설정과 사이트의 페이지는 바뀌지 않을 것으로 봅니다(어림, 재 보지 않았습니다)." 이 답으로 위젯 설정에 고르는 값 하나(밝기 스위치 숨기기)가 늘고, ADR 0061 결정 "다크 모드 스위치"의 "스위치는 모든 위젯에 보인다"에 이력과 포인터가 붙는다.

조사 셋이 돌아온 뒤 라운드 1의 나머지 셋을 올렸다. 데이터베이스의 종류, 화면의 로그인, 사이트 파일의 값은 서버의 자리가 정해진 뒤의 라운드로 미뤘다. 화면은 훅이 한 번 막았고, 설명의 사실을 이 세션이 다시 대 본 뒤 같은 글로 올렸다. 대 본 것: `web/eslint.config.mjs` 92·329·331행(Next 서버 파일 금지), `.scratch/release-image/probes/widget_runtime/README.md` 204·211행(응답 1.0~3.4ms와 3.9~24.2ms, ESLint 오류 4건), `web/packages/api-client/src/clients.ts` 19~22행(`/end-user` 경로 넷), `web/apps/portal/server/serve.ts` 16행(동기 처리기), ADR 0056 24행("컨테이너는 다섯"), `.scratch/release-image/spec.md` 221행(읽기 전용 루트), `web/apps/portal/server/load.ts` 10행(시작 때 한 번 읽는다), `pyproject.toml` 28·29행(fastapi, uvicorn). 모두 Grep이나 Read로 읽은 것이다.

> 질문: 위젯 설정을 저장하고 내주는 서버(위젯 쪽 서버)를 어떤 프로그램으로 세울까요?
>
> 사용자: "관리자 페이지의 메뉴에 미리보기 페이지가 메뉴로 들어가 있으면 좋겠어. 명칭은 시뮬레이션? 명칭은 조사해줘.
> 실제 관리자가 테스트해볼 수 있는 페이지야."

사용자가 선택지를 고르지 않고 "Other"에 글로 답했다. 올린 선택지는 넷이었다. "새 Node 서버를 따로 (Recommended)"(설명: web 폴더에 새 앱 하나를 더합니다. 위젯 미리보기 페이지와 같은 방식(프레임워크 없는 Node 표준 서버)이고, 이 서버가 데이터베이스를 들며 위젯이 설정을 받아 가는 주소와 위젯 설정 관리 화면을 함께 냅니다. 위젯 미리보기 페이지를 쓰지 않는 사이트의 위젯도 이 서버 하나에만 기대고, 위젯을 나중에 다른 저장소로 떼어 낼 때 함께 옮길 수 있습니다. 대가는 배포에서 띄우는 프로그램이 하나 늘어 nginx를 포함해 여섯이 된다는 것(지금 정해진 것은 다섯입니다, ADR 0056), 앞단 nginx의 경로 규칙과 저장용 볼륨이 더해진다는 것, 그리고 위젯이 이 서버를 부르는 통로를 새로 지어야 한다는 것입니다(지금 위젯의 코드는 Agent OS 서버의 경로 넷만 부를 수 있고, 다른 주소를 직접 부르는 것은 린트가 막습니다).), "미리보기 페이지 서버에 더하기", "위젯 앱 안에 서버 코드 허용", "파이썬 서버를 따로"다. 답은 서버의 자리를 고르지 않았고 새 요구 셋을 냈다. 위젯 미리보기 페이지가 "관리자 페이지"의 메뉴로 들어간다, 그 이름을 조사한다(사용자의 후보는 "시뮬레이션"), 그 페이지는 실제 관리자가 시험해 보는 자리다. "관리자 페이지"와 "관리자"는 용어집의 말이 아니다(운영자의 피할 말이 관리자·어드민이고, 관리 화면은 Agent OS의 웹 앱이다). 어느 화면을 가리키는지와, 메뉴로 들어간다는 것이 지금의 공개 페이지를 없애는 것인지는 다음 라운드에서 묻는다.

> 질문: 위젯 미리보기 페이지 설정 파일에 남는 값(그 페이지가 담는 사이트의 목록, 보증 모드, 보고서 링크)과 로그인 서버 항목을 화면에서 고치는 일을 0.1 판에 넣을까요?
>
> 사용자: "모두 0.1 판에" — 설명: 남는 값과 로그인 서버 항목을 모두 0.1 판의 화면에서 고칩니다. 대가는 둘째 안의 대가에 더해, 로그인 서버 항목을 짓는 portal-login 뒤에 화면 일을 한 번 더 해야 해서 0.1 판까지의 길에 일이 하나 더 선다는 것, 그리고 클라이언트 비밀 같은 비밀 값을 화면이 받아 저장할지를 따로 정해야 한다는 것입니다.

추천("0.1 판 뒤로")과 다른 안이다. 고른 설명이 가리키는 둘째 안("남는 값만 0.1 판에")의 설명: "사이트의 목록, 보증 모드, 보고서 링크를 화면에서 고칩니다. 로그인 서버 항목은 portal-login 뒤라 그때의 행으로 미룹니다. 대가는 위젯 미리보기 페이지가 실행 중에 설정을 다시 읽게 고쳐야 하고, 화면이 그 페이지의 설정 파일을 쓰거나 그 값을 데이터베이스로 옮겨야 해서 0.1 판 전에 지을 것이 는다는 것입니다. 서명 키의 경로 같은 값은 화면에서 받지 않고 파일에 남습니다." 고르지 않은 추천안의 설명: "0.1 판의 위젯 설정 관리 화면은 위젯 설정(위젯이 보일 것)만 다룹니다. 위젯 미리보기 페이지의 설정 파일에 남는 값(그 페이지가 담는 사이트의 목록, 사이트마다의 보증 모드와 보고서 링크, 서명 키의 경로)과 로그인 서버 항목은 0.1 판에서 운영자가 파일을 고친 뒤 그 페이지를 다시 띄웁니다. 화면에서 고치는 일은 0.1 판 뒤의 새 행으로 옮깁니다. 까닭은 둘입니다. 그 페이지는 설정을 시작할 때 한 번만 읽어, 화면에서 고친 값을 따르게 하려면 다시 읽는 길을 새로 지어야 합니다. 그리고 로그인 서버 항목은 portal-login 행이 지어야 생기는데 그 행이 이 행보다 뒤입니다. 대가는 0.1 판에서 미리보기 페이지에 사이트를 더하거나 보증 모드를 바꾸려면 파일을 고쳐야 한다는 것입니다."

> 질문: 0.1 판의 위젯 설정에 지난 인터뷰(ADR 0061)가 정한 항목 말고 더 넣을 것이 있을까요?
>
> 사용자: "예시 질문과 문의 링크까지" — 설명: 둘째 안에 더해 첫 화면의 예시 질문(누르면 그 질문이 보내지는 단추들)과 문의 링크를 더합니다. 대가는 지금 위젯에 없는 화면 요소 둘을 새로 지어야 하고, 지금 나란히 그리고 있는 위젯 화면(widget-login-state의 화면 그리기)에도 더해야 한다는 것입니다.

추천("더 넣지 않기")과 다른 안이다. 고른 설명이 가리키는 둘째 안("글자만 바꾸는 둘 더하기")의 설명: "로그인 단추의 문구('로그인하고 질문하기'를 다른 말로)와 URL 방식 창의 탭 제목을 따로 등록하는 칸을 더합니다. 위젯에 새 화면 요소가 생기지 않고 글자만 바뀝니다. 대가는 등록 화면의 칸과 위젯이 받아 그리는 값이 둘 는다는 것입니다." 고르지 않은 추천안의 설명: "0.1 판에서 등록하는 것은 지난 인터뷰가 정한 항목(위젯의 이름, 소개 한 줄, 입력창 안내 문구, 고지의 짧은 줄과 전문, 로그인 주소, 로그아웃 주소, 에이전트, 색 테마, 처음 밝기, 로그인 시간이 끝났을 때 알림의 모양, 로그아웃을 부르는 방법)과 방금 고르신 '밝기 스위치 숨기기'입니다. URL 방식 창의 탭 제목은 칸을 따로 두지 않고 등록한 위젯의 이름을 씁니다(지금은 고정 글자 '위젯'입니다). 로그인 단추의 문구, 첫 화면의 예시 질문, 문의 링크는 0.1 판 뒤의 widget-appearance 행이 그림 올리기, 자유 색과 함께 다룹니다. 대가는 0.1 판에서 그 셋을 바꾸지 못한다는 것입니다." 이 답으로 0.1 판의 위젯 설정에 넷이 는다. 로그인 단추의 문구, URL 방식 창의 탭 제목, 첫 화면의 예시 질문, 문의 링크다.

## 조사: "관리자 페이지의 메뉴에 미리보기 페이지"에 닿는 사실

서버의 자리 질문에 사용자가 글로 낸 요구를 풀기 전에 이 세션이 본 것이다. 모두 Grep이나 Read로 읽었고, 마지막 항목만 손으로 돌려 봤다.

- 사용자는 앞선 인터뷰에서 두 화면을 다른 말로 불렀다. 위젯 쪽은 "위젯 관리자 페이지"(일지 2026-11-11-1532 147행, 2026-11-13-1813 100행), Agent OS 쪽은 "agent os 관리자 페이지"(일지 2026-11-12-1937 299행)다. 이번 답은 앞말 없이 "관리자 페이지"다.
- 용어집(`CONTEXT.md`)에서 운영자의 피할 말이 "관리자, 어드민"이고(107~109행), 관리 화면은 Agent OS의 웹 앱이다(115~117행). 위젯 미리보기 페이지는 "위젯을 붙일 사이트나 토큰을 서명할 서버가 없을 때 위젯을 보여 주고 질문해 볼 자리이고, 사이트마다의 설정으로 그린 위젯을 골라 보고 질문해 볼 자리"이며 최종 사용자에게 사이트 토큰을 낸다(175~177행). 피할 말에 "데모 페이지"가 있다.
- Agent OS 관리 화면의 메뉴는 셋이다. 플러그인, 실행, 설정(`web/apps/admin/components/organisms/AdminNav.tsx` 10~12행).
- ADR 0047 15행: "관리 화면과 관리 API에 위젯 전용 기능을 두지 않는다. 위젯의 외형, 문구, 배치를 보거나 고치는 기능이 그것이다."
- 지금의 위젯 미리보기 페이지는 주소를 아는 사람이 여는 페이지다. `/portal/`이 페이지 하나이고 셀렉트 박스로 사이트를 고른다(`.scratch/pilot-portal/spec.md` 27행). 그 명세의 첫 사용자 스토리가 "최종 사용자가 로그인 없이 위젯 미리보기 페이지를 열어"다(31행). 이 페이지에 기대는 행이 둘 있다. public-demo("누구나 로그인 없이 묻고", `.scratch/plan.md` 63행)와 portal-login("배포 환경에서는 사내 사람만 질문하게", 71행)이다. 그래서 그 페이지를 운영자만 보게 닫으면 그 두 행이 기대던 자리가 사라진다.
- Node에 내장된 SQLite(`node:sqlite`)를 설치된 Node v24.19.0에서 손으로 돌려 봤다. 플래그 없이 실리고 경고가 0건이었으며, WAL 모드로 파일에 쓴 한글 값이 닫았다 다시 열어도 남았다(SQLite 3.53.3). 스크립트는 세션 스크래치패드의 `sqlite_check.mjs`이고 저장소에 없다. 타입 검사와 린트는 아직 지나 보지 않았다(`@types/node`는 24.19.0이다, `web/pnpm-lock.yaml` 26~28행). 데이터베이스의 종류를 고르는 라운드 전에 프로브로 옮겨 다시 잰다.
- 메뉴 이름은 서브에이전트가 웹에서 조사하고 있다(다른 제품이 운영자의 시험 화면을 부르는 이름).

## 인터뷰 라운드 2

사용자의 글 답("관리자 페이지의 메뉴에 미리보기 페이지")을 풀기 위한 셋을 올렸다. 화면은 훅이 한 번 막았고, 설명의 사실은 위 조사 절에서 대 본 것이다. "운영자만 보게 닫기"의 설명만 다시 올릴 때 끝을 "(사내 로그인은 0.1 판에 드는 계획이라 0.1 판의 계획이 바뀝니다)"로 고쳤다(public-demo는 pilot-release가 기다리지 않는 행이다, `.scratch/plan.md` 69행).

> 질문: 말씀하신 '관리자 페이지'는 어느 화면인가요? 미리보기 메뉴가 들어갈 자리를 정합니다.
>
> 사용자: "새로 짓는 위젯 쪽 화면 (Recommended)" — 설명: 이번에 새로 짓는 위젯 설정 관리 화면의 메뉴에 위젯 설정과 나란히 들어갑니다. 이미 있는 Agent OS 관리 화면(메뉴는 플러그인, 실행, 설정 셋입니다)은 그대로 둡니다. 'Agent OS 관리 화면에는 위젯 전용 기능을 두지 않는다'는 앞선 결정(ADR 0047)과 맞습니다. 대가는 운영자가 여는 화면이 둘이 되어 주소도 둘이라는 것입니다. 로그인을 한 번으로 묶을 수 있는지는 뒤의 질문에서 따로 정합니다.

고르지 않은 안은 "Agent OS 관리 화면"(Agent OS의 서버와 관리 화면이 위젯 설정을 모른다고 정한 ADR 0047과 ADR 0061을 고쳐야 한다. ADR 0061의 원문은 "`serve`, Agent OS의 관리 화면과 관리 API, 사이트 파일, `openapi.json`은 위젯 설정을 모른다"이다)과 "화면은 따로, 서로 가는 링크만"(ADR 0047에 링크 하나의 예외를 이력으로 더한다)이다.

> 질문: 메뉴로 들어간 미리보기 페이지를, 관리 화면에 로그인하지 않은 사람도 지금처럼 주소로 열 수 있어야 할까요?
>
> 사용자: "공개 주소도 남기기 (Recommended)" — 설명: 지금의 위젯 미리보기 페이지는 주소를 아는 사람이 여는 페이지로 그대로 남고, 관리 화면의 메뉴는 운영자가 그 페이지를 여는 또 하나의 입구가 됩니다. 운영자는 메뉴에서 사이트를 골라, 등록한 위젯 설정으로 그려진 위젯에 실제로 질문해 봅니다. 공개 데모(누구나 로그인 없이 질문)와 사내 로그인(사내 사람이 로그인하고 질문) 두 계획이 이 페이지에 기대고 있어 그 둘이 바뀌지 않습니다. 대가는 운영자가 시험하는 자리와 사람들이 실제로 쓰는 자리가 같은 페이지라, 저장하기 전의 설정을 운영자만 미리 볼 수는 없다는 것입니다(저장하면 곧바로 모두에게 보입니다).

고르지 않은 안은 "운영자만 보게 닫기"와 "둘로 나누기"(관리 화면 안에 운영자만 보는 시험 자리를 하나 더 짓는다)다. 이 답으로 저장하기 전의 설정을 미리 보는 기능은 0.1 판에 없다.

> 질문: 위젯 설정에 등록하는 로그인 주소와 로그아웃 주소를, 저장할 때 어디까지 검사할까요?
>
> 사용자: "주소의 형식만 검사 (Recommended)" — 설명: https://로 시작하는 완전한 주소만 받습니다(자기 PC에서 시험할 때 쓰는 http://localhost 주소는 받습니다). javascript:처럼 주소가 아닌 값을 넣어 위젯이 든 페이지에서 스크립트를 돌리는 길을 막습니다(그런 값이 스크립트로 도는 것은 브라우저의 일반 동작으로 아는 것이고 재 보지 않았습니다). 저장할 때 서버가 검사하고, 위젯도 그 주소를 열기 전에 한 번 더 봅니다. 어느 도메인의 주소인지는 가리지 않아, 로그인 서버를 다른 도메인에 둔 사이트도 그대로 등록합니다. 대가는 위젯 설정 관리 화면에 들어온 사람이 엉뚱한 도메인의 주소를 등록하는 것까지는 막지 못한다는 것입니다. 그것을 막는 것은 그 화면의 로그인뿐입니다.

고르지 않은 안은 "미리 적어 둔 도메인만"(배포 설정 파일의 목록)과 "사이트의 페이지와 같은 주소만"(사이트 파일의 허용 출처와 출처가 같은 주소)이다. 이 답으로 주소를 지키는 것이 그 화면의 로그인 하나가 되어, 화면의 로그인을 정하는 질문이 그만큼 무거워진다.

## 조사: 운영자가 위젯을 시험해 보는 화면의 이름

사용자가 "명칭은 시뮬레이션? 명칭은 조사해줘"라고 해서 서브에이전트가 공개 문서를 조사했다(122회의 도구 호출). 아래는 그 보고를 이 세션이 줄인 것이고, 이 세션은 원문을 다시 대 보지 않았다. 보고는 근거를 셋으로 갈랐다. 원문 확인(공개 문서의 본문을 내려받아 그 글자가 있는지 정규식으로 대 봤다. 스크립트는 세션 스크래치패드의 `fg.ps1`이고 저장소에 없다), 웹 요약(검색 결과나 WebFetch의 요약만 봤다), 어림(기억)이다. 로그인해야 보이는 실제 관리 화면은 보지 못해, 문서의 낱말과 화면의 메뉴 글자가 다를 수 있다. Microsoft, AWS, HubSpot의 한국어 문서는 기계 번역으로 보인다는 단서가 붙었다.

- 운영자가 실제로 메시지를 보내 시험하는 화면의 이름을 제품 단위로 센 수: Preview(미리보기) 8, Test(테스트) 6, Playground(플레이그라운드) 9, Simulator(시뮬레이터) 2, Emulator 2, Run 1, 체험 0. 플레이그라운드 아홉 가운데 여섯은 모델 제공사의 화면(OpenAI, Anthropic, Google AI Studio, CLOVA Studio, Amazon Bedrock, Microsoft Foundry)이고 상담·챗봇 제품은 셋(Tidio, Crisp, Chatbase)이다.
- 한국어로 확인된 이름: 테스트 다섯(카카오 챗봇 관리자센터의 "봇테스트", CLOVA Chatbot의 "테스트", Zendesk의 "AI 상담사 테스트", Copilot Studio, Amazon Lex), 미리보기 넷(채널톡, Dify의 "디버그 및 미리보기", HubSpot, IBM watsonx Assistant), 플레이그라운드 셋, 시뮬레이터 하나(Dialogflow CX의 번역 문서). CLOVA 둘은 웹 요약이고(네이버 클라우드 문서가 403으로 막혔다) 나머지는 원문 확인이다.
- 채널톡은 화면의 이름을 "미리보기"로 두고 설명에서 "현재 설정 그대로 ALF 상담을 무료로 테스트해 볼 수 있어요"라고 푼다(원문 확인).
- "시뮬레이션"이나 "시뮬레이터"를 직접 시험 화면에 쓰는 제품은 둘(Dialogflow CX, Alexa 개발자 콘솔)이다. 다른 뜻으로 쓰는 제품은 여덟이다. Intercom Fin, Chatbase, Voiceflow, Cognigy, Ada, Decagon, Sierra는 AI가 가상 고객을 맡아 대화를 자동으로 돌리고 채점하는 평가를 그렇게 부르고, Salesforce Agentforce는 액션을 실제로 돌리지 않는 모의 실행을 "Simulate"라고 부른다(모두 원문 확인).
- 보고의 의견: 한국어 이름으로는 "테스트"가 가장 널리 통하고 "미리보기"가 다음이다. "시뮬레이션"은 자동 평가나 모의 실행으로 읽힐 수 있어 피하는 편이 안전하다. "플레이그라운드"는 모델과 프롬프트를 실험하는 화면의 이름으로 굳어 있다.

## 조사: 형제 ADR 0062·0063이 승인됐다

라운드 2를 올린 뒤 다시 봤다. 형제 워크트리 `admin-login-design`의 ADR 0062와 0063의 머리가 `status: accepted`로 바뀌어 있다(Grep). 이 세션을 시작할 때는 둘 다 `proposed`였다. 아직 병합되지 않았다. `git fetch origin` 뒤에 새 커밋이 없었고, 열린 PR은 #575(모델 서버를 빌리는 명령) 하나다(`gh pr list --state open`). ADR 0062는 전문을 Read로 읽었고 0063은 대화 화면 항목만 Grep으로 읽었다. 이 설계에 닿는 것은 아래다.

- 운영자 계정과 그 로그인 상태를 0.1 판부터 PostgreSQL에 둔다. PostgreSQL을 들이는 일(드라이버, 표 관리 도구, 테스트와 CI가 데이터베이스를 띄우는 길, compose의 컨테이너, 백업과의 관계)은 새 행 postgres-foundation이 맡고 admin-login이 그 뒤에 선다(결정 "저장").
- 로그인 상태는 `__Host-` 쿠키 둘이고 `HttpOnly; Secure; SameSite=Strict; Path=/`다. 쿠키는 포트를 가르지 않아 호스트가 같고 포트가 다른 페이지가 보낸 요청에도 실렸고, 서버는 `Sec-Fetch-Site`가 `same-origin`인 요청만 받는다. 그 머리도 `Origin`도 없는 요청(브라우저가 아닌 프로그램)은 받는다(결정 "요청 출처 검사". 그 ADR이 근거로 든 것은 형제 워크트리의 `.scratch/admin-login/probes/cookie_relay/README.md`다. 이 세션은 그 프로브를 돌리지도 읽지도 않았고 ADR의 문장만 읽었다).
- 계약에 "지금 누구인지"를 답하는 경로가 는다(결정 "경로와 층"). 프로그램용 열쇠(API 키)는 두지 않는다(결정 "자격").
- 관리 화면은 같은 이름의 다른 포트(기본 8443)에 서고 그 포트는 기본으로 인터넷에 열린다(결정 "포트와 TLS").
- Consequences "다른 행"이 이 인터뷰를 짚는다. "둘은 서로 다른 서버의 데이터베이스다", "위젯 쪽 서버가 그 규칙(ADR 0048)의 서비스인지, 두 데이터베이스의 종류와 도구를 맞출지는 먼저 도는 쪽의 설계 인터뷰가 다른 쪽의 기능 계획을 읽고 정하며", "이 ADR의 운영자 계정이 그 화면의 로그인이 되는지도 이 ADR은 정하지 않는다". 그 ADR은 이 문장을 portal-admin의 기능 계획에도 적었다고 하는데, 형제 워크트리의 `.scratch/portal-admin/plan.md`를 `postgres-foundation`으로 Grep해 0건이었다. 병합할 때 그 파일을 다시 본다.
- ADR 0063은 Agent OS 관리 화면의 탐색에 '대화' 항목을 두어 운영자가 대화 화면에서 실행을 일으키게 한다(12행). 0.1 판에 든다. 그래서 운영자가 에이전트에 직접 물어 보는 자리는 Agent OS 쪽에 따로 생기고, 위젯 쪽의 미리보기 메뉴는 방문자가 볼 위젯을 그대로 써 보는 자리다.

## 인터뷰 라운드 3

이름 조사의 요약 표와 ADR 0062·0063의 승인, 데이터베이스 두 종류의 풀이를 본문에 적고 넷을 올렸다. 서버의 자리는 추천을 바꿔 다시 올렸다(처음에는 "새 Node 서버를 따로"였다. 미리보기가 메뉴로 들어가고 미리보기 설정까지 화면에서 고치기로 해서 한 프로그램이 지을 것이 적다고 봤다). 화면은 훅이 한 번 막았고, 다시 올리기 전에 더 대 본 것은 셋이다. ADR 0048 24행("데이터베이스는 서비스마다 따로 띄운다. 각 서비스는 연결 문자열 하나만 받고, 다른 서비스의 데이터베이스를 읽지 않으며, 자기 마이그레이션만 한다", Read), `web`의 `package.json`들에 데이터베이스 드라이버가 없다는 것(pg, postgres, sqlite 계열, prisma, drizzle 등의 이름으로 Grep해 0건), `web`의 코드에 `node:sqlite`를 쓰는 곳이 없다는 것(Grep 0건)이다. SQLite 안의 설명에는 다시 올릴 때 "(타입 검사와 린트는 아직 지나 보지 않았습니다)"를 더했다.

> 질문: 위젯 설정 관리 화면의 메뉴에 들어갈 미리보기 페이지의 메뉴 글자를 무엇으로 할까요? 문서에서 쓰는 이름(위젯 미리보기 페이지)은 그대로 두고, 화면에 보이는 글자만 정합니다.
>
> 사용자: "테스트" — 설명: 실제로 질문해 본다는 뜻이 분명하고, 조사한 한국어 서비스에서 가장 흔한 이름입니다(카카오의 봇테스트, CLOVA Chatbot의 테스트, Zendesk의 AI 상담사 테스트). 대가는 메뉴 글자와 문서의 이름이 달라져 문서에 '메뉴에 보이는 글자는 테스트'라는 한 줄이 든다는 것과, 이 저장소의 문서에서 '테스트'가 자동 시험을 가리키는 말이기도 해서 섞일 수 있다는 것입니다.

추천("미리보기")과 다른 안이다. 사용자가 처음 낸 "시뮬레이션"은 고르지 않았다. 용어집의 이름(위젯 미리보기 페이지)은 그대로이고 메뉴에 보이는 글자만 "테스트"다.

> 질문: 위젯 설정을 저장하고 내주는 서버(위젯 쪽 서버)를 어떻게 세울까요? 미리보기를 메뉴에 넣고 미리보기 설정도 화면에서 고친다는 앞의 답을 반영해 다시 여쭙니다.
>
> 사용자: "미리보기 페이지 서버를 키워 하나로 (Recommended)" — 설명: 지금의 위젯 미리보기 페이지 서버 하나가 데이터베이스, 위젯 설정 관리 화면, 위젯이 설정을 받아 가는 주소까지 맡습니다. 관리 화면의 메뉴와 미리보기 페이지가 한 프로그램이라, 화면에서 고친 값을 미리보기 페이지가 다시 띄우지 않고 따르게 짓기 쉽습니다. 위젯 쪽에서 띄우는 프로그램 수가 늘지 않습니다. 운영자의 화면과 누구나 여는 페이지는 프로그램 안에서 포트를 갈라, 공개 주소로 온 요청이 운영자의 기능에 닿지 못하게 짓습니다. 대가는 그 서버의 뼈대를 고쳐야 한다는 것(지금은 저장하는 것이 없고 요청의 본문을 읽지 않으며 읽기 전용으로 뜹니다), 그리고 위젯 미리보기 페이지를 쓰지 않는 배치도 위젯 설정을 쓰려면 이 서버를 띄워야 한다는 것입니다.
>
> 사용자(같은 답에 덧붙인 글): "근데 프론트랑 백엔드가 따로 있어야 하는거 아닌가?"

덧붙인 글은 되묻는 말이라 이 답은 아직 닫히지 않았다. 화면(프론트)과 서버(백엔드)를 어떻게 가를지를 다음 화면에서 풀어 다시 묻는다.

> 질문: 위젯 쪽 서버의 데이터베이스는 어떤 종류로 할까요?
>
> 사용자: "PostgreSQL, 위젯 쪽 컨테이너를 따로" — 설명: 둘째 안과 같되 위젯 쪽의 PostgreSQL을 따로 띄웁니다. '데이터베이스는 서비스마다 따로 띄운다'(ADR 0048)를 그대로 따르고, 위젯을 나중에 떼어 낼 때 데이터베이스를 함께 옮기기 쉽습니다. 대가는 둘째 안의 대가(드라이버 의존성, 테스트와 CI의 데이터베이스)에 더해 띄우는 프로그램과 백업할 대상이 하나씩 더 는다는 것입니다.

추천("Node에 내장된 SQLite")과 다른 안이다. 고른 설명이 가리키는 둘째 안("PostgreSQL, 같은 컨테이너에 따로")의 설명: "Agent OS가 0.1 판에 들이기로 한 PostgreSQL(ADR 0062)과 같은 종류를 쓰고, 그 컨테이너 안에 위젯 쪽의 데이터베이스와 접속 계정을 따로 만듭니다(서로의 표는 읽지 않습니다). 제품의 데이터베이스가 한 종류라 백업 절차가 하나이고, 서버를 여러 대로 늘려도 그대로 갑니다. 대가는 web 쪽에 PostgreSQL 드라이버 의존성이 새로 들고, web의 테스트와 CI가 데이터베이스를 띄워야 하며(지금 web 쪽에는 데이터베이스가 없습니다), 이 일이 Agent OS 쪽의 PostgreSQL 도입 뒤로 밀려 0.1 판까지의 순서가 길어진다는 것입니다. '데이터베이스는 서비스마다 따로 띄운다'(ADR 0048)에 예외를 적어야 합니다. 드라이버 조합은 아직 재지 않았습니다." 고른 안은 컨테이너가 따로라 ADR 0048의 예외가 들지 않는다. 드라이버는 재지 않은 채 고른 것이라 프로브로 잰 뒤 ADR에 적는다. 위에서 손으로 본 SQLite는 쓰지 않는다.

> 질문: 위젯 설정 관리 화면에는 어떤 로그인으로 들어오게 할까요?
>
> 사용자: "Agent OS 관리 화면의 계정으로 함께 (Recommended)" — 설명: 운영자는 Agent OS 관리 화면에 로그인한 그 계정 그대로 위젯 설정 관리 화면에 들어옵니다. 로그인은 한 번이고 로그인 화면도 하나입니다. 위젯 쪽 서버는 요청이 오면 Agent OS 서버에 '이 로그인이 지금 유효한지, 누구인지'를 물어 확인하고, 계정과 비밀번호는 저장하지 않습니다. 누가 설정을 바꿨는지를 계정 이름으로 남길 수 있습니다. 위젯 쪽이 Agent OS에 기대는 방향이라 'Agent OS는 위젯을 모른다'(ADR 0047)와 맞습니다. 대가는 셋입니다. 이 화면의 로그인이 Agent OS 쪽 로그인(admin-login 행, 그 앞에 PostgreSQL 도입)이 지어진 뒤에야 완성되어 0.1 판까지의 순서가 묶입니다. Agent OS 서버가 내려가 있으면 이 화면에 들어올 수 없습니다. 두 화면이 같은 이름(호스트)에 있어야 로그인 쿠키가 함께 쓰입니다. 이 방식은 ADR 0062의 문장을 읽고 짠 것이고, 그 로그인이 아직 지어지지 않아 재 보지 못했습니다(어림).

고르지 않은 안은 "위젯 쪽에 계정을 따로"와 "배포할 때 정한 비밀번호 하나"다.

Node 내장 SQLite에 더 본 것: `@types/node` 24.19.0에 `sqlite.d.ts`가 있다(주 체크아웃의 `web/node_modules`에서 `ls`로 봤다). Node 24 문서는 이 모듈을 "Stability: 1.2 - Release candidate"로 적고 v24.15.0에서 출시 후보가 됐다고 적는다(웹 요약: https://nodejs.org/docs/latest-v24.x/api/sqlite.html. 원문을 내려받아 대 보지 않았다).

## 조사: 라운드 3 뒤에 대 본 것

사용자의 되물음("프론트랑 백엔드가 따로 있어야 하는거 아닌가?")에 답하려고 화면을 짓는 방식의 사실을 봤고, 라운드 4의 화면을 훅이 한 번 막은 뒤 설명의 사실을 더 댔다. 모두 이 워크트리의 파일을 Read나 Grep으로 읽은 것이다.

- 위젯 미리보기 페이지 앱(`web/apps/portal/package.json`)의 의존성에는 React도 화면을 묶는 도구도 없다. 서버가 HTML을 직접 만들어 내고, 브라우저 스크립트는 타입만 걷어 시작 때 짓는다(`server/assets.ts`).
- 관리 화면(`web/apps/admin`)과 위젯(`web/apps/widget`, `next` 16.3.6)은 Next 앱이다. 관리 화면은 `next.config.ts`의 `rewrites`로 `serve`에 중계하고, 위젯은 `rewrites`를 두지 않는다(그 파일의 머리 주석).
- 위젯의 페이지 안 번들(`element.js`)은 `web/apps/widget/tools/element.ts`가 `vite`의 `build`로 묶는다. 화면 여럿을 가진 앱을 그렇게 지어 서버가 내는 것은 `web/apps`에 없다.
- `@agent-os/ui`의 진입점(`web/packages/ui/src/index.ts`)이 내보내는 부품은 Button, Card, Icon, IconButton, Progress, StatusBadge, Alert, Markdown, Switch, TextField다.
- 앱 사이의 import는 ESLint가 막는다(`web/eslint.config.mjs` 266행의 메시지 "앱 사이에서 import 하지 않는다. 함께 쓸 것은 packages/ 로 옮긴다").
- 위젯 미리보기 페이지 서버는 사이트 파일을 읽는다(`web/apps/portal/server/load.ts` 16행의 `readSiteFile`).
- 고지 전문의 쿠키 문장은 지금 코드가 전문의 끝에 붙인다(`web/apps/portal/server/notice.ts`). "질문이 로그인한 계정과 함께 기록된다"는 문장은 ADR 0059 결정 "고지 확인"(20행)이 넣기로 정했고 코드에는 아직 없다(ADR 0061 28행도 그렇게 적는다).
- 위젯 컨테이너는 뜰 때 운영자의 사이트 파일로 빌드한 뒤 서비스를 시작하고 치르는 값은 뜨는 시간과 이미지 크기다(ADR 0056 28행). 사이트 파일을 고치면 `serve`, 위젯 미리보기 페이지, 위젯 세 컨테이너를 다시 띄워야 한다(같은 ADR 29행).
- 위젯의 `next.config.ts`는 허용 출처를 두 자리에 굳힌다. `headers()`의 `Content-Security-Policy: frame-ancestors`(빌드 산출물 `routes-manifest.json`에 박힌다)와 `env`(번들에 박힌다)다. 요청 글자 수 상한도 `env`로 번들에 박힌다.
- `.scratch/release-image/probes/widget_runtime/README.md`의 실험 판은 `proxy.ts`가 요청마다 `frame-ancestors`를 달고 페이지를 요청 때 그려 시작 때의 사이트 파일을 따랐다고 적는다(결과 2번). 그 판은 ESLint 오류 4건에 걸린다(결과 8번. ADR 0019를 근거로 드는 ESLint 규칙의 글 "Next 서버가 돌리는 파일(route, middleware, proxy, instrumentation)을 두지 않는다"와 ADR 0021의 `app/` 경계). 이 세션은 그 README를 읽기만 했고 프로브를 다시 돌리지 않았다.

PostgreSQL의 Node 드라이버 후보 둘(`pg`, `postgres`)을 설치, 타입 검사, 린트, Docker의 PostgreSQL에서의 실행까지 대 보는 프로브를 서브에이전트에 맡겨 백그라운드로 띄웠다(자리는 `.scratch/portal-admin/probes/pg_node/`). 라운드 4의 답을 받을 때까지 보고가 오지 않았다.

## 인터뷰 라운드 4

본문에서 되물음에 답했다. "하나로"는 데이터베이스를 읽고 쓰는 서버를 하나로 모은다는 뜻이었고 화면을 어떻게 지을지는 그 선택지에 담지 못했다고 적었다. 넷을 올렸고 훅이 한 번 막았다. 다시 올리기 전에 위의 사실을 대 보고 설명을 고쳤다. 화면을 파일로 짓는 안의 "이 저장소에 없다"를 "화면 여럿을 가진 앱으로는 없다"로 고쳤고, 허용 출처 첫째 안에는 응답 머리 `frame-ancestors`가 따로 남는다는 것을, 고지 첫째 안에는 계정 문장이 아직 지어지지 않았다는 것을 더했다. 허용 출처 넷째 안의 "메모리를 더 씁니다"는 ADR 0056이 적은 "뜨는 시간과 이미지 크기"로 바꿨다.

> 질문: 위젯 설정 관리 화면(프론트)을 어떤 방식으로 지을까요? 저장하고 내주는 서버(백엔드)는 앞에서 고르신 대로 미리보기 페이지 서버입니다.
>
> 사용자(글 답): "추천대로 하는데 백엔드는 FastAPI로 하고 싶은데"

추천한 안은 "화면은 새 Next 앱으로 따로 (Recommended)"이고 그 설명은 이렇다. "Agent OS 관리 화면, 위젯과 같은 구조입니다(둘 다 Next 앱입니다). 화면은 React로 지은 새 앱이고, 그 앱이 요청을 미리보기 페이지 서버(백엔드)로 넘깁니다. 디자인 시스템의 부품(버튼, 입력 칸, 스위치 등)과, 관리 화면에서 이미 쓰는 방식(화면 부품의 층, 스토리 테스트, 사진 비교, 린트 규칙)을 그대로 씁니다. 대가는 띄우는 프로그램이 하나 는다는 것(화면을 내는 Next 서버), 앱끼리는 코드를 가져다 쓸 수 없어(린트가 막습니다) 관리 화면 앱의 부품(탐색 메뉴 등)은 다시 짓거나 공유 패키지로 옮겨야 한다는 것, 그리고 검사(e2e, 사진 비교)의 대상 앱이 하나 늘어 CI가 길어진다는 것입니다."

이 답은 둘을 말한다. 화면은 새 Next 앱이다. 백엔드는 FastAPI(파이썬)로 하고 싶다는 것이고, 이것은 라운드 3의 "미리보기 페이지 서버를 키워 하나로"와 위 설명의 "그 앱이 요청을 미리보기 페이지 서버(백엔드)로 넘깁니다"를 바꾼다. 백엔드의 자리, Node로 지은 미리보기 페이지 서버를 어떻게 할지, 파이썬의 PostgreSQL 도구를 누가 고를지가 새로 열려 다음 라운드에서 묻는다. 고르지 않은 안은 "React 화면을 파일로 지어 백엔드가 함께 내기"와 "서버가 HTML을 직접 그리기"다.

> 질문: 위젯 설정 관리 화면을 어느 주소에 둘까요?
>
> 사용자: "다른 포트를 하나 더" — 설명: 위젯 설정 관리 화면이 자기 포트에 따로 섭니다. 브라우저에서 출처가 갈려, 위젯 쪽 화면의 스크립트가 Agent OS의 관리 기능을 부르지 못합니다(Agent OS 서버가 다른 포트의 페이지에서 온 요청을 거절합니다, ADR 0062). 로그인 쿠키는 포트를 가리지 않아 그대로 함께 씁니다(ADR 0062가 근거로 든 프로브의 결과이고 이 세션은 돌려 보지 않았습니다). 대가는 인터넷에 여는 포트와 방화벽 규칙, 배포 안내의 항목이 하나씩 늘고, 운영자가 주소 둘을 기억해야 한다는 것입니다.

추천("관리 화면과 같은 포트의 다른 경로")과 다른 안이다.

> 질문: 사이트 파일에 적힌 허용 출처와 요청 글자 수 상한을 0.1 판에서 어디까지 다룰까요?
>
> 사용자: "위젯이 실행 중에 받게만 (Recommended)" — 설명: 위젯이 뜰 때 위젯 설정과 함께 그 사이트의 요청 글자 수 상한과 허용 출처도 위젯 쪽 서버에서 받아 옵니다(그 서버는 지금도 사이트 파일을 읽습니다). 두 값을 바꾸는 일은 0.1 판에서 지금처럼 사이트 파일을 고친 뒤 그 파일을 읽는 서버를 다시 띄우는 것으로 남고, 화면에서 고치는 일은 0.1 판 뒤의 새 행으로 넘깁니다. 두 값은 Agent OS가 요청을 받아들일지를 가르는 설정이라, 위젯 쪽 화면이 고치면 'Agent OS는 위젯을 모른다'는 경계(ADR 0047)와 어긋나기 때문입니다. 대가는 0.1 판에서 두 값을 화면으로 바꾸지 못한다는 것입니다. 남는 문제가 하나 있습니다. 위젯 페이지를 품어도 되는 사이트를 브라우저에 알리는 응답 머리는 받아 오는 값이 아니라 위젯 페이지를 내는 서버가 붙이는 값이라, 이것까지 실행 중에 정해야 위젯 컨테이너가 뜰 때 하는 빌드를 없앨 수 있습니다. 그 방법은 다음 질문에서 따로 여쭙니다(실험 판은 지금 규칙이 금지하는 파일을 써서만 돌았습니다).

이 설명의 "(그 서버는 지금도 사이트 파일을 읽습니다)"는 위젯 쪽 서버가 Node의 미리보기 페이지 서버라는 전제에서 쓴 문장이다. 같은 라운드의 첫 답이 백엔드를 FastAPI로 바꾸면 그 전제가 서지 않는다. 두 값을 어느 서버가 내주는지와 응답 머리를 누가 붙이는지는 사실을 더 모은 뒤 다시 확인받는다. 화면에서 고치는 일을 0.1 판 뒤의 새 행으로 넘긴다는 것은 그대로다.

> 질문: 미리보기 페이지가 고지 전문에 늘 붙이던 문장(쿠키를 둔다는 문장, 로그인한 계정과 함께 기록된다는 문장)을, 고지를 위젯이 그리게 된 뒤에는 누가 빠지지 않게 할까요?
>
> 사용자: "화면이 처음 값으로 채워 주기" — 설명: 등록 화면이 미리보기 페이지가 담는 사이트의 고지 전문에 그 문장을 처음 값으로 넣어 둡니다. 운영자가 문장을 자기 말로 다듬을 수 있습니다. 대가는 운영자가 지우면 쿠키를 두면서도 고지에서 그 사실이 빠진다는 것입니다.

추천("미리보기 페이지가 위젯에 넘겨 붙이기")과 다른 안이다. ADR 0050 결정 "시작 인자와 시작 검사"와 ADR 0059 결정 "고지 확인"의 "늘 넣는다"를 바꾸므로 두 ADR에 이력과 포인터가 든다.

## 조사: 백엔드를 FastAPI로 할 때 닿는 사실

- `pyproject.toml`: 런타임 의존성에 `fastapi>=0.140.8`, `uvicorn>=0.30`, `pydantic>=2.9`가 이미 있다. 휠에 드는 패키지는 `src/agent_os` 하나이고(`[tool.hatch.build.targets.wheel]`), import-linter의 `root_packages`는 `agent_os` 하나이며, pyright는 `src`, `tests`, `tools`를 본다. 명령은 `agent-os = "agent_os.main:main"` 하나다(Read와 Grep).
- 형제 ADR 0062 60행: "PostgreSQL의 드라이버와 표 관리 도구는 postgres-foundation의 ADR이 정한다." 형제 워크트리의 `.scratch/postgres-foundation/plan.md`는 admin-login의 인터뷰가 후보 조합(psycopg 동기와 비동기, asyncpg, SQLAlchemy Core, 표 관리 도구 셋, testcontainers, 공식 이미지)을 대 보고 고르지는 않았다고 적고, 그 결과의 원천으로 `.scratch/admin-login/probes/pg_stack/README.md`를 든다(이 세션은 그 README를 읽지 않았다). 같은 계획이 "두 행 가운데 먼저 도는 설계 인터뷰가 다른 쪽의 기능 계획을 읽고 종류와 도구를 맞출지, 컨테이너를 함께 쓸지 따로 띄울지(ADR 0048은 데이터베이스를 서비스마다 따로 띄운다고 정했다), 백업을 어떻게 묶을지를 정한다"고 적는다. 둘 다 병합 전이다.
- ADR 0047 18행: "위젯은 최종 사용자 채널의 참조 클라이언트로 이 저장소에 남는다." 43행은 "위젯 맞춤 설정을 관리 화면의 사이트 메뉴에 두고 `serve`가 공개 경로로 내준다"를 거부했다. 36행은 떼어 낼 때 끊을 연결로 위젯 빌드가 사이트 파일을 직접 읽는 것을 들고, 바꿀 방식의 하나로 "`serve`가 범용 공개 경로로 사이트 정보를 내주는 방식"을 적는다.
- 반대 방향의 선례: ADR 0048 30행은 문서 검색 서버를 agent-os 안(`src/` 아래 패키지)에 두는 안을 거부했다. 까닭은 무거운 의존성이 런타임의 잠금 파일과 CI에 들어오고 런타임의 보장과 무관한 코드가 같은 판 리듬에 묶인다는 것이다.
- ADR 0056 24행은 단독 compose의 컨테이너를 다섯, 이미지를 넷으로 적는다.
- ADR 0062 26행: 로그인 기록은 데이터베이스의 표에 계정 이름과 시각으로 한 줄씩 남기고 0.1 판에는 보는 화면을 만들지 않는다. 위젯 설정을 바꾼 기록을 물을 때 드는 선례다.
- 위젯 미리보기 페이지 서버는 설정 파일을 `web/apps/portal/server/load.ts` 88행의 `readFileSync`로 읽고, 그 폴더의 `serve.ts`, `start.ts`, `load.ts`에 파일을 지켜보는 코드(`watch`)는 없다(Grep).

## 인터뷰 라운드 5

본문에 FastAPI 백엔드가 왜 맞는지(Agent OS가 0.1 판에 파이썬으로 PostgreSQL을 들인다, FastAPI와 입력값 검사와 타입 검사와 테스트 도구가 이미 있다, 계약 파일에서 화면용 클라이언트를 만드는 방식이 이미 있다)와 치르는 값(띄우는 프로그램이 화면, 백엔드, 데이터베이스, 미리보기 페이지 서버로 는다, Node로 지은 미리보기 페이지 서버를 어떻게 할지 새로 정해야 한다, Node 드라이버 조사는 쓰지 않게 된다)을 적고 넷을 올렸다. 훅이 한 번 막았고 설명은 고치지 않고 다시 올렸다(위 조사 절의 사실로 댔다).

> 질문: FastAPI로 짓는 위젯 쪽 백엔드를 어디에 둘까요?
>
> 사용자: "이 저장소의 새 파이썬 패키지로 따로 (Recommended)" — 설명: Agent OS의 파이썬 패키지 옆에 위젯 쪽 백엔드의 패키지를 새로 두고, 자기 명령으로 따로 뜨는 프로그램으로 만듭니다. Agent OS의 코드를 가져다 쓰지 않고 HTTP로만 말하며(로그인 확인도 HTTP입니다), 그 경계를 지금의 import 검사 도구에 규칙으로 더합니다. FastAPI, 입력값 검사, 타입 검사, 테스트 도구는 이 저장소가 이미 쓰는 것이라 새로 드는 의존성은 PostgreSQL 쪽뿐입니다. 위젯이 이 저장소에 남아 있는 것(ADR 0047)과 같은 배치입니다. 대가는 띄우는 프로그램이 하나 늘고(위젯 쪽은 화면, 백엔드, 데이터베이스, 미리보기 페이지, 위젯이 됩니다), 계약 파일(openapi)과 거기서 만드는 화면용 클라이언트가 Agent OS 것과 따로 하나 더 생기며, 위젯 쪽 코드가 Agent OS와 같은 판 리듬과 잠금 파일에 묶인다는 것입니다. 문서 검색 서버 때는 같은 이유로 이 저장소 안에 두는 안을 거부했습니다(ADR 0048). 그때는 무거운 의존성이 문제였고 이번에는 이미 쓰는 의존성이라는 점이 다릅니다.

고르지 않은 안은 "Agent OS 서버 안에 경로로"와 "다른 저장소로"다.

> 질문: 지금의 미리보기 페이지 서버(Node로 지은 것)는 어떻게 할까요?
>
> 사용자: "그대로 두고 설정을 백엔드에서 받게 (Recommended)" — 설명: 미리보기 페이지 서버는 방문자에게 페이지를 내고 사이트 토큰을 내주는 지금의 일을 그대로 합니다. 화면에서 고친 사이트 목록, 보증 모드, 보고서 링크는 새 백엔드가 데이터베이스에 들고, 미리보기 페이지 서버가 그것을 백엔드에서 받아 옵니다(지금은 시작할 때 설정 파일을 읽습니다). 이미 지어 통과한 코드와 검사를 버리지 않습니다. 대가는 위젯 쪽 서버가 두 언어(파이썬 백엔드, Node 미리보기 서버)로 남고, 미리보기 서버가 백엔드에 기대어 백엔드가 내려가 있으면 새 설정을 받지 못한다는 것입니다.

고르지 않은 안은 "파이썬 백엔드로 옮겨 합치기"와 "그대로 두고 미리보기 설정은 파일로 남기기"다. 라운드 3의 "미리보기 페이지 서버를 키워 하나로"는 이 답과 앞의 답으로 바뀌었다. 미리보기 페이지 서버는 키우지 않고, 저장하는 일은 새 파이썬 백엔드가 맡는다.

> 질문: 파이썬에서 PostgreSQL을 쓰는 도구(드라이버와, 표를 만들고 올리는 도구)는 누가 고를까요?
>
> 사용자: "Agent OS 쪽이 고르는 것을 그대로 (Recommended)" — 설명: Agent OS에 데이터베이스를 들이는 행(postgres-foundation)이 고르는 드라이버, 표 관리 도구, 테스트와 CI가 데이터베이스를 띄우는 방법을 위젯 쪽 백엔드도 그대로 씁니다. 제품 안의 도구가 한 벌이고 이 행이 따로 재고 고를 것이 없습니다. 그 행의 앞 인터뷰가 후보를 이미 대 보았고 고르지는 않았습니다(그 행의 계획을 읽었고 결과 문서는 읽지 않았습니다). 대가는 이 행의 구현이 그 행의 설계가 끝날 때까지 기다린다는 것입니다(그 행은 release-image 뒤에 섭니다).

고르지 않은 안은 "이 행이 먼저 고르기"와 "따로 고르기"다. 이 답으로 이 행은 postgres-foundation을 기다린다.

> 질문: 누가 언제 위젯 설정을 바꿨는지 기록을 남길까요?
>
> 사용자: "바꿀 때마다 한 줄씩 남기기 (Recommended)" — 설명: 저장할 때마다 계정 이름, 시각, 사이트, 바뀐 항목의 이전 값과 새 값을 데이터베이스의 표에 한 줄씩 남깁니다. 로그인 주소처럼 방문자의 브라우저가 여는 값이 바뀌었을 때 누가 언제 바꿨는지 되짚을 수 있습니다. 0.1 판에는 그 기록을 보는 화면을 만들지 않습니다(Agent OS의 로그인 기록과 같은 방식입니다, ADR 0062). 위젯 설정에는 비밀 값을 두지 않으므로(ADR 0061) 값을 기록에 남겨도 됩니다. 대가는 표 하나와 저장할 때의 쓰기 하나가 늘고 기록이 계속 쌓인다는 것입니다.

고르지 않은 안은 "마지막으로 바꾼 사람과 시각만"과 "남기지 않기"다.

## 서브에이전트 보고: Node의 PostgreSQL 드라이버 후보

라운드 5의 답을 받는 사이에 보고가 왔다. 백엔드가 파이썬으로 정해져 이 결과는 고르지 않은 안의 것이다. 방향이 바뀐 것을 알려 범위를 줄이게 했고, 서브에이전트는 이미 끝난 실행만 적어 보고했다. 아래는 그 보고를 옮긴 것이고, 이 세션은 그 스크립트를 다시 돌리지 않았다. 스크립트와 README는 `.scratch/portal-admin/probes/pg_node/`에 미추적으로 있다. ADR이 이 결과를 근거로 들지 않으므로 커밋할지는 문서를 쓸 때 정한다.

- 후보는 `pg` 8.23.1(`@types/pg` 8.23.1)과 `postgres` 4.1.1이다. 환경은 Windows 10, node v24.19.0, pnpm 11.24.0, TypeScript 5.9.3, ESLint 10.11.0, typescript-eslint 8.70.1, Docker 엔진 29.9.2이고, PostgreSQL 이미지는 `postgres:18-alpine`(서버 18.7)으로 형제 워크트리의 `pg_stack/README.md`가 적은 태그와 같다고 보고했다. 이 워크트리의 `web/`에는 `node_modules`가 없어 저장소 밖 사본에 깔고 판정했다고 한다.
- 두 후보 모두 워크스페이스의 타입 검사를 지났고, 줄을 `unknown`으로 받아 좁히는 코드는 린트를 지났으며, 타입 없이 쓰는 대조 코드는 `@typescript-eslint/no-unsafe-assignment` 등으로 걸렸다고 보고했다. 제네릭 인자로 줄의 타입을 믿는 코드도 둘 다 린트를 지났는데, `number`라고 적은 `count(*)`가 실행 때 `string`이었다고 한다.
- 한글과 JSON이 든 줄을 넣고 읽기, 같은 볼륨으로 다시 띄운 뒤의 보존은 둘 다 됐다고 보고했다. 답 없는 포트에 기본값으로 붙을 때 `pg`는 감시 시간(40초)까지 오류 없이 기다렸고 `postgres`는 30초쯤에 `CONNECT_TIMEOUT`을 냈다고 한다.
- `postgres` 4.x는 첫 판이 2026-10-29이고 4.1.1은 2026-11-11에 올라왔으며 라이선스가 Unlicense이고 패키지 폴더에 라이선스 파일이 없다고 보고했다. `pg` 8.x는 첫 판이 2020-03-30이고 잠금에 패키지 15개가 새로 든다고 한다.
- 못 본 것으로 보고한 것: 리눅스와 컨테이너 안에서의 실행, 저장소의 `web/`에 실제로 더했을 때의 잠금 파일과 나머지 게이트, 트랜잭션과 연결 묶음과 마이그레이션 도구.

## 서브에이전트 보고: 위젯이 사이트 파일의 두 값을 실행 중에 얻으려 할 때 걸리는 것

읽기 전용 탐색 서브에이전트(Explore)의 보고다. 근거의 종류는 보고가 적은 대로 옮긴다. 이 세션이 따로 확인한 것은 앞 절의 `next.config.ts`와 프로브 README의 일부뿐이다.

- 두 값을 읽는 자리는 `web/apps/widget/lib/build.ts` 한 곳이다(코드를 읽었다). 허용 출처는 iframe 페이지가 토큰을 담은 `message`를 받을 때 보낸 쪽의 출처가 목록에 있는지 보는 데 쓰고(`components/pages/WidgetPage.tsx` 52행, `lib/token.ts` 32행), 요청 글자 수 상한은 입력창의 상한과 승인 거부 사유의 상한에 쓴다(`components/pages/ConnectedWidget.tsx` 77행에서 `WidgetScreen.tsx` 167행과 134행으로). 페이지 안 번들(`element.js`)에는 글자 수 상한만 들고 허용 출처는 싣지 않는다(`tools/element.ts` 13~14행 주석과 52~54행).
- 서버는 글자 수 상한을 토큰의 사이트마다의 값으로 검사하고(`src/agent_os/channel/http/end_user.py` 138행, `channel/http/limits.py` 74~93행), 위젯은 모든 사이트 가운데 가장 작은 값을 쓴다(코드를 읽었다). 루트 `openapi.json`에는 두 값이나 사이트 정보를 클라이언트에 돌려주는 경로가 없다(코드를 읽었다).
- 배포용 compose와 nginx 설정은 저장소에 아직 없고 `.scratch/` 아래 프로브뿐이다(`git ls-files`로 확인했다고 한다). `.scratch/release-image/spec.md` 267~302행의 프록시 설정에서 `add_header`는 HSTS 하나이고 CSP 머리를 프록시가 붙인다는 말은 없다. 같은 명세 211~217행은 위젯이 뜰 때 빌드하고 첫 200까지 13.6~40.7초, 빌드의 메모리 최고치 약 1.5GiB라고 적고, 228~229행은 상태 확인의 시작 유예를 위젯 300초로 둔다(문서를 읽었다).
- `.scratch/release-image/probes/widget_runtime/README.md` 결과 3번은 시작 전에 `.next/routes-manifest.json`의 `'none'`을 다른 값으로 바꿔 쓰자 proxy가 지나지 않는 경로(404, `element.js`, 글꼴)에 바꾼 값이 실렸다고 적는다. proxy 없이 이 길만으로 페이지의 머리를 내는 판은 돌리지 않았다(어림). 결과 5번은 `element.js`에 글자 수 상한을 주는 세 길을 견준다. 시작 때 다시 짓기는 서버까지 봤고(짓는 데 774~1804ms), 자리표로 지어 두고 숫자를 바꿔 넣기는 파일까지만 봤으며, 경로에서 받아 오기는 서버 쪽 절반만 봤다. 못 본 것에는 리눅스, 브라우저 동작, 앞단 프록시가 머리를 다는 길, 읽기 전용 디스크가 든다(문서를 읽었다).
- 사이트 파일을 푸는 코드는 두 벌이다. 파이썬은 `src/agent_os/main.py` 384~552행, TypeScript는 `web/packages/site-file/src/site-file.ts`이고, 위젯과 미리보기 페이지 서버가 뒤의 것을 함께 쓴다. 두 벌의 규칙은 `tests/fixtures/site_file/`의 픽스처를 양쪽 테스트가 읽어 맞춘다(코드와 문서를 읽었다).

## 조사: 라운드 6 앞에 대 본 것

- ADR 0062 결정 "두 단계와 권한 표"(13행. 처음에는 이름을 "계정과 권한"이라고 틀리게 적었고 셀프 리뷰의 표준 축이 잡아 고쳤다)는 운영자 계정의 단계를 둘로 정한다. 시스템 관리자는 하나이고 모든 일과 계정 관리를 한다. 관리자는 여럿이고 계정 관리만 빼고 모든 일을 한다. 0.1 판의 권한 이름은 다섯(보기, 플러그인 켜고 끄기, 실행 일으키기, 결정 내리기, 계정 다루기)이고, 권한을 골라 역할을 만드는 일은 새 행 admin-roles가 0.1 판 뒤에 맡는다(문서를 읽었다. 읽은 때는 형제 워크트리의 승인된 초안이었고 지금은 dev에 병합됐다).
- `.scratch/portal-admin/plan.md` 26행은 클라이언트 비밀이 설정이 파일 경로로 가리키는 값이라고 적는다(문서를 읽었다).
- `.scratch/release-image/probes/widget_runtime/README.md`는 지금 코드의 응답이 3.4ms 안쪽이고 실험 판이 3.9ms 이상이었다고 적는다(문서를 읽었다. Windows PC 한 대에서 돌린 결과이고 이 세션은 다시 돌리지 않았다).

## 인터뷰 라운드 6

질문 넷을 한 화면으로 올렸다. 훅이 처음 보는 화면이라 한 번 막았고, 위 사실을 대 본 뒤 같은 질문 문장과 라벨로 다시 올렸다.

질문 1: "허용 출처와 요청 글자 수 상한을 위젯이 빌드 없이 따르게 하는 방법은 어느 쪽으로 할까요?" 선택지는 "뜰 때 값만 바꿔 넣기 (Recommended)", "위젯 앱에 서버 쪽 파일을 허용해 요청 때마다 읽기", "Agent OS 서버가 값을 내주고 머리는 프록시가 붙이기"였다.

> 사용자: "뜰 때 값만 바꿔 넣기 (Recommended)" — 설명: 위젯 이미지는 미리 지어 두고, 컨테이너가 뜰 때 사이트 파일을 읽어 두 가지만 합니다. 위젯의 스크립트가 받아 갈 값 파일을 쓰고, 지어 둔 산출물에서 '품어도 되는 사이트' 머리의 값을 바꿔 넣습니다. 빌드가 없어져 뜨는 시간과 메모리가 줄고, 금지 규칙도 Agent OS의 계약도 고치지 않습니다. 사이트 파일을 푸는 코드도 늘지 않습니다(위젯 이미지에 이미 들어 있습니다). 대가는 사이트 파일을 고친 뒤에는 지금처럼 위젯을 다시 띄워야 한다는 것, 그리고 Next가 지어 내는 파일의 모양에 기대므로 Next의 판을 올릴 때 깨질 수 있어 시험으로 지켜야 한다는 것입니다. 예전 실험이 머리 바꿔 넣기와 값 다시 쓰기를 따로따로는 보았지만, 이 조합을 리눅스 컨테이너에서 처음부터 끝까지 돌려 본 적은 없습니다(어림). 그래서 구현의 첫 일이 이것을 재는 것이고, 서지 않으면 이 질문으로 돌아옵니다.

질문 2: "어느 계정이 위젯 설정을 고칠 수 있게 할까요?" 선택지는 "로그인한 운영자 계정 모두 (Recommended)", "시스템 관리자만", "주소 두 가지만 시스템 관리자"였다.

> 사용자: "로그인한 운영자 계정 모두 (Recommended)" — 설명: 시스템 관리자와 관리자가 모두 고칩니다. 0.1 판에는 계정이 그 두 단계뿐이고, 관리자는 Agent OS에서도 계정 관리만 빼고 모든 일을 합니다(ADR 0062). 위젯 쪽 백엔드는 '로그인이 유효한가'와 계정 이름만 확인하면 되어 Agent OS의 단계 이름을 몰라도 됩니다. 대가는 0.1 판 뒤에 역할 기능이 생겨 보기만 하는 계정 같은 것이 만들어지면, 그 계정이 위젯 설정을 고치지 못하게 그때 권한을 더해야 한다는 것입니다(그 일을 역할 기능의 계획에 적어 둡니다).

질문 3: "회사 로그인 서버 항목을 화면에서 고치게 될 때, 그 비밀 값(클라이언트 비밀)은 어떻게 다룰까요?" 선택지는 "화면은 비밀 값을 받지 않기 (Recommended)", "화면이 받아 데이터베이스에 암호화해 두기", "그 화면을 짓는 행의 설계에서 정하기"였다. 추천과 다른 안을 골랐다.

> 사용자: "그 화면을 짓는 행의 설계에서 정하기" — 설명: 이 인터뷰는 정하지 않고, 회사 로그인이 지어진 뒤에 서는 행의 설계 인터뷰로 넘깁니다. 그 화면은 어차피 회사 로그인(portal-login)이 지어진 뒤에 짓습니다. 대가는 그때 이 질문을 다시 받으신다는 것이고, 그 전까지 이 설계는 '위젯 쪽 데이터베이스에 비밀 값을 두지 않는다'까지만 적습니다.

질문 4: "지금 설정 파일에 적혀 있는 값(위젯의 이름, 소개, 색, 고지, 사이트 목록 등)은 데이터베이스로 어떻게 옮길까요?" 선택지는 "파일을 읽어 넣는 명령 하나 (Recommended)", "백엔드가 처음 뜰 때 저절로", "옮기지 않고 화면에서 새로 입력"이었다. 추천과 다른 안을 골랐다.

> 사용자: "옮기지 않고 화면에서 새로 입력" — 설명: 옮기는 길을 짓지 않습니다. 0.1 판이 처음 내는 판이라 옮길 운영 데이터가 거의 없습니다. 대가는 시험과 예시 배포가 처음 값을 넣는 다른 길(화면을 거치거나 백엔드의 주소를 직접 부르기)이 따로 필요하고, 지금 예시로 적어 둔 값을 손으로 다시 넣어야 한다는 것입니다.

질문 3의 답으로 회사 로그인 서버 항목을 화면에서 고치는 일은 portal-login 뒤의 새 행이 되고, 그 행이 설계 인터뷰를 따로 한다. 질문 4의 답으로 처음 배포한 직후의 데이터베이스는 비어 있다. 그때 위젯 미리보기 페이지가 무엇을 보이는지와 시험이 값을 넣는 길은 합의 요약에서 확인받는다.

- ADR 0062 22행: 짧은 JWT의 수명은 1~15분이고 기본은 5분이다. 28행: 계약에 느는 경로에 갱신과 지금 누구인지가 든다(문서를 읽었다).

## 인터뷰 라운드 7

질문 둘을 한 화면으로 올렸다. 훅이 한 번 막았고, 위 사실을 대 본 뒤 설명 둘을 고쳐 같은 질문 문장과 라벨로 다시 올렸다. 고친 것은 둘째 선택지에 "화면을 그리는 일은 기다리지 않습니다"와 지금 계획 표의 의존을 더한 것, 이름 질문의 둘째 선택지에서 "임시로 쓰던"을 "용어집에 올리지 않은 채 쓰던"으로 바꾼 것이다.

질문 1: "이 일을 전체 계획의 표에서 몇 줄(행)로 나눌까요?" 선택지는 "저장과 읽기를 먼저 떼어 넷으로 (Recommended)", "서버와 화면을 한 줄로, 셋으로", "한 줄에 모두, 로그인 서버 항목 화면만 따로"였다.

> 사용자: "저장과 읽기를 먼저 떼어 넷으로 (Recommended)" — 설명: 네 줄로 나눕니다. 첫째는 위젯 설정을 데이터베이스에 두고 위젯이 받아 가는 주소를 내는 서버입니다(Agent OS가 PostgreSQL을 들인 뒤). 둘째는 운영자가 쓰는 화면과 로그인 확인, 바꾼 기록, 미리보기 페이지의 사이트 목록을 화면에서 고치는 일입니다(첫째와 운영자 로그인 뒤). 셋째는 위젯이 허용 출처와 글자 수 상한을 뜰 때 받는 일입니다(이미지 짓기 뒤, 나머지와 무관). 넷째는 회사 로그인 서버 항목을 고치는 화면입니다(회사 로그인 뒤, 설계 인터뷰를 따로). 위젯이 로그인 상태를 그리는 일과 그 뒤의 회사 로그인이 첫째만 기다리므로, 운영자 로그인과 나란히 갑니다. 대가는 줄이 늘어 명세와 리뷰가 그만큼 늘고, 첫째가 끝난 때에는 값을 넣을 화면이 아직 없어 시험이 데이터베이스에 값을 직접 넣어야 한다는 것입니다.

질문 2: "새로 짓는 화면과 그 서버를 문서에서 어떤 이름으로 부를까요?" 선택지는 "위젯 관리 화면과 위젯 관리 서버 (Recommended)", "위젯 설정 관리 화면과 위젯 설정 서버"였다.

> 사용자: "위젯 관리 화면과 위젯 관리 서버 (Recommended)" — 설명: 앞서 쓰신 '위젯 관리자 페이지'에 가까운 이름입니다. 이 화면은 위젯 설정 말고도 미리보기 페이지의 사이트 목록과 '테스트' 메뉴, 나중에는 회사 로그인 서버 항목까지 담으므로 넓은 이름이 맞습니다. 대가는 Agent OS의 '관리 화면'과 낱말 하나 차이라 줄여 쓰면 섞인다는 것입니다. 그래서 용어집에 '관리 화면'으로 줄여 쓰지 않는다고 적고, 계획 문서들이 쓰던 '위젯 설정 관리 화면'을 새 이름으로 고칩니다.

## 합의 요약과 확인

frontier가 비어 아래 요약을 본문에 올리고 확인받았다. 이 결정은 에이전트가 단계대로 따르는 절차(스킬, 훅, 브랜치와 병합의 규약)를 바꾸지 않아 갈래 밟기는 하지 않았다. 요약은 사용자에게 보인 글 그대로다.

### 1. 무엇을 짓는가

| 새로 생기는 것 | 모양 |
|---|---|
| 위젯 관리 서버 | FastAPI(파이썬)로 짓는 새 프로그램입니다. 이 저장소 안의 새 패키지이지만 Agent OS의 코드를 가져다 쓰지 않고 HTTP로만 말하며, 그 경계를 검사 규칙으로 막습니다. 자기 PostgreSQL 컨테이너를 따로 씁니다. 드라이버, 표를 만들고 올리는 도구, 테스트가 데이터베이스를 띄우는 방법은 Agent OS 쪽이 고르는 것을 그대로 따릅니다. |
| 위젯 관리 화면 | 새 Next 앱입니다. Agent OS의 관리 화면과 포트만 다른 주소에 엽니다. 운영자 계정으로 함께 로그인하고, 로그인한 운영자 계정은 모두 고칠 수 있습니다. |
| 위젯 미리보기 페이지 서버 | 지금의 Node 서버를 그대로 둡니다. 사이트 목록, 보증 모드, 보고서 링크만 위젯 관리 서버에서 받아 옵니다. |
| 위젯 | 위젯 설정을 위젯 관리 서버의 공개 주소에서 받아 옵니다. 허용 출처와 글자 수 상한은 컨테이너가 뜰 때 값만 바꿔 넣어 빌드 없이 따릅니다. |

### 2. 위젯 관리 화면에서 하는 일(0.1 판)

- 위젯 설정 등록: ADR 0061이 정한 목록에 로그인 단추의 문구, URL 방식 창의 탭 제목, 첫 화면의 예시 질문, 문의 링크, 밝기 스위치 숨기기를 더합니다.
- 미리보기 페이지의 사이트 목록, 보증 모드, 보고서 링크를 고칩니다.
- "테스트" 메뉴가 위젯 미리보기 페이지를 엽니다. 공개 주소는 그대로 남고, 저장하기 전에 미리 보는 기능은 없습니다.
- 로그인 주소와 로그아웃 주소는 형식만 검사합니다.
- 고지의 고정 문장은 화면이 처음 값으로 채워 주고, 운영자가 지우면 빠집니다.
- 바꿀 때마다 기록을 한 줄씩 데이터베이스에 남깁니다. 보는 화면은 0.1 판에 없습니다.
- 0.1 판 뒤로 미루는 것: 허용 출처와 글자 수 상한을 화면에서 고치는 일(새 행), 그림 올리기와 자유 색(기존 행).

### 3. 행과 순서

| 행 | 하는 일 | 기다리는 것 |
|---|---|---|
| ① 위젯 관리 서버(새 행) | 서버의 뼈대, 데이터베이스, 위젯이 위젯 설정을 받아 가는 주소 | Agent OS의 PostgreSQL 들이기 |
| ② 위젯 관리 화면(지금의 portal-admin) | 화면, 로그인 확인, 저장 주소, 바꾼 기록, 미리보기 설정을 데이터베이스로 | ①, 운영자 로그인, 위젯의 로그인 상태 그리기 |
| ③ 위젯의 뜰 때 값 받기(새 행) | 위젯 이미지를 미리 짓고 뜰 때 값만 바꿔 넣기 | 이미지 짓기 |
| ④ 회사 로그인 서버 항목 화면(새 행) | 그 항목을 화면에서 고치기. 비밀 값은 이 행의 설계 인터뷰가 정함 | 회사 로그인, ② |
| ⑤ 허용 출처와 상한을 화면에서(새 행, 0.1 판 뒤) | 설계부터 따로 | 0.1 판 |

위젯의 로그인 상태 그리기(widget-login-state)는 ②가 아니라 ①을 기다리게 바뀝니다. ①~④는 모두 0.1 판을 내는 조건입니다.

### 4. 이 요약에서 처음 확인받는 것

질문으로 따로 올리지 않았지만 앞선 답에서 따라 나오는 것들입니다.

1. 처음 배포한 직후에는 데이터베이스가 비어 있습니다. 미리보기 페이지 주소를 열면 "등록된 사이트가 없습니다"라는 안내가 보이고, 운영자가 위젯 관리 화면에서 첫 사이트를 등록해야 위젯이 뜹니다. 시험은 화면이 쓰는 저장 주소를 직접 불러 값을 넣습니다(①만 있는 동안에는 데이터베이스에 직접 넣습니다).
2. 화면에서 저장한 값은 아무것도 다시 띄우지 않아도, 다음에 위젯이나 미리보기 페이지를 열 때 반영됩니다.
3. 미리보기 페이지의 설정 파일에는 시작에 필요한 값(공개 주소, 서명 키의 경로, 포트 같은 것)만 남습니다. 위젯의 이름, 소개, 색, 밝기, 고지 칸은 위젯의 로그인 상태 그리기 행에서 빠집니다. 파일에 남겨 두면 파일의 값이 데이터베이스의 값을 덮어, 화면에서 고쳐도 미리보기 페이지의 위젯이 바뀌지 않기 때문입니다.
4. 로그인 쿠키: 두 화면은 포트만 다른 같은 주소라서, 브라우저가 운영자의 로그인 쿠키를 위젯 관리 화면에도 보냅니다. 위젯 관리 서버는 그 쿠키를 Agent OS에 그대로 전해 "지금 누구인지"를 확인하고, 저장하거나 기록하지 않습니다. 로그인을 5분마다(기본값) 이어 주는 일도 위젯 관리 서버가 대신 전합니다. 대가는 위젯 관리 서버가 뚫리면 운영자의 로그인 상태가 드러날 수 있다는 것입니다. 이 조합은 규격으로 아는 것이고 아직 돌려 보지 않았으므로(어림), ②의 명세가 먼저 확인합니다.
5. Agent OS의 관리 화면에는 위젯 관리 화면으로 가는 링크를 두지 않습니다. Agent OS는 위젯을 모른다는 결정(ADR 0047)을 그대로 지키고, 주소는 배포 안내에 적습니다.
6. 띄우는 것이 늘어납니다. 컨테이너가 셋(위젯 관리 서버, 위젯 관리 화면, 위젯 쪽 PostgreSQL), 인터넷에 여는 포트가 하나, 백업할 데이터베이스가 하나 더 생깁니다. Agent OS 쪽 PostgreSQL까지 더하면 0.1 판의 단독 배포는 컨테이너가 다섯에서 아홉이 됩니다.
7. 위젯 설정을 받아 가는 주소는 위젯과 같은 공개 주소 아래의 정해진 경로이고, 로그인 없이 누구나 읽습니다(그래서 비밀을 두지 않습니다). 답의 세부 모양은 ①의 명세가 정합니다. 저장하는 주소는 다른 사이트에서 온 요청을 Agent OS와 같은 규칙으로 거절합니다.
8. 함께 고치는 문서: 용어집에 "위젯 관리 화면"과 "위젯 관리 서버"를 올리고, 새 ADR 하나를 쓰며, 이 결정이 바꾸는 앞선 ADR들(0061, 0050, 0059, 0056, 0047, 0046 등)에 이력과 표시를 답니다. 기능 계획은 위의 다섯 행과, 영향을 받는 행(위젯의 로그인 상태 그리기, 이미지 짓기, 배포 꾸러미, 백업, 역할 기능 등)을 고칩니다.

질문: "위 합의 요약대로 용어집과 ADR 초안과 기능 계획을 써도 될까요?" 선택지는 "이대로 쓰기 (Recommended)", "고칠 곳이 있음"이었다.

> 사용자: "이대로 쓰기 (Recommended)" — 설명: 요약의 1~4를 그대로 문서로 옮깁니다. 용어집에 이름 둘을 올리고, 새 ADR 초안을 쓰고, 기능 계획을 다섯 행으로 나눕니다. ADR 초안은 셀프 리뷰를 반영한 뒤에 다시 보여 드리고 승인을 받습니다. 그 승인 전에는 커밋하지 않습니다. 요약 4의 6번에 적은 컨테이너의 수(다섯에서 아홉)는 지금 계획대로일 때의 셈이고, Agent OS 쪽 데이터베이스의 배치는 그 행의 설계가 정합니다(어림).

## 문서를 썼다

합의 요약대로 문서를 썼다. 커밋은 하지 않았다. ADR 초안은 셀프 리뷰를 반영한 뒤 사용자에게 보여 승인을 받는다.

- 용어집(`CONTEXT.md`): 위젯 관리 화면과 위젯 관리 서버를 더했고, 위젯 미리보기 페이지 설정의 뜻을 저장 방식과 무관한 글로 고쳤다.
- ADR 0064 초안(`status: proposed`). 틀은 ADR 0061·0062와 같다(결정, Considered Options, Consequences).
- ADR 0046 이력 2026-11-15 "위젯 설정 관리가 행 넷으로 나뉘고 셋이 기준선의 행으로 더해진다".
- 기능 계획. 새로 쓴 것 넷(widget-admin-server, widget-runtime-values, portal-login-admin, site-limits-admin), 다시 쓴 것 하나(portal-admin), Blocked by나 넘기는 문장을 고친 것 열하나(widget-login-state, pilot-release, widget-appearance, portal-ldap-login, postgres-foundation, deploy-package, ops-backup-upgrade, admin-roles, portal-login, admin-login, release-image). release-image는 진행 중인 기능이라 계획의 한 문장, 명세의 Out of Scope 한 항목, 티켓 08의 "시작하기 전에" 한 줄만 고쳤다. 셋 다 "portal-admin이 release-image보다 먼저 돌 수 있다"는 전제를 적은 자리였고, 그 일이 release-image를 기다리는 widget-runtime-values로 옮겨 가며 틀린 말이 됐다. 전체 계획 표는 `uv run python tools/plan_table.py`로 다시 지었다.
- 헌법. `docs/constitution/tech.md` 끝에 문단 하나를 더했다(위젯 관리 서버는 배포가 갈리는 둘째 파이썬 패키지이고 위젯 관리 화면은 새 Next 앱이다. 구현 티켓이 들이기 전까지 저장소에 없고 표는 그대로다). 그래서 판을 3.0.100에서 3.0.102로 올렸다. 3.0.101은 형제 PR 578(`feature/05-openai-compatible-adapter-and-local-model-test`)이 먼저 매겼다(`git show origin/feature/05-openai-compatible-adapter-and-local-model-test:docs/constitution/README.md`로 판 줄을 봤다). 헌법 개정은 ADR 0064의 승인으로 사용자가 승인한다.
- PRD. 기준선 성공 조건의 괄호 문장이 "(밖으로 여는 포트는 방문자용 하나와, 로그인으로 지키는 관리 화면용 하나다)"였다. 위젯 관리 화면이 포트를 하나 더 열므로 "…관리 화면용 하나와 위젯 관리 화면용 하나다"로 고쳐 두었다. PRD는 사용자 승인으로 고치는 문서라 승인 화면에서 함께 묻는다. 서브에이전트의 보고에는 없던 자리이고, `밖으로 여는 포트`로 Grep해 찾았다.

### 합의 요약에 없던 것

합의 요약을 확인받은 화면에 없었고 문서를 쓰며 정한 것이다. ADR 0064 결정 "승인 때 함께 확인받는 세부"에 같은 목록을 두고 승인 화면에서 확인받는다.

- 위젯 미리보기 페이지 설정 파일에서 빼는 칸에 에이전트(`agent`)를 더했다. 요약은 이름, 소개, 색, 밝기, 고지 다섯을 적었다. 에이전트도 ADR 0061이 위젯 설정에 등록하게 한 값이고(그 ADR 결정 "위젯 설정"과 "0.1 판에서 등록하는 것"), 파일에 남으면 같은 까닭으로 화면에서 고친 값이 닿지 않는다.
- 위젯 관리 화면의 포트도 TLS는 앞단의 프록시가 끝낸다. 운영자의 로그인 쿠키가 `https`와 `localhost`에서만 저장된다는 것은 ADR 0062 결정 "로그인 상태"가 쿠키 프로브로 든 것이다(이 세션은 그 프로브를 다시 돌리지 않았다).
- 위젯 관리 서버가 Agent OS에 부르는 경로를 "지금 누구인지"와 "갱신" 둘로 고정하고 시험으로 지킨다.
- 위젯 설정을 받아 가는 경로는 다른 출처의 페이지에서도 읽을 수 있게 열고, 저장 경로는 위젯 관리 화면의 포트에만 둔다.
- 백업은 묶지 않고 데이터베이스마다 하되 방법과 맡는 행은 postgres-foundation의 설계가 Agent OS 쪽에 정하는 것을 따른다.
- 새 행의 슬러그와 Blocked by. 합의 요약의 가칭을 그대로 썼다. site-limits-admin은 슬라이스 10이고 widget-runtime-values와 pilot-release를 기다린다.
- release-image, ops-backup-upgrade, deploy-package에는 Blocked by를 더하지 않았다(ADR 0046 이력 2026-11-14가 이 인터뷰에 맡긴 물음이다). 위젯 쪽의 컨테이너는 widget-admin-server와 portal-admin의 명세가 release-image의 단독 compose 위에 더한다. 이 가운데 deploy-package는 셀프 리뷰 뒤에 바뀌었다. 명세 축이 짚어 그 행의 Blocked by에 portal-admin을 더했다(아래 "명세 축의 보고").
- portal-login과 portal-admin 가운데 어느 쪽이 먼저 끝날지 정해져 있지 않다. 사이트가 자기가 쓰는 로그인 서버 항목의 이름을 어디에서 가리키는지는 뒤에 끝나는 행의 명세가 정한다.
- PRD의 포트 문장과 헌법의 판(위에 적었다).
- 시작 검사가 가는 자리. 위젯 미리보기 페이지의 서버는 뜰 때 설정 파일과 사이트 파일을 대 보고 어긋나면 뜨지 않는다(ADR 0050 결정 "시작 인자와 시작 검사"). 사이트의 목록이 데이터베이스로 가면 그 검사가 뜰 때 한 번으로 설 수 없다. 인터뷰에서 묻지 않은 자리이고 둘째 서브에이전트의 보고가 짚었다. 초안은 세 자리로 갈랐다. 저장할 때 위젯 관리 서버가 모양과 이름·발급자의 겹침을 보고 거절한다. 위젯 미리보기 페이지의 서버가 목록을 받아 올 때 사이트 파일과 자기 키로 볼 수 있는 것을 사이트마다 보고, 어긋난 사이트만 닫는다. 뜰 때는 파일에 남은 시작 값만 본다. 대가는 틀린 설정이 "뜨지 않는다"가 아니라 "그 사이트만 닫힌다"로 드러난다는 것이다. 승인 화면에서 따로 묻는다.
- 배포에 느는 것. 판마다 짓는 이미지가 넷에서 여섯이 되고, 새 프로세스 둘도 루프백 규칙과 그 예외(ADR 0056)를 따른다. 고른 것에서 따라 나오는 것을 모아 적었다.
- 관리 화면의 탭과 위젯 관리 화면의 탭이 동시에 갱신하는 경우는 ADR 0062가 명세에 넘긴 "탭 둘이 동시에 갱신할 때의 짧은 유예"와 같은 경우로 다룬다.
- 로그인한 운영자 계정이면 사이트의 보증 모드와 발급자도 바꿀 수 있다. 지금은 서버의 파일을 고칠 수 있는 사람만 하던 일이다. ADR 0064 Consequences "신뢰와 노출"에 적었다.

### 앞선 ADR의 포인터

ADR 0064가 본문의 문장을 바꾸는 앞선 ADR에 `(바뀜: ADR 0064)`를 달았다. ADR 0061(다크 모드 스위치가 모든 위젯에 보인다는 문장들, 0.1 판에서 등록하는 것의 목록, widget-login-state가 portal-admin을 기다린다는 문장들), ADR 0050(설정이 사이트 여럿의 목록이고 시작 때 대 본다는 문장들, 익명 식별자 문장을 늘 넣는다는 문장, 페이지가 싣는 공개 설정과 속성 다섯, portal-admin 행의 자리), ADR 0059(없는 로그인 서버 항목을 가리키면 시작에서 구성 오류라는 문장, 계정 문장을 늘 넣는다는 문장, 로그인 방식을 화면에서 고르는 일을 portal-admin이 맡는다는 문장), ADR 0056(이미지 넷, 컨테이너 다섯, 호스트에 발행하는 포트, 프록시가 넘기는 경로, 위젯이 뜰 때 빌드한다는 결정, portal-admin 계획에 넘긴 요구), ADR 0047과 ADR 0024와 ADR 0023(허용 출처가 위젯 빌드의 입력이라는 문장들, 프록시가 넘기는 경로), ADR 0062(쿠키가 다른 포트에 실리는 한계가 방문자용 서버의 일이라는 문장)다. `open-session` 3의 `pwsh -NoProfile -File C:\project\agent\tools\open_session.ps1 -Action send …` 호출을 자동 권한 분류기가 거부했다(사유는 "Unsanctioned Communication"). 딥링크를 쏘기 전이라 새 세션은 생기지 않았다. 같은 호출을 다시 치지 않았고 다른 길로 돌아가지 않았다. 제목을 `docs/portal-admin-design`으로 되돌렸다. 워크트리의 잠금은 다시 걸지 않았다(`handoff.md` 4). 이 세션이 셀프 리뷰부터 잇고, 컨텍스트는 자동 압축이 받는다. 위 "새 세션에 낸 지시문"은 보내지지 않았다.

인계하지 못해 이 세션이 `/code-review`를 그대로 밟았다. 범위는 base `0c25ea79c795bb780aed36b079ecbd68d66e4f86`, 바뀐 파일 29개, 커밋 0개, 미추적 6개(새 계획 넷, ADR 0064, 이 일지)다. 표준 축은 sonnet·high 서브에이전트, 명세 축은 모델을 주지 않은 서브에이전트다. 명세는 이 일지의 라운드 1~7의 답과 합의 요약 1~4를 요구로, "문서를 썼다" 아래를 리뷰어 참고로 갈라 넘겼다. 그 전에 `uv run python tools/sibling_overlap.py`를 돌렸다. ADR 번호 0064와 헌법 판 3.0.102는 겹치지 않았고, 함께 고친 파일은 PR 578의 `docs/constitution/README.md`와 `docs/constitution/tech.md`, 워크트리 `mcp-shutdown-spec`의 `.scratch/plan.md`, 워크트리 `widget-login-state-screens`의 `.scratch/widget-login-state/plan.md`였다(명령의 출력을 읽었다).

### 표준 축의 보고

Critical과 Major는 없었다. Minor 여섯과 Nit 둘이다. 보고는 수로 닫은 주장, 사용자 답 인용 34개, 코드와 명세를 든 주장, 계획의 필드와 Blocked by, 헌법의 판, 살아 있는 문서의 잔존이 맞았다고 적었다(서브에이전트가 Read와 Grep으로 본 것이다). 지적마다 원문을 다시 열어 판정했다.

고친 것.

- ADR 0064 결정 "고칠 수 있는 계정"이 든 ADR 0062의 결정 이름이 틀렸다. `(ADR 0062 결정 "두 단계와 권한 표")`로 고쳤다(ADR 0062의 결정 머리를 Grep으로 봤다). 이 일지의 "조사: 라운드 6 앞에 대 본 것"의 같은 이름도 고쳤다.
- ADR 0056에 포인터 둘을 더했다. 결정 "레지스트리와 계정"의 "그 아래에 네 이미지를 공개로 올린다"와 결정 "루프백 규칙의 예외"의 "그래서 네 곳의 시작 검사에 예외를 둔다" 뒤다. 앞서 "네 프로세스"를 그때의 수로 보아 달지 않았는데, 같은 ADR의 "이미지 넷"과 "컨테이너 다섯"에는 달아 두어 본문만 읽으면 지금의 수를 잘못 알게 된다.
- 포인터의 자리 둘을 옮겼다. ADR 0056 결정 "밖으로 여는 포트"에서는 "셋은 한 공개 출처 아래에 선다." 뒤로 옮겨 이어진 두 문장을 묶었다. ADR 0061 Consequences "다른 행"에서는 "슬라이스 9이고 portal-admin을 기다린다." 바로 뒤로 옮겼다. 바뀌는 문장이 그것이고 다음 문장은 그대로 참이다.
- `CONTEXT.md`의 로그인 서버 항목. "위젯 미리보기 페이지 설정에 로그인 서버 하나를 이름 붙여 적은 것"이 고친 위젯 미리보기 페이지 설정의 뜻(운영자가 위젯 관리 화면에서 등록하는 값의 묶음)과 어긋났다. 그 항목은 portal-login-admin이 화면으로 옮길 때까지 파일에 남는다. 두는 자리를 말하지 않게 "위젯 미리보기 페이지가 로그인을 맡기는 로그인 서버 하나를 이름 붙여 적은 것."으로 고쳤다.
- ADR 0064 결정 "허용 출처와 요청 글자 수 상한"의 수. "뜰 때의 빌드에 13.6~40.7초와 약 1.5GiB"라고 적었는데 명세의 13.6~40.7초는 컨테이너 시작에서 첫 200까지의 시간이다. "release-image의 명세는 위젯 컨테이너가 시작해 첫 응답을 내기까지 13.6~40.7초, 뜰 때의 빌드의 메모리 최고치로 1,452~1,567MiB를 적는다. `.scratch/release-image/spec.md`의 "이미지의 구성"을 읽었다"로 고쳤다(그 명세 213행을 읽었다. 그 값은 명세가 프로브로 쟀다고 적은 것이고 이 세션은 돌리지 않았다).

남긴 것과 이유.

- ADR 0046의 새 이력이 PRD의 문장을 "사용자 승인으로 고쳤다"고 과거형으로 적은 것. 커밋은 사용자의 승인 뒤에만 하므로 커밋되는 글은 참이 된다. 승인받지 못하면 그 문장과 PRD를 함께 되돌린다.
- ADR 0061 결정 "기능 행"의 포인터 자리. "순서는 …"과 "widget-login-state가 portal-admin을 기다리는 까닭은 …"이 이어진 문장이고 둘 다 바뀌어, 묶음 끝에 하나를 단 것이 규칙대로다(`.claude/rules/adr.md`의 "이어진 문장 여럿을 바꿨으면 그 묶음에 하나만 단다").
- ADR 0056 Consequences "다른 행"의 포인터. 그때 한 일을 적은 문장이라는 지적이다. 본문만 읽으면 두 값을 화면에서 바꾸는 요구가 portal-admin의 것으로 읽히고, ADR 0061이 ADR 0050의 "다른 행"에 같은 꼴로 단 선례가 있어 그대로 두었다.
- ADR 0046 이력 제목의 "행 넷"과 ADR 0064의 "행 다섯". 앞의 것은 기준선의 행 넷이고 뒤의 것은 0.1 판 뒤의 한 행까지 센 것이라 뜻이 다르다.
- Blocked by와 수가 ADR, 이력, 기능 계획, 표에 되풀이된다는 표지. 표는 기능 계획에서 짓는 생성물이고 이력은 기록이다. 서로 맞는 것을 보고가 확인했다.

질문 3: "운영자가 위젯 관리 화면에서 등록한 사이트 하나가 Agent OS의 사이트 파일과 맞지 않을 때(예: 사이트 파일에 없는 발급자로 등록), 어떻게 처리할까요? 인터뷰에서 여쭙지 않고 초안을 쓰며 정한 자리입니다." 선택지는 "그 사이트만 닫기 (Recommended)", "하나라도 틀리면 전체 닫기", "저장할 때 막기"였다.

### 질문 3을 다시 물었다

사이트 파일을 쉬운 말로 풀어 본문에 적었다. Agent OS 서버에 놓인 출입 명부 파일이고, 사이트마다 발급자, 공개 키, 허용 출처, 열 에이전트, 상한을 들며, 0.1 판에서는 운영자가 서버에서 직접 고친다(`CONTEXT.md`의 사이트 파일 항목과 ADR 0056 결정 "사이트 파일을 고치면"을 읽었다). 질문 문장을 바꿔 다시 올렸고 훅이 한 번 더 막았다. 막힌 뒤 첫 선택지의 설명에서 "명부나 화면의 값을 고치면 다시 열립니다"를 고쳤다. 사이트 파일은 `serve`와 위젯 미리보기 페이지와 위젯이 뜰 때 한 번 읽으므로(ADR 0056 29행을 읽었다) 명부 쪽을 고친 때에는 다시 띄워야 한다.

질문: "Agent OS 서버에는 '어느 사이트의 질문을 받아 줄지'를 적어 둔 출입 명부 파일(사이트 파일)이 있고, 운영자가 서버에서 직접 고칩니다. 운영자가 위젯 관리 화면에서 등록한 사이트의 이름표(발급자)가 그 명부에 없으면 어떻게 처리할까요?" 선택지는 "그 사이트만 닫기 (Recommended)", "하나라도 틀리면 전체 닫기", "저장할 때 막기"였다.

> 사용자: "그 사이트만 닫기 (Recommended)" — 설명: 저장은 되지만 미리보기 페이지가 그 사이트만 열어 주지 않고, 다른 사이트는 그대로 뜹니다. 위젯 관리 화면이 운영자에게 '이 사이트는 명부와 맞지 않아 닫혀 있다'는 알림을 보여 줍니다(알림의 모양은 다음 단계의 명세가 정합니다). 운영자가 화면의 값을 고치면 다시 열리고, 명부 쪽을 고쳤다면 지금처럼 서버를 다시 띄운 뒤에 열립니다. 사이트의 이름이나 발급자가 다른 사이트와 겹치는 것은 저장할 때 바로 거절합니다. 대가: 지금은 값이 하나라도 틀리면 미리보기 페이지 서버가 아예 뜨지 않아 바로 드러나는데(지금 코드를 읽어 확인했습니다), 앞으로는 운영자가 화면의 알림이나 로그를 봐야 알 수 있습니다.

고르지 않은 두 선택지의 설명은 이렇다. "하나라도 틀리면 전체 닫기"는 "지금의 동작에 가깝게, 명부와 맞지 않는 사이트가 하나라도 있으면 미리보기 페이지가 어느 사이트도 열어 주지 않습니다. 틀린 것이 바로 드러납니다. 대가: 화면에서 사이트 하나를 잘못 저장하면 멀쩡한 다른 사이트의 위젯도 함께 멈춥니다."였다. "저장할 때 막기"는 "위젯 관리 서버가 저장하는 순간에 Agent OS의 명부 파일까지 읽어, 명부에 없는 발급자면 저장을 거절하고 화면에 바로 오류를 보여 줍니다. 틀린 값이 아예 들어가지 않습니다. 대가: 위젯 관리 서버에 명부 파일을 읽는 코드를 하나 더 지어야 하고(앞선 계획 문서는 지금 읽는 곳을 Agent OS 서버, 미리보기 페이지 서버, 위젯 빌드 세 곳으로 적습니다), 저장한 뒤에 운영자가 명부 파일을 고쳐서 어긋나는 경우는 여전히 막지 못해 그때의 처리가 따로 필요합니다."였다.

넷이 모두 승인됐다. 반영한 것은 이렇다. ADR 0064의 `status`와 색인 행을 `accepted`로 바꿨다. 결정 "시작 검사가 가는 자리"에 고른 설명의 조건 하나("운영자가 화면의 값을 고치면 그 사이트는 다시 열리고, 사이트 파일 쪽을 고쳤으면 지금처럼 다시 띄운 뒤에 열린다(ADR 0056 결정 "사이트 파일을 고치면")")와 승인 화면에서 물었다는 문장을 넣었다. 고르지 않은 두 선택지를 Considered Options에 한 항목으로 넣었다. 결정 "승인 때 함께 확인받는 세부"의 머리를 승인받은 뒤의 글로 고쳤다. PRD의 포트 문장과 deploy-package의 Blocked by는 이미 고쳐 둔 그대로다.

서브에이전트가 읽고 찾은 것과 이 세션의 판정.

- 쿠키를 전하는 길. 대상 경로가 둘로 닫혀 있고 쿠키를 저장하거나 기록하지 않는다는 문장이 있다. 갱신 때 되돌리는 `Set-Cookie`의 속성을 바꾸지 않는다는 서술이 없다. 판정: 유효(작다). 결정 "로그인"의 "그대로 실어"가 뜻하는 바이지만 명세가 확인할 항목으로 넘겼다.
- 다른 사이트에서 온 저장 요청. 거절 규칙은 적혀 있다. `Sec-Fetch-Site`가 없는 요청을 받는 것은 "Agent OS와 같은 규칙"이라는 문장이 이미 뜻한다(ADR 0062가 받아들인 한계와 같다). 판정: 남긴다. 다른 출처에 여는 응답 머리를 읽는 경로에만 단다는 서술이 없다는 것은 유효이고 명세에 넘겼다.
- 저장하는 주소의 검사. `javascript:`와 엉뚱한 도메인은 ADR이 적었다. `http://localhost` 예외를 앞 글자만 견주면 `http://localhost.example.test` 같은 주소가 지나간다는 서술이 없다. 판정: 유효. 명세에 시험으로 넘겼다.

- 바꾼 기록. 남기는 것의 목록(계정 이름, 시각, 사이트, 바뀐 항목의 이전 값과 새 값)이 닫혀 있고 쿠키는 저장하거나 기록하지 않는다고 적혀 있다. 판정: 남긴다. 기록의 보관 기간은 결정 "바꾼 기록"이 "기록이 계속 쌓인다"를 대가로 적었다.

고친 것. 모두 ADR 0064 Consequences "명세가 짓는 것"에 명세가 정할 것으로 더했고 결정은 바꾸지 않았다. ADR은 승인된 뒤이므로 그 문단에 승인 뒤에 더했다는 문장을 넣었다. 새로 쓴 문장은 아래와 같다.

- widget-admin-server의 명세: "그 명세는 셋을 더 적는다. 위젯 설정을 받아 가는 경로의 답이 위젯 설정의 항목만 싣는다는 것(같은 데이터베이스에 드는 위젯 미리보기 페이지 설정과 바꾼 기록, 나중에 들 수 있는 로그인 서버 항목이 그 경로로 나가지 않게 한다), 다른 출처에 여는 응답 머리를 그 읽는 경로에만 단다는 것, 누구나 읽는 그 경로의 요청 수를 제한할지다."
- portal-admin의 명세: "그 명세는 넷을 더 정한다. 첫째, 입력값 검사에서 로그인 주소와 로그아웃 주소의 사용자 정보 자리(`user:pw@`)와 쿼리에 든 값을 받을지다. 위젯 설정은 누구나 읽는 주소로 나가고 바꾼 기록에 이전 값과 새 값이 그대로 남으므로, 주소에 비밀이 실리면 위젯 설정에 비밀을 두지 않는다는 전제(결정 "바꾼 기록", 위 "신뢰와 노출")가 깨진다. 둘째, `http://localhost` 예외를 호스트 이름 전체로 견주는 시험이다. 앞 글자만 견주면 `http://localhost.example.test` 같은 주소가 지나간다. 셋째, 쿠키를 전하는 흐름에서 Agent OS가 낸 `Set-Cookie`를 속성을 바꾸지 않고 되돌리는지의 확인이다. 넷째, 운영자가 고지의 글을 고친 뒤 이미 고지를 확인한 브라우저에 다시 확인을 받을지다. 지금 확인은 사이트 단위로 남는다(ADR 0059 결정 "고지 확인")."

- 받는 쪽에도 적었다. `.scratch/widget-admin-server/plan.md` 16행, `.scratch/portal-admin/plan.md` 20행, `.scratch/portal-login/plan.md` 6행이다. 세 행 모두 아직 명세가 없어 순서가 어긋날 일이 없다.

- 그 화면 작업은 ADR 0064가 병합되기 전에 끝나, ADR 0064가 더한 화면 요소 셋(첫 화면의 예시 질문, 문의 링크, 밝기 스위치를 숨긴 위젯)이 그린 화면에 없다(README를 그 낱말들로 Grep했고 일치가 없었다). 그 작업이 고른 갈래 1의 안 4는 위쪽 띠의 설정 단추 메뉴에 다크 모드 스위치만 두므로, 스위치를 숨긴 사이트에서는 메뉴에 든 것이 없다. `.scratch/widget-login-state/plan.md`에 명세 전에 화면 작업을 한 번 더 열어 그 셋을 그리고 그 단추를 어떻게 할지도 그때 정한다고 적었고, ADR 0064 Consequences "화면"에도 적었다.
- 그 README의 "명세가 정할 것" 첫 항목이 위젯 설정의 고르는 값 둘(로그인 모드 사이트의 로그인 전 모양, 고지 전문을 보이는 법)을 "'위젯 설정 관리' 행(portal-admin)의 설계 인터뷰"에 넘겼다. 그 작업에서 사람이 세 갈래의 안을 모두 위젯 설정에서 고르는 값으로 두기로 골랐다고 그 README가 적는다. 이 인터뷰는 이미 닫혔고 ADR 0064는 승인된 뒤라, 결정 "0.1 판에서 등록하는 것"의 목록을 이 세션이 늘리지 않았다. `.scratch/portal-admin/plan.md`와 ADR 0064 Consequences "화면"에 portal-admin의 명세 전에 사용자에게 묻고 넣으면 ADR 0064의 이력에 쌓는다고 적었다. 보고와 다음 지시문에도 적는다.

ADR 0064에 더한 문장은 "그 화면 그리기는 이 ADR이 병합되기 전에 한 번 끝났고(`.scratch/widget-login-state/design/README.md`) 그 셋은 그 그림에 없어, 명세 전에 한 번 더 열어 그린다. 그 작업은 위젯 설정의 고르는 값 둘(로그인 모드 사이트의 로그인 전 모양, 고지 전문을 보이는 법)을 이 행의 설계 인터뷰에 넘겼는데, 인터뷰가 닫히고 이 ADR이 승인된 뒤라 결정 "0.1 판에서 등록하는 것"의 목록에 없다. portal-admin의 명세 전에 사용자에게 묻고, 넣으면 이 ADR의 이력에 쌓는다"이다. 결정 절은 고치지 않았다.

dev가 함께 들인 것 가운데 이 세션의 회고에 닿는 대기열 항목이 있다. `.scratch/retro-queue/open-session-send-denied-despite-allow-rule.md`와 `.scratch/retro-queue/cli-review-claims-path.md`다. 회고에서 새 항목을 만들기 전에 그 둘을 먼저 본다.

합치기 커밋의 첫 시도는 pre-commit의 pytest에서 멈췄다(`1 failed, 7670 passed, 7 warnings in 774.69s`). 실패한 것은 `tests/tools/test_probe_kit.py::test_배출은_줄이_계속_와도_제한_시간에_끝난다`이고 첫 커밋의 첫 시도에서 실패한 셋 가운데 하나다. 단언은 `assert lines`가 빈 목록을 받은 것이다(199행). 그 시험은 자식 파이썬을 띄운 뒤 0.5초 동안 줄을 모으므로, 자식이 0.5초 안에 첫 줄을 쓰지 못하면 빈 목록이 된다(시험의 코드를 읽고 내린 어림이다. 그때의 부하는 재지 않았다). 이 세션의 네 번의 pre-commit 가운데 두 번 실패했고 연속은 아니다(처음에는 다섯 번이라 적었는데, 트랜스크립트에서 커밋 명령을 Grep으로 세어 고쳤다). 대기열 306이 이 종류(부하에서 빨개지는 시간 시험)를 받아들여 닫았으므로(ADR 0036) 시험을 고치지 않고 같은 커밋을 다시 치며, 새 사례는 이 일지에만 적는다. 나머지 검사는 ruff 둘과 canary specs와 constitution version이 `(no files to check)Skipped`, 그 밖은 Passed였다.

둘째 시도(같은 커밋을 다시 쳤다)도 같은 시험 하나로 멈췄다(`1 failed, 7670 passed, 7 warnings in 557.74s`, web-verify 651.8초, 나머지는 첫 시도와 같다). 같은 시험이 두 번 연속 실패했으므로 다시 치지 않고 `diagnosing-bugs`를 밟았다(`CLAUDE.md` 작업 규약 6).

### 진단: 그 시험은 자식 파이썬이 0.5초 안에 뜨지 못하면 빨개진다

시험의 몸통을 되풀이하는 스크립트를 세션 스크래치패드에 지어 돌렸다. 커밋하지 않았고, 아래 수는 그 스크립트를 갈래마다 한두 번 돌려 손으로 본 것이다. 자식을 띄우고 `LineReader`를 붙여 `drain(0.5)`를 부르는 차례는 시험과 같다. 자식이 줄마다 자기 시각을 찍게 해 빈 목록의 까닭을 가르고, 회차는 `tools/probe_kit.py`의 `Rounds`로 셌다(자식의 첫 줄을 실제로 받았고, 부하 갈래에서는 태우는 프로세스가 회차 끝에 모두 살아 있는 회차만 측정으로 셌다. 측정이 아닌 회차는 없었다). 갈래는 CPU를 태우는 프로세스의 수이고 이 PC의 논리 CPU는 16개다.

- 태우는 프로세스 0개(양성 대조): 스무 번 모두 줄을 받았다. 자식이 첫 줄을 쓰기까지 0.040~0.095초였다.
- 16개: 스무 번 가운데 한 번 빈 목록이었다(가장 늦은 첫 줄 0.817초).
- 32개: 스무 번 가운데 14번 빈 목록이었다(첫 줄까지 0.117~2.735초, 가운데 값 0.933초). 판정을 다듬기 전의 판으로 돌린 한 번은 18번이었다.

빈 목록인 회차는 모두 자식의 첫 줄 시각이 배출의 창(`drain`을 부른 때부터 0.5초) 뒤였고, 자식은 제때 썼는데 읽는 스레드가 늦게 받은 회차는 없었다. 그래서 원인은 `LineReader`도 이 브랜치의 변경도 아니고, 시험이 마감 시계를 자식의 첫 줄이 아니라 `drain`을 부른 때부터 돌리는 데 있다. 부하에서 인터프리터가 뜨는 데 0.5초가 넘으면 줄을 하나도 받지 못한다. 버린 가설은 셋이다. 읽는 스레드의 지연(그런 회차가 없다), `LineReader`의 회귀(부하 없이는 스무 번 모두 통과하고, 이 브랜치와 합친 dev 커밋은 `tools`를 바꾸지 않았다), dev 합치기(첫 실패는 합치기 전의 첫 커밋에서 났다).

둘째 시도가 끝난 뒤 이 PC는 CPU 사용률 82%, python 프로세스 30개, node 프로세스 72개였고(`Get-CimInstance Win32_Processor`와 `Get-Process`로 한 번 봤다), 세션 목록에 바쁜 세션이 셋 있었다. 다른 세션의 검사가 함께 돌던 때로 어림한다.

판정. 대기열 306이 받아들여 닫은 종류(부하에서만 빨간 시간 시험)의 사례다. 그 방침대로 시험은 고치지 않는다. 고치는 길(첫 줄을 넉넉한 제한 시간으로 먼저 받은 뒤에 0.5초 배출을 잰다)이 있다는 것과, 이 시험이 이 세션의 pre-commit 다섯 번 가운데 세 번 빨갰다는 것(첫 커밋의 첫 시도, 합치기 커밋의 두 시도)은 보고에 적어 그 종류를 다시 열지 사용자가 정하게 한다. 커밋은 PC의 부하가 내려간 뒤에 다시 친다.

셋째 시도는 CPU 사용률이 세 번 연속 45% 아래인 것을 본 뒤에 쳤고(치기 직전 15%) 다른 시험 하나로 멈췄다. `tests/tools/test_rerun_runner.py::test_파일럿에서는_인계로_멈추지_않는다`가 `assert board.run() == 0`에서 1을 받았다(`1 failed, 7670 passed, 7 warnings in 553.04s`, web-verify 586.5초, 나머지는 앞의 시도와 같다). 러너가 멈춘 까닭은 시험이 찍지 않아 출력에 없다. 진단한 배출 시험은 이번에 통과했다. 같은 시험의 연속 실패가 아니고, 이 브랜치는 그 시험 파일도 `tools/rerun_runner.py`도 고치지 않았다(첫 커밋 때 이 파일을 포함한 세 파일만 따로 돌려 `127 passed`였다). 이 시험이 부하 때문에 멈췄는지는 재지 않았다(어림이다). 대기열 306의 방침대로 다시 치고, 그동안의 CPU 사용률을 15초마다 스크래치패드에 적어 둔다. 같은 시험이 또 실패하면 진단한다.
