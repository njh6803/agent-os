# 2026-09-23 (04) 지나간 실행과 멈춘 실행을 한 곳에서 본다 — admin-api 티켓 05

브랜치 `feature/05-traces-list`, PR #56(`09cb298`로 squash 병합). `GET /traces`가 실행 요약의 한 쪽
(`TracePage {runs, next_cursor}`)을 최근 실행부터 돌려준다. `?status=paused`가 곧 멈춘 실행 목록이라
`interrupts`가 Out of Scope로 넘긴 "멈춘 실행 목록 조회"가 닫혔다. 계약(`openapi.json`)에 닿았지만 06을
막지 않는다 — 다른 라우트다.

사용자 입력은 인계 지시문 하나, 세션 제목 질문 하나, 계약 결정 셋, 리뷰 반영 결정 둘, 칩과 병합 순서
질문 하나, PR·푸시·병합 지시, 회고 판정 하나였다.

## 스킬이 로드되지 않은 채 시작했다

첫 메시지가 전각 `／implement`인 채로 들어왔다. `/implement`는 사용자만 부르는 스킬이라 로드되지
않았고, 지시문을 평문으로 받아 스킬 파일을 손으로 읽고 따랐다. 작업 도중 사용자가 물었다.

> 사용자: "근데 왜 세션명을 브랜치명으로 이름을 바꾸는 건 안지켜지고 있어?"

`open-session` 4단계(이름 붙이기)는 **여는 쪽** 세션이 하는데, 사람이 새 세션에서 `／`를 고쳐 보낸
뒤 옛 세션으로 돌아와 "보냈다"고 말해야 돈다. 새 세션이 메인 패널을 차지하니 사람은 돌아가지 않는다.
04 세션의 기록(`list_events`)에서 스크립트가 화면을 못 찾아 질문으로 멈춘 것을 확인했다. 03 세션도 같은
모양이었다(두 번 연속). 이 세션은 `set_session_title self`로 스스로 고쳤고, 새 세션이 지시문을 알아보고
스스로 이름을 붙이게 하는 훅을 chore 칩으로 올렸다(진행 중).

## 결정 셋 — 프로브를 먼저 돌리고 미리보기로 물었다

04의 선례대로 후보 모양이 `openapi.json`에 어떻게 찍히는지 스크래치 앱으로 먼저 봤다. PEP 695 별칭
(`RunStatus`, `TraceSchemaVersion`, `RunRow`)이 저절로 이름 있는 스키마가 되고 기본값 없는 필드는 전부
required라 예상 밖은 없었다. 04 회고 3(미리보기에 딸린 결정이 빠졌다)을 받아 딸린 결정 넷을 미리보기에
적었다.

> 사용자: (커서 모양) "불투명 base64url (Recommended)"
> 사용자: (페이지 모양) "본문 객체 TracePage (Recommended)"
> 사용자: (알려진 한계) "ADR 0012 이력 + 테스트 (Recommended)"

## 커서가 놓치는 길 — 둘이라 적었고 셋이었다

티켓의 확인 항목을 진짜 JSONL 어댑터로 쟀다. 파일이 늦게 나타나는 길은 `run()`이 시각을 읽은 직후 같은
호출에서 파일을 만들어 프로세스 하나면 생기지 않았고, 재개된 옛 실행이 다시 멈추는 길은 티켓에 없던
것인데 프로세스 하나여도 생겼다. ADR 이력에 "들어오는 길은 둘"이라 적었다.

**셀프 리뷰의 명세 축이 셋째를 찾았다.** 쓰는 중인 마지막 줄이 표지가 되고, 표지는 시각이 없어 꼬리로
가므로 같은 실행이 한 순회에 두 번 온다. 누락이 아니라 중복이라 티켓의 "두 번 오거나"에 직접 닿았다.
두 길만 재 보고 "둘"이라 세었다 — 04 일지가 "관대함을 적을 때 그 경계를 재지 않았다"로 적은 가족이다.

> 사용자: (셋째 길) "이력에 더하고 고치기는 별도 (Recommended)"

고칠지는 06 앞에서 따로 정한다(칩, 진행 중). 06의 단건이 같은 순간 500이 되기 때문이다.

## 셀프 리뷰

두 축 모두 Critical·Major 없음. 표준 8건, 명세 3건. 고친 것: 셋째 길, base64 산술 분리, `_CursorWire`
독스트링을 strict가 실제로 막는 것(JSON 숫자뿐)에 맞춤, `_after` → `_decode_after`, `TORN` →

TDD의 빨강이 "라우트 없음" 한 가지 이유로만 났으므로 핵심 단언 넷을 변이로 따로 빨갛게 봤다.

## PR 리뷰 — 초록 뒤의 Critical

Claude Code Review는 지적 없음. CodeRabbit(수동 요청)이 인라인 하나를 Critical로 달았다 — 표지의
`reason`이 pydantic 검증 문구를 그대로 실어 `input_value`가 잘린 줄의 꼬리(도구 결과)를 목록 응답으로
되울린다(CWE-209). 경로 노출은 명세가 이미 "경계 안"으로 정했고 01 리뷰도 오탐으로 분류하며 "HTTP 층에서
재확인이 필요하다"고 단서를 달았는데, 되울림은 경로가 아니라 **내용**이라 다른 이야기였다. 실측으로 확인했다.

> 사용자: (reason 되울림) "입력 되울림만 뺀다 (Recommended)"

보안 등급은 낮춰 읽었다(경계는 인증이고 06이 같은 인증 뒤에서 원문 전체를 내보낸다). 고친 이유는
"목록은 내용을 읽는 자리가 아니다"(스토리 15)다. 어댑터에 `_describe`를 두어 목록과 단건이 같이 쓴다.
반영 커밋의 전체 재리뷰는 CodeRabbit 시간당 한도에 걸렸고("Review rate limited"), 스레드 답글이 반영
커밋의 파일 셋을 직접 보고 해결 처리했다. Claude Code Review는 두 커밋 다 지적 없음. 병합 직전에 PR
헤드와 로컬 HEAD가 같은 것을 봤다.

## 회고

후보는 넷이었고 넷 다 승인됐다.

1. **파이프 뒤 `$?` 경고 훅**(대기열 19, 11을 흡수). 지침 검사를 `| tail -3; echo $?`로 돌려 `tail`의
   종료 코드를 읽었다. 바로 알아채 파이프 없이 다시 돌렸지만 `CLAUDE.md` 환경 함정에 적힌 것을 어긴
   것이고, 11(`&&` 체인)과 같은 가족 3회째다. 규약상 지침으로 적은 뒤에도 어기면 훅 후보다.
2. **닫힌 수 주장을 리뷰가 민다**(대기열 20). "길은 둘"은 04의 "관대함은 하나", 그 앞의 "면제 조항의
   폭"과 같은 가족 3회차다. 세 번 다 명세 축이 잡았으므로 잡는 자리를 운에서 절차로 옮긴다.
3. **미룬 재확인이 받는 티켓으로**(대기열 3을 넓혔다). 01 리뷰의 "HTTP 층에서 재확인이 필요하다"가
   05 티켓에 오지 않아 PR 봇이 Critical로 잡았다. 같은 01이 커서 한계는 05의 수용 기준에 넣어 제대로
   닫혔다 — 차이는 적은 자리 하나다.
4. **칩은 병합된 것만 가리킨다**(대기열 21). 1회차라 규칙이 아니라 후보다.

> 사용자: (회고 후보 승인) "1. 파이프 뒤 $? 경고 훅, 2. 닫힌 수 주장을 리뷰가 민다, 3. 미룬 재확인이 받는 티켓에 가야, 4. 칩은 병합된 것만 가리킨다"

대기열은 열여덟에서 스물하나가 됐다. 11은 반영된 것이 아니라 19에 합쳐졌으므로 취소선 없이 그렇게 적었다 — 취소선은 반영한 줄에만 긋는다(셀프 리뷰 표준 축).

잘 된 것 둘. 결정 전 스크래치 프로브와 딸린 결정을 적은 미리보기(04 회고 3)가 이번에는 처음부터
돌았다. 명세 축이 경계값을 직접 밀어 본 것이 셋째 길을 찾았다.
