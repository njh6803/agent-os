## 찾은 사실

아래 측정은 커밋한 프로브의 것이고(마지막 "환경" 항목만 손으로 봤다) 결과는 `.scratch/mcp-shutdown/probes/README.md`다. Linux는 Docker 컨테이너(`python:3.12.10-slim-bookworm`, `--init`, WSL2 커널)다. 셀프 리뷰를 반영한 뒤 `close_paths.py`와 `full_stack.py`를 두 OS에서 다시 돌렸고, 수는 그 회차의 것이다.

- **닫기(`close_paths.py`).** mcp 1.30.0에서는 도구 호출 도중의 기한 뒤 닫기가 0초 만에 끊겨 감싸는 프로세스만 꺼지고 서버가 3초 뒤에도 남았다(두 OS). 2.3.0에서는 기한 뒤 2.0초에 `TimeoutError`가 왔고 모두 내려갔다. SIGTERM을 무시하는 서버는 Linux에서 4.0초다. 설계의 어림(Windows 4.5초, Linux 6.5초)은 쓰기 비우기와 끈 뒤 확인을 다 더한 최악값이었다. 스스로 끝나며 자식을 남기는 서버는 Linux에서 런처 없이는 자식이 남고 런처로는 내려갔다. 세션 안의 예외는 두 판 모두 `ExceptionGroup[ExceptionGroup[예외]]`로 나왔고 서버는 내려갔다. 닫기 자체가 예외로 끝나는 길(연결을 다른 태스크에서 닫아 anyio가 `RuntimeError`를 낸다, `close_fails`)도 두 판·두 OS·Linux 세 갈래 모두 약 2.0~2.1초 뒤 서버가 내려갔다(결말 뒤 닫기의 물음). 없는 명령은 Linux 런처 뒤에서 `MCPError: Connection closed`의 두 겹 그룹이 되었다. Windows의 venv 파이썬이 한 겹 더 끼어도 1.30.0에서 서버가 남았다(양성 대조가 선다).
- **CLI.** 한 번의 Ctrl+C는 두 판 모두 대개 2.2~2.4초에 CLI를 끝냈고 그 뒤 서버가 남지 않았다(Linux 1.30.0의 한 회차는 6.0초. 첫 세션은 2.7초까지로 적었는데 README의 값에 근거가 없어 둘째 세션의 셀프 리뷰가 고쳤다). 설계의 어림("네이티브 취소가 보호를 뚫는다")은 맞지 않았다. 2.3.0에서는 닫는 도중의 둘째 Ctrl+C가 CLI를 멈췄다(Linux는 셋째에 끝나고 Windows는 셋째 뒤에도 60초 안에 끝나지 않았다). 1.30.0은 Windows에서 둘째 뒤 0.1~0.3초에 끝났고, Linux에서는 둘째 뒤 2.2초에 끝나며 서버가 남았다(다시 돈 회차에서 처음 쟀다). 지금의 끝나는 꼴은 Windows 3221225786, Linux에서 SIGINT로 죽음(`Popen` -2, bash 130)이다. 시제품 처리기(첫째는 주 태스크 취소, 둘째는 곧바로 끝냄, 끝나는 꼴은 지금과 같다)는 한 번이면 2.0~2.1초, 두 번이면 둘째 뒤 0.006~0.013초에 끝났다.
- **serve(`serve_shutdown.py`).** 2.3.0에서 신호 뒤 약 5.1~5.2초에 수명이 닫히고 7.1~7.3초에 실행이 끝나 7.3~7.4초에 프로세스가 끝났다(두 OS). uvicorn의 둘째 SIGINT(강제 종료)도 서버를 닫았다(Linux). 닫기 도중의 셋째 SIGINT와 SIGKILL 뒤에는 Linux에서 부모를 보는 런처로만 서버가 내려갔다. Windows는 serve를 강제로 꺼도 Job Object가 거뒀다.
- **실제 everything(`everything.py`, Windows).** 1.30.0에서 기한 1초 뒤 node 둘과 cmd 하나가 남았다가 4초 뒤에는 없었다. 2026-10-15 인터뷰가 본 "`gc.collect()`까지 남는다"는 상류를 직접 연 갈래로도, 지금 어댑터(`McpTools`)로도 재현되지 않았다. 2.3.0에서는 기한 뒤 2.0초에 모두 없었다.
- **소비 지점(`full_stack.py`).** `aa93cf7b` 위에 시제품을 얹은 사본이 두 OS에서 pyright strict 0건, 타입 우회 0건, import 계약 다섯, 테스트 571개를 지났다. Linux의 대조군 둘(런처 없음, 부모 감시 없음)은 기대한 테스트만 빨갰다. 새 닫기 테스트 다섯은 Windows 약 27초, Linux 약 18초다.
- **환경(손으로 봤다).** 이 PC의 uv 0.10.8은 `uv run --isolated --with`의 임시 환경에서 `pywin32` 312 휠을 설치하지 못해(scripts 폴더의 임시 항목) 프로브의 환경을 `uv venv`로 만들었다. slim 이미지에는 `libatomic1`이 없어 pyright의 node가 뜨지 못했다.

## 프로브가 첫 판에서 틀린 것

- Linux의 `cli_ctrl_c` 첫 판은 보조 스레드에서 `raise_signal`로 SIGINT를 올려, 신호가 주 스레드의 epoll 대기를 깨우지 못하고 `slow(30)`이 돌아온 뒤에야 처리되었다(30초). 그 회차를 측정으로 세지 않게 표지(도구가 돌아오기 전에 끝났다)를 더하고, 보조 스레드가 SIGINT를 막고 프로세스에 보내게 고쳤다.
- 가짜 서버 첫 판은 읽는 쪽이 사라진 출력에 쓰다 난 오류로 `run()`이 끝나 스스로 죽어, serve를 SIGKILL로 끈 사례가 "서버가 내려갔다"로 잘못 나왔다. 그 오류에도 남게 고쳤다.
- serve의 첫 `force3`는 셋째 신호가 uvicorn의 처리기가 살아 있을 때 와 아무 일도 하지 않았다. 셋째를 수명 닫기가 시작한 뒤로 옮기고(`force_then_interrupt`), 그때 실행의 닫기가 아직 돌고 있었다는 표지를 더했다.
- everything 첫 판은 루프를 닫은 뒤에 남은 것을 봐, 끊긴 연결의 파이프가 루프와 함께 정리되는 모양을 쟀다. 루프를 살려 둔 채 보게 고치고 지금 어댑터의 갈래를 더했다.
- 셀프 리뷰 뒤 처리기의 끝나는 꼴을 바꾼 첫 판은 Windows에서 `os._exit(0xC000013A)`를 불러, C int를 넘는 값의 `OverflowError`로 제대로 끝나지 못했다(한 번이면 종료 코드 1, 두 번이면 끝나지 않아 60초에 프로브가 껐다). 두 번의 회차는 표지가 서지 않아 측정 아님으로 세었다. 같은 32비트를 부호 있는 값으로 주게 프로브와 시제품을 함께 고쳤다.
- 대조군의 실패 까닭을 보게 고친 `full_stack.py`의 첫 회차는 까닭이 모두 빈 글로 와 처리기 없는 대조군을 기대와 어긋났다고 셌다. pytest가 터미널이 아닌 출력을 80칸으로 보고, 한글 테스트 이름만으로 그 폭을 넘은 요약 줄에서 까닭을 통째로 뺐다. 폭(`COLUMNS`)을 넓히고, 남은 대조군 사본에서 실패 출력을 한 번 본 뒤 문구를 확인했다.

- 승인(더하는 것, 문턱 전): 명세가 정한 것이 ADR 0034 본문의 사실 둘을 거짓으로 만들었는데 이력도 포인터도 없어 명세 축이 잡았다. `.claude/rules/adr.md`는 이력이 본문을 거짓으로 만들 때만 말하므로 어긴 것이 아니라 빈자리다. 닫힌 88을 잇는 새 행 391(1회차).

- 승인(회차): `stale_parent.py`의 첫 판(PR 직전 리뷰를 반영하며 새로 지은 프로브)이 `.claude/rules/probes.md` 첫 항목을 어겼다. `spawned`의 표지가 재려는 상황(런처가 띄울지 정할 때 부모가 이미 없었다)을 보이지 못했고 `alive`의 표지는 종료 코드뿐이었으며, `died`는 시간의 경주에 기댔다. 셀프 리뷰 두 축이 잡았다. 새 프로브의 첫 판이 그 항목을 어긴 일을 잇는 열린 행 339에 회차를 더했다(3회차). 339의 처방(탐침이 나눠 쓰는 함수)은 측정인 회차를 세는 쪽을 덮지만 표지를 고르는 쪽은 덮지 못한다. 처방을 고를 때 이 사건을 함께 본다.
- 기각: 반영으로 새로 쓴 명세의 닫힌 주장 둘("…형식일 때뿐이다", "사이의 변경은 … 뿐이다")이 틀려 셀프 리뷰가 잡았다. `code-review` 두 브리프의 주장 검증 목록이 잡도록 둔 것을 잡은 것이라 회차 셈에서 빼고, 기계 검사로 옮길 수 없다.
- 기각: PR 직전 버그·성능 축이 시제품의 결함 넷(빈 커서, 런처의 번호 경주, 처리기의 쓰기 오류, 가짜 프로세스의 쓰기 실패)을 잡았다. 어긴 지침이 없고 그 축이 제 몫을 했다.
