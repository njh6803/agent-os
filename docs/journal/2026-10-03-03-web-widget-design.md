## 트리의 뿌리 — 위젯은 누구 앞에 서나

plan 행이 넘긴 것은 열을 넘었다. 최종 사용자 인증, CORS, 재접속, 원격 바인딩, 에러 노출, 꺼진 에이전트의
404, web-admin의 여덟이다. 그 모두의 위에 한 물음이 있었다. 위젯이 누구 앞에 서는가다. 로컬의 운영자라면 넘겨받은
것 대부분이 다시 넘어가고, 공개 방문자라면 주체가 설 자리가 없다. 사용자는 "사이트가 보증한 사용자"를 골랐고, 그
답이 신원의 모양, 원격 노출, 주체 이름, 실행의 주체를 가르는 검사를 한꺼번에 열었다.

## 라운드

1라운드는 뿌리 셋(사용자, 대화, 토큰 스트리밍)이었다. 대화 질문은 한 번 되돌아왔다.

> 사용자(질문에 답): "좀 더 쉽게 설명해줘"

"내일 서울 날씨 어때?" 다음 "그럼 우산 챙겨야 해?"의 예로 다시 올렸고, 답은 추천(이번에는 잇지 않는다)과 달랐다.

> 사용자(질문에 답): "런타임이 앞 교환을 넘긴다"

이 답으로 범위가 커졌다. sdk와 트레이스 형식이 바뀌는 계약이 들어왔다. 임베드도 한 번 되돌아왔다.

> 사용자(질문에 답): "둘 다 지원하는 건 어때?"

넣는 법(script와 iframe)과 그리는 곳(iframe 안과 페이지 안)을 갈라 다시 올렸고, 사용자는 그리는 곳 둘을 모두
지금 하기로 했다. 그래서 파이썬의 CORS가 범위에 들어왔다.

이 밖에 추천과 다르게 정해진 것은 여덟이다. 승인은 운영자도 할 수 있는 안이 아니라 "주인만 결정"이었다. 상한은 "시간당
속도 제한까지"였다. 고리 길이는 상한이 아니라 압축이었다.

> 사용자(질문에 답): "1번인데 에이전트 별로 컨텍스트가 따로 존재하고 런타임이 에이전트 별로 한도에 도달한 에이전트의
> 컨텍스트만 요약하는거지?"

여기서 용어가 부딪혔다. 용어집의 "컨텍스트"는 런타임이 넘기는 손잡이다. 압축의 대상을 "앞 교환", 결과를 "대화
요약"으로 부르기로 하고 용어집에 넣었다. 대화와 에이전트의 관계를 따로 물었고, 사용자는 "바꾸되 자기 교환만 앎"을
골랐다. 서빙은 정적 파일이 아니라 "Next 서버(관리 화면처럼)"였고, 프록시는 Caddy가 아니라 "nginx"였다. 스타일은
직접 쓴 CSS가 아니라 "Tailwind를 들임(ADR 0021대로)", 아이콘은 들이지 않는 안이 아니라 "lucide-react를 서브패스로"였다.

마지막 질문은 기능을 어떻게 나누느냐였다. 셋으로 나누고 앞의 둘(conversation, end-user-channel)은 나란히,
이어 가기를 최종 사용자 경로에 붙이는 것은 web-widget의 첫 계약 티켓이 맡는다.

## 디자인 시스템이 화면보다 먼저다

요약을 확인받은 뒤, 사용자가 화면 작업의 순서를 새로 꺼냈다. 붙여 넣은 다른 저장소의 대화는 사용자가 참고하지
말라고 해서 여기 남기지 않는다.

> 사용자: "화면 작업을 하기 전에 클로드 디자인으로 디자인 시스템을 만들고 만든 디자인 시스템으로 클로드 디자인의 UI
> 화면을 만들고 만들어진 디자인 시스템과 UI화면을 이용하여 화면을 만드는 작업을 진행했으면 좋겠어. 디자인 시스템을
> 만들때도 grill-with-docs나 brainstoming을 이용해서 진행하는게 좋을까?"

처음에는 Claude Code의 Artifact(Design, Design System 형식)로 만드는 길을 냈다. 이 계정에 두 형식이 있고 둘 다 아직
하나도 없는 것을 `Artifact list`로 손으로 봤다.

> 사용자: "Artifact 말고 클로드 디자인의 디자인 시스템 + UI mockups + Wireframe로 하는건 별로야?"

> 사용자(질문에 답): "아니면 더 좋은 방법이 있어?"

`DesignSync` 도구의 설명을 읽고, 공식 연동이 코드의 컴포넌트 라이브러리를 Claude Design의 디자인 시스템 프로젝트로
올리는 방향이라는 것을 확인했다. 마침 Tailwind 측정이 shadow root와 rem의 제약을 냈다. 그래서 "원천은 코드, Claude
Design은 탐색과 화면"을 추천했고 사용자가 골랐다. 두 앱이 디자인 시스템 하나를 나누는 것도 골랐다. 이 결정은 ADR
0025다(처음에는 ADR 0021 이력으로 썼다가 셀프 리뷰 뒤 옮겼다, 아래). web-widget 초안이 적었던 `packages/ui`와
Storybook을 들이지 않는다는 문장은 design-system 기능으로 넘겼다.

> 사용자(질문에 답): "1번으로 하는데 추가로 궁금한게 DESIGN.md (디자인 시스템) 파일은 앱 별로 존재할 수 있어?"

앱별로 둘 수 있다고 답했다. 다만 `DESIGN.md`는 저절로 실리지 않으므로 `.claude/rules`의 `paths`로 이어야 하고, 토큰
값은 코드에만 두고 문서는 판단 기준만 든다고 했다. 이름과 자리는 design-system 인터뷰가 정한다(plan 행).

## 잰 것

넷 모두 서브에이전트가 쟀고, 보고를 근거의 종류로 갈라 받았다. 프로브와 판은 `.scratch/web-widget/probes/README.md`다.

- **JWT 검증(`jwt_verify/`).** PyJWT, joserfc, jwcrypto 모두 소비 코드가 strict와 타입 우회 검사를 지났다. 클레임을
  `dict(...)`로 감싸야 strict가 `sub` 좁히기를 강제했다(대조군). PyJWT는 alg 이름 `Ed25519`를 받지 못했다. PyJWT와
  cryptography는 이미 락에 있었다. 이것이 RS256과 PyJWT를 골랐다.
- **위젯 스택(`widget_stack/`).** React(element 약 71.5KB gzip), Preact 11(약 9.7KB), Lit 3, 프레임워크 없음을 실제로 설치한
  사본에서 쟀다. Lit는 데코레이터가 이 툴체인에서 깨졌다. React만 jsdom의 shadow root 안에서 user-event가
  `onChange`에 닿지 않았다. 빌드 산출물이 린트 범위에 든다.
- **nginx 중계(`nginx_relay/`).** 이 기계에 nginx가 없어 nginx.org의 공식 zip 셋을 스크래치패드에만 풀었다. SSE는 기본
  설정에서도 흘렀다. 잰 판 가운데 1.24.0과 1.28.3은 상류의 잘림을 정상 종료로 보였고 1.30.5는 드러냈다. 그 까닭(1.29.7에서
  상류의 기본 HTTP 판이 1.1로 바뀜)은 CHANGES를 읽은 것이다. 경로 허용 목록은 우회를 막았고, 윈도우의 대소문자 무시만
  어긋났다.
- **Tailwind와 lucide(`widget_tailwind/`).** shadow root에서 손대지 않은 CSS는 비교한 58곳 중 31곳이 달랐고, 대체 블록을
  `@layer properties`로 다시 넣으면 0이었다. 사이트의 `html` 글자 크기가 rem 위젯을 줄였다. lucide-react 1.51.0에도
  `exports` 맵이 없어 서브패스에 손 선언이 든다.

모순, 지금 코드와 경계에 비춘 실현 가능성)이 찾고, 축마다 반박 검증자가 거르고, 완전성 비평가가 빠진 것을 물었다.
에이전트 일곱이다. 검증을 지난 것은 보안 15, 모순 20, 실현 가능성 15였고 비평이 6을 더했다. 축끼리 겹친 것이 많다.
Major로 남은 것은 둘이고, 넷은 결정이 필요해 다시 물었다.

- **Major: 구독이 끝나지 않는 갈래.** 트레이스로는 도는 실행과 결말 없음을 가를 수 없어, serve를 다시 시작한 뒤의
  결말 없음 실행에 붙은 구독이 끝나지 않는다. 구독은 상한에도 들지 않았다. 세 축이 함께 냈다.
- **Major: frame-ancestors가 빌드에 박힌다.** 인터뷰에서 "Next 시작 래퍼가 사이트 파일을 읽는다"를 추천할 때 나는
  `next.config`의 헤더가 시작 때 읽힌다고 전제했다. Next 16.3.6은 운영 모드에서 빌드 산출물의 헤더를 쓰고, 관리 화면의
  `next.config.ts` 주석이 rewrites에 대해 같은 사실을 이미 적어 두었다. 잘못된 전제로 선택지를 냈다.

> 사용자(질문에 답): "도는 실행 등록부와 구독 상한 (Recommended)", "사이트 파일을 위젯 빌드의 입력으로 (Recommended)",
> "core가 판정 (Recommended)", "사이트별 합계와 전역 상한, 재개와 구독도 셈 (Recommended)"

셋째와 넷째는 Minor였지만 결정이었다. CLI `resume`의 주체는 OS 사용자라 문서대로면 최종 사용자의 멈춘 실행을
승인할 수 있었다. 판정을 core에 두어 ADR 0009에 "결정은 그 실행의 주체만 내린다" 이력이 늘었고, 용어집의 승인자와
운영자 정의가 바뀌었다. 상한은 주체별뿐이라 사이트가 방문자마다 새 `sub`를 주면 비용이 묶이지 않았다.

그 밖에 고친 것.

- **nginx가 정규화 전의 URI를 넘긴다(비평).** `/runs/../chat/x`가 nginx를 지나 파이썬이 운영자 토큰을 원격에서
  판정한다. `proxy_pass`에 URI를 붙이고 밖에서 안으로 들어오는 사례를 e2e에 더한다고 적었다. 측정은 안에서 밖으로
  나가는 우회만 쟀다.
- **"평문 토큰이 지나는 곳은 루프백뿐"은 리다이렉트로 성립하지 않는다.** 셀프 리뷰가 한 번 고친 문장이 다시 걸렸다.
  HSTS, 평문 80은 ACME와 넘기기만, 위젯은 `https`로만 부른다는 것으로 범위를 좁혔다.
- **"일시정지 항목의 인자는 `secret_args`로 가려져 있다"는 공허하다(비평).** 승인 대상 도구는 `secret_args`를 가질 수
  없다(ADR 0009). 원문이라고 고쳤다. ADR 0009의 2026-10-03 이력도 같이 고쳤다.
- **요약의 신뢰 수준.** 요약이 최종 사용자의 지시를 출처 없이 싣는 길을 적고, 고정 프롬프트가 교환을 데이터로 감싼다고 했다.
- **`/runs`의 선택 필드는 채널 규칙(본문에 기본값 있는 필드를 두지 않는다)과 부딪힌다.** 모양을 계약 티켓에 넘기고 규칙과
  맞추라고 적었다.
- **Tailwind를 처음 들이는 기능.** 기능 순서로는 위젯이 아니라 design-system이다. ADR 0021 이력의 제목과 포인터를 고쳤다.
- 그 밖에 사이트 발급자의 유일성, 사이트 파일 경로의 오타, 열 에이전트 목록을 결정과 구독에서도 보는 것, CORS를 에러
  응답에도, postMessage의 부모 쪽 규약, sessionStorage를 주체에 묶기, 출력의 텍스트 렌더링, element 번들의 자리,
  위젯 Next의 rewrites 금지, 공급망 유예, 트레이스 보존, 형식 3 근거의 사실, 포인터 하나. 받는 쪽은 `plan.md`의 행이다.
- **떨어진 것**(반박 검증자가 거뒀다): 고리 길이의 증폭(ADR 0022가 이미 명세로 넘겼다), JWT 수명과 키 교체의 받는
  쪽(넘긴 것이 정당하다), 면마다 다른 답이 번역표 규칙과 부딪힌다(모순이 아니다), 토큰을 URL에 싣는 길(쓰지 않는다) 등.

> 사용자: "CI 끝났어"

2회차(`d4bffc8`). CI 여섯이 초록이었다. CodeRabbit은 다시 "116 files exceed the limit of 100"으로 건너뛰었다.
claude-review는 경계 지적 없이 Minor 셋과 Nit 하나를 냈다.

- **Minor(반영): 아이콘을 누가 처음 들이는지 문서끼리 다르다.** `tech.md`와 ADR 0021 이력의 제목은 design-system,
  ADR 0024는 "design-system이나 web-widget"이었다. design-system으로 맞췄다. 1회차에서 Tailwind만 고치고 아이콘의 문장을
  놓쳤다.
- **Minor(반영): ADR 0023이 용어집이 _Avoid_로 둔 "방문자"를 쓴다.** 같은 PR이 더한 말을 같은 PR이 어겼다. "익명 최종
  사용자"로 바꿨다.
- **Minor(두고 답함): ADR 0023에 결정이 여럿이다.** 주체 판정은 ADR 0009의 이력으로 따로 있다. 사이트 파일, 걸러 보낸
  스트림, 구독, 상한, CORS는 "최종 사용자에게 원격 면을 연다"는 결정 하나의 귀결이라 나누지 않았다. ADR 0025를 뗀
  기준(기존 ADR의 개정이 아니라 새 결정)과 다르다.
- **Nit(두고 답함): "PR #128의 리뷰가 찾았다".** ADR 이력이 출처 PR을 적는 관례(예: ADR 0019의 "PR #93의 CodeRabbit
  강화 제안에서 드러났다")를 따랐다.

## 회고

후보 넷을 냈고 넷 모두 승인됐다. 반영은 대기열로 미뤘다. 스킬과 설정은 바꾼 뒤 새 세션에서 실제로 불러 확인해야 하는
하네스라 설계 PR에 섞지 않았다.

> 사용자(질문에 답): "1. 설계 PR의 셋째 축, 2. 선택지의 사실을 확인, 3. CodeRabbit 프로브 제외, 4. 대기열 46의 2회차",
> "대기열에 넣기 (Recommended)"

- **승인, 대기열 100: ADR이 든 diff의 셀프 리뷰에 위협·실현 가능성 축.** 셀프 리뷰 두 축과 claude-review가 놓친 Major
  둘(구독의 결말 없음, frame-ancestors가 빌드에 박힘)과 CLI 승인 우회, nginx의 정규화 전 URI를 워크플로의 셋째 축이
  찾았다. CodeRabbit은 좌석이 없고 이 PR을 건너뛰었다. ADR 0006 이력이 든다.
- **승인, 대기열 101: 선택지 설명의 사실을 올리기 전에 확인.** frame-ancestors(헤더가 시작 때 읽힌다는 전제)와 트레이스
  형식(반대 방향의 선례를 빠뜨림) 두 번 모두 사용자가 틀린 전제 위에서 골랐다. 앞의 것은 저장소의 관리 화면 주석에 이미
  반대 사실이 있었다.
- **승인, 대기열 102: CodeRabbit의 경로 필터에서 프로브를 뺀다.** 115개 중 98개가 프로브라 리뷰가 통째로 건너뛰어졌다.
- **승인, 대기열 46의 2회차.** 셀프 리뷰의 명세 브리프에 사용자의 답을 "거절은 429"로 줄여 옮겨, 선택지 설명의 "요청
  크기 초과는 기존 422"가 빠지고 명세 축이 Major를 냈다.
- **기록만: 영어 중간 문장 둘과 판정 명령의 파이프 하나.** 훅이 알렸다.
- **기록만: 새 결정을 기존 ADR의 이력으로 썼다.** 거버넌스의 "ADR은 결정 단위"를 어겼고 셀프 리뷰가 잡아 ADR 0025로 옮겼다.
- **기록만: 고친 문장이 다시 걸렸다.** 셀프 리뷰가 "평문 토큰이 지나는 곳은 루프백뿐"을 고쳤는데, 고친 문장도 리다이렉트로
  성립하지 않아 PR 리뷰가 다시 잡았다.
