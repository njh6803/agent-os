# 2026-10-05 (05) 나란히 돌 수 있는 티켓은 세션을 하나씩 전부 연다

지시문 없이 사용자의 질문에서 시작했다. 데스크톱 앱 세션이 주 체크아웃(`docs/end-user-channel-tickets`에 다른 세션의
스테이지가 있었다)에서 시작해 `git worktree add`로 `.claude/worktrees/parallel-open-session`을 파고 거기서 일했다.
브랜치는 `chore/parallel-open-session`이다.

번호가 05인 것은 주 체크아웃에 스테이지된 일지 04(end-user-channel 티켓 세션)가 아직 main에 없기 때문이다. 그 번호를
피했다.

> 사용자: "근데 병렬로 작업은 언제부터 가능한거야?"

> 사용자: "그럼 그 전에는 병렬작업이 안됐던거야?"

> 사용자: "그럼 병렬작업이 되는 것들은 자동으로 새 세션을 각각 열어서 진행했었어??"

> 사용자: "그럼 병렬 티켓은 세션을 자동으로 여러 개 열게 해줘"

## 답한 것

- 병렬 작업의 규칙은 2026-09-20 킥오프에서 섰고(계약 티켓이 첫 blocker, 프론티어만 병렬, 티켓당 워크트리 하나), 그 뒤
  기능마다 병렬 창이 있었다. first-slice 02·03, web-admin 티켓들, conversation 03·04가 나란히 갔다.
- 그러나 세션을 여는 것은 사람이 했다. `next-session`은 후보가 여럿이어도 하나만 골랐고(2단계는 하나를 고르고
  나머지는 `plan.md`로 가리키라고 했다), `open-session`은 세션 하나만 열었다. 2026-09-21 open-session 설계에서 사용자가 "병렬 작업은 잊어줘"라고
  해 병렬 자동화는 접혀 있었다(일지 2026-09-21 open-session).

## 고친 것

- **`next-session` 2단계.** 같은 기능의 `ready-for-agent` 티켓 가운데 막힌 것이 없는 것이 둘 이상이면 하나를 고르지
  않고 묶음 전체가 다음 작업이다. 지시문은 티켓마다 하나씩이고 `---` 줄로 가른다. 이미 도는 형제(제목이 그 브랜치인
  `isRunning` 세션)는 뺀다 — 형제 하나가 병합되어 이 단계에 왔을 때 나머지를 다시 내지 않게. 결정표에 "나란히" 줄을
  첫 줄 앞에 두었다.
- **`next-session` 3단계.** 묶음의 지시문은 "어디서" 줄에 `EnterWorktree`로 워크트리에 먼저 들어가 거기서 브랜치를
  바꾸라고 적는다. 딥링크는 폴더를 싣지 못해 모든 새 세션이 같은 체크아웃에 열리고, 같은 체크아웃에서 세션 둘이 브랜치를
  바꾸면 서로의 커밋 대상이 바뀐다(일지 2026-09-23-02). 받는 쪽은 `implement` 첫 문단이다.
- **`implement` 첫 문단.** "어디서"가 워크트리를 말하면 주 체크아웃에서 브랜치를 따지 않는다. 사본의 센티널 주석은
  여섯에서 일곱으로.
- **`open-session`.** 지시문 여럿을 받아 하나씩 차례로 연다. 앞 호출의 `sent=`를 본 뒤 다음을 쏘고 사이에 다른 일을
  두지 않는다. 분할·포커스는 마지막 `sent=` 뒤 한 번이고 포커스는 첫 세션이다. 4단계의 폴더 확인은 셀프
  리뷰 뒤 루트 아래 `.claude/worktrees/`도 맞는 것으로 넓혔다가 아래 감사의 5번으로 되돌렸다. 뒤에 연 세션의 제목
  없음은 훅 결함으로 보지 않는다. "같은 파일로 스크립트를
  두 번 돌리지 않는다"로 좁혔다.
- **`operations.md` 브랜치와 병합, `KICKOFF.md`.** 새 세션을 같은 체크아웃에 워크트리 없이 연다는 옛 문장이 거짓이 되어 고쳤다.
- **스크립트와 훅은 그대로다.** `tools/open_session.ps1`은 파일 하나에 세션 하나라 여러 번 부르면 된다. 지시문 형식 아홉
  줄이 그대로라 `hook_prompt_directive`와 그 테스트도 그대로다. 정규식 `어디서:\s*새 세션`은 접두 매치라 "새 세션.
  나란히 여는 2 중 1. …"도 받는다(테스트 `test_어디서_줄의_이유는_새_세션_판정을_바꾸지_않는다`).

## 수정 검증

반영을 워크플로(`worktree-fixes-verify`)로 다시 쟀다. 고친 파일 기준 덩어리 여섯을 렌즈 둘(문제를 닫는가, 새 문장의
사실과 명령이 맞는가)로 보고 점검자 하나가 묶어 지적 마흔을 냈다. 열두 검증 모두 "닫히지 않았다"였다.

- **방향을 바꾼 것.** 4에서 Bash가 막으니 `git -C`는 PowerShell 도구로 치라고 적은 것은 앱의 워크트리 격리 가드를
  돌아가라는 안내였다. 거두고, 워크트리 세션은 다른 체크아웃을 바꾸지 않고 사람이나 주 체크아웃 세션에 넘긴다고
  고쳤다. 정리 절도 주 체크아웃 세션이 돌고 워크트리 세션은 후보만 넘긴다.
- **새 실패 경로였던 것.** 워크트리 문장이 고정형이라 이미 있는 브랜치를 잇는 세션(끊은 작업, PR 반영)이 막혔다.
  브랜치가 새것일 때와 이미 있을 때로 나눴다. open-session 1단계 가드가 next-session 3단계의 조건 셋 가운데 둘만
  봤던 것을 맞췄다. 손으로 연 세션도 받도록 implement 첫 문단에 지시문과 상관없는 자기 점검을 더했고, 설계·명세·티켓
  같은 다른 시작 프롬프트도 받도록 첫 턴 훅이 워크트리 문장을 짚는다.
- **판정을 고친 것.** 정리 판정의 첫 판("조상이면 병합됐다")은 이 절을 읽기만 하는 방식으로 돌려 보니 막 딴 빈 브랜치의
  워크트리를 지울 대상으로 골랐다. 브랜치의 병합된 PR을 반드시 요구하게 고쳤다. 지시문 훅의 막음은 ps1의 고정 머리로
  좁혔다. local 가드 검사는 워크트리에서 늘 빈 판정이라 주 체크아웃의 local도 보게 했다. ADR 재번호의 범위는
  커밋 전 변경까지 보는 `git diff --merge-base origin/main`으로.
- **근거와 문구.** 근거 표기 규약(손으로 봤다·읽었다)을 어긴 자리, "언제나 주 체크아웃에 열린다"처럼 닫힌 주장,
  앱 정리 조건의 출처(로그가 아니라 앱 번들), `--frozen-lockfile`, PR 템플릿과 `.env` 훅 안내의 워크트리 경로를 고쳤다.
- **conftest 가드의 테스트.** subprocess로 가짜 `agent_os`를 앞세운 테스트를 더했다. 구현 뒤에 쓴 테스트라 변이 표
  `.scratch/harness/probes/worktree_guards_mutations.toml`로 빨강을 봤다(가드 여섯을 하나씩 꺼 여섯 모두 빨강).
- **남긴 것.** `/git-pr-merge`로 들어오는 길은 막지 않았다. 워크트리에서 `--delete-branch`를 막는 훅은 일이 난 적이
  없어 아직 두지 않는다(`.claude/rules/tools.md`의 막는 훅 조건). 헌법 버전은 커밋 직전에 올린다 — 열린 PR #137이
  3.0.9를 쓴다.

## keepalive 테스트 진단

검증 명령을 다시 돌리자 `tests/channel/http/test_router.py`의 keepalive 테스트가 전체 실행에서 세 번 연속 빨강이었고
홀로는 초록이었다. diagnosing-bugs로 갈랐다(손으로 돌린 루프, 스크립트는 세션 스크래치패드).

- 루프: 전체를 수집하고 어댑터·채널만 돌린다(`pytest tests -k "adapters or channel"`, 25초). 원격 main 사본에서 12번
  모두 초록, 이 브랜치에서 16번 중 9번 빨강.
- 가르기: 이 브랜치의 내용을 원격 main 사본에 얹으면 빨강이라 환경이 아니라 내용이다. 반씩 되돌려 지침 검사의
  테스트 파일 하나로 좁혔다(그 테스트들은 이 루프에서 선택에서 빠져 실행되지 않는다).
- 계측(`[DEBUG-ka01]`, 사본에만 넣고 사본째 지웠다): 테스트는 서버를 띄우기 전에 0.2초 타이머를 건다. 모델이 기다리기
  시작한 시각이 원격 main에서는 0.031~0.047초, 그 테스트 파일을 얹으면 0.188~0.219초였다. 타이머 직전에 `gc.collect()`
  를 부르면 0.031~0.047초로 돌아오고 네 번 모두 초록이었다.
- 결론: 수집 때 할당이 늘어 파이썬의 전체 GC(두 분포의 차로 어림한 0.15초쯤)가 그 0.2초 창 안으로 옮겨졌다. 제품 결함이 아니라, 시간
  예산을 서버 기동 전부터 재는 테스트가 무관한 변경에 뒤집히는 것이다. 고치는 길은 테스트 쪽(모델이 기다리기 시작한
  뒤에 문을 연다)이고, 원칙 II에 닿아 사용자에게 물었다. 승인 뒤 고쳤다(아래 "승인 뒤").
