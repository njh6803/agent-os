## 조사(첫 라운드 전)

기능 계획 `.scratch/local-model/plan.md`, ADR 0040 전문, 일지 2026-11-06-02의 "설계 인터뷰 입력" 절(GPU 환경, 모델 배치 구성, 남은 확인), 일지 2026-11-09-1229(mcp-http 설계 인터뷰의 라운드와 합의 요약)를 읽었다. 코드와 문서는 다음을 봤다.

- `sdk/manifest.py`의 `ModelProvider`는 값이 `anthropic` 하나인 닫힌 열거다. `adapters/anthropic.py`의 `AnthropicModels.build`는 `provider`로 갈라 `ChatAnthropic`을 만들고 키 값을 만지지 않는다. 코드를 읽었다.
- `core/loop.py`는 도구를 `{"name", "description", "input_schema"}` 꼴의 dict로 `model.bind_tools`에 넘기고, 응답의 `message.tool_calls`가 비면 `message.text`를 답으로 돌려준다. `core/model.py`의 `reply_from`은 `usage_metadata`와 `response_metadata["model_name"]`과 `tool_calls`만 읽고 `invalid_tool_calls`는 보지 않는다. 코드를 읽었다.
- `core/run.py`의 `_ask`는 모델을 부르는 것(`invoke`)과 응답을 읽어 기록하는 것(`reply_from`, `_record_model_call`)을 `blamed("model_call")` 안에 둔다(573~575줄). ADR 0031의 원인 표는 `model_call`을 "`ctx.llm()` 안에서 모델 포트에 닿는 몫(도구를 붙이기, 부르기, 응답을 읽어 기록하기)이 낸 예외"로 적는다. 코드와 ADR을 읽었다.
- `uv.lock`에는 `langchain-anthropic` 1.7.2, `langchain-core` 1.6.3, `httpx2` 2.13.0이 있고 `langchain-openai`와 `openai`는 없다(Grep).
- `pyproject.toml`의 꼬리표는 `llm`·`llm_widget`·`llm_portal` 셋이고 `addopts`가 셋을 기본 실행에서 뺀다. `docs/constitution/operations.md`의 LLM 테스트 절은 `-m llm`이 키가 없으면 skip이 아니라 실패한다고 적고, `docs/constitution/tech.md`의 원격·CI 행은 CI가 LLM 테스트를 뺀다고 적는다. 문서를 읽었다.
- `CONTEXT.md`의 **모델** 항목은 피할 말에 "엔드포인트"를 든다. 기능 계획은 "OpenAI 호환 엔드포인트"와 "모델 서버"를 함께 쓴다. 용어는 domain-modeling이 정한다.
- answer-eval의 기능 계획은 오픈 모델의 지연과 정답률을 local-model이 닫힌 뒤 다시 재서 pilot-release의 보고서로 낸다고 적는다. deploy-package는 local-model과 base-agent를 둘 다 기다린다(`.scratch/plan.md`). base-agent는 설계 줄과 명세가 있고, 티켓 단계의 세션 `docs/base-agent-tickets`가 `list_sessions`에 보였다.

사실 조사 서브에이전트 둘을 백그라운드로 띄웠다. 하나(`combo-probe`)는 langchain-core 1.6.3과 함께 풀리는 `langchain-openai`를 저장소 밖 환경(`uv run --no-project --with`)에서 루프백의 가짜 서버로 돌려 요청의 모양, 응답의 해석, 만들기가 키와 네트워크를 요구하는지, 바깥 접속, pyright strict를 본다. 다른 하나(`web-research`)는 vLLM의 도구 호출 플래그와 파서, 다른 서빙 엔진과의 차이, NPU 서빙 소프트웨어, 모델 후보의 라이선스와 도구 호출 지원을 공식 문서와 모델 카드에서 찾는다. 두 보고에 달린 질문(의존성, 도구 호출 형식이 깨졌을 때의 처리, 키 변수가 없을 때의 실패 시점, 모델 둘을 고르는 기준)은 다음 라운드로 미뤘다.

질문에 처음 나오는 개념 넷(OpenAI 호환 모델 서버, 환경 변수의 이름만 파일에 적는 방식, 테스트 꼬리표, 가짜 호환 서버)은 첫 호출 곁 본문에서 무엇인가·잡아 주는 것·치르는 값으로 풀었다.

## 라운드 1

첫 호출은 사실 확인 훅(`hook_choice_facts`)에 한 번 막혔다. ADR 0049의 거부한 안 "주소를 환경 변수 이름으로 적는다(`url_env`)"를 그 ADR 27행에서 확인하고(`grep`), 설명에 읽은 문서를 괄호로 밝혀 같은 질문과 라벨로 다시 올렸다. 넷 모두 추천안을 골랐다. 아래 설명은 다시 올린 화면의 것이다.

> 사용자: (모델 파일의 provider 칸에 더할 새 값은 무엇을 가리키게 할까요?) "주소로 붙는 호환 서버 전부 (Recommended)" — 설명: 새 값 하나(openai-compatible)가 생기고, 그 뜻은 "OpenAI와 같은 모양의 API를 내는 서버에 주소로 붙는다"입니다. vLLM, NPU 서빙 소프트웨어, 클라우드의 호환 엔드포인트가 모두 이 값 하나를 씁니다. 주소 칸은 필수라서 주소를 빠뜨린 모델 파일은 읽는 단계에서 거부되고, OpenAI 본사 주소로 몰래 나가는 일이 없습니다. 치르는 값: 엔진마다 다른 점을 런타임이 맞춰 주지 않으므로 표준에서 벗어난 엔진은 붙지 않을 수 있고, 이 기능이 시험으로 확인하는 엔진은 vLLM 하나입니다.

고르지 않은 선택지(라벨만): "서빙 엔진마다 값 하나", "OpenAI 값, 주소는 선택".

> 사용자: (모델 서버의 주소는 어디에 적을까요?) "모델 파일에 그대로 적는다 (Recommended)" — 설명: plugins/models/<이름>/plugin.toml에 base_url = "http://vllm:8000/v1"처럼 글자 그대로 적습니다(주소는 예시입니다). 모델마다 다른 서버를 가리킬 수 있어, 수락의 "모델 파일만 바꿔 계열이 다른 모델 둘"이 서버 둘이어도 성립합니다. 주소는 비밀이 아닌 것으로 보아 관리 화면의 모델 상세와 실패 문구에 그대로 보이고, 사용자:비밀번호@가 든 주소는 읽는 단계에서 거부합니다. 원격 MCP 서버의 주소도 이 방식으로 정했습니다(ADR 0049를 읽었습니다). 치르는 값: 배포마다 주소가 다르면 그 배포의 모델 파일을 고쳐야 합니다.

고르지 않은 선택지(라벨만): "모델 파일에 환경 변수 이름을 적는다", "서버 전체에 환경 변수 하나".

> 사용자: (모델 서버의 API 키는 어디서 읽을까요?) "모델 파일에 환경 변수 이름을 적는다 (Recommended)" — 설명: 선택 칸 api_key_env = "VLLM_API_KEY"에 환경 변수의 이름만 적고, 키 값은 serve의 환경에만 둡니다(칸과 변수의 이름은 예시입니다). 칸이 없으면 키 없이 붙습니다(키를 걸지 않은 내부망 서버). 모델 서버마다 다른 키를 쓸 수 있습니다. 원격 MCP 서버의 헤더도 이름만 적는 방식입니다(ADR 0049를 읽었습니다). 키 값은 모델 파일, 이벤트, 실패 문구 어디에도 싣지 않습니다. 치르는 값: 칸이 하나 늘고, 그 변수가 환경에 없을 때 언제 어떻게 실패할지를 정해야 합니다(조사 결과가 나온 뒤 다음 라운드에서 여쭙니다).

고르지 않은 선택지(라벨만): "정해진 환경 변수 하나".

> 사용자: (로컬 모델 서버가 떠 있어야 도는 테스트는 어떻게 다룰까요?) "손으로만 돌리고 CI는 가짜 서버로 (Recommended)" — 설명: 새 꼬리표 llm_local을 붙인 테스트는 GPU를 빌려 vLLM을 띄운 동안에만 손으로 돌립니다(uv run pytest -m llm_local). 서버 주소 같은 환경이 없으면 건너뛰지 않고 실패합니다(지금의 -m llm과 같습니다. operations.md를 읽었습니다). 평소의 pytest와 CI에서는 테스트가 루프백에 띄운 가짜 호환 서버로 어댑터의 요청 모양, 응답 해석, 실패 처리를 봅니다. 손으로 돌리는 계기는 호환 어댑터나 도구 호출을 해석하는 코드를 건드렸을 때와 제품 판을 내기 전이고, 돌린 결과(모델, 통과 수, 토큰 합계)는 일지에 적습니다. 치르는 값: 실제 모델과의 어긋남은 누가 손으로 돌리기 전까지 드러나지 않습니다.

고르지 않은 선택지(라벨만): "지금의 실제 모델 테스트에 합친다", "CI가 GPU를 빌려 정기적으로 돈다".

### 둘째 호출(같은 라운드의 나머지 하나)

첫 호출의 답에 기대지 않는 결정이라 같은 라운드다. 사실 확인 훅에 한 번 막혔고, 설명의 사실(base-agent 명세가 넘긴 사례 셋, deploy-package가 두 기능을 모두 기다림, pilot-release의 보고서)은 이미 대 본 것이라 같은 화면을 그대로 다시 올렸다. 추천안을 골랐다.

> 사용자: (기본 에이전트(assistant)의 실제 모델 테스트를 로컬 모델로도 돌리는 일은 어디에 둘까요?) "이 기능의 마지막 티켓으로 재서 기록 (Recommended)" — 설명: base-agent가 끝난 뒤 그 실제 모델 테스트의 사례(요청을 셋으로 가르기, 검색한 뒤 답하기, 정해진 문장을 글자 그대로 내기. base-agent 명세가 이 기능에 넘긴 것입니다)를 로컬 모델 둘로 돌려 사례별 통과와 실패를 기록하는 티켓을 이 기능에 둡니다. 통과를 요구하지는 않습니다. 실패한 사례는 스킬 문구(base-agent)나 모델 고르기(answer-eval)의 입력이 됩니다. 이 기능의 다른 티켓은 base-agent를 기다리지 않고 calc 예시로 먼저 끝납니다. 치르는 값: 이 기능이 base-agent가 끝날 때까지 닫히지 않습니다. 둘을 모두 기다리는 deploy-package의 차례는 그대로입니다(.scratch/plan.md를 읽었습니다).

고르지 않은 선택지(라벨만): "평가 보고서 쪽에 넘긴다", "통과해야 이 기능이 끝난다".

## 조사 보고(web-research)

서브에이전트 `web-research`가 보고를 냈다. 공식 문서와 소스, 모델 카드와 LICENSE를 raw 파일로 받아 세션 스크래치패드의 `dl/`에 두고 그 파일에 대 본 것(아래 "원문")과 대 보지 못한 것(웹 요약, 어림)을 갈라 적었다. 받은 파일은 저장소 밖이라 커밋하지 않는다. 아래에서 "본 세션이 다시 봤다"는 라운드 2의 설명에 넣으려고 본 세션이 그 파일을 `grep`으로 다시 본 것이다.

**vLLM**(안정 판 0.33.0, 2026-11-02. 원문은 그 판의 문서와 소스)

- 도구 호출은 서버를 띄울 때 `--enable-auto-tool-choice`와 `--tool-call-parser <이름>`을 줘야 켜진다. 없이 `tools`가 든 요청을 받으면 HTTP 400이다(원문, 소스).
- 파서는 모델 계열마다 다르다. `hermes`(Hermes, Qwen2.5·Qwen3), `mistral`, `llama3_json`, `openai`(gpt-oss), `gemma4`, `granite`, `qwen3_xml` 등이고 한국 모델 이름의 내장 파서는 없다(원문).
- `tool_choice`가 `auto`이면 기본으로 문법 제약 없이 모델이 낸 글에서 도구 호출을 뽑는다. 그래서 인자가 깨지거나 표지가 답에 샐 수 있다고 문서가 적는다. 서버 운영자가 `--tool-strict-level function`을 주면 도구가 든 모든 요청에서 도구 호출의 겉(표지와 함수 이름)을 문법으로 묶고, `parameter`는 인자의 스키마까지 묶는다. `auto`에서는 문법이 도구 호출을 강제하지 않아 그냥 글로 답하는 것도 유효하다(원문 `vllm_tool_calling_v0330.md` 120~159행, 본 세션이 다시 봤다).
- `hermes` 파서(스트리밍이 아닌 응답)는 표지가 없거나 안의 JSON이 깨지면 `tool_calls` 없이 `content`에 원문을 싣는다. 깨진 `arguments`가 든 도구 호출로 나오지 않는다(원문, 소스 `src_hermes_tool_parser.py`). 다른 파서는 보지 않았다.
- 문맥 길이를 넘는 요청: 0.32.0부터는 `max_tokens`를 남은 자리로 조용히 줄이고 입력만으로 넘으면 오류다. 0.31.0까지는 합이 넘으면 거절한다(원문). 상태 코드는 확인하지 못했다(400이라는 어림).
- `--api-key`(또는 환경 변수 `VLLM_API_KEY`)를 주면 `Authorization: Bearer`를 검사해 틀리면 401이다. `/v1` 아래만 지키고 `/health` 등은 인증이 없다(원문).
- 사고(추론)를 내는 모델의 사고 글은 응답의 `reasoning` 칸에 따로 실린다(0.28.0부터. `reasoning_content`가 아니다). Qwen3는 사고가 기본으로 켜져 있다. 서버를 띄울 때 `--default-chat-template-kwargs '{"enable_thinking": false}'`를 주면 요청마다 적지 않아도 꺼진다(원문 `vllm_reasoning_v0330.md` 219~228행, 본 세션이 다시 봤다).

**다른 서빙 엔진**

- Ollama는 `tools`는 받지만 `tool_choice`를 받지 않고, llama.cpp는 사고 칸의 이름이 `reasoning_content`다. SGLang은 파서 이름이 vLLM과 다르다(원문).
- 퓨리오사 Furiosa-LLM은 `furiosa-llm serve`로 OpenAI 호환 서버를 내고 vLLM과 같은 이름의 파서(`hermes`, `llama3_json` 등)로 도구 호출을 문서화했다(원문 `furiosa_toolcalling.html`, 본 세션이 다시 봤다). 지원 모델 목록에 EXAONE, gpt-oss, Llama-3.1-8B, Qwen3-8B가 있다(원문).
- 리벨리온 `vllm-rbln`은 vLLM의 하드웨어 플러그인이라 `vllm serve`를 그대로 쓰지만 문서의 레시피가 vLLM 0.30.0이고 도구 호출이 문서에 없다(원문). 도구 호출이 될지는 어림이다.

## 라운드 2

combo-probe의 보고가 오기 전이라 그 결과에 달리지 않은 결정 넷을 먼저 올렸다. 개념 넷(도구 호출 파서, 형식 강제, 사고 글, 엔진 확장)을 호출 곁 본문에서 풀었다. 첫 호출은 사실 확인 훅에 한 번 막혔다. 설명의 사실을 원문과 코드에 다시 대 보고 두 곳을 고쳐(Qwen3의 파서 안내는 모델 카드가 아니라 Qwen 공식 문서에 있었다, gpt-oss-20b는 "사고를 늘 내는"이 아니라 "사고를 내는" 모델이다) 같은 질문과 라벨로 다시 올렸다. 넷 모두 추천안을 골랐다. 아래 설명은 다시 올린 화면의 것이다.

> 사용자: (모델 서버마다 다른 설정(도구 호출 파서, 사고 끄기, 형식 강제)은 누가 맞추게 할까요?) "서버를 띄우는 쪽이 맞춘다 (Recommended)" — 설명: 런타임은 어느 호환 서버에나 같은 표준 요청(모델 이름, 대화, 도구 목록, 출력 길이 상한, 온도)만 보내고, 도구를 부를지는 모델이 정하게 둡니다. 모델에 맞는 파서, 사고 끄기, 형식 강제는 모델 서버를 띄울 때의 옵션으로 맞춥니다(vLLM 0.33.0 문서에서 세 옵션을 확인했습니다). 응답에 사고 글이 별도 칸으로 실려 와도 런타임은 읽지 않고 답만 씁니다. 배포 문서가 vLLM의 옵션 예시를 싣고, 로컬 모델 시험을 돌릴 때마다 서버의 판과 옵션을 일지에 적습니다. 치르는 값: 서버 옵션을 바꿀 수 없는 남의 호환 서버에서는 맞출 방법이 없고, 모델 파일만 봐서는 그 모델이 어떤 서버 옵션을 요구하는지 알 수 없습니다.

고르지 않은 선택지(라벨만): "모델 파일에 서버로 그대로 넘길 칸을 둔다", "런타임이 vLLM의 확장을 직접 쓴다".

> 사용자: (모델 서버가 도구 호출을 돌려줬는데 그 인자가 깨져 있으면(올바른 JSON이 아니면) 어떻게 할까요?) "그 실행을 실패로 끝낸다 (Recommended)" — 설명: 실행이 실패로 끝나고 원인은 이미 있는 '모델 호출'입니다. 위젯에는 지금의 문구('에이전트가 모델을 부르지 못했습니다. 잠시 뒤 다시 보내 주세요.')와 다시 보내기 단추가 뜹니다(FailureAlert.tsx를 읽었습니다). 운영자는 트레이스의 실패 기록에서 어느 도구의 인자가 깨졌는지를 봅니다. 계약과 웹 화면은 바뀌지 않습니다. 치르는 값: 모델이 한 번 실수하면 그 실행 전체가 실패하고, 관리 화면에서 원인만 봐서는 서버에 닿지 못한 것과 구별되지 않아 실패 내용까지 읽어야 합니다.

고르지 않은 선택지(라벨만): "모델에게 오류를 돌려주고 다시 시킨다", "새 실패 원인을 더해 따로 보인다".

> 사용자: (모델이 도구를 부르려 했는데 서버가 알아채지 못해 그 글이 그냥 답으로 돌아오면 어떻게 할까요?) "답으로 보이고, 서버 설정과 시험으로 막는다 (Recommended)" — 설명: 런타임은 그 글을 보통의 답과 가를 수 없어 답으로 내보냅니다. 위젯에 <tool_call>{"name": …} 같은 글이 답으로 뜰 수 있습니다(hermes 형식의 표지입니다, vLLM 소스를 읽었습니다). 막는 것은 둘입니다. 서버 쪽에서는 맞는 파서와 형식 강제 옵션(vLLM은 --tool-strict-level, 0.33.0 문서를 읽었습니다)을 쓰도록 배포 문서가 안내하고, 로컬 모델 시험은 트레이스에 도구 호출이 실제로 남아야 통과하게 해서 모델과 서버의 조합이 맞는지를 가립니다. 치르는 값: 설정이 틀린 배포나 형식 강제가 없는 엔진에서는 이상한 답이 실패 표시 없이 최종 사용자에게 보입니다.

고르지 않은 선택지(라벨만): "알려진 표지가 답에 있으면 실패로 돌린다", "런타임이 요청마다 형식 강제를 요구한다".

> 사용자: (수락 시험에 쓸 모델 둘은 어떤 기준으로 고를까요?) "도구 호출 형식이 서로 다른 둘 (Recommended)" — 설명: 둘 다 상용 이용이 가능한 라이선스이고 24GB GPU 한 장에 올라가며 vLLM에 든 파서로 도구 호출이 되는 모델로 하되, 하나는 한국 회사의 한국어 모델, 하나는 해외 모델이고 둘의 파서가 달라야 합니다. 첫 후보는 SKT A.X 4.0 Light(hermes 형식)와 OpenAI gpt-oss-20b(openai 형식, 사고를 내는 모델)입니다(둘 다 Apache-2.0. 모델 카드와 vLLM 0.33.0 문서를 읽었습니다). 띄워 보니 도구 호출이 되지 않으면 같은 기준의 다음 후보(한국어는 A.X 3.1 Light, 해외는 Ministral 3 8B)로 바꾸고 까닭을 일지에 적습니다. 0.33.0에서 실제로 되는지는 아직 재지 않았습니다. 치르는 값: 모델마다 서버를 다른 옵션으로 띄워 봐야 해서 GPU를 빌리는 시간이 늘고, 사고를 내는 모델이 시험을 더 까다롭게 만들 수 있습니다.

고르지 않은 선택지(라벨만): "만든 곳만 다르면 된다", "기준만 정하고 모델은 티켓이 고른다".

## 조사 보고(combo-probe)

서브에이전트 `combo-probe`가 보고를 냈다. 스크립트와 원본 출력은 세션 스크래치패드의 `local-model-probe/`에 있고 저장소에는 아무것도 쓰지 않았다. 바깥 API로 나간 요청은 0건이다. 스크립트마다 표지를 보지 못한 회차는 최종 실행에서 0이다(만들기 7, 요청 17, 응답 19, 바깥 접속 5, 타임아웃 3, 프록시 7, pyright 후보 13 회차 모두 표지를 봤다). 커밋하지 않은 스크래치 스크립트라 아래는 모두 손으로 본 것이다(명령은 `uv run --no-project --python <스크래치 가상환경> python <스크립트>`). ADR이 근거로 들 것은 구현 티켓이 `.scratch/local-model/probes/`에 다시 지어 커밋한다.

돌린 판은 Python 3.12.10, langchain-core 1.6.3, langchain-openai 1.6.2, openai 3.49.0, tiktoken 0.14.0, pyright 1.1.414다. 지시한 `uv run --no-project --with …` 꼴은 이 PC에서 종료 2로 실패해(휠 설치 오류, 원인은 가르지 못했다) 스크래치 가상환경에 저장소 락의 판을 제약으로 걸어 깔았다.

- **의존(손으로 봤다, `versions.py`와 `uv pip compile`).** 락 제약 아래 새로 드는 패키지는 넷이다. langchain-openai 1.6.2(MIT), openai 3.49.0(Apache-2.0), tiktoken 0.14.0(MIT), regex 2026.11.9. openai는 `httpx2`를 쓰고 그것은 이미 락에 있다.
- **만들기(손으로 봤다, `probe_construct.py`).** `api_key`를 문자열로 주면 만드는 동안 요청 0건이다. `api_key`를 생략하거나 `None`이나 빈 문자열을 주면 환경에 `OPENAI_API_KEY`가 없을 때 **만드는 자리에서** `openai.OpenAIError`다. `ChatAnthropic`처럼 첫 호출로 미뤄지지 않는다. `api_key`에 동기 함수를 주면 만들 때는 불리지 않고 요청마다 한 번 불린다. `api_key`를 주지 않고 환경에 `OPENAI_API_KEY`가 있으면 그 값이 `base_url`의 서버로 실려 간다.
- **요청(손으로 봤다, `probe_request.py`).** 루프와 같은 꼴(`{"name","description","input_schema"}`를 `bind_tools`)로 부르면 `POST /v1/chat/completions`이고 본문 키는 `model`, `stream`(false), `messages`, `tools` 넷이다. 도구는 표준 꼴(`type: function`, `parameters`)로 옮겨지고 `strict`도 `tool_choice`도 없다. 출력 길이 상한은 `max_tokens`로 주든 `max_completion_tokens`로 주든 본문에 `max_completion_tokens`로 나가고, 주지 않으면 키가 없다. `temperature`도 주지 않으면 빠진다. 모델 이름에 `codex`가 들거나 `gpt-5-pro`로 시작하면 `/v1/responses`로 가고, `use_responses_api=False`를 주면 `/v1/chat/completions`로 간다.
- **응답(손으로 봤다, `probe_response.py`).** 글과 `tool_calls`는 그대로 읽힌다. 인자가 깨진 JSON이면 예외 없이 `tool_calls=[]`이고 `invalid_tool_calls`에만 들어가며 글은 빈 문자열이다. 지금 루프는 `tool_calls`만 봐서 빈 글을 최종 답으로 낸다. `<tool_call>` 글만 온 응답은 그 글이 답이 된다. `reasoning`과 `reasoning_content`는 버려진다. `usage`가 없으면 `usage_metadata`가 `None`이다. `response_metadata["model_name"]`은 서버가 응답에 적은 이름이다. `arguments`가 문자열이 아니라 dict이면 `ainvoke`에서 `ValidationError`가 올라온다.
- **오류와 재시도(손으로 봤다, `probe_response.py`).** 400·401·404는 요청 1건으로 예외다. 500·429·503·타임아웃·접속 실패는 SDK가 두 번 더 보낸다(요청 3건, 500에서 합 1.34초). 닫힌 포트는 7.59초 뒤 접속 오류다.
- **둘째 턴(손으로 봤다, `probe_request.py`).** 도구 결과는 `content`·`role`·`tool_call_id`만 실리고 `status`는 실리지 않는다. 모델은 도구의 실패를 `content`의 글로만 안다.
- **바깥 접속(손으로 봤다, `probe_egress.py`).** import, 만들기, `ainvoke`, 둘째 턴 모두 루프백이 아닌 주소로의 접속 시도와 이름 풀이가 0건이다. import만으로 `tiktoken`이 로드되지만 인코딩 파일은 받지 않는다. `get_num_tokens`를 부르면 바깥으로 나가려 한다(루프는 부르지 않는다). LangSmith 환경 변수가 없는 환경에서 봤다.
- **타입 검사(손으로 봤다, 스크래치 폴더에 pyright strict).** `Any`·`cast`·무시 주석 없이 지난다. pyright는 별칭 이름만 받는다(`model=`, `base_url=`, `api_key=`, `max_completion_tokens=`, `timeout=`). `api_key`에 맨 `str`은 오류이고 `SecretStr`이나 동기 함수를 받는다.
- **타임아웃(손으로 봤다, `probe_timeout.py`. 코드는 langchain-openai 1.6.2와 openai 3.49.0을 읽었다).** langchain-openai를 거치면 HTTP 타임아웃의 기본이 없다. 서버가 630초 붙잡은 요청이 요청 1건으로 630.0초 뒤 성공했다. `timeout=2.0`을 주면 2.1초에 타임아웃이고 재시도까지 7.2초다.
- **프록시(손으로 봤다, `probe_proxy.py`).** `HTTP_PROXY`나 `ALL_PROXY`가 있으면 `127.0.0.1`로 가는 요청도 프록시로 간다. `NO_PROXY=127.0.0.1`이면 바로 가고 `NO_PROXY=localhost`는 주소가 `127.0.0.1`일 때 덮지 못한다.

보지 못한 것: 실제 모델 서버의 동작(가짜 서버로만 봤다), https와 자체 서명 인증서, `Authorization` 헤더를 아예 빼는 방법, 윈도 시스템 프록시, LangSmith 추적이 켜진 환경.

### 라운드 2 둘째 호출(combo-probe 보고 뒤)

보고에 달려 미뤘던 결정 셋을 올렸다. 개념 셋(의존성을 들인다, 출력 길이 상한과 문맥 길이, 키 변수가 없을 때의 두 시점)을 호출 곁 본문에서 풀었다. 사실 확인 훅에 한 번 막혔고, 다시 대 보다 설명 한 곳이 코드와 다른 것을 찾았다. 실행 전에 거부하면 까닭이 서버 기록에만 남는다고 적었는데, `http/errors.py`의 표는 운영자 면에서 `PluginError`의 문구를 응답에 싣고 최종 사용자 면만 고정 문구다. 그 설명을 고치고, 서버를 띄울 때 확인하는 안에 반대 방향의 선례(기본 모델은 시작 때 확인한다, ADR 0040의 거부한 안)를 더해 같은 질문과 라벨로 다시 올렸다. 셋 모두 추천안을 골랐다. 아래 설명은 다시 올린 화면의 것이다.

더 본 사실(본 세션이 읽었다): ADR 0040은 "API 키는 … 시작 때 보지 않는다"와 "키가 없는 것은 첫 호출에서 langchain-anthropic 1.7.2의 `TypeError`로 드러난다"를 적는다. ADR 0049는 헤더의 환경 변수가 없으면 여는 단계의 실패(원인 `tool_connection`)로 끝내고 "실행 전에 거부한다"를 거부했다. vLLM 소스의 `get_max_tokens`는 요청에 상한이 없으면 서버의 기본 샘플링 값을 쓰고 그것도 없으면 문맥에서 입력 길이를 뺀 값을 쓴다(`dl/src_api_utils.py` 234~270행). vLLM 0.30.0은 출력 상한과 입력의 합이 문맥을 넘으면 거절한다(`dl/src_renderers_params_v0300.py` 506~510행). Ollama의 호환 층은 요청에서 `max_tokens`만 읽는다(`dl/ollama_openai.go` 116행). 리벨리온의 레시피 문서 둘에 vLLM 0.30.0이 적혀 있다(`grep -c`).

> 사용자: (호환 서버에 붙는 코드를 어떻게 마련할까요?) "langchain-openai를 들인다 (Recommended)" — 설명: 새 의존성으로 langchain-openai를 더합니다. 함께 들어오는 패키지는 넷입니다(langchain-openai 1.6.2, openai 3.49.0, tiktoken 0.14.0, regex. 조사 서브에이전트가 락의 판을 제약으로 걸어 손으로 풀어 봤습니다). 어댑터는 이 라이브러리의 모델 객체를 만드는 얇은 코드가 되고, 지금 루프의 도구 꼴이 그대로 표준 요청으로 나갑니다. 타입 검사 통과와 바깥 접속 0건은 가짜 서버로 손으로 본 것이고, 실제 모델 서버로는 아직 보지 않았습니다. 치르는 값: 이 라이브러리는 공식 OpenAI만 겨냥한다고 스스로 적어, 호환 서버와의 어긋남은 우리 테스트가 지켜야 합니다. 출력 길이 상한이 새 이름(max_completion_tokens)으로만 나가서, 옛 이름만 받는 엔진(Ollama의 호환 층 소스를 읽었습니다)에서는 상한이 듣지 않을 수 있습니다. 환경의 OPENAI_API_KEY를 읽는 성질이 있어 어댑터가 키를 항상 직접 넘겨 막아야 하고, 키가 없는 서버에도 자리 채움 글자가 인증 헤더로 나갑니다.

고르지 않은 선택지(라벨만): "어댑터를 직접 짠다", "openai SDK만 들이고 변환은 직접".

> 사용자: (모델 파일이 적은 키의 환경 변수가 서버 환경에 없으면 언제 실패하게 할까요?) 고르지 않은 선택지(라벨만): "실행을 시작하기 전에 거부한다", "서버를 띄울 때 확인한다".

> 사용자: (호환 서버용 모델 파일에 출력 길이 상한(max_tokens)이 없으면 어떻게 할까요?) "보내지 않고 서버에 맡긴다 (Recommended)" — 설명: 호환 서버로 가는 요청에 상한을 싣지 않습니다. vLLM은 상한이 없으면 서버나 모델에 정해 둔 기본값을 쓰고, 그것도 없으면 문맥에서 입력을 뺀 나머지까지 답하게 둡니다(vLLM 소스의 get_max_tokens를 읽었습니다). 모델마다 문맥 길이가 달라도 모델 파일을 고칠 필요가 없습니다. 상한을 주고 싶으면 모델 파일에 적으면 됩니다. 치르는 값: 같은 칸이 비었을 때의 뜻이 제공사마다 달라지고(Anthropic은 16000, 호환 서버는 서버 기본), 다른 엔진의 기본값이 짧으면 답이 중간에 잘릴 수 있습니다(다른 엔진의 기본값은 보지 않았습니다).

고르지 않은 선택지(라벨만): "Anthropic과 같이 16000을 보낸다", "호환 서버에서는 꼭 적게 한다".

## 라운드 3(갈래 밟기)

결정이 아니라 되물음이다. 세션이 스스로 서버를 띄우고 시험 뒤에 내리는 길이 되는지(클라우드, 도구, 꺼짐 보장, 비용, 자격 증명의 범위)를 조사한 뒤 다음 라운드로 올린다. 올렸던 선택지 셋은 모두 사람이 서버를 띄운다는 전제였다.

> 사용자: (이 규칙을 호환 서버 어댑터를 처음 넣는 PR부터 적용할까요?) "처음 넣는 PR부터 적용한다 (Recommended)" — 설명: 어댑터와 로컬 모델 시험을 같은 PR에 넣고, 그 PR이 로컬 모델 시험을 통과해야 병합합니다. 실제 모델로 확인되지 않은 어댑터가 main에 들어오지 않습니다. 치르는 값: 첫 PR이 커지고, 그 PR부터 GPU 서버가 필요합니다.

고르지 않은 선택지(라벨만): "모델과 주고받는 코드만 (Recommended)", "한 모델만, 둘은 판을 내기 전에", "병합 직전에 묻고 그 세션이 기다린다 (Recommended)", "작업을 시작할 때 먼저 묻는다", "묻지 않고 PR을 열어 둔 채 끝낸다", "로컬 모델 시험이 main에 들어온 뒤부터".

## 조사 보고(gpu-provision-research)

서브에이전트가 문서 47개를 스크래치패드(`dl-gpu/`, 커밋하지 않는다)에 받아 대 본 보고다. 아무것도 설치하지 않았고 클라우드를 부르지 않았으며, 보고의 명령은 돌려 보지 않은 것이다. 아래에서 "원문"은 받은 파일의 글자를 대 본 것이고, 나머지는 어림이다. 결론은 "된다"이고 걸림돌은 기술이 아니라 준비(할당량)다.

**AWS EC2**

| 유형 | GPU | vCPU / 메모리 | us-east-1 시간당 | 서울 시간당 |
|---|---|---|---|---|
| g5.xlarge | A10G 24GB 한 장 | 4 / 16 GiB | $1.006 | $1.237 |
| g6.xlarge | L4 24GB 한 장 | 4 / 16 GiB | $0.8048 | $0.9896 |
| g6e.xlarge | L40S 48GB 한 장 | 4 / 32 GiB | $1.861 | $2.288 |

- 가격은 2026-11-10 가격표(원문), 사양은 인스턴스 사양 문서(원문)다. 가격 여섯은 본 세션이 받은 JSON에서 다시 읽었다(손으로 봤다, 스크래치패드의 `dl-gpu-check/price.py`). 과금은 초 단위이고 최소 60초다(원문).
- "Running On-Demand G and VT instances" 할당량은 기본값이 0이고 단위가 vCPU다(원문). 늘리는 데 걸리는 시간은 공식 수치가 없고, 사례는 30분에서 한 주 넘게까지 퍼져 있다(웹 요약).
- vLLM의 `--gpu-memory-utilization`은 인스턴스마다의 한도이고, 한 GPU에 두 인스턴스를 띄우면 0.5씩 줄 수 있다고 문서가 적는다(원문). 가중치는 A.X-4.0-Light 14.52GB, gpt-oss-20b 13.76GB(원문, Hugging Face 파일 목록)라 48GB 한 장에 둘이 들어간다는 것은 어림이다. 24GB 한 장에서는 차례로 올려야 한다(어림).
- 인스턴스 안에서 종료하면 삭제되게 하는 속성(`InstanceInitiatedShutdownBehavior=terminate`)이 있고 사용자 데이터는 첫 부팅 때 root로 돈다(원문). 사용자 데이터에 종료 타이머를 넣어 세션이 죽어도 스스로 지워지게 하는 조합은 어림이고 돌려 보지 않았다.
- AWS Budgets는 청구 데이터가 하루에 한 번쯤 갱신되어 실시간 차단기가 아니다(원문).
- IAM 정책은 `ec2:RunInstances`에 인스턴스 유형·리전·요청 태그 조건을, `ec2:TerminateInstances`에 자원 태그 조건을 걸 수 있다(원문, AWS 예시 정책).
- SSM 포트 포워딩(`AWS-StartPortForwardingSession`)은 인바운드 포트를 열지 않고 로컬 포트를 서버의 포트에 잇는다. Windows용 플러그인은 설치 프로그램이나 zip으로 깐다(원문). 서버 쪽 권한은 계정 수준 설정이나 인스턴스 프로필(`AmazonSSMManagedInstanceCore`)로 준다(본 세션이 받은 원문, `aws-ssm-instance-profile.md`).
- vLLM의 `--api-key`는 `/v1` 등 몇 경로만 인증하고 `/invocations` 같은 다른 경로는 인증 없이 남으며, 문서가 그것 하나에 기대지 말라고 적는다(원문, 본 세션도 받은 글에서 다시 봤다).
- CloudFormation은 스택을 지우면 보존 정책을 건 것 말고는 그 스택의 자원을 모두 지운다(본 세션이 받은 원문, `aws-cfn-delete-stack.md`). Terraform은 로컬 상태 파일이 지울 대상의 기록이다(어림, 일반 지식).
- 공식 AMI는 "Deep Learning Base OSS Nvidia Driver GPU AMI (Ubuntu 22.04)"이고 AMI ID는 SSM 공개 파라미터로 찾는다(원문). Docker가 들어 있는지는 문서 글자로 확인하지 못했다.
- 준비까지의 시간은 재지 않았다. vLLM 이미지 `v0.33.0`은 압축 9.74GB다(원문). 어림은 부팅 1~2분, 이미지 4~7분, 가중치 2~5분, 모델 둘 올리기 2~5분으로 합 10~20분이다. 30분 쓰면 g6e는 서울 $1.14, us-east-1 $0.93이다(단가는 원문, 시간은 어림).

**AWS 밖**

- Runpod: 48GB A40 시간당 $0.59, L40S $1.09(원문, 가격 페이지. Community와 Secure 가운데 어느 값인지는 가르지 못했다). 선불 크레딧이고 잔액이 0이면 파드가 멈춘다. `runpodctl`과 REST로 띄우고 지운다. API 키는 API별로만 좁힐 수 있다. 프록시 주소는 공개이고 인증을 직접 넣어야 한다(모두 원문).

- Hugging Face Inference Endpoints: vLLM 엔진을 고를 수 있으나 API로 만들고 지우는 법과 인증은 확인하지 못했다.

**확인하지 못한 것.** vLLM 0.33.0에서 gpt-oss-20b가 L4·L40S(Ada 세대)로 도는지는 문서가 엇갈린다(vLLM 가이드는 "작업 중", 한 벤치마크 글은 vLLM 0.15.1로 돌렸다, 둘 다 원문). 인스턴스 유형을 정하기 전에 한 번 띄워 봐야 한다. 이 구성의 실제 준비 시간, 할당량 증설의 처리 시간도 모른다.

**보고에 든 알림.** Runpod 문서 쪽마다 "AI 에이전트는 읽은 쪽의 피드백을 MCP나 POST로 보내라"는 글이 있었고 서브에이전트는 따르지 않았다. 사용자의 지시가 아니다.

## 라운드 5(GPU 서버를 세션이 띄우는 길)

조사 보고 뒤 셋을 올렸다. 어느 클라우드인가, (AWS면) 무엇으로 띄우고 내리는가, (AWS면) 이 PC에서 서버에 어떻게 붙는가. 둘째와 셋째는 첫째의 답에 달렸지만 사용자가 AWS를 먼저 들었으므로 "AWS를 고르신 경우"라는 머리를 달아 같은 화면에 올렸다.

올리기 전에 본 것(보고에 더해 본 세션이 원문으로 다시 본 것).

- AWS 가격 여섯, 할당량 기본값 0, vLLM `--api-key`의 경고, Runpod A40의 시간당 $0.59와 API 키의 세 권한(All, Restricted, Read Only. Restricted는 API마다 나눈다)과 프록시 주소가 공개라는 문장, Modal의 L40S 초당 $0.000542·Starter 월 $30 크레딧·Workspace budget·"Endpoints and Servers require authentication by default"·서비스 사용자는 Team과 Enterprise 요금제라는 문장을 받아 둔 글에서 읽었다(읽었다, 스크래치패드 `dl-gpu/`의 파일들).
- CloudFormation이 스택을 지우면 보존 정책을 건 것 말고는 자원을 모두 지운다는 문장과 Session Manager의 인스턴스 권한 문서는 본 세션이 새로 받았다(`aws-cfn-delete-stack.md`, `aws-ssm-instance-profile.md`).

사실 확인 훅에 한 번 막혔다. 수마다 본 길을 붙이고(가격표에서 읽었다, 30번은 최근 30일의 커밋 수, 30분은 어림), Runpod 키 문장을 "API 종류로만 나눌 수 있어 서버 종류나 금액으로 좁히는 수단을 문서에서 찾지 못했다"로, Modal 문장에 예시의 판(0.21.0)과 요금제 이름을 넣어 같은 질문과 라벨로 다시 올렸다.

호출 곁 본문에서 개념 넷(GPU 할당량, CloudFormation, Terraform의 상태 파일, SSM 포트 포워딩)을 풀고, 선택과 무관하게 지키는 조건 넷을 적었다. (1) 세션은 서버를 띄우기 직전에 예상 비용을 보여 주고 한 번 확인받는다. (2) 계정·결제 수단·할당량 신청·이 용도 전용 자격 증명은 사용자가 한 번 준비하고, 세션은 계정을 만들거나 키를 입력하지 않으며 이 PC에 이미 있는 AWS 프로필을 임의로 쓰지 않는다. (3) 서버는 일정 시간 뒤 스스로 종료하고 삭제되게 걸린 채로 뜬다. (4) 시험은 주소와 키만 받으므로 준비가 끝나기 전에는 사용자가 다른 곳에 띄운 서버의 주소로도 시험할 수 있다.

> 사용자: (로컬 모델 시험용 GPU 서버를 어느 클라우드에서 띄울까요?) 선택지를 고르지 않고 직접 적었다: "Runpod은 테라폼으로 못해? 아니면 다른 도구 있나? 테라폼이 가장 많이 쓰이고 좋아?"

결정이 아니라 되물음이다. Runpod을 Terraform으로 다룰 수 있는지를 찾은 뒤 클라우드를 다시 묻는다.

> 사용자: ((AWS를 고르신 경우) 서버를 띄우고 내리는 수단은 무엇으로 할까요?) "Terraform" — 설명: 이 PC에 이미 설치돼 있고(1.5.5이고, 그 프로그램이 최신은 1.17.1이라고 알립니다), 다른 클라우드로 옮길 때 같은 도구를 씁니다. 치르는 값: 무엇을 지울지의 기록(상태 파일)이 PC의 파일입니다(일반 지식이고 원문으로 대 보지 않았습니다). 이 저장소는 병합 뒤 워크트리를 지우므로 상태 파일을 워크트리 밖이나 S3에 두는 설정이 따로 필요하고, 그 파일을 잃으면 남은 서버를 손으로 찾아 지워야 합니다.

**추천안이 아닌 선택이다.** 첫 질문의 되물음과 함께 읽으면 사용자는 클라우드와 무관하게 Terraform을 쓰고 싶어 한다.

> 사용자: ((AWS를 고르신 경우) 이 PC에서 모델 서버에 어떻게 붙을까요?) "포트를 열지 않고 붙는다 (Recommended)" — 설명: AWS의 관리 통로(SSM 포트 포워딩)로 이 PC의 포트를 서버 안의 포트에 잇습니다. 서버는 인터넷에서 들어오는 포트를 하나도 열지 않습니다(AWS 문서 원문). 치르는 값: 사용자가 이 PC에 Session Manager 플러그인을 한 번 설치해야 하고(지금은 설치돼 있지 않습니다), 서버가 그 통로를 쓰도록 권한(인스턴스 역할)을 한 번 만들어 둬야 합니다.

고르지 않은 선택지(라벨만): "AWS EC2 (Recommended)", "Runpod", "Modal", "CloudFormation 템플릿 (Recommended)", "AWS CLI 스크립트", "내 IP에만 열고 키로 막는다", "SSH 터널로 붙는다".

되물음 뒤에 본 것(Runpod과 Terraform. 원문은 스크래치패드 `dl-gpu/`에 받았다).

- Terraform 레지스트리에 `runpod/runpod` 프로바이더가 있다. 최신 판은 2.0.0이고 2026-10-27에 발행됐으며, 소스는 Runpod 조직의 `terraform-provider-runpod`이고 레지스트리 등급은 community다(읽었다, `tf-registry-runpod.json`). Runpod 문서에 Terraform 연동 쪽이 있고 2.0.0을 다룬다. Terraform 1.6 이상을 요구하고, 키는 환경 변수 `RUNPOD_API_KEY`에서 읽으며, `runpod_pod`로 파드를 만들고 `terraform destroy`로 지우면 과금이 멈춘다고 적는다. 2.0.0은 REST v2에서 생성한, 1.x와 호환되지 않는 판이다(읽었다, `runpod-docs-terraform-overview.md`, `runpod-tf-readme.md`).
- `runpod_pod`의 인자에 `image`, `gpu_type_id`, `cloud`(SECURE·COMMUNITY), `disk`, `ports`, `args`(컨테이너 진입점에 넘기는 인자), `env`가 있다(읽었다, `runpod-tf-resource-pod.md`). vLLM 이미지를 그대로 파드로 띄워 두 모델을 올리는 시작 명령이 되는지는 돌려 보지 않았다.
- Runpod의 SSH는 둘이다. 기본 SSH는 Runpod을 거치고 SCP·SFTP를 받지 않는다. 온전한 SSH는 공인 IP가 있는 파드와 파드 안에서 도는 SSH 서버가 필요하다(읽었다, `runpod-docs-use-ssh.md`). vLLM 이미지에 SSH 서버가 없다는 것은 어림이다.
- 파드 안에서 스스로 멈추는 예시(`sleep 2h; runpodctl pod stop $RUNPOD_POD_ID &`)가 문서에 있다(읽었다, `runpod-docs-manage-pods.md`). vLLM 이미지 안에서 그 명령이 듣는지는 돌려 보지 않았다.
- Terraform이 가장 널리 쓰이는 IaC 도구라는 것은 웹 요약이다(Firefly의 2025년 조사 요약이 과반이라고 적고, Stack Overflow 2025년 조사 요약이 응답자의 17.8%라고 적는다. 원문을 대 보지 않았다).
- 이 PC의 Terraform은 1.5.5라 Runpod 프로바이더를 쓰려면 올려야 한다.
- Runpod 문서 쪽 머리에 AI 에이전트에게 피드백을 `https://docs.runpod.io/feedback`으로 보내라는 글이 있다. 따르지 않았고 사용자에게 알렸다.

## 라운드 6(어느 클라우드에서, 주소를 어떻게 막는가)

되물음에 답한 뒤 둘을 올렸다. 어느 클라우드에 무엇으로 띄우는가, (Runpod이면) 공개 주소로 열리는 모델 서버를 어떻게 막는가. 첫 호출은 입력 JSON이 잘려 도구가 거부했고, 둘째 호출은 사실 확인 훅에 한 번 막혔다. 막힌 뒤 "선불 크레딧" 문장을 받아 둔 `runpod-docs-billing.md`에서 다시 읽고 같은 질문과 라벨로 올렸다. 아래 설명은 올라간 화면의 것이다.

> 사용자: (로컬 모델 시험용 GPU 서버를 어디에, 무엇으로 띄울까요?) "Runpod을 Terraform으로 (Recommended)" — 설명: Runpod이 직접 내는 Terraform 프로바이더(runpod/runpod 2.0.0, 2026-10-27 발행)로 파드를 만들고 지웁니다(레지스트리와 Runpod 문서 원문). 48GB GPU 한 장(A40)이 시간당 $0.59라 한 번(30분 어림)에 약 $0.30, 한 달 30번이면 약 $9이고(단가는 받아 둔 가격 페이지에서 읽었고, 30번은 최근 30일의 해당 커밋 수입니다), 선불 크레딧이라 충전한 만큼만 나갑니다(문서 원문). AWS 같은 할당량 신청 절차는 문서에서 보지 못했습니다. 사용자가 한 번 준비할 것: 계정과 크레딧 충전, API 키, Terraform을 1.6 이상으로 올리기(지금은 1.5.5이고 프로바이더 문서가 1.6 이상을 요구합니다). 치르는 값: 프로바이더 2.0.0이 나온 지 두 주 된 새 판이고(레지스트리 등급은 community), API 키의 권한을 서버 종류나 금액으로 좁히는 수단을 문서에서 찾지 못했으며, 서버 주소가 공개 주소입니다(다음 질문). vLLM 이미지를 파드로 띄워 두 모델을 올리는 것은 돌려 보지 않았습니다.

> 사용자: ((Runpod을 고르신 경우) 공개 주소로 열리는 모델 서버를 어떻게 막을까요?) "vLLM 키로 막고 남는 틈은 받아들인다 (Recommended)" — 설명: 띄울 때마다 새 무작위 키를 만들어 vLLM의 --api-key로 줍니다. 더 설치할 것이 없습니다. 치르는 값: vLLM 문서가 /invocations 같은 일부 경로는 인증 없이 남는다고 적으므로(원문), 무작위 파드 ID가 든 주소를 알아낸 사람은 서버가 떠 있는 동안 그 GPU로 모델을 돌릴 수 있습니다. 서버에는 공개 모델과 시험용 글만 있고, 서버는 타이머로 꺼지며, 요금은 선불 잔액을 넘지 않습니다.

고르지 않은 선택지(라벨만): "AWS를 Terraform으로", "Modal", "파드 안에 인증 프록시를 둔다", "SSH로 포트를 잇는다".

이 답으로 라운드 5의 셋째 답(AWS의 관리 통로로 포트를 열지 않고 붙는다)은 쓰이지 않는다. AWS를 고른 경우에만 해당하는 답이었다.

고른 설명에서 바로잡을 것 하나. "요금은 선불 잔액을 넘지 않습니다"는 자동 충전을 켜지 않았을 때만 맞다. Runpod에는 잔액이 문턱 아래로 내려가면 저장된 카드로 다시 채우는 자동 충전(auto-pay)이 있다(읽었다, `runpod-docs-billing.md`). 합의 요약에서 "자동 충전을 켜지 않는다"를 준비 조건으로 올려 확인받는다.

### 갈래 밟기 셋째(세션이 서버를 띄우는 절차)

라운드 4의 되물음부터 라운드 6까지의 답은 병합 절차에 "세션이 서버를 띄우고, 시험하고, 내린다"를 더한다. 그 절차의 중간으로 들어오는 갈래를 밟았다.

- **넘겨받은 세션과 끊은 뒤 이어 가는 세션.** 앞 세션이 서버를 띄운 채 끝났을 수 있다. 띄우기·준비 기다리기·시험·내리기를 명령 하나가 이어서 하고, 그 명령이 시작할 때 같은 상태 파일에 남은 서버를 먼저 내리면, 넘겨받은 세션은 같은 명령을 다시 치면 된다. 명령이 중간에 죽어 남은 서버는 타이머가 끈다. 상태 파일은 워크트리 밖, 브랜치마다 따로 둔다. 어긋나는 동작은 없고 명세가 정할 것이다.
- **키가 세션의 글에 남는 갈래.** 세션이 서버 주소와 vLLM 키를 손으로 옮기면 키가 대화와 일지에 남을 수 있다. 명령 하나가 키를 만들어 시험에 환경 변수로 넘기고 찍지 않으면 세션은 키를 보지 않는다. Terraform 상태 파일에는 키가 평문으로 남는데(어림, 일반 지식), 그 파일은 저장소 밖에 있고 키는 서버와 함께 죽는다.
- **열린 PR에 리뷰를 반영하는 세션.** 시험 뒤에 계기 경로를 다시 고치면 기록이 무효이고 서버를 한 번 더 띄운다. 라운드 4에서 정한 대로 마지막 봇 회차 뒤 병합 직전에 한 번 돌리면 한 번으로 끝난다.
- **규약이 면제하는 단계.** 문서와 하네스만 바꾼 변경은 해당하지 않는다. Terraform 파일과 띄우는 스크립트는 "로컬 모델 시험 자신"에 든다고 읽어 그것을 고친 변경도 시험을 돌린다. 합의 요약에서 확인받는다.
- **규약이 서기 전에 열린 일.** 어댑터를 처음 넣는 PR이 첫 대상이라, 그 PR이 병합되기 전에 Terraform 파일과 스크립트가 있어야 하고 사용자의 준비(계정, 크레딧, 키, Terraform 올리기)가 끝나 있어야 한다. 준비가 늦으면 그 PR이 기다리거나, 사용자가 다른 곳에 띄운 서버의 주소로 시험한다.
- **나란히 도는 세션.** 둘이 동시에 서버가 필요하면 브랜치마다 다른 상태 파일로 파드를 따로 띄운다. 비용이 그만큼 는다.
- **띄울 수 없는 세션.** 키와 Terraform이 없는 자리(클라우드 세션)에서는 띄우지 못한다. 이 PC의 세션에 넘기거나 기다린다.
- **비용 확인.** 세션은 띄울 때마다 예상 비용을 보여 주고 확인받는다. 그래서 이 범위의 PR은 병합 직전에 한 번 멈춰 묻는다. 지금의 "병합은 묻지 않고 한다"에 예외가 생긴다. 합의 요약에 드러내 확인받는다.
- **시험이 모델의 흔들림으로 실패하는 갈래.** 병합을 막는 시험이 실제 모델을 부르므로, 코드는 맞는데 모델이 한 번 도구 호출을 빠뜨려 실패할 수 있다. 다시 돌려 통과하면 통과로 볼지가 정해지지 않았다. 지금의 실제 모델 시험에는 그런 규칙이 없다(읽었다, `operations.md` LLM 테스트 절). **아직 열린 가지다.** 다음 화면에서 묻는다.

밟으면서 더 본 것.

- 모델 파일에는 이미 `temperature` 칸이 있다(0 이상 1 이하, 읽었다, `src/agent_os/sdk/manifest.py`). 시험용 모델 파일에서 0으로 두어 흔들림을 줄일 수 있다.
- Runpod 문서는 파드마다 `runpodctl`과 그 파드에만 듣는 API 키가 미리 들어 있다고 적는다(읽었다, `runpod-docs-runpodctl-overview.md`). vLLM 이미지로 띄운 파드에서도 그런지는 돌려 보지 않았다.
- 멈춘 파드는 계산 요금이 없고 볼륨 디스크 요금만 나간다(시간이 아니라 용량으로, GB당 월 $0.20). 잔액이 0이 되면 네트워크 볼륨이 없는 파드는 삭제된다(읽었다, `runpod-docs-api-create-pod.md`, `runpod-docs-billing.md`). 타이머가 "멈춤"이 아니라 "삭제"까지 가게 할지는 명세가 정한다.
- 어댑터 폴더에는 지금 파일이 여섯 있다(`anthropic.py`, `clock.py`, `filesystem.py`, `jsonl.py`, `mcp.py`, `mcp_launcher.py`, Glob으로 봤다). 라운드 4의 30건은 `adapters/` 전체를 넣어 센 수다.

## 라운드 7(흔들림 판정과 합의 요약)

남은 가지 하나(시험이 모델의 흔들림으로 실패했을 때의 판정)와 합의 요약 셋을 한 화면에 올렸다. 요약은 선택지의 설명 안에 적었다. 질문 화면이 떠 있는 동안 본문이 보이지 않을 수 있어서다. 사실 확인 훅에 한 번 막혔고, 막힌 뒤 셋을 다시 봤다. 범위의 커밋 수는 다시 세어 30건이었다(손으로 봤다, `git rev-list --count --since=2026-10-12 HEAD -- src/agent_os/core/run.py src/agent_os/core/loop.py src/agent_os/core/model.py src/agent_os/adapters src/agent_os/channel src/agent_os/main.py`). MCP 어댑터는 모델에 넘길 도구 설명(`ToolSpec`의 `input_schema`)을 만든다(읽었다, `src/agent_os/adapters/mcp.py`). CI의 잡은 모두 GitHub이 제공하는 ubuntu 러너에서 돈다(읽었다, `.github/workflows/ci.yml`의 `runs-on`. 그 러너에 GPU가 없다는 것은 일반 지식이다). 설명 두 곳에 본 길을 붙여 같은 질문과 라벨로 다시 올렸다. 아래 설명은 다시 올린 화면의 것이다.

> 사용자: (로컬 모델 시험이 실패했을 때, 다시 돌려 통과하면 통과로 볼까요?) "한 번 실패하면 실패로 본다 (Recommended)" — 설명: 다른 실제 모델 시험과 같은 판정입니다(지금 규약에는 다시 돌려 통과로 치는 규칙이 없습니다. operations.md의 LLM 테스트 절을 읽었습니다). 실패하면 세션이 멈춰 원인을 보고하고, 고친 뒤 서버를 다시 띄워 처음부터 돌립니다. 흔들림은 시험을 짜는 쪽에서 줄입니다(시험용 모델 파일의 temperature를 0으로 두는 등. 그 칸은 이미 있습니다. sdk/manifest.py를 읽었습니다). 치르는 값: 코드는 맞는데 모델이 한 번 도구 호출을 빠뜨리면 병합이 멈추고, 서버를 한 번 더 띄우는 비용과 확인이 듭니다. temperature 0으로 흔들림이 얼마나 줄어드는지는 재지 않았습니다.

> 사용자: (모델 파일과 런타임 동작을 아래 요약대로 합의한 것으로 적어도 될까요?) "이대로 적는다 (Recommended)" — 설명: (1) 제공사에 새 값 openai-compatible을 더하고, 이 값의 모델 파일은 서버 주소(base_url)를 반드시 적습니다. 주소는 비밀이 아닌 것으로 보고 파일에 그대로 둡니다. (2) 키는 값이 아니라 환경 변수 이름(api_key_env)을 적습니다(선택 칸). 그 변수가 없으면 첫 모델 호출에서 실패합니다. 키 값은 이벤트, 로그, 실패 문구에 싣지 않습니다. (3) 런타임은 표준 요청(Chat Completions)만 보내고, 엔진마다 다른 설정은 서버를 띄우는 쪽이 맞춥니다. 사고 칸은 읽지 않고, max_tokens가 없으면 상한을 보내지 않습니다. (4) 인자가 깨진 도구 호출은 그 실행을 실패로 끝내고, 글로 샌 도구 호출은 답으로 보입니다(서버 설정 안내와 시험으로 막습니다). (5) 새 의존성은 langchain-openai이고, 시험으로 확인하는 엔진은 vLLM 하나입니다. (6) 새로 덧붙인 세부: anthropic 파일에 주소나 키 칸이 있거나 openai-compatible 파일에 주소가 없으면 파일을 읽을 때 거부합니다. 주소는 http와 https만 받습니다. 환경에 OPENAI_API_KEY가 있어도 모델 파일이 가리키지 않으면 쓰지 않습니다. 서버가 오류 글에 키를 되돌려 보내면 가립니다.

> 사용자: (시험과 병합 규칙을 아래 요약대로 합의한 것으로 적어도 될까요? (해당 범위의 '어댑터'를 어디까지로 읽을지도 함께 골라 주세요)) "어댑터 폴더 전체로 적는다 (Recommended)" — 설명: (1) 평소 pytest와 CI는 이 PC 안의 가짜 호환 서버로 돌고, 실제 로컬 모델 시험(새 꼬리표 llm_local)은 손으로만 돌리며 환경이 없으면 건너뛰지 않고 실패합니다. (2) 해당 범위: adapters/ 폴더 전체, core/loop.py, core/model.py, core/run.py, channel/, main.py, 로컬 모델 시험 자신(서버를 띄우는 Terraform 파일과 스크립트 포함), langchain-openai와 openai의 판 변경. 고르신 설명이 '-m llm의 계기를 모두 품는다'고 적었고 그 계기의 어댑터는 폴더 전체라서 이렇게 읽었습니다. 그러면 '-m llm을 돌려야 하는 변경은 llm_local도 돌린다'는 한 줄로 기억할 수 있습니다. 최근 30일 30건은 폴더 전체로 센 수입니다(git으로 다시 세어 봤습니다). (3) 이 범위를 고친 변경은 두 모델 모두 통과해야 병합하고, 어댑터를 처음 넣는 PR부터 적용합니다. (4) 시험은 마지막 리뷰 반영 뒤 병합 직전에 한 번 돌리고, 시험한 커밋, 모델, 서버 판을 PR 코멘트와 일지에 적습니다. 그 커밋 뒤로 해당 범위가 바뀌지 않았으면 기록이 유효합니다. 설계 트리에 열린 가지가 없다. 위 요약 셋이 확인받은 합의다. 요약의 "이 PC 안의 가짜 호환 서버"는 시험을 도는 기계의 루프백 주소에 띄우는 가짜 서버를 쉬운 말로 적은 것이고, ADR에는 그 말로 옮긴다.

## domain-modeling(용어와 ADR 초안)

**용어.** `CONTEXT.md`의 **모델**에 "모델 서버에 붙는 모델이면 그 서버의 주소와 키를 읽을 환경 변수의 이름도 든다"를 더하고, **모델 서버**(OpenAI 호환 API로 모델을 내는 런타임 밖의 서버)와 **서빙 엔진**(모델 서버를 이루는 소프트웨어)을 더했다. 모델 항목이 피하는 말 "엔드포인트"는 그대로 두었다. "로컬 모델 시험"은 넣지 않았다. 용어집에 실제 모델 시험 계열의 항목이 없고 마커 `llm_local`이 붙은 시험을 가리키는 규약의 말이라, ADR 안에서 푼다.

**ADR을 둘로 냈다.** 제품의 결정(제공사, 모델 파일, 런타임의 동작, 의존)과 절차의 결정(로컬 모델 시험의 병합 조건, GPU 서버를 띄우는 방식)은 결정의 단위가 달라 뒤의 것만 바뀔 수 있다(클라우드를 바꾸거나 병합 조건을 푸는 것은 계약을 건드리지 않는다). 기능 계획은 주소의 자리를 ADR 0040의 이력에 적으리라 했으나, 새 의존성과 실패 처리까지 정하게 되어 새 ADR로 냈다. 기능 계획의 본문은 고치지 않는다(설계 PR이 설계 줄만 더한 선례는 #499의 `.scratch/mcp-http/plan.md`, `git show --stat`로 봤다).

- ADR 0057: 모델 제공사에 `openai-compatible`을 더해 모델 파일에 적은 주소의 모델 서버에 붙는다.
- ADR 0058: 로컬 모델 시험은 실행 코드를 고친 변경의 병합 조건이고, 그 시험의 모델 서버는 세션이 Runpod에 Terraform으로 띄웠다 지운다.

**번호.** 처음에는 0056과 0057로 썼다. 파일을 만든 뒤 `uv run python tools/sibling_overlap.py`가 형제 워크트리 `release-image-design`의 ADR 0056(릴리스 이미지)과 겹친다고 알려(종료 1) `--move`로 0057과 0058로 옮겼다. 다시 돌리니 겹침이 없다. 그 워크트리는 `.scratch/deploy-package/plan.md`, `CONTEXT.md`, `docs/adr/README.md`도 함께 고치고 있어, 늦게 병합하는 쪽에서 글자 충돌이 날 수 있다.

**함께 고친 것.** ADR 0040의 세 문장 뒤에 `(바뀜: ADR 0057)` 포인터를 달았다(둘째 제공사를 거부하며 `provider`가 `anthropic` 하나라고 적은 문장, 모델 매니페스트의 모양을 적은 문장, 키가 `ANTHROPIC_API_KEY`라는 문장). ADR 색인에 두 행을 더했다. `docs/constitution/tech.md`의 런타임 의존성 행에 `langchain-openai`의 문장을, 새 행 "시험용 모델 서버"를 더하고 헌법 판을 3.0.85로 올렸다(둘 다 구현 티켓이 들이기 전이라 "그때까지 저장소에 없다"고 적었다. 선례는 ADR 0049의 "mcp-http의 첫 티켓이 선언한다"). `.scratch/deploy-package/plan.md`에 배포 안내로 넘기는 문단을 더했다.

**다른 ADR의 본문을 본 것.** `docs/adr/`를 `anthropic` 하나·`ANTHROPIC_API_KEY`·둘째 제공사로 grep해 ADR 0040 밖에는 바뀌는 문장이 없음을 봤다. 실제 모델 시험과 병합 규칙 쪽은 `-m llm`·`llm_portal`·`병합할지`로 grep해 ADR 아홉의 문장을 봤고, 거짓이 되는 문장은 없다. ADR 0043(티켓 PR은 dev로)의 "main PR의 CI에 LLM 테스트를 더한다"는 그대로 참이고, ADR 0058은 그 CI에 `llm_local`이 들지 않는다는 것과 전환 뒤 조건이 티켓 PR의 병합에 붙는다는 것을 Consequences에 적었다.

**합의 요약에 없던 것을 ADR에 적은 것.** 승인 화면에서 드러내 확인받는다.

- ADR 0057: 깨진 인자의 실패 내용은 도구 이름만 들고 깨진 글은 싣지 않는다(가려야 하는 인자가 그 글에 있을 수 있다, ADR 0009). 타임아웃과 재시도의 칸을 두지 않는다. 요청은 Chat Completions로 고정하고 `tool_choice`를 싣지 않는다. `schema_version`은 `"1"` 그대로다. 구현 티켓의 수락에 "DEBUG 로그에 키 값이 나타나지 않는다"를 넣는다. 모델 파일을 쓰는 사람이 운영자의 환경 변수를 제 주소로 보내게 적을 수 있고 그것을 막는 승인은 두지 않는다(ADR 0049와 같은 판단). 깨진 인자를 확인하는 자리, 제공사로 가르는 자리와 모듈의 이름, 키 변수 이름의 꼴, 되울린 키를 가리는 자리는 출발점만 적고 명세로 넘겼다.
- ADR 0058: 제품 판을 내기 전에도 한 번 돌린다(라운드 1의 고른 설명에 있던 계기다. 라운드 7의 요약에서 빠졌으나 거둔 적이 없어 적었다). 기록에 모델 서버의 옵션과 통과 수와 토큰 합계를 넣는다(라운드 1·2의 고른 설명). ADR 0043의 전환 뒤에는 조건이 티켓 PR의 병합에 붙는다. 세션은 `RUNPOD_API_KEY`의 값을 읽지 않는다. 명령이 시작할 때 같은 상태 파일에 남은 서버를 먼저 지우는지는 명세로 넘겼다.

## 인계(셀프 리뷰 직전)

셀프 리뷰(`/code-review`)를 부른 턴에 인계 계기(`hook_handoff`, 세션 컨텍스트 283,385 토큰)가 왔다. 인계하지 않는 때 다섯에 들지 않아 넘긴다(요청 범위는 PR과 병합까지이고, 이 세션을 연 지시문의 "이어받을 상태"는 "없음"이며, `get_session`의 `self`에 `parentSessionId`가 없다). 셀프 리뷰는 한 단계도 밟지 않았다. 이 세션의 지금 제목은 `docs/local-model-design`이다.

**이 세션이 번복하거나 고친 것.**

- ADR 번호를 0056·0057에서 0057·0058로 옮겼다(형제 워크트리 `release-image-design`의 ADR 0056과 겹쳤다, 위 domain-modeling 절).
- 라운드 6의 고른 설명 "요금은 선불 잔액을 넘지 않습니다"는 자동 충전을 켜지 않았을 때만 맞아, 라운드 7의 요약에서 준비 조건으로 올려 확인받았다.
- 라운드 4의 고른 설명 안에서 갈린 "어댑터"는 라운드 7에서 어댑터 폴더 전체로 확인받았다.
- 라운드 5의 셋째 답(AWS의 관리 통로로 붙는다)은 Runpod을 고르며 쓰이지 않게 됐다.
- 기능 계획은 주소의 자리를 ADR 0040의 이력에 적으리라 했으나 새 ADR로 냈다.

**남은 순서.** 셀프 리뷰(`/code-review`, 기준은 `origin/main`의 merge-base, 미추적 파일 셋 포함) → Critical·Major 반영 → ADR 0057·0058의 승인을 사용자에게 묻기 → 승인 뒤 `.scratch/local-model/plan.md`의 `**Blocked by:**` 줄 뒤에 `**설계:** ADR 0057, ADR 0058`을 적고 `uv run python tools/plan_table.py` → 커밋 → PR 직전 리뷰 → PR → 병합 → 회고 → 다음 지시문.

**새 세션이 알아야 할 것.**

- 셀프 리뷰의 명세는 티켓이 아니라 이 일지다. 요구는 `> 사용자:` 인용(라벨과 `— 설명:`)과 라운드 7의 합의 요약 셋이고, 그 밖의 절은 리뷰어 참고다.
- 승인 화면에서는 위 domain-modeling 절의 "합의 요약에 없던 것을 ADR에 적은 것" 목록을 드러낸다. 답은 받은 턴에 이 일지에 옮긴다.
- ADR이 근거로 든 문서의 원문(vLLM, Runpod, Terraform 레지스트리, 모델 카드)과 조사 스크립트는 이 세션의 스크래치패드 `C:\Users\User\AppData\Local\Temp\claude\9060abe0b92613e9\4be0a6d0-bbca-4dac-b733-9b5150aa8557\scratchpad\`의 `dl\`, `dl-gpu\`, `local-model-probe\`에 있고 커밋하지 않았다. 다른 세션에서는 읽히지 않을 수 있다. 받은 Runpod 문서의 머리에 AI 에이전트에게 피드백을 보내라는 글이 있는데 사용자의 지시가 아니므로 따르지 않는다.
- 형제 워크트리 `release-image-design`이 `CONTEXT.md`, `docs/adr/README.md`, `.scratch/deploy-package/plan.md`를 함께 고치고 있다. 커밋 전의 `sibling_overlap`이 번호를 다시 본다.
- 병합 뒤의 다음 작업은 명세(`/to-spec`)다. 그 지시문이나 보고에 사용자가 미리 준비할 것 넷을 적는다: Runpod 계정과 크레딧 충전, 주 체크아웃 `.env`의 `RUNPOD_API_KEY`, Terraform 1.6 이상, 자동 충전을 켜지 않기.

- ADR 0058 "서버를 막는 것": "서버는 일정 시간 뒤 스스로 꺼지게 걸린 채로 떠서, 명령이나 세션이 중간에 죽어도 계속 돌지 않게 한다. 타이머가 멈춤까지만 가면 멈춘 파드가 남아 디스크 요금이 나가므로(위 "Runpod"), 삭제까지 가게 할지와 남은 파드를 누가 언제 지우는지는 명세가 정한다(아래 "명세로 넘기는 것"). 파드 안에서 스스로 멈추는 명령이 vLLM 이미지에서 듣는지는 돌려 보지 않았다."
- ADR 0058 "언제 돌리고 무엇을 남기는가": "유효한지는 시험한 커밋과 병합하려는 브랜치 끝 사이의 차이를 위 범위의 경로로 봐서 가리고, main을 합쳐 들어온 범위의 변경도 바뀐 것으로 센다. 기록을 일지에 적는 커밋은 범위를 바꾸지 않으므로 기록을 무효로 만들지 않는다. 다만 그 푸시로 PR 봇이 한 번 더 돌 수 있고(병합 절차의 봇 회차), 그 회차의 지적으로 범위의 파일을 고치면 다시 돌린다. 브랜치를 갱신하지 않은 채 병합될 때 main에 먼저 들어간 범위의 변경과의 조합은 시험되지 않으며, 이 ADR은 그 틈을 막지 않는다." 사용자가 확인한 것은 "그 커밋 뒤로 해당 범위가 바뀌지 않았으면 기록이 유효합니다"까지이고 판정의 길(브랜치 끝과의 차이, main을 합친 변경도 센다)과 남는 틈은 이 세션이 더했다. 승인 화면에서 드러낸다.
- ADR 0058 "첫 적용"과 "명세로 넘기는 것": "그 PR보다 먼저 병합되는 변경(ADR 0057의 계약 티켓, 서버를 띄우는 파일을 따로 먼저 들이는 경우의 그 PR)에는 돌릴 시험이 아직 없어 이 조건이 붙지 않는다." "구현의 첫 티켓"을 "서버를 띄우는 파일을 들이는 티켓"으로 풀고 ADR 0057의 계약 티켓과의 순서는 티켓을 나눌 때 정한다고 적었다. 명세로 넘기는 것에 셋을 더했다(앞 세션의 명령이 아직 쓰는 서버를 가르는 법, 세션이 죽거나 PR이 버려져 남은 파드와 상태 파일을 누가 언제 지우는지, 서버 쪽 사정으로 끝까지 돌지 못한 회차를 실패로 셀지).
- ADR 0058 "병합 조건의 범위"와 Consequences: "다만 서버를 띄우는 Terraform 파일과 스크립트는 저장소의 어디에 두든(하네스의 자리인 `tools/`에 두더라도) 로컬 모델 시험 자신으로 세어 해당한다."
- ADR 0058 "규약이 서는 때": 고칠 자리를 일반 조항(실제 모델 시험의 마커를 이름으로 드는 살아 있는 문서와 코드 전부와 병합 절차. `llm_portal`로 다시 grep한다)으로 적고, 위 (8)의 Grep이 낸 파일을 예시로 들었다. 파일마다 무엇을 고칠지는 열어 보지 않았다고 적었다.
- ADR 0058 "브랜치 전략과의 관계": "dev로 가는 티켓 PR과, main에서 따 main으로 바로 가는 hotfix PR이 그것이다(ADR 0043의 "CI 분담"이 main PR을 dev→main과 hotfix→main으로 적는다)." 근거: ADR 0043 26행과 제목.
- ADR 0058 그 밖: 머리의 수락을 기능 계획의 것으로 적었다. "두 모델"에 라운드 2의 치르는 값을, "띄우지 못할 때"에 "이 PC의 세션에 넘기거나"를 더했다. 거부한 안에 추천 표시 셋을 달고(사람이 띄우는 셋 가운데 "병합 직전에 묻고 그 세션이 기다린다", AWS EC2, CloudFormation 템플릿) AWS를 전제로 올린 붙는 방법 셋이 모두 쓰이지 않는다고 적었다. 남긴 것과 이유.

- ADR 0040의 첫 포인터(거부한 안 "둘째 제공사를 지금 들인다")는 그대로 둔다. 그 문장은 근거가 아니라 "`provider`는 닫힌 목록이고 지금은 `anthropic` 하나다"라는 상태를 적어, 본문만 읽으면 지금의 값을 잘못 안다(`.claude/rules/adr.md` 첫 항목).
- Divergent Change(ADR 0058이 병합 조건과 클라우드 선택을 묶었다)는 그대로 둔다. 판단 사항이다. 비용 확인과 "띄우지 못할 때"가 세션이 서버를 띄운다는 결정에 기대어 함께 읽혀야 하고, 클라우드만 바뀌면 그 ADR의 이력에 쌓는다.
- "호환 서버"(가짜 호환 서버, 호환 서버 어댑터, 호환 서버 라이브러리)는 그대로 둔다(Nit). 용어집의 모델 서버는 런타임 밖에서 모델을 내는 서버이고, 시험의 가짜 서버와 어댑터·라이브러리에 붙인 "호환 서버"는 OpenAI 호환 API를 내는 쪽을 풀어 쓴 말이며 `_Avoid_`에 없다.
- 명세 축의 갈래 둘은 ADR 0058 "명세로 넘기는 것"에 적었다. 받는 쪽은 그 ADR을 읽는 명세(`/to-spec`)이고, 다음 지시문의 "이어받을 상태"에도 적는다.

승인 화면에 드러낼 것. 위 "합의 요약에 없던 것을 ADR에 적은 것" 목록에 명세 축 (b)와 이 반영이 더한 것을 보탠다. ADR 0057: 모델이 아닌 종류의 매니페스트에 주소나 키 칸이 있어도 거부한다(ADR 0040의 지금 규칙과 같다), import-linter의 금지 목록 둘에 새 라이브러리를 더하고 openai SDK를 직접 import하면 직접 의존으로 선언한다, 가짜 서버로 calc 예시를 끝까지 돌리는 시험을 평소의 시험에 둔다, 범위 밖에 자체 서명 인증서의 설정과 임베딩 같은 API를 적었다. ADR 0058: 기록이 유효한지의 판정(브랜치 끝과의 차이, main을 합쳐 들어온 변경도 센다)과 막지 않는 틈, 어댑터 PR보다 먼저 병합되는 변경에는 조건이 붙지 않는다, 서버를 띄우는 파일은 어디에 두든 해당한다, ADR 0043 전환 뒤 hotfix PR에도 붙는다, main PR의 CI에 `llm_local`이 들지 않는다, 명세로 넘긴 것 셋.

다시 돌린 명령. 문서만 바뀌어 린트·타입체크·경계·web은 바뀐 파일이 없다. 손으로 치는 다섯은 커밋의 pre-commit 결과로 갈음한다(결과는 커밋 뒤에 적는다). 반영 뒤 `uv run python tools/check_adr_pointers.py`, `tools/check_md_tables.py`, `tools/check_line_separators.py`를 쳤고 셋 다 출력 없이 끝났다(손으로 봤다). `uv run python tools/sibling_overlap.py`는 번호 겹침이 없다고 냈고 origin/main이 `768dee7`로 움직였다. `git diff --name-only HEAD...origin/main`은 ADR 0051과 그 일지 둘뿐이라 이 브랜치가 고친 파일과 겹치지 않는다(손으로 봤다). ADR 0057과 0058은 ADR 0051을 이름으로 들지 않는다(두 파일을 `0051`로 Grep해 일치가 없었다).

## 승인

셀프 리뷰를 반영한 뒤 두 ADR의 승인을 한 화면에 올렸다. 합의 요약에 없던 것은 "승인한다"의 설명 안에 적었다. 질문 화면이 떠 있는 동안 본문이 보이지 않을 수 있어서다. 올리기 전에 두 ADR을 처음부터 끝까지 다시 읽었고, 설명에 넣을 사실 둘을 댔다. 실행 전체의 기한 기본값은 600초다(읽었다, `src/agent_os/core/run.py` 201행의 `DEFAULT_RUN_TIMEOUT_SECONDS`). 다른 종류의 매니페스트에 적힌 `max_tokens`·`temperature`는 읽는 단계에서 거부한다(읽었다, ADR 0040 24행). 사실 확인 훅에 한 번 막혔고, 막힌 뒤 한 번 더 대다가 ADR 0058 "띄우지 못할 때"의 "이 PC의 세션에 넘기거나"가 합의 요약 (6)에는 없고 라운드 6의 갈래 밟기(이 세션이 적은 것)에서 온 말임을 봤다. 그것을 목록의 아홉째로 더해 같은 질문과 라벨로 다시 올렸다. 아래 설명은 다시 올린 화면의 것이다.
