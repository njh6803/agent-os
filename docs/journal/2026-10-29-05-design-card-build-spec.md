## 측정

설계가 넘긴 "재지 못한 것" 여섯 가운데 이 PC에서 잴 수 있는 것을 `.scratch/design-card-build/probes/card_build.mjs`로 쟀다. 결과와 갈래는 그 폴더의 `README.md`가 원천이다. 셋째 실행은 75회차가 모두 측정이었고 종료 0이었다.

- 저장소에 이미 있는 vite 8.3.1과 Tailwind CLI 4.3.3만으로 묶음(17,112바이트, 전역 `AgentOsUi`)과 빌드 CSS(23,482바이트, `@layer theme`), 글꼴 772개, 카드 장면 아홉을 지었다. 새 의존은 들지 않았다.
- 카드를 페이지와 같은 차례로 실은 문서를 chromium에 띄우자 장면 11개가 오류 없이 그려졌다(React 19.3.0 전역).
- 웹 편집을 흉내 낸 층 밖 토큰이 모든 요소를 덮었고, 같은 덮기를 층 안에 두자 하나도 덮지 못했다.
- 페이지 토큰을 실으면 `data-mode`는 컴포넌트 색을 바꾸지 않았고, 다크 테마 id에 `data-mode="light"`를 붙여도 코드의 다크 색과 같았다. 페이지 id(`guncheong-light`)와 코드 선택자(`guncheong`)의 어긋남도 페이지 토큰이 덮었다.
- 재지 못한 것: 실제 페이지(카드가 뜨는지, 글꼴, 다크의 바탕, React 18.3.1), 배너, 다시 그리기.

측정 중에 판 `1793146503-9e85`의 `app.js`를 다시 읽어 찾은 것: 카드 iframe의 토큰 CSS 뒤에 `html,body{background:transparent!important}`와 `html{color-scheme:<모드>}`가 붙는다(`Hdt`). 그래서 카드 안의 컴포넌트 색은 페이지 토큰이 정하고, 투명한 바탕 뒤로 비치는 것은 페이지 쪽이다. 테마 이름에 영어 낱말을 붙이는 결정(ADR 0025 2026-10-28 이력의 다크 테마)은 그 바탕과 `color-scheme` 몫으로 여전히 든다. 그리고 `main.ts build`가 지은 `tokens.json`에 `type.fonts`가 없다(`node -e`로 그 파일의 `type` 키를 손으로 봤다. `families`와 `groups`뿐이다). 페이지는 카드의 글꼴 CSS를 `type.fonts`로만 짓는다(`VT`를 읽었다). 그래서 카드가 Noto Sans KR로 그려지려면 묶음 CSS가 `@font-face`를 품어야 한다(코드 읽기에서 낸 추론이다).

## 사용자가 고른 것

시험 이음매와 남은 측정의 자리를 물었다. 첫 화면은 훅(`hook_choice_facts`)이 한 번 막았다. 설명의 사실을 대 보았다. `playwright`가 `web/package.json`의 직접 의존인 것, `storybook` 프로젝트가 `browser: chromium()`인 것, 페이지가 React 18.3.1을 스스로 싣는 것(`format.md`의 `components/lib/*.js` 행), 배너 조건(`TZ`)이 색인의 `source.app`에서 오는 옮김 표시와 `upgraded`를 보는 것을 확인했다. 늘어나는 시간은 프로브 한 바퀴(66초, 카드 약 165번 띄움)에서 어림한 값이라고 설명에 적었다. 배너는 임시 페이지의 색인으로 흉내 낼 수 있다는 것을 어림으로 적어 다시 올렸다.

> 사용자: "이대로 (추천)" — 설명: 짓기 명령의 산출 하나를 파일 검사와 chromium 그리기로 보고, 올리기는 지금 시험에 사례를 더합니다. 새 vitest 프로젝트는 만들지 않고, web이 이미 직접 의존으로 두는 Playwright를 씁니다. 늘어나는 시간은 이 PC에서 프로브 한 바퀴가 66초(카드를 165번쯤 띄움)였던 것에서 어림한 값입니다.

> 사용자: "지금 임시 아티팩트로 (추천)" — 설명: 명세를 쓰기 전에 나만 보는 디자인 시스템 페이지를 새로 만들어 지은 파일을 올리고 앱 안 브라우저로 봅니다. 페이지가 React 18.3.1을 스스로 실으므로 제가 따로 내려받지 않습니다. 배너는 임시 페이지의 색인에 '옛 도구에서 옮겨 온 시스템'이라는 표시를 적어 흉내 낼 수 있을 것으로 봅니다(어림). 결과가 결정을 바꾸면 명세에 바로 반영합니다.

> 사용자: "저장소의 React 19 (추천)" — 설명: 새 의존 없이 앱과 같은 React 19.3.0으로 돌립니다. 묶음은 JSX를 두 판에 함께 있는 createElement 호출로 바꿔 짓습니다(프로브의 묶음에 React 19 전용 요소 표식이 0개였습니다). React 18 위의 그림은 실제 페이지에서 확인합니다.

이 화면으로 확인받은 요약: 시험은 짓기 명령의 산출 폴더 하나를 이음매로 삼아 파일 검사와 chromium 그리기를 같은 `vitest run`에서 돌고, 올리기 계획은 지금의 올리기 시험에 사례를 더한다. 실제 페이지는 명세를 쓰기 전에 임시 디자인 시스템 아티팩트로 본다. 카드 그리기 시험은 저장소의 React 19로 돈다.

## 실제 페이지

임시 Design System 아티팩트(https://claude.ai/artifact/64VW1b5F8tRcCeTZBwZA29, 나만 본다)에 프로브의 `stage/` 배치를 올리고 판 다섯(3~7)을 차례로 올려 앱 안 브라우저로 봤다(손으로 봤다). 그 뒤 페이지가 웹 저장으로 쓴 판(`1793178461-b394`)을 받아 색인을 읽었다. 판마다 바꾼 것과 본 값은 `.scratch/design-card-build/probes/README.md`의 "실제 페이지" 절이 원천이다. 카드 iframe은 다른 출처라 도구가 안을 읽지 못해, 카드 안에서 값을 글로 찍는 진단 카드(`probes/page_diag_card.html`)를 함께 올리고 화면을 찍어 읽었다.

- 카드 아홉이 모두 그려졌다. 페이지는 React·ReactDOM 18.3.1 UMD를 jsDelivr에서 실었다.
- 묶음 CSS의 글꼴 주소 `../fonts/`는 풀리지 않았다. 카드는 묶음 CSS를 문서 안의 `<style>`로 싣고 기준 주소가 `components/<이름>/preview.html`이라, `../fonts/`가 `components/fonts/`로 풀려 글꼴 오류 5, 실림 0이었다. `../../fonts/`로 바꾸자 오류 0, 실림 9(Noto Sans KR)였다. ADR 0025 2026-10-28 이력이 명세로 넘긴 글꼴 경로는 이 결과로 정한다.
- 테마 이름에 '(Dark)'가 있으면 카드가 `data-mode=dark`, `color-scheme=dark`, 투명한 바탕으로 그려졌다. 이름에서 영어 낱말을 뺀 갈래에서는 같은 id `nokcheong-dark`가 `data-mode=light`, `color-scheme=light`였고 페이지가 바탕을 칠했다. 이름을 바꾸는 결정이 모드를 가른다.
- 색인에 `source.app: "claude-design"`을 넣자 "No move is perfect" 배너가 떴고, `upgraded`를 더하자 사라졌다.

- 웹 저장은 색인의 `source`와 `upgraded`를 지켰고, `libraries`의 항목마다 `global`을 붙였다.

임시 아티팩트는 지우지 않았다. 지우는 것은 되돌릴 수 없어 사람에게 묻는다.

## vite를 부르는 길

ADR 0025 2026-10-28 이력은 짓기를 올리기 도구의 명령으로 두라고 정했는데, vite는 디자인 시스템 패키지의 개발 의존뿐이고 `web/node_modules/vite`가 없다(ls로 봤다). 도구가 vite를 import하려면 `web/` 뿌리에 의존을 더해야 하고 헌법 `tech.md`가 그때 ADR을 요구한다. 그래서 도구가 import 없는 설정 글을 파일에 쓰고 패키지 자리의 CLI를 띄우는 길을 쟀다. 결과는 프로브 README의 "vite CLI" 절이 원천이다.

- `vite_cli.mjs`(pnpm을 거친 CLI): 회차 6이 모두 측정이었다. 묶음, Button 장면, 빌드 CSS가 `card_build.mjs`의 JS API 산출과 바이트까지 같았고, 견주기의 양성 대조(Alert 장면)는 같지 않다고 나왔다. 글꼴은 772개였고 `stage/`의 770개가 모두 같은 이름으로 들었다.
- `vite_cli_tool.mts`(올리기 도구 모양): `web/tsconfig.json`을 이어받은 설정으로 strict 타입 검사를 지났고, 타입 오류를 넣은 사본은 TS2322로 빨개졌다. 처음에는 확장자를 `.ts`로 두어 `web/` 밖이라 CommonJS로 읽혀 TS1295가 났고, `.mts`로 바꿨다. 셸 없이 `process.execPath`로 패키지의 `vite/bin/vite.js`를 띄우자 공백이 든 작업 폴더에서도 같은 묶음을 냈다(647ms, pnpm을 거치면 3,046ms).

## 명세

`spec.md`의 Implementation Decisions와 Further Notes를 쓰고 서두의 수를 셌다. 넘겨받은 것 열아홉, 사용자가 고른 것 셋(본문 여섯 자리), 명세가 정한 것 스무 자리, 거부한 안 열넷이고 ADR 이력은 없다. 쓰는 중에 찾은 것:

- 빌린 빌드가 패키지 엔트리가 내보내지 않는 상수(`ICON_NAMES` 등)를 전역에 더하던 `story-constants.js`는, 지금 showcase 스토리가 그 상수를 쓰지 않아 장면에서 비어도 그려진다(grep으로 봤다). 그래서 showcase 스토리는 엔트리가 내보내는 이름만 쓴다는 제약을 명세에 적었다.
- 실제 아티팩트 색인의 `libraries`는 빈 목록이다(판 `1793146503-9e85`의 받은 색인을 읽었다). 명세는 react·react-dom 18.3.1을 `global`과 함께 적게 했다.
- 아티팩트 README의 "Migrated from the standalone version" 절만 Design 캔버스가 복사할 옛 이름 넷을 모두 든다. 명세는 그 넷을 README 본문이 들게 했다.
- `.gitignore`의 빌린 빌드 무시 줄을 지우면 그 폴더가 남은 체크아웃이 깨끗하지 않게 보인다. 주 체크아웃에는 없고 워크트리 `08-first-upload`에만 있어(ls로 봤다), 지우는 티켓이 지우기 직전에 다시 찾게 했다.

이 세션이 쓰다가 고친 것:

- 명세의 넘겨받은 것 표에 "vite가 스토리 상수를 스스로 풀었다"고 적었다. 장면은 컴포넌트 모듈을 전역으로 돌려, 엔트리가 내보내지 않는 상수는 빈다. 그 줄을 나누어 고치고 카드 결정에 위의 제약을 더했다.
- 프로브 README의 해석 문장에 타입 검사를 `pyright`로 적었다. `pnpm -C web verify`의 타입 검사로 고쳤고, 그 뒤 해석 문단이 도구 모양 측정을 가리키게 다시 썼다.
- 명세의 "빌드 CSS 둘"을 "빌드 CSS"로 고쳤다. 산출은 하나다.
- 명세가 "아래 Implementation"으로 가리키던 참조 넷을 "위"로 고쳤다. 그 절은 참조하는 문장보다 앞에 있다.
- `.scratch/plan.md`는 origin/main(`06a8f85b`)을 합칠 때 프론티어 문단이 충돌했다. main 판을 바탕으로 이 세션의 한 문장만 다시 넣었다.
