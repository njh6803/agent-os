# CI python 잡의 시간 제한을 25분으로 올린다

admin-login 명세 PR #633(`docs/admin-login`)의 봇 회차 도중 CI `python` 잡이 15분 제한에 세 번 연달아 걸려 취소됐다. dev 푸시의 실행도 같은 이유로 취소돼 dev의 CI가 빨갰다. 그 세션이 대기열 `ci-python-job-timeout-margin`의 두 길을 사용자에게 넘겼고, 사용자가 제한을 올리는 길을 골랐다. 그 질문은 #633의 일지 `2026-11-24-1644-admin-login-spec.md`의 "봇 둘째 회차와 CI 시간 제한" 절에도 적는다(그 절은 #633의 다음 커밋에 실려, #633이 병합되면 dev에 든다). 앱이 새 세션을 여는 제안을 받지 않아, 같은 세션이 같은 워크트리에서 `origin/dev`를 기준으로 이 브랜치(`chore/ci-python-job-timeout-25`)를 따서 한다. #633은 이 PR이 병합된 뒤 dev를 합쳐 CI를 다시 돌린다.

> 질문: PR #633을 병합하지 못하고 있습니다. CI의 `python` 잡이 파이썬 시험 8136개를 한 프로세스로 차례로 도는데, 잡 시간 제한 15분에 걸려 세 번 연달아 취소됐습니다. 오늘 dev 브랜치의 실행(#631 병합 뒤)과 다른 PR도 같은 이유로 취소돼, 지금 dev의 CI가 빨갛습니다. 시간 제한은 멈춘 잡을 일찍 끊어 CI가 몇 시간씩 매달리지 않게 하는 장치인데, 잡이 실제로 걸리는 시간(약 15~16분)이 이 제한에 닿아 있습니다. 어떻게 풀까요?
>
> 사용자: 제한을 25분으로 올림 (Recommended) — "작은 하네스 PR을 따로 열어 `.github/workflows/ci.yml`의 `python` 잡 `timeout-minutes`를 15에서 25로 올립니다. 그 PR이 병합되면 dev와 이 PR이 풀릴 것으로 봅니다. 잡을 끝까지 돌린 마지막 실행이 14분 16초였고, 취소된 다섯 번은 끝까지 돌지 못해 실제 시간을 모릅니다. 25분이면 충분하다는 것은 어림입니다. 대가는 정말로 멈춘 잡을 10분 늦게 끊게 되는 것입니다."

다른 선택지는 "CI의 pytest를 나눠 돌림"과 "한 번 더 다시 돌림"이었다. pytest를 나누는 길은 ADR 0035가 CI의 pytest를 한 프로세스로 두기로 한 결정을 바꾸는 일이라 이력과 승인이 든다. 머리 주석의 네 배 규칙대로면 60분이지만, 선택 화면에 올린 값은 25분이었다.

## 한 일

- `.github/workflows/ci.yml`: `python` 잡의 `timeout-minutes`를 15에서 25로 올리고, 그 잡의 주석에 까닭을 적었다. 머리 주석에서 네 배에 못 미치는 잡을 적은 문장을 오늘 잰 값으로 고쳤다(python, web, e2e, visual, e2e-standalone).
- 프로브 `.scratch/harness/probes/ci_job_durations.py 40`을 다시 돌려, 결과를 `.scratch/harness/probes/README.md`의 그 프로브 행에 적었다.
- 대기열 `ci-python-job-timeout-margin`을 이 PR의 티켓으로 닫았다. 상태 줄 하나만 고쳤다(아래 셀프 리뷰의 명세 축 (b)).
- harness 티켓 `.scratch/harness/issues/ci-python-job-timeout-25.md`를 썼다.
- 일을 시작한 뒤 `git fetch origin`에서 PR #632(위젯 관리 서버 명세)가 dev에 병합된 것을 보았다. 이 브랜치에 커밋이 없어서, 고치던 대기열 항목 하나만 버리고 dev로 빨리 감기해 옮긴 뒤 다시 고쳤다.

## 근거

- 프로브 출력(`ci_job_durations.py 40`, 2026-11-24): 성공한 실행 40개가 모두 측정이었다. 최소·중앙·최대(분)는 python 12.6·14.2·15.0, web 3.3·4.5·5.7, e2e 1.2·1.6·8.5, visual 5.7·7.5·8.3, ticket 0.1·0.2·0.3, verify 0.0·0.1·0.1이었다. `e2e-standalone`은 시험이 든 실행 4개(45348076645, 45341537006, 44939486209, 44938065888)가 3.8·3.9·7.7분이었다. 이 프로브는 `e2e-widget`과 `e2e-portal`을 재지 않는다(`JOBS`에 없다). 셀프 리뷰 명세 축이 같은 인자로 다시 돌렸을 때 최소와 최대는 같았고, web의 중앙만 새 실행이 들어와 4.4였다.
- 취소된 까닭(손으로 봤다): `gh run view`의 실행 주석에 "The job has exceeded the maximum execution time of 15m0s"가 찍힌 시도만 시간 제한으로 셌다. `cancel-in-progress`가 새 푸시로 앞 실행을 끊은 것과는 이 표지로 가른다.
- 20시 반(한국 시각, 11:30 UTC) 이후 이 글을 쓴 때(13:45 UTC쯤)까지 끝까지 돌았거나 제한에 걸린 `python` 잡은 아홉 번이다(손으로 봤다, `gh run list`와 `gh run view --attempt`).
  - 시간 제한으로 취소된 여섯: PR #632 실행 45380651521의 셋째 시도(15분 11초), dev 푸시 45388134923(15분 17초), PR #633 실행 45390683089(15분 5초. pytest 단계가 `8136 passed`로 813.63초에 지난 뒤 `check_type_escapes.py` 단계에서), PR #632 실행 45393777826의 첫 시도(15분 1초), PR #633 실행 45396000251의 두 시도(15분 16초, 15분 15초. 둘 다 pytest 단계 도중).
  - 통과한 셋: PR #631 실행 45385713964(14분 16초), PR #632 실행 45400102550(14분 21초), #632 병합 뒤 dev 푸시 45402951692(12분 46초).
  - 셈에서 뺀 둘: 실행 45393777826의 둘째 시도는 22초에 저장소 계정 이름으로 취소됐고(사람이 했는지 다른 세션이 했는지는 모른다), 실행 45405790791은 아직 돌고 있었다.
  - dev의 CI는 #632 병합 뒤의 실행으로 지금 다시 초록이다. 손상(dev가 빨간 것)은 실행 45388134923부터 45402951692까지 한 번 났다.
- 질문을 낸 22:20쯤의 셈은 "여섯 번 가운데 통과 하나"였다. 그 뒤로 끝난 시도들이 더해져 위의 아홉 번이 되었다.
- 머리 주석의 첫 초안은 네 배에 못 미치는 잡을 python·web·visual 셋으로 적었다. 프로브 출력과 지금 제한을 대 보니 e2e(15/8.5)와 e2e-standalone(20/7.7)도 못 미쳐 다섯으로 고쳤다(손으로 나눴다). 그 넷은 이 티켓의 범위 밖이라 값을 고치지 않았다.
- 시험 가운데 `timeout-minutes` 값을 단언하는 것은 없다(`tests/`를 grep했다. 표준 축은 `tools/`도 봤다).

## 셀프 리뷰 (base `a68a51d61`, 파일 다섯, 커밋 0, 미추적 둘)

표준 축(sonnet, high)은 하드 위반 0, 판단 항목 여섯을 냈다. 명세 축은 빠진 요구 0, 요구 밖 하나, 틀려 보이는 것 넷을 냈다. Critical은 없다.

고친 것:

- 명세 (c)1, 일지의 셈: "저녁 8시 반 이후 여섯 번 가운데 통과 하나"에 반례(실행 45393777826, 45400102550)가 있었다. `gh run view --attempt`로 다시 세어 위 근거 절의 아홉 번으로 고쳤다.
- 명세 (c)3, 티켓의 단계: "다음 검사 단계에서 취소됐고"를 "`check_instructions.py` 단계를 지난 뒤 `check_type_escapes.py` 단계에서"로 고쳤다.
- 명세 (b), 승인 줄: 대기열 README는 닫을 때 상태 줄 하나만 고친다고 정한다. 처음에는 #633과의 충돌을 피하려고 승인 줄에 #633의 회차를 같은 글자로 더했는데, #632가 4회차를 먼저 가져가 충돌은 어차피 난다. 승인 줄은 dev 판으로 되돌렸다. #633의 사건은 #633이 dev를 합칠 때 그 브랜치에서 5회차로 더한다.
- 명세 (c)2와 표준 1, 없는 일지를 가리킴: 대기열 항목은 위 되돌림으로 #633의 일지를 더는 가리키지 않는다. 이 일지는 질문과 답을 원문으로 싣고, 머리에 그 절이 #633의 다음 커밋에 실린다고 적었다.
- 표준 2: 이 일지에 "다음" 절이 없었다. 회고와 함께 더했다.
- 표준 3, 근거의 종류: 프로브 README 행에 취소의 근거(실행 주석의 시간 제한 문구, 손으로 봤다)를 적었다. 시간 제한인지 새 푸시의 취소인지 길이로는 가를 수 없다는 지적은, 실행 주석의 표지로 세 실행(45390683089, 45388134923, 45396000251의 첫 시도)부터 확인해 가렸다.
- 표준 4: README 행의 두 번째 "이 티켓의 범위 밖"에 티켓 이름을 적었다.
- 표준 5: `python` 잡 주석의 프로브를 전체 경로로 적었다.
- 리뷰 밖에서 고친 것: `python` 잡 주석이 "네 배면 60분인데, 멈춘 잡을 늦게 끊는 대가를 보고 사용자가 25분을 골랐다"고 적어, 60분이 선택지에 있었던 것처럼 읽혔다. 선택 화면에 올린 값이 25분이었다고 고쳤다.

남긴 것:

- 명세 (c)4: dev의 승인 줄은 #632의 4회차를 "두 시도 연속"으로 적는데, 실행 45380651521에는 셋째 시도도 시간 제한으로 취소돼 있다. #632 세션이 적은 기록 문장이라 고치지 않았다.
- 표준 6, 회차 셈: 같은 PR(#633)의 실행 45396000251은 4회차와 같은 사건으로 보고, dev 푸시의 취소는 회차가 아니라 손상으로 상태 줄에 적었다.
- 표준의 냄새(같은 수치가 주석, README 행, 티켓, 일지에 되풀이된다): 근거, 측정 기록, 요약으로 역할이 달라 그대로 뒀다.

## 커밋

- ruff 둘은 따로 쳤다. `uv run ruff check .`는 "All checks passed!", `uv run ruff format --check .`는 "2557 files already formatted"였다.
- 첫 커밋은 pre-commit의 pytest에서 막혔다(1 failed, 8135 passed, 936.94초). 빨간 것은 `tests/tools/test_rerun_runner.py::test_같은_갈래가_두_번_든_파일럿의_두_회차가_함께_돌아도_번호가_다르다`로, 두 회차가 함께 돈 수의 최대를 2로 기대했는데 1이었다. 이 변경은 `tools/`를 건드리지 않았고, 그 파일만 따로 돌리면 63 passed(159.99초)였다. 다른 세션과 함께 돌아 pytest가 936초, web-verify가 1184초 걸린 부하 아래의 시간 시험이라, 대기열 0306이 받아들여 닫은 종류의 새 사례로 보고 일지에만 적는다. 커밋을 다시 쳤다.

## 회고

이 브랜치는 admin-login 명세 세션의 회고 11이 넘긴 반영 길이고, 그 세션의 회고는 #633의 일지 `## 회고` 절에 있다. 이 브랜치에서 새로 본 후보는 셋이고 셋 모두 기각이다.

- 같은 대기열 항목을 #632와 이 브랜치가 함께 고쳤다. 기각: #633의 커밋 전 `sibling_overlap.py`가 그 파일을 `widget-admin-server-spec` 워크트리와 함께 고친 파일로 이미 알렸다(일지 `2026-11-24-1644-admin-login-spec.md`). 이미 있는 검사가 그 자리에서 알린 것이다.
- 질문 때의 셈("여섯 번 가운데 하나")을 셈한 시각 없이 일지에 옮겨 적어 낡았다. 기각: 닫힌 주장을 반례로 미는 것은 셀프 리뷰 두 브리프의 주장 검증 1이고, 명세 축이 그 자리에서 잡았다. 리뷰가 제 몫을 한 것이다.
- 티켓이 취소된 단계를 "다음 검사 단계"로 뭉뚱그렸다. 기각: 같은 까닭으로 명세 축이 잡았다.

만료할 항목은 `uv run python tools/queue_open_rows.py`의 "만료할 항목"이 (없음)이었다. 새 훅을 반영하거나 다섯째 회차로 올린 것이 없어 `tools/hook_report.py`는 돌리지 않았다.

## 다음

이 PR을 병합한 뒤 `docs/admin-login`으로 돌아가 PR #633을 잇는다. 할 일은 다섯이다.

1. 커밋하지 않은 일지 절을 되살린다.
2. `origin/dev`를 합친다. 대기열 `ci-python-job-timeout-margin`의 승인 줄 충돌은 dev 쪽 줄에 #633의 사건을 5회차로 더해 푼다.
3. 그 일지의 회고 11에 적힌 "4회차"를 5회차로 고친다.
4. 푸시하고 CI가 25분 제한 안에 끝나는지 본다.
5. 남은 봇 회차와 병합까지 간다.
