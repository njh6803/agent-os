## tidy-checkouts

첫 턴에 제목을 브랜치 이름으로 바꾸고(앱이 지은 제목 "Portal-admin 위젯 관리 화면 설계"였고 묻지 않고 바뀌었다) `tidy-checkouts`를 돌았다. 아래는 명령의 출력을 읽은 것이다.

- 주 체크아웃은 dev였고 깨끗했으며(`git status --porcelain`이 빈 출력) 원격에 없는 커밋이 없어(`git rev-list --count origin/dev..HEAD`가 0) `git merge --ff-only --no-overwrite-ignore origin/dev`로 `be22f3ff5`에서 `d80690da1`로 당겼다. 당긴 커밋은 `.claude/skills/tidy-checkouts/`를 바꾸지 않았다(`git diff --name-only`가 빈 출력).
- `judge`가 `지운다`로 낸 워크트리 넷과 브랜치 하나를 하나씩 쳤다. 지운 것은 워크트리 `portal-admin-design`과 `widget-login-state-screens`(각각의 브랜치와 함께), 브랜치 `worktree-widget-login-state-spec`이다. `05-notes-check-guards-release-note-fragments`는 다른 프로세스가 폴더를 쥐고 있어(이름 바꾸기가 `WinError 32`로 막혔다) 남았고, `widget-login-state-spec`은 도구가 "등록된 워크트리가 아니다"를 내어 남았다.
- `empty-trash`가 휴지통의 `node_modules` 일곱을 비우지 못했다. 모두 `esbuild.exe`에서 `WinError 5`였고 도구가 든 쥔 프로세스는 `node.exe`(pid 23788)와 `esbuild.exe` 둘(pid 17988, 27940)이다. 다음 `judge`가 다시 본다.
- 나머지 워크트리는 판정대로 남겼다. 까닭은 바뀐 파일, 병합된 PR 없음, 쥔 프로세스, 다시 만들 수 없는 무시된 항목, 앱의 표지였다.

그 뒤 `EnterWorktree`(name `portal-admin-screens`)로 들어와 `git switch -c docs/portal-admin-screens`로 이 브랜치를 땄다. HEAD는 `d80690da1`(PR 580의 병합)이다.

## 사용자에게 물은 것

이 일지는 선택 화면의 답을 `> 사용자: "<고른 라벨>" — 설명: <그 선택지의 설명>`으로 적는다. 따옴표 안의 라벨만 사람이 고른 것이고, 설명은 세션이 쓴 선택지의 글을 글자 그대로 옮긴 것이다. 화면은 훅(`hook_choice_facts`)이 한 번 막았고, 만료 알림의 후보 셋이 ADR 0061이 아니라 위젯 화면 작업이 그린 것이라는 대목과 widget-appearance 행의 범위를 `.scratch/widget-login-state/design/README.md` 15행과 `.scratch/widget-appearance/plan.md` 머리로 대 본 뒤 고쳐 다시 올렸다.

> 질문: 위젯 화면 작업에서 '사이트마다 고르게 하자'고 정하신 위젯 모양 두 가지가 있습니다. ① 로그인이 필요한 사이트에서 로그인하기 전의 모양(대화 안의 카드 / 입력창 자리를 단추로 / 첫 화면 안내 안의 단추)과 ② 고지 전문을 보이는 법(고지 줄 안에서 펼침 / 위젯을 덮는 상자 / 대화 안의 카드)입니다. 이 둘을 0.1 판의 위젯 관리 화면에서 사이트마다 고르게 할까요?
>
> 사용자: "둘 다 0.1 판에 넣기 (추천)" — 설명: 위젯 관리 화면의 사이트 설정에 고르는 칸이 둘 늘고, 위젯은 두 가지 모두 세 모양을 짓습니다. 만료 알림의 모양은 이미 0.1 판의 고르는 값이고(ADR 0061) 위젯 화면 작업이 그 후보를 셋으로 그렸으므로, 화면 모양을 고르는 칸 셋을 같은 판에 한꺼번에 짓고 같은 위젯 부품을 나중에 다시 열지 않습니다. 대가는 0.1 판 전에 위젯이 짓고 시험(단위 시험, e2e, 사진 비교)할 모양이 넷(두 칸마다 기본 밖의 두 모양) 는다는 것과, ADR 0064에 이력을 더해 다시 승인받아야 한다는 것입니다.

고르지 않은 안은 "0.1 판 뒤로 미루기"다. 설명: "0.1 판의 위젯은 두 가지 모두 기본 모양(대화 안의 카드, 고지 줄 안에서 펼침) 하나로 그리고, 위젯 관리 화면에도 그 칸이 없습니다. 고르는 칸과 나머지 모양은 0.1 판 뒤의 widget-appearance 행(그림 올리기, 자유 색 같은 새 모양 값을 맡은 행)으로 옮깁니다. 대가는 0.1 판에서 운영자가 그 두 모양을 바꾸지 못하고, 그 행에서 같은 위젯 부품을 다시 열어야 한다는 것입니다. 나중에 칸을 더해도 이미 등록한 설정은 기본 모양 그대로 남을 것으로 봅니다(어림, 재 보지 않았습니다)." 이 답으로 ADR 0064 결정 "0.1 판에서 등록하는 것"에 고르는 값 둘이 는다. ADR의 개정이라 이력 초안을 셀프 리뷰 뒤에 보이고 승인받는다.

> 질문: 위젯 관리 화면(사이트 목록, 사이트 하나의 설정, '테스트' 메뉴, 로그인 전 화면)의 겉모습을 무엇에 맞춰 그릴까요? 참고할 디자인(제품 이름, 주소, 화면 갈무리)이 있으시면 'Other'에 적어 주세요.
>
> 사용자: "관리 화면 + 위젯 설정 사례 조사 (추천)" — 설명: 이미 확정한 Agent OS 관리 화면(왼쪽 탐색, 표, 설정 화면)을 기준으로 삼아, 같은 운영자가 두 화면을 같은 결로 느끼게 합니다. 관리 화면에 없는 부분(사이트마다의 긴 설정 양식)만 채널톡·Intercom·Crisp 같은 상담 위젯 제품의 설정 화면을 웹에서 3~5개 찾아 규칙을 뽑고, 그 규칙을 보여 드린 뒤 방향을 한 번 더 고르시게 합니다. 대가는 그리기 전에 조사와 질문이 한 차례 더 든다는 것입니다.

고르지 않은 안은 "관리 화면에만 맞추기"다. 설명: "웹 조사 없이 Agent OS 관리 화면의 틀과 부품만으로 바로 그립니다. 빠르지만, 긴 설정 양식의 묶음과 차례는 이 세션이 정한 안으로만 보시게 됩니다."

## 조사: 위젯 설정 화면 사례

세션이 맡긴 서브에이전트가 2026-11-16에 다섯 제품(채널톡, Intercom, Crisp, Zendesk messaging Web Widget, Chatbase)의 공개 문서를 읽었다. 본문을 내려받아 그 문장이 있는 것을 본 것만 근거로 들었고, 화면 사진은 보지 않았다. 채널톡은 한국어 원문, 나머지는 영어 원문이다. 글에 든 수치는 그 문서의 값이고 잰 값이 아니다. 보고에서 뽑은 규칙은 아래다.

1. 묶음 차례는 글 → 모양 → 동작 → 로그인·보안 → 설치가 흔하다(Zendesk의 Basics → Style → … → Authentication → Installation, Intercom의 Content → Appearance … → Install → Security, Chatbase 독립 페이지의 General → Content → … → Colors → Buttons).
2. 양식은 한 페이지에 묶음 제목을 달아 늘어놓는다(Zendesk의 펼치는 섹션, 채널톡의 왼쪽 탐색과 페이지 안 탭). 탭은 데스크톱·모바일 웹, Overview·Display처럼 큰 갈래를 가를 때만 쓴다(채널톡, Chatbase의 탭 넷).
3. 저장은 명시적인 단추가 다수다(Zendesk의 Save settings, Intercom의 "Save and set live"). 자동 저장은 Crisp의 모양 설정뿐이고 같은 제품의 도메인 설정은 직접 저장한다.
4. 저장하지 않은 바뀜의 표시는 Chatbase만 문서에 있다(반영 단추에 점과 남은 바뀜의 수). 떠날 때 묻는지는 다섯 문서 모두 말하지 않는다.
5. 저장 전 미리보기는 셋이 둔다(Intercom은 설정 오른쪽, Crisp는 실제 챗박스에 바로, Chatbase는 Playground). Zendesk와 채널톡의 설정 문서에는 언급이 없다.
6. 시험하는 길은 둘이다. 관리 화면 안의 시험 위젯(Zendesk의 "Test AI agent", Chatbase Playground)과 새 탭의 공개 페이지(Chatbase Preview, Intercom이 설치된 페이지를 새 창으로, Crisp 직접 링크, 채널톡 고객용 링크)다.
7. 입력 형식 규칙은 칸 설명에 적지만(Chatbase는 http(s)로 시작하는 전체 주소, Intercom은 localhost를 받지 않고 끝 슬래시를 뺀다), 오류를 언제 어디에 보이는지는 다섯 문서 모두 말하지 않는다.
8. 밝기는 라이트·다크·시스템 셋이 흔하다(Intercom, 채널톡). Chatbase 독립 페이지는 "테마 전환 켜고 끄기"와 "기본 테마"를 따로 두어, 처음 밝기와 밝기 스위치 숨기기의 짝과 같다. 부품 이름을 밝힌 것은 Zendesk의 라디오(런처 위치), 슬라이더(모서리), 색 칸(hex 입력과 색 견본)뿐이다.

## 방향

조사의 규칙을 보인 뒤 선택 화면 하나에 질문 셋을 올렸다. 화면은 훅(`hook_choice_facts`)이 한 번 막았다. 예시 수 "바뀐 칸 3개"가 예시라는 것을 밝히고, ADR 0064 결정 "'테스트' 메뉴와 공개 주소"의 문장(저장하기 전의 설정을 운영자만 미리 볼 수는 없다)을 그 ADR 25행으로, 앱 사이의 import를 막는 규칙을 `web/eslint.config.mjs`의 정책("앱 사이에서 import 하지 않는다. 함께 쓸 것은 packages/ 로 옮긴다")으로 대 본 뒤, 저장 전 그림을 짓는 데 드는 일을 어림이라고 적어 다시 올렸다.

> 질문: 위젯 관리 화면에서 사이트 하나를 고치는 화면(위젯 설정과 위젯 미리보기 페이지 설정이 든 긴 양식)을 어떤 짜임으로 그릴까요? 조사한 다섯 제품 가운데 Zendesk·Intercom·채널톡은 한 페이지에 묶음 제목을 달아 늘어놓았고, 탭은 큰 갈래를 가를 때만 썼습니다.
>
> 사용자(Other): "한 페이지와 저장 단추 하나 (추천)이랑 탭으로 나누고 저장 하나 둘 다 보여줘"

선택지의 설명은 이렇다. "한 페이지와 저장 단추 하나 (추천)": "기본, 글, 모양, 로그인과 로그아웃, 고지, URL 방식 창, 위젯 미리보기 페이지의 묶음을 한 페이지에 차례로 늘어놓습니다. 화면 아래에 붙은 띠에 바뀐 칸의 수(예: '바뀐 칸 3개')와 '되돌리기', '저장'을 둡니다(Chatbase가 반영 단추에 남은 바뀜의 수를 띄웁니다). 띠의 글로 저장하면 다음에 위젯을 여는 사람부터 바뀐다는 것을 알립니다(Intercom 단추 이름 'Save and set live'와 같은 뜻). 목차를 어떻게 둘지(목차 없음, 왼쪽 목차, 묶음 제목을 왼쪽에 둔 두 열)는 세 안으로 그려 고르시게 합니다. 대가는 페이지가 길어 아래 묶음까지 스크롤해야 한다는 것입니다." "탭으로 나누고 저장 하나": "묶음마다 탭을 두고 저장 단추는 화면에 하나입니다(Chatbase가 설정을 탭 넷으로 나눕니다). 한 번에 보이는 칸이 적어 덜 복잡하지만, 다른 탭에서 바꾼 칸은 지금 탭에서 보이지 않아 무엇을 바꿨는지 놓치기 쉽습니다." 고르지 않은 안은 "묶음마다 저장"이다. 설명: "묶음마다 카드를 두고 카드마다 '저장' 단추를 둡니다(Zendesk 도움말이 설정을 바꾸는 절차마다 'Save settings'를 누르게 적습니다). 한 묶음만 고치고 바로 저장하기 쉽지만, 위의 묶음 일곱마다 저장 단추가 서고 여러 묶음을 고치면 여러 번 눌러야 합니다."

> 질문: 위젯 설정에서 화면 모양을 고르는 칸 셋(로그인 모드 사이트의 로그인 전 모양, 고지 전문을 보이는 법, 만료 알림의 모양)은 칸마다 세 모양 가운데 하나를 고릅니다. 예를 들어 로그인 전 모양은 '대화 안의 카드', '입력창 자리를 단추로', '첫 화면 안내 안의 단추'입니다. 이 칸을 어떻게 보일까요?
>
> 사용자: "작은 그림이 든 고르기 (추천)" — 설명: 모양마다 위젯 상자를 줄인 회색 도식 그림(카드가 대화 안에 서는지, 덮개가 상자를 덮는지)과 이름, 한 줄 설명을 담은 고르기 칸 셋을 나란히 둡니다. 이름만으로는 '입력창 자리를 단추로' 같은 모양을 떠올리기 어려워서입니다. 대가는 위젯의 그 모양이 바뀌면 그림도 함께 고쳐야 한다는 것입니다. 조사한 문서에서는 화면 모양을 그림으로 고르는 예를 찾지 못했습니다.

고르지 않은 안은 "글로만 된 고르기"다. 설명: "모양마다 라디오 단추와 이름, 한 줄 설명만 둡니다(Zendesk가 런처 위치를 라디오로 고릅니다). 고칠 그림이 없지만, 고른 모양이 실제로 어떻게 보이는지는 저장한 뒤 '테스트'에서 위젯을 열어 봐야 압니다."

> 질문: 사이트 하나의 화면에서 양식 옆에 '저장하기 전의 위젯 그림'을 둘까요? 조사한 다섯 가운데 Intercom·Crisp·Chatbase는 설정 화면에서 저장 전 모양을 보여 줍니다. ADR 0064는 '테스트' 메뉴가 공개된 위젯 미리보기 페이지로 가므로 저장 전 설정을 운영자만 미리 볼 수는 없다고 적었습니다.
>
> 사용자(Other): "양식 옆에 저장 전 위젯 그림 두기로 하고 이걸 미리보기 페이지로 하자. 테스트는 말 그대로 테스트 해보는 곳으로.
> 공개된 미리보기 페이지는 없고. 공개 계정을 하나 주는건 어때"

선택지의 설명은 이렇다. "두지 않고 저장 뒤 '테스트'로 보기 (추천)": "사이트 화면 머리에 '테스트에서 열기'를 두어, 저장한 뒤 위젯 미리보기 페이지의 그 사이트를 새 탭에 엽니다(그 페이지는 주소의 ?site=이름으로 사이트를 골라 연다. Chatbase Preview·Intercom처럼 새 탭). ADR을 고치지 않습니다. 대가는 고친 값을 보려면 먼저 저장해야 하고, 저장하면 다음에 위젯을 여는 그 사이트의 최종 사용자도 바뀐 값을 본다는 것입니다." "양식 옆에 저장 전 위젯 그림 두기": "양식 오른쪽에 지금 고친 값으로 그린 위젯을 둡니다. 저장하기 전에 볼 수 있지만, 린트 규칙이 앱 사이의 import를 막아(web/eslint.config.mjs) 위젯 관리 화면은 위젯 앱의 부품을 가져다 쓸 수 없습니다. 그래서 위젯 부품을 공유 패키지로 옮기거나 위젯이 저장 전 값을 받는 길을 새로 지어야 하고(얼마나 드는지는 어림이고 재 보지 않았습니다), ADR 0064의 그 문장이 바뀌므로 이력을 더해 다시 승인받아야 합니다."

셋째 답은 저장 전 그림을 고른 데서 더 나아가 위젯 미리보기 페이지의 성격을 바꾸는 제안이다. 양식 옆의 저장 전 그림을 "미리보기"로 부르고, "테스트"는 실제로 시험해 보는 곳으로 두며, 공개된 위젯 미리보기 페이지는 없애고 공개 계정을 하나 주자는 것이다. ADR 0064 결정 "'테스트' 메뉴와 공개 주소"에서 사용자가 고른 "공개 주소도 남기기"를 되돌리는 쪽이고, 그 결정이 근거로 든 두 계획(공개 데모, 사내 로그인)과 ADR 0050·0059에도 닿는다. 그래서 그리기 전에 무엇이 바뀌는지 풀어 보이고 뜻을 다시 물었다(아래 "위젯 미리보기 페이지를 다시 묻기").

## 위젯 미리보기 페이지를 다시 묻기

묻기 전에 대화에 풀어 보인 것: 지금 위젯 미리보기 페이지가 맡은 일은 셋이다. 공개 데모(PRD 44행 "2027-01-08까지 공개 주소에서 누구나 로그인 없이 공개 정부 문서에 대해 묻고", pilot-portal이 2026-11-10에 지어 끝냈고 0.1 판의 조건이 아니다), 기준선의 사내 질문 자리(portal-login "배포 환경에서는 사내 사람만 질문하게 한다", ADR 0064 Consequences "순서"의 0.1 판까지의 길에 있다), 운영자의 시험 자리(ADR 0064의 "테스트" 메뉴)다. 저장 전 그림을 "미리보기"로 부르면 용어집의 위젯 미리보기 페이지와 이름이 겹친다. 공개 계정이 Agent OS 운영자 계정이면 0.1 판의 단계가 시스템 관리자와 관리자 둘뿐이고 관리자는 계정 관리만 빼고 모든 일을 하므로(ADR 0062) 권하지 않는다고 적었다. 선택 화면은 훅(`hook_choice_facts`)이 한 번 막았고, PRD 44행, ADR 0064 23행(그 페이지의 서버가 사이트 토큰을 낸다), pilot-portal 기능 계획 머리(로그인 없이 온 사람에게 사이트 토큰을 낸다)로 대 본 뒤 질문과 라벨을 그대로 두고 다시 올렸다.

> 질문: 운영자가 저장한 위젯 설정으로 실제 질문을 해 보는 '테스트'와, 지금의 위젯 미리보기 페이지가 맡은 나머지 두 일(로그인 없이 누구나 묻는 공개 데모, 직원이 회사 로그인으로 들어와 묻는 사내 질문 자리)을 어떻게 나눌까요?
>
> 사용자(Other): "로그인 없이 쓰는 페이지를 없애고 공개 계정을 줄껀데. 실제 운영할 서버랑 공개용 서버랑 따로 올릴꺼야. 그래서 공개 계정으로 전부 사용해 볼 수 있게."

답의 머리는 둘째 선택지 "로그인 없이 쓰는 페이지를 없애고 공개 계정을 줌"의 라벨이다. 그 설명은 "로그인 없이 누구나 묻는 자리를 없앱니다. 공개 데모를 보러 온 사람에게는 공개한 계정 하나(질문만 하고 설정은 못 고친다)를 주고, 그 계정으로 로그인해 묻게 합니다. PRD 44행의 '누구나 로그인 없이'를 고쳐야 하고, 그 계정을 드는 자리(새 계정 종류나 로그인 서버)를 새로 정해야 합니다. 2026-11-10에 끝난 pilot-portal이 지은 익명 모드(로그인 없이 온 사람에게 사이트 토큰을 낸다)도 바뀝니다."였다. 사용자는 그 설명의 "질문만 하고 설정은 못 고친다"와 달리 공개 계정으로 "전부 사용해 볼 수 있게" 하고, 실제 운영할 서버와 공개용 서버를 따로 올린다고 덧붙였다. 고르지 않은 안은 "테스트는 운영자만, 공개 페이지는 따로 남김 (추천)"(설명: "위젯 관리 화면의 '테스트'는 운영자 계정으로 들어온 사람만 쓰는 시험 자리가 됩니다. 지금 페이지는 이름을 바꿔(예: '질문 페이지') 공개 데모와 사내 질문 자리로만 남기고, 공개 계정은 두지 않습니다. PRD 44행의 공개 데모 문장과 portal-login 행은 그대로입니다. 대가는 운영자용 시험 자리를 새로 지어야 하는 것입니다. 지금은 그 페이지의 서버가 사이트 토큰을 내므로(ADR 0064), 시험 자리가 토큰을 어디서 받을지 정해야 합니다. 얼마나 드는지는 어림이고 재 보지 않았습니다.")와 "테스트는 지금 페이지 그대로, 저장 전 그림만 더함"(설명: "양식 옆의 저장 전 그림('미리보기')만 더하고, '테스트' 메뉴는 ADR 0064 결정대로 지금의 공개 페이지를 새 탭으로 엽니다. 그 페이지의 이름만 '미리보기'와 겹치지 않게 바꿉니다. 바뀌는 것이 가장 적지만, 운영자의 시험과 최종 사용자의 질문이 같은 페이지에서 일어납니다.")다.

> 질문: 이 결정은 ADR 0064(그리고 고르는 안에 따라 ADR 0050·0059와 PRD)를 고칩니다. 어디서 정할까요?
>
> 사용자: "이 세션에서 정하고 그리기 (추천)" — 설명: 위 답으로 이 세션이 ADR 0064의 이력 초안을 씁니다. 고른 안이 PRD나 다른 ADR의 문장을 바꾸면 그 고침과 표시도 함께 씁니다. 셀프 리뷰 뒤 보여 드리고 승인받습니다. 그리는 일은 그사이에 이어 가고, '테스트' 화면도 이번 그림에 넣습니다. 대가는 이 세션의 PR이 화면과 ADR 개정을 함께 담아 커진다는 것입니다.

고르지 않은 안은 "설계 인터뷰를 따로 하기"다. 설명: "이 세션은 정해진 것(양식 두 짜임, 작은 그림 고르기, 저장 전 그림)으로 그리고, '테스트'와 공개 페이지, 공개 계정은 새 세션의 설계 인터뷰(grill-with-docs)가 라운드를 돌며 정합니다. '테스트' 화면은 그 뒤에 그립니다. 대가는 이번 그림에 '테스트'가 빠지고 화면 작업을 한 번 더 열어야 한다는 것입니다."

여기까지 정해진 것: 양식 옆에 저장 전 위젯 그림을 두고 그것을 "미리보기"라 부른다. "테스트"는 저장한 설정으로 실제로 시험해 보는 곳이다. 로그인 없이 쓰는 페이지는 없앤다. 공개 데모는 실제 운영할 서버와 따로 올리는 공개용 서버에서, 공개한 계정 하나로 제품 전부를 써 보게 한다.

## 후속 질문 둘

공개용 서버와 공개 계정이 남긴 물음 둘을 선택 화면 하나에 올렸다. 화면은 훅(`hook_choice_facts`)이 한 번 막았다. PRD 45행의 기준선 문장("안내 문서만 보고 1시간 안에 배포")과 ADR 0062의 두 결정(관리자는 계정 관리만 빼고 모든 일을 한다, 자기 비밀번호를 바꾸면 그 계정의 다른 로그인이 모두 끊긴다)을 읽어 맞는 것을 보고, "ADR 0062에 이력을 더합니다"가 제안이라는 것을 확인한 뒤 질문과 라벨을 그대로 두고 다시 올렸다.

> 질문: 실제 운영할 서버에서 직원이 회사 로그인으로 들어와 질문하는 자리(portal-login 행이 지을 것. 지금은 위젯 미리보기 페이지에 둔다)는 어떻게 할까요? 로그인 없이 쓰는 페이지는 없애기로 했고, 그 페이지는 운영자가 실제로 시험하는 '테스트' 자리가 됩니다.
>
> 사용자: "테스트 페이지에 회사 로그인 문도 둠 (추천)" — 설명: 테스트 페이지는 로그인해야 열립니다. 운영자는 운영자 계정으로 들어와 그 페이지의 모든 사이트를 시험하고, 직원은 회사 로그인으로 들어와 로그인 모드 사이트에서 질문합니다. portal-login 행은 그대로 갑니다. 대가는 '테스트'라 부르는 페이지가 직원의 질문 자리이기도 하고, 그 페이지의 서버가 운영자 로그인을 확인하는 길을 새로 지어야 한다는 것입니다(얼마나 드는지는 어림이고 재 보지 않았습니다).

고르지 않은 안은 "직원 질문 자리는 없앰"이다. 설명: "테스트 페이지는 운영자 계정으로만 들어오고, 직원은 조직이 자기 사내 사이트에 붙인 위젯으로 묻습니다. portal-login 행을 접거나 다시 씁니다. 대가는 위젯을 붙일 사내 사이트가 없는 조직은 질문할 자리가 없다는 것과, PRD 45행의 기준선('안내 문서만 보고 1시간 안에 배포')에 조직이 자기 사이트에서 토큰을 서명하는 일이 더해진다는 것입니다."

> 질문: 공개용 서버의 공개 계정은 모르는 여러 사람이 함께 씁니다. 관리자 단계로 두면 계정 관리는 못 하지만, 플러그인을 끄거나 위젯 설정을 바꾸거나 자기 비밀번호를 바꿀 수 있고, 비밀번호를 바꾸면 다른 사람의 로그인이 모두 끊깁니다(ADR 0062). 이것을 어떻게 막을까요?
>
> 사용자: "따로 막지 않음" — 설명: 지금 관리자 단계 그대로 둡니다. 누가 비밀번호를 바꾸면 다른 방문자는 로그인하지 못하고, 시스템 관리자가 비밀번호 링크를 만들어 계정을 되찾습니다. 바꿀 것이 없지만 데모가 자주 막힐 수 있습니다.

고르지 않은 안은 둘이다. "비밀번호는 못 바꾸게, 정해진 때 처음 상태로 (추천)": "공개 계정은 관리자 단계이고, 자기 비밀번호를 바꾸지 못하는 표시를 새로 답니다(지금 그런 표시가 없어 ADR 0062에 이력을 더합니다). 공개용 서버는 데이터베이스(위젯 설정, 플러그인의 켜고 끔, 대화 기록)를 정해진 때 처음 상태로 되돌리는 배포 설정을 둡니다. 주기(예: 하루 한 번)는 명세가 정합니다. 대가는 고칠 문서와 지을 것이 늘고, 방문자가 바꾼 설정과 남긴 대화가 그때 사라진다는 것입니다." "비밀번호만 못 바꾸게": "공개 계정에 비밀번호를 바꾸지 못하는 표시만 답니다(ADR 0062에 이력을 더합니다). 누가 플러그인을 끄거나 위젯 설정을 바꾸면 다음 방문자도 그 상태를 보고, 운영자가 알아채면 손으로 되돌립니다."

여기까지 정해진 것(앞 절에 더해): "테스트" 페이지는 로그인해야 열리고, 운영자 계정과 회사 로그인 둘로 들어온다. 운영자는 모든 사이트를 시험하고 직원은 로그인 모드 사이트에서 질문한다. portal-login 행은 그대로 간다. 공개 계정은 지금의 관리자 단계 그대로 두고 따로 막지 않는다. 그래서 ADR 0062는 고치지 않는다.

## ADR 0065 초안과 문서 고침(승인 전, 커밋 전)

`.claude/rules/adr.md`대로 Skill 도구로 `domain-modeling`을 불렀다. 결정을 둘로 나눴다. 고르는 값 둘은 ADR 0064 Consequences "화면"이 "넣으면 이 ADR의 이력에 쌓는다"고 적었으므로 ADR 0064 이력 2026-11-16 "위젯 설정에 로그인 전 모양과 고지 전문을 보이는 법을 고르는 값으로 더한다"로 썼다. 미리보기, 위젯 테스트 페이지, 공개 데모는 ADR 0050·0059·0064와 PRD 44행을 함께 바꾸는 새 결정이라 새 ADR 0065(`status: proposed`)로 썼다. `uv run python tools/sibling_overlap.py`는 이 변경 전에 "번호 겹침 없음"을 냈다(0065를 쓰기 전이라 그 번호는 아직 대 보지 않았다).

고친 파일(모두 커밋 전): `docs/adr/0065-…md`(새 파일), ADR 0064(결정 "0.1 판에서 등록하는 것"과 "'테스트' 메뉴와 공개 주소"에 포인터, 끝에 `## 이력`), ADR 0050(요약의 익명 식별자 문장과 결정 "경로"의 토큰 끝점 문장에 `(바뀜: ADR 0065)`), ADR 0059(결정 "화면"의 둘 다 사이트 문장에 포인터), `docs/adr/README.md`(0065 행), `CONTEXT.md`("위젯 미리보기 페이지"를 모두 "위젯 테스트 페이지"로 바꾸고 정의를 고쳤다. 초안을 쓰며 대 본 사실: `openapi.json`의 경로는 열셋이고 관리 쪽 쓰기는 `PUT /plugins/{kind}/{name}/enabled` 하나다(업로드는 슬라이스 12의 claude-code-compat). 트레이스는 `GET /traces`로 모두 읽는다. ADR 0046 이력 2026-11-06의 "공개 데모의 비용"이 시간당 비용의 최댓값을 사이트별 시간당 실행 수 상한으로 묶고, "공개 인터넷에 먼저 선다"가 도구를 읽기 전용 검색 하나만 연다고 적는다. public-demo의 기능 계획은 익명 모드로 누구나 묻고 관리 화면을 밖에 내놓지 않는다고 적고, 그 행에는 아직 설계 줄이 없다. 그래서 사용자가 "따로 막지 않음"을 고를 때 본 대가(비밀번호, 플러그인, 위젯 설정)에 없던 셋(상한 없는 운영자 쪽 실행, 켜지는 플러그인, 트레이스에서 보이는 남의 질문)을 ADR 0065 Consequences "공개 데모의 비용과 도구"에 적었고, 승인 화면에서 보인다.

## 승인

리뷰를 반영한 뒤 ADR 0065와 ADR 0064 이력의 요지를 대화에 풀어 보이고, 선택 화면 하나에 질문 셋을 올렸다. 화면은 훅(`hook_choice_facts`)이 두 번 막았다. 첫 번째에 잠금의 수를 ADR 0062 결정 "잠금과 실패 문구"의 원문에 대 보니 "다섯 번 틀려 최대 1시간 잠근다"가 틀린 줄임이었다(다섯 번이면 1분이고 그 뒤 두 배씩 최대 1시간이다). 그래서 ADR 0065 결정 "공개 데모"의 첫째 대가와 위 "셀프 리뷰"의 밀 주장 줄을 고치고 질문 문장도 고쳤다. 고친 질문 문장이 새 화면으로 잡혀 두 번째로 막혔고, 화면의 나머지 수(ADR 0063 13행의 "최종 사용자 경로의 상한은 운영자 쪽 실행에 걸지 않는다", public-demo 기능 계획의 기한 2027-01-08과 설계 줄이 없다는 것, 기능 계획 셋의 이름)를 Grep 도구로 대 본 뒤 그대로 다시 올렸다.

> 질문: 지금의 '위젯 미리보기 페이지'를 로그인해야 여는 시험 자리로 바꾸며, 문서와 용어집에서 부를 이름을 무엇으로 할까요? 위젯 관리 화면의 메뉴 글자는 어느 쪽이든 '테스트'이고 달라지는 것은 문서 속 이름뿐입니다.
>
> 사용자: "위젯 테스트 페이지 (추천)" — 설명: 문서에 '테스트 페이지'라고만 쓰면 이 저장소의 자동 시험(테스트)과 섞여서, 앞에 '위젯'을 붙입니다. 초안, 용어집(CONTEXT.md), 기능 계획 셋이 이미 이 이름이라 이 브랜치에서 더 고칠 것이 없습니다. 용어집 밖의 다른 문서는 어느 쪽이든 따로 하는 이름 바꾸기 작업이 고칩니다.

고르지 않은 안은 "테스트 페이지"다. 설명: "더 짧습니다. 대신 문서에서 자동 시험을 뜻하는 '테스트'와 섞일 수 있고, 초안과 용어집과 기능 계획 셋의 이름을 다시 바꿉니다."

> 질문: 공개 계정(공개용 서버에서 이름과 비밀번호를 공개한 운영자 계정)을 따로 막지 않으면, 고르실 때 질문에 없던 대가가 다섯 생깁니다. ① 누구나 틀린 비밀번호를 거듭 넣어 계정을 잠글 수 있고(다섯 번이면 1분, 그 뒤 틀릴 때마다 두 배씩 최대 1시간), 잠긴 동안 아무도 못 들어옵니다. ② 실행 기록에서 다른 방문자의 질문과 답을 모두 봅니다. ③ 관리 화면 대화로 '사이트별 시간당 실행 수 상한'이 걸리지 않는 실행을 일으키고, 그 실행이 묻는 승인도 스스로 내립니다. ④ 꺼 둔 플러그인을 켜고, 그 도구를 스스로 승인해 쓸 수 있습니다(문서를 읽고 이은 어림입니다). ⑤ 사이트의 발급자를 틀리게 바꿔 그 사이트를 닫습니다. 이 가운데 ③·④와 '관리 화면을 밖에 연다'는 것 자체가 공개 데모의 지금 약속 셋(시간당 비용의 최댓값, 도구는 읽기 전용 검색 하나, 관리 화면을 내놓지 않음)과 부딪칩니다. 어디서 정할까요?
>
> 사용자: "public-demo 인터뷰에 넘김 (추천)" — 설명: ADR 0065는 다섯 대가와 부딪치는 약속을 적어만 둡니다. 막는 법(운영자 쪽 실행에도 상한 두기, 공개용 서버의 모델 API에 지출 한도 걸기, 켤 수 있는 플러그인 정하기, 고지 문구)은 public-demo 행의 설계 인터뷰가 그 행의 기한(2027-01-08)과 함께 정합니다. 그 행의 기능 계획에는 아직 설계 줄이 없습니다. 대가는 그 인터뷰 전까지 이 위험이 문서에만 남는다는 것입니다.

고르지 않은 안은 "지금 이 세션에서 정함"이다. 설명: "이 세션에서 질문을 한 차례 더 드리고, 막는 법을 ADR 0065에 넣은 뒤 다시 승인받습니다. 대가는 화면 그리기가 그만큼 늦어지고, public-demo의 다른 물음(기한, 비용 셈)과 따로 정하게 된다는 것입니다."

> 질문: ADR 0065 초안(위젯 미리보기 페이지를 로그인해야 여는 '위젯 테스트 페이지'로 바꾸고, 공개 데모를 공개 계정을 둔 따로 띄운 서버로 옮기며, 위젯 관리 화면의 양식 옆에 저장 전 위젯 '미리보기'를 두는 결정)과 ADR 0064 이력(위젯 설정에 '로그인 전 모양'과 '고지 전문을 보이는 법' 칸 둘을 더함)을 확정할까요? 초안이 답 밖에서 정한 것도 함께 확정됩니다. 새 ADR로 쓴 것, 미리보기를 공유 부품으로 그리는 것, 운영자가 로그인 사이트를 시험할 때 회사 로그인을 거치는 것, 운영자의 문이 지어질 때까지 그 페이지가 지금처럼 열리는 것이 그것입니다.
>
> 사용자: "이대로 확정 (추천)" — 설명: ADR 0065의 상태를 '승인됨'으로 바꾸고(앞의 두 답에 따라 고칠 것이 있으면 고친 뒤), 위젯 관리 화면 그리기로 넘어갑니다.

고르지 않은 안은 "고칠 곳 있음"이다. 설명: "고칠 곳을 'Other'나 다음 메시지로 알려 주시면, 고친 뒤 다시 여쭙습니다. 그동안 화면 그리기는 시작하지 않습니다."

이 답으로 ADR 0065의 `status`와 `docs/adr/README.md`의 그 행을 `accepted`로 바꾸고, ADR 0065 결정 "승인 때 함께 확인받는 세부"에 승인의 답을 적었다. 앞의 두 답은 초안과 같아 본문을 더 고치지 않았다. 공개 데모의 남은 물음을 받는 쪽은 public-demo의 기능 계획 머리 문단("이 행의 설계 인터뷰가 그것들과 기한을 먼저 다시 보고 아래를 다시 쓴다")이고, 그 행의 Blocked by에 넘기는 쪽인 portal-admin이 든다.

## ui-design 2(이어받은 세션)

이어받은 세션이 그리기 전에 다시 했다. 디자인 시스템 아티팩트의 머리는 앞 세션에서 "owned by you"를 봤고, 이번 확인 폴더(`check-1`)로 `project/` 아래 열여덟 파일을 받았다. `check judge`가 `clean`, `decide --caller screen`이 `continue`, `--caller upload`가 `upload`를 냈다. 기록의 `commit`은 `dce80e5882`이고 `pending`과 `claim`은 비었다.

올리기의 절차(`.claude/skills/sync-design-system/upload.md` 1)는 워크트리의 `git status --porcelain`이 비었을 때만 분리 HEAD로 옮겨 짓게 한다. 이 워크트리에는 커밋 전의 ADR 0065와 문서 고침이 있어 비지 않았다. 그래서 분리 HEAD로 옮기지 않고, 짓기의 입력이 `origin/dev`와 같은지를 먼저 봤다. `git fetch origin` 뒤 `git log HEAD..origin/dev`가 빈 출력이고, `git diff --stat origin/dev -- web .claude/rules/web-design.md`(작업 트리와 대 본다)도 빈 출력이었다. `git merge-base --is-ancestor dce80e5882 origin/dev`는 0으로 끝났고 `git diff --stat dce80e5882 origin/dev -- web/packages/ui web/tools/sync-design-system .claude/rules/web-design.md`도 빈 출력이었다. 그 상태에서 이 작업 트리로 `assemble`(파일 804개)과 `record plan`을 돌렸고 `send`와 `delete`가 비었으며 `clearClaim`과 `firstCanonical`이 false였다. 산출 목록은 `web/tools/sync-design-system/previous-output.json`과 `cmp`가 같다고 했다. 그래서 절차 5의 "보낼 것이 없을 때"로 끝냈고, 보낸 것도 커밋할 것도 없다. 분리 HEAD로 옮기지 않은 것은 절차와 다르지만, 짓기가 읽는 `web/`과 규칙 파일이 `origin/dev`와 글자 그대로 같아 산출도 같다고 봤다.

## ui-design 3: 시작 프롬프트

`.scratch/portal-admin/design/screens-prompt.md`를 마저 썼다. 옛 이름을 위젯 테스트 페이지로 바꾸고, 참고 디자인 절(조사의 규칙 여덟, 사람이 고른 방향 넷, 가져오지 않을 것, 부딪친 자리 하나), 첫 차례의 고를 갈래 둘, 둘째 차례의 글, 고른 뒤를 더했다.

- 갈래 1은 사이트 하나 화면의 양식 짜임 네 안이다. 한 페이지와 저장 단추 하나의 목차 세 갈래(목차 없음, 왼쪽 목차, 묶음 제목을 왼쪽에 둔 두 열)와 탭과 저장 단추 하나다. 사람이 'Other'로 두 짜임을 모두 보자고 했고, 한 페이지 짜임의 설명이 목차를 세 안으로 그린다고 적었다(위 "방향"). 추천은 목차 없음이다. 1280에서 옆 탐색과 미리보기가 이미 두 기둥이라는 까닭이다.
- 갈래 2는 위젯 테스트 페이지의 들어오는 문 세 안이다. ADR 0065가 그 화면을 명세에 넘겼고 사람에게 묻지 않았다. 안은 한 칸에 위아래(추천), 나란한 카드 둘, 회사 로그인을 주로 둔 것이다.
- 정해진 화면은 앞 세션이 쓴 여섯 그대로이고, 이름만 바꿨다. 로그인이 필요한 화면의 버튼 차례는 보조("다시 확인")가 먼저이고 주("관리 화면에서 로그인")가 나중이 되게 고쳤다(디자인 시스템의 버튼 차례).
- 묶음은 일곱(기본, 글, 모양, 로그인과 로그아웃, 고지, 창으로 열 때, 위젯 테스트 페이지)이고, 화면 모양 칸은 그것이 바꾸는 상태의 묶음에 뒀다. 켜고 끄는 값은 저장해야 적용되므로 스위치가 아니라 체크박스다(디자인 시스템 `components/Switch/README.md`).
- 고지 전문의 처음 값은 `web/apps/portal/server/notice.ts`의 첫 문단과 쿠키 문장(`cookie-policy.ts`의 30일)을 읽어 지었다.
- 프롬프트를 쓴 뒤 다시 읽다가 둘째 차례 12의 셀렉트 사이트 수를 "넷"으로 잘못 셌다. 담은 사이트 넷 가운데 열리지 않는 하나를 빼면 셋이라 고쳤다. pilot-portal 띠의 바탕을 "올라온 바탕"으로 적은 것은 그 프롬프트가 말하지 않아 "본문과 경계선 한 줄로 가른다"로 고쳤다.

## ui-design 4·5: 그리기(첫 차례)

`frontend-design`을 브리프(시작 프롬프트, `.claude/rules/web-design.md`, 디자인 시스템의 쓰임새 토큰, `CONTEXT.md`의 용어)와 함께 불렀다. 그 스킬이 권한 것 가운데 저장소 규칙과 부딪친 자리는 `.scratch/design-system/design/frontend-design-conflicts.md`에 적었다.

화면 아티팩트는 Design 형식으로 새로 만들었다(제목 `portal-admin 화면 · screens-prompt.md`, https://claude.ai/artifact/Mjudw8fctjzNoDjmLPW89j). 시작 프롬프트 끝에 `아티팩트:` 줄을 적었다. 디자인 시스템(판 `1794636666-d3b5`)은 디자인 시스템 아티팩트의 파일을 서버 복사로 `project/ds/agent-os/`에 붙였다(두 호출, 207개와 185개).

첫 쪽 "1. 고를 갈래와 정해진 화면"에 아트보드 열세 장을 하나씩 쓰고 보냈다. 정해진 화면 여섯, 갈래 1(양식 짜임) 네 안, 갈래 2(들어오는 문) 세 안이다. 렌더와 사진 찍기는 하지 않았다. 갈래 1의 네 안은 칸과 값이 같고 짜임만 달라, 칸 묶음 일곱을 한 자료로 둔 생성 스크립트(세션 스크래치패드의 `gen_form.py`, `gen_door.py`)로 한 장씩 지어 보냈다. 양식 아트보드의 높이(4600, 5400, 5000, 1600)는 렌더로 잰 것이 아니라 칸 수로 어림했고, 그만큼 갈래 2의 줄을 아래로 옮겼다.

그리면서 더한 가정은 캔버스의 회색 메모에 적었다.

- 디자인 시스템의 아이콘 이름 열일곱 밖의 external-link와 chevrons-up-down은 같은 크기와 선의 Lucide 모양을 인라인 SVG로 그렸다. 새 탭으로 여는 버튼 모양 링크는 Button이 글자 뒤 아이콘을 받지 않아 a 요소에 버튼과 같은 쓰임새 토큰을 칠했다.
- 본문 폭 960px에 미리보기 칸 360px가 늘 서므로, 양식 칸은 안 1과 안 4가 576px, 안 2가 392px, 안 3의 칸 열이 376px다(CSS가 정한 값이고 렌더로 재지 않았다).
- 색 테마 견본은 견본 요소에 `data-theme`과 `data-mode`를 함께 달았다. 디자인 시스템이 `[data-mode]` 블록에서 `--primary`를 다시 선언하므로(`web/packages/ui/src/styles/theme.css`), `data-theme`만 달면 조상에서 계산된 녹청 값을 물려받는다.
- 미리보기의 밝기 단추는 누른 쪽을 옅은 바탕과 check 아이콘으로 함께 보인다(색만으로 보이지 않게). 예시 질문 줄의 입력은 TextField와 같은 쓰임새 토큰을 칠한 브라우저 기본 입력에 '예시 질문 1' 같은 이름을 달았다.
- 작은 그림 고르기의 기본 모양은 위젯 화면 작업의 README가 정한 대로(로그인 전 "대화 안의 카드", 고지 전문 "고지 줄 안에서 펼침", 만료 알림 "대화 안의 카드") 이름 뒤에 "(기본)"을 달았다.
- 들어오는 문의 띠는 pilot-portal이 확정한 띠(`.scratch/pilot-portal/design/pp-page.dc.html`, 높이 64px, 오른쪽의 다크 모드 스위치)를 따랐다. 운영자 문의 보조 버튼 둘은 일의 차례대로 "관리 화면에서 로그인", "다시 확인"이고, 안 3의 흐린 줄에 든 "다시 확인"은 동작이라 링크 모양의 버튼으로 그렸다.

## ui-design 6: 고르기(첫 차례)

선택 화면 하나에 질문 셋을 올렸다. 훅(`hook_choice_facts`)이 한 번 막아, 설명에 든 폭(576px, 392px, 376px)을 그린 CSS의 값으로 다시 셈하고 렌더로 재지 않았다고 적었으며, 한 줄에 서는 카드 수를 `minmax(160px,1fr)`로 셈해 맞는 것을 봤다. 확정 질문의 선택지 설명에는 옮기는 때(둘째 차례를 확정한 뒤)를 더했다.

> 질문: 위젯 관리 화면에서 사이트 하나(help-center)를 고치는 화면의 양식 짜임을 고른다. 캔버스 https://claude.ai/artifact/Mjudw8fctjzNoDjmLPW89j 의 가운데 줄 '갈래 1'에 네 안이 있고, 네 안 모두 칸과 바뀜 셋, 오른쪽 미리보기(폭 360px), 아래 저장 띠는 같다. 어느 짜임으로 할까?
>
> 사용자: "탭과 저장 단추 하나" — 설명: 탭 일곱 가운데 고른 탭의 칸만 보인다(그림은 '로그인과 로그아웃' 탭). 바뀐 칸이 든 탭 이름 뒤에 흐린 수 '1'이 서고, 저장 띠는 탭과 상관없이 하나라 다른 탭에서 바꾼 칸도 함께 센다.

고르지 않은 안은 셋이다. "한 페이지, 목차 없음 (추천)", 설명: "묶음 일곱(기본, 글, 모양, 로그인과 로그아웃, 고지, 창으로 열 때, 위젯 테스트 페이지)이 위에서 아래로 이어지고, 스크롤해도 미리보기와 저장 띠는 화면에 붙어 있다. 양식 칸 폭은 576px(그린 CSS가 정한 값이고 렌더로 재지 않았다). 1280 폭에 옆 탐색과 미리보기가 이미 두 기둥이라 목차를 더 두지 않는 안이다." "한 페이지, 왼쪽 목차", 설명: "양식 왼쪽에 폭 160px의 목차가 화면에 붙어 있고, 바뀐 칸이 든 묶음 이름 뒤에 흐린 수 '1'이 선다. 누르면 그 묶음으로 옮겨 간다. 대신 양식 칸이 392px(CSS가 정한 값)로 좁아져 그림 고르기 카드가 한 줄에 두 장씩 선다." ## 둘째 차례의 글

시작 프롬프트 2의 머리 문단에 첫 차례의 답으로 고른 안의 이름("탭과 저장 단추 하나", "한 칸에 두 문을 위아래로")을 넣었다. 한 페이지 짜임을 전제로 쓴 문장 다섯을 탭 짜임에 맞게 고쳤다.

- 화면 1: 고른 탭은 저장할 때의 "로그인과 로그아웃" 그대로이고, 탭 이름 뒤의 바뀐 칸의 수가 사라진다.
- 화면 3: 오류가 든 탭 둘의 이름 뒤에 바뀐 칸의 수 대신 위험 글자색의 circle-x와 오류 칸의 수가 서고, 첫 오류가 든 탭이 골라져 첫 오류 칸에 포커스가 간다.
- 화면 5: 같은 탭 짜임이고 첫 탭 "기본"이 골라져 있다. 그리지 않는 다른 탭의 처음 값은 글로만 적는다.
- 화면 8: 탭 줄은 넘치면 옆으로 밀어 보고, 고른 탭의 칸이 한 열로 선다.
- 포커스 순서에 탭 줄을 넣고, 탭 줄은 고른 탭 하나로만 들어가 좌우 화살표 키로 옮긴다는 것을 더했다. 탐색용 가정에 탭 이름 뒤의 오류 표시와 375에서 넘치는 탭을 더했다.

## ui-design 5: 그리기(둘째 차례)

둘째 쪽 "2. 고른 사이트 화면과 들어오는 문의 완성 화면"에 완성 화면 열두 장을 하나씩 쓰고 보냈다(판 17~28). 생성 스크립트(세션 스크래치패드의 `gen_mk.py`)가 첫 차례의 `gen_form.py`와 `gen_door.py`를 import해, 칸 문구와 도움말이 두 차례에서 같다. 렌더와 사진 찍기는 하지 않았다. 캔버스 색인(`canvas.json`)에 둘째 쪽의 보드 열둘과 메모 일곱을 더해 보냈다(판 29).

그리기 전에 확정한 조각을 다시 읽었다. 위젯의 로그인 상태 줄, 대화, 입력 폼, 고지 줄과 펼침, 고지 확인 덮개, 만료 카드는 widget-login-state의 확정 화면(다른 워크트리의 `.scratch/widget-login-state/design/mk-02`, `mk-03`, `mk-04`, `mk-08`, 읽기만 했다)을 그대로 옮겼다. 확인 창의 덮개(`var(--text)`에 불투명도 0.32)와 떠 있는 메뉴, 모바일의 두 줄 위 막대는 admin-login의 확정 화면(`mk-accounts-disable`, `mk-accounts`, `mk-accounts-m`)을 따랐다.

그리면서 시작 프롬프트와 다르게 그린 것과 더한 가정은 캔버스의 회색 메모(`mk-how`, `mk-assume`, `mk-door-how`)에 적었다.

- 화면 12는 ADR 0061 결정 "위젯 미리보기 페이지"를 따라 시작 프롬프트와 두 군데가 다르다. 그 결정은 "띠의 다크 모드 스위치, 고지 확인 덮개와 짧은 고지 줄, 로그인 단추 줄은 그리지 않고 위젯이 그린다"고 정했다. 그래서 위젯 아래에는 보고서 링크만 두고 짧은 고지 줄은 위젯 안에 그렸으며, 띠에는 다크 모드 스위치가 없다. 시작 프롬프트는 pilot-portal이 확정한 그대로(위젯 아래 짧은 고지 한 줄과 보고서 링크)라고 적었다.
- 들어오는 문(화면 10, 11, 첫 차례 안 1)에는 위젯이 없어 띠의 다크 모드 스위치를 남겼다. 화면 12의 띠와 다르다.
- 미리보기의 첫 화면, 대화, 고지, 만료는 help-center가 위젯 테스트 페이지에서 "둘 다"인 것에 맞춰 둘 다인 사이트의 모양으로 그렸고, 보는 상태 "로그인 전"만 로그인 모드의 모양이다. 위젯 설정에 로그인 모드를 둘지는 명세가 정한다.
- 화면 5의 미리보기는 위젯의 이름(`heading`)이 비면 에이전트 값인데(`web/apps/widget/EMBED.md`의 속성 표) 에이전트도 비어 있어, 위젯 머리에 칸 이름 "위젯의 이름"을 흐리게 두었다(제안). 입력창 안내 문구의 기본값은 위젯 코드(`web/apps/widget/components/organisms/Composer.tsx`)의 "무엇을 도와드릴까요?"다.
- 화면 11 (다)에 시작 프롬프트에 없던 보조 버튼 "다시 확인"을 두었다. 화면 8의 375 저장 띠는 흐린 문장을 뺐다.
- 아트보드 높이는 렌더하지 않고 어림했다.

## ui-design 6: 고르기(둘째 차례)

한 안 화면 열두 장을 질문 하나로 확정할지 물었다. 훅(`hook_choice_facts`)이 세 번 막았다. 첫 번째에 대 보니 질문 문장의 "완성 12만 시작 프롬프트와 다르다"는 닫힌 주장이 틀렸다. 완성 11의 "다시 확인" 버튼과 완성 8 저장 띠에서 뺀 문장도 시작 프롬프트와 다르다. 그래서 "크게 다른 것은 완성 12"로 고치고 작은 더함과 뺌을 적었다. 두 번째는 고친 문장이 새 질문이라 막혔고, 그 문장의 오자("뺄")를 고친 세 번째도 같은 까닭으로 막혀 같은 질문을 다시 열었다. 수(열두 장, 미리보기 상태 다섯, 문 상태 셋, 정해진 화면 여섯, 고른 안 둘, 고르지 않은 안 다섯)는 지은 파일과 캔버스 색인에 대 보았다.

> 질문: 캔버스 https://claude.ai/artifact/Mjudw8fctjzNoDjmLPW89j 의 둘째 쪽 '2. 고른 사이트 화면과 들어오는 문의 완성 화면'에 열두 장을 그렸다. 탭 짜임으로 그린 사이트 하나 화면의 저장한 뒤·저장 실패·떠날 때·등록·지우기·열리지 않는 사이트·375·다크 화면, 미리보기 상태 다섯, 들어오는 문의 375와 상태 셋, 운영자로 들어온 뒤의 화면이다. 시작 프롬프트와 크게 다른 것은 운영자로 들어온 뒤의 화면(완성 12)이다. ADR 0061이 짧은 고지 줄과 띠의 다크 모드 스위치를 위젯이 그린다고 정해서, 위젯 아래 고지 줄과 띠의 스위치를 빼고 보고서 링크만 두었다. 작은 더함과 뺌은 회색 메모에 적었다(완성 11의 '다시 확인' 버튼, 완성 8 저장 띠의 흐린 문장 뺌). 이 열두 장을 이대로 확정할까? 확정하면 이 열두 장과 캔버스 색인(canvas.json)이 첫 차례의 정해진 화면 여섯, 고른 안 둘과 함께 저장소의 .scratch/portal-admin/design/으로 옮겨지고, 고르지 않은 첫 차례의 다섯 안은 아티팩트에만 남는다.
>
> 사용자: "이대로 확정 (추천)" — 설명: 열두 장을 고치지 않는다. 곧바로 옮기기(ui-design 7단계)로 가서 README.md 표를 만들고, 커밋과 PR, 병합까지 이어 간다. 회색 메모에 적은 가정(저장한 뒤의 흐린 한 줄, 떠날 때의 확인 창, 사이트 지우기 문구, 375의 미리보기 덮개 등)은 결정이 아니고 명세가 다시 정한다.

고르지 않은 안은 "고칠 것이 있다"다. 설명: "고칠 아트보드와 고칠 곳을 적어 주면 그것을 고친 뒤 다시 묻는다. 완성 12를 시작 프롬프트대로(위젯 아래 짧은 고지 줄, 띠의 다크 모드 스위치) 되돌리는 것도 여기에 적는다."

확정은 캔버스 메모(`mk-decided`)에도 적었다.

## ui-design 7: 옮기기

화면 아티팩트를 판 30(`1794798388-45a7`)에서 Artifact 도구 `read`의 `paths`로 받았다. 받은 것은 정해진 화면 여섯(`Main`, `mk-sites-empty`, `mk-sites-m`, `mk-login`, `mk-login-states`, `mk-account-menu`), 고른 안 둘(`ch-form-4`, `ch-door-1`), 둘째 쪽 열두 장, `canvas.json`의 21개다. `project/ds/`는 받지 않았다. 받은 파일을 `.scratch/portal-admin/design/`에 `project/`를 뗀 이름으로 복사하고, 세션 스크래치패드에 남은 보낸 사본(`canvas-portal-admin/project/`)의 sha256 목록과 `sha256sum -c`로 대 보아 21개 모두 OK였다. 웹에서 고친 파일은 없었다.

이름은 글자, 숫자, `.`, `_`, `-`만 들고, README.md나 `*-prompt.md`, 충돌 목록과 겹치거나 대소문자만 다른 경로가 없었다.

`README.md`를 새로 썼다. 표는 화면 파일 스물에 한 줄씩이고, 칸은 시작 프롬프트 "고른 뒤" 1대로 근거 문서 여섯, 기준 커밋 `6cc67844 (어림)`, 동기화한 커밋 `agent-os main@dce80e58`, 아티팩트 주소다. 머리에는 고르지 않은 안 다섯(`ch-form-1`, `ch-form-2`, `ch-form-3`, `ch-door-2`, `ch-door-3`)을 아티팩트에만 남겼고 `canvas.json`이 그 다섯도 가리킨다는 것, 그림이 시작 프롬프트나 ADR과 다른 자리, 탐색용 가정과 제안을 적었다. 디자인 시스템 밖 아이콘은 옮긴 파일의 인라인 SVG 경로를 세어 셋(external-link, chevrons-up-down, chevron-down)임을 보았다. chevron-down은 pilot-portal의 확정 화면(`pp-page.dc.html`)에 있던 사이트 셀렉트의 모양이고, 첫 차례 메모(`fixed-how`)에는 앞의 둘만 적혀 있었다.

충돌 목록(`.scratch/design-system/design/frontend-design-conflicts.md`)의 2026-11-16 행 다섯은 첫 차례에 적었다. 둘째 차례에서 새로 부딪친 축은 없었지만, 고정폭 줄의 화면 칸이 "사이트 목록, 사이트 하나"뿐이라 계정 이름을 고정폭으로 그린 계정 메뉴와 운영자로 들어온 뒤의 화면을 더했다.

커밋 전에 `tools/sibling_overlap.py`를 치니 기준 브랜치가 `6cc67844`에서 `59536371`로 움직여 있었다. 그사이 병합된 PR 셋 가운데 widget-login-state의 둘째 화면 작업(PR 583)이 예시 질문, 문의 링크, 스위치를 숨긴 위젯을 그려 확정했다. 이 브랜치에는 커밋이 없어, 겹친 두 파일(충돌 목록, `.scratch/plan.md`)의 사본을 스크래치패드에 두고 HEAD로 되돌린 뒤 `git merge --ff-only origin/dev`로 빨리 감았다. 충돌 목록은 기준 브랜치의 widget-login-state 행 넷 뒤에 portal-admin 행 다섯을 다시 붙였고, `.scratch/plan.md`는 `tools/plan_table.py`로 다시 지었다.
