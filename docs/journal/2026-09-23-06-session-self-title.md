# 2026-09-23 (06) 새 세션이 스스로 이름을 붙인다 — open-session 4단계를 받는 쪽으로

브랜치 `chore/session-self-title`, PR #60(`729c7dc`로 squash 병합). `open-session` 4단계의 이름 붙이기를
여는 쪽에서 새 세션으로 옮겼다. UserPromptSubmit 훅 `tools/hook_prompt_directive.py`가 첫 턴의 지시문을
알아보고 `set_session_title self` 계기를 넣고, 전각 `／`가 고쳐지지 않은 채 왔으면 스킬 파일을 읽어 따르라는
계기를 붙인다. 여는 쪽은 확인만 한다. 그 훅이 만든 세션에서 오탐해 두 번째 커밋이 첫 턴으로 좁혔다.

사용자 입력은 작업 지시 하나, 지시문 형식 질문 하나, 수정 승인 하나, `/clear` 판정 하나, PR·병합 지시였다.

## 여는 쪽이 이름을 붙이면 사람의 귀환에 기댄다

문제의 기록은 일지 `2026-09-23-04-traces-list` 13~21행이다. 첫 줄이 슬래시 명령이면 앱이 딥링크의 `/`를
전각으로 바꿔 넣어 스크립트가 `held=`에서 멈추고, 사람이 새 세션에서 고쳐 보낸 뒤 옛 세션으로 돌아와야
4·5단계가 돌았다. 사람은 새 세션(메인 패널)으로 옮겨 가 돌아오지 않았다. 사이드바에 "serve 명령 구현"(티켓
03)이 지금도 그 제목이다.

> 사용자: "`open-session` 스킬 4단계를 '새 세션이 스스로 이름을 붙인다. 여는 쪽은 사람이 돌아왔을 때 확인만
> 한다'로 고치고, 5단계(옆 패널 배치)도 사람의 귀환에 기대는 것이 선택 사항임을 적는다."
> 사용자: "훅은 MCP 도구를 부를 수 없으므로 계기만 넣는다(CLAUDE.md 교정 루프의 '계기만 넣는 훅')."

받는 쪽은 `self` 하나로 자기를 가리킨다. 여는 쪽은 새 세션의 `sessionId`를 `createdAt`·`lastActivityAt`으로
추론해야 했고 그 시점이 사람의 귀환에 묶여 있었다. 옮기자 식별 문제가 통째로 사라졌다.

## 훅이 보는 것

- **줄 머리의 두 줄.** `브랜치:` 줄(값이 있다)과 `어디서: 새 세션` 줄. 문장 속에서 형식을 인용한 것은 세지
  않는다. 테스트 픽스처는 05 세션이 실제로 받은 첫 메시지 원문(트랜스크립트에서 꺼냈다)이다.
- **전각이면 스킬 파일.** 이름은 `[a-z0-9][a-z0-9-]*` 한 토막만 받는다. 이름이 곧 경로라 `／../../x`가
  `.claude/skills/` 밖을 가리키지 못하게 한다. 앱의 전각 치환은 출처 모를 링크가 명령을 일으키지 못하게
  하는 장치인데, 훅까지 온 것은 사람이 보내기를 누른 뒤라 그 확인은 이미 있었다.
- **stdin 은 바이트로.** 훅 환경의 stdin 은 cp949·`surrogateescape`다. 텍스트로 읽으면 한글이 깨져 `브랜치:`가
  매치되지 않고 **예외 없이 exit 0, 출력 0바이트**다 — "지시문이 아니다"와 구별되지 않는다. 변이로 실측했고
  단위 테스트로는 볼 수 없다. 기존 훅 넷은 ASCII 만 매치해 같은 조건에서 정상 출력을 냈다(한글 커밋 메시지가
  낀 `gh pr create`로 실측). 셀프 리뷰가 "넷도 고치라"고 했지만 근거를 보고 두었다.

## 테스트 먼저, 그리고 변이

지시문 판정 변이 여섯 중 하나(`어디서:` 줄의 `match`→`search`)가 살아남았다. 테스트의 인용 문장에 줄 머리
`브랜치:`가 없어 다른 판정이 대신 막고 있었다. AND 로 묶인 두 조건은 한쪽만 깨는 입력으로는 다른 쪽의 결함을
가린다. next-session 결정표의 "어디서 줄에 이유를 적는다"에서 나올 법한 인용으로 보강했다.

셀프 리뷰가 "형식이 세 곳에 따로 있다"(스킬 블록, 훅 상수, 테스트 사본)를 짚어, next-session 형식 절의 블록을
채워 훅에 넣는 테스트를 더했다. 스킬에서 라벨을 바꾸면 훅은 침묵하지만 이 테스트가 빨강이다(변이 둘로 확인).

## `focus`가 10초에 묶여 있었다

5단계에 `focus -TimeoutSec 90`을 적은 뒤 스크립트를 보니 `Find-RowByTitle`이 대기를 10초로 하드코딩하고
있었다. 적은 인자가 아무 효과가 없었을 것이다. `focus`만 `-TimeoutSec`을 따르게 고치고 없는 제목으로 3초·
15초를 실측했다(4.9초·16.3초에 실패). 스크립트의 회귀 시험이 없다는 대기열 17의 증거가 하나 더 늘었다.

## 그 훅이 만든 세션에서 오탐했다

첫 커밋 뒤 사용자가 지시문을 코드 펜스로 붙여 넣고 형식을 물었다.

> 사용자: "시작 프롬프트가 있는데 위에 중복으로 할 필요 있을까?"

답은 "둘 다 필요하다"였다. 첫 줄은 앱의 명령 해석기가 읽는 유일한 자리(`disable-model-invocation`
스킬은 첫 줄에서만 로드된다)이고, `시작 프롬프트:` 칸은 지시문의 기록이자 "이 세션" 경로의 유일한 원천이며
open-session 2단계가 첫 줄을 거기서 만든다.

그런데 그 메시지에 **이 훅이 발동했다.** 설정 변경이 세션 도중에 반영됐고, 줄 머리의 두 줄을 보고 이 세션
이름을 `feature/05-traces-list`로 바꾸라는 계기를 넣었다. 따르지 않았다. 확인해 보니 이 세션 제목이 앱이
지은 것이라 따랐으면 **승인 없이** 바뀌었고, 같은 제목이 둘이 되어 open-session 1단계("같은 제목의 세션이
하고 있다")가 다음 열기를 막았을 것이다. docstring 의 "사람이 지은 제목이면 앱이 승인을 묻는다"는 이 경우를
막지 못했다 — "못 보는 것"을 적어 두고도 그 주장을 재지 않았다.

내용만으로는 "지시문으로 연 세션"과 "지시문을 두고 이야기하는 세션"이 같다. 빠진 것은 **몇 번째 턴인가**라는
축이었다. 트랜스크립트에 assistant 기록이 아직 없을 때만 내도록 제안했다. 사용자 메시지 수로 세면 훅이 도는
순간 지금 프롬프트가 기록됐는지에 따라 0과 1이 갈리지만, assistant 기록은 첫 턴에 언제나 0이다.

> 사용자: "수정 승인"

경로를 모르면(키 없음·빈 값) 내지 않고, 파일이 아직 없으면 첫 턴으로 본다. 잘못 발동하면 조용히 틀리고,
안 발동하면 앱이 지은 제목이 남아 open-session 4단계의 확인이 드러내는 비대칭이다. 실측 여섯: 이 세션
트랜스크립트+오탐 난 메시지 0B, 05 세션을 첫 assistant 직전에서 자른 조각 992B, 05 전체 0B, 파일 없음 992B,
키 없음·빈 경로 0B.

두 번째 셀프 리뷰의 명세 축이 실제 트랜스크립트 200파일 5만여 줄을 훑어 전제(모든 줄이 최상위 `type`을 가진
객체, 첫 assistant 앞에 assistant 없음)를 확인했고 `/clear` 경계를 재현했다. `/clear` 뒤에는 트랜스크립트가
새 파일로 시작해 붙여 넣은 지시문에 발동한다.

> 사용자: "클리어이후도 첫턴 승인"

같은 앱 세션이 그 지시문의 일로 새로 시작하는 것이라 이름을 바꾸는 게 맞다. 대가는 `/clear` 직후 지시문을
두고 질문만 해도 이름이 바뀐다는 것이다.

## 06 을 열다가 `page=`에서 멈췄다 — 모니터 절전

일지 PR(#61)까지 병합하고 06 을 열자 `fired=` 뒤 30초 안에 `page=`가 나오지 않았다. 04→05 에 이어 2회차다.

> 사용자: "page= 실패는 지금 고쳐봐. 잘되다가 갑자기 어느 순간 왜 안되는거야"

diagnosing-bugs 로 갔다. 스크립트의 `page=` 탐색만 떼어 지금 화면에 돌리는 읽기 전용 프로브는 빨강이었지만,
화면에는 새 세션 페이지가 아니라 이 세션이 떠 있었다 — 탐색이 아니라 화면이 문제였다. 앱 로그는 MSIX 패키지
안(`%LOCALAPPDATA%\Packages\Claude_*\LocalCache\Local\Claude\logs\main.log`)에 있다(`%APPDATA%\Claude\logs`는
8월에 멈춘 옛 것이다). 딥링크마다 `second-instance: suppressing duplicate argv` 뒤 `setFocusedSession: null`과
`checkTrust`가 오는데, 성공한 10:49 와 실패한 12:18·16:31 이 똑같았다. 앱 버전도 그날 내내 같았다. 갈린 것은
사람이었다. 12:18 직전에 "Window focused — last poll 58분 전"이 있고, 16:31 에는 PC 입력이 50분 넘게 없었다.
이 PC 는 입력이 30분 없으면 모니터를 끈다.

가설: 꺼진 모니터에서 앱(Electron)이 창을 가려진 것으로 보고 그리지 않는다. 딥링크를 쏘고 20초 안에 태그가
화면에 오르는지 보는 프로브로 모니터를 `SC_MONITORPOWER`로 끄고 쏘면 2/2 빨강, 쏘기 직전에
`SetThreadExecutionState(ES_SYSTEM_REQUIRED|ES_DISPLAY_REQUIRED)`를 부르면 2/2 초록(대기 없이 1.2초). 고친
스크립트를 모니터를 끈 채 95분 무입력에서 돌려 `idle= fired= page=`(1.1초) `held=`를 봤다. 04→05 때 스크립트는
실패했는데 05 는 지시문을 받은 것도 이것으로 풀린다 — 화면은 사람이 돌아와 모니터가 켜진 뒤에 그려졌다.

스크립트는 모든 동작 전에 화면 유휴 타이머를 한 번 되돌리고 첫 줄 `idle=`에 마지막 입력 뒤의 초를 남긴다.
open-session 3단계의 "`page=`가 안 나오면 앱이 딥링크를 받지 못한 것이다"는 이번 두 번에는 틀렸다. 앱은 받았고
그리지 않았다. 회귀 시험의 올바른 자리는 없다(실제 앱과 모니터가 있어야 재현된다, 대기열 17 과 같은 벽).
`split`·`focus`가 꺼진 모니터에서 실패하는지는 재지 않았다.

## 갈린 곳

- **여는 쪽의 대신 붙이기.** 확인에서 제목이 안 보이면 여는 쪽이 붙일 수 있었다. 붙이지 않고 알리기만 한다.
  대신 붙이면 훅이 조용히 망가져도 제목이 맞게 보인다.
- **기존 훅 넷의 stdin.** 셀프 리뷰는 고치라고 했고, 실측은 ASCII 만 매치해 안전하다고 했다. 두었다.
- **두 부재의 판정.** 경로 모름 → 내지 않음, 파일 없음 → 첫 턴. 위험의 비대칭.
- **`/clear` 뒤.** 첫 턴으로 친다(사용자 승인).

## 번복하거나 고친 것

- docstring 의 "사람이 지은 제목이면 앱이 승인을 묻는다" → 틀렸다. 앱이 지은 제목은 묻지 않고 바뀐다. 첫 턴
  판정과 그 실측으로 바꿨다.
- 스킬에 적은 `-TimeoutSec 90` → 스크립트가 무시하고 있었다. 스크립트를 고쳤다.
- 테스트 픽스처의 `\n`이 파이썬 문자열에서 진짜 줄바꿈이 되어 JSON 이 깨진 줄이 됐다. 이스케이프로 바로잡았다.
- next-session 형식 절의 "진행 중인 대화에 붙여 넣는 것은 계기가 아니다" → 표준 축이 중복 금지문이라 지웠고
  명세 축은 빠졌다고 했다. 원천은 훅 docstring 이라 지운 쪽을 유지했다.
