  통제로 옮겼다. 우리 방향은 맞고(표준 정렬, 얇은 루프, 재생으로 검증하는 승인 재개, fail-closed와 트레이스), 가장 큰 빈칸은 신뢰

## Notion 페이지 대조

사용자가 든 Notion 페이지 "기능 목록"은 Notion 연동(`notion-fetch`)이 404로 거절해(연동 워크스페이스에 공유되지 않은 페이지) 내장
브라우저로 읽었다. 사용자가 브라우저 창에서 로그인한 뒤 `get_page_text`로 본문 전체를 받았다(브라우저로 읽었다, 2026-11-03). 페이지는
일곱 절이다. 에이전트 저작(BackOffice Web의 그래프 캔버스), 1층 검증 규칙, 모델 관리, 서비스·위젯, 실행 런타임, 승인, 지식(rag-mcp).
각 항목을 보고서의 표(순위 일곱, 미룬 다섯, 만들지 말 것 열)와 지금 코드에 대 본 결과를 넷으로 갈랐다.

**Agent OS로서 들어가야 하는 것(중재·강제·기록에 바로 들고 지금 없는 것).**
- MCP 게이트웨이와 스코프 집행, 신뢰 경계: 보고서 1위(플러그인 신뢰 기본값)와 같다. `ctx.tool`이 자리는 맡지만 서버마다 신뢰
  수준이나 스코프를 두는 칸이 매니페스트에 없다(`sdk/manifest.py`의 McpServer는 `command`·`args`·`secret_args`뿐이다).
- 운영자가 끼우는 강제 승인: 지금은 `requires_approval`이 에이전트 매니페스트에 있어 에이전트 저자가 정한다(`sdk/manifest.py:79`).
  운영자가 바깥에서 끼우는 승인이 "건너뛸 수 없는 강제"다.
- 상한 가운데 토큰·비용과 승인 만료: 지금 상한은 루프 10턴(`core/loop.py:27`), 실행 타임아웃, 사이트 파일의 요청 글자 수·동시
  실행·시간당 실행·구독 수(`http/sites.py:78-83`)다. 토큰·비용 상한은 없고 이벤트에 비용 칸이 없다. 만료는 토큰(JWT)에만 있고
  멈춘 실행의 승인 대기에는 없다(grep). 보고서 2위(실행 비용·지연 합계)의 전제다.
- 트레이스의 소요시간: `LlmCalled`에 토큰 수는 있고 소요시간·비용은 없으며 `ToolCalled`에는 둘 다 없다(`sdk/events.py:82-101`).
- 모델의 기밀 등급과 능력 선언: 모델 매니페스트는 `provider`·`model_id`·`max_tokens`·`temperature`다(`sdk/manifest.py:126`). 어떤
  데이터를 어떤 모델에 보낼 수 있는지는 강제의 일이고, 둘째 제공자(보고서 5위, Notion의 vLLM 내부 엔드포인트)와 맞물린다.
- 주체를 MCP 서버까지 전파: 시작 이벤트의 `principal`은 필수(ADR 0008)지만 `adapters/mcp.py`는 principal을 모른다(grep). Notion의
  "검색 신원 필터"와 "문서 단위 ACL"이 바라는 것이고 멀티테넌시 없이도 할 수 있다.
- 트레이스 보존 기간: 보존·삭제 코드가 없다. 기록의 운영 책임이라 작지만 들어간다.
- 조합 차단(익명 접근 서비스에 사내 지식 서버를 붙이는 것 같은 금지 조합): 운영자 설정 층의 강제다. 지금 없다.

**이미 있는 것.** 승인 대기와 재개(ADR 0009), 관리 화면의 승인 처리(`web/apps/admin/api/approval`), 사이트가 서명한 토큰과 허용
도메인(ADR 0023, `http/sites.py:96-99`), 위젯 임베드(ADR 0024), 실시간 스트림(ADR 0014), 호출 단위 트레이스(ADR 0039), 켜고
끄기(ADR 0017), 실패 원인(ADR 0031), 단기기억 자동 요약(ADR 0022의 대화 고리와 요약), 비밀 값 마스킹(`secret_args`, 원칙 V).

**보고서가 만들지 말라고 한 것과 부딪히는 것.** 1절 전체(자유형 그래프 캔버스, 노드 어휘 여덟, 시작 템플릿, 시뮬레이터)와 2절
전체(그래프의 검증 규칙), 5절의 그래프 실행·위임 handoff·제어권 관리·위임 컨텍스트는 그래프·노코드 빌더와 범용 멀티에이전트
프레임워크다. PRD도 그래프 빌더를 제외한다. 다만 1절의 "에이전트 계약면 편집"과 "버전 관리·발행"은 선언형 에이전트의 매니페스트로
옮길 수 있고, "3층 트레이스 재생"은 보고서 4위(트레이스 재생 평가)라 그래프 없이 들어간다. 7절 rag-mcp는 보고서의 금지 열에 없지만
우리 PRD에서는 MCP 서버 플러그인의 자리다. 런타임이 맡을 몫은 그 서버로 주체를 넘기는 것(위)뿐이다.

**보고서가 미룬 것.** 장기기억 주입(장기 메모리), tenant_id 멀티테넌시, 알림 어댑터와 원격 응답 수신·재개 링크(Slack류), 색인
예약(스케줄러). 승인 만료는 worker 없이 재개 시점에 `Clock` 포트의 지금으로 판정할 수 있어 미룬 것에 넣지 않았다.

인젝션 검사는 갈래가 둘이다. 어느 글이 신뢰 밖인지 표시하는 것은 결정적 코드의 일이라 들어가고(skill-plugin의 본문 신뢰 수준과
같다), 글을 읽어 인젝션인지 판정하는 검사기는 모델 호출이라 보장이 아니고 플러그인의 자리다.

> 사용자: 우리 프로젝트는 서비스 개념이 없는데?

맞다. "서비스"는 Notion 페이지의 개념(에이전트 하나에 접근 정책·위젯 설정·보존 기간·운영 설정을 묶어 발행한 것)이고 우리에게는 없다.
용어집의 사이트는 "위젯을 자기 페이지에 넣고 자기 사용자의 신원을 보증하는 바깥 웹 서비스. Agent OS의 일부가 아니다"이며, 우리 쪽의
묶음은 운영자의 사이트 파일 항목이다. 항목마다 `issuer`·`audience`·`allowed_origins`·`agents`·공개 키·`limits`가 있고
(`tests/fixtures/site_file/sites.toml`, `http/sites.py:96-100`), 요청은 에이전트 이름을 들며(`channel/http/bodies.py:28`) 최종 사용자
경로는 그 사이트의 `agents` 목록 안에서만 본다(`channel/http/end_user.py:144`). 그래서 위 여덟 가운데 둘을 고쳐 적는다. 운영자가
끼우는 강제 승인(2)의 자리는 새 개념이 아니라 운영자 파일(사이트 항목이나 켜짐 파일, ADR 0017)이다. 조합 차단(8)은 사이트 항목의
`agents` 허용 목록이 이미 반쪽이고, 나머지 반쪽(사이트의 접근 등급과 서버의 신뢰 수준을 맞대는 것)은 1(MCP 서버의 신뢰 수준)이 선
뒤의 일이라 따로 세지 않는다. 서비스 개념을 들이는 것은 이 대조의 결론이 아니다.

> 사용자: Agent OS랑 사실 채널은 별개가 되야 하는건가?

답의 요지(결정은 아직이다). 층으로는 이미 별개다. 원칙 IV에서 core는 채널을 import하지 않고 채널이 core의 실행·재개를 부르며,
용어집의 채널은 "런타임에 실행을 요청하고 출력을 받는 면"이다. 제품으로는 하나다. 실행을 일으키는 면이 없으면 런타임은 돌지 않고,
OS가 셸을 갖고 나오는 것과 같다. 질문의 알맹이는 보장이 어디 사느냐다. 지금 core가 강제하는 것은 루프 상한·타임아웃·승인 멈춤·
트레이스이고(`core/run.py`, `core/loop.py`), 사이트 상한(요청 글자 수, 동시·시간당 실행, 구독 수)은 최종 사용자 경로가 core 앞에서
걸며 운영자 채널에는 없다(`channel/http/limits.py` 독스트링, ADR 0023). 그래서 전체 기능의 선은 이렇다. "건너뛸 수 없는" 것(토큰·비용
상한, 서버 신뢰 수준, 운영자가 끼우는 승인, 주체 전파)은 core에 두고, 채널은 신원을 세우고 사이트의 것만 건다. 채널을 플러그인
종류(Slack류)로 여는 것은 보고서가 미룬 것이고, 이 선이 서 있으면 그때 core를 다시 쓰지 않아도 된다. 사용자가 미룬 "보장의 경계"의
한 조각이 여기서 닿았다.

> 사용자: 역할과 책임이 잘 구분되어 있는거지?

답의 요지. 층과 사람의 역할은 갈라져 있고 기계가 판정한다. 층의 의존 방향은 import-linter와 플러그인 경계 테스트가, 채널과 관리의
가름은 용어집("실행을 일으키지 않는 것은 채널이 아니다")이, 결정의 권한은 core가 가른다(실행의 주체만 결정하고 이어 가며 CLI·
운영자 채널·최종 사용자 경로가 한 규칙을 지난다. ADR 0023이 "운영자도 최종 사용자의 실행에 결정한다"를 거부했다). 운영자의 것은
운영자 파일(켜짐 파일 ADR 0017, 사이트 파일 ADR 0023)에 있고 사이트는 신원만 보증한다. 덜 가른 자리는 넷이고 모두 위 여덟에서
나왔다. 승인 정책의 저자가 운영자가 아니라 플러그인 개발자다(`requires_approval`이 에이전트 매니페스트). 상한이 core와 채널 두
곳에 있어 보장 문장이 어느 것이 어디 사는지 말해야 한다. MCP 서버는 설치가 곧 신뢰라 신뢰의 정도를 운영자가 정할 자리가 없다.
주체가 core에서 멈추고 도구 서버에 닿지 않는다.

> 사용자: 승인 정책의 저자. 클로드 코드를 참고할 수 있나

Claude Code의 권한 정책을 서브에이전트(claude-code-guide)가 공식 문서로 대 봤다(2026-11-04). permissions 페이지는 원문 832행을 끝까지
읽었고 나머지는 WebFetch 인용이라 웹 요약이다. 확인한 것: 설정 층의 우선순위는 관리 정책 > 명령줄 > 프로젝트 로컬 > 프로젝트 공유 >
사용자이고, 관리 정책은 아래 층이 덮지 못하며, allow는 층을 넘어 합쳐지고 deny는 어느 층의 것이든 다른 층의 allow를 이긴다
(https://code.claude.com/docs/en/settings.md#settings-precedence). 평가는 deny → ask → allow 순으로 첫 매치가 정하고 넓은 deny가 좁은
allow를 이기며, 규칙은 `도구(인자 패턴)` 꼴이고 MCP는 `mcp__서버__도구`·`mcp__서버`다. 문서가 스스로 적은 한계: Bash 규칙은 명령
문자열 매칭이라 `/usr/bin/curl`이나 `sh -c`를 막지 못하고 OS 경계는 샌드박스가 맡는다
(https://code.claude.com/docs/en/permissions.md). "Permission rules are enforced by Claude Code, not by the model"이 원문의 문장이고
"모델이 훅을 건너뛸 수 없다"는 문장은 찾지 못했다. PreToolUse 훅은 allow·deny·ask를 돌려주되 훅의 allow가 deny·ask 규칙을 넘지
못한다(https://code.claude.com/docs/en/permissions.md#extend-permissions-with-hooks). 서브에이전트 정의의 `tools`는 좁히기만 하고
승인을 넓히는 것은 permissionMode인데 부모가 허용한 범위 안이다(https://code.claude.com/docs/en/sub-agents.md, 웹 요약). MCP 도구
애노테이션은 권한 결정에 쓰지 않고, 서버가 권한에 주는 신호는 `_meta["anthropic/requiresUserInteraction"]: true` 하나이며 그것은 매
호출 프롬프트를 강제해 allow와 자동 모드를 건너뛰지 못하게 하는, 더 엄격해지는 쪽으로만 작동한다
(https://code.claude.com/docs/en/mcp.md#require-approval-for-a-specific-tool, 웹 요약). MCP 명세 2025-06-18은 애노테이션을 신뢰하는
서버의 것이 아니면 믿지 말라고 한다(https://modelcontextprotocol.io/specification/2025-06-18/server/tools).

우리에게 옮기면(결정은 아직이다). 저자가 셋이고 방향이 한쪽이다. 도구·에이전트의 저자는 더 엄격하게만 할 수 있고(우리의
`requires_approval`이 그 자리, Claude Code의 `requiresUserInteraction`과 서브에이전트 `tools` 좁히기), 운영자는 allow·ask·deny를 적으며,
층이 둘 이상이면 아래 층은 위 층의 deny를 풀지 못한다. 판정은 모델이 아니라 런타임 코드가 한다(우리는 core가 이미 그렇다,
`core/run.py:1265`). 자리는 ADR 0017의 가름대로 매니페스트도 `disabled.toml`도 아닌 운영자 파일 하나다. 이름 기반 규칙의 우회(같은
일을 하는 다른 도구)는 Claude Code도 문서로 인정하고 샌드박스에 넘기는데, 우리 매니페스트 주석도 "같은 일을 할 수 있는 도구는 전부
여기 들어가야 한다"로 같은 한계를 적고 있다(`sdk/manifest.py:76-78`). 남는 선택은 운영자가 저자의 `requires_approval`을 풀 수 있게
할지이고, Claude Code는 못 풀게 한다.

> 사용자: 못 풀게 하자.
> 그리고 나는 멀티 에이전트 병렬 실행도 됐으면 좋겠어.

라운드 밖의 결정: 운영자는 저자의 `requires_approval`을 풀지 못한다. 저자의 것은 더 엄격해지는 쪽으로만, 운영자 파일은 그 위에 더하는
쪽으로만 작동한다(Claude Code의 `requiresUserInteraction`과 같은 방향).

"멀티 에이전트 병렬 실행"은 뜻을 가르고 있다(아직 결정 아님). 코드에 대 본 사실: 서로 다른 실행 여럿이 동시에 도는 것은 이미
된다(실행 등록부의 칸, `--end-user-concurrent-runs`, 사이트 상한). 모델이 한 턴에 낸 도구 호출 여럿은 지금 차례로 돈다
(`core/loop.py:51-52`의 `for tool_call in message.tool_calls: await _execute`). 에이전트가 다른 에이전트를 부르는 길은 없다(컨텍스트는
`llm`·`tool`뿐). 보고서는 "리드 에이전트가 하위 에이전트에 일을 맡기는 멀티에이전트"를 빅테크 기본 사양 여덟에 넣으면서도 우리에게는
"당장 불필요"로 두었고(표 70행), 범용 오케스트레이션 프레임워크는 만들지 말 것(124행), A2A는 외부 에이전트에 일을 맡길 때만(115행)
으로 적었다.

> 사용자: 3을 뜻해. 그리고 MCP나 Skill은 클로드 코드에서 사용하는 MCP 처럼 호환이 가능했으면 좋겠어. Skill도. 클로드 코드의 플러그인은
> 기능 차제는 지금 없지만 이것도 호환 가능한 기능으로 추가해줬으면 해. 그럼 코덱스랑도 호환이 될까?

라운드 밖의 결정 둘. "멀티 에이전트 병렬 실행"은 셋째 뜻(리드 에이전트가 하위 에이전트에 일을 맡기고 여럿을 동시에 띄워 결과를
받는 것)이고 전체 기능에 더한다. MCP 서버·스킬·플러그인은 Claude Code의 디스크 형식과 호환되게 하고, Claude Code 플러그인
형식(묶음)을 읽는 것도 전체 기능에 더한다. Codex와의 호환은 질문이라 사실을 찾는다(서브에이전트 둘, 2026-11-04).

우리 쪽 사실(코드와 ADR을 읽었다). 스킬은 ADR 0041이 `plugins/skills/<이름>/`에 공통 넷만 적은 `plugin.toml`과 Agent Skills 표준의
`SKILL.md`를 함께 두기로 했고, "`SKILL.md`만 두고 `plugin.toml`을 두지 않는다"는 로더·관리 목록·켜고 끄기가 모두 `plugin.toml`을
읽는다는 이유로 거부했다(그 ADR Considered Options). 그래서 Claude Code의 스킬 폴더는 `plugin.toml` 넉 줄을 더해야 들어온다. 머리말은
PyYAML로 전체를 읽고 `name`·`description`만 쓰며 제품별 키는 거부하지 않는다. MCP 서버는 `plugins/mcp/<이름>/plugin.toml`의
`[server]`에 `command`·`args`·`secret_args`를 적고(`plugins/mcp/everything/plugin.toml`), 원격(HTTP) 서버 칸은 없다. 로더는
`<root>/<종류>/<이름>/plugin.toml`만 읽는다(`adapters/filesystem.py:57`).

Claude Code의 세 형식(서브에이전트 claude-code-guide, 2026-11-04. 모두 WebFetch라 웹 요약이고 "본문 확인"으로 표시한 것은 페이지
본문에서 읽은 것이다).
- MCP(https://code.claude.com/docs/en/mcp): 최상위 `mcpServers` 아래 서버 이름이 키다. 칸은 `type`(`http`·`sse`·`ws`. 없으면 stdio),
  `command`·`args`·`env`·`url`·`headers`·`headersHelper`·`timeout`·`alwaysLoad`·`oauth`. `${VAR}`·`${VAR:-기본값}`을 command·args·env·
  url·headers에서 치환한다. 위치는 프로젝트 루트 `.mcp.json`, 사용자 `~/.claude.json`, 플러그인 루트 `.mcp.json`(같은 `mcpServers` 래퍼).
- 스킬(https://code.claude.com/docs/en/skills): "Claude Code skills follow the Agent Skills open standard"라 적고 agentskills.io를
  가리킨다. 머리말은 전부 선택이고 `description`만 권장하며, `name` 기본값은 폴더 이름이다. 제품별 키가 많다(when_to_use, argument-hint,
  disable-model-invocation, user-invocable, allowed-tools, model, context, hooks, paths, shell 등). 모르는 칸은 무시한다. 폴더는 `SKILL.md`만
  필수이고 보조는 `scripts/`(`${CLAUDE_SKILL_DIR}`)다. 찾는 위치는 `~/.claude/skills/`, `.claude/skills/`, `<플러그인>/skills/`.
- 플러그인(https://code.claude.com/docs/en/plugins-reference, 본문 확인): `.claude-plugin/plugin.json`의 필수는 `name` 하나. 구성 요소는
  `skills/`, `commands/`(레거시), `agents/`(markdown 서브에이전트), `hooks/hooks.json`, `.mcp.json`, `.lsp.json`, `output-styles/`,
  `workflows/`, `themes/`, `monitors/`, `bin/`, `settings.json`. 셸을 실행하는 요소는 hooks·monitors의 `command`, MCP stdio의
  `command`와 http의 `headersHelper`, LSP의 `command`, `bin/`, 마켓플레이스 source `command`다. 서브에이전트 markdown 머리말은
  `name`·`description` 필수에 tools, disallowedTools, model, permissionMode, maxTurns, skills, mcpServers, hooks, memory 등이고 플러그인
  서브에이전트는 hooks·mcpServers·permissionMode를 무시한다(요약 기준). `marketplace.json`은 카탈로그이고 저장소를 호스팅하지 않는다.

Codex CLI의 세 형식(서브에이전트 general-purpose, 2026-11-04. 문서 `.md` 원문과 GitHub 소스를 curl로 받아 읽었고 사본은 세션 스크래치
`codex-docs/`에 두었다. 저장소에는 옮기지 않았다).
- MCP(https://learn.chatgpt.com/docs/extend/mcp.md, 원문): `~/.codex/config.toml`과 프로젝트 `.codex/config.toml`의
  `[mcp_servers.<이름>]`. stdio는 `command`·`args`·`env`·`cwd`, HTTP는 `url`·`auth`·`bearer_token_env_var`·`http_headers`. 도구별
  `approval_mode`, `enabled_tools`·`disabled_tools`, 시작·도구 타임아웃이 있다. `.mcp.json`은 평소에 읽지 않고 `/import`(Claude Code·
  Cursor 설정 들여오기)와 플러그인 묶음에서만 읽는다(소스 `external-agent-migration/src/mcp.rs`의 상수).
- 스킬(https://learn.chatgpt.com/docs/build-skills.md, 원문): Agent Skills 표준 위에 선다. 찾는 위치는 `.agents/skills`(저장소 루트까지
  상위 폴더), `~/.agents/skills`, `/etc/codex/skills`, 옛 경로 `.codex/skills`·`~/.codex/skills`. 파서(`skills/src/parser.rs`)가 읽는
  머리말은 `name`(없으면 폴더 이름)·`description`·`metadata.short-description`뿐이고 모르는 칸은 무시한다. 2025-12-04 rust-v0.65.0에
  실험으로 들어가 2025-12-19 v0.76.0에 기본 켜짐(릴리스 노트 원문).
- 플러그인(https://developers.openai.com/plugins/build/plugins.md, 원문): 있다. 이식형은 루트 `plugin.json`(`$schema`가
  https://agent-plugins.org/schemas/1.0.0/plugin.schema.json, `name`·`version`·`description`·`author`…) + `skills/` + `mcp.json`(서버마다
  `type` 필수) + `hooks/hooks.json` + `assets/`. 옛 형식은 `.codex-plugin/plugin.json`. **Claude Code 형식을 읽는다**: 소스
  `exec-server-protocol/src/protocol.rs`의 `DISCOVERABLE_PLUGIN_MANIFEST_PATHS = [".codex-plugin/plugin.json",
  ".claude-plugin/plugin.json", ".cursor-plugin/plugin.json"]`, 마켓플레이스도 `.claude-plugin/marketplace.json`을 찾는다. Agent Plugins
  명세(https://agent-plugins.org) 본문은 읽지 않았다.
- 에이전트 정의(https://learn.chatgpt.com/docs/agent-configuration/subagents.md, 원문): `~/.codex/agents/`·`.codex/agents/`의 TOML
  파일 하나당 에이전트 하나, `name`·`description`·`developer_instructions` 필수, `model` 선택. 플러그인 묶음 밖이고 Claude Code의
  markdown 서브에이전트와 모양이 다르다.
- Agent Skills 명세 원문(https://agentskills.io/specification.md): 필수 `name`(1–64자, 소문자·숫자·하이픈, 시작·끝 하이픈과 `--` 불가,
  부모 폴더 이름과 일치)·`description`(1–1024자). 선택 `license`·`compatibility`·`metadata`·`allowed-tools`(Experimental). 폴더 권장
  `scripts/`·`references/`·`assets/`. ADR 0041이 웹 요약으로 적은 것과 어긋나는 것은 없었다.

대조의 결론(결정은 아직이다). 스킬은 셋이 같은 표준이라 그대로 호환이고 우리 쪽 차이는 `plugin.toml` 넉 줄뿐이다. MCP는 서버가 같은
규약이라 호환이고 설정 파일 모양만 셋이 다르며, 플러그인 묶음 안의 `mcp.json`(`mcpServers` 맵, `type`과 `command`/`url`)은 Claude
Code와 Codex가 같은 모양이라 그것을 읽으면 둘 다 들어온다. 우리에게는 HTTP 서버 칸(보고서 6위 원격 MCP)과 `env`·`${VAR}` 치환이
없다. 플러그인 묶음은 Claude Code 형식(`.claude-plugin/plugin.json`)을 Codex가 그대로 읽으므로, 우리가 Claude Code 형식을 읽으면
Codex의 Claude 호환 플러그인도 들어오고, agent-plugins.org 이식형(루트 `plugin.json`)까지 읽으면 셋이 겹친다. 에이전트 정의만
호환이 없다. Claude Code는 markdown 머리말, Codex는 TOML이고 서로 읽지 않는다. 우리 선언형 에이전트가 Claude Code의 `agents/*.md`
(이름·설명·도구·모델·본문 프롬프트)를 읽으면 Claude Code 플러그인의 에이전트는 들어오고 Codex 쪽은 둘째 읽기가 따로 필요하다.
묶음에서 셸을 실행하는 요소(hooks, monitors, bin, headersHelper, 마켓플레이스 source command)는 MCP stdio의 `command`를 빼고 실행하지
않는 것이 skill-plugin의 `scripts/` 미실행과 같은 선이다. 묶음을 어떻게 들일지(우리 폴더로 풀어 `plugin.toml`을 만드는 들여오기 vs
묶음을 제자리에서 읽는 로더)는 설계 라운드의 질문이다.

> 사용자: 그럼 위임·호출 handoff, 제어권 관리는 필요 없다는 거야?

답의 요지(결정은 아직이다). 위임·호출(맡기기)은 셋째 뜻이라 필요하고 이미 골랐다. 필요 없는 것은 "실행 안에서 제어권이 오가는
엔진"(Command/goto 핸드오프, 그룹 챗, 그래프 상태 공유)이다. 우리 보장이 실행 단위라(주체만 결정 ADR 0023, 에이전트 매니페스트의
승인 목록, 실행마다 트레이스와 재생 대조) 실행 중간에 에이전트가 바뀌면 어느 에이전트의 승인 정책을 거는지와 재생 대조가 흐려진다.
그러나 그 장면(상담→결제)은 필요하고 실행 경계에서 결정적으로 된다. 지금 코드는 요청마다 에이전트 이름을 들고(`channel/http/
bodies.py:28`), 이어 가기에서도 사이트의 에이전트 목록 안이어야 하며(ADR 0023:45), 대화 고리는 다른 에이전트의 실행을 품을 수
있다(ADR 0022:82). 그래서 위젯이 다음 에이전트를 고르면 오늘도 된다. 빠진 것 둘이 Notion의 "제어권 관리"가 우리 말로 줄어든 것이다.
앞 에이전트가 "다음은 결제"를 말하는 결정적 자리(출력의 구조화된 칸을 위젯·사이트가 따르는 것), 그리고 다음 에이전트가 앞 맥락을
얼마나 받나(ADR 0022가 대화 전체 넘김을 거부했으니 넘김 메모 하나만 넘기는 모양이 후보). 전체 기능 후보에는 "실행 경계의 에이전트
넘김(다음 에이전트 + 넘김 메모)"으로 작게 넣자고 제안했다.

> 사용자: 후보에 넣어. 그러면 그래프 상태 공유, 그룹 챗, goto식 핸드오프는 우리는 안하는거야?

라운드 밖의 결정: "실행 경계의 에이전트 넘김(다음 에이전트 + 넘김 메모)"을 전체 기능 후보에 넣는다. 답의 요지: 셋은 런타임 기능으로
만들지 않는다. 그래프 상태 공유는 에이전트가 자기 교환만 아는 규칙(ADR 0022)과 트레이스가 유일한 원천이라는 원칙 V 밖에 새 저장
개념을 세우고, 그룹 챗은 다음 발화자를 고르는 엔진이라 보고서가 만들지 말라고 한 범용 오케스트레이션의 알맹이이며, goto식 핸드오프는
실행 단위 보장을 흐린다. 각 장면은 맡기기(리드가 결과를 모은다)와 실행 경계의 넘김으로 덮는다. 남는 길: 에이전트 플러그인이 제 코드
안에서 어떤 프레임워크를 쓰든 그 실행은 우리에게 실행 하나이고, 그 안의 모델·도구 호출은 `ctx.llm`·`ctx.tool`을 지나므로 호출마다의
보장은 그대로이며, 그 안의 역할 나눔은 보장하지 않는다(보장의 경계, 필요한 순간에 다룬다).

> 사용자: 그래프 상태 공유는 필요하지 않아? 트레이스로 하는 것보다 그래프 상태 공유가 더 별로야?

답의 요지(결정은 아직이다). 트레이스는 공유 상태의 대체물이 아니다. 트레이스는 덧붙이기만 하는 기록이고, 그래프 상태는 여럿이 읽고
고치는 작업물이라 서로 다른 것이다. 공유 상태가 더 나은 장면은 있다. 에이전트 여럿이 계획·할 일·발견을 한 구조에 쌓아 가는 긴
일에서, 모든 것을 리드의 프롬프트와 도구 결과로 통과시키면 토큰이 들고 구조가 깨진다. 더 별로인 것은 상태 공유 자체가 아니라 "중재를
지나지 않는 둘째 통로"다. 엔진 안의 상태 객체는 에이전트끼리 우리 모르게 글을 주고받는 길이라 중재·기록 밖이고(인젝션 통로), 재개는
트레이스를 재생해 N번째 호출을 N번째 기록과 대조하므로(ADR 0009:22) 상태가 트레이스 밖에 살면 재생이 그 상태를 복원하지 못한다. 포트
다섯에 트레이스 밖 저장소가 없다(`core/ports.py`). 그래서 모양은 둘로 가른다. 공유 작업물은 도구를 지나는 것(MCP 파일·DB 서버)으로
두면 호출마다 승인·상한·기록이 걸리고 재생에 들며, Claude Code의 서브에이전트가 파일로 나누는 것과 Anthropic의 파일시스템 마운트
메모리(보고서 25행, 검색 요약)와 같은 자리다. 엔진의 상태 객체와 리듀서는 만들지 않는다. 뒤에 "작업 상태"가 정말 필요해지면 상태를
이벤트의 접기로 두어(상태 변경이 이벤트, 상태는 그 합) 원천을 하나로 지키는 길이 있고 그때 ADR로 연다.

> 사용자: 근데 Agent OS 서버를 2개 이상 띄우면 공유 상태가 필요한거 아니야?

답의 요지(결정은 아직이다). 그렇다. 다만 그것은 에이전트끼리의 그래프 상태가 아니라 서버 층의 기반 상태다. 지금 설계는 프로세스
하나를 전제로 적어 두었다. 실행 등록부는 프로세스 메모리이고 다시 시작하면 빈다(`channel/http/runs.py:14`, ADR 0012), 상한의 셈도
프로세스 메모리이며 "워커가 하나라 충분하고(ADR 0014)"라 적혀 있다(`channel/http/limits.py:40`), 켜짐 파일 쓰기는 한 프로세스 안의
이벤트 루프가 줄세운다(ADR 0017:52), 트레이스는 로컬 디렉터리의 JSONL이다. 서버 둘이면 나뉘는 것은 트레이스(원천), 도는 실행이 어느
인스턴스에 있는지(등록부), 상한의 셈, 운영자 파일, 플러그인 디렉터리다. 트레이스가 유일한 원천이라 TraceStore 어댑터를 공유
저장소로 바꾸면 대화 고리·재개·재구독이 함께 따라오고, 재개가 트레이스 재생이라(ADR 0009) 멈춘 실행을 어느 인스턴스에서든 이어 갈 수
있는 것이 우리 설계의 이점이다. 등록부와 셈은 공유 카운터나 사이트·주체별 라우팅이 따로 필요하다. 엔진 안의 그래프 상태를 두지 않은
앞의 결정이 여기서 도움이 된다(프로세스 안의 상태 객체는 다중 인스턴스에서 가장 먼저 깨진다). PRD와 보고서는 "작은 자체 호스팅
프로세스"를 자리로 두고 멀티테넌시를 미뤘으므로, 다중 인스턴스는 이번 전체 기능에 넣지 않고 "프로세스 하나"를 보장 문장의 전제로
밝히며 바꿀 자리(TraceStore 포트, 등록부·셈, ADR 0014의 워커 하나)를 적어 두자고 제안했다.

> 사용자: 범위에 넣는다

라운드 밖의 결정: 다중 인스턴스(Agent OS 서버를 둘 이상 띄우는 것)를 전체 기능 후보에 넣는다. 설계 라운드에서 가를 가지는 넷이다.
트레이스를 공유 저장소에 두는 TraceStore 어댑터, 실행 등록부와 상한 셈의 공유(공유 카운터 vs 사이트·주체별 라우팅), 운영자 파일과
플러그인 디렉터리의 배포, ADR 0014의 "워커 하나" 전제를 이력으로 바꾸는 것.

여기까지 라운드 밖에서 전체 기능 후보로 확정한 것: 선언형 에이전트, 멀티 에이전트 맡기기(셋째 뜻. 한 턴의 도구 호출 병렬이 전제),
Claude Code 형식 호환(MCP 설정, 스킬 폴더, 플러그인 묶음. Codex의 Claude 호환 플러그인이 함께 들어온다), 실행 경계의 에이전트
넘김, 다중 인스턴스, 운영자의 승인 정책 파일(저자의 것을 풀지 못한다). Notion 대조에서 "들어가야 할 것"으로 낸 나머지(MCP 서버 신뢰
수준과 스코프, 토큰·비용 상한과 승인 만료, 트레이스의 소요시간·비용, 모델의 기밀 등급·능력 선언, 주체의 MCP 서버 전파, 트레이스 보존
기간)와 보고서 순위 가운데 아직 말하지 않은 것(OpenTelemetry 내보내기, 트레이스 재생 평가, 값 기반 비밀 마스킹)은 후보 확정을 아직
받지 않았다.

Langfuse 사실(WebFetch 웹 요약, 2026-11-04). https://langfuse.com/docs/opentelemetry/get-started: OTLP 트레이스를 `/api/public/otel`
(신호별은 `/api/public/otel/v1/traces`)에서 HTTP/protobuf와 HTTP/JSON으로 받고 gRPC는 아직 아니다. "Any OpenTelemetry compatible
instrumentation"을 받으며 Collector를 거쳐도 된다. 자체 호스팅은 v3.22.0 이상이면 된다. Langfuse SDK는 "a thin layer on top of the
official OpenTelemetry client"다. https://langfuse.com/self-hosting: Docker Compose(로컬·시험용, 단일 VM), 프로덕션은 Kubernetes(Helm)·
AWS·Azure·GCP. 구성 요소는 Web, Worker, PostgreSQL, ClickHouse, Redis/Valkey, S3. 오픈소스이고 일부 부가 기능(EE 표시: Organization
Creators, Instance Management API, UI Customization)은 라이선스 키가 필요하다. 라이선스 이름은 그 페이지에 없다.

답의 요지(결정은 아직이다). 도입하되 자리는 "OpenTelemetry 내보내기(후보 13)의 첫 대상"이다. 보고서는 자체 관측 백엔드를 만들지
말고 OTel 내보내기를 3위로 두었고, Langfuse가 OTLP를 그대로 받으므로 런타임에 Langfuse 전용 코드가 한 줄도 들지 않는다. 하지 않을
것 셋: Langfuse SDK를 core나 어댑터에 들이는 것(OTel 옆의 둘째 내보내기 길이고 벤더 결합), 프롬프트 관리를 Langfuse로 옮기는 것
(프롬프트는 플러그인 폴더의 것, ADR 0003), 트레이스의 원천을 Langfuse로 바꾸는 것(원칙 V, 재개는 우리 트레이스의 재생). 순서의
전제: 토큰·비용 칸(후보 8·9)이 있어야 Langfuse의 비용 화면이 차고, 값 기반 마스킹(후보 15)이 내보내기 전에 걸려야 프롬프트 속
비밀이 바깥으로 나가지 않는다. 후보 13의 수락 기준으로 "로컬 Docker Compose의 Langfuse에 우리 트레이스가 run_id·모델·도구·토큰과
함께 뜬다"를 제안했다. Langfuse 자체 호스팅은 서비스 여섯이라 우리 "작은 자체 호스팅 프로세스"보다 무거우니 운영자의 선택이지
필수 구성이 아니다. 트레이스 재생 평가(후보 14)는 우리 런타임이 돌려야 하는 것이라 Langfuse의 데이터셋·실험이 대신하지 못하고,
채점(LLM-as-judge)은 내보낸 트레이스 위에서 Langfuse가 할 수 있다.

> 사용자: 재개가 우리 트레이스를 재생하는 방식이라했는데? 원래 다들 트레이스로 재개를 해?

답의 요지. 아니다. 에이전트 프레임워크 대부분은 상태의 스냅샷(체크포인트)을 저장하고 거기서 이어 간다. 보고서 79행(보고서의
판단)과 조사 노트에 적힌 것: LangGraph는 체크포인터와 interrupt이고 재개하면 그 노드가 처음부터 다시 돌아 부수효과가 다시 일어난다.
OpenAI Agents SDK(JS)는 RunState를 직렬화해 클라이언트가 건넨 스냅샷으로 재개한다(노트 open_source 105행). Google ADK는 한 턴의 승인
대상 여럿 가운데 하나만 답하고 넘어간다. AIOS는 생성 도중 스냅샷을 떠 두고 복원한다(노트 concept 41·105행, 논문 원문). Microsoft
Agent Framework는 워크플로 체크포인팅(노트 91행, 자사), CrewAI Flows는 저장한 상태와 `/resume`(노트 72-73행)이다. 기록을 재생해
처음부터 다시 도는 방식은 지속 실행(durable execution) 계열(Temporal, Azure Durable Functions 등. 이 이름들은 기억이다)의 것이고, 조사
노트는 그 계열을 범위에서 다루지 않았다고 적었다(concept 119행). Pydantic AI의 Temporal·Prefect 통합이 그 계열을 에이전트에 붙인
예다(노트 86-88행). 우리는 그 계열의 방식을 실행 하나에 적용한 것이라 에이전트 프레임워크 사이에서는 드물고 소프트웨어 전체로는
낯설지 않다. 고른 이유는 ADR 0009의 거부 안 다섯이다. 프로세스 안 대기(프로세스가 죽으면 실행도 죽는다), 메시지 목록만 저장(끝을
낼 에이전트 코드가 없다), 재생 없이 모델을 다시 부름(승인한 것과 다른 호출이 나온다), 별도 체크포인터 포트(같은 사실이 두 곳, 원칙
V), LangGraph interrupt(ADR 0001의 타입 문제). 치르는 값도 적었다. 에이전트 코드가 같은 입력에 같은 호출을 내야 하고(`ctx.now()`는
재생 구간에 시작 시각을 돌려준다. ADR 0009:23), 재개마다 에이전트 코드를 처음부터 다시 돌리며(모델·도구 비용은 없다), 기록이
프롬프트와 결과를 통째로 들어 마스킹이 중요하고, 에이전트 판이 바뀌면 옛 실행을 재개하지 못한다(대조 실패로 안전하게 끝난다).

> 사용자: 다중 인스턴스에서는 체크 포인터가 괜찮지 않아?
> 아니면 재개도 플러그인 방식으로 할 수 있나?

답의 요지(결정은 아직이다). 첫째, 다중 인스턴스는 체크포인터 쪽에 유리하지 않다. 둘 다 공유 저장소가 필요하고, 재생은 멈춤이 실행을
끝내 인스턴스에 남는 상태가 없어 어느 인스턴스든 트레이스만 읽으면 재개할 수 있다(인스턴스가 무상태라 확장에 가장 좋은 모양).
체크포인터는 상태 스냅샷이라는 둘째 산출물을 두어 원천이 둘이 되고(원칙 V, ADR 0009의 거부 안), 코드 에이전트의 코루틴은 스냅샷으로
뜨지 못해 LangGraph도 노드를 처음부터 다시 돈다. 다중 인스턴스의 진짜 문제는 같은 실행을 두 인스턴스가 동시에 재개해 다음 실제
호출이 두 번 나는 경합이고(보고서 79행이 "프로세스 사이의 경합은 알려진 한계, 지금은 워커 하나로 막는다"로 적었다), 체크포인터도
같은 경합을 가지며, 푸는 법은 공유 저장소의 run_id 임대(lease)다. 다중 인스턴스 설계의 가지에 이것을 더한다. 둘째, 선언형
에이전트에서는 둘이 하나로 모인다. 런타임이 루프를 돌므로 메시지 목록이 곧 상태이고, 그 목록은 트레이스에 이미 있어(`LlmCalled`의
prompt·text·tool_calls, `ToolCalled`의 args·content) 재개는 트레이스를 접어 메시지 목록을 만들고 이어 도는 것이 된다. 에이전트 코드를
다시 돌릴 것이 없어 재생 비용도 사라지고 둘째 저장소도 없다. ADR 0009가 "메시지 목록만 저장"을 거부한 이유(끝을 낼 에이전트 코드가
없다)는 코드 에이전트의 것이라 선언형에는 걸리지 않는다. 셋째, 재개를 플러그인(`plugins/`의 종류)으로 두지는 않는다. 재개는 "승인한
것이 실행되는 것"을 대조로 지키는 보장의 일부라(`core/replay.py` 독스트링) 갈아 끼우는 코드에 두면 건너뛸 수 있게 되고, 플러그인은
sdk만 import하는데(`tests/test_plugins_boundary.py`) 재개는 core의 포트가 필요하다. 갈아 끼우는 것은 저장소(TraceStore 어댑터)이고
전략(재생 vs 접기)은 에이전트 종류에 따른 core의 동작이다. 에이전트 플러그인이 제 코드 안에서 자기 체크포인터를 쓰는 것은 막지
않지만, 우리 재생은 그 코드를 다시 돌리므로 그 안의 상태가 우리 호출 열과 어긋나면 대조 실패로 끝난다(보장의 경계).

> 사용자: 우리는 재개를 하면 처음부터 다시 다 돌리는 방식인거야?

답의 요지(ADR 0009:8과 `core/replay.py` 독스트링을 읽었다). 에이전트 코드는 처음부터 다시 돌지만, 이미 한 모델·도구 호출은 다시
하지 않고 트레이스의 기록을 돌려주며 보내려던 것이 기록과 같은지 대조한다. 기록이 소진되는 자리가 멈췄던 자리이고 거기서부터 실제
호출이 시작된다. 그래서 모델 비용과 부수효과는 다시 나지 않고, 다시 드는 것은 에이전트 코드의 실행과 트레이스 읽기뿐이다.

> 사용자: 갈아 끼울 수 있는 것은 저장소(트레이스 어댑터)는 추가해줘.

라운드 밖의 결정: 전체 기능 후보에 18번 "갈아 끼우는 트레이스 저장소(TraceStore 어댑터)"를 더한다. 후보는 열여덟이다. 코드에 대 본
사실: `TraceStore` 포트는 이미 있고 독스트링이 "첫 어댑터는 JSONL 파일"이라 적으며 쓰기·읽기·열거를 한 타입이 강제한다
(`core/ports.py:304-312`). 포트를 더하는 것이 아니라 어댑터를 더하는 것이라 ADR 0012(포트는 다섯 그대로)에 맞고, ADR 0003은
플러그인의 원천을 파일시스템으로 둔 것이지 트레이스의 저장 매체를 못박지 않았다(그 ADR에 "트레이스"가 없다, grep). 이 후보는 5번
다중 인스턴스의 첫 가지이고(공유 저장소), 12번 보존 기간의 자리이기도 하다(지우기는 어댑터의 일). 설계 질문은 셋이다. 둘째 어댑터의
매체(DB, 공유 파일 시스템, 객체 저장소), 동시 재개의 run_id 임대를 어댑터가 드는지 포트에 메서드가 느는지, 읽기 쪽 성능(지금 JSONL
열거는 디렉터리의 모든 파일을 연다. `adapters/jsonl.py:142-145`).

  그대로). `grep -A 22`와 대기열 찾기(`--search` 다섯, 그중 `스크래치`가 넓어 51행)의 큰 출력을 훅이 알렸다.
- **기각, 일회성.** Notion 연동(`notion-fetch`)이 사용자의 기능 목록 페이지에 404를 내어 내장 브라우저에서 사용자가 로그인한 뒤 읽었다.
  페이지 공유는 사람 몫이고 한 번이라 환경 개선이 아니다.
- **일지에만.** 라운드 답 넷을 받은 직후 컨텍스트 압축이 와서, 옮기기는 압축 뒤 같은 턴의 첫 호출로 했다. 압축 요약이 설명 원문을 그대로
  들고 있어 잃은 것은 없다. 훅의 경고("미루면 요지만 남는다")가 맞는 장면이었고 처방은 이미 그 훅과 grilling "옮길 때"에 있다.
- **만료.** `uv run python tools/queue_open_rows.py`를 이 워크트리와 `git fetch origin` 뒤 `--ref origin/main`으로 돌려 두 출력에 모두 든
  열두 행(102 372 373 374 375 380 382 383 385 387 388 392, 승인 날짜 2026-10-20)을 `만료 2026-11-04`로 닫았다. origin/main은 이 브랜치의
  기준(`2ba2780d`)과 같았다. 편집은 스크래치 스크립트(행 번호로 찾아 취소선과 만료 표지, 528의 승인 칸, 564 추가)로 했고
  `tools/check_md_tables.py`가 초록이다.

정해진 것.
- 보장은 건너뛸 수 없는 중재·강제·기록이고 인터뷰 범위는 전체 기능 설계다("라운드" 절의 1라운드).
- 전체 기능 후보는 열여덟이다. 1~17은 "전체 기능 후보 열일곱" 목록, 18(갈아 끼우는 트레이스 저장소, TraceStore 어댑터)은 "갈아 끼울 수
  있는 것은 저장소" 인용 아래다. 미룬 것·덮은 것·만들지 않는 것은 그 목록 아래 줄이다.
- 순서는 묶음 다섯이다. ① 신뢰·강제 7·6·10·11, ② 비용·기록 9·8·15·12·18, ③ 바깥 연결 13·3·1, ④ 여러 에이전트 2·4·14, ⑤ 확장·채널
  5·16·17. 묶음 안의 순서는 라운드에서 정한다.
- 깊이는 열여덟 전부를 이번 인터뷰에서 설계하는 것이다(추천과 다른 답). 묶음 경계마다 이 "다음"을 갱신해 인계에 대비한다(ADR 0033).
- 문서 모양. PRD에 "보장하는 것" 절과 성공의 정의 줄 하나를 더하고 "만들지 않는 것" 줄에 셋(실행 안 제어권 넘김, 엔진의 상태 객체, 범용
  오케스트레이션)을 더한다(사용자 승인). `CONTEXT.md`의 Agent OS 정의에 모델과 보장을 더한다.
- 라운드 밖의 결정(각 인용 아래). 운영자는 저자의 `requires_approval`을 풀지 못한다. 멀티 에이전트는 셋째 뜻(리드가 맡기고 병렬로 받는다)이고
  한 턴의 도구 호출 병렬이 전제다. MCP·스킬·플러그인 묶음은 Claude Code의 디스크 형식과 호환하고 Codex의 Claude 호환 플러그인이 함께
  들어온다. 그래프 상태 공유·그룹 챗·goto 핸드오프·엔진 상태 객체는 만들지 않는다. 공유 작업물은 도구(MCP 서버)를 지난다. Langfuse는 13의
  첫 대상이고 SDK를 들이지 않는다. 재개는 트레이스 재생 그대로이고(ADR 0009) 저장소만 어댑터로 갈아 끼운다.

남은 라운드. 묶음 ①부터이고 한 호출에 질문 넷까지다(grilling). 아래는 이 세션이 셈한 frontier이고 새 세션이 다시 셈해 고친다.
1. 묶음 ① 안의 순서(7·6·10·11). 기대는 관계의 후보: 6은 7의 칸을 쓸 수 있고(운영자 파일이 서버 신뢰 수준도 들 수 있다), 11은 7의 스코프를
   전제한다.
2. 6 운영자의 승인 정책 파일. 파일의 자리와 이름(켜짐 파일 `disabled.toml`처럼 `plugins/` 루트의 운영자 파일을 하나 더 두는지. ADR 0017의
   "파일 이름은 내용 하나"), 규칙의 모양(Claude Code의 `도구(인자 패턴)`과 deny→ask→allow 첫 매치를 참조할지), 합치는 법(매니페스트
   `requires_approval`과 합집합이고 집행 자리는 `core/run.py`의 승인 판정), 사이트 파일 `agents` 허용 목록과의 관계(Notion 대조의 "조합
   차단"이 여기 드는지).
3. 7 MCP 서버의 신뢰 수준과 스코프. 칸의 자리(매니페스트 `[server]`인지 운영자 파일인지. 저자와 운영자의 가름은 ADR 0017), 값의 모양(수준의
   단계 수, 스코프가 "어느 에이전트가 어느 서버·도구를"인지), 서버의 자기 신고(MCP 애노테이션)를 쓰지 않는 것(MCP 명세가 불신하고 Claude
   Code도 권한에 쓰지 않는다. 그 절의 근거), skill-plugin의 본문 신뢰 수준과 같은 축인지.
4. 10 모델의 기밀 등급·능력 선언. 모델 매니페스트의 새 칸(지금은 `provider`·`model_id`·`max_tokens`·`temperature`, `sdk/manifest.py:126`),
   등급이 맞대는 상대(사이트의 접근 등급인지, 도구 결과에 붙는 표시인지), 집행 위치(core가 실행의 모델을 세울 때), 둘째 제공자와의
   관계(`ModelProvider`는 지금 anthropic 하나, `sdk/manifest.py:32-35`).
5. 11 주체의 MCP 서버 전파. 넘기는 길(stdio 서버의 환경 변수·인자인지 MCP 요청의 `_meta`인지), `adapters/mcp.py`가 principal을 모르는 지금
   구조에서 포트 시그니처가 바뀌는지(ADR 0012는 포트 다섯 고정), 서버마다 켜고 끄는지(7의 스코프와 맞물린다), 트레이스에 무엇이
   남는지(원칙 V).
6. 보장의 경계. 사용자가 "필요한 순간에"로 미뤘다. 지금까지 닿은 것: 에이전트 코드 안의 일(플러그인이 안에서 쓰는 프레임워크, 그 안의
   상태)은 보장 밖이고, 재생 대조가 깨지면 실패로 끝난다. 묶음 ①의 어느 질문이 여기 닿으면 그 라운드에서 묻는다.
