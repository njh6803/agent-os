2026-10-12-13은 `git show origin/docs/admin-design-direction:<경로>`로 스크래치에 꺼내 읽었다. `grill-with-docs`는 사람만
부르는 스킬이라 그 파일을 읽고 `grilling`과 `domain-modeling`을 불렀다.

## 조사

서브에이전트 둘을 나란히 띄웠다.

- **스킬 배치(claude-code-guide).** 공식 문서로 본 것: 사용자 레벨 `~/.claude/skills/`가 프로젝트 레벨을 이긴다(skills).
  서브에이전트는 `AskUserQuestion`을 쓰지 못한다(sub-agents). 압축 뒤에는 부른 스킬의 본문만 스킬마다 5,000토큰까지 다시
  실린다(context-window). 보고가 데스크톱 앱의 추가 폴더를 빠뜨려 large-codebases를 직접 읽었다. 다른 저장소의 스킬을 싣는
  것은 CLI의 `--add-dir`·`/add-dir`이고 설정의 `additionalDirectories`는 싣지 않는다. 데스크톱 앱에서 더한 폴더가 어느
  쪽인지는 문서에 없다.
- **사람 몫 분류(Explore).** 런북 단계마다 사람만, 허락, 결정, 세션 혼자, 스킬이 맡음으로 갈랐다. 원격에 기대지 않는 사람
  몫(gh 로그인, 공개 결정, CodeRabbit CLI 로그인과 좌석)은 시작 때 모을 수 있고, 시크릿 등록·CodeRabbit App·보호 브랜치·첫
  PR의 Claude 코멘트는 원격이나 첫 PR 뒤에만 된다. 첫 킥오프는 세션 셋이었다. 첫 세션이 0~8단계와 첫 설계 인터뷰를 했고
  맥락이 바닥나 이어진 적이 한 번 이상 있으며, 끊긴 자리는 사람만 부르는 스킬(`/to-spec`, `/implement`) 앞이었다(일지와
  세션 기록을 읽었다). 8단계의 첫 커밋을 7단계가 등록한 `hook_git_main_commit`이 막을 수 있다고 짚었다(어림).

그 둘을 손으로 대 봤다.

- 임시 폴더에서 `git init` 뒤 `git branch --show-current`가 `main`을 냈다. 훅은 브랜치 이름만 보므로(`deny_reason`을 읽었다)
  런북대로면 첫 커밋이 막힌다. `main`은 Git for Windows의 시스템 설정(`C:/Program Files/Git/etc/gitconfig`의
  `init.defaultBranch=main`)에서 왔다는 것을 셀프 리뷰 뒤에 `git config --show-origin`으로 봤다.
- `gh api users/njh6803/settings/billing/actions`는 410("This endpoint has been moved")이고
  `gh api users/njh6803/settings/billing/usage`는 달마다 쓴 Actions 분을 냈다. 런북 1단계의 Billing 화면 확인은 세션이 명령으로
  할 수 있다.

## 인터뷰

추천은 모두 맨 앞이었고 사용자는 모두 추천을 골랐다.

> 사용자: (형태 — 자동 진행을 무엇으로 만들까요?) "얇은 진행 스킬 하나 (Recommended)" — 설명: KICKOFF.md와 kickoff/가 단계 내용의 원천으로 남고, 스킬은 단계를 순서대로 읽어 진행하는 규율(다음 단계로 넘어가기, 멈출 자리, 선택 화면, 진행 상태 기록)만 가집니다. 단계 내용을 복제하지 않습니다. '세 번 돌린 뒤에만 도구' 규칙은 이 스킬만 예외로 두도록 개정하고 ADR에 남깁니다.

> 사용자: (멈춤 — 사람만 할 수 있는 일(로그인, 토큰·시크릿, GitHub 앱 설치와 OAuth, 플랜 확인)에 닿으면 진행을 어떻게 멈추고 이어 갈까요?) "선택 화면 + 기계 확인 (Recommended)" — 설명: 그 자리에서 멈추고, 할 일과 어디서 하는지를 보인 뒤 '했다 / 건너뛴다' 같은 선택 화면을 띄웁니다. '했다'를 고르면 세션이 확인 명령(예: gh secret list의 이름과 시각, coderabbit auth status의 Seat)으로 대 보고, 맞지 않으면 다시 묻습니다. 건너뛴 일은 진행 상태에 남아 끝에 다시 보입니다.

> 사용자: (범위 — 자동 진행의 범위는 어디까지인가요?) "첫날 0~8단계 + 9단계로 넘김 (Recommended)" — 설명: 진행 스킬이 0~8단계를 순서대로 돌리고 끝에서 첫 기능의 설계 인터뷰(9단계 1)로 넘깁니다. 9단계 안의 흐름은 지금의 스킬 사슬(next-session·open-session이 세션을 잇는다)과 PR #186이 넣은 디자인 도구 차례를 그대로 씁니다. 사람만 부르는 스킬의 관문은 건드리지 않습니다.

> 사용자: (스킬 자리 — 진행 스킬을 어디에 두어 빈 새 프로젝트 폴더에서도 부를 수 있게 할까요?) "사용자 레벨 짧은 스킬 (Recommended)" — 설명: 0단계(기계당 한 번)에서 ~/.claude/skills/kickoff/SKILL.md를 만들고, 이 스킬에는 '런북 저장소의 진행 규율 파일(예: kickoff/runner.md)을 읽고 따른다'는 내용과 그 경로만 적습니다. 데스크톱 앱이든 CLI든 빈 폴더에서 연 세션에서 부를 수 있고, 진행 규율을 고쳐도 전역 스킬을 다시 복사할 필요가 없습니다. 사용자만 부르게(disable-model-invocation) 두면 다른 프로젝트의 컨텍스트에는 실리지 않습니다. 압축 뒤에는 진행 규율 파일을 다시 읽어야 합니다.

> 사용자: (진행 상태 — 어느 단계까지 끝났는지를 어디에 적어, 세션이 끊기거나 압축된 뒤에도 이어 가게 할까요?) "새 프로젝트의 진행 파일 (Recommended)" — 설명: 1단계에서 진행 파일(예: .scratch/kickoff.md)을 만들고, 단계마다 상태(끝남 / 건너뜀과 이유 / 사람 몫 대기)를 적습니다. 스킬을 다시 부르면 이 파일에서 첫 미완 단계를 찾아 이어서 진행합니다. 커밋하므로 8단계 뒤에는 원격에도 남습니다. 일지는 지금처럼 사람의 프롬프트와 갈린 곳을 적는 데 씁니다.

> 사용자: (4·5단계 — 4·5단계(setup, 헌법 인터뷰)도 선택 화면으로 묻게 하려면 어떻게 할까요?) "진행 스킬이 묻는 방식을 정함 (Recommended)" — 설명: 진행 규율에 '단계 안에서 부르는 스킬이 글로 물으라고 해도, 결정은 추천을 맨 앞에 둔 선택 화면으로 올린다'를 둡니다. 사람만 부르는 스킬(setup-matt-pocock-skills, grill-me)은 세션이 그 스킬 파일을 읽어 따릅니다(첫 킥오프와 open-session의 선례). 복사 순서는 지금 그대로입니다.

> 사용자: (검증 — 이번 변경을 무엇으로 검증할까요?) "부분 실행 + 재개 시험 (Recommended)" — 설명: 임시 폴더에서 0~2단계만 진행 스킬로 돌리고, 세션을 끊었다가 새 세션에서 스킬을 다시 불러 진행 파일에서 이어 가는지 봅니다. 사람 몫 멈춤은 1단계의 플랜 확인(GitHub Billing 화면)으로 한 번 확인합니다. 단계의 내용은 런북 그대로이므로, 진행 규율만 실제로 시험합니다.

> 사용자: (사람 몫 — 원격 저장소에 기대지 않는 사람 몫을 시작할 때 모아서 처리할까요?) "시작 때 '준비'로 모음 (Recommended)" — 설명: 0단계 앞에 준비 묶음을 둡니다. gh 로그인, 공개/비공개 결정(비공개면 Actions 분량을 명령으로 확인), CodeRabbit CLI 로그인과 좌석을 한 번에 처리하고 기계로 확인합니다. 공개 여부에 기대는 7·8단계(.coderabbit.yaml, 보호 브랜치)도 앞에서 정해집니다. 원격이나 첫 PR에 기대는 것(시크릿, CodeRabbit App, 보호, Claude 코멘트 확인)과 /context는 그 단계에서 멈춥니다.

> 사용자: (멈춤 표지 — 진행 스킬이 어디서 멈춰야 하는지를 무엇으로 알게 할까요?) "런북 단계마다 '사람 몫' 줄 (Recommended)" — 설명: KICKOFF.md의 단계마다 사람만 하는 일, 허락이 필요한 일, 결정과 그 확인 명령을 정해진 모양의 줄로 적습니다. 진행 스킬은 그 줄에서 멈춥니다. 런북이 원천인 채로 멈출 자리가 글에 드러나고, 줄의 모양은 검사로 볼 수 있습니다.

> 사용자: (세션 경계 — 킥오프를 몇 개의 세션으로 진행할까요?) "한 세션 + 9단계에서만 새 세션 (Recommended)" — 설명: 준비부터 8단계까지는 한 세션에서 진행하고, 압축은 스킬 본문의 재주입과 진행 파일로 견딥니다. 세션이 끊기면 사람이 /kickoff를 다시 쳐서 이어 갑니다. 9단계로 넘길 때는 7단계에서 복사한 next-session이 지시문을 내고 open-session이 새 세션을 엽니다.

> 사용자: (첫 커밋 — 8단계의 첫 커밋을 main 커밋 차단 훅이 막는 문제를 어떻게 풀까요?) "훅이 첫 커밋을 허용 (Recommended)" — 설명: 커밋이 하나도 없는 저장소(git rev-parse --verify HEAD가 실패하는 경우)에서는 hook_git_main_commit이 막지 않게 합니다. 훅이 막으려던 사고(다른 세션이 체크아웃을 main으로 옮긴 뒤의 커밋)는 커밋이 없는 저장소에서는 일어나지 않습니다. agent-os의 훅과 테스트를 고치면 새 프로젝트가 그대로 복사해 갑니다.

> 사용자: (허락 범위 — 세션이 하되 사람의 허락이 필요한 일 가운데, 어디까지 진행 스킬이 따로 허락 화면을 띄울까요?) "원격과 저장소 밖만 (Recommended)" — 설명: 원격에 드러나는 일(저장소 만들기, 푸시, 브랜치 보호, PR, 병합, 봇을 부르는 코멘트)과 저장소 밖을 바꾸는 일(0단계의 전역 플러그인·전역 스킬, 사용자 레벨 스킬 만들기)에는, 무엇을 어디에 하는지 보인 선택 화면을 띄웁니다. 새 프로젝트 안의 패키지 설치와 템플릿 내려받기는 Claude Code의 권한 프롬프트에 맡깁니다.

> 사용자: (첫 시작 — 진행 스킬이 아직 없는 새 기계에서는 킥오프를 어떻게 시작할까요?) "런북 경로를 읽으라는 한 줄 (Recommended)" — 설명: 사람이 런북 저장소를 clone하고, 새 프로젝트 폴더에서 연 세션에 '<clone>/kickoff/runner.md를 읽고 따르라'는 한 줄을 붙여 넣습니다. 진행 규율의 0단계가 사용자 레벨 스킬을 만들어 그 뒤로는 /kickoff로 시작하고 이어 갑니다. KICKOFF.md 머리에 그 한 줄을 적습니다.

2단계까지로 바뀌었고 사용자가 그 요약을 확인했다.

- 둘째 라운드의 검증 추천은 1단계의 Billing 화면을 사람 몫 멈춤의 시험으로 들었다. 셋째 라운드 전에 billing API가 되는 것을

  - ADR 0005 포인터가 문장 가운데에 있다(Nit): 그대로 둔다. 위 CodeRabbit 첫째와 같은 규약이다.
  - ADR과 일지의 요약 표가 겹친다(Nit): 사실과 다르다. ADR에는 표가 없고, 일지의 표는 사용자가 확인한 요약을 글자 그대로 옮긴
    기록이다(grilling "옮길 때").
