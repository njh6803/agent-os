## 적대 검증 워크플로

첫 판(줄 두 개로 표를 판정하는 정규식 검사)을 렌즈 다섯(GFM 칸 나누기, 표의 경계, 줄 구분 문자, pre-commit·CI 통합, 주장과 코드
대조)으로 공격하고 발견마다 반박자 하나를 붙였다. 에이전트 39. 첫 실행은 반박자 17이 모델 한도로 죽었고, 모델을 바꿔 resume하자
끝난 22는 캐시에서 돌아왔다. 결과는 확정 34, 반박 0, nit 14.

- **Major — `\\|`의 파이프를 구분으로 셌다.** 첫 판의 독스트링·테스트는 역슬래시가 역슬래시를 이스케이프하면 그 뒤의 파이프가
  산다는 것을 사실로 고정했는데, cmark-gfm의 칸 스캐너(`(escaped_char|[^|\r\n])+` 최장 일치)와 GitHub 렌더(`gh api markdown`)는 둘 다 한 칸으로 읽었다.
  CommonMark의 인라인 규칙을 블록 단계의 칸 나누기에 옮긴 추론이었다. "awk가 틀린 자리"라고 적은 것도 근거 없는 귀속이었다.
- **경계 쪽이 무더기였다.** `<`로 시작하는 줄을 전부 HTML 블록으로 봐서 `<b>x</b> | 2` 행에서 표를 끊었고, 목록·인용 문단의 게으른
  연속 줄을 표로 통과시켰고, 목록 한 단계 아래 네 칸 들여쓴 표를 코드로 건너뛰었고, 네 칸 들여쓴 닫는 펜스를 닫는 것으로 봤다.
  첫 판이 못 보는 것에 적은 HTML 주석 안의 표는 사실과 반대였다(주석 안의 표를 보고 `-->` 줄을 칸 1로 잡았다).
- **두 검사 모두** 없는 경로·디렉터리·지웠지만 스테이지하지 않은 추적 파일에서 트레이스백으로 죽었다 — 편집 뒤 `pytest`를 치는 이
  저장소의 보통 순서에서 저장소 상태 테스트가 빨강이 된다. "git의 판정과 같다"는 8192바이트였다(git은 8000). BOM 파일의 첫 줄 열이
  하나 밀렸다. 훅이 CPU 수만큼 나뉘어 두세 배 느렸다. 인자 없는 범위(`*.md`)가 훅 범위(`.markdown`·대문자 확장자)와 달랐다.
- **문서.** 파일을 넘기는 훅이라 commit-msg 단계에서 다시 돌지 않는다는 첫 판 일지의 문장은 거짓(커밋 메시지 파일도 text라 그
  단계에서 돈다), "pre-commit만"도
  거짓(pytest의 저장소 상태 테스트가 CI에서 저장소 전체에 돈다), KICKOFF의 "검사 넷"과 "두 번 다 코드 스팬 파이프".

## 규칙을 덧대지 않고 파서를 옮겼다

경계 쪽 발견은 규칙 하나를 고치면 옆 규칙이 새는 모양이었다 — 표가 어디서 시작하고 끝나는지는 줄 두 개가 아니라 컨테이너와 블록의
상태가 정한다. 반박자들이 cmarkgfm을 판정자로 썼으므로 그것을 커밋한 프로브로 만들고, 검사는 cmark-gfm의 줄 처리를 옮겼다. 차분
대조가 옮기며 빠뜨린 것 다섯을 차례로 찾았다. 앞의 셋은 cmark 구현의 버릇이고 뒤의 둘은 GitHub이 켠 기능이다.

1. 게으른 연속 줄은 앞 공백째 문단에 들어간다. 그 줄이 머리 행이 되면 앞 공백이 빈 칸 하나다.
2. 구분 행 모양의 줄이 칸 수로 표를 열지 못한 문단은 그 뒤로 표를 다시 열지 않는다. 빈 줄로 새 문단을 시작하면 열린다.
3. 목록 표식 뒤의 수직 탭·폼 피드는 여백이 아니다(`-\v|`는 표의 머리 행이다).
4. GitHub은 각주를 켜고 렌더한다. 각주 정의는 네 칸 들여쓰기의 컨테이너이고, 참조되지 않은 정의는 렌더되지 않는다(프로브가 참조
   문단을 붙여 살린다).
5. 한 줄짜리 링크 참조 정의만의 문단 아래 `---`는 제목 밑줄이 아니라 문단의 글이다.

생성기가 처음에는 표를 거의 만들지 않았다(3만 문서에 표가 있는 문서 468, 본문 행 33). 컨테이너 안에 표 덩어리를 두고 이어지는 줄을
흔드는 생성기로 바꾸자 절반이 표가 됐고, 어긋남이 1392가지 나왔다가 위의 넷째·다섯째로 0이 됐다.

## 편집 도구가 이스케이프를 날것으로 저장한다

줄 구분 문자 검사의 첫 판과 테스트를 역슬래시-u 이스케이프로 썼는데, 편집 도구(Write)가 U+2028·U+2029를 날것 문자로 저장했다.
pytest는 바이트 리터럴의 비 ASCII로 SyntaxError를 냈고, 새 검사를 그 두 파일에 돌리자 열 자리가 나왔다. 이 일지에서도 한 번 더 —
사고를 설명하려고 이스케이프를 글자 그대로 적은 줄이 잡혔다. PR #58과 같은 모양이다.

이어서 표 검사·그 테스트·프로브에 쓴 BOM·전각 공백·줄바꿈 없는 공백(U+00A0) 이스케이프도 날것이 됐다. 22의 검사는 세 문자만
보므로 이것은 잡지 못했고, Read 출력에 보이지 않는 글자가 있는 것을 눈으로 보고 Grep으로 찾았다. 코드는 그대로 돌았지만 소스에
보이지 않는 문자가 남는 것 자체가 22가 막으려는 사고다. 전부 `chr()` 상수로 바꿨고, 두 검사와 프로브의 독스트링·주석에 그 이유를 적었다.

## 갈린 곳

- **44의 범위.** 44는 "칸 수 검사"였다. 적대 검증 뒤 cmark-gfm의 블록 파싱을 옮긴 약 500줄의 검사가 됐다. 좁게 두면 목록·인용·HTML
  안에서 오탐과 미탐이 같이 나는 것을 확인했기 때문이다. 다른 길은 cmarkgfm을 개발 의존성으로 두고 검사가 직접 부르는 것이다(칸
  수는 sourcepos로 원문 줄에서 센다). 정확도는 그쪽이 높지만 의존성을 더하는 것은 `tech.md`가 ADR을 요구하고, 옮긴 파서는 차분
  대조가 받친다. 의존성 없는 쪽을 골랐다. 사용자가 뒤집을 수 있는 결정이다.
- **cmark의 버릇도 옮겼다.** 2(실패한 문단은 다시 표를 열지 않는다)는 명세에 없는 구현의 성질이다. GitHub이 그렇게 렌더하므로
  검사도 따른다. 그런 문단에서 둘째 시도를 "표로 읽히지 않는다"로 알린다.
- **22의 "텍스트 파일".** git의 판정(8000바이트 NUL)을 따랐다. pre-commit의 text 판정(identify)과는 조금 다르다 — 넘어온 파일 중 NUL이
  있는 것은 조용히 건너뛴다(nit, 남겼다).
- **CI 반영은 별도 워크플로 PR.** 두 검사는 pytest의 저장소 상태 테스트로 이미 CI에서 돈다. 워크플로에 따로 부르는 줄은 러너와 함께

- `\\|`의 파이프는 구분이다 → 내용이다(적대 검증, cmark·GitHub 렌더로 잰 것).
- 줄 두 개로 표를 판정 → cmark-gfm 블록 파싱을 옮김.
- 이진 판정 8192 → 8000. BOM을 열로 셈 → 벗김. 경로 오류 트레이스백 → 어긋남.
- "두 번 돌지 않는다"·"pre-commit만"·"검사 넷" 문장.
- 바깥 컨테이너가 끝나 닫힌 표는 끊긴 것이 아니다 → 그 줄이 칸을 나누면 끊긴 것이다(셀프 리뷰).
- 이스케이프 → `chr()`. 파일 다섯과 일지 한 줄.
- CLI 테스트의 열 번호 기대를 잘못 셌다(8, 실제 7). 테스트가 잡았다.
