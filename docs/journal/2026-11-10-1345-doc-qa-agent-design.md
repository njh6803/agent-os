## 설계 인터뷰 라운드 1

> 사용자: (질문이 들어왔을 때 문서 검색을 누가 시작하게 할까요?) "Agentic RAG 방식으로. 그리고 위젯의 답을 마크다운으로 할 수 있게 해줘."

선택지 밖의 답이다. 올린 선택지는 "에이전트 코드가 먼저 검색 (Recommended)"과 "모델이 스스로 검색"이었고, 이 답은 뒤의 것(모델이 검색어를 짓고 모자라면 다시 검색한다)에 위젯의 마크다운 표시라는 새 요구를 더했다. 그 선택지의 설명은 이랬다. — 설명: calc와 같은 모양입니다. 모델이 검색어를 직접 짓고, 모자라면 다시 검색합니다. 이어지는 질문도 모델이 검색어를 고쳐 씁니다. 검색을 한 번 하면 질문 하나에 모델 호출이 2번(검색 요청 1번, 답 1번)이고, 런타임이 허용하는 끝은 같은 10번입니다. 치르는 값: 검색 결과가 원본 JSON 그대로 모델에 전달되어, 코드가 조각에 번호를 붙이거나 자료 묶음으로 감쌀 수 없고 형식의 판도 확인할 수 없습니다. 문서 속 지시를 막는 것은 프롬프트 문장에만 기댑니다. 도구 호출 형식을 지키지 못하는 모델에서는 실행이 실패합니다(같은 어림). 출처를 별도 칸으로 내려면 모델의 답 글을 다시 해석해야 해서 그 길이 사실상 닫힙니다.

> 사용자: (doc-qa 묶음(에이전트, 스킬, 검색 서버 연결, 규칙 파일)을 어느 폴더에 둘까요?) "기본 plugins/ 폴더에 함께" — 설명: calc 옆에 둡니다(calc와 everything이 이미 이렇게 있습니다). 서버를 기본값으로 띄워도 doc-qa가 목록에 보입니다. 치르는 값: 규칙 파일이 폴더마다 하나라서 calc용 허락과 doc-qa용 규칙이 한 파일에 섞이고, 공개 데모가 이 폴더를 쓰면 calc와 everything도 함께 열려 배포가 다시 추려야 합니다. 검색 서버 주소는 매니페스트에 글자 그대로 적으므로(ADR 0049), 그 주소에 서버가 없는 개발자 PC에서는 doc-qa 실행이 '도구 연결 실패'로 끝납니다. 위젯의 실제 모델 e2e가 이 폴더를 통째로 복사하므로(`e2e-stack`의 `copyRepoPlugins`를 읽었습니다) 새 플러그인이 그 시험 환경에 섞입니다.

> 사용자: (실제 문서 검색 서버 이미지로 doc-qa를 돌려 보는 시험을 어디에 둘까요? (그 이미지는 아직 없습니다)) "이미지가 나올 때까지 열어 둠" — 설명: doc-qa-agent의 마지막 티켓을 '실제 이미지로 한 번 돌린다'로 두고, rag-engine의 이미지가 나올 때까지 기능을 닫지 않습니다. '끝났다'는 표시가 실제 서버와 맞물린 뒤에만 붙습니다. 치르는 값: rag-engine은 지금 명세를 마친 단계이고 저장소에는 뼈대 파일 셋만 있어서(파일 이름을 봤습니다), 기능이 몇 주(어림) 동안 진행 중으로 남고, 이 기능에 막힌 answer-eval과 public-demo의 티켓 작성도 그만큼 미뤄집니다.

세 답 모두 추천과 달랐다. 묻지 않고 넘긴 것은 하나다. doc-qa가 쓰는 도구는 `search` 하나이고 나머지 둘은 규칙 파일이 이름으로 거부한다(ADR 0046의 2026-11-06 이력에서 사용자가 골랐다). 합의 요약에서 다시 확인받는다.

라운드 1의 답이 정한 것. 모델이 검색하므로 출처는 별도 칸이 아니라 답의 글 안에 적고 `run_finished`의 계약은 바뀌지 않는다. 위젯의 마크다운 표시는 새 요구라, 후보 라이브러리 둘을 임시 폴더에 설치해 재는 프로브를 서브에이전트에 맡겼다(결과는 라운드 3 앞에 적는다). 공개 데모에서 calc가 함께 열리는 것은 사이트 파일의 열 에이전트 목록으로 막는다(`.claude/rules/core.md`의 `visible_agents` 항목을 읽었다).

## 설계 인터뷰 라운드 2

> 사용자: (한 질문에서 모델을 부르는 횟수의 끝을 어떻게 둘까요?) "에이전트마다 끝을 낮추는 칸 추가 (Recommended)" — 설명: 에이전트 매니페스트에 선택 칸(이름은 합의 요약에서 확정합니다. 예: `max_turns = 3`)을 더해서 doc-qa는 '검색 두 번과 답 한 번'까지만 돌게 합니다. 칸이 없는 에이전트는 지금처럼 10번입니다(`core/loop.py`의 `MAX_TURNS`를 읽었습니다). 끝을 넘긴 실행은 지금의 10번 초과와 똑같이 실패(실패 원인 '루프 상한')로 끝나고 답이 나오지 않습니다. 공개 데모는 시간당 최대 비용을 10번이 아니라 3번 기준으로 셈할 수 있습니다. 치르는 값: 매니페스트는 계약이라서 sdk와 openapi.json과 api-client 생성물이 함께 바뀌고(`.claude/rules/sdk.md`), 이 변경이 첫 티켓이 되어 뒤 티켓을 막으며, ADR 이력을 남깁니다. 선례는 같은 모양의 선택 칸 `conversation_limit`입니다.

> 사용자: (위젯의 마크다운 표시를 계획표의 어느 기능으로 둘까요?) "별도 기능으로 분리 (Recommended)" — 설명: 새 기능(이름은 합의 요약에서 확정합니다. 예: widget-markdown)을 계획표에 더합니다. 마크다운 표시는 calc를 포함한 모든 에이전트의 답에 적용되는 위젯의 변경이고, 새 의존성과 보안 규칙(링크, 이미지)이라는 자기 결정이 있어서 ADR도 따로 씁니다. doc-qa-agent와 서로 막지 않고 나란히 진행할 수 있습니다. 위젯이 바뀌기 전에는 마크다운 기호가 글자 그대로 보일 뿐이고 답은 읽힙니다. 설계는 이 인터뷰에서 함께 마칩니다. 치르는 값: 기능 폴더와 명세와 티켓 묶음이 하나씩 더 생깁니다.

Docker Compose에서는 서비스 이름이 곧 주소이므로 공개 데모와 참조 배포가 이 파일을 고치지 않고 그대로 씁니다(ADR 0049 결정의 전제입니다). 치르는 값: 개발자 PC에서는 이 이름으로 서버를 찾지 못해서 doc-qa 실행이 '도구 연결 실패'로 끝납니다. 로컬에서 돌리려면 매니페스트의 주소를 고쳐야 합니다(ADR 0049가 정한 방법입니다). 테스트는 임시 폴더에 주소를 바꿔 쓴 사본으로 돕니다(mcp-http의 실제 모델 테스트가 이렇게 한다고 서브에이전트가 `tests/test_main.py`에서 읽었습니다).

## 위젯 마크다운 프로브

서브에이전트가 저장소 밖 임시 폴더(세션 스크래치패드의 `md-probe`)에 React 19.3.0, TypeScript 5.9.3, `web/tsconfig.base.json`의 사본으로 작은 프로젝트를 짓고 후보 둘(react-markdown 10.1.0 + remark-gfm 4.0.1, markdown-to-jsx 9.10.6)을 설치해 스크립트를 손으로 돌렸다(`node probe/<이름>.mjs`). 프로브 파일은 아직 저장소에 옮기지 않았으므로 아래의 수는 커밋한 프로브가 다시 내는 것이 아니다(명세를 쓰는 단계가 `.scratch/<기능>/probes/`로 옮겨 다시 돌린다). 아래는 그 보고이고, 내가 산출물에서 직접 본 것은 그렇게 적는다.

- 제한(원시 HTML은 글자, 이미지는 그리지 않음, 링크는 `http`·`https`만, 새 탭과 `rel="noopener noreferrer"`)을 건 컴포넌트는 두 후보 모두 `any`·`as`·`!` 없이 쓸 수 있었다. `tsc --noEmit`이 0으로 끝났고 저장소의 `web/eslint.config.mjs` 사본에서 메시지가 0이었다(서브에이전트가 `node probe/typecheck.mjs`와 `node probe/lint.mjs`를 손으로 돌려 봤다).
- 입력 52가지를 `renderToStaticMarkup`으로 그린 결과에서 두 후보 모두 위반 0이었다(서브에이전트가 `node probe/render.mjs`를 손으로 돌려 봤다). markdown-to-jsx는 첫 시도에서 `<input type="checkbox">`와 `<footer>`가 샜고 규칙 종류 23가지를 손으로 허용 목록으로 적은 둘째 컴포넌트에서 0이 됐다.
- 크기 증분(gzip)은 react-markdown + remark-gfm이 50,964바이트(esbuild, React 밖)와 48,812바이트(Vite IIFE), markdown-to-jsx가 32,040바이트와 31,172바이트다(서브에이전트가 `node probe/size.mjs`를 손으로 돌렸고, 네 수는 내가 `out/size/summary.json`에서 봤다). ADR 0024가 적은 element 번들 약 76.4KB에 대면 약 64%와 41%라는 것은 어림이다(지금 번들은 재지 않았다).
- react-markdown의 전이 의존성은 98개이고 지난 365일 새 판이 없다. markdown-to-jsx는 의존성이 없고 지난 365일에 52판이 나왔으며 돌린 날을 기준으로 3일 된 판이었다(서브에이전트가 `node probe/deps.mjs`와 `node probe/registry.mjs`를 손으로 돌려 봤다).
- 마크다운이 아닌 글이 바뀐다. `2*3*4 = 24`가 `2<em>3</em>4 = 24`로 그려진다(같은 `render.mjs`를 손으로 돌린 결과이고, 내가 `out/render/react-markdown/restricted/x01-plain-asterisks.html`에서 봤다). `__init__.py`는 굵은 `init`이 되고 `#`으로 시작하는 줄은 제목이 된다(보고).
- 한국어 굵게가 닫히지 않는 모양이 있다. `**민법 제750조(불법행위)**는`처럼 닫는 별표 앞이 문장부호이고 뒤가 글자면 별표가 그대로 보인다(같은 `render.mjs`를 손으로 돌린 결과라고 보고받았다).
- 한 줄 바꿈은 문단 안에 `\n` 글자로 남아 CSS 없이는 공백으로 붙는다. `[1]`은 정의 줄이 없으면 글자 그대로다. GFM 각주 `[^1]`은 react-markdown에서 영어 제목 "Footnotes"를 낸다(같은 `render.mjs`를 손으로 돌린 결과라고 보고받았다). 브라우저에서 본 것은 없다.
- react-markdown은 `>`를 3,000겹 겹친 인용에서 `RangeError`를 던졌다(서브에이전트가 `node probe/stress.mjs`를 손으로 돌려 봤다. 파서 탓인지 서버 렌더 탓인지는 가르지 않았다).
- 위젯의 iframe 페이지가 내는 CSP는 `frame-ancestors` 하나다(내가 `web/apps/widget/next.config.ts` 40줄을 읽었다). 바깥 주소의 `<img>`가 요청을 보낸다는 것은 설정을 읽은 판단이고 브라우저에서 재지 않았다.
- ADR 0024의 33줄이 "마크다운을 그리게 되면 원시 HTML을 끈 렌더러만 쓴다"고 적는다(내가 읽었다). `dangerouslySetInnerHTML`은 ESLint가 막는다(서브에이전트가 `web/eslint.config.mjs` 81~85줄을 읽었다).

> 사용자: (어느 위젯의 답을 마크다운으로 그릴까요?) > 사용자: (doc-qa의 답에서 출처를 어떤 모양으로 적게 할까요?) "문장 끝 번호와 출처 목록 (Recommended)" — 설명: 문장 끝에 번호를 달고, 답의 끝에 번호 목록으로 문서 제목과 위치(쪽이나 절)와 갱신일을 적습니다. 답변 평가(answer-eval)가 목록의 줄을 읽어서 출처가 맞게 적혔는지를 자동으로 잴 수 있습니다. 갱신일은 날짜까지만 보이고, 정확한 시각과 조각 식별자는 트레이스의 검색 결과에 남아서 나중에 되짚을 수 있습니다. 근거를 찾지 못하면 출처 목록 없이 정해진 한 문장으로 답합니다(문구는 명세에서 확정합니다). 치르는 값: 마크다운 표시가 꺼진 위젯에서는 목록 기호가 글자 그대로 보입니다.

고른 선택지의 미리보기는 이랬다.

```
육아휴직은 자녀 1명당 최대 1년까지 쓸 수 있습니다. [1]
신청서는 휴직 시작 30일 전까지 내야 합니다. [2]

출처
1. 육아휴직 업무편람, 12쪽 (갱신일 2026-10-01)
2. 인사 규정, 제3장 제14조 (갱신일 2026-08-15)
```

미리보기의 두 문장은 빈 줄 없이 줄만 바꿨다. 표준 마크다운은 그 둘을 한 문단으로 붙이므로, 한 줄 바꿈을 줄바꿈으로 보이게 하는 것이 이 모양의 조건이다(합의 요약에서 확인받는다). 첫째 답으로 "꺼진 위젯"이 없어졌으므로 이 설명의 "치르는 값"은 해당하지 않는다.

> 사용자: (관리 화면의 '그린 모양'에서 답 안의 링크를 누를 수 있게 할까요?) "위젯과 똑같이 누를 수 있게 함" — 설명: 링크가 새 탭에서 열립니다. 새 탭은 관리 화면의 창에 접근하지 못합니다(`rel="noopener noreferrer"`를 붙이기 때문입니다. 브라우저의 표준 동작에 기댄 판단이고 재지 않았습니다). 운영자가 최종 사용자와 같은 조작을 봅니다. 치르는 값: 속임수 링크를 운영자가 누를 여지가 남습니다.

추천(누를 수 없게 함)과 달랐다. 관리 화면의 그린 모양은 위젯과 같은 부품을 같은 제한으로 쓴다.

## 합의 요약 첫 판과 사용자의 답

다섯 라운드의 결정과 기본값을 모은 합의 요약을 올리고 확정할지 물었다. 사용자는 선택지를 고르지 않고 이렇게 답했다.

> 사용자: 문서 질의응답 에이전트 (doc-qa-agent) 이름이 마음에 안들어. 지금 만드는 걸 기본 기본 에이전트로 만들껀데. 문서에 대한 질의 응답만 하는게 아니라 승인 같은 기능도 있잖아.
> 이름을 다시 지어보자.

합의 요약은 확인받지 못했다. 이 답으로 열린 가지는 셋이다. "기본 에이전트"가 무엇을 뜻하는지, 이 에이전트에서 승인이 실제로 일어나는 자리를 둘지, 이름을 무엇으로 할지다. 대 본 사실은 다음과 같다.

- 용어집에 "기본 에이전트"라는 말은 없고 "참조 에이전트"가 있다(`CONTEXT.md` 47~49줄을 내가 읽었다. 저장소에서 `기본 에이전트|default_agent|default agent`를 Grep했고 맞은 것이 없었다).
- 지금까지의 설계에서 이 에이전트는 승인을 한 번도 타지 않는다. 검색 도구 하나만 허락하고 나머지 둘을 막기 때문이다(라운드 1과 합의 요약 A-3). 저장소의 플러그인 가운데 승인 요구(`requires_approval`)를 쓰는 것도 없다(`plugins/`에서 `requires_approval|승인`을 Grep했고 맞은 것은 `rules.toml`의 주석 한 줄이었다).
- PRD의 16줄은 "설치형 문서 질의응답이 요구하는 승인 통제와 감사 기록은 이 런타임이 보장하는 강제와 기록 그 자체다. 기준선은 그 보장을 실제 사용처 하나 위에서 끝까지 시험하는 자리다"라고 적는다(내가 읽었다).
- `doc-qa`라는 글자는 27개 파일의 105곳에 있다(Grep의 count로 봤다). 일지와 대기열 항목 같은 기록을 빼면 PRD, ADR 넷(0045·0046·0048·0049)과 색인, 기능 계획 다섯, 명세 둘, 생성물인 전체 계획이다.
- 플러그인 이름의 패턴은 `^[a-z][a-z0-9-]{1,62}$`다(`src/agent_os/sdk/ids.py` 22줄).
- 위젯의 `agent` 속성은 필수이고, 위쪽 띠의 이름(`heading`)을 주지 않으면 `agent` 값이 보인다(`web/apps/widget/EMBED.md` 94~95줄을 Grep으로 봤다).

## 설계 인터뷰 라운드 6

> 사용자: (말씀하신 '기본 에이전트'는 어떤 뜻인가요?) 함께 내는 대표 에이전트라기보다는 이 에이전트를 기반으로 고객사에 요구사항에 맞춰 커스텀 에이전트를 만들 수 있게.
> 특별한 요구사항이 없으면 이 에이전트를 사용.

선택지 둘(함께 내는 대표 에이전트, 지정하지 않으면 답하는 기본값) 가운데 어느 것도 아닌 답이다. 이 에이전트는 고객사의 요구에 맞춘 커스텀 에이전트의 바탕이고, 요구가 없으면 그대로 쓰는 에이전트다. "바탕으로 만든다"의 방식(복사해 고치기, 설정만으로 선언하기, sdk의 바탕 클래스)이 새로 열린 가지다.

> 사용자: (이 에이전트에서 승인이 실제로 일어나는 자리를 둘까요?) "문서 전문 읽기를 승인 뒤에 부르게 엶 (Recommended)" — 설명: 검색은 지금처럼 묻지 않고 부르고, 문서 전체를 읽는 도구(`get_document`)는 막지 않고 '묻고 부르는' 도구로 엽니다. 조각만으로 부족해서 모델이 전문을 읽으려 하면 위젯에 승인 카드가 뜨고, 질문한 사람이 승인하거나 거부합니다(위젯에는 승인 카드가 이미 있습니다. `ApprovalCard.tsx`가 있는 것을 확인했습니다). 기준선이 승인 통제를 실제 사용처에서 시험하는 자리라는 PRD 16줄과 맞습니다. 공개 데모에서는 이 도구를 배포의 규칙 파일로 막습니다. 익명 사용자가 스스로 승인할 수 있기 때문입니다(`.scratch/public-demo/plan.md` 5줄에서 확인했습니다). 치르는 값: 전문 읽기는 조각보다 훨씬 많은 글을 모델에 보내므로 실행 하나의 토큰이 커질 수 있고(크기는 문서에 달려 있어 어림입니다), 시험에 승인 흐름의 사례가 더해지며, 함께 내는 규칙 파일과 공개 데모의 규칙 파일이 달라집니다.

합의 요약 첫 판의 A-3(나머지 둘을 이름으로 막는다)이 바뀐다. `get_document`는 묻는 도구가 되고 `list_knowledge_bases`만 막는다.

> 사용자: (에이전트의 이름을 무엇으로 할까요?) "assistant (Recommended)" — 설명: '도우미'라는 뜻의 가장 흔한 이름입니다. 문서 검색, 출처, 승인을 모두 품을 만큼 넓고, 위젯 머리에 그대로 보여도 어색하지 않습니다(머리에 보일 이름을 따로 주지 않으면 이 이름이 보입니다. `EMBED.md` 95줄에서 확인했습니다). 치르는 값: 무엇이든 답하는 범용 챗봇으로 읽힐 수 있어서, 스킬과 설명에 '문서의 근거로만 답한다'를 분명히 적어야 합니다.

## 라운드 7 전에 대 본 사실

- 플러그인은 고유 모듈명 `agent_os_plugins.<name>.<module>`로 로드되고 `sys.path`를 건드리지 않는다(`src/agent_os/adapters/filesystem.py` 5~6줄을 Grep으로 봤다). 플러그인은 `agent_os.sdk`만 import한다(원칙 IV). 그래서 커스텀 에이전트가 다른 플러그인의 코드를 물려받는 길은 지금 없다.
- calc의 코드에서 계산에만 해당하는 것은 프롬프트의 머리 문장 한 줄이다. 나머지는 스킬 블록과 앞 대화 블록을 엮고 `ctx.llm()`을 한 번 부른다(`plugins/agents/calc/agent.py` 전체를 내가 읽었다).
- 에이전트 매니페스트는 `entrypoint`가 필수다(`src/agent_os/sdk/manifest.py` 243~245줄을 내가 읽었다).

## 설계 인터뷰 라운드 7

> 사용자: (커스텀 에이전트를 이 에이전트 기반으로 만드는 방식을 무엇으로 할까요?) "폴더를 복사해 설정과 스킬을 바꿈 (Recommended)" — 설명: `assistant`의 코드를 어떤 일에도 묶이지 않게 씁니다. 쓸 도구 서버, 스킬, 모델, 턴과 도구 호출의 끝은 설정 파일(`plugin.toml`)이 정하고, 일하는 방법은 스킬 문서가 정합니다. 커스텀 에이전트는 폴더를 복사해 이름을 바꾸고 설정과 스킬을 고쳐서 만들며, 요구가 코드까지 닿으면 복사한 코드를 고칩니다. 만드는 순서를 안내 문서로 함께 내고, '이름만 바꾼 사본이 그대로 돈다'는 시험을 둡니다. calc의 코드가 이미 이 모양입니다(`plugins/agents/calc/agent.py`를 읽었습니다. 계산에만 해당하는 것은 머리 문장 한 줄입니다). 런타임과 계약은 이 방식 때문에 바뀌지 않습니다. 치르는 값: 사본은 원본이 나중에 고쳐져도 저절로 따라가지 않아서, 판을 올릴 때 손으로 맞춰야 합니다.

> 사용자: (용어집에서 이 에이전트를 무엇이라고 부를까요?) "'기본 에이전트'로 바꿈 (Recommended)" — 설명: 용어집의 '참조 에이전트'를 '기본 에이전트'로 바꾸고, 뜻을 '이 저장소가 함께 내는 에이전트로, 요구가 없으면 그대로 쓰고 요구가 있으면 복사해 고쳐 커스텀 에이전트의 바탕으로 삼는다'로 고칩니다. 말씀하신 말과 문서의 말이 같아집니다. PRD와 ADR이 적은 '참조 에이전트 doc-qa'도 '기본 에이전트 assistant'로 고칩니다(PRD는 승인을 받아 고치고, ADR 본문은 이력과 바뀜 표시로 남깁니다). '참조 배포'라는 말은 그대로 둡니다. 치르는 값: 런타임에는 '기본 모델'(에이전트가 모델을 고르지 않으면 런타임이 쓰는 모델)이라는 말이 이미 있어서, '기본 에이전트'도 런타임이 아는 기본값으로 오해될 수 있습니다. 용어집에 '런타임은 이 에이전트를 모른다'를 함께 적어 둡니다.

## 확인받은 합의 요약

합의 요약 둘째 판을 올리고 확정할지 물었다.

> 사용자: (이 합의 요약대로 설계를 확정하고 용어 기록과 ADR 초안으로 넘어갈까요?) "이대로 확정 (Recommended)" — 설명: 둘째 판 요약의 결정과 기본값을 그대로 두고 다음 단계로 넘어갑니다. 용어집(`CONTEXT.md`)에 새 말을 적고 ADR 초안을 쓴 뒤, 셀프 리뷰를 반영한 초안을 보여 드리고 승인을 받습니다. 코드는 이 세션에서 고치지 않습니다.

아래는 확인받은 글이다. 둘째 판이 "그대로"라고 가리킨 항목은 첫 판의 글을 옮겼다. **기본값**은 묻지 않고 둔 값이라는 표시다.

### A. 기본 에이전트 `assistant`

1. **뜻**: 고객사의 요구에 맞춘 커스텀 에이전트를 만드는 바탕이고, 특별한 요구가 없으면 그대로 쓰는 에이전트입니다. 용어집의 "참조 에이전트"를 "기본 에이전트"로 바꿉니다.
   - **기본값**: 런타임은 지금처럼 이 에이전트를 모르고, "에이전트를 지정하지 않으면 이 에이전트가 답한다"는 런타임의 기본값은 두지 않습니다. "요구가 없으면 그대로 쓴다"는 배포하는 사람이 고르는 기본 선택이라는 뜻으로 적겠습니다. 참조 배포와 질문 페이지의 예시 설정이 `assistant`를 가리키도록 이웃 계획에 넘겨 적습니다.
2. **코드**: 어떤 일에도 묶이지 않게 씁니다. 설정 파일이 고른 스킬을 지시로 엮고, 앞 대화를 데이터로 엮은 뒤 모델을 한 번 부릅니다. 문서 검색에만 해당하는 내용은 스킬 `cite-sources`, 연결 파일 `doc-search`, 규칙 파일에 둡니다.
3. **커스텀 에이전트를 만드는 길**: 폴더를 복사해 이름을 바꾸고 설정과 스킬을 고칩니다. 만드는 순서를 안내 문서로 함께 내고, "이름만 바꾼 사본이 그대로 돈다"는 시험을 둡니다.
4. **도구 셋의 규칙**:
   - 검색(`search`)은 묻지 않고 부릅니다.
   - 문서 전문 읽기(`get_document`)는 승인을 받은 뒤에 부릅니다. 위젯에 승인 카드가 뜨고 질문한 사람이 결정합니다.
   - 지식베이스 목록(`list_knowledge_bases`)은 막습니다.
   - 공개 데모는 배포의 규칙 파일로 전문 읽기도 막습니다(공개 데모의 계획에 넘겨 적습니다).
5. **시험에 더해지는 것**: 승인하면 전문을 읽고 답하는 사례, 거부하면 조각만으로 답하는 사례입니다.
6. **알려진 위험**: 전문 읽기가 돌려주는 글의 크기에 끝이 있는지는 아직 확인하지 못했습니다. 명세 단계에서 문서 검색 서버의 명세를 확인하고, 끝이 없으면 그 저장소의 계획에 넘기겠습니다.
7. **이름을 고치는 범위**:
   - **기본값**: 기능의 이름은 `doc-qa-agent`에서 `base-agent`로 바꾸고, 폴더와 다른 계획의 "기다리는 기능" 줄을 함께 고칩니다.
   - PRD의 "참조 에이전트 doc-qa" 문장은 승인을 받아 고칩니다. ADR 본문은 글자를 고치지 않고 이력과 바뀜 표시로 남깁니다. 일지와 같은 기록은 고치지 않습니다.
8. **검색 방식**: 모델이 스스로 검색 도구를 부릅니다. 에이전트 코드는 calc와 같은 모양입니다(`ctx.llm()` 한 번). 출처는 답의 글 안에 적으므로 실행 결과의 계약(`run_finished`)은 바뀌지 않습니다.
9. **놓는 자리**: 기본 `plugins/` 폴더에 calc와 함께 둡니다. 커밋하는 주소는 배포용 서비스 이름이고, 토큰은 환경 변수의 이름으로만 적습니다. 연결 파일의 이름 `doc-search`는 **기본값**입니다.
10. **검색 대상**: 지식베이스 이름을 넘기지 않고 서버의 기본 지식베이스를 씁니다(**기본값**).
11. **끝 둘**: 에이전트 설정 파일에 선택 칸 둘을 더합니다. 턴의 끝(`max_turns`)과 도구 호출의 끝(`max_tool_calls`)입니다(**기본값**: 이름).
    - 칸이 없으면 지금과 같습니다(턴 10, 도구 호출은 제한 없음).
    - 턴의 끝을 넘으면 지금처럼 실행이 실패로 끝나고, 도구 호출의 끝을 넘은 호출은 부르지 않고 "횟수를 넘었다"는 결과를 모델에 돌려줍니다.
    - **기본값**: 둘 다 1 이상의 정수만 받고, 턴의 끝은 낮추기만 할 수 있습니다(10을 넘는 값은 실행 전에 거부합니다).
    - 계약 변경(sdk, `openapi.json`, api-client)이므로 첫 티켓입니다. 에이전트가 적을 값은 명세에서 확정합니다.
12. **답의 모양**: 문장 끝에 `[1]`, 답의 끝에 "출처" 번호 목록(문서 제목, 위치, 갱신일)을 적습니다. 갱신일은 서버가 준 시각의 날짜 부분을 그대로 옮깁니다. 근거가 없으면 출처 목록 없이 정해진 한 문장으로 답합니다(문구는 명세에서 확정합니다).
13. **문서 속 지시**: 검색 결과는 데이터로만 다루고 그 안의 지시를 따르지 않는다고 스킬에 적습니다. 코드로 막는 장치는 없고, 피해의 범위는 열린 도구와 답의 글로 묶입니다.
14. **모델과 대화**(**기본값**): 설정 파일에 모델을 적지 않아 기본 모델을 따르고, 앞 대화는 calc처럼 데이터로 엮습니다. 공개 데모에서 대화 이어 가기를 열지는 공개 데모의 설계가 정합니다.
15. **시험**:
    - 빠른 검사는 검색 도구 형식의 판 1.0.0을 흉내 내는 가짜 검색 서버로 돌고, 그 판은 픽스처 파일 한 곳에만 적습니다.
    - 실제 모델 시험은 출처와 갱신일이 붙는지, 근거 없는 질문에 모른다고 답하는지, 지시가 섞인 조각을 따르지 않는지를 봅니다.
    - 위젯의 실제 모델 e2e에 사례를 하나 더합니다.
    - 마지막 티켓은 실제 문서 검색 서버 이미지로 한 번 돌리는 것이고, 그 이미지가 나올 때까지 기능을 닫지 않습니다.

### B. 답을 마크다운으로 그리기 (새 기능 둘)

**B-1. 마크다운 표시** (**기본값**: 이름 `answer-markdown`)

1. 마크다운을 그리는 부품을 공유 패키지(`web/packages/ui`)에 만들고, 위젯이 설정 없이 모든 에이전트의 답을 그 부품으로 그립니다. 사용자의 질문, 실패 안내, 인사말, 승인 카드의 도구 인자는 지금처럼 글자 그대로 둡니다(**기본값**).
2. 라이브러리는 react-markdown과 remark-gfm입니다. 원시 HTML은 글자로 보이고, 그리기에 실패하면 원문을 글자 그대로 보여 줍니다.
3. **기본값**: 그리는 것은 제목, 문단, 굵게, 기울임, 취소선, 목록, 인용, 코드, 표, 링크, 가로줄입니다. 이미지는 대체 글만 보이고, 체크박스와 각주는 그리지 않습니다.
4. 링크는 `http`·`https`만 새 탭으로 엽니다. **기본값**: `https://정상사이트@가짜사이트/`처럼 호스트를 속이는 주소는 링크로 만들지 않습니다.
5. **기본값**: 한 줄 바꿈은 줄바꿈으로 보이게 합니다(고르신 출처 미리보기의 모양이 이것을 전제로 합니다).
6. 알려진 부작용은 받아들입니다(`2*3*4 = 24`가 `234 = 24`로 보임). **기본값**: 한국어에서 굵게가 닫히지 않는 모양(`**용어(설명)**는`)은 명세 단계에서 보완 방법을 프로브로 확인한 뒤에 정합니다.
7. 명세 전에 목업을 먼저 그립니다.
8. 공개 데모가 이 기능을 기다립니다. 기본 에이전트의 기능과는 서로 기다리지 않습니다.

**B-2. 관리 화면의 전환** (**기본값**: 이름 `admin-answer-preview`)

1. 실행 상세의 출력 칸에 '원문'과 '그린 모양'을 오가는 전환을 둡니다. B-1의 부품을 같은 제한으로 쓰고, 링크는 위젯과 똑같이 새 탭으로 열립니다.
2. B-1을 기다리고, 공개 데모는 이 기능을 기다리지 않습니다.
3. **기본값**: 처음에 보이는 것은 원문이고, 전환을 두는 칸은 최종 출력 하나입니다. 세부 모양은 이 기능의 목업에서 고르십니다.

### C. 기록과 이웃 계획

1. ADR 초안을 씁니다. 기본 에이전트의 설계(뜻과 커스텀을 만드는 길을 포함합니다), 답을 마크다운으로 그리는 결정(ADR 0024와 ADR 0019의 "텍스트로 그린다"는 문장에 바뀜 표시를 답니다), 설정 파일의 새 칸 둘입니다. 초안은 셀프 리뷰를 반영한 뒤에 보여 드리고 승인을 받겠습니다.
2. 용어집에 "기본 에이전트"를 적고, "런타임은 이 에이전트를 모른다"를 함께 적습니다.
3. 공개 데모의 계획에 넘겨 적습니다. 기다리는 기능에 B-1 추가, 사이트가 여는 에이전트 목록에서 calc 제외, 날짜만 아는 문서는 그 날짜의 UTC 0시로 넣기, 검색 조각 수의 단단한 끝은 문서 검색 서버의 설정으로 낮추기, 전문 읽기를 막기입니다.
4. 참조 배포의 계획에 "예시 설정이 `assistant`를 가리킨다"를 넘겨 적습니다.
5. 답변 평가(answer-eval)의 계획에 출처 줄의 모양을 입력으로 넘겨 적습니다.
6. 마크다운 프로브의 파일을 저장소의 B-1 프로브 폴더로 옮깁니다.

첫 판의 A-13은 "피해의 범위는 읽기 전용 검색 하나와 답의 글"이라고 적었다. 전문 읽기가 승인 뒤에 열리게 되어 여기서는 "열린 도구와 답의 글"로 고쳐 옮겼다. 이 한 구절은 사용자가 본 글과 다르므로 ADR 초안의 승인 화면에서 함께 확인받는다.

## domain-modeling과 산출물

용어를 맞추고 ADR 초안 셋을 썼다. 승인 전이라 셋 다 상태는 proposed다. 코드는 고치지 않았다.

- `CONTEXT.md`. **참조 에이전트** 항목을 **기본 에이전트(Base Agent)**로 바꾸고 뜻을 고쳤다(요구가 없으면 그대로 쓰고, 요구가 있으면 복사해 고쳐 커스텀 에이전트의 바탕으로 삼는다. 런타임은 그 에이전트를 모른다). **커스텀 에이전트(Custom Agent)** 항목을 새로 넣었다. 참조 배포와 공개 데모 항목이 든 "참조 에이전트"도 "기본 에이전트"로 고쳤다. 피할 말에 옛 이름을 적었다.
- ADR 초안 셋. `docs/adr/0051-base-agent-is-task-agnostic-code-and-custom-agents-are-copies.md`(합의 요약 A의 뜻, 코드, 문서 검색이 있는 자리 셋, 도구 셋의 규칙, 답의 모양, 커스텀 에이전트를 만드는 길), `docs/adr/0052-agent-manifest-lowers-the-turn-limit-and-caps-tool-calls.md`(A-11의 칸 둘), `docs/adr/0053-model-answers-are-drawn-as-markdown-by-one-shared-component.md`(합의 요약 B). 거부한 안은 대화 기록에서 뽑은 선택지의 원문으로 적었다. `docs/adr/README.md`에 색인 행 셋(proposed, 2026-11-10)을 더했다.
- 포인터(`.claude/rules/adr.md`). ADR 0009의 "`MAX_TURNS = 10`은 실행 전체 기준이고 재생된 턴도 센다" 뒤에 `(바뀜: ADR 0052)`, ADR 0019와 ADR 0024의 "텍스트로 그린다" 문장 뒤에 `(바뀜: ADR 0053)`, ADR 0048 네 곳과 ADR 0049 두 곳에 `(바뀜: ADR 0051)`을 달았다. ADR 0046은 자기 결정의 개정이라 이력 "기본 에이전트 assistant가 참조 에이전트 doc-qa를 대신하고 공개 데모가 answer-markdown을 기다린다"를 쓰고 본문 세 곳에 그 이력의 포인터를 달았다. 달지 않은 것과 까닭은 ADR마다 Consequences의 "다른 ADR의 본문" 항목에 적었다. `uv run python tools/check_adr_pointers.py`는 0으로 끝났다.
- PRD(`docs/PRD.md`) 22줄의 제안. 승인 전이고 머리의 status 줄은 아직 고치지 않았다. 전: "참조 에이전트 doc-qa와 그 참조 배포(설치형 문서 질의응답)를 이 저장소에 두지만, 런타임은 그것을 모른다. doc-qa가 쓰는 문서 검색 서버는 다른 저장소에 있고, 런타임은 그 서버도 모른다(ADR 0048)." 후: "기본 에이전트 assistant와 그 참조 배포(설치형 문서 질의응답)를 이 저장소에 두지만, 런타임은 그것을 모른다. 기본 에이전트는 커스텀 에이전트의 바탕이고, 특별한 요구가 없으면 그대로 쓴다(ADR 0051). 기본 에이전트가 쓰는 문서 검색 서버는 다른 저장소에 있고, 런타임은 그 서버도 모른다(ADR 0048)."
- 기능 계획. `.scratch/doc-qa-agent/`를 `.scratch/base-agent/`로 옮기고(`git mv`) 계획을 다시 썼다(슬라이스 8, Blocked by mcp-http와 approval-rules, 설계 ADR 0051과 ADR 0052). `.scratch/answer-markdown/plan.md`(슬라이스 8, Blocked by 없음, 설계 ADR 0053)와 `.scratch/admin-answer-preview/plan.md`(슬라이스 10, Blocked by answer-markdown, 설계 ADR 0053)를 새로 썼다. 설계 줄은 합의 요약을 확인받은 뒤에 적었고, ADR 승인 뒤에 커밋한다. 이웃 계획 넷을 고쳤다. public-demo(기다리는 기능에 answer-markdown, 열 에이전트 목록에서 calc 제외, 날짜만 아는 문서는 UTC 0시, 전문 읽기도 deny, 검색 조각 수의 끝은 문서 검색 서버의 설정), deploy-package(기다리는 기능 이름, 예시 설정이 `assistant`를 가리킨다, 규칙 파일), answer-eval(기다리는 기능 이름, 출처 줄의 모양을 입력으로), mcp-trust(그 행 전에 기대는 것이 스킬 `cite-sources`의 지시와 열린 도구가 읽기 도구뿐이라는 것). `uv run python tools/plan_table.py`로 `.scratch/plan.md`를 다시 만들었고, 새 행 셋이 표에 생겼으며 프론티어에 `answer-markdown`과 `base-agent`가 들었다.
- 프로브. 마크다운 라이브러리를 고른 프로브를 세션 스크래치패드에서 `.scratch/answer-markdown/probes/markdown_render/`로 옮겼다(`node_modules`와 산출물 `out`은 빼고, `out/`을 그 폴더의 `.gitignore`에 적었다). `lint.mjs`의 저장소 경로 기본값이 이 워크트리의 절대 경로여서 그 폴더에서 네 단계 위로 바꿨다. 옮긴 자리에서 손으로 다시 돌려 봤다(`pnpm -C .scratch/answer-markdown/probes/markdown_render install --frozen-lockfile` 뒤 `node …/probe/typecheck.mjs`, `lint.mjs`, `deps.mjs`, `registry.mjs`, `render.mjs`, `size.mjs`, `stress.mjs`를 차례로). `render.mjs`와 `size.mjs`의 표준 출력은 앞선 실행이 남긴 기록과 `diff`로 같았고, `typecheck.mjs`와 `lint.mjs`는 경로 표기만, `deps.mjs`는 설치 로그 칸만, `registry.mjs`는 조회 시각만, `stress.mjs`는 걸린 시간만 달랐다. `lint.mjs`가 복사한 판정자 설정의 SHA-256도 앞선 실행과 같았다. 표와 돌리는 명령은 `.scratch/answer-markdown/probes/README.md`에 썼고, ADR 0053의 Consequences "프로브"를 그 폴더와 다시 돌린 사실로 고쳤다.
- 옛 표현. `doc-qa|doc_qa|참조 에이전트`로 저장소를 Grep했다. 살아 있는 문서에 남은 것은 뜻한 자리뿐이다. `CONTEXT.md`의 피할 말, ADR 0051과 base-agent 계획이 옛 이름을 설명하는 문장, 포인터를 단 ADR 0046·0048·0049의 본문, ADR 0046의 파일 이름을 든 색인 행, ADR 0048의 배경 문단과 거부한 안의 근거, ADR 0045가 든 브랜치 이름이다. 나머지는 기록(일지, 끝난 mcp-http와 retro-queue-per-item의 명세, 대기열 항목이 든 일지 파일 이름)이라 그대로 뒀다. 코드와 설정 파일(`*.py`, `*.ts`, `*.tsx`, `*.toml`, `*.json`, `*.yml`, `*.mjs`)에는 일치가 없었다.

### 묻지 않고 정한 것

합의 요약의 **기본값** 표시 밖에서 ADR과 계획을 쓰며 정한 것이다. 승인 화면에서 함께 알린다.

1. A-13의 구절을 "열린 도구와 답의 글"로 고쳤다(위 문단).
2. 문서 전문 읽기를 묻게 하는 자리는 에이전트 매니페스트의 `requires_approval`이 아니라 규칙 파일의 `ask`이고, 표는 공통 표가 아니라 `[agents.assistant]`다. 그래서 이름만 바꾼 사본은 규칙 파일의 표 이름도 바꿔야 한다(ADR 0051 "도구 셋의 규칙"과 "커스텀 에이전트를 만드는 길").
3. 슬라이스는 answer-markdown이 8, admin-answer-preview가 10이다(ADR 0053 "기능 둘과 차례").
4. PRD 22줄의 글(위 항목).
5. 턴의 끝과 도구 호출의 끝은 둘 다 재생된 것도 센다. ADR 0009의 "재생된 턴도 센다"를 따랐다(ADR 0052).
6. 지식베이스 이름을 넘기지 않는 것은 스킬의 지시이고 코드로 막는 장치는 없다(ADR 0051 "검색 대상과 조각 수").
7. base-agent의 `**Blocked by:**`에 `rag-engine:release-image`를 적지 않았다. 적으면 프론티어에서 빠져 다른 티켓까지 시작하지 못하므로, 마지막 티켓만 그 이미지를 기다린다고 본문에 적었다.
8. ADR 0046의 기준선 표에 answer-markdown 줄을 더했다(그 ADR의 2026-11-10 이력).

## 인계

산출물을 다 쓰고 셀프 리뷰(`code-review`)를 부르자 인계 계기(`hook_handoff`, 컨텍스트 251,690 토큰, 경계 `셀프 리뷰 직전`)가 왔다. `handoff.md`의 인계하지 않는 때 다섯에 들지 않아 인계한다. 계기를 낸 호출은 실패하지 않았고, 범위는 PR과 병합까지라 이 경계에서 끝나지 않으며, 지시문 없이 연 세션이라 이어받은 인계가 아니고, 인계 못함 줄이 없고, `get_session self`에 `parentSessionId`가 없다. 이 브랜치에 열린 PR은 없다(`gh pr view docs/doc-qa-agent-design --json state`가 "no pull requests found"로 끝났다). 방금 불린 `code-review`의 단계는 밟지 않았고 셀프 리뷰는 새 세션이 한다. 이 세션의 지금 제목은 `docs/doc-qa-agent-design`이다. 이 브랜치에는 커밋이 없고 변경은 모두 작업 트리에 있다. 새 세션이 이 일지를 이어 쓰고 커밋한다. 지시문은 다음이다.

ADR 0044 20줄과 61줄을 Grep으로 봤고, `core/ports.py`의 `Rule.matches`가 서버와 도구 이름만 받는 것을 Grep으로 봤다. base-agent 계획의 "명세가 먼저 확인할 것"에도 적었다.
- 명세 4. ADR 0051 Consequences의 "조건이 된다"를 "기본 에이전트의 실제 모델 시험도 그 모델로 돌릴지는 그 설계 인터뷰가 정한다(local-model 기능 계획에 넘겼다)"로 고치고, local-model 계획의 "설계 인터뷰가 먼저 볼 것" 뒤에 넘긴 것을 적었다. local-model은 base-agent를 기다리지 않으므로 "base-agent가 먼저 닫혀 있어야 돌릴 수 있다"를 함께 적었다.
- 명세 5. base-agent 계획의 수락에 두 끝의 동작(턴의 끝을 넘기면 `loop_limit`, 도구 호출의 끝을 넘은 호출은 불리지 않고 실행이 이어진다, 칸이 없으면 지금과 같다)을 더했다.
- 명세 6. answer-markdown 계획의 수락에 사용자 정보가 든 주소와 한 줄 바꿈을 더했다. ADR 0053 "링크"에 "프로브의 주소 판정(`apps/widget/lib/safe-url.ts`)은 스킴만 보고, 그 모양의 입력 `x28-link-userinfo`는 판정 없이 관찰만 했다(두 파일을 읽었다). 부품을 짓는 티켓이 이 규칙을 새로 넣고 시험한다."를 더했다. `safe-url.ts` 전체와 `cases.mjs` 314~319줄(`must: () => []`)을 내가 읽었다.
- 명세 7. ADR 0051 Considered Options의 "골랐다"를 "선택지 밖의 답으로 "Agentic RAG 방식으로"라고 답했고, 올린 선택지 가운데 "모델이 스스로 검색"이 그 방식이다"로 고쳤다. `CONTEXT.md`의 기본 에이전트 뜻을 두 문장으로 줄였다.

묻지 않고 정한 것에 둘을 더한다. 승인 화면에서 앞의 여덟과 함께 알린다.

9. answer-markdown을 기준선의 행으로 두었으므로 제품 0.1(pilot-release)도 그 기능을 기다린다. 사용자가 고른 것은 공개 데모가 기다린다는 것까지다.

## ADR 셋과 PRD 22줄의 승인

셀프 리뷰를 반영한 뒤 한 화면으로 승인을 물었다. 화면 앞에 셀프 리뷰에서 내용이 달라진 셋(전문 읽기의 `include_text`, 조각 수의 설정 `RAG_SEARCH_MAX_TOP_K`, 계획표의 기다림 두 줄), 승인받을 문서 넷, PRD 22줄의 전과 후, 묻지 않고 정한 것 열 가지(위 여덟과 9·10)를 적었다. 넷 모두 추천을 골랐다.

> 사용자: (기본 에이전트 assistant의 설계(ADR 0051)를 승인할까요?) "승인 (Recommended)" — 설명: ADR 0051의 상태가 '제안'에서 '승인됨'으로 바뀌고, base-agent 기능이 명세를 쓰는 단계로 넘어갈 수 있게 됩니다. 묻지 않고 정한 것 가운데 1·2·6·7번이 함께 확정됩니다.

> 사용자: (에이전트 설정 파일에 횟수의 끝을 적는 새 칸 둘(ADR 0052)을 승인할까요?) "승인 (Recommended)" — 설명: ADR 0052의 상태가 '승인됨'으로 바뀝니다. base-agent의 첫 티켓이 이 두 칸(모델을 부르는 횟수의 끝, 도구를 부르는 횟수의 끝)을 더하는 계약 변경이 됩니다. 묻지 않고 정한 5번(멈췄다 이어진 실행도 처음부터 다시 센다)이 함께 확정됩니다.

> 사용자: (답을 마크다운으로 그리는 결정(ADR 0053)을 승인할까요?) "승인 (Recommended)" — 설명: ADR 0053의 상태가 '승인됨'으로 바뀝니다. 위젯의 마크다운 표시는 공개 데모와 제품 0.1이 함께 기다리고, 관리 화면의 '원문/그린 모양' 전환은 제품 0.1을 낸 뒤에 시작합니다(3·8·9·10번 그대로).

고르지 않은 선택지는 "승인하되 전환을 앞당김"(관리 화면의 전환이 제품 0.1을 기다리지 않게 계획을 고친다)과 "고칠 것이 있음"이었다.

> 사용자: (PRD 22줄의 문장을 위에 적은 '후'의 글로 고치는 것을 승인할까요?) "승인 (Recommended)" — 설명: PRD의 '참조 에이전트 doc-qa'가 '기본 에이전트 assistant'로 바뀌고, PRD 머리의 상태 줄에 2026-11-10 개정 승인과 근거(ADR 0051)가 더해집니다.

승인 뒤에 한 것. ADR 0051·0052·0053의 `status`와 색인(`docs/adr/README.md`)의 세 행을 `accepted`로 바꿨다. PRD 머리의 status 줄에 "2026-11-10 개정 사용자 승인"과 근거(ADR 0051, 일지 2026-11-10-1345)를 더했다. 기능 계획 셋의 `**설계:**` 줄은 앞 세션이 적은 그대로다(base-agent는 ADR 0051과 ADR 0052, answer-markdown과 admin-answer-preview는 ADR 0053).

## origin/main 합치기와 커밋 전 확인

- `git merge --ff-only origin/main`으로 `a9d7d94`에서 `686ae72`로 옮겼다(#513, #514, #515). 이 브랜치에 커밋이 없어 빨리 감기였고, 들어온 파일 82개 가운데 이 브랜치가 고친 파일은 없었다(`git diff --name-only HEAD origin/main`의 목록과 `git status --short`를 대 봤다).
