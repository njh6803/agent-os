## 이어받은 것

워크트리는 origin/main(`983bf491`)에서 섰다. `tidy-checkouts`가 사람에게 넘긴 것(분리 HEAD 워크트리 일곱, prunable 등록

답을 기다리지 않았다.

## 찾은 사실

사실 조사는 서브에이전트 셋에 맡겼다. 이어 가기 계약 쪽은 보고가 왔고, 거슬러 읽기와 MCP 쪽 둘은 세션 사용량 한도
(429)로 도중에 멈췄다. 멈춘 둘이 스크래치패드에 남긴 결과 파일을 읽고 원인이 되는 코드는 이 세션이 직접 읽었다.
아래 수는 모두 커밋하지 않은 스크래치 스크립트의 것이라 손으로 본 것이고, 각 기능의 명세가 프로브로 다시 잰다.

- **이어 가기 계약(코드를 읽었다).** 운영자 채널의 이어 가기는 `POST /runs/{run_id}/continuation`이고 본문은
  `StartRun`이다(`channel/http/router.py`). core `run()`은 `previous_run`과 `visible_agents`를 함께 받는다
  (`core/run.py`). 표의 면 판정 `EndUserPaths.surface_of`는 `/end-user` 아래에서 시작 경로가 아닌 경로를 모두 실행을
  가리키는 경로로 본다(`http/errors.py:218-222`). 상한의 셈은 `Runs.start(..., end_user=user)` 안이고 요청 글자 수
  검사는 라우트가 부른다(`limits.py`, `end_user.py`). 최종 사용자 실패 항목은 `type`·`message`·`run_id`뿐이고
  `message`는 언제나 `"실행이 실패로 끝났다"`다(`items.py`). `run_failed`는 `error` 문자열 하나이고, 요약 실패는
  `"대화 요약이 실패했다: "`로 시작한다(`core/run.py:776-790`).
- **옛 코드가 새 필드를 만날 때(코드를 읽었다).** `adapters/jsonl.py`의 `_read_event`는 아는 종류의 모르는 필드를 검증
  오류로 올려 트레이스를 손상으로 거부하고, 모르는 종류만 `UnknownEvent`로 보존한다.
- **에이전트가 내는 이벤트(코드를 읽었다).** `_drive`는 에이전트가 낸 `conversation_summarized` 하나만 막고 나머지는
  통과시킨다. 런타임이 `RunFailed`를 만드는 자리는 넷이다(요약 실패 `_summary_outcome`, 기한 `deadline_failure`(두 진입점이
  쓴다), `_drive`의 `except Exception`, run_finished 없이 끝남). 에이전트가 낸 `run_failed`도 그대로 통과한다(셀프 리뷰가
  처음의 "다섯"을 바로잡았다).
- **거슬러 읽기(손으로 봤다, 스크래치 `walk_block.py`·`fail_after_and_cold.py`).** 트레이스 하나에 0.4~1.2ms, 그동안
  이벤트 루프의 하트비트가 같은 길이로 멈췄다. A×1 + B×10,000 → A는 10,001개를 4~14초. 방금 쓴 고리의 첫 읽기는
  1,001개에 7.5~7.7초, 둘째부터 0.3~0.9초(첫 읽기가 왜 느린지는 재지 않았다. 처음에 "디스크 캐시가 빈"으로 적은 것을 셀프
  리뷰가 바로잡았다). `timeout_seconds=0.5`에도 `run_started`까지 6.3초 걸리고 `run_finished`로 끝났다(범위가 시작 이벤트
  뒤다). 스레드로 보내면 하트비트의 가장 긴 공백 16~18ms. 한 에이전트로 1,999번 이어 간 실제
  `run()`은 부른 뒤 `run_started`까지 19.9초였다. `anyio.fail_after`는 동기 코드를 끊지 못했다.
- **MCP 서버 프로세스(손으로 봤다, 스크래치 `measure.py`. 코드를 읽었다, mcp 1.30.0).** `npx`의 everything은 cmd →
  node → cmd → node로 떴다. 계측을 단 회차(`run1.txt`)에서, 정상 종료(E0·E0b)와 닫는 도중의 기한(E3)은 실행 끝과 함께 모두
  내려갔다. 기한이 도구 호출 도중(E1, 5.0→12.93초 `CancelledError`)에 걸리면 맨 위 cmd만 내려가고 node와 그 자식은 실행 끝
  12초 뒤에도 살아 있었고, `_terminate_process_tree`는 불리지 않았다. 같은 모양의 파이썬 FastMCP 서버(S1, 자식 없음)는 남지
  않았다. 계측 없이(`--bare`) 두 번 더 돌린 E1(`run2_bare.txt`, `run3_staged.txt`)도 남았고, 그 둘에서는 명시한
  `gc.collect()` 뒤에 내려갔다. 처음에 bare 회차만 보고 "계측이 비었다"로 적은 것을 두 축이 바로잡았다. `stdio_client`의
  닫기는 stdin을 닫고 `fail_after(2.0)`로 기다려 내려가지 않으면 `_terminate_process_tree`를 부른다
  (`mcp/client/stdio/__init__.py:190-215`).
- **모델과 한도(코드를 읽었다).** 에이전트 매니페스트에는 모델 칸이 없고 모델은 `--model` > `AGENT_OS_MODEL` > 기본값으로
  서버 하나에 하나다(`adapters/anthropic.py`의 `resolve_model_name`). 2만 자는 `conversation_limit`이 없을 때의 기본값이고,
  토큰 세기로 어림하면 한국어 약 21,000토큰, 영어 약 7,100토큰이다(`.scratch/conversation/probes/token_ratio.py`).

## 라운드

라운드는 열하나였다. 처음 둘은 코드 이름과 ADR 용어를 그대로 쓴 선택지였고, 사용자가 셋째 라운드에서 답하지 않고 쉬운
설명을 요청했다. 그 뒤로는 라벨에 실제로 바뀌는 것을, 설명에 장면을 적었다. 사용자가 되물은 셋(압축 계기, 모델별 컨텍스트,
새 대화 권유)에서 추천이 바뀌었다.

1. 묶음.

   > 사용자(질문에 답): "둘로: 이어 가기 + MCP 따로 (Recommended)" — 설명: 이어 가기 기능 하나가 최종 사용자 경로의 이어
   > 가기 계약과 거슬러 읽기를 함께 든다(거슬러 읽기는 이어 가기를 열기 전의 조건이고 같은 경로가 그것을 부른다). 타임아웃
   > 뒤 MCP 서버 프로세스는 따로 떼고, 대화와 무관하므로 web-widget을 막지 않는다. web-widget은 이어 가기 기능만 기다린다.

2. 경로, 요약 실패, 기능 이름.

   > 사용자(질문에 답): "운영자 채널과 같은 모양 (Recommended)" — 설명: `POST /end-user/runs/{run_id}/continuation`, 본문은
   > 시작과 같은 `StartRun`(에이전트, 요청)이고 앞 실행은 경로에만 있다. 새 본문 컴포넌트가 없고, 면 판정이 저절로 '실행을
   > 가리키는 경로'가 되어 500→404 덮기가 걸린다. 시작처럼 요청 글자 수(422)와 동시·시간당 상한(429)을 지나고, 문서화된
   > 에러는 최종 사용자 경로 셋과 같은 401·404·409·422·429·500이다. 응답은 시작과 같은 최종 사용자 항목 스트림이다.

   > 사용자(질문에 답): "이벤트에 원인 필드를 두고 항목에 싣는다" — 설명: `run_failed`에 선택 필드(원인의 종류)를 더하고
   > 실패 항목에도 그 값을 싣는다. 타입으로 갈리는 가장 견고한 길이지만 sdk 이벤트와 계약이 바뀐다. 형식을 올릴지는 선례가
   > 갈린다(ADR 0009의 `prompt` 추가는 형식 2 그대로, ADR 0022는 형식 3으로 올렸다). 이 몫이 이 기능의 계약 티켓을 키운다.

   > 사용자(질문에 답): "end-user-continuation (Recommended)" — 설명: 용어집의 '최종 사용자'와 '이어 가기'를 그대로
   > 묶는다. 이 브랜치 이름(`docs/end-user-continuation-design`)과도 맞고, 앞 기능 `end-user-channel`과 이름이 나란히 선다.

3. 원인의 범위, 형식, 지어낸 원인을 물었다. 머리 칩이 "원인 범위", "형식", "지어낸 원인"이었고 라벨이 "요약 하나만",
   "형식 3 그대로", "런타임만 채운다"였으며 설명도 코드 이름(`_read_event`, `RESUMABLE`)으로 채웠다. 사용자는 답하지 않고 이렇게 보냈다.

   > 사용자: "UI이 선택 화면 줄 때 형식1, 형식2, 결정1, 결정2 이런식으로 설명해주지말고 실제 내용을 알려주고 내용들도
   > 이해하기 쉽게 설명해줄 수 있도록 해줘. 플랜을 세우거나 사용자 결정이 필요하거나 그냥 설명을 해줄 때 등 전부 이해하기
   > 쉽게 설명을 해줘."

   처음에는 자동 기억에 남겼다가, 다음 말을 받고 지우고 `CLAUDE.md` 원칙과 `grilling` 스킬의 라운드 문단에 넣었다. "쉽게
   썼는가"는 린터나 훅이 판정할 수 없어 교정 루프의 순서대로 지침에 둔다.

   > 사용자: "기억에 남기지 말고 지침으로 등록해줘"

   같은 세 질문을 쉬운 말로 다시 올렸다. 첫 선택지의 라벨은 "요약 실패만 따로 안내 (Recommended)", "양식 번호는 그대로
   (Recommended)", "서버만 이유를 적게 막기 (Recommended)"였다.

   > 사용자(질문에 답): "모든 실패의 종류를 안내" — 설명: 요약 실패, 시간 초과, 도구 서버가 켜지지 않음, AI 모델 호출
   > 실패, 반복 횟수 초과, 에이전트 코드의 오류를 모두 다른 이유로 적는다. 운영자도 기록에서 실패 종류를 바로 볼 수 있다.
   > 대신 지금 한데 묶여 처리되는 실패들을 하나씩 가르는 코드가 크게 늘고, 최종 사용자에게 서버 내부 구성(어떤 도구 서버가
   > 있는지 등)의 단서가 보인다.

   > 사용자(질문에 답): "양식 번호는 그대로 (Recommended)" — 설명: 실행 기록 파일 맨 위에는 '이 파일은 3번 양식'이라는
   > 번호가 있다. 칸 하나가 늘 뿐이라 번호는 3으로 둔다. 예전 판의 서버가 새 파일을 읽으면 '모르는 칸이 있다'며 그 파일을
   > 거부할 뿐이라, 잘못 읽고 엉뚱하게 동작할 위험이 없다. 실패한 실행은 애초에 다시 이어 가거나 재개하는 대상도 아니다.
   > 예전에 기록에 칸을 하나 더할 때도 번호를 올리지 않았다.

   > 사용자(질문에 답): "서버만 이유를 적게 막기 (Recommended)" — 설명: 에이전트는 플러그인 개발자가 쓴 코드라 서버가
   > 완전히 믿지 않는다. 지금은 에이전트가 실패 기록을 직접 만들어 내도 그대로 통과한다. 이 안은 이유가 든 실패 기록을
   > 에이전트가 내면, 그 실행을 이유 없는 일반 실패로 끝낸다. 에이전트가 '대화 요약' 기록을 만들지 못하게 막는 규칙이 이미
   > 있고 그것과 같은 방식이다. 이를 확인하는 테스트가 하나 늘어난다.

   "모든 종류"를 골라 "이유 없는 일반 실패"는 원인 "에이전트 코드"가 된다. 합의 요약에서 짚었다.

4. 거슬러 읽기, 도구 서버, 안내 문구. 이벤트 루프와 스레드를 "일꾼 하나"와 "별도 일꾼"으로 풀었다.

   > 사용자(질문에 답): "별도 일꾼 + 읽는 개수 상한 (Recommended)" — 설명: 이어 가기를 시작할 때의 읽기는 별도 일꾼이
   > 맡아 서버가 멈추지 않는다. 동시에 읽는 기록 수에 상한(예: 수백 개)을 두어, 별도 일꾼으로 옮기기 어려운 '승인 뒤
   > 재개'의 읽기도 짧게 끝나고, 최종 사용자가 첫 응답을 오래 기다리지 않는다. 상한을 넘은 대화를 어떻게 할지는 다음
   > 질문에서 정한다.

   설명의 "동시에 읽는"은 잘못 쓴 말이다. 상한은 거슬러 읽기 한 번이 읽는 기록 수다.

   > 사용자(질문에 답): "재현하고 고치고 Linux도 확인 (Recommended)" — 설명: 재현 측정을 저장소에 남기고, 제한 시간에
   > 걸려도 정리 절차(입력 닫기 → 기다리기 → 프로세스 묶음 통째로 끄기)가 끝까지 돌게 고친다. CI(Linux)에서도 프로세스가
   > 남지 않는지 본다. 이어 가기나 web-widget과 상관없이 나란히 진행할 수 있다.

   > 사용자(질문에 답): "위젯이 이유별 문구를 정함 (Recommended)" — 설명: 서버는 지금처럼 고정 문구 한 문장('실행이
   > 실패로 끝났다')과 이유 값만 보낸다. 실제 화면 문구는 위젯이 이유마다 정한다. 문구를 화면 디자인과 함께 다듬기 쉽고,
   > 문구를 바꿔도 서버와의 약속(계약)이 바뀌지 않는다. 이유 값을 모르는 위젯은 고정 문구를 그대로 보여 주면 된다.

## PR 리뷰

PR #245. CodeRabbit은 두 푸시 모두 OSS 한도에 걸려 리뷰가 없었다. claude-review는 첫 푸시(`06be28c8`)와 main을 합친 푸시
(`d8b61b62`)에서 두 번 돌았고 Critical·Major는 없었다.

- **첫 회차(Minor 넷, Nit 셋).** ADR 0031의 "닫힌 목록"과 "목록은 명세"가 한 문단에 섞인 것은 고쳤다. 명세가 목록을 정해도 결정을
  다시 열지 않고, 계약 티켓이 이 ADR의 이력 한 줄로 남긴다. rules 갱신은 `plan.md` 행이 첫 계약 티켓의 몫으로 이미 적었고, 손으로
  본 수는 ADR이 그렇다고 밝히며 명세가 다시 잰다. "거슬러 읽기" 문단의 포인터 둘은 바뀐 두 문장이 이어지지 않아 `adr.md`대로
  둔다. ADR 0023의 포인터 자리와 옛 문장을 고쳐 쓰자는 안은 `adr.md`(포인터는 그 문장 바로 뒤, 본문의 다른 글자는 고치지 않는다)대로
  두고, 환경 서술은 근거 규칙이 재현 조건으로 요구한다.
- **둘째 회차(Minor 둘, Nit 하나).** Considered Options 두 줄의 포인터는 `adr.md`의 "달지 않는 것"(거부한 안의 근거)이라 지웠다.
  셀프 리뷰 표준 축이 판단 항목으로 달게 한 것을 규칙 문구대로 되돌린 것이다. 수치의 근거와 ADR 0031의 열린 목록은 첫 회차와

닫은 지적은 이유를 PR 코멘트에 남겼다.
