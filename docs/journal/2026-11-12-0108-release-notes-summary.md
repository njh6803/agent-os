## 사용자 프롬프트

첫 질문은 ADR 0056이 정한 릴리스 노트를 다시 설명해 달라는 것이었다.

> 사용자: 릴리즈 노트는 어떤식으로 작성되는지 예시랑 언제 작성되는지 다시 알려줘

ADR 0056 결정 "판마다 나오는 것"·"판이 나는 때"·"번호"·"출시 후보와 정식 판"을 읽고 답했다. 판 내기 워크플로가 아직 없다는 것은 주 체크아웃에서 `ls .github/workflows/`가 `ci.yml`과 `claude-code-review.yml` 둘만 내고 `git branch -r --list 'origin/dev*'`가 아무것도 내지 않은 것으로 손으로 봤다.

이어서 사용자가 다른 곳의 프롬프트를 붙여 넣고 물었다.

> 사용자:
> ```
> main 브랜치에 풀 리퀘스트가 방금 병합되었습니다. 이 PR에 대한 릴리스 노트 항목 초안을 작성하세요.
>
> 1. PR 제목, 설명, diff를 읽으세요. 사용자에게 보이는 변경 사항이 새 기능, 버그 수정, 호환성이 깨지는 변경, 내부 전용 리팩터링 중 무엇인지 파악하세요.
> 2. 변경 사항이 내부 전용(테스트, CI, 빌드 도구, 주석, 사용하지 않는 코드 제거, 순수 리팩터링)이라면 작업을 중단하고 “내부 변경 — 릴리스 노트 없음.”이라는 댓글을 게시하세요. 이런 변경에 대해서는 항목 초안을 작성하지 마세요.
> 3. 그렇지 않으면 기여자가 아닌 최종 사용자를 위한 한 단락짜리 항목 초안을 작성하세요. 명령형으로 작성하세요. 전문 용어와 내부 코드명은 피하세요. 파일 경로, 함수 이름, 커밋 SHA는 언급하지 마세요.
> 4. 항목을 신규, 개선, 수정, 호환성 변경 중 하나로 분류하세요.
> 5. 호환성이 깨지는 변경이라면 사용자가 마이그레이션하기 위해 해야 할 일을 명시적으로 나열하세요.
> 6. 초안을 PR 댓글로 게시하세요. 저장소에 명확한 CHANGELOG.md 또는 docs/changelog 경로가 있다면 한 줄짜리 “권장 변경 로그 위치” 힌트를 포함하세요.
>
> 초안은 2~4문장으로 짧게 작성하세요. 긴 릴리스 노트는 읽히지 않습니다.
> ```
>
> 이 내용 참고하는 건 어때

붙여 넣은 프롬프트는 돌리지 않고 견주기만 했다. 고쳐서 들이기를 권했고, 어긋나는 곳 다섯 가운데 첫째로 "출시 PR 하나에는 기능 수십 개가 들어 있어서 한 단락으로 쓸 수 없다, 계기를 dev 병합으로 바꿔야 한다"고 답했다. 사용자가 그것을 바로잡았다.

> 사용자: dev 브랜치에서 기능 하나 끝나면 main으로 병합하는거 아니야?

계기는 사용자가 맞았다. ADR 0043은 제목이 "티켓 PR은 dev로 가고 기능이 끝나면 dev를 main에 merge 커밋으로 올리며 …"이고, 주기나 티켓마다 올리는 선택지를 거부하는 Considered Options의 설명이 "기준은 기능 하나가 done인 때다"로 끝난다. 이 세션은 ADR 0043을 열기 전에 출시 PR의 크기를 어림으로 말했다. 바로잡은 뒤 결론이 뒤집혔다. main에 병합될 때가 오히려 맞는 계기이고, 그 기능을 운영자에게 설명하는 단락이 판의 요약이 된다. "문서 PR마다 '노트 없음' 댓글이 쌓인다"는 둘째 지적도 거의 사라졌다. 이때 세션은 "출시 PR 하나에는 기능 하나가 들어 있다"고 사용자에게 답했는데, 이것은 다시 넓게 말한 것이었다. 출시 PR은 개발 브랜치의 머리를 올리므로(`CONTEXT.md` 출시 PR) 나란히 진행 중인 다른 기능의 티켓도 함께 실릴 수 있다. 셀프 리뷰의 명세 축이 잡았고(아래 "셀프 리뷰"), 기능 계획의 안은 기능마다 단락 하나를 쓰는 꼴로 고쳤다.

앞 답을 닫으며 세션은 "이 안을 release-image 기능 계획에 검토할 안으로 적어 둘까요?"를 묻고 버튼 "기능 계획에 적기"와 "ADR 이력으로"를 보였다. 사용자는 고르지 않고 위의 바로잡음을 물었다. 바로잡은 답을 닫으며 "바로잡은 안을 release-image 기능 계획에 검토할 안으로 적어 둘까요?"를 묻고 버튼 "기능 계획에 적기"와 "지금은 안 함"을 보였고, 사용자가 첫째를 골랐다.

> 사용자: 기능 계획에 적기

## 쓴 것

- `.scratch/release-image/plan.md` 본문의 "수락:" 앞에 검토할 안을 더했다. 명세가 검토한다는 것, 지금 노트의 약점 둘(개발자의 말, 제목이 담지 못한 할 일), 안의 출처(붙여 넣은 프롬프트를 고친 것)와 옮기지 않은 단계 셋, 계기(출시 PR이 열릴 때 별도의 잡, 핫픽스는 그 PR 하나), 단락의 단위(기능마다 하나. 출시 PR에 다른 기능의 티켓도 실릴 수 있다), 읽을 재료(기능 계획, 명세, 실린 티켓 PR의 제목), 명세에 넘긴 물음(커밋을 기능으로 묶는 길, 끝나지 않은 기능의 단락, 열린 동안 커밋이 더해질 때, 맨 위 두 자리와의 차례), 독자(운영자), 분류(제목 접두가 정하고 모델은 경고만), 노트의 모양(단락들 아래 지금의 제목 목록, 단락이 없는 PR은 목록에만, 판 내기는 기다리지 않는다), 리뷰 봇을 끄는 ADR 0043의 규칙과 갈리는 것, ADR 0056을 바꾸므로 고르면 이력과 승인이 필요하다는 것, 돌려 보지 않았다는 것이다. 셀프 리뷰를 반영해 고친 뒤의 모양이다.
- `uv run python tools/plan_table.py`를 돌렸다. 종료 코드 0이고, 이어서 친 `git status --short`가 `.scratch/release-image/plan.md` 하나만 내어 `.scratch/plan.md`가 바뀌지 않은 것을 손으로 봤다. 본문은 표에 들지 않는다(`docs/agents/issue-tracker.md` 전체 계획 절).

## 판단한 것

- **ADR이 아니라 기능 계획에 적는다.** 안은 ADR 0056 결정 "판마다 나오는 것"의 노트 문장을 바꾸지만, 초안의 품질을 돌려 보지 않았고 release-image의 명세는 dev 전환 뒤에야 시작한다(같은 기능 계획 본문 첫 문장). 지금 ADR에 이력을 쌓으면 돌려 보지 않은 안을 결정으로 적게 된다. 기능 계획에 적으면 명세가 그 안을 읽고 지난 제품 PR 몇 개에 돌려 본 뒤 고를 수 있다. 첫 물음에서 이 길과 ADR 이력으로 가는 길을 버튼으로 보였고, 사용자는 바로잡은 안을 다시 물었을 때 기능 계획에 적기를 골랐다(위 "사용자 프롬프트"). 둘째 물음의 다른 버튼은 "지금은 안 함"이었으므로, 사용자가 ADR 이력을 마다한 것은 아니다.
- **분류의 원천은 제목 접두 하나다.** 붙여 넣은 프롬프트는 모델이 네 분류를 새로 정한다. ADR 0056의 판 번호와 "올릴 때 할 일" 묶음은 접두로 정하므로, 모델이 올릴 때 운영자가 손댈 것이 있는 변경으로 읽었는데 제목에 느낌표가 없으면 노트의 단락과 묶음이 갈린다. 그 판에 `fix`만 있으면 끝자리만 올라 "끝자리만 오른 판은 이미지 태그만 바꾸면 된다"는 약속도 깨진다. 그래서 모델은 접두와 diff가 맞지 않아 보일 때 경고만 하게 적었다. 붙여 넣은 프롬프트의 "개선" 분류는 옮기지 않았다. ADR 0056의 묶음은 셋(새 기능, 고친 것, 올릴 때 할 일)이고, `feat`·`fix` 밖의 접두를 어느 묶음에 싣는지는 이미 명세의 몫이다(ADR 0056 Consequences "명세가 리눅스에서 재거나 정하는 것").
- **독자는 운영자다.** 붙여 넣은 프롬프트의 "최종 사용자"는 이 저장소의 용어로 위젯으로 실행을 요청하는 사람이고(`CONTEXT.md`), 판을 올리며 노트를 읽는 사람은 운영자다. 그대로 두면 모델이 설정과 환경 변수를 전문 용어로 보고 뺄 수 있다(어림).
- **변경 로그 위치 힌트는 옮기지 않았다.** 저장소에 `CHANGELOG.md`가 없고 노트의 자리는 GitHub 릴리스다(ADR 0056).
- **초안을 쓰는 때는 병합 뒤가 아니라 출시 PR이 열릴 때다.** 병합 뒤에 쓰면 같은 푸시로 도는 판 내기와 경합한다. 판 내기가 댓글을 기다리지 않게 하고 댓글이 없으면 제목 목록만 싣게 해, 모델 호출의 실패가 판 내기를 멈추지 않게 했다.

### 표준 축의 보고

Critical 0, Major 1, Minor 3, Nit 1. 인용과 주장은 모두 원문과 맞았다고 했다(ADR 0056 결정 "판마다 나오는 것"의 말줄임 인용, ADR 0043 Considered Options와 Consequences "티켓 검사와 봇", `claude-code-review.yml` 45행의 `uses:`, ADR 0056 Consequences의 명세 몫, `CONTEXT.md`의 최종 사용자).

1. Major. 기능 계획의 "노트는 PR 제목을 묶은 것뿐이라"는 닫힌 주장이고 반례가 있다. 같은 결정이 0.1.0과 그 출시 후보의 노트 맨 위에 소개 글 자리를 둔다. 안의 "맨 위"가 그 자리(와 취약점 경고)와 겹치는데 차례를 적지 않았다. 한 판의 노트는 지난 판 뒤의 변경 전부라 요약 댓글이 여럿일 수 있는데 "그 댓글"을 단수로 썼다. 일지의 "단락 하나가 판의 요약이 된다"도 같은 단순화다.
2. Minor. 일지 "판단한 것"의 "호환성 변경으로 읽었는데 제목에 느낌표가 없으면"은 ADR 0056의 느낌표(올릴 때 운영자가 손댈 것이 있는 변경)와 말이 어긋난다.
3. Minor. 한 문단에 새 문장 열세 개쯤이 수락 앞에 붙어 처음 보는 사람이 읽기 어렵다(`CLAUDE.md` 원칙의 사람에게 보이는 글). 기존 문단이 그랬으니 낮게 본다.
4. Minor. 일지의 ADR 0043 인용. "기준은 기능 하나가 done인 때다"는 거부한 선택지의 설명 끝에 붙은 말이고, 제목 인용은 뒤의 "hotfix는 …"을 말줄임 없이 끊었다.
5. Nit. 기능 계획의 "제목 한 줄만 실려 무엇을 할지 알 수 없다"는 보편 주장이다. 제목이 할 일을 다 담을 수도 있다.

baseline smell로는 일지 "쓴 것"이 기능 계획의 새 문장을 거의 다시 나열한다는 Duplicated Code를 판단 문제로 냈다.

### 표준 축의 판정

1. 고친다. 결정의 원문(ADR 0056 결정 "판마다 나오는 것"의 소개 글 자리와 "취약점 점검"의 경고)을 다시 읽어 맞다고 봤다.
2. 고친다. ADR 0056 결정 "번호"의 말로 바꾼다.
3. 둔다. 기능 계획의 본문은 한 문단이고 수락이 끝에 오는 것이 이 저장소의 모양이다(`docs/agents/issue-tracker.md` 전체 계획 절이 본문을 "옛 표의 내용 칸이었던 글"이라 적고, `.scratch/mcp-http/plan.md` 같은 다른 기능 계획도 한 문단 끝에 수락을 둔다. `tools/morning_collect.py`가 "수락"을 읽는다는 것은 Grep으로 이름만 봤다).
4. 고친다. 선택지의 설명이라는 것을 밝히고 제목 인용에 말줄임을 단다.
5. 고친다. 제목이 담지 못한 할 일은 실리지 않는다는 꼴로 좁힌다.

smell은 둔다. 일지는 기록이라 그 단계에서 무엇을 썼는지를 따로 남긴다.

### 명세 축의 보고

Critical 0, Major 2, Minor 4, Nit 1. ADR 0056·0043의 절 이름과 인용, `uses:` 줄, `CHANGELOG.md`가 없다는 것, 두 경로가 커밋 검사의 면제 모양이라는 것(`exempt()`를 불러 봤다고 했다), `CONTEXT.md`의 최종 사용자는 맞았다고 했다. 첫 사용자 프롬프트는 세션 기록 검색에서 같은 글자로 나왔고, 나머지 프롬프트와 세션의 자기 인용은 지금 세션의 기록을 읽지 못해 대 보지 못했다고 했다.

1. Major. 요구의 "판 내기가 실패해 다음 판에 기능 둘이 실리면 요약 단락도 둘이 됩니다"가 기능 계획에 없고 "그 댓글"이 단수다.
2. Minor. 붙여 넣은 프롬프트에서 버린 단계(내부 변경 댓글, "개선" 분류, 변경 로그 힌트)와 ADR 0056의 "사람이 쓰는 글이 없다"와 부딪히지 않는다는 점이 기능 계획에 없다.
3. Minor. 일지가 버튼의 차례를 뭉갰다. 첫 물음("ADR 이력으로"가 있던 것)을 적지 않았고, "두 길을 버튼으로 보였고 기능 계획을 골랐다"는 실제 마지막 선택지("기능 계획에 적기"/"지금은 안 함")와 다르다.
4. Minor(범위 넘침). "출시 PR에 커밋이 더해지면 다시 쓰고"는 사용자에게 보인 적이 없고 푸시마다 모델을 다시 부르는 값이 붙는다.
