## 이어받은 것

`tidy-checkouts`가 지운 것은 브랜치 `worktree-mutate-buffer-eol-and-restore-retry`와 휴지통의 `web/node_modules` 넷이다.
사람에게 넘긴 셋(머리가 다른 `skill-check-and-retro-section`, 판정 사이에 등록이 사라진 `.claude/worktrees/mutate-followups`
폴더, 같은 이름의 세션이 실행 중인 `chore/mutate-followups` 브랜치)은 지시문대로 보고만 하고 답을 기다리지 않았다. 마지막
것은 도구가 `remove-branch`로 지우라고 판정했는데, 그 브랜치가 제목인 세션이 돌고 있어 스킬의 판정 3에 따라 치지 않았다.
`remove-branch`의 판정이 실행 중인 세션의 제목을 보지 않는 틈으로 보인다(회고 후보). 휴지통의 `.venv` 넷은 python.exe
셋이 모듈을 올려 두어 남았다.

## 찾은 사실(코드를 읽었다, `ae538ca6`)

- 최종 사용자 경로는 시작·결정·구독 셋이고 이어 가기가 없다(`channel/http/end_user.py`). 표의 면 판정은 그 접두사 아래의 시작
  경로가 아닌 경로를 실행을 가리키는 경로로 보고 `PluginError`를 모두 404로 덮는다(`http/errors.py`의 `Surface`).
- 런타임이 `run_failed`를 쓰는 자리는 넷이다(`_summary_outcome`, `deadline_failure`, `_drive`의 바깥 `except`, run_finished
  없이 돌아옴). `_drive`의 바깥 `except`는 멈춘 실행만 거르고 결말이 정해졌는지(`_settled`)는 보지 않아, `run_finished` 뒤
  도구 연결 닫기가 실패하면 `run_failed`가 하나 더 붙는다. 기한 쪽(`deadline_failure`)은 같은 경우를 이미 막는다.
- 에이전트가 낸 이벤트 가운데 막히는 것은 `conversation_summarized` 하나이고, `plugins/`의 에이전트 가운데 `run_failed`를
  내는 것은 없다.
- `_drive`에서 에이전트 밖이면서 연결·선언 확인·재생 대조(`replay_event`)·닫기가 아닌 자리에서 나는 예외가 없어, 실패 원인
  "그 밖"을 지금 내는 자리가 없다.
- 관리 화면의 필드 이름 표는 `satisfies Record<EventField, string>`이라 이벤트에 필드가 늘면 컴파일에서 깨진다
  (`EventItem.tsx`).
- 설치된 anyio 4.15.1의 `to_thread.run_sync`는 기본값에서 스레드를 기다리는 범위를 `shield=not abandon_on_cancel`로 연다.

## 측정

`walk_budget.py`가 지금의 `gather_continued`를 실제 `JsonlTrace` 위에서 고리 마흔두 개로 돌렸다(약 10분, 측정이 아닌 회차
0). 방금 쓴 트레이스의 첫 읽기는 하나에 6.9~10.1ms이고 프롬프트 크기와 거의 무관했고, 둘째 읽기는 0.3~1.0ms였다. 루프
위에서 읽으면 읽는 내내 박동이 0이었고, 스레드로 보내면 가장 긴 공백이 15.2~34.1ms로 잠들기만 한 대조군(18.4~22.1ms)과 같은
크기였다. 인터뷰가 손으로 본 수는 같은 크기로 다시 나왔다. 이 값으로 교환 수 기준을 50(재개가 루프 위에서 읽는 52개가 둘째

기계에서 돌았다.

셀프 리뷰 뒤 프로브를 고쳐(불리언 인자를 자리 함수 둘로, 대조군 창을 1초와 10초로) 한 번 더 돌렸다(약 10분, 측정이 아닌 회차

**명세 축(Major 1, Minor 9, Nit 2).** 고친 것:

- CLI는 `anyio.run`이 아니라 `asyncio.run` 위다(`main.py:120-121`).
- 옛 대화가 이 기능 전의 운영자 채널과 CLI에서만 생긴다고 적은 문장의 반례(이 기능 전 최종 사용자 시작 경로의 실행, 계약
  티켓과 지도를 쓰는 티켓 사이의 틈). 옛 대화를 지도를 쓰기 시작하는 티켓 전에 쓰인 실행에서 시작한 대화로 고쳤다.
- ADR 0023 새 이력의 인용이 2026-10-05 이력의 원문과 달랐다. 원문 그대로 옮겼다.
- 구독은 자기 실행 읽기만 불러 주체 뒤의 `PluginError`가 없다. 결정과 구독 모두 404에서 500으로 바뀐다고 적은 자리를
  결정만으로 고쳤다(명세, ADR 이력, `plan.md`).
- 잔존 grep에 옛 논증의 말(하위 타입을 뺀 뒤 남는 것이 깨진 것이라는 풀이, "하위 타입 다섯")을 더했다. 새 하위 타입은 깨진 것이라
  ADR 0014의 2026-09-26 기준("깨졌나")은 그대로이고, 그 기준을 풀어 쓴 문서의 말만 "4xx 하위 타입"으로 좁힌다. ADR 0023
  이력에 그 관계를 적었다.
- 재개 대조의 던지는 자리 가운데 테스트가 없던 둘(재생의 도구 어긋남, 결정 대조의 모델 호출)을 테스트 결정에 더했다.
- 에이전트 몫의 실패 뒤 닫는 도중에 기한이 오면 결말이 무엇인지 비어 있었다. "먼저 난 실패"가 기한보다 앞선다고 정했고,
  지금 시간 초과를 기대하는 기존 테스트의 기대가 바뀐다고 적었다.
- `plan.md` 원문이 요구한 예산이 없었다. 재개가 이벤트 루프를 막는 최악 0.5초를 예산으로 두고 첫 읽기 하나의 최댓값(약
  10ms)으로 나눠 50을 얻었다(다시 돈 회차에서 52개의 첫 읽기는 0.37~0.48초).
- 지침의 동작 문장을 동작을 들이는 티켓이 쓰는 결정에 표시가 없었다. ADR 0022 이력의 "지침도 첫 티켓이 고친다"와 다른
  까닭을 적고 "(명세가 정했다)"로 표시해 스물다섯이 되었다.
- 사용자 답 1의 설명("기존 테스트에 이어 가기 요청을 하나 붙입니다")을 다시 열었고, 고른 설명의 다섯 자리 밖인 sdk
  이음매를 더했었다. 붙인다로 고치고 sdk 쪽 확인은 계약 파일과 기록 파일 테스트로 옮겼다.

- 스레드 공백의 표현이 README보다 넓었다(대조군보다 긴 34ms·25ms를 뭉갰다). 고쳤다.

**표준 축(Major 1, Minor 5, Nit 5).** Major는 위와 같다. 고친 것:

- 잔존 grep의 `previous_run\` 을 따라`는 공백이 있어 `core.md`의 "`previous_run`을 따라"에 걸리지 않았다. 공백 유무를 함께
  잡는 정규식으로 바꿨다.
- 계약 티켓이 끌고 오는 것에 생성 타입을 단 관리 화면의 테스트 픽스처(`RunPage.test.tsx`·`RunPage.decision.test.tsx`)를
  더해 여섯이 되었다.
- 프로브의 해석: 대조군의 창(1초)이 측정 창(최대 약 10초)과 달라 최장 공백을 견줄 수 없었다. 대조군을 1초와 10초 둘로
  늘리고, 루프 위의 읽기를 양성 대조로 적고, "윈도우 타이머의 눈금"은 가르지 않은 설명이라고 고쳐 다시 돌렸다. README의
  "열 배 안팎" 어림은 어느 값의 열 배인지 없어 고쳤다.
