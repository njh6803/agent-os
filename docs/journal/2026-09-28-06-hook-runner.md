## PR #94 리뷰 반영

claude-review 둘(d3bf5bd). 저장소를 가리키는 `GIT_*` 목록이 conftest와 러너에 글자 그대로 둘이었다 → conftest가 러너의
`REPO_LOCATION_VARS`를 import해 원천 하나. CLI 진입점 테스트 둘이 저장소 루트를 다시 계산했다 → 이미 import한 `ROOT`.

CodeRabbit 넷(Major 셋, Minor 하나). 셋은 러너가 초록을 거짓으로 낼 수 있는 자리라 전부 반영했다.

- `hookSpecificOutput`에 `hookEventName`이 없어도 deny로 통과했다. Claude Code는 그 필드를 요구하므로 그런 출력은 실제 세션에서
  유효하지 않다 → 필수 필드로 하고 값이 훅이 등록된 이벤트와 같은지 대조한다. `registered_hooks`가 이벤트와 `timeout`을
  `Registration`으로 돌려주고, 같은 훅이 이벤트 둘에 등록되면 거절한다. 단위 테스트가 그 누락 형태를 정상 사례로 쓰고 있었다 —
  표가 아니라 테스트가 거짓 전제를 굳히던 자리다.
- 빈자리가 한 방향(등록됐는데 표에 없다)만이었다. settings.json에서 등록만 지우면 러너는 사례를 직접 돌려 초록인데 실제 세션에는
  그 훅이 없다 → "표에 있는데 등록되지 않았다"를 더했고 등록되지 않은 훅의 사례는 돌리지 않는다. 변이 쌍에 등록 쪽을 빼는 테스트.
- 자식 `subprocess.run`에 시간 제한이 없어 훅 하나가 멈추면 pre-commit이 멈추고 커밋도 멈춘다 → settings.json이 그 훅에 준
  `timeout`(초, 없으면 Claude Code 기본 60)을 그대로 쓰고 `TimeoutExpired`는 어긋남 `timeout`이다. 제한 0초로 그 길을 재는 테스트.
- KICKOFF 7단계의 "실제 입력으로 실행 확인"이 런타임 페이로드 호환성까지 검증한다고 읽힐 수 있다 → 실제 훅 파일을 손으로 흉내 낸
  페이로드로 돌리는 것이라 런타임 입력 계약은 검증하지 않는다고 적었다. 회고 3(실제 페이로드 캡처)의 전제를 리뷰 봇이 같은
  자리에서 짚었다.

## 갈린 곳

- **승인의 해석.** 지시문은 "승인되면"이라 했고 사용자는 지시문을 그대로 넣었다. 시작 프롬프트가 반영을 말하므로 승인으로
  읽었다. 3~6은 후보로 남아 있다.
- **`stages: [pre-commit]`은 러너에만.** 다른 always_run 훅(pyright·pytest·검사들)은 commit-msg 단계에서 한 번 더 돈다 — 커밋마다
  테스트가 두 번이다. 지시문 밖이라 고치지 않고 회고 후보로 적었다.
- **CI 반영은 다음 PR.** operations.md는 pre-commit과 CI가 같다고 적는데 러너와 인용 대조는 pre-commit에만 있다. 워크플로 파일은
  별도 PR로 먼저 병합하는 규약이라 그렇다고 적었다.
- **KICKOFF 분리의 폭.** "절 분리"만 지시받았고, 감사(일지 04)가 권한 9·10단계의 축약까지 했다. 옮긴 줄은 새 파일에서 전부 "더한
  줄"이라 인용 대조가 부록 B의 프롬프트 예시 일곱을 경고했다 — 원문이 저장소 밖인 인용이라 설계상 감수한다.

1. **[검사] CRLF 가드.** `Path.write_text`가 Windows에서 CRLF를 쓰는 함정을 두 세션 연속 밟았다(일지 04 retro-queue.md, 이 세션

2. **[도구 경제] always_run 훅의 두 번 실행.** `default_install_hook_types`가 pre-commit·commit-msg 둘이라 `stages`가 없는 훅은

3. **[정보 접근] 훅의 실제 페이로드 모양.** 표는 손으로 흉내 낸다. 지시문 훅이 `transcript_path` 없이는 침묵인 것을 러너가 아니라
