# 2026-09-22 · 인터럽트 05: 거부한다

인터럽트 슬라이스의 다섯째 티켓. 04가 승인해 재개하는 길을 냈고, 여기서 거부가 실행을 죽이지 않고
사유를 모델에게 되돌린다. `/implement`로 새 세션에서 시작했고 브랜치는 `feature/05-deny`. 계약은
닿지 않았다 — `ApprovalDenied`는 티켓 01이 이미 만들어 두었다.

## 한 것

- **`Decision = Approve | Deny(reason)`.** 04가 "05가 `| Deny`를 더한다"고 자리를 비워 둔 곳이다.
  사유가 필수인 이유는 `ApprovalDenied.reason`이 필수 필드이기 때문이고, 채널이 빈 문자열을
  지어내면 사유 없는 거부가 기본값으로 굳는다. `Deny.__post_init__`가 빈 사유를 막아 core가
  뒷단이다(셀프 리뷰가 넣었다).
- **게이트의 분기 하나.** `_Context._call`이 승인 대상에서 `Deny`를 받으면 도구를 부르지 않고
  `_deny`가 `tool_called(ok=false, content="승인자가 거부했다: {사유}")`를 기록해 돌려준다. 루프는
  그 결과를 `ToolMessage(status="error")`로 모델에 되돌려 계속하고, `ctx.tool()`은 `ToolError`로
  올린다. 이미 있는 도구 실패 경로 그대로라 새 실패 경로가 없고, 루프와 직접 호출이 같은 자리를
  지나므로 경로별 구현도 없다. 결정의 갈래는 `match` + `assert_never`라 셋째 결정이 생기면
  pyright가 잡는다.
- **`resume()`이 결정에 따라 `approval_granted`나 `approval_denied`를 재생 전에 쓴다.** 재생이
  무엇을 하든 누가 왜 막았는지는 남는다.
- **CLI.** `agent-os resume <run_id> --deny --reason <사유>`. 사유 필수는 argparse 로 표현되지
  않아 `_decision()`이 `parser.error`로 진단한다(종료 코드 2, 인자 오류와 같은 코드). 공백만 있는
  사유도 없는 것으로 본다. 일시정지 출력에 거부 명령 안내 줄이 붙었다.
- `.claude/rules/core.md`(게이트·재개 줄), 티켓, 이 일지.

## 티켓이 예고하지 않은 성질 하나

**거부는 재생에서도 거부로 남는다.** 거부된 호출이 `tool_called(ok=false)`로 트레이스에 있으므로,
그 뒤 다른 승인 대상에서 멈춰 다시 재개하면 재생기가 그 실패를 되살려 도구가 실제로 불리지 않는다.
뒤의 승인이 앞의 거부를 뒤집지 않는다. 별도 코드가 아니라 "거부를 도구 실패로 기록한다"는 결정의
결과인데, 그래서 더 테스트로 못 박아 둘 가치가 있었다. 결정이 바뀌면 그 테스트가 먼저 빨개진다.

## 티켓 밖의 작은 결정 하나

`--approve --reason`도 거부한다. `ApprovalGranted`에 사유를 담을 자리가 없어 조용히 버리면 승인자가
적은 말이 어디에도 남지 않는다. 이 저장소가 반복해 고른 "조용히 버리지 않는다" 쪽이고 한 줄이라
물어보지 않고 했다. 티켓 코멘트에 적었다.

## TDD 의 모양

주 이음매 여섯, CLI 인자 다섯, CLI 표면 셋이 `ImportError`로 통째로 빨갰다(`Deny`가 없다). core 를
고치자 주 이음매 여섯이 한 번에 초록이 됐고 — 게이트 분기 하나가 전부였다는 뜻이다 — CLI 여덟은
`--deny`·`--reason`을 붙이고 `_decision()`을 고친 뒤 초록. 설계 결함을 잡은 테스트는 없었다. 04가
`_decision()`이 플래그를 실제로 읽게 고쳐 둔 덕분에 "거부가 조용히 승인으로 도는" 자리가 처음부터
없었다.

## 셀프 리뷰

두 축이 Minor 1, Nit 3, 스멜 3(표준), 부분 구현 1, 범위 밖 5(명세)를 냈다. 고친 것 넷.

- **안내한 거부 명령의 자리표시자가 진짜 사유로 기록됐다.** 명세 축이 잡았고 가장 좋은 지적이다.
  일시정지 출력에 `--deny --reason "<사유>"`를 적고 "그대로 실행해도 성립한다"는 테스트까지 썼는데,
  그것은 곧 `<사유>`라는 지어낸 사유가 기본값으로 굳을 수 있다는 뜻이다. 티켓이 막으려던 "빈
  문자열을 지어내지 않는다"를 안내 줄로 우회하는 모양이다. 안내 줄을 `--reason`에서 끝내 그대로
  치면 argparse 진단(코드 2)이 나고 사유를 이어 적어야 성립하게 바꿨다. 테스트도 그것을 잰다.
- **빈 사유 방어가 CLI에만 있었다.** `resume`이 core 함수라 `http-channel`이 오면 다시 열린다.
  `Deny.__post_init__`가 막는다. `sdk`의 `ApprovalDenied.reason`을 `min_length=1`로 조이는 것이
  더 근본이지만 계약 변경이라 후속 후보로 남겼다.
- **`isinstance(decision, Deny)` 두 곳이 `Approve`를 암묵 폴스루로 뒀다.** 표준 축의 Repeated
  Switches. CLI 쪽 docstring이 걱정한 "거부가 조용히 승인으로 도는" 모양이 core에서는 열려 있었다.
  `match` + `assert_never`.
- 동사 통일(`_refuse`→`_deny`), 이름(`_decided`→`_decision_event`, `DENIED` 인라인), CLI 테스트
  이름의 "거부한다"가 도메인 용어와 겹치는 것("진단을 낸다"), `--deny`로 없는 실행 식별자를 직접
  재는 테스트 하나.

남긴 것: `--approve --reason` 거부·`strip()`·"거부는 재생에서도 거부" 테스트는 의도한 결정. 새 테스트
여섯의 arrange 중복은 이름이 행동 명세인 관행과 상충해 헬퍼로 걷지 않았다.

## PR 직전 CodeRabbit CLI

1건, Critical, 유효. 이 세션에서 가장 값진 지적이다.

**결정이 "멈춘 그 호출"이 아니라 "재개 뒤 첫 승인 대상 호출"에 적용됐다.** `_read_paused`가
`run_paused`를 경계 이벤트로 걸러 버리므로 멈춘 도구·인자가 재개 흐름 어디에도 없었고, 게이트는
`name in approvals`만 보고 결정을 소비했다. 재생 대조는 기록이 있는 구간만 보므로 기록 **끝** 이후의
변경 둘이 지나간다. 대기 중 매니페스트에서 그 도구가 `requires_approval`에서 빠지면 거부한 도구가
게이트 없이 실행되고 결정은 뒤의 다른 도구에 적용된다. 에이전트가 바뀌어 멈춘 자리 다음에 다른 승인
대상을 부르면 `send`를 승인했는데 `delete`가 실행된다. ADR 0009가 "재생하지 않고 모델을 다시
부른다"를 기각한 이유가 그대로 열려 있었다. 04부터 있던 자리인데 04의 두 축 셀프 리뷰도, 04의
CodeRabbit도, 이 세션의 두 축도 못 봤다. 게이트가 "승인 대상인가"만 묻고 "무엇을 승인했나"를 묻지
않는다는 것은 코드 한 줄을 보면 보이는데, 재생이 결정적이라는 믿음이 기록 끝 너머까지 번졌다.

결정을 `RunPaused`(도구·마스킹된 인자)에 묶은 `_Verdict`로 컨텍스트에 넘기고, 재생이 끝난 뒤 첫
실제 호출과 대조한다. 다르면 — 다른 도구, 다른 인자, 도구 대신 모델 호출 — 결정을 적용하지 않고
재생 대조 불일치와 같은 모양(`run_resumed` 없이 `run_failed`)으로 끝낸다. 같은 호출이면 정책이
바뀌었어도 적용한다. 판정의 기준은 매니페스트가 아니라 사람이 본 화면이다. 테스트 넷이 넷 다 먼저
빨갰다. ADR 0009 이력과 `core.md`에 적었다.

CodeRabbit이 `run.py`·`main.py`·테스트 셋을 실제로 스캔했음을 `reviewedFiles`로 확인했다. 이 세션
CLI 사용 1회.
