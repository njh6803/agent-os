# Agent OS 제품 의도

status: accepted (2026-09-21 사용자 승인). 바꾸려면 사용자 승인으로. 설계 문서는 "어떻게"를 담고 이 한 장은 "누구의 어떤 문제를 왜"를 담는다. 스펙끼리 충돌할 때 무엇을 기준으로 고를지 이 문서가 답한다.

## 누구의 어떤 문제

- **에이전트를 만드는 개발자.** 서비스마다 LLM 호출, 세션, 도구 연결, 트레이스, 가드레일을 다시 만든다. 빌더는 PoC에는 좋지만 프로덕션에서 필요한 상태 제어, 예외 처리, 비용 라우팅이 안 된다.
- **운영자.** 어떤 에이전트, 도구, 모델이 등록돼 돌아가는지 한 곳에서 보고 켜고 끄고 싶다.
- **최종 사용자(나중).** 위젯이나 Slack 같은 채널에서 에이전트에게 요청한다.

## 왜 지금, 왜 우리

- 같은 주제로 두 번 시도했고 둘 다 실행 루프 없이 문서와 관리 화면만 남겼다. 세 번째는 실행부터 만든다(원칙 I).
- MCP와 Agent Skills가 표준이 되어 플러그인 경계를 우리가 발명할 필요가 없다. 런타임이 할 일은 그것들을 싣고 실행하고 기록하는 것이다.

## 무엇을 만드나

- 플러그인(agent, mcp, skill, model)을 디렉터리에서 로드해 실행하는 런타임. 실행은 이벤트 스트림이고 트레이스로 남는다.
- 실행을 일으키는 채널(CLI → HTTP → 위젯)과 구성을 다루는 관리(API → 화면).
- 만들지 않는 것: 그래프를 그리는 빌더, 범용 챗 제품, 우리만의 툴 프로토콜.

## 성공의 정의

- 2026-09-22까지 LLM을 실제로 호출하는 테스트가 통과한다.
- 2주 안에 CLI로 에이전트 하나가 MCP 도구를 써서 답하고 트레이스가 남는다.
- 그다음 슬라이스 셋: HTTP 채널, 관리 API와 화면, 위젯. 순서와 의존은 `.scratch/plan.md`.

## 스펙이 충돌하면

실행 가능성 > 계약의 안정성(sdk, 디스크 형식) > 확장성 > 편의. 앞이 뒤를 이긴다.
