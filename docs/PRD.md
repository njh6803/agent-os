# Agent OS 제품 의도

status: accepted (2026-09-21 사용자 승인, 2026-11-04 개정 사용자 승인. 개정의 근거는 ADR 0042). 바꾸려면 사용자 승인으로. 설계 문서는 "어떻게"를 담고 이 한 장은 "누구의 어떤 문제를 왜"를 담는다. 스펙끼리 충돌할 때 무엇을 기준으로 고를지 이 문서가 답한다.

## 누구의 어떤 문제

- **에이전트를 만드는 개발자.** 서비스마다 LLM 호출, 세션, 도구 연결, 트레이스, 가드레일을 다시 만든다. 빌더는 PoC에는 좋지만 프로덕션에서 필요한 상태 제어, 예외 처리, 비용 라우팅이 안 된다.
- **운영자.** 어떤 에이전트, 도구, 모델이 등록돼 돌아가는지 한 곳에서 보고 켜고 끄고 싶다.
- **최종 사용자(나중).** 위젯이나 Slack 같은 채널에서 에이전트에게 요청한다.

## 왜 지금, 왜 우리

- 같은 주제로 두 번 시도했고 둘 다 실행 루프 없이 문서와 관리 화면만 남겼다. 세 번째는 실행부터 만든다(원칙 I).
- MCP와 Agent Skills가 표준이 되어 플러그인 경계를 우리가 발명할 필요가 없다. 런타임이 할 일은 그것들을 싣고 실행하고 기록하는 것이다.

## 무엇을 만드나

- 플러그인(agent, mcp, skill, model)을 디렉터리에서 로드해 실행하는 런타임. 실행은 이벤트 스트림이고 트레이스로 남는다.
- 실행을 일으키는 채널(CLI → HTTP → 위젯)과 구성을 다루는 관리(API → 화면).
- 만들지 않는 것: 그래프를 그리는 빌더, 범용 챗 제품, 우리만의 툴 프로토콜, 실행 안의 제어권 넘김(goto 핸드오프, 그룹 챗), 엔진의 그래프 상태 객체, 범용 오케스트레이션 프레임워크. 여러 에이전트는 리드가 맡기고 병렬로 받는 모양과 실행 경계의 넘김(앞 실행이 끝나며 다음 에이전트가 잇는다)뿐이고 공유 작업물은 도구(MCP 서버)를 지난다.
- 미룬 것(이번 방향에서 설계하지 않는다): 모델의 기밀 등급·능력 선언, 분류기 승인, 승인 알림, 웹훅·스케줄러, Slack 입력 채널, A2A, 멀티테넌시, PII 처리, LLM 채점. 돌아오면 그 기능의 설계 인터뷰가 처음부터 묻는다.

## 보장하는 것

an agent OS가 보장하는 것은 에이전트 코드가 건너뛸 수 없는 셋이다.

- 중재: 실행의 모델 호출과 도구 호출은 런타임을 지난다.
- 강제: 운영자가 바깥에서 건 정책(승인 규칙, MCP 서버의 신뢰 수준, 상한, 승인 만료, 보존 기간)을 런타임이 집행하고 저자의 코드가 풀지 못한다. 운영자도 저자가 매니페스트에 적은 승인 대상을 풀지 못한다.
- 기록: 그 호출과 판정이 트레이스에 남아 되짚을 수 있다.
- 전제 둘. 배포는 프로세스 넷(serve, worker, PostgreSQL, Redis)이고 다중 인스턴스는 공유 볼륨 위다. 에이전트 코드 안의 일(저자가 손으로 엮는 글, 런타임을 거치지 않는 호출)은 보장 밖이다.
- 알아 둘 사실 둘. 최종 사용자의 글은 트레이스에 그대로 남고 보존 기간이 수명을 정한다. OTel 내보내기를 켠 기본 설정에서는 그 글이 OTLP 끝점으로 나간다.

## 성공의 정의

- 2026-09-22까지 LLM을 실제로 호출하는 테스트가 통과한다.
- 2주 안에 CLI로 에이전트 하나가 MCP 도구를 써서 답하고 트레이스가 남는다.
- 그다음 슬라이스 셋: HTTP 채널, 관리 API와 화면, 위젯. 순서와 의존은 `.scratch/plan.md`.
- 그다음: 모델 플러그인. 에이전트가 매니페스트로 고른 모델로 돌고, 모델 파일을 고치거나 켜고 끈 것이 서버를 다시 띄우지 않아도 다음 실행부터 듣는다.
- 그다음: 스킬 플러그인. 에이전트가 매니페스트로 고른 스킬의 이름·설명·본문을 컨텍스트로 받아 프롬프트에 엮고, 스킬 파일을 고치거나 켜고 끈 것이 서버를 다시 띄우지 않아도 다음 실행부터 듣는다.
- 그다음(다섯 묶음 열일곱, ADR 0042): 운영자가 바깥에서 건 정책을 에이전트 코드가 건너뛸 수 없고, 그 집행을 트레이스로 되짚을 수 있다. 순서와 의존은 `.scratch/plan.md`.

## 스펙이 충돌하면

실행 가능성 > 계약의 안정성(sdk, 디스크 형식) > 확장성 > 편의. 앞이 뒤를 이긴다.
