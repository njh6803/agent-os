# HTTP 채널 규칙

채널에만 걸리는 것이다. 봉투와 어휘, 상태 코드 표, 에러 문서, 인증, 스트림의 프레임, 테스트 이음매처럼 관리와 함께 따르는 것은 `http.md`에 있다. 원천은 ADR 0014·0015와 `.scratch/http-channel/spec.md`다. 아래는 확정된 결정이고, 코드와 다르면 코드를 고치거나 ADR을 남긴다.

- **실행은 앱의 수명이 소유한다(`runs.py`의 `Runs`).** 라우트가 `run()`·`resume()`을 제 제너레이터에서 흘리지 않는다. 그러면 끊김에서 제너레이터가 취소되고 실행이 `run_failed`도 없이 도구를 반쯤 부른 채 사라진다(ADR 0014가 거부한 모양). 채널 라우터가 수명을 들고 오고 앱에 붙으면 그것이 앱의 수명에 합쳐진다. 수명이 닫히면 남은 실행은 기다리지 않고 취소되어 결말 없음이다.
- **실행은 받는 쪽을 기다리지 않는다.** 둘 사이는 크기 제한이 없는 흐름이고 실행은 기다리지 않고 넣는다. 상한과 초과 정책은 동시 실행 상한과 함께 본다(명세 Further Notes). 이유는 느린 수신자 하나만이 아니다. **실행을 모는 루프는 이벤트와 이벤트 사이에 await 하지 않는다.** core는 도구 연결의 anyio 취소 범위 안에서 yield하므로, 그 사이의 await에서 취소를 받으면 제너레이터가 취소 범위 안에 멈춘 채 남고 나중에 다른 태스크에서 닫혀 수명의 태스크 그룹이 깨진다. 크기가 제한된 흐름에 기다리며 넣는 구현은 느린 수신자 테스트와, 끊긴 뒤 수명을 닫는 테스트에서 이것으로 빨개진다.
- **실행의 태스크가 예외를 스스로 받는다.** 태스크 그룹은 자식 하나의 예외에 형제 전부를 취소하므로, 그대로 두면 실행 하나의 디스크 오류가 다른 실행들과 앱의 수명을 함께 끝낸다. 첫 이벤트 전의 예외는 요청이 상태 코드로 말하고, 그 뒤의 것(트레이스를 쓰지 못함)은 결말 없이 닫힌 스트림과 서버 기록 한 줄로 남는다.
- **응답은 첫 이벤트를 받은 뒤에 시작한다.** 세 라우트 모두다 — `run()`(이어 가기도)은 `run_started` 앞이, `resume()`은 결정 이벤트 앞이 실행 전이다. 실행을 일으키고 첫 이벤트를 기다리는 것은 의존성(`Depends`)이다. FastAPI는 의존성을 전부 푼 뒤에 SSE 제너레이터를 부르므로 그 전의 예외가 핸들러를 지나 봉투가 된다. 제너레이터 안에서 첫 yield 전에 던지지 않는다 — 이미 200이 나간 뒤이고 예외 그룹에 감싸져 고정 문구의 500이 된다. 응답 객체를 직접 만들어 돌려주지 않는다 — FastAPI가 제너레이터 라우트에만 붙이는 keepalive를 잃는다.
- **라우터 모듈에는 `from __future__ import annotations`를 두지 않는다.** 라우트가 라우터 안에서 만든 의존성을 주해의 `Depends(...)`로 가리키는데, FastAPI는 문자열 주해를 모듈 전역에서만 풀어 스키마를 만들다 실패한다.
- **주체와 승인자와 모델은 조립이 넘긴 것이다.** 본문에서 받지 않는다. 본문 모델은 추가 필드를 무시하지 않고 422로 거절하고, 기본값 있는 필드를 두지 않는다 — 요청 본문은 검증 스키마로 실려 기본값이 곧 계약의 "선택"이 된다(ADR 0015, 명세 검토). 판별자도 예외가 아니다.
- **결정 본문은 판별자 `decision`의 유니온 `Decision = Approve | Deny`이고 라우트가 `Body()`로 받는다.** 별칭을 그대로 받으면 FastAPI가 본문을 `Body`라는 제목의 익명 유니온으로 인라인해 계약에 이름이 서지 않는다. 이름은 core의 `Approve`·`Deny`·`Decision`과 같고 라우터가 core 쪽을 별칭으로 부른다. 두 멤버는 결정이 답하는 일시정지의 자리 `pause_index`(트레이스 상세 `events`의 0부터 센 인덱스)를 필수로 든다. 엄격한 정수(`strict=True`, 0 이상)다 — lax면 문자열 `"1"`, 실수 `1.0`, 불린 `true`가 정수로 읽혀 계약의 `integer`와 어긋난다. 라우트는 그것을 core `resume()`의 따로 된 인자로 넘기기만 하고, 어긋나면 core의 `NotResumable`이 409다(ADR 0014의 2026-09-28 이력). 거부 사유는 CLI와 같은 파이썬 `str.strip`으로 다듬어 기록한다 — pydantic의 `strip_whitespace`는 다듬는 문자 집합이 달라 CLI와 다르게 기록되고, 그것만 든 사유가 core의 `Deny`까지 가 500이 된다.
- **채널은 재개할 실행의 상태도 결정의 자리도 플러그인의 켜짐도, 이어 갈 앞 실행의 존재·상태·주체도 먼저 확인하지 않는다.** 부재, 재개 불가, 꺼짐, 다른 주체, 이어 갈 수 없음, 깨진 고리는 core `run()`·`resume()`이 던진 타입을 표가 옮긴다. 포트나 `run_status()`로 먼저 보면 형식 1 판정(`RESUMABLE`)과 자리 판정과 이어 가기의 판정 순서(앞 실행 → 고리 → 준비)와 준비 단계의 판정 순서(`core.md` 실패 정책)가 core 밖으로 샌다(ADR 0014, ADR 0017, ADR 0022). 상태 코드 테스트는 먼저 확인하는 구현으로도 초록이라 이것은 리뷰가 본다.
- **이어 가기는 `POST /runs/{run_id}/continuation`(`continue_run`)이고 본문은 `POST /runs`의 `StartRun` 그대로다(ADR 0022).** 앞 실행은 경로에만 있다 — 본문에 두면 기본값을 둘 수 없어 지금의 모든 호출이 `null`을 보내야 하고, 본문 둘의 유니온은 형식 오류의 경로가 두 멤버의 이름으로 함께 실린다. 접미사가 고유한 이유는 `verbatim`이 슬래시까지 잡아 접미사 없는 `/{run_id:verbatim}`을 결정 경로 앞에 두면 `{id}/approval`을 통째로 잡기 때문이다. 이어 가기 경로와 결정 경로가 서로 가로채지 않는 것은 라우터 테스트가 고정한다. 응답은 같은 SSE 스트림이고 첫 이벤트가 `previous_run`을 든 `run_started`다. 문서화된 에러는 401, 404(앞 실행 없음, 에이전트 없음, 메시지가 가른다), 409(다른 주체, 끝나지 않음, 꺼짐, 메시지가 가른다), 422(경로의 패턴은 포트를 부르지 않고, 본문의 추가 필드), 500(고리 깨짐과 그 밖의 구성 오류. 봉투의 `message`가 그 `PluginError`의 문구)이다. 세 채널 라우트의 409 설명은 `http/routes.py`의 공유 설명 하나다. 거절된 이어 가기는 트레이스를 남기지 않는다. 주체와 모델은 조립이 넘긴 것이다.
- **동시 재개 테스트의 가짜 트레이스는 디스크에 닿는 데 시간을 들인다(`disk_seconds`).** 즉시 끝나면 core `resume()`의 읽기나 쓰기를 스레드로 보내는 변경이 스레드 타이밍에 따라 초록으로 지나간다. 불변식 자체는 `core.md`.
- **테스트는 앱의 수명을 테스트 본문의 `async with`로 연다.** `ASGITransport`는 lifespan을 보내지 않고, 수명은 anyio 태스크 그룹이라 픽스처의 setup과 teardown이 다른 태스크면 깨진다(`tests.md`의 MCP 어댑터와 같은 조건). 가짜 도구 포트는 연결을 anyio 취소 범위 안에서 연다. MCP 어댑터가 그렇고, 연결이 연 태스크가 아닌 곳에서 닫히면 그 자리에서 드러난다.
