# release-image: 판마다 서버와 관리 화면과 위젯과 질문 페이지의 컨테이너 이미지를 짓고 올리며 단독 배포 안내도 낸다.
**슬라이스:** 8
**Blocked by:** pilot-portal
**설계:** ADR 0056

dev 전환(ADR 0043 Consequences "전환"의 harness 티켓)이 끝난 뒤에 이 행의 명세와 티켓을 시작한다(사용자가 골랐다, 일지 2026-11-11-1532 라운드 4. ADR 0056 Consequences "dev 전환이 먼저다"). 전환은 하네스의 일이라 `**Blocked by:**`에 적을 수 없어 여기에 적고, 전체 계획의 프론티어는 이 행을 조건 없이 든다. 판마다 컨테이너 이미지를 짓고 올린다. 대상은 `serve`, 관리 화면, 위젯, 질문 페이지(pilot-portal)다. 질문 페이지 이미지는 빌드 산출이 아니라 소스와 `node_modules`를 그대로 담는다. node가 `.ts`를 빌드 없이 바로 돌린다(ADR 0050). 질문 페이지는 토큰 CSS와 페이지 스크립트를 시작 때 짓고 글꼴을 디자인 시스템 패키지의 경로에서 바로 내므로, 이미지의 `node_modules`에는 Tailwind CLI와 글꼴 패키지가 그대로 들어야 한다(ADR 0050 이력 2026-11-09 "띄우기의 어림을 잰 값으로 바꾸고 토큰 CSS와 페이지 스크립트는 시작 때 짓는다"). 질문 페이지(`/portal/`)는 같은 출처의 위젯 번들(`/widget/element.js`)을 싣고(ADR 0050 결정 "페이지"), 위젯 번들과 최종 사용자 경로는 한 출처에 선다(ADR 0024). 그래서 셋은 한 공개 출처 아래에 서야 하고, 프록시가 위젯 경로와 최종 사용자 접두사와 질문 페이지의 경로를 한 출처에서 넘겨 그것을 갖춘다(ADR 0056 결정 "밖으로 여는 포트". pilot-portal 명세 Out of Scope와 PR 500의 코멘트가 이 행의 설계 인터뷰에 넘겼던 물음이다). 질문 페이지의 공개 출처는 믿을 수 없는 하위 도메인이 없는 도메인에 둔다(ADR 0050 Consequences "위젯은 바뀌지 않는다"). 여기서 도메인은 질문 페이지 호스트에 `Domain` 쿠키를 심을 수 있는 등록 도메인(공개 접미사 바로 아래. `portal.example.com`이면 `example.com`)이고, 그 아래 모든 호스트(형제 도메인 포함)를 같은 운영자가 믿을 수 있게 쥐어야 한다. 익명 식별자 쿠키는 `Domain` 없이 질문 페이지 호스트에 묶이지만, 등록 도메인 아래 어느 호스트든 `Domain=example.com`으로 심은 쿠키는 질문 페이지에도 실려 형제 도메인이 심는 쿠키까지 막지는 못한다. 질문 페이지 호스트의 아래에만 믿을 수 없는 하위 도메인이 없는 것으로는 모자란다. 그 도메인은 운영자가 고르고, 배포 안내가 이 요건을 적으며, 제품이 도메인을 검사하는 길은 두지 않는다(ADR 0056 결정 "밖으로 여는 포트". pilot-portal 명세 Out of Scope가 이 행의 설계 인터뷰에 넘겼던 물음이다). 익명 식별자 쿠키가 `__Secure-` 접두를 쓰지 않는 근거는 질문 페이지의 공개 출처 앞 프록시가 443을 TLS로만 듣고 HSTS를 내는 것이다(pilot-portal 명세 "익명 식별자 쿠키", ADR 0024의 프록시 규칙). 저장소의 어떤 시험도 HSTS를 보지 않으므로(ADR 0024), 이 행이 질문 페이지 앞의 프록시를 갖출 때 HSTS를 함께 둔다. agent-os만 띄우는 단독 compose와 그 배포 안내도 이 행이 낸다(배포와 운영은 데이터를 가진 저장소가 맡는다, ADR 0048). ADR 0043이 main으로 가는 PR과 main 푸시에 더하기로 한 실제 이미지 compose e2e의 Dockerfile과 compose, 그리고 그 잡은 이 행의 첫 티켓이 짓는다(ADR 0056 결정 "실제 이미지로 띄우는 시험"). 컨테이너의 첫 프로세스에는 init을 두고(README의 "컨테이너의 첫 프로세스로 띄우면 init을 둔다" 항목), 컨테이너는 root가 아닌 사용자로 돈다. 이 기능 계획이 설계 인터뷰에 넘겼던 것(레지스트리, 태그 규칙, 이미지를 파일로 옮기는 방법, 취약점 점검 결과, 루프백에만 서는 네 프로세스에 프록시를 잇는 방법, 토큰 끝점의 빈도 제한)은 ADR 0056이 정했다. 판은 main이 움직일 때 지난 판 뒤로 제품 변경이 있으면 CI가 스스로 내고, 이미지 넷을 이 제품 전용 Docker Hub 계정에 올리며, GitHub 릴리스에 배포 파일 묶음과 소프트웨어 목록과 취약점 점검 결과를 첨부한다. 0.1.0 전의 판은 출시 후보다. 단독 compose는 nginx와 네 컨테이너를 보통의 Docker 네트워크로 묶고, 네 프로세스의 루프백 규칙에 이미지 안에서만 켜지는 명시적 예외를 둔다. 이 행의 티켓이 코드 네 곳의 시작 검사와 관리 화면의 상류 주소를 고친다. 밖으로 여는 포트는 프록시의 443과, 443으로 넘기기만 하는 80이며, 관리 화면은 compose가 서버 자신의 `127.0.0.1`에만 열어 운영자가 SSH 포트 포워딩으로 닿는다(관리 화면을 인터넷에 여는 일은 admin-login의 것이다). 위젯 컨테이너는 뜰 때 운영자의 사이트 파일로 빌드한 뒤 시작한다. 질문 페이지의 토큰 끝점 앞에는 프록시의 접속 주소별 빈도 제한을 둔다(ADR 0050 결정 "빈도 제한"이 넘긴 요건). 리눅스 x86-64의 Docker Engine과 Docker Compose만 보증하고, 배포 환경이 Docker를 허용하지 않는 곳으로 정해지면 설계를 다시 연다. 저장소의 판 번호를 0.0.0으로 바꾸는 편집은 계약 파일 `openapi.json`에 닿으므로 그 티켓이 다른 티켓을 막는다. 명세가 리눅스에서 재거나 정할 것은 ADR 0056 Consequences "명세가 리눅스에서 재거나 정하는 것"에 있고, 설계 인터뷰의 측정은 `.scratch/release-image/probes/`에 있다. 사람 몫(Docker Hub 계정 만들기, 2단계 인증, 접근 토큰 발급, GitHub 저장소에 비밀 값 등록)이 없으면 첫 판 내기가 실패한다. 판 내기 워크플로를 지어 실제로 돌려 본 티켓은 닫을 때, 그 워크플로와 판을 내는 규칙을 문서 검색 서버 저장소(rag-engine)에 옮기라고 그 저장소의 세션에 줄 지시문을 사용자에게 낸다(사용자가 청했다, 일지 2026-11-11-1532 "사용자가 정했다"). 지시문은 ADR 0043과 ADR 0056을 입력으로 받는 짧은 설계 인터뷰를 열게 하고, 그 저장소가 따로 정할 것(같은 일지 "사용자가 물었다" 절의 다섯)을 싣는다. 수락: main이 움직여 CI가 판을 내면 네 이미지가 그 판의 태그로 Docker Hub에 올라가고 git 태그가 달리며, 깨끗한 리눅스 VM에서 그 이미지만 받아 단독 compose로 띄우면 `/health`가 정상이며 위젯과 질문 페이지(`/portal/`. 이미지가 시작 때 지은 토큰 CSS와 페이지 스크립트, 패키지의 글꼴이 받아진다)에서 calc 예시에 질문할 수 있고, 질문 페이지의 토큰 끝점에 프록시의 한도를 넘겨 요청하면 거부된다
