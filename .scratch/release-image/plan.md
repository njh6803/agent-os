# release-image: 판마다 서버와 관리 화면과 위젯과 질문 페이지의 컨테이너 이미지를 짓고 올리며 단독 배포 안내도 낸다.
**슬라이스:** 8
**Blocked by:** pilot-portal
**설계:** ADR 0056

이 행이 기다리던 dev 전환(ADR 0043 Consequences "전환", ADR 0056 Consequences "dev 전환이 먼저다")은 harness 티켓 `dev-branch-create`가 닫았다(2026-11-12). 판마다 컨테이너 이미지를 짓고 올린다. 대상은 `serve`, 관리 화면, 위젯, 질문 페이지(pilot-portal)다. 질문 페이지 이미지는 빌드 산출이 아니라 소스와 `node_modules`를 그대로 담는다. node가 `.ts`를 빌드 없이 바로 돌린다(ADR 0050). 질문 페이지는 토큰 CSS와 페이지 스크립트를 시작 때 짓고 글꼴을 디자인 시스템 패키지의 경로에서 바로 내므로, 이미지의 `node_modules`에는 Tailwind CLI와 글꼴 패키지가 그대로 들어야 한다(ADR 0050 이력 2026-11-09 "띄우기의 어림을 잰 값으로 바꾸고 토큰 CSS와 페이지 스크립트는 시작 때 짓는다"). 질문 페이지(`/portal/`)는 같은 출처의 위젯 번들(`/widget/element.js`)을 싣고(ADR 0050 결정 "페이지"), 위젯 번들과 최종 사용자 경로는 한 출처에 선다(ADR 0024). 그래서 셋은 한 공개 출처 아래에 서야 하고, 프록시가 위젯 경로와 최종 사용자 접두사와 질문 페이지의 경로를 한 출처에서 넘겨 그것을 갖춘다(ADR 0056 결정 "밖으로 여는 포트". pilot-portal 명세 Out of Scope와 PR 500의 코멘트가 이 행의 설계 인터뷰에 넘겼던 물음이다). 질문 페이지의 공개 출처는 믿을 수 없는 하위 도메인이 없는 도메인에 둔다(ADR 0050 Consequences "위젯은 바뀌지 않는다"). 여기서 도메인은 질문 페이지 호스트에 `Domain` 쿠키를 심을 수 있는 등록 도메인(공개 접미사 바로 아래. `portal.example.com`이면 `example.com`)이고, 그 아래 모든 호스트(형제 도메인 포함)를 같은 운영자가 믿을 수 있게 쥐어야 한다. 익명 식별자 쿠키는 `Domain` 없이 질문 페이지 호스트에 묶이지만, 등록 도메인 아래 어느 호스트든 `Domain=example.com`으로 심은 쿠키는 질문 페이지에도 실려 형제 도메인이 심는 쿠키까지 막지는 못한다. 질문 페이지 호스트의 아래에만 믿을 수 없는 하위 도메인이 없는 것으로는 모자란다. 그 도메인은 운영자가 고르고, 배포 안내가 이 요건을 적으며, 제품이 도메인을 검사하는 길은 두지 않는다(ADR 0056 결정 "밖으로 여는 포트". pilot-portal 명세 Out of Scope가 이 행의 설계 인터뷰에 넘겼던 물음이다). 익명 식별자 쿠키가 `__Secure-` 접두를 쓰지 않는 근거는 질문 페이지의 공개 출처 앞 프록시가 443을 TLS로만 듣고 HSTS를 내는 것이다(pilot-portal 명세 "익명 식별자 쿠키", ADR 0024의 프록시 규칙). 저장소의 어떤 시험도 HSTS를 보지 않으므로(ADR 0024), 이 행이 질문 페이지 앞의 프록시를 갖출 때 HSTS를 함께 둔다. agent-os만 띄우는 단독 compose와 그 배포 안내도 이 행이 낸다(배포와 운영은 데이터를 가진 저장소가 맡는다, ADR 0048). ADR 0043이 main으로 가는 PR과 main 푸시에 더하기로 한 실제 이미지 compose e2e의 Dockerfile과 compose, 그리고 그 잡은 이 행의 첫 티켓이 짓는다(ADR 0056 결정 "실제 이미지로 띄우는 시험"). 컨테이너의 첫 프로세스에는 init을 두고(README의 "컨테이너의 첫 프로세스로 띄우면 init을 둔다" 항목), 컨테이너는 root가 아닌 사용자로 돈다. 이 기능 계획이 설계 인터뷰에 넘겼던 것(레지스트리, 태그 규칙, 이미지를 파일로 옮기는 방법, 취약점 점검 결과, 루프백에만 서는 네 프로세스에 프록시를 잇는 방법, 토큰 끝점의 빈도 제한)은 ADR 0056이 정했다. 판은 main이 움직일 때 지난 판 뒤로 제품 변경이 있으면 CI가 스스로 내고, 이미지 넷을 이 제품 전용 Docker Hub 계정에 올리며, GitHub 릴리스에 배포 파일 묶음과 소프트웨어 목록과 취약점 점검 결과를 첨부한다. 0.1.0 전의 판은 출시 후보다. 단독 compose는 nginx와 네 컨테이너를 보통의 Docker 네트워크로 묶고, 네 프로세스의 루프백 규칙에 이미지 안에서만 켜지는 명시적 예외를 둔다. 이 행의 티켓이 코드 네 곳의 시작 검사와 관리 화면의 상류 주소를 고친다. 네 곳이 같은 설정 이름과 같은 판정 규칙을 쓰는지 잠그는 시험도 그 티켓이 더한다(어긋나면 한 곳만 루프백 밖을 받는 상태가 생긴다. PR 529의 claude-review 제안). 밖으로 여는 포트는 프록시의 443과, 443으로 넘기기만 하는 80이며, 관리 화면은 compose가 서버 자신의 `127.0.0.1`에만 열어 운영자가 SSH 포트 포워딩으로 닿는다(관리 화면을 인터넷에 여는 일은 admin-login의 것이다). 위젯 컨테이너는 뜰 때 운영자의 사이트 파일로 빌드한 뒤 시작한다. 질문 페이지의 토큰 끝점 앞에는 프록시의 접속 주소별 빈도 제한을 둔다(ADR 0050 결정 "빈도 제한"이 넘긴 요건). 리눅스 x86-64의 Docker Engine과 Docker Compose만 보증하며 지원하는 Engine의 최소 판은 명세가 정한다(관리 화면을 `127.0.0.1`에 발행하는 보호가 Engine 28.0.0 이전에는 같은 L2 구간의 다른 호스트에 뚫린다는 Docker 문서의 문장이 있다. https://docs.docker.com/engine/network/port-publishing/ 의 웹 요약이고 원문은 내려받아 대 보지 않았다. PR 529의 CodeRabbit 지적), 배포 환경이 Docker를 허용하지 않는 곳으로 정해지면 설계를 다시 연다. 저장소의 판 번호를 0.0.0으로 바꾸는 편집은 계약 파일 `openapi.json`에 닿으므로 그 티켓이 다른 티켓을 막는다. 명세가 리눅스에서 재거나 정할 것은 ADR 0056 Consequences "명세가 리눅스에서 재거나 정하는 것"에 있고, 설계 인터뷰의 측정은 `.scratch/release-image/probes/`에 있다. 사람 몫(Docker Hub 계정 만들기, 2단계 인증, 접근 토큰 발급, GitHub 저장소에 비밀 값 등록)이 없으면 첫 판 내기가 실패한다. 판 내기 워크플로를 지어 실제로 돌려 본 티켓은 닫을 때, 그 워크플로와 판을 내는 규칙을 문서 검색 서버 저장소(rag-engine)에 옮기라고 그 저장소의 세션에 줄 지시문을 사용자에게 낸다(사용자가 청했다, 일지 2026-11-11-1532 "사용자가 정했다"). 지시문은 ADR 0043과 ADR 0056을 입력으로 받는 짧은 설계 인터뷰를 열게 하고, 그 저장소가 따로 정할 것(같은 일지 "사용자가 물었다" 절의 다섯)을 싣는다. 그 저장소가 agent-os의 규약 ADR을 따른다고 적고 다른 점만 적는 얇은 ADR 한 장을 두라는 요건도 싣고, 지시문을 낼 때 대기열 `rag-engine-port-by-hand`에 회차를 더한다(같은 일지 "인계한 세션에서 사용자가 정했다"). 명세는 릴리스 노트에 운영자의 말로 쓴 요약 단락을 더하는 안을 검토한다(사용자가 청했다, 일지 2026-11-12-0108). ADR 0056 결정 "판마다 나오는 것"의 노트는 맨 위의 두 자리(0.1.0과 그 출시 후보의 소개 글, 고칠 수 있는 심각한 취약점의 경고) 말고는 PR 제목을 묶은 것이라 개발자의 말이 그대로 실리고, 올릴 때 운영자가 손댈 변경도 제목이 담지 못한 할 일은 노트에 실리지 않는다. 안은 사용자가 붙여 넣은 프롬프트(main에 병합된 PR마다 최종 사용자용 2~4문장 초안을 PR 댓글로 쓴다)를 이 저장소에 맞게 고친 것이다. 그 프롬프트에서 내부 변경에 "노트 없음" 댓글을 다는 단계, "개선" 분류, 변경 로그 위치 힌트는 옮기지 않았다. 단락은 모델이 쓰므로, 사람이 판마다 노트를 쓰지 않는다는 ADR 0056의 뜻(결정 "판마다 나오는 것"의 "사람이 쓰는 글이 없다")은 그대로다. main으로 가는 출시 PR이 열릴 때 별도의 잡이 `anthropics/claude-code-action`(PR 봇과 같은 액션이다. `.github/workflows/claude-code-review.yml`의 `uses:` 줄을 grep으로 손으로 봤다)으로 운영자에게 쓰는 2~4문장의 단락을 PR 댓글로 남긴다. 단락은 출시 PR마다가 아니라 기능마다 하나다. 출시 PR은 기능 하나가 끝났을 때 열지만 개발 브랜치의 머리를 올리므로, 나란히 진행 중인 다른 기능의 티켓도 함께 실릴 수 있다(ADR 0043, `CONTEXT.md` 출시 PR). 단락의 재료는 그 기능의 기능 계획과 명세와 실린 티켓 PR의 제목이다. 출시 PR은 티켓을 가리키지 않으므로 실린 커밋을 기능으로 묶는 길은 명세가 정한다. 티켓 PR의 변경에는 그 티켓 파일이 들므로(`tools/check_ticket.py` 독스트링의 판정 5를 읽었다) 그 파일의 기능 폴더로 묶는 길이 후보다. 끝나지 않은 기능의 티켓이 실렸을 때 단락에 무엇을 쓸지와, 출시 PR이 열린 동안 개발 브랜치에 커밋이 더해지면 단락을 다시 쓸지도 명세가 정한다. 핫픽스 PR은 그 PR 하나로 단락 하나를 쓴다. 독자는 최종 사용자가 아니라 운영자다. 단락에 올릴 때 할 일을 실을지는 모델이 정하지 않고 PR 제목의 접두가 정한다. 느낌표가 붙은 변경이 하나라도 있는 기능의 단락에 올릴 때 할 일을 나열하고, 모델은 diff가 접두와 맞지 않아 보이면 경고만 한다. 판 번호와 노트가 어긋나지 않게 하려는 것이다. 경고는 개발자에게 하는 말이라 단락과 갈라 노트에 싣지 않는다. 판 내기는 그 잡이 쓴 댓글만 읽는다. 지난 판(정식 판은 지난 정식 판) 뒤의 출시 PR과 핫픽스 PR에 남은 단락을 모두 싣고, 그 아래에 지금의 제목 목록을 그대로 둔다. 기능이 여럿 실린 출시 PR, 판 내기가 실패해 다음 판에 함께 실린 변경, 지난 정식 판 뒤 전부를 싣는 정식 판에서는 단락이 여럿이다. 제목 목록을 남기는 것은 고친 것이 빠짐없이 실린다는 결정을 지키기 위해서다. 단락들과 맨 위의 두 자리 사이의 차례는 명세가 정한다. 경고와 단락을 가르는 꼴, 그 잡이 쓴 댓글을 알아보는 표지도 명세가 정한다. 제품 변경이 없는 기능(하네스 기능, 문서만 고친 기능)은 ADR 0056 결정 "판이 나는 때"가 판을 내지 않는 것이므로, 그 기능의 단락이 다음 제품 판의 노트에 실리지 않게 단락을 쓰고 싣는 범위를 제품 변경(같은 결정 "제품 변경"의 경로 목록)을 담은 기능으로 좁히는 기준도 명세가 정한다. 핫픽스도 같은 기준을 따른다. 단락이 없는 PR의 변경은 제목 목록에만 실리고, 판 내기는 댓글을 기다리지 않는다. 이 안대로면 병합한 뒤에 늦게 달린 단락은 어느 판에도 실리지 않는다. 병합하는 세션이 병합 전에 단락이 달렸는지 보는 단계를 둘지도 명세가 정한다(ADR 0056 결정 "판 내기의 차례와 실패"가 병합한 세션이 판 내기를 기다리게 하는 자리가 후보다). 리뷰 봇은 dev→main PR에서 끄지만(ADR 0043 Consequences "티켓 검사와 봇") 이 잡은 리뷰가 아니다. 이 안은 ADR 0056 결정 "판마다 나오는 것"의 "노트는 제품 변경을 한 PR의 제목을 … 묶은 것이고"를 바꾸므로, 고르면 ADR 0056에 이력을 쌓고 승인을 받는다. 초안의 품질은 명세가 지난 제품 PR 몇 개에 돌려 본 뒤 정하고, 지금은 돌려 보지 않았다. 수락: main이 움직여 CI가 판을 내면 네 이미지가 그 판의 태그로 Docker Hub에 올라가고 git 태그가 달리며, 깨끗한 리눅스 VM에서 그 이미지만 받아 단독 compose로 띄우면 `/health`가 정상이며 위젯과 질문 페이지(`/portal/`. 이미지가 시작 때 지은 토큰 CSS와 페이지 스크립트, 패키지의 글꼴이 받아진다)에서 calc 예시에 질문할 수 있고, 질문 페이지의 토큰 끝점에 프록시의 한도를 넘겨 요청하면 거부된다
