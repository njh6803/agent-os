# 릴리스 노트 요약 단락의 후보 프롬프트

`{slug}`와 `{titles}`를 채워 모델에 그대로 준다. 출처는 release-image 기능 계획 본문의 "검토할 안"이다(사용자가 붙여 넣은 프롬프트를 이 저장소에 맞게 고친 것, 일지 `docs/journal/2026-11-12-0108-release-notes-summary.md`).

```
이 저장소의 기능 `{slug}`가 끝나 운영 브랜치로 오른다. 이 기능을 판의 릴리스 노트에서 운영자에게 알리는 단락 하나를 쓴다. 파일을 고치지 않고, 아래 재료만 읽고, 단락만 답한다.

독자는 이 제품을 서버에 설치해 운영하는 사람(운영자)이다. 개발자가 아니고, 위젯으로 질문하는 최종 사용자도 아니다. 판을 올릴지 정하고, 올린 뒤 무엇이 달라지는지 알려고 읽는다.

재료(이것만 읽는다):
1. `.scratch/{slug}/plan.md`(기능 계획)
2. `.scratch/{slug}/spec.md`(명세)가 있으면 그 가운데 Problem Statement, Solution, User Stories 절
3. 이 기능의 티켓 PR 제목 목록:
{titles}

쓰는 법:
- 한국어 2~4문장의 한 단락이다. 첫 문장은 운영자에게 무엇이 새로 되거나 달라지는지다.
- 운영자의 말로 쓴다. 파일 경로, 함수와 클래스 이름, 커밋 해시, ADR 번호, 티켓 번호, 내부 패키지 이름을 쓰지 않는다. 운영자가 직접 만지는 것의 이름(설정 파일의 칸, 환경 변수, 명령, 화면의 이름)은 그대로 쓴다.
- 재료에 없는 것을 지어내지 않는다. 시험, 리팩터링, 내부 구조만 바꾼 티켓은 쓰지 않는다.
- 올릴 때 할 일: 제목 목록에 접두 뒤 느낌표(`feat!:` 꼴)가 붙은 제목이 하나라도 있으면, 단락 아래에 "올릴 때 할 일:"로 시작하는 목록으로 운영자가 판을 올리며 손댈 것을 빠짐없이 적는다. 느낌표가 붙은 제목이 없으면 그 목록을 쓰지 않는다. 이 분류는 제목의 접두가 정하고 스스로 정하지 않는다.
- 접두와 내용이 어긋나 보이면(느낌표가 없는데 운영자가 설정을 고쳐야만 하는 변경으로 읽힌다, 느낌표가 있는데 할 일을 찾지 못했다) 단락을 고치지 않고, 맨 끝에 "경고(개발자에게):"로 시작하는 줄을 따로 쓴다. 어긋나 보이지 않으면 그 줄을 쓰지 않는다.

답은 단락(과 해당하면 목록, 경고 줄)뿐이다. 머리말과 맺음말을 붙이지 않는다.
```
