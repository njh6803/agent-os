# notes_summary: 릴리스 노트 요약 단락의 후보 프롬프트를 지난 기능에 돌려 본 기록

release-image 기능 계획이 명세에 넘긴 물음("초안의 품질은 명세가 지난 제품 PR 몇 개에 돌려 본 뒤 정한다")의 기록이다. 스크립트가 아니라 손으로 한 번씩 돌린 것이어서 다시 돌리면 글이 달라진다.

## 한 일

`prompt.md`의 프롬프트를 끝난 제품 기능 넷(pilot-portal, mcp-http, approval-rules, admin-style)에 채워, 기능마다 새 서브에이전트(모델 Sonnet) 하나에 주었다. 받은 답은 `drafts.md`에 글자 그대로 있다. admin-style은 제목 하나의 접두를 `feat!:`으로 지어 바꾼 갈래다. 저장소의 이력에 느낌표가 붙은 제목이 없기 때문이다(손으로 봤다. 명령은 `drafts.md`).

## 본 것(손으로 봤다)

1. **길이.** 프롬프트는 2~4문장을 요구했고 넷 모두 넘겼다. 단락의 문장 수를 손으로 세면 pilot-portal 7, mcp-http 9, approval-rules 10, admin-style 6이다. 단락의 글자 수(공백을 넣고 줄바꿈을 뺀 것. `drafts.md`에서 단락은 한 줄이다)는 473, 542, 725, 379자다(2026-11-14에 `uv run python`으로 `drafts.md`의 그 줄을 셌다).
2. **꼴.** pilot-portal의 답은 느낌표가 없으면 쓰지 말라고 한 자리에 "이 판을 올릴 때 손댈 것은 없다"는 둘째 단락을 붙였다. admin-style의 "올릴 때 할 일" 둘째 줄은 할 일이 아니라 "서버 쪽에서 따로 손댈 것은 없습니다"였다.
3. **내용.** 넷 모두 운영자가 만지는 것의 이름(매니페스트의 칸, 규칙 파일, 화면의 이름)으로 썼고 파일 경로나 ADR 번호는 싣지 않았다. 문장마다 재료와 맞는지는 대 보지 않았다.
4. **경고 줄.** approval-rules의 답은 느낌표가 없는데 운영자가 손댈 것이 있어 보인다고 경고했다(규칙 파일이 없거나 allow에 없는 도구 호출이 승인 대기로 멈춘다). approval-rules 명세 189행이 규칙 파일이 따라가지 않은 시험이 "기본 묻는다에서 멈춘다"고 적으므로(코드를 읽었다, 그 한 행) 헛짚은 경고가 아니다. 지어 넣은 느낌표(admin-style)에는 접두가 옳은지 확인하라고 경고했다.

## 재지 못한 것

- 실제 워크플로(`anthropics/claude-code-action`)로 돌리지 않았다. 서브에이전트는 저장소의 `CLAUDE.md`를 싣고 도는 점은 같지만 허용 도구와 턴 상한이 다르다.
- 모델 하나(Sonnet), 기능마다 한 번이다. 다시 돌렸을 때 길이와 꼴이 얼마나 흔들리는지는 보지 않았다.
- 끝나지 않은 기능의 티켓이 실린 경우와 핫픽스 PR 하나의 단락은 돌리지 않았다.
- 실제로 느낌표가 붙은 변경은 이력에 없어 "올릴 때 할 일"의 품질은 지어 넣은 갈래 하나로만 봤다.
