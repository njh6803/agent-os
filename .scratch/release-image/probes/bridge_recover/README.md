# bridge_recover: 다시 만든 뒤와 껐다 켠 뒤 프록시가 뒷단에 다시 닿는가

ADR 0056 "컨테이너 배치"는 단독 배포를 다섯 컨테이너(nginx 프록시 하나 + `serve`, 관리 화면, 위젯, 위젯 미리보기 페이지)로 두고, 프록시가 compose 기본 네트워크에서 서비스 이름으로 뒷단에 닿게 했다. 그 ADR이 명세에 넘긴 두 질문을 리눅스 Docker Engine에서 잰다.

1. 뒷단 컨테이너를 다시 만들어 주소가 바뀐 뒤 프록시가 새 주소를 다시 찾는가. nginx 설정 세 변형을 견준다.
   - (가) 고정: `proxy_pass http://serve:8000;` (`nginx/static/`)
   - (나) 변수: `resolver 127.0.0.11 valid=5s ipv6=off;` + `set $backend_serve serve; proxy_pass http://$backend_serve:8000;` (`nginx/variable/`). `valid` 를 뺀 판은 `nginx/variable-novalid/`
   - (다) upstream 다시 풀기: `upstream up_serve { zone up_serve 64k; server serve:8000 resolve; }` + 같은 `resolver` (`nginx/upstream/`)
2. 서버를 껐다 켠 뒤(데몬만 다시 켠 뒤, 호스트를 다시 켠 뒤) 재시작 정책만으로 다섯 컨테이너가 돌아와 프록시가 다시 닿는가. 프록시가 뒷단보다 먼저 떠 이름을 풀지 못할 때 변형마다 어떻게 되는가. `depends_on` + `healthcheck` 가 있고 없음, 위젯처럼 늦게 뜨는 뒷단.
3. 회차마다 단언하는 표지 넷(아래 "표지").
4. 호스트의 nginx 설정 파일을 고친 뒤 `nginx -s reload` 가 먹는가. 파일 하나만 얹으면 편집기가 파일을 바꿔 끼울 때 옛 파일을 계속 보는가.

## 결론

모두 "쟀다"(칸마다 두 번, 아래 "결과"의 실행 표)이고, 괄호는 근거 절이다. 그 밖의 근거 종류는 줄마다 적는다.

1. (가) 고정은 뒷단의 주소가 바뀌면 그 뒷단에 다시 닿지 않는다. 다시 만들기, 같은 컨테이너의 다시 시작, 판 올림, 뒷단이 죽어 정책이 다시 띄운 것 모두다(1, 2). 프록시를 `nginx -s reload` 하거나 다시 시작해야 돌아온다(1, 2). 자리 채움 없는 판 올림에서도 주소가 바뀌었다(3b).
2. (가)는 옛 주소를 받은 다른 컨테이너에 요청을 보낸다. 같은 포트로 듣는 컨테이너면 그것이 200으로 답했다(3a 두 번 모두, 3b 실행 5에서 `/admin/` 을 portal 이, `/portal/` 을 admin 이 답했다).
3. (가)는 뒷단 하나라도 이름이 풀리지 않으면 nginx 가 시작하지 못해 멀쩡한 경로까지 사이트 전체가 내려간다(0, 6). 운영자가 `docker compose stop` 으로 멈춰 둔 뒷단이 있는 채 데몬이 다시 켜지면 사람 손 없이 그렇게 된다(5). 서버를 다시 켠 갈래는 (나)로만 쟀고, 그때도 `unless-stopped` 가 멈춘 뒷단을 멈춘 채 두었다(5).
4. (가)에 `depends_on` 의 `restart: true` 를 걸면 서비스를 고르지 않은 `docker compose up -d` 판 올림과 `docker compose restart <뒷단>` 에서만 compose 가 프록시를 다시 시작해 닿는다. 서비스를 고른 `up -d`, 지운 뒤의 `up -d`, compose 밖의 다시 시작, 정책의 다시 띄우기에서는 닿지 않는다(2).
5. (나) 변수 + `resolver 127.0.0.11 valid=5s` 와 (다) upstream `resolve` 는 다시 만들기, 판 올림, 서버 껐다 켜기, 멈춘 뒷단, 늦게 뜨는 뒷단 모두에서 사람 손 없이 다시 닿는다(1, 3, 4, 5, 6, 7). 뒷단이 없어도 시작하고(0, 6), 멈춘 뒷단의 경로만 502를 낸다(5, 6).
6. 다만 둘 다 다시 만든 직후 `valid` 안에서는 옛 주소로 걸 수 있고, 그 요청은 곧 실패하지 않고 매달린다(클라이언트 제한 8초까지, 상태 499). (나)는 작업 프로세스가 여럿이고 요청이 드문 이 측정에서 그 창을 드러내지 않았고(1: 열 번 모두 첫 요청부터), 작업 프로세스가 하나면 드러냈다(1w). (다)는 열 조작 모두에서 다시 만든 경로의 첫 요청이 8초 시간 초과였고(실행 2의 판 올림에서 widget 한 경로만 첫 요청부터 닿았다) 약 9초 뒤 닿았다. 실행 6의 접근 기록으로 그 요청이 옛 주소로 걸렸음을 봤다(1). 다시 푸는 때에 따라 주소 없이 몇 초 동안 곧바로 502도 냈다(1w, 3b, 4, 7).
7. `valid` 를 빼면 내장 DNS가 주는 TTL은 600초이고(3c), 다시 만든 지 25초가 지나도 일부 요청이 옛 주소로 갔다(3c 실행 6. 600초까지 가는지는 재지 않았다).
8. 재시작 정책 `unless-stopped` 는 데몬 재시작, 서버의 정상 재시작, 전원 끊김 뒤(4), `always` 는 데몬 재시작과 서버의 정상 재시작 뒤(5) 다섯 컨테이너를 모두 다시 띄웠고, 정책이 없으면 데몬 재시작과 서버의 정상 재시작 뒤 아무것도 돌아오지 않았다(5). 둘의 차이는 운영자가 멈춘 컨테이너뿐이다. `always` 는 다시 띄우고 `unless-stopped` 는 멈춘 채 둔다(5).
9. `depends_on: service_healthy` 는 처음 `up` 할 때 가장 늦은 뒷단이 건강해질 때까지 사이트 전체를 막고, 데몬이 다시 켜져 컨테이너를 다시 띄울 때는 차례를 정하지 않는다(7. 서버를 다시 켠 갈래는 재지 않았다). (나)·(다)는 그것이 없어도 늦은 뒷단의 경로만 502를 냈다(7).
10. 프록시 설정은 폴더째 얹어야 서버에서 고친 파일(이름을 바꿔 끼우는 저장, `sed -i`)이 `nginx -s reload` 로 먹는다. 파일 하나로 얹으면 `docker compose restart proxy` 를 해야 먹고 `up -d` 로는 먹지 않는다(8). 깨진 설정에는 `nginx -s reload` 가 종료 1로 끝나고 옛 설정이 계속 돈다(8).

- 원본 출력(모든 docker 명령의 출력과 시각)은 `--work` 아래 새 폴더의 `raw.log` 에 남는다(없으면 시스템 임시 폴더). 첫 줄에 그 경로가 찍힌다. 전체 실행에서 수십 MB가 된다.
- 타입 검사: `uv run pyright -p .scratch/release-image/probes/bridge_recover`(이 폴더의 `pyrightconfig.json`, strict).
- `--reuse` 는 떠 있는 dind 컨테이너를 다시 쓴다(안쪽 엔진이 받은 이미지도 다시 쓴다). 없으면 새로 만든다. `--keep` 은 끝에 dind 컨테이너와 볼륨을 남긴다. `--keep` 이 없으면 끝에 둘을 지우고 지워졌는지까지 본다. 실행 6은 `--reuse` 만 줬다.
- `--long` 은 `valid` 없는 변수 변형을 Docker 내장 DNS의 TTL(600초, 3c가 잰다)보다 오래 지켜본다.
- 종료 코드는 표지가 서지 않은 회차가 하나라도 있으면 1이다(`tools/probe_kit.py` `Rounds`).
- 전체 실행은 약 50분이다. 실행 6은 dind와 안쪽 이미지를 다시 써(`--reuse`) 47분 걸렸다(raw.log 의 첫 명령 21:42:43, dind 볼륨을 지운 명령 22:30:10). 새로 만들면 이미지를 받고 짓는 몫이 더 든다.

## 필요한 것

- Docker 데몬(이 PC는 Windows 10의 Docker Desktop). `--privileged` 컨테이너를 띄울 수 있어야 한다.
- 안쪽 엔진이 nginx와 python 이미지를 digest로 받으므로 인터넷. 뒷단 이미지는 안쪽에서 짓는다(받지 않는다).
- 호스트 포트를 쓰지 않는다. 요청은 dind 컨테이너 안(곧 "리눅스 서버" 자신)에서 busybox `wget` 으로 보낸다(`client.sh`).
- 만드는 것은 모두 이름이 `ri-recover-` 로 시작하고 표지 레이블 `ri-recover-probe=1` 이 붙는다. 지울 때 그 레이블을 보고 지운다.

## 짓는 모양

- 리눅스 엔진: 공식 `docker:29.9.2-dind` 를 `--privileged --init` 로 띄운다. 주 프로세스는 `supervise.sh` 이고 그것이 `dockerd` 를 띄우며, `dockerd` 가 끝나면 다시 띄운다.
  - "데몬만 다시 켠다": `/var/run/docker.pid` 의 pid가 `/proc/<pid>/comm` 으로 `dockerd` 일 때만 `TERM` 을 보낸다. supervise가 다시 띄운다. 표지는 바깥 `docker logs` 의 `supervise: dockerd start N` 줄 수가 늘었는가.
  - "호스트를 다시 켠다": 바깥에서 `docker restart -t 120 ri-recover-dind`. 표지는 dind의 `.State.StartedAt` 이 바뀌었는가.
  - "전원이 나갔다": 바깥에서 `docker kill` 뒤 `docker start`. 표지는 같다.
- 뒷단: 진짜 이미지가 아니라 `backend/server.py`(0.0.0.0에 묶은 작은 HTTP 서버)를 안쪽에서 `ri-recover-backend:v1`, `:v2` 로 짓는다. 응답 본문에 서비스 이름, 컨테이너 hostname, 이미지 판을 싣고, 받은 요청을 표준 출력에 접근 기록으로 남긴다. 위젯은 `START_DELAY` 로 늦게 뜨는 것을 흉내 낸다.
- 주소를 바꾸는 방법: Docker IPAM은 비어 있는 가장 낮은 주소를 준다. 먼저 `spare` 컨테이너 넷이 낮은 주소를 차지한 뒤 스택을 띄우고, 조작 직전에 넷을 지운다. 그러면 다시 만든 컨테이너가 옛 주소가 아닌 낮은 주소를 받는다. 주소가 실제로 바뀐 회차만 측정으로 센다(자리 채움을 쓰지 않는 3b는 예외, 아래 "결과를 본 뒤 바꾼 것").

### 0. 뒷단 이름이 풀리지 않는 자리에서 nginx가 시작하는가(설정 검사)

compose 네트워크 밖에서(이름 `serve`·`admin`·`widget`·`portal` 이 풀리지 않는 자리) 세 설정을 `nginx -t` 로 봤다. 쟀다(실행 1과 6, 두 번 모두 같다).

| 변형 | 결과 |
|---|---|
| (가) 고정 | 실패(종료 1). `host not found in upstream` 으로(이 실패가 그 자리에서 이름이 정말 풀리지 않는다는 대조다) |
| (나) 변수 | 통과(종료 0, `test is successful`) |
| (다) upstream `resolve` | 통과(종료 0). 오픈 소스 nginx 1.31.6이 `server … resolve` 를 받고, 시작할 때 이름을 풀지 않는다 |

실패 문구 전체는 `[emerg] host not found in upstream "serve" in /etc/nginx/conf.d/default.conf:8` 였다(탐색 때 손으로 봤다). 실제 배치에서 프록시가 뒷단보다 먼저 뜨는 경우는 항목 6과 4에서 본다.

### 1. 뒷단을 다시 만들어 주소가 바뀐 뒤 프록시가 새 컨테이너에 닿는가

조작마다 새로 띄운 배치에서 한 번씩, 실행 2와 6에서 두 번. 표의 칸은 "닿는다/닿지 않는다(본 차례)"이고, 시각은 "실행 2 / 실행 6"이다. 모든 회차에서 표지 다섯(자리 채움을 지웠다, 조작이 그 컨테이너에 닿았다(새 id 또는 새 시작 시각), 주소가 실제로 바뀌었다, 새 컨테이너가 자기 주소에서 스스로 답했다, 닿았다고 센 요청이 그 컨테이너의 접근 기록에 있다)이 섰다. 쟀다.

| 조작 | (가) 고정 | (나) 변수 `valid=5s` | (다) upstream `resolve` |
|---|---|---|---|
| `up -d --force-recreate serve` | 두 번 모두 닿지 않는다(25초 내내 시간 초과) | 두 번 모두 조작 뒤 첫 요청부터 닿는다 | 두 번 모두 닿는다. 첫 요청은 8초 시간 초과, 새 컨테이너는 8.9초 / 10.3초부터 |
| `restart serve` | 두 번 모두 닿지 않는다 | 두 번 모두 첫 요청부터 | 두 번 모두 첫 요청 시간 초과 뒤 8.9초 / 9.3초부터 |
| `docker rm -f <serve>` 뒤 `up -d` | 두 번 모두 닿지 않는다 | 두 번 모두 첫 요청부터 | 두 번 모두 첫 요청 시간 초과 뒤 9.4초 / 8.9초부터 |
| 판 올림: 뒷단 넷의 태그 v1→v2 뒤 `up -d` | 두 번 모두 넷 모두 닿지 않는다 | 두 번 모두 넷 모두 첫 요청부터 | 넷 모두 닿는다. 실행 2는 셋이 첫 요청 시간 초과 뒤 9.4초부터, widget은 첫 요청부터. 실행 6은 넷 모두 첫 요청 시간 초과 뒤 9.0초부터 |
| `up -d --force-recreate` 뒷단 넷 | 두 번 모두 넷 모두 닿지 않는다 | 두 번 모두 넷 모두 첫 요청부터 | 두 번 모두 넷 모두 첫 요청 시간 초과 뒤 9.2초 / 9.0초부터 |

- 요청 한 번의 제한은 8초다. "시간 초과"는 프록시가 8초 안에 아무 답도 하지 않은 것이다. 표본은 조작이 끝난 뒤 곧바로 보내기 시작해, 앞 표본이 끝나면 0.5초 뒤 다음을 보낸다(창 25초).
- (가)에서 다시 만들지 않은 경로는 내내 제 컨테이너가 답했다. 프록시 컨테이너는 어느 조작에서도 그대로였다(compose 가 프록시를 건드리지 않는다).
- `restart serve`(같은 컨테이너를 다시 시작)도 주소가 바뀌었다(.9→.2, .6→.2, .8→.2 등). 낮은 주소가 비어 있으면 Docker가 다시 시작한 컨테이너에 옛 주소를 지켜 주지 않는다. 쟀다(표지 "주소가 바뀌었다"가 이 조작에서도 섰다).
- (가)의 회복: `docker compose exec proxy nginx -s reload` 한 번으로 두 실행의 다섯 조작 모두 회복됐다(reload 뒤 0.3~2.0초부터 새 컨테이너). 표지는 nginx 기록의 `reconfiguring` 줄이 0→2로 는 것과 프록시 컨테이너가 그대로인 것. reload 없이 `docker compose restart proxy` 만 친 갈래도 두 번 모두 회복됐다(1.0초 / 0.2초부터, 표지는 프록시의 새 시작 시각). 쟀다.
- nginx 가 건 주소(실행 6은 접근 기록에 `$upstream_addr` 를 찍는 판이다): (가)는 조작 뒤의 모든 요청을 옛 주소로 걸었고, 그 요청은 곧 실패하지 않고 클라이언트 제한(8초)까지 매달렸다(상태 499). 다만 조작 뒤 약 20초에 보낸 요청은 2~5초 만에 `connect() failed (113: Host is unreachable)` 로 502가 됐다(실행 6의 rm 갈래, 실행 4의 항목 2 두 갈래. 접근 기록 `took` 2.1~5.1초). 커널이 옛 주소의 이웃(ARP) 항목을 실패로 둔 뒤로 본다(어림. 이웃 표는 보지 않았다). (다)의 첫 요청도 다섯 조작 모두 옛 주소로 걸려 499였다. 쟀다(실행 6). 실행 2는 접근 기록이 없던 판이라 오류 기록만 봤고, 상류 오류 줄이 없었다.
- (나)가 첫 요청부터 닿은 것은 조작 직전 요청(조작 1~2초 전)이 기억시킨 옛 주소의 유효 시간(5초) 안이었는데도다. 이 nginx는 작업 프로세스가 16개(`worker_processes auto`, dind의 `nproc` 16을 손으로 봤다)이고, resolver 가 푼 주소를 프로세스마다 따로 기억한다면 다음 요청이 옛 주소를 기억하지 않은 프로세스로 간다. 이 해석을 1w와 3c가 받친다(아래).

### 1w. 작업 프로세스를 하나로 둔 (나)와 (다), 그리고 nginx가 건 상류 주소

실행 2 뒤에 더한 갈래다. 프록시의 주 설정을 `nginx/main/*.conf` 로 얹어 접근 기록에 nginx 가 실제로 건 상류 주소(`$upstream_addr`)와 작업 프로세스 pid를 찍게 했고(작업 프로세스 수 말고는 공식 이미지의 주 설정과 같다), (나)와 (다)를 `worker_processes 1` 로 띄워 같은 조작을 했다. 쟀다(실행 3과 6, 칸마다 두 번).

| 조작 | (나) 변수, 작업 프로세스 하나 | (다) upstream `resolve`, 작업 프로세스 하나 |
|---|---|---|
| `up -d --force-recreate serve` | 두 번 모두 첫 요청이 옛 주소로 걸려 499(접근 기록 `status=499 upstream=172.19.0.8:8000 took=7.991`, 클라이언트가 8초에 끊었다), 9.4초 / 8.9초부터 새 주소 | 실행 3은 첫 요청(0.8초)부터 새 주소. 실행 6은 첫 요청이 옛 주소로 걸려 499, 9.6초부터 새 주소 |
| 판 올림(태그 v1→v2 뒤 `up -d`) | 두 번 모두 넷 모두 첫 요청(0.5초)부터 새 주소 | 실행 3은 serve·admin이 첫 요청부터 새 주소, widget·portal은 첫 요청이 옛 주소로 걸려 499, 10.4초부터 새 주소. 실행 6은 portal만 첫 요청부터 새 주소이고, 셋은 6.3초까지 주소 없이 곧바로 502(접근 기록의 상류가 `up_serve` 같은 이름) 뒤 새 주소 |

- 조작 직전 요청은 모든 회차에서 옛 주소로 갔다(접근 기록). 곧 그 요청이 이름을 풀어 옛 주소를 기억시킨 뒤에 조작이 왔다.
- 프로세스가 하나면 (나)도 `valid` 안에서는 옛 주소로 건다(두 번 모두). 조작이 `valid`(5초)보다 오래 걸리면(판 올림은 `up -d` 가 약 7초) 기억이 끝나 첫 요청부터 새 주소로 건다(두 번 모두). 이것과 3c(`valid` 를 빼면 요청이 옛 주소와 새 주소를 오갔다)로 1의 (나)가 첫 요청부터 닿은 까닭을 "작업 프로세스가 여럿이라 옛 주소를 기억하지 않은 프로세스가 받았다"로 읽는다. 다만 작업 프로세스 수와 조작의 길이를 따로 바꿔 가르지는 않았다.
- (다)는 어느 때 다시 푸느냐에 따라 세 모양이 다 나왔다. 첫 요청부터 새 주소, 옛 주소로 걸려 매달림(499), 다시 만드는 사이에 다시 풀어 주소 없이 곧바로 502. (다)는 기억을 공유 영역(`zone`)에 두고 `valid` 마다 다시 푸는 것으로 본다(어림. 코드는 읽지 않았다). 언제 다시 푸는지의 위상은 재지 않았다.
- 옛 주소로 건 요청은 실패로 곧 돌아오지 않고 클라이언트 제한(8초)까지 매달렸다(`took=7.991`, 상태 499). nginx 의 `proxy_connect_timeout` 기본값은 60초다(어림. 문서를 다시 대 보지 않았다).
- (다)는 새로 띄운 직후에도 이름을 풀기 전에는 곧바로 502를 낸다. 1w의 (다) 기준선을 세울 때 처음 여섯 요청이 `status=502 upstream=up_serve took=0.000` 이었다(실행 3의 raw.log를 손으로 봤다).

### 2. (가) 고정에 `depends_on` 의 `restart: true` 를 걸면 compose 가 프록시를 다시 시작하는가

(가)에 뒷단 넷의 `healthcheck`(`compose.health.yml`)와 프록시의 `depends_on: {<뒷단>: {condition: service_healthy, restart: true}}`(`compose.depends-restart.yml`)를 얹고 항목 1의 조작과 compose 밖의 조작 둘을 했다. `docker compose config` 가 푼 프록시의 `depends_on.serve` 는 `{"condition": "service_healthy", "required": true, "restart": true}` 였다. 표지는 항목 1과 같고, "프록시가 다시 시작됐다"는 프록시 컨테이너의 시작 시각과 id를 조작 앞뒤로 견줬다. 쟀다(실행 4와 6, 조작마다 두 번. 두 번의 결과가 칸마다 같았다).

| 조작 | 프록시 | 결과 |
|---|---|---|
| `up -d --force-recreate serve` | 그대로 | 닿지 않는다(옛 주소로 걸어 499. 실행 4에서는 조작 22초 뒤 보낸 요청이 4.1초 만에 `113: Host is unreachable` 502) |
| `restart serve` | 다시 시작됨 | 닿는다(0.6초 / 0.8초부터 새 주소) |
| `docker rm -f <serve>` 뒤 `up -d` | 그대로 | 닿지 않는다(옛 주소 499. 실행 4에서는 19.5초부터 같은 113 502) |
| 판 올림: 뒷단 넷의 태그 v1→v2 뒤 `up -d` | 다시 시작됨 | 넷 모두 닿는다(0.4초 / 0.8초부터 새 주소) |
| `up -d --force-recreate` 뒷단 넷 | 그대로 | 넷 모두 닿지 않는다(옛 주소 499) |
| `docker restart <serve>`(compose 밖) | 그대로 | 닿지 않는다(옛 주소 499) |
| serve 의 서버 프로세스가 죽어 재시작 정책이 다시 띄움 | 그대로 | 닿지 않는다(옛 주소 499) |

- 닿지 않은 다섯 조작은 두 실행 모두 `docker compose exec proxy nginx -s reload` 한 번으로 회복됐다(`reconfiguring` 줄 0→2, 0.4~2.2초부터 새 컨테이너).
- compose 가 프록시를 다시 시작한 것은 서비스를 고르지 않은 `up -d` 로 이미 있던 뒷단을 다시 만든 판 올림과, `docker compose restart serve` 둘이다. 서비스를 골라 친 `up -d --force-recreate <뒷단>` 은 프록시가 고른 목록에 없어 건드리지 않았고, 컨테이너를 지운 뒤의 `up -d` 도 프록시를 건드리지 않았다(지운 뒷단을 "새로 만든" 것이라 다시 만든 것으로 세지 않은 것으로 본다. 어림, compose 코드는 읽지 않았다). compose 를 거치지 않은 다시 시작과 정책의 다시 띄우기에는 compose 가 끼지 않는다.
- 곧 `restart: true` 는 (가)를 운영자가 정해진 명령(`docker compose pull && docker compose up -d`)으로 판을 올리거나 `docker compose restart <뒷단>` 을 칠 때만 지킨다(판 올림은 태그를 바꾼 `up -d` 로 쟀고 `pull` 은 치지 않았다). 서비스를 골라 다시 만들거나, 뒷단이 스스로 죽어 정책이 다시 띄우면 (가)는 그 뒷단에 닿지 않는다. 마지막 갈래는 사람이 손대지 않아도 나는 일이다.

### 3. 옛 주소를 남이 받으면, 자리 채움 없는 판 올림, 내장 DNS의 TTL

실행 4에서 정리 실패로 측정 아님이 된 뒤 실행 5가 다시 냈고, 실행 6이 되풀이했다(아래 "결과를 본 뒤 바꾼 것"). 쟀다(갈래마다 두 번).

**3a. 다시 만든 serve 의 옛 주소를 다른 컨테이너가 받으면.** 1과 같이 serve 를 다시 만들어 주소를 옮긴 뒤, 같은 네트워크에 같은 포트(8000)로 듣는 다른 컨테이너("squatter")를 옛 주소를 받을 때까지 하나씩 띄웠다. 조작 7초 뒤부터(`valid` 가 지난 뒤) 네 번 물었다. 표지는 serve 가 다시 만들어졌다, 주소가 바뀌었다, squatter 가 옛 주소를 받았다, squatter 와 새 serve 가 저마다 자기 주소에서 스스로 답했다, 끝 요청이 답한 컨테이너의 접근 기록에 있다.

| 변형 | 프록시의 `/serve/` 를 답한 것(두 실행 모두 같다) |
|---|---|
| (가) 고정 | 네 번 모두 squatter(엉뚱한 컨테이너가 200으로 답했다) |
| (나) 변수 | 네 번 모두 새 serve |
| (다) upstream `resolve` | 네 번 모두 새 serve |

**3b. 자리 채움 없이 판 올림.** 1의 판 올림은 자리 채움으로 주소를 일부러 비웠다. 여기서는 자리 채움 없이 태그를 바꾼 `up -d` 를 주소가 바뀔 때까지 되풀이했다(최대 여섯 번). 여섯 회차 모두 첫 번째 올림에서 주소가 바뀌었다. 뒷단이 서로의 주소를 돌려 받았다(예: 실행 5의 (가)에서 serve .2→.4, admin .3→.6, widget .4→.2, portal .6→.3. 실행 6의 (가)에서 serve .3→.2, portal .2→.3, 나머지 둘은 그대로).

| 변형 | 실행 5 | 실행 6 |
|---|---|---|
| (가) 고정 | 넷 모두 닿지 않는다. `/admin/` 은 portal 컨테이너가, `/portal/` 은 admin 컨테이너가 20초 내내 200으로 답했다(둘 다 포트 3000이라 옛 주소의 새 주인이 받았다). `/serve/` 와 `/widget/` 은 502(`connect() failed (111: Connection refused)`, 옛 주소의 새 주인은 다른 포트에서 듣는다) | 주소가 바뀐 둘(serve, portal) 모두 닿지 않는다. 서로의 옛 주소를 받았지만 포트가 달라(8000, 3000) 둘 다 502(`111: Connection refused`, nginx 가 건 상류는 옛 주소) |
| (나) 변수 | 넷 모두 첫 표본(2.8초)부터 새 컨테이너 | 넷 모두 첫 표본(1.6초)부터 새 컨테이너 |
| (다) upstream `resolve` | 바뀐 셋 가운데 portal 은 첫 표본(1.0초)부터, admin 은 4.9초, widget 은 6.3초부터 새 컨테이너. 그 전에는 502 | widget 은 첫 표본(0.9초)부터, portal 은 3.1초, serve·admin 은 5.1초부터 새 컨테이너. 그 전에는 주소 없이 곧바로 502(nginx 가 건 상류가 `up_serve` 같은 이름) |

- 운영자가 정해진 명령으로 판을 올리는 것만으로도 주소가 바뀌고, (가)는 경로가 옛 주소의 새 주인에게 간다. 같은 포트의 뒷단끼리 주소를 바꿔 받으면 다른 서비스가 200으로 답한다(실행 5). 상태 코드가 200이라 프록시의 응답 코드만 보는 감시로는 드러나지 않는다.
- (다)의 502는 엇갈림이 아니라 주소 없음이었다(실행 6의 접근 기록. 실행 5는 접근 기록을 결과에 싣기 전 판이다). 다시 만드는 사이에 다시 풀어 이름이 풀리지 않았고, 다음 다시 풀기까지 곧바로 502를 낸 것으로 본다. 다시 푸는 때가 옛 주소가 남에게 넘어간 뒤 `valid` 안이면 (나)와 (다)도 엇갈려 닿을 수 있다(어림. 이 여섯 회차에서는 나지 않았다).

**3c. `valid` 를 뺀 (나)와 내장 DNS의 TTL.** `valid=5s` 를 뺀 (나)(`nginx/variable-novalid/`)로 `up -d --force-recreate serve` 를 하고 25초 지켜봤다(작업 프로세스 16개).

| 실행 | 결과 |
|---|---|
| 5 | 첫 표본(0.8초)과 둘째 표본이 새 주소로 닿아 거기서 멈췄다 |
| 6 | 요청이 새 주소와 옛 주소를 오갔다. 1.6초·12.4초·23.3초에는 새 컨테이너가 답했고, 3.1초·13.8초·25.5초에는 옛 주소로 걸려 8초 매달렸다(접근 기록 "옛 주소 499") |

같은 네트워크의 컨테이너에서 내장 DNS(127.0.0.11)에 `serve` 를 물으니 두 번 모두 `rcode=0 answers=172.19.0.2:600`, 곧 TTL 600초였다(`backend/dns_ttl.py`). 쟀다.

- `valid` 가 없으면 작업 프로세스마다 기억한 옛 주소가 남아, 그 프로세스가 받은 요청은 다시 만든 지 25초가 지나도 옛 주소로 갔다(실행 6). 그 기억이 내장 DNS가 준 TTL(600초)까지 가는지는 재지 않았다(`--long` 갈래로 재게 해 두었지만 돌리지 않았다). 실행 5에서 바로 닿은 것은 두 표본이 모두 옛 주소를 기억하지 않은 프로세스에 간 것으로 본다(어림).

### 4. 서버를 껐다 켠 뒤 재시작 정책(`unless-stopped`)만으로 돌아오는가

새로 띄운 배치(다섯 모두 `restart: unless-stopped`, `depends_on` 없음)에서 사건 하나를 내고 사람 손 없이 75초 지켜봤다. 표지는 사건이 실제로 났다(데몬만: supervise.sh 의 dockerd 시작 횟수 증가, 서버: dind 컨테이너의 새 시작 시각)와 닿았다고 센 요청이 그 컨테이너의 접근 기록에 있다. 쟀다(실행 3과 6, 칸마다 두 번). 칸의 시각은 "실행 3 / 실행 6"에 네 경로가 모두 닿은 때다.

| 사건 | (가) 고정 | (나) 변수 | (다) upstream `resolve` |
|---|---|---|---|
| 데몬만 다시 켬(dockerd 에 TERM, supervise 가 다시 띄움) | 두 번 모두 돌아온다. 5.4초 / 10.2초(데몬이 다시 답한 때에 바로) | 두 번 모두 돌아온다. 5.8초 / 11.6초 | 두 번 모두 돌아온다. 6.0초 / 10.1초(실행 6은 serve·widget이 첫 요청 502 뒤) |
| 서버를 정상으로 껐다 켬(`docker restart` dind) | 두 번 모두 돌아온다. 5.5초(serve만 첫 요청 502 뒤) / 17.7초 | 두 번 모두 돌아온다. 4.4초 / 7.3초 | 두 번 모두 돌아온다. 14.3초(serve가 6.1~14.3초 동안 502를 여섯 번) / 8.9초 |
| 서버가 죽었다 켜짐(`docker kill` dind 뒤 `start`) | 두 번 모두 돌아온다. 6.2초(admin·portal은 첫 요청 502 뒤) / 11.1초 | 두 번 모두 돌아온다. 5.4초 / 15.7초(두 번 다 admin만 첫 요청 502 뒤) | 두 번 모두 돌아온다. 10.2초 / 8.9초 |

- 시각은 사건을 낸 때부터 잰다. "데몬이 다시 답한 때"까지는 요청을 보내지 않았다(그 전에는 dind 안의 dockerd 가 답하지 않는다). 그래서 첫 표본이 곧 데몬이 다시 답한 때다. 실행 6의 시각이 긴 것은 데몬이 다시 답하기까지가 길었던 탓이다(그 실행에서 데몬이 답한 때가 8.1~17.7초).
- 열여덟 칸 모두 다섯 컨테이너가 같은 id로 다시 시작됐고(재시작 횟수는 늘지 않았다. 데몬이 다시 띄운 것은 정책의 재시작으로 세어지지 않는다), 거의 모든 컨테이너의 주소가 바뀌었다(예: 실행 3의 (가) 데몬만 다시 켬에서 proxy .3→.6, serve .4→.2, admin .6→.4, widget .5→.3, portal .2→.5).
- (가)에서도 nginx 기록에 `host not found in upstream` 이 한 줄도 없었다(두 실행의 세 사건 모두 0→0). nginx 가 설정을 읽을 때 뒷단 넷이 이미 떠 있어 새 주소를 풀었다는 뜻이다. Docker가 다섯을 어떤 차례로 띄우는지는 고를 수 없고 재지 않았다. 뒷단이 떠 있지 않은 때 (가)가 시작하면 어떻게 되는지는 6과 5(위젯을 멈춰 둔 갈래)가 본다.
- (다)는 껐다 켠 뒤 한 경로가 몇 초 502를 냈다(정상 재시작에서 serve가 약 8초). nginx 가 처음 이름을 풀 때 그 뒷단이 아직 등록되지 않았고, 다음 다시 풀기까지 기다린 것으로 본다. 그 회차의 nginx 오류 기록에 사건 뒤 `serve could not be resolved (3: Host not found)` 가 한 줄 있었다(12:03:44 UTC, raw.log를 손으로 봤다). 같은 회차의 기준선을 띄울 때(사건 10초 전)도 `admin`·`portal`·`serve` 가 같은 오류를 냈다. 곧 (다)는 함께 뜬 뒷단이 등록되기 전에 이름을 풀면 다음 다시 풀기까지 502를 낸다.
- 첫 요청의 502(가·나)는 둘 가운데 하나로 본다(어림. 그 회차의 오류 기록은 보지 않았다). 컨테이너가 떠서 이름은 풀렸지만 서버가 아직 포트를 열지 않았거나((가)는 시작할 때 이름을 이미 풀었으므로 이쪽), 그 뒷단이 아직 등록되지 않아 이름이 풀리지 않았다((나)는 요청 때 푼다).

### 5. 재시작 정책과, 운영자가 뒷단 하나를 멈춰 둔 채 서버가 껐다 켜지면

같은 방식(4)으로 정책과 갈래를 바꿨다. "위젯을 멈춰 둠"은 사건 전에 `docker compose stop widget` 을 친 것이다. 쟀다(실행 4와 6, 칸마다 두 번. 두 번의 결과가 칸마다 같았고, 시각은 "실행 4 / 실행 6"이다).

| 갈래 | 사건 | 결과 |
|---|---|---|
| (나), `always` | 데몬만 다시 켬 | 돌아온다(8.1초 / 12.3초에 네 경로 모두) |
| (나), 정책 없음(`restart: "no"`, 대조) | 데몬만 다시 켬 | 다섯 모두 멈춘 채다(proxy 종료 코드 0, 뒷단 넷 143). 20초 내내 연결 거부 |
| (나), 정책 없음(대조) | 서버를 정상으로 껐다 켬 | 다섯 모두 멈춘 채다. 내내 연결 거부 |
| (나), `unless-stopped`, 위젯을 멈춰 둠 | 데몬만 다시 켬 | 위젯만 멈춘 채로 남는다. 나머지 셋은 닿고(admin은 실행 6에서 첫 요청 502 뒤 10.4초부터) `/widget/` 은 502 |
| (나), `always`, 위젯을 멈춰 둠 | 데몬만 다시 켬 | 멈춰 둔 위젯까지 다시 뜬다(8.9초 / 4.5초에 네 경로 모두) |
| (나), `unless-stopped`, 위젯을 멈춰 둠 | 서버를 정상으로 껐다 켬 | 위젯만 멈춘 채로 남는다. 나머지 셋은 닿는다(실행 4의 admin은 11.8초부터) |
| (나), `always`, 위젯을 멈춰 둠 | 서버를 정상으로 껐다 켬 | 멈춰 둔 위젯까지 다시 뜬다(12.7초 / 5.9초에 네 경로 모두) |
| (가) 고정, `unless-stopped`, 위젯을 멈춰 둠 | 데몬만 다시 켬 | 사이트 전체가 닿지 않는다. 뒷단 셋은 떴지만 nginx 가 `host not found in upstream` 으로 끝나기를 되풀이했다(30초 창에 재시작 횟수 +4 / +5, 그 줄 0→8 / 0→10). 네 경로 모두 연결 거부나 `Connection reset by peer` |
| (다) upstream resolve, `unless-stopped`, 위젯을 멈춰 둠 | 데몬만 다시 켬 | 위젯만 멈춘 채로 남는다. 나머지 셋이 모두 닿은 때는 7.1초 / 4.8초(첫 요청이 502였던 경로가 실행 4는 serve 하나, 실행 6은 셋)이고, `/widget/` 은 502(nginx 가 건 상류 `up_widget`, 주소 없음) |

- 정책 없음 대조가 "정책이 다시 띄운다"를 가른다. 같은 사건에서 정책이 없으면 아무것도 돌아오지 않았다.
- `/widget/` 의 502에서 nginx 가 건 상류는 (나)가 `-`(이름이 풀리지 않아 걸 주소가 없다), (다)가 `up_widget`(주소 없는 upstream)이었다. 쟀다(실행 6의 접근 기록).
- `unless-stopped` 와 `always` 의 차이는 운영자가 멈춘 컨테이너뿐이었다. `always` 는 `docker compose stop` 으로 멈춘 위젯을 데몬이 다시 켤 때 다시 띄웠고, `unless-stopped` 는 멈춘 채로 두었다.
- (가)는 뒷단 하나가 멈춘 채로 남는 것만으로(`unless-stopped` 가 그렇게 둔다) 서버를 껐다 켠 뒤 사이트 전체가 내려간다. 항목 6과 같은 일이 사람 손 없이 난다.

### 6. 뒷단 하나가 멈춘(이름이 풀리지 않는) 채 프록시가 다시 뜨면

위젯을 `docker compose stop widget` 으로 멈춘 채 `docker compose restart proxy` 를 치고 20초 지켜본 뒤 위젯을 다시 띄웠다. 표지는 위젯이 멈춰 있었다, 프록시가 실제로 다시 시작됐다(새 시작 시각이나 재시작 횟수 증가), 위젯이 다시 떴다, 닿았다고 센 요청이 위젯의 접근 기록에 있다. 쟀다(실행 3과 6, 변형마다 두 번. 두 번의 결과가 같았고, 시각은 "실행 3 / 실행 6"이다).

| 변형 | 위젯이 멈춘 20초 동안 | 위젯을 다시 띄운 뒤 |
|---|---|---|
| (가) 고정 | 프록시가 아무 경로에도 답하지 않는다. `/proxy-alive` 와 멀쩡한 `serve` 까지 연결 거부나 `Connection reset by peer`. nginx 가 `[emerg] host not found in upstream "widget"` 로 끝나고 재시작 정책이 다시 띄우기를 되풀이했다(20초에 재시작 횟수 3, 두 번 모두) | 1.5초 / 2.4초 뒤 네 경로 모두 닿는다(정책이 다시 띄운 nginx 가 이름을 풀었다, 재시작 횟수 4) |
| (나) 변수 | 프록시는 뜬다(재시작 횟수 0). `/proxy-alive` 와 `serve` 는 내내 닿고, `/widget/` 만 502 | 1.3초 / 1.2초 뒤 네 경로 모두 닿는다 |
| (다) upstream `resolve` | 프록시는 뜬다(재시작 횟수 0). `/proxy-alive` 와 `serve` 는 내내 닿고, `/widget/` 만 502 | 6.8초 / 6.3초 뒤 네 경로 모두 닿는다(다시 풀기를 기다린다) |

- (나)의 `/widget/` 502는 한 번에 약 3.3초 걸렸다(실행 3의 접근 기록 `status=502 upstream=- took=3.344`, 오류 기록 `widget could not be resolved (3: Host not found)`). (다)의 502는 곧바로였다(`took=0.000`, 상류 `up_widget`). 둘 다 raw.log를 손으로 봤다.
- 실행 6에서는 위젯을 멈춘 뒤 같은 네트워크의 admin 컨테이너에서 내장 DNS에 `widget` 을 직접 물었다. 세 회차 모두 `rcode=3`(이름 없음)이 3.3초 걸려 왔다(3311·3284·3328ms). 쟀다. 곧 (나)의 502가 3.3초 걸린 것은 내장 DNS가 모르는 이름에 "없다"고 답하기까지 걸린 시간이다. 내장 DNS가 그 3.3초 동안 바깥 DNS에 물어보는지는 재지 않았다(어림).

### 7. 늦게 뜨는 뒷단과 `depends_on` + `healthcheck`

위젯이 컨테이너가 뜬 뒤 20초 지나서야 포트를 여는 배치(`WIDGET_DELAY=20`)를 빈 자리에서 `up -d` 로 띄우며 1초 간격으로 물었다. `depends_on` 갈래는 뒷단 넷의 `healthcheck`(2초 간격, `compose.health.yml`)와 프록시의 `depends_on: {<뒷단>: {condition: service_healthy}}`(`compose.depends.yml`)를 얹었다. 표지는 위젯의 기록에 지연과 듣기 시작이 찍혔다, 위젯 경로가 닿기 전에 닿지 않는 응답을 봤다, 위젯이 지연 뒤에 닿았고 그 요청이 위젯의 접근 기록에 있다. 쟀다(실행 5와 6, 칸마다 두 번. 시각은 "실행 5 / 실행 6"이다).

| 변형 | `depends_on` 없음 | `depends_on: service_healthy` |
|---|---|---|
| (가) 고정 | 프록시와 serve 12.6초 / 3.5초, 위젯은 그때부터 502 뒤 23.0초 / 23.1초 | 셋 모두 28.7초 / 24.7초. 그 전에는 프록시가 없어 serve까지 연결 거부 |
| (나) 변수 | 프록시 5.3초 / 2.9초, serve 13.2초 / 2.9초, 위젯은 502 뒤 23.6초 / 22.2초 | 셋 모두 30.8초 / 25.6초. 그 전에는 연결 거부 |
| (다) upstream `resolve` | 프록시 4.5초 / 1.4초, serve 15.6초 / 10.4초, 위젯은 502 뒤 30.4초 / 22.5초 | 셋 모두 29.0초 / 25.2초. 그 전에는 연결 거부 |

- 칸의 시각은 "처음 답한 때"다. `up -d` 가 도는 동안은 표본 하나가 몇 초씩 걸릴 때가 있어(실행 5의 (가)는 12.6초 안에 표본 셋) 시각의 눈금이 거칠다. 실행 5의 (가)가 12.6초였던 것도 그 탓으로 본다. 실행 6에서 (가)의 프록시는 3.5초에 답했고 두 실행 모두 끝의 프록시 재시작 횟수가 0이었다(실행 5는 원본에서 손으로, 실행 6은 결과 줄로 봤다).
- `depends_on: service_healthy` 는 `up` 때 가장 늦은 뒷단이 건강해질 때까지 프록시를 띄우지 않았다. 그동안 빨리 뜬 serve 까지 사이트 전체가 연결 거부였다(두 실행 모두). 없으면 프록시가 먼저 떠 뜬 뒷단부터 닿고, 늦은 위젯 경로만 502를 냈다.
- `depends_on` 없는 (가)·(나)의 위젯 502는 nginx 가 위젯의 새 주소로 걸었는데 아직 포트가 열리지 않은 것이었다(실행 6의 접근 기록 "새 주소 502"). (가)는 처음 띄울 때 끝나지 않았다. 위젯은 컨테이너가 떠 이름은 풀리고 포트만 늦게 열려, (가)가 끝나는 조건(이름이 풀리지 않는다)에 들지 않는다.
- `depends_on` 없는 (다)는 프록시가 먼저 답하기 시작했지만, serve 까지 늦게 닿았다(15.6초 / 10.4초. (가)·(나)는 실행 6에서 3초 안에). 실행 6의 접근 기록에서 serve 와 위젯이 10.4초까지 주소 없이 곧바로 502였다(상류 `up_serve`, `up_widget`). 프록시가 뒷단보다 먼저 이름을 풀어 실패했고, 그 뒤 다시 풀기까지 주소 없이 기다린 것으로 본다. 다시 풀기의 간격이 `valid`(5초)보다 길었던 까닭은 재지 않았다(모르는 이름에 내장 DNS가 3.3초 걸려 답한 것(항목 6)이 더해졌을 수 있다. 어림).

같은 `depends_on` 배치에서 데몬만 다시 켠 갈래(위젯 20초 지연, 75초 관찰, 실행 5 / 실행 6):

| 변형 | 결과 |
|---|---|
| (가) 고정 | 데몬이 다시 답한 7.6초 / 4.8초에 serve·admin·portal이 닿고, 위젯은 502 뒤 27.9초 / 24.9초 |
| (나) 변수 | 데몬이 다시 답한 5.2초 / 3.9초에 셋이 닿고, 위젯은 502 뒤 25.2초 / 23.2초 |

- 데몬이 컨테이너를 다시 띄울 때는 `depends_on` 이 프록시를 붙잡지 않았다. `depends_on` 은 compose 가 `up` 할 때만 차례를 정한다. 서버를 껐다 켠 뒤의 차례는 4·5처럼 정해져 있지 않다.

### 8. 호스트에서 고친 설정 파일과 `nginx -s reload`

(가)의 설정을 서버(dind)의 폴더 `live/` 에 두고 프록시에 얹은 뒤, 서버에서 세 방법으로 location 하나(`/edited`, 회차마다 다른 토큰을 답한다)를 더하고 `docker compose exec proxy nginx -s reload` 를 쳤다. 얹는 방법은 폴더째(`./live:/etc/nginx/conf.d`, `compose.mount-dir.yml`)와 파일 하나(`./live/default.conf:/etc/nginx/conf.d/default.conf`, `compose.mount-file.yml`) 둘이다. 표지는 고치기 전에는 `/edited` 가 없었다, 서버의 파일에 새 줄이 들었다, 서버 파일의 inode 가 방법에 맞게 바뀌었거나 그대로다, reload 가 nginx 에 닿았다(`reconfiguring` 줄 증가). 쟀다(실행 5와 6, 칸마다 두 번. 두 번의 결과가 칸마다 같았다).

| 고치는 방법(서버 파일의 inode) | 폴더째 얹음 | 파일 하나로 얹음 |
|---|---|---|
| 제자리에서 덮어쓰기 `cat 새것 > 파일`(그대로) | reload 뒤 먹었다 | reload 뒤 먹었다 |
| 새 파일로 바꿔 끼우기 `mv 새것 파일`(바뀜) | reload 뒤 먹었다 | 먹지 않았다. 컨테이너 안의 파일에 새 줄이 없고(옛 파일을 본다) `/edited` 는 404. `docker compose up -d` 뒤에도 404, `docker compose restart proxy` 뒤 먹었다 |
| `sed -i` 로 한 줄 더하기(바뀜) | reload 뒤 먹었다 | 먹지 않았다. 위와 같다(`up -d` 로는 안 되고 `restart proxy` 로 먹었다) |

- 파일 하나로 얹으면 얹을 때의 파일에 묶여, 이름 바꾸기로 저장하는 편집(`sed -i`, 많은 편집기의 저장 방식)이 컨테이너에 보이지 않는다. 설정은 폴더째 얹는 것이 안전하다.
- `docker compose up -d` 는 compose 파일이 바뀌지 않았으므로 프록시를 다시 만들지 않아 고치지 못했다. `restart proxy` 가 얹기를 다시 해 새 파일을 봤다.

깨진 설정(`no_such_directive on;` 한 줄)을 폴더째 얹은 배치에 넣은 갈래: `nginx -t` 는 종료 1(`configuration file /etc/nginx/nginx.conf test failed`), `nginx -s reload` 도 종료 1이었다. 그 뒤 네 경로는 옛 설정으로 계속 답했고 프록시 컨테이너는 그대로였다. 쟀다(실행 5와 6, 두 번 모두 같다). reload 명령 자신이 설정을 읽다 `[emerg] unknown directive "no_such_directive"` 로 끝나 돌던 nginx 에 신호를 보내지 않은 것으로 본다. 그 회차의 원본에서 reload 명령의 오류 출력에 그 줄이 있고, 프록시의 기록에는 없었다(raw.log를 손으로 봤다).

## 결과를 본 뒤 바꾼 것

결과를 본 뒤 프로브를 고친 자리다. 판정 기준을 느슨하게 한 것은 3b 하나이고, 그 기준이 걸리는 회차(주소가 바뀌지 않은 회차)는 나지 않았다. 나머지는 결과 줄에 싣는 것을 늘렸거나 프로브의 결함을 고친 것이다.

- 실행 2(항목 1) 뒤: (가)가 닿지 않는 동안 오류 기록이 비어 nginx 가 어디로 걸었는지 보이지 않았다. 프록시의 주 설정을 `nginx/main/*.conf` 로 얹어 접근 기록에 `$upstream_addr` 와 작업 프로세스 pid를 찍게 하고, 결과 줄에 "nginx 가 건 상류"(조작 직전 요청과 조작 뒤 요청)를 더했다. 1의 (나)가 첫 요청부터 닿은 것을 가르려고 1w를 더했다.
- 실행 3(항목 6) 뒤: (나)의 `/widget/` 502가 3.3초 걸린 까닭을 보려고, 멈춘 위젯의 이름을 같은 네트워크에서 내장 DNS에 직접 묻는 질의를 결과 줄에 더했다.
- 3b(판 올림을 주소가 바뀔 때까지 되풀이): 돌리기 전에, 최대 횟수까지 올려도 주소가 바뀐 뒷단이 없으면 그것도 결과로 세게 바꿨다. 그 회차의 표지는 올릴 때마다 뒷단 넷이 실제로 다시 만들어진 것이다. 처음 판은 그런 회차를 측정 아님으로 셌다.
- 실행 5(항목 3·7·8) 뒤: 3b의 결과 줄에 바뀐 경로의 "nginx 가 건 상류"를, 7의 결과 줄에 serve·widget 경로의 "nginx 가 건 상류"와 끝의 프록시 재시작 횟수를 더했다. 실행 5의 3b (다)에서 502가 엇갈림인지 주소 없음인지, 7의 (가)가 처음 띄울 때 끝났는지를 결과 줄로 가를 수 없었다.
- 실행 4의 3a: "정리 실패" 표지가 섰다. 프로브의 결함 둘 때문이었다. squatter 를 이름의 머리를 떼지 않은 채 찾아 옛 주소를 받은 squatter 를 놓쳤고("squatter 가 옛 주소를 받았다" 표지 없음), 정리가 squatter 보다 compose 네트워크를 먼저 지우려 해 네트워크가 `Resource is still in use` 로 남았다(raw.log와 안쪽 `docker network ls` 로 손으로 봤다). 표지대로 그 회차와 그 뒤의 3·7·8 회차, 끝 정리까지 스물넷이 모두 측정 아님으로 세어졌고 종료 코드는 1이었다(앞의 5·2 회차 스물하나는 측정). 둘을 고치고 3·7·8을 다시 돌렸다. 정리 실패 표지가 프로브 자신의 결함을 잡은 사례다.

## 재지 못한 것

- 진짜 리눅스 서버의 재부팅과 `systemctl restart docker`. dind로 흉내 냈다(아래 "알려진 한계").
- 바깥 DNS에 닿지 않는 서버(인터넷 없는 곳). 내장 DNS가 모르는 이름에 "없다"고 답하기까지 3.3초 걸렸다(항목 6). 그동안 바깥 DNS에 묻는 것이라면, 바깥 DNS가 없는 서버에서는 (나)·(다)의 그 502가 더 늦거나 nginx `resolver_timeout`(기본 30초, 어림)까지 매달릴 수 있다. dind는 Docker Desktop의 DNS에 닿는다.
- `valid` 없는 (나)가 내장 DNS의 TTL(600초) 내내 옛 주소를 쓰는지(`--long`, 11분). 돌리지 않았다. 25초까지는 일부 요청이 옛 주소로 갔다(3c).
- (다)가 언제 다시 푸는지(위상)와, 요청이 많을 때 옛 주소로 가는 요청의 수. 표본은 경로마다 한 번에 요청 하나다. 요청이 많으면 모든 작업 프로세스가 옛 주소를 기억하고 있어 (나)도 `valid` 동안 옛 주소로 걸 것으로 본다(어림. 1w가 프로세스 하나로 그 모양을 봤을 뿐이다).
- (나)·(다)가 `valid` 안에서 옛 주소의 새 주인(같은 포트의 다른 뒷단)에게 거는 엇갈림. (가)에서는 3a·3b가 쟀고, (나)·(다)에서는 나지 않았지만 갈래를 따로 두지 않았다.
- 옛 주소로 건 요청이 매달리는 시간을 줄이는 설정(`proxy_connect_timeout` 등)과, (나)·(다)에서 판을 올린 뒤 `nginx -s reload` 를 더 치는 절차. reload 는 (가)에서만 쟀다.
- 7에서 `depends_on` 없는 (다)가 이름을 처음 풀지 못한 뒤 다시 풀기까지 `valid`(5초)보다 오래(약 9~11초) 주소 없이 502를 낸 까닭.
- (나)·(다)에 `depends_on` 의 `restart: true` 를 건 갈래. 2는 (가)에만 걸었다.
- 작업 프로세스 수와 조작의 길이를 따로 바꾼 갈래. 1w의 해석은 갈래 하나씩에 기댄다.
- 다른 nginx 판. 1.31.6 하나만 봤다. `server … resolve` 를 받지 않는 옛 판(1.27.3 앞, 어림)의 거부는 보지 않았다(음성 대조 없음).
- IPv6 네트워크, rootless Docker, podman, live-restore 를 켠 데몬.
- 실제 이미지 넷의 시작 시간, 건강 검사, 종료 처리. 뒷단은 흉내 서버다.
- 다른 기기에서 오는 요청과 호스트 포트 게시의 길. 요청은 서버 자신에서 보냈다.
- 재시작 정책의 기다림이 길어지는 것. 고정 변형이 오래 크래시를 되풀이하면 Docker의 다시 띄우기 간격이 늘어난다고 알려져 있지만(어림) 20초 넘게 보지 않았다.
- 세 번째 되풀이. 칸마다 두 번이다. 시각(몇 초 만에 닿았는지)은 두 번 사이에도 몇 초씩 갈려, 결론은 닿는다·닿지 않는다와 그 모양으로만 낸다.

## 알려진 한계

- dind는 진짜 재부팅이 아니다. systemd가 없어 `docker.service` 의 시작 순서와 `containerd` 서비스가 따로 도는 모양을 흉내 내지 않는다(dind에서는 dockerd가 containerd를 띄운다). 커널은 다시 켜지지 않고(Docker Desktop의 WSL2 커널 6.18.58.1), `/run` 을 tmpfs로 얹어 재부팅 때 비는 것을 흉내 낸다.
- 요청은 서버 자신(dind 안)에서 보낸다. 바깥 클라이언트와 호스트 포트 게시의 길은 재지 않는다.
- 뒷단은 흉내 서버다. 실제 `serve`, 관리 화면, 위젯 이미지의 시작 시간과 건강 검사는 재지 않는다.

## PR 직전 리뷰가 좁힌 측정 조건(2026-11-14)

위 결과를 낸 실행 뒤에 CodeRabbit CLI가 짚어 측정 조건을 좁혔다. 좁힌 판은 다시 돌리지 않았다.

- `natural`(3b)의 주소가 바뀐 갈래: 올림마다 뒷단 넷이 모두 다시 만들어졌는지(`recreated`)도 보게 했다. 전에는 주소가 바뀌지 않은 갈래만 그것을 봐서, 일부만 다시 만들어진 올림도 판 올림의 측정으로 셀 수 있었다. 기록한 회차 가운데 실행 5의 (가)·(나)와 실행 6의 (나)·(다)는 3b 절이 네 뒷단을 모두 주소가 바뀐 뒷단으로 적어 이미 보였다. 실행 5의 (가)는 네 뒷단의 주소 목록으로, 나머지 셋은 네 경로의 본 차례로다. 결과 줄의 본 차례는 주소가 바뀐 뒷단만 싣고, 주소가 바뀐 뒷단은 다시 만들어진 뒷단 가운데서만 센다(코드를 읽었다). 실행 5의 (다)에서 주소가 그대로인 serve와 실행 6의 (가)에서 주소가 그대로인 admin·widget이 다시 만들어졌는지는 기록으로는 가를 수 없다.
- `slow_up`(7)의 "위젯 경로가 닿기 전에 닿지 않는 응답을 봤다": 그 응답이 실제로 보낸 요청의 것(`asked`)이어야 하게 했다. 보내지 못한 요청도 닿지 않은 응답으로 읽혔다. 기록한 회차는 7절이 이미 보였다(닿기 전의 응답을 "502"와 "연결 거부"로 적었다. 보내지 못한 요청은 결과 줄에 "서버에 닿지 않음"으로 찍힌다).
- `boot`(4, 5, 7의 데몬 갈래)와 `unresolved`(6): 표본의 요청이 모두 실제로 나갔다는 표지("요청이 모두 실제로 나갔다")를 더했다. 닿지 않았다는 관찰이 보내지 못한 요청에서 서지 않게 하려는 것이다. 기록한 회차는 4~7절이 닿지 않은 응답을 "502", "연결 거부", `Connection reset by peer` 로 적어 실제로 보낸 요청이 닿지 않은 것은 보였다. 그러나 이 절들은 결과 줄의 요약이라, 표본의 요청이 하나도 빠짐없이 나갔는지는 기록으로는 가를 수 없다.
- `broken_round`(8의 깨진 설정): reload 가 그 설정 때문에 거부됐다는 표지(reload 명령의 출력이나 프록시의 기록에 `no_such_directive`)를 더했다. 전에는 `nginx -t` 의 실패만 봐서, `docker compose exec` 가 실행 오류로 끝나도 옛 설정이 계속 답하면 거부로 셀 수 있었다. 기록한 회차는 8절이 이미 보였다("그 회차의 원본에서 reload 명령의 오류 출력에 그 줄이 있고, 프록시의 기록에는 없었다(raw.log를 손으로 봤다)").
- `dind_up`: 측정 조건이 아니라 다시 실행하는 흐름을 고쳤다. `--keep` 으로 남긴 dind 컨테이너가 떠 있을 때 `--reuse` 없이 돌리면, 지우고 새로 만든 컨테이너를 시작하지 않아 안쪽 dockerd 를 기다리다 종료 2로 끝났다. 새로 만든 갈래에서는 시작하게 했다. 이 길은 회차를 내기 전에 끝나므로, 회차를 낸 기록의 여섯 실행은 이 길을 지나지 않았다.
