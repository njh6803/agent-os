**사용자가 고른 것은 여섯이고 본문의 여섯 자리에 "사용자가 골랐다"로 표시했다.** 시험의 이음매 넷(Testing Decisions), 예시 MCP 서버의 매니페스트를 저장소에서 바꾸는 것("이미지의 구성"의 예시 MCP 서버), 릴리스와 태그를 세분 토큰으로 만드는 것("판 내기 워크플로"의 권한과 비밀 값), 운영자용 요약 단락을 노트 조각으로 쓰는 것("릴리스 노트"), 443과 80을 서버의 IPv4 주소에만 발행하는 것("프록시 설정"의 IPv6), 초안이 git 태그를 만드는지에 기대지 않는 대조를 두는 것("판 내기 워크플로"의 초안과 git 태그)이다. 여섯 다 추천을 맨 앞에 둔 선택 화면으로 물었고 여섯 다 추천을 골랐다. 앞의 다섯은 이 명세를 쓴 세션이 물었고(일지 2026-11-13-1843 "사용자에게 물은 것 하나"부터 "다섯"까지), 여섯째는 명세 검토 뒤 티켓을 쓴 세션이 물었다(일지 2026-11-14-1748 "사용자에게 물은 것 둘"). 고르지 않은 선택지와 그 설명도 그 일지들에 있다.

**명세가 정한 것은 그 자리에 "명세가 정했다"로 표시했다.** 표시는 이 문단 밖에 스물넷이다. 스물둘은 절 머리라 그 절 전체에 걸리고, 둘은 "판 내기 워크플로"의 권한과 비밀 값(값을 담는 자리)과 "사람 몫"의 할 일 목록에 걸린다. 사용자가 고른 둘(권한과 비밀 값, "릴리스 노트")은 고른 것과 명세가 채운 것을 한 표시 안에서 가른다. 절 안의 항목이 "사용자가 골랐다"를 달면 그 항목에는 절 머리의 표시가 걸리지 않는다("이미지의 구성"의 예시 MCP 서버, "프록시 설정"의 IPv6, "판 내기 워크플로"의 권한과 비밀 값과 초안과 git 태그). 표시가 없는 것은 ADR 0056과 그 이력, 설계 일지, 기능 계획, 기존 규칙에서 왔거나, 표시한 결정을 시험과 문서로 옮긴 것이다. 절 머리에 "넘겨받은 것"이라 적은 두 절("사람 몫", "rag-engine에 줄 지시문")은 넘겨받은 일을 옮겨 적은 절이다.

**이력은 일곱이고 ADR 0056의 이력에 쌓았다.** 넷은 2026-11-13이고 셋은 2026-11-14다. 다섯째는 그 질문의 답을 자정을 넘겨 받았고, 여섯째와 일곱째는 셀프 리뷰를 반영하며 정했다. 바뀐 본문 문장마다 포인터를 달았다. 셀프 리뷰를 반영한 뒤 2026-11-14에 사용자가 일곱 모두 승인했다(일지 2026-11-13-1843 "ADR 0056 이력의 승인").

1. "릴리스 노트에 세션이 미리 쓴 노트 조각을 싣는다". 결정 "판마다 나오는 것"의 "릴리스 노트는 … 묶은 것이고 사람이 쓰는 글이 없다"를 바꾼다("릴리스 노트").
2. "이미지 안의 판 번호는 태그와 글자까지 같다". 결정 "저장소의 번호"의 두 문장이 거짓이 된다("이미지의 구성"의 판 번호).
3. "trivy-action 권고의 영향 없음 조건을 바로잡는다". Consequences "CI와 비밀 값"의 사실을 바로잡고 결정에는 닿지 않는다("취약점 점검").
4. "릴리스와 태그는 세분 토큰으로 만들고 비밀 값은 main 전용 환경에 둔다". 같은 Consequences의 "기본 토큰으로 만든 태그와 릴리스는 다른 워크플로를 일으키지 않으므로"가 내세운 까닭이 서지 않는다("판 내기 워크플로"의 권한과 비밀 값).
5. "443과 80은 서버의 IPv4 주소에만 발행한다". 결정 "밖으로 여는 포트"의 "호스트의 모든 주소에 발행하는 포트는 프록시의 443과 80이다"가 거짓이 된다("프록시 설정"의 IPv6).
6. "실제 이미지의 compose e2e 잡은 Dockerfile과 compose를 갖추는 티켓이 더한다". 결정 "실제 이미지로 띄우는 시험"과 Consequences "다른 ADR"이 잡을 더한다고 적은 "첫 티켓"이 거짓이 된다("티켓을 나눌 때 함께 둘 것", Testing Decisions의 첫째).
7. "번호 태그를 붙인 뒤 실패한 판은 남긴 초안을 공개해 끝낸다". 결정 "판 내기의 차례와 실패"의 다시 시도하는 문장과 핫픽스 문장이 번호 태그를 붙이기 전의 실패에만 그대로 맞게 된다("판 내기 워크플로", "실패한 판을 다시 돌리는 길").

지원하는 최소 판(표의 마지막 행)은 결정 "보증하는 환경"의 문장을 참으로 둔 채 판을 더하므로 이력을 쌓지 않았다. 예시 MCP 서버의 매니페스트를 고치는 자리도 같은 ADR이 정한 "미리 설치한 것을 실행하도록 고친다"를 어디서 고칠지 정한 것이라 쌓지 않았다. 앞의 것은 설계 일지가 "정하는 것이 ADR 0056의 개정이면 사용자에게 올린다"고 넘긴 것이라 이력의 승인을 물을 때 이 판단도 함께 보였다. 셀프 리뷰를 반영하며 정한 것 가운데 기능 계획의 수락을 확인하는 길과 rag-engine에 줄 지시문을 내는 세션(둘 다 Testing Decisions의 넷째)은 ADR이 아니라 기능 계획의 문장을 읽은 것이라 이력을 쌓지 않았고, 승인을 물을 때 함께 보였다. 사용자는 이력을 쌓지 않은 이 네 판단을 모두 그대로 두기로 했다(같은 일지 절).

**거부한 안은 스물한 자리에 "거부한 안:"으로 시작하는 문단으로 적었고, 그 문단들이 든 안은 마흔셋이다.** 그 가운데 여섯은 사용자에게 보인 선택지 가운데 고르지 않은 것이고, 그 문단에 그렇게 적었다("이미지의 구성"의 예시 MCP 서버, "판 내기 워크플로"의 권한과 비밀 값과 초안과 git 태그, "프록시 설정"의 IPv6).

## Problem Statement

운영자 관점. agent-os를 서버에 올리려면 지금은 저장소를 받아 파이썬과 Node 환경을 만들고, 네 프로세스(`serve`, 관리 화면, 위젯, 위젯 미리보기 페이지)를 손으로 띄운 뒤, 그 앞에 TLS를 끝내는 프록시를 직접 짜야 한다. 어느 커밋이 "판"인지 알 길이 없고, 받은 것이 무엇이 달라졌는지 적은 글도 없으며, 네 프로세스는 루프백에만 서므로 다른 컨테이너의 프록시가 닿을 수도 없다. 인터넷이 막힌 서버에 옮기는 방법도, 이미지에 든 소프트웨어와 그 취약점을 확인할 자료도 없다.

개발자(에이전트 세션) 관점. 판을 낼 사람이 따로 없다. 사용자는 판 내기를 전부 자동으로 하기를 바랐고(ADR 0056 Considered Options), 판을 내는 때와 번호와 노트가 세션의 판단에 기대면 세션마다 달라진다. 또 PR 제목만 묶은 노트는 개발자의 말이라 운영자가 무엇이 달라지는지 읽기 어렵고, 올릴 때 운영자가 손댈 것은 제목 한 줄에 담긴 만큼만 실린다(일지 2026-11-12-0108, 2026-11-13-1843).

## Solution

main이 움직이면(출시 PR이나 핫픽스가 병합되면) CI가 지난 판 뒤로 제품 변경이 있는지 보고, 있으면 커밋 제목의 접두로 번호를 계산해 판을 낸다. 판 하나는 Docker Hub의 이미지 넷(번호 태그와 커밋 해시 태그), GitHub 릴리스(노트, 배포 파일 묶음, 소프트웨어 목록, 취약점 점검 결과), 그리고 마지막에 다는 git 태그다. 0.1.0 전의 판은 모두 출시 후보다.

운영자는 릴리스에 첨부된 배포 파일 묶음 하나를 풀고, 인증서와 키 파일과 사이트 파일과 위젯 미리보기 페이지 설정과 환경 변수 파일을 채운 뒤 `docker compose up`을 친다. 그러면 nginx와 네 컨테이너가 보통의 Docker 네트워크로 묶여 뜨고, 밖에서는 서버의 IPv4 주소에 443(TLS, HSTS)과 443으로 넘기기만 하는 80만 열린다. 방문자는 한 공개 출처 아래에서 위젯과 위젯 미리보기 페이지로 질문하고, 토큰 끝점에 한도를 넘겨 요청하면 429를 받는다. 관리 화면은 서버의 `127.0.0.1`에만 열려 운영자가 SSH 포트 포워딩으로 닿는다. 네 프로세스는 이미지 안에서 compose가 준 명시적 설정이 있을 때에만 컨테이너 네트워크 쪽 주소에 묶이고, 그 밖에서는 지금처럼 루프백만 받는다.

릴리스 노트에는 커밋 제목의 목록보다 앞에 기능마다 운영자의 말로 쓴 짧은 단락이 서고, 올릴 때 운영자가 손댈 것이 있는 변경 아래에는 그 할 일이 선다. 둘 다 기능의 마지막 티켓이나 그 변경의 PR을 맡은 세션이 저장소의 작은 파일(노트 조각)로 미리 써 두고, 판 내기는 그 파일을 글자 그대로 옮길 뿐 모델을 부르지 않는다. 길이와 빠뜨림은 병합 전의 검사가 막는다.

## User Stories

1. As an 운영자, I want 릴리스에 첨부된 배포 파일 묶음 하나를 풀어 채울 것만 채우고 `docker compose up`으로 띄우기, so that 저장소를 받아 파이썬과 Node 환경을 만들지 않고 agent-os를 올린다.
2. As an 운영자, I want 이미지 태그가 판 번호와 커밋 해시뿐이고 늘 최신을 가리키는 태그가 없기, so that 어느 판이 도는지 늘 안다.
3. As an 운영자, I want 이미지 안의 `agent-os --version`과 API 문서의 판 칸이 받은 태그의 번호를 보이기, so that 띄운 것이 받은 판인지 확인한다.
4. As an 운영자, I want 끝자리만 오른 판은 환경 변수 파일의 판 번호 한 줄만 바꾸면 되기, so that 고친 것만 담긴 판을 부담 없이 올린다.
5. As an 운영자, I want 올릴 때 손댈 것이 있는 판은 가운데 자리가 오르고 노트의 "올릴 때 할 일"에 무엇을 무엇으로 바꾸는지 적히기, so that 올린 뒤 서비스가 멈추지 않는다.
6. As an 운영자, I want 노트에서 커밋 제목의 목록보다 앞에 선, 기능마다 무엇이 달라지는지 운영자의 말로 쓴 짧은 단락을 읽기, so that 제목 목록을 다 읽지 않고 판을 올릴지 정한다.
7. As an 운영자, I want 고친 것이 노트에 빠짐없이 실리기, so that 겪던 문제가 고쳐졌는지 안다.
8. As an 운영자, I want 고칠 수 있는 심각한 취약점이 든 판의 노트 맨 위에 경고가 서기, so that 그 판을 그대로 쓸지 판단한다.
9. As an 운영자, I want 릴리스에 소프트웨어 목록과 취약점 점검 결과가 첨부되기, so that 보안 검토에 낼 자료가 있다.
10. As an 운영자, I want 밖으로 열린 포트가 443과 443으로 넘기기만 하는 80뿐이기, so that 방화벽에 열 것이 둘이다.
11. As an 운영자, I want 관리 화면이 서버의 `127.0.0.1`에만 열리고 SSH 포트 포워딩으로 닿기, so that 로그인이 생기기 전에 관리 화면이 인터넷에 열리지 않는다.
12. As an 운영자, I want 내 인증서와 키 파일(사내 인증 기관이 발급한 것 포함)을 정해진 폴더에 두면 프록시가 읽기, so that 인터넷이 막힌 곳에서도 TLS를 쓴다.
13. As an 운영자, I want 스스로 서명한 인증서를 만드는 명령이 안내에 있기, so that 인증서를 받기 전에 시험 삼아 먼저 띄워 본다.
14. As an 운영자, I want 인터넷이 막힌 서버로 이미지를 파일로 옮기고 해시를 대조하는 명령이 안내에 있기, so that 폐쇄망에 반입한다.
15. As an 운영자, I want Docker Hub에서 받는 횟수 제한이 안내에 적히기, so that 여러 서버에 받다가 막히는 일을 미리 안다.
16. As an 운영자, I want 플러그인 폴더와 트레이스 폴더가 이미지 밖에 있기, so that 판을 바꿔도 내 에이전트와 기록이 남는다.

18. As an 운영자, I want 사이트 파일을 고친 뒤 무엇을 다시 띄워야 하는지 안내가 적기, so that 바꾼 허용 출처가 듣지 않아 헤매지 않는다.
19. As an 운영자, I want 서버나 Docker를 다시 켠 뒤 배포가 스스로 돌아오기, so that 재부팅이 서비스를 멈춘 채로 두지 않는다.
20. As an 운영자, I want 컨테이너 하나를 다시 만든 뒤에도 프록시가 그 컨테이너에 다시 닿기, so that 하나만 다시 띄워도 오류가 남지 않는다.
21. As an 운영자, I want 지원하는 Docker Engine과 Compose의 최소 판이 안내에 적히기, so that 관리 화면을 `127.0.0.1`에 둔 보호가 내 서버에서 실제로 서는지 안다.

## Implementation Decisions

구현 파일의 경로와 코드 조각은 새로 짓지 않는다. 규칙 문서·ADR·시험 선례의 경로와, ADR 0056이 명세에 이름을 짓게 넘긴 것(판 설정 파일, 예외 설정, 제품 변경의 경로 목록)과 다른 기능과 세션이 쓰고 읽는 자리(노트 조각, 배포 파일 묶음의 자리)는 적는다. 프로브가 낸 설정 조각은 결정을 글보다 정확히 담는 부분만 옮기고 그렇게 적는다.

### 저장소의 자리(명세가 정했다)

배포에 드는 파일은 새 최상위 폴더 `deploy/`에 둔다. 이미지 넷을 짓는 파일은 `deploy/images/`, 배포 파일 묶음의 원본(compose 파일, 프록시 설정, 환경 변수 틀, 설정 파일 틀, 배포 안내)은 `deploy/standalone/`, 판 설정 파일은 `deploy/release.toml`이다. 이 폴더 하나가 ADR 0056 결정 "제품 변경"이 든 Dockerfile·compose 파일·프록시 설정·배포 안내·판 설정 파일을 제품 변경의 경로 목록에서 한 줄로 받는다(아래 "제품 변경의 경로 목록"). 노트 조각은 `docs/release-notes/` 아래의 세 폴더 `features/`, `upgrade/`, `intro/`에 둔다(아래 "릴리스 노트"). 판 번호와 노트를 계산하는 도구와 노트 검사는 `tools/`에 두고 표준 라이브러리만 쓴다. 의존성을 설치하지 않은 CI 잡에서 `python3`로 돌기 때문이다(ci.yml의 ticket 잡이 커밋 검사를 그렇게 부른다. 코드를 읽었다).

거부한 안: Dockerfile을 앱마다 그 앱 폴더나 저장소 루트에 둔다. 제품 변경의 경로 목록이 파일마다 늘고, 배포 파일 묶음의 원본과 이미지를 짓는 파일이 흩어진다.

### 제품 변경의 경로 목록(명세가 정했다)

제품 변경은 `src/`, `web/`, `plugins/`, `uv.lock`, `deploy/` 가운데 하나라도 고친 커밋이다. ADR 0056이 든 범위를 이 다섯이 덮는다(web의 잠금 파일은 `web/` 안에 있다).

- `pyproject.toml`은 넣지 않는다. 저장소 루트의 그 파일은 하네스가 쓰는 설정(ruff, pyright, pytest, import-linter의 절)을 함께 담고(코드를 읽었다), 런타임의 의존성을 바꾸면 `uv.lock`이 함께 바뀐다. 진입점이나 빌드 설정만 바꾼 변경은 판을 내지 않는데, 그런 변경은 대개 `src/`의 변경과 함께 온다(어림).
- `web/` 안의 시험·스토리·사진 비교 파일도 제품 변경으로 센다. main은 출시 PR과 핫픽스에서만 움직이므로 시험만 바뀐 판이 나는 일은 드물고 그 판은 끝자리만 오른다. 반대로 빼는 목록을 두면 그 목록에 걸린 제품 파일의 변경이 판에서 빠지고, 그쪽이 더 나쁘다.
- 같은 까닭으로 `web/` 안의 도구(`web/tools/`)와 린트 설정(`web/eslint.config.mjs`)만 고친 변경도 제품 변경이다. 하네스의 일을 하는 파일이지만, 파이썬 쪽의 그런 파일은 `src/` 밖(루트의 `pyproject.toml`과 `tools/`)에 있어 경로로 떨어지고, web 쪽은 앱과 같은 폴더에 있어 떼려면 빼는 목록이 든다. `CONTEXT.md`의 "제품 변경"이 고친 파일이 놓인 자리로 가른다고 적은 것이 이 때문이다.
- 노트 조각(`docs/release-notes/`)은 배포 파일 묶음에 들지 않으므로 제품 변경이 아니다. 조각만 더한 PR은 판을 내지 않고, 그 조각은 다음 제품 판의 노트에 실린다.
- 크기의 감: 기준 커밋 `1117a170f`의 `origin/dev`에서 병합이 아닌 커밋 579개 가운데 `src`·`web`·`plugins`·`uv.lock`을 고친 것은 152개였다(`git rev-list --count --no-merges`에 경로를 붙여 손으로 봤다. `--full-history`를 붙여도 같았다).

거부한 안: `web/` 안에서 시험·도구·린트 설정 파일을 빼는 목록, `pyproject.toml`을 넣는 것(둘 다 위의 까닭).

### 판 설정 파일(명세가 정했다)

`deploy/release.toml`이다. TOML이고 칸은 선택 칸 `candidate_for` 하나다. 값은 `"X.Y.Z"` 꼴의 정식 판 번호(앞에 0이 없는 음 아닌 정수 셋)이고, 그 칸이 있는 동안 CI는 그 정식 판의 출시 후보만 낸다. 다른 칸이 있거나 값의 꼴이 틀리면 판 내기가 구성 오류로 멈춘다. release-image의 마지막 티켓이 판 내기 워크플로와 함께 `candidate_for = "0.1.0"`을 적은 이 파일을 만들고(아래 "티켓을 나눌 때 함께 둘 것"), pilot-release의 마지막 티켓이 그 줄을 지운다(ADR 0056 결정 "출시 후보와 정식 판"). 줄을 지운 뒤에도 파일은 남는다. 맨 앞자리를 올릴 때(1.0.0) 같은 칸에 그 번호를 적기 때문이다. `deploy/` 안이라 이 파일을 고친 커밋도 제품 변경이다.

### 번호(명세가 정했다)

판 태그는 `v<X.Y.Z>`와 `v<X.Y.Z>-rc.<n>`(n은 1 이상, 수는 모두 앞에 0이 없다) 꼴만 보고 다른 태그는 무시한다. 지난 판은 그 가운데 유의적 버전의 차례로 가장 큰 태그이고, 지난 정식 판은 `-rc.`가 없는 태그 가운데 가장 큰 것이다. 지난 판이 판을 내는 커밋의 조상이 아니면 구성 오류다.

1. 지난 판 뒤(지난 판이 없으면 저장소의 처음부터)에 제품 변경이 없으면 판을 내지 않고 성공으로 끝난다.
2. 판 설정 파일에 `candidate_for = "T"`가 있으면 다음 번호는 `T-rc.<k+1>`이다. k는 `vT-rc.<n>` 태그 가운데 가장 큰 n이고, 없으면 0이다. 커밋 접두는 번호에 쓰이지 않는다. T가 지난 정식 판보다 크지 않으면 구성 오류다. 계산한 `T-rc.<k+1>`이 지난 판보다 유의적 버전의 차례로 크지 않아도 구성 오류다. 지난 정식 판이 `v0.1.0`이고 지난 판이 `v0.2.0-rc.1`일 때 칸을 `0.1.1`로 바꾸면 `0.1.1-rc.1`은 앞의 검사를 지나지만, 다음 실행이 여전히 `v0.2.0-rc.1`을 지난 판으로 골라 이미 낸 변경의 범위가 엉키기 때문이다.
3. 그 칸이 없고 지난 판이 출시 후보 `vT-rc.<n>`이면 다음 번호는 `T`다.
4. 그 칸이 없고 지난 판이 정식 판 `vX.Y.Z`이면 그 뒤의 제품 변경 커밋들의 제목을 본다. 접두 뒤에 느낌표가 붙은 것이나 `feat`이 하나라도 있으면 `X.(Y+1).0`, 아니면 `X.Y.(Z+1)`이다. 맨 앞자리는 이 규칙으로 오르지 않는다.
5. 그 칸도 판 태그도 없으면 구성 오류다. 저장소에는 지금 태그가 하나도 없고(`git tag --list`가 아무것도 내지 않았다. 손으로 봤다), release-image의 마지막 티켓이 판 내기 워크플로와 판 설정 파일을 함께 들이므로 첫 판은 `0.1.0-rc.1`이다.
6. 계산한 git 태그가 이미 있으면 구성 오류다.

커밋은 병합 커밋을 빼고, 지난 판 태그에서 닿지 않으며 제품 경로를 고친 것을 고른다. 출시 PR과 되돌려 합치기 PR은 merge 커밋이라 빠지고(next-session `merge.md` "병합 방법"), squash로 병합된 티켓 PR과 핫픽스의 커밋이 남는다. 그래서 커밋 제목은 PR 제목에 ` (#번호)`가 붙은 것이다. 제목은 커밋 검사의 정규식 `PATTERN`(`tools/check_commit_msg.py`의 접두 여덟, 선택 범위, 선택 느낌표)만으로 읽고, 같은 검사의 길이 상한(72자)과 끝 마침표는 보지 않는다. squash 제목은 ` (#번호)`가 붙어 72자를 넘기도 하기 때문이다. 최근 squash 제목 400개가 모두 `PATTERN`을 지났고 99개가 72자를 넘었으며 그 가운데 `feat`이 37개였다(명세 검토 서브에이전트가 `git log --no-merges --format=%s -n 400 origin/dev`의 결과를 임시 스크립트로 셌다, 손으로 봤다. 이 명세를 고친 브랜치의 기준 `c21a4fc3b`에서 같은 스크립트로 다시 세면 98개와 37개이고, 기준 뒤의 유일한 커밋 `30dd4096f`에서 세면 99개와 37개라 그 수는 `30dd4096f`에서 난 것이다. 일지 2026-11-14-1748). 길이까지 보면 그 `feat`이 가운데 자리를 올리지 못한다. 꼴에 맞지 않는 제목(검사가 그대로 지나보내는 `Revert "…"` 등)은 `feat`도 느낌표도 아닌 변경으로 센다.

커밋을 고르는 길은 git의 도달 가능성과 커밋 하나하나의 변경만으로 정의했다. 첫 부모만 따라가는 길(`--first-parent`)은 틀린다. 지금의 main에서 dev를 main으로 올린 출시 병합(#542)의 첫 부모를 지난 판으로 두면 병합 커밋 하나만 나오고, 티켓의 squash 커밋은 둘째 부모 쪽에 있어 빠진다(`.scratch/release-image/probes/release_mechanics/README.md` 7번, 손으로 봤다). 경로로 거른 git 이력의 기본 단순화는 끝 상태가 같은 곁가지를 잘라 낼 수 있어(같은 README가 git 문서의 원문을 대 봤다) 쓰지 않는다. 그래서 바꾸고 되돌린 커밋 한 쌍만 있어도 둘 다 제품 경로를 고친 커밋이라 판이 난다. 지금 이력의 두 범위에서는 기본 단순화와 전체 이력이 고른 커밋 수가 같았다(42와 42, 7과 7. 같은 README 7번). 출시 병합, 되돌려 합치기, main의 핫픽스가 섞인 미래의 꼴은 재지 않았고 셋째 이음매의 사례가 잡는다. 정의가 도달 가능성과 커밋마다의 변경만 쓰므로 그 결과가 새 결정을 낳지 않는다고 본다(어림).

### 커밋 제목이 서는 자리(명세가 정했다)

번호와 노트는 main에 오른 커밋의 제목을 읽고, 노트 검사의 (가)는 PR 제목을 읽는다(아래 "노트 검사"). 둘이 어긋나지 않으려면 squash 커밋의 제목이 늘 PR 제목이어야 한다. 저장소 설정의 squash 커밋 제목은 지금 `COMMIT_OR_PR_TITLE`이고(같은 README 7번, 손으로 봤다), GitHub REST 문서는 그 값을 커밋이 하나면 그 커밋의 제목, 여럿이면 PR의 제목을 쓰는 것으로 적는다(원문을 받아 대 봤다, `https://docs.github.com/api/article?pathname=/en/rest/repos/repos`의 `squash_merge_commit_title`). 최근 병합된 PR 45개를 맞대 보니 커밋이 여럿인 42개는 squash 커밋의 제목이 모두 `<PR 제목> (#번호)`였다. 커밋이 하나인 PR은 하나였고 커밋 제목과 PR 제목이 같아 어느 쪽을 따랐는지 가르지 못했다. 남은 둘은 출시 PR과 되돌려 합치기 PR의 merge 커밋이다(`gh pr list --state merged --limit 45`의 결과와 `git log -1 --format=%s`를 세션 스크래치 스크립트로 맞대 손으로 봤다). 그래서 그 설정을 `PR_TITLE`로 바꾼다(아래 "사람 몫"). 바꾸지 않으면 커밋이 하나인 PR에서 PR 제목에만 느낌표를 붙였을 때 (가)는 초록인데 번호는 끝자리만 오른다.

거부한 안: 병합 절차가 `gh pr merge`에 squash 커밋의 제목을 직접 넘긴다. 따옴표가 든 인자는 워크트리 세션의 가드가 거부할 때가 있다(`CLAUDE.md` 환경 함정). 노트 검사가 커밋이 하나인 PR에서 커밋 제목과 PR 제목이 같은지 본다. 설정 하나로 없어지는 어긋남을 검사로 막는 것이고, 세션이 고칠 일만 는다.

### 이미지의 이름과 태그(명세가 정했다)

이미지 넷의 이름은 Docker Hub 이름공간 아래의 `serve`, `admin`, `widget`, `portal`이다. 계정이 이 제품 전용이라(ADR 0056 결정 "레지스트리와 계정") 이름에 제품 이름을 다시 붙이지 않는다. 태그는 git 태그에서 `v`를 뗀 판 번호(`0.1.0-rc.1`)와 커밋 해시 태그 `sha-<커밋 해시 40자>` 둘이다. 이미지에는 OCI 라벨 셋(`org.opencontainers.image.version`, `org.opencontainers.image.revision`, `org.opencontainers.image.source`)을 달아, 받은 이미지가 어느 판과 커밋인지 태그 없이도 읽히게 한다.

### 이미지의 구성(명세가 정했다)

크기는 `docker image inspect`의 풀린 크기다. 레지스트리에 올라가는 압축 크기는 재지 않았다.

**바탕.** `serve`는 공식 `python:3.12-slim-trixie`에 공식 `node:24-trixie-slim`의 `node` 실행 파일과 전역 npm 폴더를 복사하고 tini를 apt로 깐다. web 셋은 `node:24-trixie-slim`이다. 바탕은 digest로 고정한다. serve의 이 꼴은 382MB였고 짓는 데 19~21초가 들었다(`.scratch/release-image/probes/serve_image/README.md` 2번의 `deb-py`, 쟀다. 두 번 지었다). 두 바탕(Debian 13)의 고칠 수 있는 Critical은 0개였고(`release_mechanics` README 3번, 쟀다), 대조로 본 Debian 12의 파이썬 바탕은 Grype로 15개였다(같은 3번, 손으로 봤다). web 셋의 측정은 `node:24-bookworm-slim`(Debian 12)에서 했으므로(web_images README "잰 판") trixie에서 같게 서는지는 어림이고, 첫째 이음매의 시험이 실제 이미지로 본다. web 셋의 의존성 설치는 pnpm의 저장소와 메타데이터 캐시를 빌드 캐시 마운트로 빼 이미지에 남기지 않는다. 빼지 않으면 메타데이터 캐시 288MiB가 이미지에 남았다(web_images README 2절, 쟀다).

거부한 안: node 바탕에 uv로 CPython을 받는다(`deb-node`, 476MB, 짓는 데 47~70초. serve_image README 2번, 쟀다). 공식 파이썬 이미지를 두고 따로 받은 CPython을 쓰게 된다. alpine(311MB). serve와 예시 MCP 서버는 섰지만, Debian 두 후보에서 판을 넣은 줄이 busybox의 sed에서는 오류 없이 아무것도 바꾸지 않아 두 번 모두 `0.1.0`으로 지어졌고 빌드는 성공했다(같은 2번, 쟀다). musl이라 node 실행 파일을 Debian 계열 이미지에서 옮길 수도 없다(같은 2번, 손으로 봤다).

**사용자와 init.** 네 이미지는 uid·gid 10001의 `agentos` 사용자로 돈다. 이미지가 passwd 항목과 홈 폴더를 만든다. passwd 항목이 없는 uid로 띄우면 `serve`가 시작할 때 부르는 `getpass.getuser()`가 구성 오류 문구가 아니라 `KeyError: 'getpwuid(): uid not found'` 트레이스백으로 끝나기 때문이다(serve_image README 3번, 쟀다. 환경 변수 `USER`를 함께 주면 섰고 그 값이 채널 실행의 주체가 됐다). compose는 `user:`를 주지 않고, 배포 안내는 그것을 더하지 말라고 적는다. 네 이미지의 첫 프로세스는 tini다. tini를 둔 serve에서 `docker stop`이 uvicorn의 정상 종료 기록을 내고 0.73~3.53초 만에 종료 코드 143으로 끝났다. init 없이 agent-os가 pid 1이면 정상 종료는 했지만 다른 프로세스가 남긴 고아가 좀비로 남았다(같은 7번, 쟀다). init 없이 뜬 위젯 미리보기 페이지와 빌드 중인 위젯은 `docker stop -t 10`의 유예 10초를 다 쓰고 SIGKILL로 끝났고(137), init을 두면 1.6~2.3초에 143이었다. init 없는 위젯에는 빌드가 남긴 것으로 보이는 좀비가 일곱 회차 가운데 넷에서 남았고, init을 두면 없었다(web_images README 6절, 쟀다. 좀비가 어느 프로세스였는지는 어림). 바깥 이미지인 nginx는 compose의 `init: true`로 둔다. web 셋의 측정은 node 이미지의 uid 1000으로 했다. 넷이 같은 uid를 쓰는 것은 운영자가 키와 설정 파일의 소유를 한 번에 맞추게 하려는 것이다.

거부한 안: passwd 항목이 없을 때 `serve`가 구성 오류 문구로 끝나게 시작 검사를 고친다. 그 길은 운영자가 compose에 `user:`를 더할 때만 열리고 배포 안내가 그것을 막으며, 고쳐도 운영자가 할 일(`user:`를 지우거나 `USER`를 함께 주기)은 같다.

**판 번호.** 의존성을 먼저 잠금 검사와 함께(`uv sync --locked --no-install-project`) 깔고, 빌드 단계 안의 `pyproject.toml` 사본만 판 번호로 바꾼 뒤 프로젝트만 잠금을 보지 않고(`--frozen`) 깐다(serve_image README 1번의 `b1-frozen`, 쟀다. 두 실행에서 같았다). 의존성은 잠금 검사를 지나고 이미지 안의 판은 넣은 번호가 된다. 저장소 파일은 바꾸지 않는다. 판을 넣은 뒤에는 빌드 단계가 설치된 패키지의 판을 넘긴 번호와 대 보고, 다르면 빌드를 실패시킨다. 같은 판 넣기 줄이 alpine의 sed에서는 아무것도 바꾸지 않았는데도 빌드가 성공했기 때문이다(같은 README 2번, 쟀다).

거부한 안: 사본의 판 번호만 바꾸고 잠금 검사를 건다(`a1`). 실패했다. 잠금 파일의 판 줄까지 사본에서 고친다(`a3`). 지났지만 잠금 파일의 글자 모양에 기댄다. 동적 판(`c`). 저장소의 `pyproject.toml`과 `uv.lock`을 한 번 바꿔 커밋해야 한다(같은 1번).

이미지 안의 `agent-os --version`, 설치된 패키지의 판, 도는 serve의 `/openapi.json`의 `info.version`이 모두 `0.1.0-rc.1`이었다. 정규화된 꼴 `0.1.0rc1`은 설치 폴더 이름과 uv의 설치 줄에만 보였다(같은 1번, 쟀다. 두 실행에서 같았다). 그래서 이미지 안의 번호는 태그와 글자까지 같다. ADR 0056 결정 "저장소의 번호"의 "`0.1.0rc1` 꼴로 보일 것이다"는 거짓이 되어 이력을 쌓는다(서두 "이력").

**serve.** 쓰는 자리는 플러그인 루트 `/app/plugins`와 트레이스 폴더 `/data/traces` 둘이고, 그 밖의 루트는 읽기 전용(`read_only`)이다. 운영자 파일 `disabled.toml`은 같은 폴더에 임시 파일을 쓴 뒤 바꿔 끼우므로, 파일이 아니라 플러그인 루트 폴더 자체가 쓰기 가능해야 한다(serve_image README 5번, 코드를 읽었다). 예시 MCP 서버를 실행 파일 이름으로 띄우는 매니페스트(아래 "예시 MCP 서버")로 uid 10001, 네트워크 없음, 읽기 전용 루트에 두 자리만 이름 있는 볼륨으로 붙여 띄우자, 플러그인 끄고 켜기가 204였고 채널 실행이 MCP 연결을 지나 모델 호출에서 끝났으며(API 키를 주지 않았다) 서버 로그에 쓰기 오류가 없었다. 볼륨 없이 띄워 `docker diff`로 본 쓴 자리도 그 둘뿐이었고 `/tmp`와 홈에는 쓰지 않았다(같은 5번 (가)(나), 쟀다. 두 실행에서 같았다).

홈 폴더 `/home/agentos`에는 앱 사용자 소유의 tmpfs(`uid=10001,gid=10001,mode=0700`)를 준다. 운영자가 npx로 띄우는 MCP 서버(스토리 24)는 홈에 npm의 캐시와 기록을 쓰기 때문이다. 읽기 전용 루트에서 지금 매니페스트(`npx -y`)로 실행하자 서버 로그에 `npm error code ENOENT`가 찍히고 실행이 MCP 연결 실패(`tool_connection`)로 끝났고, 홈에 그 tmpfs를 주자 같은 실행이 모델 호출까지 갔다(같은 5번 (나), 쟀다. 네트워크가 있는 갈래다). `/tmp`는 읽기 전용 그대로였는데도 돌았으므로 쓰는 자리를 주지 않는다. node가 `/tmp`에 쓰려던 컴파일 캐시를 쓰지 못할 뿐이다(같은 5번 (가)(나)). tmpfs는 컨테이너를 다시 띄우면 비므로 npx는 다시 띄울 때마다 패키지를 다시 받는다(어림). 인터넷이 막힌 곳에서는 npx가 레지스트리에 묻다 실패하므로(아래 "예시 MCP 서버") 운영자가 npx로 띄우는 MCP 서버가 서지 않는다. 배포 안내가 그 한계를 적고, 그런 곳에서 운영자의 stdio MCP 서버를 들여오는 길은 deploy-package의 반입 절차가 정한다(Out of Scope).

**예시 MCP 서버(사용자가 골랐다).** 이미지는 `@modelcontextprotocol/server-everything`을 판을 고정해(지금 2.3.0) 전역에 깔고, 저장소의 예시 매니페스트 `plugins/mcp/everything/plugin.toml`은 `command = "mcp-server-everything"`, `args = []`로 바꾼다. 사용자가 세 안 가운데 이것을 골랐다(일지 2026-11-13-1843 "사용자에게 물은 것 넷"). ADR 0056 결정 "서버 이미지의 Node와 예시 MCP 서버"가 정한 "미리 설치한 것을 실행하도록 고친다"를 어디서 고칠지 정한 것이라 이력은 쌓지 않는다. 전역에 깔아 둬도 지금 매니페스트의 `npx -y`는 판을 적든 적지 않든 레지스트리에 물었고, 네트워크가 없으면 71.5~73.8초 뒤 이름 풀이 실패(`EAI_AGAIN`)로 끝났다. 실행 파일 이름으로 띄우면 네트워크 없이 0.34~1.18초에 답했다(serve_image README 4번, 쟀다. 두 실행에서 같았다). 실제 serve(네트워크 없음, 읽기 전용 루트, 실행 제한 30초)에서 지금 매니페스트의 `calc` 실행은 32.1초 뒤 실행 제한으로 끝났고, 바꾼 매니페스트는 0.64~1.16초 뒤 모델 호출에서 끝났다(같은 4번, 쟀다).

매니페스트를 바꾸면 calc를 실제 모델로 돌리는 모든 곳에 같은 실행 파일이 있어야 한다. 깔지 않은 곳에서는 실제 모델 시험이 MCP 연결에서 실패한다. 그래서 매니페스트를 고치는 티켓이 같은 변경에서 셋을 고친다. ci.yml의 `llm` 잡에는 setup-node 다음에 같은 판을 전역에 까는 단계를 더한다(그 잡의 `-m llm`과 `-m llm_widget` 단계가 모두 그 뒤에 돈다). `docs/constitution/operations.md`의 LLM 테스트 절에는 개발 PC에서 그 판을 전역에 까는 준비 한 줄을 더한다(손으로 치는 `-m llm_portal`도 개발 PC에서 돈다). 위젯과 위젯 미리보기 페이지의 Playwright 설정이 실제 모델 프로젝트의 제한 시간을 설명하며 그 MCP 서버를 "npx"로 적은 주석도 고친다(`web/apps/widget/playwright.config.ts`, `web/apps/portal/playwright.config.ts`. 코드를 읽었다). 모델을 부르지 않는 시험은 저마다 적은 매니페스트를 쓰므로 바뀌지 않는다(`tests/test_server.py`의 `EVERYTHING` 픽스처와 `tests/sdk/test_manifest.py`, `tests/adapters/test_filesystem.py`의 매니페스트 글, 코드를 읽었다). Windows 개발 PC에서는 mcp SDK가 명령 이름을 `shutil.which`로 찾고, 찾지 못하면 `.cmd`·`.bat`·`.exe`·`.ps1`을 붙여 다시 찾는다(이 저장소 `.venv`의 mcp `os/win32/utilities.py`의 `get_windows_executable_command`, 코드를 읽었다). 그래서 npm이 전역 폴더에 만든 `.cmd`가 `PATH`에 있으면 띄울 수 있다고 본다. 개발 PC에서 실제로 띄워 보지는 않았고, 그 티켓이 `-m llm`으로 본다.

거부한 안: npx를 두고 판만 적고(`npx -y 패키지@2.3.0`) 이미지는 serve의 작업 폴더에 그 판을 깐다. 개발 PC와 CI는 그대로지만, 네트워크 없이 뜨는 것은 serve가 그 작업 폴더에서 돌 때뿐이었다. 작업 폴더를 `/tmp`로 바꾸자 30초 안에 답하지 않았다(같은 4번, 쟀다). 이미지를 지을 때만 매니페스트의 명령을 바꿔 넣는다. 이미지 안의 예시 매니페스트가 저장소의 것과 달라져 관리 화면에 저장소와 다른 명령이 보이고, 저장소 쪽 명령에는 판이 적히지 않는다. 이 둘은 사용자가 고르지 않았다.

**플러그인 루트와 트레이스 폴더를 붙이는 것.** 단독 compose는 둘을 이름 있는 볼륨으로 붙인다. 빈 이름 있는 볼륨은 처음 붙일 때 한 번 이미지의 내용을 소유자째 복사했다. 이미지가 uid 10001 소유로 둔 플러그인 루트는 볼륨에서도 10001 소유였고 끄기가 204였다. 이미지의 플러그인 폴더를 root 소유로 바꾼 대조군은 볼륨도 root 소유가 되어 끄기가 500이었다(serve_image README 6번, 쟀다. 리눅스 엔진을 Docker-in-Docker로 흉내 냈다). 그래서 이미지는 플러그인 루트와 트레이스 폴더를 uid 10001 소유로 만든다. root 컨테이너가 먼저 붙여 파일을 쓴 볼륨은 그 뒤 경로가 10001 소유인 이미지로 붙여도 root 소유로 남아 10001이 쓰지 못했다(bridge_edge README 6절, 쟀다. 한 회차). 먼저 붙은 컨테이너의 이미지에 그 경로가 없었던 것과 볼륨에 이미 파일이 있었던 것 가운데 무엇이 갈랐는지는 가르지 않았다(같은 6절). 복원처럼 root 컨테이너로 볼륨에 먼저 쓰는 절차는 소유를 10001로 넘기는 단계를 함께 둬야 하고, 그 절차는 ops-backup-upgrade의 것이다(Out of Scope).

이미 채워진 볼륨은 판을 올려도 바뀌지 않았다. 다음 판을 흉내 낸 이미지의 새 파일과 바뀐 매니페스트가 볼륨에 실리지 않았고, 같은 이미지를 빈 볼륨에 붙이면 실렸다(serve_image README 6번, 쟀다). 그래서 새 판의 예시 플러그인이 바뀌어도 운영자의 볼륨에는 실리지 않는다. 새 판의 예시를 받는 길은 판 올림의 절차를 정하는 ops-backup-upgrade의 것이다(Out of Scope). 위의 예시 매니페스트 변경은 첫 판에 이미 들므로 그 길이 필요 없다(어림).

바인드 마운트는 복사하지 않았다. 빈 폴더를 붙이면 serve가 기본 모델 플러그인이 없다는 구성 오류로 시작에서 끝났다(같은 6번). 컨테이너의 uid가 쓰지 못하는 폴더를 붙이면 serve는 서고 `/health`도 200이었지만, 플러그인 끄기가 500이었고 실행도 트레이스 파일을 열지 못해 이벤트 하나 없이 500이었다. 폴더의 소유를 10001에게 넘기면 둘 다 됐다(같은 5번 (라), 쟀다). 상태 확인은 이 상태를 가르지 못한다. 없는 경로를 주면 Docker가 root 소유로 만들어 10001이 쓰지 못했다(bridge_edge README 6절, 쟀다). 그래서 배포 안내는 바인드 마운트를 쓰려는 운영자에게 이미지의 플러그인을 그 폴더로 먼저 옮기고 두 폴더의 소유를 `10001:10001`로 넘기라고 적는다. 그 명령은 배포 안내를 쓰는 티켓이 실제로 돌려 본다.

거부한 안: 단독 compose가 호스트 폴더를 바인드 마운트로 붙인다. 운영자가 파일을 바로 보는 편함은 있지만, 띄우기 전에 플러그인을 옮기고 소유를 넘기는 일을 빠뜨리면 상태 확인이 초록인 채 끄기와 실행이 500이다.

**관리 화면.** 운영 의존성과 이미지를 지을 때 만든 `.next`를 담고 시작 래퍼로 띄운다. 686.9MiB였고 uid 1000과 읽기 전용 루트로 섰으며, 컨테이너 시작에서 첫 200까지 2.05~2.70초였다(web_images README 2, 7절, 쟀다). 상류는 아래 "관리 화면의 상류"다.

거부한 안: Next의 `output: "standalone"`(290.6MiB). 시작 래퍼를 거치지 않고 시작 때 `next.config.ts`도 읽지 않아, 듣는 주소와 상류의 검사가 돌지 않았다. `HOSTNAME`을 주지 않으면 Docker가 넣은 컨테이너 ID로 컨테이너 주소에만 묶였다(같은 README 3, 4절, 쟀다).

**위젯.** 뜰 때 운영자의 사이트 파일로 빌드한 뒤 서비스를 시작한다(ADR 0056 결정 "위젯 이미지"). 이미지에는 워크스페이스 전체 의존성을 잠금 파일을 얼려 깔고, 이미지를 지을 때 `next typegen`으로 `next-env.d.ts`와 `.next/types`를 미리 만들며, 빌드가 쓰는 자리(`.next`, `public`)를 앱 사용자 소유로 둔다. 이 꼴은 874.3MiB였다(web_images README 2절, 쟀다). 미리 만든 `next-env.d.ts`가 없으면 root가 아닌 사용자의 빌드가 그 파일을 쓰려다 실패했다(같은 README 8절, 손으로 봤다). 이 이미지는 지을 때 정한 uid로만 뜬다. 다른 uid로 띄우면 `public` 아래에 폴더를 만들지 못해 멈췄다(같은 8절, 쟀다). 위젯의 루트는 읽기 전용으로 두지 않는다. 빌드가 앱 폴더 안에 쓰기 때문이다. 읽기 전용 루트에 `.next`와 `public`만 tmpfs로 주어도 섰지만(같은 README 7절, 한 번), 빌드 산출물이 컨테이너의 메모리에 들고 다시 띄울 때마다 처음부터 빌드한다(어림). 루트를 읽기 전용으로 두지 않아도 앱 사용자가 쓸 수 있는 자리는 이미지가 그 사용자 소유로 둔 곳뿐이다.

뜰 때의 빌드는 이 PC에서 기본 세 회차가 19.7~29.9초였고 컨테이너 시작에서 첫 200까지는 21.5~31.4초였다. 위젯의 모든 회차로 넓히면 첫 200까지 13.6~40.7초였다(같은 README 1절, 쟀다. 다른 측정이 함께 돌아 범위로만 읽는다). 빌드의 메모리 최고치는 같은 1절의 잰 회차에서 1,452~1,567MiB였다(표의 회차와 네트워크 없이 지은 세 회차. 그 절이 손으로 본 앞선 값은 1,454~1,527MiB). 읽기 전용 루트에 tmpfs를 준 한 회차는 1,591MiB였다(같은 README 7절. tmpfs에 쓴 산출물이 메모리에 든 것으로 그 README가 풀이한다, 어림). 스왑 없이 2GiB로 제한하면 섰고, 1GiB 이하로 제한하면 빌드 도중 OOM으로 죽었다(같은 1절, 제한마다 한 번). 그래서 단독 compose는 컨테이너에 메모리 제한을 두지 않고, 배포 안내는 위젯이 뜰 때 그만큼의 메모리를 쓴다고 적는다. 1GiB와 2GiB 사이의 문턱은 재지 않았고, 너무 낮은 제한은 위젯이 뜨지 못하게 한다.

네트워크가 없어도(`--network none`) 빌드하고 섰다(같은 1절, 쟀다). 그래서 인터넷이 막힌 곳에서도 위젯이 뜬다. 위젯과 관리 화면의 이미지에는 `NEXT_TELEMETRY_DISABLED=1`을 둔다. 주지 않으면 빌드 기록이 익명 사용 자료를 모은다는 안내를 찍었다(같은 1절).

이미지의 시작은 사이트 파일의 자리를 컨테이너 안의 정해진 경로로 늘 넘긴다. 사이트 파일의 환경 변수를 주지 않으면 위젯이 멈추지 않고, 어느 사이트에도 끼워 넣을 수 없는(`frame-ancestors 'none'`) 채로 조용히 떴기 때문이다(같은 README 10절, 쟀다). 그 경로에 파일이 없거나, 폴더이거나, 깨졌거나, 앱 사용자가 읽지 못하면 빌드 전에 1.7~2.6초 만에 까닭을 적은 진단과 함께 종료 1로 끝났다(같은 10절). 사이트 파일을 바꾸고 같은 컨테이너를 다시 띄우면 바뀐 파일로 다시 빌드했다(같은 README 11절, 한 번).

거부한 안: 운영 의존성만 깐다(664.0MiB). 빌드가 `@tailwindcss/vite`를 찾지 못해 실패했다(같은 README 2절, 손으로 봤다). 빌드가 import하는 개발 의존성만 남기고 시험 파일을 지운다(745.7MiB). 섰지만 잠금 파일을 얼리지 못하고(`--no-frozen-lockfile`), 시험 파일을 남기면 앱의 tsconfig가 시험 파일까지 담아 타입 검사가 실패하므로 이미지를 지을 때 저장소의 시험 파일을 지워야 한다(같은 2절). CI가 시험한 의존성과 이미지의 의존성이 같다는 보증을 128.6MiB와 바꾸지 않는다. 뜰 때의 빌드에서 타입 검사를 끈다. 빌드가 11.8~12.9초로 줄었지만 메모리 최고치는 같았고(같은 1절, 쟀다), 위젯의 `next.config.ts`를 고쳐야 하며, ADR 0056은 위젯 코드를 고치지 않기로 했다.

**위젯 미리보기 페이지.** 운영 의존성과 `apps/portal`, `packages/site-file`, `packages/ui`의 소스를 담고 node가 `.ts`를 빌드 없이 돈다. 351.0MiB였고 uid 1000, 네트워크 없음, 읽기 전용 루트, 읽기 전용 설정 볼륨으로 섰다(web_images README 2, 9절, 쟀다). 설정이 가리키는 개인 키 파일은 앱 사용자가 읽을 수 있어야 한다. root 소유 0600의 키는 `portal.private_key: 읽지 못한다`로 시작에서 끝났다(같은 9절).

**상태 확인.** 네 이미지 모두 compose의 상태 확인으로 컨테이너 안에서 자기 프로세스에 묻는다. web 셋의 이미지에는 curl과 wget이 없어 node의 `fetch`로 묻는다. 관리 화면은 `/`, 위젯은 `/widget`, 위젯 미리보기 페이지는 `/portal/health`이고, 셋 다 healthy가 됐으며 듣지 않는 포트에 건 대조는 unhealthy였다(web_images README 5절, 쟀다). 위젯은 빌드하는 동안 확인이 실패한 채 `starting`이었다가 선 뒤에 healthy가 됐다(같은 5절).

serve는 이미지에 든 python 한 줄로 묻는다. `urllib`로 `http://127.0.0.1:8000/health`를 4초 제한으로 열어 200이면 0, 아니면 1로 끝나는 명령이다. 정상인 serve에는 세 번 모두 0, 듣지 않는 포트에는 세 번 모두 1이었고 한 번에 576~768ms였다. 같은 명령을 compose의 상태 확인과 같은 뜻의 `docker run` 옵션으로 달자 띄운 뒤 12.2~12.5초에 healthy가 됐고, 듣지 않는 포트에 건 대조는 unhealthy였다(serve_image README 8번, 쟀다). 이미지에 든 node의 한 줄도 0.2초 남짓에 같은 판정을 냈지만(같은 8번), node는 예시 MCP 서버 때문에 든 것이라 serve 자신의 런타임인 파이썬으로 묻는다. 이미지의 사용자로 띄운 serve가 서기까지는 6.1~24.2초였다(같은 README 2, 3번, 쟀다. 다른 측정과 함께 돌아 부하에 따라 흔들렸다). 그래서 시작 유예 30초 안에 대개 서고, 유예가 끝난 뒤의 실패도 재시도가 남아 느린 시작 한 번으로 unhealthy가 되지 않는다(어림). 이 확인은 바인드 마운트의 쓰기 실패를 가르지 못한다(위 "플러그인 루트와 트레이스 폴더를 붙이는 것").

- web 셋의 확인 한 번은 123~934ms였고, 위젯 미리보기 페이지에서 한 번 14,784ms가 기록됐다(web_images README 5절, 까닭은 보지 못했다). 그래서 느린 확인 한 번으로 unhealthy가 되지 않게 재시도를 둔다.
- 위젯의 시작 유예(start period)는 잰 가장 긴 시작(40.7초)보다 넉넉히 둔다. 유예보다 빌드가 길면 빌드 중의 실패가 재시도에 세어 unhealthy가 된다(web_images README 5절, Docker의 정의에서 미룬 어림). 유예 동안에는 확인 간격을 짧게 하는 `start_interval`을 써서 선 때를 빨리 안다(Compose 2.20.2, Engine 25.0부터. `release_mechanics` README 6번, 원문을 받아 대 봤다).
- 첫 값은 간격 30초, 제한 시간 10초, 재시도 3, 시작 간격 2초, 시작 유예는 위젯 300초와 나머지 30초다(어림). 첫째 이음매의 시험이 이 값으로 선다.
- 프록시에는 상태 확인을 두지 않는다. 설정이 틀리면 nginx가 끝나고 재시작 정책이 다시 띄운다.

### 루프백 규칙의 예외(명세가 정했다)

설정은 둘이 함께 있을 때에만 켜진다. 하나는 이미지를 지을 때 root 소유로 굽는 표지 파일 `/etc/agent-os/image`이고, 다른 하나는 compose가 컨테이너에 주는 환경 변수 `AGENT_OS_CONTAINER_NETWORK=1`이다. 표지 파일이 "이미지 안에서만"을, 환경 변수가 "명시적"을 맡는다(ADR 0056 결정 "루프백 규칙의 예외"). 앱 사용자는 root가 아니므로 표지 파일을 만들 수 없고, 개발 PC에는 그 경로가 없다.

- 켜지면 받는 듣는 주소는 `0.0.0.0` 하나가 늘 뿐이다. 다른 IPv4 주소, `::`, 이름은 여전히 거부한다. compose 네트워크의 컨테이너 주소는 뜰 때마다 바뀌고, 프록시는 뒷단에 IPv4로만 걸기 때문이다(아래 "프록시 설정"의 IPv6).
- 환경 변수가 없거나 빈 값이면 꺼진 것이고, `1`이 아닌 다른 값(`true`, `0` 등)은 구성 오류다. 오타가 조용히 꺼짐으로 읽히지 않게 한다.
- 진단은 경우마다 다르다. 환경 변수는 있는데 표지 파일이 없으면 "이미지 밖에서는 켜지지 않는다"고 말하고, 표지 파일만 있고 환경 변수가 없는데 `0.0.0.0`을 받으면 지금의 루프백 진단에 그 환경 변수를 알리는 한 줄을 더한다.
- 네 프로세스가 같은 규칙을 따로 든다(ADR 0056 Consequences "다른 ADR"). `serve`의 `--host`, 관리 화면과 위젯 시작 래퍼의 `--hostname`, 위젯 미리보기 페이지 설정의 `portal.host`가 그 자리다. 판정은 표지 파일의 유무를 인자로 받는 순수 함수로 두어 시험이 두 경우를 모두 넣는다. 사례 표 하나를 파이썬과 TS 시험이 함께 읽어 네 곳이 같은 판정을 내는지 잠근다(선례는 사이트 파일의 규칙 사례를 파이썬과 위젯 빌드가 함께 읽는 `tests/fixtures/site_file/`).

예외가 켜졌을 때 `0.0.0.0`을 주는 자리는 지금의 시작 인자와 설정 그대로다. `serve`는 `--host`, 관리 화면과 위젯은 시작 래퍼의 `--hostname`, 위젯 미리보기 페이지는 설정 파일의 `portal.host`다. 환경 변수 `HOSTNAME`으로는 주지 않는다. 시작 래퍼는 `--hostname`이 없으면 `127.0.0.1`을 next에 늘 넘기고, `next start`는 `HOSTNAME`을 읽지 않으며, Docker는 그 변수에 컨테이너 ID를 넣는다. 그 변수를 읽는 것은 Next의 `output: "standalone"` 서버 틀뿐이다(`.scratch/release-image/probes/web_images/README.md` 3절. 이미지 안 next 16.3.6의 코드를 읽었고, 관리 화면 시작 래퍼에 준 인자가 `HOSTNAME`보다 앞서는 것을 쟀다). 위젯 미리보기 페이지는 `PORT`와 `HOSTNAME`을 줘도 설정 파일의 주소에 섰다(같은 3절, 쟀다). 그래서 배포 파일 묶음의 위젯 미리보기 페이지 설정 틀이 `host = "0.0.0.0"`을 적는다.

거부한 안: 환경 변수 하나만으로 켠다. 개발 PC에서 그 변수를 내보내면 루프백 밖에 묶인다. 표지 파일 하나만으로 켠다. 이미지를 `docker run`으로 띄운 운영자가 모르는 사이에 루프백 밖에 묶이고, 명시적이라는 요건을 채우지 못한다.

### 관리 화면의 상류(명세가 정했다)

관리 화면 이미지는 지을 때 상류를 `http://serve:8000`으로 넣는다. 상류는 빌드 산출물에 굳고, 시작할 때 준 `AGENT_OS_UPSTREAM`은 검사를 다시 돌릴 뿐 중계 대상을 바꾸지 않았다(web_images README 4절, 쟀다. 컨테이너 안에 가짜 상류 둘을 두고 시작 때 다른 값을 줘도 지을 때의 상류가 답했다). 그래서 예외는 상류에도 걸린다. 예외가 켜지면 상류의 호스트로 `127.0.0.1` 밖에 compose의 서비스 이름 `serve` 하나만 더 받는다. 이미지를 짓는 단계에도 표지 파일과 환경 변수를 두어 빌드 때의 검사를 지나게 하고, 시작 때 다시 도는 검사는 컨테이너의 표지 파일과 compose가 준 환경 변수로 지난다. 운영자는 상류를 바꾸지 못한다. 서비스 이름을 바꾸는 배치는 이미지를 다시 지어야 하고 0.1의 범위 밖이다. 측정용 예외를 넣어 지은 사본은 같은 네트워크의 별칭 `serve`로 관리 API의 요청을 넘겼고, SSE 이벤트 넷이 0.4초 간격으로 하나씩 왔다. 예외 없는 판은 같은 네트워크에서 500이었다(같은 4절, 쟀다). 빌드 때 `http://serve:8000`을 주면 예외 없는 판의 빌드가 종료 1로 실패했다(같은 4절).

상류 검사의 실패는 시작 기록에 `Ready` 줄이 먼저 찍힌 뒤에 난다(같은 4절). 그래서 시험과 배포 안내는 기록의 `Ready` 줄이 아니라 종료 코드와 상태 확인으로 떴는지 본다.

거부한 안: 시작할 때 빌드 산출물의 상류를 바꿔 쓴다. `routes-manifest.json`의 주소를 바꿔 다시 띄우면 다른 컨테이너로 넘겼지만(같은 4절) Next의 내부 파일에 기대는 길이고, 산출물에 쓸 수 있어야 해서 읽기 전용 루트와 함께 쓰지 못한다(같은 4절, 어림). 관리 화면도 위젯처럼 뜰 때 빌드한다. 상류 하나 때문에 뜨는 시간과 메모리를 치른다. 예외가 켜지면 상류의 호스트로 이름을 모두 받는다. 쓰는 값이 늘 `serve` 하나인데 받는 범위만 넓어진다.

### 발행하는 포트와 지원하는 최소 판(명세가 정했다)

단독 compose가 호스트에 발행하는 포트는 셋이다. 프록시의 443과 80은 호스트의 모든 IPv4 주소(`0.0.0.0`)에, 관리 화면의 3000은 `127.0.0.1`에만 발행한다. IPv6 쪽에는 아무것도 발행하지 않는다(아래 "프록시 설정"의 IPv6). serve, 위젯, 위젯 미리보기 페이지는 발행하지 않는다. 프록시는 컨테이너 안에서 8443과 8080을 듣고 443과 80을 그 둘로 발행한다. 시제품이 그 꼴로 읽기 전용 루트와 모든 권한(capability)을 뺀 채 섰고, 공식 nginx 이미지의 프로세스 18개가 모두 uid 101이었다(`.scratch/release-image/probes/bridge_edge/README.md` 5절, 쟀다). 같은 조건의 uid 101 소켓은 컨테이너 안의 80과 443에도 묶였지만(같은 5절. 컨테이너의 `net.ipv4.ip_unprivileged_port_start`가 0이었고, nginx로 묶어 보지는 않았다) 그 값에 기대지 않으려고 1024 위의 포트를 듣는다. 운영자는 SSH 포트 포워딩으로 서버의 `127.0.0.1:3000`에 닿는다.

컨테이너 안에서 듣는 포트는 지금의 기본값을 그대로 쓴다. serve는 8000, 관리 화면과 위젯은 3000이다(serve의 시작 인자 기본값과, 환경 변수 `PORT`가 없으면 3000을 쓰는 두 시작 래퍼를 코드에서 읽었다). 위젯 미리보기 페이지는 설정 파일의 `portal.port`가 빠지면 구성 오류이므로(코드를 읽었다) 배포 파일 묶음의 설정 틀이 3000을 적는다. ADR 0056이 짚은 대로 관리 화면과 위젯의 기본이 둘 다 3000이지만, 컨테이너마다 네트워크 이름공간이 따로라 겹치지 않고 프록시는 서비스 이름과 그 포트로 건다(아래 "프록시 설정"의 `upstream`).

지원하는 최소 판은 Docker Engine 28.3.3과 Docker Compose 2.20.2다.

- Engine. Docker 문서는 28.0.0보다 오래된 판에서 같은 L2 구간의 호스트가 localhost에 발행한 포트에 닿는다고 적는다. 릴리스 노트는 28.0.0이 이웃 호스트가 루프백 주소에 발행한 포트에 닿던 문제를, 28.3.3이 firewalld를 다시 읽은 뒤 루프백에만 발행한 포트가 로컬 네트워크에서 닿던 문제(CVE-2025-54388)를 고쳤다고 적는다(`release_mechanics` README 6번과 bridge_edge README 3절, 원문을 받아 대 봤다). 관리 화면을 `127.0.0.1`에만 둔 보호는 이 판부터 선다.
- 측정. Engine 27.5.1의 서버를 Docker-in-Docker로 흉내 내니, 같은 L2의 이웃이 서버를 경유지로 삼아 관리 화면 컨테이너의 주소로 바로 걸면 200이었다. filter FORWARD 정책이 ACCEPT일 때와 DROP일 때 모두 그랬다. 서버의 `127.0.0.1:3000`으로 보내도록 경로를 고친 이웃도 8회차 가운데 6에서 관리 화면에 닿았다. 28.0.0과 29.9.2는 userland-proxy를 켠 때와 끈 때, 두 FORWARD 정책 모두에서 두 길을 다 막았다. 보호를 끈 네트워크(`gateway_mode_ipv4=nat-unprotected`)의 컨테이너에는 같은 길로 닿았으므로(양성 대조) 막은 것은 엔진의 규칙이다(bridge_edge README 3절, 쟀다). 최소 판 28.3.3도 두 모드와 두 FORWARD 정책에서 두 길을 모두 막았고, 막은 규칙의 꼴은 29.9.2와 같았다(같은 README 9절, 쟀다). 28.0.0과 28.3.3 사이, 28.3.3과 29.9.2 사이의 판은 재지 않았다.
- Compose 2.20.2는 상태 확인의 `start_interval` 때문이다(`release_mechanics` README 6번, 원문을 받아 대 봤다). Engine 28.3.3은 그것이 요구하는 Engine 25.0을 덮는다.
- 배포 안내는 최소 판과 함께 Docker 문서의 두 문장을 경고로 옮긴다. `DOCKER_INSECURE_NO_IPTABLES_RAW=1`을 준 데몬에서는 `127.0.0.1`에 발행한 포트에 로컬 네트워크의 호스트가 닿을 수 있다는 28.0.2 릴리스 노트의 문장과, 28.0.0보다 오래된 판의 위 문장이다(bridge_edge README 3절). rootless 모드의 Docker와 firewalld·ufw를 쓰는 서버에서는 재지 않았다고도 적는다(같은 README "재지 못한 것").
- 최소 판 28.3.3에서 잰 것은 Docker-in-Docker로 흉내 낸 서버의 경유 공격(위 측정과 아래 "프록시 설정"의 IPv6)과 443·80을 IPv4에만 발행한 배치다(bridge_edge README 7, 8, 9절). 실제 이미지로 띄운 배치는 최소 판에서 돌려 보지 않았다. 첫째 이음매의 시험은 러너에 깔린 판에서 돈다(그 판은 보지 않았다).

### 프록시 설정(명세가 정했다)

프록시는 공식 `nginx` 이미지의 안정판 alpine(지금 1.30.6)을 digest로 고정해 쓴다. 우리가 짓지 않는 바깥 이미지라 compose가 권한을 좁힌다. `user: "101:101"`, 읽기 전용 루트, 모든 권한(capability) 빼기, `/tmp` tmpfs, `init: true`이고, 이 꼴로 섰으며 프로세스 18개가 모두 uid 101이었다(bridge_edge README 5절, 쟀다). `no-new-privileges`도 더한다. proxy_config의 측정과 bridge_edge 5절의 시제품이 그 옵션을 켠 채 섰다(`proxy_config/run.py`의 `HARDENED`, `proxy_config/README.md`의 측정 조건, `bridge_edge/compose.yml`의 proxy 서비스. 코드를 읽었다). 설정은 배포 파일 묶음에 드는 두 파일이다. 주 설정은 공식 이미지의 것을 바꿔 끼워 pid 파일과 임시 폴더를 `/tmp` 아래로 옮기고(공식 이미지의 기본 자리는 root만 쓴다), 사이트 설정이 아래를 담는다. 측정한 두 파일은 `.scratch/release-image/probes/proxy_config/nginx/`의 `nginx.conf`와 `proxy.conf`이고, 결정을 담은 부분을 그 `proxy.conf`에서 아래 조각으로 옮겼다.

```nginx
resolver 127.0.0.11 valid=5s ipv6=off;
upstream up_portal { zone up_portal 64k; server portal:3000 resolve; }  # serve, widget도 같은 꼴

map $uri $portal_token_key {
    "~^/portal/sites/[^/]+/token$" $binary_remote_addr;
    default "";
}
limit_req_zone $portal_token_key zone=portal_token:10m rate=30r/m;

server {                     # 8443(TLS). 8080은 return 308 https://$host$request_uri;
    add_header Strict-Transport-Security "max-age=31536000" always;
    client_max_body_size 1m;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
    limit_req_status 429;
    location /portal/ {
        limit_req zone=portal_token burst=10 nodelay;
        proxy_pass http://up_portal/portal/;
    }
    location / { return 404; }
}
```

- **포트와 TLS.** 8443은 TLS만 듣고(TLSv1.2와 1.3) 8080은 모든 요청을 같은 Host의 https 주소로 308로 넘긴다. 443에 TLS로 걸면 TLSv1.3이었고, 평문 HTTP는 nginx의 400이었으며 뒷단으로 넘기지 않았다. 80의 GET 넷과 POST 하나가 ACME 확인 경로까지 모두 308이었다(bridge_edge README 5절, 쟀다). 넘기는 주소는 `$host`로 지어, Host에 포트가 붙어 와도 `Location`에는 포트가 없었다(proxy_config README 4번, 쟀다). 그래서 https를 443이 아닌 호스트 포트로 발행하면 80의 넘김이 닿지 않는 443을 가리킨다. 배포 안내가 발행 포트를 고치지 말라고 적는 까닭에 이것도 든다.
- **HSTS.** `max-age=31536000`(1년)을 `always`로 붙인다. 200·404·429 응답에 모두 실렸다(bridge_edge README 5절, 쟀다). 익명 식별자 쿠키가 `__Secure-` 접두를 쓰지 않는 근거가 이 머리다(release-image 기능 계획 본문). `includeSubDomains`와 `preload`는 붙이지 않는다. 공개 출처 아래의 다른 호스트와 브라우저의 HSTS 사전 목록은 운영자의 도메인 운영에 닿는 일이라 제품이 정하지 않는다.
- **경로.** ADR 0024와 ADR 0050이 든 허용 목록만 넘긴다. `/end-user/`는 serve, `= /widget`과 `/widget/`은 위젯, `= /`와 `/portal/`은 위젯 미리보기 페이지로 가고, 나머지(`= /end-user`, `= /portal`, `/`)는 nginx가 404로 답한다. 모든 `proxy_pass`는 upstream 이름에 URI를 붙인 꼴이라 nginx가 정규화한 경로를 넘긴다(ADR 0024). 이 설정에서 넘기는 다섯 가지는 기대한 뒷단의 200이었고, `/health`, `/admin`, `/api/agents`, `/end-user`, `/portal`, `/plugins`, `/WIDGET`의 일곱은 HSTS가 붙은 nginx의 404였으며 어느 뒷단에도 닿지 않았다(proxy_config README 3번, 쟀다). 시제품은 우회 꼴(`/end-user/../runs`, `/end-user/%2e%2e/runs`, `/widget/../admin`)을 포함한 404 스무 가지와 넘기는 열 가지를 쟀다(bridge_edge README 5절, 쟀다).
- **넘기는 머리.** `X-Forwarded-For`는 접속 주소 하나로, `X-Forwarded-Proto`는 `https`로 덮어쓴다(ADR 0024). 클라이언트가 두 머리를 실어 보내도 뒷단은 클라이언트의 주소와 `https`를 받았다(proxy_config README 5번, 쟀다).
- **본문 상한.** `client_max_body_size 1m`이다. 1,048,576바이트는 200, 1,048,577바이트는 nginx의 413이었고, 상한 아래의 큰 본문은 tmpfs인 `/tmp`에 임시 파일로 쓰였다(proxy_config README 7번, 쟀다. 임시 파일은 손으로 봤다). ADR 0024는 이 값을 사이트 파일의 요청 크기보다 크게 두어 파이썬의 422가 답하게 하라고 적는다. 요청 글자 수의 기본 상한 20,000자는 한 글자가 JSON에서 6바이트가 되어도(제어 문자의 이스케이프) 120,000바이트라 그 안이다(HTTP 채널의 기본값을 코드에서 읽고 셈했다). 사이트 파일의 `request_chars`는 1 이상이기만 하면 되므로, 배포 안내는 그 값을 17만 자 남짓보다 크게 올리면 nginx의 413이 422보다 먼저 답할 수 있다고 적는다(셈이다).
- **SSE.** 프록시는 응답 버퍼링을 끄지 않는다. 뒷단이 `X-Accel-Buffering: no`를 붙이면 0.5초 간격의 이벤트 넷이 따로 닿았고, 붙이지 않은 대조는 넷이 1.51초에 한꺼번에 닿았다. 클라이언트가 받은 응답에는 그 머리가 없었다(proxy_config README 6번, 쟀다). 그래서 이벤트가 따로 흐르는 것은 뒷단이 붙이는 그 머리에 기댄다(ADR 0024는 FastAPI가 붙인다고 적는다). 실제 serve로 이벤트가 흐르는지는 첫째 이음매의 시험이 위젯에서 답을 받으며 본다.
- **키 파일.** 운영자는 인증서와 키를 정해진 폴더에 두고, 프록시가 그 폴더를 읽기 전용으로 붙인다. uid 101의 nginx는 `root:root 0600`인 키를 읽지 못해 종료 1로 끝났고, `root:101 0640`이면 TLSv1.3으로 떴다(proxy_config README 8번, 쟀다). `101:101 0600`도 지났다(bridge_edge README 5절, 쟀다). 배포 안내는 앞의 꼴(`chgrp 101`, `chmod 640`)을 적는다. root가 키를 쥔 채 그룹 읽기만 열기 때문이다. 스스로 서명한 인증서를 만드는 명령은 시제품이 쓴 openssl 한 줄(같은 5절)에서 시작하고, 배포 안내를 쓰는 티켓이 실제로 돌려 본다.
- **설정을 고칠 때.** 설정 파일은 폴더째 얹는다. 파일 하나로 얹으면 이름을 바꿔 끼우는 저장(`sed -i`와 많은 편집기의 저장)이 컨테이너에 보이지 않아 `nginx -s reload`로 먹지 않았고, `docker compose restart proxy`를 해야 먹었다. 폴더째 얹으면 세 저장 방법 모두 reload로 먹었다(bridge_recover README 8번, 쟀다). 깨진 설정에는 `nginx -t`와 reload가 모두 종료 1이었고 옛 설정이 계속 답했다(같은 8번, 쟀다). 그래서 배포 안내는 고친 뒤 `nginx -t`로 먼저 보고 reload하라고 적는다.

거부한 안: `nginxinc/nginx-unprivileged` 이미지. 같은 설정으로 섰고 프로세스가 모두 uid 101이었지만(bridge_edge README 5절, 쟀다), 공식 이미지에 compose의 `user:`를 주는 것으로 같은 꼴이 섰다. 받는 바깥 이미지의 게시자를 하나로 둔다. root로 띄우고 권한 하나(`CHOWN`)를 더한다. root에서 모든 권한을 빼면 임시 폴더의 `chown`이 실패했고 `CHOWN`을 더해야 섰다(같은 5절, 쟀다). uid 101로 띄우면 그 권한이 필요 없다.

**토큰 끝점의 빈도 제한.** 열쇠는 위의 `map`이 nginx가 정규화한 경로(`$uri`)로 가른다. 토큰 끝점이면 접속 주소, 아니면 빈 값이고, 빈 열쇠의 요청은 세지 않는다(nginx limit_req 모듈 문서, 원문을 받아 대 봤다). 수치는 접속 주소마다 분당 30번에 `burst=10 nodelay`이고, 넘으면 429다.

- 한 클라이언트가 토큰 끝점에 12번 연달아 보내면 11번 200, 12번째 429였고, 오류 기록에 그 구역의 거부 줄이 남았다. 바로 뒤의 다른 경로는 제한 밖이라 200이었다. 확인 경로로 15번 보낸 뒤에도 토큰 끝점은 11번을 받아, 빈 열쇠의 요청이 그 클라이언트의 몫을 먹지 않았다(proxy_config README 2번, 쟀다). 같은 L2의 이웃 둘은 같은 때에 보내도 저마다 11번을 받아 주소마다 따로 셌다(bridge_edge README 2절, 쟀다).
- 토큰 경로를 달리 적은 열 가지 가운데 `%6D`, `//`, `x/../`와 그 겹침은 제한에 들었고 뒷단은 정규화한 경로를 받았다. 끝의 `/`, 대문자 `TOKEN`, `%2F`, `;x`의 넷은 제한 밖이었지만 위젯 미리보기 페이지가 토큰을 내지 않는 경로다. 열 가지 모두 제한을 가른 경로와 뒷단이 받은 경로가 같았다(proxy_config README 1번, 쟀다. 위젯 미리보기 페이지가 경로를 글자 그대로 견주는 것은 bridge_edge README 2절이 코드를 읽었다).
- 수치의 바탕. 위젯은 요청을 보낼 때마다 토큰을 새로 받으므로 사람 하나가 10초마다 질문하면 분당 6번쯤이고(bridge_edge README 2절, 코드를 읽고 셈한 어림), 분당 30번은 그 다섯 배다. `nodelay`가 없으면 한꺼번에 온 요청이 0~3초씩 늦춰졌으므로(같은 2절, 쟀다) `nodelay`를 둔다.
- 거부 코드는 `limit_req_status 429`를 적어야 429이고, 적지 않으면 503이었다. 429 응답에는 `Retry-After`가 없었다(같은 2절, 쟀다).
- 한계. 회사망이나 통신사의 NAT 뒤에 있는 여러 사람은 한 주소로 보여 한 통을 같이 쓴다(어림, bridge_edge README "재지 못한 것"). 이 한도는 서명 요청의 폭주를 막는 장치이고, 실행의 비용은 serve의 주체별·사이트별 상한이 막는다(ADR 0050 결정 "빈도 제한"). reload 뒤의 제한 상태와 쉰 뒤 다시 채워지는 정확한 시각은 재지 않았다(proxy_config README "재지 못한 것").

거부한 안: 토큰 끝점을 정규식 `location`으로 떼고 원문을 넘긴다. 시제품이 그 꼴이었다. 위젯 미리보기 페이지가 경로를 글자 그대로 견주므로 지금은 다른 경로로 새지 않지만(bridge_edge README 2절, 코드를 읽었다), 정규식 `location`의 `proxy_pass`에는 URI를 붙일 수 없어(nginx proxy 모듈 문서, 원문을 받아 대 봤다) 세 변형을 뒷단이 원문 그대로 받았다(같은 2절, 쟀다). ADR 0024의 규칙에 예외를 하나 두게 된다. 분당 10번. 사람 하나의 어림(분당 6번)에 너무 가깝다.

**IPv6(사용자가 골랐다. 이 명세를 쓰며 물었다, 일지 2026-11-13-1843 "사용자에게 물은 것 다섯").** 단독 compose는 프록시의 443과 80을 서버의 IPv4 주소에만 발행하고(`"0.0.0.0:443:8443"`, `"0.0.0.0:80:8080"`), 안쪽 네트워크에는 IPv6를 켜지 않는다. IPv6로만 접속하는 방문자는 닿지 못한다. ADR 0056 결정 "밖으로 여는 포트"의 "호스트의 모든 주소에 발행하는" 문장이 바뀌므로 이력을 쌓았다(서두 "이력"의 다섯째).

- 까닭. 호스트 주소를 적지 않고 발행하면(Docker의 기본) 안쪽 네트워크가 IPv4뿐일 때 IPv6로 온 손님은 docker-proxy를 거쳐 모두 안쪽 게이트웨이 주소 하나로 보였고, userland-proxy를 끄면 닿지 못했다(bridge_edge README 1절, 쟀다. 엔진 27.5.1·28.0.0·29.9.2). 그렇게 뭉친 이웃 둘이 같은 때에 보내면 위 빈도 제한이 둘을 한 통에서 셌다(같은 README 2절, 쟀다. 29.9.2). IPv6 방문자 전체가 접속 주소 하나의 한도를 나눠 쓰게 된다.
- IPv4에만 발행한 배치. 서버 안에서 IPv6 쪽 443·80에는 듣는 소켓도, IPv6 주소에 묶인 docker-proxy도, ip6tables의 DNAT 규칙도 없었다. 이웃이 서버의 IPv6 `:443`·`:80`으로 건 요청과 서버 자신이 `[::1]:443`·자기 바깥 IPv6 주소로 건 요청은 refused였고, 같은 배치에서 서버 호스트의 IPv6 대조 포트에는 모두 닿았다. IPv4 이웃 둘은 저마다의 주소로 보였고, 서버 자신이 `127.0.0.1:443`으로 건 요청은 안쪽 게이트웨이로 보였다. Engine 28.3.3과 29.9.2, userland-proxy를 켠 때와 끈 때가 모두 같았다(같은 README 8절, 쟀다). 이 배치에서 빈도 제한과 TLS·경로를 다시 재지는 않았다. 시제품 배치와 견주어 바뀐 것은 IPv6 갈래뿐이고 IPv4 갈래의 값은 같았으므로(같은 8절) 위의 빈도 제한과 "포트와 TLS", "경로"의 측정이 그대로 선다고 본다(어림). 첫째 이음매의 시험이 이 발행으로 띄워 429와 TLS와 404를 본다.
- 설정으로 옮기면. 프록시의 `listen`도 IPv4만 둔다. 잰 설정(`proxy_config/nginx/proxy.conf`)에서 `listen [::]:8443 ssl`과 `listen [::]:8080` 두 줄을 뺀다. 안쪽 네트워크가 IPv4뿐이라 그 소켓에 오는 연결이 없고, 커널에 IPv6가 없는 서버에서 nginx가 `[::]`에 묶지 못해 시작에서 끝나는 길을 남기지 않으려는 것이다. nginx가 끝나는 것은 어림이다. 공식 이미지의 시작 스크립트 `/docker-entrypoint.d/10-listen-on-ipv6-by-default.sh`가 `/proc/net/if_inet6`이 없으면 "ipv6 not available"을 적고 기본 설정에 `listen [::]`을 더하지 않는 것을, 고정한 1.30.6 alpine 이미지에서 꺼내 읽었다. 뒷단의 이름은 위 `resolver`의 `ipv6=off`로 A 레코드만 푼다. 두 줄을 뺀 설정은 재지 않았고, 첫째 이음매의 시험이 그 설정으로 띄운다.
- 배포 안내에 넘기는 것. 공개 출처의 도메인에는 IPv4 주소(A 레코드)만 등록하라고 적는다. 이름에 IPv6 주소(AAAA 레코드)가 있을 때 브라우저가 IPv6의 refused 뒤 IPv4로 넘어가는지는 재지 않았다(같은 README "재지 못한 것").
- 한계. IPv6만 주는 통신망도 보통 IPv4 사이트로 이어 주는 변환 장치(NAT64 등)를 두므로 그 가입자는 IPv4로 닿는다고 본다(어림). 그런 장치 뒤의 여러 사람은 한 IPv4 주소로 보여 한 통을 같이 쓴다(위 빈도 제한의 한계와 같다, 어림).

거부한 안: 안쪽 네트워크에 IPv6를 켜고 443과 80을 두 주소 체계 모두에 발행한다. 사용자에게 보인 선택지 가운데 고르지 않은 것이다. IPv6 손님도 저마다의 주소로 보였고(bridge_edge README 1절, 쟀다. 29.9.2), 같은 L2의 이웃이 서버를 경유해 컨테이너의 IPv6 주소로 거는 길도 28.0.0, 28.3.3, 29.9.2가 막았다(같은 README 7절, 쟀다). 그러나 Docker 27.0.1 릴리스 노트는 ip6tables가 돌지 않는 호스트에서는 엔진이 떠도 IPv6를 켠 네트워크를 만들 수 없다고 적는다(`release_mechanics` README 6번, 원문을 받아 대 봤다). 그런 서버에서는 첫 `docker compose up`이 네트워크를 만들지 못한다고 본다(재지 않았다). 또 IPv6 가입자는 주소를 묶음으로 받으므로 주소를 바꿔 가며 주소별 한도를 비켜 갈 수 있다(어림. Docker Hub도 로그인하지 않은 받기를 IPv6 /64마다 센다, 아래 "배포 안내"). Docker의 기본대로 호스트 주소를 적지 않고 발행하고 안쪽 네트워크는 IPv4만 둔다. IPv6 손님이 모두 게이트웨이 주소 하나로 보여 한도를 함께 썼다(같은 README 1, 2절, 쟀다). 이 안은 선택지에 넣지 않았다.

### 프록시가 뒷단을 다시 찾는 길(명세가 정했다)

프록시 설정은 뒷단마다 공유 메모리 영역(`zone`)을 둔 `upstream` 묶음을 두고, 그 안의 `server`에 `resolve`를 붙여 Docker 내장 DNS(`127.0.0.11`)에서 이름을 다시 푼다(`resolver 127.0.0.11 valid=5s ipv6=off`). 리눅스 Docker Engine 29.9.2를 Docker-in-Docker로 흉내 낸 서버에서 세 변형을 견준 가운데 (다)다(`.scratch/release-image/probes/bridge_recover/README.md`, 쟀다. 칸마다 두 번이다).

- 고정 주소(가)는 뒷단의 주소가 바뀌면 그 뒷단에 다시 닿지 않았다. 다시 만들기, 같은 컨테이너의 다시 시작, 판 올림, 뒷단 넷을 함께 다시 만들기가 모두 그랬고, 같은 컨테이너를 다시 시작해도 주소가 바뀌었다. `nginx -s reload`나 프록시를 다시 시작해야 돌아왔다(같은 README 1번). 옛 주소를 같은 포트로 듣는 다른 컨테이너가 받으면 그 컨테이너가 200으로 답했다. 판 올림 한 번으로 같은 포트(3000)의 두 뒷단이 서로의 옛 주소를 받아, 한 경로를 다른 서비스가 20초 내내 답한 회차도 있었다(같은 3번). 상태 코드가 200이라 응답 코드만 보는 감시로는 드러나지 않는다. 뒷단 하나라도 이름이 풀리지 않으면 nginx가 `host not found in upstream`으로 끝나기를 되풀이해 멀쩡한 경로까지 사이트 전체가 내려갔고, 운영자가 멈춰 둔 뒷단이 있는 채 데몬이 다시 켜지면 사람 손 없이 그렇게 됐다(같은 0, 5, 6번).
- (다)는 같은 조작 모두에서 사람 손 없이 다시 만든 뒷단에 닿았다. 다만 다시 만든 경로의 첫 요청은 열 칸에서 모두 옛 주소로 걸려 클라이언트 제한(8초)까지 매달렸고(상태 499), 8.9~10.3초부터 새 컨테이너가 답했다. 예외는 판 올림 한 번의 위젯 경로 하나다(같은 1번). 다시 푸는 때에 따라서는 주소 없이 곧바로 502를 몇 초 냈다(판 올림에서 6.3초까지, 같은 1w, 3b번). 처음 띄울 때와 서버를 껐다 켠 뒤에도 함께 뜬 뒷단이 등록되기 전에 이름을 풀면 다음 다시 풀기까지 502였다(같은 4, 7번. 길게는 10.4초). 멈춘 뒷단 하나는 그 경로만 502이고 나머지는 닿았다(같은 5, 6번).
- 명세가 고른 설정 전체(nginx 1.30.6)에서도 다시 만든 뒷단에 reload 없이 닿았다. 한 회차는 첫 요청이 옛 주소로 가 클라이언트 제한(3초)까지 매달린 뒤 3.5초 뒤의 둘째 요청이 새 주소에 닿았고, 다른 회차는 첫 요청부터 새 주소였다(proxy_config README 9번, 쟀다). 옛 주소로 간 요청이 클라이언트가 끊지 않으면 얼마나 매달리는지는 재지 않았다(같은 README "재지 못한 것").
- 변수로 이름을 푸는 (나)도 다시 닿았고, 작업 프로세스 16개에서는 첫 요청부터 닿았다. 작업 프로세스를 하나로 두면 `valid` 안에서 옛 주소로 걸어 (다)와 같은 창을 드러냈다(bridge_recover README 1, 1w번). 그런데 `proxy_pass`에 변수를 쓰면 지시어에 적은 URI가 요청의 URI를 그대로 바꿔 넣는다(nginx proxy 모듈 문서의 `proxy_pass` 절, 원문을 받아 대 봤다). 그래서 정규화한 경로를 넘기라는 ADR 0024의 규칙("넘기는 URI는 nginx가 정규화한 것이다")을 지키려면 경로를 손으로 다시 짜야 한다. (다)는 `proxy_pass`에 URI를 붙인 보통의 꼴을 그대로 쓴다.
- `valid`를 빼면 내장 DNS가 준 TTL이 600초였고, 다시 만든 지 25초가 지나도 일부 요청이 옛 주소로 갔다(같은 README 3c, 쟀다). 그래서 `valid=5s`를 둔다.
- 서버나 Docker를 다시 켠 뒤에는 재시작 정책 `unless-stopped`만으로 다섯이 돌아왔다(데몬만 다시 켬, 서버의 정상 재시작, 전원 끊김. 같은 README 4번). 정책이 없으면 아무것도 돌아오지 않았다(대조, 5번). `always`는 운영자가 `docker compose stop`으로 멈춘 컨테이너까지 다시 띄웠다(5번). 그래서 다섯 컨테이너의 정책은 `unless-stopped`이다.
- `depends_on`은 두지 않는다. (다)는 뒷단 이름이 풀리지 않아도 뜨고(같은 README 0, 6번) 뒷단이 뜨면 다시 풀어 닿는다. `depends_on: service_healthy`를 걸면 처음 `up`할 때 가장 늦은 뒷단이 건강해질 때까지 프록시가 뜨지 않아, 20초 늦게 포트를 연 뒷단을 기다리는 24.7~30.8초 동안 사이트 전체가 연결 거부였다. 데몬이 다시 켜질 때는 차례를 정하지도 않았다(같은 7번). 실제 위젯은 뜰 때의 빌드로 13.6~40.7초가 걸린다(위 "이미지의 구성").
- `server`의 `resolve`는 오픈 소스 nginx 1.27.3부터 있다(`release_mechanics` README 6번, nginx의 CHANGES와 모듈 문서의 원문을 받아 대 봤다). 세 변형은 1.31.6(메인라인)에서, 고른 설정 전체(proxy_config)와 시제품(bridge_edge 5절)은 1.30.6(안정판)에서 쟀고, 두 판 모두 다시 만든 뒷단에 reload 없이 닿았다. 단독 compose는 공식 이미지의 안정판을 digest로 고정한다. 판을 바꿀 때 동작이 덜 바뀌는 쪽이다(어림).
- 배포 안내는 컨테이너 하나를 다시 만들거나 판을 올린 직후 약 10초 동안 그 뒷단으로 가는 요청이 매달리거나 502일 수 있다고 적는다.

거부한 안: 고정 주소에 `depends_on`과 상태 확인을 더한다. 처음 뜰 때의 차례만 맞출 뿐 다시 만든 뒷단(1번)과 멈춘 뒷단(5, 6번)을 풀지 못하고, 처음 뜰 때 사이트 전체를 막는다(7번). 고정 주소에 `depends_on`의 `restart: true`를 건다. compose가 프록시를 다시 시작해 닿은 것은 서비스를 고르지 않은 `up -d`와 `docker compose restart <뒷단>`뿐이었고, 서비스를 고른 `up -d`, 지운 뒤의 `up -d`, compose 밖의 다시 시작, 정책의 다시 띄우기에서는 닿지 않았다(같은 2번). 변수로 이름을 푼다(위의 까닭).

### 배포 파일 묶음(명세가 정했다)

릴리스에 첨부하는 압축 파일 하나이고 이름은 `agent-os-<판 번호>.tar.gz`(`v` 없음)다. 풀면 같은 이름의 폴더 하나가 나오고, 그 안에 `deploy/standalone/`의 파일이 판 번호와 이미지 이름공간을 채운 채 든다. 판 번호는 환경 변수 틀의 한 줄이고 compose 파일은 그 값으로 이미지 넷의 태그를 고른다. 끝자리만 오른 판은 그 한 줄만 바꾸면 된다는 약속(ADR 0056 결정 "번호")이 운영자의 손에서 한 줄 고치기가 되게 하려는 것이다. 든 것은 compose 파일, 프록시 설정, 환경 변수 틀, 사이트 파일과 위젯 미리보기 페이지 설정의 틀, 배포 안내다.

운영자가 채우는 자리와 그것이 컨테이너에 붙는 꼴은 아래다.

- 프록시 설정은 폴더째 프록시에 읽기 전용으로 얹는다. 파일 하나로 얹으면 서버에서 고친 파일이 reload로 먹지 않았다(위 "프록시 설정"의 설정을 고칠 때).
- 인증서와 키는 폴더 하나에 두고 프록시에 읽기 전용으로 얹는다. 키는 `root:101 0640`이다(같은 절의 키 파일).
- 사이트 파일은 폴더 하나에 두고, 그것을 읽는 세 컨테이너(serve, 위젯, 위젯 미리보기 페이지)에 읽기 전용으로 얹는다. 위젯 미리보기 페이지 설정과 그 개인 키는 다른 폴더 하나에 두고 위젯 미리보기 페이지 컨테이너에만 읽기 전용으로 얹는다. 개인 키를 읽는 것은 위젯 미리보기 페이지뿐이고(`web/apps/portal/server/config.ts`의 `private_key`), serve는 사이트 파일의 공개 키만 읽으며(`src/agent_os/main.py`의 `public_keys`), 위젯은 뜰 때마다 의존성의 코드로 빌드를 돈다(위 "이미지의 구성"의 위젯. 셋 다 코드를 읽었다). 두 폴더 모두 앱 사용자(uid·gid 10001)가 읽을 수 있어야 한다. root 소유 0600의 개인 키로는 위젯 미리보기 페이지가 시작에서 끝났다(web_images README 9절, 쟀다. 그 측정의 앱 사용자는 uid 1000이었다). 배포 안내는 키를 쥔 주인은 root로 두고 그룹 10001에 읽기만 여는 꼴을 적고, 그 명령은 배포 안내를 쓰는 티켓이 실제로 돌려 본다.
- 플러그인 루트와 트레이스 폴더는 묶음에 들지 않고, compose가 만드는 이름 있는 볼륨 둘이다(위 "이미지의 구성"의 "플러그인 루트와 트레이스 폴더를 붙이는 것"). 백업과 복원이 지킬 자리가 이 둘이다(ops-backup-upgrade).
- 환경 변수 틀에는 판 번호와 이미지 이름공간, 관리 토큰과 그것과 다른 채널 토큰, 기본 모델의 이름, 모델 제공사의 API 키가 든다. 비밀 값이 들므로 배포 안내는 그 파일을 운영자만 읽게 두라고 적는다. 그 파일의 값을 컨테이너에 넘기는 것은 serve 하나다. 관리 토큰, 채널 토큰, 기본 모델의 이름, API 키는 serve만 읽고(`src/agent_os/main.py`와 모델 플러그인), web 셋의 앱 코드는 이 이름들을 읽지 않는다(`web/apps`에서 그 이름을 grep하면 관리 화면의 토큰 입력 부품 둘이 화면에 보이는 안내 글에 쓰고, 그 부품을 그리는 페이지 시험 둘이 그 안내 글을 단언하고, e2e 스택 셋이 시험 준비에 쓸 뿐 값을 읽는 앱 코드는 없다. 코드를 읽었다). 판 번호와 이미지 이름공간은 compose 파일이 이미지 태그를 고를 때만 쓴다. 루프백 예외의 환경 변수는 compose 파일이 서비스마다 직접 준다. 운영자가 끄거나 바꿀 값이 아니기 때문이다.

### 배포 안내(명세가 정했다)

배포 파일 묶음에 드는 한국어 문서 하나다. 적는 것은 아래다.

- 보증하는 환경(리눅스 x86-64의 Docker Engine과 Docker Compose, 위 "발행하는 포트와 지원하는 최소 판")과 0.1 판의 범위 밖(Podman, RHEL 계열 전용 바탕 이미지, ARM 서버).
- 공개 출처를 둘 도메인의 요건. 등록 도메인 아래 모든 호스트(형제 도메인 포함)를 같은 운영자가 믿을 수 있게 쥐어야 한다(release-image 기능 계획 본문이 ADR 0050의 요건을 풀어 적은 문장). 제품은 도메인을 검사하지 않는다.
- 채울 것과 그 자리. 인증서와 키 파일, 사이트 파일, 위젯 미리보기 페이지 설정과 그 개인 키, 환경 변수 파일(관리 토큰, 그것과 다른 채널 토큰, 기본 모델의 이름, 모델 제공사의 API 키), 플러그인 폴더.
- 시험 삼아 띄울 때 스스로 서명한 인증서를 만드는 명령. 인증서 갱신은 운영자 몫이다.
- 띄우기와 확인(`docker compose up -d`, 컨테이너 상태 확인), 관리 화면에 닿는 SSH 포트 포워딩 명령.
- compose 파일의 발행 포트를 고치지 말라는 경고와 그 까닭(`serve`나 관리 화면을 호스트의 모든 주소에 발행하면 암호화 없이 열린다. ADR 0056 Consequences "잃는 것").
- 사이트 파일을 고친 뒤의 절차(`serve`, 위젯 미리보기 페이지, 위젯 세 컨테이너를 다시 띄우고, 위젯이 다시 뜨는 동안 위젯은 응답하지 않는다. ADR 0056 결정 "사이트 파일을 고치면").
- 인터넷이 막힌 곳의 반입 명령(인터넷이 되는 PC에서 받아 `docker save`로 파일로 저장하고, 옮겨서 `docker load`로 불러온 뒤 해시를 대조한다). 그 명령을 실제로 돌려 본 기록은 배포 안내를 쓰는 티켓이 남긴다(ADR 0056 결정 "인터넷이 막힌 곳").
- 판을 바꿀 때 먼저 그 판의 노트에서 "올릴 때 할 일"을 본다는 한 줄. 판 올림의 절차 전체는 ops-backup-upgrade의 것이다.
- 서버의 메모리. 위젯은 뜰 때마다 빌드하며 1.6GiB 가까이 쓴다(위 "이미지의 구성"의 위젯).
- 위 절들이 배포 안내에 넘긴 것. compose에 `user:`를 더하지 말라는 경고("이미지의 구성"의 사용자와 init). 인터넷이 막힌 곳에서는 운영자가 npx로 띄우는 MCP 서버가 서지 않는다는 것(같은 절의 serve). 플러그인 루트와 트레이스 폴더를 바인드 마운트로 바꾸려는 운영자가 칠 명령(같은 절의 "플러그인 루트와 트레이스 폴더를 붙이는 것"). 키 파일의 소유와 권한, 설정을 고친 뒤 `nginx -t`로 보고 reload하는 차례, `request_chars`를 크게 올리면 413이 먼저 답할 수 있다는 것("프록시 설정"). 컨테이너 하나를 다시 만들거나 판을 올린 직후 약 10초("프록시가 뒷단을 다시 찾는 길"). 공개 출처의 도메인에는 IPv4 주소(A 레코드)만 등록하라는 것과 IPv6로만 접속하는 방문자는 닿지 못한다는 것, 그리고 443과 80의 발행에서 `0.0.0.0`을 지우면 Docker의 기본 설정(userland-proxy를 켬)에서 IPv6 방문자가 주소 하나로 뭉쳐 토큰 끝점의 한도를 함께 쓴다는 것("프록시 설정"의 IPv6).
- Docker Hub에서 받는 횟수 제한. 문서의 문장(로그인하지 않으면 6시간에 IPv4 주소나 IPv6 /64마다 100회, 무료 개인 계정은 6시간에 200회, GET만 세고 HEAD는 세지 않는다)을 옮기고 그 문서의 주소를 함께 적는다. 같은 IPv4 주소 뒤의 여러 서버가 로그인하지 않은 몫을 함께 쓴다는 것도 적는다. 문서에 그 문장은 없고, 표의 칸("100 per IPv4 address or IPv6 /64 subnet")에서 읽은 것이다(어림). 같은 때 가격 페이지는 개인 계정을 시간당 100회로 적었고, 로그인하지 않고 물은 실제 응답의 머리는 1시간 창의 100회(`ratelimit-limit: 100;w=3600`)였다(`release_mechanics` README 4번. 문서와 가격 페이지는 원문을 받아 대 봤고, 응답 머리는 손으로 봤다). 세 자리가 서로 맞지 않으므로 수치는 Docker가 바꿀 수 있다고 적는다.

### 판 내기 워크플로(명세가 정했다)

판 내기는 새 워크플로 하나이고 main의 푸시에서 돈다. 동시 실행 묶음 하나로 한 번에 하나만 돌고, 기다리는 실행은 가장 나중 것만 남는다(GitHub의 기본 동작, `release_mechanics` README 1번의 동시 실행 줄, 원문을 받아 대 봤다). 남은 실행이 지난 판 태그 뒤의 제품 변경을 다시 보므로, 취소된 실행의 변경도 그 판에 실린다.

잡은 둘이다. 둘로 나누는 까닭은 아래 "실패한 판을 다시 돌리는 길"이다.

1. **짓고 시험하고 올린다.** 번호와 노트를 계산하고(지난 판 태그에 공개 릴리스가 없으면 실패하고, 제품 변경이 없으면 여기서 성공으로 끝난다. 아래 "초안과 git 태그"), 이미지 넷을 지어 러너에 싣고, 첫째 이음매의 시험을 돌리고, 점검하고, 커밋 해시 태그로만 올린다. 출력은 판 번호와 이미지 넷의 digest다. 둘째 잡이 릴리스에 올릴 파일(배포 파일 묶음, 이미지마다의 소프트웨어 목록과 점검 결과, 노트의 글)은 판 번호와 digest를 적은 파일과 함께 그 실행의 아티팩트로 올린다.
2. **번호를 붙이고 공개한다.** 같은 실행에서 첫째 잡의 아티팩트를 받아 첫째 잡의 출력과 맞대 보고, 아래 사전 확인을 지나면 초안 릴리스를 그 커밋의 전체 해시로 만들고, 그 번호의 git 태그가 원격에 생기지 않았는지 본 뒤(둘 다 아래 "초안과 git 태그") 자산을 올리고, 번호 태그를 아래의 지키는 차례로 붙이고, 초안을 공개한다. 번호 태그를 붙이는 단계 앞에서 실패하면 초안을 지우고, 그 단계부터 뒤에서 실패하면 초안을 남긴다. 다만 사전 확인이 앞 실행이 남긴 이 커밋의 초안을 지우고 새로 만든 실행은 번호 태그를 붙이는 단계 앞에서 실패해도 새 초안을 지우지 않고 남긴다. 앞 실행이 번호 태그를 일부 붙였을 수 있어, 지우면 그 판을 끝낼 초안이 없어지기 때문이다. 남긴 초안은 그 번호의 판을 끝내는 길이다(아래 "실패한 판을 다시 돌리는 길").

둘째 잡의 사전 확인은 그 번호로 이미 있는 것을 본다. 공개 릴리스가 있으면, 그 태그가 이 커밋을 가리킬 때는 더 할 일 없이 성공으로 끝나고 다른 커밋을 가리키면 실패한다. 공개 릴리스 없이 git 태그만 있으면 실패한다. 초안이 남아 있으면, 이 커밋의 초안은 지우고 새로 만든다. 취소나 제한 시간 때문에 지우는 단계가 돌지 못했거나, 번호 태그 뒤에 실패해 남긴 초안이다. 다른 커밋의 초안이면 실패한다. 앞 실행이 번호 태그를 붙인 뒤 끝내지 못한 판이라, 지우면 그 판을 끝낼 길이 없어진다.

아티팩트는 보존 기간을 다시 돌리기의 기한(처음 실행 뒤 30일)보다 짧게 두지 않고, 첫째 잡이 다시 돌면 같은 이름을 덮어쓴다. 둘째 잡만 다시 돌아도 실행 번호(`github.run_id`)가 그대로이고 아티팩트 받기의 기본값이 지금 실행이므로, 다시 돈 둘째 잡은 첫 회차가 올린 것을 받는다고 본다(`release_mechanics` README 8번. 문서는 원문을 받아 대 봤고, 다시 돈 잡이 실제로 받는지는 어림이다).

번호 태그를 공개보다 먼저 붙인다. 공개 뒤에 태그 붙이기가 실패하면 이미지 없는 공개 릴리스와 git 태그가 남는다. 거꾸로면 레지스트리의 번호 태그와 초안만 남고, 같은 실행을 다시 돌릴 때 지키는 차례가 같은 digest를 보고 지나간다. 이 차례는 GitHub에 릴리스를 실제로 만들어 보지 않고 원문과 gh의 소스로 세운 것이다(`release_mechanics` README 1번, 어림). 초안이 git 태그를 만들지 않고 공개할 때 만든다는 것도 원문에서 직접 찾지 못했다(같은 1번). 그래서 첫 판 내기를 지켜보는 세션이 초안 단계에서 태그가 없었는지 실행 기록에서 본다(Testing Decisions의 넷째).

**초안과 git 태그(사용자가 골랐다. 첫째 잡의 공개 릴리스 확인과 그 실패의 절차는 명세가 채웠다. 티켓을 쓰며 물었다, 일지 2026-11-14-1748 "사용자에게 물은 것 둘").** 사용자가 고른 선택지의 설명에 든 것은 아래 첫째 항목(초안 직후의 태그 대조와 정리 단계의 태그 지우기)과 셋째 항목(받은 아티팩트의 대조)이다. 위의 두 어림(초안이 git 태그를 만들지 않는다, 다시 돈 둘째 잡이 첫 회차의 아티팩트를 받는다)이 틀려도 판이 조용히 빠지지 않게 대조 셋을 둔다. 명세 검토가 짚은 길은 이렇다(같은 일지 "명세 검토"의 B1). 초안이 태그를 만든다면, 번호 태그 앞에서 실패해 초안만 지운 판이 git 태그를 남긴다. 다음 실행의 번호 도구는 그 태그를 지난 판으로 골라 그 뒤의 변경만 보고, 그 사이에 제품 변경이 없으면 판을 내지 않고 성공으로 끝난다. 스토리 33이 아무 경고 없이 깨진다.

- 둘째 잡은 초안을 만든 직후 그 번호의 git 태그가 원격에 있는지 본다. 있으면 번호 태그를 붙이기 전에 실패하고, 정리 단계가 초안과 함께 그 태그를 지운다. 이 대조로 실패한 실행은 위의 "새 초안을 남기는" 예외에 들어도 초안을 지운다. 초안이 태그를 만든다면 앞 실행도 번호 태그 앞에서 같은 대조로 멈췄으므로 끝낼 판이 남아 있지 않다.
- 첫째 잡은 번호 도구가 지난 판으로 고른 태그에 공개 릴리스가 있는지 GitHub에 묻고, 없으면 실패한다. 번호 도구는 판 번호와 함께 지난 판으로 고른 태그를 내고, 판 태그가 하나도 없는 첫 판에서는 고른 태그가 없어 이 확인을 건너뛴다. 제품 변경이 없어 성공으로 끝나는 갈래보다 먼저 본다. 취소나 제한 시간 때문에 정리 단계가 돌지 못해 태그가 남은 경우를 잡는다. 그 실패의 절차는 아래 "실패한 판을 다시 돌리는 길"이다.
- 둘째 잡은 첫째 잡의 아티팩트를 받은 직후, 받은 파일이 다 있고 그 안에 적힌 판 번호와 digest가 첫째 잡의 출력과 같은지 본다. 받지 못했거나 다르면 사전 확인과 초안 만들기 전에 실패한다.

어림이 맞으면 세 대조는 늘 지나고 차례는 위와 같다. 틀리면 첫 판 내기가 번호 태그 앞에서 실패로 드러나고, 초안과 태그는 지워져 레지스트리의 커밋 해시 태그만 남는다(어림. 이 길은 돌려 보지 않았다). 그때는 판 내기의 차례를 다시 정해야 하므로 ADR 0056 결정 "판 내기의 차례와 실패"로 돌아간다. 이 대조들은 그 결정이 지킬 것으로 든 "실패한 판 내기가 그 판의 git 태그와 공개된 릴리스를 남기지 않는다"를 어림에 기대지 않고 지키는 장치라 이력을 쌓지 않는다.

거부한 안: 버릴 공개 저장소를 하나 만들어 두 어림을 티켓 전에 잰다. 어림이 사실로 바뀌지만, 바깥에 저장소를 만들고 지우는 일이 들고 티켓 발행이 그만큼 늦는다. 사용자에게 보인 선택지 가운데 고르지 않은 것이다.

번호 태그를 지키는 차례(쟀다, 같은 README 2번, 로컬 레지스트리 19회차): 번호 태그를 조회해 없으면 해시 태그를 그대로 복사해 붙이고(`docker buildx imagetools create`. 원본이 증명이 붙은 이미지 색인이면 기본값으로 digest가 같았다), 같은 digest면 그대로 두고, 다른 digest면 거부하고, 조회가 실패하면 붙이지 않는다. "없다"는 조회 출력의 마지막 줄이 `: not found`로 끝날 때뿐이다. 종료 코드는 없음과 실패가 모두 1이라 가르지 못했다. Docker Hub는 없는 저장소를 `pull access denied`로 답하므로 해시 태그를 올려 저장소가 생긴 뒤에 조회한다(같은 2번, 손으로 봤다). 레지스트리 자체는 덮어쓰기를 막지 않았다(양성 대조).

이미지는 한 번 러너에 실어(증명 없음) 시험한 뒤, 같은 빌더가 캐시로 다시 지어 증명과 함께 올린다. 실은 이미지의 Id가 올린 이미지의 플랫폼 매니페스트 config digest와 같았다(같은 README 5번, 쟀다). 다만 그 측정은 이 PC의 옛 이미지 저장 방식(overlay2)에서 났고 GitHub 러너의 저장 방식은 보지 못했다(같은 README의 "도구의 판"과 5번). containerd 저장 방식에서는 Id가 config digest가 아닐 수 있다(어림). 그래서 워크플로는 이미지마다 저장 방식에 기대지 않는 대조로 시험한 이미지와 올린 이미지가 같은지 단언하고, 다르면 첫째 잡이 실패한다(번호 태그와 릴리스 앞이다). 견주는 값은 설정과 레이어를 함께 가리켜야 한다(두 빌드가 낸 config digest 같은 것). OCI 이미지 명세는 config의 `rootfs`가 레이어의 내용 주소(`diff_ids`)를 가리켜 config의 해시가 파일 시스템의 해시에 기댄다고 적고, Dockerfile의 `ENV`는 파일 시스템을 바꾸지 않아 레이어에 대응하지 않는 이력 항목이 된다고 적는다(`https://github.com/opencontainers/image-spec/blob/main/config.md`, 원문을 받아 대 봤다). 그래서 레이어의 diff_id 목록만 견주는 대조는 `ENV` 같은 설정만 다른 두 이미지를 같다고 읽으므로 받지 않는다(PR 봇이 짚었다, 일지 2026-11-14-1748). 그 값을 무엇으로 얻을지는 워크플로를 짓는 티켓이 러너에서 정한다. 증명을 켠 채 러너에 실으면 빌드가 실패했다(같은 5번). 빌드 캐시는 GitHub Actions 캐시에 이미지마다 다른 범위로 둔다. 범위를 같게 두면 마지막 이미지의 캐시만 남는다(같은 5번, 원문을 받아 대 봤다). 쓰는 액션은 커밋 해시로 고정한다(ADR 0027). 명세를 쓸 때의 판과 커밋은 같은 README 5번에 있고, 워크플로를 짓는 티켓이 그때의 최신으로 다시 고른다.

판 내기에 걸리는 시간은 재지 않았다(ADR 0056 Consequences "명세가 리눅스에서 재거나 정하는 것"이 넘긴 것). 워크플로 전체는 release-image의 출시 PR이 병합될 때 처음으로 끝까지 돌기 때문이다. 그보다 먼저, 이미지 넷을 짓고 첫째 이음매의 시험을 돌리는 몫은 티켓들이 이 PC의 Docker로 돌린 시간이 일지에 남고, ci.yml의 새 잡이 그 잡을 더한 티켓 뒤의 첫 출시 PR에서 처음 돌아 그 잡의 기록에도 시간이 남는다(Testing Decisions의 첫째). 점검과 올리기와 릴리스는 첫 판 내기에서 처음 돈다. 두 잡의 제한 시간은 워크플로를 짓는 티켓이 어림으로 시작하고(ci.yml 머리 주석의 규약), 첫 판 내기를 지켜보는 세션이 걸린 시간을 일지에 적는다(Testing Decisions의 넷째). 걸린 시간에 기대는 결정은 없다고 본다. 병합한 세션은 판 내기의 실행이 끝날 때까지 보고(아래 "병합 절차와 규약 문서"), 둘째 잡만 다시 돌리는 길은 첫째 잡의 시간을 다시 치르지 않는다(아래 "실패한 판을 다시 돌리는 길").

**권한과 비밀 값(사용자가 골랐다. 담는 자리는 명세가 정했다).** 릴리스와 태그를 만드는 단계는 워크플로의 기본 토큰(`GITHUB_TOKEN`)이 아니라 세분 토큰(fine-grained PAT)을 쓴다. GitHub REST 문서는 릴리스를 만들고 고치는 끝점에서, `target_commitish`의 커밋이 기본 브랜치에 견주어 `.github/workflows/` 아래 파일을 더하거나 고쳤으면 워크플로를 고칠 권한이 있는 토큰을 요구하고 기본 토큰은 그 권한을 받을 수 없다고 적는다(`release_mechanics` README 1번, 원문을 받아 대 봤다). 이 저장소의 기본 브랜치는 dev이고 판은 main에서 내므로, ADR 0056이 정한 회복 길인 워크플로의 핫픽스는 기본 토큰으로 판을 내지 못한다(어림. 무엇과 견주는지는 문서에 없고 돌려 보지 않았다). 사용자가 세 길 가운데 이것을 골랐다(일지 2026-11-13-1843 "사용자에게 물은 것 셋").

- 세분 토큰은 이 저장소 하나에 코드(Contents)와 워크플로(Workflows)의 읽기·쓰기를 주고, 다른 권한은 고르지 않는다.
- 두 비밀 값(Docker Hub 접근 토큰, 세분 토큰)은 저장소의 비밀 값이 아니라 배포 브랜치를 `main` 하나로 좁힌 GitHub 환경(environment)의 비밀 값으로 두고, 판 내기의 두 잡만 그 환경을 쓴다. 환경의 비밀 값은 그 환경을 쓰는 잡만 읽고, 배포 브랜치를 고르면 이름이 맞는 브랜치만 그 환경을 쓴다(GitHub 문서 `deployments-and-environments`, 원문을 받아 대 봤다. 공개 저장소는 모든 요금제에서 쓸 수 있고, 이 저장소는 공개다. `gh repo view`로 손으로 봤다). ADR 0056의 "그 값은 판 내기 잡만 읽는다"를 지키는 장치다. 다른 브랜치의 PR이 워크플로를 고쳐 비밀 값을 읽으려 해도 그 잡은 환경을 쓰지 못한다.
- 단계마다 그 단계가 쓰는 비밀 값만 넘긴다. 세분 토큰은 둘째 잡의 릴리스 단계(초안 만들기, 자산 올리기, 공개, 실패할 때 초안과 그 번호의 git 태그 지우기)만 받는다. 워크플로의 기본 토큰은 읽기 권한(`contents: read`)만 둔다. 그래서 위 "초안과 git 태그"의 정리 단계가 태그를 지우는 것도 세분 토큰으로 한다.
- 첫째 잡은 시험과 점검을 마친 뒤에 Docker Hub에 로그인한다. 로그인은 러너에 자격 파일을 남기는데, 시험은 의존성의 코드를 러너에서 돌리기 때문이다(어림).
- 세분 토큰이 만든 태그와 릴리스는 기본 토큰의 것과 달리 다른 워크플로를 일으킬 수 있다. 문서는 기본 토큰이 일으킨 이벤트가 새 실행을 만들지 않는다고만 적고(같은 README 1번의 이벤트 줄, 원문을 받아 대 봤다), 세분 토큰 쪽은 그 문장의 반대로 읽은 것이다(같은 1번의 기본 브랜치 함정 줄, 어림). 지금 태그나 릴리스의 이벤트로 도는 워크플로는 없다(`.github/workflows/`의 두 파일, 코드를 읽었다). ADR 0056 Consequences "CI와 비밀 값"의 "기본 토큰으로 만든 태그와 릴리스는 다른 워크플로를 일으키지 않으므로" 문장이 바뀌어 이력을 쌓는다(서두 "이력").
- 세분 토큰의 만료는 사람이 고른다. 만료 없음도 고를 수 있지만 1년 동안 쓰지 않은 토큰은 GitHub가 지운다(GitHub 문서 `managing-your-personal-access-tokens`, 원문을 받아 대 봤다). 만료나 삭제로 둘째 잡이 인증에 실패하면 원인이 저장소 밖이므로, 갱신한 뒤 실패한 잡을 다시 돌린다(아래 "실패한 판을 다시 돌리는 길").

거부한 안: 기본 토큰을 지키고 워크플로의 버그를 출시 PR로 고친다. 워크플로 수정이 dev에 쌓인 다른 변경과 함께 나가야 하고, 문서 풀이에 따라서는 dev의 워크플로가 main보다 앞선 동안 다른 핫픽스의 판도 실패할 수 있다. 임시 저장소에서 기본 토큰이 실패하는 경우를 먼저 잰다. 재더라도 워크플로 핫픽스의 실패는 남을 가능성이 크다(이 둘은 사용자가 고르지 않았다). GitHub App의 설치 토큰을 쓴다. 짧게 사는 토큰이지만 사람이 앱을 만들고 설치하고 개인 키를 비밀 값으로 넣는 일이 세분 토큰 하나보다 크다.

### 릴리스 노트(사용자가 골랐다. 파일의 자리와 모양과 차례는 명세가 정했다)

사용자는 운영자용 요약 단락을 CI의 모델이 아니라 기능의 마지막 티켓을 맡은 세션이 저장소의 파일로 쓰게 골랐다(일지 2026-11-13-1843 "사용자에게 물은 것 둘"). 판 내기는 그 파일을 글자 그대로 옮기고 모델을 부르지 않는다. 이 선택은 ADR 0056 결정 "판마다 나오는 것"의 "릴리스 노트는 … 묶은 것이고 사람이 쓰는 글이 없다"를 바꾸므로 ADR 0056에 이력을 쌓는다(이 명세의 서두 "이력"). 노트가 제목의 묶음만이 아니게 되는 것이고, 판을 낼 때 글을 새로 쓰는 사람이 없다는 뜻은 그대로다.

노트 조각은 셋이다.

- **기능 단락** `docs/release-notes/features/<기능 slug>.md`. 제품 변경을 담은 기능의 마지막 티켓을 맡은 세션이 그 티켓 PR에 싣는다. 운영자에게 무엇이 달라지는지를 운영자가 만지는 것(설정 칸, 화면, 명령)의 이름으로 쓴 한 단락이고, 파일 경로·ADR 번호·티켓 이름을 싣지 않으며 올릴 때 할 일을 쓰지 않는다. 모양은 아래 "노트 검사"의 (다)다.
- **올릴 때 할 일** `docs/release-notes/upgrade/<이름>.md`. 제목 접두에 느낌표를 붙인 PR이 그 PR에 싣는다. 운영자가 올릴 때 무엇을 무엇으로 바꾸는지 구체적으로 쓴다. 이름은 검사하지 않지만 그 PR이 새로 더한 파일이어야 한다(같은 이름이 이미 있으면 고친 것이 되어 (가)를 채우지 못한다).
- **소개 글** `docs/release-notes/intro/<X.Y.Z>.md`. 그 정식 판과 그 출시 후보들의 노트 맨 위에 싣는다. `intro/0.1.0.md`는 release-image의 마지막 티켓이 기능 단락과 함께 쓴다. 첫 판이 0.1.0의 출시 후보이고, 그 노트에도 소개 글의 자리를 둔다는 결정(ADR 0056 결정 "판마다 나오는 것")이 그 판부터 채워지게 하려는 것이다. 정식 판을 내기 전에 pilot-release가 고칠 수 있다.

노트의 차례는 아래다. 빈 묶음은 머리째 뺀다.

1. 고칠 수 있는 심각한 취약점의 경고(아래 "취약점 점검").
2. 소개 글. 판이 `X.Y.Z`나 `X.Y.Z-rc.<n>`이고 판을 내는 커밋에 `intro/X.Y.Z.md`가 있으면 싣는다.
3. 기능 단락. 노트가 싣는 범위(출시 후보는 지난 판 뒤, 정식 판은 지난 정식 판 뒤) 안에서 더해진 `features/` 파일을 더해진 커밋의 차례로, 판을 내는 커밋에 있는 글 그대로 싣는다. 범위 밖에서 더해진 조각은 그 뒤에 고쳐졌어도 다시 싣지 않는다.
4. "올릴 때 할 일". 범위 안의 제품 변경 가운데 느낌표가 붙은 커밋의 제목을 하나씩 적고, 그 커밋이 더한 `upgrade/` 파일의 글을 그 아래에 둔다.
5. "새 기능". 느낌표 없는 `feat` 커밋의 제목.
6. "고친 것". 느낌표 없는 `fix` 커밋의 제목.
7. "그 밖의 변경". 나머지 여섯 접두와 꼴에 맞지 않는 제목. ADR 0056이 명세에 넘긴 "`feat`도 `fix`도 아닌 접두의 변경을 노트의 어느 묶음에 싣는지"의 답이다.

커밋 하나는 한 묶음에만 선다. 제목은 접두와 범위와 느낌표를 떼고 끝의 ` (#번호)`는 남긴다. 기능 단락이 쓰는 것은 끝난 기능뿐이라, 기능의 티켓 일부가 먼저 판에 실리면 그 판에는 제목만 서고 단락은 기능이 끝난 뒤의 판에 선다. 핫픽스는 기능 단락을 쓰지 않는다. 운영자가 손댈 것이 있으면 다른 PR처럼 느낌표와 `upgrade/` 조각으로 싣는다.

기능 계획이 명세에 넘긴 물음 가운데 CI 댓글 안에 딸린 것(실린 커밋을 기능으로 묶는 길, 끝나지 않은 기능의 티켓, 출시 PR이 열린 동안 더해진 커밋, 경고와 단락을 가르는 꼴, 잡이 쓴 댓글을 알아보는 표지, 병합 전에 단락이 달렸는지 보는 단계)은 사용자의 선택으로 물을 자리가 없어졌다. 조각은 기능 폴더 이름으로 묶이고, 끝나지 않은 기능은 조각이 없으며, 빠뜨림은 병합 전의 검사가 막는다. 제품 변경이 없는 기능의 단락은 아래 (나)가 막는다.

거부한 안: `feat!` 커밋을 "올릴 때 할 일"과 "새 기능"에 함께 싣는다. 같은 줄이 두 번 서고, 운영자에게 중요한 쪽은 앞의 것이다. 기능 단락 앞에 기능 이름을 머리로 단다. 운영자는 기능 slug를 모르고, 단락이 스스로 무엇에 관한 것인지 말한다.

### 노트 검사(명세가 정했다)

새 도구 하나가 pre-commit과 CI의 ticket 잡에서 돌고, PR 제목만 고쳤을 때는 아래의 작은 워크플로에서 (가)만 돈다. pre-commit은 스테이지된 변경을, CI는 PR의 변경 전체(base에서 머리까지)를 본다. 훅은 각자 설치해야 하므로 CI가 최종 판정이다(ci.yml 머리 주석). 머리가 main이나 dev인 PR(출시 PR, 되돌려 합치기 PR)은 건너뛴다. 그 PR에는 티켓들이 더한 조각이 한꺼번에 실리기 때문이다.

- **(가) 느낌표와 할 일.** 커밋 검사의 정규식 `PATTERN`에 맞지 않는 PR 제목은 빨강이다. 그 제목이 squash 커밋의 제목이 되어 번호를 정하기 때문이다. 위 "번호"와 같은 기준으로 읽으므로 길이 상한과 끝 마침표는 보지 않는다. 길이는 번호를 바꾸지 않고, ` (#번호)`를 뗀 최근 PR 제목 400개 가운데 72자를 넘는 것이 4개 있었다(같은 서브에이전트가 셌다, 손으로 봤다). 커밋 검사가 꼴을 보지 않고 지나보내는 제목(그 검사의 `PASS_PREFIXES`, `Revert "…"` 등)은 받고, 위 "번호"처럼 느낌표가 없는 제목으로 읽는다. 제목 접두에 느낌표가 있으면 그 PR이 `upgrade/` 파일을 하나 이상 새로 더하고 제품 경로를 하나 이상 고쳐야 한다. 느낌표가 없는데 `upgrade/` 파일을 새로 더했으면 빨강이다(있던 파일을 고치는 것은 된다). PR 제목이 필요하므로 CI에서만 본다. 제목은 ticket 잡에 환경 변수로 넘긴다. 워크플로 식에 PR 제목을 바로 넣으면 명령 주입이 되기 때문이다(zizmor의 template-injection).
- **(나) 기능 단락의 빠뜨림.** 변경이 기능 계획 `.scratch/<slug>/plan.md`에 `**끝:**` 줄을 더하거나 `features/<slug>.md`를 더하면, 그 기능이 제품 변경을 담았는지 본다. 그 기능의 티켓 파일(`.scratch/<slug>/issues/` 아래)을 고친 커밋 가운데 제품 경로도 고친 것이 하나라도 있으면(지금 보는 변경 포함) 담은 것이다. 티켓 PR의 변경에는 그 티켓 파일이 들어 있다(`tools/check_ticket.py` 독스트링의 판정 5. 코드를 읽었다). 담았으면 변경 뒤의 트리에 `features/<slug>.md`가 있어야 하고, 담지 않았으면 그 파일을 더하지 못한다. `features/` 파일의 이름은 있는 기능 계획의 slug여야 한다.
- **(다) 모양.** 조각은 모두 비어 있지 않고 `#`으로 시작하는 줄(머리)이 없다. 노트가 머리를 단다. 기능 단락은 빈 줄 없는 한 단락이고 줄바꿈을 뺀 글자 수가 400자 이하다. 소개 글의 이름은 `X.Y.Z.md`다. 올릴 때 할 일과 소개 글에는 길이 상한을 두지 않는다. 할 일은 빠짐없는 것이 짧은 것보다 중요하다.

400자는 지난 기능 넷에 돌려 본 초안이 2~4문장 제한을 넘겨 6~10문장, 379~725자를 쓴 데서 정했다(`.scratch/release-image/probes/notes_summary/README.md`의 1번. 문장 수는 손으로, 글자 수는 `uv run python`으로 셌다). 그 초안의 문장 하나는 평균 60~72자라 4문장이면 240~290자 안팎이고(어림), 2~4문장의 예(일지 2026-11-13-1843의 미리보기, 3문장)는 줄바꿈을 빼고 145자다(`uv run python`으로 셌다). 400자면 4문장 단락에 여유가 남고, 초안 넷 가운데 셋(473·542·725자)이 걸리며 6문장인 하나(379자)는 지난다.

푸시 뒤에 PR 제목만 고치면 ci.yml은 다시 돌지 않는다. ci.yml은 `pull_request`의 기본 이벤트(열림, 푸시, 다시 열림)에만 돌고 제목을 고치는 `edited`는 그 안에 없다(코드를 읽었다). `edited`를 ci.yml에 더하면 PR 설명을 고칠 때마다 CI 전체가 다시 돌므로, 같은 도구를 (가)만 보게 부르는 작은 워크플로를 따로 두고 그것만 `edited`에 돌린다. dev와 main으로 가는 PR에서 돌고, 위처럼 머리가 main이나 dev인 PR은 건너뛰며, 제목은 같은 까닭으로 환경 변수로 넘긴다. 노트 검사 도구를 짓는 티켓이 함께 싣는다. 이 워크플로는 필수 검사에 넣지 않는다. 제목을 고치지 않은 PR에서는 돌지 않아, 필수로 두면 결과가 오지 않아 병합이 막히기 때문이다. 그래서 그 빨강은 GitHub가 막지 않고, 병합하는 세션이 `gh pr checks`에 실패가 없는지 보는 단계(next-session `merge.md` "워크트리에서 병합할 때" 1)가 멈춘다.

검사가 못 보는 것: 사람이 위 워크플로의 빨강을 두고 웹에서 병합하면, 그 커밋은 노트에 할 일 없이 제목만 선다. 단락의 내용이 맞는지는 리뷰 봇과 셀프 리뷰가 본다.

### 느낌표의 기준과 그것을 보는 때(명세가 정했다)

느낌표는 운영자가 판을 올릴 때 자기가 쥔 것을 고쳐야 하는 변경에 붙인다. 쥔 것은 ADR 0056 결정 "번호"가 든 넷(설정, 환경 변수, 데이터, 플러그인 코드)이고, 설정에는 사이트 파일, 위젯 미리보기 페이지 설정, 규칙 파일, 플러그인 매니페스트, 배포 파일 묶음에서 운영자가 고친 파일이 든다. 손대지 않으면 올린 뒤 동작이 멈추는 변경(기본값이 바뀌어 전에 돌던 도구 호출이 승인 대기로 멈추는 것 같은)도 든다. 기본값이 안전한 새 선택 설정이나 화면 안에서 자리를 옮긴 것은 들지 않는다.

이 기준은 `docs/constitution/operations.md`에 적고, 보는 자리는 셋이다. 티켓 PR의 서식(`.github/PULL_REQUEST_TEMPLATE.md`)에 "올릴 때 운영자가 손댈 것" 칸을 더해 PR을 쓰는 세션이 답하게 한다. claude-review의 프롬프트에 변경과 접두의 느낌표가 맞는지 보는 줄을 더한다. 노트 검사의 (가)가 느낌표와 할 일 파일의 짝을 본다. claude-review의 워크플로를 고치는 PR은 리뷰가 건너뛰므로 다른 파일과 함께 싣지 않는다(PR 서식의 `.github/` 줄과 그 워크플로의 가드 스텝). 그래서 프롬프트 줄은 따로 티켓 하나로 낸다.

저장소의 이력에는 접두 뒤에 느낌표가 붙은 커밋이 아직 하나도 없다(`git log --format='%h %s' origin/dev`의 출력을 걸러 손으로 봤다. 일지 2026-11-13-1843). 지난 기능 하나(approval-rules)는 이 기준이면 느낌표가 붙었을 변경으로 읽힌다(어림. 그 명세의 시험이 규칙 파일이 따라가지 않으면 "기본 묻는다에서 멈춘다"고 적는다. `notes_summary` README 4번).

### 취약점 점검(명세가 정했다)

점검 도구는 Grype이고 소프트웨어 목록은 Syft가 내는 SPDX 2.3 JSON이다. 둘 다 digest로 고정한 공식 컨테이너 이미지로 돌리고 액션을 거치지 않는다. 대상은 판 내기가 러너에 실은 이미지를 `docker save`로 받은 파일이다.

- 경고의 문턱은 고칠 수 있는(고친 판이 나와 있는) Critical이다. Grype의 `--only-fixed --fail-on critical`은 찾으면 종료 코드 2, 없으면 0, 입력이 없으면 1이라 문턱과 오류가 갈렸다(쟀다, `release_mechanics` README 3번. 여섯 대상·도구 짝에 문턱 둘을 걸어 열둘 모두 거르지 않은 JSON의 건수와 맞았다). 2면 노트 맨 위에 경고를 싣고 판은 낸다. 0과 2가 아닌 종료 코드는 점검이 실패한 것이라 판 내기가 실패한다. 점검 결과가 없는 릴리스를 내지 않기 위해서다. 원인은 대개 저장소 밖(DB 받기)이라 다시 돌리기의 길로 간다.
- High는 문턱에 넣지 않는다. 지금 바탕 둘에 고칠 수 있는 High가 2개와 8개 있어(zlib 둘과 node 이미지 안 npm 꾸러미 여섯, 같은 README 3번) 바탕 이미지가 다시 지어지기 전까지 모든 판에 경고가 선다. 늘 서는 경고는 읽히지 않는다.
- 릴리스에는 이미지마다 Grype의 거르지 않은 JSON과 Syft의 SPDX JSON을 첨부한다. 경고는 걸린 CVE 번호와 꾸러미와 고친 판을 적는다.
- Syft의 SPDX는 파일마다의 목록을 담아 Trivy의 것보다 열 배쯤 크다(파이썬 바탕에서 2,307,094바이트 대 193,876바이트, 같은 README 3번). 릴리스 자산 하나의 크기 한도 안이라고 본다(어림).
- Grype의 DB는 풀어 둔 크기가 3.20GiB다(같은 README 3번). 실행마다 받을지 캐시에 둘지는 워크플로를 짓는 티켓이 정한다.

거부한 안: Trivy. 2026년 3월의 공급망 사고(GHSA-69fq-xp46-6x23)로 `aquasecurity/trivy-action`의 판 태그 77개 가운데 76개와 `aquasecurity/setup-trivy`의 태그 전부가 악성 커밋으로 옮겨졌고, trivy-action v0.36.0이 입력이 없을 때 쓰는 Trivy 판(v0.70.0)은 다른 권고(GHSA-mcj4-mphf-j9ff, `< 0.71.1`)의 범위에 든다(같은 README 3번, 권고와 액션 정의의 원문을 받아 대 봤다). 또 Trivy는 기본으로 익명 사용 자료를 보낸다(도움말의 `--disable-telemetry` 설명, 같은 README 3번, 손으로 봤다). Debian 12 양성 대조에서 Grype는 Trivy가 고칠 수 있는 Critical·High로 센 CVE 35개를 모두 냈고 47개를 더 냈다. 두 후보 바탕에서는 둘이 같았다(같은 README 3번, 쟀다). Critical과 High를 함께 문턱으로 둔다(위의 까닭).

ADR 0056 Consequences "CI와 비밀 값"의 trivy-action 문장은 커밋으로 고정한 사용자는 영향이 없었다고 적는데, 권고의 영향 없음 조건은 2025-04-09 뒤의 안전한 커밋으로 고정한 경우다(같은 README 3번). 이 명세가 Trivy를 쓰지 않아 결정에는 닿지 않지만 본문의 사실이 틀렸으므로 이력에서 바로잡는다(서두 "이력").

### 실패한 판을 다시 돌리는 길(명세가 정했다)

ADR 0056이 정한 두 길 가운데 원인이 저장소 밖에 있을 때의 길은 실패한 잡만 다시 돌리는 `gh run rerun <실행> --failed`다. 다시 돌린 잡에 기대는 잡도 함께 돌고, 다시 돌지 않는 잡의 출력은 앞의 것을 쓴다(GitHub 문서의 원문을 받아 대 봤다, `release_mechanics` README 8번). 판 내기의 둘째 잡만 실패했으면 첫째 잡이 낸 digest와 아티팩트를 그대로 받아, 번호 태그를 지키는 차례가 같은 digest를 보고 이어 간다. 실행 전체를 다시 돌리면 같은 커밋을 다시 지어 digest가 달라지고(캐시를 다 써도 이미지 색인의 digest가 달랐다. 쟀다, 같은 README 8번. 증명 매니페스트가 달라져서라는 풀이는 어림이다), 번호 태그를 이미 붙였다면 지키는 차례가 거부해 끝나지 못한다. 그래서 `docs/constitution/operations.md`의 다시 돌리는 절차는 `--failed`를 적는다. 다시 돌리기는 처음 실행 뒤 30일 안에만 된다(같은 README 8번).

원인이 저장소 안이면 ADR 0056의 길은 핫픽스다. 번호 태그를 붙이기 전의 실패는 초안이 지워지고 레지스트리에는 많아야 해시 태그가 남으므로, 핫픽스의 실행이 같은 번호로 판을 낸다. 번호 태그를 붙인 뒤의 실패는 핫픽스로 바로 가지 않는다. 핫픽스가 main을 움직이면 새 실행이 같은 번호를 계산하고 사전 확인이 앞 커밋의 초안을 보고 실패한다. 앞 실행을 다시 돌려도 처음 실행과 같은 커밋(`GITHUB_SHA`)으로 돌므로(같은 README 8번의 원문) 고친 워크플로로는 끝낼 수 없다고 본다(워크플로 파일도 그 커밋의 것을 쓴다는 것은 어림이다). 그래서 그 판은 남긴 초안으로 끝낸다. 사람이 GitHub 화면에서 그 초안을 공개하고, 그 뒤에 핫픽스를 올린다. 번호 태그가 넷 가운데 일부만 붙었을 수 있으므로, 사람은 지키는 차례와 같은 명령을 네 이미지 모두에 친 뒤 공개한다. 공개하기 전에 초안에 위 "판 내기 워크플로"가 릴리스에 올리는 파일(배포 파일 묶음, 이미지마다의 소프트웨어 목록과 점검 결과)이 모두 있고 본문에 노트의 글이 있는지 보고, 빠진 것은 그 실행의 아티팩트에서 받아 올린다. 사전 확인이 앞 초안을 지우고 새로 만든 실행이나 자산을 올리다 끊긴 실행은 일부만 올렸을 수 있다(PR 직전 리뷰가 짚었다, 일지 2026-11-14-1748). 받은 파일은 올리기 전에 둘째 잡과 같은 대조(받은 파일이 다 있고 그 안에 적힌 판 번호와 digest가 첫째 잡의 출력과 같은지)를 거친다. 아래의 둘째 잡만 다시 돌린 회차가 그 대조에서 실패해 이 길로 온 판은 같은 아티팩트를 다시 받는 것이라 특히 그렇다. 대조를 지나지 않으면 그 파일을 올리지 않고 공개도 하지 않은 채 멈추고, ADR 0056 결정 "판 내기의 차례와 실패"로 돌아가 다시 정한다. 실행 전체를 다시 돌리는 길은 이 판에서 막혀 있다. 번호 태그가 붙은 뒤라 새 digest를 지키는 차례가 거부한다(이 절의 첫 문단. PR 봇이 짚었다, 일지 2026-11-14-1748). 이미 붙은 이미지는 같은 digest라 그 차례가 그대로 두므로(위 "판 내기 워크플로"의 지키는 차례), 어느 이미지에 붙었는지 먼저 가려낼 일이 없다. 실패한 잡을 다시 돌리는 길도 같은 차례로 네 이미지를 모두 본다. 공개가 git 태그를 만들므로 핫픽스의 실행은 다음 번호를 계산한다(어림. 이 길은 돌려 보지 않았고, 초안이 공개할 때 태그를 만든다는 것은 위 "판 내기 워크플로"의 같은 풀이에 기댄다).

번호 태그 뒤에 실패한 판이 끝나기 전에 main이 다시 움직였으면(위의 핫픽스든 다른 병합이든) 새 실행은 사전 확인에서 실패한다. 앞 판을 위의 두 길 가운데 하나로 끝낸 뒤, 새 실행을 처음부터 다시 돌린다. 새 실행은 번호를 다시 계산해야 하기 때문이다.

첫째 잡이 지난 판 태그에 공개 릴리스가 없어 실패했으면(위 "판 내기 워크플로"의 초안과 git 태그), 그 태그와 같은 번호의 초안은 앞 실행이 정리 단계 없이 끝나 남긴 것이다. 번호 태그는 초안 단계의 태그 대조 뒤에 붙으므로 그 판에는 붙지 않았다. 사용자에게 청해 그 초안과 태그를 지운 뒤, 실패한 실행 전체를 다시 돌린다.

둘째 잡의 첫 시도가 받은 아티팩트의 대조에서 실패했으면(같은 "초안과 git 태그"의 셋째 항목) 사전 확인과 초안 만들기 전이라 초안도 번호 태그도 없고, 레지스트리에는 첫째 잡이 올린 커밋 해시 태그만 남는다. 그래서 실패한 실행 전체를 다시 돌린다. 같은 커밋을 다시 지어 해시 태그의 digest가 바뀌지만 번호 태그가 아직 없어 지키는 차례가 막지 않는다(어림. 이 길은 돌려 보지 않았다). 둘째 잡만 다시 돌린 회차가 이 대조에서 실패했으면 앞 회차가 남긴 초안과 번호 태그가 있을 수 있다. 사람이 GitHub 화면과 레지스트리에서 그 번호의 초안과 번호 태그를 보고, 번호 태그가 하나라도 붙었으면 위의 남긴 초안으로 끝내는 길을 따른다. 붙지 않았으면 실행 전체를 다시 돌린다. 남은 같은 커밋의 초안은 새 실행의 사전 확인이 지우고 새로 만든다(위 "판 내기 워크플로"의 사전 확인). 초안 직후의 태그 대조에서 실패했으면 초안이 git 태그를 만든다는 뜻이다. 정리 단계가 초안과 그 태그를 지우므로 남는 것은 해시 태그뿐이고, 판 내기의 차례를 ADR 0056 결정 "판 내기의 차례와 실패"로 돌아가 다시 정한 뒤 고친 워크플로를 핫픽스로 올린다(위 "초안과 git 태그"의 끝 문단).

동시 실행 묶음이 기다리던 실행을 더 나중 실행으로 바꾸며 취소한 것은 다시 돌리지 않는다. 남은 실행이 그 변경까지 싣는다(위 "판 내기 워크플로"). 이 절의 절차는 모두 같은 문서에 적는다.

거부한 안: 실패하면 늘 초안을 지운다. 번호 태그 뒤의 실패에서 그 번호의 판을 끝낼 길이 없어진다. 번호 태그를 지키는 차례가 digest 대신 이미지의 커밋 라벨을 견준다. 같은 커밋의 다른 digest로 번호 태그를 옮기게 되어, 운영자가 이미 받은 이미지와 같은 번호의 다른 이미지가 생긴다(같은 README 8번이 같은 풀이를 적는다). 번호를 계산할 때 Docker Hub의 번호 태그도 보고 비켜 간다. 이미지만 있고 릴리스가 없는 번호가 남는다.

### 병합 절차와 규약 문서(명세가 정했다)

규약 문서는 그것을 바꾸는 티켓이 같은 변경에서 고친다(ADR 0056 Consequences "규약 문서", "병합 절차").

- `next-session`의 `merge.md`: 출시 PR과 핫픽스의 "병합 뒤"에 판 내기를 기다리는 단계를 더한다. 기다림은 병합 커밋의 해시로 판 내기 워크플로의 실행을 찾아 끝까지 보고, 결과를 넷으로 가른다. 판을 냈으면 판 번호와 릴리스 주소를 적고, 제품 변경이 없어 판 없이 성공했으면 그렇다고 적는다. 기다리던 중 더 나중 실행에 밀려 취소됐으면 그 나중 실행을 같은 방법으로 끝까지 보고, 취소된 실행은 다시 돌리지 않는다. 실패했으면 실패한 단계, 원인이 저장소에 있는지 밖에 있는지, 번호 태그를 붙인 뒤였는지를 가려 위 "실패한 판을 다시 돌리는 길"대로 다음 작업으로 넘기고, 사람이 초안을 공개해야 하면 사용자에게 청한다. 결과는 보고와 일지에 적는다. 판 내기 워크플로를 짓는 티켓이 한다. 하네스를 고치는 일이라 그 티켓은 워크트리에서 하고, 고친 스킬을 새 세션에서 불러 본다.
- `docs/constitution/operations.md`: 느낌표의 기준, 노트 조각을 쓰는 때, 판이 나는 차례와 실패한 판을 다시 돌리는 절차를 적는다. 문서 위치 절의 기록 목록에 "판으로 나간 노트 조각"을 더한다. 나간 조각을 고쳐도 다음 노트에 다시 실리지 않으므로 잔존 grep이 그것을 고치라고 하지 않게 한다.
- `docs/constitution/tech.md`: 스택 행에 레지스트리(Docker Hub), 프록시(nginx), 점검 도구를 더한다.
- `docs/agents/issue-tracker.md`: 기능의 마지막 티켓을 닫는 커밋이 `**끝:**` 줄과 함께 기능 단락을 싣는다는 것을 더한다. `CLAUDE.md` 지도 표의 기능 계획 행이 `**끝:**` 줄을 적는 주체를 적으므로 그 행에서 이 문서를 가리키게 한다.
- `.github/workflows/ci.yml` 머리 주석의 "실제 이미지의 compose e2e 는 이 파일에 아직 없다" 문장은 그 잡을 더하는 티켓이 고친다. 같은 티켓이 `merge.md` 출시 PR 절에서 그 주석을 들어 main에서만 더 도는 검사가 아직 없다고 적은 문장도 고친다. 그 문장은 ci.yml 머리 주석이 llm 잡을 main에서만 더 도는 검사로 적은 뒤로 이미 맞지 않고, 그 잡이 dev에 오르면 출시 PR이 더 지나는 검사가 하나 더 늘기 때문이다(티켓을 쓰며 판 내기 워크플로의 티켓에서 옮겼다, 일지 2026-11-14-1748). 그 잡을 verify의 needs에 넣으므로 같은 티켓이 검사 잡의 수(지금 일곱)를 적은 문장도 모두 고친다.
- `CONTEXT.md`의 "릴리스 노트"와 "노트 조각"은 이 명세의 PR이 더했다.

### 사람 몫(넘겨받은 것)

Docker Hub 계정 만들기, 2단계 인증, 접근 토큰 발급, GitHub 저장소에 비밀 값과 변수를 넣는 일은 사람 몫이다(ADR 0056 결정 "레지스트리와 계정"). 이것이 없으면 첫 판 내기가 실패한다. 판 내기 워크플로를 짓는 티켓이 사람에게 할 일을 한 화면으로 보이고, 원하는 이름이 비어 있는지는 그때 사람이 본다. release-image의 출시 PR을 병합하기 전에 그 일이 끝났는지 묻는다.

사람이 할 일의 목록(명세가 정했다). 판 내기 워크플로를 짓는 티켓이 이 목록을 한 화면으로 보인다.

1. Docker Hub에 이 제품의 이름으로 무료 개인 계정을 만들고 2단계 인증을 켠다.
2. 읽기와 쓰기 권한의 접근 토큰을 발급한다. 지우기 권한은 쓰지 않는다.
3. GitHub에서 세분 토큰(fine-grained PAT)을 만든다. 저장소는 이 저장소 하나만 고르고, 권한은 Contents와 Workflows에 읽기·쓰기를 주고 다른 권한은 고르지 않는다. 만료는 사람이 고른다(위 "판 내기 워크플로"의 권한과 비밀 값). 워크플로를 짓는 티켓은 이름과 권한을 미리 채운 만들기 주소(GitHub 문서가 적는 템플릿 주소)를 보인다.
4. GitHub 저장소 설정에서 환경 하나를 만들어 배포 브랜치를 `main` 하나로 좁히고, 그 환경에 비밀 값 둘(2의 접근 토큰과 3의 세분 토큰)과 변수 하나(Docker Hub 계정 이름, 곧 이미지 이름공간)를 넣는다. 환경과 값의 이름은 워크플로를 짓는 티켓이 정한다.
5. 저장소 설정에서 squash 병합의 기본 커밋 제목을 PR 제목으로 바꾼다(REST의 값 `PR_TITLE`. 위 "커밋 제목이 서는 자리"). 저장소 설정을 바꾸는 일이라 세션이 하지 않는다.
6. Docker Hub의 계정 아래에 저장소 넷(`serve`, `admin`, `widget`, `portal`. 위 "이미지의 이름과 태그")을 공개로 미리 만든다.

저장소를 미리 만드는 것은 첫 올리기가 저장소를 만드는지와 그 저장소가 공개인지를 보지 못했기 때문이다(로그인하지 않아 보지 못했다). 명세 검토가 사람 몫 한 줄로 이 어림을 없애자고 짚었다(일지 2026-11-14-1748 "명세 검토"의 S10). 미리 만들어 두면 번호 태그의 조회가 저장소 없음(`pull access denied`)을 만나지 않고, 운영자가 로그인 없이 받을 수 있다. Docker Hub에는 정해진 태그를 다시 올리지 못하게 하는 설정(변경 불가 태그)이 있고 문서에 무료 개인 계정을 막는 적힘은 없지만, 기능 표가 베타로 적고 로그인하지 않아 켜지는지 확인하지 못했다(`release_mechanics` README 2번, 원문을 받아 대 봤다). 번호 태그를 지키는 차례가 같은 일을 하므로 그 설정에 기대지 않는다.

### rag-engine에 줄 지시문(넘겨받은 것)

기능 계획 본문은 판 내기 워크플로를 지어 실제로 돌려 본 티켓이 닫을 때, 그 워크플로와 판을 내는 규칙을 rag-engine에 옮기라고 그 저장소의 세션에 줄 지시문을 사용자에게 낸다고 적는다(release-image 기능 계획 본문, 일지 2026-11-11-1532). 지시문은 ADR 0043과 ADR 0056(이 명세가 정한 것을 담은 이력 포함)을 입력으로 받는 짧은 설계 인터뷰를 열게 하고, 그 저장소가 따로 정할 것 다섯을 싣는다. agent-os의 규약 ADR을 따른다고 적고 다른 점만 적는 얇은 ADR 한 장을 두라는 요건도 싣고, 지시문을 낼 때 대기열 `rag-engine-port-by-hand`에 회차를 더한다. "실제로 돌려 본"은 release-image의 출시 PR이 병합된 뒤의 첫 실제 판 내기이므로, 이 지시문은 그것을 지켜본 세션이 낸다(아래 Testing Decisions의 넷째 이음매).

### 티켓을 나눌 때 함께 둘 것(명세가 정했다)

티켓의 수와 경계는 `/to-tickets`가 정한다. 이 명세가 정하는 것은 한 변경에 함께 실어야 하는 것과 먼저 와야 하는 것이다.

- `pyproject.toml`의 `version`을 `0.0.0`으로 바꾸는 편집은 `openapi.json`의 판 칸과 `uv.lock`의 자기 패키지 항목을 함께 바꾼다. 계약 파일에 닿으므로 그 티켓이 다른 티켓을 막는다(ADR 0056 결정 "저장소의 번호", 작업 규약 2).
- 네 프로세스의 예외와 관리 화면 상류의 예외, 그리고 그것을 잠그는 사례 표는 한 변경에 싣는다. 한 곳만 루프백 밖을 받는 상태가 기준 브랜치에 남지 않게 한다.
- 첫째 이음매의 시험 패키지와 ci.yml의 새 잡은 Dockerfile과 compose 파일·프록시 설정이 모두 갖춰지는 변경에 함께 싣는다(ADR 0056 결정 "실제 이미지로 띄우는 시험"과 이력 2026-11-14 "실제 이미지의 compose e2e 잡은 Dockerfile과 compose를 갖추는 티켓이 더한다"). 이미지 넷을 짓는 티켓이 네 프로세스의 예외를 들이는 티켓 뒤에 오므로(아래 항목) 그 변경은 release-image의 첫 티켓이 아니다. dev로 가는 그 PR에서는 잡이 시험하지 않으므로, 그 티켓은 시험을 이 PC의 Docker로 돌린 결과를 일지에 적는다(Testing Decisions의 첫째).
- claude-review의 프롬프트 줄은 따로 티켓 하나다(위 "느낌표의 기준과 그것을 보는 때").
- `merge.md`, PR 서식, 규약 문서를 고치는 티켓은 하네스를 고치는 일이라 워크트리에서 하고, 고친 스킬을 새 세션에서 불러 본다(작업 규약 3).
- 판 내기 워크플로를 들이는 티켓은 이미지 넷, compose 파일, 번호·노트 도구를 들이는 티켓 뒤에 온다. 워크플로가 그것들을 부른다.
- 판 내기 워크플로와 판 설정 파일 `deploy/release.toml`은 함께 release-image의 마지막 티켓에 싣고, 그 티켓은 배포 안내와 배포 파일 묶음을 들이는 티켓 뒤에 온다. 어느 기능이든 `**끝:**` 줄이 dev에 오르면 출시 PR이 열리고, 끝나지 않은 기능의 조각도 막지 않고 함께 main에 오른다(next-session `merge.md`의 "출시 PR"). 그래서 둘이 먼저 dev에 오르면 다른 기능의 출시 PR이 main에 닿는 순간 판 내기가 돌아, 배포 안내가 빠진 묶음으로 `0.1.0-rc.1`을 공개할 수 있다. 명세 검토가 짚었다(일지 2026-11-14-1748 "명세 검토"의 S2). 워크플로만 먼저 오르면 판 설정 파일도 판 태그도 없어 구성 오류로 실패하고(위 "번호"의 5), 판 설정 파일만 먼저 오르면 아무것도 돌지 않는다. 둘을 함께 늦게 싣는 것이 둘 다를 막는다.
- 이미지 넷을 짓는 티켓은 네 프로세스의 예외를 들이는 티켓 뒤에 온다. 예외가 없으면 이미지 안의 프로세스가 compose 네트워크 쪽 주소에 묶이지 못하고, 관리 화면 이미지는 상류 `serve`를 넣어 지을 수 없다(위 "관리 화면의 상류").
- 마지막 티켓이 위의 둘과 함께 `docs/release-notes/features/release-image.md`, `docs/release-notes/intro/0.1.0.md`, 기능 계획의 `**끝:**` 줄을 싣는다(위 "릴리스 노트"). 그 끝 줄이 dev에 오르면 열리는 출시 PR이 첫 판을 낸다.

## Testing Decisions

좋은 시험은 운영자와 방문자에게 보이는 것(열린 포트, 경로와 상태 코드, 화면에서 질문하고 받는 답)과 도구가 내는 것(번호, 노트의 글, 검사의 판정)을 본다. 이미지 안의 파일 배치나 Dockerfile의 줄은 단언하지 않는다. 예외로 root가 아닌 사용자와 이미지 안의 판 번호는 결정이 요구하는 성질이라, 띄운 컨테이너에서 본다.

이음매는 넷이다(사용자가 골랐다. 이 명세를 쓰며 물었다, 일지 2026-11-13-1843 "사용자에게 물은 것 하나"). 새로 만드는 것은 첫째 하나다.

1. **실제 이미지의 단독 배포(새 이음매).** 지은 이미지 넷과 `deploy/standalone/`의 compose 파일과 프록시 설정으로 단독 배포를 띄우고, 브라우저(Playwright의 Chromium)가 방문자처럼 프록시의 443으로 들어간다. 80의 넘김과 관리 화면의 `127.0.0.1:3000`은 아래 사례에서 따로 본다.
   - 사례: 위젯 미리보기 페이지가 그려진다(이미지가 시작 때 지은 토큰 CSS와 페이지 스크립트, 패키지의 글꼴이 받아진다). 거기서 질문하고 답을 받는다. 토큰 끝점에 한도를 넘겨 요청하면 429다. 정해진 경로 밖(관리 API의 경로, `serve`의 `/health`, 최종 사용자 접두사 밖으로 나가는 우회)은 404다. 80은 443으로 넘기고 443의 응답에 HSTS가 있다. 관리 화면은 프록시로 닿지 않고 호스트의 `127.0.0.1`에 발행한 포트로 닿는다. 띄운 배치가 발행한 포트는 프록시의 `0.0.0.0:443`·`0.0.0.0:80`과 관리 화면의 `127.0.0.1:3000` 셋뿐이다(Docker에 발행한 포트를 묻는다. 위 "프록시 설정"의 IPv6). 띄운 컨테이너에서 사용자가 root가 아니고 `agent-os --version`이 지을 때 넣은 번호인지 본다.
   - 평소에는 모델 없이 정해진 답을 하는 픽스처 에이전트로 돈다(`@agent-os/e2e-stack`의 픽스처 플러그인. web-widget 명세 Testing Decisions 4가 세웠다). 환경 변수가 켜지고 API 키가 있을 때만 calc 예시를 실제 모델로 묻는 묶음이 더해진다. 위젯 미리보기 페이지 e2e가 Playwright 프로젝트 둘을 두고 실제 모델 프로젝트를 환경 변수가 켜졌을 때만 더하는 것과 같은 방식이다(`web/apps/portal/playwright.config.ts`를 읽었다).
   - 시험은 새 워크스페이스 패키지 하나에 두고 e2e-stack의 픽스처 플러그인과 토큰 서명을 다시 쓴다. 그 패키지는 `web/` 안이라 제품 경로에 든다(위 "제품 변경의 경로 목록"의 둘째 항목).
   - 도는 곳은 ci.yml의 새 잡과 판 내기 워크플로의 "실제로 띄워 시험" 단계다. ci.yml의 잡은 ADR 0043 Consequences "CI 분담"이 정한 대로 main으로 가는 PR과 main 푸시에서 이미지 넷을 지어 시험하고, 그 밖의 PR과 푸시(dev로 가는 티켓 PR, dev 푸시)에서는 곧바로 성공으로 끝난다. verify는 건너뛴 잡을 빨강으로 보므로(ci.yml의 verify 주석) `if:`로 잡을 건너뛰지 않고 잡 안에서 끝내며, 잡을 verify의 needs에 넣는다. 제품 변경이 있는 main 푸시에서는 ci.yml의 잡과 판 내기의 단계가 같은 시험을 두 번 돈다. 판 내기의 단계는 올릴 이미지 자체를 시험하려는 것이고, main 푸시는 출시 PR과 핫픽스의 병합에서만 나므로 겹침을 받아들인다. 잡의 첫 제한 시간은 어림이다(ci.yml 머리 주석의 규약).
   - dev로 가는 PR에서는 이 시험이 CI에서 돌지 않는다. 그래서 `deploy/`나 이 시험 패키지를 고친 티켓은 같은 시험을 이 PC의 Docker로 돌려 결과와 걸린 시간을 일지에 적고, 그 로컬 명령을 `CLAUDE.md`의 검증 명령에 다른 e2e처럼 "건드렸을 때 친다"는 조건과 함께 더한다. CI에서 이 잡이 처음 시험하는 것은 그 잡을 더한 티켓이 dev에 오른 뒤 열리는 첫 출시 PR이다. 다른 기능이 release-image보다 먼저 끝나면 그 기능의 출시 PR이 먼저 이 잡을 지난다(next-session `merge.md`의 "출시 PR"은 끝나지 않은 기능의 조각도 막지 않고 함께 올린다).
   - 선례는 관리 화면·위젯·위젯 미리보기 페이지의 e2e(`web/apps/*/playwright.config.ts`)와 `web/packages/e2e-stack`이다.
2. **네 프로세스의 시작 검사(있는 자리).** 예외의 판정과 관리 화면 상류 주소의 판정을 각 프로세스의 시작 검사 시험에 더한다. 자리는 `tests/test_main.py`의 루프백 시험, `web/apps/admin/tools/loopback.test.ts`·`start.test.ts`·`start.spawn.test.ts`, `web/apps/widget/tools/start.test.ts`·`start.spawn.test.ts`, `web/apps/portal/server/config.test.ts`다. 사례 표 하나(표지 파일의 유무 × 환경 변수가 없음·빈 값·`1`·다른 값 × 주소가 `127.0.0.1`·`::1`·`0.0.0.0`·그 밖의 IPv4·`::`·이름)를 파이썬과 TS 시험이 함께 읽어 네 곳이 같은 판정과 같은 진단의 종류를 내는지 잠근다(선례 `tests/fixtures/site_file/`). 관리 화면 상류는 같은 표에 주소의 호스트 칸을 더한다. 시험은 `/etc`에 표지 파일을 만들지 않고, 판정 함수가 표지 파일의 유무를 인자로 받는다. 표지 파일을 실제로 읽는 길은 첫째 이음매가 띄운 컨테이너에서 본다.
3. **판 번호·노트 도구와 노트 검사(있는 방식).** 임시 git 저장소에 커밋과 태그를 만들어 넣는다(선례 `tests/tools/test_check_ticket.py`, `tests/tools/test_check_commit_msg.py`). 번호의 사례는 태그 없이 출시 후보 칸만 있을 때의 `rc.1`, 출시 후보가 있을 때의 다음 차례, 칸을 지운 뒤의 정식 판, 정식 판 뒤의 `fix`만·`feat`·느낌표·그 밖의 접두만, ` (#번호)`가 붙어 72자를 넘는 `feat` 제목이 가운데 자리를 올림(위 "번호"), 제품 경로를 고치지 않은 커밋만 있을 때 판을 내지 않음, merge 커밋으로 합친 출시 PR과 되돌려 합치기를 흉내 낸 이력, 판으로 나간 핫픽스가 다음 판에 다시 실리지 않음, 구성 오류 다섯(칸이 지난 정식 판보다 크지 않음, 칸으로 계산한 출시 후보가 지난 판보다 크지 않음, 칸도 태그도 없음, 계산한 태그가 이미 있음, 지난 판이 조상이 아님)이다. 노트의 사례는 차례와 빈 묶음 빼기, 범위 밖에서 더해진 조각을 다시 싣지 않음, 느낌표 커밋 아래의 할 일 글, 출시 후보와 정식 판의 소개 글, 정식 판이 지난 정식 판 뒤 전부를 싣는 것이다. 노트 검사는 (가)(나)(다)의 빨강과 초록, 머리가 main이나 dev인 PR을 건너뛰는 것이다.
4. **판 내기 워크플로(자동 시험 없음).** 워크플로 자체에는 자동 시험을 두지 않는다. zizmor가 워크플로를 감사하고(ADR 0027), 워크플로가 부르는 도구는 셋째가 시험한다. release-image의 출시 PR이 병합될 때 처음으로 끝까지 도는 실행을 그 출시 PR을 병합한 세션이 지켜보고 결과를 일지에 적는다(ADR 0056 결정 "실제 이미지로 띄우는 시험"). 그 세션은 잡마다 걸린 시간을 함께 적고, 초안 단계에서 git 태그가 생기지 않았는지 실행 기록에서 본다(위 "판 내기 워크플로"). 실패하면 ADR 0056 결정 "판 내기의 차례와 실패"의 두 길로 고친다(위 "실패한 판을 다시 돌리는 길"). 사용자는 판 내기를 출시 PR 전에 연습 모드로 한 번 돌려 보는 안을 고르지 않았다.
   - 첫 판이 나면 같은 세션이 기능 계획의 수락을 확인한다. 이 PC에서 그 판의 이미지를 지운 뒤 번호 태그로 받고, 릴리스에 첨부된 배포 파일 묶음을 풀어 띄운 뒤, 첫째 이음매의 시험을 실제 모델 묶음까지 켜서 돌린다. 그래서 시험 패키지는 이미지의 이름공간과 태그를 환경 변수로 받는다. 수락의 "깨끗한 리눅스 VM"은 이 PC에 없으므로 둘로 나눠 본다. 깨끗한 리눅스에서 뜨는 것은 판 내기가 GitHub 러너에서 지은 이미지로 돌린 시험이 보고, 레지스트리에서 받은 이미지와 릴리스의 배포 파일 묶음으로 뜨는 것은 이 PC의 Docker가 본다. 수락의 `/health`는 프록시가 밖으로 내지 않으므로(첫째의 사례) `serve` 컨테이너의 상태 확인이 정상인지로 보고, 위젯은 위젯 미리보기 페이지가 싣는 위젯으로 본다.
   - 같은 세션이 rag-engine에 줄 지시문을 낸다(위 "rag-engine에 줄 지시문").

## Out of Scope

이 명세가 정하는 것은 판을 만들어 올려 두는 데까지다(ADR 0056 여는 문단). 다른 기능에 넘기는 것은 받는 쪽의 기능 계획 본문에도 "release-image 명세가 넘긴 것(2026-11-13, `.scratch/release-image/spec.md`의 Out of Scope)"으로 적었고, 받는 기능의 `**Blocked by:**`를 대 봤다.

- **서버에 올리는 절차, 문서 검색 서버를 같은 네트워크로 잇는 일, 모델 파일까지 포함한 반입 절차**는 deploy-package의 것이다. `**Blocked by:**`에 release-image가 있다. 참조 배포가 단독 compose의 80과 관리 화면의 `127.0.0.1` 발행을 따를지도 그 행의 설계 인터뷰가 정한다(ADR 0056 Consequences "PRD와 기준선"). 443과 80을 서버의 IPv4 주소에만 발행하는 것(위 "프록시 설정"의 IPv6)을 따를지도 같다. 인터넷이 막힌 곳에서 운영자가 더한 stdio MCP 서버(npx로 띄우는 것)를 들여오는 길도 그 행의 반입 절차가 정한다. npx는 그런 곳에서 서지 않는다(위 "이미지의 구성"의 serve).
- **백업, 복원, 판 올림의 절차**는 ops-backup-upgrade의 것이다. `**Blocked by:**`에 release-image가 있다. 이 명세는 판 번호를 환경 변수 파일의 한 줄로 두고 노트에 "올릴 때 할 일"을 싣는 데까지 한다. 판을 올려도 이미 채워진 플러그인 볼륨은 바뀌지 않으므로 새 판의 예시 플러그인을 받는 길, 그리고 root 컨테이너로 볼륨에 먼저 쓰는 복원이 소유를 uid 10001로 넘기는 단계도 그 행의 것이다(위 "이미지의 구성"의 "플러그인 루트와 트레이스 폴더를 붙이는 것").
- **진단 묶음**은 diag-bundle의 것이다. `**Blocked by:**`에 release-image가 있다. 그 행이 묶을 판은 이미지의 OCI 라벨과 `agent-os --version`으로 읽힌다.
- **관리 화면의 로그인과 관리 화면을 인터넷에 여는 일**은 admin-login의 것이다. `**Blocked by:**`에 release-image가 있다.
- **공개 데모의 배포와 그 규칙 파일**은 public-demo의 것이다. `**Blocked by:**`에 release-image가 있다. 이미지에 든 파일을 덮는지 플러그인 루트를 따로 두는지는 그 행의 설계 인터뷰가 이 명세의 이미지 구성(위 "이미지의 구성"의 serve 문단과 플러그인 폴더)을 보고 정한다.
- **판 설정 파일의 출시 후보 줄을 지우는 일과 정식 판 0.1.0**은 pilot-release의 것이다. 그 행은 admin-login과 deploy-package를 거쳐 release-image 뒤에 온다.
- **위젯이 사이트 파일을 요청 때마다 읽는 일, 허용 출처와 요청 글자 수 상한을 화면에서 바꾸는 일**은 portal-admin의 것이다(ADR 0056 Considered Options). 그 행의 `**Blocked by:**`는 pilot-portal뿐이라 release-image보다 먼저 돌 수 있다. 그때 위젯 컨테이너가 뜰 때 빌드하는 것을 바꾸게 되므로 그 행의 기능 계획에 그 사실을 적었다.
- **판 내기 워크플로와 규칙을 rag-engine에 옮기는 일**은 그 저장소의 것이고, 이 명세는 지시문을 내는 데까지 한다(위 "rag-engine에 줄 지시문").
- **0.1 판의 범위 밖**: Podman, RHEL 계열 전용 바탕 이미지, ARM 서버(ADR 0056 결정 "보증하는 환경"), 인증서를 프록시가 스스로 발급받는 것(ACME), 인증서 갱신의 자동화, 늘 최신을 가리키는 이미지 태그, 이미지 서명. 이미지 서명은 ADR 0056이 다루지 않았고 받는 기능이 없다. 필요해지면 새 행이다.
- **판 내기를 미리 연습하는 모드**는 사용자가 고르지 않았다(Testing Decisions의 넷째).

## Further Notes

- **측정 환경의 한계.** 리눅스 서버는 하나도 쓰지 않았다. 모든 측정은 이 PC(Windows 10)의 Docker Desktop(엔진 29.9.2, WSL2 커널) 위에서 돌았고, 리눅스 서버는 Docker-in-Docker로 흉내 냈다(bridge_edge, bridge_recover, serve_image README의 항목 5·6). 그래서 실제 스위치와 서로 다른 커널, 실제 서버의 방화벽(firewalld·ufw), rootless Docker, SELinux, 바인드 마운트한 호스트 폴더의 uid는 재지 않았다(각 README의 "재지 못한 것"). 측정은 여러 세션이 한 데몬을 나눠 쓴 채 돌았으므로 걸린 시간은 범위로만 읽는다. 실제 리눅스 엔진 위의 단독 배포는 첫째 이음매의 시험이 GitHub의 리눅스 러너에서 처음 본다.
- **첫 판 내기에서 볼 것.** Testing Decisions의 넷째가 든 것(잡마다 걸린 시간, 초안 단계에서 git 태그가 없었는지)에 더해, 사람이 미리 만든 Docker Hub의 저장소 넷에서 로그인 없이 이미지가 받아지는지(위 "사람 몫")와 이미지의 압축 크기를 본다. 압축 크기와 받는 시간은 재지 않았고(위 "이미지의 구성"의 크기는 풀린 크기다), 인터넷이 막힌 곳에 파일로 옮길 때의 크기가 그것에 기댄다.
- **세분 토큰의 갱신.** 세분 토큰이 만료되거나 1년 동안 쓰이지 않아 지워지면 판 내기의 둘째 잡이 인증에서 실패한다. 그때는 사람이 토큰을 다시 만들어 환경의 비밀 값을 바꾸고, 세션이 실패한 잡만 다시 돌린다(위 "판 내기 워크플로"의 권한과 비밀 값, "실패한 판을 다시 돌리는 길"). 만료를 길게 고르면 그 일이 드물어지고, 짧게 고르면 새는 토큰이 쓰일 수 있는 동안이 짧아진다.
- **다시 잴 때.** 프로브마다 다시 돌리는 명령과 잰 판이 그 README에 있다(`.scratch/release-image/probes/README.md`의 표). nginx나 Docker Engine의 판을 바꾸는 티켓은 판에 기대는 측정(프록시가 뒷단을 다시 찾는 길, 발행한 포트의 보호)을 다시 돌려 본다. PR 직전 리뷰가 bridge_edge, bridge_recover, serve_image, web_images 네 프로브에 측정 조건(재려는 상황이 그 회차에 실제로 났다는 표지)을 더했고, 고친 판은 아직 돌리지 않았다. 앞선 실행의 기록으로 그 표지를 가를 수 없는 회차가 있고, 각 README의 "PR 직전 리뷰가 좁힌 측정 조건(2026-11-14)" 절이 그 회차를 든다. 이 명세에서 그 회차에 기대는 자리는 "이미지의 구성"(빌드 중인 위젯을 멈출 때, 다음 판의 새 파일), "발행하는 포트와 지원하는 최소 판", "프록시 설정"의 IPv6, "프록시가 뒷단을 다시 찾는 길"의 걸린 시간이다. 그 절을 구현하는 티켓은 고친 판을 먼저 다시 돌려 본다. PR의 CodeRabbit 첫 회차가 낸 Minor 가운데 여덟은 측정 판정 기준을 조이는 지적이라 고치지 않았다(`release_mechanics`의 `scan_tools.py`와 `registry_tags.py`, `serve_image`, `web_images`, `proxy_config`, `bridge_edge`의 프로브이고 목록은 일지 `docs/journal/2026-11-13-1843-release-image-spec.md`의 "봇 첫 회차"). 그 프로브에 기대는 절을 구현하는 티켓은 다시 돌리기 전에 그 여덟을 먼저 고친다. `release_mechanics`와 `proxy_config`는 위 목록에 없던 프로브라, 그 둘에 기대는 절을 구현하는 티켓도 여덟 가운데 그 프로브의 몫을 고친 판을 다시 돌린다. 어느 티켓이 어느 프로브를 고쳐 다시 돌리는지는 티켓의 수락 기준이 든다. 다시 잰 결과가 이 명세의 문장과 다르면 그 티켓은 구현을 멈추고 이 명세와 ADR 0056 이력으로 돌아간다.
