# 11: main이 움직이면 CI가 판 번호를 계산해 이미지와 릴리스를 낸다

**What to build:** main에 푸시가 오면 새 판 내기 워크플로가 돈다. 첫째 잡은 번호와 노트를 계산하고, 이미지 넷을 지어 09의 실제 이미지 시험을 돌리고, 점검한 뒤 커밋 해시 태그로만 올린다. 둘째 잡은 번호 태그를 지키는 차례로 붙이고 릴리스를 공개한다. 릴리스에는 배포 파일 묶음, 이미지마다의 소프트웨어 목록과 점검 결과, 노트가 붙는다(스토리 1, 2, 5~9). 판의 때와 번호는 사람이 정하지 않고(스토리 32), 실패한 판은 git 태그와 공개 릴리스를 남기지 않으며(스토리 33), 한 번 올라간 번호 태그는 다른 이미지로 덮이지 않는다(스토리 34). 출시 PR과 핫픽스를 병합한 세션은 판 내기를 끝까지 기다려 결과를 적는다(스토리 40). 사람이 할 일은 한 화면에 모이고(스토리 41), 두 토큰은 main에서 도는 판 내기 잡만 읽는다(스토리 42).

이 티켓이 release-image의 마지막 티켓이다. 판 내기 워크플로와 판 설정 파일 `deploy/release.toml`(`candidate_for = "0.1.0"`)을 함께 싣고, 기능 단락, 소개 글, 기능 계획의 `**끝:**` 줄도 함께 싣는다. 둘이 먼저 dev에 오르면 다른 기능의 출시 PR이 배포 안내가 빠진 묶음으로 첫 판을 낼 수 있기 때문이다(명세 "티켓을 나눌 때 함께 둘 것", 명세 검토 S2. 이 티켓의 "명세 검토"와 그 번호는 일지 `docs/journal/2026-11-14-1748-release-image-tickets.md`의 "명세 검토" 절을 가리킨다). 그 끝 줄이 dev에 오르면 열리는 출시 PR이 첫 판 `0.1.0-rc.1`을 낸다.

`merge.md`와 규약 문서를 고치는 하네스 티켓이기도 하다. 워크트리에서 하고 고친 스킬을 새 세션에서 불러 본다(작업 규약 3).

근거는 명세 "판 설정 파일", "번호"의 5, "이미지의 이름과 태그", "판 내기 워크플로"(초안과 git 태그, 권한과 비밀 값 포함), "릴리스 노트", "취약점 점검", "실패한 판을 다시 돌리는 길", "병합 절차와 규약 문서", "사람 몫", Testing Decisions의 넷째다. 측정은 `.scratch/release-image/probes/release_mechanics/README.md`이고 이 티켓이 그 프로브를 고쳐 다시 돈다(아래 "프로브").

**Blocked by:** 05, 06, 10

**Status:** ready-for-agent

### 첫째 잡: 짓고 시험하고 올린다

- [ ] main의 푸시에서 돌고, 동시 실행 묶음 하나로 한 번에 하나만 돌며 기다리는 실행은 가장 나중 것만 남는다
- [ ] 04의 도구로 번호와 노트를 계산한다. 번호 도구가 지난 판으로 고른 태그(04의 번호 도구가 판 번호와 함께 낸다)에 공개 릴리스가 있는지 GitHub에 묻고, 없으면 실패한다. 판 태그가 하나도 없는 첫 판(`0.1.0-rc.1`)에서는 고른 태그가 없어 이 확인을 건너뛴다. 이 확인은 제품 변경이 없어 성공으로 끝나는 갈래보다 먼저 한다(명세 "초안과 git 태그")
- [ ] 이미지 넷을 증명 없이 러너에 실어 09의 시험을 돌린다. 그 뒤 같은 빌더가 캐시로 다시 지어 증명(출처 증명 `mode=max`, SBOM)과 함께 커밋 해시 태그 `sha-<커밋 해시 40자>`로만 올린다. 빌드 캐시는 GitHub Actions 캐시에 이미지마다 다른 범위로 둔다
- [ ] 시험한 이미지와 올린 이미지가 같은지 이미지 저장 방식에 기대지 않는 대조로 단언하고, 다르면 실패한다(명세 검토 S7). 무엇을 견줄지(두 빌드가 낸 config digest, 레이어의 diff_id 목록 같은 것)는 이 티켓이 정한다. 명세는 러너에서 정하라고 적었으므로, 이 티켓의 PR에서 잠시 도는 잡 같은 길로 러너의 저장 방식에서 고른 대조가 서는지 한 번 보고 일지에 적는다. 볼 길이 없으면 고른 대조와 그 사실을 일지에 적고, 첫 판을 지켜보는 세션이 볼 것으로 다음 지시문에 넘긴다
- [ ] 점검은 digest로 고정한 Grype와 Syft의 공식 컨테이너 이미지로, 러너에 실은 이미지를 `docker save`로 받은 파일에 돌린다(액션을 거치지 않는다). Grype의 고칠 수 있는 Critical 문턱이 종료 코드 2면 노트 맨 위에 경고를 싣고 판은 내며, 0과 2가 아닌 종료 코드면 실패한다. Grype DB를 실행마다 받을지 캐시에 둘지는 이 티켓이 정한다
- [ ] Docker Hub 로그인은 시험과 점검을 마친 뒤에 한다
- [ ] 출력은 판 번호와 이미지 넷의 digest다. 배포 파일 묶음(04의 도구), 이미지마다의 Grype JSON(거르지 않은 것)과 Syft의 SPDX JSON, 노트의 글, 판 번호와 digest를 적은 파일을 그 실행의 아티팩트로 올린다. 보존 기간은 30일보다 짧지 않고, 첫째 잡이 다시 돌면 같은 이름을 덮어쓴다

### 둘째 잡: 번호를 붙이고 공개한다

- [ ] 첫째 잡의 아티팩트를 받은 직후, 받은 파일이 다 있고 그 안의 판 번호와 digest가 첫째 잡의 출력과 같은지 본다. 받지 못했거나 다르면 사전 확인과 초안 만들기 전에 실패한다
- [ ] 사전 확인은 명세 "판 내기 워크플로"의 차례다. 그 번호의 공개 릴리스가 이 커밋을 가리키면 성공으로 끝나고, 다른 커밋이면 실패한다. 공개 릴리스 없이 git 태그만 있으면 실패한다. 이 커밋의 초안은 지우고 새로 만들고, 다른 커밋의 초안이면 실패한다
- [ ] 초안 릴리스를 그 커밋의 전체 해시로 만든 직후 그 번호의 git 태그가 원격에 있는지 본다. 있으면 번호 태그를 붙이기 전에 실패하고, 정리 단계가 초안과 그 태그를 지운다. 이 대조로 실패한 실행은 "새 초안을 남기는" 예외에 들어도 초안을 지운다(명세 "초안과 git 태그")
- [ ] 자산을 올리고, 04의 번호 태그 판정으로 이미지 넷에 번호 태그를 붙이고(없으면 해시 태그를 `docker buildx imagetools create`로 복사, 같은 digest면 그대로, 다른 digest면 거부, 조회 실패면 붙이지 않음), 초안을 공개한다
- [ ] 번호 태그를 붙이는 단계 앞에서 실패하면 초안을 지우고, 그 단계부터 뒤에서 실패하면 남긴다. 사전 확인이 앞 실행의 이 커밋 초안을 지우고 새로 만든 실행은 번호 태그 앞에서 실패해도 새 초안을 남긴다(위 태그 대조의 실패는 빼고)

### 권한과 고정

- [ ] 두 비밀 값(Docker Hub 접근 토큰, 세분 토큰)과 변수 하나(이미지 이름공간)는 배포 브랜치를 `main` 하나로 좁힌 GitHub 환경에 두고, 판 내기의 두 잡만 그 환경을 쓴다. 환경과 값의 이름은 이 티켓이 정한다
- [ ] 세분 토큰은 둘째 잡의 릴리스 단계(초안 만들기, 자산 올리기, 공개, 실패할 때 초안과 그 번호의 git 태그 지우기)만 받는다. 기본 토큰으로는 태그를 지우지 못하므로 정리 단계의 태그 지우기도 세분 토큰으로 한다. 워크플로의 기본 토큰은 `contents: read`만 둔다. 단계마다 그 단계가 쓰는 비밀 값만 넘긴다
- [ ] 쓰는 액션은 이 티켓을 할 때의 최신으로 다시 골라 커밋 해시로 고정한다(ADR 0027. 명세를 쓸 때의 판은 `release_mechanics` README 5번). 두 잡의 제한 시간은 어림으로 시작한다(ci.yml 머리 주석의 규약). 워크플로 감사(zizmor)를 지난다

### 규약 문서

- [ ] `.claude/skills/next-session/merge.md`의 출시 PR과 핫픽스의 "병합 뒤"에 판 내기를 기다리는 단계를 더한다. 병합 커밋의 해시로 판 내기 워크플로의 실행을 찾아 끝까지 보고, 결과를 넷으로 가른다(판을 냈다, 제품 변경이 없어 판 없이 성공했다, 더 나중 실행에 밀려 취소됐다, 실패했다). 실패의 갈래는 실패한 단계와 원인의 자리와 번호 태그 앞뒤를 가려 "실패한 판을 다시 돌리는 길"대로 다음 작업으로 넘기고, 사람이 초안을 공개하거나 지워야 하면 사용자에게 청한다(명세 "병합 절차와 규약 문서"). 고치기 전에 Skill 도구로 `writing-for-agents`를 부르고(`.claude/rules/agent-docs.md`), 고친 `merge.md`가 새 세션에서 실리는지 본다
- [ ] `docs/constitution/operations.md`에 판이 나는 차례와 실패한 판을 다시 돌리는 절차를 적는다. 명세 "실패한 판을 다시 돌리는 길"의 갈래를 모두 든다. 쓰기 전에 그 절의 문단을 하나씩 대 보고 빠진 갈래가 없는지 본다. 갈래의 예는 `gh run rerun <실행> --failed`, 번호 태그 앞뒤의 핫픽스, 남긴 초안을 사람이 공개하기 전에 네 이미지 모두에 지키는 차례의 명령을 치고 초안의 자산과 노트가 다 있는지 보기, main이 다시 움직인 뒤, 지난 판 태그에 공개 릴리스가 없어 첫째 잡이 실패했을 때 사용자에게 청해 초안과 태그를 지운 뒤 실행 전체를 다시 돌리기, 받은 아티팩트의 대조에서 실패했을 때 실행 전체를 다시 돌리기(둘째 잡만 다시 돌린 회차면 남은 번호 태그가 있는지로 가르기), 초안 직후의 태그 대조에서 실패했을 때 ADR 0056 결정 "판 내기의 차례와 실패"로 돌아가기, 취소된 실행은 다시 돌리지 않기다
- [ ] `docs/constitution/tech.md`의 스택 행에 레지스트리(Docker Hub), 프록시(nginx), 점검 도구(Grype, Syft)를 더한다
- [ ] 헌법 판을 한 번 올린다(`docs/constitution/README.md`. 올린 까닭은 일지에. 명세 검토 N4). 판을 매기기 전에 `tools/sibling_overlap.py`로 형제 브랜치가 먼저 가져간 판을 본다
- [ ] 고친 규약의 옛 표현을 하네스 전체에서 grep해 살아 있는 문서의 잔존이 0인지 본다(작업 규약 4)

### 사람 몫

- [ ] 명세 "사람 몫"의 여섯을 한 화면으로 사용자에게 보인다. 세분 토큰은 이름과 권한(이 저장소 하나, Contents와 Workflows의 읽기·쓰기)을 미리 채운 만들기 주소(GitHub 문서가 적는 템플릿 주소)를, 환경과 비밀 값과 변수는 이 티켓이 정한 이름을 함께 보인다. 보인 화면을 일지에 적는다
- [ ] 이 티켓의 PR을 병합한 세션은 출시 PR의 계기가 서므로(`merge.md` "출시 PR"), 출시 PR을 병합하기 전에 사람 몫 여섯이 끝났는지 사용자에게 묻는다. 첫 판을 지켜보고 일지에 적는 일(잡마다 걸린 시간, 초안 단계에서 git 태그가 없었는지, 로그인 없이 받아지는지, 압축 크기, 이 PC에서 받은 이미지와 묶음으로 09의 시험을 실제 모델 묶음까지 켜서 돌리기)과 rag-engine에 줄 지시문은 그 출시 PR을 병합한 세션의 것이다(명세 Testing Decisions의 넷째, "rag-engine에 줄 지시문"). 이 티켓은 그 일을 하지 않고 다음 지시문에 넘긴다
