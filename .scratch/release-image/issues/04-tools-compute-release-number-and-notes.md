# 04: 도구가 판 번호와 릴리스 노트와 배포 파일 묶음을 짓고 번호 태그를 판정한다

**What to build:** 판 내기 워크플로(11)가 부를 도구가 `tools/`에 선다. 표준 라이브러리만 쓰고 의존성을 깔지 않은 CI 잡에서 `python3`로 돈다(명세 "저장소의 자리"). 넷이다.

- **번호.** 저장소의 git 이력과 판 태그와 판 설정 파일(`deploy/release.toml`)을 읽어, 판을 낼지와 다음 판 번호와 지난 판으로 고른 태그와 노트가 싣는 커밋 범위를 낸다. 구성 오류는 까닭과 함께 0이 아닌 코드로 끝난다.
- **노트.** 범위의 커밋 제목과 노트 조각(`docs/release-notes/{features,upgrade,intro}/`)과 이미지마다의 취약점 점검 결과를 받아 릴리스 노트의 글을 낸다.
- **배포 파일 묶음.** `deploy/standalone/`의 파일에 판 번호와 이미지 이름공간을 채워 `agent-os-<판 번호>.tar.gz`(풀면 같은 이름의 폴더 하나)를 짓는다.
- **번호 태그 판정.** 번호 태그 조회의 출력과 종료 코드와 올린 digest를 받아 "붙인다", "그대로 둔다", "거부한다", "붙이지 않는다(조회 실패)"를 가르는 순수 함수다(스토리 34).

개발 세션이 판의 때와 번호를 정하지 않게 하고(스토리 32), 운영자가 받는 묶음을 첫 판 전에 시험으로 짓게 하려는 것이다(스토리 1, 4). 묶음과 번호 태그 판정은 명세 Testing Decisions의 셋째 밖이었고, 명세 검토가 덮이지 않은 스토리로 짚어 이 티켓에 넣었다(일지 2026-11-14-1748 "명세 검토"의 S4).

근거는 명세 "저장소의 자리", "제품 변경의 경로 목록", "판 설정 파일", "번호", "커밋 제목이 서는 자리", "릴리스 노트", "취약점 점검"(경고의 문턱과 글), "배포 파일 묶음", "판 내기 워크플로"의 번호 태그를 지키는 차례, Testing Decisions의 셋째다. 측정은 `.scratch/release-image/probes/release_mechanics/README.md` 2번(번호 태그 조회의 출력)과 7번(커밋 고르기)이고 이 티켓은 다시 돌리지 않는다(11이 그 프로브를 고쳐 다시 돈다).

**Blocked by:** 01

**Status:** ready-for-agent

### 번호

- [ ] 판 태그는 `v<X.Y.Z>`와 `v<X.Y.Z>-rc.<n>`(앞에 0 없음) 꼴만 보고, 규칙 1~6과 구성 오류를 명세 "번호" 그대로 짓는다. 판 설정 파일은 선택 칸 `candidate_for` 하나만 받고, 다른 칸이나 틀린 꼴은 구성 오류다
- [ ] 제품 변경은 `src/`, `web/`, `plugins/`, `uv.lock`, `deploy/` 가운데 하나라도 고친 커밋이다. 이 목록은 한 자리에 두어 05의 노트 검사가 같은 것을 쓴다
- [ ] 커밋은 병합 커밋을 빼고, 지난 판 태그에서 닿지 않으며 제품 경로를 고친 것을 고른다. 첫 부모만 따라가지 않고, 경로로 거른 git 이력의 기본 단순화도 쓰지 않는다(명세가 든 두 까닭)
- [ ] 번호 도구는 판을 낼지와 다음 판 번호와 함께 지난 판으로 고른 태그를 내고, 판 태그가 하나도 없으면 없다고 낸다. 11의 첫째 잡이 그 태그에 공개 릴리스가 있는지 볼 때 쓴다(명세 "초안과 git 태그"). 시험은 태그가 있을 때와 없을 때 둘을 본다
- [ ] 제목은 커밋 검사(`tools/check_commit_msg.py`)의 `PATTERN`만으로 읽고 길이와 끝 마침표는 보지 않는다. 같은 정규식을 두 벌 두지 않는다. 꼴에 맞지 않는 제목은 `feat`도 느낌표도 아닌 변경으로 센다(명세 "번호", 명세 검토 S1)

### 노트

- [ ] 차례는 명세 "릴리스 노트"의 일곱(경고, 소개 글, 기능 단락, 올릴 때 할 일, 새 기능, 고친 것, 그 밖의 변경)이고 빈 묶음은 머리째 뺀다. 커밋 하나는 한 묶음에만 서고, 제목은 접두와 범위와 느낌표를 떼고 끝의 ` (#번호)`는 남긴다
- [ ] 싣는 범위는 출시 후보면 지난 판 뒤, 정식 판이면 지난 정식 판 뒤다. 기능 단락은 범위 안에서 더해진 `features/` 파일을 더해진 커밋의 차례로, 판을 내는 커밋의 글 그대로 싣고, 범위 밖에서 더해진 조각은 그 뒤에 고쳐졌어도 다시 싣지 않는다. 할 일은 느낌표 커밋이 더한 `upgrade/` 파일의 글을 그 제목 아래에 둔다
- [ ] 경고는 이미지마다의 Grype 결과(거르지 않은 JSON)에서 고칠 수 있는 Critical을 골라 CVE 번호와 꾸러미와 고친 판을 적는다. 그런 것이 없으면 경고 묶음이 빠진다(스토리 8, 명세 검토 S4)

### 묶음과 번호 태그 판정

- [ ] 묶음의 이름은 `agent-os-<판 번호>.tar.gz`(`v` 없음)이고, 풀면 같은 이름의 폴더 하나가 나와 그 안에 `deploy/standalone/`의 파일이 판 번호와 이미지 이름공간을 채운 채 든다. 채우는 자리를 틀에 어떻게 표시하는지는 이 티켓이 정해 도구의 독스트링에 적는다. 09가 그 꼴로 틀을 쓴다. 이 티켓의 시험은 임시 폴더의 틀로 묶음을 짓고 풀어 본다
- [ ] 번호 태그 판정의 "없다"는 조회 출력의 마지막 줄이 `: not found`로 끝날 때뿐이다. 종료 코드는 없음과 실패가 모두 1이라 가르지 못한다(release_mechanics README 2번). 같은 digest면 그대로 두고, 다른 digest면 거부하고, 조회가 실패하면 붙이지 않는다. 시험의 입력은 그 README 2번이 기록한 출력 문자열이다

### 시험과 규칙

- [ ] 실패하는 시험을 먼저 쓴다. 임시 git 저장소에 커밋과 태그를 만들어 넣는다(선례 `tests/tools/test_check_ticket.py`, `tests/tools/test_check_commit_msg.py`. 임시 디렉터리의 git은 `.claude/rules/tools.md`의 `REPO_LOCATION_VARS` 항목을 따른다). 사례는 명세 Testing Decisions 셋째의 번호 사례와 노트 사례 모두에 위의 셋(` (#번호)`가 붙어 72자를 넘는 `feat` 제목이 가운데 자리를 올림, 경고 묶음, 묶음 짓기)과 번호 태그 판정의 네 갈래를 더한 것이다
- [ ] 도구가 부르는 외부 명령(git)에는 호출마다 시간 제한을 둔다(`.claude/rules/tools.md`, `tools/check_instructions.py`의 `calls_without_timeout`)
- [ ] 의존성 없는 `python3`로 도구가 도는지 `.venv` 밖에서 한 번 본다(ci.yml의 ticket 잡이 커밋 검사를 그렇게 부른다)
- [ ] 검증 명령이 모두 초록이다
