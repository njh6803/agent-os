# 05: 노트 검사가 노트 조각의 빠뜨림과 모양을 병합 전에 막는다

**What to build:** 개발 세션이 기능의 마지막 티켓을 닫으며 기능 단락(`docs/release-notes/features/<slug>.md`)을 빠뜨리면 커밋이 막히고(스토리 35), PR 제목 접두에 느낌표를 붙였는데 할 일 파일(`docs/release-notes/upgrade/<이름>.md`)을 새로 더하지 않았으면 CI가 빨갛다(스토리 36). 티켓 PR의 서식은 "올릴 때 운영자가 손댈 것"을 묻는다(스토리 37의 앞 절). 느낌표를 붙이는 기준과 노트 조각을 쓰는 때는 운영 규약 문서에 선다.

검사 도구 하나가 pre-commit과 CI의 ticket 잡에서 돌고, PR 제목만 고쳤을 때는 작은 워크플로에서 (가)만 돈다. 리뷰 봇이 접두와 변경을 맞대는 줄(스토리 37의 뒤 절)은 06이 따로 낸다. claude-review의 워크플로를 고치는 PR은 리뷰가 건너뛰기 때문이다.

하네스를 고치는 티켓이다(PR 서식, 규약 문서, `implement` 스킬, 이슈 트래커 문서). 워크트리에서 하고 고친 스킬을 새 세션에서 불러 본다(작업 규약 3).

근거는 명세 "노트 검사", "느낌표의 기준과 그것을 보는 때", "릴리스 노트"의 조각 셋, "병합 절차와 규약 문서"의 `operations.md`·`issue-tracker.md` 항목, "커밋 제목이 서는 자리", Testing Decisions의 셋째(노트 검사 사례)다. 측정은 `.scratch/release-image/probes/notes_summary/README.md` 1번(400자)이다. 이 티켓의 "명세 검토"와 그 번호(S3, N4 같은 것)는 일지 `docs/journal/2026-11-14-1748-release-image-tickets.md`의 "명세 검토" 절을 가리킨다.

**Blocked by:** 04

**Status:** ready-for-agent

### 검사

- [ ] (가) 느낌표와 할 일: 커밋 검사의 `PATTERN`에 맞지 않는 PR 제목은 빨강이다. 길이 상한과 끝 마침표는 보지 않는다. 커밋 검사의 `PASS_PREFIXES`로 시작하는 제목은 받고 느낌표가 없는 제목으로 읽는다(명세 검토 S1). 접두에 느낌표가 있으면 그 PR이 `upgrade/` 파일을 하나 이상 새로 더하고 제품 경로를 하나 이상 고쳐야 한다. 느낌표가 없는데 `upgrade/` 파일을 새로 더했으면 빨강이다(있던 파일을 고치는 것은 된다). 제목 읽기와 제품 경로 목록은 04의 도구와 같은 자리를 쓴다
- [ ] (나) 기능 단락의 빠뜨림: 변경이 기능 계획에 `**끝:**` 줄을 더하거나 `features/<slug>.md`를 더하면, 그 기능의 티켓 파일을 고친 커밋 가운데(지금 보는 변경 포함) 제품 경로도 고친 것이 있는지 본다. 있으면 변경 뒤의 트리에 `features/<slug>.md`가 있어야 하고, 없으면 그 파일을 더하지 못한다. `features/` 파일의 이름은 있는 기능 계획의 slug여야 한다. 티켓 PR은 squash로 병합되고 그 변경에는 티켓 파일이 들어 있으므로(명세 (나)가 든 `tools/check_ticket.py` 판정 5) 기준 브랜치의 이력에서는 한 티켓의 제품 변경과 티켓 파일이 한 커밋에 있다. 한 PR 안에서 제품 변경과 끝 줄이 다른 커밋에 나뉘면 pre-commit은 놓칠 수 있고, CI가 PR의 변경 전체를 지금 보는 변경으로 보아 잡는다(PR 봇이 짚었다, 일지 2026-11-14-1748)
- [ ] (다) 모양: 조각은 모두 비어 있지 않고 `#`으로 시작하는 줄이 없다. 기능 단락은 빈 줄 없는 한 단락이고 줄바꿈을 뺀 글자 수가 400자 이하다. 소개 글의 이름은 `X.Y.Z.md`다. 할 일과 소개 글에는 길이 상한이 없다
- [ ] pre-commit은 스테이지된 변경을, CI는 PR의 변경 전체(base에서 머리까지)를 본다. 머리가 main이나 dev인 PR(출시 PR, 되돌려 합치기 PR)은 건너뛴다. (가)는 PR 제목이 필요하므로 CI에서만 보고, 제목은 ticket 잡에 환경 변수로 넘긴다(워크플로 식에 바로 넣지 않는다. zizmor의 template-injection)
- [ ] PR 제목만 고쳤을 때 (가)를 다시 보는 작은 워크플로를 따로 두고 `pull_request`의 `edited`에만 돌린다. dev와 main으로 가는 PR에서 돌고, 머리가 main이나 dev인 PR은 건너뛰며, 제목은 환경 변수로 넘긴다. 필수 검사에 넣지 않는다(제목을 고치지 않은 PR에서는 돌지 않아 결과가 오지 않기 때문이다). ci.yml에 `edited`를 더하지 않는다
- [ ] 실패하는 시험을 먼저 쓴다. 사례는 (가)(나)(다)의 빨강과 초록과 머리가 main이나 dev인 PR을 건너뛰는 것이고, 임시 git 저장소에서 돈다(선례 `tests/tools/test_check_ticket.py`). (나)는 지난 기능의 꼴(제품 변경을 담은 기능, 담지 않은 기능, 없는 slug의 `features/` 파일)과, 한 PR 안에서 제품 변경과 끝 줄을 다른 커밋에 두고 기능 단락을 빠뜨린 것이 CI의 범위(base에서 머리까지)에서 빨강인 것을 사례로 둔다
- [ ] 이 검사를 CLAUDE.md "검증 명령"의 게이트 목록과 수에 넣고, 옛 수를 grep해 살아 있는 문서의 잔존이 0인지 본다. 09도 게이트를 더하므로 먼저 병합된 쪽의 수에서 센다

### 규약 문서와 서식

- [ ] `docs/constitution/operations.md`에 느낌표의 기준(명세 "느낌표의 기준과 그것을 보는 때"의 첫 문단)과 노트 조각을 쓰는 때(조각 셋을 누가 언제 싣는지)를 적고, 문서 위치 절의 기록 목록에 "판으로 나간 노트 조각"을 더한다. 헌법 판을 올린다(`docs/constitution/README.md`. 올린 까닭은 일지에. 명세 검토 N4). 판을 매기기 전에 `tools/sibling_overlap.py`로 형제 브랜치가 먼저 가져간 판을 본다
