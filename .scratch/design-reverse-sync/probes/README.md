## 2026-10-21 결과

- `as-is`: 설치 0, 링크가 섰다. 타입 검사가 2로 끝났고, 출력 줄의 `tsc.codes`(타입 검사 출력에서 모은 오류 번호)가 TS2834·TS2835 둘뿐이었다. 표지로 단언한 것은 `contrast.ts`의 줄에 그 둘 가운데 하나가 있다는 것이고, 다른 번호가 없다는 것은 출력으로 봤다. `node`는 1로 끝났고 첫 import `"../testing"`을 폴더 import로 읽어 `ERR_UNSUPPORTED_DIR_IMPORT`를 냈다.
- `self-contained`: 설치 0, 링크가 섰다. 타입 검사 0, 오류 번호 없음. `node`가 0으로 끝나며 `{"pairs":43,"failures":43}`을 찍었다. 모든 쓰임새 토큰을 검정으로 준 실행이라 짝 43개가 모두 실패하는 것이 기대값이고, 계산이 실제로 돌았다는 표지다.
- 요약: 측정 2, 측정 아님 0, 기대와 다름 0. 종료 0.

두 갈래는 같은 설치(작업 공간 의존, `exports`가 `.ts` 파일을 바로 가리키는 경로, Node의 타입 지우기 실행)를 나누고, 다른 것은 내보낸 파일 안의 상대 import 유무뿐이다. 그래서 `as-is`의 실패를 `exports`가 `.ts`를 가리키는 탓이나 작업 공간 링크 탓으로 읽는 해석은 `self-contained`가 같은 설치로 초록인 것이 배제한다(양성 대조). 반대로 `self-contained`의 초록이 그 상대 import를 없앤 덕이라는 해석은, 같은 설치에서 상대 import만 남긴 `as-is`가 그 import의 자리에서 빨간 것이 받친다.

## 임시 아티팩트에서 손으로 본 것 (2026-10-22)

스크립트로 다시 낼 수 없는 도구와 브라우저 조작이다. 판 id, 바이트 수, sha256은 Claude Code의 Artifact 도구(`read`, `publish`)가 낸 값이다. 계정은 `claude auth status`로 본 claude.ai 로그인 계정이다(이름은 적지 않는다, `docs/agents/issue-tracker.md`의 계정 항목). 형식 목록에 Design System 형식(판 `1792632348-7c2b`, 계약 0.2.47)이 있어 그 형식으로 비공개 임시 아티팩트(`https://claude.ai/artifact/6iLQRxU1UBgyfd6GiUTXQy`, 지금은 지웠다)를 만들었다. 비공개라 사람도 같은 주인 계정으로 페이지를 열고 고쳤다. 만들기, 부탁 셋, 지우기는 사람의 승인을 받았고, 승인 밖의 넷째 부탁(아래 갈래 B의 저장)은 까닭과 건너뛸 길을 함께 적어 부탁했다(일지 `docs/journal/2026-10-26-11-build-tokens-json.md`).

- **올리기.** 만든 판 `1792670407-5cfc`에 색인(`project/design-system.json`, `editing` 키 없음, 522 B, `31cf8ed9…`), 이 티켓이 지은 `tokens.json`(40554 B, `191da4dc…`, 시험 자료 `uploaded-tokens.json`), 사람 몫만 든 README(238 B, `5813ed60…`)를 올려 판 `1792670467-a367`이 되었다. 지은 파일의 맞대는 값은 `29bb660d…`다.
- **고치지 않고 열기.** 열기 전에 다시 읽으니 판과 sha256 셋이 그대로였다. 사람이 고치지 않고 페이지를 열었다고 답한("열었다") 뒤 다시 읽으니, 판 `1792670467-a367`과 sha256 셋이 그대로였고 README에 생성 몫도 붙지 않았다. 그래서 여는 것만으로는 페이지가 저장하지 않는다고 본다(어림). 양성 대조는 아래 저장이다. 사람이 저장하자 판이 바뀌고, 페이지 꼴의 칸(`type.fonts` 등)이 없던 `tokens.json`이 페이지 꼴로 다시 쓰였으며, README에 생성 몫이 붙었다. 열기가 저장했다면 같은 표지가 보였을 것이다. 다만 페이지가 열렸다는 것은 사람의 답으로만 알고 세션이 따로 보지 않았으며, 한 번 본 것이다. 연 뒤 시간이 지나서 저장하는 길과 편집하러 다시 연 때 저장하는 길도 가르지 못했다. 아래 저장에서 사람이 고친 것은 둘인데 판이 셋 생겼고, 판마다 무엇이 바뀌었는지 보지 않아 하나가 다시 열기에서 났을 수 있다.
- **사람의 저장과 받은 꼴.** 사람이 페이지에서 `gray-50`의 녹청 라이트 값을 `#f4f8fb`에서 `#f0f4f8`로, `radius-m` 설명을 빈 칸에서 `버튼과 카드의 모서리`로 고쳐 저장했다. 그 사이 판 셋(3~5)이 생겼고, 판마다 무엇이 바뀌었는지는 보지 않았다. 페이지가 `api/tokens.md`, `manifest.json`, `tokens.css`를 새로 썼다(명세 "기록"이 해시와 비교에서 빼는 파일이다). 아래 `publish` 뒤의 판 `1792671359-792c`에서 받은 `tokens.json`(41375 B, `8ec4aab6…`, 시험 자료 `page-saved-tokens.json`)을 올린 파일과 맞대면 차이는 고친 둘뿐이고 맞대는 값은 `771d7b32…`다. 원문 꼴의 다른 점은 `tokens-json.test.ts`의 `pageRewrite`가 옮긴 것과 같다. 반투명 일곱의 문자열 값이 첫 테마의 객체가 되고, `type.fonts`에 빈 목록, 묶음에 빈 `note`, 스타일마다 `letterSpacing "0"`·`fontStyle "normal"`·`opticalSize null`·빈 `family`·빈 `sample`이 붙으며, `fontWeight`가 문자열이 된다. 키의 차례, 두 칸 들여쓰기, 끝 줄바꿈은 그대로다. 그래서 앞 커밋이 페이지 스크립트에서 옮긴 꼴과 다른 점이 없다. 명세 "페이지 스크립트를 읽은 것"이 든 셋(문자열 색 값을 첫 테마의 객체로, 빈 설명 칸, 소문자) 밖의 둘(기본값 채우기, 굵기의 문자열화)도 그 꼴에 이미 있었고 정규 꼴이 같은 값으로 읽어, 05가 바꿀 문법은 없다. 관찰한 형식 판은 위의 `1792632348-7c2b`이고, 문법과 페이지 스크립트를 읽은 판은 `1792564314-af13`이다. 이 해석의 양성 대조는 맞대기가 고친 둘을 실제로 낸 것이고, 페이지가 꼴을 다시 쓰지 않아 같다는 해석은 저장본에만 있는 빈 `type.fonts`가 배제한다(둘 다 `tokens-json.test.ts`의 받은 저장본 사례가 고정한다).
- **README의 생성 몫.** 같은 판에서 받은 README(1706 B, `fa615f74…`, 시험 자료 `page-saved-README.md`)는 올린 사람 몫 238바이트(끝 줄바꿈 포함)가 그대로 앞에 있고, 그 뒤에 `\n\n---\n\n`과 생성 몫("## Consuming this system (generated — do not edit)", 이어서 "## Index (generated — do not edit)")이 붙었다. 명세 "맞대는 것"의 주석이 든 생성 머리 가운데 "## Quick start"는 이 판에서 나오지 않았다. 색인은 sha256이 그대로였다(페이지가 `lastChange`를 고치지 않았다). 시험 자료는 Prettier가 빈 줄 둘을 하나로 줄여 `web/.prettierignore`에서 그 파일 하나만 뺐다.
- **`force` 없이 보낸 `publish`.** 갈래 둘을 봤다.
  - 갈래 A. 세션의 마지막 읽기는 판 `1792670467-a367`이었다. 사람이 위처럼 저장한 뒤, 다시 읽지 않고 그 판에 없던 새 파일 하나(`project/sync-probe.json`)를 `force` 없이 `publish`했다. 거부되지 않고 판 `1792671359-792c`가 되었다.
  - 갈래 B. 판 `1792671359-792c`를 다시 읽은 뒤, 사람이 `spacing-4` 설명에 `카드 안쪽 여백`을 넣어 저장했다. 다시 읽지 않고 사람이 고친 파일(`project/tokens.json`, 판 `1792671359-792c`의 내용 그대로)을 `force` 없이 `publish`하니 거부되었다. 도구 결과는 "Nothing was published or removed"로 시작해, 보낸 파일 가운데 세션이 마지막으로 본 내용과 지금 내용이 다른 파일이 있다고 적었다. 파일마다 "project/tokens.json: you last saw it at version 1792671359-792c; someone has since replaced it (version 1792671590-1318)"과 지금의 sha256(`620ee6b3…`)과 바이트 수(41395)를 들었고, 내용은 건네지 않았다. 안내는 그 파일을 다시 읽고 바뀐 것을 다시 얹어 보내라는 것이었다.
  - 해석. 검사가 없다는 해석은 B가, 보낸 파일이 무엇이든 아티팩트 판 하나로 견준다는 해석(세션이 마지막으로 읽은 뒤 아티팩트가 바뀌었으면 거부한다)은 A가 배제한다. A에서 아티팩트는 세션이 읽은 판보다 셋 앞서 있었는데도 지나갔다. 남는 해석은 둘이고 가르지 못했다. (1) 보낸 파일마다 이 세션이 그 파일을 마지막으로 본 판과 견준다(파일 단위). (2) 이미 있는 경로를 보낼 때만 세션이 마지막으로 읽은 아티팩트 판과 견준다. A는 새 경로를, B는 사람이 바꾼 경로를 보내 두 해석 모두 A의 통과와 B의 거부를 낸다. 가르는 갈래(다른 쪽이 다른 파일만 바꾼 뒤 이미 있는 경로를 보낸다)는 돌리지 않았다. 도구 결과의 문구가 파일마다 "you last saw it"을 들어 (1)에 가깝다고 보지만 문구로 고른 것이다. "Nothing was published or removed"는 파일 하나를 보낸 B의 문구이고, 여러 파일을 보낼 때 하나만 바뀌었으면 모두 막히는지는 보지 않았다.
- **지우기.** 사람이 확인한 뒤 지웠다. 시험 자료 셋은 지우기 전에 받아 도구가 낸 sha256과 같은 것을 확인했고, 그 sha256은 `tokens-json.test.ts`가 대 본다.

## 재지 못한 것 (임시 아티팩트)

- 두 세션 사이의 거부. 위에서 나중에 쓴 쪽은 페이지였다. 06의 `claim` 쓰기는 두 세션이 같은 기록 파일을 읽고 차례로 쓰는 경합이라, 늦게 쓴 세션이 거부된다는 것은 위 두 해석 모두에서 나오는 어림이다.
