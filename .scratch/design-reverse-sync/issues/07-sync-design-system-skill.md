# 07: `/sync-design-system` 스킬과 절차 옮기기 — 확인·들이기·올리기를 한 스킬이 하고, 흩어진 올리기 절차는 그 스킬을 가리킨다

**What to build:** 프로젝트 스킬 `/sync-design-system`이 선다. Claude도 부를 수 있고, 인자 `확인`은 확인만 하고 "찾았을 때"대로 멈추며, `올리기`는 확인 뒤 보내고, 인자 없이 부르거나 사람이 "디자인 시스템을 고쳤다"고 말하면 들이기다. 스킬은 Artifact 도구와 `gh`로 바깥 값을 받아 파일로 넘기고, 판단은 04·05·06의 스크립트 명령과 결정표 함수가 한다. 들이기는 다음 번호 `web-edit` 티켓을 쓰고 `claim`을 쓴 뒤 들이기 명령으로 디자인 토큰 CSS를 고치고, 묻는 것은 사람에게 묻는다. 올리기는 빌드가 필요하면 멈춰 사람에게 `/design-sync`를 한 번 쳐 달라고 부탁하고, 그 빌드 스크립트만 써서 바뀐 파일을 보내고 기록을 쓴다. 지금 올리기 절차를 든 문서 넷(`docs/agents/issue-tracker.md` 화면 디자인 절, `.design-sync/NOTES.md`의 돌리는 법, `.scratch/admin-style/design/screens-prompt.md`의 1단계, `.claude/rules/web-design.md`의 머리 문장)은 이 스킬을 가리키는 포인터로 줄인다(스토리 4·5·6·12·14·15·18·19·20·21·23·24·28·29·35).

근거는 `.scratch/design-reverse-sync/spec.md`의 "찾았을 때", "겹침", "거꾸로 동기화"의 "티켓"·"티켓의 절"과 그 2026-10-22 주석들, "토큰 밖 편집", "올리기" 전부, "멈춘 상태의 자리", "스킬", "바뀌는 문서와 스킬", "확인"의 "읽는 것"·"기록이 없거나 읽히지 않을 때"·"아티팩트를 읽지 못할 때", Testing Decisions의 "스킬과 문서"와 그 주석이다. 결정은 ADR 0025의 2026-10-21 이력("절차의 자리", "함께 고치는 것")이다.

04(들이기 명령)와 06(기록·확인·결정표)을 쓴다. 02가 낡은 판 `publish`의 거부를 손으로 본 결과를 읽어 `claim` 쓰기와 거부의 문장에 반영한다(거부되지 않았으면 PR 직전과 병합 직전의 다시 읽기가 유일한 방어라고 적는다). 이 티켓은 08을 막는다. 스킬과 절차 옮기기를 한 티켓에 두는 까닭은, 나누면 문서가 아직 없는 스킬을 가리키게 되기 때문이다(명세 Further Notes의 주석).

**02가 넘긴 것(2026-10-22).** 02가 적은 절차(세션이 읽은 뒤 사람이 페이지에서 저장하고, 앞서 읽은 판을 기준으로 다른 파일 하나를 `force` 없이 보낸다)로는 `publish`가 거부되지 않았다. 보낸 파일이 세션이 본 적 없는 새 경로였다. 사람이 바꾼 파일을 보내니 거부되었고, 도구 결과는 아무것도 올리지 않았다고 적고 바뀐 내용을 건네지 않은 채 그 파일을 다시 읽고 합쳐 보내라고 안내했다. 검사가 파일 단위인지, 이미 있는 경로에만 아티팩트 판을 견주는지는 가르지 못했다(06의 메모). 두 세션 사이에서도 늦은 쪽이 거부된다는 것은 그 관찰을 옮긴 어림이고(잰 것은 페이지가 나중에 쓴 경우다), 두 세션이 같은 새 파일을 함께 만들면 거부되지 않을 것으로 본다. 그 두 갈래는 명세 "겹침"의 PR 직전과 병합 직전의 다시 읽기가 막는다. 문구와 재지 못한 것은 `.scratch/design-reverse-sync/probes/README.md`의 "임시 아티팩트에서 손으로 본 것"이다.

**04가 넘긴 것(2026-10-27, 티켓 04 셀프 리뷰).** 들이기 명령의 답 파일과 묻는 목록에서 스킬이 맡는 몫이 셋이다. 꼴의 원천은 `web/tools/sync-design-system/import.ts`의 모듈 독스트링("답")과 `Asked`의 독스트링이다.

- 묻는 목록의 `conflict`(코드와 웹이 다르게 바꾼 자리)에서 `webReason`이 null이 아니면 스크립트가 웹 값을 옮기지 못하는 자리다(`choices`가 `code` 하나). 사람이 웹 값을 고르면 답 파일에 `web`을 적지 않고(`input` 오류다) 세션이 그 까닭의 묻는 것처럼 고친다. 대응 바꾸기면(`mapping`) 위 들이기 절의 대응과 덮기 문단대로다.
- 제안이 난 자리(웹만 바꾼 원색이 명암비에 걸린 자리)는 답 파일에서 `code`와 `suggested`만 받고 걸린 웹 값(`web`)은 받지 않는다(명세 "고를 때까지 걸린 값은 커밋하지 않고"). 스킬은 그 자리에 걸린 값을 그대로 쓰는 선택지를 내지 않는다.
- 코드와 웹이 다르게 바꾼 자리는 `web`을 고른 들이기에서야 명암비가 판정되어 제안이 난다. 그 들이기는 그 자리에 `web`·`code`·`suggested`를 모두 받고, `web`을 고른 채 끝나면 보고의 `contrast.failures`가 비지 않는다. 그래서 스킬은 답을 고친 들이기를 다시 돌린 뒤 `failures`가 빈 것을 보고서야 커밋한다.

**Blocked by:** 04, 06

**Status:** ready-for-agent

### 스킬의 머리와 차례

- [ ] **스킬을 쓰기 전에 Skill 도구로 `writing-for-agents`를 부른다**(`.claude/rules/agent-docs.md`)
- [ ] **`disable-model-invocation`을 두지 않는다.** 설명은 번들 스킬 `/design-sync`와 헷갈리지 않게 "Claude 아티팩트의 디자인 시스템"과 "들이기·올리기"를 말하고, 사람이 스킬 이름 없이 "디자인 시스템을 고쳤다"고만 말해도 불릴 낱말을 든다
- [ ] **"찾았을 때"를 스킬 안 한 절에 두고, 다른 절(들이기, 올리기)은 그 절을 부른다.** 결정표 함수가 낸 선택지를 AskUserQuestion으로 보이고, 선택지를 스킬 본문에 다시 풀어 쓰지 않는다
- [ ] **스킬이 쓰는 낱말은 명세 "낱말"대로다.** "올리기"는 디자인 시스템 올리기이고, 번들 스킬이 하던 일은 "번들 스킬의 업로드", 그 빌드 스크립트로 카드를 짓는 일은 "빌린 빌드"다. 명세는 "디자인 토큰"을 "토큰"으로 줄였지만, 스킬과 문서에서는 줄이지 않고 "디자인 토큰"으로 쓴다

### 확인

- [ ] **`read`의 `paths`로 두 번 받는다.** 먼저 `tokens.json`, 색인, 기록을 받고, 05가 낸 뒤의 경로를 한 번 더 받는다. 경로마다 도구가 없다는 까닭으로 읽지 못했는지 다른 까닭으로 읽지 못했는지를 파일로 적어 확인 명령에 넘긴다
- [ ] **지금 브랜치와 지금 코드에서 지은 `tokens.json`을 확인 명령에 넘긴다.** 확인이 들이는 중을 내면 `gh pr list --head <claim의 브랜치> --state all`의 결과를 병합 커밋까지 PR 상태 파일로 적고(실패하면 실패로 적는다) 결정표 함수에 넘긴다
- [ ] **아티팩트를 읽지 못하면 까닭(도구가 낸 문구와 `claude auth status`의 계정)을 보이고 결정표의 판단할 수 없음 선택지로 묻는다**(스토리 21)

### 들이기

- [ ] **확인부터 하고, 찾은 것을 그대로 들인다.** 다른 작업의 브랜치에서 불렸으면 브랜치를 바꾸지 않고 "먼저 들인다"처럼 새 세션을 연다. 작업 없는 자리(주 체크아웃의 main, 새 워크트리)면 그 세션이 티켓 브랜치를 딴다
- [ ] **들이기 티켓을 코드를 고치기 전에 쓴다.** 번호는 origin/main의 이 폴더 `issues/`에서 가장 큰 번호의 다음이고, 이름은 `NN-web-edit-<짧은 slug>`, 브랜치는 `feature/NN-web-edit-<짧은 slug>`다. 절은 찾은 웹 편집(토큰, 벌, 전과 후, 토큰 밖 파일), 사람이 고른 것(`> 사용자:` 인용), 판정 결과(걸린 짝과 고른 값), 수용 기준이다. 수용 기준에는 검증 명령, 사진을 다시 만들었는지, PR을 열기 직전과 병합 직전에 기록을 다시 읽어 `claim`이 자기 것인지 보는 것, 고친 디자인 토큰 CSS가 `pnpm -C web verify`의 포맷 검사를 지나는 것을 넣는다
- [ ] **`claim`을 기록 명령으로 짓고 `force` 없이 기록만 `publish`한 뒤 다시 읽는다.** 자기 것이 아니면 멈추고 그 브랜치를 사람에게 알린다. 거부되면 합치지 않고 확인부터 다시 한다. 병합된 남의 `claim`이면 이어받고, 사람이 지우기를 고른 남의 `claim`만 덮는다
- [ ] **들이기 명령에 기준본을 넘긴다.** `claim`이 이어받은 기준본을 들면 그것이고, 아니면 기록의 기준본이다. 이어받기를 시작할 때는 확인 명령이 낸 이어받을 기준본을 기록 명령에 넘겨 `claim`에 넣은 뒤 그것을 넘긴다. 압축·인계 뒤나 "웹에서 다시 고친다" 뒤에 이을 때도 `claim`의 기준본을 넘기고, `claim`의 사본을 기준본으로 넘기지 않는다. 들이기 명령의 묻는 목록은 사람에게 묻고, 사람이 들이기로 고른 묻는 것(대응 바꾸기 등)은 `.claude/rules/web-design.md`의 대응과 덮기 문단대로 세션이 고친다. 토큰 밖 편집은 "저장소 파일에 옮긴다"와 "버린다"로 묻는다(스토리 12)
- [ ] **"웹에서 다시 고친다"를 고르면** 사람이 다시 고친 뒤 확인을 다시 돌려 자기 `claim`의 사본과 해시를 새로 쓴다
- [ ] **크기를 바꾸면 그 크기를 박아 둔 스토리 단언도 같은 PR에서 고치고, 기본 테마(녹청)가 쓰는 값을 바꾸면 `pnpm -C web visual:update`로 정답 사진을 다시 만들어 PR 본문에 적는다**(스토리 13)
- [ ] **PR을 열기 직전에 origin/main의 이 폴더를 다시 보고, 같은 번호가 먼저 들어왔으면 티켓 파일과 브랜치 이름을 옮기고 같은 단계에서 `claim`을 새 브랜치와 티켓 경로로 다시 쓴다.** 차례는 브랜치 이름을 먼저 바꾸고 `claim`을 다시 쓰는 것이다(명세 "자기 `claim`"의 2026-10-22 주석)
- [ ] **병합한 뒤 이어서 올리기를 한다.** 그 올리기가 `claim`을 비운다

### 올리기

- [ ] **확인을 먼저 하고, 웹 편집이 없거나 사람이 고른 뒤에 보낸다.** 화면 작업에서 "계속한다"를 골랐어도 돈다
- [ ] **origin/main을 체크아웃한 자리에서 한다.** 기록의 커밋이 지금 HEAD의 조상인지 보아 옛 코드로 되돌리지 않는다. 기록이 없는 첫 올리기는 색인 `lastChange`의 `via`가 든 커밋으로 보고, `via`에 커밋이 없으면 멈추고 묻는다. `via`가 부분 올리기(`agent-os 부분 main@<짧은 SHA>`)면 그 커밋 뒤로 바뀐 것으로 보아 빌드가 필요하다(`docs/agents/issue-tracker.md` 화면 디자인 절). 지금 색인의 `via`가 그 꼴이다(셀프 리뷰가 판 `1792564314-af13`의 색인을 받아 손으로 봤다)
- [ ] **병합된 `claim`을 보내는 올리기는 PR 상태 파일의 병합 커밋이 지금 HEAD의 조상인지 먼저 본다.** 아니면 보내지 않고 `git fetch` 뒤 origin/main을 다시 체크아웃해 처음부터 한다. 병합 전의 HEAD로 보내면 `claim`이 든 파일을 옛 값으로 보내고 `claim`까지 비운다(명세 "병합됐으면"의 2026-10-22 주석)
- [ ] **보낼 것과 빌드가 필요한지는 05·06의 함수가 낸다.** 스킬은 `git diff --name-only <기록의 커밋> HEAD`와 되돌릴 파일·웹에서 더한 경로(사람이 "덮어쓴다"를 고른 확인이 찾은 것, 병합된 `claim`이 든 것)를 넘긴다
- [ ] **빌드가 필요하면 멈추고 명세 "사람이 친 턴"의 부탁 문구로 부탁한 뒤 턴을 끝낸다.** 부탁에는 "치면 업로드는 하지 않고 빌드 스크립트만 써서 `/sync-design-system`의 올리기를 잇는다"를 함께 적는다. 사람이 친 턴에서는 번들 스킬 본문의 업로드(`DesignSync`)를 하지 않고 빌드 스크립트만 쓴다. 빌린 빌드의 세부(변환기 인자, 복사, 검사)는 `.design-sync/NOTES.md`의 그 절을 가리킨다
- [ ] **빌드한 커밋을 빌드 산출 곁에 남긴다.** 빌드한 뒤 끊겨 다시 들어온 올리기는 그 커밋이 지금 HEAD와 같으면 다시 부탁하지 않고 그 산출을 쓰고, 다르거나 없으면 낡은 산출을 쓰지 않고 다시 부탁한다
- [ ] **풀린 폴더를 찾는다.** 스킬 본문 앞에 실린 "Base directory" 줄을 먼저 보고, 없으면 `claude --version`의 판으로 `bundled-skills/<판>/` 아래 `design-sync` 폴더를 찾으며, 그 판의 폴더가 없으면 멈추고 묻는다
- [ ] **보내기 직전에 확인을 다시 한다.** 처음 확인과 결과가 달라졌으면 보내지 않고 "찾았을 때"로 돌아간다. `publish`가 거부되면 Artifact 도구의 안내(합쳐 다시 보낸다)를 따르지 않고 멈추고 확인부터 다시 한다
- [ ] **한 호출에 들지 않으면(255개와 16 MiB 가운데 작은 쪽) 첫 호출이 `pending`이 든 기록을, 마지막 호출이 `pending` 없는 기록을 함께 보낸다.** 마지막 호출에서 색인의 `lastChange` 넷을 새로 적는다
- [ ] **기록이 없으면 빌드 산출을 아티팩트의 sha256과 맞대 보낼 것을 고른다**(첫 올리기와 편집이 꺼진 동안 기록을 잃은 때)

### 멈춘 상태

- [ ] **"고를 때까지 기다림"과 "`/design-sync`를 쳐 주기를 기다림"은 그 턴의 질문과 부탁이다.** 답하기 전에 인계하면 `next-session`의 "이어받을 상태"에 그 상태와 찾은 것의 요약(또는 올리기의 단계와 "사람이 `/design-sync`를 치면 빌드 스크립트만 쓴다")을 적으라고 스킬이 말한다
- [ ] **"먼저 들인다"를 고른 화면 세션은 브랜치를 바꾸지 않고 들이기를 `next-session` 꼴의 지시문으로 내어 `open-session`으로 새 세션을 연다.** 그 세션의 일지와 "이어받을 상태"에 기다리는 들이기의 브랜치를 적고, 병합 뒤 main을 합쳐 잇는다. "계속한다"는 일지에 `> 사용자:` 인용으로 남기고 "이어받을 상태"에 적는다
