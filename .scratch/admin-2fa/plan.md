# admin-2fa: 관리 화면의 로그인에 2단계 인증을 더해, 비밀번호가 새도 그것만으로는 들어오지 못하게 한다.
**슬라이스:** 10
**Blocked by:** admin-login, pilot-release

관리 화면 로그인의 2단계 인증. admin-login의 설계 인터뷰에서 사용자가 2단계 인증(비밀번호에 더해 휴대폰 인증 앱의 6자리 코드를 넣는 것)을 "0.1 판에는 넣지 않음"으로 골랐고, 그 선택지의 설명이 뒤의 기능으로 전체 계획에 새 행을 세운다고 적어 이 행이 섰다(일지 2026-11-14-2152 "2단계 인증(비밀번호에 더해 휴대폰 인증 앱의 6자리 코드를 넣는 것)을 0.1 판에 넣을까요?", ADR 0062 Considered Options의 2단계 인증 항목). 0.1 판에서 인터넷에 기본으로 열린 로그인 화면을 지키는 것은 8자 규칙의 비밀번호와 잠금뿐이고(ADR 0062 Consequences "한계"), 그동안은 배포 안내가 방화벽으로 관리 화면용 포트를 좁히기를 권한다. 사용자가 고른 8자 규칙은, 그 인터뷰의 조사가 옮긴 바로는 NIST와 OWASP가 2단계 인증 없이 쓰기에 짧다고 보는 길이다(같은 일지 "비밀번호에 어떤 규칙을 둘까요?"의 선택지 설명. 이 행의 설계가 원문에 다시 댄다). 설계 인터뷰가 먼저 볼 것: 수단을 고른다(인증 앱의 시간 기반 코드, 패스키, 복구 코드를 함께 둘지). 누구에게 요구할지를 정한다(시스템 관리자만, 모든 운영자 계정, 배포 설정으로 고르기, 계정마다 스스로 켜기). 기기를 잃은 사람이 다시 들어오는 길을 정한다(복구 코드, 시스템 관리자가 풀어 줌, 시스템 관리자 자신은 서버에서 치는 명령. ADR 0062의 첫 계정을 만드는 명령과 같은 길인지). 코드를 만드는 비밀 값을 데이터베이스에 두는 모양을 정한다(백업에 함께 담긴다. ADR 0062가 서명 키에서 받아들인 것과 같은 한계다). 틀린 코드를 잠금의 틀린 횟수에 세는지, 비밀번호 링크로 비밀번호를 다시 정한 계정의 2단계가 어떻게 되는지, 2단계를 지난 뒤의 운영자 로그인 상태가 지금의 쿠키 둘과 어떻게 이어지는지를 정한다. 스크립트와 테스트와 e2e의 로그인을 정한다. ADR 0062는 프로그램용 열쇠를 두지 않아 스크립트도 운영자 계정으로 로그인하므로, 2단계가 켜진 배포에서 스크립트가 로그인하는 길이 걸려 있다. 새 의존성이 있으면 ADR로 남긴다. 수락: 시험 환경에서 2단계 인증이 켜진 운영자 계정은 맞는 비밀번호만으로는 관리 화면에 들어오지 못하고 코드까지 맞아야 들어오며, 기기를 잃은 운영자가 설계가 정한 길로 다시 들어온다
