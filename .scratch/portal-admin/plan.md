# portal-admin: 사이트마다의 위젯 설정을 위젯 쪽 서버의 데이터베이스에 두고 운영자가 위젯 설정 관리 화면에서 등록해, 파일을 열지 않고 위젯이 보일 것을 바꾼다.
**슬라이스:** 9
**Blocked by:** pilot-portal

위젯 설정 관리. 위젯 설정(`CONTEXT.md`)을 드는 위젯 쪽 서버의 데이터베이스와, 운영자가 그것을 등록하는 위젯 설정 관리 화면이다. 그 화면은 위젯 쪽의 것이고 `CONTEXT.md`의 관리 화면(Agent OS의 웹 앱)과 다른 것이라 이 계획은 그 말로 적지 않는다(ADR 0061). 행의 이름은 세울 때의 것이다. 이 행은 사용자가 pilot-portal 설계 인터뷰에서 다시 꺼낸 요구(사이트마다 위젯을 설정하는 관리 화면이 있어야 한다, 일지 2026-11-09-1410의 "사용자가 앞서 말한 요구를 다시 꺼냄")에서, pilot-portal이 "설정은 파일로, 미리보기까지 지금"으로 범위를 자르며 선 것이다(ADR 0050 Consequences "다른 행"). 그때는 위젯 미리보기 페이지 설정 파일을 고치는 화면이었고 제품 1.0 묶음(슬라이스 10)이었다. 2026-11-14의 설계 인터뷰(일지 2026-11-13-1813)가 이 행을 고쳐 세웠다. 사용자가 로그인 주소와 고지의 글 같은 달라지지 않는 값을 "위젯 관리자 페이지에서 위젯 설정으로 등록"하자고 했고, 그 값을 드는 자리를 묻는 질문에 "위젯 서버의 데이터베이스"라고 답했으며, 짓는 때를 묻는 질문에 "0.1 판에 넣기"를 골랐다. 그래서 이 행은 0.1 판의 행이 됐고(ADR 0046 이력 2026-11-14) pilot-release가 이 행을 기다리며, 위젯이 위젯 설정을 받아 오는 일을 맡는 widget-login-state가 이 행을 기다린다.

ADR 0061이 이 행에 정해 둔 것은 방향이다. 위젯 설정은 사이트마다 위젯 쪽 서버가 데이터베이스에 들고, 운영자가 위젯 설정 관리 화면에서 등록하며, 위젯은 임베드 속성(URL 방식은 주소)에 적힌 사이트의 이름으로 뜰 때 받아 온다. 임베드 속성에 따로 적은 값이 위젯 설정보다 앞선다. 위젯은 사이트 토큰을 받기 전에도 고지와 로그인 단추를 그려야 하므로 위젯 설정을 토큰 없이 받아 오고, 그래서 위젯 설정에는 비밀을 두지 않는다. `serve`, Agent OS의 관리 화면과 관리 API, 사이트 파일, `openapi.json`은 위젯 설정을 모른다(ADR 0047의 방향 그대로다). 0.1 판에서 등록하는 것은 글(위젯의 이름, 소개 한 줄, 입력창 안내 문구, 고지의 짧은 줄과 전문, 로그인 주소, 로그아웃 주소)과 고르는 값(에이전트, 색 테마 넷 가운데 하나, 처음 밝기, 로그인 시간이 끝났을 때 알림의 모양, 로그아웃을 부르는 방법)이다(ADR 0061 결정 "0.1 판에서 등록하는 것"). 그림 올리기와 자유 색은 widget-appearance가 0.1 판 뒤에 맡는다.

이 행에는 아직 설계가 없다. ADR 0061이 이 행의 설계 인터뷰에 넘긴 것(결정 "이 ADR이 정하지 않는 것")은 아래다. 인터뷰는 사실을 재며 정한다.

- 위젯 쪽 서버를 어느 프로그램으로 세울지. 위젯 앱에는 서버 코드를 둘 수 없다(워크스페이스가 Next의 서버 파일을 금지하고 ADR 0024가 그 예외를 거부했다). 위젯이 요청 때마다 값을 읽는 실험 판의 측정은 `.scratch/release-image/probes/widget_runtime/README.md`에 있다(Windows에서만 돌았다. 그 판은 Next 서버 파일 금지와 `app/` 경계의 ESLint 규칙에 걸린다).
- 데이터베이스의 종류. 이 저장소에는 지금 데이터베이스가 없어(`docs/constitution/tech.md`) 스택을 바꾸는 결정이고 ADR이 든다.
- 위젯 설정 관리 화면에 누가 들어오는지. 위젯 설정의 로그인 주소와 로그아웃 주소는 위젯이 최종 사용자의 브라우저에서 열거나 부르는 주소라, 그것을 바꿀 수 있는 사람과 주소의 검사를 먼저 정한다(ADR 0061 Consequences "신뢰와 노출").
- 위젯 설정 관리 화면을 용어집에 어떤 이름으로 올릴지. `CONTEXT.md`의 관리 화면은 Agent OS의 웹 앱이고 그 로그인은 admin-login 행의 것이라, 섞이지 않는 이름을 정한다(ADR 0061 머리 문단).
- 맞춤 항목의 목록. 0.1 판의 범위는 위에 적었고, 사용자가 추천해 달라고 한 후보는 일지 2026-11-13-1813 "인터뷰 라운드 4"에 있다.
- 위젯이 위젯 설정을 받아 오는 주소와 답의 모양. widget-login-state가 이것을 기다린다.
- 백업과 복원, 배포 꾸러미에 넣는 일. 서버와 데이터베이스가 늘면 release-image의 단독 compose, deploy-package의 참조 배포, ops-backup-upgrade의 절차가 바뀌므로, 인터뷰가 정한 모양을 그 세 행의 기능 계획에 넘긴다.
- 위젯 미리보기 페이지 설정이 지금 드는 값(이름, 소개, 색, 밝기, 고지)을 위젯 설정으로 옮기는 방법과 처음 띄웠을 때의 값. 위젯 미리보기 페이지가 담는 사이트의 로그인 주소와 로그아웃 주소(그 페이지의 끝점이다, ADR 0059)를 운영자가 손으로 등록하는지도 여기에 든다. 위젯 미리보기 페이지는 모르는 칸을 거부하므로(pilot-portal 명세 "위젯 미리보기 페이지 설정"의 2026-11-10 주석) 그 파일의 칸을 줄이면 `schema_version`을 어떻게 할지도 함께 본다.
- 위젯 미리보기 페이지가 사이트의 고지 글과 무관하게 고지 전문에 넣는 문장 둘(익명 식별자를 둔다는 문장, 질문이 로그인한 계정과 함께 기록된다는 문장)을 누가 보장하는지.
- 다크 모드 스위치를 숨기는 값을 둘지. ADR 0061의 "늘 사람이 고르기"와 부딪히므로 사용자에게 다시 묻는다.

이 행이 고쳐 서기 전에 넘겨받은 것은 아래다. 0.1 판에 넣을지는 설계 인터뷰가 사용자에게 다시 묻는다. ADR 0061은 이 넷을 0.1 판에 넣는다고도 뺀다고도 정하지 않았다(그 ADR의 Consequences "다른 행").

- 위젯 미리보기 페이지 설정(`CONTEXT.md`. TOML, 사이트 여럿의 목록. ADR 0050. 칸은 pilot-portal 명세 "위젯 미리보기 페이지 설정")을 화면에서 고치는 일. 처음 선 때의 범위다. 위젯의 모양과 고지가 위젯 설정으로 옮겨 간 뒤 그 파일에 남는 것(사이트의 목록, 보증 모드, 로그인 서버 항목, 보고서 링크)을 화면에서 고칠지 본다.
- 사이트 파일의 허용 출처와 요청 글자 수 상한을 화면에서 바꾸는 일. release-image의 설계 인터뷰에서 사용자가 더한 요구다(일지 2026-11-11-1532 "위젯 질문에 사용자가 되물었다"). 두 값은 사이트 파일의 것이고, 그 파일을 읽는 세 곳을 함께 고쳐야 바꾼 값이 다시 띄우지 않고 듣는다. `serve`는 사이트 파일을 시작할 때 한 번 읽고(변경 시각으로 다시 읽기는 ADR 0023의 2026-11-04 이력이 정했을 뿐 구현되지 않았다), 위젯 미리보기 페이지도 시작 때 한 번 읽으며(ADR 0050), 위젯은 빌드에 굳는다(ADR 0024). 그래서 release-image의 위젯 컨테이너는 뜰 때 사이트 파일로 빌드하고, 이 일이 나오기 전까지 운영자는 사이트 파일을 직접 고친 뒤 세 컨테이너를 다시 띄운다(ADR 0056 결정 "위젯 이미지"와 "사이트 파일을 고치면"). 사용자는 위젯이 그 값을 실행 중에 읽도록 고치는 일을 이 행을 만들 때 함께 하기로 골랐다. 위젯이 값을 `serve`에 물어 받아 오는 길은 재지 않았다. 사이트 파일은 채널의 신뢰 설정이라(`CONTEXT.md`) 위젯 쪽의 화면이 그것을 고쳐도 되는지, ADR 0047의 경계와 어떻게 맞추는지도 설계 인터뷰가 본다.
- 로그인 방식을 화면에서 고르는 일. portal-login의 설계가 넘겼다(2026-11-12). 사용자가 로그인 방식을 화면에서 고르기를 물었고, 0.1 판은 설정 파일로 정하되 화면에서 고르는 일은 이 행이 맡기로 했다(일지 2026-11-12-1937 라운드 2). 그래서 화면이 고치는 것에 로그인 서버 항목(`CONTEXT.md`. 방식, 주소, 식별자로 쓸 주장, 유지 시간의 기준, 로그아웃 방식)과 사이트가 가리키는 항목이 든다(ADR 0059 결정 "로그인 서버 항목"). 클라이언트 비밀은 설정이 파일 경로로 가리키는 값이라 화면이 그 값을 받아 쓸지는 설계 인터뷰가 본다. 이 일을 넘겨받을 때 이 행은 제품 1.0 묶음(슬라이스 10)이라 0.1 판의 portal-login보다 뒤였다. 2026-11-14에 순서가 바뀌어 이 행이 portal-login보다 앞이므로(widget-login-state가 이 행을, portal-login이 widget-login-state를 기다린다), 이 행이 돌 때 로그인 서버 항목은 아직 코드에 없다. 이 일을 portal-login 뒤의 어느 행의 어느 자리에 둘지도 설계 인터뷰가 정한다.
- release-image 명세가 넘긴 것(2026-11-13, `.scratch/release-image/spec.md`의 Out of Scope): 이 행이 위젯이 사이트 파일을 실행 중에 읽게 바꾸면, release-image의 위젯 이미지가 뜰 때마다 하는 빌드가 필요 없어진다. 그때 이 행이 함께 고칠 것은 위젯 이미지(뜰 때의 빌드, 워크스페이스 전체 의존성, 읽기 전용이 아닌 루트), 단독 compose에서 위젯 상태 확인의 시작 유예(300초), 배포 안내의 메모리 문장과 사이트 파일을 고친 뒤의 절차다(그 명세 "이미지의 구성"의 위젯과 상태 확인, "배포 안내"). 이 행의 `**Blocked by:**`에는 release-image가 없어 이 행이 먼저 돌 수 있다. 그러면 위의 것은 아직 없으므로, 그 사실을 release-image 기능 계획 본문에 적어 위젯 이미지를 짓는 티켓이 보게 한다.

수락: 시험 환경에서 운영자가 위젯 설정 관리 화면에서 사이트 하나의 위젯 이름과 고지의 글을 등록하면, 그 사이트의 이름으로 위젯 설정을 받아 온 답에 등록한 값이 실리고, 띄운 것을 내렸다 올려도 그 값이 남는 테스트가 통과한다. 등록한 값으로 위젯이 그려지는 것은 widget-login-state의 수락이 본다
