# portal-admin 명세: 운영자가 위젯 관리 화면에서 사이트마다의 위젯 설정과 위젯 테스트 페이지 설정을 등록하고, 저장 전에 미리보기로 보며, 위젯 테스트 페이지는 로그인한 사람만 연다

Status: ready-for-agent

슬라이스 9(`portal-admin`). 설계는 ADR 0064(설계 인터뷰의 일지 2026-11-15-1312)와 ADR 0065(일지 2026-11-16-0025)가, 화면은 `/ui-design portal-admin`(같은 일지 2026-11-16-0025, 화면은 `.scratch/portal-admin/design/`, 사람이 고른 것과 명세에 넘긴 제안은 그 `README.md`)이 정했다. 이 명세는 그 결정을 바꾸지 않고 꼴, 규칙, 화면의 빈 자리, 시험을 채운다. ADR 본문에서 포인터를 단 자리는 열하나이고 아래 "이력" 문단에 있다. 이 명세는 `/to-spec`으로 새 세션에서 썼고 설계 인터뷰를 다시 열지 않았다(일지 2026-11-16-1705). 명세를 쓰기 전에 사람에게 물은 넷(예시 질문의 모양, 고지 재확인, 새 아이콘, 시험의 이음매)의 답은 그 일지의 "사용자에게 물은 것과 답"에 글자 그대로 있다. 셀프 리뷰 뒤에 하나를 더 물었고(미리보기의 높이를 넘는 글을 다루는 법) 그 답은 같은 일지의 "셀프 리뷰 뒤에 물은 것과 답"에 있다. 용어는 `CONTEXT.md`의 운영자, 운영자 계정, 관리 화면, 최종 사용자, 사이트, 사이트 파일, 사이트 토큰, 보증 모드, 익명 모드, 로그인 모드, 위젯, 위젯 설정, 위젯 관리 서버, 위젯 관리 화면, 위젯 테스트 페이지, 위젯 테스트 페이지 설정, 미리보기, 고지, 고지 확인, 디자인 시스템, 쓰임새 토큰, 테마, 모드를 쓴다. 위젯 관리 화면은 "관리 화면"으로 줄이지 않는다. 관리 화면은 Agent OS의 웹 앱이다. 사이트를 저장할 때마다 하나씩 오르는 수는 "저장 번호"라 부른다(같은 일지 "용어"). 기준 커밋은 `02dcfe97d`(2026-11-16, `origin/dev`)이고 코드를 읽은 자리는 그 커밋의 것이다. 명세를 쓰기 전에 화면 아티팩트의 화면 파일 스물하나를 그 커밋의 것과 대 보았고 내용이 다른 파일은 없었다(웹 편집 확인, 같은 일지 "읽은 것과 찾은 것"). 이 명세를 쓰는 동안 widget-login-state의 명세(PR 593)가 dev에 들어왔고, 병합된 글에 다시 댔다(Further Notes).

**넘겨받은 것은 열여덟이고 절 제목의 괄호에 "넘겨받았다"로 표시한다.** ADR 0064와 ADR 0065의 결정과 Consequences, 기능 계획(`.scratch/portal-admin/plan.md`), 확정한 화면, widget-login-state의 명세가 정해서 넘긴 것이다. (1) 프로그램 사이의 길. (2) 위젯 관리 화면의 틀과 주소. (3) 로그인하지 않았거나 로그인 시간이 끝났을 때. (4) 사이트 목록. (5) 바뀜, 저장 띠, 떠날 때. (6) 미리보기. (7) 미리보기를 그리는 부품. (8) 사이트 등록과 고지 전문의 처음 값. (9) 주소의 검사. (10) 저장 경로. (11) 저장할 때의 검사. (12) 바꾼 기록. (13) 로그인 확인. (14) 위젯 테스트 페이지 설정을 데이터베이스로. (15) 사이트마다의 검사와 닫힌 사이트. (16) 위젯 테스트 페이지의 운영자 문. (17) 예시 질문의 모양을 답에 싣는다. (18) 포트와 compose. 어느 결정이나 화면에서 넘겨받았는지는 절마다 본문이 ADR의 결정 이름이나 완성 화면의 파일 이름으로 적는다.

**사용자가 고른 것은 여섯이고 절 제목의 괄호에 "사용자가 골랐다"로 표시한다**(첫째는 화면 작업의 일지 2026-11-16-0025와 디자인 `README.md`, 다음 넷은 일지 2026-11-16-1705 "사용자에게 물은 것과 답", 여섯째는 같은 일지 "셀프 리뷰 뒤에 물은 것과 답"). 사이트 하나의 화면은 탭과 저장 단추 하나의 짜임이다. 예시 질문의 모양은 "0.1 판에 고르는 칸을 넣기"다. 운영자가 고지를 고쳐도 이미 확인한 브라우저에는 "다시 띄우지 않기"다. 확정한 화면이 그려 쓴 새 아이콘 셋은 "셋 다 더하기"다. 시험의 이음매는 "브라우저로 한 번 끝까지, 규칙은 서버 시험"이다. 미리보기의 높이를 넘는 글은 "넘친 글은 테스트 페이지에서 보기"다. 뒤의 다섯은 모두 추천한 안이었다.

**스물셋은 명세가 넘겨받은 것 안에서 스스로 정했고 각 절 제목의 괄호에 "명세가 정했다"로 표시한다(괄호는 한 항목을 더 잘게 나눠 적기도 한다).** 위젯 관리 서버가 위젯 테스트 페이지의 서버에 묻는 길, 위젯 관리 화면의 주소와 틀을 두는 자리, 로그인을 다시 확인하는 때와 양식을 지키는 것, 사이트 목록의 차례와 빈 칸의 표시, 칸마다의 꼴과 상한과 비웠을 때, 바뀜을 세는 법과 그림에 없는 상태, 보는 상태마다의 입력과 밝기 단추의 규칙, 공유 패키지의 범위와 그 안의 규칙과 스토리와 사진의 자리와 미리보기를 가리는 법, 고지 전문의 처음 값의 문장과 넣는 때와 그 문장을 얻는 자리, 사이트 지우기, 주소의 검사를 사용자 정보 자리와 쿼리와 보고서 링크까지 넓힌 것, 저장 경로의 가름과 중계가 넘기는 경로와 저장 번호와 거절의 꼴, 저장할 때의 검사가 내는 까닭의 가름과 동시에 온 저장에서 겹침을 막는 법, 바꾼 기록의 한 줄이 담는 것과 지운 사이트의 기록, 로그인 확인에서 갱신을 일으키는 쪽과 전하고 되돌리는 것의 꼴과 부르는 클라이언트와 답의 가름, 위젯 테스트 페이지의 서버가 설정을 받아 오는 때와 차례와 제한 시간과 받아 오지 못했을 때의 답, 닫힌 사이트에 내는 답과 로그를 남기는 때, 닫힌 사이트를 알리는 길, 운영자 문의 끝점의 가름과 사이트 고르기의 글과 띠의 스위치, 포트의 번호와 프로그램마다 받는 값, 선행 기능에 기대는 것, 문구, 시험의 사례다.

**먼저 확인한 것은 셋이다.** ADR 0064와 ADR 0065의 Consequences "재지 않은 것"이 이 명세에 넘긴 물음 셋을 명세를 쓰며 확인했다(색인은 `.scratch/portal-admin/probes/README.md`). 운영자의 로그인 쿠키를 다른 포트의 서버가 Agent OS에 전해 로그인을 이어 주는 흐름은 `.scratch/portal-admin/probes/login_relay/`가, 위젯 테스트 페이지의 서버가 요청마다 위젯 관리 서버에 묻는 것은 `.scratch/portal-admin/probes/settings_fetch/`가 다시 낸다(쟀다). 위젯의 화면 부품을 공유 패키지로 옮기는 것과 미리보기를 가리는 법은 `.scratch/portal-admin/probes/shared_widget_parts/`의 패치와 명령으로 본 것이다(손으로 봤다). Agent OS의 로그인 경로(admin-login)와 위젯 관리 서버(widget-admin-server)가 아직 없어 앞의 둘은 그 서버들을 대역으로 세웠다. 본문의 "쟀다", "손으로 봤다", "코드를 읽었다", "어림"은 `docs/agents/issue-tracker.md`의 "프로브와 근거"가 가른 종류다.

**이력은 넷이다.** 넷 다 이 명세와 같은 커밋에서 썼고 날짜는 2026-11-16이다(`.claude/rules/adr.md`). 첫째는 ADR 0064의 "위젯 설정에 예시 질문의 모양을 고르는 값으로 더한다"이고, 결정 "0.1 판에서 등록하는 것"의 첫 문장에 포인터를 이어 단다. 둘째는 ADR 0064의 "등록하는 주소 넷에 같은 검사를 걸어 사용자 정보 자리를 받지 않고, 위젯 테스트 페이지의 설정 파일에 시작 값 둘을 더한다"이고, 두 자리에 포인터를 단다. 결정 "주소의 검사"의 둘째 문장과 결정 "위젯 미리보기 페이지 설정"의 시작 값 문장이다. 셋째는 ADR 0064의 "로그인 시간이 끝났을 때의 갱신은 화면이 부르고, 위젯 테스트 페이지의 서버는 설정을 요청마다 받아 와 기억하지 않는다"이고, 다섯 자리에 포인터를 단다. 결정 "로그인"의 두 자리(쿠키를 브라우저에 되돌리는 문장, 명세가 먼저 확인한다는 끝 문장), 결정 "위젯 미리보기 페이지 설정"의 짧게 기억하는 문장, Consequences "재지 않은 것"의 두 자리다. 넷째는 ADR 0065의 "위젯 테스트 페이지의 서버도 화면이 부른 갱신만 전하고, 미리보기는 옮긴 부품을 고치지 않고 감싼 요소로 가린다"이고, 세 자리에 포인터를 단다. 결정 "미리보기"의 옮기는 일을 재 보지 않았다는 문장, 결정 "위젯 테스트 페이지"의 운영자 계정 항목에서 쿠키를 전해 확인하는 방식을 적은 두 문장(이어진 두 문장이라 포인터는 하나다), Consequences "재지 않은 것"이다.

## Problem Statement

운영자는 지금 위젯이 보일 것을 바꾸려면 서버의 파일을 고치고 프로그램을 다시 띄워야 한다. 위젯의 이름, 소개, 색, 고지의 글, 사이트의 목록이 모두 위젯 테스트 페이지 설정 파일에 있고, 그 파일은 서버에 들어갈 수 있는 사람만 고친다. 문구 하나를 바꾸는 일에도 서버 접속과 다시 띄우기가 든다.

widget-admin-server와 widget-login-state가 끝나면 위젯은 위젯 관리 서버의 데이터베이스에 든 위젯 설정으로 그려진다. 그런데 그 값을 넣는 길이 없다. 그 두 기능의 시험은 데이터베이스에 값을 직접 넣는다. 운영자에게는 값을 넣는 화면도, 저장하는 주소도, 누가 무엇을 바꿨는지의 기록도 없다.

운영자는 값을 고친 결과를 저장하기 전에 볼 수 없다. 저장하면 다음에 위젯을 여는 최종 사용자가 곧바로 그 값을 본다. 로그인 전의 모양이나 로그인 시간이 끝났을 때의 알림처럼 일부러 만들기 어려운 상태는 저장한 뒤에도 보기 어렵다.

위젯 테스트 페이지는 지금 주소를 아는 누구나 연다. 로그인하지 않은 사람이 사이트 목록을 보고, 익명 사이트의 사이트 토큰을 받아 질문한다. 운영자가 시험하려고 등록한 사이트가 그대로 밖에 보인다.

위젯 테스트 페이지는 뜰 때 설정 파일과 사이트 파일을 대 보고 하나라도 어긋나면 뜨지 않는다. 사이트의 목록이 화면에서 바뀌는 값이 되면 이 검사는 뜰 때 한 번으로 설 수 없고, 운영자가 화면에서 틀린 값을 저장했을 때 그것을 알 길도 없다.

## Solution

운영자는 관리 화면에 로그인한 그대로, 같은 이름의 다른 포트에 선 위젯 관리 화면을 연다. 로그인을 다시 하지 않는다.

첫 화면은 사이트 목록이다. 사이트마다 사이트 이름, 위젯 이름, 에이전트, 위젯 테스트 페이지에 담았는지와 그 보증 모드, 마지막으로 바꾼 때와 바꾼 계정이 한 줄로 선다. 처음 배포한 직후에는 "등록된 사이트가 없다"와 "사이트 등록" 단추가 선다.

사이트 하나를 열면 탭 일곱(기본, 글, 모양, 로그인과 로그아웃, 고지, 창으로 열 때, 위젯 테스트 페이지)에 칸이 나뉘어 있고, 양식 옆에는 미리보기가 붙어 있다. 운영자가 칸을 고치면 미리보기의 위젯이 그 자리에서 그 값으로 바뀐다. 미리보기 위의 "보는 상태"에서 첫 화면, 대화가 한 번 오간 뒤, 로그인 전, 로그인한 뒤, 고지 확인 전, 고지 전문을 연 뒤, 로그인 시간이 끝남을 골라 보고, 밝기 단추로 밝게와 어둡게를 바꿔 본다. 미리보기는 질문을 보내지 않는다.

고친 칸이 있으면 화면 아래에 저장 띠가 붙어 "바뀐 칸 3개"와 "되돌리기", "저장"을 보인다. 다른 탭에서 고친 칸은 그 탭 이름 뒤의 수로 보인다. 저장하면 아무것도 다시 띄우지 않아도 다음에 위젯을 여는 사람부터 그 값을 본다. 틀린 값은 저장되지 않는다. `javascript:`로 시작하는 로그인 주소나 다른 사이트가 이미 쓰는 발급자를 넣으면 그 칸 아래에 까닭이 서고, 오류가 든 탭 이름 뒤에 표시가 붙는다. 저장할 때마다 누가, 언제, 어느 사이트의, 무엇을 무엇으로 바꿨는지가 기록에 남는다.

옆 탐색의 "테스트"를 누르면 위젯 테스트 페이지가 새 탭으로 열리고, 운영자는 저장한 값으로 그려진 실제 위젯에 질문해 본다. 위젯 테스트 페이지는 이제 로그인한 사람만 연다. 로그인하지 않은 브라우저에는 사이트 목록도 사이트 토큰도 내지 않고 들어오는 문만 보인다. 운영자는 관리 화면에 로그인한 그대로 들어와 모든 사이트를 시험한다.

운영자가 사이트 파일에 없는 발급자를 등록하면 저장은 되지만 위젯 테스트 페이지는 그 사이트만 열지 않는다. 위젯 관리 화면은 목록의 그 줄에 "열리지 않음"을, 표 위와 그 사이트의 화면에 까닭과 고치는 법을 보인다. 다른 사이트는 그대로 열린다.

로그인하지 않은 브라우저로 위젯 관리 화면을 열면 "로그인이 필요하다"와 "관리 화면에서 로그인" 단추가 서고, 관리 화면에서 로그인한 뒤 그 탭으로 돌아오면 화면이 열린다.

## User Stories

들어오기

1. 운영자로서, 관리 화면에 로그인한 그대로 위젯 관리 화면에 들어가고 싶다. 로그인을 두 번 하지 않기 위해서다.
2. 운영자로서, 로그인하지 않은 채 위젯 관리 화면을 열면 무엇을 해야 하는지와 관리 화면의 로그인 화면으로 가는 단추를 보고 싶다. 빈 화면이나 오류만 보고 멈추지 않기 위해서다.
3. 운영자로서, 관리 화면에서 로그인한 뒤 위젯 관리 화면의 탭으로 돌아오면 새로 고치지 않아도 화면이 열리기를 바란다.
4. 운영자로서, 로그인 시간이 끝났으면 처음 온 것과 다른 안내("로그인이 끝났다")를 보고 싶다. 왜 화면이 닫혔는지 알기 위해서다.
5. 운영자로서, Agent OS 서버가 답하지 않아 로그인을 확인하지 못한 것과 로그인하지 않은 것을 구별해 보고 싶다. 다시 로그인해도 풀리지 않는 일에 로그인을 되풀이하지 않기 위해서다.
6. 운영자로서, https가 아닌 주소로 화면을 열었으면 그 주소에서는 로그인할 수 없다는 말을 보고 싶다.
7. 운영자로서, 화면을 쓰는 동안 짧은 로그인 수명이 끝나도 화면이 스스로 이어 주어 하던 일을 계속하고 싶다.
8. 운영자로서, 양식을 고치던 중에 로그인이 끝나도 고친 칸이 사라지지 않기를 바란다. 다시 로그인한 뒤 그대로 저장하기 위해서다.
9. 운영자로서, 옆 탐색 맨 아래에서 지금 들어온 계정 이름을 보고 싶다. 바꾼 기록에 어느 이름으로 남는지 알기 위해서다.
10. 운영자로서, 계정 메뉴에서 관리 화면을 새 탭으로 열고 싶고, 로그아웃은 관리 화면에서 한다는 말을 보고 싶다.

사이트 목록

11. 운영자로서, 등록한 사이트를 한 표에서 보고 싶다. 사이트 이름, 위젯 이름, 에이전트, 위젯 테스트 페이지에 담았는지, 마지막으로 바꾼 때와 계정을 한눈에 보기 위해서다.
12. 운영자로서, 처음 배포한 직후의 빈 목록에서 무엇을 해야 위젯이 뜨는지 안내를 보고 싶다.
13. 운영자로서, 목록을 새로 고쳐 다른 운영자가 방금 바꾼 것을 보고 싶다.
14. 운영자로서, 위젯 테스트 페이지가 열지 않는 사이트가 있으면 목록에서 그 줄과 까닭과 고치는 법을 보고 싶다. 서버의 로그를 열지 않고 알기 위해서다.
15. 운영자로서, 좁은 화면에서도 가로로 밀지 않고 목록을 보고 싶다.

사이트 등록과 고치기

16. 운영자로서, 사이트를 새로 등록하고 싶다. 사이트 개발자가 태그에 적을 이름을 정하기 위해서다.
17. 운영자로서, 사이트 이름은 등록한 뒤에 바꾸지 못한다는 것을 등록할 때 알고 싶다.
18. 운영자로서, 이미 있는 사이트 이름으로 등록하려 하면 그 칸에서 까닭을 보고 싶다.
19. 운영자로서, 칸이 일곱 탭에 나뉘어 있어 고치려는 것만 보고 싶다.
20. 운영자로서, 위젯의 이름, 소개 한 줄, 입력창 안내 문구를 고치고 싶다.
21. 운영자로서, 첫 화면의 예시 질문을 넷까지 등록하고 차례대로 보이게 하고 싶다.
22. 운영자로서, 예시 질문을 세로 목록, 감기는 알약, 입력창 위 띠 가운데 어느 모양으로 보일지 고르고 싶다.
23. 운영자로서, 문의 링크의 주소를 등록하고 싶다.
24. 운영자로서, 색 테마 넷 가운데 하나를 견본을 보고 고르고 싶다.
25. 운영자로서, 위젯의 처음 밝기를 정하거나 기기의 설정을 따르게 하고 싶다.
26. 운영자로서, 위젯에서 밝기 스위치를 숨겨 위젯을 정한 밝기로 고정하고 싶다.
27. 운영자로서, 로그인 주소와 로그아웃 주소, 로그인 단추의 문구, 로그아웃을 부르는 방법을 등록하고 싶다.
28. 운영자로서, 로그인 전의 모양과 로그인 시간이 끝났을 때 알림의 모양을 작은 그림을 보고 고르고 싶다.
29. 운영자로서, 고지의 짧은 줄과 고지 전문을 고치고, 고지 전문을 보이는 법을 고르고 싶다.
30. 운영자로서, 사이트가 위젯을 창으로 열 때 브라우저 탭에 보일 제목을 정하고 싶다.
31. 운영자로서, 사이트를 위젯 테스트 페이지에 담을지 고르고, 담으면 발급자와 보증 모드와 보고서 링크를 정하고 싶다.
32. 운영자로서, 위젯 테스트 페이지에 담는 사이트를 등록할 때 고지 전문에 익명 식별자와 계정 기록의 문장이 미리 들어 있기를 바란다. 빠뜨리지 않고 자기 말로 다듬기 위해서다.
33. 운영자로서, 주소 칸을 떠나는 순간 형식이 틀렸으면 바로 알고 싶다. 저장을 눌러 보기 전에 고치기 위해서다.
34. 운영자로서, 칸마다 무엇을 넣는지 도움말 한 줄을 보고 싶다.

바뀜과 저장

35. 운영자로서, 어느 칸을 고쳤는지 칸의 라벨에서 보고 싶다.
36. 운영자로서, 다른 탭에서 고친 칸이 있다는 것을 탭 이름 뒤의 수로 보고 싶다. 저장하기 전에 놓치지 않기 위해서다.
37. 운영자로서, 화면 아래의 띠 하나에서 바뀐 칸의 수를 보고 한 번에 저장하고 싶다.
38. 운영자로서, 고친 것을 마지막으로 저장한 값으로 되돌리고 싶다.
39. 운영자로서, 저장한 뒤 무엇이 언제부터 바뀌는지 한 줄로 보고 싶다.
40. 운영자로서, 저장이 거절되면 어느 칸이 왜 거절됐는지 그 칸에서 보고, 그 칸이 든 탭으로 옮겨 가기를 바란다.
41. 운영자로서, 다른 운영자가 그사이 같은 사이트를 고쳤으면 내 저장이 그것을 조용히 덮지 않기를 바란다.
42. 운영자로서, 저장하지 않은 채 떠나려 하면 한 번 물어 주기를 바란다.
43. 운영자로서, 저장한 값이 아무것도 다시 띄우지 않아도 다음에 위젯을 여는 사람에게 보이기를 바란다.

미리보기

44. 운영자로서, 칸을 고치는 대로 양식 옆의 위젯이 그 값으로 바뀌는 것을 보고 싶다. 저장하기 전에 최종 사용자가 볼 모양을 확인하기 위해서다.
45. 운영자로서, 로그인 전, 로그인한 뒤, 고지 확인 전, 고지 전문을 연 뒤, 로그인 시간이 끝남처럼 일부러 만들기 어려운 상태를 골라 보고 싶다.
46. 운영자로서, 미리보기의 밝기를 밝게와 어둡게로 바꿔 보고 싶다.
47. 운영자로서, 미리보기가 실제 위젯과 같은 부품으로 그려지기를 바란다. 미리보기에서 본 것과 최종 사용자가 보는 것이 다르지 않기 위해서다.
48. 운영자로서, 미리보기가 질문을 보내지 않는다는 것을 알고 싶다. 미리 보다가 비용이 들거나 기록이 남지 않기 위해서다.
49. 운영자로서, 좁은 화면에서는 단추로 미리보기를 화면 가득 열어 보고 싶다.
50. 키보드와 화면 읽기 프로그램을 쓰는 운영자로서, 미리보기 안의 단추에 포커스가 들어가지 않고 미리보기가 한 줄로 읽히기를 바란다.

사이트 지우기

51. 운영자로서, 쓰지 않는 사이트를 지우고 싶다.
52. 운영자로서, 지우기 전에 무엇이 지워지고 그 사이트 이름을 적은 위젯이 어떻게 되는지 보고 한 번 더 확인하고 싶다.
53. 운영자로서, 지운 일도 누가 언제 했는지와 지우기 전의 값이 기록에 남기를 바란다.

위젯 테스트 페이지

54. 운영자로서, 옆 탐색의 "테스트"로 위젯 테스트 페이지를 새 탭에 열고 싶다.
55. 운영자로서, 사이트 화면에서 그 사이트를 고른 채로 위젯 테스트 페이지를 열고 싶다.
56. 운영자로서, 관리 화면에 로그인한 그대로 위젯 테스트 페이지에 들어가 담은 사이트를 모두 시험하고 싶다.
57. 운영자로서, 위젯 테스트 페이지의 띠에서 지금 어느 계정으로 들어왔는지 보고 싶다.
58. 운영자로서, 위젯 테스트 페이지의 사이트 고르기에서 위젯의 이름과 사이트 이름을 함께 보고 싶다.
59. 운영자로서, 로그인 시간이 끝나면 위젯 테스트 페이지가 들어오는 문으로 돌아가 까닭을 보이기를 바란다.
60. 로그인하지 않은 사람으로서, 위젯 테스트 페이지의 주소를 알아도 사이트 목록과 사이트 토큰을 받지 못하고 들어오는 문만 본다.
61. 운영자로서, 사이트 하나가 사이트 파일과 어긋나도 다른 사이트는 그대로 열리기를 바란다.
62. 운영자로서, 어긋난 사이트의 값을 화면에서 고치면 아무것도 다시 띄우지 않아도 그 사이트가 다시 열리기를 바란다.
63. 운영자로서, 열 수 있는 사이트가 하나도 없을 때 위젯 테스트 페이지가 빈 화면 대신 무엇을 해야 하는지 보이기를 바란다.

안전

64. 운영자로서, `javascript:`로 시작하는 값이 로그인 주소나 로그아웃 주소나 문의 링크로 저장되지 않기를 바란다. 위젯이 든 페이지에서 스크립트가 도는 길을 막기 위해서다.
65. 운영자로서, 비밀번호가 든 주소(`https://이름:비밀번호@…`)가 저장되지 않기를 바란다. 위젯 설정은 누구나 읽는 주소로 나가고 바꾼 기록에 값이 남기 때문이다.
66. 운영자로서, 다른 사이트의 페이지가 내 로그인 쿠키로 저장 요청을 보내도 거절되기를 바란다.
67. 운영자로서, 위젯 관리 화면의 스크립트가 Agent OS의 관리 기능을 부르지 못하기를 바란다.
68. 운영자로서, 로그인하지 않은 요청으로는 어느 설정도 읽거나 고칠 수 없기를 바란다. 누구나 읽는 것은 위젯이 받아 가는 위젯 설정 하나다.
69. 시스템 관리자로서, 로그인 주소가 바뀌었을 때 누가 언제 무엇에서 무엇으로 바꿨는지 데이터베이스에서 되짚고 싶다.
70. 시스템 관리자로서, 위젯 쪽 서버의 로그와 데이터베이스에 운영자의 로그인 쿠키 값이 남지 않기를 바란다.

배포

71. 배포하는 운영자로서, 단독 compose에 위젯 관리 화면이 함께 뜨고 정해진 포트에서 열리기를 바란다.
72. 배포하는 운영자로서, 그 포트의 번호를 바꾸거나 인터넷에서 닫을 수 있기를 바란다.
73. 배포하는 운영자로서, 위젯 테스트 페이지가 설정 파일의 사이트 목록이 아니라 화면에서 등록한 사이트를 담기를 바란다. 사이트를 더할 때 파일을 고치고 다시 띄우지 않기 위해서다.
74. 배포하는 운영자로서, 위젯 관리 서버나 Agent OS 서버가 내려가 있을 때 위젯 테스트 페이지와 위젯 관리 화면이 까닭을 말하고 다시 시도할 길을 주기를 바란다.

짓는 사람

75. 사이트 개발자로서, 운영자가 화면에서 값을 바꿔도 내 페이지의 태그를 고치지 않고 싶다.
76. 개발자로서, 주소의 형식 규칙이 서버와 화면과 위젯에서 같다는 것을 사례 표 하나로 확인하고 싶다. 한 곳만 고쳐 어긋나지 않기 위해서다.
77. 개발자로서, 위젯 관리 서버와 위젯 테스트 페이지의 서버가 Agent OS에 부르는 경로가 둘뿐이라는 것을 시험이 지키기를 바란다.
78. 개발자로서, 위젯의 화면 부품을 공유 패키지로 옮긴 뒤에도 위젯의 사진 비교가 기준 그림을 고치지 않고 통과하기를 바란다. 옮기는 일이 위젯의 모양을 바꾸지 않았음을 알기 위해서다.
79. 개발자로서, 관리 화면에 로그인해 사이트를 등록하고 위젯 테스트 페이지에서 그 값으로 그려진 위젯을 보는 길 전체를 브라우저 시험 하나가 밟기를 바란다.
80. 개발자로서, 화면이 확정한 그림과 어긋나지 않았는지 사진 비교로 확인하고 싶다.
81. 운영자로서, 화면이 한꺼번에 보낸 요청들이 로그인 시간이 끝난 것을 함께 알아도 갱신은 한 번만 일어나기를 바란다. 같은 갱신용 번호가 두 번 쓰여 로그인이 끊기는 일을 막기 위해서다.
82. 운영자로서, 사이트의 보증 모드를 익명에서 로그인으로 바꿔 저장하면 위젯 테스트 페이지가 바로 다음 요청부터 그 사이트에 익명 토큰을 내지 않기를 바란다.
83. 시스템 관리자로서, 로그인하지 않은 사람이 위젯 테스트 페이지에 보낸 요청이 위젯 쪽 데이터베이스의 조회를 일으키지 않기를 바란다.

## Implementation Decisions

화면은 `.scratch/portal-admin/design/`의 완성 화면이 원천이고 이 절은 그 화면이 말하지 않는 것을 적는다(ADR 0025). 화면과 이 절이 다르면 이 절이 앞선다. 다른 자리는 "화면과 다르게 짓는 것"에 모았다.

### 프로그램 사이의 길 (넘겨받았다. 위젯 관리 서버가 위젯 테스트 페이지의 서버에 묻는 길은 명세가 정했다)

이 기능이 끝나면 프로그램들이 서로를 부르는 길은 아래와 같다. "안쪽 길"은 앞단의 프록시가 밖에서 넘기지 않는 경로이고, 같은 서버나 같은 컨테이너 네트워크 안에서만 닿는다. 위젯 관리 화면의 중계도 안쪽 길을 넘기지 않는다("저장 경로").

| 부르는 쪽 | 받는 쪽 | 무엇을 | 무엇으로 연다 |
|---|---|---|---|
| 운영자의 브라우저 | 위젯 관리 화면(프록시의 위젯 관리 화면용 포트) | 화면과 그 화면이 보내는 요청 | 운영자 로그인 쿠키 |
| 위젯 관리 화면의 중계 | 위젯 관리 서버 | 운영자용 경로로 온 브라우저의 요청을 그대로 | 받은 쿠키와 요청 출처 머리를 그대로 전한다 |
| 위젯 관리 서버 | Agent OS 서버 | "지금 누구인지"와 "갱신" 둘뿐 | 쿠키만 전한다 |
| 위젯 테스트 페이지의 서버 | Agent OS 서버 | "지금 누구인지"와 "갱신" 둘뿐 | 쿠키만 전한다 |
| 위젯 테스트 페이지의 서버 | 위젯 관리 서버 | 위젯 테스트 페이지 설정 | 안쪽 길 |
| 위젯 관리 서버 | 위젯 테스트 페이지의 서버 | 사이트마다 열리는지와 까닭 | 안쪽 길 |
| 위젯 | 위젯 관리 서버(공개 주소 아래의 정해진 경로) | 그 사이트의 위젯 설정 | 누구나 읽는다(widget-admin-server가 짓는다) |

- 위젯 관리 화면은 요청을 위젯 관리 서버로만 넘긴다. 브라우저가 Agent OS 서버나 위젯 테스트 페이지의 서버를 직접 부르지 않는다.
- 위젯 관리 서버와 위젯 테스트 페이지의 서버는 Agent OS 서버에 운영자 계정이 누구인지만 묻는다. 부르는 경로는 둘뿐이고 그것을 시험이 지킨다(Testing Decisions).
- 여섯째 줄은 이 명세가 더한 길이다. 위젯 관리 서버는 사이트 파일을 읽지 않으므로(ADR 0064 결정 "시작 검사가 가는 자리") 사이트가 사이트 파일과 맞는지를 스스로 알 수 없고, 그것을 아는 프로그램은 위젯 테스트 페이지의 서버뿐이다. 자세한 것은 "닫힌 사이트를 알리는 길"에 있다.

### 위젯 관리 화면의 틀과 주소 (넘겨받았다. 주소와 틀을 두는 자리는 명세가 정했다)

- 위젯 관리 화면은 `web/` 워크스페이스의 새 Next 앱이다. 관리 화면 앱이 쓰는 방식을 그대로 따른다. 화면 부품의 층, 스토리와 사진 비교, 린트 규칙, 시작 래퍼, 브라우저의 요청을 상류로 넘기는 중계다(`.claude/rules/web-workspace.md`, `.claude/rules/web-design.md`, ADR 0019, ADR 0021). 다만 중계가 넘기는 경로는 관리 화면 앱과 달리 운영자용 경로로 좁힌다("저장 경로").
- 관리 화면 앱의 코드는 가져다 쓰지 못한다(앱 사이의 import는 판정자가 막는다). 옆 탐색과 위 막대 같은 틀은 디자인 시스템 패키지의 부품으로 이 앱 안에 다시 짓는다. 이 기능이 앱 밖으로 옮기는 화면 부품은 미리보기에 쓰는 위젯의 것뿐이다("미리보기를 그리는 부품"). ADR 0064 결정 "위젯 관리 화면"이 "다시 짓거나 공유 패키지로 옮겨야" 한다고 적은 둘 가운데 다시 짓기를 골랐다. 관리 화면 앱은 admin-login이 막 고친 앱이라 그 부품을 옮기는 일을 이 기능에 얹지 않는다.
- 틀은 완성 화면 그대로다. 옆 탐색에 "사이트"와 "테스트" 둘이 서고, 맨 아래에 지금 들어온 계정의 이름이 선다. "테스트"는 위젯 테스트 페이지를 새 탭으로 여는 링크이고 글자 뒤에 새 탭 아이콘이 붙는다. 폭이 좁으면 옆 탐색 대신 두 줄 위 막대가 선다.
- 계정 자리를 누르면 메뉴가 열린다. 메뉴에는 "Agent OS 운영자 계정"이라는 흐린 글과 계정 이름, 새 탭으로 여는 "관리 화면 열기", 그리고 "로그아웃은 관리 화면에서 한다. 관리 화면에서 로그아웃하면 이 화면에서도 나간다."가 있다. 로그아웃 단추는 두지 않는다. 위젯 관리 서버가 Agent OS에 부르는 경로가 둘뿐이기 때문이다.
- 주소는 넷이다. `/`는 `/sites`로 넘긴다. `/sites`는 사이트 목록, `/sites/<사이트 이름>`은 사이트 하나, `/new`는 사이트 등록이다. 화면의 탐색용 가정은 등록을 `/sites/new`로 보았는데, 그러면 이름이 `new`인 사이트의 화면과 겹치므로 등록의 주소를 사이트 이름 밖에 두었다.
- 고른 탭은 주소에 싣지 않는다. 사이트 화면을 열면 "기본" 탭이 골라져 있고, 저장한 뒤에는 저장할 때의 탭이 그대로다.
- 화면의 밝기는 보는 사람 기기의 설정을 따른다. 그림에 밝기를 고르는 것이 없어 스위치를 두지 않는다.
- 화면은 링크를 만들 주소 둘을 안다. 관리 화면의 주소("관리 화면에서 로그인", "관리 화면 열기")와 위젯 테스트 페이지의 주소("테스트", "위젯 테스트 페이지에서 열기")다. 둘 다 이미지에 굳히지 않고 컨테이너가 뜰 때 받으며, 받지 않았으면 지금 화면과 같은 이름으로 짓는다. 관리 화면은 그 이름의 관리 화면용 기본 포트이고, 위젯 테스트 페이지는 그 이름의 방문자용 주소 아래 `/portal/`이다("포트와 compose").

### 로그인하지 않았거나 로그인 시간이 끝났을 때 (넘겨받았다. 다시 확인하는 때와 양식을 지키는 것은 명세가 정했다)

- 위젯 관리 화면은 어느 주소로 열든 먼저 지금 누구인지를 묻는다. 답이 오기 전에는 틀만 그린다.
- 로그인하지 않았으면 그 주소에서 "로그인이 필요하다" 화면을 그린다(완성 화면 `mk-login.dc.html`). 다른 주소로 옮기지 않는다. 로그인한 뒤에는 열려던 화면이 그 자리에서 열린다.
- "관리 화면에서 로그인"은 관리 화면의 주소를 새 탭으로 연다. 관리 화면은 로그인하지 않은 채 어느 화면을 열어도 로그인 화면으로 보내므로(ADR 0062 결정 "화면") 로그인 화면의 주소를 따로 알 필요가 없다. 로그인한 뒤 위젯 관리 화면으로 되돌려 보내 달라고 관리 화면에 요구하지 않는다. 그래서 Agent OS의 계약에 더하는 것이 없다.
- 다시 확인하는 때는 둘이다. 그 탭이 다시 보이게 될 때와 "다시 확인"을 누를 때다.
- 상태 셋은 완성 화면 `mk-login-states.dc.html` 그대로다.
  - 로그인 시간이 끝남: 이 탭에서 로그인이 한 번이라도 확인된 뒤에 로그인이 끊겼으면 "로그인이 끝났다" 알림을 함께 보인다.
  - Agent OS 서버가 답하지 않음: 위젯 관리 서버가 로그인을 확인하지 못했다고 답하면("로그인 확인") "로그인을 확인하지 못했다" 알림과 "다시 확인"만 보인다.
  - https가 아닌 주소: 브라우저가 그 페이지를 보안 컨텍스트로 보지 않으면 요청을 보내지 않고 "이 주소에서는 로그인할 수 없다"를 보인다. 로그인 쿠키가 `https`와 서버 자신(`localhost`)에서만 저장되기 때문이다(ADR 0062 결정 "로그인 상태").
- 사이트 화면에 저장하지 않은 바뀜이 있을 때 로그인이 끊기면 화면을 바꾸지 않는다. 양식을 그대로 두고 저장 띠에 "로그인이 끝났다. 관리 화면에서 다시 로그인한 뒤 저장한다."를 보인다. 운영자가 다른 탭에서 로그인하고 돌아와 저장을 다시 누르면 된다. 바뀜이 없을 때는 "로그인이 필요하다" 화면으로 바꾼다.

### 사이트 목록 (넘겨받았다. 차례와 빈 칸의 표시는 명세가 정했다)

- 완성 화면 `Main.dc.html`, `mk-sites-empty.dc.html`, `mk-sites-m.dc.html` 그대로다.
- 줄은 마지막으로 바꾼 때가 가까운 차례로 선다. 쪽을 나누지 않는다.
- "위젯 이름" 칸은 위젯의 이름이 비어 있으면 에이전트의 이름을 흐리게 보인다. 위젯이 그때 에이전트의 이름을 그리기 때문이다.
- "위젯 테스트 페이지" 칸은 담지 않은 사이트면 흐린 "담지 않음", 담은 사이트면 그 보증 모드("익명", "로그인", "둘 다"), 담았지만 위젯 테스트 페이지가 열지 않는 사이트면 경고 아이콘과 "열리지 않음"이다.
- 열리지 않는 사이트가 하나라도 있으면 표 위에 경고 알림 하나가 서고, 사이트마다 한 줄씩 까닭과 고치는 법을 적는다. 까닭마다의 문장은 "닫힌 사이트를 알리는 길"의 표에 있다.
- 위젯 테스트 페이지의 서버가 답하지 않아 열리는지 확인하지 못했으면 그 칸은 보증 모드만 보이고, 표 위에 정보 알림 "위젯 테스트 페이지가 답하지 않아 사이트가 열리는지 확인하지 못했다."가 선다. 이 알림은 그림에 없고 이 명세가 더했다.
- "새로 고침"은 목록을 다시 받아 온다.

### 사이트 하나의 화면과 칸 (사용자가 골랐다. 칸마다의 꼴과 상한, 비웠을 때는 명세가 정했다)

짜임은 사용자가 고른 탭과 저장 단추 하나다(`.scratch/portal-admin/design/README.md`). 탭 일곱 가운데 고른 탭의 칸만 보이고, 저장 띠는 탭과 상관없이 화면에 하나다. 완성 화면은 `ch-form-4.dc.html`, `mk-site.dc.html`, `mk-site-error.dc.html`, `mk-site-m.dc.html`, `mk-site-dark.dc.html`이다.

화면 머리는 돌아가기 링크 "사이트 목록", 사이트 이름, 위젯 이름과 마지막으로 바꾼 때와 계정이다. 오른쪽 위에는 "위젯 테스트 페이지에서 열기"와 더 보기 단추가 선다. "위젯 테스트 페이지에서 열기"는 그 사이트를 고른 위젯 테스트 페이지를 새 탭으로 열고, 위젯 테스트 페이지에 담았고 열리는 사이트에만 선다. 저장하지 않은 바뀜이 있어도 여는 것은 마지막으로 저장한 값이다.

| 고지 | 고지의 짧은 줄 | 한 줄, 200자까지 | 고지의 짧은 줄 | 위젯이 줄의 글 없이 "고지 전문" 단추만 그린다 |
| 고지 | 고지 전문 | 여러 줄, 4,000자까지 | 고지 전문 | 위젯에 "고지 전문" 단추와 고지 확인 덮개가 없다. 위젯 테스트 페이지에 담는 사이트는 비울 수 없다 |
| 고지 | 고지 전문을 보이는 법 | 작은 그림 고르기 셋 | 고지 전문을 보이는 법 | 늘 하나가 골라져 있다(기본은 고지 줄 안에서 펼침) |
| 창으로 열 때 | 탭 제목 | 한 줄, 100자까지 | URL 방식 창의 탭 제목 | 위젯이 위젯의 이름을 쓴다 |
| 위젯 테스트 페이지 | 위젯 테스트 페이지에 담는다 | 체크박스. 끄면 아래 세 칸이 사라진다 | 그 사이트의 위젯 테스트 페이지 설정이 있는지 | 꺼짐 |
| 위젯 테스트 페이지 | 발급자 | 한 줄, 500자까지 | 발급자 | 담는 사이트는 받지 않는다 |
| 위젯 테스트 페이지 | 보증 모드 | 라디오 셋 | 보증 모드 | 담는 사이트는 늘 하나가 골라져 있다(등록 화면의 처음 값은 익명) |
| 위젯 테스트 페이지 | 보고서 링크 | 주소 | 보고서 링크 | 위젯 테스트 페이지가 보고서 링크를 그리지 않는다 |

- 주소인 칸 넷(문의 링크, 로그인 주소, 로그아웃 주소, 보고서 링크)의 규칙은 "주소의 검사"다.
- 예시 질문은 줄마다 한 줄 입력과 지우기 단추가 서고, 아래에 "예시 질문 더하기"가 선다. 넷이 차면 그 단추는 쓸 수 없는 상태가 된다. 빈 줄은 저장할 때 빠진다. 줄의 차례가 위젯에 보이는 차례다. 넷과 100자는 위젯이 받는 상한과 같다(widget-login-state의 명세).
- 문의 링크는 주소 한 칸이다. 위젯이 보이는 글은 "문의하기"로 고정이고(widget-login-state의 명세) 운영자가 바꾸지 못한다. 화면의 탐색용 가정은 글과 주소 두 칸이었다.
- 발급자는 주소처럼 생겼어도 사이트 파일의 열쇠라 글자 그대로 받고 주소의 검사를 걸지 않는다.
- "위젯 테스트 페이지에 담는다"를 끄고 저장하면 그 사이트의 발급자와 보증 모드와 보고서 링크는 지워진다. 다시 켜면 세 칸이 빈 채로 선다.
- 위젯 설정에 보증 모드나 로그인 모드를 두지 않는다. 보증 모드는 위젯의 칸이 아니고(ADR 0061), 위젯 테스트 페이지에 담는 사이트의 것만 위젯 테스트 페이지 설정이 든다. 화면이 명세에 넘긴 "위젯 설정에 로그인 모드를 둘지"의 답이다.
- 글 칸은 저장할 때 앞뒤의 공백을 잘라 내고, 잘라서 빈 글이 되면 비운 것으로 저장한다. 고지 전문은 줄바꿈을 `\n`으로 고르게 한 뒤 앞뒤만 자른다. 문단 사이의 빈 줄은 그대로 둔다. 자르는 쪽은 위젯 관리 서버이고, 화면은 저장한 뒤 서버가 돌려준 값으로 양식을 다시 채운다.
- 작은 그림 고르기는 완성 화면이 정한 대로 라디오 묶음이다. 카드 전체가 라디오 하나의 라벨이고, 고른 카드는 테두리와 체크 아이콘으로 함께 보인다.
- 도움말은 칸 아래에 서고 문구는 완성 화면과 시작 프롬프트(`screens-prompt.md`)의 것을 쓴다. 주소인 칸에는 그 칸의 도움말 뒤에 주소의 도움말이 이어 붙는다(문의 링크가 그렇다). 이 명세가 고치거나 더하는 문구는 "문구"에 있다.

### 예시 질문의 모양을 고르는 칸 (사용자가 골랐다)

사용자가 "0.1 판에 고르는 칸을 넣기"를 골랐다(일지 2026-11-16-1705). "글" 탭의 예시 질문 칸 바로 아래에 작은 그림 고르기 하나가 는다. 고르는 것은 "세로 목록"(기본), "감기는 알약", "입력창 위 띠"이고 그 모양은 위젯의 화면 작업이 확정한 것이다(`.scratch/widget-login-state/design/README.md`의 "위젯 설정이 더한 화면"). 이 칸은 확정한 화면에 없어, 다른 작은 그림 고르기 셋과 같은 부품과 같은 치수로 짓고 회색 도식 그림 셋은 티켓이 그 세 모양을 보고 그린다. 이 결정은 ADR 0064의 이력이다(서두 "이력").

### 바뀜, 저장 띠, 떠날 때 (넘겨받았다. 바뀜을 세는 법과 그림에 없는 상태는 명세가 정했다)

- 바뀐 칸은 지금 값이 마지막으로 저장한 값과 다른 칸이다. 고쳤다가 되돌려 놓은 칸은 바뀐 칸이 아니다. 예시 질문은 목록 전체가 한 칸이다. 바뀐 칸은 라벨 뒤에 흐린 "바뀜"이 붙고, 그 칸이 든 탭 이름 뒤에 그 탭의 바뀐 칸 수가 흐리게 선다.
- 바뀐 칸이 하나라도 있으면 저장 띠가 화면 아래에 붙는다. 왼쪽에 "바뀐 칸 N개"와 흐린 "저장하면 다음에 위젯을 여는 사람부터 바뀐다."가, 오른쪽에 "되돌리기"와 "저장"이 선다. 좁은 폭에서는 흐린 문장을 뺀다. 저장 띠가 나타날 때 포커스를 옮기지 않는다.
- "되돌리기"는 모든 칸을 마지막으로 저장한 값으로 돌려놓는다. 묻지 않는다.
- "저장"은 그 사이트의 위젯 설정과 위젯 테스트 페이지 설정을 한 번에 보낸다. 보내는 동안 두 단추는 쓸 수 없는 상태다.
- 저장이 되면 저장 띠가 사라지고, 화면 머리의 마지막으로 바꾼 때와 계정이 바뀌며, 머리 아래에 흐린 "저장했다. 다음에 위젯을 여는 사람부터 바뀐다."가 다음 바뀜까지 남는다.
- 주소인 칸은 칸을 떠날 때 화면이 형식을 보고, 어긋나면 그 칸 아래에 오류를 보인다. 다른 규칙은 저장을 눌렀을 때 위젯 관리 서버가 본다. 화면의 검사는 빨리 알리려는 것이고, 받을지를 정하는 쪽은 서버다.
- 서버가 칸을 거절하면 그 칸 아래에 까닭이 서고, 저장 띠는 위험 아이콘과 "저장하지 못했다. 칸 N개를 고친다."로 바뀐다. 오류가 든 탭 이름 뒤에는 바뀐 칸의 수 대신 위험 아이콘과 오류 칸의 수가 선다. 첫 오류가 든 탭이 골라지고 첫 오류 칸에 포커스가 간다. 칸의 값을 고치면 그 칸의 오류는 사라진다.
- 그림에 없는 저장 실패가 셋 있고 모두 저장 띠의 글로 알린다. 양식은 그대로 둔다.
  - 요청이 닿지 않았거나 서버가 오류를 냈으면 "저장하지 못했다. 잠시 뒤 다시 저장한다."
  - 다른 운영자가 그사이 같은 사이트를 저장했으면 "다른 계정이 이 사이트를 먼저 고쳤다. 새로 불러온 뒤 다시 고친다."와 보조 단추 "새로 불러오기"다. 새로 불러오면 이 화면의 바뀜은 사라진다("저장 경로"의 저장 번호).
  - 로그인이 끝났으면 위 "로그인하지 않았거나 로그인 시간이 끝났을 때"의 글이다.
- 바뀐 칸이 있는 채로 화면 안의 다른 곳으로 가려 하면 확인 창이 묻는다(완성 화면 `mk-leave.dc.html`). 탭을 바꾸는 것은 떠나는 것이 아니다. 창이 열리면 포커스는 "머무르기"에 가고 Esc로 닫힌다. 브라우저 탭을 닫거나 새로 고칠 때는 브라우저가 띄우는 확인에 맡긴다.
- 키보드와 화면 읽기 프로그램의 동작은 캔버스 메모가 제안한 대로 한다. 탭 줄은 고른 탭 하나로만 들어가고 좌우 화살표 키로 탭을 옮긴다. 좁은 폭에서 넘치는 탭은 옆으로 밀어 본다.

### 미리보기 (넘겨받았다. 보는 상태마다의 입력과 밝기 단추의 규칙은 명세가 정했다. 높이를 넘는 글을 다루는 법은 사용자가 골랐다)

- 미리보기는 사이트 화면의 양식 옆에 붙은 칸이고, 양식을 스크롤해도 화면에 붙어 있다. 지금 양식의 값(저장하지 않은 값 포함)으로 위젯을 그린다. 질문을 보내지 않고, Agent OS에도 위젯 관리 서버에도 묻지 않는다(ADR 0065 결정 "미리보기").
- 그리는 것은 위젯 앱이 쓰는 것과 같은 화면 부품이다("미리보기를 그리는 부품"). 위젯 관리 화면은 위젯의 모양을 흉내 낸 부품을 따로 짓지 않는다.
- 미리보기와 실제 위젯이 다른 것은 입력뿐이다. 실제 위젯은 위젯 설정을 받아 오고 사이트에 토큰을 물어 상태를 정한다. 미리보기는 양식의 값을 위젯 설정으로 쓰고, 운영자가 고른 "보는 상태"가 아래 표의 견본 입력을 정한다.

| 보는 상태 | 화면 부품에 주는 견본 입력 |
|---|---|
| 첫 화면 | 질문할 수 있고 대화가 비어 있다 |
| 대화가 한 번 오간 뒤 | 질문할 수 있고 견본 대화(질문 하나, 도구 줄 하나, 출력 하나)가 있다 |
| 로그인 전 | 로그인해야 질문하는 사이트에서 로그인하지 않았다 |
| 로그인한 뒤 | 견본 이름으로 로그인했고 대화가 비어 있다 |
| 고지 확인 전 | 고지를 아직 확인하지 않았다 |
| 고지 전문을 연 뒤 | 첫 화면에서 고지 전문을 열었다 |
| 로그인 시간이 끝남 | 로그인 시간이 끝났다 |

- 견본 대화와 견본 이름은 위젯 관리 화면이 든 정해진 값이고 운영자가 바꾸지 못한다. 견본 대화의 글은 완성 화면 `mk-preview-states.dc.html`의 것이다.
- 보는 상태는 늘 일곱이다. 로그인 주소가 비어 있거나 고지 전문이 비어 있어 실제 위젯이 그 상태에서 그릴 것이 줄어도, 미리보기는 실제 위젯이 그 입력에서 그리는 그대로 그린다. 상태를 숨기거나 따로 안내하지 않는다.
- 로그인 모드 사이트의 "로그인 전"에는 예시 질문이 보이지 않는다. 위젯이 그때 예시 질문을 그리지 않기 때문이다(widget-login-state의 명세). 확정한 그림의 "로그인 전"은 예시 질문 셋을 보였다("화면과 다르게 짓는 것").
- 밝기 단추 "밝게"와 "어둡게"는 미리보기의 위젯만 바꾼다. 위젯 관리 화면 자신의 밝기와 무관하다. 사이트 화면을 열 때의 값은 양식의 처음 밝기가 "밝게"나 "어둡게"면 그 값이고 "기기 설정을 따른다"면 "밝게"다. 운영자가 양식의 처음 밝기를 고치면 밝기 단추도 그 값으로 옮겨 간다.
- 미리보기 안의 위젯은 보기만 하는 그림이다. 그 안의 단추와 입력창은 포커스를 받지 않고 눌러도 아무 일도 일어나지 않으며, 화면 읽기 프로그램에는 "미리보기, 저장하지 않은 값으로 그린 위젯" 한 줄로 읽힌다.
- 미리보기 안은 굴려 볼 수 없다. 가리는 법("미리보기를 그리는 부품")이 마우스의 누름과 휠을 위젯에 넘기지 않기 때문이다. 미리보기 위에서 휠을 굴리면 위젯 안이 아니라 위젯 관리 화면이 구른다. 그래서 미리보기의 높이를 넘는 글은 한쪽 끝만 보인다. 실험에서 첫 화면의 긴 글은 처음이, 긴 대화는 끝이 보였다(손으로 봤다, `.scratch/portal-admin/probes/shared_widget_parts/README.md`의 "휠과 클릭"). 고지 전문을 그리는 부품은 아직 없어 그 글이 어느 쪽을 보일지는 보지 못했다. 넘친 나머지는 저장한 뒤 위젯 테스트 페이지의 실제 위젯에서 본다. 미리보기 아래에 흐린 도움말 한 줄이 그것을 알리고("문구"), 좁은 폭의 미리보기에도 같은 줄이 선다. 고르지 않은 안은 둘이고 둘 다 해 보지 않았다. 미리보기의 높이를 글에 맞춰 늘리면 미리보기의 위젯이 실제 위젯과 다른 높이로 그려진다. 가린 요소 밖에 스크롤하는 조작을 따로 두면 위젯 관리 화면이 부품 안에서 넘치는 자리를 찾아 대신 굴려야 한다(둘 다 어림이다). 이 셋을 셀프 리뷰 뒤에 사용자에게 물었고 사용자가 지금의 안인 "넘친 글은 테스트 페이지에서 보기"를 골랐다(일지 2026-11-16-1705 "셀프 리뷰 뒤에 물은 것과 답").
- 좁은 폭에서는 미리보기 칸이 없고, 화면 머리의 "미리보기" 단추가 미리보기를 화면 가득 연다(완성 화면 `mk-site-m.dc.html`).
- 사이트 등록 화면의 미리보기는 비운 칸마다 위젯의 기본값으로 그린다. 위젯의 이름과 에이전트가 모두 비어 있을 때 위젯 머리에 흐린 "위젯의 이름"을 두는 것은 그림의 제안 그대로다.

### 미리보기를 그리는 부품 (넘겨받았다. 패키지의 범위와 그 안의 규칙, 스토리와 사진의 자리, 가리는 법은 명세가 정했다. 손으로 봤다)

ADR 0065 결정 "미리보기"가 정한 것이다. 위젯 앱의 화면 부품을 `web/packages/` 아래의 공유 패키지로 옮겨 위젯 앱과 위젯 관리 화면이 같은 부품을 쓴다. 그 ADR이 이 명세에 넘긴 물음 둘(옮기는 데 드는 일, 옮긴 부품이 위젯 앱의 사진 비교를 그대로 통과하는지)은 `.scratch/portal-admin/probes/shared_widget_parts/`가 기준 커밋의 부품을 실제로 옮겨 보았다. 패치를 붙인 뒤 명령을 한 번씩 쳐서 본 실험이라, 아래의 결과는 "쟀다"가 아니라 "손으로 봤다"다(2026-11-16. 패치와 다시 돌리는 법과 본 판은 그 폴더의 `README.md`). 그 폴더의 스크립트 가운데 가리는 법을 본 것 하나는 기대와 견줘 종료 코드를 내지만, 패치를 붙이고 Storybook을 지은 체크아웃에서 한두 번 돌린 것이라 같은 종류로 적는다. 실제로 옮기는 때는 widget-login-state가 로그인 상태와 고지와 밝기 스위치의 화면을 지은 뒤라 그때의 부품 수와 줄 수는 다르다. 본 것은 옮기는 방식이 서는지다.

- **패키지.** `web/packages/widget-ui`(`@agent-os/widget-ui`)를 새로 둔다. 위젯의 화면 부품과, 부품이 읽는 값의 모양과 글자를 내는 모듈을 든다.
- **옮기기만 한다.** 옮기는 티켓은 파일을 옮기고 import와 설정을 맞추는 일만 한다. 부품의 모양과 동작을 고치지 않고 모듈을 쪼개지 않는다. 폴더의 모양(`components/` 아래의 층과 `lib/`)을 그대로 두어 옮긴 파일끼리의 import가 바뀌지 않게 한다. 실험에서 옮긴 20파일 가운데 17파일이 한 글자도 바뀌지 않았고, 변경 전체는 34파일에 더한 줄 137, 뺀 줄 31이었다(손으로 봤다). 값의 모양을 든 모듈에는 위젯 앱의 대화를 돌리는 쪽만 쓰는 규칙(대화의 상태를 잇는 함수, 재접속 간격, 상한의 계산)도 함께 들어 있다. 그것을 앱에 남기게 쪼개는 길은 해 보지 않았고, 옮기는 티켓에 넣지 않는다. 옮기기와 고치기를 한 변경에 섞지 않아야 "기준 그림이 그대로다"가 옮기기의 판정이 된다.
- **판정.** 위젯의 사진 비교가 기준 그림을 한 장도 고치지 않고 통과한다(Testing Decisions). 실험에서 `pnpm -C web verify`가 옮기기 전과 뒤에 같은 수로 통과했고(시험 2,754 통과, 1 건너뜀), 위젯의 사진 비교 44건이 정답 사진 77장과 그대로 맞았으며, 위젯 e2e 19건이 통과했다(손으로 봤다. 옮긴 뒤의 검사는 한 번씩 쳤다). 사진이 옮긴 소스를 찍었다는 것은 옮긴 뒤에 지은 스토리 색인의 43스토리가 모두 패키지에서 실린 것으로 봤다.
- **스토리와 사진의 자리.** 스토리는 부품과 함께 패키지로 가고, 위젯 앱의 Storybook이 패키지의 스토리를 싣는다. 스토리 시험과 사진 비교와 정답 사진의 폴더는 위젯 앱의 것을 그대로 쓴다. 스토리의 `title`은 바꾸지 않는다. 정답 사진의 이름이 스토리 id에서 나오고 그 id가 `title`에서 나오기 때문이다(코드를 읽었다, 그 폴더의 `README.md` "검사 결과"). 위젯 앱의 페이지 시험은 앱에 남는다. 패키지가 자기 Storybook과 사진 폴더를 갖는 길은 해 보지 않았고 고르지 않았다. 정답 사진 77장의 자리와 사진 비교의 명령과 CI의 잡을 함께 옮겨야 한다(어림).
- **스타일.** 패키지는 Tailwind가 패키지의 소스를 훑게 하는 CSS 파일 하나를 내보내고, 패키지를 쓰는 앱은 전역 CSS에서 그것을 들인다. 그 줄이 빠지면 빌드는 통과하고 부품은 규칙 없는 클래스로 그려진다. 실험에서 그 줄을 지우자 위젯 앱의 스토리 시험 43건 가운데 31건이, 위젯 관리 화면 대신 쓴 관리 화면 앱의 미리보기 스토리 여섯이 모두 "규칙 없는 클래스"로 실패했고, 관리 화면 앱의 빌드는 그대로 통과했다(손으로 봤다). 그래서 패키지를 쓰는 앱은 공유 화면을 그리는 스토리를 스토리 시험에 둔다. 위젯 관리 화면에서는 미리보기의 스토리가 그것이다.
- **감싼 요소.** 미리보기 칸은 위젯을 감싼 요소에 색 테마와 밝기와 밀도(보통)와 높이를 준다. 위젯의 틀이 자기 자리를 채우게 그려지기 때문이다. 실험에서 문서 뿌리가 밝고 촘촘한 밀도일 때, 감싼 요소에 준 어두운 밝기와 보통 밀도가 위젯에만 먹었다(손으로 봤다). 밝기 단추가 미리보기의 위젯만 바꾼다는 규칙("미리보기")이 이것에 선다.
- **값만으로 그린다.** 패키지의 코드는 생성 클라이언트와 데이터를 받아 오는 라이브러리(swr)를 값으로 들이지 않는다. 타입으로만 들인다. 그 규칙을 판정자에 패키지 전체로 걸고 판정자 시험에 사례를 붙인다(`.claude/rules/web-workspace.md`). 지금의 규칙은 organisms와 templates에만 걸려 있어 패키지의 화면(pages 층)에는 걸리지 않는다(코드를 읽었다, 기준 커밋의 `web/eslint.config.mjs`). 미리보기가 Agent OS에도 위젯 관리 서버에도 묻지 않는다는 것(ADR 0065)을 이 규칙과 미리보기의 시험("네트워크 요청이 하나도 나가지 않는다")이 함께 지킨다.
- **경계.** 패키지 안에서도 층의 규칙은 그대로 선다. 패키지의 molecule에 organism을 들이는 파일을 심자 판정자가 잡았다(손으로 봤다). 패키지에서 앱으로 가는 상대 import는 심어도 잡히지 않았다(손으로 봤다). 그 길이 열려 있으면 패키지를 거쳐 한 앱의 코드가 다른 앱에 실리므로, 패키지의 코드가 `apps/` 아래를 들이지 않는다는 규칙을 판정자에 더하고 사례를 붙인다. 새 패키지의 타입 검사 설정에는 디자인 시스템 패키지의 소스를 따라가는 데 필요한 옵션 하나가 더 든다(손으로 봤다, 그 폴더의 `README.md` "부딪힌 문제와 푼 방법").
- **가리는 법.** 미리보기 칸은 옮긴 부품을 고치지 않고 감싼 요소 둘로 위젯을 가린다. 바깥 요소에 그림의 역할(`role="img"`)과 이름 "미리보기, 저장하지 않은 값으로 그린 위젯"을 주고, 위젯을 감싼 안쪽 요소에 `inert`와 `aria-hidden="true"`를 함께 준다. "미리보기"가 정한 "보기만 하는 그림"을 짓는 방법이다.
  - 가리지 않으면 접근성 검사에 걸린다. 위젯의 틀은 대화 자리를 `<main>`으로 그리므로, 관리 화면 앱의 틀 안에 그대로 두자 스토리 시험의 axe가 위반 셋(`landmark-main-is-top-level`, `landmark-no-duplicate-main`, `landmark-unique`)을 냈다(손으로 봤다).
  - 둘을 함께 준 갈래와 `inert`만 준 갈래에서는 두 폭 모두 위반 셋이 사라지고 새 위반이 없었다. 위젯은 가린 뒤에도 그려졌고, 키보드의 Tab을 실제로 눌렀을 때 포커스가 위젯 안에 한 번도 들지 않고 다음 단추에 닿았으며, Chromium의 접근성 트리에는 그 이름의 그림 하나만 남고 위젯의 `<main>`과 제목과 단추와 입력창이 없었다(손으로 봤다. 폭 둘에서 한 번씩이고, 가리지 않은 갈래에서는 포커스가 위젯 안에 들고 단추가 트리에 잡혔다). 가리면 위젯의 제목도 트리에서 빠져 화면의 제목이 하나로 남는다.
  - `aria-hidden`만 준 갈래는 쓰지 않는다. 포커스가 위젯 안에 들었고 axe가 새 위반 둘(`aria-hidden-focus`, `nested-interactive`)을 냈다(손으로 봤다).
  - Chromium에서는 둘을 함께 준 것과 `inert`만 준 것이 갈리지 않았다. 그래도 둘을 함께 주는 까닭은 둘이다. 스토리 시험이 쓰는 역할 찾기는 `inert`를 보지 않고 `aria-hidden`을 보아, `inert`만 주면 "미리보기 안의 단추가 역할로 잡히지 않는다"를 그 시험으로 볼 수 없다(코드를 읽었다, 그 폴더의 `README.md` "읽은 코드"). 그리고 Chromium 밖의 브라우저와 실제 화면 읽기 프로그램이 `inert`만으로 위젯을 건너는지는 보지 않았다.
  - 시험이 보는 자리가 갈린다. axe 위반이 없다는 것, 이름 붙은 그림이 하나라는 것, 그 안의 단추가 역할로 잡히지 않는다는 것은 스토리 시험이 본다. "Tab이 미리보기를 건너 다음 조작에 닿는다"는 브라우저로 끝까지 가는 시험이 본다. 스토리 시험의 흉내 Tab은 `inert` 앞에서 문서 몸통에 머물러, 실제 Tab이 닿은 단추에 닿지 못했다(손으로 봤다).
  - 가린 미리보기는 마우스도 받지 않는다. 둘을 함께 준 갈래에서 위젯의 단추 자리를 실제 마우스로 눌러도 단추의 처리기가 불리지 않았고, 넘친 자리 위에서 휠을 굴려도 그 자리는 그대로인 채 페이지가 굴렀다. 가리지 않은 갈래에서는 처리기가 한 번 불리고 휠이 위젯 안을 굴렸다(손으로 봤다. 폭 둘에서 한 번씩이고, 누른 것은 단추 하나, 본 스크롤은 휠뿐이다). "미리보기"의 "눌러도 아무 일도 일어나지 않는다"가 이것으로 서고, 같은 까닭으로 미리보기 안을 굴려 볼 수 없다.
  - ADR 0065 결정 "미리보기"가 대가로 적은 "미리보기와 실제 위젯이 다른 것이 입력(저장 전 값, 미리 정한 예시 대화)뿐이도록 지켜야 한다"는 그대로 선다. 가리는 것은 위젯 관리 화면의 감싼 요소이고 부품은 같다. 부품이 `<main>`을 그리는 자리를 입력으로 바꾸는 안은 고르지 않았다. 옮기는 티켓이 부품을 고치게 되기 때문이다.
  - 대가는 둘이다. 미리보기가 화면 읽기 프로그램에 그림 한 줄로만 읽힌다. 화면을 보지 못하는 운영자는 미리보기로 위젯의 글을 확인하지 못하고, 양식의 칸에서 같은 글을 읽거나 저장한 뒤 위젯 테스트 페이지에서 실제 위젯을 쓴다. 그리고 미리보기의 높이를 넘는 글은 한쪽 끝만 보인다("미리보기"). 그 ADR에 이력을 더했다(서두 "이력").
- **옮기는 티켓이 함께 고치는 자리.** 배포 이미지를 짓는 파일 셋은 워크스페이스 패키지의 `package.json`을 하나씩 복사하므로 새 패키지의 줄을 더한다(코드를 읽었다. 이미지를 지어 보지는 않았다). 사진 비교의 컨테이너가 잇는 패키지의 목록을 견주는 시험(`web/tools/visual.test.ts`)에 새 패키지를 더한다. `.scratch/web-widget/probes/`의 변이 표 일곱과 `.scratch/admin-style/probes/canary/web_workspace_organisms.toml`이 옮기는 경로를 가리키므로 그 경로를 고친다. 옮긴 파일의 머리 주석이 가리키는 앱의 경로도 고친다. 규칙 문서는 "티켓이 코드와 같은 티켓에서 고치는 문서"에 있다.

### 사이트 등록과 고지 전문의 처음 값 (넘겨받았다. 문장과 넣는 때, 그 문장을 얻는 자리는 명세가 정했다)

- 사이트 등록 화면은 사이트 하나의 화면과 같은 탭 짜임이고 칸이 비어 있다(완성 화면 `mk-site-new.dc.html`). 사이트 이름 칸을 쓸 수 있고, 저장 띠는 "새 사이트"와 "취소", "등록"이다. 등록하면 그 사이트의 화면으로 간다.
- 사이트 이름의 꼴은 widget-admin-server의 명세가 정한 것을 따른다(ADR 0064 Consequences "명세가 짓는 것"). 화면의 도움말과 오류 문구는 그 꼴을 말로 옮긴다. 화면의 "영문 소문자, 숫자, 하이픈만 쓴다"는 그 명세가 서기 전의 가정이다.
- 등록 화면을 열면 "위젯 테스트 페이지에 담는다"는 켜져 있고 보증 모드는 익명이며, 고지 전문 칸에는 아래 세 문단이 처음 값으로 들어 있다.

  ```text
  이 위젯에서 보낸 질문과 받은 출력은 기록되고, 출력을 만들기 위해 모델 API로 보내집니다.

  이 브라우저를 알아보기 위해 익명 식별자를 쿠키로 둡니다. 쿠키는 마지막으로 질문한 뒤 30일 동안 남습니다.

  로그인하면 질문이 로그인한 계정과 함께 기록됩니다.
  ```

  둘째와 셋째 문단이 ADR 0064 결정 "고지의 고정 문장"의 두 문장이다. 첫 문단은 위젯 테스트 페이지가 고지 글을 적지 않은 사이트에 쓰던 기본 글에서 "이 페이지"를 "이 위젯"으로 바꾼 것이다.
- 처음 값은 등록 화면을 열 때 넣는다. 그 뒤 그 칸은 운영자의 것이고, 화면은 운영자가 적은 글을 고치지 않는다. "위젯 테스트 페이지에 담는다"를 꺼도 그 칸은 그대로다. 켤 때는 그 칸이 비어 있을 때에만 처음 값을 넣는다. 등록 화면에서든 이미 등록한 사이트의 화면에서든 같다. ADR 0064 결정 "고지의 고정 문장"이 처음 값을 넣는 자리를 "위젯 미리보기 페이지가 담는 사이트의 고지 전문"으로 적었으므로, 나중에 담는 사이트도 빈 칸이면 그 문장을 받는다. 치르는 값은 하나다. 담았다가 끈 사이트의 고지 전문에 위젯 테스트 페이지의 쿠키를 말하는 문장이 남을 수 있고, 그것을 지우는 일은 운영자의 몫이다.
- 운영자가 그 문장을 지우고 저장해도 받는다(ADR 0064가 적은 대가다). 다만 위젯 테스트 페이지에 담는 사이트의 고지 전문을 통째로 비우면 저장을 거절한다("저장할 때의 검사").
- 둘째 문단의 날 수는 위젯 테스트 페이지의 서버가 익명 식별자 쿠키에 주는 수명이고 지금 30일이다(기준 커밋의 `web/apps/portal/server/cookie-policy.ts`, 코드를 읽었다). 그 수와 처음 값의 문장은 위젯 테스트 페이지의 서버와 위젯 관리 화면이 함께 쓰는 `web/packages/` 아래의 공유 패키지 한 곳에 둔다. 두 앱이 수를 따로 들면 쿠키의 수명을 고쳤을 때 고지의 문장이 따라가지 않는다.

### 사이트 지우기 (명세가 정했다)

- 사이트 화면의 더 보기 메뉴에 "사이트 지우기"가 있고, 누르면 확인 창이 묻는다(완성 화면 `mk-delete.dc.html`). "지우기"를 누르면 그 사이트의 위젯 설정과 위젯 테스트 페이지 설정이 지워지고 사이트 목록으로 간다.
- 지운 일은 바꾼 기록에 남고, 지우기 전의 값이 이전 값으로 실린다("바꾼 기록").
- 지운 사이트의 이름을 적은 위젯은 등록되지 않은 사이트의 답을 받는다. 그 답과 그때 위젯이 그리는 것은 widget-admin-server와 widget-login-state의 명세가 정한 것이다. 위젯 테스트 페이지에서는 그 사이트가 빠진다.
- 지운 이름으로 사이트를 다시 등록할 수 있다. 새 사이트이고 지운 사이트의 값을 이어받지 않는다.
- 저장하지 않은 바뀜이 있어도 지울 수 있다. 확인 창이 한 번 묻는 것으로 충분하다.
- 지우기가 되지 않으면 확인 창을 닫지 않고, 창의 단추 위에 까닭을 한 줄로 보인다. 까닭은 셋이고 글은 저장 띠의 것과 짝을 이룬다("문구"). 저장 번호가 다르다(다른 계정이 그사이 이 사이트를 고쳤다), 요청이 실패했다, 로그인이 끝났다다. 저장 번호가 다를 때는 "지우기" 단추를 끄고 "취소"만 남긴다. 운영자가 창을 닫고 화면을 새로 불러와 고쳐진 값을 본 뒤에 다시 지우게 하려는 것이다. 지우기는 저장 띠가 없는 화면에서도 누를 수 있어 저장 띠에 알릴 수 없다. 확정한 그림에는 이 줄이 없다("화면과 다르게 짓는 것").

### 주소의 검사 (넘겨받았다. 사용자 정보 자리와 쿼리, 보고서 링크까지 넓힌 것은 명세가 정했다)

운영자가 등록하는 주소 넷(로그인 주소, 로그아웃 주소, 문의 링크, 보고서 링크)에 같은 규칙 하나를 건다.

- 주소로 풀리는 글이어야 하고, 2,000자까지 받는다.
- `https://`로 시작하는 완전한 주소이거나, 호스트 이름이 `localhost`이거나 `.localhost`로 끝나는 `http://` 주소여야 한다. `.localhost`까지 받는 것은 widget-login-state의 명세가 더한 ADR 0064의 이력이다(이력 2026-11-16 "시험할 때 받는 http 주소를 호스트 이름이 .localhost로 끝나는 것까지 넓힌다"). 호스트 이름은 주소를 풀어 이름 전체로 견준다. `http://localhost.example.test`는 받지 않는다(ADR 0064 Consequences "명세가 짓는 것"의 둘째).
- 사용자 정보 자리(`https://이름:비밀번호@…`의 `@` 앞)가 있는 주소는 받지 않는다. 이름만 있고 비밀번호가 없어도 받지 않는다. 그 자리는 자격을 싣는 데만 쓰이고, 위젯 설정은 누구나 읽는 주소로 나가며 바꾼 기록에 값이 그대로 남는다(같은 자리의 첫째).
- 쿼리와 `#` 뒤는 받는다. 로그인 주소에 돌아올 자리나 사이트의 식별자를 쿼리로 싣는 사이트가 있고, 쿼리를 막으면 그런 사이트가 등록하지 못한다. 대신 주소 칸의 도움말에 "주소에 비밀 값을 넣지 않는다. 위젯 설정은 누구나 읽을 수 있다."를 더한다. 쿼리에 든 값이 비밀인지는 검사가 가를 수 없다.
- 이 규칙을 보는 자리는 셋이다. 위젯 관리 서버가 저장할 때 보고 어긋나면 거절한다. 위젯 관리 화면이 칸을 떠날 때 본다. 위젯이 그 주소를 열거나 부르기 전에 한 번 더 본다. 위젯의 검사는 widget-login-state가 짓고, 이 기능이 거기에 사용자 정보 자리의 규칙과 2,000자 상한을 더한다. 사용자 정보 자리는 그 명세가 이 명세에 넘긴 일이고, 길이는 세 자리의 규칙을 글자까지 같게 두어 사례 표 하나로 잠그려고 이 명세가 더했다. 위젯 관리 서버와 위젯 관리 화면은 받지 않는 까닭까지 가르고("저장할 때의 검사"), 위젯은 받는지만 가른다. 위젯은 통과하지 못한 주소를 없는 것으로 다룰 뿐 까닭을 보이지 않기 때문이다(widget-login-state의 명세 "주소의 검사").
- 세 자리는 한 사례 표를 함께 읽어 같은 판정을 내는지 시험한다(Testing Decisions "주소의 사례 표"). 화면과 위젯은 TypeScript이고 서버는 파이썬이라 코드를 함께 쓸 수 없다.
- 보고서 링크는 지금 `http`나 `https` 주소면 받는다(기준 커밋의 `web/apps/portal/server/config.ts`, 코드를 읽었다). 이 명세가 위 규칙으로 좁힌다. 운영자가 등록하는 주소의 규칙을 하나로 두기 위해서이고, 값을 옮기는 길을 짓지 않으므로 옮기다 걸리는 값이 없다.
- 어느 도메인의 주소인지는 가리지 않는다(ADR 0064 결정 "주소의 검사").

### 저장 경로 (넘겨받았다. 경로의 가름과 중계가 넘기는 경로, 저장 번호, 거절의 꼴은 명세가 정했다)

위젯 관리 서버의 계약 파일에 운영자용 경로 일곱과 안쪽 길 하나를 더한다. 그 계약을 고치는 티켓이 이 기능의 첫 티켓이고 다른 티켓을 막는다. 경로의 이름과 접두사, 오류 답의 봉투는 widget-admin-server의 명세가 세운 관례를 따르고, 아래는 경로마다의 일이다.

| 경로 | 하는 일 |
|---|---|
| 지금 누구인지 | 받은 쿠키를 Agent OS의 "지금 누구인지"에 전하고 계정 이름을 답한다 |
| 갱신 | 받은 쿠키를 Agent OS의 "갱신"에 전하고, Agent OS가 낸 `Set-Cookie`를 그대로 되돌린다 |
| 사이트 목록 | 사이트마다 사이트 이름, 위젯의 이름, 에이전트, 위젯 테스트 페이지에 담았는지와 보증 모드, 열리는지와 까닭, 마지막으로 바꾼 때와 계정 |
| 사이트 하나 | 그 사이트의 위젯 설정과 위젯 테스트 페이지 설정 전부, 열리는지와 까닭, 마지막으로 바꾼 때와 계정, 저장 번호 |
| 사이트 등록 | 새 사이트를 만든다 |
| 사이트 고치기 | 그 사이트의 위젯 설정과 위젯 테스트 페이지 설정을 통째로 바꾼다 |
| 사이트 지우기 | 그 사이트를 지운다 |
| 위젯 테스트 페이지 설정(안쪽 길) | 위젯 테스트 페이지에 담은 사이트마다 사이트 이름, 발급자, 보증 모드, 보고서 링크, 위젯의 이름 |

- 운영자용 경로 일곱은 위젯 관리 화면의 포트로만 닿는다. 프록시의 방문자용 포트는 위젯이 위젯 설정을 받아 가는 경로 하나만 위젯 관리 서버로 넘긴다(ADR 0064 결정 "위젯 설정을 받아 가는 주소").
- 위젯 관리 화면의 중계는 운영자용 경로 일곱만 위젯 관리 서버로 넘긴다. 안쪽 길과 위젯 설정을 받아 가는 경로는 넘기지 않고, 그 밖의 경로로 온 요청은 위젯 관리 서버에 닿지 않은 채 없다는 답을 받는다. 관리 화면 앱의 중계는 상류의 경로를 가리지 않고 넘기므로(기준 커밋의 `web/apps/admin/next.config.ts`, 코드를 읽었다) 이 자리만은 그 방식을 그대로 따르지 않는다. 그대로 따르면 위젯 관리 화면용 포트로 온 요청 가운데 브라우저의 머리가 없는 것이 안쪽 길에 닿아, 위젯 테스트 페이지에 담은 사이트의 값을 로그인 없이 읽는다. 일곱을 어떻게 가르는지(한 머리 아래에 모으는지, 경로를 하나씩 드는지)는 계약 티켓이 정한다.
- 운영자용 경로 일곱은 요청 출처를 Agent OS와 같은 규칙으로 본다. `Sec-Fetch-Site`가 있으면 `same-origin`만 받고, 없으면 `Origin`도 없을 때만 받는다(ADR 0062 결정 "요청 출처 검사"). 위젯 관리 화면의 중계는 브라우저가 보낸 `Sec-Fetch-Site`와 `Origin`과 `Cookie`를 고치지 않고 위젯 관리 서버에 전하고, 판정은 위젯 관리 서버가 한다. 관리 화면의 중계와 Agent OS 서버가 일을 나눈 방식과 같다.
- 사이트를 읽고 쓰는 경로 다섯은 요청마다 로그인을 확인한다("로그인 확인"). 로그인한 운영자 계정이면 누구나 읽고 쓴다. 위젯 관리 서버는 계정의 단계를 묻지 않는다(ADR 0064 결정 "고칠 수 있는 계정").
- 사이트 고치기는 통째로 바꾼다. 화면이 양식의 모든 칸을 보내고, 서버가 지금 값과 견주어 바뀐 항목을 가른다. 바뀐 항목이 하나도 없으면 아무것도 쓰지 않고 성공을 답한다. 바꾼 기록도 남기지 않고 저장 번호도 올리지 않는다.
- **저장 번호.** 사이트마다 저장할 때 하나씩 오르는 수를 든다. 이 명세는 그 수를 저장 번호라고 부른다. "판"은 이 저장소에서 제품과 형식의 판을 가리키는 말이라 쓰지 않았다. "사이트 하나"의 답에 저장 번호가 실리고, "사이트 고치기"와 "사이트 지우기"는 화면이 읽은 저장 번호를 함께 보낸다. 서버의 것과 다르면 쓰지 않고 거절한다. 화면은 저장 띠에 다른 계정이 먼저 고쳤다고 알린다("바뀜, 저장 띠, 떠날 때"). 통째로 바꾸는 저장이라 저장 번호를 보지 않으면 늦게 저장한 운영자가 앞 운영자의 바뀜을 모르는 채 덮고, 바꾼 기록의 이전 값이 그 운영자가 화면에서 본 값과 달라진다.
- **거절의 꼴.** 값이 어긋난 저장은 칸마다의 까닭을 목록으로 답한다. 한 줄은 항목의 이름과 까닭의 이름이고, 발급자가 겹쳤을 때는 겹친 사이트의 이름을 더 싣는다. 어긋난 값 자체는 싣지 않는다. 첫 어긋남에서 멈추지 않고 모두 모아 낸다. 화면에 보일 문장은 서버가 아니라 화면이 든다.
- 답의 갈래는 여섯이다. 로그인하지 않았거나 로그인 시간이 끝났다, 요청 출처가 어긋났다, 그 이름의 사이트가 없다, 저장 번호가 다르다, 값이 어긋났다, 로그인을 확인하지 못했다(Agent OS 서버가 답하지 않는다)다. 상태 코드는 계약 티켓이 widget-admin-server의 관례에 맞춰 정하되 여섯이 서로 다른 답이어야 한다.
- 안쪽 길은 로그인을 보지 않는다. 그 답은 위젯 테스트 페이지에 담은 사이트의 값만 싣고, 담지 않은 사이트와 바꾼 기록을 싣지 않는다. 위젯 테스트 페이지 설정에는 비밀을 두지 않는다(ADR 0064 Consequences "신뢰와 노출"). 브라우저가 보낸 요청(`Sec-Fetch-Site`나 `Origin`이 있는 요청)은 거절한다. 안쪽 길에 닿는 길은 같은 서버나 컨테이너 네트워크 안에서 위젯 관리 서버를 직접 부르는 것뿐이다. 프록시의 방문자용 포트도 위젯 관리 화면의 중계도 그 경로를 넘기지 않는다.
- 시험과 예시 배포는 처음 값을 이 저장 경로로 넣는다(ADR 0064 결정 "값을 옮기는 길은 짓지 않는다"). 운영자 계정으로 로그인해 받은 쿠키로 부른다. 프로그램용 열쇠는 두지 않는다(ADR 0062 결정 "자격").

### 저장할 때의 검사 (넘겨받았다. 까닭의 가름과 동시에 온 저장에서 겹침을 막는 법은 명세가 정했다)

위젯 관리 서버는 사이트 등록과 사이트 고치기에서 아래를 보고, 하나라도 어긋나면 아무것도 쓰지 않는다.

| 까닭 | 걸리는 때 |
|---|---|
| 비었다 | 사이트 이름, 에이전트가 비었다. 위젯 테스트 페이지에 담는 사이트의 발급자, 보증 모드, 고지 전문이 비었다 |
| 꼴이 아니다 | 사이트 이름이 widget-admin-server가 정한 꼴이 아니다. 한 줄인 칸에 줄바꿈이 있다 |
| 너무 길다 | 글이 그 칸의 상한을 넘는다. 주소인 칸의 2,000자도 이 까닭이다. 예시 질문이 넷을 넘는다 |
| 고르는 값이 아니다 | 색 테마, 처음 밝기, 로그아웃을 부르는 방법, 모양 넷, 보증 모드가 정해진 값 밖이다 |
| 주소가 아니다 | 주소인 칸이 "주소의 검사"의 꼴에 어긋난다. 주소로 풀리지 않는다, `https://`도 받는 `http://` 주소도 아니다 |
| 주소에 사용자 정보 자리가 있다 | 주소인 칸의 주소에 사용자 정보 자리가 있다. 꼴은 맞지만 받지 않는 주소라 화면이 다른 글을 보이도록 따로 가른다("문구") |
| 이름이 이미 있다 | 등록하려는 사이트 이름이 이미 있다 |
| 발급자가 겹친다 | 위젯 테스트 페이지에 담는 다른 사이트가 같은 발급자를 쓴다 |

- 발급자의 겹침은 위젯 테스트 페이지에 담은 사이트들 사이에서 글자 그대로 견준다. 발급자가 겹치면 익명 사이트의 토큰으로 로그인 사이트의 에이전트를 열 수 있기 때문이다(ADR 0050, ADR 0064 결정 "시작 검사가 가는 자리"의 첫째).
- 이름과 발급자의 두 검사는 다른 사이트의 줄을 보는 검사다. 서로 다른 사이트의 저장 둘이 같은 때에 오면, 각자 아직 저장이 끝나지 않은 상대의 줄을 보지 못한 채 둘 다 검사를 지날 수 있다. 저장 번호는 사이트마다 따로 올라 그 둘을 줄 세우지 못한다("저장 경로"). 그래서 이 둘은 서버가 쓰기 전에 읽어 보는 검사에만 맡기지 않고 데이터베이스의 제약으로도 건다. 사이트 이름은 표 전체에서 하나뿐이어야 하고, 발급자는 위젯 테스트 페이지에 담는 사이트들 사이에서 하나뿐이어야 한다. 담지 않는 사이트의 발급자는 견주지 않는다. 제약에 걸린 저장은 아무것도 쓰지 않고, 읽어 보는 검사가 거절했을 때와 같은 까닭("이름이 이미 있다", "발급자가 겹친다")과 같은 꼴(발급자면 겹친 사이트의 이름을 싣는다)로 답한다. 제약을 거는 꼴(조건이 붙은 유일 인덱스 등)과, 사이트 이름의 제약이 widget-admin-server의 표에 이미 있는지는 표를 더하는 티켓이 그 기능이 세운 표에 맞춰 정한다.
- 위젯 테스트 페이지에 담는 사이트의 고지 전문이 비면 거절하는 것은 이 명세가 더했다. 위젯 테스트 페이지는 고지를 확인하지 않은 브라우저에 토큰을 내지 않고 고지 확인을 요구하는데, 고지 전문이 없으면 위젯이 그 요구에 보일 덮개가 없어 그 사이트의 위젯이 서지 못한다(widget-login-state의 명세가 이 명세에 넘긴 물음이다).
- 에이전트가 실제로 있는지, 그 사이트의 열 에이전트에 드는지는 보지 않는다. 위젯 관리 서버는 Agent OS에 그것을 묻지 않고, 틀린 이름은 `serve`가 질문을 받을 때 거절한다(ADR 0064 결정 "시작 검사가 가는 자리").
- 발급자가 사이트 파일에 있는지도 보지 않는다. 위젯 관리 서버는 사이트 파일을 읽지 않는다(같은 결정). 그 사이트는 저장되고, 위젯 테스트 페이지가 열지 않는다("닫힌 사이트를 알리는 길").
- 로그인 주소와 로그아웃 주소는 하나만 있어도 받는다. 위젯이 둘을 따로 다룬다.
- 보증 모드 "로그인"과 "둘 다"는 회사 로그인의 문이 서기 전에도 받는다. 그때 위젯 테스트 페이지가 로그인 사이트를 어떻게 다루는지는 "위젯 테스트 페이지의 운영자 문"에 있다.

### 바꾼 기록 (넘겨받았다. 한 줄이 담는 것과 지운 사이트의 기록은 명세가 정했다)

- 사이트를 등록하고, 고치고, 지울 때마다 위젯 쪽 데이터베이스의 표에 한 줄을 남긴다. 저장과 기록은 한 트랜잭션이다. 기록을 쓰지 못하면 저장도 되지 않는다.
- 한 줄이 담는 것은 다섯이다. 시각, 계정 이름, 사이트 이름, 한 일(등록, 고침, 지움), 바뀐 항목마다의 이전 값과 새 값이다. 등록은 이전 값이 없고 지움은 새 값이 없다. 고침은 바뀐 항목만 싣는다.
- 계정 이름은 로그인 확인에서 Agent OS가 답한 이름이다. 화면이 보낸 값을 쓰지 않는다.
- 기록은 사이트를 지워도 남는다. 사이트 이름은 글자로 남고, 같은 이름으로 다시 등록한 사이트의 기록과 한 표에 차례대로 선다.
- 기록을 보는 화면은 0.1 판에 없고, 기록을 내주는 경로도 두지 않는다(ADR 0064 결정 "바꾼 기록"). 시스템 관리자가 데이터베이스에서 읽는다.
- 사이트 목록과 사이트 화면의 "마지막으로 바꾼 때"와 계정은 그 사이트의 가장 새 기록과 같은 값이다. 사이트의 줄에 따로 두든 기록에서 읽든 화면에 보이는 값이 기록과 어긋나지 않아야 한다.
- 기록에는 값이 그대로 남는다. 위젯 설정과 위젯 테스트 페이지 설정에 비밀을 두지 않는다는 전제에 선 것이고(ADR 0064), 주소의 사용자 정보 자리를 받지 않는 것이 그 전제를 지키는 검사다.
- 쿠키와 토큰은 기록에도 로그에도 남기지 않는다(원칙 V).
- 표는 widget-admin-server가 세운 표 관리 도구로 더한다. 이 기능이 그 데이터베이스에 더하는 것은 넷이다. 바꾼 기록의 표, 위젯 테스트 페이지 설정(담는지, 발급자, 보증 모드, 보고서 링크), 사이트마다의 저장 번호, 위젯 설정의 예시 질문의 모양("예시 질문의 모양을 답에 싣는다")이다. 발급자가 겹치지 않게 하는 제약은 위젯 테스트 페이지 설정의 칸과 함께 더한다("저장할 때의 검사").

### 로그인 확인 (넘겨받았다. 갱신을 일으키는 쪽, 전하고 되돌리는 것의 꼴, 부르는 클라이언트, 답의 가름은 명세가 정했다. 쟀다)

ADR 0064 결정 "로그인"과 ADR 0065 결정 "위젯 테스트 페이지"가 정한 것이고, 위젯 관리 서버와 위젯 테스트 페이지의 서버가 같은 규칙을 쓴다. 두 ADR이 돌려 보지 않았다고 넘긴 흐름은 `.scratch/portal-admin/probes/login_relay/`가 대역과 Chromium으로 쟀다. 아래의 "쟀다"는 그 프로브가 낸 것이고, 재는 법과 판과 재지 못한 것은 그 폴더의 `README.md`에 있다. Agent OS의 로그인 경로는 admin-login이 짓기 전이라 Agent OS는 대역이고, 대역이 고른 것(경로와 쿠키의 이름, 유예의 뜻, 거절 때 쿠키를 지우는 줄)이 admin-login의 명세와 다르게 서면 그 자리를 다시 잰다(Further Notes).

- **확인.** 로그인을 보는 경로는 요청마다 받은 로그인 쿠키를 Agent OS의 "지금 누구인지"에 전해, 로그인이 유효한지와 계정 이름을 받는다. 서버는 그 답을 기억하지 않는다. 그래서 관리 화면에서 로그아웃하면 다음 요청부터, 계정이 '쓰지 않음'이 되면 짧은 JWT의 수명(기본 5분, ADR 0062 결정 "유지 시간") 안에 이 화면에서도 나간다.
- **전하는 것.** Agent OS에 보내는 요청에는 운영자의 로그인 쿠키 둘을 담은 `Cookie` 머리만 싣는다. 브라우저가 보낸 다른 머리(`Sec-Fetch-Site`, `Origin`, `Referer`)와 다른 쿠키는 싣지 않는다. `Cookie`만 실은 요청은 잰 클라이언트 다섯(`httpx` 0.28.1, `httpx2` 2.13.0, Node의 `fetch`, `node:http`, `openapi-fetch` 0.17.0) 모두에서 `Origin`도 `Sec-Fetch-Site`도 없이 닿아 Agent OS 대역의 요청 출처 검사를 지났다(쟀다). Node의 `fetch`와 `openapi-fetch`는 `sec-fetch-mode: cors`를 스스로 붙인다. 대역의 검사는 ADR 0062가 적은 대로 `Sec-Fetch-Site`와 `Origin`만 보아 걸리지 않았고, admin-login이 `Sec-Fetch-Mode`도 보게 지으면 이 길이 걸린다(어림. admin-login의 기능 계획에 적었다). 브라우저의 머리를 그대로 전한 대조에서는 주소창으로 연 요청(`Sec-Fetch-Site: none`)과 다른 포트의 링크로 연 요청(`same-site`)이 403으로 걸렸고, 화면의 스크립트가 보낸 요청은 그 포트 기준의 `same-origin`이 Agent OS 대역에 자기 출처의 것처럼 닿아 지났다(쟀다). 그래서 요청 출처는 Agent OS에 맡기지 않고 서버마다 자기 포트에서 본다("저장 경로", "위젯 테스트 페이지의 운영자 문").
- **갱신을 일으키는 쪽은 화면이다.** 서버는 "지금 누구인지"가 로그인 시간이 끝났다고 답해도 스스로 "갱신"을 부르지 않고, 로그인하지 않았다는 답을 낸다. 화면의 스크립트가 그 답을 받으면 서버의 "갱신"을 부르고, 그 응답을 받은 뒤 같은 요청을 다시 보낸다. 같은 탭에서 그 답을 함께 받은 요청들은 진행 중인 갱신 하나를 함께 기다린다. 요청 하나는 한 번만 다시 보내고, 다시 보낸 요청도 같은 답을 받으면 로그인하지 않은 것으로 다룬다. 관리 화면의 규칙(ADR 0062 결정 "로그인 상태"의 "화면은 요청이 401로 돌아오면 갱신을 한 번 부르고 그 요청을 다시 보낸다")과 같다.
  - 서버가 스스로 갱신하는 꼴은 고르지 않았다. 탭 하나가 동시에 보낸 요청 넷이 저마다 같은 갱신용 번호로 갱신을 불러, 유예가 없을 때 Agent OS 대역이 옛 번호의 재사용으로 그 로그인을 끊었다(쟀다).
  - 화면이 부르는 꼴에서는 같은 번호를 든 갱신이 없었고, 유예가 없어도 로그인이 살아 있었다. 답 하나가 갱신이 끝난 뒤에 닿아 갱신이 둘이 된 회차에서도, 둘째가 첫 갱신이 낸 새 번호를 들고 가 살아 있었다(쟀다). 잰 것은 프로브의 화면 스크립트다. 갱신의 응답을 받기 전에 둘째 갱신을 부르는 꼴로 지으면 같은 번호가 둘 간다(어림). 그래서 "진행 중인 갱신을 함께 기다린다"와 "응답을 받은 뒤 다시 보낸다"를 화면의 시험이 지킨다(Testing Decisions).
  - ADR 0064 결정 "로그인"의 문장은 서버가 스스로 이어 주는 것으로도 읽혀, 그 ADR에 이력을 더했다(서두 "이력").
  - 위젯 테스트 페이지의 서버 대역(Node)에서도 화면이 부르는 꼴이 유예 없이 살아 있었다. 전역 `fetch`로 부른 길과 `node:http`로 부른 길에서 같은 번호를 든 갱신이 없었고, 다음 만료 뒤의 요청과 갱신도 됐다. 위젯 관리 서버 대역이 `httpx2`로 부를 때도 같았다(쟀다). 이 셋은 유예가 없는 회차를 하나씩만 쟀다. 서버가 스스로 갱신하는 꼴, 유예가 있는 회차, 답 하나가 늦게 닿는 회차, 탭 둘의 회차는 위젯 관리 서버 대역이 `httpx`로 부르는 길에서만 쟀다.
- **되돌리는 것.** "갱신"의 응답에는 Agent OS가 낸 `Set-Cookie`를 줄마다 옮긴다. 줄의 수와 차례와 글자를 바꾸지 않고, 여러 줄을 한 값으로 합치지 않는다. 갱신이 거절될 때 Agent OS가 쿠키를 지우는 줄을 내면 그것도 같은 방식으로 옮긴다. ADR 0064 Consequences "명세가 짓는 것"의 셋째다. 다섯 길(위젯 관리 화면의 Next 중계와 파이썬 서버를 거친 길을 `httpx`와 `httpx2`로 하나씩, Node 서버가 `fetch`와 `node:http`와 `openapi-fetch`로 부른 길 하나씩) 모두에서 브라우저가 받은 두 줄이 대역이 낸 두 줄과 글자까지 같았고, 저장된 쿠키의 속성이 갱신 전과 같았다(쟀다). 두 줄을 한 값으로 합쳐 옮긴 대조에서는 JWT 쿠키만 새 값이 되고 갱신용 번호 쿠키가 옛 값으로 남아, 다음 갱신이 옛 번호의 재사용이 되는 상태였다(쟀다).
- **저장하지 않는다.** 서버는 쿠키를 저장하지도 로그에 남기지도 않는다(ADR 0064 결정 "로그인", 원칙 V). Agent OS를 부르는 HTTP 클라이언트가 응답의 `Set-Cookie`를 기억하지 않게 짓는다.
- **부르는 클라이언트.** 두 서버 모두 새 의존성을 더하지 않고, 응답의 쿠키를 기억하지 않는 클라이언트로 부른다.
  - 위젯 관리 서버는 이 저장소의 런타임 의존성에 이미 있는 `httpx2`로 부른다(`docs/constitution/tech.md`의 런타임 의존성 행. 지금은 MCP 어댑터가 쓴다고 선언해 둔 것이고, `httpx`는 시험 전용이라 쓰지 않는다). 잠금 파일에 새 패키지가 들지 않는다. 그 서버를 짓는 티켓이 그 행에 이 쓰임을 적는다("티켓이 코드와 같은 티켓에서 고치는 문서"). `httpx2` 2.13.0의 `AsyncClient`는 받은 `Set-Cookie`를 클라이언트의 쿠키 통에 기본으로 넣었고, 통에 든 쿠키 가운데 `Secure`가 없는 것을 쿠키 없이 온 다음 요청에 실었다(쟀다). 로그인 쿠키는 실리지 않았는데, 그 까닭이 `Secure`인데 대역의 주소가 `http://`여서라는 것은 어림이고 `https://` 주소에서는 재지 못했다. 그래서 통이 쿠키를 받지 않게 짓는다. 그 판의 `AsyncClient`에는 쿠키 저장을 끄는 인자가 없어(코드를 읽었다), 프로브는 받는 도메인이 하나도 없는 정책의 통(표준 라이브러리 `http.cookiejar`)을 주었다. 그 클라이언트는 갱신 응답을 받은 뒤에도 통이 비어 있었고, 요청이 든 `Cookie` 머리는 그대로 Agent OS 대역에 닿아 갱신이 됐다(쟀다). 요청마다 클라이언트를 새로 만드는 방법과 응답 뒤에 통을 비우는 방법은 재지 않았다. 어느 방법으로 짓든 시험이 "기억하지 않는다"를 지킨다(Testing Decisions).
  - 위젯 테스트 페이지의 서버는 전역 `fetch`를 직접 부르지 않고 생성 클라이언트(`openapi-fetch`)로 부른다. `web/` 아래의 코드에 걸린 규칙이고(ADR 0021, `web/eslint.config.mjs`), 같은 판정자가 앱이 `openapi-fetch`를 직접 들이는 것도 막으므로 그 클라이언트는 생성 클라이언트 패키지에 더한다. Agent OS의 두 경로를 부르는 클라이언트는 `web/packages/api-client`에, 위젯 관리 서버의 안쪽 길을 부르는 클라이언트는 widget-admin-server가 세우는 그 서버의 생성 클라이언트 패키지에 둔다("선행 기능에 기대는 것"). 두 클라이언트는 토큰 머리를 싣지 않고, 호출마다 받은 `Cookie` 머리와 제한 시간의 신호를 받는다.
  - `openapi-fetch` 0.17.0의 클라이언트로 부른 길에서 대역이 받은 머리는 전역 `fetch`를 직접 부른 길과 이름도 값도 차례도 같았고, `Origin`도 `Sec-Fetch-Site`도 없어 요청 출처 검사를 지났다(쟀다). `Set-Cookie`는 호출이 돌려준 원래의 응답에서 줄마다 꺼낼 수 있었고(`response.headers.getSetCookie()`), 브라우저가 받은 두 줄과 거절 때 지우는 두 줄이 대역이 낸 것과 같았다(쟀다). 그 클라이언트는 받은 쿠키를 다음 요청에 싣지 않았고, `Secure`가 없는 쿠키로 갈라 본 갈래에서도 그랬다(쟀다. Node 24.19.0에서 본 것이다). 제한 시간의 신호(`AbortSignal.timeout`)를 넘긴 호출은 제한 시간에 `TimeoutError`를 던졌고, 던져진 것의 모양이 전역 `fetch`를 직접 부른 길과 같았다(쟀다. 답의 머리가 오기 전에 걸린 경우다).
  - 잰 것은 타입을 주지 않은 클라이언트에 경로 글자를 준 호출이고, 몸이 없는 호출이다. 계약에서 만든 타입을 준 클라이언트가 실행 때 똑같이 군다는 것은 어림이다. 이 길로는 화면이 갱신을 부르는 흐름 전체를 재지 않았고, 안에서 전역 `fetch`를 부르므로 `fetch` 길과 같으리라고 본다(어림). 그 클라이언트로 지은 서버의 시험이 위 사례들을 다시 본다(Testing Decisions).
- **갱신이 제한 시간에 끊겼을 때.** "갱신"에도 같은 제한 시간이 걸린다(아래 "답의 가름"). Agent OS가 번호를 이미 바꿨는데 그 답이 제한 시간 뒤에 오면 새 번호가 브라우저에 닿지 않는다. 프로브의 대역은 끊긴 호출에서도 번호를 바꿨다(코드를 읽었다). 그 뒤의 갱신은 옛 번호를 들고 가므로, 유예 안이면 받아 주고 유예가 지났으면 로그인이 끊긴다고 본다(어림. 그 뒤의 갱신은 재지 않았다). 관리 화면이 Agent OS를 직접 부르다 답을 받지 못했을 때와 같은 일이라, 따로 막지 않고 "탭 사이의 동시 갱신"의 끝 항목처럼 다룬다. 운영자는 다시 로그인하고 저장하지 않은 바뀜은 화면이 지킨다.
- **부르는 경로는 둘이다.** "지금 누구인지"와 "갱신"뿐이다. 로그인, 로그아웃, 계정을 다루는 경로를 부르지 않는다. 시험이 그 둘 밖의 호출이 없는지를 본다(Testing Decisions).
- **답의 가름.** 로그인 쪽의 답은 둘이다("저장 경로"의 여섯 가운데 둘). Agent OS가 로그인하지 않았다고 답하면 "로그인하지 않았거나 로그인 시간이 끝났다"를 낸다. 쿠키가 없는 것, 시간이 끝난 것, 갱신이 거절된 것을 가르지 않는다. 화면은 어느 쪽이든 갱신을 한 번 부르고, 그래도 같은 답이면 로그인이 필요하다고 보인다. Agent OS가 정해진 시간 안에 답하지 않거나 서버 오류를 답하면 "로그인을 확인하지 못했다"를 낸다. 그 시간은 2초다(어림. 고른 근거는 "위젯 테스트 페이지 설정을 데이터베이스로"의 제한 시간에 있다). 확인하지 못했을 때 화면은 로그인이 끝났다고 보이지 않는다("로그인하지 않았거나 로그인 시간이 끝났을 때").
- **탭 사이의 동시 갱신.** 탭 하나 안에서는 위 규칙만으로 유예 없이 선다. 관리 화면의 탭과 위젯 관리 화면의 탭처럼 포트가 다른 탭 둘이 같은 순간에 갱신하면, 유예가 없을 때 로그인이 끊겼다(쟀다). 포트가 다르면 출처가 달라 탭 사이에 갱신을 하나로 묶을 길이 없다고 본다(어림). 이 경우는 ADR 0062가 admin-login의 명세에 넘긴 "탭 둘이 동시에 갱신할 때의 짧은 유예"에 기댄다(ADR 0064 결정 "로그인"). 위젯 테스트 페이지의 탭까지 치면 같은 로그인을 갱신하는 화면이 셋이 된다.
  - 이 기능이 그 유예에 바라는 것은 하나다. 유예 안에 온 옛 번호를 받아 준 뒤에는, 그 갱신들이 낸 번호 가운데 어느 것이 브라우저에 남든 다음 갱신이 통해야 한다. 프로브의 대역에서, 앞서 낸 번호를 옛 번호로 돌리는 유예는 응답이 닿는 차례를 일부러 뒤집은 회차에서 다음 갱신에 로그인을 끊었고, 앞서 낸 번호도 통하게 두는 유예는 살아 있었다(쟀다). 차례를 건드리지 않은 회차에서는 이 PC의 루프백에서 뒤집힘이 나지 않았고, 실제 네트워크에서 얼마나 뒤집히는지는 재지 못했다. admin-login의 기능 계획에 이것을 적었다.
  - 유예가 받아 주지 못해 로그인이 끊기면 운영자는 관리 화면에서 다시 로그인한다. 저장하지 않은 바뀜은 화면이 지킨다("로그인하지 않았거나 로그인 시간이 끝났을 때").

### 위젯 테스트 페이지 설정을 데이터베이스로 (넘겨받았다. 받아 오는 때와 차례, 제한 시간, 받아 오지 못했을 때의 답은 명세가 정했다. 쟀다)

ADR 0064 결정 "위젯 미리보기 페이지 설정"이 정한 것이다. 위젯 테스트 페이지의 서버는 담는 사이트의 목록과 사이트마다의 값을 설정 파일이 아니라 위젯 관리 서버의 안쪽 길("저장 경로")에서 받아 온다. 그 ADR이 이 명세에 넘긴 물음(요청 때 위젯 관리 서버에 물어도 응답이 느려지지 않는지, 그 값을 짧게 기억할지)은 `.scratch/portal-admin/probes/settings_fetch/`가 쟀다. 위젯 관리 서버가 아직 없어 위젯 관리 서버, "지금 누구인지", 위젯 테스트 페이지의 서버가 모두 대역이고, PC 한 대의 루프백에서 PostgreSQL만 컨테이너로 띄워 쟀다. 아래의 "쟀다"는 그 범위의 값이다. 배포(컨테이너 사이의 네트워크)의 값은 재지 못했고, 재는 법과 판과 재지 못한 것은 그 폴더의 `README.md`에 있다.

- **받아 오는 때.** 사이트의 값이 필요한 요청마다 받아 온다. "들어온 사람", 사이트의 토큰, 고지 확인의 기록이 그 요청이다. 페이지, 정적 파일, 상태 확인은 사이트의 값을 싣지 않으므로("위젯 테스트 페이지의 운영자 문") 위젯 관리 서버도 Agent OS도 부르지 않는다. 그래서 위젯 관리 서버가 내려가 있어도 페이지와 문은 뜨고 상태 확인은 지금처럼 답한다.
- **차례.** 로그인을 먼저 확인하고("로그인 확인"), 들어온 것이 확인된 요청에서만 받아 온다. 로그인하지 않은 요청은 위젯 관리 서버에 닿지 않는다. 위젯 테스트 페이지의 주소는 방문자용 포트에 열려 있어, 누구나 보낼 수 있는 요청이 데이터베이스 조회를 일으키지 않게 하려는 것이다. 두 호출을 함께 보내면 더 빠르지만(아래) 고르지 않았다.
- **기억하지 않는다.** 받아 온 값을 요청 사이에 기억하지 않는다. 운영자가 저장한 값은 다음 요청부터 보인다. 근거는 아래다.
  - 요청마다 한 번 묻는 것이 페이지 응답에 더한 시간은 호스트의 CPU 부하가 낮던 되풀이 넷에서 중앙값 3.3~4.8ms, p95 4.9~13.5ms였다(`node:http`로 연결을 이어 쓸 때). 부하가 100%이던 되풀이 둘에서는 중앙값 21~39ms, p95 62~94ms였다(쟀다).
  - "지금 누구인지"까지 차례로 부르면 중앙값 26.3~27.2ms가, 함께 부르면 15.7~15.9ms가 더해졌다(전역 `fetch`, 부하가 낮던 되풀이 넷. 쟀다). 이 값에는 잰 PC의 Node 24.19.0이 쉬던 연결에 요청을 쓰기 전에 기다리는 타이머가 호출마다 들어 있다. 윈도에서 그 타이머는 15.6ms 뒤에 불렸고, 리눅스 컨테이너의 Node 24.22.3에서는 이어 쓰는 `fetch`와 `node:http`의 중앙값 차가 0.2~0.3ms였다(쟀다). 배포는 리눅스 컨테이너라 그 몫이 작으리라고 보지만, 두 호출을 차례로 부르는 갈래를 리눅스에서 재지는 않았다(어림).
  - 2초 동안 기억하는 갈래는 50ms마다 요청을 보냈을 때 300 가운데 290이 기억에서 답했다(쟀다). 요청이 2초에 한 번보다 드물면 기억은 한 번도 맞지 않는다. 위젯 테스트 페이지는 운영자가 시험하는 페이지라 요청이 그만큼 잦지 않다고 본다(어림. 실제 빈도는 재지 않았다).
  - 기억하면 저장한 값이 그 시간만큼 늦게 보인다. 보증 모드를 익명에서 로그인으로 바꾼 사이트에도 그 시간 동안은 익명 토큰이 나간다.
  - 기억은 위젯 관리 서버가 내려간 것을 가려 주지 못한다. 기억한 시간이 지나면 똑같이 받아 오지 못한다.
- **연결.** 연결을 이어 쓸지 요청마다 새로 맺을지는 정하지 않는다. 새로 맺어도 이어 쓸 때보다 중앙값이 0.5~0.8ms 느릴 뿐이었고(`node:http`, 부하가 낮던 되풀이 넷), 대역이 쉬는 연결을 닫은 뒤(6초를 쉰 뒤)의 첫 요청도 새 연결로 답을 받았다(쟀다, 방법마다 서른 번). 대역이 연결을 닫는 바로 그 순간에 보낸 요청은 재지 못했다.
- **제한 시간.** 위젯 관리 서버를 부르는 호출에 제한 시간 2초를 건다(어림). 제한 시간이 없을 때 3초 늦게 답하는 대역을 부른 요청은 페이지 응답도 3초 넘게 걸렸다. 연결만 받고 답하지 않는 상대에는 `fetch`가 304초와 307초 뒤에야 스스로 끊었고 `node:http`는 330초까지 끊지 않았다(쟀다. 답하지 않는 갈래는 실행마다 한 번씩 모두 두 번이다). 1초 제한을 건 호출은 1.00~1.02초에 끊겼다(쟀다). 살아 있는 대역을 부른 요청 36,120개에서 실패는 없었고, 페이지 응답의 최댓값은 부하가 높던 실행의 411ms였다(쟀다). 2초는 그 값보다 넉넉히 길게 고른 값이고, 배포에서 맞는 값인지는 재지 못했다. 끊긴 호출도 대역은 끝까지 처리했으므로(쟀다) 제한 시간은 위젯 관리 서버의 일을 덜어 주지 않고 운영자가 기다리는 시간만 줄인다. "로그인 확인"과 "닫힌 사이트를 알리는 길"의 제한 시간도 같은 값이다. 제한 시간은 서버를 지을 때 받는 값으로 두어 시험이 짧은 값으로 돈다.
- **받아 오지 못했을 때.** 연결이 거절되거나, 제한 시간이 지나거나, 위젯 관리 서버가 오류를 답하거나, 답이 꼴에 맞지 않으면 받아 오지 못한 것이다. 앞서 받은 값을 대신 쓰지 않는다.
  - "들어온 사람"은 계정 이름과 함께 사이트의 목록을 받아 오지 못했다고 답한다. 로그인은 확인됐으므로 페이지는 문으로 돌아가지 않는다. 위쪽 띠의 "운영자 `<계정 이름>`"을 그대로 두고, 위젯 자리에 경고 알림과 보조 단추 "다시 확인"을 보인다("문구"). 이 상태는 그림에 없어, 문의 상태 (다)(Agent OS 서버가 답하지 않음)와 같은 짜임으로 지었다("화면과 다르게 짓는 것").
  - 사이트의 토큰과 고지 확인의 기록은 설정을 받아 오지 못했다는 답을 내고 토큰을 내지 않는다. 들어오지 않았다는 답과도, 없는 사이트의 답과도 다른 답이다. 페이지는 이 답에 "갱신"을 부르지 않는다. 페이지의 `tokenProvider`는 이 답을 끝점이 답하지 못한 것으로 다루고, 위젯은 토큰을 받지 못했을 때의 알림을 보인다(widget-login-state의 명세 "위젯 테스트 페이지").
  - 내려가 있는 대역을 부른 호출은 연결 거절을 받아 차례로 보낼 때 중앙값 0.6~2.2ms에 실패했다(쟀다. 루프백의 닫힌 포트에서 본 것이다). 컨테이너가 내려가 이름이 풀리지 않거나 패킷이 버려지는 경우는 재지 못했고, 그때는 제한 시간이 호출을 끊는다고 본다(어림).
  - 받아 오지 못한 요청마다 까닭의 종류(연결 거절, 제한 시간, 오류 답, 꼴이 아님)를 로그에 한 줄 남긴다. 들어온 운영자의 요청에서만 나는 줄이라 로그를 채우지 않는다. 쿠키와 계정 이름은 싣지 않는다.
- **처리기.** 지금의 처리기는 요청을 받아 답을 바로 돌려주는 함수이고, 사이트의 목록은 뜰 때 한 번 만든 값에 들어 있다(기준 커밋의 `web/apps/portal/server/handler.ts`와 `web/apps/portal/tools/start.ts`, 코드를 읽었다). 요청마다 다른 서버를 부르려면 처리기와 그것을 거는 겉이 답을 기다렸다가 돌려주는 꼴로 바뀐다. 사이트마다의 판정과 답을 짓는 부분은 지금처럼 값을 받아 값을 내는 함수로 남긴다.
- **부르는 법.** 다른 서버를 부르는 클라이언트는 "로그인 확인"의 것과 같은 규칙을 따른다.

### 사이트마다의 검사와 닫힌 사이트 (넘겨받았다. 닫힌 사이트에 내는 답과 로그를 남기는 때는 명세가 정했다)

- 위젯 테스트 페이지의 서버는 사이트 파일과 개인 키를 지금처럼 뜰 때 한 번 읽는다. 읽지 못하거나 사이트 파일이 판정을 지나지 못하면 뜨지 않는다. 사이트 파일을 고치면 지금처럼 다시 띄운다(ADR 0056 결정 "사이트 파일을 고치면").
- 위젯 테스트 페이지 설정을 받아 오면 사이트마다 아래를 본다(ADR 0064 결정 "시작 검사가 가는 자리"의 둘째). 지금 뜰 때 하는 대조(`.scratch/pilot-portal/spec.md`의 "시작 검사와 진단")에서 에이전트의 갈래를 뺀 것이다. 에이전트는 위젯 설정의 값이 되어 `serve`가 질문을 받을 때 본다.

| 까닭 | 걸리는 때 |
|---|---|
| 발급자가 사이트 파일에 없다 | 그 발급자를 가진 사이트가 사이트 파일에 없다 |
| 공개 출처가 허용 출처에 없다 | 위젯 테스트 페이지의 공개 출처가 사이트 파일의 그 사이트 허용 출처에 없다 |
| 키가 맞지 않는다 | 설정의 키 식별자가 그 사이트의 공개 키에 없거나, 그 공개 키가 위젯 테스트 페이지의 개인 키와 짝이 아니다 |

- ADR이 든 넷째 갈래(로그인이 필요한 사이트가 쓰는 로그인 서버 항목이 없다)는 로그인 서버 항목이 서는 portal-login과 함께 든다("순서에 달린 것").
- 까닭이 하나라도 있는 사이트는 닫는다. 들어온 사람에게 내는 사이트 목록에서 빠지고, 그 사이트의 끝점은 없는 사이트를 물었을 때와 같은 답을 낸다. 다른 사이트는 그대로 선다.
- 까닭은 로그에 한 줄로 남긴다. 그 사이트가 열리거나 닫히거나 까닭이 달라질 때만 남긴다. 요청마다 남기면 닫힌 사이트 하나가 로그를 채운다. 줄은 지금의 진단처럼 자리와 까닭이고 값(키의 글, 출처)을 싣지 않는다. 사이트 이름은 싣는다.
- 판정은 순수한 함수 하나다. 사이트의 값(사이트 이름, 발급자, 보증 모드), 뜰 때 읽은 사이트 파일, 개인 키를 받아 사이트마다 열림이나 까닭들을 낸다. 받아 올 때의 판정과 아래 "닫힌 사이트를 알리는 길"의 답이 이 함수 하나를 쓴다. 두 자리가 같은 사이트를 다르게 판정하지 않게 하기 위해서다.

### 닫힌 사이트를 알리는 길 (명세가 정했다)

ADR 0064가 이 명세에 넘긴 것이다(결정 "시작 검사가 가는 자리"의 끝). 운영자는 사이트 파일에 없는 발급자를 등록할 수 있고, 그 사이트는 저장되지만 위젯 테스트 페이지가 열지 않는다. 그것을 아는 프로그램은 사이트 파일과 키를 든 위젯 테스트 페이지의 서버뿐이다.

- 위젯 테스트 페이지의 서버에 안쪽 길 하나를 둔다. 사이트의 목록(사이트마다 사이트 이름, 발급자, 보증 모드)을 받아 사이트마다 열리는지와 까닭들을 답한다. 위의 판정 함수를 그대로 쓰고, 받은 목록을 기억하지 않는다.
- 위젯 관리 서버는 운영자용 답에 사이트의 열림을 실을 때마다 이 길을 묻는다. "사이트 목록"은 위젯 테스트 페이지에 담은 사이트 전부를, "사이트 하나"는 그 사이트를 데이터베이스의 지금 값으로 묻는다. 사이트 등록과 사이트 고치기의 답은 "사이트 하나"와 같은 것을 싣는다. 그래서 저장한 직후의 화면이 방금 저장한 값의 판정을 보인다.
- 위젯 관리 서버는 위젯 테스트 페이지의 서버의 주소를 시작 값으로 받는다. 없어도 뜨는 값이다. 그 값이 없거나, 답이 2초(어림) 안에 오지 않거나, 답이 꼴에 맞지 않으면 열림을 "확인하지 못했다"로 싣고 나머지 답은 그대로 낸다. 저장은 이 물음이 실패해도 된다.
- 이 길은 `/portal/` 밖의 경로에 둔다. 프록시가 위젯 테스트 페이지의 서버로 넘기는 것은 `/`와 `/portal/` 아래뿐이고 나머지는 프록시가 404로 답하므로(`.scratch/release-image/spec.md`의 "프록시 설정") 밖에서 닿지 않는다. 그 위에 브라우저가 보낸 요청(`Sec-Fetch-Site`나 `Origin`이 있는 요청)을 거절한다. 답에는 받은 사이트의 이름과 열림과 까닭의 이름만 싣는다.
- 화면은 닫힌 사이트를 두 자리에서 알린다. 사이트 목록의 경고 알림 "위젯 테스트 페이지가 열지 않는 사이트가 있다"와, 사이트 화면의 머리 아래에 서는 경고 알림 "위젯 테스트 페이지가 이 사이트를 열지 않는다"다(완성 화면 `Main.dc.html`, `mk-site-broken.dc.html`). 까닭마다의 문장은 아래와 같고, 까닭이 여럿이면 문장을 이어 보인다. 사이트 화면의 알림은 끝에 "위젯 설정은 그대로 쓰인다."를 붙인다. 닫힌 것은 위젯 테스트 페이지의 그 사이트뿐이고, 사이트의 페이지에 붙인 위젯은 위젯 설정을 그대로 받아 가기 때문이다.

| 까닭 | 화면의 문장 |
|---|---|
| 발급자가 사이트 파일에 없다 | 발급자 `<발급자>`이 사이트 파일에 없다. 사이트 파일에 그 발급자를 더하고 위젯 테스트 페이지를 다시 띄우거나, 아래 발급자를 고친다. |
| 공개 출처가 허용 출처에 없다 | 사이트 파일이 이 사이트에 허용한 출처에 위젯 테스트 페이지의 주소가 없다. 사이트 파일에 그 주소를 더하고 위젯 테스트 페이지를 다시 띄운다. |
| 키가 맞지 않는다 | 사이트 파일의 이 사이트 공개 키에 위젯 테스트 페이지의 키가 없다. 사이트 파일에 그 공개 키를 더하고 위젯 테스트 페이지를 다시 띄운다. |

- 사이트 파일을 고친 뒤 무엇을 다시 띄우는지의 전체 절차는 배포 안내가 든다. 화면의 문장은 운영자가 이 화면에서 바로 볼 변화(위젯 테스트 페이지가 그 사이트를 여는 것)에 필요한 것만 말한다.
- 고르지 않은 안은 셋이다.
  - 위젯 테스트 페이지의 서버가 판정을 위젯 관리 서버에 올려 두는 안. 운영자가 저장한 직후에 보이는 판정이 저장하기 전의 값의 것이 된다.
  - 위젯 관리 화면이 브라우저에서 위젯 테스트 페이지의 끝점을 직접 부르는 안. 두 화면은 포트가 달라 다른 출처이고, 로그인 쿠키를 실은 다른 출처의 요청을 위젯 테스트 페이지에 열어야 한다.
  - 위젯 테스트 페이지의 서버가 물음을 받으면 위젯 테스트 페이지 설정을 스스로 다시 받아 와 판정하는 안. 위젯 관리 서버가 요청 하나를 처리하는 도중에 자기에게 되돌아오는 요청을 받게 된다.

### 위젯 테스트 페이지의 운영자 문 (넘겨받았다. 끝점의 가름, 사이트 고르기의 글, 띠의 스위치는 명세가 정했다)

위젯 테스트 페이지는 로그인해야 연다(ADR 0065 결정 "위젯 테스트 페이지"). 이 기능이 짓는 것은 운영자 문이다. 회사 계정 문은 portal-login이 짓고, 그때까지 들어오는 문은 완성 화면 `mk-door-states.dc.html`의 (가)처럼 운영자 문 하나다.

- 서버가 내는 페이지에는 사이트의 목록도 사이트의 값도 싣지 않는다. 지금은 페이지가 사이트들의 공개 설정을 데이터로 실어 낸다(기준 커밋의 `web/apps/portal/server/page.ts`, 코드를 읽었다). 페이지의 스크립트가 아래의 "들어온 사람"을 물어 그 답으로 문이나 사이트 화면을 그린다.
- 위젯 테스트 페이지의 서버가 답하는 끝점은 아래와 같다. 브라우저가 부르는 것은 모두 `/portal/` 아래에 있다.

| 끝점 | 누구에게 답하나 | 답 |
|---|---|---|
| 페이지, 정적 파일, 상태 확인 | 누구나 | 지금 그대로다. 페이지는 사이트의 값을 싣지 않는다 |
| 들어온 사람 | 누구나 | 들어왔으면 계정 이름과 열린 사이트의 목록(사이트마다 사이트 이름, 위젯의 이름, 보증 모드, 보고서 링크). 들어왔는데 목록을 받아 오지 못했으면 계정 이름과 그 사실("위젯 테스트 페이지 설정을 데이터베이스로"). 아니면 들어오지 않았다는 답 |
| 갱신 | 누구나 | 받은 쿠키를 Agent OS의 "갱신"에 전하고 Agent OS가 낸 `Set-Cookie`를 그대로 되돌린다 |
| 사이트의 토큰, 고지 확인의 기록 | 들어온 브라우저 | 지금의 답. 들어오지 않았으면 들어오지 않았다는 답 |

- 들어왔는지는 요청마다 운영자의 로그인 쿠키를 Agent OS의 "지금 누구인지"에 전해 확인한다. 흐름은 "로그인 확인"의 것과 같다. 위젯 테스트 페이지의 서버는 들어온 브라우저를 기억하지 않는다. 그래서 관리 화면에서 로그아웃하면 다음 요청부터 문이 닫힌다.
- 들어온 브라우저에만 답하는 끝점과 "갱신"은 요청 출처를 Agent OS와 같은 규칙으로 본다("저장 경로"). 고지 확인의 기록이 지금 하는 `Origin` 대조는 그대로 둔다.
- 운영자는 열린 사이트를 모두 시험한다. 익명 모드 사이트와 둘 다 사이트에서는 고지를 확인한 뒤 익명 식별자로 토큰을 받는다(ADR 0065). 운영자 계정의 이름은 사이트 토큰에 싣지 않는다. 사이트 토큰의 주체는 그 사이트의 최종 사용자를 가리키는 값이고 운영자 계정은 Agent OS의 계정이기 때문이다. 로그인 모드 사이트는 회사 로그인이 서기 전이라 지금처럼 위젯 자리에 "이 사이트는 로그인이 필요합니다." 알림이 서고 끝점은 거절한다. 그 자리를 로그인으로 바꾸는 일은 portal-login이 한다.
- 위젯은 토큰을 페이지가 준 함수(`tokenProvider`)로 받고, 그 함수가 토큰 끝점을 부른다(widget-login-state의 명세 "위젯 테스트 페이지"). 그 함수와 페이지의 다른 요청이 들어오지 않았다는 답을 받으면, 페이지는 "갱신"을 한 번 부르고 같은 요청을 다시 보낸다. 그래도 같은 답이면 화면을 문으로 바꾸고 "로그인 시간이 끝남" 상태를 보인다(완성 화면 `mk-door-states.dc.html`의 (나)).
- 문은 그 탭이 다시 보이게 될 때와 "다시 확인"을 누를 때 "들어온 사람"을 다시 묻는다. Agent OS 서버가 답하지 않으면 같은 화면의 (다)를 보인다.
- "관리 화면에서 로그인"은 관리 화면의 주소를 새 탭으로 연다. 위젯 테스트 페이지의 서버는 그 주소를 설정 파일의 시작 값으로 받고, 없으면 공개 주소의 이름에 관리 화면용 기본 포트를 붙여 짓는다.
- 운영자로 들어온 뒤의 화면은 완성 화면 `mk-tester.dc.html`이다. 위쪽 띠에 사이트 고르기가 서고 오른쪽 끝에 흐린 "운영자 `<계정 이름>`"이 선다. 위젯 아래에는 보고서 링크만 선다. 고지 줄과 밝기 스위치는 위젯이 그린다(ADR 0061 결정 "위젯 미리보기 페이지").
- 사이트 고르기의 항목은 "`<위젯의 이름>` (`<사이트 이름>`)"이고, 위젯의 이름이 비어 있으면 사이트 이름만 쓴다. 지금은 설정 파일의 위젯 이름을 썼는데 그 칸이 위젯 설정으로 옮겨 가므로, 위젯 테스트 페이지 설정을 받아 가는 답이 위젯의 이름을 함께 싣는다("저장 경로"의 안쪽 길).
- 어느 사이트를 고를지는 지금처럼 주소의 `?site=`가 정한다. 그 이름의 사이트가 없거나 닫혀 있으면 첫 사이트를 고른다. 위젯 관리 화면의 "위젯 테스트 페이지에서 열기"는 이 주소를 연다.
- 들어온 운영자에게 열 수 있는 사이트가 하나도 없으면 위젯 자리에 "열 수 있는 사이트가 없다. 위젯 관리 화면에서 사이트를 위젯 테스트 페이지에 담는다."를 보인다. 처음 배포한 직후가 이 경우다(ADR 0064 결정 "값을 옮기는 길은 짓지 않는다").
- 들어오는 문의 띠에는 밝기 스위치를 두지 않는다. 문의 화면은 보는 사람 기기의 설정을 따른다. 운영자로 들어온 뒤의 띠에 스위치가 없으므로(위 ADR 0061) 같은 띠가 들어오기 전과 뒤에 달라지지 않게 했다. 화면이 명세에 넘긴 물음이다(`.scratch/portal-admin/design/README.md`).
- 위젯 테스트 페이지의 서버는 쿠키의 값과 계정 이름을 로그에 남기지 않는다.
- 위젯 테스트 페이지의 설정 파일에서 사이트의 목록을 통째로 뺀다. 남는 것은 시작 값이다. 공개 주소, 서명 키의 경로와 키 식별자, 듣는 주소와 포트, 위젯 관리 서버의 주소(ADR 0064 결정 "위젯 미리보기 페이지 설정")에 이 명세가 둘을 더한다. Agent OS 서버의 주소(운영자 문이 로그인을 확인하는 데 쓴다)와 관리 화면의 주소(문의 링크에 쓰고 없어도 된다)다. 파일의 `schema_version`은 widget-login-state가 올린 값에서 하나 더 올린다. 옛 판의 파일은 지금처럼 뜰 때 거절한다.

### 고지를 고쳐도 다시 확인받지 않는다 (사용자가 골랐다)

ADR 0064 Consequences "명세가 짓는 것"의 넷째다. 사용자가 "다시 띄우지 않기"를 골랐다(일지 2026-11-16-1705).

- 운영자가 고지의 짧은 줄이나 고지 전문을 고쳐도, 이미 고지를 확인한 브라우저에 고지 확인을 다시 받지 않는다. 확인은 지금처럼 사이트 단위로 남는다(ADR 0059 결정 "고지 확인").
- 고친 글은 다음에 위젯을 열 때부터 고지 줄과 "고지 전문" 단추에 보인다.
- 대가는 이미 확인한 사람이 고친 고지를 스스로 열어 보지 않으면 모른다는 것이다. 기록하는 것이나 보내는 곳이 달라지는 고침이면 운영자가 다른 길로 알려야 하고, 배포 안내에 그렇게 적는다.
- 고르지 않은 안은 고지 전문에 판을 두고 판이 바뀌면 확인 쿠키를 무효로 하는 것이다. 오탈자를 고쳐도 모든 사람에게 덮개가 다시 뜨고, 그것을 가리려면 운영자에게 "다시 확인받기"를 고르는 칸을 하나 더 주어야 한다.

### 예시 질문의 모양을 답에 싣는다 (넘겨받았다)

- 위젯은 예시 질문의 세 모양을 모두 그릴 줄 알지만, widget-login-state에서는 그 값이 위젯 설정의 답에 실리지 않아 기본 모양으로만 선다. 답에 싣고 읽는 일을 그 명세가 이 값을 더하는 기능에 넘겼다(widget-login-state의 명세 "위젯 설정의 항목과 앞서는 차례").
- 이 기능이 넷을 더한다. 위젯 설정의 표에 칸 하나, 위젯 설정을 받아 가는 답에 칸 하나, 위젯이 답에서 그 값을 읽어 화면 부품에 주는 것, 그리고 그 값이 답으로 닿았을 때의 시험이다(Testing Decisions).
- 값의 이름과 목록 밖의 값을 다루는 법은 다른 모양 값 셋과 같게 한다. 위젯은 모르는 값이면 기본 모양으로 그리고 `console.error`를 남긴다(같은 명세).
- 답에 칸을 더하는 것이 답의 판 표시를 올리는지는 widget-admin-server의 명세가 세운 규칙을 따른다. 칸이 없는 답을 받은 위젯은 기본 모양으로 그린다.

### 새 아이콘 셋 (사용자가 골랐다)

사용자가 "셋 다 더하기"를 골랐다(일지 2026-11-16-1705). 화면이 디자인 시스템의 아이콘 이름 밖에서 직접 그린 셋을 디자인 시스템 패키지의 아이콘에 더한다.

| 아이콘 | 쓰이는 자리 |
|---|---|
| external-link | 새 탭으로 여는 링크. 탐색의 "테스트", "관리 화면에서 로그인", "관리 화면 열기", "위젯 테스트 페이지에서 열기", 위젯 테스트 페이지의 보고서 링크 |
| chevrons-up-down | 옆 탐색 맨 아래의 계정 자리와 좁은 폭 위 막대의 계정 버튼 |
| chevron-down | 위젯 테스트 페이지의 사이트 고르기 |

- 모양은 다른 아이콘과 같은 Lucide의 것이고 크기와 선의 굵기도 같다(`.claude/rules/web-design.md`).
- 더하는 티켓 하나가 함께 고치는 것은 넷이다. 디자인 시스템 패키지의 아이콘 목록, 그 수를 세는 스토리 시험(지금 열일곱을 세고 스물이 된다. 기준 커밋의 `web/packages/ui/src/components/atoms/Icon.stories.tsx`, 코드를 읽었다), 아이콘 전체를 찍은 사진 비교의 기준 그림, 디자인 시스템 아티팩트다. 아티팩트에는 더한 뒤 `/sync-design-system 올리기`로 올린다. 사용자가 셋을 더하기로 고를 때 들은 값이다(일지 2026-11-16-1705).
- 새 탭으로 여는 링크는 글자 뒤에 external-link가 붙고, 화면 읽기 프로그램에는 "(새 탭에서 열림)"이 함께 읽힌다.

### 포트와 compose (넘겨받았다. 포트의 번호와 프로그램마다 받는 값은 명세가 정했다)

- 프록시가 듣는 포트에 위젯 관리 화면용 하나가 는다(ADR 0064 결정 "배포에 느는 것"). 호스트에 발행하는 번호의 기본은 8444다. 관리 화면용 포트(기본 8443, ADR 0062 결정 "포트와 TLS")와 같은 방식으로 운영자가 번호를 바꾸거나 닫을 수 있고, 닫으면 서버 자신의 `127.0.0.1`에서만 열린다. 여닫는 설정의 이름은 admin-login의 명세가 관리 화면용 포트에 세운 꼴을 따른다. 여기의 번호는 호스트에 여는 번호다. 지금의 프록시는 컨테이너 안에서 8443(방문자용 TLS)과 8080을 듣고 compose가 그 둘을 호스트의 443과 80으로 발행하므로(`deploy/standalone/proxy/site.conf`와 `deploy/standalone/compose.yaml`을 읽었다), 프록시가 컨테이너 안에서 듣는 번호는 포트를 더하는 티켓이 그 둘과 겹치지 않게 고른다.
- 이 포트는 TLS만 듣고 방문자용, 관리 화면용과 같은 인증서를 쓴다. 이 포트로 온 요청은 경로를 가리지 않고 위젯 관리 화면의 컨테이너로 넘긴다. 위젯 관리 서버의 운영자용 경로는 위젯 관리 화면의 중계를 거쳐서만 닿는다. 프록시는 경로를 가리지 않지만 그 중계가 운영자용 경로 일곱만 위젯 관리 서버로 넘기므로("저장 경로"), 이 포트에서도 안쪽 길은 닿지 않는다.
- 위젯 관리 화면은 관리 화면과 같은 이름(호스트)으로 열어야 한다. 로그인 쿠키는 그 이름에만 실리고 포트는 가리지 않는다(ADR 0062 결정 "로그인 상태"). `https://admin.example.com:8443`에서 로그인하고 `https://widget.example.com:8444`를 열면 쿠키가 실리지 않아 "로그인이 필요하다"만 보인다. 배포 안내에 이 조건을 적는다.
- 단독 compose에 위젯 관리 화면의 컨테이너 하나를 더한다. 판마다 짓는 이미지이고 판 번호는 Agent OS와 같다. 다른 프로세스와 같이 루프백에만 묶이고, 이미지 안에서만 켜지는 명시적인 설정이 있을 때에만 컨테이너 네트워크의 주소에 묶인다(ADR 0056 결정 "루프백 규칙의 예외"). 그 판정이 다른 자리들과 같은지는 같은 사례 표로 잠근다(`tests/fixtures/container_network/cases.json`). 컨테이너는 호스트에 포트를 발행하지 않는다.
- 프로그램마다 이 기능이 더하는 시작 값은 아래와 같다. 주소는 모두 같은 서버나 컨테이너 네트워크 안의 것이다.

| 프로그램 | 값 | 없으면 |
|---|---|---|
| 위젯 관리 화면 | 위젯 관리 서버의 주소 | 뜨지 않는다 |
| 위젯 관리 화면 | 관리 화면의 주소, 위젯 테스트 페이지의 주소 | 지금 화면과 같은 이름으로 짓는다("위젯 관리 화면의 틀과 주소") |
| 위젯 관리 서버 | Agent OS 서버의 주소 | 뜨지 않는다 |
| 위젯 관리 서버 | 위젯 테스트 페이지의 서버의 주소 | 사이트가 열리는지를 "확인하지 못했다"로 답한다 |
| 위젯 테스트 페이지의 서버 | 위젯 관리 서버의 주소, Agent OS 서버의 주소 | 뜨지 않는다 |
| 위젯 테스트 페이지의 서버 | 관리 화면의 주소 | 공개 주소의 이름에 관리 화면용 기본 포트를 붙인다 |

- 위젯 관리 서버와 위젯 쪽 PostgreSQL의 컨테이너, 프록시가 위젯 설정을 받아 가는 경로를 넘기는 줄은 widget-admin-server가 더한다. 이 기능은 그 위에 위젯 관리 화면의 컨테이너와 프록시의 포트 하나, 위 시작 값을 더한다.
- compose와 프록시 설정은 release-image가 지은 것 위에 더한다(ADR 0064 Consequences "운영"). 그 파일들은 이 명세를 쓰는 동안 dev에 들어왔다(PR 592, `deploy/standalone/`). 서비스는 프록시, `serve`, 관리 화면, 위젯, 위젯 테스트 페이지 다섯이고, 호스트에 여는 포트는 프록시의 443과 80, 관리 화면의 `127.0.0.1:3000` 셋이며, 프록시는 허용 목록의 경로만 넘기고 나머지에는 404로 답한다(`compose.yaml`과 `proxy/site.conf`를 읽었다). 프록시가 관리 화면용 포트를 듣게 하는 일은 admin-login이(ADR 0062 결정 "포트와 TLS"), 위젯 관리 서버와 그 데이터베이스의 컨테이너는 widget-admin-server가 그 위에 더한다. 그래서 배포에 닿는 티켓은 그 두 기능의 것이 든 뒤에 돈다.
- 위젯 관리 화면의 컨테이너에는 상태 확인을 둔다. 방식은 release-image가 관리 화면의 컨테이너에 둔 것과 같다.

### 선행 기능에 기대는 것 (명세가 정했다)

이 기능을 막는 세 기능 가운데 둘(widget-admin-server, admin-login)은 이 명세를 쓸 때 명세가 없고, 하나(widget-login-state)는 이 명세를 쓰는 동안 명세가 병합됐다(PR 593). 그래서 이 명세가 그 기능들에 기대는 것을 여기 모으고, 같은 것을 그 기능들의 기능 계획에도 적었다. 그 명세가 아래와 다르게 서면 이 기능의 티켓을 쪼개기 전에 이 명세를 다시 연다(Further Notes).

- **widget-admin-server.** 사이트 이름의 꼴은 주소의 경로 한 토막에 그대로 쓸 수 있어야 한다. 위젯 관리 화면의 `/sites/<사이트 이름>`과 위젯 테스트 페이지의 사이트 끝점, 익명 식별자 쿠키의 경로가 그 이름을 쓴다. 지금 위젯 테스트 페이지 설정이 받는 꼴(영문 소문자로 시작하고 영문 소문자, 숫자, 하이픈으로 이어지는 2~63자. 기준 커밋의 `web/apps/portal/server/config.ts`, 코드를 읽었다)이 그렇다. 표 관리 도구로 표와 칸을 더할 수 있어야 한다. 오류 답의 봉투와 경로의 접두사 관례가 있어야 하고, 운영자용 경로와 누구나 읽는 경로를 프록시가 접두사로 가를 수 있어야 한다. 그 서버의 계약에서 만드는 생성 클라이언트 패키지가 있어야 하고, 이 기능이 거기에 위젯 관리 화면이 운영자용 경로를 부르는 클라이언트와 위젯 테스트 페이지의 서버가 안쪽 길을 부르는 클라이언트를 더한다("로그인 확인"의 "부르는 클라이언트").
- **admin-login.** "지금 누구인지"는 계정 이름을 답한다. "갱신"은 새 쿠키를 `Set-Cookie`로 낸다. 두 경로가 루트 `openapi.json`에 서서 생성 클라이언트 패키지의 타입에 든다. 두 경로는 서버가 보낸 요청(`Sec-Fetch-Site`도 `Origin`도 없는 요청)을 받는다(ADR 0062 결정 "요청 출처 검사"). 관리 화면은 로그인하지 않은 채 어느 화면을 열어도 로그인 화면으로 보낸다. 관리 화면용 포트를 여닫는 설정의 이름이 선다. 탭 둘이 동시에 갱신할 때의 짧은 유예(ADR 0062가 그 명세에 넘겼다)에 이 기능이 기대는 정도는 "로그인 확인"에 있다.
- **widget-login-state.** 위젯의 화면 부품이 위젯 설정의 항목과 상태를 입력으로 받는다. 위젯 테스트 페이지 설정 파일에서 에이전트와 모양과 고지의 칸이 빠졌다. 페이지의 `tokenProvider`가 토큰 끝점을 부르고 토큰 답을 JSON으로 받는다. 위젯에 주소의 검사가 있다.

### 순서에 달린 것 (뒤에 끝나는 기능의 명세에 넘긴다)

portal-login과 이 기능 가운데 뒤에 끝나는 쪽의 명세가 정하기로 한 것이 셋이다. 둘은 ADR 0064 Consequences "명세가 짓는 것"이, 하나는 화면 그리기가 portal-login의 기능 계획에 적었다(ADR 0065 결정 "위젯 테스트 페이지"). portal-login은 이 명세를 쓸 때 설계만 있고 명세가 없다. 어느 쪽이 뒤에 끝날지 알 수 없어 이 명세는 셋을 정하지 않고, 이 기능이 그것 없이 서는 모양만 적는다.

- **사이트가 쓰는 로그인 서버 항목의 이름.** 이 기능의 위젯 테스트 페이지 설정에는 그 칸이 없다. portal-login이 먼저 끝나 있으면 그 이름을 두는 자리를 이 기능의 티켓을 쪼개기 전에 정한다. 제안은 위젯 테스트 페이지 설정의 사이트마다의 칸 하나로 두고 "위젯 테스트 페이지" 탭에 고르는 칸을 더하는 것이다. 닫힌 사이트의 넷째 까닭(로그인 서버 항목이 없다)도 그때 든다.
- **위젯 테스트 페이지가 담는 사이트의 로그인 주소와 로그아웃 주소.** 이 기능에서는 운영자가 위젯 설정에 손으로 적고, 화면은 처음 값을 채우지 않는다. 그 주소가 될 위젯 테스트 페이지의 끝점이 portal-login 전에는 없기 때문이다. 화면이 처음 값으로 채워 줄지는 portal-login이 그 끝점을 지은 뒤에 정한다.
- **회사 계정 문.** 회사 계정 문으로 들어온 사람에게 어느 사이트를 보일지, 문의 화면, 로그인 서버 항목이 여럿일 때 문에 무엇을 둘지다. 이 기능은 운영자 문만 짓고, 운영자에게는 열린 사이트를 모두 보인다.

### 문구 (명세가 정했다)

화면의 글은 완성 화면과 시작 프롬프트(`.scratch/portal-admin/design/screens-prompt.md`)의 것을 쓴다. 아래는 이 명세가 고치거나 더하는 글이다. 문체는 그 화면들의 평서문("…한다", "…못한다")을 따른다.

| 자리 | 글 |
|---|---|
| 주소인 칸 넷의 도움말 | https://로 시작하는 완전한 주소를 넣는다. 자기 PC에서 시험할 때는 http://localhost 주소도 된다. 주소에 비밀 값을 넣지 않는다. 위젯 설정은 누구나 읽을 수 있다. |
| 문의 링크의 도움말 | 위젯의 입력창 아래에 "문의하기"로 보인다. |

| 고지 전문의 도움말(사이트 등록) | 위젯 테스트 페이지에 담는 사이트라 익명 식별자와 계정 기록의 문장을 처음 값으로 넣어 두었다. 자기 말로 다듬어도 된다. |

| 미리보기 아래의 도움말 | 미리보기 안은 스크롤할 수 없다. 긴 글의 나머지는 저장한 뒤 "테스트"에서 본다. |
| 칸 아래: 비었다 | 비워 둘 수 없다. |
| 칸 아래: 한 줄인 칸의 줄바꿈 | 한 줄로 적는다. |
| 칸 아래: 너무 길다 | `<N>`자까지 적을 수 있다. |
| 칸 아래: 주소가 아니다 | https://로 시작하는 완전한 주소를 넣는다. |
| 칸 아래: 주소에 사용자 정보 자리가 있다 | 주소에 이름이나 비밀번호를 넣을 수 없다. |
| 칸 아래: 이름이 이미 있다 | 이 이름의 사이트가 이미 있다. |
| 칸 아래: 발급자가 겹친다 | 이 발급자는 사이트 `<이름>`이 이미 쓴다. 발급자는 사이트마다 달라야 한다. |
| 칸 아래: 고지 전문이 비었다 | 위젯 테스트 페이지에 담는 사이트는 고지 전문을 비울 수 없다. |
| 저장 띠: 요청 실패 | 저장하지 못했다. 잠시 뒤 다시 저장한다. |

| 지우기 확인 창: 로그인이 끝났다 | 로그인이 끝났다. 관리 화면에서 다시 로그인한 뒤 지운다. |

- 사이트 이름의 도움말과 꼴이 아닐 때의 글은 widget-admin-server의 명세가 정한 꼴을 말로 옮긴다.
- 서버는 까닭의 이름만 답하고 위 글은 화면이 든다("저장 경로"). "고르는 값이 아니다"와 "예시 질문이 넷을 넘는다"는 화면이 그런 값을 보내지 못하게 막으므로 글을 두지 않고, 그 답이 오면 저장 띠의 요청 실패 글을 보인다.

### 화면과 다르게 짓는 것

완성 화면과 그 탐색용 가정 가운데 이 명세가 다르게 정한 자리다. 화면 파일은 고치지 않는다. 화면은 확정한 때의 기록이고 구현은 이 절을 따른다.

- 사이트 등록의 주소는 `/new`다. 가정은 `/sites/new`였다("위젯 관리 화면의 틀과 주소").
- 문의 링크는 주소 한 칸이다. 가정은 글과 주소 두 칸이었다.
- "글" 탭에 예시 질문의 모양을 고르는 칸이 는다. 그림에는 없다.
- 미리보기의 예시 질문과 문의 링크는 위젯이 그리는 그대로 보인다. 그림은 예시 질문을 가운데 정렬한 보조 버튼 줄로 그렸고 문의 링크를 그리지 않았다. 위젯의 그 모양은 그림 뒤에 확정됐다(`.scratch/widget-login-state/design/README.md`의 "위젯 설정이 더한 화면").
- 미리보기의 "로그인 전"에는 예시 질문이 없다. 그림은 셋을 보였다.
- 미리보기 아래에 흐린 도움말 한 줄이 는다. 그림에는 없다("미리보기").
- 들어오는 문의 띠에 밝기 스위치가 없다. 그림(`ch-door-1.dc.html`, `mk-door-m.dc.html`)에는 있다.
- 들어오는 문은 portal-login 전까지 운영자 문 하나다. 그림의 기본(`ch-door-1.dc.html`)은 문 둘이고, 문 하나의 그림은 상태 (가)다.
- 좁은 폭의 사이트 화면에서 "위젯 테스트 페이지에서 열기"는 더 보기 메뉴 안에 든다. 그리지 않은 제안이었다.
- 그림에 없는 상태에 글을 더했다. 저장 실패 셋, 지우기 확인 창 안의 지우기 실패 셋("사이트 지우기"), 사이트가 열리는지 확인하지 못했을 때의 알림, 위젯 테스트 페이지에 열 사이트가 없을 때의 안내, 위젯 테스트 페이지가 사이트 목록을 받아 오지 못했을 때의 알림, 등록한 뒤의 고지 전문 도움말이다("문구").
- 사이트 이름의 도움말과 오류 글은 widget-admin-server의 명세가 정한 꼴을 따른다. 그림의 글은 가정이다.

### 티켓이 코드와 같은 티켓에서 고치는 문서

- `.claude/rules/web-design.md`의 "패턴과 화면(organisms 이상)은 앱이 짓는다(ADR 0026)"에 미리보기의 공유 패키지를 넣어 고치고, 그 문서의 `paths`에 새 패키지의 자리를 더한다. 지금의 `paths`는 디자인 시스템 패키지와 앱의 `components`만 덮어, 옮긴 부품을 열어도 그 규칙이 실리지 않는다(코드를 읽었다). ADR 0026 본문의 그 문장에는 포인터 "(바뀜: ADR 0065)"가 이미 있다. 고친 뒤 `/sync-design-system 올리기`를 돈다(`.scratch/portal-admin/plan.md`).
- `docs/constitution/tech.md`: 위젯 관리 화면이 저장소에 없다는 문장을 그 앱을 들이는 티켓이 고친다(ADR 0064 Consequences "스택"). 새 공유 패키지도 적는다. 런타임 의존성 행에는 위젯 관리 서버가 Agent OS의 두 경로를 `httpx2`로 부른다는 것을 로그인 확인을 짓는 티켓이 적는다.
- `README.md`의 구조와 `CLAUDE.md`의 레이어 줄: 새 앱과 새 공유 패키지.
- `CLAUDE.md`의 검증 명령과 게이트의 수, `docs/constitution/operations.md`의 CI 잡과 LLM 테스트 절: 새 e2e와 사진 비교가 는다(Testing Decisions). CI 잡의 수를 적은 자리가 둘 더 있어 잡을 더하는 티켓이 함께 고친다. `docs/constitution/tech.md`의 원격·CI 행과 next-session `merge.md`의 "함께 오르는 진행 중 조각"이고, 둘 다 지금 여덟으로 센다(읽었다). 뒤의 구절은 카나리아 명세 `.scratch/harness/probes/canary/next_session_ci_job_count.toml`이 기대 값으로 든다.
- `tests/fixtures/container_network/cases.json`을 읽는 자리에 위젯 관리 화면이 는다. 그 표를 든 문서는 루트 `README.md`의 두 자리이고(구조의 `fixtures/container_network/` 줄과, "네 프로세스의 판정은 … 사례 표 하나가 잠근다"는 문장) 둘 다 프로세스를 넷으로 세므로 함께 고친다. ADR 0056 결정 "루프백 규칙의 예외"가 "네 프로세스"로 센 자리에는 포인터 "(바뀜: ADR 0064)"가 이미 있고, `.claude/rules/` 아래에는 그 표를 든 규칙이 없다(기준 커밋에서 `container_network`를 grep으로 봤다).
- 위젯 테스트 페이지의 설정 파일 예시와 그 파일을 설명하는 문서: 사이트의 목록을 빼고 시작 값 둘을 더한다.
- 배포 안내: 위젯 관리 화면용 포트와 여닫는 법, 관리 화면과 같은 이름으로 열어야 한다는 것, 첫 사이트를 위젯 관리 화면에서 등록하는 단계, 사이트 파일을 고친 뒤 무엇을 다시 띄우는지의 절차("닫힌 사이트를 알리는 길"), 고지를 고쳐도 다시 확인받지 않는다는 것. 단독 배포의 안내는 release-image의 티켓 10이 `deploy/standalone/`에 짓기로 되어 있고(그 티켓 파일을 읽었다. 이 명세를 쓸 때 그 안내는 아직 없다), 그 안내가 선 뒤에 도는 티켓은 그 문서를 고친다. 고칠 안내가 아직 없으면 deploy-package의 기능 계획에 적는다(이 명세가 넘긴 것은 `.scratch/deploy-package/plan.md`에 적어 두었다).
- `CONTEXT.md`: 이 기능이 새로 쓰는 말이 용어집에 들 만한지는 그 말을 처음 코드에 들이는 티켓이 `domain-modeling`으로 가른다. 후보는 바꾼 기록이다.

## Testing Decisions

### 좋은 시험

- 밖에서 보이는 것만 본다. 요청에 돌아온 답, 데이터베이스에 남은 줄, 화면에 그려진 것, 대역이 받은 요청이다. 안쪽 함수의 이름이나 불린 횟수를 보지 않는다.
- 규칙은 가장 높은 이음매 하나에서 본다. 저장할 때의 규칙은 위젯 관리 서버의 HTTP 경로에서, 화면의 동작은 화면 부품에서, 길 전체는 브라우저에서 한 번 본다. 사용자가 "브라우저로 한 번 끝까지, 규칙은 서버 시험"을 골랐다(일지 2026-11-16-1705). 같은 규칙을 세 높이에서 되풀이해 시험하지 않는다.
- 시험은 처음 값을 저장 경로로 넣는다(ADR 0064 결정 "값을 옮기는 길은 짓지 않는다"). 데이터베이스에 직접 넣는 것은 저장 경로를 거치면 만들 수 없는 상태(옛 판의 줄 등)를 만들 때뿐이다.
- 시험 이름은 행동을 말하는 한국어 문장이다(`.claude/rules/web-workspace.md`).

### 이음매와 사례 (사용자가 골랐다. 사례는 명세가 정했다)

| 이음매 | 보는 것 | 선례 |
|---|---|---|
| 위젯 관리 서버의 HTTP 경로(pytest, 진짜 PostgreSQL, Agent OS 대역) | 저장 경로의 규칙 전부 | widget-admin-server가 세우는 서버 시험과 그 PostgreSQL 준비, `tests/test_server.py` |
| 주소의 사례 표 | 서버와 화면과 위젯이 같은 주소에 같은 판정을 낸다 | `tests/fixtures/container_network/cases.json`과 그것을 읽는 시험들 |
| 위젯 관리 화면의 화면 부품(Vitest) | 바뀜, 저장 띠, 거절, 떠날 때, 로그인이 필요한 화면의 상태 | 관리 화면 앱의 화면 부품 시험 |
| 미리보기(Vitest) | 양식의 값과 보는 상태가 화면 부품의 입력이 되는 것 | `web/apps/widget/testing/`의 하네스 |
| 스토리와 사진 비교 | 완성 화면과 같은 그림 | `pnpm -C web visual:admin`, `visual:widget` |
| 위젯 테스트 페이지의 서버(요청을 받아 응답을 내는 함수) | 운영자 문, 사이트마다의 검사, 안쪽 길 | `web/apps/portal/server/handler.test.ts` |
| 브라우저로 끝까지 한 번(Playwright) | 수락 문장의 길 | `web/apps/admin/e2e/`, `web/apps/portal/e2e/`, `web/packages/e2e-stack` |

위젯 관리 서버의 HTTP 경로에서 보는 사례는 아래다. Agent OS 대역은 "지금 누구인지"와 "갱신"을 흉내 내고 받은 요청을 모두 적어 둔다.

- 검사 표의 까닭마다 거절되고 데이터베이스가 그대로다. `javascript:`로 시작하는 로그인 주소가 그 하나다. 여러 칸이 어긋나면 까닭이 모두 온다.
- 등록, 고침, 지움마다 바꾼 기록에 한 줄이 남고 계정 이름과 이전 값과 새 값이 맞다. 바뀐 항목이 없는 저장은 줄을 남기지 않는다. 화면이 계정 이름을 지어 보내도 기록에는 Agent OS가 답한 이름이 남는다.
- 저장 번호가 다른 저장과 지움은 거절되고 앞 저장의 값이 남는다.
- 서로 다른 두 사이트를 같은 발급자로, 둘 다 위젯 테스트 페이지에 담아 같은 때에 저장하면 하나만 저장되고 다른 하나는 "발급자가 겹친다"로 거절된다. 같은 이름의 사이트 둘을 같은 때에 등록해도 하나만 선다. 한쪽의 쓰기가 끝나기 전에 다른 쪽이 읽어 보는 검사를 지나도록 맞물린 사례이고, 데이터베이스의 제약이 막는 것을 본다("저장할 때의 검사").
- 로그인 쿠키가 없거나 Agent OS가 거절한 요청은 읽기도 쓰기도 거절된다.
- 요청 출처: `Sec-Fetch-Site`가 `cross-site`, `same-site`, `none`인 요청과, `Sec-Fetch-Site` 없이 `Origin`만 있는 요청이 거절된다. `same-origin`인 요청과 둘 다 없는 요청은 받는다.
- 위젯 관리 서버가 Agent OS 대역에 보낸 요청이 두 경로뿐이다. 모든 운영자용 경로를 한 번씩 부른 뒤 대역이 적어 둔 목록으로 본다(ADR 0064 Consequences "신뢰와 노출").
- "갱신"의 답이 Agent OS 대역이 낸 `Set-Cookie` 줄들과 글자 그대로 같고 줄의 수도 같다(ADR 0064 Consequences "명세가 짓는 것"의 셋째). 대역이 갱신을 거절하며 쿠키를 지우는 줄을 냈을 때도 같다.
- Agent OS 대역이 로그인 시간이 끝났다고 답한 요청 뒤에, 대역이 받은 요청에 "갱신"이 없다. 서버는 스스로 갱신하지 않는다("로그인 확인").
- 브라우저의 머리(`Sec-Fetch-Site`, `Origin`, `Referer`)와 로그인 쿠키가 아닌 쿠키를 함께 실어 보낸 요청에서, Agent OS 대역이 받은 요청에는 그 머리들이 없고 `Cookie`에는 로그인 쿠키 둘뿐이다.
- "갱신"을 한 번 지난 뒤 쿠키 없이 보낸 요청에서, Agent OS 대역이 받은 요청에 쿠키가 없다. 서버의 클라이언트가 앞선 응답의 쿠키를 기억하지 않는다.
- 알아볼 수 있는 표식을 넣은 쿠키로 모든 경로를 부른 뒤, 서버의 로그 출력과 데이터베이스의 모든 표에 그 표식이 없다.
- Agent OS 대역이 답하지 않으면 로그인을 확인하지 못했다는 답이 온다. 로그인하지 않았다는 답과 다르다.
- 안쪽 길은 위젯 테스트 페이지에 담은 사이트만, 정해진 칸만 싣는다. 브라우저의 머리가 있는 요청은 거절한다.
- 위젯 테스트 페이지의 서버 대역이 닫혔다고 답한 사이트는 목록과 사이트 하나의 답에 까닭과 함께 실린다. 대역이 답하지 않으면 "확인하지 못했다"가 실리고 나머지 답은 온다.
- 위젯 설정을 받아 가는 답에 예시 질문의 모양이 실린다.

주소의 사례 표는 주소마다 받는지와, 받지 않으면 그 까닭을 적은 파일 하나다. 적어도 아래를 든다. 표를 읽는 시험이 세 자리(위젯 관리 서버, 위젯 관리 화면, 위젯)에 하나씩 있고, 어느 자리의 시험이 표를 읽지 않으면 그것을 잡는 시험을 둔다(선례의 방식). 위젯 관리 서버와 위젯 관리 화면의 시험은 판정과 까닭을 함께 견주고, 위젯의 시험은 판정만 견준다("주소의 검사").

| 주소 | 판정 | 까닭 |
|---|---|---|
| `https://help.example.com/login` | 받는다 | |
| `https://help.example.com/login?return=/orders#top` | 받는다 | |
| `http://localhost:3000/login`, `http://site.localhost:3000/login` | 받는다 | |
| `http://localhost.example.test/login` | 받지 않는다 | 주소가 아니다 |
| `http://help.example.com/login` | 받지 않는다 | 주소가 아니다 |
| `https://user:pw@help.example.com/login`, `https://user@help.example.com/login` | 받지 않는다 | 주소에 사용자 정보 자리가 있다 |
| `javascript:alert(1)`, `data:text/html,x`, `mailto:help@example.com` | 받지 않는다 | 주소가 아니다 |
| `//help.example.com/login`, `/login`, `help.example.com/login` | 받지 않는다 | 주소가 아니다 |
| 2,000자를 넘는 `https://` 주소 | 받지 않는다 | 너무 길다 |

위젯 관리 화면의 화면 부품에서 보는 사례는 아래다.

- 칸을 고치면 "바뀜"과 탭의 수와 저장 띠의 수가 서고, 값을 되돌려 놓으면 사라진다. 예시 질문을 둘 고쳐도 한 칸으로 센다.
- "되돌리기"가 모든 칸을 마지막으로 저장한 값으로 돌린다.
- 거절의 답을 받으면 칸 아래에 글이 서고, 첫 오류의 탭이 골라지고, 그 칸에 포커스가 간다.
- 저장 번호가 다르다는 답, 요청 실패, 로그인이 끝났다는 답마다 저장 띠의 글이 다르고 양식의 값이 그대로다.
- 지우기가 같은 세 답을 받으면 확인 창이 열린 채 그 까닭의 글을 보이고 사이트 목록으로 가지 않는다. 저장 번호가 다르다는 답 뒤에는 "지우기" 단추가 꺼져 있다.
- 바뀐 칸이 있는 채 다른 화면으로 가려 하면 확인 창이 뜨고, 탭을 바꿀 때는 뜨지 않는다.
- 로그인이 필요한 화면의 상태 넷(처음, 로그인이 끝남, 확인하지 못함, https가 아님)이 답에 따라 선다. 탭이 다시 보이면 다시 묻는다.
- 동시에 보낸 요청 여럿이 함께 로그인하지 않았다는 답을 받으면 "갱신"은 한 번만 나가고, 요청들은 그 응답이 온 뒤에 한 번씩만 다시 나간다. 다시 보낸 요청이 같은 답을 받으면 "갱신"을 또 부르지 않고 로그인이 필요한 화면을 보인다. 위젯 테스트 페이지의 페이지 스크립트에도 같은 사례를 둔다("로그인 확인").
- 사이트 등록 화면의 고지 전문에 처음 값이 들어 있고, 그 날 수가 위젯 테스트 페이지의 쿠키 수명과 같은 값에서 온다. "위젯 테스트 페이지에 담는다"를 켤 때 고지 전문이 비어 있으면 처음 값이 들어가고, 글이 있으면 그대로다. 끌 때는 그대로다.
- 탭 줄, 확인 창, 작은 그림 고르기의 키보드 동작.

미리보기에서 보는 사례는 아래다. 미리보기가 위젯과 같은 그림을 내는지는 여기서 보지 않는다. 같은 부품이라는 것이 그 보장이고, 부품의 그림은 위젯의 시험과 사진 비교가 본다.

- 양식의 칸마다 고친 값이 화면 부품의 입력에 실린다. 비운 칸은 위젯의 기본값으로 간다.
- 보는 상태 일곱마다 표의 견본 입력이 간다.
- 밝기 단추의 처음 값과 양식의 처음 밝기를 고쳤을 때의 옮겨 감.
- 미리보기가 그려지는 동안 네트워크 요청이 하나도 나가지 않는다.
- 미리보기가 "미리보기, 저장하지 않은 값으로 그린 위젯"이라는 이름의 그림 하나로 잡히고, 그 안의 단추와 입력창과 `<main>`이 역할로 잡히지 않는다. 관리 화면 앱의 틀을 두른 스토리에 접근성 검사의 위반이 없다. 이 둘은 스토리 시험이 본다. 미리보기를 가리지 않으면 위반 셋이 나고 위젯의 단추가 잡힌다("미리보기를 그리는 부품"의 "가리는 법").
- Tab이 미리보기 안에 서지 않고 다음 조작에 닿는다는 것은 스토리 시험으로 보지 않는다. 그 시험의 흉내 Tab이 `inert`를 건너지 못하기 때문이고, 브라우저로 끝까지 가는 시험이 본다(아래 4).

스토리와 사진 비교는 아래를 든다.

- 위젯 관리 화면의 완성 화면마다 스토리를 두고 사진 비교에 넣는다. 사이트 목록(값이 있을 때, 빈 때, 좁은 폭), 로그인이 필요한 화면과 상태 셋, 사이트 하나(탭마다, 바뀜, 저장한 직후, 저장 실패, 좁은 폭, 어두운 밝기), 미리보기의 보는 상태 일곱, 사이트 등록, 확인 창 둘, 열리지 않는 사이트, 계정 메뉴다. 사진 비교의 명령과 CI의 `visual` 잡에 새 앱을 더한다.
- 위젯의 화면 부품을 공유 패키지로 옮기는 티켓은 위젯의 사진 비교가 기준 그림을 하나도 고치지 않고 통과하는 것을 수락 조건으로 둔다. 기준 그림을 고쳐야 통과하면 옮기는 일이 위젯의 모양을 바꾼 것이다.
- 예시 질문의 모양이 답으로 닿는 위젯의 사례를 위젯 전체의 시험과 위젯 e2e에 더한다(widget-login-state가 넘겼다).

위젯 테스트 페이지의 서버에서 보는 사례는 아래다. 위젯 관리 서버와 Agent OS는 대역이다.

- 운영자 쿠키가 없는 요청: 페이지에 사이트의 이름이 하나도 없다. "들어온 사람"은 들어오지 않았다고 답하고 사이트를 싣지 않는다. 토큰과 고지 확인의 기록은 거절한다.
- 운영자 쿠키가 있고 Agent OS 대역이 받아 준 요청: "들어온 사람"이 계정 이름과 열린 사이트를 답하고, 익명 모드 사이트의 토큰이 나온다. 토큰의 주장에 계정 이름이 없다.
- 발급자가 사이트 파일에 없는 사이트, 공개 출처가 허용 출처에 없는 사이트, 키가 맞지 않는 사이트는 목록에 없고 끝점이 없는 사이트의 답을 낸다. 같은 설정의 다른 사이트는 열린다. 값을 고친 설정을 다시 받아 오면 그 사이트가 열린다.
- 닫힘의 로그는 상태가 바뀔 때 한 줄이고, 같은 상태의 요청을 되풀이해도 늘지 않는다.
- 판정의 안쪽 길이 받아 올 때의 판정과 같은 답을 낸다. 브라우저의 머리가 있는 요청은 거절한다.
- Agent OS 대역에 보낸 요청이 두 경로뿐이고, "갱신"의 `Set-Cookie`가 줄의 수까지 글자 그대로 돌아오며(거절 때 지우는 줄도 그렇다), 표식을 넣은 쿠키와 계정 이름이 로그에 없다. 위젯 관리 서버의 사례 셋(스스로 갱신하지 않는다, 로그인 쿠키 둘을 담은 `Cookie`만 전한다, 클라이언트가 쿠키를 기억하지 않는다)을 이 서버에서도 본다. 이 사례들은 생성 클라이언트 패키지에 더한 클라이언트로 지은 서버에서 돈다. 프로브가 타입 없는 클라이언트로 잰 것을 계약의 타입을 준 클라이언트로 다시 보는 자리다.
- 운영자 쿠키가 없거나 Agent OS 대역이 거절한 요청에서는 위젯 관리 서버 대역이 받은 요청이 없다. 페이지, 정적 파일, 상태 확인의 요청에서는 두 대역이 받은 요청이 없다.
- 위젯 관리 서버 대역의 값을 바꾼 뒤의 첫 요청이 새 값을 답한다. 익명 모드이던 사이트를 로그인 모드로 바꾸면 바로 다음 토큰 요청이 거절된다(기억하지 않는다).
- 위젯 관리 서버 대역이 내려가 있거나, 제한 시간 안에 답하지 않거나, 오류를 답하거나, 꼴에 맞지 않는 답을 내면 "들어온 사람"이 계정 이름과 함께 목록을 받아 오지 못했다고 답하고, 토큰과 고지 확인의 기록은 설정을 받아 오지 못했다는 답을 낸다. 그 답은 들어오지 않았다는 답과 다르다. 답하지 않는 대역에도 제한 시간 안에 답이 온다(시험은 제한 시간을 짧게 준다).
- Agent OS 대역이 답하지 않으면 "들어온 사람"이 로그인을 확인하지 못했다고 답한다("위젯 테스트 페이지의 운영자 문").
- 옛 판의 설정 파일과 사이트의 목록이 남은 설정 파일은 뜰 때 거절한다.

이 기능이 새로 두는, 브라우저로 끝까지 가는 시험은 하나다. 관리 화면, 위젯 관리 화면, 방문자용 주소를 같은 이름의 다른 포트에 세운다. 로그인 쿠키가 그 이름에 실려야 하기 때문이다.

1. 로그인하지 않은 브라우저로 위젯 테스트 페이지를 열면 문만 보이고, 위젯 관리 화면을 열면 "로그인이 필요하다"가 보인다.
2. 관리 화면에서 운영자 계정으로 로그인한다.
3. 위젯 관리 화면을 열어 사이트 하나를 등록한다. 위젯 테스트 페이지에 담고 익명 모드로 둔다.
4. 위젯의 이름과 고지의 짧은 줄을 고치면 저장하기 전에 미리보기의 위젯이 그 글로 바뀐다. Tab을 눌러 화면의 조작을 끝까지 돌아도 포커스가 미리보기의 위젯 안에 한 번도 서지 않고, 미리보기 뒤의 조작(저장 단추)에는 닿는다.
5. 저장한다. 아무것도 다시 띄우지 않는다.
6. 위젯 테스트 페이지를 열면 그 사이트의 위젯이 고친 이름과 고지로 그려지고, 고지를 확인한 뒤 질문 하나에 출력이 선다(e2e 준비의 가짜 모델).
7. 바꾼 기록에 그 계정 이름과 이전 값과 새 값이 남아 있다.

- 이 시험은 위젯 관리 화면 앱의 e2e로 두고 CI에 그 앱의 e2e 잡을 더한다. 준비는 `web/packages/e2e-stack`에 더한다. 위젯 관리 서버와 그 PostgreSQL, Agent OS의 계정이 준비에 든다.
- 위젯 테스트 페이지의 기존 e2e와 실제 모델 e2e(`-m llm_portal`)는 운영자로 들어오는 단계를 앞에 더하고, 사이트를 설정 파일이 아니라 저장 경로로 넣는다. 그 시험들이 보던 것(고지 확인, 토큰, 사이트 바꾸기)은 그대로 본다. 그 시험들의 준비에 위젯 관리 서버와 데이터베이스가 드는 것은 widget-login-state가 먼저 더하고(그 명세의 Testing Decisions "수락 문장의 자리"), 이 기능이 더하는 것은 Agent OS의 운영자 계정과 로그인 단계다. 그래서 이 기능이 CI에 새로 치르는 값은 위젯 관리 화면 앱의 e2e 잡 하나와 기존 두 시험의 준비가 길어지는 것이다.
- 위젯 관리 화면의 중계는 그 앱의 e2e 준비가 띄운 진짜 앱으로 본다. 위의 끝까지 가는 시험이 운영자용 경로를 중계로 지나고, 같은 준비에서 사례 둘을 더 본다. 로그인 쿠키도 브라우저의 머리도 없는 요청으로 위젯 관리 화면의 주소에서 안쪽 길을 부르면 없다는 답이 오고 위젯 테스트 페이지 설정이 실리지 않는다. 그리고 로그인한 브라우저의 페이지가 "갱신"을 중계로 부르면 그 답의 `Set-Cookie` 두 줄이 브라우저의 쿠키로 서서, 쿠키 둘의 값이 부르기 전과 달라진다. 수명이 끝나기를 기다리지 않고 "갱신"을 바로 불러 본다. 중계가 넘기는 경로의 가름 자체는 그 앱의 설정을 읽는 빠른 시험으로도 잠근다(선례는 관리 화면 앱의 `next.config.test.ts`).
- 프록시와 compose: 위젯 관리 화면용 포트가 위젯 관리 화면으로만 가고, 방문자용 포트에서 위젯 관리 서버의 운영자용 경로와 안쪽 길, 위젯 테스트 페이지의 안쪽 길이 닿지 않는다. 위젯 관리 화면용 포트에서 위젯 관리 서버의 안쪽 길이 닿지 않는 것은 위의 중계 사례가 본다. 자리는 단독 배포 e2e다(`web/packages/e2e-standalone`. release-image 명세 Testing Decisions의 첫째 이음매이고, 지은 이미지와 `deploy/standalone/`의 compose와 프록시를 실제로 띄운다). 그 시험에는 호스트에 연 포트가 80, 443, 3000 셋뿐이라는 사례와 허용 목록 밖의 경로가 404라는 사례가 이미 있어(`e2e/deployment.e2e.ts`, 코드를 읽었다), 포트와 컨테이너를 더하는 티켓이 그 목록을 고치고 위의 사례를 더한다. CI의 그 잡은 main으로 가는 PR과 main 푸시에서만 실제로 시험하므로(`.github/workflows/ci.yml`의 `e2e-standalone` 잡을 읽었다), 그 티켓은 이 PC의 Docker로 돌린 결과를 일지에 적는다(`CLAUDE.md` 검증 명령의 단독 배포 e2e).
- 손으로 치는 검증 명령에 는 것(새 e2e, 새 사진 비교)을 `CLAUDE.md`의 검증 명령에 적는다("티켓이 코드와 같은 티켓에서 고치는 문서").

## Out of Scope

다른 기능이 맡는 것은 받는 기능의 이름을 적었다. 그 기능의 기능 계획(`.scratch/<기능>/plan.md`)에 설계가 이미 적어 둔 것은 그대로 두고, 이 명세가 새로 넘기는 것을 portal-login, portal-login-admin, deploy-package, widget-login-state의 기능 계획에 더 적었다. 앞서 끝나는 기능에 바라는 것("선행 기능에 기대는 것")은 admin-login과 widget-admin-server의 기능 계획에 적었다.

- **회사 계정 문과 회사 로그인.** portal-login이 한다. 위젯 테스트 페이지의 회사 계정 문, 로그인 모드 사이트의 로그인, 위젯 테스트 페이지의 로그인과 로그아웃 끝점, 닫힌 사이트의 넷째 까닭(로그인 서버 항목이 없다)이다. portal-login의 Blocked by에는 이 기능이 없어 어느 쪽이 먼저 끝날지 정해져 있지 않다. 그래서 "순서에 달린 것"은 뒤에 끝나는 쪽이 정한다.
- **로그인 서버 항목을 화면에서 고치는 일.** portal-login-admin이 한다(이 기능과 portal-login을 기다린다). "위젯 테스트 페이지" 탭에 사이트가 쓰는 로그인 서버 항목을 고르는 칸이 들면 그 기능이나 portal-login이 더한다.
- **허용 출처와 요청 글자 수 상한.** 위젯이 뜰 때 그 값을 받는 일은 widget-runtime-values가, 화면에서 고치는 일은 0.1 판 뒤의 site-limits-admin이 한다.
- **계정마다 고칠 수 있는 것을 가르는 일.** admin-roles가 한다. 이 기능에서는 로그인한 운영자 계정이면 누구나 모든 사이트를 읽고 쓴다(ADR 0064 결정 "고칠 수 있는 계정").
- **공개 데모와 공개 계정.** public-demo가 한다(ADR 0065 결정 "공개 데모").
- **배포 파일 묶음과 배포 안내.** deploy-package가 한다. 위젯 관리 화면용 포트와 여닫는 법, 같은 이름으로 열어야 한다는 조건, 첫 사이트를 등록하는 단계, 사이트 파일을 고친 뒤 무엇을 다시 띄우는지의 절차를 그 기능이 안내에 싣는다.
- **위젯 쪽 데이터베이스의 백업과 복원.** ops-backup-upgrade가 한다. 이 기능이 그 데이터베이스에 더하는 표(바꾼 기록)도 그 대상이다.
- **이름 바꾸기.** 코드와 문서에 남은 "위젯 미리보기 페이지"를 "위젯 테스트 페이지"로 바꾸는 일은 ADR 0065 결정 "이름"의 chore가 한다. 이 기능의 티켓은 자기가 고치는 파일에서만 새 이름을 쓴다.
- **위젯이 모양들을 그리는 일.** widget-login-state가 한다. 이 기능은 위젯의 화면 부품을 옮기고 예시 질문의 모양을 답에 실을 뿐, 부품이 그리는 모양을 바꾸지 않는다.
- **위젯이 긴 글을 받았을 때의 접근성.** widget-login-state가 본다(이 기능보다 먼저 끝난다). 옮긴 부품을 가리지 않고 둔 스토리에 미리보기의 높이를 넘는 긴 안내를 주자 접근성 검사가 `scrollable-region-focusable`을 냈다. 위젯의 `<main>`이 스크롤되는데 키보드로 닿을 길이 없다는 위반이다(손으로 봤다, `.scratch/portal-admin/probes/shared_widget_parts/README.md`의 "휠과 클릭". 관리 화면 앱의 Storybook에서 본 것이고 위젯 앱의 Storybook에서는 보지 않았다). 가린 미리보기에서는 나지 않아 이 기능의 일이 아니다. 예시 질문과 고지 전문을 짓는 그 기능의 티켓이 글이 상한까지 찼을 때의 스토리로 본다.

짓지 않는 것은 아래다. 받는 기능이 없다.

- 바꾼 기록을 보는 화면과 그것을 내주는 경로(ADR 0064 결정 "바꾼 기록").
- 설정 파일의 값을 데이터베이스로 옮기는 명령(같은 ADR 결정 "값을 옮기는 길은 짓지 않는다").
- 사이트 이름을 바꾸는 일. 사이트 개발자의 태그가 그 이름을 적고 있어, 바꾸려면 새 이름으로 등록하고 옛 사이트를 지운다.
- 사이트 목록의 찾기, 거르기, 쪽 나누기. 0.1 판의 사이트 수에서는 표 하나로 본다.
- 저장하지 않은 값을 위젯 테스트 페이지에서 보는 일. 저장하기 전에 보는 자리는 미리보기이고, 위젯 테스트 페이지는 저장한 값만 그린다(ADR 0065 결정 "미리보기").
- 미리보기에서 질문을 보내는 일.
- 고지를 고친 뒤 다시 확인받는 일("고지를 고쳐도 다시 확인받지 않는다").
- 위젯 관리 화면의 밝기를 고르는 스위치와 다른 언어의 화면.
- 위젯 관리 화면에서 로그아웃하는 단추. 로그아웃은 관리 화면에서 한다.
- Agent OS의 계약(`sdk`, `openapi.json`, 사이트 파일의 형식, 사이트 토큰의 주장)을 바꾸는 일. 이 기능은 그것을 하나도 바꾸지 않는다.

## Further Notes

- **티켓을 쪼개기 전에 다시 볼 것.** 이 기능은 세 기능을 기다리고(widget-admin-server, admin-login, widget-login-state) 그 가운데 앞의 둘은 이 명세를 쓸 때 명세가 없다. 이 명세가 그 기능들에 기댄 것은 "선행 기능에 기대는 것"에 모았다. `/to-tickets`를 돌기 전에 세 명세를 열어 그 절과 대 보고, 어긋난 자리(경로의 접두사와 오류 답의 봉투, 사이트 이름의 꼴, 답의 판 표시 규칙, 포트를 여닫는 설정의 이름, 짧은 유예)를 이 명세에서 고친다. portal-login이 그때 끝나 있으면 "순서에 달린 것"도 정한다.
- **widget-login-state의 명세는 이 명세를 쓰는 동안 병합됐다(PR 593).** 이 명세는 병합 전의 초안을 읽고 썼고, 병합된 글(`.scratch/widget-login-state/spec.md`)에 다시 댔다. 이 명세가 든 절 이름 셋("위젯 설정의 항목과 앞서는 차례", "주소의 검사", "위젯 테스트 페이지")이 그대로 있고, 기대는 내용(예시 질문의 넷과 100자, 로그인 전에는 예시 질문을 그리지 않는 것, 문의 링크의 글 "문의하기", `tokenProvider`가 끝점이 답하지 못하면 던지는 것, 그 명세가 이 기능에 넘긴 다섯)도 같다. 그 기능의 티켓이 구현하며 명세를 고치면 위와 같은 때에 맞춘다.
- **첫 티켓은 계약이다.** 위젯 관리 서버의 계약 파일에 "저장 경로"의 경로들을 더하는 티켓이 다른 티켓을 막는다(`CLAUDE.md` 작업 규약 2). 그 뒤는 얇게 끝까지 가는 차례를 권한다. 로그인을 확인하고 사이트 하나를 등록해 목록에 보이는 길을 먼저 세우고, 그 위에 칸과 검사와 바꾼 기록, 미리보기(부품을 옮기는 티켓이 앞선다), 위젯 테스트 페이지가 설정을 받아 오는 것, 운영자 문, 닫힌 사이트의 알림, compose, 끝까지 가는 브라우저 시험을 얹는다.
- **부품을 옮기는 티켓은 다른 일을 섞지 않는다.** 위젯의 화면 부품을 공유 패키지로 옮기는 변경은 위젯의 모양을 바꾸지 않는다는 것을 사진 비교로 보이는 변경이다. 같은 티켓에서 부품을 고치면 그 증거가 흐려진다. 예시 질문의 모양을 답에 싣는 일과 위젯의 주소 검사에 사용자 정보 자리와 길이 상한을 더하는 일은 다른 티켓으로 둔다.
- **상한의 수는 어림이다.** 칸마다의 글자 수 상한과 주소의 2,000자는 재지 않고 정했다. 서버가 다른 서버를 부르는 호출의 제한 시간 2초는 PC 한 대의 루프백에서 잰 페이지 응답의 최댓값(411ms)보다 길게 고른 값이고, 배포에서는 재지 못했다("위젯 테스트 페이지 설정을 데이터베이스로"). 운영에서 걸리면 수만 고친다. 예시 질문의 넷과 100자만 위젯이 받는 상한에 맞춘 값이다.
- **프로브의 대역이 고른 것은 선행 명세와 다시 댄다.** 로그인 쪽의 측정(`.scratch/portal-admin/probes/login_relay/`)에서 Agent OS는 대역이고, 대역이 경로와 쿠키의 이름, 갱신이 거절될 때 쿠키를 지우는 줄, 유예의 두 뜻, JWT의 수명을 골랐다. 설정 쪽의 측정(`settings_fetch/`)의 대역은 데이터베이스 드라이버 하나(psycopg 3의 동기 연결 묶음)를 골랐다. admin-login과 widget-admin-server의 명세가 다르게 서면 "로그인 확인"과 "위젯 테스트 페이지 설정을 데이터베이스로"의 "쟀다"가 선 자리를 다시 본다. 다시 잴 자리는 프로브마다의 `README.md`의 "재지 못한 것"이 든다.
- **관리 화면 앱의 중계가 500을 낸 일이 한 번 있었다.** 로그인 쪽 프로브의 전체 실행 하나에서, 대역의 uvicorn이 쉬는 연결을 기본값(5초) 뒤에 닫을 때 관리 화면 앱의 Next 중계가 요청 넷 가운데 둘에 500을 냈다(쟀다). 까닭은 재지 못했다. 상류가 쉬는 연결을 닫는 순간과 중계가 그 연결을 다시 쓰는 순간이 겹쳤다는 것은 어림이다. 프로브는 대역이 연결을 닫기까지의 시간을 300초로 늘려 돌았고 그렇게 돈 전체 실행에서는 다시 나지 않았다. 기본값으로 돈 다른 전체 실행 하나에서도 나지 않았으므로 이것으로 까닭이 가려진 것은 아니다. 위젯 관리 화면도 같은 방식의 중계로 위젯 관리 서버에 닿으므로, 이 기능의 e2e가 드물게 500으로 실패하면 이것을 먼저 본다. `serve`의 그 값을 정하는 일은 admin-login의 기능 계획에 적었다.
- **위젯 관리 서버가 내려가 있을 때.** 위젯 관리 화면은 요청마다 위젯 관리 서버를 거치므로 "로그인을 확인하지 못했다"와 같은 화면을 보인다. 운영자가 보기에 두 까닭(Agent OS 서버가 답하지 않는다, 위젯 관리 서버가 답하지 않는다)이 갈리지 않는다. 0.1 판에서는 그대로 두고, 가르려면 화면의 중계가 상류에 닿지 못했다는 답을 따로 내게 한다.
- **쓰는 말.** 이 명세는 위젯 관리 화면을 "관리 화면"으로 줄이지 않는다. "관리 화면"은 Agent OS의 웹 앱이다. "테스트"는 메뉴에 보이는 글자에만 쓰고, 자동으로 도는 검사는 "시험"이라고 적었다(ADR 0064 결정 ""테스트" 메뉴와 공개 주소"가 적은 대가다).
