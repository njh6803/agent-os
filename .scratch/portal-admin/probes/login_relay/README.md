# login_relay: 운영자 로그인 쿠키를 다른 포트의 서버가 Agent OS에 전하는 흐름

기능 `portal-admin`의 명세가 쓰는 프로브다. ADR 0064 결정 "로그인"과 Consequences "재지 않은 것", ADR 0065 Consequences "재지 않은 것"이 돌려 보지 않았다고 넘긴 흐름을 대역(스텁)과 실제 Chromium으로 쟀다. 결정은 하지 않고 결과만 낸다.

재는 흐름은 이렇다. 운영자가 관리 화면(포트 A)에서 로그인해 쿠키 둘을 받는다. 브라우저는 같은 호스트의 다른 포트(위젯 관리 화면 B, 위젯 테스트 페이지 C)에도 그 쿠키를 보낸다. 그 포트의 서버가 받은 쿠키를 Agent OS의 "지금 누구인지"와 "갱신" 경로에 전해 로그인을 확인하고 이어 주며, 갱신 때 Agent OS가 낸 새 `Set-Cookie`를 브라우저에 되돌린다.

실제 Agent OS의 로그인 경로도, 위젯 관리 서버도, 위젯 테스트 페이지 서버의 운영자 문도 아직 없다. 그래서 셋 다 대역이고, 아래 결과는 대역과 실제 Chromium과 실제 관리 화면 앱의 Next 중계 사이에서 잰 것이다.

## 돌리는 법

저장소 루트에서 친다.

```
pnpm -C web install --frozen-lockfile
node .scratch/portal-admin/probes/login_relay/probe.mjs
```

- 종료 코드 0은 셋이 모두 맞을 때뿐이다. 예외 없이 끝났다, 표지가 없는 회차가 없다, `stable` 결과가 `expected.json`과 같다.
- `--mode dev`는 `next build` 없이 `next dev`로 포트 B를 띄운다. 기본은 `start`다(빌드가 `web/apps/admin/.next/`를 다시 쓴다. 무시되는 폴더다).
- `--only control,clients,setcookie,flow,concurrency,raw,jar,openapi`로 묶음을 고르면 `expected.json`과 견주지 않는다.
- `--update`는 이 실행의 `stable`을 `expected.json`에 받아 적는다. 측정이 아닌 회차가 하나라도 있으면 쓰지 않는다.
- `--out <폴더>`에 원본 기록 `results.json`을 쓴다(없으면 임시 폴더). 대역 셋이 받은 요청의 머리, 중계가 한 호출, 프로세스 셋의 출력이 든다.
- `--rounds 5`(응답의 차례를 건드리지 않는 chain 회차의 수), `--ttl 2`(JWT 수명, 초), `--grace 1`(유예, 초. `ttl`보다 작아야 한다), `--keep-alive 300`(대역 둘이 쉬는 연결을 닫기까지의 초. 까닭은 아래 "측정 밖에서 본 것"), `--channel chromium`.

같은 체크아웃에서 두 실행을 함께 돌리지 않는다. `start` 모드의 빌드가 같은 `.next/`를 쓴다.

## 필요한 것

- `uv`(대역 둘은 `uv run python`으로 뜬다. 맨 `python`은 쓰지 않는다)와 프로젝트의 파이썬 의존성(FastAPI, uvicorn, httpx, httpx2)
- Node와 `web/`의 의존성(`pnpm -C web install --frozen-lockfile`), Playwright의 Chromium. `openapi-fetch`는 따로 설치하지 않는다. `web/packages/api-client`가 의존하는 것을 그 패키지를 기준으로 풀어 쓴다(`probe.mjs`의 머리)
- Windows에서는 PowerShell, 그 밖에서는 `ps`(프로세스를 끄기 직전에 명령줄을 읽는다)

포트는 실행마다 빈 포트를 고른다. 띄운 프로세스 셋(A, W, B)은 끝에 트리째 내리고, 포트가 연결을 거절하는지로 내려갔는지 본다. 끄기 직전에 그 pid의 명령줄을 읽어 이 실행의 포트가 있을 때만 끈다(Windows는 `taskkill /T /F`, 그 밖은 프로세스 그룹). 없으면 끄지 않고 그 pid를 찍으며, 그때 프로세스가 남아 있으면 포트 확인에 걸려 실행이 "내리지 못했다"로 끝난다. Windows 밖의 갈래(`ps`로 명령줄을 읽는다)는 돌려 보지 않았다. C는 측정 스크립트의 프로세스 안에 선다.

위젯 관리 서버 대역은 Agent OS를 부르는 HTTP 클라이언트를 셋 두고, 셋 다 `AsyncClient` 하나를 서버가 사는 동안 함께 쓴다. 경로의 첫 마디가 고른다.

- 마디 없음(브라우저의 `/api/<경로>`): httpx 0.28.1. 이 저장소에서는 dev 전용 의존성이다. 처음 잰 길이라 결과 3, 결과 4의 대부분, 결과 5는 이 길에서만 쟀다.
- `/x2/<경로>`(브라우저의 `/api/x2/<경로>`): httpx2 2.13.0. 이 저장소의 런타임 의존성이다. 결과 1, 결과 2, 결과 4의 설계 2(유예 0), 덤을 이 길에서도 쟀다.
- `/x2n/<경로>`: 쿠키를 받지 않는 통을 준 httpx2. 덤의 대조에만 쓴다.

위젯 테스트 페이지 서버 대역은 세 길로 부른다. Node의 전역 `fetch`(경로 `/fetch/...`), `node:http`의 `request`(경로 `/http/...`), `openapi-fetch`의 클라이언트(경로 `/oaf/...`)다. 셋째 길의 클라이언트는 `createClient({ baseUrl })`로 하나를 지어 서버가 사는 동안 함께 쓴다. `web/`의 판정자(`web/eslint.config.mjs`)가 전역 `fetch`를 직접 쓰는 것을 막으므로 실제 서버가 쓸 호출 방식은 셋째 길이다. 결과 1, 결과 2, 결과 6을 그 길에서 쟀다.

## 대역이 고른 것

ADR 0062에서 옮긴 것은 넷이다. 쿠키 둘(수명이 짧은 HS256 JWT와 서버가 기억하는 갱신용 번호)이 `__Host-` 접두사에 `HttpOnly; Secure; SameSite=Strict; Path=/`다. 갱신용 번호는 쓸 때마다 바뀌고 이미 바꾼 옛 번호가 다시 오면 그 로그인을 끊는다. JWT는 서버 상태를 보지 않는다. 요청 출처 검사는 `Sec-Fetch-Site`가 있으면 `same-origin`만 받고, 없으면 `Origin`도 없을 때만 받는다.

ADR이 정하지 않아 대역이 고른 것은 아래다. 실제 구현이 다르게 고르면 그 자리의 결과는 다시 재야 한다.

- 경로 이름(`/auth/login`, `/auth/me`, `/auth/refresh`, `/auth/logout`), 쿠키 이름(`__Host-aos_at`, `__Host-aos_rt`), 응답의 모양. JWT 쿠키는 세션 쿠키이고 갱신용 번호 쿠키는 `Max-Age=1800`이다. 쿠키 줄은 Starlette의 `set_cookie`와 `delete_cookie`가 짓는다.
- 갱신이 거절되면 401에 쿠키 둘을 지우는 줄(`Max-Age=0`)을 싣는다. "지금 누구인지"의 401에는 싣지 않는다.
- "짧은 유예"의 뜻. ADR은 유예를 둔다고만 적었다. 대역은 뜻 둘을 설정으로 둔다. 둘 다, 이미 바꾼 옛 번호가 바뀐 때부터 유예 안에 다시 오면 끊지 않고 새 JWT와 새 번호를 낸다. 다른 것은 앞서 낸 번호를 어떻게 두느냐다.
  - `chain`: 앞서 낸 번호를 그 순간 옛 번호로 돌린다. 통하는 번호는 언제나 마지막에 낸 하나다.
  - `family`: 앞서 낸 번호도 그대로 통한다. 통하는 번호가 여럿이 된다.
  - 유예가 지난 옛 번호가 오면 두 뜻 모두 그 로그인을 끊는다. 유예 0은 유예가 없다는 뜻이다.
  - 셋째 뜻(유예 안의 옛 번호에 앞서 낸 것과 같은 번호를 다시 내준다)은 대역에 없고 재지 않았다.
- 비밀번호를 보지 않는다. 로그인은 정해진 계정 이름 하나만 받는다. 쿠키 값은 대역이 지은 무작위 값이고 비밀이 아니다.
- JWT 수명 2초, 유예 1초. 실제 값(분 단위)과 다르다. 만료를 기다리는 시간을 줄이려는 것이다.

중계의 설계 둘도 대역이 지은 것이다.

- 설계 1(중계가 스스로 갱신): 중계가 "지금 누구인지"에서 401을 받으면 그 자리에서 "갱신"을 부르고, 받은 `Set-Cookie` 줄을 자기 응답에 싣는다.
- 설계 2(화면이 갱신을 한 번 부름): 중계는 401을 그대로 돌려준다. 페이지의 스크립트가 401을 받으면 중계의 갱신 경로를 부르고 요청을 다시 보낸다. 같은 탭에서 동시에 401을 받은 요청들은 갱신 하나를 함께 기다린다.

## 표지

회차마다 재려는 상황이 실제로 났다는 것을 단언하고, 표지가 하나라도 없는 회차는 측정으로 세지 않는다. 그런 회차가 있으면 종료 코드가 0이 아니다. 표지의 목록은 `probe.mjs`의 머리 주석이 든다. 요약하면 이렇다.

- JWT가 실제로 만료됐다: Agent OS 대역의 기록에 그 요청의 "지금 누구인지"가 401 `access_expired`로 있다.
- 갱신 요청이 중계에서 왔다: 그 기록에 브라우저만 붙이는 `Sec-Fetch-Site`가 없고, 주소의 `probe=<태그>.<길>`이 그 중계의 길이다.
- 포트 B의 요청이 Next 중계를 지났다: 위젯 관리 서버 대역이 받은 머리에 Next의 프록시가 붙이는 `x-forwarded-host: localhost:<B>`가 있다.
- 쿠키 값이 실제로 바뀌었다: 브라우저 저장소의 값이 대역이 그 갱신에서 낸 값이다(이름표 `at0·rt0 → at1·rt1`).
- 동시 갱신이 실제로 났다: 같은 번호(`rt0`)를 든 갱신이 둘 이상 대역에 닿았다.
- 설계 2가 실제로 시험됐다: 요청 넷이 모두 401을 받았다(페이지가 센 수).
- 응답의 차례가 실제로 뒤집혔다: 브라우저에 남은 번호가 대역이 먼저 낸 `rt1`이다.
- 늦은 401이 실제로 갱신이 끝난 뒤에 닿았다: 화면이 갱신을 두 번 불렀고 둘째가 든 번호가 첫 갱신이 낸 `rt1`이다.
- 클라이언트가 쿠키가 든 응답을 실제로 받았다: 그 회차에 중계가 한 호출의 기록에 `Set-Cookie` 줄이 있다.
- 제한 시간이 실제로 걸렸다: 끊긴 호출이 대역의 기록에 있고, 던져진 것의 이름이 `TimeoutError`이고, 걸린 시간이 제한 시간과 대역이 답을 잡아 둔 시간 사이다. 대역이 답을 잡아 두었다는 것은 긴 제한 시간의 호출이 그 시간 뒤에 답을 받은 것으로 본다.

결과를 본 뒤 판정 기준을 두 번 바꿨다.

- 설계 2 회차의 `stable`에서 갱신의 수와 번호(대역에 닿은 갱신의 수, 판정의 차례, 든 번호, 화면이 부른 수, 통하는 번호, 서버의 마지막 번호, 브라우저에 남은 값)를 뺐다. `dev` 모드의 한 회차에서 갱신이 둘이 나, 회차마다 갈릴 수 있는 값이라는 것이 드러났기 때문이다. 대신 갱신의 수와 무관한 둘(판정의 가짓수가 교체뿐인가, 같은 번호를 든 갱신이 둘 이상이었는가)을 `stable`에 넣었고, 갱신이 둘인 경우를 일부러 만드는 회차를 더했다.
- 설계 2의 표지 이름을 "요청 넷이 모두 401을 받은 뒤에 화면이 갱신을 불렀다"에서 "요청 넷이 모두 401을 받았다"로 고쳤다. 단언이 보는 것은 페이지가 센 401의 수뿐이고, 갱신이 넷 다 닿은 뒤에 불렸는지는 보지 않는다. 옛 이름이 단언보다 넓었다.
- 대역 둘의 keep-alive를 300초로 늘린 것은 아래 "측정 밖에서 본 것"이 적는다. 판정 기준은 그대로다.

지금 판의 마지막 실행 셋(2026-11-16. `--update`를 준 `start` 실행, 인자 없는 `start` 실행, `--mode dev` 실행)은 모두 회차 45개가 모두 측정이었고 표지 241개가 모두 있었다. 뒤의 둘은 `expected.json`과 같아 종료 코드 0이었다.

## 결과

근거의 종류를 문장 끝에 적는다. "쟀다"는 2026-11-16에 이 스크립트가 낸 값이고 `expected.json`의 `stable`에 있다. 회차마다 갈릴 수 있는 값(응답이 닿는 차례에 달린 것)은 `stable`에 넣지 않았고 그렇다고 적는다.

### 1. 서버 사이 요청이 스스로 붙이는 머리와 요청 출처 검사

중계가 `Cookie` 머리 하나만 더했을 때 Agent OS 대역이 받은 머리다(쟀다. 대역이 받은 그대로이고, uvicorn이 이름을 소문자로 준다).

| 클라이언트 | GET(지금 누구인지) | POST(갱신)에 더 붙는 것 | 검사 |
|---|---|---|---|
| httpx 0.28.1 | `host`, `accept: */*`, `accept-encoding: gzip, deflate, zstd`, `connection: keep-alive`, `user-agent: python-httpx/0.28.1`, `cookie` | `content-length: 0` | 통과, 200 |
| Node `fetch` | `host`, `connection: keep-alive`, `cookie`, `accept: */*`, `accept-language: *`, `sec-fetch-mode: cors`, `user-agent: node`, `accept-encoding: gzip, deflate` | `content-length: 0` | 통과, 200 |
| `node:http` | `cookie`, `host`, `connection: keep-alive` | `content-length: 0` | 통과, 200 |
| httpx2 2.13.0 | `host`, `accept: */*`, `accept-encoding: gzip, deflate`, `connection: keep-alive`, `user-agent: python-httpx2/2.13.0`, `cookie` | `content-length: 0` | 통과, 200 |
| `openapi-fetch` 0.17.0 | `host`, `connection: keep-alive`, `cookie`, `accept: */*`, `accept-language: *`, `sec-fetch-mode: cors`, `user-agent: node`, `accept-encoding: gzip, deflate` | `content-length: 0` | 통과, 200 |

- 다섯 다 `Origin`과 `Sec-Fetch-Site`를 붙이지 않았다. GET도 POST도 그랬다(쟀다).
- `openapi-fetch`의 클라이언트가 보낸 머리는 Node의 `fetch`를 직접 부른 길과 이름도 값도 차례도 같았다(쟀다). 표의 그 행이 대역이 받은 머리 전체이고, `openapi-fetch`가 스스로 더한 머리는 없었다. 이 호출들에는 몸이 없다. 몸이 있는 호출에는 `openapi-fetch`가 `Content-Type: application/json`을 더하고, 넘기지 않으면 `redirect: "follow"`로 부른다(둘 다 코드를 읽었다. 0.17.0의 `dist/index.mjs`. 재지 않았다).
- httpx2가 붙이는 머리는 httpx와 둘이 다르다. `user-agent`의 이름과 판이 다르고, `accept-encoding`에 `zstd`가 없다(쟀다. 이 설치에서 그랬다는 것이고, `zstd`는 설치된 압축 라이브러리에 달릴 수 있다는 것은 어림이다).
- Node의 `fetch`는 `sec-fetch-mode: cors`를 스스로 붙인다. ADR 0062의 검사는 `Sec-Fetch-Site`와 `Origin`만 보므로 걸리지 않았다(쟀다. 대조 회차가 `Sec-Fetch-Mode: cors`만 든 요청을 대역이 받는 것을 따로 보였다). 실제 검사가 `Sec-Fetch-Mode`도 보게 지어지면 이 길이 걸린다(어림).
- 같은 요청에서 브라우저는 중계에 `sec-fetch-site: same-origin`을 보냈고 POST에는 `origin: http://localhost:<그 포트>`도 보냈다. 그 머리들은 Agent OS 대역에 닿지 않았다(쟀다).

### 2. `Set-Cookie`가 중계를 지나 브라우저에 닿는 모양

- 다섯 길(브라우저 → Next(B) → 위젯 관리 서버 대역의 httpx → Agent OS 대역, 같은 길의 httpx2, 브라우저 → C의 `fetch` 길 → Agent OS 대역, 브라우저 → C의 `node:http` 길 → Agent OS 대역, 브라우저 → C의 `openapi-fetch` 길 → Agent OS 대역) 모두에서, Agent OS 대역이 낸 두 줄과 브라우저가 받은 두 줄(CDP의 `Network.responseReceivedExtraInfo`)이 줄 수도 차례도 글자도 같았다. 브라우저가 거절한 줄은 없었다(쟀다).
  - 줄을 따로 꺼내는 API는 httpx와 httpx2가 같다. 대역은 두 클라이언트의 응답에 같은 코드 `response.headers.get_list("set-cookie")`를 쓴다(쟀다. httpx2 2.13.0의 `_models.py`에 `Headers.get_list`가 있는 것은 코드를 읽었다).
  - `openapi-fetch`의 호출(`client.GET(…)`, `client.POST(…)`)이 돌려주는 객체의 `response` 칸이 원래의 `Response`다. 위젯 테스트 페이지 서버 대역은 `result.response.headers.getSetCookie()`로 줄마다 꺼내 자기 응답에 실었고, 브라우저가 받은 두 줄이 Agent OS 대역이 낸 것과 같았다(쟀다. 답이 200이든 401이든 `response` 칸이 있었고, 401에 실린 지우는 줄 둘도 같은 코드로 닿았다).
  - 줄의 모양: `__Host-aos_at=<값>; HttpOnly; Path=/; SameSite=strict; Secure`, `__Host-aos_rt=<값>; HttpOnly; Max-Age=1800; Path=/; SameSite=strict; Secure`
- 쿠키 저장소의 속성은 갱신 전과 같았다. `domain=localhost`(호스트 전용), `path=/`, `httpOnly=true`, `secure=true`, `sameSite=Strict`이고 JWT 쿠키는 세션 쿠키, 갱신용 번호 쿠키는 만료가 `Max-Age`를 따랐다(쟀다. `context.cookies()`).
- 갱신이 거절될 때 대역이 낸 지우는 줄 둘(`<이름>=""; expires=<그때의 시각>; HttpOnly; Max-Age=0; Path=/; SameSite=strict; Secure`)도 다섯 길 모두 그대로 닿았고, 닿은 뒤 브라우저의 저장소에 쿠키가 없었다(쟀다).
- 대조: 중계가 줄마다 옮기지 않고 `headers["set-cookie"]` 한 값으로 옮기면 브라우저는 쉼표로 이어진 한 줄을 받았다. JWT 쿠키만 새 값이 됐고 갱신용 번호 쿠키는 옛 값(`rt0`)으로 남았다(서버가 낸 것은 `rt1`). 다음 갱신이 옛 번호 재사용이 되는 상태다(쟀다). 그대로 옮긴다는 것은 줄마다 옮긴다는 뜻이어야 한다.

### 3. 흐름 전체

여섯 갈래를 쟀다. 포트 B의 설계 1과 설계 2(httpx), 포트 C의 설계 1(`fetch`, `node:http`), 포트 C의 주소로 문서 열기(`fetch`, `node:http`. 문서 요청은 화면이 갱신을 부를 수 없어 서버가 스스로 갱신하는 길이다).

여섯 갈래 모두 아래 차례가 그대로 났다(쟀다).

1. 포트 A의 페이지가 로그인한다(200).
2. 다른 포트의 요청이 만료 전에 200이다.
3. JWT가 만료된 뒤 다른 포트의 요청이 200이다. 대역의 기록은 "지금 누구인지" 401 `access_expired`, 갱신에서 번호 교체(`rt0 → rt1`), 다시 확인 200이고, 브라우저의 쿠키가 `at1·rt1`로 바뀌었다.
4. 포트 A의 페이지가 중계가 갱신해 준 쿠키(`at1`)로 200을 받는다.
5. 다시 만료된 뒤 포트 A의 페이지가 `rt1`로 직접 갱신한다(200).
6. 다른 포트의 요청이 포트 A가 갱신한 쿠키(`at2`)로 200을 받는다.

로그인이 끊긴 갈래는 없었다. 요청이 하나씩 차례로 가는 흐름이다. 동시에 가는 경우는 4다.

### 4. 동시에 여러 요청이 갱신을 일으킬 때

만료 직후 페이지가 요청 넷을 동시에 보냈다(쟀다. 값은 `expected.json`의 회차 이름 "4. …" 아래). 따로 적지 않은 줄은 포트 B의 페이지이고 중계가 httpx로 부른다.

| 설계 | 유예 | 대역에 닿은 갱신 | 대역의 판정(닿은 차례) | 그 뒤 |
|---|---|---|---|---|
| 1 | 0 | 4개, 모두 `rt0` | 교체, 재사용이라 끊음, 끊긴 로그인 둘 | 로그인이 끊겼다. 페이지는 200 하나와 401 셋을 받았고 다음 요청이 401이다 |
| 1 | chain, 차례를 건드리지 않음 | 4개, 모두 `rt0` | 교체, 유예 셋 | 살아 있다. 브라우저에 남은 번호가 서버의 마지막 번호(`rt4`)였다 |
| 1 | chain, 응답의 차례를 뒤집음 | 4개, 모두 `rt0` | 교체, 유예 셋 | 그 순간은 넷 다 200. 브라우저에 `rt1`이 남았고(서버의 마지막은 `rt4`) 다음 갱신이 재사용으로 끊겼다 |
| 1 | family, 차례를 건드리지 않음 | 4개, 모두 `rt0` | 교체, 유예 셋 | 살아 있다. 통하는 번호 넷(`rt1`에서 `rt4`)이 남았다 |
| 1 | family, 응답의 차례를 뒤집음 | 4개, 모두 `rt0` | 교체, 유예 셋 | 살아 있다. 브라우저의 `rt1`로 다음 갱신이 됐다 |
| 2 | 0 | 같은 번호를 든 갱신이 없다 | 모두 교체 | 살아 있다. 요청 넷이 401을 받았고 다시 보낸 넷이 200 |
| 2 | chain | 같은 번호를 든 갱신이 없다 | 모두 교체 | 위와 같다 |
| 2 | family | 같은 번호를 든 갱신이 없다 | 모두 교체 | 위와 같다 |
| 2 | 0, 401 하나가 갱신이 끝난 뒤에 닿음 | 2개. `rt0`을 든 것과 `rt1`을 든 것 | 교체, 교체 | 살아 있다. 브라우저에 남은 번호가 서버의 마지막 번호(`rt2`)였다 |
| 2, 포트 C의 `fetch` 길 | 0 | 같은 번호를 든 갱신이 없다 | 모두 교체 | 살아 있다. 요청 넷이 401을 받았고 다시 보낸 넷이 200, 다음 만료 뒤의 요청과 갱신도 됐다 |
| 2, 포트 C의 `node:http` 길 | 0 | 같은 번호를 든 갱신이 없다 | 모두 교체 | 위와 같다 |
| 2, 포트 B의 중계가 httpx2로 부름 | 0 | 같은 번호를 든 갱신이 없다 | 모두 교체 | 위와 같다 |

- 설계 1에서는 탭 하나만으로 동시 갱신이 났다. 요청 넷이 저마다 같은 번호로 갱신을 불렀다(쟀다).
- 유예 0초에서 요청 넷의 로그인을 지킨 것은 설계 2뿐이다(쟀다).
- 설계 2의 화면이 부른 갱신의 수는 회차마다 갈릴 수 있는 값이다. 대역의 화면 스크립트는 진행 중인 갱신만 함께 기다린다. 그래서 401 하나가 갱신이 끝난 뒤에 닿으면 갱신을 한 번 더 부른다. 포트 B의 httpx 회차 셋(유예 0, chain, family)은 `start` 모드 전체 실행 열의 회차 서른에서 늘 하나였고, `dev` 모드 전체 실행 넷 가운데 첫 실행의 family 회차에서 둘이 났다(쟀다. 수는 저장한 출력에서 세어 손으로 봤다. 그 첫 `dev` 실행은 갱신의 수를 `stable`에 두던 그때의 `expected.json`과 달라 1로 끝났다). 포트 C의 두 길과 httpx2의 회차는 `start` 전체 실행 넷과 `dev` 전체 실행 둘에서 늘 하나였고, `dev` 모드로 묶음만 골라 돌린 실행 하나의 httpx2 회차에서 둘이 났다(손으로 봤다). 그 둘째 갱신은 첫 갱신이 낸 새 번호를 들고 갔고 대역이 교체로 받았다. 브라우저가 첫 갱신의 `Set-Cookie`를 저장한 뒤에 화면이 둘째를 부르기 때문이다. 표의 "401 하나가 갱신이 끝난 뒤에 닿음" 줄은 그 경우를 일부러 만든 회차다. 중계가 넷째 요청의 답을 800밀리초 늦춘다. 유예 0초에서도 로그인이 살아 있었다(쟀다).
- 차례를 건드리지 않은 chain 회차는 실행마다 다섯이다. 2026-11-16의 `start` 전체 실행 열에서 측정인 회차 마흔아홉 모두, `Set-Cookie`가 브라우저에 닿은 차례가 대역이 낸 차례(`rt1`에서 `rt4`)와 같았고 로그인이 살아 있었다(쟀다. 닿은 차례는 회차마다 갈릴 수 있는 값이라 `expected.json`에 없고 `results.json`의 `racy`에 있다. 실행마다의 수는 저장한 출력에서 그 줄을 세어 손으로 봤다). 이 PC의 루프백에서 그랬다는 것이고, 실제 네트워크에서 차례가 뒤집히는 빈도는 재지 못했다.
- "응답의 차례를 뒤집음"은 대역이 갱신 응답을 닿은 차례의 거꾸로 늦춰(600, 400, 200, 0밀리초) 만든 것이다. 번호를 바꾸는 일은 닿은 차례대로 바로 하고 응답만 늦춘다. 뒤집힘이 실제로 났다는 것은 브라우저에 남은 번호가 `rt1`이라는 표지로 봤다(쟀다).

탭 둘이 동시에 갱신하는 경우도 쟀다. 한 탭은 포트 A의 페이지가 Agent OS 대역의 갱신 경로를 직접 부르고, 다른 탭은 포트 B의 페이지가 설계 2의 갱신 경로(중계)를 부른다. 둘이 같은 번호를 들고 겹치게, 대역이 갱신 응답을 잡아 둔다.

| 유예 | 대역의 판정(닿은 차례) | 그 뒤 |
|---|---|---|
| 0 | 교체, 재사용이라 끊음 | 로그인이 끊겼다. 먼저 닿은 탭은 200, 다른 탭은 401과 지우는 줄을 받아 브라우저의 쿠키가 지워졌다 |
| chain, 응답을 같은 시간(150밀리초) 잡아 둠 | 교체, 유예 | 살아 있다. 브라우저에 남은 번호가 서버의 마지막 번호(`rt2`)였다(회차마다 갈릴 수 있는 값) |
| chain, 응답의 차례를 뒤집음 | 교체, 유예 | 브라우저에 `rt1`이 남았고 다음 갱신이 재사용으로 끊겼다 |
| family, 같은 시간 잡아 둠 | 교체, 유예 | 살아 있다 |
| family, 응답의 차례를 뒤집음 | 교체, 유예 | 살아 있다 |

- 유예 0초에서는 탭 둘의 동시 갱신이 로그인을 끊었다. 한 탭이 중계 밖(포트 A)이라 중계의 설계와 상관없다(쟀다). 화면 쪽에서 탭 사이에 갱신을 하나로 묶는 길은 재지 않았다. 포트가 다르면 출처가 달라 탭 사이 잠금(Web Locks, BroadcastChannel)을 함께 쓰지 못한다는 것은 어림이다.
- `start` 전체 실행 열의 탭 둘 회차 쉰 개 모두 포트 A의 직접 갱신이 대역에 먼저 닿았다(쟀다. 수는 저장한 출력에서 세어 손으로 봤다). 중계의 갱신이 먼저 닿는 차례는 나지 않아 재지 못했다. 대역의 판정은 닿은 차례만 보므로 결과가 같을 것이라는 것은 어림이다.

### 5. 중계가 Agent OS에 무엇을 내보내는가

브라우저가 중계에 보낸 머리와 Agent OS 대역에 닿은 머리를 맞댔다(쟀다).

| 브라우저의 요청 | 브라우저가 붙인 `Sec-Fetch-Site` | `Cookie`만 전하는 중계 | 머리를 그대로 전하는 중계 |
|---|---|---|---|
| 주소창으로 포트 B의 경로 열기 | `none` | 통과, 200 | 거절, 403 |
| 포트 B의 링크로 포트 C의 문서 열기 | `same-site` | 통과, 200 | 거절, 403 |
| 포트 B 페이지의 `fetch` GET | `same-origin` | (1에서 통과) | 통과, 200 |
| 포트 B 페이지의 `fetch` POST | `same-origin`, `Origin: http://localhost:<B>` | (1에서 통과) | 통과, 200 |

- 중계가 `Cookie`만 전하면 Agent OS 대역에 닿은 요청에 브라우저의 `Sec-Fetch-*`, `Origin`, `Referer`가 없었고 검사를 지났다(쟀다).
- 브라우저의 머리를 그대로 전하면, 주소창 이동과 다른 포트에서 온 링크 이동은 403으로 거절됐다(쟀다). 위젯 관리 화면과 위젯 테스트 페이지를 주소로 여는 요청이 바로 이 둘이다.
- 그대로 전해도 포트 B 페이지의 `fetch`는 지났다. 브라우저가 포트 B 기준으로 붙인 `same-origin`이 Agent OS 대역에는 자기 출처에서 온 것처럼 보인다(쟀다). 대역은 `Origin`의 값을 자기 주소와 견주지 않는다(ADR 0062가 적은 규칙대로다). 중계가 머리를 그대로 전하면 Agent OS의 요청 출처 검사가 다른 출처(포트 B)의 판정을 물려받는다.

### 6. `openapi-fetch`로 부르는 길

위젯 테스트 페이지 서버 대역이 Agent OS 대역을 전역 `fetch`가 아니라 `openapi-fetch` 0.17.0의 클라이언트로 부르는 길(`/oaf/...`)이다. 볼 것 넷 가운데 머리와 요청 출처 검사는 결과 1의 표와 그 아래 항목에, `Set-Cookie` 두 줄과 원래의 `Response`에 닿는 방법은 결과 2에 적었다. 여기는 나머지 둘이다.

호출에 `AbortSignal.timeout(…)`을 넘겼을 때를 쟀다. 대역이 갱신의 답을 1200밀리초 잡아 두게 하고, 중계가 `client.POST("/auth/refresh", { …, signal: AbortSignal.timeout(<제한 시간>) })`으로 불렀다.

| 길 | 제한 시간 5000밀리초 | 제한 시간 300밀리초 |
|---|---|---|
| `openapi-fetch` | 답을 받았다(200) | 던졌다. 이름 `TimeoutError`, 생성자 `DOMException`, 메시지 `The operation was aborted due to timeout`, `code` 23, `cause` 없음 |
| Node `fetch` 직접 | 답을 받았다(200) | 위와 같다 |

- 제한 시간이 걸린 호출은 값을 돌려주지 않고 던졌다. 던져진 것의 모양이 전역 `fetch`를 직접 부른 길과 같았다(쟀다). `openapi-fetch`는 미들웨어가 없으면 `fetch`가 던진 것을 감싸지 않고 그대로 다시 던지고, `{ error, response }`로 돌려주는 것은 서버가 답한 경우다(코드를 읽었다. `dist/index.mjs`).
- 제한 시간에 끊겼다는 것은 오류의 이름 `TimeoutError`로 봤다. 같은 회차에서 그 호출이 대역에 닿았다는 것(대역의 기록)과, 걸린 시간이 제한 시간과 잡아 둔 시간 사이라는 것을 표지로 봤다(쟀다. 걸린 시간은 회차마다 갈릴 수 있는 값이라 `results.json`의 `racy`에 있다. `expected.json`을 받아 적은 실행에서 긴 호출은 1208밀리초와 1196밀리초, 짧은 호출은 311밀리초와 306밀리초에 끝났다. 앞의 값이 `openapi-fetch`, 뒤의 값이 `fetch` 직접이다). 긴 호출이 1200밀리초보다 조금 일찍 끝난 것은 대역의 `asyncio.sleep`이 이 PC의 시계 눈금만큼 일찍 깨기 때문이라는 것은 어림이다. 그래서 표지의 문턱에 여유를 뒀다. 긴 호출은 1150밀리초 이상, 짧은 호출은 280밀리초 이상 1200밀리초 미만을 본다.
- 대역은 끊긴 호출에서도 번호를 이미 바꾼다. 번호는 닿은 순간에 바꾸고 답만 늦추기 때문이다(코드를 읽었다. `agentos_stub.py`). 그러면 새 번호는 브라우저에 닿지 않는다. 갱신에 제한 시간이 걸리면 다음 갱신이 옛 번호 재사용이 된다는 것은 어림이다. 그 뒤의 갱신은 재지 않았다.

클라이언트가 쿠키를 기억하는지도 쟀다.

- 함께 쓰는 `openapi-fetch` 클라이언트가 `Set-Cookie` 두 줄이 든 갱신 응답을 받은 뒤, 쿠키 없이 온 요청을 같은 클라이언트로 전했다. 대역이 받은 그 요청에 `Cookie` 머리가 없었고 401이었다(쟀다).
- 갈래: `Secure` 없는 쿠키(`probe_plain`)가 든 응답을 같은 클라이언트가 받게 한 뒤에도, 쿠키 없이 온 요청에 `Cookie` 머리가 없었다(쟀다). 로그인 쿠키만으로는 "쿠키를 들지 않는다"와 "들고 있지만 `Secure`라 `http://` 상류에 싣지 않았다"가 갈리지 않아 이 갈래를 뒀다.
- 양성 대조는 덤의 httpx와 httpx2다. 같은 대역의 같은 경로에서 그 둘의 기본 통은 `probe_plain=kept-by-client`를 다음 요청에 실었다(쟀다).
- `openapi-fetch`에 쿠키를 드는 자리가 없다는 것은 코드를 읽었다(`dist/index.mjs`는 `Request`를 지어 `fetch`에 넘길 뿐이다). 그 아래 Node의 `fetch`가 쿠키를 저장하지 않았다는 것은 Node v24.19.0에서 잰 결과이고 다른 판은 재지 않았다.

### 덤. 함께 쓰는 클라이언트가 쿠키를 들고 있는가

httpx 0.28.1과 httpx2 2.13.0을 따로 쟀고 아래 넷은 두 클라이언트에서 값이 같았다(쟀다). 통은 클라이언트마다 따로다.

- 갱신 응답을 받은 뒤, 서버가 사는 동안 함께 쓰는 `AsyncClient`의 쿠키 통에 `__Host-aos_at`과 `__Host-aos_rt`가 들어 있었다(`domain=127.0.0.1`, `secure=True`). 두 클라이언트 모두 받은 `Set-Cookie`를 기본으로 클라이언트에 저장한다(쟀다).
- 그 뒤 쿠키 없이 온 요청에는 그 쿠키가 실리지 않았다. 대역이 받은 요청에 `Cookie`가 없었고 401이었다(쟀다).
- 대조: `Secure`가 없는 쿠키(`probe_plain`)를 같은 클라이언트가 받게 하자, 그 뒤 쿠키 없이 온 요청에 `probe_plain=kept-by-client`가 실려 대역에 닿았다(쟀다). 통에 든 쿠키를 다음 요청에 싣는 클라이언트라는 뜻이다.
- 자기 `Cookie` 머리를 든 요청에는 통의 쿠키가 섞이지 않았다. 대역이 받은 쿠키 이름이 그 요청의 둘뿐이었다(쟀다).
- 로그인 쿠키가 실리지 않은 까닭이 `Secure`인데 상류가 `http://`여서라는 것은 어림이다. 대역의 상류는 `http://127.0.0.1`뿐이고 `https://` 상류에서는 재지 않았다. 그 어림이 맞으면 상류가 `https://`일 때 한 운영자의 쿠키가 쿠키 없이 온 다른 요청에 실린다.

쿠키 통을 쓰지 않게 만든 httpx2 클라이언트를 대조로 쟀다.

- httpx2 2.13.0의 `AsyncClient`에는 쿠키 저장을 끄는 인자가 없다. 응답마다 `self.cookies.extract_cookies(response)`를 부르고(`_client.py`의 `_send_single_request`), `cookies` 인자에 `http.cookiejar.CookieJar`를 주면 `Cookies`가 그 통을 그대로 쓴다(`_models.py`의 `Cookies.__init__`. 둘 다 코드를 읽었다). 그 판의 문서는 보지 않았다.
- 그래서 대역은 받는 도메인이 하나도 없는 정책의 통을 준다. `httpx2.AsyncClient(cookies=CookieJar(policy=DefaultCookiePolicy(allowed_domains=[])))`이고 둘 다 표준 라이브러리 `http.cookiejar`의 것이다.
- 그 클라이언트는 `Set-Cookie` 두 줄이 든 갱신 응답을 받은 뒤에도 통이 비어 있었다. `Secure` 없는 쿠키가 든 응답을 받은 뒤에도 비어 있었고, 그 뒤 쿠키 없이 온 요청에 아무 쿠키도 실리지 않았다(쟀다. 같은 회차에서 그 응답들을 실제로 받았다는 것을 표지로 봤다).
- 그 클라이언트로도 자기 `Cookie` 머리를 든 요청은 쿠키 둘이 그대로 Agent OS 대역에 닿았고 갱신이 됐다(쟀다). 통을 막아도 중계가 전하는 `Cookie` 머리는 막히지 않는다.
- 요청마다 클라이언트를 새로 만드는 방법과, 함께 쓰는 클라이언트의 통을 응답 뒤에 비우는 방법은 재지 않았다. 뒤의 것은 동시에 가는 요청 사이에 통이 잠깐 차 있을 수 있다는 것이 어림이다.

## 측정 밖에서 본 것

대역 둘의 uvicorn을 기본값(쉬는 연결을 5초 뒤에 닫는다)으로 돌린 전체 실행 둘 가운데 하나에서, 설계 1의 chain 회차 하나가 측정이 아니었다. 포트 B 페이지의 요청 넷 가운데 둘이 500을 받았다.

- 그 둘은 위젯 관리 서버 대역에 닿지 않았다. 대역의 기록에 그 태그가 없고 대역 둘의 출력도 비어 있었다(쟀다. 그 실행의 `results.json`).
- 500은 Next의 중계가 낸 것으로 본다. Next 16.3.6의 `next/dist/server/lib/router-utils/proxy-request.js`는 상류로 가는 요청이 오류로 끝나면 `Failed to proxy`를 찍고 500 `Internal Server Error`로 답한다(코드를 읽었다). 그 실행은 앱의 출력을 남기지 않아 그 줄을 보지는 못했다. 지금 판은 `results.json`의 `adminOutput`에 남긴다.
- 까닭은 재지 못했다. Next의 중계는 상류와의 연결을 다시 쓰고(대역이 받은 머리가 `connection: keep-alive`다. 쟀다), 그 회차의 요청 넷은 앞 회차의 요청 넷에서 5초쯤 뒤였다. 상류가 쉬는 연결을 닫는 순간과 중계가 그 연결을 다시 쓰는 순간이 겹쳤다는 것은 어림이다.
- 재려는 것이 연결의 수명이 아니라 쿠키와 갱신이라, 프로브는 대역 둘의 `--keep-alive`를 300초로 준다. 그렇게 돈 전체 실행 열둘(`start` 여덟, `dev` 넷)에서는 다시 나지 않았다(쟀다. 기본값으로 돈 앞의 전체 실행 하나에서도 나지 않았으므로, 이것으로 까닭이 가려진 것은 아니다). `--keep-alive 5`를 주면 그때의 조건으로 돈다.

Next 중계 뒤에 uvicorn을 두는 구성이면 실제로도 날 수 있는 일이라 적어 둔다. 실제 구성에서의 빈도는 재지 못했다.

## 해석의 대조와 갈래

결과에서 끌어낸 해석마다, 그 해석이 맞으면 나올 결과가 실제로 나온다는 양성 대조와 다른 해석을 가르는 갈래를 적는다. 둘 가운데 하나가 없는 것은 어림으로 적었다.

- "서버 사이 요청은 요청 출처 검사에 걸리지 않는다."
  - 양성 대조: 대조 회차가 같은 대역이 `Sec-Fetch-Site: same-site`, `cross-site`, `none`, 그리고 `Origin`만 든 요청을 403으로 거절하는 것을 보였다. 검사는 켜져 있다.
  - 갈래: 지난 까닭이 "머리가 없어서"인지 "중계에서 온 요청은 봐주어서"인지. 같은 중계가 브라우저의 머리를 그대로 전하면 403이 났다(5). 머리가 없어서다.
- "`Set-Cookie`는 중계를 지나도 그대로 닿는다."
  - 양성 대조: 줄을 한 값으로 합쳐 옮기는 중계에서는 견줌이 다르다고 나왔고 갱신용 번호 쿠키가 바뀌지 않았다. 견줌이 다름을 잡아낸다.
  - 갈래: 줄이 같아도 브라우저가 저장하지 않았을 수 있다. 저장소의 값이 `at0·rt0`에서 `at1·rt1`로 바뀐 것을 표지로 봤고, CDP가 거절한 줄이 없다고 했다.
- "설계 1은 유예 0초에서 로그인을 끊고 설계 2는 지킨다."
  - 양성 대조: 대조 회차가 옛 번호 재사용이 끊는다는 것을 먼저 보였다.
  - 갈래: 설계 2에서 같은 번호를 든 갱신이 없는 까닭이 "요청이 동시에 가지 않아서"일 수 있다. 요청 넷이 모두 401을 받았다는 것(페이지가 센 수)과 대역의 기록에 401 `access_expired`가 넷이라는 것을 표지로 봤다. 설계 1에서는 같은 번호를 든 갱신이 넷 닿았다.
  - 갈래: 설계 2가 지키는 까닭이 "갱신이 하나라서"만은 아니다. 401 하나가 갱신이 끝난 뒤에 닿아 갱신이 둘이 된 회차에서도, 둘째가 새 번호를 들고 가 유예 0초에서 살아 있었다.
  - 잰 것은 대역의 화면 스크립트(진행 중인 갱신을 함께 기다리는 것)다. 실제 화면의 코드가 다르게 지어지면 다시 재야 한다. 화면이 갱신의 응답을 받기 전에 둘째 갱신을 부르는 꼴이면 같은 번호를 든 갱신이 둘이 된다(어림).
- "chain 뜻의 유예는 응답의 차례가 뒤집히면 다음 갱신에서 로그인을 끊는다."
  - 양성 대조: 뒤집음 회차에서 브라우저에 남은 번호가 `rt1`이고 다음 갱신이 `reuse_revoked`였다.
  - 갈래: 끊긴 까닭이 뒤집힘 자체인지 chain이 앞서 낸 번호를 옛 번호로 돌린 것인지. 같은 뒤집음에서 family는 살아 있었다. 그리고 차례를 건드리지 않은 chain 회차는 살아 있었다. 둘이 함께 있어야 끊긴다.
  - 뒤집힘은 대역이 만든 것이다. 실제로 얼마나 나는지는 재지 못했다.
- "httpx와 httpx2의 쿠키 통에 든 로그인 쿠키는 다른 요청에 실리지 않았다."
  - 양성 대조: `Secure` 없는 쿠키는 실렸다. 통이 다음 요청에 쿠키를 싣는다.
  - 갈래가 없다. `https://` 상류를 재지 않아, 실리지 않은 까닭이 `Secure`와 `http://`의 조합이라는 것은 어림이다.
- "받는 도메인이 없는 정책의 통을 준 httpx2 클라이언트는 쿠키를 들지도 싣지도 않는다."
  - 양성 대조: 같은 응답들을 받은 기본 통의 httpx2 클라이언트는 쿠키 셋을 들었고 `Secure` 없는 쿠키를 다음 요청에 실었다.
  - 갈래: 통이 빈 까닭이 "응답이 오지 않아서"일 수 있다. 그 회차에서 갱신 응답의 `Set-Cookie` 두 줄과 `Secure` 없는 쿠키의 줄을 그 클라이언트가 받았다는 것을 중계의 호출 기록으로 봤다.
  - 잰 것은 `http://127.0.0.1` 상류와 이 정책 하나다. 다른 방법으로 통을 끄는 것은 재지 않았다.
- "`openapi-fetch`의 클라이언트는 받은 쿠키를 다음 요청에 싣지 않는다."
  - 양성 대조: 같은 대역의 같은 경로에서 httpx와 httpx2의 기본 통은 `Secure` 없는 쿠키를 다음 요청에 실었다(덤). 이 걸음은 쿠키가 실리는 것을 잡아낸다.
  - 갈래: 실리지 않은 까닭이 "응답을 받지 않아서"일 수 있다. 그 회차에서 갱신 응답의 `Set-Cookie` 두 줄과 `Secure` 없는 쿠키의 줄을 그 클라이언트가 받았다는 것을 중계의 호출 기록으로 봤다.
  - 갈래: 까닭이 "`Secure`라 `http://` 상류에 싣지 않아서"일 수 있다. `Secure` 없는 쿠키도 실리지 않았다.
- "`AbortSignal.timeout`을 넘긴 `openapi-fetch` 호출은 제한 시간에 `TimeoutError`를 던진다."
  - 양성 대조: 같은 회차에서 제한 시간 5000밀리초의 호출은 대역이 잡아 둔 1200밀리초 뒤에 답을 받았다. 대역이 답을 늦추고 있었고 연결은 됐다.
  - 갈래: 던져진 까닭이 제한 시간이 아니라 연결 실패일 수 있다. 끊긴 호출이 대역의 기록에 있었고, 이름이 `TimeoutError`였고, 걸린 시간이 제한 시간보다 길고 잡아 둔 시간보다 짧았다.
  - 갈래: 던져진 것을 `openapi-fetch`가 바꿨을 수 있다. 전역 `fetch`를 직접 부른 길과 모양을 견줬고 같았다.
  - 잰 것은 답의 머리가 오기 전에 걸리는 제한 시간이다. 머리는 왔고 몸을 읽는 중에 걸리는 경우는 재지 않았다.

## 재지 못한 것

- 실제 Agent OS의 로그인 경로, 실제 위젯 관리 서버, 실제 위젯 테스트 페이지 서버. 셋 다 아직 없어 대역으로 쟀다. 대역이 고른 것(위 절)이 실제와 다르면 그 자리는 다시 재야 한다. 특히 유예의 뜻, 거절 때 지우는 줄을 싣는지, 쿠키 줄을 짓는 코드(대역은 Starlette), 요청 출처 검사가 보는 머리.
- 유예의 셋째 뜻(유예 안의 옛 번호에 같은 후속 번호를 다시 내준다). 응답의 차례가 뒤집혀도 버티면서 통하는 번호가 하나로 남을 것이라는 것은 어림이다.
- 실제 네트워크에서 응답의 차례가 뒤집히는 빈도. 이 PC의 루프백에서 건드리지 않은 회차는 뒤집히지 않았다.
- 포트 C(Node 대역)와 httpx2에서의 동시 갱신 가운데 설계 2의 유예 0 밖의 것. 포트 C의 두 길(`fetch`, `node:http`)과 httpx2는 설계 2의 유예 0 회차 하나씩만 쟀다. 설계 1, 유예 chain과 family, 늦은 401을 일부러 만드는 회차, 탭 둘은 포트 B의 httpx에서만 쟀다. 포트 C의 문서 요청은 하나씩 가는 흐름(3)만 쟀다.
- 탭 둘에서 중계의 갱신이 먼저 닿는 차례, 탭 셋 이상, 창을 여럿 띄운 경우.
- Chromium 밖의 브라우저(Firefox, Safari). `Sec-Fetch-Site`를 붙이는 방식과 `__Host-` 쿠키를 `http://localhost`에서 받는 방식이 다를 수 있다.
- `https://`와 TLS, nginx 같은 앞단. 브라우저가 `http://localhost`를 안전한 출처로 다뤄 `Secure`와 `__Host-` 쿠키를 받은 것이고, 실제 호스트 이름에서는 `https://`가 있어야 한다. `localhost`가 아닌 호스트 이름과 포트가 다른 두 출처도 재지 않았다.
- `https://` 상류에서 httpx와 httpx2의 쿠키 통이 `Secure` 쿠키를 다른 요청에 싣는지(덤).
- httpx와 httpx2 밖의 파이썬 HTTP 클라이언트. httpx2로는 결과 1, 결과 2, 결과 4의 설계 2(유예 0), 덤만 쟀고, 흐름 전체(3)와 머리를 그대로 전하는 대조(5)는 httpx로만 쟀다.
- 요청마다 새로 만드는 클라이언트, 응답 뒤에 통을 비우는 클라이언트, 쿠키 통을 끈 httpx(0.28.1) 클라이언트. 쿠키를 받지 않는 통은 httpx2에서만 쟀다.
- `openapi-fetch`의 길에서의 흐름 전체(3), 동시 갱신(4), 머리를 그대로 전하는 대조(5). 이 길로는 결과 1, 결과 2, 결과 6만 쟀다. 안에서 전역 `fetch`를 부르므로 `fetch` 길과 같을 것이라는 것은 어림이다.
- `openapi-fetch`에 미들웨어를 단 클라이언트, 몸이 있는 호출, 다른 곳으로 돌려보내는 답(기본이 `redirect: "follow"`다), 몸을 읽는 중에 걸리는 제한 시간, `openapi.json`에서 만든 타입을 준 클라이언트. 프로브는 `openapi-fetch`의 `createClient({ baseUrl })`를 바로 불러 타입 없는 클라이언트에 경로 문자열을 줬다. 타입이 실행 때의 동작을 바꾸지 않는다는 것은 어림이다. `web/packages/api-client`가 클라이언트를 짓는 함수들은 `createClient<…>({ baseUrl, headers })`를 부르고 미들웨어를 달지 않는다(코드를 읽었다. `src/clients.ts`). 그 함수들을 거친 호출은 재지 않았다.
- 갱신이 제한 시간에 끊긴 뒤의 흐름(6). Node v24.19.0 밖의 Node에서 `fetch`가 쿠키를 저장하는지.
- 머리 이름의 대소문자. uvicorn이 이름을 소문자로 주어 Agent OS 대역에서는 볼 수 없었다.
- Next 중계가 낸 500의 까닭(측정 밖에서 본 것).
- 로그아웃, 계정이 '쓰지 않음'이 된 뒤의 흐름, 쿠키가 하나만 온 경우. 대역에 경로는 있으나 중계를 거쳐 재지 않았다.
