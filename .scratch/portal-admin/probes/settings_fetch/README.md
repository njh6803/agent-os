# portal-admin settings_fetch 프로브

위젯 테스트 페이지의 서버(`web/apps/portal`, `node:http`)는 지금 뜰 때 설정 파일에서 사이트 목록을 읽어 메모리에 둔다. 위젯 관리 화면(`portal-admin`)이 생기면 그 목록의 원천이 위젯 관리 서버(FastAPI 와 자기 PostgreSQL)로 옮겨 가고, 운영자가 저장하면 아무것도 다시 띄우지 않고 바로 반영되어야 한다. 그래서 명세가 "요청 때마다 위젯 관리 서버에 묻는다"와 "짧게 기억한다(캐시)" 가운데 하나를 골라야 하고(ADR 0064 Consequences 의 "재지 않은 것"), 이 프로브는 그때 쓸 사실을 잰다. 요청마다 묻는 것이 페이지 응답에 더하는 시간, 2초 기억과의 차이, 위젯 관리 서버가 내려가 있거나 느리거나 답하지 않을 때의 동작이다. 여기서는 결정하지 않고 본 것만 적는다. 규약은 `docs/agents/issue-tracker.md` 의 "프로브와 근거"다.

위젯 관리 서버는 아직 없어 셋 다 대역이다. 위젯 관리 서버 대역과 "지금 누구인지" 대역은 FastAPI 앱 하나의 두 경로이고(`admin_stub.py`), 위젯 테스트 페이지 서버 대역은 의존성 없는 `node:http` 서버다(`portal_stub.mjs`).

결과는 2026-11-16 에 `run.py --hang` 을 두 번 돌린 것이다. 실행 `792ec2`(18:14~18:24, 541초)와 실행 `3467e1`(18:24~18:39, 855초)이고 둘 다 측정 99 회차, 측정 아님 0 회차, 종료 코드 0 이다. 실행 하나는 같은 측정을 60초씩 쉬어 가며 세 번 되풀이한다. 실행 `792ec2` 는 호스트 CPU 부하가 낮던 때(되풀이를 시작할 때 11%, 28%, 77%), 실행 `3467e1` 은 높던 때(100%, 100%, 62%)다. `fetch_idle_timer.mjs` 는 같은 날 윈도 호스트에서 세 번, 리눅스 컨테이너에서 두 번 돌렸다.

**범위.** 모두 PC 한 대의 루프백(`127.0.0.1`)에서 쟀다. PostgreSQL 만 Docker Desktop 의 컨테이너이고 대역 셋과 요청을 보내는 쪽은 윈도 호스트의 프로세스다. 배포(컨테이너 사이의 네트워크)에서는 재지 못했다. 아래 시간은 이 PC 의 값이고, 그 가운데 큰 몫 둘(호스트에서 컨테이너의 PostgreSQL 로 가는 길, 이 PC 의 Node 가 이어 쓰는 연결에서 기다리는 타이머)은 배포에서 같다고 볼 근거가 없다.

근거의 종류는 넷이다. 프로브가 다시 낸다(`run.py` 나 `fetch_idle_timer.mjs` 가 표지를 보고 낸 값), 손으로 봤다(명령과 함께 적는다), 코드를 읽었다(파일과 줄), 어림.

## 요약

명세가 고를 때 쓸 한 줄씩이다. 수치와 갈래는 결과 절에 있다. 따로 적지 않은 줄은 프로브가 다시 낸다.

1. 요청마다 사이트 목록을 한 번 묻는 것이 페이지 응답에 더한 시간은, `node:http` 로 연결을 이어 쓸 때 부하가 낮던 되풀이 넷(되풀이를 시작할 때 호스트 CPU 부하 11%, 28%, 77%, 62%)에서 중앙값 3.3~4.8ms, p95 4.9~13.5ms 였다(부르지 않는 기준 갈래는 중앙값 0.3~0.5ms). 부하가 100% 이던 되풀이 둘에서는 중앙값 21~39ms, p95 62~94ms 였다.
2. 그 시간의 대부분은 대역이 PostgreSQL 을 조회한 시간이다(부하가 낮을 때 3.2~4.7ms 가운데 2.1~3.0ms, 부하 100% 일 때 39ms 가운데 37ms). 같은 세 문장을 컨테이너 안에서 `pgbench` 로 돌리면 부하와 무관하게 중앙값 0.43~0.70ms 였다. 차이가 호스트에서 컨테이너로 가는 길의 몫인지 파이썬 드라이버의 몫인지는 가르지 못했다.
3. 같은 호출을 전역 `fetch` 로 하면 이 PC 에서는 중앙값이 8.7~16.3ms 더해졌다(부하가 낮던 되풀이 넷). `node:http` 보다 5~12ms 크다. 이 PC 의 Node 24.19.0 에 든 undici 7.29.0 이 쉬던 연결에 요청을 쓰기 전에 `setTimeout(…, 0)` 하나를 기다리고, 윈도에서 그 타이머가 15.6ms 뒤에 불리기 때문이다. 리눅스 컨테이너의 Node 24.22.3(undici 7.30.2)에서는 같은 자리가 `setImmediate` 이고 `fetch` 와 `node:http` 의 중앙값 차가 0.2~0.3ms 였다(`fetch_idle_timer.mjs`).
4. "지금 누구인지"까지 부르면, 차례로 부를 때 중앙값 26.3~27.2ms, 함께 부를 때 15.7~15.9ms 가 더해졌다(부하가 낮던 되풀이 넷, `fetch`. 3 의 타이머가 든 값이고, 같은 되풀이에서 한 번 부른 값은 8.7~16.3ms 였다). `node:http` 로는 둘을 부르는 갈래를 두지 않았다.
5. 요청마다 새 연결을 맺어도 이어 쓸 때보다 중앙값이 0.5~0.8ms 느릴 뿐이었다(`node:http`, 부하가 낮던 되풀이 넷). 6초 쉰 뒤(대역이 쉬는 연결을 닫은 뒤)의 첫 요청도 새 연결로 답을 받았고 실패는 없었다(방법마다 서른 번).
6. 2초 기억을 두면 맞은 요청은 다른 서버를 부르지 않아 중앙값 0.64~1.02ms 였고, 빗나간 요청은 한 번 묻는 값을 그대로 치렀다. 50ms 마다 하나씩 300 번 보내면 10 번 빗나갔다. 요청이 2초에 한 번보다 드물면 모두 빗나간다(어림. 페이지가 받는 요청의 빈도는 재지 않았다).
7. 대역이 내려가 있으면 페이지 대역은 `ECONNREFUSED` 를 받아 중앙값 0.6~2.2ms(최댓값 18ms. 순차)에 502 를 냈다. 루프백의 닫힌 포트에서 본 것이고, 패킷이 버려지는 경우와 이름이 풀리지 않는 경우는 재지 않았다.
8. 대역이 3초 느리면 제한 시간이 없을 때 페이지 응답도 3.01~3.05초가 걸렸고(200), 호출에 1초 제한(`AbortSignal.timeout`)을 걸면 1.005~1.023초에 `TimeoutError` 로 끊겨 502 를 냈다. 끊긴 요청도 대역은 끝까지 처리했다.
9. 대역이 연결만 받고 답하지 않으면, 제한 시간이 없는 `fetch` 는 304~307초 뒤에 `HeadersTimeoutError` 로 끝났고 `node:http` 는 330초까지 오류 없이 기다리고 있었다(요청을 보낸 쪽이 그때 끊었다).
10. 살아 있는 대역을 부른 요청 36,120 개(호출 48,120 번. 몸풀기 요청은 빼고 센 것이다)에서 실패는 없었고, 페이지 응답의 최댓값은 부하가 낮던 실행에서 121ms(호출 하나), 191ms(호출 둘), 부하가 높던 실행에서 411ms(호출 하나), 395ms(호출 둘)였다.
11. 지금의 처리기는 동기 함수다. 요청마다 다른 서버를 부르려면 처리기와 그것을 거는 겉이 비동기가 되어야 한다(코드를 읽었다, 아래 "지금의 서버 코드").

## 다시 돌리기

저장소 루트에서 친다. 저장소의 `pyproject.toml` 과 `uv.lock` 은 고치지 않는다. PostgreSQL 드라이버는 `uv run --with` 로 그 실행에만 얹는다.

```sh
uv run --with "psycopg[binary,pool]" python .scratch/portal-admin/probes/settings_fetch/run.py --hang
```

짧게 돌려 보려면(1~2분, 수치는 쓰지 않고 표지만 본다):

```sh
uv run --with "psycopg[binary,pool]" python .scratch/portal-admin/probes/settings_fetch/run.py --passes 1 --count 20 --warmup 5 --chunk 10 --cache-count 60 --idle-count 2 --slow-count 1 --down-count 2
```

`fetch` 의 타이머만 볼 때(호스트, 그리고 리눅스 컨테이너. 둘째 줄의 `<프로브 폴더>` 는 이 폴더의 절대 경로다):

```sh
node .scratch/portal-admin/probes/settings_fetch/fetch_idle_timer.mjs
docker run --rm --network none -v <프로브 폴더>:/probe:ro node:24-trixie-slim node /probe/fetch_idle_timer.mjs
```

- 필요한 것: 도는 Docker 데몬(리눅스 엔진)과 이미지 `postgres:18-alpine`(없으면 `run.py` 가 받지 않고 멈춘다. 먼저 `docker pull postgres:18-alpine`), PATH 의 `node`(24 에서만 돌려 봤다)와 `docker`, `uv`, 그리고 psycopg 를 처음 받을 때의 네트워크(PyPI). FastAPI 와 uvicorn 은 저장소 잠금의 것을 쓴다. 윈도에서는 프로세스의 명령줄과 CPU 부하를 읽으려고 `powershell` 을 부른다. 컨테이너 줄에는 이미지 `node:24-trixie-slim` 이 있어야 한다. LLM 은 부르지 않는다.
- 하는 일: PostgreSQL 컨테이너 하나(이름 `portal-admin-settings-fetch-<실행 표지>`)를 호스트의 `127.0.0.1` 임의 포트로 띄우고 표 셋(사이트 10 줄, 계정 20 줄, 회차 표지 1 줄)을 채운다. 대역 둘과 요청을 보내는 쪽을 `127.0.0.1` 의 임의 포트에 띄운다. 끝에서 대역은 명령줄에 실행 표지가 있을 때만 끄고(pid 만 보고 끄지 않는다), 컨테이너는 그 이름으로만 익명 볼륨과 함께 지운다. 데이터베이스 비밀번호는 실행마다 무작위로 만든 프로브용 값이고 명령줄에 싣지 않는다(환경 변수로 넘긴다). `--hang` 이 띄우는 요청 둘은 330초 뒤에 스스로 끝난다. `run.py` 가 강제로 죽으면(정리 단계를 돌지 못하면) 대역 프로세스와 컨테이너가 남는다. 다음 실행은 같은 접두의 남은 컨테이너를 알리기만 하고 지우지 않으므로 그 이름으로 손으로 지운다.
- 원본 기록: `--work <폴더>`(없으면 시스템 임시 폴더) 아래에 요청마다의 기록(`records-*.jsonl`), 계획(`plan-*.json`), 대역의 로그, `summary.json` 이 남는다. 저장소에는 두지 않는다.
- 걸리는 시간: 기본값(되풀이 3, 갈래마다 500 요청, 되풀이 사이 60초)으로 부하가 낮을 때 541초, 높을 때 855초였다(프로브가 찍은 값). `--hang` 은 330초를 기다리지만 되풀이와 겹쳐 돌아 기본값에서는 시간을 더하지 않는다. 되풀이를 줄이면 `--hang` 이 330초를 채운다.
- 고르는 값: `--passes`(되풀이 수, 기본 3), `--gap-seconds`(60), `--count`(500), `--concurrency`(10), `--chunk`(50), `--warmup`(30), `--cache-count`(300), `--cache-gap-ms`(50), `--idle-count`(5), `--slow-count`(3), `--down-count`(10), `--hang`. 측정이 아닌 회차가 하나라도 있으면 종료 코드가 1 이다.
- 위 줄들을 돌려 본 모양(손으로 봤다, 2026-11-16). 둘째 줄(짧은 실행)과 셋째 줄(호스트의 타이머 프로브)은 저장소 루트에서 글자 그대로 쳤다. 짧은 실행은 측정 33 회차, 측정 아님 0 회차, 종료 코드 0 이었고 96초가 걸렸다(호스트 CPU 부하 100%. 부하가 36~48% 이던 앞선 실행은 55초였다). 첫 줄은 스크립트를 절대 경로로 주고 `--work <폴더>` 를 붙여 돌렸다(결과의 두 실행). 넷째 줄은 PowerShell 에서 `<프로브 폴더>` 에 절대 경로를 넣어 쳤다. Git Bash 에서는 `/probe` 가 윈도 경로로 바뀔 수 있어 쳐 보지 않았다.
- 린트: `uv run ruff check .scratch/portal-admin/probes/settings_fetch`, `uv run ruff format --check .scratch/portal-admin/probes/settings_fetch`.

## 무엇을 어떻게 쟀나

- **대역의 모양.** 위젯 관리 서버 대역은 요청마다 연결 묶음(가장 적게 4, 많게 10)에서 연결을 빌려 사이트 10 줄을 `SELECT` 하고 JSON 으로 답한다. 연결은 psycopg 의 기본값(autocommit 끔)이라 요청 하나가 `BEGIN`, `SELECT`, `COMMIT` 을 보낸다. 경로 함수는 `def` 이고 FastAPI 가 스레드 풀에서 돌린다. "지금 누구인지" 대역은 쿠키 값을 해시해 20 줄짜리 표에서 계정 하나를 찾는다. **고른 드라이버 하나로 잰 것이다.** 이 저장소의 데이터베이스 도구는 아직 정해지지 않았고, 비동기 드라이버나 autocommit 을 켠 연결로는 재지 않았다.
- **갈래.** 페이지 대역은 요청의 질의가 고른 대로 움직인다. 다른 서버를 부르지 않는다(`none`, 지금의 모양), 사이트 목록을 묻는다(`sites-*`), 사이트 목록 다음에 "지금 누구인지"를 차례로 묻는다(`both-seq-fetch`), 둘을 함께 묻는다(`both-par-fetch`). 부르는 방법은 전역 `fetch` 와 `node:http` 둘이고, 연결은 이어 쓰는 것과 요청마다 새로 맺는 것(`sites-newconn-*`) 둘이다.
- **번갈아 잰다.** 순차 단계(`seq`)는 요청 하나마다 갈래를 바꾸고 시작 갈래도 돌려 가며 갈래마다 500 번 보낸다. 동시 단계(`conc10`)는 갈래마다 50 개씩 묶어 번갈아 동시 10 으로 500 번 보낸다. 재기 전에 갈래마다 30 번을 먼저 보내고 통계에서 뺀다.
- **시간.** 요청을 보낸 쪽이 요청을 쓰기 시작한 때부터 답의 본문을 다 읽은 때까지다. 보내는 쪽과 페이지 대역 사이의 연결은 이어 쓴다. p95 와 p99 는 가까운 순위법이고(p95 는 정렬한 n 개 가운데 ceil(0.95n) 번째), 중앙값은 n 이 짝수면 가운데 두 값의 평균이다. "기준과의 차"는 같은 되풀이 같은 단계의 `none` 갈래와의 중앙값(또는 p95)의 차다.
- **표지.** 회차는 (되풀이, 단계, 갈래) 하나이고, 재려는 상황이 그 회차에 났다는 표지를 본 뒤에만 측정으로 센다. 요청마다 물었다는 표지는 답마다 대역이 돌려준 일련번호가 서로 다르고 그 수가 요청 수와 같다는 것, 데이터베이스를 조회했다는 표지는 답에 든 줄 수가 10 이고 답에 든 값(nonce)이 그 되풀이 직전에 데이터베이스에 써 둔 값과 같다는 것이다. 되풀이마다 대역이 센 요청 수가 페이지 대역이 적은 호출 수와 같고(사이트 목록 6,380, "지금 누구인지" 2,120), 끝에 PostgreSQL 통계의 표 훑기 수가 대역이 끝낸 조회의 수와 같았다(사이트 표 20,682, 계정 표 6,360. 두 실행 모두). 나머지 표지는 `run.py` 의 독스트링에 있다.

### fetch 와 node:http 의 차이

순차 단계에서 이어 쓰는 `fetch` 갈래는 새 연결을 맺는 `fetch` 갈래보다 느렸다(`sites-fetch` 8.9~16.4ms, `sites-newconn-fetch` 4.5~6.0ms. 실행 `792ec2`). 까닭을 `fetch_idle_timer.mjs` 로 갈랐다. 작은 `node:http` 서버(데이터베이스 없음)에 네 갈래를 요청 하나마다 번갈아 200 번씩 보내고, 따로 띄운 프로세스에서 `fetch` 호출과 소켓 쓰기 사이에 걸리는 타이머를 스택과 함께 적는다. 표지는 이어 쓰는 갈래에서 서버가 본 상대 포트가 한 가지인 것, 새 연결 갈래에서 서버가 요청마다 `Connection: close` 를 본 것, 추적한 요청마다 소켓 쓰기를 한 번 본 것이다. 다섯 번 모두 어긋난 표지가 없었다(출력의 `problems` 가 비었다). 아래는 마지막 판을 처음 돌린 값이고 괄호는 그 앞 판의 실행이다(앞 판은 추적이 `setImmediate` 를 적지 않았을 뿐 재는 부분은 같다). 호스트에서 마지막 판을 한 번 더 돌린 값은 `fetch` 이어 쓰기 9.60 / 14.28, `node:http` 이어 쓰기 0.68 / 0.97, `setTimeout` 15.72 / 24.18 이었고 추적은 같았다. 모두 프로브가 다시 낸다.

- 이 PC 의 Node 는 쉬던 연결에 요청을 쓰기 전에 0ms 타이머 하나를 기다리고, 윈도에서 그 타이머는 시스템 시계의 다음 틱(15.6ms 간격)에 불린다. 그래서 이어 쓰는 `fetch` 호출마다 0~15.6ms 가 붙는다. 20ms 를 쉰 뒤에 보낸 요청은 한 틱을 다 기다렸고(추적의 타이머 기다림 중앙값 15.0~15.3ms), 쉬지 않고 잇달아 보낸 요청은 그보다 적게 기다렸다(세 실행의 중앙값 9.6, 11.1, 13.3ms).
- `run.py` 의 값과 맞는다. 순차 단계 `sites-fetch` 의 왕복 칸은 p95 가 여섯 되풀이 모두 17.5~18.4ms 였고(한 틱 15.6ms 에 `node:http` 의 왕복을 더한 값 언저리다), 50ms 마다 보낸 기억 단계의 빗나간 요청은 왕복이 16.6~17.6ms 였다. 순차 단계의 중앙값이 되풀이에 따라 8.9ms 와 16.4ms 로 갈린 까닭(틱과 요청이 맞물리는 자리로 본다)은 가르지 않았다. 어림이다.
- 판과 플랫폼을 따로 바꿔 보지는 못했다. 본 것은 두 조합뿐이다(윈도 + undici 7.29.0, 리눅스 + undici 7.30.2). 윈도의 undici 7.30.2 에서 기다림이 없는지, 리눅스의 undici 7.29.0 에서 기다림이 1ms 쯤인지는 어림이다. 로컬에 있는 `node:24` 이미지 셋(`trixie-slim`, `bookworm-slim`, `alpine`)이 모두 24.22.3 이었고 새 이미지나 Node 를 받지 않았다(손으로 봤다, 이미지마다 `docker run --rm <이미지> node -p "process.versions.node + ' undici ' + process.versions.undici"`).
- 윈도의 틱 간격은 다른 프로그램이 시계 해상도를 올리면 짧아진다. 잰 때의 값은 위 표의 `setTimeout` 줄이다.
- 저장소의 `web/` 은 Node `>=24 <25` 를 받는다(코드를 읽었다, `web/package.json` 6~7 줄). 두 판 모두 그 범위 안이라, 이 기다림이 있는지는 띄우는 Node 의 작은 판에 달렸다.

### 2초 기억과의 차이

`sites-fetch` 에 2초 기억을 둔 갈래를 50ms 마다 하나씩 300 번 보냈다(15초). 맞은 요청의 표지는 다른 서버를 부르지 않았고 그 값의 일련번호가 앞서 빗나간 요청의 것이라는 것, 빗나간 요청의 표지는 새 일련번호를 받았다는 것이다. 되풀이마다 290 번 맞고 10 번 빗나갔다.

| 갈래 | n | 중앙값 `792ec2` | 최댓값 `792ec2` | 중앙값 `3467e1` | 최댓값 `3467e1` |
|---|---|---|---|---|---|
| 맞음(`cache2s-hit-fetch`) | 290 | 0.64 / 0.74 / 0.73 | 1.27 / 2.55 / 1.45 | 1.02 / 0.84 / 0.79 | 22.38 / 1.95 / 1.28 |
| 빗나감(`cache2s-miss-fetch`) | 10 | 19.93 / 20.71 / 20.85 | 22.67 / 22.63 / 30.34 | 79.99 / 48.67 / 21.60 | 114.35 / 60.91 / 26.62 |

- 맞은 요청은 같은 되풀이의 순차 단계 `none` 갈래(0.28~0.61ms)보다 0.3~0.4ms 느렸다. 기준 갈래를 같은 간격(50ms)으로 재지 않아, 그 차가 기억을 찾는 값인지 쉬었다 보내는 값인지는 가르지 못했다.
- 빗나간 요청이 순차 단계의 `sites-fetch` 보다 느린 것은 위 타이머 때문이다(50ms 를 쉰 뒤라 한 틱을 다 기다린다). `node:http` 로 기억을 두는 갈래는 재지 않았다.
- 기억이 맞는 비율은 요청의 빈도에 달렸다. 초당 20 번이면 300 가운데 290 이 맞았고, 2초에 한 번보다 드물면 모두 빗나간다(어림. 위젯 테스트 페이지가 실제로 받는 요청의 빈도는 재지 않았다). 기억을 두면 운영자가 저장한 값이 길게는 그 시간만큼 늦게 보인다(프로브의 기억은 시간이 지나야만 버린다. 저장할 때 버리게 하는 길은 재지 않았다).

### 쉰 뒤의 첫 요청

6초를 쉰 뒤에 하나씩 다섯 번 보냈다. uvicorn 은 쉬는 연결을 5초 뒤에 닫는다(코드를 읽었다, uvicorn 0.53.0 의 `uvicorn/config.py` 234 줄 `timeout_keep_alive: int = 5`. 프로브는 그 값을 바꾸지 않았다). 표지는 대역이 본 상대 포트가 요청마다 다르다는 것(새 연결)이고, 방법마다 서른 번(되풀이 여섯 × 다섯) 모두 그랬다.

| 갈래 | n | 중앙값 `792ec2` | 최댓값 `792ec2` | 중앙값 `3467e1` | 최댓값 `3467e1` |
|---|---|---|---|---|---|
| `none-idle6s` | 5 | 0.29 / 0.36 / 0.38 | 0.42 / 0.61 / 0.38 | 0.58 / 0.50 / 0.54 | 0.82 / 0.55 / 0.56 |
| `sites-idle6s-fetch` | 5 | 5.14 / 5.86 / 6.04 | 5.35 / 8.06 / 14.19 | 71.33 / 22.71 / 9.23 | 241.16 / 43.90 / 10.06 |
| `sites-idle6s-http` | 5 | 4.19 / 5.76 / 5.64 | 5.17 / 8.84 / 13.91 | 87.28 / 19.11 / 8.48 | 183.48 / 32.06 / 12.76 |

두 방법 모두 닫힌 연결을 알아채고 새 연결로 답을 받았고 오류는 없었다. 값은 새 연결 갈래와 비슷했다. 대역이 연결을 닫는 바로 그 순간(5초 언저리)에 보낸 요청은 재지 않았다. 프로브의 첫 판에서 `node:http` 의 이어 쓰는 Agent 가 6초 쉰 소켓을 다시 쓰다 `ECONNRESET` 을 받은 일이 있었는데, 요청을 보내는 쪽과 페이지 대역(Node 의 HTTP 서버) 사이의 연결이었다(손으로 봤다, 첫 연기 실행의 원본 기록. 그 뒤 보내는 쪽이 쉰 다음 새 연결로 먼저 한 번 보내게 고쳤다).

### 대역이 느릴 때

대역이 조회 앞에 데이터베이스에서 3초를 잔다(`pg_sleep`). 갈래마다 세 번씩 보냈다. 느렸다는 표지는 대역이 적은 조회 시간이 3,000ms 이상이라는 것이고(가장 작은 값 3,005.5ms), 제한 시간이 걸렸다는 표지는 오류의 이름이다.

| 갈래 | 페이지 응답 | 중앙값 `792ec2` | 최댓값 `792ec2` | 중앙값 `3467e1` | 최댓값 `3467e1` |
|---|---|---|---|---|---|
| 제한 없음, `fetch` | 200 | 3011.24 / 3010.04 / 3018.58 | 3030.16 / 3016.21 / 3042.57 | 3036.06 / 3047.83 / 3011.71 | 3097.01 / 3068.14 / 3032.39 |
| 제한 없음, `node:http` | 200 | 3011.17 / 3009.15 / 3016.44 | 3066.93 / 3010.59 / 3021.83 | 3050.53 / 3040.26 / 3010.98 | 3074.73 / 3055.84 / 3012.34 |
| 1초 제한, `fetch` | 502. `TimeoutError`(코드 23) | 1010.39 / 1004.97 / 1014.08 | 1013.86 / 1013.81 / 1020.57 | 1023.06 / 1018.26 / 1012.05 | 1023.26 / 1024.50 / 1014.52 |
| 1초 제한, `node:http` | 502. `AbortError`(`ABORT_ERR`), 까닭이 `TimeoutError`(코드 23) | 1013.56 / 1012.49 / 1008.33 | 1014.09 / 1013.23 / 1015.97 | 1020.36 / 1018.48 / 1012.70 | 1021.38 / 1021.04 / 1014.46 |

- 제한 시간이 없으면 페이지가 대역만큼 느려진다. 1초 제한은 5~25ms 늦게 걸렸다. 제한은 두 방법 모두 `AbortSignal.timeout(1000)` 을 호출에 넘겨 걸었다.
- 끊긴 요청도 대역은 끝까지 처리했다. 되풀이마다 대역이 받은 지연 요청이 12, 끝낸 것이 12 였다(제한 없는 여섯과 끊긴 여섯). 부르는 쪽이 끊어도 대역의 스레드와 데이터베이스 연결은 그 시간 동안 잡혀 있다. 느린 요청이 연결 묶음(10)이나 스레드 풀을 채울 때의 동작은 재지 않았다.

### 대역이 내려가 있을 때

되풀이마다 대역 하나를 따로 띄워 `fetch` 와 `node:http` 로 한 번씩 답을 받은 뒤 끄고, 그 포트를 불렀다. 내려가 있었다는 표지는 끄기 전에 그 포트에서 답을 받았고, 명령줄의 표지를 보고 껐고, 끈 뒤와 잰 뒤에 파이썬 소켓도 거절됐고(`ConnectionRefusedError`, errno 10061), 그 사이 살아 있는 대역에 닿은 요청이 없었다는 것이다. 실패의 까닭은 모든 요청에서 `ECONNREFUSED` 였다(`fetch` 는 `TypeError` 의 까닭으로, `node:http` 는 `Error` 의 코드로). 페이지 대역은 502 를 냈다.

| 갈래 | n | 중앙값 `792ec2` | 최댓값 `792ec2` | 중앙값 `3467e1` | 최댓값 `3467e1` |
|---|---|---|---|---|---|
| 순차, `fetch` | 10 | 0.79 / 0.77 / 1.82 | 8.05 / 7.76 / 16.42 | 2.21 / 1.71 / 1.69 | 17.95 / 14.34 / 10.72 |
| 순차, `node:http` | 10 | 0.61 / 0.63 / 1.64 | 1.17 / 1.17 / 2.28 | 2.05 / 1.53 / 1.34 | 3.47 / 2.30 / 1.89 |
| 순차, `fetch` + 1초 제한 | 10 | 0.70 / 0.84 / 1.81 | 0.96 / 1.64 / 2.39 | 2.19 / 1.72 / 1.65 | 2.53 / 2.03 / 2.15 |
| 동시 10, `fetch` | 10 | 6.55 / 6.54 / 10.75 | 6.82 / 6.68 / 11.00 | 12.91 / 10.79 / 9.72 | 13.55 / 11.03 / 9.96 |
| 동시 10, `node:http` | 10 | 4.62 / 3.66 / 5.98 | 4.85 / 4.16 / 6.82 | 8.08 / 5.66 / 5.13 | 9.50 / 6.30 / 6.25 |

- Node 는 닫힌 루프백 포트의 거절을 몇 ms 안에 받았다. 같은 포트에 파이썬 소켓(`socket.create_connection`)으로 붙으면 거절을 받기까지 2.0~2.6초가 걸렸다(프로브가 찍은 값, 열두 번). 둘이 다른 까닭은 보지 않았다.
- 이것은 루프백의 닫힌 포트에서 본 것이다. 컨테이너가 내려가 이름이 풀리지 않는 경우, 호스트가 꺼져 패킷이 버려지는 경우에는 거절이 오지 않으므로 이 값이 그대로 나오지 않는다. 재지 않았다.

### 대역이 답하지 않을 때

연결을 받고 요청 줄만 읽은 뒤 답하지 않는 소켓을 불렀다(`--hang`). 표지는 그 소켓이 요청 줄 둘을 받았다는 것이다. 실행마다 한 번씩이다.

| 갈래 | 실행 `792ec2` | 실행 `3467e1` |
|---|---|---|
| 제한 없음, `fetch` | 304.1초 뒤 `TypeError`, 까닭이 `HeadersTimeoutError`(`UND_ERR_HEADERS_TIMEOUT`). 502 | 307.1초 뒤 같은 오류. 502 |
| 제한 없음, `node:http` | 330.0초에 요청을 보낸 쪽이 끊을 때까지 오류도 답도 없었다 | 같다 |

`fetch` 는 헤더를 300초쯤 기다리다 스스로 끊었고, `node:http` 는 330초 안에는 끊지 않았다. 그 뒤로도 끝없이 기다리는지는 보지 않았다.

### 지금의 서버 코드

코드를 읽었다. 재지 않았다.

- 처리기는 동기 함수다. `export function handle(request: PortalRequest, context: PortalContext): PortalResponse`(`web/apps/portal/server/handler.ts` 89 줄), 그것을 거는 겉의 타입도 `(request: PortalRequest) => PortalResponse` 다(`web/apps/portal/server/serve.ts` 16 줄). 사이트 목록은 뜰 때 한 번 만든 `context` 에 들어 있다(`web/apps/portal/tools/start.ts` 92~97 줄). 요청마다 다른 서버를 부르려면 처리기와 겉이 `Promise` 를 돌려주게 바뀌어야 한다.
- 서버 코드와 시험은 전역 `fetch` 를 쓰지 않는다고 처리기의 머리 주석이 적고(`handler.ts` 3~4 줄), 판정자가 전역 `fetch` 를 막는다(`web/eslint.config.mjs` 99~104 줄의 목록과 221 줄의 `no-restricted-globals`. "HTTP 는 생성 클라이언트로 부른다"). 생성 클라이언트는 `openapi-fetch` 이고 그 안에서 `fetch` 를 부른다(같은 파일 98 줄의 주석). 생성 클라이언트를 거친 호출은 재지 않았다. 전역 `fetch` 를 직접 부른 값과 같다고 보는 것은 어림이다.

## 해석의 대조와 갈래

해석마다 그것이 맞으면 나올 결과를 보이는 대조와, 같은 관찰을 설명하는 다른 해석을 가르는 갈래를 적는다. 둘 가운데 하나가 없는 것은 어림이라고 적는다.

- **"`sites-*` 갈래의 시간은 요청마다 대역과 데이터베이스에 다녀온 시간이다."** 대조: 답마다 일련번호가 다르고 그 수가 요청 수와 같다. 답의 줄 수가 10 이고 nonce 가 그 되풀이 직전에 써 둔 값이다. PostgreSQL 통계의 표 훑기 수가 대역이 끝낸 조회의 수와 같다. 갈래: 부르지 않는 `none` 갈래(호출 0, 순차에서 0.3~0.6ms)와 기억이 맞은 요청(호출 0, 0.6~1.0ms)은 그 시간이 붙지 않는다.
- **"이어 쓰는 `fetch` 가 느린 것은 쓰기 전에 0ms 타이머 하나를 기다리기 때문이다."** 대조: 추적한 요청 30 모두에서 `fetch` 호출과 소켓 쓰기 사이에 `scheduleIdleSocketValidation` 이 건 `setTimeout` 이 있었고 쓰기는 그것이 불린 0.08ms 뒤였다. 아무 일 없는 `setTimeout(…, 0)` 도 같은 15.6ms 였다. 갈래: 서버가 `fetch` 의 요청에 늦게 답한다는 해석이면 새 연결의 `fetch` 도 느려야 하는데 `node:http` 와 0.4~0.7ms 차였다. 연결을 이어 쓰는 것 자체가 느리다는 해석이면 `node:http` 의 이어 쓰기도 느려야 하는데 0.4~0.6ms 였다. 같은 자리가 `setImmediate` 인 판(리눅스 컨테이너)에서는 차가 0.2~0.3ms 였다. 판과 플랫폼을 따로 바꾼 갈래는 없다.
- **"조회 시간의 대부분은 PostgreSQL 이 아니라 그 앞의 길이다."** 대조: 같은 세 문장이 컨테이너 안의 `pgbench` 로는 0.43~0.70ms 였고 호스트 부하가 100% 일 때도 그랬다. 갈래가 모자라다. 길(Docker Desktop 의 포트 전달)과 파이썬 드라이버·스레드를 가르는 갈래(컨테이너 안에서 psycopg 로, 호스트에서 `pgbench` 로)가 없어 어느 쪽인지는 어림이다.
- **"내려간 대역에는 몇 ms 안에 실패한다."** 대조: 그 포트에서 먼저 답을 받았고, 끈 뒤 파이썬 소켓도 거절됐고, 오류 코드가 모두 `ECONNREFUSED` 다. 갈래: 주소나 페이지 대역의 잘못으로 실패했다는 해석이면 끄기 전에도 실패했어야 하는데, 같은 주소가 끄기 직전에는 두 방법 모두에 200 으로 답했다(`downtarget-alive-*`). 살아 있는 대역에 잘못 닿은 요청도 없었다. 루프백의 닫힌 포트 밖으로는 일반화하지 않는다.
- **"제한 시간이 없으면 느린 대역만큼 기다리고, 걸면 그 시간에 끊긴다."** 대조: 대역이 적은 조회 시간이 3,005ms 이상이고 제한 없는 갈래가 200 으로 3.01~3.10초였다. 갈래: 제한을 건 갈래는 같은 대역에 1.00~1.02초에 `TimeoutError` 였고, 대역의 셈(받은 것 12, 끝낸 것 12)이 끊긴 요청도 대역에 닿았음을 보인다.
- **"답하지 않는 대역에 `fetch` 는 5분쯤 뒤에 스스로 끊고 `node:http` 는 끊지 않는다."** 대조: 답하지 않는 소켓이 요청 줄 둘을 받았다. `fetch` 는 304.1초와 307.1초에 `UND_ERR_HEADERS_TIMEOUT` 이었다. `node:http` 쪽은 330초까지 끊지 않았다는 것만 봤다. 갈래마다 실행에 한 번씩(모두 두 번)이다.

## 재지 못한 것

- 배포의 모양. 컨테이너 사이의 네트워크, 이름 풀이, TLS, 프록시를 지나는 길에서는 재지 못했다. 대역 셋이 모두 호스트의 프로세스였다.
- 실제 위젯 관리 서버와 Agent OS 서버의 "지금 누구인지" 경로. 아직 없거나 부르지 않았다. 대역은 조회 하나와 작은 JSON 뿐이고 인증, 미들웨어, 기록이 없다.
- 다른 드라이버와 설정. psycopg 3 동기 연결 묶음(autocommit 끔, `def` 경로) 하나로만 쟀다. 비동기 드라이버, autocommit, 연결 묶음의 크기, uvicorn 작업자 여럿은 재지 않았다.
- 리눅스 호스트와 리눅스의 Node 에서의 측정 전체. 리눅스에서 본 것은 `fetch_idle_timer.mjs` 하나다.
- 같은 Node 판을 두 플랫폼에서, 두 Node 판을 같은 플랫폼에서 견주는 것.
- 부하가 없는 때의 시간. 측정 내내 다른 세션이 같은 PC 를 썼다. 호스트 CPU 부하가 가장 낮던 되풀이가 11% 로 시작했다.
- 조회 시간에서 길과 드라이버의 몫을 가르는 것.
- 생성 클라이언트(`openapi-fetch`)를 거친 호출, `node:http` 로 둘을 부르는 갈래, `node:http` 로 기억을 두는 갈래.
- 대역이 내려간 다른 모양(이름이 풀리지 않는다, 패킷이 버려진다, 연결을 받은 직후 끊는다)과 연결을 맺는 데 걸리는 제한 시간.
- 대역이 쉬는 연결을 닫는 순간에 보낸 요청, 대역이 다시 뜬 직후의 첫 요청.
- 느린 요청이 대역의 연결 묶음이나 스레드 풀을 채울 때, 동시 10 보다 큰 동시성, 오래 도는 부하.
- 기억을 저장할 때 버리게 하는 길, 실패했을 때 옛 값을 쓰는 길, 2초가 아닌 시간.
- 위젯 테스트 페이지가 실제로 받는 요청의 빈도.

## 남긴 것

- 컨테이너와 프로세스: 없다. 실행마다 끝에서 자기 컨테이너를 지웠다고 찍었고(`정리: 컨테이너 portal-admin-settings-fetch-<표지> 지웠다`), 모두 끝난 뒤 `docker ps -a --filter name=portal-admin-settings-fetch-` 가 비었고 명령줄에 실행 표지나 `settings_fetch` 가 든 프로세스가 없었다(손으로 봤다, `Get-CimInstance Win32_Process`). 익명 볼륨은 컨테이너와 함께 지우게 했고(`docker rm -f -v`) 남았는지는 따로 세지 않았다.
- 이미지: 새로 받거나 지은 것이 없다. `postgres:18-alpine` 과 `node:24-trixie-slim` 은 이미 있던 것이다.
- 원본 기록: 세션 스크래치패드(저장소 밖)에 있고 커밋하지 않는다. `--work` 없이 돌린 짧은 실행이 시스템 임시 폴더에 남긴 폴더 하나는 지웠다. 다시 돌리면 `--work` 폴더에 같은 모양으로 남는다.
