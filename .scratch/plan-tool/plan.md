# plan-tool: 여러 단계를 밟는 커스텀 에이전트가 계획표를 적고, 그 계획표가 질문한 사람의 화면에도 보인다.
**슬라이스:** 15
**Blocked by:** text-to-sql
**설계:** 일지 2026-11-10-1845-memory-search-design

계획표(`CONTEXT.md`). 여러 단계를 밟는 커스텀 에이전트가 실행 하나 안에서 할 일과 진행 상태를 적어 두는 목록이다. 내는 것은 저장소가 없는 작은 도구 서버 하나와 스킬 하나이고, 기본 에이전트 `assistant`에는 붙이지 않는다. 사용자가 "계획이 질문한 사람의 화면에도 보이게"를 골랐다. 위젯이 "1. 규정 찾기 완료, 2. 재고 조회 중"처럼 단계를 보여 준다. 실행 하나 안에서만 쓰고, 같은 대화의 다음 질문까지 남는 메모는 만들지 않는다. 화면에 보이려면 셋이 바뀐다. 최종 사용자 항목은 도구 호출의 인자를 싣지 않으므로(ADR 0023이 `tool_called`의 인자와 결과를 싣지 않는다고 정했다. `src/agent_os/channel/http/items.py`의 진행 항목 주석) 그 결정을 고치는 ADR 0023의 이력, 채널 계약 `openapi.json`의 변경, 위젯의 변경이다. 런타임이 특정 도구의 이름을 알면 안 되므로(원칙 IV. ADR 0048이 런타임은 문서 검색 서버를 모른다고 정한 것과 같은 방향이다) 화면에 보여도 되는 인자를 도구 쪽에서 선언하는 일반 장치가 필요하고, 그 방식은 명세가 정한다. 계약을 바꾸는 결정이라 명세는 ADR 0023의 이력 초안을 함께 쓰고 사용자 승인을 받으며, 계약 티켓이 첫 티켓이고 다른 티켓을 막는다. 묶음(슬라이스 15)의 뜻과 시작하는 때와 차례는 ADR 0046의 2026-11-10 이력 "제품 1.0에 지식베이스 고르기가 들고 커스텀 에이전트의 부품 다섯이 새 묶음으로 선다"가 원천이다. Blocked by의 text-to-sql은 기술적 의존이 아니라 사용자가 고른 차례다. 계획표는 실행이 길어질수록 쓸모가 커서 새 묶음의 마지막에 뒀다. 알아 둘 것: 계획표를 적고 고치는 호출도 그 에이전트의 도구 호출의 끝(`max_tool_calls`, ADR 0052)을 나눠 쓰고, 실행 하나가 모델을 많아야 10번 부르는 지금은 효과가 작을 수 있다(어림. `src/agent_os/core/loop.py`의 `MAX_TURNS = 10`). 명세가 정할 것: 화면에 보여도 되는 인자를 선언하는 자리와 모양(매니페스트를 바꾸면 sdk 계약이다), 그 선언을 누가 믿는지(믿지 않는 서버의 선언으로 인자가 최종 사용자에게 나가도 되는지. mcp-trust와 맞춘다), 최종 사용자 항목의 새 모양, 위젯이 계획표를 그리는 모양(`ui-design`), 도구의 이름과 인자, 스킬의 본문, 계획표를 붙이지 않은 에이전트의 스트림이 바뀌지 않는다는 시험. 범위 밖: 같은 대화의 다음 질문까지 남는 메모, 계획표를 기본 에이전트에 붙이는 것. 수락: 계획표를 붙인 커스텀 에이전트에게 여러 단계가 필요한 질문을 하면 위젯에 단계 목록이 보이고 단계가 끝날 때마다 상태가 바뀌며, 계획표를 붙이지 않은 에이전트의 최종 사용자 스트림은 지금과 같고, 선언하지 않은 인자는 화면에 나가지 않는 테스트와 위젯 e2e가 통과한다
