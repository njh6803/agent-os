# 0036: **CI가 인터프리터 충돌에서 단서를 남기지 않는다.** PR #78의 첫 실패 로그는 "545 passed" 뒤 종료 코드 139뿐이었다.

**상태:** 닫힘 (`chore/ci-timeouts-and-faulthandler`, 2026-10-15, 일지 2026-10-16-14): python 잡의 `PYTHONFAULTHANDLER`, 앞 스텝의 `core_pattern`, pytest 스텝 안의 `ulimit -c`, 실패 시 gdb의 `bt`·`info sharedlibrary`. PR #241에서 일부러 충돌시켜 손으로 봤다. 종료 중 충돌은 두 스택이 모두 남았고 테스트 도중의 충돌은 C 스택만 남았다
**어디로:** `.github/workflows/ci.yml`
**승인:** 사용자 승인 2026-09-26, 일지 2026-09-26-04.

pytest의 faulthandler는 세션이 끝나며 꺼지고 코어도 남지 않아, 로컬 19/19 초록 앞에서 CI를 루프로 탐침 아홉 번을 돌렸다(약 1.5시간). 결정적 단서는 여덟째의 코어 덤프 C 스택이었다. 정보 접근이라 검사다 — `ci.yml`의 `env`에 `PYTHONFAULTHANDLER: "1"`(종료 중 충돌의 파이썬 쪽 스택), 그리고 코어 두 곳. `ulimit -c unlimited`는 셸마다라 **pytest를 돌리는 그 `run` 단계 안에서** 걸고(`kernel.core_pattern`은 시스템 전역이라 앞 단계여도 된다), `if: failure()` 스텝은 남은 코어를 gdb로 열어 `bt`와 `info sharedlibrary`만 찍는다(PR #79 CodeRabbit). 탐침 셋째에서 `PYTHONFAULTHANDLER`가 재현을 없애지 않는 것을 봤다. 워크플로 변경은 별도 PR로 먼저 병합한다(`operations.md` 리뷰 파이프라인. 2026-09-28 정정: 그 규칙은 `claude-code-review.yml`에만 걸리고 `ci.yml`은 별도 PR이 필요 없다, ADR 0021의 2026-09-28 이력)
