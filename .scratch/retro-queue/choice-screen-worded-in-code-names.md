# choice-screen-worded-in-code-names: 승인 화면의 선택 질문을 코드 이름과 설계 용어(층, 포트, 어댑터)로 써서, 사용자가 질문을 알아보지 못하고 쉽게 다시 설명해 달라고 했다

**상태:** 열림
**어디로:** 대상 미정, 회차 감시. 후보는 `tools/hook_choice_facts.py`가 처음인 선택 화면을 막을 때 질문 문장과 라벨에 든 코드 이름(백틱 스팬, 점이나 밑줄로 이은 식별자)을 함께 찍는 것이다. 지침은 이미 있다(`CLAUDE.md` 원칙의 선택지 라벨 줄)
**승인:** 자체 승인 2026-11-15, 5회차(1회차는 `CLAUDE.md` 원칙의 그 줄이 든 일지 2026-10-15-17의 사건이다), 일지 2026-11-14-2152-admin-login-design.md·2026-11-15-1312-portal-admin-design.md·2026-11-17-2031-plain-words-in-written-artifacts.md(4회차, 2026-11-17)·2026-11-20-1928-diag-bundle-design.md(5회차, 2026-11-20). ADR 불필요

말 풀이를 본문에 먼저 실었는데도(대기열 114의 처방) 질문 문장과 라벨이 설계 용어 그대로라 답을 받지 못했다. 폴더 셋의 표와 "부탁의 목록"이라는 말로 다시 묻자 답을 받았다.

(4회차는 선택 화면이 아니라 파일로 쓰는 글이다. 사용자가 명세, 티켓, 용어집의 낯선 말도 쉬운 말로 고쳐 달라고 했다. 그 몫은 `.scratch/harness/issues/plain-words-in-written-artifacts.md`가 `CLAUDE.md` 원칙의 줄을 파일로 쓰는 글까지 넓히고 용어집을 다시 써서 반영했다. 위 `어디로:`의 선택 화면 훅은 이 꼴에 닿지 않는다)

(5회차는 설계 인터뷰의 첫 선택 화면이다. 질문과 라벨에 코드 이름은 없었고, 기능 계획의 말("진단 묶음")과 짧은 라벨만으로 물어 사용자가 "자세하게 이해하기 쉽게 설명해줘."라고 했다. 코드 이름을 찍는 위 후보는 이 꼴도 잡지 못한다. 처방을 고를 때는 질문이 무엇을 정하는지와 고르면 무엇이 바뀌는지를 장면으로 적었는지를 보는 길을 함께 본다)
