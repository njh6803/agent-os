# 04: 진행 규율을 사람이 임시 폴더에서 돌려 검증한다

**What to build:** 사람이 이 기계의 데스크톱 앱(Windows)에서 임시 폴더를 열고 런북 머리의 한 줄로 킥오프를 시작해, 진행 규율이 사용자 레벨 스킬을 만들고 준비부터 4단계까지 차례로 진행하며 사람 몫 줄에서 멈추는지, 압축과 세션 끊김 뒤에 진행 파일에서 잇는지 본다. 이 검증으로 이 기계에 `~/.claude/skills/kickoff/SKILL.md`가 실제로 설치된다. 검증에서 드러난 진행 규율과 런북의 어긋남은 이 티켓에서 고친다. 진행 규율에는 자동 이음매가 없어(헤드리스 `claude -p`에는 `AskUserQuestion`이 없다. 명세 검토의 임시 스크립트로 본 것이라 어림이다) 이것이 그 확인이다.

이 티켓은 이 티켓의 세션이 직접 돌지 않는다. 이 티켓의 세션은 사람에게 차례를 안내하고, 사람이 임시 폴더에서 연 다른 세션의 진행 파일과 일지를 읽어 결과를 이 티켓의 일지에 적는다.

근거는 `.scratch/kickoff-auto-flow/spec.md`의 Testing Decisions "진행 규율의 검증"(여덟 차례가 원천이다)과 "자동으로 보지 않는 것", Out of Scope의 받는 쪽이다. 사용자가 고른 이음매이고, 고른 설명과 다른 세 곳은 명세 서두와 그 절에 있다(일지 2026-10-12-34, 2026-10-13-01).

**Blocked by:** 03

**Status:** ready-for-agent

### 전제

- [ ] 01·02·03이 main에 병합되고 `tidy-checkouts`로 당겨진 주 체크아웃(`C:/project/agent`)을 런북 clone으로 쓴다. 티켓의 워크트리를 clone으로 쓰지 않는다. 그러면 만든 `SKILL.md`가 병합 뒤 지워질 경로를 가리킨다(명세 검토의 지적, 일지 2026-10-13-01)
- [ ] 이 기계의 `~/.claude/skills/kickoff/`가 아직 없다. 있으면 무엇이 만들었는지 보고 사람에게 묻는다
- [ ] 임시 폴더는 저장소 밖이다

### 차례 (명세의 여덟)

- [ ] 1. clone의 `git -C <clone> status --porcelain`과 `git -C <clone> rev-parse HEAD`를 적는다. 런북 머리의 한 줄을 붙여 넣는다
- [ ] 2. 진행 규율이 사용자 레벨 스킬을 만들 허락을 묻고 만든 뒤 멈춘다. 같은 세션에서 `/kickoff`를 친다(`~/.claude/skills`가 이미 있어 `/reload-skills`가 필요 없는 갈래). 데스크톱 앱의 입력창에서 세션 도중에 만든 스킬이 바로 불리는지가 이 차례의 측정이다
- [ ] 3. 준비를 돈다. 결정은 시험용 값으로 고르고 원격은 만들지 않는다. billing 조회와 CodeRabbit 확인이 실제로 돈다. 진행 파일의 사람 몫 표에 단계 `시작`의 행이 있다
- [ ] 4. 0단계가 끝남으로 적힌다
- [ ] 5. 1단계 뒤 사람이 `/compact`를 친다. 압축 뒤 진행 규율과 진행 파일을 다시 읽고 2단계로 간다. 시작의 확인이 다시 묻지 않는다(붙여 넣기 판정을 건너뛰고, 런북 판이 같고, clone 상태는 보이기만 한다)
- [ ] 6. 같은 세션에서 2·3·4단계를 돈다. 2단계의 결정이 선택 화면으로 온다. 4단계의 setup을 Read로 따르며 그 질문을 선택 화면으로 묻는다(스토리 20). 그 사이 새 프로젝트의 스킬을 Skill 도구로 부르지 않는다
- [ ] 7. 4단계 뒤 세션을 끝낸다. 진행 파일에 기록된 런북 커밋을 `KICKOFF.md`를 바꾼 앞 커밋(`git -C <clone> log --oneline -2 -- KICKOFF.md`의 둘째)으로 손으로 바꾼다. 같은 폴더의 새 세션에서 `/kickoff`를 친다. 바뀐 커밋의 목록을 보이고 새 판으로 이을지 묻고(스토리 18), 새 판을 고르면 5단계부터 이으려 한다. 거기서 멈춘다
- [ ] 8. clone의 `status --porcelain`과 `rev-parse HEAD`가 1에서 적은 것과 같다(스토리 32). 주 체크아웃은 여러 세션이 쓰므로, 다르면 `git -C <clone> reflog`와 바뀐 파일로 그 차이가 어디서 왔는지 보고 다른 세션의 병합·당기기·미추적 파일은 빼고 판정한다. 진행 규율이 clone의 파일이나 브랜치를 바꾼 흔적이 없으면 통과다

### 보는 것과 기록

- [ ] 단계의 차례, 사람 몫 줄에서의 멈춤과 그 선택 화면의 모양(추천이 맨 앞, 선택지마다 설명), 진행 파일의 갱신(대기, 끝남), 일지의 `> 사용자:` 인용과 거기에 다른 저장소의 이름이 없는지, 런북 clone 상태의 표시를 본다
- [ ] 결과와 사람이 친 것을 이 티켓의 일지에 적는다. 차례마다 기대와 실제를 나란히 적고, 어긋난 곳은 그대로 남긴다
- [ ] 만든 `~/.claude/skills/kickoff/SKILL.md`는 지우지 않는다. 그것이 이 기계의 실제 설치다. 임시 폴더는 검증 뒤 지운다

### 어긋났을 때

- [ ] 진행 규율이나 런북의 어긋남은 이 티켓의 브랜치에서 고친다. 고친 동작은 병합 전에 다시 돌려 본다. 임시 폴더의 세션에 이 티켓의 워크트리에 있는 `kickoff/runner.md`를 가리키는 한 줄을 붙여 넣는다. 시작 확인이 clone의 브랜치가 main이 아니라고 물으면 "이 판으로 간다"를, 스킬이 다른 clone(주 체크아웃)을 가리킨다고 물으면 "둔다"를 고른다. 그 갈래도 검증의 일부로 적는다. 이 다시 돌리기는 명세에 없고 이 티켓이 정한 길이다. 붙여 넣은 한 줄로 돌므로 `/kickoff`로 부른 스킬의 길과 압축 뒤 다시 실리는 것은 다시 보지 못한다. 고친 것이 그 둘에 닿으면 병합하고 당긴 뒤 주 체크아웃에서 그 차례(2나 5)만 다시 돌고 일지에 적는다
- [ ] 고친 것이 명세나 ADR 0028의 결정을 바꾸면 멈추고, 명세를 고치거나 ADR 이력을 제안한다
- [ ] 같은 실패가 두 번 이어지면 추측 수정을 멈추고 `diagnosing-bugs`를 쓴다

### 받는 쪽

- [ ] 이 기계에서 돌지 않는 스토리는 두 번째 프로젝트의 킥오프가 받는다. 5(원격의 허락), 8·9("했다 / 건너뛴다"의 고리), 13(조직의 비관리자), 14(무엇을 만들지 모를 때), 19(명령의 실패), 22~25(8단계와 끝), 31(단계 안에서 끊긴 뒤 잇기. 이 검증은 단계 사이에서만 끊는다), 35(런북 어긋남. 이번에 나면 그것으로 본다)다. `.scratch/plan.md`의 기능이 아니라서 행을 두지 않는다(명세 Out of Scope). 이 목록을 일지의 "다음"에 남긴다
