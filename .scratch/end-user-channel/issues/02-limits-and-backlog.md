# 02: 상한과 백로그 — 너무 길거나 잦은 요청은 422·429로 거절되고 느린 수신자는 그 연결만 끊긴다

**What to build:** 최종 사용자 경로에서 요청 글자 수가 그 사이트의 상한을 넘으면 422(`body.request`)다. 주체별·사이트별·전역의 동시 실행 수, 주체별·사이트별 시간당 실행 수, 주체별 구독 수를 넘으면 429이고 봉투의 `code`가 여섯째 어휘, `message`가 어느 상한인지를 들며 `Retry-After`가 붙는다. 결정(재개)도 동시 실행과 시간당 실행에 든다. 상한에 걸린 요청은 core에 닿지 않아 트레이스도 셈도 늘지 않고 서버 기록 한 줄이 남는다. 사이트 파일의 상한 표로 값을 바꾸고 전역 동시 실행만 `serve` 인자다. 연결마다 쌓이는 프레임이 1,000을 넘으면 그 연결만 닫히고 실행은 계속 돈다(`/runs`도 같다). 운영자 채널 `/runs`와 관리 API에는 상한이 없다.

01의 틈 셋(429는 계약에 있되 내지 않는다, 상한 표를 적은 사이트 파일은 거절된다, 422 설명의 글자 수를 서버가 재지 않는다)을 닫는다. 03 뒤인 이유는 타임아웃으로 실패한 실행이 칸을 돌려주는 사례를 재려면 타임아웃이 있어야 해서이고(명세 검토 보고가 타임아웃 ≤ 상한의 순서를 권했다. 일지 2026-10-05-04), 04 뒤인 이유는 429 응답에 CORS 헤더가 붙고 `Retry-After`가 노출 헤더에 있는 것을 재려면 CORS 미들웨어가 있어야 해서다(같은 일지의 셀프 리뷰 절, 명세 축 Major). 그래서 이 티켓이 마지막에 서고 05와 함께 잎이다.

근거는 `.scratch/end-user-channel/spec.md`의 "상한", "백로그", "사이트 파일"(상한 표), "CLI와 `serve`"(전역 상한 인자), Testing의 "상한"과 "둘째 구동자" 절과 그 2026-10-05 명세 검토·to-tickets 주석이다. ADR 0023과 ADR 0014의 2026-10-03 이력이 앞선 결정이다. 기본값은 사용자가 고른 중간 묶음이고 재지 않은 어림이다.

**Blocked by:** 01, 03, 04

**Status:** ready-for-agent

### 사이트 파일의 상한 표와 `serve` 인자

- [ ] **사이트 항목에 선택 상한 표가 는다.** 값마다 선택이고 요청 글자 수, 주체별 동시 실행, 주체별 시간당 실행, 사이트별 동시 실행, 사이트별 시간당 실행, 주체별 구독의 여섯이다. 1 이상의 엄격한 정수(`conversation_limit`과 같은 규칙). 0·음수·불린·실수·숫자 문자열은 시작 때 구성 오류다. 키 이름은 이 티켓이 짓는다. 01이 "모르는 키는 손상"으로 거절하던 파일이 이 티켓부터 선다
- [ ] **적지 않은 값은 기본값이다.** 요청 글자 수 20,000, 주체별 동시 2, 주체별 시간당 60, 사이트별 동시 20, 사이트별 시간당 1,000, 주체별 구독 4, 그리고 전역 동시 50. **기본값 일곱은 채널의 한 곳이 소유한다**(루프 상한이 core의 한 곳에 있는 것과 같은 모양). 01이 시작 경로의 422 설명에 글자로 적은 20,000은 이 티켓이 그 상수에서 읽게 고쳐 한 곳이 된다
- [ ] **전역 동시 실행 상한은 `serve` 인자다.** `serve` 인자의 기본은 없음이고 없음이면 위의 50이다(명세 검토 nit. 같은 값이 두 곳에 서지 않는다). 0 이하는 구성 오류. 인자 이름은 이 티켓이 짓는다
- [ ] **`serve` 테스트.** 상한 값 0·실수·문자열 → 종료 코드 1과 진단. 새 인자가 `create_app`에 닿는다

### 셈 (채널)

- [ ] **요청 글자 수는 코드 포인트 수다.** 시작 본문의 `request`가 그 사이트의 상한을 넘으면 422이고 `violations`가 `body.request`를 가리킨다. 01이 적은 422 설명의 단위가 이 동작과 맞는지 다시 본다
- [ ] **동시 실행은 등록부로 센다.** 그 주체·그 사이트·전역에서 최종 사용자 경로가 일으켜 지금 도는 실행의 수다. 결정도 든다. 실행이 끝나거나 실패하거나 일시정지하면 풀린다
- [ ] **시간당 실행은 미끄러지는 창이다.** 주체와 사이트마다 최근 3,600초 안의 시작 시각 목록을 든다. 시작과 결정 모두 센다. 요청이 오면 먼저 창 밖의 시각과 비어 버린 키를 지우고(명령), 그다음 수를 본다(질의). 둘을 한 함수에 섞지 않는다(CQS). 시계는 `Clock` 포트다
- [ ] **구독 수는 주체마다 열린 구독 연결(`GET`)의 수다.** 시작·결정 응답의 연결은 세지 않는다. 연결이 닫히면 줄어든다
- [ ] **검사의 자리는 인증과 본문 검증 뒤, core 앞이다.** 422(형식, 글자 수)가 먼저, 429가 그다음, core의 404·409는 그 뒤다. 남의 실행에 낸 결정도 상한에 걸릴 수 있다(429가 404보다 먼저. 드러나는 것은 자신의 셈뿐). 목록 밖 에이전트로 보낸 시작도 같다
- [ ] **칸의 입장과 반환은 등록부 한 곳이 소유한다.** 상한 검사와 칸 차지(등록부에 예약으로 넣기)는 `await` 없이 한 걸음이라 동시 요청 둘이 마지막 칸을 함께 차지하지 못한다. 반환은 실행이 등록부를 떠나는 한 자리(01이 둔 그 자리)에서 꼭 한 번이다 — 첫 이벤트 전의 실행 전 실패(404·409·500 전부), 결말(끝남·실패·일시정지), 타임아웃(03), 앱 종료의 취소. 시작·결정 응답의 연결이 끊긴 것은 반환이 아니다. 시간당 셈은 시각이라 반환이 없다
- [ ] **429의 예외 타입은 `agent_os.http`가 소유하고 채널이 던진다**(명세 검토 should-fix. 표는 채널 타입을 import할 수 없고 라우트는 상태 코드를 스스로 정하지 않는다). 타입이 `Retry-After` 초와 어느 상한인지를 들고, `failure_for`의 갈래 하나가 그것을 429와 헤더로 옮긴다. 01이 둔 `_CODE_BY_STATUS`의 429 행이 어휘를 준다. 이름은 이 티켓이 짓는다
- [ ] **`Retry-After`의 값.** 시간당에 걸리면 가장 오래된 시각이 창을 나가는 초(올림, 1 이상). 동시 실행이나 구독 수에 걸리면 5초. `message`는 어느 상한인지 들되 주체별인지 사이트별인지 전역인지는 들지 않는다
- [ ] **상한에 걸린 요청은 서버 기록에 남는다.** `remember_failure`로 사이트의 발급자와 어느 상한인지를 적는다. 주체(`sub`)는 적지 않는다
- [ ] **운영자 채널과 관리 API에는 걸지 않는다.** 셈은 프로세스 메모리이고 다시 시작하면 비워진다

### 백로그

- [ ] **연결마다 쌓이는 프레임 상한은 1,000이고 바이트는 세지 않는다.** 흐름의 버퍼 크기가 그 값이고 넣을 자리가 없으면 그 연결의 흐름만 닫는다(`send_nowait`의 가득 참). 실행은 계속되고 최종 사용자는 구독으로 다시 붙는다. `/runs`도 같은 값이다(지금은 무제한). 실행을 모는 루프는 여전히 이벤트 사이에 `await` 하지 않는다

### 테스트

- [ ] **상한.** 주체별 동시 2(둘째 시작 200, 셋째 429와 `Retry-After: 5`), 결정도 셈에 듦, 사이트별 합계(주체 셋이 각 2 → 일곱째 429. 기본값 20을 사이트 파일에서 6으로 낮춰 잰다), 전역(`create_app` 인자로 낮춰 잰다), 시간당(가짜 시계를 돌려 창을 나가면 다시 받는 것, `Retry-After`가 남은 초), 구독 수, 429가 core에 닿지 않는 것(포트 호출 0), 실제 429 응답의 `code`가 여섯째 어휘인 것, 허용 출처의 429 응답에 CORS 헤더 셋이 붙고 `Retry-After`가 노출 헤더에 드는 것(04의 미들웨어. 04의 CORS 테스트가 429를 빼고 여섯 상태 코드만 보므로 429는 여기서 본다), 서버 기록 한 줄
- [ ] **칸의 반환**(스토리 55, 명세 검토가 덮이지 않았다고 짚었다). 실행 전 실패 뒤·결말 뒤·타임아웃 뒤(03)·앱 종료 뒤에 칸이 돌아와 다음 시작이 200이고, 시작 응답의 연결이 끊긴 뒤에는 돌아오지 않는다. `create_app`과 둘째 구동자로 사례마다
- [ ] **백로그.** 둘째 구동자에서 1,001 프레임째에 그 연결만 닫히고 실행은 끝까지 가며 다른 구독은 산다. `/runs`도 같다

### 지침과 잔존

- [ ] **`channel.md`에 상한의 셈과 검사 자리, 칸의 입장·반환의 소유, 백로그 1,000(`/runs`도)을 적고 "크기 제한이 없는 흐름" 항목을 고친다.** `http.md`에 429의 예외 타입과 표의 갈래, `Retry-After`. 채널의 실행 소유 모듈 독스트링(무제한 → 1,000, 상한을 두지 않는 이유 문단)을 고친다
- [ ] **잔존이 0이다.** `크기 제한이 없는 흐름`, `상한을 두지 않는 이유`, `범위 밖에 둔 동시 실행 상한`을 저장소 전체에서 grep한다(기록 제외)
- [ ] **기능을 닫는지는 병합 직전에 판정한다.** `git fetch` 뒤 `origin/main`의 05 티켓 파일 `Status:`가 `done`이면 이 PR이 `.scratch/plan.md`의 end-user-channel 행을 `done`으로 바꾸고 프론티어 문단을 고친다. 아니면 05가 닫는다. main이 최신 기준(strict)이라 뒤에 병합되는 쪽은 앞의 병합을 들인 뒤에야 병합되므로 둘이 함께 열려 있어도 한쪽은 반드시 본다(01·03·04는 이 티켓이 막혀 있던 것이라 이미 `done`이다)
- [ ] 검증 명령이 모두 초록이다. `channel/`과 `main.py`를 건드리므로 기존 `-m llm`을 한 번 돌려 일지의 검사 절에 적는다

### 이 티켓이 정할 것

1. 사이트 파일 상한 표의 키 이름 여섯
2. `serve`의 전역 상한 인자 이름
3. 429 예외 타입의 이름과 그것이 드는 필드
4. 기본값 일곱이 사는 채널의 한 곳(모듈과 상수 이름)

### 01이 넘긴 메모 (2026-10-06)

- 사이트 파일 읽기와 진단은 `main.py`에 있다(`_SiteEntry`·`_read_sites`·`_keys_of` 등, 티켓 01이 그 자리로 정했다). 01의 셀프 리뷰가 `main.py`가 조립에 더해 사이트 파일의 스키마와 진단까지 맡는 것을 Divergent Change로 짚었고 보류했다. 이 티켓이 상한 표의 키를 들이면 그 읽기가 더 자라므로, 모듈을 나눌지 여기서 다시 본다(일지 `docs/journal/2026-10-06-01-end-user-channel-contract.md`의 셀프 리뷰 절)
- 같은 자리의 `_read_sites`가 `Sites | list[str]`(진단 목록)를 돌려주고 `_serve`와 `_configuration_problems`가 `isinstance`로 가른다. 01의 셀프 리뷰와 PR #137 3회차 claude-review가 짚었고 보류했다. 모듈을 나눌 때 실패를 담는 타입으로 바꿀지 함께 본다
- 시작·결정·구독은 모두 의존성이 등록부에 받는 쪽을 열고, 닫는 것은 응답 제너레이터(`RunStream.items()`의 `with`, `_Subscription.frames()`의 `finally`)다. 요청이 의존성과 제너레이터 시작 사이에서 끝나면 그 받는 쪽은 실행이 끝날 때까지 실황에 남는다(PR #137 3회차 claude-review가 구독에서 짚었다. 같은 모양이 운영자 경로에도 있다. 코드를 읽었고 재지는 않았다). 주체별 구독 상한을 셀 때 이것이 세어지는지 재고, 닫는 자리를 둘지 여기서 정한다
