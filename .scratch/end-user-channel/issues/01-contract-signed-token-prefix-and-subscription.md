# 01: 계약 — 사이트가 서명한 토큰으로 자기 접두사의 시작·결정·구독을 쓰고 걸러진 항목을 받는다

**What to build:** `serve`가 사이트 파일을 받아 뜨면, 사이트의 백엔드가 RS256으로 서명한 JWT를 든 요청이 `/runs`와 다른 새 접두사 아래 경로 셋(시작, 결정, 구독)을 연다. 주체는 `발급자|sub`이고 시작 이벤트에 그대로 남는다. 응답은 최종 사용자 항목(시작·진행·일시정지·결정·끝남·실패·끝내지 못함)의 SSE 스트림이고 프레임마다 `id`가 그 항목의 근거인 트레이스 인덱스다. 프롬프트, 도구 결과, 주체, 예외 원문, 대화 요약은 내려가지 않는다. 연결이 끊긴 최종 사용자는 구독으로 `Last-Event-ID` 다음부터 다시 받고, 도는 실행에는 생기는 대로 붙으며, 서버가 다시 떠 사라진 실행은 끝내지 못했다는 항목으로 닫힌다. 남의 실행, 손상된 남의 실행, 없는 실행, 열 에이전트 밖의 실행은 모두 같은 404 고정 문구다. CLI `resume`은 최종 사용자의 실행에 진단과 종료 코드 1이다. 채널 토큰과 관리 토큰은 새 접두사에서 통하지 않고 서명 토큰은 그 밖에서 통하지 않는다.

이 기능의 계약 티켓이고 02·03·04·05를 막는다. 계약은 `openapi.json`(새 접두사의 경로 셋, 항목 유니온과 멤버 일곱, 고아 컴포넌트 하나, 에러 어휘 여섯째, `Retry-After` 응답 헤더의 문서, 계약 파일의 설명이 두 면에서 세 면으로)과 그것이 끌고 오는 것 전부다. 끌고 오는 것은 명세가 찾은 넷(라우트와 core의 판정·서명 토큰 검증·투영, api-client의 타입 테스트, 인증 전수 검사, 어휘 수를 세는 테스트와 문서)에 2026-10-05 명세 검토가 더한 셋(채널 테스트의 컴포넌트 차집합 등식, 전수 검사의 면 분류가 2분법이라 새 접두사가 조용히 관리로 분류되는 것, 상태 코드→어휘 표에 429가 없으면 `invalid_request`로 접히는 것. 셋 다 to-tickets가 코드로 다시 봤다)이다. 리뷰의 질문은 "동작하나"가 아니라 이 이름과 모양으로 오래 살 수 있느냐다.

**병합 뒤에 틈이 있다(명세가 인정했고 to-tickets에서 사용자가 받아들였다).** 429는 계약에 있되 서버가 내지 않는다(상한은 02). preflight는 새 접두사에서도 401 그대로다(CORS는 04). 실행에 타임아웃이 없다(03). 관리 화면은 최종 사용자의 멈춘 실행에 결정 자리를 그대로 보이고 누르면 409 봉투가 보인다(05. 명세 검토가 결정 컴포넌트의 실패 안내 코드를 읽어 그 사이 거짓이 되는 계약이 없다고 봤다). 사이트 파일에 상한 표를 적으면 모르는 키라 시작에서 거절된다(fail-closed. 상한 표의 키는 02가 들인다). 시작의 422 설명은 요청 글자 수의 단위와 기본값을 말하되 서버는 글자 수를 재지 않는다(02). 이 티켓이 쓰는 문장(독스트링, 주석, rules, 계약의 설명)은 틈 동안에도 참이어야 한다 — 계약과 표와 타입이 약속하는 것을 말하고, 02~05가 들일 동작을 지금 난다고 적지 않는다(conversation 01의 규칙).

근거는 `.scratch/end-user-channel/spec.md`의 "이음매", "계약 티켓", "서명 토큰", "사이트 파일"(상한 표 제외), "주체", "인증 미들웨어와 접두사 표", "경로 셋", "core — 열 에이전트와 주체의 판정", "core — 재개의 판정 순서", "면별 응답 번역", "최종 사용자 스트림", "투영", "등록부와 구독", "CLI와 `serve`"(사이트 파일 인자와 OS 이름 가드), "api-client", "`openapi.json`", "문서 갱신" 절과 그 2026-10-05 명세 검토·to-tickets 주석이다. ADR 0023과 ADR 0009·0010·0011·0014·0015·0017의 2026-10-03 이력, ADR 0014·0023의 2026-10-05 이력이 앞선 결정이다.

### 서명 토큰 (공용 층 `agent_os.http`)

- [x] **`pyjwt[crypto]`를 직접 의존으로 선언한다.** 잠긴 패키지의 집합과 판은 바뀌지 않고 선언과 락의 메타데이터만 바뀐다(ADR 0023). `uv lock`을 돌린 결과가 그것과 다르면 멈춰 보고한다. `tech.md` 런타임 의존성 행의 "end-user-channel이 직접 의존으로 선언한다"를 지난 사실로 고친다
- [x] **허용 알고리즘은 RS256 하나이고 필수 클레임은 `iss`, `sub`, `aud`, `exp`, `iat` 다섯이다.** `sub`는 비지 않은 문자열(숫자 거부). `exp - iat`가 600초를 넘으면 거절하고 소비 지점이 센다. 시계 여유 30초가 `exp`·`iat`·`nbf`에 같이 걸린다. 클레임은 `dict(...)`로 감싸 `Mapping[str, object]`로 받는다(타입 우회 없이 `sub`를 좁히는 조건)
- [x] **검증 순서는 토큰 형식 → 발급자로 사이트 항목 → `kid`로 키 → 서명·필수 클레임·`aud`·`iss`(라이브러리) → `exp`·`iat`·`nbf`·수명(소비 지점) → `sub`다.** 발급자와 `kid`는 서명을 검증하기 전에 서명 없이 읽어 항목 하나와 키 하나를 고른다. 헤더에 `kid`가 있으면 그 `kid`의 키만, 없으면 목록을 차례로. 어느 단계든 실패는 같은 401이고 문구는 기존 고정 문구 하나(`UNAUTHORIZED_MESSAGE`)다. 원인은 서버 기록에 `request_id`와 함께 남고 토큰 값은 기록하지 않는다(원칙 V)
- [x] **시간 클레임은 검증 자리가 `Clock` 포트로 센다**(to-tickets에서 사용자가 골랐다. 셀프 리뷰 두 축의 Major). 라이브러리의 시간 검증(`verify_exp`·`verify_iat`·`verify_nbf`)은 끄고, `exp`·`iat`·`nbf`와 수명 600초와 여유 30초를 소비 지점이 시계 포트의 지금으로 판정한다. 미래 `iat`도 여기서 거절한다. 명세의 "라이브러리가 본다" 문장들은 그렇게 바뀐다(명세의 주석). `create_app`이 받는 시계가 인증 표(서명 토큰 줄)에도 닿는다 — 공용 층이 core의 포트를 받는 것은 http → core 방향이라 원칙 IV 안이다. 그래서 만료·미래 `iat`·여유·수명 사례와 스토리 15를 가짜 시계로 잰다. 프로브 `jwt_claims.py`가 실제 시간으로 잰 라이브러리의 판정(여유가 셋에 같이 걸림, 미래 `iat` 거절)을 소비 지점이 같은 뜻으로 옮긴다
- [x] **`aud`는 그 사이트 항목의 대상 하나다.** 문자열이면 같아야 하고 배열이면 포함해야 한다(라이브러리의 규칙)
- [x] **접두사 표에 셋째 줄이 는다.** 새 접두사는 서명 토큰 검증, `/runs`는 채널 토큰, 그 밖은 관리 토큰 그대로다. 표의 값이 "토큰 하나" 또는 "서명 토큰(사이트 목록)"의 둘이 되고 모양은 이 티켓이 짓는다. 접두사 비교(경로 조각 단위, 서로를 품지 않음)는 공용 층의 함수 하나로 두어 인증 표와 표의 면 판정이 쓴다(04의 CORS 분기도 같은 함수를 쓴다)
- [x] **검증을 지난 요청은 주체(`발급자|sub`)와 사이트 항목을 요청의 상태에 심는다.** 라우트의 의존성이 그것을 읽어 core에 주체를, 열 에이전트 판정에 사이트를 넘긴다. 본문에서 받지 않는다(ADR 0015)
- [x] **채널 토큰과 관리 토큰은 새 접두사에서 401이고 서명 토큰은 그 밖에서 401이다.** 인증 없이 지나가는 것은 `/health` 하나 그대로다(`PUBLIC_PATHS`는 바뀌지 않는다). preflight는 이 티켓에서는 어디서나 401 그대로다(04)
- [x] **토큰 테스트.** `create_app` 테스트가 `cryptography`로 RSA 키 둘(사이트 둘)과 `kid` 둘(한 사이트의 교체)을 만들어 서명한다. 정상 수락과 주체가 시작 이벤트에 드는 것. 거절 열다섯이 모두 같은 401 문구이고 서버 기록이 원인을 든다 — 서명 틀림, 만료, 미래 `iat`, 수명 601초, `iat`·`sub`·`aud`·`exp`·`iss` 없음, 다른 대상, 모르는 발급자, 모르는 `kid`, `alg` `none`, HS256(공개 키 PEM을 비밀로), 형식 깨짐. 사이트 둘의 키를 바꿔 서명한 토큰은 401. `kid` 없는 토큰은 키 둘인 사이트에서 차례로 시도해 수락. 열다섯 밖의 경계 셋 — 빈 `sub`와 숫자 `sub`는 401, 수명이 꼭 600초인 토큰은 수락(프로브 `jwt_claims.py`가 잰 경계)
- [x] **토큰 만료 뒤에도 열린 스트림은 끊기지 않는다**(스토리 15, 명세 검토가 덮이지 않았다고 짚었다). 둘째 구동자에서 실황을 받는 동안 가짜 시계를 `exp`와 여유를 지나게 돌려도 항목이 계속 오고, 같은 토큰으로 보낸 다음 요청은 401이다. 위의 시계 포트 결정이 이것을 잴 수 있게 한다. 토큰은 요청 하나를 여는 것이고 연결은 그 요청이다

### 사이트 파일 (모양은 공용 층, 읽기는 `main.py`)

- [x] **TOML이고 `schema_version = "1"` 필수다.** 사이트 항목의 배열이고 항목마다 발급자, 대상, 공개 키 목록(항목마다 PEM과 선택 `kid`), 허용 출처 목록, 열 에이전트 목록이다. **상한 표는 이 티켓에 없다**(02가 키를 들인다. 모르는 키는 손상이라 틈 동안 상한을 적은 파일은 시작에서 거절된다). 키 이름은 이 티켓이 짓는다
- [x] **구성 오류 전부를 `serve`가 시작 자리에서 모아 진단하고 끝난다.** 인자를 줬는데 파일 없음·손상, 모르는 키, 발급자가 비었거나 겹치거나 `|`를 품음, 공개 키가 PEM(SubjectPublicKeyInfo)으로 읽히지 않거나 RSA가 아님, 한 사이트 안에서 `kid`가 겹치거나 `kid` 없는 항목이 둘 이상, 열 에이전트 이름이 플러그인 이름 패턴 위반, 허용 출처에 `*`. 토큰·호스트·모델 진단과 같은 자리(`_configuration_problems`)에서 함께 낸다. 진단에 토큰이나 키 값을 싣지 않는다
- [x] **열 에이전트에 없는 이름은 구성 오류가 아니다.** 요청 때 core의 부재(404)가 답한다
- [x] **허용 출처는 이 티켓에서 읽고 검증하되 쓰지 않는다**(CORS는 04). 비어 있을 수 있다
- [x] **인자가 없으면 사이트 없음이다.** 새 접두사는 서되 모든 토큰이 401이다. `create_app`이 사이트 목록을 받고 비면 그렇다. `tools/export_openapi.py`가 `create_app`을 키워드 전부로 부르므로 새 인자가 필수면 함께 고친다(명세 검토가 코드를 읽었다)
- [x] **모델의 층.** 사이트 목록의 타입은 공용 층이 소유하고 TOML의 키 이름과 손상 판정은 `main.py`가 소유한다. 공용 층은 TOML을 모른다. 어댑터가 아니다(`create_app`의 인자라 조립이 읽는 구성)
- [x] **`serve` 테스트.** 사이트 파일 없음(인자 없음)으로 뜨고 새 접두사의 모든 토큰이 401. 위 구성 오류 각각 → 종료 코드 1과 진단(값은 싣지 않음). 열 에이전트에 없는 이름은 뜬다. 새 인자가 `create_app`에 닿는다(기존 serve 테스트가 uvicorn 호출을 기록하는 것과 같은 모양)

### 주체와 OS 이름 가드

- [x] **주체 이름은 `<발급자>|<sub>`다.** 첫 `|`에서 가르면 짝이 하나로 정해진다(발급자가 `|`를 품지 않으므로). `Principal` 타입은 패턴 없는 문자열 그대로이고 sdk는 바뀌지 않는다
- [x] **OS 사용자 이름에 `|`가 들면 `serve`·`run`·`resume`이 시작 자리에서 끝난다.** `getpass.getuser()`로 주체를 만드는 자리(`main.py`)에서 본다. `serve`는 다른 구성 오류와 모아서, `run`·`resume`은 종료 코드 1과 진단. 테스트는 `LOGNAME`·`USERNAME`으로 심는다. 그래서 `|`가 든 주체는 언제나 최종 사용자이고 그 밖은 언제나 OS 사용자다(ADR 0015 이력이 계약 티켓에 넘긴 것)

### core — 열 에이전트 집합, 자기 실행 읽기, 재개의 판정 순서

- [x] **`run()`과 `resume()`이 선택 인자 하나를 더 받는다: 호출자가 볼 수 있는 에이전트의 집합.** 없음은 전부다. 운영자 채널과 CLI는 없음을, 최종 사용자 경로는 그 사이트의 열 에이전트 목록을 넘긴다. `run()`에서 요청이 댄 에이전트가 집합 밖이면 `Absent`이고 메시지는 없는 에이전트와 글자 그대로 같으며 매니페스트를 읽기 전이라 플러그인 포트가 불리지 않는다. `resume()`에서 트레이스가 가리키는 에이전트가 집합 밖이면 `Absent`이고 메시지는 없는 실행과 같은 꼴이다. 이어 가기(`previous_run`)에서는 요청이 댄 에이전트만 본다(앞 실행의 에이전트가 집합 밖이어도 선다). 이름은 이 티켓이 짓는다. **타임아웃 인자는 이 티켓에 없다**(03)
- [x] **자기 실행 읽기 함수를 core에 둔다.** 입력은 트레이스 포트, 실행 식별자, 주체, 에이전트 집합이고, 없음(`Absent`) → 손상(`PluginError`) → 다른 주체(`DifferentPrincipal`) → 열 에이전트 밖(`Absent`)의 순서로 판정해 읽은 트레이스를 돌려준다. 동기이고 `await`가 없다. **손상은 지금 재개가 손상이라 부르는 것 그대로다** — 단건 읽기(`link_of`: 모르는 종류, 빈 트레이스, 식별자 어긋남, 시작 이벤트로 열리지 않음)와 기록 규칙(`check_record_rules`: 앞 실행 필드의 패턴, 요약 이벤트의 자리와 개수). ADR 0014의 2026-10-05 이력이 적은 순서(없음 → 손상 → 다른 주체 → 열 에이전트 밖 → 형식 1 → …)에 걸음을 더하거나 손상의 뜻을 좁히지 않는다. `resume()`의 첫 걸음이 이것을 부르고 그 뒤 형식 1 → 일시정지 아님 → 자리 어긋남 → 고리를 이어 간다. 구독(채널)도 같은 함수를 부르므로 기록 규칙을 어긴 트레이스는 구독도 손상이다. **이어 가기의 `gather_continued`와는 나누지 않는다**(2026-10-05 to-tickets가 정했다. 명세는 앞 셋을 나누는 것을 재량으로 두었는데, 이어 가기의 기록 규칙은 주체·끝남 뒤라 이 함수를 쓰면 그 결정된 순서가 바뀐다 — 명세 검토 should-fix. 나누지 않으면 둘 다 제 순서를 지킨다). 이름은 이 티켓이 짓는다
- [x] **재개의 판정 순서는 없음 → 손상 → 다른 주체 → 열 에이전트 밖 → 형식 1 → 일시정지 아님 → 자리 어긋남 → 고리 → 준비 → 결정 쓰기다.** 지금 순서에서 바뀌는 것은 형식 1이 손상 뒤로 가고 주체와 열 에이전트가 끼는 것이다(ADR 0014의 2026-10-05 이력). 손상에 기록 규칙이 드는 것은 지금과 같다. 대가는 손상된 형식 1 트레이스에 보낸 결정이 409에서 500으로 바뀌는 것이고 테스트가 그것을 고정한다. 형식 1 트레이스의 주체도 읽힌다(`RunStarted.principal`은 첫 슬라이스부터 필수. 명세 검토가 sdk 이벤트 모델과 JSONL 어댑터의 읽기 코드를 읽었다). 거부는 결정 이벤트를 쓰기 전이라 트레이스는 그대로다. 첫 걸음에 `await`가 없다는 불변식은 그대로다
- [x] **결정의 주체 판정은 `DifferentPrincipal`이다.** conversation 01이 지은 타입 그대로이고, 그 독스트링(core 포트 모듈)을 고친다 — 던지는 자리가 이어 가기 하나라고 적은 것을 둘로, 그리고 "최종 사용자 경로의 404와 CLI의 진단은 그 기능이 더한다"처럼 이 기능을 미래형으로 가리킨 문장을 지난 사실로(CLI의 진단은 기반 타입 처리로 이미 있다). 메시지는 남의 주체 이름을 들지 않는다
- [x] **core 테스트.** "결정의 자리" 절 옆에 "결정의 주체" 절. 순서의 사례마다 둘씩 어긋나게 해 앞의 것이 이기는지 본다(없음, 손상 — 단건 읽기와 기록 규칙 각각, 다른 주체, 열 에이전트 밖, 형식 1, 일시정지 아님, 자리, 고리, 준비). 다른 주체의 결정은 트레이스가 그대로다. 열 에이전트: 집합 밖은 `Absent`이고 메시지가 없는 에이전트와 글자 그대로 같으며 플러그인 포트가 불리지 않는다, 없음은 전부, 이어 가기는 요청한 에이전트만. 자기 실행 읽기: 네 판정을 그 순서로 거치고 트레이스를 돌려주며 같은 가짜로 `resume()`을 돌린 결과와 맞는다
- [x] **CLI `resume`으로 최종 사용자의 실행에 결정하면 진단과 종료 코드 1이다**(스토리 61, 명세 검토가 덮이지 않았다고 짚었다). CLI 테스트 하나. `DifferentPrincipal`은 기반 타입으로 잡히므로 CLI 코드는 바뀌지 않는다

### 면별 응답 번역 (공용 표)

- [x] **`failure_for`가 면을 인자로 받고 면은 셋의 열거다** — 운영자(지금 그대로), 최종 사용자의 시작 경로, 최종 사용자의 실행을 가리키는 경로. 불리언 둘이 아니라 열거 하나(`CODING_STANDARDS.md`). 핸들러가 요청 경로를 조립이 넘긴 새 접두사와 비교해(공용 층의 접두사 비교 함수) 면을 정한다. 라우트는 상태 코드를 스스로 정하지 않는다
- [x] **최종 사용자 면의 404는 모두 고정 문구 하나다.** `Absent`의 메시지도 덮는다(명세 검토가 명세의 두 문장이 반대라고 짚었고 "덮는다"가 맞다). 덮기: `DifferentPrincipal`(409) → 404. 실행을 가리키는 경로의 `PluginError`(하위 타입이 아닌 500) → 404(ADR 0023의 2026-10-05 이력. 원인은 서버 기록에 `request_id`와 함께). `Disabled`(409) → 409이되 메시지는 종류와 이름 없는 고정 문구(문구는 이 티켓이 짓고 `_DOCUMENTED_ERRORS`에 적지 않는다). `NotResumable`·`NotContinuable`은 메시지 그대로. 시작 경로의 `PluginError`는 500 고정 문구 그대로
- [x] **서버 기록은 덮기 전의 것을 남긴다.** `remember_failure`가 표가 뽑은 원래 상태 코드와 예외 이름과 문구를 적는다
- [x] **운영자 면은 바뀌지 않는다.** 같은 가짜 트레이스(남의 손상된 실행)에 운영자 채널은 500 원문, 최종 사용자 면은 404 고정이고 서버 기록은 둘 다 원인을 든다
- [x] **상태 코드→어휘 표(`_CODE_BY_STATUS`)에 429가 들고 어휘 여섯째가 선다**(to-tickets가 찾았다. 429가 표에 없으면 `invalid_request`로 접힌다). 이 티켓에서 429를 내는 자리는 없다 — 그 예외 타입과 표의 갈래는 02다. 어휘 수를 세는 테스트와 `http.md`의 "다섯"이 여섯이 된다

### 새 접두사의 경로 셋과 프레임 (채널)

- [x] **접두사 하나 아래 셋.** 시작(`POST`, 본문은 `StartRun` 그대로), 결정(`POST`, 실행 식별자를 경로에, 본문은 `Decision` 그대로), 구독(`GET`, 실행 식별자를 경로에, 본문 없음, 선택 헤더 `Last-Event-ID`). 실행 식별자는 `verbatim` 변환기와 sdk의 패턴으로. 새 본문 컴포넌트는 없다. 접두사와 경로 이름과 `operation_id` 셋은 이 티켓이 짓고 용어집(`## 구조`, `## 실행`)에 기댄다. 새 접두사는 `/runs`를 품지도 `/runs`에 품기지도 않는다
- [x] **문서화된 에러는 셋 모두 401, 404, 409, 422, 429, 500이다.** 429는 `Retry-After` 응답 헤더를 문서에 든다(에러 문서 모듈이 헤더를 실을 수 있게 넓힌다). 409 설명은 공유 설명 그대로. 시작의 422 설명에 요청 글자 수의 단위(코드 포인트)와 기본값 20,000을 글자로 적고 테스트가 고정한다 — 지금 에러 문서 모듈의 설명은 상태 코드마다 공유 문자열 하나라 경로 하나만 다른 설명을 드는 모양을 이 티켓이 정한다(아래 정할 것). (to-tickets에서 사용자가 골랐다. 값 자체는 사이트 파일이 원천이고 위젯 빌드가 거기서 읽는다 — web-widget 행). 이 티켓에서 422를 내는 것은 형식뿐이고 글자 수 초과의 422는 02다
- [x] **프레임은 `data:` 한 줄과 `id:` 한 줄이다.** `id`는 그 항목의 근거인 트레이스 인덱스(0부터)의 십진 글자. `event:`·`retry:`는 싣지 않는다. 라우트의 반환 주해는 `AsyncIterator[항목 유니온 | SkipJsonSchema[ServerSentEvent]]`이고 `ServerSentEvent(data=항목, id=...)`를 yield한다(측정 `sse_id_frames.py` 모양 E). `/runs`는 `data:`만 그대로다
- [x] **항목 유니온은 판별자 `type`의 pydantic 유니온이고 계약에 이름 있는 컴포넌트로 서며 `itemSchema.properties.data.contentSchema`가 그것을 바로 가리킨다.** 별칭을 한 겹 더 두지 않는다. 항목 컴포넌트 이름 일곱과 유니온 이름은 기존 컴포넌트(특히 `Decision`·`Approve`·`Deny`·`RunStarted` 같은 이벤트와 본문의 이름)와 겹치지 않는다(명세 검토 nit. 겹치면 FastAPI가 모듈 경로로 이름을 짓고 `-Input/-Output` 검사가 못 잡는다). 이름은 이 티켓이 짓고 용어집의 "최종 사용자 항목"에 기댄다
- [x] **고아 컴포넌트는 `ServerSentEvent` 하나다.** 계약 테스트가 "참조되지 않는 컴포넌트의 집합은 `ServerSentEvent` 하나"를 고정한다. 후처리로 지우지 않는다
- [x] **시작 응답도 구독과 같은 프레임이다.** 시작 항목부터 결말까지이고 `id`를 든다. 결정 응답은 결정 항목부터이고 `id`는 `pause_index + 1`부터
- [x] **시작과 결정의 상태 코드.** 시작: 에이전트가 열 에이전트 밖이거나 없으면 같은 404(메시지까지), 꺼졌으면 409 고정 문구, 구성 오류 500 고정 문구. 결정: 남의 실행 404(운영자 채널은 같은 실행에 409), 없는 실행 404, 손상 404(서버 기록은 500과 원인), 열 에이전트 밖 404, 일시정지 아님·자리 어긋남 409, 꺼짐 409 고정 문구, 404의 메시지가 넷 모두 같은 고정 문구. 트레이스가 그대로인 것. 라우트는 core에 집합을 넘길 뿐 먼저 확인하지 않는다(`channel.md`)
- [x] **채널 라우터는 셋을 어디에 두는가.** 새 접두사의 라우터가 기존 채널 라우터와 같은 `Runs`(등록부)를 나눠 쓴다. 모양(라우터 하나에 접두사 둘인지, 라우터 둘이 등록부 하나를 받는지)은 이 티켓이 정한다. 어느 쪽이든 채널과 관리는 서로를 import하지 않고 `server.py`가 조립한다

### 투영 (채널)

- [x] **이벤트 하나가 항목 하나 또는 없음이 되고 종류로만 가른다.** `run_started` → 시작(`run_id`), `tool_called` → 진행(도구 이름, 성패), `run_paused` → 일시정지(도구 이름, 인자 원문), `approval_granted`·`approval_denied` → 결정(허가인지 거부인지, 거부의 사유), `run_finished` → 끝남(출력), `run_failed` → 실패(고정 문구 하나, `run_id`). `llm_called`·`run_resumed`·`conversation_summarized`는 없음이라 프레임을 내지 않고 인덱스만 지난다. 끝내지 못함은 구독이 닫을 때만 낸다. 필드 이름은 이 티켓이 짓는다
- [x] **실패 항목의 고정 문구는 하나다.** 요약 실패도 도구 서버 기동 실패도 같다(가르는 것은 web-widget)
- [x] **테스트.** 가짜 에이전트가 도구 호출·일시정지·실패를 내어 항목 일곱의 투영과 `id`가 0부터 트레이스 인덱스와 같은 것. 요약 이벤트가 든 트레이스(가짜가 손으로 쓴다)는 그 자리를 건너뛴다. 항목에 프롬프트·도구 결과·주체·예외 원문이 없다

### 등록부와 구독 (채널. 명세 검토 blocker: 구독 라우트와 등록부는 한 티켓이다)

- [x] **등록부는 채널의 `Runs`가 든다.** 앱의 수명이 소유하는 실행에 `run_id`로 이름표를 달고, 실행 하나에 실황 하나(지금 받는 쪽들의 송신 흐름 목록)를 둔다. 실행의 태스크가 이벤트를 받으면 트레이스 인덱스를 붙여 모든 흐름에 `await` 없이 넣고, 결말이 나면 흐름을 닫고 등록부에서 뺀다. 실행이 등록부를 떠나는 자리는 하나다(02의 칸 반환이 그 자리를 쓴다). 포트가 아니다. **흐름의 크기 상한은 이 티켓에서 무제한 그대로다**(백로그 1,000은 02)
- [x] **인덱스의 셈.** `run()`이 낸 첫 이벤트가 0이고 하나씩 는다. `resume()`이 낸 첫 이벤트의 인덱스는 `pause_index + 1`이다. 트레이스에 쓰인 줄의 자리와 같다
- [x] **시작·결정 응답도 등록부의 흐름 하나다.** 처음부터(또는 결정부터) 받는 구독과 같은 프레임이다
- [x] **구독의 첫 걸음은 한 걸음이다.** `Last-Event-ID` 해석 → core의 자기 실행 읽기 → 같은 걸음에 등록부를 보고 도는 실행이면 실황에 흐름을 붙인다. 셋 사이에 `await`가 없다. 그 뒤 트레이스에서 `Last-Event-ID` 다음 인덱스부터 투영해 보내고 네 갈래로 간다. **트레이스의 결말이 등록부 보기보다 우선한다**(명세 검토 nit. 마지막 이벤트를 쓴 뒤 도구 연결을 닫는 동안 실행이 등록부에 남는 창이 있다)
- [x] **네 갈래.** 끝남·실패: 나머지를 보내고 닫는다. 일시정지: 일시정지 항목까지 보내고 닫는다. 등록부에 있음: 나머지를 보낸 뒤 실황에서 오는 것을 보내고 결말 항목 뒤 닫는다(중복을 거르는 벨트는 두지 않는다). 등록부에 없고 결말도 없음: 나머지를 보내고 끝내지 못함 항목으로 닫는다. 그 항목의 `id`는 마지막 이벤트의 인덱스 + 1이다
- [x] **`Last-Event-ID`.** 선택 헤더. `^[0-9]{1,12}$`를 어기면 422(`violations`의 `field`는 `header.last-event-id`). 없으면 처음부터. 트레이스의 마지막 인덱스보다 크면 409이고 **그 판정은 자기 실행 읽기의 네 판정(404) 뒤다**(명세 검토 nit. 존재 노출의 순서). 질의 파라미터는 두지 않는다
- [x] **구독의 상태 코드.** 남의 실행 404, 손상 404, 열 에이전트 밖 404, 모르는 종류가 섞인 트레이스도 손상이라 404. 404의 메시지가 넷 모두 같은 고정 문구다. 결정의 자리가 오래됐는지는 보지 않는다
- [x] **둘째 구동자 테스트.** 도는 실행에 구독이 붙으면 그 뒤 이벤트가 생기는 대로 오고 빠짐·중복이 없다(가짜 모델이 이벤트 시점을 조절한다). `Last-Event-ID` 없음(처음부터), 중간(그다음부터, 빈자리를 건너뛴 다음), 마지막(아무 항목 없이 닫힘 또는 실황만), 범위 밖 409, 형식 위반 422. 네 갈래 각각. 선례는 `_Wire`와 `disk_seconds`

### `openapi.json`, api-client, 손 목록

- [x] **계약 파일이 `create_app().openapi()`와 같다.** 바뀌는 것: 새 접두사의 경로 셋과 에러 문서, 항목 유니온과 멤버 일곱과 고아 `ServerSentEvent`, 어휘 여섯째, `Retry-After` 헤더 문서, 계약 설명(두 면 → 셋. 한 줄 후보: 최종 사용자 경로는 사이트가 서명한 토큰으로 연다). 바뀌지 않는 것: `/runs`와 관리 경로, `StartRun`·`Decision`, 이벤트와 매니페스트, 봉투. 같은 커밋에 다시 생성한 클라이언트 타입이 든다
- [x] **api-client에 최종 사용자 경로 목록(셋)을 더해 관리 클라이언트의 경로에서 뺀다.** 채널 클라이언트는 결정 하나 그대로. 타입 테스트의 기대와 "채널의 경로 셋" 주석을 고친다. 위젯 클라이언트는 web-widget이다
- [x] **손 목록 셋.** 채널 테스트의 컴포넌트 차집합 등식(`EXISTING_COMPONENTS`와 다섯의 등식)에 항목 일곱·유니온·고아를 더한다(저절로 빨개진다). 전수 검사의 면 분류(`_under_channel`, 채널 아니면 관리의 2분법)를 3분법으로 고쳐 "새 접두사에 채널·관리 토큰 401", "그 밖에 서명 토큰 401"이 실제로 재어진다(명세 검토. 고치지 않으면 새 접두사가 관리로 분류되어 조용히 초록이다). 손으로 든 채널 오퍼레이션 목록(`CHANNEL_OPERATIONS`)은 그대로 두고 새 접두사의 오퍼레이션 목록을 따로 든다 — 409를 문서화한 오퍼레이션 전부와 그 목록의 등식을 단언하는 테스트가 있어 새 경로가 409를 문서화하는 순간 빨개지고, 기존 목록에 더하면 항목마다 `contentSchema`가 `Event`를 가리킨다는 단언이 새 경로에서 빨개진다(셀프 리뷰 표준 축이 코드를 읽었다). 409 등식은 두 목록의 합과 비교하고 `contentSchema` 단언은 목록마다 제 유니온을 본다
- [x] **계약 테스트.** 최신성, 세 경로의 문서화된 에러가 봉투이고 미디어 타입이 JSON, 어휘 여섯과 1:1, 항목 유니온이 이름 있는 컴포넌트이고 `contentSchema`가 그것을 가리키며, 참조되지 않는 컴포넌트의 집합이 `ServerSentEvent` 하나

11. 인증 표의 서명 토큰 줄이 시계 포트를 받는 모양

### 이 티켓이 정한 것 (2026-10-06)

위 "이 티켓이 정할 것" 열하나다. 근거와 대안은 일지 `docs/journal/2026-10-06-01-end-user-channel-contract.md`.

1. **접두사와 경로와 `operation_id`**: 접두사 `/end-user`(용어집 "최종 사용자"를 면의 이름으로). 시작 `POST /end-user/runs`(`start_end_user_run`), 결정 `POST /end-user/runs/{run_id}/approval`(`decide_end_user_approval`), 구독 `GET /end-user/runs/{run_id}/subscription`(`subscribe_end_user_run`, 용어집 "구독"). 접미사가 있는 이유는 운영자 채널과 같다 — `verbatim`이 슬래시까지 잡는다.
2. **항목 유니온과 멤버 일곱**: `EndUserItem`(판별자 `type`). `StartedItem`(`started`, `run_id`), `ProgressItem`(`progress`, `tool`, `ok`), `PausedItem`(`paused`, `tool`, `args`), `DecidedItem`(`decided`, `decision`은 `approve`·`deny`, `reason`은 거부의 사유이고 허가면 `null`), `FinishedItem`(`finished`, `output`), `FailedItem`(`failed`, 고정 문구 `message`, `run_id`), `UnfinishedItem`(`unfinished`, 필드 없음). `…Item`으로 지어 본문 `Decision`·`Approve`·`Deny`와 이벤트 `RunStarted` 같은 기존 이름과 겹치지 않는다. 판별자 값도 이벤트의 것(`run_started` 따위)과 다르다.
3. **어휘 여섯째**: `too_many_requests`(429). 기존 다섯처럼 상태의 뜻을 말하는 낱말이다.
4. **사이트 파일의 키**: `schema_version = "1"`, `[[sites]]`마다 `issuer`, `audience`, `allowed_origins`, `agents`, 그리고 `[[sites.public_keys]]`마다 `pem`과 선택 `kid`. 허용 출처와 열 에이전트는 비어 있을 수 있되 적어야 하고, 공개 키는 하나 이상이다. 값은 엄격한 타입이다.
5. **접두사 표의 값과 사이트 목록 타입**: `Credential = SharedToken | SiteSigned`(`http/auth.py`). 사이트 목록은 `Sites`(항목 `Site`, 키 `SiteKey`, `http/sites.py`). 검증을 지난 요청의 신원은 `EndUser`(주체와 사이트 항목)이고 라우트가 `end_user_of`로 읽는다.
6. **집합 인자와 자기 실행 읽기**: `run(..., visible_agents=)`·`resume(..., visible_agents=)`(호출자가 볼 수 있는 에이전트), `read_own_run(trace, run_id, principal, visible_agents) -> OwnTrace`(형식 버전과 읽은 실행). `core/run.py`에 둔다.
7. **면과 꺼짐의 고정 문구**: `Surface`(`OPERATOR`, `END_USER_START`, `END_USER_RUN`, `http/errors.py`)와 `failure_for(error, surface)`. 면은 조립이 넘긴 `EndUserPaths`(접두사와 시작 경로)로 정한다. 꺼짐 409의 문구는 "에이전트를 지금 쓸 수 없다"(`UNAVAILABLE_MESSAGE`). 404의 고정 문구는 공유 404 설명 그대로이고 `NOT_FOUND_MESSAGE`로 이름을 줬다.
8. **`serve`의 인자**: `--site-file PATH`(용어집 "사이트 파일").
9. **라우터의 나눔**: `channel_router` 하나가 `Runs` 하나와 수명을 들고 접두사 둘의 하위 라우터를 품는다(`_operator_router`와 `end_user_router(runs, …)`). 본문 모델은 두 면이 같이 쓰므로 `channel/http/bodies.py`로 옮겼다(계약의 이름은 그대로).
10. **경로 하나의 설명과 429 헤더**: `documented_stream_errors(*statuses, descriptions={…})` — 그 라우트에서만 다르게 말할 설명을 라우트 선언에 둔다. 429의 `Retry-After`는 상태 코드에 딸린 헤더 표(`_DOCUMENTED_HEADERS`)가 그 상태를 적는 라우트마다 붙인다. 스키마는 정수 하나이고 하한은 설명에 적는다.
11. **서명 토큰 줄의 시계**: `SiteSigned(sites=, clock=)`. `create_app`이 채널에 넘기는 시계와 같은 것이고, 검증은 시간 클레임에 닿을 때만 `clock.now()`를 부른다.
