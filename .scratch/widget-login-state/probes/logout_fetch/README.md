# logout_fetch: 창 없이 부르는 로그아웃이 통하는 조건

ADR 0061 결정 "로그아웃"은 위젯이 위젯 설정의 로그아웃 주소를 브라우저가 쿠키를 실어 보내는 요청으로 직접 부른다고 정하고, 그것이 통하는 조건을 어림으로 적은 뒤 이 기능의 명세가 재라고 넘겼다(같은 ADR Consequences "재지 않은 것"). `probe.mjs`가 그것을 잰다. 위젯 코드는 아직 없어 위젯이 보낼 요청(본문과 덧붙인 머리가 없는 POST, `credentials: "include"`)을 흉내 낸다. 재는 칸, 표지, 띄우는 것은 그 스크립트의 머리 주석이 원천이다. 인증서와 프록시는 옆 프로브와 함께 쓰는 `../kit.mjs`의 것이다.

## 다시 돌리기

```bash
node .scratch/widget-login-state/probes/logout_fetch/probe.mjs --engine chromium
```

- 필요한 것: `web/`의 의존성(`pnpm -C web install --frozen-lockfile`), Playwright의 Chromium, `openssl`(Git Bash의 것으로 돌렸다). 네트워크를 타지 않는다. hosts 파일을 건드리지 않는다.
- 약 4분이다(2026-11-16에 `time`으로 두 번 쟀고 3분 59초와 3분 55초였다).
- 결과가 같은 폴더의 `expected.json`과 같고 표지가 모두 있으면 0으로 끝난다. 원본 기록은 `--out`으로 준 폴더(주지 않으면 임시 폴더)의 `results.json`이다.
- `--engine`을 주지 않으면 세 엔진(chromium, firefox, webkit)을 모두 띄우려 한다. 이 PC에는 Playwright 1.63.0이 찾는 Firefox와 WebKit 빌드가 없어 그 둘은 "브라우저를 띄웠다" 표지가 없고 1로 끝난다(아래 "재지 못한 것").

## 잰 판

Playwright 1.63.0, Chromium 153.0.8010.12(Playwright가 내려받은 headless shell, 기본 프로필), Node v24.19.0, OpenSSL 1.1.1k, Windows 10. 2026-11-16.

## 재는 것의 이름

- **위젯이 도는 자리**는 일곱이다. 로그아웃 요청을 보내는 문서와 로그아웃 주소의 짝이다. 페이지 안 방식은 사이트의 페이지가 요청을 보내고, iframe 방식과 URL 방식은 위젯의 문서가 보낸다. 쿠키는 칸마다 로그아웃 주소의 출처에 심는다.
- **부르는 법**은 다섯이다. `fetch`의 `mode`(`cors`, `no-cors`), `redirect`(`follow`, `manual`), 끝점이 CORS 응답 머리를 내는지의 짝이다. `mode: "cors"`에 `redirect: "manual"`인 둘(끝점이 CORS 응답 머리를 내지 않는 것과 출처를 허용하는 것)이 명세가 고른 부르는 법이고, 나머지 셋은 그것을 고르기 전에 견준 것이다.
- **통했다**는 그 자리와 `SameSite`에서 로그아웃 요청에 쿠키가 실렸고, 그 뒤 새 탭에서 연 로그아웃 주소의 출처로 가는 요청에 쿠키가 없었다는 뜻이다. **통하지 않았다**는 쿠키가 실리지 않았고 쿠키가 남았다는 뜻이다.

## 결과

Chromium 하나의 결과다. 칸마다의 값은 프로브가 `expected.json`과 견주는 것이고(본 갈래 105칸, 덤 갈래 126칸), 아래 두 표의 "통했다"와 "통하지 않았다"는 프로브가 끝에 찍는 `요약` 줄을 옮긴 것이다. `Sec-Fetch-Site`와 `Origin` 칸, `fetch`의 끝은 프로브가 칸마다 찍은 줄을 손으로 읽어 줄였다(그 값들도 `expected.json`에 있다).

### 끝점이 204로 답할 때 (본 갈래)

부르는 법 다섯이 자리와 `SameSite`마다 모두 같은 결과를 냈다. 부르는 법마다 갈린 칸은 없었다.

| 위젯이 도는 자리 | 요청을 보낸 문서와 로그아웃 주소 | 끝점이 받은 `Sec-Fetch-Site` | 끝점이 받은 `Origin` | `SameSite=Lax` | `SameSite=Strict` | `SameSite=None` |
|---|---|---|---|---|---|---|
| 페이지 안 방식 | 사이트의 페이지가 같은 출처의 주소를 부른다 | `same-origin` | 페이지의 출처 | 통했다 | 통했다 | 통했다 |
| 페이지 안 방식 | 사이트의 페이지가 등록 도메인이 같은 다른 출처의 주소를 부른다 | `same-site` | 페이지의 출처 | 통했다 | 통했다 | 통했다 |
| 페이지 안 방식 | 사이트의 페이지가 등록 도메인이 다른 주소를 부른다 | `cross-site` | 페이지의 출처 | 통하지 않았다 | 통하지 않았다 | 통했다 |
| iframe 방식 | 사이트와 등록 도메인이 같은 위젯의 문서가 사이트의 페이지의 출처에 있는 주소를 부른다 | `same-site` | 위젯의 출처 | 통했다 | 통했다 | 통했다 |
| iframe 방식 | 사이트와 등록 도메인이 다른 위젯의 문서가 사이트의 페이지의 출처에 있는 주소를 부른다 | `cross-site` | 위젯의 출처 | 통하지 않았다 | 통하지 않았다 | 통했다 |
| URL 방식 | 사이트와 등록 도메인이 같은 위젯의 창이 사이트의 페이지의 출처에 있는 주소를 부른다 | `same-site` | 위젯의 출처 | 통했다 | 통했다 | 통했다 |
| URL 방식 | 사이트와 등록 도메인이 다른 위젯의 창이 사이트의 페이지의 출처에 있는 주소를 부른다 | `cross-site` | 위젯의 출처 | 통하지 않았다 | 통하지 않았다 | 통했다 |

위젯 쪽에서 본 `fetch`의 끝은 로그아웃이 통했는지와 따로 움직였다.

- 같은 출처로 부르면 다섯 부르는 법 모두 응답(204)을 읽었다.
- 다른 출처로 부르면, 끝점이 CORS 응답 머리를 내지 않을 때 `mode: "cors"`는 `redirect`가 `follow`든 `manual`이든 `TypeError`로 거절됐다. 그 칸에서도 쿠키가 실린 요청은 끝점에 닿았고 쿠키는 지워졌다. 끝점이 출처를 허용하면 응답(204)을 읽었고, `mode: "no-cors"`는 내용을 볼 수 없는 응답으로 끝났다.
- 어느 칸에서도 요청 앞에 `OPTIONS`가 오지 않았다(프로브의 `요약` 줄이 두 갈래를 합쳐 0칸으로 찍는다). 본문과 덧붙인 머리가 없는 POST라서라고 본다(어림. 본문이나 머리를 더한 요청과 견주지 않았다).

### 끝점이 303으로 답하며 그 응답에 지우는 `Set-Cookie`를 실을 때 (덤 갈래)

같은 자리 일곱과 `SameSite` 셋에서, `mode`와 끝점의 CORS 응답 머리의 짝 셋을 `redirect`의 두 값으로 봤다. 아래 표는 명세가 고른 부르는 법(`mode: "cors"`, `redirect: "manual"`)의 두 칸(끝점이 CORS 응답 머리를 내지 않는 것과 출처를 허용하는 것)이다. 두 칸은 자리와 `SameSite`마다 같은 결과를 냈고, 모든 칸에서 요청이 끝점에 닿았으며 브라우저가 다음 주소를 부르지 않았다.

| 위젯이 도는 자리 | `SameSite=Lax` | `SameSite=Strict` | `SameSite=None` |
|---|---|---|---|
| 페이지 안 방식, 같은 출처의 주소 | 통했다 | 통했다 | 통했다 |
| 페이지 안 방식, 등록 도메인이 같은 다른 출처의 주소 | 통했다 | 통했다 | 통했다 |
| 페이지 안 방식, 등록 도메인이 다른 주소 | 통하지 않았다 | 통하지 않았다 | 통했다 |
| iframe 방식, 위젯의 출처가 사이트와 등록 도메인이 같다 | 통했다 | 통했다 | 통했다 |
| iframe 방식, 위젯의 출처가 사이트와 등록 도메인이 다르다 | 통하지 않았다 | 통하지 않았다 | 통했다 |
| URL 방식, 위젯의 출처가 사이트와 등록 도메인이 같다 | 통했다 | 통했다 | 통했다 |
| URL 방식, 위젯의 출처가 사이트와 등록 도메인이 다르다 | 통하지 않았다 | 통하지 않았다 | 통했다 |

나머지 칸에서 본 것이다(프로브의 `요약` 줄 둘과 칸마다 찍은 줄).

- **요청이 끝점에 닿지 않은 칸**은 `mode: "no-cors"`에 `redirect: "manual"`을 함께 준 칸이고, 다른 출처로 부르는 자리 여섯의 `SameSite` 셋 모두에서 그랬다(`fetch`가 `TypeError`로 거절됐다). 같은 출처로 부르는 자리에서는 그 짝도 끝점에 닿았다.
- **브라우저가 다음 주소를 부른 칸**은 모두 `redirect: "follow"`다. 같은 출처로 부르는 자리에서는 짝 셋 모두 불렀다. 다른 출처로 부르는 자리에서는 `mode: "no-cors"`와 끝점이 출처를 허용하는 `mode: "cors"`가 불렀고, 끝점이 CORS 응답 머리를 내지 않는 `mode: "cors"`는 303 응답에서 `fetch`가 거절되어 부르지 않았다.
- 고른 부르는 법의 `fetch`는 같은 출처에서 내용을 볼 수 없는 리다이렉트 응답(`opaqueredirect`)으로 끝났다. 다른 출처에서는 끝점이 출처를 허용하면 같은 응답으로 끝났고, CORS 응답 머리를 내지 않으면 `TypeError`로 거절됐다. 거절된 칸에서도 쿠키가 실린 요청은 끝점에 닿았고 쿠키는 지워졌다.

## 결과를 본 뒤 바꾼 판정 기준

첫 판은 칸마다 "이 회차의 POST가 끝점에 정확히 한 번 닿았다"가 없으면 측정이 아니라고 셌다. 첫 실행에서 덤 갈래의 한 칸(iframe 방식, `mode: "no-cors"`, `redirect: "manual"`)이 그 표지 없이 걸렸고, 원본 기록에서 그 회차의 `fetch`가 `TypeError`로 거절됐고 끝점에 닿은 요청이 없다는 것을 봤다. 브라우저가 그 조합의 요청을 보내지 않는다는 것이 재야 할 사실이라, 덤 갈래에서만 기준을 바꿨다. 끝점에 닿지 않은 `manual` 칸은 같은 자리와 `SameSite`와 부르는 법의 `follow` 칸이 끝점에 닿았고 `fetch`가 거절로 끝났을 때 "닿지 않았다"는 측정으로 센다. 주소가 틀렸거나 서버가 죽어 닿지 않은 것이라면 `follow` 칸도 닿지 않기 때문이다. 본 갈래의 기준은 바꾸지 않았다.

같은 날 셀프 리뷰 뒤에 재는 칸을 넓혔다. 판정 기준은 그대로다. 첫 판은 자리 여섯, 부르는 법 셋(모두 `redirect: "follow"`)이었고 덤 갈래는 자리 둘과 `SameSite=Lax`뿐이어서, 명세가 고른 부르는 법(`mode: "cors"`, `redirect: "manual"`)은 덤 갈래의 두 칸에서만 쟀다. 넓힌 판은 그 부르는 법을 본 갈래에 더하고(부르는 법 다섯), 페이지 안 방식에서 등록 도메인이 다른 주소를 부르는 자리를 더했으며(자리 일곱), 덤 갈래를 같은 자리 일곱과 `SameSite` 셋으로 넓혔다. 첫 판이 잰 62칸(본 갈래 54칸, 덤 갈래 8칸)은 넓힌 판에서 모두 같은 값으로 다시 났다(손으로 봤다. 넓히기 전에 떠 둔 `expected.json`의 사본과 넓힌 뒤의 것을 칸마다 `JSON.stringify`로 견주는 한 줄을 `node -e`로 돌렸고, 그 사본과 한 줄은 커밋하지 않았다).

## 읽는 법

- **통하는지를 정한 것은 쿠키가 요청에 실리느냐였고, 끝점의 CORS 응답 머리가 아니었다.** 같은 자리와 같은 `SameSite`에서 CORS 응답 머리만 다른 칸이 모두 같은 결과를 냈다. 쿠키가 다른 까닭으로 사라진 것이 아니라는 것은 대조 둘이 가른다. 로그아웃을 부르지 않은 회차에서는 새 탭의 요청에 쿠키가 실렸고, 등록 도메인이 다른 자리의 `Lax`와 `Strict` 칸에서는 로그아웃을 불렀는데도 쿠키가 남았다.
- **잰 일곱 자리에서 `Lax`와 `Strict` 쿠키가 실린 자리와 빠진 자리는 요청을 보낸 문서의 출처와 로그아웃 주소의 출처가 같은 등록 도메인 아래인지로 갈렸다.** 끝점이 받은 `Sec-Fetch-Site`가 `cross-site`인 세 자리에서만 빠졌다(위 표). 프로브가 견준 축은 그 둘이다. 페이지 안 방식의 세 자리는 로그아웃 주소를 바꿔 가며 봤고, iframe 방식과 URL 방식의 네 자리는 위젯의 출처를 바꿔 가며 봤다. iframe 방식의 등록 도메인이 다른 자리는 맨 위 페이지가 로그아웃 주소와 같은 출처인데도 쿠키가 빠졌으므로, 맨 위 페이지와 로그아웃 주소의 관계만으로 갈리는 것은 아니다. 요청을 보낸 문서와 그것을 담은 맨 위 페이지가 둘 다 같은 등록 도메인 아래여야 하는지는 가르지 않았다. iframe 방식과 URL 방식에서 로그아웃 주소는 늘 사이트의 페이지와 같은 출처였기 때문이다(아래 "재지 못한 것").
- **ADR 0061 결정 "로그아웃"의 "끝점이 출처를 허용할 때만 통한다"는 CORS 응답 머리의 뜻으로는 맞지 않았다.** 위젯이 응답을 읽지 않고 토큰을 다시 물어 판정하는 한(그 결정이 정한 방법이다) 끝점이 CORS 응답 머리를 낼 필요가 없다. 이 프로브의 끝점은 어떤 `Origin`의 요청도 받았다. 사이트의 끝점이 `Origin`이나 `Sec-Fetch-Site`를 보고 요청을 거절하면 통하지 않을 것이고(어림, 그런 끝점은 흉내 내지 않았다), 그때 끝점이 받는 `Origin`은 페이지 안 방식에서는 페이지의 출처, iframe 방식과 URL 방식에서는 위젯의 출처다(위 표, 쟀다).
- **같은 ADR의 "같은 등록 도메인 아래에 있을 때만 통한다"는 `SameSite=None` 쿠키에는 맞지 않았다.** 등록 도메인이 다른 세 자리에서 `SameSite=None` 쿠키는 실렸고 지워졌다. 다만 이것은 이 Chromium 빌드의 기본 프로필에서의 결과다. 서드파티 쿠키를 막는 설정이나 브라우저에서는 실리지 않을 수 있다(어림, 재지 않았다). `Lax`와 `Strict`에는 그 문장이 맞았다.
- **명세가 고른 부르는 법은 견준 다른 부르는 법과 같은 자리에서 통했고, 끝점이 303으로 답해도 다음 주소를 부르지 않았다.** `mode: "no-cors"`에 `redirect: "manual"`을 함께 주면 다른 출처로는 요청이 나가지 않았다. 그 칸은 같은 주소의 `follow` 회차가 끝점에 닿은 것을 보고서야 측정으로 셌다.

## 재지 못한 것

- Firefox와 WebKit. Playwright 1.63.0이 찾는 빌드(`firefox-1543`, `webkit-2359`)가 이 PC에 없다(있는 것은 `firefox-1509`, `webkit-2248`이다). 내려받지 않았다. 등록 도메인이 다른 자리의 결과는 엔진의 서드파티 쿠키 정책에 달려 있어 엔진마다 다를 수 있다(어림).
- 제품 브라우저(Chrome, Safari, 휴대폰의 브라우저)와 사람이 바꾼 쿠키 설정. 잰 것은 Playwright의 Chromium headless shell 하나다.
- iframe 방식과 URL 방식에서 로그아웃 주소가 사이트의 페이지와 다른 출처인 자리(로그인을 다른 주소에 둔 사이트가 그 두 방식을 쓰는 경우). 그 두 방식의 네 자리는 로그아웃 주소가 사이트의 페이지와 같은 출처다.
- `Domain`을 적은 쿠키, `Partitioned` 쿠키, `__Host-` 접두 쿠키. 쿠키는 `Domain` 없이 `Secure; HttpOnly; Path=/`로만 심었다.
- 요청의 `Origin`이나 `Sec-Fetch-Site`를 보고 거절하는 끝점, CSRF 토큰을 요구하는 끝점. 프로브의 끝점은 모두 받는다.
- GET으로 부르는 로그아웃, 본문이나 덧붙인 머리가 있는 요청, 평문 `http`.
- 로그인 서버에서도 함께 로그아웃하는 방식(끝점이 로그인 서버의 주소로 넘기는 경우). 덤 갈래의 다음 주소는 같은 서버의 `/after`이고, 다음 주소가 다른 출처인 경우는 보지 않았다.
- 이름 다섯은 `.test` 아래다. 브라우저가 그것을 뜻한 대로 같은 등록 도메인과 다른 등록 도메인으로 읽었다는 것은 칸마다 `Sec-Fetch-Site`로 봤다.
