# pilot-portal 명세: 위젯을 담는 질문 페이지가 고지를 확인한 브라우저에 익명 사이트 토큰을 낸다

Status: ready-for-agent

슬라이스 7(`pilot-portal`). 설계는 설계 인터뷰(일지 2026-11-09-1410)와 ADR 0050이, 화면은 `/ui-design pilot-portal`(일지 2026-11-09-1839, 화면은 `.scratch/pilot-portal/design/`, 표는 그 `README.md`)이 정했고, 이 명세는 그 결정을 바꾸지 않고 이름·끝점·설정의 칸·문구·시험을 채운다. 명세를 쓰기 전에 사람에게 물은 다섯(화면이 근거 문서와 다른 자리 넷과 이음매)의 답은 일지 2026-11-09-2258에 글자 그대로 있다. 이 명세는 `/to-spec pilot-portal`로 새 세션에서 썼고 설계 인터뷰를 다시 열지 않았다. 용어는 `CONTEXT.md`의 질문 페이지, 질문 페이지 설정, 사이트, 사이트 파일, 사이트 토큰, 보증 모드, 익명 모드, 로그인 모드, 익명 식별자, 익명 주체, 고지, 고지 확인, 위젯, 최종 사용자, 운영자, 테마, 모드, 밀도, 요청을 따른다. 화면에 보이는 글은 "요청" 대신 "질문"을 쓴다(아래 "위젯 문구"). "코드를 읽었다"는 이 브랜치의 기준 커밋 `9d789569`(pilot-portal 화면을 들인 origin/main)의 코드와, 이 PC의 node 24.19.0과 pnpm 11.24.0, `web/` 워크스페이스의 pnpm이 설치한 typescript 5.9.3, next 16.3.6, smol-toml 1.9.1, tailwindcss 4.3.3이다(판은 프로브가 시작 때 각 패키지의 `package.json`에서 읽어 찍는다). 프로브는 이 PC(Windows 10)에서만 돌렸고 배포 이미지의 Linux에서는 재지 않았다.

**넘겨받은 것은 열여섯이다.** (1) 앱과 서버. `web/apps/` 아래 앱 하나이고 표준 라이브러리 `node:http` 서버 하나가 페이지·끝점·정적 파일을 내며 무상태다. `127.0.0.1`과 `::1`에서만 듣고 TLS를 끝내는 프록시 뒤에 선다. `serve`를 부르지 않고 사이트 파일을 디스크에서 읽는다(ADR 0050 결정 "앱과 서버"). (2) 띄우기. node가 타입만 벗겨 `.ts`를 빌드 없이 돌리고 import는 확장자를 붙이며 빌드 단계와 `dist` 폴더가 없다. 워크스페이스 패키지도 node가 읽을 수 있는 꼴이어야 하고 그 조합은 명세 전의 프로브가 잰다(결정 "띄우기"). (3) 시작 인자는 질문 페이지 설정 TOML과 `serve`의 사이트 파일 둘이고, 설정은 사이트 여럿의 목록이며, 시작 때 두 파일을 대 보아 하나라도 어긋나면 뜨지 않는다. 두 파일은 시작 때 한 번 읽는다(결정 "시작 인자와 시작 검사"). (4) 경로. `/`는 `/portal/`로 302, `/portal/`이 페이지 하나, 사이트마다 `/portal/sites/<이름>/` 아래 상태·확인(POST)·토큰 끝점, `/portal/health`, 정적 파일, 그 밖은 404. 페이지는 고른 사이트를 질의 `?site=<이름>`에 남기고 사이트가 하나면 셀렉트 박스를 숨긴다(결정 "경로"). (5) 익명 식별자 쿠키. 확인 끝점이 UUID v4를 `HttpOnly`, `SameSite=Strict`, `Path=/portal/sites/<이름>`, 30일로 두고, `Origin`이 공개 출처와 같을 때만 내며, 꼴이 맞는 쿠키가 있으면 만료만 다시 적고, 토큰을 낼 때마다 만료를 다시 적으며, `Secure`는 공개 출처가 https일 때만 붙인다(결정 "익명 식별자 쿠키"). (6) 토큰. RS256, 헤더 `kid`, `iss`는 그 사이트의 발급자, `sub`는 `anon-<쿠키 UUID의 해시>`, `aud`는 사이트 파일의 그 사이트 `audience`, `exp`는 `iat`+120초. 키 하나로 모든 사이트에 서명한다(결정 "토큰"). (7) 키 만들기 명령 하나가 `node:crypto`로 RSA 2048 키 쌍을 만들어 개인 키를 PEM으로 쓰고 `[[sites.public_keys]]` 조각을 출력한다(결정 "키 만들기 명령"). (8) 페이지. 서버가 그린 HTML 하나에 사이트 목록과 공개 설정을 JSON 데이터 블록으로 싣고, 스크립트는 같은 출처의 파일이며, 상태 끝점에 물어 덮개를 그리고, 위젯은 페이지 안 방식(`<agent-os-widget>`과 같은 출처의 `/widget/element.js`, 속성 다섯, `tokenProvider`)이고, 사이트를 바꾸면 이동 없이 속성과 토큰 끝점을 바꿔 끼우며, 로그인 사이트는 위젯 없이 알림을, CSP는 `default-src 'none'`에 다섯을 `'self'`로 열고 `frame-ancestors 'none'`·`base-uri 'none'`을 더한다(결정 "페이지"). (9) 모양. 디자인 시스템의 토큰 CSS와 글꼴 CSS를 같은 출처에서 내어 쓰고, 화면은 명세 전에 그린 것을 가리킨다(결정 "모양과 화면"). (10) 기록에 쿠키 값과 토큰을 싣지 않는다(결정 "기록"). (11) 함께 쓰는 코드. 사이트 파일 읽기와 e2e 준비(중계, 픽스처 플러그인, `serve` 띄우기)를 워크스페이스 패키지로 옮기고 위젯이 그것을 쓰게 고치며, 중계는 상류 셋을 받는다(결정 "함께 쓰는 코드"). (12) 질문 페이지는 빈도 제한을 두지 않는다(결정 "빈도 제한"). (13) 시험. Vitest의 목록과 Playwright e2e의 목록, 실제 모델 e2e 하나, 기능 계획의 수락 셋(결정 "테스트"). (14) 화면. 페이지 머리는 띠에 셀렉트와 다크 모드 스위치만(갈래 1 안 2), 둘 다 사이트의 비활성 로그인 단추는 위젯 바로 위(갈래 2 안 1), 완성 화면 35개(디자인 `README.md`의 표). (15) 쿠키 꼴 검사만 두고 서명을 두지 않으며 `__Host-` 접두를 쓰지 않는다. 질문 페이지의 공개 출처는 믿을 수 없는 하위 도메인이 없는 도메인에 둔다는 배치 요건이다(ADR 0050 Consequences "위젯은 바뀌지 않는다"). (16) 전역 `fetch` 금지가 질문 페이지의 스크립트에도 걸리고 Next 서버 파일 이름 넷을 피한다(Consequences "전역 `fetch` 금지"). ADR이 명세에 넘긴 자리(폴더 이름, 끝점 이름, 패키지의 이름과 수, 설정의 칸 이름, 키 명령의 이름, 마커 이름, 로그인 사이트 끝점의 상태 코드와 문구, `Origin` 거절의 상태 코드, 상태 끝점의 응답 모양, 전역 `fetch` 금지를 푸는 길, `Secure`일 때의 쿠키 이름과 접두)는 아래 절들이 정한다.

**사용자가 고른 것은 다섯이다**(일지 2026-11-09-2258 "사람에게 물은 것"). 페이지 뿌리의 밀도는 보통(`data-density="regular"`. 넓은 창에서도 사이트 상자·덮개 단추·고지 글이 위젯 안 글자와 같은 크기다). 라이트 기본 화면은 그림 그대로(소개가 든 첫 화면). 입력창 이름은 화면이 "질문", 개념어가 "요청"(용어집의 요청 항목에 단서를 단다). 둘 다 사이트의 비활성 로그인 단추 곁은 알림 부품이 아니라 글 한 줄(ADR 0050의 그 문장을 이력으로 고친다). 이음매는 Playwright e2e가 주, Vitest가 보조.

**스물여섯은 명세가 넘겨받은 것 안에서 스스로 정했고 각 절 제목의 괄호에 "명세가 정했다"로 표시한다(괄호는 한 항목을 더 잘게 나눠 적기도 한다).** 앱과 패키지의 이름과 수(`portal`, `site-file`, `e2e-stack`, `@agent-os/ui`의 서브패스 둘), `site-file` 패키지가 내는 모델의 칸, tsconfig의 모듈 해석, 페이지 스크립트를 `.ts`로 두고 시작 때 벗기는 길, 토큰 CSS를 시작 때 지어 메모리에서 내는 길, 글꼴을 패키지 파일에서 바로 내는 길, 설정의 칸 이름과 선택·필수·기본값, 기본 고지 글과 쿠키 문장이 늘 끝에 붙는 것, 끝점 이름과 응답 모양, 상태 코드 셋(로그인 사이트 403, `Origin` 403, 미확인 401의 본문), 쿠키 이름 하나와 같은 이름이 여럿일 때, 토큰 응답의 형식, 키 명령의 이름과 인자, 시작 진단의 모양과 시작 로그, 데이터 블록의 모양과 상태를 묻는 시점, 확인 뒤 포커스의 자리와 접근성 역할, 다크 모드 스위치, 페이지 CSS의 꼴(접두 클래스, 인라인 SVG 아이콘, 위젯 자리 크기), 위젯 문구 넷과 TextField의 이름표 숨김, 중계의 셋째 상류와 e2e 준비 패키지의 내용, HTTP 요청 처리기를 순수 함수로 두는 것, 전역 `fetch` 금지를 푸는 길(페이지 스크립트 파일 하나의 ESLint 블록), 고칠 자리의 묶음, Vitest와 e2e의 사례, e2e의 사이트 넷과 다른 출처 페이지와 사이트 하나의 둘째 인스턴스와 CI 잡 이름, 실제 모델 e2e의 마커 이름.

**이력은 셋이다.** ADR 0050의 2026-11-09 이력 "띄우기의 어림을 잰 값으로 바꾸고 토큰 CSS와 페이지 스크립트는 시작 때 짓는다"와 "둘 다 사이트의 비활성 로그인 단추 곁은 알림이 아니라 글 한 줄이다", 2026-11-10 이력 "짧은 고지는 위젯이 보일 때만 보인다"(셀프 리뷰가 본문과 명세의 어긋남을 잡아 더했다). 셋 다 이 명세와 같은 커밋에서 초안을 쓰고 사용자가 승인했다(작업 규약 5, 일지 2026-11-09-2258의 "승인"). 첫째는 결정 "띄우기"의 "재기 전에는 어림이다"에, 둘째는 결정 "페이지"의 "같은 알림이 붙은 비활성 로그인 단추를 둔다"에, 셋째는 같은 결정의 "짧은 고지는 위젯 곁에 늘 보인다"에 포인터를 단다(`.claude/rules/adr.md`). 같은 편집에서 첫 단락의 일반 명사 "포털"(용어집이 피하는 말)을 "사이트"로, Consequences의 "포털 호스트"를 "질문 페이지의 호스트"로 고쳤고 그것은 결정이 아니라 낱말이라 첫 이력에 한 줄로 적었다. 그 고침도 같은 승인에서 함께 물었다.

**거부한 안은 서른여덟이고 각 절의 "거부한 안:" 표시에 있다.**

측정은 `.scratch/pilot-portal/probes/node_ts_workspace.py`(여섯 묶음, 스물네 회차. 2026-11-10에 셀프 리뷰를 받아 회차 넷을 더했다. 결과와 근거의 종류는 그 `README.md`)다. 아래에서 "쟀다"는 그 프로브가 다시 내는 것, "손으로 봤다"는 명령과 함께 적은 것, "코드를 읽었다"는 기준 커밋의 코드, "어림"은 재지 않은 것이다(`docs/agents/issue-tracker.md` 프로브와 근거).

(2026-11-10 명세 검토와 to-tickets: 검토(`spec-reviewer`)는 막는 문제 없이 고칠 것 열넷과 문구 열둘을 냈다. 고칠 것은 결정이 빈 자리 셋(위젯 자리의 그림자, 시작 때 토큰 CSS를 짓는 길의 의존, 새 패키지 둘의 모듈 해석), 묶음 사이의 막힘과 묶음의 크기, 빠졌거나 어떤 구현에서도 초록일 수 있는 시험 사례, 셈이 정해지지 않은 자리("여섯 갈래", 넓은 창 대 보기), 디자인 시스템 부품과 아이콘의 수, 피할 폴더 이름, 옮기는 파일의 참조와 루프백 주석, Linux에서 재지 않은 것이다. 보고의 문장은 그대로 옮기지 않았다. 본 세션이 코드를 읽어 대 본 뒤 각 절에 같은 머리의 주석으로 적었다(일지 2026-11-10-0330). 옛 문장은 지우지 않고 주석이 바로잡는다. 서두의 수는 이렇게 바뀐다. **사용자가 고른 것은 여섯이다.** 여섯째는 묶음을 티켓 아홉으로 나누는 것이다("고칠 자리의 묶음"의 주석. 고른 라벨과 설명의 원문은 일지 2026-11-10-0330의 "분할"). 명세가 정한 것은 스물여섯에 열둘이 더해져 서른여덟이다(그림자의 모양, `@agent-os/ui`의 `tailwindcss`를 실행 의존으로, 새 패키지 둘의 `nodenext`, 디자인 시스템 부품 셋을 HTML로 옮기는 것과 아이콘 다섯, 피할 폴더 이름, 사이트 파일 대조 여섯 갈래의 이름, `portal.host` 줄의 꼴, `fetch` 예외의 범위, 글꼴 파일의 `ETag`, 실제 모델 e2e의 사이트, 넓은 창 대 보기의 산출, Linux 확인의 자리). 이력은 셋 그대로다(이 검토는 ADR 0050을 고치지 않는다). 거부한 안은 서른여덟에 여덟이 더해져 마흔여섯이다(그림자의 둘, 의존의 하나, 패키지 해석의 하나, Linux 프로브의 하나, `fetch` 예외의 하나, 분할의 둘). 이야기 16의 "첫 티켓 하나"는 티켓 둘(01, 02)로 바뀐다("고칠 자리의 묶음"의 주석).)

## Problem Statement

최종 사용자 경로는 사이트가 RS256으로 서명한 사이트 토큰만 받는다(ADR 0023). 공개 데모(public-demo)에도 배포 환경에도 위젯을 붙일 사이트나 토큰을 서명할 서버가 없을 수 있어, 위젯을 보여 주고 질문해 볼 길이 없다. 그리고 사이트마다 위젯의 설정(에이전트, 제목, 소개, 테마, 밝음)과 보증 모드가 다를 수 있는데, 그 설정으로 그린 위젯을 골라 보고 질문해 볼 자리가 없다. ADR 0050은 이 저장소가 함께 내는 질문 페이지 하나가 사이트 여럿을 담고, 고지를 확인한 브라우저의 익명 식별자로 사이트 토큰을 내기로 했다. 이 명세는 그 페이지를 만들 수 있게 이름·끝점·설정·문구·시험을 정한다.

## Solution

`web/apps/portal`에 `node:http` 서버 하나를 둔다. 서버는 질문 페이지 설정(사이트 여럿의 목록)과 `serve`의 사이트 파일을 시작 때 읽어 대 보고, 어긋나면 뜨지 않는다. `/portal/`이 페이지 하나이고, 셀렉트 박스로 고른 사이트의 설정으로 `<agent-os-widget>`을 그린다. 처음 온 브라우저는 그 사이트의 고지 전문과 "확인하고 질문하기" 단추가 위젯을 덮은 덮개를 보고, 단추를 누르면 확인 끝점이 그 사이트 경로의 익명 식별자 쿠키를 주며, 위젯이 요청마다 부르는 토큰 끝점이 그 식별자로 120초짜리 토큰을 그 사이트의 발급자로 서명해 낸다. 보증 모드가 로그인인 사이트는 위젯 대신 "아직 제공하지 않는다"는 알림을, 둘 다인 사이트는 익명 흐름 위에 비활성 로그인 단추와 글 한 줄을 둔다. 페이지의 모양은 디자인 시스템의 토큰 CSS와 글꼴을 같은 출처에서 내어 쓰고, 페이지 스크립트와 토큰 CSS는 서버가 시작 때 지어 메모리에서 낸다. 사이트 파일 읽기와 e2e 준비 코드는 워크스페이스 패키지로 옮겨 위젯과 나눠 쓴다. 위젯의 입력창 문구를 "질문"으로 바꾸고 디자인 시스템의 TextField에 이름표를 화면에서만 숨기는 길을 더한다.

## User Stories

1. As a 최종 사용자, I want 로그인 없이 질문 페이지를 열어 고지를 한 번 확인한 뒤 바로 질문하고 싶다. 그래야 계정 없이 에이전트를 써 볼 수 있다.
2. As a 최종 사용자, I want 같은 브라우저로 다시 와도 고지를 다시 확인하지 않고 이어서 질문하고 싶다. 그래야 올 때마다 전문을 읽지 않는다.
3. As a 최종 사용자, I want 질문하기 전에 무엇이 기록되고 어디로 보내지는지, 쿠키를 둔다는 것을 읽고 싶다. 그래야 개인정보를 넣지 않을 수 있다.
4. As a 최종 사용자, I want 사이트가 여럿일 때 셀렉트 박스로 골라 그 사이트의 위젯을 보고 싶다. 그래야 사이트마다 다른 설정을 한 페이지에서 본다.
5. As a 최종 사용자, I want 사이트를 바꾸면 새 대화가 시작된다는 것을 알고 싶다. 그래야 앞 대화가 사라진 까닭을 안다.
6. As a 최종 사용자, I want 로그인이 필요한 사이트에서는 왜 질문할 수 없는지 글로 보고 싶다. 그래야 빈 화면이나 눌리지 않는 단추만 보지 않는다.
7. As a 최종 사용자, I want 다크 모드로 바꿔 보고 싶다. 그래야 내 화면 설정에서 위젯이 어떻게 보이는지 본다.
8. As a 화면 읽기 프로그램을 쓰는 최종 사용자, I want 덮개가 뜰 때 포커스가 멋대로 옮겨지지 않고, 확인한 뒤에는 위젯으로 가며, 사이트를 바꾼 뒤의 안내가 한 번 읽히기를 바란다. 그래야 지금 어디에 있는지 놓치지 않는다.
9. As a 질문 페이지를 띄우는 운영자, I want 설정 파일 하나와 `serve`의 사이트 파일로 페이지를 띄우고, 두 파일이 어긋나면 시작에서 어느 칸이 틀렸는지 듣고 싶다. 그래야 첫 질문이 401로 거절될 때야 어긋남을 알지 않는다.
10. As a 질문 페이지를 띄우는 운영자, I want 명령 하나로 서명 키를 만들고 사이트 파일에 붙일 공개 키 조각을 받고 싶다. 그래야 PEM을 손으로 다듬지 않는다.
11. As a 질문 페이지를 띄우는 운영자, I want 시작 로그와 요청 처리에 쿠키 값과 토큰이 남지 않기를 바란다. 그래야 로그를 모아도 익명 주체가 토큰을 받는 열쇠(쿠키 값)가 새지 않는다.
12. As a 운영자, I want 트레이스와 관리 화면에서 익명 주체를 `anon-` 접두로 바로 알아보고 싶다. 그래야 로그인한 사람의 실행과 가른다.
13. As a public-demo 설계자, I want 사이트 하나만 적은 설정으로 셀렉트 박스 없는 페이지를 얻고, 고지 글과 보고서 링크를 설정으로 주고 싶다. 그래야 공개 데모가 새 화면을 만들지 않는다.
14. As a 위젯 개발자, I want 사이트 파일 읽기와 e2e 준비 코드를 질문 페이지와 한 패키지로 나눠 쓰고 싶다. 그래야 같은 코드의 셋째 사본이 생기지 않는다.
15. As a 저장소 기여자, I want 질문 페이지의 코드가 다른 두 앱처럼 `pnpm -C web verify`의 린트·타입 검사·Vitest를 지나고 e2e가 CI에서 돌기를 바란다. 그래야 새 앱이 게이트 밖에 서지 않는다.
16. As a 리뷰어, I want 패키지를 뽑는 변경이 첫 티켓 하나에 모여 다른 티켓이 그 뒤에 서기를 바란다. 그래야 위젯 빌드와 위젯 e2e가 한 커밋에서 함께 바뀐다.

## Implementation Decisions

### 앱과 패키지 (넘겨받았다. 이름과 수, `site-file`이 내는 모델의 칸, 디자인 시스템 패키지의 서브패스 둘은 명세가 정했다. 쟀다)

- 질문 페이지 앱은 `web/apps/portal`(`@agent-os/portal`)이다. 코드 이름과 경로에서만 쓰는 "portal"은 용어집이 허용한 자리다(`CONTEXT.md` 질문 페이지의 _Avoid_). 사람에게 보이는 글에는 "질문 페이지"를 쓴다.
- 패키지는 둘을 새로 뽑는다. `web/packages/site-file`(`@agent-os/site-file`)은 위젯 빌드의 사이트 파일 읽기(허용 출처의 표기 규칙 포함)를 옮긴 것이고 smol-toml을 제 의존성으로 든다. 읽은 사이트 파일은 사이트마다 발급자, `audience`, 열 에이전트, 허용 출처, 공개 키(`kid`, `pem`), 요청 글자 수 상한을 든 모델로 내고, 위젯 빌드는 그 가운데 합친 허용 출처와 가장 작은 요청 글자 수만 쓴다(지금 위젯의 읽기는 칸의 모양은 모두 판정하되 값은 그 둘만 낸다. 코드를 읽었다). 질문 페이지의 시작 검사가 나머지 칸을 쓴다. 위젯의 `next.config.ts`가 이것을 쓰게 고친다. `web/packages/e2e-stack`(`@agent-os/e2e-stack`)은 위젯 e2e의 중계, 픽스처 플러그인(저장소 플러그인 복사 포함), `serve` 띄우기와 빈 포트·기다리기·끄기 도우미, 사이트 키와 토큰 서명(`token.ts`)을 옮긴 것이고 두 앱의 devDependency다. 위젯의 사이트 서버(`site.ts`, `element-site.ts`)는 위젯만의 시험 페이지라 옮기지 않는다. 관리 화면 e2e의 사본은 그대로 둔다(ADR 0050).
- `@agent-os/ui`에 서브패스 둘을 연다. `./themes`는 `THEMES`·`DEFAULT_THEME`·`MODES`·`DENSITIES`를 내는 `themes.ts`이고, `./fonts`는 위젯의 `tools/fonts.ts`(글꼴 CSS가 가리키는 woff2 목록, `@font-face` 목록, 복사)와 그 `FontFaceSource` 타입을 옮긴 node 쪽 도우미다. 위젯의 시작 래퍼와 페이지 안 번들이 그것을 쓰게 고친다. 두 파일 모두 `.tsx`를 거치지 않고 상대 import에 확장자가 있다.
- 패키지 셋의 진입점과 그 안의 상대 import는 모두 확장자를 붙인다. 쟀다(`node_ts_workspace.py`의 `strip_api_client_root`가 확장자 없는 지정자에서 `ERR_MODULE_NOT_FOUND`, `strip_themes_file`이 확장자 있는 지정자로 읽힘). 패키지 이름으로 읽히는 까닭은 node가 pnpm 링크를 실제 경로로 풀어 그 파일이 `node_modules` 밖이기 때문이고(쟀다. 양성 대조 `strip_inside_node_modules`, 갈래 `strip_preserve_symlinks`), 그래서 질문 페이지를 띄우는 명령에 `--preserve-symlinks`를 넣지 않는다. 패키지의 의존성(smol-toml)은 그 패키지 폴더의 `node_modules` 링크를 거쳐 pnpm 스토어로 풀린다(`strip_package_dep`이 `openapi-fetch`를 pnpm 스토어의 실제 경로로 푼 것은 쟀고, 그 경로를 가리키는 링크가 `api-client` 패키지 폴더의 `node_modules`에 있는 것은 `ls -la`로 손으로 봤다. `site-file` 패키지 자신은 아직 없어 그 자리로는 재지 않았고 같은 길로 풀릴 것으로 본다. 어림). 위젯의 `next.config.ts`는 기본 길과 node 네이티브 길 모두에서 워크스페이스 패키지의 `.ts` 진입점과 `smol-toml`을 읽는다(쟀다, `next_config_*` 네 회차. 옮겨 갈 패키지가 아직 없어 `@agent-os/ui/contrast`가 그 자리의 대리다). 지금 그 파일의 `./tools/site-file.ts` import는 시작 래퍼의 `process.chdir`에 기대 맞는 것이고(쟀다, `next_config_legacy_other_cwd_decoy`), 패키지로 옮기면 그 가정이 사라진다.
- 질문 페이지의 파일 이름은 `route`, `middleware`, `proxy`, `instrumentation`을 피한다. ESLint의 Next 서버 파일 금지가 파일 이름 글롭으로 모든 앱에 걸린다(ADR 0050 Consequences).
- 거부한 안: 패키지 하나(`shared`)에 둘을 함께 둔다(시험 전용 코드가 운영 의존성이 된다. e2e 준비는 devDependency여야 한다). 거부한 안: 글꼴 도우미를 `site-file`이나 `e2e-stack`에 둔다(글꼴 파일의 주인은 디자인 시스템 패키지다). 거부한 안: `@agent-os/ui`의 루트 진입점을 node가 읽게 고친다(그 진입점은 확장자 없는 재내보냄에서 `ERR_MODULE_NOT_FOUND`로 먼저 막히고, 확장자를 적어도 `.tsx`는 `ERR_UNKNOWN_FILE_EXTENSION`이라 React 부품을 다시 내보내는 한 읽히지 않는다. 쟀다, `strip_root_index`·`strip_tsx_file`).

(2026-11-10 명세 검토: 셋을 더한다. 첫째, 질문 페이지 앱은 파일 이름 넷과 함께 ESLint 층 경계가 요소로 가르는 폴더 이름(`app`, `components/*`, `api/*`, `hooks/queries/*`, `types/*`, `stores`)도 피하고, 서버 코드는 그 밖의 폴더(예: `server/`)에 둔다(명세가 정했다). 층 경계는 그 폴더 패턴으로 요소를 가르고(`web/eslint.config.mjs` 184~201줄을 읽었다), `app` 폴더의 파일이 `node:http`를 import하면 `boundaries/dependencies`로 빨갛고 같은 내용을 `server/`에 두면 지난다(검토가 임시 스크립트로 손으로 봤다). 둘째, 옮기는 파일을 가리키는 살아 있는 참조는 아래 묶음 A가 든 셋(EMBED.md, README, `tech.md`)보다 많다. `src/agent_os/main.py`(319·521줄), `tests/test_main.py`(1902줄), `tests/fixtures/site_file/README.md`(두 언어가 함께 읽는 픽스처의 Node 쪽 경로), `tests/test_widget_llm.py`(`e2e/stack.ts`와 `e2e/env.ts`를 든다), `web/apps/admin/e2e/stack.ts`의 머리 주석, 위젯의 `lib/build.ts`·`lib/build.test.ts`·`next.config.test.ts`·`element/fonts.ts`·`tools/start.ts`·`tools/element.test.ts`, 저장소 `.gitignore`의 글꼴 폴더 주석(`web/apps/widget/tools/fonts.ts`를 든다) 등이다(grep으로 찾았다. 셀프 리뷰가 `.gitignore`를 더 찾았다). 이 목록은 닫힌 목록이 아니고, 패키지를 뽑는 티켓의 수용 기준은 옛 경로의 grep 잔존 0이다. 셋째, `FontFaceSource`는 위젯의 `tools/fonts.ts`가 아니라 `element/fonts.ts`에 있고(읽었다) 브라우저 쪽 코드가 쓴다. `./fonts`로 옮길 때 그 타입도 함께 옮기고 브라우저 쪽은 `import type`으로 읽는다. 새 서브패스 둘은 진입점 판정 스토리(`web/packages/ui/src/Entrypoints.stories.tsx`)와 node 풀이 시험(선례 `web/tools/contrast-module.test.ts`)에 더한다. 그러면 Further Notes의 `./themes` 어림이 늘 도는 판정이 된다. 패키지를 둘(사이트 파일과 서브패스, e2e 준비)로 나눠 뽑는 것은 "고칠 자리의 묶음"의 주석이다.)

### 띄우기와 타입 검사 (넘겨받았다. tsconfig의 해석, 페이지 스크립트의 길, 토큰 CSS와 글꼴을 내는 길은 명세가 정했다. 쟀다)

- 앱의 `start` 스크립트는 `node tools/start.ts --config <질문 페이지 설정> --site-file <사이트 파일>`이다. 두 인자는 필수이고 듣는 호스트와 포트는 설정에서 읽는다. 빌드 단계와 `dist` 폴더가 없고 앱 폴더에 산출을 쓰지 않는다.
- 앱의 tsconfig는 `web/tsconfig.base.json`을 extends 하고 `module`과 `moduleResolution`을 `nodenext`로, `allowImportingTsExtensions`와 `types: ["node"]`를 두며, 페이지 스크립트가 쓰는 DOM 라이브러리를 `lib`에 든다. `nodenext`와 `bundler` 둘 다 서고(쟀다, `tsc_*` 여섯 회차. 변이가 두 해석 모두에서 `TS2322`), `nodenext`를 고른 까닭은 node가 실제로 푸는 규칙(확장자 필수)을 타입 검사가 같이 강제하기 때문이다(쟀다. 확장자 없는 상대 import가 `nodenext`에서는 `TS2835`로 빨갛고 `bundler`에서는 지난다, `tsc_nodenext_extensionless`·`tsc_bundler_extensionless`). `pnpm -C web verify`의 `typecheck`가 워크스페이스 전체를 돌므로 새 앱과 패키지 둘은 그 안에 든다.
- 페이지 스크립트는 앱 안 `browser/` 폴더의 `.ts` 파일 하나다. 브라우저는 `.ts`를 읽지 못하므로 서버가 시작 때 `node:module`의 `stripTypeScriptTypes`(`strip` 모드)로 타입만 벗겨 메모리에 두고 `/portal/portal.js`로 낸다. 쟀다(`page_script_strip`: 벗긴 산출이 돌아 기대한 값을 내고 타입 주석이 남지 않으며 줄 수가 원본과 같다. `page_script_strip_enum`: 지울 수 없는 문법은 `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`로 거부된다). 잰 것은 그 둘(타입 별칭이 벗겨지고 `enum`이 거부된다)뿐이다. 벗기지 못하는 문법의 목록(`enum`, 런타임 코드가 있는 `namespace`, 매개변수 프로퍼티)과 TypeScript 5.8 이상에서 `erasableSyntaxOnly: true`를 두라는 권고는 Node 문서가 적는다(`nodejs.org/api/typescript.html`, 2026-11-10에 읽었다). 그래서 기준 tsconfig의 `erasableSyntaxOnly`를 지난 스크립트가 벗기기에서 막히지 않는 것은 문서로 아는 것이고 재지 않았다. 그 스크립트는 import와 export가 없는 고전 스크립트이고 전역에 이름을 두지 않게 함수 하나로 감싼다. node가 그 API를 처음 부를 때 stderr에 두 줄(`ExperimentalWarning: stripTypeScriptTypes is an experimental feature and might change at any time`와 그 아래 `--trace-warnings` 안내)을 찍는다(`node -e`로 손으로 봤다. 명령은 프로브 README). 그 줄을 끌지는 티켓이 정한다.
- 디자인 토큰 CSS는 서버가 시작 때 짓는다. `@agent-os/ui`의 `build`가 쓰는 둘째 명령(`tailwindcss -i <theme.css> -o <출력>`)을 Tailwind CLI로 돌려 결과를 메모리에 읽고 `/portal/theme.css`로 낸다(주석, 티켓 06의 구현: `-o`를 주지 않으면 CLI가 CSS를 표준 출력에 내므로 임시 폴더를 만들고 지우는 길은 두지 않았고, `server/assets.test.ts`의 "토큰 CSS 를 Tailwind CLI 로 지어 메모리에 읽는다"가 실제 CLI로 그 길을 단언한다). 작업 디렉터리는 `@agent-os/ui` 패키지 폴더다(그 자리에서 잰 것이다). 쟀다(`theme_css_build`: 지시문 4→0, 29,569바이트, 변수 167개, 화면 그림이 읽는 변수 27개 모두 선언, 실행마다 0.3~0.7초. `theme_css_build_child`: node 프로세스가 같은 명령을 `child_process`의 자식으로 띄워 산출을 메모리에 읽고 파일을 지운 것이 바로 돌린 것과 같은 29,569바이트다). 산출에는 토큰과 함께 `base` 레이어의 기본 초기화와 그 패키지 소스에서 긁은 유틸리티 클래스 122개가 든다(쟀다). 그래서 페이지 CSS는 그 유틸리티에 기대지 않는다(아래 "모양"). 앱은 `@tailwindcss/cli`와 `tailwindcss`를 `@agent-os/ui`와 같은 판으로 제 의존성에 든다.
- 글꼴은 복사하지 않고 패키지 파일에서 바로 낸다. `@agent-os/ui/fonts`의 목록으로 `/portal/fonts.css`(`@font-face` 386개. `url()`은 `/portal/fonts/<파일 이름>`)를 메모리에 짓고, `/portal/fonts/<파일 이름>`은 그 목록에 든 woff2 파일(386개, 5,853,912바이트)만 디스크에서 흘려보낸다. 목록 밖 이름은 404다. 쟀다(`fonts_files`. 위젯의 `tools/fonts.ts`를 그 자리에서 돌린 값이다. 옮겨 갈 자리인 그 패키지 안에서 `@agent-os/ui/fonts.css`가 자기 참조로 풀리는 것은 `fonts_css_self_reference`가 쟀고, 옮긴 도우미 파일 자체가 도는지는 재지 않았다. 어림). 글꼴 가족 이름은 글꼴 CSS의 것(`Noto Sans KR`, `Noto Sans Mono`) 그대로라 토큰 CSS의 `--sans`·`--mono`가 그것을 가리킨다.
- 거부한 안: 페이지 스크립트를 손으로 쓴 `.js`와 `@ts-check`로 둔다(타입 검사의 길이 둘이 되고 ESLint의 TypeScript 글롭 밖이다). 거부한 안: 페이지 스크립트를 esbuild로 묶는다(빌드 단계가 생긴다). 거부한 안: `@agent-os/ui`의 `build`가 내는 `dist/theme.css`에 기댄다(그 `dist`를 이미지 빌드와 e2e 준비가 먼저 만들어야 하고 ADR 0050이 `dist` 폴더를 거부했다). 거부한 안: 토큰만 뽑는 Tailwind 입력을 따로 둔다(재지 않았고, 유틸리티는 페이지 CSS가 쓰지 않으면 해가 없다). 거부한 안: 글꼴을 위젯처럼 앱 폴더로 복사한다(앱 폴더에 산출이 생기고 5.6MiB가 두 벌이 된다).

### 질문 페이지 설정 (넘겨받았다. 칸 이름과 선택·필수·기본값, 판과 모르는 칸의 거부, 기본 고지 글의 자리는 명세가 정했다)

- TOML이고 `schema_version = "1"`이 필수다(사이트 파일과 같은 규약). 모르는 칸은 거부한다. 읽는 데는 smol-toml을 쓴다.
- `[portal]` 표(공통). `public_origin`(필수. 질문 페이지의 공개 출처. 사이트 파일의 허용 출처와 같은 표기 규칙을 지나야 하고 `site-file` 패키지의 그 규칙으로 판정한다), `private_key`(필수. 개인 키 PEM 파일의 경로. 상대 경로는 설정 파일의 폴더 기준), `kid`(필수. 빈 글이 아니다), `host`(선택. 기본 `127.0.0.1`. `127.0.0.1`·`::1` 밖이면 구성 오류), `port`(필수. 1 이상 65535 이하의 정수).
- `[[sites]]` 표(사이트마다. 하나 이상이어야 하고 비어 있으면 구성 오류다). `name`(필수. 경로와 쿠키 경로에 쓰는 이름. 플러그인 이름과 같은 꼴 `^[a-z][a-z0-9-]{1,62}$`), `issuer`(필수. 사이트 파일의 항목을 고르는 열쇠), `agent`(필수. 에이전트 하나), `heading`(필수. 위젯 위쪽 띠와 셀렉트 항목과 페이지 제목에 쓴다), `intro`(선택. 없으면 위젯이 그 줄을 그리지 않는다), `theme`(선택. `THEMES`의 키. 기본 `nokcheong`), `mode`(선택. `light`·`dark`. 없으면 브라우저의 시스템 설정을 따른다. 위젯의 속성과 같은 규칙), `assurance`(필수. `anonymous`·`login`·`both`), `notice`(선택. 고지 글. 없으면 질문 페이지의 기본 글. 적었는데 비었거나 공백뿐이면 구성 오류다), `report_url`(선택. `http`·`https` 주소). 모양 칸 넷의 이름은 위젯의 임베드 속성 이름(`heading`, `intro`, `theme`, `mode`)과 같아 옮겨 적지 않고 그대로 속성에 싣는다.
- 고지 전문은 서버가 사이트마다 미리 짓는다. 사이트가 `notice`를 적었으면 그 글이 전문이고(빈 글이나 공백뿐인 글은 기본 글로 덮지 않고 시작 진단이 거부한다. 위 설정 절), 적지 않았으면 기본 글 세 문단("이 페이지에서 보낸 질문과 받은 출력은 기록되고, 출력을 만들기 위해 모델 API로 보내집니다." / "이 브라우저를 알아보기 위해 익명 식별자를 쿠키로 둡니다. 쿠키는 마지막으로 질문한 뒤 30일 동안 남습니다." / "이름, 연락처, 주민등록번호 같은 개인정보를 질문에 넣지 마세요.")이다. 둘째 문단(쿠키 문장)은 사이트가 글을 적어도 전문 끝에 늘 붙고, 그 안의 "30일"은 쿠키 수명 상수에서 그려 둘이 어긋나지 않는다. 짧은 고지는 "질문과 출력은 기록되고 모델 API로 보내집니다. 개인정보를 넣지 마세요."이고 사이트가 바꾸지 못한다(짧은 줄은 질문 페이지의 것이고 전문이 사이트의 것이다).
- 거부한 안: 모양 칸을 한국어 이름으로 짓는다(위젯 속성으로 옮겨 적는 표가 하나 생긴다). 거부한 안: `mode`를 필수로 한다(위젯의 기본값인 시스템 설정을 따르는 길이 막힌다). 거부한 안: 짧은 고지도 사이트가 적게 한다(전문과 두 벌이 되어 어긋날 수 있다). 거부한 안: 비었거나 공백뿐인 `notice`를 적지 않은 것과 같게 본다(설정의 실수가 기본 글로 조용히 덮인다. PR #504의 CodeRabbit이 빈 `notice`로 전문이 쿠키 문장만 남는 것을 짚었고, 덮기 대신 거부를 골랐다).

(2026-11-10 명세 검토: 뒤에 칸을 더할 때 `schema_version`을 올리는지는 이 명세가 정하지 않는다. 칸을 더하는 기능(portal-admin, widget-appearance)의 명세가 정하고, 두 기능 계획 본문의 "설계 인터뷰가 먼저 볼 것"에 그 물음을 적었다.)

### 시작 검사와 진단 (넘겨받았다. 진단의 모양과 시작 로그는 명세가 정했다)

- 시작 때 다음을 모두 보고 하나라도 어긋나면 뜨지 않는다. 설정의 모양(판, 모르는 칸, 필수 칸, 값의 꼴, `sites`가 하나 이상, 적힌 `notice`가 공백만이 아님, `theme`는 `THEMES`에, `mode`는 `MODES`에, `assurance`는 셋 가운데). 사이트 파일이 `site-file` 패키지의 판정을 지난다(모양 판정은 지금 위젯의 읽기와 같고 서버의 pydantic 모델과 같은 규칙이며, 읽어 내는 칸은 위 "앱과 패키지"대로 넓힌다). 발급자가 사이트 파일에 있다. 설정 안에서 `issuer`와 `name`이 겹치지 않는다(보증 모드와 상관없이). `agent`가 그 사이트의 열 에이전트에 든다. `public_origin`이 그 사이트의 허용 출처에 든다. 개인 키 파일이 읽히고 RSA 개인 키다(PKCS#8과 PKCS#1 둘 다 받는다). `kid`로 고른 그 사이트의 공개 키가 개인 키에서 난 공개 키와 같다(SPKI DER 바이트로 견준다). `host`가 루프백이다.
- 진단은 stderr에 `구성 오류:` 한 줄 뒤에 어긋난 자리마다 `<자리>: <까닭>` 한 줄이다. 자리는 `sites[1].agent`, `portal.public_origin` 꼴이고 까닭에 값(키의 글, 경로의 내용)은 싣지 않는다. 예외는 `portal.host` 하나다. 루프백 거절의 문구는 위젯 시작 래퍼의 것과 같은 꼴(`portal.host 는 루프백만 받는다(127.0.0.1, ::1). 받은 값: <값>`)이고 받은 값을 싣는다. 호스트 값은 비밀이 아니고 위젯 시작 래퍼도 싣는다. 관리 화면 시작 래퍼가 상류 주소의 진단에 값을 싣지 않는 것은 그 주소에 계정의 비밀번호가 실릴 수 있어서라 여기에는 해당하지 않는다(둘 다 코드를 읽었다). 종료 코드는 1이다.
- 두 파일과 키는 시작 때 한 번 읽는다. 운영 중에 바꾸면 다시 띄워야 한다(ADR 0050).
- 시작 로그는 stdout에 한 줄, `질문 페이지가 http://<host>:<port>/portal/ 에 섰다. 사이트 <N>개.`이다. `host`가 `::1`이면 주소의 호스트 자리는 대괄호로 감싼 `[::1]`이다(`http://[::1]:<port>/portal/`. IPv6 주소는 대괄호 없이는 URL의 호스트가 되지 않는다). 접근 로그는 남기지 않는다(접근 기록은 프록시의 몫이다). 쿠키 값과 토큰은 어떤 출력에도 싣지 않는다(ADR 0050 결정 "기록", 원칙 V의 연장).
- 거부한 안: 어긋남을 첫 것 하나만 알린다(사이트 파일 읽기는 문제를 모두 모아 알린다. 같은 규칙으로 간다). 거부한 안: 요청마다 한 줄씩 기록한다(쿠키·토큰이 섞일 길이 생기고 프록시가 이미 남긴다).

(2026-11-10 명세 검토: 셋을 정한다. 첫째, 아래 Vitest의 "사이트 파일 대조의 여섯 갈래"는 이 여섯이다(명세가 정했다). 사이트 파일이 `site-file` 패키지의 판정을 지나지 못한다, `issuer`가 사이트 파일에 없다, `agent`가 그 사이트의 열 에이전트 밖이다, `public_origin`이 그 사이트의 허용 출처 밖이다, `kid`가 그 사이트의 공개 키에 없다, `kid`로 고른 공개 키가 개인 키에서 난 공개 키와 다르다. 설정 안의 겹침(`issuer`, `name`), 개인 키를 읽지 못하거나 RSA가 아닌 것, 루프백 밖 `host`는 설정의 갈래이고 Vitest가 따로 본다. 둘째, `portal.host` 줄도 다른 줄과 같은 `<자리>: <까닭>` 꼴인 `portal.host: 루프백만 받는다(127.0.0.1, ::1). 받은 값: <값>`이다(명세가 정했다). 위의 "위젯 시작 래퍼의 것과 같은 꼴"은 받은 값을 싣는다는 뜻으로 읽는다. 위젯 래퍼의 줄은 `--hostname 은 루프백만 받는다(…). 받은 값: …`이다(`web/apps/widget/tools/start.ts`를 읽었다). 셋째, 루프백 목록은 네 벌이 된다(`serve`의 `LOOPBACK_HOSTS`, 관리 화면 `tools/loopback.ts`, 위젯 `tools/start.ts`, 질문 페이지). `src/agent_os/main.py`의 `LOOPBACK_HOSTS` 위 주석, 관리 화면 `tools/loopback.ts`와 위젯 `tools/start.ts`의 머리 주석 셋이 "셋을 함께 고친다"고 적어(읽었다. 셀프 리뷰가 `main.py`의 주석을 더 찾았다), 질문 페이지를 처음 만드는 티켓이 그 주석을 넷으로 고친다(ADR 0050 결정 "앱과 서버").)

### 경로와 끝점 (넘겨받았다. 끝점 이름, 응답 모양, 상태 코드와 본문, 캐시 헤더는 명세가 정했다)

| 메서드와 경로 | 하는 일 | 응답 |
|---|---|---|
| `GET /` | 페이지로 넘긴다 | 302 `Location: /portal/`. 질의(`?site=…`)는 그대로 붙인다 |
| `GET /portal/` | 페이지 하나 | 200 `text/html; charset=utf-8`. 질의는 보지 않는다(스크립트가 읽는다) |
| `GET /portal/portal.js`, `/portal/portal.css`, `/portal/theme.css`, `/portal/fonts.css` | 페이지 스크립트, 페이지 CSS, 토큰 CSS, 글꼴 CSS | 200. 각각 `text/javascript`, `text/css`(`charset=utf-8`). 메모리의 글 |
| `GET /portal/fonts/<파일 이름>` | 글꼴 파일 | 200 `font/woff2`. 목록 밖 이름은 404 |
| `GET /portal/health` | 살아 있음 | 200 `application/json` `{"status":"ok"}` |
| `GET /portal/sites/<이름>/acknowledgement` | 그 사이트의 고지 확인 여부 | 200 `application/json` `{"acknowledged":true}` 또는 `{"acknowledged":false}`. 쿠키가 있고 꼴이 맞으면 참 |
| `POST /portal/sites/<이름>/acknowledgement` | 고지 확인. 쿠키를 낸다 | `Origin`이 없거나 `public_origin`과 다르면 403(쿠키 없음). 같으면 204와 `Set-Cookie`(쿠키가 없거나 꼴이 틀리면 새 UUID, 꼴이 맞으면 같은 값으로 만료만 다시). 본문은 읽지 않는다 |
| `POST /portal/sites/<이름>/token` | 사이트 토큰 | 쿠키가 있고 꼴이 맞으면 200 `text/plain; charset=utf-8`에 토큰 글 하나와 만료를 다시 적은 `Set-Cookie`. 없거나 꼴이 틀리면 401 `text/plain` "고지 확인이 필요합니다." |
| 그 밖 | | 모르는 사이트 이름과 모르는 경로는 404, 아는 경로의 다른 메서드는 405와 `Allow` |

- 보증 모드가 `login`인 사이트의 세 끝점은 메서드와 쿠키와 상관없이 403 `text/plain; charset=utf-8` "이 사이트는 로그인이 필요합니다. 로그인은 아직 제공하지 않습니다."다(페이지의 알림과 같은 글). `both`는 `anonymous`와 같다.
- 끝점 응답(`/portal/sites/…`, `/portal/health`)에는 `Cache-Control: no-store`를, 페이지와 정적 파일에는 `Cache-Control: no-cache`와 내용 해시의 `ETag`를 단다(조건부 요청에 304). 모든 응답에 `X-Content-Type-Options: nosniff`를 단다.
- 토큰 끝점은 `Origin`을 보지 않는다. 쿠키가 `SameSite=Strict`라 다른 사이트에서 일으킨 요청에는 쿠키가 실리지 않고, 쿠키 없는 요청은 401이다(ADR 0050 Consequences).
- 거부한 안: 토큰을 GET으로 낸다(브라우저와 중간 캐시가 저장할 수 있고, 만료를 다시 적는 쓰기가 든다). 거부한 안: 상태 끝점 대신 스크립트가 쿠키를 읽는다(`HttpOnly`라 읽지 못한다). 거부한 안: 로그인 사이트의 끝점을 404로 숨긴다(페이지가 보증 모드를 이미 보이고, 404는 모르는 이름과 섞인다). 거부한 안: 정적 파일에 긴 `max-age`를 둔다(파일 이름에 판이 없어 다시 띄운 뒤 옛 파일이 남는다). 거부한 안: `/portal`(끝 슬래시 없음)을 `/portal/`로 302한다(ADR 0050 결정 "경로"의 프록시 전달 규칙이 `= /`와 `/portal/` 둘뿐이라 운영에서 그 경로는 프록시의 404다. 시험 중계만 넘기면 운영과 시험이 갈린다).

(2026-11-10 명세 검토: 글꼴 파일의 `ETag`는 서버가 시작 때 목록의 파일마다 내용 해시로 짓는다. 순수 HTTP 요청 처리기는 글꼴 응답의 본문으로 파일 경로를 돌려주고, `node:http`에 거는 겉이 그 파일을 흘려보낸다(명세가 정했다). 다른 정적 파일과 페이지는 메모리의 글이라 본문이 그대로 글이다.)

### 익명 식별자 쿠키 (넘겨받았다. 쿠키 이름, 같은 이름이 여럿일 때, 접두 없음은 명세가 정했다)

- 이름은 사이트와 상관없이 `portal_anon` 하나다. 속성은 `HttpOnly; SameSite=Strict; Path=/portal/sites/<이름>; Max-Age=2592000`(30일)이고 `public_origin`이 `https`일 때만 `Secure`가 붙는다. 값은 소문자 UUID v4(36자)이고 그 꼴이 아니면 없는 것으로 본다. 경로가 사이트마다 다르므로 같은 이름으로도 사이트마다 다른 쿠키가 선다(브라우저는 쿠키를 이름·도메인·경로로 가른다. RFC 6265 5.3을 읽었다).
- 요청에 같은 이름의 쿠키가 둘 이상 실리면 첫 것을 쓴다. 브라우저는 경로가 긴 쿠키를 먼저 싣고, 경로 길이가 같으면 먼저 만들어진 쿠키를 먼저 싣는다(RFC 6265 5.4의 SHOULD. 읽었다, 재지 않았다). 그래서 상위 도메인에 `Path=/`나 더 짧은 경로로 심은 쿠키보다 그 사이트 경로의 쿠키가 먼저 오지만, 형제 도메인이 같은 경로로 먼저 심은 쿠키는 앞에 와 그 값이 쓰인다. 그 한계는 ADR 0050 Consequences("한계가 하나 더 있다")가 받아들인 것이고 배치 요건(위 (15))이 막는다.
- `__Host-` 접두는 `Path=/`를 요구해 사이트별 경로와 맞지 않고(ADR 0050), `__Secure-` 접두는 쓰지 않는다. 쓰면 `https` 운영과 `http` e2e에서 쿠키 이름이 달라져 e2e가 운영의 이름을 보지 못하고, 그 접두가 막는 것(같은 호스트의 평문 출처가 덮어쓰는 것)은 TLS만 듣는 프록시와 HSTS가 이미 막는다(ADR 0024).
- 거부한 안: 사이트별 쿠키 이름(`portal_anon_<이름>`)을 둔다(경로가 이미 가르고, 형제 도메인이 심는 쿠키는 이름으로 막지 못한다). 거부한 안: 같은 이름이 여럿이면 없는 것으로 본다(상위 도메인에 심은 쿠키 하나로 모든 확인이 막힌다).

### 토큰 (넘겨받았다. 응답 형식은 명세가 정했다)

- 헤더는 `{"alg":"RS256","typ":"JWT","kid":<설정의 kid>}`, 본문은 `iss`(그 사이트의 발급자), `sub`(`anon-<해시 32자>`. 쿠키 값의 글자 36자를 SHA-256에 넣어 소문자 16진으로 쓴 앞 32자이고 소금은 없다), `aud`(사이트 파일의 그 사이트 `audience`), `iat`(지금, 초), `exp`(`iat`+120)의 다섯이다. `nbf`는 넣지 않는다. 서명은 `node:crypto`의 RSA-SHA256이고 선례는 위젯 e2e의 `token.ts`(패키지로 옮긴다)다.
- 응답은 토큰 글 하나(`text/plain`)다. 페이지 스크립트의 `tokenProvider`가 그 글을 그대로 돌려준다(EMBED.md의 `tokenProvider` 꼴). 200이 아니면 던져 위젯이 "로그인 정보를 받지 못했습니다." 알림을 보인다(EMBED.md).
- 거부한 안: JSON 봉투로 낸다(`tokenProvider`가 문자열 하나를 돌려주면 되고 봉투를 풀 코드가 는다).

(2026-11-10 PR 봇 회차: `sub`를 쿠키 UUID 원문에서 그 해시로 바꾼다. 트레이스를 읽을 수 있는 사람이 원문을 쿠키로 심어 그 익명 주체의 토큰을 받고 멈춘 실행의 승인을 대신 내는 길을 닫는다. 사용자가 골랐고 ADR 0050 이력 2026-11-10 "익명 주체의 이름은 쿠키 값의 해시다"가 결정을 기록한다. 해시는 쿠키 값 36자 글자의 SHA-256을 소문자 16진으로 쓴 앞 32자이고 소금이 없다. 같은 쿠키가 같은 주체로 이어져야 하기 때문이다. 시험은 쿠키 값에서 같은 해시를 스스로 계산해 대조하고, 트레이스의 글에 쿠키 값 원문이 들지 않는 것도 본다.)

### 키 만들기 명령 (넘겨받았다. 이름과 인자, 파일의 꼴은 명세가 정했다)

- 앱의 스크립트 `make-key`다. `pnpm -C web/apps/portal make-key -- --private-key <경로> --kid <kid>`로 부른다. RSA 2048 키 쌍을 만들어 개인 키를 PKCS#8 PEM으로 그 경로에 쓰고(이미 있으면 덮어쓰지 않고 종료 코드 1. POSIX에서는 모드 0600), stdout에 사이트 파일에 붙일 `[[sites.public_keys]]` 조각(`kid`와 SPKI PEM `pem`)을 TOML 그대로 출력한다. 키 파일은 커밋하지 않는다.
- 거부한 안: 설정 파일의 `[portal]` 조각까지 출력한다(사이트 파일과 설정 두 파일에 붙일 것을 한 출력에 섞는다).

### 페이지 (넘겨받았다. 데이터 블록의 모양, 상태를 묻는 시점, 사이트 바꾸기 뒤 안내를 거두는 시점, 포커스의 자리와 접근성 역할, 다크 모드 스위치, 제목은 명세가 정했다. 사용자가 밀도와 라이트 기본 화면과 둘 다 사이트의 글 한 줄을 골랐다)

- 서버는 질의와 쿠키를 보지 않고 같은 HTML을 낸다. HTML은 `lang="ko"`, 뿌리에 `data-density="regular"`와 첫 사이트의 `data-theme`·`data-mode`, 토큰 CSS·글꼴 CSS·페이지 CSS 링크, 데이터 블록 `<script type="application/json">`(사이트마다 `name`, `heading`, `intro`, `theme`, `mode`, `assurance`, `notice`(전문), `reportUrl`과 쿠키 수명 일수. `<`는 `\u003c`로 이스케이프한다(JSON 문자열의 유니코드 이스케이프. `</script>`가 든 고지 글이 데이터 블록을 닫지 못하게 한다)), 페이지 스크립트 `<script src="/portal/portal.js">`, 위젯 번들 `<script src="/widget/element.js">`, `<noscript>`의 한 줄("이 페이지는 스크립트가 있어야 동작합니다.")을 든다. 인라인 스크립트와 인라인 스타일은 없다. 응답 헤더에 `Content-Security-Policy: default-src 'none'; script-src 'self'; connect-src 'self'; style-src 'self'; font-src 'self'; img-src 'self'; frame-ancestors 'none'; base-uri 'none'`을 단다(ADR 0050. 위젯의 구성 스타일시트는 `style-src 'self'`에서 칠해진다, EMBED.md CSP 절). 위젯 번들이 같은 출처에 있어야 한다는 배치 전제는 release-image가 정한다(아래 Out of Scope).
- 화면의 뼈대는 디자인 `README.md` 표의 완성 화면 그대로다. 위쪽 띠에 라벨 "사이트"와 셀렉트(사이트가 하나면 둘 다 숨긴다), 디자인 시스템 스위치 모양의 "다크 모드" 스위치. 그 아래 가운데 한 열에 정보 글 한 줄(`role="status"`), 둘 다 사이트의 단추 줄, 위젯 자리(폭 400px, 높이 560px, `bg-raised`와 `shadow-float`. 좁은 폭에서는 좌우 16px 여백에 남은 폭), 짧은 고지 한 줄과 "고지 전문" 단추(`aria-expanded`·`aria-controls`. 누르면 아래로 전문이 펼쳐지고 다시 누르면 접힌다), 보고서 링크 "이 에이전트의 평가 보고서"(새 탭, `rel="noopener"`, 바깥 링크 아이콘은 꾸밈이라 숨긴다. `reportUrl`이 없으면 그리지 않는다). 페이지 제목(`<title>`)과 화면 읽기 프로그램만 읽는 `<h1>`은 고른 사이트의 `heading`이고 사이트를 바꾸면 함께 바뀐다.
- 사이트 고르기. 스크립트는 `?site=`를 읽어 그 이름의 사이트를, 없거나 모르면 첫 사이트를 고른다. 고르면 뿌리의 `data-theme`·`data-mode`를 그 사이트의 값으로(`mode`가 없으면 시스템 설정으로) 두고, `<agent-os-widget>`의 속성 다섯을 채우고, `tokenProvider`를 그 사이트의 토큰 끝점을 POST로 부르는 함수로 바꾸고, `?site=`를 `history.replaceState`로 적는다. 셀렉트로 바꾸면 같은 일을 하고 정보 글 "사이트를 바꿔 새 대화로 시작합니다."를 보인다. 그 글은 다음에 사이트를 바꾸거나 `tokenProvider`가 다음에 불릴 때(첫 요청을 보내는 순간) 거둔다. 같은 에이전트의 두 사이트 사이를 바꿔도 발급자와 `sub`가 바뀌어 위젯이 저장한 대화를 지운다(ADR 0024, ADR 0050 Consequences).
- 확인 흐름. 고를 때마다 상태 끝점에 묻는다. 답이 오기까지 위젯 자리에는 아무것도 보이지 않다가 0.3초를 넘기면 움직이지 않는 뼈대(`aria-label="고지 확인 여부를 묻는 중"`. 그림의 뼈대와 같다)를 보인다. 미확인이면 위젯 자리를 덮개가 덮는다. 덮개는 대화 상자가 아니라 제목 "질문하기 전에 읽어 주세요"를 단 영역(`<section aria-labelledby>`)이고 나타날 때 포커스를 옮기지 않는다. 전문은 넘치면 그 칸만 스크롤하고, 아래에 폭을 채운 주 버튼 "확인하고 질문하기"가 있다. 누르면 단추에 `aria-busy`를 두고 두 번째 누름을 무시하며 확인 끝점을 POST로 부른다. 204면 덮개를 걷고 짧은 고지를 보이며 포커스를 위젯 자리(위젯 요소를 감싼 페이지의 상자. `tabindex="-1"`을 둔다)로 옮긴다. 위젯 요소 자신에는 `tabindex`를 두지 않는다. 실패하면 단추 위에 `role="alert"`의 위험 알림(제목 "고지 확인을 기록하지 못했습니다.", 본문 "잠시 뒤 다시 눌러 주세요.")을 보이고 단추를 다시 누를 수 있게 한다. 짧은 고지는 위젯이 보일 때만 보인다(상태를 묻는 동안, 덮개가 있는 동안, 로그인 사이트에서는 숨긴다. ADR 0050 결정 "페이지"의 "짧은 고지는 위젯 곁에 늘 보인다"는 이 문장으로 바뀌어 이력에 적는다).
- 보증 모드별 모습. `anonymous`는 위의 흐름이다. `login`은 위젯 요소를 두지 않고 위젯 자리와 같은 크기의 상자에 정보 알림(제목 "이 사이트는 로그인이 필요합니다.", 본문 "로그인은 아직 제공하지 않습니다.")을 두며 짧은 고지는 없다. `both`는 익명 흐름에 더해 위젯 자리 바로 위 한 줄에 `disabled`인 보조 버튼 "로그인하고 질문하기"와 글 한 줄 "로그인은 아직 제공하지 않습니다. 지금은 로그인 없이 질문할 수 있습니다."를 둔다. 단추는 포커스를 받지 않고 글이 읽는 차례에서 단추 바로 뒤에 온다.
- 다크 모드 스위치. 켜고 끄면 뿌리의 `data-mode`와 위젯의 `mode` 속성을 함께 `dark`·`light`로 바꾼다. 처음 값과 사이트를 바꾼 뒤의 값은 그 사이트의 `mode`(없으면 시스템 설정)이고 저장하지 않는다. ADR 0050에 없던 것이고 화면 작업에서 사람이 들였다(일지 2026-11-09-1839).
- 포커스 차례는 셀렉트, 다크 모드 스위치, 위젯 요소 또는 덮개의 단추, "고지 전문" 단추, 보고서 링크다.
- 거부한 안: 서버가 `?site=`를 읽어 사이트마다 다른 HTML을 낸다(HTML이 질의에 따라 갈려 캐시와 시험의 사례가 는다. 설계 인터뷰에서 사용자가 "페이지 하나에서 클라이언트가 위젯을 바꿔 끼운다"를 골랐다, 일지 2026-11-09-1410). 거부한 안: 확인 뒤 포커스를 위젯 안 입력창으로 옮긴다(EMBED.md "지킬 것"이 공개 표면으로 드는 것은 속성 다섯, 요소 이름과 `tokenProvider`, 번들 경로이고 shadow root 안의 요소는 들지 않는다). 거부한 안: 다크 모드 스위치의 값을 브라우저에 저장한다(미리보기의 쓰임이고 사이트의 설정이 원천이다). 거부한 안: 상태 끝점을 주기적으로 다시 묻는다(바뀌는 것은 이 페이지의 확인 단추뿐이다).

(2026-11-10 PR 직전 리뷰: 첫 항목의 데이터 블록에 사이트마다 `agent`를 더한다. 사이트 고르기가 채우는 `<agent-os-widget>`의 속성 다섯 가운데 `agent`는 `[[sites]]`의 필수 칸인데(위 "질문 페이지 설정") 데이터 블록의 목록에 없어, 페이지 스크립트가 그 값을 얻을 곳이 없었다. 에이전트 이름은 위젯 요소의 속성으로 어차피 DOM에 보이는 값이라 데이터 블록에 실어도 새로 드러나는 것이 없다. ADR 0050 결정 "페이지"의 공개 설정 목록(이름, 제목, 소개, 테마, 밝음, 보증 모드, 고지 글, 보고서 링크)에도 에이전트가 없지만, 이 주석은 실리는 것을 더하기만 해 그 문장이 글자 그대로 여전히 참이므로 이력과 포인터를 달지 않는다(`.claude/rules/adr.md`의 달지 않는 것). 결정을 더하지 않고 빠진 칸을 채우는 것이라 서두의 수는 바뀌지 않는다. 받는 티켓은 06이다.)

### 모양 (넘겨받았다. 페이지 CSS의 꼴, 디자인 시스템에 더하지 않는 것은 명세가 정했다. 사용자가 밀도를 골랐다. 쟀다)

- 페이지 CSS(`/portal/portal.css`)는 손으로 쓴 파일 하나이고 토큰을 `var(--…)`로만 읽는다. 클래스 이름은 모두 `pp-` 접두라 토큰 CSS 산출에 든 유틸리티 클래스와 겹치지 않는다. 화면 그림이 읽는 변수 27개는 산출에 모두 선언된다(쟀다, `theme_css_build`). 밀도를 따르는 높이와 글자는 밀도 변수(`--control-h`, `--body-size`)를 읽고 px로 박지 않는다(`.claude/rules/web-design.md`).
- 디자인 시스템에 없는 부품은 페이지 CSS로 그린다. 셀렉트는 브라우저 기본 `<select>`를 토큰으로 칠한 것(높이 `--control-h`, 경계 `--border-control`, 모서리 `--radius-m`, 오른쪽 꺾쇠), 폭을 채운 주 버튼과 그 안의 도는 표시(`prefers-reduced-motion`에서 멈춘다), 아이콘 `chevron-down`·`external-link`·`loader-circle`은 Lucide 모양의 인라인 SVG(선 1.5px)다. 디자인 시스템 패키지에는 더하지 않는다.
- 뿌리 밀도는 보통이라 넓은 창에서도 바깥 부품이 위젯 안 글자와 같은 크기다. 디자인 표의 넓은 창 그림은 바깥이 촘촘으로 그려졌으므로(디자인 `README.md` "그림이 시작 프롬프트나 근거 문서와 다른 자리") 그 그림은 치수가 아니라 배치의 근거다. 보통 밀도로 그린 실제 화면을 넓은 창에서 그 그림과 배치로 대 보는 것은 묶음 C의 일이다(사용자 답 "그림의 넓은 창 화면은 그 크기로 다시 봐야 한다", 일지 2026-11-09-2258).
- 거부한 안: 셀렉트 부품과 아이콘 셋을 디자인 시스템에 더한다(React 부품은 React를 싣지 않는 질문 페이지가 쓰지 못하고, 아이콘 셋은 다른 쓰는 곳이 없다). 거부한 안: 페이지가 토큰 CSS의 유틸리티 클래스를 쓴다(그 목록은 디자인 시스템 패키지의 소스가 정하는 것이라 페이지가 쓰는 클래스가 빠질 수 있다). 거부한 안: 질문 페이지의 사진 비교를 둔다(정적 빌드가 없고 서버가 그린다. 범위 밖).

(2026-11-10 명세 검토: 셋을 정한다. 첫째, 위젯 자리·덮개·뼈대·로그인 상자의 그림자(그림의 `shadow-float`)는 페이지 CSS가 모양을 직접 적고 색만 변수에서 읽는다. 값은 `0 8px 24px var(--shadow-color), 0 1px 2px var(--shadow-color)`이고, 그 값의 원천인 `theme.css`의 `--shadow-float`를 주석으로 가리킨다(명세가 정했다). 디자인 시스템은 `--shadow-float`를 `@theme inline`에 두어 뿌리 변수로 내지 않는다(그 주석을 읽었다). 토큰 CSS 산출에 `--shadow-float:` 선언은 없고 유틸리티 `.shadow-float`가 값을 그 자리에 박는다(검토가 Tailwind CLI 산출을 임시 스크립트로 손으로 봤다). 위 "토큰을 `var(--…)`로만 읽는다"와 "화면 그림이 읽는 변수 27개"는 그림이 `var()`로 읽은 것만 센 것이고, 이 그림자가 그 규칙의 하나뿐인 예외다. 거부한 안: 디자인 시스템이 `--shadow-float`를 뿌리 변수로도 낸다(뿌리에서 `var(--shadow-color)`가 뿌리의 모드로 풀려 물려진다. 그 주석이 밀도의 별칭처럼 뿌리에 선언을 내지 않으려고 inline에 둔다고 적는다). 거부한 안: 페이지가 유틸리티 `.shadow-float` 하나만 쓴다(위 거부한 안 "페이지가 토큰 CSS의 유틸리티 클래스를 쓴다"와 같은 까닭). 둘째, React를 싣지 않는 페이지는 디자인 시스템에 있는 부품도 쓰지 못한다. 그림이 부르는 Alert(위험, 정보)·Button(보조, 쓸 수 없음)·Switch는 그 부품의 마크업과 ARIA(Switch는 `<input type="checkbox" role="switch">`와 상태 글)를 옮긴 HTML과 페이지 CSS로 그린다(명세가 정했다). 아이콘은 셋이 아니라 다섯이다. `chevron-down`, `external-link`, `loader-circle`에 정보 글 줄과 짧은 고지 줄의 `info`, 위험 알림의 `circle-x`가 더해진다(그림 `pp-page.dc.html`과 디자인 시스템의 `Alert.tsx`·`Switch.tsx`를 읽었다). 위 둘째 항목과 거부한 안의 "아이콘 셋"은 이 다섯으로 읽는다. 셋째, 넓은 창 대 보기는 사이트 여럿을 그리는 티켓이 1280px과 375px에서 기본·덮개·로그인·둘 다 화면을 Playwright로 찍어 PR 본문에 디자인 그림과 나란히 싣는 것으로 끝난다(명세가 정했다). 찍은 그림은 사진 비교의 정답으로 커밋하지 않는다(위 거부한 안).)

### 위젯 문구와 TextField (명세가 정했다. 사용자가 입력창 이름을 골랐다)

- 위젯의 입력창은 이름표를 화면에서 숨기고 화면 읽기 프로그램이 읽는 이름을 "질문"으로 둔다. 입력창 안내(placeholder)는 "무엇을 도와드릴까요?", 첫 화면 안내는 "아래 입력창에 적어 보내 주세요.", 앞 요청이 422로 돌아왔을 때의 오류 글은 "질문을 보낼 수 없습니다. 질문을 고쳐 다시 보내 주세요."다. 화면 작업에서 사람이 고른 글 둘과 입력창 이름(일지 2026-11-09-1839, 캔버스 메모 `mk-how`), 그리고 같은 규칙으로 바꾼 오류 글이다. 위젯 문구라 위젯을 넣은 모든 사이트에 함께 보인다. 이름표 "요청"으로 입력창을 찾거나 두 안내 글을 대 보는 테스트·스토리·e2e(디자인 `README.md`가 센 14파일 33줄. 코드를 읽었다)도 함께 고친다.
- 디자인 시스템의 TextField에 이름표를 화면에서만 숨기는 선택 속성을 더한다. `<label for>`는 그대로 두어 접근 이름이 이름표에서 나오고, 화면에서만 숨긴다. 스토리와 그 `.md`에 그 변형을 더하고 사진 비교의 정답(`pnpm -C web visual:update`, `visual:widget:update`)을 다시 만든다.
- 개념어는 그대로 "요청"이다. `CONTEXT.md`의 요청 항목에 "사람에게 보이는 글에서는 질문이라 부른다"는 단서를 단다(이 명세와 같은 커밋, domain-modeling 스킬을 거친다).
- 거부한 안: 위젯이 TextField 대신 같은 클래스의 기본 `textarea`를 쓴다(칸의 클래스와 오류 글 자리가 두 벌이 된다. 그림이 그렇게 그린 것은 부품에 숨기는 길이 없어서였다). 거부한 안: 이름표를 없애고 `aria-label`만 둔다(디자인 시스템은 브라우저 기본 요소와 `<label for>`로 짓는다). 거부한 안: 화면의 글도 "요청"으로 맞춘다(사용자가 고르지 않았다).

### 함께 쓰는 e2e 준비와 중계 (넘겨받았다. 패키지의 내용과 중계의 셋째 상류는 명세가 정했다)

- `@agent-os/e2e-stack`의 중계는 상류를 `serve`, 위젯 Next, 질문 페이지(선택) 셋으로 받는다. `/end-user/` 아래는 `serve`로, `/widget`(질의 포함)과 `/widget/` 아래는 Next로, `/`(정확히)와 `/portal/` 아래는 질문 페이지로 넘기고(ADR 0050 결정 "경로"의 프록시 규칙과 같다) 그 밖은 404다. 질문 페이지 상류를 주지 않으면 그 셋도 404라 위젯 e2e의 동작은 그대로다. 응답은 모으지 않고 흘려보낸다(지금 중계와 같다).
- 위젯 e2e의 `stack.ts`는 그 패키지의 도우미로 다시 쓰되 사례와 사이트 서버는 그대로다. 두 앱의 Playwright 설정은 각자 두고 `globalSetup`만 패키지를 쓴다.
- 거부한 안: 질문 페이지가 자기 e2e 준비 사본을 둔다(ADR 0050이 거부했다).

(2026-11-10 명세 검토: 둘을 더한다. 첫째, 지금 위젯 e2e의 준비는 트레이스를 `AGENT_OS_WIDGET_TRACES`가 준 폴더(주지 않으면 작업 폴더 아래)에 남기고 Playwright 사례에는 그 자리를 넘기지 않는다. 그 변수는 실제 모델 래퍼 `tests/test_widget_llm.py`가 준다(`web/apps/widget/e2e/stack.ts`와 `env.ts`를 읽었다. e2e 파일에 트레이스를 여는 줄이 없는 것은 grep으로 봤다). 아래 Playwright e2e의 트레이스 주체 사례가 서려면 `@agent-os/e2e-stack`이 트레이스 폴더를 시험에 넘겨야 하고, 그 길은 e2e 준비를 뽑는 티켓이 더한다. 둘째, 중계의 셋째 상류와 그 `upstreamOf` 사례는 질문 페이지를 처음 중계 뒤에 띄우는 티켓이 더한다. 뽑는 티켓은 지금 중계를 그대로 옮긴다.)

### HTTP 요청 처리기와 서버 (명세가 정했다)

- 서버는 HTTP 요청을 받아 응답을 내는 순수 함수 하나(메서드, 경로, 헤더, 쿠키 → 상태, 헤더, 본문)와 그것을 `node:http`에 거는 얇은 겉으로 나뉜다. 순수 함수는 시계와 UUID 만들기를 인자로 받아 시험이 고정한다. Vitest는 그 함수를 부르고 e2e가 실제 소켓을 지난다(사용자가 고른 이음매의 나눔).
- 거부한 안: 시험이 실제 포트에 서버를 띄워 HTTP로 부른다(전역 `fetch` 금지에 걸리고, 그 길은 e2e가 이미 지난다).

### 전역 `fetch` 금지의 예외 (넘겨받았다. 길은 명세가 정했다)

- `web/eslint.config.mjs`에 질문 페이지의 페이지 스크립트 파일 하나(앱의 `browser/` 폴더)만을 `files`로 드는 블록을 두어 `no-restricted-globals`와 `no-restricted-properties`의 HTTP 전역 셋 금지를 끄고, 설정 파일에 경로와 이유(부르는 것이 Agent OS의 API가 아니라 질문 페이지 자신의 끝점이라 생성 클라이언트의 대상이 아니다)를 함께 적는다(`.claude/rules/web-workspace.md`). 서버 코드와 시험과 e2e는 `fetch`를 쓰지 않는다(서버는 `node:http`, 시험은 순수 함수, e2e는 Playwright의 요청 컨텍스트). `web/eslint.config.test.ts`에 그 파일에서는 지나고 그 앱의 다른 파일에서는 걸리는 사례를 더한다.
- 거부한 안: 페이지 스크립트가 `XMLHttpRequest`를 쓴다(같은 금지에 걸리고 더 낫지 않다). 거부한 안: 질문 페이지 앱 전체를 예외로 둔다(서버 코드가 `fetch`로 바깥을 부르는 길이 열린다).

(2026-11-10 명세 검토: 페이지 스크립트 파일의 블록은 `fetch` 하나만 푼다(명세가 정했다). 지금 두 규칙은 HTTP 전역 셋(`fetch`, `EventSource`, `XMLHttpRequest`)을 한 목록으로 막아(`web/eslint.config.mjs` 103~108줄과 210줄 근처를 읽었다) 규칙째 끄면 셋이 모두 풀리고, 위 거부한 안의 "`XMLHttpRequest`는 같은 금지에 걸린다"가 그 파일에서 거짓이 된다. 블록은 `fetch`를 뺀 목록으로 두 규칙을 다시 건다. `web/eslint.config.test.ts`에는 그 파일에서도 `XMLHttpRequest`가 걸리는 사례를 함께 더한다. 거부한 안: 그 파일에서 두 규칙을 끈다(HTTP 전역 셋이 함께 풀린다).)

## Testing Decisions

### 좋은 시험

바깥 행동만 본다. 서버는 요청과 응답(상태, 헤더, 본문, `Set-Cookie`)을, 페이지는 브라우저에 보이는 것과 끝점에 닿은 요청을, 위젯은 화면의 글을 본다. 벗긴 스크립트의 글자나 CSS 산출의 바이트 수는 단언하지 않는다. 시간 단언은 홀로 돌린 시간의 넉넉한 배수로 두고 Linux CI를 생각한다(`.claude/rules/tests.md`). 환경이 없어 skip되는 시험은 두지 않는다(원칙 II). TS 시험의 이름은 행동을 말하는 한국어 문장이다.

### Vitest (넘겨받았다. 사례는 명세가 정했다)

node 프로젝트에서 순수 함수를 부른다. 설정 읽기(맞는 파일이 읽히고, 어긋남마다 그 자리가 진단에 들고 값은 들지 않되 루프백 밖 `host`만 받은 값이 든다. 사이트 파일 대조의 여섯 갈래 각각, 모르는 칸, 판, `name` 꼴, 빈 `sites`, 비었거나 공백뿐인 `notice`, 루프백 밖 `host`, 개인 키와 공개 키의 불일치), 시작 로그의 주소(`127.0.0.1`은 그대로, `::1`은 대괄호 `[::1]`), 토큰(공개 키로 검증되고 클레임 다섯이 기대와 같으며 `exp - iat`가 120이고 `kid`가 실린다), 쿠키 판정(`Origin` 없음·다른 출처·같은 출처, 꼴이 맞는 쿠키는 같은 값으로 만료만 다시, 꼴이 틀린 쿠키는 새 값, 같은 이름 둘이면 첫 것, `https` 공개 출처에서만 `Secure`), 상태 끝점의 두 답, 로그인 사이트 세 끝점의 403, 미확인 토큰의 401, 리다이렉트가 질의를 지키는 것, 모르는 이름의 404와 다른 메서드의 405, 페이지 HTML(데이터 블록이 `</script>`가 든 고지 글을 이스케이프하고, CSP 헤더가 글자 그대로이며, `nosniff`가 있고, 인라인 스크립트가 없고, 뿌리에 `data-density="regular"`가 있다), 정적 파일의 콘텐츠 타입과 `ETag`·304, 글꼴 목록 밖 이름의 404, 벗긴 페이지 스크립트가 JavaScript로 파싱된다(`vm.Script`), 키 명령의 출력이 TOML로 읽히고 그 `pem`이 개인 키의 공개 키와 같다. 중계의 `upstreamOf`에 셋째 상류의 두 규칙(`/` 정확히, `/portal/` 아래)과 상류 없을 때의 404.

(2026-11-10 명세 검토: 빠진 사례를 더한다(받는 티켓을 괄호에 적는다). 고지 전문 짓기에서 사이트가 `notice`를 적으면 그 글 끝에 쿠키 문장이 붙고, 적지 않으면 기본 글 세 문단이며, 쿠키 문장의 "30일"이 쿠키 수명 상수에서 그려진다(04. 설정을 읽을 때 사이트마다 짓는다). 키 명령이 이미 있는 파일을 덮어쓰지 않고 종료 코드 1로 끝나며 그 파일이 그대로다(04). 토큰 끝점의 200이 받은 쿠키와 같은 값으로 `Max-Age=2592000`의 `Set-Cookie`를 다시 낸다(05). "사이트 파일 대조의 여섯 갈래"는 "시작 검사와 진단"의 주석이 이름을 든 여섯이다(04).)

### Playwright e2e (넘겨받았다. 사이트 넷, 다른 출처 페이지, 사이트 하나의 둘째 인스턴스, CI 잡 이름은 명세가 정했다)

- 준비는 `@agent-os/e2e-stack`으로 실제 `serve`(픽스처 플러그인), 그 사이트 파일로 빌드한 위젯 Next, 질문 페이지, 상류 셋의 중계를 띄운다. 공개 출처는 `http://portal.localhost:<중계 포트>`이고 사이트 파일의 모든 사이트가 그것과 아래 둘째 인스턴스의 루프백 출처를 허용 출처로 든다(시작 검사의 `public_origin` 대조를 지나기 위해서다). 사이트는 넷이다. 익명 사이트 둘(같은 픽스처 에이전트. 하나는 `hourly_runs_per_site = 1`), 둘 다 사이트 하나(같은 에이전트), 로그인 사이트 하나. 다른 출처 `http://other.localhost:<포트>`의 작은 페이지 하나가 확인 끝점으로 폼 POST를 보낸다(질문 페이지 e2e의 것이다). 사이트 하나의 모습은 설정에 사이트 하나만 적은 둘째 질문 페이지 프로세스를 제 루프백 주소로 열어 셀렉트와 라벨이 숨는 것만 본다(위젯 번들은 그 출처에 없어 그리지 않는다).
- 사례. 처음 온 브라우저에 덮개가 보이고 짧은 고지가 없으며 상태 끝점이 거짓이고 확인 전 토큰 끝점이 401이다(요청 컨텍스트). 확인하면 덮개가 걷히고 포커스가 위젯 자리에 있고 Tab으로 입력창 "질문"이 포커스를 받으며(위젯 머리의 "새 대화" 단추가 첫 Tab을 먼저 받아 입력창은 둘째 Tab이다. 2026-11-10 티켓 07의 e2e가 실제 위젯에서 봤다), 위젯을 벗어났다가 Tab으로 되돌아와도 입력창에 닿고, 요청에 답이 서고, 트레이스의 주체가 `<발급자>|anon-<그 브라우저의 쿠키 값의 해시 32자>`이고 트레이스 어디에도 쿠키 값 원문이 없다(기능 계획의 수락 둘). 확인 뒤 쿠키를 지우고 질문하면 위젯이 "로그인 정보를 받지 못했습니다."를 보인다. 다른 출처 페이지의 폼 POST 뒤에도 상태 끝점이 거짓이고 쿠키가 없다. 확인한 사이트에서 같은 에이전트의 다른 사이트로 바꾸면 앞 대화가 없고 정보 글이 보이며, 미확인 사이트로 바꾸면 덮개가 보인다. `?site=`로 열면 그 사이트가 골라진다. 로그인 사이트는 위젯 없이 알림을 보이고, 둘 다 사이트는 `disabled` 단추와 그 바로 뒤의 글을 보인다. 상한 1인 사이트의 둘째 요청이 거부되어 위젯이 상한 알림을 보인다(기능 계획의 수락 셋째). 다크 모드 스위치가 뿌리와 위젯의 모드를 함께 바꾼다. 페이지에 CSP 위반 콘솔 메시지가 없고 본문의 글꼴 변수가 토큰 값으로 풀린다. 사이트 하나의 둘째 인스턴스에서 셀렉트와 라벨이 없다.
- CI에 잡 `e2e-portal`을 더해 `verify`의 `needs`에 넣는다(`e2e-widget`과 같은 모양. Next 빌드를 한 번 더 한다). 로컬 명령은 `pnpm -C web/apps/portal exec playwright test`이고 질문 페이지, `e2e-stack`, 서버의 최종 사용자 경로를 건드렸을 때 친다(`CLAUDE.md` 검증 명령과 `tech.md` 원격·CI 행에 적는다).

(2026-11-10 명세 검토: 하나를 고치고 사례를 더한다(받는 티켓을 괄호에 적는다). 다른 출처 페이지의 폼 POST 사례는 그 탐색 응답이 403인 것을 `page.waitForResponse`로 단언하고, 같은 출처의 확인 POST가 204를 받는 것을 양성 대조로 둔다(07). 쿠키가 남지 않은 것만으로는 서버의 거절인지 브라우저의 거부인지 가르지 못한다. ADR 0050은 `SameSite=Strict`가 쿠키를 받는 요청은 막지 않는다고 적고 그것을 브라우저로 재지 않았다. 더하는 사례: 확인한 뒤 새로 고치면 덮개가 없다(07). 덮개가 나타날 때 `document.activeElement`가 옮겨지지 않는다(07). 사이트의 `notice`가 덮개의 전문에 쓰인다(07). 질문 페이지 프로세스의 출력에 그 브라우저의 쿠키 값과 토큰 끝점이 낸 토큰이 없다(07. 준비가 모은 프로세스 출력을 본다). 사이트를 바꾼 뒤의 정보 글이 `role="status"`이고, 다음 사이트 바꾸기와 첫 요청을 보낼 때 거둬진다(08). `reportUrl`이 있는 사이트는 링크가 있고 없는 사이트는 없다(08).)

## Out of Scope

- 질문 페이지와 위젯 번들(`/widget/element.js`)과 최종 사용자 경로(`/end-user/`)가 한 공개 출처 아래에 서야 한다는 배치 전제와, 그것을 프록시가 어떻게 갖추는지. release-image의 설계 인터뷰가 정한다(그 기능 계획 본문에 적었다. `**Blocked by:**`에 pilot-portal이 있다). 토큰 끝점 앞의 프록시 빈도 제한, 네 프로세스와 프록시 잇기, 이미지에 소스와 `node_modules`를 담는 것도 그 행이다(ADR 0050). 질문 페이지의 공개 출처를 믿을 수 없는 하위 도메인이 없는 도메인에 두는 배치 요건(위 (15))도 그 기능 계획 본문에 적었다. 그 요건의 "도메인"은 질문 페이지 호스트에 `Domain` 쿠키를 심을 수 있는 등록 도메인(공개 접미사 바로 아래)이고 "하위 도메인"은 그 아래 모든 호스트라 형제 도메인까지 든다. 질문 페이지 호스트의 아래만 보는 것으로는 모자란다(PR #504의 CodeRabbit이 짚어 기능 계획 본문에 풀어 적었다).
- 로그인 갈래. 로그인 사이트의 세 끝점이 403으로 거절하는 지금 동작과 `both`의 비활성 단추를 portal-login이 채운다(그 기능 계획 본문에 적었다).
- 공개 데모의 고지 글(`notice` 칸), 사이트 하나의 설정, 보고서 링크(`report_url`)의 값. public-demo의 설계 인터뷰가 정한다(그 기능 계획 본문에 적었다. 그 `**Blocked by:**`에 pilot-portal은 없고 release-image를 거쳐 간접으로 막힌다).
- 질문 페이지 설정을 화면에서 고치는 관리 화면과 설정을 다시 띄우지 않고 읽는 것(portal-admin). 새 모양 칸(widget-appearance). 두 기능 계획의 "칸 이름은 명세가 짓는다" 문장을 이 명세를 가리키게 고쳤다.
- 관리 화면 e2e의 준비 코드 사본을 패키지로 합치는 것(ADR 0050).
- 디자인 시스템에 셀렉트 부품과 아이콘 셋을 더하는 것, 질문 페이지의 사진 비교.
- 위젯에 포커스를 입력창으로 옮기는 공개 메서드를 더하는 것(아래 Further Notes).
- 사이트 파일과 질문 페이지 설정을 운영 중에 다시 읽는 것(ADR 0050).

(2026-11-10 명세 검토: 관리 화면 e2e의 준비 사본을 합치는 것과 위젯에 포커스 메서드를 더하는 것은 받는 기능이 없다. 지금 받을 기능 계획을 세우지 않는다. 앞의 것은 ADR 0050이 그대로 두기로 했고, 뒤의 것은 쓰는 쪽이 생길 때 정한다. `__Secure-` 접두를 쓰지 않는 근거인 HSTS는 운영의 프록시가 맡고 어떤 시험도 보지 않는다. 그 한 줄을 release-image 기능 계획 본문에 더했다.)

- 프로브의 수는 2026-11-09에 돌린 실행의 것이다. 첫 실행은 16회차 가운데 15회차 측정, 둘째는 18회차 모두 측정, 셋째는 명세를 쓰며 더한 페이지 스크립트 묶음 두 회차(첫 판은 갈래의 표지를 틀린 오류 코드로 적어 측정 아님 하나였고 고친 뒤 둘 다 측정), 그 뒤 여섯 묶음 스무 회차 전체를 다시 돌렸다. 2026-11-10에 셀프 리뷰를 받아 회차 넷을 더하고 스물네 회차 전체를 다시 돌렸다(다섯째 실행. 모두 측정). 결과를 본 뒤 바꾼 기준과 근거의 종류는 프로브 `README.md`에 있다.
- 재지 않은 것(어림). `@agent-os/ui`의 `./themes` 서브패스는 `./contrast`와 같은 길(export 지도를 지나 실제 경로로 푼다)이라 서리라 보되 그 이름으로는 재지 않았다. `site-file` 패키지에서 `smol-toml`이 풀리는 것은 그 패키지가 아직 없어 `strip_package_dep`이 잰 길로 미루어 본다. 둘 다 틀려도 고칠 길이 하나(서브패스를 열고 의존성을 적는다)라 결정이 바뀌지 않고, 묶음 A의 첫 일은 이 둘을 그 자리에서 대 보는 것이다. 글꼴 CSS의 자기 참조와 Tailwind CLI를 자식으로 띄우는 것은 틀리면 결정(토큰 CSS를 시작 때 짓는 길, 글꼴 도우미의 자리)이 바뀌는 것이라 셀프 리뷰를 받아 2026-11-10에 회차 둘을 더해 쟀다(위 "띄우기와 타입 검사").
- 질문 페이지는 React를 싣지 않지만 `@agent-os/ui`를 의존성으로 들므로 pnpm이 그 peer 의존성(react, react-dom)을 질문 페이지 아래에도 설치할 수 있다(어림. 컨테이너 이미지의 크기에만 닿는다).
- 확인한 뒤 포커스는 위젯 자리(위젯 요소를 감싼 페이지의 상자)에 두고 거기에 `tabindex="-1"`을 준다. 위젯 요소(호스트)에는 `tabindex`를 두지 않는다. 위젯이 입력창으로 포커스를 옮기는 공개 메서드를 내면 그때 바꾼다. EMBED.md의 공개 표면이 는다는 뜻이라 이 기능에서 더하지 않는다. 호스트에 두지 않는 까닭(2026-11-10 PR #506의 CodeRabbit 둘째 회차가 짚어 고쳤다. 손으로 봤다): Claude 데스크톱 앱의 내장 브라우저 창에서 연 임시 HTML 셋(열린 그림자 루트 안에 `<input>`을 둔 호스트를 `tabindex="-1"`, `"0"`, 감싼 상자에 `"-1"`로 갈랐다. 세션 스크래치패드에 두었고 커밋하지 않았다)을 Tab 키로 돌며 `document.activeElement`와 `shadowRoot.activeElement`를 읽었다. `-1` 호스트 앞의 링크에서 Tab 한 번이 호스트 뒤의 링크로 갔다(입력창을 건너뛰었다). 호스트가 포커스를 받은 상태에서 Tab 한 번은 입력창으로 들어갔다. `0` 호스트는 호스트 자신이 한 번 멈춘 뒤 다음 Tab이 입력창에 닿았다. 호스트를 감싼 상자에 `-1`을 두면 상자 앞의 링크에서 Tab 한 번이 입력창에 닿았다. 그래서 호스트의 `-1`은 확인 직후에는 되지만 위젯을 벗어났다가 Tab으로 되돌아오면 입력창에 닿지 못한다. `0`은 입력창에 닿지만 이름 없는 멈춤이 하나 는다. 감싼 상자는 둘 다 없다. 브라우저는 그 한 종류만 봤다(어림. Firefox와 Safari는 보지 않았다).
- `SameSite=Strict`라 다른 사이트의 링크로 들어온 첫 문서 요청에는 쿠키가 실리지 않지만, 페이지 HTML은 쿠키를 보지 않고 스크립트의 같은 출처 요청에는 실리므로 흐름이 끊기지 않는다(draft-ietf-httpbis-rfc6265bis-19의 "Strict"를 읽었다. 브라우저로 재지 않았다).
- 디자인 표의 넓은 창 그림(1280px)은 바깥이 촘촘으로 그려졌고 명세는 뿌리를 보통으로 정했다. 그림을 다시 그리지 않는다. 치수의 원천은 토큰 CSS이고 그림은 배치의 근거다.
- 다크 모드 스위치와 위젯 문구 변경은 ADR 0050에 없던 것으로 화면 작업에서 사람이 들였다. 이력에 쌓지 않는다(ADR의 결정을 바꾸지 않고 더하는 것이다). ADR 0050 Consequences의 머리 "위젯은 바뀌지 않는다"는 그 문단이 말하는 쿠키·토큰의 흐름(위젯은 쿠키를 모르고 `tokenProvider`만 부른다)에 대한 것이고, 이 명세가 바꾸는 위젯 문구·TextField·사이트 파일 읽기와 e2e 준비의 자리는 그 흐름이 아니라 포인터를 달지 않는다.
