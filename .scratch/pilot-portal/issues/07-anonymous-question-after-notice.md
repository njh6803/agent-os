# 07: 처음 온 최종 사용자가 고지 덮개에서 "확인하고 질문하기"를 누른 뒤 로그인 없이 질문한다

**What to build:** 처음 온 브라우저로 질문 페이지를 열면 위젯 자리를 덮개가 덮는다. 덮개에는 제목 "질문하기 전에 읽어 주세요", 그 사이트의 고지 전문(무엇이 기록되고 모델 API로 보내지는지, 쿠키를 둔다는 것), 폭을 채운 주 버튼 "확인하고 질문하기"가 있다. 단추를 누르면 덮개가 걷히고, 위젯 아래에 짧은 고지 "질문과 출력은 기록되고 모델 API로 보내집니다. 개인정보를 넣지 마세요."와 "고지 전문" 단추가 보이며, 포커스가 위젯으로 옮겨 간다. 그 뒤로는 로그인 없이 질문하고 답을 받는다. 같은 브라우저로 다시 오면 덮개 없이 이어서 질문한다. 확인을 기록하지 못하면 단추 위에 "고지 확인을 기록하지 못했습니다." / "잠시 뒤 다시 눌러 주세요." 알림이 뜨고 단추를 다시 누를 수 있다(스토리 1, 2, 3, 8의 덮개 부분). 기능 계획의 수락 셋(처음 온 최종 사용자가 로그인 없이 calc 예시에 질문한다, 트레이스의 주체가 그 브라우저에 준 식별자로 지은 이름이다, 사이트별 시간당 실행 수 상한을 넘긴 요청이 거부된다)이 질문 페이지 e2e로 선다. 수락 첫째는 이 티켓이 픽스처 에이전트로 흐름을 세우고, "calc 예시에"의 몫은 실제 모델이 드는 09가 맡는다.

07은 06과 03 뒤이고 08과 09를 막는다. 06의 페이지와 질문 페이지 e2e 준비 위에 확인 흐름을 그리고, e2e가 위젯 입력창을 03이 바꾼 이름 "질문"으로 찾는다.

**병합 뒤에 틈이 있다(to-tickets에서 사용자가 아홉 장 분할을 골랐다).** 이 티켓까지 병합된 main에는 셀렉트가 없어 첫 사이트나 `?site=`로 고른 사이트만 본다. 보증 모드별 모습도 아직 없어, 로그인 사이트를 `?site=`로 열면 상태 끝점까지 그 사이트의 끝점 셋이 403이다(명세 "경로와 끝점"). 상태를 묻다 실패했을 때 페이지가 무엇을 보이는지는 명세가 정하지 않았으므로 이 티켓이 맞추지 않고, 로그인 사이트의 모습은 08이 그린다. 다크 모드 스위치와 보고서 링크도 08이 더한다. 아직 이 앱을 띄우는 배포가 없으므로 바깥에 보이는 것은 바뀌지 않는다.

근거는 `.scratch/pilot-portal/spec.md`의 "페이지"의 확인 흐름 항목과 포커스 차례, "질문 페이지 설정"의 고지 전문과 짧은 고지, "모양"과 그 2026-11-10 명세 검토 주석 둘째(부품을 HTML로 옮기는 것, 아이콘 다섯), Testing Decisions의 "Playwright e2e"의 사례와 그 주석이다. 화면은 `.scratch/pilot-portal/design/`의 기본·덮개·뼈대·실패 화면(표는 그 `README.md`)이다. 수락 셋은 `.scratch/pilot-portal/plan.md`다. 앞선 결정은 ADR 0050의 결정 "페이지"와 그 2026-11-10 이력 "짧은 고지는 위젯이 보일 때만 보인다", Consequences(`SameSite=Strict`가 쿠키를 받는 요청은 막지 않는다)다.

**Blocked by:** 06 (질문 페이지가 고른 사이트의 설정으로 위젯을 그린다). 06의 페이지 스크립트·페이지 CSS·질문 페이지 e2e 준비(사이트 넷, 다른 출처 페이지, 프로세스 출력, 트레이스 폴더)를 쓴다. 03 (위젯 입력창을 "질문"으로 부른다). e2e가 입력창을 이름 "질문"으로 찾는다

**Status:** ready-for-agent

### 확인 흐름

- [ ] **사이트를 고를 때마다 상태 끝점에 묻고, 답이 오기까지 위젯 자리에는 아무것도 보이지 않다가 0.3초를 넘기면 움직이지 않는 뼈대(`aria-label="고지 확인 여부를 묻는 중"`)를 보인다**(명세 "페이지")
- [ ] **미확인이면 위젯 자리를 덮개가 덮는다.** 덮개는 대화 상자가 아니라 제목을 단 영역(`<section aria-labelledby>`)이고 나타날 때 포커스를 옮기지 않는다. 전문은 넘치면 그 칸만 스크롤하고, 아래에 폭을 채운 주 버튼 "확인하고 질문하기"가 있다. 전문은 데이터 블록의 `notice`(04가 지은 전문)다
- [ ] **단추를 누르면 `aria-busy`를 두고 두 번째 누름을 무시하며 확인 끝점을 POST로 부른다.** 204면 덮개를 걷고 짧은 고지를 보이며 포커스를 위젯 요소(`tabindex="-1"`)로 옮긴다. 실패하면 단추 위에 `role="alert"`의 위험 알림(제목 "고지 확인을 기록하지 못했습니다.", 본문 "잠시 뒤 다시 눌러 주세요.")을 보이고 단추를 다시 누를 수 있게 한다
- [ ] **짧은 고지와 "고지 전문" 단추(`aria-expanded`·`aria-controls`. 누르면 아래로 전문이 펼쳐지고 다시 누르면 접힌다)는 위젯이 보일 때만 보인다.** 상태를 묻는 동안과 덮개가 있는 동안에는 숨긴다(ADR 0050의 2026-11-10 이력)
- [ ] **위험 알림과 주 버튼은 디자인 시스템 Alert·Button의 마크업과 ARIA를 옮긴 HTML과 페이지 CSS로 그린다.** 주 버튼 안의 도는 표시(`loader-circle`)는 `prefers-reduced-motion`에서 멈춘다. 아이콘 `loader-circle`, `info`(짧은 고지 줄), `circle-x`(위험 알림)는 Lucide 모양의 인라인 SVG(선 1.5px)이고 꾸밈이라 숨긴다(명세 "모양"과 그 주석 둘째)
- [ ] **포커스 차례는 위젯 요소 또는 덮개의 단추, "고지 전문" 단추 순이다**(명세 "페이지". 셀렉트·스위치·보고서 링크는 08)

### 질문 페이지 e2e 사례

- [ ] **처음 온 브라우저에 덮개가 보이고 짧은 고지가 없으며, 상태 끝점이 거짓이고 확인 전 토큰 끝점이 401이다**(요청 컨텍스트)
- [ ] **덮개가 나타날 때 `document.activeElement`가 옮겨지지 않는다**
- [ ] **사이트의 `notice`가 덮개의 전문에 쓰인다.** 그 글 끝에 쿠키 문장이 붙는다
- [ ] **확인하면 덮개가 걷히고 포커스가 위젯 요소에 있으며, 입력창 "질문"으로 보낸 요청에 답이 서고, 트레이스의 주체가 `<발급자>|anon-<그 브라우저의 쿠키 값의 해시 32자>`이고 그 폴더의 트레이스 어디에도 쿠키 값 원문이 없다**(기능 계획의 수락 첫째와 둘째). 트레이스는 02의 길로 넘겨받은 폴더에서 읽는다
- [ ] **확인한 뒤 새로 고치면 덮개가 없다**
- [ ] **확인 뒤 쿠키를 지우고 질문하면 위젯이 "로그인 정보를 받지 못했습니다."를 보인다**
- [ ] **다른 출처 페이지의 폼 POST는 그 탐색 응답이 403인 것을 `page.waitForResponse`로 단언하고, 그 뒤에도 상태 끝점이 거짓이며 쿠키가 없다.** 같은 출처의 확인 POST가 204를 받는 것을 양성 대조로 둔다. 쿠키가 남지 않은 것만으로는 서버의 거절인지 브라우저의 거부인지 가르지 못하기 때문이다(명세 "Playwright e2e"의 주석)
- [ ] **`hourly_runs_per_site = 1`인 사이트의 둘째 요청이 거부되어 위젯이 상한 알림을 보인다**(기능 계획의 수락 셋째)
- [ ] **질문 페이지 프로세스의 출력에 그 브라우저의 쿠키 값과 토큰 끝점이 낸 토큰이 없다.** 06의 준비가 모은 프로세스 출력을 본다(ADR 0050 결정 "기록"). 같은 출력에 04의 시작 로그 한 줄이 있는 것을 양성 대조로 함께 단언한다. 출력을 모으지 못해 비어 있어도 "없다"는 초록이기 때문이다
