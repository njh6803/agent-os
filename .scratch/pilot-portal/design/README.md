# pilot-portal 화면

질문 페이지의 완성 화면이다. `/ui-design pilot-portal`이 Design 아티팩트에 그리고 사람이 확정한 것을 그 스킬의 7단계가 옮겼다(일지 2026-11-09-1839). 규약은 `docs/agents/issue-tracker.md`의 화면 디자인 절이고, 그린 순서와 화면은 시작 프롬프트 `screens-prompt.md`다. 그리며 `frontend-design`과 저장소 규칙이 부딪친 자리는 `.scratch/design-system/design/frontend-design-conflicts.md`의 2026-11-09 pilot-portal 행이다.

아티팩트에는 쪽이 둘이다. "1. 고를 갈래"(아트보드 여섯)와 "2. 완성 화면"(아트보드 35개)이고, 여기 옮긴 것은 완성 화면 35개와 캔버스 색인 `canvas.json`이다. 고를 갈래 여섯은 아티팩트에만 남겼다. 고른 두 안(`ch-head-2.dc.html`, `ch-login-1.dc.html`)도 완성 화면이 둘을 합쳐 다시 그렸으므로 옮기지 않았다. 그래서 `canvas.json`의 `boards`와 `order`는 여기 없는 `ch-*.dc.html` 여섯도 가리킨다. 그 아트보드를 다시 보려면 아티팩트를 연다. 화면 파일은 디자인 시스템을 `ds/agent-os/` 아래에서 불러오고 그 폴더는 옮기지 않았다(스킬 7단계가 `project/ds/`를 뺀다). 화면 파일이 함께 부르는 `./support.js`는 형식이 내주는 파일이라 옮길 지원 파일이 아니다. 저장소에서 브라우저로 그려지는지는 보지 않았다.

완성 화면은 질문 페이지 부품 하나(`pp-page.dc.html`)를 상태와 폭만 바꿔 불러 쓴다. 부품은 `screen`(상태 열넷), `narrow`(좁은 폭), `dark`(다크)를 받고 1280px 기본 화면 아트보드를 겸한다. `mk-<상태>-<폭>.dc.html` 33개는 그 부품을 `<dc-import>`로 부르는 틀이고, `mk-select-list.dc.html`은 펼친 셀렉트 목록 그림이다. 그래서 부품을 고치면 모든 화면이 함께 바뀐다.

사람이 고른 안이다(일지 2026-11-09-1839의 "고를 갈래").

- 페이지 머리(갈래 1): 안 2. 띠에 사이트 셀렉트와 다크 모드 스위치만 두고, 페이지 제목은 화면 읽기 프로그램만 읽는다. 고르지 않은 안 1은 띠 한 줄에 사이트 제목과 셀렉트와 스위치를, 안 3은 위젯 바로 위 가운데에 제목과 소개를 두는 것이었다. 추천은 안 1이었다.
- 둘 다 사이트의 비활성 로그인 단추 자리(갈래 2): 안 1(위젯 바로 위). 고르지 않은 안 2는 위젯 아래의 짧은 고지 위, 안 3은 위쪽 띠의 스위치 곁이었다.

그리며 둔 제안과 탐색용 가정이다. 결정이 아니고 명세가 결정으로 바꾸거나 다시 묻는다(시작 프롬프트 "고른 뒤" 3). 캔버스의 메모(`notes`의 `mk-how`, `mk-confirmed`)에도 적혀 있다.

- 위젯 문구. 사람이 확정 전에 두 번 고쳤다. 입력창 안내는 "무엇을 도와드릴까요?"이고 "요청"을 뺐다. 입력창 위의 이름표는 없애고 화면 읽기 프로그램만 읽는 이름 "질문"(`aria-label`)을 남겼다. 첫 화면 안내는 "아래 입력창에 적어 보내 주세요."다. 지금 위젯 코드는 이름표 "요청"과 안내 "요청을 적어 주세요"(`web/apps/widget/components/organisms/Composer.tsx`), 첫 화면 안내 "아래에 요청을 적어 보내 주세요."(`web/apps/widget/components/molecules/Welcome.tsx`)이고, 이름표 "요청"을 달거나 그 이름으로 입력창을 찾는 줄과 두 안내 문구가 든 줄이 `web/` 아래 14파일 33줄이다(테스트·스토리·e2e와 그 도우미 포함. 테스트가 보내는 글로 "요청"을 넣는 `ask(user, "요청")` 줄은 세지 않았다). 위젯 문구라 위젯을 넣은 모든 사이트에 함께 보인다. 같은 입력창의 오류 글(앞 요청이 422로 돌아왔을 때 `TextField`의 `error`로 뜨는 "요청을 보낼 수 없습니다. 요청을 고쳐 다시 보내 주세요.", `Composer.tsx`)에도 낱말 "요청"이 남는다. 그 상태는 그리지 않았다. 디자인 시스템의 `TextField`는 이름표가 칸 위에 늘 보이는 부품이라, 그림의 입력창은 `TextField`와 같은 클래스로 칠한 기본 `textarea`다. `TextField`에 이름표를 숨기는 길을 더할지(디자인 시스템 변경), 위젯이 기본 `textarea`를 쓸지는 명세가 정한다.
- 다크 모드 스위치는 사람이 들인 제안이다. ADR 0050은 밝음을 질문 페이지 설정이 사이트마다 정하는 값으로 두었고 바꾸는 단추는 정하지 않았다.
- 디자인 시스템에 없는 것: 셀렉트 부품(브라우저 기본 `select`를 쓰임새 토큰으로 칠했다), 폭을 채우는 주 버튼(덮개의 "확인하고 질문하기". `Button`에 폭을 정하는 prop이 없어 같은 쓰임새 토큰으로 그렸다), 아이콘 `chevron-down`, `external-link`(Lucide 모양을 선 1.5px로 그 자리에 그렸다). 그 주 버튼의 누르는 중은 `Button`의 `loading`과 같은 모양(글자를 감추고 가운데에 도는 표시)으로 손으로 그렸다. 도는 표시 `loader-circle`은 디자인 시스템에 `Spinner`(`web/packages/ui/src/components/atoms/Icon.tsx`)로 있지만 `Button`·`IconButton`의 불러오는 중과 값을 모르는 `Progress` 안에서만 쓰고, `Icon`의 이름에는 없다. 도는 표시는 그림에서 멈춰 있다.
- 짧은 고지는 위젯이 보일 때만 보인다. 상태를 묻는 동안 숨기는 것은 가정이다. 화면 문구(짧은 고지, 고지 전문, 사이트를 바꾼 뒤의 정보 글, 덮개의 실패 알림)는 시작 프롬프트의 제안이고, 실패 알림과 로그인 사이트 알림은 알림 부품(`Alert`)의 제목과 본문으로 나눴다.
- 예시 사이트 셋(계산 도우미 `calc-demo` 익명, 매장 계산 도우미 `store` 둘 다, 직원 계산 도우미 `staff` 로그인), 사이트 바꾸기의 예(매장 계산 도우미에서 계산 도우미로), 사이트의 긴 고지 글(지어낸 다섯 문단과 쿠키 문장), 위젯 자리 400×560px은 탐색용 가정이다. 다크 기본 화면과 고지 전문 펼침은 대화가 오간 위젯으로 그렸다.
- 키보드와 화면 읽기 프로그램의 제안(포커스 차례, 덮개가 나타날 때와 확인한 뒤의 포커스, 상태 알림, 비활성 단추 곁 글의 읽는 차례)은 `mk-how` 메모다.

그림이 시작 프롬프트나 근거 문서와 다른 자리다. 시작 프롬프트 "고른 뒤" 3대로 명세 전에 사람에게 묻는다. 셀프 리뷰가 파일을 읽어 찾았고, 렌더해 보지는 않았다(일지 2026-11-09-1839 "셀프 리뷰").

- 밀도. 시작 프롬프트는 밀도 보통(`data-density="regular"`)으로 그리라고 했는데, `pp-page.dc.html`은 위젯 자리에만 `data-density="regular"`를 달고 페이지 뿌리에는 달지 않았다. 디자인 토큰 CSS는 속성이 없으면 폭 768px 이상에서 촘촘(조작 높이 32px, 본문 14px)을 준다(`web/packages/ui/src/styles/theme.css`의 `@media (width >= 768px)`). 그래서 넓은 창에서는 위젯 자리 밖에서 밀도를 따르는 것(셀렉트 박스의 높이 `var(--control-h)`, 덮개의 고지 전문 글 `text-body`와 "확인하고 질문하기" 단추의 높이)이 촘촘으로 풀리고 위젯만 보통일 것으로 어림한다. `text-small`(고지 줄, 라벨)은 밀도와 상관없는 12px이다. 명세가 페이지 뿌리의 밀도를 정한다.
- 라이트 기본 화면. 시작 프롬프트는 확인한 기본 화면을 "위젯에 질문과 출력이 한 번 오간 모습"으로 그리라고 했는데, `pp-page.dc.html`은 대화를 다크 화면과 고지 전문 펼침에서만 그린다. 그래서 라이트에서 위젯이 보이는 기본 화면, 셀렉트 포커스, 사이트 하나, 둘 다 사이트 확인 뒤의 위젯은 소개가 든 첫 화면이다(확인한 사이트끼리 바꾼 화면은 빈 새 대화가 맞다).
- 입력창 이름. 화면 읽기 프로그램이 읽는 이름 "질문"은 `CONTEXT.md`가 요청(Request)의 피할 말로 든 낱말이다. 같은 용어집의 질문 페이지·고지·고지 확인 항목은 그 이름이나 정의에 "질문"을 쓴다. 위젯 입력창에서 두 말을 어떻게 가를지는 용어집과 함께 정한다.
- 둘 다 사이트의 단추 곁 글. ADR 0050 결정 "페이지"는 "같은 알림이 붙은 비활성 로그인 단추"라 적었고, 그림은 사람이 고른 다른 문구("로그인은 아직 제공하지 않습니다. 지금은 로그인 없이 질문할 수 있습니다.")를 알림 부품이 아닌 글 한 줄로 둔다. 명세가 ADR 문장을 손볼 때 함께 본다.
