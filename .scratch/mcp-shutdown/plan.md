# mcp-shutdown: 실행이 취소되거나 서버가 내려갈 때 MCP 서버 프로세스와 그 자식까지 함께 내려가게 한다.
**슬라이스:** 4
**Blocked by:** end-user-channel
**끝:** 2026-10-22

실행 타임아웃이나 serve 종료로 실행이 취소되어도 MCP 서버 프로세스와 그 자식이 내려가게 한다. web-widget에서 떼어 냈다(설계 인터뷰 2026-10-15, 일지 2026-10-15-17). end-user-channel 티켓 02가 넘긴 것: 타임아웃이 끊은 도구 연결의 닫기 뒤 실제 MCP 서버 프로세스가 내려가는지는 재지 않았다(티켓 03·02, 프로브 `run_timeout.py`도 태스크 그룹이 깨지지 않는 것까지다). 동시 실행 칸은 돌아와도 프로세스가 남으면 상한이 묶으려던 비용이 남는다. 2026-10-15 인터뷰에서 세션 스크래치패드의 `measure.py`(실제 core `run(timeout_seconds=)`와 실제 `McpTools`)로 손으로 본 것(커밋하지 않았다, 이 Windows 기계): `npx`로 띄운 everything은 cmd → node → cmd → node로 뜨고, 정상 종료와 닫는 도중의 기한에서는 함께 내려갔다. 계측을 단 회차에서 기한이 도구 호출 도중(5.0→12.93초, `CancelledError`)에 걸리자 맨 위 cmd만 내려가고 node와 그 자식은 실행 끝 12초 뒤에도 살아 있었다. 계측 없이 두 번 더 돌려도 남았고, 그 두 번에서는 명시한 `gc.collect()` 뒤에야 내려갔다. 설계 인터뷰(2026-10-16, 일지 2026-10-16-36)가 원인을 찾고 길을 정했다. 원인, 결정, 알려진 한계, 구현 티켓이 함께 고칠 자리는 ADR 0034가 원천이다. 요지는 어댑터가 앞서 기대던 어댑터 라이브러리 대신 mcp 2(`>=2.3,<3`)를 직접 써서 상류의 보호된 닫기를 받고, 서버 여럿은 차례로 닫으며, Linux에서는 런처가 서버의 프로세스 그룹을 거두는 것이다. 회귀 테스트는 파이썬 가짜 서버 둘과 하트비트 파일로 기본 테스트 묶음에서 Windows·Linux 모두 돈다. 재현 프로브(실제 `npx`의 everything, 이 PC)는 `.scratch/mcp-shutdown/probes/`에 커밋한다. 런처는 그것이 없으면 회귀 테스트가 CI(Linux)에서 빨갛다는 것을 먼저 보인 뒤 들이고, 그 측정으로 python-sdk에 이슈 초안을 써서 사용자의 승인을 받고 올린다(상류가 고치면 런처를 뺀다). 명세가 정하고 잴 것: 닫는 데 드는 시간과 그만큼 늦어지는 `run_failed` 전달·동시 실행 칸 반환·serve 종료(두 번째 Ctrl+C나 컨테이너의 강제 종료가 닫기를 끊는 경우도), 런처의 모양(자기도 든 그룹을 어떤 신호로 끌지, 그룹이 다 내려가기 전에 런처가 끝나는 길, 서버의 종료 코드를 넘기는 법)과 자리, Linux에서 서버 명령이 없을 때 실패가 런처 안에 묻히지 않고 서버 기동 실패 테스트가 초록인 길, Windows에서 `.venv\Scripts\python.exe`가 실제 파이썬을 자식으로 띄우는 런처라 가짜 서버의 프로세스가 한 겹 더 끼는 것(인터뷰의 측정 서브에이전트가 `wmic`로 부모 프로세스를 손으로 봤다), CLI의 Ctrl+C(네이티브 취소)에서 서버가 남는지, 결말 뒤 닫기의 예외에서도 서버가 내려가는지(end-user-continuation 명세가 넘긴 것), 인터뷰의 수(모두 커밋하지 않은 스크래치 스크립트의 것)를 프로브로 다시 재는 것. 계약은 바뀌지 않아 계약 티켓이 없다. 다른 기능을 막지 않는다. (2026-10-16 end-user-continuation to-tickets가 넘긴 것: 그 기능의 티켓 02가 결말이 정해진 뒤 도구 연결 닫기의 예외를 버리고 `run_failed`를 덧붙이지 않게 바꾼다(2026-10-20 #325로 들어왔다). core에는 그 예외를 기록하는 길이 없다. 그 닫기에서 도구 서버 프로세스가 남는지는 이 기능이 본다 — 타임아웃이 아닌 닫기 실패의 경우다. 이 기능은 그 티켓을 기다리지 않았다. 그 티켓 앞에도 같은 닫기가 돌았고 바뀐 것은 결말의 기록뿐이다) (2026-10-20 명세 `.scratch/mcp-shutdown/spec.md`: 위 "명세가 정하고 잴 것"은 명세가 닫았고 그 서두의 목록이 원천이다. 사용자가 고른 셋은 회귀 테스트의 자리(어댑터 테스트), Linux 런처의 부모 감시(부모가 죽어도 서버의 그룹을 끈다), CLI의 둘째 Ctrl+C(곧바로 끝낸다)이고, 뒤의 둘과 측정이 바꾼 어림 둘(CLI의 Ctrl+C, serve 종료 중의 강제 종료)은 ADR 0034의 2026-10-17 이력이고, 그 이력이 명세 때문에 거짓이 된 본문의 사실 둘(서버가 뜨자마자 죽을 때의 글, 대기열 34 대목)도 적는다. 컨테이너의 첫 프로세스로 띄울 때의 init은 배포 기능이 없어 넘기지 않고 구현 티켓이 README의 serve 안내에 한 줄로 알린다. 어댑터에서 나가는 예외는 내장 타입이다(여는 실패 `ConnectionError`, 호출 실패 `RuntimeError`, 연결 안의 예외는 겉봉 없이 그 객체). 마지막 것이 그때 main의 결함 하나를 고쳤다(티켓 02). MCP 서버가 붙은 실행이 연결을 연 채 트레이스를 쓰지 못하면 `run()`이 `run_failed`를 쓴 뒤 예외 그룹을 밖으로 올렸다(`probes/write_failure.py`). 결말 뒤 닫기가 예외로 끝나도 서버는 내려갔다(`probes/close_paths.py`의 `close_fails`). 시제품이 `83f09401` 위에서 두 OS의 검사와 테스트 658개를 지났고 대조군은 기대한 테스트만 빨갰다(PR 직전 리뷰를 반영한 회차. Linux 런처가 뜨기 전에 부모가 끝난 회차는 `probes/stale_parent.py`가 잰다). CLI 처리기는 2.3.0으로 올리는 티켓과 같이 가거나 그 앞에 서야 한다. 쪼개기는 to-tickets가 정한다) (2026-10-21 to-tickets: 명세 검토가 blocker 1·should-fix 12·nit 3을 냈고 명세의 주석과 티켓으로 닫았다. blocker는 서버를 닫는 도중에 온 첫 Ctrl+C가 2.3.0에서 CLI를 끝내지 못하는 것이고, 사용자가 첫 Ctrl+C를 실행을 감싼 취소 범위로 전하는 안을 골랐다(ADR 0034의 2026-10-21 이력, `probes/close_paths.py`의 `cli_ctrl_c_closing`). 티켓은 셋이고 사용자가 이 나눔을 골랐다(`.scratch/mcp-shutdown/issues/`). 01 의존성·어댑터·픽스처·닫기 사례 1·쪽 나눔·CLI 처리기 → 02 경계의 예외(닫기 사례 3·4)와 03 POSIX 런처(닫기 사례 2·5, 명령 찾아보기, 상류 이슈 초안)가 01 뒤에 나란히. 01은 헌법 파일(`tech.md`)에 닿아 둘을 막는다. 02와 03 가운데 마지막에 병합되는 쪽이 닫는다)
