# 취소된 실행의 MCP 서버도 내려간다: 어댑터가 mcp 2를 직접 쓰고, Linux에서는 런처가 서버의 프로세스 그룹을 거둔다

Status: ready-for-agent

슬라이스 4(`mcp-shutdown`). 근거는 이 기능의 결정인 `docs/adr/0034`(MCP 어댑터는 mcp 2를 직접 써서 취소된 실행의 MCP 서버도 끝까지 닫는다)다. 이 명세의 PR이 ADR 0034의 이력 하나(2026-10-17 "Linux 런처는 부모가 죽어도 서버의 프로세스 그룹을 끄고, CLI는 둘째 Ctrl+C에 곧바로 끝난다")를 올린다. 그 밖에 실행 타임아웃과 serve 종료의 `docs/adr/0014`, 최종 사용자 면의 상한과 동시 실행 칸의 `docs/adr/0023`, 실패 원인의 `docs/adr/0031`, `.scratch/plan.md`의 mcp-shutdown 행, 설계 인터뷰(`docs/journal/2026-10-16-36-mcp-shutdown-design.md`), 그 앞의 인터뷰(`docs/journal/2026-10-15-17-end-user-continuation-design.md`), end-user-continuation 명세(`.scratch/end-user-continuation/spec.md`)가 넘긴 결말 뒤 닫기의 물음이다. 이 명세가 "코드를 읽었다"고 적은 것은 `aa93cf7b`(이 명세를 처음 쓰는 동안의 origin/main)의 코드를 `30949cfc`(PR을 올리기 전의 origin/main)에서 다시 대 본 것과, PyPI에서 받아 해시를 대 본 mcp 2.3.0 휠(`sha256:dd0c44c0…`)과, 저장소 `.venv`에 설치된 uvicorn 0.53.0과 Python 3.12.10의 `asyncio`다. 그 사이 main에 들어온 end-user-continuation 티켓 02(#325)가 core의 실패 정책을 바꿨다. 실패를 연결을 닫기 전에 붙잡고 먼저 난 실패가 결말이다. 그래서 이 명세의 한 결정(연결 안의 예외는 겉봉 없이)의 근거가 바뀌었고, 결정은 그대로 두되 바뀐 근거로 다시 쟀다(아래 "경계를 넘는 예외").

이 명세는 설계 인터뷰와 다른 세션에서 썼다. 인터뷰의 대화가 없으므로 ADR 0034, `plan.md`의 행, 그 일지가 맥락을 대신했고, 그것으로 모자란 결정은 사용자에게 물었다. 용어는 `CONTEXT.md`의 `## 구조`(운영자, 최종 사용자, 어댑터, 포트, 도구, MCP 서버)와 `## 실행`(실행, 이벤트, 트레이스, 실행 상태, 실패 원인, 도구 연결, 등록부)을 따른다. "런처"는 어댑터 안의 부품이라 용어집에 넣지 않는다(명세가 정했다).

**넘겨받은 것은 아홉이다.** `plan.md` 행의 "명세가 정하고 잴 것"이 일곱이다. 닫는 데 드는 시간과 그만큼 늦어지는 것들(`run_failed` 전달, 동시 실행 칸 반환, serve 종료, 두 번째 Ctrl+C나 강제 종료가 닫기를 끊는 경우), 런처의 모양(끌 신호, 그룹이 다 내려가기 전에 런처가 끝나는 길, 서버의 종료 코드를 넘기는 법)과 자리, Linux에서 서버 명령이 없을 때의 실패와 서버 기동 실패 테스트, Windows의 `.venv` 파이썬이 한 겹 더 끼는 것, CLI의 Ctrl+C, 결말 뒤 닫기의 예외, 설계 인터뷰의 수를 프로브로 다시 재는 것이다. 여덟째는 PR #266 claude-review 첫 회차 Nit와 둘째 회차 Minor가 넘긴 것으로, ADR 0034의 어댑터·런처 항목에 뭉쳐 있던 열린 물음을 요구 항목으로 나눠 적는 것이다(아래 "어댑터"와 "Linux 런처"의 하위 항목). 아홉째는 셋째 회차 Minor가 넘긴 것으로, 어댑터가 mcp의 예외를 `run_failed`의 글로 그대로 내보내는 것이 "서드파티는 경계에서 감싼다"(`CODING_STANDARDS.md`)와 맞는지다(아래 "경계를 넘는 예외"). **셋은 사용자가 이 명세를 쓰며 골랐다.** 회귀 테스트의 자리(어댑터 테스트), Linux 런처의 부모 감시(부모가 죽어도 서버의 그룹을 끈다), CLI의 둘째 Ctrl+C(곧바로 끝낸다)다. 셋 다 추천을 맨 앞에 둔 선택 화면에서 물었다. 뒤의 둘은 ADR 0034의 결정과 알려진 한계를 바꾸므로 **ADR 0034의 이력 하나**를 이 PR에 초안으로 올리고 사용자가 승인한다. 그 이력은 이 명세의 측정이 바꾼 어림 둘(알려진 한계의 CLI 문장, serve 종료 항목의 강제 종료 문장)과, 이 명세가 정한 것 때문에 거짓이 된 본문의 사실 둘(서버가 뜨자마자 죽을 때의 글, 구현 티켓이 고칠 자리의 대기열 34 대목)도 함께 적는다. **열여덟은 명세가 ADR의 문장을 구현이 닿는 자리로 옮기다 스스로 정했고 각 절에 "(명세가 정했다)"로 표시한다.** 런처를 용어집에 넣지 않는 것, 서버들을 연 순서의 반대로 닫는 것, 경계를 넘는 예외 셋(서버를 여는 실패는 `ConnectionError`, 도구 호출의 실패는 `RuntimeError`, 연결 안의 예외는 겉봉 없이 그대로), POSIX에서 띄우기 전에 명령을 찾아보는 것, 런처의 자리와 띄우는 법, 런처가 그룹의 우두머리가 아니면 띄우지 않는 것, 런처가 표준 입출력의 자기 사본을 놓는 것, 런처가 그룹을 SIGKILL로 한 번에 끄는 것, 서버의 종료 코드를 넘기지 않는 것, 런처가 서버를 띄우지 못하면 한 줄과 종료 코드 127로 끝나는 것, CLI 처리기를 CLI 채널의 함수로 두는 것, 중단된 CLI가 지금과 같은 꼴로 끝나며 추적 대신 한 줄을 남기는 것, 컨테이너의 init을 README의 serve 안내가 알리는 것, 결말 뒤 닫기의 예외를 프로브로 재고 테스트로 고정하지 않는 것, 닫기 테스트의 사례 다섯, CLI 처리기의 테스트다. 표시가 없는 것은 ADR이나 기존 규칙에서 나왔다. **거부한 안은 열여덟이고**(셋은 사용자가 고르지 않은 안이다) 각 절에 "거부한 안"으로 적었다. 결정이 더 필요해지면 멈추고 ADR의 이력을 제안한다.

## Problem Statement

실행 타임아웃이 도구 호출 도중에 걸리면, 그 실행이 띄운 MCP 서버가 내려가지 않고 남는다. 2026-10-15 인터뷰가 이 PC에서 실제 `npx`의 everything 서버로 그것을 봤고, 이 명세가 같은 모양을 가짜 서버로 다시 쟀다. 지금 판(mcp 1.30.0)에서는 기한 뒤 닫기가 첫 기다림에서 끊겨 감싸는 프로세스(npx나 cmd에 해당)만 꺼지고, 입력이 닫혀도 끝나지 않는 그 아래의 진짜 서버는 3초 뒤에도 살아 있었다(`close_paths.py`의 `cancel`, Windows와 Linux 모두). 원인은 ADR 0034가 적었다. 닫기 절차가 취소된 범위 안에서 돌아 첫 await에서 다시 취소되기 때문이다. 실제 everything은 이 명세의 프로브에서 1초 뒤에 남았다가 4초 뒤에는 없었다(`everything.py`). 끊긴 연결의 입력이 곧 닫혀 입력의 끝을 보고 스스로 끝난 것으로 본다(어림, 가르지 않았다). 인터뷰는 core `run()`을 거친 실행에서 그것이 `gc.collect()`까지 남는 것을 봤다.

남은 서버는 운영자에게 비용이다. 최종 사용자 경로는 동시 실행의 칸으로 비용을 묶는데(ADR 0023), 칸은 실행이 끝나면 돌아오지만 프로세스는 남아 메모리와 그 서버가 쥔 자원(브라우저, 파일, 네트워크 연결)을 계속 쓴다. 기한에 걸리는 실행이 잦을수록 쌓인다. 운영자가 serve를 멈출 때도 같은 길이다. 앱의 수명이 도는 실행을 취소하면 닫기가 같은 자리에서 끊긴다. 이 명세가 잰 바로는 Linux에서는 serve가 끝난 뒤에도 서버가 남았고, Windows에서는 serve 프로세스가 끝나는 순간 Job Object가 닫혀 서버도 함께 꺼졌다(`serve_shutdown.py`의 `graceful`, mcp 1.30.0).

Linux에는 빈틈이 하나 더 있다. 입력이 닫히면 스스로 끝나는 서버가 자식을 남기면, 정상으로 닫아도 그 자식이 남는다(`close_paths.py`의 `exit_child_normal`). mcp 2.x로 올려도 그렇다. 상류의 닫기는 서버가 유예 안에 스스로 끝나면 묶음 끄기를 건너뛰고, Windows는 그때도 Job Object에 남은 프로세스를 거두지만 POSIX에는 그 장치가 없기 때문이다(ADR 0034).

## Solution

**MCP 어댑터가 mcp 2(`>=2.3,<3`)를 직접 쓴다(ADR 0034).** 서버마다 상류의 `stdio_client`와 `ClientSession`을 열고 닫는다. 상류는 닫기 전체를 라이브러리 안에서 취소로부터 보호하고 기다림마다 시간 상한을 두며, Windows에서는 닫는 즉시 남은 Job Object를 정리한다. 그래서 실행 타임아웃이나 serve 종료로 실행이 취소되어도 서버와 그 자식이 내려간 뒤에 실행의 태스크가 끝난다. 입력이 닫혀도 끝나지 않는 서버를 닫는 데는 서버 하나에 약 2초가 든다.

**Linux에서는 서버를 작은 런처 뒤에 띄운다(ADR 0034).** 런처가 서버의 프로세스 그룹을 이끌고, 서버가 끝나거나 런처를 띄운 agent-os 프로세스가 죽으면 그룹 전체를 끈다(부모가 죽는 경우는 사용자가 골랐다. ADR 0034의 2026-10-17 이력). Windows는 상류의 Job Object가 같은 일을 하므로 런처를 쓰지 않는다.

**CLI는 Ctrl+C를 직접 받는다(사용자가 골랐다. ADR 0034의 2026-10-17 이력).** 첫 번째는 지금처럼 실행을 취소해 서버를 닫으며 끝내고, 두 번째는 곧바로 끝낸다. mcp 2.3.0에서는 닫는 도중의 둘째 Ctrl+C가 CLI를 멈추게 해서다(측정). 둘 다 지금처럼 Ctrl+C로 끝난 꼴(셸에서 130)로 끝나고, 추적 대신 한 줄을 남긴다(명세가 정했다).

**어댑터에서 나가는 예외는 내장 타입이다(명세가 정했다).** 서버를 여는 동안의 실패는 서버 이름과 명령과 원인을 든 `ConnectionError`, 도구 호출의 실패는 서버와 도구를 든 `RuntimeError`이고, 연결 안에서 난 예외는 mcp의 태스크 그룹이 씌운 겉봉 없이 그 객체 그대로 나온다. 운영자는 `run_failed`에서 `ExceptionGroup[ExceptionGroup[MCPError: Connection closed]]` 대신 어느 서버가 무엇 때문에 열리지 않았는지를 읽는다. 연결을 연 채 트레이스를 쓰지 못한 실행은 `run_failed`를 쓴 뒤 예외 그룹을 밖으로 올리지 않고 그것으로 끝난다(지금은 올린다. 측정).

**core와 HTTP 채널의 코드는 바뀌지 않는다.** 포트(`ToolSource`, `ToolConnection`), sdk, `openapi.json`이 그대로라 계약 티켓이 없다. serve 종료는 지금 그대로 실행을 취소하고, 닫기가 끝날 때까지 기다리는 것은 상류의 보호된 닫기가 한다. 그 사실을 말하는 독스트링과 지침의 문장을 고친다.

## User Stories

### 운영자

1. 운영자로서, 도구 호출 도중에 실행 타임아웃이 걸려도 그 실행이 띄운 MCP 서버와 그 아래 프로세스가 모두 내려가기를 바란다. 남은 프로세스가 메모리와 서버가 쥔 자원을 계속 쓰기 때문이다.
2. 운영자로서, `npx`나 `uvx`처럼 서버를 감싸 띄우는 명령을 써도 감싼 프로세스만이 아니라 그 아래의 진짜 서버까지 내려가기를 바란다. 지금 남는 것이 바로 그 진짜 서버다.
3. 운영자로서, 실행 타임아웃으로 실패한 실행이 지금처럼 `run_failed`("실행이 N초 안에 끝나지 않았다")로 끝나기를 바란다. 닫기를 보호하는 것이 결말을 바꾸지 않는다(측정에서 호출한 쪽의 기한 범위가 그대로 기한을 받았다).
4. 운영자로서, 기한 뒤 `run_failed`가 오기까지 늦어지는 시간을 알고 싶다. 입력이 닫혀도 끝나지 않는 서버는 하나에 약 2초, SIGTERM까지 무시하는 서버는 Linux에서 약 4초다.
5. 운영자로서, serve를 멈출 때 도는 실행의 MCP 서버가 정리된 뒤에 프로세스가 끝나기를 바란다. 멈추는 데 연결 유예 5초에 닫기 약 2초가 더 든다.
6. 운영자로서, serve를 멈추며 Ctrl+C를 두 번 눌러도 서버가 정리되기를 바란다. uvicorn의 강제 종료는 앱의 수명 닫기를 건너뛰지만, 그 뒤 asyncio가 남은 태스크를 취소하고 끝나기를 기다리는 동안 닫기가 끝까지 간다(Linux에서 쟀다).
7. 운영자로서, Linux에서 agent-os 프로세스가 갑자기 죽어도(`kill -9`, 메모리 부족으로 강제 종료, 닫는 도중의 또 다른 Ctrl+C) MCP 서버가 남지 않기를 바란다(사용자가 골랐다). Windows는 프로세스가 끝날 때 Job Object가 닫혀 이미 그렇다.
8. 운영자로서, 입력이 닫히면 스스로 끝나는 서버가 남긴 자식도 Linux에서 함께 내려가기를 바란다. Windows에서는 상류의 Job Object가 이미 거둔다.
9. 운영자로서, 서버 명령을 잘못 적었으면 `run_failed`가 어느 서버의 어느 명령을 찾지 못했는지 말하기를 바란다. Linux에서도 Windows에서도 같은 꼴의 글이다.
10. 운영자로서, 서버가 뜨자마자 죽으면 `run_failed`가 그 서버의 이름과 연결이 닫혔다는 원인을 들기를 바란다. 지금은 두 겹의 `ExceptionGroup` 안에 `McpError: Connection closed`만 있다.
11. 운영자로서, MCP 서버가 붙은 실행이 연결을 연 채 트레이스를 쓰지 못했을 때 `run_failed`를 쓴 뒤에는 그것으로 끝나기를 바란다. 지금은 core가 그 연결을 닫을 때 들어가는 닫기 신호(`GeneratorExit`)를 mcp의 태스크 그룹이 두 겹으로 감싸, `run()`이 결말을 쓴 뒤에도 예외 그룹을 밖으로 올린다(core에 진짜 어댑터를 물린 프로브로 쟀다). 에이전트가 낸 예외는 core가 연결을 닫기 전에 붙잡아 이미 `run_failed`에 그대로 실린다(같은 프로브).
12. 운영자로서, 도구 호출 도중에 서버가 죽으면 그 도구 결과가 어느 서버의 어느 도구가 실패했는지 말하기를 바란다. 모델과 트레이스가 그 글을 본다.
13. 운영자로서, 서버 여럿을 쓰는 에이전트의 실행이 기한에 걸리면 서버들이 하나씩 닫혀 늦어짐이 서버 수에 비례한다는 것을 안다(ADR 0034).
14. 운영자로서, Linux의 프로세스 목록에서 서버 위에 작은 파이썬 프로세스(런처)가 하나씩 보이는 까닭을 알고 싶다. 서버의 프로세스 그룹을 거두는 것이 그 일이다.

### CLI를 쓰는 사람(운영자, 플러그인 작성자)

15. CLI를 쓰는 사람으로서, `agent-os run`·`resume` 도중에 Ctrl+C를 한 번 누르면 서버가 정리된 뒤 끝나기를 바란다. 약 2~3초가 든다(측정).
16. CLI를 쓰는 사람으로서, 기다리기 싫어 Ctrl+C를 한 번 더 누르면 CLI가 곧바로 끝나기를 바란다(사용자가 골랐다). 지금 판(1.30.0)은 Windows에서 그랬고 Linux에서는 2초쯤 뒤 서버를 남긴 채 끝났으며, 2.3.0을 그대로 쓰면 두 OS에서 멈춘다(측정).
17. CLI를 쓰는 사람으로서, 곧바로 끝낸 뒤에도 서버가 남지 않기를 바란다. Windows에서는 Job Object가, Linux에서는 런처의 부모 감시가 거둔다(측정).
18. CLI를 쓰는 사람으로서, 중단으로 끝난 CLI가 지금처럼 Ctrl+C로 끝난 꼴로 끝나기를 바란다. 셸에서 130이라 끝남(0)·실패(1)·일시정지(3)와 갈리고, 그 꼴을 보고 Ctrl+C를 알아보는 부모 프로세스가 지금과 같이 반응한다(명세가 정했다).

### 최종 사용자

19. 최종 사용자로서, 내 실행이 시간 초과로 끝난 뒤 다음 실행을 곧 시작할 수 있기를 바란다. 동시 실행의 칸은 닫기가 끝난 뒤 돌아오므로 약 2초 늦게 돌아온다.
20. 최종 사용자로서, 실패 항목이 지금과 같은 고정 문구와 원인을 들기를 바란다. 닫기를 보호하는 것이 항목을 바꾸지 않는다.

### MCP 서버 플러그인 작성자

21. 플러그인 작성자로서, 매니페스트의 서버 명령과 인자를 지금처럼 적기를 바란다. 런처는 어댑터가 끼우는 것이라 매니페스트가 모른다.
22. 플러그인 작성자로서, 서버가 입력이 닫히면 스스로 끝나는 것이 가장 빠른 닫기라는 것을 안다. 그러면 닫는 데 0.5초도 들지 않는다(측정).
23. 플러그인 작성자로서, 내 서버가 스스로 새 세션으로 떼어 낸 자식은 런처도 상류도 거두지 못한다는 것을 안다(ADR 0034의 알려진 한계).

### 런타임 기여자

24. 기여자로서, 닫기 회귀 테스트가 기본 테스트 묶음에서 이 PC(Windows)와 CI(Linux) 모두 돌기를 바란다. 새 라이브러리도 Node도 네트워크도 필요 없다(ADR 0034).
25. 기여자로서, 닫기 테스트가 실제 MCP 어댑터를 core와 같은 취소 범위 안에서 열어 재기를 바란다(사용자가 골랐다). 서버를 닫는 코드는 어댑터뿐이다(CLI 처리기는 닫기를 기다릴지만 정한다).
26. 기여자로서, Linux에서 런처를 빼면 닫기 테스트가 빨개지는 것을 보고 싶다. 런처가 하는 일을 테스트가 실제로 보는지가 그것으로 선다(ADR 0034, 이 명세의 측정).
27. 기여자로서, mcp 3이 나오면 닫기 테스트와 프로브를 다시 돌린 뒤 결정으로 들이기를 바란다(ADR 0034, 판 범위 `<3`).
28. 기여자로서, 어댑터의 예외가 포트 밖으로 mcp의 타입을 내보내지 않기를 바란다(`CODING_STANDARDS.md`의 "서드파티는 경계에서 감싼다").
29. 기여자로서, 런처가 실수로 다른 프로세스 그룹을 끄지 않기를 바란다. 그룹의 우두머리가 아니면 아무것도 띄우지 않는다.
30. 기여자로서, 상류가 POSIX의 빈틈을 고치면 런처를 뺄 계기가 문서에 있기를 바란다(ADR 0034의 "상류에 알린다").

## Implementation Decisions

ADR 0034와 그 2026-10-17 이력이 결정한 것을 구현이 닿는 자리로 옮겨 적는다. 이 명세가 정한 것은 서두에 셌고 각 절에 표시한다. 시제품은 `.scratch/mcp-shutdown/probes/prototype/`(어댑터, 런처, 테스트)와 `close_paths.py`의 `_run_with_force_exit`(CLI 처리기)에 있고, `full_stack.py`가 저장소 사본에 얹어 두 OS에서 검사와 테스트를 돌렸다(아래 "소비 지점까지 잰 것"). 시제품은 이 명세가 정한 모양을 구현할 수 있다는 근거이고, 구현 티켓이 옮길 때는 지금 코드의 관례를 따른다.

### 의존성 (ADR 0034)

- **`langchain-mcp-adapters`를 빼고 `mcp>=2.3,<3`을 직접 의존으로 둔다.** 하한은 이 명세가 잰 판 2.3.0이다. 3은 닫기 테스트와 프로브를 다시 돌린 뒤 ADR 0034의 이력으로 들인다.
- **락의 변화는 설계 인터뷰가 본 것과 같다.** `full_stack.py`의 `uv lock`이 mcp를 1.30.0에서 2.3.0으로 올리고 `mcp-types` 2.3.0과 `opentelemetry-api` 1.45.1을 더하며 `langchain-mcp-adapters`·`httpx-sse`·`pydantic-settings`·`python-dotenv`를 뺐다(패키지 84개, `30949cfc` 위에서). anyio 4.15.1과 pydantic 2.13.5는 그대로다.
- **Windows에서 mcp 2.3.0은 `pywin32`를 끌어온다.** 저장소의 락에 이미 `pywin32` 312가 있다. 이 PC의 uv 0.10.8은 `uv run --isolated --with`의 임시 환경에서 그 휠을 설치하지 못했고(scripts 폴더의 임시 항목을 거부했다), `uv venv`로 만든 환경과 저장소 사본의 `uv sync`에서는 설치했다(손으로 봤다). 프로브의 README가 환경을 `uv venv`로 만드는 까닭이다.

### 어댑터 (ADR 0034)

- **서버마다 상류의 `stdio_client`와 `ClientSession`을 열고, `initialize()` 뒤 `list_tools`를 커서 끝까지 따라 도구 목록을 만든다.** 도구는 `ToolSpec`(이름, 설명, 입력 스키마)으로, 호출 결과는 `ToolResult`로 바꾼다. 결과의 글은 텍스트 블록과 텍스트 리소스의 글을 이어 붙인 것이고, 도구가 `isError`를 돌려주면 `ok=false`다. 없는 도구는 지금처럼 `LookupError`다. 포트의 모양은 그대로다.
- **서버들은 연 순서의 반대로 하나씩 닫는다(명세가 정했다).** ADR 0034가 "차례로 닫는다"고 정한 것을 지금 어댑터가 쓰는 탈출 스택의 순서 그대로 옮겼다. 거부한 안은 연 순서대로 닫는 것이다. 뒤에 연 서버가 앞의 것에 기대는 경우가 없어 순서로 얻는 것이 없고, 탈출 스택을 쓰지 않으면 연결이 열리다 만 서버를 닫는 길을 손으로 짜야 한다.
- **닫는 데 드는 시간.** 상류의 닫기는 입력을 닫고 서버가 끝나기를 2초 기다린 뒤, 끝나지 않으면 묶음을 끈다(코드를 읽었다). Windows의 묶음 끄기는 Job Object를 곧바로 끝내고, POSIX는 그룹에 SIGTERM을 보내 2초 기다린 뒤 SIGKILL을 보낸다. 잰 값은 아래 표다(`close_paths.py`, README의 결과). ADR 0034가 상수를 더해 어림한 최악값(Windows 약 4.5초, Linux 약 6.5초)은 쓰기 비우기(0.5초)와 끈 뒤의 확인(2초)을 모두 더한 것이다. 앞의 것은 서버가 입력을 읽지 않아 쓰기가 막혔을 때만, 뒤의 것은 SIGKILL로도 끝나지 않는 프로세스에서만 다 쓴다(코드를 읽은 어림).

  | 서버의 모양 | Windows | Linux |
  |---|---|---|
  | 입력이 닫히면 스스로 끝난다(자식을 남긴다) | 0.20~0.42초 | 0.18~0.46초 |
  | 입력이 닫혀도 끝나지 않는다 | 2.0~2.2초 | 2.0초 |
  | SIGTERM까지 무시한다 | 해당 없음(곧바로 끝낸다) | 4.0초 |

  범위는 mcp 2.3.0의 갈래(Windows는 venv 파이썬을 끼운 것, Linux는 런처의 세 갈래)를 합친 것이다. 셀프 리뷰 앞의 회차도 같은 크기였다.

- **그만큼 늦어지는 것.** 기한 뒤의 `run_failed`는 진입점이 취소 범위를 나온 뒤에 쓰고 그 범위가 도구 연결의 닫기를 감싸므로(`core/run.py`, 코드를 읽었다), 닫기만큼 늦게 온다. 최종 사용자 경로의 동시 실행 칸은 실행의 태스크가 끝나는 자리에서 돌아오므로(`.claude/rules/channel.md`) 같은 만큼 늦다. 둘 다 코드를 읽은 어림이고, 진짜 core와 채널에 진짜 어댑터를 물려 재지 않았다. `plan.md`의 행은 이 둘을 재라고 넘겼지만, 늦어짐의 크기는 위 표의 닫기 시간이고 그것이 결말과 칸 반환 앞에 놓인다는 것은 코드의 순서라 따로 재지 않았다(명세 축 리뷰가 짚었다). 테스트는 이 늦어짐을 고정하지 않는다. 값이 상류의 상수와 서버의 모양에 달려 있어서다.

#### 서버를 여는 실패 (넘겨받은 것: Linux의 서버 기동 실패)

- **POSIX에서는 서버를 띄우기 전에 명령을 찾아본다(명세가 정했다).** 어댑터가 실행 경로에서 서버 명령을 찾고(`shutil.which`), 없으면 띄우지 않고 `FileNotFoundError`를 낸다. 찾은 경로를 런처에 넘긴다(이름만 준 명령이면 실행 경로에서 찾은 경로이고, `./srv`처럼 경로가 든 명령이면 받은 그대로다. 코드를 읽었다). `shutil.which`는 실행 권한이 있는 파일만 찾으므로 실행 권한이 없는 명령도 여기서 "찾지 못했다"가 된다. 런처 없이 띄웠다면 `PermissionError`였을 것이다(코드를 읽은 어림). 런처 뒤에서는 명령이 없다는 실패가 런처 안에서 나 클라이언트에는 연결이 닫힌 것으로만 보이기 때문이다. 이 명세가 Linux에서 재 보니 런처 없이는 `FileNotFoundError: [Errno 2] No such file or directory: '…'`가 왔고, 런처 뒤에서는 `ExceptionGroup[ExceptionGroup[MCPError: Connection closed]]`가 왔으며 원인은 런처가 표준 에러에 남긴 한 줄에만 있었다(`close_paths.py`의 `missing_command`). 상류가 서버를 띄울 때 넘기는 환경의 `PATH`는 이 프로세스의 `PATH` 그대로라(코드를 읽었다) 찾아본 결과가 띄울 때와 같다. 거부한 안은 런처가 그 실패를 구별되는 종료 코드로 알리는 것이다. mcp의 클라이언트는 종료 코드를 읽지 않아(코드를 읽었다) 어댑터가 그것을 받을 길이 없다. 또 하나의 거부한 안은 Windows에서도 찾아보는 것이다. 상류가 `.cmd`·`.bat`·`.exe`·`.ps1`까지 붙여 찾고 없으면 그대로 띄워 `FileNotFoundError`가 나므로(코드를 읽었다, 측정) 지금과 같고, 찾아보면 상류가 받는 `.ps1` 서버를 어댑터가 막을 수 있다.

#### 경계를 넘는 예외 (넘겨받은 것: PR #266 셋째 회차 Minor)

- **서버를 여는 동안의 실패는 `ConnectionError`다(명세가 정했다).** 띄우기, 세션 열기, `initialize()`, 도구 목록 읽기 가운데 어디서든 예외가 나면 어댑터가 서버 이름과 매니페스트의 명령과 원인을 든 `ConnectionError`로 바꿔 내고 원래 예외를 원인(`__cause__`)으로 잇는다. 원인의 글은 예외 그룹을 펼친 것이다. 취소(실행 타임아웃이 연결 도중에 오는 것)는 예외가 아니라 바꾸지 않는다. 그래서 서버를 여는 실패의 글이 OS와 무관하게 "MCP 서버 이름(명령)에 붙지 못했다: 원인"의 꼴이 된다. 그 실패 원인(ADR 0031)은 "도구 연결"이지만, 같은 원인이어도 서버를 연 뒤의 실패(선언한 도구가 없을 때의 `LookupError` 같은 것)는 이 꼴이 아니다. 원인의 자리가 연결이라는 것은 end-user-continuation 명세의 "실패 원인 — 가르는 법"이 자리로 정하므로 이 타입과 무관하다.
- **도구 호출의 실패는 `RuntimeError`다(명세가 정했다).** 세션이 호출에서 예외를 내면(서버가 호출 도중에 죽었거나 프로토콜 오류를 돌려줬다) 서버와 도구를 든 `RuntimeError`로 바꾼다. core는 지금처럼 그것을 실패한 도구 결과로 바꿔 모델에 돌려준다(`.claude/rules/core.md` 실패 정책). 도구가 `isError`로 돌려준 실패는 예외가 아니라 결과라 그대로다.
- **연결 안에서 난 예외는 겉봉 없이 그대로 나온다(명세가 정했다).** 연결 안에서 빠져나온 예외는 상류의 태스크 그룹 두 겹을 지나며 `ExceptionGroup[ExceptionGroup[예외]]`가 된다(`BaseException`이면 `BaseExceptionGroup`). 부르는 쪽이 연결을 연 채 낸 예외, 연결 안의 yield에 멈춘 제너레이터를 닫을 때 들어가는 `GeneratorExit`, 먼저 연 서버의 태스크 그룹을 지나는 여는 실패가 모두 그렇다. 지금 판도 2.3.0도 같았다(`close_paths.py`의 `raise_inside`, `write_failure.py`). 어댑터는 여는 단계부터 연결 안에서 빠져나온 예외를 기억해 두고, 닫기를 지나 나온 그룹을 한 겹씩 내려가며 겹마다 하나만 들었는지 보다가 그 예외를 만나면 그 자리에서 멈추고 그 객체를 다시 던진다. 던진 것이 그 자신 예외 그룹이면(에이전트가 낸 그룹) 그 그룹이 그대로 나온다. 시제품의 첫 판은 잎까지 내려간 뒤에 견줘 그 경우에 겉봉을 벗기지 못했다(셀프 리뷰가 짚었다). 그 밖의 그룹(닫기에서 다른 예외가 더 났다)은 그대로 낸다.
  - **보이는 자리는 둘이다.** 하나는 서버를 여는 실패의 글이다. 뜨자마자 끝나는 서버의 `ConnectionError`가 두 겹 그룹에 싸여 `run_failed`에 실리지 않는다. 다른 하나는 core가 연결을 닫는 길이다. core는 결말 전의 트레이스 쓰기가 실패하면 `run_failed`를 쓴 뒤 연결 안에 멈춘 제너레이터를 그 자리에서 닫는다(`core/run.py`의 `_drive`, 코드를 읽었다). 그때 들어간 `GeneratorExit`가 그룹으로 나오면 그 닫기가 그룹을 내 `run()`이 결말을 쓴 뒤에도 예외로 끝난다. core에 진짜 어댑터를 물린 프로브로 재 보니, 둘째나 셋째 쓰기만 실패하는 트레이스에서 지금 판(langchain-mcp-adapters와 mcp 1.30.0, Windows)과 벗기지 않는 2.3.0 시제품(두 OS)은 `run_failed`(원인 그 밖)를 쓴 뒤 `BaseExceptionGroup[BaseExceptionGroup[GeneratorExit]]`를 올렸다. 벗기는 시제품은 가짜 포트를 쓰는 core 테스트처럼 `run_failed`로 끝났다(두 OS. `write_failure.py`).
  - **에이전트의 예외와는 무관하다.** 에이전트가 낸 예외와 런타임 자신의 예외는 core가 연결을 닫기 전에 붙잡으므로(`.claude/rules/core.md`의 실패 정책, end-user-continuation 티켓 02) 이 결정이 없어도 `run_failed`의 글이 그 예외 하나이고 원인은 던진 자리다. 같은 프로브가 둘을 쟀다. 에이전트가 도구를 부른 뒤 낸 `ValueError`는 원인이 에이전트 코드였고, 실패하는 도구를 부른 에이전트가 잡지 않은 런타임의 `ToolError`는 원인이 도구 실패였다(지금 판과 벗기지 않는 시제품 모두, 밖으로 나온 예외 없음). 처음 판은 둘의 원인을 모두 에이전트 코드로 적었다(명세 축 리뷰가 짚어 프로브에 둘째 사례를 더했다). 이 명세의 처음 판은 이 결정의 근거를 그 글에 두었다. 티켓 02가 그 근거를 없앴고 위의 둘이 남았다.
  - 거부한 안은 둘이다. 하나는 그룹을 끝까지 펼쳐 잎 하나를 고르는 것이다. 에이전트 코드가 스스로 낸 예외 그룹까지 펼친다. 다른 하나는 core의 연결 자리(`_connected`)에서 그룹을 벗기는 것이다. 연결이 안의 예외를 바꾸지 않는다는 것은 core 테스트의 가짜 포트(`FakeTools`)가 이미 따르는 모양이라, 그것을 어기는 쪽(상류의 태스크 그룹)을 아는 어댑터가 고친다. core에서 벗기면 core가 mcp의 구조를 알게 되고, 가짜 포트로는 그 길을 재지 못한다.
- **이 셋으로 "서드파티는 경계에서 감싼다"가 선다.** 지금은 mcp의 예외 객체가 포트를 넘어 core에 닿고 core가 그것을 글로 바꿔 `run_failed`에 싣는다(`core/run.py`의 `_describe`, 코드를 읽었다). 연결을 닫는 길에서는 mcp의 그룹이 `run()` 밖으로까지 나간다. 객체가 sdk로 가지는 않지만 그 그룹은 `run()`을 부르는 채널까지 가고, mcp의 구조(두 겹의 그룹)와 타입 이름이 운영자가 읽는 글까지 간다. 거부한 안은 지금 그대로 두는 것이다. 글이 어느 서버의 실패인지 말하지 않고, 서버가 여럿이면 운영자가 가를 길이 없으며, 결말을 쓴 실행이 예외로 끝난다.

#### 테스트 픽스처 서버 (ADR 0034)

- **`mcp.server.fastmcp`가 없어져 `mcp.server.mcpserver`의 `MCPServer`로 옮긴다.** 2.x 서버는 `ToolError`가 아닌 예외의 글을 클라이언트에 보내지 않으므로 실패를 내는 픽스처 도구가 `ToolError`를 던진다(코드를 읽었다, 시제품의 픽스처가 그 테스트를 지났다).

### Linux 런처 (ADR 0034. 부모 감시는 사용자가 골랐다)

- **자리와 띄우는 법(명세가 정했다).** 런처는 어댑터 층(`agent_os.adapters`) 안의 모듈 파일 하나이고 표준 라이브러리만 쓴다. 어댑터가 POSIX에서 서버 명령을 `<이 프로세스의 파이썬> -I <런처 파일> <찾은 서버 명령> <인자…>`로 바꿔 상류에 넘긴다. `-I`는 런처 파일의 폴더가 `sys.path`에 들어 같은 폴더의 어댑터 모듈 이름(`mcp` 등)이 표준 라이브러리나 패키지를 가리지 않게 한다. 거부한 안은 패키지 모듈로 띄우는 것(`-m`)이다. 런처가 뜰 때마다 `agent_os` 패키지의 `__init__`과 그것이 import하는 것을 읽는다.
- **그룹의 우두머리가 아니면 띄우지 않는다(명세가 정했다).** 상류는 POSIX에서 서버를 새 세션으로 띄우므로(`start_new_session=True`, 코드를 읽었다) 런처가 그룹의 우두머리다. 런처는 시작하자마자 그것을 보고, 아니면 한 줄을 남기고 서버를 띄우지 않고 끝난다. 런처가 그룹을 끄는 것은 자기 그룹을 끄는 것이라, 새 세션 없이 띄우면 부른 쪽의 그룹이 꺼진다.
- **서버는 같은 그룹의 자식이고 표준 입출력을 상속으로 물려받는다. 런처는 자기 사본을 놓는다(명세가 정했다).** 입력과 출력을 중간에서 옮기지 않으므로 지연이 없다(ADR 0034). 런처가 출력의 쓰는 쪽을 쥐고 있으면 서버가 끝나도 클라이언트가 출력의 끝을 보지 못한다. 그래서 런처는 서버를 띄운 뒤 자기 입력과 출력을 `/dev/null`로 바꾼다. 표준 에러는 남긴다(띄우기 실패를 알린다).
- **끄는 때는 둘이다.** 서버가 끝났을 때와, 런처를 띄운 부모가 죽었을 때다(사용자가 골랐다). 런처는 서버를 기다리는 동안 0.2초마다 부모 프로세스 번호를 보고, 바뀌었으면(부모가 죽어 다른 프로세스에 입양되었다) 서버가 끝나기 전이라도 끈다. 부모 감시 없는 런처로는 serve를 SIGKILL로 끄거나 닫기 도중에 SIGINT가 한 번 더 와 serve가 닫기를 마치지 못하고 끝나면, 입력이 닫혀도 끝나지 않는 서버와 그것을 감싼 프로세스가 남았다. 부모 감시가 있으면 3초 안에 내려갔다(`serve_shutdown.py`의 `sigkill`·`force_then_interrupt`, Linux). CLI를 둘째 Ctrl+C로 곧바로 끝낸 경우도 같다(`close_paths.py --cli-handler force`의 `cli_ctrl_c_twice`). 거부한 안은 서버가 끝날 때만 끄는 것(ADR 0034의 처음 결정, 사용자가 고르지 않았다)과, 부모가 죽으면 커널이 신호를 보내게 하는 길(`prctl`의 `PR_SET_PDEATHSIG`)이다. 뒤의 것은 표준 라이브러리에 없어 `ctypes`로 libc를 불러야 하고, 그 호출은 타입이 없어 원칙 III의 판정자가 막거나 pyright strict가 알 수 없는 타입으로 짚는다(어림).
- **끄는 신호는 SIGKILL이고 그룹 전체를 한 번에 끈다(명세가 정했다).** 그룹에는 런처 자신도 들어 그 자리에서 함께 끝난다. 그래서 런처가 끄는 길에는 "그룹이 다 내려가기 전에 런처가 끝나는 길"이 없다. 커널이 그룹의 모든 프로세스에 같은 신호를 한 번에 보내기 때문이다. 런처가 끄기 전에 밖에서 먼저 죽으면(런처만 노린 SIGKILL, 메모리 부족으로 런처가 강제 종료됨) 그 길은 남는다. 상류는 런처가 끝난 것을 서버가 스스로 끝난 것으로 보고 묶음 끄기를 건너뛰어 서버가 남는다(코드를 읽은 어림. 재지 않았다). Windows에서 상류가 남은 프로세스를 거두는 방식(Job Object를 닫으면 곧바로 끝난다)과 같은 세기다. 거부한 안은 SIGTERM을 먼저 보내고 유예를 두는 것이다. 이때 끄는 것은 서버가 이미 끝나고 남은 것이거나 부모가 죽은 뒤의 것이라 정리를 기다려 줄 상대가 없고, 런처가 자기 그룹의 나머지가 다 내려갔는지 알려면 `/proc`를 훑어야 하며, 런처가 SIGTERM을 견디도록 처리기를 둬야 한다. 처리기는 무시(SIG_IGN)와 달리 exec에서 풀려 서버에 물려가지 않지만(어림), 유예만큼 매 닫기가 늦어진다.
- **서버의 종료 코드는 넘기지 않는다(명세가 정했다).** 런처는 SIGKILL로 끝나 상류가 보는 종료 코드는 -9다. 상류의 클라이언트는 종료 코드를 읽지 않고 서버가 끝났는지만 본다(`_wait_for_process_exit`가 `returncode`가 없음인지만 본다. 코드를 읽었다). 거부한 안은 런처가 그룹의 나머지만 끈 뒤 서버의 코드로 끝나는 것이다. 세션의 우두머리는 그룹을 떠날 수 없어 자기를 뺀 그룹을 한 번에 끌 길이 없고, 그룹을 훑어 하나씩 끄면 그 사이에 새로 생긴 프로세스를 놓친다.
- **서버를 띄우지 못하면 한 줄과 종료 코드 127로 끝난다(명세가 정했다).** 어댑터가 명령을 미리 찾아보므로 이 길은 그 사이에 명령이 사라졌거나 실행 권한을 잃었을 때뿐이다. 클라이언트에는 연결이 닫힌 것으로 보이고 어댑터의 `ConnectionError`가 그 원인을 "연결이 닫혔다"로 든다. 런처의 한 줄은 서버의 표준 에러와 같은 곳(serve의 표준 에러)에 남는다.
- **런처가 늘리는 것.** 서버마다 파이썬 프로세스가 하나 늘고(뜨는 데 수십 밀리초와 메모리 몇 MB, ADR 0034의 어림. 재지 않았다), 0.2초마다 깨어난다. 부모가 죽은 뒤 런처가 그것을 알기까지 많아야 0.2초 동안 서버가 남는다. 프로세스 목록에서 런처가 서버 위에 보인다.

### CLI의 Ctrl+C (넘겨받은 것. 둘째 Ctrl+C는 사용자가 골랐다)

- **지금의 첫 Ctrl+C는 서버를 닫는다(측정).** CLI는 `asyncio.run`으로 돌아 첫 Ctrl+C가 주 태스크를 네이티브로 한 번 취소한다. 그 취소는 첫 await에서 한 번 나고 다시 오지 않아, 보호된 닫기는 그 뒤로 끝까지 간다. 두 OS에서 재 보니 지금 판(1.30.0)에서도 2.3.0에서도 Ctrl+C 한 번 뒤 대개 2.2~2.4초에 CLI가 끝났고 그 뒤 서버가 남지 않았다(Linux 1.30.0의 한 회차는 6.0초. `close_paths.py`의 `cli_ctrl_c`). ADR 0034의 알려진 한계("CLI는 … 이 한계에 든다", "Linux에서는 남을 것으로 본다")는 어림이 맞지 않았고, 이 명세의 PR이 올리는 이력이 그것을 바로잡는다.
- **2.3.0에서는 닫는 도중의 둘째 Ctrl+C가 CLI를 멈춘다(측정).** 둘째 SIGINT에 `asyncio.run`이 KeyboardInterrupt로 나와 남은 태스크를 다시 취소하고 끝나기를 기다리는데, 상류의 출력 비우기가 취소에서 보호된 채 살아 있는 서버의 출력 끝을 기다려 그 태스크가 끝나지 않는다(코드를 읽은 어림. 20초에 찍은 주 스레드의 스택이 `asyncio.runners._cancel_all_tasks` 안에 있었다). Linux에서는 셋째 Ctrl+C에야 끝났고(둘째 10초 뒤에 보낸 셋째에서 0.16~0.39초), Windows에서는 셋째 뒤에도 60초 안에 끝나지 않았다(`cli_ctrl_c_twice`, 두 회차). 1.30.0은 Windows에서 둘째 뒤 0.1~0.3초에 끝나 서버도 내려갔고, Linux에서는 둘째 뒤 2.2초에 끝났지만 서버가 남았다.
- **CLI가 Ctrl+C를 직접 받는다(사용자가 골랐다).** CLI가 `asyncio.run` 앞에 SIGINT 처리기를 단다. 그러면 asyncio의 러너는 자기 처리기를 달지 않는다(SIGINT 처리기가 기본값일 때만 단다. Python 3.12의 `asyncio/runners.py`, 코드를 읽었다). 첫 번째는 러너처럼 주 태스크를 한 번 취소하고 이벤트 루프를 깨운다. 보호된 닫기가 끝까지 가고 취소가 주 태스크를 빠져나오면 CLI는 표준 에러에 한 줄을 남기고 끝난다. 두 번째는 표준 에러에 다른 한 줄을 남기고 정리 없이 곧바로 끝난다. 처리기가 끝나면 이전 SIGINT 처리기를 되돌린다. 시제품(`close_paths.py --cli-handler force`, 두 OS와 두 판)으로 재 보니 첫 번째만이면 2.02~2.11초 뒤에 서버를 닫고 끝났고, 두 번째면 그 뒤 0.006~0.013초에 끝났다. 남은 서버는 Windows에서는 Job Object와 함께 내려갔고, Linux에서는 부모를 보는 런처로 3초 안에 내려갔으며 그 밖의 런처로는 남았다. 저장소 사본에 얹은 처리기와 그 테스트도 두 OS에서 초록이었고, 처리기를 `asyncio.run` 그대로로 바꾼 사본에서는 두 테스트가 기대한 까닭으로 빨갰다(`full_stack.py`, 아래 "소비 지점까지 잰 것"). 트레이스는 지금처럼 결말 없이 남는다. 다만 곧바로 끝내면 쓰던 줄이 파일에 반쪽으로 남을 수 있다. JSONL 어댑터는 쓰기를 버퍼에 담았다가 파일을 닫을 때 비우고(코드를 읽었다), 신호 처리기는 그 사이의 어느 바이트코드 경계에서도 돈다. 그 어댑터는 끝나지 않은 마지막 줄을 커밋되지 않은 것으로 읽어(`.claude/rules/adapters.md`의 줄 경계 규칙) 트레이스의 앞부분은 그대로 읽히고, 그 실행은 어차피 결말 없음이라 재개도 이어 가기도 되지 않는다. 거부한 안은 고치지 않고 알려진 한계로 적는 것이다(사용자가 고르지 않았다).
- **처리기는 CLI 채널의 함수 하나다(명세가 정했다).** `asyncio.run(main())`과 같은 모양으로 코루틴 함수를 받아 돌리고(시제품 `prototype/src/agent_os/channel/cli/interrupt.py`의 `run_interruptibly`), 조합 층의 `run`·`resume`이 `asyncio.run` 대신 부른다. 표준 에러의 한 줄은 CLI가 정하는 표시라 채널의 몫이다("채널은 표시만 결정한다", CLI 채널의 모듈 독스트링). 거부한 안은 조합 층에 두는 것이다. 조합 층은 조립만 하고, 그 자리에 두면 처리기의 테스트가 조합 층 전체(uvicorn, 모델 어댑터)를 import한다.
- **사용자가 고른 답에 적힌 크기와 다르다.** 답의 설명은 "CLI 진입점 코드가 스무 줄 안팎 늘고 테스트가 하나 는다"였다. 시제품의 처리기는 독스트링과 주석을 빼고 52줄이고 테스트는 둘(한 번, 두 번)이다. 끝나는 꼴을 두 OS에서 지금과 같게 지키는 코드(아래)와, 두 사례를 가르는 테스트를 명세가 더했다. 고른 동작은 그대로다.
- **중단으로 끝난 CLI는 지금과 같은 꼴로 끝난다(명세가 정했다).** 지금 CLI는 KeyboardInterrupt를 처리하지 않는다(`main.py`, 코드를 읽었다). CLI처럼 `asyncio.run`으로 돌다 그렇게 끝난 프로브의 자식은 POSIX에서 SIGINT로 죽었고(`Popen`이 보는 값 -2, bash가 보는 값 130) Windows에서는 `STATUS_CONTROL_C_EXIT`(3221225786)로 끝났다(측정, 두 OS). 처리기는 첫 번째로 끝나든 두 번째로 끝나든 같은 꼴로 끝낸다. POSIX에서는 SIGINT를 기본 처리로 되돌려 자기에게 보내고, Windows에서는 그 코드로 곧바로 끝난다(`os._exit`는 C int를 받아 그 값을 부호 있는 수로 준다. 처음 시제품이 그대로 줬다가 `OverflowError`로 끝나지 못한 것을 프로브가 잡았다). 셸은 두 꼴을 모두 130으로 봤고(측정, Linux의 bash), 그래서 지금의 끝남 0·실패 1·일시정지 3과 갈린다. 한 줄은 실행을 중단했다는 것과 트레이스에 결말 없이 남는다는 것이고, 두 번째의 한 줄은 닫기를 기다리지 않았다는 것을 더한다. 지금 찍히는 KeyboardInterrupt의 추적은 찍히지 않는다. 거부한 안은 `exit(130)`으로 끝내는 것이다. 셸의 값은 같지만 Windows의 값이 바뀌고, SIGINT로 죽은 꼴을 보고 Ctrl+C를 알아보는 부모(bash의 반복문 같은 것)는 자식이 Ctrl+C를 스스로 처리했다고 보고 멈추지 않을 수 있다(bash의 관례로 본 어림, 재지 않았다).
- **serve는 이 처리기를 쓰지 않는다.** uvicorn이 자기 신호 처리기를 달고(코드를 읽었다), 둘째 SIGINT를 강제 종료로 받는다(아래).

### serve 종료 (ADR 0034, ADR 0014)

- **serve 종료는 코드가 바뀌지 않는다.** 앱의 수명이 닫히면 도는 실행을 취소하고(`Runs.lifespan`), 실행의 태스크가 끝나기를 태스크 그룹이 기다린다. 상류의 닫기가 취소에서 보호되므로 그 기다림이 서버의 닫기를 포함한다. 이 명세가 잰 serve 종료(uvicorn 0.53.0, 유예 5초, 열린 스트림 하나, 입력이 닫혀도 끝나지 않는 서버 하나. 앱은 `Runs.lifespan`과 같은 모양의 흉내이고 진짜 `Runs`와 core가 아니다)는 신호 뒤 약 5.1~5.2초에 수명이 닫히고 약 7.1~7.3초에 실행이 끝나 약 7.3~7.4초에 프로세스가 끝났다(두 OS, `serve_shutdown.py`의 `graceful`). 그래서 ADR 0014의 "기다리지 않고 취소한다"는 실행이 끝나기를 기다리지 않는다는 뜻으로 남는다(ADR 0034).
- **Ctrl+C 두 번.** uvicorn은 두 번째 SIGINT를 강제 종료로 받아 연결 유예와 수명 닫기를 건너뛴다(코드를 읽었다). 그래도 서버는 내려갔다. 이 명세가 잰 판에서는 Python 3.12의 `Server.wait_closed`가 열린 연결을 기다려 유예 5초가 그대로 들었고(어림, 시각이 `graceful`과 같았다), 그 뒤 serve가 돌아오며 asyncio가 남은 태스크를 취소하고 끝나기를 기다리는 동안 보호된 닫기가 끝까지 갔다(`force`, Linux. Windows에서는 다른 프로세스 그룹에 Ctrl+C를 보낼 수 없어 재지 않았다). 그 기다림 도중에 SIGINT가 한 번 더 오면 그때는 uvicorn의 신호 처리기가 풀려 있어 asyncio가 기다리기를 그만두고, 프로세스가 닫기를 마치지 못한 채 끝난다(`force_then_interrupt`, Linux). 그 뒤 Linux에서는 부모 감시가 서버를 거둔다. Windows에서는 serve를 강제로 끈 경우(`sigkill`, TerminateProcess) Job Object가 거뒀다.
- **컨테이너.** 컨테이너가 멈추면 그 안의 프로세스는 함께 끝난다(PID 네임스페이스의 첫 프로세스가 끝나면 커널이 나머지를 끈다. 어림, 재지 않았다). agent-os를 컨테이너의 첫 프로세스로 띄우면 고아가 된 프로세스를 거둘 init이 없어 상류의 그룹 기다림이 상한(2초)까지 간다고 상류가 적었고 `docker run --init`을 예로 들었다(`terminate_posix_process_tree`의 독스트링, 코드를 읽었다). 런처가 끈 서버도 그 컨테이너에서는 거둘 이가 없어 좀비로 남을 것으로 본다(POSIX의 입양 규칙으로 본 어림, 재지 않았다). 이 명세의 Linux 측정은 모두 `docker run --init`으로 돌았다. 컨테이너 배포를 정하는 기능이 아직 없어(`plan.md`) 넘기지 않고, 구현 티켓이 README의 serve 안내에 한 줄을 더한다(아래 "고칠 자리", 명세가 정했다). 거부한 안은 Out of Scope로 두고 배포 기능에 넘기는 것이다. 받는 행이 없어 이 기능이 닫히면 넘긴 것이 사라진다(명세 축 리뷰가 짚었다).

### 결말 뒤 닫기의 예외 (넘겨받은 것: end-user-continuation 명세)

- **넘겨받은 물음은 타임아웃이 아닌 닫기 실패다.** 결말이 정해진 뒤 도구 연결을 닫는 일 자체가 예외로 끝날 때 서버가 남는가다(`plan.md`의 mcp-shutdown 행 괄호). core의 테스트는 그것을 닫힐 때 터지는 가짜 포트(`FlakyCloseTools`, "MCP 의 anyio 취소 범위가 실제로 이렇게 터진다")로 잰다.
- **닫기가 예외로 끝나도 서버는 내려간다(측정).** 상류의 닫기는 서버를 끄는 일을 `finally`에서 하므로(2.3.0은 취소로부터 보호한 채, 코드를 읽었다), 그 뒤의 정리가 터져도 서버는 이미 꺼진다. 이 명세가 그 가짜 포트가 흉내 내는 실패를 진짜로 냈다. 연결을 한 태스크에서 열고 다른 태스크에서 닫으면 anyio가 `RuntimeError`("Attempted to exit cancel scope in a different task than it was entered in")로 닫기를 끝낸다. 두 OS, 두 판(1.30.0, 2.3.0), Linux의 세 갈래(런처 없음, 서버가 끝날 때만 끄는 런처, 부모도 보는 런처) 모두에서 닫기가 약 2.0~2.1초 뒤 그 예외로 끝났고 감싼 프로세스와 서버가 내려갔다(`close_paths.py`의 `close_fails`). 이 실패는 취소가 아니라 지금 판(1.30.0)에서도 닫기가 끊기지 않는다. end-user-continuation의 티켓 02(#325)가 그 예외를 결말에 덧붙이지 않고 버리게 바꿨고(그 명세의 "결말 뒤 닫기", `core/run.py`의 `_connected`), 닫기는 그대로 돈다.
- **프로브로 재고 어댑터 테스트로 고정하지 않는다(명세가 정했다).** 진짜로 닫기를 터뜨리는 길이 다른 태스크에서 닫는 잘못된 쓰임뿐이라, 그것을 테스트로 두면 core가 하지 않는 모양을 고정하게 된다(core는 같은 태스크에서 열고 닫는다. `core/run.py`의 `async with`, 코드를 읽었다). 서버를 끄는 `finally`는 정상 닫기와 같은 자리라 사례 1~3이 그 길을 지난다. core 쪽은 `FlakyCloseTools`가 이미 고정한다. 거부한 안은 그 사례를 어댑터 테스트에 더하는 것이다. 이 명세의 처음 판이 사례 3(연결 안의 예외)으로 이 물음을 덮는다고 적었던 것은 닫기 자체는 정상인 길이라 물음과 달랐다(명세 축 리뷰가 짚었다).

### 고칠 자리 (ADR 0034가 든 것과 이 명세가 더한 것)

- **`pyproject.toml`**: 의존성 선언과 주석 둘(mcp가 어댑터 뒤에서 온다는 것, httpx가 mcp 뒤에서 이미 락파일에 있다는 것. mcp 2.3.0은 httpx 대신 httpx2를 쓴다), import-linter 금지 목록 둘(`langchain_mcp_adapters`를 지우지 않고 `mcp`로 바꾼다. 지우면 직접 의존이 된 mcp를 core와 sdk가 import해도 막히지 않는다).
- **`docs/constitution/tech.md`**의 런타임 의존성 행(mcp가 어댑터의 직접 의존이고 판 범위는 `>=2.3,<3`).
- **`.claude/rules/core.md`**의 포트 표(ToolSource의 첫 어댑터)와 **`adapters.md`**의 첫 슬라이스 어댑터 문장. `adapters.md`에는 이 명세가 정한 경계의 예외 셋과 POSIX 런처(자리, 띄우는 법, 끄는 때, 신호)를 한 항목으로 더한다.
- **`.claude/rules/channel.md`**의 "수명이 닫히면 남은 실행은 기다리지 않고 취소되어 결말 없음이다"에 닫기를 기다린다는 것을 더한다. 같은 말을 하는 채널 실행 수명 모듈의 모듈 독스트링("앱이 멈추면 실행을 기다리지 않고 취소한다")과 수명 독스트링, `tests/channel/http/test_end_user.py`의 수명 테스트 독스트링(`test_앱이_멈추며_취소한_실행도_칸을_돌려준다`)도 고친다.
- **MCP 어댑터 테스트 모듈의 독스트링**: 지금의 "MCP 의 stdio 클라이언트는 anyio 취소 범위라 같은 태스크에서 닫혀야 한다"는 2.3.0에서도 맞는다(`stdio_client`가 태스크 그룹을 연다. 코드를 읽었다). 닫기 절의 하트비트 방식과 못 보는 것(멈춰 있지만 살아 있는 프로세스)을 더한다.
- **CLI**: CLI 채널에 처리기 모듈과 그 테스트를 더하고, 조합 층의 `run`·`resume`이 `asyncio.run` 대신 그 함수를 부른다. CLI 채널의 모듈 독스트링의 종료 코드 목록에 중단(POSIX는 SIGINT로 죽음, 셸에서 130. Windows는 3221225786)을 더하고, 처리기 모듈의 독스트링에 첫 번째와 두 번째, 남은 서버를 누가 거두는지를 적는다.
- **core의 `_Body._connected` 독스트링**의 "그 닫기에서 도구 서버 프로세스가 남는지는 mcp-shutdown 이 본다". 결말 뒤 닫기가 예외로 끝나도 서버는 내려간다는 것(위 "결말 뒤 닫기의 예외")으로 바꾼다. core의 코드는 바뀌지 않는다.
- **`README.md`의 serve 안내**: 컨테이너의 첫 프로세스로 띄우면 `docker run --init`처럼 고아를 거두는 init을 둔다는 한 줄(위 "컨테이너").
- **대기열 34**는 고치지 않는다. 그 행이 든 거짓 하한(`langchain-mcp-adapters>=0.1`, mcp 상한이 없어 mcp 2.2.0에서 import 실패)은 이 기능이 그 패키지를 빼며 사라지지만, 행은 2026-10-20에 만료로 닫혔다(ADR 0036). 새 하한 `mcp>=2.3`은 이 명세가 잰 판이다. ADR 0034 본문이 그 대목을 고칠 자리로 든 문장에는 이 명세의 PR이 올리는 이력이 포인터를 단다.
- **ADR 0034**: 이 명세의 PR이 올리는 이력과 그 포인터. 구현 티켓은 ADR을 고치지 않는다.

### 상류에 알린다 (ADR 0034)

- **계기는 그대로다.** 구현 티켓의 CI가 런처 없이는 Linux에서 자식이 남는다는 것을 보이면 그 측정으로 python-sdk에 이슈 초안을 써서 사용자의 승인을 받고 올린다. 이 명세의 측정(`full_stack.py`의 런처 없는 대조군, Docker의 Linux)이 같은 것을 이미 보였으므로 초안은 그것도 든다. 상류가 고치면 런처를 뺀다. 부모 감시는 상류의 몫이 아니라(상류는 부모가 죽는 경우를 다루지 않는다. 코드를 읽었다) 런처를 뺄 때 다시 본다. 둘째 네이티브 취소에서 출력 비우기가 끝나지 않는 것도 초안이 함께 들 수 있다(상류의 주석이 네이티브 취소가 보호를 뚫을 수 있다고 이미 적었다).

### 소비 지점까지 잰 것

`full_stack.py`가 저장소 사본(`30949cfc`)의 의존성을 바꾸고 시제품(어댑터, 런처, 픽스처 서버, 닫기 테스트의 가짜 프로세스, CLI 처리기, 어댑터와 처리기의 테스트)을 얹은 뒤 검사와 테스트를 돌렸다. 그 사본에서 `write_failure.py`가 core `run()`에 진짜 어댑터를 물린 실행도 쟀다.

- **두 OS 모두**(이 명세의 셀프 리뷰를 반영한 뒤의 회차): 시제품 파일의 ruff 검사와 포맷 0건, pyright strict 0건, 타입 우회 검사 0건, import 계약 다섯 모두 유지, `tests/adapters`·`tests/core`·`tests/channel` 656개 통과(지금 646개와 새 테스트 열 개, 1개는 `llm` 표지로 빠졌다). `write_failure.py`의 네 사례는 모두 `run_failed`로 끝났고 `run()` 밖으로 예외가 나오지 않았다. 쓰기 사례 둘의 원인은 그 밖, 에이전트의 예외는 에이전트 코드, 런타임의 `ToolError`는 도구 실패였다.
- **대조군**: 기대한 테스트만 기대한 까닭(실패 요약 줄의 문구)으로 빨갰다. 처리기를 `asyncio.run` 그대로로 바꾸면 처리기의 두 테스트가 빨갰다(두 OS). 어댑터가 겉봉을 벗기지 않으면 겉봉을 보는 테스트 넷(닫기의 사례 3 "연결 안의 예외"와, 경계의 예외 테스트 가운데 뜨자마자 끝나는 서버·연결 안에서 던진 예외 그룹·yield에 멈춘 제너레이터)이 그룹의 글로 빨갰고, 그 사본의 `write_failure.py`는 쓰기 사례 둘에서 `run_failed`를 쓴 뒤 `BaseExceptionGroup`을 올렸다(두 OS). 런처를 빼면 사례 2와 5가, 부모 감시를 빼면 5만 빨갰다(Linux).
- **지금 판**(저장소 `30949cfc`, Windows): `write_failure.py`의 쓰기 사례 둘이 `run_failed`를 쓴 뒤 `GeneratorExit`를 든 `BaseExceptionGroup`을 올렸고, 에이전트의 예외와 런타임의 `ToolError`는 `run_failed`에 그대로 실렸다.
- 앞선 회차(`30949cfc` 위에서 셀프 리뷰 앞의 시제품으로 656개, `aa93cf7b` 위에서 571개, `8a2163eb` 위에서 543개. `aa93cf7b`와 `8a2163eb`에서는 경계의 예외 테스트 둘(뜨자마자 끝나는 서버, yield에 멈춘 제너레이터)과 ruff 단계와 겉봉 대조군이 없었다)도 두 OS에서 같은 판정이었다. README의 결과.

## Testing Decisions

### 이음매 (사용자가 골랐다)

**닫기는 MCP 어댑터 테스트 하나다**(`tests/adapters/test_mcp.py`). 진짜 MCP 어댑터를 core와 같은 취소 범위(`anyio.move_on_after`. 기한은 범위가 취소를 받았는지로 본다) 안에서 열고, 파이썬으로 쓴 가짜 MCP 서버와 그 서버가 띄운 가짜 프로세스가 하트비트 파일을 쓰게 해, 닫은 뒤 그 기록이 멈췄는지 본다(ADR 0034). 서버를 닫는 코드가 어댑터뿐이라 거기서 잰다(CLI 처리기는 닫기를 기다릴지만 정하고 아래 따로 잰다). core와 채널의 테스트는 지금처럼 가짜 포트를 쓴다. 하나의 예외가 아래 CLI 처리기의 테스트다. 채널(`tests/channel/cli/`)의 테스트이지만 진짜 어댑터를 쓴다. 사용자가 고른 답의 설명은 "core와 채널 테스트는 지금처럼 가짜 포트를 쓴다"였고, 처리기의 테스트는 그 답 뒤에 명세가 정했다. 처리기가 바꾸는 둘째 Ctrl+C의 모양이 진짜 상류의 닫기에서만 나서 가짜 포트로는 처리기를 빠뜨린 구현도 초록이 된다(아래). core와 HTTP 채널의 테스트는 답대로 가짜 포트다. core의 실행 타임아웃과 결말 뒤 닫기는 가짜 포트로 이미 고정되어 있고(`tests/core/test_run.py`의 "실행 타임아웃" 절), 채널의 수명 테스트도 그대로다. 거부한 안(사용자가 고르지 않았다)은 core의 실행 진입점에 진짜 어댑터를 물려 `run_failed`와 서버의 소멸을 한 테스트에서 보는 것이다.

**CLI 처리기는 그 함수의 테스트 하나다(명세가 정했다).** 처리기가 프로세스를 끝내므로 자식 프로세스에서 잰다. 자식은 처리기 아래에서 진짜 MCP 어댑터로 닫기 테스트의 가짜 서버(입력이 닫혀도 끝나지 않는 서버)를 열고, 그 서버가 도구 호출을 받았다는 표지 파일이 생기면 스스로 SIGINT를 올린다. 그 서버를 닫는 데 상류의 유예 2초가 들어 둘째 SIGINT(첫째 0.5초 뒤)는 닫는 도중에 온다. 자식은 도구 호출이 취소된 시각을 남기고, 테스트는 첫째가 그 호출을 취소했는지(두 번이면 그 시각이 둘째보다 앞서는지)를 먼저 본다. 재려는 상황이 났다는 표지다. 처음 판은 연결 뒤 0.5초를 고정으로 쉬고 눌러 그것을 보지 않았다(표준 축 리뷰가 짚었다). 그다음 한 번이면 서버를 닫은 뒤 중단의 꼴과 한 줄로 끝나고 서버의 하트비트가 멈췄는지, 두 번이면 둘째 뒤 1초 안에 같은 꼴과 다른 한 줄로 끝나는지 본다. 1초는 둘째로 끊었을 때의 같은 양(자식이 둘째를 보낸 시각부터 부모가 끝을 본 시각까지)을 홀로 돌린 프로브에서 잰 0.006~0.013초의 70배가 넘고, 끊지 못했을 때의 끝(둘째 뒤 약 1.5초, 부하에서는 더 늦다)과 가르는 문턱이다. 신호를 올리는 법은 OS마다 다르다(POSIX는 올리는 스레드가 SIGINT를 막고 프로세스에 보내야 주 스레드가 받는다. Windows는 그 스레드에서 올리면 된다. `close_paths.py`의 `interrupt`가 선례다). 기대는 두 OS가 같다. 두 번 누른 뒤 서버가 남지 않는 것은 위 닫기 테스트의 사례 5(프로세스가 갑자기 죽음)가 본다. 거부한 안은 진짜 어댑터 대신 취소에서 보호된 기다림으로 상류의 닫기를 흉내 내는 것이다. asyncio의 네이티브 취소가 anyio의 보호를 뚫어, 그 흉내로는 처리기 없이도 둘째 SIGINT 뒤 곧바로 끝났다(명세 축 리뷰가 손으로 봤다. Windows 0.126초, Linux 0.043초. 상류의 주석도 네이티브 취소가 보호를 뚫을 수 있다고 적었다). 그러면 처리기를 빠뜨린 구현도 초록이 된다. 진짜 2.3.0의 닫기가 둘째에서 끝나지 않는 까닭은 보호 자체가 아니라 출력 비우기가 살아 있는 서버의 출력 끝을 기다리는 데 있다(위 "CLI의 Ctrl+C").

**좋은 테스트의 기준**: 밖에서 보이는 동작만 본다. 프로세스가 남았는지(하트비트), 호출한 쪽이 받은 예외의 타입과 글, 도구 결과, 종료 코드다. 런처가 있는지, 상류의 어느 함수를 지났는지는 보지 않는다. 같은 테스트가 Windows에서는 상류의 Job Object로, Linux에서는 런처로 초록이어야 한다.

### 닫기 테스트의 사례 다섯 (명세가 정했다)

가짜 프로세스는 테스트 폴더의 모듈 하나가 역할로 나눠 든다. 감싸는 프로세스(서버를 자식으로 띄우고 그 종료 코드로 끝난다), 입력이 닫혀도 끝나지 않는 서버(오래 걸리는 도구와 스스로 죽는 도구가 있다. 읽는 쪽이 사라진 출력에 쓰다 난 오류에도 남는다), 입력이 닫히면 자식을 남기고 끝나는 서버, 하트비트만 쓰는 자식이다. 입력이 닫히면 끝나는 서버를 뺀 셋은 하트비트를 쓰고 멈춤 파일이 생기거나 120초가 지나면 스스로 끝난다. 그 서버는 하트비트를 쓰지 않고(그 자식이 쓴다) 입력이 닫혀야 끝난다. 테스트는 끝날 때 멈춤 파일을 만들어 남은 것을 끝낸다. 120초는 한 사례가 부하에서 쓰는 가장 긴 시간(아래 하트비트가 생기기를 기다리는 30초, 닫기, 멈췄는지 보는 15초)보다 넉넉하게 둔다. 짧으면 닫기가 서버를 끄지 못한 회차에서도 가짜 프로세스가 스스로 끝나 초록이 될 수 있다. 프로세스 번호로 끄지 않는다(번호는 다시 쓰여 남의 프로세스를 끌 수 있다. 일지 2026-10-16-36 "사고").

1. **도구 호출 도중의 기한**: 감싸는 프로세스 아래의 서버에서 오래 걸리는 도구를 부르는 도중에 기한이 온다. 기한 범위가 그 취소를 받고(보호된 닫기가 취소를 삼키지 않는다), 감싸는 프로세스와 서버가 모두 멈춘다.
2. **자식을 남기는 서버의 정상 닫기**: 서버가 띄운 자식이 닫은 뒤 멈춘다. Linux에서 런처가 하는 일이다.
3. **연결 안의 예외**: 연결을 연 채 던진 예외가 그 객체 그대로(그룹이 아니라) 나오고 감싸는 프로세스와 서버가 멈춘다. 경계의 예외("연결 안에서 난 예외는 겉봉 없이 그대로 나온다")를 함께 본다.
4. **도구 호출 도중에 서버가 죽음**: 스스로 죽는 도구를 부르면 서버 이름과 도구를 든 `RuntimeError`다.
5. **연결을 연 프로세스가 갑자기 죽음**: 자식 프로세스가 연결을 열고 기다리는 동안 테스트가 그것을 강제로 끈다(`Popen.kill`). 감싸는 프로세스와 서버가 멈춘다. Linux에서는 런처의 부모 감시가, Windows에서는 Job Object가 하는 일이다.

그리고 경계의 예외 테스트가 넷 더 있다. 첫째는 지금 테스트의 기대를 바꾸고 나머지 셋은 새로 더한다. 하트비트는 보지 않는다.

- 지금의 서버 기동 실패 테스트는 기대를 바꾼다. 없는 명령은 서버 이름과 명령을 든 `ConnectionError`이고 그 원인이 `FileNotFoundError`다. 두 OS에서 같다.
- 뜨자마자 끝나는 서버(`python -c pass`)는 서버 이름과 "Connection closed"를 든 `ConnectionError` 하나로 나온다. 세션을 연 뒤의 실패라 상류의 태스크 그룹에 싸이는 길이다.
- 연결 안에서 던진 예외 그룹은 겉봉만 벗고 그 그룹 객체로 나온다. 시제품의 첫 판이 놓친 경우다.
- 연결 안의 yield에 멈춘 제너레이터를 닫으면(`aclose`) 예외 없이 닫힌다. core의 `_drive`가 트레이스 쓰기 실패 뒤에 연결을 닫는 모양이다.

**하트비트의 판정**: 가짜 프로세스가 0.1초마다 한 바이트를 덧붙이고, 테스트는 15초의 기한까지 1초씩 거듭 견주어 그 사례의 하트비트가 모두 1초 동안 자라지 않으면 멈춘 것으로 본다. `tests/tools/test_run_checks.py`의 `_stops_growing`이 선례이고 `.claude/rules/tests.md`가 그 꼴을 요구한다. 한 번만 견주는 판정은 부하에서 꺼지는 프로세스의 마지막 쓰기를 산 프로세스로 읽어 흔들렸다(대기열 306). 이 명세의 처음 판이 선례로 든 0.5초 한 번의 판정(그때의 `tests/tools/test_mutate.py`의 `_뛰는지`)이 그 꼴이었다. 멈춰 있지만 살아 있는 프로세스는 가려내지 못한다(ADR 0034가 받아들인 대가). 거짓 초록은 하트비트가 자라지 않는 다른 까닭(쓰기 실패)에서만 나므로, 각 사례는 닫기 전에 하트비트가 생긴 것을 먼저 기다린다(상한 30초. 다른 세션의 테스트와 겹친 부하에서 홀로 돈 사례 5가 12.5초 걸렸고, 20초로 두던 판은 전체 회차에서 그 기다림을 넘겼다). 사례 5는 하트비트가 생기지 않았으면 그 까닭으로 빨갛다.

**빨강을 먼저 본다.** 런처는 그것이 없으면 사례 2와 5가 CI(Linux)에서 빨갛다는 것을 먼저 보인 뒤 들인다(ADR 0034). 이 명세가 Docker의 Linux에서 시제품으로 그것을 이미 봤다(`full_stack.py`의 대조군). Windows에서는 지금 판(1.30.0)으로 사례 1의 모양에서 서버가 남는다(`close_paths.py`의 `cancel`). Windows의 `.venv` 파이썬은 진짜 파이썬을 자식으로 띄우는 런처라 가짜 프로세스마다 한 겹이 더 끼지만, 그 겹이 있어도 지금 판에서 서버가 남아(`close_paths.py --python venv`의 `cancel`) 테스트가 빨강을 볼 수 있다(넘겨받은 것). 경계의 예외는 어댑터가 겉봉을 벗기지 않는 사본에서 겉봉을 보는 네 테스트(닫기의 사례 3과, 경계의 예외 테스트 가운데 뜨자마자 끝나는 서버·연결 안에서 던진 예외 그룹·yield에 멈춘 제너레이터)가 그룹의 글로 빨갰고, 그 사본에서 core에 진짜 어댑터를 물린 실행은 결말을 쓴 뒤 예외 그룹을 올렸다(`full_stack.py`의 대조군과 `write_failure.py`, 두 OS). CLI 처리기의 테스트는 처리기를 `asyncio.run` 그대로로 바꾼 사본에서 두 사례가 빨갰다. 한 번이면 중단의 한 줄 대신 KeyboardInterrupt의 추적이 찍혔고, 두 번이면 자식이 30초 안에 끝나지 않았다(`full_stack.py`의 대조군, 두 OS). 한 번의 사례에서 종료 코드의 단언은 그 사본에서도 지났다(실패한 것은 그 뒤의 한 줄 단언이다). 처리기 없는 지금의 끝나는 꼴과 처리기의 꼴이 같다는 것이고, 처리기가 그 꼴을 지키는지를 그 단언이 본다.

**시간**: 새 테스트 열 개(어댑터 여덟, CLI 처리기 둘)가 테스트 시간으로 Linux에서 약 35초를 더한다. 닫기 사례 다섯이 약 23초, 새로 더한 경계의 예외 테스트 셋이 약 3초, CLI 처리기의 두 테스트가 약 10초다(`full_stack.py`의 `--durations`, Docker). Windows(이 PC)에서는 약 49초였다(닫기 다섯 약 30초, 새 경계 셋 약 4초, 처리기 둘 약 15초). 같은 때 Docker의 회차가 함께 돌았다. 셀프 리뷰 앞의 회차는 CPU가 89%로 붐비던 때라 Windows에서 약 88초였고, 시간이 바뀌지 않은 픽스처 테스트도 이 회차(1.8~2.8초씩)보다 길게 4.3~5.6초씩 걸렸다. pre-commit의 pytest는 여러 작업자로 나뉘어 돌아(ADR 0035) 벽시계로 늘어나는 것은 그보다 작다(어림). 하트비트 판정은 1초 동안 자라지 않는지를 보므로 사례마다 1초 넘게 들고, 사례 1·3과 처리기의 한 번 사례는 상류의 유예 2초를 기다린다.

**모듈**: MCP 어댑터와 CLI 처리기다. 런처는 어댑터 테스트가 Linux에서 지나며 함께 재고 따로 단위 테스트를 두지 않는다. 런처의 갈래(우두머리가 아님, 띄우기 실패)는 프로세스 그룹과 신호를 다루는 POSIX 코드라 Windows에서 돌 수 없고, skip은 세션 실패다(`.claude/rules/tests.md`). 그래서 POSIX에서만 뜻이 있는 단언은 두지 않고 두 OS에서 같은 기대가 서는 사례만 둔다.

## Out of Scope

- **스스로 새 세션으로 떼어 낸 자식, Windows에서 Job Object에 넣기 전의 짧은 틈에 생긴 자식, Windows의 대체 프로세스(`FallbackProcess`)의 스레드.** ADR 0034의 알려진 한계 그대로다.
- **닫는 시간을 줄이는 것.** 서버 여럿을 동시에 닫는 안은 ADR 0034가 거부했다. 입력이 닫히면 스스로 끝나는 서버가 가장 빠르다(사용자 스토리 22).
- **컨테이너 배포 자체.** agent-os를 컨테이너로 띄우는 길(이미지, 설정)은 아직 없고 `plan.md`에 그 기능이 없다. 그 길이 생길 때 필요한 init은 이 기능의 README 한 줄이 알린다(위 "컨테이너").
- **mcp 3.** ADR 0034대로 닫기 테스트와 프로브를 다시 돌린 뒤 결정으로 들인다.
- **결말 뒤 닫기의 예외를 결말에 덧붙이지 않는 것.** end-user-continuation의 티켓 02가 이미 했다(#325). 이 기능은 그 닫기에서 서버가 내려가는지만 본다(위 "결말 뒤 닫기의 예외").
- **serve의 신호 처리.** uvicorn의 것을 그대로 쓴다. 닫기 도중의 셋째 SIGINT와 SIGKILL 뒤에 남는 것은 부모 감시와 Job Object가 거둔다.

## Further Notes

- **티켓.** 계약이 바뀌지 않아 계약 티켓이 없다(ADR 0034). 의존성과 어댑터를 바꾸는 것, 런처를 들이는 것, CLI 처리기를 나눌지는 to-tickets가 정한다. 런처를 들이기 전에 그것 없는 Linux CI의 빨강을 보이는 순서는 ADR 0034가 정했다. CLI 처리기는 2.3.0으로 올리는 티켓과 같이 가거나 그 앞에 서야 한다. 뒤에 서면 그 사이 main의 CLI가 둘째 Ctrl+C에 멈춘다. 다른 기능을 막지 않는다.
- **이 명세의 측정이 설계 인터뷰의 수와 다른 것.** 서버 하나를 닫는 시간(인터뷰는 상수를 더한 최악값 Windows 4.5초, Linux 6.5초만 적었다 → 흔한 모양으로 잰 값은 2.0초, SIGTERM까지 무시하는 서버 4.0초. 최악값은 여전히 어림이고 닿는 조건은 위 "닫는 데 드는 시간"), CLI의 Ctrl+C(ADR의 어림 "Linux에서는 남을 것으로 본다" → 잰 값 "한 번은 두 OS에서 내려가고, 두 번은 2.3.0에서 멈춘다"), 서버가 뜨자마자 죽을 때의 글(인터뷰가 손으로 본 대로 두 판 모두 두 겹 그룹이었다 → 이 명세의 경계 예외가 바꾼다)이다. 인터뷰의 도구 호출 도중 기한(약 2.0초 뒤 서버와 손자까지 내려감)과 지금 테스트의 통과는 같은 크기로 다시 나왔다. 실제 everything이 지금 판에서 `gc.collect()`까지 남는 모양은 이 명세의 프로브가 재현하지 못했다(README).
- **다시 재지 않은 인터뷰의 수.** ADR 0034가 거부한 안의 근거(어댑터가 라이브러리 바깥에서 닫기를 보호하는 안의 22회·15회, 연결 코드를 복사해 고치는 안의 334초 멈춤)는 인터뷰의 스크래치 스크립트로 손으로 본 것이고 이 명세는 다시 재지 않았다. 고른 안(mcp 2.3.0)의 측정이 그 안들을 대신하지 않으므로, 그 안을 다시 꺼내면 그때 프로브로 잰다. ADR 0034의 "실제 core `run()`으로도 `run_failed`("실행이 6초 안에 끝나지 않았다")로 끝난 뒤 남은 프로세스가 없었다"도 다시 재지 않았다. 이 명세가 core `run()`에 진짜 어댑터를 물려 잰 것은 트레이스 쓰기 실패와 예외의 결말(`write_failure.py`)이고 기한이 아니다. 기한 뒤의 닫기는 core와 같은 취소 범위를 연 어댑터 테스트(사례 1)와 `close_paths.py`의 `cancel`이 쟀다.
