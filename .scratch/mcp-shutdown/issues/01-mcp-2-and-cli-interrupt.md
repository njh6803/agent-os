# 01: mcp 2 — 취소된 실행의 MCP 서버도 닫힌 뒤에 실행이 끝나고, CLI는 Ctrl+C를 직접 받는다

**What to build:** 실행 타임아웃이 도구 호출 도중에 걸리거나 serve를 멈춰 실행이 취소되어도, 그 실행이 띄운 MCP 서버와 그 아래 프로세스(`npx`가 띄운 진짜 서버까지)가 내려간 뒤에 실행이 끝난다. 결말은 지금과 같다(기한이면 "실행이 N초 안에 끝나지 않았다"). MCP 어댑터는 `langchain-mcp-adapters`를 빼고 mcp 2(`>=2.3,<3`)의 stdio 클라이언트와 세션을 직접 써서, 도구 목록과 호출과 지금의 동작(도구 에러면 `ok=false`, 없는 도구는 `LookupError`, 서버 기동 실패는 연결 단계의 예외)을 그대로 지킨다. CLI에서 `run`·`resume` 도중 Ctrl+C를 한 번 누르면, 도구 호출 도중이든 답이 보인 뒤 서버를 닫는 도중이든 서버를 닫고 끝난다. 한 번 더 누르면 닫기를 기다리지 않고 곧바로 끝난다. 둘 다 지금처럼 Ctrl+C로 끝난 꼴(셸에서 130)이고 추적 대신 한 줄을 남긴다. Linux에서 서버가 남긴 자식과 CLI를 곧바로 끝낸 뒤의 서버는 아직 남는다(03이 거둔다).

근거는 `.scratch/mcp-shutdown/spec.md`의 Solution, "의존성", "어댑터"(그 아래 "서버를 여는 실패"와 "경계를 넘는 예외"는 02·03), "테스트 픽스처 서버", "CLI의 Ctrl+C", "serve 종료", "결말 뒤 닫기의 예외", "고칠 자리", Testing Decisions(이음매, 사례 1, 쪽 나눔, 하트비트, 처리기, LLM 테스트와 전체 검사)와 그 2026-10-21 명세 검토 주석이다. 결정은 ADR 0034 본문과 그 2026-10-17·2026-10-21 이력이다(런처의 부모 감시, CLI의 둘째 Ctrl+C, 첫 Ctrl+C를 취소 범위로 전하는 것은 사용자가 골랐다). 시제품은 `.scratch/mcp-shutdown/probes/prototype/`이고 `full_stack.py`가 저장소 사본에 얹어 두 OS에서 검사와 테스트를 돌렸다. 시제품의 처리기(`run_interruptibly`)는 첫 Ctrl+C를 네이티브 취소로 전하는 고치기 전의 모양이다. 범위로 전하는 모양의 시제품은 `close_paths.py`의 `_run_with_scope_cancel`이다.

이 티켓은 헌법 파일(`tech.md`)을 고쳐 계약에 닿고(CLAUDE.md 작업 규약 2), 02·03을 막는다. 02·03은 어차피 2.3.0 위에서만 선다. 다른 기능은 막지 않는다.

**Blocked by:** None (can start immediately)

**Status:** done

### 의존성과 헌법

이 절보다 아래 "닫기 테스트"의 사례 1을 먼저 쓰고, 지금 판(1.30.0)에서 빨간 것을 본 뒤 의존성을 바꾼다(원칙 II). 위에서부터 따르면 락을 되돌려야 한다.

- [x] **`langchain-mcp-adapters`를 빼고 `mcp>=2.3,<3`을 직접 의존으로 둔다.** 락의 변화가 명세의 "락의 변화는 설계 인터뷰가 본 것과 같다"(오르는 것, 새로 드는 것, 빠지는 것, 패키지 84개)와 다르면 멈추고 본다
- [x] **`pyproject.toml`의 두 주석과 import-linter 금지 목록 둘을 고친다.** 금지 목록의 `langchain_mcp_adapters`는 지우지 않고 `mcp`로 바꾼다. 지우면 직접 의존이 된 mcp를 core와 sdk가 import해도 막히지 않는다
- [x] **`tech.md`의 런타임 의존성 행을 고치고 같은 커밋이 헌법 판의 patch를 올린다**(`docs/constitution/README.md`. 앞선 의존성 행 변경 3.0.10·3.0.12가 선례다)

### 어댑터와 픽스처

- [x] **서버마다 상류의 stdio 클라이언트와 세션을 열고, `initialize()` 뒤 도구 목록을 커서 끝까지 따른다.** 커서가 없거나 빈 글이면 끝이고, 1000쪽을 넘으면 여는 단계가 실패한다. 결과의 글은 텍스트 블록과 텍스트 리소스의 글을 이어 붙인 것이다. 포트의 모양은 그대로다
- [x] **서버들은 연 순서의 반대로 하나씩 닫는다**(지금 어댑터의 탈출 스택 순서)
- [x] **픽스처 서버를 `mcp.server.mcpserver`의 `MCPServer`로 옮기고, 실패를 내는 픽스처 도구는 `ToolError`를 던진다**(2.x 서버는 그 밖의 예외의 글을 클라이언트에 보내지 않는다). 그 픽스처를 실제 CLI로 띄우는 `tests/test_main.py`도 지난다
- [x] **있던 어댑터 테스트(목록, 호출, 실패, 없는 도구, 서버 기동 실패)가 그대로 지난다.** 서버 기동 실패의 기대(`FileNotFoundError`)는 이 티켓에서 바꾸지 않는다. 2.3.0은 띄우는 자리에서 그 예외를 그대로 낸다(두 OS, `close_paths.py`의 `missing_command`). 바꾸는 것은 02다

### 닫기 테스트 (사례 1)

- [x] **가짜 프로세스 모듈을 테스트 폴더에 둔다.** 역할은 감싸는 프로세스, 입력이 닫혀도 끝나지 않는 서버(오래 걸리는 도구와 스스로 죽는 도구, 읽는 쪽이 사라진 출력에 쓰다 난 오류에도 남는다), 입력이 닫히면 자식을 남기고 끝나는 서버, 하트비트만 쓰는 자식이다. 멈춤 파일이나 120초로 스스로 끝나고, 테스트는 프로세스 번호로 끄지 않는다. 02·03의 사례도 이 모듈을 쓴다
- [x] **하트비트 판정은 15초의 기한까지 1초씩 거듭 견주어 모두 1초 동안 자라지 않으면 멈춘 것이다**(`.claude/rules/tests.md`, `tests/tools/test_run_checks.py`의 `_stops_growing`이 선례). 각 사례는 닫기 전에 하트비트가 생기기를 먼저 기다린다(상한 30초)
- [x] **사례 1(도구 호출 도중의 기한)**: 진짜 어댑터를 core와 같은 취소 범위(`anyio.move_on_after`) 안에서 열고 감싸는 프로세스 아래 서버의 오래 걸리는 도구를 부르는 도중에 기한이 온다. 기한 범위가 그 취소를 받고(보호된 닫기가 취소를 삼키지 않는다) 감싸는 프로세스와 서버가 모두 멈춘다. 지금 판(1.30.0)으로 먼저 빨간 것을 보고, 그 까닭이 서버의 하트비트가 자란 것인지 본다(Windows에서 `--python venv` 겹이 있어도 서버가 남았다. 명세의 "빨강을 먼저 본다"). 시제품의 가짜 서버는 2.x에만 있는 `MCPServer`를 쓰므로, 빨강을 보는 동안만 1.x의 `FastMCP`로 물러서게 하고(`.scratch/mcp-shutdown/probes/fakes.py`가 선례다) 2.3.0으로 올린 뒤 그 갈래를 지운다
- [x] **쪽 나눔 테스트 둘**: 저수준 `Server`로 지은 가짜 서버가 도구 하나와 빈 커서를 내면 연결이 그 도구 하나로 열리고, 같은 커서를 거듭 내면 여는 단계가 실패하고 그 글이 쪽 수를 든다. 두 테스트는 30초 기한 안에서 연다(고치기 전에는 같은 쪽을 끝없이 물어 기한에 걸렸다). 어댑터가 커서를 끝까지 따르게 하기 전에 두 테스트를 먼저 쓰고, 커서가 `None`이 아닌 동안 따르기만 하는 어댑터(시제품의 첫 판, 빈 글을 끝으로 보지 않고 쪽 상한이 없다)로 둘 다 기한의 `TimeoutError`로 빨간 것을 본 뒤 빈 글의 끝과 1000쪽 상한을 더한다(원칙 II, 명세의 쪽 나눔 테스트). 실패의 모양(서버 이름을 든 `ConnectionError`)은 02가 조인다. 이 티켓의 단언은 예외 그룹 안의 잎에서 쪽 수를 찾는다

### CLI 처리기

범위의 취소는 범위를 나갈 때까지 기다림마다 다시 들어오지만(손으로 봤다) 결말은 바뀌지 않는다고 본다. 트레이스 쓰기는 동기이고, 서버마다의 닫기는 상류가 보호하며, core는 기한을 자기 범위의 `cancelled_caught`로 가려 바깥 범위의 취소를 시간 초과로 읽지 않는다(코드를 읽었다. 서버 여럿으로는 재지 않았다). 에이전트의 정리 코드가 `finally`에서 기다리면 그 기다림은 끊긴다. 실행 타임아웃의 기한(`move_on_after`)도 같은 범위 취소이고 core는 그 범위 안에서 에이전트의 제너레이터를 닫으므로(`core/run.py`의 기한 범위와 `_closing`, 코드를 읽었다) 첫 Ctrl+C는 기한과 같은 꼴이 될 뿐이다. 저장소의 플러그인 에이전트에는 `finally`가 없다(`plugins/`에서 grep했다). 이것을 재는 테스트는 두지 않는다. 아래 처리기 테스트의 자식은 core를 거치지 않고 `-m llm`은 Ctrl+C를 누르지 않는다.

- [x] **CLI 채널에 처리기 함수 하나를 두고 조합 층의 `run`·`resume`이 `asyncio.run` 대신 부른다.** `asyncio.run` 앞에 SIGINT 처리기를 달아 러너가 제 처리기를 달지 않게 하고, 끝나면 이전 처리기를 되돌린다
- [x] **첫 번째는 주 태스크를 취소하지 않고, 주 코루틴을 감싼 anyio 취소 범위의 취소를 이벤트 루프에 맡긴다**(`loop.call_soon_threadsafe`. ADR 0034의 2026-10-21 이력). 상류의 보호된 닫기가 그 취소를 닫기를 마친 뒤에 받아, 닫는 도중에 눌러도 서버를 닫고 끝난다. 두 번째는 표준 에러에 다른 한 줄을 버퍼를 거치지 않고 쓰고 정리 없이 곧바로 끝난다
- [x] **첫 SIGINT가 범위를 잡기 전이나 루프가 닫힌 뒤에 와도 중단의 꼴로 끝나고 추적을 찍지 않는다.** 시제품(`_run_with_scope_cancel`)은 범위를 잡기 전의 첫 SIGINT를 둘째처럼 다루고, 루프가 닫힌 뒤의 `loop.call_soon_threadsafe`는 `RuntimeError: Event loop is closed`를 낸다(손으로 봤다). 처리기를 되돌리기 전의 틈도 같다. 어느 한 줄을 쓸지는 구현이 정하되 끝나는 꼴은 아래와 같다
- [x] **처리기는 주 스레드에서만 달 수 있다.** `signal.signal`은 다른 스레드에서 `ValueError`를 낸다(손으로 봤다). 지금 `main()`을 부르는 길(CLI 진입점, `tests/test_main.py`의 in-process 호출)이 그대로 지나는지 본다
- [x] **끝나는 꼴은 처리하지 않은 KeyboardInterrupt로 끝나는 파이썬과 같다.** POSIX는 SIGINT를 기본 처리로 되돌려 자기에게 보내고, Windows는 `os._exit`에 `STATUS_CONTROL_C_EXIT`를 부호 있는 32비트로 준다. 표준 출력이나 에러에 쓰다 `OSError`가 나도 그 꼴로 끝난다
- [x] **한 줄은 트레이스의 상태를 말하지 않는다**(명세의 "중단으로 끝난 CLI" 2026-10-21 주석). 첫 번째의 한 줄은 실행을 중단했다는 것, 두 번째의 한 줄은 닫기를 기다리지 않았다는 것을 더한다. 결말을 쓴 뒤 닫는 동안 눌러도 끝나는 꼴은 중단이다
- [x] **처리기 테스트는 넷이고 자식 프로세스에서 잰다.** 자식은 처리기 아래에서 진짜 어댑터로 입력이 닫혀도 끝나지 않는 가짜 서버를 열고 스스로 SIGINT를 올린다(POSIX는 올리는 스레드가 SIGINT를 막고 프로세스에 보낸다. Windows는 그 스레드에서 올린다). 각 사례는 재려는 상황이 났다는 표지를 먼저 본다. (구현에서 둘을 더해 여섯이다. 셀프 리뷰가 눌린 뒤 주 코루틴이 취소가 아닌 예외로 끝나는 사례를, PR 직전 리뷰가 SIGINT를 무시한 채 시작하면 그 무시를 지키는 사례를 더했다. 일지 2026-10-21-06)
  - 한 번(도구 호출 도중): 서버가 호출을 받았다는 표지 뒤에 누르고, 첫째가 그 호출을 취소했다는 시각을 본 뒤, 서버를 닫고 중단의 꼴과 첫째의 한 줄로 끝나고 서버의 하트비트가 멈췄는지 본다
  - 두 번: 첫째 0.5초 뒤 둘째를 누르고, 둘째 뒤 1초 안에 같은 꼴과 둘째의 한 줄로 끝나는지 본다. (PR 직전 리뷰: 둘째는 첫째가 호출을 취소했다는 표지 뒤에 누른다. 명세 Testing Decisions의 같은 날 주석)
  - 닫기를 시작한 뒤의 한 번: 자식이 도구를 한 번 부르고 연결을 나서기 직전에 표지 파일을 쓰고, 그 0.5초 뒤 한 번 누른다. 자식은 연결을 나선 뒤 닫기 끝의 시각을 남긴다. 누름이 그 표지 뒤이고 닫기 끝보다 앞이라는 것(닫기 끝이 없으면 앞으로 센다)을 본 뒤, 상류의 유예 안에 중단의 꼴과 첫째의 한 줄로 끝나고 서버의 하트비트가 멈췄는지 본다. 범위로 전하는 시제품은 누른 뒤 1.48~1.56초였고 네이티브 취소로 전하면 10초 안에 끝나지 않았다(`close_paths.py`의 `cli_ctrl_c_closing`, 두 OS). 문턱은 그 둘을 가르고 부하를 견디는 값으로 정한다. 끝나지 않은 자식은 `Popen` 핸들로 끈다. 시제품의 처리기(`run_interruptibly` 그대로)로 이 사례가 빨간 것을 먼저 본다. 프로브는 stdio 클라이언트를 직접 열었고 이 테스트는 진짜 어댑터를 쓴다
  - 쓰기 실패: 진짜 어댑터 없이 자식이 처리기 아래에서 잠들다 스스로 SIGINT를 올리고, 부모는 자식의 표준 에러 파이프를 곧바로 닫는다. 자식이 중단의 종료 코드로 끝난다. 쓰기 실패를 넘기지 않는 처리기로 먼저 빨간 것을 본다(명세 검토의 임시 스크립트에서는 종료 코드 120이었다)
- [x] **처리기를 `asyncio.run` 그대로로 바꾸면 앞의 세 사례가 빨갛다.** 한 번은 한 줄 대신 KeyboardInterrupt의 추적이 찍히고, 두 번과 닫기를 시작한 뒤의 한 번은 끝나지 않는다(`full_stack.py`의 대조군과 `close_paths.py`). 이 대조를 한 번 손으로 돌려 일지에 적는다
