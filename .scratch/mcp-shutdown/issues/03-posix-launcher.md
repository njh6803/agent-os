# 03: POSIX 런처 — 서버가 끝나거나 agent-os 프로세스가 죽으면 그 서버의 프로세스 그룹이 모두 내려간다

**What to build:** Linux(그리고 Windows가 아닌 모든 OS)에서 MCP 서버를 작은 런처 뒤에 띄운다. 입력이 닫히면 스스로 끝나는 서버가 자식을 남겨도, 정상으로 닫은 뒤 그 자식까지 내려간다. agent-os 프로세스가 갑자기 죽어도(`kill -9`, 메모리 부족으로 강제 종료, CLI의 둘째 Ctrl+C, serve 닫기 도중의 셋째 SIGINT) 서버와 그 아래가 곧 모두 내려간다(런처는 0.2초마다 부모를 보고, 측정은 3초 뒤에 모두 내려간 것을 봤다). Windows는 상류의 Job Object가 이미 같은 일을 하므로 런처를 쓰지 않는다. 서버 명령을 잘못 적었을 때의 글은 런처를 거쳐도 Windows와 같은 꼴이다(명령을 미리 찾아본다). 매니페스트는 바뀌지 않는다. 런처는 어댑터가 끼우는 것이라 플러그인 작성자가 모른다. 프로세스 목록에서 서버 위에 작은 파이썬 프로세스(런처)가 하나씩 보인다.

근거는 `.scratch/mcp-shutdown/spec.md`의 Solution 둘째 문단, 사용자 스토리 2·7·8·14·17·21·23·26·29·30, "서버를 여는 실패", "Linux 런처" 전체, "상류에 알린다", Testing Decisions의 사례 2·5, "빨강을 먼저 본다", "모듈"과 그 2026-10-21 명세 검토 주석, Out of Scope의 런처 한계다. 결정은 ADR 0034 본문의 런처와 그 2026-10-17 이력(부모 감시는 사용자가 골랐다)이다. 시제품은 `.scratch/mcp-shutdown/probes/prototype/src/agent_os/adapters/mcp_launcher.py`와 어댑터의 `_parameters`이고, 잰 것은 `close_paths.py`(`--launcher`), `serve_shutdown.py`, `stale_parent.py`, `full_stack.py`의 POSIX 단계다.

02와 나란히 돈다. 둘 다 MCP 어댑터 모듈과 그 테스트 모듈을 고쳐 뒤에 병합되는 쪽이 앞의 것을 합친다. 서버 기동 실패 테스트는 어느 쪽이 먼저 병합되어도 초록이다. 명령 찾아보기가 02가 감싸는 여는 단계 안에서 `FileNotFoundError`를 내므로, 02가 먼저면 02의 `ConnectionError`가 그것을 감싸고, 이 티켓이 먼저면 지금의 기대와 그대로 맞는다.

**Blocked by:** 01

**Status:** ready-for-agent

### 빨강을 먼저 본다

- [x] **닫기 테스트의 사례 2와 5를 더하고, 런처 없이 Linux CI에서 빨간 것을 먼저 보인다.** 사례 2는 자식을 남기는 서버의 정상 닫기 뒤 그 자식이 멈추는 것, 사례 5는 자식 프로세스가 연결을 열고 기다리는 동안 테스트가 그것을 `Popen.kill`로 끈 뒤 감싸는 프로세스와 서버가 멈추는 것이다(01의 가짜 프로세스 모듈과 하트비트 판정). draft PR에 두 사례만 든 실험 커밋을 푸시하고, 그 CI 실행이 끝까지 돌아 Linux의 `python` 잡에서 두 사례가 하트비트가 자란 까닭으로 빨간 것을 본 뒤 그 실행의 URL을 PR 본문에 남긴다. CI는 같은 브랜치의 새 푸시가 앞 실행을 취소하므로(`cancel-in-progress`) 그 실행이 끝날 때까지 푸시하지 않고, 취소되었으면 다시 돌린다. 선례는 `docs/constitution/operations.md`의 draft 실험 커밋이다. Windows에서는 두 사례가 Job Object로 이미 초록이다
- [x] **런처를 넣은 뒤 두 사례가 두 OS에서 초록이고, 부모 감시를 빼면 사례 5만 빨갛다**(`full_stack.py`의 대조군이 Docker의 Linux에서 같았다. 이 대조는 손으로 한 번 돌려 일지에 적는다)

### 런처

- [x] **자리와 띄우는 법.** 런처는 어댑터 층 안의 모듈 파일 하나이고 표준 라이브러리만 쓴다. 어댑터가 Windows가 아닌 OS에서 서버 명령을 `<이 프로세스의 파이썬> -I <런처 파일> <이 프로세스의 번호> <찾은 서버 명령> <인자…>`로 바꿔 상류에 넘긴다. `-I`는 런처 파일의 폴더를 `sys.path`에 넣지 않아 같은 폴더의 모듈 이름이 표준 라이브러리나 패키지를 가리지 않게 한다
- [x] **띄우기 전에 명령을 찾아본다.** 어댑터가 실행 경로에서 서버 명령을 찾고(`shutil.which`), 없으면 띄우지 않고 `FileNotFoundError`를 낸다. 찾은 경로를 런처에 넘긴다. 이 예외는 02가 감싸는 여는 단계 안에서 난다. Windows에서는 찾아보지 않는다(상류가 `.cmd`·`.ps1`까지 붙여 찾는다)
- [x] **그룹의 우두머리가 아니면 띄우지 않는다.** 런처는 시작하자마자 그것을 보고, 아니면 물려받은 표준 에러에 한 줄을 남기고 거부의 종료 코드 2로 끝난다
- [x] **뜨자마자 어댑터가 넘긴 번호와 부모를 견주어, 이미 다르면 띄우지 않는다.** 한 줄과 종료 코드 2다(뜬 뒤 스스로 읽은 번호와 견주는 시제품의 첫 판은 그 틈을 놓쳤다)
- [x] **서버는 같은 그룹의 자식이고 표준 입출력을 상속으로 물려받는다.** 런처는 서버를 띄운 뒤 자기 입력과 출력을 `/dev/null`로 바꾸고 표준 에러는 남긴다
- [x] **끄는 때는 서버가 끝났을 때와 부모가 죽었을 때다.** 서버를 기다리는 동안 0.2초마다 부모 번호를 보고, 바뀌었으면 서버가 끝나기 전이라도 끈다. 끄는 신호는 SIGKILL이고 그룹 전체(런처 자신도)를 한 번에 끈다. 서버의 종료 코드는 넘기지 않는다
- [x] **서버를 띄우지 못하면 한 줄과 종료 코드 127로 끝난다.** 찾아본 뒤에 명령이 사라졌거나, 실행할 수 없는 형식이거나, 셔뱅이 가리키는 인터프리터가 없을 때다. 클라이언트에는 연결이 닫힌 것으로 보인다
- [x] **서버 기동 실패 테스트가 런처를 거치는 Linux에서도 지난다**(위 머리의 병합 순서 문단)

### 프로브

- [x] **우두머리가 아닌 갈래(스토리 29)를 재는 프로브를 더한다.** `stale_parent.py`처럼 대조군을 두고 `full_stack.py`의 POSIX 단계에 엮는다. 새 세션으로 띄운 중간 프로세스가 런처를 새 세션 없이 띄우면 런처는 종료 코드 2와 "우두머리가 아니라" 한 줄을 남기고 서버의 표지를 만들지 않으며 중간 프로세스는 0으로 끝난다. 검사 줄을 끈 대조군은 서버를 띄운 뒤 부른 쪽의 그룹을 꺼 중간 프로세스가 -9로 끝난다(명세 검토가 Docker의 Linux에서 임시 스크립트로 세 회차씩 손으로 봤다). 표지와 프로세스를 끄는 규칙은 `.claude/rules/probes.md`를 따른다
- [x] **구현된 런처에 대고 `stale_parent.py`와 새 프로브를 Docker의 Linux에서 돌려 기대대로인지 프로브 README에 적는다.** `stale_parent.py`는 표준 라이브러리만 쓰고, 지금 폴더 아래 `src/agent_os/adapters/mcp_launcher.py`를 런처로 띄우며 런처의 표준 에러에서 "이미 끝나"와 "런처:"를 찾는다(셋 다 그 프로브 코드의 상수다). 그래서 저장소 루트를 지금 폴더로 두고 돌린다. 구현의 런처 파일 이름이나 한 줄의 문구가 시제품과 다르면 프로브의 상수를 구현에 맞추고, 새 프로브도 같은 꼴로 짓는다

### 상류에 알린다

- [x] **python-sdk에 올릴 이슈 초안을 `.scratch/mcp-shutdown/` 아래 파일 하나로 쓴다.** 위 빨간 CI 실행의 URL과 명세의 측정(`full_stack.py`의 런처 없는 대조군, `close_paths.py`의 `exit_child_normal`)을 든다. 닫는 도중의 네이티브 취소 뒤 자식이 끝나지 않는 것(`cli_ctrl_c_closing`, `cli_ctrl_c_twice`. 상류의 어디서 멈추는지는 가르지 않았다)도 함께 들 수 있다
- [x] **초안을 사용자에게 보여 승인을 받은 뒤에만 올린다.** 바깥에 글을 올리는 일이라서다. 올렸으면 그 이슈의 URL을, 승인되지 않았으면 그 사실을 일지와 런처 모듈의 독스트링에 적는다

### 문서와 독스트링

- [x] **`.claude/rules/adapters.md`에 런처 항목을 더한다.** 자리, 띄우는 법, 명령 찾아보기, 끄는 때, 신호, 프로세스 목록에서 서버 위에 보인다는 것(스토리 14), 상류가 POSIX의 빈틈을 고치면 런처를 뺀다는 계기(스토리 30), 그리고 알려진 한계 둘이다. 하나는 스스로 새 세션으로 떼어 낸 자식을 런처도 상류도 거두지 못한다는 것(스토리 23), 다른 하나는 런처가 그룹을 끄기 전에 밖에서 먼저 죽으면(런처만 노린 SIGKILL, 메모리 부족) 상류가 서버가 끝난 것으로 보고 묶음 끄기를 건너뛰어 서버가 남는다는 것이다(코드를 읽은 어림. 재지 않는다. 어느 결과든 결정이 바뀌지 않는다). 경계의 예외 항목은 02가 같은 파일에 더한다
- [x] **런처 모듈의 독스트링이 그 일과 대가와 뺄 계기를 든다.** 서버의 프로세스 그룹을 거두는 일, 프로세스 목록에서 서버 위에 보인다는 것(스토리 14), 서버마다 프로세스 하나와 0.2초마다의 깨어남, Windows가 아닌 모든 OS에서 서지만 macOS는 재지 않았다는 것, 스스로 새 세션으로 떼어 낸 자식은 거두지 못한다는 것(스토리 23), 그리고 상류가 POSIX의 빈틈을 고치면 런처를 빼고 그때 부모 감시를 다시 본다는 것(스토리 30)이다
- [x] **처리기 모듈의 독스트링에 둘째 Ctrl+C로 곧바로 끝낸 뒤 남은 서버를 POSIX에서는 런처의 부모 감시가 거둔다는 것을 더한다.** 01은 그때 참인 대로 "POSIX에서는 남을 수 있다"고 적었다
- [x] **MCP 어댑터 모듈의 독스트링에서 POSIX가 남기는 자식의 문장을 런처가 거두는 것으로 바꾼다.** 01은 그때 참인 대로 "유예 안에 스스로 끝난 서버가 남긴 자식은 남는다"고 적었다(01 셀프 리뷰가 짚었다, 일지 2026-10-21-06)
- [x] **`README.md`의 init 항목에 런처가 끈 서버가 init 없는 컨테이너에서 좀비로 남을 수 있다는 것을 더할지 본다.** 명세 "컨테이너"의 어림이고 런처가 들어와야 생기는 일이라 01은 뺐다(01 셀프 리뷰, 일지 2026-10-21-06). 같은 항목의 "자손 없이 서버 혼자인 그룹은 서버가 `serve`의 직접 자식이라 asyncio가 거둔다"도 다시 쓴다. 런처가 들어오면 `serve`의 직접 자식은 런처이고 서버는 그 아래다(01 PR 직전 리뷰)

### 검증과 기능 닫기

- [x] **원칙 III를 지킨다.** 런처의 POSIX 코드도 pyright strict와 타입 우회 검사를 지난다(`prctl`처럼 `ctypes`가 드는 길은 쓰지 않는다)
- [x] 검증 명령이 모두 초록이다. 어댑터를 건드리므로 `-m llm`과 전체 `tools/run_checks.py`를 돌려 일지의 검사 절에 적는다. 이 PC(Windows)의 `-m llm`은 런처를 지나지 않으므로, 런처 쪽은 CI의 Linux와 위 프로브가 본다고 함께 적는다
- [ ] **기능을 닫는지는 main을 마지막으로 들인 뒤, 병합 바로 앞에 판정한다.** `git fetch` 뒤 `origin/main`의 02 티켓 파일 `Status:`가 `done`이면 이 PR이 `.scratch/plan.md`의 mcp-shutdown 행을 `done`으로 바꾸고 프론티어 문단을 고친다. 아니면 02가 닫는다. main이 최신 기준(strict)이라 뒤에 병합되는 쪽은 앞의 병합을 들여야 병합할 수 있는데, strict는 코드를 묶을 뿐 판정한 때를 묶지 않는다. 그래서 판정 뒤에 main을 다시 들였으면 다시 판정한다. 아니면 둘 다 "아직"으로 판정한 채 병합되어 아무도 닫지 않는다(셀프 리뷰가 짚었다. 01은 이 티켓을 막고 있어 이미 `done`이다)
