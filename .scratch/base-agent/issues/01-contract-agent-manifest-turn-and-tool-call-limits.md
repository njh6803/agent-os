# 01: 계약 — 에이전트 매니페스트에 턴의 끝과 도구 호출의 끝이 생기고 런타임이 지킨다

**What to build:** 에이전트 저자가 매니페스트에 선택 칸 `max_turns`(턴의 끝)와 `max_tool_calls`(도구 호출의 끝)를 적으면 런타임이 그 실행을 그 값으로 묶는다. 턴의 끝을 넘긴 실행은 지금처럼 원인 `loop_limit`의 `run_failed`로 끝나고 문구가 그 끝을 싣는다. 도구 호출의 끝을 넘은 호출은 불리지 않는다. 적용 규칙 칸(`rule`)이 빈 `tool_called(ok=false)`가 정해진 문구로 남고, 루프에서는 그 글이 도구 결과로 모델에 돌아가 실행이 이어진다. 턴의 끝을 10보다 크게 적은 에이전트의 실행은 준비 단계에서 시작 전에 거부된다. 두 칸을 적지 않은 에이전트는 지금과 똑같이 돈다(턴의 끝 10, 도구 호출의 끝 없음). 관리 API와 관리 화면의 플러그인 상세는 매니페스트 JSON에 두 칸을 싣는다.

이 기능의 계약 티켓이고 03을 막는다(04·05·06·07은 03을 거쳐 막힌다. 02는 이 티켓과 나란히 돈다). 계약은 sdk 에이전트 매니페스트의 두 칸, `openapi.json`, api-client의 생성물이다. 끌고 오는 것은 관리 화면에서 매니페스트 객체를 손으로 적은 여섯 파일과 사진 정답, core의 집행, 규칙 문서와 독스트링이다. 칸만 읽히고 집행이 없는 판이 main에 서지 않게 계약과 집행을 한 티켓에 둔다(명세 "고칠 자리의 묶음"의 A 줄, to-tickets에서 사용자가 이 분할을 골랐다. 일지 2026-11-11-1555). 리뷰의 질문은 "동작하나"에 더해 이 칸 이름과 뜻(무엇을 한 번으로 세는지, 셈과 승인의 차례)으로 오래 살 수 있느냐다.

근거는 `.scratch/base-agent/spec.md`의 Implementation Decisions "매니페스트의 칸 둘", "도구 호출을 세는 법", "셈과 승인의 차례", "끝을 넘은 호출의 기록", "턴의 끝", "고칠 자리의 묶음"의 A 줄과 Testing Decisions "두 끝의 시험"이다. 앞선 결정은 ADR 0052(칸 둘과 그 뜻), ADR 0009(재개하면 재생된 턴도 센다, 상한을 올리는 것은 별도 결정), ADR 0044의 2026-11-10 이력 "도구 호출의 끝을 넘은 호출은 집행의 차례에 들기 전에 거부된다"다. 사진 정답이 바뀌는 선례는 ADR 0049의 2026-11-10 이력 "관리 화면의 매니페스트 JSON에 transport 줄이 늘어 사진 정답이 바뀐다"다.

**Blocked by:** None (can start immediately)

**Status:** done

### sdk — 매니페스트의 칸 둘

- [x] 에이전트 매니페스트에 선택 칸 `max_turns`와 `max_tool_calls`가 있다. 모양은 선례 `conversation_limit`과 같다. 1 이상의 엄격한 정수만 받고 기본은 없음이다. 0, 음수, 불린, 숫자 문자열, 실수(`2.0` 포함)는 매니페스트를 읽는 단계에서 거부한다
- [x] 에이전트가 아닌 종류가 적으면 `<종류> 플러그인은 max_turns 를 갖지 않는다`, `<종류> 플러그인은 max_tool_calls 를 갖지 않는다`로 거부한다
- [x] sdk는 10을 적지 않는다. `max_turns = 11`은 읽힌다. 두 칸 사이의 관계도 검사하지 않는다
- [x] 직렬화 스키마에서 두 칸은 `conversation_limit`처럼 required이고 값은 1 이상의 정수나 null이다. `openapi.json` 스냅샷과 api-client의 생성물이 함께 바뀐다
- [x] `.claude/rules/sdk.md`의 에이전트 매니페스트 선택 칸 항목에 두 칸이 들고, "런타임은 `tool_called.rule`을 … 연결에 없는 이름에는 비운다"에 끝을 넘은 호출이 든다

### core — 턴의 끝

- [x] 루프는 그 실행에 걸린 끝까지 돈다. 끝은 매니페스트의 `max_turns`이고 없으면 core의 10이다. 넘기면 원인 `loop_limit`의 `run_failed`이고 문구는 `루프가 <끝>턴 안에 멈추지 않았다`다. 마지막 턴에 모델이 낸 도구 호출은 지금처럼 실행한 뒤에 던진다
- [x] 10을 넘는 값은 core가 실행을 준비할 때 보고, 넘으면 기반 타입 `PluginError`로 실행을 시작하지 않는다. 실행 식별자를 만들기 전이라 트레이스가 없다. 문구는 `에이전트 <이름> 의 max_turns 가 루프 상한 10 을 넘는다`이고 적힌 값을 되울리지 않는다
- [x] 채널은 그 거부를 다른 깨짐과 같이 운영자 면 500, 최종 사용자 면 고정 문구의 500으로 낸다. 매니페스트 자체는 읽히므로 관리 화면의 플러그인 목록과 상세에는 그 에이전트가 그대로 보인다
- [x] 그 거부의 자리는 준비 순서의 깨짐 묶음 맨 앞이다(부재 다음, mcp의 깨짐보다 앞). 꺼진 에이전트여도 이 거부가 먼저 난다
- [x] 재개도 준비를 다시 지난다. 멈춘 사이 값을 10 넘게 고쳤으면 재개가 결정 이벤트를 쓰기 전에 거부되고 그 실행은 일시정지 그대로다. 멈춘 사이 값을 낮췄으면 재생된 턴이 새 끝을 넘는 자리에서 `loop_limit`으로 끝난다

### core — 도구 호출의 끝

- [x] 한 번은 도구를 부르는 한 자리에 들어온 시도 하나이고 결말이 무엇이든 센다(성공, 도구의 실패, 연결에 없는 이름, 운영자의 deny, 승인자의 거부, 끝 넘음)
- [x] 셈은 그 자리의 맨 앞, 실행이 이미 멈췄는지를 본 바로 뒤이자 재생된 기록을 찾기 전에 올린다. 재생된 호출도 처음과 같은 번호로 다시 세어지고, 멈춘 호출은 재개 뒤 같은 번호로 한 번만 세어진다. 이미 멈춘 실행에서 더 부른 호출은 세지 않는다
- [x] 끝을 넘었는지는 "결정을 꺼내고 재개를 기록한다" 바로 뒤, "연결에 없는 이름" 앞에서 본다. 그래서 끝을 넘은 호출은 승인 대상이어도 `run_paused`가 나지 않고, 연결에 없는 이름이어도 deny인 도구여도 같은 문구로 거부되며, 도구는 불리지 않는다
- [x] 재생된 호출은 재개 사이에 끝이 바뀌었어도 기록 그대로 돌려주고 다시 판정하지 않는다. 멈춘 사이 끝을 낮춰 멈춘 호출이 끝을 넘게 됐으면 결정을 꺼내고 재개를 기록한 뒤 끝 넘음으로 거부한다(결정이 승인이어도 부르지 않는다)
- [x] 끝을 넘은 호출의 기록은 `tool_called(ok=false)`이고 `content`는 `도구 호출 횟수를 넘었다: 이 실행은 도구를 <N>번까지 부른다`, `args`는 마스킹을 지난 인자, `rule`은 비운다. 이벤트의 계약과 적용 규칙의 다섯 값은 바뀌지 않는다
- [x] 직접 부른 에이전트(`ctx.tool()`)는 같은 글의 `ToolError`를 받고, 흘리면 원인 `tool_failure`다
- [x] 도구 호출의 끝을 적지 않은 에이전트의 실행은 이 판정을 지나지 않는다

### 시험 (명세 "두 끝의 시험")

- [x] 매니페스트(선례 `tests/sdk/test_manifest.py`의 `conversation_limit` 사례): 칸마다 1은 받고 0·음수·불린·숫자 문자열·실수는 거부한다. 에이전트가 아닌 종류는 거부한다. 적지 않으면 없음이다. `max_turns = 11`은 읽힌다. openapi 스냅샷에 두 칸이 required로 실린다
- [x] 턴의 끝(선례 `tests/core/test_run.py`의 `test_루프가_상한을_넘으면_실패_이벤트로_끝난다`, 재개 절의 `test_루프_상한은_재생된_턴을_포함해_세고_멈추고_재개를_반복해도_무한히_돌지_않는다`, "실행 전 실패의 갈래" 절): 끝이 3인 에이전트가 세 턴 내내 도구를 내면 `loop_limit`이고 문구가 3을 싣는다. 칸이 없으면 10턴째에 같은 원인이고 문구가 10을 싣는다(지금의 시험이 그대로 초록이다). 끝이 11이면 `PluginError`로 시작 전에 거부되고 트레이스가 없으며 문구가 적은 값을 싣지 않는다. 그 거부가 mcp의 깨짐과 꺼짐보다 먼저 난다. 멈춘 실행의 재개도 같은 거부를 받고 결정 이벤트가 쓰이지 않는다. 멈춘 사이 끝을 낮춘 재개는 재생된 턴이 새 끝을 넘는 자리에서 `loop_limit`이다
- [x] 도구 호출의 끝(같은 파일의 "거부", "결정은 멈춘 호출에 묶인다", "실행 전·연결 직후·재개의 검사 셋" 절): 끝이 2인 에이전트가 도구를 셋 내면 셋째가 불리지 않고(가짜 도구 소스의 호출 기록이 둘) 정해진 문구와 빈 `rule`의 `tool_called(ok=false)`가 남으며 실행은 답으로 끝난다. 한 턴에 셋을 내도 같다. 연결에 없는 이름, 운영자의 deny, 승인자의 거부, 도구의 실패가 각각 한 번으로 세어진다. 끝을 넘은 호출이 승인 대상이어도 `run_paused`가 나지 않는다. 끝을 넘은 호출이 deny인 도구여도 문구는 끝 넘음이다. 직접 호출은 같은 문구의 `ToolError`를 받고 흘리면 `tool_failure`다. 재개한 실행에서 재생된 호출이 다시 세어져 승인 한 번이 횟수를 더 주지 않는다. 멈춘 사이 끝을 낮춘 재개는 결정이 승인이어도 끝 넘음으로 거부되고 도구가 불리지 않는다. 그 재개에서 재생된 호출은 낮춘 끝을 넘는 번호여도 기록 그대로 돌아오고 `tool_called`가 새로 쓰이지 않는다. 칸이 없는 에이전트는 도구를 몇 번이든 부른다
- [x] 위 사례들은 "런타임이 기록한 `tool_called` 가운데 끝 넘음의 문구가 아닌 것은 많아야 N개"를 호출 기록의 수로 단언한다. 문구만 보는 단언은 도구가 실제로 불렸는지를 보지 못한다
- [x] 검증 명령이 모두 초록이다. api-client를 건드리므로 관리 화면 e2e(`pnpm -C web/apps/admin exec playwright test`)와 관리 화면 사진 비교도 친다. 예외: 관리 화면 e2e의 `decision.e2e.ts` 첫 시험이 이 PC에서 5초 기대 시간에 걸려 실패했다(기대 시간을 늘린 임시 설정에서는 통과, main 대조는 안 했다). 판정은 CI의 `e2e` 잡이 한다
