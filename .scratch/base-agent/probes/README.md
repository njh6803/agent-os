# base-agent 프로브

명세가 근거로 드는 측정 스크립트다. 규약은 `docs/agents/issue-tracker.md`의 "프로브와 근거", 짓는 규칙은 `.claude/rules/probes.md`다. 근거로 드는 자리는 `.scratch/base-agent/spec.md`, ADR 0051의 2026-11-10 이력 둘과 2026-11-11 이력, 명세가 결과를 넘긴 기능 계획 셋(`.scratch/public-demo/plan.md`, `.scratch/answer-eval/plan.md`, `.scratch/local-model/plan.md`), 일지 `docs/journal/2026-11-10-1906-base-agent-spec.md`와 `docs/journal/2026-11-11-1555-base-agent-tickets.md`다.

## 돌리는 법

실제 모델을 부르므로 비용이 든다. 환경에 `ANTHROPIC_API_KEY`가 있어야 하고(없으면 2로 끝난다), 워크트리에서는 주 체크아웃의 `.env`를 `--env-file`로 읽는다(`docs/constitution/operations.md` LLM 테스트). 저장소 루트(워크트리면 그 루트)에서 돈다.

```sh
uv run --env-file <.env 경로> python .scratch/base-agent/probes/skill_follow.py --rounds 2
uv run --env-file <.env 경로> python .scratch/base-agent/probes/skill_follow.py --only "전문 읽기 거부,빈 전문" --rounds 3 --out <기록을 둘 폴더>
```

인자 없이 돌리면 사례 스물여덟을 한 바퀴 돈다. `--only`는 사례 이름을 쉼표로 이어 받는다. 모르는 사례 이름과 1보다 작은 `--rounds`는 돌리지 않고 2로 끝난다(손으로 봤다, `… skill_follow.py --only bogus_case`가 "모르는 사례: bogus_case"를 찍고 2로 끝났다). 프로브는 가짜 검색 서버를 루프백의 빈 포트에 띄우고 자기가 쥔 `Popen` 핸들로만 끈다. 기본 구성이 아닌 것으로 도는 사례 일곱(서버를 모드로 띄우는 다섯과 매니페스트의 `conversation_limit`을 1로 적는 둘)은 회차마다 제 서버와 플러그인 루트를 따로 띄운다. 서버의 모드는 넷이다. 실패 모드 둘(`--tool-cap N`, `--search-down`), 빈 색인(`--empty-index`), 전문 창의 상한(`--text-max-chars N`, 기본 20000)이고 뜻은 `fake_doc_search.py`의 독스트링이 적는다. 플러그인 루트와 트레이스는 임시 폴더에 쓰고 지우지 않는다. 끝에 찍는 경로는 기록(`skill_follow.json`)과 트레이스 폴더 둘이다. `--out`을 주지 않으면 기록도 그 임시 폴더에 쓴다.

프로브는 통과와 실패를 가르지 않는다. 사례마다 재려는 상황이 그 회차에 났다는 표지를 본 뒤, 모델이 한 일을 낱말로 적는다. 표지가 없는 회차는 측정이 아니라고 세고, 그런 회차가 하나라도 있으면 1로 끝난다(`tools/probe_kit.py`의 `Rounds`).

## 2026-11-11 결과 (초안 7)

### 초안 7: 결과를 보기 전에 바꾼 글자와 판정, 적은 기대

이 절은 돌리기 전에 적었다. 초안 6의 "답 둘을 하나로" 2회차는 셋째 실행이 두 답을 저마다의 "출처" 블록째 이어 붙여, 한 답 안에서 `[1]`이 육아휴직 업무편람과 연차휴가 운영지침을 함께 가리켰다(초안 6 절의 "기대와 달랐던 것"). 스킬의 두 지시("앞의 답 그대로 옮긴다"와 "같은 문서의 같은 위치는 같은 번호를 쓴다")가 답 여럿을 합치는 경우에 부딪혀 생긴 틀린 출처로 보고 둘을 고쳤다.

**스킬.** `draft/skills/cite-sources/SKILL.md`의 둘째 갈래에서 "앞의 답을 다듬을 때는 남긴 문장이 쓰는 번호와 "출처"의 줄을 앞의 답 그대로 옮긴다." 바로 뒤에 한 문장을 더했다. 다른 글자는 초안 6 그대로다.

    앞의 답 여럿을 하나로 합칠 때는 같은 번호가 다른 출처를 가리키지 않게 번호를 다시 매기고 "출처" 목록도 하나로 합친다.

**판정(결과를 보기 전에 바꿨다).** "답 둘을 하나로"의 판정 `_merged`는 초안 6까지 마지막 "출처" 줄 뒤의 줄만 읽었다(`rpartition`). 그래서 초안 6 2회차의 False는 육아휴직 업무편람의 줄을 보지 못한 값이었고, 같은 번호가 두 문서를 가리킨 것은 판정에 드러나지 않았다. 지금은 출력 전체에서 "출처" 블록을 모두 읽는다. 블록은 앞뒤의 `*`, `#`, `:`를 뗀 글이 "출처"인 줄이 열고, 그 아래 `N. …` 꼴의 줄을 모은다. 목록 줄 뒤에 목록이 아닌 줄이 나오면 닫힌다. 블록이 하나이고, 같은 번호를 쓴 출처 줄이 둘 이상 없고, 두 문서의 줄이 모두 있을 때만 "출처 블록 하나에 번호가 겹치지 않음 True"다. 블록 수, 두 줄이 쓴 번호, 두 문서가 다 있는지는 늘 괄호에 함께 찍는다. 새 읽기를 초안 6의 기록에 대 보니 1회차는 블록 1개에 번호 1·2·3, 2회차는 블록 2개에 번호 1·1·2였다(손으로 봤다, 스크래치패드의 `merged_check7.py <프로브 폴더> <초안 6 기록 폴더>`). 표지(`_carried`, 셋째 실행의 프롬프트에 앞의 답 둘이 글자 그대로 실렸다)는 그대로다.

**돌릴 것.** 스킬의 글자를 고쳤으므로 사례 스물여덟 두 바퀴를 다시 돌고, 따로 "답 둘을 하나로"만 세 바퀴를 더 돈다(`--only`). 기록은 새 `--out` 폴더에 둔다.

**기대.**

- 답 둘을 하나로: 다섯 회차 모두 셋째 실행이 검색하지 않고, 출처 블록 하나에 번호 1·2·3을 매겨 True.
- 다듬기, 요약만 남은 다듬기: 앞의 답 하나를 다듬는 요청이라 더한 문장이 닿지 않는다. 초안 6의 판정과 같다(다듬기는 검색 없이 번호 둘과 출처 줄 둘을 남기고, 요약만 남은 다듬기는 검색한다).
- 앞 대화를 묻는 말, 앞 대화 없이 앞 질문을 묻는 말, 요약만 남은 앞 대화를 묻는 말: 초안 6의 판정과 같다.
- 정해진 문장으로 답한 사례 아홉: 열여덟 회차 모두 글자 그대로.
- 나머지: 초안 6의 판정과 같다. 긴 문서의 전문 승인에서 읽지 않은 뒷부분을 "찾지 못했다"고 답하는 것은 사용자가 고른 선택지가 치르는 값으로 받아들였다(본 세션의 판정). 이 판에서도 그 말을 판정으로 가르지 않고 출력만 적는다.

- **칸.** 결과는 rag-engine의 출력 모델을 칸 설명까지 옮긴 pydantic 모델의 `model_dump_json()` 글이다. 그래서 JSON에 띄어쓰기가 없고(앞 판은 `json.dumps`라 `": "`였다), 식별자는 UUID, 갱신일은 `Z`로 끝나며, 조각의 `location`에 `block_kind`와 블록 순번의 `block_range`가 실린다. structured content도 싣고 outputSchema를 내므로, mcp 2.3.0이 성공 결과를 그 스키마로 서버와 클라이언트에서 검증한다. 도구 설명 글과 주석, 입력의 이름·타입·기본값(`search`의 `top_k`는 null 기본, `filter`의 모델과 칸 설명, `get_document`의 `offset`, `max_chars`)도 옮겼다.
- **창.** `get_document`가 `include_text`면 rag-engine 명세 197줄의 규칙(블록 경계에서 자르고 `next_offset`을 준다)으로 창을 낸다. 함수는 `app/document_text.py`를 그대로 옮겼다. 상한과 기본값은 `--text-max-chars N`(기본 20000)이고 도구 설명 글의 수도 그 값이 된다.
- **오류.** 다섯 코드의 `isError` 결과를 실패 결과로 직접 돌려준다. 글은 `{"type":"about:blank","title":"검색을 쓸 수 없다","status":503,"code":"search_unavailable","request_id":"<uuid4>"}` 꼴이다(앞 판은 `title`에 코드를 적었고 인자 오류 셋을 보통 결과로 돌려주었으며 `invalid_argument`의 상태가 400이었다. 지금은 422다). 식별자가 UUID가 아니면 `invalid_argument`다.
- **새 모드 둘.** `--empty-index`(현재 색인 판이 없을 때처럼 `results`가 빈 배열), `--text-max-chars N`. 실패 모드 둘(`--tool-cap N`, `--search-down`)은 그대로이고, `--search-down`은 입력과 지식베이스를 확인한 뒤에 실패한다.
- 서버를 실제 mcp 클라이언트로 띄워 도구 목록(설명 글, inputSchema, outputSchema의 칸)과 오류 결과 다섯 갈래(UUID가 아닌 식별자, 없는 문서, `max_chars` 0, 없는 지식베이스, 빈 질의)의 글과, 긴 문서의 첫 창을 받아 봤다(손으로 봤다, 스크래치패드의 `list_tools6.py`를 `--text-max-chars 320`으로 돌렸다). 실제 rag-engine 서버가 내는 목록과 글자 그대로 대 보지는 않았다. 같은 서명과 같은 mcp 판에서 지어지므로 같다고 본다(어림).

그래서 기대가 바뀐 사례는 여섯이다. 근거 있음과 인사가 섞인 물음은 위치가 "12쪽"에서 가장 안쪽 절 제목 "2.1 휴직 기간"으로 바뀌었다(판정에서 "12쪽"을 빼고 위치를 따로 가른다). 두 가지 물음은 PDF 근거라 출처 줄에 쪽(3쪽, 5쪽)을 기대하게 더했다. 전문 읽기 승인은 제목이 `## 2.6 복직 절차` 줄로 들어가 `#` 표시를 떼고 적는지를 더했다. 빈 전문과 검색 실패는 표지의 글자가 새 JSON의 꼴로 바뀌었다(빈 전문은 `"text_length":null,"text":null,"next_offset":null`, 검색 실패는 위 오류 글의 `code`까지). 나머지 사례의 기대는 그대로다. 이어지는 물음과 지시가 섞인 조각의 출처 줄도 쪽 대신 절 제목이 되지만, 그 두 사례의 판정은 위치를 보지 않는다.

- **실패 모드의 글자.** 끝 넘음을 흉내 내는 모드는 런타임이 낼 문구(명세 "끝을 넘은 호출의 기록")를 실패 결과로 돌려준다. 런타임이 거부한 것이 아니므로 트레이스가 다르다. 런타임의 거부는 적용 규칙 칸이 비고 서버에 닿지 않는데, 이 흉내는 서버에 닿아 실패한 호출이라 적용 규칙이 `allow`로 남는다. 모델이 받는 글은 같다(아래 "초안 5: 실패 모드 사례"에 그 글을 트레이스에서 본 것을 적었다). 검색 실패 모드의 오류 글에 든 `status` 503은 문서 검색 서버의 명세에서 찾지 못해 지은 값이다.
- **가르지 못한 것.** 스킬의 어느 문장이 어느 행동을 만들었는지는 대조 갈래(그 문장을 뺀 판)를 두지 않아 가르지 못했다. 두 가지는 스킬의 글자 없이는 나올 수 없어 스킬이 닿았다는 표지가 된다. 정해진 문장의 글자와, 출처 줄의 꼴(`1. 제목, 위치 (갱신일 YYYY-MM-DD)`)이다. 인사에 검색 없이 답한 것, 다듬을 때 다시 검색하지 않은 것, 끝 넘음을 받은 뒤 도구를 더 내지 않은 것, 전문의 위치를 절의 제목으로 적은 것(초안 2는 그 문장이 없는데도 그렇게 적었다)은 스킬 없이도 그랬을 수 있다.
- **재지 않은 것.** 매니페스트의 두 끝(`max_turns`, `max_tool_calls`)은 코드에 없어 걸지 않았다. 도구 호출의 끝은 위 흉내로 그 문구를 받은 모델이 한 일만 쟀고, 턴의 끝은 흉내도 내지 않았다. 다른 모델, 실제 문서 검색 서버, 긴 전문, 검색 결과가 비어 오는 때, `get_document`가 실패하는 때, 검색이 한 번만 실패하고 다시 부르면 되는 때는 재지 않았다. 답의 뜻이 맞는지는 정해 둔 낱말(쪽, 날짜, 숫자)이 답에 있는지로만 봤다.

### 초안의 차례

스킬의 글자를 다섯 번 지었다. 앞의 세 판은 돌린 범위가 좁다. 판마다의 기록은 세션 스크래치패드에 두고 커밋하지 않았다. 명세에 실린 글자는 초안 5다.

"물음 하나에는 검색어 하나로 한 번 검색하고, 그 결과를 읽은 뒤에 다시 검색할지 정한다"가 한 턴의 검색 둘을 줄였는지는 가르지 못했다. 그 문장이 없던 초안 2는 한 회차뿐이고(11개 가운데 6개), 문장이 든 초안 3과 4의 네 회차에서는 같은 사례들의 실행 44개 가운데 14개였다. 초안 5의 두 바퀴에서는 같은 사례들의 실행 22개 가운데 6개였다(초안 3 뒤에 더한 사례까지 넣은 수는 아래 "초안 5: 횟수와 토큰"). 줄었을 수 있으나 앞의 판이 한 회차라 어림이다.

정해진 문장으로 답한 사례는 일곱이다(근거 없음, 범위 밖 추천, 범위 밖 상식, 지침 무시 요구, 전문 읽기 거부, 빈 전문, 전문이 필요한 물음). 열네 회차 모두 앞뒤 공백을 다듬은 출력이 정해진 문장과 글자 그대로 같았다.

눈에 띈 것은 둘이다. 요약만 남은 다듬기는 스킬의 글자대로 검색하는 갈래로 갔다. 답 둘을 하나로 정리할 때 스킬은 번호와 출처 줄을 "앞의 답 그대로" 옮기라고 적는데, 두 답의 번호가 겹치자 모델이 번호를 다시 매겼다. 겹친 번호를 그대로 두면 틀린 답이 되므로 받아들이고, 그 경우의 문장은 스킬에 더하지 않았다.

### 초안 5: 새 갈래 열하나 두 바퀴와 정해진 문장 사례 다섯 세 바퀴

위의 두 바퀴 앞에 좁은 실행 둘을 돌렸다.

- **새 갈래 열하나 두 바퀴.** 초안 5가 고친 글자가 닿는 사례 셋(지시가 섞인 조각, 다듬기, 앞 대화를 묻는 말)과 새 사례 여덟이다. 22회차가 모두 측정이었고 측정 아님은 0, 종료 코드 0이었다. 실패 모드 사례 셋을 뺀 여덟 사례의 판정은 위 표와 같았다(이 실행의 판정 글자는 "정해진 문장이 아닌 답" 자리에 "다른 답"이 찍혔다. 아래 "결과를 본 뒤 바꾼 것").
- **정해진 문장 사례 다섯 세 바퀴.** 근거 없음, 범위 밖 추천, 범위 밖 상식, 전문 읽기 거부, 끝 넘음 뒤 근거 없음이다. 15회차가 모두 측정이었고 측정 아님은 0, 종료 코드 0이었다. 열다섯 회차 모두 정해진 문장 그대로였다. 범위 밖 상식의 한 회차는 한 번만 검색했고 나머지 회차는 검색을 두 번 냈다.

그래서 초안 5로 전문 읽기에 거부를 보낸 다섯 회차(두 바퀴와 세 바퀴)는 모두 정해진 문장 그대로였고 전문에만 있는 내용(7일)은 답에 없었다. 초안 4에서는 다섯 회차 가운데 하나가 말을 붙였다(아래 "초안 4"). 두 판의 차이가 글자 때문인지 회차의 흔들림인지는 가르지 못했다. 초안 5가 고친 두 자리는 거부 뒤의 답을 다루는 문장이 아니다.

실패 모드가 아닌 사례에서 정해진 문장으로 답한 회차는 초안 5의 실행들을 모아 스물아홉이고(근거 없음 8, 범위 밖 추천 5, 범위 밖 상식 5, 지침 무시 요구 2, 전문 읽기 거부 5, 빈 전문 2, 전문이 필요한 물음 2) 모두 글자 그대로였다(손으로 봤다, 위 "근거의 종류"의 스크립트).

### 초안 5: 실패 모드 사례

가짜 서버의 실패 모드 둘로 도는 사례 셋이다. 회차마다 그 모드의 서버를 따로 띄운다. 표지는 스킬이 닿았다는 것과, 재려는 글로 시작하는 실패 결과가 기록된 뒤에 모델이 다시 불렸다는 것이다.

**첫 판은 글 앞에 머리말이 붙었다.** 가짜 서버의 첫 판은 실패를 `ToolError`를 던져 냈다. mcp 2.3.0은 도구 함수가 던진 `ToolError`의 글 앞에 `Error executing tool <이름>: `을 붙여 결과로 돌려준다(`server/mcpserver/tools/base.py`를 읽었다. 그 밖의 예외는 예외의 글 없이 `Error executing tool <이름>`만 간다. 같은 파일 204~213줄). 그래서 모델이 받은 글은 런타임이 낼 문구가 아니라 `Error executing tool search: 도구 호출 횟수를 넘었다: 이 실행은 도구를 1번까지 부른다`였다. 독스트링에는 코드 한 곳만 읽고 "머리말 없이 결과의 글이 된다"고 적어 두었고, 트레이스의 `tool_called.content`를 보고서야 알았다(손으로 봤다. 스물다섯 사례 두 바퀴의 트레이스 폴더를 `Error executing tool search:`로 Grep해 여덟 줄이 나왔다). 위의 세 실행(열하나 두 바퀴, 다섯 세 바퀴, 스물다섯 두 바퀴)의 실패 모드 회차 열다섯은 그 머리말이 붙은 글로 잰 것이다.

**고친 판.** 실패 결과를 `CallToolResult`로 직접 돌려주게 고쳤다. 고친 뒤 여섯 사례(실패 모드 셋과 근거 있음, 근거 없음, 전문 읽기 승인)를 세 바퀴 돌렸다. 18회차가 모두 측정이었고 측정 아님은 0, 종료 코드 0이었다. 그 실행의 트레이스에서 본 것은 둘이다(손으로 봤다).

- 실패 결과의 글이 머리말 없이 시작했다. 트레이스 폴더를 `Error executing`으로 Grep해 0건이었고, 끝 넘음 결과 여섯의 `content`는 `도구 호출 횟수를 넘었다: 이 실행은 도구를 1번까지 부른다`와 글자 그대로 같았으며, 검색 실패 결과 여섯의 `content`는 `{"type": "about:blank", "title": "search_unavailable"`로 시작했다.
- 정상 결과의 글은 고치기 전과 같았다. 고치기 전의 트레이스(스물다섯 사례 두 바퀴)와 고친 뒤의 트레이스에 함께 있는 성공한 호출 다섯 가지(검색어가 같은 검색 넷과 전문 읽기 하나)의 `content`가 글자 그대로 같았다(스크래치패드의 `compare_tool_results.py`로 두 폴더를 대 봤다. 커밋하지 않았다). 그래서 실패 모드가 아닌 사례의 앞선 결과는 다시 재지 않았다.

그 뒤 표지를 "글에 그 문구가 들어 있다"에서 "글이 그 문구로 시작한다"로 조였다. 머리말이 붙은 글은 이 표지로는 측정이 아니다. 조인 표지로 실패 모드 사례 셋을 한 바퀴 더 돌렸다. 3회차가 모두 측정이었고 측정 아님은 0, 종료 코드 0이었으며, 그 트레이스 폴더도 `Error executing`으로 Grep해 0건이었다(손으로 봤다). 그래서 고친 판으로 잰 회차는 사례마다 넷이다(세 바퀴는 조이기 전의 표지로 세었고 글의 머리는 위처럼 손으로 봤다).

| 사례 | 요청과 모드 | 고친 판 네 회차 | 머리말이 붙은 판 |
|---|---|---|---|
| 끝 넘음 뒤 근거 없음 | 출산 축하금은 얼마야?(`--tool-cap 1`) | 네 회차 모두 한 번 검색하고, 표현을 바꾼 둘째 검색이 끝 넘음으로 돌아오자 도구를 더 내지 않고 정해진 문장 그대로 답했다(모델 3, 도구 2) | 일곱 회차 모두 결과가 같았다 |
| 끝 넘음 뒤 두 가지 물음 | 연차휴가는 며칠 주는지, 그리고 국내 출장 숙박비 상한은 얼마인지 알려줘(`--tool-cap 1`) | 네 회차 모두 한 턴에 검색 둘을 냈고 둘째가 끝 넘음으로 돌아오자 도구를 더 내지 않았다. 첫 검색의 결과만으로 15일과 8만원을 번호와 출처 줄과 함께 답했다(모델 2, 도구 2) | 네 회차 모두 결과가 같았다 |
| 검색 실패 | 육아휴직은 최대 몇 년까지 쓸 수 있어?(`--search-down`) | 네 회차 모두 실패를 받고 표현을 바꿔 한 번 더 검색했고, 그것도 실패하자 도구 없이 답했다. 답은 정해진 문장이 아니라 검색 기능의 오류(503)로 문서를 확인하지 못했으니 잠시 뒤 다시 물어 달라는 안내였다(모델 3, 도구 2) | 네 회차 가운데 셋은 같은 안내였고, 하나는 정해진 문장 뒤에 검색 기능에 오류가 나고 있다는 한 문장을 괄호로 붙였다 |

끝 넘음 뒤 두 가지 물음에서 둘째 물음까지 답할 수 있었던 것은 가짜 서버의 첫 검색이 조각 여섯을 모두 돌려주기 때문이다. 조각이 많은 실제 서버에서는 첫 검색의 결과에 둘째 물음의 근거가 없을 수 있다(재지 않았다).

고친 판의 검색 실패 네 회차의 답은 이렇다.

    검색 기능에 일시적인 오류(503)가 발생해 등록된 문서를 조회하지 못했습니다. 근거를 확인할 수 없어 답변을 드리기 어려우니, 잠시 후에 다시 질문해 주세요.

    지금 문서 검색 기능이 일시적으로 작동하지 않아(오류 503) 등록된 문서를 확인할 수 없었습니다. 근거 없이 답변드릴 수는 없으니, 잠시 후 다시 질문해 주시겠어요?

    지금 문서 검색 기능이 일시적으로 응답하지 않아(오류 503) 등록된 문서를 확인하지 못했습니다. 검색 없이 답변드릴 수는 없으니, 잠시 후 다시 질문해 주세요.

    지금 문서 검색 기능에 일시적인 오류(503)가 발생해 근거를 확인하지 못했습니다. 잠시 후 다시 질문해 주시면 등록된 문서에서 육아휴직 사용 기간을 찾아 답변드리겠습니다.

스킬에는 검색이 실패했을 때의 지시가 없다. 정해진 문장은 검색했는데 근거가 없을 때의 것이라, 이 답들은 스킬의 글자와 어긋나지 않는다. 명세는 이 갈래의 지시를 더하지 않고 관찰로 적었다(명세의 Further Notes).

### 초안 5: 횟수와 토큰 (사례 스물다섯 두 바퀴)

- 기본 구성으로 돈 실행 50개 가운데 가장 많이 쓴 값은 모델 3번, 도구 3번, 한 턴의 도구 2개, 입력 15,168 토큰, 출력 1,081 토큰이다(프로브가 찍었다). 모델 3번에 도구 3번은 전문 사례들에서 났다(한 턴에 검색 둘, 전문 읽기, 답). 기본 구성이 아닌 사례의 실행은 이 셈에 넣지 않는다.
- 인사 한 번의 입력은 2,461 토큰이다. 스킬이 실린 프롬프트와 도구 정의가 드는 값으로 본다(내역은 가르지 않았다. 어림).
- 한 턴에 도구를 둘 이상 낸 실행은 50개 가운데 16개다(프로브가 찍었다). 여섯은 두 가지를 물은 요청의 실행 여섯 모두다(두 가지 물음, 다듬기와 앞 대화를 묻는 말의 첫 요청). 나머지 열은 물음이 하나이고 검색한 실행 32개 가운데 났다(손으로 봤다, 위 스크립트). 지침 무시 요구의 1회차, 범위 밖 추천의 2회차, 전문 읽기 승인의 2회차, 전문 읽기 거부·제목 없는 전문·빈 전문의 두 회차씩, 전문이 필요한 물음의 1회차다. 조각에 근거가 있는 물음의 실행 14개(근거 있음, 지시가 섞인 조각, 인사가 섞인 물음, 이어지는 물음의 두 실행, 답 둘을 하나로의 앞 두 실행)에서는 나지 않았다.
- 한 턴에 둘을 낸 실행은 차례로 검색한 실행보다 모델 호출이 하나 적었다. 범위 밖 추천의 2회차는 모델 2번에 입력 8,463 토큰이고, 차례로 두 번 검색한 1회차는 모델 3번에 입력 12,673 토큰이다. 가짜 서버의 값이다.

### 초안 4: 전문 사례 셋 한 바퀴와 "전문 읽기 거부" 세 바퀴

전문 사례 셋(전문 읽기 승인, 제목 없는 전문, 빈 전문)은 사례 둘을 더한 직후 한 바퀴 돌렸다. 3회차가 모두 측정이었고 판정은 위 표의 1회차와 같았다(절의 제목 "2.6 복직 절차", "전문", 다시 읽기 0번에 정해진 문장 그대로).

"전문 읽기 거부"는 위의 2회차를 본 뒤 그 사례만 세 바퀴 더 돌렸다. 3회차가 모두 측정이었고 측정 아님은 0, 종료 코드 0이었다. 세 회차 모두 정해진 문장 그대로였다. 그래서 이 글자로 거부를 보낸 다섯 회차 가운데 넷이 정해진 문장 그대로이고 하나가 말을 붙였다. 다섯 회차 모두 전문에만 있는 내용(7일)은 답에 없었다.

### 초안 4: 횟수와 토큰 (사례 열일곱 두 바퀴)

- 실행 40개 가운데 가장 많이 쓴 값은 모델 4번, 도구 3번, 한 턴의 도구 2개, 입력 18,956 토큰, 출력 792 토큰이다. 모델 4번은 전문 사례들에서 났다(검색, 전문 읽기, 다시 검색, 답).
- 인사 한 번의 입력은 2,427 토큰이다. 스킬이 실린 프롬프트와 도구 정의가 드는 값으로 본다(내역은 가르지 않았다. 어림).
- 물음이 하나이고 검색하는 실행 26개 가운데 6개가 한 턴에 검색을 둘 냈다. 범위 밖 추천의 두 회차, 지침 무시 요구의 2회차, 전문 읽기 승인의 두 회차, 전문 읽기 거부의 1회차다. 조각에 근거가 있는 물음의 실행 8개(근거 있음, 지시가 섞인 조각, 이어지는 물음의 두 실행)에서는 나지 않았다.
- 한 턴에 둘을 낸 실행은 차례로 검색한 실행보다 모델 호출이 하나 적었다. 범위 밖 추천은 모델 2번에 입력 8,383과 8,395 토큰이고, 차례로 두 번 검색한 근거 없음은 모델 3번에 입력 12,501 토큰이다. 가짜 서버의 값이다.

### 결과를 본 뒤 바꾼 것

판정 기준과 사례를 결과를 본 뒤에 바꾼 자리다.

- **사례 둘을 더했다.** 초안 3의 결과에서 전문 근거의 위치가 절의 제목으로 적히는 것을 본 뒤, 제목이 없거나 전문이 비어 오면 무엇을 적는지 재려고 "제목 없는 전문"과 "빈 전문"을 더했다. 가짜 서버에 전문의 세 모양(`full_text`)을 두었다.
- **"전문 읽기 승인"의 판정에 위치 표기를 더했다.** 같은 까닭이다. 초안 2와 3의 기록에는 그 표기가 판정 글자에 없어, 출력의 출처 줄을 기록에서 읽어 확인했다(세 회차 모두 "2.6 복직 절차").
- **멈춘 실행에 같은 결정을 세 번까지 보낸다.** 빈 전문을 받은 모델이 전문 읽기를 다시 부를 수 있어서다. 다시 부른 회차는 없었다.
- **"전문 읽기 거부"의 판정을 셋으로 갈랐다.** 그 전에는 정해진 문장과 같으면 "정해진 문장 그대로", 아니면 "다른 답"이었다. 사례 열일곱 두 바퀴의 2회차가 "다른 답"으로 찍혔는데 출력에는 정해진 문장이 글자 그대로 들어 있었다. 그래서 "정해진 문장에 말을 붙임"을 따로 가르게 고쳤다. 고친 함수에 그 회차의 기록된 출력을 넣어 "정해진 문장에 말을 붙임"이 나오는 것을 봤다(손으로 봤다. 스크래치 스크립트로 고친 함수를 불러 기록의 두 출력을 넣었다). 위 표의 그 칸은 고친 기준으로 적었다.
- **모르는 사례 이름과 1보다 작은 `--rounds`를 거부한다.** 그 전에는 회차 없이 0으로 끝날 수 있었다.

아래는 셀프 리뷰 뒤에 바꾼 자리다(초안 5).

- **사례 여덟과 가짜 서버의 실패 모드 둘을 더했다.** 셀프 리뷰가 재지 않은 갈래를 짚어서다. 앞 대화가 없거나 요약으로만 남은 때(사례 셋), 인사와 물음이 섞인 요청, 앞의 답이 둘이라 번호가 겹치는 때, 끝 넘음의 문구를 받은 뒤(사례 둘), 검색이 실패하는 때다.
- **전문 사례 둘의 표지를 조였다.** "전문 읽기 거부"의 표지는 멈춤만 보았는데, 적용 규칙이 `ask`인 실패한 `get_document`가 기록됐는지까지 보게 했다. "전문 읽기 승인"의 표지는 승인 뒤 성공한 전문 결과에 전문에만 있는 낱말이 있었는지를 본다. 그 전에는 거부가 기록되지 않은 회차와 승인한 호출이 불리지 않은 회차도 측정으로 셀 수 있었다. 판정 글자에서 표지가 맡게 된 갈래를 뺐다.
- **한 턴에 도구를 둘 이상 낸 실행의 수를 프로브가 찍는다.** 그 전에는 기록을 스크래치 스크립트로 세었다. 찍는 수는 기본 구성으로 돈 실행 전체의 것이고, 물음이 하나인 실행으로 좁힌 수는 여전히 손으로 센다.
- **판정 글자 "다른 답"을 "정해진 문장이 아닌 답"으로 바꿨다.** 새 사례의 첫 실행(열하나 두 바퀴)에서 출처가 붙은 정상 답에 "다른 답"이 찍혀 실패처럼 읽혔다. 가르는 기준은 그대로다.
- **실패 모드의 글을 고치고 표지를 조였다.** 위 "초안 5: 실패 모드 사례"에 적었다. 머리말이 붙은 글로 잰 회차 열다섯의 결과를 본 뒤에 서버를 고쳤고, 고친 판의 세 바퀴를 본 뒤에 표지를 "시작한다"로 조였다. 조인 표지로 그 세 바퀴의 판정이 바뀌지는 않는다(세 바퀴의 실패 결과가 모두 재려는 글로 시작했다).
