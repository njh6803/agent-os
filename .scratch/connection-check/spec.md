# connection-check 명세: 플러그인 화면이 켜 둔 MCP 서버와 모델에 붙는지를 행마다 보이고, 배포 안내에 문제 해결 절을 둔다

Status: ready-for-agent

슬라이스 9(`connection-check`). 설계는 설계 인터뷰(일지 2026-11-20-1928)와 ADR 0067이 정했고, 이 명세는 그 결정이 명세에 넘긴 자리를 채운다. `/to-spec`으로 새 세션에서 썼고 설계 인터뷰를 다시 열지 않았다. 이 세션의 일지는 `docs/journal/2026-11-21-0502-connection-check-spec.md`이고, 사람에게 물은 화면 하나(질문 넷)와 답이 거기 글자 그대로 있다. 용어는 `CONTEXT.md`의 접속 확인, 운영자, 모델 서버, 단독 배포, 배포 파일 묶음, 제품 판을 따른다. 이 명세에서 "스스로 하는 확인"은 플러그인 화면이 열려 있는 동안 화면이 정해진 간격으로 부르는 확인이고, "눌러서 하는 확인"은 운영자가 행의 '접속 확인' 버튼을 누를 때만 하는 확인이다. "읽었다"는 따로 적지 않으면 명세를 쓰기 시작할 때의 기준 커밋 `a5e0a68c7`(그때의 origin/dev)의 코드와 문서를 읽은 것이다. 명세를 쓰는 동안 기준 브랜치가 `17fe2b169`로 앞섰고(PR 615, postgres-foundation의 티켓 03. `serve`는 표의 판이 맞는 데이터베이스에 닿아야 뜬다), 이 브랜치의 기준은 지금 그 커밋이다. 셀프 리뷰를 반영하며 더한 "읽었다"는 그 커밋에서 읽었다. 그 커밋이 고친 파일 가운데 이 명세가 드는 것은 그 커밋에서 다시 대 봤다. `.claude/rules/http.md`의 절 이름 셋이 그대로이고, `src/agent_os`에서 로거를 만지는 코드가 여전히 MCP 어댑터의 필터 하나뿐이며, 실제 `serve`를 띄우는 시험과 관리 화면 e2e가 이제 테스트 데이터베이스를 받아 뜬다(읽었다). 측정은 `.scratch/connection-check/probes/`이고, 프로브마다 재는 것과 다시 돌리는 명령과 잰 판은 그 `README.md`의 표에 있다. 측정은 모두 이 PC(Windows 10)에서 2026-11-21에 돌았다.

**넘겨받은 것은 아래 표의 열여덟 행이다.** ADR 0067의 결정과 Consequences가 "명세가 정한다"로 넘긴 것을 물음 하나씩 나눈 열셋, 기능 계획 본문이 앞선 기능의 명세에서 받아 넘긴 넷, 기능 계획의 수락 조건 하나다. 같은 물음을 다른 곳(기능 계획의 "명세가 먼저 볼 것", PR 직전 리뷰가 넘긴 넷)이 다시 든 것은 그 행에 괄호로 붙였다. 답한 자리의 따옴표는 이 명세의 절 이름이다.

**사용자가 고른 것은 넷이다.** 넷 모두 추천안이고 거절은 없다. 질문과 선택지의 원문은 위 일지에 있다.

1. 시험 방식은 여섯 가지 그대로다(Testing Decisions).
2. 모델은 제공사마다 다른 요청으로 확인한다. `anthropic`은 그 모델 하나를 묻고, `openai-compatible`은 목록을 받아 이름을 찾는다("모델을 확인하는 법").
3. 스스로 하는 확인은 30초마다 하고, 보이지 않는 탭에서는 멈추며 돌아오면 바로 한 번 확인한다("간격과 보이지 않는 탭").
4. 모델이 붙지 못했을 때는 `serve`가 가른 까닭과 응답 상태 번호만 보이고, 서버가 적어 보낸 글은 싣지 않는다("화면에 보이는 글과 비밀").

**셀프 리뷰 뒤에 사용자가 고른 것은 셋이다.** 셋 모두 추천안이고 거절은 없다. 질문과 선택지의 원문은 같은 일지의 "이력 승인과 함께 물은 화면" 절에 있다.

5. ADR 0067의 2026-11-21 이력과 포인터 셋을 승인했다.
6. `anthropic` 패키지의 판은 1.x 안에서 열어 둔다(`>=1.7,<2`. "모델을 확인하는 법"의 의존성).
7. 빌린 모델 서버가 목록 요청에 어떻게 답하는지는, 모델 쪽 확인을 구현하는 티켓이 로컬 모델 시험에 확인 한 번을 더해 잰다(Testing Decisions의 일곱째). 그래서 시험 방식은 일곱이 됐다.

**이력은 하나다.** 2는 ADR 0067 결정 "모델을 확인하는 법"의 문장(모델마다 목록을 묻는다)과 어긋나므로 그 ADR에 2026-11-21 이력 "모델은 제공사마다 다른 요청으로 확인하고, anthropic 패키지를 직접 의존으로 선언한다"를 더했고, 사용자가 승인했다(위 5). 나머지는 명세가 정했고 Implementation Decisions의 열두 절이다.

## Problem Statement

운영자가 단독 배포를 띄웠는데 에이전트가 답하지 않는다. 까닭은 여럿일 수 있다. 모델 서버가 꺼졌을 수도 있고, 원격 MCP 서버가 꺼졌을 수도 있고, 키나 토큰이 틀렸을 수도 있다. 지금 운영자가 이것을 가르는 길은 실행을 한 번 일으켜 실패하게 한 뒤, 관리 화면의 실행 상세에서 실패 글을 읽는 것뿐이다. 그 길은 실행을 일으킬 수 있는 사람이 있어야 열리고, 최종 사용자가 먼저 실패를 겪은 뒤에야 드러나는 때가 많다. 플러그인 화면은 플러그인이 켜져 있는지만 보여 주고, 켜 둔 플러그인이 가리키는 바깥 서버에 실제로 붙는지는 보여 주지 않는다.

`serve`가 아예 뜨지 않으면 관리 화면도 볼 수 없다. 그때 서버에서 무엇을 치고 무엇을 읽어야 하는지는 배포 안내의 4절과 12절에 흩어져 있고, `serve`와 `migrate`가 멈출 때 찍는 글의 뜻을 한 자리에서 찾을 수 없다. 지금 떠 있는 판이 무엇인지 읽는 법도 적혀 있지 않다. 그리고 도움을 청하려고 출력을 남에게 붙여 넣을 때 어느 명령의 출력에 비밀번호와 키가 그대로 찍히는지도 운영자는 알지 못한다.

## Solution

두 가지를 만든다.

첫째, 관리 화면의 플러그인 화면(첫 페이지의 플러그인 목록)에서 MCP 구역과 모델 구역의 행마다 접속 확인의 결과를 보인다. 켜 둔 원격 MCP 서버와 켜 둔 모델의 행은 화면을 열면 바로 `확인하는 중`이 되었다가 `붙음`이나 `붙지 못함`으로 바뀌고, 붙지 못했으면 그 까닭이 글로 함께 보인다. 화면을 열어 둔 동안 30초마다 다시 확인하므로, 서버가 꺼지면 30초쯤 뒤에 그 행이 `붙지 못함`으로 바뀐다. 전송이 stdio인 MCP 서버의 행에는 '접속 확인' 버튼이 있고, 운영자가 누를 때만 `serve`가 그 서버의 프로세스를 한 번 띄워 확인한 뒤 끈다. 꺼 둔 플러그인의 행은 결과를 보이지 않고 버튼도 누를 수 없다. 확인은 화면이 아니라 `serve`가 하고, 결과는 화면에만 있다.

둘째, 배포 안내(`deploy/standalone/README.md`)의 맨 뒤에 '문제 해결' 절을 새로 둔다. `serve`가 뜨지 않아 화면을 볼 수 없을 때 서버에서 칠 명령, `serve`와 `migrate`가 멈출 때 찍는 글의 뜻, 지금 떠 있는 판을 읽는 법, 남에게 보여도 되는 출력과 안 되는 출력을 적는다. `serve`는 떴는데 에이전트가 답하지 않을 때는 플러그인 화면의 접속 확인을 보라고 가리킨다.

## User Stories

1. 운영자로서, 플러그인 화면을 열면 켜 둔 원격 MCP 서버마다 붙는지를 그 행에서 바로 보고 싶다. 실행을 일으키지 않고도 서버가 살아 있는지 알기 위해서다.
2. 운영자로서, 켜 둔 모델마다 붙는지를 그 행에서 바로 보고 싶다. 모델 서버가 꺼졌는지를 최종 사용자가 실패를 겪기 전에 알기 위해서다.
3. 운영자로서, 붙지 못한 행에서 까닭을 글로 읽고 싶다. 서버가 꺼졌는지, 키가 틀렸는지, 모델 이름이 틀렸는지를 가르기 위해서다.
4. 운영자로서, 원격 MCP 서버의 토큰이 틀렸을 때 글 끝의 `(HTTP 401 Unauthorized)`를 보고 싶다. 꺼진 서버와 토큰 불일치를 구별하기 위해서다.
5. 운영자로서, 모델의 키가 틀렸을 때 `키를 받아들이지 않았다(HTTP 401)`를 보고 싶다. 꺼진 모델 서버와 키 문제를 구별하기 위해서다.
6. 운영자로서, 모델 파일에 적은 `model_id`가 틀렸을 때 그 이름의 모델이 없다는 글을 보고 싶다. 오타를 실행 전에 잡기 위해서다.
7. 운영자로서, 모델 파일에 제공사의 모델 조회가 아는 날짜를 뗀 짧은 이름(`claude-opus-4-5` 같은)을 적어도 붙음으로 보고 싶다. 제공사가 아는 이름을 목록에 없다는 까닭만으로 없는 모델로 잘못 보지 않기 위해서다.
8. 운영자로서, 화면을 열어 둔 동안 결과가 30초마다 스스로 새로워지기를 바란다. 서버가 꺼진 것을 새로 고치지 않고도 알기 위해서다.
9. 운영자로서, 다른 탭을 보는 동안에는 확인이 멈추기를 바란다. 보지 않는 화면이 바깥 서버에 요청을 계속 보내지 않게 하기 위해서다.
10. 운영자로서, 탭으로 돌아오면 바로 한 번 확인되기를 바란다. 떠나 있던 사이의 옛 결과를 믿지 않기 위해서다.
11. 운영자로서, 다시 확인하는 동안 앞선 결과가 깜빡이며 사라지지 않기를 바란다. 30초마다 행이 흔들리면 읽기 어렵기 때문이다.
12. 운영자로서, 확인 요청 자체가 실패하면(`serve`에 닿지 못했거나 `serve`가 오류로 답했으면) 앞선 `붙음`이 남지 않고 `확인하지 못함`을 보고 싶다. 옛 결과를 지금의 것으로 믿지 않기 위해서다.
13. 운영자로서, 느린 서버 하나 때문에 다른 행의 결과가 늦어지지 않기를 바란다. 행마다 따로 결과를 받기 위해서다.
14. 운영자로서, 답이 없는 서버의 확인이 정해진 시간 뒤에 `붙지 못함`으로 끝나기를 바란다. `확인하는 중`이 끝없이 남지 않게 하기 위해서다.
15. 운영자로서, stdio MCP 서버의 행에서 '접속 확인' 버튼을 눌러 그 서버가 뜨고 도구 목록을 내는지 확인하고 싶다. 명령이 틀렸거나 실행 파일이 없는 것을 실행 전에 알기 위해서다.
16. 운영자로서, stdio MCP 서버는 내가 누를 때만 띄워지기를 바란다. 화면을 열어 둔 것만으로 서버에서 프로세스가 되풀이해 뜨지 않게 하기 위해서다.
17. 운영자로서, 버튼을 누른 뒤 응답이 올 때까지 그 버튼이 눌리지 않기를 바란다. 같은 서버를 겹쳐 띄우지 않기 위해서다.
18. 운영자로서, stdio 확인의 결과 옆에 확인한 시각을 보고 싶다. 스스로 새로워지지 않는 결과가 언제 것인지 알기 위해서다.
19. 운영자로서, 확인이 끝난 stdio 서버의 프로세스가 서버에 남지 않기를 바란다. 확인할 때마다 프로세스가 쌓이지 않게 하기 위해서다.
20. 운영자로서, 꺼 둔 플러그인의 행에는 결과가 보이지 않고 버튼도 눌리지 않기를 바란다. 꺼 둔 것은 확인하지 않는다는 것을 화면에서 알기 위해서다.
21. 운영자로서, 플러그인을 켜면 그 행의 확인이 바로 시작되고 끄면 결과가 사라지기를 바란다. 스위치와 결과가 어긋나지 않게 하기 위해서다.
22. 운영자로서, 매니페스트를 읽지 못한 행(이유를 글자로 보이는 표지 행)에는 접속 확인이 없기를 바란다. 무엇에 붙어야 할지 알 수 없는 것을 확인한다고 보이지 않기 위해서다.
23. 운영자로서, 에이전트와 스킬의 행에는 접속 확인이 없기를 바란다. 바깥 서버를 가리키지 않는 플러그인에 뜻 없는 표시가 붙지 않게 하기 위해서다.
24. 운영자로서, 붙지 못한 까닭의 글에 키나 토큰이 실리지 않기를 바란다. 화면을 남에게 보이거나 화면 사진을 찍어도 비밀이 새지 않게 하기 위해서다.
25. 운영자로서, 모델 쪽 실패 글에는 서버가 적어 보낸 글이 실리지 않기를 바란다. 서버가 받은 키를 오류 글에 되울려도 화면에 닿지 않게 하기 위해서다.
26. 운영자로서, 접속 확인이 토큰을 쓰지 않기를 바란다. 화면을 열어 둔 시간만큼 모델 사용료가 늘지 않게 하기 위해서다.
27. 운영자로서, 접속 확인의 결과가 서버 로그와 트레이스와 데이터베이스에 쌓이지 않기를 바란다. 30초마다 생기는 줄이 진짜 기록을 가리지 않게 하기 위해서다.
28. 운영자로서, `붙음`이 무엇까지 뜻하는지 배포 안내에서 읽고 싶다. 붙음인데도 실행이 실패할 수 있는 경우(사용 한도, 권한)를 알기 위해서다.
29. 관리 토큰만 가진 운영자로서, 채널 토큰 없이도 접속 확인을 쓰고 싶다. 실행을 일으킬 권한이 없어도 배포가 살아 있는지 보기 위해서다.
30. 운영자로서, `serve`가 뜨지 않을 때 서버에서 칠 명령을 배포 안내의 한 절에서 찾고 싶다. 화면을 볼 수 없을 때 어디서부터 볼지 알기 위해서다.
31. 운영자로서, `serve`와 `migrate`가 멈추며 찍는 글마다 뜻과 할 일을 그 절에서 읽고 싶다. 글을 보고 바로 고칠 것을 알기 위해서다.
32. 운영자로서, `serve`의 기록에 보이는 `ERROR:` 접두와 `Application startup failed. Exiting.` 줄이 무엇인지 알고 싶다. 그 줄을 까닭으로 잘못 읽지 않기 위해서다.
33. 운영자로서, `migrate`가 `Exited (0)`으로 남은 것이 고장이 아니라는 것을 문제 해결 절에서도 확인하고 싶다. 멀쩡한 것을 고치려 들지 않기 위해서다.
34. 운영자로서, 위젯이 종료 1로 끝났을 때와 관리 화면이 `Ready` 줄 뒤에 실패했을 때의 뜻을 읽고 싶다. 사이트 파일 문제와 서버 연결 문제를 가르기 위해서다.
35. 운영자로서, 지금 떠 있는 판을 읽는 명령을 알고 싶다. `.env`를 고친 뒤 다시 띄우지 않았을 때 `.env`의 값과 떠 있는 판이 다를 수 있기 때문이다.
36. 운영자로서, 어느 명령의 출력을 남에게 보내면 안 되는지 알고 싶다. 도움을 청하다가 데이터베이스 비밀번호와 키를 흘리지 않기 위해서다.
37. 운영자로서, `serve`는 떴는데 에이전트가 답하지 않을 때 무엇을 볼지 문제 해결 절에서 안내받고 싶다. 플러그인 화면의 접속 확인으로 이어 가기 위해서다.
38. 이 저장소에서 일하는 개발자로서, 접속 확인의 두 길이 타입으로 갈려 있기를 바란다. 스스로 하는 확인의 길에 stdio 서버를 띄우는 코드가 실수로 섞이지 않게 하기 위해서다.
39. 이 저장소에서 일하는 개발자로서, 접속 확인의 응답이 계약(`openapi.json`)에 닫힌 값으로 실리기를 바란다. 화면 코드가 상태 넷을 빠짐없이 다루는지 컴파일러가 잡게 하기 위해서다.
40. 이 저장소에서 일하는 개발자로서, 접속 확인이 실행과 같은 주소와 같은 키로 묻기를 바란다. 확인은 붙음인데 실행은 다른 서버에 붙어 실패하는 일이 없게 하기 위해서다.

## Implementation Decisions

### 경로와 응답

요청 하나가 플러그인 하나를 확인한다. 느린 서버 하나가 다른 행의 결과를 막지 않게 하려는 것이고(ADR 0067 결정 "확인은 `serve`가 한다"의 첫 조건), 화면은 행마다 요청을 따로 보낸다. 오퍼레이션(계약에 이름이 실리는 호출 하나. 메서드와 경로의 짝이다)은 둘이고 경로는 같다.

| 오퍼레이션 | 메서드와 경로 | `operationId` | 부르는 때 | 실제로 확인하는 플러그인 |
|---|---|---|---|---|
| 스스로 하는 확인 | `GET /plugins/{kind}/{name}/connection-check` | `check_connection` | 화면이 열려 있는 동안 30초마다 | 켜 둔 원격 MCP 서버, 켜 둔 모델 |
| 눌러서 하는 확인 | `POST /plugins/{kind}/{name}/connection-check` | `check_connection_by_launching` | 운영자가 '접속 확인' 버튼을 누를 때 | 켜 둔 stdio MCP 서버 |

- **메서드.** 스스로 하는 확인은 `GET`이다. `serve`의 상태를 바꾸지 않고 프로세스를 띄우지 않으며, 화면의 읽기 훅이 다른 읽기와 같은 길로 부른다. 다만 바깥 서버에 요청이 나가므로 결과가 다시 쓰이지 않게 두 응답 모두 `Cache-Control: no-store`를 싣는다. 눌러서 하는 확인은 프로세스를 띄우므로 `POST`이고 본문이 없다(ADR 0067 결정 "확인은 `serve`가 한다"의 셋째 조건).
- **경로 파라미터.** `kind`는 `mcp`와 `model` 둘만 받는 닫힌 값이고 계약에 새 열거(받는 값을 몇 개로 못박은 타입) 하나로 실린다. `agent`와 `skill`은 형식 오류(422, `violations`의 `field`는 `path.kind`)다. 에이전트와 스킬에는 접속 확인이 없다는 것(ADR 0067 결정 "자리")이 생성 클라이언트의 타입에서도 드러난다. `name`은 다른 플러그인 경로와 같은 규칙으로 받는다(`.claude/rules/http.md`의 "파일 경로로 조립되는 경로 파라미터").
- **응답.** 두 오퍼레이션의 성공 응답(200)은 같은 모양이고, 칸 `status`의 값으로 가르는 닫힌 넷이다. 계약에는 `status`를 판별자(어느 모양인지 알려 주는 칸)로 하는 유니온(여러 모양 가운데 하나인 타입)으로 실어, 생성 클라이언트에서 `reason`이 `unreached`일 때만 있는 값으로 좁혀지게 한다.

| `status` | 뜻 | 더 드는 칸 |
|---|---|---|
| `reached` | 붙었다 | 없음 |
| `unreached` | 붙어 보았지만 붙지 못했다 | `reason`: 붙지 못한 까닭의 글(비지 않은 문자열) |
| `disabled` | 꺼 둔 플러그인이라 확인하지 않았다 | 없음 |
| `not_applicable` | 이 오퍼레이션이 확인하는 플러그인이 아니라 확인하지 않았다 | 없음 |

- **`not_applicable`인 경우.** 스스로 하는 확인에서는 stdio MCP 서버이고, 눌러서 하는 확인에서는 원격 MCP 서버와 모델이다. 화면은 목록이 준 매니페스트로 어느 행에 어느 오퍼레이션을 부를지 이미 알기 때문에 이 값은 화면이 보통 받지 않는다. 화면을 거치지 않고 경로를 직접 부르는 요청에도 `serve`가 두 길을 지키게 하는 값이다.
- **붙지 못한 확인은 오류 응답이 아니다.** 붙지 못함도 꺼짐도 200이다(ADR 0067 결정 "붙지 못한 확인은 오류 응답이 아니다"). 오류 응답은 다른 관리 경로와 같은 것만 낸다. 토큰이 없거나 틀리면 401, 형식 오류는 422, 없는 플러그인은 404, 깨진 매니페스트와 깨진 운영자 파일과 모델 파일의 구성 오류는 500이다. 409와 429는 내지 않고 에러 코드의 어휘 여섯은 그대로다.
- **인증.** 두 오퍼레이션은 관리의 면이고 미들웨어(모든 요청이 라우트보다 먼저 지나는 층)의 기본값(관리 토큰) 뒤에 선다. 라우트에 따로 거는 것은 없다(ADR 0011, `.claude/rules/http.md`).
- **선언의 차례.** 새 `GET`은 관리 라우터에서 단건 조회(`GET /plugins/{kind}/{name}`)보다 먼저 선언한다. 단건 조회의 이름 변환기는 슬래시까지 잡는다(읽었다, `src/agent_os/admin/http.py`의 켜고 끄기 라우트 위 주석이 `GET …/calc/enabled`가 단건 조회에 이름 `calc/enabled`로 맞은 뒤 패턴이 422로 거른다고 적는다). 그래서 새 `GET`을 뒤에 선언하면 `GET /plugins/mcp/calc/connection-check`가 단건 조회에 이름 `calc/connection-check`로 맞아 422가 될 것으로 본다(어림. 돌려 보지 않았다). Testing Decisions의 첫째 시험이 이 차례를 고정한다. `POST`는 지금 플러그인 경로에 같은 메서드의 라우트가 없어 차례를 타지 않는다(읽었다, 같은 파일. 플러그인 경로의 라우트는 `GET` 둘과 `PUT` 하나다).
- **계약에 박히는 것.** 응답 모델의 독스트링은 한 줄이고, 라우트는 `operation_id`와 자기가 내는 에러의 문서를 적는다(`.claude/rules/http.md`의 "계약에 박히는 것 둘을 손으로 준다"). `openapi.json`과 생성한 TS 타입이 같은 커밋에 실린다.

### 판정의 차례

두 오퍼레이션 모두 아래 차례로 판정하고, 앞에서 정해지면 뒤는 하지 않는다.

1. 형식 오류면 422다.
2. 그 종류와 이름의 플러그인이 없으면 404다.
3. 매니페스트를 읽지 못하면 500이고, 켜짐을 적은 운영자 파일이 깨졌으면 500이다. 여기까지는 `.claude/rules/admin.md`의 판정 순서 그대로다.
4. 꺼 둔 플러그인이면 `disabled`다. 화면이 보낸 값이 아니라 `serve`가 읽은 켜짐으로 판정한다(ADR 0067 결정 "꺼 둔 플러그인").
5. 이 오퍼레이션이 확인하는 플러그인이 아니면 `not_applicable`이다.
6. 확인하고 `reached`나 `unreached`를 돌려준다.

4와 5에서 끝난 요청은 확인하는 포트를 한 번도 부르지 않는다. 그래서 `GET`은 어떤 입력으로도 프로세스를 띄우지 않는다.

### MCP 서버를 확인하는 법

방법은 ADR 0067 결정 "MCP 서버를 확인하는 법"이 정했다. 실행이 서버 하나를 여는 것과 같은 단계(접속, 세션 열기, 초기화, 도구 목록 읽기)를 지난 뒤 닫고, 어댑터가 실행에서 쓰는 서버 하나를 여는 함수를 그대로 다시 쓴다. 명세가 더 정하는 것은 다음이다.

- **붙었다.** 도구 목록을 읽을 때까지 예외 없이 지났으면 붙은 것이다. 도구가 하나도 없어도 붙은 것이다.
- **붙지 못했다.** 여는 동안의 실패는 실행의 실패 글을 그대로 까닭으로 돌려준다. 글은 `MCP 서버 <이름>(<명령이나 주소>)에 붙지 못했다: <원인>`이고, 서버가 오류 응답을 돌려줬으면 끝에 ` (HTTP <코드> <이유>)`가 붙는다. 서버가 되울린 헤더 값을 가리는 것도 실행과 같다(ADR 0049 이력 2026-11-09 "서버가 되울린 헤더 값을 실패 문구에서 가린다"). 그래서 꺼진 원격 서버는 연결 오류의 글로, 토큰 불일치는 글 끝의 `(HTTP 401 Unauthorized)`로 갈린다.
- **기한을 넘겼다.** 까닭은 `MCP 서버 <이름>(<명령이나 주소>)에 붙지 못했다: <N>초 안에 준비되지 않았다`다. 앞머리를 실행의 글과 같게 두어 어느 서버인지가 같은 자리에 보이게 한다.
- **여는 단계 밖의 예외.** 닫는 동안 난 예외처럼 여는 단계 밖에서 난 것은 접속 확인이 바꾸지 않고 그대로 올려 500이 된다. 실행에서 같은 예외가 드러나는 것과 다르게 꾸미지 않으려는 것이다.
- **stdio 서버.** 실행과 같은 길로 띄우고(윈도우가 아닌 OS에서는 런처 뒤에, ADR 0034), 확인이 끝나면 닫아 프로세스를 끈다. 명령을 찾지 못한 것도 여는 단계 안의 실패라 같은 글이 된다. 요청 하나가 서버 하나만 띄운다.
- **닫기.** 원격 서버는 ADR 0049의 닫는 길(세션 종료 요청을 2초 유예 안에서 보낸다)을, stdio 서버는 ADR 0034의 정리 길을 지난다. 기한에 닿아 끊긴 확인도 같은 길로 거둔다.

접속 확인은 서버 하나만 열기 때문에, 서버 여럿이 같은 이름의 도구를 낼 때 실행이 실패하는 것은 보지 못한다(ADR 0067 Consequences "접속 확인이 보지 못하는 것").

### 모델을 확인하는 법

사용자가 고른 대로 제공사마다 다른 요청으로 확인한다. 두 요청 모두 답변을 만들지 않는 `GET`이고 토큰을 쓰지 않는다.

| 제공사 | 보내는 요청 | 붙었다고 보는 때 |
|---|---|---|
| `anthropic` | 그 모델 하나를 묻는 요청 `GET /v1/models/<model_id>` 한 건 | 응답이 200이다 |
| `openai-compatible` | 목록을 묻는 요청 `GET <base_url>/models` 한 건 | 응답이 200이고 목록에 `model_id`와 글자가 같은 `id`가 있다 |

- **목록으로 확인하지 않는 까닭(`anthropic`).** 실제 Anthropic에서 목록은 15개였고 날짜를 뗀 이름 `claude-opus-4-5`는 거기 없었는데, 그 이름 하나를 묻는 요청은 200이었고 `claude-opus-4-5-20251101`이 돌아왔다(쟀다, `.scratch/connection-check/probes/model_requests_live.py`). 목록에 그 글자가 있는지로 가르면 날짜를 뗀 이름을 적은 모델 파일을 없는 모델로 잘못 가른다. 하나를 묻는 요청은 모델 파일의 id `claude-opus-5`에 200, 없는 id에 404, 지어낸 키에 401로 갈렸다(같은 프로브). 돌아온 id가 물은 id와 달라도 200이면 붙은 것이다. 모델을 부르는 요청이 날짜를 뗀 이름을 받는지는 재지 않았다. 공식 문서의 모델 쪽은 표 아래 각주에서, 4.6 세대 앞의 모델은 별칭이 날짜 붙은 id를 가리키는 이름이라고 적는다(웹 요약, `https://platform.claude.com/docs/en/about-claude/models/overview`).
- **하나를 묻지 않는 까닭(`openai-compatible`).** 빌린 모델 서버가 목록 요청에 답해 준비 확인을 지났다는 기록은 있지만(읽었다, 일지 `docs/journal/2026-11-13-1423-llm-local-command-rents-model-servers.md`), id 하나를 묻는 요청을 그런 서버가 받는지는 본 적이 없다. 그래서 답한다고 알려진 목록 요청을 쓴다. 로컬 모델 시험의 준비 확인도 같은 요청을 쓴다. 빌린 서버마다 `GET <주소>/models`가 200으로 낸 이름들에 그 모델 이름이 있어야 준비된 것으로 본다(읽었다, `tools/llm_local.py`의 `fetch_models`와 `servers_ready`). 띄운 모델 서버로는 이번에 재지 않았고, 모델 쪽 확인을 구현하는 티켓이 로컬 모델 시험에서 잰다(Testing Decisions의 일곱째. 사용자가 골랐다).
- **요금.** 하나를 묻는 응답의 본문에 쓴 양을 적는 칸(`usage`)이 없었고, 응답 헤더에 속도 제한을 적는 이름도 없었다(쟀다, `.scratch/connection-check/probes/model_requests_live.py`). 공식 문서의 Models API 쪽과 가격 쪽에서 이 요청에 요금을 매기는 문장은 찾지 못했다(웹 요약이다. 받은 쪽과 받은 길은 프로브 `README.md`의 "쓴 양과 요금"에 있고, 그 가운데 목록 쪽은 `https://platform.claude.com/docs/en/api/models/list`다. 붙지 않는다고 적은 문서도 없어 요금이 없다는 것은 어림이다). 30초마다 묻는 것이 어떤 한도에 걸리는지는 재지 않았다.
- **요청의 수.** `anthropic`의 하나를 묻는 요청과 `openai`의 목록 요청은 각각 요청 한 건이었고, `openai`의 목록은 서버가 다음 쪽이 있다고 답해도 한 건으로 끝났다(쟀다, `.scratch/connection-check/probes/model_requests_loopback.py`). 그래서 `openai-compatible`의 확인은 첫 쪽만 본다. 모델 서버의 목록은 보통 짧다고 보지만(어림) 첫 쪽에 실리지 않은 모델은 없는 모델로 보인다.
- **재시도하지 않는다.** 확인은 요청을 한 번만 보낸다. `anthropic` 라이브러리의 기본 설정은 500에 요청을 세 건 보냈고, 재시도를 끄면 한 건이었다(쟀다, `.scratch/connection-check/probes/model_requests_loopback.py`). 재시도를 두면 꺼진 서버의 확인이 기한을 채우고 바깥 서버가 받는 요청이 는다.
- **실행과 같은 주소와 같은 키.** 접속 확인은 실행이 그 모델을 부를 때 쓰는 주소와 키로 묻는다. `anthropic`은 실행과 같은 인자로 만든 모델 객체가 정한 주소와 키를 그대로 받아 쓰고, 접속 확인이 환경 변수를 따로 읽어 같은 규칙을 다시 짓지 않는다. 환경에 주소 변수를 심고 실행과 같은 인자로 만든 모델의 호출과, 그 모델의 공개 칸으로 만든 클라이언트의 확인 요청이 같은 서버에 같은 키로 닿았고, 같은 환경에서 인자 없이 만든 클라이언트의 주소는 `https://api.anthropic.com`이었다(쟀다, `.scratch/connection-check/probes/model_requests_loopback.py`). 곧 확인하는 클라이언트를 환경에만 맡기면 주소를 바꾼 배포에서 확인과 실행이 다른 서버에 묻는다. `openai-compatible`은 모델 파일의 `base_url`로 묻고, 키는 실행이 호출마다 키를 읽는 규칙 그대로 읽는다(읽었다, `src/agent_os/adapters/openai_compatible.py`의 `_KeySource`). 모델 파일에 `api_key_env` 칸이 없으면 실행처럼 자리 채움 글자(`no-key`)를 보낸다. 칸이 있는데 그 환경 변수가 없거나 비었으면, 또는 값에 인증 헤더로 보낼 수 없는 글자가 있으면 실행은 요청을 보내기 전에 실패한다(같은 코드). 접속 확인도 그때는 요청을 보내지 않고 `unreached`로 가른다(아래 "화면에 보이는 글과 비밀"의 키 없음과 키 모양 갈래). 환경이 행선지와 키를 바꾸지 못하게 주소와 키를 인자로 준다는 것은 실행 쪽과 같은 규칙이다(`.claude/rules/adapters.md`의 모델 소스 항목). 실행은 환경의 `OPENAI_API_KEY`를 요청에 싣지 않고 환경의 `OPENAI_PROXY`를 따르지 않으므로(읽었다, 같은 모듈의 독스트링 "요청"), 확인의 요청도 그 둘을 따르지 않는다. `openai-compatible` 쪽이 실행과 같은 서버에 같은 키로 닿는지는 재지 않았고 구현 티켓이 가짜 모델 서버로 고정한다.
- **키가 없는 `anthropic` 모델.** 실행과 같은 인자로 만든 모델의 키 칸이 비었으면 요청을 보내지 않고 `unreached`로 가른다. 실행도 키 없이는 첫 호출에서 실패한다(읽었다, `.claude/rules/adapters.md`). 키가 없을 때 그 칸의 값이 무엇인지는 재지 않았고 구현 티켓이 시험으로 고정한다.
- **구성 오류.** 모델 종류가 아닌 매니페스트와 공백뿐인 `model_id`는 실행에서와 같은 구성 오류이고 500이다. 붙어 보기 전에 걸러지는 것이라 `unreached`가 아니다.
- **`붙음`이 뜻하는 것.** 제공사나 모델 서버가 답했고, 키를 받아들였고, 그 이름의 모델을 안다는 데까지다. 그 키로 그 모델을 실제로 부를 수 있는지(사용 한도, 권한, 모델을 부르는 쪽의 장애)는 이 요청으로 가르지 못한다(어림. ADR 0067 Consequences "접속 확인이 보지 못하는 것"). `anthropic` 모델의 주소를 환경 변수로 바꿔 다른 중계 서버에 붙인 배포에서 그 서버가 하나를 묻는 요청을 모르면, 실행은 되는데 접속 확인은 `붙지 못함`으로 보일 수 있다(재지 않았다). 문제 해결 절이 이 둘을 운영자에게 적는다.
- **의존성.** `anthropic`의 요청은 `anthropic` 패키지로 보낸다. 지금은 `langchain-anthropic`이 끌어오는 패키지이고 직접 쓰는 의존성으로 선언되어 있지 않다(읽었다, `pyproject.toml`). 구현 티켓이 직접 의존으로 선언하고(판은 `>=1.7,<2`로 적는다. 사용자가 골랐다. 지금 깔린 판은 1.7.0이고 `langchain-anthropic` 설치본이 요구하는 범위는 `>=0.120.0,<2.0.0`이다. 읽었다, `uv.lock`과 그 설치본의 `METADATA`), 층 경계 계약의 금지 모듈 목록 둘(core가 제공사를 모른다는 계약과 sdk가 엔진을 모른다는 계약)에 `openai`와 나란히 더하며, `docs/constitution/tech.md`의 의존성 줄을 고친다(ADR 0067 이력 2026-11-21). 그 두 계약은 core와 sdk가 이 패키지를 import하지 못하게 할 뿐이다. 채널과 관리와 조립 층이 import하지 못하게 막는 계약은 `openai`에도 없어(읽었다, `pyproject.toml`의 `[tool.importlinter]`), 어댑터만 import한다는 것은 검사가 아니라 규약으로 선다. 선언해도 설치되는 판이 그대로라는 것은 어림이고 티켓이 잠금 파일의 차이로 확인한다.

### 화면에 보이는 글과 비밀

- **MCP 쪽.** 실행의 실패 글과 가리기를 그대로 쓴다(위 "MCP 서버를 확인하는 법"). 그 가리기가 서버가 값을 바꿔 되울린 것과 8자보다 짧은 값을 놓친다는 한계(ADR 0049 이력 2026-11-09 "서버가 되울린 헤더 값을 실패 문구에서 가린다"의 "남는 한계")는 그대로 남는다. 그 글은 지금도 실패한 실행의 트레이스에 실려 관리 화면의 실행 상세에 보이므로, 플러그인 화면이 새로 여는 노출은 아니다.
- **모델 쪽은 `serve`가 지은 글만 보인다.** 사용자가 고른 것이다. 서버가 오류 본문에 적은 글과 되울린 키가 두 라이브러리 모두 예외의 글에 그대로 실렸기 때문에(쟀다, `.scratch/connection-check/probes/model_requests_loopback.py`), 예외의 글을 옮기지 않는다. 까닭은 아래 닫힌 아홉 갈래 가운데 하나이고, 위에서부터 먼저 맞는 갈래다. 바뀌는 자리는 모델 이름, 주소, 응답 상태 번호, 기한의 초, 환경 변수 이름, 예외 종류 이름뿐이다.

| 갈래 | 드는 때 | 까닭의 뒷부분 |
|---|---|---|
| 키 없음 | `anthropic` 모델의 키 칸이 비었다. 또는 `openai-compatible` 모델 파일에 `api_key_env` 칸이 있는데 그 환경 변수가 없거나 비었다(둘 다 요청을 보내지 않는다) | `키가 없다(환경 변수 <이름>)` |
| 키 모양 | `openai-compatible` 모델의 그 환경 변수 값에 인증 헤더로 보낼 수 없는 글자가 있다(요청을 보내지 않는다) | `키에 인증 헤더로 보낼 수 없는 글자가 있다(환경 변수 <이름>)` |
| 시간 초과 | 기한 안에 답이 없었다 | `<N>초 안에 답이 없었다` |
| 닿지 못함 | 연결 오류(닫힌 포트, 이름 풀이 실패 같은 것) | `서버에 닿지 못했다` |
| 키 거절 | 응답 상태가 401이나 403이다 | `키를 받아들이지 않았다(HTTP <코드>)` |
| 모델 없음(`anthropic`) | 하나를 묻는 요청의 응답 상태가 404다 | `그 이름의 모델이 없다고 답했다(HTTP 404)` |
| 모델 없음(`openai-compatible`) | 목록은 받았는데 `model_id`와 같은 `id`가 없다 | `그 이름의 모델이 목록에 없다` |
| 그 밖의 상태 | 위에 없는 오류 상태(429, 5xx, `openai-compatible`의 404 같은 것) | `서버가 오류로 답했다(HTTP <코드>)` |
| 그 밖 | 응답을 읽지 못했거나 위 어디에도 들지 않는 예외 | `확인하지 못했다(<예외 종류 이름>)` |

- **시간 초과를 닿지 못함보다 먼저 가른다.** 두 라이브러리 모두 시간 초과의 예외가 연결 오류 예외의 하위 종류다(읽었다, 이 저장소에 설치된 `anthropic`과 `openai` 패키지의 `_exceptions.py`에 `class APITimeoutError(APIConnectionError)`가 있다. 판은 프로브 `README.md`의 표). 연결 오류를 먼저 보면 답이 늦은 서버가 `서버에 닿지 못했다`로 읽히므로 표의 차례대로 본다. 어댑터가 건 기한에 닿아 끊긴 확인도 시간 초과다.
- **환경 변수 이름.** `anthropic` 모델의 이름은 `ANTHROPIC_API_KEY`이고, `openai-compatible` 모델의 이름은 모델 파일의 `api_key_env`에 적힌 글자다. 그 글자는 관리의 플러그인 조회가 매니페스트에 실어 이미 돌려주는 것이라(읽었다, `src/agent_os/sdk/manifest.py`의 `api_key_env` 칸 위 주석이 값이 아니라 이름이라 관리 API 응답에 실린다고 적고, `src/agent_os/admin/http.py`의 `read_plugin`이 매니페스트를 응답에 싣는다) 플러그인 화면이 새로 여는 노출이 아니다. 변수의 값은 어느 갈래에도 싣지 않는다.
- **글의 앞머리.** 모델 쪽 까닭은 `모델 <이름>(<주소>)에 붙지 못했다: <뒷부분>`이다. MCP 쪽 글과 같은 꼴이라 어느 플러그인의 어느 주소인지가 같은 자리에 보인다. 주소는 요청을 보낸 API의 뿌리(`anthropic`은 모델 객체가 정한 주소, `openai-compatible`은 `base_url`)다. 주소는 비밀이 아니지만(ADR 0067 결정 "비밀") 환경 변수에서 온 주소에는 검사가 걸려 있지 않으므로, 글에는 사용자 정보 자리(`user:password@`)와 쿼리 문자열을 뗀 주소를 싣는다.
- **예외를 잇지 않는다.** 모델 쪽 확인은 라이브러리 호출에서 난 예외를 종류를 가리지 않고 위 갈래의 `unreached`로 바꾸고, 원래 예외를 올리지도 기록하지도 않는다. 그 밖 갈래를 둔 까닭이 이것이다. 예상하지 못한 예외를 그대로 올리면 서버 기록에 그 예외의 글(서버가 쓴 글과 되울린 키가 실릴 수 있다)이 남는다.
- **응답 상태는 싣는다.** 상태 번호는 서버가 쓴 글이 아니라 프로토콜의 값이고, 401과 404와 5xx를 가르는 데 꼭 필요하다. 두 라이브러리 모두 오류 상태의 예외가 서버가 준 상태 번호를 들고 있었다(쟀다, `.scratch/connection-check/probes/model_requests_loopback.py`. 잰 상태는 `anthropic`이 401·403·404·429·500·529이고 `openai`가 401·404·429·500이다). 갈래는 예외의 종류가 아니라 그 번호로 가른다.

### 기한

기한은 붙어 보는 데 주는 시간이고, 확인하는 포트 메서드가 불린 때부터 센다. 넘기면 확인을 끊고, 연 것을 닫은 뒤 `unreached`를 돌려준다. 그래서 기한에 닿은 확인의 응답은 기한에 닫는 시간을 더한 만큼 걸린다(아래 "기한 뒤의 정리").

| 확인 | 기한 | 까닭 |
|---|---|---|
| 원격 MCP 서버 | 10초 | 간격 30초보다 짧아야 같은 행의 확인이 겹치지 않는다 |
| 모델 | 10초 | 위와 같다. 실제 Anthropic에 하나를 물은 요청 셋(있는 id, 없는 id, 지어낸 키)의 응답은 세 번의 실행에서 0.21~1.0초였다(쟀다, `.scratch/connection-check/probes/model_requests_live.py`. 실행마다 가장 긴 값은 그 실행이 처음 보낸 요청인 있는 id의 것이었고 차례로 0.46초, 0.44초, 1.0초였다). 닫힌 포트는 실행마다 2.0~2.8초에 연결 오류로 끝났다(쟀다, `.scratch/connection-check/probes/model_requests_loopback.py`. 명세를 쓴 세션들이 돌린 실행이 2.0~2.1초였고, 셀프 리뷰의 두 서브에이전트가 다시 돌려 보고한 실행이 2.5~2.7초였으며, PR 직전 리뷰를 반영한 뒤의 두 실행이 2.2~2.8초였다) |
| stdio MCP 서버 | 20초 | 관리 화면의 중계에 걸린 기본 제한 30초 안에, 닫는 시간까지 들어야 한다(아래) |

- **stdio의 20초.** 브라우저의 요청은 관리 화면의 서버가 `serve`로 넘겨 주는데, 그 중계의 기본 제한이 30초다(읽었다, Next 16.3.6 설치본의 `next/dist/server/lib/router-utils/proxy-request.js`. 제한에 닿아 끊기는 것을 돌려 보지는 않았다). 기한에 닿은 뒤 프로세스를 거두는 시간까지 그 안에 들어야 하므로 20초로 둔다. 거두는 시간은 서버의 모양에 달렸고, 입력이 닫혀도 끝나지 않는 서버가 2.0~2.2초, 종료 신호(SIGTERM)까지 무시하는 서버가 POSIX에서 4.0초였다(읽었다, `src/agent_os/adapters/mcp.py`의 모듈 독스트링이 옮긴 `.scratch/mcp-shutdown/spec.md`의 "닫는 데 드는 시간". 이 명세가 다시 재지 않았다). 그러면 가장 늦은 응답이 24초쯤이다(20초에 4.0초를 더한 어림). 실행은 서버를 여는 동안의 기한이 따로 없으므로(ADR 0067 결정 "기한"), 처음 띄울 때 패키지를 내려받느라 20초를 넘기는 서버(`npx`로 띄우는 서버 같은 것)는 실행에서는 붙는데 접속 확인에서는 `붙지 못함`으로 보일 수 있다. 문제 해결 절이 이것을 적는다.
- **기한 뒤의 정리.** 기한에 닿은 원격 MCP 서버의 확인은 닫는 길의 유예 2초까지 더 걸려, 응답이 12초쯤에 올 수 있다(ADR 0049). 그래도 간격 30초 안이라 같은 행의 확인이 겹치지 않는다. 모델 쪽은 닫을 세션이 없어 기한이 곧 응답의 상한이라고 본다(어림. 라이브러리가 요청을 끊는 데 드는 시간은 따로 재지 않았다). stdio MCP 서버는 위 "stdio의 20초"다.
- **값을 주는 자리.** 기한은 어댑터를 만들 때 주는 값이고 기본이 위 표의 값이다. 시험은 짧은 기한을 준다.
- **실행의 기한은 바뀌지 않는다.** 원격 MCP 서버의 접속 기한 30초와 실행 기한은 그대로다.

### 간격과 보이지 않는 탭

- **간격은 30초다.** 사용자가 골랐다. 플러그인 화면이 목록을 그리면 켜 둔 원격 MCP 서버와 켜 둔 모델의 행마다 바로 한 번 확인하고, 그 뒤 30초마다 다시 확인한다. 기한(10초)에 닫는 시간(2초까지)을 더해도 간격보다 짧아 한 행의 확인은 겹치지 않는다.
- **보이지 않는 탭에서는 멈춘다.** 다른 탭을 보거나 창을 내려 화면이 보이지 않는 동안에는 확인을 보내지 않고, 돌아오면 바로 한 번 확인한 뒤 다시 30초마다 확인한다.
- **화면을 떠나면 멈춘다.** 다른 페이지로 가거나 탭을 닫으면 확인이 멈춘다(ADR 0067 결정 "화면이 스스로 하는 확인"). `serve`가 스스로 시작하는 확인은 없다.
- **목록을 따른다.** 관리 토큰이 없으면 부르지 않는다. 목록을 다시 읽어 행이 꺼짐으로 바뀌면 그 행의 확인을 멈추고 결과를 지우며, 켜짐으로 바뀌면 바로 확인한다. 목록의 새로 고침 버튼을 누르면 스스로 하는 확인도 바로 한 번 다시 한다.
- **요청의 수.** 열어 둔 화면 하나가 행 하나에 분당 2건을 보낸다. 켜 둔 원격 MCP 서버가 m개이고 모델이 n개면 화면 하나가 `serve`에 분당 2(m+n)건을 보내고, `serve`가 바깥 서버마다 분당 2번 붙는다. 원격 MCP 서버는 그때마다 세션 하나가 열리고 닫힌다. 탭과 운영자의 수만큼 곱해진다(ADR 0067 Consequences "바깥 서버가 받는 것").
- **읽기 정책의 예외.** 관리 화면은 시간이 흐르는 것만으로는 서버를 다시 부르지 않는다는 규칙(web-admin 명세 "주기 폴링은 없다"와 스토리 35)에 스스로 하는 확인을 예외로 적는다. 그 규칙의 까닭은 서버와 트레이스 디렉터리를 훑는 비용이 화면을 열어 둔 시간에 비례하면 안 된다는 것이다. 이 예외는 플러그인 화면에서만, 창이 보이는 동안에만, 켜 둔 원격 MCP 서버와 모델의 행 수만큼만 요청을 보내므로 비용이 행의 수에 묶인다. 목록과 다른 화면의 읽기 정책은 그대로다. 같은 규칙의 다른 예외는 ADR 0063 결정 "주기 읽기의 예외"다.

### 행에 보이는 것

글자와 상태의 종류는 이 명세가 정한다. 생김새(어느 칸에 두는지, 배지의 색, 긴 글을 접는 법)는 디자인 시스템의 기존 부품으로 화면 티켓이 정하고, 새 부품이 필요하면 그 티켓 전에 `/ui-design connection-check`로 그린다.

| 행 | 보이는 것 |
|---|---|
| 켜 둔 원격 MCP 서버, 켜 둔 모델(첫 응답 전) | `확인하는 중` |
| 같은 행(응답이 `reached`) | `붙음` |
| 같은 행(응답이 `unreached`) | `붙지 못함`과 까닭의 글 전체 |
| 같은 행(확인 요청이 실패했다) | `확인하지 못함`과 그 실패의 글 |
| 켜 둔 stdio MCP 서버 | '접속 확인' 버튼. 누르기 전에는 결과가 없다. 누르면 응답까지 버튼이 눌리지 않고 `확인하는 중`이 보이며, 응답 뒤에는 `붙음`이나 `붙지 못함`과 까닭, 그리고 확인한 시각이 보인다 |
| 꺼 둔 MCP 서버, 꺼 둔 모델 | 결과를 보이지 않는다. stdio 서버의 버튼은 누를 수 없는 모양이다 |
| 매니페스트를 읽지 못한 행(표지 행) | 접속 확인을 두지 않는다 |
| 에이전트, 스킬 | 접속 확인을 두지 않는다 |

- **다시 확인하는 동안.** 30초마다 다시 확인하는 동안 앞선 결과를 지우지 않는다(`.claude/rules/web-workspace.md`의 "다시 확인하는 동안 보인 것을 지우지 않는다").
- **확인 요청이 실패하면.** `serve`에 닿지 못했거나 `serve`가 오류로 답하면 앞선 결과를 지우고 `확인하지 못함`만 보인다. 운영자가 옛 `붙음`을 지금의 것으로 믿지 않게 하려는 것이고, 목록을 다시 읽다 실패했을 때의 규칙(`.claude/rules/web-admin.md`)과 같은 까닭이다. 401이면 다른 관리 요청처럼 관리 토큰을 내려놓는다.
- **응답이 `disabled`나 `not_applicable`이면.** 목록이 그 사이 바뀐 것이므로 그 행의 결과를 지우고 목록을 다시 읽는다.
- **stdio 결과의 수명.** 눌러서 얻은 결과는 화면에만 있다. 목록을 다시 읽어도 남고, 그 플러그인을 끄거나 페이지를 떠나면 사라진다. 스스로 새로워지지 않으므로 확인한 시각을 함께 보인다.
- **색만으로 가르지 않는다.** 상태는 글자로 읽힌다. 화면 읽기 도구에는 상태가 바뀔 때만 알리고, 30초마다 같은 결과를 다시 읽어 주지 않는다.
- **자리.** 플러그인 화면의 목록에만 둔다. 플러그인 상세 페이지에는 두지 않는다(ADR 0067 결정 "자리").

### 겹치는 확인과 잦은 확인

- **`serve`는 줄이지 않는다.** `serve`는 접속 확인의 상태를 들지 않는다. 같은 플러그인의 확인이 겹쳐 와도 각각 확인하고, 409와 429로 풀지 않는다(ADR 0067 Consequences "버튼을 연달아 누를 때"). 진행 중인 확인을 기억해 나눠 주거나 결과를 잠깐 들고 있는 것도 하지 않는다. 그러려면 `serve`에 결과를 두는 자리가 생기는데, 결과는 화면에만 있다는 결정과 어긋난다.
- **화면이 줄인다.** 스스로 하는 확인은 행마다 한 번에 하나만 보내고, '접속 확인' 버튼은 응답이 올 때까지 눌리지 않는다.
- **남는 것.** 화면을 거치지 않고 관리 토큰으로 경로를 직접 되풀이해 부르면 그 수만큼 확인이 돈다. 눌러서 하는 확인이면 그 수만큼 프로세스가 뜨고, 각각 기한 20초에 닫는 시간을 더한 안에 거둬진다. 관리 토큰은 운영자의 것이고 이 판은 서버 쪽 상한을 두지 않는다. 공개 계정이 같은 버튼을 누를 수 있다는 것은 ADR 0067 Consequences "공개 데모"가 이미 받아들였다.

### 결과가 남는 자리

- **결과는 화면에만 있다.** `serve`는 접속 확인의 결과를 서버 로그에도 트레이스에도 데이터베이스에도 남기지 않는다(ADR 0067 결정 "결과가 있는 자리"). `unreached`는 성공 응답이라 에러 하나에 한 줄을 남기는 서버 기록에도 들지 않는다. 500은 다르다. 모델 파일의 구성 오류나 깨진 파일로 500이 되는 행은 오류 응답이라, 화면이 그 행을 30초마다 다시 확인하는 동안 서버 기록에 30초마다 한 줄이 남는다(읽었다, `.claude/rules/http.md`의 "에러 하나가 서버 표준 에러에 그 추적 식별자로 한 줄 남는다"). 그 줄은 붙어 본 결과가 아니라 고쳐야 할 구성을 알리는 것이라 줄이지 않는다.
- **접근 기록.** 요청마다 웹 서버의 접근 기록 한 줄은 남는다. 열어 둔 화면 하나가 행마다 분당 두 줄을 더한다.
- **HTTP 라이브러리의 로거는 그대로 둔다.** 모델 쪽 요청 셋(성공 둘, 401 하나)을 보냈을 때 루트 로거가 기본 수준(WARNING)이면 찍힌 줄이 0이었고, INFO면 `httpx2` 로거가 요청마다 주소 전체와 응답 상태가 든 한 줄을 찍었으며, DEBUG까지 내려도 키 글자가 든 줄은 없었다(쟀다, `.scratch/connection-check/probes/model_requests_loopback.py`). 곧 모델 쪽 요청도 원격 MCP 쪽과 같은 줄을 남기고, 기본 수준에서는 남기지 않는다. `serve`의 코드에는 로깅을 구성하는 자리가 없다(읽었다, `src/agent_os` 전체에서 로거를 만지는 것은 MCP 어댑터의 필터 하나뿐이다). 접속 확인의 길에서만 그 로거를 끄는 장치는 두지 않는다. 로그 수준을 일부러 낮춘 배포에서는 30초마다 행마다 한 줄이 늘고, 그 줄에는 주소와 상태만 실린다. `serve`를 실제로 띄웠을 때 루트 로거의 수준이 기본 그대로인지는 재지 않았고, Testing Decisions의 다섯째 시험이 실제 `serve`의 표준 오류에 그 줄이 없는지를 본다.

### 포트와 층

포트는 늘지 않고 다섯 그대로다. 도구 포트와 모델 포트에 접속 확인의 메서드가 는다(ADR 0067 결정 "포트와 층"). 이름과 시그니처는 아래와 같고, 이 모양이 저장소의 pyright strict 설정에서 선다는 것을 쟀다. 후보의 진단이 0개, 타입 우회가 0개였고 일부러 넣은 줄 아홉에 기대한 진단 열하나(줄과 규칙의 쌍)가 모두 났다(쟀다, `.scratch/connection-check/probes/check_port_split.py`. 모양은 같은 폴더의 `port_split_shape.py`).

```python
@dataclass(frozen=True)
class Reached: ...


@dataclass(frozen=True)
class Unreached:
    reason: str


type CheckOutcome = Reached | Unreached


class ToolSource(Protocol):
    def connect(
        self, servers: Mapping[PluginName, McpServer]
    ) -> AbstractAsyncContextManager[ToolConnection]: ...
    async def check_remote(self, name: PluginName, server: HttpServer) -> CheckOutcome: ...
    async def check_stdio(self, name: PluginName, server: StdioServer) -> CheckOutcome: ...


class ModelSource(Protocol):
    def build(self, manifest: PluginManifest) -> ChatModel: ...
    async def check(self, manifest: PluginManifest) -> CheckOutcome: ...


# 관리가 받는 묶음. 조립하는 자리가 포트에서 꺼낸 확인 함수를 넣는다.
@dataclass(frozen=True)
class AutomaticChecks:  # 스스로 하는 확인의 길
    plugins: PluginSource
    remote: Callable[[PluginName, HttpServer], Awaitable[CheckOutcome]]
    model: Callable[[PluginManifest], Awaitable[CheckOutcome]]


@dataclass(frozen=True)
class LaunchingChecks:  # 눌러서 하는 확인의 길
    plugins: PluginSource
    stdio: Callable[[PluginName, StdioServer], Awaitable[CheckOutcome]]
```

- **확인 메서드의 약속.** 붙지 못한 것은 예외가 아니라 `Unreached`로 돌려준다. 기한에 닿으면 확인을 끊고, 연 것을 닫은 뒤 `Unreached`로 돌아온다(위 "기한"). 취소는 삼키지 않는다. 구성 오류는 실행과 같은 예외로 올린다.
- **관리는 포트가 아니라 확인 함수를 받는다.** 관리 라우터는 도구 포트를 통째로 받지 않고, 조립하는 자리(`server`)가 포트에서 꺼낸 확인 함수만 받는다. 그래서 관리는 `connect`를 부를 수 없고, `.claude/rules/admin.md`의 첫 항목 "관리는 실행을 일으키지 않고, 관리 라우터는 도구 포트를 받지 않는다."가 글자 그대로 선다.
- **두 길은 받는 묶음이 다르다.** 스스로 하는 확인의 길이 받는 묶음에는 플러그인 소스와 원격 확인과 모델 확인만 있고 stdio 확인이 없다. 눌러서 하는 확인의 길이 받는 묶음에는 플러그인 소스와 stdio 확인만 있다. stdio 서버를 원격 확인에 넘기는 줄, stdio 확인을 원격 확인의 자리에 넘기는 줄, 스스로 하는 확인의 묶음에서 stdio 확인을 꺼내는 줄이 모두 타입 오류로 걸렸다(쟀다, `.scratch/connection-check/probes/check_port_split.py`).
- **타입이 막지 못하는 것.** 스스로 하는 확인의 묶음에 stdio 확인의 칸을 새로 더하는 변경은 타입 오류가 아니다(어림. 재지 않았다). 그 변경은 Testing Decisions의 첫째 시험(stdio 서버를 `GET`으로 확인하면 `not_applicable`이고 stdio 확인이 한 번도 불리지 않는다)이 잡는다. 받은 확인 함수에서 포트로 거슬러 올라가는 길은 재지 않았다.
- **응답의 `disabled`와 `not_applicable`은 포트의 값이 아니다.** 둘은 관리가 붙어 보기 전에 내리는 판정이라 관리 층의 응답 모델에만 있고, 포트의 결과는 붙었다와 붙지 못했다 둘이다.
- **core는 부르지 않는다.** 포트는 core가 선언하지만 접속 확인의 메서드를 부르는 것은 관리뿐이다. 런타임은 접속 확인을 모른다.
- **결과 타입이 사는 층.** `Reached`, `Unreached`, `CheckOutcome`은 포트의 시그니처가 돌려주므로 core의 포트 선언 옆에 둔다. 관리는 core를 import할 수 있어(`admin → http → core`) 이 타입을 그대로 받는다. `Unreached.reason`은 `str`이고, 어댑터는 `anthropic`과 `httpx`의 예외나 응답 객체를 이 `str` 밖으로 내보내지 않는다. 어댑터 안에서 붙지 못한 까닭의 예외(`anthropic.APIStatusError` 같은 것)를 받아 `Unreached`로 바꾸고, 서드파티 타입이 포트의 반환값에 비치지 않는 것이 구현 티켓의 완료 조건이다(`CODING_STANDARDS.md`의 "서드파티는 경계에서 감싼다").
- **묶음이 사는 층.** `AutomaticChecks`와 `LaunchingChecks`는 포트도 sdk 계약도 아니고 관리가 받는 인자의 모양이다. 관리 층(`agent_os.admin`)이 정의하고, `server`가 포트에서 꺼낸 확인 함수로 채워 관리 라우터에 넘긴다. core와 adapters는 이 둘을 모른다.

### 문제 해결 절

배포 안내의 맨 뒤에 `## 13. 문제 해결`을 새로 둔다. 맡는 것은 `serve`가 뜨지 않아 관리 화면을 볼 수 없을 때다(ADR 0067 결정 "`serve`가 뜨지 않을 때").

- **4절은 옮기지 않고 가리킨다.** 4절의 `migrate`가 멈췄을 때 까닭을 읽는 법과 "띄우기가 끊겼을 때" 소절은 그대로 두고, 13절이 그 자리와 12절(데이터베이스 비밀번호 바꾸기)을 가리킨다. 제품이 멈출 때 찍는 글이 그 두 제목을 가리키고 있어, 옮기면 글과 안내가 어긋난다. 4절에는 13절을 가리키는 한 줄만 더한다.
- **먼저 칠 명령.** `docker compose ps --all`로 서비스마다의 상태를 보고, `docker compose logs` 뒤에 서비스 이름을 붙여 그 서비스의 기록을 본다. 상태를 읽는 법을 함께 적는다. `healthy`와 `Up`은 뜬 것이고, `migrate`의 `Exited (0)`은 일을 마친 것이며, 그 밖의 `Exited`와 `Restarting`과 `Created`는 볼 것이다. 서비스 이름은 4절의 표를 가리킨다.
- **멈출 때의 글의 뜻.** `serve`와 `migrate`가 멈출 때와 다시 시도할 때 찍는 글마다 뜻과 할 일을 표로 적는다. 글의 원천은 postgres-foundation 명세의 "멈출 때의 글" 표이고, 13절의 표는 그 표의 글을 빠짐없이 든다. 종료 코드도 적는다. `serve`는 연결 문자열이 없거나 읽지 못하면 1로, 데이터베이스에서 멈추면 3으로 끝나고, `migrate`는 멈출 때 늘 1이다. `serve`가 3으로 멈출 때 기록의 첫 줄 앞에 붙는 `ERROR:`와 끝의 `ERROR: Application startup failed. Exiting.`은 웹 서버가 붙이는 줄이고 까닭이 아니라는 것도 적는다. 다만 그 두 줄은 postgres-foundation 명세가 윈도 호스트에서 웹 서버를 띄워 잰 것이고, 리눅스 컨테이너의 `serve`가 같은 줄을 찍는지는 그 명세도 재지 않았다(읽었다, `.scratch/postgres-foundation/spec.md`). 13절의 티켓이 실제 컨테이너의 기록에서 그 줄을 본 뒤에 적는다.
- **위젯과 관리 화면.** 위젯이 종료 1로 끝났으면 사이트 파일이 없거나 깨졌거나 읽히지 않는 것이고, 까닭이 기록에 글로 찍힌다. 관리 화면은 `Ready` 줄을 찍은 뒤에 서버로 가는 연결을 확인하다 실패할 수 있으므로, 떴는지는 기록의 줄이 아니라 상태와 종료 코드로 본다. 뒤의 것은 4절에 이미 있는 말이라 13절은 가리키고 종료 코드의 뜻만 더한다.
- **지금 떠 있는 판.** `.env`의 `AGENT_OS_VERSION`은 다음에 띄울 판이고, `.env`를 고친 뒤 다시 띄우지 않았으면 떠 있는 판과 다를 수 있다. 떠 있는 판은 `docker compose ps`의 이미지 칸에 보이는 태그와, 떠 있는 `serve` 컨테이너 안에서 치는 `agent-os --version`으로 읽는다. 뒤의 호출은 단독 배포 e2e가 이미 같은 꼴로 부른다(읽었다, `web/packages/e2e-standalone/`). 이미지의 라벨로 읽는 길은 적지 않는다. 라벨을 읽는 명령이 아래의 남에게 보내면 안 되는 출력과 같은 명령(`docker inspect`)이라 운영자가 헷갈리기 쉽다.
- **남에게 보여도 되는 출력.** `docker compose config`는 `.env`의 값과 끼워 넣은 값을 모두 평문으로 찍는다. 지어낸 값만 든 임시 프로젝트에서 지어낸 비밀번호와 키 글자가 출력에 그대로 있었다(손으로 봤다, `docker compose --env-file <임시>/probe.env -f <임시>/compose.yaml config`, Docker 29.9.2와 Compose 5.6.1). 같은 프로젝트에서 `docker compose config --images`는 이미지 이름과 태그 한 줄만 찍었다(손으로 봤다, 같은 명령에 `--images`를 붙였다). 그래서 13절은 `docker compose config`와 컨테이너에 대한 `docker inspect`의 출력을 남에게 보내지 말라고 적는다. `docker inspect`가 컨테이너의 환경 변수를 보인다는 것은 재지 않은 어림이라 구현 티켓이 지어낸 값으로 확인한 뒤 적는다. `serve`와 `migrate`가 멈출 때 찍는 글에는 비밀번호도 데이터베이스 드라이버가 낸 글도 없지만(postgres-foundation 명세 "멈출 때의 글"), 기록 전체를 남에게 보내기 전에는 한 번 훑어보라고 적는다.
- **`serve`는 떴는데 에이전트가 답하지 않을 때.** 관리 화면의 플러그인 화면에서 접속 확인을 보라고 가리키고(4절 "관리 화면에 닿기"), `붙지 못함`의 글을 읽는 법을 예 셋으로 적는다. 꺼진 모델 서버는 `서버에 닿지 못했다`, 틀린 키는 `키를 받아들이지 않았다(HTTP 401)`, 원격 MCP 서버의 토큰 불일치는 글 끝의 `(HTTP 401 Unauthorized)`다. `붙음`이 뜻하는 범위와, 처음 띄울 때 내려받는 stdio 서버가 20초를 넘기면 `붙지 못함`으로 보일 수 있다는 것도 적는다.
- **명령은 돌려 본 뒤에 적는다.** 13절에 적는 명령은 구현 티켓이 실제 배포 파일 묶음을 띄운 자리에서 돌려 본 뒤에 적고, 돌려 본 기록을 일지에 남긴다. 이 명세가 손으로 본 것은 임시 프로젝트의 `docker compose config` 둘과 `docker compose ps --all`의 머리줄뿐이다.
- **안내의 말.** 배포 안내는 저장소 안의 말을 쓰지 않는다는 기존 검사(`tests/tools/test_deploy_guide.py`의 안의 말 목록)가 13절에도 걸린다. 그 목록에 `세션`과 `명세`가 있으므로 13절은 그 낱말 없이 쓴다.

## Testing Decisions

좋은 시험은 바깥에서 보이는 행동만 본다. 응답의 값과 상태 코드, 가짜 서버가 받은 요청, 화면에 보이는 글자, 포트가 불린 횟수를 보고, 안쪽 함수의 이름과 호출 차례는 보지 않는다. 사용자가 확인한 시험 방식은 아래 일곱이다. 첫째부터 여섯째는 명세를 쓰기 전에 확인받았고, 일곱째는 셀프 리뷰 뒤에 사용자가 더했다.

1. **관리 경로(가짜 포트).** 가짜 포트를 끼운 앱에 요청을 보낸다. 기존 관리 경로의 시험과 같은 길이고 네트워크와 디스크를 타지 않는다(`.claude/rules/http.md`의 "테스트는 `create_app()`에 가짜 포트를 주입하고", 선례는 `tests/test_server.py`). 보는 것은 다음이다. 상태 넷이 응답에 실리는 모양, `unreached`의 `reason`이 포트가 준 글 그대로인 것, 판정의 차례(없는 플러그인 404, `agent`와 `skill`은 422이고 `violations`의 필드가 `path.kind`, 깨진 매니페스트 500, 깨진 운영자 파일 500, 운영자 파일이 깨졌어도 없는 플러그인은 404), 모델 파일의 구성 오류를 포트가 예외로 올리면 500인 것, 새 `GET`이 단건 조회에 가로채이지 않는 것(이름에 슬래시가 든 단건 조회의 422가 아니라 접속 확인의 응답이 온다), 꺼 둔 플러그인과 대상이 아닌 플러그인에서 확인하는 포트의 호출 횟수가 0인 것, stdio 서버를 `GET`으로 확인하면 `not_applicable`이고 stdio 확인이 불리지 않는 것, 원격 서버와 모델을 `POST`로 확인하면 `not_applicable`인 것, 두 응답의 `Cache-Control`, 토큰 없는 요청의 401. 계약 파일의 최신성과 세 면의 전수 검사는 기존 시험이 새 오퍼레이션 둘을 함께 본다.
2. **어댑터(이 PC 안의 가짜 서버).** MCP 쪽은 가짜 원격 MCP 서버와 실제로 띄우는 stdio 서버로, 모델 쪽은 가짜 모델 서버로 붙여 본다. 선례는 `tests/adapters/`의 MCP 시험과 `tests/adapters/fake_model_server.py`의 가짜 모델 서버다. 보는 것은 다음이다. 붙는 서버는 `Reached`, 닫힌 포트는 연결 오류의 글, 401을 내는 서버는 MCP 쪽이 글 끝의 `(HTTP 401 Unauthorized)`이고 모델 쪽이 `키를 받아들이지 않았다(HTTP 401)`, 없는 모델은 제공사마다의 글, 답이 늦는 서버는 짧게 준 기한 뒤에 시간 초과의 글, 서버가 오류 본문에 키를 되울려도 `reason`에 그 글자가 없는 것, 가짜 서버가 받은 요청이 한 건이고 메서드와 경로와 키 헤더가 기대와 같은 것, 주소 변수를 바꾼 환경에서 `anthropic` 확인이 그 주소로 가는 것, 키가 없는 `anthropic` 모델에서 요청이 0건인 것, `openai-compatible` 모델이 `api_key_env` 칸이 없으면 자리 채움 글자를 싣고 칸이 있는데 변수가 없거나 값의 글자가 맞지 않으면 요청이 0건이며 `reason`에 변수의 값이 없는 것, `openai-compatible`의 확인이 모델 파일의 주소로 가고 환경의 `OPENAI_API_KEY`를 싣지 않는 것, stdio 확인이 끝난 뒤와 기한에 닿은 뒤에 띄운 프로세스가 남지 않는 것. 프로세스와 기한을 재는 단언의 상한은 `.claude/rules/tests.md`의 시간 단언 항목을 따른다.
3. **화면(브라우저 없이).** 화면 부품만 띄우고 가짜 응답과 가짜 시계로 본다. 선례는 관리 화면의 페이지 시험과 스토리(부품을 상태마다 따로 띄워 보는 견본), 사진 비교다. 보는 것은 다음이다. 목록이 그려지면 켜 둔 원격 MCP 서버와 모델의 행마다 요청이 한 건 나가고 stdio와 꺼 둔 행과 표지 행과 에이전트·스킬에는 나가지 않는 것, 30초 뒤 다시 나가는 것, 보이지 않는 동안 나가지 않고 돌아오면 바로 나가는 것, 다시 확인하는 동안 앞선 결과가 남는 것, 확인 요청이 실패하면 앞선 결과가 지워지고 `확인하지 못함`이 보이는 것, 버튼을 누르면 `POST`가 한 건 나가고 응답까지 버튼이 눌리지 않는 것, 플러그인을 끄면 결과가 사라지는 것, 응답이 `disabled`나 `not_applicable`이면 그 행의 결과를 지우고 목록을 다시 읽는 것, 목록의 새로 고침 버튼을 누르면 스스로 하는 확인이 바로 한 번 다시 나가는 것, stdio 결과 옆에 확인한 시각이 보이는 것, 401이면 관리 토큰을 내려놓는 것. 생김새는 스토리와 사진 정답(사진 비교가 기준으로 삼는 화면 사진)으로 지킨다(행의 상태마다 하나씩).
4. **실제 브라우저 장면 하나.** 관리 화면 e2e에 장면 하나를 더한다. 실제 `serve`와 실제 중계를 지나, 붙는 원격 MCP 서버의 행에 `붙음`이, 닿지 않는 모델의 행에 `붙지 못함`과 `서버에 닿지 못했다`가 뜨는지 본다. 그 시험 묶음에 가짜 원격 MCP 서버와, 닫힌 포트를 가리키는 모델 픽스처(시험이 쓰려고 미리 둔 플러그인 파일)를 새로 더한다. 새 픽스처는 어느 에이전트도 쓰지 않게 두어 다른 e2e의 실행이 거기 기대지 않게 한다. 픽스처 플러그인은 단독 배포 e2e도 함께 쓰므로 그 e2e를 함께 돌린다(`CLAUDE.md` 검증 명령의 web 괄호). `serve`는 데이터베이스에 닿아야 뜨므로, 이 장면도 그 시험 묶음의 다른 장면처럼 표를 올린 테스트 데이터베이스를 받아 `serve`를 띄운다(읽었다, `web/apps/admin/e2e/stack.ts`). 그 묶음은 `serve`에 자기 환경을 그대로 물려주고 기본 모델 픽스처의 제공사가 `anthropic`이다(읽었다, `web/packages/e2e-stack/src/serve.ts`와 `plugins.ts`). 그래서 접속 확인이 들어오면, 플러그인 화면을 여는 기존 장면마다 기본 모델의 행이 확인을 보낸다. 환경에 Anthropic 키가 있으면 그 요청이 실제 제공사로 가고, 없으면 그 행이 `붙지 못함`과 키가 없다는 글을 보일 것으로 본다(어림. 돌려 보지 않았다). 이 장면의 티켓이 그 묶음의 `serve`가 접속 확인으로 실제 제공사에 닿지 않게 하고, 기존 장면이 그 행의 새 글자에 깨지지 않는지를 함께 본다.
5. **실제 Anthropic에 한 번.** 키가 있을 때만 도는 시험(`-m llm`)에 하나를 더한다. 실제 `serve`를 띄워 기본 모델의 접속 확인이 `reached`인지 보고, `serve`의 표준 오류에 HTTP 라이브러리의 요청 줄(`HTTP Request:`)이 없는지도 본다. 모델을 부르지 않아 토큰을 쓰지 않는다. 선례는 `tests/test_main.py`의 실제 `serve`를 띄우는 시험이다. 그 시험들처럼 테스트 데이터베이스 컨테이너가 떠 있어야 돈다(`docs/constitution/operations.md` LLM 테스트).
6. **배포 안내.** 기존 문서 검사(`tests/tools/test_deploy_guide.py`)의 필수 낱말에 13절이 꼭 가져야 할 것을 더한다. 절 제목, 판을 읽는 명령, 남에게 보내지 말라는 명령 둘, 웹 서버가 붙이는 줄의 글, 접속 확인을 가리키는 말이다. 그 검사는 이 저장소의 안내가 지나는 시험과 낱말 하나가 빠진 안내를 잡는 시험이 짝으로 서 있다. 13절의 표가 `serve`와 `migrate`가 멈출 때 찍는 글을 빠짐없이 드는지도 이 검사가 본다. 글의 고정된 부분은 손으로 옮겨 적지 않고 제품 코드가 그 글을 짓는 자리에서 가져와, 제품의 글이 바뀌면 안내의 검사가 빨개지게 한다. 제품 코드에 시험이 읽을 수 있는 자리가 없으면 13절의 티켓이 그 자리를 정한다.
7. **빌린 모델 서버에 한 번.** 로컬 모델 시험(`-m llm_local`. Runpod에서 모델 서버 둘을 빌려 띄우고 도는 시험이다)에 하나를 더한다. 빌린 서버마다 `openai-compatible` 모델의 접속 확인을 한 번 불러 `Reached`인지 본다. 이 명세가 재지 않은 것(띄운 모델 서버가 목록 요청에 200과 그 모델 이름으로 답하고, 확인의 요청이 그 서버에 닿는지)을 실제 서버로 고정한다. 모델 쪽 확인을 구현하는 티켓은 어댑터를 고치므로 병합 조건의 범위에 들어 이 시험을 어차피 돌린다(`docs/constitution/operations.md` LLM 테스트의 "범위"). 그래서 서버를 따로 더 빌리지 않는다.

**수락 조건을 덮는 자리.** 일부러 깨뜨린 배포 셋은 둘째 시험이 글의 수준에서 모두 덮는다. 꺼진 모델 서버와 꺼진 MCP 서버는 닫힌 포트로, 토큰 불일치는 401을 내는 가짜 서버로 만든다. 넷째 시험이 그 가운데 하나(닿지 않는 모델)를 실제 화면까지 잇는다. 실제 배포 파일 묶음을 깨뜨려 보는 시험은 두지 않는다.

**타입.** 포트의 모양은 프로브가 이미 쟀고, 구현 뒤에는 저장소의 타입체크가 같은 것을 본다. 가짜 포트는 포트를 상속하지 않고 시그니처로 만족하며 픽스처가 포트 타입으로 적는다(`.claude/rules/tests.md`). 접속 확인의 메서드가 없는 옛 가짜를 포트 자리에 넘기는 줄이 타입 오류로 걸렸으므로(쟀다, `.scratch/connection-check/probes/check_port_split.py`), 포트에 메서드를 더하는 티켓은 기존 가짜 전부에 그 메서드를 함께 더해야 한다.

## Out of Scope

- **진단 묶음 명령, 진단 페이지, 확인 결과를 담는 데이터베이스 표.** 만들지 않는다(ADR 0067 결정 "만들지 않는 것").
- **`serve`가 스스로 시작하는 확인, 확인 결과의 이력, 알림.** 화면을 열어 둔 동안만 확인한다. 꺼졌을 때 메일이나 웹훅으로 알리는 것은 하지 않는다.
- **서버 쪽 상한과 겹침 막기.** 409와 429, 진행 중인 확인을 나눠 주는 것, 결과를 잠깐 들고 있는 것을 두지 않는다.
- **모델을 실제로 불러 보는 확인.** 토큰을 쓰는 확인은 하지 않는다. 그래서 사용 한도와 권한은 가르지 못한다.
- **`openai-compatible`에서 모델 하나를 묻는 요청과 목록의 둘째 쪽 읽기.**
- **에이전트와 스킬의 행, 플러그인 상세 페이지의 접속 확인.**
- **판 번호를 관리 화면에 보이는 것.** 판은 문제 해결 절이 적는 명령으로 읽는다(ADR 0067 Considered Options).
- **로깅 구성과 로그 수준 설정.** `serve`에 로깅을 구성하는 코드를 더하지 않는다.
- **중계의 제한 30초 늘리기, 실행의 기한과 실행의 실패 글 바꾸기.**
- **프록시와 위젯 같은 다른 컨테이너에 `serve`가 붙어 보는 것.**
- **문서 검색 서버 쪽 진단과 통합 배포의 관리 명령.** 설계가 이미 넘겼다(`.scratch/deploy-package/plan.md`의 "connection-check의 설계가 넘긴 것"). 이 명세가 다른 기능에 새로 넘기는 것은 없다.

## Further Notes

- **티켓의 차례.** 첫 티켓은 계약이다. 경로 둘과 응답 모델이 `openapi.json`과 생성한 TS 타입에 실리고, 포트에 메서드가 늘며, 관리 경로가 가짜 포트로 시험된다(ADR 0067 Consequences "계약 변경이 첫 티켓이다"). 그 뒤 어댑터의 MCP 쪽 확인, 어댑터의 모델 쪽 확인(의존성 선언 포함), 화면, e2e 장면, 문제 해결 절이 선다. 어댑터 둘과 화면은 계약 티켓 뒤에 나란히 갈 수 있고, e2e 장면은 셋이 모두 선 뒤다.
- **문제 해결 절의 티켓이 기다리는 것은 없다.** 13절의 "멈출 때의 글의 뜻" 표는 제품이 실제로 찍는 글을 적는다. 그 글을 내는 postgres-foundation의 티켓 03(`serve`가 뜰 때 데이터베이스를 확인한다)은 이 명세를 쓰는 동안 병합됐고(PR 615, 2026-11-21) 그 기능은 끝났다. 그래서 기능 계획의 `**Blocked by:**`에 더할 것이 없고, 그 티켓은 13절의 표를 병합된 코드가 실제로 찍는 글과 대 본 뒤에 쓴다.
- **구현 티켓이 함께 고칠 자리.** ADR 0067 Consequences "구현 티켓이 함께 고칠 자리"가 든 것(`.claude/rules/admin.md`의 첫 항목, `.claude/rules/core.md`의 포트 표, 두 포트의 독스트링, 조립 층과 관리 라우터의 주석, 배포 안내와 그 검사, 플러그인 목록 화면과 사진 정답)에 이 명세가 다음을 더한다. `.claude/rules/web-admin.md`에 읽기 정책의 예외를 적고 읽기 정책의 주석을 고친다. `.claude/rules/adapters.md`의 모델 소스 항목과 MCP 항목에 접속 확인의 메서드를 적는다. 같은 모델 소스 항목과 `src/agent_os/adapters/anthropic.py`의 모듈 독스트링이 적는 "이 모듈은 키 값을 만지지 않는다"는, 접속 확인이 모델 객체가 든 키를 확인하는 클라이언트에 넘기면 그대로는 맞지 않으므로 함께 고친다. `docs/constitution/tech.md`의 의존성 줄("anthropic SDK는 `langchain-anthropic` 뒤에서 온다")과 `pyproject.toml`의 같은 뜻의 주석을 고치고, 층 경계 계약의 금지 모듈 목록 둘에 `anthropic`을 더한다. `docs/constitution/tech.md`를 고치는 커밋은 헌법의 판을 올린다(`docs/constitution/README.md`의 판 줄). `docs/constitution/operations.md`의 LLM 테스트 절이 `-m llm` 시험을 늘어놓으면 다섯째 시험을 더하고, 같은 절의 로컬 모델 시험 설명에 일곱째 시험을 더한다.
- **재지 않은 것.** 띄운 모델 서버가 목록 요청에 어떻게 답하는지와 목록이 여러 쪽인지. `openai-compatible`의 확인이 실행과 같은 서버에 같은 키로 닿는지. 키가 없는 `anthropic` 모델의 키 칸의 값. 30초마다 묻는 요청이 제공사의 어떤 한도에 걸리는지. 주소를 바꿔 다른 중계 서버에 붙인 `anthropic` 모델에서 하나를 묻는 요청이 통하는지. 중계의 30초 제한에 닿았을 때 화면에 무엇이 오는지. 실제 `serve`의 루트 로거 수준. `docker inspect`의 출력. 원격 MCP 서버가 확인 한 번에 받는 요청의 수. 모델을 부르는 요청이 날짜를 뗀 이름을 받는지. 새 `GET`을 단건 조회 뒤에 선언했을 때의 응답. 리눅스 컨테이너의 `serve`가 `ERROR:` 줄을 찍는지. 접속 확인이 든 뒤 기존 e2e 장면의 기본 모델 행에 무엇이 보이는지. 이 가운데 구현 티켓이 시험으로 고정할 것은 해당 절에 적었다.
- **프로브를 다시 돌 때.** `anthropic`, `openai`, `langchain-anthropic`, pyright의 판을 올리면 `.scratch/connection-check/probes/README.md`의 표에 적힌 명령으로 다시 돈다. 실제 API에 닿는 프로브는 `GET`만 보내고 모델을 부르지 않는다.
- **측정의 범위.** 측정은 모두 Windows 10의 이 PC 한 대에서 돌았고 리눅스 컨테이너에서는 돌지 않았다. 닫힌 포트가 연결 오류로 끝나는 데 걸린 2.0~2.8초는 같은 PC에서도 실행마다 달랐고, 운영체제마다도 다를 수 있다(어림).
