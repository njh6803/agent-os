# connection-check: 관리 화면의 플러그인 화면에서 켜 둔 MCP 서버와 모델에 붙는지 보여 주고, 배포 안내에 문제 해결 절을 둔다.
**슬라이스:** 9
**Blocked by:** release-image, mcp-http
**설계:** ADR 0067

접속 확인(ADR 0067, `CONTEXT.md`). 이 행의 옛 이름은 diag-bundle이고, 문제를 살필 때 판과 구성과 최근 실패 원인을 파일 하나로 묶는 명령을 계획했다. 설계 인터뷰(일지 2026-11-20-1928)가 그 명령을 접었다. 파일로 묶는 진단 명령, 따로 두는 진단 페이지, 확인 결과를 담는 데이터베이스 표는 만들지 않는다. 만드는 것은 둘이다. 첫째는 관리 화면의 플러그인 화면(첫 페이지 `/`의 플러그인 목록)에 두는 접속 확인이다. MCP 구역과 모델 구역의 행마다, 켜 둔 플러그인이 가리키는 바깥 서버에 `serve`가 실제로 붙어 본 결과를 보인다. 켜 둔 원격 MCP 서버와 켜 둔 모델은 화면이 열려 있는 동안 화면이 정해진 간격으로 스스로 되풀이해 확인하고, 전송이 stdio인 MCP 서버는 행의 '접속 확인' 버튼을 운영자가 누를 때만 프로세스를 한 번 띄워 확인한다. 꺼 둔 플러그인은 확인하지 않고, 그 판정은 화면이 아니라 `serve`가 한다. 모델은 '쓸 수 있는 모델 목록'을 묻는 요청으로 확인한다. 붙지 못한 까닭은 그 행에 글로 보이고, 결과는 화면에만 있다(서버 로그에도 트레이스에도 데이터베이스에도 남기지 않는다). 에이전트와 스킬의 행, 플러그인 상세 페이지에는 두지 않는다. 둘째는 배포 안내(`deploy/standalone/README.md`)에 새로 두는 '문제 해결' 절이다. `serve`가 뜨지 않아 화면을 볼 수 없을 때를 맡고, 서버에서 칠 명령(`docker compose ps`, `docker compose logs` 뒤에 서비스 이름)과 `serve`·`migrate`가 멈출 때 찍는 글의 뜻과 지금 떠 있는 판을 읽는 법(`.env`의 `AGENT_OS_VERSION`이 띄운 이미지의 태그다)을 적는다. 판 번호는 관리 화면에 보이지 않는다. 원래 계획이 묶음에 담으려던 구성 보기, 최근 실패 원인, 트레이스의 글 싣기는 이 행에서 빠졌고 지금의 화면(플러그인 상세 페이지, 실행 상세 페이지) 그대로다. 문서 검색 서버 쪽 진단과 통합 배포의 관리 명령은 각 계획의 설계에 넘겼다(`.scratch/deploy-package/plan.md`의 "connection-check의 설계가 넘긴 것"). 첫 티켓은 계약이다: `openapi.json`에 접속 확인의 관리 경로가 늘고 생성한 TS 타입(`web/packages/api-client`)이 함께 바뀐다. sdk는 바뀌지 않는다. 경로의 이름, 요청 하나가 플러그인 몇을 확인하는지, 응답의 모양, 확인의 간격과 기한의 값, 모델 쪽 실패 글과 그 가리기는 명세가 정한다. 배포 안내 4절에 이미 있는 실패 안내(`migrate`가 멈췄을 때 까닭을 읽는 법, "띄우기가 끊겼을 때" 소절)를 문제 해결 절로 옮겨 올지 가리키기만 할지도 명세가 정한다(ADR 0067 결정 "`serve`가 뜨지 않을 때"). 명세가 지킬 조건은 ADR 0067 결정의 "확인은 `serve`가 한다"(조건 넷), "붙지 못한 확인은 오류 응답이 아니다", "비밀", "포트와 층"이다. 명세가 먼저 볼 것은 둘이다. 모델 목록 요청에 요금이 붙는지와 로컬 모델 서버가 그 요청에 답하는지를 프로브로 실제로 돌려 확인한다(그 ADR 결정 "모델을 확인하는 법". 요금이 붙거나 답하지 않는 서버가 있으면 그 항목을 이력으로 다시 정한다). 화면이 스스로 하는 확인의 길이 stdio MCP 서버를 받지 못하게 타입으로 가르는 모양이 pyright에서 서는지도 프로브로 본다(그 ADR 결정 "포트와 층". 서지 않으면 아키텍처 테스트로 지킨다). 구현 티켓이 함께 고칠 규칙 파일과 독스트링은 그 ADR Consequences "구현 티켓이 함께 고칠 자리"에 있다. 수락: 일부러 깨뜨린 배포(모델 서버 꺼짐, MCP 서버 꺼짐, 토큰 불일치)에서 플러그인 화면만 보고 원인을 가를 수 있다. mcp-http 명세가 넘긴 것(2026-11-09, `.scratch/mcp-http/spec.md`): 원격 MCP 서버의 접속 확인은 어댑터가 서버 하나를 여는 함수의 경계를 다시 쓴다(ADR 0049 Consequences "뒤 기능이 기대는 것"). 그 실패 문구는 서버가 돌려준 오류 응답의 상태를 원인 끝에 `(HTTP 401 Unauthorized)`처럼 들므로, 토큰 불일치는 꺼진 서버(`ConnectError`)와 문구에서 갈린다(명세 "실패 문구"). release-image 명세가 넘긴 것(2026-11-13, `.scratch/release-image/spec.md`의 Out of Scope): 판은 이미지의 OCI 라벨 셋(`org.opencontainers.image.version`, `.revision`, `.source`)과 이미지 안의 `agent-os --version`으로도 읽힌다(그 명세 "이미지의 이름과 태그", "이미지의 구성"의 판 번호). 문제 해결 절이 `.env`의 값에 더해 이 길도 적을지는 명세가 정한다. 위젯은 뜰 때마다 사이트 파일로 빌드하므로 사이트 파일이 없거나 깨졌거나 읽히지 않으면 빌드 전에 까닭을 적은 글과 함께 종료 1로 끝난다(같은 명세 "이미지의 구성"의 위젯). 관리 화면 상류 검사의 실패는 시작 기록에 `Ready` 줄이 찍힌 뒤에 나므로, 떴는지는 기록의 줄이 아니라 종료 코드와 상태 확인으로 본다(같은 명세 "관리 화면의 상류"). 문제 해결 절은 이 둘의 뜻도 적는다. 단독 compose의 서비스는 지금 일곱(`proxy`, `postgres`, 한 번 돌고 끝나는 `migrate`, `serve`, `admin`, `widget`, `portal`)이고 상태 확인이 없는 것은 `proxy`와 `migrate`다(2026-11-20에 서브에이전트가 `deploy/standalone/compose.yaml`을 읽은 보고다. 일지 2026-11-20-1928 "배포 쪽"). postgres-foundation의 설계와 명세가 넘긴 것(2026-11-17 ADR 0066, 2026-11-18 `.scratch/postgres-foundation/spec.md`의 Out of Scope): `serve`와 `migrate`가 멈출 때와 다시 시도할 때 찍는 글은 그 명세 "멈출 때의 글"의 표가 전부이고, 문제 해결 절이 뜻을 적을 글이 그것이다. 글은 이유를 적은 첫 줄과, 갈래에 따라 두 칸 들인 설명 줄 하나로 된다. `serve`는 연결 문자열이 없거나 읽지 못하면 1로, 데이터베이스에서 멈추면 3으로 끝나고, `migrate`는 멈출 때 늘 1이다. `serve`가 3으로 멈출 때 uvicorn은 첫 줄 앞에 `ERROR:`를 붙이고 끝에 `ERROR: Application startup failed. Exiting.`을 더한다(그 명세의 같은 절). 글에는 비밀번호도 드라이버가 낸 글도 싣지 않는다(같은 절). 데이터베이스 비밀번호가 `.env`에 있으므로, 문제 해결 절이 안내하는 명령의 출력에 비밀 값이 드러나는지를 명세가 본다(`docker compose config`와 `docker inspect`의 출력이 `.env`의 값을 그대로 보인다는 것은 코드를 읽은 어림이다. 같은 일지 "배포 쪽")
