# 06: 배포 안내에 문제 해결 절(13절)이 생긴다

**What to build:** 운영자가 단독 배포 안내(`deploy/standalone/README.md`)의 맨 뒤에서 `## 13. 문제 해결`을 찾는다. `serve`가 뜨지 않아 관리 화면을 볼 수 없을 때 서버에서 먼저 칠 명령(`docker compose ps --all`, `docker compose logs <서비스>`)과 상태를 읽는 법이 있고, `serve`와 `migrate`가 멈추며 찍는 글마다 뜻과 할 일이 표로 있으며, 지금 떠 있는 판을 읽는 명령과 남에게 보내면 안 되는 출력이 있다. `serve`는 떴는데 에이전트가 답하지 않으면 플러그인 화면의 접속 확인으로 이어 가라는 안내와 `붙지 못함`의 글을 읽는 예 셋이 있다. 4절에는 13절을 가리키는 한 줄이 생긴다. 제품이 멈출 때 찍는 글이 바뀌면 안내의 검사가 빨개진다.

04 뒤에 05와 나란히 간다(to-tickets에서 사용자가 골랐다). 13절이 가리키는 화면의 접속 확인과 모델 쪽 글이 선 뒤에 써야 안내가 아직 없는 화면을 가리키는 때가 없다. 05와 함께 고치는 파일은 없을 것으로 본다(어림).

근거는 명세 `.scratch/connection-check/spec.md`의 "문제 해결 절" 전부와 "결과가 남는 자리"의 HTTP 라이브러리 로거 항목, Testing Decisions의 여섯째와 일곱째, Further Notes의 "문제 해결 절의 티켓은 화면 뒤다", 사용자 이야기 28과 30~37이다. 결정은 ADR 0067의 결정 "`serve`가 뜨지 않을 때"와 Considered Options(판 번호를 화면에 보이지 않는 까닭)다. 멈출 때의 글의 원천은 postgres-foundation 명세(`.scratch/postgres-foundation/spec.md`)의 "멈출 때의 글" 표이고, 그 글을 내는 코드는 병합되어 있다(PR 615). 이 티켓의 "명세 검토"는 일지 `docs/journal/2026-11-22-0159-connection-check-tickets.md`의 "명세 검토" 절을 가리킨다.

**Blocked by:** 04

**Status:** ready-for-agent

### 13절에 싣는 것(명세 "문제 해결 절")

- [ ] 4절의 `migrate`가 멈췄을 때 까닭을 읽는 법과 "띄우기가 끊겼을 때" 소절, 12절(데이터베이스 비밀번호 바꾸기)은 옮기지 않고 가리킨다. 제품이 멈출 때 찍는 글이 그 제목들을 가리키므로 제목은 바꾸지 않는다
- [ ] 먼저 칠 명령과 상태를 읽는 법을 적는다. `healthy`와 `Up`은 뜬 것, `migrate`의 `Exited (0)`은 일을 마친 것, 그 밖의 `Exited`와 `Restarting`과 `Created`는 볼 것이다. 서비스 이름은 4절의 표를 가리킨다
- [ ] `serve`와 `migrate`가 멈출 때와 다시 시도할 때 찍는 글마다 뜻과 할 일과 종료 코드를 표로 적는다. 표가 드는 글의 경계는 postgres-foundation 명세의 "멈출 때의 글" 표다(명세 "멈출 때의 글의 뜻"). `serve`가 시작할 때 내는 다른 진단(토큰, 사이트 파일 같은 것)은 이 표에 들지 않는다. 그 글에도 `(ADR 0011)`·`(ADR 0015)`·`(ADR 0023)`이 들어(`src/agent_os/main.py`), 13절에 옮기기로 하면 아래 `ADR` 항목과 같은 충돌이 난다. `serve`는 연결 문자열이 없거나 읽지 못하면 1, 데이터베이스에서 멈추면 3이고, `migrate`는 멈출 때 늘 1이다. 표의 글은 병합된 코드가 실제로 찍는 글과 대 본 뒤에 적는다
- [ ] `serve`가 3으로 멈출 때 붙는 `ERROR:` 머리와 끝의 `ERROR: Application startup failed. Exiting.`이 웹 서버의 줄이고 까닭이 아니라는 것을 적는다. 그 두 줄은 윈도 호스트에서만 재 본 것이므로, 실제 리눅스 컨테이너의 `serve` 기록에서 그 줄을 본 뒤에 적고 본 기록을 일지에 남긴다
- [ ] 위젯이 종료 1로 끝났을 때의 뜻(사이트 파일이 없거나 깨졌거나 읽히지 않는다)과, 관리 화면은 `Ready` 줄 뒤에도 실패할 수 있어 떴는지를 상태와 종료 코드로 본다는 것을 적는다. 뒤의 것은 4절을 가리키고 종료 코드의 뜻만 더한다
- [ ] 지금 떠 있는 판은 `docker compose ps`의 이미지 칸과, 떠 있는 `serve` 컨테이너 안에서 치는 `agent-os --version`으로 읽는다고 적는다. `.env`의 `AGENT_OS_VERSION`은 다음에 띄울 판이라 다를 수 있다는 것도 적는다. 이미지의 라벨로 읽는 길은 적지 않는다
- [ ] `docker compose config`와 컨테이너에 대한 `docker inspect`의 출력을 남에게 보내지 말라고 적는다. `docker inspect`가 컨테이너의 환경 변수를 보인다는 것은 지어낸 값만 넣은 컨테이너로 확인한 뒤 적고, 확인한 기록을 일지에 남긴다. 기록 전체를 남에게 보내기 전에는 한 번 훑어보라고도 적는다
- [ ] `serve`는 떴는데 에이전트가 답하지 않을 때는 플러그인 화면의 접속 확인을 보라고 가리키고(4절 "관리 화면에 닿기"), `붙지 못함`의 글을 읽는 예 셋(`서버에 닿지 못했다`, `키를 받아들이지 않았다(HTTP 401)`, 글 끝의 `(HTTP 401 Unauthorized)`)을 적는다. `붙음`이 뜻하는 범위(사용 한도와 권한은 가르지 못한다), 주소를 바꿔 다른 중계 서버에 붙인 `anthropic` 모델은 그 서버가 모델 하나를 묻는 요청을 모르면 실행은 되는데 `붙지 못함`으로 보일 수 있다는 것(명세 "`붙음`이 뜻하는 것"), 처음 띄울 때 내려받는 stdio 서버가 20초를 넘기면 `붙지 못함`으로 보일 수 있다는 것도 적는다
- [ ] 원격 MCP 서버의 주소에 토큰을 넣지 말고 헤더에 두라고 적는다. 로그 수준을 INFO 이하로 낮추면 HTTP 라이브러리가 요청마다 주소 전체를 기록하기 때문이다
- [ ] 4절에 13절을 가리키는 한 줄을 더한다
- [ ] 13절에 적는 명령은 실제 배포 파일 묶음을 띄운 자리에서 돌려 본 뒤에 적고, 돌려 본 명령과 출력의 요지를 일지에 남긴다
- [ ] 안내의 말 검사(`tests/tools/test_deploy_guide.py`의 안의 말 목록)에 걸리는 낱말(`세션`, `명세`, `ADR` 등)을 13절에 쓰지 않는다

### 검사(명세 Testing Decisions의 여섯째)

- [ ] 기존 문서 검사의 필수 낱말에 13절이 꼭 가져야 할 것을 더한다. 절 제목, 판을 읽는 명령, 남에게 보내지 말라는 명령 둘, 웹 서버가 붙이는 줄의 글, 접속 확인을 가리키는 말이다
- [ ] `Exited (0)`, 위젯의 종료 1, `Ready` 줄 뒤의 실패처럼 4절에 이미 있는 낱말은 안내 전체에서 찾으면 13절에서 빠져도 초록이다. 그래서 13절에 있어야 할 낱말은 13절만 잘라 찾는다(이야기 33·34, 명세 검토)
- [ ] 13절의 표가 위 경계 안의 글(postgres-foundation 명세의 "멈출 때의 글" 표에 든 글)을 빠짐없이 드는지 본다. 글의 고정된 부분은 손으로 옮겨 적지 않고 제품 코드가 그 글을 짓는 자리에서 가져온다. 지금 그 글은 사적 상수와 메서드 안의 문자열이라 시험이 읽을 자리가 없으므로(`src/agent_os/adapters/postgres/database.py`, `src/agent_os/main.py`), 그 자리를 제품 코드에 낸다. 자리의 모양(공개 이름인지, 글을 짓는 함수인지)을 정해 일지에 적는다(명세 검토 S7이 이 티켓에 넘겼다)
- [ ] `serve`가 연결 문자열 없이 1로 끝날 때의 글이 `(ADR 0066)`을 담는데 안내의 말 목록에 `ADR`이 있다. 제품의 글에서 ADR 번호를 뺄지, 안내가 옮기는 조각에서 그 괄호를 뺄지를 정해 일지에 적는다. 앞의 것이면 운영자가 보는 글이 바뀌는 제품 변경이므로 그 글을 보는 기존 시험을 함께 고치고, 바뀐 글을 일지와 PR 본문에 적는다. 기능 단락은 이 티켓이 먼저 병합되면 아직 없으므로, 마지막으로 병합하는 티켓이 아래 "기능을 닫는 일"대로 싣는다
- [ ] 저장소 상태 검사의 짝을 둔다. 이 저장소의 안내가 지나는 시험과, 13절에서 낱말 하나나 멈출 때의 글 하나가 빠진 안내를 잡는 시험이다(`.claude/rules/tests.md`). 제품의 글을 바꾼 사본으로 안내의 검사가 빨개지는 것도 본다

### 기능을 닫는 일

05와 나란히 가므로, 이 기능의 티켓 가운데 마지막으로 병합하는 쪽이 아래를 맡는다. 규칙은 `docs/agents/issue-tracker.md`의 "끝 줄을 적는 때"와 "나란히 돈 마지막 티켓 둘"이고, 기능 단락을 쓰는 법은 `docs/constitution/operations.md`의 "릴리스 노트 원고"다.

- [ ] 병합 직전에 `git fetch origin` 뒤 기준 브랜치를 합치고, 합친 판에서 이 기능의 다른 티켓(`.scratch/connection-check/issues/`에서 이 티켓 밖의 전부)의 `Status:`를 본다. 모두 done이나 wontfix이면 이 PR이 마지막이라 아래 항목을 맡고, 열린 티켓이 하나라도 있으면 맡지 않는다. 05만 보지 않고 전부를 보는 것은 그 사이 티켓이 더해질 수 있어서다. 어느 쪽이든 저장소 상태 시험(`test_이_저장소의_…`)을 돌려 판정과 맞는지 본다
- [ ] 마지막이면 같은 커밋에 셋을 싣는다. 기능 계획(`.scratch/connection-check/plan.md`)의 `**끝:**` 줄, 기능 단락(`docs/release-notes/features/connection-check.md`. 이 기능의 티켓 전부가 바꾼 제품 변경을 담고, 이 티켓이 멈출 때의 글을 바꿨으면 그것도 싣는다), `uv run python tools/plan_table.py`를 돌린 `.scratch/plan.md`다. 끊긴 뒤 이어받았거나 컨텍스트가 압축된 뒤라 끝 줄이 이미 있으면 다시 적지 않는다
- [ ] 마지막이 아니라고 보고 병합했으면, 병합 뒤 다시 `git fetch origin`으로 열려 있던 티켓이 그 사이 병합됐는지 본다. 두 PR이 같은 때 서로 마지막이 아니라고 보고 병합하면 끝 줄을 아무도 적지 않는다. dev에는 strict 보호가 없어 두 PR 모두 초록으로 병합되고, 그 뒤 dev의 push CI가 저장소 상태 시험으로 빨개진다. 그때는 끝 줄과 기능 단락을 싣는 고침 PR을 낸다. 같은 고침 PR이 이미 열렸거나 병합됐으면(`gh pr list`) 내지 않는다
