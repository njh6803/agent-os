# 05: 실제 브라우저에서 붙는 원격 MCP 서버와 닿지 않는 모델의 행을 본다

**What to build:** 관리 화면 e2e에 장면 하나가 생긴다. 실제 `serve`와 실제 중계를 지난 브라우저가 플러그인 화면을 열면, 시험이 띄운 가짜 원격 MCP 서버의 행에 `붙음`이 뜨고, 닫힌 포트를 가리키는 모델의 행에 `붙지 못함`과 `서버에 닿지 못했다`가 뜬다. 화면 부품의 시험(04)이 가짜 응답으로 본 것을 실제 경로 전체로 한 번 잇는다.

04 뒤에 06과 나란히 간다. 04가 병합되어야 화면이 확인을 보내기 때문이다. 06과 함께 고치는 파일은 없을 것으로 본다(어림).

근거는 명세 `.scratch/connection-check/spec.md`의 Testing Decisions 넷째와 "수락 조건을 덮는 자리", 사용자 이야기 1~3이다. 결정은 ADR 0067의 결정 "화면이 스스로 하는 확인"이다. 관리 화면 e2e의 준비가 다른 e2e의 패키지를 쓰지 않는 까닭은 ADR 0050 결정 "함께 쓰는 코드"다.

**Blocked by:** 04

**Status:** done

### 픽스처

- [x] 관리 화면 e2e의 준비(`web/apps/admin/e2e/stack.ts`)가 가짜 원격 MCP 서버를 하나 띄우고, 그 주소를 가리키는 원격 MCP 픽스처와 닫힌 포트를 가리키는 `openai-compatible` 모델 픽스처를 임시 플러그인 루트에 쓴다. 가짜 원격 MCP 서버는 저장소에 이미 있는 시험용 서버(`tests/mcp_http_server.py`와 그것을 띄우는 `tests/mcp_http.py`)를 다시 쓸 수 있는지 먼저 본다
- [x] 새 픽스처 둘은 어느 에이전트도 쓰지 않게 둔다. 다른 장면의 실행이 거기 기대지 않게 하려는 것이다
- [x] 닫힌 포트는 시험이 잠깐 열었다 닫은 포트처럼 그 PC에서 실제로 닫혀 있는 것을 쓴다. 정해 둔 번호에 기대지 않는다
- [x] 장면이 끝나면 띄운 가짜 서버를 다른 프로세스처럼 거둔다. 그 출력도 실패를 볼 수 있게 `test-results/`에 남긴다(준비의 머리 설명)
- [x] 픽스처를 관리 화면 e2e의 준비에만 두면 위젯·위젯 테스트 페이지·단독 배포 e2e는 영향을 받지 않는다. 가짜 서버나 픽스처를 다른 e2e가 함께 쓰는 패키지(`web/packages/e2e-stack`)에 두기로 했으면 그 e2e들을 함께 돌린다(`CLAUDE.md` 검증 명령의 web 괄호)

### 장면

- [x] 기존 장면처럼 표를 올린 테스트 데이터베이스를 받아 띄운 `serve`로 돈다(같은 준비 파일)
- [x] 플러그인 화면을 열면 원격 MCP 픽스처의 행이 `붙음`이 되고, 모델 픽스처의 행이 `붙지 못함`이 되며 그 행에 `서버에 닿지 못했다`가 보이는 것을 본다. 상태는 색이 아니라 글자로 찾는다
- [x] 기다리는 시간은 기한(원격 MCP 서버와 모델 10초)과 중계를 지나는 시간을 넘게 넉넉히 두되, 30초 간격의 다시 확인을 기다리지 않는다. 첫 확인의 결과만 본다
- [x] 장면의 이름은 행동을 말하는 한국어 문장이다(`.claude/rules/web-workspace.md`)

### 기능을 닫는 일

06과 나란히 가므로, 이 기능의 티켓 가운데 마지막으로 병합하는 쪽이 아래를 맡는다. 규칙은 `docs/agents/issue-tracker.md`의 "끝 줄을 적는 때"와 "나란히 돈 마지막 티켓 둘"이고, 기능 단락을 쓰는 법은 `docs/constitution/operations.md`의 "릴리스 노트 원고"다.

- [ ] 병합 직전에 `git fetch origin` 뒤 기준 브랜치를 합치고, 합친 판에서 이 기능의 다른 티켓(`.scratch/connection-check/issues/`에서 이 티켓 밖의 전부)의 `Status:`를 본다. 모두 done이나 wontfix이면 이 PR이 마지막이라 아래 항목을 맡고, 열린 티켓이 하나라도 있으면 맡지 않는다. 06만 보지 않고 전부를 보는 것은 그 사이 티켓이 더해질 수 있어서다. 어느 쪽이든 저장소 상태 시험(`test_이_저장소의_…`)을 돌려 판정과 맞는지 본다
- [ ] 마지막이면 같은 커밋에 셋을 싣는다. 기능 계획(`.scratch/connection-check/plan.md`)의 `**끝:**` 줄, 기능 단락(`docs/release-notes/features/connection-check.md`. 이 기능의 티켓 전부가 바꾼 제품 변경을 담고, 06이 멈출 때의 글을 바꿨으면 그것도 싣는다), `uv run python tools/plan_table.py`를 돌린 `.scratch/plan.md`다. 끊긴 뒤 이어받았거나 컨텍스트가 압축된 뒤라 끝 줄이 이미 있으면 다시 적지 않는다
- [ ] 마지막이 아니라고 보고 병합했으면, 병합 뒤 다시 `git fetch origin`으로 열려 있던 티켓이 그 사이 병합됐는지 본다. 두 PR이 같은 때 서로 마지막이 아니라고 보고 병합하면 끝 줄을 아무도 적지 않는다. dev에는 strict 보호가 없어 두 PR 모두 초록으로 병합되고, 그 뒤 dev의 push CI가 저장소 상태 시험으로 빨개진다. 그때는 끝 줄과 기능 단락을 싣는 고침 PR을 낸다. 같은 고침 PR이 이미 열렸거나 병합됐으면(`gh pr list`) 내지 않는다
