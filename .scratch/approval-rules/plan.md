# approval-rules: 운영자가 승인 규칙 파일로 도구 호출을 거부하거나 승인을 요구하거나 허용하게 정한다.
**슬라이스:** 7
**Blocked by:** skill-plugin
**끝:** 2026-11-08

운영자의 승인 규칙 파일(후보 6). 플러그인 루트의 운영자 파일에 공통 표와 에이전트별 표를 두고 도구 호출을 deny → `requires_approval`(저자) → ask → allow → 묻는다의 차례로 집행한다. deny는 모델의 도구 목록에서 빼고 직접 호출은 거부로 기록한다. 기본이 묻는다라 예시 에이전트의 allow 규칙을 함께 둔다. 운영자는 저자의 `requires_approval`을 풀지 못한다(ADR 0042 묶음 ①). 설계는 일지 2026-11-05-08, ADR 0044. 사용자가 고른 다섯: 어느 규칙이 호출을 정했는지(적용 규칙)를 두 이벤트의 선택 칸으로 남기고 트레이스 형식은 그대로(칸의 모양은 ADR 0044), 재개에서 운영자의 deny가 결정을 이김(ADR 0009 이력), 규칙 파일은 모양만 보고 이름의 실재는 보지 않음, 한 에이전트의 서버들이 같은 이름의 도구를 내면 연결 직후 실패하고 도구 명세가 서버 이름을 듦(모양은 ADR 0012 이력), 관리 API·관리 화면은 바꾸지 않음. ADR 0046이 넘긴 것: mcp-http와 둘 다 `adapters/mcp.py`를 고치므로, 나중에 병합하는 쪽이 충돌을 풀고 도구마다 싣는 서버 이름이 원격 MCP 서버의 도구에도 실리는지를 시험으로 본다. 규칙 파일은 실행을 준비할 때마다 플러그인 포트의 동기 메서드 하나로 읽는다(ADR 0012 이력). `CONTEXT.md`에 저자·승인 요구·적용 규칙이 섰다. 명세가 2026-11-05 에 섰다(`.scratch/approval-rules/spec.md`, 일지 2026-11-05-10). 명세 전에 사용자가 셋을 더 골랐다. 규칙 줄의 셋째 꼴 `<서버>:<도구>`와 allow 의 서버 필수, 승인 결정의 서버 묶음(`run_paused` 의 서버 칸과 재개의 대조), 그 에이전트의 표를 연결 뒤 대 보는 검사(ADR 0044 의 2026-11-05 이력 넷, ADR 0009 의 2026-11-05 둘째 이력). 2026-11-06 에 명세 검토를 거쳐 티켓 여섯으로 쪼갰다(`.scratch/approval-rules/issues/`, 일지 2026-11-05-11). 01 계약(트레이스의 적용 규칙·서버 칸) → 02 규칙 파일 읽기와 03 도구의 서버 이름·같은 이름 검사(나란히) → 04 호출마다의 집행 → 05 실행 전·연결 직후·재개의 검사 셋과 06 실제 모델 시험(나란히)이고, 분할은 사용자가 골랐다. 01 이 끝나(일지 2026-11-06-05) 기능이 `in-progress`가 됐고, 01 을 기다리던 02·03 이 풀렸다. 다음은 나란히 도는 02·03 이다
