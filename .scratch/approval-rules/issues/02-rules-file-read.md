# 02: 규칙 파일 읽기 — 운영자의 `rules.toml`이 core의 규칙 값이 된다

**What to build:** 운영자가 플러그인 루트(`disabled.toml`이 있는 자리)에 `rules.toml`을 두면 플러그인 포트의 동기 메서드 `read_rules()`가 그것을 core의 불변 값 `Rules`로 읽는다. 파일은 `schema_version = "1"`과 공통 표 `[common]`, 에이전트별 표 `[agents.<에이전트 이름>]`이고, 표마다 `deny`·`ask`·`allow` 문자열 배열이 있다. 규칙 줄은 세 꼴(맨 도구 이름 `add`, 서버의 모든 도구 `everything:*`, 서버에 묶인 도구 하나 `everything:add`)이고 `allow`에는 서버를 붙인 두 꼴만 쓴다. 파일이 없으면 빈 `Rules`다. 깨졌으면 `PluginError`이고 문구는 경로와 깨진 칸의 자리·오류 종류·pydantic의 문구를 들되 적힌 값을 되울리지 않는다. core에는 규칙이 도구에 맞는지와, 한 호출에 어느 규칙이 적용되는지(`AppliedRule` 다섯 가운데 하나)를 내는 순수 함수가 선다.

02는 01 뒤이고 03과 나란히 돈다. 04가 02와 03을 기다린다. 수용 기준의 고칠 자리로 대 본 03과의 겹침은 줄이 다른 여섯 파일이다. `core/ports.py`(이 티켓은 규칙 값과 `PluginSource.read_rules`, 03은 `ToolSpec.server`와 `ToolConnection.tools()`의 약속), `tests/core/test_run.py`·`tests/channel/http/test_router.py`·`tests/channel/http/test_end_user.py`(이 티켓은 가짜 플러그인 소스의 `read_rules`, 03은 가짜 연결의 서버 칸), `.claude/rules/core.md`(포트 표의 `PluginSource` 행과 `ToolSource` 행), `.claude/rules/adapters.md`(운영자 파일 항목과 MCP 어댑터 항목)다. 구현하며 겹치는 파일이 더 나와도 같다. 어느 파일이든 뒤에 병합되는 쪽이 앞의 것을 합친다.

**병합 뒤에 틈이 있다(to-tickets에서 사용자가 분할을 골랐다).** 런타임은 아직 `read_rules()`를 부르지 않는다. 그래서 운영자가 `rules.toml`을 두어도 효과가 없고, 깨진 파일도 실행을 막지 않는다. 런타임이 실행을 준비할 때마다 읽고 집행하는 것은 04다. 이 티켓이 쓰는 문장(독스트링, 주석, rules)은 틈 동안에도 참이어야 한다. 런타임이 언제 읽는지가 아니라 포트와 어댑터가 무엇을 약속하는지를 말한다.

**문구의 원천은 `spec.md`이고 ADR 0044 이력이 아니다.** ADR 0044의 2026-11-05 이력은 깨짐과 읽기 실패의 문구가 `disabled.toml`의 둘 그대로라고 적지만, 2026-11-06 명세 검토가 깨짐 문구의 둘째 줄을 값을 벗긴 꼴로 바꿨다. 이력은 기록이라 고치지 않는다. 두 문서가 어긋나 보이면 이 티켓의 "깨짐의 문구" 기준과 `spec.md`의 "깨짐과 읽기 실패의 문구"를 따른다.

근거는 `.scratch/approval-rules/spec.md`의 "파일 이름", "표와 키와 규칙 줄의 모양", "핵심의 규칙 값과 포트 메서드", "깨짐과 읽기 실패의 문구"와 그 2026-11-06 명세 검토 주석, "고칠 자리의 묶음"의 B 줄과 그 주석, Testing Decisions의 "핵심의 규칙 값"·"파일시스템 어댑터"와 그 주석이다. 앞선 결정은 ADR 0044의 "자리와 읽는 때"·"모양"·"집행의 차례"·"층과 포트"와 2026-11-05 이력 "규칙 줄에 서버에 묶인 도구 하나의 꼴이 늘고 allow는 서버를 붙인다", ADR 0012의 2026-11-05 이력(포트는 다섯 그대로), ADR 0017(운영자 파일은 어댑터가 형식을 소유한다)이다.

**Blocked by:** 01 (계약 — 트레이스의 도구 호출과 멈춤에 적용 규칙·서버 칸이 는다). 적용 규칙을 내는 함수가 01의 `AppliedRule`을 돌려주고, 계약 티켓이 그 기능의 다른 티켓을 막는다(ADR 0044 Consequences, `CLAUDE.md` 작업 규약 2)

**Status:** ready-for-agent

### core — 규칙 값과 적용 규칙

- [ ] **규칙의 값 타입은 core가 소유한다(`core/ports.py`).** 규칙 하나는 불변 값 `Rule`이고 서버(플러그인 이름 또는 없음)와 도구(이름 또는 없음)의 쌍으로 세 꼴을 나타낸다. 맨 이름은 서버 없음, `서버:*`는 도구 없음, `서버:도구`는 둘 다 있음이고 둘 다 없음은 만들 수 없다. 표 하나는 불변 값 `RuleSet`(`deny`·`ask`·`allow` 세 열), 파일 전체는 불변 값 `Rules`(공통 표 하나와 에이전트 이름 → 표의 지도)다. 규칙 값을 sdk에 두지 않는다(명세의 거부한 안)
- [ ] **규칙이 도구에 맞는지(`matches`)를 core가 낸다.** 맨 이름은 그 표가 덮는 에이전트의 모든 서버에서 그 이름의 도구에, `서버:*`는 그 서버 플러그인의 모든 도구에, `서버:도구`는 그 서버의 그 이름 도구에만 맞는다
- [ ] **`matches`와 아래 적용 규칙 함수가 받는 도구는 도구 명세(`ToolSpec`)가 아니라 서버 플러그인 이름과 도구 이름의 쌍이다.** `ToolSpec.server`는 03이 더하므로, 명세를 받게 짜면 이 티켓이 03을 기다리게 되어 둘이 나란히 돌지 못한다. 05의 마스킹과 묻기 검사도 연결 전에 매니페스트만으로 그 쌍을 안다(명세 "마스킹과 묻기의 충돌"의 "서버 이름과 도구 이름의 쌍, 매니페스트만으로 안다"). 셀프 리뷰 명세 축이 이 숨은 간선을 짚었다
- [ ] **한 호출의 적용 규칙을 내는 함수를 core가 낸다.** 차례는 운영자의 deny → 저자의 `requires_approval` → 운영자의 ask → 운영자의 allow → 아니면 `default`이고 `AppliedRule` 하나를 돌려준다. 공통 표와 에이전트 표는 목록 종류마다 합집합이라, 공통 표의 deny를 에이전트 표의 allow가 풀지 못하고 그 반대도 같다. 공개 이름으로 두고 이 티켓의 순수 함수 시험이 쓴다(04 전까지 런타임이 부르지 않아도 pyright의 쓰이지 않은 이름 경고에 걸리지 않는다는 것은 명세 검토의 어림이다. pyright로 확인한다). 05의 마스킹과 묻기 검사가 저자의 승인 요구를 뺀 차례로 이 함수를 다시 쓴다
- [ ] **순수 함수 시험을 `tests/core/`에 둔다.** 세 꼴의 맞음과 안 맞음, 공통 표와 에이전트 표의 합집합, 차례 다섯의 각 갈래, 공통 deny와 에이전트 allow가 겹치면 deny인 것과 그 반대다. 스토리 2의 "그 에이전트에만 걸린다"는 `[agents.other] deny`가 calc의 호출에 걸리지 않는 사례와, 양성 대조로 같은 줄을 `[agents.calc]`에 두면 걸리는 사례로 본다(명세 검토가 찾은 빈 자리)

### 포트와 어댑터 — `read_rules`

- [ ] **`PluginSource`에 동기 메서드 `read_rules()`가 늘고 `Rules`를 돌려준다.** 인자가 없고 파일이 없으면 빈 `Rules`(공통 표가 비고 에이전트 표가 없다)이며 실패는 `PluginError`다. `read_disabled()`와 같은 모양이고 포트는 다섯 그대로다. 파일시스템 어댑터의 읽기는 `read_disabled`처럼 교체 재시도(`_retrying`)를 지난다(명세 검토의 nit). 캐시하지 않아 부를 때마다 디스크를 읽는다
- [ ] **파일의 모양은 파일시스템 어댑터가 읽을 때 본다.** TOML 문법, 맨 위의 `schema_version = "1"`(필수), 어느 층에서든 모르는 키(`extra="forbid"`), 에이전트 이름의 플러그인 이름 패턴, 세 배열의 타입, 규칙 줄의 패턴, `allow`의 서버 필수다. 규칙 줄은 콜론이 많아야 하나이고, 콜론 앞은 플러그인 이름 패턴, 뒤는 `*` 또는 콜론과 공백이 아닌 글자 하나 이상이다. 빈 조각(`:add`, `everything:`), 콜론 둘, 공백이 든 줄, `allow`의 맨 이름은 깨진 파일이다. 콜론 뒤의 `*`는 언제나 서버의 모든 도구이고 이름이 `*`인 도구 하나만 가리키는 표기는 없다(`spec.md`가 받아들인 잔여. MCP 도구 이름 규약이 `*`를 허용 글자에서 뺀다). `everything:*`가 어떤 도구에도 맞고 `Rule`이 도구 없음으로 읽히는 것을 시험이 본다 어댑터가 문자열을 `Rule`로 바꿔 넘긴다(`read_disabled`가 이름 패턴을 보고 `PluginKey`를 만드는 것과 같은 나눔)
- [ ] **거부하지 않는 것도 단언한다.** 표가 하나도 없는 파일, 세 배열이 모두 빠진 표, 한 배열 안의 같은 줄 둘과 서로 겹치는 줄(`everything:*`와 `everything:add`), 같은 도구가 `deny`와 `allow`에 함께 적힌 것, 실재하지 않는 에이전트의 표다
- [ ] **깨짐의 문구는 `운영자 파일이 깨졌다: <경로>` 첫 줄 뒤에 오류 종류와 깨진 칸의 자리와 pydantic의 문구(`msg`)만 싣고 적힌 값을 되울리지 않는다.** 매니페스트를 읽지 못한 문구와 같은 길(`adapters/filesystem.py`의 `_describe`)이다. 그 함수는 입력 없이 뽑은 검증 오류마다 종류·자리·문구를 한 조각으로 잇는다(셀프 리뷰가 코드를 읽었다). allow의 맨 이름과 패턴을 어긴 줄은 자리(`agents.calc.allow.0`)와 종류(`string_pattern_mismatch`)로 드러난다. 까닭은 원칙 V다. 모르는 키(`api_key = "sk-ant-…"`)의 값을 pydantic의 `extra_forbidden` 문구가 그대로 싣고, 이 문구는 운영자 면 500 봉투와 서버 기록 한 줄로 나간다(명세 검토가 임시 스크립트로 손으로 봤다). 읽기 실패(열기 실패, UTF-8 아님)는 `운영자 파일을 읽을 수 없다: <경로>\n<오류>`다. `disabled.toml`의 두 문구는 바꾸지 않는다
- [ ] **어댑터 시험을 `tests/adapters/test_filesystem.py`에 둔다.** 없는 파일은 빈 `Rules`, 세 꼴 읽기, `allow`의 맨 이름 거부, 콜론 둘·빈 조각·공백 거부, 모르는 키 거부, 에이전트 이름 패턴 거부, 형식 버전 거부, UTF-8 아님, 깨짐 문구에 자리와 오류 종류가 들고 모르는 키에 심은 값은 들지 않는 것, 읽기 사이에 파일을 고치면 둘째가 새 규칙을 돌려주는 것이다. 실패를 기대하는 시험은 문구의 자리와 종류로 까닭을 단언한다(`CODING_STANDARDS.md`). 선례는 같은 파일의 `test_운영자_파일이_없으면_꺼진_것이_없다`부터 손상의 `PluginError` 경로까지의 운영자 파일 시험들이다
- [ ] **core가 어댑터와 TOML 라이브러리를 import하지 않는다.** `uv run lint-imports`가 판정한다
