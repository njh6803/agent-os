# 03: 도구가 서버 이름을 들고, 같은 이름의 도구는 연결 직후 실패한다

**What to build:** MCP 어댑터가 연결을 열며 도구마다 그 도구를 낸 서버 플러그인의 이름을 도구 명세(`ToolSpec`)의 필수 칸 `server`에 실어 넘긴다. 한 에이전트가 고른 서버 둘이 같은 이름의 도구를 내면 연결이 `같은 이름의 도구가 둘이다: <도구> (<앞서 모은 서버>, <겹친 서버>)`로 실패하고, 실행은 연결 직후 `run_failed`(원인 `tool_connection`)로 끝나며 그 메시지에 두 서버 이름이 든다(스토리 10). 지금은 뒤 서버의 도구가 앞 서버의 같은 이름 도구를 조용히 덮어 어느 서버의 도구가 돌았는지 알 수 없다.

03은 01 뒤이고 02와 나란히 돈다. 04가 02와 03을 기다린다. 02와 겹치는 파일은 02의 머리 문단에 적었다. 어느 파일이든 뒤에 병합되는 쪽이 앞의 것을 합친다.

**병합 뒤에 틈이 있다(to-tickets에서 사용자가 분할을 골랐다).** core는 아직 `ToolSpec.server`를 읽지 않는다. 규칙을 서버에 대 보는 것은 04, 재개 때 서버를 대 보는 것은 05다. 같은 이름 검사는 이 티켓에서 바로 듣는다. to-tickets 시점(main `83a66cdc`)에 저장소의 에이전트(`plugins/agents/`)와 두 e2e 꾸러미(`web/apps/widget/e2e/plugins.ts`, `web/apps/admin/e2e/stack.ts`)에서 `mcp`를 적은 에이전트는 모두 서버 하나만 고른다(Grep으로 봤다). 그래서 이 검사로 깨지는 기존 구성은 없을 것이다(어림). 이 티켓이 쓰는 문장은 틈 동안에도 참이어야 한다.

근거는 `.scratch/approval-rules/spec.md`의 "핵심의 규칙 값과 포트 메서드"의 `ToolSpec` 불릿, "같은 이름의 도구 — 검사의 자리와 문구", "고칠 자리의 묶음"의 B 줄과 그 주석, Testing Decisions의 "MCP 어댑터"와 그 2026-11-06 명세 검토 주석이다. 앞선 결정은 ADR 0044의 "같은 이름의 도구"와 ADR 0012의 2026-11-05 이력(`ToolSpec`에 서버 플러그인 이름 칸이 는다)이다.

**Blocked by:** 01 (계약 — 트레이스의 도구 호출과 멈춤에 적용 규칙·서버 칸이 는다). 계약 티켓이 그 기능의 다른 티켓을 막는다(ADR 0044 Consequences, `CLAUDE.md` 작업 규약 2)

**Status:** done

### MCP 어댑터

- [x] **도구마다 서버 플러그인 이름을 싣는다.** 길 모으기의 도구 하나가 이미 그 서버의 이름을 든다(코드를 읽었다)
- [x] **같은 이름 검사는 연결을 열며 서버들의 도구를 이름으로 모으는 자리(`adapters/mcp.py`의 `routes[route.tool.name]`)에 있다.** 같은 이름이 이미 있으면 모으기를 멈추고 던진다. 서버는 매니페스트의 순서대로 하나씩 열며 모으므로 겹친 서버 뒤의 서버는 열리지 않고, 같은 이름을 낸 서버가 셋 이상이어도 문구에는 처음 겹친 둘만 든다. 던지기 전에 이미 연 서버는 연결의 탈출 스택이 닫는 것을 본다(그 스택이 연 순서의 반대로 닫는 것은 코드를 읽었다)
- [x] **던지는 예외의 타입은 이 티켓이 정하고 내장 타입이다**(`.claude/rules/adapters.md`의 "MCP ToolSource가 던지는 예외의 타입은 내장이고 mcp의 타입으로 던지지 않는다"). core의 `run_failed.error`에는 `<타입>: ` 접두가 붙으므로(`core/run.py`의 `_describe`) 시험은 문구의 부분 일치로 본다. 연결 예외가 core에 `ExceptionGroup`으로 감싸여 오는지는 명세 검토가 보지 못했다. 아래 어댑터 시험이 core가 부르는 연결의 입구에서 정한 내장 타입 그대로를 단언해 잰다. 감싸여 나오면 그 단언이 빨개진다. 아래 core 사례는 가짜가 던지므로 감싸임을 재지 못한다(셀프 리뷰 명세 축). 앞서 연 서버의 문맥(`_opened`)이 그 안을 지나 나온 예외의 겉봉을 벗기는 길이 있다는 것은 코드를 읽었다
- [x] **어댑터 시험을 `tests/adapters/test_mcp.py`에 둔다.** `ToolSpec.server`가 서버 플러그인 이름인 것, 같은 픽스처 stdio 서버(`mcp_fixture_server.py`)를 두 플러그인 이름으로 열면 두 이름을 든 예외인 것, 서버 하나는 그대로 열리는 것(양성 대조)이다. 같은 이름의 예외는 예외 그룹이 아니라 정한 내장 타입 그대로 나오는 것을 단언한다(위 불릿). 같은 `McpServer`를 두 `PluginName`으로 넘기면 같은 이름을 만들 수 있다(명세 검토가 `_fixture_connection`을 읽었다). 선례는 같은 파일의 `test_서버의_도구_목록과_입력_스키마를_준다`와 연결 오류 시험들이다

### core — 메시지가 트레이스까지

- [x] **두 서버 이름이 트레이스까지 가는 것(스토리 10)을 core 사례 하나가 잰다.** 그 문구로 던지는 가짜 도구 소스를 core에 꽂아 원인 `tool_connection`과 메시지의 부분 일치를 본다(명세 검토의 nit). 연결에 들어가는 동안의 예외를 `tool_connection`으로 받는 길은 지금 그대로다(`.claude/rules/core.md` 실패 정책)

### 생성자 — 포트 적합성

- [x] **`ToolSpec`을 만드는 자리가 `server`를 채운다.** to-tickets 시점에 생성자는 세 시험 파일의 넷(`tests/core/test_run.py` 1, `tests/channel/http/test_router.py` 2, `tests/channel/http/test_end_user.py` 1), MCP 어댑터, 이 기능의 프로브 `.scratch/approval-rules/probes/all_deny_resume_call.py`의 `ADD`다(명세 검토가 Grep으로 셌다). 프로브는 점 디렉터리라 pyright가 검사 없이 0 errors를 낸다(`docs/constitution/operations.md` 환경 규약 상세). 그래서 고친 뒤 그 파일을 `__main__`이 아닌 모듈로 불러들여 `ADD`가 만들어지는 것만 보고, 측정(`main`)은 돌리지 않는다. 그대로 돌리면 키가 있을 때 API를 여섯 번 다시 부르고 키가 없을 때 `측정 아님`으로 끝난다(셀프 리뷰 명세 축). 측정은 끝나 결과를 다시 쓰지 않는다. 지난 기능의 프로브는 그때의 측정 기록이라 고치지 않는다
- [x] **세 시험 파일의 가짜 연결은 도구마다 서버 이름을 들고, 적지 않으면 기본 서버 이름 하나를 쓴다.** 04가 가짜 플러그인 소스의 기본 규칙(공통 표 allow에 자기 서버 전부와 이 기본 서버의 `<서버>:*`)을 이 이름에 맞춰 넣는다(명세의 "예시 규칙 파일과 시험 자리의 규칙 파일" 주석). core·router·end_user의 세 가짜가 같은 규약을 쓴다
