# approval-rules 명세: 운영자의 규칙 파일을 도구 호출마다 집행한다

Status: ready-for-agent

운영자가 플러그인 루트에 둔 규칙 파일(`rules.toml`)로 도구 호출을 막고(deny), 묻고(ask), 묻지 않고 허락하는(allow) 기능의 명세다. 설계는 일지 2026-11-05-08과 ADR 0044, 그리고 ADR 0009·0012·0017·0019·0041의 2026-11-04·05 이력이 정했고, 이 명세는 그 결정을 바꾸지 않고 이름과 문구와 자리를 채운다. 이 명세는 `/to-spec approval-rules`로 새 세션에서 썼고 설계 인터뷰를 다시 열지 않았다(일지 2026-11-05-10).

**넘겨받은 것은 열둘이다.** (1) 규칙 파일은 플러그인 루트의 운영자 파일이고 `disabled.toml`과 같은 규칙으로 읽는다. 실행을 준비할 때마다 한 번 읽고 캐시하지 않으며, 없으면 규칙이 없는 것이고, 깨졌으면 `PluginError`(운영자 면 500, 최종 사용자 면 고정 문구 500)다(ADR 0044 "자리와 읽는 때", ADR 0017의 2026-11-04 이력). (2) 모양은 공통 표 하나와 에이전트별 표이고, 표마다 `deny`·`ask`·`allow` 세 문자열 배열이다(ADR 0044 "모양"). (3) 집행의 차례는 운영자의 deny → 저자의 승인 요구(`requires_approval`) → 운영자의 ask → 운영자의 allow → 적힌 규칙이 없으면 묻는다이고, 운영자는 저자의 승인 요구를 풀지 못한다(ADR 0044 "집행의 차례", ADR 0042). (4) deny는 모델의 도구 목록에서 그 도구를 빼고, 에이전트의 직접 호출과 모델이 이름으로 부른 호출은 `tool_called(ok=false)`로 기록하며 실행은 계속된다. ask와 묻는다는 `run_paused`로 멈추고 allow는 그냥 부른다(ADR 0044 "집행의 차례"). (5) 어느 규칙이 호출을 정했는지(용어집의 **적용 규칙**, 값 다섯)가 `tool_called`와 `run_paused`의 선택 칸 하나에 남고 트레이스 형식은 3 그대로다. 계약 파일과 생성 TS 타입과 관리 화면의 필드 이름 표가 바뀌고 칸의 이름은 다른 이벤트의 필드 이름과 겹치지 않는다(ADR 0044 "기록", `.claude/rules/sdk.md`). (6) 재개도 준비 단계에서 지금 디스크의 규칙을 읽어 집행하고, 멈춘 사이 deny가 된 도구는 결정이 승인이어도 부르지 않고 거부로 기록한다. 결정이 멈춘 호출에 묶이는 것과 다른 호출이면 `run_resumed` 없이 `run_failed`로 끝나는 것은 그대로다(ADR 0044 "재개", ADR 0009의 2026-11-05 이력). (7) 한 에이전트의 연결에 같은 이름의 도구가 둘 이상이면 연결 직후 `run_failed`(원인 `tool_connection`)이고, 어댑터가 도구마다 그 도구를 낸 서버 플러그인의 이름을 `ToolSpec`에 실어 넘긴다(ADR 0044 "같은 이름의 도구", ADR 0012의 2026-11-05 이력). (8) 규칙 파일은 `PluginSource`의 동기 메서드 하나로 읽고 포트는 다섯 그대로다(ADR 0044 "층과 포트", ADR 0012의 2026-11-05 이력). (9) 관리 API와 관리 화면은 필드 이름 표의 줄 외에 바꾸지 않고 규칙 파일을 고치는 화면은 없다(ADR 0044 "범위 밖"). (10) 전역 `*`와 인자 패턴은 없고, 저자의 승인 요구가 가리키는 도구가 실재하는지 보는 지금의 검사는 deny로 빼기 전의 전체 목록에 대 본다(ADR 0044 "모양"·"집행의 차례"). (11) 기본이 묻는다라 저장소의 calc와 e2e·테스트가 allow 규칙 파일을 함께 둔다(ADR 0042 묶음 ①, ADR 0044 "치르는 값"). (12) 구현 티켓이 코드와 같은 티켓에서 고치는 하네스 문서는 ADR 0044 Consequences의 목록이고, 거기에 일지 2026-11-05-08 "다음"의 둘(`.claude/rules/core.md` 재개 항목의 "같은 호출이면 정책이 바뀌었어도 적용한다"를 저자의 승인 요구로 좁히는 것, `.claude/rules/sdk.md` 선택 필드 항목에 옛 판이 새 칸이 든 줄을 거부하는 비대칭을 적는 것)이 든다.

**넷은 사용자가 이 명세를 쓰며 골랐다.** 규칙 줄의 셋째 꼴 `<서버>:<도구>`를 더하고 allow에는 서버를 꼭 붙이는 것("표와 키와 규칙 줄의 모양"), 승인 결정을 서버에도 묶는 것("서버 칸과 재개의 대조"), 그 에이전트의 표에 적힌 이름을 연결 뒤 대 보는 것("에이전트 표의 검사"), 시험을 붙이는 자리(Testing Decisions의 "이음매"). 고른 라벨과 설명의 원문은 일지 2026-11-05-10이다.

**열여덟은 명세가 넘겨받은 것 안에서 스스로 정했고 각 절 제목의 괄호에 "명세가 정했다"로 표시한다.** 파일 이름, 규칙 줄의 패턴, 핵심의 규칙 값과 포트 메서드의 모양, 깨짐과 읽기 실패의 문구, 게이트의 차례와 연결 목록에 없는 이름의 호출, 모델의 도구 목록을 거르는 자리, 거부 문구, 적용 규칙 칸의 이름과 값, 결정이 적용된 호출의 적용 규칙, 두 칸의 런타임 전용, 서버 칸의 이름과 대조 문구와 없는 이름의 처리, 같은 이름 검사의 자리와 문구, 에이전트 표 검사의 자리와 문구, 마스킹과 묻기의 충돌, 모두 deny인 재개의 처리, 예시 규칙 파일의 내용, 고칠 자리의 묶음, 실제 모델 시험 하나의 모양. 그 가운데 "마스킹과 묻기의 충돌"은 설계가 묻지 않은 자리를 이 명세가 코드를 읽어 찾은 것이다.

**이력은 다섯이다.** ADR 0044의 2026-11-05 이력 넷("규칙 줄에 서버에 묶인 도구 하나의 꼴이 늘고 allow는 서버를 붙인다", "승인 결정은 서버에도 묶인다", "그 에이전트의 표는 연결 뒤 대 본다", "명세가 정한 것과 잰 것")과 ADR 0009의 2026-11-05 둘째 이력("재개의 일치 검사는 서버도 본다"). 이력은 이 명세와 같은 커밋에서 초안을 쓰고 사용자가 승인한다(작업 규약 5).

**거부한 안은 마흔여덟이고 각 절의 "거부한 안:" 표시에 있다.**

측정은 `.scratch/approval-rules/probes/`의 하나(`all_deny_resume_call.py`)이고 결과는 그 `README.md`다. 이 명세에서 "쟀다"는 그것을 가리키고, 코드를 읽은 것과 어림은 그렇게 적는다.

## Problem Statement

운영자 관점. 지금 도구 호출을 멈추는 길은 저자가 매니페스트에 적은 `requires_approval` 하나다. 운영자는 배치에서 어떤 도구를 아예 막거나(deny), 저자가 요구하지 않은 도구에도 승인을 요구하거나(ask), 반대로 묻지 않고 돌릴 도구(allow)를 정할 수 없고, 정하려면 저자의 매니페스트를 고쳐야 한다. 호출이 왜 그냥 돌았는지, 왜 멈췼는지가 트레이스에 남지 않아 운영자가 뒤에 규칙을 대 볼 수 없다. 한 에이전트가 고른 서버 둘이 같은 이름의 도구를 내면 뒤 서버가 앞 서버를 조용히 덮어(`adapters/mcp.py`의 도구 이름으로 모은 길, ADR 0044) 어느 서버의 도구가 돌았는지 알 수 없다. 승인 결정은 도구 이름과 인자에만 묶여, 멈춘 사이 서버 목록이 바뀌면 같은 이름의 다른 서버 도구에 승인이 적용된다(PR 469의 CodeRabbit이 Major로 짚었다, 일지 2026-11-05-08). 저자 관점. 운영자가 자기 승인 요구를 풀 수 있으면 매니페스트의 약속이 서지 않는다. 최종 사용자 관점. 운영자가 막은 도구를 모델이 부르려 할 때 실행이 죽지 않고 모델이 거부를 알고 이어 가야 한다.

## Solution

운영자가 플러그인 루트에 `rules.toml`을 둔다. 파일은 `schema_version = "1"`과 공통 표 `[common]`, 에이전트별 표 `[agents.<에이전트 이름>]`로 되고, 표마다 `deny`·`ask`·`allow` 문자열 배열이 있다. 규칙 줄은 세 꼴이다. 맨 도구 이름(`add`), 서버의 모든 도구(`everything:*`), 서버에 묶인 도구 하나(`everything:add`). allow에는 서버를 붙인 두 꼴만 쓴다. 런타임은 실행을 준비할 때마다 이 파일을 읽어 그 실행의 모든 도구 호출을 deny → 저자의 승인 요구 → ask → allow → 묻는다의 차례로 집행하고, 어느 규칙이 정했는지를 `tool_called`와 `run_paused`의 선택 칸 `rule`에 남긴다. deny에 맞는 도구는 모델의 도구 목록에서 빠지고 부르면 `운영자가 거부했다: <서버>:<도구>`로 거부된다. `run_paused`는 멈춘 도구의 서버도 선택 칸 `server`에 들고, 재개는 이름·인자·서버가 모두 같을 때만 결정을 적용하되 운영자의 deny는 결정을 이긴다. 어댑터는 연결을 열며 같은 이름의 도구가 둘 이상이면 던지고 도구마다 서버 이름을 넘긴다. 그 에이전트의 표에 적힌 도구와 서버가 연결에 없으면 연결 직후 실패한다. 저장소는 calc를 위한 예시 `plugins/rules.toml`을 두고 e2e·테스트의 플러그인 루트도 allow 규칙 파일을 둔다.

## User Stories

1. As an 운영자, I want `rules.toml`의 공통 표에 `deny = ["everything:send_mail"]`을 적으면 모든 에이전트에서 그 도구가 모델의 도구 목록에서 빠지고 부르면 거부되기, so that 저자의 매니페스트를 고치지 않고 배치에서 도구를 막는다.
2. As an 운영자, I want 에이전트별 표 `[agents.calc]`의 규칙이 그 에이전트에만 걸리고 공통 표와는 목록 종류(deny·ask·allow)의 차례로만 겹치기, so that 에이전트마다 다른 규칙을 한 파일에 둔다.
3. As an 운영자, I want 규칙 파일을 고친 것이 다음 실행과 다음 재개부터 듣기, so that 서버를 다시 띄우지 않고 규칙을 바꾼다.
4. As an 운영자, I want 규칙 파일이 깨졌을 때 운영자 채널의 500 메시지에 경로와 검증 오류가 적히고 실행이 시작되지 않기, so that 깨진 규칙으로 도구가 조용히 열리거나 막히지 않는다.
5. As an 운영자, I want allow에 맨 도구 이름을 적으면 파일이 깨진 것으로 거부되기, so that 다른 서버가 같은 이름의 도구를 가져와도 그것이 뜻밖에 열리지 않는다.
6. As an 운영자, I want 에이전트 표에 적은 도구나 서버가 그 에이전트의 연결에 없으면 연결 직후 `run_failed`(원인 `tool_connection`)로 알리기, so that deny의 오타가 allow 뒤에 숨어 그 도구를 묻지 않고 돌리지 않는다.
7. As an 운영자, I want 트레이스의 `tool_called`와 `run_paused`에서 그 호출을 정한 규칙(`rule`)을 보기, so that 왜 그냥 돌았는지와 왜 멈췼는지를 뒤에 대 본다.
8. As an 운영자, I want 멈춘 실행의 `run_paused`에 서버 이름(`server`)이 있고 재개 때 그 도구가 다른 서버에서 오면 재개 불일치로 끝나기, so that 승인이 내가 본 그 서버의 그 도구에만 적용된다.
9. As an 운영자, I want 멈춘 사이 deny로 바꾼 도구는 승인자가 승인해도 불리지 않고 거부로 기록되기, so that 운영자의 deny를 누구의 결정으로도 넘지 못한다.
10. As an 운영자, I want 한 에이전트가 고른 서버 둘이 같은 이름의 도구를 내면 연결 직후 서버 둘의 이름을 든 `run_failed`로 알리기, so that 어느 서버의 도구가 돌았는지 모르는 채 규칙이 걸리지 않는다.
11. As an 운영자, I want 마스킹할 인자가 있는 도구를 규칙이 묻게(ask나 적힌 규칙 없음) 두면 실행 전에 그 도구와 고칠 길을 든 오류를 받기, so that 승인 뒤 마스킹된 값이 도구에 가는 실패를 실행 중에 만나지 않는다.
12. As a 저자, I want 매니페스트의 `requires_approval`이 운영자의 allow보다 먼저 집행되기, so that 내가 적은 승인 요구를 운영자가 풀지 못한다.
13. As a 저자, I want 내 에이전트가 `ctx.tool()`로 deny된 도구를 부르면 `ToolError`로 거부 문구를 받고 실행은 계속되기, so that 거부를 알고 다른 길로 간다.
14. As a 저자, I want 연결에 없는 이름으로 `ctx.tool()`을 부르면 묻지 않고 `도구가 없다: <이름>`으로 거부되기, so that 없는 도구를 승인하라고 사람에게 묻지 않는다.
15. As a 저자, I want 내가 `yield`한 `tool_called`·`run_paused`에 `rule`이나 `server`를 채우면 실행이 `run_failed`(원인 `agent_code`)로 끝나기, so that 내 코드가 운영자의 규칙을 사칭한 기록을 남길 수 없다.
16. As a 최종 사용자, I want 운영자가 막은 도구를 모델이 부르려 할 때 실행이 죽지 않고 모델이 거부를 알고 답하기, so that 막힌 도구 때문에 대화가 끊기지 않는다.
17. As a 최종 사용자, I want 깨진 규칙 파일 때문에 실행이 거부될 때 고정 문구의 500을 받기, so that 서버 안쪽의 파일 경로가 밖으로 새지 않는다.
18. As a 저장소 기여자, I want 포트가 다섯 그대로이고 가짜 플러그인 소스에 규칙을 꽂아 core를 시험하기, so that 시험이 빠르고 결정적이다.
19. As a 저장소 기여자, I want 저장소의 `plugins/rules.toml`로 calc와 `-m llm` 시험이 기본 묻는다에서 멈추지 않기, so that 기존 예시와 시험이 그대로 돈다.
20. As a 저장소 기여자, I want 실제 모델 시험 하나가 모두 deny가 된 재개를 끝까지 돌리기, so that 도구 정의 없는 모델 호출을 API가 받는다는 측정이 실제 재개 길에서도 서는 바깥 증거가 있다.

## Implementation Decisions

구현 파일의 경로와 코드 조각은 새로 짓지 않는다. 규칙 문서·ADR·테스트 선례의 경로와 ADR 0044가 이미 든 구현 경로는 옮겨 적는다. 아래 TOML은 운영자가 쓰는 파일의 보기이고 코드가 아니다.

### 자리와 읽는 때 (넘겨받았다)

규칙 파일은 플러그인 루트(`disabled.toml`이 있는 자리)의 운영자 파일이다. 런타임은 실행과 재개를 준비할 때마다 한 번 읽고 캐시하지 않는다. 읽는 자리는 준비 순서의 깨짐 묶음 가운데 "운영자 파일의 손상"이고 꺼진 집합(`disabled.toml`)을 읽는 자리와 같다(`.claude/rules/core.md` 준비 순서). 파일이 없으면 규칙이 없는 것이고 모든 호출이 저자의 승인 요구와 묻는다로만 집행된다. 깨졌으면 실행 식별자가 생기기 전의 `PluginError`라 트레이스가 없다. 운영자 채널은 500에 원문을, 최종 사용자 면은 고정 문구의 500을 낸다(`.claude/rules/http.md`의 500 갈래). 관리 API는 이 파일을 쓰지 않는다. (2026-11-06 명세 검토: 두 운영자 파일과 마스킹 검사의 차례를 정한다. 깨짐 묶음의 "운영자 파일의 손상"에서 규칙 파일을 먼저 읽고 꺼진 집합을 이어 읽으며, 그 뒤가 아래 "마스킹과 묻기의 충돌"이고, 그다음이 꺼짐 판정이다. 지금은 꺼진 집합의 읽기와 판정이 한 호출(`_reject_disabled(plugins.read_disabled(), …)`)이라 C가 둘을 가른다(`core/run.py`의 `_prepare`를 읽었다). 두 파일이 모두 깨졌으면 규칙 파일의 문구가 나오고, 규칙 파일이 멀쩡한데 마스킹과 묻기의 충돌과 꺼진 집합의 손상이 함께 있으면 꺼진 집합의 손상이 나온다. 파일 하나의 손상은 두 파일의 내용을 맞대는 검사보다 먼저 보여야 운영자가 고칠 파일을 바로 안다. 시험은 결함 둘을 함께 심어 이 두 쌍을 본다.)

### 파일 이름 (명세가 정했다)

`rules.toml`이다. 용어집의 **규칙 파일(Rules File)**과 ADR 0042의 "운영자 파일은 둘이 는다"(규칙 파일과 서버 파일)에 맞춘 이름이고, 뒤에 올 서버 파일은 `servers.toml`이 자연스럽다(mcp-trust가 정한다). 거부한 안: **`approval.toml`.** 이 파일은 승인만 아니라 deny도 적으므로 이름이 좁다. 거부했다. **`policy.toml`.** 용어집에 정책이라는 말이 없고 규칙 파일이 이미 용어다. 거부했다.

### 표와 키와 규칙 줄의 모양 (넘겨받았다. 셋째 꼴과 allow의 서버는 사용자가 골랐다. 키 이름과 패턴은 명세가 정했다)

```toml
schema_version = "1"

[common]
deny = ["everything:send_mail", "rm"]
ask = ["everything:write_file"]
allow = ["everything:*"]

[agents.calc]
allow = ["everything:add"]
```

- 맨 위에 `schema_version = "1"`이 필수다(`disabled.toml`과 같다). 공통 표는 `[common]`, 에이전트별 표는 `[agents.<에이전트 이름>]`이다. 에이전트 이름은 플러그인 이름 패턴이어야 하고, 그 에이전트가 실재하는지는 보지 않는다(아래 "에이전트 표의 검사"는 그 에이전트가 돌 때 그 표만 본다). 표마다 `deny`·`ask`·`allow`는 모두 선택이고 기본은 빈 배열이다. 모르는 키는 어느 층에서든 거부한다(`extra="forbid"`, `disabled.toml`과 같다). 공통 표도 에이전트 표도 없어도 된다.
- 규칙 줄은 세 꼴이다(ADR 0044의 둘에 사용자가 고른 셋째가 더해졌다). **맨 도구 이름**(`add`)은 그 표가 덮는 에이전트의 모든 서버에서 그 이름의 도구에 맞는다. **서버의 모든 도구**(`everything:*`)는 그 서버 플러그인의 모든 도구에 맞는다. **서버에 묶인 도구 하나**(`everything:add`)는 그 서버의 그 이름 도구에만 맞는다. 콜론은 많아야 하나이고, 콜론 앞은 플러그인 이름 패턴, 뒤는 `*` 또는 도구 이름이다. 도구 이름의 글자는 콜론과 공백이 아닌 글자 하나 이상이다. 도구 이름의 글자 집합을 더 좁히지 않는 이유는 규칙 줄의 도구 이름이 ADR 0044 "모양"의 "도구 이름 그대로", 곧 MCP 서버가 정한 이름 그대로여야 하기 때문이다. 빈 조각(`:add`, `everything:`), 콜론 둘, 공백이 든 줄은 깨진 파일이다. 콜론 뒤의 `*`는 언제나 서버의 모든 도구이고, 이름이 `*`인 도구 하나만 가리키는 표기는 없다. MCP의 도구 이름 규약이 허용 글자를 영문자·숫자·`_`·`-`·`.`로 정하므로(규약의 SHOULD, 2025-11-25판을 읽었다) `*`라는 이름의 도구는 규약 밖이고, 그런 도구가 있어도 `서버:*`에 함께 들어갈 뿐 따로 풀거나 막을 길이 없는 것을 받아들인다.
- **allow에는 서버를 붙인 두 꼴만 쓴다.** `allow`에 맨 도구 이름이 있으면 깨진 파일이다. 열어 주는 규칙은 넓게 맞으면 뜻밖의 도구가 열리므로 정확해야 하고, 막는 deny와 묻는 ask는 넓게 맞아도 안전한 쪽이라 맨 이름을 받는다(사용자가 골랐다, 일지 2026-11-05-10).
- 한 배열 안의 같은 줄 둘과 서로 겹치는 줄(`everything:*`와 `everything:add`)은 거부하지 않는다. 효과가 같거나 포함 관계라 해석이 갈리지 않는다. 같은 도구가 `deny`와 `allow`에 함께 적힌 것도 거부하지 않는다. 집행의 차례가 deny를 먼저 보므로 뜻이 하나다.
- 공통 표와 에이전트 표는 목록 종류마다 합집합이다. 어느 표에 적혔는지는 차례에 들지 않고, deny → 승인 요구 → ask → allow의 차례만 있다. 그래서 공통 표의 deny를 에이전트 표의 allow가 풀지 못하고, 에이전트 표의 deny를 공통 표의 allow가 풀지 못한다.

거부한 안: **에이전트 표가 공통 표를 덮어쓴다(가까운 표 우선).** 운영자가 공통 deny를 에이전트 allow로 풀 수 있게 되어 공통 표가 배치의 하한이 되지 못한다. 거부했다. **`[agent.calc]`(단수).** 매니페스트의 종류 폴더가 `agents/`라 복수와 맞춘다. 거부했다. **키를 한국어로.** 매니페스트의 키가 영어이고 이 파일만 다르면 운영자가 두 규약을 익힌다. 거부했다. **에이전트 이름의 실재를 읽을 때 본다.** 운영자 파일은 매니페스트 목록을 모르는 채 읽히고(`read_disabled`는 디렉터리 없는 이름도 집합에 둔다, `.claude/rules/adapters.md`), 이름이 틀린 표는 어느 실행에도 걸리지 않는다. allow의 오타는 기본이 묻는다라 뜻밖에 묻는 데서 그치지만, deny의 오타는 조용히 효력이 없고 같은 도구에 맞는 공통 allow가 있으면 묻지 않고 돈다. 아래 "에이전트 표의 검사"도 표가 걸리는 에이전트가 돌 때만 돌아 표 이름의 오타는 닫지 못한다(ADR 0044 "모양"이 받아들인 잔여 위험이다). 거부했다. **도구 이름을 Anthropic API의 도구 이름 규칙(영숫자·밑줄·하이픈)으로 좁힌다.** MCP 서버가 다른 글자(점 등)를 쓰면 그 도구에 규칙을 적을 수 없게 된다. 거부했다. **같은 배열의 겹친 줄을 거부한다.** 매니페스트 `skills`의 중복 거부는 순서가 뜻을 갖는 자리의 규칙이고 규칙 배열은 집합이다. 거부했다.

### 핵심의 규칙 값과 포트 메서드 (명세가 정했다)

- 핵심(`core/ports.py`)이 규칙의 값 타입을 소유한다. 규칙 하나는 불변 값 `Rule`이고 서버(플러그인 이름 또는 없음)와 도구(이름 또는 없음)의 쌍으로 세 꼴을 나타낸다. 맨 이름은 서버 없음, `서버:*`는 도구 없음, `서버:도구`는 둘 다 있음이고 둘 다 없음은 만들 수 없다. 표 하나는 불변 값 `RuleSet`(`deny`·`ask`·`allow` 세 열)이고 파일 전체는 불변 값 `Rules`(공통 표 하나와 에이전트 이름 → 표의 지도)다. 규칙이 도구에 맞는지(`matches`)와 한 호출의 적용 규칙을 내는 함수(차례를 적용해 다섯 값 가운데 하나를 돌려준다)는 핵심에 있다. 집행은 핵심의 것이다.
- `PluginSource`에 동기 메서드 `read_rules()`가 늘고 `Rules`를 돌려준다. 파일이 없으면 빈 `Rules`(공통 표가 비고 에이전트 표가 없다)다. 인자가 없고 실패는 `PluginError`다. `read_disabled()`와 같은 모양이고 `.claude/rules/core.md`의 포트 표 `PluginSource` 행에 든다.
- 파일의 모양(TOML 문법, 형식 버전, 모르는 키, 에이전트 이름 패턴, 세 배열의 타입, 규칙 줄의 패턴, allow의 서버 필수)은 파일시스템 어댑터가 읽을 때 본다. 어댑터가 문자열을 `Rule`로 바꿔 핵심의 값으로 넘긴다. `read_disabled`가 이름 패턴을 보고 `PluginKey`를 만드는 것과 같은 나눔이다.
- `ToolSpec`에 그 도구를 낸 서버 플러그인의 이름 칸 `server`가 늘고 필수다(ADR 0012의 2026-11-05 이력). 테스트의 가짜 도구 연결과 프로브 `probes/all_deny_resume_call.py`의 `ADD`도 이 칸을 채운다.

거부한 안: **규칙을 문자열 그대로 핵심에 넘기고 집행할 때마다 가른다.** 깨진 줄이 읽을 때가 아니라 첫 호출에서 드러나고, 가르는 코드가 호출마다 돈다. 거부했다. **`read_rules(agent)`로 그 에이전트의 몫만 돌려준다.** 공통 표와 에이전트 표를 합치는 규칙이 어댑터로 샌다. 거부했다. **규칙 값을 sdk에 둔다.** 플러그인이 규칙을 읽을 일이 없고 운영자 파일의 형식은 어댑터가 소유한다(ADR 0017). 거부했다.

### 깨짐과 읽기 실패의 문구 (명세가 정했다)

- 깨짐은 `운영자 파일이 깨졌다: <경로>\n<검증 오류>`이고 읽기 실패(열기 실패, UTF-8 아님)는 `운영자 파일을 읽을 수 없다: <경로>\n<오류>`다. `disabled.toml`의 두 문구 그대로이고 경로가 파일을 가른다. 검증 오류는 pydantic 문구의 전문이고 입력 값이 든다. 운영자 파일의 손상 문구는 매니페스트 문구가 값을 벗기는 보호의 밖이다(`.claude/rules/adapters.md`의 "운영자 파일(`disabled.toml`)의 손상 문구는 이 보호 밖이고 검증 오류 전문을 싣는다". `disabled.toml`의 깨짐 문구가 오류를 그대로 싣는 것은 코드를 읽었다). 규칙 줄의 값은 도구 이름과 서버 이름이라 비밀이 아니고, 운영자 파일의 규칙을 둘로 나누지 않는다.
- allow의 맨 이름과 패턴을 어긴 줄은 pydantic의 패턴 위반으로 드러나므로 문구에 어느 배열의 몇째 줄인지(`agents.calc.allow.0`)와 그 줄의 값이 든다.

(2026-11-06 명세 검토: 값을 벗기는 쪽으로 바꾼다. "규칙 줄의 값은 비밀이 아니다"는 모르는 키의 값을 덮지 못한다. `[agents.calc]`에 `api_key = "sk-ant-…"`를 적으면 pydantic의 `extra_forbidden` 문구가 그 값을 `input_value`로 싣는다(검토 서브에이전트가 임시 스크립트로 손으로 봤다). 이 문구는 운영자 면 500 봉투와 서버 기록 한 줄로 나가 원칙 V("이벤트와 로그에 API 키, 토큰, 비밀번호를 싣지 않는다")에 닿는다. 그리고 `disabled.toml`이 전문을 싣는 것은 받아들인 결정이 아니라, 매니페스트 문구를 닫은 티켓의 범위 밖이라 닫지 않은 잔여다(`.claude/rules/adapters.md`의 그 항목을 읽었다). 그래서 깨짐 문구의 둘째 줄은 매니페스트를 읽지 못한 문구와 같은 길(`adapters/filesystem.py`의 `_describe`)로 오류 종류와 칸의 자리와 pydantic의 문구(`msg`)만 싣고 값을 되울리지 않는다(셀프 리뷰가 `_describe`를 읽어 문구의 셋째 조각을 바로잡았다). 첫 줄 `운영자 파일이 깨졌다: <경로>`와 읽기 실패의 문구는 그대로다. allow의 맨 이름과 패턴을 어긴 줄은 자리(`agents.calc.allow.0`)와 오류 종류(`string_pattern_mismatch`)로 드러나고 그 줄의 값은 싣지 않는다. 아래 거부한 안의 "검증 오류에서 값을 벗긴다"를 받아들인 것이다. `disabled.toml`의 문구는 이 기능이 바꾸지 않는다.)

거부한 안: **`규칙 파일이 깨졌다`로 문구를 따로 둔다.** 운영자 파일의 문구가 둘이 되고 경로가 이미 가른다. 거부했다. **검증 오류에서 값을 벗긴다(매니페스트 문구처럼).** 운영자 파일의 선례(`disabled.toml`)는 전문을 싣고, 이 파일만 벗기면 운영자 파일의 문구 규약이 둘이 된다. 규칙 줄의 값은 비밀이 아니라 벗길 까닭도 없다. 거부했다.

### 집행의 차례와 게이트의 자리 (넘겨받았다. 연결 목록에 없는 이름은 명세가 정했다)

승인 게이트는 컨텍스트가 도구를 부르는 한 자리(`core/run.py`의 `_Context._call`)이고 루프의 호출과 에이전트의 직접 호출이 같이 지난다(ADR 0009, `.claude/rules/core.md`). 이 기능이 그 자리를 다음 차례로 만든다.

1. 멈춘 실행이면 더 가지 않는다. 인자를 마스킹한다. 재생 구간이면 기록을 돌려준다(그대로다).
2. 결정이 있으면 멈춘 호출과 같은 호출인지 본다. 같은 호출은 같은 도구 이름, 같은 마스킹된 인자, 그리고 멈춤 기록에 서버 칸이 있고 지금 연결에 그 이름의 도구가 있으면 같은 서버다(아래 "서버 칸과 재개의 대조". 그 이름의 도구가 없으면 서버를 대 보지 않고 3이 거부한다). 다르면 결정을 적용하지 않고 `run_resumed` 없이 `run_failed`(원인 `resume_mismatch`)다(그대로다. 서버가 늘었다).
3. **연결 목록에 없는 이름이면 게이트에 들지 않고 거부한다.** 결과는 `tool_called(ok=false)`, 내용은 어댑터가 쓰던 문구 그대로 `도구가 없다: <이름>`, 적용 규칙 칸은 없음(`null`)이다. 루프에서는 모델에 돌아가고 직접 부른 에이전트는 `ToolError`다. 결정이 있었으면 소비되어 버려진다(멈춘 사이 그 도구를 낸 서버가 매니페스트에서 빠진 재개가 이 경우다). 소비는 지금처럼 `run_resumed` 기록과 함께 2 바로 뒤이고, 이 거부와 5의 거부는 그 뒤에 온다(`_Context._call`의 `_take_verdict`와 `_resume`의 차례. 코드를 읽었다). 없는 도구를 사람에게 승인하라고 묻지 않기 위해서다. 지금은 이 호출이 어댑터의 `LookupError`를 `_call_safely`가 바꾼 `LookupError: 도구가 없다: <이름>`의 실패 결과가 되는데(코드를 읽었다) 기본이 묻는다가 되면 게이트가 먼저 멈춰 버리므로 자리를 게이트 앞으로 옮기고, 내용은 예외 타입의 접두 없이 어댑터의 문구만 싣는다.
4. 적용 규칙을 낸다. 운영자의 deny에 맞으면 **deny**, 저자의 `requires_approval`에 들면 **requires_approval**, ask에 맞으면 **ask**, allow에 맞으면 **allow**, 아니면 **default**(적힌 규칙 없음, 묻는다)다. 공통 표와 에이전트 표를 합쳐 본다.
5. deny면 도구를 부르지 않고 `tool_called(ok=false, rule="deny")`에 거부 문구를 담아 기록하고 실행은 계속된다. 결정이 있어도 같다(운영자의 deny가 결정을 이긴다, ADR 0009의 2026-11-05 이력).
6. requires_approval·ask·default면 결정이 없을 때 `run_paused(rule=<그 값>, server=<서버>)`로 멈춘다. 결정이 있으면 승인은 부르고 거부는 `tool_called(ok=false)`에 `승인자가 거부했다: <사유>`를 담아 기록한다(그대로다).
7. allow면 결정이 없을 때 그냥 부른다. 결정이 있으면(멈춘 사이 ask가 allow로 바뀐 재개) 6과 같이 적용한다. 승인은 부르고 거부는 `tool_called(ok=false)`에 `승인자가 거부했다: <사유>`를 담아 기록하며, 칸은 아래 "결정이 적용된 호출의 적용 규칙"대로 멈춘 까닭을 든다(ADR 0044 "재개"가 그 밖의 변화는 지금 규칙대로 결정을 적용한다고 정했다).
8. 마스킹된 인자가 실제 도구에 가려는 것을 막는 검사와 호출과 기록은 그대로다.

거부한 안: **연결 목록에 없는 이름도 게이트를 지나 묻는다.** 없는 도구의 승인을 사람에게 묻고, 승인 뒤 어댑터가 `도구가 없다`로 실패한다. 거부했다. **없는 이름을 `run_failed`로 끝낸다.** 도구 에러는 모델에 되돌려 계속하는 것이 실패 정책이고(`.claude/rules/core.md`), 지금도 실패 결과로 계속된다. 거부했다. **없는 이름의 기록에 적용 규칙 `deny`를 적는다.** 운영자가 막은 것이 아니다. 거부했다.

### 모델의 도구 목록 (넘겨받았다. 거르는 자리는 명세가 정했다)

컨텍스트가 모델을 부를 때마다 연결의 도구 목록을 읽어 모델에 붙이는 자리(`_Context.llm`, 코드를 읽었다)에서, 운영자의 deny에 맞는 도구를 빼고 붙인다. 공통 표와 에이전트 표를 합쳐 본다. 저자의 승인 요구와 ask에 맞는 도구는 그대로 붙는다(부르면 멈춘다). 목록이 비면 지금처럼 도구 없는 모델을 부른다(`core/loop.py`의 `_bind`, 아래 "모두 deny인 재개"). 저자의 승인 요구가 가리키는 도구가 실재하는지 보는 검사(`_reject_unknown_declarations`)는 거르기 전의 전체 목록에 대 본다(ADR 0044). (2026-11-06 명세 검토: "모델을 부를 때마다"는 정확히는 `ctx.llm()` 한 번마다다. `_Context.llm`이 루프 앞에서 `self._tools.tools()`를 한 번 읽는다(코드를 읽었다). 규칙이 한 실행 안에서 바뀌지 않아 행동은 같다.)

거부한 안: **연결을 열 때 한 번 걸러 둔다.** 연결의 도구 목록은 호출마다 읽고 있고 규칙은 준비마다 읽혀 한 실행 안에서 바뀌지 않으므로 둘 다 맞지만, 거르기를 두 자리에 두면 모델 목록과 게이트가 다른 판단을 할 수 있다. 호출마다 같은 함수로 낸다. 거부했다.

### 거부 문구 (명세가 정했다)

운영자의 deny로 거부된 호출의 `tool_called.content`와 에이전트가 받는 `ToolError`의 문구는 `운영자가 거부했다: <서버>:<도구>`다. 승인자의 거부 `승인자가 거부했다: <사유>`와 나란한 꼴이고 주체가 다르다. 도구를 늘 `<서버>:<도구>` 꼴로 적는 것은 운영자가 어느 서버의 도구가 막혔는지 바로 알게 하기 위해서다.

거부한 안: **맞은 규칙 줄을 문구에 싣는다.** 공통 표와 에이전트 표에서 여럿이 맞을 수 있고 적용 규칙 칸이 이미 deny임을 말한다. 거부했다. **`운영자 규칙이 거부했다`.** 승인자의 문구와 주어의 꼴을 맞춘다. 거부했다.

### 적용 규칙 칸의 이름과 값 (명세가 정했다)

- 칸의 이름은 `rule`이다. `tool_called`와 `run_paused`에 선택 칸으로 늘고 기본값은 없음(`null`)이라 형식 1·2·3의 옛 줄이 그대로 읽히고 형식은 3 그대로다. 직렬화 스키마에서는 required이고 `null`을 허락한다(`shortcuts`·`cause`의 선례, `.claude/rules/sdk.md`). 관리 화면의 필드 이름 표(`web/apps/admin/components/organisms/EventItem.tsx`)에 `rule`과 `server`가 없음을 읽었다. 표에 `rule: "적용 규칙"`을 더한다.
- 값은 닫힌 목록 다섯의 `AppliedRule`이고 sdk가 소유해 내보낸다. `deny`(운영자의 deny), `requires_approval`(저자의 승인 요구), `ask`(운영자의 ask), `allow`(운영자의 allow), `default`(적힌 규칙 없음, 그래서 묻는다). 용어집 **적용 규칙**의 다섯과 하나씩 맞는다. 주체를 값에 붙이지 않는 것은 deny·ask·allow는 운영자만, 승인 요구는 저자만 적을 수 있어 값이 이미 주체를 말하기 때문이다. 계약의 컴포넌트 이름은 별칭 이름 `AppliedRule`이다(`FailureCause`의 선례).
- `run_paused.rule`은 `requires_approval`·`ask`·`default` 셋 가운데 하나다(deny와 allow는 멈추지 않는다). `tool_called.rule`은 그냥 부른 호출이 `allow`, 운영자가 거부한 호출이 `deny`, 결정이 적용된 호출은 아래 절, 연결 목록에 없는 이름은 없음이다.
- 재생 구간의 기록은 다시 쓰지 않으므로 옛 줄의 없음이 새 값으로 채워지는 일은 없다.

거부한 안: **값 `none`(적힌 규칙 없음).** JSON의 `null`(칸이 없는 옛 줄)과 글자가 비슷해 읽는 쪽이 헷갈린다. 거부했다. **값 `operator_deny` 같이 주체를 붙인 이름.** 주체가 값에서 이미 유일하다. 거부했다. **칸 이름 `policy`·`gate`.** 용어집의 말이 적용 규칙이다. 거부했다. **적용 규칙을 `tool_called`에만 둔다.** 멈춘 실행을 보는 운영자가 왜 멈췼는지(저자의 요구인지 자기 ask인지 적힌 규칙 없음인지)를 바로 보지 못한다. 거부했다.

### 결정이 적용된 호출의 적용 규칙 (명세가 정했다)

결정(승인·거부)이 적용된 호출의 `tool_called.rule`은 그 호출을 멈춘 `run_paused.rule`과 같다. 승인되어 불린 호출은 `requires_approval`·`ask`·`default` 가운데 멈춘 까닭 그대로이고, 승인자가 거부한 호출도 같다. 예외는 하나다. 재개 때 운영자의 deny에 맞으면 결정이 무엇이든 부르지 않고 `deny`로 기록한다(ADR 0009의 2026-11-05 이력). 멈춘 사이 ask가 allow로 바뀌거나 승인 요구에서 빠진 것은 결정을 그대로 적용하고 칸도 멈춘 까닭을 든다. 적용 규칙은 "도구 호출 하나를 막을지, 멈출지, 그냥 부를지를 정한 규칙의 출처"(용어집)이고, 멈춘 호출을 정한 것은 멈추게 한 규칙과 그 뒤의 결정 이벤트이기 때문이다. (2026-11-06 명세 검토: 이 기능 전에 멈춘 실행은 `run_paused`에 `rule`이 없다. 그 결정이 적용된 호출의 `tool_called.rule`은 `requires_approval`이다. 이 기능 전의 런타임이 멈추는 까닭은 저자의 승인 요구 하나뿐이었고(`_Context._call`은 `name in self._policy.approvals`일 때만 `_pause`를 부른다, 코드를 읽었다), 없음은 연결 목록에 없는 이름에 준 값이라 둘이 겹치면 운영자가 가르지 못한다. 운영자의 deny 예외는 그대로다. 시험은 칸 없는 옛 멈춤 기록을 재개해 승인과 거부 모두에서 `requires_approval`을 본다.)

거부한 안: **재개 때 다시 낸 적용 규칙을 적는다.** 멈춘 사이 ask가 allow가 되면 승인자가 거부한 호출이 `allow`로 기록되어 결정 이벤트와 모순으로 읽힌다. 거부했다. **결정이 적용된 호출에는 칸을 비운다.** 운영자가 이 호출이 왜 멈췼었는지를 `run_paused`까지 거슬러 봐야 한다. 거부했다.

### 두 칸은 런타임만 쓴다 (명세가 정했다)

에이전트가 `yield`한 `tool_called`나 `run_paused`에 `rule`이나 `server`가 채워져 있으면 그 이벤트를 쓰지 않고 `run_failed`(원인 `agent_code`)로 끝낸다. 대화 요약과 실패 이벤트를 막는 판정(`_reject_runtime_only`, ADR 0031)과 같은 길이고 재생 구간에서도 같다. 두 칸이 비어 있는 에이전트의 `tool_called`는 지금처럼 통과한다. 지어낸 `run_paused`는 지금도 멈춘 것으로 치지 않아 실행이 `agent_code`로 끝나는데(`tests/core/test_run.py`의 `test_에이전트가_지어낸_일시정지_이벤트는_실행을_멈춘_것으로_치지_않는다`), 칸이 채워진 것은 그보다 먼저 쓰지 않고 끝낸다. 에이전트의 기록이 운영자의 규칙을 사칭하면 트레이스를 읽는 운영자가 가를 수 없기 때문이다(ADR 0044가 명세에 넘긴 물음, PR 봇이 짚었다). (2026-11-06 명세 검토: 칸은 셋이다. `tool_called.rule`, `run_paused.rule`, `run_paused.server`이고 `tool_called`에는 `server`가 없다(아래 "서버 칸과 재개의 대조"). 이 판정은 묶음 A가 맡는다("고칠 자리의 묶음"의 A 줄 주석).)

거부한 안: **에이전트의 `tool_called` 자체를 런타임 전용으로 막는다.** 지금 통과하는 이벤트를 막아 기존 에이전트가 깨진다. 거부했다. **칸이 채워진 것을 비워서 쓴다.** 조용히 고치면 에이전트 작성자가 잘못을 모른다. 거부했다.

### 서버 칸과 재개의 대조 (사용자가 골랐다. 칸의 이름과 문구, 없는 이름의 처리는 명세가 정했다)

- `run_paused`에 선택 칸 `server`가 늘고 멈춘 도구를 낸 서버 플러그인의 이름을 든다. 기본값은 없음이라 옛 줄이 그대로 읽히고 형식은 3 그대로다. 이벤트의 다른 식별자 필드와 같이 sdk의 패턴을 걸지 않는다(`.claude/rules/sdk.md`). 필드 이름 표에 `server: "서버"`를 더한다.
- 재개의 일치 검사(`_require_paused_call`)는 도구 이름과 마스킹된 인자에 더해, 멈춤 기록에 `server`가 있고 지금 연결에 그 이름의 도구가 있으면 그 도구를 낸 서버와 같은지 본다. 다르면 재개 불일치다. 지금 연결에 그 이름의 도구가 없으면(멈춘 사이 그 서버가 매니페스트에서 빠졌다) 서버를 대 보지 않고, 재개가 아닐 때와 같이 게이트 앞에서 `도구가 없다: <이름>`으로 거부하며 결정은 소비된다("집행의 차례" 3). 사용자의 답은 서버가 다를 때만 불일치라 했고, 없는 이름까지 불일치로 넓히면 같은 상황이 서버 칸의 유무로 `run_failed`와 계속으로 갈리므로 명세가 이렇게 정했다. 지금 코드는 이름과 인자만 대 보고 없는 이름을 `_call_safely`의 실패 결과로 넘긴다(코드를 읽었다). 문구는 지금 문구에 서버를 더한 `재개 뒤 첫 호출이 멈춘 자리와 다르다. 멈춘 것은 도구 <서버>:<도구> <인자>, 지금 <서버>:<도구> <인자>. 결정을 적용하지 않는다`이고 서버가 없는 쪽은 `(서버 없음)`으로 적는다. 멈춤 기록에 `server`가 없는 옛 트레이스는 지금처럼 이름과 인자만 본다.
- `tool_called`에는 서버 칸을 더하지 않는다. 승인을 묶는 데 필요한 것은 멈춤 기록이고, 모든 도구 호출의 서버를 트레이스에 적는 것은 mcp-trust가 `tool_called`에 신뢰 수준을 적을 때 함께 정한다(Out of Scope).

거부한 안: **서버를 `tool_called`에도 적는다.** 이 기능의 물음이 아니고 mcp-trust가 같은 이벤트에 칸을 더한다. 거부했다. **서버가 다르면 불일치가 아니라 거부로 기록하고 계속한다.** 결정이 다른 호출에 적용되지 않게 하는 지금의 규칙은 다른 호출을 `run_failed`로 끝내는 것이다(ADR 0009의 2026-09-22 이력 "결정은 정책이 아니라 멈춘 호출에 묶인다"). 거부했다. **지금 그 이름의 도구가 없으면 재개 불일치로 끝낸다.** 서버 칸이 없는 옛 멈춤 기록은 같은 상황에서 3의 거부로 계속되어, 같은 상황의 끝이 칸의 유무로 갈린다. 거부했다. **옛 트레이스(서버 없음)의 재개를 거부한다.** 서버 칸이 없는 멈춘 실행은 이 기능 전에 멈춘 것이고 받아들인 비대칭이다(ADR 0044 "치르는 값"). 거부했다.

### 같은 이름의 도구 — 검사의 자리와 문구 (명세가 정했다)

- 검사는 MCP 어댑터에 있다. 연결을 열며 서버들의 도구를 이름으로 모을 때(`adapters/mcp.py`의 `routes[route.tool.name]`, ADR 0044가 읽었다) 같은 이름이 이미 있으면 모으기를 멈추고 던진다. 연결에 들어가는 동안의 예외는 핵심이 도구 연결의 실패로 받아 `run_failed`(원인 `tool_connection`)를 쓴다(`.claude/rules/core.md` 실패 정책). 문구는 `같은 이름의 도구가 둘이다: <도구> (<앞서 모은 서버>, <겹친 서버>)`이다. 서버는 매니페스트의 순서대로 하나씩 열며 모으므로(코드를 읽었다) 겹친 서버 뒤의 서버는 열리지 않고, 같은 이름을 낸 서버가 셋 이상이어도 문구에는 처음 겹친 둘만 든다. 운영자가 하나를 빼고 다시 돌려 다음 겹침을 알게 되는 값을 치르고, 끝까지 모아 던지는 쪽은 실패할 연결을 모든 서버까지 여는 값을 치르므로 고르지 않았다.
- 포트 `ToolConnection.tools()`의 약속에 한 연결 안에서 도구 이름은 유일하고 어댑터가 보장한다는 문장을 적는다(`core/ports.py` 독스트링, `.claude/rules/core.md`의 포트 표 `ToolSource` 행). 핵심은 다시 보지 않는다.

거부한 안: **핵심이 연결 뒤 목록에서 본다.** 지금 어댑터의 연결은 이름으로 모은 딕셔너리의 값을 돌려줘 같은 이름이 하나로만 보이므로(ADR 0044), 핵심에 두려면 연결이 덮지 않은 목록을 돌려주도록 어댑터의 길 찾기 구조까지 바꿔야 한다. 정보가 있는 자리에서 한 번 본다. 거부했다. **어댑터와 핵심이 둘 다 본다.** 핵심의 검사는 어댑터가 덮은 목록에서는 돌 수 없는 죽은 코드다. 거부했다.

### 에이전트 표의 검사 (사용자가 골랐다. 자리와 문구는 명세가 정했다)

- 그 에이전트의 표(`[agents.<이름>]`)에 적힌 줄은 연결 직후 대 본다. 자리는 저자의 승인 요구가 가리키는 도구가 실재하는지 보는 검사(`_reject_unknown_declarations`) 바로 뒤이고 원인은 같은 `tool_connection`이다. 맨 도구 이름은 연결의 도구 가운데 그 이름이 하나는 있어야 하고, `서버:*`는 그 서버가 에이전트 매니페스트의 `mcp`에 있어야 하며, `서버:도구`는 그 서버가 낸 그 이름의 도구가 있어야 한다. 하나라도 어긋나면 `run_failed`이고 문구는 `규칙 파일의 에이전트 표가 가리키는 도구가 없다: <에이전트> 의 <줄>, <줄>`로 어긋난 줄을 모두 알린다. 줄의 글자는 문구에 싣지 않고 자리(`agents.<에이전트>.<deny·ask·allow>.<번호>`)만 싣는다. 모양을 통과한 줄도 맨 도구 이름 자리에는 어떤 글자든 들 수 있어 운영자가 잘못 적은 비밀이 트레이스에 남을 수 있기 때문이다(원칙 V. 깨짐 문구가 값을 벗기는 것과 같은 방식이다). 문구의 `<줄>`은 이 자리다. 공통 표는 여러 에이전트에 걸쳐 어느 한 실행에서 다 대 볼 수 없으므로 모양만 본다(ADR 0044). 그래서 deny의 오타가 allow 뒤에 숨는 길(ADR 0044 "모양")은 에이전트 표에서는 막히고 공통 표에서는 남는다.
- 검사는 deny로 빼기 전의 전체 목록에 대 본다(저자의 승인 요구 검사와 같다).

거부한 안: **공통 표도 그 실행의 연결에 대 본다.** 공통 표에 쓴 도구를 모든 에이전트가 가져야 해 공통 표가 사실상 모든 에이전트가 같이 쓰는 서버의 규칙만 담게 된다(선택 화면의 셋째 안, 사용자가 고르지 않았다). 거부했다. **읽을 때 매니페스트 목록으로 본다.** 도구 이름은 서버에 붙어야 알 수 있어 읽을 때는 서버 이름까지만 볼 수 있고, 검사가 둘로 갈린다. 거부했다. **어긋난 줄을 경고로 남기고 돈다.** 새 이벤트 종류가 필요하고, 저자의 승인 요구 오타가 실패인 것과 어긋난다. 거부했다.

### 마스킹과 묻기의 충돌 (명세가 정했다)

마스킹할 인자(`secret_args`)가 있는 도구는 승인 대상이 될 수 없다. 재개가 재생한 모델 응답의 인자는 마스킹된 값이라 승인 뒤 실제 호출이 그 값을 보내게 되기 때문이고, 지금은 `requires_approval`과 겹치는 도구를 실행 전에 `PluginError`로 거부한다(`approval_conflicts`, ADR 0009, `.claude/rules/sdk.md`). 기본이 묻는다가 되면 운영자의 ask나 적힌 규칙 없음도 같은 도구를 멈추게 하므로 같은 충돌이다. 그래서 준비 단계에서 규칙 파일을 읽은 뒤, 에이전트가 고른 서버들의 `secret_args`에 든 도구(서버 이름과 도구 이름의 쌍, 매니페스트만으로 안다)마다 저자의 승인 요구를 뺀 차례로 적용 규칙을 내어 `ask`나 `default`면 `PluginError`로 거부한다. 문구는 `마스킹된 인자를 가진 도구는 묻는 규칙에 걸릴 수 없다: <서버>:<도구> (규칙 파일에 allow 나 deny 를 적는다)`다. deny에 맞는 도구는 불리지 않으므로 충돌이 아니고 allow에 맞는 도구는 묻지 않으므로 충돌이 아니다. 자리는 준비 순서의 깨짐 묶음에서 운영자 파일 읽기 바로 뒤, 꺼짐 판정 앞이다. (2026-11-06 명세 검토: "운영자 파일 읽기"는 규칙 파일과 꺼진 집합을 모두 읽은 뒤다. 위 "자리와 읽는 때"의 주석.) 실행 식별자가 생기기 전이라 트레이스가 없고, 운영자 채널은 500에 원문을, 최종 사용자 면은 고정 문구의 500을 낸다.

거부한 안: **묻는 규칙에 걸린 마스킹 도구를 멈추게 두고 승인 뒤 실패하게 둔다.** 승인한 사람이 승인 뒤에야 실패를 보고, 그 실패는 지금 코드가 `마스킹된 인자를 실제 도구에 보낼 수 없다`로 끝내는 길이다(`_reject_masked_args`, 코드를 읽었다). 실행 전에 안다. 거부했다. **연결 직후 실제 도구 목록으로 본다.** `secret_args`는 매니페스트에 서버마다 적혀 실행 전에 알 수 있고, 지금의 승인 충돌 검사도 실행 전이다. 거부했다. **마스킹 도구는 규칙과 무관하게 묻지 않고 돌린다.** 운영자가 적지 않은 도구를 묻는다는 기본에 구멍을 낸다. 거부했다.

### 모두 deny인 재개 (명세가 정했다. 쟀다)

멈춘 사이 운영자가 에이전트의 도구를 모두 deny로 돌리면 재개는 멈춘 호출을 거부로 기록한 뒤 도구 호출 블록이 이미 든 대화를 도구 정의 없이 모델에 보낸다. ADR 0044는 API가 그런 요청을 거부하면 `model_call` 원인의 `run_failed`라고 어림했다. 쟀다. 이 저장소의 모델 플러그인(`claude-opus-5`)을 실제 어댑터로 만들고 루프와 같은 묶기로 그 대화를 보내자 도구 정의 없이도 두 회차 모두 받았고, 양성 대조(거부된 도구의 정의를 붙인 같은 대화)도 받았다(`probes/README.md`). 그래서 **처리를 따로 두지 않는다.** 모두 deny인 재개는 거부 기록 뒤 도구 없는 모델 호출로 이어진다. 측정에서는 두 회차 모두 모델이 도구를 부르지 않고 글로 답했고, 둘째 회차는 거부 문구를 되울렸다(`probes/README.md`). 실제 재개 길이 `run_finished`로 끝나는 것은 구현 티켓의 실제 모델 시험 하나가 실제 재개로 잰다(아래 "실제 모델 시험 하나"). 그 전까지는 어림이다. 다른 모델이나 다른 날의 API가 거부하면 그때의 결말은 지금 실패 정책대로 `model_call` 원인의 `run_failed`이고 그것을 바꾸지 않는다.

거부한 안: **deny된 도구의 정의를 `tool_choice` none으로 붙여 보낸다.** 측정에서 API가 그 모양도 받았지만 필요가 없고, ADR 0044의 "deny인 도구는 모델에 붙이는 도구 목록에서 뺀다"와 어긋난다. 거부했다. **역사의 도구 호출 블록을 글로 바꿔 보낸다.** 트레이스에 없는 대화를 만들어 재생 대조의 전제를 깬다. 거부했다. **모두 deny면 재개를 거부한다.** 운영자가 막은 뒤에도 멈춘 실행이 끝까지 가야 최종 사용자의 대화가 닫힌다. 거부했다.

### 예시 규칙 파일과 시험 자리의 규칙 파일 (넘겨받았다. 내용은 명세가 정했다)

- 저장소의 `plugins/rules.toml`은 `schema_version`과 에이전트 표 하나다. `[agents.calc]`에 `allow = ["everything:*"]`. 공통 표는 두지 않는다. 예시가 배치 전체를 여는 모양을 보이지 않기 위해서다(ADR 0044 "allow는 `<서버>:*`나 에이전트별 표로 쓰기를 권한다"). 파일 머리의 주석이 세 꼴과 차례를 한 줄씩 적는다. `README.md`의 플러그인 루트 트리에 `rules.toml` 줄이 `disabled.toml` 줄 옆에 든다.
- `-m llm` 시험 여섯(`tests/test_main.py`)은 플러그인 루트를 만드는 길이 갈린다(여섯의 그 줄을 코드로 읽었다). `_copy_repo_plugins`로 임시 루트를 만드는 하나(한도를 작게 적은 calc의 요약 시험)는 그 도우미가 저장소 `plugins/`에서 calc와 그것이 쓰는 플러그인 폴더 넷만 복사하므로 루트의 `rules.toml`이 따라가지 않는다. 그 도우미가 `rules.toml`도 복사하게 고친다(묶음 D). 고치지 않으면 그 시험 하나가 기본 묻는다에서 멈춘다. `plugins/` 통째를 복사하는 하나(모델 이름을 바꾸는 시험)와 저장소 루트에서 바로 도는 하나(calc 이어 가기)는 저장소의 예시 파일을 쓰고, 도구 없는 에이전트(asker)의 하나는 게이트에 들지 않는다. `gatedcalc`와 가짜 서버 `fixture`를 `_write_plugin`·`_write_mcp_plugin`으로 손수 쓰는 둘(CLI 재개, HTTP 승인)은 규칙 파일이 없어 `add`의 승인 요구에서 지금처럼 멈추되 모델이 다른 도구를 부르면 기본에서 멈추므로, 아래 채널·서버 테스트와 같은 꼴의 파일을 그 루트에도 둔다(묶음 D). 위젯 e2e의 플러그인 꾸러미(`web/apps/widget/e2e/plugins.ts`)는 `tools` 에이전트의 서버 `fixture`를 여는 `[agents.tools] allow = ["fixture:*"]`를 쓴다. 승인 요구가 있는 e2e 에이전트는 승인 요구가 allow보다 먼저라 그대로 멈춘다. 파일시스템 플러그인 루트를 만드는 채널·서버 테스트의 도구 에이전트도 같은 꼴의 파일을 둔다. 자리의 셈은 구현 티켓이 테스트를 돌려 센다(ADR 0044는 어림이라 적었다).
- core 시험의 가짜 플러그인 소스(`tests/core/test_run.py`의 `FakePlugins`)는 `read_rules`를 갖고, 기본 규칙은 자기 서버 전부의 `<서버>:*` allow다. 그래야 도구를 부르는 기존 사례가 바뀌지 않고, 게이트를 재는 사례만 규칙을 명시한다.
- (2026-11-06 명세 검토: 위 두 항목의 셋을 바로잡는다. (1) "파일시스템 플러그인 루트를 만드는 채널·서버 테스트"는 없다. 채널 시험(`tests/channel/http/test_router.py`, `tests/channel/http/test_end_user.py`)은 가짜 포트를 쓰고 관리 시험(`tests/test_server.py`)은 실행하지 않는다(검토가 코드를 읽었다). 그래서 그 자리는 규칙 파일이 아니라 가짜의 기본 규칙으로 고친다. (2) "자기 서버 전부의 `<서버>:*` allow"로는 기존 사례가 바뀌지 않는다는 주장이 서지 않는다. core 시험의 기본 `FakePlugins`는 서버가 없고(`servers=()`) 가짜 연결(`FakeConnection`)의 도구에는 서버가 없다(본 세션이 코드를 읽었다). 도구를 든 가짜 연결을 서버 없는 가짜 플러그인 소스와 쓰는 시험이 열둘이다(검토 서브에이전트가 임시 스크립트로 AST를 세어 손으로 봤다). 그래서 가짜 연결은 도구마다 서버 이름을 들고 기본 서버 이름 하나를 두며, 가짜 플러그인 소스의 기본 규칙은 공통 표의 allow에 자기 서버 전부와 그 기본 서버의 `<서버>:*`를 둔다. 에이전트 표에 두지 않는 것은 C의 에이전트 표 검사가 매니페스트 `mcp`에 없는 서버를 거부하기 때문이다(채널 시험에는 `mcp` 없이 도구를 부르는 에이전트가 있다). core·router·end_user의 세 가짜가 같은 규약을 쓴다. (3) 위젯 e2e의 실제 모델 모드는 저장소 플러그인 루트를 복사한 뒤 꾸러미를 그 위에 쓰므로(`web/apps/widget/e2e/stack.ts`의 `copyRepoPlugins` 뒤 `writeFixturePlugins`, 본 세션이 읽었다) 꾸러미의 `rules.toml`이 저장소의 것을 덮는다. 꾸러미의 파일은 모드와 무관하게 `[agents.calc] allow = ["everything:*"]`도 든다. 에이전트 이름의 실재는 보지 않으므로 calc가 없는 모드에서도 깨지지 않는다.)

거부한 안: **예시를 공통 표 `allow = ["everything:*"]`로 둔다.** 예시를 베낀 배치가 모든 에이전트의 everything 도구를 열게 된다. 거부했다. **가짜의 기본을 빈 규칙(모두 묻는다)으로 둔다.** 도구를 부르는 기존 사례 다수가 멈춰 모두 고쳐야 하고, 그 고침이 이 기능의 뜻을 가린다. 거부했다.

### 계약과 관리 화면 (넘겨받았다)

`openapi.json`에 `ToolCalled.rule`, `RunPaused.rule`, `RunPaused.server`, 컴포넌트 `AppliedRule`이 들고 생성 TS 타입과 스토리·테스트의 리터럴이 바뀐다. 관리 화면은 필드 이름 표의 두 줄 외에 바꾸지 않고 두 칸은 다른 칸처럼 이름과 값으로 보인다. 최종 사용자 면의 항목 투영(`channel/http/items.py`의 진행 항목과 멈춤 항목)은 두 칸을 싣지 않는다. 최종 사용자에게 운영자의 규칙과 서버 이름은 서버 안쪽의 구성이다. 관리 API에 규칙 파일을 읽거나 쓰는 경로는 없다. 이 기능 전의 코드가 새 칸이 든 줄을 읽으면 손상으로 거부하는 비대칭은 ADR 0044가 받아들였고 `.claude/rules/sdk.md`의 선택 필드 항목에 적는다(넘겨받은 것 12).

거부한 안: **묶음 하나(계약부터 예시까지).** 한 세션에 들기 어려운 크기(어림)이고 계약 파일을 따로 리뷰하지 못한다. 거부했다. **B를 어댑터와 포트로 나눈다.** 어댑터의 읽기가 핵심의 값을 만들어 둘이 같은 커밋에 있어야 초록이다. 거부했다.

### 실제 모델 시험 하나 (사용자가 골랐다. 모양은 명세가 정했다)

`tests/test_main.py`에 `-m llm` 시험 하나를 더한다. 저장소 `plugins/`를 임시 루트에 복사하고(고친 `_copy_repo_plugins`가 `rules.toml`도 옮긴다) 그 `rules.toml`을 `[agents.calc] ask = ["everything:*"]`로 바꿔 실제 CLI로 calc를 돌리면 첫 도구 호출에서 멈춘다(`run_paused.rule`이 `ask`, `server`가 `everything`). 그 뒤 파일을 `[agents.calc] deny = ["everything:*"]`로 바꾸고 다른 프로세스에서 승인으로 재개한다(선례는 같은 파일의 멈춘 실행을 다른 프로세스에서 재개하는 시험). 단언은 트레이스의 끝이 `run_finished`이고, 재개 뒤의 `tool_called`가 `ok=false`·`rule="deny"`·내용 `운영자가 거부했다: everything:<도구>`이며, `run_failed`가 없다는 것이다. 이 하나가 재개의 규칙 다시 읽기, 운영자 deny가 결정을 이기는 것, 도구 정의 없는 모델 호출을 API가 받는 것(측정)을 실제 길에서 함께 잰다. 나머지 `-m llm` 시험은 예시 규칙 파일로 그대로 지나가야 하고 수가 늘지 않는다. 멈추는 자리를 보는 단언은 모델이 첫 호출로 `add`를 부르는 데 기대지 않고 어느 도구든 멈춘 것을 본다(도구 이름은 결과이지 표지가 아니다).

거부한 안: **실제 모델 시험을 더하지 않는다.** 측정은 손으로 지은 대화였고 실제 재개 길을 지나지 않았다(`probes/README.md`의 재지 않은 것). 거부했다. **core의 가짜 모델로만 잰다.** API가 받는지는 가짜가 말할 수 없다. 거부했다.

## Testing Decisions

### 이음매 (사용자가 골랐다)

주 이음매는 core의 `run()`·`resume()`에 가짜 플러그인 소스와 가짜 도구 연결을 꽂는 자리다(`tests/core/test_run.py`의 `_run`과 `FakePlugins`·`FakeTools`). 가짜 플러그인 소스가 `Rules`를 들고(기본은 자기 서버 전부의 `<서버>:*` allow) 읽은 횟수를 세며, 가짜 도구 연결이 도구마다 서버 이름을 든다. (2026-11-06 명세 검토: 괄호의 기본 규칙은 위 "예시 규칙 파일과 시험 자리의 규칙 파일"의 주석 (2)가 바로잡았다. 가짜 연결은 도구마다 서버 이름을 들되 적지 않으면 기본 서버 이름 하나를 쓰고, 가짜 플러그인 소스의 기본 규칙은 공통 표의 allow에 자기 서버 전부와 그 기본 서버의 `<서버>:*`를 둔다.) 집행의 차례, 모델 목록 거르기, 거부 기록과 문구, 멈춤의 두 칸, 결정이 적용된 호출의 칸, 재개의 규칙 다시 읽기와 deny 우선, 서버 대조의 불일치, 없는 이름의 거부, 두 칸의 런타임 전용, 마스킹과 묻기의 충돌, 에이전트 표의 검사와 문구, 준비의 순서를 여기서 잰다. 바깥 경계는 기존 시험 자리에 얇은 시험이 맡는다. 파일 읽기와 깨짐과 두 문구는 파일시스템 어댑터 시험(`tests/adapters/test_filesystem.py`), 같은 이름 검사와 `ToolSpec.server`는 MCP 어댑터 시험(`tests/adapters/test_mcp.py`, 같은 픽스처 stdio 서버 `mcp_fixture_server.py`를 두 플러그인 이름으로 띄워 같은 이름을 만든다), 두 칸의 직렬화와 `AppliedRule`은 sdk 시험, 투영이 두 칸을 싣지 않는 것은 HTTP 항목 시험, 바깥 증거는 위의 실제 모델 시험 하나다.

### 좋은 시험

- 바깥 행동만 단언한다. 트레이스의 이벤트 열과 칸의 값, 예외의 타입과 문구, 가짜가 기록한 호출과 모델이 받은 도구 목록(`ToolAwareFakeModel`의 선례). (2026-11-06 명세 검토: `ToolAwareFakeModel`은 받은 도구 목록의 선례가 아니다. `bind_tools`가 `binds`만 세고 `tools`를 버린다(본 세션이 코드를 읽었다). 일부만 빼는 시험을 위해 C가 그 가짜가 받은 목록을 기록하게 넓히거나 새 가짜를 둔다. 모두 deny인 경우는 지금도 `binds`의 수로 잰다. `core/loop.py`의 `_bind`가 빈 목록이면 도구를 붙이지 않는다(ADR 0044가 코드를 읽었다).) 준비의 순서는 두 결함을 함께 심어 어느 오류가 먼저 나오는지로 잰다(`test_준비의_순서는_부재_깨짐_꺼짐_진입점_모델_만들기다`의 선례).
- 실패를 기대하는 시험은 실패의 까닭(표지)을 단언한다(`CODING_STANDARDS.md`). 깨진 규칙 파일은 pydantic 문구의 자리(`agents.calc.allow.0` 등)와 값을(2026-11-06 명세 검토: 값은 싣지 않는다. 시험은 자리와 오류 종류를 보고, 모르는 키에 심은 값이 문구에 없는 것을 본다. "깨짐과 읽기 실패의 문구"의 주석), 연결 직후의 실패는 원인 `tool_connection`과 문구의 자리를(줄의 글자는 싣지 않는다. 심은 값이 문구에 없는 것도 본다), 재개 불일치는 원인 `resume_mismatch`와 두 서버를 본다.
- 운영자의 deny가 결정을 이기는 시험은 승인과 거부 두 결정에서 모두 `tool_called(ok=false, rule="deny")`인 것을 보고, 양성 대조로 deny가 아닌 변화(ask → allow)에서는 승인이 불리는 것을 본다.
- 환경이 없으면 skip이 아니라 실패다(`.claude/rules/tests.md`). `-m llm`은 `ANTHROPIC_API_KEY`가 없으면 실패한다.
- 빨강을 먼저 본다(헌법 원칙 II). A의 첫 빨강은 리터럴이 타입 검사에서 깨지는 것과 `openapi.json` 최신성 시험, B의 첫 빨강은 `read_rules`가 없어 가짜가 포트 적합성에서 깨지는 것(pyright)과 같은 이름의 두 서버가 조용히 덮이는 어댑터 시험, C의 첫 빨강은 규칙 없는 가짜로 도구를 부른 실행이 멈추지 않는 것, D의 첫 빨강은 실제 모델 시험이다.

### 시험할 모듈과 선례

- sdk 이벤트: 두 이벤트의 새 칸이 기본값 없음으로 옛 줄을 읽고, 직렬화 스키마에서 required이며 `null`을 허락하고, `AppliedRule` 밖의 값을 거부하는 것. 선례 `tests/adapters/test_jsonl.py`의 `test_실패_원인과_바로가기가_왕복하고_헤더는_3_그대로다`와 `test_새_필드_둘의_키가_없는_옛_줄은_원인과_바로가기가_없음으로_읽힌다`.
- 핵심의 규칙 값: 세 꼴의 맞음과 안 맞음, 공통 표와 에이전트 표의 합집합, 차례 다섯의 각 갈래. 선례는 `tests/core/`의 순수 함수 시험. (2026-11-06 명세 검토: 스토리 2의 "그 에이전트에만 걸린다"를 재는 사례가 없었다. `[agents.other] deny`가 calc의 호출에 걸리지 않는 것과, 양성 대조로 같은 줄을 `[agents.calc]`에 두면 걸리는 것을 본다.)
- 파일시스템 어댑터: 없는 파일은 빈 `Rules`, 세 꼴 읽기, allow의 맨 이름 거부, 콜론 둘·빈 조각·공백 거부, 모르는 키 거부, 에이전트 이름 패턴 거부, 형식 버전 거부, UTF-8 아님, 깨짐 문구에 자리와 값이 드는 것, 읽기 사이에 파일을 고치면 둘째가 새 규칙을 돌려주는 것. 선례 `tests/adapters/test_filesystem.py`의 운영자 파일 시험들(`test_…없으면_꺼진_것_없다`부터 손상의 `PluginError` 경로까지). (2026-11-06 명세 검토: 첫 선례의 이름은 `test_운영자_파일이_없으면_꺼진_것이_없다`다. 깨짐 문구에는 값 대신 자리와 오류 종류가 든다. "깨짐과 읽기 실패의 문구"의 주석.)
- MCP 어댑터: `ToolSpec.server`가 서버 플러그인 이름인 것, 같은 픽스처 서버를 두 이름으로 열면 두 이름을 든 예외인 것, 서버 하나는 그대로 열리는 것(양성 대조). 선례 `tests/adapters/test_mcp.py`의 `test_서버의_도구_목록과_입력_스키마를_준다`와 연결 오류 시험들. (2026-11-06 명세 검토: 같은 이름 검사가 던지는 예외 타입은 B가 정한다. core의 `run_failed.error`에는 `<타입>: ` 접두가 붙으므로(`core/run.py`의 `_describe`) 시험은 문구의 부분 일치로 본다. 두 서버 이름이 트레이스까지 가는 것(스토리 10)은 그 문구로 던지는 가짜 도구 소스를 core에 꽂아 원인 `tool_connection`과 문구를 보는 사례 하나가 잰다.)
- core 집행: 위 이음매의 목록 전부. 선례는 `tests/core/test_run.py`의 "거부", "재개", "결정은 멈춘 호출에 묶인다", "꺼진 플러그인", "실행 전 실패의 갈래" 절과 `test_에이전트가_지어낸_일시정지_이벤트는_실행을_멈춘_것으로_치지_않는다`.
- HTTP 두 면: 깨진 규칙 파일의 운영자 면 500 원문과 최종 사용자 면 고정 문구 500, 투영이 두 칸을 싣지 않는 것. 선례 `tests/channel/http/test_end_user.py`의 없는 모델 시험과 `tests/test_server.py`의 트레이스 상세 시험. (2026-11-06 명세 검토: 선례의 자리를 바로잡는다. 투영이 두 칸을 싣지 않는 것의 선례는 `tests/channel/http/test_end_user.py`의 `test_항목은_프롬프트도_도구_결과도_주체도_싣지_않는다`이고, 운영자 면 500 원문의 선례는 `tests/channel/http/test_router.py`의 `test_실행_전_구성_오류는_500_봉투이고_message_가_그_PluginError_의_문구다`다(본 세션이 Grep으로 찾았다). `tests/test_server.py`의 트레이스 상세는 관리 API라 두 칸이 그대로 실린다. 위 "이음매"의 "HTTP 항목 시험"도 앞의 것을 가리킨다. 투영은 칸을 골라 항목을 만들어(`channel/http/items.py`, 검토가 코드를 읽었다) 새 칸이 저절로 실리지 않으므로 이 시험은 회귀를 막는 몫이다.)
- 저장소 상태: `plugins/rules.toml`을 실제 어댑터로 읽어 `Rules`가 되고 calc의 표만 있는 것(저장소의 플러그인을 실제 어댑터로 읽는 선례는 `tests/test_calc_plugin.py`).
- 경계: 핵심이 어댑터와 TOML 라이브러리를 import하지 않는 것은 `uv run lint-imports`가 판정한다.

## Out of Scope

- `tool_called`의 서버 칸과 신뢰 수준. mcp-trust가 운영자의 서버 파일과 함께 정한다(`.scratch/plan.md`의 mcp-trust 행).
- 운영자의 서버 파일(`servers.toml`)과 믿지 않는 서버의 결과 감싸기. mcp-trust.
- 전역 `*`와 인자 패턴 규칙. 내장 도구가 생길 때 더한다(ADR 0044 "모양").
- 저자의 `requires_approval`에 `<서버>:<도구>` 꼴을 더하는 것. 저자의 목록은 맨 이름 그대로이고 묻는 방향이라 넓게 맞아도 안전하다(사용자의 첫째 답이 deny와 ask가 맨 이름을 받는 까닭으로 든 판단, 일지 2026-11-05-10). 받는 기능은 없다.
- 공통 표의 이름을 연결과 대 보는 것과 에이전트 표의 에이전트 이름 실재. 받는 기능은 없다.
- 관리 API·관리 화면에서 규칙 파일을 읽거나 고치는 것(ADR 0044 "범위 밖").
- 실행 도중에 바뀐 규칙 파일을 다시 읽는 것. 규칙은 준비마다 한 번이다(ADR 0044).
- 최종 사용자 면의 항목에 적용 규칙과 서버를 싣는 것.

## Further Notes

- 프로브 하나의 결과는 `.scratch/approval-rules/probes/README.md`다. 이 명세가 ADR 0044의 어림 하나(모두 deny인 재개의 API 거부)를 측정으로 바로잡았고, 그 결과가 ADR 0044의 2026-11-05 이력 "명세가 정한 것과 잰 것"에 있다.
- 기본이 묻는다라 규칙 파일이 없는 배치는 모든 도구 호출에서 멈추고, 마스킹할 인자가 있는 도구를 쓰는 에이전트는 규칙 파일 없이는 실행 전에 거부된다(위 "마스킹과 묻기의 충돌"). 두 가지 모두 운영자가 `rules.toml`을 두는 것으로 풀린다. 저장소의 예시 파일이 그 모양이다.
- 옛 판의 코드가 새 칸이 든 `tool_called`·`run_paused` 줄을 손상으로 거부하는 비대칭은 ADR 0044가 받아들인 것이고, `.claude/rules/sdk.md`의 선택 필드 항목이 그것을 적는다(묶음 A).
- 설계 인터뷰가 보기로 든 Claude Code의 MCP 도구 규칙(`mcp__서버__도구`)과 이 파일의 꼴은 이제 둘 다 서버에 묶인 단일 도구 꼴을 갖되, 이 파일은 콜론으로 가르고 맨 이름 꼴도 deny·ask에 남긴다.
