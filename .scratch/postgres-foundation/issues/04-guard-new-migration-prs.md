# 04: 새 마이그레이션 파일을 더한 PR은 느낌표와 번호의 꼴을 검사받는다

**What to build:** 개발 세션이 제품 마이그레이션 폴더에 새 파일을 더한 PR을 제목에 느낌표 없이 열면 노트 검사가 빨갛다(사용자 이야기 28). 느낌표가 있으면 지금처럼 `docs/release-notes/upgrade/`의 원고를 요구한다. 마이그레이션 번호가 겹치거나 건너뛰거나, 앞 번호의 사슬이 끊기거나, 마지막 번호가 둘이거나, 되돌리는 함수 `downgrade`가 들면 저장소 상태 시험이 빨갛다(사용자 이야기 29). 나란히 짠 두 브랜치가 같은 번호를 들고 오면, 나중에 병합하는 쪽이 기준 브랜치를 합친 뒤 이 시험이 빨개진다. 둘 다 이 기능 뒤에 admin-login이 더하는 `0002`부터를 지키는 검사다(사용자 이야기 34).

두 검사는 제품 폴더에 `0001`이 든 뒤에 든다(02). 짝이 보는 폴더의 경로는 01이 정했는데 그 변경의 제품 폴더는 비어 git에 담기지 않아, 경로가 맞는지 시험할 파일이 `0001` 전에는 없다(명세 검토 B1).

근거는 명세 `.scratch/postgres-foundation/spec.md`의 "노트 검사의 짝", "마이그레이션 파일", "저장소 상태 시험"의 둘째, "티켓을 나눌 때 함께 둘 것"의 넷째, Testing Decisions의 넷째와 머리 문단(`tools/`의 코드는 지금의 규칙대로 본다)이다. 결정은 ADR 0066 결정 "승인 때 함께 확인받는 세부"의 첫째와 "판 되돌리기"다. 이 티켓의 "명세 검토"와 그 번호는 일지 `docs/journal/2026-11-19-0050-postgres-foundation-tickets.md`의 "명세 검토" 절을 가리킨다.

03과 이 티켓은 고치는 파일이 겹치지 않아 나란히 돌 수 있다. 둘 가운데 늦게 병합하는 쪽이 같은 커밋에서 기능 계획에 `**끝:**` 줄을 적고 `uv run python tools/plan_table.py`를 돌리며, 기능 단락 `docs/release-notes/features/postgres-foundation.md`를 싣는다. 병합 직전에 `git fetch origin` 뒤 기준 브랜치를 합치고 저장소 상태 시험(`test_이_저장소의_…`)을 돌린다(`docs/agents/issue-tracker.md`의 "나란히 돈 마지막 티켓 둘").

**Blocked by:** 02

**Status:** ready-for-agent

### 노트 검사의 짝

- [ ] `tools/check_notes.py`의 제목 판정(`title_problems`)에 짝을 더한다. PR이 제품 마이그레이션 폴더에 파일을 새로 더했는데 제목에 느낌표가 없으면 문제이고, 그 글이 무엇을 할지(제목에 느낌표를 붙이고 원고를 싣는다) 알려 준다. 느낌표가 있으면 지금의 원고 판정이 그 뒤를 잇는다. 원고의 글은 검사하지 않는다
- [ ] `tests/tools/test_check_notes.py`에 사례를 둔다. 느낌표 없이 제품 폴더에 파일을 더하면 문제, 느낌표가 있으면 짝은 지나가고 원고 판정으로 넘어감, 시험용 마이그레이션 폴더에 더한 파일은 짝의 대상이 아님, 제품 폴더의 파일을 고치기만 한 것은 짝의 대상이 아님이다(명세 "노트 검사의 짝")
- [ ] 짝이 쓰는 경로의 폴더에 마이그레이션 파일이 하나 이상 있는지 보는 저장소 상태 시험을 둔다. 경로를 일부러 틀리게 한 변이에서 빨개진다(명세 같은 절의 마지막 항목, `.claude/rules/tests.md`의 `tools/` 항목 "훑은 범위가 비면 실패하게 한다", 명세 검토 B1)
- [ ] 짝을 실제 실행으로 한 번 본다. 느낌표 없는 제목과 제품 폴더에 더한 파일로 검사를 돌려 빨개지는 것과, 느낌표를 붙이면 그 문제가 사라지는 것을 일지에 적는다(작업 규약 3). CI가 PR 제목을 보는 길에도 짝이 드는지 같은 실행에서 본다

### 마이그레이션 폴더의 꼴

- [ ] 제품 마이그레이션 폴더의 파일들이 명세 "저장소 상태 시험"의 둘째가 든 꼴인지 보는 저장소 상태 시험을 둔다. 번호가 `0001`부터 하나씩 오르고, 파일마다 앞 번호를 가리키며, 마지막 번호가 하나이고, `downgrade`가 없다(명세 "마이그레이션 파일", 명세 검토 S7)
- [ ] 이 저장소가 지금 통과함을 재는 시험(`test_이_저장소의_…`)과, 겹친 번호·건너뛴 번호·끊긴 사슬·`downgrade`가 든 파일을 하나씩 넣은 변이 시험(`test_…을_잡는다`)을 둔다. 훑은 파일이 하나도 없으면 실패한다(`.claude/rules/tests.md`의 `tools/` 항목)

### 검증

- [ ] CLAUDE.md의 검증 명령이 모두 초록이다
- [ ] 노트 검사는 하네스라 실제 실행 결과로 확인한다(위 짝의 마지막 항목). `src/`를 고치지 않으므로 LLM 시험의 병합 조건에 들지 않는다
