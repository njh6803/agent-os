# postgres-foundation clone_xdist 프로브

ADR 0066 결정 "테스트 데이터베이스"는 pytest-xdist의 작업자마다 템플릿 데이터베이스를 만들어 마이그레이션을 한 번 올리고, 시험마다 그것을 복제한다(`CREATE DATABASE … TEMPLATE`)고 정했다. 그리고 둘을 명세에 넘겼다. "컨테이너 하나를 작업자들이 나눠 쓰는 배치는 그 프로브가 재지 않았으므로, 템플릿 복제가 시험 하나에 얼마나 드는지와 함께 명세가 잰다"와 "여러 세션이 한 컨테이너를 함께 쓰므로 데이터베이스 이름이 세션 사이에 겹치지 않게 짓는 것도 명세가 정한다"다. 결정 "위젯 관리 서버"는 "테스트 도우미(컨테이너를 확인하고 템플릿을 만드는 픽스처)를 `tests/` 안에 하나 두고 두 패키지의 시험이 함께 쓸 수 있는지는 이 행의 명세가 그 도우미를 지으며 확인한다(어림)"고 적었다. 이 프로브는 그 셋을 장난감 시험 묶음으로 잰다. 함께 본 것은 둘이다. 동기 드라이버 없이(asyncpg뿐이다) 세션 범위 픽스처를 짓는 두 꼴과, Alembic에 연결을 넘겨 이미 도는 이벤트 루프 안에서 마이그레이션을 올리는 길이다. 여기서는 결정하지 않고 본 것만 적는다. 규약은 `docs/agents/issue-tracker.md`의 "프로브와 근거"다.

장난감(`toy/`)은 저장소의 모양을 줄인 것이다. 패키지 A(`pkg_a`, agent_os의 자리)와 B(`pkg_b`, 위젯 관리 서버의 자리)는 서로를 import하지 않고, 저마다 SQLAlchemy Core 표 정의와 Alembic 마이그레이션(판 번호를 일부러 둘 다 `0001`로 두었다)을 가진다. 공용 도우미는 `toy/tests/database.py` 하나이고 두 패키지 어느 것도 import하지 않는다. 패키지마다 다른 것(마이그레이션을 올리는 함수와 데이터베이스 이름의 접두 `toy_a`·`toy_b`)은 패키지의 `conftest.py`가 인자로 넘긴다. 시험은 A가 240개, B가 80개(합 320개)이고, 저마다 받은 데이터베이스에 붙어 줄 하나를 넣고 읽고 표 목록과 표의 판을 본다. pytest 설정은 저장소 루트의 것에서 이 측정에 걸리는 줄(`pythonpath = ["."]`, `--import-mode=importlib`, `asyncio_mode = "auto"`, `RuntimeWarning`을 오류로)을 옮겼다.

결과 표는 2026-11-18 16:12:08~16:19:45의 실행 `4c01a9f3` 하나의 값이다(측정 11회차, 측정 아님 0회차, 종료 코드 0). 같은 날 앞선 전체 실행 셋도 모두 측정 11회차, 측정 아님 0회차였고, 그 값은 범위를 적을 때만 든다. `67baa8b2`(15:35:44~15:44:56, `--basetemp`와 꼴의 표지가 없던 판), `04ca09a8`(15:45:49~15:53:34, 꼴의 표지가 없던 판), `9009ba71`(16:00:37~16:06:03, 타입을 고치기 전의 판)이다. 판의 차이는 "결과를 본 뒤 바꾼 것"에 있다.

**시간 값은 모두 부하가 있던 때의 값이다.** 측정하는 동안 같은 PC의 같은 Docker 데몬에서 같은 기능의 다른 프로브 둘(컨테이너 `pgf-stack-*`, `pgf-recover-*`)과 다른 세션의 컨테이너(`rag-engine-*`)가 함께 돌았고(조정 세션이 알렸다), 다른 세션들의 pytest(`-n 8`을 포함한다)도 같은 PC에서 돌았다(15:28 무렵 프로세스 목록에서 손으로 봤다). 프로브가 실행마다 찍은 호스트 CPU 부하는 표의 "호스트 부하" 칸이고 19~100%였다(회차로 세지 않는다). 그래서 실행 사이, 갈래 사이의 시간 차이는 부하의 차이와 가르지 못한다. 조용한 때에 다시 재야 한다.

근거의 종류는 넷이다. 프로브가 다시 낸다(`run.py`가 표지를 보고 센 회차의 값), 손으로 봤다(명령과 함께 적는다), 코드를 읽었다(파일과 줄), 어림.

## 다시 돌리기

저장소의 `pyproject.toml`과 `uv.lock`은 고치지 않는다. 도구 셋은 저장소 밖 폴더의 사본에 더해 저장소의 잠금과 함께 푼다(`.scratch/admin-login/probes/pg_stack/README.md`의 방법이다). 아래에서 `<tree>`는 저장소 밖의 빈 폴더다. 저장소 루트에서 친다.

```sh
cp pyproject.toml uv.lock README.md <tree>/
uv add --project <tree> --no-sync -r .scratch/postgres-foundation/probes/requirements.in
uv sync --project <tree> --frozen --no-install-project
uv run --project <tree> --no-sync python .scratch/postgres-foundation/probes/clone_xdist/run.py
```

- 앞의 세 줄은 이 측정이 치지 않았다. 조정 세션이 그 셋으로 미리 지어 둔 `<tree>`(세션 스크래치패드의 `pgf-tree`)를 받아 썼다. 같은 세 줄을 실제로 친 기록은 `stack/README.md`의 "다시 돌리기"에 있다. 마지막 줄은 `--work <스크래치 폴더>`를 붙여 쳤고 인자 없이는 치지 않았다. 인자가 없으면 원본 출력의 자리만 `<시스템 임시 폴더>/clone-xdist-probe/run-<실행 토큰>/`으로 바뀐다(코드를 읽었다, `run.py`의 `main`).
- 걸리는 시간: 전체 한 바퀴가 5분 26초~7분 45초였다(원본 기록의 첫 줄과 끝 줄의 시각. 서버 없음 갈래가 113초 걸린 `67baa8b2`는 9분 12초).
- 필요한 것: 도는 Docker 데몬(리눅스 엔진)과 로컬에 받아 둔 이미지 `postgres@sha256:b9f6b8ff03b62f3cfd9d9ba3fe56226a9991c79d3fb46fd46536263bf02be553`. `docker run --pull never`로 띄우므로 이미지가 없으면 받지 않고 실패한다. 그때는 먼저 `docker pull postgres@sha256:b9f6b8ff03b62f3cfd9d9ba3fe56226a9991c79d3fb46fd46536263bf02be553`을 친다. LLM은 부르지 않는다.
- 하는 일: 이름이 `clone-xdist-probe-<실행 토큰 8자>`인 PostgreSQL 컨테이너를 tmpfs와 `fsync=off`·`synchronous_commit=off`·`full_page_writes=off`로 호스트의 `127.0.0.1` 빈 포트에 띄우고, 끝나면(`finally`) 그 이름의 컨테이너만 `docker rm -f -v`로 익명 볼륨과 함께 지운다. 프로세스째 죽이면 `finally`가 돌지 않아 컨테이너가 남는다(한 번 그랬다. 그때는 `docker rm -f -v clone-xdist-probe-<실행 토큰>`으로 지운다). 비밀번호는 측정용 고정 값(`agent_os_test`)이고 그 컨테이너 밖에서는 쓰이지 않는다. pytest의 임시 폴더는 원본 출력 폴더 안에 둔다(`--basetemp`).
- `--only absent,n8,n1,migrate-each,pair,file-copy,session-loop`로 갈래를 고른다(정적 회차와 컨테이너 회차는 늘 돈다). `file-copy`의 표지는 같은 실행의 `n8` 값에 기대므로 `n8` 없이 고르면 측정 아님이 된다. 측정이 아닌 회차가 하나라도 있으면 종료 코드가 1이다.
- 타입 검사만: `uv run --project <tree> --no-sync python -m pyright -p .scratch/postgres-foundation/probes/clone_xdist`(파일 15개, 오류 0. 분석 여부는 `--outputjson`의 `summary.filesAnalyzed`로 봤다). 린트: `uv run ruff check .scratch/postgres-foundation/probes/clone_xdist`, `uv run ruff format --check .scratch/postgres-foundation/probes/clone_xdist`.
- 편집기가 이 폴더의 파일에 "sqlalchemy를 찾지 못한다"고 알리는 것은 저장소의 가상 환경에 도구 셋이 없어서다. 측정은 `<tree>`의 인터프리터로 돈다.

### 도우미 하나를 두 패키지가 함께 쓴다

도우미(`toy/tests/database.py`)는 패키지마다 다른 것 둘(마이그레이션 함수, 이름의 접두)을 인자로 받아 픽스처를 지어 내고, 패키지의 conftest가 `template_database = template_fixture(PREFIX, upgrade)`, `database = database_fixture(PREFIX, upgrade)` 두 줄로 받는다. 뿌리 conftest는 `database_url` 하나만 둔다. 시험 파일은 자기 패키지와 `tests.database`를 import한다(`pythonpath = ["."]`와 `--import-mode=importlib`로 풀린다. 저장소의 시험도 `from tests.… import`를 이미 쓴다, 손으로 봤다: `tests/` 아래 25개 파일).

표지(프로브가 다시 낸다): 도우미의 글자로 적힌 import에 `pkg_a`·`pkg_b`가 없고(`['__future__', 'asyncio', 'collections', 'contextlib', 'dataclasses', 'json', 'os', 'pathlib', 'pytest', 'pytest_asyncio', 're', 'sqlalchemy', 'time', 'uuid']`), 새 인터프리터에서 `tests.database`만 불렀을 때 `sys.modules`의 장난감 패키지가 `[]`이다. 양성 대조로 `tests.pkg_a.conftest`를 부르면 `['pkg_a', 'pkg_a.database']`가 실린다. 두 패키지는 서로와 `tests`를 import하지 않는다. 그리고 pytest를 돈 모든 회차에서 시험 기록이 A의 데이터베이스에서 A의 표 셋과 `alembic_version`만, B의 데이터베이스에서 B의 표 둘과 `alembic_version`만 봤다. `pytest_asyncio`는 세션 루프 꼴의 픽스처를 짓는 데만 쓴다.

### 세션 범위 픽스처의 두 꼴

드라이버가 asyncpg뿐이라 세션 범위 픽스처(템플릿을 만들고 지우는 것, 서버를 확인하는 것)를 짓는 길이 둘이다. 시험마다의 `database` 픽스처는 어느 쪽이든 그 시험의 루프에서 도는 비동기 픽스처다.

- `sync_run`: 동기 픽스처가 `asyncio.run`으로 코루틴을 돈다. 도우미의 기본이고 주 측정(`-n 8`, `-n 1`, 대조, 동시, FILE_COPY)의 꼴이다.
- `session_loop`: `@pytest_asyncio.fixture(scope="session", loop_scope="session")` 비동기 픽스처가 pytest-asyncio의 세션 루프에서 돈다. "세션 루프 픽스처" 갈래의 꼴이다.

둘 다 네 실행 모두 표지가 다 있었고 경고도 없었다(프로브가 다시 낸다. 템플릿 기록에 적힌 꼴을 표지로 본 것은 뒤의 두 실행이다). 시간은 둘을 가르지 못했다. 세션 루프 갈래의 pytest는 같은 실행의 `-n 8` 세 번보다 한 번 짧고(`04ca09a8`, 29.45초 대 31.26~34.87초), 두 번 길고(`9009ba71` 41.56초 대 21.38~24.28초, `4c01a9f3` 40.46초 대 26.39~33.37초), 한 번 그 범위 안이었다(`67baa8b2`, 34.89초 대 21.43~55.15초). 그 갈래는 늘 맨 끝에 돌아 부하의 차이와 가르지 못한다.

명세에 넘길 것(어림, 측정이 아니다): 저장소의 규약은 `session_loop` 쪽이다. `.claude/rules/tests.md`는 "`asyncio.run()`을 직접 부르지 않는다"고 적고, ADR 0007은 "한 저장소에 두 방식을 두지 않는다"고 적으며, 저장소에서 `asyncio.run`을 부르는 시험은 그 규칙의 예외라고 독스트링에 밝힌다(코드를 읽었다, `tests/adapters/test_openai_compatible.py` 604~607줄). 그리고 `loop_scope`를 픽스처에 적으면 비워 둔 `asyncio_default_fixture_loop_scope`에 기대지 않는다(코드를 읽었다, pytest-asyncio 1.4.0 `plugin.py` 927~930줄). 두 꼴이 실패할 자리는 "재지 못한 것"에 있다.

### 마이그레이션에 연결을 넘기기

패키지의 `upgrade(connection)`은 `alembic.ini` 없이 `Config()`를 짓고 `config.attributes["connection"]`에 받은 동기 연결을 넣어 `command.upgrade(config, "head")`를 부른다. `env.py`는 그 연결로 `context.configure`하고 엔진을 만들지도 `asyncio.run`을 부르지도 않는다. 도우미는 비동기 엔진의 `engine.begin()` 안에서 `await connection.run_sync(upgrade)`로 부르고 블록을 나올 때 커밋한다.

이 길은 이미 도는 루프 안의 세 자리에서 모두 됐다. `sync_run`의 `asyncio.run` 안(템플릿), `session_loop`의 세션 루프 안(템플릿), 대조 갈래의 시험 루프 안(시험마다)이다. 표지(프로브가 다시 낸다)는 템플릿을 새 연결로 열어 본 표가 그 패키지의 표와 `alembic_version`이고 판이 `0001`인 것, 그 템플릿에서 복제한 시험과 대조 갈래의 시험이 본 판이 `["0001"]`인 것이다. 새 연결에서 보였으므로 커밋됐다. 막히지 않았으므로 `.scratch/admin-login/probes/pg_stack/alembic_async/env.py`의 꼴과 `asyncio.to_thread`로 물러서는 대조는 짓지 않았다.

### 동시 두 실행과 이름

이름은 `<접두>_template_<uuid4 hex>`와 `<접두>_test_<uuid4 hex>`다. pytest 실행 둘(`-n 4`씩)을 같은 컨테이너에 함께 띄웠고, 둘 다 표지가 다 있었으며 둘이 만든 이름 656개가 모두 달랐고, 끝난 뒤 `toy_`로 시작하는 데이터베이스가 남지 않았다(프로브가 다시 낸다. 남은 데이터베이스는 모든 갈래에서 0이었다). uuid4라 겹칠 확률이 무시할 만하다는 것은 어림이고, 이 측정은 656개만 봤다.

### pytest가 끝나지 않던 실행

`--basetemp`를 주지 않던 판에서 서버 없음 갈래의 pytest가 두 번 오래 걸렸다.

- 첫 전체 실행 `74ec6aca`: 출력이 `[100%]`까지 찍힌 뒤 요약 줄 없이 5분 넘게 멈췄고, 그때 남은 프로세스는 pytest의 주 프로세스 하나였다(작업자는 끝났다). 손으로 봤다(출력 파일과 `Get-CimInstance Win32_Process`). 그 실행을 끊었고, `finally`가 돌지 않아 남은 컨테이너를 손으로 지웠다. 그래서 그 실행에는 회차의 셈이 없다.
- `--only absent`로 돈 `d45eac33`: 9.53초.
- 전체 실행 `67baa8b2`: 113.66초(벽시계 119.25초). 도는 도중(시작 뒤 55초 무렵) 주 프로세스의 커널 시간이 32.2초, 사용자 시간이 7.7초였다(손으로 봤다, `Win32_Process`의 `KernelModeTime`·`UserModeTime`). 같은 실행의 `-n 8`은 같은 판으로 21.43~55.15초였다.
- `--basetemp`를 준 뒤 세 번: 11.16초, 7.78초, 10.17초. 멈춘 적이 없다.

해석(어림): pytest 9.1.1은 세션 끝(`pytest_sessionfinish`)에, 임시 폴더의 뿌리가 정해졌으면 그 뿌리의 정리 작업을 돌린다. 사용자가 뿌리를 주지 않았으면 그것은 `pytest-of-<사용자>` 아래 옛 `pytest-<번호>` 폴더를 셋만 남기고 지우는 것이다(코드를 읽었다, `_pytest/tmpdir.py` 315~340줄). 그 폴더는 이 PC의 다른 세션들이 함께 쓰고, 15:43 무렵 `pytest-*`가 18개 있었다(손으로 봤다). 커널 시간이 큰 것은 파일 지우기와 맞는다. 그러나 xdist의 주 프로세스가 그 뿌리를 정하는지(xdist 코드는 읽지 않았다), 멈춘 자리가 실제로 그 정리였는지는 보지 않았고(스택을 찍기 전에 끊었다), `--basetemp` 없이도 9.53초인 실행이 있어 `--basetemp`가 멈춤을 없앴다고 가르지도 못했다. 저장소의 러너(`tools/run_checks.py`)는 `--basetemp`를 주지 않는다(코드를 읽었다, grep).

## PR 봇이 짚은 틈

PR 606의 봇(CodeRabbit) 첫 회차가 이 프로브에 Critical 하나와 Major 여덟(#11~#18)을 냈다. 위 결론은 그대로 선다. 프로브 코드는 고치지 않았다(#12의 주석과 위 "결과를 본 뒤 바꾼 것"의 지나친 문장만 고쳤다). 고치면 다시 돌려 이 README와 명세의 수치를 바꿔야 하기 때문이다. 다시 돌릴 사람은 항목마다의 고침을 먼저 넣는다. 판정은 측정한 세션의 원본 출력(`run-*` 여섯)과 잰 판의 라이브러리 소스(pytest 9.1.1, SQLAlchemy 2.1.8)로 했다.

- **Critical 도우미의 `repr`(`toy/tests/database.py`의 `Database`).** pytest는 실패 출력에 시험 함수의 인자를 `saferepr`로 찍고, 장난감 `Database`의 기본 `repr`에는 비밀번호가 든 주소가 든다. 남은 출력 어디에도 `Database(url=`이 없어 기록에는 실리지 않았고, 그 비밀번호는 공개된 측정용 고정 값이다. 명세는 제품 도우미의 `repr`에 비밀번호를 싣지 않게 정했다("시험 데이터베이스의 이름과 도우미"의 "주소를 다루는 법"). 고침: 주소 칸을 `field(repr=False)`로 둔다.
- **#11 파생 주소의 질의 문자열(같은 파일의 `url_for`).** 경로만 시험마다의 이름으로 바꾸므로, 질의의 `database`가 남으면 그 이름을 덮는다. 이 프로브의 주소에는 질의가 없어(`run.py`가 짓는 주소) 기록에 닿지 않는다. 명세는 질의가 든 주소를 받지 않게 정했다(같은 절). 고침: 질의가 든 주소를 받지 않는다.
- **#12 세션 픽스처 꼴의 표지.** `style` 칸은 고른 꼴의 값이 작업자까지 닿았다는 것까지만 가른다. 위 "결과를 본 뒤 바꾼 것"의 문장과 `run.py`의 주석이 그보다 많이 주장해 고쳤다. 고침: 그 꼴의 픽스처 안에서 따로 표지를 남기고(세션 루프 꼴이면 돈 루프가 pytest-asyncio의 세션 루프인지), 그 표지로 센다.
- **#13 상대 경로 `--work`.** 자식 pytest가 다른 폴더에서 같은 상대 경로를 받는다. 기록된 실행은 절대 경로였다(원본 `raw.log`의 머리). 고침: 받자마자 절대 경로로 바꾼다.
- **#14 서버 설정 검사에 떨어진 컨테이너.** 설정 검사(`fsync=off` 등)에 떨어져도 뒤의 갈래가 그 서버로 돈다. 기록된 실행은 컨테이너 회차가 측정이었다. 고침: 검사를 지난 서버로만 뒤의 갈래를 띄운다.
- **#15 동시 회차의 `wall_s`.** 두 pytest를 차례로 거둬 둘째의 걸린 시간이 첫째의 끝까지 늘 수 있다. 이 틈은 동시 회차에만 걸리고, 위 표에서 그 회차는 두 줄(94.78초, 94.83초)이다. 본문과 명세는 그 회차의 시간으로 pytest가 스스로 적은 초(88.45, 88.46)를 쓴다. 두 출력 파일의 마지막 쓰기가 21ms 차이라 부풀림은 수십 ms다. 고침: 프로세스마다 마감과 끝난 시각을 따로 둔다.
- **#16 `FILE_COPY`의 기준에 든 측정 아닌 회차.** 판정에 떨어진 `n8` 회차의 WAL 값도 기준에 든다. 기록된 `n8`은 모두 측정이었다. 고침: 측정인 회차만 기준에 넣는다.
- **#17 동시 회차가 도중에 실패할 때.** 띄운 pytest를 거두지 않고 다음 회차로 간다. 기록된 실행은 측정 아님이 0이라 그 예외가 나지 않았다. 고침: 띄운 프로세스를 바로 목록에 넣고 `finally`에서 끝내고 거둔다.
- **#18 두 pytest가 실제로 겹쳤는지.** 판정에 겹침의 표지가 없다(규칙 위반이다). 원본으로는 겹침이 선다. 둘 다 16:16:29에 띄웠고(원본 `raw.log`) 각자 88.4초를 돌았으며, 작업자 여덟의 JSONL 마지막 쓰기가 16:18:02.57~03.14에 몰렸다(원본을 손으로 봤다). 고침: 실행마다 데이터베이스 일의 시작과 끝을 같은 시계로 적고, 두 구간이 겹친 회차만 센다.

둘째 회차는 이 프로브에 Major 다섯을 냈다. 넷은 위 넷과 같은 자리다(동시 회차의 `wall_s`는 #15, 동시 회차가 도중에 실패할 때는 #17, `FILE_COPY`의 기준에 든 `n8`은 #16, 컨테이너 설정 확인에 실패한 서버는 #14). 새 것은 하나다.

- **WAL 위치를 읽는 함수(`run.py`의 `snapshot`).** `pg_current_wal_lsn()`은 디스크에 쓴 끝을 돌려주고, 버퍼에 넣었지만 아직 쓰지 않은 WAL은 빠진다. 이 프로브는 `synchronous_commit=off`로 띄우므로 끝의 스냅숏에서 그 몫이 그 실행의 차에서 빠질 수 있다. 그래도 `FILE_COPY`의 결론(시험당 WAL이 기본 전략의 절반보다 적다)은 선다고 본다. 쓰지 않은 WAL은 WAL 버퍼의 크기를 넘을 수 없고, 기본 설정에서 그 크기는 `shared_buffers`의 1/32(이 서버의 기본 128MB면 4MB)다(PostgreSQL의 기본값을 기억으로 적었다, 어림). `FILE_COPY`의 시험당 228.8KB에 실행 전체의 몫 4MB를 더해도 시험이 둘 이상인 실행이면 기본 전략의 절반(2260KB 남짓)에 닿지 않는다. 고침: 두 스냅숏 모두 `pg_current_wal_insert_lsn()`을 읽는다.

## 재지 못한 것

- 부하가 없는 때의 시간. 위 굵은 글씨 문단.

- 세션 픽스처 두 꼴의 실패 양식. `sync_run`은 이미 도는 루프 안에서 처음 불리면(비동기 시험 본문의 `request.getfixturevalue` 등) `asyncio.run`이 거부할 것이고, `session_loop`은 세션 루프에서 만든, 루프에 매인 객체(풀을 쥔 엔진 등)를 시험의 루프에서 쓰면 실패할 것이다. 둘 다 어림이고 갈래를 두지 않았다. 장난감의 세션 픽스처는 템플릿 이름(문자열)만 넘긴다. ADR 0007의 "setup과 teardown이 다른 태스크" 문제는 anyio 취소 범위를 쥔 자원의 것이고, 장난감의 세션 픽스처는 연결을 쥔 채 넘기지 않아 그 자리를 보지 않았다.
