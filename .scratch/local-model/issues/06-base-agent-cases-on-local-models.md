# 06: 기본 에이전트의 사례를 두 로컬 모델로 기록한다 — base-agent의 실제 모델 시험을 고치지 않고 모델 자리만 바꿔 한 번 돌린다

**What to build:** base-agent와 answer-eval의 저자가 기본 에이전트(assistant)의 실제 모델 사례가 두 로컬 모델(A.X 4.0 Light, gpt-oss-20b)에서 어떻게 되는지의 기록을 받는다(스토리 28). 세션은 03의 명령 `run`의 `--` 뒤에 base-agent 05의 실제 모델 시험을 고르는 명령을 넣어 한 번 돌리고, 사례마다 두 모델의 통과와 실패를 기록한다. 통과를 요구하지 않는다. 실패한 사례는 스킬 문구(base-agent)나 모델 고르기(answer-eval)의 입력이 된다. 상시 시험을 더하지 않는다.

이 기능의 마지막 티켓이다(ADR 0058 결정 "기본 에이전트의 사례"). 다른 티켓은 base-agent를 기다리지 않고 calc 예시로 먼저 끝난다. base-agent의 실제 모델 시험(base-agent 05, 사례 열넷)에는 지금 모델을 바꿀 자리가 없어, 이 티켓을 나누며 base-agent 05의 차림에 이음매 하나를 더했다. 모델 차림(모델 플러그인의 이름, 복사한 플러그인 루트에 더할 모델 파일, 그 모델의 키 검사)의 목록이 그 시험 모듈의 한 자리에서 정해지고, 사례가 그 목록으로 매개변수화되어 CLI의 `--model`과 `serve`의 기본 모델이 모두 차림을 따른다. 기본 목록은 저장소의 Anthropic 모델 하나다. 이 티켓은 사례를 고치지 않고 그 목록만 두 로컬 모델의 차림으로 바꿔, pytest 한 번(모델 서버 대여 한 번)으로 두 모델을 돈다. pytest를 모델마다 따로 부르면 둘째 실행이 시작할 때 03이 넣은 basetemp를 지우고 JUnit XML을 덮어써(pytest 9.1.1의 `_pytest/tmpdir.py` `getbasetemp`와, 파일을 `"w"`로 여는 `_pytest/junitxml.py`를 읽었다), 기록 묶음의 통과 수와 토큰 합계에 둘째 모델 것만 남는다. ADR 0058이 든 세 갈래(요청을 셋으로 가르기, 검색한 뒤 답하기, 정해진 문장을 글자 그대로 내기)는 그 사례들에 든다.

근거는 `.scratch/local-model/spec.md`의 "고칠 자리의 묶음"의 E 줄과 그 2026-11-12 주석(06의 이음매)이다. 앞선 결정은 ADR 0058의 결정 "기본 에이전트의 사례"와 그 거부한 안(사례를 answer-eval에 넘기는 것, 사례의 통과를 이 기능의 끝 조건으로 하는 것), 결정 "한 번 실패하면 실패"와 무효 회차(명세 "모델 서버를 띄우는 명령")다. 돌릴 시험은 `.scratch/base-agent/issues/05-real-model-assistant-answers-with-sources.md`의 사례 열넷이고, 그 시험이 띄우는 가짜 문서 검색 서버는 base-agent 02다.

**Blocked by:** 05(모델 서버 어댑터와 로컬 모델 시험. 이 티켓이 두 로컬 모델에 붙는 길이다). 그리고 기능 base-agent(그 티켓 05의 실제 모델 시험과 이음매가 서야 돌릴 사례가 있다. 2026-11-12에 base-agent의 티켓 04~07은 ready-for-agent다)

**Status:** ready-for-agent

### 차림

- [ ] base-agent 05의 시험 모듈에 모델 차림의 목록을 정하는 한 자리가 있고 사례가 그 목록으로 매개변수화되는지 본다. 있으면 그 독스트링이 적은 법대로 그 목록만 바꾼다. base-agent 05가 그 자리 없이 닫혀 있거나 차림이 모델 파일을 더하지 못하거나 사례가 목록으로 매개변수화되지 않으면, 이 티켓이 그 자리를 더하거나 넓힌다. 그때도 사례의 단언은 고치지 않고, `-m llm`의 실제 Anthropic 모델로 그 시험이 여전히 초록인 것을 본다
- [ ] 두 로컬 모델의 차림은 복사한 플러그인 루트에 모델 파일을 하나씩 더한다. 모양은 05의 로컬 모델 시험과 같다(`base_url`과 `model_id`는 03의 환경 변수 여섯에서, `temperature = 0`, `max_tokens`는 적지 않음, 키 변수가 있으면 `api_key_env`에 그 이름). 환경 변수 이름은 03의 상수를 import해 쓴다

### 돌리기

- [ ] 03의 명령으로 돌린다. `--yes` 없이 친 예상 비용을 사용자에게 보여 확인받은 뒤 `--yes`로 다시 치고, `--` 뒤에 base-agent 05의 사례 전부를 고르는 pytest 명령 하나를 넣어 두 모델을 한 회차에 돌린다
- [ ] 통과를 요구하지 않으므로 사례의 실패는 다시 돌릴 까닭이 아니다. 무효 회차(서버 쪽 사정으로 판정을 내지 못한 회차)만 비용 확인을 다시 받고 다시 띄우며, 연달아 둘이면 멈춰 보고한다. 연달은 수는 일지와 03이 상태 폴더에 남긴 회차 파일로 센다. 끊긴 뒤 이어받은 세션도 그 둘로 센다

### 기록

- [ ] 명령이 끝난 그 턴에 기록 묶음과 무효 회차의 까닭을 일지에 옮긴다. 옮기기 전에 끊겼으면 이어받은 세션이 상태 폴더의 회차 파일에서 옮긴다
- [ ] 사례마다 두 모델의 통과와 실패(03이 받은 JUnit XML의 시험 이름에 차림이 든다), 실패한 사례의 실패 단언을 기록 묶음(시험한 커밋, 두 모델, 서빙 엔진의 판과 서버 옵션, GPU, 통과 수와 토큰 합계, 걸린 시간, 실제 단가, Terraform 출력에서 가린 것이 있었는지)과 함께 `.scratch/local-model/probes/README.md`의 날짜 절에 적는다. 돌린 명령도 적어 같은 기록을 다시 낼 수 있게 한다
- [ ] 세 갈래(요청을 셋으로 가르기, 검색한 뒤 답하기, 정해진 문장을 글자 그대로 내기)가 어느 사례인지와 그 결과를 따로 적는다
- [ ] 실패한 사례를 받는 기능에 넘긴다. 모델 고르기의 입력은 오픈 모델로 answer-eval을 다시 돌리는 pilot-release의 기능 계획 본문(`.scratch/pilot-release/plan.md`)에 적는다. answer-eval의 Blocked by에는 local-model이 없어 이 티켓보다 먼저 닫힐 수 있고(명세 "다른 기능에 넘기는 것"의 answer-eval 항목), pilot-release는 deploy-package를 거쳐 local-model에 막혀 이 티켓 뒤에 돈다. 기능 계획을 고쳤으니 `uv run python tools/plan_table.py`를 돈다. 그리고 스킬 문구를 고칠 일은 일지의 "다음"에 적어 사용자가 고르게 한다. 기록 묶음을 일지와 PR 코멘트에 옮긴다
- [ ] 이 티켓을 닫는 커밋이 기능 계획(`.scratch/local-model/plan.md`)에 `**끝:**` 줄을 적고 `uv run python tools/plan_table.py`를 돌린다

### 검증

- [ ] 시험 코드를 고치지 않았으면 손으로 치는 다섯이다. 이음매를 더했으면 `-m llm`도 친다
