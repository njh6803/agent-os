# mcp-http 명세: 원격 MCP 서버에 매니페스트의 주소로 실행마다 붙고, 취소된 실행에서도 종료 요청을 보낸다

Status: ready-for-agent

슬라이스 7(`mcp-http`). 설계는 설계 인터뷰(일지 2026-11-09-1229)와 ADR 0049가 정했고, 이 명세는 그 결정을 바꾸지 않고 자리와 문구와 시험을 채운다. ADR이 명세에 넘긴 자리 둘(닫기 보호의 자리, 실패 문구의 쿼리 문자열)은 아래 "닫기"와 "실패 문구"가 정한다. 이 명세는 `/to-spec mcp-http`로 새 세션에서 썼고 설계 인터뷰를 다시 열지 않았다(일지 2026-11-09의 mcp-http-spec 일지). 용어는 `CONTEXT.md`의 MCP 서버, 전송, 원격 MCP 서버, 도구, 도구 연결(실패 원인 `tool_connection`), 실행, 이벤트, 트레이스, 어댑터, 포트, 운영자를 따른다. "코드를 읽었다"는 이 브랜치의 기준 커밋 `1d5d0ed8`(ADR 0049를 들인 origin/main)의 코드와, 저장소 `.venv`의 mcp 2.3.0·httpx2 2.13.0·httpcore2 2.13.0·anyio 4.15.1·pydantic 2.13.5다.

**넘겨받은 것은 열아홉이다.** (1) 매니페스트의 모양. `transport`는 `"stdio"`·`"http"`의 닫힌 값이고 없으면 `"stdio"`다. http 모양은 `url`과 선택 표 `[server.headers]`(헤더 이름 → 환경 변수 이름)이고 `secret_args`는 두 모양이 같이 쓴다. `url`은 `http`·`https`만 받고 사용자 정보가 들면 거부하며, 환경 변수 이름은 글자·숫자·밑줄 꼴만 받고, 한 모양의 칸을 다른 모양에 적으면 모르는 칸으로 거부된다. sdk에는 모양마다 모델이 하나씩 서고(`StdioServer`, `HttpServer`) `transport`로 가르는 합이 `McpServer`다. `openapi.json`에는 두 모양이 oneOf로 서고 생성 TS 타입도 둘로 갈리며 `schema_version`은 `"1"` 그대로다(ADR 0049 결정 "매니페스트"). (2) 주소는 매니페스트에 글자 그대로 적고 관리 API의 매니페스트 응답과 실패 문구에 실린다(결정 "주소"). (3) 접속은 실행마다 어댑터가 접속 직전에 헤더의 환경 변수를 읽어 `httpx2.AsyncClient`를 만들고(값 전체를 그대로 싣고, 기한은 mcp의 기본값, `trust_env`는 기본값) mcp의 `streamable_http_client`에 넘겨 세션을 열고 도구 목록을 읽는 것이다. 그 뒤는 stdio와 같은 연결이고 도구마다 `ToolSpec.server`에 플러그인 이름이 실린다(결정 "접속"). (4) 여는 동안의 실패는 stdio와 같은 자리에서 `ConnectionError`가 되고 문구는 `MCP 서버 <이름>(<주소>)에 붙지 못했다: <원인>`이며, 환경 변수가 없으면 원인은 `헤더 <헤더 이름>의 환경 변수 <변수 이름>이 없다`다. 헤더 값은 문구에도 원인에도 트레이스에도 싣지 않고, core는 그 예외를 원인 `tool_connection`의 `run_failed`로 쓰며, 재시도와 접속 기한의 칸은 없다(결정 "실패"). (5) 닫기는 실행 기한이나 `serve` 종료로 취소된 실행에서도 2초 안에 세션 종료 요청(DELETE)을 서버에 보내고 클라이언트를 닫는 것이다. 보호의 자리는 명세의 프로브가 정하고, 프로브가 ADR의 첫째 안(라이브러리 문맥 닫기를 `CancelScope(shield=True)`로 감싼다)이 서지 않는 쪽으로 나오면 대안으로 가되 ADR 0049의 이력에 쌓고 그 문장에 포인터를 단다. 프로브는 종료 요청의 도달만이 아니라 기한이 걸린 실행이 지금처럼 시간 초과의 `run_failed`로 끝나는지도 본다(결정 "닫기", 설계 일지의 "다음"). (6) `httpx2`를 런타임 직접 의존으로 선언하고 `>=2.13,<3`으로 묶는다(결정 "의존"). (7) 시험 픽스처는 지금의 stdio 픽스처와 같은 `MCPServer`를 streamable HTTP로 루프백의 빈 포트에 띄운 서버이고, 사례는 도구 목록·호출·`ToolSpec.server`, 헤더 값이 서버에 닿음, 헤더 변수 없음, 꺼진 서버가 `tool_connection`으로 끝남, 취소된 실행에서 종료 요청이 닿음, calc 예시가 http 모양으로 도구를 써 트레이스가 남음이다. `plugins/mcp/`에 http 모양의 예시는 두지 않는다(결정 "시험"). (8) 범위 밖은 접속을 미리 확인하는 길(diag-bundle), 운영자의 서버 파일과 신뢰 수준·도구 정의 해시(mcp-trust), SSE 전송, OAuth, 재시도, 접속 기한의 칸이다(결정 "범위 밖"). (9) 계약 변경이 첫 티켓이고 다른 티켓을 막는다. 관리 화면의 테스트 픽스처와 스토리 넷이 `transport`를 더해야 하고, `[server]`에 `command`가 없는 거부 문구를 든 스토리의 글은 운영자 파일의 문구를 흉내 낸 임의의 글이라 그대로 두며, e2e의 stdio 매니페스트도 그대로다(ADR 0049 Consequences "계약 변경이 첫 티켓이다"와 그 이력 2026-11-10). (10) 구현 티켓이 함께 고칠 자리는 `pyproject.toml`의 주석 둘, 어댑터의 모듈 독스트링과 실패 문구, `.claude/rules/sdk.md`의 `[server]` 문장, `.claude/rules/adapters.md`의 MCP 항목 셋, `.claude/rules/core.md`의 포트 표와 실패 정책, import-linter의 금지 목록 둘이다(Consequences "구현 티켓이 함께 고칠 자리"). (11) 실패 문구의 주소에서 쿼리 문자열을 뺄지는 명세가 원칙 V에 묶어 정하고, 쿼리가 든 주소의 연결 실패와 로그 경로를 시험 사례로 둔다(Consequences "문구에 실리는 것과 실리지 않는 것", PR #499 둘째 회차 보류). (12) 구현 티켓의 수락에 "`secret_args`가 있는 도구를 http 모양의 서버에 부르며 루트 로거를 DEBUG로 켠 테스트에서 그 값이 로그에 나타나지 않는다"를 넣고 막는 자리는 구현 티켓이 정한다(Consequences "로그"). (13) 취소된 실행의 끝이 종료 요청만큼 최대 2초 늦고 정상 종료는 늦지 않는다는 어림을 프로브가 잰다(Consequences "닫는 데 시간이 든다"). (14) `schema_version`을 `"1"`로 두는 근거를 ADR 0008의 선택 칸 선례로 매니페스트 절에 한 문장 적는다(PR #499 둘째 회차 보류). (15) HTTP 종료의 회귀 시험에 실행 기한 초과의 결말(종료 요청의 전달과 원인 `timeout`의 `run_failed`)을 더한다(같은 보류). (16) `CONTEXT.md`의 원격 MCP 서버 항목에 `transport = "http"`가 streamable HTTP를 뜻한다는 한 줄을 더한다(같은 보류). (17) 평문 http로 인증 헤더를 보내는 것을 운영자가 명시적으로 허락하는 표지는 결정 변경이라 이 명세가 정하지 않고, mcp-trust 서버 파일의 안으로 그 기능 계획에 적어 그 설계에서 사용자에게 묻는다(이 세션의 지시문이 이어받은 상태). (18) `[server.headers]`의 환경 변수 이름을 mcp-trust 서버 파일의 허락 목록으로 좁히는 요구는 그 기능 계획에 이미 적혔다(설계 일지의 "다음". 이 명세는 확인만 했다). (19) 기능 계획의 수락 둘(시험용 원격 MCP 서버에 calc 예시가 주소로 붙어 도구를 쓰고 트레이스가 남는다, 서버를 끈 채 돌린 실행이 원인 `tool_connection`으로 끝난다)과 approval-rules와의 접점(두 행이 같은 어댑터 파일을 고치므로 나중에 병합하는 쪽이 충돌을 풀고 원격 MCP 서버의 도구에도 `ToolSpec.server`가 실리는지를 시험으로 본다)이다(`.scratch/mcp-http/plan.md`, ADR 0049 Consequences "approval-rules와의 접점").

**열넷은 명세가 넘겨받은 것 안에서 스스로 정했고 각 절 제목의 괄호에 "명세가 정했다"로 표시한다.** 판별자의 갈래, `url` 검사의 수단, 헤더 이름의 검사, 거부 문구의 위치와 스토리, 환경 변수 없음이 여럿일 때의 문구와 값의 판정, 응답 훅의 역할, 실패 문구의 주소 모양, 오류 응답의 상태를 원인에 덧붙이는 것, 닫기 보호의 자리, 종료 요청의 모양과 실패 처리, 세션을 여는 자리의 나뉨, 시험 픽스처의 모양과 더한 사례, 고칠 자리의 묶음, 실제 모델 시험 하나의 모양. 그 가운데 "오류 응답의 상태"는 설계가 묻지 않은 자리를 이 명세가 재어 찾은 것이다(라이브러리가 401을 상태 코드 없는 예외로 바꾼다).

**이력은 둘이다.** ADR 0049의 2026-11-09 이력 "닫기 보호는 라이브러리 문맥을 닫은 뒤의 finally에 두고 종료 요청은 어댑터가 직접 보낸다"와 "오류 응답의 상태를 원인에 덧붙인다". 둘 다 이 명세와 같은 커밋에서 초안을 쓰고 사용자가 승인했다(작업 규약 5, 일지 2026-11-09-1611의 "승인"). 앞의 것이 거짓으로 만드는 결정 "닫기"의 문장(종료 요청은 라이브러리 문맥의 `finally`에서 나가고 어댑터는 그 문맥을 닫는 호출을 감쌀 수 있을 뿐이라는 문장)에 포인터를 단다(`.claude/rules/adr.md`). 뒤의 것은 결정 "실패"에 더하는 것이라 본문의 문장을 거짓으로 만들지 않아 포인터가 없다. 이 명세의 초안은 실패 문구의 주소에서 쿼리 문자열과 조각을 떼는 결정도 같은 이력에 적고 결정 "주소"에 포인터를 달았으나, 사용자가 같은 승인에서 주소 전체를 골라 그 문단과 포인터를 걷었다. 주소는 ADR 결정 "주소" 그대로 실리고 떼는 안은 아래 "실패 문구"의 거부한 안이다.

**거부한 안은 열하나이고 각 절의 "거부한 안:" 표시에 있다.**

측정은 `.scratch/mcp-http/probes/`의 둘이다. `http_close.py`(픽스처 서버 `http_fixture_server.py`와 `linux.sh`가 한 프로브다)와 `manifest_shape.py`이고 결과는 그 `README.md`다. 이 명세에서 "쟀다"는 그것을 가리키고, 코드를 읽은 것과 어림은 그렇게 적는다. Windows는 이 PC, Linux는 Docker 컨테이너(`python:3.12.10-slim-bookworm`, WSL2 커널)다. 매니페스트 모양은 OS를 가르지 않아 Windows에서만 쟀다.

(2026-11-09 명세 검토와 to-tickets: 검토(`spec-reviewer`)는 막는 문제 둘과 고칠 것 일곱, 문구 여섯을 냈다. 막는 문제의 하나는 묶음 A만 병합된 main이다. `McpServer`가 합이 되면 어댑터와 모델을 만드는 자리 열 곳이 A 안에서 바뀌어야 하는데, 그때 어댑터가 http 모양을 어떻게 다루는지 정하지 않았다("계약과 관리 화면"의 주석). 다른 하나는 서버가 JSON-RPC 오류 글에 헤더 값을 담아 돌려주면 그 글이 실패 문구와 트레이스에 실리는 것이다("실패 문구"의 주석). 고칠 것은 리디렉션의 틀린 전제("닫기"의 주석), 응답 훅이 지나간 응답의 상태를 붙이는 것("실패 문구"), ADR 0049 결정 "닫기"의 포인터, DEBUG 로그 시험의 자리와 종료 요청의 세 조각을 한 묶음에 두는 것("고칠 자리의 묶음"), 빠진 시험 사례(스토리 12·14·15와 결정 셋, Testing Decisions의 주석), 헤더 이름과 변수 이름 패턴의 계약 표시("매니페스트")다. 보고의 문장은 그대로 옮기지 않았다. 본 세션이 코드를 읽어 대 본 뒤 각 절에 같은 머리의 주석으로 적었다(일지 2026-11-09-2138). 옛 문장은 지우지 않고 주석이 바로잡는다. 서두의 수는 이렇게 바뀐다. **둘은 사용자가 이 검토 뒤에 골랐다.** 서버가 되울린 헤더 값을 실패 문구에서 가리는 것("실패 문구")과, 어댑터가 보내는 종료 요청이 같은 출처의 메서드를 지키는 리디렉션만 따르는 것("닫기")이다. 고른 라벨과 설명의 원문은 일지 2026-11-09-2138의 "결정"이다. 명세가 정한 것은 열넷에 다섯이 더해져 열아홉이다(A의 http 갈래가 내는 임시 실패, 헤더 패턴의 계약 표시, 프로토콜 헤더 이름의 거부, 가리기의 세부, 리디렉션 판정을 짓는 수단). 이력은 셋이다(셋째는 ADR 0049의 2026-11-09 "서버가 되울린 헤더 값을 실패 문구에서 가린다". 결정 "실패"와 요약, Consequences "문구에 실리는 것과 실리지 않는 것"의 문장에 포인터를 단다). 사용자가 같은 자리에서 결정 "닫기" 첫 문장과 요약 문장에 첫째 이력의 포인터를 다는 것도 골랐다. 거부한 안은 열하나에 일곱이 더해져 열여덟이다(되울림의 둘, 리디렉션의 셋, 프로토콜 헤더 이름을 받기, http 서버를 건너뛰기). 넘겨받은 것 (19)의 approval-rules는 2026-11-08에 끝났다(`.scratch/approval-rules/plan.md`의 끝 줄). 그래서 어댑터의 충돌을 푸는 쪽은 이 기능이고, 원격 MCP 서버의 도구에 `ToolSpec.server`가 실리는지는 그대로 접속 묶음의 사례다.)

## Problem Statement

운영자 관점. 지금 MCP 서버는 플러그인이 띄우는 프로세스(stdio) 하나라, core가 실행마다 도구에 연결할 때 서버 프로세스가 새로 뜬다. 임베딩 모델과 색인을 올리는 문서 검색 서버(ADR 0048)는 그래서 질문마다 시작 비용을 치른다. 이 명세가 잰 바로는 보호 없는 닫기는 취소된 실행에서 세션 종료 요청을 보내지 않으므로(`http_close.py`의 `deadline_plain`), 주소로 붙는 전송을 더하기만 하면 실행 기한에 걸린 실행마다 서버 쪽 세션이 유휴 만료(mcp 2.3.0의 기본 1800초. ADR 0049)까지 남는다.

매니페스트 저자 관점. 주소로 붙는 서버를 적을 칸이 없다. 토큰을 실으려면 값을 매니페스트에 적을 수밖에 없고 그것은 원칙 V(이벤트와 로그에 비밀을 싣지 않는다)와 매니페스트가 비밀을 들지 않는다는 ADR 0009의 방향에 어긋난다.

운영자 관점(실패). 원격 MCP 서버가 꺼졌을 때, 토큰이 틀렸을 때 무엇이 보이는지가 정해져 있지 않다(기능 계획의 "설계 인터뷰가 먼저 볼 것"). mcp 2.3.0은 401처럼 본문이 JSON-RPC 오류가 아닌 오류 응답을 상태 코드 없이 "Server returned an error response"라는 예외로 바꾸므로(쟀다. `http_close.py`의 `unauthorized`. 글만 든 401이다) 라이브러리의 글만 옮기면 꺼진 서버와 틀린 토큰이 문구에서 갈리지 않고, diag-bundle의 수락(일부러 깨뜨린 배포에서 묶음만 보고 원인을 가른다)이 서지 않는다.

## Solution

mcp 플러그인의 `[server]` 표에 `transport = "http"`와 `url`을 적고, 헤더가 필요하면 `[server.headers]`에 헤더 이름마다 환경 변수 이름을 적는다. 런타임은 실행마다 그 주소에 streamable HTTP로 붙어 도구 목록을 읽고 도구를 부른 뒤 닫는다. 헤더 값은 접속 직전에 환경에서 읽어 요청에만 싣고 어디에도 기록하지 않는다. `transport`가 없는 지금의 매니페스트는 stdio로 읽혀 그대로 돈다.

```toml
schema_version = "1"
kind = "mcp"
name = "doc-search"
version = "0.1.0"

[server]
transport = "http"
url = "http://rag-engine:8000/mcp"

[server.headers]
Authorization = "DOC_SEARCH_TOKEN"
```

헤더 값은 환경 변수의 값 전체라 `DOC_SEARCH_TOKEN`에 `Bearer …`까지 담는다. 여는 동안 실패하면 실행은 지금처럼 원인 `tool_connection`의 `run_failed`로 끝나고, 문구 `MCP 서버 doc-search(http://rag-engine:8000/mcp)에 붙지 못했다: <원인>`의 주소는 매니페스트의 `url` 그대로이며, 서버가 오류 응답을 돌려줬으면 원인 끝에 `(HTTP 401 Unauthorized)`처럼 상태가 붙어 꺼진 서버(`ConnectError: All connection attempts failed`)와 틀린 토큰이 갈린다. 연결을 닫을 때는 실행 기한이나 `serve` 종료로 취소된 실행에서도 2초 안에 세션 종료 요청을 보내고, 기한의 결말(원인 `timeout`)은 그대로다.

## User Stories

1. 운영자로서, 임베딩 모델과 색인을 올린 문서 검색 서버를 한 번만 띄워 두고 실행마다 거기에 붙게 하고 싶다. 그래야 질문마다 시작 비용을 치르지 않는다.
2. 매니페스트 저자로서, `[server]`에 `transport = "http"`와 `url`만 적어 원격 MCP 서버를 가리키고 싶다. 그래야 stdio 플러그인과 같은 자리에 같은 방식으로 플러그인을 둔다.
3. 매니페스트 저자로서, 지금 있는 stdio 매니페스트를 한 글자도 고치지 않고 그대로 쓰고 싶다. 그래야 이 기능이 들어와도 배포가 깨지지 않는다.
4. 매니페스트 저자로서, 토큰 같은 헤더 값을 매니페스트에 적지 않고 환경 변수 이름만 적고 싶다. 그래야 비밀이 저장소와 관리 API 응답에 남지 않는다.
5. 운영자로서, 헤더의 환경 변수를 빠뜨렸을 때 어느 헤더의 어느 변수가 없는지를 실패 원인에서 보고 싶다. 그래야 값이 아니라 이름만 보고 고친다.
6. 운영자로서, 원격 MCP 서버가 꺼져 있으면 실행이 `tool_connection`으로 끝나고 문구에 서버 이름과 주소가 보이기를 바란다. 그래야 어느 서버가 문제인지 안다.
7. 운영자로서, 토큰이 틀렸을 때와 서버가 꺼졌을 때가 실패 문구만으로 갈리기를 바란다. 그래야 진단 묶음(diag-bundle)만 보고 원인을 가른다.
8. 운영자로서, 실패 문구와 트레이스에 토큰 값이 남지 않기를 바란다. 그래야 트레이스를 공유해도 비밀이 새지 않는다. 주소는 비밀이 아니라고 보아(ADR 0049 결정 "주소") 쿼리 문자열까지 그대로 실리므로, 쿼리 문자열에 비밀을 적지 않는 것은 운영자의 몫이다(아래 "실패 문구", Out of Scope).
9. 운영자로서, 실행 기한에 걸린 실행이 서버 쪽 세션을 남기지 않기를 바란다. 그래야 서버가 유휴 만료까지 세션을 쥐지 않는다.
10. 운영자로서, 종료 요청에 답하지 않는 서버 때문에 실행의 끝이 2초보다 더 늦어지지 않기를 바란다. 그래야 꺼져 가는 서버가 실행을 붙들지 못한다.
11. 운영자로서, 기한에 걸린 실행의 결말이 지금처럼 원인 `timeout`의 `run_failed`이기를 바란다. 그래야 닫기 보호가 결말을 바꾸지 않는다.
12. 운영자로서, `serve`를 끌 때 도는 실행의 원격 세션도 닫히기를 바란다. 그래야 서버를 다시 띄우지 않아도 세션이 쌓이지 않는다.
13. 에이전트 저자로서, 원격 MCP 서버의 도구가 stdio 서버의 도구와 같은 모양으로 `ToolSpec.server`에 플러그인 이름을 달고 오기를 바란다. 그래야 approval-rules의 서버 규칙이 두 전송에 똑같이 걸린다.
14. 운영자로서, 관리 API의 매니페스트 응답에서 서버가 어느 전송인지와 주소를 보고 싶다. 그래야 배포가 어느 서버를 가리키는지 확인한다.
15. 관리 화면 개발자로서, 생성 TS 타입이 `transport`로 좁혀져 `url`과 `command`를 잘못 읽는 코드가 컴파일에서 걸리기를 바란다. 그래야 두 모양을 섞어 읽는 버그가 실행 전에 잡힌다.
16. 운영자로서, `[server]`에 다른 모양의 칸을 섞어 적으면(http에 `command`) 읽는 단계에서 어느 칸이 틀렸는지 듣고 싶다. 그래야 오타가 조용히 무시되지 않는다.
17. 운영자로서, 사용자 정보(`user:pass@`)가 든 주소나 http·https가 아닌 주소는 읽는 단계에서 거부되기를 바란다. 그래야 비밀이 주소에 실린 채 관리 API에 나오지 않는다.
18. 최종 사용자로서, 원격 MCP 서버의 실패를 지금과 같은 고정 문구로 보고 싶다. 그래야 서버의 주소나 내부 사정이 최종 사용자 면에 새지 않는다.
19. doc-qa-agent의 저자로서, 이 모양으로 문서 검색 서버 플러그인을 적고 싶다. 그래야 그 기능이 매니페스트 모양을 새로 정하지 않는다.
20. diag-bundle의 저자로서, 서버 하나를 여는 함수의 경계를 접속 확인에 다시 쓰고 싶다. 그래야 접속 확인과 실제 접속이 같은 길을 지난다.
21. 운영자로서, 루트 로거를 DEBUG로 켜도 도구 호출의 `secret_args` 값과 토큰 값이 로그에 남지 않기를 바란다. 그래야 문제를 살피려 로그를 켜는 순간 비밀이 새지 않는다.
22. 리뷰어로서, 계약 변경이 첫 티켓 하나에 모여 다른 티켓이 그 뒤에 서기를 바란다. 그래야 sdk·`openapi.json`·생성 TS 타입이 한 커밋에서 함께 바뀐다.

## Implementation Decisions

### 매니페스트 (넘겨받았다. 판별자의 갈래, `url`과 헤더 이름 검사의 수단, 거부 문구의 위치와 스토리는 명세가 정했다. 쟀다)

- sdk의 `[server]`는 모양마다 모델이 하나다. stdio 모양은 `transport`(닫힌 값 `"stdio"`, 기본값 `"stdio"`), `command`, `args`(기본 빈 튜플), `secret_args`(기본 빈 표)이고, http 모양은 `transport`(닫힌 값 `"http"`, 필수), `url`, `headers`(기본 빈 표), `secret_args`다. 두 모델 모두 매니페스트 공통 설정(모르는 칸 거부, 불변, 직렬화 스키마에서 기본값 있는 칸도 required)을 쓴다. `McpServer`는 그 둘을 `transport`로 가르는 합이고, 매니페스트의 `server` 칸은 그 합 또는 없음이다.
- 가르는 판별자는 호출 가능 판별자다(pydantic의 `Discriminator`에 함수를 준다). `transport`가 없으면 `"stdio"`로 읽는다. 쟀다(`manifest_shape.py`). 보통 판별자(`Field(discriminator="transport")`)는 칸이 없는 입력을 `union_tag_not_found`로 거부해 지금 매니페스트가 모두 깨진다. 호출 가능 판별자는 칸 없음을 stdio 모양으로 읽고, http 모양·섞인 칸·모르는 값은 보통 판별자와 같은 위치·같은 종류로 거부한다. 두 갈래의 OpenAPI 스키마 차이는 호출 가능 판별자 쪽에 `discriminator.mapping`이 빠지는 것뿐이고, openapi-typescript 7.13.0이 만든 TS 타입은 두 갈래 모두 `transport: "stdio"`·`transport: "http"` 리터럴을 들며 tsc 5.9.3 `--strict`가 `transport`로 좁힌 코드를 통과시키고 좁히지 않고 `url`을 읽은 코드를 TS2339로 거부한다(소비 지점까지 쟀다). 거부한 안: `transport`가 없는 매니페스트를 거부한다(옛 파일이 모두 깨지고 ADR의 "지금 있는 매니페스트는 고치지 않는다"에 어긋난다). 거부한 안: 모델 하나에 `command`·`url`을 모두 선택 칸으로 두고 검사기로 가른다(생성 TS 타입이 좁혀지지 않아 소비자가 두 칸을 다 선택 칸으로 다루고, `openapi.json`에 두 모양이 서지 않아 ADR의 결정과 어긋난다).
- 거부 문구의 위치. 운영자가 보는 글은 매니페스트를 읽을 수 없다는 지금의 문구 규칙(종류, 위치, pydantic의 문구. 값은 되울리지 않는다) 그대로다. 위치는 http에 `command`를 적으면 `server.http.command`, stdio에 `url`을 적으면 `server.stdio.url`(둘 다 모르는 칸), `transport`가 모르는 값이면 `server`(기대 태그 `'stdio', 'http'`를 든 pydantic 문구)다(쟀다). 모르는 값의 pydantic 문구에는 받은 `transport` 값이 실리는데, 그 칸은 닫힌 값이라 비밀이 아니므로 막지 않는다(명세가 정했다). stdio 모양에서 `command`가 없을 때의 위치는 `server.command`에서 `server.stdio.command`로 바뀐다(쟀다. `manifest_shape.py`의 stdio에 `command` 없음 사례. 종류는 `missing`이고 두 갈래가 같다. sdk 매니페스트 시험이 고정한다). 그 거부를 든 관리 화면 스토리의 글은 운영자 파일의 문구를 흉내 낸 임의의 글이지 런타임의 문구가 아니라 그대로 둔다(명세가 정했다). 거부한 안: 스토리의 글을 새 위치로 고친다(스토리는 문구의 자리를 보는 것이지 문구를 대 보는 것이 아니다).
- `url`은 문자열 그대로 보관한다. 검사는 읽는 단계에서 `urllib.parse.urlsplit`으로 scheme이 `http`·`https`인지, netloc에 `@`(사용자 정보)가 없는지, 호스트가 비지 않았는지를 보고 그 밖은 판정하지 않는다(명세가 정했다). 쿼리 문자열과 조각은 막지 않는다(ADR Consequences "문구"의 알려진 한계). 거부한 안: pydantic의 `AnyHttpUrl`로 받는다(빈 경로에 `/`를 붙이고 호스트를 소문자로 바꾸는 정규화가 있어 ADR의 "글자 그대로"와 어긋나고, 관리 API 응답이 파일과 달라진다).
- `[server.headers]`의 키(헤더 이름)는 RFC 9110의 토큰 문자(``!#$%&'*+-.^_`|~``와 글자·숫자)만 받고 값(환경 변수 이름)은 `^[A-Za-z0-9_]+$`만 받는다. 둘 다 읽는 단계의 거부다(헤더 이름의 검사는 명세가 정했다. 공백이나 콜론이 든 이름을 httpx2 2.13.0은 요청을 만들 때 거부하지 않고 그대로 싣는다(손으로 봤다. `httpx2.Request`에 `Bad Name`과 `A:B`를 주면 헤더에 그대로 든다). 서버가 그것을 어떻게 읽을지 알 수 없으므로 읽는 단계에서 잡는다). 같은 글자의 헤더 이름 둘은 TOML이 막는다. 대소문자만 다른 이름 둘(`Authorization`과 `authorization`)은 TOML이 막지 않고(손으로 봤다. `tomllib`이 둘 다 읽는다) HTTP 헤더 이름은 대소문자를 가르지 않아 한 헤더에 값 둘이 실리므로, 읽는 단계에서 거부한다(명세가 정했다). 표가 비어 있어도 된다.

(2026-11-09 명세 검토: 둘을 정한다(명세가 정했다). 첫째, 헤더 이름과 환경 변수 이름의 패턴은 검사기가 아니라 타입의 제약(pydantic의 `StringConstraints(pattern=…)`)으로 걸어 `openapi.json`에 같은 규칙이 실리게 한다(`.claude/rules/sdk.md`의 `skills` 항목과 같은 까닭). pydantic 2.13.5는 키와 값에 패턴을 건 `dict`를 직렬화 스키마의 `patternProperties`(키 패턴 → 값 패턴)로 낸다(모델 하나를 `uv run python -c`로 만들어 손으로 봤다). 대소문자만 다른 이름 둘의 거부는 스키마로 나타낼 수 없어 검사기에 남는다. sdk 매니페스트 시험이 직렬화 스키마의 `patternProperties`와 대소문자만 다른 이름 둘의 거부를 사례로 든다. 둘째, 라이브러리나 HTTP가 스스로 정하는 헤더 이름 아홉(`Host`, `Content-Length`, `Transfer-Encoding`, `Connection`, `Accept`, `Content-Type`, `Mcp-Session-Id`, `Mcp-Protocol-Version`, `Last-Event-Id`)은 대소문자를 가리지 않고 읽는 단계에서 거부한다. 클라이언트의 기본 헤더는 요청마다의 헤더보다 먼저 합쳐지므로(httpx2 2.13.0 `_client.py`의 `_merge_headers`를 읽었다) mcp가 요청마다 싣는 `accept`·`content-type`·`mcp-session-id`·`mcp-protocol-version`·`last-event-id`(mcp 2.3.0 `client/streamable_http.py`의 `_prepare_headers`와 재개 경로를 읽었다)는 매니페스트의 값을 조용히 덮는다. `Host`를 적으면 httpx2가 주소의 호스트를 싣지 않는다(같은 판 `_models.py`를 읽었다). `Content-Length`·`Transfer-Encoding`·`Connection`은 HTTP의 틀을 정하는 이름이다. 지금 받았다가 나중에 막으면 있던 매니페스트가 깨지므로 지금 막는다. 거부한 안: 받고 라이브러리에 맡긴다(값이 조용히 덮이거나 요청이 다른 호스트 이름으로 간다).)
- `schema_version`은 `"1"` 그대로다. ADR 0008의 2026-09-21 이력이 `requires_approval`과 `secret_args` 같은, 비어 있으면 지금과 같은 선택 칸을 더하며 판을 올리지 않았고 그때의 기준(기존 필드의 뜻이나 필수 여부가 바뀔 때 올린다)대로다. `transport` 없음이 stdio라 옛 매니페스트의 뜻은 바뀌지 않는다.

### 계약과 관리 화면 (넘겨받았다)

- `openapi.json`의 매니페스트 응답에서 `server`는 `anyOf`에 `oneOf[StdioServer, HttpServer]`와 `null`이 서는 모양이고, 두 모델 모두 `transport`가 required다(직렬화 스키마에서 기본값 있는 칸도 required인 공통 설정. 쟀다). 계약 파일은 `uv run python tools/export_openapi.py`로 뽑고(`.claude/rules/http.md`), 생성 클라이언트는 web의 `generate:api-client`로 만들며 최신성은 `check:api-client`와 pytest의 계약 테스트가 판정한다.
- 생성 TS 타입에서 `server`는 `transport` 리터럴로 좁히는 합이 된다. `server` 값을 생성 타입으로 적은 관리 화면의 테스트 픽스처와 스토리 넷은 `transport: "stdio"`를 더한다. 관리 화면의 컴포넌트는 `server`의 칸을 읽지 않아 화면은 바뀌지 않는다(ADR 0049 Consequences). e2e의 stdio 매니페스트는 `transport`가 없어도 stdio라 그대로다.
- 이 변경(sdk 모델, `openapi.json`, 생성 TS 타입, 픽스처 넷)이 첫 티켓이고 다른 티켓을 막는다(`docs/agents/issue-tracker.md`).

(2026-11-09 명세 검토: 첫 티켓이 혼자 병합될 수 있게 셋을 더한다. 첫째, `McpServer`가 두 모델의 합(호출할 수 없는 `Annotated` 별칭이다, `manifest_shape.py`)이 되면 어댑터가 `server.command`·`server.args`를 읽는 자리(`_connecting`의 문구와 `_parameters`)가 pyright를 지나지 못한다(`src/agent_os/adapters/mcp.py`를 읽었다). 그래서 첫 티켓이 어댑터를 `transport`로 가른다. 한 서버를 여는 문맥과 실패를 바꾸는 자리는 두 전송이 함께 쓰고(아래 "세션을 여는 자리와 두 전송의 공통"), 실패 문구의 괄호는 stdio면 명령, http면 매니페스트의 `url`이다. http 갈래는 여는 단계 안에서 `NotImplementedError("http 전송은 아직 구현되지 않았다")`를 던진다(명세가 정했다). 그래서 첫 티켓만 병합된 main에서 http 매니페스트로 돌린 실행은 `MCP 서버 <이름>(<url>)에 붙지 못했다: NotImplementedError: http 전송은 아직 구현되지 않았다`로 원인 `tool_connection`의 `run_failed`이고, 그 시험이 첫 티켓의 수락이다. 다음 묶음이 이 갈래를 실제 접속으로 바꾸며 그 시험도 바꾼다. 거부한 안: http 서버를 건너뛰고 나머지 서버로 돈다(그 서버의 도구가 조용히 빠지고, 선언 확인이나 규칙 줄이 그 도구를 가리킬 때만 드러난다). 둘째, `McpServer(`로 모델을 만드는 자리 열 곳(`tests/adapters/test_mcp.py` 여덟, `tests/core/test_run.py` 하나, `tests/channel/cli/test_interrupt.py` 하나. 본 세션이 `grep -rn "McpServer(" tests src`로 셌다. 그 가운데 `test_mcp.py`의 `_PARENT`와 `test_interrupt.py`의 `_MCP_CHILD`는 자식 스크립트 문자열 안이라 pyright가 보지 못하고 실행할 때만 깨진다, 검토가 읽었다)과 `sdk/manifest.py`의 `[server]` 없음 문구(`mcp 플러그인은 [server] 표가 필요하다 (command, args)`)를 첫 티켓이 고친다. 문구는 두 모양을 든다(`mcp 플러그인은 [server] 표가 필요하다 (command, args 또는 transport = "http", url)`). 셋째, 덮이지 않았던 스토리 둘의 시험을 첫 티켓에 둔다. 스토리 14는 `tests/test_server.py`의 선례대로 임시 플러그인 루트에 http 매니페스트를 두고 관리 API 응답의 `transport`·`url`·`headers`(헤더 이름과 변수 이름)를 본다. `url`은 대문자가 든 호스트와 빈 경로로 적어 응답이 글자 그대로인지 단언한다(`AnyHttpUrl`을 거부한 결정을 고정한다). 스토리 15는 `web/packages/api-client/src/clients.test-d.ts`의 선례대로 tsc가 판정하는 타입 시험이다. `transport`로 좁힌 뒤 `url`을 읽는 코드가 지나고, 좁히지 않고 `url`을 읽는 줄에는 `@ts-expect-error`를 단다.)

### 접속 (넘겨받았다. 환경 변수 없음이 여럿일 때의 문구와 값의 판정, 응답 훅의 역할은 명세가 정했다. 쟀다)

- 어댑터는 접속 직전에 `[server.headers]`의 환경 변수를 매니페스트에 적힌 순서로 읽는다. 하나라도 없으면 붙지 않고 `ConnectionError`로 끝내며 원인은 `헤더 <헤더 이름>의 환경 변수 <변수 이름>이 없다`다. 여럿이 없으면 그 문장을 매니페스트 순서로 `; `로 잇는다(명세가 정했다. 하나씩 고치며 여러 번 실패하지 않게). 값의 내용은 판정하지 않는다. 빈 문자열도 있는 것으로 보고 그대로 싣는다(명세가 정했다. 값을 보는 코드는 값을 되울릴 길을 연다). 막는 것은 하나다. 값에 ASCII 인쇄 가능 글자(0x20~0x7e)와 탭이 아닌 글자(개행 같은 제어 문자, 비ASCII 글자)가 들면 값을 라이브러리에 넘기지 않고 붙지 않으며, 원인은 `헤더 <헤더 이름>의 환경 변수 <변수 이름>의 값에 헤더 값으로 쓸 수 없는 글자가 있다`다. 이 문장에도 값은 싣지 않고, 여럿이면 없는 변수의 문장과 같이 매니페스트 순서로 `; `로 잇는다(명세가 정했다). 까닭은 손으로 본 것이다(프로브로 남기지 않았다). httpx2 2.13.0은 개행·NUL이 든 값을 `LocalProtocolError: Illegal header value b'<값 전체>'`로 거부하고 비ASCII 글자는 `UnicodeEncodeError`가 그 글자 하나와 자리를 싣는다. 그 예외가 그대로 원인이 되면 토큰이 `run_failed`로 트레이스에 남아 원칙 V를 어기고, 파일에서 읽은 비밀 값의 끝에는 개행이 흔히 붙는다. 이 거부는 구현 티켓의 시험이 사례로 잡는다("시험 픽스처의 모양과 더한 사례"). 헤더 값은 환경 변수의 값 전체다.
- 클라이언트는 `httpx2.AsyncClient`이고 기본 헤더가 그 값들, 기한은 mcp가 자기 클라이언트에 쓰는 값(접속·쓰기·풀 30초, 읽기 300초. ADR 0049), `trust_env`는 기본값이다. 응답 훅(`event_hooks`의 `response`) 하나를 단다. 훅은 응답의 `Mcp-Session-Id` 헤더를 받아 두고(mcp 2.3.0은 세션 식별자를 내주지 않는다. ADR 0049), 2xx가 아닌 응답의 메서드·상태 코드·이유 구절을 마지막 것 하나로 받아 둔다(명세가 정했다. 프로브의 훅은 모든 응답을 쌓아 두고 어댑터는 마지막 하나만 둔다. 문구에 싣는 것이 마지막 하나라 결과는 같다). 응답 본문은 읽지 않는다. 쟀다(`http_close.py`): 응답 훅은 세션 식별자를 받고, 401 응답을 `POST 401 Unauthorized`로 받는다. httpx2 2.13.0에 응답 훅이 있는지 ADR이 어림으로 남긴 것은 이것으로 섰다.
- 그 클라이언트를 mcp의 `streamable_http_client`에 넘기되 라이브러리의 종료 요청은 끈다(`terminate_on_close=False`. 까닭은 "닫기"). 세션을 열어 `initialize`하고 도구 목록을 읽는다(쪽 나눔의 상한은 stdio와 같다). 그 뒤의 호출은 stdio와 같은 연결이고 도구마다 `ToolSpec.server`에 플러그인 이름이 실린다.
- 실행 전 거부, 재시도, 접속 기한의 칸은 없다(ADR 0049).

(2026-11-09 명세 검토: 라이브러리의 종료 요청을 끄는 것(`terminate_on_close=False`), 어댑터가 보내는 종료 요청(아래 "닫기"), 응답 훅이 세션 식별자를 받아 두는 것은 한 묶음(아래 "고칠 자리의 묶음" 주석의 B2)에 함께 든다. 앞의 것만 먼저 들어오면 정상 닫기에서도 종료 요청이 나가지 않기 때문이다. 그래서 접속 묶음(B1)은 라이브러리의 기본값(`terminate_on_close=True`)으로 붙고, 정상 닫기의 종료 요청은 라이브러리가 보낸다(`http_close.py`의 `normal`이 그 길이고 종료 요청이 닿았다). B2가 들어올 때까지 취소된 실행은 종료 요청을 보내지 않는다(`deadline_plain`). 묶음을 이렇게 나누는 것은 "고칠 자리의 묶음"을 고친 것이다.)

### 실패 문구 (넘겨받았다. 주소의 모양과 오류 응답의 상태는 명세가 정했다. 쟀다)

- 문구는 `MCP 서버 <이름>(<주소>)에 붙지 못했다: <원인>`이다. stdio 모양은 지금처럼 괄호에 명령이 선다.
- `<주소>`는 매니페스트의 `url` 그대로다(쿼리 문자열과 조각 포함. ADR 0049 결정 "주소". 명세가 정했다). 이 명세의 초안은 원칙 V를 들어 쿼리 문자열과 조각을 뗀 것을 제안했으나 사용자가 2026-11-09의 승인에서 주소 전체를 골랐다(일지 2026-11-09-1611의 "승인"). 주소는 비밀이 아니라는 ADR의 결정이 그대로 서고, 이 문구는 `run_failed`로 트레이스에 남고 운영자 면에 보이므로 운영자가 쿼리 문자열에 비밀을 적으면 트레이스에 남는다(알려진 한계. ADR 0049 Consequences "문구에 실리는 것과 실리지 않는 것". 배포 안내가 적는다, 아래 Out of Scope). 관리 API의 매니페스트 응답도 파일 그대로다. 쟀다: 라이브러리의 예외 글에는 쿼리 문자열이 실리지 않지만(`closed_port`, `unauthorized`) 라이브러리 로거의 줄에는 실린다(아래 "로그"). 거부한 안: 쿼리 문자열과 조각을 뗀 것(scheme, 호스트와 포트, 경로). 트레이스에 비밀이 남지 않게 하려는 이 명세의 초안이었고 사용자가 승인에서 거부했다. 거부한 안: 원점만(경로가 다른 서버 둘을 가르지 못한다).
- `<원인>`은 지금의 규칙(예외 종류와 글, 예외 그룹은 펼친다)대로다. 꺼진 서버는 `ConnectError: All connection attempts failed`다(쟀다. 예외 그룹 안의 잎 하나). 서버가 2xx가 아닌 응답을 돌려줬으면 응답 훅이 받아 둔 마지막 오류 응답을 원인 끝에 ` (HTTP <상태 코드> <이유 구절>)`로 덧붙인다(명세가 정했다). 토큰이 없거나 틀려 서버가 401을 돌려주면 `MCPError: Server returned an error response (HTTP 401 Unauthorized)`다(쟀다. 프로브의 사례는 헤더 없이 연 것이고 틀린 값은 따로 돌리지 않았다. 픽스처는 기대한 값과 다른 `Authorization`의 요청을 모두 같은 401로 막는다, `http_fixture_server.py`를 읽었다). 까닭은 mcp 2.3.0이 본문이 JSON-RPC 오류가 아닌 오류 응답(401처럼 글만 든 것)을 404 밖에서는 상태 코드 없이 그 글 하나로 바꿔(쟀다. 본문이 JSON-RPC 오류인 오류 응답은 그 오류를 그대로 올리고, 404는 세션 유무에 따라 `Not Found`나 `Session terminated`다. mcp 2.3.0 `client/streamable_http.py`의 코드를 읽었다) 꺼진 서버와 틀린 토큰이 갈리지 않기 때문이고, diag-bundle의 수락(토큰 불일치를 가른다)이 이것에 기댄다. 응답 본문은 싣지 않는다(서버가 정한 글이라 무엇이든 들 수 있다). 거부한 안: 본문의 앞 몇 글자를 싣는다(원칙 V). 거부한 안: 상태 코드를 `run_failed`의 새 칸으로 둔다(이벤트 모양이 바뀌어 계약 변경이 커진다. 문구로 충분하다).
- 헤더 값은 문구에도 원인(`__cause__`)에도 트레이스에도 없다(ADR 0049). 쟀다: 토큰 값은 예외 글에 실리지 않는다(헤더 값으로 쓸 수 없는 글자가 든 값은 이 쟀다 밖이다. 위 "접속"의 거부가 값을 라이브러리에 넘기지 않아 막는다).

(2026-11-09 명세 검토: 응답 훅이 받아 두는 상태를 좁힌다. 위 "접속"의 규칙(2xx가 아닌 응답의 마지막 하나)은 라이브러리가 넘기고 지나간 응답을 붙인다. httpx2 2.13.0의 응답 훅은 리디렉션 응답을 포함해 보낸 요청마다의 응답에서 돈다(`_client.py`의 `_send_handling_redirects`를 읽었다). mcp 2.3.0은 `initialize` 뒤 GET으로 서버의 알림 흐름을 여는데, 서버가 오류 응답(405 등)을 돌려주면 그 예외를 삼키고 다시 시도할 뿐 세션을 실패로 보지 않는다(`client/streamable_http.py`의 `handle_get_stream`을 읽었다). 같은 출처의 307은 라이브러리가 스스로 따른다(아래 "닫기"의 주석). 그 뒤 여는 단계의 다른 요청이 오류 상태 코드를 받지 않고 실패하면(도구 목록 요청이 307을 지나 2xx의 JSON-RPC 오류로 거절되는 것 등) 옛 규칙은 그 405나 307을 원인 끝에 붙여 운영자를 잘못 이끈다. 상태를 덧붙이는 것은 여는 동안의 실패뿐이라 도구 호출의 실패에는 어느 규칙에서도 붙지 않는다. 그래서 훅은 POST 응답마다 받아 둔 상태를 바꾸고, 2xx면 지우며, GET과 DELETE의 응답은 받아 두지 않는다. 문구에 붙는 것은 마지막 POST가 2xx가 아니었을 때의 그 상태 하나다. 이것은 "응답 훅의 역할"을 고친 것이다.)

(2026-11-09 명세 검토와 사용자의 결정: 위 "쟀다"는 라이브러리가 지은 예외 글만 본 것이다. 서버가 400 이상의 오류 응답을 `content-type: application/json`으로 보내며 본문에 JSON-RPC 오류를 담으면 mcp 2.3.0은 그 오류의 글을 그대로 예외로 올린다(`client/streamable_http.py` 398~416줄을 읽었다). 그래서 서버가 받은 `Authorization` 값을 그 글에 되울리면 값이 실패 문구와 트레이스에 실린다. 검토는 httpx2의 `MockTransport`로 401과 JSON-RPC 오류 본문을 돌려주는 서버를 지은 임시 스크립트에서 원인이 `MCPError: bad credentials: Bearer echo-secret-9f3a token=echo-secret-9f3a`로 나오는 것을 봤다(Windows에서 한 번. 커밋한 프로브가 아니다, 일지 2026-11-09-2138). 사용자는 보낸 값을 찾아 가리기를 골랐다(같은 일지의 "결정"). 세부는 명세가 정했다. 가릴 글은 헤더마다 환경에서 읽은 값 전체와, 값이 공백 하나로 나뉜 `<낱말> <나머지>` 꼴이면 그 나머지(`Bearer <토큰>`의 토큰)다. 8자보다 짧은 글은 가리지 않는다(상관없는 글자까지 바꾸지 않게 한다). 가리는 자리는 어댑터가 짓는 두 문구, 곧 여는 동안의 `ConnectionError` 문구와 도구 호출이 실패할 때의 `RuntimeError` 문구다. 긴 글부터 글자 그대로 찾아 `[가림: 헤더 <헤더 이름>]`으로 바꾼다. 가린 것이 하나라도 있으면 그 예외를 원인을 잇지 않고 던져(`from None`) 원인 체인의 글에 값이 남지 않게 한다. `from None`도 `__context__`는 남기지만, core의 문구(`_describe`)는 예외의 종류와 글만 쓰고 `__context__`는 취소를 찾는 판정(`_cancellation_under`)만 따라간다(`src/agent_os/core/run.py`를 읽었다). 가린 것이 없으면 지금처럼 원인을 잇는다. 그래서 `.claude/rules/adapters.md`의 예외 항목("원래 예외가 `__cause__`다")을 접속 묶음이 함께 고친다. 알려진 한계는 셋이다. 서버가 값을 바꿔(인코딩, 일부, 대소문자) 되울리면 놓친다. 8자보다 짧은 값은 가리지 않는다. 도구가 오류로 돌려준 결과(`isError`)의 본문은 예외가 아니라 도구 결과로 모델과 트레이스에 가므로 가리지 않는다. 거부한 안: 서버가 쓴 오류 글을 싣지 않는다(라이브러리가 지은 안내, 곧 따르지 않은 리디렉션과 끝난 세션의 글도 같은 `MCPError`로 와서 함께 사라지고 운영자가 원인을 가르기 어려워진다). 거부한 안: 지금대로 두고 한계로 적는다(원칙 V와 글자 그대로 어긋난다). 이 결정은 ADR 0049의 2026-11-09 이력 "서버가 되울린 헤더 값을 실패 문구에서 가린다"에 쌓고, 헤더 값이 어디에도 실리지 않는다는 문장 셋(요약, 결정 "실패", Consequences "문구에 실리는 것과 실리지 않는 것")에 포인터를 단다.)

### 닫기 (넘겨받았다. 보호의 자리와 종료 요청의 모양은 명세가 정했다. 쟀다)

- 결정. 라이브러리의 종료 요청을 끄고(`terminate_on_close=False`) 라이브러리 문맥(세션, 전송)을 보호 없이 닫은 뒤, 같은 `finally`에서 `CancelScope(shield=True)` 안에 어댑터가 자기 클라이언트로 세션 종료 요청(DELETE)을 2초 유예(`move_on_after`) 안에서 보내고, 유예가 지났어도 같은 보호 안에서 클라이언트를 닫는다(유예는 종료 요청에만 걸린다. 한 유예에 둘을 함께 두면 종료 요청이 걸렸을 때 닫기가 건너뛰어진다). 정상 종료도 같은 길이다. 보호 범위는 취소되지 않은 범위에서는 아무것도 바꾸지 않는다.
- 까닭(쟀다. `http_close.py`, Windows와 Linux 각 3회차, 두 OS 같음). ADR 0049의 첫째 안(라이브러리 문맥을 닫는 호출을 보호로 감싼다)은 `RuntimeError: Attempted to exit a cancel scope that isn't the current tasks's current cancel scope`로 끝난다(`deadline_shield_exit`). 라이브러리가 안에서 연 취소 범위(태스크 그룹)를, 그 뒤에 연 보호 범위가 현재 범위인 채로 닫게 되어 anyio가 중첩 위반으로 거부하는 것이다(해석. anyio 4.15.1의 문구). 그 예외가 새면 결말은 기한이 아니라 예외가 된다. 라이브러리의 종료 요청을 끄고 같은 자리에서 보호해도 같은 예외다(`deadline_shield_delete`. 갈래: 원인은 종료 요청이 아니라 보호의 자리다). 보호 없이 문맥을 닫은 뒤 다음 문장에 보호를 두면 그 문장은 돌지 않는다(`deadline_shield_after`. 취소된 범위에서는 닫기의 `await`가 끝나며 취소가 다시 올라간다). 문맥 닫기를 `try`에, 보호를 `finally`에 두면 종료 요청이 같은 세션 식별자로 서버에 닿고(응답 200), 기한의 표지(`cancelled_caught`)가 참이며, 예외가 새지 않는다(`deadline_shield_finally`). 종료 요청에 답하지 않는 서버에서는 2초에 끊고 결말이 그대로이며 클라이언트 닫기는 유예가 지난 뒤에도 0.0초 안에 끝난다(`deadline_shield_finally_hang`. 닫기 2.0초, `client_closed` 참). ADR 0034가 stdio에서 본 양상(안쪽 task group이 취소를 삼켜 `cancelled_caught`가 거짓이 된다)은 `cancelled_caught`를 기록한 네 갈래 어디에서도 나지 않았다(예외로 끝난 세 갈래는 기록이 없다). 양성 대조는 `normal`(같은 픽스처에 종료 요청이 닿는다)과 `deadline_plain`(보호 없이는 닿지 않는다)이다.
- 종료 요청의 모양(명세가 정했다). 매니페스트의 `url` 그대로(쿼리 문자열 포함. 서버가 쿼리로 라우팅할 수 있다)에 DELETE를 보내고, 헤더는 클라이언트의 기본 헤더에 `accept: application/json, text/event-stream`, `content-type: application/json`, `mcp-session-id`(응답 훅이 받아 둔 것), `mcp-protocol-version`(`initialize` 결과의 값)을 더한 것이다. 라이브러리가 보내는 모양과 같다(코드를 읽었다). 세션 식별자를 받지 못했으면(`initialize` 전에 실패했거나 서버가 세션 식별자를 주지 않는다) 보내지 않는다. 응답은 보지 않고, 요청의 예외(연결이 끊기는 전송 오류 포함)와 2초 초과는 삼키며 기록하지 않는다(어댑터는 로그를 쓰지 않는다. 아래 "로그"). 그 뒤 같은 보호 안에서 유예와 상관없이 클라이언트를 닫는다. 쟀다(`http_close.py`)는 `httpx2.HTTPError`를 삼키는 코드까지이고 서버가 DELETE의 연결을 끊는 사례는 따로 돌리지 않았다. 구현 티켓의 시험이 잡는다. 리디렉션을 따를지(`follow_redirects`)는 이 명세가 정하지 않았다. 아래 Further Notes에 적었다.
- 2초는 stdio 상류가 서버가 스스로 끝나기를 기다리는 유예와 같은 값이고(ADR 0034·0049) 어댑터 안의 한 상수다.
- 걸리는 시간(쟀다. `http_close.py`, 세 회차의 범위). 라이브러리가 종료 요청을 보내는 정상 닫기(`normal`)는 Windows 0.0~0.016초(0.0은 시계 해상도 아래로 본다. 어림), Linux 0.002~0.003초. 어댑터가 보내는 길이 취소된 실행에서 종료 요청의 왕복과 클라이언트 닫기까지 마치는 데는 Windows 0.0~0.016초, Linux 0.002~0.003초이고, 기한부터 돌아오기까지는 Windows 0.02~0.031초, Linux 0.005초. 종료 요청에 답하지 않는 서버는 두 OS 모두 2.0초 안팎. 정상 종료가 어댑터의 길(위 결정의 모양)을 지날 때는 같은 실행의 `normal`과 견줘 Windows 0.0~0.015초(`normal` 0.015초), Linux 0.003~0.005초(`normal` 0.003~0.004초)로 같은 범위다(쟀다. `http_close.py`의 `normal_own_delete`. 셀프 리뷰 뒤 더해 같은 날 `normal`과 함께 두 OS에서 따로 돌렸다). ADR 0049 Consequences가 어림으로 적고 프로브에 넘긴 "정상 종료는 늦지 않는다"는 이것으로 섰다.
- 이 결정은 ADR 0049 결정 "닫기"의 "종료 요청은 라이브러리 문맥의 `finally`(789~791줄)에서 나가고 어댑터는 그 문맥을 닫는 호출을 감쌀 수 있을 뿐이다"를 거짓으로 만든다. 종료 요청은 라이브러리가 아니라 어댑터가 보내고, 보호는 그 문맥을 닫는 호출을 감싸지 않는다. 그 바로 앞 문장 "보호의 자리는 라이브러리 바깥이다"는 이 모양에서도 참이다(보호는 어댑터의 `finally`에 있다). 같은 커밋에서 ADR 0049의 이력에 쌓고 거짓이 된 문장에 포인터를 단다. 거부한 안: 보호 없이 서버의 유휴 만료에 맡긴다(ADR이 거부했다). 거부한 안: 종료 요청을 별도 태스크로 띄워 실행이 끝난 뒤 보낸다(실행 밖에 태스크가 남아 구조적 동시성이 깨지고 `serve` 종료가 그것을 기다리지 않는다). 거부한 안: 라이브러리 전송의 비공개 속성에서 세션 식별자를 읽는다(판이 바뀌면 조용히 깨진다. 응답 훅은 공개 경계다).

(2026-11-09 명세 검토와 사용자의 결정: 아래 Further Notes의 리디렉션 문단은 전제 둘이 틀렸다. mcp 2.3.0의 `create_mcp_http_client`는 리디렉션을 따르지 않는다(독스트링 "Redirect following is left at the httpx2 default (off)"). 라이브러리는 자기 요청을 요청마다 `follow_redirects=False`로 보낸 뒤 같은 출처이고 메서드를 지키는 리디렉션만 스스로 따르며, 클라이언트의 `follow_redirects`는 보지 않는다(`mcp/shared/_httpx_utils.py`의 `request_within_origin`과 `client/streamable_http.py`의 `streamable_http_client` 독스트링을 읽었다). 그래서 `/mcp`를 `/mcp/`로 307로 돌려보내는 서버에도 초기화와 도구 호출은 선다. 리디렉션을 따르지 않는 것은 어댑터가 직접 보내는 종료 요청 하나이고, 검토는 그 요청이 307 응답에서 멈춰 서버에 닿지 않는 것을 임시 스크립트로 봤다(Windows에서 한 번, 일지 2026-11-09-2138). 사용자는 같은 서버 안에서만 따라가기를 골랐다(같은 일지의 "결정"). 어댑터는 종료 요청을 `follow_redirects=False`로 보내고, 응답이 리디렉션이면 httpx2가 지어 둔 다음 요청(`Response.next_request`)이 세 조건을 모두 갖출 때만 그것을 보낸다. 세 조건은 같은 출처(scheme·호스트·포트가 같거나, 기본 포트를 쓰는 같은 호스트의 http에서 https로), 메서드가 DELETE 그대로(httpx2는 302·303에서 메서드를 GET으로 바꾼다), 위치에 사용자 정보가 없음이고, 라이브러리가 자기 요청에 쓰는 조건과 같다. 판정은 httpx2의 공개 API(`Response.next_request`, `URL`의 칸)로 짓고 라이브러리의 비공개 모듈(`mcp.shared._httpx_utils`)은 import하지 않는다(명세가 정했다. 판이 바뀌면 조용히 깨진다). httpx2의 횟수 상한은 한 번의 `send` 안에서만 세므로(`_client.py`의 `_send_handling_redirects`를 읽었다) 어댑터가 따른 횟수를 세어 클라이언트의 `max_redirects`를 넘지 않게 한다. 2초 유예는 따르는 요청까지 모두 덮는다. 조건을 갖추지 못한 리디렉션은 따르지 않고 그 응답으로 끝낸다(응답은 보지 않는다). 그래서 다른 출처로는 `Authorization` 밖의 인증 헤더도 세션 식별자도 실려 가지 않는다(httpx2의 `_redirect_headers`는 출처가 다를 때 `Authorization`만 뗀다, 읽었다). 삼키는 예외는 위 "종료 요청의 모양"대로 `httpx2.HTTPError`와 2초 초과다. 서버가 DELETE의 연결을 끊을 때 나는 `RemoteProtocolError`가 `HTTPError` 아래라 삼켜지는 것은 검토가 임시 스크립트로 봤다(같은 일지). 거부한 안: 라이브러리가 따라간 끝 주소를 응답에서 받아 두었다가 그 주소로 보낸다(종료 요청을 매니페스트의 `url` 그대로 보낸다는 위 문장이 바뀐다). 거부한 안: 따라가지 않는다(`/mcp/`로 돌려보내는 서버에서는 정상 종료에도 종료 요청이 닿지 않고 흔적도 남지 않아, 서버가 세션을 유휴 만료까지 쥔다). 거부한 안: 어디로든 따라간다(다른 출처로 `Authorization` 밖의 인증 헤더와 세션 식별자가 실려 간다).)

### 로그 (넘겨받았다. 쟀다)

- 어댑터는 로그를 쓰지 않는다. 저장소는 로깅을 설정하지 않고(ADR 0049) 종료 요청의 실패도 기록하지 않는다.
- 라이브러리 로거에 실리는 것(쟀다. 캡처는 `mcp`·`httpx2`·`httpcore2` 로거의 DEBUG). `mcp.client.streamable_http`가 DEBUG로 `Connecting to StreamableHTTP endpoint: <주소 전체>`를, `httpx2`가 INFO로 `HTTP Request: POST <주소 전체> "HTTP/1.1 401 Unauthorized"`를 찍고 둘 다 쿼리 문자열을 포함한다. 기본 WARNING에서는 나오지 않는다. 토큰 값(요청 헤더)은 세 로거의 DEBUG 줄 어디에도 실리지 않는다(쟀다. 두 OS 33회차 모두 로그에 없었고, 그 가운데 양성 대조(그 값이 서버의 요청 헤더에 닿은 기록)가 있는 것은 토큰을 실어 연결을 연 아홉 사례 27회차다. 헤더 없이 연 `unauthorized`와 실었으나 서버에 닿지 않은 `closed_port`의 6회차는 양성 대조가 없다).
- 구현 티켓의 수락(ADR 0049): `secret_args`가 있는 도구를 http 모양의 서버에 부르며 루트 로거를 DEBUG로 켠 테스트에서 그 값이 로그에 나타나지 않는다. 막는 자리는 구현 티켓이 정한다. 이 명세는 같은 테스트에 헤더 값(토큰)도 나타나지 않는다는 단언을 더한다(명세가 정했다. "시험 픽스처의 모양과 더한 사례").
- 쿼리 문자열의 로그 경로는 런타임이 켜는 수준에서 시험한다. 쿼리가 든 주소로 닫힌 포트에 붙어 실패하는 사례에서 루트 로거를 기본 수준(WARNING)으로 잡은 로그에 쿼리 문자열이 없다는 단언을 둔다(명세가 정했다. "시험 픽스처의 모양과 더한 사례". 쿼리 문자열이 실리는 자리를 트레이스의 실패 문구와 라이브러리 로거의 DEBUG·INFO 둘로 고정하는 단언이다. 어댑터와 core에는 로거가 없어 지금은 아무것도 걸리지 않는 단언이고, 뒤에 주소를 찍는 로거가 기본 수준으로 들어오면 빨개진다. 지금의 구현으로는 빨개질 수 없어 티켓의 수락으로 세지 않는 선택 사항이다. 주소를 찍는 로거를 들이는 티켓이 이 단언을 그 티켓의 수락으로 올린다. PR #501의 claude-review가 짚었다). 라이브러리 로거가 DEBUG·INFO로 주소 전체를 찍는 것은 라이브러리의 동작이라 시험으로 고정하지 않고 프로브가 재어 배포 안내에 넘긴다(아래 Out of Scope. deploy-package의 기능 계획에 적었다).

(2026-11-09 명세 검토: 위 "기본 WARNING에서는 나오지 않는다"에는 라이브러리가 WARNING으로 찍는 줄이 빠졌다. mcp 2.3.0은 따르지 않은 리디렉션(다른 출처, 메서드가 바뀌는 것)을 만나면 `Redirect to <위치> not followed; …`를 WARNING으로 찍는다(`client/streamable_http.py`의 `_unfollowed_redirect`와 그것을 찍는 390~391줄을 읽었다. GET 흐름에서는 `GET stream not opened: …`이다). 저장소는 로깅을 설정하지 않으므로 그 줄은 파이썬 `logging`의 마지막 수단 처리기(`lastResort`)로 stderr에 나올 것이다(어림. 돌려 보지 않았다). 실리는 것은 서버가 정한 위치에서 사용자 정보·쿼리 문자열·조각을 뗀 주소(scheme·호스트·포트·경로)이고 헤더 값은 실리지 않는다(같은 파일의 `_unfollowed_redirect`, 72~84줄과 그것이 부르는 `shared/_httpx_utils.py`의 `redirect_location`, 172~177줄을 읽었다). 서버가 그 위치의 경로에 옮겨 적은 글은 실린다. 라이브러리의 동작이라 시험으로 고정하지 않는다. 위 쿼리 문자열의 WARNING 단언은 접속 묶음(B1)의 닫힌 포트 사례에 두는 회귀 단언이고, 리디렉션이 없는 사례라 이 줄과 부딪히지 않는다.)

### 세션을 여는 자리와 두 전송의 공통 (명세가 정했다)

- 한 서버를 여는 함수와 여는 동안의 실패를 `ConnectionError`로 바꾸는 자리(ADR 0049가 `_opened`·`_connecting`으로 부른 것)는 두 전송이 공유하고, 그 아래 세션을 여는 자리만 `transport`로 갈라진다. stdio 갈래는 지금 그대로이고 http 갈래는 "접속"의 클라이언트와 "닫기"의 `finally`를 든다. diag-bundle이 접속 확인에 다시 쓰는 경계는 서버 하나를 여는 함수다(ADR 0049 Consequences "뒤 기능이 기대는 것").
- 환경을 읽는 코드는 어댑터의 http 갈래에만 있다(`.claude/rules/adapters.md`). core와 sdk는 환경을 모른다.
- stdio의 런처와 프로세스 그룹 정리(ADR 0034)는 http 갈래에 걸리지 않는다.

### 실제 모델 시험 하나 (넘겨받았다. 모양은 명세가 정했다)

calc 예시가 http 모양의 플러그인으로 도구를 써 트레이스가 남는 시험은 `-m llm`이다. 저장소의 플러그인을 임시 루트에 복사하고 거기에 http 모양의 mcp 플러그인 하나를 적어 넣은 뒤(시험이 띄운 HTTP 픽스처의 주소), calc의 매니페스트가 그 플러그인을 고르게 바꿔 CLI로 돌린다. 수락은 답에 계산 결과가 있고 트레이스에 그 서버의 도구 호출(`tool_called`)이 남는 것이다. 선례는 실제 모델로 calc를 돌리는 지금의 시험(`tests/test_main.py`)이다. `plugins/mcp/`에 http 모양의 예시는 두지 않는다(ADR 0049).

(2026-11-09 to-tickets: 저장소의 규칙 파일 `plugins/rules.toml`은 `[agents.calc] allow = ["everything:*"]`이고, `tests/test_main.py`의 `_copy_repo_plugins`가 그 파일을 임시 루트로 옮긴다(둘 다 읽었다). calc의 `mcp`를 http 플러그인으로 바꾸고 규칙 파일을 그대로 두면 에이전트 표의 줄이 연결에 없는 서버를 가리켜 실행이 연결 직후 원인 `tool_connection`의 `run_failed`로 끝난다(`.claude/rules/core.md` 실패 정책). 그래서 시험은 임시 루트의 규칙 파일도 그 플러그인의 이름으로 바꾼다.)

## Testing Decisions

### 좋은 시험

바깥 행동만 본다. 매니페스트는 읽힌 모델의 종류와 거부의 위치·종류를, 어댑터는 서버가 받은 요청(기록 파일)과 돌려준 예외의 문구를, core는 이벤트의 열과 `run_failed`의 원인을 본다. 응답 훅이나 보호 범위 같은 안쪽은 시험하지 않는다. 시간 단언은 홀로 돌린 시간의 넉넉한 배수로 두고 Linux CI를 생각한다(`.claude/rules/tests.md`). anyio 어댑터 시험은 본문에서 `async with`로 연다. 환경이 없어 skip되는 시험은 두지 않는다(원칙 II).

### 시험 픽스처의 모양과 더한 사례 (명세가 정했다)

- HTTP 픽스처는 지금의 stdio 픽스처와 같은 `MCPServer`에 add 도구와 잠드는 도구를 두고, 요청마다 메서드·경로·쿼리 문자열·`Authorization`·`Mcp-Session-Id`를 기록 파일에 JSON 한 줄로 남기는 ASGI 미들웨어를 앞에 끼워 uvicorn으로 루프백의 빈 포트에 띄운 별도 프로세스다. 선택 인자로 기대한 `Authorization` 값과 다른 요청을 401로 막고, DELETE를 지정한 초만큼 잠재운다. 프로브의 픽스처 서버(`http_fixture_server.py`)가 그 모양이고 시험 픽스처는 그것을 옮긴다. 시험은 포트가 열릴 때까지 TCP 접속으로 기다리고 프로세스는 쥔 핸들로만 끈다.
- 어댑터 시험의 사례. 도구 목록·호출·`ToolSpec.server`(두 서버 가운데 하나가 http여도 서버 이름이 실린다). 헤더 변수가 있을 때 그 값이 서버의 요청 헤더에 닿는다(기록 파일). 헤더 변수가 없으면 붙지 않고 문구가 헤더 이름과 변수 이름을 들며 값은 어디에도 없다. 둘이 없으면 둘 다 든다. 끝에 개행이 붙은 값의 변수로는 붙지 않고 문구가 헤더 이름과 변수 이름을 들며 값은 문구와 원인 체인 어디에도 없다. 닫힌 포트에 쿼리 문자열이 든 주소로 붙으면 문구에 서버 이름과 매니페스트의 `url` 그대로의 주소(쿼리 문자열 포함)가 있고 토큰 값은 문구와 원인 체인에 없다. 같은 사례에서 루트 로거를 기본 수준(WARNING)으로 잡은 로그에 쿼리 문자열이 없다(지시문이 둔 로그 경로의 시험. 위 "로그"). 401을 돌려주는 서버에 붙으면 원인에 `HTTP 401 Unauthorized`가 있다. 정상 닫기에 종료 요청이 같은 세션 식별자로 닿는다. 도구 호출 도중에 기한이 오면 종료 요청이 닿고 기한의 표지가 참이며 예외가 새지 않는다. 종료 요청에 답하지 않는 서버에서는 닫기가 2초 안팎에 돌아온다. `initialize` 전에 실패하면 종료 요청을 보내지 않는다. 선례는 `tests/adapters/test_mcp.py`의 서버 기동 실패·둘째 서버 실패·기한에 서버 내려감 시험이다.
- core를 지나는 시험. 도구 호출 도중에 실행 기한이 오면 `run_failed`의 원인이 `timeout`이고 종료 요청이 서버에 닿았다(PR #499가 넘긴 회귀 시험. 실행 타임아웃 시험의 선례를 따른다). 서버를 끈 채 돌린 실행은 원인 `tool_connection`으로 끝난다(기능 계획의 수락). `secret_args`가 있는 도구를 부르며 루트 로거를 DEBUG로 켜면 그 값과 헤더 값이 로그에 없다(구현 티켓의 수락).
- sdk 매니페스트 시험의 사례. `transport` 없음은 stdio로 읽힌다. http 모양이 읽힌다. http에 `command`, stdio에 `url`은 그 위치의 모르는 칸으로 거부된다. 모르는 `transport`는 거부된다. `ftp://`와 scheme 없는 주소, 사용자 정보가 든 주소는 거부된다. 토큰 문자가 아닌 헤더 이름과 패턴 밖의 변수 이름은 거부된다. 직렬화 스키마에서 `server`는 두 모양의 oneOf이고 두 모양 모두 `transport`가 required다. 선례는 `tests/sdk/test_manifest.py`의 서버 표·직렬화 스키마 시험이다.
- 계약과 관리 화면. `openapi.json` 최신성 시험과 생성 클라이언트의 `check:api-client`가 그대로 판정한다. 픽스처 넷은 `pnpm -C web verify`의 tsc가 본다.

## Out of Scope

- ADR 0049가 범위 밖으로 둔 여섯. 접속을 미리 확인하는 길(diag-bundle. 서버 하나를 여는 함수의 경계를 다시 쓴다. 그 기능 계획의 `**Blocked by:**`에 mcp-http를 더했다), 운영자의 서버 파일과 신뢰 수준·도구 정의 해시(mcp-trust), SSE 전송, OAuth, 재시도, 접속 기한의 칸.
- 평문 http로 인증 헤더를 보내는 것을 운영자가 명시적으로 허락하는 표지(mcp-trust. 그 기능 계획에 안을 적었고 그 설계에서 묻는다. `**Blocked by:**`에 mcp-http가 있다).
- `[server.headers]`의 환경 변수 이름을 허락 목록으로 좁히기(mcp-trust. 그 기능 계획에 있다).
- 문서 검색 서버를 가리키는 실제 플러그인(doc-qa-agent. `**Blocked by:**`에 mcp-http가 있다).
- 주소의 쿼리 문자열에 든 비밀을 매니페스트 단계에서 막기. 알려진 한계로 둔다(ADR 0049). 라이브러리 로거가 DEBUG·INFO로 주소 전체를 찍는 것은 배포 안내의 몫이다(deploy-package. `.scratch/deploy-package/plan.md` 본문에 ADR 0049가 넘긴 배포 안내 둘과 같은 자리로 적었고 `**Blocked by:**`에 mcp-http를 더했다).
- 실행 사이의 연결 재사용이나 연결 풀. 실행마다 접속하고 닫는다(ADR 0046·0049).
- 서버 쪽 세션의 유휴 만료 설정. 서버의 몫이다(ADR 0049 Consequences "서버의 몫").
- stdio 모양에 `[server.headers]`를 허용하기. 모르는 칸으로 거부된다.
- 최종 사용자 면과 위젯의 문구. 지금의 실패 항목 그대로다(ADR 0049 "바꾸지 않는 것").

## Further Notes

- 프로브의 수는 2026-11-09에 네 번 돌린 실행 가운데 마지막(응답 훅의 상태 기록, 토큰 로그, `httpcore2` 로거를 더한 판)의 것이고 README에 두 OS가 함께 있다. 앞선 세 실행은 사례와 기록 칸을 더해 가며 돌았고 겹치는 사례의 판정은 같았다. 셀프 리뷰 뒤 더한 사례 둘(`normal_own_delete`, 매니페스트의 stdio에 `command` 없음)은 같은 날 따로 돌렸다. 앞의 것은 `normal`과 함께 두 OS에서, 뒤의 것은 매니페스트 프로브 전체(16회차)를 다시 돌려서다. PR의 CodeRabbit 첫 회차를 반영해 `http_close.py`(예외 글의 비밀값 검사를 전체 글로, 종료 요청의 전송 오류를 삼킴, 유예를 종료 요청에만 둠, 기한 취소를 본 회차만 측정으로 셈)를 두 OS에서 열두 사례 전체로, `manifest_shape.py`(읽힌 모델이 기대와 같을 때만 측정, `--node-modules`를 절대 경로로)를 Windows에서 다시 돌렸다. 둘 다 측정 아님 0회차였고 README의 시간 범위는 그 판이다.
- 닫힌 포트의 거부까지 걸린 시간은 Windows 2.036~2.037초, Linux 0.002초다(쟀다. `http_close.py`의 `closed_port`). Windows의 2초는 루프백에서 IPv6와 IPv4를 차례로 시도하며 생기는 소켓의 거부 지연으로 본다(어림. 가르지 않았다. 설계 일지가 손으로 본 2.175초와 같은 자리). 꺼진 서버의 실패 시험은 그 시간을 단언하지 않는다.
- mcp 2.3.0이 종료 요청을 보내는 조건과 세션 식별자를 내주지 않는 것, 오류 응답을 상태 코드 없는 예외로 바꾸는 것은 그 판의 코드다. mcp를 올리는 티켓은 `terminate_on_close`의 뜻과 응답 훅으로 받는 세션 식별자, 404의 두 문구를 다시 대 본다.
- 리디렉션 정책은 정해지지 않았다(PR #501의 CodeRabbit 첫 회차가 짚었고 구현 티켓을 쪼개기 전에 정한다). 프로브의 클라이언트와 이 명세의 "접속"은 `follow_redirects`를 두지 않아 httpx2의 기본값(따르지 않음)이다(코드를 읽었다. 프로브에 그 인자가 없다). mcp가 자기 클라이언트를 만들 때는 따르게 하지만(어림. `create_mcp_http_client`를 읽지 않았다) 어댑터는 자기 클라이언트를 만든다. 그래서 `/mcp`를 `/mcp/`로 307으로 돌려보내는 서버(마운트 경로를 쓰는 ASGI 앱에서 흔하다. 어림)에는 초기화가 307 응답에서 끝나 `HTTP 307 Temporary Redirect`로 실패한다. 따르게 하면 종료 요청의 DELETE도 같은 클라이언트라 메서드를 지키며 따르지만(httpx 동작, 어림) 리디렉션 대상이 다른 출처이면 `Authorization`만 떼이고 다른 이름의 인증 헤더(`X-Api-Key` 등)는 실려 간다(어림. httpx의 리디렉션 헤더 처리를 읽지 않았다). 정할 것은 따를지, 따른다면 같은 출처만인지다. 사용자에게 묻는 결정이라 이 PR이 정하지 않았다.

(2026-11-09 명세 검토: 이 문단의 전제 둘(mcp가 자기 클라이언트에서는 리디렉션을 따르게 한다, 307 서버에는 초기화가 실패한다)은 틀렸고, 정책은 사용자가 정했다. 위 "닫기"의 주석이 바로잡는다.)
- 매니페스트 프로브(`manifest_shape.py`)는 주 체크아웃의 `web/node_modules`로 돌았다(워크트리에는 없다). 판은 저장소의 것과 같다(openapi-typescript 7.13.0, typescript 5.9.3).
- 상태 코드를 원인에 덧붙이는 결정은 설계가 묻지 않은 자리라 결정 "실패"에 더하는 것이고, ADR 0049의 둘째 이력에 적는다. 본문의 문장을 거짓으로 만들지 않아 포인터가 없다. 이 명세의 초안은 같은 이력에 쿼리 문자열을 떼는 결정을 함께 적고 결정 "주소"의 문장 하나에 포인터를 달았으나, 사용자가 승인에서 주소 전체를 골라 그 문단과 포인터를 걷었다(서두의 "이력은 둘이다", "실패 문구"의 거부한 안).
