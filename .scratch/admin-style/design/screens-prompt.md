# admin-style 화면 프롬프트

Claude Design(claude.ai/design)에서 관리 화면의 화면을 그릴 때 붙여 넣는 시작 프롬프트다. 와이어프레임으로 배치를 먼저 고르고, 고른 배치를 UI mockups로 완성한다. 둘 다 `/design-sync`로 올린 디자인 시스템으로 그린다(ADR 0025). 확정한 화면은 명세 직전의 근거가 된다.

프롬프트에 든 것은 세 가지다. **결정**은 ADR 0026(첫째 2026-10-06 이력의 반응형, 둘째 이력의 테마와 모드, 첫째 2026-10-12 이력의 설정 화면·아이콘·폭), `.scratch/plan.md`의 admin-style 행, 이 기능의 설계 인터뷰(일지 2026-10-12-01)가 정한 것이다. 화면 문구는 `CONTEXT.md`의 말과 관리 화면의 지금 문구에서 왔다. **이 프롬프트의 제안**은 와이어프레임에 두 안을 그릴 화면, 관리 화면만 쓰는 부품의 목록(표, 링크, 탐색 항목, 코드 칸, 테마 카드)처럼 그리는 데 필요해서 더한 것이고, 명세가 다시 정한다. 두 프롬프트의 "배치와 밀도"·"시각 방향"도 제안이다. 2026-10-12 사용자가 디자인이 예쁘지 않다며 관리 화면에 맞게 다시 디자인해 달라고 해(일지 2026-10-12-11) 참고 디자인에서 뽑은 규칙을 넣었고, 출처와 가져오지 않을 것은 `.scratch/design-system/design/refresh-prompt.md`의 "참고 디자인"이다. 그 재탐색이 고른 결과(ADR 0026의 새 이력)가 이 프롬프트의 값(기본 테마와 테마 이름, 배치와 밀도의 수치)과 다르면 재탐색 결과가 이기고, 그리기 전에 이 프롬프트를 고친다. **탐색용 가정**은 인터뷰가 묻지 않고 둔 것과 그리기 위한 값이고, 아래 두 프롬프트 끝의 "탐색용 가정"에 모았다.

## 하는 법

1~5는 사람이 한다. 내려받기(6)부터는 기본으로 명세 세션이 한다(아래 "고른 뒤").

그리기는 디자인 시스템의 재탐색(`.scratch/design-system/design/refresh-prompt.md`)이 패키지에 반영되고 `/design-sync`로 다시 올라간 뒤다. 차례는 `.scratch/plan.md`의 design-refresh 행이다.

1. **디자인 시스템을 맞춘다.** 그리기 직전에 `/design-sync`를 돌려 `web/packages/ui`를 Claude Design의 디자인 시스템 프로젝트에 맞춘다(`docs/agents/issue-tracker.md`의 화면 디자인 절). 사람이 세션에서 시작하는 스킬이다. 그 뒤 `packages/ui`가 바뀌었으면 다시 돈다. 저장소의 첫 `/design-sync`는 2026-10-12에 이 기능이 돌았다(일지 2026-10-12-07).
테마 다섯의 글꼴이 올라가 패키지 `build`는 고치지 않았다. 디자인 시스템 프로젝트의 이름은 "Agent OS 디자인 시스템"이고, 2에서
이것을 고른다.
2. **새 프로젝트를 연다.** Claude Design의 첫 화면에서 새 프로젝트를 시작하고, 입력창 아래의 Design system은 1에서 맞춘 Agent OS의 것을 고른다. 템플릿은 Wireframe이다. 템플릿이 긴 글 대신 질문 양식을 띄우면 아래 "양식이 뜨면"의 짧은 답을 칸마다 넣고, 긴 글은 양식을 보낸 뒤 같은 대화에 넣는다. 이 프롬프트를 쓴 세션은 로그인하지 않아 Wireframe과 UI mockups 템플릿이 양식을 띄우는지 보지 못했다(2026-10-12).
3. **와이어프레임을 그린다.** "1. 와이어프레임"을 넣는다. 글이 잘리면 "그릴 화면" 앞과 뒤를 두 번에 나눠 넣는다.
4. **안을 고른다.** A·B를 그린 화면마다 하나를 고르고, 고칠 것이 있으면 대화로 더 요청한다. 고른 뒤 같은 대화에 "실행 하나는 A, 플러그인 목록은 B, 설정은 A로 골랐다. 고른 안을 디자인 파일 안의 쪽에 적어 줘"처럼 넣는다. 대화에만 남은 결과는 내보낸 파일에 실리지 않을 수 있다(`kickoff/prompting.md`).
5. **완성 화면을 그린다.** 같은 프로젝트의 대화에 "2. UI mockups"를 넣는다. 고쳐 넣을 곳은 없다. 그 대화에서 템플릿을 바꿀 수 없어 그리기 어색하면, UI mockups 템플릿으로 새 프로젝트를 열고 고른 와이어프레임의 갈무리와 함께 같은 글을 넣는다. 그때는 프로젝트가 둘이고, 명세 세션에 링크 둘을 준다.
6. **내보낸다.** 디자인 파일을 연 채 오른쪽 위 Share → Export → Project HTML에서 Project archive(ZIP)를 고른다. Project archive는 프로젝트의 파일 전부를 담으므로, 한 프로젝트면 와이어프레임과 완성 화면이 함께 온다. 정해진 자리는 저장소의 바로 위 폴더(이 PC에서는 `C:\project`)다. 메뉴와 저장 창의 동작은 `.scratch/design-system/design/exploration-prompt.md`의 하는 법 4와 같다.

## 1. 와이어프레임

```text
Agent OS의 관리 화면을 와이어프레임으로 그려 줘. 관리 화면은 운영자가 플러그인을 켜고 끄고, 실행 목록과 실행 하나를 보고, 일시정지한 실행에 결정을 내리는 웹 앱이다. 지금 화면은 스타일 없이 서 있고, 이번에는 서버와 주고받는 것과 화면의 주소는 그대로 두고 겉모습과 배치를 새로 정한다. 색은 쓰지 말고 회색조로 부품의 자리, 크기, 차례만 보여 줘. 부품은 고른 디자인 시스템의 것(버튼, 아이콘 버튼, 글 입력, 스위치, 상태 배지, 알림, 표면, 아이콘)을 쓴다. 표, 링크, 탐색 항목, 코드 칸, 테마 카드처럼 관리 화면만 쓰는 부품은 디자인 시스템의 크기 단계로 그린다. 모든 결과는 대화의 답이 아니라 디자인 파일 안에 넣어 줘. 그 파일을 내보내 쓴다.

틀: 폭 768px 이상은 왼쪽 옆 탐색, 미만은 위 막대다. 탐색 항목은 플러그인, 실행, 설정 셋이고 위 막대에서도 메뉴 단추나 서랍 없이 셋이 늘어선다. 운영자의 이름이나 사진은 두지 않는다(관리 화면은 운영자의 신원을 모른다). 관리 토큰을 넣는 화면에는 탐색이 없다.

배치와 밀도: 운영자가 하루에 여러 번 열어 목록을 훑는 도구 화면이라 촘촘하게 둔다. 옆 탐색은 폭 256px 안팎에 항목 높이 36px, 아이콘과 글자를 함께 둔다. 화면 머리는 제목, 개수, 흐린 설명 한 줄이고, 그 화면에 동작이 있으면(읽는 화면의 새로 고침) 오른쪽 위에 둔다. 표가 중심이고 한 줄 칸의 행은 촘촘하다(36px 안팎). 표 위에 거르기를 두고, 실행 ID와 시각은 고정폭 칸이다. 묶음은 경계선보다 여백으로 나누고, 위계는 화면 제목만 크게 두고 나머지는 글자 굵기로 짓는다.

그릴 화면: 화면마다 데스크톱 1280px과 모바일 375px 두 폭이다. 아래에서 "A·B"라고 적은 화면은 데스크톱 배치를 두 안으로 그려 줘. 나머지는 한 안이다.
1. 관리 토큰 넣기: 설명 한 문단(agent-os serve를 띄울 때 AGENT_OS_ADMIN_TOKEN에 준 값이고, 이 탭에만 남고 탭을 닫으면 사라진다), 가린 입력 하나, "넣기". "관리 토큰이 거부됐다"와 서버에 닿지 못했을 때의 알림. 채널 토큰이 남아 있으면 "토큰 지우기" 버튼.
2. 플러그인 목록(첫 화면): 종류 넷(에이전트, MCP, 스킬, 모델)으로 묶고 행마다 이름(링크), 스위치, "켜짐"/"꺼짐". 행 아래의 표지 줄 둘: "읽을 수 없는 매니페스트: <이유>", "로더가 생기기 전에는 효과가 없다"(스킬과 모델). 빈 묶음은 "등록된 것이 없다". 켜고 끄기에 실패하면 목록 머리의 알림. A·B: A는 종류마다 묶은 행 목록, B는 종류를 열로 둔 표 하나.
3. 플러그인 하나: 이름, "켜짐"/"꺼짐", 매니페스트 JSON 코드 칸.
4. 실행 목록: 상태 거르기(전부, 일시정지, 끝남, 실패, 결말 없음). 데스크톱은 표이고 열은 상태(상태 배지), 실행(링크), 에이전트, 주체, 시작, 마지막이다. 모바일은 실행마다 카드다. 상태 없이 이유만 있는 "읽을 수 없는 트레이스: <이유>" 행, 아래의 "더 보기".
5. 실행 하나: 제목은 실행 식별자. 이벤트 열은 이벤트마다 종류와 시각을 머리로 한 카드이고, 필드를 모두 펼친 채 "용어집의 말 + 계약 이름"과 값으로 보인다. 그 아래에 결정 자리(도구 이름과 인자, 승인자 안내, 거부 사유 칸, 버튼 "거부"와 "승인")와 재개 스트림. A·B: A는 결정 자리가 이벤트 열 아래, B는 데스크톱에서 결정 자리가 오른쪽 옆 칸에 붙어 스크롤해도 보인다. 모바일은 둘 다 아래다.
6. 설정: 첫머리에 "테마는 이 브라우저에, 토큰은 이 탭에만 남는다. 서버의 구성은 바꾸지 않는다"는 뜻의 한 줄. 테마(카드 다섯 가운데 하나를 고르는 라디오 묶음), 채널 토큰(가린 입력과 "채널 토큰 넣기", 넣었으면 "채널 토큰을 넣었다"), "토큰 지우기"(관리 토큰과 채널 토큰을 모두 지운다). A·B: A는 테마 카드 다섯이 한 줄, B는 격자.

지켜 줄 것:
- 폭 320px에서도 가로 스크롤 없이 다시 흘러야 한다(WCAG 2.2의 리플로). 긴 JSON, 프롬프트, 인자는 줄을 바꿔 흐른다.
- 포인터로 누르는 목표는 가로세로 24px 이상이다.
- 상태는 색만으로 보이지 않는다. 상태 배지의 아이콘과 글자를 함께 쓴다.
- 빈 목록과 불러오는 중은 디자인 시스템 문서의 패턴 03.3, 03.4의 모양을 쓰되 문구와 열은 이 화면의 것으로 바꾼다. 요청이 실패하면(목록이나 하나를 읽지 못함, 켜고 끄지 못함, 결정을 보내지 못함) 패턴 03.2의 알림 모양으로 메시지를 보인다. 패턴에 있는 "다시 실행", "실행 보기", "위젯 넣는 법", "거르기 지우기", 기간, "요청"·"플러그인" 열은 관리 화면에 없는 동작과 데이터라 쓰지 않는다. 다시 읽다 실패하면 이미 보인 목록을 지우고 실패만 보인다.

탐색용 가정(결정이 아니니 바꿔도 된다): 설정 화면은 다른 화면처럼 관리 토큰을 넣은 뒤에 열린다. 탐색의 차례는 첫 화면에 맞춰 플러그인, 실행, 설정. 틀의 제품 이름은 "Agent OS".
```

## 2. UI mockups

4에서 고른 안을 디자인 파일에 적게 한 뒤 넣는 글이다.

```text
앞에서 고른 와이어프레임 안대로 관리 화면의 완성 화면을 그려 줘. 디자인 시스템의 기본 테마(먹)의 라이트 모드로 그린다. 화면과 폭은 와이어프레임과 같다(데스크톱 1280px, 모바일 375px). 모든 결과는 디자인 파일 안의 쪽으로 넣어 줘.

그릴 것에 더할 것:
- 실행 하나의 결정 자리는 디자인 시스템 문서의 패턴 03.1(승인 묻기)을 따른다. 버튼은 "거부"(보조)가 먼저, "승인"(주)이 나중이고, 자리 폭 360px 미만에서는 둘이 위아래로 꽉 찬다. 도구 이름은 고정폭 font-medium, 인자는 고정폭으로 고치거나 줄이지 않고 글자 그대로 보인다. 거부 사유는 반드시 적어야 하고 비면 "거부"가 막힌다.
- 결정 자리의 변형 넷. 기본. 꺼진 플러그인이 있어 막힘("꺼진 플러그인이 있어 재개할 수 없다: 에이전트 calc, MCP filesystem. 다시 켜면 결정을 낼 수 있다."). 최종 사용자의 실행(결정 자리 대신 "최종 사용자의 실행이라 결정은 그 사람만 낸다"). 채널 토큰이 없음(결정 자리 대신 "결정을 내리려면 설정에서 채널 토큰을 넣는다"와 설정으로 가는 링크). 최종 사용자의 실행이면 채널 토큰이 없어도 그 실행의 한 줄만 보이고, 형식 1 트레이스("형식 1 트레이스라 읽을 수 있지만 재개할 수 없다")에는 결정 자리도 안내도 없다.
- 재개 스트림이 끊겼을 때의 정보 알림: "재개 스트림이 끊겼다. 실행은 서버에서 계속된다" / "창을 닫거나 떠나도 실행은 끝까지 간다. 돌아오면 트레이스로 이어 본다".
- 실패 알림은 메시지 아래에 "추적 식별자: <값>"을 고정폭으로 보인다.
- 읽는 화면(목록, 하나)은 머리에 "새로 고침"을 두고, 다시 읽는 동안 "다시 확인하는 중"을 보인다.
- 설정의 테마 카드는 카드마다 그 테마로 칠한 작은 표본(테마 이름, 주 버튼, 상태 배지 하나, 고정폭 글자 한 줄)을 보인다. 테마는 먹, 청록, 공문, 황토, 자두이고 고른 카드가 드러난다. 카드 아래에 "모드(라이트·다크)는 시스템 설정을 따른다"는 뜻의 한 줄.
- 실행 목록의 시각은 "2026-10-12 14:03:22"처럼 적는다. 실행 하나의 이벤트 필드 값(시각 포함)은 트레이스의 글자 그대로다.

지켜 줄 것:
```

## 양식이 뜨면

Wireframe이나 UI mockups 템플릿이 질문 양식을 띄울 때 칸에 넣을 짧은 답이다. 칸의 이름은 보지 못했으므로 뜻이 가까운 칸에 넣고, 긴 글(위의 1이나 2)은 양식을 보낸 뒤 같은 대화에 넣는다.

- 무엇을 그리나: `Agent OS 관리 화면. 운영자가 플러그인을 켜고 끄고, 실행 목록과 실행 하나를 보고, 일시정지한 실행에 결정(승인·거부)을 내린다. 화면 여섯: 관리 토큰 넣기, 플러그인 목록, 플러그인 하나, 실행 목록, 실행 하나, 설정.`
- 누가 쓰나: `에이전트를 운영하는 개발자와 운영자. 데스크톱과 모바일 모두.`
- 폭: `데스크톱 1280px, 모바일 375px. 768px 이상은 옆 탐색, 미만은 위 막대.`
- 지킬 것: `한국어 문구. 디자인 시스템의 컴포넌트와 쓰임새 토큰만. 320px에서 가로 스크롤 없음. 누르는 목표 24px 이상. Claude Console·OpenAI Platform처럼 조용하고 촘촘한 도구 화면(무채색, 색은 상태에만, 표가 중심). 그 제품들의 로고·브랜드 색·글꼴·화면 구성은 복제하지 않고 배너·차트·검색·계정 표시는 없다.`

## 고른 뒤

하는 법 1~5를 마친 뒤의 일이다. 사람은 세션이 브라우저를 쓸 때 로그인하고 내려받기를 허락하며, 묻는 것에 답한다. 내려받기, 파일 옮기기, 기록, 명세는 명세 세션이 한다. 차례와 저장 창을 다루는 법은 `.scratch/design-system/design/exploration-prompt.md`의 "고른 뒤"와 같고, 이 기능에서 다른 것만 적는다.

1. **내려받는다.** Claude Design 프로젝트의 링크(하는 법 5에서 프로젝트가 둘로 갈렸으면 둘)는 지시문에서 받고, 없으면 사람에게 묻는다. 링크에서 `file=`을 떼고 열어 파일 목록에서 와이어프레임과 완성 화면이 모두 있는지 본다. 내려받기마다 파일 이름, 출처, 크기를 보이고 허락을 받는다.
2. **파일을 옮긴다.** 정해진 자리(`C:\project`)에서 가장 새 ZIP을 찾아 풀고, `.dc.html`들과 `support.js`를 이 폴더(`.scratch/admin-style/design/`)로 옮긴다. `.thumbnail`은 옮기지 않고, 정해진 자리의 ZIP은 지우지 않는다. 맞는 파일이 없거나 여럿이면 사람에게 묻는다.
3. **표를 만든다.** 이 폴더에 `README.md`를 만들고 `docs/agents/issue-tracker.md` 화면 디자인 절의 표를 둔다. 그 절대로 화면마다 한 줄이고, 한 파일에 화면이 여럿이면 파일 칸이 같은 줄이 여럿이다.
   - 근거 문서: `docs/adr/0026-design-system-is-one-package-judged-by-storybook.md`, `.scratch/plan.md`(admin-style 행), `.scratch/admin-style/design/screens-prompt.md`
   - 기준 커밋: 붙여 넣은 날의 그 근거 문서들의 커밋이다. 구하는 명령과 `--until`의 자리는 탐색 프롬프트의 "고른 뒤" 3과 같고, 칸에 "(어림)"을 붙인다.
   - 동기화한 커밋: 하는 법 1의 `/design-sync`가 올린 `packages/ui`의 커밋이다. `/design-sync`의 상태(`.design-sync/`)가 커밋됐으면 그 커밋에서 읽고, 모르면 사람에게 묻는다.
   - A·B를 그린 화면의 줄에는 고른 안을 함께 적는다. 디자인 파일에 적혀 있지 않으면 사람에게 묻는다.
4. **명세를 쓴다.** to-spec 스킬의 차례대로 쓰고, 명세가 완성 화면을 가리킨다(ADR 0025). 그림이 이 프롬프트나 ADR 0026의 첫째 2026-10-12 이력과 다르면(없는 데이터를 그렸거나, 금지한 말을 썼거나, 새 아이콘을 썼으면) 명세 전에 사람에게 묻는다. 탐색용 가정은 명세가 결정으로 바꾸거나 다시 묻는다.
