# skill-plugin 명세: 스킬을 실행마다 읽어 컨텍스트로 넘기는 플러그인

Status: ready-for-agent

설계는 ADR 0041과 설계 일지 2026-11-03-02다. 이 명세는 그 설계가 명세에 넘긴 것과 봇 회차가 보류한 둘을 정하고, 설계가 이미 정한 것은 다시 결정하지 않고 티켓이 읽을 자리에 옮긴다. 용어는 `CONTEXT.md`의 스킬(에이전트가 매니페스트로 골라 컨텍스트로 받는 절차 지식의 폴더), 머리말(스킬 문서의 첫머리에서 이름과 설명을 적는 부분. 본문은 그 뒤다), 컨텍스트(런타임이 에이전트에게 넘기는 손잡이)다. "스킬 문서"는 폴더 안의 `SKILL.md` 파일을 가리킨다.

**넘겨받은 것은 열하나다.** (1) 스킬은 `plugins/skills/<이름>/`의 플러그인이고 그 폴더에 공통 넷(`schema_version = "1"`, `kind = "skill"`, `name`, `version`)만 적은 `plugin.toml`과 Agent Skills 표준의 `SKILL.md`가 함께 있다. 스킬 문서는 `---`로 감싼 YAML 머리말 뒤에 마크다운 본문이고, 머리말의 필수 칸은 `name`과 `description`이며, `name`은 폴더 이름과 같아야 하고 이름의 규칙은 플러그인 이름 패턴이다. 본문은 머리말 뒤의 글 그대로이고 크기 상한이 없다. 스킬 문서가 없거나, 머리말이 YAML로 읽히지 않거나, 필수 두 칸이 없거나 비었거나, `name`이 폴더 이름과 다르면 매니페스트의 어긋남과 같은 `PluginError`이고, 읽지 못한 문구는 경로와 줄·칸 위치와 오류 종류만 싣고 머리말의 값을 되울리지 않는다. (2) 머리말은 PyYAML(`yaml.safe_load`)로 전체를 읽고 두 칸만 쓰며 표준의 선택 칸과 제품별 키는 읽지도 거부하지도 않는다. PyYAML은 `pyproject.toml`의 직접 의존성과 `docs/constitution/tech.md`의 런타임 의존성 줄에 들고, 머리말을 읽는 함수는 `parse_manifest`처럼 sdk에 두며 어댑터의 읽기가 그것을 부른다. (3) 에이전트 매니페스트에 플러그인 이름 패턴의 선택 칸 `skills`가 늘고 기본은 빈 목록이며, 에이전트가 아닌 종류가 적으면 읽는 단계에서 거부하고 `schema_version`은 "1" 그대로다(ADR 0008의 2026-11-03 이력). (4) 실행을 준비할 때마다 `skills`에 적힌 이름마다 매니페스트와 스킬 문서를 읽고 캐시하지 않는다. 준비 순서는 깨짐의 끝인 모델 뒤·운영자 파일 앞에 스킬이, 꺼짐의 끝에 스킬(적힌 순서)이 서고 `tests/core/test_run.py`의 "꺼진 플러그인" 절이 고정한다. 없거나 읽히지 않으면 없는 mcp와 같은 `PluginError`(운영자 면 500, 최종 사용자 면 고정 문구 500), 꺼졌으면 `Disabled`(409)이고 문구는 `꺼진 플러그인이다: skill <이름> (에이전트 <이름> 이 쓴다)`다. 재개도 같은 준비를 지나 지금 디스크의 본문을 받고, 멈춘 사이 고친 본문이 재개 대조에 걸리거나 걸리지 않는 범위는 ADR 0041 "준비 단계에 스킬 판정이 는다"다. (5) `PluginSource`에 스킬 하나의 스킬 문서를 읽어 돌려주는 메서드 `read_skill`이 늘고 포트는 다섯 그대로다. 단건 읽기의 약속(부재는 값, 손상은 `PluginError`)을 따르고 목록은 매니페스트만 읽어 스킬 문서가 없는 폴더도 관리 목록의 보통 행이다(ADR 0012의 2026-11-03 이력). (6) `AgentContext.skills`는 매니페스트 `skills`의 순서를 지킨 불변 열이고 원소는 이름·설명·본문을 든 불변 값 sdk `Skill`이다. 값은 `run()` 전에 정해져 실행 안에서 바뀌지 않고 재개해도 같은 준비로 다시 만들며, 고르지 않은 실행에서는 빈 열이다. 본문은 에이전트 코드와 같은 신뢰 수준이라 지시로 엮어도 되고, 런타임은 `llm()`에 아무것도 붙이지 않으며, core의 컨텍스트와 테스트의 가짜 컨텍스트가 이 멤버를 시그니처로 만족한다. (7) 트레이스는 형식 3 그대로이고 스킬 이름을 이벤트에 적지 않는다. (8) 계약이 바뀐다. `openapi.json`의 `PluginManifest`에 `skills`가 들고 생성 타입과 스토리·테스트의 리터럴이 바뀌며 관리 API의 경로는 늘지 않고 스킬의 설명과 본문은 관리 API에 나오지 않는다. 관리 화면은 로더 없는 종류 집합과 안내 줄을 걷고, 결정 칸의 꺼짐 미리 알림이 에이전트가 고른 스킬도 mcp와 같은 꼴로 센다. 화면 디자인 단계는 없고 첫 티켓이 계약 티켓이다. (9) 저장소가 예시 스킬 하나를 두고 calc가 `skills`로 고르며 calc 코드가 본문을 프롬프트에 엮고, `tests/test_calc_plugin.py`의 `FRESH_PROMPT`가 바뀐다. (10) 이번 범위 밖은 ADR 0041의 "이번 범위 밖" 불릿이다. (11) 구현 티켓이 고칠 곳은 ADR 0041의 "구현 티켓이 고칠 곳" 불릿이다.

**둘은 사용자가 이 명세를 쓰며 골랐다.** 시험을 붙이는 자리(Testing Decisions의 "이음매")와 예시 스킬의 이름과 본문의 갈래("예시 스킬").

**열셋은 명세가 넘겨받은 것 안에서 스스로 정했고 각 절 제목의 괄호에 "명세가 정했다"로 표시한다.** 머리말을 본문에서 떼는 규칙, 머리말의 두 칸과 값의 모양, sdk의 스킬 값과 읽는 함수, 머리말 거부를 `PluginError`로 바꾸는 층, 포트 `read_skill`의 시그니처와 돌려주는 값의 자리, 읽지 못한 문구와 이름 어긋남 문구, 매니페스트 `skills`의 중복, 실행 준비의 순서와 없음의 문구, 컨텍스트 멤버의 타입과 신뢰 경계 문구, 예시 스킬을 엮는 모양, YAML의 import 경계, 고칠 자리의 묶음, 실제 모델 호출 하나. 앞의 넷째와 다섯째가 봇 회차(일지 2026-11-03-02 "봇 회차 (셋째 세션)")가 명세에 보류한 둘이다.

**이력은 둘이다.** ADR 0041의 2026-11-03 이력(명세가 정한 다섯과 잰 것 둘)과 ADR 0012의 2026-11-03 둘째 이력(`read_skill`의 시그니처와 돌려주는 값의 자리).

**거부한 안은 스물여섯이고 각 절의 "거부한 안:" 표시에 있다.**

측정은 `.scratch/skill-plugin/probes/`의 셋이고 결과는 그 `README.md`다. 설계가 잰 `yaml_frontmatter.py`에 이 명세가 `frontmatter_split.py`와 `frontmatter_values.py`를 더했다. 이 명세에서 "쟀다"는 그 셋을 가리키고, 손으로 본 것과 코드를 읽은 것과 원문을 읽은 것과 어림은 그렇게 적는다. Agent Skills 표준은 설계가 웹 요약으로 읽었고, 이 명세는 표준 페이지(https://agentskills.io/specification)와 참조 구현 `skills-ref`의 `parser.py`·`validator.py`(github `agentskills/agentskills` main)의 원문을 2026-11-03에 내장 브라우저로 읽었다. 설계가 웹 요약으로 적은 것 가운데 이 명세가 쓰는 넷(필수 두 칸, 선택 칸 넷, `name`의 규칙, 본문의 형식 제한 없음)은 원문과 같았다. 참조 구현이 머리말 읽기에 PyYAML이 아니라 strictyaml을 쓰고, 표준의 여섯 칸 밖의 키를 거부하며, `name`을 NFKC로 정규화하는 것도 같은 원문에서 읽었다(아래 "머리말의 두 칸과 값의 모양").

## Problem Statement

에이전트 개발자 관점. 에이전트에게 절차 지식(어떤 형식으로 답할지, 요청을 어떻게 읽을지)을 주려면 에이전트 코드의 프롬프트 문자열에 적어야 한다. 그 글을 고치려면 코드를 고치고 서버를 다시 띄워야 하고, 같은 글을 여러 에이전트가 쓰려면 복사해야 하며, 다른 제품용으로 이미 Agent Skills 표준으로 쓰인 스킬 폴더를 그대로 들일 수 없다. 운영자 관점. 관리 화면에는 `plugins/skills/`에 둔 파일이 스킬 행으로 뜨고 켜고 끌 수 있지만 "로더가 생기기 전에는 효과가 없다"는 안내 줄이 붙어 있고, 실제로 런타임이 그 파일을 읽지 않아 켜고 꺼도 아무것도 달라지지 않는다.

## Solution

스킬이 다른 셋(에이전트, mcp, 모델)과 같은 플러그인이 된다. 운영자는 `plugins/skills/<이름>/`에 넉 줄의 `plugin.toml`과 표준의 `SKILL.md`를 두고, 에이전트 개발자는 매니페스트의 `skills = ["<이름>", …]`으로 스킬을 고른다. 런타임은 실행을 준비할 때마다 고른 스킬의 매니페스트와 스킬 문서를 읽어 이름·설명·본문을 컨텍스트의 `skills`로 넘기고, 에이전트 코드는 그것을 자기 프롬프트에 엮는다. 그래서 스킬 문서를 고치거나 관리 화면에서 켜고 끈 것이 서버를 다시 띄우지 않아도 다음 실행부터 듣고, 꺼진 스킬을 쓰는 실행은 꺼진 mcp처럼 409로 거부되며, 깨진 스킬 문서는 실행 전에 500으로 드러난다. 관리 화면의 스킬 행에서 안내 줄이 사라지고 결정 칸이 꺼진 스킬을 미리 알린다. 트레이스는 바뀌지 않고 `ctx.llm()`도 바뀌지 않는다. 저장소의 calc가 예시 스킬 하나를 골라 실제 모델 시험이 스킬 경로를 끝까지 지난다.

## User Stories

1. As an 에이전트 개발자, I want 매니페스트에 `skills = ["<이름>"]`을 적어 스킬을 고르기, so that 절차 지식을 코드 밖의 파일로 둔다.
2. As an 에이전트 개발자, I want `ctx.skills`로 이름·설명·본문을 매니페스트에 적은 순서로 받기, so that 내 프롬프트에 내가 정한 모양으로 엮는다.
3. As an 에이전트 개발자, I want `skills`를 적지 않으면 `ctx.skills`가 빈 열이기, so that 지금 있는 에이전트가 그대로 돈다.
4. As an 에이전트 개발자, I want `ctx.llm()`이 그대로이고 런타임이 프롬프트에 아무것도 붙이지 않기, so that 모델이 받은 글이 트레이스의 `llm_called.prompt`와 같다.
5. As an 에이전트 개발자, I want 스킬 본문이 에이전트 코드와 같은 신뢰 수준이라는 것이 sdk 문서에 적혀 있기, so that 대화 멤버와 달리 지시로 엮어도 된다는 것을 안다.
6. As an 에이전트 개발자, I want 내가 고른 스킬이 없거나 스킬 문서가 없을 때 에이전트 이름과 스킬 이름이 든 오류를 받기, so that 어느 매니페스트와 폴더를 고칠지 바로 안다.
7. As an 에이전트 개발자, I want 매니페스트의 `skills`에 같은 이름을 두 번 적으면 읽는 단계에서 거부되기, so that 오타가 조용히 지나가지 않는다.
8. As an 운영자, I want 다른 제품용으로 쓰인 스킬 폴더를 `plugin.toml` 넉 줄만 더해 그대로 들이기(이름이 플러그인 이름 패턴에 맞을 때), so that 머리말의 제품별 키를 지우지 않아도 된다.
9. As an 운영자, I want 스킬 문서의 본문을 고치면 다음 실행부터 듣기, so that 서버를 다시 띄우지 않고 지식을 고친다.
10. As an 운영자, I want 관리 화면에서 스킬을 끄면 그 스킬을 쓰는 다음 실행이 409로 거부되기, so that 켜고 끄기가 실제 효과를 가진다.
11. As an 운영자, I want 운영자 채널의 409·500 메시지에 플러그인의 종류와 이름과 그것을 쓰는 에이전트가 적히기, so that 어느 파일을 고칠지 바로 안다.
12. As an 운영자, I want 머리말이 깨진 스킬 문서의 오류 문구에 경로와 줄·칸과 오류 종류만 있고 머리말에 적은 값이 없기, so that 머리말에 잘못 적은 비밀이 목록·상세·실행 오류로 나가지 않는다.
13. As an 운영자, I want 머리말의 `name`이 폴더 이름과 다르면 실행 전에 거부되기, so that 복사해 온 스킬의 이름을 고치지 않은 것이 드러난다.
14. As an 운영자, I want 관리 화면의 스킬 행에서 "로더가 생기기 전에는 효과가 없다"가 사라지기, so that 화면이 지금의 동작을 말한다.
15. As an 운영자, I want 결정 칸이 멈춘 실행의 에이전트가 고른 스킬이 꺼져 있으면 mcp처럼 미리 알리기, so that 누른 뒤의 409를 기다리지 않는다.
16. As an 운영자, I want 스킬 문서가 없는 스킬 폴더도 관리 목록에 보통 행으로 뜨기, so that 등록했다고 믿는 것과 실제가 어긋나지 않는다.
17. As a 최종 사용자, I want 꺼진 스킬 때문에 거부될 때 종류와 이름 없는 고정 문구의 409를 받기, so that 서버 안쪽의 구성이 밖으로 새지 않는다.
18. As a 최종 사용자, I want 없거나 깨진 스킬 때문에 실패할 때 고정 문구의 500을 받기, so that 위젯이 저장한 대화를 지우지 않는다.
19. As a 최종 사용자, I want 재개가 지금 디스크의 스킬 문서로 돌기, so that 운영자가 바꾼 지식이 내 다음 실행부터 듣는다.
20. As a 저장소 기여자, I want 포트가 다섯 그대로이고 가짜 하나로 core를 시험하기, so that 시험이 빠르고 결정적이다.
21. As a 저장소 기여자, I want 생성된 TS 타입이 `skills`를 필수로 받아 옛 리터럴이 타입 검사에서 깨지기, so that 계약 변경이 조용히 지나가지 않는다.
22. As a 저장소 기여자, I want `import yaml`이 sdk 밖에서 import-linter에 막히기, so that 머리말 읽기가 한 층에만 산다.
23. As a 저장소 기여자, I want 실제 모델 시험 하나가 저장소의 예시 스킬 본문이 모델에 간 것을 트레이스로 보기, so that 스킬 경로가 끝까지 도는 바깥 증거가 있다.
24. As a 저장소 기여자, I want 머리말 가르기와 두 칸 검증의 경계 사례가 프로브와 같은 사례로 sdk 시험에 서기, so that 명세가 잰 것과 구현이 어긋나지 않는다.

## Implementation Decisions

구현 파일의 경로와 코드 조각은 새로 짓지 않는다. 규칙 문서·ADR·테스트 선례의 경로와 ADR 0041이 이미 든 구현 경로는 옮겨 적는다.

### 스킬 폴더와 매니페스트 (넘겨받았다)

- 폴더는 `plugins/skills/<이름>/`이고 `plugin.toml`은 공통 넷뿐이며 종류별 칸이 없다. 스킬 종류가 다른 종류의 칸(`entrypoint`, `mcp`, `requires_approval`, `conversation_limit`, `model`, 모델의 넷, `[server]`)을 적으면 지금처럼 거부한다(`tests/sdk/test_manifest.py`의 종류별 거부 선례).
- 에이전트 매니페스트의 `skills`는 플러그인 이름 패턴의 목록이고 선택 칸이며 기본은 빈 목록이다(`mcp = [...]`와 같은 모양). 에이전트가 아닌 종류가 적으면 `requires_approval`처럼 거부한다. 이름의 패턴은 sdk의 `PluginName` 그대로라 런타임이 다시 검증하지 않고, 가리키는 스킬 플러그인이 실재하는지는 매니페스트만으로 알 수 없어 실행 준비가 본다. `schema_version`은 "1" 그대로다.

### 머리말을 본문에서 떼는 규칙 (명세가 정했다. 쟀다)

- 규칙은 줄 단위다. 스킬 문서의 첫 줄이 `---` 그대로여야 하고, 그 뒤 처음 나오는 `---` 그대로인 줄이 닫는 줄이다. 줄은 `\n`으로 가르고 두 표지 줄을 알아볼 때만 줄 끝의 `\r` 하나를 뗀다(CRLF. `\r`이 둘이면 표지 줄이 아니다). 머리말은 두 표지 줄 사이의 글이고, 본문은 닫는 줄의 줄 바꿈 뒤의 글 그대로다. 머리말도 본문도 앞뒤를 다듬지 않는다. 첫 줄이 `---`가 아니면 "머리말로 시작하지 않는다", 닫는 줄이 없으면 "머리말이 닫히지 않았다"로 거부한다.
- 파일 전체를 `yaml.safe_load`에 그대로 넘기면 둘째 `---`가 둘째 문서의 시작이라 거부되므로(`ComposerError`. 쟀다, `frontmatter_split.py`의 양성 대조) YAML에 넘기기 전에 이 규칙이 선다. 이 규칙이 LF, CRLF, 본문 안의 `---` 줄(본문에 남는다), 본문 없음, 닫는 줄 뒤 줄 바꿈 없음, 머리말 값 안의 `---`(줄 가운데. 값 그대로)를 기대한 머리말과 본문으로 내고, BOM으로 시작하거나 앞에 빈 줄이 있거나 머리말 없이 본문뿐이거나 첫 줄 끝의 `\r`이 둘인 글을 "시작하지 않는다"로 거부하는 것을 쟀다(같은 프로브). 빈 머리말(`---` 두 줄이 붙음)은 YAML이 `None`을 내므로 아래 "두 칸과 값의 모양"의 "맵이 아니다"로 거부된다(쟀다).
- 어댑터는 스킬 문서를 매니페스트와 같은 길(텍스트 모드 `read_text(encoding="utf-8")`. `adapters/filesystem.py`의 `_parse`를 읽었다)로 읽는다. 그 길은 파이썬의 보편 줄 바꿈이라 CRLF 파일의 줄 끝이 `parse_skill`에 닿기 전에 `\n`이 되고(쟀다, 같은 프로브의 파일 회차), 그래서 실제 폴더에서 읽은 본문은 LF다. 규칙의 `\r` 떼기는 글을 직접 넘기는 호출(sdk 시험, 다른 어댑터)에서 쓰인다. BOM은 그 길로 읽어도 U+FEFF가 첫 글자로 남아 "시작하지 않는다"로 거부된다(쟀다). 첫 줄 끝의 `\r`이 둘인 파일과 홀로 선 `\r`(옛 Mac 줄 끝)뿐인 파일은 그 길이 `\r`을 모두 `\n`으로 바꿔 받아들여진다(쟀다, 같은 프로브의 파일 회차). 그래서 `\r` 둘의 거부와 홀로 선 `\r`의 거부는 글을 직접 넘길 때만 나고, 어댑터를 지나는 시험은 그 거부를 기대하지 않는다.
- 줄 단위 규칙이 잃는 유효 입력은 없다. 머리말 안의 `---` 줄(열 0)은 큰따옴표 스칼라 안이면 `ScannerError`, 블록 스칼라 안이나 평문 스칼라의 이어지는 줄이면 `ComposerError`로 YAML 자체가 거부하고, 같은 세 자리에서 그 줄만 뺀 모양은 받아들여진다(세 자리와 그 대조를 쟀다, 같은 프로브의 갈래 회차. 거부의 까닭은 그 줄이지 둘러싼 모양이 아니다). 까닭은 PyYAML 스캐너가 열 0의 `---` 뒤에 공백이나 줄 바꿈이 오면 자리와 무관하게 문서 시작으로 보기 때문이다(설치된 6.0.3의 `yaml/scanner.py` `check_document_start`를 읽었다). 그래서 닫는 줄로 삼은 `---` 줄이 유효한 머리말 안에 있을 수 없다.
- 거부한 안: Agent Skills 참조 구현 `skills-ref`의 `parser.py`가 쓰는 글자 열 가르기(`content.split("---", 2)`. 원문을 읽었다. 참조 구현은 머리말 읽기에 strictyaml을 쓰지만 이 가르기는 읽기 전의 글자 열 처리라 라이브러리와 무관하다). 값 안의 `---`(`description: 가 --- 나`)에서 머리말을 `가 `에서 끊어 설명이 `가`가 된다(쟀다, 갈래 회차). 줄 단위 규칙은 같은 입력을 값 그대로 읽는다. 거부한 안: 닫는 줄의 꼬리 공백 허용(`--- `). "그대로"라는 규칙 하나가 "다듬은 뒤"가 되고 재지 않았다. 거부한 안: BOM(U+FEFF)을 벗겨 주는 것. 첫 줄이 `---` 그대로여야 한다는 규칙 하나로 닫히고, 매니페스트도 BOM 뒤의 TOML을 `tomllib`이 거부한다(쟀다, 같은 프로브의 대조 회차). 거부한 안: 참조 구현처럼 본문의 앞뒤 공백을 다듬는 것. ADR 0041이 "본문은 머리말 뒤의 글 그대로"라고 정했고, 다듬는 것은 엮는 에이전트의 몫이다.

### 머리말의 두 칸과 값의 모양 (명세가 정했다. 쟀다)

- 뗀 머리말을 `yaml.safe_load`로 읽은 값이 맵이 아니면(빈 머리말의 `None`, 스칼라, 목록) "머리말이 맵이 아니다"로 거부한다.
- 맵은 sdk의 pydantic 모델로 좁힌다. 모양은 `strict=True`, `extra="ignore"`, `frozen=True`에 `name`은 플러그인 이름 패턴(`PLUGIN_NAME_PATTERN`)의 문자열, `description`은 `min_length=1`의 문자열에 공백뿐을 거부하는 검증자다. `strict`라 문자열 아닌 값 — 정수(`name: 123`), 불린, 널(`~`), 날짜로 읽히는 값(`2026-11-03`), `!!binary`의 bytes, 목록(`description: [a, b]`) — 이 모두 `string_type`으로 거부되고, 빈 문자열은 `string_too_short`, 공백뿐은 `value_error`, 패턴 밖의 `name`(대문자, 한 글자)은 `string_pattern_mismatch`, 칸이 없으면 `missing`이다(쟀다, `frontmatter_values.py`. 표지 열둘은 그 README). 표준의 선택 칸(`license`, `compatibility`, `metadata`, `allowed-tools`)과 제품별 키(`disable-model-invocation`)는 무시된다(쟀다). 값은 다듬지 않는다 — `description`의 앞뒤 공백은 그대로다. 참조 구현의 `validator.py`는 표준의 여섯 칸 밖의 키를 거부하고 `name`을 NFKC로 정규화한다(원문을 읽었다). 모르는 키를 무시하는 것은 ADR 0041의 결정이고, 그래서 참조 구현의 검증을 지나지 못하는 다른 제품용 스킬도 들어온다(저장소 `.claude/skills` 가운데 다섯이 쓰는 `disable-model-invocation`이 그 예다). 정규화는 하지 않는다 — 패턴이 ASCII 소문자만 받으므로 전각 글자처럼 정규화해야 맞는 이름은 그대로 거부된다.
- ADR 0041이 "없거나 비었거나"로 적은 거부에 "문자열이 아니거나"가 이렇게 더해진다(둘째 세션의 PR 직전 보안 리뷰가 명세에 더한 것. 일지 2026-11-03-02). 본문이 비어 있어도 거부하지 않는다 — 표준은 본문에 형식 제한을 두지 않고(원문을 읽었다), 효과 없는 스킬을 두는 것은 운영자의 선택이다.
- 거부한 안: pydantic 없이 `isinstance(value, str)`로 보는 것. 참조 구현이 그렇게 하지만(원문을 읽었다), 패턴·길이·공백의 셋을 손으로 더 봐야 하고 거부의 표지(`type`과 `loc`)가 매니페스트와 다른 모양이 된다. 거부한 안: lax 모드. 명세가 잰 경계는 strict뿐이고, lax가 bytes를 문자열로 받는지 재지 않았다. 거부한 안: 표준의 이름 규칙 가운데 패턴이 보지 않는 것(끝 하이픈 금지, 연속 하이픈 금지)과 설명의 1024자 상한을 더 보는 것. ADR 0041이 이름의 규칙을 플러그인 이름 패턴(둘에서 63자라 표준의 64자 이름은 이미 받지 않는다)으로 정했고 본문 크기 상한을 범위 밖에 두었다. 설명의 상한도 같은 자리라 범위 밖이다(아래 Out of Scope). 거부한 안: 이름 패턴을 표준이 허락하는 유니코드 소문자(참조 구현 `validator.py`는 `isalnum()`으로 받는다, 원문을 읽었다)로 넓히는 것. 이름은 폴더 이름이자 매니페스트의 `name`이라 에이전트·mcp·모델과 한 규칙(플러그인 이름 패턴, ADR 0041)이고, 그래서 한글이나 전각 글자가 든 이름의 스킬 폴더는 들어오지 못한다(아래 Out of Scope).

### sdk의 스킬 값과 읽는 함수 (명세가 정했다)

- sdk에 불변 값 `Skill`이 선다. `Conversation`·`Exchange`와 같은 `frozen` dataclass이고 멤버는 셋 — `name`(`PluginName`), `description`(`str`), `body`(`str`)이다. 다른 멤버는 없다(선택 칸은 범위 밖이다). sdk의 공개 표면(`agent_os.sdk`)에 `Skill`과 아래 함수가 든다.
- sdk에 `parse_skill(text) -> Skill`이 선다. 스킬 문서의 글을 받아 위 두 절의 규칙대로 머리말을 떼고 YAML로 읽고 모델로 좁혀 `Skill`을 돌려준다. `name`은 모델이 패턴을 지났으므로 `PluginName`으로 감싼다. 폴더 이름과의 대조는 이 함수의 몫이 아니다(아래 "포트 `read_skill`"). `import yaml`은 이 함수가 사는 모듈만 한다(아래 "YAML의 import 경계").
- 실패는 세 종류이고 모두 `ValueError` 계열이다. 가르기와 맵 아님은 고정 문구의 `ValueError`, 두 칸의 거부는 pydantic `ValidationError`(`ValueError`의 하위), 머리말이 YAML로 읽히지 않는 것(YAML 읽기가 낸 어떤 예외든)은 아래 절이 정한 `ValueError`다. `parse_manifest`가 `tomllib`의 `TOMLDecodeError`(`ValueError`)와 `ValidationError`를 그대로 내는 것과 같은 모양이라, 어댑터가 잡는 예외의 집합이 매니페스트와 같다.
- 거부한 안: `Skill`을 pydantic 모델로 두는 것. 관리 API에 나가지 않는 값이라 직렬화 스키마가 필요 없고, 컨텍스트의 다른 값(`Conversation`)이 dataclass다. 거부한 안: 머리말 모델을 공개 표면에 올리는 것. 두 칸만 보는 사적인 좁힘이고, 플러그인이 쓸 것은 `Skill`뿐이다.

### 머리말 거부를 `PluginError`로 바꾸는 층 (명세가 정했다. 봇 회차의 보류 하나)

- `yaml.YAMLError`는 `ValueError`가 아니라서(ADR 0041이 설치된 판을 읽었다) 어댑터의 매니페스트 읽기 `_parse`가 잡는 모양(`OSError`, `ValidationError`, `ValueError`)을 그대로 쓰면 날것으로 올라간다. 그리고 `yaml.safe_load`가 내는 예외는 `YAMLError`만이 아니다 — 명시적 태그(`!!int`, `!!float`, `!!bool`, `!!timestamp`)의 값 변환이 실패하면 변환 함수의 `ValueError`·`KeyError`·`AttributeError`가 그대로 올라오고, 앞의 셋은 `str`에 운영자가 적은 값을 싣는다(쟀다, `frontmatter_values.py`의 태그 회차 넷. 셀프 리뷰 표준 축이 손으로 쳐 보인 반례다). 바꾸는 층은 sdk다. `parse_skill`이 `yaml.safe_load` 호출 하나를 `except Exception`으로 감싸 거기서 난 모든 예외를 고정 문구의 `ValueError`로 바꿔 던지고(원인은 `__cause__`. 감싸는 범위는 그 호출 하나이고 가르기와 모델 좁히기는 밖이다. 넓은 `except`의 선례는 어댑터의 진입점 import `_import`다), 어댑터의 `read_skill`은 매니페스트와 같은 집합(`OSError`, `ValidationError`, `ValueError`)을 잡아 `PluginError`로 만든다. 그래서 `yaml`의 예외 타입을 아는 층이 sdk 하나이고, 어댑터는 YAML을 모른 채 매니페스트와 같은 길로 감싼다.
- 바꿔 던지는 문구는 `머리말이 YAML로 읽히지 않는다: <오류 종류>`이고, 예외가 `MarkedYAMLError`이고 `problem_mark`가 있으면 ` (줄 N, 칸 M)`이 붙는다. 오류 종류는 예외의 클래스 이름(`ScannerError`, `ValueError` 등)이고, 줄·칸은 `problem_mark`에서 읽어 파일 기준 1부터 세는 값으로 옮긴다(`problem_mark.line`은 넘긴 머리말 글 기준 0부터라 — 쟀다, `frontmatter_values.py` — 여는 `---` 줄만큼 1을 더하고 1부터 세느라 1을 더 더한다. 칸은 1을 더한다). `problem_mark`가 없는 `YAMLError`(`ReaderError` 등)와 `YAMLError`가 아닌 예외는 줄·칸 없이 종류만이다. `str(error)`와 `problem`·`context` 문구는 어디에도 싣지 않는다 — `MarkedYAMLError`의 `str`이 문제 자리의 원문 조각을 싣는 것(쟀다, 같은 프로브의 양성 대조)과 `problem` 문구가 원문의 글자를 들 수 있는 것(설치된 6.0.3의 `yaml/scanner.py`·`parser.py`·`composer.py`·`constructor.py`를 `%r` 자리로 훑었다. 스캐너의 `found character %r that cannot start any token`, 컴포저의 `found undefined alias %r` 꼴)과 태그 변환의 `ValueError`·`KeyError`가 값을 싣는 것(쟀다, 같은 프로브) 때문이다.
- 거부한 안: `yaml.YAMLError`만 잡는 것(이 명세의 첫 판). 태그 변환의 예외가 어댑터의 `except` 집합 밖(`KeyError`, `AttributeError`)으로 날것으로 올라가거나 안(`ValueError`)으로 들어와 `_describe`의 `str`에 값이 실린다. 셀프 리뷰 표준 축이 잡았다. 거부한 안: 어댑터가 YAML 읽기의 예외를 직접 잡는 것. 어댑터가 `import yaml`을 하게 되어 YAML을 아는 층이 둘이 되고, 원문 조각을 빼는 일도 어댑터가 다시 한다. 거부한 안: core가 잡는 것. 봇 회차가 짚은 대로 core가 `import yaml`을 하게 된다(원칙 IV의 "코어는 바깥을 모른다"와 아래 import 경계). 거부한 안: sdk에 새 예외 클래스(`SkillError`)를 두는 것. 어댑터의 `except` 집합이 매니페스트와 달라지고, `TOMLDecodeError`가 `ValueError`인 것과 같은 모양이 이미 있다.

### 포트 `read_skill`의 시그니처와 돌려주는 값의 자리 (명세가 정했다. 봇 회차의 보류 하나)

- `PluginSource.read_skill(name: PluginName) -> Skill | None`이다. 동기다(재개의 첫 걸음에 `await`가 없다는 불변식이 준비 단계에 걸린다. `.claude/rules/core.md`의 재개 항목). 돌려주는 값은 sdk의 `Skill`이다. 원문을 돌려주고 core가 파싱하는 안은 core가 `import yaml`을 하게 되어 봇 회차가 짚은 대로 두지 않는다.
- 부재는 값으로 말한다. 그 이름의 스킬 폴더에 스킬 문서 파일이 없으면 `None`이다(폴더 자체가 없어도 `None`. 매니페스트의 부재는 `read_manifest`가 따로 말한다). 손상은 `PluginError`다 — 파일을 여는 것부터(OSError, UTF-8 아님) 가르기, YAML, 두 칸의 검증까지 전부이고, 머리말의 `name`이 인자의 이름과 다른 것도 `PluginError`다(아래 "읽지 못한 문구"). 어댑터는 경로를 인자의 `PluginName`으로만 조립하고 머리말의 값으로 경로를 만들지 않는다(둘째 세션의 PR 직전 보안 리뷰 메모. 패턴이 `..`과 구분자를 막는 것은 `sdk/ids.py`의 주석).
- 종류 인자는 받지 않는다. 스킬 문서는 스킬 종류에만 있다.
- 거부한 안: `read_skill`이 매니페스트까지 함께 돌려주는 것. `read_manifest`가 이미 그 일을 하고, 부재의 두 갈래(매니페스트 없음, 스킬 문서 없음)를 한 값으로 말할 수 없다. 거부한 안: 없는 스킬 문서를 어댑터가 `PluginError`로 내는 것. 단건 읽기의 약속(부재는 값)과 ADR 0012의 2026-11-03 이력에 어긋난다.

### 읽지 못한 문구와 이름 어긋남 문구 (명세가 정했다. 쟀다)

- 어댑터가 스킬 문서를 읽지 못한 `PluginError`의 문구는 `스킬 문서를 읽을 수 없다: <경로>` 한 줄 뒤에 이유 한 줄이다. 이유는 매니페스트와 같은 길(`adapters/filesystem.py`의 `_describe`)로 만든다 — pydantic `ValidationError`는 입력·문맥·URL 없이 `<type> (<칸>): <msg>`이고(쟀다. `str`에는 값이 실리고 거른 문구에는 없다), 그 밖의 예외는 `str` 그대로다. 그 밖의 예외는 `parse_skill`의 고정 문구 `ValueError`(위 두 절. YAML 읽기의 모든 예외가 거기서 바뀐다)와 파일을 여는 `OSError`·`UnicodeDecodeError`(경로와 바이트 위치)뿐이라 머리말의 값이 실리지 않는다. 이 문구를 내는 출구(관리 상세 500, 실행 전 500, 서버 기록)는 `_describe`가 만든 `PluginError`를 그대로 쓰고 예외의 `str`을 따로 싣지 않는다(`.claude/rules/adapters.md`).
- 머리말의 `name`이 인자의 이름과 다르면 `디렉터리와 머리말의 name이 어긋난다: <경로> 는 <이름> 자리인데 <머리말의 name>`이다(매니페스트의 `디렉터리와 name이 어긋난다` 문구와 같은 꼴). 머리말의 `name`을 싣는 것은 그것이 플러그인 이름 패턴을 지난 값뿐이기 때문이다(ADR 0041).
- 깨진 스킬 문서가 `PluginError`로 서고 문구에 원문 조각이 없음을 고정하는 시험 하나(둘째 세션의 PR 직전 보안 리뷰가 명세에 더한 것)는 어댑터 자리다. 닫히지 않은 따옴표 뒤에 비밀처럼 보이는 값을 둔 스킬 문서를 실제 폴더에 쓰고, `read_skill`이 `PluginError`이며 문구에 경로와 오류 종류(`ScannerError`)와 줄이 있고 그 값이 없음을 단언한다. 선례는 `tests/adapters/test_filesystem.py`의 `test_칸에_잘못_적은_값은_매니페스트를_읽지_못한_문구에_다시_나오지_않는다`다. sdk 자리에는 `parse_skill`의 `ValueError` 문구에 같은 값이 없음을 단언하는 사례가 선다(닫히지 않은 따옴표와 `!!int` 태그의 둘. 뒤의 것은 `YAMLError`가 아닌 예외의 길이다).
- 거부한 안: 문구에 `problem` 문구("found unexpected end of stream" 등)를 더 싣는 것. 운영자에게 더 친절하지만 그 문구가 원문의 글자를 들 수 있어(위 절) 종류와 줄·칸으로 충분하다고 본다.

### 매니페스트 `skills`의 중복 (명세가 정했다)

- `skills`에 같은 이름이 두 번 있으면 매니페스트를 읽는 단계에서 거부한다(sdk의 검증자. 문구는 `agent 플러그인의 skills 에 같은 이름이 두 번 있다: <이름>`). 컨텍스트의 열이 "매니페스트의 순서 그대로"라는 규칙에 "같은 이름은 한 번"이라는 둘째 규칙을 두지 않기 위해서다.
- `mcp` 목록의 중복은 지금 core가 이름별 사전으로 모아 조용히 하나가 된다(`core/run.py`의 `_resolve_servers`. 코드를 읽었다). 그 동작은 이 명세가 건드리지 않는다.
- 거부한 안: `mcp`처럼 조용히 하나로 합치는 것. 오타가 숨고, 컨텍스트의 열이 매니페스트의 순서와 달라진다. 거부한 안: 두 번 읽어 두 번 넣는 것. 같은 본문이 모델에 두 번 간다.

### 실행 준비의 순서와 없음의 문구 (명세가 정했다)

- 지금의 순서 부재 → 깨짐(mcp 없음 → 마스킹과 승인의 충돌 → 모델 없음·읽히지 않음) → 운영자 파일의 손상 → 꺼짐(에이전트 → mcp → 모델) → 진입점 import → 모델 만들기(`core/run.py`의 `_prepare`. 코드를 읽었다)가 이렇게 된다. **부재 → 깨짐(mcp 없음 → 마스킹과 승인의 충돌 → 모델 없음·읽히지 않음 → 스킬) → 운영자 파일의 손상 → 꺼짐(에이전트 → mcp → 모델 → 스킬) → 진입점 import → 모델 만들기.** 스킬의 깨짐은 `skills`에 적힌 순서대로 이름마다 매니페스트 없음·읽히지 않음 → 스킬 문서 없음·읽히지 않음·이름 어긋남이고, 한 이름을 끝낸 뒤 다음 이름이다. 깨짐과 꺼짐이 같은 순서(에이전트 → mcp → 모델 → 스킬) 하나인 것은 ADR 0041 그대로다.
- 없음의 문구는 mcp와 같은 꼴이다. 매니페스트가 없으면 `에이전트 <이름> 이 지정한 skill 플러그인이 없다: <스킬>`, 매니페스트는 있는데 스킬 문서가 없으면(`read_skill`이 `None`) `에이전트 <이름> 이 지정한 skill 플러그인에 SKILL.md 가 없다: <스킬>`이다(둘 다 이 명세가 정한 새 문구다). 읽히지 않음은 어댑터의 `PluginError` 그대로다. 문구가 싣는 것은 패턴을 지난 플러그인 이름뿐이다.
- 스킬 매니페스트와 스킬 문서는 준비 한 번에 이름마다 한 번 읽는다. 꺼진 집합도 지금처럼 한 번 읽어 넷을 본다. 재개는 기록된 에이전트의 매니페스트를 지금 디스크에서 읽어 같은 순서를 지난다.
- 거부한 안: 스킬 문서 읽기를 꺼짐 뒤로 미루는 것(꺼진 스킬의 깨진 문서는 보지 않게). 깨짐이 꺼짐보다 먼저라는 규칙에 예외가 하나 더 생기고(지금 예외는 진입점 import 하나), ADR 0041이 스킬 문서의 거부를 깨짐에 두었다. 거부한 안: 스킬의 깨짐을 mcp 앞에 두는 것. 꺼짐의 순서와 어긋나 규칙이 둘이 된다(ADR 0040의 모델과 같은 논증).

### 컨텍스트 멤버의 타입과 신뢰 경계 문구 (명세가 정했다)

- `AgentContext`의 멤버는 읽기 전용 속성 `skills`이고 타입은 `tuple[Skill, ...]`이다(`Conversation.exchanges`가 `tuple[Exchange, ...]`인 것과 같다). core의 컨텍스트가 준비 결과에서 받아 들고, sdk 시험·어댑터 시험·core 시험의 가짜 컨텍스트가 같은 이름의 속성을 둔다 — `conversation`을 더할 때와 같은 자리들이다(`tests/sdk/test_agent.py`의 `FakeContext` 등).
- sdk의 독스트링(`AgentContext`와 `Skill`의 모듈)이 신뢰 경계를 `conversation`의 반대편으로 적는다. 스킬 본문은 운영자가 플러그인 폴더에 둔 파일이라 에이전트 코드와 같은 신뢰 수준이고, 에이전트는 그것을 지시로 엮어도 된다. 런타임은 `llm()`에 붙이지 않는다. `.claude/rules/sdk.md`의 "스킬은 절차 지식이다" 줄이 이 멤버를 적는 줄로 바뀐다.
- 거부한 안: `Sequence[Skill]`로 선언하는 것. 불변이 타입에 드러나지 않고, sdk의 다른 불변 값이 든 열(`Conversation.exchanges`)이 `tuple`이다.

### 예시 스킬 (사용자가 골랐다. 엮는 모양은 명세가 정했다)

- 저장소의 예시 스킬은 `answer-format`이다. `plugins/skills/answer-format/plugin.toml`은 공통 넷(`version = "0.1.0"`)이고, `SKILL.md`의 머리말은 `name: answer-format`과 한 줄의 `description`(계산 답을 적는 형식. 최종 답만 내는 에이전트가 답을 쓸 때 쓴다), 본문은 세 문장이다 — 답은 값 하나만 쓴다, 단위·설명·계산 과정을 붙이지 않는다, 계산할 수 없으면 왜 할 수 없는지 한 문장으로 답한다. 정확한 글은 티켓이 그 파일에 쓰고, `FRESH_PROMPT`의 시험이 그 글을 고정한다.
- `plugins/agents/calc/plugin.toml`에 `skills = ["answer-format"]`이 든다. calc 코드는 스킬마다 `지침 <이름>: <본문>` 블록 하나를 머리 문장("계산 요청이다. …") 뒤, 앞 대화 블록 앞에 두고, 블록 사이와 블록 뒤는 빈 줄 하나다. 본문은 앞뒤 공백을 다듬어 엮는다(다듬는 것이 에이전트의 몫이라는 위 "떼는 규칙"). 스킬이 없으면 블록이 없어 그 전과 같은 모양이다. 앞 대화 블록이 데이터라고 밝히는 것과 달리 스킬 블록은 지시다(위 신뢰 경계).
- 그래서 `tests/test_calc_plugin.py`의 `FRESH_PROMPT`는 머리 문장 뒤에 그 블록이 든 글로 바뀌고, 실제 모델 시험(`-m llm`. `tests/test_main.py`의 calc 사례)과 위젯의 실제 모델 e2e(`-m llm_widget`. `copyRepoPlugins`가 저장소 `plugins/`를 통째로 옮긴다)가 스킬 경로를 끝까지 지난다. `tests/test_main.py`의 `_copy_repo_plugins`(calc와 `everything`과 기본 모델만 복사한다. 코드를 읽었다)는 calc가 고른 스킬 폴더도 복사한다.
- 사용자가 고르지 않은 갈래: 한국어 계산 요청을 연산으로 옮기는 규칙의 스킬(`korean-arithmetic`). 둘 다 calc의 답을 바꾸지 않으려는 지식이고, 고른 것은 본문이 짧고 "최종 답만 짧게 답한다"는 머리 문장과 같은 방향이라 모델이 다른 답을 내지 않을 것으로 본다(돌려 보지 않았다, 어림. 실제 모델 시험이 묶음 D에서 잰다). 고르지 않은 것은 규칙이 모델의 답을 바꿀 여지가 있어 그 시험을 다시 봐야 할 수 있었다(어림).
- 거부한 안: 스킬 블록을 앞 대화 블록 뒤에 두는 것. 지시가 데이터 뒤에 서면 데이터 안의 글이 지시로 읽힐 틈이 커진다. 거부한 안: 예시 스킬을 둘 두는 것. 하나로 경로가 끝까지 돌고, 관리 목록에 느는 행이 하나다.

### YAML의 import 경계 (명세가 정했다)

- `import yaml`은 sdk의 `parse_skill`이 사는 모듈만 한다. 이것을 import-linter 계약으로 고정한다 — sdk 밖의 모든 층(`agent_os.core`, `agent_os.adapters`, `agent_os.channel`, `agent_os.admin`, `agent_os.http`, `agent_os.server`, `agent_os.main`)이 `yaml`을 import하지 못하는 `forbidden` 계약 하나다(`pyproject.toml`의 `[tool.importlinter]`. 선례는 "core knows no provider"). sdk가 `yaml`을 import해도 되는 것은 지금 계약("sdk knows no engine")이 막는 넷에 `yaml`이 없기 때문이다(ADR 0041).
- `pyproject.toml`의 직접 의존성에 `pyyaml>=6.0`이 들고, `docs/constitution/tech.md`의 런타임 의존성 줄에 "sdk: `pyyaml`(스킬 문서의 머리말, ADR 0041)"이 든다. 설치된 판은 6.0.3이고(쟀다) `langchain-core`의 전이 의존성과 같은 판이라 락의 패키지는 늘지 않는다(ADR 0041).
- 거부한 안: 계약 없이 규칙 문서에만 적는 것. 린터가 잡을 수 있는 것은 도구 설정에 둔다(`CLAUDE.md`의 교정 루프).

### 고칠 자리의 묶음 (명세가 정했다)

ADR 0041의 "구현 티켓이 고칠 곳"을 넷으로 묶는다. 묶음마다 혼자 초록이어야 하고(모든 검증 명령), 의존은 A → B, A → C, B → D다. B와 C는 나란히 돌 수 있다. 티켓으로 쪼개는 것은 to-tickets다.

- **A 계약과 읽기.** sdk의 `Skill`·`parse_skill`과 머리말 모델(위 네 절), `AgentContext.skills`(core의 컨텍스트는 빈 열을 들고 가짜 컨텍스트들이 속성을 둔다), 매니페스트의 `skills`와 중복 거부, `PluginSource.read_skill`과 어댑터의 구현(문구 둘), `openapi.json`과 생성 타입과 스토리·테스트의 리터럴(`skills: []`), import-linter 계약, `pyproject.toml`의 `pyyaml`과 `tech.md`, `.claude/rules/sdk.md`의 종류별 칸 불릿과 스킬 줄, `.claude/rules/core.md`의 포트 표 `PluginSource` 행, `src/agent_os/sdk/manifest.py`의 `PluginKind` 위 주석. A가 선 뒤 B 전까지는 매니페스트가 `skills`를 받지만 런타임이 읽지 않는 과도 상태이고, 저장소의 매니페스트는 D까지 `skills`를 적지 않는다.
- **B 런타임.** 준비 단계의 스킬 판정(위 "실행 준비의 순서")과 컨텍스트에 실제 값 싣기, 꺼짐 판정에 스킬, 옛 셈("mcp와 모델")을 적은 독스트링·주석 셋(`core/run.py`의 `_prepare`, `core/ports.py`의 `Disabled`, `channel/http/end_user.py`의 500 주석), `.claude/rules/core.md`의 준비 순서 문장과 `Disabled` 문장, `.claude/rules/http.md`의 최종 사용자 면 500 갈래 목록, `README.md`의 `disabled.toml` 줄과 트리.
- **C 관리 화면.** `PluginList.tsx`의 로더 없는 종류 집합과 안내 줄 걷기와 그것을 기대하는 스토리·vitest·e2e(`PluginList.stories.tsx`, `HomePage.test.tsx`의 `NO_EFFECT`, `web/apps/admin/e2e/admin-token.e2e.ts`), `RunDecision.tsx`의 `disabledFor`가 `manifest.skills`를 `스킬 <이름>` 꼴로 세는 것과 그 시험.
- **D 예시.** `plugins/skills/answer-format/`, calc의 매니페스트와 코드, `FRESH_PROMPT`, `_copy_repo_plugins`, 실제 모델 호출의 단언(아래).

### 실제 모델 호출 하나 (명세가 정했다)

더하는 하나는 새 시험이 아니라 `tests/test_main.py`의 calc 시험(저장소 `plugins/`를 복사해 실제 CLI로 calc가 답하고 트레이스에 모델 호출이 남는 것을 보는 `-m llm` 시험)에 드는 단언이다. 트레이스의 첫 `llm_called.prompt`에 저장소의 `plugins/skills/answer-format/SKILL.md` 본문(시험이 그 파일을 읽어 다듬은 글)이 들어 있는지 본다. 스킬 문서가 파일에서 읽혀 에이전트가 엮은 글로 모델에 갔다는 바깥 증거다. 이 단언은 런타임 전의 코드에서는 초록일 수 없다 — 그 코드의 calc는 `ctx.skills`가 없어 블록을 엮지 못한다. 나머지 `-m llm` 시험은 수가 늘지 않고, 위젯의 실제 모델 e2e는 스택이 저장소 플러그인을 통째로 복사하므로 그대로다.

## Testing Decisions

### 이음매 (사용자가 골랐다)

주 이음매는 core의 `run()`·`resume()`에 가짜 플러그인 소스를 꽂는 자리다(`tests/core/test_run.py`의 `_run`과 `FakePlugins`). 가짜가 스킬 매니페스트의 이름 집합과 스킬 문서를 이름별로 따로 들어 "매니페스트는 있는데 스킬 문서가 없다"를 흉내 내고, 읽은 횟수를 센다. 준비의 순서(깨짐 넷의 자리, 꺼짐 넷의 자리), 이름마다 한 번 읽는 것, 컨텍스트의 열이 매니페스트 순서인 것, 꺼진 스킬의 `Disabled`, 없는 스킬·없는 스킬 문서의 `PluginError`와 문구, 재개가 지금 디스크의 문서를 쓰는 것(멈춘 사이 가짜의 본문을 바꾸고 재개 대조 어긋남이 나는 것과, 첫 모델 호출 전에 멈춘 실행에서는 바뀐 본문이 들어가는 것)을 여기서 잰다. 바깥 경계는 기존 시험 자리에 얇은 시험 하나씩이 맡고(아래), 더하는 실제 모델 호출은 위의 단언 하나다. 예외 하나는 sdk의 `parse_skill`과 머리말 모델이다 — 새 규칙(가르기, 두 칸, 예외 바꾸기)이 사는 자리라 얇은 하나가 아니라 프로브 두 파일의 사례 전부를 같은 입력으로 시험한다(명세가 잰 것과 구현이 어긋나지 않게. 사용자 이야기 24). 사용자가 고른 답은 sdk의 읽는 함수도 "얇게 하나씩"에 넣었는데, 이 명세가 그 함수만 이렇게 넓혔다. 고르지 않은 둘(실제 파일시스템 어댑터를 주 이음매로 쓰기, HTTP 앱에 요청 넣기)은 일지 2026-11-03-03에 있다.

### 좋은 시험

- 바깥 행동만 단언한다. 컨텍스트의 값(판정 에이전트가 `ctx.skills`를 출력에 옮긴다), 예외의 타입과 문구, 상태 코드와 봉투, 가짜가 기록한 호출과 그 인자. 준비의 순서는 두 결함을 함께 심어 어느 오류가 먼저 나오는지로 잰다(선례는 `tests/core/test_run.py`의 `test_준비의_순서는_부재_깨짐_꺼짐_진입점_모델_만들기다`).
- 실패를 기대하는 시험은 실패의 까닭(표지)을 단언한다(`CODING_STANDARDS.md`). 머리말 거부는 프로브 README의 표지(`string_type` 등)를 그대로 쓰고, 문구에 값이 없는 것은 값이 있어야 할 양성 대조(`str(error)`)와 함께 본다.
- 환경이 없으면 skip이 아니라 실패다(`.claude/rules/tests.md`). `-m llm`은 `ANTHROPIC_API_KEY`가 없으면 실패한다(지금과 같다).
- 빨강을 먼저 본다(헌법 원칙 II). A의 첫 빨강은 리터럴이 타입 검사에서 깨지는 것과 `openapi.json` 최신성 시험과 import-linter 계약(어댑터가 `yaml`을 import해 보면 빨강)이고, B의 첫 빨강은 가짜의 스킬 문서 읽기가 한 번도 불리지 않는 것, D의 첫 빨강은 `FRESH_PROMPT`다.

### 시험할 모듈과 선례

- sdk 스킬 값과 읽는 함수: 프로브 두 파일의 사례 전부(가르기 다섯과 거부 다섯, 값 안의 `---`, 빈 머리말, 머리말 안 `---` 줄 세 자리와 그 대조 셋, 받는 셋과 거부 열둘, 명시적 태그 넷, 문구에 값 없음 둘)를 같은 입력으로. `name`이 `PluginName`인 것, `Skill`이 불변인 것. 선례 `tests/sdk/test_manifest.py`(받기·거부의 매개변수 시험, `tests/sdk/test_conversation.py`의 값 시험).
- sdk 매니페스트: `skills`의 받기·기본값·종류별 거부·패턴·중복 거부, 직렬화 스키마의 `required`. 선례 `tests/sdk/test_manifest.py`의 `model` 칸 시험 넷과 `test_직렬화_스키마에서_새_다섯_칸은_모두_required이고_null을_허락한다`.
- 어댑터: 실제 폴더에서 `read_skill`의 부재(`None`), 읽힘, 이름 어긋남, 깨진 머리말의 `PluginError`와 문구에 값 없음(위 "읽지 못한 문구"의 시험 하나), UTF-8 아님, 경로가 인자의 이름으로만 조립되는 것. 선례 `tests/adapters/test_filesystem.py`의 `test_없는_플러그인은_None이다`, `test_디렉터리와_name이_어긋나면_에러다`, `test_칸에_잘못_적은_값은_매니페스트를_읽지_못한_문구에_다시_나오지_않는다`.
- core 준비: 위 이음매. 선례 `tests/core/test_run.py`의 "꺼진 플러그인" 절과 모델의 여섯(`test_없는_모델은_실행_전에_PluginError_이고_트레이스가_없다`부터 `test_준비의_순서는_부재_깨짐_꺼짐_진입점_모델_만들기다`까지).
- HTTP 두 면: 운영자 채널에서 없는 스킬·없는 스킬 문서의 500(원문)과 꺼진 스킬의 409(종류·이름·에이전트), 최종 사용자 면에서 고정 문구 500과 409, `GET /plugins`가 에이전트 행을 `skills`와 함께 내는 것. 선례 `tests/test_server.py`의 `test_core_의_구성_오류는_500이고_code_가_internal_error_다`·`test_core_의_꺼짐은_409이고_code_가_conflict_다`, `tests/channel/http/test_end_user.py`의 `test_꺼진_모델은_운영자_면은_이름을_들고_최종_사용자_면은_고정_문구의_409다`·`test_없는_모델은_운영자_면은_500_원문이고_최종_사용자_면은_고정_문구의_500이다`.
- 관리 화면: 스킬 행에 안내 줄이 없는 것(vitest·스토리·e2e), 결정 칸이 꺼진 스킬을 `스킬 <이름>`으로 알리는 것, 리터럴의 새 칸. 선례 `web/apps/admin/components/pages/HomePage.test.tsx`의 안내 줄 시험(`NO_EFFECT`)과 `RunDecision`의 꺼진 mcp·모델 미리 알림 시험.
- calc: `FRESH_PROMPT`(블록이 든 새 글), 스킬이 둘이면 매니페스트 순서로 블록 둘, 앞 대화 블록과의 자리. 선례 `tests/test_calc_plugin.py`의 세 시험.
- 저장소 상태: `plugins/skills/answer-format/`을 실제 어댑터로 읽어 `Skill`이 되는 것(저장소의 플러그인을 실제 어댑터로 읽는 선례는 `tests/test_calc_plugin.py`).
- 경계: import-linter 계약은 `uv run lint-imports`가 판정한다. 플러그인 경계 시험(`tests/test_plugins_boundary.py`)은 `*.py`만 읽어 예시 스킬 폴더에 닿지 않는다(코드를 읽었다).

## Out of Scope

- ADR 0041의 "이번 범위 밖" 그대로다. 표준의 선택 칸(`allowed-tools` 포함), 부속 파일(`scripts/`, `references/`, `assets/`), 본문 크기 상한, 단계적 공개, 관리 API의 스킬 설명. 여기에 이 명세가 더한 것 셋 — 표준의 이름 규칙 가운데 플러그인 이름 패턴이 보지 않는 것(끝 하이픈 금지, 연속 하이픈 금지. 64자 이름은 패턴이 63자까지라 이미 받지 않는다, ADR 0041), 표준과 참조 구현이 허락하는 유니코드 소문자 이름(패턴은 ASCII만 받아 한글·전각 이름의 스킬 폴더는 들어오지 못한다. 사용자 이야기 8의 "그대로 들이기"는 ASCII 이름에서만 성립한다), 설명의 1024자 상한. 받는 기능은 없고 `.scratch/plan.md`의 다른 행에 적지 않는다(받는 쪽을 이름으로 적을 기능이 아직 없다).
- `mcp` 목록의 중복을 조용히 하나로 합치는 지금의 동작(위 "매니페스트 `skills`의 중복").
- 런타임의 시스템 메시지 주입은 미룬 것이 아니라 거부한 안이다(ADR 0041).

## Further Notes

- 프로브 셋의 결과는 `.scratch/skill-plugin/probes/README.md`다. `frontmatter_split.py`의 `split_front_matter`와 `frontmatter_values.py`의 `Frontmatter`가 이 명세의 규칙과 모델을 코드로 적은 것이고, 티켓이 sdk에 두는 함수와 모델은 그 사례로 시험한다. 프로브를 import하지는 않는다(프로브는 저장소 코드가 아니다).
- 머리말이 깨진 스킬 문서를 관리 목록이 어떻게 보이는지는 바뀌지 않는다. 목록은 매니페스트만 읽으므로 그 폴더는 보통 행이고, 깨짐은 그것을 고른 에이전트의 실행 전 500과 서버 기록으로 드러난다(ADR 0041 "포트에 메서드 하나가 는다"). 관리 상세는 매니페스트 JSON 그대로다.
- 멈춘 사이 스킬 본문을 고친 실행의 재개가 대조 어긋남으로 끝나는 것과 첫 모델 호출 전에 멈춘 실행에서는 그렇지 않은 것은 ADR 0041이 받아들인 한계이고, 이 명세는 그 두 갈래를 주 이음매의 시험으로 고정한다.
