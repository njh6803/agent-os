# 09: 관리 화면의 로그인과 갱신 규칙

**What to build:** 운영자가 관리 화면의 아무 주소나 열면, 로그인하지 않았을 때 `/login?next=<그 주소>`로 간다. 이름과 비밀번호를 넣고 로그인하면 보던 화면으로 돌아오고, 옆 탐색의 맨 아래에 계정 이름과 단계가 선다. 그 자리를 누르면 메뉴가 열리고 "로그아웃"을 누르면 `/login?notice=logged-out`에 "로그아웃했다"가 선다. 짧은 JWT(로그인할 때 받는 5분짜리 출입증 쿠키)가 만료돼도 화면이 저절로 갱신(갱신용 번호 쿠키로 새 출입증을 받는 일)해 운영자는 알아채지 못하고, 갱신까지 실패하면 `/login?next=<지금 주소>&notice=expired`에 "로그인이 끝났다. 다시 로그인한다"가 선다. 계정이 하나도 없는 서버의 로그인 화면은 입력 칸 대신 첫 계정을 만드는 명령 두 꼴을 보인다. 설정 화면에서 두 토큰의 입력 칸이 사라지고 테마 고르기만 남는다.

이 티켓으로 관리 화면은 공유 토큰(지금 설정 화면에 넣는, 모두가 함께 쓰는 비밀 글 둘)을 쓰지 않는다. 서버는 13까지 공유 토큰도 받으므로, 위젯과 위젯 테스트 페이지의 e2e 하네스(시험이 서버를 띄우고 준비하는 코드)는 그대로 돈다.

근거는 명세 `.scratch/admin-login/spec.md`의 "관리 화면의 페이지와 주소"(표의 `/login`과 그 밖의 화면, "next", "로그인 화면", "로그인 화면의 알림", "https가 아닌 주소", "탐색", "로그아웃", "설정 화면", "토큰이 있던 두 자리를 받는 것"), "화면이 갱신을 부르는 규칙", "공유 토큰을 없애는 자리"의 "관리 화면", "계약과 생성물"의 "생성 클라이언트 패키지", Testing Decisions의 "화면의 페이지 시험", "공유 토큰을 걷는 것", "관리 화면 e2e", "사진 비교"다. 측정은 `.scratch/admin-login/probes/swr_poll/`(결과 3, 실패에서 주기 읽기가 쉬는 것)과 `cookie_relay/`(결과 3)이다. 그린 화면은 `.scratch/admin-login/design/`의 로그인 화면이다. 결정은 ADR 0062, ADR 0021과 ADR 0026의 이력(명세가 받는 자리를 적었다)이다. 이 티켓의 "명세 검토"는 일지 `docs/journal/2026-11-25-1007-admin-login-tickets.md`의 "명세 검토(spec-reviewer)" 절을 가리킨다.

### 생성 클라이언트

- [ ] 생성 클라이언트 패키지(계약에서 지어 낸 타입과 요청 함수를 담은 `web/packages/api-client`)에 토큰을 받지 않는 운영자 클라이언트 하나를 더한다. 최종 사용자 경로를 뺀 운영자 경로 전부를 안다. 관리 화면을 그 클라이언트로 옮긴다. 토큰을 받는 옛 클라이언트 둘(`createAdminClient(adminToken)`, `createChannelClient(channelToken)`)은 e2e 하네스가 아직 쓰므로 남기고 13이 걷는다
- [ ] 경로 목록을 고정한 타입 시험(`clients.test-d.ts`)에 새 클라이언트를 더한다

### 로그인 화면

- [ ] `/login`은 뜰 때 첫 계정 확인을 읽고, 참이면 입력 칸 대신 `agent-os operator system-admin <계정 이름>`과 `docker compose exec serve agent-os operator system-admin <계정 이름>`을 보인다
- [ ] 로그인이 401이면 입력 칸 위에 "로그인하지 못했다"가 남고 비밀번호 칸만 비운다. 로그인한 채 로그인 화면을 열면 `next`나 `/`로 보낸다. 다만 `notice=password-set`이 붙은 주소는 로그인한 채여도 보내지 않고 로그인 화면을 그대로 보인다(로그인한 브라우저에서 다른 계정의 링크로 비밀번호를 정한 끝에 오는 주소라, 보내면 안내가 사라지고 새 계정으로 로그인하지 못한다)
- [ ] `next`는 지금 화면의 출처를 기준으로 URL로 풀어 출처가 같을 때만 받고, 로그인 화면과 비밀번호 정하기 화면의 주소는 풀린 주소의 경로로 가려 받지 않는다. 이동은 풀린 주소의 `href`(출처까지 든 절대 주소)로 하고 경로만 떼어 쓰지 않는다. `https://admin.example:8443//evil.test/x`는 출처가 같지만 경로만 떼면 `//evil.test/x`가 되어 브라우저가 다른 사이트로 보내기 때문이다. 그 밖이면 `/`로 간다. 앞 글자만 보는 검사(`/`로 시작하고 `//`나 `/\`로 시작하지 않는다)는 쓰지 않는다. URL로 풀면 탭과 줄바꿈이 지워져 `/<탭>/evil.test`가 그 검사를 지나 다른 사이트로 풀리기 때문이다(명세 "관리 화면의 페이지와 주소"의 "`next`")
- [ ] 알림 `notice`의 값 셋(`logged-out`, `expired`, `password-set`)과 문구를 명세대로 보인다. 모르는 값은 무시한다
- [ ] 주소가 `http:`이고 호스트가 `localhost`도 `127.0.0.1`도 `[::1]`도 아니면 "이 주소는 https가 아니라 로그인할 수 없다. https 주소로 연다"를 보인다. `[::1]`이 `__Host-` 쿠키를 받는지는 재지 않은 어림이므로, `.scratch/admin-login/probes/cookie_relay/`에 `[::1]` 갈래를 더해 재고 README에 결과를 적는다. 받지 않으면 이 조건에서 `[::1]`을 빼고 명세를 고친다

### 로그인이 필요한 화면

- [ ] 로그인이 필요한 화면은 그리기 전에 `GET /auth/me`를 읽고, 갱신까지 실패하면 `/login?next=<지금 주소>`로 보낸다
- [ ] pages(서버 데이터를 읽는 화면 층)가 "지금 누구인지"의 답(계정 이름, 단계, `token_minutes`, `run_timeout_seconds`)을 읽어 organisms(받은 값으로 그리기만 하는 부품 층)에 props로 넘긴다. organisms와 templates가 SWR 훅과 스토어와 생성 클라이언트를 가져오지 않는다는 층 정책은 그대로다
- [ ] 탐색: 폭 768px 이상에서는 옆 탐색의 맨 아래에 계정 자리(이름과 단계)가 서고 누르면 위로 메뉴가 열린다. 768px 미만에서는 위 막대가 두 줄이고 첫 줄에 계정 버튼이 선다. 메뉴의 항목은 이 티켓에서 "로그아웃" 하나이고 "내 비밀번호 바꾸기"는 12가 더한다. 아이콘은 08의 `chevrons-up-down`과 `log-out`이다
- [ ] 로그아웃: 로그아웃 요청도 갱신 규칙을 지난다. 204거나 갱신이 401이면 `/login?notice=logged-out`으로 보낸다. 쿠키를 지우는 응답을 받지 못했으면(네트워크가 끊겼거나 500) 로그인 화면으로 가지 않고 메뉴 자리에 "로그아웃하지 못했다. 다시 누른다"를 보인다

### 갱신 규칙

- [ ] 화면의 모든 요청이 지나는 공통 층 하나에 명세 "화면이 갱신을 부르는 규칙"을 둔다. 401이면 갱신 한 번과 다시 보내기 한 번, 같은 탭의 갱신은 하나(겹친 401은 도는 갱신을 함께 기다린다), 갱신이 401이면 `notice=expired`로 로그인 화면이다. 다시 보낸 요청이 또 401이면 갱신을 다시 부르지 않고 로그인 화면으로 보낸다
- [ ] 로그인, 갱신, 첫 계정 확인, 링크로 비밀번호 정하기는 규칙을 지나지 않는다. 로그아웃은 지난다
- [ ] 401에서 갱신하고 다시 보내는 일은 SWR(관리 화면이 서버 데이터를 읽고 들고 있는 라이브러리)이 결과를 받기 전에 요청 함수 안에서 끝낸다. SWR은 읽기가 실패하면 실패가 걷힐 때까지 주기 읽기를 쉬기 때문이다(`swr_poll` 결과 3). 플러그인 화면의 접속 확인(30초마다)이 짧은 JWT가 끝날 때마다 멈추지 않는다. 스트림이 열린 동안의 갱신은 11이 한다

### 토큰을 걷는 자리

- [ ] 설정 화면의 두 토큰 입력 칸과 지우기 버튼, 토큰 스토어(`web/apps/admin/stores/tokens.ts`), 생성 클라이언트가 토큰 머리를 싣는 관리 화면의 자리를 없앤다. 그 스토어를 가리키던 판정자 사례(층 정책을 지키는 린트 규칙이 막아야 할 예로 든 import, `web/eslint.config.mjs`와 그 시험)와 타입 import도 걷는다
- [ ] 관리 화면은 뜰 때 `sessionStorage`의 `agent-os-admin-tokens`를 지운다
- [ ] 결정 자리(`RunDecision`)에서 채널 토큰이 없을 때 서던 갈래를 걷는다. 결정 버튼은 권한 `decide`를 가진 계정(두 단계 모두)에게 선다. `.claude/rules/web-admin.md`의 결정 자리 줄에서 채널 토큰을 말하는 부분을 고친다. 규칙 파일을 고치기 전에 Skill 도구로 `writing-for-agents`를 부른다

### 시험

- [ ] 페이지 시험(vitest와 jsdom): 갱신 규칙(401에서 갱신 하나와 다시 보내기 하나, 겹친 401이 갱신 하나를 함께 기다리는 것, 갱신이 401이면 `notice=expired`, 다시 보낸 요청이 또 401이면 갱신을 다시 부르지 않고 로그인 화면으로 가는 것), 로그아웃의 세 갈래(204, 갱신의 401, 쿠키를 지우는 응답 없음), `next`의 검증(`//evil.test`, `/<탭>/evil.test`, `/<줄바꿈>/evil.test`, `https://evil.test/`, 같은 출처의 `https://admin.example:8443//evil.test/x`는 받되 이동하는 곳이 그 절대 주소 그대로라 다른 사이트로 나가지 않는 것, 로그인 화면의 주소는 `/`로 가고 `/chat?x=1`은 받는 것), 로그인한 채 연 로그인 화면(보통 주소는 `next`나 `/`로 가고 `notice=password-set`이 붙은 주소는 가지 않는 것), https가 아닌 주소의 알림, 첫 계정 안내, 뜰 때 `agent-os-admin-tokens`를 지우는 것
- [ ] 관리 화면 e2e: 토큰을 넣던 준비를 로그인으로 바꾼다. 시험이 서버 명령으로 계정을 만든다. 먼저 Playwright의 API 요청 문맥(`request.newContext()`)이 `http://127.0.0.1:<포트>`에서 받은 `Secure` 쿠키를 담고 싣는지, 그 쿠키가 브라우저 문맥으로 넘어가는지를 재고 결과를 프로브로 남긴다. 재지 못하거나 싣지 않으면 `page.context().request`나 로그인 화면을 지나는 길로 쿠키를 받는다(명세 Testing Decisions의 "관리 화면 e2e")
- [ ] 로그인 화면을 지나 플러그인 목록이 서는 e2e 하나를 더한다
- [ ] 사진 비교: 로그인 화면(입력 칸, 실패, 첫 계정 안내, https 알림)과 계정 자리가 선 탐색을 관리 화면의 사진 정답에 더한다
