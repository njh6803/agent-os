# 06: 계정을 다루는 경로, 링크로 비밀번호 정하기, 내 비밀번호 바꾸기

**What to build:** 시스템 관리자로 로그인한 프로그램이 `POST /accounts`에 `{name}`을 보내면 관리자 단계의 운영자 계정이 만들어지고, 그 계정의 비밀번호 링크 토큰과 기한(24시간 뒤)을 201로 받는다. 그 토큰을 `POST /auth/set-password`에 새 비밀번호와 함께 보내면 비밀번호가 정해지고, 그 계정은 로그인할 수 있다. 같은 링크는 두 번 쓰이지 않는다(404 "이 링크는 더 쓸 수 없다"). 시스템 관리자는 계정 목록을 읽고, 링크를 다시 만들고, 계정을 비활성으로 바꾸거나 되돌리고, 잠금을 푼다. 관리자가 이 경로를 부르면 403 "이 계정으로는 할 수 없다"다. 로그인한 운영자는 `POST /auth/password`로 자기 비밀번호를 바꾸고, 그러면 그 계정의 다른 로그인이 모두 끊긴다. 잠긴 계정이 비밀번호를 바꾸려 하면 409 "계정이 잠겼다. 잠시 뒤에 다시 한다"다.

이 티켓은 경로 일곱을 계약에 더하므로 계정 화면을 짓는 12를 막는다.

근거는 명세 `.scratch/admin-login/spec.md`의 "경로"(표의 일곱, "이 기능은 429를 내지 않는다"), "요청을 판정하는 차례", "계정 이름과 비밀번호", "비밀번호 링크", "계정을 다루는 경로", "권한 표", "로그인을 끊는 일", "계정 저장소의 포트"의 "한 트랜잭션에 묶을 일", "로그인 기록"(이 티켓은 일곱 종류), "로그인하지 않은 요청의 응답", "계정 화면과 내 비밀번호"의 "내 비밀번호 바꾸기", Testing Decisions의 "진짜 데이터베이스가 보는 경합", "전수 검사"다. 결정은 ADR 0062 결정 "비밀번호 링크", "첫 계정", "잠금과 실패 문구", "두 단계와 권한 표", "로그인 기록"이다. 이 티켓의 "명세 검토"는 일지 `docs/journal/2026-11-25-1007-admin-login-tickets.md`의 "명세 검토(spec-reviewer)" 절을 가리킨다.

### 계약

- [x] 경로 일곱(`change_my_password`, `set_password_by_link`, `list_accounts`, `create_account`, `create_password_link`, `set_account_active`, `unlock_account`)을 명세 "경로"의 표대로 계약에 더한다. 오류 문서도 그 표의 칸 그대로다
- [x] 경로 파라미터 `{name}`은 바꾸지 않고 이름 규칙에 대며, 어기면 422다(02의 이름 함수)
- [x] 목록의 줄은 `name`, `tier`, `state`(`active`, `disabled`, `password_unset`), `locked_until`, `created_at`이다. `state`는 해시와 비활성으로 바꾼 시각 둘에서 나온다
- [x] `openapi.json`과 생성 TS 타입이 같은 커밋에 실린다

### 권한과 자격

- [x] 계정을 다루는 다섯은 권한 표에 `manage_accounts`로, `change_my_password`는 로그인만 요구하는 줄로, `set_password_by_link`는 로그인 없이 여는 줄로 더한다(명세 "권한 표"의 "전수 검사"는 최종 사용자 경로와 `/health`를 뺀 모든 오퍼레이션을 표에서 찾는다). `change_my_password`는 짧은 JWT(로그인할 때 받는 5분짜리 출입증 쿠키)로만 연다. 공유 토큰(13이 걷을 때까지 함께 받는, 모두가 함께 쓰는 비밀 글)으로 오면 401이다
- [x] 공개 경로 목록(로그인 없이 열리는 경로의 목록)에 링크로 비밀번호 정하기를 더한다(다섯)
- [x] `.claude/rules/admin.md`의 "관리 라우트는 409도 429도 내지 않는다"를 409 쪽만 고친다. 계정을 다루는 경로와 내 비밀번호 바꾸기가 409를 낸다. 429는 그대로 내지 않는다. 규칙 파일을 고치기 전에 Skill 도구로 `writing-for-agents`를 부른다

### 판정

- [x] 계정 만들기, 링크 만들기, 활성과 비활성, 잠금 풀기의 갈래를 명세 "계정을 다루는 경로"대로 짓는다. 경로의 `{name}`이 가리키는 계정(요청한 사람이 아니다)이 시스템 관리자면 링크 만들기와 활성 바꾸기가 409이고, 비활성이면 링크 만들기가 409다. 활성 바꾸기는 그 계정이 이미 그 상태면 아무것도 바꾸지 않고 204다
- [x] 비활성으로 바꾸면 그 계정의 로그인을 모두 끊고 쓰지 않은 링크를 못 쓰게 한다. 링크를 새로 만들면 그 계정의 쓰지 않은 앞 링크를 못 쓰게 한다
- [x] 링크로 비밀번호 정하기는 형식(422), 링크(쓰지 않았고 기한 안이고 그 계정이 비활성이 아니어야 한다. 아니면 404와 고정 문구), 비밀번호 규칙(422)의 차례다. 링크를 잠가 쓰고 해시를 적고 로그인을 끊는 일은 한 트랜잭션이다. 성공하면 잠금과 틀린 횟수를 지우고 로그인시키지 않는다
- [x] 내 비밀번호 바꾸기는 형식(422) → 새 비밀번호 규칙(422, `body.new_password`, 횟수에 들지 않는다) → 잠김(409) → 지금 비밀번호 견줌(로그인과 같이 짧은 트랜잭션에서 횟수를 미리 늘리고 연결 없이 견준다. 틀리면 422, `body.current_password`) → 새 해시를 트랜잭션 밖에서 짓고, 짧은 트랜잭션에서 줄을 다시 잠가 해시가 견준 것 그대로인지 본 뒤 저장한다. 해시가 바뀌었으면(견주는 사이에 링크로 비밀번호가 정해졌다) 아무것도 바꾸지 않고 422(`body.current_password`, "지금 비밀번호가 맞지 않는다")다. 성공하면 204이고 바꾼 브라우저의 로그인만 남기고 그 계정의 다른 로그인을 모두 끊는다
- [x] 로그인 기록에 풀림, 계정 만듦, 비활성으로 바꿈, 활성으로 바꿈, 링크 만듦, 링크로 비밀번호를 정함, 비밀번호 바꿈을 명세 "로그인 기록"의 표대로 남긴다. 한 일이 있을 때만 남긴다

### 시험

- [x] 경합: 같은 링크로 동시에 온 비밀번호 정하기 둘 가운데 하나만 204다
- [x] 같은 이름의 계정 만들기가 409이고, 그 응답과 서버 기록에 카나리아(기록에서 찾아낼 수 있게 일부러 심은 글자)로 심은 이름이 실리지 않는다
- [x] 관리자가 계정을 다루는 경로에 칸이 틀린 JSON 본문을 보내면 403이고, JSON으로 읽히지 않는 본문은 422다(권한이 형식보다 먼저다, 명세 "요청을 판정하는 차례")
- [x] 공유 토큰으로 계정을 다루는 다섯을 부르면 403이고(공유 토큰은 `manage_accounts`를 갖지 않는다), `change_my_password`를 부르면 401이다(명세 "공유 토큰과 쿠키를 함께 받는 기간"의 "공유 토큰의 권한"과 "로그인으로만 여는 경로")
- [x] 시스템 관리자를 가리킨 링크 만들기와 활성 바꾸기, 비활성 계정을 가리킨 링크 만들기가 409다
- [x] 비활성으로 바꾼 계정의 갱신이 401이고, 로그인이 401이며, 쓰지 않은 링크가 404다. 되돌리면 `password_unset`이던 계정은 다시 `password_unset`이다
- [x] 잠긴 계정의 내 비밀번호 바꾸기가 409이고, 틀린 지금 비밀번호가 422이며 다섯째부터 잠근다. 새 비밀번호 규칙 위반은 횟수에 들지 않는다
- [x] 지금 비밀번호를 견준 뒤 저장하기 전에 링크로 비밀번호가 정해지면 내 비밀번호 바꾸기가 422이고, 링크로 정한 해시가 남는다. 견줌과 둘째 트랜잭션 사이에 끼어드는 길은 03이 로그인의 같은 갈래에 정한 것을 쓴다
- [x] 링크로 정한 뒤 그 계정의 다른 로그인이 끊기고, 내 비밀번호를 바꾼 뒤 바꾼 쪽의 로그인은 남는다
- [x] 전수 검사: 공개 경로가 다섯이고, 로그인 기록 표 전체에 카나리아로 심은 비밀번호와 링크 토큰이 없다
