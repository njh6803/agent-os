# admin-login hash_load 프로브

admin-login 명세가 비밀번호를 다루는 자리에서 정할 것을 잰 프로브다. 해시 설정과 길은 ADR 0062 결정 "비밀번호 저장"과 "비밀번호 규칙"에서 정해져 있다. Argon2id(`argon2-cffi`), m=19456, t=2, p=1, 해시와 견줌은 `anyio.to_thread.run_sync` 로 이벤트 루프 밖의 스레드에서, 없는 계정의 로그인도 같은 계산을 한 번, 비밀번호는 8~128자에 영문 대문자·숫자·특수문자(영문자도 숫자도 아닌 글자) 각 1자 이상이다. 그 위에서 넷을 잰다. ADR 0062 Consequences "재지 못한 것"이 명세에 넘긴 셋(uvicorn 의 실제 요청 길, 여러 해시를 한꺼번에 돌릴 때의 메모리, 틀린 비밀번호의 견줌 시간)이 앞의 셋이다.

1. 로그인 K 개(1, 4, 16, 40, 100)가 한꺼번에 들어올 때 프로세스의 최고 상주 메모리와 요청 하나의 걸린 시간. AnyIO 의 기본 스레드 한도(40)와 견줌만 쓰는 작은 `anyio.CapacityLimiter`(4, 2)를 견준다. 끝난 뒤에 남는 상주와 그 까닭, 그것을 줄이는 할당기 설정 둘의 효과와 mmap 문턱 설정의 시간 값도 본다.
2. 실제 uvicorn 요청 길. 로그인 흉내 경로와 `/health` 를 가진 작은 Starlette 앱에서 로그인이 몰리는 동안 `/health` 의 걸린 시간이 얼마나 느는지. 스레드를 거치는 경로(`/thread-health`)도 본다.
3. 틀린 비밀번호, 맞는 비밀번호, 없는 계정의 가짜 저장 값 견줌이 같은 시간 분포인지(걸린 시간으로 계정이 있는지 드러나지 않는지). 함수 길과 HTTP 길.
4. 유니코드. NFKC 가 바꾸는 입력, 정규화 뒤 코드 포인트로 센 8~128 과 바이트로 센 것, argon2-cffi 의 비 ASCII 왕복, 4바이트 글자 128 자의 해시.

여기서는 결정하지 않고 본 것만 적는다. 규약은 `docs/agents/issue-tracker.md` 의 "프로브와 근거", 짓는 규칙은 `.claude/rules/probes.md` 다. 제품 코드는 만들지도 고치지도 않았다.

결과는 실행 토큰 `9f1d11` 한 번이다. 2026-11-24 17:42:47 에 시작해 18:20:59 에 끝났다(약 38분). 측정 396 회차, 측정 아님 6 회차로 종료 코드 1 이었고, 끝난 뒤 남은 컨테이너가 0 이었다(프로브가 다시 낸다, 실행 출력의 끝 줄). 측정 아님 여섯은 HTTP 길의 시간 비교 셋(판정의 조건인 5ms 대조가 서지 않았다)과 HTTP 창 셋(부하 프로세스가 끝나 창이 없었다)이다. 결론은 측정인 회차만으로 냈다. 호스트 CPU 부하(`Win32_Processor.LoadPercentage` 의 순간 값)는 컨테이너를 띄우기 직전 97%, 끝난 직후 100% 였다(프로브가 다시 낸다). 컨테이너가 쓰는 CPU 는 16 개 가운데 6 개라, 이 프로브 밖의 부하가 컸다. 무엇이 그 부하를 냈는지는 보지 않았다.

그 뒤 갈래 셋(해시만 도는 스레드 넷의 끝난 뒤 상주 `burst_pool`, 아레나 하나 설정의 견줌 한 번 시간 `alloc_arena`, 해시만 도는 스레드 넷의 uvicorn 서버 `http_pool`)을 더해 그 셋만 실행 `075196` 한 번으로 쟀다. 결과와 회차의 셈은 아래 "덧붙인 갈래(실행 `075196`)"가 원천이다. 앞의 결과는 그대로 두었다.

근거의 종류는 넷이다. 프로브가 다시 낸다(`run.py` 가 표지를 보고 센 회차와 그 출력의 표), 손으로 봤다(명령이나 원본 기록과 함께 적는다), 코드를 읽었다(파일과 판과 줄), 어림. 웹 요약은 쓰지 않았다.

요약. 수치와 표는 아래 "결과"가 원천이다.

1. 동시 해시의 최고 상주는 견줌을 맡은 일꾼 스레드의 가짓수에 19 MiB(m=19456 KiB)를 곱한 만큼이다. 기본 한도(40)는 K=40·100 에서 761 MiB, 전용 한도 4 는 76 MiB, 2 는 38 MiB 로 K 와 상관없이 묶였다(프로브가 다시 낸다).
2. 끝난 뒤에도 그만큼 남는다. 새지는 않고(같은 프로세스에서 세 번 넘겨도 같다) 일꾼 스레드가 정리된 뒤에도 남았다. 해시가 아닌 스레드 일이 기본 일꾼 묶음을 함께 쓰면 전용 한도 4·2 를 두어도 해시가 36~43 개 스레드에 돌아가며 얹혀 685~818 MiB 가 남았다(프로브가 다시 낸다). glibc 가 스레드마다 둔 아레나가 그 메모리를 들고 있다는 설명은 어림이다.
3. 할당기 설정 둘이 남는 상주를 묶었다. `GLIBC_TUNABLES=glibc.malloc.mmap_threshold=131072` 는 1 MiB 아래로 줄이고 견줌 한 번에 +18.3ms(설정 없음의 47% 쯤)를 더했다. `glibc.malloc.arena_max=1` 은 다른 스레드 일과 함께여도 0.7~19.8 MiB 로 줄였고 최고 상주는 76 MiB(한도 4)였다. 아레나 하나의 견줌 한 번 시간 값은 재지 않았다(프로브가 다시 낸다).
4. 함수 길에서 요청 하나의 걸린 시간은 한도를 CPU 수 언저리로 좁히면 줄었다(K=40, CPU 4 개: 기본 531ms, 한도 4 278ms). K 개가 다 끝나는 시간은 한도가 CPU 수보다 작으면 늘었다(CPU 4 개 K=100: 기본 1270ms, 한도 2 2321ms) (프로브가 다시 낸다).
5. uvicorn 길에서 해시를 스레드로 넘기면 이벤트 루프는 막히지 않았다(루프에서 바로 견주는 양성 대조와 견줌). CPU 4 개에서 `/health` 부하 90분위는 기본 한도 98~101ms, 전용 한도 20~28ms 였다(바탕 3~4ms). 기본 일꾼 묶음을 거치는 `/thread-health` 의 90분위는 기본 한도 245~2072ms, 전용 한도 18~259ms 였다. 서버 최고 상주는 K=100 에서 기본 819 MiB, 한도 4 153 MiB, 한도 2 115~116 MiB 였다. CPU 2 개에서는 `sleep` 대조도 `/health` 가 비슷하게 늦어 해시의 몫을 가르지 못했다(프로브가 다시 낸다).
6. 함수 길에서 틀린 비밀번호 둘과 없는 계정 둘(가짜 저장 값과 견줌, 견줌 대신 새 해시)은 맞는 비밀번호와 견줌 시간이 갈리지 않았다. 1ms 를 갈라내는 측정이다. 새 해시 쪽만 되풀이 2 에서 +0.64ms, p=0.017 로 문턱 0.01 에 가까웠다. 가짜 저장 값을 다른 매개변수로 만들면 +274ms 로 드러났다(프로브가 다시 낸다). HTTP 길은 5ms 대조가 서지 않아 판정하지 못했다(측정 아님).
7. NFKC 정규화가 글자 수를 바꿔 길이 판정이 갈린다(NFD 한글 9→7 자, U+FDFA 일곱 11→130 자). 정규화 앞의 글은 정규화한 글로 만든 저장 값을 통과하지 못했다. 4바이트 글자 128 자는 UTF-8 503 바이트, UTF-16 253 단위이고 잘리지 않고 해시됐다. 짝 없는 서로게이트는 규칙을 통과하고 해시에서 `UnicodeEncodeError` 로 끝났다(프로브가 다시 낸다).
8. (실행 `075196`) 해시를 해시만 도는 스레드 넷(`ThreadPoolExecutor(max_workers=4)` 와 `run_in_executor`)에서 돌리면 다른 스레드 일과 함께여도 견줌을 맡은 스레드가 넷이었고, 남는 상주가 셋째 번 뒤 76.7~76.9 MiB 였다. 같은 실행의 기본 일꾼 묶음 + 한도 4 는 39~42 가지, 742.0~799.2 MiB 였다(프로브가 다시 낸다).
9. (실행 `075196`) 아레나 하나 설정은 한 스레드에서 견줌 한 번의 시간을 가르지 못했다(+0.8ms, p=0.58). 스레드 넷이 함께 견주는 판에서는 +17.0ms 였고 같은 판의 mmap 문턱 설정은 +19.4ms 였다(프로브가 다시 낸다). 그 판에서는 5ms 를 더한 대조도 +10.1ms 로 더한 것보다 크게 잡혔다.
10. (실행 `075196`) uvicorn 서버에서 해시만 도는 스레드 넷은 서버 최고 상주가 134.9 MiB(견줌 스레드 4 가지)로, 같은 실행의 `thread` 한도 4 의 153.9 MiB(5 가지)보다 해시 하나 몫(19.0 MiB) 작았다. CPU 4 개 K=100 의 `/health` 부하 90분위는 20.3ms(창 하나)와 22.2ms 였다(프로브가 다시 낸다).

## 다시 돌리기

저장소 루트에서 친다. `<폴더>` 는 결과를 남길 폴더다(없으면 만든다).

```sh
uv run --offline python .scratch/admin-login/probes/hash_load/run.py docker --work <폴더>
```

- 필요한 것: 도는 Docker 데몬(리눅스 엔진)과 이 PC 에 이미 있는 이미지 `admin-login-pwhash-probe-linux:latest`. 그 이미지는 `../password_hash/Dockerfile` 로 지은 것이고 저장소 잠금의 패키지와 argon2-cffi 25.1.0 이 `/app/.venv` 에 있다. 이 프로브는 이미지를 짓지도 받지도 않는다. 이미지가 없으면 `../password_hash/README.md` 의 "다시 돌리기"로 짓는다(그 길은 네트워크를 쓴다). 호스트 쪽은 저장소의 `.venv` 로 돌고 argon2-cffi 가 없어도 된다. 네트워크, LLM, 데이터베이스를 쓰지 않는다.
- 하는 일: 컨테이너 하나를 `--rm --memory 2g --memory-swap 2g --cpuset-cpus 0-5` 로 띄운다(이름 `admin-login-hashload-probe-<실행 토큰>`). 저장소는 읽기 전용으로 `/repo` 에, `<폴더>` 는 `/work` 에 붙이고 그 안에서 `run.py here` 를 돈다. 끝나면 그 이름과 글자 그대로 같은 컨테이너만 찾아 지운다. 볼륨, 네트워크, 이미지는 만들지 않는다. `<폴더>` 에 `raw-<토큰>.log`(컨테이너 출력 전부), `results-<토큰>.json`(모든 결과), `children-<토큰>.log`(하위 프로세스의 명령과 원본 출력), `server-*.log`, `sampler-*.log`, `samples-*.jsonl` 이 남는다.
- 실행 `075196` 이 더한 갈래만 돌려면(앞의 갈래를 다시 돌지 않는다) 같은 명령에 `--items alloc_arena,burst_pool,http_pool` 을 붙인다. 셋 가운데 하나만 돌려면 그 이름 하나를 준다. 실행 `075196` 이 그 명령이다(약 10분).
- 고르기(기본값): `--items unicode,timing,alloc,burst,http,alloc_arena,burst_pool,http_pool`(실행 `9f1d11` 때의 기본값은 앞의 다섯이었다), `--server-cpus 2,4`(서버와 burst 의 CPU 수. `burst_pool` 도 따르고 `http_pool` 은 4 로 고정이다), `--burst-rounds 5`, `--late-rounds 2`(끝난 뒤의 상주 갈래의 회차), `--http-rounds 3`, `--timing-n 400`(함수 길의 묶음 수), `--timing-repeats 2`, `--http-timing-n 200`(HTTP 길의 묶음 수), `--alloc-pairs 10`, `--alloc-n 60`, `--timeout 7200`(초).
- 측정이 아닌 회차가 하나라도 있으면 종료 코드가 1 이다. 항목 하나가 예외로 끝나면 그 항목을 측정 아님 한 회차로 세고 다음 항목으로 간다.
- 호스트(윈도)에서 바로 돌리려면 argon2-cffi 가 있는 환경의 파이썬으로 `run.py here --work <폴더>` 를 친다(예: `../password_hash/README.md` 의 임시 트리와 `uv run --project <tree> --no-sync python …`). 윈도에서는 CPU 를 고정하지 않고 끄기 전의 명령줄 확인을 하지 않는다. 이번 결과에는 호스트 실행이 없다.
- 린트: `uv run ruff check .scratch/admin-login/probes/hash_load`, `uv run ruff format --check .scratch/admin-login/probes/hash_load`.

## 결과

### 항목 1. 동시 로그인의 메모리와 걸린 시간(함수 길)

`burst.py` 를 갈래마다 새 프로세스로 띄워 CPU 2 개(0·1)와 4 개(0~3)에 고정하고 갈래마다 회차 5 를 돌았다. 메모리 읽기의 양성 대조(64 MiB 를 쓴 프로세스)가 64.0~64.0 MiB 로 섰고, burst 의 회차 206 이 모두 표지(견줌이 모두 참, 겹친 해시 수가 1 이상이고 한도 이하, 갈래마다 더한 표지)를 냈다(프로브가 다시 낸다). 아래 표의 "최고 상주가 는 양"은 해시 앞의 바닥에서 잰 것이고 회차와 CPU 수 사이의 차는 1 MiB 안이었다. "요청 중앙"은 회차마다 낸 중앙값 다섯의 중앙, "최대"는 모든 요청 가운데 가장 긴 것, "다 끝난 시간"은 K 개를 넘긴 뒤 마지막 결과를 받기까지의 회차 중앙이다.

### 항목 2. uvicorn 요청 길에서 `/health` 가 늦어지는 정도

`server.py`(작은 Starlette 앱을 `uvicorn.run` 으로, h11, `_UnixSelectorEventLoop`)를 서버 설정마다 띄웠다. 서버는 CPU 0 부터 2 개나 4 개, 표본 프로세스는 CPU 4, 부하 프로세스는 CPU 5 에 고정했다. 표본 프로세스는 `/health`(이벤트 루프에서 바로 답한다)와 `/thread-health`(빈 일을 기본 한도로 넘긴 뒤 답한다. 제품의 동기 경로 흉내)를 하나씩 차례로 보낸다. 부하 프로세스는 로그인 K 개를 한꺼번에 보낸다. 서버 설정은 다섯이다. `thread` 는 견줌을 `anyio.to_thread.run_sync` 로 넘기고 기본 한도, 전용 한도 4, 2 의 셋이다. `sleep` 은 견줌 대신 40ms 잠들기를 기본 한도로 넘기는 대조(CPU 를 쓰지 않고 스레드 자리만 차지한다), `direct` 는 견줌을 이벤트 루프에서 바로 하는 양성 대조(K 1·4·16)다.

창(로그인을 보낸 때부터 마지막 응답까지) 하나가 회차이고 K 마다 회차 3 이다. 회차 138 가운데 135 가 표지(로그인 K 개가 모두 200 과 참, 서버가 센 겹친 해시가 1 이상 한도 이하, 창과 겹친 표본이 하나 이상)를 냈다(프로브가 다시 낸다). 남은 셋은 CPU 4 개의 `thread` 기본 한도 K=100 의 #2·#3 과 한도 4 K=100 의 #3 이다. 부하 프로세스가 로그인 요청에서 `httpx.ReadError` 로 끝나 창이 없었다(손으로 봤다, `children-9f1d11.log` 의 `client.py` 86행 traceback. 서버 기록에는 200 이 아닌 응답이 없었다). uvicorn 의 연결 유지 5초(`timeout_keep_alive=5`, uvicorn 0.53.0 `uvicorn/config.py` 234행)와 httpx 의 5초(`keepalive_expiry=5.0`, httpx 0.28.1 `httpx/_config.py` 178행, 둘 다 코드를 읽었다)가 맞물려 서버가 닫은 연결을 클라이언트가 다시 썼다는 것은 어림이다. 그 두 줄은 측정인 창 하나(기본 한도)와 둘(한도 4)로 냈다.

### 항목 4. 유니코드

입력마다 NFKC 로 정규화한 글로 해시를 만들고 같은 글이 통과하고 한 글자 더한 글이 걸리는 것을 표지로 봤다. 열일곱 입력이 모두 측정이다(프로브가 다시 낸다, 유니코드 15.0.0). "규칙"은 길이(코드 포인트 8~128)와 글자 종류를 함께 본 판정이고 두 가지로 읽었다. ASCII 읽기는 대문자 `A`~`Z`, 숫자 `0`~`9`, 특수문자는 ASCII 영문자와 숫자가 아닌 모든 글자다. 유니코드 읽기는 `str.isupper`, `str.isdigit`, `str.isalnum` 이 거짓인 글자다(`unicode_check.py`).

모든 "됨" 행에서 마지막 글자를 뺀 글도 걸렸다. 503 바이트(128 자)와 507 바이트(129 자)에서도 마지막 글자가 견줌을 가른 것이라, 이 범위에서 argon2-cffi 가 비밀번호를 잘라 쓰지 않았다(프로브가 다시 낸다). 위 표에서 읽히는 것.
- 정규화를 거치면 글자 수가 바뀌어 길이 판정이 갈린다. NFD 한글 9 자는 NFKC 뒤 7 자로 8 자 아래가 되고, U+FDFA 일곱(11 자)은 130 자로 128 자를 넘는다(프로브가 다시 낸다).
- 정규화 앞의 글은 정규화한 글로 만든 저장 값을 통과하지 못했다(프로브가 다시 낸다). 그래서 정규화를 한다면 저장할 때(비밀번호를 정할 때)와 견줄 때(로그인) 둘 다에서 해야 한다. 한쪽만 하면 같은 글을 친 사람이 걸린다(표의 "정규화 앞의 글은 걸림"이 그 장면이다).
- 글자 종류의 판정은 읽기에 따라 갈린다. ASCII 읽기에서는 전각 글자, 켈빈 기호, 위 첨자가 정규화 앞에서 걸리고 뒤에서 통과한다. 한글은 ASCII 읽기에서 특수문자로 세고 유니코드 읽기에서는 세지 않는다(프로브가 다시 낸다).
- 4바이트 글자 128 자는 UTF-8 로 503 바이트, UTF-16 으로 253 단위다. 브라우저의 `maxlength` 와 `String.length` 가 UTF-16 단위로 센다면 같은 비밀번호를 화면은 128 을 넘었다고, 서버는 128 이하라고 본다(단위의 수는 프로브가 다시 내고, 브라우저가 그 단위로 센다는 것은 이 프로브가 재지 않은 어림이다).
- 짝 없는 서로게이트는 규칙을 통과하고 해시에서 `UnicodeEncodeError` 로 끝났다. 규칙만으로는 막히지 않는다(프로브가 다시 낸다).

## 덧붙인 갈래(실행 `075196`)

실행 `9f1d11` 뒤에 갈래 셋(`burst_pool`, `alloc_arena`, `http_pool`)을 더해 그 셋만 한 번 돌았다. 2026-11-24 19:17:16 에 시작해 19:27:29 에 끝났다(약 10분). 측정 50 회차, 측정 아님 2 회차로 종료 코드 1 이었다(프로브가 다시 낸다, 실행 출력의 끝 줄). 끝난 뒤 이 프로브의 컨테이너는 남지 않았다(프로브가 다시 낸다, "정리: 컨테이너 0". `docker ps -a` 에도 `admin-login-hashload-probe-` 로 시작하는 것이 없었다, 손으로 봤다). 측정 아님 둘은 `http_pool` 의 전용 스레드 서버 K=100 의 #2·#3 이다. 실행 `9f1d11` 과 같이 부하 프로세스가 로그인 요청에서 `httpx.ReadError` 로 끝나 창이 없었다(손으로 봤다, `children-075196.log` 의 `client.py` 86행·66행 traceback). 그 서버 기록에는 200 이 아닌 응답이 없었고, 로그인 몸통을 읽다 난 `starlette.requests.ClientDisconnect` 가 하나 있었다(손으로 봤다, `server-075196-18201.log`). 호스트 CPU 부하는 컨테이너를 띄우기 직전 79%, 끝난 직후 100% 였다(프로브가 다시 낸다). 판(파이썬, argon2-cffi, anyio, starlette, uvicorn, glibc, cgroup)은 실행 `9f1d11` 과 같았다(프로브가 다시 낸다, 실행의 첫 줄 "환경"). 결과를 낸 실행 앞의 시험 실행은 아래 "판정 기준을 바꾼 것"에 있다.

### 해시만 도는 스레드 넷의 끝난 뒤 상주(함수 길)

`burst.py --pool 4` 는 견줌을 `concurrent.futures.ThreadPoolExecutor(max_workers=4, thread_name_prefix="hashpool")` 에 `asyncio.get_running_loop().run_in_executor` 로 넘기고 기다린다. 동시에 도는 견줌은 그 묶음의 스레드 수가 묶어 `CapacityLimiter` 를 두지 않았다. AnyIO 4.15.1 의 `to_thread.run_sync` 는 함수와 인자 밖에 `abandon_on_cancel`, `cancellable`, `limiter` 만 받아 스레드 묶음을 고를 길이 없다(코드를 읽었다, anyio 4.15.1 `anyio/to_thread.py` 27~32행). 그래서 해시만 도는 스레드를 두려면 이 길이 된다. 조건은 위 "끝난 뒤에 남는 상주"와 같다(K=40, 잇달아 셋, 다른 스레드 일은 5ms 잠들기를 기본 한도로 40 개씩, CPU 2 개와 4 개, 갈래마다 회차 2). 같은 실행에서 견주려고 앞선 갈래 둘(한도 4 의 잇달아 셋, 한도 4 의 다른 스레드 일과 잇달아 셋)을 회차마다 전용 스레드 갈래 둘 뒤에 이어 돌았다(차례는 섞지 않았다).

메모리 읽기의 양성 대조가 64.0~64.0 MiB 로 섰고 16 회차가 모두 표지를 냈다(프로브가 다시 낸다). 표지는 견줌이 모두 참, 동시 1~4, 셋 번이 다 돌았다, 다른 스레드 일 갈래에서 그 일이 돈 횟수(4748~12723), 전용 스레드 갈래에서 견줌을 맡은 스레드 이름이 모두 `hashpool` 로 시작하고 그 가짓수가 4 를 넘지 않는 것이다. 값은 해시 앞의 바닥에서 잰 MiB 이고 읽기는 위 표와 같다. ### 아레나 하나의 견줌 한 번 시간

위 "할당기 설정이 견줌 한 번에 더하는 시간"과 같은 짜임이다. `timing.py` 를 갈래 하나(`correct` 60 번)로 띄운 프로세스를 짝마다 섞은 차례로 띄우고, 프로세스마다 중앙값을 낸 뒤 같은 짝의 설정 없음과 짝지어 견줬다. 한 스레드 판(CPU 0)은 설정 없음, `GLIBC_TUNABLES=glibc.malloc.arena_max=1`, 설정 없이 5ms 를 더하는 대조의 셋이다. 한 스레드에서는 모든 할당이 주 아레나로 가서 아레나 수를 묶어도 달라질 것이 없다는 해석(어림, glibc 코드를 읽지 않았다)을 가르려고, 스레드 넷이 함께 견주는 판(`timing.py --threads 4`, CPU 0~3)을 더했다. 그 판은 같은 스레드 넷이 호출마다 `threading.Barrier` 에서 만나 함께 견주고 스레드마다 표본 하나를 낸다. mmap 문턱 설정도 그 판에 넣었다. 짝 10 이고 한 스레드 판 프로세스 30, 스레드 넷 판 프로세스 40 이 모두 결과가 기대대로였고 프로세스가 본 `GLIBC_TUNABLES` 가 준 값과 같았다. 스레드 넷 판의 프로세스 40 은 모두 호출 60 번 모두에서 넷이 함께 견줌 안에 있었고 견줌을 맡은 스레드가 넷이었다(문턱은 호출의 90% 이상). 양성 대조가 두 판 모두 섰다(프로브가 다시 낸다).

| (실행 `9f1d11`) 한 스레드 | mmap 문턱 설정 | 56.8ms(52.4~64.0) | +18.3ms(+16.8~+19.2), 0.0051 |

- 한 스레드에서는 아레나 하나가 견줌 한 번의 시간을 가르지 못했다(+0.8ms, p=0.58. 같은 판의 5ms 대조는 갈렸다). 스레드 넷이 함께 견주면 아레나 하나는 +17.0ms(설정 없음의 38% 쯤), mmap 문턱은 +19.4ms(44% 쯤) 였다(프로브가 다시 낸다). 아레나 하나와 mmap 문턱을 맞대 짝지은 비교는 하지 않았다.
- 스레드 넷 판의 5ms 대조가 +10.1ms 로, 더한 시간보다 크게 잡혔다(프로브가 다시 낸다). 그 판에서 더한 일이 시간에 부풀려 잡힌다면 아레나 하나와 mmap 문턱의 값도 한 스레드 판의 값(+18.3ms)과 같은 자로 견줄 수 없다. 부풀린 까닭(CPU 0~3 를 컨테이너 안의 다른 프로세스와 나눠 쓰는 몫 등)은 재지 않았다(어림).
- 아레나 하나가 스레드 넷에서만 시간을 더하는 까닭(해시마다 운영체제에서 메모리를 새로 받는 것인지, 아레나 하나의 잠금을 기다리는 것인지)은 가르지 않았다. 실행 `9f1d11` 에서 아레나 하나가 남는 상주를 0.7~19.8 MiB 로 줄인 것과 맞춰 앞의 것이라고 읽는 것은 어림이다.

### uvicorn 서버의 해시만 도는 스레드 넷

`server.py --mode pool --limit 4` 는 견줌을 해시만 도는 스레드 넷(`ThreadPoolExecutor`, 이름 머리 `hashpool`)에 `run_in_executor` 로 넘긴다. `/thread-health` 는 그대로 기본 일꾼 묶음을 쓴다. 항목 2 와 같은 조건(서버 CPU 0~3, 표본 프로세스 CPU 4, 부하 프로세스 CPU 5, K 1·4·16·40·100, K 마다 회차 3)으로 돌고, 같은 실행에서 견주려고 `thread` 한도 4 서버를 그 뒤에 다시 돌았다. 회차 30 가운데 28 이 표지(로그인 K 개가 모두 200 과 참, 서버가 센 겹친 해시가 1 이상 4 이하, 창과 겹친 표본이 하나 이상, 전용 스레드 서버에서는 견줌 스레드 이름이 모두 `hashpool` 로 시작하고 그 가짓수가 4 이하)를 냈다(프로브가 다시 낸다). 남은 둘은 위의 측정 아님 둘이라 전용 스레드 서버의 K=100 은 창 하나다. 읽기는 항목 2 의 표와 같다.

- 로그인의 걸린 시간은 항목 2 와 같은 까닭으로 이 길에서 견주지 않는다.

### 해시만 도는 스레드 길이 AnyIO 길과 다른 점(코드를 읽었다, 재지 않았다)

- 취소. AnyIO 의 `run_sync` 는 기본(`abandon_on_cancel=False`)에서 취소를 막고 스레드의 일이 끝날 때까지 기다린다(anyio 4.15.1 `anyio/_backends/_asyncio.py` 2671행 `CancelScope(shield=not abandon_on_cancel)`). `run_in_executor` 가 돌려준 것을 기다리던 쪽이 취소되면 `concurrent.futures.Future.cancel()` 을 부른다(CPython 3.12.10 `asyncio/futures.py` 389~394행, 호스트의 파이썬이다. 컨테이너는 3.12.16 이고 그 코드는 읽지 않았다). 아직 시작하지 않은 견줌은 돌지 않고 돌던 견줌은 끝까지 돈다는 것은 그 `cancel` 의 알려진 동작이고 코드는 읽지 않았다(어림). 클라이언트가 끊은 로그인의 견줌이 돌지 않을 수 있다는 뜻이다.
- `contextvars`. AnyIO 는 넘긴 함수를 부른 쪽의 `contextvars` 사본에서 돌린다(같은 파일 2698행 `copy_context`, 1100행 `context.run`). `loop.run_in_executor` 는 `executor.submit(func, *args)` 로 사본 없이 넘긴다(CPython 3.12.10 `asyncio/base_events.py` 853행·867행).
- 스레드 수. `ThreadPoolExecutor` 는 놀고 있는 스레드가 없을 때만 `max_workers` 까지 스레드를 새로 만든다(CPython 3.12.10 `concurrent/futures/thread.py` 184~195행). 전용 스레드 갈래의 견줌 스레드 가짓수가 늘 4 였던 것(위)과 맞는다.

결론마다 그 해석이 맞으면 나올 결과가 실제로 나온다는 양성 대조와, 같은 관찰을 설명하는 다른 해석을 가르는 갈래를 둔 자리다. 표지와 문턱은 `run.py` 독스트링이 원천이다.

## 재지 못한 것

- 배포할 서버. CPU 를 2·4 개로 고정한 이 PC 의 WSL2 위 컨테이너만 봤다. 고정한 CPU 가 같은 물리 코어의 두 하이퍼스레드인지는 모른다. 측정 앞뒤로 호스트 CPU 부하가 97~100% 였다(결과 머리). 걸린 시간의 절대값은 조용한 PC 보다 크고 흔들린다.
- 실제 제품의 로그인 길. FastAPI, pydantic 의 몸통 검증, 데이터베이스 조회, 세션 쿠키, 요청 출처 검사, 접근 기록을 거치지 않는 흉내 앱이다. 제품에서 기본 스레드 한도를 함께 쓰는 동기 경로(관리 경로의 `def` 다섯, `src/agent_os/admin/http.py` 157·172·253·301·324행, FastAPI 0.141.1 `fastapi/routing.py` 354행이 `run_in_threadpool` 으로 넘기고 Starlette 1.6.0 `starlette/concurrency.py` 34행이 한도 없이 `anyio.to_thread.run_sync` 를 부른다. 코드를 읽었다)는 5ms 잠들기로 흉내 냈을 뿐이다.
- 한도를 넘은 로그인을 어떻게 다룰지. 이 프로브의 한도는 기다리게만 한다. 기다리는 줄의 상한이나 곧바로 거절하는 길(예: 429)은 재지 않았다.
- uvicorn 의 일꾼 프로세스 여럿(`--workers`). 프로세스 하나만 봤다. 일꾼마다 한도와 남는 상주가 따로 선다는 것은 어림이다.
- glibc 밖의 할당기(Alpine 의 musl, jemalloc). 이미지는 Debian 의 glibc 2.41 이다. glibc 의 mmap 문턱과 아레나의 동작은 이 프로브에서 glibc 코드를 읽지 않았고, 측정이 그 설명과 맞는다는 것만 봤다.
- 해시를 AnyIO 의 일꾼 묶음 밖의 전용 스레드에서 돌리는 길. ADR 0062 가 `anyio.to_thread.run_sync` 로 정해 실행 `9f1d11` 에서는 재지 않았다. 실행 `075196` 에서 함수 길(K=40, CPU 2·4 개, 회차 2)과 uvicorn 서버(CPU 4 개)를 쟀다("덧붙인 갈래"). 거기서도 재지 않은 것은 아래 "실행 `075196` 이 재지 못한 것"이다.
- 아레나를 하나로 묶는 설정의 시간 값. 실행 `9f1d11` 에서는 한 스레드에서 도는 `alloc` 에서는 달라질 것이 없어 넣지 않았고, 동시 burst 의 걸린 시간(회차 둘)만 있었다. 실행 `075196` 에서 한 스레드 판과 스레드 넷 판으로 쟀다("덧붙인 갈래").
- 네트워크를 건너는 시간 차. HTTP 길은 같은 컨테이너의 127.0.0.1 이다. 공격자가 보는 쪽의 잡음은 이보다 크다는 것이 어림이다.
- HTTP 길의 견줌 시간. 5ms 대조가 서지 않아 맞는·틀린·없는 계정의 비교 셋이 측정 아님이다. 묶음을 늘리거나 조용한 PC 에서 다시 돌면 설 수 있다는 것은 어림이다.
- CPU 4 개의 `thread` 기본 한도 K=100 의 창 둘과 한도 4 K=100 의 창 하나. 부하 프로세스가 `httpx.ReadError` 로 끝났다(항목 2). 연결 유지 시간이 맞물린 탓이라는 것은 어림이고, 클라이언트의 `keepalive_expiry` 를 서버의 5초보다 짧게 두는 고침은 하지 않았다.
- HTTP 길의 로그인 시간에서 부하 프로세스의 몫. 부하 프로세스를 CPU 하나에 고정했고 `sleep` 대조도 K=100 에서 1초 안팎이었다. 그 몫을 따로 재지 않았다.
- CPU 2 개에서 `/health` 의 지연 가운데 해시의 몫. `sleep` 대조도 비슷하게 늦어 가르지 못했다.
- 정규화의 다른 형식(NFC)과 브라우저가 입력 단계에서 하는 일. 서버의 파이썬에서 NFKC 만 봤다. 브라우저의 `maxlength` 와 `String.length` 가 UTF-16 단위로 센다는 것은 이 프로브가 잰 것이 아니라 그 단위의 수를 함께 낸 것이다.
- 짝 없는 서로게이트가 제품 길에 닿는지. Starlette 의 `Request.json` 은 `json.loads` 를 쓴다(코드를 읽었다, Starlette 1.6.0 `starlette/requests.py` 265행). FastAPI 와 pydantic 이 그 글을 그대로 넘기는지는 재지 않았다. argon2-cffi 의 `verify` 도 `hash` 처럼 비밀번호를 같은 인코딩으로 바꾼다(코드를 읽었다, argon2-cffi 25.1.0 `argon2/_password_hasher.py` 29~35행과 259행). `verify` 의 예외는 재지 않았다.
- 호스트(윈도)의 값.

실행 `075196` 이 재지 못한 것.

- 해시만 도는 스레드의 수가 4 가 아닌 판, 전용 스레드에 할당기 설정(mmap 문턱, 아레나 하나)을 더한 판, 전용 스레드 묶음을 닫은 뒤(스레드가 끝난 뒤)의 남는 상주. 전용 스레드는 0.5초 뒤 읽기 때 살아 있었다.
- 전용 스레드 길의 K=100 함수 길과 K=1·4·16 의 끝난 뒤 상주. K=40 만 돌았다. 전용 스레드 넷이면 K 와 상관없이 넷 몫이라는 것은 실행 `9f1d11` 의 한도 4 표에서 미룬 어림이다.
- uvicorn 서버의 전용 스레드 넷을 CPU 2 개에서 돈 것, 그 서버의 K=100 창 둘째와 셋째(`httpx.ReadError`, 위). K=100 의 90분위는 창 하나의 값이다.
- 전용 스레드 길의 취소와 `contextvars` 가 AnyIO 길과 다르게 움직이는 것. 코드를 읽었을 뿐이다("해시만 도는 스레드 길이 AnyIO 길과 다른 점"). 클라이언트가 끊은 로그인에서 견줌이 도는지, 줄에서 기다리던 견줌이 빠지는지는 재지 않았다.
- 아레나 하나와 mmap 문턱이 스레드 넷의 견줌 한 번에 시간을 더하는 까닭(쪽 부재 횟수, 아레나 잠금을 기다린 시간). 둘을 맞대 짝지은 비교도 하지 않았다.
- 스레드 넷 판의 5ms 대조가 +10.1ms 로 잡힌 까닭. 그 판의 더한 시간이 얼마나 부풀려 잡히는지 모르므로, 그 판의 +17.0ms·+19.4ms 를 한 스레드 판의 +18.3ms 와 같은 자로 견주지 않는다.
- 해시만 도는 스레드를 제품에 두는 모양(FastAPI 의 수명 주기에서 묶음을 열고 닫기, uvicorn 의 일꾼 프로세스 여럿에서 프로세스마다 묶음이 서는 것).

## 판정 기준을 바꾼 것

모두 시험 실행의 결과를 본 뒤 결과를 낸 실행 앞에 바꿨고, 바꾼 것과 까닭은 `run.py` 와 `burst.py` 의 독스트링에도 있다. 시험 실행의 결과는 결론에 쓰지 않았다.

- burst 와 http 의 표지. 첫 판은 "동시 스레드 수의 최대값이 `min(K, 한도)` 와 같다"였다. 시험 실행 `c00f0f`(CPU 2 개, 회차마다 1 번)에서 기본 한도의 K=40 이 35, HTTP 의 K=16·40·100 이 15·31·34 였다. 해시가 겹치는 수가 CPU 와 요청이 닿는 빠르기에 따라 K 보다 적은 것은 재려는 상황의 결과이지 그 상황이 나지 않은 것이 아니라서, "1 이상이고 한도를 넘지 않는다"로 바꾸고 그 최대값을 결과로 낸다.
- 시간 비교의 짜임과 검정. 첫 판은 모든 표본을 한꺼번에 섞은 차례로 돌고 두 갈래의 값 분포를 짝짓지 않고 견줬다(콜모고로프-스미르노프). `c00f0f` 에서 1ms 대조가 벽시계 시간으로 갈리지 않아(n=20) CPU 시간을 더하고 벽시계 쪽 대조를 5ms 로 바꿨다. 둘째 시험 실행 `c5f1e2`(n=30)에서도 1ms 대조가 두 시간 모두 갈리지 않았다. 그래서 묶음으로 짝짓는 짜임과 윌콕슨 부호 순위 검정으로 바꾸고, 함수 길의 대조를 두 시간 모두 1ms 로 되돌렸다. HTTP 길의 대조는 5ms 그대로다. 콜모고로프-스미르노프는 참고로만 낸다.
- 늦게 읽기의 표지. 첫 판은 "12초 쉰 뒤 살아 있는 스레드 1"이었다. `c5f1e2` 에서 41 과 5 가 나왔다. AnyIO 의 일꾼은 스스로 끝나지 않고 다음 `run_sync` 가 오래 논 일꾼을 정리한다는 것을 코드에서 읽었고(anyio 4.15.1 `_backends/_asyncio.py` 1045행, 2674~2696행), 빈 일 하나로 그 정리를 부르고 표지를 2 로 바꿨다.
- 갈래를 더한 것. 셋째 시험 실행 `d656da` 에서 끝난 뒤의 상주가 최고 상주와 같고 일꾼 스레드가 정리된 뒤에도 남는 것을 보고 잇달아 셋과 할당기 설정을 더했다. 그 뒤의 시험 실행 셋(`d6a952`, `0f0e73`, `e6f6e3`)을 보며 다른 스레드 일과 함께, 거기에 할당기 설정과 아레나 하나를 더한 갈래, `alloc` 항목, 모든 회차의 견줌 스레드 가짓수를 차례로 더했다. 이미 있던 갈래의 표지와 문턱은 바꾸지 않았다.
- 함수 길의 묶음 수. 시험 실행의 잡음을 보고 300 에서 400 으로 늘렸다.
- 실행 `075196` 의 갈래 셋(`burst_pool`, `alloc_arena`, `http_pool`)은 표지와 문턱(스레드 넷 판의 "호출의 90% 이상에서 넷이 함께", 전용 스레드 이름의 머리, 견줌 스레드 가짓수 4 이하)을 시험 실행 `b61b40` 앞에 정했고 그 뒤 바꾸지 않았다. `b61b40` 은 회차를 줄여(`--alloc-pairs 2 --alloc-n 10 --late-rounds 1 --http-rounds 1 --server-cpus 2`) 짜임이 도는지만 봤다. 측정 17, 측정 아님 3 이었고 셋은 짝 2 로는 5ms 대조가 문턱 0.01 에 닿을 수 없는 `alloc_arena` 의 설정 비교였다(짝 2 의 부호 순위 검정이 낼 수 있는 가장 작은 p 가 0.18). 그 결과는 결론에 쓰지 않았다. 앞선 항목의 표지와 문턱도 바꾸지 않았다. `burst_round` 와 `item_alloc` 은 새 갈래를 받게 고쳤지만 앞선 갈래의 인자, 차례, 시드, 회차 이름은 그대로다(코드를 읽었다, 이 판의 `run.py`).
