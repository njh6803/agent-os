# swr_poll — 결말 없는 실행의 트레이스를 3초마다 다시 읽다 멈추는 규칙을 설치된 SWR 로 짓기

ADR 0063 의 결정 "도는 실행을 이어 보기"와 "주기 읽기의 예외"는 관리 화면이 마지막 실행의 실행 상태가 결말
없음이면 그 실행의 트레이스만 3초마다 다시 읽고, 끝남·실패·일시정지가 되거나 마지막 이벤트 뒤 10분 동안 새
이벤트가 없으면 그만 읽고, 창이 가려진 동안에는 읽지 않게 했다. 그 ADR 의 Consequences "재지 않은 것"은
`refreshInterval` 에 준 함수가 0 을 돌려주면 다시 읽기가 멈추는지를 돌려 보지 않았다고 적었다. 이 프로브는 그것과
가려짐, 실패, 10분 조건을 설치된 SWR 로 jsdom 에서 돌려 잰다. 고르지는 않는다. 고르는 것은 admin-login 명세다.

**지금 상태(2026-11-24)**: 열세 번 돌았다. 마지막 판으로 돈 세 번(11~13)이 32 회차 모두 측정이었고, 12 와 13 은 11 이 쓴
스냅샷과 같아 종료 코드 0 이었다(13 은 `poll.probe.ts` 의 주석만 고친 뒤다). 1~10 의 경과는 아래 "판정 기준을 바꾼 것".
이 워크트리에는 `node_modules` 가 없어 열세 번 모두 주 체크아웃의 `web/` 에 깔린 의존성으로 돌았다(그 체크아웃과 이
워크트리의 `web/pnpm-lock.yaml` 은 같았다. `cmp` 로 손으로 봤고 9번째 앞에 다시 봤다). 9~13번째의 앞과 뒤에 그 체크아웃의
`web/node_modules/.modules.yaml` 고친 시각이 같았다(16:48:06, 6번째 실행의 시각. `ls` 로 손으로 봤다).

| 파일 | 무엇 |
|---|---|
| `poll.probe.ts` | 측정. 회차, 표지, 대역 데이터, 갈래는 그 머리 주석과 회차 이름이 원천이다. 회차마다 어느 꼴을 도는지는 `Pattern` 의 주석 |

## 다시 돌리기

의존성이 깔린 체크아웃의 저장소 루트에서

```
node web/node_modules/vitest/vitest.mjs run --config .scratch/admin-login/probes/swr_poll/vitest.config.mjs
```

의존성이 없는 체크아웃(새 워크트리)에서는 깔린 체크아웃의 vitest 를 절대 경로로 띄운다. 설정이 그 vitest 가 놓인
`web/` 을 찾아 거기서 푼다.

```
node <의존성이 깔린 체크아웃>/web/node_modules/vitest/vitest.mjs run --config .scratch/admin-login/probes/swr_poll/vitest.config.mjs
```

- 설정 경로는 절대 경로로 줘도 된다. 9~13번째는 이 워크트리에서
  `node C:/project/agent/web/node_modules/vitest/vitest.mjs run --config <이 폴더의 절대 경로>/vitest.config.mjs` 로 돌았다.
- 필요한 것: `web/` 의 의존성(관리 화면 앱의 swr·react·react-dom·@testing-library/react, 워크스페이스의 vitest·jsdom).
  새로 깔 것은 없다. 네트워크와 Docker 를 쓰지 않는다.
- 8~23초였다(열세 번의 vitest `Duration` 줄, 손으로 봤다. 32 회차인 9~13번째는 16~18초).
- 쓰는 것: OS 임시 폴더의 `agent-os-swr-poll-results.json`(원본 기록: 판, 의존성을 푼 `web/`, 회차마다 표지와 결과)과
  vite 캐시 `agent-os-swr-poll-probe-vite/`. `expected.json` 은 없을 때만 쓴다. 앱의 소스와 `node_modules` 는 고치지 않는다.
- 종료 코드 0 은 32 회차가 모두 측정이고 결과가 `expected.json` 과 같을 때뿐이다. 측정 아닌 회차가 하나라도 있거나
  스냅샷과 다르거나 스냅샷에 없는 회차가 있거나 스냅샷이 없어 새로 썼으면 1 이다. 스냅샷을 다시 박으려면 지우고 두 번 돌린다.
- **`pnpm -C web/apps/admin exec vitest run --config ../../../.scratch/admin-login/probes/swr_poll/vitest.config.mjs`
  는 쓰지 않는다.** 6번째 실행이 이 꼴(주 체크아웃의 `web/apps/admin` 으로)이었고 결과는 스냅샷과 같았지만, pnpm 11.24.0
  의 `exec` 가 vitest 를 띄우기 전에 그 체크아웃의 설치를 돌렸다. 출력 머리가 패키지 101개를 저장소에서 다시 놓고
  (내려받기 0) 관리 화면 앱의 직접 의존성 다섯(`@agent-os/ui`, `@tailwindcss/postcss`, `@tailwindcss/vite`,
  `tailwindcss`, `vite`)을 더했다고 적었고, 그 체크아웃의 `web/node_modules/.modules.yaml` 의 고친 시각이 그 시각으로
  바뀌었다. 잠금 파일과 `package.json` 은 그대로였다(`cmp` 와 `ls` 로 손으로 봤다). 그 체크아웃의 `node_modules` 가
  잠금 파일보다 뒤처져 있었기 때문이라고 읽는다(어림). 그래서 위처럼 node 로 직접 띄운다.

## 장치

- `renderHook` 으로 `useSWR(키, 가짜 fetcher, { ...READ, ...회차의 옵션, refreshInterval })` 을 띄운다. 캐시는 회차마다
  새 `Map` 이다(앱의 `testing/render.tsx` 와 같은 `provider`).
- `READ` 는 앱의 읽기 정책(`web/apps/admin/hooks/queries/admin/index.ts` 의 `READ`)을 옮긴 값이고, 회차 0 이 이
  프로브가 든 체크아웃의 그 파일 글과 견준다.
- 가짜 시계는 vitest 의 `useFakeTimers` 로 `setTimeout`·`clearTimeout`·`setInterval`·`clearInterval`·`Date` 만 바꾼다.
  시각을 100ms 씩 `act` 안에서 밀어 그 사이마다 React 가 그린다. 아래의 시각은 모두 시작에서 잰 ms 다.
- 가짜 fetcher 는 불린 시각과 돌려준 것을 스스로 적고 곧바로 끝난다(응답 지연 0). 그래서 주기 읽기가 3초 배수에 맞는다.
  데이터는 트레이스의 대역 `{ status, events, lastEventAt }` 이고 회차의 대본이 정한다.
- 규칙 함수: 데이터가 없으면 3000(회차 1b 는 0), 결말 없음이 아니면 0, 결말 없음이면 `Date.now() - lastEventAt < 600000`
  일 때 3000 아니면 0. 불릴 때마다 시각·받은 데이터·돌려준 값을 적는다.
- `refreshInterval` 을 주는 갈래 셋: stable(회차마다 한 번 지은 함수. 모듈 수준 함수나 의존성 없는 `useCallback` 과 같은
  모양), inline(그리기마다 새로 짓는 함수), state(숫자. 데이터가 바뀔 때 `useEffect` 가 규칙으로 다시 정해 상태에 둔다).
  admin-login 명세가 고른 것은 inline 이다. 2·3·4 의 회차는 첫 판이 stable 로만 쟀고, 9번째 실행부터 같은 시각·데이터·
  실패로 꼴만 inline 으로 바꾼 회차를 짝으로 둔다. 회차 이름에 꼴이 없는 2a~2e·3a·3b 는 stable 이다.
- 실패는 가짜 fetcher 가 `ProbeFailure`(Error 의 하위 클래스, `status` 필드. null 이면 응답 없음)를 던져 흉내 낸다. 앱의
  요청 함수 `readTrace`(`web/apps/admin/api/traces/index.ts` 39~49줄)는 응답이 없으면 `unreachable(cause)`, 데이터가 아닌
  응답이면 `failureOf(response.status, error)` 로 `RequestFailure`(`web/apps/admin/api/failure/index.ts` 12~24·36~43줄.
  Error 의 하위 클래스이고 `status` 와 에러 봉투 `envelope` 를 든다)를 던진다. 훅 `useTrace` 는 그것을 `orRejectAdminToken`
  으로 감싸 401 에서만 관리 토큰을 내려놓고 같은 실패를 다시 던진다(`hooks/queries/traces/index.ts` 60~70줄,
  `hooks/queries/admin/index.ts` 22~32줄). 코드를 읽었다(2026-11-24 의 docs/admin-login 브랜치). `ProbeFailure` 는 그
  모양(async 함수가 Error 의 하위 클래스를 던져 거절된 약속, `status` 필드)을 따르고 봉투는 싣지 않는다. 3c 의 500 도 같다.
- 그리는 쪽은 앱의 `readOf`(`components/pages/read.ts`)처럼 `data`·`error`·`isValidating` 을 그리는 동안 읽는다. 회차
  4c 의 `data` 줄(stable 과 inline 에 하나씩)만 `data` 만 읽는다.
- 가려짐은 `document.visibilityState`(와 `hidden`)를 이 프로브의 getter 로 덮고 `visibilitychange` 를 문서에 쏴서 흉내
  낸다. getter 가 hidden 을 돌려준 읽기를 시각과 함께 적는다. 이 프로브 자신의 이벤트 기록은 getter 를 거치지 않는다.

## 결과(2026-11-24, 프로브가 쟀다)

근거의 종류. 아래 수와 시각은 모두 `poll.probe.ts` 가 결과로 찍어 `expected.json` 에 박은 것이고 다시 돈 실행이 그
스냅샷과 견준다. 표의 "stable 과 같다"·"다르다"도 두 회차의 찍힌 결과를 견준 것이다. "때문이다"·"로 읽는다"로 끝나는
문장은 해석이고, 그 대조와 갈래는 아래 "해석의 갈래"에 있다. SWR 의 코드를 든 문장은 설치본 `swr@2.5.1` 의
`dist/use-swr-emll9s78.mjs` 와 `dist/config-context-ext53wcz.mjs` 를 읽은 것이다.

stable 과 inline 을 짝으로 잰 여덟 쌍(2a·2d·3a·3b·4a·4b·4c 두 줄) 가운데 읽은 시각이 갈린 것은 둘이다. 창에 돌아와 읽은
뒤의 틱이 inline 에서는 돌아온 시각에서 3초씩으로 옮겨 갔다(2a·3b. 돌아온 순간의 읽기 자체는 둘 다 있었다). 나머지
여섯은 읽은 시각과 횟수가 같았다(4c 두 줄은
그린 시각과 알림 조건도 같았다). 규칙이 불린 기록을 두 꼴 모두 찍는 3a·4a·4b 에서는 inline 쪽의 호출이 더 많았다.

## 해석의 갈래

- **0 이면 멈춘다.** 양성 대조는 1c stable 이다. 결말 없음이면 같은 stable 함수로 3초마다 계속 돈다. 1a 의 기록에서 6초에
  규칙이 0 을 낸 뒤 읽기가 끊겼다.
- **stable 함수가 다시 돌지 않는 까닭.** 주기를 거는 효과의 의존성이 `refreshInterval`·`refreshWhenHidden`·
  `refreshWhenOffline`·`key` 이고(`use-swr-emll9s78.mjs` 604~639줄), 함수가 0 을 내면 다음 타이머를 걸지 않으며(613줄),
  stable 함수면 새 데이터로 다시 그려도 의존성이 그대로라 효과가 다시 돌지 않기 때문이라고 읽는다. 갈래는 inline 과
  state 다. 둘은 새로 고침이 결말 없음을 읽은 뒤 다시 돌았다. 그래서 "SWR 이 0 을 한 번 받으면 어떤 꼴이든 영영 멈춘다"는
  해석은 서지 않는다. 1b stable 이 시작하지 않은 것도 같은 까닭으로 읽는다. 효과가 마운트 때 한 번 규칙을 부르는데, 그때
  첫 읽기가 아직 끝나지 않아 데이터가 undefined 다.
- **inline 이 굶는 까닭.** 다시 그릴 때마다 함수가 새것이라 효과가 다시 돌며 타이머를 지우고 3초를 새로 건다. 1c inline 의
  규칙이 다시 그린 시각마다 불린 것(20번)이 효과가 다시 돈 표시이고, stable 과 state 는 0번이었다. 1a inline 이 다시 그리기가
  읽기 직후에만 나는 장면에서 3초마다 돈 것이 "inline 은 다른 까닭으로 깨진다"는 해석을 거른다.
- **가린 동안 읽지 않는 것.** 2a 에서 틱은 3초마다 돌며 가려짐을 읽었고(사슬이 살아 있다) 읽기만 없었다. 2b 대조는 같은
  장면에서 가려짐만 무시하면 틱마다 읽는다는 것을 보인다. inline 도 같았다(2a inline). 가린 동안에는 읽기가 없어 다시
  그려지지 않으므로 inline 함수가 새로 지어지지 않고, 그래서 stable 과 같은 길이라고 읽는다.
- **돌아온 순간의 읽기는 `revalidateOnFocus` 의 몫이다.** 2c 대조(거짓)에서는 돌아온 순간 읽지 않았다. 2d 에서 읽지 않은
  것은 포커스 다시 읽기의 5초 간격(`focusThrottleInterval` 기본값 5000, `config-context-ext53wcz.mjs` 578줄) 안이라서다.
  2e 대조(0)가 같은 시각에 읽었다. 이 간격은 마운트 시각과 마지막 포커스 읽기에서 센다(`use-swr-emll9s78.mjs` 539~551줄).
  2d 는 그 가운데 마운트 시각 쪽만 보인다. 마지막 포커스 읽기 쪽은 2f 가 보인다. 22초의 돌아옴은 마운트에서 5초를 넘겨
  읽었고, 그 3초 뒤인 25초의 돌아옴은 읽지 않았다. 2g 대조(0)는 같은 시각에 두 번 다 읽어, 25초에 읽지 않은 것이 이
  간격의 몫이라는 해석의 양성 대조다. 23초에 가린 순간 2g 는 visibilityState 를 읽었고 2f 는 읽지 않았다. 549줄의 조건이
  `now > nextFocusRevalidatedAt` 을 `isActive()` 보다 먼저 보므로, 2f 의 23초가 22초 읽기에서 센 간격 안이었다는 표시다.
  "25초 틱이 돌아옴과 같은 ms 에 hidden 으로 돌아 읽기를 막았다"는 해석은 2g 도 같은 25초 틱(hidden 읽기 25초)을 지나고
  읽었으므로 서지 않는다. 그래서 명세가 처음 적은 "앞선 돌아옴에서 5초 안이면 곧바로 읽지 않는다"는 정확히는 "앞서 돌아와
  읽은 때(또는 마운트)에서 5초 안"이고, 명세는 이 결과로 그 문장을 고쳤다. 앞선 돌아옴이 읽지 않았으면 그것은 간격을 새로 세지 않는다(550줄의 설정이 읽을 때만
  난다, 코드를 읽었다. 그 장면은 재지 않았다).
- **돌아와 읽은 뒤의 첫 틱이 읽지 않은 것(2a 의 72초, 2e 의 3초)** 은 2초 중복 제거(`dedupingInterval` 기본값 2000,
  `config-context-ext53wcz.mjs` 579줄, 틱의 다시 읽기가 `WITH_DEDUPE` 다)로 읽는다. 중복 제거를 끈 대조는 재지 않아 이
  해석은 어림이다. stable 회차의 이야기다.
- **inline 에서 돌아와 읽은 뒤 틱이 돌아온 시각으로 옮겨 가는 것(2a inline 73.5초, 3b inline 33.5초).** 돌아온 순간의
  읽기로 `isValidating` 이 바뀌어 다시 그려질 때 inline 함수가 새것이라 주기 효과가 다시 돌고, 옛 타이머를 지운 뒤
  그 시각에서 3초를 새로 걸기 때문이라고 읽는다. 표시는 돌아온 시각에 규칙이 불린 것(2a inline 70.5초 두 번, 3b inline
  30.5초 두 번. 포커스 읽기는 규칙을 부르지 않는다, 546~552줄)과 2a inline 에서 72초에 불리지 않은 것(옛 틱이 지워졌다)이다.
  같은 효과의 다시 돌기는 1c inline(다시 그린 시각마다 규칙이 불렸다, stable 은 0번)이 양성 대조다. 갈래는 2a stable 이다.
  같은 장면에서 다시 그려도 함수가 같아 효과가 돌지 않고 72초 틱이 남는다. 그래서 inline 에서는 돌아온 뒤 중복 제거로
  빠지는 틱이 없고, 다음 읽기가 돌아온 때에서 3초 뒤다. 그 뒤의 간격은 두 꼴 모두 3초이고, 정해진 구간 안의 읽은 수는
  틱의 자리에 따라 하나씩 갈렸다(2a 의 80초까지 inline 넷·stable 셋, 3b 의 45초까지 inline 다섯·stable 여섯).
- **inline 에서 규칙이 틱마다 세 번 불리는 것(3a·4a·4b inline).** 틱의 읽기가 `isValidating` 을 켰다 끄며 두 번 다시
  그리고 그때마다 효과가 다시 돌며 규칙을 부르고, 옛 사슬의 `.then(next)` 도 규칙을 부른 뒤에야 `timer !== -1` 을 보고
  타이머를 걸지 않기 때문이라고 읽는다(606~616줄, 코드를 읽었다). stable 은 한 번이다. 어느 호출이 어느 자리의 것인지는
  찍지 않아 이 나눔은 어림이다. 읽은 시각에는 영향이 없었다.
- **실패 뒤 읽지 않는 것.** 틱의 조건이 캐시에 실패가 없을 때만 읽기 때문이라고 읽는다(`!getCache().error`, 620줄). 3a 에서
  규칙이 3초마다 계속 불려(사슬이 살아 있다) 데이터는 마지막으로 성공한 것을 받았고, 새로 고침이나 돌아온 순간의 읽기가
  성공해 실패가 걷히자 다음 틱부터 마운트를 다시 하지 않고 돌았다. "실패가 사슬을 끊는다"는 해석은 서지 않는다. 앱의
  `shouldRetryOnError: false` 라 SWR 의 재시도는 없다. 재시도를 켠 갈래는 재지 않았다. inline 도 같았다(3a inline, 3c).
  실패가 난 3초에는 다시 그려져 효과가 다시 돌지만 그 뒤로는 실패가 남은 동안 읽기가 없어 다시 그려지지 않는다.
- **실패의 종류(네트워크, 401, 500).** 3c(500)와 3a inline(네트워크)의 결과가 모두 같았다. SWR 은 fetcher 가 던진 것을 그대로
  `error` 에 두고, 그 내용을 보는 자리는 `shouldRetryOnError` 가 함수일 때의 재시도 판단뿐이다(`use-swr-emll9s78.mjs` 435~464줄,
  코드를 읽었다). 앱은 그것을 끄므로 실패의 종류가 SWR 의 주기 읽기를 가르지 않는다고 읽는다. 3a·3c 가 같은 것이 그 해석과
  맞는 결과다. 다른 상태 코드(404 등)와 봉투를 실은 실패는 재지 않았고 코드 읽기로 넓힌 어림이다. 401 이 앱에서 SWR 밖의
  길을 타는 것은 아래 "재지 못한 것".
- **10분.** 4b 대조가 경계가 마지막 이벤트 시각을 따라 움직이는 것을 보인다. 경계를 지난 읽기가 하나 있는 것은 규칙이 읽기가
  끝난 뒤에만 불리고(621줄 `revalidate(...).then(next)`), 틱 자체는 규칙을 다시 묻지 않고 읽기 때문이라고 읽는다. 4d 대조는
  숫자를 데이터가 바뀔 때만 다시 정하면 새 이벤트가 없는 한 경계를 보지 못한다는 것을 보인다. inline 도 4a·4b 에서 stable 과
  같은 시각에 멈췄고 경계를 지난 읽기도 하나였다. inline 에서 다시 그릴 때 효과가 부르는 규칙도 같은 `Date.now()` 로
  판정하므로 멈추는 때가 옮겨 가지 않는다고 읽는다.
- **알림이 서는가.** SWR 은 그리는 동안 읽은 필드가 바뀔 때만 다시 그린다(앱의 `readOf` 주석이 적는 것. 코드에서는
  반환값의 getter 가 `stateDependencies` 에 읽은 필드를 적고 바뀜을 그 필드로만 견준다, `use-swr-emll9s78.mjs` 119~140줄과
  692~704줄). 데이터가 같은 값(깊은 비교로 같다)으로 오면 `data` 만 읽는 쪽은 그리지 않아 알림 조건을 다시 계산할 자리가
  없다고 읽는다. 4c 의 두 갈래는 같은 조건 함수를 쓰고 읽는 필드만 달랐고, 그리기 횟수가 590초 뒤 8번과 0번으로 갈렸다.
  inline 도 같은 8번과 0번이었다(4c inline 두 줄). `data` 만 읽는 쪽은 다시 그려지지 않으므로 inline 함수도 새로 지어지지
  않아 stable 과 같은 길이라고 읽는다.

## 재지 못한 것

- 실제 브라우저. 탭 전환, 창 최소화, 다른 창에 가려짐, 뒤로 가기 캐시, 백그라운드 탭의 타이머 늦춤, `window` 의 `focus`
  이벤트로 돌아오는 길. jsdom 의 visibilityState 를 덮고 이벤트를 쏜 흉내다.
- 실제 앱 코드(`useTrace`, `readOf`, `RunDetail`, `RunPage`)와 실제 트레이스, 실제 서버. 대역 데이터와 옮긴 `READ` 다.
- 응답 지연. 지연이 있으면 다음 틱이 응답이 끝난 뒤 3초라는 것은 621줄을 읽은 어림이다.
- 서버 시계와 브라우저 시계의 차이. 10분 판정의 마지막 이벤트 시각은 서버가 적고 지금 시각은 브라우저의 것이다.
- React StrictMode 와 개발 모드(`next dev`)에서 효과가 두 번 도는 것, 실제 브라우저의 React 스케줄링. 그리기는 100ms 씩 민
  `act` 의 끝에서 나므로 inline 과 state 의 새 타이머는 100ms 단위로 선다.
- `shouldRetryOnError: true`, `revalidateOnReconnect`, `refreshWhenOffline` 과 온·오프라인, 실행 목록의 `useSWRInfinite`.
- 401 의 앱 쪽 길. 지금 앱은 관리 요청의 401 에서 관리 토큰을 내려놓아(`orRejectAdminToken`) 키가 null 이 되고 읽기가 아예
  멈춘다(코드를 읽었다, `web/apps/admin/hooks/queries/admin/index.ts` 21~40줄과 `hooks/queries/traces/index.ts` 60~70줄,
  2026-11-24 의 docs/admin-login 브랜치). admin-login 이 로그인 상태를 쿠키로 옮기면 이 길이 바뀐다. 프로브는 SWR 층의 실패만 본다.
- 데이터가 바뀔 때만 정체성이 바뀌는 함수(지난 데이터로 memo 한 것 등)의 갈래.
