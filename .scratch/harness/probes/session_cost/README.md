# 소급 측정 프로브: 세션 비용과 사전 지표

지난 트랜스크립트로 작업 종류별 비용의 기준선과 흩어짐을 재고, 티켓을 열기 전에 알 수 있는 지표가 드러난 난이도를
맞히는지 잰다. ADR 0029 "바꾸는 절차"의 첫 단계이고 설계는 일지 2026-10-12-37의 "다음" 절 ②다. 이 결과로 결정표의
칸을 바로 바꾸지 않는다. 칸을 바꾸는 것은 같은 종류의 티켓을 레벨만 바꿔 여는 스윕이고, 이 프로브는 그 스윕에 필요한
표본 수와 판정 기준을 낸다.

범위 밖: 모델끼리의 비교. 중복을 뺀 응답의 66%가 `claude-opus-5-5`·`xhigh`라(사전 등록의 셀프 리뷰 서브에이전트가
스크래치 스크립트로 셌다, 2026-10-13) 기록만으로는 모델이나 레벨의 효과를 가를 수 없다. 브랜치마다 모델·레벨 분포는
내되 비교하지 않는다.

## 파일

| 파일 | 하는 일 |
|---|---|
| `collect.py` | 트랜스크립트, `gh`(PR의 GraphQL 한 묶음과 워크플로 실행 목록), `git`(merge-base 판본의 티켓)을 읽어 브랜치마다 한 행을 `branches.json`에 쓴다. `gh` 응답은 `cache/`(커밋하지 않는다)에 두고 다시 돌 때 치지 않는다. `--refresh`로 다시 받는다 |
| `analyze.py` | `branches.json`만 읽어 측정 표지, 양성 대조, 기준선, 사전 등록한 가설의 판정, 탐색 표를 찍는다. 사전 등록 절의 SHA-256이 `analyze.py`의 `PREREG_SHA256`과 다르면 판정하지 않는다 |
| `judge.py` | 모델 판정 실험. `plan`은 호출 수와 금액 어림만 찍고, `run --yes`가 API를 부른다. `score`가 순위와 보정을 낸다 |
| `costs.py` | 단가표와 응답 하나의 API 환산 비용. 위의 셋과 `cache_read_fit.py`가 같이 쓴다 |
| `cache_read_fit.py` | 단가표의 모델마다 캐시 읽기 배수 후보(입력의 0.025·0.05·0.1배) 가운데 어느 것이 `cost-state`의 금액과 맞는지 센다. 단가표를 공식 가격표와 Claude Code의 셈 둘에 대 보는 데 쓴다(`docs/model-selection.md`의 다시 재는 절차) |
| `branches.json` | `collect.py`의 출력. 수와 이름(브랜치, PR 제목, 티켓 경로)만 있고 프롬프트와 티켓 본문은 없다 |
| `judge_results.jsonl` | `judge.py run`의 응답. 다시 돌 때 API를 치지 않고 `score`를 낸다 |

돌리는 법(워크트리 루트에서, 트랜스크립트는 `~/.claude/projects/`):

```bash
PYTHONUTF8=1 uv run python .scratch/harness/probes/session_cost/collect.py
PYTHONUTF8=1 uv run python .scratch/harness/probes/session_cost/analyze.py
PYTHONUTF8=1 uv run python .scratch/harness/probes/session_cost/judge.py plan
PYTHONUTF8=1 uv run python .scratch/harness/probes/session_cost/cache_read_fit.py
```

`collect.py`는 `gh` 인증과 이 저장소의 원격이 든다. `judge.py run`은 `anthropic` SDK를
`uv run --with anthropic==1.7.0`으로 받고 `ANTHROPIC_API_KEY`가 든다(워크트리에서는 `--env-file ../../../.env`). 판을
고정하지 않으면 실행마다 최신 판을 받아 기록의 기준이 바뀐다. 모델 판정 실험은 `pytest`의 `llm` 마커 테스트로
두지 않았다. 통과·실패를 단언하는 테스트가 아니라 결과를 내는 측정이고, 기본 실행에서 돌지 않는다는 성질은 `run`이
`--yes` 없이는 API를 부르지 않는 것으로 갖는다.

### 자료

트랜스크립트는 `~/.claude/projects/` 아래 이름이 `C--project-agent`로 시작하는 폴더의 `*.jsonl` 전부다. 본 세션 기록은
폴더 바로 아래, 서브에이전트 기록은 `<세션>/subagents/` 아래에 있다. 아래 정의가 기대는 기록의 모양은 2026-10-12~13에
이 PC의 그 기록을 스크래치 스크립트로 훑어 손으로 본 것이다(Claude Code 2.1.237~2.1.296, 데스크톱 앱). `user`,
`assistant`, `system` 기록에는 `timestamp`, `cwd`, `gitBranch`, `sessionId`가 있다. 작업 폴더(`cwd`)가 이 저장소의 주
체크아웃 경로와 그 아래가 아닌 기록(옆 저장소 `agent-runtime-platform`·`ai-agent-platform`, 상위 폴더 `C:\project`,
카나리아가 만든 `agent-canary-*` 폴더)은 세지 않고 그 비용을 따로 적는다.

PR과 커밋은 `gh api graphql`로, 워크플로 실행은 `gh run list`로, 티켓은 `git show <커밋>:<경로>`로 읽는다.

### 비용

- 응답 하나는 `assistant` 기록을 `message.id`로 묶은 것이다. 같은 응답은 내용 블록마다 기록이 나뉘고 출력 토큰은 뒤
  조각이 크므로, 출력 토큰이 가장 큰 조각의 usage를 쓴다. 같은 `message.id`가 다른 세션 파일(포크, 옮겨진 세션)에 다시
  실려도 한 번만 센다. 모델이 `<synthetic>`인 응답은 세지 않는다.
- 응답의 API 환산 비용은 usage의 다섯 칸에 모델 단가를 곱한 합이다. 입력, 출력, 캐시 읽기, 5분 캐시 쓰기(입력 단가의
  1.25배), 1시간 캐시 쓰기(입력 단가의 2배). TTL 갈래(`cache_creation`)가 없으면 5분으로 본다. 단가는 `costs.py`의 표이고
  출처와 어림의 구분은 그 독스트링에 있다. 단가표에 없는 모델의 응답은 비용에서 빠지고 그 수를 표지로 적는다.
- 본 세션의 비용과 서브에이전트의 비용을 갈라 적는다. 서브에이전트 기록은 대부분 최종 usage가 없어 출력 토큰이 빠지므로
  (스트림 시작의 usage만 남는다) 그 비용은 낮게 잡힌다. 최종 usage가 없는 서브에이전트 응답의 수를 표지로 적는다.
- SDK로 띄운 세션(`entrypoint`가 `sdk-py`)의 비용도 따로 적는다.
- 생각 토큰은 `output_tokens_details.thinking_tokens`다. 그 칸이 없는 응답이 있어, 생각 토큰의 비율은 그 칸이 있는
  응답만으로 셈한다.
- 브랜치마다 세션 수(귀속된 본 세션 기록이 있는 세션)와 응답 수(본 세션, 서브에이전트)를 적는다.

### 귀속

- PR 브랜치는 이 저장소의 PR 가운데 하나라도 머리 브랜치(`headRefName`)로 쓴 이름이다. 브랜치에 PR이 여럿이면 마지막으로
  병합된 것(병합된 것이 없으면 마지막 것)을 그 브랜치의 PR로 본다.
- 트리거는 `user` 기록 가운데 `tool_result`가 아니고, `isMeta`가 아니고, 컴팩션 요약(`isCompactSummary`이거나 글이
  `This session is being continued`로 시작)이 아닌 것이다. 글이 `[Request interrupted`로 시작하면 중단, `origin.kind`가
  `human`이면 사람, `origin`이 다른 값이면 자동이다. `origin`이 없으면 `promptSource`나 `turnOrigin`이 `sdk`이거나 글이
  `<task-notification>`으로 시작할 때 자동, 아니면 사람이다.
- 턴은 트리거 하나부터 다음 트리거 전까지의 본 세션 기록이다. 턴 안에 PR 브랜치 기록이 있으면 그 턴 전체가 처음 나온 PR
  브랜치로 간다. 없으면(`main`, `worktree-*`, 분리 HEAD, PR이 없는 이름) 같은 세션에서 뒤에 오는 가장 가까운 턴의
  브랜치로, 그것도 없으면 앞의 가장 가까운 턴의 브랜치로 간다. 세션 전체에 PR 브랜치가 없으면 귀속되지 않는다.
- 본 세션의 응답은 그 응답의 첫 조각이 든 턴의 브랜치로 간다. 서브에이전트의 응답은 부모 세션에서 그 시각에 시작한
  가장 늦은 턴의 브랜치로 간다(그보다 이르면 첫 턴).

### 시간

- 사람 대기는 `AskUserQuestion` 조각의 시각부터 그 `tool_result`의 시각까지의 구간을 합집합으로 더한 것이다.
- 턴 시간은 트리거의 시각부터 그 턴의 마지막 기록의 시각까지에서 사람 대기를 뺀 것이다. 사람이 다음 메시지를 치기 전의
  빈 구간은 턴 사이라 들지 않는다.
- 도구 시간은 `AskUserQuestion` 밖의 `tool_use` 조각 시각부터 그 `tool_result` 시각까지의 구간을 합집합으로 더한 것이다.
  권한 확인을 기다린 시간은 가를 수 없어 여기 든다. 모델 시간은 턴 시간에서 도구 시간을 뺀 것이다.
- 본 세션 기록만 센다. 나란히 돈 세션(다른 세션, SDK 세션)의 턴 시간은 겹쳐 더해진다.

### 재작업과 사람 개입

- PR 뒤 커밋: 그 PR의 커밋 가운데 부모가 하나이고 커미터 시각(`committedDate`)이 PR이 열린 시각보다 뒤인 것. rebase와
  amend는 커미터 시각을 다시 써서 PR 앞의 커밋도 뒤로 셀 수 있다. 이 저장소는 PR 뒤에 main을 병합 커밋으로 들이므로(부모
  둘이라 빠진다) 그런 일은 드물다고 본 어림이다.
- 봇 코멘트: PR 작성자가 아닌 계정의 코멘트·리뷰·인라인 코멘트 가운데 본문이 비지 않았고 한도 알림(`rate limited`,
  `Review limit reached`, `Action not completed`)이 아닌 것.
- 심각도: 봇 코멘트 본문에서 심각도를 적은 글자의 수. `[Critical]`, `[Major]`, `[Minor]`, `[Nit]`(claude-review)과
  `🔴 Critical`, `🟠 Major`, `🟡 Minor`, `🔵 Trivial`(CodeRabbit의 `_🟡 Minor_` 모양, `Trivial`은 `Nit`으로 센다)이다.
- CI 실패: 그 브랜치에서 병합 전에 돈 `ci` 워크플로 실행 가운데 결론이 `failure`인 것. 리뷰 워크플로(`Claude Code
  Review`)는 계정 한도로도 실패해 세지 않는다.
- 재작업 점수: PR 뒤 커밋 + 봇 Critical·Major + CI 실패.
- 하네스 마찰: 오류로 끝난 도구 결과의 수, 그 가운데 훅이 막은 것(결과 글에 `hook error`나 `PreToolUse:<도구> hook`이
  든 것), 그리고 `toolDenialKind`의 종류별 수.
- 사람 개입: 사람 트리거 가운데 지시문(`다음 작업:`이 든 글)도 그 브랜치의 첫 사람 트리거(과제 진술)도 아닌 것, 중단,
  `AskUserQuestion` 호출의 합.
- 지연된 실패: 뒤에 열린 PR의 제목·본문이 `#<이 PR 번호>`를 드는 수, `diagnosing-bugs` 스킬 호출, 대기열
  (`.scratch/retro-queue.md`)에서 `#<이 PR 번호>`를 드는 행, main의 커밋 제목 가운데 `revert`나 `되돌`과 `#<이 PR 번호>`를
  함께 들고 제목 끝의 squash 번호 `(#M)`이 이 PR이 아닌 것.

### 사전 지표

- 출처: feature 브랜치는 merge-base 판본의 티켓이다. 티켓은 파일 이름이 브랜치 이름의 `feature/` 뒤와 같은
  `.scratch/<slug>/issues/<그 이름>.md`이고(`feature/01-noto-sans-mono`면 `01-noto-sans-mono.md`), merge-base는 PR 첫
  커밋의 부모다. 그 부모가 로컬에 없으면 첫 커밋의 커미터 시각 전의 마지막 `origin/main` 커밋이다. 그 밖의 브랜치는 그
  브랜치의 첫 사람 트리거 글이다. diff 크기는 결과 쪽이라 지표가 아니다.
- 수용 기준 수: `- [ ]`나 `- [x]`로 시작하는 줄(들여쓴 것 포함)의 수.
- 명령으로 닫히는 몫: 수용 기준 가운데 `테스트`, `test_`, `uv run`, `pnpm`, `pytest`, `검증 명령` 가운데 하나를 든 줄의
  비율.
- 열린 결정 수: 제목(`#`으로 시작하는 줄)에 `정할 것`이 든 절 아래, 다음 제목 전까지의 목록 항목(번호와 글머리, 들여쓴
  것 포함) 수와, 그 절 밖 본문 줄(제목 줄은 빼고)에서 정규식 `이 티켓이 \S*(짓|정하|정한|정할|고르|판정)`에 맞는 수의 합.
- 계약 접촉: 티켓 파일 이름에 `contract`가 있거나 본문에 `sdk/`, `openapi.json`, `헌법`, `docs/constitution` 가운데
  하나가 있다.
- 글자 수, 이름으로 든 층의 수(`sdk`, `core`, `channel`, `admin`, `adapters`, `http`, `server`, `main`, `web`), 이름으로
  든 파일·모듈의 수(백틱 안의 확장자 있는 경로, 서로 다른 것), Blocked by 수(`**Blocked by:**` 줄에서 첫 여는 괄호 전까지의
  두 자리 번호),
  참조 ADR 수(서로 다른 `ADR NNNN`), 제목의 동사가 조사·설계인지(첫 `# ` 줄에 `조사`, `설계`, `탐색`, `검토`, `고른다`,
  `정한다`, `측정`, `잰다` 가운데 하나), 기능의 첫 티켓인지(`01-`), 브랜치 종류.
- 브랜치 종류: `feature/`는 구현, `chore/`와 `claude/`는 하네스, `fix/`는 수정, `docs/`는 이름이 `-spec`으로 끝나면
  명세, `-tickets`로 끝나면 티켓, `design`이 들면 디자인, 그 밖은 문서다.
- 시기: 지시문(`다음 작업:`이 든 사람 트리거)이 처음 나온 시각보다 먼저 열린 PR은 이른 시기(early)로 표시한다.

### 모집단과 결과 변수

모집단은 main에 병합된 PR의 브랜치 가운데 귀속된 응답이 하나 이상인 것이다. 가설 1·2는 그 가운데 구현 브랜치 중
merge-base 판본의 티켓을 찾은 것이다. 드러난 난이도의 주된 값은 브랜치의 API 환산 비용(본 세션과 서브에이전트의 합)이다.
턴 시간, 사람 개입, 재작업 점수는 부 결과로 찍되 가설의 판정에 쓰지 않는다.

서브에이전트의 비용은 출력 토큰이 빠져 낮게 잡힌다(위 "비용"). 그래서 가설마다 같은 판정을 본 세션의 비용만으로 되풀이한다.
합으로 선 판정이 본 세션 비용으로도 서면 그대로 적고, 아니면 "서브에이전트 셈에 따라 갈린다"를 붙인다.

### 양성 대조

- 단가: 세션마다 Claude Code가 남긴 `cost-state` 기록의 모델별 토큰을 단가표로 셈해, 캐시 쓰기가 모두 5분인 값과 모두
  1시간인 값 사이에 그 기록의 `costUSD`(±1%)가 드는지 본다. $0.01 이상인 모델·세션 쌍 가운데 밖인 것이 5%를 넘으면
  단가표가 Claude Code의 셈과 다른 것으로 보고 가설을 판정하지 않는다.
- 비용의 몫: 같은 세션에서 이 프로브가 기록으로 셈한 비용을 `cost-state`의 `totalCostUSD`로 나눈 비의 십분위를 찍는다.
  `cost-state`는 서브에이전트의 최종 출력과 컴팩션까지 들고, 프로세스가 끝날 때 쓰여 다시 시작한 세션은 뒤 프로세스의
  몫만 든다. 그래서 비는 문턱 없이 찍는다.
- 턴 시간: 드물게 남은 `system` 기록 `turn_duration`(Claude Code가 잰 턴의 `durationMs`)과 그 기록이 든 턴을 이 프로브가 잰
  시간(사람 대기를 빼기 전)을 나란히 찍는다.

### 가설 1 (범위가 열렸는지)

열린 결정 수가 많을수록 비용이 크다. 판정: Spearman ρ(순위가 같으면 평균 순위)가 0.3 이상이고, 브랜치를 다시 뽑는
부트스트랩(2,000회, `random.Random(0)`, 정렬한 값의 5번째와 95번째 백분위)의 90% 구간 아래 끝이 0보다 크면 선다.
"정할 것" 절은 뒤에 쓴 티켓에만 있어 시기와 섞인다. 그래서 같은 판정을 이른 시기가 아닌 브랜치만으로 되풀이해, 거기서도
ρ가 0.2 이상이면 "선다", 전체에서만 서면 "시기와 섞여 선다"로 적는다.

### 가설 2 (계약 접촉)

계약에 닿는 티켓이 비용이 크다. 판정: 접촉 쪽 비용 중앙값을 비접촉 쪽 중앙값으로 나눈 비가 1.5 이상이고, 두 무리를 따로
다시 뽑는 부트스트랩(2,000회, `random.Random(0)`)의 90% 구간 아래 끝이 1보다 크면 선다. 무리마다 5개 이상이어야 판정한다.

### 판정하지 않는 조건

아래 가운데 하나라도 맞으면 가설을 판정하지 않고 "결론 없음"을 찍는다.

- 이 저장소 기록의 비용 가운데 어느 브랜치에도 귀속되지 않은 몫이 20%를 넘는다.
- 분석 창(이 저장소의 첫 기록 이후에 열린 PR)의 병합된 PR 가운데 귀속된 응답이 없는 것이 20%를 넘는다.
- 가설의 표본이 20보다 적다(가설 2는 무리마다 5보다 적어도).
- 위 "양성 대조"의 단가 대조가 5%를 넘는다.

PR을 찾지 못한 브랜치 이름 가운데 `main`, `worktree-*`, `HEAD`(분리 HEAD)가 아닌 것과 그 기록 수는 판정 조건이 아니라

### 스윕의 판정 기준

이 프로브가 아니라 ④(결정표 갱신)의 스윕이 쓴다.

- 작업 종류 k는 위의 브랜치 종류다. 기준 갈래는 그 종류의 지금 결정표 칸이고, 비교 갈래는 모델이나 레벨만 바꾼 칸이다.
- 표본 수: 이 프로브가 낸 종류 k의 로그 비용 표준편차를 σ_k라 할 때 한 갈래에 n_k = ⌈2·(1.645 + 0.842)²·σ_k² / δ²⌉,
  δ = ln(1/0.7). 기하평균 비용 30% 감소를 한쪽 유의수준 0.05, 검정력 0.8로 가르는 수다. 한 갈래라도 n_k에 못 미치면
  판정하지 않고 칸을 둔다. 병합된 브랜치가 셋보다 적어 σ_k를 셀 수 없는 종류는 스윕하지 않는다.
- 비용 비는 비교 갈래 대 기준 갈래의 기하평균 비용 비이고, 두 갈래를 따로 다시 뽑는 부트스트랩(2,000회,
  `random.Random(0)`)의 90% 구간을 함께 낸다.
- 레벨을 내린다(비교 갈래가 낮은 칸): 비용 비 구간의 위 끝이 1보다 작고, 비교 갈래의 재작업 점수 중앙값이 기준 갈래
  재작업 점수의 3사분위 이하이고, 비교 갈래의 사람 개입 중앙값이 기준 갈래 중앙값 + 1 이하다.
- 레벨을 올릴 근거가 선다(비교 갈래가 높은 칸): 비교 갈래의 재작업 점수 중앙값이 기준 갈래 재작업 점수의 1사분위 이하이고,
  비교 갈래의 사람 개입 중앙값이 기준 갈래 중앙값 이하다. 비용 비를 함께 적고 올릴지는 사용자가 정한다. n_k는 비용으로 정한
  수라 품질 쪽 비교에는 검정력을 보장하지 않는다.
- 둘 다 아니면 칸을 그대로 두고 결과를 ADR 0029 이력에 적는다.

### 모델 판정 실험

돌리기 전에 호출 수와 금액을 사용자에게 보고하고 승인을 받는다(`judge.py plan`).

- 판정자: `claude-opus-5-5`, 노력 `high`, 대체 모델(fallbacks) 없음. 다른 모델이 답하면 판정자가 섞인다. 판정자는 저장소를
  읽지 않고 셋만 본다. 실험을 돌리는 체크아웃의 `CLAUDE.md`(그것이 `@`로 싣는 `docs/constitution/principles.md`를 펼친
  것), 기준 티켓 열 개(merge-base 판본의 본문과 실제 결과), 대상 티켓 하나(merge-base 판본).
- 기준 티켓: 가설의 모집단을 비용 순(같으면 브랜치 이름 순)으로 세워 i = 0..9마다 round(i·(N−1)/9)번째를 고른 열 개.
  평가에서 뺀다.
- 묻는 것: 턴 수, 바뀐 파일 수, 턴 시간 합(분)의 80% 범위(아래 끝, 위 끝), 축별 1~3 채점(모호함, 범위, 새로움, 검증의
  어려움, 계약 접촉)과 축마다 이유 한 줄. 같은 대상을 세 번 묻고 값마다 세 번의 중앙값을 쓴다. 세 번이 모두 측정(멈춤
  까닭이 `end_turn`이고 답이 스키마에 맞는 JSON)인 대상만 센다.
- 주된 지표: 시간 범위의 가운데 값(아래 끝과 위 끝의 기하평균, 0.1분 아래는 0.1로)과 실제 턴 시간 합의 Spearman ρ. 비용이
  아니라 시간인 까닭은 판정자가 금액의 눈금을 모르고, 기준 티켓의 결과로 보여 줄 수 있는 단위가 턴 수·파일 수·시간이기
  때문이다. 쓸모 있다고 보는 기준은 셋이다. ρ ≥ 0.4, 대상을 다시 뽑는 부트스트랩(2,000회, `random.Random(0)`)의 90% 구간
  아래 끝이 0보다 크다, 같은 대상에서 위 "사전 지표" 하나하나와 실제 턴 시간 합의 |ρ| 가운데 가장 큰 것보다 0.1 이상 크다.
  대상이 20보다 적으면 판정하지 않는다.
- 보정: 80% 범위가 실제 값을 담은 비율이 0.6 이상 0.95 이하면 보정됐다고 본다. 턴 수, 파일 수, 시간을 따로 본다.
- 축 다섯의 합과 비용의 ρ는 탐색으로 찍는다.
- "못 맞힌다"는 결과는 맥락 없이 티켓만 본 판정자가 못 맞힌다는 뜻이다. 맥락을 가진 실제 세션이 못 맞힌다는 뜻이 아니다.

### 2026-10-13 캐시 읽기 단가 대조

지표 문서(`docs/model-selection.md`)를 쓰며 `costs.py`의 단가를 공식 가격표(`curl`로 받은
`platform.claude.com/docs/en/about-claude/pricing.md`, 2026-10-13)와 대 보니 `claude-sonnet-5-5`의 캐시 읽기가 달랐다.
가격표는 입력의 0.05배($0.10)이고 `costs.py`는 0.1배($0.20)다. 나머지 모델은 같았다. 어느 쪽이 Claude Code의 셈인지
`cache_read_fit.py`로 갈랐다. 트랜스크립트는 첫 실행과 같은 폴더를 이날 다시 읽었고 `cost-state`가 있는 세션은 679개, 모델·세션
쌍은 743개로 첫 실행의 단가 대조와 같다. 이 프로브는 시간 창 없이 그때의 트랜스크립트를 읽어, 기록이 쌓이면 아래 수가 바뀐다.
다시 내는 것은 어느 배수가 맞는지의 판정이다. 같은 날 셀프 리뷰 뒤에 다시 돌리자 세션 687개, `claude-sonnet-5-5` 558쌍 가운데
0.1배 안이 557이었다. 판정 칸(쌍의 95% 이상을 담는 배수가 하나뿐인지)과 종료 코드는 셀프 리뷰 뒤에 더했고, 그 판에서 여섯 모델 모두
"표와 같다"로 0으로 끝났다.

| 모델 | 쌍 | 표의 배수 | 0.025배 안 | 0.05배 안 | 0.1배 안 | 캐시 읽기 몫 중앙값 |
|---|---|---|---|---|---|---|
| claude-opus-5-5 | 92 | 0.05 | 1 | 92 | 0 | 0.571 |
| claude-fable-5-1 | 12 | 0.025 | 12 | 2 | 2 | 0.256 |
| claude-sonnet-5-5 | 550 | 0.1 | 97 | 234 | 549 | 0.049 |
| claude-opus-5 | 1 | 0.1 | 0 | 0 | 1 | 0.871 |
| claude-sonnet-5 | 29 | 0.1 | 12 | 20 | 29 | 0.292 |
| claude-haiku-4-5 | 59 | 0.1 | 19 | 22 | 59 | 0.088 |

Claude Code는 `claude-sonnet-5-5`의 캐시 읽기를 0.1배로 셈했다(550쌍 가운데 549, 0.05배면 234). 그래서 `costs.py`는 Claude
Code의 셈과 맞고 공식 가격표와는 다르다. 첫 실행의 결론은 바뀌지 않는다고 본다. 이 저장소의 `claude-sonnet-5-5` 쌍은 캐시 읽기
몫의 중앙값이 0.049라(서브에이전트와 카나리아로 보인다, 어림) 단가를 반으로 내리면 중앙값의 쌍에서 그 금액이 약 2.5% 준다(중앙값에서
셈한 값). 기준선 표는 본 세션 비용의 90% 이상이 `claude-opus-5-5`인 브랜치라 닿지 않는다. 반대로 본 세션 전체를 Sonnet 5.5로
돌리는 스윕에서는 캐시 읽기 몫이 `claude-opus-5-5`(0.571)와 비슷하다면 어느 단가를 쓰느냐로 그 갈래의 비용이 약 3할 갈린다(어림).
웹 검색 요금(건당 $0.01)을 빼고 대 보니 첫 실행에서 두 끝 밖이던 `claude-haiku-4-5` 둘이 안으로 들었다. 표의 배수에서 밖으로
남은 쌍은 `claude-sonnet-5-5` 하나다.
