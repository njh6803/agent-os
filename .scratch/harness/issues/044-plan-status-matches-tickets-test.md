# 044: `plan.md` 기능 행의 상태가 티켓의 `Status:`와 어긋나는 것을 저장소 상태 시험으로 막는다

**What to build:** `.scratch/plan.md`의 기능 행 상태(`todo`·`in-progress`·`done`)는 그 기능의 `.scratch/<slug>/issues/` 티켓이 병합될 때 사람이 손으로 바꾼다(`docs/agents/issue-tracker.md` 전체 계획 절). 이 규약이 문서에만 있어 세 번 어겨졌다. 기능의 첫 티켓(design-card-build 03, PR #430)이 병합됐는데 행이 `todo`로 남았고(둘째 티켓의 PR #433이 병합 전에 고쳤다), 첫 티켓 둘(skill-plugin 01 PR #462, 02 PR #461)이 병합됐는데 행이 `todo`로 남아 셋째 티켓의 PR #463이 고쳤고, 마지막 티켓(skill-plugin 04, PR #465)이 병합됐는데 행이 `in-progress`로 남아 043이 고쳤다. pytest 저장소 상태 시험 하나(`tests/test_plan_status.py`)로 이 어긋남들을 막는다.

시험은 `plan.md` 표의 행마다 그 기능 폴더의 티켓 `**Status:**` 줄을 읽어 두 가지를 본다. 하나라도 `done`인 티켓이 있으면 행이 `todo`가 아니다. 티켓이 모두 닫혔고(`done` 또는 `wontfix`) `done`이 하나 이상이면 행이 `done`이다. 반대 방향(행이 티켓보다 앞선다, `done` 행에 열린 티켓이 있다)은 보지 않는다. `docs/agents/issue-tracker.md`는 기능 밖에서 제품 코드를 고치는 일을 그 기능 폴더의 새 티켓으로 더하면서 행은 `done` 그대로 두라고 하므로, `done` 행의 열린 티켓은 정상이다. 시험은 먼저 main의 지금 상태가 지나는지 본다. 지나지 않으면 어긋난 행을 이 PR이 함께 고친다. 읽은 범위가 비면 실패하게 한다(`.claude/rules/tests.md`, 대기열 98). 변이 테스트는 첫 티켓 병합 뒤의 `todo`와 마지막 티켓 병합 뒤의 `in-progress`를 각각 잡는지 본다.

대기열 546은 이 PR이 닫는다. 그 행의 3회차 셈은 PR #468의 claude-review가 느슨하다고 짚었다(546 자체의 사건은 첫 티켓 병합 뒤 `todo`가 남은 것이라 마지막 티켓 병합 뒤 `in-progress`가 남은 이번 사건과 모양이 다르고, 만료한 104·399의 체인을 이어 3회차로 센 근거가 행에 한 줄뿐이다). 행을 닫을 때 그 셈을 다시 판정해 닫힘 칸에 적는다.
