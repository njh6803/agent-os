# 025: 병합 뒤 원격 정리가 지우는 대신 원격에 브랜치가 남았는지 본다

**What to build:** `next-session`의 "워크트리에서 병합할 때" 3(원격 정리)은 병합 뒤 `git push origin --delete <브랜치>`로 원격 브랜치를 지운다. 자동 모드 분류기가 그 명령을 다섯 번 거부해 원격 브랜치가 남았고(일지 2026-10-23-49, 2026-10-27-02·04·07·09), 사용자가 고른 대로 2026-10-27에 저장소의 병합 뒤 브랜치 자동 삭제를 켰다(`delete_branch_on_merge: true`, 일지 2026-10-27-12). 이제 그 명령은 지울 브랜치가 없다. 2026-10-28 PR #408 병합 뒤 친 `git push origin --delete feature/11-pilot-and-prereg`가 "remote ref does not exist"로 끝났다(이 티켓을 연 지시문의 "이어받을 상태"). 3을 `git fetch --prune origin` 뒤 `git ls-remote --heads origin <브랜치>`의 출력이 비었는지 보는 것으로 바꾸고, 절의 끝 줄도 그 출력으로 판정하게 고친다. 출력이 비지 않은 갈래(자동 삭제가 돌지 않았다)도 적는다. 같은 명령을 병합 절차로 적은 다른 살아 있는 자리를 grep해 함께 고친다.

## Comments

- 2026-10-28 셀프 리뷰: 두 축이 원격에 닿지 못한 `ls-remote`도 종료 128에 출력이 비어 "없음"으로 읽힌다고 짚었다. 그래서 수용 기준 1·2의 "출력이 비었는지"를 `git ls-remote --exit-code --heads origin <브랜치>`의 종료 코드로 판정하게 했다. 2는 출력 없이 맞는 ref가 없을 때이고 0은 줄이 나올 때이며, 그 밖(접속 실패 128)은 판정하지 못한 것이다. 출력이 비었는지를 본다는 기준의 뜻은 2가 맡고, 실패를 가르는 몫이 더해졌다. 기준 4는 이 워크트리에서 `--exit-code`를 붙여 다시 쳐서 병합된 `feature/11-pilot-and-prereg`가 종료 2(출력 없음), `main`이 종료 0과 한 줄이었다(일지 2026-10-29-01 셀프 리뷰).
- 2026-10-28 PR 직전 리뷰: `bug-perf-review`가 `ls-remote`의 패턴이 이름 꼬리로 맞대 `old/<브랜치>`도 잡아 거짓 `원격 브랜치 남음`을 낸다고 짚었다(임시 저장소에서 손으로 봤다). 그래서 3의 명령을 `git ls-remote --exit-code --heads origin refs/heads/<브랜치>`로 바꿨다. 기준 1·4의 명령은 이 패턴으로 읽는다. 이 워크트리에서 다시 쳐서 `refs/heads/feature/11-pilot-and-prereg`가 종료 2(출력 없음), `refs/heads/main`이 종료 0과 한 줄이었다. 같은 리뷰가 낸 나머지 셋(`fetch` 실패 뒤 낡은 `origin/main`, PR 상태를 읽지 못하거나 `CLOSED`인 갈래, 지운 뒤 다시 볼 때의 `fetch --prune`)도 3에 반영했다(일지 2026-10-29-01 PR 직전 리뷰).
