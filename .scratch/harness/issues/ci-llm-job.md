# ci-llm-job: main으로 가는 PR과 main 푸시에서 LLM 호출 테스트를 CI로 돌린다

**What to build:** ADR 0043 Consequences "CI 분담"은 main PR(dev→main, hotfix→main)과 main 푸시에 LLM 테스트(`-m llm`, `-m llm_widget`)를 더한다고 정했다. 지금 `.github/workflows/ci.yml`의 머리 주석(6행)은 LLM 호출 테스트를 CI에서 돌리지 않고 손으로 돌린다고 적는다. 사용자는 API 키 시크릿을 넣기로 했고, 잡은 이 후속 티켓에서 만들기로 골랐다(`dev-branch-create`의 사람의 몫 (다), 일지 2026-11-12-1148-dev-branch-create). 이 티켓이 그 잡을 짓는다.

- base가 main인 PR과 main 푸시에서만 LLM을 부르는 잡 하나를 더한다. dev로 가는 티켓 PR에서는 LLM을 부르지 않는다. `verify`는 건너뛴 잡도 빨강으로 보므로(`ci.yml` 331~333행의 주석), 잡 수준 `if`로 건너뛰게 하고 `needs`에 이으면 dev로 가는 PR이 모두 빨개진다. `needs`에 없는 잡도 `verify`가 빨강으로 본다(334~338행의 주석. 일부러 밖에 둘 잡은 그 차집합의 예외에 이름을 더한다). 그래서 `ticket` 잡처럼 잡은 늘 돌고 대상이 아니면 한 줄을 찍고 지나게 하거나(305행의 주석), 참고 모드 동안은 `needs`에 잇지 않고 차집합의 예외에 더하는 것 가운데 하나를 고른다.
- 키는 그 잡에만 준다(잡 수준 `env`나 단계 수준 `env`. 워크플로 수준에 두지 않는다). 포크 PR에서는 시크릿이 오지 않으므로 그때의 갈래를 정한다.
- 처음에는 막지 않는 참고 모드로 돌려 결과가 얼마나 흔들리는지 먼저 잰다. 웹 조사에서 나온 권고이고(`dev-branch-create` 일지의 "사람의 몫 (가)~(라)"에 든 (다)의 설명, 웹 검색 결과의 요약), 막는 게이트로 바꾸는 때는 잰 뒤에 사용자에게 묻는다.
- `-m llm_widget`·`-m llm_portal`처럼 브라우저가 드는 표지는 `e2e-widget`·`e2e-portal` 잡의 환경 변수(`AGENT_OS_WIDGET_LLM`, `AGENT_OS_PORTAL_LLM`)와 얽힌다. 어느 표지까지 이 잡에 싣는지 정한다.

**대기열:** 없음

**Status:** done

**막는 티켓:** 없다. 시크릿이 저장소에 없으면 잡이 실제로 도는지 볼 수 없으니, 시작할 때 사용자에게 시크릿을 넣었는지 먼저 묻는다(이 세션은 키를 다루지 않는다).

## 수용 기준

- [x] 시크릿이 저장소에 있는지 사용자에게 확인받았다(값은 보지 않는다)
- [x] base가 main인 PR과 main 푸시에서만 LLM 테스트 잡이 돌고, dev로 가는 PR에서는 건너뛴다
- [x] 키가 그 잡에만 주어진다
- [x] 첫 판은 참고 모드이고, 막는 게이트로 바꾸는 조건을 티켓 끝에 적었다
- [x] `ci.yml` 머리 주석의 LLM 호출 테스트를 돌리지 않는다는 문장(6행)이 사실에 맞게 바뀌었다
- [x] 참고 모드에서도 dev로 가는 티켓 PR의 `verify`가 이 잡 때문에 빨개지지 않는다
- [x] 검증 명령이 모두 초록이다

## 결과

- **시크릿.** 사용자가 이 세션의 선택 화면에서 저장소 Actions 시크릿 `ANTHROPIC_API_KEY`를 넣었다고 답했다. 값은 보지 않았고 GitHub에서 목록으로 확인하지도 않았다. 이름은 테스트가 읽는 환경 변수와 같다(`tests/core/test_model.py`, `tests/test_main.py`, `tests/test_widget_llm.py`가 `ANTHROPIC_API_KEY`를 `os.environ`에서 본다).
- **잡 모양.** `ci.yml`의 `llm` 잡이다. 조건은 잡 수준 `if`이고, main 푸시이거나 base가 main이면서 머리 저장소가 이 저장소인 PR일 때 돈다. 포크 PR은 시크릿이 오지 않아 건너뛴다. 키는 pytest 스텝 둘에만 `env`로 주고(YAML을 읽어 `env`가 든 스텝이 마지막 둘뿐인 것을 봤다) 워크플로 수준에는 없다. 스텝 둘은 `-m llm`, `-m llm_widget`이고 둘째는 첫째가 실패해도 돈다.
- **싣는 표지.** ADR 0043이 꼽은 `llm`과 `llm_widget`만 싣는다. `llm_portal`은 ADR이 꼽지 않아 뺐다. 더하려면 `llm` 잡에 스텝 하나(`uv run pytest -m llm_portal -q`)를 붙이면 된다. 브라우저 설치는 이미 있다.
- **verify.** `llm`은 `needs`에 잇지 않고 `verify`의 차집합 예외(`jq`의 `["verify", "llm"]`)에 이름을 더했다. dev로 가는 PR에서 잡이 건너뛰어져도 `verify`는 빨개지지 않는다. 잡이 빨개도 `verify`는 초록이다.
- **돌려 보지 못한 것.** 이 티켓의 PR은 dev로 가므로 `llm` 잡은 이 PR에서 건너뛴다. 잡이 실제로 키를 읽고 모델을 부르는지, 건너뛴 잡이 `verify`의 잡 목록 조회에 어떻게 보이는지는 첫 dev→main PR이나 main 푸시 실행에서야 본다. 로컬에서는 zizmor(지적 0)와 `tests/tools/test_zizmor_gate.py`(25개 통과)만 돌렸다. `timeout-minutes: 25`는 재지 않은 어림이다.

## 막는 게이트로 바꾸는 조건

사용자가 아래를 보고 승인한 뒤에만 `llm`을 `verify`의 `needs`로 옮긴다(그때 차집합 예외에서 `llm`을 뺀다). 옮기기 전에 `llm`이 대상이 아닌 실행(dev로 가는 PR, 포크 PR)에서 건너뛰어도 `verify`가 빨개지지 않게 먼저 바꾼다. `ticket` 잡처럼 잡은 늘 돌고 대상이 아니면 한 줄을 찍고 성공으로 지나게 하거나, `verify`가 그 실행의 `llm` 건너뜀만 허용하고 다른 실패는 계속 거부하게 고친다. `verify`는 건너뛴 잡을 빨강으로 보므로 이 바꿈 없이 `needs`로만 옮기면 dev로 가는 PR이 모두 빨개진다. 참고 모드의 실행 기록은 GitHub Actions의 `ci` 워크플로에서 `llm` 잡을 걸러 읽는다.

1. `llm` 잡이 든 실행이 열 번 쌓였다(dev→main PR, hotfix→main PR, main 푸시를 합쳐). 이 열 번은 이 세션이 정한 어림이고 잰 값이 아니다. `ci` 워크플로의 `concurrency`가 `cancel-in-progress: true`라 같은 PR에 푸시가 이어지면 도는 중인 `llm` 실행이 취소되니(`ci.yml`을 읽었다), 취소된 실행은 세지 않는다. 열 번이 오래 걸리면 사용자가 문턱을 낮춘다.
2. 그 열 번에서 실패 원인을 세 갈래로 나눠 적었다. 키·권한 문제, 네트워크·서비스 일시 장애, 모델 답의 흔들림(같은 코드에서 초록과 빨강이 갈린 경우)이다. 앞의 둘은 고치고 다시 센다. 셋째가 한 번이라도 있으면 막기 전에 그 시험을 고치거나 재시도를 정한다.
3. 실행 시간과 토큰 합계(`LLM 토큰 합계 …` 줄)를 보고 비용이 감당할 만하다고 사용자가 답했다.
4. 막으면 키 문제 때문에 dev→main 출시가 서는 일이 생긴다. 그때 키를 바꿀 사람과 절차를 정했다.
