# server-login-requirement: 도구 서버가 로그인이 필요하다고 응답하면 그것을 로그인 요구로 받아, 익명인 사람에게 로그인 안내를 보인다.
**슬라이스:** 10
**Blocked by:** step-up-login, principal-propagation, pilot-release

도구 서버의 응답이 일으키는 로그인 요구. step-up-login은 로그인 요구(`CONTEXT.md`)의 계기를 운영자가 규칙 파일에 적는 것 하나로 냈다(ADR 0060). 설계 인터뷰에서 사용자가 계기 셋을 모두 두기를 물었고 "운영자 지정만 0.1 판, 나머지 둘은 뒤 판"을 골라 이 행이 섰다(일지 2026-11-12-1937 "계기의 범위"). principal-propagation을 기다리는 까닭은 도구 서버가 질문한 사람이 익명인지 알아야 이 응답을 낼 수 있기 때문이다. 그 기능 계획이 "익명 주체인지가 형식에 실려야 한다"고 적었고, 익명 주체의 요청을 거부하기로 한 서버(기억 서버 ADR 0054, 조회 서버 ADR 0055)가 그 거부를 최종 사용자의 화면에 어떻게 알리는지는 아직 정해지지 않았다(같은 일지 "이 저장소의 계획과 지금 구조"). 지금 구조에서는 도구의 실패가 모델에 돌아가 답 글로만 화면에 닿는다. MCP 2025-11-25 규격에는 서버가 주소에서 무언가를 마쳐야 요청을 처리할 수 있다고 알리는 오류 `URLElicitationRequiredError`가 있다(인터뷰가 받아 둔 규격 사본에서 손으로 봤다. 이 저장소의 MCP 클라이언트가 그것을 다루는지는 보지 않았다). 화면과 로그인 흐름은 step-up-login의 것을 그대로 쓴다(ADR 0060의 의도이고 지어 보지 않았다). 설계 인터뷰가 먼저 볼 것: 서버의 어떤 응답을 로그인 요구로 읽는지(규격의 오류, 약속한 오류 코드, principal-propagation이 정할 거부 코드)와 믿지 않는 서버(mcp-trust)의 그 응답을 받아들일지, 그 응답이 실행을 끝내는지 모델에 돌아가는지, 도구가 이미 불린 뒤라는 점(운영자의 로그인 요구는 부르기 전에 막는다), 서버가 알린 주소를 화면에 그대로 쓸지. 수락: 익명 주체의 요청에 로그인이 필요하다고 응답하는 시험용 도구 서버를 둔 시험 환경에서, 둘 다 사이트의 익명인 사람에게 로그인 안내가 뜨고 로그인한 뒤 같은 질문에 답이 나온다
