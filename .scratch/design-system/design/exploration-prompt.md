# design-system 탐색 프롬프트

Claude Design(claude.ai/design)에서 디자인 시스템의 겉모습 방향을 고를 때 붙여 넣는 시작 프롬프트다. 이 단계는 값(색, 글꼴, 모서리, 간격)의 방향을 고르는 일이고, 디자인 시스템 프로젝트는 만들지 않는다. 디자인 시스템은 코드가 생긴 뒤 `/design-sync`가 올린다(ADR 0025).

프롬프트에 든 것은 세 가지다. **결정**은 ADR 0026(반응형은 첫째, 테마와 모드는 둘째, 색 토큰의 두 층은 셋째 2026-10-06 이력)과 ADR 0025가 정한 것이고, 화면 문구의 말은 `CONTEXT.md`와 관리 화면의 지금 문구(켜짐, 꺼짐)에서 왔다. **이 프롬프트의 제안**은 ADR이 "바탕, 글자, 강조, 위험 등"까지만 적은 색 쓰임새의 목록, 버튼과 알림의 변형, 화면의 결, 3단계의 패턴 목록처럼 고르는 데 필요해서 더한 것이고 명세가 다시 정한다. **탐색용 가정**은 폭과 굵기 수 같은 값이고, 명세나 그 앱의 기능이 다시 정한다(위젯 자리의 폭은 web-widget이 정한다).

## 하는 법

1. Claude Design의 첫 화면에서 새 프로젝트를 시작한다. Design systems 탭에서 만들지 않는다. 입력창 아래의 Design system은 `None`으로 두고, 템플릿은 Color + type pairing을 고른다. 이 템플릿은 긴 글을 받지 않고 짧은 질문 양식을 먼저 띄운다(긴 글을 붙이면 잘렸다는 안내가 나왔다, 2026-10-06 사용자의 화면 갈무리).
2. 양식의 칸마다 아래 "1. 방향 고르기"의 답을 넣고 보낸다. 칸의 이름은 영어지만 답은 한국어로 써도 되고, 결과도 한국어로 나왔다(같은 날 사용자가 써 봤다. 그때의 첫 답은 테마를 라이트·다크 둘로 적었고, 둘째 이력에 맞춰 고쳤다). 나온 방향 가운데 살릴 것을 고른다. 2026-10-06에는 다섯이 나왔고 사용자가 다섯 모두를 테마로 살리기로 했다(ADR 0026의 둘째 2026-10-06 이력). 고치고 싶은 것은 대화로 더 요청한다.
3. 같은 프로젝트의 대화에 "2. 다섯 테마로 그리기"를 넣어 공통 크기, 테마 표, 컴포넌트 표본, 대략의 화면을 받는다. 넣기 전에 글 끝의 `<기본 테마 이름>`을 다섯 가운데 고른 하나의 이름으로 바꾼다. 그 템플릿에서 화면을 그리기 어색하면 UI mockups 템플릿으로 새 프로젝트를 시작해, 다섯 테마의 색과 글꼴을 함께 붙여 넣고 2를 넣는다. 2단계가 이 템플릿에서 어떻게 도는지는 아직 확인하지 않았다.
4. 같은 대화에 "3. 디자인 시스템 문서처럼 보강하기"를 넣어 기초, 컴포넌트마다의 상태 표·해부도·쓰는 법, 패턴, 디자인 토큰 목록과 props 표의 초안을 받는다. 3단계가 어떻게 도는지도 아직 확인하지 않았다.
5. 테마 표, 공통 크기 표, 컴포넌트 표본, 화면, 보강한 문서를 Claude Design이 내보내는 형식으로 내려받는다. 어떤 형식이 되는지는 확인하지 않았다. 내보낸 파일을 둘 자리는 6에서 고르는 길이 정한다.
6. 내보낸 파일을 이 폴더에 넣고, 이 폴더의 `README.md` 표에 파일마다 한 줄을 적는다. 이 탐색의 칸은 이렇다. 근거 문서는 `.scratch/design-system/design/exploration-prompt.md`와 `docs/adr/0026-design-system-is-one-package-judged-by-storybook.md`이다. 기준 커밋은 그 둘을 마지막으로 바꾼 main의 커밋(`git log -1 --format=%h origin/main -- <근거 문서 둘>`)이고, 병합되기 전의 브랜치에서 글을 붙여 넣었으면 그 브랜치가 main에 병합된 뒤에 같은 명령으로 구한다. 동기화한 커밋은 "없음"이다. 칸의 뜻과 파일을 넣는 자리의 규약은 `docs/agents/issue-tracker.md`의 화면 디자인 절이다. 두 길 가운데 하나를 고른다.
   - **직접 적는다.** 그것을 커밋할 세션이 이미 있을 때의 길이다. 파일을 그 세션의 작업 폴더(워크트리면 `.claude/worktrees/<이름>/`) 안의 이 폴더에 넣고, 표의 줄도 그 폴더의 `README.md`에 적는다. 그런 세션이 아직 없으면 맡기는 길로 간다.
   - **다음 명세 세션에 맡긴다.** 내보낸 파일은 저장소 밖(내려받기 폴더 등)에 그대로 두고, 명세 세션에 그 경로와 붙여 넣은 날을 알린다. 그 세션이 파일을 이 폴더로 옮기고 줄을 채워 자기 커밋에 싣는다. 기준 커밋은 `git log -1 --format=%h --until="<붙여 넣은 날> 23:59" origin/main -- <근거 문서 둘>`로 구한다. `--until`은 `--` 앞에 둔다. 뒤에 두면 경로로 읽혀 날짜가 조용히 빠진다(2026-10-06에 `--until="2026-10-05 23:59"`를 두 자리에 두고 손으로 돌려 봤다. 앞에 두면 빈 출력, 뒤에 두면 그날 이후의 커밋이 나왔다). 붙여 넣은 순간을 알 수 없으므로 칸에 "(어림)"을 붙인다.

## 1. 방향 고르기

Color + type pairing 템플릿의 양식 칸마다 넣는 답이다. 글 칸은 400자까지 받는다(양식의 글자 수 표시, 사용자의 화면 갈무리).

What are the pairings for?

```text
Agent OS의 디자인 시스템. 앱 둘이 하나를 나눠 쓴다. ① 위젯: 남의 웹사이트 안에 들어가는 작은 창. 최종 사용자가 에이전트에게 요청을 보내고 출력을 받으며, 도구를 쓰기 전에 승인을 물으면 허가하거나 사유를 붙여 거부한다. ② 관리 화면: 운영자가 플러그인을 켜고 끄고, 실행 목록과 상세를 본다. 테마마다 라이트·다크 모드. 화면 문구는 한국어.
```

Start from an existing design system?: 비워 둔다.

Who's the audience?

```text
위젯은 여러 사이트의 한국어 최종 사용자(데스크톱과 모바일). 관리 화면은 에이전트를 운영하는 개발자와 운영자이고, 데스크톱과 모바일 모두에서 쓴다.
```

How many pairings?: 5(2026-10-06에는 5로 받아 다섯을 모두 살렸다. 적게 보려면 3). How divergent?: A mix. Show each pairing applied to: UI components.

Anything fixed or off-limits?

```text
답은 한국어로. 한글 글꼴은 OFL이고 저자가 동적 서브셋을 내는 것(예: Pretendard), 굵기 2~3. 색은 쓰임새 이름(바탕, 올라온 바탕, 글자, 흐린 글자, 테두리, 강조, 강조 위 글자, 위험, 경고, 성공, 정보, 포커스 링)으로 라이트·다크 두 벌, hex와 명암비를 적는다(WCAG 2.2 AA: 본문 4.5:1, 큰 글자·UI 경계·포커스 링 3:1). 길이는 모두 px. 화려함보다 오래 봐도 피곤하지 않은 도구 화면. 위젯은 남의 사이트에서 튀지 않되 정체성이 보이게.
```

## 2. 다섯 테마로 그리기

1단계의 방향을 모두 테마로 살릴 때 넣는 글이다. 방향 하나만 살릴 때는 첫 단락을 고른 방향 하나로 라이트와 다크 모드를 그려 달라는 말로 바꾸고, 2번의 테마 표와 3·4번의 나란히 보이기를 그 하나로 줄인다.

```text
앞의 다섯 안을 모두 테마로 쓴다. 테마는 색과 글꼴만 다르고, 모양(모서리, 간격, 크기 단계, 그림자의 크기를 포함한 컴포넌트 모양)과 화면 레이아웃은 다섯 테마가 함께 쓴다. 그림자의 색은 테마와 모드를 따른다. 테마마다 라이트와 다크 두 모드를 가진다. 아래를 그려 줘.

1. 공통 크기: 모든 길이는 px로 적는다(rem을 쓰지 않는다). 글자 크기 단계, 간격 단계, 모서리 둥글기, 그림자 단계, 그리고 반응의 기준 폭 후보(위젯은 창이 아니라 자기 자리의 폭에 반응하므로 그 컨테이너 크기, 관리 화면은 데스크톱과 모바일까지 반응하므로 그 화면 중단점). 기준 폭은 꼭 필요한 것만 둔다. 다섯 테마가 이 하나를 함께 쓴다.
2. 테마 표: 색은 두 층이다. 테마마다 이름, 글꼴과 굵기, 원색 토큰, 쓰임새 토큰의 대응표를 적는다. 원색 토큰은 강조, 회색, 위험·경고·성공·정보 계열마다 밝기 단계와 그 hex 값이다(단계의 수와 이름은 제안해 줘). 대응표는 라이트·다크 모드마다 쓰임새 토큰(바탕, 올라온 바탕, 글자, 흐린 글자, 테두리, 강조, 강조 위 글자, 위험, 경고, 성공, 정보, 포커스 링)이 어느 원색 토큰을 가리키는지와, 글자와 그 바탕 짝의 명암비다. 다섯 테마의 쓰임새 토큰 이름과 원색 토큰의 계열·단계 이름은 모두 같아야 한다(같은 컴포넌트에 바꿔 끼운다). 기준은 WCAG 2.2 AA다(본문 4.5:1, 큰 글자·UI 경계·의미를 싣는 아이콘·포커스 링 3:1).
3. 컴포넌트 표본: 공통 모양으로 한 번 그린다. 버튼(주, 보조, 위험), 아이콘 버튼, 글 입력(한 줄과 여러 줄), 스위치, 상태 배지(일시정지, 끝남, 실패, 결말 없음), 알림(실패, 경고, 정보), 진행 표시, 표면(카드), 선으로 그린 아이콘 몇 개. 포인터로 누르는 목표는 가로세로 24px 이상이다(WCAG 2.2의 목표 크기). 그리고 표본의 일부(주 버튼, 글 입력, 상태 배지, 알림)를 다섯 테마 × 두 모드로 바꿔 끼워 나란히 보여 줘.
4. 대략의 화면(와이어프레임 수준) 셋: 위젯의 대화(요청과 출력이 몇 번 오간 모습과 입력창), 위젯의 승인 묻기(도구 이름과 인자를 글자 그대로 보이고, 허가와 사유를 붙인 거부), 관리 화면의 실행 목록(실행마다 상태 배지). 위젯 둘은 자리 폭 320px과 400px 두 가지로, 관리 화면은 데스크톱과 모바일 두 가지로 그려 레이아웃이 어떻게 바뀌는지 보여 줘. 폭 320px에서도 가로 스크롤 없이 다시 흘러야 한다(WCAG 2.2의 리플로). 화면은 기본 테마로 그리고, 위젯의 대화 하나만 다섯 테마로 나란히 보여 줘.

지켜 줄 것:
- 화면 문구는 한국어이고 이 말을 쓴다: 실행, 요청, 출력, 대화, 승인, 허가, 거부, 일시정지, 끝남, 실패, 결말 없음, 플러그인, 켜짐, 꺼짐, 운영자. "세션", "메시지", "답변", "채팅", "진행 중"은 쓰지 않는다.
- 컴포넌트는 쓰임새 토큰만 쓰고 원색 토큰을 직접 쓰지 않는다. 테마나 모드가 바뀌면 같은 쓰임새 토큰에 다른 값이 들어간다. 컴포넌트마다 다크 전용 색이나 테마 전용 색을 따로 두지 않는다.
- 상호작용 부품은 브라우저 기본 요소로 짓는다(버튼, 대화상자, 스위치로 쓰는 체크박스). 그 요소로 지을 수 없는 모양은 피한다.
- 화려함보다 오래 봐도 피곤하지 않은 도구 화면이 목표다. 위젯은 남의 사이트 안에서 튀지 않되 스스로의 정체성이 보여야 한다.

기본 테마는 <기본 테마 이름>이다.

탐색용 가정(결정이 아니니 바꿔도 된다): 버튼 크기는 둘, 위젯 자리의 폭은 320~400px, 관리 화면은 데스크톱 1280px 안팎과 모바일 375px 안팎.
```

## 3. 디자인 시스템 문서처럼 보강하기

2단계의 결과를 디자인 시스템 문서의 모양으로 채우는 글이고, 같은 대화에 넣는다. 항목은 디자인 시스템 문서에 보통 드는 것(사용자가 Claude Design에 물어 받은 목록, 일지 2026-10-06-12)이다. 받은 디자인 토큰 목록과 props 표는 명세의 재료다. 코드에 옮긴 뒤의 원천은 코드다(ADR 0025).

```text
지금까지 그린 것을 디자인 시스템 문서처럼 정리해 줘. 순서는 기초 → 컴포넌트 → 패턴 → 화면이다.

1. 기초: 공통 크기와 테마 표를 한 자리에 모은다. 색은 두 층(원색 토큰 → 쓰임새 토큰)으로 보이고, 글자, 간격, 모서리, 그림자, 기준 폭을 같은 자리에 둔다.
2. 컴포넌트마다 한 면을 둔다.
   - 상태 표: 기본, 올림(포인터를 올림), 누름, 포커스, 쓸 수 없음, 오류, 불러오는 중. 그 컴포넌트에 없는 상태는 "없음"이라고 적는다. 상태마다 쓰는 쓰임새 토큰을 적고, 앞의 열두 쓰임새 토큰에 없는 것이 필요하면(예: 올림이나 누름의 바탕) 새 쓰임새 토큰의 이름과 그것이 가리키는 원색 토큰을 따로 모아 적는다.
   - 해부도와 치수: 부분의 이름(테두리, 안쪽 여백, 아이콘, 글자 등)과 그 값. 값은 공통 크기의 단계 이름과 px로 적는다.
   - 쓰는 법: 언제 쓰는지, 그리고 해도 되는 것과 안 되는 것을 짝으로 한두 개씩.
3. 패턴: 컴포넌트를 엮는 방식. 승인 묻기(도구 이름과 인자, 허가와 사유를 붙인 거부), 실행의 실패를 알리는 알림, 빈 목록, 불러오는 중인 목록.
4. 화면: 앞에서 그린 화면 셋(위젯의 대화, 위젯의 승인 묻기, 관리 화면의 실행 목록)이 어느 패턴과 컴포넌트로 지어졌는지 가리킨다.
5. 구현 연결의 초안: 디자인 토큰 목록을 JSON 하나로 적는다(원색 토큰은 테마마다 값, 쓰임새 토큰은 테마와 모드마다 가리키는 원색 토큰의 이름, 공통 크기는 한 벌). 그리고 컴포넌트마다 props 표(이름, 타입, 기본값, 뜻)를 둔다. 변형은 문자열 값 몇 가운데 하나로 고른다(예: 버튼의 변형은 주, 보조, 위험).

지켜 줄 것: 앞에서 준 "지켜 줄 것"을 그대로 지킨다. 상태의 색도 쓰임새 토큰만 쓴다. 포커스는 모든 상호작용 컴포넌트에서 포커스 링 토큰으로 보인다(WCAG 2.2 AA의 포커스 보임).
```

## 고른 뒤

- 다음 명세 세션(`/to-spec`)이 내보낸 결과로 디자인 토큰의 값을 정한다. 내보낸 hex 값과 크기, 3단계의 디자인 토큰 목록과 props 표는 그 재료일 뿐이고, 코드에 옮긴 뒤에는 디자인 토큰의 값이 코드에만 산다(ADR 0025·0026). 명암비는 구현 티켓의 단위 테스트가 열 벌(테마 다섯 × 모드 둘) 모두 다시 계산하므로, 위 표의 명암비는 고르는 데 쓰는 참고다. 기본 테마의 이름도 이 폴더의 `README.md`에 적어 둔다.
- 테마마다 글꼴이 달라도 위젯은 사이트가 고른 테마의 글꼴만 받는다. 글꼴의 굵기 수는 페이지 안 위젯이 받는 양에 닿는다. 정적 굵기의 동적 서브셋은 굵기마다 따로 받고, 가변 글꼴의 동적 서브셋은 한 벌로 모든 굵기를 덮지만 조각이 더 크다. 한글 문장 하나에 정적 Regular는 39,944바이트, 가변은 83,512바이트였다(`.scratch/design-system/probes/README.md`의 font_shadow 결과).
