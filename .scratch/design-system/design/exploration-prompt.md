# design-system 탐색 프롬프트

Claude Design(claude.ai/design)에서 디자인 시스템의 겉모습 방향을 고를 때 붙여 넣는 시작 프롬프트다. 이 단계는 값(색, 글꼴, 모서리, 간격)의 방향을 고르는 일이고, 디자인 시스템 프로젝트는 만들지 않는다. 디자인 시스템은 코드가 생긴 뒤 `/design-sync`가 올린다(ADR 0025).

프롬프트에 든 것은 세 가지다. **결정**은 ADR 0026(반응형은 그 2026-10-06 이력)과 ADR 0025가 정한 것이고, 화면 문구의 말은 `CONTEXT.md`와 관리 화면의 지금 문구(켜짐, 꺼짐)에서 왔다. **이 프롬프트의 제안**은 ADR이 "바탕, 글자, 강조, 위험 등"까지만 적은 색 쓰임새의 목록, 버튼과 알림의 변형, 화면의 결처럼 고르는 데 필요해서 더한 것이고 명세가 다시 정한다. **탐색용 가정**은 폭과 굵기 수 같은 값이고, 명세나 그 앱의 기능이 다시 정한다(위젯 자리의 폭은 web-widget이 정한다).

## 하는 법

1. Claude Design에서 일반 디자인 프로젝트를 하나 만든다.
2. 아래 "1. 방향 고르기"를 넣고, 나온 방향 가운데 하나를 고른다. 고치고 싶은 것은 대화로 더 요청한다.
3. "2. 고른 방향으로 그리기"를 넣어 컴포넌트 표본과 대략의 화면을 받는다.
4. 고른 방향의 팔레트 표, 크기 표, 컴포넌트 표본, 화면을 Claude Design이 내보내는 형식으로 내보내 이 폴더에 둔다. 어떤 형식이 되는지는 확인하지 않았다.
5. 이 폴더의 `README.md` 표에 내보낸 파일마다 한 줄을 적는다(직접 적거나 다음 명세 세션에 맡긴다). 근거 문서는 `.scratch/design-system/design/exploration-prompt.md`와 `docs/adr/0026-design-system-is-one-package-judged-by-storybook.md`이고, 기준 커밋은 프롬프트를 붙여 넣을 때 그 둘을 읽은 main의 커밋(`git log -1 --format=%h origin/main`)이며, 동기화한 커밋은 "없음"이다. 칸의 뜻은 `docs/agents/issue-tracker.md`의 화면 디자인 절이다.

## 1. 방향 고르기

```text
Agent OS라는 플러그인 기반 에이전트 런타임의 디자인 시스템 방향을 찾고 있어. 앱 둘이 디자인 시스템 하나를 나눠 쓴다.

- 위젯: 남의 웹사이트 안에 들어가는 작은 창. 최종 사용자가 에이전트에게 요청을 보내고 출력을 받는다. 끝난 실행을 이어 가면 요청과 출력이 쌓여 대화가 된다. 에이전트가 도구를 쓰기 전에 승인을 물으면 최종 사용자가 허가하거나 사유를 붙여 거부한다. 밝은 사이트와 어두운 사이트 어디에 들어가도 어색하지 않아야 한다. 위젯은 창의 폭이 아니라 사이트가 내준 자기 자리의 폭에 맞춰 배치를 바꾼다(CSS 컨테이너 쿼리).
- 관리 화면: 운영자가 플러그인을 켜고 끄고, 실행 목록과 실행 상세를 본다. 데스크톱과 모바일 모두에서 쓰므로 완전히 반응한다.

방향을 서너 개 제안해 줘. 방향마다 아래만 보여 줘.

1. 색: 라이트 테마와 다크 테마 두 벌. 색은 쓰임새 이름으로만 정한다. 바탕, 올라온 바탕(카드), 글자, 흐린 글자, 테두리, 강조, 강조 위 글자, 위험, 경고, 성공, 정보, 포커스 링. 테마마다 각 색의 hex 값과, 글자와 그 바탕 짝의 명암비를 적어 줘. 기준은 WCAG 2.2 AA다. 본문 글자는 4.5:1, 큰 글자는 3:1, 컴포넌트를 알아보는 데 필요한 경계(입력창 테두리, 스위치의 윤곽)와 의미를 싣는 아이콘과 포커스 링은 3:1이다.
2. 글꼴: 한글 웹폰트 하나. 오픈 폰트 라이선스(OFL)이고 저자가 동적 서브셋을 내는 글꼴이어야 한다(예: Pretendard). 영문과 숫자도 그 글꼴로 쓰는 안을 먼저 보여 주고, 영문이나 숫자에 다른 글꼴을 짝지으면 더 나은 방향이 있으면 그 안도 보여 줘(짝을 두면 위젯이 받는 글꼴이 는다). 한글과 영문이 섞인 문장으로 보여 줘.
3. 크기: 모든 길이는 px로 적는다(rem을 쓰지 않는다). 글자 크기 단계, 간격 단계, 모서리 둥글기, 그림자 단계, 그리고 반응의 기준 폭 후보(위젯의 컨테이너 크기, 관리 화면의 화면 중단점). 기준 폭은 꼭 필요한 것만 둔다.
4. 작은 표본: 주 버튼, 글 입력 한 줄, 상태 배지 넷(일시정지, 끝남, 실패, 결말 없음). 라이트와 다크 둘 다.

마지막에 방향마다 장단점을 한두 줄로 비교해 줘.

탐색용 가정(결정이 아니니 바꿔도 된다): 위젯 자리의 폭은 320~400px, 관리 화면은 데스크톱 1280px 안팎과 모바일 375px 안팎, 글꼴 굵기는 둘이나 셋.
```

## 2. 고른 방향으로 그리기

```text
고른 방향으로 아래를 라이트와 다크 둘 다 그려 줘.

1. 컴포넌트 표본: 버튼(주, 보조, 위험), 아이콘 버튼, 글 입력(한 줄과 여러 줄), 스위치, 상태 배지(일시정지, 끝남, 실패, 결말 없음), 알림(실패, 경고, 정보), 진행 표시, 표면(카드), 선으로 그린 아이콘 몇 개. 포인터로 누르는 목표는 가로세로 24px 이상이다(WCAG 2.2의 목표 크기).
2. 대략의 화면(와이어프레임 수준) 셋: 위젯의 대화(요청과 출력이 몇 번 오간 모습과 입력창), 위젯의 승인 묻기(도구 이름과 인자를 글자 그대로 보이고, 허가와 사유를 붙인 거부), 관리 화면의 실행 목록(실행마다 상태 배지). 위젯 둘은 자리 폭 320px과 400px 두 가지로, 관리 화면은 데스크톱과 모바일 두 가지로 그려 배치가 어떻게 바뀌는지 보여 줘. 폭 320px에서도 가로 스크롤 없이 다시 흘러야 한다(WCAG 2.2의 리플로).

지켜 줄 것:
- 화면 문구는 한국어이고 이 말을 쓴다: 실행, 요청, 출력, 대화, 승인, 허가, 거부, 일시정지, 끝남, 실패, 결말 없음, 플러그인, 켜짐, 꺼짐, 운영자. "세션", "메시지", "답변", "채팅", "진행 중"은 쓰지 않는다.
- 컴포넌트는 쓰임새 색만 쓰고, 테마가 바뀌면 같은 이름에 다른 값이 들어간다. 컴포넌트마다 다크 전용 색을 따로 두지 않는다.
- 상호작용 부품은 브라우저 기본 요소로 짓는다(버튼, 대화상자, 스위치로 쓰는 체크박스). 그 요소로 지을 수 없는 모양은 피한다.
- 화려함보다 오래 봐도 피곤하지 않은 도구 화면이 목표다. 위젯은 남의 사이트 안에서 튀지 않되 스스로의 정체성이 보여야 한다.

탐색용 가정(결정이 아니니 바꿔도 된다): 버튼 크기는 둘.
```

## 고른 뒤

- 다음 명세 세션(`/to-spec`)이 내보낸 결과로 디자인 토큰의 값을 정한다. 내보낸 hex 값과 크기는 그 재료일 뿐이고, 코드에 옮긴 뒤에는 디자인 토큰의 값이 코드에만 산다(ADR 0025·0026). 명암비는 구현 티켓의 단위 테스트가 다시 계산하므로, 위 표의 명암비는 고르는 데 쓰는 참고다.
- 글꼴의 굵기 수는 페이지 안 위젯이 받는 양에 닿는다. 정적 굵기의 동적 서브셋은 굵기마다 따로 받고, 가변 글꼴의 동적 서브셋은 한 벌로 모든 굵기를 덮지만 조각이 더 크다. 한글 문장 하나에 정적 Regular는 39,944바이트, 가변은 83,512바이트였다(`.scratch/design-system/probes/README.md`의 font_shadow 결과).
