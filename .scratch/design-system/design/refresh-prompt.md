# design-system 재탐색 프롬프트

Claude Design(claude.ai/design)에서 디자인 시스템의 색·글꼴·밀도를 관리 화면 기준으로 다시 고를 때 붙여 넣는 시작 프롬프트다. 2026-10-12 사용자가 올린 디자인 시스템을 보고 디자인이 예쁘지 않다며 관리 화면에 맞게 다시 디자인해 달라고 했다(일지 2026-10-12-11의 "방향 전환"). 처음 탐색은 `exploration-prompt.md`이고 하는 법과 고른 뒤의 차례가 같다. 하는 법은 짧게 다시 적고, 메뉴와 저장 창 같은 자세한 것은 그 파일을 가리킨다.

처음 탐색과 크게 다른 것은 셋이다. 그 밖에 짝의 수, 그릴 화면, 관리 화면만 쓰는 부품도 다르다.

- **참고를 넣는다.** 처음 탐색은 참고할 제품 없이 위젯과 관리 화면을 한꺼번에 넣었다. 이번에는 아래 "참고 디자인"의 규칙과 가져오지 않을 것을 프롬프트에 넣는다.
- **관리 화면이 기준이다.** 위젯은 같은 디자인 시스템이 남의 사이트 안에서도 맞는지 확인하는 표본 하나로만 그린다.
- **밀도와 화면을 보고 고른다.** 처음 탐색의 화면은 와이어프레임 수준이었다. 이번에는 관리 화면 셋을 실제 색과 글꼴로 그리고, 실행 목록을 두 밀도로 나란히 그린다.

프롬프트에 든 것의 종류는 처음 탐색과 같다. **결정**은 ADR 0025(원천은 코드)와 ADR 0026에서 그대로인 것이다. 색 토큰의 두 층, 테마는 색과 글꼴의 한 벌이고 모드 둘(라이트, 다크)을 가진다는 것, `data-theme`·`data-mode`, 길이는 px, 화면 중단점 768px, WCAG 2.2 AA, 글꼴의 조건(OFL, 자가 호스팅, 한글은 저자가 낸 동적 서브셋)이다. 컴포넌트가 쓰임새 토큰만 쓰고 상호작용 부품을 브라우저 기본 요소로 짓는 것은 `.claude/rules/web-design.md`의 규칙이다. **이 프롬프트의 제안**은 참고 디자인에서 뽑은 규칙, 모든 테마의 회색을 무채색이나 아주 옅은 색조로 두고 강조색을 하나로 두라는 것, 밀도 두 벌이다. 테마의 수는 이번 탐색이 다시 추천한다(지금은 다섯). **탐색용 가정**은 두 프롬프트 끝에 모았다. 고른 결과로 바뀌는 결정은 ADR 0026의 새 이력으로 적고 승인을 받는다(아래 "고른 뒤").

## 참고 디자인

2026-10-12에 웹에서 찾았다. 출처마다 읽은 정도가 다르다.

- [AdminLTE의 관리 화면 디자인 원칙](https://adminlte.io/blog/admin-dashboard-design/): 원문을 읽었다(요약 도구로).
- [Linear의 UI 재설계 글](https://linear.app/now/how-we-redesigned-the-linear-ui): 원문을 읽었다(요약 도구로).
- AdminLTE의 2026 대시보드 예 글(Linear, Stripe, Vercel 평)과 디자인 지침 글들: 검색 결과의 요약만 봤다. 셀프 리뷰가 그 글의 주소를 열자 404였다.

가져올 것(괄호는 출처이고, 수치는 그 글이나 요약이 든 값이지 우리가 잰 값이 아니다):

- 바탕은 무채색이거나 아주 옅은 색조이고 강조색은 하나다. 강조색은 주 버튼, 선택, 링크, 포커스에만 쓴다(Linear 원문: 테마를 바탕색·강조색·대비 셋으로 정한다. Vercel·Linear는 검색 요약).
- 색은 상태를 알리는 신호다. 성공·경고·위험은 상태 배지와 알림에만 쓰고, 색만으로 알리지 않고 아이콘이나 글자를 함께 쓴다(AdminLTE 원칙 원문).
- 운영 화면은 촘촘함이 장점이다. 표가 중심이고, 숫자는 오른쪽 정렬과 자릿수 폭이 같은 숫자다(AdminLTE 원칙 원문). 실행 ID·시각 같은 식별자는 고정폭 글꼴이고 격자선은 흐리게 둔다(Stripe는 검색 요약).
- 옆 탐색은 좁게(200~240px) 두고 옅은 바탕에 아이콘과 글자를 함께 둔다. 진한 바탕으로 칠하지 않는다(검색 요약).
- 묶음은 경계선보다 여백과 글자 굵기로 나눈다(AdminLTE 원칙 원문). 간격 단계는 지금 디자인 시스템의 것(4·8·12·16·24·32)을 그대로 쓴다.
- 위계는 글자의 크기와 굵기로 짓고, 경계선보다 높낮이(바탕의 밝기 차이)로 면을 가른다(Linear 원문).
- 빈 목록과 불러오는 중도 처음 쓰는 사람이 보는 화면으로 설계한다(AdminLTE 원칙 원문).

가져오지 않을 것:

- 그 제품들의 로고, 브랜드 색, 글꼴을 그대로 쓰지 않는다. 화면 구성을 복제하지 않는다.
- 다크 우선으로 두지 않는다. 라이트와 다크를 함께 두고 모드는 시스템을 따른다(ADR 0026의 둘째 2026-10-06 이력).
- 차트, 지표 타일, 명령 팔레트, 키보드 단축키처럼 관리 화면에 없는 것을 그리지 않는다.
- 한글이 없는 영문 전용 글꼴을 본문에 쓰지 않는다.

## 하는 법

1~3은 사람이 Claude Design 안에서 한다. 4(내려받기)부터는 기본으로 다음 세션이 한다.

1. Claude Design의 첫 화면에서 새 프로젝트를 시작한다. 입력창 아래의 Design system은 `None`으로 바꾼다. 기존 디자인 시스템을 고르면 그 색과 글꼴로 그려 새 방향을 볼 수 없다. 지금은 조직 기본값인 "Agent OS 디자인 시스템"이 골라져 있을 수 있다. 2026-10-06 첫 탐색은 `None`으로 시작했다. 템플릿은 Color + type pairing이고, 칸마다 400자인 질문 양식을 먼저 띄운다(`exploration-prompt.md`의 하는 법 1).
2. 양식의 칸마다 아래 "1. 방향 고르기"의 답을 넣고 보낸다. 나온 안 가운데 기본 테마로 쓸 것 하나를 고르고, 고칠 것은 대화로 더 요청한다.
3. "2. 그리고 문서로 정리하기"의 `<고른 안>`을 2에서 고른 안의 이름으로 바꾸고 같은 대화에 한 번에 넣는다. 글이 잘리면 `---` 줄 앞과 뒤를 두 번에 나눠 넣는다. 그린 화면을 보고 마음이 바뀌면 같은 대화에 다른 안의 이름으로 "1~4를 이 안으로 다시 그려 줘"라고 넣는다.
4. 결과를 Project archive(ZIP)로 내려받아 정해진 자리(저장소의 바로 위 폴더, 이 PC에서는 `C:\project`)에 둔다. 메뉴와 저장 창은 `exploration-prompt.md`의 하는 법 4와 같다.

## 1. 방향 고르기

What are the pairings for?

```text
Agent OS의 디자인 시스템을 다시 고른다. 기준은 관리 화면이다(운영자가 플러그인을 켜고 끄고, 에이전트 실행 목록과 상세를 보고, 멈춘 실행을 승인·거부한다). 같은 시스템을 남의 웹사이트 안의 작은 위젯도 쓴다. 참고: Linear, Vercel, Stripe의 제품 화면처럼 조용하고 촘촘한 도구 화면. 무채색 바탕에 강조색 하나, 색은 상태에만, 표가 중심, ID와 시각은 고정폭. 색, 글꼴, 밀도를 함께 고른다. 화면 문구는 한국어.
```

Start from an existing design system?: 비워 둔다.

Who's the audience?

```text
관리 화면은 에이전트를 운영하는 개발자와 운영자다. 하루에 여러 번 열어 목록을 훑고 실패를 찾고 결정을 내린다. 데스크톱이 주이고 모바일에서도 쓴다. 위젯은 여러 사이트의 한국어 최종 사용자다.
```

How many pairings?: 4. How divergent?: A mix. Show each pairing applied to: UI components.

Anything fixed or off-limits?

```text
답은 한국어로. 한글 글꼴은 OFL이고 저자가 동적 서브셋을 내는 것(예: Pretendard), 굵기 2~3. 고정폭 글꼴 하나. 색은 두 층(원색 → 쓰임새: 바탕, 올라온 바탕, 글자, 흐린 글자, 테두리, 강조, 강조 위 글자, 위험, 경고, 성공, 정보, 포커스 링), 라이트·다크, WCAG 2.2 AA. 길이는 px. 회색은 무채색이나 아주 옅은 색조, 강조색은 하나. 그러데이션, 큰 그림자, 과한 둥근 모서리, 로고·브랜드 색 복제는 쓰지 않는다.
```

## 2. 그리고 문서로 정리하기

```text
앞의 안 가운데 <고른 안>을 기본 테마로 쓴다. 테마는 색과 글꼴의 한 벌이다. 모든 테마에서 회색은 무채색이나 아주 옅은 색조이고 강조색은 하나다. 모양(모서리, 간격, 크기 단계, 그림자의 크기)과 레이아웃은 모든 테마가 함께 쓴다. 테마를 몇 개 둘지 추천하고 이유를 한 줄 적어 줘(지금은 다섯이다). 테마마다 라이트와 다크 두 모드를 가진다. 표, 추천과 그 이유, 뒤의 문서 정리까지 모든 결과는 대화의 답이 아니라 디자인 파일 안의 쪽으로 넣어 줘. 그 파일을 내보내 그대로 쓴다.

1. 공통 크기: 모든 길이는 px로 적는다(rem을 쓰지 않는다). 간격 단계(4·8·12·16·24·32), 모서리(작게), 그림자(떠 있는 것에만), 옆 탐색의 폭, 화면 중단점 768px 하나. 밀도는 두 벌(촘촘, 보통)을 제안해 줘. 벌마다 관리 화면의 본문과 표 글자, 표의 행 높이, 입력과 버튼의 높이가 다르다. 화면 제목만 크게 둔다. 모든 테마가 이것을 함께 쓴다.
2. 테마 표: 색은 두 층이다. 테마마다 이름, 글꼴과 굵기, 원색 토큰, 쓰임새 토큰의 대응표를 적는다. 원색 토큰은 강조, 회색, 위험·경고·성공·정보 계열마다 밝기 단계와 그 hex 값이다. 대응표는 라이트·다크 모드마다 쓰임새 토큰(바탕, 올라온 바탕, 글자, 흐린 글자, 테두리, 강조, 강조 위 글자, 위험, 경고, 성공, 정보, 포커스 링)이 어느 원색 토큰을 가리키는지와, 글자와 그 바탕 짝의 명암비다. 상태(올림, 누름, 쓸 수 없음 등)에 필요한 쓰임새 토큰이 이 열둘에 없으면 이름을 더해 같은 대응표에 넣는다. 모든 테마의 쓰임새 토큰 이름과 원색 토큰의 계열·단계 이름은 같아야 한다.
3. 컴포넌트 표본: 공통 모양으로 한 번 그린다. 버튼(주, 보조, 위험), 아이콘 버튼, 글 입력, 스위치, 상태 배지(일시정지, 끝남, 실패, 결말 없음), 알림(실패, 경고, 정보), 진행 표시, 카드, 선으로 그린 아이콘 몇 개. 관리 화면만 쓰는 부품도 같은 모양으로 그린다: 표(머리, 행, 고정폭 칸, 오른쪽 정렬 숫자 칸), 링크, 옆 탐색 항목(기본, 선택), 코드 칸, 테마 카드. 포인터로 누르는 목표는 가로세로 24px 이상이다.
4. 화면: 관리 화면 셋을 기본 테마의 실제 색과 글꼴로 그린다. 실행 목록(상태 거르기, 표: 상태 배지, 실행 ID, 에이전트, 주체, 시작, 마지막), 실행 하나(이벤트마다 종류와 시각을 머리로 한 카드 열과, 아래의 결정 자리: 도구 이름과 인자를 고정폭 글자 그대로, 거부 사유 칸, "거부"(보조)가 먼저이고 "승인"(주)이 나중), 플러그인 목록(종류 넷으로 묶고 행마다 이름, 스위치, "켜짐"/"꺼짐"). 틀은 폭 768px 이상에서 왼쪽 옆 탐색(플러그인, 실행, 설정), 미만에서 위 막대다. 각 화면을 데스크톱 1280px과 모바일 375px으로 그린다. 실행 목록은 두 밀도로 나란히, 그리고 라이트와 다크로 그린다. 빈 실행 목록과 불러오는 중인 실행 목록도 그린다. 마지막으로 위젯의 대화 하나(요청과 출력이 몇 번 오간 모습과 입력창)를 자리 폭 320px으로 그려 같은 시스템이 남의 사이트 안에서도 맞는지 보여 줘.

지켜 줄 것:
- 화면 문구는 한국어이고 이 말을 쓴다: 운영자, 관리 화면, 플러그인, 에이전트, MCP, 스킬, 모델, 켜짐, 꺼짐, 실행, 요청, 출력, 이벤트, 트레이스, 주체, 일시정지, 끝남, 실패, 결말 없음, 결정, 승인, 거부, 거부 사유, 재개, 설정, 테마, 모드. "세션", "메시지", "답변", "채팅", "진행 중", "실행 중", "콘솔", "대시보드", "어드민", "관리자", "허가", "확인"(승인의 뜻으로)은 쓰지 않는다.
- 컴포넌트는 쓰임새 토큰만 쓰고 원색 토큰을 직접 쓰지 않는다. 컴포넌트마다 다크 전용 색이나 테마 전용 색을 따로 두지 않는다.
- 포커스는 모든 상호작용 컴포넌트에서 포커스 링 토큰으로 보인다. 상호작용 부품은 브라우저 기본 요소(버튼, 링크, 라디오, 스위치로 쓰는 체크박스, 글 입력)로 짓는다.
- 상태는 색만으로 보이지 않는다. 상태 배지의 아이콘과 글자를 함께 쓴다.
- 폭 320px에서도 가로 스크롤 없이 다시 흘러야 한다. 긴 인자와 JSON은 줄을 바꿔 흐른다.
- 참고한 제품의 로고, 브랜드 색, 화면 구성을 복제하지 않는다. 차트, 지표 타일, 명령 팔레트는 그리지 않는다.

탐색용 가정(결정이 아니니 바꿔도 된다): 촘촘한 벌의 본문과 표 글자는 14px 안팎이고 표의 행은 36px 안팎이다. 옆 탐색은 220~240px이다. 예시 값은 에이전트 calc와 support-bot, MCP filesystem, 도구 payments.refund, 시각 "2026-10-12 14:03:22".

이어서 위에서 그린 것을 디자인 시스템 문서처럼 정리해 디자인 파일 안의 쪽으로 넣어 줘. 순서는 기초 → 컴포넌트 → 패턴 → 화면이고, 위의 "지켜 줄 것"을 그대로 지킨다.

1. 기초: 공통 크기, 밀도 두 벌, 테마 표를 한 자리에 모은다. 색은 두 층(원색 토큰 → 쓰임새 토큰)으로 보이고, 글자, 간격, 모서리, 그림자, 표의 행 높이, 옆 탐색의 폭, 중단점을 같은 자리에 둔다.
2. 컴포넌트마다 한 면을 둔다. 상태 표(기본, 올림, 누름, 포커스, 쓸 수 없음, 오류, 불러오는 중. 없는 상태는 "없음"), 상태마다 쓰는 쓰임새 토큰, 해부도와 치수(공통 크기의 단계 이름과 px), 쓰는 법(언제 쓰는지, 해도 되는 것과 안 되는 것의 짝).
3. 패턴: 승인 묻기, 실행의 실패를 알리는 알림, 빈 목록, 불러오는 중인 목록, 표의 거르기.
4. 화면: 위에서 그린 화면들이 어느 패턴과 컴포넌트로 지어졌는지 가리킨다.
5. 구현 연결의 초안: 디자인 토큰 목록을 JSON 하나로 적는다(원색 토큰은 테마마다 값, 쓰임새 토큰은 테마와 모드마다 가리키는 원색 토큰의 이름, 공통 크기와 밀도는 한 벌씩). 컴포넌트마다 props 표(이름, 타입, 기본값, 뜻)를 둔다. 변형은 문자열 값 몇 가운데 하나로 고른다.
```

## 고른 뒤

차례와 사람이 하는 일은 `exploration-prompt.md`의 "고른 뒤"와 같다. 다른 것만 적는다.

1. **내려받고 옮긴다.** 그 절의 1·2와 같다. 디자인 파일 이름은 Claude Design이 붙인 것으로 찾고, 옛 `Agent OS 디자인 시스템 v3.dc.html`은 지우지 않는다.
2. **표를 채운다.** `README.md` 표에 새 디자인 파일의 줄을 더한다. 근거 문서는 이 파일과 `docs/adr/0026-design-system-is-one-package-judged-by-storybook.md`이고, 동기화한 커밋은 "없음"이다. 기본 테마 줄은 사람의 답으로 고친다.
3. **결정을 묻고 ADR 초안을 쓴다.** 사람에게 기본 테마, 테마의 수, 글꼴, 밀도(촘촘과 보통 가운데 관리 화면의 기본, 위젯의 기본)를 묻는다. 고른 것을 ADR 0026의 새 이력 초안으로 쓰고, 셀프 리뷰를 반영한 뒤 보여 주고 승인을 받는다(`CLAUDE.md` 작업 규약 5).
4. **반영은 기능으로 한다.** 차례는 `.scratch/plan.md`의 design-refresh 행이다. 패키지의 디자인 토큰 CSS와 테마 목록, 판정 스토리, 사진 비교 정답(`pnpm -C web visual:update`, Docker)을 고치고, 보여 주기용 미리보기와 기초 카드, 목록 타일을 만든 뒤 사람이 `/design-sync`를 다시 돈다. 테마의 이름·수·기본 테마나 밀도가 바뀌면 함께 고칠 자리가 있다.
   - `.scratch/admin-style/design/screens-prompt.md`: 기본 테마 "먹", 테마 다섯의 이름, 배치와 밀도의 수치.
   - `.design-sync/`: 사용 규약 `conventions.md`와 그 검사기, 변환기 포크의 기본 테마 `muk`(고치면 다시 채점한다, NOTES), 목록 타일 `thumbnail.html`.
   - `.claude/rules/web-design.md`(먹과 공문을 든 판정 문장), `CONTEXT.md`의 테마.
