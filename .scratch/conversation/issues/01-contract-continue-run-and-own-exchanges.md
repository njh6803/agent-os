# 01: 계약 — 운영자가 HTTP로 끝난 실행을 이어 가고, 에이전트는 자기 교환만 받는다

**What to build:** 채널 토큰으로 `POST /runs/{run_id}/<접미사>`에 `POST /runs`와 같은 본문(에이전트와 요청)을 보내면 새 실행이 서고 같은 SSE 스트림이 온다. 그 에이전트는 컨텍스트의 읽기 전용 멤버로 고리에서 자기가 처리한 교환(요청과 출력, 오래된 것부터)을 받고, 대화 요약은 없음이다. 다른 에이전트의 교환은 오지 않는다. 앞 실행이 없으면 404, 남의 실행이거나 `run_finished`로 끝나지 않았으면 409, 고리가 깨졌으면 500이 봉투로 온다. 트레이스는 형식 3이고 형식 1·2는 지금처럼 읽힌다. 이어 간 실행이 멈췄다 재개돼도 에이전트는 같은 멤버를 받는다. 에이전트가 대화 요약 이벤트를 내면 그 실행은 `run_failed`다. 관리 화면은 새 종류와 필드를 알고 컴파일되며, 결정 e2e가 형식 3 트레이스를 지난다.

이 기능의 계약 티켓이고 02·03·04를 막는다. 계약은 sdk 넷(컨텍스트 멤버와 값 타입, `run_started`의 선택 필드, 대화 요약 이벤트, 매니페스트의 선택 필드), 트레이스 형식 3, core의 하위 타입 둘과 이어 가기 진입점, `openapi.json`의 새 경로와 새 컴포넌트, 지침 다섯이다. 끌고 오는 것은 명세가 찾은 여섯(라우트와 core 진입점, 형식 3 헤더, 생성 클라이언트와 관리 화면의 컴파일, 결정 자리 조건, 채널 경로 목록, 픽스처)에 2026-10-04 명세 검토가 더한 넷(셋째 `satisfies` 표, 모든 종류의 매니페스트 픽스처와 펼친 문자열, 손으로 든 채널 오퍼레이션 목록, 공유 409 설명)이다. 새 경로와 새 필드 때문에 저절로 빨개지는 기존 테스트(컴포넌트 이름의 정확한 집합, 409가 채널 라우트에만 있다는 단언, 헤더 "2" 단언)는 끌고 오는 것으로 세지 않고 각 절에 적었다. 리뷰의 질문은 "동작하나"가 아니라 이 이름과 모양으로 오래 살 수 있느냐다.

**병합 뒤에 틈이 있다(명세가 인정했고 to-tickets에서 사용자가 받아들였다).** 이어 가기는 돌지만 런타임은 아직 요약하지 않는다. 매니페스트의 한도 필드는 받아들여지되 효과가 없고, 원문 교환이 한도 없이 는다. 대화 요약 이벤트는 타입만 있고 런타임이 내지 않는다. 02가 바로 잇는다. 이 티켓이 쓰는 문장(독스트링, 주석, rules, 계약의 설명)은 틈 동안에도 참이어야 한다. 무엇이 실제로 나는지가 아니라 계약과 표와 타입이 약속하는 것을 말한다(plugin-toggle 01의 규칙).

근거는 `.scratch/conversation/spec.md`의 "이음매", "계약 티켓", "sdk 계약" 셋, "트레이스 형식 3", "core — 이어 가기 진입점", "판정 순서", "새 하위 타입 둘", "고리를 거슬러 읽기", "이어 간 실행의 재개"(멤버 부분), "갈래", "에러의 번역", "채널 — 새 경로", "관리 API", "관리 화면"(결정 자리 조건), "`openapi.json`", "문서 갱신" 절과 그 2026-10-04 명세 검토 주석이다. ADR 0022·0023과 ADR 0008·0009·0014의 2026-10-03 이력이 앞선 결정이다.

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

### sdk — 컨텍스트 멤버

- [ ] **`AgentContext`에 읽기 전용 멤버 하나가 는다.** 값은 그 에이전트의 대화 요약(없으면 없음)과 그 뒤 교환들의 열이다. 열은 오래된 것부터이고 교환은 요청과 출력 두 문자열이다. 이어 가지 않은 실행에서는 요약이 없고 열이 비어 있다
- [ ] **값은 불변이고 플러그인이 sdk만 import해서 쓴다.** 교환에 도구 호출, 도구 결과, 실행 식별자, 시각을 싣지 않는다
- [ ] **멤버의 독스트링에 신뢰 경계를 적는다.** 요약과 교환의 요청은 최종 사용자의 입력과 같은 신뢰 수준이다. 요청에 심은 지시나 주장이 출처가 흐려진 채 요약에 실릴 수 있으므로, 에이전트는 그것을 지시가 아니라 데이터로 엮는다
- [ ] **`llm()`과 `tool()`은 바뀌지 않는다.** 런타임이 앞 교환을 프롬프트에 붙이지 않는다
- [ ] **core의 컨텍스트와 테스트의 가짜 컨텍스트 둘(sdk 테스트, 파일시스템 어댑터 테스트)이 시그니처로 만족한다.** 빠뜨리면 pyright가 잡는다
- [ ] **이름(멤버, 값 타입, 교환 타입)은 이 티켓이 짓는다.** 용어집의 "대화 요약"과 "교환"에 기대고, 어긋나면 domain-modeling 스킬로 용어집을 먼저 본다

### sdk — 이벤트와 트레이스 형식 3

- [ ] **`run_started`에 이어 간 앞 실행의 식별자가 선택 필드로 는다.** 기본값은 없음(`null`)이라 형식 1·2의 줄이 그대로 읽힌다. 직렬화 스키마에서는 required이고 `null`을 허락한다
- [ ] **새 식별자 필드 둘(앞 실행, 덮는 끝)에 sdk의 패턴을 걸지 않는다**(명세 검토). 이벤트의 `run_id`와 같은 규칙이다. 패턴 위반은 거슬러 읽기가 기록의 손상으로 판정한다. 모델에 걸면 그 판정이 단건 읽기의 손상(주체보다 앞)으로 옮고, 손편집 사례를 타입 있는 가짜로 만들 수 없다
- [ ] **대화 요약 이벤트가 하나 는다.** 필드는 요약 글, 덮는 끝(덮인 교환 가운데 가장 최근 실행의 식별자), 모델 이름, 입력 토큰 수, 출력 토큰 수다. 덮는 범위의 시작은 적지 않는다. 독스트링은 한 줄이고 논증은 `#` 주석이다
- [ ] **요약 글의 필드 이름은 `text`가 아니다**(명세 검토). `text`면 관리 화면의 필드 이름 표가 "응답 텍스트"를 붙이고 `satisfies`가 새 항목을 요구하지 않는다
- [ ] **직렬화 스키마에서 새 필드와 새 이벤트의 필드가 required다**(sdk 테스트)
- [ ] **JSONL 어댑터가 헤더에 3을 쓴다.** 형식 집합에 `"3"`이 늘고 재개할 수 있는 형식은 2와 3이다. 형식 1·2·3 파일을 읽고, 새 이벤트와 시작 이벤트의 새 필드가 왕복하며, 형식 2 파일에 재개가 이어 쓴 뒤에도 헤더는 2다. 헤더 "2"를 단언하는 어댑터 테스트 둘을 고친다
- [ ] **옛 런타임이 형식 3 파일을 헤더에서 통째로 거부하는 것은 형식 목록이 한다.** 명세 검토가 임시 스크립트로 봤다(pydantic 2.13.5. 지금 코드의 헤더 모델에 `"3"`을 넣으면 `literal_error (schema_version)`, 헤더 2 아래 새 필드가 든 `run_started` 줄은 `extra_forbidden`. 커밋된 프로브는 아니다). 따로 만들 것은 없다

### sdk — 매니페스트의 한도

- [ ] **에이전트 매니페스트에 한도(앞 교환의 글자 수)가 선택 필드로 는다.** 필드의 기본은 없음이고 숫자 기본값을 두지 않는다. 기본 20,000은 02에서 core가 소유한다. `schema_version`은 "1" 그대로다
- [ ] **값은 1 이상의 엄격한 정수다.** 없음과 1 이상의 정수를 받고, 0·음수·불린·숫자 문자열·실수(`2.0` 포함)를 매니페스트를 읽는 단계에서 거부한다. 에이전트가 아닌 종류가 적으면 `requires_approval`처럼 거부한다
- [ ] **관리 API의 매니페스트 응답에 필드가 실린다.** 적지 않은 에이전트는 없음이다. 라우트는 바뀌지 않고, 실행 요약의 필드는 일곱 그대로라 앞 실행을 목록에 싣지 않는다(명세 "관리 API")
- [ ] **이름은 이 티켓이 짓는다**

### core — 하위 타입 둘과 409의 정의

- [ ] **`PluginError`의 하위 타입 둘.** **다른 주체**는 이어 가는 쪽의 주체가 앞 실행의 `run_started` 주체와 다른 것이다. ADR 0023이 "core의 새 하위 타입"으로 적은 그것이고, 결정의 주체 판정(end-user-channel)도 같은 것을 쓴다. **이어 갈 수 없음**은 앞 실행이 있고 주체가 같지만 `run_finished`로 끝나지 않은 것이다(실패, 일시정지, 결말 없음). 메시지는 `run_status()`로 파생한 상태를 든다. `NotResumable`을 쓰지 않는다. 그 이름과 독스트링은 재개를 말한다
- [ ] **공용 표에 둘이 409로 늘고 기반 타입보다 먼저다.** 뒤집히면 500이 되는 것을 테스트가 잡는다. 에러 코드는 새로 늘지 않고 409 `conflict`의 뜻이 는다
- [ ] **core 테스트의 하위 타입 목록(`_SUBTYPES`, 주석 "하위 타입 셋")에 둘을 더한다.** 그것을 빼고 깨짐을 단언하는 사례들이 저절로 따라온다. 하위 타입이 서로 겹치지 않음을 보는 사례도 둘을 더해 넓힌다
- [ ] **409의 정의 문장을 고친다.** "대상의 상태가 요청을 허락하지 않는 것"을 "대상의 상태나 주체가 요청을 허락하지 않는 것"으로. 자리는 명세가 센 것(rules `core.md`·`http.md`, core 포트 모듈의 `PluginError`와 `Disabled` 독스트링, core 실행 모듈의 모듈 독스트링, HTTP 층의 `failure_for`와 `ErrorCode`, 테스트 독스트링 셋)에 명세 검토가 더한 **공유 409 설명**(HTTP 층 에러 문서 모듈의 값 "있지만 지금 상태로는 받을 수 없다"와 그 주석)이다. 공유 설명을 고치기로 했다(to-tickets에서 사용자가 골랐다). `POST /runs`와 결정 경로의 409 설명도 함께 바뀌고 `openapi.json`과 생성 타입에 실린다. end-user-channel이 결정 경로에도 다른 주체의 409를 더하므로 거기서도 참이다
- [ ] **이름 둘은 이 티켓이 짓는다.** 용어집의 "주체"와 "이어 가기"에 기댄다
- [ ] **end-user-channel의 계약 티켓이 이 티켓보다 먼저 열려 있으면**, 먼저 연 쪽이 다른 주체의 하위 타입과 그것을 드는 자리(표의 한 줄, `_SUBTYPES`, `http.md`·`core.md`의 하위 타입 목록, 409의 정의 문장과 공유 설명, 그리고 공유 설명이 박히는 다시 생성한 계약 파일과 클라이언트 타입)만 작은 PR로 따로 병합하고, 다른 쪽은 그것을 들인 뒤 이어 간다(명세의 하위 타입 절, 명세 검토). to-tickets 시점(main `e222b5f`)에 그쪽은 브랜치도 PR도 `.scratch/end-user-channel/`도 없었다. 시작할 때 다시 본다

### core — 이어 가기 진입점과 판정 순서

- [ ] **이어 가기는 새 실행이다.** 새 실행 식별자와 새 트레이스 파일이고 `run_started`를 쓴다. 입력은 앞 실행, 에이전트, 요청, 주체다. 시그니처(새 함수인지 `run()`의 인자인지)는 이 티켓이 정하되 조건은 둘이다. 이어 가지 않는 지금의 `run()` 호출이 그대로 돈다. 앞 실행 자리의 "없음"은 새 대화라는 뜻 하나뿐이고 고리를 짐작하는 기본값이 없다. 몸통은 `_drive`를 공유한다
- [ ] **요청이 댄 앞 실행은 포트에 닿기 전에 `is_run_id`를 지난다.** 어기면 `Absent`이고 포트를 부르지 않는다. 재개는 거르지 않으며 이것은 명세가 정한 것이다(명세 검토)
- [ ] **판정 순서는 세 덩어리이고 모두 실행 식별자를 만들기 전이라 트레이스가 생기지 않는다**
  - 앞 실행: 없음(`Absent`) → 손상(`PluginError`. 단건 읽기의 손상과, 재개가 보는 모르는 종류·빈 트레이스·식별자 어긋남·시작 이벤트로 열리지 않음) → 다른 주체 → 이어 갈 수 없음
  - 고리: 거슬러 읽다 만나는 실행이 없거나, 손상이거나, 주체가 다르거나, `run_finished`로 끝나지 않았거나, 앞 실행 필드가 패턴을 어기거나, 요약 이벤트가 `run_started` 바로 뒤가 아닌 자리에 있거나 둘 이상이거나, 고리가 순환하거나, 가장 가까운 요약이 덮는 끝을 만나지 못한 채 고리의 처음에 닿으면 `PluginError`다. 메시지는 그 실행 식별자와 이유를 들고 테스트가 그것을 단언한다(스토리 46). 앞 실행 자신의 앞 실행 필드 패턴과 요약 자리 위반도 이 덩어리에 든다. 주체와 끝남 뒤라 "손상은 주체보다 앞"의 논거와 갈리지만 동작은 이것이고, 최종 사용자 경로에서는 오히려 존재를 덜 드러낸다(명세 검토). 독스트링에 한 줄로 밝힌다
  - 준비: 지금 `_prepare`의 순서 그대로다(부재 → 깨짐 → 꺼짐 → 진입점 import). 요청이 댄 에이전트가 없으면 `Absent`다
- [ ] **순서를 core 테스트가 하나씩 고정한다.** 없음, 손상, 다른 주체, 끝나지 않음(실패·일시정지·결말 없음 각각), 고리 깨짐의 사례 전부, 준비 단계(없는 에이전트, 꺼짐)가 고리 뒤라는 것. 주체가 끝나지 않음보다 먼저이고 손상이 주체보다 먼저다. 거절된 이어 가기는 트레이스를 남기지 않는다. 선례는 "결정의 자리" 절과 "꺼진 플러그인" 절이다
- [ ] **`Absent`의 독스트링이 드는 "요청이 이름을 댄 것"에 이어 가기의 앞 실행이 는다.** core 실행 모듈의 모듈 독스트링(실행 전 실패의 열거)도 같이 는다

### core — 거슬러 읽기와 멤버의 값

- [ ] **앞 실행에서 시작 이벤트의 앞 실행 필드를 따라 거슬러 가며 `TraceStore.read`로 트레이스 전체를 읽는다.** 지금 에이전트와 같은 실행은 교환 하나(시작 이벤트의 요청과 `run_finished`의 출력)를 낸다. 그 트레이스에 대화 요약 이벤트가 있고 아직 요약을 만나지 않았으면 그것이 가장 가까운 요약이다. 다른 에이전트의 실행은 교환도 요약도 내지 않고 지나간다
- [ ] **멈추는 자리.** 가장 가까운 요약을 만나면 그 요약이 덮는 끝의 실행까지 거슬러 가되, 그 실행은 읽지 않고 멈춘다. 요약이 없으면 고리의 처음(앞 실행 필드가 없는 실행)까지 간다. 더 오래된 요약은 쓰지 않는다. 덮는 끝에서 멈추는 것을 가짜 트레이스가 읽힌 실행 식별자로 본다. 이 티켓에서 요약 이벤트는 가짜 트레이스에 손으로 쓴 것이다
- [ ] **동기이고 이벤트 루프 위에서 돈다.** 포트에 가벼운 읽기 메서드를 더하지 않는다. 긴 고리가 루프를 막는 것은 알려진 한계다(명세)
- [ ] **에이전트가 받는 값을 테스트 에이전트가 출력에 옮겨 판정한다.** 이어 가지 않으면 요약 없음과 빈 열. 같은 에이전트로 셋을 이어 가면 교환 셋이 오래된 것부터. A → B → A면 A는 A의 교환만, B는 B의 교환만. 형식 1·2의 끝난 실행도 이어 간다(형식 1·2 실행은 고리의 처음이다). 같은 앞 실행을 둘이 이어 가면 둘 다 선다(갈래)
- [ ] **값은 런타임이 에이전트를 부르기 전에 정하고 실행 안에서 바뀌지 않는다**

### core — 이어 간 실행의 재개 (멤버)

- [ ] **재개는 시작 이벤트의 앞 실행에서 다시 거슬러 읽어 처음과 같은 멤버를 준다.** 고리의 실행에 손으로 쓴 요약이 있으면 처음처럼 그것에서 멈춘다. 재개되는 실행 자신의 트레이스에 든 요약 이벤트를 읽는 것, 그 자리와 개수의 검증, 재생 기록 열에서 빼는 것, 요약할지를 다시 판정하지 않는 것은 모두 02다(명세 검토 blocker 2의 둘째 묶음). 이 티켓에서는 재개되는 실행의 트레이스에 요약 이벤트를 손으로 넣어도 잴 수 없다. 재생 기록 열이 그것을 빼지 않아 에이전트의 첫 모델 호출에서 대조 불일치가 나기 때문이다(셀프 리뷰가 찾았다). 이 티켓에서 런타임은 요약 이벤트를 쓰지 않으므로 02 전까지 그 문장들은 거짓이 되지 않는다
- [ ] **거슬러 읽기는 재개의 첫 걸음 안이다.** 지금의 트레이스 판정(없음 → 형식 1 → 손상 → 일시정지 아님 → 자리 어긋남) 뒤, 준비 앞이고 `await`가 없다. 고리가 깨졌으면 결정 이벤트를 쓰기 전에 `PluginError`라 실행은 일시정지 그대로다. 멈춘 사이 거슬러 읽는 범위의 트레이스를 지우면 그렇고, 그보다 오래된 트레이스를 지우면 재개가 그대로 선다. 재개의 주체 비교 대상은 멈춘 실행의 `run_started` 주체다(명세 검토)
- [ ] **승인 대상에서 멈춘 이어 간 실행을 재개하면 에이전트가 같은 멤버를 받아 재생 대조가 통과한다.** 형식 2 트레이스의 재개와 이어 가지 않은 형식 3 실행의 재개는 바뀌지 않는다

### core — 에이전트가 낸 요약 이벤트 (명세 검토 blocker 1)

- [ ] **에이전트가 대화 요약 이벤트를 yield하면 그 실행은 `run_failed`로 끝난다.** 이어 가지 않은 실행에서도 그렇다. 지금 런타임은 에이전트의 다른 이벤트를 그대로 통과시키지만, 요약 이벤트는 다음 실행의 거슬러 읽기가 트레이스에서 읽는 입력이라 에이전트가 지어낸 것이 통과하면 런타임의 것과 가를 수 없다
- [ ] **이것은 02가 아니라 이 티켓이다.** 거슬러 읽기가 요약 이벤트를 입력으로 읽는 티켓과 같아야 한다. 02로 미루면 그 사이 플러그인 하나가 끝난 실행의 요약 자리 밖에 요약을 내어, 그 실행을 지나는 모든 이어 가기를 영구히 500으로 만들 수 있다(고리의 실행은 바뀌지 않는다)
- [ ] **`.claude/rules/core.md`의 런타임이 발행하는 이벤트 목록에 요약 이벤트와 "에이전트가 내면 실패"를 더한다**

### 채널 — 새 경로

- [ ] **`/runs` 아래의 새 경로이고 고유한 리터럴 접미사를 둔다**(코드를 읽으면 선다. `verbatim` 변환기의 정규식이 슬래시를 포함하므로 접미사 없는 `/{run_id:verbatim}`을 결정 경로 앞에 등록하면 `abc/approval`을 통째로 잡는다. 명세 검토가 임시 스크립트로도 봤다). 결정 경로가 가로채이지 않는 것을 라우터 테스트가 고정한다. 실행 식별자는 `verbatim` 변환기와 sdk의 패턴으로 받는다. 본문은 `POST /runs`의 본문 모델 그대로라 새 본문 컴포넌트가 없다. 주체와 모델은 조립이 넘긴 것이다
- [ ] **응답은 같은 SSE 스트림이고 첫 이벤트 `run_started`, 프레임이 트레이스 한 줄과 글자로 같다.** 실행은 앱의 수명이 소유하고 첫 이벤트를 의존성에서 기다린다(`channel.md`)
- [ ] **채널은 앞 실행을 먼저 확인하지 않는다.** core가 던진 타입을 표가 옮긴다. 상태 코드 테스트는 먼저 확인하는 구현으로도 초록이라 이것은 리뷰가 본다
- [ ] **404(앞 실행 없음, 에이전트 없음), 409(다른 주체, 끝나지 않음, 꺼짐), 422(경로의 패턴은 퍼센트 인코딩으로 밀고 포트를 부르지 않는다, 본문의 추가 필드), 500(고리 깨짐. 봉투의 `message`가 그 `PluginError`의 문구다)이 JSON 봉투이고 계약에 적힌다.** 문서화된 에러는 401, 404, 409, 422, 500이다
- [ ] **인증 표는 바뀌지 않고 전수 검사가 저절로 덮는다.** 손으로 든 채널 오퍼레이션 목록(`CHANNEL_OPERATIONS`)에 새 경로를 더한다. 빠뜨려도 빨개지지 않는다(명세 검토). 컴포넌트 이름의 정확한 집합(`EXISTING_COMPONENTS`)과 409가 채널 라우트에만 있다고 단언하는 테스트는 저절로 빨개지므로 고친다
- [ ] **채널 라우터 모듈 독스트링의 경로 수, `channel.md`의 새 경로와 "채널은 앞 실행을 먼저 확인하지 않는다"**
- [ ] **경로 이름과 `operation_id`는 이 티켓이 짓는다.** 용어집의 "이어 가기"에 기댄다

### `openapi.json`과 생성 클라이언트

- [ ] **계약 파일이 `create_app().openapi()`와 같다.** 바뀌는 것: 새 경로와 그 에러 문서, `Event` 유니온의 새 멤버, `RunStarted`의 새 필드, 트레이스 상세와 실행 요약의 형식 버전 열거에 `"3"`, 에이전트 매니페스트의 새 필드, 그리고 공유 409 설명(위 하위 타입 절). 바뀌지 않는 것: 에러 코드, `POST /runs`와 결정의 본문과 경로, 제목과 설명
- [ ] **같은 커밋에 다시 생성한 클라이언트 타입이 든다.** 생성기가 `anyOf[integer(minimum 1), null]`을 어떤 TS 타입으로 내는지는 돌려서 본다(명세 검토가 확인하지 못한 것)
- [ ] **api-client의 채널 경로 목록(`ChannelPath`)에 새 경로를 더하고 타입 테스트의 기대와 "채널의 경로 둘" 주석을 고친다.** 채널 클라이언트가 그 경로를 쓸지는 정하지 않는다
- [ ] **이벤트 종류나 필드를 키로 삼는 `satisfies` 표 셋이 새 종류와 필드를 안다.** api-client 스트림 술어의 종류 목록(`EVENT_TYPES`), 관리 화면 이벤트 필드 이름 표(`FIELD_NAMES`. 앞 실행·요약 글·덮는 끝에 용어집의 말), 결정 훅의 스트림 끝맺음 표(`ENDS_STREAM`. 요약은 `false`다. 결말이 아니고 `run_status()`의 갈래 밖이다. 명세 검토가 더했다)

### 관리 화면 — 컴파일과 결정 자리

- [ ] **결정 자리의 형식 조건을 "형식 1이 아니다"로 바꾼다**(`RunDecision`). 그 독스트링("형식 2 트레이스다")을 고치고 결정 페이지 테스트에 형식 3의 멈춘 실행 사례를 더한다. 형식 1에는 서지 않는다(기존)
- [ ] **생성 타입을 단 픽스처가 새 필드를 얻는다.** `Trace`의 시작 이벤트(앞 실행 없음), 생성 타입을 단 매니페스트 픽스처 전부(매니페스트 컴포넌트는 종류 넷이 공유한다. 홈·플러그인·결정 페이지 테스트에 흩어져 있고 tsc가 하나씩 잡는다), 그리고 매니페스트를 펼친 문자열 픽스처(`CALC_MANIFEST`. `JSON.stringify`와 `toContain`으로 비교하므로 타입 검사가 아니라 vitest에서 빨개진다. 명세 검토)
