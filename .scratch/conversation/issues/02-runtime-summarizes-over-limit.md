# 02: 요약 — 한도를 넘으면 런타임이 요약하고, 재개는 요약을 다시 만들지 않는다

**What to build:** 이어 가기에서 거슬러 읽기가 모은 원문 교환의 글자 수가 그 에이전트의 한도(매니페스트, 없으면 20,000)를 넘으면, 런타임이 에이전트를 부르기 전에 그 실행의 모델과 고정 프롬프트로 앞 요약과 오래된 교환을 새 요약에 접는다. 가장 최근 교환들은 한도의 절반 안에서 원문으로 남는다. 요약 이벤트가 `run_started` 바로 뒤에 서고(HTTP 스트림의 둘째 프레임) 요약 글, 덮는 끝, 모델, 토큰 수를 든다. 에이전트는 새 요약과 원문 꼬리를 받는다. 요약이 실패하면 그 실행은 에이전트를 부르지 않고 `run_failed`로 끝나며(HTTP는 200 스트림 안의 `run_failed`), 같은 앞 실행으로 다시 이어 가면 다시 요약한다. 이어 간 실행이 멈췄다 재개되면 모델을 다시 부르지 않고 자기 트레이스의 요약을 쓴다.

01의 틈을 닫는다. 01이 세운 타입(요약 이벤트, 한도 필드)에 동작이 붙는다. 03을 막는다. 03의 LLM 테스트가 셋째 이어 가기에서 요약을 요구한다.

근거는 `.scratch/conversation/spec.md`의 "core — 대화 요약", "이어 간 실행의 재개"(요약 부분), "sdk 계약 — 매니페스트"(기본값의 자리), Testing의 "요약"과 "재개" 절, 2026-10-04 명세 검토(blocker 2와 한도를 내린 뒤의 재개, 목표 길이의 올림, 스토리 15·24·35)다. ADR 0022의 "압축은 이어 가기를 시작할 때 에이전트를 부르기 전에 한다"가 앞선 결정이다.

**Blocked by:** 01

**Status:** ready-for-agent

### 계기와 원문 범위

- [ ] **원문 교환(가장 가까운 요약 뒤의 것)의 글자 수 합이 한도를 넘으면 요약한다.** 같으면 하지 않는다. 글자 수는 파이썬 `len`(코드 포인트)이고 교환마다 요청과 출력을 더한다. 요약 글은 세지 않는다
- [ ] **한도는 이어 가는 실행의 에이전트 매니페스트에서 읽고, 없으면 core가 소유한 기본 20,000이다.** 루프 상한과 목록 상한이 core에 있는 것과 같은 자리다. 한도를 적지 않은 에이전트에서 기본값이 쓰이는 것(계기와 목표 글자 수 5,000)을 테스트가 본다(스토리 35, 명세 검토)
- [ ] **가장 최근 교환부터 거꾸로 세어 합이 한도의 절반을 넘지 않는 데까지 원문으로 남기고, 나머지 교환과 가장 가까운 요약을 새 요약에 접는다.** 계기 때문에 적어도 교환 하나는 접힌다. 가장 최근 교환 하나가 절반보다 길면 그것도 접힌다. 테스트는 한도와 같을 때와 하나 넘을 때, 꼬리의 범위, 긴 마지막 교환을 본다
- [ ] **덮는 끝은 접힌 교환 가운데 가장 최근 실행이다**

### 모델 호출과 고정 프롬프트

- [ ] **모델은 그 실행의 모델 포트 그대로이고 도구를 붙이지 않는다.** 루프 상한(10턴)에 들지 않는다
- [ ] **시스템 메시지는 명세의 문구이고 `{target}`이 목표 글자 수다.** **목표는 한도의 4분의 1을 올림한 값이다**(to-tickets에서 사용자가 골랐다. 명세 검토가 반올림과 하한이 없다고 적은 자리. 한도가 1 이상이라 목표는 저절로 1 이상이다). 모델의 출력 상한으로 강제하지 않는다. 넘어도 다음 요약이 다시 접는다
- [ ] **사용자 메시지는 JSON 문서 하나다.** 키는 `previous_summary`(문자열이나 `null`)와 `exchanges`(`request`와 `output`을 든 객체의 열, 오래된 것부터)다. 요청에 든 따옴표·괄호·지시 같은 글이 JSON 문자열 안에 남는 것과, 앞 요약이 데이터에 드는 것을 테스트가 본다
- [ ] **시스템 메시지를 글자 그대로 단언하지 않고 요소마다 본다.** 출처 표시의 지시, 데이터를 기록으로만 다루라는 지시, 대화의 언어, 목표 글자 수. 가짜 모델이 받은 것이 시스템 메시지 하나와 사용자 메시지 하나인 것을 본다. 가짜 모델이 그 메시지 열을 그대로 받는지는 돌려서 본다(명세 검토가 확인하지 못한 것)
- [ ] **문구를 고치면 명세의 그 절을 함께 고친다.** 문구는 런타임 하나라 ADR이 말한 "고정 프롬프트"다

### 요약 이벤트

- [ ] **요약 이벤트를 쓰고 나서 에이전트를 부른다.** 자리는 `run_started` 바로 뒤이고 실행 하나에 많아야 하나다. 글, 덮는 끝, 모델 이름, 입력·출력 토큰 수를 든다. 요약 글은 마스킹하지 않는다(ADR 0022. `llm_called.text`와 같은 성격이라 새 노출면이 아니고 ADR 0009의 열린 문제와 같은 경계다). 런타임이 아는 비밀 값을 자유 형식 글에서 걸러 내는 값 기반 마스킹은 ADR 0009·0022의 이력 초안으로 따로 본다(PR #130의 CodeRabbit 지적, 사용자 결정 2026-10-04. `plan.md`의 conversation 행). 그 이력이 이 티켓보다 먼저 서면 이 티켓이 따른다
- [ ] **에이전트는 새 요약과 원문 꼬리를 받는다.** 다음 이어 가기는 그 요약과 그 뒤의 교환만 받고 고리를 덮는 끝에서 멈춘다(그 앞의 트레이스를 읽지 않는다). 01이 손으로 쓴 요약으로 잰 사례가 런타임이 쓴 요약으로도 선다
- [ ] **HTTP에서 요약 이벤트는 스트림의 둘째 프레임이다**(스토리 24, 명세 검토). 쓰기만 하고 흘리지 않으면 CLI가 스트림에서 센 안내 줄의 자리가 하나 밀린다
- [ ] **요약 이벤트는 재생 기록 열에 들지 않는다.** 재개 진입점이 경계 이벤트를 빼는 자리(`_BOUNDARY`)에 든다. 빠지면 재개의 모델 대조가 `LlmCalled`가 아닌 기록을 받아 `Mismatch`이고, 멤버를 쓰지 않는 에이전트도 실패한다(명세 검토 blocker 2)

### 실패

- [ ] **모델 호출이 예외를 내면(SDK의 재시도 뒤) 요약 이벤트 없이 `run_failed`이고, 에이전트를 부르지 않으며 도구도 연결하지 않는다.** 요약 글이 비었거나 공백뿐이어도 같은 실패다. 빈 요약을 쓰면 접힌 교환이 조용히 사라진다. 메시지는 대화 요약이 실패했다는 것을 들고 테스트가 그 문구를 단언한다(스토리 15, 명세 검토)
- [ ] **런타임은 SDK 밖에서 다시 시도하지 않고 대신할 길(원문으로 진행, 오래된 교환 잘라 내기)도 두지 않는다.** 같은 앞 실행으로 다시 이어 가면 다시 요약한다. 실패한 실행은 고리에 들지 않는다
- [ ] **HTTP에서 요약 실패는 200 스트림 안의 `run_failed`다.** 첫 이벤트 `run_started`는 이미 나갔다

### 재개

- [ ] **재개는 모델을 다시 부르지 않는다.** 가짜 모델의 요약 호출 수가 늘지 않는다
- [ ] **재개는 요약할지를 다시 판정하지 않는다.** 자기 트레이스에 요약 이벤트가 없으면 요약하지 않은 실행이었고, 멈춘 사이 매니페스트의 한도를 바꿔도 다른 값을 만들지 않는다
- [ ] **자기 트레이스에 요약 이벤트가 있으면 그것이 가장 가까운 요약(이미 만난 요약)이고 그 덮는 끝 바로 뒤까지 읽는다(덮는 끝 자체는 읽지 않는다).** 01의 재개는 고리에서 다시 거슬러 읽는 것까지였고, 자기 요약을 읽는 것은 재생 기록 열에서 빼는 것과 같은 변경이라 이 티켓이다. **이어 가기 사이에 한도를 내린 경우**를 테스트가 덮는다(명세 검토). 앞선 요약을 든 실행이 원문 꼬리 안에 설 수 있는데, 재개가 일반 규칙(처음 만난 요약에서 멈춤)으로 읽으면 처음과 다른 멤버가 된다. 자기 요약을 이미 만난 요약으로 다루면 맞다. 한도가 같으면 이 경우는 생기지 않는다
- [ ] **자기 트레이스의 요약 이벤트도 자리와 개수를 검증한다**(to-tickets가 정했다. 명세 검토가 빠졌다고 적은 자리). `run_started` 바로 뒤가 아니거나 둘 이상이면 고리의 실행과 같은 손상 `PluginError`이고 결정 이벤트를 쓰기 전이라 실행은 일시정지 그대로다. 01의 "에이전트가 내면 실패"가 서 있어 손편집에서만 생기는 경우이고, 고리의 실행에 거는 규칙을 자기 트레이스에만 빼는 이유가 없다
- [ ] **승인 대상에서 멈춘 이어 간 실행(요약이 있는 것과 없는 것)을 재개하면 에이전트가 같은 멤버를 받아 재생 대조가 통과한다**

### 지침

- [ ] **`core.md`에 요약의 계기와 원문 범위, 실패 정책(요약 실패는 재시도 없이 `run_failed`), 재개에서 요약하지 않음과 다시 판정하지 않음, 그리고 재생 기록 열에 들지 않는 이벤트(경계 이벤트와 요약 이벤트. 지금 `core.md`에는 그 목록이 없고 core 실행 모듈의 상수에만 있다. 새 문장이다).** 01이 02나 틈을 가리켜 쓴 문장을 `02`·`틈`으로 grep해(요약 이벤트와 한도 필드와 컨텍스트 멤버의 독스트링, `sdk.md`·`core.md`, 새 경로의 계약 설명이 그 예다) 지금 동작과 맞게 다듬는다
- [ ] 검증 명령이 모두 초록이다. core 실행 모듈을 건드리므로 기존 `-m llm`을 한 번 돌려 일지의 검사 절에 적는다. 새 LLM 사례는 03이다

### 01이 넘긴 메모 (2026-10-04, PR #131 리뷰)

- 거슬러 읽기(`_Link`, `_continued`, `_resumed_conversation`, `_read_link`, `_walk`, `_next_link`, `_require_link`)가 `core/run.py`에 약 200줄 들어왔다. 요약 생성을 더하기 전에 고리 읽기를 `core/` 안의 별도 모듈로 옮길지 먼저 정한다(claude-review 3회차 Minor). 포트는 늘지 않으므로 경계 문제가 아니라 모듈이 바뀌는 이유가 둘로 갈리는 문제다.
- `_continued`와 `_resumed_conversation`의 셋 줄 중복, `_walk`가 첫 링크에 `_require_link`를 다시 돌려 주체·끝남이 그 링크에서 죽은 분기인 것, `_require_link`가 값을 돌려주는 이름인 것(`_finished_of` 같은 이름)은 02가 이 자리를 지날 때 함께 본다(1·2·3회차 Minor·Nit, 일지 2026-10-04-03의 PR 리뷰 절).
