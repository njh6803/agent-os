# conversation 프로브

명세·ADR·코드 주석이 근거로 드는 측정 스크립트다. 규약은 `docs/agents/issue-tracker.md`의 "프로브와 근거".

둘 다 저장소 루트에서 돈다.

```sh
PYTHONUTF8=1 uv run python .scratch/conversation/probes/chain_walk.py
PYTHONUTF8=1 uv run --env-file .env python .scratch/conversation/probes/token_ratio.py
```

| 파일 | 재는 것 | 근거로 드는 자리 | 다시 돌 때 | 잰 판 |
|---|---|---|---|---|
| `chain_walk.py` | 대화의 고리를 끝에서 처음까지 거슬러 읽는 비용. 실제 `JsonlTrace`로 끝난 실행 N개(10, 100, 1000)의 트레이스를 임시 디렉터리에 쓰고, 포트의 `read`로 하나씩 읽는 시간을 프롬프트 길이(한글 2,000자, 20,000자, 60,000자)마다 잰다. 포트에 없는 대조군 둘을 함께 잰다. "머리와 끝"은 헤더와 시작 이벤트와 마지막 줄만 파싱하고 마지막 줄을 찾으려 끝까지 흘려 읽는다. "머리만"은 헤더와 시작 이벤트만 파싱하고 닫는다. 고리는 `previous` 필드가 아직 없어 메모리의 목록으로 흉내 낸다. 도구 결과가 작은 트레이스 한 모양만 잰다 | `spec.md`의 "고리를 거슬러 읽기"와 그 비용 | 인자 없음. 임시 디렉터리에 최대 약 60MB를 쓰고 지운다. 고리 1000개에 프롬프트 60,000자인 조합은 약 180MB라 뺀다(`SKIP`). 같은 측정을 세 번 해 가장 짧은 것을 적고, 방금 쓴 파일이라 OS 캐시에 있으므로 하한이다. 시각은 기계에 따라 다르다 | Python 3.12.10, pydantic 2.13.5. 윈도우 10(AMD64), 2026-10-04 |
| `token_ratio.py` | 한도를 글자 수로 잴 때 그것이 토큰으로 얼마인지. Anthropic 토큰 세기 API(`count_tokens`, 모델을 부르지 않는다)로 이 프로브가 지은 한국어·영어 대화 표본 4,000자씩의 토큰 수를 세고, 마침표 하나뿐인 메시지의 토큰 수를 틀의 몫으로 뺀다 | `spec.md`의 "기본 한도" | `.env`의 `ANTHROPIC_API_KEY`가 있어야 한다. 모델 이름을 인자로 줄 수 있고 기본은 런타임의 기본 모델이다 | anthropic 1.7.0, 모델 claude-opus-5, 2026-10-04 |
| `continuation_mutations.toml` | 티켓 01의 가드가 실제로 무는지. 판정 순서(다른 주체가 끝나지 않음보다 앞, 고리가 준비보다 앞), 요청이 댄 앞 실행의 패턴 거르기, 덮는 끝에서 멈추기, 다른 에이전트의 교환을 안 모으기, 에이전트가 낸 요약 이벤트의 실패, 요약 자리 검증, 표의 하위 타입 둘(빼면 500), 어댑터 헤더 3, 한도의 엄격 검증, 결정 자리의 형식 조건(vitest), 스트림 술어의 종류 목록(tsc)을 하나씩 되돌려 그 테스트가 빨개지는지 본다 | 티켓 01의 테스트가 구현 전에 import 오류로만 빨갰다는 것(일지 2026-10-04-03) | `PYTHONUTF8=1 uv run python tools/mutate.py .scratch/conversation/probes/continuation_mutations.toml`. vitest·tsc 변이는 `web`에서 돌아 수 분 든다. 코드를 옮기면 `--check`로 원문을 본다 | tools/mutate.py, 2026-10-04 |

## 2026-10-04 결과

`chain_walk.py`. 파일 하나의 크기는 한글이 UTF-8로 3바이트라 프롬프트 글자 수의 약 세 배다. 처음 판의 대조군은 프롬프트가 든 셋째 줄까지 파싱해서 원인을 가르지 못했고(셀프 리뷰가 잡았다), 둘로 나눠 다시 쟀다. 아래가 다시 잰 값이다.

|---|---|---|---|---|---|---|

| 10 | 20,000 | 61.4 | 6.0 | 0.60 | 1.9 | 1.2 |

| 100 | 20,000 | 61.4 | 59.8 | 0.60 | 19.7 | 12.0 |
| 100 | 60,000 | 178.6 | 127.6 | 1.28 | 29.3 | 12.5 |
| 1000 | 2,000 | 8.6 | 285.5 | 0.29 | 155.3 | 124.6 |
| 1000 | 20,000 | 61.4 | 614.6 | 0.61 | 204.4 | 125.3 |

- 비용은 지나는 실행의 수에 비례하고, `read`는 트레이스 하나에 0.3~1.3ms다.
- 머리만 읽어도 트레이스 하나에 약 0.12ms가 들고 파일 크기와 무관하다(파일을 열고 두 줄을 파싱하는 몫).
- 머리와 끝과 머리만의 차이(끝까지 흘려 읽는 몫)는 파일 크기를 따라 실행 1000개에 31~79ms다.
- `read`와 머리와 끝의 차이(가운데 줄을 파싱하는 몫)가 가장 크고, 프롬프트가 클수록 커진다. 머리와 끝은 `read`보다 1.8~4.4배, 머리만은 2.3~10.2배 짧았다(표의 합계로 나눈 값). 어느 쪽이든 실행 수에 비례하는 것은 그대로다.
