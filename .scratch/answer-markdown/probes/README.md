# answer-markdown 프로브

명세·ADR·코드 주석이 근거로 드는 측정 스크립트다. 규약은 `docs/agents/issue-tracker.md`의 "프로브와 근거".

`markdown_render/`는 모델이 지은 답을 마크다운으로 그릴 라이브러리를 고르고(2026-11-10, 설계), 고른 라이브러리 위에 지을 부품의 방법을 정하는(2026-11-11, 명세) 프로브다. 라이브러리 후보는 react-markdown + remark-gfm과 markdown-to-jsx이고, marked는 크기와 의존성을 견주는 데만 든다. 후보마다 제한을 건 컴포넌트(`apps/widget/components/molecules/MarkdownReact.tsx`, `MarkdownJsx.tsx`)와 주소 판정(`apps/widget/lib/safe-url.ts`)을 짓고, 그것이 저장소와 같은 타입 검사와 판정자 설정을 지나는지, 위험한 입력에서 무엇을 그리는지, 번들이 얼마나 느는지를 본다. 명세 단계는 react-markdown 위에 합친 시제품(`apps/widget/components/molecules/AnswerMarkdown.tsx`, `apps/widget/lib/answer-markdown/`, `apps/widget/lib/link-url.ts`)을 지어 줄바꿈, 한국어 굵게, 글자로 둘 기호, 문장 끝 번호, 출처 덩이, 각주, 깊이 가드, 글자만 내는 갈래의 방법을 견줬다. 시제품은 프로브의 것이고 제품 코드가 아니다. 스크립트마다 측정이 아닌 회차를 세는 조건과 양성 대조는 그 파일의 머리 주석에 있다.

```sh
pnpm -C .scratch/answer-markdown/probes/markdown_render install --frozen-lockfile
node .scratch/answer-markdown/probes/markdown_render/probe/typecheck.mjs
node .scratch/answer-markdown/probes/markdown_render/probe/lint.mjs
node .scratch/answer-markdown/probes/markdown_render/probe/deps.mjs
node .scratch/answer-markdown/probes/markdown_render/probe/registry-selftest.mjs
node .scratch/answer-markdown/probes/markdown_render/probe/registry.mjs
node .scratch/answer-markdown/probes/markdown_render/probe/render.mjs
node .scratch/answer-markdown/probes/markdown_render/probe/report.mjs
node .scratch/answer-markdown/probes/markdown_render/probe/size.mjs
node .scratch/answer-markdown/probes/markdown_render/probe/stress.mjs
node .scratch/answer-markdown/probes/markdown_render/probe/shape.mjs
node .scratch/answer-markdown/probes/markdown_render/probe/textcompare.mjs
node .scratch/answer-markdown/probes/markdown_render/probe/plaintext.mjs
node .scratch/answer-markdown/probes/markdown_render/probe/callsites.mjs

uv run --env-file .env python -X utf8 .scratch/answer-markdown/probes/output_tokens.py claude-opus-5
```

저장소 루트에서 돈다. Node 24와 pnpm 11.24.0이 있어야 하고, 설치는 `pnpm-workspace.yaml`의 정책대로 설치 스크립트를 돌리지 않는다. 산출물은 `markdown_render/out/`에 생기고 커밋하지 않는다(그 폴더의 `.gitignore`). Node 스크립트마다 표준 출력의 마지막 줄이 결과의 JSON 한 줄이다. 바깥에 요청을 보내는 것은 둘이다. `registry.mjs`가 `https://registry.npmjs.org/`에 읽기 요청을 보내고, `output_tokens.py`가 Anthropic의 토큰 세기 API에 이 프로브가 지은 글(기호와 공백뿐이다)을 보낸다. 뒤의 것은 `.env`의 `ANTHROPIC_API_KEY`가 있어야 하고, 워크트리에서는 `--env-file ../../../.env`로 주 체크아웃의 것을 읽는다(`docs/constitution/operations.md` LLM 테스트). `callsites.mjs`, `axe.mjs`, `browser.mjs`는 설치된 Playwright가 이미 내려받아 둔 Chromium을 쓰고 내려받지 않는다(없으면 종료 코드 3). `browser.mjs`는 여덟 부분을 모두 돌면 10분 넘게 걸린다. `tailwind_utilities.mjs`는 `web/`의 설치(`pnpm -C web install`)를 쓴다.

## 2026-11-10의 결과(설계)

아래 표의 앞 일곱 줄에서 "2026-11-10"으로 적은 결과는 그날 손으로 돌려 본 것이다. 처음에는 설계 인터뷰의 조사 서브에이전트가 저장소 밖 임시 폴더에서 돌렸고, 같은 날 이 폴더로 옮긴 뒤 위 명령을 순서대로 다시 돌려 그 실행이 남긴 표준 출력과 견줬다. `render.mjs`와 `size.mjs`의 출력은 글자까지 같았다. `typecheck.mjs`와 `lint.mjs`는 경로 표기만 달랐고, `deps.mjs`는 설치 로그 칸만 달랐다(옮긴 자리에는 `out/install.log`가 없다). `registry.mjs`는 시각만 달랐고, `stress.mjs`는 걸린 시간만 달랐다. 옮기며 고친 것은 `lint.mjs`의 저장소 경로 기본값(지은 워크트리의 절대 경로를 이 폴더에서 네 단계 위로)과 그 머리 주석뿐이다. 그날 브라우저에서 본 것은 없다. 렌더의 판정은 `react-dom/server`의 `renderToStaticMarkup`이 낸 HTML을 parse5로 읽은 나무에서 한 것이다.

결과를 본 뒤 바꾼 기준은 하나다. `typecheck.mjs`의 양성 대조는 처음에 허용 목록 `switch`에서 갈래 하나를 지우면 TS2366("끝에 return이 없다")이 난다고 기대했는데 걸리지 않았다. 반환 타입 `ReactNode`가 `undefined`를 품기 때문이다. 그래서 컴포넌트의 `default` 갈래에 `never` 대입을 넣고 기대를 TS2322로 바꿨다(그 파일의 머리 주석). 그리고 `MarkdownJsx.tsx`는 첫 판에서 할 일 목록의 `input`과 각주의 `footer`가 제한을 지나 그려졌고, 허용 목록과 `overrides`를 고친 뒤 다시 돌린 것이 아래의 결과다. 첫 판의 산출물은 커밋하지 않았으므로 이 문장은 조사 서브에이전트의 보고다.

## 2026-11-11의 결과(명세)

answer-markdown의 명세 단계(일지 2026-11-11-1057)가 같은 판(react-markdown 10.1.0, remark-gfm 4.0.1. `registry.mjs`가 그날 두 패키지 모두 지난 365일에 새 판이 없다고 냈다)으로 기존 스크립트를 다시 돌리고 아래 표의 뒤 여덟 줄을 더했다. 스크립트와 시제품의 첫 판은 프로브 서브에이전트가 지었고 사용량 한도로 보고 없이 끝났다. 그 뒤 명세를 쓴 세션이 스크립트를 읽고, 표의 결과를 모두 직접 돌려 봤다. 직접 돌리며 고친 것은 여섯이다.

- 글자만 내는 갈래에서 표의 칸과 줄이 붙었다(`plaintext.mjs`의 첫 실행에서 19가지 입력이 어긋났다. 예: "조문내용제750조불법행위…"). 시제품 주석의 전제("표의 칸 사이에 줄 끝 글자가 남는다")가 틀렸고, 표 요소 바로 아래의 공백 글자 노드는 그려지지 않았다. 칸 뒤에 공백, 줄 뒤에 줄 끝 글자를 두게 고쳤다.
- 각주 문법이 숨긴 영어 제목 "Footnotes"와 돌아가기 표시 "↩"를 더하고 본문의 `[^1]`을 표지 없는 `1`로 바꿨다(`plaintext.mjs`와 `textcompare.mjs`에서 봤다). remark-gfm에는 각주만 끄는 옵션이 없어, 각주 노드를 원문의 글자로 되돌리는 변환(`lib/answer-markdown/footnotes.ts`)을 더했다.
- `plaintext.mjs`의 첫 판은 "화면의 갈래가 물러서면 글자만의 갈래도 물러선다"를 전제로 두었다. `>` 3,000겹은 Node에서 스택 문턱 근처라, 세 번의 실행 가운데 둘은 세 갈래가 함께 물러섰고 하나는 글자만의 갈래만 물러섰다. 일부만 물러선 입력을 어긋남과 따로 세고, 깊이 가드를 켠 묶음의 절을 더했다.
- `tailwind_utilities.mjs`의 첫 판은 기준선에 없는 줄만 모아, 기준선의 다른 규칙에 글자가 같은 선언이 있는 후보 넷을 "선언 다름"으로 냈다. 규칙 전체를 뽑아 견주게 고쳤다.
- 할 일 목록(`- [x] 한 일`)의 표시가 화면에서 사라졌다. remark-gfm이 표시를 글에서 떼어 항목의 `checked`로 옮기고, 허용 목록이 그것을 그리는 `input`을 내지 않기 때문이다(`render.mjs`의 `x50-task-list` 산출에서 봤다). 명세를 쓰다 찾았다. 목표 모양 다섯(`shape-cases.mjs`의 할 일 묶음 `g01`~`g05`. id가 `g01-task-list`처럼 `-task`로 이어지는 것이고, 한 줄 바꿈 묶음의 `g01`~`g06`과는 다른 사례다)을 먼저 적고 변환 없이 `shape.mjs`를 돌려, 표시가 든 넷(`g01`~`g04`)이 목표와 다르고 표시가 아닌 대괄호(`g05`)는 목표와 같다는 것을 본 뒤, 표시를 원문 글자 그대로 되돌리는 변환(`lib/answer-markdown/task-marks.ts`)을 더했다. 변환의 첫 판을 돌리기 전에 `g06`(표시 바로 뒤가 굵게이고 대문자 `[X]`)을 더했다. 첫 판은 그 모양에서 원문의 표시를 찾는 자리를 틀리게 어림해 `g06`이 소문자 `[x]`로 나왔고, 파서의 코드(`mdast-util-gfm-task-list-item` 2.0.1)를 읽어 자리를 고친 뒤 여섯이 모두 맞았다. 그 뒤 `typecheck.mjs`, `lint.mjs`, `size.mjs`, `shape.mjs`, `textcompare.mjs`, `plaintext.mjs`를 다시 돌렸다. `lint.mjs`는 볼 파일을 목록으로 들고 있어, 새 파일을 목록에 더하기 전의 실행은 그 파일을 부르는 줄에서 `no-unsafe-call`(타입을 풀지 못한 호출)을 냈다.
- 할 일 표시 변환(`task-marks.ts`)이 저장소의 판정자 규칙에 걸렸다. 승인 뒤에 `lint.mjs`를 다시 돌리니 그 파일의 세 함수가 `checked`를 불리언 매개변수로 받아 `no-restricted-syntax`(불리언 매개변수를 두지 않는다)가 셋 났다. 이 문서의 앞 판은 그 파일을 넣은 15파일의 결과를 "오류 0"으로 적었는데, 그 수가 어느 실행의 것인지는 알 수 없다(그 파일의 수정 시각은 그 판을 적은 때와 다시 돌린 때 사이에 바뀌지 않았다). 부르는 쪽이 `checked`로 표시 글자(`[x]`, `[ ]`)를 골라 넘기게 고쳤고, 다시 돌려 15파일 모두 오류 0·경고 0을 봤다. 아래 표의 "오류 0"은 고친 뒤의 값이다.

**승인 뒤에 다시 돌린 것.** 사용자가 ADR 0053의 이력을 승인하며 둘을 더 골랐다(일지 2026-11-11-1057 "승인"). 글자로 두는 별표의 범위를 "글자가 낀 식까지 넓힘"으로, 화면 그림과 부품이 달라지던 자리를 "그림에 맞추고 디자인 시스템을 넓힘"으로 골랐다. 그래서 시제품이 쓰는 규칙(`lib/answer-markdown/index.ts`의 `ANSWER_DIGIT_RULE`)을 여는 묶음의 앞과 닫는 묶음의 뒤만 보는 규칙으로 바꾸고, `shape-cases.mjs`에 넓힌 규칙이 잡지 않는 식 둘(`d59`, `d60`)을, `shape-entry.tsx`에 넓힌 규칙을 굵게 되살리기의 앞과 뒤에 둔 갈래 둘을 더했다. `tailwind_utilities.mjs`에는 토큰 하나(위첨자 번호의 왼쪽 틈)와 후보 둘(`mt-3`, `leading-0`)을 더했다. 그 뒤 `shape.mjs`, `lint.mjs`, `typecheck.mjs`, `size.mjs`, `plaintext.mjs`, `textcompare.mjs`, `axe.mjs`, `tailwind_utilities.mjs`를 다시 돌린 것이 아래 표의 수다. `axe.mjs`는 측정 아님 0으로 끝났고, 저장한 출력의 줄(대조 14, 표 32, 코드 18, 화면 20)을 아래 표의 서술과 손으로 대 보니 같았다. `browser.mjs`와 `callsites.mjs`는 넓힌 규칙으로 다시 돌리지 않았다. 두 프로브와 `inputs.mjs`, `browser-kit.mjs`에는 숫자에 별표가 붙은 입력이 없다(스크립트를 읽었다). 그래서 두 줄의 결과는 좁은 규칙을 쓰던 시제품의 것이다.

`browser.mjs`는 두 번 돌렸다. 첫 실행(15:46)은 각주 변환, 할 일 표시 변환, 글자만의 갈래의 표 칸 처리를 더하기 전의 시제품이었고, 그 뒤 `browser.mjs`와 `inputs.mjs`가 고쳐졌다(16:41). 셀프 리뷰 뒤 지금의 스크립트와 시제품으로 한 번 더 돌렸다(18:01. 측정이 아닌 회차 0). 두 보고를 걸린 시간만 빼고 줄마다 견주니 442줄 가운데 19줄이 달랐다. 죽는 첫 깊이, 목록이 죽는 단계, 가드, 넘치는 깊이, 실패를 받는 두 방법, CSS 후보의 높이는 같았고, 다른 줄은 Node 갈래가 그린 겹의 수와 스택의 함수 이름, 그리고 던지는 문턱 가까이에서 던짐과 죽음이 갈린 다섯 회차였다(아래 표의 `browser.mjs` 줄). 두 보고를 견준 것은 손으로 봤다(첫 실행의 보고를 세션 스크래치패드에 복사해 두고 `uv run python -c`로 줄마다 견줬다. `out/`은 커밋하지 않으므로 첫 실행의 보고는 저장소에 없다). 그 프로브의 입력에는 각주와 할 일 목록이 없고 글자만의 갈래를 그리지 않는다. 셀프 리뷰는 `typecheck.mjs`의 "tsc가 본 파일" 목록에 `task-marks.ts`가 빠진 것도 짚었고, 더한 뒤 다시 돌린 결과는 같았다(오류 0, 본 파일 314개). `callsites.mjs`는 할 일 표시 변환을 더하기 전의 시제품으로 돌렸고 그 입력에 할 일 목록이 없다(`axe.mjs`는 위 문단대로 승인 뒤에 다시 돌렸다). `callsites.mjs`의 F(Testing Library의 `findByText`)는 그 라이브러리를 돌린 것이 아니라 매처의 규칙을 페이지 안에서 옮긴 어림이다. `tailwind_utilities.mjs`는 규칙이 생기는지까지만 보고, 그 클래스로 그린 화면이 화면 파일과 같은 모양인지는 보지 않는다. `output_tokens.py`는 명세의 "깊이 가드"를 쓰다 더했다. `browser.mjs`의 보고에서 가드를 켠 들여쓴 목록 1,000겹이 약 22초 걸린 것을 다시 읽고, 그 글이 출력 상한 안에서 나올 수 있는지를 셌다. 상한 안의 가장 깊은 깊이(479겹)의 시간은 따로 재지 않았고, 200겹과 500겹의 시간 사이에 있다고 보는 것은 어림이다.
