# end-user-continuation: 최종 사용자 경로에서도 앞 대화를 이어 가고, 긴 대화의 비용과 실패 원인을 다룬다.
**슬라이스:** 4
**Blocked by:** conversation, end-user-channel
**끝:** 2026-10-20

최종 사용자 경로의 이어 가기와 긴 대화의 비용. web-widget에서 화면과 무관한 몫으로 떼어 냈다(설계 인터뷰 2026-10-15, 일지 2026-10-15-17). 경로와 본문은 운영자 채널의 이어 가기와 같은 모양이고, 시작처럼 요청 글자 수와 동시·시간당 상한을 지나며, 응답과 문서화된 에러는 최종 사용자 경로의 시작과 같고(최종 사용자 항목 스트림, 401·404·409·422·429·500), 판정은 core에 이미 있다(ADR 0022의 첫째 2026-10-15 이력). 500→404 덮기는 표에 있되 ADR 0023의 2026-10-16 이력이 주인을 확인하기 전의 손상으로 좁혔고 그 좁힘은 티켓 05가 들였다(core의 하위 타입 `TraceDamagedBeforePrincipal`, 면은 운영자와 최종 사용자 둘). 실패한 실행은 런타임이 정한 실패 원인을 들고 최종 사용자 실패 항목에도 싣는다. 실패의 모든 종류를 가르고 자리를 모르는 것은 그 밖이며, 원인이 든 `run_failed`는 런타임만 내고, 트레이스 형식은 3 그대로이고, 화면 문구는 위젯이 정한다(ADR 0031). 긴 대화는 시작 이벤트의 에이전트별 바로가기로 지금 에이전트의 실행만 따라가고, 요약은 원문 교환의 글자 수나 교환 수(core가 든 값) 가운데 하나라도 넘으면 일어나며, 거슬러 읽는 실행 수에 모든 면의 상한(core가 든 값)을 둔다. 원문 꼬리도 교환 수로 묶으면 상한에 닿는 것은 바로가기가 없는 옛 고리(와 기준이 서기 전에 쓰인 바로가기 대화)뿐이고 그때는 상한까지 모은 것만 넘긴다. 이어 가기를 시작할 때의 거슬러 읽기는 스레드에서 하고 재개의 거슬러 읽기는 이벤트 루프 위에 남는다(ADR 0022의 둘째 2026-10-15 이력). 명세가 정할 것이던 열은 명세(2026-10-16, `.scratch/end-user-continuation/spec.md`)가 닫았고 그 서두의 목록이 원천이다. 사용자가 고른 넷은 이음매(있는 자리에 실제 `serve`의 최종 사용자 경로를 이어 가는 `-m llm` 하나를 더한다, 추천과 달랐다), 구성 오류의 404(주인을 확인하기 전의 손상만 404로 덮고 주체를 확인한 뒤의 고장은 최종 사용자 면 어디서나 500 고정 문구다, ADR 0023의 2026-10-16 이력), 요약 도중의 시간 초과(원인은 시간 초과, 추천과 달랐다), 에이전트가 처리하지 않은 `ToolError`(원인 "도구 실패"를 따로 둔다)다. 명세가 정한 스물여섯 가운데 주된 것: 실패 원인의 목록은 명세의 "실패 원인 — 목록" 절이고(계약 티켓이 ADR 0031의 이력으로 남긴다) 런타임이 던진 예외 객체 그 자체가 빠져나왔을 때만 그 원인이며, 먼저 난 실패가 닫기의 예외와 기한보다 앞선다. 에이전트가 낸 `run_failed`는 원인과 무관하게 막는다. 결말 뒤 도구 연결 닫기의 실패는 덧붙이지 않는다(지금은 `run_finished` 뒤에 `run_failed`가 붙는다). 바로가기는 에이전트에서 실행으로 가는 지도이고 새 대화는 빈 지도, 옛 대화(앞 실행에 지도가 없음)는 없음이 이어진다. 교환 수 기준은 50이고 꼬리는 교환 수의 절반(25)으로도 묶는다. 읽기 상한은 100(앞 실행을 센다)이고 `기준 + 2 ≤ 상한`을 테스트가 고정한다. 이어 가기의 판정 전부를 한 번의 스레드 호출로 보낸다. 측정은 `.scratch/end-user-continuation/probes/walk_budget.py`이고 인터뷰의 수가 같은 크기로 다시 나왔다(결과는 그 README). 취소되면 스레드의 읽기를 기다리는 것은 같은 자리의 `thread_cancel_wait.py`가 쟀다(명세 검토가 짓고 to-tickets가 옮겼다). 교환 수 기준의 예산은 재개가 이벤트 루프를 막는 최악 0.5초 안팎이다(재개는 자기 트레이스를 포함해 많아야 51개를 읽는다. 명세 검토가 셈을 바로잡았다). 첫 티켓은 계약: 새 경로, `run_started`의 바로가기와 `run_failed`의 실패 원인, 최종 사용자 실패 항목의 원인, `openapi.json`, api-client, 관리 화면의 필드 이름 표와 생성 타입을 단 테스트 픽스처. 계약 티켓은 `.claude/rules/`의 계약 문장을 고치고, 동작의 문장(원인의 갈래, 바로가기, 교환 수, 상한, 스레드, 덮기)은 그 동작을 들이는 티켓이 쓴다. 기본 한도를 모델의 컨텍스트 크기에 맞추는 일은 에이전트마다 모델이 달라질 때(모델 플러그인) 다시 본다. 명세 검토(2026-10-16)는 blocker 1·should-fix 10·nit 8이었고 명세의 주석과 티켓으로 닫았다. blocker는 원인 필드를 싣는 티켓과 에이전트가 낸 `run_failed`를 막는 동작이 갈라지면 그 사이 에이전트가 지어낸 원인이 실패 항목까지 나간다는 것이었고, 막는 동작을 계약 티켓에 넣었다. 티켓은 여섯이다(`.scratch/end-user-continuation/issues/`, 2026-10-16). 01 계약(이어 가기 경로, 원인·바로가기 필드, 에이전트가 낸 `run_failed` 막기) → 02 실패 원인·03 바로가기·05 404 덮기·06 관리 화면(01 뒤, 나란히) → 04 교환 수·상한·스레드(03 뒤). 잎은 02·04·05·06이고 마지막에 병합되는 쪽이 닫는다. `in-progress`는 01이 바꾼다. 02·03·05와 03 뒤의 04는 core 실행 모듈과 그 테스트, 그리고 `.claude/rules/core.md`의 실패 정책 항목(한 줄)을 함께 고쳐 나란히 돌리면 병합 충돌을 풀 수 있다. to-tickets에서 사용자가 고른 것: 여섯으로 쪼갬, 실제 모델 테스트는 01이 이어 가기 요청을 붙이고 03이 지도 단언을 더함. to-tickets가 정한 넷은 명세 서두의 주석이다
