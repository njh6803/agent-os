# 02: 실패 원인 — 런타임이 쓰는 모든 실패가 생긴 자리의 원인을 들고, 먼저 난 실패가 결말이다

**What to build:** 런타임이 쓰는 `run_failed`가 모두 실패 원인 아홉 가운데 하나를 든다. 요약 호출이 실패하면 대화 요약, 기한이 오면(요약 도중이어도) 시간 초과, 도구 서버에 붙지 못하거나 매니페스트가 없는 도구를 가리키면 도구 연결이다. 에이전트가 `ctx.llm()`의 모델 예외나 루프 상한의 예외, `ctx.tool()`의 `ToolError`, 재개 대조의 예외를 잡지 않고 그대로 두면 그 원인이고, 감싸거나 다른 예외로 바꾸면 에이전트 코드다. 에이전트의 다른 예외, 결말 없이 돌아온 것, 런타임만 내는 이벤트나 이벤트가 아닌 값을 낸 것은 에이전트 코드이고, 결말 전에 트레이스 쓰기가 한 번 실패한 것은 그 밖이다. 최종 사용자 실패 항목과 운영자 채널의 `run_failed`에 그 원인이 실린다. 에이전트 몫의 실패 뒤 도구 연결을 닫다 다른 예외가 나거나 기한이 와도 원인과 메시지는 먼저 난 실패이고, 결말이 정해진 뒤 닫기가 실패해도 `run_failed`가 덧붙지 않는다.

01의 틈 가운데 원인을 닫는다. 01이 세운 필드와 값 집합에 동작이 붙는다. 막는 티켓은 없다(잎).

근거는 `.scratch/end-user-continuation/spec.md`의 "실패 원인 — 목록", "실패 원인 — 가르는 법", "에이전트가 낸 `run_failed`"(원인 부분), "최종 사용자 실패 항목" 절, Testing Decisions의 core "실패 원인"·"결말 뒤 닫기" 항목과 HTTP "실패 항목의 원인"·"운영자 채널" 항목, 그리고 그 2026-10-16 명세 검토·to-tickets 주석이다. ADR 0031이 앞선 결정이고 정한 목록은 01이 그 이력 한 줄로 남겼다.

**Blocked by:** 01

**Status:** ready-for-agent

### 자리와 원인

- [ ] **원인은 실패가 처음 생긴 자리로 정하고 몸통(`_Body`)이 정한다.** 요약 호출의 실패(`_summary_outcome`)는 대화 요약, 기한(`deadline_failure`)은 시간 초과다. 요약 단계인지는 보지 않는다(사용자가 골랐다). 메시지는 지금 그대로다
- [ ] **도구 연결.** `connect`에 들어가는 동안의 예외와 선언 확인(`_reject_unknown_declarations`)의 예외다
- [ ] **런타임이 에이전트에게 던지는 실패는 던지는 자리에서 그 예외 객체를 원인과 함께 기억한다.** 모델 호출은 `ctx.llm()`에서 모델 포트에 닿는 몫 전부다 — 도구를 붙이기(`model_caller`, `_ask` 밖에서 불린다), 부르기, 응답을 읽어 기록하기. 도구 실패는 `ctx.tool()`이 던지는 `ToolError`이고 승인자가 거부한 직접 호출(`_deny`)도 든다. 루프 상한은 `run_loop`의 상한 예외다 — `run_loop`는 몸통을 모르므로 훅을 넘기거나 `ctx.llm()`에서 그 예외를 받아 기억한다(그 안에서 도는 것은 런타임의 클로저뿐이라 거기서 나온 그 예외는 언제나 런타임의 것이다, 명세 검토가 코드를 읽었다). 재개 대조는 재생 기록과의 어긋남, 멈춘 호출과의 어긋남(`_require_paused_call`, `_ask`의 결정 대조), 마스킹된 인자(`_reject_masked_args`)의 예외다
- [ ] **에이전트에서 빠져나온 예외가 기억한 객체 그 자체(`is`)면 그 원인이고 아니면 에이전트 코드다.** 잡아 그대로 다시 던지면 같은 객체라 원인이 남는다. 감싸거나(`raise … from`) 다른 예외로 바꾸거나 예외 그룹에 넣으면 에이전트 코드다. 타입으로 가르지 않는다 — `ToolError`는 sdk의 공개 타입이라 에이전트가 스스로 던질 수 있다. 기억하는 것은 마지막 하나가 아니라 그 실행 안에서 던진 예외 전부이고 몸통과 수명이 같다. 에이전트가 받는 예외를 런타임의 새 타입으로 감싸지 않는다
- [ ] **몸통이 에이전트 밖에서 내는 실패.** 재생 구간에서 에이전트가 낸 이벤트가 기록과 어긋난 것(`replay_event`)은 재개 대조다. 에이전트가 런타임만 내는 이벤트(`conversation_summarized`, `run_failed`)를 낸 것(01이 세운 갈래), 결말 없이 돌아온 것("에이전트가 run_finished 없이 끝났다"), sdk의 이벤트가 아닌 값을 낸 것은 에이전트 코드다. 이벤트가 아닌 값은 몸통이 쓰기 전에 보고 끝낸다 — 지금은 트레이스 쓰기에서 속성 오류로 터져 아래 그 밖의 자리와 갈리지 않는다
- [ ] **그 밖은 `_drive` 안에서 결말 전에 이벤트를 트레이스에 쓰다 난 예외다.** 쓰기가 한 번만 실패하면 뒤의 `run_failed`가 남고 그것이 그 밖을 든다. 모든 쓰기가 실패하면 지금처럼 결말 없이 올라온다(`FullDiskTrace`). 요약 이벤트는 `_drive` 밖(`_Body.events`)에서 쓰고, 그 쓰기의 실패는 지금처럼 결말 없음이다(to-tickets가 정했다. 명세 검토)
- [ ] **원인을 정하는 갈래는 자리마다 하나이고 기본 갈래를 두지 않는다.** 몸통이 실패를 받는 자리를 닫힌 열거로 두고(연결, 에이전트, 결말 전 쓰기. 요약과 기한은 따로 선 자리다) 자리에서 원인으로 가는 갈래의 빠짐을 pyright가 보게 한다(`assert_never`). 새 자리를 열거에 더하면 원인을 정하지 않은 갈래가 타입 검사에서 빨개진다 — 그것이 목록을 다시 볼 계기다(to-tickets가 정했다. 명세 검토). 타입 검사가 보지 못하는 것이 하나 남는다. 에이전트 자리 안에서 런타임이 새로 던지는 예외를 던지는 자리에서 기억하지 않으면 그 예외는 에이전트 코드로 간다. 그래서 런타임이 에이전트에게 던지는 예외를 더하는 변경은 기억과 원인 단언 테스트를 함께 더한다고 core 실행 모듈의 독스트링에 적는다(셀프 리뷰 명세 축). ADR 0031이 자리를 모르는 예외를 그 밖으로 보는 문장은 여덟 자리 밖에서 런타임이 실패를 받는 자리가 그 밖이라는 뜻으로 읽는다
- [ ] **`run_finished`를 낸 뒤 돌아오지 않고 예외를 낸 에이전트는 지금처럼 실패로 끝난다.** 원인은 위의 일반 규칙대로다 — 빠져나온 예외가 기억한 런타임 예외 그 객체면 그 원인이고 아니면 에이전트 코드다(명세 검토가 고쳤다). 트레이스에는 `run_finished` 뒤에 `run_failed`가 선다(지금 동작)
- [ ] **`run_failed`까지 쓰지 못하면 원인도 없다.** 결말 없음이다(지금 그대로)
- [ ] **진입점은 기한 범위가 만든 `TimeoutError`만 기한으로 본다.** 지금은 진입점이 `except TimeoutError`로 받아, 몸통이 `except Exception`으로 받지 않는 자리(요약 이벤트 쓰기)에서 디스크나 네트워크 드라이브가 낸 `TimeoutError`(`OSError`의 하위, ETIMEDOUT)도 기한이 온 것으로 읽혀 "실행이 N초 안에 끝나지 않았다"와 원인 시간 초과가 쓰인다. 범위의 상태(`fail_after`가 연 범위가 실제로 취소를 걸었는지)로 가르고, 아니면 위의 결정대로 결말 없이 올라오게 한다. 테스트는 요약 이벤트 쓰기에서 `TimeoutError`를 내는 가짜 트레이스(PR 직전 `bug-perf-review`)

### 먼저 난 실패와 결말 뒤 닫기

- [ ] **몸통은 "결말을 썼다"(`_settled`의 지금 뜻)와 "쓸 결말을 붙잡았다"를 따로 든다.** 둘을 한 표지로 합치면 붙잡은 실패를 쓰기 전에 기한이 올 때 `deadline_failure`가 없음을 돌려 결말 없이 끝난다
- [ ] **에이전트 몫의 실패(예외, 결말 없이 돌아옴)와 선언 확인의 실패를 도구 연결을 닫기 전에 붙잡고, 원인과 메시지를 모두 그것으로 정한다.** 닫기의 예외는 뒤따른 것이라 버린다. 선언 확인은 to-tickets가 더했다 — 그 실패도 연결 안에서 나서, 붙잡지 않으면 뒤의 닫기 예외가 빠져나와 이 규칙이 그 자리에서만 서지 않는다(명세의 기본 갈래 절 주석)
- [ ] **닫는 도중에 기한이 와도 결말은 붙잡은 실패다.** 진입점은 붙잡은 결말이 있으면 시간 초과 대신 그것을 쓰고, 이미 썼으면 아무것도 덧붙이지 않는다. 지금 이 경우를 시간 초과로 적는 테스트(`test_run_finished_없이_돌아온_뒤_연결을_닫다_기한이_오면_그_결말은_실패다`)의 기대가 바뀐다 — 결말이 하나라는 요점은 그대로다
- [ ] **결말이 정해진 뒤 닫기가 실패하면 `run_failed`를 덧붙이지 않는다.** 지금은 에이전트가 `run_finished`를 낸 뒤 닫기가 예외를 내면 `_drive`의 바깥 `except`가 `run_failed`를 하나 더 쓴다(멈춘 실행만 막는다). 기한 쪽이 이미 막는 것과 같은 기준을 예외 쪽에도 건다. 닫기의 예외는 버린다. 대가가 있다 — 지금은 그 실패가 `run_finished` 뒤의 `run_failed`로 트레이스에 보이는데, 이 티켓 뒤에는 트레이스에도 서버 기록에도 흔적이 남지 않는다. 채널에는 첫 이벤트 뒤 core에서 올라온 예외를 추적 식별자와 함께 서버 기록 한 줄로 남기는 길이 있지만(채널 등록부의 실행 태스크), 그 길로 올리려면 결말을 쓴 뒤 다시 던져야 해 CLI의 종료 코드와 멈춘 실행의 선례(닫기의 예외를 버린다)가 갈린다. 명세의 결정대로 버리고 이 대가를 core 실행 모듈의 독스트링에 적는다(PR 직전 `bug-perf-review`가 짚었다). 그 닫기에서 도구 서버 프로세스가 남는지는 mcp-shutdown이 본다

### 테스트 (core, 가짜 포트)

- [ ] **갈래마다 트레이스의 마지막 `run_failed`가 그 원인을 든다.** 명세 Testing Decisions의 "실패 원인" 목록 전부다
  - 대화 요약: 요약 모델의 예외, 빈 글(기존 "대화 요약 — 실패" 절의 사례에 원인을 더한다)
  - 시간 초과: 모델 호출·도구 호출·요약 호출 도중의 기한(기존 "실행 타임아웃" 절). 요약 도중도 시간 초과다
  - 도구 연결: 연결 실패(`BrokenTools`), 매니페스트가 없는 도구를 가리킴
  - 모델 호출: 모델이 예외를 내고 에이전트가 잡지 않음, 모델에 도구를 붙이다 예외가 남, 잡아 그대로 다시 던짐. 감싸 던지면 에이전트 코드
  - 도구 실패: 직접 부른 도구가 실패를 돌려줌, 예외를 냄, 거부됨(재개)을 에이전트가 잡지 않음
  - 루프 상한: 모델이 10턴 동안 도구만 부름
  - 재개 대조: 재생의 프롬프트 어긋남, 재생의 도구 이름이나 인자의 어긋남, 재생 구간에서 에이전트가 낸 이벤트의 어긋남, 재개 뒤 첫 호출이 다른 도구, 재개 뒤 첫 호출이 도구 대신 모델, 마스킹된 인자. 던지는 자리마다 하나다
  - 에이전트 코드: 에이전트의 예외, `run_finished` 없이 돌아옴, 지어낸 `run_paused` 뒤 돌아옴(`ForgingAgent`), `conversation_summarized`를 냄, 원인 있는·없는 `run_failed`를 냄(01의 사례에 원인을 더한다), 이벤트가 아닌 값을 냄
  - 그 밖: 이벤트 쓰기가 한 번만 실패하는 가짜 트레이스. 모든 쓰기가 실패하면 지금처럼 결말 없이 올라온다
- [ ] **동일성으로 가르는 두 결정을 가르는 사례**(명세 검토). 에이전트가 스스로 만든 `ToolError`를 던지면 에이전트 코드다 — 타입으로 가르는 구현이 빨개진다. 앞서 받은 모델 예외를, 뒤에 받은 `ToolError` 다음에 다시 던지면 모델 호출이다 — 마지막 하나만 기억하는 구현이 빨개진다. 가짜 도구 연결의 실패와 실패하는 가짜 모델로 지금 이음매에서 잰다
- [ ] **먼저 난 실패.** 에이전트가 예외를 낸 뒤 닫기도 실패하면 원인과 메시지가 에이전트의 예외다. 결말 없이 돌아온 뒤 닫기가 실패하면 원인은 에이전트 코드이고 메시지는 결말이 없다는 것이다(`FlakyCloseTools`). 결말 없이 돌아온 뒤 닫는 도중에 기한이 와도 원인은 에이전트 코드다(기존 기한 사례의 기대를 바꾼다). 선언 확인이 실패한 뒤 닫기도 실패하면 원인은 도구 연결이고 메시지는 선언 확인의 것이다(닫기의 예외를 메시지로 남기는 구현이 빨개진다, 셀프 리뷰 명세 축)
- [ ] **결말 뒤 닫기.** `run_finished` 뒤 닫기가 실패하면 `run_failed`가 없고 결말은 끝남이다(`FlakyCloseTools`로 끝나는 에이전트). 멈춘 실행은 기존 사례 그대로다
- [ ] **선례.** "대화 요약"의 "실패" 절, "실행 타임아웃" 절, `FlakyCloseTools`·`WrappingAgent`·`ForgingAgent`

### 면

- [ ] **최종 사용자 경로에서 요약 실패의 실패 항목이 원인 대화 요약을 든다**(`create_app()` + `ASGITransport`)
- [ ] **01이 `null`로 고친 실패 항목의 dict 단언 두 자리를 실제 원인 값으로 고친다**(명세 검토)
- [ ] **운영자 채널 `/runs`의 `run_failed`가 원인을 든다.** 원문 이벤트라 저절로 실리는 것을 사례 하나가 본다
- [ ] **CLI는 바뀌지 않는다.** 실패는 지금처럼 표준 에러에 `실행 실패: <error>`이고 원인을 찍지 않는다

### 지침과 잔존

- [ ] **`.claude/rules/core.md`의 실패 정책에 원인을 적는다.** 런타임이 쓰는 `run_failed`는 모두 원인을 든다는 것, 원인을 정하는 자리와 동일성 규칙, 기본 갈래가 없고 빠짐을 타입 검사가 보는 것, 먼저 난 실패와 결말 뒤 닫기. 실행 타임아웃 항목의 "결말은 이벤트의 종류가 아니라 몸통이 정한다"에 붙잡은 결말을 더한다
- [ ] **core 실행 모듈의 모듈 독스트링(실패의 열거)과 몸통의 `_settled` 주석을 고친다.** 트레이스 쓰기 사례의 독스트링("run_failed 로 바꾸지 못하는 유일한 실패")을 고친다 — 한 번만 실패한 쓰기는 이제 그 밖의 `run_failed`다
- [ ] **01이 틈을 가리켜 쓴 문장을 `02`·`틈`·`기록되지 않은`으로 grep해 지금 동작과 맞게 다듬는다.** 실패 항목 원인 필드의 계약 설명은 옛 트레이스와 틈 동안의 실패가 여전히 `null`이므로 그대로 참인지 본다
- [ ] **잔존이 0이다.** `유일한 실패`를 저장소 전체에서 찾는다(제외 범위는 명세 잔존 grep)

- [ ] **기능을 닫는지는 병합 직전에 판정한다.** `git fetch` 뒤 `origin/main`의 나머지 잎(04·05·06) 티켓 파일 `Status:`가 모두 `done`이면 이 PR이 `.scratch/plan.md`의 end-user-continuation 행을 `done`으로 바꾸고 프론티어 문단을 고친다. 아니면 뒤에 병합되는 잎이 닫는다. main이 최신 기준(strict)이라 뒤에 병합되는 쪽은 앞의 병합을 들인 뒤에야 병합되므로 마지막 잎은 반드시 본다(01은 이 티켓이 막혀 있던 것이라 이미 `done`이다. end-user-channel 티켓 02의 선례)

### 명세 검토가 확인하지 못한 것
