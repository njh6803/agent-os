# 01: 계약 — 위젯이 끝난 실행을 이어 가고, 실패와 시작 이벤트가 원인과 바로가기의 자리를 든다

**What to build:** 사이트가 서명한 토큰으로 최종 사용자 경로의 이어 가기(`POST /end-user/runs/{run_id}/<접미사>`)에 시작과 같은 본문(에이전트, 요청)을 보내면 새 실행이 서고 시작과 같은 최종 사용자 항목 스트림이 온다. 첫 프레임은 새 실행의 시작 항목(`id` 0)이다. 시작처럼 요청 글자 수(422)와 동시·시간당 실행 수(429)를 지난다. 앞 실행이 없거나 남의 것이거나 손상이거나, 요청한 에이전트가 없거나 그 사이트의 열 에이전트 밖이면 같은 404 고정 문구, 앞 실행이 끝나지 않았으면 그 상태를 말하는 409, 꺼졌으면 고정 문구의 409다. 이어 간 실행이 승인 대상에서 멈추면 최종 사용자 경로로 결정하고 구독한다. `run_failed`와 최종 사용자 실패 항목에 실패 원인의 자리가, `run_started`에 바로가기의 자리가 생기고, 계약에 원인의 값 아홉이 닫힌 목록으로 실린다. 에이전트가 `run_failed`를 내면(원인이 있든 없든) 그 실행은 런타임의 `run_failed` 하나로 끝난다. 관리 화면은 새 필드를 알고 컴파일된다. 실제 `serve`에서 최종 사용자 경로로 시작한 실행을 이어 가면 이어 간 답이 앞 대화를 안다.

이 기능의 계약 티켓이고 02~06을 막는다. 계약은 sdk 필드 둘과 원인의 값 집합, `openapi.json`(이어 가기 경로와 그 에러 문서, 이벤트 컴포넌트 둘의 새 필드, 원인의 값 집합 컴포넌트, 실패 항목의 원인 필드)과 그것이 끌고 오는 것 전부다. 끌고 오는 것은 명세가 찾은 여섯(라우트, 컴포넌트 차집합 등식, 손으로 든 오퍼레이션 목록 둘, api-client의 경로 목록과 타입 테스트, 관리 화면의 필드 이름 표, 생성 타입을 단 테스트 픽스처)에 2026-10-16 명세 검토가 더한 둘(실패 항목의 dict 단언 두 자리, 실행 상세의 필드 이름 목록)이다. 오퍼레이션 목록 하나(`test_router.py`)는 명세의 설명과 달리 저절로 빨개진다. 에이전트가 낸 `run_failed`를 막는 동작도 이 티켓이다(명세 검토 blocker). 리뷰의 질문은 "동작하나"가 아니라 이 이름과 모양으로 오래 살 수 있느냐다.

**병합 뒤에 틈이 있다(명세가 받아들였고 to-tickets에서 사용자가 여섯으로 쪼개기를 골랐다).**

- 런타임은 원인을 아직 채우지 않는다. 그동안 쓰인 실패는 원인이 영구히 `null`이라 이 기능 전의 트레이스와 같은 지위다(02가 채운다).
- 런타임은 바로가기를 아직 쓰지 않는다. 그동안 시작한 대화는 바로가기 없음이 이어지는 옛 대화로 남는다(03이 쓴다).
- 이어 가기의 거슬러 읽기는 지금처럼 앞 실행을 하나씩 따라가고 이벤트 루프 위에서 돈다(03·04가 묶는다).
- 이어 가기 경로는 실행을 가리키는 경로라 지금의 표대로 요청한 에이전트의 구성 오류와 깨진 고리도 404다(05가 500으로 바꾼다). 위젯이 아직 없어 그 404에 대화를 지우는 쪽이 없다.
- 관리 화면은 원인과 바로가기를 글자로 보인다(06이 바로가기를 링크로 그린다).

이 티켓이 쓰는 문장(독스트링, 주석, rules, 계약의 설명)은 틈 동안에도 참이어야 한다. 계약과 표와 타입이 약속하는 것을 말하고, 02~05가 들일 동작을 지금 난다고 적지 않는다(conversation 01의 규칙). "런타임이 쓰는 `run_failed`는 모두 원인을 든다", "바로가기를 따라 읽는다", "지도의 패턴을 기록 규칙이 본다" 같은 문장은 이 티켓이 쓰지 않는다.

근거는 `.scratch/end-user-continuation/spec.md`의 "이음매", "계약 티켓", "경로", "실패 원인 — 목록", "에이전트가 낸 `run_failed`", "최종 사용자 실패 항목", "바로가기"(모양), "api-client", "`openapi.json`", "문서 갱신" 절, Testing Decisions의 "`create_app()`과 `ASGITransport`"·"JSONL 어댑터"·"바깥 이음매" 절과 그 2026-10-16 명세 검토·to-tickets 주석이다. ADR 0031과 ADR 0022의 첫째 2026-10-15 이력이 앞선 결정이다.

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

### sdk — 새 필드 둘과 원인의 값

- [ ] **`RunFailed`에 실패 원인의 선택 필드 하나(기본 없음)가 는다.** 값은 명세 "실패 원인 — 목록" 표의 아홉(대화 요약, 시간 초과, 도구 연결, 모델 호출, 도구 실패, 루프 상한, 재개 대조, 에이전트 코드, 그 밖)의 닫힌 목록이다. 직렬화 스키마에서 required이고 `null`을 허락한다
- [ ] **`RunStarted`에 바로가기의 선택 필드 하나(기본 없음)가 는다.** 값은 에이전트 이름에서 실행 식별자로 가는 지도다. 모델에 패턴을 걸지 않는다 — 이벤트의 다른 식별자 필드(`previous_run`)와 같은 규칙이다. 키와 값의 패턴을 기록 규칙이 보는 것은 03이다(명세 검토)
- [ ] **이름(필드 둘, 값 아홉, 값 집합의 타입)은 이 티켓이 짓는다.** 용어집의 "실패 원인"에 기대고, 바로가기는 시작 이벤트의 필드라 용어집에 넣지 않는다(명세 서두). 새 필드 이름은 다른 이벤트의 필드 이름과 겹치지 않는다 — 관리 화면의 필드 이름 표가 필드 이름을 키로 써서 `reason`·`error`·`summary` 같은 이름을 다시 쓰면 "실패 원인"·"바로가기"를 붙일 자리가 없다(명세 검토. 요약 글이 `text`를 피한 선례)
- [ ] **계약에 실리는 모델의 독스트링은 한 줄이고 논증은 `#` 주석이다**(`.claude/rules/http.md`)
- [ ] **sdk 테스트를 따로 두지 않는다.** 새 필드가 선택이고 직렬화 스키마에서 required인 것은 아래 계약 컴포넌트 테스트와 JSONL 어댑터의 옛 줄 읽기가 본다(명세 이음매)

### core — 에이전트가 낸 `run_failed` (명세 검토 blocker)

- [ ] **에이전트가 `run_failed`를 yield하면 원인이 있든 없든 그 실행은 런타임의 `run_failed` 하나로 끝난다.** 메시지가 에이전트가 적은 `error`를 든다. 에이전트의 제너레이터는 그 자리에서 닫힌다. `conversation_summarized`를 막는 갈래와 같은 규칙이고 재생 구간에서도 같다. 그 런타임 `run_failed`의 원인은 아직 없고(틈) 02가 에이전트 코드를 단다
- [ ] **이것이 이 티켓인 이유.** 원인 필드를 싣는 티켓과 갈라지면, 그 사이 main에서 에이전트가 지어낸 원인이 지금의 통과 규칙과 투영을 지나 최종 사용자 실패 항목까지 그대로 나가고 빨개지는 테스트가 없다. ADR 0031의 "원인이 든 `run_failed`는 런타임만 낸다"가 조용히 무효가 된다
- [ ] **core 테스트.** 원인 있는 `run_failed`를 내는 에이전트와 원인 없는 것을 내는 에이전트 각각에서 트레이스의 `run_failed`가 하나이고 메시지가 에이전트의 `error`를 든다. 그 뒤 `run_finished`를 내도 결말은 실패다. 그 뒤 결말 없이 돌아와도 `run_failed`가 둘이 아니다. 최종 사용자 경로에서 실패 항목이 하나다(명세의 "에이전트가 낸 `run_failed`" 이유 절)
- [ ] **`.claude/rules/core.md`의 런타임만 내는 이벤트 항목과 core 실행 모듈의 독스트링을 고친다.** 런타임만 낼 수 있는 이벤트가 `conversation_summarized`와 `run_failed` 둘이 되고, 에이전트가 낸 다른 이벤트를 그대로 통과시킨다는 문장의 예외가 둘이 된다

### JSONL 어댑터

- [ ] **새 필드 둘이 왕복한다.** 필드가 없는 형식 1·2·3 줄은 없음으로 읽힌다(두 필드가 선택이고 기본이 없음). 헤더는 3 그대로다
- [ ] **`.claude/rules/adapters.md`에 형식이 3 그대로이고 새 필드 둘이 든 줄을 이 기능 전의 코드는 손상으로 거부한다는 것을 적는다**(ADR 0031)

### 채널 — 이어 가기 경로

- [ ] **경로는 최종 사용자 접두사 아래 이어 가기다.** 본문은 `StartRun` 그대로이고 새 본문 컴포넌트가 없다. 앞 실행은 경로에만 있다. 실행 식별자는 `verbatim` 변환기와 sdk의 패턴으로 받는다. 접미사가 고유한 까닭은 운영자 채널과 같다. 이어 가기·결정·구독의 경로가 서로 가로채지 않는 것을 라우터 테스트가 고정한다. 경로 이름과 `operation_id`는 이 티켓이 짓고 손으로 준다(운영자 채널의 `continue_run`, 최종 사용자 면의 `start_end_user_run` 모양에 맞춘다)
- [ ] **상한과 판정의 순서는 시작과 같다.** 인증 → 본문 검증 → 요청 글자 수(422, `violations`의 `body.request`) → 동시·시간당 실행(429, 등록부가 실행을 받으며 본다) → core(`run(previous_run=, visible_agents=, timeout_seconds=)`). 이어 가기도 동시 실행의 칸을 차지하고 시간당 셈에 든다. 남의 앞 실행에 보낸 이어 가기도 404보다 429가 먼저다
- [ ] **채널은 앞 실행의 존재·상태·주체도 에이전트가 열 에이전트 목록 안인지도 먼저 확인하지 않는다.** 상태 코드 테스트는 먼저 확인하는 구현으로도 초록이라 이것은 리뷰가 본다(`.claude/rules/channel.md`)
- [ ] **응답은 시작과 같은 항목 스트림이다.** 첫 프레임은 새 실행의 시작 항목(`id` 0)이고 앞 실행과 바로가기는 항목에 싣지 않는다. 대화 요약 이벤트는 프레임 없이 인덱스만 지난다(지금 투영 그대로)
- [ ] **문서화된 에러는 401, 404, 409, 422, 429, 500이다.** 422 설명은 시작 경로의 것(요청 글자 수의 단위 코드 포인트와 기본값 20,000자)을 나눠 쓴다. 기존 422 설명 테스트에 이어 가기를 더한다(스토리 22, 명세 검토)
- [ ] **HTTP 사례**(`create_app()` + `ASGITransport`, 둘째 구동자는 스트림의 수명에만). 스트림이 시작 항목부터 끝남 항목까지 오고 트레이스의 `run_started`가 앞 실행을 든다. 404(앞 실행 없음, 남의 앞 실행, 남의 손상된 앞 실행, 요청한 에이전트가 없음, 열 에이전트 밖)가 같은 고정 문구다. 409(앞 실행이 실패·일시정지·결말 없음은 상태를 말하고, 꺼짐은 고정 문구). 422(요청 글자 수 초과의 `violations`, 경로 패턴은 포트를 부르지 않음, 본문의 추가 필드). 429(동시 실행과 시간당 실행이 이어 가기를 센다). 모두 JSON 봉투이고 CORS 헤더가 붙는다. 500 사례는 덮기를 바꾸는 05가 더한다 — 이 티켓에서는 지금의 표대로 404다
- [ ] **이어 간 실행이 승인 대상에서 멈춘 뒤 최종 사용자 경로로 결정하고 구독한다**(스토리 13, 명세 검토). 이어 간 실행도 그냥 실행이다
- [ ] **손으로 든 오퍼레이션 목록 둘에 이어 가기를 더한다.** `test_router.py`의 것은 `test_409_는_채널_라우트에만_있다`가 409를 문서화한 오퍼레이션 전부와 순서까지 등호로 보므로 저절로 빨개지고, 라우터에 등록한 차례대로 더한다. `test_end_user.py`의 것은 저절로 덮지 않는다(명세 검토). 인증 전수 검사는 새 경로가 서명 토큰으로만 열린다는 것을 저절로 덮는다 — 돌려서 본다
- [ ] **실행 타임아웃을 넘긴다.** 채널 라우터가 받은 `run_timeout_seconds`를 이어 가기의 `run()`에도 `timeout_seconds`로 넘긴다

### 투영과 실패 항목

- [ ] **최종 사용자 실패 항목이 원인 필드를 하나 더 든다.** 값은 이벤트의 원인과 같은 값 집합이고 계약에서 같은 컴포넌트를 가리킨다. 직렬화 스키마에서 required이고 `null`을 허락한다(거부 사유 `reason`의 모양). 고정 문구와 실행 식별자는 그대로다. 항목 유니온의 멤버는 일곱 그대로다
- [ ] **원인 필드의 계약 설명은 틈 동안에도 참인 말로 쓴다.** 예를 들면 "원인이 기록되지 않은 실패는 `null`"이다. "옛 트레이스"라고만 쓰면 이 티켓과 02 사이에 쓰인 실패가 그 설명을 거짓으로 만든다(명세 검토)
- [ ] **투영은 종류로만 가르고 `run_failed`의 원인을 그대로 옮긴다.** 원인 없는 옛 `run_failed`를 구독이 다시 보내면 항목의 원인이 `null`이다(테스트)
- [ ] **실패 항목을 dict 등호로 단언하는 `test_end_user.py`의 두 자리를 원인 `null`로 고친다.** 저절로 빨개진다. 02가 실제 값으로 한 번 더 고친다(명세 검토)
- [ ] **실패 항목 모듈의 주석 "실패 원인을 항목에 싣는 것은 end-user-continuation 이 더한다"를 지금 사실로 고친다**

### `openapi.json`과 생성 클라이언트

- [ ] **계약 파일이 `create_app().openapi()`와 같다.** 바뀌는 것: 이어 가기 경로와 그 에러 문서, `RunFailed`와 `RunStarted`의 새 필드, 실패 원인의 값 집합 컴포넌트, 최종 사용자 실패 항목의 원인 필드. 바뀌지 않는 것: 에러 코드 여섯, 시작·결정·구독의 본문과 경로, 트레이스 형식의 열거(`"3"`까지), 404·500의 공유 설명
- [ ] **채널 테스트의 컴포넌트 차집합 등식(`EXISTING_COMPONENTS`)을 고친다.** 원인의 값 집합이 이름 있는 컴포넌트로 서면 저절로 빨개진다. 항목 유니온의 멤버 수를 보는 테스트는 그대로다
- [ ] **계약 테스트.** 이벤트 컴포넌트 둘의 새 필드와 실패 항목의 원인 필드가 required이고 `null`을 허락하며, 실패 원인의 값이 아홉이다(sdk 테스트를 따로 두지 않는 자리)
- [ ] **같은 커밋에 다시 생성한 클라이언트 타입이 든다.** 생성기가 지도(`additionalProperties`)를 어떤 TS 타입으로 내는지는 돌려서 본다
- [ ] **api-client의 최종 사용자 경로 목록(`EndUserPath`)에 이어 가기가 넷째로 는다.** 관리 클라이언트의 경로 집합에 이어 가기가 없다는 것을 타입 테스트(`clients.test-d.ts`)가 고정한다 — 관리 경로는 생성된 경로에서 채널과 최종 사용자의 경로를 뺀 것이라, 빠뜨리면 이어 가기 경로가 관리 경로로 잘못 들어간다. 목록의 경로 주석을 고친다. 위젯 클라이언트는 web-widget이다

### 관리 화면 — 컴파일

- [ ] **필드 이름 표(`satisfies Record<EventField, string>`)에 두 줄이 는다.** "실패 원인"과 "바로가기". 이것 없이는 `pnpm -C web verify`가 빨갛다. 값은 지금의 글자 그리기 그대로다(바로가기의 링크는 06)
- [ ] **생성 타입을 단 테스트 픽스처가 새 필드를 얻는다.** 실행 상세 페이지 테스트 둘(`RunPage.test.tsx`·`RunPage.decision.test.tsx`)의 시작 이벤트(바로가기 없음), 그리고 실패 이벤트를 생성 타입으로 지은 픽스처가 있으면 그 원인
- [ ] **실행 상세 페이지 테스트가 시작 이벤트의 필드 이름 목록을 `toEqual`로 고정한 자리에 바로가기 줄을 더한다**(명세 검토. 저절로 빨개진다)

### ADR 0031의 이력 한 줄

- [ ] **정한 원인의 목록을 ADR 0031의 이력 한 줄로 남긴다**(ADR 0031의 Consequences "정해진 목록은 계약 티켓이 이 ADR의 이력 한 줄로 남긴다"). 값의 이름과 뜻(명세 표의 "뜻" 열)이고, 가르는 법은 명세와 02가 원천이다. 본문 문장을 거짓으로 만들지 않으므로 포인터를 달지 않는다(`.claude/rules/adr.md`). 사용자 승인은 PR에서 받는다

### 바깥 이음매 (`-m llm`, 사용자가 골랐다)

- [ ] **기존 `test_실제_serve_에서_사이트가_서명한_토큰으로_시작한_실행이_항목과_id_를_흘린다`에 이어 가기 요청 하나를 붙이고 테스트 이름을 붙인 단언에 맞게 고친다.** 그 테스트의 조립(사이트 파일, 서명 토큰, 실제 uvicorn)을 그대로 쓴다
- [ ] **asker 에이전트가 대화 멤버의 교환을 프롬프트에 엮는다.** 이어 가지 않은 실행의 프롬프트는 요청 그대로라 기존 단언이 선다. asker는 이 테스트 하나만 쓴다
- [ ] **첫 요청이 이름 같은 사실을 주고 이어 간 요청이 그것을 묻는다.** 이어 간 스트림의 프레임이 시작 항목(`id` 0)과 끝남 항목이고, 이어 간 실행의 출력에 그 사실이 있으며, 트레이스의 `run_started`가 앞 실행을 든다. 지도 단언은 03이 더한다(to-tickets에서 사용자가 골랐다)
- [ ] **지금 테스트는 트레이스 파일 하나를 전제한다(`(trace_file,) =`).** 실행이 둘이 되므로 그 자리를 고친다

### 지침과 잔존

- [ ] **rules 다섯을 고친다.** `sdk.md`(이벤트의 새 필드 둘과 원인의 값 집합. 바로가기는 모델에 패턴을 걸지 않는다는 것까지), `adapters.md`(위), `channel.md`(최종 사용자 경로 넷, 이어 가기의 상한 셈과 타임아웃, 실패 항목의 원인, "남의 실행에 낸 결정과 구독 … 404보다 429가 먼저"에 이어 가기), `http.md`(이어 가기의 422 설명이 시작 경로의 것을 나눠 쓴다. 실행을 가리키는 경로의 열거에 이어 가기를 더한다 — 05가 그 문장을 다시 쓴다), `core.md`(위 런타임만 내는 이벤트). 동작의 문장(원인의 갈래, 바로가기, 교환 수, 상한, 스레드, 덮기)은 그 동작을 들이는 티켓이 쓴다(명세)
- [ ] **실행을 가리키는 경로를 "결정, 구독"으로 열거한 자리**(`http.md`, 표의 면 열거 독스트링, 최종 사용자 면 모듈 독스트링)에 이어 가기를 더한다. 틈 동안 이어 가기 경로도 그 면이라 이것이 참이다
- [ ] **잔존이 0이다.** `아래 셋이다`, `경로 셋`, `경로_셋`, `면의 셋`, `그대로 통과`, `` 예외는 `conversation_summarized` 하나 ``를 저장소 전체에서 찾는다. 테스트 이름 `test_경로_셋이_…`와 `test_router.py`의 409 테스트 독스트링 "최종 사용자 면의 셋"이 걸린다(명세 검토). 그리고 동시 실행의 칸과 시간당 셈에 드는 것을 "시작과 결정"으로 열거한 자리를 `시작과 결정`·`시작·결정`으로 찾아 이어 가기를 더한다(셀프 리뷰 표준 축. `serve`의 상한 진단, 최종 사용자 면 모듈 독스트링, 상한·등록부 모듈이 걸린다) — 이 둘은 다른 뜻으로도 걸리므로 칸과 셈을 말하는 자리만 고친다. 무엇이 기록이라 제외되는지는 `docs/constitution/operations.md` 문서 위치 절이 정하고(살아 있는 문서 안의 이력도 기록이다), `.claude/worktrees/` 아래도 제외한다. 글자 grep은 같은 뜻의 다른 말을 놓치므로 걸린 것 둘레도 읽는다. 명세의 나머지 잔존 말은 02~05가 지운다
- [ ] **이 티켓이 새로 쓰거나 고치는 문장은 전부 틈 동안에도 참이다.** 02~06이나 틈을 가리켜 쓴 문장은 뒤 티켓이 `02`~`06`·`틈`으로 grep해 다시 읽는다
