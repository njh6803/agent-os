# 02: 위젯 빌드가 사이트 파일을 읽지 않고 `frame-ancestors 'none'`으로 지으며, 서비스 시작이 뜰 때 그 값을 사이트 파일의 허용 출처로 바꿔 넣는다

**What to build:** 운영자가 사이트 파일에 허용 출처를 더하거나 빼고 위젯을 다시 띄우면, 그 출처의 페이지가 위젯 페이지를 품을 수 있게 되거나 더는 품지 못한다(사용자 이야기 3, 4, 27). 다시 빌드하지 않는다. 빌드는 사이트 파일을 읽지 않고 응답 머리를 아무도 품지 못한다는 값(`frame-ancestors 'none'`)으로 짓고, 응답 머리 목록(`.next/routes-manifest.json`)의 원본을 남긴다. 서비스 시작이 뜰 때마다 그 원본에서 값 하나를 바꾼 사본을 Next가 읽는 자리에 쓴다. 그래서 한 번 빌드한 산출물을 사이트 파일만 바꿔 가며 다시 띄울 수 있다(29). 바꿀 자리가 기대한 모양이 아니면 위젯이 틀린 값으로 조용히 뜨지 않고 까닭을 말하며 끝난다(14). 사이트 파일의 진단은 "다시 빌드한다"가 아니라 "다시 띄운다"고 말한다(8). 서비스 시작의 길은 빌드 도구를 불러오지 않는다. Next의 판을 올리는 PR에서 산출물의 모양이 바뀌었으면 그 PR의 위젯 e2e가 빨개진다(31). iframe 방식의 임베드 코드는 그대로다(24).

근거는 명세 `.scratch/widget-runtime-values/spec.md`의 "품어도 되는 사이트를 알리는 응답 머리", "시작 래퍼의 세 명령"(빌드 행과 서비스 시작의 응답 머리 몫, 원본을 남기는 항목, 빌드 도구를 불러오지 않는 항목), "사이트 파일이 없거나 깨졌을 때"의 진단 문장, "위젯 이미지"의 쓰는 자리 항목, "구현 티켓이 코드와 같은 티켓에서 고치는 문서", "티켓을 나눌 때 함께 둘 것"의 응답 머리 티켓, Testing Decisions의 둘째·셋째 이음매다. 결정은 ADR 0064 결정 "허용 출처와 요청 글자 수 상한"이고, 이 방법이 Next가 문서로 약속하지 않은 파일의 모양에 기댄다는 대가도 그 ADR이 적었다. 측정은 `.scratch/widget-runtime-values/probes/prebuilt_start/`의 결과 1, 2, 3, 5, 7이다. 이 티켓의 "명세 검토"와 그 글자는 일지 `docs/journal/2026-11-27-1523-widget-runtime-values-tickets.md`의 "명세 검토" 절을 가리킨다.

빌드를 닫는 일과 뜰 때 바꿔 넣는 일은 한 티켓에 든다. 빌드만 닫히면 모든 위젯이 어느 사이트에도 품기지 못하고, 바꿔 넣는 쪽만 들어가면 사이트 파일의 값을 굳힌 산출물에서 자리를 찾지 못해 서비스 시작이 멈춘다(명세 "티켓을 나눌 때 함께 둘 것"). 세션이 도중에 인계되면 아래 묶음 단위로 끊되, 빌드와 원본과 바꿔 넣기는 한 커밋에 든다.

이 티켓은 헌법(`docs/constitution/tech.md`, `operations.md`)을 고치고 판을 올리지만 이 기능의 첫 티켓이 아니다. `docs/agents/issue-tracker.md`의 "계약(… 헌법)을 바꾸는 티켓은 그 기능의 첫 티켓이며 다른 티켓을 막는다"의 예외다. 고치는 문장(위젯 빌드가 사이트 파일을 읽어 두 값을 싣는다, 위젯 e2e가 같은 사이트 파일로 빌드한 위젯을 띄운다)은 빌드가 사이트 파일을 읽지 않게 되는 이 변경에서야 거짓이 되므로 이 변경에 실어야 한다(명세 "구현 티켓이 코드와 같은 티켓에서 고치는 문서"). 이 티켓은 03을 막으므로, 헌법을 바꾸는 티켓이 그 뒤의 티켓보다 먼저 선다는 규약의 뜻은 지킨다. 선례는 postgres-foundation 03과 design-system 02다(셀프 리뷰).

**Blocked by:** 01(서비스 시작이 사이트 파일을 읽고 값 파일을 쓴 뒤에 Next를 부르는 준비 단계)

**Status:** ready-for-agent

### 빌드

- [ ] 빌드(`build`)가 사이트 파일을 읽지 않는다. 사이트 파일의 환경 변수가 있어도 산출물이 같고, 응답 머리는 `frame-ancestors 'none'`으로 굳는다(명세 "시작 래퍼의 세 명령"의 빌드 행). 빌드 때의 Next 설정(`web/apps/widget/next.config.ts`)이 사이트 파일을 읽지 않게 하는 방법은 구현이 고른다. 개발 서버에서는 지금처럼 그 설정이 뜰 때 사이트 파일을 읽어 응답 머리를 낸다(같은 절의 개발 서버 항목). 페이지 안 스크립트를 짓는 설정은 01이 이미 사이트 파일을 보지 않게 했다
- [ ] 빌드가 끝나면 응답 머리 목록의 원본이 남아 있다. 원본은 래퍼의 빌드가 남긴다. 래퍼는 Next의 실행 파일을 같은 프로세스 안에서 돌리고(`web/apps/widget/tools/start.ts`의 `runNext`), Next 16.3.6의 그 실행 파일은 빌드가 끝나기를 기다리지 않고 돌아오고(`program.parse`) 빌드를 마치면 `process.exit(0)`으로 끝난다. 그래서 Next를 부른 줄 뒤의 복사는 빌드보다 먼저 돌아 앞 빌드의 낡은 목록을 남기거나 목록이 없어 실패한다(명세 검토 D, 셀프 리뷰). 프로세스가 끝날 때 도는 처리기, 빌드를 자식 프로세스로 돌리기 같은 길 가운데 구현이 고르고, 고른 길을 래퍼의 머리 주석에 까닭과 함께 적는다. 원본의 이름과 자리도 구현이 고른다
- [ ] `@agent-os/site-file`의 `buildInput`은 이 티켓 뒤에 빌드가 아니라 서비스 시작과 개발 서버가 부른다. 이름을 그대로 둘지 바꿀지는 구현이 고른다. 바꾸면 그 이름을 든 주석과 문서도 함께 고친다(명세 검토의 nit)

### 서비스 시작이 응답 머리를 바꿔 넣는다

- [ ] 서비스 시작(`start`)이 01의 값 파일을 쓴 뒤, 원본을 JSON으로 풀어 머리의 이름이 `Content-Security-Policy`이고 값이 `frame-ancestors`로 시작하는 자리를 찾는다. 그 자리가 정확히 하나이고 값이 글자 그대로 `frame-ancestors 'none'`일 때만 합친 허용 출처를 공백으로 이은 `frame-ancestors <출처> <출처>`(목록이 비면 `'none'`)로 바꾼 사본을 Next가 읽는 자리에 쓰고, 그 뒤에 Next를 부른다. 자리가 없거나, 둘 이상이거나, 값이 다르면 아무것도 쓰지 않고 까닭을 적은 진단과 함께 종료 1로 끝난다(명세 "바꿀 자리를 찾는 규칙"과 "넣는 값"). 원본은 고치지 않는다
- [ ] 머리의 이름은 대소문자를 가리지 않고 견준다(명세 셋째 이음매의 첫 항목, 명세 검토의 nit)
- [ ] 사본은 그 자리를 열어 바로 쓴다. 임시 파일에 쓴 뒤 이름을 바꿔 덮지 않는다(명세 "위젯 이미지"의 쓰는 자리 항목, 명세 검토 H)
- [ ] 진단은 운영자가 할 일을 말한다. 자리를 찾지 못한 진단은 사이트 파일이 아니라 그 판의 산출물의 문제라는 것이 읽히게 쓴다. 03이 배포 안내의 문제 해결에 이 진단을 들어 "앞 판으로 되돌리고 알린다"를 적는다(명세 "배포 안내"의 문제 해결 항목)
- [ ] 서비스 시작의 길이 스크립트를 짓는 도구를 불러오지 않는다. 지금 `start.ts`는 `./element.ts`를 정적으로 불러와 어느 명령에서나 Vite와 Tailwind의 Vite 플러그인을 함께 불러온다. 빌드와 개발 서버에서만 그것을 불러오게 바꾼다(명세 "시작 래퍼의 세 명령"의 둘째 항목). 서비스 시작이 기대는 파일(시작 래퍼, Next 설정, `@agent-os/site-file`)이 TypeScript 패키지 없이 Node만으로 도는지도 함께 본다. 03의 이미지에는 그 셋이 없다

### 진단 문장

- [ ] `web/packages/site-file/src/site-file.ts`의 진단 끝 문장 "고친 뒤 다시 빌드한다."를 "고친 뒤 위젯을 다시 띄운다."로 고친다(명세 "사이트 파일이 없거나 깨졌을 때"). 같은 문장의 뒤("… 를 빼면 어느 사이트도 위젯을 iframe 으로 품지 못한다")는 그대로 맞는지 본다. 고친 문장을 단언하는 사례를 둔다(사용자 이야기 8, 명세 검토 K)

### 시험(명세 Testing Decisions 셋째 이음매의 응답 머리 몫)

- [ ] 바꿀 자리를 찾는 규칙. 자리가 정확히 하나이고 값이 `'none'`이면 그 값만 바뀌고 다른 머리 규칙(글꼴, 스크립트, 값 파일에 다는 머리)은 글자 그대로다. 자리가 없을 때, 둘일 때, 값이 `'none'`이 아닐 때, 이름의 대소문자만 다를 때를 넣는다. 실패하는 갈래는 아무것도 쓰지 않았다는 것과 진단의 글을 단언한다
- [ ] 차례. `web/apps/widget/tools/start.test.ts`에서 서비스 시작이 값 파일과 사본을 쓴 뒤에 Next를 부르고, 사본을 쓰지 못하면 부르지 않는다(명세 검토 F. 성공하는 갈래를 보는 길은 01이 고른 것을 따른다)
- [ ] `web/apps/widget/tools/start.spawn.test.ts`의 "상대 경로로 준 사이트 파일을 래퍼를 부른 자리에서 찾고, 읽지 못하면 빌드가 그 진단으로 실패한다"를 빌드가 사이트 파일을 읽지 않는 행동에 맞게 바꾼다. 서비스 시작 쪽 같은 사례는 01이 더했다(명세 "함께 바뀌는 지금의 사례")
- [ ] 같은 파일에 서비스 시작이 빌드 도구 없이 서는 사례를 둔다. Vite, Tailwind의 Vite 플러그인, TypeScript를 불러오면 실패하는 로더로 서비스 시작을 부른다. 이 시험에는 빌드 산출물(원본)이 없고 래퍼가 쓰는 자리가 저장소의 앱 폴더라(`start.ts`의 `APP`), Next를 부르는 자리까지 가게 두면 원본이 없어 멈추거나 저장소에 쓴다. 그래서 없는 사이트 파일을 주어 아무것도 쓰기 전에 끝나게 하고, 로더의 거절이 아니라 사이트 파일의 진단으로 끝나는지 본다. 래퍼가 처음 불러오는 모듈의 정적 불러오기는 이것으로 잡힌다. 01이 차례의 성공 갈래에서 쓸 자리를 시험이 주는 길을 골랐으면 원본도 그 자리에 주어 Next를 부르는 자리까지 본다. 뒤 단계에서 늦게 불러오는 것은 03의 단독 배포 e2e가 본다(명세 셋째 이음매, 명세 검토 G, 셀프 리뷰)
- [ ] `web/apps/widget/next.config.test.ts`의 묶음 "변수가 준 사이트 파일을 읽지 못하면 빌드가 실패한다"와 Next의 설정이 사이트 파일을 읽어 `frame-ancestors`를 빌드에 싣는 사례들("두 언어가 함께 읽는 사이트 파일의 합친 허용 출처가 frame-ancestors 에 …"가 그 예다)은 빌드 때의 설정이 사이트 파일과 무관하게 `'none'`을 낸다는 것과, 개발 서버에서는 지금처럼 사이트 파일을 읽어 응답 머리를 낸다는 것을 보게 바뀐다. 어느 사례가 이 파일에 남고 어느 사례가 서비스 시작의 시험으로 옮겨 가는지는 고른 방법에 따라 정한다(명세 "함께 바뀌는 지금의 사례")
- [ ] 이 이음매에서는 실제 `next build`를 돌리지 않는다. 실제 빌드가 낸 산출물의 모양은 아래 위젯 e2e의 준비가 지난다

### 위젯 e2e와 위젯 테스트 페이지 e2e(명세 Testing Decisions 둘째 이음매의 응답 머리 몫)

- [ ] `web/apps/widget/e2e/stack.ts`의 준비가 빌드에는 띄울 때와 값이 다른 사이트 파일(미끼)을 주고, 띄울 때 사이트 파일을 준다. 빌드가 사이트 파일을 읽어 버리면 미끼의 허용 출처가 산출물에 들어 "허용 출처의 페이지는 위젯을 품고 허용 밖 출처의 페이지는 품지 못한다"가 빨개진다(명세 검토 L). 준비가 실제 빌드의 산출물을 래퍼로 띄우므로, 원본이 남지 않았거나 산출물의 모양이 달라 자리를 찾지 못하면 준비에서 멈춘다
- [ ] 사례가 위젯만 다시 띄우는 손잡이를 짓는다. 지금은 준비(`globalSetup`)가 위젯 프로세스를 쥐고 있어 사례가 잡을 길이 없다(`web/apps/widget/playwright.config.ts`, 명세 검토 E). 준비가 사례에 다시 띄우는 길을 내주거나 그 사례만 따로 위젯을 띄우는 꼴 등이고 구현이 고른다. 다시 띄우기 전에 앞 위젯을 끈다. 같은 앱 폴더의 값 파일과 사본을 덮어쓰기 때문이다(명세 "시작 래퍼의 세 명령"의 마지막 항목)
- [ ] 그 손잡이로 사례를 더한다. 한 번 빌드한 산출물로 사이트 파일을 바꿔 위젯만 다시 띄우면 응답 머리와 값 파일과 입력창의 상한이 새 값을 따른다. 값이 빌드에 굳는 판이라면 실패하는 사례다. 사례들이 띄워 둔 위젯 하나를 차례로 함께 쓰므로(`workers: 1`) 끝에 원래의 사이트 파일로 다시 띄워 뒤의 사례에 넘긴다(명세 둘째 이음매의 둘째 항목)
- [ ] `web/apps/portal/e2e/stack.ts`도 빌드와 띄우기를 가른다. 띄울 때 그 e2e의 사이트 파일을 주고, 빌드에 미끼를 줄지는 구현이 고른다(명세 "티켓을 나눌 때 함께 둘 것"의 셋째 항목). 다시 띄우는 사례는 그 e2e에 더하지 않는다
