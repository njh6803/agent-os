# 01: 위젯이 뜰 때 사이트 파일의 두 값을 값 파일(`/widget/runtime.json`)로 쓰고, 화면과 페이지 안 스크립트가 그 파일을 받아 입력창의 상한과 허용 출처로 쓴다

**What to build:** 운영자가 사이트 파일의 요청 글자 수 상한을 고치고 위젯을 다시 띄우면, 위젯의 입력창이 새 상한까지만 받는다(사용자 이야기 5, 22). 위젯이 뜰 때 시작 래퍼가 사이트 파일을 읽어 값 파일을 쓰고, 받은 허용 출처와 상한을 로그 한 줄로 찍는다(9). 값 파일은 위젯 출처의 `/widget/runtime.json`이고, 허용 출처와 상한 두 키만 든 JSON이다(19). iframe 방식의 페이지와 페이지 안 방식의 스크립트가 열릴 때 이 파일을 받는다(25). 받는 동안 위젯은 틀만 그리고 입력을 막으며, iframe 방식은 토큰을 묻지 않는다(20). 받지 못하면 늦어도 10초 안에 알림이 뜬다. 다시 받으면 풀릴 수 있는 실패에는 "위젯 설정을 받아 오지 못했습니다."와 "다시 시도" 단추가, 값 파일이 없는 404에는 지금의 "위젯 설정이 올바르지 않습니다."가 뜬다(21). 페이지 안 방식의 스크립트가 상한을 담지 않으므로, 그 스크립트의 내용과 무결성 해시는 운영자가 사이트 파일을 고쳐도 바뀌지 않는다(26). 개발 서버도 뜰 때 값 파일을 쓴다(28). 브라우저 쪽에서 두 값을 읽는 자리는 여전히 하나다(30).

이 티켓 뒤에도 빌드는 지금처럼 사이트 파일을 읽어 응답 머리(`frame-ancestors`)를 굳힌다. 그 값을 뜰 때 바꿔 넣는 일은 02의 것이다. 지금의 위젯 이미지는 뜰 때 빌드한 뒤 서비스 시작을 부르므로(`deploy/images/widget.Dockerfile`의 `CMD`), 이 티켓만 들어간 이미지도 사이트 파일의 두 값을 따를 것으로 본다(명세의 어림. 아래 검증의 단독 배포 e2e가 확인한다).

근거는 명세 `.scratch/widget-runtime-values/spec.md`의 "값 파일", "합친 허용 출처와 가장 작은 상한", "시작 래퍼의 세 명령"(서비스 시작과 개발 서버의 값 파일 몫), "사이트 파일이 없거나 깨졌을 때", "브라우저 쪽이 값을 받는 길", "위젯 이미지"의 쓰는 자리 항목(링크를 따라 바로 쓴다), "구현 티켓이 코드와 같은 티켓에서 고치는 문서", "티켓을 나눌 때 함께 둘 것"의 값 파일 티켓, Testing Decisions의 둘째·셋째·넷째 이음매다. 결정은 ADR 0064 결정 "허용 출처와 요청 글자 수 상한"이다. 측정은 `.scratch/widget-runtime-values/probes/prebuilt_start/`다. 이 티켓의 "명세 검토"와 그 글자(A, B 같은 것)는 일지 `docs/journal/2026-11-27-1523-widget-runtime-values-tickets.md`의 "명세 검토" 절을 가리킨다. 받지 못했을 때의 두 갈래는 같은 일지의 "사용자에게 물은 것: 받지 못했을 때와 티켓 나누기"에서 사용자가 골랐다.

쓰는 쪽, 받는 쪽, 값 파일에 다는 머리 규칙은 한 티켓에 든다. 셋 가운데 하나만 들어가면 모든 위젯이 설정 오류로 닫히거나 페이지 안 방식만 닫힌다(명세 "티켓을 나눌 때 함께 둘 것"). 세션이 도중에 인계되면 아래 묶음 단위로 끊되, 쓰는 쪽과 받는 쪽과 머리 규칙은 한 커밋에 든다.

**Blocked by:** 없음

**Status:** ready-for-agent

### 서비스 시작과 개발 서버가 값 파일을 쓴다

- [ ] `web/apps/widget/tools/start.ts`의 서비스 시작(`start`)이 듣는 주소를 검사한 뒤 사이트 파일을 읽고, 값 파일을 쓰고, 받은 값을 한 줄로 찍은 뒤에 Next를 부른다. 어느 단계든 실패하면 진단을 찍고 Next를 부르지 않은 채 종료 1로 끝난다(명세 "시작 래퍼의 세 명령"의 표와 "사이트 파일이 없거나 깨졌을 때"). 사이트 파일의 환경 변수가 없으면 멈추지 않고 빈 허용 출처와 기본 상한 20000으로 쓴다. 진단은 지금 빌드가 내는 것(`web/packages/site-file/src/site-file.ts`)을 그대로 쓴다. 그 끝 문장 "고친 뒤 다시 빌드한다"를 "다시 띄운다"로 고치는 일은 빌드가 사이트 파일을 읽지 않게 되는 02의 것이다
- [ ] 개발 서버(`dev`)의 준비 단계도 값 파일을 쓴다(사용자 이야기 28). 개발 서버의 응답 머리는 지금처럼 Next의 설정이 뜰 때 사이트 파일을 읽어 낸다
- [ ] 값 파일은 `web/apps/widget/public/runtime.json`이고 Next가 공개 파일로 `/widget/runtime.json`에 낸다. 두 값은 지금 빌드가 쓰는 `@agent-os/site-file`의 같은 함수(`buildInput`)가 낸다(명세 "합친 허용 출처와 가장 작은 상한"). 키는 `allowedOrigins`와 `requestChars` 둘뿐이다. 상한이 `Number`로 바꿀 때 무한대가 되면(약 1.8×10^308 이상) 가장 큰 유한한 수(`Number.MAX_VALUE`)로 쓴다. 그대로 두면 JSON에 `null`로 나가, 위젯이 다시 시도로도 풀리지 않는 알림에 갇힌다(명세 셋째 이음매의 "값 파일의 모양", 셀프 리뷰)
- [ ] 값 파일은 그 자리를 열어 바로 쓴다. 임시 파일에 쓴 뒤 이름을 바꿔 덮지 않는다. 03이 그 자리를 쓰는 폴더 안을 가리키는 링크로 바꿀 때 이 코드를 다시 고치지 않게 하려는 것이다(명세 "위젯 이미지"의 쓰는 자리 항목, 명세 검토 H)
- [ ] 뿌리 `.gitignore`의 위젯 줄들(시작 래퍼가 짓는 파일들)에 `/web/apps/widget/public/runtime.json`을 더한다
- [ ] 받은 값을 알리는 줄에는 합친 허용 출처의 목록과 상한만 싣는다. 사이트 파일의 다른 값(공개 키, 발급자, 열 에이전트)은 싣지 않는다(명세 "값 파일"의 "비밀이 아니다")

### 값 파일의 응답 머리와 빌드가 싣던 값

- [ ] `web/apps/widget/next.config.ts`의 `headers`에 `/runtime.json`의 `Access-Control-Allow-Origin: *`를 글꼴과 스크립트의 규칙 옆에 더한다. 캐시 머리는 더하지 않는다(명세 "값 파일"의 "누가 읽는가"와 "캐시")
- [ ] 브라우저 쪽이 더는 읽지 않는 빌드 값을 걷는다. Next 설정의 `env`가 싣는 두 이름과, 페이지 안 스크립트를 짓는 설정(`web/apps/widget/tools/element.ts`의 `elementBuildConfig`)이 `process.env.AGENT_OS_WIDGET_REQUEST_CHARS`로 박는 상한이다. 그래서 스크립트의 내용이 사이트 파일과 무관해진다(사용자 이야기 26). 두 이름(`WIDGET_ORIGINS_ENV`, `WIDGET_REQUEST_CHARS_ENV`)을 쓰는 다른 자리가 남지 않으면 `@agent-os/site-file`의 내보내기에서도 걷는다(이 티켓을 쓸 때 그 이름이 든 파일은 `web/` 안에 일곱이었다, Grep했다)
- [ ] 빌드 때의 Next 설정은 이 티켓에서 바꾸지 않는다. `frame-ancestors`는 지금처럼 빌드가 사이트 파일에서 굳힌다

### 브라우저 쪽이 값 파일을 받는다

- [ ] 두 값을 읽는 자리(지금 `web/apps/widget/lib/build.ts`)가 값 파일을 받아 온 결과를 주게 바꾸고, 다른 코드는 그 자리를 거쳐서만 값을 읽는다(명세 "브라우저 쪽이 값을 받는 길"의 첫 항목)
- [ ] iframe 방식의 페이지는 자기 출처의 `/widget/runtime.json`을, 페이지 안 방식의 스크립트는 자기가 실려 온 출처의 `/widget/runtime.json`을 받는다(`web/apps/widget/element/base.ts`의 기준 주소). 기준 주소를 얻지 못하면 받지 않는다. 쿠키와 자격 증명은 싣지 않는다. iframe 방식은 두 값을, 페이지 안 방식은 상한만 쓴다
- [ ] 값 파일을 받는 파일 하나에만 전역 `fetch`를 푼다. `web/eslint.config.mjs`에 위젯 테스트 페이지의 예외(`PORTAL_PAGE_SCRIPT`, `HTTP_GLOBALS_WITHOUT_FETCH`)와 같은 꼴로 경로와 까닭을 적고, `web/eslint.config.test.ts`에 그 파일에서는 지나가고 같은 앱의 다른 파일에서는 `no-restricted-globals`로 막히는 사례를 붙인다(명세 검토 A, `.claude/rules/web-workspace.md`)
- [ ] 받는 동안에는 틀(위쪽 띠와 빈 대화 자리)만 그리고 입력을 막는다. iframe 방식은 값을 받기 전에 자기를 품은 페이지에 토큰을 묻지 않고, 이전 대화를 되살리는 일도 값을 받은 뒤에 시작한다(명세 "받는 동안")
- [ ] 받은 답을 읽을 때 두 키만 보고 모르는 키는 무시한다. 허용 출처는 글자의 목록이고, 상한은 1 이상의 정수다. 상한을 안전한 정수(`Number.isSafeInteger`)로 좁히지 않는다. 사이트 파일이 위로 막지 않고 받은 큰 상한에서 위젯이 닫히기 때문이다(명세 셋째 이음매의 "값 파일의 모양")
- [ ] 받지 못했을 때를 두 갈래로 가른다(명세 "받지 못했을 때"). 요청 실패, 5xx, 10초 안에 답 없음, 읽지 못하는 답, 404가 아닌 다른 200 밖의 답에는 알림 "위젯 설정을 받아 오지 못했습니다."와 단추 "다시 시도"를 보이고 입력을 막는다. 단추를 누르면 받는 동안의 화면으로 돌아가 값 파일을 다시 받는다. 404에는 지금의 알림 "위젯 설정이 올바르지 않습니다. 사이트 관리자에게 알려 주세요."를 보이고 "다시 시도"를 그리지 않는다. 스스로 다시 시도하지 않는다
- [ ] 알림과 단추는 디자인 시스템에 있는 부품으로 짓는다(`web/packages/ui/src/components/molecules/Alert.tsx`의 `actions`). 새 부품을 더하지 않는다. 받아 오지 못한 상태의 이야기를 `web/apps/widget/components/pages/WidgetScreen.stories.tsx`에 더한다. 화면 코드를 처음 고칠 때 오는 알림대로 `sync-design-system` `확인`을 부른다
- [ ] 문구는 widget-login-state 명세의 문구 표("위젯 설정을 받아 오지 못했다" 행)와 글자 그대로 같다. 그 기능이 이 알림과 단추를 다시 쓰고 두 받기를 합친다(그 기능 계획 `.scratch/widget-login-state/plan.md`의 "widget-runtime-values 명세가 넘긴 것" 문단)
- [ ] 이 티켓을 시작할 때 기준 브랜치에 widget-login-state가 이미 들었는지 본다. 이 티켓은 막는 것이 없고 그 기능은 widget-admin-server를 기다려서 대개 이 티켓이 먼저 들겠지만(어림), 차례가 정해져 있지는 않다. 그 기능이 먼저 들었으면(위젯 설정을 받는 상태와 "위젯 설정을 받아 오지 못했습니다." 알림과 "다시 시도"가 이미 위젯에 있으면) 그 받는 상태와 알림을 다시 쓰고 새로 짓지 않으며, 두 받기를 하나의 받는 상태와 실패 상태로 합친다. 두 받기 가운데 하나만 실패했을 때 "다시 시도"가 무엇을 다시 받는지는 그 기능의 명세가 정한 대로 따른다(같은 넘김 문단의 마지막 문장, 셀프 리뷰)

### 시험(명세 Testing Decisions 셋째·넷째 이음매의 값 파일 몫)

- [ ] 값 파일의 모양. 허용 출처가 없는 사이트 파일, 사이트가 여럿인 사이트 파일(합친 목록과 가장 작은 상한), 환경 변수가 없을 때를 넣고, 쓴 파일이 두 키만 든 객체와 글자 그대로 같은지 본다(사용자 이야기 19). 2^53을 넘는 상한 하나와 `Number`로 바꿀 때 무한대가 되는 상한 하나를 쓰는 쪽과 읽는 쪽에 함께 넣는다. 뒤의 것은 쓴 파일에 `Number.MAX_VALUE`가 들고, 읽는 쪽이 그 값을 상한으로 받는지 본다
- [ ] 차례. `web/apps/widget/tools/start.test.ts`에서 서비스 시작이 값 파일을 쓴 뒤에 Next를 부르고, 없는 파일·깨진 파일·빈 변수에서는 부르지 않는다. 실패하는 갈래는 Next를 부르지 않았다는 것과 함께 진단의 글을 단언한다(명세 검토 F). 성공하는 갈래는 쓸 자리를 시험이 주어 단언하거나 위젯 e2e에 맡긴다. 래퍼가 앱 폴더를 자기 자리에서 셈하므로(`start.ts`의 `APP`) 그대로 두면 시험이 저장소의 앱 폴더에 쓴다. 지금 "서비스 시작이 `next start`만 부른다"고 단언하는 사례는 값 파일을 쓰는 단계 뒤에 Next를 부르는 차례로 바뀐다(명세 "함께 바뀌는 지금의 사례")
- [ ] 개발 서버의 준비가 값 파일을 쓴다는 사례를 같은 파일에 둔다(사용자 이야기 28)
- [ ] `web/apps/widget/tools/start.spawn.test.ts`에 상대 경로로 준 사이트 파일을 서비스 시작이 래퍼를 부른 자리에서 찾고, 읽지 못하면 그 진단으로 Next를 부르기 전에 끝나는 사례를 더한다. 빌드가 그 진단으로 실패하는 지금의 사례는 빌드가 아직 사이트 파일을 읽으므로 남기고, 02가 바꾼다
- [ ] `web/apps/widget/tools/element.test.ts`의 상한을 싣는 사례들(명세 "함께 바뀌는 지금의 사례"가 든 셋)은 스크립트가 상한을 싣지 않고, 사이트 파일의 환경 변수를 달리 주어도 스크립트를 짓는 설정이 같다는 사례로 바뀐다
