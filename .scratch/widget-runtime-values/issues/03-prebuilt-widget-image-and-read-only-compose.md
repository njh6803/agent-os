# 03: 위젯 이미지를 판을 낼 때 미리 지어 두어 컨테이너가 빌드 없이 뜨고, 단독 compose가 위젯에 읽기 전용 루트와 쓰는 폴더 하나와 시작 유예 30초를 준다

**What to build:** 운영자가 새 판의 위젯 이미지로 `docker compose up -d`를 치면, 위젯 컨테이너가 빌드하지 않고 몇 초 안에 응답하며 메모리를 1.6GiB씩 쓰지 않는다(사용자 이야기 1, 2). 사이트 파일을 고친 뒤 위젯을 다시 띄워도 응답이 끊기는 시간이 몇 초다(6). 위젯 컨테이너의 루트가 읽기 전용이고, 쓰는 자리는 메모리에 두는 폴더 `/run/agent-os-widget` 하나다(10). 상태가 몇 초 안에 healthy가 되고, 뜨지 못한 위젯은 다른 컨테이너와 같은 시작 유예 30초 뒤에 드러난다(11, 12). 배포 안내는 위젯 몫의 메모리 1.6GiB를 요구하지 않고, 이미 위젯을 열어 둔 화면은 새로 고쳐야 새 값을 받는다고 적는다(13, 18). 위젯 이미지는 인터넷이 막힌 곳에서도 뜨고, 지금보다 작으며, 끌 때 금방 꺼진다(15, 16, 17). 값을 바꿔 넣는 단계를 건너뛴 채로는 이미지의 위젯이 서지 않는다(34). 이 PC의 Docker로 실제 이미지를 통째로 띄우는 시험이 이 모두를 확인하고(32), main으로 가는 PR의 CI가 같은 시험을 돈다(33).

근거는 명세 `.scratch/widget-runtime-values/spec.md`의 "위젯 이미지", "단독 compose의 위젯", "배포 안내", "품어도 되는 사이트를 알리는 응답 머리"의 "값을 바꿔 넣는 단계를 건너뛰면", "구현 티켓이 코드와 같은 티켓에서 고치는 문서"의 옛 말 찾기, "티켓을 나눌 때 함께 둘 것"의 둘째 항목, Testing Decisions의 첫째 이음매, Further Notes다. 결정은 ADR 0064 결정 "허용 출처와 요청 글자 수 상한"이고, 이 티켓이 바꾸는 지금의 이미지는 ADR 0056 결정 "위젯 이미지"가 정했다. 측정은 `.scratch/widget-runtime-values/probes/prebuilt_start/`의 결과 1, 2, 4, 5, 6이다. 이 티켓의 "명세 검토"와 그 글자는 일지 `docs/journal/2026-11-27-1523-widget-runtime-values-tickets.md`의 "명세 검토" 절을 가리킨다.

이미지와 compose는 이 티켓에서 함께 바꾼다. 읽기 전용 루트는 쓰는 폴더의 링크가 든 이미지에서만 서고, 시작 유예 30초는 뜰 때 빌드하지 않는 이미지에서만 맞다(명세 "티켓을 나눌 때 함께 둘 것").

**Blocked by:** 02(빌드가 사이트 파일 없이 `'none'`으로 짓고 원본을 남기며, 서비스 시작이 값 파일과 응답 머리 목록의 사본을 쓴 뒤 빌드 도구 없이 Next를 부른다)

**Status:** ready-for-agent

### 위젯 이미지

- [ ] `deploy/images/widget.Dockerfile`이 명세 "위젯 이미지"대로다. 워크스페이스 전체 의존성이 깔린 단계에서 사이트 파일 없이 시작 래퍼로 한 번 빌드하고, 그 단계는 뜬 뒤의 이미지에 남지 않는다. 뜬 뒤의 이미지에는 위젯과 그것이 기대는 워크스페이스 패키지의 운영 의존성(잠금 파일을 얼린 채 깐다), 빌드 산출물, 공개 파일, 서비스 시작에 드는 파일만 담는다
- [ ] 지은 이미지 안에 Vite, Tailwind의 Vite 플러그인, TypeScript와 시험 쪽 패키지가 없고 Next는 있는 것을 본다. 단독 배포 e2e의 사례로 둘 수 있으면 두고, 손으로 본 것이면 명령과 결과를 일지에 적는다
- [ ] 앱 폴더 안의 두 자리(Next가 읽는 응답 머리 목록과 값 파일)를 `/run/agent-os-widget` 안을 가리키는 심볼릭 링크(다른 자리의 파일을 가리키기만 하는 파일. 열면 가리킨 파일이 열린다)로 두고, 그 폴더를 앱 사용자(uid·gid 10001) 소유, 권한 0700으로 만들어 둔다. 이미지를 짓는 PC에서 위젯을 띄운 적이 있어 그 자리에 파일이 남아 있어도 이미지에는 링크만 들게, `deploy/images/widget.Dockerfile.dockerignore`에 `apps/widget/public/runtime.json`을 더한다(명세 "위젯 이미지"의 쓰는 자리 항목, 명세 검토 nit 3). `.next`는 이미 빠져 있다
- [ ] 덜어 내는 것 다섯을 덜어 낸다. 뜰 때의 빌드, 워크스페이스 전체 의존성, `.next`와 `public`을 앱 사용자 소유로 넘기던 `chown`, `next typegen`, tini(컨테이너의 첫 프로세스로 떠서 끄라는 신호를 위젯에 전하는 작은 프로그램)에 주던 프로세스 그룹 옵션 `-g`다. 시작 명령은 사이트 파일의 자리를 넘기고 `start`만 부른다(명세 "위젯 이미지"의 "덜어 내는 것"과 "그대로인 것")
- [ ] 그대로인 것(바탕 이미지와 그 digest(이미지의 내용으로 지은 고유 값. 이 값으로 받으면 같은 이미지만 받는다), tini, 앱 사용자, 루프백 예외의 표지 파일, `NEXT_TELEMETRY_DISABLED=1`, 포트 3000, 라벨 셋)을 그대로 둔다

### 단독 compose

- [ ] `deploy/standalone/compose.yaml`의 `widget` 서비스에 읽기 전용 루트를 주고, `/run/agent-os-widget`을 uid·gid 10001, 권한 0700의 tmpfs(디스크가 아니라 메모리에 두는 폴더. 컨테이너가 꺼지면 비워진다)로 준다. 옵션을 적는 꼴은 같은 파일의 `serve`가 쓰는 꼴을 따른다(명세 "단독 compose의 위젯")
- [ ] 위젯의 상태 확인에서 `start_period: 300s`를 지워 공통 값(30초)을 쓴다. 확인하는 명령은 그대로다
- [ ] 메모리 제한은 지금처럼 두지 않는다. "위젯은 뜰 때 사이트 파일로 빌드하므로 루트를 읽기 전용으로 두지 않고 메모리 제한도 두지 않는다"는 주석을 고친다. 능력 빼기와 권한 상승 막기는 더하지 않는다(명세의 거부한 안)
- [ ] PR 제목의 느낌표를 판정한다(`docs/constitution/operations.md`의 "느낌표의 기준"). 새 이미지는 쓰는 폴더를 이미지 안에도 앱 사용자 소유로 두므로, 운영자가 옛 `compose.yaml`(읽기 전용 루트도 tmpfs도 없고 시작 유예가 300초다)을 그대로 두어도 설 것으로 본다(명세 "위젯 이미지"의 쓰는 자리 항목, 프로브 결과 2의 쓰기 가능한 루트 회차). 새 이미지를 옛 compose 파일로 한 번 띄워 그것을 확인하고 일지에 적는다. 서면 느낌표를 붙이지 않는다. 서지 않으면 느낌표를 붙이고 `docs/release-notes/upgrade/`에 원고를 싣는다

### 배포 안내

- [ ] `deploy/standalone/README.md`의 "서버의 메모리", "4. 띄우기와 확인", "사이트 파일이나 위젯 테스트 페이지 설정을 고쳤을 때", 문제 해결의 "위젯과 관리 화면"을 명세 "배포 안내"대로 고친다. 문제 해결에 더하는 진단은 02가 지은 "응답 머리 목록의 모양이 기대와 다르다"는 진단의 글로 가리킨다
- [ ] "사이트 파일이나 위젯 테스트 페이지 설정을 고쳤을 때"의 502 문장에 적는 시간은 아래 단독 배포 e2e의 다시 띄우는 사례가 프록시를 거쳐 잰 값으로 적는다. 이 명세의 0.60~1.96초는 컨테이너 안에서 잰 값이라 쓰지 않는다(명세 검토 O)
- [ ] `tests/tools/test_deploy_guide.py`가 안내에 있어야 한다고 보는 낱말 가운데 "1.6GiB"(서버의 메모리)를 걷고, 새 "서버의 메모리" 문단의 낱말로 바꾼다. 지금 시험이 그 낱말을 요구하므로 그대로 두면 안내를 고친 커밋이 빨개진다

### 단독 배포 e2e(명세 Testing Decisions 첫째 이음매)

- [ ] `web/packages/e2e-standalone/e2e/deployment.e2e.ts`에 명세 첫째 이음매의 사례 넷이 있다. 위젯 컨테이너가 빌드 없이 뜬다(읽기 전용 루트, healthy, 받은 값을 알리는 한 줄이 있고 Next의 빌드 머리말 "Creating an optimized production build"가 없다. 명세 검토 R). 허용 출처에 든 출처의 페이지만 위젯 페이지를 품는다(품는 쪽의 문서를 어디서 낼지는 명세의 그 항목대로 구현이 고른다. 명세 검토 M). 사이트 파일의 상한을 바꾸고 위젯 컨테이너를 다시 띄우면 값 파일과 위젯 테스트 페이지의 입력창이 새 상한을 따르고, 끝에 되돌린다. 지은 위젯 이미지에서 시작 래퍼를 거치지 않고 Next만 부르면 0이 아닌 코드로 끝난다(사용자 이야기 34, 명세 검토 K)
- [ ] 다시 띄우는 사례가 배포 안내가 운영자에게 주는 명령으로 위젯을 다시 띄우고, 프록시를 거쳐 위젯이 다시 200을 낼 때까지의 시간을 재어 일지에 적는다(명세 검토 O)
- [ ] 위젯 컨테이너의 서비스 정의가 바뀌므로 지금 사례 가운데 위젯을 함께 보는 것(서비스 목록, root가 아닌 사용자, 발행된 포트)이 그대로 초록인지 본다
- [ ] `deployment.e2e.ts`의 `RESTART_TIMEOUT_MS` 주석("다시 띄울 때 위젯이 사이트 파일로 다시 빌드한다")과 `web/packages/e2e-standalone/e2e/env.ts`의 `UP_WAIT_SECONDS` 주석("위젯이 뜰 때 사이트 파일로 빌드하는 시간이 대부분이다")을 고친다. 두 값을 줄일지는 이 티켓이 잰 시간으로 정하고, 줄이면 그 까닭을 주석에 적는다
- [ ] 단독 배포 e2e를 이 PC에서 돌린다. dev로 가는 PR의 CI는 이 e2e를 돌리지 않는다. 결과와 이미지마다 짓는 시간과 e2e 전체 시간을 일지에 적는다. 이야기 2, 15, 16, 17(뜰 때의 메모리, 네트워크 없이 서기, 이미지의 크기, 끄는 시간)은 프로브가 잰 것으로 받치되, 이 실행에서 같은 값을 볼 수 있으면 함께 적는다(명세 Testing Decisions 끝 문단)

### 문서

- [ ] 위젯 컨테이너가 뜰 때 빌드한다고 적은 말을 저장소 전체에서 찾아 살아 있는 문서와 주석에서 고친다(명세 "구현 티켓이 코드와 같은 티켓에서 고치는 문서"의 이미지 티켓 몫). 찾는 말의 예는 "뜰 때 빌드", "다시 빌드", "사이트 파일로 빌드"다. 이 티켓을 쓸 때 본 자리는 `deploy/images/widget.Dockerfile`과 `deploy/standalone/compose.yaml`의 주석, `deploy/standalone/README.md`, 위의 단독 배포 e2e 주석 둘이다. `.github/workflows/ci.yml`의 `e2e-standalone` 잡 주석도 그때 다시 본다. release-image의 명세와 티켓은 끝난 기능의 기록이라 고치지 않는다
- [ ] deploy-package의 기능 계획에 이 명세가 적어 둔 새 값(메모리, 뜨는 시간)이 이 티켓이 잰 값과 어긋나면 그 문단을 고친다
