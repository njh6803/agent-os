# widget-runtime-values: 위젯 이미지를 미리 지어 두고 컨테이너가 뜰 때 사이트 파일의 허용 출처와 요청 글자 수 상한만 받게 해, 뜰 때마다 하던 빌드를 없앤다.
**슬라이스:** 9
**Blocked by:** release-image
**설계:** ADR 0064

위젯이 사이트 파일의 두 값을 뜰 때 받는 일. 지금 위젯은 사이트 파일의 허용 출처와 요청 글자 수 상한을 빌드에 굳히고(ADR 0024), 그래서 release-image의 위젯 컨테이너는 뜰 때마다 운영자의 사이트 파일로 빌드한다(ADR 0056 결정 "위젯 이미지"). release-image의 설계 인터뷰에서 사용자가 두 값을 화면에서 바꾸는 요구를 더하며 위젯이 그 값을 실행 중에 읽도록 고치는 일을 portal-admin 행에 함께 두기로 했고(일지 2026-11-11-1532 "위젯 질문에 사용자가 되물었다"), portal-admin의 설계 인터뷰(일지 2026-11-15-1312)에서 사용자가 0.1 판의 범위로 "위젯이 실행 중에 받게만"을, 방법으로 "뜰 때 값만 바꿔 넣기"를 골라 이 행이 섰다. 0.1 판의 행이다(ADR 0046 이력 2026-11-15). 두 값을 화면에서 고치는 일은 0.1 판 뒤의 site-limits-admin이 설계부터 한다.

정한 것은 ADR 0064 결정 "허용 출처와 요청 글자 수 상한"이 원천이다. 위젯 이미지는 미리 지어 두고, 컨테이너가 뜰 때 사이트 파일을 읽어 두 가지만 한다. 위젯의 스크립트가 받아 갈 값 파일을 쓰고, 지어 둔 산출물에서 위젯 페이지를 품어도 되는 사이트를 알리는 응답 머리(`frame-ancestors`)의 값을 바꿔 넣는다. Next의 서버 파일을 금지하는 규칙(ADR 0019, ADR 0024)과 Agent OS의 계약은 고치지 않는다. 사이트 파일을 고친 뒤에는 지금처럼 위젯을 다시 띄운다.

이 행의 첫 일은 확인이다. 앞선 실험(`.scratch/release-image/probes/widget_runtime/README.md`)은 응답 머리를 바꿔 넣는 것과 값을 다시 쓰는 것을 따로따로 보았고, 둘을 합친 이 조합을 리눅스 컨테이너에서 처음부터 끝까지 돌려 본 적은 없다(어림). 명세 전에 프로브로 그 조합이 서는지, 읽기 전용 디스크에서도 서는지를 재고, 서지 않으면 ADR 0064의 그 결정으로 돌아가 사용자에게 다시 묻는다. Next가 지어 내는 파일의 모양에 기대는 방법이라, Next의 판을 올릴 때 깨지는 것을 잡는 시험을 함께 둔다.

release-image를 기다리는 까닭은 그 행이 짓는 위젯 이미지와 단독 compose와 배포 안내를 고치기 때문이다. 그 행의 명세가 넘긴 것(2026-11-13, `.scratch/release-image/spec.md`의 Out of Scope)이 이 행의 것이 됐다. 함께 고칠 것은 위젯 이미지(뜰 때의 빌드, 워크스페이스 전체 의존성, 읽기 전용이 아닌 루트), 단독 compose에서 위젯 상태 확인의 시작 유예(300초), 배포 안내의 메모리 문장이다(그 명세 "이미지의 구성"의 위젯과 상태 확인, "배포 안내"). 구현 티켓이 코드와 같은 티켓에서 고치는 문서는 `web/apps/widget/EMBED.md`(번들이 사이트 파일의 값을 담아 빌드된다는 문장), `docs/constitution/tech.md`의 웹 칸(위젯 빌드가 두 값을 싣는다는 문장), `CONTEXT.md`의 사이트 파일 항목(위젯 빌드가 그 파일을 입력으로 읽는다는 말)이다. 명세가 짓는 것은 ADR 0064 Consequences "명세가 짓는 것"에 있다(값 파일의 자리와 모양, 응답 머리를 바꿔 넣는 방법, 지금처럼 합친 허용 출처와 가장 작은 상한을 쓸지).

수락: 리눅스에서 미리 지은 위젯 이미지로 컨테이너를 띄우면 뜰 때 빌드하지 않고 서고, 사이트 파일의 허용 출처에 든 사이트의 페이지만 위젯 페이지를 품을 수 있으며, 사이트 파일의 요청 글자 수 상한을 바꾸고 컨테이너를 다시 띄우면 위젯이 새 상한을 따르는 테스트가 통과한다
