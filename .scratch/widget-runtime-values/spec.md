# widget-runtime-values 명세: 위젯 이미지를 미리 지어 두고, 컨테이너가 뜰 때 사이트 파일의 허용 출처와 요청 글자 수 상한만 받는다

Status: ready-for-agent

슬라이스 9(`widget-runtime-values`). 설계는 portal-admin의 설계 인터뷰(일지 2026-11-15-1312)와 ADR 0064 결정 "허용 출처와 요청 글자 수 상한"이 정했고, 이 명세는 그 ADR이 명세에 넘긴 자리를 채운다. 결정을 바꾼 것은 없다(아래 "이력"). 이 명세는 `/to-spec widget-runtime-values`로 새 세션에서 썼고 설계 인터뷰를 다시 열지 않았다. 이 세션의 일지는 `docs/journal/2026-11-27-0407-widget-runtime-values-spec.md`이고, 사람에게 물은 하나의 화면과 답이 거기 글자 그대로 있다. 용어는 `CONTEXT.md`의 위젯, 사이트, 사이트 파일, 최종 사용자, 운영자, 단독 배포, 배포 파일 묶음, 위젯 테스트 페이지를 따른다. "코드를 읽었다"는 명세를 쓸 때의 origin/dev인 커밋 `e7c53cba3`의 코드다. 측정은 `.scratch/widget-runtime-values/probes/prebuilt_start/`이고, 재는 것과 다시 돌리는 명령과 잰 판은 `.scratch/widget-runtime-values/probes/README.md`의 표에, 결과는 그 폴더의 `README.md`에 있다. 아래에서 "프로브 결과 N"은 그 README의 "결과" 절의 N번이다. 측정은 모두 이 PC(Windows 10)의 Docker Desktop 위에서 돌았고 리눅스 서버에서는 재지 않았다(Further Notes).

**넘겨받은 것은 아래 표의 열한 행이다.** ADR 0064 Consequences "명세가 짓는 것"이 늘어놓은 여섯, 같은 ADR의 "재지 않은 것"이 이 행의 첫 일로 넘긴 확인 둘, 기능 계획 본문이 든 둘, 같은 ADR의 "다른 행"이 넘긴 하나다. 답한 자리의 따옴표는 이 명세의 절 이름이다.

**사용자가 고른 것은 하나이고 본문의 한 자리에 "사용자가 골랐다"로 표시했다.** 시험의 이음매(Testing Decisions)다. 추천을 맨 앞에 둔 선택 화면으로 물었고 추천을 골랐다. 고르지 않은 선택지 둘과 그 설명은 일지의 "사용자에게 물은 것 하나"에 있다.

**명세가 정한 것은 그 자리에 "명세가 정했다"로 표시했다.** 표시는 이 문단 밖에 열이고, 열 모두 절 머리라 그 절 전체에 걸린다. 표시가 없는 것은 ADR 0064, 기능 계획, 기존 규칙에서 왔거나, 표시한 결정을 시험과 문서로 옮긴 것이다.

**이력은 없다.** 이 명세는 ADR 0064의 그 결정이 적은 것(뜰 때 두 가지만 한다, Next의 서버 파일을 금지하는 규칙과 Agent OS의 계약을 고치지 않는다, 사이트 파일을 고친 뒤에는 위젯을 다시 띄운다)을 그대로 따르고 그 ADR 본문의 문장을 거짓으로 만들지 않는다. 이 명세로 낡는 다른 ADR의 문장은 허용 출처가 위젯 빌드의 입력이라는 것과 위젯 컨테이너가 뜰 때 빌드한다는 것을 결정으로 적은 문장들이고, ADR 0064가 그런 문장에 이미 `(바뀜: ADR 0064)` 포인터를 달았다. ADR 0023, ADR 0024, ADR 0047, ADR 0056에서 포인터가 달린 그 문장들을 읽었다(네 ADR은 예이고, 그런 문장이 이 넷에만 있다는 뜻이 아니다). 포인터가 없는 쪽도 봤다. `docs/adr/`에서 "빌드"가 "사이트 파일", "허용 출처", "뜰 때", "글자 수 상한" 가운데 하나와 같은 줄에 든 줄을 찾아, 포인터가 없는 줄을 한 줄씩 열었다(손으로 봤다. `grep -n "빌드" docs/adr/*.md`를 그 낱말들로 걸렀고 ADR 0064 자신은 뺐다). 그 줄들은 거부한 안의 근거, 지난 이력 항목, 그때 명세에 넘긴 것의 목록, 그때 코드를 옮긴 일을 적은 문장, 지금도 맞는 문장이었다. `.claude/rules/adr.md`가 포인터를 달지 않는다고 정한 종류이거나 결정이 그대로인 문장이라, 이 명세가 새로 달 포인터는 없다. 그 ADR이 조합을 재 보지 않았다고 적은 문장("재지 않은 것")은 그때의 사실을 적은 것이고, 잰 결과가 결정과 어긋나지 않아 이력으로 다시 볼 것이 없다.

**거부한 안은 일곱 자리에 "거부한 안:"으로 시작하는 문단으로 적었고, 그 문단들이 든 안은 열아홉이다.** 그 가운데 둘은 사용자에게 보인 선택지 가운데 고르지 않은 것이고, 그 문단에 그렇게 적었다(Testing Decisions).

## Problem Statement

운영자(Agent OS를 서버에 올려 돌리는 사람)가 단독 배포(서버 한 대에 Docker Compose로 올리는 배포)를 띄우면, 위젯 컨테이너는 뜰 때마다 위젯을 처음부터 빌드한다. 위젯(사이트의 웹 페이지 안에 들어가는 대화 앱)이 사이트 파일(운영자가 어느 사이트를 받아들일지 적어 두는 파일)의 두 값을 빌드에 굳히기 때문이다. 두 값은 허용 출처(그 사이트의 페이지가 놓인 웹 주소. 여기 든 주소의 페이지만 위젯 페이지를 품을 수 있다)와 요청 글자 수 상한(질문 하나에 받을 수 있는 글자 수)이다. 미리 지어 둔 이미지는 운영자의 사이트 파일을 알 수 없으므로 컨테이너가 뜰 때 빌드할 수밖에 없었다(ADR 0056 결정 "위젯 이미지").

그 때문에 운영자가 겪는 일은 아래와 같다. 수치는 release-image의 측정이다(`.scratch/release-image/spec.md`의 "이미지의 구성"을 읽었다. 이 PC에서 잰 값이다).

- 위젯이 뜰 때 메모리를 1.6GiB 가까이 쓴다(빌드의 최고치 1,452~1,567MiB). 메모리를 1GiB 이하로 제한한 컨테이너에서는 빌드 도중 메모리 부족으로 죽었다. 그래서 단독 compose는 위젯에 메모리 제한을 두지 못하고, 배포 안내는 서버에 그만큼의 여유를 요구한다.
- 위젯 컨테이너가 시작해 첫 응답을 내기까지 13.6~40.7초가 걸린다. 그동안 위젯은 응답하지 않고 프록시가 502로 답한다. 사이트 파일을 고칠 때마다, 서버를 다시 켤 때마다 같은 일이 난다.
- 뜨지 못한 위젯이 5분 동안 드러나지 않는다. 위젯의 상태 확인에만 시작 유예 300초가 걸려 있고(`deploy/standalone/compose.yaml`을 읽었다), Docker는 유예 동안의 실패를 세지 않는다(Docker의 동작으로 아는 것이고 이 명세가 재지 않았다). 위젯에만 긴 값을 둔 까닭은 뜰 때의 빌드를 기다리려는 것으로 본다(어림. release-image 명세는 그 값을 어림이라고만 적었다).
- 위젯 컨테이너만 루트 파일 시스템이 읽기 전용이 아니다. 빌드가 앱 폴더 안에 쓰기 때문이다. 다른 web 컨테이너 둘(관리 화면, 위젯 테스트 페이지)은 읽기 전용이다.
- 위젯 이미지에 빌드 도구와 시험용 패키지까지 워크스페이스 전체 의존성이 들어 있다(874.3MiB).

사이트의 개발자(위젯을 자기 페이지에 넣는 쪽)도 하나를 겪는다. 페이지 안 방식(사이트 페이지가 위젯의 스크립트 하나를 불러 그 페이지 안에 위젯을 그리는 방식)의 스크립트가 요청 글자 수 상한을 담아 빌드되므로, 운영자가 사이트 파일을 고쳐 위젯을 다시 빌드할 때마다 스크립트의 내용이 바뀐다. 무결성 검사(`integrity`)를 쓰는 사이트는 그때마다 해시를 새로 받아 바꿔야 한다(`web/apps/widget/EMBED.md`를 읽었다).

## Solution

위젯 이미지를 판을 낼 때 한 번, 사이트 파일 없이 지어 둔다. 컨테이너가 뜰 때는 사이트 파일을 읽어 두 가지만 한다(ADR 0064).

1. 위젯의 스크립트가 받아 갈 값 파일을 쓴다. 두 값이 든 작은 JSON 파일이고, 위젯은 열릴 때 이 파일을 받아 입력창의 상한과 허용 출처로 쓴다.
2. 지어 둔 산출물에서, 위젯 페이지를 품어도 되는 사이트를 알리는 응답 머리(`frame-ancestors`)의 값을 사이트 파일의 허용 출처로 바꿔 넣는다.

그 뒤 빌드 없이 바로 서비스를 시작한다. 운영자의 눈에 달라지는 것은 아래다. 수치는 이 명세의 측정이고(프로브 결과 1, 2, 6), 이 PC에서 시제품 이미지로 잰 값이다.

- 위젯 컨테이너가 시작해 첫 응답을 내기까지 0.60~1.96초였다(지금은 13.6~40.7초).
- 뜬 직후의 메모리 최고치가 77.7~96.2MiB였다(지금은 1,452~1,567MiB). 서버의 메모리에 위젯 몫으로 1.6GiB를 따로 볼 필요가 없어진다.
- 사이트 파일을 고친 뒤에는 지금처럼 위젯을 다시 띄운다. 달라지는 것은 다시 뜨는 동안 빌드를 기다리지 않는다는 것이다. 프록시를 거쳐 응답이 끊기는 시간은 재지 않았다(아래 "배포 안내").
- 위젯 컨테이너의 상태가 띄운 뒤 2.58~2.95초에 healthy(상태 확인 명령이 성공해 Docker가 정상이라고 표시한 상태)가 됐다. 시작 유예는 다른 컨테이너와 같은 30초가 된다.
- 위젯 컨테이너의 루트가 읽기 전용이 된다. 쓰는 자리는 메모리에 두는 작은 폴더 하나뿐이다.
- 위젯 이미지가 작아진다. 빌드 도구가 뜬 뒤의 이미지에서 빠지고, 시제품 이미지는 690.6MiB였다(지금은 874.3MiB).

최종 사용자(위젯으로 질문하는 사람)와 사이트의 개발자에게 위젯의 동작은 지금과 같다. 허용 출처에 든 사이트의 페이지만 위젯 페이지를 품을 수 있고, 입력창은 사이트 파일의 상한까지만 받는다. 달라지는 것은 하나다. 페이지 안 방식의 스크립트가 사이트 파일의 값을 담지 않으므로, 그 내용은 판이 바뀔 때만 바뀌고 운영자가 사이트 파일을 고쳐도 그대로다.

두 값을 화면에서 고치는 일과 다시 띄우지 않고 바뀐 값이 듣게 하는 일은 이 명세의 것이 아니다(Out of Scope).

## User Stories

1. 운영자로서, 위젯 컨테이너가 뜰 때 빌드하지 않고 바로 서기를 원한다. 그래야 `docker compose up -d` 뒤 몇 초 안에 위젯이 응답한다.
2. 운영자로서, 위젯이 뜰 때 메모리를 1.6GiB씩 쓰지 않기를 원한다. 그래야 메모리가 작은 서버에서도 위젯이 메모리 부족으로 죽지 않는다.
3. 운영자로서, 사이트 파일에 허용 출처를 더하고 위젯을 다시 띄우면 그 출처의 페이지가 위젯 페이지를 품을 수 있기를 원한다. 그래야 새 사이트를 받아들일 때 이미지를 다시 지을 필요가 없다.
4. 운영자로서, 사이트 파일에서 허용 출처를 빼고 위젯을 다시 띄우면 그 출처의 페이지가 위젯 페이지를 더는 품지 못하기를 원한다. 그래야 끊은 사이트가 위젯을 계속 띄우지 못한다.
5. 운영자로서, 사이트 파일의 요청 글자 수 상한을 고치고 위젯을 다시 띄우면 위젯의 입력창이 새 상한을 따르기를 원한다. 그래야 서버가 받는 글자 수와 입력창이 받는 글자 수가 맞는다.
6. 운영자로서, 사이트 파일을 고친 뒤 위젯이 응답하지 않는 시간이 몇 초이기를 원한다. 그래야 그사이에 위젯을 연 최종 사용자가 오류를 볼 틈이 짧다.
7. 운영자로서, 사이트 파일이 없거나 깨졌으면 위젯이 뜨지 않고 까닭을 로그에 글로 남기기를 원한다. 그래야 어느 사이트도 품지 못하는 채로 조용히 뜬 위젯을 뒤늦게 발견하지 않는다.
8. 운영자로서, 그 진단이 "다시 빌드한다"가 아니라 "다시 띄운다"고 말하기를 원한다. 그래야 내가 할 일을 바로 안다.
9. 운영자로서, 위젯이 뜰 때 받은 허용 출처와 상한을 로그 한 줄로 보기를 원한다. 그래야 고친 값이 실제로 들어갔는지 `docker compose logs widget`으로 확인한다.
10. 운영자로서, 위젯 컨테이너의 루트가 읽기 전용이기를 원한다. 그래야 위젯도 다른 web 컨테이너와 같은 수준으로 잠긴다.
11. 운영자로서, 위젯 컨테이너의 상태가 몇 초 안에 healthy로 바뀌기를 원한다. 그래야 띄운 직후 `docker compose ps`로 다 떴는지 바로 본다.
12. 운영자로서, 뜨지 못한 위젯이 5분이 아니라 다른 컨테이너와 같은 유예 뒤에 unhealthy로 드러나기를 원한다. 그래야 문제를 일찍 안다.
13. 운영자로서, 배포 안내가 위젯 몫의 메모리 1.6GiB를 요구하지 않기를 원한다. 그래야 서버 사양을 실제 필요에 맞게 고른다.
14. 운영자로서, 판을 올린 뒤 위젯이 틀린 허용 출처로 조용히 뜨는 일이 없기를 원한다. 새 판의 산출물 모양이 기대와 다르면 위젯이 뜨지 않고 까닭을 말해야 한다.
15. 운영자로서, 인터넷이 막힌 곳에서도 위젯이 뜨기를 원한다. 뜰 때 바깥에서 아무것도 받지 않아야 한다.
16. 운영자로서, 받아야 하는 위젯 이미지가 지금보다 작기를 원한다. 그래야 받는 시간과 파일로 옮길 때의 크기가 준다.
17. 운영자로서, 위젯 컨테이너를 끌 때 금방 꺼지기를 원한다. 그래야 다시 띄우는 일이 짧게 끝난다.
18. 운영자로서, 이미 위젯을 열어 둔 최종 사용자의 화면은 새로 고쳐야 새 값을 받는다는 것을 배포 안내에서 읽기를 원한다. 그래야 바꾼 상한이 왜 바로 안 보이는지 헷갈리지 않는다.
19. 운영자로서, 값 파일에 비밀이 들지 않기를 원한다. 누구나 읽을 수 있는 파일이므로 허용 출처와 상한 말고는 실려서는 안 된다.
20. 최종 사용자로서, 위젯이 열린 뒤 준비가 끝나기 전에는 입력이 막혀 있기를 원한다. 그래야 상한을 모르는 채 보낸 긴 글이 서버에서 거절되는 일이 없다.
21. 최종 사용자로서, 위젯이 값을 받지 못했을 때 위젯을 쓸 수 없다는 알림을 보기를 원한다. 그래야 빈 화면 앞에서 기다리지 않는다.
22. 최종 사용자로서, 입력창이 서버가 받는 글자 수까지만 받기를 원한다. 그래야 다 쓴 글이 길다는 이유로 거절되지 않는다.
23. 최종 사용자로서, 위젯이 지금만큼 빨리 열리기를 원한다. 값을 받는 요청 하나가 더해져도 눈에 띄게 느려져서는 안 된다.
24. 사이트의 개발자로서, iframe 방식(사이트 페이지가 위젯 페이지를 틀 안에 품는 방식)으로 넣은 위젯이 지금과 같은 임베드 코드로 뜨기를 원한다. 그래야 내 페이지를 고치지 않는다.
25. 사이트의 개발자로서, 페이지 안 방식으로 넣은 위젯이 상한을 스스로 받아 오기를 원한다. 그래야 내 페이지의 임베드 코드에 값을 적지 않는다.
26. 사이트의 개발자로서, 페이지 안 방식의 스크립트의 무결성 해시가 운영자가 사이트 파일을 고칠 때마다 바뀌지 않기를 원한다. 그래야 `integrity` 값을 판이 바뀔 때만 고친다.
27. 사이트의 개발자로서, 허용 출처에 없는 내 시험 페이지가 위젯 페이지를 품으려 하면 브라우저가 막기를 원한다. 그래야 허용 출처에 넣어 달라고 운영자에게 청해야 한다는 것을 안다.
28. 위젯을 고치는 개발 세션으로서, 개발 서버(`dev`)가 지금처럼 사이트 파일 하나를 주면 그 값으로 뜨기를 원한다. 그래야 개발하는 방법이 바뀌지 않는다.
29. 위젯을 고치는 개발 세션으로서, 한 번 빌드한 산출물을 사이트 파일만 바꿔 가며 다시 띄울 수 있기를 원한다. 그래야 값을 바꿔 보는 일에 빌드를 기다리지 않는다.
30. 위젯을 고치는 개발 세션으로서, 두 값을 읽는 브라우저 쪽 자리가 하나이기를 원한다. 그래야 값을 받는 길을 바꿀 때 한 곳만 고친다.
31. Next의 판을 올리는 개발 세션으로서, 지어 둔 산출물의 모양이 바뀌었으면 dev로 가는 PR의 CI에서 빨강을 보기를 원한다. 그래야 출시 직전이 아니라 판을 올리는 그 PR에서 고친다.
32. 이미지를 고친 티켓의 세션으로서, 실제 이미지를 통째로 띄우는 시험을 이 PC의 Docker로 돌려 수락 셋을 확인하기를 원한다. 그래야 CI가 그 시험을 돌리지 않는 dev PR에서도 이미지가 서는 것을 본다.
33. 판을 내는 세션으로서, main으로 가는 PR에서 실제 위젯 이미지가 빌드 없이 뜨고 두 값을 따르는지 CI가 보기를 원한다. 그래야 깨진 위젯 이미지가 판으로 나가지 않는다.
34. 보안을 검토하는 사람으로서, 값을 바꿔 넣는 단계를 건너뛴 채로는 이미지의 위젯이 서지 않기를 원한다. 그래야 허용 출처가 반영되지 않은 위젯이 뜨는 길이 없다.
35. site-limits-admin을 설계하는 세션으로서, 위젯이 두 값을 어디서 어떤 모양으로 받는지가 적혀 있기를 원한다. 그래야 다시 띄우지 않고 값을 바꾸는 길을 그 위에 설계한다.
36. deploy-package를 설계하는 세션으로서, 위젯의 메모리와 뜨는 시간의 새 값이 그 기능 계획에 적혀 있기를 원한다. 그래야 통합 배포의 대상 사양을 옛 값으로 적지 않는다.

## Implementation Decisions

### 명세 전의 확인

기능 계획이 이 행의 첫 일로 둔 확인이다. ADR 0064는 미리 짓고 뜰 때 값만 바꿔 넣는 조합을 리눅스 컨테이너에서 처음부터 끝까지 돌려 본 적이 없다고 적었고, 서지 않으면 그 결정으로 돌아가 사용자에게 다시 묻기로 했다. 시제품 이미지와 시제품 진입 단계로 돌려 본 결과 조합이 섰고, 그 결정으로 돌아갈 것이 없다. 여섯 실행의 164회차가 모두 측정이었다(재려는 상황이 그 회차에 실제로 났다는 표지를 본 회차다). 넷째 실행은 셀프 리뷰 뒤에 프로브가 단언하는 표지를 넓혀 일곱 섹션 전체를 다시 돌린 것이다. 다섯째 실행은 PR을 열기 전의 리뷰가 짚은 표지와 대조를 고친 뒤, 그 사이에 받은 origin/dev(`afba83679`)의 `web/`으로 이미지를 다시 지어 일곱 섹션 전체를 돌린 것이다. 여섯째 실행은 PR의 리뷰 봇이 짚은 표지와 대조를 고친 뒤 다섯째 실행과 같은 이미지로 일곱 섹션 전체를 돌린 것이다(셋 다 프로브 README의 "결과를 본 뒤 바꾼 것"). 아래 표와 이 명세의 범위는 여섯 실행을 합친 것이고, 앞 네 실행과 다섯째 실행과 여섯째 실행을 따로 본 범위는 프로브 README의 결과 2와 6에 있다.

| 물음 | 결과 | 근거 |

| 다른 출처의 문서가 값 파일을 받는가 | 받았다. 같은 요청으로 다른 출처에 열지 않은 위젯 페이지를 받으면 실패했다 | 같은 결과, 쟀다 |

시제품은 실제 구현이 아니다. 저장소의 파일을 고치지 않고 이미지 안에서만 필요한 것을 채웠으므로, 시제품이 채운 자리는 모두 구현이 새로 짓는 자리다. 결과를 읽을 때 알아야 할 차이를 예로 든다(전부가 아니고, 시제품의 파일마다 하는 일은 프로브 README의 "파일" 표에 있다). 진입 단계가 위젯의 시작 래퍼가 아니라 따로 쓴 스크립트였다(그래서 래퍼의 루프백 검사를 거치지 않았다). 위젯의 코드가 값 파일을 받아 쓰는 데까지는 가지 않았다(브라우저가 받을 수 있는지까지만 봤다). 값 파일에 다는 `Access-Control-Allow-Origin: *` 규칙은 저장소의 Next 설정이 아니라 이미지 안의 사본에 더했다. 응답 머리 목록의 원본은 래퍼의 빌드가 아니라 이미지를 짓는 파일이 복사해 남겼다. 이런 차이는 구현 티켓의 시험이 본다(Testing Decisions).

### 값 파일(명세가 정했다)

위젯의 스크립트가 받아 가는, 두 값이 든 파일이다.

- **자리.** 위젯이 내주는 공개 파일 하나이고 주소는 위젯의 공개 주소 아래 `/widget/runtime.json`이다. 글꼴과 페이지 안 방식의 스크립트처럼 Next가 정적 파일로 낸다. 단독 배포의 프록시는 `/widget` 아래를 이미 위젯으로 넘기므로 프록시 설정을 고치지 않는다(`deploy/standalone/proxy/site.conf`를 읽었다).
- **모양.** JSON 객체 하나이고 키는 둘이다. 아래는 시제품이 프로브의 사이트 파일 하나로 낸 값 파일의 전문이다(프로브 결과 2).

  ```json
  {"allowedOrigins":["https://probe-a.example"],"requestChars":771133}
  ```

  `allowedOrigins`는 모든 사이트의 허용 출처를 합친 목록이고 허용 출처가 하나도 없으면 빈 목록이다. `requestChars`는 모든 사이트의 요청 글자 수 상한 가운데 가장 작은 값이다. 두 값은 지금 빌드가 사이트 파일에서 끌어내는 것과 같은 함수가 낸다(아래 "합친 허용 출처와 가장 작은 상한").
- **판 표시를 두지 않는다.** 값 파일과 그것을 읽는 스크립트는 같은 이미지에서 나온다. 읽는 쪽은 두 키만 읽고 모르는 키는 무시한다. 나중에 값을 더할 때는 키를 더하고, 있는 키의 뜻을 바꾸지 않는다.
- **누가 읽는가.** 누구나 읽는다. 토큰도 쿠키도 없는 읽기다. 페이지 안 방식의 스크립트는 사이트의 문서에서 이 파일을 받으므로(다른 출처의 요청이다) 응답에 `Access-Control-Allow-Origin: *`를 단다. 글꼴과 스크립트에 이미 다는 것과 같은 머리다. 이 머리가 있을 때 다른 출처의 문서가 두 값을 읽었고, 머리가 없는 위젯 페이지를 같은 요청으로 받으면 실패했다(프로브 결과 7, 쟀다).
- **비밀이 아니다.** 두 값은 지금도 밖에 보인다. 합친 허용 출처는 위젯의 모든 응답의 머리에, 가장 작은 상한은 페이지 안 방식의 스크립트 안에 실려 있다(`web/apps/widget/next.config.ts`와 `web/apps/widget/tools/element.ts`를 읽었다). 값 파일에는 이 둘만 싣고 사이트 파일의 다른 값(공개 키, 발급자, 열 에이전트)은 싣지 않는다.
- **캐시.** 따로 머리를 더하지 않는다. Next가 공개 파일에 다는 `Cache-Control: public, max-age=0`과 ETag(파일의 내용이 바뀌면 함께 바뀌는 표시. 브라우저가 이 값을 서버에 보내 파일이 그대로인지 묻는다)가 그대로 붙어, 브라우저는 위젯을 열 때마다 서버에 다시 확인한다. 내용이 바뀌자 ETag도 바뀌었다(프로브 결과 2, 3, 쟀다).
- **쓰는 때.** 위젯이 뜰 때마다 새로 쓴다. 빌드는 이 파일을 짓지 않는다. 글꼴이나 스크립트처럼 지어지는 파일이라 저장소에 커밋하지 않고, 저장소가 무시하는 목록(뿌리 `.gitignore`의 위젯 줄들)에 더한다.

거부한 안: 지어 둔 스크립트와 페이지의 글에서 자리표를 찾아 뜰 때 바꿔 넣는다. 스크립트의 내용이 사이트 파일마다 달라져 무결성 해시가 계속 사이트 파일에 묶이고, Next가 지어 낸 파일 여럿을 고쳐야 해서 판을 올릴 때 깨질 자리가 는다. 위젯 페이지의 HTML에 값을 박는다. 페이지 안 방식의 스크립트는 그 HTML을 받지 않는다. 값을 전역 변수로 세우는 스크립트 파일로 낸다. 사이트 페이지의 전역을 건드리고 사이트가 넣을 태그가 하나 는다. Next의 서버 파일(요청 때 도는 코드)로 값을 낸다. ADR 0019와 ADR 0024가 금지하고 ADR 0064가 그 규칙을 고치지 않기로 했다. Agent OS 서버가 값을 공개 경로로 낸다. ADR 0064가 고르지 않은 안이고 Agent OS의 계약이 바뀐다.

### 품어도 되는 사이트를 알리는 응답 머리(명세가 정했다)

브라우저는 위젯 페이지의 응답에 실린 `Content-Security-Policy: frame-ancestors …`를 보고, 그 페이지를 틀 안에 품으려는 페이지의 출처가 거기 없으면 막는다. 지금은 이 값이 빌드 때 정해진다. 이것을 뜰 때 정하게 바꾼다.

- **빌드는 늘 닫힌 값으로 짓는다.** 빌드는 사이트 파일을 읽지 않고, 그 머리의 값을 아무도 품지 못한다는 뜻의 `frame-ancestors 'none'`으로 짓는다.
- **지어 둔 원본을 남긴다.** Next는 빌드할 때 응답 머리의 목록을 산출물 안의 파일(`routes-manifest.json`)에 적어 두고, 서비스를 시작할 때 그 파일을 읽어 응답에 머리를 단다(Next 16.3.6에서 쟀다. 그 파일의 값을 바꾸고 띄우자 응답의 머리가 바뀐 값이었다, 프로브 결과 2, 3). 빌드가 낸 그 파일을 원본으로 따로 남기고, 뜰 때마다 원본을 읽어 값 하나를 바꾼 사본을 Next가 읽는 자리에 쓴다. 원본은 고치지 않는다. 그래서 다시 띄울 때 앞서 넣은 값 위에 덧쓰지 않고 늘 지은 때의 모양에서 다시 만든다.
- **바꿀 자리를 찾는 규칙.** 원본을 JSON으로 풀어, 머리의 이름이 `Content-Security-Policy`이고 값이 `frame-ancestors`로 시작하는 자리를 찾는다. 그 자리가 정확히 하나이고 값이 글자 그대로 `frame-ancestors 'none'`일 때만 바꾼다. 자리가 없거나, 둘 이상이거나, 값이 다르면 아무것도 쓰지 않고 까닭을 적은 진단과 함께 종료 1로 끝난다. Next의 판이 올라 파일의 모양이 바뀌었거나 빌드가 사이트 파일을 읽어 버린 산출물이면, 틀린 값으로 조용히 뜨는 대신 뜨지 않는다. 시제품의 이미지에서 그 자리는 하나였고 값은 `frame-ancestors 'none'`이었다(프로브 결과 1, 쟀다).
- **넣는 값.** 지금 빌드가 내던 것과 같은 꼴이다. 합친 허용 출처를 공백으로 이은 `frame-ancestors <출처> <출처>`이고, 목록이 비면 `frame-ancestors 'none'`이다.
- **걸리는 범위.** 지금처럼 `/widget` 아래의 모든 응답이다. 페이지, 스크립트, 값 파일, 없는 경로의 404에 같은 값이 붙었다(프로브 결과 2, 쟀다).
- **값을 바꿔 넣는 단계를 건너뛰면.** 이미지에서는 Next가 읽는 자리가 뜰 때 채워지는 빈 자리라(아래 "위젯 이미지"), 그 단계 없이 Next를 바로 부르면 파일을 열지 못해 서지 못했다(프로브 결과 5, 쟀다). 운영의 길은 이미지이므로, 허용 출처를 넣지 않은 채 운영 위젯이 뜨는 길은 그 이미지에 없다. 이미지 밖(개발 PC, e2e)에서는 그 자리가 보통 파일이라 사정이 다르다. 래퍼를 거치지 않고 Next를 바로 부르면 그 파일에 든 값으로 뜬다. 갓 지은 산출물이면 `'none'`이고, 앞서 래퍼로 띄운 적이 있으면 그때 넣은 값이다(구조에서 미룬 어림이고 재지 않았다). 래퍼를 거치지 않는 시작은 지금도 루프백 검사를 건너뛰는 길이라 쓰지 않는다.

이 방법은 Next가 문서로 약속하지 않은 파일의 모양에 기댄다(ADR 0064가 대가로 적었다). 그래서 위 규칙이 모양이 달라진 것을 뜰 때 잡고, Testing Decisions의 둘째가 판을 올리는 PR에서 먼저 잡는다.

거부한 안: 프록시가 그 머리를 단다. 프록시 없이 띄운 위젯은 머리가 없어 아무 사이트나 품을 수 있게 된다(ADR 0064 Considered Options). 파일을 JSON으로 풀지 않고 글자 바꾸기로 고친다. 따옴표가 든 값이라 이스케이프에 따라 못 찾거나 엉뚱한 자리를 바꿀 수 있다. 원본을 남기지 않고 Next가 읽는 파일을 제자리에서 고친다. 다시 띄울 때는 앞서 넣은 값이 들어 있어 "지은 때의 값일 때만 바꾼다"는 검사를 걸 수 없다. Next를 감싸는 서버를 따로 두어 응답마다 머리를 단다. ADR 0019와 ADR 0024가 금지한다.

### 합친 허용 출처와 가장 작은 상한(명세가 정했다)

지금처럼 쓴다. 위젯이 받는 허용 출처는 모든 사이트의 허용 출처를 합친 목록이고, 상한은 모든 사이트의 상한 가운데 가장 작은 값이다. 사이트 파일에서 두 값을 끌어내는 코드는 지금 빌드가 쓰는 것을 그대로 쓴다(`web/packages/site-file`. ADR 0064가 사이트 파일을 푸는 코드가 늘지 않는다고 적은 그 코드다).

까닭은 위젯이 내는 값 파일과 응답 머리가 사이트를 가리지 않고 하나씩이기 때문이다. 위젯 페이지는 자기를 품은 페이지가 어느 사이트의 것인지 응답을 낼 때 알지 못한다. 사이트마다의 값은 Agent OS 서버가 요청을 받을 때 그 사이트의 것으로 따로 지킨다(두 값은 Agent OS가 요청을 받아들일지를 가르는 설정이다, ADR 0064). 위젯 쪽의 값은 브라우저가 틀을 막는 문과 입력창의 편의에 쓰인다. 그래서 상한이 서로 다른 사이트가 함께 있으면 위젯의 입력창은 지금처럼 가장 작은 상한을 따른다.

거부한 안: 값 파일에 사이트마다의 값을 싣고 위젯이 자기 사이트의 것을 고른다. 위젯이 자기가 어느 사이트에 놓였는지를 알아야 하고 사이트의 목록이 누구나 읽는 파일에 사이트별로 드러난다. 사이트마다 다른 값을 위젯이 따르게 하는 일은 이 명세의 범위 밖이다(Out of Scope).

### 시작 래퍼의 세 명령(명세가 정했다)

위젯에는 개발 서버, 빌드, 서비스 시작이 모두 거치는 시작 래퍼가 있다(`web/apps/widget/tools/start.ts`를 읽었다. 듣는 주소가 루프백인지 검사하고 빌드의 입력을 준비한다). 그 래퍼의 세 명령이 사이트 파일을 읽는 때를 아래처럼 바꾼다.

| 명령 | 지금 | 바뀐 뒤 |
|---|---|---|
| 빌드(`build`) | 사이트 파일을 읽어 두 값을 산출물에 굳힌다. 읽지 못하면 진단과 함께 실패한다 | 사이트 파일을 읽지 않는다. 사이트 파일의 환경 변수가 있어도 산출물이 같다. 응답 머리는 `'none'`으로 굳고 스크립트는 상한을 담지 않는다. 빌드가 끝나면 응답 머리 목록의 원본이 남아 있다 |
| 서비스 시작(`start`) | 빌드 산출물을 그대로 낸다. 응답 머리는 빌드 때 굳은 값이 나간다. 래퍼는 사이트 파일을 읽지 않지만 Next가 설정 파일을 읽으며 사이트 파일도 읽어, 읽지 못하면 Next가 같은 진단으로 끝난다(그 파일의 머리 주석이 손으로 봤다고 적는다) | 듣는 주소를 검사한 뒤 사이트 파일을 읽고, 값 파일과 응답 머리 목록의 사본을 쓰고, 그 뒤에 Next를 부른다. 어느 단계든 실패하면 Next를 부르지 않고 종료 1로 끝난다 |
| 개발 서버(`dev`) | 뜰 때 사이트 파일을 읽는다 | 지금처럼 뜰 때 사이트 파일을 읽어 같은 두 값을 낸다(응답 머리와 값 파일) |

- 서비스 시작이 뜰 때 받은 값을 한 줄로 찍는다. 합친 허용 출처의 목록과 상한이다. 비밀이 아니고(위 "값 파일"), 운영자가 고친 값이 들어갔는지 컨테이너의 로그에서 본다.
- 서비스 시작의 길은 빌드 도구를 불러오지 않는다. 지금 래퍼는 어느 명령으로 불려도 스크립트를 짓는 도구(Vite와 Tailwind)를 함께 불러온다(같은 파일을 읽었다). 뜬 뒤의 이미지에는 그 도구가 없으므로(아래 "위젯 이미지"), 서비스 시작은 운영 의존성만 깔린 곳에서 서야 한다.
- 개발 서버에는 지어 둔 응답 머리 목록이 없다. 그래서 개발 서버의 응답 머리는 지금의 길(Next의 설정이 뜰 때 사이트 파일을 읽는다)로 내고, 값 파일은 준비 단계가 쓴다. 빌드에서는 같은 설정이 사이트 파일을 읽지 않게 하는 방법은 구현이 고른다. 이 명세가 정하는 것은 위 표의 행동이다.
- 응답 머리 목록의 원본은 래퍼의 빌드가 남긴다. 이미지를 짓는 파일도, 위젯 e2e도, 개발 PC도 같은 빌드 명령을 부르기 때문이다. 시제품에서는 이미지를 짓는 파일이 원본을 복사했고, 래퍼가 남기는 길은 재지 않았다(파일 하나를 복사하는 일이다). Testing Decisions의 둘째의 준비가 실제 빌드로 그 길을 지난다.
- 사이트 파일의 경로가 상대 경로이면 래퍼를 부른 자리 기준으로 푸는 지금의 동작은 그대로다.
- 이미지 밖에서는 뜰 때 쓰는 두 파일(응답 머리 목록의 사본과 값 파일)이 위젯 앱 폴더 안의 보통 파일이다. 그래서 한 체크아웃에서 사이트 파일이 다른 위젯 둘을 함께 띄우면 뒤에 뜬 쪽이 값 파일을 덮어쓴다. 지금도 위젯 e2e와 위젯 테스트 페이지 e2e의 준비가 같은 앱 폴더에 빌드를 쓰므로(`web/apps/portal/e2e/stack.ts`의 빌드 주석을 읽었다) 한 체크아웃에서 둘을 함께 돌리면 서로의 산출물을 덮어쓴다고 본다(어림). 그래서 새로 생기는 종류의 제약은 아니다.

### 사이트 파일이 없거나 깨졌을 때(명세가 정했다)

- 이미지의 시작은 지금처럼 사이트 파일의 자리(컨테이너 안의 `/etc/agent-os/site/sites.toml`)를 늘 넘긴다.
- 그 자리에 파일이 없거나 내용이 깨졌으면, 서비스 시작이 지금 빌드가 내던 것과 같은 진단을 찍고 Next를 부르지 않은 채 종료 1로 끝난다(프로브 결과 5, 쟀다. 넣은 것은 둘이다. 없는 파일과, 필수 칸이 빠지고 모르는 칸이 든 파일이다). 폴더이거나 앱 사용자(컨테이너 안에서 위젯을 돌리는, root가 아닌 계정)가 읽지 못하는 파일도 같은 함수가 같은 진단으로 거절한다고 본다. release-image가 빌드 길에서 잰 것이고(그 명세의 "이미지의 구성") 서비스 시작의 길에서는 재지 않았다(어림).
- 진단의 끝 문장은 지금 "고친 뒤 다시 빌드한다"로 시작한다(`web/packages/site-file/src/site-file.ts`를 읽었다). 뜰 때 읽게 되면 운영자가 할 일은 다시 띄우는 것이므로 그 문장을 "고친 뒤 위젯을 다시 띄운다"로 고친다.
- 사이트 파일의 환경 변수가 아예 없으면 멈추지 않고 닫힌 채 뜬다. 응답 머리는 `'none'`, 값 파일은 빈 허용 출처와 기본 상한 20000이다(프로브 결과 5, 쟀다). 지금의 동작과 같고 개발할 때 사이트 파일 없이 띄우는 길이다. 이미지는 경로를 늘 넘기므로 운영에서는 이 길로 들지 않는다.
- 단독 compose의 재시작 정책 때문에, 사이트 파일이 깨진 채면 위젯 컨테이너는 끝났다가 다시 뜨기를 되풀이한다. 지금과 같고, 배포 안내의 문제 해결 절이 그 경우를 든다(아래 "배포 안내").

### 브라우저 쪽이 값을 받는 길(명세가 정했다)

- **읽는 자리는 하나다.** 위젯의 브라우저 쪽 코드에서 두 값을 읽는 자리는 지금 한 곳이다(`web/apps/widget/lib/build.ts`를 읽었다. 빌드가 굳힌 글을 읽는다). 그 한 곳이 값 파일을 받아 온 결과를 주게 바꾸고, 다른 코드는 그 자리를 거쳐서만 값을 읽는다.
- **받는 주소.** iframe 방식의 페이지는 자기 출처의 `/widget/runtime.json`을 받는다. 페이지 안 방식의 스크립트는 자기가 실려 온 출처의 `/widget/runtime.json`을 받는다. 그 스크립트는 지금도 API의 기준 주소를 자기가 실려 온 출처로 잡고(`web/apps/widget/element/base.ts`를 읽었다) 글꼴을 그 출처의 `/widget/fonts/`에서 받는다. 기준 주소를 얻지 못한 페이지에서는 지금처럼 그 출처로 아무것도 보내지 않으므로 값 파일도 받지 않는다. 쿠키와 자격 증명은 싣지 않는다.
- **방식마다 쓰는 값.** iframe 방식은 두 값을 모두 쓴다. 페이지 안 방식은 상한만 쓴다. 부모 창에 토큰을 묻지 않아 허용 출처가 필요 없기 때문이다(`web/apps/widget/tools/element.ts`의 머리 주석을 읽었다).
- **받는 동안.** 입력을 막는다. 지금도 이전 대화를 되살리는 동안에는 보내기가 막혀 있고(`web/apps/widget/components/pages/WidgetScreen.tsx`를 읽었다), 값을 받는 일이 끝나는 것을 그 조건에 더한다. iframe 방식의 페이지는 값을 받기 전에는 자기를 품은 페이지에 사이트 토큰을 묻지 않는다. 그 페이지는 토큰의 답이 허용 출처에서 왔을 때만 받는데(`web/apps/widget/lib/token.ts`를 읽었다), 허용 출처를 모르는 동안에는 어느 페이지도 믿을 수 없기 때문이다.
- **받지 못했을 때.** 요청이 실패했거나, 응답이 200이 아니거나, 모양이 틀렸으면(허용 출처가 글자의 목록이 아니다, 상한이 양의 정수가 아니다) 위젯은 닫힌 채로 남는다. 지금 위젯 설정이 틀렸을 때 보이는 알림("위젯 설정이 올바르지 않습니다. 사이트 관리자에게 알려 주세요.")을 그대로 보이고 입력을 막는다. 새 화면 요소와 새 문구를 더하지 않는다. 최종 사용자가 화면을 새로 고치면 다시 받는다.
- **열려 있는 화면.** 위젯은 열릴 때 한 번 값을 받는다. 운영자가 사이트 파일을 고치고 위젯을 다시 띄워도, 이미 열려 있는 화면은 새로 고치기 전까지 앞의 값을 쓴다.
- **스크립트는 사이트 파일의 값을 담지 않는다.** 페이지 안 방식의 스크립트는 지금 상한을 담아 지어진다. 값 파일에서 받게 되면 스크립트의 내용은 사이트 파일과 무관해지고, 같은 판의 이미지에서는 어느 배포에서나 같다.
- 상한을 세는 단위(코드 포인트)와 입력창의 동작은 그대로다.

거부한 안: 값을 받지 못하면 기본 상한으로 열어 둔다. iframe 방식은 허용 출처 없이는 토큰을 물을 수 없어 어차피 닫혀야 하고, 두 방식이 다르게 굴면 같은 장애가 방식에 따라 다르게 보인다. 값 파일은 페이지와 스크립트를 내준 같은 서버가 내므로 그것만 받지 못하는 일은 드물 것으로 본다(어림). 받지 못하면 스스로 여러 번 다시 시도한다. 같은 까닭으로 드문 경우를 위해 기다리는 상태와 시도 횟수를 더하지 않는다.

### 위젯 이미지(명세가 정했다)

- **빌드는 이미지를 지을 때 한 번 한다.** 사이트 파일 없이, 워크스페이스 전체 의존성이 깔린 단계에서 빌드한다. 이 단계는 뜬 뒤의 이미지에 남지 않는다.
- **뜬 뒤의 이미지에 담는 것.** 위젯과 그것이 기대는 워크스페이스 패키지의 운영 의존성(잠금 파일을 얼린 채 깐다), 빌드 산출물, 공개 파일(글꼴과 스크립트), 서비스 시작에 드는 파일(시작 래퍼, Next의 설정, 사이트 파일을 읽는 패키지)이다. 빌드 도구(Vite, Tailwind의 Vite 플러그인, TypeScript)와 시험 쪽 패키지는 담지 않는다. 시제품의 이미지에는 Next가 깔려 있고 그 셋은 없었으며, 그 꼴로 섰다(프로브 결과 1, 2, 쟀다).
- **크기.** 시제품은 690.6MiB였다(지금은 874.3MiB). 운영 의존성만 깐 단계가 666.9MiB라 대부분이 의존성이다(프로브 결과 1, 쟀다).
- **쓰는 자리는 폴더 하나다.** 뜰 때 쓰는 파일은 둘이다. Next가 읽는 응답 머리 목록의 사본과 값 파일이다. 이미지는 앱 폴더 안의 그 두 자리를 `/run/agent-os-widget` 폴더 안을 가리키는 심볼릭 링크(다른 자리의 파일을 가리키기만 하는 파일. 열면 가리킨 파일이 열린다)로 두고, 서비스 시작은 그 링크를 따라 그 폴더에 쓴다. 그래서 루트가 읽기 전용이어도 그 폴더 하나만 쓸 수 있으면 선다. Next는 링크를 따라가 두 파일을 읽고 냈다(프로브 결과 4, 쟀다). 그 폴더는 이미지에도 앱 사용자 소유(권한 0700)로 만들어 두어, 루트를 읽기 전용으로 두지 않고 띄워도 선다(프로브 결과 2의 쓰기 가능한 루트 회차, 쟀다). 이미지를 짓는 PC에서 위젯을 띄운 적이 있어 그 두 자리에 파일이 남아 있어도, 이미지에는 그 자리에 링크만 있어야 한다.
- **덜어 내는 것.** 뜰 때의 빌드, 워크스페이스 전체 의존성, 빌드가 쓰던 자리(`.next`, `public`)를 앱 사용자 소유로 넘기던 것, root가 아닌 사용자의 빌드를 위해 이미지를 지을 때 미리 만들던 타입 파일(`next typegen`), 빌드 중에 끌 때를 위해 init(컨테이너의 첫 프로세스로 떠서 끄라는 신호를 위젯에 전하는 작은 프로그램. 이 이미지는 tini를 쓴다)에 주던 프로세스 그룹 옵션(`-g`)이다. 뜰 때 빌드의 자식 프로세스가 없으므로 그 옵션 없이 0.16~1.16초에 종료 코드 143으로 꺼졌다(프로브 결과 2. 끄기를 잰 쉰 회차에 프로브가 적은 값이다).
- **그대로인 것.** 바탕 이미지와 그 digest, init(tini), 앱 사용자(사용자 번호와 그룹 번호인 uid·gid가 10001이다), 이미지 안에서만 켜지는 루프백 예외의 표지 파일, `NEXT_TELEMETRY_DISABLED=1`, 사이트 파일의 자리를 늘 넘기는 시작 명령, 포트 3000, 이미지의 라벨 셋이다.
- **네트워크 없이 선다.** 네트워크를 끊은 컨테이너에서 섰다(프로브 결과 4, 쟀다). 인터넷이 막힌 곳에서도 뜬다.
- **다른 uid.** 지금처럼 이미지를 지을 때 정한 uid로 뜬다. 쓰는 폴더가 그 uid의 것이라 다른 uid로는 쓰지 못할 것으로 본다(어림, 재지 않았다).
- **이미지를 짓는 시간이 는다.** 뜰 때 하던 빌드가 이미지를 지을 때로 옮겨 온다. 이 PC에서 그 단계는 캐시 없이 64.2초와 73.8초였고, 의존성을 까는 층이 캐시에서 온 채 소스가 바뀌어 다시 돈 다섯째 실행에서는 25.7초였다(프로브 결과 1. 64.2초는 손으로 봤다. 세 값이 벌어진 까닭은 가르지 않았다). 판 내기와 실제 이미지를 띄우는 CI 잡이 위젯 이미지를 짓는 시간이 그만큼 늘 것으로 본다(어림, CI에서 재지 않았다).

거부한 안: 뜰 때 쓰는 두 파일을 링크 없이 앱 폴더 안의 보통 파일로 둔다. 읽기 전용 루트에서 쓰지 못해 서비스 시작이 끝났다(프로브 결과 4, 쟀다). 빌드 산출물 폴더와 공개 파일 폴더를 통째로 tmpfs로 준다. 뜰 때마다 산출물을 그리로 복사해야 하고 산출물 전체가 컨테이너의 메모리에 든다(시제품의 두 폴더는 22MB와 7MB였다). `/tmp`를 쓰는 자리로 삼는다. 무엇이든 쓰는 넓은 자리라, 위젯이 쓰는 것이 두 파일뿐이라는 것이 배포 설정에서 보이지 않는다.

### 단독 compose의 위젯(명세가 정했다)

- **읽기 전용 루트와 쓰는 폴더.** 위젯 서비스에 읽기 전용 루트를 주고, `/run/agent-os-widget`을 앱 사용자 소유(uid·gid 10001, 권한 0700)의 tmpfs로 준다. 그 꼴로 섰다(프로브 결과 4, 쟀다. 읽기 전용 하나만 건 회차와, 능력을 모두 빼고 권한 상승을 막은 회차 모두. 단독 compose가 줄 꼴대로 읽기 전용 하나만 걸고 네트워크를 붙인 채 띄운 것은 여섯째 실행의 한 번이고, 그 앞 세 실행의 같은 회차는 네트워크도 끊은 채였다). tmpfs의 옵션을 적는 꼴은 같은 compose 파일의 serve가 이미 쓰는 꼴이라(`deploy/standalone/compose.yaml`을 읽었다) 지원하는 최소 판을 올리지 않는다.
- **상태 확인의 시작 유예.** 위젯만 따로 두던 300초를 지우고 다른 컨테이너와 같은 공통 값(30초)을 쓴다. 확인하는 명령은 그대로다. 공통 값에서 2.58~2.95초에 healthy가 됐고, 아무도 듣지 않는 포트에 건 대조는 25초 동안 돈 확인이 모두 실패한 채 `starting`이었다(프로브 결과 6, 쟀다). 프로브는 그 명령을 셸을 거쳐 불렀고 compose는 셸 없이 부른다. compose 파일 그대로의 상태 확인은 Testing Decisions의 첫째가 본다.
- **메모리 제한.** 지금처럼 두지 않는다. 뜰 때 빌드하므로 제한을 두지 않는다고 적은 주석은 고친다. 제한 값을 정하지 않는 까닭은 근거가 얇기 때문이다. 256MiB로 제한한 회차는 넷뿐이었고(최고치 77.7~81.6MiB로 섰다), 오래 띄운 위젯의 메모리는 재지 않았다.
- **그대로인 것.** 이미지 이름, 재시작 정책, 루프백 예외의 환경 변수, 사이트 파일 폴더를 읽기 전용으로 얹는 것, 프록시 설정이다.

거부한 안: 위젯에 메모리 제한 값을 둔다. 위의 까닭으로 값을 고를 근거가 모자란다. 위젯에 능력 빼기와 권한 상승 막기를 더한다. 그 꼴로도 섰지만 다른 web 컨테이너 둘이 받지 않는 제한이라, 위젯에만 더하면 세 컨테이너의 잠금 수준이 다시 갈린다. 세 컨테이너에 함께 더하는 일은 이 기능의 범위 밖이다.

### 배포 안내(명세가 정했다)

배포 파일 묶음에 드는 운영자용 문서(`deploy/standalone/README.md`를 읽었다)에서 고치는 것은 아래다. 절은 그 문서의 제목으로 가리킨다.

- **"서버의 메모리".** 위젯이 뜰 때마다 빌드하며 1.6GiB 가까이 쓴다는 문단과 메모리 제한을 새로 걸지 말라는 문장을 뺀다. 그 자리에는 위젯이 뜰 때 빌드하지 않는다는 것과, 재 본 PC에서 뜬 직후 90MiB 안팎을 썼다는 것을 적는다. 권하는 제한 값은 적지 않는다.
- **"4. 띄우기와 확인".** 위젯이 뜰 때 빌드하므로 몇 분이 걸린다는 말과, 빌드하는 동안 위젯의 상태가 `starting`이라는 문장을 뺀다. 처음 띄울 때 시간이 드는 것은 이미지를 받는 일이다.
- **"사이트 파일이나 위젯 테스트 페이지 설정을 고쳤을 때".** 위젯이 뜰 때 사이트 파일로 빌드한다는 말을 뜰 때 사이트 파일을 읽는다는 말로 고친다. 세 컨테이너를 다시 띄우는 명령은 그대로다. 위젯이 다시 빌드하는 10초에서 30초 동안 502가 난다는 문장은 위젯이 다시 뜨는 몇 초 동안으로 고친다. 그 문장에 적을 시간은 실제 이미지를 띄우는 시험을 이 PC에서 돌린 티켓이 프록시를 거쳐 잰 값으로 적는다(이 명세의 0.60~1.96초는 컨테이너 안에서 잰 값이고 프록시를 거치지 않았다). 그리고 한 문장을 더한다. 이미 위젯을 열어 둔 화면은 새로 고쳐야 새 값을 받는다.
- **문제 해결의 "위젯과 관리 화면".** 위젯이 종료 1로 끝났을 때 사이트 파일을 보라는 지금의 문장은 그대로 맞다. 한 가지를 더한다. 로그의 진단이 지어 둔 응답 머리 목록의 모양이 기대와 다르다는 것이면 사이트 파일의 문제가 아니라 그 판의 이미지의 결함이므로, 앞 판으로 되돌리고 알린다.

### 구현 티켓이 코드와 같은 티켓에서 고치는 문서

기능 계획이 넘긴 셋이다.

- `web/apps/widget/EMBED.md`. 무결성 검사를 다루는 항목이 "번들은 운영자의 사이트 파일 값(요청 글자 수 상한)을 담아 빌드되므로 운영자가 위젯을 다시 빌드할 때마다 해시를 새로 받아 바꿔야 한다"고 적는다. 스크립트가 사이트 파일의 값을 담지 않고, 해시는 운영자가 판을 올릴 때 새로 받는다는 말로 고친다. 사이트 파일의 값을 다루는 절의 "위젯도 같은 파일로 빌드된다"는 위젯이 뜰 때 같은 파일을 읽는다는 말로 고친다.
- `docs/constitution/tech.md`의 웹 칸. "위젯 빌드는 서버와 같은 사이트 파일을 … 읽어 합친 허용 출처와 가장 작은 요청 글자 수 상한을 싣는다"는 문장을, 위젯이 뜰 때 그 파일을 읽어 두 값을 값 파일과 응답 머리로 낸다는 말로 고친다. 근거가 되는 결정은 ADR 0064이고, 헌법의 판을 올리는 규칙은 `docs/constitution/README.md`를 따른다.
- `CONTEXT.md`의 사이트 파일 항목. 피할 말의 풀이에 든 "위젯 빌드와 위젯 테스트 페이지가 이 파일을 입력으로 읽기는 하지만"을 위젯이 뜰 때 읽는다는 말로 고친다. 같은 편집에서 "값 파일"을 용어집에 올린다. ADR 0064와 이 명세가 쓰는 이름인데 용어집에 아직 없다(`CONTEXT.md`를 Grep했다). 용어집은 `domain-modeling` 스킬로 고친다(`CLAUDE.md` 지도).

같은 티켓은 위젯이 빌드할 때 사이트 파일을 읽는다거나 뜰 때 빌드한다고 적은 말을 저장소 전체에서 찾아, 살아 있는 문서와 주석에 남은 것을 고친다(`CLAUDE.md` 작업 규약 4). 찾는 말과 나온 자리를 아래에 예로 든다. 둘 다 전부가 아니고, 구현 티켓이 그때의 저장소에서 다시 찾는다.

- 찾는 말의 예: "뜰 때 빌드", "빌드에 굳", "다시 빌드", "빌드의 입력", "사이트 파일로 빌드", "같은 파일로 빌드".
- 이 명세를 쓰며 그 말로 찾아 나온 자리의 예(Grep했다): 이미지를 짓는 파일과 compose 파일의 주석, 시작 래퍼와 Next 설정의 머리 주석, 배포 안내, 위젯과 위젯 테스트 페이지의 e2e 준비와 설정(`e2e/stack.ts`, `playwright.config.ts`), 단독 배포 e2e의 주석(`web/packages/e2e-standalone/e2e/deployment.e2e.ts`, `env.ts`), CI 워크플로의 주석(`.github/workflows/ci.yml`), 루트 `README.md`의 트리 설명, `docs/constitution/operations.md`의 가드레일 절이다. 마지막 것은 헌법의 문서라 `docs/constitution/README.md`의 판 규칙을 따른다.
- `.scratch/` 아래에서 나온 자리(다른 기능의 기능 계획과 명세)는 `docs/constitution/operations.md`의 문서 위치 절로 기록인지 살아 있는 문서인지를 가른 뒤에 고친다. release-image의 명세와 티켓은 끝난 기능의 기록이라 고치지 않는다.

### 티켓을 나눌 때 함께 둘 것(명세가 정했다)

- 위젯의 코드(시작 래퍼, 브라우저 쪽, 그 시험과 위젯 e2e, 위 문서 셋)가 먼저이고, 이미지와 compose와 배포 안내와 실제 이미지를 띄우는 시험이 그 뒤다. 코드만 바뀐 사이에는 지금의 이미지가 뜰 때 빌드한 뒤 서비스 시작이 사이트 파일을 읽어 값을 넣으므로, 느리지만 맞게 설 것으로 본다(구조에서 미룬 어림이고 재지 않았다. 그 티켓이 단독 배포 e2e를 이 PC에서 돌려 확인한다). 거꾸로는 서지 않는다. 미리 지어 둔 이미지는 뜰 때 값을 받는 코드가 있어야 사이트 파일을 따른다.
- 이미지와 compose는 한 티켓에서 함께 바꾼다. 읽기 전용 루트는 쓰는 폴더의 링크가 든 이미지에서만 서고(링크 없는 이미지는 읽기 전용 루트에서 끝났다, 프로브 결과 4), 시작 유예 30초는 뜰 때 빌드하지 않는 이미지에서만 맞다.
- 위젯 테스트 페이지의 e2e도 위젯을 같은 시작 래퍼로 빌드하고 띄운다(`web/apps/portal/e2e/stack.ts`를 읽었다). 래퍼의 행동을 바꾸는 티켓은 그 e2e의 준비도 함께 고치고 로컬에서 돌린다.

## Testing Decisions

좋은 시험은 바깥에서 보이는 행동을 본다. 위젯이 내는 응답 머리와 값 파일의 응답, 브라우저에서 틀이 실리거나 막히는 것, 입력창이 받는 글자 수, 서비스 시작의 종료 코드와 진단이다. 래퍼 안에서 어떤 함수가 불렸는지는 보지 않는다.

이음매는 넷이고 새로 만드는 것은 없다(사용자가 골랐다. 일지 2026-11-27-0407 "사용자에게 물은 것 하나"). 있는 시험 넷에 사례를 더한다.

1. **실제 이미지의 단독 배포.** 지은 이미지들과 `deploy/standalone/`의 compose 파일로 단독 배포를 띄우고 브라우저가 프록시로 들어가는 시험이다(`web/packages/e2e-standalone/e2e/deployment.e2e.ts`, release-image 명세 Testing Decisions의 첫째가 세웠다). 기능 계획의 수락 셋을 사례로 더한다.
   - 위젯 컨테이너가 빌드 없이 뜬다. 위젯 컨테이너의 루트가 읽기 전용이고 상태가 healthy이며, 컨테이너의 로그에 뜰 때 받은 값을 알리는 한 줄이 있고 Next의 빌드 머리말이 없다. 빌드는 앱 폴더 안에 쓰므로 읽기 전용 루트에서는 돌 수 없다.
   - 허용 출처에 든 사이트의 페이지만 위젯 페이지를 품는다. 사이트 파일의 허용 출처에 든 출처의 페이지가 품은 틀에는 위젯의 문서가 실리고, 다른 출처의 페이지가 품은 틀은 브라우저가 막는다.
   - 사이트 파일의 요청 글자 수 상한을 바꾸고 위젯 컨테이너를 다시 띄우면 위젯이 새 상한을 따른다. 값 파일이 새 상한을 내고, 위젯 테스트 페이지에서 연 위젯의 입력창이 새 상한까지만 받는다. 같은 배치를 다른 사례가 함께 쓰므로 이 사례는 끝에 사이트 파일을 되돌리고 위젯을 다시 띄운다. 선례는 컨테이너를 다시 만드는 사례 "백엔드 하나를 다시 만들어도 프록시가 새 주소를 따라 15초 안에 다시 200 을 낸다"다.
   - 이 시험은 CI에서 main으로 가는 PR과 main 푸시에서만 돈다(`.github/workflows/ci.yml`의 `e2e-standalone` 잡을 읽었다). dev로 가는 PR에서는 `deploy/`나 이미지를 짓는 파일을 고친 티켓이 이 PC의 Docker로 돌려 결과와 걸린 시간을 일지에 적는다(release-image 명세가 정한 규약이고 `CLAUDE.md`의 검증 명령에 있다).
2. **위젯 e2e.** 실제 serve와 실제 위젯을 띄워 브라우저로 보는 시험이다(`web/apps/widget/e2e/`). 준비 단계가 지금은 사이트 파일로 빌드한 뒤 띄우는데(`web/apps/widget/e2e/stack.ts`를 읽었다), 빌드는 사이트 파일 없이 하고 띄울 때 사이트 파일을 주게 바꾼다. 그러면 있는 사례 전부가 뜰 때 값을 받는 길을 지난다("허용 출처의 페이지는 위젯을 품고 허용 밖 출처의 페이지는 품지 못한다", "입력창의 글자 수 상한은 서버의 기본값과 같다", 페이지 안 방식의 사례들). 준비가 실제 빌드의 산출물을 시작 래퍼로 띄우므로, 산출물의 모양이 달라 바꿀 자리를 찾지 못하면 준비에서 멈추고 사례가 모두 빨개진다. 바꾸고 더하는 것은 둘이다.
   - 준비의 사이트 파일이 기본값(20,000)과 다른 상한을 갖게 한다. 지금의 사례 "입력창의 글자 수 상한은 서버의 기본값과 같다"는 입력창과 서버가 모두 기본값이라(그 사례의 단언을 읽었다), 위젯이 값 파일에서 받은 상한과 코드에 든 기본값을 가르지 못한다. 그 사례는 입력창과 서버가 사이트 파일의 상한을 함께 따르는지를 보게 바뀐다.
   - 한 번 빌드한 산출물로 사이트 파일을 바꿔 위젯만 다시 띄우면, 응답 머리와 값 파일과 입력창의 상한이 새 값을 따른다. 값이 빌드에 굳는 판이라면 실패하는 사례다. 사례들은 띄워 둔 위젯 하나를 함께 쓰며 차례로 돌므로(`web/apps/widget/playwright.config.ts`의 `workers: 1`을 읽었다), 이 사례는 끝에 원래의 사이트 파일로 다시 띄워 뒤의 사례에 넘긴다.
   - 이 시험은 모든 PR의 CI에서 돈다(같은 파일의 `e2e-widget` 잡을 읽었다. main으로 가는 PR만 고르는 문이 없다). 그래서 Next의 판을 올리는 PR이 이 시험을 지나고, 지어 둔 산출물의 모양이 바뀌어 값을 바꿔 넣지 못하거나 바꾼 값을 Next가 응답에 달지 않으면 그 PR에서 빨개진다.
3. **시작 래퍼의 시험.** 래퍼의 판정을 보는 단위 시험, 실제 프로세스를 띄우는 시험, 래퍼의 명령이 읽는 두 설정(스크립트를 짓는 설정과 Next의 설정 파일)의 시험이다(`web/apps/widget/tools/start.test.ts`, `start.spawn.test.ts`, `element.test.ts`, `web/apps/widget/next.config.test.ts`). pre-commit과 CI의 `pnpm -C web verify`에서 돈다.
   - 바꿀 자리를 찾는 규칙. 자리가 정확히 하나이고 값이 `'none'`이면 그 값만 바뀌고 다른 머리 규칙(글꼴, 스크립트, 값 파일에 다는 머리)은 글자 그대로다. 자리가 없을 때, 둘일 때, 값이 `'none'`이 아닐 때는 아무것도 쓰지 않고 진단을 낸다.
   - 값 파일의 모양. 허용 출처가 없는 사이트 파일, 사이트가 여럿인 사이트 파일(합친 목록과 가장 작은 상한), 환경 변수가 없을 때다.
   - 차례. 서비스 시작이 사이트 파일을 읽고 두 파일을 쓴 뒤에 Next를 부르고, 실패하면 부르지 않는다(선례 "준비가 실패하면 next 를 부르지 않는다"). 없는 파일, 깨진 파일, 빈 변수를 넣는다. 폴더와 읽지 못하는 파일은 따로 넣지 않는다. 같은 함수가 가르는 갈래이고 release-image가 실제 이미지에서 잰 길이다.
   - 빌드가 사이트 파일을 읽지 않는다. 빌드의 준비와 스크립트를 짓는 설정과 빌드 때의 Next 설정이 사이트 파일의 환경 변수를 보지 않는다. 사이트 파일의 환경 변수를 달리 주어도 스크립트의 내용이 같고, 빌드가 굳히는 응답 머리는 늘 `'none'`이다.
   - 함께 바뀌는 지금의 사례. 지금의 사례 가운데 이 명세가 바꾸는 행동을 단언하는 것은 같은 티켓이 고친다. 빌드가 사이트 파일을 읽는다는 것, 빌드가 두 값을 산출물에 싣는다는 것, 서비스 시작이 준비 없이 Next만 부른다는 것을 단언하는 사례가 그렇다. 시험이 실패해서 시험을 고치는 일(원칙 II가 막는다)이 아니라, 명세가 행동을 바꿔 사례가 말할 것이 바뀌는 일이다. 아래는 파일마다의 예이고 전부가 아니다(네 파일을 읽었다). 구현 티켓이 위의 성질로 다시 찾는다.
     - `start.spawn.test.ts`의 "상대 경로로 준 사이트 파일을 래퍼를 부른 자리에서 찾고, 읽지 못하면 빌드가 그 진단으로 실패한다"는 그 진단으로 끝나는 쪽이 서비스 시작으로 바뀐다(둘 다 Next를 부르기 전에 끝나 빠른 사례다).
     - `element.test.ts`의 묶음 "변수가 준 사이트 파일을 읽지 못하면 빌드가 실패한다"는 없어진다. 같은 파일의 "사이트 파일을 주지 않으면 서버의 기본 상한을 싣는다"와 "두 언어가 함께 읽는 사이트 파일의 가장 작은 상한을 싣고, 허용 출처는 싣지 않는다"는 스크립트가 상한을 싣지 않는다는 사례로 바뀐다.
     - `next.config.test.ts`에는 같은 이름의 묶음 "변수가 준 사이트 파일을 읽지 못하면 빌드가 실패한다"가 하나 더 있고, Next의 설정이 사이트 파일을 읽어 두 값을 빌드에 싣는 것을 보는 사례들이 있다("두 언어가 함께 읽는 사이트 파일의 합친 허용 출처가 frame-ancestors 에, 가장 작은 상한이 빌드에 든다"가 그 예다). 설정이 값을 빌드에 싣지 않게 되므로 이 사례들은 빌드 때의 설정이 사이트 파일과 무관하게 닫힌 값을 낸다는 것과, 개발 서버에서는 지금처럼 사이트 파일을 읽어 응답 머리를 낸다는 것을 보게 바뀐다. 어느 사례가 이 파일에 남고 어느 사례가 서비스 시작의 시험으로 옮겨 가는지는 빌드에서 설정이 사이트 파일을 읽지 않게 하는 방법에 달려 있어 구현 티켓이 정한다(위 "시작 래퍼의 세 명령"). 값 파일에 다는 `Access-Control-Allow-Origin: *` 규칙의 사례는 글꼴과 스크립트의 같은 사례 옆에 더한다.
     - `start.test.ts`의 명령마다 부르는 차례를 보는 사례는 서비스 시작이 `next start`만 부른다고 단언한다. 서비스 시작이 값을 넣는 단계 뒤에 Next를 부르는 차례로 바뀐다.
   - 이 이음매에서는 실제 `next build`를 돌리지 않는다. 커밋마다 도는 시험에 빌드 한 번의 시간을 더하지 않으려는 것이다. 실제 빌드가 낸 산출물의 모양은 둘째 이음매의 준비가 지난다.
4. **위젯의 브라우저 쪽 단위 시험.** 위젯의 화면과 값을 읽는 자리의 시험이다(`web/apps/widget/lib/build.test.ts`와 화면의 시험들). 값 파일의 응답을 흉내 내어 세 경우를 본다. 값을 받기 전에는 입력이 막혀 있고 iframe 방식은 토큰을 묻지 않는다. 받은 뒤에는 입력창이 받은 상한을 따르고 토큰을 받은 허용 출처로 묻는다. 요청이 실패했거나 200이 아니거나 모양이 틀리면 설정 오류 알림이 보이고 입력이 막힌다. 페이지 안 방식은 스크립트가 실려 온 출처의 `/widget/runtime.json`을 받고, 기준 주소를 얻지 못하면 받지 않는다. `build.test.ts`의 지금 사례들("빌드 값은 빌드가 싣는 이름 그대로 process.env 의 점 표기로 읽는다"가 그 예다)은 빌드가 굳힌 글을 읽는 것을 보므로 값 파일을 읽는 사례로 바뀐다. 셋째 이음매의 "함께 바뀌는 지금의 사례"와 같은 일이다.

위젯의 코드를 고친 티켓은 `CLAUDE.md`의 검증 명령이 그 경우에 치라고 한 것도 친다. 위젯의 실제 모델 e2e(`-m llm_widget`)와 위젯의 사진 비교(`pnpm -C web visual:widget`)다. 새 화면 요소가 없으므로 사진의 정답은 바뀌지 않을 것으로 본다(어림).

거부한 안: 위젯 이미지를 실제로 지어 띄우는 시험을 모든 PR의 CI에서 돌리는 잡을 새로 만든다. 사용자에게 보인 선택지 가운데 고르지 않은 것이다. 이미지가 깨진 것을 일찍 알지만 PR마다 이미지를 짓는 시간이 들고 CI 잡이 하나 는다. 실제 이미지를 띄우는 시험 하나에만 사례를 둔다. 이것도 고르지 않은 선택지다. 그 시험은 main으로 가는 PR에서만 돌아, Next의 판을 올려서 깨진 것을 출시 직전에야 알게 된다.

## Out of Scope

다른 기능에 넘기는 것은 받는 쪽의 기능 계획 본문에도 적었고, 받는 기능의 `**Blocked by:**`를 대 봤다. 받는 쪽은 site-limits-admin과 deploy-package의 기능 계획이고, 두 곳 모두 "widget-runtime-values 명세가 넘긴 것(2026-11-27,"으로 시작하는 문단이다(그 괄호의 뒤쪽에는 이 명세의 어느 절에서 왔는지를 적었다).

- **두 값을 화면에서 고치는 일과, 다시 띄우지 않고 바뀐 값이 듣게 하는 일**은 site-limits-admin의 것이다(ADR 0064 결정 "기능 행", 0.1 판 뒤). `**Blocked by:**`에 widget-runtime-values가 있다. 그 행의 설계가 이 명세 위에 짓는 것은 위젯이 두 값을 받는 자리와 모양(위 "값 파일"과 "품어도 되는 사이트를 알리는 응답 머리")과, 브라우저 쪽에서 두 값을 읽는 자리가 하나라는 것이다. 그 설계가 정할 것으로 넘긴 것은 넷이다. 떠 있는 위젯이 값 파일과 응답 머리를 다시 쓰는 길, 이미 열려 있는 화면이 새 값을 받는 때, 위젯 앞에 응답을 캐시하는 프록시가 있을 때, 위젯이 사이트마다 다른 값을 따를지다.
- **사이트마다 다른 허용 출처와 상한을 위젯이 따르는 일**은 이 명세가 하지 않는다(위 "합친 허용 출처와 가장 작은 상한"). 받는 기능을 따로 세우지 않았고, site-limits-admin의 설계가 정할 것 넷의 마지막으로 그 기능 계획에 적었다. 그 행의 수락은 사이트 하나의 상한을 바꾸면 위젯이 새 상한을 따른다고 적는데, 가장 작은 상한을 쓰는 위젯은 다른 사이트의 상한이 더 작으면 바뀌지 않기 때문이다.
- **통합 배포의 대상 사양과 메모리 문장**은 deploy-package의 것이다. 그 행의 `**Blocked by:**`에는 widget-runtime-values가 없어 그 행이 먼저 돌 수 있었지만, 아직 돌지 않았다(그 행에는 기능 계획만 있고 명세도 배포 파일도 없다). 그래서 이 명세가 고칠 통합 배포의 문장은 없고, 그 기능 계획이 옛 값으로 적은 문장("위젯은 뜰 때마다 빌드하며 1.6GiB 가까운 메모리를 쓰므로 대상 사양의 메모리에 넣는다")이 이 기능 뒤에는 맞지 않는다는 것과 새 값을 그 기능 계획에 적었다. 통합 배포가 단독 compose에서 따를 것 셋(읽기 전용 루트와 쓰는 폴더, 시작 유예, 사이트 파일을 고친 뒤 다시 띄우기)과 그 설계가 볼 것 둘도 함께 적었다. 볼 것의 하나는 앞단의 캐시이고(Further Notes), 다른 하나는 그 기능 계획의 "위젯처럼 정적 파일로 낼 수 있는 것은 프록시가 바로 내준다"다. 프록시가 위젯의 파일을 바로 내면 Next가 붙이는 응답 머리가 빠지고, 값 파일은 컨테이너가 뜰 때 메모리의 폴더에 쓰이는 파일이라 프록시가 읽을 자리에 없다.
- **위젯 컨테이너의 메모리 제한 값**과 **web 컨테이너 셋에 능력 빼기와 권한 상승 막기를 더하는 일**은 하지 않는다(위 "단독 compose의 위젯"). 받는 기능이 없다. 필요해지면 새 행이다.
- **값을 받지 못했을 때 위젯이 스스로 다시 시도하는 일**은 하지 않는다(위 "브라우저 쪽이 값을 받는 길").
- **serve와 위젯 테스트 페이지가 사이트 파일을 읽는 방식**은 그대로다. 둘 다 시작할 때 한 번 읽고, 사이트 파일을 고친 뒤에는 지금처럼 다시 띄운다.
- **위젯 이미지를 더 줄이는 일**은 하지 않는다. Next의 단독 실행 출력(`output: "standalone"`)은 시작 래퍼를 거치지 않아 release-image가 거부했다(그 명세의 "이미지의 구성").

## Further Notes

- **측정 환경의 한계.** 리눅스 서버는 쓰지 않았다. 모든 측정은 이 PC(Windows 10)의 Docker Desktop(엔진 29.9.2, WSL2 커널)의 리눅스 컨테이너에서 돌았다. 기능 계획의 수락이 말하는 "리눅스에서"는 실제 이미지를 띄우는 시험이 GitHub의 리눅스 러너에서 처음 본다(Testing Decisions의 첫째). 재지 못한 것은 프로브 README의 "재지 못한 것"에 있다. 서버의 폴더를 컨테이너 안에 그대로 붙이는 바인드 마운트(단독 compose가 사이트 파일을 주는 방식이다. 프로브는 사이트 파일을 이름 붙은 볼륨이나 이미지 안의 파일로 줬다), 프록시를 거친 요청, 위젯의 코드가 값 파일을 받아 쓰는 것, 시작 래퍼의 루프백 검사, Chromium 밖의 브라우저, 오래 띄운 컨테이너의 메모리다. 같은 Docker 데몬을 다른 세션이 함께 쓴 PC라 시간은 범위로만 읽는다.
- **Next의 판을 올릴 때.** 이 방법은 Next 16.3.6이 지어 낸 파일의 모양에 기댄다. 판을 올리는 티켓은 프로브를 다시 돌려 본다(명령은 `.scratch/widget-runtime-values/probes/README.md`의 표). 모양이 달라졌으면 Testing Decisions의 둘째가 그 PR의 CI에서, 첫째가 main으로 가는 PR에서, 서비스 시작의 검사가 뜰 때 잡는다. 바꿀 자리의 수나 값이 달라진 것이면 시험이 놓쳐도 위젯이 뜨지 않는 쪽으로 실패한다. Next가 그 파일을 더는 읽지 않게 바뀐 것이면 위젯이 지은 때의 값(`'none'`)으로 떠서 어느 사이트도 품지 못하고, 시험의 허용 출처 사례가 그것을 잡는다(둘 다 구조에서 미룬 어림이다).
- **앞단에 캐시를 둘 때.** 위젯 페이지의 응답은 공유 캐시가 오래 두어도 된다는 머리(`Cache-Control: s-maxage=31536000`)를 단다(프로브 결과 2, 쟀다). 미리 그려 둔 페이지에 Next가 다는 머리이고 지금도 같다. 응답을 캐시하는 프록시나 CDN을 위젯 앞에 두면 페이지와 함께 `frame-ancestors` 머리까지 캐시에 남아, 사이트 파일을 고치고 위젯을 다시 띄워도 옛 값이 나갈 수 있다. 단독 배포의 프록시는 응답을 캐시하지 않는다(`deploy/standalone/proxy/`에 캐시 설정이 없다, 코드를 읽었다). 통합 배포가 앞단에 캐시를 둘지는 deploy-package의 설계가 보도록 그 기능 계획에 적었다.
- **떠 있는 동안 사이트 파일만 고쳤을 때.** 위젯은 뜰 때 한 번 읽으므로 다시 띄우기 전까지 앞의 값을 낸다(구조에서 미룬 어림이고 재지 않았다). serve와 위젯 테스트 페이지도 같다. 떠 있는 위젯의 값 파일이나 응답 머리 목록의 사본을 다시 썼을 때 무엇이 나가는지도 재지 않았다. 값 파일은 요청마다 디스크에서 나가는 공개 파일이라 바뀐 내용이 나갈 것으로 보지만(어림), 응답 머리 목록은 Next가 시작할 때만 읽는지 떠 있는 동안에도 다시 읽는지 모른다. 다시 띄우지 않고 듣게 하는 일은 site-limits-admin의 것이고, 이 두 가지를 그 기능 계획에 적었다.
- **첫 판 내기에서 볼 것.** 이 변경이 든 첫 판을 내는 세션은 판 내기와 `e2e-standalone` 잡이 위젯 이미지를 짓는 데 걸린 시간을 일지에 적는다. 이미지를 지을 때의 빌드가 CI 러너에서 얼마나 걸리는지는 재지 않았다.
- **release-image 명세와의 관계.** 그 명세의 "이미지의 구성"이 위젯에 대해 적은 것(뜰 때의 빌드, 874.3MiB, 읽기 전용이 아닌 루트, 메모리 제한을 두지 않는 까닭, 시작 유예 300초)과 "배포 안내"의 메모리 항목은 그 기능이 지은 때의 기록으로 남고, 위젯 이미지의 지금 모양은 이 명세가 원천이다.
