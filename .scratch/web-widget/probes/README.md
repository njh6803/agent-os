# web-widget 프로브

명세·ADR·코드 주석이 근거로 드는 측정 스크립트다. 규약은 `docs/agents/issue-tracker.md`의 "프로브와 근거".

`jwt_verify/`는 위젯 토큰(사이트 백엔드가 서명한 JWT)을 검증할 라이브러리와 서명 키 종류를 고르는 측정이다. 후보는 PyJWT, joserfc, jwcrypto이고 알고리즘은 HS256, EdDSA·Ed25519(같은 Ed25519 서명의 두 이름, 뒤의 것이 RFC 9864의 새 이름), RS256이다. 셋 다 저장소 루트에서 돌고, 먼저 `make_envs.py`로 후보마다 빈 가상 환경을 만든다. 저장소 `.venv`와 `uv.lock`은 건드리지 않는다.

```sh
PYTHONUTF8=1 uv run python .scratch/web-widget/probes/jwt_verify/make_envs.py <환경 루트>
PYTHONUTF8=1 uv run python .scratch/web-widget/probes/jwt_verify/check_types.py <환경 루트>
PYTHONUTF8=1 <환경 루트>/<후보>/.venv/Scripts/python .scratch/web-widget/probes/jwt_verify/cases.py <후보>
PYTHONUTF8=1 uv run python .scratch/web-widget/probes/jwt_verify/cases.py pyjwt
PYTHONUTF8=1 uv run python .scratch/web-widget/probes/jwt_verify/deps.py <환경 루트> <작업 디렉터리>
```

## 2026-10-03 결과

- 타입: 세 후보의 소비 지점 모두 pyright strict 오류 0, 타입 우회 0. 대조군은 기대한 오류만 냈다(`dict(...)`로 감싼 쪽의 `reportReturnType` 하나, jwcrypto는 `object`로 선언한 쪽의 `reportIndexIssue`와 `reportUnknownVariableType`). 좁히지 않고 `sub`를 돌려주는 코드도 `dict[str, Any]`를 그대로 쓰면 strict를 지난다.
- 실행: 허용 알고리즘을 하나로 고정한 소비 지점은 세 후보 모두 만료·다른 키·`aud`·`iss`·`alg: none`·혼동 토큰을 거부했다. 예외는 셋 다 라이브러리의 기반 예외 밖으로 새지 않았다. 벗어난 것은 둘이다. PyJWT는 헤더 alg가 "Ed25519"인 토큰을 받지 못한다(알고리즘 목록에 "EdDSA"뿐). jwcrypto는 기본 여유가 60초라 30초 전에 만료된 토큰을 받았다.
- 고정하지 않으면: PyJWT는 `algorithms` 없이 `decode`를 부르면 `DecodeError`다. joserfc의 기본 허용은 HS256·RS256·ES256뿐이라 EdDSA·Ed25519 토큰은 고정하지 않으면 거부되고, 허용 목록에 `none`을 넣으면 서명 없는 토큰을 통과시킨다(`SecurityWarning`만 낸다). 혼동 토큰은 셋 다 키의 형식으로 막았다(PyJWT는 PEM을 HMAC 비밀로 쓰지 않고, joserfc·jwcrypto는 HS256에 oct 키를 요구한다).
- 의존성: 세 후보 모두 순수 파이썬이고 네이티브는 `cryptography`(abi3 wheel)와 `cffi`다. 둘 다 이미 락에 있다(`mcp` → `pyjwt[crypto]`). 락 사본에서 `uv add pyjwt[crypto]`는 락을 바꾸지 않았고(`>=2.14.0`), joserfc와 jwcrypto는 각각 자기 하나만 더했다.

## 2026-10-23 결과 — anyio의 두 사실

`anyio_facts.py`를 한 번 돌려 측정 5회차, 측정 아님 0회차였다. 아래는 그 탐침이 찍은 것이다. 셀프 리뷰 표준 축이 둘째 사실이 취소의 종류에 갈린다고 짚어(그 서브에이전트가 `uv run python`으로 손으로 봤다) 갈래를 나눠 지었다.

- 몸통이 태스크 그룹 안에서 던진 `ValueError`는 그룹 밖으로 `ExceptionGroup`(그 안에 `ValueError`)으로 나왔다. 그룹 없이 던진 대조는 `ValueError` 그대로였다.
- 기다리던 받는 쪽에 `send_nowait`로 항목을 넘긴 뒤, 취소하지 않으면 받는 쪽이 그 항목을 받았다(대조). 곧바로 받는 쪽 태스크를 asyncio의 `Task.cancel()`로 취소하면 받는 쪽은 `CancelledError`로 끝났고 흐름에는 항목이 남지 않아 항목이 사라졌다. 받는 쪽을 감싼 anyio `CancelScope`의 `cancel()`로 취소하면 받는 쪽이 그 항목을 받고 끝났다. 그래서 항목을 잃는 것은 날 취소뿐이다. 범위 취소에서 잃지 않는 까닭(깨어날 준비가 된 태스크에는 anyio가 취소를 미룬다)은 재지 않았다.

## 2026-10-23 결과 — pnpm 띄우기

`pnpm_spawn.py`를 한 번 돌려 측정 4회차, 측정 아님 0회차였다. 아래는 그 탐침이 찍은 것이다.

- 이름으로는 뜨지 않는다. uv가 `pnpm`을 이름으로 띄우면 `Failed to spawn: pnpm`(`program not found`)으로 끝났고, `uv run --env-file` 아래의 pytest 안에서 `subprocess.run(["pnpm", "--version"])`도 `FileNotFoundError`(`WinError 2`)였다.
- 경로로는 뜬다. 같은 pytest 안에서 `shutil.which("pnpm")`이 `pnpm.CMD`의 경로를 줬고, 그 경로로 띄운 `pnpm -C web exec node`가 `.env`에서 온 값을 읽었으며, 같은 경로의 `pnpm -C web/apps/admin exec playwright --version`이 `Version 1.63.0`을 냈다. 이 회차가 양성 대조다. "pnpm이 그 환경의 PATH에 없다"는 해석은 같은 프로세스의 `shutil.which`가 찾은 것으로 갈렸다. 그래서 이름으로 뜨지 않는 까닭은 uv가 아니라, 확장자 없는 이름을 `.cmd`로 찾지 않는 실행 파일 찾기다(npm 전역 폴더에는 확장자 없는 `pnpm`이 셸 스크립트로 있고, 그 옆이 `pnpm.cmd`다. `ls`로 손으로 봤다).
- 첫 실행은 넷 모두 측정이 아니었다. `--env-file`에 역슬래시 경로를 주자 uv가 역슬래시가 빠진 경로를 찾았다(`No environment file found`). 슬래시 경로로 바꿔 다시 돌렸고, 판정 기준은 바꾸지 않았다. 둘째 실행도 pytest가 `-q -s`에서 진행 점을 다음 줄 앞에 붙여 탐침이 보고 둘을 놓쳤고(측정 아님 2), 줄 안의 머리를 찾게 고쳐 셋째 실행이 위의 결과다.
- Playwright가 띄우는 손자(`uv run … serve`)까지 값이 닿는지는 재지 않았다.
