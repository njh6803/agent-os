# 05: 대화 — iframe 위젯에서 요청을 보내고, 도는 동안 무엇을 부르는지 보고, 출력을 받아 이어 간다

**What to build:** 최종 사용자가 iframe 위젯에 요청을 적어 보내면, 위젯은 사이트에서 서명 토큰을 postMessage로 받아 최종 사용자 경로로 실행을 시작한다. 요청이 오른쪽의 옅은 상자로 올라가고 그 아래 진행 표시가 돈다. 모델이 도구를 요청하면 이름표가 "orders.lookup 부르는 중"으로 바뀌고, 도구가 끝날 때마다 도구 줄(아이콘, 고정폭 도구 이름, 성공·실패)이 쌓인다. 끝나면 도구 줄이 "도구 3개를 불렀습니다" 한 줄로 접히고 출력이 글자 그대로 선다. 다음 요청은 마지막으로 끝난 실행의 이어 가기다. "새 대화"는 화면과 기억을 비운다.

화면 동작은 MSW로 시험하므로 core의 실시간 중계(02) 없이 지을 수 있다. 02가 병합되기 전의 실제 서버에서는 이름표와 도구 줄이 결말 바로 앞에 한꺼번에 온다.

**병합 뒤에 틈이 있다.** 실패 원인마다의 알림과 거절의 표는 07, 승인 묻기는 08, 저장과 새로 고침과 재접속은 09가 들인다. 그동안 이 티켓은 실패 항목(`failed`)과 끝내지 못함 항목(`unfinished`)을 실패 원인 표의 마지막 행 문구("실행이 실패로 끝났습니다.")와 "다시 보내기"로 그리고, 401과 토큰을 받지 못한 것 밖의 거절은 "요청을 처리하지 못했습니다. 잠시 뒤 다시 보내 주세요."와 "다시 보내기"로 그린다. 승인 묻기 항목(`paused`)이 오면 진행 표시를 걷고 입력창을 막아 둔다. 이 티켓이 쓰는 시험 이름과 주석은 그 틈 동안에도 참이어야 한다.

근거는 `.scratch/web-widget/spec.md`의 "임베드"(iframe 방식, 토큰을 받지 못한 경우), "대화 화면", "요청이 거절될 때"의 401 행, "접근성" 절과 Testing Decisions 1·3이다. 화면은 `.scratch/web-widget/design/`의 `mk-conversation`이고, 글자 수 표시는 `mk-limit`의 마지막 둘(상한 근처, 넘음)이다.

**Blocked by:** 01 (계약 — `calling` 항목과 위젯 클라이언트), 04 (사이트 파일 — 허용 출처와 글자 수 상한)

**Status:** ready-for-agent

### 토큰

- [ ] **위젯은 01의 위젯 클라이언트로 요청하고, 요청마다 새로 받은 토큰을 `Authorization`으로 넘긴다**
- [ ] **iframe 방식의 API 기준 주소는 자기 페이지의 출처이고, 최종 사용자 경로는 그 아래 `/end-user`다.** 위젯 페이지와 같은 출처라 그 요청은 CORS를 지나지 않는다(명세 "임베드" 절의 API의 기준 주소)
- [ ] **iframe의 토큰 요청.** 토큰이 필요할 때 `window.parent`에 `{type: "agent-os/token-request", id}`를 보낸다. `id`는 요청마다 새 무작위 문자열이고 대상 출처는 `"*"`다
- [ ] **받는 메시지는 `event.source`가 `window.parent`이고, `event.origin`이 04가 빌드에 넣은 허용 출처이며, `id`가 기다리는 요청과 같은 `{type: "agent-os/token", id, token}`뿐이다.** 나머지는 버린다. `token`이 문자열이 아니면 토큰을 받지 못한 것이다
- [ ] **토큰을 받지 못하면**(거부, 문자열 아닌 값, 10초 안에 답 없음) 요청을 보내지 않고 위험 알림 "로그인 정보를 받지 못했습니다. 페이지를 새로 고쳐 주세요."를 버튼 없이 보인다. 서버의 401도 같은 화면이다

### 보내기와 진행

- [ ] **Enter는 보내고 Shift+Enter는 줄을 바꾼다. 한글을 조합하는 중(`isComposing`)에 누른 Enter는 보내지 않는다**
- [ ] **보내기 버튼은 입력이 비었거나(앞뒤 공백만 있는 것도), 글자 수 상한을 넘었거나, 실행이 돌거나 멈춰 있거나, 질의가 잘못됐을 때 막힌다.** 상한의 기다림으로 막히는 것은 07이 더한다. 버튼의 크기는 디자인 시스템 버튼 그대로이고 여러 줄 입력창의 아래 끝에 맞춘다
- [ ] **글자 수.** 세는 단위는 코드 포인트이고 상한은 04가 빌드에 넣은 값이다. 상한의 90% 이상이면 입력창 아래에 "19,850 / 20,000"처럼 센 수를, 넘으면 "20,000자를 넘었습니다"를 위험 색으로 보인다. 그 글은 `aria-describedby`로 입력창에 묶는다
- [ ] **진행 표시의 이름표.** 실행마다 부르는 중인 도구의 줄을 든다. `calling`이 오면 그 `tools`를 줄 끝에 붙이고, `progress`가 오면 줄에서 같은 이름의 첫 것을 뺀다. 이름표는 줄의 첫 이름에 " 부르는 중"을 붙인 글이고, 줄이 비면 "요청을 처리하고 있습니다."다. 거부한 도구도 `progress`(실패)로 빠지므로 `decided`는 줄을 바꾸지 않는다. 모델 없이 `ctx.tool()`로 부른 도구는 줄에 들지 않고 그 `progress`는 그냥 지나간다
- [ ] **도구 줄.** `progress`마다 한 줄이 쌓인다. 결말(끝남, 실패, 끝내지 못함)이 오면 "도구 N개를 불렀습니다" 한 줄로 접히고, 그 줄은 `aria-expanded`를 가진 버튼이라 눌러 편다. 도구 줄이 없는 실행에는 그 줄도 없다
- [ ] **출력.** `finished`의 `output`을 글자 그대로, 줄바꿈을 지키고 긴 낱말은 줄 끝에서 꺾어 그린다. 마크다운으로 그리지 않고, HTML 조각은 글자로 보인다(ADR 0024)

### 이어 가기와 새 대화

- [ ] **다음 요청.** 이어 갈 마지막으로 끝난 실행이 있으면 그 실행의 이어 가기이고, 없으면 시작이다. `finished`가 오면 이어 갈 실행이 그 실행이 된다
- [ ] **"다시 보내기"**는 같은 요청 글을 같은 규칙으로 보내고 새 교환으로 덧붙인다. 실패한 교환은 그대로 남는다
- [ ] **"새 대화".** 응답이 결말 전이면 막히고 쉬고 있을 때는 열린다. 누르면 묻지 않고 화면과 기억을 비우고 열린 스트림을 끊는다(저장을 비우는 것은 09가 더한다)
- [ ] **스크롤.** 새 내용이 오면 최종 사용자가 대화의 끝을 보고 있었을 때만 끝으로 내린다

### 접근성

- [ ] **포커스 차례**는 위쪽 띠의 "새 대화" → 대화 안의 버튼 → 입력창 → 보내기다. 포커스 표시는 디자인 시스템의 것이다
- [ ] **숨긴 `role="status"` 영역 하나가 새 도구 줄("orders.lookup 성공", "orders.lookup 실패")과 끝난 출력을 차례로 한 번씩 읽는다.** 진행 표시의 "부르는 중"은 읽지 않는다. 보이는 대화 목록 자체에는 `aria-live`나 `role="log"`를 달지 않는다(둘 다 읽히면 같은 줄이 두 번 들린다). 승인 묻기의 읽기는 08이 더한다
- [ ] **움직임 줄이기 설정에서는 진행 표시의 도는 모양이 멈춘다.** 포인터 대상은 24px 이상이다

### 시험

- [ ] **화면 동작 테스트(`widget-pages`, MSW).** 최종 사용자 경로와 스트림 프레임(`id`와 `data`)을 생성 타입으로 흉내 내고 처리하지 않은 요청은 실패다(선례는 관리 화면의 페이지 시험과 `apps/admin/testing/`). 토큰 요청과 거르기(부모가 아님, 허용 밖 출처, 다른 `id`, 문자열 아닌 토큰, 10초), 이름표의 규칙(`calling`, `progress`, 거부, 직접 호출), 접힘과 `aria-expanded`(스토리 6), 이어 가기와 시작의 갈림(스토리 9), 새 대화가 막히고 열리는 때와 스트림 끊기(스토리 11), 글자 수의 90%와 넘음과 `aria-describedby`(스토리 36), Enter와 Shift+Enter와 `isComposing`, 읽기 영역의 차례와 대화 목록에 살아 있는 영역 속성이 없는 것(스토리 38), 포커스 차례, 틈 동안의 실패·거절 문구
- [ ] **위젯 스토리(`widget-storybook`).** 대화 organism을 폭 320px과 400px에서 그려 분류 판정, 접근성, 사진을 본다. 대화의 스토리 시험이 스크롤을 본다(끝을 보고 있을 때 새 내용이 오면 끝으로 내려가고, 위로 올려 둔 동안에는 머문다). jsdom은 레이아웃을 하지 않아 화면 동작 테스트에서는 재지 못한다
