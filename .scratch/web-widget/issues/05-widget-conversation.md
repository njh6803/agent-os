# 05: 대화 — iframe 위젯에서 요청을 보내고, 도는 동안 무엇을 부르는지 보고, 출력을 받아 이어 간다

**What to build:** 최종 사용자가 iframe 위젯에 요청을 적어 보내면, 위젯은 사이트에서 서명 토큰을 postMessage로 받아 최종 사용자 경로로 실행을 시작한다. 요청이 오른쪽의 옅은 상자로 올라가고 그 아래 진행 표시가 돈다. 모델이 도구를 요청하면 이름표가 "orders.lookup 부르는 중"으로 바뀌고, 도구가 끝날 때마다 도구 줄(아이콘, 고정폭 도구 이름, 성공·실패)이 쌓인다. 끝나면 도구 줄이 "도구 3개를 불렀습니다" 한 줄로 접히고 출력이 글자 그대로 선다. 다음 요청은 마지막으로 끝난 실행의 이어 가기다. "새 대화"는 화면과 기억을 비운다.

화면 동작은 MSW로 시험하므로 core의 실시간 중계(02) 없이 지을 수 있다. 02가 병합되기 전의 실제 서버에서는 이름표와 도구 줄이 결말 바로 앞에 한꺼번에 온다.

**병합 뒤에 틈이 있다.** 실패 원인마다의 알림과 거절의 표는 07, 승인 묻기는 08, 저장과 새로 고침과 재접속은 09가 들인다. 그동안 이 티켓은 실패 항목(`failed`)과 끝내지 못함 항목(`unfinished`)을 실패 원인 표의 마지막 행 문구("실행이 실패로 끝났습니다.")와 "다시 보내기"로 그리고, 401과 토큰을 받지 못한 것 밖의 거절은 "요청을 처리하지 못했습니다. 잠시 뒤 다시 보내 주세요."와 "다시 보내기"로 그린다. 승인 묻기 항목(`paused`)이 오면 진행 표시를 걷고 입력창을 막아 둔다. 이 티켓이 쓰는 시험 이름과 주석은 그 틈 동안에도 참이어야 한다.

근거는 `.scratch/web-widget/spec.md`의 "임베드"(iframe 방식, 토큰을 받지 못한 경우), "대화 화면", "요청이 거절될 때"의 401 행, "접근성" 절과 Testing Decisions 1·3이다. 화면은 `.scratch/web-widget/design/`의 `mk-conversation`이고, 글자 수 표시는 `mk-limit`의 마지막 둘(상한 근처, 넘음)이다.

**Blocked by:** 01 (계약 — `calling` 항목과 위젯 클라이언트), 04 (사이트 파일 — 허용 출처와 글자 수 상한)

**04가 넘기는 값.** 위젯 빌드는 사이트 파일에서 끌어낸 두 값을 `next.config.ts`의 `env`로 번들에 싣는다. 합친 허용 출처는 `AGENT_OS_WIDGET_ORIGINS`(출처를 공백 하나로 이은 글. 빈 글이면 빈 목록이고 postMessage를 모두 버린다), 가장 작은 요청 글자 수 상한은 `AGENT_OS_WIDGET_REQUEST_CHARS`(십진수 글)다. 이름은 `web/apps/widget/tools/site-file.ts`의 상수 `WIDGET_ORIGINS_ENV`·`WIDGET_REQUEST_CHARS_ENV`다. 번들에서는 `process.env.AGENT_OS_WIDGET_ORIGINS`처럼 점으로 읽는다. 설치된 Next 16.3.6의 `next-config-js/env.md`는 `env`의 값을 `process.env.이름`의 자리에 빌드 때 바꿔 넣고, `process.env`를 구조 분해하면 동작하지 않는다고 적는다. `guides/environment-variables.md`는 변수로 고른 이름(`process.env[varName]`)과 `process.env`를 다른 이름에 담아 읽는 것(`const env = process.env`)을 바꿔 넣지 않는다고 적는데, 그 예는 `NEXT_PUBLIC_` 변수다. `env`의 값에도 그대로 들어맞는다는 것은 미루어 본 것이다. 글자로 쓴 대괄호(`process.env["…"]`)는 두 문서에 없다.

**Status:** done

### 토큰

- [x] **위젯은 01의 위젯 클라이언트로 요청하고, 요청마다 새로 받은 토큰을 `Authorization`으로 넘긴다**
- [x] **iframe 방식의 API 기준 주소는 자기 페이지의 출처이고, 최종 사용자 경로는 그 아래 `/end-user`다.** 위젯 페이지와 같은 출처라 그 요청은 CORS를 지나지 않는다(명세 "임베드" 절의 API의 기준 주소)
- [x] **iframe의 토큰 요청.** 토큰이 필요할 때 `window.parent`에 `{type: "agent-os/token-request", id}`를 보낸다. `id`는 요청마다 새 무작위 문자열이고 대상 출처는 `"*"`다
- [x] **받는 메시지는 `event.source`가 `window.parent`이고, `event.origin`이 04가 빌드에 넣은 허용 출처이며, `id`가 기다리는 요청과 같은 `{type: "agent-os/token", id, token}`뿐이다.** 나머지는 버린다. `token`이 문자열이 아니면 토큰을 받지 못한 것이다
- [x] **토큰을 받지 못하면**(거부, 문자열 아닌 값, 10초 안에 답 없음) 요청을 보내지 않고 위험 알림 "로그인 정보를 받지 못했습니다. 페이지를 새로 고쳐 주세요."를 버튼 없이 보인다. 서버의 401도 같은 화면이다

### 보내기와 진행

- [x] **Enter는 보내고 Shift+Enter는 줄을 바꾼다. 한글을 조합하는 중(`isComposing`)에 누른 Enter는 보내지 않는다**
- [x] **보내기 버튼은 입력이 비었거나(앞뒤 공백만 있는 것도), 글자 수 상한을 넘었거나, 실행이 돌거나 멈춰 있거나, 질의가 잘못됐을 때 막힌다.** 상한의 기다림으로 막히는 것은 07이 더한다. 버튼의 크기는 디자인 시스템 버튼 그대로이고 여러 줄 입력창의 아래 끝에 맞춘다
- [x] **글자 수.** 세는 단위는 코드 포인트이고 상한은 04가 빌드에 넣은 값이다. 상한의 90% 이상이면 입력창 아래에 "19,850 / 20,000"처럼 센 수를, 넘으면 "20,000자를 넘었습니다"를 위험 색으로 보인다. 그 글은 `aria-describedby`로 입력창에 묶는다
- [x] **진행 표시의 이름표.** 실행마다 부르는 중인 도구의 줄을 든다. `calling`이 오면 그 `tools`를 줄 끝에 붙이고, `progress`가 오면 줄에서 같은 이름의 첫 것을 뺀다. 이름표는 줄의 첫 이름에 " 부르는 중"을 붙인 글이고, 줄이 비면 "요청을 처리하고 있습니다."다. 거부한 도구도 `progress`(실패)로 빠지므로 `decided`는 줄을 바꾸지 않는다. 모델 없이 `ctx.tool()`로 부른 도구는 줄에 들지 않고 그 `progress`는 그냥 지나간다
- [x] **도구 줄.** `progress`마다 한 줄이 쌓인다. 결말(끝남, 실패, 끝내지 못함)이 오면 "도구 N개를 불렀습니다" 한 줄로 접히고, 그 줄은 `aria-expanded`를 가진 버튼이라 눌러 편다. 도구 줄이 없는 실행에는 그 줄도 없다
- [x] **출력.** `finished`의 `output`을 글자 그대로, 줄바꿈을 지키고 긴 낱말은 줄 끝에서 꺾어 그린다. 마크다운으로 그리지 않고, HTML 조각은 글자로 보인다(ADR 0024)

### 이 티켓이 정한 것

근거와 고른 까닭은 일지 2026-10-24-09이다.

1. **대화의 스크롤 자리는 포커스를 받는 영역(`role="region"`, 이름 "대화")이다.** 도구 줄이 없는 교환만 있으면 대화 안에 포커스 받는 것이 없어 키보드로 스크롤할 길이 없고, 위젯 스토리의 axe(`scrollable-region-focusable`)가 잡았다. 그래서 포커스 차례는 "새 대화" → 대화 영역 → 대화 안의 버튼 → 입력창 → 보내기다. 명세 "접근성"의 차례에 영역 하나가 끼었다. 이름은 영역이 들고 그 안의 목록(`ol`)은 이름이 없다.
2. **시작 항목 뒤에 결말 없이 끝난 스트림도 틈 동안 "요청을 처리하지 못했습니다."와 "다시 보내기"다.** 명세는 그것을 끊김으로 보고 다시 잇는다(재접속). 09가 그 길로 바꾼다.
3. **"새 대화"가 스트림을 끊는 것은 위젯이 낸 요청의 `signal`로 본다.** MSW 3.0.0에서 끊김은 읽는 쪽에만 닿아 핸들러에서 보이지 않는다(`.scratch/web-admin/probes/msw_abort.mjs`의 2026-09-30 결과: 핸들러의 `request.signal`은 끊기지 않았고 스트림의 `cancel`은 불리지 않았다). 시험은 전역 fetch를 엿봐 받은 `Request`의 `signal`이 끊겼는지 본다.
4. **빌드 값은 `lib/build.ts` 한 자리에서 `process.env.이름`의 점 표기로 읽는다.** 이름이 사이트 파일 모듈의 상수와 같은지는 `lib/build.test.ts`가 그 파일의 글자로 본다. 페이지 시험은 빌드를 거치지 않아 `testing/setup.ts`가 같은 이름의 환경 변수를 둔다.
5. **보내기는 빈 입력에서 막힌다.** 03의 첫 화면 시험이 빈 입력의 보내기를 열린 것으로 단언하던 것을 막힌 것으로 고쳤다.
6. **토큰 요청의 `id`를 만들지 못하면 토큰을 받지 못한 것이다.** `crypto.randomUUID`는 보안 맥락(https, localhost)에만 있어, 그 밖에서 던지면 요청을 보내지 않고 "로그인 정보를 받지 못했습니다."를 보인다. 던지게 두면 교환이 결말 없이 돈다(셀프 리뷰가 잡았다).
