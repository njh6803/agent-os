# 위젯: 최종 사용자가 사이트 안의 창에서 에이전트에게 요청하고, 도는 동안 무엇을 부르는지 보고, 스스로 승인한다

Status: ready-for-agent

슬라이스 4(`web-widget`). 근거는 이 기능의 결정인 `docs/adr/0024`(위젯은 한 앱 폴더에서 iframe 페이지와 페이지 안 번들을 내고 nginx 뒤에 선다)와 최종 사용자 면의 ADR들(`0022` 대화, `0023` 최종 사용자 채널, `0026` 디자인 시스템, `0031` 실패 원인), `.scratch/plan.md`의 web-widget 행, 화면 디자인(`.scratch/web-widget/design/`의 README, 시작 프롬프트 `screens-prompt.md`, 캔버스 메모), 화면 일지(`docs/journal/2026-10-23-30-web-widget-screens.md`), 앞 기능의 명세 둘(`.scratch/end-user-channel/spec.md`, `.scratch/end-user-continuation/spec.md`)이다. 이 명세가 "코드를 읽었다"고 적은 것은 `db92d68a`의 코드다.

이 명세는 설계 인터뷰(2026-10-03, ADR 0024)와 다른 세션에서 썼다. 인터뷰의 대화가 없으므로 위 문서들이 맥락을 대신했고, 그것으로 모자란 결정은 사용자에게 물었다. 용어는 `CONTEXT.md`를 따른다. 이 명세가 "상한"을 더했다. 무엇을 세는지(종류)와 누구 몫으로 세는지(범위)를 가르는 말이다.

**넘겨받은 것은 서른여덟이다.** `plan.md` 행이 이 기능에 넘긴 것이 스물이다. 테마와 모드를 넘기는 길, 글꼴 파일을 위젯 출처에서 `Access-Control-Allow-Origin`과 함께 내는 길, 고유한 family 이름으로 글꼴을 등록하는 코드, CSP가 글꼴을 막을 때의 임베드 안내, 상속 속성을 실제 커스텀 요소에서 재는 것, 폭마다의 organisms 스토리와 사진, 위젯의 스토리 테스트 프로젝트와 그 CSS가 서는지, 사진 비교를 나눠 쓸 길, 테마 값의 검사, `IconName` 밖의 아이콘, `data-density`와 그 시험, 글꼴 양을 다시 재는 것, `@source`, 실패 원인마다의 문구와 권할 일, 404에 곧바로 지울지, 500이 거듭될 때 새 대화의 길, 요청 글자 수 상한을 빌드가 읽는 것, nginx의 본문 상한, 임베드 안내의 내용, fetch로 읽는 스트림과 `Last-Event-ID`다. 화면 디자인 README의 제안과 탐색용 가정이 아홉이다. 409·500 알림의 다시 보내기, 연결 수 상한 띠의 문구, 첫 화면의 할 수 있는 일 한 줄, 진행 표시의 지금 부르는 도구, 알림 버튼의 자리, 거절마다 요청이 남는 자리, 기다리는 초의 읽기와 `mk-a11y` 메모, 보내기 버튼의 높이, 예시의 이름·도구·높이다. 셀프 리뷰와 PR 직전 리뷰가 더한 어긋남이 일곱이다. 알림의 제목, 입력창 위의 띠, 404와 409의 범위, 결정의 거절, 상한의 종류와 범위, 인자의 글자 꼴, 끝내지 못함의 문구다. 그리고 일지 2026-10-23-30의 "다음"이 옛 `docs/web-widget-spec` 브랜치 하나를, ADR 0024가 계약 티켓에 넘긴 위젯 경로의 이름 하나를 넘겼다. plan.md 행의 "진행 표시의 지금 하는 일"은 README의 진행 표시 항목과 같은 것이라 한 번만 셌다. ADR 0024가 티켓에 넘긴 셋(시작 래퍼, vite 판, TOML 파서)은 그대로 티켓에 둔다.

**여섯은 사용자가 이 명세를 쓰며 골랐다**(일지 2026-10-23-40). core가 모델·도구 호출의 이벤트를 실행 도중에 흘리고 최종 사용자 항목에 "부르기 시작함"을 더한다(추천과 달랐다. 처음 물은 설명의 기술 조건 둘이 틀려 바로잡아 다시 물었다), 서버가 429에 상한의 종류를 코드로 준다(추천과 달랐다), 입력창 위의 띠는 위젯 앱의 자기 부품이다, 이음매 다섯에 실제 모델 e2e를 하나 더한다(추천과 달랐다), 사진 비교 도우미를 디자인 시스템 패키지의 하위 경로로 내보낸다(셋째 답의 설명과 글자로 부딪혀 결정을 승인받을 때 따로 물었다), 그리고 명세 검토 뒤에 그 실제 모델 e2e를 원칙 I의 판정 명령에서 떼어 따로 치는 명령으로 둔다. 여섯 모두 추천을 맨 앞에 둔 선택 화면에서 물었다. 첫째는 core의 구조를 지금 시제로 정해야 해서 이 명세가 시제품으로 쟀고, **ADR 0039**가 그 구조와 거부한 안을 든다. 첫째와 둘째의 계약 몫은 **ADR 0023의 이력 하나(2026-10-23)**와 ADR 0010 본문의 포인터다. 404를 한 번 더 시도하는 것과 위젯 경로의 이름은 ADR 0024의 본문을 바꾸므로 **ADR 0024의 이력 하나(2026-10-23)**로 올린다. 넷째와 여섯째(실제 모델 e2e와 그 명령)는 LLM 테스트 규약(`docs/constitution/operations.md`)을 바꾸므로 **ADR 0024의 이력 하나(2026-10-23)**를 더 둔다. 다섯째는 ADR을 바꾸지 않는다. 모두 사용자가 승인한다.

**쉰아홉은 명세가 ADR과 화면을 구현이 닿는 자리로 옮기다 스스로 정했고, 각 절에 "(명세가 정했다)"로 표시한다.** 명세 검토를 반영하며 여덟이, PR 직전 리뷰를 반영하며 하나(사유의 상한)가 늘었고, 06 구현 중에 nginx를 범위 밖으로 옮기며 둘(nginx의 틀, 로컬의 nginx를 찾는 길)이 빠졌다(일지 2026-10-24-10). 계약 둘(`calling` 항목의 모양, 429의 `LimitEnvelope`), api-client 둘(토큰을 요청마다 넘김, `id`와 keepalive를 내는 읽기), 배치와 빌드 여덟(번들과 글꼴의 경로, 사이트 파일의 환경 변수, 가장 작은 글자 수 상한, 사이트 파일을 읽지 못할 때, 허용 출처 표기의 규칙, 사이트 파일의 판, 아이콘, vitest 프로젝트의 이름), 임베드 열하나(번들의 꼴, 속성 다섯, 토큰 함수, postMessage의 모양, 10초, 잘못 준 속성, 크기, open shadow root, API의 기준 주소, 같은 에이전트 둘, 임베드 안내), 글꼴 둘(`*`를 Next가 다는 것, 예산 없음), 대화 화면 여덟(첫 화면, 진행 표시 이름표의 규칙, Enter, 보내기 버튼의 크기, 90%, 새 대화, 다시 보내기의 새 교환, 스크롤), 저장 여섯(키, 도는 교환, 묶음 견주기, 용량, 저장의 판, 저장하지 않는 것), 승인 셋(인자의 글자 꼴, 사유를 다듬는 글자, 사유의 상한), 실패 둘(원인의 문구 표, 끝내지 못함), 거절의 표 하나, 재접속 셋(45초, 간격, 끊김을 마지막 항목으로 가르는 것), 상한 둘(문구, 기다릴 시간), 띠 하나(하나만 서는 것과 그 차례), 접근성 둘(메모를 받아들임, "부르는 중"을 읽지 않음), 프록시 하나(본문 상한의 셈), 테스트 셋(`e2e-widget` 잡, 두 언어가 같은 사이트 파일을 읽는 것, 실제 모델 e2e를 파이썬 시험이 감싸는 것과 그 기준), 티켓의 차례 하나(계약 다음 core), 옛 브랜치 하나다. 표시가 없는 것은 ADR이나 기존 규칙, 사용자의 답에서 나왔다. 결정이 더 필요해지면 멈추고 ADR의 이력을 제안한다.

## Problem Statement

사이트(남의 웹 서비스)에 로그인한 최종 사용자는 Agent OS의 에이전트를 쓸 길이 없다. 최종 사용자 경로(시작, 이어 가기, 결정, 구독)와 그 스트림의 항목, 실패 원인, 상한은 서버에 섰지만(ADR 0022·0023·0031), 그것을 부르는 화면이 없다. 사이트 개발자도 자기 페이지에 넣을 것이 없다. 화면 여덟은 그려졌고(`.scratch/web-widget/design/`), 그 화면은 서버가 지금 주지 않는 것을 둘 그렸다.

- **실행 도중의 진행.** 화면은 도구 줄이 실행 도중 쌓이고 진행 표시가 "<도구 이름> 부르는 중"을 보이는 모습이다. 그러나 지금 core는 모델·도구 호출 안에서 생긴 이벤트를 에이전트가 다음 이벤트를 낼 때까지 모은다. 루프 전체가 `ctx.llm()` 한 번인 에이전트(저장소의 계산 에이전트)는 도구 줄이 결말 바로 앞에 한꺼번에 온다. 지금 부르는 도구도 알 수 없다. 도구 항목은 호출이 끝난 뒤에만 오기 때문이다. 이 명세가 시제품으로 쟀다(`.scratch/web-widget/probes/` README의 2026-10-23 결과).
- **상한의 종류.** 화면은 동시 실행, 시간당 실행, 연결 수를 갈라 문구를 다르게 그렸다. 그러나 429 봉투는 어느 상한인지를 사람이 읽는 글(`message`)로만 말한다.

그 밖에 화면이 계약보다 좁게 그린 자리(404·409의 범위, 결정의 거절, 끝내지 못함의 원인)와 디자인 시스템과 어긋나는 자리(알림의 제목, 입력창 위의 띠)가 남아 있다(디자인 README의 어긋남 목록).

## Solution

`web/apps/widget`이 같은 React 컴포넌트로 iframe 페이지와 사이트 페이지 안의 커스텀 요소 번들을 내고, nginx 뒤의 한 출처에서 서빙된다(ADR 0024). 최종 사용자가 보는 모습은 이렇다.

- 사이트가 준 자리에 위젯 창이 선다. 위쪽 띠에 에이전트 이름과 "새 대화" 글자 버튼이 있고, 아래에 여러 줄 입력창과 보내기 버튼이 있다. 첫 화면에는 사이트가 정한 할 수 있는 일 한 줄(있을 때)과 "아래에 요청을 적어 보내 주세요."가 보인다.
- 요청을 보내면 요청이 오른쪽의 옅은 상자로 올라가고, 그 아래 진행 표시가 돈다. 모델이 도구를 요청하는 순간 진행 표시의 이름표가 "orders.lookup 부르는 중"으로 바뀌고, 도구가 끝날 때마다 도구 줄(아이콘, 고정폭 도구 이름, 성공·실패)이 한 줄씩 쌓인다. 끝나면 도구 줄이 "도구 3개를 불렀습니다" 한 줄로 접히고 출력이 글자 그대로 선다.
- 에이전트가 승인을 물으면 대화 안에 테두리 카드가 서서 도구 이름과 인자를 고정폭 원문으로 보인다. 최종 사용자가 거부 사유를 적어 거부하거나 승인한다. 그동안 입력창은 막히고 그 위 띠가 "승인이나 거부를 먼저 골라 주세요."를 보인다.
- 실행이 실패하면 출력이 올 자리에 알림이 서서, 실패 원인마다 정한 문구와 실행 식별자, 다음에 할 일 버튼("다시 보내기", 원인에 따라 "새 대화")을 보인다. 요청을 보낼 때 거절되면 상태 코드마다 정한 길(알림, 한 번 더 시도한 뒤 새 대화, 입력창 위의 띠)을 간다.
- 연결이 끊기면 받은 것은 그대로 두고 입력창 위 띠가 "연결이 끊겨 다시 잇고 있습니다."를 보이며 같은 실행에 다시 붙는다. 너무 자주 보내 상한에 걸리면 띠가 상한의 종류에 맞는 문구와 다시 보낼 수 있기까지의 시간을 보이고 보내기를 막는다.
- 같은 탭에서 새로 고치면 대화가 이어지고, 돌던 실행이나 멈춘 실행에는 다시 붙는다. 사이트 계정이 바뀌면 앞 사람의 대화는 보이지 않는다.

서버 쪽에서는 둘이 바뀐다. core가 모델·도구 호출의 이벤트를 기록하는 자리에서 곧바로 흘리고(ADR 0039), 최종 사용자 스트림에 "부르기 시작함" 항목이, 429 봉투에 상한의 종류가 더해진다(ADR 0023 이력). 운영자 `/runs`와 CLI도 실행 도중에 이벤트를 받게 된다.

## User Stories

대화와 진행

1. 최종 사용자로서, 사이트 페이지 안의 위젯에 요청을 적어 보내고 싶다. 그래야 사이트를 떠나지 않고 에이전트에게 일을 맡길 수 있다.
2. 최종 사용자로서, 첫 화면에서 이 에이전트로 무엇을 할 수 있는지 한 줄로 보고 싶다. 그래야 무엇을 물을지 안다.
3. 최종 사용자로서, 요청을 보낸 직후 위젯이 일하고 있다는 표시를 보고 싶다. 그래야 다시 보내지 않고 기다린다.
4. 최종 사용자로서, 에이전트가 도구를 부르기 시작하는 순간 그 도구 이름을 보고 싶다. 그래야 오래 걸리는 까닭을 안다.
5. 최종 사용자로서, 도구가 끝날 때마다 그 도구가 성공했는지 실패했는지 한 줄로 보고 싶다. 그래야 결과를 믿을지 판단한다.
6. 최종 사용자로서, 실행이 끝나면 도구 줄이 한 줄 요약으로 접히고 눌러 다시 펼 수 있기를 바란다. 그래야 대화가 길어지지 않으면서도 무엇을 불렀는지 다시 볼 수 있다.
7. 최종 사용자로서, 출력을 줄바꿈이 지켜진 글자 그대로 보고 싶다. 그래야 주문 번호 같은 값을 그대로 옮길 수 있다.
8. 최종 사용자로서, 출력에 HTML 조각이 들어 있어도 그것이 실행되지 않기를 바란다. 그래야 내 사이트 계정이 안전하다.
9. 최종 사용자로서, 앞선 요청과 출력을 에이전트가 기억한 채로 다음 요청을 이어 보내고 싶다. 그래야 "그럼 반품은요?"처럼 짧게 물을 수 있다.
10. 최종 사용자로서, 대화가 아무리 길어도 새 대화를 하라는 권유를 받지 않고 이어 가고 싶다. 그래야 맥락을 잃지 않는다.
11. 최종 사용자로서, "새 대화"를 눌러 화면과 기억을 비우고 처음부터 시작하고 싶다. 그래야 다른 일을 새로 맡길 수 있다.
12. 최종 사용자로서, 같은 탭에서 페이지를 새로 고쳐도 대화가 남아 있기를 바란다. 그래야 실수로 새로 고쳐도 다시 묻지 않는다.
13. 최종 사용자로서, 새로 고친 뒤 돌고 있던 실행의 진행과 출력을 이어 받고 싶다. 그래야 기다린 일을 잃지 않는다.
14. 최종 사용자로서, 새 탭에서 사이트를 열면 새 대화로 시작하기를 바란다. 그래야 남이 같은 기기에서 내 대화를 보지 않는다.
15. 최종 사용자로서, 같은 탭에서 사이트 계정이 바뀌면 앞 사람의 대화가 보이지 않기를 바란다. 그래야 공용 기기에서도 안전하다.

승인

16. 최종 사용자로서, 에이전트가 승인을 물을 때 어떤 도구를 어떤 인자로 부르려는지 고치거나 줄이지 않은 원문으로 보고 싶다. 그래야 무엇을 승인하는지 안다.
17. 최종 사용자로서, 거부할 때 사유를 적고 싶다. 그래야 에이전트가 다른 길을 찾는다.
18. 최종 사용자로서, 사유를 비운 채로는 거부 버튼이 눌리지 않기를 바란다. 그래야 빈 사유로 거부하는 실수를 하지 않는다.
19. 최종 사용자로서, 결정한 뒤 카드의 버튼이 사라지고 "승인했습니다" 또는 "거부했습니다: <사유>" 한 줄이 남기를 바란다. 그래야 내가 무엇을 골랐는지 기록이 남는다.
20. 최종 사용자로서, 결정을 기다리는 동안 입력창이 막히고 왜 막혔는지 안내를 보고 싶다. 그래야 새 요청이 어디로 가는지 헷갈리지 않는다.
21. 최종 사용자로서, 결정을 보냈는데 거절되면 카드가 다시 결정을 받을 수 있는 상태로 돌아오거나, 결정할 수 없게 된 까닭을 보고 싶다. 그래야 승인이 사라졌는지 걱정하지 않는다.
22. 최종 사용자로서, 다른 탭에서 이미 결정한 실행이면 이 탭의 카드도 그 결과를 따라가기를 바란다. 그래야 같은 결정을 두 번 하지 않는다.

실패와 거절

23. 최종 사용자로서, 실행이 실패하면 왜 실패했는지 내가 이해할 말로 보고 싶다. 그래야 다시 보낼지 바꿔 보낼지 정한다.
24. 최종 사용자로서, 실패한 요청을 버튼 하나로 같은 대화에 다시 보내고 싶다. 그래야 다시 적지 않는다.
25. 최종 사용자로서, 앞선 대화를 정리하다 실패했거나 시간이 다 된 실패에서는 새 대화로 시작하는 버튼도 보고 싶다. 그래야 같은 실패를 되풀이하지 않는다.
26. 최종 사용자로서, 실패 알림에서 실행 식별자를 보고 싶다. 그래야 사이트나 운영자에게 알릴 때 그것을 건넨다.
27. 최종 사용자로서, 로그인 정보가 넘어오지 않아 거절되면 페이지를 새로 고치라는 안내를 보고 싶다. 그래야 무엇을 해야 하는지 안다.
28. 최종 사용자로서, 이어 가던 대화를 서버가 찾지 못하면 위젯이 알아서 새 대화로 같은 요청을 보내고 그렇게 했다고 알려 주기를 바란다. 그래야 요청을 잃지 않는다.
29. 최종 사용자로서, 서버가 잠깐 읽기에 실패한 것뿐이면 대화가 지워지지 않기를 바란다. 그래야 일시적인 고장에 대화를 잃지 않는다.
30. 최종 사용자로서, 서버가 거듭 요청을 처리하지 못하면 새 대화를 고를 길을 보고 싶다. 그래야 고쳐지지 않는 고장에 갇히지 않는다.
31. 최종 사용자로서, 서버가 다시 시작해 실행이 사라졌으면 원인을 단정하지 않는 안내와 다시 보내기를 보고 싶다. 그래야 틀린 설명을 믿지 않는다.

연결과 상한

32. 최종 사용자로서, 연결이 끊겨도 이미 받은 진행과 출력이 그대로 남기를 바란다. 그래야 처음부터 다시 보지 않는다.
33. 최종 사용자로서, 연결이 끊기면 위젯이 스스로 다시 잇고 그동안 그 사실을 한 줄로 보고 싶다. 그래야 위젯이 멈췄는지 기다리는 중인지 안다.
34. 최종 사용자로서, 너무 자주 보내 거절되면 어떤 상한에 걸렸고 언제 다시 보낼 수 있는지 보고 싶다. 그래야 기다릴 시간을 안다.
35. 최종 사용자로서, 상한에 걸린 요청이 입력창에 남기를 바란다. 그래야 기다린 뒤 다시 적지 않는다.
36. 최종 사용자로서, 요청이 글자 수 상한에 가까워지면 남은 글자 수를 보고, 넘으면 보내기 전에 막히기를 바란다. 그래야 보낸 뒤 거절되지 않는다.

접근성과 모양

37. 키보드 사용자로서, 위쪽 띠부터 대화 안의 버튼, 입력창, 보내기까지 차례대로 옮겨 다니고 포커스가 늘 보이기를 바란다. 그래야 마우스 없이 쓴다.
38. 화면 읽기 프로그램 사용자로서, 새 도구 줄, 끝난 출력, 승인 묻기가 차례로 한 번씩 읽히기를 바란다. 그래야 화면을 보지 않고도 따라간다.
39. 화면 읽기 프로그램 사용자로서, 기다리는 초가 매초 읽히지 않고 다시 보낼 수 있게 될 때 한 번 더 읽히기를 바란다. 그래야 소음에 묻히지 않는다.
40. 최종 사용자로서, 위젯이 사이트가 고른 테마와 라이트·다크 모드로 그려지기를 바란다. 그래야 사이트와 어울린다.
41. 최종 사용자로서, 좁은 자리(320px)에서도 긴 인자와 긴 출력이 가로 스크롤 없이 다시 흐르기를 바란다. 그래야 모바일에서도 읽는다.
42. 최종 사용자로서, 움직임 줄이기 설정을 켰으면 도는 표시가 멈추기를 바란다. 그래야 어지럽지 않다.

사이트 개발자

43. 사이트 개발자로서, script 한 줄과 커스텀 요소 하나, 또는 iframe 태그 하나로 위젯을 넣고 싶다. 그래야 내 프런트엔드 스택과 무관하게 붙인다.
44. 사이트 개발자로서, 내 백엔드가 서명한 짧은 토큰을 함수(페이지 안 방식)나 postMessage(iframe 방식)로 요청마다 넘기고 싶다. 그래야 비밀이 브라우저에 남지 않는다.
45. 사이트 개발자로서, 에이전트, 위쪽 띠의 이름, 할 수 있는 일 한 줄, 테마, 모드를 속성이나 주소의 질의로 정하고 싶다. 그래야 내 서비스에 맞춘다.
46. 사이트 개발자로서, 속성을 잘못 주면 위젯 안의 알림과 브라우저 콘솔에서 무엇이 틀렸는지 보고 싶다. 그래야 연동을 빨리 고친다.
47. 사이트 개발자로서, 내 페이지의 CSS가 위젯을 깨지 않고 위젯의 CSS가 내 페이지로 새지 않기를 바란다. 그래야 서로의 화면이 안전하다.
48. 사이트 개발자로서, 내 페이지의 글자 크기 설정(`html { font-size }`)과 무관하게 위젯 크기가 같기를 바란다. 그래야 레이아웃을 예측한다.
49. 사이트 개발자로서, 클레임, 토큰 수명, 키, `sub`의 의무, 허용 출처, postMessage 규약을 적은 임베드 안내를 읽고 싶다. 그래야 서버 코드를 읽지 않고 연동한다.
50. 사이트 개발자로서, 허용 출처가 아닌 페이지가 iframe 위젯을 품거나 토큰을 가로채지 못하기를 바란다. 그래야 클릭을 가로채는 공격을 막는다.

운영자와 플러그인 작성자

51. 운영자로서, 사이트 파일 하나로 서버(CORS, 상한)와 위젯 빌드(frame-ancestors, 글자 수 상한)가 같은 허용 출처와 값을 쓰기를 바란다. 그래야 두 곳을 따로 맞추지 않는다.
52. 운영자로서, `deploy/nginx/`의 설정으로 TLS를 끝내고 최종 사용자 접두사와 위젯 경로만 바깥에 내보내고 싶다. 그래야 운영자 토큰과 원문 스트림이 원격에 닿지 않는다. (이 기능의 범위에서 뺐다. 아래 "nginx와 배포"와 Out of Scope)
53. 운영자로서, `/runs` 스트림에서도 모델·도구 호출의 이벤트를 실행 도중에 받고 싶다. 그래야 오래 걸리는 실행이 어디에 있는지 본다.
54. 운영자로서, 트레이스 쓰기가 실패하면 그 뒤의 도구가 불리지 않기를 바란다. 그래야 기록에 없는 부작용이 생기지 않는다.
55. 플러그인 작성자로서, 에이전트 코드를 바꾸지 않아도 `ctx.llm()`과 `ctx.tool()`의 이벤트가 실행 도중에 흐르기를 바란다. 그래야 모든 에이전트가 위젯의 진행 표시를 얻는다.
56. 플러그인 작성자로서, 함께 부른 도구(`asyncio.gather`)가 지금처럼 겹쳐 돌기를 바란다. 그래야 실시간 중계가 내 에이전트를 느리게 하지 않는다.
57. 플러그인 작성자로서, 실행이 버려질 때 내 정리 코드가 어떻게 끊기는지 sdk 문서에서 읽고 싶다. 그래야 정리 코드를 올바르게 쓴다.

## Implementation Decisions

### core — 실시간 중계(ADR 0039)

사용자가 "이 기능에서 core까지 바꾼다"를 골랐다(일지 2026-10-23-40). 구조는 이 명세가 시제품으로 재서 정했다(`.scratch/web-widget/probes/live_relay.patch`와 `live_relay.py`, README의 2026-10-23 결과).

- **에이전트는 몸통(`_Body`)이 연 anyio 태스크 그룹의 자식 태스크에서 돈다.** 에이전트 태스크가 에이전트의 제너레이터를 순회하고 닫는다(`_closing` 그대로). 몸통은 태스크 사이로 오는 신호를 기다렸다가, 신호가 오면 컨텍스트의 줄에 쌓인 이벤트를 모두 꺼내 내보내고 그 신호에 답한다.
- **컨텍스트는 이벤트를 기록하는 자리마다 몸통에 신호를 보내고 답을 기다린다(맞물림).** 시제품에서 신호를 보낸 자리는 다섯이다. 모델을 부르기 직전과 모델 호출을 기록한 뒤, 도구를 부르기 직전(게이트를 지난 뒤)과 도구 호출을 기록한 뒤, 거부를 기록한 뒤다. 부르기 직전의 신호는 그 앞에 쌓인 런타임 이벤트(재개의 `run_resumed` 따위)를 먼저 흘린다. 에이전트가 낸 이벤트도 줄에 넣고 같은 신호를 보낸다. 줄이 비었으면 기다리지 않는다. 재생 구간에서 되살린 호출은 이미 트레이스에 있으므로 흘릴 것이 없다.
- **신호는 다음을 청하는 `anyio.Event` 하나이고 크기 0의 메모리 흐름으로 건넌다. 이벤트 자체는 흐름에 싣지 않는다.** 흐름에 실은 항목은, 받는 쪽이 깨어나기 전에 asyncio의 날 취소(`Task.cancel()`)로 끝나면 사라진다. anyio 취소 범위로 끊으면 받는 쪽에 닿았다(`.scratch/web-widget/probes/anyio_facts.py`로 쟀다, ADR 0039의 거부한 안). 이벤트가 줄에 남아 있으므로, 몸통이 끝날 때 남은 것을 꺼내는 지금의 정리(`_attend`의 `finally`)가 그대로 받는다.
- **에이전트 태스크는 취소가 아닌 예외를 모두 그 객체 그대로 붙잡아 몸통에 넘기고, 신호의 보내는 쪽을 닫아 몸통의 기다림을 끝낸다.** 몸통은 받은 예외를 태스크 그룹 밖에서 다시 던진다. 같은 객체라 런타임이 던진 예외의 동일성 판정(`_Thrown`, ADR 0031)이 그대로 선다. 일시정지 신호도 이 길로 몸통에 닿는다. 취소는 붙잡지 않고 다시 던진다.
- **몸통 자신의 예외(트레이스 쓰기 실패, 소비자가 스트림을 닫음)는 태스크 그룹 안에서 붙잡아 그룹을 취소한 뒤 그룹 밖에서 다시 던진다.** anyio 4.15.1의 태스크 그룹은 그룹 안에서 빠져나온 취소 아닌 예외를 `BaseExceptionGroup`으로 감싼다(`anyio_facts.py`로 쟀다. 몸통이 그룹 안에서 던진 `ValueError`가 그룹 밖으로 `ExceptionGroup`이 되어 나왔다). 감싼 채 올라가면 몸통이 실패를 받는 자리의 타입 판정이 깨진다.

시제품의 핵심 모양이다(시제품에서 옮겼다. 이름과 자리는 구현이 정한다). `_run_agent`가 받은 `outcome`에 예외를 적는 것은 시제품의 지름길이고 `CODING_STANDARDS.md`의 "출력 인자를 쓰지 않는다"에 걸린다. 구현은 에이전트 태스크의 예외를 몸통에 돌려주는 길을 출력 인자 없이 짓는다.

```python
async def _relay(self, agent, ctx) -> AsyncGenerator[Event]:
    bell, rings = anyio.create_memory_object_stream[anyio.Event]()
    ctx.bind(bell)
    outcome = _Outcome()
    async with anyio.create_task_group() as group, rings:
        group.start_soon(self._run_agent, agent, ctx, bell, outcome)
        try:
            async for ring in rings:
                for pending in ctx.take_events():
                    yield pending
                ring.set()
        except BaseException as error:
            if isinstance(error, anyio.get_cancelled_exc_class()):
                raise
            group.cancel_scope.cancel()
            outcome.error = error
    if outcome.error is not None:
        raise outcome.error


async def release(self) -> None:  # 컨텍스트
    if not self._pending or self._bell is None:
        return
    proceed = anyio.Event()
    await self._bell.send(proceed)
    await proceed.wait()
```

대가는 ADR 0039의 Consequences다. 구현 티켓이 함께 고치는 문서는 셋이다. `.claude/rules/core.md`에서는 두 문장을 고친다. "에이전트의 `finally`가 `run()`이 끝나기 전에 같은 태스크에서 돈다"를 "에이전트를 돌린 태스크에서 돈다"로 바꾸고, "범위가 yield를 건너므로 부르는 쪽은 이벤트 사이에 await 하지 않는다"의 까닭에 몸통의 태스크 그룹을 더한다. sdk `BaseAgent.run`의 독스트링에는 플러그인 작성자가 알아야 할 셋을 적는다(ADR 0039 Consequences). 정리 코드는 에이전트를 돌린 태스크에서 돌고, 에이전트가 바꾼 컨텍스트 변수는 부른 쪽에 보이지 않으며, 버려진 실행에서는 정리 코드의 await가 취소된다. `.claude/rules/channel.md`의 "실행을 모는 루프는 이벤트와 이벤트 사이에 await 하지 않는다"의 까닭(core가 취소 범위 안에서 yield한다)에도 몸통의 태스크 그룹을 더한다. `.scratch/end-user-continuation/probes/contract_mutations.toml`의 변이 "에이전트의 제너레이터를 닫지 않는다"가 바뀐 단언에서도 빨개지는지 다시 보고, 표지(`expect_output`)가 맞지 않으면 고친다.

### 계약 — 부르기 시작함 항목과 429의 상한 종류(ADR 0023 이력 2026-10-23)

사용자가 고른 둘(core까지 바꾼다, 서버가 상한의 종류를 코드로 준다)의 계약 몫이다. 계약이 바뀌므로 이 티켓이 기능의 첫 티켓이고(`docs/agents/issue-tracker.md`), 이 계약을 쓰는 티켓(core의 실시간 중계, 위젯 클라이언트를 쓰는 화면)을 막는다. 계약을 쓰지 않는 위젯 앱의 뼈대와 사이트 파일 입력은 나란히 간다(Further Notes의 티켓의 차례).

- **최종 사용자 항목에 `calling`(`CallingItem`)이 는다. 필드는 `tools` 하나이고, 모델이 요청한 도구의 이름을 `llm_called`의 `tool_calls` 차례대로 담은 문자열 목록이다.** `tool_calls`가 빈 `llm_called`는 지금처럼 항목이 없으므로 `tools`는 늘 하나 이상이고, 스키마가 그것을 말한다(최소 길이 1). 인자와 도구 호출 식별자는 싣지 않는다. 계약에 실리는 한 줄 설명은 시점을 말하지 않는다("모델이 요청한 도구의 이름"). 이 항목이 core의 실시간 중계 없이 먼저 병합되면 지금처럼 도구가 끝난 뒤에 나오므로, 시점을 말하는 설명은 그사이 main에서 거짓이 된다. 도구마다 항목을 하나씩 내지 않고 목록 하나로 싣는 것은 투영이 이벤트 하나를 항목 하나 또는 없음으로 옮기는 규칙(`.claude/rules/channel.md`의 투영 항목)을 지키기 위해서다. 그래서 프레임의 `id`는 지금처럼 그 이벤트의 인덱스이고 `Last-Event-ID`의 뜻도 그대로다. (명세가 정했다)
- **429 봉투는 별도 스키마 `LimitEnvelope`이고, 봉투의 네 필드에 필수 필드 `limit`을 더한다. 값은 `concurrent_runs`(동시 실행 수), `hourly_runs`(시간당 실행 수), `subscriptions`(구독 수)의 셋이다.** 최종 사용자 면의 라우트 넷의 429만 이 스키마를 가리키고, 그 넷의 다른 상태 코드와 운영자·관리 경로의 모든 에러는 지금의 `ErrorEnvelope` 그대로다. 네 필드의 스키마는 `ErrorEnvelope`와 글자 그대로 같다. 그래서 `code`는 `ErrorCode`를 가리키고 값은 늘 `too_many_requests`이며, `message`는 지금의 글 그대로다. `limit`의 값 집합은 이름 있는 컴포넌트 `LimitKind`(상한의 종류)다. 지금 서버의 상한 열거는 값이 봉투 문구에 드는 한국어 이름이라 그대로 `limit`의 값이 될 수 없고, 구현이 대응을 짓는다. 동시 실행 상한의 세 범위(주체별, 사이트별, 전역)는 모두 `concurrent_runs`가 된다. 봉투에 선택 필드를 더하지 않고 스키마를 가르는 까닭은, 생성 클라이언트에서 429 응답의 `limit`이 늘 있는 값으로 좁혀지고 다른 상태 코드의 봉투가 네 필드 그대로 남기 때문이다. (명세가 정했다)
- 운영자 채널(`/runs`)과 관리 API의 계약은 바뀌지 않는다. 운영자 스트림은 원문 이벤트라서, `llm_called`가 실행 도중에 오는 것은 시점만 바뀐 것이다.
- 함께 고치는 문서는 둘이다. `.claude/rules/channel.md`의 투영 항목("종류로만 가른다")에 `llm_called`의 조건과 `calling`을 더한다. `.claude/rules/http.md`의 봉투 항목("네 필드가 전부 required다")에 429의 다섯째 필드를, 예외 표 항목("봉투의 문구는 어느 상한인지만 말하고")에 `limit`을 더한다. `openapi.json`을 다시 뽑고 api-client를 다시 생성한다.
- 함께 고치는 시험은 넷이다. 봉투를 단언하는 둘은 지금 모든 에러를 `ErrorEnvelope` 하나로 견주므로 위 규칙(최종 사용자 경로 넷의 429만 `LimitEnvelope`)으로 고친다. `tests/test_server.py`의 `test_문서화된_에러_응답이_전부_봉투이고_내는_에러를_빠뜨리지_않는다`와 `tests/channel/http/test_end_user.py`의 `test_경로_넷이_지은_operation_id_와_봉투_에러_문서와_항목_유니온을_든다`다. 같은 파일의 `test_항목_유니온은_판별자_type_의_이름_있는_컴포넌트이고_멤버가_일곱이다`는 여덟이 된다. `tests/test_main.py`의 LLM 시험 `test_실제_serve_에서_서명한_토큰으로_시작한_실행을_최종_사용자_경로로_이어_가면_앞_대화를_안다`의 독스트링에서 "모델 호출은 항목이 없어"의 앞에 '도구를 요청하지 않은'을 붙인다(그 시험의 에이전트는 도구가 없어 단언은 그대로다).

### api-client — 위젯 클라이언트(ADR 0024)

- **`packages/api-client`에 위젯 클라이언트를 더한다. 기준 주소(`URL`)를 인자로 받고, 타입에 드는 경로는 최종 사용자 경로 넷뿐이다.** 서명 토큰은 클라이언트가 들지 않고 부르는 쪽이 요청마다 `Authorization` 헤더로 넘긴다. 위젯은 토큰 손잡이가 실패한 것을 요청을 보내기 전에 가려 401과 같은 화면으로 보여야 하기 때문이다. (명세가 정했다)
- **최종 사용자 스트림의 읽기는 프레임의 `id`를 함께 낸다.** 지금의 `readFrames`는 `data`만 읽고 `id:` 줄을 버려서, 위젯이 결정의 `pause_index`와 구독의 `Last-Event-ID`를 얻을 길이 없다. 최종 사용자 항목을 읽는 함수를 하나 더해 프레임마다 `id`(십진 정수)와 항목을 내고, 항목은 `type`의 판별자 술어(`calling` 포함)로 좁힌다. 모르는 `type`이나 읽지 못한 프레임은 원문으로 내고 위젯은 건너뛴다. `data` 없이 주석만 든 블록(서버의 keepalive)도 그것이 왔다는 값으로 낸다. 지금의 `readFrames`는 그 블록에서 값을 내지 않아, 부르는 쪽은 도구가 오래 도는 동안 스트림이 살아 있는지 알 길이 없다. 위젯의 무응답 판정(아래 재접속)이 그 값을 센다. 운영자 쪽 `readFrames`의 동작은 바뀌지 않는다. (명세가 정했다)
- 프레임 크기 상한은 두지 않는다(ADR 0024). 스트림은 브라우저의 `EventSource`가 아니라 fetch로 읽고, 구독의 `Last-Event-ID`는 계약의 헤더 파라미터로 보낸다(plan.md 행이 end-user-channel 명세에서 넘겨받은 것).

### 위젯 앱의 배치와 빌드(ADR 0024)

- **경로.** Next의 `basePath`는 `/widget`이다(ADR 0024 이력 2026-10-23). iframe 페이지는 `/widget`, element 번들은 `/widget/element.js`, 글꼴 파일은 `/widget/fonts/` 아래다. 번들과 글꼴은 빌드가 Next의 `public/`에 넣는다. (명세가 정했다: 번들과 글꼴의 경로)
- **빌드의 입력은 사이트 파일 하나다.** 빌드는 시작 래퍼를 지나 환경 변수 `AGENT_OS_SITE_FILE`이 가리키는 사이트 파일(`serve --site-file`과 같은 파일)을 읽고, 거기서 둘을 빌드에 넣는다. (명세가 정했다: 변수 이름)
  - 모든 사이트의 허용 출처를 합친 목록. iframe 페이지의 `frame-ancestors`와 postMessage의 출처 거르기가 쓴다. 변수가 없거나 합친 목록이 비면 `frame-ancestors 'none'`이고 postMessage도 모두 버린다(ADR 0024의 fail-closed).
  - 모든 사이트의 요청 글자 수 상한 가운데 가장 작은 값. 사이트가 값을 적지 않았으면 서버의 기본값 20,000이다. 위젯은 자기가 어느 사이트에 들었는지 빌드 때 모르고(두 임베드가 부모의 출처를 아는 길이 다르다), 가장 작은 값을 쓰면 서버가 거절할 요청을 보내지 않는다. 대가는 상한이 더 큰 사이트도 작은 값으로 막히는 것이다. (명세가 정했다)
  - 변수가 없으면 위의 둘(`'none'`과 기본값 20,000)로 빌드한다. 변수가 경로를 줬는데 그 파일이 없거나 읽지 못하면 빌드가 실패한다. 서버의 `serve --site-file`이 같은 파일로 뜨지 못하는 것과 같은 갈래다. 변수를 준 것은 사이트를 열려는 뜻이라, 조용히 `'none'`으로 빌드하면 위젯이 어느 사이트에서도 서지 않는데 빌드는 초록이 된다. 읽지 못하는 것은 둘이다. 하나는 파일의 모양이 서버의 규칙과 어긋난 것이다. TOML이 깨졌거나, 판(`schema_version`)이 `"1"`이 아니거나, 모르는 키가 있거나, 필수 키가 빠졌거나(사이트 항목의 `issuer`·`audience`·`public_keys`·`allowed_origins`·`agents`. 서버의 사이트 파일 모델에서 기본값이 없는 다섯이다), 값의 타입이 엄격한 타입과 다르면(수를 글자로 적은 것 등) 그렇다. `allowed_origins`가 빠진 항목을 빈 목록으로 읽으면 빌드가 조용히 `'none'`으로 초록이 되므로 이 갈래도 실패다. 다른 하나는 빌드가 읽는 두 값이 서버가 거절할 값인 것이다. 아래 표기 밖의 허용 출처나 1보다 작은 요청 글자 수 상한이 그렇다. 서버만 읽는 값의 뜻(발급자의 빔·겹침·구분 문자, 공개 키의 PEM과 `kid`의 겹침, 열 에이전트의 이름 패턴)은 빌드가 다시 판정하지 않는다. 그 값이 틀린 파일로는 serve가 뜨지 못해 조용히 지나가지 않고, PEM까지 두 언어로 판정하면 같은 검사를 두 벌 유지하게 된다. (명세가 정했다: 파일을 읽지 못할 때)
- **허용 출처의 표기 검사.** ADR 0024는 표기(스킴, 호스트, 포트, 와일드카드 금지)를 파이썬과 Node가 같은 픽스처로 판정한다고 정했는데, 지금 파이썬은 사이트 파일을 읽을 때 `"*"` 하나만 거절한다. 표기는 브라우저가 `Origin` 헤더에 싣는 직렬화 그대로여야 한다. 스킴은 `http`나 `https`이고, 호스트는 소문자 ASCII(국제화 도메인은 퓨니코드)이며, 기본 포트(`http`의 80, `https`의 443)는 적지 않는다. IPv4 호스트는 앞에 0이 없는 십진수 넷을 점으로 잇는다. IPv6 호스트는 대괄호 안에 브라우저가 적는 꼴이다. RFC 5952 압축형이되 IPv4를 품은 주소도 16진수로 적는다(파이썬의 `compressed`는 판에 따라 IPv4 매핑 주소(`::ffff:0:0/96`)를 점으로 적어 기준으로 쓰지 않는다. 티켓 04). 포트는 앞에 0이 없는 65535 이하의 십진수다. 경로, 끝 슬래시, 질의, 조각, 사용자 정보, `*`, `null`은 없다. 그와 다른 표기는 CORS와 `frame-ancestors`에서 조용히 맞지 않기 때문이다. 포트의 범위를 적지 않으면 규칙의 글만 따른 파이썬 판정은 `https://example.com:99999`를 지나게 두고 Node의 `new URL`은 65536부터 `ERR_INVALID_URL`로 거절해(65535와 0은 받았다) 두 언어의 판정이 갈린다. 앞의 규칙만으로는 소문자이고 기본 포트를 글자로 적지 않았는데 브라우저의 직렬화와 다른 값이 남는다. Node 24.19.0의 `new URL(v).origin`이 `http://127.1`, `http://0x7f.0.0.1`, `http://127.000.000.001`을 `http://127.0.0.1`로, `https://[0:0:0:0:0:0:0:1]`을 `https://[::1]`로, `https://example.com:0443`을 `https://example.com`으로 바꿨다(명세 검토가 먼저 보았고, 셀프 리뷰가 `node -e`로 다섯을 `new URL(v).origin`에 넣어 다시 손으로 봤다). 이 다섯은 막히는 사례다. `https://example.com:65536`과 IPv4를 품은 IPv6 `http://[::ffff:1.2.3.4]`도 막히는 사례다. 뒤의 것은 Node 24.19.0의 `new URL(v).origin`과 파이썬 3.12.10의 `ipaddress.IPv6Address("::ffff:1.2.3.4").compressed`가 모두 16진 꼴 `::ffff:102:304`로 바꿨다(포트 넷과 이 둘을 세션 스크래치패드의 스크립트로 `node`와 `uv run python`에 넣어 손으로 봤다, 일지 2026-10-23-40). 이 규칙의 지나는 사례와 막히는 사례를 커밋한 JSON 픽스처 하나에 두고, 파이썬은 사이트 파일을 읽을 때(serve가 뜨지 못한다) Node는 위젯 빌드에서(빌드가 실패한다) 그 픽스처로 같은 판정을 고정한다. serve가 뜨지 못할 때의 구성 오류 문구는 어긋난 항목과 어긴 규칙을 말한다. (명세가 정했다: 규칙의 목록)
- **사이트 파일의 판은 `"1"` 그대로다.** 위 검사는 지금 파이썬이 `"*"` 하나만 거절하던 것을 조인다. 지금 허용 출처를 쓰는 것은 서버의 CORS 하나이고(서버의 조립을 읽었다), 그 CORS는 `Origin`을 글자 그대로 견준다. 조여서 막히는 표기는 두 갈래다. 대문자, 기본 포트, 끝 슬래시와 경로, 정규형이 아닌 IP처럼 브라우저의 직렬화와 글자가 다른 표기는 전에도 어떤 `Origin`과도 맞지 않아 조용히 죽어 있던 항목이다. 그와 달리 `null`과 http(s)가 아닌 스킴(`capacitor://localhost` 같은 웹뷰 앱의 출처)은 전에 맞던 항목이고, 이 검사가 그 뜻을 바꾼다. 두 갈래 모두 Starlette `CORSMiddleware`의 `is_allowed_origin`을 `uv run python`으로 불러 손으로 봤다. `allow_origins`에 `"null"`과 `"capacitor://localhost"`를 주면 둘에 True였고, `"https://Example.com"`, `"https://example.org:443"`, `"http://127.1"`을 주면 브라우저가 보낼 `https://example.com`, `https://example.org`, `http://127.0.0.1`에 모두 False였다. `null`은 브라우저가 출처가 불투명한 문맥(샌드박스 iframe, `file:` 페이지)에서 보내는 값이라 어느 사이트든 그런 문맥을 지어 그 항목에 맞출 수 있으므로, 허용 목록이 사이트를 가리는 뜻이 없어진다(HTML 표준의 불투명 출처 직렬화를 근거로 든 것이고 브라우저로 재지는 않았다). http(s)가 아닌 스킴은 웹뷰 앱이나 브라우저 확장의 출처이고, 이 기능은 사이트의 웹 페이지에 넣는 두 임베드만 정한다(Out of Scope). 그래서 `null`과 그 스킴을 의도해서 막는다. 그런 항목이 든 파일로는 serve가 구성 오류로 멈추고 문구가 항목과 규칙을 말하므로, 운영자는 조용히 바뀐 동작이 아니라 멈춘 serve로 알게 된다. 판을 올리면 운영자가 맞는 파일까지 고쳐야 하므로 판은 그대로 두고, 이 비호환을 여기 적는다. (명세가 정했다)
- **스타일.** 위젯의 CSS는 디자인 토큰 CSS를 `@import`하고 `@source`로 위젯 소스를 덮는다(디자인 토큰 CSS가 `source(none)`이다). iframe 페이지는 글꼴 CSS도 싣고, element 번들은 디자인 토큰 CSS만 `?inline`으로 싣는다(plan.md 행의 design-system to-tickets).
- **아이콘.** `IconName` 열여섯으로 그린다. 화면 여덟이 쓴 아이콘 여덟(`send`, `wrench`, `circle-check`, `info`, `circle-pause`, `circle-x`, `x`, `check`)이 모두 그 안에 있다(화면 파일을 grep했다). 위쪽 띠와 알림의 버튼은 글자 버튼이다. 새 아이콘이 필요해지면 앱이 lucide를 직접 들이지 않고 `IconName`에 더한다. (명세가 정했다)
- **테스트 프로젝트.** 뿌리 `vitest.config.ts`에 위젯의 페이지 테스트 프로젝트(jsdom, 이름 `widget-pages`)와 스토리 테스트 프로젝트(chromium, 이름 `widget-storybook`)를 더한다. 이름이 패키지의 `storybook`, 관리 화면의 `pages`와 겹치면 Vitest가 거부한다(Vitest 5.0.2의 배포 코드에 `is not unique. All projects should have unique names.`라는 오류 문구가 있다. 코드를 읽었다). 위젯의 Storybook은 `apps/widget/.storybook/`이다(ADR 0026 이력, design-system 티켓 01). 위젯의 CSS가 Storybook에서 서는지는 스토리 시험이, 두 산출물의 빌드에서 서는지는 e2e가 본다. (명세가 정했다: 이름)
- **사진 비교.** 디자인 시스템 패키지의 사진 비교 도우미(Storybook 정적 빌드를 열고 스토리를 찍는 테스트 도구)를, 정적 빌드의 자리를 인자로 받게 바꿔 `@agent-os/ui/visual` 하위 경로로 내보낸다. 패키지의 컴포넌트와 토큰은 바뀌지 않고, 바뀌는 것은 그 테스트 도구의 자리뿐이다. 위젯은 자기 설정과 정답 사진을 위젯 앱 안에 둔다. 로컬 명령은 지금처럼 사진 비교 명령에 패키지 경로(`apps/widget`)를 준다. CI의 `visual` 잡은 같은 컨테이너에서 위젯의 Storybook 정적 빌드와 비교를 한 단계씩 더하고, 실패하면 위젯의 결과도 아티팩트로 올린다. (사용자가 골랐다: 도우미를 패키지의 하위 경로로 내보내는 것. 셋째 답의 설명 "디자인 시스템 패키지 … 바뀌지 않습니다"와 글자로 부딪혀 결정을 승인받을 때 따로 물었다. 잡과 명령의 모양은 그 선택을 따른다)
- **ADR 0024가 티켓에 넘긴 셋은 그대로 티켓이 정한다.** 시작 래퍼를 공유 자리로 옮길지 위젯이 자기 래퍼를 둘지, 워크스페이스의 vite 판을 고정할지, Node의 TOML 파서와 그 판이다. 셋 다 계약과 디스크 형식에 들지 않는다(명세 검토). vite는 디자인 시스템 패키지가 이미 `^8.3.1`로 선언했고 잠금 파일은 8.3.1이다(`web/packages/ui/package.json`과 `web/pnpm-lock.yaml`을 읽었다).

### 임베드

- **번들의 꼴.** element 번들은 모듈이 아니라 즉시 실행되는 classic 스크립트 하나(IIFE)다. 다른 출처의 `<script type="module">`은 CORS로 받으므로 번들 응답에 `Access-Control-Allow-Origin`이 없으면 사이트에서 실리지 않는다. classic 스크립트는 `<script>`에 `crossorigin` 속성이 없으면 CORS 없이 실리고, 청크로 나뉘지 않아 사이트가 넣을 것이 한 줄로 남는다. 사이트가 오류 보고나 무결성 검사를 위해 `crossorigin="anonymous"`를 붙이면 classic 스크립트도 CORS로 받으므로, 번들 응답에도 글꼴과 같은 `Access-Control-Allow-Origin: *`를 단다(아래 글꼴). (명세가 정했다)
- **페이지 안 방식.** 사이트는 `<script src="https://<위젯 출처>/widget/element.js">`와 `<agent-os-widget>` 요소 하나를 넣는다. 속성은 다섯이다. (명세가 정했다: 속성의 이름과 뜻)
  - `agent`(필수): 에이전트 이름. 플러그인 이름의 패턴(`^[a-z][a-z0-9-]{1,62}$`)을 지나야 한다.
  - `heading`: 위쪽 띠에 보일 이름. 없으면 `agent` 값이다. HTML 전역 속성 `title`은 요소 전체에 말풍선을 띄우므로 쓰지 않는다.
  - `intro`: 첫 화면의 할 수 있는 일 한 줄. 없으면 그 줄을 그리지 않는다.
  - `theme`: 패키지가 내보내는 테마 목록의 키. 없으면 기본 테마다.
  - `mode`: `light` 또는 `dark`. 없으면 시스템 설정을 따른다.

  서명 토큰은 요소의 속성(property) `tokenProvider`(`() => Promise<string>`)로 받고, 위젯은 요청을 보낼 때마다 그것을 부른다. (명세가 정했다)
- **iframe 방식.** 사이트는 `<iframe src="https://<위젯 출처>/widget?agent=…&heading=…&intro=…&theme=…&mode=…">`를 넣는다. 질의의 이름과 뜻은 위 속성과 같다. 토큰은 postMessage로 받는다. (명세가 정했다: 메시지의 모양)
  - 위젯은 토큰이 필요할 때 `window.parent`에 `{type: "agent-os/token-request", id}`를 보낸다. `id`는 요청마다 새 무작위 문자열이다. 이 메시지에는 비밀이 없어 대상 출처를 `"*"`로 둔다. iframe이 부모의 출처를 모든 브라우저에서 미리 알 길은 없다.
  - 사이트는 그 iframe의 창에만, 위젯 출처를 대상으로 `{type: "agent-os/token", id, token}`을 보낸다(ADR 0024).
  - 위젯은 `event.source`가 `window.parent`이고, `event.origin`이 빌드에 든 허용 출처이며, `id`가 기다리는 요청과 같은 메시지만 받는다. 나머지는 버린다. `token`이 문자열이 아니면 토큰을 받지 못한 것이다.
- **토큰을 받지 못한 경우.** 함수가 없거나, 거부되거나, 문자열이 아닌 값을 주거나, 10초 안에 답하지 않으면 요청을 보내지 않고 401과 같은 화면을 보인다. (명세가 정했다: 10초)
- **잘못 준 속성.** `agent`가 없거나 패턴 밖이면 위젯이 대화 자리에 위험 알림(제목 "위젯 설정이 올바르지 않습니다.", 본문 "사이트 관리자에게 알려 주세요.")을 보이고 입력창을 막으며, 속성 이름을 든 `console.error`를 남긴다. `theme`이나 `mode`가 목록 밖이면 기본값으로 그리고 `console.error`만 남긴다. 위젯은 그대로 쓸 수 있기 때문이다. (명세가 정했다)
- **크기.** 위젯은 자기 자리를 채운다. 페이지 안 방식의 호스트는 `display: block`이고 폭과 높이는 사이트가 정한다. iframe 방식에서는 iframe의 크기다. 화면 디자인의 높이 560px은 예시다. 지원하는 가장 좁은 폭은 320px이다. (명세가 정했다)
- **Shadow DOM.** element는 `open` 모드의 shadow root에 그린다. 페이지 스크립트는 사이트의 출처에서 이미 위젯과 같은 권한으로 돌므로(ADR 0024) `closed`는 막아 주는 것이 없고 e2e의 조회만 어렵게 한다. (명세가 정했다)
- **API의 기준 주소.** element는 번들 스크립트의 출처, iframe은 자기 페이지의 출처다. element는 번들이 처음 실행될 때 `document.currentScript`가 `HTMLScriptElement`의 인스턴스일 때만 그 `src` 속성(property)에서 출처를 읽어 둔다. 그 값은 classic 스크립트가 최상위를 실행하는 동안에만 있다. 인스턴스인지 먼저 보는 것은 DOM clobbering 때문이다. `document`의 이름 있는 속성이 내장 속성을 가리므로, 사이트 페이지에 `<img name="currentScript" src="https://<다른 출처>/">`가 있으면 `document.currentScript`가 그 요소를 돌려준다. 사이트가 사용자 글을 `name` 속성을 남기는 새니타이저로 그리면 누구나 그 요소를 넣을 수 있고, 위젯이 그 `src`를 기준 주소로 쓰면 요청마다 서명 토큰이 그 출처로 간다. 그래서 `getAttribute("src")`나 `"src" in`으로 좁히지 않는다. 인스턴스가 아니면(없음, 다른 요소, 컬렉션) 요청을 보내지도 토큰 함수를 부르지도 않고, 잘못 준 속성과 같은 위험 알림과 `console.error`를 남긴다(보안 리뷰, 일지 2026-10-23-40). 둘 다 nginx 뒤의 위젯 출처이고, 최종 사용자 경로는 그 아래 `/end-user`다. iframe 방식의 요청은 같은 출처라 CORS를 지나지 않는다. 서버는 허용 밖 출처를 막지 않고 응답 헤더만 내지 않으므로(최종 사용자 면의 CORS 모듈 독스트링을 읽었다) 그대로 동작한다. (명세가 정했다)
- **같은 페이지에 같은 에이전트의 위젯을 둘 두는 것은 지원하지 않는다.** 저장의 키가 에이전트로 갈리므로 둘이 한 저장을 나눠 쓰게 된다. (명세가 정했다)
- **임베드 안내.** 위젯 앱 폴더에 마크다운 하나를 둔다. 사이트 개발자가 서버 코드를 읽지 않고 붙일 수 있도록, 두 방식의 태그와 속성, 서명 토큰(RS256, 클레임 다섯 `iss`·`sub`·`aud`·`exp`·`iat`, 수명 600초 이하, 키 교체의 `kid`, 그리고 `sub`는 사이트가 인증한 오래 가는 사용자 식별자여야 한다는 사이트의 의무(ADR 0023)), 허용 출처의 표기, postMessage에서 사이트가 지킬 것, 사이트의 CSP에서 열어 둘 자리(`script-src`·`connect-src`·`font-src`에 위젯 출처, iframe 방식은 `frame-src`), CSP가 글꼴을 막으면 시스템 글꼴로 그려진다는 것, 같은 에이전트를 한 페이지에 둘 두지 않는 것, 사이트가 기대는 공개 표면(속성 다섯, postMessage의 `type` 둘)을 바꿀 때는 옛 이름을 한동안 함께 받는다는 것을 적는다. 사이트의 엄격한 `style-src`가 shadow root에 넣은 스타일을 막는지는 재지 않았다. e2e가 `style-src 'self'`인 사이트 페이지에서 페이지 안 위젯이 스타일을 갖는지 보고, 막히면 안내의 CSP 자리에 `style-src`를 더한다. (명세가 정했다: 자리와 목차)

### 테마·모드·밀도·글꼴(ADR 0026과 그 이력)

- `theme`과 `mode`는 호스트의 `data-theme`·`data-mode`로 옮겨 패키지 CSS의 `:host(...)`가 받는다. iframe은 문서의 `html`에 같은 속성을 단다. 테마 값의 검사는 패키지가 내보내는 테마 목록을 읽는다.
- 페이지 안 번들의 호스트와 iframe 문서의 `html`에 `data-density="regular"`를 단다(design-refresh 명세). 빠뜨리면 페이지 안 위젯이 넓은 창에서 촘촘해지므로 페이지 테스트와 e2e가 그 속성을 본다.
- shadow 안의 감싼 요소가 컨테이너이고, 레이아웃의 기준 폭은 `@wide:`(360px)다. 상속 속성은 그 감싼 요소에서 패키지 CSS가 다시 정하고, 그것이 실제 커스텀 요소 안에서 사이트의 `letter-spacing`과 `html { font-size }`를 막는지는 e2e가 잰다.
- **글꼴.** iframe 페이지는 글꼴 CSS를 그대로 싣는다. element 번들은 글꼴 파일을 번들에 박지 않고(라이브러리 모드는 `?url` 자산도 박는다), 위젯 출처의 `/widget/fonts/`에서 `FontFace`로 사이트 문서에 등록한다. family 이름은 위젯만 쓰는 고유한 이름이고, 감싼 요소에서 `--sans`·`--mono`를 그 이름으로 다시 정한다. 글꼴 응답과 element 번들 응답(`/widget/element.js`)에는 `next.config`의 헤더가 `Access-Control-Allow-Origin: *`를 달고 nginx는 그대로 넘긴다. 둘 다 자격 증명 없이 받는 공개 파일이라 `*`로 둔다. 번들은 사이트가 `crossorigin` 속성을 붙였을 때만 그 헤더가 쓰인다(위 번들의 꼴). (명세가 정했다: `*`와 Next가 다는 것)
- 글꼴의 양에 예산을 두지 않는다. plan.md 행이 넘긴 "예산을 볼 때 다시 잰다"는 예산이 서는 날의 일이다(Out of Scope). (명세가 정했다)

### 대화 화면

모양은 화면 디자인 그대로다(`mk-conversation`, `mk-dark`, `mk-themes`). 위쪽 띠는 고른 A(이름과 "새 대화" 글자 버튼)다.

- **첫 화면.** `intro`가 있으면 그 한 줄을, 그 아래 "아래에 요청을 적어 보내 주세요."를 보인다. 디자인의 제안을 받아들였다. (명세가 정했다)
- **진행 표시의 이름표.** 실행이 도는 동안 대화의 끝에 진행 표시(값 모름)가 선다. 이름표는 아래 규칙으로 고른 도구 이름에 " 부르는 중"을 붙인 글이고, 고를 도구가 없으면 고정 문구 "요청을 처리하고 있습니다."다. 이름표는 글자열이라 도구 이름이 고정폭으로 보이지 않는다. " 부르는 중"을 붙이는 꼴은 디자인의 제안을 받아들였고, 고정 문구와 아래 규칙은 명세가 정했다. (명세가 정했다)
  - 위젯은 실행마다 부르는 중인 도구의 줄을 든다. `calling` 항목이 오면 그 `tools`를 줄 끝에 붙이고, `progress` 항목이 오면 줄에서 같은 이름의 첫 것을 뺀다. 이름표의 도구는 줄의 첫 이름이다.
  - 거부한 도구도 `progress` 항목(실패)으로 빠진다. 런타임은 거부한 도구를 부르지 않고 실패한 도구 호출로 기록하기 때문이다(런타임의 거부 처리와 항목의 투영을 코드로 읽었다). 그래서 `decided` 항목은 줄을 바꾸지 않는다.
  - 에이전트가 모델 없이 `ctx.tool()`로 부른 도구는 `calling`이 없어 줄에 들지 않고, 그 `progress`는 뺄 것이 없어 그냥 지나간다. 그동안 이름표는 고정 문구다.
  - 다시 붙어 처음부터 받은 항목에도 같은 규칙으로 줄을 다시 짓는다. 그래서 새로 고친 뒤에도 같은 이름표가 선다.
- **도구 줄.** `progress` 항목마다 한 줄(아이콘, 고정폭 도구 이름, 성공·실패)이 쌓인다. 결말(끝남, 실패, 끝내지 못함)이 오면 "도구 N개를 불렀습니다" 한 줄로 접히고, 그 줄은 `aria-expanded`를 가진 버튼이라 눌러 편다. 도구 줄이 없는 실행에는 그 줄도 없다.
- **출력.** `finished`의 `output`을 글자 그대로, 줄바꿈을 지키고 긴 낱말은 줄 끝에서 꺾어 그린다. 마크다운으로 그리지 않는다(ADR 0024).
- **보내기.** Enter는 보내고 Shift+Enter는 줄을 바꾼다. 한글 입력을 조합하는 중에 누른 Enter는 보내지 않는다. 보내기 버튼은 입력이 비었거나(앞뒤 공백만 있는 것도), 글자 수 상한을 넘었거나, 실행이 돌거나 멈춰 있거나, 상한의 기다림이 남았거나, 속성이 잘못됐을 때 막힌다. (명세가 정했다: Enter의 규칙)
- **보내기 버튼의 크기.** 디자인 시스템 버튼의 크기 그대로이고, 여러 줄로 늘어나는 입력창의 아래 끝에 맞춘다. 화면 디자인이 입력창 높이에 맞춘 것은 어림이었다. 크기는 위젯 스토리의 사진이 고정한다. (명세가 정했다)
- **글자 수.** 세는 단위는 서버와 같은 코드 포인트다. 상한의 90% 이상이 되면 입력창 아래에 "19,850 / 20,000"처럼 센 수를 보이고, 넘으면 "20,000자를 넘었습니다"를 위험 색으로 보인다. 그 글은 `aria-describedby`로 입력창에 묶는다. (명세가 정했다: 90%)
- **새 대화.** 시작·이어 가기·결정의 응답이나 다시 붙은 구독이 결말 전이면 막힌다. 멈춘 실행을 기다릴 때와 쉬고 있을 때는 열린다. 누르면 묻지 않고 저장과 화면을 비우고 열린 스트림을 끊는다. 멈춘 실행은 서버에 남고 위젯은 그것을 잊는다. (명세가 정했다)
- **다음 요청과 다시 보내기.** 이어 갈 마지막으로 끝난 실행이 있으면 다음 요청은 그 실행의 이어 가기이고, 없으면 시작이다. "다시 보내기"는 같은 요청 글을 같은 규칙으로 보내고 새 교환으로 덧붙인다. 실패한 교환은 그대로 남는다. (명세가 정했다: 새 교환으로 덧붙이는 것)
- **스크롤.** 새 내용이 오면, 최종 사용자가 대화의 끝을 보고 있었을 때만 끝으로 내린다. (명세가 정했다)

### 저장(ADR 0024)

- sessionStorage의 키는 `agent-os-widget:<에이전트 이름>`이다. 페이지 안 방식에서는 사이트 출처의 저장소라서, 사이트의 다른 키와 섞이지 않게 접두사를 둔다. (명세가 정했다) sessionStorage는 탭마다 따로라 새 탭은 빈 저장으로 시작한다. 브라우저의 "닫은 탭 다시 열기"가 그것을 되살리는지는 확인하지 않았다. 되살려도 아래 묶음 견주기가 다른 계정의 대화를 그리지 않는다.
- 드는 것은 토큰의 발급자와 `sub`, 교환들(요청 글, 도구 줄의 이름과 성패, 결말인 출력 또는 실패 원인과 run_id 또는 끝내지 못함과 run_id, 결정의 기록), 이어 갈 마지막으로 끝난 실행의 run_id, 다시 붙을 실행(돌거나 멈춘 것)의 run_id다. 도는 교환에는 요청 글만 든다. 새로 고친 뒤 다시 붙으면 처음부터 받아 그 교환을 다시 짓는다. (명세가 정했다: 도는 교환은 요청 글만)
- **상태의 옮김.** `started`가 오면 다시 붙을 실행이 그 run_id가 된다. `finished`가 오면 이어 갈 실행이 그 실행이 되고 다시 붙을 실행은 빈다. `failed`나 `unfinished`가 오면 다시 붙을 실행만 빈다. `paused`가 오면 다시 붙을 실행이 그대로 남는다.
- **묶음 견주기.** 저장한 것이 있으면 위젯은 먼저 토큰을 받아 그 페이로드의 `iss`·`sub`를 저장한 것과 견준 뒤에 그린다. 그동안은 진행 표시만 보인다. 다르면 저장을 지우고 빈 화면으로 시작한다. 요청을 보낼 때마다 새로 받은 토큰도 같이 견준다. 페이로드는 검증하지 않고 base64url을 풀어 읽기만 하며, 검증은 서버가 한다. 풀지 못한 토큰은 받지 못한 토큰과 같다. 토큰을 받지 못하면 저장을 지우지도 그리지도 않고 401과 같은 화면을 보인다. 앞 사용자의 교환이 토큰 없이 그려지지 않게 하기 위해서다. (명세가 정했다)
- 저장이 용량을 넘으면 오래된 교환부터 뺀다. 교환을 다 빼도 넘으면 묶음과 run_id만 두고, 그것도 넘으면 저장하지 않고 메모리로만 이어 간다. (명세가 정했다)
- **저장의 판.** 저장한 값은 판 번호 필드(처음은 1)를 든다. 읽을 때 판이 다르거나 모양 검사를 지나지 못하면 묶음이 다를 때처럼 지우고 빈 화면으로 시작한다. 위젯을 다시 배포한 뒤 옛 모양의 저장을 만나는 길이다. TS에서는 타입 단언을 쓰지 못하므로(원칙 III) 읽는 자리는 어차피 실행 중에 모양을 검사한다. (명세가 정했다)
- **저장하지 않는 것.** 교환은 그 실행의 `started` 항목이 올 때 저장에 든다. 그 전에 거절된 요청(거절 표의 모든 행)과 그 알림, 이어 가기의 404 뒤에 남기는 정보 알림, 입력창의 글은 저장하지 않는다. 그래서 새로 고친 뒤에는 결말이 있거나 다시 붙을 교환만 보인다. 거절된 요청은 실행이 서지 않아 다시 붙을 것이 없고, 알림은 그 순간의 안내다. (명세가 정했다)

### 승인 묻기

모양은 화면 디자인 그대로다(`mk-approval`). 입력창은 고른 A(막힌 채 남고, 그 위 띠가 "승인이나 거부를 먼저 골라 주세요.")다.

- **인자의 글자 꼴.** 도구 이름은 고정폭 `font-medium`이다. 인자는 `JSON.stringify(args, null, 2)`의 글(받은 키 차례, 두 칸 들여쓰기, 한글을 이스케이프하지 않는다)을 고정폭으로, 줄바꿈을 지키고 긴 값은 아무 자리에서나 꺾어 그린다. 고치거나 줄이지 않는다. (명세가 정했다)
- 결정의 `pause_index`는 `paused` 프레임의 `id`다.
- 사유를 다듬어 비면 "거부"가 막힌다. 다듬는 글자는 서버와 같이 파이썬 `str.strip()`이 지우는 글자(`str.isspace()`가 참인 글자)다. JS의 `trim()`은 U+001C~U+001F와 U+0085를 지우지 않고 U+FEFF를 지워 서버와 갈리므로 쓰지 않는다(`node -e`로 글자마다 `String.fromCharCode(c).trim()`을, `uv run python -c`로 `chr(c).strip()`을 찍어 손으로 봤다). 갈리면 위젯이 보낸 사유가 422로 돌아오거나 서버가 받을 사유를 위젯이 막는다. (명세가 정했다: 다듬는 글자) 사유에도 입력창과 같은 글자 수 상한과 같은 셈(코드 포인트)을 쓴다. 상한의 90% 이상이면 사유 칸 아래에 센 수를, 넘으면 "20,000자를 넘었습니다"를 보이고 "거부"가 막힌다. 서버의 결정 본문은 사유의 길이를 묶지 않아, 묶지 않으면 긴 사유가 운영자 프록시의 본문 상한에 걸려 413이 되고 위젯은 그것을 표 밖의 상태로만 보인다(`channel/http`의 결정 본문 모델에 최대 길이가 없는 것을 PR 직전 리뷰가 읽었다). (명세가 정했다: 사유의 상한) 보내는 동안에는 두 버튼과 사유 칸이 막힌다. `decided` 항목이 오면 버튼과 칸이 걷히고 "승인했습니다" 또는 "거부했습니다: <사유>" 한 줄이 남는다. 결정의 응답은 결정 항목부터 실행을 이어 받으므로 그 뒤는 대화의 흐름과 같다.
- 같은 탭을 복제한 탭(sessionStorage가 복사된다)이 이미 결정했으면, 이 탭의 결정은 409를 받고 아래 표의 다시 보기로 그 결정을 따라간다.

### 실패 원인의 문구(ADR 0031)

실패 항목의 `message`(고정 문구)는 그리지 않고, `cause`마다 아래 문구를 위험 알림으로 보인다. 제목은 알림 부품의 `title`이고, 본문은 나머지 문장과 실행 식별자 줄("실행 식별자: run_…", 고정폭 작은 글자)이다. 버튼은 알림 부품의 `actions` 자리에 둔다. 디자인은 캔버스의 제약 때문에 제목을 비우고 버튼을 본문에 넣었는데, 부품의 쓰는 법("제목에 일어난 일을, 본문에 까닭이나 할 일을")대로 바꾼다. 문구와 권할 일은 시작 프롬프트(`screens-prompt.md`)의 표를 받아들였다. (명세가 정했다)

| `cause` | 제목 | 본문의 문장 | 버튼 |
|---|---|---|---|
| `conversation_summary` | 앞선 대화를 정리하지 못해 끝내지 못했습니다. | 없음 | 다시 보내기, 새 대화 |
| `timeout` | 정해진 시간 안에 끝나지 않았습니다. | 없음 | 다시 보내기, 새 대화 |
| `tool_connection` | 에이전트가 쓰는 도구에 연결하지 못했습니다. | 잠시 뒤 다시 보내 주세요. | 다시 보내기 |
| `model_call` | 에이전트가 모델을 부르지 못했습니다. | 잠시 뒤 다시 보내 주세요. | 다시 보내기 |
| `tool_failure` | 도구가 실패했거나 거부되어 끝내지 못했습니다. | 없음 | 다시 보내기 |
| `loop_limit` | 정해진 단계 안에 끝내지 못했습니다. | 요청을 나눠 보내 주세요. | 없음. 포커스가 입력창으로 간다 |
| `resume_mismatch` | 멈춘 실행을 이어서 끝내지 못했습니다. | 없음 | 다시 보내기 |
| `agent_code` | 에이전트에 문제가 있어 끝내지 못했습니다. | 없음 | 다시 보내기 |
| `other`, `null`, 모르는 값 | 실행이 실패로 끝났습니다. | 없음 | 다시 보내기 |

- **끝내지 못함.** `unfinished` 항목에는 제목 "실행을 끝내지 못했습니다.", 본문 "다시 보내 주세요."와 실행 식별자, 버튼 "다시 보내기"의 위험 알림을 보인다. 디자인의 "서버가 다시 시작해 이 실행을 끝내지 못했습니다."는 원인을 단정하므로 쓰지 않는다. 계약의 그 항목은 실행이 결말 없이 사라졌다는 것만 말하고, 트레이스를 쓰지 못해 결말 없이 끝난 실행도 이 항목이 된다. (명세가 정했다)

### 요청이 거절될 때 — 경로와 상태 코드마다(ADR 0023, end-user-continuation 명세)

거절 알림은 요청 글이 대화에 남은 채 그 아래, 출력이 올 자리에 선다(디자인의 제안). 429와 422만 요청을 입력창으로 되돌리고 대화에서 뺀다. 알림 문구의 첫 문장이 제목이고 나머지가 본문이다. 갈래는 응답의 상태 코드로 가르고 봉투의 `message`는 읽지 않는다. 화면이 계약보다 좁게 그린 404·409와 그리지 않은 결정의 거절을 이 표가 덮는다. (명세가 정했다: 표 전부)

| 경로 | 받은 것 | 위젯이 하는 일 |
|---|---|---|
| 넷 모두 | 401, 또는 토큰을 받지 못함 | 위험 알림 "로그인 정보를 받지 못했습니다. 페이지를 새로 고쳐 주세요." 버튼은 없다. 구독이면 다시 잇기를 멈춘다. 결정이면 알림이 카드 아래에 서고 카드의 버튼이 다시 열린다 |
| 시작 | 404 | 위험 알림 "이 에이전트를 찾을 수 없습니다. 사이트 관리자에게 알려 주세요." 버튼은 없고 `console.error`를 남긴다. 에이전트가 없거나 그 사이트의 열 에이전트 밖이라 다시 보내도 같다 |
| 이어 가기 | 404 | 1초 뒤 한 번 더 보낸다. 또 404면 저장과 화면을 비우고 정보 알림 "이전 대화를 이어 갈 수 없어 새 대화로 시작합니다."를 남긴 채 같은 요청을 시작으로 보낸다(ADR 0024 이력 2026-10-23). 이어 가기의 404에는 에이전트가 없거나 그 사이트의 열 에이전트 밖인 것도 들어, 그 시작이 다시 404를 받을 수 있다. 그때는 시작의 404 행대로 하고 더 보내지 않는다 |
| 구독 | 404 | 1초 뒤 한 번 더. 또 404면 저장과 화면을 비우고 같은 정보 알림을 남긴다. 다시 보낼 요청은 없다 |
| 결정 | 404 | 1초 뒤 한 번 더. 또 404면 카드의 버튼과 사유 칸을 걷고 그 아래 정보 알림 "이 승인 묻기는 더 이상 받을 수 없습니다."를 남긴다. 다시 붙을 실행을 비우고 입력창을 연다 |
| 시작, 이어 가기 | 409 | 위험 알림 "에이전트를 지금 쓸 수 없습니다. 잠시 뒤 다시 보내 주세요." 버튼은 "다시 보내기"다. 꺼진 에이전트와 끝나지 않은 앞 실행이 같은 코드라 가르지 않는다. 위젯은 끝난 실행만 이어 가므로 뒤의 것은 생기지 않는다 |
| 결정 | 409 | `Last-Event-ID`를 일시정지 프레임의 `id`로 두고 그 실행을 다시 구독한다. 새 항목이 오면 그것을 따라간다(다른 탭이 결정했다). 아무것도 없이 닫히면 일시정지가 그대로이므로, 카드 아래 위험 알림 "결정을 보내지 못했습니다. 잠시 뒤 다시 골라 주세요."를 보이고 버튼을 다시 연다 |
| 구독 | 409 | `Last-Event-ID` 없이 처음부터 다시 구독하고 이미 받은 `id`는 건너뛴다. 또 409면 500과 같다 |
| 시작, 이어 가기 | 422 | 요청을 입력창으로 되돌리고 그 아래 "요청을 보낼 수 없습니다. 요청을 고쳐 다시 보내 주세요."를 보인다. 위젯이 글자 수와 에이전트 이름을 먼저 막으므로 드물다 |
| 결정 | 422 | 500과 같다 |
| 시작, 이어 가기 | 429 | 요청을 입력창으로 되돌리고 입력창 위 띠가 상한의 문구와 기다릴 시간을 보인다(아래 상한) |
| 결정 | 429 | 띠가 상한의 문구를 "다시 고를 수 있습니다"로 끝맺어 보이고 그동안 결정 버튼을 막는다. 시간이 다 되면 버튼을 다시 연다. 저절로 다시 보내지 않는다 |
| 구독 | 429 | 재접속 띠 "연결이 많아 N초 뒤에 다시 잇습니다. 받은 내용은 그대로 있습니다."를 보인 뒤 다시 구독한다 |
| 시작, 이어 가기 | 500, 표 밖의 상태, 응답 전의 네트워크 실패, 시작 항목 전에 끊긴 스트림 | 위험 알림 "요청을 처리하지 못했습니다. 잠시 뒤 다시 보내 주세요." 버튼은 "다시 보내기"다. 같은 대화에서 이것이 세 번째로 거듭되면 "새 대화"도 단다. 결말을 받은 요청이 하나 오면 셈이 처음으로 돌아간다 |
| 결정 | 500, 표 밖의 상태, 응답 전의 네트워크 실패, `decided` 항목 전에 끝난 스트림 | 카드 아래 같은 문구의 위험 알림을 보이고 버튼을 다시 연다. 결정이 이미 서버에 닿았으면 다시 고른 결정이 409를 받아 위 409 행대로 그 결정을 따라간다 |
| 구독 | 422, 500, 표 밖의 상태 | 재접속과 같은 간격으로 다시 구독한다. 세 번 거듭되면 다시 잇기를 멈추고 같은 문구의 위험 알림과 "새 대화"를 보인다. 422는 위젯이 보낸 `Last-Event-ID`나 경로가 틀린 것이라 다시 보내도 같지만, 세 번으로 멈추므로 따로 두지 않는다 |
| 구독 | 응답 전의 네트워크 실패 | 끊긴 것과 같다. 아래 재접속의 간격대로 끝없이 다시 잇는다. 연결이 돌아오기를 기다리는 것이라 세지 않는다 |

### 재접속

- 스트림이 끝나거나, 읽는 도중 네트워크가 끊기거나, 45초 동안 프레임도 keepalive도 오지 않으면, 그 실행에서 마지막으로 받은 항목으로 가른다. 이번 응답에서 받았든 앞 응답에서 받았든 같다. 결말(끝남, 실패, 끝내지 못함)이면 끝난 것이고, `paused`이면 결정을 기다리는 것이며, 그 밖이면 끊긴 것이다. `paused` 뒤에 닫힌 스트림을 끊김으로 세면, 다시 이을 때마다 같은 `paused`까지 받고 또 닫혀 끝없이 다시 잇는다. 경로마다 다른 것은 둘이다. 시작과 이어 가기의 응답이 시작 항목 전에 끝나면 새 실행이 서지 않은 것이라 거절 표의 500 행이다. 결정의 응답이 `decided` 항목 전에 끝나면 거절 표의 결정 행이다. (명세가 정했다: 마지막 항목으로 가르는 것) 서버는 15초마다 keepalive를 보내므로 45초는 그것을 셋 놓친 것이다. 위젯은 keepalive가 온 것을 api-client의 읽기가 내는 값으로 안다(위 api-client). 백로그를 넘겨 서버가 잘라 낸 스트림도 결말 없이 끝나 같은 길을 간다. (명세가 정했다: 45초)
- 끊기면 받은 것을 그대로 두고, 입력창 위 띠에 진행 표시와 "연결이 끊겨 다시 잇고 있습니다. 받은 내용은 그대로 있습니다."를 보이며, 마지막으로 받은 프레임의 `id`를 `Last-Event-ID`로 두고 그 실행을 구독한다. 간격은 1, 2, 4, 8, 16초이고 그 뒤로는 30초마다이며 끝이 없다. 붙으면 띠가 걷힌다. (명세가 정했다: 간격)
- 새로 고친 뒤 다시 붙을 실행이 있으면 `Last-Event-ID` 없이 구독해 처음부터 받는다. 멈춘 실행이면 승인 묻기가 다시 선다(ADR 0023).
- 구독에도 요청마다 토큰이 든다. 토큰은 요청을 시작할 때만 검증되므로 열린 스트림은 만료와 무관하다(ADR 0024).

### 상한(ADR 0023 이력 2026-10-23)

- **429의 `limit`마다 띠의 문구가 다르다.** 범위를 모르므로 그 사람의 몫으로 단정하지 않는다. 디자인의 "이미 끝나지 않은 실행이 있습니다."와 "다 썼습니다"를 아래처럼 바꾼다. (명세가 정했다)
  - `concurrent_runs`: "동시에 처리할 수 있는 요청이 가득 찼습니다. N초 뒤에 다시 보낼 수 있습니다."
  - `hourly_runs`: "한 시간 동안 받을 수 있는 요청 수에 닿았습니다. N분 뒤에 다시 보낼 수 있습니다."
  - `subscriptions`: 구독에서만 난다. 위 표의 재접속 띠 문구다. 디자인의 제안("연결이 끊겨 5초 뒤에 다시 잇습니다.")은 기다리는 까닭이 상한이라는 것을 말하지 않아 바꿨다.
  - 모르는 값: "요청이 많아 N초 뒤에 다시 보낼 수 있습니다."
- **기다릴 시간.** `Retry-After`의 초이고, 없거나 읽지 못하면 5초다. 60초 이상이면 분으로 올려 적는다(디자인의 "12분 뒤"). 띠의 숫자는 매초 줄지만, 화면 읽기 프로그램에는 띠가 설 때 한 번, 시간이 다 되어 "이제 다시 보낼 수 있습니다."로 바뀔 때 한 번 읽힌다. 줄어드는 숫자는 `aria-hidden`이다. (명세가 정했다: 5초와 분으로 올리는 것)
- 시작과 이어 가기의 429에서는 시간이 다 되면 띠가 "이제 다시 보낼 수 있습니다."로 바뀌어 다음에 보낼 때까지 남는다. 저절로 다시 보내지 않는다.

### 입력창 위의 띠 — 위젯 앱의 부품(사용자가 골랐다)

- 디자인이 손으로 엮은 `<div role="status">` 여덟(재접속 둘, 상한 셋, 승인 기다림 셋)을 위젯 앱의 부품 하나로 짓는다. 디자인 시스템의 디자인 토큰, `Icon`, `Progress`를 쓰고, 띠 때문에 디자인 시스템 패키지의 컴포넌트와 Claude Design의 카드를 바꾸지는 않는다. 판정은 위젯의 Storybook(분류 판정, 접근성, 사진 비교)이다.
- 모양은 화면 그대로 위 테두리 한 줄이고, 앞에 아이콘이나 진행 표시 하나, 그 뒤에 글이 온다. 띠는 한 번에 하나만 서고, 여럿이 겹치면 재접속, 상한, 승인 기다림의 차례로 앞의 것을 보인다. (명세가 정했다: 하나만 서는 것과 그 차례)
- `role="status"`이고 글이 바뀔 때 한 번 읽힌다.

### 접근성

화면 디자인의 `mk-a11y` 메모를 결정으로 받아들인다. (명세가 정했다)

- 포커스 차례는 위쪽 띠의 "새 대화" → 대화 영역 → 대화 안의 버튼(펼치기, 알림의 버튼, 승인 카드) → 입력창 → 보내기다. 대화 영역은 스크롤 자리라 키보드로 스크롤하도록 포커스를 받는다(티켓 05의 "이 티켓이 정한 것" 1). 포커스 표시는 디자인 시스템의 것을 쓴다.
- 승인 묻기가 서면 포커스가 카드의 제목으로 가고, 결정한 뒤에는 결과 줄로 간다. 입력창이 다시 열려도 포커스를 옮기지 않는다.
- 보이는 대화 목록 자체는 화면 읽기 프로그램이 저절로 읽는 영역이 아니다. 목록에 `aria-live`나 `role="log"`를 달지 않고, 읽는 일은 아래 숨긴 영역 하나가 맡는다. 둘 다 읽히면 같은 줄이 두 번 들린다.
- 숨긴 `role="status"` 영역 하나가 새 도구 줄("orders.lookup 성공", "orders.lookup 실패"), 끝난 출력, "승인이 필요합니다: payments.refund"를 차례로 한 번씩 읽는다. 진행 표시의 "부르는 중"은 이 영역이 읽지 않는다. 이름표가 자주 바뀌어 소음이 되기 때문이다. (명세가 정했다: "부르는 중"을 읽지 않는 것)
- 실패와 거절의 위험 알림은 `role="alert"`이고(알림 부품의 위험 색이 그렇다), 정보 알림은 `role="status"`다. 알림과 띠가 같이 서면 알림이 먼저 읽힌다.
- 움직임 줄이기 설정에서는 진행 표시의 도는 모양이 멈춘다(디자인 시스템의 아이콘이 `motion-reduce:animate-none`을 단다).
- 포인터 대상은 24px 이상이다(시작 프롬프트).

### nginx와 배포(ADR 0024와 그 이력 2026-10-24)

- 운영의 배치는 ADR 0024 그대로다. 위젯 페이지와 최종 사용자 경로는 TLS를 끝내는 역방향 프록시 뒤의 한 출처에 서고, 프록시는 최종 사용자 접두사(`/end-user/`)를 파이썬에, 위젯 경로(`= /widget`과 `/widget/`)를 Next에 넘기며 나머지를 막는다. 운영의 인증서는 운영자가 마련한다(ADR 0011 이력 2026-10-03).
- **프록시 설정의 틀(`deploy/nginx/`)과 실제 nginx로 하는 판정은 이 기능에서 뺐다**(사용자가 06 구현 중에 골랐다, 일지 2026-10-24-10). 운영자가 설정을 스스로 짓는다. 그때 지킬 것은 ADR 0024의 nginx 항목(정규화한 경로를 넘기기, `proxy_http_version 1.1`, `X-Forwarded-*` 덮어쓰기, 끝 슬래시 없는 위젯 경로, SSE를 모으지 않기)이 원천이다. 위젯 e2e는 같은 출처를 시험 안의 작은 중계로 만들고(아래 Testing Decisions 4), 그 중계는 nginx의 경로 정규화와 버퍼링을 흉내 내지 않는다.
- 프록시의 본문 상한은 240,091바이트 이상이어야 한다. 요청 글자 수로 묶인 본문(시작, 이어 가기) 가운데 가장 큰 것은 요청 글자 수 20,000이 모두 BMP 밖 글자이고 인코더가 그것을 `\u` 이스케이프(서로게이트 둘, 글자 하나에 12바이트)로 쓴 것이다. 파이썬 `json.dumps`의 기본이 그렇고, 가장 긴 에이전트 이름(63자)과 그 요청을 든 시작 본문이 240,091바이트였다. 위젯이 쓰는 `JSON.stringify`는 이스케이프하지 않아 같은 본문이 80,088바이트였다(둘 다 `uv run python`과 node로 손으로 봤다). 위젯 밖의 클라이언트도 같은 경로를 부를 수 있으므로 가장 큰 쪽에 맞춘다. 사이트 파일에서 `request_chars`를 올리면 이 상한도 그 수 × 12에 1KB를 더한 값 이상이어야 한다. 결정 본문의 거부 사유는 서버가 길이를 묶지 않으므로, 위젯 밖의 클라이언트가 프록시의 상한보다 큰 사유를 보내면 파이썬의 422가 아니라 프록시의 413이 답할 수 있다. 위젯은 사유에도 요청 글자 수 상한을 둬(위 승인 묻기) 그 경계에 닿지 않는다. (명세가 정했다: 셈. 이 셈을 적을 틀은 위 줄대로 범위 밖이다)

## Testing Decisions

좋은 테스트는 바깥에서 보이는 행동을 본다. core에서는 소비자가 받은 이벤트의 차례와 시점, 서버에서는 HTTP 응답, 위젯에서는 화면에 보이는 글과 역할이다. 위젯의 조회는 역할과 이름으로 한다. 구현의 이름(내부 상태, 신호의 모양)은 단언하지 않는다. 시점은 잠이 아니라 이벤트로 맞추고, 기다리는 시험마다 시간 제한을 둔다. TS 시험의 이름은 행동을 말하는 한국어 문장이다(`.claude/rules/web-workspace.md`).

사용자가 고른 이음매는 여섯이다(일지 2026-10-23-40). 그 앞에 서버의 두 층이 있다.

**core.** `tests/core/test_run.py`이고, 선례는 `ClosingAgent`의 시험들(정리 코드가 어느 태스크에서 도는지)이다.

- 모델 호출이 도구 호출을 들었을 때, 그 도구가 불리는 순간 소비자는 이미 그 `llm_called`를 받았다. 가짜 도구가 불릴 때 소비자가 받은 이벤트의 목록을 남겨 본다. 도구 호출의 `tool_called`도 다음 모델 호출 전에 소비자에게 닿는다.
- `llm_called`를 트레이스에 쓰다 실패하면 그 도구는 불리지 않는다(가짜 도구가 불린 수가 0이다).
- `asyncio.gather`로 함께 부른 도구 둘은 둘 다 시작한 뒤에야 끝난다. 둘이 서로를 기다리는 악수가 제한 시간 안에 풀리는지로 본다.
- 정리 코드의 태스크를 단언한 시험(`test_런타임이_멈춘_에이전트의_정리_코드는_실행이_끝나기_전에_같은_태스크에서_돈다`, 매개변수 세 사례)은 "에이전트를 돌린 태스크에서 돈다"로 바뀌고 이름도 그 뜻으로 바뀐다. `contract_mutations.toml`의 변이가 세 사례의 바뀐 단언에서도 빨개지는지 다시 본다.
- 소비자가 실행 도중 스트림을 닫으면 에이전트의 태스크가 취소되고 정리 코드가 돌며 실행이 제한 시간 안에 끝난다.
- 런타임이 에이전트 자리에서 던진 실패는 같은 객체로 몸통에 닿는다. 지금의 `_Thrown` 시험이 그대로 초록이다.
- 지금의 시험 전부가 초록이다. 시제품은 그 가운데 `tests/core`, `tests/channel`, MCP 어댑터 시험의 553개를 둘째 실행에서 모두 지났다. 첫 실행에서는 `tests/channel/cli/test_interrupt.py`의 Ctrl+C 시험 둘이 다른 세션들의 부하 아래(CPU 88%)에서 실패했다. 그 시험의 자식은 `core/run.py`를 import하지 않아 부하 몫으로 보았지만, 부하 아래에서만 나는 패치 몫의 실패는 가르지 못했다(프로브 README의 2026-10-23 결과). 구현 티켓에서 그 둘이 빨개지면 이 단서부터 본다.

**서버의 계약.** `tests/channel/http/test_end_user.py`와 항목의 단위 시험이고, 선례는 그 파일의 "구독", "상한", "계약" 절이다.

- `tool_calls`가 든 `llm_called`는 `calling` 항목(도구 이름의 차례)이 되고, 빈 것은 항목이 없다. 프레임의 `id`는 그 이벤트의 인덱스다.
- 실제 앱을 지나는 시작의 스트림에서, 가짜 도구는 시험이 HTTP로 `calling` 프레임을 받은 뒤에야 끝난다. 에이전트는 `ctx.llm()` 한 번의 루프가 그 도구를 부르는 모양(저장소의 계산 에이전트와 같다)이다. 시험은 스트림을 둘째 구동자(이 파일의 "둘째 구동자" 절)로 읽어 그 프레임을 본 뒤 도구를 풀고, 실행이 제한 시간 안에 결말에 닿는지로 본다. 지금 core에서는 그 프레임이 도구가 끝난 뒤에야 나오므로 제한 시간에 걸려 빨개진다. 차례만 보는 시험은 지금 core에서도 초록이라 실시간 중계를 가르지 못한다. 이 시험은 `calling` 항목과 실시간 중계가 둘 다 있어야 초록이라, 계약 티켓 뒤에 오는 core 티켓이 든다(Further Notes의 티켓 차례).
- 429 봉투의 `limit`이 상한마다 맞다. 동시 실행의 세 범위는 모두 `concurrent_runs`, 시간당의 두 범위는 `hourly_runs`, 구독은 `subscriptions`다. `openapi.json`의 최신성 시험은 그대로 초록이고, 봉투를 단언하는 시험 둘은 위 계약 절의 규칙(최종 사용자 경로 넷의 429만 `LimitEnvelope`)으로 고쳐 초록이다. 생성 타입에서 429 응답의 `limit`이 늘 있는 값으로 좁혀지는 것은 api-client의 타입 시험이 본다.
- 운영자 `/runs`의 스트림에서도 같은 모양으로, 가짜 도구가 시험이 `llm_called` 프레임을 받은 뒤에야 끝난다(운영자 채널 시험이 선례다). core만 있으면 초록이라 core 티켓이 든다.
- 허용 출처 표기 픽스처의 사례마다 사이트 파일 읽기가 지나거나 막히고, 막히면 serve의 구성 오류 문구가 그 항목을 말한다(`tests/test_main.py`의 사이트 파일 절이 선례다).
- 커밋한 TOML 사이트 파일 픽스처 하나(사이트 둘, 그 가운데 하나만 기본값보다 작은 `request_chars`를 적는다)를 파이썬의 사이트 파일 읽기가 읽어, 합친 허용 출처와 가장 작은 글자 수 상한이 아래 5의 Node 시험이 같은 파일에서 끌어낸 값과 같다는 것을 고정한다. 두 언어의 시험이 같은 기대값을 하나의 JSON에서 읽는다. Node 파서가 키 경로를 잘못 읽으면 위젯은 조용히 20,000을 쓰고 서버는 422를 내는데, 그 갈림을 다른 시험은 보지 않는다. (명세가 정했다: 두 언어가 같은 사이트 파일을 읽는 것)

1. **화면 동작 테스트(vitest `widget-pages`, jsdom).** 위젯의 화면을 light DOM에 그리고(ADR 0024의 테스트 항목), 바깥 경계인 HTTP 하나만 가짜로 둔다. 가짜는 MSW이고 최종 사용자 경로 넷과 스트림 프레임(`id`와 `data`)을 생성 타입으로 흉내 내며, 처리하지 않은 요청은 실패다. 선례는 관리 화면의 페이지 시험과 `apps/admin/testing/`이다. 아래가 시험이다.
   - 위 "요청이 거절될 때"의 행마다, 실패 원인의 행마다, 끝내지 못함(스토리 31).
   - 진행 표시 이름표의 규칙(`calling`, `progress`, 거부, 직접 호출, 다시 붙기), 결말 뒤의 접힘 줄("도구 N개를 불렀습니다")과 그 `aria-expanded`(스토리 6).
   - 다음 요청이 이어 가기인지 시작인지와 저장 절의 상태 옮김(스토리 9), 새 대화가 막히고 열리는 때와 누르면 저장과 화면을 비우고 스트림을 끊는 것(스토리 11).
   - 저장(묶음이 다르면 지움, 토큰 전에 그리지 않음, 용량, 판이 다르거나 모양이 틀리면 지움, 저장하지 않는 것).
   - 재접속의 간격과 45초 무응답(가짜 시계. keepalive 블록이 오는 동안은 끊김으로 세지 않는다), 끊김을 마지막 항목으로 가르는 것.
   - 상한의 기다림과 읽기.
   - 사유를 다듬는 글자(U+001C~U+001F와 U+0085만 든 사유는 "거부"가 막히고, U+FEFF만 든 사유는 막히지 않는다. 스토리 18).
   - 글자 수의 90% 표시와 넘었을 때의 글, 그 글의 `aria-describedby`(스토리 36).
   - Enter는 보내고 Shift+Enter와 조합 중(`isComposing`)의 Enter는 보내지 않는다. jsdom 30.1.1은 `KeyboardEvent`의 `isComposing`을 그대로 넘겼다(`node -e`로 `web`에 깐 jsdom을 불러 `new KeyboardEvent('keydown', {key: 'Enter', isComposing: true})`의 값을 찍어 손으로 봤다).
   - 숨긴 `role="status"` 영역이 새 도구 줄, 끝난 출력, 승인 묻기를 차례로 한 번씩 읽고 "부르는 중"은 읽지 않는 것(스토리 38).
   - 포커스의 옮김, 속성 검사, `data-density`.

   MSW는 도중의 끊김을 만들지 못하므로 결말 없이 닫는 것으로 만든다(`apps/admin/testing/stream.ts`의 주석). shadow root는 마운트만 단위 시험이 본다. 스크롤은 jsdom이 레이아웃을 하지 않아(같은 `node -e`에서 `height: 50px; overflow: auto`인 상자에 문단 둘을 넣어도 `scrollHeight`가 0이었다) 여기서 재지 않고 3이 본다.
2. **api-client 단위 테스트(vitest `node`).** 선례는 `packages/api-client/src/stream.test.ts`와 `clients.test-d.ts`다. 프레임의 `id`를 읽고, 항목을 술어로 좁히며(`calling` 포함), 모르는 `type`이 원문이 되고, `data` 없이 주석만 든 블록이 keepalive 값이 되며(그 파일의 `streamOf`로 조각을 넣는다), 구독이 `Last-Event-ID` 헤더를 보낸다. 타입 시험은 위젯 클라이언트가 운영자 경로를 받지 않는 것과, 429 응답의 `limit`이 늘 있는 `LimitKind` 값으로 좁혀지는 것을 본다.
3. **위젯 스토리(위젯의 Storybook, vitest `widget-storybook`, 사진 비교).** 실제 브라우저에서 폭 320px과 400px마다 organisms(대화, 승인 묻기, 실패 알림, 재접속, 상한)와 띠 부품을 그려 분류 판정(`@agent-os/ui/testing`), 접근성(addon-a11y), 사진을 본다. 디자인 시스템 패키지의 스토리가 선례다. 대화의 스토리 시험이 스크롤도 본다. 끝을 보고 있을 때 새 내용이 오면 끝으로 내려가고, 위로 올려 둔 동안에는 그 자리에 머문다.
4. **e2e(Playwright, CI 잡 `e2e-widget`).** 실제 브라우저, 사이트 파일과 RS256 키를 준 실제 `serve`, 그 사이트 파일로 빌드한 실제 Next, 둘을 한 출처 아래에 모으는 시험 안의 작은 중계(`/end-user/`는 serve로, `/widget`과 `/widget/`은 Next로, 나머지는 404. nginx 대신이다, 위 "nginx와 배포"), 그리고 다른 출처의 사이트 페이지 하나에 두 임베드를 넣는다. 선례는 관리 화면 e2e의 준비(`apps/admin/e2e/stack.ts`)다. 키와 토큰은 `node:crypto`가 짓는다. TLS는 두지 않고, 출처는 모두 `*.localhost` 호스트 이름이다(브라우저가 보안 맥락으로 본다). 에이전트는 임시 플러그인 루트에 짓는, 모델 없이 도는 것들이다. 도구를 직접 부르는 것, 승인 대상에서 멈추는 것, 출력에 HTML 조각을 내는 것, 새로 고치는 동안 끝나지 않는 것이다. 보는 것은 아래와 같다.
   - 다른 출처의 사이트 페이지에서 `<script src>` 한 줄로 element 번들이 실리고, 번들이 읽은 기준 주소로 최종 사용자 경로를 부른다. `crossorigin="anonymous"`를 붙인 `<script>`로도 실린다.
   - 번들의 `<script>` 앞에 `<img name="currentScript" src="https://<다른 출처>/">`를 둔 사이트 페이지에서, 그 출처로는 요청이 하나도 가지 않고 토큰 함수가 불리지 않으며 위젯은 위험 알림을 보인다.
   - 두 임베드의 토큰 넘기기. 부모가 아니거나 허용 밖 출처에서 온 postMessage는 버려진다. e2e는 부모가 아닌 보낸 쪽(같은 허용 출처의 형제 프레임, 허용 밖 출처의 프레임)을 본다. 부모이면서 허용 밖 출처인 보낸 쪽은 `frame-ancestors`가 먼저 막아 e2e에서 만들 수 없고, 그 갈래는 위젯의 페이지 시험(jsdom)이 본다.
   - 페이지 안 방식의 CORS. 허용 출처의 페이지에서는 읽히고 허용 밖 출처에서는 읽히지 않는다.
   - `frame-ancestors`. 허용 출처는 iframe을 품고 허용 밖은 품지 못한다.
   - Shadow DOM의 격리와 `data-density`. 사이트의 `letter-spacing`과 `html { font-size: 10px }`가 위젯의 크기를 바꾸지 않고, 위젯의 CSS가 사이트로 새지 않는다.
   - 출력의 HTML 조각이 실행되지 않는다.
   - 새로 고친 뒤 도는 실행과 멈춘 실행에 다시 붙는다.
   - 글꼴이 위젯 출처에서 `Access-Control-Allow-Origin`과 함께 온다.
   - CSP가 `style-src 'self'`인 사이트 페이지에서 페이지 안 위젯이 스타일을 갖는지. 막히면 임베드 안내의 CSP 자리에 `style-src`를 더하고, 이 사례는 그 자리를 열어 둔 페이지에서 스타일이 서는 것을 본다.
   - 입력창의 글자 수 상한이 서버의 기본값과 같다. 서버에 직접 보낸 20,000자는 받고 20,001자는 422다.
   - SSE가 결말 전에 흐르는 것. 도구를 직접 부르는 에이전트가 다음 도구에서 기다리는 동안 첫 도구 줄이 위젯 화면에 서 있는 것으로 본다. core의 실시간 중계와 중계가 응답을 모으지 않는 것이 함께 있어야 초록이다. nginx의 사례(80과 443, HSTS, 우회 경로, 대소문자, 본문 크기의 경계)는 범위 밖이다(위 "nginx와 배포").

   CI에서는 관리 화면의 `e2e` 잡과 같은 모양으로 돌고, 필수 검사 `verify`의 `needs`에 더한다. 로컬에서는 위젯, api-client의 위젯 몫, 서버의 최종 사용자 경로를 건드렸을 때 친다. `CLAUDE.md`의 검증 명령 절에서는 셋을 고친다. web 줄의 괄호에 그 명령과 치는 때를 더하고, "게이트는 열다섯"을 열여섯으로, "남은 둘인 e2e와 사진 비교는 CI만 돈다"를 위젯 e2e까지 셋으로 바꾼다. (명세가 정했다: 잡을 따로 두는 것)

   새 잡은 그 셋 밖의 닫힌 문장도 거짓으로 만든다. CI 잡의 수, 매 푸시에서 도는 e2e의 수, 실제 `serve`를 띄우는 구동자의 수를 세어 닫은 문장과, 실제 uvicorn·사이트 파일·서명 토큰의 조립을 지나는 자리를 "유일한"으로 닫은 문장이다. 잡을 더하는 티켓이 그런 말(잡의 수, "e2e 하나", "구동자", "유일한 자리")로 저장소를 grep해 살아 있는 문서의 잔존을 0으로 만든다. 지금 아는 자리는 다섯이다. `docs/constitution/tech.md` 원격·CI 행의 "잡 다섯"(헌법 문서이므로 `docs/constitution/README.md`의 판을 patch로 올리고 `tools/check_constitution_version.py`가 그것을 본다), `.claude/rules/http.md`의 "실제 `serve`의 둘째 구동자인 관리 화면의 e2e"와 "매 푸시에서 도는 것은 e2e 하나다", `tests/test_main.py`의 최종 사용자 경로 LLM 시험 독스트링의 "실제 실행으로 보는 유일한 자리다", 같은 파일의 serve 판정 시험 독스트링의 "매 푸시에서 도는 관리 화면의 e2e(실제 serve 의 둘째 구동자)", `web/apps/admin/e2e/stack.ts` 머리 주석의 "e2e 는 실제 `serve` 의 둘째 구동자이고"이다(뒤의 둘은 PR 직전 리뷰가 찾았다). "구동자"는 같은 앱을 ASGI로 직접 부르는 시험의 이름이기도 하다(`docs/constitution/tech.md`의 같은 절, `tests/channel/http/test_end_user.py` 머리). 그 뜻의 일치는 고치지 않고, 위젯 e2e를 부를 이름이 그 이름과 겹치지 않게 한다.

5. **허용 출처 표기 픽스처와 사이트 파일.** 파이썬(사이트 파일 읽기)과 Node(위젯 빌드 설정의 시험)가 같은 JSON 파일의 사례를 읽어 같은 판정을 고정한다. 빌드 설정의 시험은 관리 화면의 `next.config.test.ts`가 선례이고, 변수가 없을 때의 `frame-ancestors 'none'`과 기본값 20,000, 변수가 준 파일이 없거나 깨졌을 때의 빌드 실패, 위 "서버의 계약"에 둔 TOML 사이트 파일 픽스처에서 끌어낸 두 값도 거기서 본다. 픽스처 둘과 두 언어의 판정은 한 티켓에 든다. 갈라 들이면 먼저 들어온 쪽의 판정을 다른 언어가 고정하지 않는 사이가 생긴다.
6. **실제 모델 e2e(사용자가 골랐다).** 위젯 e2e에 Playwright 프로젝트 `llm`을 두고, 저장소의 계산 에이전트(`plugins/agents/calc`)로 위젯에서 요청 하나를 보내 출력이 서는 것까지 본다. 모델이 도구를 부를지는 단언하지 않는다. 그 프로젝트는 마커 `llm_widget`을 단 파이썬 시험 하나가 자식 프로세스로 돌린다. 그 프로젝트는 감싸는 시험이 자식의 환경에 준 `AGENT_OS_WIDGET_LLM=1`이 있을 때만 Playwright 설정의 프로젝트 목록에 들고, 없으면 목록에 없다. 그래서 위의 로컬 명령(프로젝트를 지정하지 않은 `playwright test`)과 CI의 `e2e-widget`은 플래그 없이 그 프로젝트를 돌리지 않는다. CI에서만 빼면 실제 모델 e2e가 병합된 뒤로 로컬 명령이 실제 모델을 부르고, 키가 없는 셸에서는 위젯 e2e가 빨개진다(PR 직전 리뷰). 그 설정은 위젯 앱의 vitest `node` 시험이 변수가 없을 때와 있을 때의 프로젝트 목록으로 본다. 명령은 `uv run --env-file .env pytest -m llm_widget`이고, 원칙 I의 판정 명령(`-m llm`)과 따로다(사용자가 명세 검토 뒤에 골랐다). 위젯은 같은 출처의 중계를 거쳐서만 최종 사용자 경로에 닿아, `-m llm`에 넣으면 core나 채널을 고칠 때마다 Next·Vite 빌드와 브라우저가 있어야 하고 없으면 원칙 I의 판정이 빨개지기 때문이다. 그 마커는 `pyproject.toml`에 선언하고 기본 실행의 제외(`addopts`의 `-m`)에도 더한다. 키가 없으면 실패하는 규칙과 토큰 합계 줄은 지금의 LLM 시험과 같다. 토큰 합계는 `tests/conftest.py`가 `llm`과 함께 `llm_widget` 마커의 시험도 세게 고치고, 그 시험이 `tmp_path`를 트레이스 자리로 넘긴다. 손으로 치는 때는 위젯, api-client의 위젯 몫, 서버의 최종 사용자 경로와 항목의 투영을 건드렸을 때다. core만 고친 작업은 이 명령을 치지 않고, 위젯까지의 길은 CI의 `e2e-widget`이 모델 없는 에이전트로 본다. 파이썬 시험이 감싸는 까닭은 키가 없으면 실패하는 규칙과 토큰 합계 줄이 지금의 LLM 시험과 한 길로 남기 때문이다. 그 시험은 pnpm을 이름이 아니라 `shutil.which("pnpm")`이 준 경로로 띄운다. 이 PC의 Windows에서는 `uv run --env-file` 아래의 pytest가 `pnpm`을 이름으로 띄우지 못했고(`FileNotFoundError`. uv가 직접 띄워도 `Failed to spawn: pnpm`), 그 경로(`pnpm.CMD`)로는 띄워 `.env`의 값이 손자 node까지 닿았으며 Playwright도 떴다(`.scratch/web-widget/probes/pnpm_spawn.py`로 쟀다, README의 2026-10-23 결과). Playwright가 다시 띄우는 `serve`까지 값이 닿는지는 재지 않았다. 관리 화면 e2e의 준비가 serve의 환경에 부모의 환경을 펼치므로(`apps/admin/e2e/stack.ts`를 읽었다) 그것을 본뜨면 닿고, 아래 둘째 기준이 실행 때 그것을 확인한다. 그 시험의 기준은 다섯이다. (명세가 정했다: 파이썬 시험이 감싸는 것과 그 기준)
   - Playwright의 JSON 리포터로 통과 1, 건너뜀 0을 단언한다. 종료 코드 0만 보면 Playwright 쪽에서 모두 건너뛴 실행이 초록이 된다.
   - `tmp_path`를 serve의 트레이스 자리로 넘기고, 거기 `llm_called`가 있음을 단언한다. 키가 serve에 닿지 않으면 모델 호출이 없어 빨개진다.
   - 화면에 선 출력이 그 트레이스의 `run_finished`의 `output`과 같다.
   - `shutil.which("pnpm")`이 없으면 pnpm을 깔라는 문구로 실패한다.
   - 제한 시간에 걸리면 Playwright가 띄운 프로세스까지 정리한다. `.cmd`를 거친 자식을 끊어도 손자 node가 남을 수 있다. 명세 검토가 임시 스크립트로 손으로 봤다고 보고했고(출력 파이프 없이 끊은 회차에서 손자가 살아 있었다고 했다), 그 명령은 남지 않았다. 넘기는 인자는 고정 글자이고 cmd.exe의 메타 문자(`&`, `^`, `%`)가 들지 않는다.

   Playwright 프로젝트 `llm`, 그것을 감싸는 시험, 마커와 conftest의 셈, 그 프로젝트를 변수가 있을 때만 세우는 설정과 그 시험, `docs/constitution/operations.md`의 LLM 테스트 절, `CLAUDE.md` 검증 명령 절의 첫 괄호(위젯의 실제 모델 e2e의 명령과 치는 때)와 pre-commit이 갈음하지 않는 것을 든 문장(`-m llm` 곁에 `-m llm_widget`)은 한 티켓에 든다. 갈라 들이면 키 없는 CI가 실제 모델을 부르거나, 아무도 돌리지 않는 프로젝트가 생긴다(명세 검토). ADR 0024 이력 2026-10-23 "실제 모델을 부르는 위젯 e2e는 LLM 시험 하나가 감싼다"가 이것을 든다.

   새 마커는 LLM 시험이 모두 `llm` 마커이고 기본 실행이 그 하나만 뺀다고 닫은 문장과, 사이트 파일과 서명 토큰의 조립을 실제 소켓과 실제 모델로 지나는 자리를 "유일한"으로 닫은 문장을 거짓으로 만든다. 같은 티켓이 그런 말(`llm` 마커와 백틱 없이 쓴 llm 마커, `-m "not llm"`, `-m llm`, "유일한 자리")로 저장소를 grep해 살아 있는 문서의 잔존을 0으로 만든다. `-m llm`의 일치에는 그 명령을 그대로 안내하는 문장도 들어, 하나씩 읽어 닫은 문장만 고친다. 지금 아는 자리는 `tests/conftest.py`의 독스트링, `tests/test_main.py` 머리 독스트링의 "llm 마커가 붙은 것만 실제 모델을 부른다", `tests/test_conftest.py`의 기본 실행을 `-m "not llm"`으로 적은 독스트링 둘, `tools/llm_tokens.py` 머리 독스트링, `.coderabbit.yaml`의 "llm 마커 없이 기본 실행에 들어가는지", `tools/hook_env_read.py`가 LLM 테스트 명령으로 `-m llm`만 안내하는 문구(앞의 다섯은 PR 직전 리뷰가 찾았다), `.claude/rules/tests.md`의 "LLM을 실제로 호출하는 테스트는 `llm` 마커를 붙인다", `docs/constitution/operations.md` LLM 테스트 절의 같은 문장과 "기본 `pytest -q`는 이 마커를 제외한다"(헌법 문서이므로 판을 patch로 올린다), `.claude/rules/http.md`의 "실제 소켓과 실제 모델로 지나는 유일한 자리다"이다. conftest가 `llm_widget` 시험도 세는 것은 그 셈의 pytester 시험(`tests/test_conftest.py`의 토큰 합계 시험이 선례)이 먼저 빨갛게 본다.

## Out of Scope

- **429 봉투에 상한의 범위(주체별, 사이트별, 전역)를 싣는 것.** 사용자가 고른 안의 조건이다(ADR 0023 이력 2026-10-23).
- **`calling` 항목에 인자를 싣는 것.** 화면이 이름만 쓴다.
- **출력을 마크다운으로 그리는 것.** ADR 0024가 원시 HTML을 끈 렌더러라는 조건으로 날을 남겼다.
- **사이트마다 다른 요청 글자 수 상한을 위젯이 가려 적용하는 것.** 위젯은 가장 작은 값 하나를 쓴다.
- **같은 페이지에 같은 에이전트의 위젯 둘.**
- **웹뷰 앱이나 브라우저 확장(http(s)가 아닌 스킴의 출처)에 위젯을 넣는 것.** 허용 출처의 표기가 그 스킴을 막는다. 그것을 맡을 기능이 계획에 없어 넘기지 않는다.
- **element 번들의 무결성 해시(SRI).** 번들의 경로에 판이 없어 위젯을 다시 빌드할 때마다 해시가 바뀐다. 판을 붙인 경로로 내는 일은 이 기능 밖이다.
- **사이트 페이지에서 위젯을 여닫는 단추와 전체 화면 모드.** 위젯은 사이트가 준 자리를 채우고, 그 자리를 여닫는 것은 사이트의 몫이다.
- **글꼴 양의 예산과 다시 재기.** 예산을 다루는 기능이 계획에 없어 다른 기능에 넘기지 않는다.
- **관리 화면에서 도는 실행을 실시간으로 보는 화면.** 이 기능은 운영자 `/runs` 스트림을 실시간으로 만들 뿐이고, 관리 화면은 지금처럼 트레이스를 읽는다. 그 화면을 맡을 기능이 계획에 없어 넘기지 않는다.
- **한국어 밖의 언어.**
- **타임아웃 뒤의 MCP 서버 프로세스.** mcp-shutdown으로 갔다(plan.md 행).
- **역방향 프록시 설정의 틀(`deploy/nginx/`)과 실제 nginx로 하는 판정(80과 443, HSTS, 우회 경로, 대소문자, 본문 크기의 경계).** 사용자가 06 구현 중에 이 기능에서 뺐다(일지 2026-10-24-10, ADR 0024 이력 2026-10-24). 운영자가 설정을 짓고, 지킬 것은 ADR 0024의 nginx 항목과 위 "nginx와 배포"의 본문 상한이다. 그것을 맡을 기능이 계획에 없어 넘기지 않는다.

다른 기능에 새로 넘기는 것은 없다. 위의 mcp-shutdown은 이미 그 행이 받았다.

## Further Notes

- **티켓의 차례.** 계약 티켓(`calling`, `limit`)이 기능의 첫 티켓이고(`docs/agents/issue-tracker.md`), core의 실시간 중계 티켓이 그 뒤다. 최종 사용자 스트림의 실시간 시험이 `calling` 항목과 실시간 중계가 둘 다 있어야 초록이라, 그 시험을 드는 core 티켓을 계약 뒤에 둔다. 나란히 두면 그 시험이 들 티켓이 정해지지 않는다(명세 검토). core 티켓은 실제 서버를 띄우는 위젯 e2e 티켓부터 막는다. 사용자가 고른 안의 설명은 "그 티켓이 위젯 티켓을 막습니다"였고, to-tickets에서 사용자가 대화 화면을 core와 나란히 두는 나누기를 골랐다. 대화 화면은 MSW로 시험해 core 없이 지을 수 있다. 위젯 앱의 뼈대와 빌드(사이트 파일 입력, 표기 픽스처와 두 언어의 판정)도 실행의 이벤트를 쓰지 않아 계약·core와 나란히 갈 수 있다. api-client의 위젯 클라이언트는 계약 뒤이고, 화면들과 e2e가 그 뒤다. 나눈 티켓은 `.scratch/web-widget/issues/`다.
