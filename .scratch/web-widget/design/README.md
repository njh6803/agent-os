# web-widget 화면

위젯의 완성 화면이다. `/ui-design web-widget`이 Design 아티팩트에 그리고 사람이 확정한 것을 그 스킬의 7단계가 옮겼다(일지 2026-10-23-20). 규약은 `docs/agents/issue-tracker.md`의 화면 디자인 절이고, 그린 순서와 화면은 시작 프롬프트 `screens-prompt.md`다. 그리며 `frontend-design`과 저장소 규칙이 부딪친 자리는 `.scratch/design-system/design/frontend-design-conflicts.md`의 2026-10-23 web-widget 행이다.

아티팩트에는 쪽이 둘이다. "와이어프레임"(아트보드 일곱, 회색조)과 "완성 화면"(아트보드 여덟)이고, 여기 옮긴 것은 완성 화면 여덟과 캔버스 색인 `canvas.json`이다. 와이어프레임은 아티팩트에만 남겼다. 그래서 `canvas.json`의 `boards`와 `order`는 여기 없는 와이어프레임 파일(`Main.dc.html`, `wf-*.dc.html`)도 가리킨다. 와이어프레임을 다시 보려면 아티팩트를 연다. 화면 파일은 디자인 시스템을 `ds/agent-os/` 아래에서 불러오고 그 폴더는 옮기지 않았다(스킬 7단계가 `project/ds/`를 뺀다). 화면 파일이 함께 부르는 `./support.js`는 아티팩트의 파일 목록(`list` `scope: "files"`)에 없고 `project/support.js`를 `read`하면 그 경로에 파일이 없다고 나와, 옮길 지원 파일이 아니다. 저장소에서 브라우저로 그려지는지는 보지 않았다.

와이어프레임에서 A·B 두 안을 그린 갈래는 둘이고, 사람이 고른 안(일지 2026-10-23-20의 6단계)으로 완성 화면을 그렸다.

- 대화의 위쪽 띠: A('새 대화'를 글자 버튼으로 늘 보인다). 고르지 않은 B는 줄임표 아이콘 버튼의 메뉴 안에 두는 것이었다. 디자인 시스템에 메뉴 부품이 없다.
- 승인을 기다리는 동안의 입력창: A(막힌 채 남기고 그 위 띠에 "승인이나 거부를 먼저 골라 주세요."). 고르지 않은 B는 입력창을 숨기는 것이었다.

그리며 둔 제안과 탐색용 가정이다. 결정이 아니고 명세가 결정으로 바꾸거나 다시 묻는다(시작 프롬프트 "고른 뒤" 2). 캔버스의 메모(`notes`의 `wf-how`, `mk-how`, `mk-a11y`)에도 적혀 있다.

- 409·500 거절 알림의 "다시 보내기" 버튼은 시작 프롬프트에 없던 제안이다.
- 연결 수 상한으로 5초 뒤 다시 붙는 띠의 문구("연결이 끊겨 5초 뒤에 다시 잇습니다. 받은 내용은 그대로 있습니다.")는 시작 프롬프트에 문구가 없어 지은 것이다.
- 첫 화면의 할 수 있는 일 한 줄("주문, 배송, 환불을 물어볼 수 있습니다.")은 사이트가 정하는 문장으로 가정했다. 위젯이 그 문장을 어디서 받는지는 근거 문서에 없다. 그 아래의 "아래에 요청을 적어 보내 주세요." 한 줄은 시작 프롬프트에 없던 제안이다.
- 지금 부르는 도구는 디자인 시스템 진행 표시(값 모름)의 이름표에 "<도구 이름> 부르는 중"으로 들어간다. 이름표는 글자열이라 도구 이름이 고정폭으로 보이지 않는다.
- 실패 알림의 버튼은 알림 부품의 `actions` 자리가 아니라 본문 안에 두었다. 캔버스에서 ReactNode를 넘길 수 없어서다.
- 보낼 때 거절된(429) 요청은 입력창에 남는다. 실행 실패와 401·409·500은 요청이 대화에 남은 채 출력이 올 자리에 알림이 선다. 404는 한 번 더 시도한 뒤 저장한 대화를 비우고, 정보 알림을 남긴 채 같은 요청을 새 대화로 보낸다.
- 기다리는 초는 화면 읽기 프로그램에 매초 읽히지 않는다. 키보드와 화면 읽기 프로그램의 나머지 제안(포커스 차례, 승인 묻기가 나타날 때와 결정한 뒤의 포커스, 살아 있는 영역)은 `mk-a11y` 메모다.
- 글자 수 상한 화면의 보내기 버튼 높이 맞춤은 어림이다.
- 위쪽 띠의 에이전트 이름 "주문 도우미", 예시 도구, 예시 실행 식별자, 예시 요청과 출력, 높이 560px은 시작 프롬프트의 탐색용 가정 그대로다. 예시 도구에는 `shipping.track`과 `refunds.policy`를 더했다.

옮긴 뒤 셀프 리뷰와 PR 직전 리뷰가 찾은, 화면이 계약이나 디자인 시스템과 어긋나는 자리다. 화면 파일은 아티팩트에서 받은 그대로 두었고(웹 편집 확인이 sha256으로 맞대므로), 어떻게 할지는 명세가 정한다.

- 알림의 제목. 실패·거절 화면의 알림과 재접속 화면의 끝내지 못함 알림은 모두 알림 부품(`Alert`)의 필수 `title`을 비우고 문구를 본문에 넣었다. 부품은 제목 자리를 늘 그리고 본문을 흐린 글자(`text-text-muted`)로 그리므로(`web/packages/ui/src/components/molecules/Alert.tsx`), 화면의 문구는 제목 없이 흐린 글자로 선다. 부품의 쓰는 법은 "제목에 일어난 일을, 본문에 까닭이나 할 일을 적습니다."다(`Alert.md`).
- 입력창 위의 띠. 연결이 끊긴 일, 상한, 승인을 기다리는 동안의 안내를 입력창 바로 위에 띄우는 띠 여덟(재접속 둘, 상한 셋, 승인 묻기 셋)은 알림 부품이 아니라 손으로 엮은 `<div role="status">`다. 일곱은 아이콘과 글자이고 재접속의 하나는 진행 표시 부품(`Progress`)이며, 모두 위 테두리 한 줄만 둔다. 디자인 시스템에는 띠 모양의 부품이 없고(`web/packages/ui/src/components`), 알림 부품은 둥근 모서리와 네 변 테두리와 올린 바탕을 가진 카드다(`Alert.tsx`의 `rounded-l border bg-bg-raised`). 띠를 새 부품으로 지을지, 알림 부품의 한 변형으로 쓸지, 앱이 짓는 패턴으로 둘지는 명세가 정한다.
- 404와 409의 범위. 시작 프롬프트의 거절 줄은 404를 이어 갈 실행이 없는 것으로, 409를 에이전트를 지금 쓸 수 없는 것으로만 읽었다. 계약은 더 넓다. 최종 사용자 면의 404에는 요청한 에이전트가 없거나 그 사이트의 열 에이전트 밖인 것도 들고, 409에는 꺼진 에이전트 말고도 결정을 받을 수 없는 실행의 상태(일시정지가 아니거나 지나간 자리 등), 아직 끝나지 않은 앞 실행, 구독의 `Last-Event-ID`가 트레이스의 마지막 자리보다 큰 것이 든다(`.claude/rules/channel.md`의 최종 사용자 면 항목, `src/agent_os/channel/http/end_user.py`의 라우트 주석). 시작 프롬프트의 거절 줄과 그 줄대로 그린 거절 화면을 따르면, 지나간 결정에도 "에이전트를 지금 쓸 수 없습니다."가 뜨고(결정의 거절은 그리지 않았다. 다음 항목), 에이전트가 없어 난 404에도 대화를 비우고 새 대화로 다시 보내 같은 404를 또 받는다.
- 결정의 거절. 시작 프롬프트의 거절 줄은 결정도 거절될 수 있다고 적지만, 결정을 보낸 뒤 거절되는 모습은 어느 화면에도 없다. 거절 화면과 상한 화면은 모두 시작이나 이어 가기의 요청 글이 대화나 입력창에 남는 모습이다. 결정 경로도 401·404·409·429·500을 내고, 결정도 동시 실행의 칸을 차지하고 시간당 셈에 들어 429를 받을 수 있다(`.claude/rules/channel.md`의 최종 사용자 면 항목과 상한 항목). 승인이나 거부를 보낸 뒤 거절되면 승인 카드의 버튼과 거부 사유 칸이 어떻게 되는지, 알림이 어디에 서는지, 상한의 "다시 보낼 수 있습니다"가 결정 버튼에 어떻게 걸리는지는 명세가 정한다.
- 상한의 종류와 범위. 계약의 429는 에러 코드 `too_many_requests` 하나이고, 어느 상한(동시 실행 수, 시간당 실행 수, 구독 수)인지는 봉투의 `message` 글에만 있다(`.claude/rules/http.md`의 예외 표 항목). 동시 실행 상한은 주체별·사이트별·전역 셋, 시간당 실행 상한은 주체별·사이트별 둘이고, 봉투는 그 가운데 어느 것인지 말하지 않는다(`src/agent_os/channel/http/limits.py`의 `_refusal`). 화면은 동시 실행, 시간당 실행, 연결 수를 갈라 그렸고, 동시 실행 문구("이미 끝나지 않은 실행이 있습니다.")는 사이트별·전역 상한에, 시간당 문구("한 시간에 보낼 수 있는 요청을 다 썼습니다.")는 사이트별 상한에 걸렸을 때 맞지 않는다. 사이트 전체의 상한에 걸린 사람은 자기 요청이 몇 건 안 되는데도 다 썼다는 말을 본다.
- 인자의 글자 꼴. 계약의 일시정지 항목은 인자를 객체(`PausedItem.args`)로 준다. 화면은 그것을 JSON 글자로 그렸고, 객체를 어떤 꼴의 글자로 바꿀지(들여쓰기, 키 차례)는 정하지 않았다.
- 끝내지 못함의 문구. "서버가 다시 시작해 이 실행을 끝내지 못했습니다."는 원인을 하나로 단정한다. 계약의 `UnfinishedItem`은 "실행이 끝내지 못하고 사라졌다."고만 하고, 첫 이벤트 뒤에 트레이스를 쓰지 못해 결말 없이 끝난 실행도 구독에서 이 항목이 된다(`.claude/rules/channel.md`의 실행의 태스크 항목과 구독 항목. 규칙을 읽은 것이고 재지 않았다).
