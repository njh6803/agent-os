# web-widget 화면 프롬프트

위젯의 화면 다섯(대화, 승인 묻기, 실패, 재접속 중, 상한에 걸림)을 그릴 때 그리는 쪽에 주는 시작 프롬프트다. 와이어프레임으로 배치를 먼저 고르고, 고른 배치를 UI mockups로 완성한다. 둘 다 디자인 시스템 아티팩트에 올린 디자인 시스템으로 그린다(ADR 0025와 그 2026-10-16·2026-10-20 이력). 확정한 화면은 명세 직전의 근거가 된다(`.scratch/plan.md`의 web-widget 행).

프롬프트에 든 것은 세 가지다. **결정**은 ADR 0022·0023·0024·0026·0031, `.scratch/plan.md`의 web-widget 행, 최종 사용자 면의 계약(`openapi.json`의 최종 사용자 항목 일곱과 에러, 실패 원인 아홉)과 상한 셋(계약에는 429 하나이고, 어느 상한인지는 봉투의 `message` 글에만 있다. `.claude/rules/http.md`)과 end-user-continuation 명세(`.scratch/end-user-continuation/spec.md`의 사용자 스토리 1~23, "실패 원인 — 목록", "최종 사용자 면의 404 덮기")가 정한 것이다. 위젯이 화면에 실을 수 있는 자료가 여기서 정해진다. 화면 문구의 말은 `CONTEXT.md`와 `.claude/rules/web-design.md`에서 왔다. **이 프롬프트의 제안**은 그리는 데 필요해서 더한 것이고 명세가 다시 정한다. 와이어프레임에서 고를 갈래, 실패 원인마다의 문구와 버튼, 404·500을 받은 뒤의 길, 화면마다 그릴 상태가 여기 든다. 계획 행이 "위젯이 정한다"고 넘긴 것(원인마다의 문구, 원인에 따라 권할 일, 404에 곧바로 지울지, 500이 거듭될 때 새 대화를 고를 길, 진행 표시의 "지금 하는 일" 자리)은 여기서 제안하고 명세가 정한다. 두 프롬프트의 "배치와 밀도"·"시각 방향"은 아래 "참고 디자인"에서 사람이 고른 방향이다(일지 2026-10-23-30). **탐색용 가정**은 자리 높이, 위쪽 띠의 에이전트 이름, 예시 값이고 두 프롬프트 끝의 "탐색용 가정"에 모았다.

옛 프롬프트(커밋 `8acd9a48`의 이 파일, 단독 Claude Design용)는 재료로만 썼다. 테마 다섯과 "먹" 테마, 원인 없는 실패 항목, 선택으로 둔 거부 사유는 그 뒤의 결정(design-refresh의 테마 넷과 녹청 기본, ADR 0031, 계약의 `Deny.reason` 최소 1자)과 어긋나 바꿨다. 재탐색 디자인 파일(`.scratch/design-system/design/Agent OS Design System.dc.html`)의 4.8 위젯은 자리 폭 320px, 밀도 보통, 창만 `shadow-float`, 요청은 오른쪽 상자이고 출력은 상자 없는 글, 화면 읽기 프로그램에만 들리는 "요청:"·"출력:" 머리말을 가져온다. 그 일시정지 줄의 "운영자의 결정을 기다립니다"는 가져오지 않는다. 최종 사용자의 실행은 그 사람이 승인자다(`CONTEXT.md`의 승인자). 디자인 시스템 아티팩트에는 그 파일의 패턴이 없어(admin-style의 시작 프롬프트와 같은 사정) 아래 두 프롬프트는 패턴을 번호가 아니라 모양으로 적는다.

## 하는 법

`/ui-design web-widget`으로 한다. 그 스킬이 순서의 원천이고, 이 파일은 그 스킬의 3단계가 쓰는 시작 프롬프트다(참고와 방향은 이미 골랐으므로 그 단계는 다시 묻지 않는다).

1. **디자인 시스템을 맞춘다(스킬 2단계).** 디자인 시스템 아티팩트의 `via`가 부분 올리기(`agent-os 부분 main@c41adad`)였고, 사람이 다시 올리지 않고 그리기를 골랐다(일지 2026-10-23-30). 전체 올리기는 design-reverse-sync 티켓 08이 맡는다.
2. **와이어프레임을 그린다(스킬 5단계).** 아래 "1. 와이어프레임"이 그릴 것이다. 아티팩트 하나에 와이어프레임과 완성 화면을 함께 두고 페이지로 가른다.
3. **안을 고른다(스킬 6단계).** A·B를 그린 갈래마다 사람이 하나를 고른다. 고른 안은 디자인 파일 안에도 적는다.
4. **완성 화면을 그린다(스킬 5단계).** 같은 아티팩트의 다음 페이지에 "2. UI mockups"를 그린다.
5. **저장소로 옮긴다(스킬 7단계).** 아래 "고른 뒤"가 이 기능의 표 칸이다.

## 참고 디자인

`kickoff/prompting.md`의 "참고 디자인 조사"대로 했다. 기준 화면은 관리 화면이고 위젯은 같은 시스템이 남의 사이트 안에서도 맞는지 보는 표본이라, 색·글꼴·간격은 디자인 시스템 그대로 두고 대화의 배치만 참고에서 고른다. 사람은 줄 참고가 없다고 해, 세션이 맡긴 서브에이전트가 다섯 제품의 원문을 받아 읽었다. 글이 든 수치는 그 글의 값이고 잰 값이 아니다.

- OpenAI ChatKit: [테마](https://developers.openai.com/api/docs/guides/chatkit-themes), [위젯](https://developers.openai.com/api/docs/guides/chatkit-widgets), [응답 중 갱신](https://github.com/openai/chatkit-python/blob/main/docs/guides/update-client-during-response.md)
- Intercom Messenger(Fin): [메신저 갱신](https://www.intercom.com/help/en/articles/9319961-updates-to-the-messenger), [Designing the front door](https://ideas.fin.ai/p/designing-the-front-door)(2026-06), [메신저 접근성](https://www.intercom.com/blog/messenger-accessibility/)(2018)
- Vercel AI Elements: [Confirmation](https://elements.ai-sdk.dev/components/confirmation), [Tool](https://elements.ai-sdk.dev/components/tool)
- GitHub Copilot Chat(VS Code): [승인](https://github.com/microsoft/vscode-docs/blob/main/docs/agents/run/approvals.md)
- Microsoft Bot Framework Web Chat: [알림](https://github.com/microsoft/BotFramework-WebChat/blob/main/docs/NOTIFICATION.md), [접근성](https://github.com/microsoft/BotFramework-WebChat/blob/main/docs/ACCESSIBILITY.md)

Claude(claude.ai)는 대화 안 승인 화면의 문구와 배치를 밝힌 공개 문서를 찾지 못해 넣지 않았다.

뽑은 공통 규칙:

1. 도구 호출은 이름과 상태만 보이는 한 줄이다(AI Elements, VS Code, ChatKit, Web Chat).
2. 진행 줄은 쌓이다가 끝나면 한 줄 요약으로 접힌다(ChatKit, AI Elements, VS Code).
3. 잠깐 보이는 상태 문구(연결 중 등)는 한 줄을 갈아 끼우고 기록에 남기지 않는다(ChatKit, Web Chat, Intercom).
4. 승인은 대화 흐름 안의 카드에서 묻고, 결정한 뒤에는 버튼을 없애고 결과를 한 줄로 남긴다(AI Elements, ChatKit, Web Chat). AI Elements 예제도 거부(테두리)가 먼저, 승인(채움)이 나중이다.
5. 승인 화면은 도구 이름과 인자 원문을 그대로 보인다(VS Code, AI Elements).
6. 오류에는 원인을 밝힌 문구와 다시 시도하는 동작을 짝지어 둔다(ChatKit, Web Chat, VS Code).
7. 강조색 하나와 회색조로 칠하고 상태 색은 작은 아이콘과 배지에만 쓴다(ChatKit, AI Elements, Web Chat). Intercom은 Fin의 Spotlight 화면에서 글래스모피즘, 터미널풍 고정폭, 브랜드 그라데이션을 포함한 열두 가지쯤의 방향을 시험하고 모두 버렸다고 적었다. 까닭으로 든 문장은 "Distinctive AI styles tend to age fast"이고, 고른 것은 페이지의 강조색을 따르는 옅은 반투명 배경이다.
8. 연결 상태는 대화 기록 밖의 고정된 자리(Web Chat은 대화와 입력창 사이)에 둔다. 대화 영역은 살아 있는 영역이고, 새 항목은 보이는 기록과 따로 둔 영역이 읽는다(Web Chat, Intercom, AI Elements).

고른 방향은 **조용한 기록형**이다(AI Elements, VS Code에 가깝고 진행 표시는 ChatKit에 가깝다). 요청만 오른쪽 상자에 담고 출력은 상자 없이 폭을 다 쓰며, 도구 진행은 한 줄씩 쌓다가 끝나면 접는다. 승인은 테두리 카드, 연결과 상한의 알림은 입력창 바로 위의 띠다. 고르지 않은 것은 메신저형(양쪽 말풍선과 이름 첫 글자 동그라미)과 작업 기록형(모두 왼쪽, 도구 줄을 접지 않음)이다. 추천안의 접힌 요약에 든 걸린 시간은 위젯이 받지 않아(진행 항목은 도구 이름과 성패뿐) 개수로만 적는다.

가져오지 않을 것(사람이 추천 목록대로 골랐다): 로고, 브랜드 색과 글꼴(OpenAI Sans, Calibri 등), 위젯을 여닫는 둥근 런처 단추, 상담원·팀 사진과 아바타, 마크다운 렌더링(출력은 글자 그대로), 첨부·좋아요·모델 고르기·음성, "항상 허용"·"이 세션 동안" 같은 범위 승인, 인자 편집, 대화 목록 패널, 시작 질문 예시, 응답 시간 안내, 상담원 넘김, 적응형 카드와 캐러셀, 흘러나오는 글자 효과와 입력 중 표시. 움직임은 디자인 시스템의 도는 표시 하나이고 움직임 줄이기 설정에서 멈춘다.

## 1. 와이어프레임

```text
Agent OS 위젯의 화면 다섯(대화, 승인 묻기, 실패, 재접속 중, 상한에 걸림)을 와이어프레임으로 그려 줘. 색은 쓰지 말고 회색조로 부품의 자리, 크기, 차례만 보여 줘. 부품은 고른 디자인 시스템의 것(버튼, 아이콘 버튼, 글 입력, 상태 배지, 알림, 진행 표시, 카드, 아이콘)을 쓴다. 갈래와 메모까지 모든 결과는 대화의 답이 아니라 디자인 파일 안에 넣어 줘. 그 파일을 내보내 쓴다.

위젯은 사이트(남의 웹사이트)가 자기 페이지의 한 자리에 넣는 창이다. 최종 사용자(그 사이트에 로그인한 사람)가 에이전트에게 요청을 보내고 출력을 받는다. 에이전트가 도구를 쓰기 전에 승인을 물으면 최종 사용자 자신이 승인하거나 사유를 붙여 거부한다. 그 실행을 요청한 사람이 승인자이고, 운영자를 기다리는 일은 없다. 끝난 실행 뒤에 새 요청을 보내면 대화가 이어지고, 대화가 길어도 새 대화를 권하지 않는다(서버가 이어 간다). 승인을 기다리는 동안에는 실행이 끝나지 않았으므로 새 요청을 이어 갈 수 없다. 위젯은 사이트가 준 자리를 채우고, 승인 묻기도 남의 화면을 덮는 창이 아니라 위젯 안의 대화에서 묻는다. 테마와 모드(라이트, 다크)는 사이트가 고르므로 위젯 안에 고르는 부품은 없다. 위젯 자리를 여닫는 것도 사이트의 몫이라 여는 단추와 닫기 단추는 그리지 않는다.

위젯이 받는 것은 아래뿐이다. 이 밖의 것은 화면에 없으니 지어내지 않는다.
- 실행이 시작됨: 실행 식별자.
- 도구 하나가 불림: 도구 이름과 성공 여부. 걸린 시간, 도구 결과, 모델이 중간에 쓴 글은 없다.
- 승인을 기다리며 일시정지: 도구 이름과 인자(JSON) 원문. 왜 그 도구를 쓰는지 설명하는 글은 없다.
- 결정이 기록됨: 승인인지 거부인지와 거부 사유.
- 끝남: 출력(글자). 마크다운이나 HTML로 그리지 않고 줄바꿈을 지킨 글자 그대로 보인다.
- 실패: 실패 원인(아홉 가운데 하나이거나 없음)과 실행 식별자. 예외 원문이나 내부 경로는 없다.
- 끝내지 못함: 다시 붙어 보니 서버가 다시 시작해 그 실행이 사라졌다.
- 요청을 보낼 때(시작, 이어 가기, 결정, 다시 붙기)의 거절: 신원을 받지 못함(401), 이어 갈 실행이 이 사람에게 없음(404), 에이전트를 지금 쓸 수 없음(409), 상한에 걸림(429: 동시 실행 수, 시간당 실행 수, 연결 수 가운데 하나와 다시 보내도 되기까지의 초), 서버가 요청을 처리하지 못함(500). 요청의 글자 수 상한(기본 20,000자)은 위젯이 미리 알아 보내기 전에 막는다. (셀프 리뷰가 더함, 2026-10-23: 계약의 404와 409는 이 줄보다 넓다. 404에는 요청한 에이전트가 없거나 열 에이전트 밖인 것이, 409에는 결정을 받을 수 없는 실행의 상태와 끝나지 않은 앞 실행과 범위 밖의 `Last-Event-ID`가 든다. 화면은 이 줄대로 그렸고, 어긋나는 자리는 `README.md`에서 셀프 리뷰와 PR 직전 리뷰가 찾은 자리의 목록이다. 결정의 거절은 이 줄에 들지만 그리지 않았다.)

틀: 위쪽 띠(에이전트 이름, 새 대화), 가운데 대화(교환이 위에서 아래로 쌓이고 넘치면 대화만 스크롤), 아래 입력창(여러 줄 글 입력과 보내기 아이콘 버튼). 위젯 창 하나만 떠 있는 것이라 그림자를 쓰고, 그 안의 카드와 알림은 그림자 없이 바탕과 테두리로 선다.

배치와 밀도: 조용한 기록형이다. 요청은 왼쪽에 여백을 남기고 오른쪽에 붙은 옅은 상자에 담고, 출력은 상자 없이 왼쪽부터 자리 폭을 다 쓴다. 교환 사이는 여백으로 가르고 경계선이나 말풍선 꼬리를 두지 않는다. 화면 읽기 프로그램에만 들리는 "요청:"·"출력:" 머리말을 단다. 도구 진행은 출력이 올 자리 위에 도구마다 한 줄(아이콘, 고정폭 도구 이름, 성공·실패 글자)로 쌓이고, 실행이 끝나면 "도구 3개를 불렀습니다" 한 줄로 접혀 눌러 펼친다. 승인은 대화 흐름 안의 테두리 카드다. 연결이 끊긴 일과 상한 알림은 기록에 남기지 않는 한 줄 띠로 입력창 바로 위에 뜨고, 실패는 출력이 올 자리에 알림으로 남는다. 밀도는 보통(버튼과 입력 40px, 본문 15px)이다.

그릴 화면과 고를 갈래:
1. 대화: 아직 요청이 없는 첫 화면(무엇을 할 수 있는지 한 줄과 입력창), 요청과 출력이 두세 번 오간 모습, 실행이 도는 동안 도구 줄이 쌓이는 모습, 끝난 뒤 접힌 요약과 출력, 다음 요청을 쓰는 중. A·B: 위쪽 띠의 "새 대화"를 A는 글자 버튼으로 늘 보이고, B는 줄임표 아이콘 버튼의 메뉴 안에 둔다.
2. 승인 묻기: 대화 안의 카드 하나에 도구 이름, 인자의 코드 칸, 거부 사유 입력, 버튼 둘. 결정한 뒤에는 버튼이 사라지고 "승인했습니다" 또는 "거부했습니다: <사유>" 한 줄이 남는다. 인자가 긴 경우(줄을 바꿔 흐른다)도 그린다. A·B: 결정을 기다리는 동안 입력창을 A는 막힌 채 남기고 그 위 띠에 "승인이나 거부를 먼저 골라 주세요"를 보이고, B는 입력창을 숨겨 카드가 대화 맨 아래에 놓인다.
3. 실패: 출력이 올 자리의 알림과 다음에 할 일 버튼. 실행이 실패로 끝남(원인 셋의 예: 시간 초과, 도구 연결, 원인 없음), 끝내지 못함, 에이전트를 지금 쓸 수 없음, 신원을 받지 못함, 이어 갈 대화가 없어 새 대화로 시작함, 서버가 처리하지 못함(대화는 남는다).
4. 재접속 중: 출력을 기다리다 연결이 끊겨 같은 실행에 다시 붙는 동안. 이미 받은 것은 그대로 남고, 입력창 위 띠가 연결 상태를 보인다.
5. 상한에 걸림: 너무 자주 보내 거절되어 얼마 뒤에 다시 보낼 수 있는 때(동시 실행 수는 5초, 시간당 실행 수는 12분)의 입력창 위 띠와 막힌 보내기 버튼, 요청이 글자 수 상한에 가까워진 입력창과 넘은 입력창.

폭: 위젯은 창이 아니라 자기 자리의 폭에 반응한다. 화면마다 자리 폭 320px과 400px 두 가지로 그린다. A·B 갈래는 320px으로만 두 안을 그린다. 레이아웃이 갈리는 기준 폭은 360px 하나다(그 미만에서 승인 묻기의 두 버튼이 위아래로 꽉 찬다). 320px에서도 긴 인자와 긴 출력까지 가로 스크롤 없이 다시 흘러야 한다(WCAG 2.2의 리플로).

지켜 줄 것:
- 상태는 색만으로 보이지 않는다. 아이콘 모양이나 글자를 함께 쓴다.
- 포인터로 누르는 목표는 가로세로 24px 이상이다.
- 승인 묻기의 버튼은 "거부"(보조)가 먼저, "승인"(주)이 나중이다. 도구 이름과 인자는 고치거나 줄이지 않고 글자 그대로 고정폭으로 보인다.
- 불러오는 중의 뼈대는 0.3초를 넘길 때만 보이고 움직이지 않는다.

탐색용 가정(결정이 아니니 바꿔도 된다): 자리 높이 560px. 위쪽 띠의 에이전트 이름은 사이트가 정한 "주문 도우미". 예시 도구는 orders.lookup과 payments.refund, 예시 실행 식별자는 run_01JA7Q8M2K.
```

시각 방향: 조용한 기록형. Vercel AI Elements, VS Code Copilot Chat, OpenAI ChatKit의 대화처럼 평평하고 조용하게 그린다.

- 강조색은 포커스, 링크, 주 버튼(승인, 보내기)에만 쓴다. 성공·경고·위험의 색은 상태 배지와 알림, 도구 줄의 작은 아이콘에만 쓴다.
- 도구 줄과 접힌 요약은 작은 글자(text-small)와 흐린 글자색(text-muted)이고, 도구 이름만 고정폭이다.
- 승인 카드는 테두리로만 서고 바탕을 칠하지 않는다. 위쪽 띠와 대화, 입력창은 경계선 한 줄로 가른다.
- 움직임은 디자인 시스템의 도는 표시 하나이고 움직임 줄이기 설정에서 멈춘다. 글이 흘러나오는 효과, 입력 중 표시, 그라데이션, 반투명 유리 효과는 쓰지 않는다.
- 그 제품들의 로고, 브랜드 색, 글꼴, 화면 구성을 복제하지 않는다. 런처 단추, 아바타와 사진, 마크다운 렌더링, 첨부·좋아요·모델 고르기, 범위 승인("항상 허용"), 대화 목록 패널, 시작 질문 예시는 그리지 않는다.

탐색용 가정(결정이 아니니 바꿔도 된다): 위쪽 띠의 에이전트 이름 "주문 도우미". 예시 요청 "어제 주문한 우산 배송 어디쯤이에요?", 예시 출력은 줄바꿈이 든 서너 줄과 긴 주문 번호 하나. 예시 인자 {"order_id": "ORD-2026-10-22-000184", "amount": 18900, "reason": "배송 지연"}.
