# site-limits-admin: 사이트 파일의 허용 출처와 요청 글자 수 상한을 화면에서 고쳐, 아무것도 다시 띄우지 않고 바꾼 값이 듣게 한다.
**슬라이스:** 10
**Blocked by:** widget-runtime-values, pilot-release

사이트 파일(`CONTEXT.md`)의 허용 출처와 요청 글자 수 상한을 화면에서 고치는 일. release-image의 설계 인터뷰에서 사용자가 더한 요구다(일지 2026-11-11-1532 "위젯 질문에 사용자가 되물었다"). portal-admin의 설계 인터뷰(일지 2026-11-15-1312)에서 사용자가 0.1 판의 범위로 "위젯이 실행 중에 받게만"을 골라, 위젯이 두 값을 뜰 때 받는 일은 widget-runtime-values가 0.1 판에 하고 화면에서 고치는 일은 이 행이 0.1 판 뒤에 설계부터 하게 됐다(ADR 0064 결정 "허용 출처와 요청 글자 수 상한"과 "기능 행"). 0.1 판에는 들지 않는다. 그때까지 운영자는 사이트 파일을 직접 고친 뒤 그 파일을 읽는 컨테이너를 다시 띄운다(ADR 0056 결정 "사이트 파일을 고치면").

이 행에는 아직 설계가 없다. 0.1 판에서 뺀 까닭이 설계의 첫 물음이다. 두 값은 Agent OS가 요청을 받아들일지를 가르는 채널의 신뢰 설정이라(`CONTEXT.md`의 사이트 파일), 위젯 쪽의 화면이 그것을 고치면 ADR 0047의 경계와 어긋난다. 설계 인터뷰가 먼저 볼 것은 아래다.

- 어느 화면이 고치는지. Agent OS의 관리 화면인지 위젯 관리 화면인지, 그리고 값의 원천이 사이트 파일로 남는지 데이터베이스로 옮기는지를 정한다. 사이트 파일의 형식은 Agent OS의 계약이다.
- 그 파일을 읽는 세 곳이 다시 띄우지 않고 바뀐 값을 듣는 길. `serve`는 사이트 파일을 시작할 때 한 번 읽고(변경 시각으로 다시 읽기는 ADR 0023의 2026-11-04 이력이 정했을 뿐 구현되지 않았다), 위젯 미리보기 페이지도 시작 때 한 번 읽으며(ADR 0050), 위젯은 widget-runtime-values 뒤에 컨테이너가 뜰 때 받는다. ADR 0064가 0.1 판에서 고르지 않은 안 둘(위젯이 요청 때마다 사이트 파일을 읽는 안, Agent OS 서버가 두 값을 공개 경로로 내주는 안)이 다시 후보다. 앞의 것의 측정은 `.scratch/release-image/probes/widget_runtime/README.md`에 있고(Windows에서만 돌았고 Next의 서버 파일 금지 규칙에 걸린다) 뒤의 것은 재지 않았다.
- 누가 고치는지. 허용 출처를 넓히면 그 사이트의 페이지가 위젯을 품고 최종 사용자 경로를 부를 수 있게 되므로, 고칠 수 있는 계정과 바꾼 기록을 정한다. admin-roles의 권한과 함께 본다.

widget-runtime-values 명세가 넘긴 것(2026-11-27, `.scratch/widget-runtime-values/spec.md`의 Out of Scope): 위젯이 두 값을 받는 자리와 모양이 정해졌다. 위젯은 뜰 때 사이트 파일을 한 번 읽어 두 가지를 한다. 값 파일(`/widget/runtime.json`. 모든 사이트의 허용 출처를 합친 목록과 가장 작은 상한이 든 JSON이고 누구나 읽는다)을 쓰고, 지어 둔 응답 머리 목록에서 위젯 페이지를 품어도 되는 사이트를 알리는 응답 머리의 값을 바꿔 넣는다(그 명세의 "값 파일"과 "품어도 되는 사이트를 알리는 응답 머리"). 위젯의 브라우저 쪽 코드는 한 자리에서만 두 값을 읽고, 화면이 열릴 때 한 번 값 파일을 받는다. 그래서 다시 띄우지 않고 바뀐 값이 듣게 하려면 이 행의 설계가 아래 넷을 정한다.

- 떠 있는 위젯이 값 파일과 응답 머리를 다시 쓰는 길. 값 파일은 요청마다 디스크에서 나가는 공개 파일이라 다시 쓰면 바뀐 내용이 나갈 것으로 보지만, 응답 머리 목록은 Next가 시작할 때만 읽는지 떠 있는 동안에도 다시 읽는지 재지 않았다(그 명세의 Further Notes "떠 있는 동안 사이트 파일만 고쳤을 때").
- 이미 열려 있는 위젯 화면이 새 값을 받는 때. widget-runtime-values 뒤에는 화면을 새로 고쳐야 받는다.
- 위젯 앞에 응답을 캐시하는 프록시가 있을 때. 위젯 페이지의 응답은 공유 캐시에 오래 남아도 된다는 머리를 달아, 품어도 되는 사이트를 알리는 머리가 그 응답과 함께 캐시에 남을 수 있다(그 명세의 Further Notes "앞단에 캐시를 둘 때").
- 위젯이 사이트마다 다른 값을 따를지. 그 명세는 지금처럼 합친 허용 출처와 가장 작은 상한을 쓰고 사이트마다의 값을 범위 밖에 뒀다. 그래서 화면에서 사이트 하나의 상한을 올려도 다른 사이트의 상한이 더 작으면 위젯의 입력창은 바뀌지 않는다. 아래 수락의 "위젯이 새 상한을 따르고"가 그 사이트의 페이지에 놓인 위젯을 말하는지는 이 행의 설계가 정한다.

수락: 시험 환경에서 운영자가 화면에서 사이트 하나의 요청 글자 수 상한을 바꾸면, 아무것도 다시 띄우지 않고 `serve`와 위젯이 새 상한을 따르고, 허용 출처에서 뺀 사이트의 페이지는 위젯 페이지를 품지 못한다
