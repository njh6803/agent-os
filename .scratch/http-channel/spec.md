# HTTP 채널: HTTP로 실행을 일으켜 이벤트 스트림으로 받고, HTTP로 승인한다

Status: ready-for-agent

슬라이스 2(`http-channel`). 근거는 `docs/adr/0014`(응답은 이벤트 스트림이고 실행은 연결에 묶이지 않는다), `docs/adr/0015`(채널 전용 토큰과 주체), `docs/adr/0016`(공용 배관은 `agent_os.http` 층) 셋이 이 기능의 결정 전부이고, 그 셋이 앞선 ADR에 남긴 이력 둘(ADR 0010의 2026-09-24 "채널이 붙으며 앱의 인자와 에러 어휘가 는다", ADR 0011의 2026-09-24 "미들웨어가 접두사로 토큰을 가르고 채널은 자기 토큰을 쓴다"), 재개와 재생과 자기 승인의 `docs/adr/0009`, 실행 상태 파생 규칙의 소유권인 `docs/adr/0012`, `docs/PRD.md`, `docs/constitution/`, 그리고 2026-09-24 설계 인터뷰(`docs/journal/2026-09-24-03-http-channel-design.md`)다. 용어는 `CONTEXT.md`의 `## 구조`(채널, 관리), `## 실행`(이벤트 스트림, 트레이스, 실행 상태, 주체), `## 인터럽트`(승인, 결정, 승인자, 재개, 재생)를 따른다.

새 결정을 만들지 않는다. 이 명세가 정한 것은 ADR이 명세에 넘긴 셋뿐이다 — 스트림 항목이 계약에 실리는 이름(ADR 0010의 2026-09-24 이력), 테스트 이음매와 채널을 지나는 LLM 테스트(일지 2026-09-24-03의 "다음"). 뒤의 둘은 사용자가 이 명세를 쓰며 골랐다. 결정이 필요해지면 멈추고 ADR을 제안한다.

## Problem Statement

실행을 일으키는 면이 CLI 하나뿐이다. `agent-os run`은 서버가 도는 기계의 셸에서만 칠 수 있고, 그 결과는 그 셸의 표준 출력으로만 나온다. 슬라이스 4의 위젯이 설 자리가 없고, 슬라이스 3의 관리 화면이 승인 버튼을 둘 자리도 없다. 관리 API가 선 지금도 운영자가 할 수 있는 것은 **보는 것**까지다 — 멈춘 실행의 `run_id`를 관리 API에서 얻은 뒤 셸로 가서 `agent-os resume`을 쳐야 한다. 관리는 실행을 일으키지 않는다고 용어집이 정했으므로 그 버튼은 관리에 둘 수 없다. 채널이 있어야 한다.

**HTTP로 옮기는 순간 CLI에서는 없던 질문이 셋 생긴다.**

- **연결은 끊긴다.** CLI의 프로세스는 실행과 수명이 같지만 HTTP 연결은 그렇지 않다. 가장 단순한 구현 — 라우트가 `run()`을 그대로 흘리는 것 — 은 끊김에서 실행을 취소하고, 그 취소는 `run_failed`도 남기지 않은 채 도구를 반쯤 부른 실행을 만든다(2026-09-24 프로브). 연결이 끊기는 것은 전송의 사건이지 사람의 결정이 아니다.
- **실패의 모양이 둘로 갈린다.** CLI는 실행 전 실패(`PluginError`)를 진단으로, 실행 안의 실패(`run_failed`)를 스트림으로 가른다. 스트리밍 응답은 첫 바이트 전에 상태 코드를 확정하므로, 가르는 자리를 정하지 않으면 없는 에이전트를 부른 요청이 200으로 시작한 뒤 끊긴 스트림이 된다.
- **누가 요청했고 누가 허락했는지를 요청이 말하게 된다.** CLI의 주체와 승인자는 OS 사용자였다. HTTP 본문에서 받으면 트레이스의 "누가 허락했나"가 증명이 아니라 주장이 된다.

**그리고 관리와 채널이 한 앱에 서는데 배관이 관리 쪽에 있다.** 에러 봉투, 예외를 상태 코드로 옮기는 표, 에러 문서, 경로 변환기, 인증 미들웨어가 전부 `admin` 안에 있고, 원칙 IV가 채널이 관리를 import하는 것을 금한다. "라우터 하나 더 마운트"가 아니라 층 경계 문제다.

## Solution

`agent-os serve`가 관리 API와 함께 HTTP 채널을 세운다. 채널의 경로는 둘이다.

- `POST /runs` — `{agent, request}`를 받아 실행 하나를 일으키고, 그 실행의 **이벤트 스트림**을 `text/event-stream`으로 돌려준다
- `POST /runs/{run_id}/approval` — 멈춘 실행에 결정 하나(`{"decision": "approve"}` 또는 `{"decision": "deny", "reason": "…"}`)를 받아 재개하고, 재개된 실행의 스트림을 같은 모양으로 돌려준다

스트림의 프레임 하나는 `data:` 한 줄이고, 그 값은 트레이스 한 줄과 같은 이벤트 JSON 하나다. 결말 이벤트(`run_finished`, `run_failed`, `run_paused`)를 보낸 뒤 닫힌다. 단위는 이벤트이고 모델의 토큰이 아니다.

**실행은 연결에 묶이지 않는다.** 클라이언트가 떠나도 실행은 끝까지 가고 트레이스에 남는다. 스트림에 나간 이벤트는 이미 트레이스에 있으므로, 떠난 쪽은 나머지를 관리 API의 트레이스 상세에서 본다. 서버가 멈추면 떠난 실행을 기다리지 않고 취소하며 그 실행은 결말 없음이다.

**실행 전 실패는 상태 코드와 관리 API와 같은 에러 봉투로, 실행 안의 실패는 200 스트림 속 `run_failed`로 답한다.** 경계는 첫 이벤트다. 없는 에이전트와 없는 실행은 404, 재개할 수 없는 실행(일시정지 아님, 형식 1)은 409, 그 밖의 구성 오류는 500이다.

**채널은 자기 토큰으로 선다.** `/runs` 접두사 아래는 채널 토큰(`AGENT_OS_CHANNEL_TOKEN`)만, 그 밖은 관리 토큰만 통과하고, 인증 없이 지나가는 것은 여전히 `/health` 하나다. 두 토큰이 모두 있고 서로 달라야 `serve`가 선다. 실행의 주체와 승인자는 `serve` 프로세스의 OS 사용자이고 요청에서 받지 않는다.

공용 배관은 새 층 `agent_os.http`로 옮기고, 원칙 IV의 의존 방향이 `main → server → {channel | admin | adapters} → http → core → sdk`가 된다.

## User Stories

### HTTP로 에이전트를 부르는 개발자

1. 개발자로서, 에이전트 이름과 요청을 한 번의 HTTP 요청으로 보내 실행을 일으키고 싶다. 서버가 도는 기계의 셸에 들어가지 않고 원격 프로그램에서 부르기 위해서다.
2. 개발자로서, 그 응답으로 실행의 이벤트를 생기는 대로 받고 싶다. 모델 호출이 수십 초 걸리는 실행에서 끝날 때까지 빈 화면을 보지 않기 위해서다.
3. 개발자로서, 스트림의 단위가 이벤트이고 토큰이 아니기를 바란다. 트레이스와 단위가 같아야 하나를 읽는 코드로 다른 하나도 읽기 때문이다.
4. 개발자로서, 스트림의 프레임 하나가 트레이스 한 줄과 같은 JSON이기를 바란다. 스트림만을 위한 두 번째 스키마를 배우지 않기 위해서다.
5. 개발자로서, 이벤트의 종류를 JSON의 `type` 한 곳에서 읽고 싶다. 종류가 프레임의 `event:`와 본문 두 곳에 적히면 어긋날 수 있고, 브라우저의 기본 `onmessage`가 받지 못하는 모양은 쓰기 번거롭기 때문이다.
6. 개발자로서, 스트림이 결말 이벤트를 보낸 뒤 닫히기를 바란다. 언제 읽기를 멈출지 스트림이 말해 주어야 하기 때문이다.
7. 개발자로서, 스트림의 첫 이벤트에서 실행 식별자를 얻고 싶다. 나중에 승인을 보내거나 관리 API에서 트레이스를 찾을 때 그것이 열쇠이기 때문이다.
8. 개발자로서, 실행이 시작되기도 전에 실패한 요청은 상태 코드와 에러 봉투로 받고 싶다. 200으로 시작했다가 끊긴 스트림은 서버의 거절인지 네트워크의 사고인지 구분할 수 없기 때문이다.
9. 개발자로서, 실행 안의 실패는 스트림 속 `run_failed`로 받고 싶다. 트레이스가 남는 실패와 남지 않는 실패가 CLI와 같은 경계로 갈려야 한 번 배운 것으로 두 채널을 읽기 때문이다.
10. 개발자로서, 없는 에이전트를 부르면 404를 받고 싶다. 내 오타와 서버 고장을 구분하기 위해서다.
11. 개발자로서, 서버 쪽 구성이 깨져 실행할 수 없으면 500을 받고 싶다. 4xx를 받으면 잘못 요청했다고 믿고 운영자에게 알리지 않기 때문이다.
12. 개발자로서, 본문이 틀리면 어느 필드가 왜 틀렸는지 받고 싶다. 422 한 줄만으로는 고칠 곳을 찾을 수 없기 때문이다.
13. 개발자로서, 채널의 에러가 관리 API와 같은 봉투로 오기를 바란다. 한 서버의 두 면이 다른 에러 모양이면 생성 클라이언트가 에러 타입을 둘 받기 때문이다.
14. 개발자로서, 응답마다 추적 식별자를 헤더로 받고 싶다. 스트림이 이상했던 요청을 서버 기록과 잇기 위해서다.
15. 개발자로서, 연결이 끊겨도 실행이 끝까지 가기를 바란다. 네트워크가 한 번 끊겼다고 도구를 반쯤 부른 채 기록 없이 사라진 실행이 생기면 안 되기 때문이다.
16. 개발자로서, 스트림에서 본 이벤트가 이미 트레이스에 있기를 바란다. 스트림에서 본 사실을 트레이스에서 못 찾는 일이 없어야 하기 때문이다.
17. 개발자로서, 끊긴 뒤의 나머지를 관리 API의 트레이스 상세에서 볼 수 있기를 바란다. 스트림과 트레이스는 같은 사실의 두 모습이기 때문이다.
18. 개발자로서, 결말 이벤트 없이 닫힌 스트림이 무엇을 뜻하는지 알고 싶다. 서버가 멈춰 그 실행을 끝내지 못했다는 뜻이고, 그 트레이스는 결말 없음이다.
19. 개발자로서, 모델이 오래 조용해도 연결이 살아 있기를 바란다. 중간 프록시가 유휴 연결을 자르기 때문이다.
20. 개발자로서, 중간 장치가 스트림을 모았다가 한꺼번에 보내지 않기를 바란다. 모아서 보내면 스트림의 의미가 없기 때문이다.
21. 개발자로서, 스트림 항목의 스키마가 계약에 이름 있는 타입으로 실리기를 바란다. 생성 클라이언트가 `Streamitem Start Run` 같은 익명 유니온을 받지 않게 하기 위해서다.
22. 개발자로서, 스트림의 이벤트와 트레이스 상세의 이벤트가 같은 컴포넌트를 가리키기를 바란다. 같은 이벤트를 두 타입으로 다루지 않기 위해서다.
23. 개발자로서, 모델을 요청에서 고르지 않아도 되기를 바란다. 서버가 정한 모델로 도는 것이 이 채널의 계약이고, 채널을 부르는 쪽이 비용을 정하지 않기 때문이다.

### 승인자

24. 승인자로서, 멈춘 실행을 HTTP로 승인하거나 거부하고 싶다. 서버의 셸 앞에 앉지 않고 결정하기 위해서다.
25. 승인자로서, 무엇을 승인하는지 `run_paused`의 도구와 인자에서 보고 싶다. 시작한 쪽은 스트림의 마지막 이벤트에서, 운영자는 관리 API의 트레이스 상세에서 본다.
26. 승인자로서, 사유 없는 거부가 요청 단계에서 거절되기를 바란다. 사유 없는 거부가 기본값으로 굳으면 모델이 왜 막혔는지 모른 채 계속하기 때문이다.
27. 승인자로서, 공백뿐인 사유도 없는 것으로 보기를 바란다. CLI와 같은 규칙이어야 두 채널에서 같은 결정이 같게 기록되기 때문이다.
28. 승인자로서, 승인에 사유를 붙이면 거절되기를 바란다. 내가 적은 말이 어디에도 남지 않은 채 조용히 버려지는 것을 막기 위해서다.
29. 승인자로서, 결정을 보낸 응답으로 재개된 실행의 스트림을 받고 싶다. 승인 뒤 무슨 일이 일어났는지 같은 요청에서 보기 위해서다.
30. 승인자로서, 재개 스트림의 첫 이벤트가 내 결정이기를 바란다. 내 결정이 기록된 뒤에 재개가 시작됐다는 것을 스트림이 보여 주어야 하기 때문이다.
31. 승인자로서, 재개 스트림이 멈추기 전에 이미 본 이벤트를 되풀이하지 않기를 바란다. 재생된 사실은 새 사실이 아니기 때문이다.
32. 승인자로서, 없는 실행에 결정을 보내면 404를, 멈춰 있지 않은 실행에 보내면 409를 받고 싶다. 식별자를 잘못 적은 것과 이미 누군가 결정한 것은 다른 일이기 때문이다.
33. 승인자로서, 형식 1 트레이스의 실행에 결정을 보내면 409를 받고 싶다. 읽을 수는 있어도 재개할 수 없는 실행이기 때문이다.
34. 승인자로서, 같은 실행에 결정 둘이 동시에 도착해도 하나만 받아들여지기를 바란다. 두 번 누른 버튼 하나가 승인된 도구를 두 번 실행하게 하면 안 되기 때문이다.
35. 승인자로서, 받아들여지지 않은 쪽이 409를 받기를 바란다. 내 결정이 무시됐다는 것을 알아야 하기 때문이다.
36. 승인자로서, 재개가 다시 `run_paused`로 끝나면 같은 경로로 다음 결정을 낼 수 있기를 바란다. 한 턴에 승인 대상이 둘이면 두 번 멈추기 때문이다.
37. 승인자로서, CLI에서 시작한 실행을 HTTP로 승인할 수 있기를, 그 반대도 되기를 바란다. 트레이스가 같으면 같은 실행이기 때문이다.
38. 승인자로서, 결정이 어긋난 호출에 적용되지 않기를 바란다. 재개 뒤 첫 호출이 멈춘 그 호출이 아니면 스트림이 `run_resumed` 없이 `run_failed`로 끝나야 한다(ADR 0009, 채널과 무관하게 core가 지킨다).

### 운영자

39. 운영자로서, `agent-os serve` 하나로 관리 API와 채널이 함께 서기를 바란다. 프로세스 둘을 따로 띄우고 맞추지 않기 위해서다.
40. 운영자로서, 모델을 `serve` 시작 때 한 번 정하고 싶다. `--model`, `AGENT_OS_MODEL`, 기본값 순이고 CLI와 같은 규칙이어야 두 채널이 같은 모델로 돈다고 믿을 수 있기 때문이다.
41. 운영자로서, 채널 토큰이 없으면 `serve`가 뜨지 않기를 바란다. 관리 토큰과 같은 fail-closed여야 하기 때문이다.
42. 운영자로서, 두 토큰이 같으면 `serve`가 뜨지 않기를 바란다. 같은 값이면 분리가 무효가 되는데 요청 시점에는 그것을 알아챌 길이 없기 때문이다.
43. 운영자로서, 구성 오류가 모아서 한 번에 나오기를 바란다. 하나씩 나오면 고치고 다시 치고 또 막히기 때문이다.
44. 운영자로서, 진단에 토큰 값이 실리지 않기를 바란다. 표준 에러는 셸 이력과 CI 로그로 흘러가기 때문이다.
45. 운영자로서, 채널 실행의 주체와 승인자가 `serve`를 띄운 OS 사용자로 기록되기를 바란다. 요청 본문의 자기 신고를 받으면 트레이스의 "누가 허락했나"가 증명이 아니라 주장이 되기 때문이다.
46. 운영자로서, 신원이 하나인 지금 트레이스의 주체와 승인자가 늘 같다는 것을 알고 있고 싶다. 그 필드가 사람을 구분해 주지 못한다는 것을 모르고 믿으면 안 되기 때문이다.
47. 운영자로서, 서버를 멈출 때 클라이언트가 떠난 실행을 기다리지 않기를 바란다. 멈추라는 명령이 어떤 실행이 끝나기를 무한히 기다리면 안 되기 때문이다.
48. 운영자로서, 서버를 멈춰 끝내지 못한 실행이 결말 없음으로 보이기를 바란다. 실패라고 적으면 트레이스가 일어나지 않은 판정을 말하게 되기 때문이다.
49. 운영자로서, 채널에서 일으킨 실행이 같은 서버의 관리 API 목록과 상세에 바로 보이기를 바란다. 두 면이 같은 트레이스 디렉터리를 보기 때문이다.
50. 운영자로서, 관리 화면을 읽기 전용 대시보드로 둘지 승인 콘솔로 둘지 토큰으로 고르고 싶다. 대시보드에 준 자격 증명이 실행까지 일으키면 안 되기 때문이다.

### 보안을 신경 쓰는 운영자

51. 운영자로서, 채널 경로가 관리 토큰으로 열리지 않기를 바란다. 트레이스를 읽을 권한이 비용과 부작용이 있는 실행을 일으킬 권한이 되면 안 되기 때문이다.
52. 운영자로서, 관리 경로가 채널 토큰으로 열리지 않기를 바란다. 위젯에 준 토큰으로 모든 실행의 트레이스를 읽을 수 있으면 안 되기 때문이다.
53. 운영자로서, 새 채널 경로를 `/runs` 밖에 두는 실수가 열림이 아니라 막힘이 되기를 바란다. 기본값이 관리 토큰이면 그 실수는 틀린 토큰으로 막힐 뿐이다.
54. 운영자로서, `/runsx` 같은 경로가 채널로 분류되지 않기를 바란다. 문자열 접두사 비교가 경계를 흐리면 안 되기 때문이다.
55. 운영자로서, 인증 없이 지나가는 경로가 여전히 `/health` 하나이기를 바란다. 채널이 붙었다고 allowlist가 자라면 안 되기 때문이다.
56. 운영자로서, 본문의 에이전트 이름과 경로의 실행 식별자가 파일 경로로 조립되기 전에 형식 검증을 거치기를 바란다. 둘 다 원격 입력이 되었고, 검증이 없으면 `..`와 경로 구분자가 플러그인 루트와 트레이스 루트를 벗어나기 때문이다.
57. 운영자로서, 채널도 루프백에만 서기를 바란다. 같은 프로세스, 같은 바인딩이고 토큰이 평문으로 실리기 때문이다.
58. 운영자로서, 채널 스트림이 트레이스 상세와 같은 노출이라는 것을 알고 싶다. 이벤트가 마스킹 범위 그대로 실리고 그 노출의 경계가 채널 토큰이기 때문이다.
59. 운영자로서, 토큰이 이벤트에도 로그에도 에러 봉투에도 실리지 않기를 바란다. 원칙 V이기 때문이다.
60. 운영자로서, 채널 토큰의 비교도 값에 따라 시간이 달라지지 않기를 바란다. 비교 시간이 곧 토큰을 한 글자씩 알려 주는 경로이기 때문이다.

### 관리 화면을 만드는 개발자(슬라이스 3)

61. 화면 개발자로서, 승인 버튼을 "내용은 관리 API로 보고 결정은 채널로 낸다"는 배치로 만들 수 있기를 바란다. 관리는 실행을 일으키지 않으므로 결정을 받을 경로가 거기 없기 때문이다.
62. 화면 개발자로서, 관리와 채널이 한 계약 파일에 같은 에러 모양으로 실리기를 바란다. 클라이언트를 한 번 생성해 두 면에 쓰기 위해서다.
63. 화면 개발자로서, 계약 파일의 제목과 설명이 두 면을 함께 말하기를 바란다. 지금의 "읽기 전용이고 실행을 일으키지 않는다"가 채널이 붙는 순간 거짓이 되기 때문이다.
64. 화면 개발자로서, 채널 경로의 `operationId`와 본문 타입이 사람이 지은 이름이기를 바란다. 생성 클라이언트의 함수 이름과 타입 이름이 그것이기 때문이다.
65. 화면 개발자로서, 결정 본문이 판별자 하나로 갈리는 유니온이기를 바란다. 허가와 거부가 같은 모양의 선택 필드로 뒤섞이면 생성 타입이 "사유 있는 허가"를 허용하기 때문이다.

### 런타임 기여자

66. 런타임 기여자로서, core가 여전히 HTTP 상태 코드를 모르기를 바란다. core는 바깥을 모르기 때문이다.
67. 런타임 기여자로서, 부재와 재개 불가가 core의 타입으로 갈리고 번역은 표 한 곳에 있기를 바란다. 채널이 포트와 `run_status()`로 먼저 확인하면 형식 1 판정이 core 밖으로 새기 때문이다.
68. 런타임 기여자로서, CLI가 바뀌지 않기를 바란다. CLI는 기반 타입을 잡으므로 하위 타입이 생겨도 같은 진단을 낸다.
69. 런타임 기여자로서, 채널과 관리가 서로를 import하지 않기를 바란다. 공용인 것은 공용 층에 있어야 조립 층이 갈리지 않기 때문이다.
70. 런타임 기여자로서, 에러 봉투와 상태 코드 표와 에러 문서가 한 곳에만 있기를 바란다. 같은 스키마가 둘이면 컴포넌트 이름이 부딪히거나 언젠가 어긋나기 때문이다.
71. 런타임 기여자로서, 어댑터가 HTTP 층을 import하지 못하기를 바란다. 어댑터는 HTTP 표면이 아니기 때문이다.
72. 런타임 기여자로서, 원칙 IV의 문언과 판정자(import-linter)와 코드가 한 PR에서 움직이기를 바란다. 셋이 어긋난 순간이 있으면 그 순간의 규칙은 판정할 대상이 없거나 거짓이기 때문이다.
73. 런타임 기여자로서, 동시 재개의 불변식이 테스트로 고정되기를 바란다. `resume()`의 첫 걸음에 `await` 하나가 들어오는 날 승인된 도구가 두 번 실행되는데, 그것을 막는 것이 지금은 설계가 아니라 우연이기 때문이다.
74. 런타임 기여자로서, "실행은 연결에 묶이지 않는다"가 테스트로 고정되기를 바란다. 가장 단순한 구현이 저절로 그 반대가 되기 때문이다.
75. 런타임 기여자로서, 미들웨어 둘 뒤에서도 스트림이 모이지 않는다는 것이 테스트로 고정되기를 바란다. 미들웨어를 바꾸는 날 스트림이 조용히 한 덩어리가 될 수 있기 때문이다.
76. 런타임 기여자로서, 채널 전체를 가짜 포트로 판정할 수 있기를 바란다. 네트워크와 모델 없이 커밋마다 돌기 위해서다.
77. 런타임 기여자로서, 공용 배관을 옮기는 것이 관리 API의 행동을 하나도 바꾸지 않기를 바란다. 기존 서버 테스트 전부가 그대로 초록이어야 옮긴 것이지 고친 것이 아니다.
78. 런타임 기여자로서, HTTP 표면의 공통 규칙이 관리 파일이 아니라 새 층을 여는 순간 실리기를 바란다. 채널을 만지는 세션이 관리 규칙 파일을 열어야만 봉투 규칙을 알게 되면 안 되기 때문이다.
79. 런타임 기여자로서, 원칙 III를 지키며 이 기능을 만들 수 있기를 바란다. 스트림과 ASGI를 다루는 코드가 타입 우회의 첫 선례가 되면 안 되기 때문이다.

### 이음매

테스트가 미는 지점은 다섯이고 **새 이음매는 없다.** 가장 높은 둘이 이 기능의 것이다.

- **주 이음매는 관리 API가 만든 그대로다.** `create_app()`에 가짜 포트를 주입하고 httpx `AsyncClient` + `ASGITransport`로 민다. 경로, 인증, 상태 코드, 에러 봉투, 스트림의 내용, 동시 재개, `openapi.json`의 최신성을 이것이 판정한다. 끝까지 가는 실행의 스트림은 응답 본문 전체로 받아 프레임으로 나눠 본다.
- **같은 이음매에 구동자가 하나 는다(이 명세가 정했다).** `create_app()`이 만든 그 앱을 `app(scope, receive, send)`로 직접 부르고, `receive`가 원하는 때에 `http.disconnect`를 내며 `send`가 받은 메시지를 순서대로 기록한다. 쓰는 곳은 셋뿐이다 — 조각별 전달, 끊겨도 실행은 끝까지, 서버가 멈추면 떠난 실행은 결말 없음. (2026-09-24 명세 검토가 넷째로 "느린 수신자"를 더했다. `send`를 막아 둔 채 실행이 결말로 끝나는지 본다. 이 명세가 "스트림의 수명 셋"이라 적은 자리는 모두 넷으로 읽는다. 티켓 03) `ASGITransport`는 이것을 잴 수 없다. 응답을 끝까지 모은 뒤에야 `http.disconnect`를 보내고 lifespan을 돌리지 않는다(httpx 0.28.1, 2026-09-24 확인).
- **"첫 이벤트 전 실패는 상태 코드"는 두 구동자가 나눠 잰다.** 상태 코드 쪽은 `ASGITransport`로 충분하다 — 응답 시작 메시지의 상태를 그대로 보여 주고, 시작한 뒤에 앱이 예외를 내면 404 봉투가 아니라 예외로 올라오므로 "200으로 시작한 뒤 끊긴 스트림"이 초록으로 지나가지 않는다. 스트림 쪽("첫 이벤트가 나오면 응답이 바로 시작한다")은 조각별 전달의 측정이 함께 잰다 — 실행이 끝나기 전에 첫 프레임이 `send`에 도착하려면 응답이 이미 시작해 있어야 한다.
- **ADR 0010의 2026-09-22 이력과의 관계.** 그 이력은 "클라이언트를 손으로 짜는 안은 거부했다"고 적었다. 거부한 것은 HTTP 왕복을 짜는 두 번째 클라이언트였다 — 그 코드가 자기는 테스트되지 않기 때문이다. 이 구동자는 HTTP를 짜지 않는다. ASGI 메시지를 그대로 주고받으므로 이음매 자체의 말로 말하고, 요청 줄·헤더 파싱·청크 해석이 없다. 그래도 일반 요청에 쓰지 않는다. 스트림의 수명 셋 밖으로 번지면 그 이력의 논증이 그대로 걸린다. 이 한계를 새 층의 rules 파일에 적는다.
- **나머지 셋은 기존 이음매를 넓힌다.** core의 `run()`·`resume()`(실행 전 실패의 하위 타입), CLI 표면의 `serve`(토큰 둘, `--model`, `create_app`에 넘기는 것), 그리고 바깥 이음매 하나(`-m llm`, 아래).

### 계약 티켓 — 첫 티켓이고 나머지 전부를 막는다

일지 2026-09-24-03의 "다음"이 적은 목록 그대로다. 사람에게 보이는 새 동작은 없고 관리 API의 행동도 바뀌지 않는다. 리뷰의 질문은 "이 층 경계와 이름으로 오래 살 수 있나"다.

- **공용 배관이 `agent_os.http`로 간다**(ADR 0016). 에러 봉투 셋(`ErrorEnvelope`, `ErrorCode`, `Violation`), `failure_for`와 그 표, `install_error_handlers`, `AssignRequestId`, `error_envelope`·`remember_failure`·`request_id_of`, `_documented_errors`, `_Verbatim`, 인증 미들웨어. 관리 라우터와 관리의 응답 모델(`Health`, 목록과 상세의 행, 커서)은 `admin`에 남는다.
- **헌법 원칙 IV의 문언**이 의존 방향 `main → server → {channel | admin | adapters} → http → core → sdk`와 "어댑터는 `http`를 import하지 않는다"를 적는다. 열거가 느는 것이라 minor다(ADR 0016). 첫 문장의 금지 열거("`agent_os.core`는 … import하지 않는다")에 `agent_os.http`를 더할지는 층의 순서가 이미 막는 것이라 그 PR에서 문언과 함께 본다.
- **헌법 버전.** 2026-09-24 이 명세를 쓸 때 헌법 버전 드리프트 칩(`chore/constitution-version-drift`, 대기열 9와 함께 닫는다)은 병합되지 않았다 — `docs/constitution/README.md`는 여전히 2.3.3(Last Amended 2026-09-21)인데 헌법 파일은 그 뒤 PR 여섯에서 바뀌었다(일지 2026-09-24-03의 "발견한 것"). **그래서 원칙 IV 개정의 버전 번호를 그 정리와 맞춘다.** 드리프트를 정리하는 것은 칩의 일이고 계약 티켓이 대신하지 않는다. 칩이 계약 티켓보다 먼저 병합되는 편이 낫다(일지 2026-09-24-03의 "다음"). 그러면 계약 티켓은 정리된 번호에서 minor를 올린다. 계약 티켓을 시작할 때 칩이 아직이면, 번호를 짓기 전에 칩과 맞춘다 — 두 PR이 같은 번호를 서로 모르게 쓰지 않는다. (2026-09-24 명세 검토: 칩이 아직 없으면 맞출 상대가 없으므로 이것은 "칩이 먼저"라는 뜻이다. 티켓 01이 그 병합에 막힌다)
- **`CLAUDE.md`의 레이어 목록에 `src/agent_os/http/` 줄이 늘고 의존 방향 줄이 바뀐다.** 헌법과 같은 문언이다.
- **import-linter는 층 하나와 금지 하나로 판정한다**(ADR 0016). 층 계약에서 `agent_os.http`가 `{channel | admin | adapters}` 아래, core 위에 서고, `adapters → http`를 따로 막는다. 계약 이름의 방향 문자열도 같이 고친다.
- **`.claude/rules/admin.md`의 HTTP 표면 공통 규칙이 새 층의 rules 파일로 간다.** 봉투와 어휘, 상태 코드 표, 에러 문서, `verbatim`, `operation_id`, 한 줄 독스트링, 테스트 이음매가 그것이다. `paths`는 새 층과 채널과 관리와 `server.py`를 덮고(ADR 0016), 지금 `admin.md`가 덮는 계약 파일과 그 생성기와 테스트도 따라간다. 목록과 상세의 모양과 커서처럼 관리에만 걸리는 것은 `admin.md`에 남는다. 테스트 이음매 줄에 위의 예외(ASGI 직접 호출은 스트림의 수명 셋에만)를 함께 적는다.
- **core의 `PluginError` 아래에 하위 타입 둘**(ADR 0014). **부재**는 없는 에이전트와 없는 실행, **재개 불가**는 일시정지가 아닌 실행과 형식 1 트레이스다. 나머지 — 깨진 매니페스트, 없는 mcp, 마스킹과 승인의 충돌, 진입점 import 실패, 손상된 트레이스, 결정 이벤트를 쓰지 못함 — 는 `PluginError` 그대로다. 클래스 이름은 티켓이 짓되 HTTP의 어휘(`NotFound`, `Conflict`)를 쓰지 않는다. core는 상태 코드를 모른다. 이름이 용어집에 자리를 얻을지는 domain-modeling 스킬이 그 자리에서 본다.
- **에러 어휘가 다섯이 된다.** `conflict`가 409다(ADR 0010의 2026-09-24 이력). 표가 MRO로 옮긴다 — 부재 404, 재개 불가 409, 그 밖의 `PluginError` 500. 관리 라우트는 409를 내지 않고, 관리 쪽 부재는 그대로 포트의 `None`을 라우트가 404로 말한다.
- **FastAPI의 하한을 `fastapi.sse`가 들어온 버전으로 올리고 `tech.md`의 HTTP 행과 맞춘다**(ADR 0014). 지금 선언은 `fastapi>=0.115`이고 락파일은 0.141.1이다. 몇 버전인지는 티켓이 재서 적는다.
- **`openapi.json`의 제목과 설명이 관리와 채널을 함께 말한다**(ADR 0010의 2026-09-24 이력). 계약 파일의 머리가 바뀌므로 같은 PR에서 파일이 함께 바뀐다. (2026-09-24 명세 검토가 첫 채널 라우트인 티켓 03으로 옮겼다. 여기서 바꾸면 채널이 없는 main에서 반대 방향으로 거짓이 된다)

### 공유 층 `agent_os.http`

- **채널과 관리와 `server`가 이것을 import하고, 이것은 core와 sdk만 import한다.** 채널과 관리는 여전히 서로를 import하지 않고 `main`과 `server`가 조립한다.
- **인증 미들웨어는 접두사→토큰 표를 받는 일반형이 되고 표는 `server`가 넘긴다**(ADR 0015, ADR 0011의 2026-09-24 이력). 미들웨어는 여전히 앱 전체에 걸리고 라우트가 보호를 opt-in하지 않는다. 기본값은 관리 토큰이다.
- **접두사 비교는 경로 조각 단위다.** `/runs`와 `/runs/…`는 채널이고 `/runsx`는 아니다. 미들웨어와 라우팅이 같은 경로 문자열을 보므로, 채널로 분류된 경로가 관리 라우트에 닿거나 그 반대가 되는 길은 없다.
- **`PUBLIC_PATHS`는 `/health` 하나 그대로다.**

### core — 실행 전 실패가 하위 타입으로 갈린다

- **`run()`과 `resume()`의 시그니처와 이벤트는 바뀌지 않는다.** 바뀌는 것은 실행 전에 던지는 예외의 타입뿐이다.
- **CLI는 기반 타입(`PluginError`)을 잡으므로 진단도 종료 코드도 그대로다.** 기존 CLI 테스트가 그것을 판정한다.
- **동시 재개의 불변식.** `resume()`의 첫 걸음 — 트레이스 읽기, 일시정지 확인, 결정 이벤트 쓰기 — 에 `await`가 없다. 그래서 한 이벤트 루프 안에서는 같은 실행의 둘째 결정이 마지막 이벤트를 결정으로 읽고 재개 불가가 된다(ADR 0014). 이것은 이제 우연이 아니라 불변식이고 채널 테스트가 고정한다. 트레이스 쓰기를 비동기로 바꾸거나 스레드로 보내는 변경이 이것을 깨뜨리며, 그 테스트가 그 자리에서 깨진다.

### HTTP 표면 — 경로 둘

- **`POST /runs`** — 본문 `{agent, request}`. 에러는 401, 404(없는 에이전트), 422(본문 형식), 500(그 밖의 구성 오류).
- **`POST /runs/{run_id}/approval`** — 본문은 결정이고 `decision`을 판별자로 한 유니온이다(ADR 0014). 에러는 401, 404(없는 실행), 409(재개 불가), 422(본문과 경로 파라미터의 형식), 500.
- **`operation_id`와 본문 타입의 이름은 그 라우트를 만드는 티켓이 짓는다.** 관리 API의 `operation_id`가 티켓에서 지어진 것과 같다. 셋이 조건이다 — `operation_id`를 손으로 준다(관리 규칙 그대로), 본문과 결정의 유니온이 이름 있는 컴포넌트다, 결정의 멤버 이름이 core의 `Approve`·`Deny`·`Decision`과 겹치는지 보고 정한다. 겹치게 두면 한 저장소에서 같은 이름이 두 층의 다른 타입을 가리키고, 가르면 용어집의 "결정"과 계약의 이름이 멀어진다. 어느 쪽이든 `openapi.json`에 박히므로 그 PR에서 사용자가 본다. (2026-09-24 명세 검토가 넷째 조건 "기존 계약 컴포넌트와 겹치지 않는다"를 더했다. 겹치면 기존 이벤트 컴포넌트가 `-Input`·`-Output`으로 갈라진다. 티켓 04)
- **결정의 규칙은 CLI의 `_decision`과 같다.** 승인에 `reason`이 오면 422, 거부의 사유가 없거나 공백뿐이면 422다. core의 `Deny`가 한 번 더 막는다. 422의 `violations`가 그 필드를 가리킨다.
- **본문의 `agent`는 `sdk`의 플러그인 이름 패턴을 만족해야 한다.** `plugins/agents/{agent}/plugin.toml`로 조립되는 원격 입력이라, 관리의 `{name}`과 같이 포트에 닿기 전에 422로 끝난다. **경로의 `{run_id}`는 `verbatim` 변환기와 실행 식별자 패턴으로 받는다.** 관리의 `/traces/{run_id}`와 같은 규칙이고 같은 이유다.
- **`request`는 문자열이면 된다.** CLI가 받는 것과 같다.
- **채널이 원격 입력으로 바꾸는 것은 등록된 에이전트의 이름 하나다.** 매니페스트와 진입점과 MCP 서버의 명령은 여전히 운영자가 쓴 플러그인 루트에서 오고(ADR 0003), 요청이 그 내용을 싣거나 바꾸는 길은 없다. 진입점은 그 에이전트 디렉터리의 파일로만 로드되고(`agent_os_plugins.<name>.<module>`), MCP 서버는 셸 없이 argv로 뜬다(`StdioConnection`의 `command`와 `args`). 플러그인 루트는 신뢰 경계 안이고 이 기능은 신뢰하지 않는 매니페스트를 다루지 않는다 — 지금까지의 전제 그대로다. 달라지는 것은 그 실행을 **누가 일으키나**이고, 그 경계가 채널 토큰이다(CodeRabbit PR #67).
- **본문 모델도 계약에 박힌다.** 독스트링은 한 줄이고 논증은 `#` 주석에 둔다. 기본값 있는 필드가 있으면 직렬화 스키마에서 required가 되게 한다. 관리의 모델이 따르는 규칙 그대로다. (2026-09-24 명세 검토: 요청 본문은 검증 스키마를 써서 이 규칙이 효과가 없다. 요청 본문 모델에는 기본값을 두지 않는다. 티켓 03·04)
- **채널에는 승인 요청을 읽는 경로가 없다**(ADR 0014). 시작한 쪽은 스트림 마지막의 `run_paused`에서, 운영자는 관리 API에서 본다.

### 스트림

- **미디어 타입은 `text/event-stream`이고 FastAPI의 `EventSourceResponse`를 쓴다.** keepalive 주석(15초)과 버퍼링을 막는 헤더(`Cache-Control: no-cache`, `X-Accel-Buffering: no`)가 붙는다(fastapi 0.141.1, 2026-09-24 확인).
- **프레임은 `data:` 하나다.** `event:`와 `id:`를 싣지 않는다(ADR 0014). 테스트가 프레임에 `data` 말고는 없음을 고정한다. 계약의 `itemSchema`에는 FastAPI의 정형 SSE 스키마를 따라 `event`·`id`·`retry`가 선택 필드로 적힌다. 서버가 보내지 않는 필드를 계약이 선택 필드로 광고하는 것이다. 그대로 둘지 지울지는 정하지 않았다(Further Notes). (2026-09-24 닫힘: 둔다, ADR 0014의 이력)
- **스트림 항목은 `sdk`의 `Event`이고 계약의 이름도 `Event`다(이 명세가 정했다).** 트레이스 상세의 `TraceEvent`가 아니다 — 스트림은 이 런타임이 방금 낸 이벤트라 모르는 종류의 표지가 들 자리가 없다(ADR 0010의 2026-09-24 이력). 지금 그대로 쓰면 항목이 `Streamitem Start Run`이라는 제목의 익명 `oneOf`로 인라인된다. 채널 쪽에 `sdk`의 `Event`를 가리키는 이름 있는 별칭을 두면 `#/components/schemas/Event`가 생기고, `TraceEvent`는 멤버 열(아홉과 표지 하나)의 평평한 `oneOf` 그대로이며 두 유니온이 같은 멤버 컴포넌트를 가리킨다(2026-09-24 프로브). **`sdk`는 바뀌지 않는다.** 이름이 용어집의 "이벤트"와 `sdk`의 이름과 같아서 계약에 새 말을 들이지 않는다.
- **`/runs`의 스트림은 `run_started`로 시작하고 결말 이벤트로 끝난다.** 재개 스트림은 결정 이벤트(`approval_granted` 또는 `approval_denied`), `run_resumed`, 새 사실, 결말 순이다. 재생된 사실은 다시 나가지 않는다(ADR 0009). 재개 뒤 첫 호출이 멈춘 그 호출이 아니면 `run_resumed` 없이 `run_failed`다.
- **결말 이벤트 없이 닫힌 스트림은 서버가 그 실행을 끝내지 못했다는 뜻이다.** 서버 프로세스가 죽었거나 멈추며 실행을 취소한 경우이고 그 트레이스는 결말 없음이다.
- **응답은 첫 이벤트를 받은 뒤에 시작한다**(ADR 0014). 첫 이벤트가 나오기 전의 예외는 기존 예외 핸들러를 지나 봉투가 되고, 첫 이벤트가 나온 뒤의 실패는 `run_failed`로 스트림에 있다. `run()`에서는 `run_started` 앞이, `resume()`에서는 결정 이벤트 앞이 실행 전이다. 둘 다 그 앞에 `await`가 없어 첫 이벤트는 빨리 온다 — 느린 것(MCP 연결, 모델 호출)은 전부 그 뒤다. FastAPI는 의존성을 전부 푼 뒤에 SSE 제너레이터를 부르고 응답을 시작하므로(fastapi 0.141.1의 라우팅, 2026-09-24 확인) 첫 이벤트를 기다릴 자리가 있다. 어떻게 기다리는지는 티켓이 정한다.

### 실행은 앱이 소유한다 — 연결에 묶이지 않는다

- **채널은 실행을 요청의 태스크 밖에서 몬다. 앱의 수명(lifespan)이 실행들을 소유하고, 요청은 그 실행의 이벤트를 받아 흘릴 뿐이다.** 끊김에서 취소되는 것은 요청 범위의 태스크 그룹 안에 있는 것뿐이다 — 라우트 제너레이터는 `CancelledError`를 받지만 요청 밖에서 만든 태스크는 끝까지 간다(2026-09-24 프로브, 미들웨어 둘 뒤에서도 같다).
- **`BaseHTTPMiddleware` 둘(`AssignRequestId`, 인증)이 스트림 앞에 서도 스트림은 모이지 않는다.** 같은 프로브에서 첫 프레임이 제너레이터가 다음으로 가기 전에 `send`에 도착했고, 두 미들웨어가 붙인 헤더가 스트림 응답에 있었다. 인증 미들웨어가 일반형이 되며 기반 클래스를 바꾸더라도 판정은 둘째 구동자의 조각별 전달 테스트가 한다.
- **실행은 받는 쪽을 기다리지 않는다.** 받는 쪽이 느리면 그 실행의 이벤트가 쌓이고, 떠나면 버린다. 버려도 잃는 것이 없다 — 이미 트레이스에 있다. 실행은 트레이스에 계속 쓴다.
- **앱이 멈출 때 클라이언트가 떠난 실행은 기다리지 않고 취소한다**(ADR 0014). `CancelledError`는 `_drive`의 `except Exception`을 지나치므로 `run_failed`가 붙지 않고 그 실행은 결말 없음이다. 트레이스 쓰기가 동기라 취소가 반쪽 줄을 남기지 않는다. 연결이 남아 있는 실행을 어떻게 하는지는 ADR이 정하지 않았고, uvicorn이 멈추는 순서에 달려 있다(Further Notes). (2026-09-24 닫힘: 유예 뒤에 연결이 남은 실행도 취소한다, ADR 0014의 이력)
- **도구 연결은 실행의 태스크 안에서 열리고 닫힌다.** `_drive`가 `async with`로 연결을 연 채 도는 구조 그대로라, anyio 취소 범위를 쓰는 MCP 어댑터의 진입과 종료가 같은 태스크에 있다(`.claude/rules/tests.md`가 픽스처에 대해 경고한 그 조건).
- **워커는 하나다.** `uvicorn.run`에 앱 객체를 넘기는 지금 방식이 그것을 보장한다(워커가 여럿이면 uvicorn이 import 문자열을 요구하며 시작 실패로 끝난다, ADR 0014). 동시 재개 불변식이 기대는 "한 이벤트 루프"가 이것이다.

### 인증 — 토큰 둘

- **채널 토큰은 `AGENT_OS_CHANNEL_TOKEN`이고 환경변수로만 들어온다**(ADR 0015). `main.py`가 읽어 `create_app`에 넘긴다. 공백만 있는 토큰을 없는 것으로 보는 규칙, 통과한 토큰을 다듬지 않고 넘기는 규칙, 상수 시간 비교는 관리 토큰과 같다.
- **`create_app`도 빈 토큰과 같은 두 토큰을 거부한다.** 지금 빈 관리 토큰을 거부하는 자리에서다. 진단과 종료 코드로 운영자에게 말하는 것은 `serve`의 몫이고, 여기서는 그런 앱이 만들어지지 않는다는 것까지다.
- **채널 토큰은 아무 멈춘 실행에나 결정을 낼 수 있다.** 신원이 하나라 실행마다 소유자를 가를 기준이 없다(ADR 0015). CLI에서 시작한 실행을 HTTP로 승인하는 것도, 그 반대도 된다(`--traces`가 같은 디렉터리를 가리킬 때).
- **노출.** 채널 스트림은 그 실행의 이벤트를 마스킹 범위 그대로 싣는다. 관리 API의 트레이스 상세와 같은 노출이고 같은 열린 문제다(ADR 0009의 2026-09-22 이력 "관리 API가 트레이스를 내보내도 마스킹 범위는 인자뿐이다"). 경계는 채널 토큰이 맡는다. 원칙 V와의 긴장은 관리 API 명세가 적은 그대로이고 이 기능이 넓히지도 좁히지도 않는다.

### 주체와 승인자

- **채널은 주체 하나를 실행의 주체와 결정의 승인자로 함께 쓴다**(ADR 0015). 그 값은 `create_app`이 받는다(구현 세부, 아래 `create_app` 절). `main.py`가 CLI에서 하듯 `serve` 프로세스의 OS 사용자로 채운다. 채널이 스스로 OS 사용자를 읽지 않는다 — 신원의 출처를 정하는 것은 조립이다.
- **요청에서 주체도 승인자도 받지 않는다**(ADR 0015). 본문에 그 필드가 없고, 오면 무시하지 않고 422다. 이 저장소의 모델이 전부 추가 필드를 받지 않는 관례를 따른 것이고, 논증은 CLI가 승인에 붙은 사유를 "조용히 버리는 대신 거부한다"고 적은 것과 같다 — 보낸 쪽이 자기 값이 쓰였다고 믿게 두지 않는다.

### `create_app`

- **모델과 도구와 시계 포트, 채널 토큰을 받는다**(ADR 0010의 2026-09-24 이력). **주체도 받는다** — 이것은 그 이력의 목록에 없고, ADR 0015가 정한 출처("`serve` 프로세스의 OS 사용자")를 조립 층이 채우는 자리라 구현 세부로 적는다. 관리 라우터는 여전히 플러그인과 트레이스 포트만 받는다 — "관리 라우터는 도구 포트를 받지 않는다"는 그대로다.
- **트레이스 포트 하나를 관리와 채널이 함께 쓴다.** 채널에서 일으킨 실행이 같은 서버의 관리 API에 바로 보인다. 쓰는 중인 실행의 상세는 어댑터가 온전한 줄까지 돌려준다(2026-09-23 쓰는 중인 마지막 줄).
- **라우터를 마운트하는 자리는 여전히 `server`다.** 채널 라우터가 하나 는다.

### `main.py` — `serve`

- **`--model`이 는다.** CLI와 같은 규칙(`--model` > `AGENT_OS_MODEL` > 기본값)으로 시작 때 한 번 푼다. API 키는 시작 때 보지 않는다 — CLI와 같이 실행 안의 `run_failed`로 드러난다(ADR 0014).
- **구성 오류는 모아서 한 번에 낸다.** 지금의 둘(관리 토큰 없음, 루프백 아님)에 채널 토큰 없음, 두 토큰이 같음이 는다(ADR 0015). 빈 모델 지정도 같은 목록에 든다 — 모델을 시작 때 푸는 순간 그것도 시작 자리의 구성 오류다. 값은 싣지 않는다.
- **`serve`가 도구 포트(MCP)와 시계를 만들어 넘긴다.** 어댑터를 만드는 자리는 여전히 `main.py`다.
- **"serve 를 먼저 가르는 이유는 관리 API 가 읽기 전용이라 모델이 필요 없기 때문이다"는 더 이상 사실이 아니다**(ADR 0010의 2026-09-24 이력). 이 주석과 그 분기를 고친다.

### `openapi.json`

- **경로 둘과 본문 타입과 `Event`와 `conflict`가 는다.** 최신성 테스트가 그대로 판정한다. 라우트나 모델을 건드린 커밋은 이 파일을 함께 담는다.
- **계약 파일의 머리(제목, 설명)는 계약 티켓이 바꾼다.** (2026-09-24 명세 검토가 티켓 03으로 옮겼다. 위 "계약 티켓" 절의 같은 주석)

### 문서 갱신

- **바뀐 결정을 참조하는 문장을 같이 고치고 옛 표현의 잔존을 저장소 전체에서 grep한다**(`CLAUDE.md` 작업 규약 4). 알려진 자리는 이렇다 — 조립 층 독스트링의 "이번에는 관리 라우터 하나뿐", `create_app`의 "도구 포트를 받지 않는다", 관리 인증 모듈 독스트링의 "`http-channel` 은 이 결정을 물려받지 않는다", CLI 채널 독스트링의 "serve 는 실행을 일으키지 않아", `serve` 도움말의 "관리 API 를 루프백에 세운다", `ServeArgs`의 "관리 API 를 세우는 데 필요한 값 넷", `README.md`의 트리.
- **`plan.md`의 목표 배치에는 `http/`와 `channel/http/`가 이미 있다.** 기능 상태가 바뀔 때 행을 고친다.
- **새 층의 rules 파일과 `admin.md`는 계약 티켓에서, 채널에만 걸리는 규칙은 그것을 만드는 티켓에서 고친다.**

## Testing Decisions

좋은 테스트는 **바깥 행동만** 본다. 이 기능에서 바깥 행동은 **HTTP 응답**(상태 코드, 헤더, 에러 봉투, 스트림의 프레임), **트레이스에 남은 이벤트**, **ASGI로 나간 메시지의 순서**(스트림의 수명 셋에서만), **`openapi.json` 파일**, **core가 던지는 예외의 타입**, **`serve`의 종료 코드와 진단과 `create_app`에 넘긴 것**이다. 실행을 소유하는 자료구조, 큐, 태스크의 개수, 미들웨어의 구현은 단언하지 않는다. 테스트 이름은 행동 명세로 쓴다.

원칙 II대로 구현 전에 실패하는 테스트를 쓴다. 테스트가 실패하면 테스트를 고치지 않고 멈춰 보고한다.

### 공용 배관의 이동은 행동을 바꾸지 않는다

계약 티켓의 증명은 **기존 서버 테스트 전부가 import 경로만 바뀐 채 그대로 초록**이라는 것이다. 층 경계는 import-linter가 판정하고, 어댑터가 `http`를 import하면 금지 계약이 깨진다. 새 테스트는 하위 타입과 어휘에만 는다.

### 주 이음매 — `create_app()`과 `ASGITransport` (기존)

`tests/test_server.py`가 프리어 아트다. 가짜는 포트 Protocol을 상속하지 않고 시그니처로 만족하며 픽스처가 포트 타입으로 annotate한다. 모델과 도구와 시계의 가짜는 `tests/core/test_run.py`의 것(`FakeClock`, `FakeTools`, `ToolAwareFakeModel`, 승인 대상을 부르는 에이전트)이 선례다. 채널의 실행은 앱의 수명이 소유하므로 **테스트가 앱의 수명을 직접 연다** — `ASGITransport`는 lifespan을 보내지 않는다. 채널 테스트를 어느 파일에 두는지는 티켓이 정한다.

여기서 판정하는 것:

- `POST /runs`가 `text/event-stream`으로 답하고, 프레임마다 `data:` 하나이며 그 값이 트레이스의 같은 줄과 같은 JSON이다. 프레임에 `event:`·`id:`가 없다
- 스트림이 `run_started`로 시작해 결말 이벤트로 끝나고, 스트림의 이벤트 열이 트레이스의 이벤트 열과 같다
- 승인 대상에서 멈춘 실행의 스트림이 `run_paused`로 끝나고 그 이벤트가 도구와 (마스킹된) 인자를 든다
- 응답에 `X-Request-Id`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`가 있다
- 실행 안의 실패(도구 연결 실패, 모델 실패)는 200 스트림 속 `run_failed`다
- 없는 에이전트는 404 봉투이고 트레이스가 생기지 않는다. 깨진 매니페스트, 없는 mcp, 마스킹과 승인이 겹치는 매니페스트, 진입점 import 실패는 500 봉투이고 역시 트레이스가 없다
- 본문의 `agent`에 `..`나 경로 구분자나 절대 경로가 들어오면 422이고 플러그인 포트가 불리지 않는다. 필드 누락과 추가 필드(주체, 승인자, 모델)도 422다
- `POST /runs/{run_id}/approval`의 승인이 결정 이벤트로 시작해 `run_resumed`를 지나 결말로 끝나는 스트림을 준다. 거부는 `approval_denied`에 사유를 싣고, 거부된 도구는 불리지 않는다
- 재개 스트림에 재생된 사실(멈추기 전의 `run_started`, 모델 호출, 도구 호출)이 다시 나오지 않는다
- 승인에 `reason`이 오면, 거부에 사유가 없거나 공백뿐이면 422이고 `violations`가 그 필드를 가리키며 트레이스에 결정이 쓰이지 않는다
- 없는 실행은 404, 끝난 실행과 실패한 실행과 형식 1 트레이스는 409 봉투이고 `code`가 `conflict`다. 손상된 트레이스는 500이다
- 경로의 `{run_id}`에 `..`나 경로 구분자나 개행이 들어오면 422이고 트레이스 포트가 불리지 않는다(퍼센트 인코딩으로 민다. 관리 테스트와 같은 이유)
- **같은 실행에 결정 둘을 한 루프에서 동시에 보내면 하나는 스트림, 하나는 409다.** 트레이스의 결정 이벤트가 하나이고 승인된 도구가 한 번만 불렸다. 두 요청을 `asyncio.gather`로 보낸다
- 실행과 결정 이벤트의 주체와 승인자가 `create_app`에 넘긴 주체이고, 본문으로 보낸 값은 쓰이지 않는다(422)
- 채널 밖에서(core의 `run()`을 직접 불러) 멈춘 실행을 채널이 재개할 수 있다. CLI에서 시작한 실행을 HTTP로 승인하는 것과 같은 모양이다
- **토큰의 두 방향.** `app.openapi()`가 아는 경로를 전수로 돌며, 채널 경로는 관리 토큰으로 401, 관리 경로는 채널 토큰으로 401이다. allowlist 밖 전부가 토큰 없이 401이라는 지금의 검사는 그대로다
- `/runsx`는 채널 토큰으로 401이고 관리 토큰으로는 401이 아니다(라우트가 없으니 404). 접두사가 경로 조각 단위라는 것이 이 대조다
- `create_app`이 빈 채널 토큰과 같은 두 토큰을 거부한다
- `openapi.json`이 `create_app().openapi()`와 같다. 스트림 항목이 `#/components/schemas/Event`를 가리키고, 결정 본문이 판별자 `decision`의 유니온이며, 두 라우트가 `operation_id`와 에러 문서를 든다
- 에러 코드 어휘가 다섯이고 상태 코드와 1:1이다. 표 밖의 상태 코드가 계열로 접히는 지금의 검사는 그대로다

### 둘째 구동자 — 같은 앱에 ASGI 직접 호출 (스트림의 수명 셋)

프리어 아트는 저장소에 없고 2026-09-24 스크래치 프로브가 모양을 보였다. 가짜 모델이 테스트가 풀어 줄 때까지 기다리게 해 실행의 진행을 테스트가 쥔다. 셋만 잰다. (2026-09-24 명세 검토가 넷째로 "느린 수신자"를 더했다. 위 "이음매" 절의 같은 주석, 티켓 03)

- **조각별 전달.** 미들웨어 둘(`AssignRequestId`, 인증) 뒤에서도 첫 이벤트의 프레임이 `send`에 도착한 뒤에 실행이 다음으로 간다. 모델을 풀기 전에 `run_started` 프레임을 받는다
- **끊겨도 실행은 끝까지.** 첫 프레임을 받고 `receive`가 `http.disconnect`를 낸 뒤 모델을 풀면, 앱 호출은 돌아오고 트레이스는 결말 이벤트로 끝난다. 끊김이 실행까지 전해지지 않는다
- **서버가 멈추면 떠난 실행은 결말 없음.** 실행을 모델 앞에 세워 둔 채 앱의 수명을 닫으면 닫기가 기다리지 않고 돌아오고, 트레이스의 마지막 이벤트가 결말이 아니다(`run_status()`가 결말 없음이다). 연결이 남은 실행은 이 테스트가 재지 않는다 — uvicorn이 멈추는 순서를 먼저 잰다(Further Notes)

### core — 실행 전 실패의 하위 타입 (기존)

`tests/core/test_run.py`가 프리어 아트다.

- 없는 에이전트(`run`)와 없는 실행(`resume`)이 부재 타입이다
- 일시정지가 아닌 실행과 형식 1 트레이스의 `resume`이 재개 불가 타입이다
- 손상된 트레이스, 깨진 매니페스트, 없는 mcp, 마스킹과 승인의 충돌, 결정 이벤트를 쓰지 못함은 둘 중 어느 것도 아닌 `PluginError`다
- 둘 다 `PluginError`의 하위 타입이다. CLI의 기존 테스트가 진단과 종료 코드가 그대로임을 판정한다

### CLI 표면 — `serve` (기존)

인자 파싱은 `tests/channel/cli/test_main.py`, 구성 오류와 `create_app`에 넘긴 것은 `tests/test_main.py`의 `uvicorn_calls` 픽스처가 프리어 아트다. 구성 오류는 서버가 서기 전에 끝나므로 포트를 열지 않는다.

- `serve`가 `--model`을 받는다
- 채널 토큰이 없거나 공백뿐이면, 두 토큰이 같으면 진단을 내고 실패 종료 코드로 끝난다. 서버가 뜨지 않는다
- 관리 토큰 없음, 채널 토큰 없음, 루프백 아님이 한꺼번에 나온다. 진단에 두 토큰의 값이 없다
- 빈 모델 지정이 같은 목록에 든다
- 통과하면 `create_app`이 두 토큰, 모델, 도구와 시계 포트, OS 사용자 이름의 주체를 받는다

### 바깥 이음매 — 실제 `serve`와 실제 모델 (`-m llm`, 이 명세가 정했다)

**하나다.** 실제 `agent-os serve`를 서브프로세스로 빈 포트에 띄우고, 승인 대상을 가진 계산 에이전트(`gatedcalc`)와 실제 stdio 도구 서버를 임시 플러그인 루트에 둔다. `POST /runs`의 스트림이 `run_paused`로 끝나면 그 실행 식별자로 `POST /runs/{run_id}/approval`을 보내고, 재개 스트림이 올바른 답을 담은 `run_finished`로 끝나는 것을 본다. 트레이스는 실행 하나에 파일 하나이고, 결정·`run_resumed`·도구 호출이 그 순서다.

가짜로 증명할 수 없는 것을 한 번에 잰다 — `main.py`의 조립, uvicorn이 실제 소켓으로 SSE를 흘리는 것, 실제 모델이 채널을 지나는 것, 멈춘 실행이 요청을 건너 트레이스로 재개되는 것. 프리어 아트는 `tests/test_main.py`의 두 `-m llm` 테스트(`_cli`로 실제 프로세스를 띄우는 것과, 멈춘 실행을 다른 프로세스가 재개하는 것)다. 키가 없으면 skip이 아니라 실패하고, 기본 실행에서는 빠진다. 테스트가 실패해도 서버 프로세스가 남지 않게 정리한다.

## Out of Scope

- **토큰 단위 스트리밍.** 단위는 이벤트다(용어집의 이벤트 스트림, first-slice 명세의 비목표).
- **취소와 타임아웃.** 결정 없이 취소를 들이면 실행이 도구를 반쯤 부른 채 기록 없이 사라진다(ADR 0014).
- **재접속.** 구독 경로(`GET /runs/{run_id}/events`)와 SSE `id`는 경로와 필드를 더하는 가산 변경이라 지금 계약을 깨지 않는다. 소비자가 있는 `web-widget`이 물려받는다.
- **여러 요청을 한 대화로 잇기.** 실행 하나가 요청 하나다.
- **최종 사용자 인증, CORS, 위젯 설정, 원격 바인딩.** `web-widget`이 물려받는다(ADR 0011·0014·0015). 채널도 루프백만이다.
- **채널에서 승인 요청 읽기(`GET /runs/{run_id}/approval`).** 관찰이 채널로 샌다(ADR 0014).
- **요청마다 모델 고르기.** 채널 토큰을 가진 쪽이 비용을 정하게 되고, 모델 플러그인이 예약만 된 지금 이름을 검증할 기준이 없다(ADR 0014).
- **실행 목록.** 관리 API의 `/traces`가 이미 한다.
- **동시 실행 상한.**
- **프로세스 사이의 경합.** CLI `resume`과 HTTP 승인이 같은 순간 같은 실행에 오면 둘 다 통과한다. 막으려면 어댑터의 조건부 이어쓰기와 파일 잠금이 필요하고 포트가 바뀐다. 알려진 한계다(ADR 0014).
- **실행별 소유자, 4-eyes, 자기 승인 금지.** 신원이 하나라 가를 기준이 없다(ADR 0009, 0015).
- **트레이스의 마스킹 범위 확대.** 열린 문제는 그대로다(ADR 0009의 2026-09-22 이력들).
- **관리 화면의 승인 버튼.** `web-admin`의 것이다. 이 기능은 그 버튼이 결정을 낼 경로까지다.

## Further Notes

- **계약 티켓이 첫 티켓이고 나머지 전부를 막는다.** 원칙 IV를 바꾸는 헌법 개정이 들어 있으므로 그 PR에서 사용자가 바뀐 문언을 본다 — ADR 0016이 승인한 것은 개정의 내용(열거에 `http`가 는다)이지 문언이 아니다.
- **(2026-09-24 티켓을 쪼개기 전의 명세 검토가 아래의 열린 항목을 닫거나 넘겼다. 원문은 그때 열려 있던 상태의 기록이고, 답은 각 항목 첫 문장 뒤의 괄호 주석과 ADR 0014의 이력에 있다.)**
- **재개하려는 실행의 에이전트가 그새 사라졌으면 404가 된다.** (열림 → 2026-09-24 닫힘, ADR 0014의 이력: 재개에서는 부재가 아니라 `PluginError`라 500이다. 티켓 01·04) `resume()`이 트레이스를 읽은 뒤 에이전트 매니페스트를 다시 읽고, 없으면 부재 타입을 던지기 때문이다. 실행은 있으므로 "없는 실행"과 문구로만 갈린다. ADR 0014가 부재에 "없는 에이전트"를 넣은 문장을 그대로 적용한 결과이고 새 결정이 아니다. 명세 검토에서 이 모양이 괜찮은지 본다 — 다르게 가려면 ADR 0014의 이력이다.
- **연결이 남은 스트림이 있을 때 uvicorn이 멈추는 순서는 재 보고 적는다.** (열림 → 2026-09-24 명세 검토가 쟀고 닫힘, ADR 0014의 이력: 기본값은 연결이 끝날 때까지 수명 종료를 미룬다. `serve`가 유예를 넘기고 유예 뒤에 연결이 남은 실행도 취소한다. 티켓 03) ADR 0014가 정한 것은 "서버가 멈출 때 클라이언트가 떠난 실행은 기다리지 않고 취소한다"까지다. 연결된 클라이언트가 있을 때 uvicorn이 그 응답을 기다린 뒤 수명을 닫는지는 이 명세가 확인하지 않았다. 앱의 수명을 다루는 티켓이 구현 전에 재고, 기다린다면 그것이 운영자 스토리 47과 어긋나는지 본다. 연결이 남은 실행을 취소할지 끝까지 둘지와 응답 종료·실행 취소·수명 종료의 순서가 새로 정할 것이 되면 ADR 0014의 이력이다(CodeRabbit PR #67도 같은 자리를 짚었다).
- **계약의 `itemSchema`가 서버가 보내지 않는 `event`·`id`·`retry`를 선택 필드로 광고한다.** (열림 → 2026-09-24 닫힘, ADR 0014의 이력: 광고를 둔다. 서버는 `data`만 보내고 테스트와 rules가 그것을 적는다. 티켓 03) FastAPI의 정형 SSE 스키마가 그렇다. 그대로 두면 생성 클라이언트가 오지 않을 필드를 타입에 갖고, 지우려면 계약을 만드는 쪽에 손을 대야 한다. ADR 0014가 `event:`와 `id:`를 보내지 않기로 한 것과 모순은 아니지만 계약이 약속하는 것과 서버가 하는 것이 어긋난 자리라 명세 검토에서 본다(CodeRabbit PR #67도 같은 자리를 짚었다). 바로 위 3.1·3.2 항목과 같은 자리를 건드리므로 함께 정한다.
- **느린 수신자의 백로그에 상한을 두지 않는다.** (2026-09-24 명세 검토: 계약에 박히지 않아 그대로 넘긴다. 대신 "실행은 받는 쪽을 기다리지 않는다"를 티켓 03의 테스트가 고정한다) 받는 쪽이 느리면 그 실행이 낸 이벤트만큼 쌓이고, 실행이 끝나거나 받는 쪽이 떠나면 사라진다. 여러 실행과 여러 느린 연결이 겹칠 때의 합은 동시 실행 수에 비례하고, 그것은 범위 밖에 둔 동시 실행 상한의 문제다. 연결별 상한과 초과 정책(연결 종료냐 폐기냐)은 새 결정이라 동시 실행 상한과 함께 본다(CodeRabbit PR #67, 보류).
- **계약 파일은 `openapi: 3.1.0`을 선언하지만 스트림 응답은 3.2의 `itemSchema`로 적힌다.** (열림 → 2026-09-24 닫힘: `web-admin`이 생성기를 고를 때 잰다. 받는 쪽인 `plan.md`의 web-admin 행에 적었다) FastAPI가 그렇게 낸다. 3.1 기반 검증기나 생성기는 이 필드를 무시하거나 문서를 거부할 수 있다(CodeRabbit PR #67, 이 명세는 재지 않았다). **먼저 닿는 소비자는 위젯이 아니라 같은 파일에서 클라이언트를 생성하는 슬라이스 3의 관리 화면이다** — 채널 경로가 계약에 실리는 순간 관리 화면의 생성도 그 파일 전체를 읽는다. 그래서 명세 검토에서 둘 중 무엇을 할지 정한다: 채널 라우트 티켓이 계약 파일을 3.1 검증기로 한 번 재 보는 것, 또는 `web-admin`이 생성기를 고를 때 그 파일로 재는 것. 앞엣것이 검증기를 의존성으로 들이면 ADR이다. 이 기능은 계약에 이름 있는 `Event`를 두는 데까지다.
- **fastapi 하한을 올릴 때 lowest-direct 해석으로 한 번 돌려 본다.** 다른 하한도 실제 사용을 따라가지 않는지 알 수 있다(일지 2026-09-24-03 회고 4, 기록만).
- **태그로 두 면을 가르는 것은 정하지 않았다.** (2026-09-24 받는 쪽인 `plan.md`의 web-admin 행에 적었다) 지금 계약에 태그가 없고, 생성기 가운데 태그로 클래스를 가르는 것이 있어 나중에 더하면 생성된 코드의 모양이 바뀐다. 슬라이스 3·4가 생성기를 고를 때 본다.
- **본문 `request`의 크기 상한은 두지 않는다.** 루프백과 토큰 뒤이고 CLI도 두지 않는다. 동시 실행 상한과 함께 필요가 증명되면 본다.
- **PR 직전에는 `coderabbit-review`를 돌린다**(일지 2026-09-22-07). PR과 병합은 사용자가 말할 때다.
- **환경 규약은 그대로다.** 파이썬 명령 앞에 `PYTHONUTF8=1`, Git Bash에서는 `uv run python`, ini 계열 파일은 ASCII만. 검사 도구가 내가 생각하는 것을 실제로 봤는지 먼저 확인한다.
