# 04: `POST /runs/{run_id}/approval` — HTTP로 결정을 내고 재개된 실행의 스트림을 받는다

**What to build:** 승인자가 멈춘 실행의 식별자와 결정 하나(`{"decision": "approve"}` 또는 `{"decision": "deny", "reason": "…"}`)를 보내면 실행이 재개되고, 응답으로 재개된 실행의 스트림이 03과 같은 모양으로 온다. 첫 이벤트는 그 결정이고, 멈추기 전에 이미 본 사실은 다시 나오지 않는다. 식별자를 잘못 적은 것(404)과 이미 누군가 결정한 것(409)이 갈리고, 같은 서버에 같은 실행의 결정이 둘 동시에 와도 하나만 받아들여진다. CLI에서 시작한 실행을 HTTP로 승인하는 것도 된다. 슬라이스 3의 승인 버튼이 결정을 낼 자리가 이것이다 — 내용은 관리 API로 보고 결정은 채널로 낸다.

**동시 재개의 불변식을 이 티켓의 테스트가 처음 고정한다.** 지금 그것을 지키는 것은 설계가 아니라 우연이다. `resume()`의 첫 걸음에 `await`가 없을 뿐이다. 트레이스 쓰기를 비동기로 바꾸거나 스레드로 보내는 변경은 성능 개선처럼 보이지만 승인된 도구를 두 번 실행하게 만든다. 그런 변경이 들어오는 순간 이 테스트가 깨져야 한다.

근거는 ADR 0014와 그 2026-09-24 이력 "재개에서 트레이스가 가리키는 에이전트가 없으면 부재가 아니라 `PluginError`다", ADR 0009와 그 이력, ADR 0015.

**Blocked by:** 03

**Status:** done

- [x] 본문이 `decision`을 판별자로 한 유니온이고, 계약에서 이름 있는 컴포넌트다. 허가와 거부가 같은 모양의 선택 필드로 섞이지 않는다
- [x] **판별자 `decision`에도 기본값을 두지 않는다.** 두면 요청 본문의 스키마에서 `decision`이 required에서 빠진다. 계약은 "선택"이라 말하는데 서버는 판별자 없는 본문을 `union_tag_not_found`로 거부한다(명세 검토의 프로브). 03과 같은 규칙이다
- [x] 승인에 `reason`이 오면 422다. 거부의 사유가 없거나 공백뿐이어도 422다. 어느 쪽이든 `violations`가 그 필드를 가리키고 트레이스에 결정이 쓰이지 않는다. core의 `Deny`가 한 번 더 막는다
- [x] **거부 사유는 CLI처럼 앞뒤 공백을 다듬어 기록한다.** CLI의 결정 해석은 다듬은 사유를 넘기는데, pydantic의 문자열은 공백을 그대로 둔다. 두 채널에서 같은 결정이 같게 기록되어야 한다(스토리 27, 명세 검토). 테스트 한 줄이 고정한다
- [x] 결정 본문에 승인자 필드가 오면 422다. 결정 이벤트의 승인자는 `create_app`에 넘긴 주체다(ADR 0015)
- [x] 경로의 `{run_id}`는 `verbatim` 변환기와 실행 식별자 패턴으로 받는다. `..`나 경로 구분자나 개행이 들어오면 422이고 트레이스 포트가 불리지 않는다. 테스트는 퍼센트 인코딩으로 민다. 관리의 `/traces/{run_id}`와 같은 규칙이고 같은 이유다
- [x] 상태 코드는 아래와 같다. 어느 경우든 트레이스에 결정이 쓰이지 않는다
  - 없는 실행: 404
  - 끝난 실행, 실패한 실행, 결말 없는 실행, 형식 1 트레이스: 409 봉투이고 `code`는 `conflict`
  - 손상된 트레이스: 500
  - **트레이스가 가리키는 에이전트가 그새 사라진 실행: 500이고 404가 아니다**(ADR 0014의 2026-09-24 이력)
- [x] **채널은 포트나 `run_status()`로 실행의 상태를 먼저 확인하지 않는다.** 부재와 재개 불가는 core의 `resume()`이 던진 타입을 표가 옮긴다. 먼저 확인하면 형식 1 판정(`RESUMABLE`)이 core 밖으로 새는데, 그것이 ADR 0014가 거부한 안이다(스토리 67). 위의 상태 코드 목록은 먼저 확인하는 구현으로도 초록이라서 이 기준은 리뷰가 확인한다
- [x] 승인의 스트림은 결정 이벤트로 시작해 `run_resumed`를 지나 결말로 끝난다. 거부는 `approval_denied`에 사유를 싣고, 거부된 도구는 불리지 않는다
- [x] 재개 스트림에 재생된 사실(멈추기 전의 `run_started`, 모델 호출, 도구 호출)이 다시 나오지 않는다. 재개 뒤 첫 호출이 멈춘 그 호출이 아니면 스트림이 `run_resumed` 없이 `run_failed`로 끝난다. core가 지키는 것이 채널을 지나도 그대로임을 한 번 본다
- [x] **같은 실행에 결정 둘을 한 루프에서 동시에 보내면 하나는 스트림, 하나는 409다.** 트레이스의 결정 이벤트는 하나이고 승인된 도구는 한 번만 불린다. 두 요청을 `asyncio.gather`로 보낸다. 테스트 이름이 불변식을 말한다. 이 불변식의 범위는 이벤트 루프 하나(워커 하나)다. **프로세스 사이의 경합은 알려진 한계이고 이 티켓이 막지 않는다.** CLI `resume`과 HTTP 승인이 같은 순간 같은 실행에 오면 둘 다 통과한다. 막으려면 어댑터의 조건부 이어쓰기와 파일 잠금이 필요하고 포트가 바뀐다(ADR 0014, 명세 Out of Scope, PR 직전 CodeRabbit)
- [x] 재개가 다시 `run_paused`로 끝나면 같은 경로로 둘째 결정을 내 끝까지 간다. 한 턴에 승인 대상이 둘인 에이전트로 잰다(스토리 36)
- [x] 채널 밖에서(core의 `run()`을 직접 불러) 멈춘 실행을 채널이 재개한다. CLI에서 시작한 실행을 HTTP로 승인하는 것과 같은 모양이다
- [x] `operation_id`와 본문 타입의 이름을 이 티켓이 짓는다. 조건은 넷이다
  - `operation_id`를 손으로 준다
  - 본문과 결정의 유니온이 이름 있는 컴포넌트다
  - 결정의 멤버 이름이 core의 `Approve`·`Deny`·`Decision`과 겹치는지 보고 정한다. core의 셋은 pydantic 모델이 아니라서 계약에는 나오지 않는다. 겹치게 두면 한 저장소에서 같은 이름이 두 층의 다른 타입을 가리킨다. 가르면 용어집의 "결정"과 계약의 이름이 멀어진다. 파이썬 쪽 비용은 import 별칭뿐이다
  - **기존 계약 컴포넌트와 겹치지 않는다.** 예를 들어 멤버를 `ApprovalGranted`·`ApprovalDenied`로 지으면 기존 이벤트 컴포넌트가 `-Input`·`-Output`으로 갈라지고 `Event`·`TraceEvent`의 참조도 따라 바뀐다(명세 검토의 프로브)

  이름은 `openapi.json`에 박히므로 PR에서 사용자가 본다
- [x] 03이 만든 계약 이름 테스트를 결정 유니온까지 넓힌다. 기존 컴포넌트 이름 집합이 그대로이고, `-Input`·`-Output`이 없으며, `Event`와 `TraceEvent`가 같은 멤버 컴포넌트를 가리킨다(스토리 22)
- [x] 라우트의 에러 문서는 401, 404, 409, 422, 500이다. 409는 이 라우트에만 있다
- [x] 채널에는 승인 요청을 읽는 경로가 없다(ADR 0014). 시작한 쪽은 스트림 마지막의 `run_paused`에서, 운영자는 관리 API에서 본다
