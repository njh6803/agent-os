# 03: `POST /runs` — HTTP로 실행을 일으켜 그 이벤트 스트림을 받는다

**What to build:** 개발자가 에이전트 이름과 요청 하나를 채널 토큰과 함께 보내면 실행이 일어나고, 응답으로 그 실행의 이벤트가 생기는 대로 `text/event-stream`으로 온다. 프레임 하나가 트레이스 한 줄과 같은 JSON이고, 스트림은 `run_started`로 시작해 결말 이벤트를 보낸 뒤 닫힌다. **실행은 연결에 묶이지 않는다** — 클라이언트가 떠나도, 느려도 실행은 끝까지 가서 트레이스에 남고, 떠난 쪽은 나머지를 같은 서버의 관리 API 상세에서 본다. 실행이 시작되기도 전에 실패하면 상태 코드와 관리 API와 같은 에러 봉투로 답한다. 운영자는 `agent-os serve` 하나로 관리 API와 채널을 함께 세우고 모델을 시작 때 한 번 정한다.

**가장 큰 티켓이고 더 줄일 수 없다.** 떼어 낼 수 있어 보이는 조각마다 그 사이의 main이 조용히 거짓이 된다(명세 검토의 질문 2).

- 실행 소유를 미루면: 라우트가 요청 태스크에서 `run()`을 흘리는 가장 단순한 구현이 된다. 그러면 끊김에서 실행이 기록 없이 취소된다(ADR 0014가 거부한 모양).
- 첫 이벤트 대기를 미루면: 없는 에이전트를 부른 요청이 200으로 시작한 뒤 끊긴 스트림이 된다.
- 유예를 미루면: `serve`의 종료가 연결된 실행을 제한 없이 기다린다.
- `serve` 배선을 미루면: `create_app`의 필수 인자가 느는 순간 `main.py`가 깨진다.

스트림의 수명 넷은 둘째 구동자로만 잴 수 있고, 그 구동자는 실행을 일으키는 라우트가 있어야 쓸 수 있다.

근거는 ADR 0014와 그 2026-09-24 이력 셋, ADR 0015, ADR 0010의 2026-09-24 이력 "채널이 붙으며 앱의 인자와 에러 어휘가 는다", 명세의 "이음매"·"스트림"·"실행은 앱이 소유한다"·"`create_app`"·"`main.py` — `serve`" 절.

**Blocked by:** 02

**Status:** ready-for-agent

### 스트림

- [ ] `POST /runs`가 본문 `{agent, request}`를 받아 `text/event-stream`으로 답한다. 프레임마다 `data:` 하나이고, 그 값이 트레이스의 같은 줄과 **문자열로** 같다. 파싱한 뒤 비교하면 두 직렬화(트레이스는 이벤트 하나, 스트림은 유니온)가 어긋나는 날을 놓친다. 프레임에 `event:`·`id:`가 없다
- [ ] 스트림이 `run_started`로 시작해 결말 이벤트로 끝나고, 스트림의 이벤트 열이 트레이스의 이벤트 열과 같다. 승인 대상에서 멈춘 실행의 스트림은 `run_paused`로 끝나고, 그 이벤트가 도구와 마스킹된 인자를 든다
- [ ] 응답에 `X-Request-Id`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`가 있다. 모델이 조용한 동안 keepalive 주석이 나간다. 간격을 줄여 잰다. 첫 이벤트를 기다리는 방식을 이 티켓이 정하는데, keepalive를 잃을 수 있는 유일한 자리가 거기라서 이 테스트가 그 자리를 닫는다(명세 검토)
- [ ] 실행 안의 실패(도구 연결 실패, 모델 실패)는 200 스트림 속 `run_failed`다
- [ ] 채널에서 일으킨 실행이 같은 앱의 관리 API 목록과 상세에 바로 보인다. 트레이스 포트 하나를 두 면이 함께 쓴다

### 실행 전 실패와 입력

- [ ] **응답은 첫 이벤트를 받은 뒤에 시작한다.** 첫 이벤트 전의 예외는 기존 예외 핸들러를 지나 봉투가 된다. 없는 에이전트는 404 봉투이고 트레이스가 생기지 않는다
- [ ] 다음 넷은 500 봉투이고 역시 트레이스가 없다: 깨진 매니페스트, 없는 mcp, 마스킹과 승인이 겹치는 매니페스트, 진입점 import 실패
- [ ] **500 테스트는 상태 코드만 보지 않고 봉투의 `message`가 그 `PluginError`의 문구인지도 단언한다.** 제너레이터 안에서 첫 yield 전에 던지면 예외 그룹으로 감싸져 표의 마지막 갈래(고정 문구의 500)로 간다. 상태 코드만 보면 그 구현도 초록이다(명세 검토의 프로브)
- [ ] 본문의 `agent`가 `sdk`의 플러그인 이름 패턴을 만족하지 않으면 422이고 플러그인 포트가 불리지 않는다. `..`, 경로 구분자, 절대 경로가 그런 값이다. 필드 누락도 422이고, 추가 필드(주체, 승인자, 모델)도 무시하지 않고 422다. `violations`가 그 필드를 가리킨다. `request`는 문자열이면 된다
- [ ] **요청 본문 모델에는 기본값 있는 필드를 두지 않는다.** 직렬화 스키마의 required 규칙은 요청 본문(검증 스키마)에 효과가 없다. 그래서 기본값이 있으면 계약은 "선택"이라 말하고 서버는 필수로 받는다(명세 검토의 프로브). 본문 모델의 독스트링은 한 줄이다
- [ ] **422의 서버 기록 한 줄은 위치와 문구만 싣고 입력값을 싣지 않는다.** 지금은 검증 오류를 문자열 그대로 적어 본문 원문이 기록에 간다. 명세 검토가 쟀다: 추가 필드에 넣은 값이 그대로 찍혔다. 관리 API의 입력은 짧은 식별자였지만 채널의 본문은 프롬프트다. 공용 층의 규칙이라 관리 API에도 함께 걸린다(원칙 V). 테스트가 기록에 입력값이 없음을 잰다

### 실행은 앱이 소유한다

- [ ] 실행은 앱의 수명(lifespan)이 소유하고, 요청은 그 실행의 이벤트를 받아 흘릴 뿐이다. `ASGITransport`는 lifespan을 보내지 않으므로 채널 테스트가 앱의 수명을 직접 연다
- [ ] 도구 연결은 실행의 태스크 안에서 열리고 닫힌다. MCP 어댑터의 anyio 취소 범위가 진입과 종료를 같은 태스크에서 본다
- [ ] **둘째 구동자.** 같은 앱을 ASGI로 직접 부른다. `receive`가 원하는 때에 끊김을 내고, `send`가 받은 메시지를 순서대로 기록한다. 가짜 모델은 테스트가 풀어 줄 때까지 기다려서, 실행의 진행을 테스트가 쥔다. 이 구동자를 쓰는 곳은 아래 넷뿐이다(HTTP 층 rules의 예외):
  - [ ] **조각별 전달.** 미들웨어 둘 뒤에서도 모델을 풀기 전에 `run_started` 프레임이 `send`에 도착한다
  - [ ] **끊겨도 끝까지.** 첫 프레임 뒤 끊김을 내고 모델을 풀면, 앱 호출은 돌아오고 트레이스는 결말 이벤트로 끝난다
  - [ ] **느린 수신자.** `send`를 막아 둔 채 모델을 풀어도 트레이스가 결말로 끝난다. 실행은 받는 쪽을 기다리지 않는다. 크기가 제한된 큐에 기다리며 넣는 자연스러운 구현은 이것을 어기면서 나머지 테스트를 모두 통과한다(명세 검토)
  - [ ] **서버가 멈추면 결말 없음.** 실행을 모델 앞에 세워 둔 채 앱의 수명을 닫으면, 닫기가 기다리지 않고 돌아오고 `run_status()`가 결말 없음이다
- [ ] `serve`가 uvicorn에 유예(`timeout_graceful_shutdown`)를 넘긴다(ADR 0014의 2026-09-24 이력 "서버를 멈출 때 연결이 남은 실행도 유예 뒤에 취소한다"). 유예의 길이는 이 티켓이 정한다. 연결된 스트림이 있을 때의 순서는 앱의 수명을 직접 닫는 테스트로 잴 수 없으므로 조립 테스트가 넘긴 값을 판정한다

### 계약

- [ ] 스트림 항목이 `#/components/schemas/Event`를 가리킨다. 채널 쪽에 `sdk`의 `Event`를 가리키는 이름 있는 별칭을 두고, `sdk`는 바뀌지 않는다. `TraceEvent`는 멤버 열의 평평한 `oneOf` 그대로이고, 두 유니온이 같은 멤버 컴포넌트를 가리킨다. 익명 `Streamitem …` 제목이 계약에 없다. **테스트가 잰다** — 기존 컴포넌트 이름 집합이 그대로이고 새 이름만 늘었으며, `-Input`·`-Output`이 없고, `Event`와 `TraceEvent`가 같은 멤버 컴포넌트를 가리킨다(스토리 22). `Event` 컴포넌트가 생기는 이 티켓에서 재야 04까지의 사이에 테스트 없는 주장으로 남지 않는다. 04가 결정 유니온을 더하며 같은 테스트를 넓힌다
- [ ] 계약의 `itemSchema`에는 FastAPI의 정형 `event`·`id`·`retry`가 선택 필드로 실린 채 둔다(ADR 0014의 2026-09-24 이력 "계약의 스트림 항목 스키마는 FastAPI의 정형 그대로 둔다"). 서버는 `data`만 보낸다는 것과 그 이유를 HTTP 층의 rules 파일에 적는다
- [ ] 라우트에 `operation_id`를 손으로 주고 에러 문서(401, 404, 422, 500)를 단다. 409는 이 라우트에 없다. 본문 타입의 이름은 이 티켓이 짓는다. 기존 계약의 컴포넌트 이름과 겹치지 않는다 — 겹치면 기존 컴포넌트가 `-Input`·`-Output`으로 갈라진다
- [ ] 계약 파일의 제목과 설명이 관리와 채널을 함께 말한다(ADR 0010의 2026-09-24 이력). 01이 미룬 자리다
- [ ] `openapi.json`이 `create_app().openapi()`와 같다
- [ ] **토큰의 두 방향을 전수로 잰다.** `app.openapi()`가 아는 경로를 돌며, 채널 경로는 관리 토큰으로 401, 관리 경로는 채널 토큰으로 401이다. 방향마다 열거가 비어 있으면 실패한다. 02가 구체 경로로 잰 것을 전수로 넓힌다

### 조립

- [ ] `create_app`이 모델·도구·시계 포트와 주체를 받는다. 관리 라우터는 여전히 플러그인과 트레이스 포트만 받는다. 실행의 주체는 `create_app`에 넘긴 것이고 본문에서 받지 않는다(ADR 0015)
- [ ] `serve`가 `--model`을 받는다. 모델은 시작 때 한 번 푼다. 순서는 `--model` > `AGENT_OS_MODEL` > 기본값이고 CLI와 같은 규칙이다. 빈 모델 지정은 다른 구성 오류와 같은 목록에 들어 한 번에 나온다. API 키는 시작 때 보지 않는다 — CLI처럼 실행 안의 `run_failed`로 드러난다
- [ ] `serve`가 도구 포트(MCP)와 시계를 만들고, 주체를 OS 사용자로 채워 넘긴다. CLI가 하는 것과 같다. 채널이 스스로 OS 사용자를 읽지 않는다 — 신원의 출처를 정하는 것은 조립이다
- [ ] 바뀐 결정을 참조하는 문장을 같이 고친다:
  - 조립 층 독스트링의 "이번에는 관리 라우터 하나뿐"
  - `create_app` 독스트링과 `.claude/rules/admin.md`의 "도구 포트를 받지 않는다"
  - `main.py`의 "serve 를 먼저 가르는 이유는 관리 API 가 읽기 전용이라 모델이 필요 없기 때문이다"와 그 분기
  - `_serve` 독스트링의 "관리 API 를 세운다"
  - CLI 채널 독스트링의 "serve 는 실행을 일으키지 않아"
  - `serve` 도움말의 "관리 API 를 루프백에 세운다"
  - `ServeArgs`의 "관리 API 를 세우는 데 필요한 값 넷"
  - `tech.md` 테스트 행의 이음매(둘째 구동자)
  - `README.md`의 트리

  옛 표현의 잔존을 저장소 전체에서 grep해 0인지 본다
- [ ] HTTP 층 rules 파일의 `paths`가 채널 HTTP 모듈과 그 테스트를 덮는다. 01에서는 대상이 없어 지침 검사가 막았던 glob이다. 채널에만 걸리는 규칙은 이 티켓이 적는다
- [ ] lowest-direct 해석으로 한 번 돌린다. fastapi 하한에서 `fastapi.sse`가 서는지, 다른 하한도 실제 사용을 따라가는지 본다(명세 Further Notes, 기록만). `fastapi.sse`를 처음 import하는 것이 이 티켓이라 01이 아니라 여기서 잰다
- [ ] 원칙 III를 지킨다. 스트림과 ASGI를 다루는 코드가 타입 우회의 첫 선례가 되지 않는다. 필요해 보이면 멈춰 보고한다
- [ ] 검사 넷이 초록이다
